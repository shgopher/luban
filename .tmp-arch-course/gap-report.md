### C-2 · 4R 架构定义（Rank / Role / Relation / Rule）与静态 / 动态架构图

**为什么算缺。** 实际执行的 grep：

```bash

```

`4R` 零命中；`Rank` 只命中 `v2/L2-架构风格/30-微服务/30.7-跨服务查询与数据聚合.md:42` 的排序字段（`Rank int // 越小越新`）；`静态图` 只命中 `v2/附录/83-架构文档与表达/83.7-Agent画架构图.md:24`，讲的是 HTML/SVG 导出格式，与 4R 无关。库里的视图体系是 C4（`83.1` 上下文/容器/组件/代码）加 4+1 的零散引用（`83.1:123` 一句「部署图（C4 有 Deployment 图作为补充）」），**没有把图分成「静态结构」与「动态序列」两类来讨论数量、读者与产出时机**。

**课程原文给了什么（第 1 讲 + 第 51 讲）。**

- 第 1 讲把架构重定义为：*「软件架构指软件系统的顶层（Rank）结构，它定义了系统由哪些角色（Role）组成……」*，`4R 是指 4 个关键词：Rank，Role，Relation 和 Rule`。
- 第 51 讲把这套定义直接落到画图上：`第一步，明确Rank`（不要事无巨细把一个大系统画在一张图里）；`我把描述Role和Relation的架构图称为静态架构图，描述Rule的系统序列图称为动态架构图`；数量经验是 `静态架构图……一般是1～2张`、`动态架构图是一般是多张，因为核心场景数量不止一个`。

这条缺的后果很具体：`58.6` 的备选方案、`58.3` 的架构评审、`83.2` 的制图规范各自都在讨论「画什么」，但没有一句共同的定义能回答「这张图是 Rank 还是 Rule、该有几张」。

**建议补到哪一章哪一节。** 新增 `v2/附录/83-架构文档与表达/83.8-4R 架构定义与静态动态视图.md`（与下面的 B-1 合成一页更省），结构：① 4R 一句话 + 四个关键词各问什么；② 静态架构图（Role+Relation，1–2 张）与动态架构图（Rule，序列图，多张）的分工表；③ 与 C4、4+1 的取舍对照（`83.1` 的 C4 负责缩放级别，4R 负责「一张图回答一个问题」）；④ 反模式：把 Rank 画成部署图、把 Rule 画成静态框线图。同时在 `83.1` 与 `83.2` 开头各加一句交叉引用。

**现有页面写了什么。** `26.6:17` 给了另一套粒度：*「三个粒度：包 / 模块 / 服务」*，判据是边界破坏成本（包=import、模块=版本、服务=网络）；`58.8:33` 给了模块与框架的关系：*「**着眼于模块而不是框架**——框架是易变的业务流、可复用性更低」*；`82.5:56` 提到「子系统、模块、类」可以继续按模型/接口/实现三层展开。

**怎么补。** 与 C-2 合写一页 `83.8`（或独立 `v2/附录/82-架构设计方法/82.0-架构的定义与六个概念.md`）：第一段给顶层结构定义，第二段给六概念两两对照表（系统/子系统、模块/组件、框架/架构），第三段用「逻辑视角 vs 物理视角」解释「为什么同一个系统有多套正确架构」，并指到 `26.6` 的三粒度继续往下读。

### B-24 · 中台批判（加餐）的核心论点

**现有页面写了什么。** `78.2:70–79` 有「中台为什么会失败」四条根因（为共享而共享 / 边界画错 / 组织没配套 / 考核错位），并给出一句非常锋利的判据：*「判断一个中台该不该存在，只问一句：**去掉它，两条业务线会重复造多少东西？**」*，还划了「管到能力、不管策略」的边界。结构上比课程更整齐。

**缺哪一半。** 课程加餐的四个核心论点，库里一个都没有：

1. **中台按 KPI 分配资源 → 抱大业务大腿**：*「中台抱大业务的大腿，小业务抱中台的大腿，因为中台也是有KPI的……中台的KPI怎么来？当然是大部分来源于支持的业务了」*；小业务被拒只需要一句「你这个业务不通用」，且「不会存在仲裁委员会」，即使判为共性也会「排在很后面……几个月半年」。
2. **共性需求不可持续提炼**：0→1 建设时有多个样本可分析，建成后「中台和业务方天然存在对共性需求的不同诉求」——业务方希望自己的需求算共性（让中台出人），中台希望等多家都提了再抽象。
3. **轮子会换 → 业务被动架构演进**：*「中台确实把轮子造好了，但是它每隔一段时间就会把轮子换一遍」*，且不长期维护老轮子；中台演进频率 = 多业务演进叠加，和「技术平台（存储、消息队列）演进不影响业务」根本不同。
4. **只能是某类业务的中台**：*「实际上应该叫『电商中台』『支付中台』……而不应该是『阿里中台』」*——跨业务域复用不成立。

**怎么补。** 在 `78.2` 的「中台为什么会失败」之后加一节「中台的四个反例」，直接用上面四条（每条配一句课程原话 + 一句本库判据），并在 `78.2` 反模式表里加两行：「用考核接入数量代替业务效果」「向跨域的中台要复用」。若想保持 78.2 篇幅，可独立成 `v2/组织/78-技术组织设计/78.6-中台批判的四个反例.md`，在 78.2 与 `77.2`（中台不是团队类型）互链。

## 结论

计数：**A = 16 / B = 6 / C = 2**。这套库对《从0开始学架构》的吸收集中在校验「有数字、有判据」的部分（可用性算术、FMEA、备选方案、环评、三原则、异地多活、幂等），缺的几乎全是**结构性、视图性、清单性**的知识点——这也符合它的体裁：章节按质量属性与组件组织，天然不产出「一张总表」。

最值得补的 5 个点（排序依据 = 缺口大小 × 可复用性）：

1. **C-2 · 4R 定义与静态/动态架构图**（新增 `83.8`）。缺口最大的一处：它不是某个专题的缺失，而是全书视图语言的缺省位——`83.x` 的制图规范、`58.6` 的备选方案、`58.3` 的评审都在讨论「画什么」，却没有共同定义。补一页，被引用面最广。
2. **B-1 · 顶层结构与六概念**（与 C-2 合页）。缺口紧随其后，且与 4R 同源（第 1 讲 → 第 51 讲）。它是「架构 vs 框架」「模块 vs 组件」这类高频争论的止血点，工程与教学双重复用。
3. **C-20 · 互联网架构模板五层**（新增第 35 章）。全库唯一能给读者「从零起步的骨架」的东西，且与 `84.x` 案例形成「先有模板、再看案例」的互补；没有它，`82.1` 的推导只能从需求裸推，门槛偏高。
