### 22丨想成为架构师，你必须知道CAP理论

- **核心结论**
  CAP 定理（CAP theorem）又称布鲁尔定理，是布鲁尔 2000 年在 ACM PODC 上提出的猜想，2002 年由 MIT 的 Gilbert 与 Lynch 证明。它的准确定义要在「第二版」语境下理解：**在一个互相连接并共享数据的节点集合中，涉及读写操作时，C/A/P 只能保证两个**。落到工程上，因为网络不可能 100% 可靠，**P 不是可选项**，所以真实分布式系统只能是 CP 或 AP；所谓 CA 在分布式语境下不成立。

- **完整判据/清单/步骤**
  1. **前提判据（第二版新增，用来筛掉「假 CAP 对象」）**
     - 必须是分布式系统，且满足 `interconnected`（互相连接）+ `share data`（共享数据）→ Memcache 集群不互联不共享数据，**不是** CAP 探讨对象；MySQL 集群互联且做数据复制，**是** CAP 探讨对象。
     - 必须涉及 `write/read pair`（读写操作），不是系统的所有功能 → ZooKeeper 的选举机制**不是** CAP 探讨对象。
  2. **三要素：第一版 vs 第二版逐条辨析**

     | 要素 | 第一版（不严谨、好记） | 第二版（严谨） | 关键差异 |
     |---|---|---|---|
     | C 一致性 | All nodes see the same data at the same time（所有节点同一时刻看到相同数据） | A read is guaranteed to return the most recent write for a given client（对指定客户端，读保证返回最新写结果） | ①节点 node → 客户端 client；②关键词 see → read（节点是「拥有」数据而非「看到」，该用 have）；③第一版强调 same time + same data，第二版不强调 |
     | A 可用性 | Every request gets a response on success/failure（每个请求得到成功或失败响应） | A non-failing node will return a reasonable response within a reasonable amount of time (no error or timeout)（非故障节点在合理时间内返回合理响应） | ①every request → non-failing node（故障节点本来就可能不响应）；②success/failure 太泛 → reasonable response + reasonable time，且明确 no error or timeout |
     | P 分区容忍 | System continues to work despite message loss or partial failure | The system will continue to function when network partitions occur | ①work（运行，返回错误也算 work）→ function（履行职责，与 A 一脉相承）；②说原因 message loss（只是丢包，定义狭隘）→ 说现象 network partitions（丢包/中断/拥塞皆算） |

  3. **第一版 C 为什么不严谨（原文自带的反证）**
     - 事务执行过程中系统本就处于不一致状态（不同节点数据不完全一致），所以「同一时刻拥有相同数据」无法成立；
     - 第二版从 client 读的角度描述就没问题：事务未提交时 client 读不到，失败回滚后 client 也读不到中间数据。
  4. **「合理」不等于「正确」**
     - 应该返回 100 却返回 90：是「成功响应」但**不正确**；可以是**合理**的结果（不是错乱值）。
  5. **为什么必须选 P（推理链）**
     - 网络无法 100% 可靠 → 分区是必然现象 → 若选 CA 放弃 P，则分区时为保 C 必须禁止写入 → 写请求返回 error → 违背 A（A 要求 no error、no timeout）→ **CA 与分布式互斥**。
  6. **CP 与 AP 的判定动作**

     | 选择 | 分区后节点 N2（数据仍是旧值 x，最新值 y 在 N1）的行为 | 牺牲 |
     |---|---|---|
     | CP | 返回 Error，告知「系统现在发生了错误」 | 牺牲 A（可用性） |
     | AP | 直接把本地旧值 x 返回给客户端 | 牺牲 C（一致性），但 x 是「合理」而非「错误」的结果 |

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 2000 年 | 布鲁尔在 ACM PODC 提出 CAP 猜想 |
  | 2002 年 | Gilbert & Lynch 发表证明，猜想升级为定理 |
  | 2014/06、2014/08 | Robert Greiner 前后两版文章（第一篇被标记 outdated，部分中文译文正参考了它） |
  | 三个要素取两个 | CAP 的结论；落到分布式必选 P，故只剩 CP/AP |

- **案例/数据**
  - Memcache 集群（不互联、不共享数据）→ 不属于 CAP 探讨对象；MySQL 集群（互联 + 复制）→ 属于。
  - ZooKeeper 选举机制 → 不是 CAP 探讨对象（不涉及数据读写）。
  - 事务执行中的中间态 → 证明「所有节点同一时刻看到相同数据」不成立，故第一版 C 需修正。
  - 应返 100 实返 90 → 「成功的响应」≠「正确的结果」，故第二版 A 只承诺「合理」。

- **反例与坑**
  - 直接照抄网上第一版定义（或被标记 outdated 的中文译文）→ 定义过泛，无法落地判断。
  - 把「整个系统」当 CAP 的讨论单位 → 见 23 篇，粒度错在系统级。
  - 认为可以选 CA → 分区时禁写会返回 error，与 A 冲突；分布式理论上不存在 CA 架构。
  - 把 P 当作「可牺牲项」→ P 是网络物理事实，不是设计选项。
  - 把 AP 返回的旧值当成「错误数据」→ 原文强调它是「合理」结果，只是不最新。

- **原文金句**
  - 「对于一个分布式计算系统，不可能同时满足一致性（Consistence）、可用性（Availability）、分区容错性（Partition Tolerance）三个设计约束。」
  - 「分布式系统理论上不可能选择 CA 架构，只能选择 CP 或者 AP 架构。」
  - 「这里 N2 节点返回 x，虽然不是一个"正确"的结果，但是一个"合理"的结果，因为 x 是旧的数据，并不是一个错乱的值，只是不是最新的数据而已。」
  - 「第一版虽然不严谨，但非常简单和容易记住。」

- **可迁移到知识库的主题**
  - CAP 两版定义的逐词差异（节点视角 vs 客户端视角；see vs read；work vs function；原因 vs 现象）——可直接做成「术语精度」词条。
  - 「什么是 CAP 探讨的对象」的前置判据（interconnected + share data + write/read pair）。
  - 「合理 ≠ 正确」在可用性定义中的位置：它解释了为什么 AP 系统返回陈旧值不算违约。
  - 「P 为什么不是选项」的推理链（禁写→error→违 A）。

### 23丨想成为架构师，你必须掌握的CAP细节

- **核心结论**
  CAP 是被高度抽象过的理论，落地时必须补上四个细节：**取舍粒度是「数据」不是「系统」；CAP 忽略网络延迟；无分区时可同时满足 CA；「牺牲」不等于什么都不做，要为分区恢复做准备**。同时要把 CAP 与 ACID、BASE 摆正关系：ACID 是数据库事务理论，CAP 是分布式系统设计理论，BASE 是 CAP 中 AP 方案的延伸。

- **完整判据/清单/步骤**
  1. **细节一：CAP 关注的粒度是数据，而不是整个系统**
     - 布鲁尔原文：「C 与 A 之间的取舍可以在同一系统内以非常细小的粒度反复发生，而每一次的决策可能因为具体的操作，乃至因为牵涉到特定的数据或用户而有所不同。」
     - 落地动作：把系统内的数据**按应用场景和要求分类**，每类数据各自选 CP 或 AP，而不是给整个系统贴一个标签。
     - 判据样例：用户账号数据（ID、密码）→ CP；用户信息数据（昵称、兴趣、性别、自我介绍）→ AP。若整系统限 CP，则不符合用户信息场景；整系统限 AP，则不符合账号场景。
  2. **细节二：CAP 是忽略网络延迟的**
     - 隐含假设：事务提交时数据**瞬间**复制到所有节点；现实中复制总要花时间（同机房几毫秒、北京→广州几十毫秒），这段时间内 A、B 节点不一致 → **CAP 的 C 在实践中不可能完美实现**。
     - 推论（原文的关键让步）：对余额、库存这类业务上必须强一致的数据，「理论上要求选择 CP 而实际上 CP 都做不到，**只能选择 CA**」——即**单点写入、其他节点做备份，无法分布式多点写入**。
     - 边界澄清：这不等于该系统不能上分布式；只是「单个用户余额、单个商品库存」不能分布式，系统整体仍可分布式。做法是**按 key 分区**：user id 0~100 存 Node 1、101~200 存 Node 2，Client 按 id 路由；单个用户的读写只落在一个节点。
     - 该设计的代价与收益：节点故障时该节点上的用户不可读写；但把故障影响面从「全部用户」缩到「一部分用户」（如 20%）。
  3. **细节三：正常运行情况下，不存在 CP 和 AP 的选择，可以同时满足 CA**
     - 前提：CP/AP 二选一的前提是**发生了分区**；P 不存在（节点间网络正常）时没有理由放弃 C 或 A。
     - 所以架构设计要同时回答两问：分区发生时选 CP 还是 AP；分区没发生时如何保证 CA。
     - CA 的实现方式也随数据而异：账号数据用**消息队列**实现 CA（能较好控制实时性，实现复杂）；用户信息数据用**数据库同步**实现 CA（某些场景延迟较高，但使用简单）。
  4. **细节四：放弃并不等于什么都不做，需要为分区恢复后做准备**
     - 「牺牲」的误导：让人以为分区期间什么都不做；实际是整个运行周期里大部分时间正常，分区时间很短。
     - 动作 A（选 CP 的数据）：分区期间**记录日志**。例：账号数据选 CP，分区时节点 1 可继续注册、节点 2 注册返回 error；节点 1 把未同步的新用户记录到日志，分区恢复后按日志同步给节点 2，重新达到 CA。
     - 动作 B（选 AP 的数据）：分区期间两边都可改，恢复后**按规则合并**。原文给的三种合并规则：最后修改优先、字数最多优先、完全把冲突报告出来由人工选择。
  5. **ACID 四项（原文定义）**

     | 项 | 原文含义 | 补充 |
     |---|---|---|
     | Atomicity 原子性 | 事务中所有操作要么全部完成、要么全部不完成，不会在中间环节结束；出错回滚到开始前状态 | — |
     | Consistency 一致性 | 事务开始前和结束后，数据库的完整性没有被破坏 | 指**数据完整性**，非分布式一致性 |
     | Isolation 隔离性 | 允许多个并发事务同时读写修改；防止交叉执行导致不一致 | 四级：读未提交、读提交、可重复读、串行化 |
     | Durability 持久性 | 事务处理结束后修改永久，即便系统故障也不丢失 | — |

  6. **ACID vs CAP 的辨析（原文给的三个不同）**
     - A 不同：ACID 的 A 是 Atomicity，CAP 的 A 是 Availability。
     - C 同名不同义：ACID 的 C 是数据库数据完整性，CAP 的 C 是分布式节点中的数据一致性。
     - 场景不同：ACID 面向数据库事务，CAP 面向分布式系统数据读写 → 对比「类似关公战秦琼」，没有太多可比性。
  7. **BASE 三项（原文定义 + 关键词）**

     | 项 | 原文定义 | 关键词与判据 |
     |---|---|---|
     | Basically Available 基本可用 | 分布式系统出现故障时，允许损失**部分**可用性，即保证**核心**可用 | 关键词「部分」和「核心」；要先划定哪些可损失、哪些必须保 |
     | Soft State 软状态 | 允许系统存在中间状态，且该中间状态不影响整体可用性 | 这里的中问状态**就是** CAP 里的数据不一致 |
     | Eventual Consistency 最终一致性 | 所有数据副本经过一定时间后，最终达到一致状态 | 关键词「一定时间」和「最终」；不同数据可容忍的不一致时间不同 |

  8. **三者关系（原文结论）**
     - ACID = 数据库事务完整性的理论；CAP = 分布式系统设计理论；BASE = CAP 中 **AP 方案的延伸**。
     - BASE 是对 CAP 的延伸与补充，具体补充两点：①CAP 忽略延时 → 完美 CP 不存在，CP 方案实际也是最终一致性，只是「一定时间」是几毫秒；②AP 牺牲一致性只是分区期间，恢复后应达到最终一致性。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 同机房几毫秒 / 跨地域几十毫秒（北京→广州） | 说明复制延迟必然存在，CAP 的 C 无法完美实现 |
  | user id 0~100 / 101~200 | 分区键样例，说明单用户单点写、整体仍可分布式 |
  | 20% 用户 | 说明按 key 分区把节点故障影响面缩小（「只影响 20% 肯定比影响所有用户好」） |
  | 99.99%（4 个 9）→ 一年 50 分钟 | 论证分区时间在全年占比极小，「牺牲」是暂时的 |
  | 99.999%（5 个 9）→ 一年 5 分钟 | 同上，量化「正常时间远大于分区时间」 |
  | 用户账号：1 分钟内一致 | 最终一致性的「一定时间」取值样例（用户 1 分钟内不太可能切到另一节点） |
  | 用户发布的微博：30 分钟内一致 | 同上（用户看不到明星最新微博无感知） |

- **案例/数据**
  - 用户管理系统（账号数据 CP / 用户信息数据 AP）→ 证明「按数据分类取舍」而非按系统。
  - 按 user id 分区（Node 1 / Node 2）→ 单个用户无法分布式多点写，但整体可分布式；故障只影响部分用户。
  - 挖掘机挖断光缆后支付宝只有部分用户业务异常 → 佐证分区架构缩小影响面（原文以此解释现象）。
  - 账号数据分区期间日志补同步 → 恢复后重新达到 CA。
  - 用户爱好冲突（节点 1 改「旅游、美食、跑步」，节点 2 改「美食、游戏」）→ 三种合并规则分别得到不同结果。
  - 登录是核心功能、注册是非核心功能 → 说明 BASE「基本可用」要先做核心/非核心划分：注册不了只流失少量新用户，登录不了则海量存量用户无法使用。

- **反例与坑**
  - 从「整个系统」角度选 CP 或 AP → 顾此失彼，无论怎么做都有问题。
  - 以为选了 CP 就真的能做到 CP → 忽略延迟，几毫秒的复制窗口内系统并不符合 CP。
  - 以为「单个余额不能分布式」= 「整个系统不能上分布式」→ 原文明确澄清这是两件事。
  - 把「牺牲」理解成「分区期间什么都不做」→ 丢掉日志记录/冲突合并，恢复后无法回到 CA。
  - 拿 ACID 的 C/A 去和 CAP 的 C/A 对比 → 关公战秦琼，结论无效。
  - 把 CAP 的一致性当成「最终一致性」→ 原文明确 CAP 的一致性就是强一致性，最终一致性属于 BASE。

- **原文金句**
  - 「CAP 关注的粒度是数据，而不是整个系统。」
  - 「CAP 是忽略网络延迟的。」
  - 「理论上要求选择 CP 而实际上 CP 都做不到，只能选择 CA。」
  - 「ACID 是数据库事务完整性的理论，CAP 是分布式系统设计理论，BASE 是 CAP 理论中 AP 方案的延伸。」

- **可迁移到知识库的主题**
  - 「按数据分类选 CP/AP」的落地方法（含账号 CP / 用户信息 AP 的判据）。
  - 「忽略延迟」这一隐含假设带来的工程结论：完美 CP 不存在；余额/库存只能单点写（本文件第 22、23 两篇在此处与「分布式只能 CP/AP」的常见讲法存在措辞张力，见文末分析）。
  - 分区期间的两种善后动作：CP→日志补同步；AP→冲突合并（最后修改优先 / 字数最多 / 人工仲裁）。
  - ACID 与 CAP 的「同名不同义」对照表。
  - BASE 三要素的「关键词判据」（部分/核心、中间状态、一定时间/最终）。

### 24丨FMEA方法，排除架构可用性隐患的利器

- **核心结论**
  高可用比高性能复杂，因为异常场景多，漏一个就留隐患（墨菲定律）。FMEA（Failure mode and effects analysis，故障模式与影响分析）是一套**分析与思考的方法**（不是领域技能或工具），它**不指导如何设计架构**，而是在架构设计出来之后，逐部件假设故障、填满一张表，从而把「全面分析可用性」这件事变成可执行动作。

- **完整判据/清单/步骤**
  1. **FMEA 的四个执行步骤**
     1. 给出初始的架构设计图；
     2. 假设架构中某个部件发生故障；
     3. 分析此故障对系统功能造成的影响；
     4. 根据分析结果，判断架构是否需要进行优化。
  2. **FMEA 分析表（原文逐项，共 11 项；前 10 项为表体，第 11 项「后续规划」是汇总产出）**
     - 口径说明：常见说法是「10 列」（功能点→解决措施），但原文明确列到第 11 项「后续规划」，且它的作用是「汇总不足 + 按风险排序 + 给改进规划」，不是可省略的备注列。

     | # | 列 | 填写判据（原文） | 常见错误 |
     |---|---|---|---|
     | 1 | 功能点 | 从**用户角度**看的功能，如「登录」「注册」 | 用模块功能当功能点（数据库存储功能、Redis 缓存功能**不能**作为功能点） |
     | 2 | 故障模式 | 故障点 + 故障形式，只描述**现象**不写原因；要量化 | 写「MySQL 响应慢」（应写「MySQL 响应时间达到 3 秒」） |
     | 3 | 故障影响 | 该功能点受什么影响：偶尔不可用/完全不可用/部分用户不可用/响应缓慢/出错 | 写「大部分用户无法登录」（应写「20% 的用户无法登录」） |
     | 4 | 严重程度 | 站在**业务**角度，分「致命/高/中/低/无」五档 | 纠缠精确档位 |
     | 5 | 故障原因 | 单独列出原因，因为概率/检测手段/处理措施三者都随原因不同 | 把原因混进故障模式 |
     | 6 | 故障概率 | 某个具体**故障原因**发生的概率，分「高/中/低」三档 | 试图绝对量化 |
     | 7 | 风险程度 | 严重程度 × 故障概率，用于判断最终等级 | 只看严重程度不看概率 |
     | 8 | 已有措施 | 现有系统对该原因的措施：检测告警 / 容错 / 自恢复 | 把「有监控」当成「有容错」 |
     | 9 | 规避措施 | 为**降低发生概率**而做的事，技术手段或管理手段 | 与解决措施混为一谈 |
     | 10 | 解决措施 | 为**解决问题**而做的事，一般技术手段 | 明明能解决却只做规避 |
     | 11 | 后续规划 | 汇总「缺措施/措施不够」之处，结合风险程度排序，考虑资源投入，优先解决高风险 | 不排优先级、不落资源 |

  3. **两个计算公式（原文）**
     - `严重程度 = 功能点重要程度 × 故障影响范围 × 功能点受损程度`
     - `风险程度 = 严重程度 × 故障概率`
  4. **严重程度的五档与原文判定样例**

     | 档位 | 原文样例 |
     |---|---|
     | 致命 | 超过 70% 用户无法登录 |
     | 高 | 超过 30% 的用户无法登录 |
     | 中 | 所有用户登录时间超过 5 秒；所有用户都无法修改资料 |
     | 低 | 10% 的用户登录时间超过 5 秒；20% 的用户无法修改头像 |
     | 无 | 原文未明确给出样例（档位名在「致命/高/中/低/无」中列出） |

     - 争议处理：没有绝对标准，建议相关人讨论确定；**不建议花太多时间争论，争执不下时架构师裁定即可**。
  5. **故障原因为什么要单列（三条理由）**
     - 不同原因**发生概率**不同（MySQL bug 概率远低于没有索引）；
     - 不同原因**检测手段**不同（磁盘坏道要专门的运维检查系统；慢查询只需配慢查询日志）；
     - 不同原因**处理措施**不同（bug 只能升级版本；没索引就加索引）。
  6. **故障概率的三类评估要点**
     - 硬件：随使用时间推移概率上升（新盘坏道率低，用了 3 年的盘高很多）；
     - 开源系统：成熟版本低、刚发布版本高；已有使用经验低、刚开始尝试高；
     - 自研系统：同开源，成熟低、新开发高；
     - 高/中/低是**相对**的，只为定优先级、决定资源投入，不必绝对量化（绝对量化有成本且常常做不到）。
  7. **已有措施的三档能力**
     - 检测告警：只检测 + 告警，系统自己不处理，需人工干预；
     - 容错：检测到后靠备份手段应对（如 MySQL 主备机，业务服务器检测到主机连不上自动连备机读）；
     - 自恢复：检测到后系统自己恢复（如 Hadoop 把故障机上的副本重新分配到其他机器）；注意恢复主要指**业务**恢复，一般不能真正修复故障（Hadoop 不能把坏道盘修好）。
  8. **规避 vs 解决的抉择判据**
     - 能解决优先解决；但磁盘坏道、开源系统 bug 这类系统自己解决不了的，只能规避。
     - 规避措施可以是技术（MySQL 里冗余一份 MongoDB 数据）或管理（强制更换使用超 2 年的磁盘）。
  9. **产出**：把「后续规划」列汇总成待改进措施清单，并据此改架构（原文案例最终得到三条措施）。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 20 世纪 40 年代后期 | 美国空军正式采用 FMEA（起源） |
  | MySQL 响应时间 3 秒 | 故障模式的「量化描述」示例 |
  | 70% / 30% 用户无法登录 | 严重程度「致命 / 高」的分界样例 |
  | 所有用户登录超 5 秒 / 10% 用户超 5 秒 | 严重程度「中 / 低」的样例（同因不同范围） |
  | 所有用户无法修改资料 / 20% 用户无法修改头像 | 「中 / 低」样例（不同功能点重要程度） |
  | 20% vs 40% | 故障影响只需预估量级，不需要 21.25% 这种精度 |
  | 3 年（硬盘） | 概率评估：使用年限上升 → 坏道概率上升 |
  | 2 年（强制换盘） | 管理型规避措施的阈值样例 |
  | 地震 5 级以上 20 世纪才 1 次（1940 年，广州） | 低概率原因样例 |
  | 机房空调烧坏约 2 年 1 次 | 中概率原因样例 |
  | 机架掉电约 1 年 1 次 | 高概率原因样例（同样影响、不同概率 → 不同风险级别） |

- **案例/数据**
  - 用户管理系统（MySQL 存储 + Memcache 缓存 + Server 业务处理，功能点仅「登录」「注册」）→ FMEA 后「后续规划」汇总出三条改进：**MySQL 增加备机、MC 从单机扩展为集群、MySQL 双网卡连接**，并据此画出改进后架构。
  - 「MySQL 响应时间达到 3 秒」→ 原因可能是磁盘坏道 / 慢查询 / 连接网络故障 / MySQL bug，但现象相同则业务影响相同，故原因另列。
  - 「某个机房业务瘫痪」：原因=地震（概率低）→ 风险低；原因=空调烧坏（2 年 1 次）→ 风险中；原因=机架掉电（1 年 1 次）→ 风险高 → 同一影响、不同原因，风险等级不同。
  - 地震导致机房中断 → 无法解决，只能靠备份中心规避；机柜断电 → 把业务机分散到不同机柜规避；敏感数据泄露 → 数据库加密解决；MongoDB 断电丢数据 → 在 MySQL 冗余一份、故障时重建。

- **反例与坑**
  - 把 FMEA 当成「设计方法」→ 它只在架构出来后做复核，不能替代设计。
  - 用模块（MySQL、Redis）当功能点 → 表就从「用户视角」滑成「实现视角」，影响面估不准。
  - 故障模式写成「慢」「不稳定」→ 无法量化影响，也无法判断是否达标。
  - 在故障模式里塞原因 → 后面的概率/检测/处理三列失去意义。
  - 把「有告警」当作「已容错」→ 三档能力要分开标注，否则误判风险已关闭。
  - 只做解决措施、不考虑规避措施（或反之）→ 对无法根治的故障（坏道、开源 bug）会没有对策。
  - 在严重程度档位上争论不休 → 原文明确让架构师裁定，别耗时间。

- **原文金句**
  - 「FMEA 是一套分析和思考的方法，而不是某个领域的技能或者工具。」
  - 「FMEA 并不能指导我们如何做架构设计，而是当我们设计出一个架构后，再使用 FMEA 对这个架构进行分析，看看架构是否还存在某些可用性的隐患。」
  - 「不管哪种原因，只要现象是一样的，对业务的影响就是一样的。」
  - 「一般来说，如果某个故障既可以采取规避措施，又可以采取解决措施，那么我们会优先选择解决措施，毕竟能解决问题当然是最好的。」

- **可迁移到知识库的主题**
  - FMEA 11 列（10 列表体 + 后续规划）的逐列判据，尤其是「功能点必须是用户视角」这条最容易走偏的约束。
  - 两个乘法公式及其定位差异：严重程度用于定档，风险程度用于排序。
  - 「同一影响 × 不同原因 → 不同风险」的概率分档法（硬件/开源/自研三类）。
  - 已有措施的三档能力模型（检测告警 < 容错 < 自恢复）。
  - 规避 vs 解决的抉择判据（系统能否自己解决）。

### 25丨高可用存储架构：双机架构

- **核心结论**
  存储高可用的本质是**数据复制到多个存储设备、用冗余换可用**，其复杂性集中在「复制延迟」与「复制中断」导致的数据不一致。分析任何存储高可用方案都要回答四个问题：数据如何复制、各节点职责是什么、如何应对复制延迟、如何应对复制中断。双机架构分主备、主从、双机切换（互连式/中介式/模拟式）、主主四类。

- **完整判据/清单/步骤**
  1. **统一分析框架（四问）**：数据如何复制？各个节点的职责是什么？如何应对复制延迟？如何应对复制中断？
     - 口径说明：冷备/温备/热备这一组划分**不在本篇**（25、26 两篇均未出现），原文是在 27 篇（计算高可用）给出**冷备与温备**两档，**热备原文未明确**。
  2. **主备复制**
     - 机制：备机只做备份、不承担实际业务读写；备机要变主机需**人工操作**。
     - 优点（两条）：客户端不需感知备机（灾难恢复后只是「主机地址换了」）；主备之间只需数据复制，无须状态判断与主备切换这类复杂操作。
     - 缺点（两条）：备机不提供读写，硬件成本浪费；故障后需人工干预、无法自动恢复（人工效率低，找人可能耗 10 分钟；深更半夜没人知道；人工操作易错，因为一年才 2、3 次，不熟练）。
     - 适用：内部后台管理系统（学生管理、员工管理、假期管理）——数据变更频率低，丢失可人工补全。
  3. **主从复制**
     - 机制：「从」=随从/仆从，要帮主人干活，即从机承担**读**；主机负责读写，从机只负责读、不负责写。
     - 与主备的差别：从机正常情况下也提供读操作。
     - 优点：主机故障时读相关业务可继续；从机提供读，发挥硬件性能。
     - 缺点：客户端需感知主从关系并分流（复杂度高于主备）；从机读业务会受复制延迟影响而出错；故障时仍需人工干预。
     - 适用：写少读多业务（论坛、BBS、新闻网站），读操作数量是写的 10 倍甚至 100 倍以上。
  4. **双机切换**
     - 要解决的问题（主备/主从的两个共性缺陷）：主机故障后无法写；主机无法恢复时需人工指定新主机。
     - 定义：在主备/主从基础上增加「切换」功能，由系统自动决定主机角色并完成角色切换；主备切换与主从切换在切换设计上**无差别**。
     - **三个关键设计点（缺一不可）**
       1. **主备间状态判断**：①状态传递的**渠道**（互相连接，还是第三方仲裁）；②状态检测的**内容**（机器是否掉电、进程是否存在、响应是否缓慢等）。
       2. **切换决策**：①**切换时机**（掉电才升？进程不存在就升？响应超 2 秒就升？3 分钟内连续重启 3 次才升？）；②**切换策略**（旧主机恢复后是否再切回去，还是自动成为新备机）；③**自动程度**（全自动 / 半自动，如系统判断后等人工点一下「切换」按钮）。
       3. **数据冲突解决**：旧主机恢复后新旧主机数据冲突如何处理（例：旧主机新增 ID=100 未复制，切换后新主机又新增 ID=100，恢复后两条 ID=100 怎么办）。
     - 复杂度量级：复制方案 1000 行代码，切换方案可能 10000 行，多出的 9000 行用于实现上面 3 个设计点。
     - **三种状态传递形态**

       | 形态 | 机制 | 优点 | 缺点/代价 |
       |---|---|---|---|
       | 互连式 | 主备机直接建立状态传递通道（网络端口/串口线；可主发备、可备拉主；可与复制通道共用或独立；可单条/多条/混合） | 直观、状态信息丰富 | 状态通道本身故障（如网线被踢掉）→ 备机误判主机故障并升级 → **可能出现两个主机**；加多通道只降低概率，不根治，且通道越多决策越复杂（可能收到矛盾状态） |
       | 中介式 | 引入第三方中介，主备都连中介并经中介传状态（MongoDB Replica Set：主/备存储数据，仲裁节点不存数据，客户端只连主备不连仲裁） | ①连接管理更简单（主备只当中介的客户端）；②状态决策更简单（见下方四步算法） | 中介本身要高可用：中介宕机 → 系统进入**双备**状态，写业务不可用 → 递归陷阱 |
       | 模拟式 | 主备间只有复制通道、无状态通道；备机模拟成客户端向主机发模拟读写，按响应判断主机状态 | 实现更简单（省去状态通道的建立与管理） | 状态信息只有响应（HTTP 404、超时、响应超 3 秒），没有 CPU/IO 负载、吞吐量等，基于有限状态决策**可能偏差** |

     - 中介式的状态决策算法（原文四条）
       1. 无论主机还是备机，初始状态都是备机；只要与中介断开连接就降级为备机（因此可能出现双备机）；
       2. 主机与中介断连后，中介能立刻告知备机，备机升级为主机；
       3. 若是网络中断导致主机与中介断连，主机自己降级为备机；网络恢复后旧主机以新备机身份上报状态；
       4. 若掉电重启或进程重启，旧主机初始为备机，恢复连接后发现已有主机，保持备机不变；
       5. 连接都正常时按实际状态决定是否切换（如主机响应超 3 秒 → 主机降备、备机升主）。
     - 中介选型建议：开源已有成熟方案 ZooKeeper、Keepalived；**工程实践推荐基于 ZooKeeper 搭建中介式切换架构**（ZK 自身已解决中介的高可用）。
     - 客户端配合（互连式场景）：①主备共享对客户端唯一的地址（如虚拟 IP，主机绑定 VIP）；②客户端同时记录主备地址，哪个能访问就访问哪个，备机收到请求直接拒绝（理由「备机不对外提供服务」）。
  5. **主主复制**
     - 机制：两台都是主机，互相复制给对方，客户端可任选一台读写；**不存在切换概念**，客户端无须区分角色。
     - 表面简单（无状态传递、无状态决策、无切换），实际复杂在**数据必须能双向复制**。
     - 适用判据：只适合**临时性、可丢失、可覆盖**的数据（session、用户行为日志、论坛草稿）。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 10 分钟 | 主备故障后打电话找人的时间成本（论证人工恢复慢） |
  | 1 年 2、3 次 | 人工切换操作频率低 → 不熟练 → 易出错 |
  | 读操作是写的 10 倍甚至 100 倍以上 | 主从复制的适用场景判据（写少读多） |
  | 响应超 2 秒 / 2 秒 | 切换时机的一个候选阈值（「主机响应时间超过 2 秒就升级」） |
  | 3 分钟内连续重启 3 次 | 切换时机的另一个候选阈值 |
  | 响应时间超过 3 秒 | 中介式正常连接下的切换触发样例 |
  | 1000 行 vs 10000 行 | 复制方案 vs 切换方案的代码量量级，说明切换复杂度高一个量级 |

- **案例/数据**
  - MySQL / Redis / MongoDB 都提供主备复制 → 主备是最常见最简单的方案。
  - 用户 ID=100 冲突（旧主机新增未复制，切换后新主机又新增同 ID）→ 说明「数据冲突解决」是切换方案必备设计点。
  - 虚拟 IP / 客户端双地址探测备机拒绝 → 说明切换要客户端配合，否则切换后访问会中断。
  - MongoDB Replica Set（主 M / 备 S / 仲裁 A）→ 中介式的工业实现。
  - ZooKeeper、Keepalived → 现成的中介式方案，推荐直接用。
  - 用户 ID 按数字增长做双向复制 → 主机 A 分配 100、主机 B 也分配 100 → 冲突。
  - 库存 100：A 减 1 得 99，B 减 2 得 98，A 把 99 复制覆盖 B 的 98 → 实际应为 97，被覆盖成 99 → 主主不能用于库存/余额。

- **反例与坑**
  - 主备/主从当成「自动高可用」→ 二者都要人工切换，可用性受人工效率与出错率限制。
  - 互连式只靠加通道解决「双主」→ 只是降低概率，且多通道状态可能矛盾。
  - 中介式忽略中介自身高可用 → 递归陷阱：为高可用引入中介，中介又要高可用……
  - 模拟式把「响应正常」当成「主机健康」→ 状态信息维度太少，决策可能偏差。
  - 主主复制用于用户 ID、库存、余额 → 双向复制直接产生冲突或数据被覆盖。
  - 切换方案只做「检测 + 升级」，不做数据冲突解决 → 旧主机恢复后数据错乱。
  - 客户端不配合（不共享 VIP、不记录主备地址）→ 切换后流量打不到新主机。

- **原文金句**
  - 「存储高可用方案的本质都是通过将数据复制到多个存储设备，通过数据冗余的方式来实现高可用，其复杂性主要体现在如何应对复制延迟和中断导致的数据不一致问题。」
  - 「如果复制方案的代码是 1000 行，那么切换方案的代码可能就是 10000 行，多出来的那 9000 行就是用于实现上面我所讲的 3 个设计点的。」
  - 「这就陷入了一个递归的陷阱：为了实现高可用，我们引入中介，但中介本身又要求高可用，于是又要设计中介的高可用方案……如此递归下去就无穷无尽了。」
  - 「主主复制架构对数据的设计有严格的要求，一般适合于那些临时性、可丢失、可覆盖的数据场景。」

- **可迁移到知识库的主题**
  - 存储高可用的「四问」分析框架（复制方式/节点职责/复制延迟/复制中断）。
  - 双机切换的三个设计点与复杂度量级（含「数据冲突解决」这个常被漏掉的点）。
  - 状态传递的三种形态（互连式/中介式/模拟式）及其失效模式（双主、双备、决策偏差）。
  - 中介式递归陷阱与「用 ZooKeeper 当中介」的工程结论。
  - 主主复制的数据适用性判据（临时/可丢失/可覆盖），以及 ID、库存、余额的反例。

### 26丨高可用存储架构：集群和分区

- **核心结论**
  主备/主从/主主都有一个隐含假设——「主机能存下所有数据」，而单机存储与处理能力有极限，于是需要多机。集群按角色分**数据集中集群（1 主多备/1 主多从）**与**数据分散集群（每台存一部分 + 备份一部分）**；当故障域上升到「城市/地区级」，则要用**数据分区**（地理分区），并额外设计分区之间的复制规则（集中式/互备式/独立式）。

- **完整判据/清单/步骤**
  1. **集群的定义与判据**：多台机器组合成一个统一系统，数量上**至少 3 台**（主备、主从都是 2 台）。
  2. **数据集中集群**
     - 本质：1 主多备 / 1 主多从；数据**只能往主机写**，读可按主备/主从灵活配置。
     - 因机器更多而新增的三个复杂点：
       1. **主机如何把数据复制给备机**：存在多条复制通道 → 增大主机复制压力（需降低复制压力或降低复制对读写的影响）；多备机之间可能数据不一致（需检查与修正）。
       2. **备机如何检测主机状态**：多台备机各自判断，判断结果可能不同 → 如何处理不同判断。
       3. **主机故障后如何决定新主机**：多台备机都能升主，但只能有一台升主 → 选谁、备机之间如何协调。
     - 代表方案：ZooKeeper，通过 **ZAB 算法**解决上述问题，但 ZAB 复杂度很高。
     - 适用判据：客户端只能写主机 → 适合**数据量不大、集群机器数量不多**（ZK 一般推荐 5 台左右，数据量单机能支撑）。
  3. **数据分散集群**
     - 机制：每台服务器负责存储一部分数据；同时为提升硬件利用率，每台又备份一部分数据。
     - 核心难点是**数据分配算法**，三个设计点：
       1. **均衡性**：不能出现某台服务器分区数量是另一台的几倍；
       2. **容错性**：部分服务器故障时，把原属故障机的分区分配给其他服务器；
       3. **可伸缩性**：扩容后能自动把部分分区迁移到新服务器，并保证扩容后整体均衡。
     - 与集中式的关键差异：每台都能处理读写，**不存在「负责写的主机」角色**；但仍需一个角色执行分配算法——可以是独立服务器，也可以是集群选举出的一台（此时也叫「主机」，但职责与集中式的主机不同）。
     - 代表方案：Hadoop（独立服务器 Namenode 负责分区分配：管理命名空间、确定数据块到 Datanode 的映射，Datanode 处理读写并在 Namenode 统一调度下做块创建/删除/复制）；Elasticsearch（**选举**一台 master node 做分配：创建/删除索引、跟踪集群节点、决定分片分配到哪些节点，强调 master 稳定）。
     - 适用判据：客户端可向任意服务器读写 + 良好可伸缩性 → 适合**业务数据量巨大、机器数量庞大**（Hadoop/HBase 可达上百台甚至上千台）。
  4. **数据分区（地理分区）**
     - 产生背景：前面所有方案都基于「部分硬件故障」，而水灾、大停电、大地震会让一个城市/地区的基础设施全部瘫痪 → 需要按**地理级别故障**设计。
     - 机制：数据按规则分区，不同分区位于不同地理位置，每个分区存一部分数据；某地灾难只影响部分数据，恢复时可用其他地区备份帮助快速恢复。
     - 三个设计考虑：
       1. **数据量**：直接决定分区规则复杂度。数据量越大 → 规则越复杂、要考虑的越多（运维定位难、改配置风险、需地理容灾）。
       2. **分区规则**：按地理位置可分**洲际分区 / 国家分区 / 城市分区**；选择需综合业务范围与成本。
          - 洲际：跨洲网络延迟已大到不适合在线服务 → 可不互通，或仅作备份；
          - 国家：面向不同国家用户（语言/法律/业务不同）→ 一般也仅作备份；
          - 城市：同国同地区、延迟低、业务相似 → **可分区同时对外提供服务**，满足异地多活类需求。
       3. **复制规则**：分区本身只是「分散风险」，每个分区数据量仍很大，仍需复制方案；三种规则见下表。

     | 复制规则 | 机制 | 优点 | 缺点 |
     |---|---|---|---|
     | 集中式 | 存在一个总备份中心，所有分区都备份到该中心 | 设计简单（各分区无直接联系、互不影响）；扩展容易（新增武汉分区只需把数据复制到西安备份中心） | 成本较高（需建独立备份中心） |
     | 互备式 | 每个分区备份**另外一个分区**的数据 | 成本低（直接利用已有设备） | 设计复杂（分区既存业务又承担备份，互相关联影响）；扩展麻烦（加武汉分区要改广州→武汉、武汉→北京，且北京已有的广州历史数据难处理） |
     | 独立式 | 每个分区有**自己独立的备份中心** | 设计简单（互不影响）；扩展容易（新分区自建备份中心即可） | 成本高（每分区独立备份中心，场地成本为主，显著高于集中式） |

     - 独立式的关键细节：**备份不与原分区同城/同地理位置**（北京→天津、上海→杭州、广州→汕头），目的是规避同城同时受灾（如北京分区在朝阳区、备份在通州区，整个北京停电则两个机房都不能工作）。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 至少 3 台 | 集群与双机（2 台）的数量分界 |
  | Intel 386 几百 MB / 奔腾几十 GB / 酷睿多核几个 TB | 单机存储能力演进，说明仍追不上业务增长 |
  | 2013 年 Facebook 2500 亿张照片、250 PB（250 × 1024TB）、日均上传 3 亿 5000 万张 | 论证单机不可能存储/处理，必须集群 |
  | ZooKeeper 推荐 5 台左右 | 数据集中集群的规模判据 |
  | 单台 MySQL 500GB；2TB → 至少 4 台 | 数据量 → 分区数量的换算样例 |
  | 200TB 数据 → 不是简单扩到 800 台 | 说明数据量到某量级后复杂度本质变化 |
  | 800 台中每周可能 1~2 台故障 | 运维复杂度论据（从 800 台里定位 2 台不容易） |
  | 上百台甚至上千台（Hadoop/HBase） | 数据分散集群的规模区间 |

- **案例/数据**
  - Facebook 2500 亿张照片 / 250PB / 日均 3.5 亿张 → 单机不可行 → 集群架构。
  - ZooKeeper + ZAB → 数据集中集群的典型，5 台左右即可。
  - Hadoop Namenode（独立服务器分配分区）vs Elasticsearch master node（选举产生）→ 两种分区管理角色的实现方式。
  - 北京/上海/广州三地 + 西安备份中心 → 集中式复制；新增武汉分区只需复制到西安 → 扩展容易。
  - 互备式新增武汉：改广州→武汉、武汉→北京，北京已有的广州历史数据难以处理 → 扩展麻烦。
  - 北京（朝阳区）机房 + 通州区备份，全北京停电 → 两机房同时不可用 → 备份必须跨城（天津/杭州/汕头）。

- **反例与坑**
  - 把「集群」等同于「把机器堆多」→ 集中式集群的多通道复制、多备机判断、选主三个复杂度会同时放大。
  - 在数据集中集群里指望客户端任意写 → 客户端只能写主机，写错了就破坏一致性。
  - 数据分散集群没有均衡/容错/伸缩三性 → 扩容或故障后分区倾斜、无法迁移。
  - 用「远距离大集群」代替地理分区 → 跨地域复制延迟与不稳定会让集群本身不可用（原文思考题正面提出这个问题）。
  - 分区备份放在同城不同区 → 城市级停电/灾害时主备同时失效。
  - 只做分区不做分区内复制 → 单个分区数据损坏仍是不可接受的损失。

- **原文金句**
  - 「集群就是多台机器组合在一起形成一个统一的系统，这里的"多台"，数量上至少是 3 台；相比而言，主备、主从都是 2 台机器。」
  - 「数据集中集群架构中，客户端只能将数据写到主机；数据分散集群架构中，客户端可以向任意服务器中读写数据。正是因为这个关键的差异，决定了两种集群的应用场景不同。」
  - 「因此，数据量越大，分区规则会越复杂，考虑的情况也越多。」
  - 「如果北京分区机房在朝阳区，而备份机房放在通州区，整个北京停电的话，两个机房都无法工作。」

- **可迁移到知识库的主题**
  - 数据集中集群 vs 数据分散集群的判别式：**客户端能否向任意节点写**。
  - 集中式集群的三个放大复杂度（多复制通道 / 多备机状态判断 / 多备机选主）。
  - 数据分散集群分配算法的三性（均衡性/容错性/可伸缩性）与两种「主机」职责差异（Namenode vs 选举 master）。
  - 地理分区的三级规则（洲际/国家/城市）与各自能否「同时对外服务」。
  - 分区复制的三种规则（集中式/互备式/独立式）的成本-复杂度权衡，以及「备份必须跨城」的铁律。

### 27丨如何设计计算高可用架构？

- **核心结论**
  计算高可用的本质是**通过冗余规避部分硬件损坏**，单台服务器做不到，所以设计思想就是「加服务器」。它的复杂度不在计算本身，而在**任务管理**：任务在某台机器执行失败后，如何重新分配到新机器。两个关键点是「哪些服务器可以执行任务」与「任务如何重新执行」。常见架构：主备（冷备/温备）、主从、集群（对称/非对称）。

- **完整判据/清单/步骤**
  1. **两个关键设计点**
     - **哪些服务器可以执行任务**：①每台都能执行（类似计算高性能的集群，如访问网站某页面）；②只有特定「主机」能执行（类似存储高可用的集群，如 ZooKeeper 只有 Leader 处理写请求），主机故障后要挑选新主机。
     - **任务如何重新执行**：①已分配任务失败不做任何处理，只保证新任务能分到非故障机；②设**任务管理器**，服务器执行完回传结果，由管理器决定是否重新分配到其他服务器。
     - 「任务分配器」是**逻辑概念**，不要求有独立模块：Nginx 承担了任务分配器职责；后台批处理可设独立任务分配系统；ZooKeeper 的 Follower 收到写请求转发 Leader、收到读请求自己处理，也是逻辑上的任务分配器。
  2. **主备（计算高可用）**
     - 与存储主备的差别：**无须数据复制**，因此更简单。
     - 详细设计（四步）：①主机执行所有计算任务（读写数据、执行操作）；②主机故障时任务分配器**不会自动**把任务发给备机，此时系统不可用；③主机能恢复（人工或自动）→ 分配器继续发给主机；④主机不能恢复（如硬盘损坏短时间修不好）→ **人工**把备机升为主机，分配器改发新主机，同时**人工增加新机器作备机**以维持主备形态。
     - **按备机状态细分**
       - **冷备**：备机的程序包与配置文件都准备好，但**业务系统没有启动**（注意：备机的服务器是启动的）；主机故障后需人工手工启动业务系统，并把分配器的请求切到备机。
       - **温备**：备机的业务系统**已经启动**，只是不对外提供服务；主机故障后人工只需把分配器的请求切到备机。
       - 取舍：冷备可节省能源；温备能大大减少手工操作时间 → **一般推荐温备**。
       - **热备**：原文未明确（本讲只给出冷备与温备两档）。
     - 优点：简单，主备机不需交互，状态判断与切换由人工执行。
     - 缺点：都落在「人工操作」上——发现慢（可能 1 小时后才发现）、切换慢（可能半小时才完成）、易出错（改错配置、启动错程序）。
     - 适用：内部管理系统、后台管理系统（使用人数不多、频率不高），不适合在线业务。
  3. **主从（计算高可用）**
     - 与存储主从类似：从机也要执行任务；任务分配器需**先给任务分类**，决定哪些发主机、哪些发备机。
     - 详细设计（四步）：①正常情况下主机执行部分任务（任务 A）、备机执行部分任务（任务 B）；②主机故障时分配器**不会**把原属主机的任务转给从机，仍照发主机（不管成败）；③主机能恢复 → 恢复原分配策略；④主机不能恢复 → **人工**把原从机升为主机（一般只改配置），增加新机器作从机，就绪后恢复原策略。
     - 优点：从机也执行任务，发挥硬件性能。缺点：需任务分类，分配器更复杂。
  4. **集群（计算高可用）**
     - 分类：**对称集群**（每台角色相同，都能执行所有任务，即负载均衡集群）与**非对称集群**（分角色，如 Master-Slave，不同角色执行不同任务）。
     - 与存储高可用的差异：**计算高可用集群包含 2 台服务器的集群**；存储把双机与集群分开，计算则 2 台与多台在设计上无本质区别，不需区分。
     - **负载均衡集群详细设计（三步）**：①正常时分配器按策略（随机、轮询）分配；②某台故障后不再分给它，改分给其他服务器；③故障机恢复后重新分配给它。
       - 两个设计关键点：**分配策略**（轮询和随机基本够用）+ **状态检测**（既要检测服务器状态：是否宕机、网络是否正常；也要检测任务执行状态：是否卡死、执行时间是否过长）。常用做法是心跳传递服务器信息与任务信息，再据实际情况定判断条件。
     - **非对称集群详细设计（三步）**：①用某种方式区分角色（ZAB 选举，或简单取存活节点中 ID 最小者为 Master）；②分配器把不同任务发给不同角色（任务 A→Master，任务 B→Slave）；③指定类型服务器故障时重新分配角色（Master 故障 → 从剩余 Slave 中指定一个为 Master；Slave 故障 → 只需从集群剔除，不必重分配角色）。
       - 两个复杂点：任务分配策略更复杂（任务要分类型对应角色）；角色分配策略实现复杂（可能需要 ZAB、Raft 这类选举算法）。
     - 案例（ZooKeeper）：无独立任务分配器节点，每个 Server 都是分配器（Follower 判断写转发 Leader、读自己处理）；角色由 ZAB 选举，Leader 故障后所有 Follower **暂停读写**开始选举，选出新 Leader 才继续对 Client 提供服务。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 1 小时 | 主备故障可能「已发生但维护人员还没发现」的时长 |
  | 半个小时 | 人工完成切换操作的耗时 |
  | 页面平均 500 毫秒内返回 | 在线页面访问系统的正常基线 |
  | 1 分钟内响应时间超过 1 秒（含超时）的页面数量占 80% | 该场景的「服务器有故障」判断条件 |
  | 后台任务正常 5 分钟内完成 | 后台统计系统的正常基线 |
  | 单任务执行超过 10 分钟未结束 | 该场景的故障判断条件 |
  | 2 台 | 计算高可用集群的最小规模（与存储集群的 3 台区分） |

- **案例/数据**
  - Nginx 反向代理 + 静态文件读本地缓存 → 「任务分配器是逻辑概念」，不必额外加模块。
  - ZooKeeper Follower 转发写请求 → 逻辑任务分配器。
  - 在线页面系统（500ms 基线 → 1 分钟内 80% 请求超 1 秒即判故障）→ 说明状态判断条件必须按业务定制。
  - 后台统计任务（5 分钟基线 → 单任务超 10 分钟未结束即判故障）→ 同上，两类业务判据差异极大。
  - ZooKeeper ZAB 选举 → 非对称集群的角色分配实现（Leader 故障期间暂停读写）。

- **反例与坑**
  - 把计算的「主备」照搬存储主备 → 忘了计算主备无须数据复制，会把方案做得不必要地复杂。
  - 主备/主从以为会自动切换 → 原文反复强调「任务分配器不会自动把任务发给备机」，切换靠人工。
  - 冷备/温备混淆 → 冷备是「业务系统未启动」，不是「服务器未启动」。
  - 选冷备省能源 → 换来更长的 RTO；原文推荐温备。
  - 状态检测只看机器（宕机/网络）不看任务（卡死/执行过长）→ 会漏判「机器活着但任务废了」。
  - 非对称集群只处理 Master 故障 → Slave 故障虽不必重分配角色，但仍需把故障机从集群剔除。
  - 用存储集群「≥3 台」的规则套计算集群 → 计算集群 2 台就算集群。

- **原文金句**
  - 「计算高可用的本质是通过冗余来规避部分故障的风险，单台服务器是无论如何都达不到这个目标的。」
  - 「"任务分配器"是一个逻辑的概念，并不一定要求系统存在一个独立的任务分配器模块。」
  - 「冷备可以节省一定的能源，但温备能够大大减少手工操作时间，因此一般情况下推荐用温备的方式。」
  - 「不同业务场景的状态判断条件差异很大，实际设计时要根据业务需求来进行设计和调优。」

- **可迁移到知识库的主题**
  - 计算高可用 vs 存储高可用的差异清单（无数据复制；2 台即集群；复杂度在任务管理）。
  - 冷备 / 温备的定义边界（业务系统是否启动；服务器是否启动），以及「推荐温备」的成本-时间权衡；热备在本讲缺失。
  - 负载均衡集群的状态检测要同时覆盖「机器状态 + 任务执行状态」，并给出两个按业务定阈值的实例。
  - 对称集群 vs 非对称集群的设计步骤与两个复杂点。
  - 「任务分配器是逻辑角色」的判定方法（Nginx、Follower、批处理调度）。

### 28丨业务高可用的保障：异地多活架构

- **核心结论**
  计算/存储高可用都只解决「部分服务器故障」；当所有服务器同时故障（机房断电、火灾、地震、水灾），且备份系统恢复可能要半小时到 12 小时，就需要**异地多活**。它的关键点是**异地**（不同地理位置）+ **多活**（各地系统都能提供业务服务）。但代价很高（复杂度质变 + 成本上升），并非所有业务都该做。

- **完整判据/清单/步骤**
  1. **判定「是不是异地多活」的两条标准**
     1. 正常情况下，用户无论访问哪一个地点的业务系统，都能得到**正确**的业务服务；
     2. 某个地方业务异常时，用户访问其他地方正常的业务系统，能得到正确的业务服务。
     - 对照物：「备」= 备份，正常情况下不对外服务；要让「备」变「活」需要大量人工干预和操作、花大量时间。
  2. **要不要做的判据**
     - 代价：①系统复杂度**质的变化**（要设计复杂的多活架构）；②成本上升（多在一个或多个机房搭独立一套业务系统）。
     - 可以不做（只做异地备份即可）：新闻网站、企业内部 IT 系统、游戏、博客站点——中断对用户影响不大（A 新闻网站看不了就换一个）。
     - 需要做：共享单车、滴滴出行、支付宝、微信——中断影响很大（支付宝用不了就没法买东西）。
     - 补充：业务规模很大时应尽量做——既提升异常场景体验，也减少广告等衍生收入损失（新闻网站几小时不可访问会伤口碑、损失广告收入）。
  3. **三种架构模式（按地理位置距离划分）**
     - 口径说明：**本篇原文只给出三种**（同城异区/跨城异地/跨国异地），并未出现「第四种模式」；若把「不做多活、只做异地备份」当作对照基线，可凑成四类，但原文没有这样命名，第四种**原文未明确**。

     | 模式 | 定义/做法 | 关键机制 | 优点 | 局限与适用 |
     |---|---|---|---|---|
     | **同城异区** | 同城不同区的多个机房（北京海淀 + 通州），用专用高速网络连接 | 同城距离一般几十千米，搭高速网络后传输速度与单机房几乎一样 → **逻辑上可视为同一个机房** | 大幅降低多活的设计复杂度与成本；能解决机房火灾、停电、空调故障等高频高破坏故障 | 对新奥尔良水灾、美加大停电这类极端灾难**无能为力**；原文结论：**综合复杂度、成本、故障概率，同城异区是应对机房级别故障的最优架构** |
     | **跨城异地** | 不同城市的多个机房，且距离要**远**（北京 + 广州，而非广州 + 深圳） | 要应对「同城异区解决不了」的极端灾难（水灾、大停电），距离必须远 | 能有效应对极端灾难事件 | 距离带来网络传输速度下降（物理定律），复杂度**量变引起质变**；强一致数据（余额）无法跨城多活 |
     | **跨国异地** | 不同国家的多个机房 | 距离更远，数据同步延时正常就有几秒 | 面向不同地区用户提供服务；只读类业务做多活 | 几秒延迟已**违反第一条判定标准**（访问任一点都应得到正确服务），故「多活」含义与跨城不同 |

  4. **跨城异地的物理约束（原文论证链）**
     - 光速真空约 30 万千米/秒，光纤中约 20 万千米/秒，加上网络设备处理，实际远达不到理论速度。
     - 中间不可控因素多：挖掘机挖断光纤、中美海底电缆被拖船扯断、骨干网故障；这些线路多由第三方维护，无法预知也无法干预。
     - 广州→北京正常 RTT 约 50 毫秒，网络波动时可飙升到 500 毫秒甚至 1 秒；线路丢包时延迟可能几秒几十秒。
     - 同城异区也会遇到，但距离短、经过线路与设备少，概率低很多；且多通道成本低（跨城多通道成本高不少）。
  5. **强一致数据为什么不能跨城多活（判据）**
     - 银行存款余额、支付宝余额这类强一致数据**无法做到跨城异地多活**；支付宝等金融系统对余额一般只做同城异区。
     - 能做跨城多活的判据：数据一致性要求不高、数据不怎么改变、或丢失影响不大——用户登录（不一致时重登即可）、新闻类网站（一天内新闻变化少）、微博类（丢微博或评论影响不大）。
  6. **跨国异地的两类正当场景**
     - 为不同地区用户提供服务（亚马逊中国服务中国用户、亚马逊美国服务美国用户，账号不互通）；
     - 只读类业务做多活（谷歌搜索：资料已在搜索引擎上，访问英国或美国谷歌结果基本相同，且不需最新实时资料，几秒延迟无影响）。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 半小时 ~ 12 小时 | 极端故障后把备份系统恢复到可正常提供业务的耗时（论证需要多活） |
  | 几十千米 | 同城异区两机房的距离量级（可近似单机房） |
  | 30 万千米/秒（真空）/ 20 万千米/秒（光纤） | 光速约束，说明跨城延迟不可消除 |
  | RTT 约 50 毫秒（广州↔北京正常） | 跨城基线 |
  | RTT 500 毫秒 ~ 1 秒（网络波动） | 跨城劣化上限样例 |
  | 几秒 ~ 几十秒（丢包时） | 跨城极端延迟样例 |
  | 正常几秒（跨国同步延时） | 跨国异地已违反「正常情况下访问任一点都正确」的标准 |
  | 几年或十几年一次 | 极端灾难发生概率（论证同城异区仍是最优） |
  | 余额 10000 元 → 转出 20000 元 | 跨城多活做余额的后果（双花） |

- **案例/数据**
  - 机房断电 / 火灾 / 地震 / 水灾 → 所有服务器故障 → 触发异地多活需求。
  - 备份系统平时不对外服务 → 存在很多「隐藏问题」没被发现 → 恢复时间可能是半小时也可能是 12 小时。
  - 新闻网站 / 内部 IT / 游戏 / 博客 → 可只做异地备份；共享单车 / 滴滴 / 支付宝 / 微信 → 需要多活。
  - 北京海淀 + 通州两机房 → 同城异区的典型部署。
  - 用户 A 余额 10000：广州转 5000 给 B（广州余 5000），光缆断未同步（北京仍 10000），北京再转 10000 给 C（北京余 0），广州又转 5000 给 D（广州余 0）→ **共转出 20000** → 强一致数据不能跨城多活。
  - 上海 + 纽约微博机房 → 上海发博，纽约关注者可能看不到 → 跨国「多活」含义不同。
  - 亚马逊中/美账号不互通；谷歌搜索跨国结果基本相同 → 跨国多活的两类正当场景。

- **反例与坑**
  - 不管什么业务都上异地多活 → 复杂度质变 + 成本上升，新闻/内部系统完全没必要。
  - 把「异地备份」当「异地多活」→ 备份平时不服务，切过去要大量人工与时间，且隐藏问题多。
  - 以为同城异区能扛一切 → 对新奥尔良水灾、美加大停电无能为力（但原文仍判定它是最优架构，因为高频故障是机房级）。
  - 跨城距离选得太近（广州 + 深圳）→ 无法应对大范围停电/灾害，失去跨城的意义。
  - 对余额/库存做强一致跨城多活 → 双花漏洞，被黑客利用后果不堪设想。
  - 跨国多活照搬跨城多活的语义 → 几秒延迟已违反「任一点都正确」的标准。
  - 忽视跨城线路的第三方属性 → 挖断光缆/海底电缆这类故障无法预知、无法干预。

- **原文金句**
  - 「顾名思义，异地多活架构的关键点就是异地、多活……多活就是指不同地理位置上的系统都能够提供业务服务，这里的"活"是活动、活跃的意思。」
  - 「跨城异地虽然能够有效应对极端灾难事件，但"距离较远"这点并不只是一个距离数字上的变化，而是量变引起了质变，导致了跨城异地的架构复杂度大大上升。」
  - 「最终，本来余额 10000 元的用户 A，却转了 20000 元出去给其他用户。」
  - 「结合复杂度、成本、故障发生概率来综合考虑，同城异区是应对机房级别故障的最优架构。」

- **可迁移到知识库的主题**
  - 异地多活的两条判定标准（正常时任一点正确；异常时他点正确）与「活/备」的判别式。
  - 按地理距离的三分法（同城异区/跨城异地/跨国异地）及各自的「能解决什么、不能解决什么」。
  - 「强一致数据不能跨城多活」的判据与双花论证（余额 10000 → 转出 20000）。
  - 距离-延迟-复杂度的量变到质变链条（光速、RTT、光纤挖断）。
  - 跨国多活的两种合法形态（分区用户服务、只读多活）。

### 29丨异地多活设计4大技巧

- **核心结论**
  跨城异地多活是复杂度最高的一种，其设计围绕四个思维误区展开，每个误区对应一个技巧：**保证核心业务的异地多活、保证核心数据最终一致性、采用多种手段同步数据、只保证绝大部分用户的异地多活**。核心思想一句话：**采用多种手段，保证绝大部分用户的核心业务异地多活**。

- **完整判据/清单/步骤**
  1. **技巧 1：保证核心业务的异地多活**
     - 误区：「我要保证所有业务都能异地多活」。
     - 反证（用户子系统的三个业务）：
       - **注册**：A 中心注册未同步即宕机，让用户去 B 中心重注册 → 手机号唯一性无法判断；A 恢复后数据冲突**无解**（同一手机号不能以后一次注册为准）。
       - 改业务规则（允许一号多账号）不可行：这是**核心业务规则**，修改代价极大，几乎所有业务都要重设计。
       - **用户信息**：两边都改的冲突，「按时间合并（最后修改生效）」有个坑——**无法保证多中心所有机器时间绝对一致**，只要误差超过 1 秒，就可能「先修改的反而不生效」；「全局唯一递增 ID」成本很高，因为该系统本身又要异地多活、同样面对一致性与冲突。
     - 结论与判据：**优先实现核心业务的异地多活**；判断依据是**业务影响**（受影响用户数量），不是业务是否「重要」。
     - 为什么登录最简单：每个中心都有所有用户的账号和密码，用户在哪个中心都能登录；A 中心宕机后到 B 中心重新登录即可。
     - 遗留问题（由技巧 4 收尾）：用户在 A 改了密码未同步到 B，到 B 无法登录怎么办。
  2. **技巧 2：保证核心数据最终一致性**
     - 误区：「我要所有数据都实时同步」。反证：业务要求越快越好，物理上做不到（光速/网络），**所有数据实时同步是达不到的目标**。
     - 三种缓解手段：
       1. **减少机房距离、搭高速网络**：类似同城异区，但跨城高速网络成本远超同城，一般只有巨头能承担；
       2. **减少数据同步，只同步核心业务相关数据**：不重要不同步、同步后没用不同步。例：登录产生的 token/session 数据量大，**不需要**同步（丢失后重新登录即可）；代价是用户体验（要重新输账号密码或点一次登录），但相比同步所有数据的代价可接受；
       3. **保证最终一致性，不保证实时一致性**（即 23 期 BASE）：A 机房注册用户，不要求 50 毫秒同步到所有机房，正常 5 分钟、异常甚至 1 小时或 1 天。
     - 最终一致性的**差异化处理**（判据）：账号信息——用户在 A 注册后 5 分钟内跑到 B，B 没有该数据 → B 需**按路由规则到 A 请求数据**；用户信息——5 分钟后同步也可以，不需额外措施，但用户会看到旧信息（体验问题，由技巧 4 收尾）。
  3. **技巧 3：采用多种手段同步数据**
     - 误区：「只使用存储系统的同步功能」。
     - 反例（存储自带同步不够用的证据）：
       - MySQL 5.1 复制是**单线程**，网络抖动或大量同步时延迟长，短则十几秒、长则十几分钟；且即使监控发现延迟也「只能干等」；
       - Redis 3.0 之前没有 Cluster 只有主从；**2.8 之前**从机宕机或断连重连都会触发**全量主从复制**，主机会生成内存快照（主机仍可服务），但作为读的从机长时间无法对外服务。
     - 结论：拓开思路，多种手段配合存储同步，甚至不用存储同步、改自研。
     - **五种手段与对应数据（原文给的组合）**

       | 手段 | 做法 | 适用数据 |
       |---|---|---|
       | 消息队列 | 账号数据通过消息队列同步到其他中心 | 账号（只创建、不修改不删除） |
       | 二次读取 | 本地读失败时按路由规则再去对端读一次（第一次本地、第二次对端） | 账号（兜住消息队列也延迟的情况） |
       | 存储系统同步 | 用数据库同步机制复制 | 密码（改动频率低，不可能 1 秒内连改多次）、用户信息 |
       | 回源读取 | 不同步数据；B 拿到 session id 后按路由判断归属，直接去 A 请求 | 登录 session（数据量大） |
       | 重新生成数据 | 回源失败（A 宕机）→ 登录失败，让用户重新在 B 登录，生成新 session | session |

     - 原文备注：以上仅示意，实际方案更复杂，还有很多细节。
  4. **技巧 4：只保证绝大部分用户的异地多活**
     - 误区：「我要保证业务 100% 可用」。答案：**没有巧妙办法**，物理规律（光速、网络、硬盘读写、极端异常不可控）决定无法 100% 解决；对策是「**忍**」——忍受一小部分用户/业务损失，否则为了最后 0.01% 的完美方案，可能连 99.99% 都保不住。
     - 受影响规模判据：实时强一致业务受影响的用户可能更多，**甚至达到 1/3**。例：银行转账必须在北京业务中心才可用，否则不允许自助转账。
     - 用业务手段换取多活（依然牺牲体验）：把「实时转账」改为「转账申请」——上海中心不立即转账，只记录请求后异步发起；北京不可用则等待重试；若 2 小时后北京恢复发现余额不足，则申请失败。代价是用户从「一次操作」变成「提交申请 + 确认结果」两步。
     - 三种安抚/补偿手段：**挂公告**（说明有问题和基本原因；不便说原因就发「技术哥哥正在紧急处理」这类轻松公告）；**事后补偿**（代金券、小礼包）；**补充体验**（如转账结果直接发短信，免去用户反复登录确认）。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 1 秒 | 多中心时钟误差容忍上限（超过 1 秒，「最后修改生效」就可能颠倒） |
  | 日活 1000 万 / 每天注册几万 / 改用户信息不到 1 万 | 论证应保登录而非注册/用户信息（按受影响用户数判断） |
  | 50 毫秒 | 「不要求这么快同步」的对比基准（业务不强求实时） |
  | 5 分钟 / 1 小时 / 1 天 | 最终一致性的三档时限（正常/异常/兜底） |
  | MySQL 5.1 单线程复制延迟：十几秒 ~ 十几分钟 | 论证存储自带同步不可靠 |
  | Redis 3.0 / 2.8 | 版本阈值：3.0 前无 Cluster；2.8 前重连触发全量复制 |
  | 0.01% vs 99.99% | 「为极小比例做完美方案会拖垮整体」的量级论证 |
  | 1/3 | 实时强一致业务可能受影响的用户比例上限 |
  | 2 小时 | 「转账申请」等待重试的时间样例（北京恢复后可能余额不足） |

- **案例/数据**
  - 用户子系统（注册/登录/用户信息）+ 用户分区架构（每分区有其他数据备份，路由层按邮箱/手机号 Hash 定中心）→ 论证「全部多活」无解。
  - 手机号唯一性冲突 → 注册多活无解；改业务规则（一号多账号）代价极大。
  - 时间合并 + 中心间时钟误差 >1 秒 → 先改的不生效。
  - 日活 1000 万：登录 1000 万 vs 每天注册几万 vs 改信息不到 1 万 → 应保登录。
  - 几百万用户登录不了 → 客服热线被打爆、微博微信到处传宕机 → 互联网大事件。
  - token/session 不同步 → 用户重新登录的代价 < 同步所有数据的代价。
  - MySQL 5.1 复制延迟十几秒~十几分钟且只能干等；Redis 2.8 前重连全量复制 → 从机长时间不可读。
  - 银行转账：小明在北京开户，若不限定北京中心，则 1 万元可在北京转张三 1 万、上海再转李四 1 万，两次都成功 → 必须限定单中心；改用「转账申请」可实现多活但牺牲体验。

- **反例与坑**
  - 追求「所有业务都多活」→ 注册这类业务的多活本身无解，硬做会改核心业务规则。
  - 用「最后修改生效」做跨中心合并却不校时 → 误差 1 秒就颠倒顺序。
  - 用全局唯一递增 ID 解决冲突而不考虑它自己也要多活 → 成本转嫁，问题没消失。
  - 追求「所有数据实时同步」→ 物理上不可达。
  - 只依赖存储系统同步（MySQL 单线程复制、Redis 2.8 前全量复制）→ 极端场景下无法满足业务。
  - 追求 100% 业务可用 → 为 0.01% 牺牲 99.99%。
  - 实时强一致业务硬做多活 → 双花类漏洞（转账案例）。
  - 做了多活却不做用户安抚 → 体验损失无人兜底。

- **原文金句**
  - 「答案其实很简单：优先实现核心业务的异地多活架构！」
  - 「所有数据都实时同步，实际上是一个无法达到的目标。」
  - 「异地多活也无法保证 100% 的业务可用，这是由物理规律决定的，光速和网络的传播速度、硬盘的读写速度、极端异常情况的不可控等，都是无法 100% 解决的。」
  - 「采用多种手段，保证绝大部分用户的核心业务异地多活！」

- **可迁移到知识库的主题**
  - 四个「完美主义误区」及其反证的通用结构（想要全部 → 举一个无解的具体场景 → 收敛到核心）。
  - 「核心」的判定标准从「业务重要性」改为「受影响用户数量」（登录 vs 注册 vs 用户信息）。
  - 五种数据同步手段与数据特征的对应表（消息队列/二次读取/存储同步/回源读取/重新生成）。
  - 「时间合并需要全局时钟」这个隐蔽前提，以及 1 秒误差导致顺序颠倒。
  - 无法 100% 可用时的三层兜底：业务改造（转账申请）+ 公告 + 补偿。

### 30丨异地多活设计4步走

- **核心结论**
  掌握 4 大技巧后，跨城异地多活的具体设计按四步走：**业务分级 → 数据分类 → 数据同步 → 异常处理**。前两步是「选定范围并识别数据特征」，第三步是「按特征配同步方案」，第四步是「为必然发生的异常兜底」。

- **完整判据/清单/步骤**
  1. **第 1 步：业务分级**
     - 目的：按标准挑出核心业务，只为它设计多活，降低整体复杂度与实现成本。
     - 三个分级标准：
       1. **访问量大的业务**：用户管理系统里登录访问量最大；
       2. **核心业务**：QQ 的主场景是聊天，QQ 空间虽重要但次于聊天；
       3. **产生大量收入的业务**：QQ 聊天难插广告、难带来收益；QQ 空间可插很多广告 → **从收入角度，QQ 空间做多活的优先级反而高于 QQ 聊天**。
     - 产出：核心业务清单（案例：登录同时符合「访问量大」和「核心业务」两条 → 定为核心业务）。
  2. **第 2 步：数据分类**
     - 目的：识别核心业务相关的**所有数据及其特征**，这些特征会影响后续方案。
     - 五个分析维度：

       | 维度 | 含义 | 对方案的影响 | 原文样例 |
       |---|---|---|---|
       | 数据量 | 总量 + 新增/修改/删除量 | 增量就是要同步的数据；量越大同步延迟几率越高 | — |
       | 唯一性 | 是否要求多个异地机房产生的同类数据必须唯一 | 不要求唯一 → 两地都可产生；要求唯一 → 要么单点产生，要么设计唯一生成算法 | 用户 ID：两机房不同用户生成相同 ID 即业务出错 |
       | 实时性 | A 机房改数据后要求多久同步到 B | 要求越高，同步方案越复杂 | — |
       | 可丢失性 | 数据能否丢失 | 可丢失 → 方案可简化 | session 可丢失（重登即可）；用户 ID 不可丢失（丢了就丢好友、钱等） |
       | 可恢复性 | 丢失后能否用某种手段恢复 | 可恢复 → 影响小 → 可降低架构复杂度 | 微博重发一篇即恢复；密码可通过找回重设；账号丢失则不可恢复 |

     - 产出：核心业务的数据特征表（案例以登录业务为例）。
  3. **第 3 步：数据同步**
     - 目的：按数据特点设计不同同步方案。三种常见方案：

       | 方案 | 机制 | 优点 | 缺点/适用判据 |
       |---|---|---|---|
       | 存储系统同步 | MySQL 主从、主主同步等 | 最常用最简单（主流存储几乎都有） | 通用、无法按业务特点定制；如 MySQL 只有一个同步通道，为保事务性，量大或网络延迟时同步延迟严重 |
       | 消息队列同步 | 独立 MQ（Kafka、ActiveMQ、RocketMQ） | 灵活、可解耦 | **只适合无事务性、无时序性要求**的数据：账号 A/B 先后注册可乱序；密码先改 m 再改 n 必须保序，不能走 MQ |
       | 重复生成 | 数据不同步，各机房各自生成 | 无需同步成本 | 只适合**可重复生成**的数据：登录产生的 cookie、session、缓存 |

     - 产出：按数据特征分配同步方案（案例给出登录业务各类数据的方案表）。
  4. **第 4 步：异常处理**
     - 前提认知：无论同步方案如何设计，极端异常下**总会有部分数据异常**（延迟、丢失、不一致）。
     - 三个目的：①问题发生时避免少量数据异常导致整体业务不可用；②问题恢复后修正异常数据；③安抚用户、弥补损失。
     - 四类措施：

       | 措施 | 机制 | 设计关键点（原文） |
       |---|---|---|
       | **多通道同步** | 多种方式同时同步，某通道故障可由其他通道补 | ①一般两通道即可（更多通道降风险但成本大增）；②数据库通道与 MQ 通道**不能共用同一网络连接**（否则网络故障两通道同时挂，可一个走公网一个走内网）；③数据必须**可重复覆盖**（先到后到结果一致）：新建账号符合、密码不符合 |
       | **同步和访问结合** | 异地机房通过**接口**访问对端拿数据 | ①接口通道与数据库同步通道不能共用网络（如接口走公网、同步走内网）；②数据有**路由规则**（A/B/C 三机房时，B 拿到不属自己的数据要能判断访问 A 还是 C）；③有同步通道时**优先读本地，本地读不到再走接口**，以降低跨机房访问量，适合实时性要求非常高的数据 |
       | **日志记录** | 关键操作前后各记一条日志，存独立位置；恢复后与数据对比修复 | 三级保存方式对应三级故障：①服务器上存日志 + 数据库存数据（应对单台数据库服务器故障/宕机）；②本地独立系统存日志（应对业务服务器与数据库同时宕机，如部署在同机架/同电源线路）；③日志异地保存（应对机房宕机）。故障越严重 → 方案复杂度与成本越高 |
       | **用户补偿** | 人工补偿，弥补系统兜不住的那一小部分 | 定位：系统方案保证 99.99% 用户不受影响，人工补偿弥补 0.01% 的损失；常见形式：代金券、礼包、礼品、红包；有时成本较大但综合收益值得 |

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 三条分级标准 | 业务分级的判据集合（访问量/核心/收入） |
  | 五个数据维度 | 数据分类的判据集合（量/唯一性/实时性/可丢失/可恢复） |
  | 三种同步方案 | 数据同步的方案集合（存储/MQ/重复生成） |
  | 四类异常措施 | 异常处理的措施集合（多通道/同步+访问/日志/补偿） |
  | 两通道 | 多通道同步的推荐数量（更多则成本大增） |
  | 99.99% / 0.01% | 系统方案与人工补偿的分工边界 |
  | 约 200 元人民币 | 炉石传说 2017 回档补偿的单用户价值 |
  | 1000 游戏金币 + 15 个卡牌包（经典 ×5、上古之神的低语 ×5、龙争虎斗加基森 ×5） | 补偿的具体构成（等价 25 卡牌包） |
  | 2017 年 1 月 18 日 18 点 | 补偿资格的时间分界（此前登录过国服玩家） |

- **案例/数据**
  - 用户管理系统：登录（访问量大 + 核心业务）→ 定为核心业务。
  - QQ 聊天 vs QQ 空间：从核心业务看聊天优先，从收入看空间优先 → 分级标准会给出不同结论，需显式取舍。
  - session 可丢失 vs 用户 ID 不可丢失；微博可恢复、密码可找回、账号不可恢复 → 五维标签直接决定同步方案。
  - 账号注册可乱序（A、B 顺序无关）→ 可走 MQ；密码改 m 再改 n 必须保序 → 不能走 MQ。
  - 账号数据「MQ + MySQL 主从」双通道（除非两通道同时故障）→ 多通道同步。
  - B 机房通过接口访问 A 机房取账号信息 → 同步与访问结合。
  - 炉石传说 2017 回档：每人约 200 元补偿，玩家反而「求暴雪再来一次回档」→ 补偿可显著改善口碑。

- **反例与坑**
  - 业务分级只按「重要性」不做量化 → 产品/业务方各说各的重要（原文思考题正是此困境）。
  - 数据分类漏掉「可恢复性」→ 把可恢复数据当成不可恢复，方案过度复杂（或反之，低估损失）。
  - 用 MQ 同步有严格时序要求的数据（密码）→ 顺序错乱导致密码错误。
  - 用存储同步处理大流量/大增量 → MySQL 单通道，延迟严重且无法定制。
  - 双通道走同一网络 → 网络故障时两通道同时失效。
  - 双通道同步「不可重复覆盖」的数据 → 先后到达导致最终值错误。
  - 日志只存本机 → 机房级故障时日志与数据一起没了。
  - 只做技术方案、不留人工补偿预算 → 0.01% 的用户无人兜底。

- **原文金句**
  - 「按照一定的标准将业务进行分级，挑选出核心的业务，只为核心业务设计异地多活，降低方案整体复杂度和实现成本。」
  - 「无论数据同步方案如何设计，一旦出现极端异常的情况，总是会有部分数据出现异常的。」
  - 「系统的方案是为了保证 99.99% 的用户在故障的场景下业务不受影响，人工的补偿是为了弥补 0.01% 的用户的损失。」
  - 「只要在 2017 年 1 月 18 日 18 点之前登录过国服《炉石传说》的玩家，均可获得与 25 卡牌包等值的补偿。」

- **可迁移到知识库的主题**
  - 业务分级的三标准及「标准之间会打架」的处理（QQ 聊天 vs QQ 空间）。
  - 数据分类五维标签法，可直接作为「数据特征 → 同步方案」的决策矩阵。
  - 三种同步方案的适用判据，尤其是「MQ 不能用于有时序要求的数据」。
  - 四类异常处理措施的设计约束（通道隔离、可重复覆盖、路由规则、日志分级、人工补偿边界）。

### 31丨如何应对接口级的故障？

- **核心结论**
  异地多活应对的是**系统级故障**（宕机、机房、网络），影响大但概率小；接口级故障则是「系统没宕机、网络没中断，但业务出问题了」（响应缓慢、大量超时、大量异常），主因是压力/负载过高。应对手段四种：**降级、熔断、限流、排队**，核心思想与异地多活一致——**优先保证核心业务、优先保证绝大部分用户**。

- **完整判据/清单/步骤**
  1. **故障成因清单**
     - 内部原因：程序 bug 导致死循环；某个接口导致数据库慢查询；程序逻辑不完善耗尽内存。
     - 外部原因：黑客攻击；促销/抢购带来超出平时几倍甚至几十倍的用户；第三方系统大量请求；第三方系统响应缓慢。
  2. **降级**
     - 定义：把某些业务或接口的功能降低——可以只提供部分功能，也可以完全停掉所有功能（论坛降为只能看帖 → 再降为只能看帖和评论不能发评论；App 日志上传接口可完全停掉一段时间）。
     - 判据：**丢车保帅**，优先保核心业务（论坛 90% 流量是看帖 → 优先保看帖；日志上传只是辅助 → 可停）。
     - 两种实现方式：

       | 方式 | 做法 | 优点 | 缺点 |
       |---|---|---|---|
       | 系统后门降级 | 系统预留降级 URL，访问即执行降级指令，指令由 URL 参数传入；有一定安全隐患，故 URL 中加密码等安全措施 | 实现成本低 | 服务器数量多时要一台台操作，效率低；故障处理争分夺秒时很浪费时间 |
       | 独立降级系统 | 把降级操作独立到单独系统，可实现复杂权限管理、批量操作 | 支持批量与权限 | 需额外建设一套系统 |

  3. **熔断**
     - 与降级的分界（原文核心判据）：**降级应对系统自身的故障，熔断应对依赖的外部系统故障**。
     - 触发条件与机制：A 服务的 X 功能依赖 B 的接口 → B 响应很慢时 A 的 X 也被拖慢 → A 的线程都卡在 X 上 → A 其他功能被卡住。此时 A **不再请求 B 的这个接口**，A 内部发现是请求 B 该接口就**立即返回错误**，避免 A 被拖慢甚至拖死。
     - 实现要点两个：①**必须有统一的 API 调用层**，由它采样/统计；接口调用散落在代码各处就无法统一处理；②**阈值设计**：如「1 分钟内 30% 的请求响应时间超过 1 秒就熔断」，其中「1 分钟」「30%」「1 秒」都影响最终效果；实践路径是先分析定阈值 → 上线观察 → 再调优。
  4. **限流**
     - 与降级的分界：降级从**功能优先级**角度考虑；限流从**用户访问压力**角度考虑。
     - 定义：只允许系统能承受的访问量进来，超出能力的请求被丢弃；「丢弃」体验不好，但保证一部分请求正常响应总比全部不能响应好。
     - 两类方式：

       | 类别 | 子类 | 含义与样例 |
       |---|---|---|
       | **基于请求限流** | 限制总量 | 限制某指标累积上限：某直播间总用户上限 100 万，超过后新用户无法进入；抢购商品只有 100 个，限制参与用户上限 1 万，1 万之后直接拒绝 |
       | | 限制时间量 | 限制一段时间内某指标上限：1 分钟内只允许 10000 个用户访问；每秒请求峰值最高 10 万 |
       | **基于资源限流** | 内部关键资源 | 连接数、文件句柄、线程数、请求队列；如 Netty 实现服务器，请求先入队列，队列长度最大 10000，满了拒绝后续请求；或 CPU 占用率超 80% 就开始拒绝新请求 |

     - 基于请求限流的两大实践难题：①**阈值难找**（设定 1 分钟 10000 用户，可能 6000 就扛不住；也可能到 10000 压力还不大却已开始丢用户）；②**硬件相关**（32 核与 64 核差别很大，且 64 核性能不是 2 倍，可能是 1.5 倍甚至 1.1 倍，不能靠简单数学换算）。找阈值的两条路径：性能压测（有覆盖场景有限的缺陷）、逐步优化（先设定阈值 → 上线观察 → 不合理再调）。基于请求限流更适合**业务功能比较简单**的系统（负载均衡、网关、抢购）。
     - 基于资源限流的两个难点：如何确定**关键资源**、如何确定关键资源的**阈值**；同样是「先推断选择 → 测试验证 → 上线观察 → 优化」的调优过程。优点：比基于请求限流更能有效反映当前系统压力。
  5. **排队**
     - 定位：**限流的一个变种**——限流是直接拒绝用户，排队是让用户等待一段时间；等了很久再进系统，体验不一定比限流好（12306 是最有名的例子）。
     - 实现约束：排队需临时缓存大量业务请求，单个系统内部无法缓存这么多数据 → 一般要用**独立系统**实现（如 Kafka 缓存用户请求）。
     - 参考架构（1 号店「双 11」秒杀排队系统）三模块：
       1. **排队模块**：接收抢购请求，先入先出保存；每个参加秒杀的商品一个队列，队列大小按参与商品数量（或加点余量）自定义；
       2. **调度模块**：排队模块到服务模块的动态调度；不断检查服务模块，一旦处理能力有空闲，就从队头把用户请求调入服务模块并分发；它是中介，还承担**调节系统处理能力**的职责——可根据服务模块实际处理能力动态调节向排队系统拉取请求的速度；
       3. **服务模块**：调用真正业务处理并返回结果，调用排队模块接口回写业务处理结果。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 90% 流量是看帖 | 论坛降级时优先保看帖的判据 |
  | 1 分钟 / 30% / 1 秒 | 熔断阈值的三个参数（窗口、比例、响应时间） |
  | 直播间 100 万用户上限 | 限制总量的样例 |
  | 商品 100 个 / 参与上限 1 万 | 限制总量的样例（抢购） |
  | 1 分钟 10000 个用户；每秒峰值 10 万 | 限制时间量的样例 |
  | 队列长度 10000（Netty） | 基于资源限流的样例 |
  | CPU 占用率 80% | 基于资源限流的触发阈值样例 |
  | 32 核 vs 64 核：1.5 倍甚至 1.1 倍 | 论证阈值不能按硬件指标线性换算 |
  | 几倍甚至几十倍的突增用户 | 外部原因的量级（促销/抢购） |

- **案例/数据**
  - 数据库慢查询耗尽服务器资源 → 读写超时 → 用户看到「一会异常一会正常」→ 说明接口级故障的表现形态。
  - 论坛「只能看帖 → 只能看帖和评论」、App 日志上传停掉 → 降级的两档粒度。
  - A 服务 X 功能依赖 B 接口，B 慢拖死 A → 熔断的触发与收益。
  - 1 号店双 11 秒杀排队（排队/调度/服务三模块）→ 排队需要独立系统 + 动态调度。
  - 12306 排队 → 排队体验不一定优于限流。

- **反例与坑**
  - 混淆降级与熔断 → 一个是「自己不行了就少做」，一个是「别人不行了就别等」。
  - 熔断没有统一 API 调用层 → 调用散落各处，无法统一采样与拦截。
  - 阈值拍脑袋且不调优 → 要么过早丢弃（压力不大就限流），要么形同虚设。
  - 按 CPU 核数线性推算限流阈值 → 64 核不是 32 核的 2 倍（可能 1.5 甚至 1.1 倍）。
  - 降级只靠后门 URL → 机器多时一台台操作，故障时来不及。
  - 在单机内做排队 → 缓存不下大量请求。
  - 认为排队比限流「更友好」→ 用户等很久再进系统，体验未必更好。

- **原文金句**
  - 「接口级故障的典型表现就是系统并没有宕机，网络也没有中断，但业务却出现问题了。」
  - 「降级的核心思想就是丢车保帅，优先保证核心业务。」
  - 「降级的目的是应对系统自身的故障，而熔断的目的是应对依赖的外部系统故障的情况。」
  - 「限流指只允许系统能够承受的访问量进来，超出系统访问能力的请求将被丢弃。」

- **可迁移到知识库的主题**
  - 接口级故障 vs 系统级故障的判别（是否宕机/断网）与成因清单（内部 3 类 / 外部 4 类）。
  - 降级 / 熔断 / 限流 / 排队四者的**分界判据**（自身 vs 依赖；功能优先级 vs 访问压力；拒绝 vs 等待）。
  - 熔断的两个实现前提（统一调用层、阈值可调优）。
  - 基于请求限流 vs 基于资源限流的对比，以及「阈值不可线性换算」的硬件反例。
  - 排队系统的三模块职责与「调度模块动态调节拉取速度」这一设计要点。

### 32丨可扩展架构的基本思想和模式

- **核心结论**
  软件与硬件/建筑最大的差异是**可扩展**：硬件出厂即定型、建筑完工即定型，软件若长期不更新反而说明没有生命力。可扩展设计的主要思考点是「如何避免扩展时改动范围太大」，而所有方法万变不离其宗，基本思想就是一个字——**拆**。按不同思路拆会得到不同架构：面向流程→分层，面向服务→SOA/微服务，面向功能→微内核。

- **完整判据/清单/步骤**
  1. **基本思想：拆**
     - 定义：把原本大一统的系统拆成多个规模小的部分，扩展时只改其中一部分，无需到处改 → 减少改动范围、降低改动风险。
     - 与日常「拆」的区别：拆房子/拆快递是破坏性的、拆完就扔；软件系统的拆是**建设性的**（要让系统更优美），因此难度高得多。
  2. **三种拆分思路**（按范围从大到小：**流程 > 服务 > 功能**）

     | 思路 | 定义 | 判据/边界 |
     |---|---|---|
     | 面向流程拆分 | 把整个业务流程拆为几个阶段，每个阶段作为一部分 | 阶段由流程本身决定，与上层应用无关 |
     | 面向服务拆分 | 把系统提供的服务拆开，每个服务作为一部分 | 服务是「对外提供的能力」 |
     | 面向功能拆分 | 把系统提供的功能拆开，每个功能作为一部分 | 功能是某个服务内部的具体能力 |

  3. **用 TCP/IP 协议栈区分三个概念（原文的判别样例）**
     - **流程** = TCP/IP 四层模型：应用层 → 传输层 → 网络层 → 物理+数据链路层；不管应用层是什么，这个流程都不变。
     - **服务** = 应用层的 HTTP、FTP、SMTP（Web 服务 / 文件服务 / 邮件服务）。
     - **功能** = 每个服务提供的功能：HTTP 提供 GET、POST；FTP 提供上传下载；SMTP 提供邮件发送与收取。
  4. **学生信息管理系统的三种拆法**
     - 面向流程（4 层）：展示层（页面设计：登录/注册/信息管理/安全设置页面）→ 业务层（业务逻辑：登录/注册/信息管理/修改密码）→ 数据层（数据访问：增删改查、记日志）→ 存储层（MySQL、Memcache）。
     - 面向服务：注册、登录、信息管理、安全设置四个服务。
     - 面向功能：注册服务再拆为手机号注册/身份证注册/学生邮箱注册；登录服务拆为手机号/身份证/邮箱登录；信息管理拆为基本信息/课程信息/成绩信息；安全设置拆为修改密码/安全手机/找回密码。
  5. **为什么必须选一种拆法（判据）**
     - 不同拆分方式**本质上决定了系统的扩展方式**。
     - 不拆分也能控制改动范围的理想前提是：团队都是高手、熟悉业务、新人很快掌握细节——现实中不成立（菜鸟程序员按「哪里容易改」选改 A 还是 B；有人粗心；有人某天状态不好；新人不知历史代码为何「恶心」就顺手改漂亮）。
     - 因此**合理的拆分能强制保证：即使程序员出错，出错范围也不会太广、影响也不会太大**。
  6. **三种拆法各自的扩展优势**
     - 面向流程：扩展时多数只需改一层，少数改关联的两层，不会所有层同时改。例：存储层从只支持 MySQL 扩展到同时支持 MySQL 与 Oracle → 只需改存储层和数据层，展示层与业务层不动。
     - 面向服务：扩展某服务或新增服务时只改相关服务。例：注册服务加「学号注册」→ 只改注册服务和登录服务，信息管理与安全设置不动。
     - 面向功能：扩展某功能或新增功能时只改相关功能。例：加「学号注册」→ 新增一个功能模块 + 改登录功能模块，其他不受影响。
  7. **三种思路对应的三种架构与组合方式**
     - 面向流程 → 分层架构；面向服务 → SOA、微服务；面向功能 → 微内核架构。
     - 三者**不是非此即彼**，可组合：整体用微服务（注册/登录/信息管理/安全四个服务）→ 注册服务内部用分层架构 → 登录服务内部用微内核架构。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 一个字「拆」 | 可扩展设计的基本思想（原文主张） |
  | 流程 > 服务 > 功能 | 三个概念的范围排序 |
  | TCP/IP 四层 | 流程的样例（4 个阶段） |
  | 学生管理系统 4 层（展示/业务/数据/存储） | 面向流程拆分的样例 |
  | 4 个服务 / 每服务 3 个功能 | 面向服务与面向功能拆分的粒度样例 |
  | 3 种架构映射 | 分层 / SOA·微服务 / 微内核 |

- **案例/数据**
  - Windows 3.0 → 95 → XP → 10 持续演进 → 说明有生命力的软件必须不断迭代。
  - 金字塔矗立千年结构不变、CPU 出厂不再回厂加工 → 反衬软件的可扩展特性。
  - TCP/IP 四层 / HTTP·FTP·SMTP / GET·POST → 区分流程、服务、功能。
  - 学生管理系统三种拆法得到三张差异很大的架构图 → 拆法决定架构。
  - 存储层从 MySQL 扩展到 MySQL+Oracle → 只改两层。
  - 注册服务加「学号注册」→ 只改注册 + 登录两个服务。
  - 微服务 + 分层 + 微内核组合 → 三种拆法可共存于一个系统。

- **反例与坑**
  - 以为「不拆也能写得好」→ 依赖「团队全是高手」这一不成立的前提。
  - 随便挑一种拆法 → 拆法决定扩展方式，选错等于把扩展成本埋进未来。
  - 把「流程/服务/功能」混用 → 层次混乱（如把 HTTP 的 GET 说成服务）。
  - 只拆不约束边界 → 拆完仍到处改，白拆。
  - 认为三种架构互斥 → 原文明确可组合。

- **原文金句**
  - 「所有的可扩展性架构设计，背后的基本思想都可以总结为一个字：拆！」
  - 「形象地说，软件系统中的"拆"是建设性的，因此难度要高得多。」
  - 「不同的拆分方式，本质上决定了系统的扩展方式。」
  - 「合理的拆分，能够强制保证即使程序员出错，出错的范围也不会太广，影响也不会太大。」

- **可迁移到知识库的主题**
  - 「拆」作为可扩展唯一基本思想的论证（建设性拆 vs 破坏性拆）。
  - 流程 / 服务 / 功能的三级范围判据与 TCP/IP 判别样例。
  - 「拆法决定扩展方式」以及不拆分的现实前提为何不成立。
  - 三种拆法与三种架构（分层/SOA·微服务/微内核）的映射及组合用法。

### 33丨传统的可扩展架构模式：分层架构和SOA

- **核心结论**
  可扩展架构模式发展缓慢，微服务成了「银弹」式的滥用对象（高性能、高可用都用微服务，实际是大炮打蚊子，违背「合适原则」和「简单原则」）。传统模式有两个：**分层架构**（靠隔离关注点支撑扩展，代价是冗余与性能）与 **SOA**（靠服务 + ESB + 松耦合解决企业异构系统重复建设，代价是 ESB 的复杂度与性能瓶颈）。

- **完整判据/清单/步骤**
  1. **分层架构（N 层架构）**
     - 基本判据：N 至少是 2 层；常见 3 层（MVC、MVP）、4 层；**5 层比较少见**，一般只有复杂系统（如操作系统内核）才达到或超过 5 层。
     - 三种划分维度（对象 + 维度）：

       | 形态 | 划分对象 | 划分维度 | 依赖关系 |
       |---|---|---|---|
       | C/S、B/S | 整个业务系统 | 用户交互（交互部分独立一层，支撑交互的后台另一层） | 两层 |
       | MVC、MVP | 单个业务子系统 | 职责 | **比较灵活**，MVC 中各层两两交互 |
       | 逻辑分层（OS 内核、TCP/IP、Android、J2EE） | 单个子系统或整个业务系统 | 职责 | **自顶向下依赖** |

     - 设计核心判据：**各层之间的差异足够清晰、边界足够明显**，看到架构图就能看懂整个架构——这也是「不能分太多层」的原因。否则同一功能小明认为该放 A 层、老王认为该放 B 层 → 分层混乱，落地后 A、B 层乱成一锅粥，失去分层意义。
     - 支撑扩展的机理：**隔离关注点（separation of concerns）**，每层组件只处理本层逻辑（展示层只管展示、业务层只管业务），扩展某层时其他层不受影响。例：Linux 内核增加新文件系统只需改文件存储层。
     - 但「分层」不等于「能扩展」，还必须满足：**层与层之间的依赖是稳定的**。反例：Linux 若只是把 ext2/ext3/reiser 划成「文件系统层」而没有 **VFS 抽象**，则新增文件系统后所有基于文件系统的功能都要适配新接口；有了 VFS，只需 VFS 适配新文件系统，其他功能依赖 VFS 不受影响。
     - 接口是否独立成层：操作系统这类复杂系统，接口本身可以成为独立一层（如 VFS 独立）；简单业务系统里接口可能只是几个 Java interface，独立成层就「比较重」（如 J2EE 的 Presentation Layer 与 Business Layer 之间硬拆接口层显得多余）。
     - **层层传递约束**：分层确定后业务流程按层依次传递，**不能在层之间跳跃**（C/S 中用户必须先用 C 层再由 C 转 S；J2EE 4 层收到请求后必须按层传递）。
       - 好处：强制把依赖限定为两两依赖，降低整体复杂度（Business Layer 被 Presentation Layer 依赖，自己只依赖 Persistence Layer）。
       - 代价：**冗余**——不管业务多简单，每层都要参与，甚至每层都写一个简单包装函数。
     - 冗余的具体证据：「查看头像」功能需要 Presentation Layer 的 `AvatarView.displayAvatar` → Business Layer 的 `AvatarBizz.getAvatarUrl` → Persistence Layer 的 `AvatarDao.getAvatarUrl`，后两者**名称和参数一模一样**。
     - 是否可绕过分层：**不建议**。一旦自由绕过（Presentation 直接访 Persistence、Business 直接访 Database），时间一长架构就混乱，扩展时无法控制受影响范围，牵一发动全身。冗余的代价换来的复杂度其实很低（`getAvatarUrl` 实现极简，不会增加太多工作量）。
     - 性能代价：每次请求都要穿越所有分层，有些事是多余的。但原文判断：这点损失在 80 年代可能明显，**现在硬件与网络性能已质变，绝大部分场景可忽略不计**。
  2. **SOA**
     - 定义与历史：Service Oriented Architecture，诞生于上世纪 90 年代；**1996 年** Gartner 两位分析师 Roy W. Schulte 与 Yefim V. Natis 发表第一个 SOA 报告；**2005 年** Gartner 预言 2008 年 SOA 将成为 80% 开发项目的基础——历史证明「并不十分靠谱」。
     - 落地分布：更多在传统企业（制造、金融）落地，互联网行业没有大规模实践；互联网最早推行 SOA 的是亚马逊（贝索斯推动，间接促成后来云计算）。
     - 诞生背景（三个问题）：
       1. 企业各部门有独立 IT 系统（人力/财务/销售），功能重复建设（员工离职要在三个系统分别删权限）；
       2. 各系统采购自不同供应商、技术不同，企业不太可能基于它们重构；
       3. 业务发展后流程需要多系统协作，但各系统无标准实现（人力 Java 对外 RPC、财务 C# 对外 SOAP），每次新流程都要协调大量系统并定制开发，效率很低。
     - 三个关键概念：

       | 概念 | 原文定义 | 关键判据 |
       |---|---|---|
       | 服务 | 所有业务功能都是一项服务；服务意味着对外提供**开放的能力**，其他系统要用时无须定制开发 | 服务可大可小（人力资源管理是一项服务，人员基本信息管理、组织结构管理也可各自独立成服务）；粗粒度还是细粒度要按企业实际情况判断 |
       | ESB | Enterprise Service Bus，企业服务总线；参考计算机总线概念，把企业内各服务连接起来 | 目的是**屏蔽异构系统各不相同的接口方式**，达到高效互联互通 |
       | 松耦合 | 减少各服务间的依赖和互相影响 | 服务独立运行，甚至不清楚有多少依赖；不松耦合则一个服务升级会让依赖它的服务全故障；但「真正做到松耦合并没有那么容易」，完全后向兼容是复杂任务 |

     - SOA 的作用层级判据：SOA 是**高层级架构理念**——可以说「某企业采用 SOA 架构构建 IT 系统」，但不会说「某个独立系统采用 SOA 架构」。原因：人力系统本身可能就是采购的、ESB 也是采购的，若再内部拆子服务并部署独立 ESB，成本高且无收益。
     - ESB 的诟病（原文逐条）：需实现协议转换、数据转换、透明的动态路由；例：ESB 把 JSON 转 Java；把 REST 协议转成 RMI 和 AMQP 两个不同协议。
     - ESB 复杂度来源：协议有很多种（JMS、WS、HTTP、RPC），数据格式有很多种（XML、JSON、二进制、HTML），互转工作量和复杂度都很大，且转换要耗大量计算性能；**ESB 承载消息太多时会成为整个系统的性能瓶颈**。
     - ESB 的辩护：SOA 的 ESB 设计是**无奈之举**——企业应用 SOA 时异构系统已存在多年，完全重写或按统一标准改造的成本非常大，只能靠 ESB 适配存量系统。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | N ≥ 2 层 | 分层架构的最小层数 |
  | 5 层及以上 | 少见，只有复杂系统（OS 内核）才达到 |
  | 3 层 / 4 层 | 常见分层（MVC/MVP；J2EE 4 层） |
  | 1996 年 | 第一份 SOA 报告（Gartner，Schulte & Natis） |
  | 2005 年 → 2008 年 → 80% | Gartner 预言及其落空 |
  | 4 层 | J2EE 的层数与「层层传递」的样例 |
  | 3 层包装函数（AvatarView / AvatarBizz / AvatarDao） | 分层冗余的量化样例 |

- **案例/数据**
  - Linux 内核新增文件系统只改文件存储层 → 隔离关注点支撑扩展。
  - Linux VFS 抽象 → 没有 VFS 则每加文件系统都要改所有上层功能；有 VFS 只改 VFS 适配。
  - J2EE Presentation/Business/Persistence 三层同名方法 → 分层冗余，但实现简单、复杂度低。
  - 员工离职需在人力/财务/销售三系统分别删权限 → SOA 诞生背景（重复建设）。
  - 人力系统 Java+RPC、财务系统 C#+SOAP → 异构系统协作无标准，ESB 的必要性。
  - ESB 把 JSON 转 Java、把 REST 转 RMI+AMQP → ESB 的工作量与性能成本。
  - 亚马逊内部系统均以服务方式构造 → 间接催生云计算。

- **反例与坑**
  - 把微服务当银弹 → 高性能/高可用场景也上微服务，大炮打蚊子，违背合适原则与简单原则。
  - 分层分得太细 → 层间差异不清晰、边界模糊，功能归属争议，落地后混乱。
  - 只分层不做稳定依赖抽象（缺 VFS）→ 扩展时仍要改一大片。
  - 为「省一次调用」绕过中间层 → 架构逐渐混乱，扩展失控。
  - 简单业务系统硬拆独立接口层 → 显得多余、增加无谓复杂度。
  - 指望分层提升性能 → 恰好相反，分层有冗余与性能损失（尽管现代可忽略）。
  - 让单个系统内部也套一套 SOA + 独立 ESB → 成本高、无收益（SOA 是企业级理念）。
  - 把 ESB 做成什么都管的中心 → 承载消息多时自身成为性能瓶颈。
  - 误以为 SOA 已被淘汰 → 传统企业（制造、金融）仍是主要落地场景。

- **原文金句**
  - 「分层架构设计最核心的一点就是需要保证各层之间的差异足够清晰，边界足够明显，让人看到架构图后就能看懂整个架构。」
  - 「分层架构之所以能够较好地支撑系统扩展，本质在于隔离关注点（separation of concerns）。」
  - 「分层结构的代价就是冗余。」
  - 「SOA 最广为人诟病的就是 ESB。」

- **可迁移到知识库的主题**
  - 分层的三种划分维度（用户交互/职责-灵活/职责-自顶向下）及其代表形态。
  - 「层间边界清晰 + 依赖稳定」两个必要条件，以及 VFS 作为反例/正例的对照。
  - 分层冗余（同名包装函数）与「不建议绕过」的取舍论证。
  - SOA 的三概念（服务/ESB/松耦合）与「SOA 只适用于企业级」的层级判据。
  - ESB 的复杂度与性能瓶颈，以及「ESB 是兼容存量系统的无奈之举」这一定性。

### 34丨深入理解微服务架构：银弹or焦油坑？

- **核心结论**
  微服务不是 Martin Fowler 提出的（他只是系统阐述），其历史可追到 2005 年。它与 SOA 的关系有三种流行观点，原文通过**服务粒度、服务通信、服务交付、应用场景**四点对比，判定「微服务和 SOA 是相似但本质不同的架构理念」（第三种观点），二者无优劣、只有场景不同。若不加思考地采用，微服务会变成焦油坑——原文列了六个具体的坑。

- **完整判据/清单/步骤**
  1. **历史节点（判据：谁在什么时候提出/定型）**
     - 2005 年：Dr. Peter Rodgers 在 Web Services Edge 大会提出「Micro-Web-Services」；
     - 2011 年：一个软件架构工作组用「microservice」描述这种架构模式；
     - 2012 年：同一工作组正式确定用「microservice」代表该架构；
     - 2012 年：ThoughtWorks 的 James Lewis 在 QCon San Francisco 2012 演讲；
     - 2014 年：James Lewis 与 Martin Fowler 合写学术性文章详细阐述微服务。
  2. **与 SOA 关系的三种观点**
     - 观点一：微服务是 SOA 的实现方式（「用 HTTP RESTful 实现 ESB 的 SOA」「用 SOA 构建单个系统就是微服务」「微服务就是更细粒度的 SOA」）；
     - 观点二：微服务是**去掉 ESB 后**的 SOA（传统 SOA 最被诟病的是庞大复杂低效的 ESB，去掉 ESB 改轻量级 HTTP 就是微服务）；
     - 观点三：微服务是一种和 SOA **相似但本质不同**的架构理念（相似在都关注「服务」、都靠服务拆分解决可扩展性；不同在是否有 ESB、服务粒度、架构设计目标）。
     - 结论：**第三种观点**。
  3. **四点对比（判据表）**

     | 对比项 | SOA | 微服务 |
     |---|---|---|
     | 服务粒度 | 粗（「员工管理系统」就是一个服务） | 细（拆为员工信息管理、考勤管理、假期管理、福利管理等多个服务） |
     | 服务通信 | ESB 作为关键组件，负责服务定义、服务路由、消息转换、消息传递，**重量级** | 统一协议与格式（RESTful、RPC），**无须 ESB**；理念是 **Smart endpoints and dumb pipes（聪明的终端，愚蠢的管道）** |
     | 服务交付 | 无特殊要求（更多考虑兼容已有系统） | 要求**快速交付** → 需要自动化测试、持续集成、自动化部署等敏捷实践；否则规模一大（如超过 20 个微服务）就难以快速交付，部署成本呈指数上升 |
     | 应用场景 | 庞大、复杂、异构的企业级系统（系统发展多年、技术各异、内部开发 + 外部采购、无法推倒重来） | 快速、轻量级、基于 Web 的互联网系统（业务变化快、需快速尝试与交付、对外基本都是 HTTP RESTful 接口） |

     - 「dumb pipes」的含义（原文解释）：ESB 太强大——既知道每个服务的协议类型（RMI 还是 HTTP），又知道数据类型（XML 还是 JSON），还知道数据格式（2017-01-01 还是 01/01/2017）；微服务的 dumb pipes **只做消息传递，对消息格式和内容一无所知**。
     - Fowler 原文三关键词：**small、lightweight、automated**，是微服务与 SOA 的本质区别所在。
  4. **六个坑（原文逐条）**
     1. **服务划分过细，服务间关系复杂**：单个服务复杂度下降，但**整个系统复杂度上升**——微服务把系统内复杂度转移为系统间复杂度；理论上 n 个服务的复杂度是 `n×(n-1)/2`，整体复杂度随服务数量增加呈**指数级**增加（3 个服务关系简单，细粒度后单个服务小了但关系复杂很多）。
     2. **服务数量太多，团队效率急剧下降**：「微」字本身是陷阱；有的团队 5~6 人却拆出 30 多个微服务，人均维护 5 个以上；一个简单需求要涉及多个微服务，光接口就有 6~7 个；开发要设计多个接口、打开多个工程、调试部署多个程序、提测打多个包；测试要部署多个环境、准备多个微服务数据、测多个接口；运维每次上线要操作多个微服务且可能有依赖关系。
     3. **调用链太长，性能下降**：微服务间走 HTTP 或 RPC，每次调用必过网络；线上接口调用平均响应约 **50 毫秒**，一次用户请求经 6 次调用即 300 毫秒，很多高性能场景无法满足；为支撑只能大幅加硬件 → 硬件成本大幅上升。
     4. **调用链太长，问题定位困难**：任一微服务故障都会导致整个业务失败，且故障存在扩散现象。样例：Service C 数据库慢查询 → C 给 B 响应错误 → B 给 A 响应错误 → A 给用户响应错误；实际定位时没有图那么清晰，先查 A 可能花半小时到 1 小时才发现是 B 返回错误，再查 B 重复同样步骤……最后可能几小时才定位到 C 的数据库慢查询。若多个微服务同时发生不同类型故障（C 的数据库慢查询 + C 到 D 的网络故障），排查需要大量信息和人力。
     5. **没有自动化支撑，无法快速交付**：全靠人工时，微服务不但达不到快速交付，甚至不如大而全系统高效——没有自动化测试则每次要测大量接口；没有自动化部署则每次部署 6~7 个服务、几十台机器要逐台敲 shell；没有自动化监控则每次定位要人工查几十台机器、几百个微服务的状态与日志。
     6. **没有服务治理，微服务数量多了后管理混乱**：「lightweight」在规模变大后变成问题，三个具体场景——**服务路由**（某服务有 60 个节点部署在 20 台机器，其他依赖方如何知道部署情况）；**服务故障隔离**（60 个节点中 5 个故障，依赖方如何处理）；**服务注册和发现**（60 扩到 80 或缩到 40，增减节点如何让依赖方知道）。全靠人工则混乱，最终必须依赖自动化服务管理系统——于是微服务推崇的 lightweight **最终发展成和 ESB 几乎一样的复杂程度**。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 2005 / 2011 / 2012 / 2014 | 微服务概念的历史节点 |
  | 4 个服务（员工信息/考勤/假期/福利） | 微服务粒度细于 SOA 的样例 |
  | 超过 20 个微服务 | 无自动化支撑时「整体难以快速交付」的量级阈值 |
  | n×(n-1)/2 | 服务间关系数量的理论公式（复杂度指数增长） |
  | 5~6 人 / 30+ 微服务 / 人均 5+ 个 | 服务数量过多的团队反例 |
  | 6~7 个接口；打多个包；部署几十台机器 | 单需求跨服务的具体开销 |
  | 50 毫秒（单次调用平均响应） | 调用链成本基线 |
  | 6 次调用 → 300 毫秒 | 性能下降的量化样例 |
  | 半小时到 1 小时（定位一层） | 故障定位时间成本 |
  | 60 节点 / 20 台机器；5 个故障；60→80 或 60→40 | 服务治理三个场景的规模样例 |
  | 三个关键词 small / lightweight / automated | 微服务与 SOA 的本质区别 |

- **案例/数据**
  - 员工管理系统：SOA 里是一个服务，微服务里拆成四个 → 粒度差异。
  - C 数据库慢查询导致 A 报错 → 故障扩散与定位困难（逐层半小时~1 小时，累计几小时）。
  - C 数据库慢查询 + C→D 网络故障同时发生 → 多故障叠加时定位更复杂。
  - 60 节点部署 20 台机器的服务 → 路由/隔离/注册发现三个治理问题。
  - 5~6 人团队拆 30+ 微服务 → 效率急剧下降。
  - 6 次调用 × 50ms = 300ms → 调用链性能损耗。

- **反例与坑**
  - 以为 Martin Fowler 是微服务提出者 → 他只是系统阐述者。
  - 以为「微服务 = SOA」或「微服务 = SOA 去掉 ESB」→ 原文判定二者本质不同（四点差异）。
  - 把微服务当银弹，不考虑团队规模、业务发展、基础技术支撑 → 掉进焦油坑。
  - 迷信「微」字，把服务拆得越小越好 → 系统间复杂度按 n(n-1)/2 上升。
  - 没有自动化测试/部署/监控就上微服务 → 效率反而低于单体。
  - 相信 lightweight 不需要治理 → 规模一大，治理系统会长成另一个 ESB。
  - 拿微服务改造企业级异构系统 → 改造成本可能远超实施 SOA 的成本。

- **原文金句**
  - 「服务划分过细，单个服务的复杂度确实下降了，但整个系统的复杂度却上升了，因为微服务将系统内的复杂度转移为系统间的复杂度了。」
  - 「Martin Fowler 将微服务架构的服务通讯理念称为"Smart endpoints and dumb pipes"，简单翻译为"聪明的终端，愚蠢的管道"。」
  - 「随着微服务种类和数量越来越多，如果没有服务治理系统进行支撑，微服务提倡的 lightweight 就会变成问题。」
  - 「这时就会发现，微服务所推崇的"lightweight"，最终也发展成和 ESB 几乎一样的复杂程度。」

- **可迁移到知识库的主题**
  - 微服务与 SOA 的四维对比表（粒度/通信/交付/场景）与「第三种观点」的判定依据。
  - Small / Lightweight / Automated 三关键词，以及「automated 才是成败手」的反直觉结论。
  - 六个坑的完整清单，其中 n(n-1)/2、50ms×6=300ms、60 节点三场景是可量化的论据。
  - 「微服务把系统内复杂度转移为系统间复杂度」这一本质表述。
  - 「lightweight 最终会长成 ESB」的规模效应。

### 35丨微服务架构最佳实践-方法篇

- **核心结论**
  针对上一讲的三个陷阱（拆分过细、缺 automated、lightweight 不成立），方法篇给出三条实践：**用「三个火枪手」原则按团队规模定服务粒度**；**按目的选择四种拆分方式并可自由组合**；**按优先级搭建微服务基础设施**。原文强调：真正决定微服务成败的是被忽略的 **automated**。

- **完整判据/清单/步骤**
  1. **服务粒度：「三个火枪手」原则**
     - 规则：**一个微服务三个人负责开发**（类比贝索斯的「两个披萨」理论）；按团队规模反推服务数量，业务发展、团队扩大后再拆已有的服务。
     - 规模换算样例：6 人 → 2 个微服务；扩到 12 人 → 拆成 4 个微服务。
     - 为什么是 3 个人（三条论证）：
       1. **系统规模**：3 人时系统复杂度刚好「每个人都能全面理解整个系统，又能进行分工」；2 人复杂度不够（无法体现技术实力）；4 人及以上则无法深入了解细节。
       2. **团队管理**：3 人可形成稳定备份（1 人休假或调走，剩 2 人可支撑）；2 人抽走 1 人后剩 1 人压力很大；1 人是单点，没有备份很危险。
       3. **技术提升**：3 人能形成有效讨论又能快速达成一致；2 人可能互相坚持己见或都经验不足导致设计缺陷；1 人没有讨论易陷入思维盲区；4 人及以上可能有人只「完成任务」不认真参与。
     - 阶段差异：设计开发阶段用「三个火枪手」；进入维护期、无须太多开发时，人均可维护 1 个甚至几个微服务；但考虑人员备份，**每个微服务最好安排 2 个人维护**，每个人可维护多个。
  2. **拆分方法（四种，可组合）**

     | 拆分方式 | 排序依据 | 做法判据 | 收益/注意 |
     |---|---|---|---|
     | **基于业务逻辑** | 职责范围 | 识别业务模块职责，每模块一个服务 | 最直观；但团队对「职责范围」理解差异大、易争论（电商拆 3 个还是 6 个服务）；不能只看业务逻辑定粒度，要用「三个火枪手」先算服务数量再划职责 |
     | **基于可扩展** | 稳定性 | 成熟少改的 → 稳定服务（粒度可粗，无强关联也可同子系统，如日志服务 + 升级服务）；经常变化的 → 变动服务（粒度可细但别太细，始终控制服务总数） | 提升迭代效率，避免误伤成熟功能引发线上问题 |
     | **基于可靠性** | 优先级 | 可靠性要求高的核心服务与要求低的非核心服务拆开，重点保核心 | 三好处：①避免非核心故障影响核心（如大量日志上报拖垮核心）；②核心服务高可用方案更简单（功能逻辑更简单、数据更少、组件更少）；③降低高可用成本（核心服务占用机器带宽更少，只对核心做高可用更省） |
     | **基于性能** | 性能压力 | 把性能要求高或压力大的模块拆出来 | 避免性能压力大的服务影响其他服务；常见按瓶颈拆 Web 服务、数据库、缓存；如电商抢购把排队功能独立为服务 |

     - 组合判据：四种不是多选一，可按实际情况自由排列组合。样例：基于可靠性拆出 A、基于性能拆出 B、基于可扩展拆出 C/D/F，加上原有 X，最终共 6 个服务（A/B/C/D/F/X）。
     - 粒度校准样例（先算数量再划职责）：团队 10 人支撑业务 → 按三个火枪手约需 4 个服务 → 「登录、注册、用户信息管理」可都划入「用户服务」；团队 100 人 → 服务可达 40 个 → 「用户登录」就是一个服务；团队 1000 人 → 「用户连接管理」可能是一个独立服务。
  3. **基础设施的定位与搭建优先级**
     - 定位判据：大部分人关注 small 与 lightweight，但**真正决定成败的是 automated**——服务粒度不合理，落地遇到麻烦自然会拆/合；而 automated 基础设施不健全，微服务就是焦油坑。
     - 认知纠偏：微服务基础设施图看起来比 ESB 还复杂 → 微服务并不轻量；**微服务没有减少复杂度，只是把复杂度从 ESB 转移到了基础设施**（「服务发现」「服务路由」本来就是 ESB 的功能，只是被剥离成独立基础系统）。
     - 两个不必悲观的理由：已有开源全家桶（Spring Cloud 涵盖服务发现、服务路由、网关、配置中心等）；微服务数量不多时并非每项基础设施都必需。
     - **四档搭建优先级**
       1. 服务发现、服务路由、服务容错：最基本的微服务基础设施；
       2. 接口框架、API 网关：提升开发效率（接口框架提升内部服务开发效率，API 网关提升与外部系统对接效率）；
       3. 自动化部署、自动化测试、配置中心：提升测试与运维效率；
       4. 服务监控、服务跟踪、服务安全：进一步提升运维效率。
     - 重要性的规模依赖：第 3、4 类的重要性随微服务节点数量增加而越来越重要；节点少时可人工支撑，效率不高但基本能顶住。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 3 个人 / 1 个微服务 | 「三个火枪手」原则的核心比例 |
  | 2 个披萨 | 贝索斯的团队规模类比 |
  | 6 人 → 2 服务；12 人 → 4 服务 | 按团队规模换算服务数量 |
  | 2 人维护 1 个微服务（维护期） | 人员备份的最低建议 |
  | 10 人 → 约 4 个服务；100 人 → 约 40 个服务；1000 人 → 「用户连接管理」独立 | 粒度校准的三档样例 |
  | 3 个服务 vs 6 个服务（电商） | 「业务逻辑拆分」职责争议的样例 |
  | 4 档基础设施优先级 | 搭建顺序 |
  | 6 个服务（A/B/C/D/F/X） | 四种拆分方式组合的样例结果 |

- **案例/数据**
  - 6 人团队 → 2 个微服务；扩到 12 人 → 4 个 → 展示「按团队规模定粒度、随规模再拆」。
  - 电商拆「商品/交易/用户」3 个 vs「商品/订单/支付/发货/买家/卖家」6 个 → 两种都「合理」，说明不能只按业务逻辑定粒度。
  - 日志上报：量大时若不拆分可能拖垮核心服务 → 基于可靠性拆分的收益。
  - 电商抢购：性能压力最大的是入口排队 → 排队独立为服务（基于性能拆分）。
  - 10 人团队：登录/注册/用户信息管理合并为「用户服务」；100 人：登录独立；1000 人：用户连接管理独立 → 同一业务在不同规模下的粒度不同。
  - Spring Cloud 作为开源全家桶 → 小团队也能起步。

- **反例与坑**
  - 认为「拆得越细越正确」→ 业务逻辑拆分粗细分都说得通，必须靠团队规模校准。
  - 先拆服务再想团队 → 5~6 人维护 30 个服务的局面（上一讲的坑）。
  - 用 2 人或 1 人负责一个微服务 → 无备份、无讨论、易成单点。
  - 稳定服务也拆得很细 → 违反「稳定服务粒度可粗」的判据。
  - 只做业务逻辑拆分 → 漏掉可靠性、性能、可扩展三个更有针对性的维度。
  - 四种拆分方式只选一种 → 原文明确可自由组合。
  - 一上来就自建全套基础设施 → 应先按优先级、结合开源方案；节点少时第 3、4 类可人工顶住。
  - 相信微服务「轻量」→ 复杂度只是从 ESB 转移到基础设施。

- **原文金句**
  - 「分享一个我认为微服务拆分粒度的"三个火枪手"原则，即一个微服务三个人负责开发。」
  - 「大部分人主要关注的是微服务的"small"和"lightweight"特性，但实际上真正决定微服务成败的，恰恰是那个被大部分人都忽略的"automated"。」
  - 「因此也可以说，微服务并没有减少复杂度，而只是将复杂度从 ESB 转移到了基础设施。」
  - 「以上几种拆分方式不是多选一，而是可以根据实际情况自由排列组合。」

- **可迁移到知识库的主题**
  - 「三个火枪手」原则的三条论证（系统规模/团队备份/技术讨论），以及维护期「2 人备份」的修正。
  - 四种拆分方式（业务逻辑/可扩展/可靠性/性能）的排序依据与收益，及「先算数量再划职责」的校准方法。
  - 基础设施的四档优先级与「automated 决定成败」的判断。
  - 「复杂度守恒」：微服务没减少复杂度，只是把它从 ESB 移到基础设施。

### 36丨微服务架构最佳实践-基础设施篇

- **核心结论**
  每项微服务基础设施都是一个平台/系统/解决方案，自研过程与做业务系统类似（需求分析→架构设计→开发→测试→部署上线）。本讲逐项说明 11 项基础设施的主要作用与关键设计点：自动化测试、自动化部署、配置中心、接口框架、API 网关、服务发现、服务路由、服务容错、服务监控、服务跟踪、服务安全。

- **完整判据/清单/步骤**
  1. **自动化测试**
     - 为什么需要：拆成多个独立服务后接口数量大增，且提倡快速交付、版本周期短、更新频繁；人工回归工作量大、效率低，达不到快速交付。
     - 覆盖范围判据：代码级单元测试、单个系统级集成测试、系统间接口测试；理想是每类都自动化，**如果因团队规模/人力无法全面覆盖，至少要做到接口测试自动化**。
  2. **自动化部署**
     - 为什么需要：微服务需部署的节点比大一统系统增加几倍甚至十几倍，部署频率也大幅提升（原文：业务系统 70% 的工作日都有部署操作）→ 部署次数是大一统系统的几十倍；人工处理人力投入大且易错。
     - 功能清单：版本管理、资源管理（机器管理、虚拟机管理）、部署操作、回退操作。
  3. **配置中心**
     - 为什么需要：节点数量非常多，人工登录每台机器改配置效率低、易错；部署或排障时需快速增删改查配置；**有的运行期配置需动态修改且所有节点即时生效**，人工做不到。
     - 功能清单：配置版本管理（同一微服务 10 个节点服务移动用户、20 个节点服务联通用户，配置项相同但配置值不同）、增删改查配置、节点管理、配置同步、配置推送。
  4. **接口框架**
     - 为什么需要：微服务提倡轻量通信（HTTP/REST 或 RPC）统一接口协议，但**光统一协议不够，还要统一数据格式**（如指定 HTTP/REST + JSON + JSON 规范）；否则有的用 XML、有的用 JSON、有的用键值对，即使都用 JSON 格式也不一样 → 每个微服务要适配几套甚至几十套协议，等于把 ESB 做的事转交给微服务自己做。
     - 形态判据：**接口框架不是一个可运行的系统**，一般以库或包的形式提供给所有微服务调用（如基础技术团队提供 Java 包、Python 包、C 库）。
  5. **API 网关**
     - 为什么需要：外部系统若点对点调用微服务，则「非常头大」——它不需要也无法理解微服务的职责分工与边界，只关注自己需要的能力；且安全与权限若由每个微服务自己实现，工作量大且重复。
     - 定位与功能：外部系统访问的唯一接口；包括**接入鉴权**（是否允许接入）、**权限控制**（可访问哪些功能）、**传输加密**、**请求路由**、**流量控制**。
  6. **服务发现**
     - 为什么需要：手工配置工作量大（配置文件几百上千行，几十个节点就是几万几十万行）；节点经常变化（扩容增节点、故障隔离减节点、灰度升级新老版本并行），希望变化能及时同步到所有依赖方，手工配置不可能实时生效。
     - 两种实现方式：

       | 方式 | 机制 | 优点 | 风险 |
       |---|---|---|---|
       | **自理式** | 每个微服务自己完成服务发现：向 SERVICE REGISTRY 取注册信息，然后直接访问目标实例 | 实现简单（功能以统一库/包提供，不必各自重复实现）；访问压力分散到各微服务节点，性能与可用性无明显压力 | 功能需以库的形式嵌入（原文视为简单之处） |
       | **代理式** | 微服务之间有一个负载均衡系统（LOAD BALANCER）完成服务发现 | 结构清晰，微服务本身实现简单很多 | ①**可用性风险**：LB 故障影响所有微服务间调用；②**性能风险**：所有调用流量都过 LB，随服务数量与流量增长成为瓶颈；需把 LB 做成集群，但集群又增加复杂性 |

     - 共同核心：**服务注册表**——记录所有服务节点的配置与状态；每个微服务启动后注册自己的信息，然后由微服务或 LB 到注册表查询可用服务。
  7. **服务路由**
     - 与发现的关系：发现解决「有哪些可用节点」，路由解决「这次请求挑哪个具体节点」。
     - 实现位置判据：一般不独立成系统，通常与服务发现一起实现——自理式则由微服务内部实现路由；代理式则由 LB 实现路由。
     - 核心是**路由算法**：随机路由、轮询路由、最小压力路由、最小连接数路由。
  8. **服务容错**
     - 为什么需要：单个微服务故障概率变小、影响范围减少，但节点数量大增 → **系统中某个微服务出故障的概率大大增加**；微服务故障有扩散特点（见 34 期），不及时处理会扩散到看起来很多节点都故障。
     - 三种常见能力：**请求重试、流控、服务隔离**；通常集成在服务发现与服务路由系统中。
  9. **服务监控**
     - 为什么需要：节点数量大增 → 需监控的机器、网络、进程、接口调用数等对象大增；故障时需快速据各类信息定位。人工不可行（举个简单例子：打开几十个节点的日志看一遍就要十几分钟）。
     - 两个作用：①实时搜集并分析信息，避免「故障后再分析」，减少处理时间；②在实时分析基础上预警，在问题萌芽阶段发现，降低影响范围与时间。
     - 设计判据：数据量大，**建议做成独立系统**，不要集成到服务发现、API 网关等系统中。
  10. **服务跟踪**
      - 与监控的分界（原文判据）：监控做节点级收集，但若要看**某一个请求**在微服务中的完整路径，监控难以实现（每个服务都把完整请求链实时发给监控，数据量大到无法处理）。
      - 宏观 vs 微观：A 通过 HTTP 请求 B 十次、B 返回 JSON——**服务监控**记录请求次数、响应时间平均值、响应时间最高值、错误码分布；**服务跟踪**记录其中某次请求的发起时间、响应时间、响应错误码、请求参数、返回的 JSON 对象。
      - 技术来源：绝大部分请求跟踪实现基于 Google 的 Dapper 论文《Dapper, a Large-Scale Distributed Systems Tracing Infrastructure》。
  11. **服务安全**
      - 为什么需要：数据分散在各微服务节点，任意微服务都能访问所有其他节点，但业务上部分敏感数据/操作只允许部分微服务访问。
      - 三部分：**接入安全、数据安全、传输安全**。
      - 实现方式：通常集成到配置中心——配置中心配置接入安全策略与数据安全策略，微服务节点从配置中心取配置，处理调用请求时按策略处理；策略通用，一般封装成通用库给各微服务调用。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 70% 的工作日都有部署操作 | 论证部署频率高 |
  | 部署次数是大一统系统的几十倍 | 自动化部署的必要性 |
  | 部署节点增加几倍甚至十几倍 | 同上 |
  | 10 个节点服务移动 / 20 个节点服务联通 | 配置版本管理的样例（同项不同值） |
  | 配置文件几百上千行；几十个节点 → 几万几十万行 | 手工配置不可行的量化 |
  | 十几分钟（人工看几十个节点日志） | 服务监控必要性的量化 |
  | 10 次请求 | 监控（聚合）与跟踪（单次明细）的对比样例 |
  | 11 项基础设施 | 本讲覆盖范围 |

- **案例/数据**
  - 业务系统 70% 工作日有部署、部署次数是大一统系统几十倍 → 必须自动化部署。
  - 同微服务 10 节点（移动）+20 节点（联通），配置项相同、配置值不同 → 配置中心需要版本管理。
  - JSON 规范样例 → 接口框架以「多语言解析包」形式提供。
  - 灰度升级（部分节点先升、新老并行）→ 服务发现要能实时同步节点变化。
  - LB 集群化后自身复杂性上升 → 代理式的代价。
  - A 调 B 十次 → 监控记聚合指标、跟踪记单次明细。
  - Dapper 论文 → 分布式跟踪的理论与实现源头。

- **反例与坑**
  - 只统一协议不统一数据格式 → 各服务适配几十套协议，等于自己实现 ESB。
  - 把接口框架做成「可运行系统」→ 它应是库/包。
  - 外部系统直连微服务 → 外部方无从理解边界，且安全权限在每个服务重复实现。
  - 用代理式服务发现却不做 LB 高可用 → 单点故障影响全部服务间调用。
  - 把服务路由当独立系统 → 一般与服务发现同处实现。
  - 把服务监控集成进 API 网关/服务发现 → 数据量大，应独立。
  - 用服务监控做单请求链路追踪 → 数据量不可承受，应交给服务跟踪。
  - 手工维护服务注册信息 → 几十万行配置无法实时生效。

- **原文金句**
  - 「接口框架不是一个可运行的系统，一般以库或者包的形式提供给所有微服务调用。」
  - 「每个微服务启动后都需要将自己的信息注册到服务注册表，然后由微服务或者 LOAD BALANCER 系统到服务注册表查询可用服务。」
  - 「服务监控和服务跟踪的区别可以简单概括为宏观和微观的区别。」
  - 「通常情况下，服务监控需要搜集并分析大量的数据，因此建议做成独立的系统，而不要集成到服务发现、API 网关等系统中。」

- **可迁移到知识库的主题**
  - 11 项基础设施的「问题 → 作用 → 关键设计点」清单，可做成微服务就绪度检查表。
  - 服务发现的两种形态（自理式/代理式）及代理式的双风险（可用性/性能）。
  - 服务监控 vs 服务跟踪的宏观/微观判据与 Dapper 来源。
  - 接口框架「是库不是系统」、配置中心的「版本管理」、API 网关的五项职责等易混淆点。

### 37丨微内核架构详解

- **核心结论**
  微内核架构（Microkernel Architecture），又称插件化架构（Plug-in Architecture），是**面向功能拆分**的可扩展架构，通常用于基于产品（product-based：多版本、需下载安装、与 web-based 相对）的应用。它包含**核心系统**（与具体业务无关的通用功能）与**插件模块**（具体业务逻辑）两类组件，本质是**把变化部分封装在插件里**，从而在不影响整体稳定的前提下快速灵活扩展。

- **完整判据/清单/步骤**
  1. **基本组成（两类组件）**
     - **核心系统（core system）**：负责与具体业务功能无关的通用功能，如模块加载、模块间通信。
     - **插件模块（plug-in modules）**：负责实现具体业务逻辑（如「学生信息管理」中的「手机号注册」）。
     - 稳定-变化判据：核心系统功能稳定、不会因业务扩展而不断修改；插件按业务需要不断扩展。
  2. **三个设计关键点（核心系统的关键技术）**

     | 关键点 | 要解决的问题 | 实现判据 |
     |---|---|---|
     | **插件管理** | 核心系统需知道当前有哪些插件可用、如何加载、何时加载 | 常见做法是**插件注册表**机制：注册表可以是配置文件、代码或数据库；含每个插件的名字、位置、加载时机（启动就加载 or 按需加载） |
     | **插件连接** | 插件如何连到核心系统 | 核心系统必须制定**连接规范**，插件按规范实现、核心系统按规范加载；常见机制：OSGi（Eclipse 使用）、消息模式、依赖注入（Spring 使用），甚至分布式协议（RPC、HTTP Web） |
     | **插件通信** | 插件之间如何通信 | 设计时插件完全解耦，但实际业务必然出现「一个流程需多个插件协作」；插件间无直接联系，**通信必须通过核心系统**，故核心系统需提供通信机制（类比计算机主板总线：CPU、内存、硬盘、网卡独立设计，靠总线通信） |

  3. **OSGi 架构（第一个具体实现）**
     - 组织与规范：OSGi = Open Services Gateway initiative，本身指 OSGi Alliance；1999 年 3 月由 Sun Microsystems、IBM、爱立信等成立，最初名 Connected Alliance，非盈利国际组织，旨在建立开放服务规范（OSGi specification）；现在谈 OSGi 一般指规范本身。
     - 历史转向：最初面向**嵌入式**（机顶盒、服务网关、手机、汽车）；因具备动态化、热插拔、高可复用性、高效性、扩展方便等优点，被用到 PC 应用开发；Eclipse 采用后成为首选插件化标准；现在更多把 OSGi 当作**微内核架构模式**。
     - 关键判据：**OSGi 是插件化标准，不是可运行框架**；Eclipse 采用的 OSGi 框架叫 **Equinox**，类似实现还有 Apache Felix、Spring DM；Eclipse 从 **3.0** 起抛弃自研插件框架改用 OSGi。
     - 三层逻辑架构：

       | 层 | 对应微内核关键点 | 内容 |
       |---|---|---|
       | **Module 层** | 插件管理 | 插件称为 **Bundle**，每个 Bundle 是一个 Java JAR，内含元数据文件 **MANIFEST.MF**（Bundle 名称、描述、开发商、classpath、需导入的包和输出的包等），核心系统加载这些信息备用 |
       | **Lifecycle 层** | 插件连接 | 提供执行时模块管理、模块对底层 OSGi 框架的访问；精确定义 Bundle 生命周期操作（**安装、更新、启动、停止、卸载**），Bundle 必须按规范实现（如实现 BundleActivator 的 start/stop） |
       | **Service 层** | 插件通信 | 提供**服务注册**功能：插件把自己能提供的服务注册到 OSGi 核心的服务注册中心，需要别的服务时在注册中心检索（注意：这里的服务注册**不是**插件管理里的插件注册，而是插件间通信机制） |

  4. **规则引擎（第二个具体实现）**
     - 定位：从结构上看属于微内核架构的一种具体实现——**执行引擎**可看作微内核，它解析配置好的业务流、执行其中的条件和规则，以此支持业务灵活多变。
     - 应用领域：计费、保险、促销等。电商促销规则样例：满 100 送 50；3 件立减 50；3 件 8 折；第 3 件免费；跨店满 200 减 100；新用户立减 50……（原文称完整列下来可能几十上百种，加排列组合达几百上千种方案）。
     - 为什么规则引擎能应对（三条优点）：**可扩展**（业务逻辑实现与业务系统分离，不改业务系统即可扩展新功能）；**易理解**（规则用自然语言描述，业务人员可理解操作，不像代码只有程序员能懂）；**高效率**（一般提供可视化定制、审批、查询、管理）。
     - 基本架构（三步流程）：①开发人员把业务功能分解提炼为多个规则，保存在**规则库**；②业务人员按需排列组合规则、配置成业务流程，保存在**业务库**；③规则引擎执行业务流程实现业务功能。
     - **与微内核三关键点的映射（原文逐条）**：
       1. **插件管理**：规则就是插件，引擎就是内核；规则可被引擎加载执行；规则一般保存在规则库（通常用数据库存储）。
       2. **插件连接**：类似程序员要用 Java/C++ 语言，规则引擎规定**规则开发语言**，业务人员基于规则语言编写规则文件，引擎加载执行 → 规则引擎的插件连接机制**就是规则语言**。
       3. **插件通信**：规则间通信方式是**数据流和事件流**；单个规则不依赖其他规则，故规则之间没有主动通信，规则只输出数据或事件，由引擎传递到下一个规则。
     - 代表产品：**JBoss Drools**（Java 编写，基于 **Rete 算法**）；优点：社区活跃且应用广泛、执行速度快、兼容 Java Rule Engine API（JSR-94）、提供基于 Web 的 BRMS——**Guvnor**（规则管理知识库，支持规则版本控制、在线修改与编译）。
     - 局限（反例）：Drools 号称简单易用，但**规则语言实际与编程语言比较类似**，普通业务人员学习与理解成本仍较高 → 通常需基于 Drools 再封装，把规则配置做成可视化操作（如电商反欺诈示例）。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 两类组件（核心系统 + 插件） | 微内核的组成判据 |
  | 三个关键点（管理/连接/通信） | 核心系统的设计清单 |
  | 5 个生命周期操作（安装/更新/启动/停止/卸载） | OSGi Lifecycle 层的规范内容 |
  | 1999 年 3 月 | OSGi Alliance 成立时间（Sun/IBM/爱立信，原名 Connected Alliance） |
  | Eclipse 3.0 | Eclipse 改用 OSGi 的版本（框架为 Equinox） |
  | 三层（Module / Lifecycle / Service） | OSGi 逻辑架构，与三关键点一一对应 |
  | 促销规则 6 例 → 几十上百种规则 → 几百上千种方案 | 论证规则引擎的必要性 |
  | JSR-94 | Drools 兼容的 Java Rule Engine API 规范 |
  | Rete 算法 | Drools 的规则匹配算法 |

- **案例/数据**
  - Eclipse（IDE）、UNIX（操作系统）、淘宝 App（客户端）→ 微内核的典型产品型应用；保险公司保险核算逻辑系统把不同险种逻辑封装成插件 → 企业业务系统也可用微内核。
  - Eclipse 3.0 改用 OSGi（Equinox）；另有 Felix、Spring DM → 区分「标准」与「框架实现」。
  - MANIFEST.MF 样例（Bundle-ManifestVersion: 2、Bundle-Name: UserRegister、Bundle-SymbolicName、Bundle-Version: 1.0、Bundle-Activator、Import-Package、Export-Package）→ Module 层的元数据形态。
  - `UserRegisterActivator implements BundleActivator` 的 start/stop；`context.registerService(...)` 与 `getServiceReference` → 说明 Lifecycle 与 Service 层的代码形态。
  - 促销规则（满 100 送 50 等）几十上百种、组合后几百上千种 → 纯代码实现跟不上业务变化。
  - Drools + Guvnor → 规则版本控制与在线修改编译；规则语言仍偏编程 → 需封装成可视化。

- **反例与坑**
  - 把「插件化」等同于「随便加模块」→ 缺少核心系统的三关键点（注册表、连接规范、通信机制）就不算微内核。
  - 让插件之间直接互相调用 → 破坏解耦；原文明确通信必须通过核心系统。
  - 把 OSGi 当成可运行框架 → 它是标准；具体实现是 Equinox / Felix / Spring DM。
  - 混淆 OSGi 的「服务注册」与「插件注册」→ 前者是插件间通信机制，后者是插件管理。
  - 把微内核用于不属于 product-based 的场景 → 原文限定它通常用于多版本、需下载安装的产品型应用。
  - 认为规则引擎能让业务人员零成本上手 → Drools 规则语言仍类似编程语言，需再做可视化封装。
  - 规则之间做主动通信 → 规则只需输出数据/事件，由引擎传递。

- **原文金句**
  - 「微内核架构（Microkernel Architecture），也被称为插件化架构（Plug-in Architecture），是一种面向功能进行拆分的可扩展性架构。」
  - 「微内核的架构本质就是将变化部分封装在插件里面，从而达到快速灵活扩展的目的，而又不影响整体系统的稳定。」
  - 「微内核的核心系统设计的关键技术有：插件管理、插件连接和插件通信。」
  - 「虽然设计的时候插件间是完全解耦的，但实际业务运行过程中，必然会出现某个业务流程需要多个插件协作，这就要求两个插件间进行通信。」

- **可迁移到知识库的主题**
  - 微内核「核心系统 / 插件」的稳定-变化划分判据，以及产品型（product-based）适用边界。
  - 三关键点（插件管理-注册表 / 插件连接-规范 / 插件通信-经核心）的完整实现清单。
  - OSGi 三层（Module/Lifecycle/Service）与三关键点的一一映射，及「标准 vs 框架（Equinox/Felix/Spring DM）」的区分。
  - 规则引擎作为微内核实例的三点映射（规则=插件、规则语言=连接、数据流/事件流=通信）与 Drools 的能力/局限。

## 附：16 篇中最可能「缺」或「讲法不同」的 8 个点

> 判断依据：一是原文独有的结构性清单（分类法/三档/四步），二是与常见教材口径存在措辞差异的地方。括号内为可对照的知识库位置（若有）。

1. **双机切换的三种状态传递形态：互连式 / 中介式 / 模拟式**（含各自失效模式：互连式状态通道故障会出「双主」、中介式中介宕机会退化成「双备」并陷入递归陷阱、模拟式状态信息太少会决策偏差）——原文用「状态传递渠道」这一个维度就把切换方案分成三类，而常见讲法只讲「主备/主从 + VIP + 心跳」，缺这一层分类与「双主/双备」两种具体故障后果的对应。

2. **「CAP 做不到时只能选 CA（单点写入）」这一措辞**——23 篇针对余额、库存明确写「理论上要求选择 CP 而实际上 CP 都做不到，只能选择 CA。也就是说，只能单点写入，其他节点做备份」；而主流讲法（含本知识库 CAP 章节）会判定「自称 CA 只有单机/没做故障检测/撒谎三种可能」。同一现象（单点写 + 备份），原文叫 CA，通行口径叫「单写者 CP」，这是一处真实的讲法冲突。

3. **CAP 忽略网络延迟 → 完美 CP 不存在，CP 方案实际也是「最终一致性，只是『一定时间』是几毫秒」**——这条把 CP 与 BASE 打通了，常见讲法习惯把 CP 与最终一致性对立起来，很少承认「CP 也是最终一致性的一个特例」。

4. **数据分区的三种复制规则：集中式 / 互备式 / 独立式**（集中式要建总备份中心、互备式扩展时「北京已有的广州历史数据」无处安放、独立式成本最高）+「备份必须跨城」的细节（北京→天津、上海→杭州、广州→汕头）——这是地理级高可用里唯一成体系的复制拓扑分类，常见多活/灾备讲法一般只讲「两地三中心」，缺这三种备份中心拓扑及其扩展性代价。

5. **FMEA 的「故障模式只写现象、原因单列」以及原因必须单列的三个理由（概率/检测手段/处理措施都随原因不同）**——常见讲法容易把「故障模式」和「故障原因」合成一列；原文的判据是「不管什么故障原因，故障现象相同，对功能点的影响就相同」，因此影响分析用现象、对策分析用原因，两列不能合并。另：原文表是 11 项（多出「后续规划」一列，且它是全部汇总的产出）。

6. **异地多活四技巧里的两个「隐蔽前提」：跨中心「最后修改生效」必须先有全局时钟（误差 >1 秒就会顺序颠倒），以及「5 种数据同步手段」与数据特征的绑定（消息队列只适合无时序数据，密码不能走 MQ）**——常见讲法会推荐 LWW 合并与 MQ 同步，但很少点明 LWW 依赖全局时钟、MQ 依赖无时序，这两个前提一旦不成立方案直接失效。

7. **微服务粒度用「三个火枪手 = 1 个服务 3 个人」反推服务数量（以及 3 而不是 2/4 的三条论证：系统规模、团队备份、技术讨论）**——主流讲法按「业务能力/限界上下文」定粒度，容易陷入「职责范围」争论；原文给的是**先按团队规模算数量、再划职责**的反向算法（10 人≈4 个服务、100 人≈40 个），并且明确「业务逻辑拆分粗细分都说得通，不能只看业务逻辑定粒度」。

8. **「微服务没有减少复杂度，只是把复杂度从 ESB 转移到了基础设施」，且 lightweight 规模大了会长成另一个 ESB**——常见讲法把微服务描述为「比 SOA 更轻、去掉了 ESB」，原文用「服务发现/路由/容错/网关/配置中心/监控/跟踪/安全」这一整套基础设施证明：ESB 的功能没消失，只是被拆成了独立基础系统；因此对「微服务=轻量级」这句话要打问号（这也是 34 篇「焦油坑」与 35 篇「automated 决定成败」的连接点）。
