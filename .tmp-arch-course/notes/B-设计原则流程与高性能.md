## 08 | 架构设计三原则

### 08 | 架构设计三原则
- **核心结论**
  - 优秀程序员与架构师之间的鸿沟是「不确定性」：编程本质上是确定的（同样代码谁写、何时执行结果都确定，「确定」不等于「正确」，有 bug 也是确定的）；架构设计本质上是不确定的，没有语法约束，更多是「面对多种可能性时进行选择」。
  - 架构设计领域没有通用规范，主要依赖经验与直觉，但在研究架构发展历史、QQ/淘宝/Facebook 等多家公司架构后，可提炼出三个共性原则：**合适原则（合适优于业界领先）、简单原则（简单优于复杂）、演化原则（演化优于一步到位）**。
  - 三原则是用来「做选择」的判据：技术选先进还是选熟悉、选 Angular 还是 React、选 MySQL 还是 MongoDB、要不要照搬淘宝，都回到这三条。
- **完整判据/清单/步骤**
  - **原则一：合适原则 —— 宣言「合适优于业界领先」**
    - 反例：2011 年，一个几个人规模的业务团队提出做对标腾讯 QQ 的「亿级用户平台」，最终失败。这里的失败不是系统做不出来，而是系统没有按照最初的目标实现。
    - 判断「合适」的三条依据（即「脚踏实地」的三个层面）：
      1. **将军难打无兵之仗**（人力约束）：大公司分工细，某通信大厂做一个 OM 管理系统就有十几个人，阿里中间件团队几十个人；大部分公司整个研发团队 100 多人，某个业务团队十几个人。十几个人的团队想做几十个人团队的事还要做得更好，难度可想而知。→ 没那么多人却想干那么多活，是失败的第一个主要原因。
      2. **罗马不是一天建成的**（积累约束）：业界领先方案不是天才灵机一动加班加点做出来的，而是几年逐步完善。阿里中间件团队 2008 年成立，到写作时已十年；外界只看到抗住多少次「双 11」，踩过的坑只有自己知道，而这些挑战和踩坑正是架构设计的关键促进因素。→ 没有那么多积累却想一步登天，是失败的第二个主要原因。
      3. **冰山下面才是关键**（业务约束）：业界领先方案多是「逼」出来的——业务发展到一定阶段，量变导致质变，出现新问题，已有方式无法应对，才通过创新尝试产生新方案。GFS 诞生在 Google 而非 Microsoft，主要因素是 Google 有庞大数据，而不是 Google 工程师更聪明。→ 没有卓越的业务场景却幻想灵光一闪成为天才，是失败的第三个主要原因。
    - 正面判据：真正优秀的架构都是在企业当前人力、条件、业务等各种约束下设计出来的，能合理整合资源、发挥最大功效、并能快速落地；这也是很多 BAT 出来的架构师到小公司或创业团队反而做不出成绩的原因——没有平台、资源、积累，只生搬硬套大公司做法，失败概率非常高。
  - **原则二：简单原则 —— 宣言「简单优于复杂」**
    - 为什么会走向复杂：技术活的历史（瑞士钟表、瓦特蒸汽机、莱特兄弟飞机、摩托罗拉手机）都是越来越精细复杂；建筑审美的迁移（长城、泰姬陵、悉尼歌剧院、迪拜帆船酒店）；团队评价压力（主备用「心跳」实现被认为太简单，引入 ZooKeeper 做决策因为用了 ZAB 协议就显得「高大上」，而真正理解 ZAB 的人很少）。
    - 判据：**「复杂」在制造领域代表先进，在建筑领域代表领先，但在软件领域恰恰相反，代表的是「问题」。**
    - 软件复杂性体现在两方面：
      1. **结构的复杂性**——复杂系统几乎毫无例外有两个特点：组成系统的组件数量更多；组件之间的关系也更复杂。
         - 问题一：组件越多，越可能某个组件故障导致系统故障（可用性可算，见数字节）。
         - 问题二：某个组件改动会影响关联的所有组件，且递归影响更多组件（5 组件系统中 A 改动影响 B/C/E，D 又影响 E）；一旦变更涉及外部系统，需要协调各方统一方案评估、资源协调、上线配合，影响开发效率。
         - 问题三：定位问题更难——组件多则逐一排查，关系复杂则「表现故障的组件并不是真正问题的根源」。
      2. **逻辑的复杂性**——不能靠「把组件数量降到 1」来解决。逻辑复杂的典型特征：
         - 单个组件承担太多功能（电商的商品管理、商品搜索、商品展示、订单管理、用户管理、支付、发货、客服全放一个组件），导致软件工程每个环节都出问题：代码上百万/上千万行、clone 一次 30 分钟；几十上百人维护，菜鸟改一行导致整站崩溃；需求雪片般飞来，开几十个分支再各种合并覆盖；产品/研发/测试/项目管理不停开会协调；每天上线几十个版本、系统每隔 1 小时重启一次；线上故障几十人扑上去定位。
         - 采用复杂算法，难以理解→难以实现→难以修改→出问题难以快速解决。例：ZooKeeper 功能主要是选举，为分布式选举采用 ZAB 协议，功能相对简单但实现复杂；etcd 采用 Raft，更容易理解、更容易实现。
    - 根因判据：电路一旦设计好进入生产就不再变化，复杂性只影响设计阶段；而软件系统投入使用后还有源源不断的需求，要不断修改，复杂性在整个生命周期都有很大影响。
    - 结论判据：简单方案和复杂方案都能满足需求时，最好选简单方案；《UNIX 编程艺术》的 KISS（Keep It Simple, Stupid!）原则同样适用于架构设计。
  - **原则三：演化原则 —— 宣言「演化优于一步到位」**
    - 建筑与软件的本质差异：建筑一旦完成（甚至一旦开建）就不可再变，软件却要随业务不断发展变化。吉萨大金字塔 4000 多年前完成至今仍是当初的架构；明长城 600 多年前完成，保存下来的还是当年结构；白宫 1800 年建成，200 年来几次扩展但整体结构无变化，只是旁边空地扩建或内部布局改造。而 Windows 8 与 Windows 1.0 已是两个不同的系统，Android 6.0 与 Android 1.6 差异也很大——设计者都是顶尖天才，也不可能在 1985 年设计出 Windows 8、在 2009 年设计出 Android 6.0。
    - 反例（一步到位的两种做法及后果）：要么照搬业界大公司公开发表的方案；要么投入庞大资源做各种预测、分析、设计。后果都是投入巨大、落地遥遥无期；更沮丧的是就算终于落地，也发现很多预测和分析是不靠谱的。
    - 生物演化的三步类比 → 软件架构设计的三步：
      1. 生物要适应当时的环境 → 设计出来的架构要满足当时的业务需要。
      2. 生物不断繁殖，传递有利基因、剔除或修复不利基因 → 架构要在实际应用过程中不断迭代，保留优秀设计、修复有缺陷设计、改正错误设计、去掉无用设计，逐渐完善。
      3. 环境变化时生物快速改变适应，无法调整就被淘汰，新生物保留一部分被淘汰生物的基因 → 业务变化时架构要扩展、重构甚至重写；代码也许重写，但有价值的经验、教训、逻辑、设计（类似基因）可以在新架构中延续。
    - 行动判据：不要贪大求全、不要盲目照搬大公司；认真分析当前业务特点，明确业务面临的主要问题，设计合理架构、快速落地满足业务，然后在运行中不断完善、随业务演化。即使大公司团队做新系统也要遵循演化原则，不能因为人多资源多就上来一步到位——业务发展和变化很快，再牛的团队也不可能完美预测所有业务发展变化路径。
- **数字与阈值**
  - 组件故障率 10%（假设 10% 时间不可用）：用于量化「结构复杂→可用性下降」；3 组件可用性 = (1-10%)³ = **72.9%**，5 组件 = (1-10%)⁵ = **59%**，两者相差 **13%**——用途：证明组件数量本身就是可用性成本。
  - **30 分钟**：假设淘宝所有功能塞进单一组件时，代码规模上百万/上千万行，`clone` 一次代码的耗时——用途：说明逻辑复杂对研发效率的破坏。
  - **1 小时**：同一假设场景下系统重启间隔（每天上线几十个版本）——用途：说明逻辑复杂的运维代价。
  - **2008 年**：阿里中间件团队成立年份，到写作时已发展十年——用途：说明业界领先方案需要长期积累，无法速成。
  - **4000 多年 / 600 多年 / 1800 年 + 200 年**：金字塔、明长城、白宫的存续与改造时间——用途：反衬「建筑求永恒、软件求变化」。
  - **1985 / 2009**：Windows 1.0 与 Android 1.6 的年代，对应 Windows 8 / Android 6.0 的差距——用途：证明顶尖团队也无法提前预判十几年的架构。
  - **十几个人 / 100 多人 / 几十个人**：业务团队、公司研发团队、大厂中间件团队的规模对比——用途：合适原则的人力判据。
- **案例/数据**
  - 「亿级用户平台」（2011，几个人团队对标 QQ）→ 结论：没有腾讯的人、没有 QQ 的用户积累、没有 QQ 的业务，失败在一开始就注定；三个失败原因全占。→ 合适原则。
  - 「心跳 vs ZooKeeper 做主备」→ 结论：复杂性常被当作方案水平的评价指标，会把架构师推向无谓的复杂；ZooKeeper 的 ZAB 协议理解者极少，但不妨碍大家认为它优秀。→ 简单原则。
  - ZooKeeper（ZAB）与 etcd（Raft）→ 结论：同样的功能目标，算法越易理解，实现与维护越简单，应优先简单。
  - BAT 架构师到小公司/创业团队做不出成绩 → 结论：脱离平台、资源、积累的生搬硬套，失败概率非常高。
- **反例与坑**
  - 以「达到和 Google 相同的技术水平」「性能大大优于阿里集团的 YY 方案」作为方案目标与 KPI 卖点。
  - 认为「复杂 = 高级」：主备不用心跳而用 ZooKeeper，只因 ZAB 显得高深。
  - 把建筑审美移植到软件：追求宏伟、精美、艺术、豪华，不能寒酸、不能简单。
  - 试图一步到位设计「不管业务如何变化都稳如磐石」的架构，或直接照搬淘宝架构。
  - 用「把组件数降到 1」来对抗结构复杂性，结果掉进逻辑复杂性。
- **原文金句**
  - 「合适原则宣言：“合适优于业界领先”。」
  - 「“复杂”在制造领域代表先进，在建筑领域代表领先，但在软件领域，却恰恰相反，代表的是“问题”。」
  - 「对于建筑来说，永恒是主题；而对于软件来说，变化才是主题。」
  - 「如果没有把握“软件架构需要根据业务发展不断变化”这个本质，在做架构设计的时候就很容易陷入一个误区：试图一步到位设计一个软件架构，期望不管业务如何变化，架构都稳如磐石。」
- **可迁移到知识库的主题**
  - `合适原则`、`简单原则/KISS`、`演化原则`、`结构复杂度 vs 逻辑复杂度`、`架构不确定性`

## 09 | 架构设计原则案例

### 09 | 架构设计原则案例
- **核心结论**
  - 即使是 BAT 这样中国互联网技术最顶尖水平的公司，其架构发展历程也同样遵循合适、简单、演化三原则。
  - 业务决定技术：每个阶段的架构选择都由当时的业务驱动力决定（要「快」→ 买；要「性能」→ 买更贵的；「买」也搞不定了 → 重构/自研）。
  - 淘宝与手机 QQ 的共同规律：先简单方式满足当时业务（简单原则 + 合适原则），随业务发展逐步演化（演化原则）；罗马不是一天建成，架构也不是一开始就完美、然后一劳永逸。
- **完整判据/清单/步骤**
  - **淘宝六阶段（每阶段：驱动力 → 动作 → 遵循原则）**
    1. **个人网站**：2003-04-07 马云提出成立淘宝，2003-05-10 上线，中间只有 1 个月 → 答案是「买一个」。决策依据是「快」：初创时没有过多考虑技术是否优越、性能是否海量、稳定性如何，主要考虑因素是快——等花几个月甚至十几个月搞出强大系统，市场机会可能就没了。买什么样的？「轻量一点的，简单一点的」：买系统是为了「快速可用」，买轻量级系统是为了「快速开发」，因为上线后必有大量需求。→ 合适原则 + 简单原则。
    2. **Oracle / 支付宝 / 旺旺**：2003 年底 MySQL 撑不住（非典 + 市场运作，流量交易量迅速上涨）→ 技术替代方案非常简单，就是换成 Oracle，原因除容量大、稳定、安全、性能高，还有人才原因（买「性能」）。后来又买 NAS（NetApp）作为数据库存储设备，加 Oracle RAC 实现负载均衡。此时离上线不到半年，最快支撑业务的方式仍是买。→ 合适原则 + 简单原则。
    3. **Java 时代 1.0（脱胎换骨）**：起因是 PHP 连接池 SQL Relay（开源，因 BEA 的连接池工具太贵买不起）经常死锁、死锁必须重启，而数据库必须用 Oracle，于是决定换开发语言；请 Sun 公司的人先把淘宝从 PHP 热切换到 Java。选择 Java 的理由：当时最成熟的网站开发语言、有良好企业开发框架、被世界主流大规模网站普遍采用、有 Java 经验的人才多、后续维护成本低。这次没有「买」而是「重构」→ 演化原则。
    4. **Java 时代 2.0（坚若磐石）**：做数据分库、放弃 EJB、引入 Spring、加入缓存、加入 CDN、采用开源 JBoss——「看起来没有章法可循，其实都是围绕着提高容量、提高性能、节约成本来做的」。为什么此时不「买」：买也搞不定了；原有方案存在固有缺陷（Oracle 再强大，做 like 类搜索也不可能达到纯搜索系统 Solr、Sphinx 的性能，这是机制决定的）；且规模增大后成本成为关键（买 1~2 台 Oracle 不心疼，买 100 台就是关键因素）。→ 量变带来质变 → 演化原则。
    5. **Java 时代 3.0**：从商用转为「自研」，典型是去 IOE 化。
    6. **分布式时代**：自研技术自成一派，除支撑自身海量业务，也开始影响整个互联网技术发展。驱动力：业务规模急剧上升后，原本不是主要复杂度的 IOE 成本成为主要问题，于是用自研系统降成本——去 IOE 是架构的再一次演化。
  - **手机 QQ 四阶段（按用户规模划分：十万级、百万级、千万级、亿级；规律是用户规模先上去，然后产生各种问题，倒逼架构升级）**
    1. **十万级 IM 1.X**：架构简单得不能再简单、普通得不能再普通 → 合适原则 + 简单原则。
    2. **百万级 IM 2.X**（2001 年同时在线突破一百万）：第一代架构明显撑不住，主要问题——接入服务器内存（单个在线用户约 2KB，2GB 内存只能支持一百万在线）；CPU / 网卡包量和流量 / 交换机流量等瓶颈；单台服务器支撑不下所有在线用户/注册用户。按演化原则重构，方案相比现在仍简单得多 → 合适 + 简单。
    3. **千万级 IM 3.X**（2005 年同时在线突破一千万）：第二代撑百万没问题，撑千万产生新问题——同步流量太大、状态同步服务器遇单机瓶颈；所有在线用户在线状态信息量太大，单台接入服务器存不下，在线数继续增加时甚至单台状态同步服务器也存不下；单台状态同步服务器支撑不下所有在线用户；单台接入服务器支撑不下所有在线用户的在线状态信息。再次演化，此版方案「相比之前的方案来说并不简单了，这是业务特性决定的」。
    4. **亿级 IM 4.X**（2010 年 3 月同时在线过亿）：第三代不适应，主要问题——灵活性很差（「昵称」长度增加一半需要两个月；增加「故乡」字段需要两个月；最大好友数从 500 变成 1000 需要三个月）；无法支撑某些关键功能（好友数上万、隐私权限控制、PC QQ 与手机 QQ 不可互踢、微信与 QQ 互通、异地容灾）。更严重的是：IM 后台 1.0 到 3.5 都是在原基础上改造升级，持续打补丁已难以支撑亿级在线，**IM 后台 4.0 必须从头开始、重新设计实现**。重设计后架构本身拆分为两个主要架构：**存储架构**与**通信架构**。
- **数字与阈值**
  - **1 个月**（2003-04-07 提出 → 2003-05-10 上线）：用途——时间压力是「买」而非「做」的唯一决定性依据。
  - **2003 年底 / 不到半年**：MySQL 撑不住、随后买 Oracle + 高端存储的时间点——用途——证明「买性能」也是被业务速度逼出来的短期解。
  - **1663 万商品数、8931 万 PV、1390 万注册会员（2005 年）**：用途——量变到质变的量化标志，此后必须从架构上调整而非继续「买」。
  - **100 台 Oracle**：假设的采购规模，用途——说明成本何时从可忽略变成关键约束。
  - **100 万 / 1000 万 / 1 亿**：QQ 同时在线人数的三个台阶（2001、2005、2010-03），用途——用户规模是 IM 架构分期的唯一主轴。
  - **2KB / 50 字节 / 400×5 字节=2000 字节 / 2GB**：单个在线用户存储量、索引与在线状态、好友表大小、单机内存上限——用途——推导出「2GB 只能支撑一百万在线」这一硬容量判据。
  - **2 个月 / 2 个月 / 3 个月**：昵称长度加一半、增加「故乡」字段、好友数 500→1000 的开发周期——用途——量化第三代架构「灵活性很差」，成为 4.0 重写的直接理由。
- **案例/数据**
  - 淘宝「买一个网站」→ 结论：业务要「快」时，技术也要「快」，架构选型服从业务节奏（合适 + 简单）。
  - 淘宝买 Oracle / NAS / RAC → 结论：**买方案**（第一阶段）与**买性能**（第二阶段）都是合适原则下的时间换空间。
  - SQL Relay 死锁导致换语言 → 结论：技术已经影响业务（频繁死锁重启影响用户），这是不得不解决的技术问题，属于演化而非「买」。
  - 2005 年数据量（1663 万商品、8931 万 PV、1390 万会员）→ 结论：靠「买」解决不了，必须整体架构调整；量变引起质变。
  - 去 IOE → 结论：复杂度主项会随规模迁移（成本从次要变主要），架构随之再演化。
  - QQ 4.0 从头重写 → 结论：演化不等于永远打补丁；补丁成本超过重写成本时，重写也是演化的一种形式（且有价值的经验/逻辑可延续）。
- **反例与坑**
  - 流量一涨就条件反射地「优化系统、优化架构、分拆业务」——淘宝在 2003 年底的选择是先换更强的商用软硬件（买），因为那是最快的方法。
  - 认为大厂架构可以照搬：淘宝是「买 → 买更强 → 重构 → 优化 → 自研 → 分布式」一路被业务逼出来的，不是一次设计出来的。
  - 长期靠打补丁演进：IM 1.0→3.5 持续打补丁，最终无法支撑亿级在线，只能 4.0 重写。
  - 在业务初期就按最终规模设计（反推自 15 讲的「做 10 个业务有 1 个能活」）。
- **原文金句**
  - 「从这个实例我们可以看到：淘宝最开始的时候业务要求就是“快”，因此反过来要求技术同样要“快”，业务决定技术，这里架构设计和选择主要遵循的是“合适原则”和“简单原则”。」
  - 「这些杂七杂八的修改，我们对数据分库、放弃 EJB、引入 Spring、加入缓存、加入 CDN、采用开源的 JBoss，看起来没有章法可循，其实都是围绕着提高容量、提高性能、节约成本来做的。」
  - 「这就是“量变带来质变”的一个典型案例，业务和系统发生质变后，架构设计遵循“演化原则”的思想，需要再一次重构甚至重写。」
  - 「罗马不是一天建成的，架构也不是一开始就设计成完美的样子，然后可以一劳永逸一直用下去。」
- **可迁移到知识库的主题**
  - `业务决定技术`、`架构演化史`、`量变引起质变`、`去IOE`、`IM架构分层（存储/通信）`

## 10 | 架构设计流程：识别复杂度

### 10 | 架构设计流程：识别复杂度
- **核心结论**
  - 架构设计的本质目的是解决软件系统的复杂性，所以设计架构的第一步是分析系统的复杂性。
  - 判断错复杂度则方向全错：即使后续方案再完美再先进，都是南辕北辙，做得越好、错得越多、越离谱（例：系统本来是业务逻辑复杂、功能耦合，却设计了 TPS 50000/秒 的高性能架构，性能再优秀也毫无意义）。
  - 复杂度主要来自「高性能」「高可用」「可扩展」，但不能生搬硬套：**大部分场景复杂度只是其中一个，少数情况包含两个**；真出现同时要解决三个或以上，要么说明系统之前设计有问题，要么是架构师判断失误；即使真认为要同时满足，也必须做优先级排序。
- **完整判据/清单/步骤**
  - **架构设计流程四步（本讲是第 1 步）**：① 识别复杂度 → ② 设计备选方案 → ③ 评估和选择备选方案 → ④ 详细方案设计。
  - **第 1 步：识别复杂度 —— 动作与输出**
    - 输入：业务需求、现有系统现状（如系统间协作效率低的抱怨）、团队与资源背景（团队规模、语言栈、开发平台/数据库、机房部署情况）。
    - 动作一：判断复杂度落在哪几项（高性能 / 高可用 / 可扩展 / 安全 / 成本…），并明确「不是每个架构都必须同时满足三方面」。
    - 动作二：若存在多个复杂度，**列出主要复杂度问题，再按业务、技术、团队等综合情况排序，优先解决当前最主要的那一个**。
    - 动作三（经验不足时）：采用「排查法」，从不同角度逐一分析。
    - 输出：一份有优先级、可量化的复杂度清单（本讲案例输出为「高性能消息读取、高可用消息写入、高可用消息存储、高可用消息读取」四项）。
  - **为什么要「一个个来」而不是一次解决全部**（判据清单）：
    - 要做的事情太多，反而感觉无从下手。
    - 设计方案本身太复杂，落地时间遥遥无期。
    - 同一个方案要解决不同的复杂性，有的设计点互相矛盾（例：提升可用性需要把数据及时刷盘，刷盘反过来影响性能）。
  - **对「按优先级解决会导致推倒重来」这一普遍担忧的判据**：理论上可能，现实中几乎不可能，原因在于软件系统的可塑性和易变性——同一个复杂度问题可以有多个方案，总能挑出综合性价比最高的；即使真要推倒重来，新方案也必须同时解决已被解决的问题，而能达到这种理想状态的方案基本都靠引入新技术（例：Hadoop 能同时解决高可用、高性能、大容量三个大数据处理复杂度问题）。
  - **排查法操作模板（逐个复杂度自问自答，并给出量化推导）**：
    1. 这个消息队列是否需要高性能？→ 用日总量换算 TPS/QPS，再乘峰值系数与预留系数。
    2. 这个消息队列是否需要高可用性？→ 按「丢消息的业务后果」分级判断（写入/存储/读取分别判断）。
    3. 这个消息队列是否需要高可扩展性？→ 按功能是否会持续变化判断。
    4. （可扩展）其他复杂度：金融系统考虑安全性，有的公司考虑成本等。
  - **排查法实战推导链（前浪微博消息队列）**：
    - 背景：用户每天发 1000 万条微博 → 微博子系统一天产生 1000 万条消息 → 假设平均一条消息被 10 个子系统读取 → 其他子系统读取约 1 亿次。
    - 「一天的数据不算数，要看 1 秒的数据」：平均每秒写入 115 条、每秒读取 1150 条。
    - 按峰值设计：峰值取平均值的 3 倍 → TPS 345、QPS 3450 → 这个量级**不要求高性能**。
    - 但业务会增长，需预留余量：因基数较低，设计目标设为峰值的 4 倍 → **TPS 1380、QPS 13800**。
    - 判定：TPS 1380 并不高，但 QPS 13800 已经比较高了 → **高性能读取是复杂度之一**。
    - 高可用判定：微博子系统丢消息→没审核→触犯国家法律法规，非常严重；等级子系统丢消息→VIP 没拿到奖品和专属服务→用户不满意、流失损失收入，虽关键但没审核严重 → 综合判定需要高可用，且**写入、存储、读取都要**。
    - 可扩展判定：消息队列功能很明确、基本无须扩展 → 可扩展性不是关键。
    - 输出：高性能消息读取 + 高可用消息写入 + 高可用消息存储 + 高可用消息读取。
  - **背景约束（影响后续方案设计的输入）**：中间件团队约 6 人；团队熟悉 Java，有一个新同事 C/C++ 很牛；开发平台 Linux、数据库 MySQL；整个业务系统单机房部署，没有双机房。
- **数字与阈值**
  - **TPS 50000/秒 vs 实际不到 500**：过度设计系统的标称值与真实值——用途：识别复杂度错误的代价量化。
  - **40 多个子系统 / 近 1 年 / 2 年 / 不到 20 个**：亿级用户平台初始子系统数、开发时长、接手团队重构时长、合并后子系统数——用途：说明复杂度判断错误的长期成本。
  - **1000 万条/天**：微博日发帖量（假设）——用途：推导链条起点。
  - **10 个子系统**：平均每条消息的读取方数量（假设）——用途：把写入量放大为 1 亿次读取。
  - **115 条/秒、1150 条/秒**：日量摊到秒的平均读写——用途：证明「日量吓人、秒量不大」。
  - **3 倍**：峰值相对平均值的倍数（原文「峰值一般取平均值的 3 倍」）——用途：从均值推到峰值 TPS 345 / QPS 3450。
  - **4 倍**：设计目标相对峰值的余量倍数（因基数低）——用途：得到 TPS 1380 / QPS 13800 的最终设计目标。
  - **2 倍 / 8 倍 / 10 倍 / 100 倍**：余量倍数的可调范围与红线——原文明确「不同的业务可以是 2 倍，也可以是 8 倍，但一般不要设定在 10 倍以上，更不要一上来就按照 100 倍预估」——用途：防止余量变成过度设计。
  - **6 人**：中间件团队规模——用途：后续方案评估中「自研存储不可行」的硬约束。
  - **一天内平均每秒写入 115 / 读取 1150**：由 1000 万 / 86400 与 1 亿 / 86400 得来——用途：示范「按秒算」的换算方法。
- **案例/数据**
  - 「亿级用户平台」（对标 QQ，40 多个子系统，开发近 1 年上线）→ 结论：高性能、高可用、可扩展、安全一应俱全的过度设计是多此一举，并带来运维效率低（每次版本升级十几个子系统同步升级、易错、回滚可能二次问题）、开发效率低、问题定位难、实际 TPS 连 500 都不到；业务没发展起来、原设计人员离开，接手团队又花 2 年重构合并子系统才稳定。
  - 接手团队的处理顺序 → 结论：先降子系统数量（开发效率提升、小问题基本消失），再做异地多活，效果非常好；即「一个个来」优于「一次全解」。
  - 前浪微博消息队列 → 结论：1000 万/天 + 10 倍读取看似吓人，换算成 TPS/QPS 后只有读取一项真正构成高性能复杂度。
- **反例与坑**
  - 用模板套复杂度：任何系统都要求同时满足高性能、高可用、可扩展。
  - 只看一天的总量、不看每秒的量（架构师关注 TPS/QPS）。
  - 性能余量按 10 倍、100 倍预估 → 过度设计。
  - 一次架构重构解决所有复杂度问题（会无从下手、方案过大、设计点互相矛盾）。
  - 把「复杂度多」当成架构水平高的证明。
- **原文金句**
  - 「如果对系统的复杂性判断错误，即使后续的架构设计方案再完美再先进，都是南辕北辙，做的越好，错的越多、越离谱。」
  - 「1000 万和 1 亿看起来很吓人，但对于架构师来说，关注的不是一天的数据，而是 1 秒的数据，即 TPS 和 QPS。」
  - 「正确的做法是将主要的复杂度问题列出来，然后根据业务、技术、团队等综合情况进行排序，优先解决当前面临的最主要的复杂度问题。」
  - 「注意，这里的设计目标设定为峰值的 4 倍是根据业务发展速度来预估的，不是固定为 4 倍，不同的业务可以是 2 倍，也可以是 8 倍，但一般不要设定在 10 倍以上，更不要一上来就按照 100 倍预估。」
- **可迁移到知识库的主题**
  - `识别复杂度`、`排查法`、`TPS/QPS 换算`、`峰值系数与预留系数`、`复杂度优先级排序`

## 11 | 架构设计流程：设计备选方案

### 11 | 架构设计流程：设计备选方案
- **核心结论**
  - 架构师的工作并不神秘：成熟的架构师对已有技术非常熟悉、对已验证的架构模式烂熟于心，然后根据对业务的理解，**挑选合适的架构模式进行组合，再对组合后的方案进行修改和调整**。
  - 软件技术几十年发展，新技术层出不穷，但经过时间考验、被各种场景验证过的成熟技术其实更多（高可用的主备/集群、高性能的负载均衡/多路复用、可扩展的分层/插件化等），有了明确目标后「按图索骥」就能找到可选方案。
  - 只有当这种方式完全无法满足需求时才考虑创新，而方案创新绝大部分情况下也是基于已有成熟技术（NoSQL 的 K-V 存储与数据库索引类似，Memcache 只是把数据库索引独立出来做成缓存系统；Hadoop 大文件存储的基础是集群方案 + 数据复制方案；Docker 虚拟化的基础是 LXC；LevelDB 的文件存储结构是 Skip List）。
- **完整判据/清单/步骤**
  - **第 2 步的输入/输出/动作**：输入＝第 1 步产出的复杂度清单（高性能消息读取、高可用写入/存储/读取）+ 团队与资源约束（Java、6 人、Linux+MySQL、单机房）；动作＝按「已有模式组合」找方案、做技术选型、把差异做明显；输出＝3~5 个差异明显、粒度只到选型的备选方案。
  - **第 2 步：设计备选方案 —— 三种常见错误、每条弊端、正确做法**
    - **错误一：设计最优秀的方案。** 技术情结：要设计优秀架构才能体现技术能力（高可用里集群明显比主备优秀强大；高性能里淘宝的 XX 方案是业界领先）。→ 按「合适原则」「简单原则」，挑选适合自己业务、团队、技术能力的方案才是好方案；否则要么浪费大量资源开发无用系统（TPS 50000 设计、实际 500），要么根本无法实现（10 人团队开发现在的整个淘宝系统）。
    - **错误二：只做一个方案。** 心里简单设想几个方案、简单判断哪个最好，然后直接进入详细设计。弊端三条：
      1. 心里评估过于简单、可能没想全面，只因某一个缺点就否决某方案；而实际上没有哪个方案是完美的，某个地方有缺点的方案可能是综合来看最好的方案。
      2. 架构师经验、知识、技能也有局限，某个评估标准或经验可能不正确，或老经验不适合新情况，甚至评估标准本身就是架构师原来理解错的。
      3. 单一方案会导致过度辩护：评审时针对问题和疑问竭尽全力为设计辩护，经验不足者可能强词夺理。
    - **错误三：备选方案过于详细。** 把备选方案等同于最终方案，每个都写很细。弊端三条：
      1. 耗费大量时间和精力。
      2. 注意力集中到细节、忽略整体技术设计，导致备选方案数量不够或差异不大。
      3. 评审时其他人被细节绕进去、评审效果很差（例：针对某个定时器该 1 分钟还是 30 秒争论得不可开交）。
    - **正确做法（四条判据）**：
      1. **数量 3~5 个为最佳**：少于 3 个可能思维狭隘、考虑不周全；多于 5 个耗费大量精力和时间，且方案之间差别可能不明显。
      2. **差异要比较明显**：主备 vs 集群差异明显；同样主备，用 ZooKeeper 做决策 vs 用 Keepalived 做决策差异也明显；但都用 ZooKeeper、一个检测周期 1 分钟一个 5 分钟，这**不是架构差异而是细节差异**，不适合做成两个方案。
      3. **技术不要只局限于已经熟悉的技术**：要放宽视野；「如果你手里有一把锤子，所有的问题在你看来都是钉子」——例如架构师对 MySQL 很熟悉，不管什么存储都基于 MySQL 设计，性能不够就先想 MySQL 分库分表，而事实上也许引入一个 Memcache 缓存就能解决问题。
      4. **备选阶段关注的是技术选型，而不是技术细节**：例：ZooKeeper vs Keepalived 实现主备差异很大；但都用 ZooKeeper，一个节点设计成 `/service/node/master`、另一个 `/company/service/master`，并无明显差异，不该作为两个备选方案，节点路径如何设计留到最终方案细化。
  - **实战：前浪微博消息队列的三个备选方案（设计动作）**
    - 目标输入（来自第 1 步）：高性能消息读取 + 高可用消息写入 + 高可用消息存储 + 高可用消息读取；QPS 13800；团队 Java、6 人；Linux + MySQL；单机房。
    - **方案 1：采用开源 Kafka** —— 理由：成熟开源消息队列方案，功能强大、性能非常高、已经比较成熟，很多大公司在用。
    - **方案 2：集群 + MySQL 存储** —— 推导步骤：
      - 先考虑单服务器高性能：高性能消息读取属「计算高可用」范畴（原文如此），单服务器高性能备选方案很多。
      - 语言选择：团队开发语言是 Java；虽然有人觉得 C/C++ 更适合写高性能中间件，但架构师综合判断**无须为语言性能优势让整个团队切换语言**，继续用 Java。
      - 网络库：Netty 是 Java 领域成熟的高性能网络库 → 基于 Netty 开发。
      - 因设计 QPS 13800，单机即使 Netty 也「有很大风险」→ 采用**集群方式**满足高性能消息读取，集群负载均衡算法用**简单的轮询**。
      - 高可用写入与高性能读取同理用集群；因为消息只要写入集群中一台就算成功写入，所以分配算法也用轮询：正常情况下客户端依次写入不同服务器，某台异常时客户端直接写下一台正常服务器。
      - 最复杂的是「高可用存储」与「高可用读取」：前者要求已写入消息在单台宕机时不丢失，后者要求已写入消息在单台宕机时可继续读取 → 利用 MySQL 主备复制实现高可用存储，用服务器主备方案实现高可用读取。
      - 方案要点：数据分散集群架构，集群中服务器分组、每组存一部分消息数据；每组一台主 MySQL + 一台备 MySQL，组内主备数据复制、**组间数据不同步**；正常情况下组内主服务器对外提供写入与读取服务、备服务器不对外提供服务；主服务器宕机时备服务器对外提供消息读取服务；客户端轮询写入与读取。
    - **方案 3：集群 + 自研存储方案** —— 在方案 2 基础上把 MySQL 存储换成自研存储：MySQL 的关系型特点并不很契合消息队列的数据特点，参考 Kafka 的做法，自己实现一套文件存储和复制方案。
    - 方案空间的可扩展提示：开源方案可选 Kafka、ActiveMQ、RabbitMQ；集群方案的存储可选 MySQL、HBase、Redis 与 MySQL 结合；自研文件系统可参考 Kafka、LevelDB、HBase。
- **数字与阈值**
  - **3~5 个**：备选方案数量的最佳区间——用途：少于 3 思维狭隘，多于 5 精力浪费且差异不明显。
  - **1 分钟 vs 5 分钟检测周期**：ZooKeeper 主备决策的两种参数——用途：界定「细节差异不算备选方案」。
  - **QPS 13800 / TPS 1380**：第 1 步得出的设计目标——用途：判定单机不可行、必须集群的直接依据。
  - **6 人**：中间件团队规模——用途：语言与自研范围被团队背景约束。
  - **10 人团队 / TPS 50000 / 实际 500**：能力与目标错配的两个极端示例——用途：说明「最优秀方案」错误与「单一方案」风险的后果。
- **案例/数据**
  - Kafka 作为方案 1 → 结论：成熟开源、性能高、大厂在用，是「按图索骥」最省力的一格。
  - Netty + Java + 集群 + MySQL 主备（方案 2）→ 结论：团队技术栈本身就是备选范围的硬约束；高性能靠集群横向扩展、高可用靠主备复制。
  - 自研文件存储（方案 3）→ 结论：存储不契合是自研的唯一正当理由，参考对象是 Kafka 的做法。
  - 「备选方案 2 和 3 都基于 Netty、用 Java」→ 结论：**通常情况下成熟的团队不会轻易改变技术栈，反而是新成立的技术团队更倾向采用新技术**。
- **反例与坑**
  - 一上来就设计「最优秀」的方案（集群一定优于主备、淘宝的方案一定对）。
  - 只做一个方案，然后进入详细设计。
  - 把备选方案写成最终方案（细节淹没选型，评审跑偏到 1 分钟还是 30 秒）。
  - 只在自己熟悉的技术里找方案（锤子与钉子）。
  - 把「同一技术的参数差异」当成两个架构方案。
- **原文金句**
  - 「架构师的工作并不神秘，成熟的架构师需要对已经存在的技术非常熟悉，对已经经过验证的架构模式烂熟于心，然后根据自己对业务的理解，挑选合适的架构模式进行组合，再对组合后的方案进行修改和调整。」
  - 「备选方案的数量以 3 ~ 5 个为最佳。少于 3 个方案可能是因为思维狭隘，考虑不周全；多于 5 个则需要耗费大量的精力和时间，并且方案之间的差别可能不明显。」
  - 「正确的做法是备选阶段关注的是技术选型，而不是技术细节，技术选型的差异要比较明显。」
  - 「通常情况下，成熟的团队不会轻易改变技术栈，反而是新成立的技术团队更加倾向于采用新技术。」
- **可迁移到知识库的主题**
  - `备选方案设计`、`技术选型 vs 技术细节`、`架构模式组合`、`锤子与钉子`、`技术栈约束`

## 12 | 架构设计流程：评估和选择备选方案

### 12 | 架构设计流程：评估和选择备选方案
- **核心结论**
  - 挑最终方案很难，原因三条：每个方案都是可行的（不可行就不该作为备选）；没有哪个方案是完美的（A 有性能缺点、B 有成本缺点、C 有新技术不成熟风险）；评价标准主观性强（「复杂」难以量化，评审常争得面红耳赤）。
  - 实践中常见的四种指导思想（最简派、最牛派、最熟派、领导派）本身不存在绝对对错，关键是**不同场景采取不同方式**；判断「有时候」的方法就是 **360 度环评**：列出需要关注的质量属性点，分别从这些维度评估每个方案，再综合挑选适合当时情况的最优方案。
  - 环评后仍要用**按优先级选择**（而非数量对比法、加权法）才能得出最终方案。
- **完整判据/清单/步骤**
  - **四种错误指导思想（作为反面清单）**：
    - **最简派**：挑看起来最简单的。例：全文搜索，方案 1 基于 MySQL、方案 2 基于 Elasticsearch；MySQL 查询简单，ES 倒排索引复杂得多（要设计索引、要设计分布式），于是干脆选 MySQL。
    - **最牛派**：挑技术上最牛的（性能最高、可用性最好、功能最强，或淘宝用的、微信开源的、Google 出品的）。例：缓存选型，Memcache 是纯内存缓存、支持基于一致性 hash 的集群；Redis 支持持久化、数据字典、主备、集群，「看起来比 Memcache 好很多」，于是选 Redis。
    - **最熟派**：基于过往经验挑最熟悉的。例：C++ 出身的开发人员设计运维管理系统，因不熟 Python / Ruby on Rails，继续选 C++。
    - **领导派**：列出备选方案自己拿捏不定，让领导定夺（选对是领导厉害，选错是领导背锅）。
  - **第 3 步的输入/输出/动作**：输入＝全部备选方案 + 评审会上研发/测试/运维/业务主管的多方意见；动作＝列质量属性、逐方案逐维度评估、填环评表、按优先级决策；输出＝一张 360 度环评表 + 一个被明确论证过取舍的最终方案。
  - **第 3 步：评估和选择备选方案 —— 360 度环评的操作**
    1. 列出需要关注的质量属性点。常见清单（7 项）：**性能、可用性、硬件成本、项目投入、复杂度、安全性、可扩展性**。
    2. 分别从这些质量属性维度评估每个方案。
    3. 整理出 **360 度环评表**，一目了然地看到各方案优劣点。
    4. 用**按优先级选择**得出最终方案（见下）。
  - **评估每个质量属性时的约束（合适原则 + 简单原则）**：避免贪大求全，某个质量属性能够满足一定时期内业务发展就可以了。例：购物网站现在 TPS 1000，预期 1 年内发展到 TPS 2000（业务一年翻倍已很好），则性能超过 2000 的方案都合适；不能因为淘宝 TPS 10 万就也按 10 万设计。
  - **未来业务规模预估方法（演化原则）**：把当前业务规模乘以 **2~4**——现在基数低乘 4，基数高乘 2。例：现 TPS 1000 → 按 4000 设计；现 TPS 10000 → 按 20000 设计。担心「一年翻 10 倍」是小概率，每次都考虑会导致过度设计、投入浪费；真出现就重做方案，代价可接受（业务迅猛发展时钱和人不是问题，淘宝和微信都有过多次大规模重构）。
  - **理想方案判据**：最好能做到「简单扩容就能跟上业务发展」——例：TPS 2000 时 2 台机器，TPS 20000 时把机器扩到 20 台即可。但现实往往不理想，因为量变引起质变，哪些地方质变很难提前很久预判。
  - **量变质变的具体判据（5 人团队 → 20 人团队，TPS 2000 → 20000 时发生的两个质变）**：
    1. 团队规模扩大：20 人在同一系统上开发，开发效率变低、迭代变慢，常出现某功能开发完要等另一功能才能一起测试上线 → 需要把系统拆分为更多子系统。
    2. 原来单机房的集群设计不满足业务需求 → 需要升级为异地多活架构。
    3. 反例：不能「事后诸葛亮」地一开始就拆分并支持异地多活——最初只有 5 个人，要在有限时间内完成后来 20 个人才能完成的高性能、异地多活、可扩展架构，项目时间会遥遥无期，业务等不了。
  - **两种「看似正确实际错误」的选择方法**
    - **数量对比法**：看哪个方案优点多就选哪个（5 个质量属性中 A 占优 3 个、B 占优 2 个 → 选 A）。问题一：把所有质量属性重要性等同，没考虑优先级（BAT 成本不是问题，可用性和可扩展性远比成本重要；创业公司成本可能很重要）。问题二：会出现优点数量相同（6 个属性各 3 个）无法选择；若为制造数量不对称强行再加一个不重要的属性，这个最后加入的不重要属性反而成了决定因素，同样犯了不区分优先级的问题。
    - **加权法**：给每个质量属性权重（性能高中低 = 10/5/3 分，成本高中低 = 5/3/1 分），加总选最高分。问题：无法客观给出权重得分——为何性能是 10/5/3 而不是 5/3/1 或 100/80/60？没有明确标准；甚至会出现为选某方案故意调高/调低权重分值，「最后方案的选择就变成了一个数字游戏」。
  - **正确做法：按优先级选择** ——架构师综合当前业务发展情况、团队人员规模和技能、业务发展预测等因素，把质量属性按优先级排序；先挑满足第一优先级的，都满足再看第二优先级，依此类推。会不会出现多个方案各属性优缺点完全一样？理论上可能、实际上不可能——因为备选方案设计时已要求差异明显。
  - **评审组织方式（实战输入）**：架构师组织备选方案评审会议，参加人包括研发、测试、运维、几个核心业务主管；各方从自身视角给意见，架构师汇总成环评表并决策。
- **数字与阈值**
  - **TPS 1000 / 2000 / 10 万**：当前值、一年后预期值、淘宝对标值——用途：界定「性能合适」的区间，反对按大厂标准设计。
  - **2 ~4 倍**：业务规模预估系数（基数低取 4、基数高取 2）——用途：性能与硬件成本类属性的评估基准。
  - **TPS 1000→4000、TPS 10000→20000**：系数应用示例——用途：示范预估算法。
  - **2 台 → 20 台**：TPS 2000 → 20000 的理想扩容路径——用途：衡量方案是否「简单扩容即可跟上业务」。
  - **5 人 / 20 人、TPS 2000 / 20000**：团队与业务同步翻十倍的质变场景——用途：说明量变引起质变、无法长期预判。
  - **7 个质量属性**：性能、可用性、硬件成本、项目投入、复杂度、安全性、可扩展性——用途：360 度环评的默认维度清单。
  - **5 个属性 3:2 / 6 个属性 3:3**：数量对比法失效的两个具体情形——用途：证明「数优点」不成立。
  - **10/5/3 与 5/3/1**、**100/80/60**：加权法可能给出的权重分值——用途：证明权重分值是任意设定的数字游戏。
  - **4 台机器/分组（2 台服务器 + 2 台数据库）、12 台服务器**：方案 2 的成本量化——用途：环评中「硬件成本」一栏的实际数据。
  - **6 人**：中间件团队规模——用途：排除自研存储的关键判据。
- **案例/数据**
  - 前浪微博评审（方案 1 Kafka）→ 业务主管倾向（成熟、各团队了解过）；部分研发支持（省开发投入）；部分研发质疑（Kafka 设计目的是支撑大容量**日志**消息传输，而本项目要的是**业务数据可靠传输**）；运维**强烈反对**（Kafka 是 Scala 编写，运维无维护 Scala 系统经验、出问题难快速处理；已有成熟运维体系含部署/监控/应急，Kafka 无法融入、需单独投入人力）；测试倾向（成熟、无须太多测试投入）。
  - 方案 2（集群 + MySQL）→ 研发认为简单，但部分人怀疑性能（MySQL 存消息不如文件系统），并担心「用 MySQL 做消息队列比较土、另类」影响技术声誉；运维赞同（可融入现有运维体系、MySQL 可靠性有保证、有丰富运维经验），但认为成本高（一个数据分组需 4 台机器）；测试认为测试人力投入大（功能、性能、可靠性测试）；业务主管既不肯定也不否定（反正不是业务团队投入人力，只要稳定可靠即可）。
  - 方案 3（集群 + 自研存储）→ 部分研发认为是好方案（展现技术实力、性能高于 MySQL）；另一部分认为复杂度太高、按目前人力和技术实力做到稳定可靠需较长迭代，过程中可能因存储出现严重问题（如文件损坏丢大量数据）；运维不太赞成（此前遇到过存储系统故障导致数据丢失、损失惨重，如 MongoDB 丢数据、Tokyo Tyrant 丢数据无法恢复；不相信中间件团队的技术实力足以自研存储）；测试赞同运维（自研存储测试难度高、投入大）；业务主管保留意见（新系统上线肯定有 bug，存储系统出 bug 最严重）。
  - 最终选**方案 2**，三条理由 → 排除方案 1 主因是**可运维性**（再成熟的系统上线后都可能出问题，出问题无法快速解决就满足不了业务；且 Kafka 主要设计目标是高性能日志传输，而本项目主要目标是业务消息可靠传输）；排除方案 3 主因是**复杂度**（团队 6 人还有其他中间件系统要开发维护，无法支撑自研存储，参考简单原则）；方案 2 优点是复杂度不高、能很好融入现有运维体系、可靠性有保障。
  - 对方案 2 三个缺点的回应 → 性能：业务目前需要的不高、方案 2 能满足，即使后续需求增加，数据分组方案也能平行扩展（演化原则）；成本：一个分组 4 台机器、支撑当前业务可能需 12 台服务器，但备机（服务器和数据库）主要用作备份，**可以和其他系统并行部署在同一台机器上**；技术不优越：设计目的不是证明自己（合适原则），而是更快更好满足业务需求。
  - 同一组备选方案在不同团队会有不同结果 → 结论：创业公司初创团队人手不够、要快速上线，会选 Kafka；阿里人多力量大、业务复杂，会选自研（RocketMQ）。备选方案选择不只看性能高低、技术是否优越，业务需求特点、运维团队经验、已有技术体系、团队技术水平都会影响选择。
- **反例与坑**
  - 最简派（只看实现简单，忽略是否匹配业务）、最牛派（只看技术标签）、最熟派（只用手熟的）、领导派（把决策责任上交）。
  - 数量对比法：把质量属性等同看待；为凑数量强行加一个不重要的属性。
  - 加权法：权重分值无客观标准，容易变成「数字游戏」。
  - 按大厂标准定自己的性能目标（淘宝 10 万 TPS）。
  - 为小概率的 10 倍增长做过度设计。
  - 「事后诸葛亮」式架构：一开始就按 20 人团队、异地多活的规模设计。
- **原文金句**
  - 「真正应该选择哪种方法来评估和选择备选方案呢？我的答案就是“360 度环评”！具体的操作方式为：列出我们需要关注的质量属性点，然后分别从这些质量属性的维度去评估每个方案，再综合挑选适合当时情况的最优方案。」
  - 「这种方案主要的问题在于把所有质量属性的重要性等同，而没有考虑质量属性的优先级。」
  - 「这个分数是很难确定的，没有明确的标准，甚至会出现为了选某个方案，设计师故意将某些权重分值调高而降低另外一些权重分值，最后方案的选择就变成了一个数字游戏了。」
  - 「正确的做法是按优先级选择，即架构师综合当前的业务发展情况、团队人员规模和技能、业务发展预测等因素，将质量属性按照优先级排序，首先挑选满足第一优先级的，如果方案都满足，那就再看第二优先级……以此类推。」
- **可迁移到知识库的主题**
  - `360度环评`、`质量属性优先级`、`数量对比法与加权法之误`、`运维可融入性`、`过度设计与演化`

## 13 | 架构设计流程：详细方案设计

### 13 | 架构设计流程：详细方案设计
- **核心结论**
  - 详细方案设计就是**将方案涉及的关键技术细节确定下来**——把选定的备选方案细化成可以落地的设计方案。
  - 详细设计里也会遇到「多选一」（如 Nginx 负载均衡策略五选一），但这类技术选择是**轻量级**的，无须像备选方案阶段那样做环评，只须按技术的适用场景选择。
  - 极端情况：详细设计阶段发现备选方案不可行，主因通常是备选阶段遗漏了某个关键技术点或关键质量属性（典型是被忽略的**开发周期**）。
- **完整判据/清单/步骤**
  - **第 4 步的输入/输出/动作**：输入＝选定的最终方案（此时粒度还比较粗，无法指导开发）；动作＝把关键技术细节逐项拍板（必要时按适用场景做轻量级技术选择）；输出＝一套可落地、能指导开发的设计点（表结构、复制范围、倒换方式、读写路径、通信协议等）。
  - **第 4 步：详细方案设计 —— 产出什么（示例清单）**
    - 若选 Elasticsearch：索引按业务划分还是一个大索引；副本数量 2/3/4；集群节点数量 3/6。
    - 若选 MySQL 分库分表：哪些表要分库分表；按什么维度分；分库分表后联合查询怎么处理。
    - 若选 Nginx 做负载均衡：Nginx 主备怎么做；负载均衡策略用哪个（权重分配？轮询？ip_hash？）。
  - **Nginx 五种负载均衡策略的适用场景（详细设计阶段的「按场景选」示范）**

    | 策略 | 做法 | 适用场景 / 关键行为 |
    |---|---|---|
    | 轮询（默认） | 每个请求按时间顺序逐一分配到不同后端服务器，各服务器分配请求数基本一致；后端服务器 down 掉能自动剔除 | 后端同构、无会话粘性的通用场景 |
    | 加权轮询 | 根据权重轮询，权重高的服务器分配更多请求 | 后端服务器性能不均，如新老服务器混用 |
    | ip_hash | 每个请求按访问 IP 的 hash 结果分配，每个访客固定访问一个后端服务器 | 解决 session 问题，如购物车类应用 |
    | fair | 按后端服务器响应时间分配，响应时间短的优先 | 后端性能不均衡；可防止某台性能不足还继续接同样多请求而雪崩 |
    | url_hash | 按访问 URL 的 hash 结果分配，每个 URL 定向到同一台后端服务器 | 后端服务器能缓存 URL 响应结果的情况 |
    - 选择示例：电商架构与 session 强相关，用 Nginx 做集群负载均衡时选 **ip_hash** 比较合适。
  - **防止「详细设计推翻备选方案」的三条做法**
    1. 架构师不但要做备选方案设计和选型，还要对备选方案的**关键细节有较深入理解**（例：选 ES 的前提是自己对索引、副本、集群等设计原理有深入理解；不能道听途说 ES 很牛就选，更不能做把「细节我们不讨论」挂在嘴边的「PPT 架构师」）。
    2. 通过**分步骤、分阶段、分系统**等方式尽量降低方案复杂度——方案越复杂，某个细节推翻整个方案的可能性越高。
    3. 方案本身很复杂时，采取**设计团队**的方式设计，博采众长，防止 1~2 个架构师出现思维盲点或经验盲区。
  - **实战：前浪微博消息队列（方案 2）需要细化的 6 个设计点**
    1. **数据库表如何设计？** 两类表：日志表（消息写入时快速存储到 MySQL）、消息表（每个消息队列一张表）。流程：业务系统发布消息先写日志表，日志表写入成功即代表消息写入成功；后台线程再从日志表读取写入记录，把消息内容写入消息表；业务系统读消息时从消息表读。表结构：日志表 `MQ_LOG` 字段为日志 ID、发布者信息、发布时间、队列名称、消息内容；消息表表名即队列名称，字段为消息 ID（递增生成）、消息内容、消息发布时间、消息发布者。日志表要及时清除已写入消息表的日志数据；消息表最多保存 30 天的消息数据。
    2. **数据如何复制？** 直接采用 MySQL 主从复制；**只复制消息存储表，不复制日志表**。
    3. **主备服务器如何倒换？** 用 ZooKeeper 做主备决策：主备服务器都连 ZooKeeper 建立自己的节点，主服务器路径 `/MQ/server/分区编号/master`、备机 `/MQ/server/分区编号/slave`，节点类型 EPHEMERAL；备机监听主机节点消息，发现主服务器节点断连后，备服务器修改自己的状态，对外提供消息读取服务。
    4. **业务服务器如何写入消息？** 消息队列系统设两个角色：生产者、消费者，每个角色有唯一名称；提供 SDK 供业务系统调用；SDK 从配置读取所有消息队列服务器信息，采取**轮询**算法向主服务器发起写入请求；若某个主服务器无响应或返回错误，SDK 把请求发到下一台服务器。
    5. **业务服务器如何读取消息？** SDK 从配置读取所有服务器信息，**轮流向所有服务器**发起读取请求；消息队列服务器需记录每个消费者的消费状态（当前消费者已读到哪条消息），收到读取请求时返回下一条未被读取的消息。
    6. **通信协议如何设计？** 考虑后续可能对接多种编程语言的系统、为提升兼容性：传输协议用 **TCP**，数据格式用 **ProtocolBuffer**。
    - 注：原文明确这还不是完整设计方案，只是示例，用于说明「细化方案具体如何去做」。
- **数字与阈值**
  - **副本 2/3/4、节点 3/6**：ES 详细设计中需要拍板的具体数值档位——用途：说明「细节确定」是什么颗粒度。
  - **5 种策略**：Nginx 轮询、加权轮询、ip_hash、fair、url_hash——用途：详细设计阶段的轻量级选型清单。
  - **30 天**：消息表数据保存上限——用途：容量与清理策略的约束。
  - **1 年**：某项目因细节太多导致预计开发周期长达 1 年，最终废弃原备选方案——用途：量化「遗漏开发周期这一质量属性」的代价。
  - **1~2 个架构师**：易出现思维盲点/经验盲区的人数规模——用途：论证复杂方案要用设计团队。
- **案例/数据**
  - Elasticsearch / MySQL 分库分表 / Nginx 三个「细化清单」→ 结论：详细设计的产出是**一串可执行的技术决定**，而非再讨论要不要用这个技术。
  - Nginx 五策略按场景选（电商选 ip_hash）→ 结论：细节级技术选择按适用场景直接定，不必再做 360 度环评。
  - 某项目在详细设计阶段发现方案庞大、要开发 1 年而废弃 → 结论：备选阶段遗漏「开发周期」这一质量属性，会导致整个选型作废；这正是「关键技术点/质量属性要在备选阶段想全」的反证。
  - 前浪微博 6 个细化点 → 结论：详细方案要覆盖表结构、复制范围、故障倒换、写入路径、读取路径、通信协议六个面，缺一项就无法指导开发。
- **反例与坑**
  - 做「PPT 架构师」：把「细节我们不讨论」挂在嘴边，选型靠道听途说。
  - 备选阶段遗漏关键质量属性（如开发周期），到详细设计才发现不可行，只能废弃方案、调整目标计划和方案。
  - 方案过于庞大复杂，某个细节就能推翻全局。
  - 由 1~2 个架构师闭门完成复杂方案设计（思维盲点、经验盲区）。
- **原文金句**
  - 「简单来说，详细方案设计就是将方案涉及的关键技术细节给确定下来。」
  - 「但实际上这里的技术方案选择是很轻量级的，我们无须像备选方案阶段那样操作，而只需要简单根据这些技术的适用场景选择就可以了。」
  - 「例如，架构师选择了 Elasticsearch 作为全文搜索解决方案，前提必须是架构师自己对 Elasticsearch 的设计原理有深入的理解，比如索引、副本、集群等技术点；而不能道听途说 Elasticsearch 很牛，所以选择它，更不能成为把“细节我们不讨论”这句话挂在嘴边的“PPT 架构师”。」
  - 「方案本身的复杂度越高，某个细节推翻整个方案的可能性就越高，适当降低复杂性，可以减少这种风险。」

## 14 | 高性能数据库集群：读写分离

### 14 | 高性能数据库集群：读写分离
- **核心结论**
  - 关系数据库因 ACID 和强大 SQL 仍是各类业务系统的关键核心存储，很多场景下高性能设计的核心就是关系数据库的设计；但业务发展与数据增长速度远超数据库厂商的优化速度，单机难以满足，必须用集群提升性能。
  - 高性能数据库集群两种方式：**读写分离**——本质是把访问压力分散到集群多个节点，**但没有分散存储压力**；**分库分表**——既分散访问压力，又分散存储压力。
  - 读写分离实现逻辑不复杂，但有两个细节引入设计复杂度：**主从复制延迟**与**分配机制**。
- **完整判据/清单/步骤**
  - **基本原理（四条实现要点）**：
    1. 数据库服务器搭建主从集群，一主一从、一主多从都可以。
    2. 数据库主机负责读写操作，从机只负责读操作。
    3. 数据库主机通过复制将数据同步到从机，**每台数据库服务器都存储了所有的业务数据**。
    4. 业务服务器将写操作发给主机、读操作发给从机。
  - **术语判据：主从集群 vs 主备集群**——「从机」的「从」可理解为「仆从」，仆从要帮主人干活，「从机」需要提供读数据功能；「备机」一般仅提供备份功能、不提供访问功能。用「主从」还是「主备」要看场景，两个词并不完全等同。
  - **复杂度一：主从复制延迟 —— 问题与三种解法（含代价）**
    - 问题：写主机后立刻（1 秒内）读，读操作走从机，主机还没复制过来 → 读不到最新数据。例：用户刚注册完立刻登录，系统提示「你还没有注册」。
    - 解法 1：**写操作后的读操作指定发给主服务器**（如注册完成后登录时的账号读取也发主机）。代价：与业务强绑定，对业务侵入和影响较大；新来的程序员不知道这样写就会引入 bug。
    - 解法 2：**读从机失败后再读一次主机（二次读取）**。代价：与业务无绑定，只需封装底层数据库访问 API，实现代价较小；但二次读取多时会大大增加主机读压力（例：黑客暴力破解账号 → 大量二次读取 → 主机可能顶不住读压力崩溃）。
    - 解法 3：**关键业务读写操作全部指向主机，非关键业务采用读写分离**。例：用户管理系统里注册+登录全部访问主机；用户介绍、爱好、等级等采用读写分离——即使改了自我介绍查询到旧值，业务影响比「不能登录」小很多，可以忍受。
  - **复杂度二：分配机制 —— 两种封装方式（含各自特点）**
    - 方式 A：**程序代码封装**（也称「中间层封装」）——在代码中抽象一个数据访问层，实现读写分离和数据库连接管理（例如基于 Hibernate 简单封装即可）。特点：
      1. 实现简单，且可根据业务做较多定制化功能。
      2. 每个编程语言都要自己实现一次，无法通用；一个业务含多种语言的多个子系统时重复开发量大。
      3. 故障情况下如果主从切换，可能需要所有系统改配置并重启。
      - 开源代表：淘宝 **TDDL**（Taobao Distributed Data Layer，外号「头都大了」）——通用数据访问层，功能封装在 jar 包供业务代码调用；基本原理是基于集中式配置的 jdbc datasource 实现，具有主备、读写分离、动态数据库配置等功能。
    - 方式 B：**中间件封装**——独立一套系统，实现读写分离和数据库连接管理；对业务服务器提供 **SQL 兼容协议**，业务服务器无须自己做读写分离，访问中间件与访问数据库没有区别（在业务服务器看来中间件就是一个数据库服务器）。特点：
      1. 能支持多种编程语言（对业务提供标准 SQL 接口）。
      2. 要支持完整 SQL 语法和数据库服务器协议（如 MySQL 客户端与服务器连接协议），实现复杂、细节特别多、很容易出 bug、需要较长时间才能稳定。
      3. 中间件自己不执行真正读写，但所有数据库操作请求都要经过它，性能要求也很高。
      4. 数据库主从切换对业务服务器无感知——中间件可探测主从状态（例如向某个测试表写一条数据，成功的是主机、失败的是从机）。
      - 开源代表：MySQL 官方先提供 **MySQL Proxy**（一直未正式 GA），现推荐 **MySQL Router**（功能：读写分离、故障自动切换、负载均衡、连接池）；奇虎 360 的 **Atlas**（基于 MySQL Proxy 实现）——对后端 DB 相当于客户端、对前端应用相当于一个 DB，实现了 MySQL 客户端与服务端协议，并维护连接池以降低 MySQL 负担。
    - **选型判据**：数据库中间件复杂度比程序代码封装**高出一个数量级**，一般情况下建议采用程序语言封装的方式，或使用成熟的开源数据库中间件；如果是大公司，可以投入人力自研中间件——因为这套系统一旦做好，接入的业务系统越多，节省的程序开发投入越多，价值越大。
  - **适用规模判据（原文思考题方向的相关论述）**：读写分离只分散读压力、每台仍存全量数据，因此受单机存储容量与写入能力约束——存储压力需靠 15 讲的分库分表解决。
- **数字与阈值**
  - **1 秒 / 1 分钟**：MySQL 主从复制延迟的常见值与大量数据同步时的极端值——用途：界定「写后立即读」的不一致窗口。
  - **一主一从 / 一主多从**：主从集群的可选形态——用途：说明从机数量可横向增加以扩读能力。
  - **高出一个数量级**：数据库中间件相对程序代码封装的复杂度差——用途：选型时的默认否决理由。
  - **测试表写入**：中间件探测主从的技术手段（对测试表写一条数据，成功是主机、失败是从机）——用途：说明主从切换对业务无感知的实现原理。
- **案例/数据**
  - 注册后立刻登录被提示「你还没有注册」→ 结论：主从延迟是业务可见的 bug，不是理论问题。
  - 黑客暴力破解导致大量二次读取、主机被压垮 → 结论：二次读取把压力转移回主机，安全性事件会放大该缺陷。
  - 用户管理系统「注册+登录走主机、介绍/爱好/等级走读写分离」→ 结论：按业务重要性分级是成本最低的延迟规避手段。
  - TDDL（jar 包 + 集中式配置 jdbc datasource）→ 结论：程序封装路线适合单一语言栈、追求简单与定制。
  - MySQL Proxy → MySQL Router、Atlas → 结论：中间件路线能多语言、主从切换无感知，但实现复杂、易出 bug、性能要求高。
- **反例与坑**
  - 把「主从」当「主备」用（或反之）：备机不提供访问，从机要提供读。
  - 写后立即读却走从机 → 业务 bug。
  - 用「二次读取」兜底一切：高并发/攻击场景会把读压力全推回主机。
  - 小团队自研数据库中间件（复杂度高一个数量级、细节多、易出 bug）。
  - 误以为读写分离能解决存储瓶颈（它不分散存储压力）。
- **原文金句**
  - 「高性能数据库集群的第一种方式是“读写分离”，其本质是将访问压力分散到集群中的多个节点，但是没有分散存储压力；第二种方式是“分库分表”，既可以分散访问压力，又可以分散存储压力。」
  - 「“从机”的“从”可以理解为“仆从”，仆从是要帮主人干活的，“从机”是需要提供读数据的功能的；而“备机”一般被认为仅仅提供备份功能，不提供访问功能。」
  - 「由于数据库中间件的复杂度要比程序代码封装高出一个数量级，一般情况下建议采用程序语言封装的方式，或者使用成熟的开源数据库中间件。」
  - 「这个系统一旦做好，接入的业务系统越多，节省的程序开发投入就越多，价值也越大。」
- **可迁移到知识库的主题**
  - `读写分离`、`主从延迟`、`二次读取`、`TDDL/Atlas/MySQL Router`、`主从vs主备`

## 15 | 高性能数据库集群：分库分表

### 15 | 高性能数据库集群：分库分表
- **核心结论**
  - 读写分离不分散存储压力；当数据量达到千万甚至上亿条，单台数据库服务器的存储能力成为瓶颈，必须把存储分散到多台服务器。
  - 分库分表包含「分库」和「分表」两大类：**业务分库**按业务模块分散；**分表**分垂直分表与水平分表。两者都能分散存储压力并提升性能，但都会引入复杂性。
  - 对小公司初创业务**不建议一开始就业务分库**；对已有成熟方案、用户规模海量的成熟大公司，**最好在业务开始设计时就考虑业务分库**。
- **完整判据/清单/步骤**
  - **单库存储瓶颈的三个表现（判据）**：数据量太大读写性能下降（即使有索引，索引也会变得很大，性能同样下降）；数据文件很大，备份和恢复耗时很长；数据文件越大，极端情况下丢失数据风险越高（例：机房火灾导致主备机都故障）。
  - **业务分库 —— 定义与三个新问题**
    - 定义：按业务模块把数据分散到不同数据库服务器。例：电商的用户、商品、订单三块数据分别放三台服务器。
    - 问题 1 **join 操作**：原本同库的表分散后无法用 SQL join。例「查询购买了化妆品的用户中女性用户列表」：订单库有用户 ID、性别在用户库 → 只能先从订单库查出购买化妆品的用户 ID 列表，再到用户库查这批 ID 中的女性用户，实现比 join 复杂。
    - 问题 2 **事务**：同库不同表可同一事务修改，分库后无法用事务统一修改。厂商的分布式事务方案（如 MySQL XA）性能太低，与高性能存储目标相违背。例：下单扣库存，同库可用事务保证「扣库存 + 生成订单」要么都成功要么都失败；分库后需业务程序自己模拟——先扣库存、成功后生成订单，若订单库异常导致生成订单失败，业务程序要把库存加回；若业务程序自身异常导致生成订单失败，库存无法恢复，只能人工通过日志等方式手工修复。
    - 问题 3 **成本**：本来 1 台服务器搞定，现在要 3 台；考虑备份则 2 台变 6 台。
    - **小公司初创业务不建议一开始拆分的三条理由**：
      1. 初创业务不确定性很大，业务不一定能发展起来，开始时并没有真正的存储和访问压力，业务分库不能带来价值。
      2. 分库后表间 join、数据库事务无法简单实现。
      3. 分库后不同数据要读写不同数据库，代码需增加按数据类型映射到不同库的逻辑，增加工作量；而初创期最重要的是快速实现、快速验证，分库会拖慢业务节奏。
    - **对「为何不一开始就设计好」的回答（按三原则）**：
      1. 「如果业务真的发展很快」概率很低——做 10 个业务有 1 个能活下去就很不错，更何况快速发展，和中彩票概率差不多；每个业务都按淘宝、微信规模设计，「不但会累死自己，还会害死业务」。
      2. 真发展很快，后面再分库也不迟——业务发展好则资源投入加大，可以用更多人和钱解决分库带来的代码与业务复杂问题、成本问题。
      3. 单台数据库服务器性能没有想象中弱——一般能支撑 **10 万用户量级**的业务；初创业务从 0 到 10 万级用户并没有想象中快。
    - **成熟大公司的判据**：已有业务分库成熟解决方案，且即使是尝试性新业务用户规模也是海量的，与初创小公司有本质区别 → 最好在业务开始设计时就考虑业务分库（例：在淘宝上做一个新业务，一开始就要设计业务分库甚至分表）。
  - **分表 —— 两种切分方式（蛋糕比喻）**
    - **垂直分表**（从上往下切）：刀的运动轨迹与蛋糕垂直，切成高度相等（面积可相等也可不等）的两部分 → 对应表**记录数相同但包含不同的列**。例：切成表 A（ID、name、age、sex）与表 B（ID、nickname、description）。
    - **水平分表**（从左往右切）：刀的运动轨迹与蛋糕平行，切成面积相等（高度可等可不等）的两部分 → 对应表**列相同但包含不同的行数据**。例：两个表都含 ID、name、age、sex、nickname、description，但一个存 ID 1~999999，另一个存 ID 1000000~9999999。
    - 切分次数不局限：可以切两次，也可以切很多次（像切蛋糕可以切很多刀）。
    - **是否需要分散到不同数据库服务器**：不强制。单表切成多表后，新表即使在同一台服务器也可能带来可观性能提升；若性能已满足业务要求，可以不拆到多台（因为业务分库会引入很多复杂性问题）；若单表拆多表后单台仍无法满足性能要求，就不得不再次进行业务分库。
  - **垂直分表的适用与代价**：适合把**不常用且占大量空间**的列拆出去。例：婚恋网站筛选用 age 和 sex，nickname 和 description 主要用于展示、一般不在业务查询中用到，且 description 本身较长 → 独立到另一张表，查询 age/sex 时有性能提升。代价：表操作数量增加——原来一次查询可取 name/age/sex/nickname/description，现在要两次查询。
  - **水平分表的适用与代价（四个复杂性）**
    - 适用：表行数特别大的表。判据：有的公司要求单表行数超过 **5000 万**就必须分表（可作参考、不是绝对标准，关键看访问性能）；复杂的表可能超过 **1000 万**就要分；简单的表即使超过 **1 亿行**也可以不分；但数据量到**千万级**时架构师就要警觉（很可能是性能瓶颈或隐患）。
    - 复杂性 1 **路由**：需增加路由算法计算某条数据属于哪个子表。三种路由算法对比：

      | 路由算法 | 做法 | 设计复杂点 | 优点 | 缺点 |
      |---|---|---|---|---|
      | 范围路由 | 选有序数据列（整形、时间戳等）作路由条件，不同分段分散到不同表。例：按 1000000 范围分段，1~999999 到库 1，1000000~1999999 到库 2 | 分段大小选取：太小→子表过多、维护复杂；太大→单表仍有性能问题。**建议分段 100 万至 2000 万之间** | 可随数据增加平滑扩充新表（100 万→1000 万只需加新表，原有数据不动） | 分布不均匀：按 1000 万分表，可能某分段只有 1000 条、另一分段有 900 万条 |
      | Hash 路由 | 取某列（或几列组合）值做 Hash 运算后分散。例：`user_id % 10`，ID 985 → 5 号表，ID 10086 → 6 号表 | 初始表数量选取：太多维护麻烦、太少单表性能问题；且增加子表非常麻烦，所有数据都要重分布 | 表分布比较均匀 | 扩充新表很麻烦，所有数据都要重分布 |
      | 配置路由 | 用独立的路由表记录路由信息。例：`user_router` 表含 `user_id`、`table_id` 两列，按 user_id 查 table_id | 无算法设计难点，但多一次查询 | 设计简单、使用灵活，尤其扩充表时只需迁移指定数据再改路由表 | 必须多查询一次影响整体性能；路由表太大（几亿条）自身可能成瓶颈；若再对路由表分库分表，又陷入「选路由算法」的死循环 |
    - 复杂性 2 **join 操作**：数据分散在多个表，与其他表 join 需在业务代码或数据库中间件中做多次 join 查询再合并结果。
    - 复杂性 3 **count() 操作**：分表后某些业务逻辑仍把多表当一张表（如取总记录数用于分页或展示）。两种处理方式：

      | 方式 | 做法 | 优点 | 缺点 |
      |---|---|---|---|
      | count() 相加 | 在业务代码或中间件中对每个表 count() 后相加 | 实现简单 | 性能低：20 张表要 20 次 `count(*)`，串行可能需几秒 |
      | 记录数表 | 新建表（如 table_name、row_count），每次插入或删除子表数据成功后都更新该表 | 获取记录数性能大大优于相加，只需一次简单查询 | 复杂度增加不少：对子表的操作要同步操作记录数表，有业务逻辑遗漏就数据不一致；两操作无法放同一事务，异常时可能出现子表成功而记录数表失败；且增加写压力（每次 insert/delete 都要 update） |
      - 折中：对不要求记录数实时精确的业务，可后台定时更新记录数表——定时通过 count() 相加计算再更新，是两种方式的结合。
    - 复杂性 4 **order by 操作**：排序无法在数据库中完成，只能由业务代码或中间件分别查询每个子表数据后汇总排序。
  - **实现方式**：同样分「程序代码封装」与「中间件封装」，但比读写分离更复杂——读写分离只需判断 SQL 是读还是写（判断 SELECT/UPDATE/INSERT/DELETE 关键字即可），分库分表除判断操作类型外，还要判断 SQL 操作的表、操作函数（如 count）、order by、group by 等，再按不同操作分别处理（例：order by 需先从多个库查到各库数据，再重新 order by 才能得到最终结果）。
- **数字与阈值**
  - **千万 / 上亿条**：触发存储瓶颈的数据量级——用途：判定是否必须分散存储。
  - **5000 万**：有的公司规定的「单表行数必须分表」阈值（参考值、非绝对标准）——用途：行业经验线。
  - **1000 万 / 1 亿**：复杂表需分表的量级 / 简单表可不分的量级——用途：说明阈值取决于表的访问性能。
  - **千万级**：架构师的「警觉线」——用途：把阈值从规则变成风险信号。
  - **100 万 ~ 2000 万**：范围路由建议的分段大小区间——用途：分段设计的可操作区间。
  - **1~999999 / 1000000~9999999**、**user_id % 10（985→5、10086→6）**：范围路由与 Hash 路由的具体示例数值——用途：说明两种路由的计算方式。
  - **1 台 → 3 台、2 台 → 6 台**：业务分库的服务器成本变化（含备份）——用途：量化「成本问题」。
  - **10 万用户量级**：单台数据库服务器一般可支撑的业务规模——用途：反驳「初创就必须分库」。
  - **10 个业务 1 个活 / 中彩票**：创业成功率类比——用途：论证不为小概率做重设计。
  - **20 张表 / 几秒**：count() 相加的表数量与串行耗时——用途：量化 count() 相加的性能缺点。
  - **几亿条**：配置路由的路由表可能达到的规模——用途：说明配置路由自身的瓶颈。
- **案例/数据**
  - 电商用户/商品/订单分三库 → 结论：业务分库是最自然的分散维度，但立刻带来 join、事务、成本三笔账。
  - 「查询购买化妆品的女性用户」→ 结论：join 变成两次查询 + 应用层过滤。
  - 下单扣库存 → 结论：分库后事务要靠业务补偿，且「业务程序自身异常」这类情况无法自动恢复，只能人工修数据。
  - 婚恋网站把 nickname/description 垂直拆出 → 结论：垂直分表用「查询频率」换「单行宽度」，代价是查询次数翻倍。
  - 淘宝几亿用户数据不可能放一张表 → 结论：单表容量与性能是水平分表的直接动因。
  - 配置路由的「死循环」→ 结论：任何路由方案都会把问题推到下一层，没有免费的路由。
- **反例与坑**
  - 初创业务一上来就业务分库（拖慢节奏、增加成本、join 与事务丢失）。
  - 认为「反正以后要分，不如现在分」——忽略成功率与资源约束。
  - 误以为单表切成多表就必须分散到不同数据库（不必要，反而引入分库复杂性）。
  - Hash 路由分表后随意增加表数量（全量数据重分布）。
  - 用 count() 相加做高频分页统计。
  - 记录数表与子表操作不同步（数据不一致、无法同事务）。
  - 把分库分表当成读写分离的同类替代（前者才解决存储）。
- **原文金句**
  - 「分表能够有效地分散存储压力和带来性能提升，但和分库一样，也会引入各种复杂性。」
  - 「但不管怎样，当看到表的数据量达到千万级别时，作为架构师就要警觉起来，因为这很可能是架构的性能瓶颈或者隐患。」
  - 「做 10 个业务有 1 个业务能活下去就很不错了，更何况快速发展，和中彩票的概率差不多。」
  - 「如果我们每个业务上来就按照淘宝、微信的规模去做架构设计，不但会累死自己，还会害死业务。」
- **可迁移到知识库的主题**
  - `业务分库`、`垂直分表/水平分表`、`范围路由/Hash路由/配置路由`、`count与order by跨表`、`单表容量阈值`

## 16 | 高性能 NoSQL

### 16 | 高性能 NoSQL
- **核心结论**
  - 关系数据库并不完美，四个缺点分别催生四类 NoSQL 方案；NoSQL 的优势本质上是**牺牲 ACID 中的某个或某几个特性**。
  - 不能盲目迷信 NoSQL 是银弹，应把 NoSQL 作为 SQL 的有力补充：**NoSQL != No SQL，而是 NoSQL = Not Only SQL**。
- **完整判据/清单/步骤**
  - **关系数据库的四个缺点 → 四类 NoSQL 的对应关系（总表）**

    | 关系数据库缺点 | 具体表现 | 对应 NoSQL 类别 | 代表产品 |
    |---|---|---|---|
    | 存储的是行记录，无法存储数据结构 | 「我关注的人」是用户 ID 列表，只能拆成多行再查询组装，无法直接存一个列表 | K-V 存储 | Redis |
    | schema 扩展很不方便 | 表结构强约束、操作不存在的列会报错；扩列要执行 DDL（CREATE/ALTER/DROP），且可能长时间锁表 | 文档数据库 | MongoDB |
    | 大数据场景下 I/O 较高 | 统计类运算即使只针对某一列，也会把整行数据从存储读入内存 | 列式数据库 | HBase |
    | 全文搜索功能比较弱 | 只能用 like 整表扫描匹配，性能非常低 | 全文搜索引擎 | Elasticsearch |
  - **一、K-V 存储（Redis）**
    - 定义：Key 是数据标识（与关系库主键含义一样），Value 是具体数据。
    - Redis 特征：开源（BSD 许可）的高性能 K-V 缓存和存储系统；Value 是具体的数据结构——**string、hash、list、set、sorted set、bitmap、hyperloglog**（7 种），因此常被称为「数据结构服务器」。
    - 以 List 为例的典型操作（原文列举 4 个）：`LPOP key` 从队列左边出队一个元素；`LINDEX key index` 通过索引获取一个元素；`LLEN key` 获得 List 长度；`RPOP key` 从队列右边出队一个元素。
    - 对照：用关系数据库实现 `LPOP` 需要——① 每条数据除行 ID 还要有位置编号（不能用行 ID 当位置编号，因为会往列表头部插入数据）；② 查询出第一条数据；③ 删除第一条数据；④ 更新从第二条开始的所有数据的位置编号。→ 实现麻烦、多次 SQL、性能很低。
    - 缺点：**不支持完整的 ACID 事务**——Redis 虽提供事务，但只能保证隔离性和一致性（I 和 C），**无法保证原子性和持久性（A 和 D）**。
    - 判据：大部分业务并不需要严格 ACID（例：没把 A 加进 B 的粉丝列表，业务影响非常小）→ 应根据业务特性和要求决定是否用 Redis，不能因为它不遵循 ACID 就直接放弃。
  - **二、文档数据库（MongoDB）**
    - 定义：最大特点是 **no-schema**，可存储和读取任意数据；绝大部分文档数据库存储格式是 JSON（或 BSON），因为 JSON 自描述、无须使用前定义字段，读取不存在的字段也不会像 SQL 那样报语法错误。
    - 三个优势：① **新增字段简单**——无须 DDL，程序代码直接读写即可；② **历史数据不会出错**——即使没有新增字段也只返回空值，代码做兼容处理即可；③ **很容易存储复杂数据**——JSON 能描述复杂结构。
    - 复杂数据示例：用户管理系统的 ID、姓名、性别、爱好（列表）、邮箱、地址（省市区+楼盘）、学历（多条：学校/专业/入学毕业年份）。关系库需要基本信息、爱好、地址、学历多张表；文档库一个 JSON 即可全部描述（原文给出含 `hobbies` 数组、`address` 对象、`education` 对象数组的 JSON 样例）。
    - 适用场景：特别适合**电商和游戏**——不同商品属性差异很大（冰箱 vs 笔记本电脑），即使是同类商品也有不同属性（LCD 与 LED 显示器参数指标不同）；用关系库很麻烦，用文档库简单方便、扩展新属性更容易。
    - 代价一：**不支持事务**。例：用 MongoDB 存商品库存，下单需先扣库存再创建订单（事务操作）；关系库实现简单，MongoDB 无法做到事务性，异常时可能库存被扣减但订单没创建 → 对事务要求严格的场景不能用文档数据库。
    - 代价二：**无法实现关系数据库的 join 操作**。例：查「购买了苹果笔记本用户中的女性用户」，关系库一个 join 搞定；文档库要查两次（先查订单表中购买苹果笔记本的用户，再查这些用户哪些是女性）。
  - **三、列式数据库（HBase）**
    - 定义：按列存储数据的数据库；对应传统关系数据库被称为「行式数据库」（按行存储）。
    - 行式存储的两个优势（也是列式的劣势来源）：① 业务同时读取多个列时效率高——列按行存在一起，一次磁盘操作就能把一行中各列读入内存；② 能一次性完成一行中多个列的写操作，保证行写操作的原子性和一致性；否则列存储可能出现某次写操作有的列成功有的列失败，导致数据不一致。
    - 列式优势的典型场景：**海量数据统计**。例：计算某城市体重超重人员数据，实际只需读「体重」一列；行式存储即使只用一列也会读出整行——单行用户信息 1KB、体重只占 4 字节，行式仍读整行 1KB 是明显浪费；列式每个用户只读 4 字节，I/O 大大减少。
    - 列式第二个优势：**更高压缩比**——行式一般 3:1 到 5:1，列式一般 8:1 到 30:1，因为单个列的数据相似度比行更高。
    - 列式的劣势（场景反转即优势变劣势）：① 需要**频繁更新多个列**时——列式不同列存在磁盘不连续空间，更新多列是随机写；行式同一行多列连续，一次磁盘写完成，列式随机写效率远低于行式；② 高压缩率在更新场景成为劣势——更新要解压、改、再压缩、写盘。
    - 适用判据：一般用于**离线的大数据分析和统计**场景——主要针对部分列/单列操作，且数据写入后无须再更新删除。
  - **四、全文搜索引擎（Elasticsearch）**
    - 为什么索引无能为力（两条判据）：① 全文搜索条件可随意排列组合，用索引满足则索引数量会非常多；② 模糊匹配索引无法满足，只能用 like 整表扫描，效率非常低。
    - 举例（婚恋网站「程序员发布信息、用户来搜索程序员」）：美女1「性别 + PHP + 上海」（PHP 要模糊匹配「语言」列、上海查「地点」列，用索引需建「地点」索引）；美女2「性别 + 鹅厂 + 旅游」（旅游模糊匹配「爱好」列、鹅厂查「单位」列，需建「单位」索引）；美女3「性别 + 猫厂 + 北京 + Java + 技术专家」（猫厂+北京可走索引，Java、技术专家只能模糊匹配）；帅哥4「性别 + 美丽 + 美女」（只能模糊匹配「自我介绍」列）→ 搜索条件无法列举完全、排列组合非常多 → 关系数据库不足。
    - 基本原理：**倒排索引**（Inverted index），也称反向索引、置入档案或反向档案——建立**单词到文档**的索引；与之相对的是**正排索引**——建立**文档到单词**的索引。
      - 正排索引适用于根据文档名称查文档内容（例：点开「面向对象葵花宝典是什么」按标题查内容）。
      - 倒排索引适用于根据关键词查文档内容（例：想看「设计」相关文章，把所有包含「设计」的文章搜出来）。
    - 使用方式：全文搜索引擎的索引对象是**单词和文档**，关系数据库的索引对象是**键和行**，术语差异大、不能简单等同；要让全文搜索引擎支持关系型数据的全文搜索，需做转换——目前常用做法是把关系型数据按对象形式转换为 **JSON 文档**，再输入全文搜索引擎建索引。例：把程序员信息表转成 3 个 JSON 文档（含 id、姓名、性别、地点、单位、爱好、语言、自我介绍）。
    - ES 索引基本原理（原文引用官方文档）：ES 是分布式文档存储，能存储和检索复杂数据结构（序列化为 JSON 文档）并以实时方式提供；每个字段的所有数据默认都被索引，即每个字段都有为快速检索设置的专用倒排索引；并且能在相同查询中使用所有倒排索引、以惊人速度返回结果。
- **数字与阈值**
  - **7 种**：Redis Value 的数据结构（string、hash、list、set、sorted set、bitmap、hyperloglog）——用途：说明 K-V 的「值」并非只能是字符串。
  - **MySQL 可能锁表 1 小时**：DDL 修改 schema 的极端锁表时长——用途：量化 schema 强约束的代价。
  - **1KB / 4 字节**：单行用户信息大小 / 体重列大小——用途：量化行式存储的 I/O 浪费（250 倍冗余）。
  - **3:1 ~ 5:1**：行式数据库一般压缩率——用途：与列式对比。
  - **8:1 ~ 30:1**：列式数据库一般压缩率——用途：说明列式省存储的空间收益。
  - **4 类 / 7 种结构 / 4 个 List 操作**：NoSQL 分类数、Redis 结构数、原文列举的 List 命令数——用途：界定本篇覆盖面。
- **案例/数据**
  - 微博关注关系（用户 ID 列表）→ 结论：关系库无法直接存列表，K-V/数据结构服务器更自然。
  - 电商商品属性差异（冰箱 vs 笔记本、LCD vs LED）→ 结论：no-schema 在属性差异大的品类上收益最大。
  - MongoDB 扣库存 + 建订单 → 结论：文档库缺事务，强事务场景不可用。
  - 「购买苹果笔记本的女性用户」→ 结论：文档库无 join，需两次查询 + 应用层拼装。
  - 体重统计 → 结论：列式在「只读少数列 + 大批量」场景碾压行式。
  - 婚恋网站四个搜索请求 → 结论：全文搜索的条件组合爆炸使索引方案不可行，必须倒排索引。
- **反例与坑**
  - 把 NoSQL 当银弹、认为 NoSQL = No SQL、架构设计无需关系数据库。
  - 用关系库模拟 List（位置编号 + 查 + 删 + 批量更新位置）——多次 SQL、性能低。
  - 在需要严格事务的场景用 MongoDB（扣库存与建订单不一致）。
  - 用列式库做频繁多列更新（随机写 + 解压/压缩开销）。
  - 试图用索引解决全文搜索（索引数量爆炸 + like 全表扫描）。
  - 直接把关系库的「键和行」概念套到全文搜索引擎（术语与模型不同，必须先转 JSON 文档）。
- **原文金句**
  - 「世上没有免费的午餐，NoSQL 方案带来的优势，本质上是牺牲 ACID 中的某个或者某几个特性，因此我们不能盲目地迷信 NoSQL 是银弹，而应该将 NoSQL 作为 SQL 的一个有力补充，NoSQL != No SQL，而是 NoSQL = Not Only SQL。」
  - 「Redis 的事务只能保证隔离性和一致性（I 和 C），无法保证原子性和持久性（A 和 D）。」
  - 「全文搜索引擎的索引对象是单词和文档，而关系数据库的索引对象是键和行，两者的术语差异很大，不能简单地等同起来。」
  - 「基于上述列式存储的优缺点，一般将列式存储应用在离线的大数据分析和统计场景中，因为这种场景主要是针对部分列单列进行操作，且数据写入后就无须再更新删除。」
- **可迁移到知识库的主题**
  - `NoSQL四分类`、`no-schema`、`倒排索引vs正排索引`、`列式压缩比`、`ACID取舍`

## 17 | 高性能缓存架构

### 17 | 高性能缓存架构
- **核心结论**
  - 缓存的基本原理：**将可能重复使用的数据放到内存中，一次生成、多次使用，避免每次使用都去访问存储系统**；用于弥补存储系统在特定业务场景下的不足。
  - 缓存能大幅提升性能（Memcache 单台简单 K-V 查询 TPS 50000 以上），但同时给架构引入更多复杂性；若不针对这些复杂性处理，某些场景下甚至会导致整个系统崩溃。
  - 原文口径：本讲覆盖的是**三类缓存问题（穿透、雪崩、热点）+ 两种实现方式（程序代码中间层、独立中间件）**，原文未出现「5 种缓存方式」的枚举，以下按原文如实记录。
- **完整判据/清单/步骤**
  - **需要缓存的典型场景（两条判据）**
    1. **需要经过复杂运算后得出的数据，存储系统无能为力**：例论坛首页展示当前多少用户同时在线，用 MySQL 存用户状态则每次获取总数都要 count(*) 大量数据，无论怎么优化性能都不会太高；要实时展示，MySQL 无法支撑。
    2. **读多写少的数据，存储系统有心无力**：绝大部分在线业务读多写少，微博/淘宝/微信读业务占整体业务量 90% 以上；例明星发一条微博几千万人浏览，MySQL 写入只有一条 insert，但每次浏览都要 select 一次，几千万条 select 压力非常大。
  - **一、缓存穿透 —— 两种情形与各自解法**
    - 定义：缓存没有发挥作用——业务系统去缓存查数据但缓存中没有，于是需要再次去存储系统查询。
    - 情形 1 **存储数据不存在**：存储中没有某数据就不会在缓存中存，导致每次查询都穿透到存储返回「不存在」。通常读取不存在数据的请求量不大，但异常情况（如被黑客攻击、故意大量访问读取不存在数据的业务）可能把存储系统拖垮。→ 解法：查询存储系统没找到时，**直接设置一个默认值（空值或具体值）存到缓存**，第二次读缓存就取到默认值、不再访问存储。
    - 情形 2 **缓存数据生成耗费大量时间或资源**：存储中存在数据，但生成缓存需较长时间或大量资源；若恰在业务访问时缓存失效，访问压力全部集中到存储系统。典型是电商商品分页：数据巨大不能全缓存，只能按分页缓存；难以预测用户访问哪些分页，最简单是每次点分页时按分页计算生成缓存。正常情况下基本满足要求，但被竞争对手用爬虫遍历时性能出问题。具体链条：分页缓存有效期设为 1 天（太长则不能反映真实数据）→ 通常用户不会从第 1 页看到最后 1 页，访问集中在前 10 页，第 10 页以后缓存过期失效可能性很大 → 竞争对手每周来爬取，爬虫遍历所有分类所有数据、从第 1 页读到最后一页，很多分页缓存可能都失效 → 大量分页没有缓存，从数据库生成缓存又非常耗性能（order by limit），爬虫把整个数据库拖慢。
    - 情形 2 的应对：**没有太好的解决方案**（爬虫会遍历所有数据、来爬时间不确定，不可能为应对爬虫把所有数据永久缓存）。通常方案：要么识别爬虫然后禁止访问（但可能影响 SEO 和推广）；要么做好监控、发现问题后及时处理（爬虫不是攻击、不会暴力破坏，影响是逐步的，监控发现后有时间处理）。
  - **二、缓存雪崩 —— 定义与两种解法**
    - 定义：缓存失效（过期）后引起系统性能急剧下降。缓存过期被清除后业务系统需重新生成缓存，要再次访问存储、再次运算，耗时几十毫秒甚至上百毫秒；高并发系统几百毫秒内可能接到几百上千个请求，旧缓存已清除、新缓存未生成，且处理请求的线程都不知道另有线程正在生成缓存 → 所有请求都去重新生成缓存、都去访问存储 → 对存储造成巨大压力 → 拖慢整个系统，严重时数据库宕机、形成连锁反应导致整个系统崩溃。
    - 解法 1 **更新锁**：对缓存更新操作加锁，保证只有一个线程能更新缓存；未获取更新锁的线程要么等锁释放后重新读缓存，要么返回空值或默认值。注意分布式集群场景：几十上百台服务器，即使单台只有一个线程更新，合起来也有几十上百个线程同时更新，同样存在雪崩 → 必须用**分布式锁**（如 ZooKeeper）。
    - 解法 2 **后台更新**：由后台线程更新缓存而非业务线程；缓存本身有效期设为**永久**，后台线程定时更新。需处理一个特殊场景：缓存系统内存不够时会「踢掉」一些缓存数据，从被踢到下次定时更新之间，业务线程读缓存返回空值、而业务线程本身又不会更新缓存 → 业务上表现为「数据丢了」。两种补救：
      1. 后台线程除定时更新外，还**频繁读取缓存**（如 1 秒或 100 毫秒一次），发现被踢就立刻更新。实现简单，但读取间隔不能设太长（否则这段时间业务访问拿不到真正数据、只有空缓存值，用户体验一般）。
      2. 业务线程发现缓存失效后，通过**消息队列**发消息通知后台线程更新；可能出现多个业务线程都发消息，但后台线程收到消息后、更新前可判断缓存是否存在，存在就不更新，因此无影响。依赖消息队列、复杂度高一些，但更新更及时、用户体验更好。
    - 判据：后台更新既适应单机多线程也适合分布式集群，相比更新锁要简单一些；还适合业务刚上线时的**缓存预热**（系统上线后将相关缓存数据直接加载到缓存系统，而不是等用户访问触发加载）。
  - **三、缓存热点 —— 解法与一个关键细节**
    - 定义：缓存系统本身性能虽高，但某些特别热点数据若大部分甚至所有业务请求都命中同一份缓存数据，该数据所在缓存服务器压力也很大。例：某明星微博发布「我们」宣告恋爱，短时间内上千万用户围观。
    - 解法：**复制多份缓存副本**，把请求分散到多个缓存服务器，减轻单台压力。例：微博对粉丝数超过 100 万的明星，每条微博生成 **100 份缓存**，数据一样，通过在缓存 key 里加上编号区分，每次读缓存随机读其中某份。
    - 关键细节：**不同缓存副本不要设置统一的过期时间**，否则会出现所有副本同时生成、同时失效，引发缓存雪崩效应；正确做法是设定一个过期时间范围，不同副本的过期时间是该范围内的**随机值**。
  - **实现方式（两种）**：由于缓存的各种访问策略与存储的访问策略相关，上述缓存设计方案通常**集成在存储访问方案中**——可采用「程序代码实现」的**中间层**方式，也可采用**独立的中间件**来实现。
- **数字与阈值**
  - **90% 以上**：在线业务中读业务占比——用途：论证读多写少的普遍性与缓存收益。
  - **TPS 50000 以上**：单台 Memcache 简单 key-value 查询能力——用途：量化缓存层能承接的读量级。
  - **几十毫秒甚至上百毫秒**：重新生成缓存的耗时——用途：解释雪崩窗口内请求堆积的原因。
  - **几百毫秒 / 几百上千个请求**：高并发系统的请求密度——用途：说明雪崩在毫秒级就会发生。
  - **1 天**：分页缓存的有效期示例——用途：平衡「反映真实数据」与「命中率」。
  - **前 10 页**：用户实际访问集中的分页范围——用途：解释第 10 页以后缓存必然过期。
  - **每周**：竞争对手爬虫的爬取频率示例——用途：说明缓存失效是被周期性触发的。
  - **100 万粉丝 / 100 份缓存**：触发缓存副本策略的明星粉丝门槛与副本数量——用途：量化热点分散的力度。
  - **1 秒 / 100 毫秒**：后台线程巡检缓存的间隔——用途：控制「被踢后空窗期」的长度。
- **案例/数据**
  - 论坛首页「同时在线人数」→ 结论：复杂运算（count(*)）类数据必须靠缓存，存储层优化无效。
  - 明星一条微博几千万浏览 → 结论：读多写少场景下缓存是唯一可行解。
  - 电商分页 + 爬虫遍历 → 结论：缓存穿透的第二种情形（生成代价高）没有根治方案，只能识别爬虫或加强监控。
  - 缓存被内存淘汰「踢掉」→ 结论：永久有效期 + 后台更新必须配巡检或消息通知，否则表现为「数据丢了」。
  - 明星「我们」微博 → 结论：热点数据要靠副本分散，副本过期时间要随机化。
- **反例与坑**
  - 缓存不命中就每次都查库返回「不存在」（穿透，且可被攻击放大）。
  - 把缓存有效期设成统一值（副本同时失效 → 雪崩）。
  - 单机更新锁就以为解决了集群雪崩（几十上百台机器 × 1 线程 = 几十上百并发更新）。
  - 后台更新时缓存设永久却不管「被踢」，业务读到空缓存。
  - 为应对爬虫把所有分页数据永久缓存（既不可行也没必要）。
  - 认为缓存只是「加个 Redis」，不设计穿透/雪崩/热点策略。
- **原文金句**
  - 「缓存就是为了弥补存储系统在这些复杂业务场景下的不足，其基本原理是将可能重复使用的数据放到内存中，一次生成、多次使用，避免每次使用都去访问存储系统。」
  - 「缓存虽然能够大大减轻存储系统的压力，但同时也给架构引入了更多复杂性。」
  - 「缓存副本设计有一个细节需要注意，就是不同的缓存副本不要设置统一的过期时间，否则就会出现所有缓存副本同时生成同时失效的情况，从而引发缓存雪崩效应。」
  - 「这些关键点本身在技术上都不复杂，但可能对业务产生很大的影响，轻则系统响应变慢，重则全站宕机，架构师在设计架构的时候要特别注意这些细节」
- **可迁移到知识库的主题**
  - `缓存穿透`、`缓存雪崩与更新锁`、`缓存热点与副本`、`缓存预热`、`分布式锁`

## 18 | 单服务器高性能模式：PPC 与 TPC

### 18 | 单服务器高性能模式：PPC 与 TPC
- **核心结论**
  - 高性能架构设计主要集中在两方面：**尽量提升单服务器性能、发挥到极致**；**单服务器撑不住时设计服务器集群方案**。最终能否高性能还与具体实现及编码相关，但「架构设计决定了系统性能的上限，实现细节决定了系统性能的下限」。
  - 单服务器高性能的关键之一是**并发模型**，两个关键设计点：**服务器如何管理连接**、**服务器如何处理请求**；两者最终都与操作系统的 **I/O 模型（阻塞、非阻塞、同步、异步）** 与 **进程模型（单进程、多进程、多线程）** 相关。
  - PPC（Process Per Connection）与 TPC（Thread Per Connection）是传统模型：实现简单，但都无法支撑高并发。
- **完整判据/清单/步骤**
  - **PPC —— 流程与三个弊端**
    - 定义：每次有新连接就新建一个进程专门处理该连接的请求，是传统 UNIX 网络服务器采用的模型。
    - 流程 4 步：① 父进程接受连接（accept）；② 父进程 fork 子进程；③ 子进程处理连接的读写请求（read、业务处理、write）；④ 子进程关闭连接（close）。
    - 细节：父进程 fork 后直接调用 close，并非真的关闭连接，只是把连接的文件描述符**引用计数减一**；真正的关闭发生在子进程也 close、引用计数变为 0 后，由操作系统关闭（参见《UNIX 网络编程：卷一》）。
    - 适用：实现简单，比较适合**连接数没那么多**的情况，例如数据库服务器；互联网兴起前普通业务服务器也运作得挺好，世界上第一个 web 服务器 **CERN httpd** 就采用该模式。
    - 弊端 1 **fork 代价高**：从操作系统角度创建进程代价很高，要分配很多内核资源、要把内存映像从父进程复制到子进程；即使有 Copy on Write（写时复制），创建进程代价仍然很大。
    - 弊端 2 **父子进程通信复杂**：fork 时文件描述符可通过内存映像复制传给子进程，但 fork 完成后父子进程通信麻烦，需采用 IPC 方案。例：子进程要在 close 前告诉父进程自己处理了多少个请求以支撑父进程做全局统计，就必须用 IPC 传递。
    - 弊端 3 **支持的并发连接数量有限**：若每个连接存活时间较长、新连接又源源不断，进程数量越来越多，操作系统进程调度和切换频率越来越高，系统压力越来越大 → 一般情况下 PPC 能处理的并发连接数量**最大也就几百**。
  - **prefork —— 预创建进程**
    - 动机：PPC 在连接进来时才 fork，fork 代价高导致用户访问感觉慢；prefork 提前创建进程（pre-fork），系统启动时预先创建好进程再开始接受用户请求，新连接进来时省去 fork 操作，让用户访问更快、体验更好。
    - 实现关键：多个子进程都 **accept 同一个 socket**，有新连接进入时操作系统保证只有一个进程能最后 accept 成功。
    - 副作用：**「惊群」现象**——虽然只有一个子进程 accept 成功，但所有阻塞在 accept 上的子进程都会被唤醒，导致不必要的进程调度和上下文切换；幸运的是操作系统可解决（例：Linux 2.6 版本后内核已解决 accept 惊群问题）。
    - 判据：prefork 与 PPC 一样仍存在父子进程通信复杂、并发连接数量有限的问题，因此目前实际应用也不多；Apache 服务器提供 MPM prefork 模式，推荐在需要可靠性或与旧软件兼容的站点采用，**默认最大支持 256 个并发连接**。
  - **TPC —— 流程、改进与新问题**
    - 定义：每次有新连接就新建一个线程专门处理该连接的请求。线程比进程轻量、创建消耗少得多；多线程共享进程内存空间、线程通信比进程通信简单。
    - 改进：TPC 实际解决或弱化了 PPC 的「fork 代价高」和「父子进程通信复杂」两个问题。
    - 流程 4 步：① 父进程 accept；② 父进程创建子线程（pthread）；③ 子线程处理连接读写请求；④ 子线程关闭连接。
    - 与 PPC 的差异细节：主进程**不用 close** 连接——因为子线程共享主进程的进程空间，连接的文件描述符没有被复制，只需一次 close。
    - 新问题 1：创建线程虽比创建进程代价低，但并非没有代价，高并发时（如每秒上万连接）仍有性能问题。
    - 新问题 2：无须进程间通信，但**线程间的互斥和共享又引入复杂度**，可能一不小心导致死锁。
    - 新问题 3：多线程会互相影响，某个线程异常可能导致整个进程退出（例如内存越界）。
    - 另加：仍存在 CPU 线程调度和切换代价。
    - 判据：TPC 本质上和 PPC 基本类似；**在并发几百连接的场景下，反而更多采用 PPC**——因为 PPC 没有死锁风险，也不会多进程互相影响，稳定性更高。
  - **prethread —— 预创建线程（两种实现）**
    - 动机：与 prefork 类似，预先创建线程后再接受请求，省去创建线程操作。
    - 由于多线程数据共享与通信更方便，prethread 的实现比 prefork 更灵活，常见两种：
      1. **主进程 accept，然后将连接交给某个线程处理**。
      2. **子线程都尝试去 accept，最终只有一个线程 accept 成功**。
    - 代表：Apache 的 **MPM worker** 模式本质上是一种 prethread 方案，但稍作改进——先创建多个进程，每个进程里再创建多个线程；主要考虑稳定性：即使某个子进程里的某个线程异常导致整个子进程退出，还有其他子进程继续提供服务，不会整个服务器挂掉。
    - 判据：prethread 理论上可比 prefork 支持更多并发连接；Apache MPM worker 模式**默认支持 16 × 25 = 400 个并发处理线程**。
- **数字与阈值**
  - **TPS 30000 → 8000**：一行不恰当的 debug 日志造成的能力下降——用途：量化「实现细节决定下限」。
  - **响应时间 2 毫秒 → 40 毫秒**：一个 `tcp_nodelay` 参数造成的延迟放大——用途：量化参数级影响。
  - **最大也就几百**：PPC 可处理的并发连接数量上限——用途：判定 PPC 不适用于互联网高并发。
  - **Linux 2.6**：内核解决 accept 惊群问题的版本——用途：说明 prefork 的惊群已被系统层修复。
  - **256**：Apache MPM prefork 默认最大并发连接数——用途：prefork 的容量基线。
  - **每秒上万连接**：TPC 仍会出性能问题的高并发量级——用途：界定 TPC 的适用边界。
  - **16 × 25 = 400**：Apache MPM worker 默认进程数 × 每进程线程数 = 并发处理线程数——用途：prethread 的容量基线。
- **案例/数据**
  - CERN httpd 采用 PPC → 结论：PPC 在低并发年代是合格方案，模式本身没有错，只是场景变了。
  - Apache prefork（默认 256）→ 结论：prefork 用在「要可靠性或兼容旧软件」的站点，而非高并发主战场。
  - Apache MPM worker（16 进程 × 25 线程）→ 结论：多进程 + 多线程的组合是为稳定性：线程崩溃只带走一个子进程。
  - 并发几百连接时更倾向 PPC → 结论：稳定性（无死锁、进程隔离）在低并发下比「轻量」更重要。
- **反例与坑**
  - 用 PPC 承载互联网级并发（fork 代价 + IPC + 进程数爆炸）。
  - 以为 prefork 就解决了 PPC 的全部问题（通信复杂与并发上限仍在）。
  - 以为 TPC 没有代价（创建线程有代价、互斥引入死锁、单线程异常可拖垮整个进程）。
  - 忽略 prethread 的惊群/锁竞争细节（第二种实现依赖 accept 竞争）。
  - 忽略一行日志、一个 `tcp_nodelay` 参数对性能的实质影响。
- **原文金句**
  - 「形象地说，架构设计决定了系统性能的上限，实现细节决定了系统性能的下限。」
  - 「因此，一般情况下，PPC 方案能处理的并发连接数量最大也就几百。」
  - 「TPC 实际上是解决或者弱化了 PPC fork 代价高的问题和父子进程通信复杂的问题。」
  - 「TPC 方案本质上和 PPC 方案基本类似，在并发几百连接的场景下，反而更多地是采用 PPC 的方案，因为 PPC 方案不会有死锁的风险，也不会多进程互相影响，稳定性更高。」
- **可迁移到知识库的主题**
  - `PPC/TPC`、`prefork/prethread`、`惊群问题`、`并发模型两要素`、`Apache MPM`

## 19 | 单服务器高性能模式：Reactor 与 Proactor

### 19 | 单服务器高性能模式：Reactor 与 Proactor
- **核心结论**
  - PPC 与 TPC 的优点是实现简单，缺点是**都无法支撑高并发场景**；互联网海量用户业务下完全无能为力，需要 Reactor / Proactor。
  - Reactor 的由来：**I/O 多路复用 + 线程池**，完美解决 PPC/TPC 的问题；Reactor 也叫 **Dispatcher 模式**——I/O 多路复用统一监听事件，收到事件后分配（Dispatch）给某个进程。
  - Reactor 是**非阻塞同步**网络模型（真正的 read 和 send 仍需用户进程同步操作）；Proactor 是**异步**网络模型（内核完成 I/O 后通知程序）。
- **完整判据/清单/步骤**
  - **演进逻辑（四步推导，每步解决上一阶段的问题）**
    1. PPC 的问题：每个连接都创建进程、连接结束进程销毁，是很大浪费 → 想法：**资源复用**，创建进程池，把连接分配给进程，一个进程处理多个连接的业务。
    2. 新问题：一个进程处理多个连接时，若沿用「read → 业务处理 → write」流程，当前连接没数据可读就**阻塞在 read** 上；此时其他连接有数据可读也处理不了 → 无法高性能。
    3. 最简单解法：把 read 改为**非阻塞**，进程不断轮询多个连接。问题：轮询消耗 CPU；一个进程处理几千上万连接时轮询效率很低。
    4. 正解：**只有当连接上有数据时进程才去处理** → **I/O 多路复用**。两个关键实现点：
       - 多条连接共用一个阻塞对象，进程只需在一个阻塞对象上等待，无须轮询所有连接；常见实现有 **select、epoll、kqueue**。
       - 某条连接有新数据可处理时，操作系统通知进程，进程从阻塞状态返回，开始业务处理。
  - **Reactor 的两个核心组成部分**：**Reactor**（负责监听和分配事件）+ **处理资源池**（进程池或线程池，负责处理事件）。
  - **Reactor 的三种典型实现（由两个可变因素组合而来）**
    - 两个可变因素：Reactor 的数量（一个或多个）；资源池的数量（单进程/多进程，线程类似）。
    - 理论上 2×2 = 4 种，但「多 Reactor 单进程」相比「单 Reactor 单进程」既复杂又没有性能优势，**只是理论方案、实际没有应用** → 最终三种：单 Reactor 单进程/线程、单 Reactor 多线程、多 Reactor 多进程/线程。
    - 进程还是线程的选择，更多与编程语言及平台相关：Java 一般用线程（如 Netty），C 语言进程和线程都可以（Nginx 用进程、Memcache 用线程）。
    - **方案 1：单 Reactor 单进程/线程** ——流程：① Reactor 对象通过 select 监控连接事件，收到事件后通过 dispatch 分发；② 若是连接建立事件，由 **Acceptor** 处理，Acceptor 通过 accept 接受连接并创建一个 **Handler** 处理该连接后续的各种事件；③ 若不是连接建立事件，Reactor 调用该连接对应的 Handler（第 2 步创建的）响应；④ Handler 完成 read → 业务处理 → send 的完整业务流程。
      - 优点：很简单，没有进程间通信、没有进程竞争，全部在同一进程内完成。
      - 缺点 1：只有一个进程，无法发挥多核 CPU 性能；只能部署多个系统来利用多核，但带来运维复杂度（本来维护一个系统，现在一台机器上维护多套）。
      - 缺点 2：Handler 在处理某个连接的业务时，整个进程无法处理其他连接的事件，很容易导致性能瓶颈。
      - 适用：实践中应用场景不多，**只适用于业务处理非常快速**的场景；代表：**Redis**。
      - 语言细节：C 语言编写的系统一般用单 Reactor 单进程（没必要在进程中再创建线程）；Java 编写的一般用单 Reactor 单线程（JVM 是一个进程，虚拟机中有很多线程，业务线程只是其中之一）。
    - **方案 2：单 Reactor 多线程** ——流程：① 主线程中 Reactor 通过 select 监控连接事件，收到后 dispatch 分发；② 连接建立事件由 Acceptor 处理并创建 Handler；③ 非连接建立事件由对应 Handler 响应；④ **Handler 只负责响应事件、不做业务处理**，read 到数据后发给 **Processor**；⑤ Processor 在**独立子线程**中完成真正的业务处理，再把结果发给主进程的 Handler；Handler 收到响应后通过 send 返回 client。
      - 优点：能充分利用多核多 CPU 处理能力。
      - 问题 1：多线程数据共享和访问较复杂——子线程完成业务处理后要把结果传给主线程的 Reactor 发送，涉及共享数据互斥与保护；以 Java NIO 为例，Selector 是线程安全的，但 `Selector.selectKeys()` 返回的键集合是**非线程安全**的，对 selected keys 的处理必须单线程处理或采取同步措施保护。
      - 问题 2：Reactor 承担所有事件监听和响应、只在主线程运行，**瞬间高并发时会成为性能瓶颈**。
      - 为什么没有「单 Reactor 多进程」：多进程时子进程完成业务后要把结果返回父进程并通知父进程发给哪个 client，很麻烦——父进程只通过 Reactor 监听连接事件然后分配，子进程与父进程通信并不是一个连接；若要模拟成连接加入 Reactor 监听则很复杂。而多线程共享数据、线程间通信非常方便，虽要额外考虑同步，但复杂度比进程间通信低很多。
    - **方案 3：多 Reactor 多进程/线程** ——流程：① 父进程中 **mainReactor** 通过 select 监控**连接建立事件**，收到后通过 Acceptor 接收，将新连接分配给某个子进程；② 子进程的 **subReactor** 将 mainReactor 分配的连接加入连接队列监听，并创建一个 Handler 处理该连接的各种事件；③ 有新事件时 subReactor 调用对应 Handler 响应；④ Handler 完成 read → 业务处理 → send 完整流程。
      - 反直觉判据：方案看起来比单 Reactor 多线程复杂，但**实际实现时反而更加简单**——原因：① 父进程与子进程职责非常明确（父只负责接收新连接、子负责后续业务处理）；② 交互简单（父只需把新连接传给子进程，子进程无须返回数据）；③ 子进程之间互相独立，无须同步共享（仅限于网络模型相关的 select、read、send 无须同步共享，「业务处理」仍可能需要同步共享）。
      - 代表：**Nginx 用多 Reactor 多进程**；**Memcache 和 Netty 用多 Reactor 多线程**。
      - Nginx 的差异（重要细节）：标准多 Reactor 多进程由主进程的 mainReactor accept；而 Nginx **主进程仅创建监听端口、并不创建 mainReactor 来 accept**，而是由**子进程的 Reactor 来 accept**，通过**锁**控制一次只有一个子进程 accept；子进程 accept 新连接后就放到自己的 Reactor 处理，不再分配给其他子进程。
  - **Proactor —— 异步模型**
    - 动机：Reactor 是非阻塞**同步**网络模型，因为真正的 read 和 send 都需要用户进程同步操作（「同步」指用户进程执行 read/send 这类 I/O 操作时是同步的）；把 I/O 改为异步可进一步提升性能。
    - 命名：Proactor 直译「前摄器」难理解，类似词 proactive 意为「主动的」，译作「主动器」更好理解。
    - 心智模型对比：**Reactor = 「来了事件我通知你，你来处理」；Proactor = 「来了事件我来处理，处理完了我通知你」**。这里的「我」是操作系统内核，「事件」是新连接/有数据可读/有数据可写等 I/O 事件，「你」是程序代码。
    - 流程 5 步：① **Proactor Initiator** 创建 Proactor 和 Handler，并将两者通过 **Asynchronous Operation Processor** 注册到内核；② Asynchronous Operation Processor 处理注册请求并完成 I/O 操作；③ Asynchronous Operation Processor 完成 I/O 后通知 Proactor；④ Proactor 根据不同事件类型回调不同 Handler 进行业务处理；⑤ Handler 完成业务处理（Handler 也可以注册新的 Handler 到内核进程）。
    - 现实判据：理论上 Proactor 比 Reactor 效率高一些（异步 I/O 能充分利用 DMA 特性、让 I/O 与计算重叠），但实现真正的异步 I/O 操作系统需要做大量工作：**Windows 通过 IOCP 实现了真正的异步 I/O**，**Linux 下 AIO 并不完善**，因此 Linux 下高并发网络编程都以 **Reactor 模式为主**；即使 **Boost.Asio** 号称实现 Proactor，其实 Windows 下用 IOCP，**Linux 下是用 Reactor 模式（epoll）模拟出来的异步模型**。
- **数字与阈值**
  - **4 种 → 3 种**：Reactor 理论组合数与实际可用方案数（「多 Reactor 单进程」被排除）——用途：说明模式变体的取舍依据是「是否带来性能优势」。
  - **几千上万连接**：单进程轮询多个连接时效率很低的连接量级——用途：判定「非阻塞 + 轮询」不可行。
  - **Linux 2.6 / select、epoll、kqueue**：I/O 多路复用的内核实现与代表 API——用途：Reactor 的底层依赖清单。
  - **1 个进程 vs 多核 CPU**：单 Reactor 单进程无法利用多核——用途：单进程方案的核心容量限制。
- **案例/数据**
  - Redis 用单 Reactor 单进程 → 结论：业务处理极快时，单进程事件循环足够（无 IPC、无竞争）。
  - Netty 用多 Reactor 多线程、Memcache 用多 Reactor 多线程 → 结论：Java/线程栈生态下主流选择。
  - Nginx 用多 Reactor 多进程 + 子进程加锁 accept → 结论：模式落地会有工程化变体，不能照抄示意图。
  - Java NIO 的 `Selector.selectKeys()` 非线程安全 → 结论：单 Reactor 多线程的共享数据同步是真实成本。
  - Boost.Asio 在 Linux 用 epoll 模拟异步 → 结论：「宣称 Proactor」不等于「内核级异步 I/O」。
- **反例与坑**
  - 用阻塞 read + 进程池处理多连接（一个连接阻塞拖死整个进程）。
  - 用「非阻塞 + 轮询」代替 I/O 多路复用（CPU 空转、上万连接效率极低）。
  - 采用「多 Reactor 单进程」（更复杂且无性能收益，理论方案）。
  - 单 Reactor 多线程下让 Reactor 承担全部监听与响应（瞬间高并发成瓶颈）。
  - 在 Linux 上追求「真正的 Proactor」（AIO 不完善，实际仍是 Reactor/epoll 模拟）。
  - 把 Reactor 当异步模型（它是非阻塞同步）。
- **原文金句**
  - 「I/O 多路复用结合线程池，完美地解决了 PPC 和 TPC 的问题，而且“大神们”给它取了一个很牛的名字：Reactor，中文是“反应堆”。」
  - 「Reactor 可以理解为“来了事件我通知你，你来处理”，而 Proactor 可以理解为“来了事件我来处理，处理完了我通知你”。」
  - 「多 Reactor 多进程 / 线程的方案看起来比单 Reactor 多线程要复杂，但实际实现时反而更加简单」
  - 「Reactor 是非阻塞同步网络模型，因为真正的 read 和 send 操作都需要用户进程同步操作。」

## 20 | 高性能负载均衡：分类及架构

### 20 | 高性能负载均衡：分类及架构
- **核心结论**
  - 单服务器无论怎么优化都有性能天花板，撑不住时要设计高性能集群；高性能集群的本质是**通过增加更多服务器提升整体计算能力**。
  - 计算的特点（同样输入数据和逻辑在哪台服务器执行都得到相同输出）决定了：**高性能集群的复杂度主要体现在任务分配**——需要增加一个**任务分配器**（现在更流行的叫法是**负载均衡器**），并为任务选择合适的**任务分配算法**。
  - 「负载均衡」这个名称有误导性：任务分配并不只考虑计算单元负载均衡，不同算法目标不同——有的基于负载，有的基于性能（吞吐量、响应时间），有的基于业务。记住：**负载均衡不只是为了计算单元的负载达到均衡状态**。
- **完整判据/清单/步骤**
  - **三种负载均衡分类（原理 / 优点 / 缺点）**
    1. **DNS 负载均衡**
       - 原理：DNS 解析同一个域名可以返回不同的 IP 地址；一般用来实现**地理级别**的均衡（北方用户访问北京机房、南方用户访问深圳机房）。例：同样 `www.baidu.com`，北方用户解析到 61.135.165.224（北京机房），南方用户解析到 14.215.177.38（深圳机房）。
       - 优点：① 简单、成本低——负载均衡工作交给 DNS 服务器，无须自己开发或维护设备；② 就近访问、提升访问速度——可按请求来源 IP 解析成距离用户最近的服务器地址。
       - 缺点：① **更新不及时**——DNS 缓存时间较长，修改配置后很多用户仍访问旧 IP，访问失败、既达不到负载均衡也影响正常使用；② **扩展性差**——控制权在域名商，无法按业务特点做更多定制化功能和扩展特性；③ **分配策略比较简单**——支持的算法少；不能区分服务器差异（不能根据系统与服务状态判断负载）；无法感知后端服务器状态。
       - 变体：对时延和故障敏感的业务，有的公司自己实现 **HTTP-DNS**（用 HTTP 协议实现私有 DNS 系统），优缺点与通用 DNS 正好相反。
    2. **硬件负载均衡**
       - 原理：通过单独的硬件设备实现，这类设备与路由器、交换机类似，可理解为用于负载均衡的基础网络设备；典型设备 **F5** 和 **A10**。
       - 优点：① 功能强大——全面支持各层级负载均衡、全面算法、支持全局负载均衡；② 性能强大——软件负载均衡支持到 10 万级并发已经很厉害，硬件可支持 **100 万以上**并发；③ 稳定性高——商用设备经过严格测试与大规模使用；④ 支持安全防护——还具备防火墙、防 DDoS 攻击等功能。
       - 缺点：① **价格昂贵**（最普通的一台 F5 就是一台「马 6」，好一点的就是「Q7」）；② **扩展能力差**——可按业务配置，但无法扩展和定制。
    3. **软件负载均衡**
       - 原理：通过负载均衡软件实现，常见 **Nginx** 与 **LVS**：Nginx 是软件的 **7 层**负载均衡，LVS 是 Linux 内核的 **4 层**负载均衡。
       - 4 层与 7 层的区别：在于协议和灵活性——Nginx 支持 HTTP、E-mail 协议；LVS 是 4 层、和协议无关，几乎所有应用都可以做（聊天、数据库等）。
       - 性能量级：Nginx 万级（普通 Linux 服务器上装一个 Nginx 大概 5 万/秒）；LVS 十万级（据说可达 80 万/秒）；F5 百万级（200 万/秒到 800 万/秒都有，数据来源网络、仅供参考，需按实际业务场景做性能测试）。
       - 优点：① 简单——部署和维护都比较简单；② 便宜——买台 Linux 服务器装上软件即可（普通 Linux 服务器批发价约 1 万元，相比 F5 是「自行车和宝马的区别」）；③ 灵活——4 层/7 层可按业务选择，也可方便扩展（如通过 Nginx 插件实现定制化功能）。
       - 缺点（都是与硬件相比，并非不能用）：① 性能一般——一个 Nginx 大约能支撑 5 万并发；② 功能没有硬件那么强大；③ 一般不具备防火墙和防 DDoS 等安全功能。
  - **负载均衡典型架构（三级组合）**
    - 组合基本原则：**DNS 负载均衡用于实现地理级别的负载均衡；硬件负载均衡用于实现集群级别的负载均衡；软件负载均衡用于实现机器级别的负载均衡。**
    - 三层示例（假想 `www.xxx.com` 部署在北京、广州、上海三机房）：
      1. **地理级别**：用户访问时 DNS 按地理位置决定返回哪个机房 IP（图中返回广州机房 IP）。
      2. **集群级别**：广州机房用 F5，F5 收到请求后做集群级均衡，把请求发给 3 个本地集群之一（假设发给「广州集群 2」）。
      3. **机器级别**：广州集群 2 用 Nginx，Nginx 把请求发给集群内某台服务器，服务器处理并返回响应。
    - 适用范围判据：这个三层架构一般只在**大型业务场景**才这样用；业务量没那么大没必要严格照搬——例：一个大学的论坛完全不需要 DNS 负载均衡、也不需要 F5，只用 Nginx 做简单负载均衡就足够。
- **数字与阈值**
  - **61.135.165.224 / 14.215.177.38**：百度北京机房与深圳机房的 IP，用途：DNS 按地域返回不同 IP 的具体示例。
  - **10 万级并发**：软件负载均衡「已经很厉害」的量级，用途：软硬件能力分界的概念线。
  - **100 万以上并发**：硬件负载均衡可支持的并发量级，用途：硬件方案的能力上限描述。
  - **5 万/秒**：一台 Nginx 的大致处理能力（万级），用途：软件负载均衡的容量基线。
  - **80 万/秒**：LVS 据说可达的处理能力（十万级），用途：4 层软件负载均衡的容量基线。
  - **200 万 ~ 800 万/秒**：F5 的性能区间（百万级，来源网络、仅供参考、需实测），用途：硬件方案的能力上限。
  - **1 万元**：普通 Linux 服务器批发价，用途：与 F5 做性价比对比（自行车 vs 宝马）。
  - **3 个机房 / 3 个本地集群**：典型架构示例中的层级数量，用途：说明三级均衡的嵌套关系。
- **案例/数据**
  - 百度同一域名按地域解析到不同机房 IP → 结论：DNS 是地理级均衡最省事的手段。
  - HTTP-DNS 自研 → 结论：DNS 的缺点（更新不及时、不可控）可以被私有协议方案反转，代价是自建。
  - F5/A10 的「马 6 / Q7」比喻 → 结论：硬件方案的性价比只在大流量下成立。
  - Nginx 5 万/秒 vs LVS 80 万/秒 vs F5 200–800 万/秒 → 结论：4 层 > 7 层、硬件 > 软件的容量阶梯。
  - 大学论坛只需 Nginx → 结论：三级架构是「大型业务」的解法，不是通用标配。
- **反例与坑**
  - 把「负载均衡」理解成「让各服务器负载相等」（目标可能是性能、业务粘性等）。
  - 用 DNS 做细粒度、需要快速生效的均衡（缓存导致更新不及时、无法感知后端状态）。
  - 小业务上 F5（负担不起且浪费）。
  - 以为软件负载均衡能顶替硬件（性能、功能、安全防护三方面都不足）。
  - 业务量不大却照搬「DNS + F5 + Nginx」三层架构。
- **原文金句**
  - 「考虑到“负载均衡”已经成为了事实上的标准术语，这里我也用“负载均衡”来代替“任务分配”，但请你时刻记住，负载均衡不只是为了计算单元的负载达到均衡状态。」
  - 「DNS 负载均衡用于实现地理级别的负载均衡；硬件负载均衡用于实现集群级别的负载均衡；软件负载均衡用于实现机器级别的负载均衡。」
  - 「4 层和 7 层的区别就在于协议和灵活性」
  - 「需要注意的是，上图只是一个示例，一般在大型业务场景下才会这样用，如果业务量没这么大，则没有必要严格照搬这套架构。」

## 21 | 高性能负载均衡：算法

### 21 | 高性能负载均衡：算法
- **核心结论**
  - 负载均衡算法数量较多、还可按业务特性定制，抛开细节差异、按**算法期望达到的目的**可分为 4 大类：**任务平分类、负载均衡类、性能最优类、Hash 类**。
  - 具体算法（本篇详述 6 种）：**轮询、加权轮询、负载最低优先、性能最优（响应时间优先）、源地址 Hash、ID Hash**。
  - 总规律：越「聪明」的算法（感知服务器状态/响应时间）效果越好，但复杂度与代价急剧上升，实际应用反而没有轮询（含加权轮询）多。
- **完整判据/清单/步骤**
  - **四大类定义（判据清单）**
    1. **任务平分类**：把收到的任务平均分配给服务器处理；「平均」可以是绝对数量的平均，也可以是比例或权重上的平均。
    2. **负载均衡类**：根据服务器负载分配；这里的负载不一定是通常说的「CPU 负载」，而是系统当前的压力——可用 CPU 负载衡量，也可用连接数、I/O 使用率、网卡吞吐量等衡量。
    3. **性能最优类**：根据服务器响应时间分配，优先把新任务分配给响应最快的服务器。
    4. **Hash 类**：根据任务中某些关键信息做 Hash 运算，把相同 Hash 值的请求分到同一台服务器；常见有源地址 Hash、目标地址 Hash、session id hash、用户 ID Hash 等。
  - **算法 1：轮询**
    - 做法：收到请求后按顺序轮流分配到服务器上。
    - 优点/缺点同源：最简单，无须关注服务器本身状态。例：某服务器因程序 bug 进入死循环导致 CPU 负载很高，负载均衡系统不感知、仍继续发请求；集群中新机器 32 核、老机器 16 核，也不关注，新老机器分配任务数一样。
    - 边界（重要区分）：**「无须关注服务器本身状态」的关键词是「本身」**——只要服务器在运行，运行状态不关注；但服务器直接宕机、或与负载均衡系统断连，负载均衡系统**能够感知**并需要处理（例如把服务器从可分配列表删除，否则服务器都宕机了任务还不断分配给它，明显不合理）。
    - 判据：**「简单」是轮询算法的优点，也是它的缺点。**
  - **算法 2：加权轮询**
    - 做法：根据服务器权重分配任务；权重一般是根据硬件配置**静态配置**的（动态计算更契合业务但复杂度更高）。
    - 目的：解决不同服务器处理能力有差异的问题。例：新机器 32 核、老机器 16 核，理论上可假设新机器处理能力是老机器 2 倍，按 2:1 分配更多任务给新机器，充分利用新机器性能。
    - 局限：解决了「配置差异」问题，但仍**无法根据服务器的状态差异**分配任务。
  - **算法 3：负载最低优先**
    - 做法：把任务分配给当前负载最低的服务器；负载指标随任务类型和业务场景不同：
      - LVS 这种 4 层网络负载均衡设备，可用**连接数**判断服务器状态（连接数越大压力越大）。
      - Nginx 这种 7 层负载系统，可用 **HTTP 请求数**判断服务器状态（Nginx 内置算法不支持这种方式，需要扩展）。
      - 自研负载均衡系统时可按业务特点选指标：CPU 密集型用 CPU 负载，I/O 密集型用 I/O 负载。
    - 价值：解决了轮询无法感知服务器状态的问题。
    - 代价（三条具体复杂度）：
      1. **最少连接数优先**要求负载均衡系统统计每个服务器当前建立的连接；其应用场景**仅限于负载均衡接收的任何连接请求都会转发给服务器**处理，否则若负载均衡系统与服务器之间是**固定连接池**方式就不适合。例：LVS 可以采取该算法；而通过连接池方式连接 MySQL 集群的负载均衡系统就不适合。
      2. **CPU 负载最低优先**要求以某种方式收集每个服务器的 CPU 负载，且要确定以 1 分钟负载还是 15 分钟负载为标准——不存在 1 分钟肯定比 15 分钟好或差；不同业务最优时间间隔不同：间隔太短容易频繁波动，太长又可能峰值来临时响应缓慢。
      3. 复杂度大幅上升：轮询可能 **5 行代码**就能实现，负载最低优先可能要 **1000 行**才能实现，甚至需要负载均衡系统和服务器都开发代码；若算法本身没设计好或不适合业务运行特点，算法本身就可能成为性能瓶颈、或引发很多莫名其妙的问题。
    - 判据：效果看起来很美好，但**实际真正应用的场景反而没有轮询（包括加权轮询）那么多**。
  - **算法 4：性能最优类**
    - 视角差异：负载最低优先是**站在服务器角度**分配；性能最优是**站在客户端角度**分配——优先把任务分配给处理速度最快的服务器，以最快响应客户端。
    - 本质：也是感知服务器状态，只是用**响应时间**这个外部标准衡量。
    - 复杂度（三条）：① 需收集和分析每个服务器**每个任务**的响应时间，大量任务场景下收集与统计本身消耗较多性能；② 为减少消耗可**采样**统计（抽样部分任务响应时间估算整体），但采样率太低结果不准、太高消耗大，确定合适采样率本身也复杂；③ 无论全量还是采样，都要选合适**周期**（10 秒内最优？1 分钟内最优？5 分钟内最优？）——没有放之四海而皆准的周期，需按实际业务判断，甚至上线后要不断调优才能达到最优设计。
  - **算法 5/6：Hash 类（源地址 Hash、ID Hash）**
    - 做法：根据任务中某些关键信息 Hash，把相同 Hash 值请求分到同一台服务器，目的是满足特定**业务需求**（会话/事务粘性）。
    - **源地址 Hash**：把同一源 IP 的任务分给同一服务器，适合存在**事务、会话**的业务。例：浏览器登录网上银行会生成会话信息，会话是临时的、关闭浏览器即失效；后台无须持久化会话，只需在某台服务器上临时保存，但需保证会话存在期间用户每次访问同一服务器 → 用源地址 Hash 实现。
    - **ID Hash**：把某个 ID 标识的业务分到同一服务器处理，这里的 ID 一般是**临时性数据的 ID**（如 session id）。例：上述网银场景，用 session id hash 同样能达到「同一会话期间每次都访问同一台服务器」的目的。
- **数字与阈值**
  - **32 核 vs 16 核**：新老机器配置差异，用途：说明轮询不感知配置、加权轮询按 2:1 分配的依据。
  - **2:1**：按配置推算的加权比例（新机器处理能力假设为老机器 2 倍），用途：加权轮询的具体算法示例。
  - **1 分钟 / 15 分钟**：CPU 负载统计的两个候选时间窗，用途：说明「负载」定义本身就需要拍板且无绝对优劣。
  - **5 行 / 1000 行**：轮询与负载最低优先的实现代码量对比，用途：量化复杂度差距。
  - **10 秒 / 1 分钟 / 5 分钟**：性能最优类的候选统计周期，用途：说明「最优」依赖周期选择、需持续调优。
  - **4 大类 / 6 种算法**：本篇的分类数与详述算法数，用途：界定本篇覆盖面（原文另有「目标地址 Hash、用户 ID Hash」等同类提及）。
- **案例/数据**
  - 死循环导致 CPU 高、负载均衡仍继续发请求 → 结论：轮询的「简单」直接等于「不感知状态」的缺点。
  - 服务器宕机/断连被剔除 → 结论：轮询并非完全不感知，它感知的是「可用性」而非「负载」。
  - LVS 用连接数、Nginx 用 HTTP 请求数（需扩展） → 结论：负载指标要匹配设备层级。
  - 连接池方式连 MySQL 的负载均衡不适合最少连接数优先 → 结论：算法必须匹配「请求是否被转发」这一前提。
  - 网银会话用源地址 Hash / session id hash → 结论：Hash 类是为业务粘性服务，不是为均衡服务。
- **反例与坑**
  - 认为轮询「完全不感知服务器」（宕机、断连是能感知并需剔除的）。
  - 用固定连接池 + 最少连接数优先（前提不成立，算法失效）。
  - 用「负载最低优先」却不设计指标采集与时间窗（算法自身成瓶颈、频繁抖动）。
  - 追求「每个任务都统计响应时间」（统计开销反噬性能）。
  - 把 Hash 类当均衡算法用（它解决的是会话粘性，可能加剧不均衡）。
  - 为了「效果最好」选最复杂算法，而忽略其运维与实现成本。
- **原文金句**
  - 「总而言之，“简单”是轮询算法的优点，也是它的缺点。」
  - 「需要注意的是负载均衡系统无须关注“服务器本身状态”，这里的关键词是“本身”。」
  - 「通俗来讲，轮询可能是 5 行代码就能实现的算法，而负载最低优先算法可能要 1000 行才能实现，甚至需要负载均衡系统和服务器都要开发代码。」
  - 「负载最低优先算法虽然效果看起来很美好，但实际上真正应用的场景反而没有轮询（包括加权轮询）那么多。」
