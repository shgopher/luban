### 38丨架构师应该如何判断技术演进的方向？

- **原标题**：38 | 架构师应该如何判断技术演进的方向？

- **核心结论**
  判断技术演进方向的正确坐标系不是技术本身，而是**企业业务发展**。原文的推理链是两步：第一步看业务属于哪一类——**产品类业务是「技术创新推动业务发展」，服务类业务是「业务发展推动技术发展」**；第二步看业务处于什么阶段，据此判断当前的主要复杂度是**功能复杂度**还是**规模复杂度**。合起来一句话：*「除非是开创新的技术能够推动或者创造一种新的业务，其他情况下，都是业务的发展推动了技术的发展。」*

- **完整判据/清单/步骤**

  1. **先排除三种错误立场（原文点名的三个派别）**

     | 派别 | 价值观（原文） | 典型话术 | 原文指出的问题 |
     |---|---|---|---|
     | 潮流派 | 新技术肯定能带来很大收益 | 「NoSQL 很火，咱们要大规模地切换为 NoSQL」「将我们的 MySQL 切换为 Hadoop 吧」「Node.js 使得 JavaScript 统一前后端」 | ①新技术需要时间成熟，刚出来就用会成「实验小白鼠」；②新技术需要学习、花费时间，学完发现不适用则是人力浪费 |
     | 保守派 | 稳定压倒一切 | 「MySQL 咱们用了这么久了……业务用 MySQL，数据分析也用 MySQL，报表还用 MySQL」「业务用 Java，工具用 Java，平台也用 Java」 | 享受不到新技术收益；新技术多是为解决旧技术固有缺陷，**不是量变而是质变**，收益是爆发式而非线性 |
     | 跟风派 | 别人用了我就用 | 「这项技术腾讯用了吗？腾讯用了我们就用」「阿里用了 Hadoop……咱们也要尽快用起来」「Google 都用了 Docker，咱们也用吧」 | ①没有风可跟时怎么办、自己是领头羊怎么办；②对手信息不易获取且不全面，容易「邯郸学步」；③适用于对手的技术不一定适用于自己 |

  2. **跳出技术的理由（原文的元论证）**
     - 三派共同的病根：都是「站在技术本身的角度来考虑问题」。
     - 正确高度：企业的业务发展。
     - 业务发展的**铁三角**：**市场、技术、管理**，三者支撑业务，业务处于三角形中心；任一因素不足都可能导致业务停滞。专栏只讨论「技术 ↔ 业务」的相互影响。

  3. **业务二分法（这是全套判断的枢纽，判据是「用户选择的根本驱动力」）**

     | 维度 | 产品类 | 服务类 |
     |---|---|---|
     | 原文举例 | 360 杀毒软件、苹果 iPhone、UC 浏览器 | 百度搜索、淘宝购物、新浪微博、腾讯 IM |
     | 本质 | 具备某种「功能」，单个用户购买或免费使用来完成任务，**用户对产品是独占的** | 大量用户使用服务来完成需要与其他人交互的任务，**单个用户「使用」但不「独占」** |
     | 用户选择的根本驱动力 | **功能**（功能更强、性能更先进、体验更顺畅、外观更漂亮） | **规模**（「服务的用户越多，服务的价值就越大」） |
     | 因果方向 | **技术创新推动业务发展** | **业务发展推动技术发展** |
     | 技术的作用 | 功能/性能/体验/外观都需要强大技术支撑 | 技术不是驱动力，规模扩张后对技术提出越来越高的要求 |

  4. **产品类「技术推动业务」的证据链**
     - 苹果开发智能手机，将诺基亚推下王座，自己成为全球手机行业新王者。
     - 2G 时代 UC 浏览器独创云端架构解决上网慢；智能机时代自研 U3 内核，兼顾高速、安全、智能及可扩展性。

  5. **服务类「业务推动技术」的论证（两条反证）**
     - **淘宝反证**：模仿者只要愿意投入，**半年**就能把「淘宝网/支付宝/一淘/菜鸟物流」这类产品全部开发出来，但没有意义——用户选的是整套网络购物服务，而该服务已具备规模，别人不具备同等规模的服务能力。
     - **微信反证（思想实验）**：假设做出一个耗电只有微信 **1/10**、体验比微信好 **10 倍**的产品，绝大部分用户也不会迁移，因为「微信不是一个互联网产品，而是一个互联网服务」，单个人换掉没有意义。

  6. **服务类业务的发展闭环（原文给出的循环）**
     提出一种创新的服务模式 → 吸引了一批用户 → 业务开始发展 → 吸引了更多用户 → 服务模式不断完善和创新 → 吸引越来越多的用户 → （循环）。

  7. **产品类在长时间尺度上也会反转**
     技术创新开创一个新业务之后，后续业务发展也会反向推动技术发展。证据：第一代 iPhone 缺少 3G 支持且只能通过 Web 发布应用，第二代才支持 3G 并内置 GPS；UC 浏览器随功能变强，原架构不满足，先后经过 7.0、8.0、9.0 等几个技术差异很大的版本。

  8. **技术演进的模式（业务如何驱动技术）**
     - 无论什么行业的业务，技术要同步发展，**无一例外是因为业务「复杂度」上升，原有技术无法支撑**。
     - 复杂度只有两个来源：**功能不断叠加**、**规模扩大**（后者进一步对性能和可用性提出更高要求）。
     - 因此关键动作是：**判断业务当前和接下来一段时间的主要复杂度是什么**。判断不准 → 投入大量人力和时间做对业务没作用的事；判断准 → 技术推动业务更快发展。
     - 判断标准：**基于业务发展阶段进行判断**（这也是「架构师必须具备业务理解能力」的原因）。不同行业路径不同，架构师必须结合行业发展和企业自身情况判断。

  9. **两个行业的时间轴模板（照此格式分析自己的行业）**

     | 时间 | 银行 IT 系统的主要复杂度 | 应对 |
     |---|---|---|
     | 90 年代 | 业务范围扩大、功能越来越复杂 → 内部系统数量变多、单系统功能变复杂 | 原文未明确 |
     | 2004 年以后 | 柜台转向网上银行 → 稳定性、安全性、易用性 | 由银行 IT 系统自己解决 |
     | 2009 年以后 | 移动支付复杂度（「双 11」海量支付） → 高性能、稳定性、安全性 | 银行与移动支付服务商（支付宝、微信）一起解决 |

     | 时间 | 淘宝的主要复杂度 | 应对 |
     |---|---|---|
     | 2003 年 | 业务刚创立，如何快速开发各种需求 | 买了一个 PHP 写的系统来改 |
     | 2004 年 | 上线后请求量大大增加，如何保证性能 | 用 Oracle 取代 MySQL |
     | 用户再增长 | 仍是性能和稳定性 | 用 Java 替换 PHP |
     | 2005 年 | 单一 Oracle 库无法满足性能 | 分库分表、读写分离、缓存 |
     | 2008 年 | 系统内部耦合（交易与商品耦合、支付与支付宝强耦合），逻辑复杂、体验差 | 系统解耦，把交易中心、类目管理、用户中心从大一统系统拆出 |

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 10 多年 | 原文对「最近技术发展目不暇接」的时间尺度描述 |
  | 3 | 支撑业务发展的铁三角因素数（市场、技术、管理） |
  | 2 | 业务分类数（产品类 / 服务类） |

  | 1/10、10 倍 | 微信思想实验中的耗电与体验假设值 |
  | 90 年代 / 2004 / 2009 | 银行 IT 复杂度切换的三个时点 |
  | 2003 / 2004 / 2005 / 2008 | 淘宝复杂度切换的四个时点 |
  | 1 亿以上、PV 2.5 亿以上 | 2008 年淘宝商品数量与 PV，用于说明复杂度已转为「内部耦合」 |

- **案例/数据**
  - 苹果智能手机取代诺基亚 → 产品类业务里，技术创新能直接改写行业格局。
  - UC 浏览器云端架构（2G 时代）与 U3 内核（智能机时代） → 产品类的竞争力来自技术本身。
  - 淘宝/微信不可被「更好的产品」替代 → 服务类的护城河是规模，不是功能。
  - 淘宝 2003→2008 的五段技术动作 → 每一段技术选择都由当期主要复杂度决定，而不是由技术潮流决定。
  - 银行 90 年代→2009 年 → 同一个行业在不同阶段的主要复杂度完全不同，所以「行业模板」不存在，只有「阶段分析法」。

- **反例与坑**
  - 潮流派：新技术不成熟期上车，成为小白鼠；学完发现不适用，人力浪费。
  - 保守派：把「一把锤子」当万能，把所有问题都看成钉子；错过质变级收益（「有了拖拉机，你还偏偏要用牛车」）。
  - 跟风派：无风可跟 / 自己是领头羊时失效；信息不全面导致邯郸学步；对手适用的技术未必适用自己。
  - 生搬硬套：不考虑实际情况照抄别派做法，出现「橘生淮南则为橘，生于淮北则为枳」。
  - 架构师只盯技术：会「不识庐山真面」，因为「只缘身在此山中」。
  - 判断错复杂度：投入大量人力和时间做对业务没有作用的事情。

- **原文金句**
  - 「不识庐山真面，只缘身在此山中。」
  - 「如果你手里有一把锤子，那么所有的问题都变成了钉子。」

### 39丨互联网技术演进的模式

- **原标题**：39 | 互联网技术演进的模式

- **核心结论**
  互联网业务因「规模决定一切」而有共同的发展路径：**初创期 → 发展期 → 竞争期 → 成熟期**；四个时期的差别只体现在**业务复杂性**和**用户规模**两条主线上，而这两条主线的本质都是**「量变带来质变」**。技术演进的全部目标可以收敛为一个字——满足业务对**「快」**的要求；*「当发现你的业务快不起来的时候，其实就是技术的水平已经跟不上业务发展的需要了，技术变革和发展的时候就到了。」*

- **完整判据/清单/步骤**

  1. **四期划分（先定期，再定手段）**

     | 时期 | 业务特征 | 技术要务 | 典型手段 |
     |---|---|---|---|
     | 初创期 | 一个创新业务点，重点在「创新」不在「完善」，一开始不可能完善；团队最弱小（可能就几个技术人员） | 只有一个要求：「快」 | 十八般武艺都用上：**能买就买，有开源的就用开源的** |
     | 发展期 | 市场验证可行，用户变多，不断加新功能 | 快速实现各种需求 | 堆功能 → 优化（优化派/架构派）→ 架构（拆） |
     | 竞争期 | 对手加入，互相学习模仿，业务更完善、更多创新，技术压力更上一层 | 解决「重复造轮子」和「系统交互一团乱麻」 | 平台化 + 服务化 |
     | 成熟期 | 成为领头羊或行业成熟，市场地位牢固，创新机会不大、竞争不激烈 | 从「求快求新」转向「求精」：响应时间、体验、成本 | 无固定套路的逐项优化，可复用前几期手段 |

  2. **发展期的三小步（原文明确的分段）**
     - **堆功能期**：团队规模不大、需求紧，最快方式是继续在原系统加功能；重构、优化、架构即使想做也会被人力和业务压力放到一边。
     - **优化期**：功能变多、系统变复杂，继续堆功能越来越吃力（「做一个需求要改好多地方，一不小心就改出了问题」），直到团队或产品人员受不了。
       - **优化派**：重构、分层、优化某条 MySQL 查询、机械硬盘换 SSD、MySQL 换 Oracle、加 Memcache。优点：改动小、可快速实施；缺点：可能过不了多久系统又撑不住。
       - **架构派**：把大系统拆成多个互相配合的小系统（如购物系统拆为登录认证子系统、订单系统、查询系统、分析系统）。优点：一次调整可支撑较长期发展；缺点：动作大、耗时长、对业务影响大。
       - **原文判断：大部分情况下「优化派」会赢**，因为「优化」是最快的方式；至于优化派撑不了多久，其实不用考虑太多，因为业务能否发展到那个阶段还是未知数，**保证当下的竞争力是最主要的问题**。
     - **架构期**：优化顶不住了（再怎么优化系统能力总有极限），架构派扬眉吐气。手段归根结底一个字「**拆**」，什么地方都可以拆：
       - **拆功能**：购物系统拆为登录认证、订单、查询、分析等子系统。
       - **拆数据库**：MySQL 一台变两台、2 台变 4 台，增加 DBProxy、分库分表。
       - **拆服务器**：服务器一台变两台、2 台变 4 台，增加负载均衡系统如 Nginx、HAProxy。

  3. **竞争期的病灶与药方（一一对应，不能混用）**
     - 病灶一：**重复造轮子**——系统越来越多，各系统相似工作越来越多（每个系统都有存储、都要用缓存、都要用数据库；新建系统又要全做一遍）。
       - 药方：**平台化**。存储平台化（淘宝 TFS、京东 JFS）；数据库平台化（百度 DBProxy、淘宝 TDDL）；缓存平台化（Twitter Twemproxy、豆瓣 BeansDB、腾讯 TTC）。
     - 病灶二：**系统交互一团乱麻**——交互关系变网状，交互数量与系统数量成**平方比**。
       - 药方：**服务化**。异步通知用消息队列（淘宝 Notify、MetaQ，开源 Kafka、ActiveMQ）；同步调用用服务框架（Facebook thrift、当当网 Dubbox、淘宝 HSF）。

  4. **成熟期的判断与做法**
     - 判断标志：市场地位牢固、业务创新机会不大、竞争压力不激烈，求快求新没有很大空间。
     - 业务转向「求精」的三问：响应时间是否比对手快？用户体验是否比对手好？成本是否比对手低？
     - 技术做法：该拆的拆了、该平台化的平台化了，大动作不多，主要是优化；但**为了某个优化也可能做很大改变**（如响应时间 200ms→50ms，可能要从 CDN、数据库、网络多方面同时优化）。优化没有固定套路，按竞争要求找出自己的弱项逐项优化，并可复用之前各时期的手段。

  5. **用户规模这条主线的两个影响面**
     - **性能**：以 MySQL 为例，再简单的查询、再高的硬件配置，单台机器支撑的 TPS/QPS 最高也就是**万级**（低的几千、高的不过几万）。用户量增长后必须用多台 MySQL，这**不是数量增加而是本质改变——集中式存储变为分布式存储**，随之要处理分库分表、读写分离、复制、同步等，复杂度大幅上升。
     - **可用性**：用户量越大，宕机影响越大。
       - 口碑：1 万用户宕机 1 小时可能没大影响；100 万用户宕机 10 分钟，投诉电话被打爆，用户再到朋友圈抱怨，「很可能你就不会再有机会发展下一个 100 万用户了」。
       - 收入：1 万用户宕机 1 小时可能只损失几千元；100 万用户宕机 10 分钟损失可能几十万元。

  6. **量变到质变的判定模型**
     - 原文：用户规模发展到什么阶段才由量变带来质变，「虽然不同的业务有所差别，但基本上可以按照下面这个模型去衡量」——**该模型在清洗文本中缺失（原为配图），具体分档阈值原文未明确**，需回原课程图核对。
     - 可确定的是：复杂度与用户规模这两个因素「本质其实都是量变带来质变」。

  7. **提前量原则（原文给出的最优做法）**
     - 应对质变的处理方式各期不同，但核心目标都是满足业务「快」的要求。
     - 更好的做法：**在问题还没有真正暴露出来时，就根据趋势预测下一个转折点，提前做好技术准备**（原文同时指出这对技术人员要求非常高）。

  3. **SQL 分支的四级演进（原文顺序）**
     - ① **先纠正一个误解**：NoSQL 不是「No SQL」，而是 **Not Only SQL**，是 SQL 的补充；关系数据不可能被完全抛弃。
     - ② **选型**：Oracle 太贵且需专人维护，互联网行业一般用 **MySQL、PostgreSQL** 这类开源数据库。优点：开源免费、拿来就用；缺点：性能相比商业数据库差一些。
     - ③ **拆分**：性能要求变高后必然要把数据拆到多个数据库实例（原文强调「其实 Oracle 也一样，只是时间早晚的问题」）。拆分带来新复杂度：**数据如何拆分、数据如何组合**。
     - ④ **中间件化**：如果每个业务都实现一遍拆分逻辑，重复造轮子导致投入浪费、效率降低，所以业务到一定阶段就把这部分功能独立成中间件，如百度 DBProxy、淘宝 TDDL。原文提示：把分库分表做到**自动化和平台化**技术要求很高，一般只有规模很大的公司自己做；**中小公司建议用开源方案：MySQL Router（MySQL 官方推荐）、Atlas（360 开源）**。
     - ⑤ **平台化**：SQL 服务器越来越多、每个业务各自部署集群后，出现两个新问题——数据库资源使用率不高（浪费）、各 SQL 集群分开维护（维护成本越来越高）。所以实力雄厚的大公司会在 SQL 集群上构建 **SQL 存储平台**，以**对业务透明**的形式提供：**资源分配、数据备份、迁移、容灾、读写分离、分库分表**。代表：淘宝 **UMP（Unified MySQL Platform）**。

  4. **NoSQL 分支的演进与平台三功能**
     - 与 SQL 的两点不同：**数据结构不同**（Memcache 的 key-value、Redis 的复杂数据结构、MongoDB 的文档结构）；**无一例外把性能作为一大卖点**。这两点正好弥补关系数据库的不足，所以在互联网行业「NoSQL 的应用基本上是基础要求」。
     - NoSQL 自带集群（Memcache 一致性 Hash 集群、Redis 3.0 集群），所以起步阶段很方便，不像 SQL 分库分表那么复杂；**一般公司不会在开始时就考虑包装成存储平台**。
     - 何时需要平台：节点上千甚至几千时。平台价值两条：集中管理提升运维效率；提升资源利用效率（2000 台机器利用率提升 10% 就减少 200 台，一年省几十万元）。
     - 统一存储平台的三个功能：**资源动态按需分配**（同一台 Memcache 按内存利用率分配给多个业务）、**资源自动化管理**（新业务只申请多少缓存空间，无需关注具体哪些服务器）、**故障自动化处理**（某台 Memcache 挂掉后由备份服务器立刻接管，不丢失很多缓存数据）。
     - 规模判据（原文的收益门槛）：只有几十台 NoSQL 服务器做平台收益不大；几千台则收益很大。

  5. **小文件存储的判据与做法**
     - 适用数据：商品图片/描述、用户图片、一条微博内容等「用于展示的数据」。
     - 三个典型特征：**数据小（一般 1MB 以下）、数量巨大、访问量巨大**。
     - 结论：每个业务自己做海量存储和海量访问效率低、重复造轮子，所以要**做成统一的和业务无关的平台**。
     - **与小文件/大文件的关键差异**：小文件存储**不一定需要公司或业务规模很大**，原文认为「业务在起步阶段就可以考虑做小文件统一存储」。
     - 做法：得益于开源运动和大数据火爆，在开源方案上封装一个小文件存储平台并不太难；底层可用 **HBase、Hadoop、Hypertable、FastDFS**，「只需要将这些开源方案再包装一下基本上就可以用了」。
     - 典型实现：**淘宝 TFS、京东 JFS、Facebook Haystack**。

  6. **大文件存储的判据与做法**
     - 两类大文件：**业务上的大数据**（Youtube 视频、电影网站电影）、**海量的日志数据**（访问日志、操作日志、用户轨迹日志）。
     - 与小文件相反：数量没那么多，但每个文件很大——**几百 MB、几个 GB 常见，几十 GB、几 TB 也有可能**；因此**不能直接把小文件存储系统拿来存大文件**。
     - 技术源头：Google 三篇大数据论文 **Bigtable / MapReduce / GFS** 开启大数据时代；Yahoo 开源的 **Hadoop 系列（HDFS、HBase）** 基本垄断开源界大数据处理；后续还有更多开源方案。
     - 选型结论（原文认为这块反而最简单）：自建一套完整大数据方案难度和成本太高，开源方案已成熟，**「你没有太多选择，只能用这几个流行的开源方案」——Hadoop、HBase、Storm、Hive**。
     - 平台化：实力雄厚的大公司基于开源方案结合业务特点封装成大数据平台，如**淘宝云梯、腾讯 TDW**。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 1MB | 小文件「数据小」的上界判据 |
  | 3.5 亿张/天 | Facebook 2013 年每天上传照片数（小文件「数量巨大」的证据） |
  | 10 亿 | Facebook 每天的访问量（小文件「访问量巨大」的证据） |

  | 3 篇论文 | Bigtable / MapReduce / GFS，大数据时代起点 |

- **案例/数据**
  - 淘宝 UMP → SQL 平台化后的标准能力集（分配/备份/迁移/容灾/读写分离/分库分表）就是对业务透明的价值。

     |---|---|---|
     | 开发框架 | Java：SSH、SpringMVC、Play；Ruby：Ruby on Rails；PHP：ThinkPHP；Python：Django | 互联网公司「都会指定一个大的技术方向，然后使用统一的开发框架」。**总原则：优选成熟的框架，避免盲目追逐新技术** |
     | Web 服务器 | Java：Tomcat、JBoss、Resin；PHP/Python：Nginx；万能：Apache；二次开发代表：淘宝 Tengine | 「拿来主义」，挑一个流行的开源服务器即可；一般公司「只需要将开源服务器摸透，优化一下参数，调整一下配置就差不多了」 |
     | 容器 | Docker（代表） | 相比虚拟机：没有跨平台，但**启动快、几乎不占资源**；原文判断「Docker 类的容器技术将是技术发展的主流方向」 |

  2. **为什么要统一开发框架（原文给出的三个问题 + 三个理由）**
     - 不统一的三宗罪：①技术人员之间没有共同的技术语言，交流合作少；②每类技术都需要投入大量人力和资源才能熟练精通；③不同团队之间人员无法快速流动，人力资源不能高效利用。
     - 选成熟框架的三个理由：①成熟框架资料文档齐备，各种坑基本都有人踩过，遇到问题容易搜索解决；②受众更广，招聘更容易招到合适人才；③更加稳定，不会出现大变动，适合长期发展。
     - Apache 的取舍判据（原文原话）：不用过早担心性能，「等到业务真的发展到 Apache 撑不住的时候再考虑切换也不迟，那时候你有的是钱，有的是人，有的是时间」。

  3. **容器带来的两个变化（原文明确的两条）**
     - **运维方式革命性变化**：启动快、几乎不占资源、随时启停 → 基于 Docker 打造自动化运维、智能化运维将成为主流方式。
     - **设计模式本质变化**：启动一个新容器实例代价如此低 → 鼓励设计思路朝「微服务」方向发展。
     - 举例：一个传统网站含登录注册、页面访问、搜索；没有容器时除非访问量特别大，否则这些功能一开始都集成在一个系统里；有了容器后**一开始就可以按服务方式设计，避免后续访问量增大时又要重构系统**。
     - 落地证据：腾讯万台规模的 Docker 应用实践；新浪微博红包的大规模 Docker 集群。

  4. **服务层的入口判据：系统间依赖的增长曲线**
     - 现状：完成 A 业务系统可能需要 B、C、D、E 等十几个其他系统协作。
     - 原文表述为「系统间的依赖是呈指数级增长的」，给出的算例是：**3 个系统相互关联的路径为 3 条，6 个系统相互关联的路径为 15 条**（即两两组合 C(n,2)；「指数级」是原文措辞，算例实际是平方级）。

  5. **配置中心：问题 → 好处 → 设计要点**
     - 分散配置的三类问题：①某功能上线需多系统一起上线，配置检查、沟通协调耗时；②处理线上问题需多系统配合查信息，操作效率低、协调耗时；③各系统用文本编辑改配置，**没有自动校验机制**，容易配错且很难发现（案例：把 IP 里的数字 **0** 误敲成字母 **O**，肉眼极难发现，程序检查很容易）。
     - 通用配置中心的四条好处：①集中配置多个系统，操作效率高；②配置都在一处，检查方便、协作效率高；③可实现**程序化规则检查**（最小值/最大值/是否 IP/是否 URL，用正则即可）；④相当于备份了系统配置，需要搭新环境时能快速搭建和恢复业务。
     - 恢复场景的价值：整机磁盘坏掉、主板坏掉等不可恢复故障时，程序包已存在 + 配置中心的配置，就能很快搭新环境恢复业务；否则「几十个配置文件重新一个个去 Vim 中修改，耗时很长，还很容易出错」。
     - 设计要点：用「**系统标识 + host + port**」标识唯一一个系统运行实例是常见做法。

  6. **服务中心：要解决的两个问题 + 两种实现**

     | 实现 | 机制（原文） | 与 DNS / 总线的类比 | 关键差异 |
     |---|---|---|---|
     | 服务名字系统（Service Name System） | 把 Service 名称解析为「**host + port + 接口名称**」 | 类比 DNS（Domain Name System） | 「真正发起请求的还是请求方」 |
     | 服务总线系统（Service Bus System） | **由总线系统完成调用** | 类比计算机总线 | 「服务请求方都不需要直接和服务提供方交互了」 |

     - 不建服务中心时的两个具体痛点：
       - 换接口：10 个系统依赖 A 的 X 接口，A 实现更好的 Y 接口，要让 10 个系统切换，则这 10 个系统的**几十上百台机器**配置都要改并重启，效率很低。
       - 机器变动：A 有 20 台机器、其中 5 台故障；走域名则在**域名缓存失效前**仍可能访问到故障机；走 IP 则 A 每次增删机器，其他 10 个系统的几十上百台机器都要同步修改。
     - 结论：服务中心就是为了解决跨系统依赖的「**配置**」和「**调度**」问题。

  7. **消息队列：异步通知的判据、效果与难点**
     - 需求来源：互联网业务要「快」，很多处理必须异步。例：大 V 发一条微博后要给关注者发消息，不可能等所有消息发完才告诉大 V 发布成功。
     - 传统做法的问题：生产者直接调用消费者接口，业务庞大、子系统增多后「整个系统的结构就像一张蜘蛛网」。
     - 消息队列能力：既可「一对一」通知，也可「一对多」广播。
     - 引入后的五条效果（原文逐条）：①整体结构从**网状**变为**线性**，结构清晰；②消息生产和消费**解耦**，实现简单；③增加新的消费者，生产者**完全不需要任何改动**，扩展方便；④消息队列可做高可用、高性能，避免各业务子系统各自做一套，减轻工作量；⑤业务子系统只需聚焦业务（原文与第④条并列陈述）。
     - 难点与选型：基本功能实现简单，但要做到**高性能、高可用、消息时序性、消息事务性**比较难。开源成熟方案：**RocketMQ、Kafka、ActiveMQ**；若业务对可靠性、时序、事务性要求较高，则要深入研究这些方案，「否则很容易踩坑」。
     - 自研的判据：开源用起来方便但**要改很麻烦**；消息队列相对简单，很多公司会花人力重复造轮子，好处是**可根据自己的业务特点做快速适配开发**。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 3 条 / 15 条 | 3 个系统 / 6 个系统的相互关联路径数（依赖随系统数平方增长） |
  | 10 个系统、几十上百台机器 | 换接口/机器变动时的同步改造规模 |
  | 20 台、5 台 | A 系统机器数与故障机器数（域名缓存与 IP 直连的两个坑） |
  | 3 个 | 配置中心要解决的分散配置问题数 |
  | 4 条 | 通用配置中心的好处数 |
  | 3 条 | 统一开发框架要解决的团队问题数 |
  | 3 条 | 选成熟框架的理由数 |
  | 5 条 | 引入消息队列后的效果条数 |

- **案例/数据**
  - 淘宝 Tengine → 大公司在开源 Web 服务器上做二次开发；一般公司只需调参调配置。
  - 腾讯万台 Docker、微博红包大规模 Docker 集群 → 容器在 BAT 级别已有较多应用。
  - IP 的 0 被敲成字母 O → 人工文本配置的典型错法，配置中心用正则即可拦住。
  - 大 V 发微博 → 消息队列从「蜘蛛网」到「线性」的标准叙事。
  - 10 个系统依赖 A 的 X 接口 → 服务中心存在的量化理由（几十上百台机器要重启）。

- **反例与坑**
  - 各团队各用一套开发框架/语言 → 语言不通、招聘困难、人员不能流动、每类技术都要重复精通。
  - 盲目追新框架 → 违背「优选成熟框架」总原则（文档少、坑多、招人难、不稳定）。
  - 过早担心 Apache 性能 → 原文明确说等到撑不住再换也不迟。
  - 配置散落在各系统文本文件里 → 上线协同难、排障难、无校验、灾难恢复要手改几十个文件。
  - 用域名或 IP 硬编码跨系统调用 → 域名缓存导致故障机仍在服务，IP 变动导致全量同步改配置。
  - 生产者直接调消费者接口做异步通知 → 网状依赖、联调灾难。

### 42丨互联网架构模板：“网络层”技术

- **原标题**：42 | 互联网架构模板：“网络层”技术

- **核心结论**
  网络层的存在理由是：*「单个系统的高可用和高性能并不等于整体业务的高可用和高性能」*。互联网业务的高性能和高可用**必须从更高的角度去设计，这个高点就是「网络」**。原文同时划清边界：这里的网络层**不是**「如何搭建一个局域网」，「强调的是站在网络层的角度整体设计架构，而不是某个具体网络的搭建」。该层由四段递进构成：**负载均衡 → CDN → 多机房 → 多中心**。

- **完整判据/清单/步骤**

  1. **负载均衡：先认清「为什么必须有多台」**
     - 原因：每个系统的处理能力有限，为应对大容量访问必须用多个系统。
     - 原文量化：一台 **32 核 64GB 内存**的机器，压测每秒处理 Hello World 的 HTTP 请求**不超过 2 万**；实际业务机器处理 HTTP 请求每秒可能才**几百 QPS**；而互联网业务并发**超过 1 万**比较常见，双十一、过年发红包等极端场景每秒可达**几十万**请求。

  2. **负载均衡的四类方案（按作用范围与层次分工，不能互相替代）**

     | 方案 | 层次/性质 | 作用范围 | 原文定位与关键判据 |
     |---|---|---|---|
     | DNS | 应用层解析 | **地理级别**（北方用户访问北京机房、南方访问广州机房） | 「最简单也是最常见的负载均衡方式」；**一般不用来做机器级负载均衡，因为太耗费 IP 资源**（百度搜索可能要 10000 台以上机器，不可能都配公网 IP） |
     | HTTP-DNS | 自研私有 DNS（HTTP 协议实现） | 地理/策略级，主要用在 **App** 业务 | 有实力的公司为时延和故障敏感的业务自研；Web 业务实现麻烦（URL 解析由浏览器完成，只有 JavaScript 访问能像 App 那样灵活控制） |
     | Nginx | **软件的 7 层**负载均衡 | 同一地点内**机器级** | 支持 HTTP、E-mail 协议 |
     | LVS | **内核的 4 层**负载均衡 | 同一地点内机器级 | 和协议无关，「几乎所有应用都可以做，例如聊天、数据库等」 |
     | F5 | **硬件的 4 层**负载均衡 | 同一地点内机器级 | 同上，性能最高、单价最贵 |

     - **DNS 的两条缺点（原文逐条）**：①**缓存时间比较长**——即使把某台业务机器从 DNS 服务器上删除，由于缓存，还是有很多用户会继续访问已删除的机器；②**不够灵活**——DNS 不能感知后端服务器状态，只能按配置策略负载均衡；也无法做到「配置好的机器多分请求」这类灵活策略。
     - **HTTP-DNS 的三优两缺**：优点 **灵活**（可按业务需求灵活设置各种策略）、**可控**（自研系统，IP 更新与策略更新不依赖外部服务商）、**及时**（不受传统 DNS 缓存影响，可非常快更新数据、隔离故障）；缺点 **开发成本高**（没有通用解决方案，需自己开发）、**侵入性**（需 App 基于 HTTP-DNS 改造）。
     - **软件 vs 硬件的选择判据（原文的性价比算法）**：性能上 Nginx 是**万级**（一般 Linux 服务器装个 Nginx 大概 **5 万/秒**）、LVS 是**十万级**（据说可达 **80 万/秒**）、F5 是**百万级**（**200 万～800 万/秒**）。硬件单台贵（一台最便宜的 F5 都是**几十万**），但按同等请求量级折算可能更便宜：假设每秒 100 万请求，**一台 F5 就够，用 Nginx 可能要 20 台**，折算下来 F5 成本反而低。结论：**性能要求不高用软件负载均衡；性能要求很高推荐硬件负载均衡**。
     - 云化选项：阿里云 SLB、UCloud ULB，「中小公司直接购买即可」。

  3. **CDN 的定位与取舍**
     - 定义与本质：解决用户网络访问时的「**最后一公里**」效应，本质上是一种「**以空间换时间**」的加速策略——把内容缓存在离用户最近的地方，用户访问的是缓存内容而不是站点实时内容。
     - 体系范围：分布式存储、全局负载均衡、网络重定向、流量控制等都属于 CDN 范畴；在视频、直播等领域没有 CDN 用户不可能流畅观看。
     - 取舍判据：**独立搭建成本巨大，很少有公司自己设计和搭建**；从 CDN 服务商购买即可（网宿、蓝汛；阿里云、腾讯云也提供）。大部分程序员和架构师不需要深入理解 CDN 细节。

  4. **多机房：三种形态与各自妥协**
     - 存在理由：从架构上，**单机房就是一个全局的网络单点**；停电、机房网络中断、地震、水灾都可能让一个机房完全瘫痪。
     - 核心因素：**如何处理时延带来的影响**。

     | 形态 | 做法 | 收益 | 代价/限制（原文） |
     |---|---|---|---|
     | 同城多机房 | 同城多机房，投入重金搭**私有高速网络** | 基本能做到和同机房一样的效果，对业务影响很小 | 投入较大，非大公司承受不起；遇极端地震、水灾仍有很大风险 |
     | 跨城多机房 | 不同城市建机房，机房间通过网络做数据复制（如 MySQL 主备复制） | 实现简单 | 跨城时延要求业务做妥协：不要求实时强一致，只保证**最终一致性**；和业务强相关——微博可以，支付宝转账不行（余额是强一致性） |
     | 跨国多机房 | 地理更远、时延更大 | 一般**仅用于备份和服务本国用户** | 时延太大 + 用户跨国访问太慢 |

  5. **多中心：与多机房的本质差别（原文的分界线）**
     - 前提关系：**多中心必须以多机房为前提**，但「从设计的角度来看，多中心相比多机房是本质上的飞越，难度也高出一个等级」。
     - 多机房的目标是**灾备**：机房故障时较快把业务切到另一机房；**允许一定时间中断（例如 10 分钟、1 个小时）**，**允许业务有损失**（未同步数据不能马上恢复，或要等几天，甚至永远不能恢复）。
     - 多中心的要求：**每个中心都同时对外提供服务**，且**业务能自动在多中心之间切换**，故障后**不需人工干预或很少人工干预就能自动恢复**。
     - 多中心的关键难点：**数据一致性**和**数据事务性**如何保证；两者都与业务紧密相关，**目前没有很成熟的且通用的解决方案**，需基于业务特性详细分析和设计。
     - 现实证据：淘宝对外宣称多中心，但商品浏览、订单、支付的多中心方案都要**独立设计和实现**；国内银行、支付宝这类系统**没有完全实现多中心**（否则不会出现「挖掘机一铲子下去，支付宝中断 4 小时」的故障）。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 32 核 / 64GB | 压测所用机器规格 |
  | 2 万/秒 | 该机器 Hello World HTTP 请求上限 |
  | 几百 QPS | 实际业务机器的 HTTP 处理能力 |
  | 1 万并发 / 几十万每秒 | 互联网常见并发与极端峰值（双十一、红包） |
  | 10000 台以上 | 百度搜索机器量级，说明为何 DNS 不做机器级均衡 |
  | 5 万/秒 | Nginx 性能（万级） |
  | 80 万/秒 | LVS 性能（十万级，据说） |
  | 200 万～800 万/秒 | F5 性能（百万级） |
  | 几十万 | 一台最便宜 F5 的价格 |
  | 100 万请求/秒、1 台 F5 vs 20 台 Nginx | 软硬件成本折算的算例 |
  | 10 分钟 / 1 小时 | 多机房切换可接受的中断时长 |
  | 4 小时 | 支付宝被挖断光缆后中断时长（多中心未完全实现的证据） |

- **案例/数据**
  - `dig baidu.com` 看实际 IP 数 → 原文提示可自查「DNS 不会给上万台机器配公网 IP」。
  - 微博跨城多机房：北京发微博、广州 10 分钟后看到也可以 → 最终一致性可接受的业务样本；支付宝转账 → 强一致，不可照搬。
  - 淘宝多中心按业务线分别设计 → 多中心没有通用方案。
  - 支付宝中断 4 小时 → 「宣称多中心」与「真多中心」的差距。

- **反例与坑**
  - 用 DNS 做机器级负载均衡 → 耗费大量公网 IP 资源。
  - 忽视 DNS 缓存 → 已下线机器仍在接流量。
  - 期待 DNS 感知后端状态或做加权 → DNS 做不到（要灵活只能自研 HTTP-DNS，代价是开发成本 + App 侵入）。
  - 只看单价选负载均衡 → 一台 F5 几十万，但 100 万 QPS 场景下比 20 台 Nginx 更便宜。
  - Web 业务照搬 HTTP-DNS → URL 解析在浏览器手里，只有 JS 访问可控。
  - 自建 CDN → 成本巨大，直接买。
  - 把多机房当多中心 → 多机房允许中断与数据损失，多中心要求同时服务 + 自动切换。
  - 认为多中心有通用方案 → 原文明确「没有很成熟的且通用的解决方案」。

- **原文金句**
  - 「单个系统的高可用和高性能并不等于整体业务的高可用和高性能。」
  - 「互联网业务的高性能和高可用需要从更高的角度去设计，这个高点就是『网络』。」
  - 「CDN 是为了解决用户网络访问时的『最后一公里』效应，本质上是一种『以空间换时间』的加速策略。」
  - 「多中心相比多机房是本质上的飞越，难度也高出一个等级。」

- **可迁移到知识库的主题**
  - 负载均衡四分法（DNS / HTTP-DNS / 软件 7 层 / 硬件与内核 4 层）与软硬件成本折算。
  - CDN 的定位（空间换时间）与自建/购买判据。
  - 多机房三形态（同城/跨城/跨国）与一致性妥协表。
  - 多机房 vs 多中心的判据（是否允许中断、是否允许数据损失、是否自动切换）。
  - 「单机房 = 全局网络单点」作为可用性论证的起点。

### 43丨互联网架构模板：“用户层”和“业务层”技术

- **原标题**：43 | 互联网架构模板：“用户层”和“业务层”技术

- **核心结论**
  **用户层**处理的是「怎么把分散的用户连起来并触达他们」——用户管理（SSO / 授权登录）、消息推送、存储云与图片云；其数据量巨大但**实现不难**，因为用户之间没有强业务关联。**业务层**「没有办法提炼一些公共的系统或者组件」，面临的唯一挑战是**复杂度**，而解法只有一把「屠龙宝刀」——**拆**；拆到几百上千个子系统后再用「**合**」（虚拟业务域 + 网关）收敛认知复杂度。

- **完整判据/清单/步骤**

  1. **用户层组件总表**

     | 组件 | 原文子项 | 解决什么问题 | 关键选择建议 |
     |---|---|---|---|
     | 用户管理 | 单点登录 SSO（cookie / JSONP / token；最成熟开源方案 CAS）、授权登录（OAuth 2.0） | 多子系统不可能各自管理庞大用户；平台化后需允许第三方接入 | SSO 用 CAS；开放平台用 OAuth 2.0，「私有协议漏洞多，第三方接入也麻烦」 |
     | 消息推送 | 短信、邮件、站内信、App 推送（iOS：APNS；Android：GCM / 厂商推送 / 自研 / 第三方） | 触达用户 | 中小公司不涉敏感数据 → 用第三方（友盟、极光）；涉敏感数据 → 自研 |
     | 存储云 / 图片云 | CDN + 小文件存储 | 用户上传文件的存储与访问 | 除非 BAT 级别，不建议重复造轮子，直接买云服务；图片因处理链复杂而独立成系统 |

  2. **用户管理的两个目标（按业务阶段递进）**
     - 目标一 **单点登录（SSO，又叫统一登录）**：稍大的互联网业务必然多子系统，不可能每个都管理庞大用户。技术手段有 cookie、JSONP、token 等，**目前最成熟的开源单点登录方案当属 CAS**。
     - 目标二 **授权登录**：业务做大成为平台后，开放是促进业务进一步发展的手段，需允许第三方应用接入；最流行的是 **OAuth 2.0**，「基本上已经成为了事实上的标准」；要做开放平台最好用它，私有协议漏洞多、第三方接入也麻烦。

  3. **用户管理「量大但不难」的判据（原文的架构判断）**
     - 量级：一般至少**千万级**，QQ、微信、支付宝这种巨无霸是**亿级**。
     - 但实现不难，原因是：**用户数据量虽大，不同用户之间没有太强的业务关联**——「A 用户登录和 B 用户登录基本没有关系」。
     - 结论：**用一个简单的负载均衡架构就能轻松应对**（基本架构为负载均衡 + 多实例）。

  4. **消息推送的落地判据（按平台分叉）**
     - 短信 / 邮件 / 站内信：调用不同 API 即可，技术上没有难度（短信依赖运营商接口，邮件依赖邮件服务商接口，站内信是系统自带通知）。
     - iOS：系统规范且封闭，**基本上只能使用苹果的 APNS**。
     - Android 国外：用 **GCM** 和 APNS 差别不大。
     - Android 国内：情况复杂——**GCM 不能用**；各手机厂商定制 Android、推送实现不完全一样。
     - 因此 Android 推送「五花八门」：有实力的大厂自研（**阿里云移动推送、腾讯信鸽推送、百度云推送**）；第三方商业服务（**友盟推送、极光推送**）。
     - 选型建议：中小公司不涉敏感数据 → **推荐第三方**（专业做推送，消息到达率有一定保证）；涉敏感数据 → 自研，此时有技术挑战。
     - 自研推送的**三大功能**：**设备管理**（唯一标识、注册、注销）、**连接管理**、**消息管理**。
     - 自研推送的**三大挑战**：
       1. **海量设备和用户管理**：设备数量众多，存储和管理复杂；还要把用户和设备关联，提取用户特征做分类或打标签，以支持差异化推送。
       2. **连接保活**：推送必须有连接通道，但应用不可能一直在前台；大部分设备为省电省流量会限制后台运行，通道可能被中断导致消息无法及时送达。「连接保活是整个消息推送设计中细节和黑科技最多的地方」——例如应用互相拉起、找手机厂商开白名单。
       3. **消息管理**：并非每条消息都发给每个用户，而要按用户特征选人推送；用户特征变化大、排列组合多，选人逻辑必须设计得非常灵活，可采取**规则引擎之类的微内核架构技术**。

  5. **存储云 / 图片云的三个数据特征与实现**
     - 三个特征：**数据量大**（用户基数大、上传频繁；2016 年微信朋友圈每天上传图片达 10 亿张）、**文件体积小**（大部分图片几百 KB 到几 MB，短视频播放时间在几分钟内）、**访问有时效性**（刚上传时访问最多，随时间推移访问量越来越小）。
     - 实现：本质是「**CDN + 小文件存储**」（小文件存储即第 40 讲的技术）。
     - 为什么不自己造：有了云之后，除非 BAT 级别，直接买云服务「可能是最快也是最经济的方式」。
     - 为什么图片云要独立成一个系统（而不是与存储云合一）：因为**图片业务更复杂**——除存储和访问外，还包括**裁剪、压缩、美化、审核、水印**等处理。

  6. **业务层的判断：无公共组件，只有「拆」**
     - 原文明确：互联网业务千差万别，分解下来是不同的系统，**业务层没有办法提炼公共的系统或者组件**。
     - 抛开业务差异，各互联网业务最终面临的问题类似：**业务复杂度越来越高**；主要原因是系统越来越庞大、业务越来越多。
     - 解法：「屠龙宝刀」——**拆**，化整为零、分而治之，把整体复杂性分散到多个子业务或子系统（具体方式见可扩展架构模式的分层架构、微服务、微内核）。
     - 电商样例的三个发展阶段：**第一阶段**所有功能在 1 个系统；**第二阶段**商品和订单拆到 2 个子系统；**第三阶段**商品子系统和订单子系统各自再拆，共 **6 个子系统**。
     - 现实量级：淘宝内部大大小小的子系统「据说」已有**成百上千**个。

  7. **拆过头的补救：合（虚拟业务域）**
     - 触发条件：子系统达到**几百上千**时，出现新复杂度——**没有人能够说清楚业务的调用流程**，出问题排查特别复杂。
     - 解法仍是「合」：「合久必分、分久必合」，但**合的方式不一样**——按「**高内聚、低耦合**」原则，把职责关联比较强的子系统合成一个**虚拟业务域**，然后**通过网关对外统一呈现**，类似设计模式中的 **Facade 模式**。
     - 注意：这不是把子系统合并回大系统，而是加一层「域 + 网关」的呈现层。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 千万级 | 用户管理系统的一般用户量下限 |
  | 亿级 | QQ/微信/支付宝的用户量级 |
  | 2016 年、10 亿张/天 | 微信朋友圈每天上传图片数（存储云的容量依据） |
  | 几百 KB ~ 几 MB / 几分钟 | 用户上传文件的体积与时长特征 |
  | 3 | 用户上传数据的特征数（量大、体积小、访问有时效性） |
  | 3 | 自研推送的功能数（设备管理/连接管理/消息管理） |
  | 3 | 自研推送的挑战数（海量设备与用户、连接保活、消息管理） |
  | 1 → 2 → 6 | 电商样例三阶段的子系统数 |
  | 成百上千 | 淘宝子系统数量级 |
  | 几百上千 | 触发「合」（虚拟业务域）的子系统数量阈值 |

- **案例/数据**
  - CAS 架构、OAuth 2.0 → 用户管理的两个标准件（一个对内统一登录，一个对外授权）。
  - 2016 年微信朋友圈 10 亿张/天 → 存储云必须按「海量小文件 + 时效性访问」设计。
  - 淘宝内部「成百上千」个子系统 → 业务层拆分的真实规模（跨篇对照：手机淘宝首页第一屏 10+ 子业务、微信「发现」tab 7 个子业务，见第 49 讲）。
  - 淘宝成百上千子系统 → 虚拟业务域不是理论优雅，而是认知救急。
  - 图片的裁剪/压缩/美化/审核/水印 → 为什么「CDN + 小文件存储」相同却要拆成两个系统。

- **反例与坑**
  - 每个子系统各自管理用户 → 用户数据重复、无法统一登录（所以要 SSO）。
  - 开放平台用私有授权协议 → 漏洞多、第三方接入麻烦（应用 OAuth 2.0）。
  - 中小公司自研 Android 推送 → 连接保活是「黑科技最多」的地方，成本极高；不涉敏感数据应先用第三方。
  - 把用户量大当成技术难点 → 原文明确用户之间无强关联，简单负载均衡即可。
  - 图片云照抄存储云 → 忽略图片处理链（裁剪/压缩/审核/水印）。
  - 业务层想提炼「公共业务组件」 → 原文明确业务层提炼不出公共系统或组件，只能靠拆。
  - 无限拆下去 → 几百上千子系统后无人能说清调用流程，排障极难。
  - 用「合成大系统」来解决拆过头 → 原文否定此路，正解是「虚拟业务域 + 网关」。

- **原文金句**
  - 「用户管理虽然数据量巨大，但实现起来并不难。」
  - 「连接保活是整个消息推送设计中细节和黑科技最多的地方。」
  - 「这把『屠龙宝刀』就是『拆』，化整为零、分而治之。」
  - 「合久必分、分久必合。」

- **可迁移到知识库的主题**
  - 用户层能力清单（SSO / OAuth / 推送 / 图片云）与选型判据。
  - 「数据量大 ≠ 技术难」的判据：看数据之间有无强业务关联。
  - Android 推送的国内分叉与自研三功能/三挑战。
  - 业务层「拆 → 合（虚拟业务域 + 网关/Facade）」的完整闭环。

### 44丨互联网架构模板：“平台”技术

- **原标题**：44 | 互联网架构模板：“平台”技术

- **核心结论**
  平台的产生逻辑是一条直线：业务规模小、系统复杂度不高时，运维/测试/数据分析/管理由各系统各团队独立完成；规模变大、子系统变多后「继续采取各自为政的方式……重复工作非常多」，于是把这些**支撑功能**做成平台，目的是「**避免重复造轮子，减少不规范带来的沟通和协作成本**」。原文把平台分为四类：**运维平台、测试平台、数据平台、管理平台**。

- **完整判据/清单/步骤**

  1. **四类平台总表**

     | 平台 | 核心职责（原文） | 关键设计点 |
     |---|---|---|
     | 运维平台 | **配置、部署、监控、应急**（每个职责对应系统生命周期的一个阶段） | **四化：标准化、平台化、自动化、可视化** |
     | 测试平台 | 单元测试、集成测试、接口测试、性能测试 | 核心目的是提升测试效率从而提升产品质量，**设计关键就是自动化**；架构含用例/资源/任务/数据四模块 |
     | 数据平台 | **数据管理、数据分析、数据应用** | 数据管理四职责、数据分析四领域、数据应用在线/离线两类 |
     | 管理平台 | **权限管理**（身份认证 + 权限控制） | 面向业务系统、中间件系统、平台系统统一管理 |

  2. **运维平台：四职责（按生命周期阶段拆）**
     - **配置**：负责资源的管理——机器管理、IP 地址管理、虚拟机管理等。
     - **部署**：负责将系统发布到线上——包管理、灰度发布管理、回滚等。
     - **监控**：负责收集系统上线运行后的相关数据并进行监控，以便及时发现问题。
     - **应急**：负责系统出故障后的处理——停止程序、下线故障机器、切换 IP 等。

  3. **运维平台：四化（原文明确「四化」是核心设计要素）**
     - **标准化**：制定运维标准，规范**配置管理、部署流程、监控指标、应急能力**，各系统按标准实现，避免不同系统不同处理方式。
       - 原文的强判据：**「标准化是运维平台的基础，没有标准化就没有运维平台。」**
       - 例外处理（重要）：如果某个系统就是无法改造自己来满足运维标准，**不改系统，由中间方完成规范适配**。例：某系统用 RESTful 接口查性能指标，而运维标准是「性能数据通过日志定时上报」，那就写一个定时程序访问 RESTful 接口取数据，再转换为日志上报到运维平台。
     - **平台化**：在标准化基础上把运维操作都集成到平台，由平台完成运维工作。好处三条：
       1. 将运维标准**固化到平台中**，无须运维人员死记硬背；
       2. 平台提供简单方便的操作，相比人工操作**低效且容易出错**；
       3. 平台**可复用**——「一套运维平台可以支撑几百上千个业务系统」。
     - **自动化**：把大量重复操作固化，由系统自动完成。
       - 部署例子：一次手工部署需要「登录机器、上传包、解压包、备份旧系统、覆盖旧系统、启动新系统」；有平台后只需点「开始部署」，完成后通知部署人员。
       - 监控例子：平台实时收集数据并初步分析，异常时自动告警，**无须运维人员盯着数据看，或者写一大堆「grep + awk + sed」来分析日志**才能发现问题。
     - **可视化**：目的**提升数据查看效率**，尤其在故障应急时「时间就是生命……能减少 1 分钟的时间就可能挽回几十万元的损失」。
       - 原理类比**汽车仪表盘**：纯数字罗列让人眼花、难与具体情况联系；仪表盘通过指针偏离幅度与指向区域颜色，能一目了然看出是低速/中速/高速。
       - 相比简单数据罗列的三个优点：①能直观看到数据的**相关属性**（最小值 0、最大 100、单位 MPH）；②能**将数据的含义展示出来**（不同速度的颜色指示）；③能**将关联数据整合一起展示**（速度与里程）。

  4. **测试平台：四模块（自动化是目标，四模块是骨架）**
     - **用例管理**：测试自动化主要靠脚本或代码（单元测试用例是代码、接口测试用例可用 Python、可靠性测试用例可用 Shell）；为了能重复执行，平台需把用例管理起来，**管理维度：业务、系统、测试类型、用例代码**。例：「网购业务的订单系统的接口测试用例」。
     - **资源管理**：用例要放到具体运行环境才能执行；运行环境包括**硬件**（服务器、手机、平板电脑等）、**软件**（操作系统、数据库、Java 虚拟机等）、**业务系统**（被测试的系统）。除性能测试外，一般自动化测试对性能要求不高，所以**大部分测试平台都会用虚拟技术（虚拟机、Docker）充分利用硬件资源**。
     - **任务管理**：职责是把测试用例分配到具体资源上执行、跟踪执行情况。原文定位：**「任务管理是测试平台设计的核心，它将测试平台的各个部分串联起来从而完成自动化测试。」**
     - **数据管理**：记录执行时间、执行结果、用例执行期间的 CPU/内存占用等，作用三条：
       1. 展现当前用例的执行情况；
       2. 作为历史数据用于对比，**发现明显变化趋势**（例：某版本后单元测试覆盖率从 **90% 下降到 70%**）；
       3. 作为大数据的一部分做数据挖掘（例：某业务一年执行 **10000** 个用例，另一业务只执行 **1000** 个，两个业务规模和复杂度差不多，为何差异这么大？）。

  5. **数据平台：三层结构（管理 → 分析 → 应用）**
     - **数据管理（基础功能，四职责）**：
       - 数据采集：从业务系统搜集日志、用户行为、业务数据等并传送到数据平台；
       - 数据存储：把采集的数据存到平台，供后续分析；
       - 数据访问：对外提供各种读写协议（SQL、Hive、Key-Value 等）；
       - 数据安全：平台通常多业务共享，敏感数据需保护，防止被其他业务读取甚至修改。
     - **数据分析（四领域）**：
       - 数据统计：根据原始数据统计总览数据（PV、UV、交易额等）；
       - 数据挖掘：这里特指**传统**数据挖掘方式（有经验的分析人员基于数据仓库构建规则来发现隐含规律/现象/问题），经典案例是沃尔玛「啤酒与尿布」的关联关系；
       - 机器学习、深度学习：属于数据挖掘的具体实现方式，但与传统方式差异较大，**数据平台需为它们独立设计**。
     - **数据应用（在线 + 离线）**：在线如推荐、广告；离线如报表、欺诈检测、异常检测。
     - 前提判据（原文的重要限流）：数据应用发挥价值的前提是**有「大数据」**——数据规模达到一定程度，分析挖掘才能发现价值。**「如果数据没有达到一定规模，通常情况下做好数据统计就足够了」**，很多初创企业无须一开始就照 BAT 建数据平台。

  6. **管理平台：两段式权限模型**
     - 覆盖对象：业务系统（如淘宝网）、中间件系统（如 Kafka）、平台系统（如运维平台）——都需要权限管理，各自实现效率太低、重复工作多。
     - **身份认证**：确定当前操作人员身份，防止非法人员进入（如不允许匿名用户进入）；为避免每个系统各自管理用户，通常使用**企业账号**做统一认证和登录。
     - **权限控制**：根据身份确定操作权限，防止未经授权的人操作（如不允许研发人员进入财务系统查看别人的工资）。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 4 | 运维平台职责数（配置/部署/监控/应急） |
  | 4 | 运维平台设计要素「四化」数 |
  | 3 | 平台化好处条数 |
  | 3 | 可视化相比数据罗列的优点数 |
  | 3 | 测试平台数据管理的作用数 |
  | 4 | 测试平台模块数（用例/资源/任务/数据） |
  | 4 | 数据管理职责数与数据分析领域数 |

- **案例/数据**
  - 「一套运维平台支撑几百上千个业务系统」→ 平台化的规模收益。
  - RESTful 转日志上报的定时程序 → 标准化的兜底手段：改造中间方而不是改造系统。

  - 覆盖率 90%→70% → 数据管理做趋势对比的价值。
  - 啤酒与尿布 → 传统数据挖掘的经典定义案例。
  - 「研发不能看财务系统里别人的工资」→ 权限控制的边界示例。

- **反例与坑**
  - 支撑功能各自为政 → 重复工作、标准不一、沟通协作成本高（平台化的起点）。
  - 没有标准化就直接上平台 → 违背「没有标准化就没有运维平台」。
  - 用「改造系统」硬推标准化 → 原文给的正解是由中间方做规范适配。
  - 靠人工部署/人工盯监控/写 grep+awk+sed 查日志 → 低效且易错，应急时最致命。
  - 数据只有一堆数字没有可视化 → 故障应急时看不出来状态。
  - 初创企业照 BAT 建数据平台 → 数据规模不够，分析挖掘发现不了价值，做好统计即可。
  - 权限管理各系统自建 → 效率低、重复劳动、账号体系割裂。

- **原文金句**
  - 「标准化是运维平台的基础，没有标准化就没有运维平台。」
  - 「一套运维平台可以支撑几百上千个业务系统。」
  - 「任务管理是测试平台设计的核心，它将测试平台的各个部分串联起来从而完成自动化测试。」
  - 「只有当数据的规模达到一定程度，基于数据的分析、挖掘才能发现有价值的规律、现象、问题等。」

- **可迁移到知识库的主题**
  - 运维平台四职责 + 四化的完整设计清单。
  - 测试平台四模块（用例/资源/任务/数据）与自动化落地路径。
  - 数据平台三层（管理/分析/应用）与「先有数据规模，再谈数据应用」的判据。
  - 统一权限模型（认证 + 授权）与「企业账号」实践。
  - 平台化的通用收益论证（固化标准、降低出错、可复用）。

### 45丨架构重构内功心法第一式：有的放矢

- **原标题**：45 | 架构重构内功心法第一式：有的放矢

- **核心结论**
  架构重构的第一性问题不是「怎么改」，而是「**改哪几个**」。原文的判断：*「期望通过架构重构来解决所有问题当然是不现实的，所以架构师的首要任务是从一大堆纷繁复杂的问题中识别出真正要通过架构重构来解决的问题，集中力量快速解决。」* 这一式的名字叫「有的放矢」。

- **完整判据/清单/步骤**

  1. **先承认重构比新设计难（原文三条，属于前提认知）**

     | 难点 | 原文表述 | 与新设计的对比 |
     |---|---|---|
     | 业务已经上线，不能停下来 | 「给飞行中的波音 747 换引擎」 | 新设计业务还没上线，即使做砸了对业务也不会有太大影响 |
     | 关联方众多，牵一发动全身 | 不同关联方的资源投入程度、业务发展速度、对架构痛点的敏感度差异很大 | 新架构上线前对关联方没有影响 |
     | 旧架构的约束 | 必须在旧架构基础上进行，限制技术选择范围 | 新设计的技术选择余地大得多 |

     - 补充：即使推倒重来，新架构也受旧架构约束——**业务在旧架构上产生的数据不能推倒重来**，新架构必须考虑如何转换旧数据。

  2. **重构对架构师的三重能力要求（原文逐条）**
     - 业务上：能说服产品经理**暂缓甚至暂停业务**来进行架构重构。
     - 团队上：能与其他团队**达成一致的架构重构计划和步骤**。
     - 技术上：能给出**让技术团队认可的架构重构方案**。
     - 原文的总结句：「既要说得动老板，也要镇得住同事；既要技术攻关，又要协调资源；既要保证业务正常发展，又要在指定时间内完成目标。」

  3. **重构时机的识别信号（什么时候该怀疑是架构问题）**
     - 轻微表现：系统响应慢、数据错误、某些用户访问失败。
     - 严重表现：宕机、数据库瘫痪、数据丢失。
     - 另一种表现：**系统开发效率很低**。
     - 时间判据：一开始团队只针对具体问题逐个解决，但**持续较长时间（例如持续了半年甚至一年）情况都不见好转**，此时才可能想到是架构问题，由架构师牵头做重构分析。

  4. **第一式的核心动作：从问题清单里做减法**
     - 反例起点：架构师一上来搜集系统当前问题，汇总成一个 **100 行的 Excel 表格**，然后「看到这样一个表格就懵了」。
     - 正确动作：识别出**真正要通过架构重构解决的问题**，集中力量快速解决；其余问题另行处理。
     - 原文明确反对的两种姿态：**「新官上任三把火」的冲动**、**摊大饼式或运动式的重构和优化**。

  5. **「要不要重构」的判据（原文给出的简单做法，可直接照用）**
     - **假设现在需要从 0 开始设计当前系统，新架构和老架构是否类似？**
       - 差异不大 → 采取**系统优化**即可；
       - 差异很大 → 可能就要进行**系统重构**。
     - 原文同时承认这是判断题而非计算题：「判断到底是采取架构重构还是采取系统优化，可能不同的架构师和团队都有不同的看法。」

  6. **三个案例：问题 → 重构目标 → 效果（原文的重构目标写法可直接复用）**

     | 系统 | 原文指出的根因 | 重构目标 | 重构效果 |
     |---|---|---|---|
     | **M 系统**（后台管理系统，管理所有游戏相关数据） | 系统**耦合了 P 业务独有的数据和所有业务公用的数据**，导致可扩展性差（同一张表里一部分字段是所有业务公用的「游戏数据」，一部分是 P 业务「独有的数据」，改表时代码和逻辑都很复杂） | 将游戏数据和业务数据**拆分**，解开两者耦合，使两个系统都能独立快速发展 | 重构后 M 系统和 P 业务后台系统**每月上线版本数是重构前的 4 倍** |
     | **S 系统**（游戏接入核心系统，一旦故障大量玩家不能登录） | 不具备多中心能力；**数据库主库是全局单点**，一旦主库不可用，两个集群的写业务都不可用 | 实现**双中心**：任意一个机房都能提供完整服务，某机房故障时另一机房全部接管 | 可用性从 **3 个 9 提升到 4 个 9**；重构前最夸张的一个月有 **4 次**较大线上故障，重构后经历了机房交换机宕机、运营商线路故障、机柜断电等问题，对业务都没有大的影响 |
     | **X 系统**（创新业务主系统） | 业务快速尝试期「怎么方便怎么操作、怎么快速怎么做」，很多东西都「塞」到同一个系统，导致**已经改不动**；且所有功能在一个系统里，**一个功能出问题整站不可用**（如某功能把数据库拖慢，整站所有业务跟着慢） | 将各个功能**拆分到不同子系统**，降低单个系统的复杂度 | 各系统之间通过接口交互，虽然看似增加接口工作量，但各系统发展和开发速度比原来快很多，系统相对更简单，也不会出现某个子系统有问题就所有业务都有问题 |

     - **M 与 X 的关键辨析（原文特别强调，最容易被误判）**：两者「看起来比较类似，都是可扩展性存在问题」，但**根本原因不一样**——M 是**耦合了不同业务的数据**；X 是**把业务相关的所有功能都放在同一个系统中**。

  7. **非重构问题怎么办（原文的收尾步骤，不可省略）**
     - 重构完成后再启动多个**优化项目**去解决当初被排除的问题。
     - 此时优化**主要由团队内部完成**，和其他团队没有太多关联，**优化速度很快**。
     - 反证：如果**没有重构就做优化**，则每次优化都要拉一大堆关联业务团队来讨论方案，**效率非常低下**。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 747 | 「给飞行中的波音 747 换引擎」——重构风险的类比 |
  | 半年甚至一年 | 问题持续多久仍不见好转，才该怀疑架构 |
  | 100 行 | 问题汇总 Excel 的行数（反面起点：想一次解决所有问题） |
  | 4 倍 | M 系统重构后每月上线版本数的提升倍数 |
  | 3 个 9 → 4 个 9 | S 系统可用性提升（99.9% → 99.99%） |
  | 4 次/月 | S 系统重构前最夸张一个月的较大线上故障次数 |

- **案例/数据**
  - M 系统：表级字段耦合（公用游戏数据 + P 业务独有数据）→ 拆分后发布频率 4 倍。
  - S 系统：数据库主库单点 → 双中心 → 3 个 9 到 4 个 9，且扛住了交换机宕机/线路故障/机柜断电。
  - X 系统：功能全塞一个系统 → 拆子系统 → 开发变快、故障不再全站连坐。
  - M 系统当初被列出但**未纳入重构**的问题：数据经常出错、单机宕机后后台操作不能进行、性能差、界面丑、代码混乱——说明「有的放矢」是主动排除，不是看不见。

- **反例与坑**
  - 想用一次重构解决 100 个问题 → 「团队累死累活弄大半年，最后发现好像什么都做了，但每个问题都依然存在」。
  - 新官上任三把火 / 摊大饼式、运动式重构 → 原文点名反对。
  - 看到问题就想到重构 → 把系统优化能解决的事做成大工程。
  - 只做系统优化、从不重构 → 根因（耦合/单点）不动，问题反复。
  - 混淆 M 与 X 的根因 → 用「拆数据」去治「功能堆叠」，或用「拆功能」去治「数据耦合」，方案会跑偏。
  - 重构后不跟进优化项 → 当初排除的问题无人认领。

- **原文金句**
  - 「给飞行中的波音 747 换引擎。」
  - 「既要说得动老板，也要镇得住同事。」
  - 「假设我们现在需要从 0 开始设计当前系统，新架构和老架构是否类似？」
  - 「期望通过架构重构来解决所有问题当然是不现实的。」

- **可迁移到知识库的主题**
  - 「重构 or 优化」的二分判据（从 0 设计的相似度测试）。
  - 重构目标的三段式写法（根因 → 目标 → 可量化效果）。
  - 「耦合不同业务的数据」vs「功能堆叠在同一系统」两种可扩展性病因的鉴别。
  - 重构的准入条件（业务已上线、关联方多、旧架构约束）与所需的三重能力。
  - 先重构后优化的顺序论证（否则每次优化都要跨团队协调）。

### 46丨架构重构内功心法第二式：合纵连横

- **原标题**：46 | 架构重构内功心法第二式：合纵连横

- **核心结论**
  第二式解决的是「**怎么让人同意并配合**」。原文把沟通拆成两条线：**合纵 = 与利益相关方（多为非技术人员：产品、项目、运营）达成共识**，**连横 = 与相关/配合的技术系统团队达成协同**。两条线共用一个方法论：*「将技术语言转换为通俗语言，以事实说话，以数据说话，是沟通的关键！」* 注意原文特意声明「这里不是指办公室政治」。

- **完整判据/清单/步骤**

  1. **合纵：为什么必须做（前提判断）**
     - 架构重构是大动作、持续时间长、占用研发资源（含开发和测试），**不可避免地会影响业务功能开发**。
     - 所以推动重构启动需花费大量精力游说和沟通，目的是「让大家对于重构能够达成一致共识，避免重构过程中不必要的反复和争执」。

  2. **合纵的第一个坑：对非技术人员讲技术术语（原文三组对话，几乎可直接当反例教材）**

     | 技术人员说 | 对方内心反应（原文） | 术语失配原因 |
     |---|---|---|
     | 「我们系统现在的可扩展性太差了，改都改不动！」 | 「可扩展性，和扩胸运动有关吗？扩展什么呢？……不就是找个地方写代码嘛……」 | 抽象名词无对应业务感受 |
     | 「我们的可用性太差，现在才 3 个 9，业界都是 4 个 9！」 | 「什么是 3 个 9，三九感冒灵？4 个 9 和 3 个 9 不就是差个 9 嘛……」 | 指标口径未翻译成后果 |
     | 「我们系统设计不合理，A 业务和 B 业务耦合！」 | 「耦合，莲藕还是藕断丝连？A 业务和 B 业务本来就是互相依赖的呀……」 | 技术定义与日常语义冲突 |

     - 原文补充立场：这些示例「并无嘲笑产品、运营和项目人员不懂技术的意思」，只说明术语在跨领域沟通时很难达成共识。

  3. **合纵的第二个坑：凭感觉而不是凭数据说话**
     - 反面样本：技术人员说「系统耦合导致我们的开发效率很低」，但没有数据也没有样例，「其他人员很难有直观的印象」。

  4. **合纵的正确动作：把指标翻译成「业务能感知的损失」**
     - **M 系统的翻译法**：把「可扩展性」转换为「**版本开发速度很慢，每次设计都要考虑是否对门户有影响，是否要考虑对其他业务有影响**」。
     - **M 系统的数据取证**：收集 **1 个月**里的版本情况，发现——
       - 有几个版本**设计阶段讨论 1 周甚至 2 周，但开发只有 2 天**；
       - **一个月才做了 4 个版本**；
       - 最极端的一个版本：**讨论 2 周、开发 2 天，然后等了 1 个月才和门户系统一起上线**。
       - 效果：「项目经理和产品经理一听都被吓到了」。
     - **S 系统的翻译法**：不直接说可用性是几个 9，而是整理**线上故障的次数、每次影响的时长、影响的用户、客服的反馈意见**，再**拿其他系统的数据做对比**；结果「无论是产品人员、项目人员，还是运营人员，明显就看出系统的可用性有问题了」。

  5. **连横：两个真实阻力（原文点名）**
     - 阻力一：**「这对我有什么好处」**。
     - 阻力二：**「这部分我这边现在不急」**。
     - 原文先给了一个判断：连横因为「大家都是做技术的，有比较多的共同语言」，所以沟通相对容易一些，但也不是想推动就能推动。

  6. **连横的错误打法：把问题人为拔高**
     - 典型话术：「你应该站在部门的角度来考虑这个问题」「这对公司整体利益有帮助」。
     - 原文给出两条否定理由：①这种拔高**一般都比较虚，无法明确**，不同的人理解也不一样，无法达成共识；②如果对公司和部门有利、但对某个小组没用甚至不利，**那可能是因为目前的方案不够好**，还可以考虑另外的方案。

  7. **连横的正确策略（原文十二字方针）**
     - **「换位思考、合作双赢、关注长期」**。
     - 展开：站在对方角度思考，重构对他有什么好处、能帮他解决什么问题、带来什么收益。

  8. **连横的完整样板：C 系统案例（说服链条逐段还原）**
     - 背景：C 系统和 M 系统**通过数据库直连共用数据库**；重构方案是去掉两系统同时操作底层数据库，改为 **C 系统调用 M 系统接口来写数据库**。
     - 对方的初始抵触（客观代价）：C 系统短期改动很大，要**将十几个功能都从直接读写数据库改为跨系统接口调用**。
     - 说服的关键动作：分析出 C 系统其实也深受当前架构之苦，三条痛点——
       1. **数据经常出错要排查**（C 和 M 都在写同一个数据库，逻辑很难保证完全一致）；
       2. **要跟着 M 系统同步开发**（M 增加表或字段，C 要从数据库自己读出来，还要理解逻辑）；
       3. **C 系统要连两个数据库，出问题不好查**（C 自己还有数据库）。
     - 收益对齐：这些问题在 M 系统重构后都可以解决；短期有工作量，但**中长期肯定省很多事情**（如数据问题排查主要变成 M 系统的事，C 通过接口取数据、无须关注数据相关业务逻辑）。
     - 结果：C 系统很乐意一起做重构，且事实证明对两个系统都有很大好处。

  9. **连横的兜底手段（两种情况分别处理）**
     - 情况 A：**真的**出现「对公司或部门有利、对某个小组不利」→ 需要**协调更高层级的管理者**才能推动，**平级推动是比较难的**。
     - 情况 B：对方说「这部分我们现在不急」——
       - 先承认可能是找借口：「我也不排除这种可能性。但就算真的是找借口，那也是因为大家没有达成一致意见，可能对方不好意思直接拒绝」→ 按「这对我有什么好处」的方法处理。
       - 若对方真有更重要的业务 → **勉为其难也不好，还是「换位思考」**；可以等待，但**必须明确正式启动的时间**：「例如，3 个月后开始、6 月份开始，**千万不能说『以后』『等不忙的时候』这种无法明确的时间点**」。
     - 情况 C：计划与方案都要留弹性 —「除了计划上灵活一点，方案上也可以灵活一点」：可以先不做这个系统的重构，先把其他需要重构的做完；大部分需要重构的系统要做的事很多，**分阶段处理在风险规避、计划安排上更加灵活可控**。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 1 周甚至 2 周 vs 2 天 | M 系统单个版本「设计讨论时长 vs 开发时长」的失衡数据 |
  | 1 个月 / 4 个版本 | M 系统一个月的产出（版本数少得让对方震惊） |
  | 讨论 2 周 + 开发 2 天 + 等 1 个月 | 最极端版本的完整时间账 |
  | 十几个功能 | C 系统改造需从直连数据库改为接口调用的功能数 |
  | 3 个月后 / 6 月份 | 允许等待时必须给出的明确启动时点示例 |

- **案例/数据**
  - 「可扩展性」→「设计讨论 2 周、开发 2 天、一个月 4 个版本」→ 产品/项目经理被吓到：**同一事实换语言，说服力完全不同**。
  - S 系统用「故障次数 + 影响时长 + 影响用户 + 客服反馈 + 横向对比」替代「几个 9」→ 三个非技术角色同时看懂。
  - C 系统从「短期改十几个功能」的抵触到「很乐意一起做」→ 连横靠的是把对方的三条痛点摆出来并证明重构能消掉它们。
  - 平级推不动时必须上升 → 组织层面的现实约束（不是技术问题）。

- **反例与坑**
  - 用「可扩展性 / 3 个 9 / 耦合」直接对产品、项目、运营讲 → 鸡同鸭讲，甚至被怀疑在忽悠人。
  - 只有结论没有数据样例（「耦合导致效率低」）→ 对方没有直观印象。
  - 人为拔高到「部门角度 / 公司整体利益」→ 太虚、无法明确、无法达成共识；且可能掩盖方案本身不够好。
  - 把「这对我有什么好处」理解成对方自私 → 原文明确否定这种理解。
  - 对方说「不急」就直接放弃或硬压 → 要么错过真实原因（不好意思拒绝），要么伤关系。
  - 用「以后」「等不忙的时候」当时间承诺 → 等于没有承诺。
  - 试图平级推动「对某小组不利」的重构 → 原文：比较难，需要更高层级。

- **原文金句**
  - 「将技术语言转换为通俗语言，以事实说话，以数据说话，是沟通的关键！」
  - 「换位思考、合作双赢、关注长期。」
  - 「千万不能说『以后』『等不忙的时候』这种无法明确的时间点。」
  - 「如果对公司和部门有利，但对某个小组没用甚至不利，那么可能是因为目前的方案不够好。」

- **可迁移到知识库的主题**
  - 技术方案对非技术干系人的「翻译模板」（指标 → 时间账 → 横向对比）。
  - 跨团队推动的阻力分类与对应话术（好处 / 不急 / 对小组不利）。
  - 「拔高 vs 换位」两种说服路径的失效条件。
  - 重构立项沟通的材料清单（版本周期数据、故障统计、横向对比）。
  - 分阶段与明确时点作为「等待」的两条纪律。

### 47丨架构重构内功心法第三式：运筹帷幄

- **原标题**：47 | 架构重构内功心法第三式：运筹帷幄

- **核心结论**
  第三式解决「**识別出核心问题之后仍落不了地**」的问题：架构师还要识别**为解决这个问题需要做哪些准备事项、先解决哪些问题**，然后**分段实施**。原文一句话总结：*「将要解决的问题根据优先级、重要性、实施难度等划分为不同的阶段，每个阶段聚焦于一个整体的目标，集中精力和资源解决一类问题。」*

- **完整判据/清单/步骤**

  1. **为什么需要第三式（问题链）**
     - 需要重构的系统，基本都是「各种历史原因和历史问题没有及时处理，遗留下来逐渐积累，然后到了一个临界点，各种问题开始互相作用，集中爆发」。
     - 若只针对核心复杂度问题直接重构，会发现**还是无法落地**——「很多条件不具备或者有的问题没解决的情况下就是不能做架构重构」。

  2. **从 100 到 50：先做一次范围收敛**
     - 原文流程：从最初 **100 个**问题列表，挑选出其中 **50 个**需要在架构重构中解决；其中一些是**基础能力建设或准备工作**，另一些是**架构重构的核心工作**。
     - 这一步的产出是一张表（问题 + 归类），但**有了表还不等于能执行**。

  3. **反例：逐个解决 50 个问题的三宗罪（原文逐条）**
     - ①**没有区分优先级**：所有问题一视同仁，没有集中有限资源解决最重要/最关键的问题，「导致最后做了大半年，回头一看好像做了很多事情，但没取得什么阶段性的成果」。
     - ②**没有将问题分类**：相似问题没有统筹考虑，**方案可能出现反复**，效率不高。
     - ③**迫于业务版本压力专挑容易的做**：稍微难一点的问题因复杂度和投入被搁置，「达不到重构的真正目的」。

  4. **X 系统的真实教训（反例 → 正解）**
     - 反例阶段：加入前已整理过系统问题，大项包括**可用性、性能、安全、用户体验**，每个大项又包括**十几二十个子项**；实施时「基本上就是挑软柿子捏，觉得哪个好落地、占用资源不太多，就挑来做」，结果**做了半年，好像做了很多功能，但整体却没什么进展**。
     - 正解阶段：成立「**X 项目**」，在原有问题基础上识别出——
       - 架构的**核心复杂度**是「庞大的系统集成了太多功能，可扩展性不足」；
       - 但当前**可用性也不高**，经常出线上问题，耗费大量人力处理；
       - 因此识别出：**若要做架构重构，就需要系统处于一个比较稳定的状态**，不要经常出线上问题；
       - 而可用性不高的原因有三类：硬件资源不够用、某些系统组件使用不合理、架构上存在问题。
     - 阶段划分（原文以图给出，文字可还原为）：
       - **第一阶段「救火」**：解决机器过载、缓存响应慢、虚拟机挂死等问题导致的故障；
       - **第二阶段**：把多个底层系统切换到公司统一的公共组件，解决组件、外部系统故障导致的系统故障；
       - **第三阶段「服务化」**：真正的架构重构。
     - 补充：原文举例说明前两阶段会包含「业务降级、接入服务中心」这类准备事项。
     - 关键判断：**「真正的架构重构在第三阶段，第一阶段和第二阶段都是为了第三阶段做准备」**；若没有前两阶段铺垫直接做第三阶段，重构方案需要糅合前两阶段的事项（业务降级、接入服务中心等），**会导致方案不聚焦、异常复杂**。

  5. **S 系统的策略变体（同一方法、不同排序）**
     - 背景差异：S 系统主要问题就是可用性不高，**并没有系统耦合的问题**。
     - 策略：**「先救火、后优化、再重构」**。
       - 救火阶段：**扩容**（防止资源不足导致系统被压死）+ **Nginx 一键切换功能**（故障时快速切换）。
       - 优化阶段：解决一些明显的可用性问题（包括性能问题等）。
       - 重构阶段：把原来的**单点数据库改为多中心**。

  6. **「分段实施」的三条收益（原文）**
     - ①每个阶段都有明确目标，做完之后效果明显，团队信心足，后续推进更加容易；
     - ②每个阶段的工作量不会太大，**可以和业务并行**；
     - ③每个阶段的改动不会太大，**降低了总体风险**。

  7. **制定分段策略的四步法（原文明确「分享一下我的经验」）**
     - **第一步 优先级排序**：将**明显且又比较紧急**的事项优先落地，解决目前遇到的主要问题。
       - 例：扩容在 S 系统和 X 系统中都是最优先实施——不扩容则「系统隔三差五一会出现响应超时报警，一会来个过载报警，一会来个大面积不可用」，这些问题耗费大量人力和精力，**也就没法做其他事情了**。
     - **第二步 问题分类**：将问题按**性质**分类，每个阶段集中解决一类。
       - 例：X 系统第二阶段把多个底层系统切换到公司统一的公共组件，提升整体可用性。
     - **第三步 先易后难**（原文明确指出这与直觉相反）。
       - 被否定的直觉：「擒贼先擒王」——先攻克最难的问题，其他问题就不在话下。原文判为「看起来很美好，但实际上不可行」，理由三条：
         1. 一开始就做最难的部分，会发现**想解决这个最难的问题，要先解决其他容易的问题**；
         2. 最难的问题耗时都比较长、占用资源比较多，做了一两个月还没有进展和成果，**会影响相关人员对项目的评价和看法，也可能影响团队士气**；
         3. **刚开始的分析并不一定全面**，一开始对最难/最关键事项的判断可能会出错。
       - 「先易后难」的三条好处（一一对应）：
         1. 随着项目推进，简单问题逐渐解决，**原来看起来很难的问题已经不那么难了，甚至有的问题可能都消失了**；
         2. 能比较快地看到成果（成果可能不大），对后续推进和提升团队士气有很大好处；
         3. 随着项目进行，**原来遗漏的点、分析判断错误的点会逐渐显示出来**，可及时调整，有效保证整体重构效果。
     - **第四步 循序渐进**：评估每阶段耗时，可能有的阶段 1 个月、有的 6 个月；虽然这是客观事实，但「按照固定的步骤和节奏，更有利于项目推进」。
       - **硬阈值：每个阶段最少 1 个月，最长不要超过 3 个月；如果评估超过 3 个月的，那就再拆分为更多阶段。**
       - 排期技巧（X 项目）：先划分阶段，每阶段再分**任务子集**；任务子集较小时**多个可并行**，较大时**当成一个独立的里程碑**推进。

### 48丨再谈开源项目：如何选择、使用以及二次开发？

- **原标题**：48 | 再谈开源项目：如何选择、使用以及二次开发？

- **核心结论**
  开源不是「拿来就用」，而是一套**成本收益判断**：**选**要聚焦业务/成熟/运维三件事，**用**要做到深入研究、灰度发布、做好应急三道闸，**改**要「保持纯洁，加以包装」，最后才考虑「发明你要的轮子」。原文的比喻是全文纲领：*「不要重复发明轮子，但要找到合适的轮子！但别忘了，如果你开的是保时捷，可别找个拖拉机的轮子。」*

- **完整判据/清单/步骤**

  1. **前提：开源的真实风险画像**
     - 收益：DRY（Don't repeat yourself）原则，节省大量人力和时间，加快业务发展。
     - 风险：小的影响可能是**宕机半小时**，大的可能是**丢失几十万条数据**，甚至灾难性事故是**全部数据都丢失**。
     - 反向事实：开源项目反而是**最不遵守 DRY 原则**的——MySQL/PostgreSQL、MongoDB/Cassandra、Memcached/Redis、Gson/Jackson、Angular/React，「相似的轮子很多」，所以选择本身成了难题。

  2. **选 · 维度一：聚焦是否满足业务（而不是「是否优秀」）**
     - 判据：**聚焦于是否满足业务，不需要过于关注开源项目是否优秀**；不要因为担心选了 A 错过 B 而无所适从。
     - 量化口径（原文原话）：**「如果你的业务要求 1000 TPS，那么一个 20000 TPS 和 50000 TPS 的项目是没有区别的。」**
     - 对「TPS 以后涨了怎么办」的回答：架构可以不断演进，等真需要这么高时再重构，遵循架构设计原则中的「**合适原则**」和「**演化原则**」。
     - 反例 **Tokyo Tyrant（TT）**：本想「既可做缓存取代 Memcached，又有持久化存储可取代 MySQL」，于是在业务里大量使用，结果——
       1. **不能完全取代 MySQL**，于是有两份存储，设计时每次都要讨论决策「什么数据放 MySQL、什么数据放 TT」；
       2. 功能看起来高大上，但 **bug 不少且有致命 bug**（例如所有数据不可读，后来自己研究源码写工具才恢复了部分数据）；
       3. 功能强大但**需要较长时间熟悉细节**，不熟悉随便用很容易踩坑。
       - 反思结论：当时的业务 **Memcached + MySQL 完全能够满足**，而且大家都熟悉，**完全不需要引入 TT**。

  3. **选 · 维度二：聚焦是否成熟（考察三项）**
     - 前提认知：新项目总宣称性能更高、功能更强、引入更多新概念，但「都有意无意地隐藏了一个负面的问题：**更加不成熟**」；不要以为作者厉害就没有 bug——「Windows、Linux、MySQL 的开发者都是顶级的开发者，系统一样有很多 bug」。
     - 不成熟的代价：轻则宕机，重则**宕机后重启都恢复不了**，更严重是**数据丢失都找不回来**。
     - **三项考察清单**：
       1. **版本号**：除非特殊情况，**不要选 0.X 版本，至少选 1.X 版本，版本号越高越好**；
       2. **使用的公司数量**：一般项目会把采用自己的公司列在主页，**公司越大越好、数量越多越好**；
       3. **社区活跃度**：发帖数、回复数、问题处理速度等。

  4. **选 · 维度三：聚焦运维能力（最容易被忽略的维度）**
     - 现状批评：架构师选型基本只聚焦技术指标（性能、可用性、功能），「几乎不会去关注运维方面的能力」；但上生产后一旦出问题，「运维、研发、测试都只能干瞪眼，求菩萨保佑了」。
     - **三项考察清单**：
       1. **日志是否齐全**：有的项目日志只有寥寥启动停止几行，出了问题根本无法排查；
       2. **是否有命令行、管理控制台等维护工具**，能看到系统运行时的情况；
       3. **是否有故障检测和恢复能力**，例如告警、切换等。
     - 补充判据：如果是**开源库**（如 Netty 这种网络库），本身不具备运维能力，则需在使用时把关键信息通过日志记录下来（例如在 Netty 的 Handler 里打印关键日志）。

  5. **用 · 闸门一：深入研究，仔细测试**
     - 反例批评：「看了几个 Demo，把程序跑起来就开始部署到线上」，如同「看了一下开车指南……然后就开车上路了，其实是非常危险的」。
     - **五步研究/测试清单**：
       1. 通读开源项目的**设计文档或白皮书**，了解设计原理；
       2. **核对每个配置项的作用和影响，识别出关键配置项**；
       3. 进行**多种场景的性能测试**；
       4. 进行**压力测试，连续跑几天**，观察 CPU、内存、磁盘 I/O 等指标波动；
       5. 进行**故障测试：kill、断电、拔网线、重启 100 次以上、切换**等。
     - 反例 **Elasticsearch**：团队基本拿来就用，**倒排索引是什么都不太清楚**，配置全用默认值，跑起来就上线；结果遇到**节点 ping 时间太长、剔除异常节点太慢，导致整站访问挂掉**。
     - 反例 **MySQL**：很多团队最初没怎么研究，业务抱怨 MySQL 太慢；定位后发现**最关键的几个参数（`innodb_buffer_pool_size`、`sync_binlog`、`innodb_log_file_size` 等）都没有配置或者配置错误**。

  6. **用 · 闸门二：小心应用，灰度发布**
     - 核心论点：**研究再深入、测试再仔细，都只能降低风险，不可能完全覆盖所有线上场景**。
     - 反例仍是 TT：「其实我们在应用之前专门安排一个高手看源码、做测试，做了大约 1 个月，但最后上线还是遇到各种问题」；原文结论是「线上生产环境的复杂度，真的不是测试能够覆盖的」。
     - 落地纪律：**时刻对线上环境和风险要有敬畏之心**；经验是「**先在非核心的业务上用，然后有经验后慢慢扩展**」。

  7. **用 · 闸门三：做好应急，以防万一**
     - 论点：即使前面做得非常完善，也可能「运气不好遇到一个之前全世界的使用者从来没遇到的 bug」，导致业务无法恢复；**存储方面尤其致命**。
     - 反例 **MongoDB 丢数据**：某业务使用 MongoDB，宕机后**部分数据丢失、无法恢复、也没有其他备份**，人工恢复都无能为力，只能「接一个用户投诉处理一个」，导致 DBA 和运维从此反对用 MongoDB。
     - 落地建议：对重要业务或数据，**最好有另外一个比较成熟的方案做备份**，尤其是数据存储——例如用 MongoDB 或 Redis 时，**可以用 MySQL 做备份存储**；「这样做虽然复杂度和成本高一些，但关键时刻能够救命」。

  8. **改 · 策略一：保持纯洁，加以包装（首选）**
     - 为什么不要大改：①投入太大（「Redis 这种级别的开源项目，真要自己改，至少要投入 2 个人，搞 1 个月以上」）；②**失去跟随原项目演进的能力**（改得太多，即使原项目继续演进也无法合并，因为差异太大）。
     - 正确做法：**不要改动原系统，而是开发辅助系统**——监控、报警、负载均衡、管理等。
     - 样板：要给 Redis 加集群功能，**不要改 Redis 本身，而是增加一个 proxy 层**实现（Twitter 的 **Twemproxy** 就是这样做的）；Redis 到 **3.0** 后本身提供了集群功能，原有方案**简单切换到 Redis 3.0 即可**。
     - 若实在要改原系统：建议**直接给开源项目提需求或者 bug**；弊端是**响应比较缓慢**——急则自己改，不急则做好备份或应急手段即可。

  9. **改 · 策略二：发明你要的轮子（有条件的正解）**
     - 前提判断：选与不选开源项目，「核心还是一个成本和收益的问题」；「最主要的问题是：**没有完全适合你的轮子**」。
     - 软件与硬件的差异（原文的底层论证）：硬件领域造一个尺寸与众不同的轮子，其他车都用不上，「工艺再高、质量再好也是白费」；软件领域没有绝对工业标准，可以造很多相似轮子且基本能到处用（缓存从 Memcached 换 Redis 不会有太大问题）。
     - 通用方案的局限：开源项目为大规模应用考虑的是**通用处理方案**，而不同业务差异较大，通用方案不一定完美适配。
     - 案例（自研缓存框架）：Memcached 通过一致性 Hash 提供集群，但「我们的业务缓存如果有一台宕机，整个业务可能就被拖慢了」，需要**缓存备份**能力，而 Memcached 没有、Redis 当时也没有集群功能 → **投入 2~4 个人、约 2 个月**，基于 **LevelDB 的原理**自研了一套缓存框架，支持**存储、备份、集群**，后来又增加**跨机房同步**，「很大程度上提升了业务的可用性水平」。
     - 结论：**如果有钱有人有时间，投入人力去重复发明完美符合自己业务特点的轮子也是很好的选择**（BAT 等财大气粗的公司都是这样做的，否则也不会有那么多好用的开源项目）。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 半小时 / 几十万条 / 全部 | 开源踩坑的三级损失量级 |
  | 1000 vs 20000 / 50000 TPS | 「业务够用即最优」的量化判据 |
  | 0.X / 1.X | 版本号成熟度门槛（不选 0.X，至少 1.X） |
  | 重启 100 次以上 | 故障测试的强度要求 |
  | 连续跑几天 | 压力测试的持续时间要求 |
  | 约 1 个月 | TT 上线前「高手看源码 + 测试」的投入，仍然出问题（说明测试有天花板） |
  | 2 人 / 1 个月以上 | 大改 Redis 级别项目的投入估算 |
  | 2~4 人 / 约 2 个月 | 自研缓存框架的实际投入 |
  | Redis 3.0 | 自带集群的版本节点（说明「等上游」有时是最优解） |

- **案例/数据**
  - TT 三条罪（两份存储、致命 bug 数据不可读、细节学习成本高）→ 选型只看「功能强大」的代价；业务本可用 Memcached + MySQL 满足。
  - Elasticsearch 全默认配置上线 → 节点 ping 长、剔除慢 → 整站挂：**「配置项即风险点」**。
  - MySQL 三个关键参数未配 → 性能被误判为「MySQL 太慢」：**先核对配置再谈选型**。
  - MongoDB 无备份丢数据 → DBA/运维从此反对：**一次数据事故会锁定技术栈**。
  - Twemproxy 加 proxy 层 vs 改 Redis 内核 → 「包装优先」的标准范式。
  - 2~4 人 2 个月自研缓存框架（LevelDB 原理）→ 有钱有人有时间时自研是正解。

- **反例与坑**
  - 看了几个 Demo 就上生产（「看了开车指南就上路」）。
  - 用「功能更强/概念更新」作为选型依据，忽略成熟度（0.X 版本、无公司列表、社区冷清）。
  - 只看性能/功能，不看日志、维护工具、故障检测与恢复。
  - 期待开源项目「完全替代」现有存储 → TT 的两份存储困境。
  - 认为「高手看源码 + 测 1 个月」就能覆盖线上 → 原文明确不可能。
  - 存储类开源项目不做第二套备份 → MongoDB 丢数据后无法恢复。
  - 直接改开源项目内核 → 投入大 + 失去跟随上游演进的能力。
  - 用「提 issue/需求」当唯一路径 → 响应缓慢，急事会误期。

- **原文金句**
  - 「不要重复发明轮子，但要找到合适的轮子！但别忘了，如果你开的是保时捷，可别找个拖拉机的轮子。」
  - 「如果你的业务要求 1000 TPS，那么一个 20000 TPS 和 50000 TPS 的项目是没有区别的。」
  - 「再怎么深入地研究，再怎么仔细地测试，都只能降低风险，但不可能完全覆盖所有线上场景。」
  - 「时刻对线上环境和风险要有敬畏之心，小心驶得万年船。」

- **可迁移到知识库的主题**
  - 开源选型三维清单（业务匹配 / 成熟度 / 运维能力）与各自的可核查项。
  - 开源上线三道闸（研究测试 → 灰度 → 应急备份）与对应检查表。
  - 「保持纯洁，加以包装」的二次开发范式（proxy/辅助系统 vs 改内核）。
  - 「自研轮子」的成本收益判据与投入量级参考。
  - 配置项审计（关键参数清单）作为引入开源组件的标准动作。

### 49丨谈谈App架构的演进

- **原标题**：49 | 谈谈App架构的演进

- **核心结论**
  App 架构史是「**当期主要复杂度换了，架构就得换**」的连续剧：Web App（快 + 便宜）→ 原生 App（体验）→ Hybrid（快 + 体验的折中）→ 组件化 & 容器化（超级 App 的可扩展性）→ 跨平台（省人力）。原文用它验证了四条架构理念：*「架构是系统的顶层结构」*、*「架构设计的主要目的是为了解决软件系统复杂度带来的问题」*、*「架构设计需要遵循三个主要原则：合适原则、简单原则、演化原则」*、*「架构设计首先要掌握业界已经成熟的各种架构模式，然后再进行优化、调整、创新」*。

- **完整判据/清单/步骤**

  1. **五个阶段的完整对照表（阶段 → 当期主要复杂度 → 架构手段 → 遵循的原则）**

     | 阶段 | 当期主要复杂度 | 架构形态与做法 | 遵循的原则 | 时间/证据 |
     |---|---|---|---|---|
     | **Web App** | 「快速开发」+「低成本」 | **包壳架构**：在 Web 业务上包一个 App 壳，业务逻辑完全还是 Web 实现，壳只完成安装功能，用户看起来像在用 App，实际和浏览器访问 PC 网站没太大差别 | **合适原则 + 简单原则** | 大约 **2010 年前后**；淘宝 **2013 年**才决定「All in 无线」 |
     | **原生 App** | **用户体验** | 用原生开发保证体验；可利用移动设备在用户体验方面的优化与技术优势 | **演化原则** | 大约 **2013 年前后**开始快速发展；Android/iOS 工程师「就像现在的人工智能工程师一样非常抢手」 |
     | **Hybrid App** | 复杂度**回到「快速开发」** | 按业务要求分流：**体验要求高的用原生实现，体验要求不高的用 Web 实现**；核心设计思想即此分流 | **合适原则** | 三平台（Android、iOS、Windows Phone）原生完全不兼容，同功能要三份开发 |
     | **组件化 & 容器化** | 超级 App 的**可扩展性**（几十上百个业务集中在一个 App，各自独立团队、持续扩展） | 拆分为众多**组件**，组件遵循预先制定好的**规范**，**独立开发、独立测试、独立上线**；组件间依赖通过**消息系统**通信，实现组件隔离 | **演化原则** | 手机淘宝首页第一屏初步估计 **10 个以上**子业务；微信「发现」tab **7 个**子业务 |
     | **跨平台 App** | **人力投入**（同功能 Android、iOS 各开发一遍） | React Native（Facebook）、Weex（阿里）、Flutter（Google） | 违背**简单原则**（增加了方案复杂度） | Airbnb 宣布放弃 React Native，回归原生技术 |

  2. **阶段一 Web App 的决策逻辑（原文的因果链）**
     - 业务背景：2010 年前后移动互联网发展迅速，但受**用户设备、移动网络速度**约束，PC 互联网仍是主流，移动互联网是新鲜事物，前景「当年大家也不一定能完全看得清楚」。
     - 组织证据：淘宝 2013 年才开始决定「All in 无线」——即在此之前移动端只是尝试。
     - 尝试性业务的要求：**快速 + 低成本**；当时 Android、iOS 虽已能开发 App，但**原生开发成本太高**。
     - 因此 Web App 包壳架构成为首选尝试架构，它主要解决「快速开发」和「低成本」两个复杂度问题。

  3. **阶段二原生 App 的触发条件（三条劣势逐条）**
     - ①**移动设备的发展速度远远超过 Web 技术的发展速度**，Web App 的体验相比原生差距越来越明显；
     - ②移动互联网趋势越来越明显，**App 承载的业务逻辑越来越复杂**，进一步加剧 Web App 的体验问题；
     - ③移动设备在用户体验方面有很多优化和改进，**Web App 无法利用这些技术优势，只有原生 App 才能利用**。
     - 结论：复杂度从「快速开发 + 低成本」转向「**用户体验**」，保证体验用原生最合适，遵循**演化原则**。

  4. **阶段三 Hybrid 的成立条件（原文的关键限定）**
     - 背景：移动互联网已成明确大趋势，团队要考虑的不是「要不要转移动互联网」，而是「**如何在移动互联网更具竞争力**」；竞争方式是「看谁更快抓住用户需求和痛点」，复杂度**又回到「快速开发」**。
     - 原生痛点：Android、iOS、Windows Phone 三个主流平台原生开发**完全不能兼容**，同样功能要三平台重复开发，且每个平台还有差异，「因此自然快不起来」。
     - 解法与其边界：Web 的体验还是远远不如原生，「其实**没有办法完美解决**」，但可以**按业务要求选取不同方案**。
     - 原文的精确措辞（易被误读，务必保留）：Hybrid「能够较好的**平衡**『用户体验』和『快速开发』两个复杂度问题（注意是『平衡』，**不是『同时解决』**）」。

  5. **阶段四组件化 & 容器化的前提与机制**
     - 前提：只有**超级 App**（业务规模大、业务复杂，「用户看来可能是一个 App，但事实上承载了几十上百个业务」）才需要。
     - **App 与后端系统的本质区别（原文的核心论证，决定了「拆」的边界）**：

       | 维度 | App / 前端 | 后端系统 |
       |---|---|---|
       | 是否面向用户 | 面向用户 | 不面向用户 |
       | 拆分后的呈现 | 再怎么拆，对用户**只能呈现同一个 App**，不可能拆成几十个独立 App | 采用微服务后可拆分为**几百上千个子服务**都没有问题 |
       | 技术栈 | 再怎么拆，**技术栈是一样的**，不然没法集成在一个 App 里 | 不同微服务**可以用不同的技术栈**开发 |

     - 机制：组件遵循预先制定好的规范，**独立开发、独立测试、独立上线**；若组件依赖其他组件，**组件之间通过消息系统通信**，以此实现组件隔离，避免团队互相依赖影响，提升团队开发效率和系统可扩展性。
     - **组件化 vs 容器化的唯一区别（原文明确）**：规范、拆分、团队协作都一样，**区别在发布方式**——
       - **组件化 = 静态发布**：所有组件各自独立开发测试，然后**跟随 App 的某个版本统一上线**；
       - **容器化 = 动态发布**：容器可以**动态加载**组件，组件准备好了直接发布，容器会动态更新组件，**无需等待某个版本才能上线**。
     - 适用范围判据（原文明确）：遵循**演化原则**，只有业务复杂度发展到一定规模后才适应，所以「大厂应用这个架构的比较多，而中小公司的 App，业务没那么复杂，其实并不一定需要采用组件化和容器化架构」。
     - 延伸阅读：手机淘宝参考《Atlas：手淘 Native 容器化框架和思考》，微信参考《微信 Android 客户端架构演进之路》。

  6. **阶段五跨平台的现状判断（原文的谨慎立场）**
     - 驱动力：站企业角度希望减少人力投入成本；跨平台方案可避免「Android 开发一遍、iOS 也要开发一遍」。
     - 代表方案：Facebook 的 **React Native**、阿里的 **Weex**、Google 的 **Flutter**。
     - 判断：**「目前这几个方案都不算很成熟」**，且在用户体验方面与原生 App 仍有差距；证据是 **Airbnb 宣布放弃使用 React Native，回归使用原生技术**。
     - 原文附带：前端情况类似，可参考玉伯《Web 研发模式演变》。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 2010 年前后 | Web App 为主流尝试架构的时间点 |
  | 2013 年 | 淘宝决定「All in 无线」的年份；也是原生 App 快速发展的年份 |
  | 3 | 当年三大主流平台数（Android、iOS、Windows Phone） |
  | 10 个以上 | 手机淘宝首页第一屏的子业务数 |
  | 7 个 | 微信「发现」tab 的子业务数 |
  | 几十上百 | 超级 App 承载的业务数 |
  | 几百上千 | 后端微服务可拆分的子服务数（与 App 的对照） |

- **案例/数据**
  - 淘宝 2013 年「All in 无线」→ 解释为什么 2010 年前后 Web App 是理性选择（当时移动端只是尝试）。
  - 手机淘宝首页 10+ 子业务、微信「发现」7 个子业务 → 超级 App 的可扩展性复杂度是真实的。
  - Airbnb 放弃 React Native → 跨平台方案尚未成熟的直接证据。
  - 三平台（Android/iOS/Windows Phone）不兼容 → Hybrid 存在的根因（同功能三份开发）。

- **反例与坑**
  - 在尝试性业务上用原生开发 → 成本太高，违背合适/简单原则。
  - 在体验敏感业务上继续用 Web App → 移动设备与 Web 技术差距越拉越大，体验问题会变成主要矛盾。
  - 认为 Hybrid 能「同时解决」体验与速度 → 原文明确只是「平衡」，无法完美解决。
  - 把后端微服务的拆法照搬到 App → App 不能拆成几十个独立 App，技术栈也必须统一。
  - 中小公司上组件化/容器化 → 业务复杂度不够，违背演化原则。
  - 现在就押注跨平台方案 → 不成熟 + 体验差距，已有公司回退。

- **原文金句**
  - 「App 再怎么拆，对用户还是只能呈现同一个 App，不可能将一个 App 拆分为几十个独立 App。」
  - 「Hybrid App 能够较好的平衡『用户体验』和『快速开发』两个复杂度问题（注意是『平衡』，不是『同时解决』）。」
  - 「架构设计的主要目的是为了解决软件系统复杂度带来的问题。」
  - 「架构设计需要遵循三个主要原则：合适原则、简单原则、演化原则。」

- **可迁移到知识库的主题**
  - 客户端架构演进五阶段表（复杂度 → 形态 → 原则）。
  - 超级 App 的组件化/容器化判据，以及「静态发布 vs 动态发布」的分界。
  - App 与后端在「可拆分粒度 / 技术栈自由度」上的本质差异（拆分解空间）。
  - 跨平台方案的成熟度评估与回退案例。
  - 「合适/简单/演化」三原则在客户端场景的实例化。

  **各章写作要求（原文的方括号说明 + 案例示范）**

  1. **1. 需求介绍** — 要求：描述需求的**背景、目标、范围**。
     - 正例（案例写法）：先说业务现状（业务拆分出的子系统越来越多、目前系统间都是同步调用），再列三个具体问题——**性能问题**（用户发一条微博后，微博发布子系统需同步调用「统计子系统」「审核子系统」「奖励子系统」等共 **8 个**子系统，性能很低）、**耦合问题**（新增「广告子系统」时，广告子系统要开发新接口给微博发布子系统调用）、**效率问题**（各子系统接口参数和实现有细微差别，每次都要重新设计接口和联调，开发与测试团队重复工作量大），最后给结论（需要引入消息队列做系统解耦，把同步调用改为异步通知）。
     - 反例：只写「要做一个消息队列」而不写背景与问题量化（原文用「8 个子系统同步调用」把痛点写实）。

  2. **2. 需求分析 · 5W** — 要求：Who、When、What、Why、Where 五项逐一定义。
     - **Who**：需求利益干系人，包括开发者、使用者、购买者、决策者等。
     - **When**：需求使用时间，包括季节、时间、里程碑等。
     - **What**：需求的产出是什么，包括系统、数据、文件、开发库、平台等。
     - **Where**：需求的应用场景，包括国家、地点、环境等（例如测试平台只会在测试环境使用）。
     - **Why**：需求需要解决的问题，通常和需求背景相关。
     - 案例填写：Who = 业务子系统（发消息/收消息）；When = 子系统需要发送异步通知时；What = 需要开发消息队列系统；Where = 开发、测试、生产环境都需要部署；Why = 将子系统解耦，把同步调用改为异步通知。

  3. **2. 需求分析 · 1H** — 要求：**这里的 How 不是设计方案也不是架构方案，而是关键业务流程**。
     - 原文补充：消息队列这部分内容很简单，但有的业务系统 1H 就是具体的用例（举例：可尝试写 ATM 机取款的业务流程）；如果是复杂业务系统，这部分**也可以独立成「用例文档」**。
     - 案例：消息队列两大核心功能——业务子系统发送消息给消息队列；业务子系统从消息队列获取消息。

  4. **2. 需求分析 · 8C** — 要求：写清 8 个约束和限制（Constraints）。
     - **8C 清单**：性能 Performance、成本 Cost、时间 Time、可靠性 Reliability、安全性 Security、合规性 Compliance、技术性 Technology、兼容性 Compatibility。
     - **原文的关键提醒（写作纪律）**：需求中涉及的性能、成本、可靠性等**仅仅是利益关联方提出的诉求，不一定准确**；如果经过分析有的约束没有必要，或成本太高、难度太大，**这些约束是可以调整的**。
     - 案例填写（逐项示范）：性能 = 需要达到 Kafka 的性能水平；成本 = 参考 XX 公司设计方案，**不超过 10 台服务器**；时间 = 期望 **3 个月内**上线第一个版本，在两个业务尝试使用；可靠性 = 需要达到 **99.99%**；安全性 = 仅在生产环境内网使用，无需考虑网络安全；如消息含敏感信息由发送方自行加密，消息队列本身不考虑通用加密；合规性 = 按公司目前的 **DevOps 规范**开发；技术性 = 团队主要研发人员是 Java，**最好用 Java 开发**；兼容性 = 之前没有类似系统，**无需考虑兼容性**。

  5. **3. 复杂度分析** — 要求：分析需求的复杂度，常见的有高可用、高性能、可扩展等。
     - **原文的写作纪律（极重要）**：「文档的内容省略了分析过程，实际操作的时候**每个约束和限制都要有详细的逻辑推导，避免完全拍脑袋式决策**」。
     - 高可用（案例的推导方式）：按业务后果分级——微博子系统若消息丢了导致没有审核、触犯国家法律法规，非常严重；等级子系统若用户达到等级后没拿到奖品和专属服务，VIP 用户不满导致流失和收入损失，虽然关键但**没有审核子系统丢消息那么严重**。综合结论：消息队列需要高可用性，**消息写入、消息存储、消息读取都需要保证高可用**。
     - 高性能（案例的完整推算，见「数字与阈值」）：结论是 TPS 1380 并不高，但 **QPS 13800 已经比较高了，因此高性能读取是复杂度之一**。
     - 可扩展：消息队列功能很明确、基本无须扩展，**因此可扩展性不是关键复杂度**（即「不构成复杂度」也要写明结论）。

  6. **4. 备选方案** — 要求：**至少 3 个**备选方案，每个方案描述**关键实现**，**无须描述具体实现细节**。
     - 案例的三个方案：①直接引入开源 Kafka；②集群 + MySQL 存储；③集群 + 自研存储。

  7. **5. 备选方案评估** — 要求：**备选方案 360 度环评**；并注意「**备选方案评估的内容会根据评估会议的结果进行修改**，也就是说架构师首先给出自己的备选方案评估，然后举行备选方案评估会议，再根据会议结论修改备选方案文档」。

  **各章写作要求与正反例**

  1. **1. 总体方案 / 2. 架构总览** — 要求：从整体上描述方案结构，**核心内容是架构图 + 针对架构图的描述**（模块/子系统职责、核心流程）。
     - 正例（案例的「架构关键设计点」四条，可作为写法模板）：
       1. 采用**数据分散集群**的架构，集群中的服务器进行分组，每个分组存储一部分消息数据；
       2. 每个分组包含**一台主 MySQL 和一台备 MySQL**，分组内主备数据复制，**分组间数据不同步**；
       3. 正常情况下，分组内的**主服务器**对外提供消息写入和读取服务，**备服务器不对外提供服务**；主服务器宕机时，备服务器对外提供**消息读取**服务；
       4. 客户端采取**轮询**策略写入和读取消息。
     - 反例：只有一张图没有职责与关键设计点说明（原文模板明确要求「以及针对架构图的描述」）。

  2. **3. 核心流程** — 要求：给出关键业务流程（案例为消息发送流程、消息读取流程）；原文在此处省略了流程描述。

  3. **4. 详细设计 · 高可用设计** — 要求：按可靠性链路拆成三段分别写（发送 / 存储 / 读取），每段都要写清「做不到时怎么办」。
     - 消息发送可靠性（正例：机制 + 兜底 + 明确不做的部分）：业务服务器嵌入 SDK，SDK 支持**轮询发送**；某分组主服务器发不出去时，SDK 挑下一个分组主服务器重发，**依次尝试所有主服务器直到成功**；若全部失败，SDK 可**缓存消息**也可**直接丢弃**，具体策略在启动 SDK 时通过配置指定。原文同时声明局限：若 SDK 缓存了消息未发送、恰好业务服务器重启，**缓存消息将永久丢失，这种情况 SDK 不做处理**，业务方需对非常关键的消息自己实现永久存储。
     - 消息存储可靠性：消息存 MySQL，每组一主一备，主备复制保证存储高可用；若主备出现复制延迟、恰好主服务器宕机导致数据无法恢复，则**部分消息永久丢失，这种情况不做针对性设计**，由 **DBA 监控主备复制延迟，超过 30 秒告警并及时处理**。
     - 消息读取可靠性（正例：角色分工 + 状态判定落到具体机制）：每组一主一备，主服务器支持发送和读取，备服务器**只支持读取**；主正常时备不对外服务，只有备判断主故障时才对外提供读取服务。主备角色与分组信息**通过配置指定**，状态判断和决策**通过 ZooKeeper**：主备启动时分别连 ZooKeeper，在 `/MQ/Server/[group]` 下建 **EPHEMERAL** 节点（group1 的主节点为 `/MQ/Server/group1/master`，备节点为 `/MQ/Server/group1/slave`）；节点超时时间可配置，**默认为 10 秒**。
  4. **4. 详细设计 · 高性能设计** — 要求：写具体设计（案例此处省略）。
  5. **4. 详细设计 · 可扩展设计** — 要求与正反例（原文最实用的一条写作纪律）：
     - **正例**：如果方案不涉及，**简单写上「无」**，「表示设计者有考虑但不需要设计」。
     - **反例**：**完全不写**——「否则如果完全不写的话，方案评审的时候可能会被认为是遗漏了设计点」。
     - 案例即写「无」。
  6. **4. 详细设计 · 安全设计** — 要求：拆成身份识别与权限控制两部分。
     - 身份识别：给业务子系统分配**身份标识和接入 key**，SDK 首先建连接并做身份校验，服务器**中断校验不通过的连接**；因此任何子系统要接入都必须先申请身份标识和 key，以此**防止恶意系统任意接入**。
     - 队列权限：某些队列信息敏感，只允许部分子系统发送或读取；**队列权限保存在配置文件中**，收到发送/读取请求时先根据子系统身份标识和配置的权限信息判断，无权限则拒绝服务。
  7. **4. 详细设计 · 其他设计 / 部署方案** — 要求：其他设计包括上述以外的考虑点（如指定开发语言、符合公司某些标准），**篇幅较长也可以独立描述**。
     - 案例「其他设计」：接入公司已有的**运维平台**发布和部署；输出日志给公司已有的**监控平台**，监控健康状态（发送消息数量、消息大小、积压消息数量等），详细监控指标在后续设计方案中列出。
     - 案例「部署方案」：服务器和数据库服务器**混布**——一台服务器上部署同一分组的主服务器和主 MySQL，或备服务器和备 MySQL；理由是消息队列服务器主要 **CPU 密集型**、MySQL 是**磁盘密集型**，混布互相影响几率不大。硬件基本要求：**32 核 48G 内存 512G SSD**；考虑到动态扩容需求不高且对性能要求较高，**使用物理服务器，不采用虚拟机**。
  8. **5. 架构演进规划** — 要求：需求虽完善，但一次做完项目周期可能很长，因此**分阶段实施**（第一期、第二期……）。
     - 案例三期：**第一期**实现消息发送、权限控制功能，预计 **3 个月**；**第二期**实现消息读取功能，预计 **1 个月**；**第三期**实现主备基于 ZooKeeper 切换的功能，预计 **2 周**。

- **数字与阈值**
  | 数字 | 用途 |
  |---|---|
  | 1000 万条/天 | 前浪微博用户每天发送的微博数（写入基数） |
  | 10 个子系统 | 平均一条消息被读取的次数 |
  | 1 亿次/天 | 其他子系统读取消息总量 |
  | 115 条/秒、1150 条/秒 | 按一天折算的平均写入/读取速率 |
  | 3 倍 | 峰值对平均值的倍数 → TPS 345、QPS 3450 |
  | 4 倍 | 设计目标对峰值的倍数（预留容量）→ **TPS 1380、QPS 13800** |
  | 8 个 | 微博发布需同步调用的子系统数（性能问题量化） |
  | 至少 3 个 | 备选方案数量下限 |
  | 99.99% | 消息队列可靠性约束 |
  | 10 台服务器 | 成本约束上限 |
  | 3 个月 | 第一版上线时间约束；也是第一期工期 |

- **案例/数据**

  - TPS/QPS 推导（1000 万 → 115/1150 → ×3 → ×4）→ 复杂度分析里「有推导」与「拍脑袋」的分水岭。

  - 混布（CPU 密集 + 磁盘密集）→ 部署方案的论证要给出资源特征理由。

- **反例与坑**
  - 备选方案少于 3 个 → 违背模板硬要求。
  - 备选方案里写具体实现细节 → 原文明确「无须描述具体实现细节」。
  - 复杂度分析只写结论不写推导 → 「完全拍脑袋式决策」。
  - 把 8C 当铁律照抄 → 原文明确约束「不一定准确」，可调整。
  - 把 1H 写成设计方案/架构方案 → 原文明确 1H 是**关键业务流程**。
  - 可扩展设计完全不写 → 评审会认为遗漏设计点。
  - 详细设计只写「做了什么」不写「做不到时怎么办」→ 案例对每一处局限都明确声明（SDK 缓存丢失、复制延迟丢消息均「不做针对性设计」，并指定责任方）。
  - 部署方案不给资源特征依据 → 混布会被质疑。

- **原文金句**
  - 「备选方案评估后会选择一个方案落地实施，架构设计文档就是用来详细描述细化方案的。」
  - 「实际操作的时候每个约束和限制都要有详细的逻辑推导，避免完全拍脑袋式决策。」
  - 「如果方案不涉及，可以简单写上『无』，表示设计者有考虑但不需要设计。」
  - 「需求中涉及的性能、成本、可靠性等仅仅是利益关联方提出的诉求，不一定准确。」

  - 架构设计文档的双模板（备选方案 / 架构设计）与逐章写作要求。
  - 5W + 1H + 8C 的需求分析骨架（可直接做成模板字段）。
  - 复杂度分析的三段式（高可用/高性能/可扩展）+ 必须给出推导的纪律。
  - 「可扩展写『无』」这类文档级反例清单（评审视角）。

### 51丨如何画出优秀的软件系统架构图？

- **原标题**：51 | 如何画出优秀的软件系统架构图？（2022 年补写）

- **核心结论**
  画不好架构图的根因不是画工，而是**不知道「该画哪些内容」**：画少了怕漏关键信息，画多了抓不住重点。原文的解法是拿 **4R 架构定义**（Rank/Role/Relation/Rule）当内容边界，把图分成**静态架构图（Role + Relation，1～2 张）**与**动态架构图（Rule，多张系统序列图）**；**4+1 视图只是历史标准，在分布式时代并不实用**；再按「读者与用途」选六类常见图之一。

- **完整判据/清单/步骤**

  #### 一、4+1 视图：五个视图与它为什么不好用

  1. **来源**：**1995 年**，Philippe Kruchten 在论文中指出「过去用单一视图描述软件系统架构的问题」，并提出 4+1 视图作为解决方案。原文引用的核心论点：「有时，软件架构的问题来源于系统设计者过早地划分软件或者过分地强调软件开发的某一个方面……此外，软件架构往往不能解决它的所有『用户』的问题。……作为补救措施，我们建议使用几个并发视图来组织对软件架构的描述，其中每个视图分别解决一组特定的问题。」
  2. **五个视图（逐个：视角 → 关注点 → 对应 UML）**

     | 视图 | 英文 | 视角 | 关注什么 | 对应 UML 图 |
     |---|---|---|---|---|
     | **逻辑视图** | Logical | 终端用户 | 系统提供给用户的**功能** | class、state diagrams |
     | **处理视图** | Process | 动态角度 | 系统的**处理过程** | sequence、activity diagrams |
     | **开发视图** | Development | 程序员 | 系统的**逻辑组成** | package diagrams |
     | **物理视图** | Physical | 系统工程师 | 系统的**物理组成** | deployment diagrams |
     | **场景视图** | Scenarios | 用户 | 系统需要实现的**需求** | use case diagrams |

  3. **逻辑视图的「功能」≠ 场景视图的「需求」（原文专门加备注，最易混）**
     - 一个需求可能涉及**多个功能**：「取款」这个场景涉及「插卡」「密码验证」「出钞」等功能。
     - 多个需求可能涉及**同一个功能**：「取款」和「转账」是两个不同需求，但都涉及「密码验证」这个功能。
  4. **4+1 视图在实际工作中不流行的三个原因（原文逐条）**
     - ①**架构复杂度增加**：1995 年系统大部分还是单体，现在分布式系统越来越多；用 4+1 表示分布式系统会遇到困难——「比如微服务架构下有那么多的微服务，Development view 就不好表示」。
     - ②**绑定 UML 图**：UML 图画架构图存在问题，**主要问题是不美观，表达能力弱**（原文配图对比：左图 UML 工具、右图 Visio，「UML 图的缺点十分明显」）。
     - ③**理解困难**：逻辑视图、开发视图和处理视图比较容易混淆——「有人把逻辑视图理解为软件开发的类结构图，也有人把处理视图和开发视图等同，还有人认为逻辑视图就是开发视图」。

  #### 二、核心指导思想：4R 架构定义与四步画图法

  1. **4R 定义（原文引用第 1 讲）**：「软件架构指软件系统的**顶层（Rank）结构**，它定义了系统由哪些**角色（Role）**组成，角色之间的**关系（Relation）**和运作**规则（Rule）**。」
  2. **四步法（顺序不可换，每步对应图上的一个元素）**

     | 步骤 | 动作 | 对应图元素 | 原文要点 |
     |---|---|---|---|
     | 第一步 | **明确 Rank** | 图的边界/级别 | 不要事无巨细地把一个大系统的方方面面都画在一张图里；明确系统所属级别（**L0～L4**），只描述这个级别的架构信息 |
     | 第二步 | **画出 Role** | 区块、图标、节点 | 从不同角度分解系统，看系统包含哪些角色 |
     | 第三步 | **画出 Relation** | 角色之间的连接线 | 不同的连接线可以代表不同的关系 |
     | 第四步 | **画出 Rule** | 系统序列图 | 挑选**核心场景**，画出角色之间如何协作完成某项具体业务功能 |

  3. **静态图 vs 动态图（原文的分类与数量经验）**

     | 类型 | 描述内容 | 图的形态 | 数量经验（原文） |
     |---|---|---|---|
     | **静态架构图** | Role + Relation | 结构图（区块/图标 + 连线） | **一般 1～2 张**：比较简单用一张就够；比较复杂就用两张分别展现 |
     | **动态架构图** | Rule | 系统序列图 | **一般是多张**，因为核心场景数量不止一个 |

  #### 三、六类常见架构图（定义 / 使用场景 / 画图技巧 / 参考案例）

  | # | 图类型 | 定义 | 使用场景 | 画图技巧 | 参考案例 |
  |---|---|---|---|---|---|
  | 1 | **业务架构图** | 描述系统对用户提供了什么**业务功能**，类似于 4+1 视图的场景视图 | ①产品人员规划业务（产品规划和汇报会议上展现业务全局）；②给高 P 汇报业务（P7+ 以上不能光讲技术，也要讲业务发展）；③给新员工培训业务 | ①通过**不同颜色标识业务状态**（哪些发展好、哪些问题多、哪些稳定、哪些竞争激烈）；②**业务分组管理**（类似业务放一个分组，用虚线框或相同背景标识）；③**区块对齐**（可改变区块长短大小做对齐，让整体更美观） | AlipayHK 业务架构图（三点关键信息：浅红=正在进行、绿色=明年规划；分 4 组：钱包业务、第三方业务、商家服务、用户管理；「转账」「社交红包」区块较长只是为了对齐更美观，**不代表量级或重要程度**，要表达量级应用颜色） |
  | 2 | **客户端和前端架构图** | 描述客户端和前端的**领域逻辑架构**，关注从逻辑角度如何分解客户端或前端应用 | ①整体架构设计（由客户端/前端架构师完成本领域设计）；②架构培训 | ①用**不同颜色标识不同角色**；②用**连接线表示关系**，若有多种关系（直接调用 vs 事件通知）可用**不同形状的线条**；③**分层或分组**管理类似角色 | 微信客户端架构 3.x（三点关键信息：用灰、蓝、深灰、浅蓝表示不同类型模块；两类连接线——双向的 WebViewUI 与 app:UI、单向的 app:UI 与 Net Scene 等；整体分 4 组，对应背景色不同的四个大区块） |
  | 3 | **系统架构图** | 描述**后端的逻辑架构**，又叫「后端架构」或「技术架构」；不管是业务系统、中间件系统，还是基础的操作系统、数据库系统，系统架构都是软件系统架构的**核心** | ①整体架构设计；②架构培训 | ①不同颜色标识不同角色；②连接线表示关系；③**逻辑分组** | 简单系统：MongoDB Sharding 系统架构图；复杂系统：**先用一张图展示角色（Role）及每个角色的核心功能，再用一张图展示角色之间的关系（Relation）**，参考支付中台系统架构图（完整关系图太大，原文只摘取一部分作示意） |
  | 4 | **应用架构图** | 描述后端系统由**哪些应用**组成——**一个应用就是一个可部署发布运行的程序**，它是项目开发过程中开发测试运维团队协作的基础 | ①项目开发、测试；②运维部署发布；③**子域架构设计** | ①不同颜色标识不同角色；②连接线表示关系；③**复杂系统分域来画** | 简单系统：应用架构与系统架构基本等价，参考 MongoDB Sharding（图中 Router/mongos、Config Servers、Shard/replica set 既含系统架构角色信息，又含应用信息）；复杂系统（如支付中台，应用可能几百上千个）：**按子域画**，参考支付中台会员域的应用架构图 |
  | 5 | **部署架构图** | 描述后端系统**具体如何部署**，主要包含**机房信息、网络信息和硬件信息**等 | ①总体架构设计；②运维规划和优化 | **用图标代替区块**，看起来更美观、更容易理解（六类图里唯一只给了一条技巧的） | 一个简单的支付系统部署架构图 |
  | 6 | **系统序列图** | 描述某个业务场景下，系统**各个角色如何配合**起来完成业务功能 | **结合「系统架构、应用架构和部署架构」来使用** | **使用 UML 的序列图来画** | 「扫码支付」这一支付核心场景的系统序列图（其角色对应前面支付中台系统架构图的关系图角色） |

  #### 四、画图通用规则与其他标准的取舍

  1. **配色纪律（原文在业务架构图处给出，属全篇通用）**：「**千万不要画得五颜六色，一般一张图的颜色数量控制在 3 种以内是比较好的**。」并且画之前要想清楚：**哪些信息是这张图要重点展示的关键信息，哪些信息顺带讲一下就可以了**。
  2. **「美观」不能携带错误语义**：区块长短只用于对齐美观，**不代表业务量级或重要程度**；要表达量级/重要度应改用颜色。
  3. **复杂度决定图的数量**：静态图 1～2 张；系统复杂时角色与关系分两张；应用架构复杂时按子域拆多张。
  4. **其他架构标准为何不套用（原文的取舍说明）**
     - **TOGAF**（业务架构 / 数据架构 / 应用架构 / 技术架构）：这是**企业级**架构，基本上要到 **CTO 这个级别**才能接触；且注意 TOGAF 的「业务架构」与本文同名但**意义不同**，其「数据架构」指的是**数据资产的架构**，不是大数据平台架构。
     - **C4 模型**（Context、Container、Component、Code）：**表达能力又不够**。
     - 结论：**「目前业界并没有就架构图标准达成共识」**；原文的六类图是作者根据个人经验整理，并声明「这些架构图，都是我在不同类型不同规模不同业务的公司（**华为、UC、阿里和蚂蚁**等）里面验证过的，你可以放心地使用」。

- **案例/数据**
  - AlipayHK 业务架构图：浅红「MTR」= 正在进行、绿色「人传人」= 明年规划；4 组（钱包/第三方/商家服务/用户管理）；长区块只为对齐 → 一张业务图同时承载「状态 + 分组 + 美观」三件事。
  - 微信客户端架构 3.x：灰/蓝/深灰/浅蓝四色区分模块；双向线与单向线区分关系类型；4 个大区块 → 客户端图的「角色 + 关系类型 + 分组」范式。

  - 作者经历（华为/UC/阿里/蚂蚁）→ 六类图经过多类型公司验证。

- **反例与坑**
  - 把 4+1 视图当「标准」硬套分布式系统 → Development view 在微服务下无法表示。
  - 用 UML 工具画架构图 → 不美观、表达能力弱。
  - 混淆逻辑视图 / 处理视图 / 开发视图 → 原文点名的三大理解困难。
  - 一张图里塞完整个大系统 → 违背「明确 Rank」，信息太多太密导致「架构图都看不清」。
  - 复杂系统只画一张系统架构图 → 原文要求角色与关系分两张。
  - 把几百上千个应用画在一张应用架构图里 → 应分域（子域）画。
  - 五颜六色、颜色超过 3 种 → 重点信息被淹没。
  - 用区块长短暗示业务量级/重要度 → 误导读者，量级应用颜色表达。
  - 直接套 TOGAF 或 C4 → 前者是企业级（CTO 层），后者表达能力不够。
  - 「茶壶里煮饺子，有货倒不出」→ 技术强但讲不清，架构图的表达能力是独立技能。

- **原文金句**
  - 「很多同学技术能力很强，架构设计也做得很好，但是在给别人讲解的时候，总感觉像是『茶壶里煮饺子，有货倒不出』。」
  - 「不要事无巨细地把一个大系统的方方面面都在一张架构图中展现出来，而应该明确你要阐述的系统所属的级别（L0～L4）。」
  - 「千万不要画得五颜六色，一般一张图的颜色数量控制在 3 种以内是比较好的。」
  - 「目前业界并没有就架构图标准达成共识。」

- **可迁移到知识库的主题**
  - 4R 架构定义与「静态图 1～2 张 / 动态图多张」的视图分工。
  - 六类架构图的「定义 / 场景 / 技巧 / 案例」四段式卡片（可直接做成选图决策表）。
  - 4+1 视图的失效条件（分布式、UML 绑定、三视图混淆）与 TOGAF/C4 的取舍。
  - 架构图配色与视觉语义纪律（≤3 色、长度不承载量级）。
  - 复杂系统的图表组合（角色图 + 关系图 + 子域应用图 + 核心场景序列图）。
