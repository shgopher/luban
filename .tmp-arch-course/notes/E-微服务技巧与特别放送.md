### 微服务架构技巧篇：接口类设计技巧

> 文件：`07 -微服务架构技巧__0 |接口类设计技巧.txt`

- **核心结论**
  微服务架构的技术挑战都源于「两个分布式」——**服务分布式**（功能由多个微服务提供）与**数据分布式**（数据分散在多个独立存储系统）。本篇解决服务分布式带来的接口问题，三个抓手是 **BFF、GraphQL、接口循环调用**。其中 BFF/GraphQL 有成熟落地方法；**接口循环调用目前没有根治方案，只能按问题驱动事后处理**。

- **完整判据/清单/步骤**

  **A. 服务分布式引发的三个典型问题（BFF 的存在理由）**
  1. **请求性能问题**——不是单个接口的处理性能，而是前端与服务端之间来回请求的**网络消耗**；多接口时即便并行发送，移动端网络不稳定，只要一两个请求慢，整个页面就加载缓慢。
  2. **网络带宽问题**——单个接口数据不大，但 HTTP header 等协议开销占比高，**大量小请求抬高机房入口带宽成本**。
  3. **前端开发成本问题**——前端要理解并对接多个后端微服务，开发量、联调量都增加；后端多版本接口时，**版本选择与适配**成为前端负担。

  **B. BFF 定义与访问逻辑（做法）**
  - 定义：Backend For Frontend，中文译「前端专属后端」或「服务前端的后端」，位于前端与后端微服务之间的**中间层**，做数据的**整合、转换、适配**。
  - 两条路径：普通不复杂页面 → 前端发普通微服务接口请求，**API 网关直接转发**给对应微服务；复杂页面 → 前端发**聚合接口**请求，网关转发给 **BFF**，BFF 再分别请求多个微服务并组装结果返回。

  **C. 为什么不在 API 网关做聚合（为什么 + 反例）**
  - 做法：聚合逻辑放 BFF，**不放网关**。
  - 为什么：API 网关是**与业务无关的网络基础设施**，对稳定性和可靠性要求很高，一旦故障就是**整个业务系统全部故障**，因此应尽量避免改动；而 BFF 与业务相关，会随业务版本频繁迭代，**本质上与 API 网关的定位和要求冲突**。
  - 反例：把聚合逻辑写进网关 —— 业务每迭代一次就动一次全站入口。

  **D. BFF 三个应用场景**
  1. **接口聚合**（最常见）：微服务提供原子接口，BFF 按各前端页面需求做访问、转换、合并、裁剪，对前端提供聚合接口，让前端拿到最优化数据结构。
  2. **多端适配**：为每类前端（App / H5 / 桌面）提供量身定制的服务接口，满足各自特点与限制。
  3. **接口兼容**：隔离后端接口版本变化，一段时间内**同时支持旧版和新版 API**，允许前端逐步迁移，不影响用户体验。

  **E. BFF 落地第一问：前端开发还是后端开发（做法 + 为什么 + 适用）**

  | 维度 | 前端负责（一般 Node.js） | 后端负责（后端语言栈） |
  |---|---|---|
  | 好处 1 | 前端最清楚自己要什么聚合接口，可灵活定制，**不依赖后端即可独立迭代** | 后端更熟悉微服务与后端技术，开发更高效，**可做复杂 BFF（如支持缓存）** |
  | 好处 2 | JS 一套技术栈同时写前端和 BFF，**大幅降低沟通成本** | 开发、维护、监控、部署**复用后端已有基础设施** |
  | 不足 1 | 前端仍需熟悉复杂的后端微服务架构与细粒度接口；涉及存储/缓存处理时经验不足 | 增加前后端沟通成本，后端要理解复杂多变的前端需求 |
  | 不足 2 | BFF 与后端技术栈不同（后端主流 Java、.Net、PHP、Golang、Python），带来**维护、监控、部署麻烦**，因为 DevOps 基础设施基本与语言强相关 | — |
  | 适用 | 业务不复杂、团队不大、BFF 轻量、主要做接口聚合 | 业务复杂、团队大、BFF 重量级、需多端适配与高并发 |

  **F. BFF 落地第二问：哪些页面用 BFF（判据 + 反例）**
  - 反例判据：**不要「每个前端页面都提供一个 BFF 接口」**，开发成本太高；大部分页面简单且访问量不大，收益不足。
  - 正例判据：**访问量大且复杂的页面**用 BFF 提供聚合或适配接口；普通页面直接访问微服务。**一级页面和二级页面（首页和导航页）大概率适合**。
  - 兜底判据：不确定时**先上线业务，再按监控数据（访问量、加载时间）判断**是否补 BFF。

  **G. GraphQL（做法 + 为什么）**
  - 定义：用于 API 的**查询语言规范**，Facebook 开发，2015 年开源；客户端可指定确切需要的数据，减少过量数据传输，并能一次性从多个数据源取数。
  - 三步原理：① 客户端发 Query（取数）或 Mutation（改数）；② 服务器按类型与内容解析，从本地存储、NoSQL、其它微服务、第三方服务取数；③ 服务器按 GraphQL 格式包装，**返回结构与请求结构对应**。
  - 与标准 HTTP 的差异：标准 HTTP 是**多次调用不同后端 API 各取数据片段**；GraphQL 是**一次 HTTP 请求、查询字符串里写清所有需要的数据**。
  - 与 BFF 的关系（关键辨析）：**GraphQL 是 API 接口规范，BFF 是 API 接口架构**，二者本质不同。可以在 API 网关实现、在专属 GraphQL 服务实现、也可在 BFF 实现；**通常「在 BFF 中实现 GraphQL」是最佳选择，GraphQL 是 BFF 的黄金搭档**。

  **H. 接口循环调用（问题 + 两个预防措施 + 为什么都无效）**
  - 定义：某接口在执行过程中**直接或间接调用自身**，形成无限循环调用链。
  - 两个后果：① 资源消耗**指数级**增长（CPU、内存、带宽），最终性能下降甚至崩溃；② 若涉及共享资源（数据库锁、文件锁）的获取释放，**可能死锁**。
  - 微服务下更隐蔽：调用关系链复杂，一旦出现影响更大、定位处理更复杂。
  - 预防措施 1「**梳理调用链**」：人工梳理依赖、画调用关系图找环。**为什么无效**：① 线上真实调用关系极复杂，人工梳理只覆盖核心处理步骤；作者见过一次业务处理涉及**内部近 100 次接口请求**的链路图，找不同团队的人都讲不清；② 循环调用多发生在**特殊分支**而非正常逻辑（正常逻辑测试很容易发现），事前分析基本不可能，线上出了再定位也要花相当长时间。
  - 预防措施 2「**请求唯一标识**」：每次调用带全局唯一请求 ID，调用前检查是否已出现相同 ID，出现即停止调用。**为什么无效**：对性能影响严重——要把一段时间内发出的请求 ID 和状态都保存下来，且**每次调用都要先检查**，而实际上**可能 99.999% 的接口请求都不会触发循环调用**。
  - 结论：**都是事后处理，等线上真出问题后再分析优化**。

- **案例/数据**
  - 复杂页面需请求多个后端接口 → 一个慢请求拖慢整页 → 移动端体验受损（BFF 的原始动机）。
  - 后端主流技术栈列举：Java、.Net、PHP、Golang、Python（论证前端写 BFF 的技术栈割裂）。
  - 线上日志分析出的调用链路图：一次业务处理近 100 次内部接口请求，**无人能完整讲清**，连自己负责的微服务中间有些请求也要翻代码才知道。
  - GraphQL 举例：博客应用中客户端一次查询取某作者的全部文章标题与内容。

- **反例与坑**
  1. 在 **API 网关**里做接口聚合 —— 业务迭代会污染全站入口的稳定性。
  2. **每个页面都做 BFF 接口** —— 开发成本高、收益低。
  3. 把 GraphQL 等同于 BFF —— 规范与架构混淆，导致「以为引入 GraphQL 就有了 BFF」。
  4. 指望靠**人工梳理调用链**发现循环调用 —— 效率极低、效果几乎没有。
  5. 给所有接口加**请求唯一标识检查** —— 为 0.001% 的场景付 100% 的性能代价。
  6. 认为拆分微服务后接口层「自然会变好」 —— 三个问题（性能/带宽/前端成本）是拆分**必然带来**的。

### 微服务架构技巧篇：分布式事务

> 文件：`07 -微服务架构技巧__02 | 分布式事务.txt`

- **核心结论**
  数据分布式带来的挑战，本质是「原来能在单个关系数据库上完成的复杂操作，拆分后没法用了」。应对手段是两个：**分布式事务**（本篇）与**全局幂等**（下一篇）。微服务层面的分布式事务叫**业务级分布式事务**（以区别于 XA 这类数据库层事务），业界成熟模式**四种：本地事务消息、MQ 事务消息、TCC、SAGA**。原文**没有**把 2PC、最大努力通知列为独立方案讲解（只在 TCC 处提到"符合 2PC 协议"，在小结处提到 Seata 的 XA 模式）。

- **完整判据/清单/步骤**

  **A. 背景：为什么微服务不需要存储过程**
  - 存储过程之恶：见到过**长达几百上千行**的存储过程，看代码、调试、定位、修改、重用、移植都是「地狱级」难度；即便有规范限制，只要没有严格审核监督，开发人员就会逐步滥用。
  - 为什么微服务里没必要：单个微服务职责简化、数据范围缩小、**微服务之间只能通过接口访问**，从根源上改变了复杂存储过程生存的土壤；简单的存储过程相比代码没有优势。
  - 但随之产生新挑战，按两种拆分模式看：① 各微服务仍用关系数据库 —— 原来单库的简单事务模式也**不可行**；② 各微服务按数据特点用不同存储（如用户 MongoDB、交易 MySQL）—— **更不可能**实现满足 ACID 的传统事务。

  **B. 方案一：本地事务消息（Transaction Outbox）—— 4 步流程**
  1. A 服务（发起者）先做正常业务逻辑，然后启动**一个本地数据库事务**，在同一事务中写入业务数据 + 写入一条**事务消息到本地事务消息表**。
     - 事务消息内容：**事务全局 ID、子事务 ID、事务操作（commit / rollback）、事务发起时间、事务关键参数（如用户 ID、交易 ID）、事务执行状态**。
  2. A 本地事务成功后，通过**接口调用或消息队列**把事务消息发给 B 服务。
  3. B 收到后读取关键信息执行本地事务，同样**在一个事务中既写业务数据、又写事务消息数据**。
  4. B 通过接口或 MQ 返回执行结果；A 收到后更新本地事务消息表状态。
  - **异常处理四条**：
    - 步骤 2 失败 → A **重试发送**事务消息。
    - 步骤 4 失败（A 没收到 B 结果）→ A **也重试发送**事务消息。
    - 步骤 3 中 B **先查本地事务消息表**：有对应消息说明已执行过，直接读状态返回 A；没有则首次收到，正常执行。
    - A 决定整体回滚 → 读本地消息表记录，向 B 发 **rollback** 事务消息。
  - 评价：**优点**是记录了分布式事务执行所需的相关信息，**故障恢复和人工订正非常方便**；**不足**是**异常处理分支多、整体逻辑复杂**。
  - 适用：原文未明确给出场景判据（只在小结中定性为「不依赖第三方但实现比较复杂」）。

  **C. 方案二：MQ 事务消息（RocketMQ）—— 7 步流程**
  1. Sender 发送一条特殊的 **Half（半事务）消息**给 RocketMQ 服务端。
  2. RocketMQ 持久化成功后回 **Ack**，此时消息被标记为「**暂不能投递**」，即半事务消息。
  3. Sender 开始执行**本地事务**。
  4. Sender 按本地事务结果向 RocketMQ 提交**二次确认**：Commit 或 Rollback；若一直收不到二次确认，RocketMQ 会**回查事务状态**。
  5. 收到 Commit → 半事务消息标记为**可投递**并投递给 Subscriber；收到 Rollback → 回滚事务，**不投递**。
  6. Subscriber 收到事务消息后执行本地事务。
  7. Subscriber 按执行结果提交消费结果（成功或失败）。
  - 设计初衷：由 MQ 承担事务消息处理流程，**降低事务消息的实现复杂度和业务开发难度**，提供高性能、可扩展、易使用的事务消息方案。
  - **关键边界（必须记住）**：RocketMQ 事务消息**保证本地主分支事务与下游消息发送事务的一致性，但不保证消息消费结果和上游事务的一致性**。因此下游业务分支要**自行保证消息正确处理**，消费端要做**消费重试**：短暂失败靠重试保证最终成功；异常导致一直失败则**可能需要人工处理**。

  **D. 方案三：TCC（Try-Confirm-Cancel）—— 4 步流程**
  - 三操作定义：
    - **Try**：资源预留，对业务资源**检查并预留**。
    - **Confirm**：确认操作，对业务处理提交（commit）。**只要 Try 成功，该步骤就一定成功**。
    - **Cancel**：取消操作，对业务处理取消（rollback），**释放 Try 预留的资源**。
  - 步骤：① 主业务应用向**事务协调器**申请启动事务；② 分别调用下游多个服务的 **Try 接口**预留/锁定资源；③ 主业务应用按多个 Try 结果判断提交或回滚，向协调器发「提交」或「回滚」请求；④ 协调器调用下游各服务的 **Confirm 或 Cancel**。
  - 定位：**应用层面符合 2PC 协议**的分布式事务解决方案。
  - 评价：**侵入式**——Try/Confirm/Cancel 三个操作都要业务系统实现且对外提供接口，**对业务系统入侵性非常大，设计相对复杂**；**优点是完全不依赖数据库**，能实现**跨存储系统、跨应用资源管理**，通过侵入式编码把不同数据访问实现成一个原子操作，更好解决复杂业务场景下的分布式事务。

  **E. 方案四：SAGA —— 补偿协议**
  - 出处：Hector Garcia-Molina 与 Kenneth Salem **1987 年**论文《SAGAS》，全称 Sequence of Atomic Transactions for Global Applications（全局应用的原子事务序列）；主要用于解决复杂分布式系统中**长事务（Long-Running Transactions）**问题。
  - 原理：把一个长事务拆成一系列**子事务**，每个子事务都有对应的**补偿事务**；子事务是独立本地事务，按顺序依次执行。全部正向操作成功 → 提交；任一正向操作失败 → **回退执行前面各参与者的逆向回滚操作**，回滚已提交者，使事务回到初始状态。
  - 评价：非常适合**复杂的、包含多个步骤的业务流程**；把长事务分解为多个小而易管理的子事务，可对每个子事务及其补偿事务**单独设计实现**；业务需求变化或要增加新环节时，**很容易对事务序列修改和扩展**。

  **F. 选型建议（原文只给了小结级的一句话定位，没有判定树/权重表）**
  | 方案 | 原文一句话定位 | 依赖 | 侵入性 | 适用（原文措辞） |
  |---|---|---|---|---|
  | 本地事务消息 | 不依赖第三方，但整体实现比较复杂 | 仅本地库 + 接口/MQ | 低（业务侧自建消息表） | 原文未明确 |
  | MQ 事务消息 | RocketMQ 提供分布式事务处理机制，**简化业务开发难度和复杂度** | 必须用 RocketMQ | 低 | 原文未明确 |
  | TCC | 可支持**跨异构存储系统**，但**对应用侵入很大** | 需事务协调器 | **高**（三接口都要业务实现） | 复杂业务场景下需要跨存储/跨应用资源的原子操作 |
  | SAGA | 分布式事务「**元老**」，适合**长事务**的一致性处理 | 需补偿逻辑 | 中（每子事务写补偿） | 复杂、多步骤的长事务流程 |

  - 原文补充的**学习路径**：推荐开源方案 **Apache Seata**（阿里开源，高性能、简单易用，提供 **AT、TCC、SAGA、XA** 四种事务模式），「非常适合全面、深入学习和应用」。
  - 原文**未明确**给出的内容：2PC/3PC 的独立讲解、最大努力通知、选型的量化判据、各方案的具体性能数据。

  - TCC 的边界承诺：**只要 Try 成功，Confirm 就一定成功** —— 这是 TCC 可用性的前提假设。

- **反例与坑**

### 微服务架构技巧篇：全局幂等

> 文件：`07 -微服务架构技巧__03 | 全局幂等.txt`

- **核心结论**
  分布式事务靠接口/消息协作，而接口可能失败、消息可能丢失，只能**靠重试保证最终一致**，重试就必须有**全局幂等**。加「全局」二字是因为服务分布式：同一请求/消息**不一定由同一个微服务实例处理**，所以要在多个实例范围内保证幂等。
  **总体设计原理一句话**：把业务操作看成一个**对象**，对象具备「**全局唯一标识**」和「**状态**」，通过**状态控制**实现幂等。不同模式的差别只体现在三处：全局唯一标识**如何生成**、幂等状态**如何判断**、**应用在什么场景**。

- **完整判据/清单/步骤**

  **A. 幂等的定义与判定边界**
  - 定义：某个操作或函数可以多次执行并保持同样效果——无论执行多少次，结果都不会改变；对同一输入重复应用不产生额外效果或变化。
  - 生活例：微信/支付宝支付时网络断了、用户刷新重付 —— 不做幂等判断会**一个订单支付两次**；有幂等判断则**一个订单只支付一次**。
  - 原文对「幂等 vs 重复提交」的处理：原文用「防止异常情况下业务重复处理导致用户损失或者用户体验不好」来界定接口级幂等的目标，把「重复提交」当作需要被幂等拦住的**异常场景**，而幂等本身是「多次执行结果不变」的**数学性质**；**原文未用「幂等 / 重复提交」这对术语做专门的概念辨析**（未给出「幂等是服务端性质、防重是客户端/业务约束」这类对照），此点标「原文未明确」。

  **B. 模式一：事务级同步处理模式（消息处理与业务处理同步）**
  1. A 服务（发起者）为 B 服务要执行的分布式事务**分配一个全局 ID**，并写入一条事件记录：分布式事务执行状态、发起时间、更新时间、业务参数等。
  2. A 发送事件消息给 B。
  3. B 收到后**先提取全局 ID 做幂等判断**：已处理过 → 直接读本地记录的处理结果返回 A；未处理过 → 执行分布式事务处理，完成后**同步记录**处理结果（全局 ID、状态 done/fail、完成时间等）。
  4. B 返回事件处理消息给 A。
  5. A 更新本地事件状态为「**完成**」——注意**不一定是「成功」**，只要 B 返回了处理结果，无论成功失败都算完成。
  - **超时未收到结果的 4 种可能**：① A 发出的消息丢失（步骤 2）；② B 返回的消息丢失（步骤 4）；③ B 服务挂掉；④ B 事务处理过程中出异常。**处理动作**：无论哪种都要**重发事件消息**；多次重发（**一般尝试 3 次**）仍失败，则**告警提示人工处理**。
  - 适用：需要**同步处理、处理简单、处理速度快**的场景，一般通过**接口调用**交互，例如用 TCC 的 Try 接口扣库存。

  **C. 模式二：事务级异步处理模式（消息处理与业务处理分开）**
  - 与同步模式整体逻辑大体一致，**唯一区别在 B 的处理**：B 收到事件消息后**先保存事件消息**，再**异步**处理业务操作，完成后再更新本地事件消息状态。
  - 适用：**处理速度慢、处理时间长**的场景，一般通过**消息队列**交互，例如用 SAGA 处理项目管理中的一些流程。

  **D. 模式三：接口级自动幂等（业务接口防重）**
  - 定义：提供接口的微服务**在接口处理逻辑里实现幂等**，防止异常情况下业务重复处理造成用户损失或体验不好；典型场景**用户下单、支付**。
  - 三步：① A 发起调用，接口参数中**包含全局 ID，或能从参数中组装出全局 ID**；② B 提取/组装全局 ID 做幂等判断，已处理则读之前保存的处理结果，未处理则执行业务；③ B 返回结果给 A。
  - **全局 ID 的两种来源**：由调用方生成（如**前端生成唯一 Token**）；从接口参数中组装（如「**用户 ID + 订单 ID**」标识一次支付请求）。

  **E. 四种幂等判断技术手段（做法 + 适用）**
  | 手段 | 做法 | 适用场景 | 原文评价 |
  |---|---|---|---|
  | **数据库唯一索引** | 用全局唯一标识做唯一索引，**判断插入是否成功**即得「是/否」 | **创建数据**类业务：用户注册、创建订单 | 最简单可靠 |
  | **Redis SETNX** | key 不存在时才能设置，用「全局唯一标识」做 key | **分布式事务、定时任务调度** | 若系统已用 Redis，更推荐 |
  | **ZooKeeper 创建节点** | 节点已存在则创建失败，用「全局唯一标识」做节点名 | 与 SETNX 类似 | **性能差一些**，且要维护 ZK 集群，整体更复杂麻烦；**已用 Redis 则更推荐 Redis** |
  | **状态机判断** | 全局状态复杂时用状态机；数据库保存状态，更新时用 `Update …… Where …… and status = XXX` | 订单状态（Pending Payment / Paid / Shipped 等）等**多状态流转** | 复杂状态的唯一选择 |

  - 状态设计的基本分层：**简单状态**用「是/否」表示是否处理过；**复杂状态**用状态机判断。

- **数字与阈值**
  | 数字 | 含义 |
  |---|---|
  | 3 | 全局幂等的三种处理模式（事务级同步 / 事务级异步 / 接口级自动） |
  | 4 | 四种幂等判断手段（唯一索引 / SETNX / ZK 节点 / 状态机） |
  | 4 | 同步模式超时未收到结果的四种原因 |
  | 3 次 | 重发事件消息的一般尝试次数，超过则告警转人工 |
  | 2 | 全局 ID 的两种来源（调用方生成 Token / 参数组装） |
  | 3 | 幂等的三个差异维度（标识如何生成、状态如何判断、适用场景） |

- **案例/数据**
  - 微信/支付宝支付断网重刷：不做幂等 → 一单付两次；做了 → 一单只付一次（原文唯一的完整业务案例）。
  - 全局 ID 组装例：「用户 ID + 订单 ID」标识一次支付请求；前端生成唯一 Token。
  - 状态机例：订单状态 Pending Payment / Paid / Shipped。
  - 同步/异步模式对应的分布式事务配对例：TCC 的 Try 扣库存（同步）；SAGA 处理项目管理流程（异步）。

- **反例与坑**
  1. **没有全局 ID 就直接重试** —— 重试机制本身会制造重复数据，分布式事务的正确性依赖幂等兜底。
  2. 把「A 更新为成功」当成唯一完成态 —— 原文明确：只要 B 返回了处理结果，**成功和失败都算「完成」**，否则会无限重试。
  3. 用 ZooKeeper 做高并发幂等判断 —— 性能比 Redis 差，还要多维护一套集群。
  4. 复杂状态还用「是/否」两态判断 —— 必须上状态机 + `status = XXX` 条件更新。
  5. 以为幂等只在分布式事务里需要 —— **下单、支付等关键接口**同样要「接口级自动幂等」。
  6. 重试无上限、无告警 —— 原文规定 3 次后转人工。

- **原文金句**
  - 「全局幂等方案总体设计原理是将业务操作理解为一个对象，对象本身具备“全局唯一标识”和“状态”，通过状态控制来实现幂等特性。」
  - 「如果已经处理过，则直接读取之前保存的处理结果；如果没有处理过，则进行业务处理。」
  - 「注意不一定是“成功”，只要是B服务返回了处理结果，无论“成功”“失败”都是完成」
  - 「如果多次重发（一般尝试3次）后还是失败，A服务可能要采取告警等手段来提示人工进行处理。」

### 聊聊异地多活成熟的架构模式

> 文件：`07 -微服务架构技巧__04 | 聊聊异地多活成熟的架构模式.txt`

- **核心结论**
  2018 年专栏讲的是**物理部署三模式**（同城异区、跨城异地、跨国异地）+ **4 步** + **4 大技巧**；6 年后业界成熟的是**三种架构模式**：**业务定制型、业务通用型、存储通用型**。总思路统一为三段：**网络架构 + 计算架构 + 存储架构**。2018 年那套「业务定制型」**并未过时**，且不管是否上云、是否云原生都依然可行。

- **完整判据/清单/步骤**

  **A. 总体思路三分法（一切模式的公共骨架）**
  | 段 | 要回答的问题 | 具体手段 |
  |---|---|---|
  | **网络架构** | 系统如何调度流量 | **网络流量调度**用 DNS/GSLB 把请求分到多个异地机房；**业务流量调度**按业务规则（如用户归属机房）路由到指定机房 |
  | **计算架构** | 如何冗余计算资源 | **静态分配**（比较浪费钱）或**动态生成**（实现比较复杂，可能有风险） |
  | **存储架构** | 关键业务数据如何同步 | 如何保证一致性；故障时数据不一致对业务的影响如何处理 |

  **B. 模式一：业务定制型（= 2018 年专栏那套）**
  - 核心思想：「**定制**」——根据**业务特点和数据特点**设计专属方案。
  - 两个关键设计点：① **按业务优先级排序，优先保证核心业务异地多活**（用户中心例：优先「登录」，「注册」和「用户信息管理」可不做）；② 基于核心业务的流程与数据设计定制化架构（A 业务数据用「数据库 + 消息队列」快速同步；B 业务数据用「CDC + 算法」做数据双写）。
  - 3 个优点：① 对基础设施无强要求（机房部署、存储系统、时延），**支持远距离两城市部署**，可应对区域级故障与灾难；② 复杂度相对低（可针对具体业务特殊处理）；③ **落地成本低**——异地双活两机房各冗余 **50%** 资源即可，无需大量配套系统，故障时在网络层整体切流量到正常机房。
  - 2 个缺点：① **不通用**，每个业务都要单独做、业务要改造（例：游戏接入、游戏商店、浏览器各自实现）；② **难扩展**，核心业务重大变化就得重新设计（例：微博从图文为主改为短视频为核心）。
  - 适用：业务规模不大、业务不复杂、业务数量不多的企业团队；案例：**阿里游戏异地多活架构**。

  **C. 模式二：业务通用型（单元化 / LDC）**
  - 核心思想：提供**通用**的异地多活架构，避免对业务大量定制化改造；**通过配套服务实现**，**无需按业务优先级排序筛选业务**。
  - **准入判据（一句话）**：**只要业务支持 BASE（最终一致性）就能异地多活部署；如果业务必须强一致性，就采用中心化部署。**
  - 四类配套服务：
    1. **流量调度**：用算法/策略把不同来源流量分配到不同目标节点，优化资源利用、提升性能、保障服务质量、应对高并发与故障。简单版只做网络流量调度；复杂版还能调度微服务应用到数据库、存储系统的流量。
    2. **配置中心**：集中管理配置（数据库连接、缓存配置等），统一存储、管理、**支持动态更新**。切换/接管时起关键作用——**没有配置中心统一管理，快速接管和恢复无从谈起**。
    3. **建站平台**：通过容器化技术，在故障切换时**临时申请**软硬件资源，快速创建并运行微服务处理请求。正常时不必冗余太多资源，**大幅降低运行成本**；其**关键基础系统是配置中心**。
    4. **数据同步**：统一底层同步工具/系统，跨存储介质、跨系统、跨数据中心同步；手段包括数据库复制、消息队列、CDC，实时或定时传递变更。
  - **关键物理判据**：远距离（**两地时延超过 30ms**）的数据同步，不管什么技术手段，**本质上都是最终一致性**。
  - 2 个优点：① 对硬件基础设施无强要求，一般部署在远距离两城市，支持区域级故障处理；② **业务基本不用改造**，只判断是否支持 BASE。
  - 3 个缺点：① **配套服务复杂**（流量调度、容灾切换、建站平台、配置管理、数据同步）；② **存在全局单点业务**（库存、卖家等相关业务）；③ 配套服务**开发成本高**，需专门团队研发维护。
  - 适用：**业务数量多、业务强一致性要求不高的大公司**（只有支持多个业务，配套服务才能发挥最大价值）；案例：**淘宝、支付宝的单元化架构（LDC，Logic Data Center）**。

  **D. 模式三：存储通用型（随分布式一致性数据库兴起）**
  - 核心思想：采用**本身已支持分布式一致性**的存储系统，架构上**天然支持**异地多活。
  - 原理：存储底层用分布式一致性算法（**Raft、Paxos**）保障多节点间**强一致性**；面对网络分区、节点故障，**只要不是极端情况下多个机房同时故障**，就能保证系统整体可用且数据一致；业务层可放心读写。
  - 2 个优点：① 架构天然支持异地多活，**业务除了切换存储系统外基本不用改造**；② **支持数据强一致性**，适合金融交易等要求高的复杂业务。
  - 3 个缺点：
    1. **需要分布式一致性存储系统支持**，而**可选不多**：ZooKeeper、etcd、OceanBase、TiDB；其中 **ZooKeeper 和 etcd 不支持大规模数据存储**，**OceanBase 和 TiDB 是数据库存储系统，目前应用比较多**。
    2. **对机房部署有强要求**：只能**近邻部署**，因为一致性算法要保性能则底层时延越低越好，**经验数据是不要超过 10ms**；国内支持这种部署的城市主要有 **4 组：北京+天津、广州+深圳、成都+重庆、上海+杭州**。
    3. **成本高**：需要「**两地三中心**」甚至「**三地五中心**」部署。
  - 适用：对**数据一致性、灾难恢复有强要求**的业务（金融、电信）；案例：**网商银行**异地多活底层采用 **OceanBase**。

### 云原生时代架构师的进化之道

> 文件：`07 -微服务架构技巧__05  | 云原生时代架构师的进化之道.txt`

- **核心结论**
  云原生是**云计算发展的 3.0 阶段**，可概括为公式 **云原生 = 服务化 + 容器化 + 网格化 + 云产品**；其**技术本质核心是「可弹性扩展」**，服务化/容器化/网格化解决**计算架构**的弹性，云产品解决**存储架构**的弹性。云原生对行业的两大影响是**抹平技术层差**与**降低岗位技能要求**；对架构师而言**岗位会增多**（大量存量企业要云原生化），但能力重心从「架构技术」转向「业务理解」。

- **完整判据/清单/步骤**

  **A. CNCF 定义与三个关键点**
  - 定义：「云原生技术有利于各组织在**公有云、私有云和混合云**等新型动态环境中，构建和运行**可弹性扩展**的应用。云原生的代表技术包括**容器、服务网格、微服务、不可变基础设施和声明式 API**。」
  - 三个关键点：① 必须**在云计算环境中**实现——没有「云」就谈不上云原生；② 必须是**可弹性扩展**的应用——不能弹性扩展就不是真正的云原生；③ 代表技术五项（容器、服务网格、微服务、不可变基础设施、声明式 API）。
  - 简化公式：**云原生 = 服务化 + 容器化 + 网格化 + 云产品**（推理：不管公有云/私有云/混合云，**不可变基础设施都由云产品的方式提供**）。

  **B. 云计算三阶段（为什么会出现云原生）**
  | 阶段 | 名称 | 云厂家提供 | 用户还要做什么 | 原文例证 |
  |---|---|---|---|---|
  | 1.0 | **云托管** | 硬件基础设施：服务器、网络、存储 | 不用买机器、租机房、拉网线；但仍要自己装软件、搭环境、部署程序 | — |
  | 2.0 | **云服务** | 云产品实现基础服务：关系数据库、负载均衡、CDN | 不用装 MySQL、配主备同步、写脚本做快照备份；但**仍要自己做容量规划和高性能设计**（如自己实现分库分表，评估错或超预期后扩容很麻烦） | MySQL 云服务 |
  | 3.0 | **云原生** | 提供**实现弹性扩展**的云产品 | 关系数据库云产品**本身已实现可弹性扩展**，并支持很多原来要自己设计的高级特性 → **大大简化软件设计复杂度** | 阿里云 PolarDB 官方介绍 |

  **C. 技术本质的判定**
  - 「云原生的技术本质核心其实就是『**可弹性扩展**』。服务化、容器化、网格化、云产品这些技术，本质上都是为了实现『可弹性扩展』。」
  - 分工：**服务化、容器化、网格化** = 应用的**计算架构**可弹性扩展；**应用存储架构**的可弹性扩展**通过云厂家提供的云原生产品实现**。

  **D. 行业影响两条**
  1. **抹平技术层差**：技术层差 = 不同规模/等级公司处于不同技术层级，巨头掌握前沿核心技术，小初创技术简单基础。开源运动已大幅降低层差，但**人才能力差异**导致同样开源系统理解掌握差异很大（如很多大公司基于 Nginx 二次开发做定制）。云原生进一步抹平：云厂家把**原来只有巨头才掌握的高级能力封装进云产品**供所有企业使用（PolarDB 例：中小公司自己不可能实现，很多技术能力不够的巨头也无法实现）。
  2. **降低岗位技能要求**：原文以表格呈现（**该表格内容以图片形式给出，纯文本中缺失，具体岗位与结论映射原文未明确**），正文只给出结论：整体上云原生**降低绝大部分技术岗位的技能要求**，技术人员需要**更多关注业务本身**。

  **E. 架构师抓机遇的 4 个动作**
  1. **发挥业务积累优势**，结合数字化趋势把系统演进到**微服务**。理由：国内三大趋势是**数字化、国产化、云原生**；云原生是数字化的基础，大部分云厂家也提供国产化替代产品，因此**云原生也是国产化的基础**；而**微服务架构是应用容器、K8s、网格等技术的基础**。
  2. **用容器和云原生技术做弹性资源管理，降低硬件成本**。判据：业界统计**线上服务器使用率（按 CPU 使用率评估）平均约 20%–30%**，基于容器弹性扩缩容可大幅降本。
  3. **用 K8s + 网格统一跨语言基础设施，降低运维成本**。理由：企业常用多语言（Java 面向对象/类库/跨平台适合企业级与后端；C++ 高性能/贴近硬件适合游戏与系统软件），多语言应用的运维挑战随规模放大；K8s + 网格把 Java、C++ 等应用纳入**统一管理体系**，运维团队不必为每种语言学一套手段。
  4. **用云产品快速搭建顶尖架构**（异地多活、弹性扩缩容、全球部署）。理由：云产品覆盖计算/存储/网络，具备高可扩展性、可靠性、灵活性，多地数据中心 + 智能网络连接与数据同步 → 多活 + 故障无缝接管。

  **F. 进化建议（分两类人）**
  - **还不是架构师（3 条）**：
    1. 先积累行业业务经验，成为**技术业务都懂的 π 型人才**。论证：云原生之前架构师的技术能力（高性能/高可用/可扩展/可伸缩）至关重要；云原生时代这些**大部分由云产品实现**，于是「**是否对业务有深刻理解、架构是否契合业务特点**」成为设计优秀架构的关键，**架构师对业务的熟练程度会越来越重要**。
    2. **学习云厂家云产品并考认证**，考虑到时间精力，**建议先考初级认证**，先大体了解（例：阿里云 ACA 助理工程师认证，考核云计算基础产品的理解与使用）。举例：阿里云**飞天**操作系统（海量数据处理/大规模计算）、腾讯云**万象优图**（图片处理与多媒体）。
    3. **系统学习 K8s**，因为它是**事实上的标准**；重点在**原理与使用**（集群管理、资源调度、服务发现、负载均衡），如懂资源调度算法就能合理分配计算资源、避免浪费或过载。**并且不一定要转 Golang**——K8s 用 Go 写，但提供了丰富 API 和命令行工具，可用 Python 写自动化部署脚本、用 Java 开发与 K8s 集成的业务系统，**重点在理解架构与功能，而非学某一种语言**。
  - **已经是架构师（4 条）**：
    1. **系统学习架构设计方法论** —— 这是开展工作的基石，提供指导原则和流程，才能「在面对复杂多变的业务挑战时游刃有余，而不是只会生搬硬套以往的经验」。
    2. **深入学习并对比多家云厂家产品**，为老板决策（**Why、What、How**）提供技术支撑。对比维度：性能、功能、价格、服务质量；云的优势：按需付费降低前期投入、高度可扩展（高峰扩容/低谷缩容）。
    3. **以数字化为契机推动业务上云** —— 数字化涵盖业务流程优化、商业模式创新、客户体验、内部管理变革；上云可打破传统 IT 架构束缚。
    4. **对已上云系统推动云原生化** —— 容器化、微服务、DevOps，落地多活架构、弹性架构。

### AI 时代架构师的进化

> 文件：`08-特别放送 (7讲)__AI时代架构师的进化.txt`

- **核心结论**
  大模型的技术本质就是 **G、P、T 三个字母**，一句话概括：**「通过海量资料训练得到自然语言模式和知识的概率模型，然后基于概率模型生成输出内容」**。架构师是**业务与技术之间的桥梁**，需要业务、技术、管理三方面能力，核心动作是「**理解业务需求 → 判断关键点与复杂点 → 设计适合业务和团队的架构**」。**结论：目前基于 Transformer 架构的大模型无法取代架构师**（原文把问题框在「未来 3 到 5 年」的疑问上，并给出四个理由），但会**降低架构设计的技术门槛、加剧竞争**。

- **完整判据/清单/步骤**

  **A. GPT 三字母逐条**
  | 字母 | 含义 | 原文要点 |
  |---|---|---|
  | **G** | Generative，生成式 | 能根据输入提示或上下文生成连贯、有逻辑且符合语言规则的文本（对话、文章、故事）；与传统机器学习中**判别式模型**（主要用于分类和判断）相区别 |
  | **P** | Pretrained，预训练 | 在大规模语料上预先训练，**融合无监督学习、监督学习、强化学习**；学到语法、语义、语言逻辑关系等知识，使模型面对具体任务时能**更快更好地微调或适应**，提高性能与泛化能力 |
  | **T** | Transformer | **2017 年** Ashish Vaswani 等人在论文《Attention Is All You Need》提出；**完全基于注意力机制，摒弃传统 RNN 和 CNN 结构**；在机器翻译任务上取得显著性能提升，开启 NLP 新篇章；GPT 即基于 Transformer 构建 |

  **B. 大模型三大优势**
  1. **强大的语言理解与生成能力**：文本自然流畅，对话/写作/翻译出色（GPT-4 可生成连贯、有逻辑、内容丰富的文章，能理解复杂语义并恰当回应）。
  2. **知识融合与泛化能力强**：海量数据训练 → 融合多领域知识，对未知场景与任务泛化好（医疗、金融、法律等跨领域适应）。
  3. **特征提取与表示学习高效**：自动学习复杂特征与模式，提取更高级、更抽象的特征表示（图像领域可提取物体特征、场景信息，识别分类精度高）。

  **C. 大模型四个缺点（由「预训练」和「概率」两个本质导致）**
  1. **计算资源需求巨大**：参数数以亿计甚至更多，训练与部署需高性能 GPU 集群，耗大量电力 → 成本高，且限制在资源受限环境使用。
  2. **训练时间长**：规模大、数据大，训练可能需**数周甚至数月** → 开发迭代慢，不利于快速响应市场与技术变化。例：ChatGPT 刚推出时**训练数据截止到 2021 年**，问《流浪地球 2》或 Apple M2 芯片就答不上来或编造。
  3. **存在数据偏见和伦理问题**：输出依赖数据，数据有偏差或不完整 → 有偏见的结果；还可能被用于生成虚假信息、恶意攻击（虚假新闻、深度伪造）。
  4. **大模型幻觉**：生成或推理时产生与客观事实不符、逻辑不合理、与上下文不连贯的内容（原文附 ChatGPT 早期广为流传的错误案例图，**具体案例内容以图片给出，原文未明确文字**）。

  **D. 架构师能力模型（3×3 = 9 条）**
  - **技术能力**
    1. **扎实的计算机基础知识**：编程语言、数据结构、算法、操作系统、计算机网络、数据库原理，能用来构建系统、优化性能、解决复杂问题。
    2. **丰富的架构设计经验**：熟悉分层、微服务、分布式等架构模式，能按需求选型并做详细设计（模块划分、接口定义、数据流向设计）。
    3. **熟悉各种技术框架和组件**：SpringBoot、Redis、MySQL、MongoDB 等，能**基于业务和团队特点**选择技术。
  - **业务能力**
    1. **行业理解**：行业发展趋势、市场动态、竞争对手情况。
    2. **业务理解**：业务领域的专业概念、术语、规则、流程。
    3. **业务理解能力**：从复杂业务需求中**提炼核心的技术问题**，设计优雅高效的架构方案。
  - **管理能力**
    1. **团队管理能力**：团队组建、培训、激励；按项目需求组队，做技术培训与指导。
    2. **风险管理能力**：识别技术/市场/人员风险，制定应对策略与预案，做**架构可靠性设计**。
    3. **多维沟通能力**：对业务部门与客户、技术团队内部、跨部门（产品/测试/运维）三方沟通，协调资源推动项目。
  - **一句话总结（记不住就记这句）**：架构师需要**理解业务需求，判断业务需求中的关键点和复杂点，然后设计适合业务和团队的架构**；过程中有大量沟通（与业务、团队、老板、协作部门），**通过沟通获取非常多的显性和隐性信息**。

  **E. 「大模型能否取代架构师」——四个理由（结论：不能）**
  1. **沟通信息无法完整输入**：架构设计前需要大量沟通，大模型无法完全胜任；不可能把沟通过程获取的所有信息都输入给模型（效率极低），且**很多隐性信息或潜意识判断无法直接感知、也无法用语言精确描述**。即便造一个大模型机器人参与讨论也不行——这些信息**碎片化且有差异化**，要让模型据此判断需要非常多类似案例训练，而企业业务/团队/技术一直在变，**辛苦训练几个月甚至 1 年，可能还没训练完训练资料就过时了**。
  2. **概率生成 vs 差异化诉求本质冲突**：模型输出「要么是大而全的，要么是业界常用的方案」；架构师的方案虽含共性部分，但**和团队及业务相关的部分才是关键**。企业为获得竞争优势必然有大量业务差异化与特殊性，**这正好与大模型的技术本质矛盾**。原文给出一张大模型生成的架构方案图，评语是：看似面面俱到，**实际不能真正指导开发团队实现，很像「PPT 架构师」的输出**。
  3. **利益干系人的平衡与「江湖」无法参与**：架构设计要平衡取舍各方诉求，涉及人类情感与人际关系——「有人的地方就有江湖」，大模型连理解都做不到，更不用说参与。原文举例：团队换了新来的阿里系高 P 领导、偏爱阿里云技术，你做架构设计时不得不考虑；而模型无法完成这种「考虑」，也无法体会你是要站队、先观察、还是坚持己见。
  4. **「预训练」本质决定无法创新**：只能在**已有成熟技术**中挑选和设计，无法创造新的架构思路或方案。例：谷歌 **2008 年三篇大数据论文**开创大数据时代，驱动因素是原有技术方案都已无法满足业务发展，技术团队**开创性**地创造新思路；大模型不具备这种创新能力。

  **F. 进化建议（4 条）**
  1. **掌握大模型相关技术**：深入原理、应用场景、优势与局限；思考如何与现有系统和业务集成、如何用大模型优化架构设计（如学微调技术做业务定制）。
  2. **成为业务领域专家**：保持对业务创新的敏感度，了解新技术/新模式/新趋势并融入架构；理解核心流程、关键指标、发展趋势，**从业务战略层面结合大模型和 AI 做架构规划**。
  3. **推动技术创新与实践**：把大模型与区块链、物联网等结合，探索新架构模式与应用场景，通过实践积累经验。
  4. **利用大模型提升能力**：借大模型快速了解新兴技术（如边缘计算、量子计算与架构设计的结合点），获取学习资料与路径推荐，制定个性化学习计划。

  **G. 方法论层面的两个否定（原文的「怎么判断」）**
  - 否定「先研读 100 篇 AI 经典英文论文才能判断」：**这是错误的思维**；正确做法是**基于大模型的技术本质和架构师岗位的核心能力综合判断**。
  - 否定「凡新技术浪潮就焦虑」的默认反应：原文承认 AI「确实在某些岗位上正逐步取代人类」，但把架构师岗位单独拿出来论证。

### ChatGPT 来临，架构师何去何从？

> 文件：`08-特别放送 (7讲)__ChatGPT来临，架构师何去何从？.txt`

- **核心结论**
  ChatGPT 是 OpenAI **2022 年 11 月底**推出的聊天机器人，**推出仅两个月月活估计已达 1 亿**，成为史上增长最快的消费应用。它的技术本质仍是「用大量已有数据训练算法模型，模型按概率输出回答」。**结论：ChatGPT 不能取代架构师，「至少在 5~10 年内不用担心」**，理由四条：业务需求差异性无法训练、架构判断无法标准化、技术不断演进、架构师需要创新能力。但技术人员的**技能与学习方式必须升级**；最可能被取代的是「**标准化的常规工作**」。

- **完整判据/清单/步骤**

  **A. 爆火的两个判据（能力表现 + 增长数据）**
  - 能力表现：回答「几乎和真人聊天的感觉类似」，上下文**有连贯逻辑性**；能根据描述**直接写代码、写论文、写报告**。
  - 增长数据：**2 个月 1 亿月活**；对比 TikTok 用 **9 个月**、Instagram 用 **两年半**。
  - 历史定位：上一个如此火热的是围棋 **AlphaGo**（击败李世石后带起 AI 热潮）。

  **B. GPT 的技术本质与三个能力缺陷**
  - 本质：「用大量已有的数据去训练算法模型，然后算法模型根据概率输出回答结果。」
  - 缺陷 1：**数据样本量越少，训练结果越差**（案例：学员调侃 ChatGPT 的回答「一本正经的瞎扯」，内容大部分是阿里云王坚博士的资料）。
  - 缺陷 2：**数据无法及时更新**（案例：《流浪地球 2》相关提问；训练数据只到 **2021 年底**）。
  - 缺陷 3：**历史数据对未来影响很大**（案例：前几年中台流行，若用大量中台内容训练，2022 年已没人讲中台，模型回答架构设计时**仍会输出大量中台内容**）。

  **C. 架构师职责与四个能力关键词**
  - 本质：「**业务和技术的桥梁**」。
  - 核心职责链：深入理解业务需求 → **判断**业务需求带来的系统复杂度 → **设计**备选方案来应对或降低复杂度 → 基于各种情况做**取舍**。
  - 四个关键词：**理解、判断、设计、取舍**。

  **D. 「不能取代」的四条理由**
  1. **业务需求的差异性无法训练**：即使同为电商商品评论功能，淘宝/京东/拼多多的具体做法都有很多细节差异；新创业公司做法又不同；同一公司同一业务**换个产品经理需求就可能调整**。ChatGPT 目前**不具备理解特定场景下的人类语言**，简单说就是**没法和客户讨论需求**，而架构师必须理解业务才能设计。
  2. **架构设计过程中的判断无法标准化**：要按**利益干系人诉求、团队技术水平、业务发展情况**做判断与取舍，这些**不能标准化也不能被训练**；涉及和人打交道，「有人的地方就有江湖」，模型无法理解特定团队里人情世故的微妙关系。例：**同样的业务、同样的团队，换个 leader 就可能导致架构推翻重来**。
  3. **技术不断演进**：用旧架构文档和方案训练，模型需要很长时间和大量数据才能更新；而技术圈演进极快——「前几年还大火的中台，到无人问津只需要不到 1 年时间；去年火热的低代码，今年可能就被替换为云原生了」；且训练数据只到 2021 年底。
  4. **架构师需要创新能力**：谷歌三篇论文开创大数据时代、**Redis 的诞生、Nginx 的横空出世**都需要创新；而模型本质是基于已有数据训练，**目前难以做到真正有价值的创新**。

### 加餐｜单服务器高性能模式性能对比

> 文件：`08-特别放送 (7讲)__加餐｜单服务器高性能模式性能对比.txt`

- **核心结论**
  第 18、19 讲讲 PPC/TPC、Reactor/Proactor 只给了理论、**没有实测数据**（作者无完整测试环境、不能用公司服务器压测）。本篇摘录一份网络公开的 Linux 服务器网络模型系列文章（作者 shuveb，unixism.net + GitHub `zerohttpd`）的**7 种模式实测对比**，并给出读表方法：**「横向看对比，纵向看转折」**。最重要的结论是：**epoll 不是万能的**，并发 2000 以内各模式性能相差无几；超过 10000 后单进程 epoll 也开始下降——这正是**Redis 用单进程 Reactor、Nginx 必须用多进程 Reactor** 的原因。

- **完整判据/清单/步骤**

  **A. 7 种模式与课程术语的映射（必须先对齐名词）**
  | 原文模式名 | 对应课程术语 |
  |---|---|
  | iterative | 迭代式（每请求一进程、串行） |
  | forking | **PPC** |
  | preforked | **prefork**（预派生进程） |
  | threaded | **TPC** |
  | prethreaded | **prethread**（预派生线程） |
  | poll | poll 多路复用 |
  | epoll | **Reactor** |

  **B. 读表方法（可迁移的分析技巧）**
  - **横向看对比**：固定并发数，比较各模式性能。例：并发 1000 时 **preforking、prethreaded、epoll 三者性能相近** → 说明 epoll 并非在任何场景都优于其它模式。
  - **纵向看转折**：沿单一模式看随并发增长的拐点。例：prethreaded（源码设 **100 个线程**）在 **11000 并发**时性能 **2200**，到 **12000 并发**时**急剧下降到 970** → 推测触发 **C10K** 问题，**线程上下文切换的性能消耗超越 IO 处理**，成为系统瓶颈。

  **C. 六条解读结论（原文逐条）**
  1. **创建进程的消耗是创建线程的消耗的 4 倍左右**。
  2. **并发 2000 以内**时，preforked、prethreaded、epoll 性能**相差无几**，甚至 preforked 和 prethreaded 有时还**稍高**。→ 推论：**内部系统、中间件等并发不高的系统并不一定需要 epoll**，用 preforked/prethreaded 能达到相同性能，**且实现更简单**。
  3. 并发达到 **8000 以上**，只有 **pthreaded 和 epoll** 能继续运行，但性能也有下降，**epoll 下降更平稳**。
  4. prethreaded 在 **12000 并发**时性能急剧下降，**推测触发 C10K**，线程上下文切换消耗超越 IO 处理。
  5. **poll 随并发数增多稳定下降**，因为需要**遍历的描述符越多性能越低**；select 原理类似（作者未单独写），区别是 **select 最大支持连接数受限于 `FD_SETSIZE` 参数**。
  6. **epoll 在并发超过 10000 时性能开始下降，但比较平稳**。隐含关键设计点：**epoll 不是万能的，连接数太多时单进程 epoll 也不行**。→ **Redis 用单进程 Reactor**（内部访问，并发一般不超 10000）；**Nginx 必须用多进程 Reactor**（互联网访问，并发很容易超过 10000）。

  **D. 数据可信度声明（原文自带的边界）**
  - 测试环境未详细说明：作者只提到**租来的云服务器、CPU 只有 1 核**（未说型号），**内存、带宽、磁盘均未介绍**，只能假设硬件性能足够。
  - 为什么仍可参考：「从理论上来说，网络模型的核心性能部件就是 CPU，因此如下数据是具备参考意义的。」
  - **完整数据表以图片给出，纯文本中缺失**；本篇可引用的具体数字仅有正文点名的 **2200 / 970**（11000 / 12000 并发）与 **100 个线程**。

  **E. 拓展学习（原文给的三条）**

  2. 测试代码仓库：`https://github.com/shuveb/zerohttpd`

### 加餐｜扒一扒中台皇帝的外衣

> 文件：`08-特别放送 (7讲)__加餐｜扒一扒中台皇帝的外衣.txt`

- **核心结论**
  中台概念自 **2015 年阿里提出**，**2019 年起**被大会与公众号大力宣扬，但「绝大部分谈中台的都是做中台的」，**用中台的人很少出来评价**。作者以**两个真实使用方项目**（手游交易系统迁移到电商中台、在支付中台上从 0 到 1 搭钱包）为依据，从**使用者视角**给出四条针对「中台价值」的批判与两条针对「中台效果」的批判。**结论不是否定中台，而是：中台不是灵丹妙药，也不是放之四海而皆准；明确适应场景和坑才能落地。**

- **完整判据/清单/步骤**

  **A. 作者的立场与证据资格（先立可信度）**
  - 没真正负责做过中台，但**做过平台和中间件**；更重要的是**参与过两个基于中台的业务项目**（手游交易系统→电商中台；支付中台从 0 到 1 搭钱包），因此**不用质疑「中台能力不行」「组织能力不行」才会有这些问题**。
  - 对「唱衰」的反驳机制：一说中台有问题，就有人跳出来说「你们能力不行」「中台是一个业务、组织、技术的协同，你们肯定是组织没保证」。
  - 方法论前提（作者的技术理念）：「没有完美的技术，没有放之四海皆好的技术，如果你只能看到一项技术的好处，而看不到坑，那实际上很可能就会掉到坑里去。」

  **B. 四条核心论点（针对「中台的价值」）**

  **论点 1：业务部门并不独立**
  - 宣称：中台让各业务部门保持相对独立和分权、保证敏感性与创新性，同时用强大平台总协调、平衡集权与分权、降低组织变革成本。
  - 实际：基于中台的业务被**分为不同优先级**；**大业务对中台的影响力远大于小业务，核心业务远大于新业务**。因为**中台也有 KPI**，而 KPI 大部分来源于所支持的业务，大业务天然在 KPI 数据上占优。形象说法：**「中台抱大业务的大腿，小业务抱中台的大腿」**。
  - 后果：大业务的创新**不管是不是共性**，中台都鼎力支持（因为「是不是共性需求」由**中台自己判断**，而不是每次拉所有业务方评估投票）；小业务被拒只需一句「你这个业务不通用」「你这个需求太特殊」。
  - 小业务无处申诉：**不存在仲裁委员会之类机构**；就算有，**去仲裁的时间都够你自己把业务实现 5 遍了**。即便被认定为共性需求，小业务也可能因优先级被排到「很后面」——**不是几天几周，很可能几个月半年**。而**初创业务一开始规模必然小**，基于中台的开发模式**很可能制约创新业务的快速发展**，除非该创新业务一开始就有重量级人物挂帅、对中台有足够影响力。

  **论点 2：中台并不总是能够提炼共性需求**
  - 口径校准：这里的「需求」**不是**「交易」这个粒度，而是「交易」系统里**一个个实际的功能点**；坚持说「交易」是共性需求，**这实际上是一句正确的废话**。
  - 为什么建设期能提炼：**从 0 到 1 建设时**已经有多个业务需求样本，哪些共性哪些个性比较容易分析出来。
  - 为什么建成后不能：**业务方总期望把自己的需求划为共性**（这样中台出人实现）；**中台总期望先别划为共性**，等多个业务都有类似需求再抽象提炼（否则中台每个需求都当共性，**中台会累死**）。
  - 决定性事实：**几乎不太可能出现多个业务同时提出某个需求**——除了**国家颁布的法律法规相关需求**外，绝大部分业务需求都是**某个业务方先提出**的；此时中台**无法判断是否为共性**，只能回到潜规则：**优先满足大业务，拒绝小业务**（大业务做了数据好看、KPI 有保证；小业务就算以后被证明是共性，前期做了也没多少数据，费力不讨好）。

  **论点 3：中台的「轮子」会不断变化**
  - 误解：「避免重复造轮子」被理解为「中台把轮子造好，业务方直接用」。
  - 实际：轮子造好了，但**每隔一段时间就换一遍**（数据模型、接口、架构都要随业务发展变化）。为了「复用」目标，**推出新轮子后就不再长期维护老轮子**——否则同时维护 **4~5 个相似的轮子**，复用就无从谈起。于是**基于中台的业务必须在某个时间段内完成轮子切换，相当于被动做了一次架构演进**。
  - 与「没有中台也会演进」的差异：**中台的架构演进频率比独立业务架构更快**，因为**中台融合了多个相似业务的发展**。例：中台支持 10 个业务，其中 1 个发展很快，中台必须跟着演进，**剩余 9 个即使毫无发展也必须跟着被动演进**；若 10 个都在发展，演进更快。
  - 有没有技术能让中台演进不影响业务？**绝大部分情况下都不可能**，这是由本质决定的：**中台演进的绝大部分动力来源于业务，不可能反过来不影响业务**。这点与**技术平台（存储、消息队列）不同**——技术平台的演进动力来源于**技术更新**，可以做到不影响业务。

  **论点 4：中台是某类业务的中台，不是所有业务的中台**
  - 逻辑：中台本质是提炼共性需求复用；**业务差异太大则复用度不高**，提炼与维护中台的代价**抵不上复用的价值**。
  - 命名判据：应该叫「**电商中台**」「**支付中台**」「**物流中台**」「**出行中台**」「**视频中台**」「**保险中台**」，而**不应该是「阿里中台」「腾讯中台」「百度中台」「滴滴中台」**。
  - 「技术中台」的名实之辨：现在很多原来做中间件和技术平台的团队把「XX 平台」改名为「技术中台」，**从广义角度也可以**（存储、缓存、消息队列确实是各业务线共性需求）；但通常说中台时的「需求」指的是**业务需求**（客户可以使用到的功能）。
  - 推论：**即使只看到「茅台云商」这种中台项目的 PPT，也能大概率推断该项目失败可能性非常高**（因为跨业务域差异过大）。

  **C. 两条「效果」批判**

  **论点 5（效果 1）：业务方对中台的能力「很清楚地不知道」**
  - 宣称：中台让业务方清楚体系里有什么能力、能更快理解选择使用；中台提供基础解决方案，业务方按需定制即可更快。
  - 实际：**几乎没有人能完整知道中台里各个域、各子系统的能力**，更谈不上业务方更快理解选择使用。理由：一张中台架构 PPT 满满一页甚至几页、大框小框**几十上百个**，对应线上系统可能**几百上千个**，这么复杂的系统**不可能有人知道所有功能与细节**。
  - 「定制一下就能上线」的悖论：除非**复制一个和已有业务基本一样的业务**，否则基本不可能。因为中台方案必然是基于已有业务抽象出的「共性需求」大集合：
    - **可定制化度高 → 可复用度低**；
    - **可定制化度低 → 可复用度高，但业务可扩展度低**；
    - 而**从本质出发，中台必然选「可定制度低、可复用度高」**，于是**只有复制一个非常类似的新业务时，中台方案才有很大价值**——但对同一公司来说，**为何要复制两个基本一样的业务呢？** 若真有中台选「可定制度高」，当新业务与已有业务差异较大时，**大量工作量会耗费在定制那部分**，方案同样没多大价值。
  - 真实运作方式：中台分很多「**域**」（交易、搜索、会员等），业务方写出需求，**拉上各域的产品接口人和技术接口人，一个域一个域讨论**。以会员域为例：业务方讲解需求 → 会员域接口人评估哪些能力支持、哪些不支持 → 不支持的部分判定是共性还是个性 → **共性**要给中台修改方案，且方案**要会员域架构师评审**（因为改中台影响所有业务）；**个性**要设计中台与业务方的交互方式（接口、配置、扩展包等）。
  - 代价数据：「编码的时间确实少了，但是**前期的沟通和后期的联调非常耗时间**，随便做个什么项目，**拉上 20~30 人算一般的，稍微大点的项目拉上 50~100 人也是很正常**。」

  **论点 6（效果 2）：中台所谓的「快」并没有严谨的衡量**
  - 现有论证的问题：各类文章都说「有了中台开发快」，但**没有详细案例和分析到底有多快**；仅有的几个案例「看起来很夸张，但没有详细背景描述其实并没有说服力」——某个业务上线快，到底是因为**第一版功能很简单**、还是**第一版投入了大量人力**、还是**真的用了中台**？
  - 作者实测：两个接入中台的项目**看不出快**。需求讲解与讨论、方案设计讨论、后期业务系统与中台系统联调，**这些工作量并没有减少，反而还有一定程度的增加**，因为中台在分析需求、设计方案、联调测试时要**考虑对其它业务的影响**。
  - 效率提升只体现在两处：① **编码工作量确实会少**（大量代码可重用）；② **中台人员对已有类似业务和技术很熟悉**，需求确认和方案设计更高效。**全流程综合来看，很难判断效率到底高还是低。**
  - 反例对照：作者在阿里游戏做过几个从 0 到 1 的项目，老板重视，**把原类似系统的核心开发人员拉过去**、代码从原系统拷贝改，**开发效率一样很高**——核心原因简单说就是「**熟手开发**」。

  **D. 结论与「正确姿势」**
  - 作者自陈：总体看像在质疑中台，**其实不然**；中台的好处已有太多文章，本篇补的是**使用者视角**。
  - 落到架构设计三原则的**第一条「合适原则」**：**「中台不是灵丹妙药，不要有问题就想着用中台解决；中台也不是放之四海而皆准，明确中台的适应场景和可能的坑，才能更好地落地中台！」**
  - 引用提出中台的逍遥子的告诫：**「中台并不适用于每家公司的每个阶段。在独立业务拓展期、突破期，一定用独立团、独立师、独立旅建制来做」，否则就会变成瓶颈；但发展到一定阶段、出现太多山头时，就要「关停并转、要合并同类项。问管理要效率，取消重复性建设」。**

- **反例与坑**

  2. **以为小业务也能公平获得中台资源** —— KPI 决定优先级，小业务被「不通用」一句话拒掉。
  3. **以为共性需求会被客观识别** —— 判断权在中台，且几乎没有多业务同时提需求的场景（除法规）。
  4. **以为轮子造好就稳定** —— 每轮换代都不再维护老轮子，业务被迫跟着迁移。
  5. **做「阿里中台」式的跨域大中台** —— 业务差异大 → 复用度低 → 代价超过价值，应叫「电商中台/支付中台」。
  6. **用「某业务上线快」当中台有效的证据** —— 缺背景（功能简单？人力堆叠？），不构成论证。
  7. **只看编码工作量下降就判定提效** —— 沟通与联调增加，全流程未必更快。
  8. **相信「中台演进不影响业务」** —— 与技术平台不同，中台演进动力来自业务，必然传导。

### 如何高效地学习开源项目｜“华仔，放学别走！”第 3 期

> 文件：`08-特别放送 (7讲)__如何高效地学习开源项目丨“华仔，放学别走！”第3期.txt`

- **核心结论**
  对开源项目**不能采取「拿来主义」**——看似很快实现需求，但技术水平没有提升，甚至出现「用了很多开源项目、知道很多项目名，技术却止步不前」的窘境。正确方法是**「自顶向下」五步：安装 → 运行 → 原理研究 → 测试 → 源码研究**，其中**源码不是第一步，而是最后一步**。时间安排上：**前三步必做，第四步在准备采用时做，第五步按时间灵活安排**；宁可**每季度吃透一个**，也不要蜻蜓点水。

- **完整判据/清单/步骤**

  **A. 四个必须先破除的误区（原文逐条列出，附反驳）**
  | 误区 | 原文反驳 |
  |---|---|
  | 「只有开发这些开源项目的人才能真正理解，我没法参与开发，因此很难深入理解」 | 不管什么身份都可以学到很多东西；要理解 Redis 的网络模型，**不需要成为 Redis 开发者**，也不需要一定要用到 Redis，只要具备一定网络编程基础 + 读源码即可 |
  | 「我的项目没有用 Redis，不用的话很难深入理解」 | 同上：**不需要一定要用到**才能学 |
  | 「数据结构和算法很重要，所以我只要研究其数据结构和算法就够了，例如 Nginx 用的红黑树」 | 这两点在学习开源项目时**并没有那么重要**；Nginx 用红黑树管定时器，**知道这点就够了**，不必研究其红黑树源码如何写，除非你要改这部分（作者认为极少人有此需求） |
  | 「Talk is cheap, show me the code」，一头扎进源码逐行阅读 | 效率太低、效果也不好；**应先掌握功能、原理、关键设计，再看源码**，看源码的目的是**学代码写作方式与关键技术实现** |

  **B. 三个正确观念（先立后破）**
  1. 不管你是什么身份，**都可以从开源项目中学到很多东西**。
  2. **不要只盯着数据结构和算法**，这两点在学习开源项目时并没有那么重要。
  3. **采取「自顶向下」的方法，源码不是第一步，而是最后一步**。

  **C. 「自顶向下」五步（完整保留）**

  **第一步：安装**（远不止「照手册敲命令」）
  通过安装过程可获取三类关键信息：
  - **① 依赖组件**——依赖是系统设计与实现的基础。
    - Nginx 源码安装依赖：**pcre、pcre-devel、openssl、openssl-devel、zlib**；光看名字就能推测：openssl 可能和 HTTPS 有关，zlib 可能和压缩有关。
    - Memcache 最大依赖是 **libevent**；既然 libevent 是高性能网络库，就能**大概推测 Memcache 的网络实现应该是 Reactor 模型**。
  - **② 安装目录**——提供使用与运行的基本信息。
    - Nginx 安装后目录：`conf` 放配置、`logs` 放日志、`sbin` 是运行程序，**但 `html` 是什么？** 这个疑问会促使你继续研究。
    - Redis 安装后**只有一个 `bin` 目录**——大部分人看到会惊讶「这也太简单了」，尤其是与 Nginx 相比；于是自然产生疑问：Redis 如何配置？日志保存在哪里？**带着问题去学习效率最高**。
  - **③ 系统提供了哪些工具**——如 Redis 的 `redis-benchmark`、`redis-check-aof`，从名字能猜出使用场景，这些工具在**故障定位处理、性能测试**时可能非常方便。

  **第二步：运行**（重点看**命令行**和**配置文件**）
  - 二者提供两个关键信息：**系统具备哪些能力**、**系统将会如何运行**；是「窥视系统内部运行机制和原理的一扇窗口」。
  - Memcache 启动参数例：可看出 ① 支持 **UNIX socket 通信和 TCP 通信**；② 可以**指定内存大小**；③ `lock memory` 看起来和内存有关，但**具体是什么意思？配置和不配置有什么区别？**
  - 作者的习惯（强判据）：**「不管三七二十一，先把所有的配置项全部研究一遍」**——包括配置项的原理、作用、影响，并**尝试修改配置项看系统变化**。例：把 Memcache 的 `--conn-limit` 改为 **1**，观察多个连接请求时返回什么错误、记录什么日志。
  - 经验阈值：**如果把每个命令行参数和配置项的作用和原理都全部掌握清楚了，基本上对系统已经很熟悉了。**

  **第三步：原理研究**（关键在「**系统性**」三个字）
  - 「系统性」体现在**两个方面**：
    - **① 关键特性的基本实现原理**——每个流行项目受欢迎都有卖点（高性能、高可用、可扩展），**这些牛 X 的技术实现就是我们要学习的地方**。
      - Memcache 高性能 = **基于 libevent 实现高性能网络模型 + 内存管理 Slab Allocator 机制**；要彻底理解其网络模型，需掌握**多路复用、Linux epoll、Reactor 模型、多线程**等知识 → 学到「一个具体项目如何把这些东西全部串起来」。
      - React 的 **Virtual DOM**：实现原理是什么、为何要实现、如何构建 Virtual DOM 树、与 DOM 什么关系 → 即使不用 React，也能学到**如何写出高性能前端代码**。
    - **② 优缺点对比分析**（原文「特别强调」）——**只有清楚掌握技术方案的优缺点后才算真正掌握这门技术**，也只有掌握优缺点才能在架构设计时做出合理选择。方法：**把两个类似的系统对比，看实现差异以及不同实现的优缺点**。
      - 典型对比：**Memcache 用多线程 vs Redis 用单进程**各自优缺点；Memcache 与 Redis 的**集群方式**各自优缺点；即使 Redis 自身，也可对比 **RDB 与 AOF** 两种模式。
  - **原理研究的三种手段**：
    1. **通读项目的设计文档**——如 **Kafka 的设计文档**基本涵盖消息队列设计的关键决策；**Disruptor 的设计白皮书**详细阐述 Java 单机高性能的设计技巧。
    2. **阅读网上已有的分析文档**——热门项目已有大量分析，可站在前人基础上避免重复投入；**但**不同人经验/水平/关注点不同，结论可能有差异甚至错误，**不能完全参照**；好方式是**多方对照**：看很多篇，比较共同点与差异点。
    3. **Demo 验证**——资料难查、自己不确定时，**真正写 Demo 验证**，通过打印日志或调试理解细节。例：写一个简单的分配内存程序，用 `jmap`、`jstat`、`jstack` 观察 JVM 垃圾回收的具体表现。

  **第四步：测试**
  - **什么时候必须测**：如果**真的准备在实际项目中使用**，**必须自己测**；只是自己学习研究，可以看网上的测试文档（构建完整测试用例费时费机器）。
  - **为什么不能照搬别人的结果**：别人的测试结果**不一定与你的业务场景契合**，简单参考很可能得出错误结论。例：**开源系统版本不同，测试结果可能差异较大**；同样 K-V 存储，**别人测的 value 是 128 字节，你的场景 value 达到 128k 字节**，结果差异很大。
  - **铁律（原文强调）**：**「测试一定要在原理研究之后做，不能安装完成立马就测试！」** 原因：不熟悉系统时，很可能**命令行、配置参数没用对**，或**运行模式选择不对**，导致没按业务特点搭对环境、没设计合理用例，最终**得出错误结论、误导设计决策**。
  - **反例（原文实例）**：曾有团队**安装完 MySQL 5.1 后就做性能测试**，结果「让人大跌眼镜」，定位后发现 `innodb_buffer_pool_size` **用的是默认值 8M**。

  **第五步：源码研究**
  - 目的：**学习原理背后的具体编码如何实现**，用这些技巧提升编码能力。
  - 典型可学点：**Redis 的 RDB 快照、Nginx 的多 Reactor 模型、Disruptor 如何用 volatile + CAS 做无锁设计、Netty 的 Zero-Copy**。
  - **不建议通读源码**：想掌握每行代码含义和作用非常耗时，尤其 **MySQL、Nginx 这种规模的项目，即使是它们的开发人员，都不一定每个人都掌握了所有代码**。要**带着明确目的**研究，做到有的放矢——**这也是源码研究放在最后的原因**。
  - 技巧：对**基础库**，可以自己写 Demo 调基础库完成简单功能，然后**通过调试看调用栈**理解处理逻辑，比单纯看代码更高效。例：**Netty 4.1 版本的 telnet 服务器样例调试堆栈**，通过堆栈看到完整调用栈。

  **D. 时间分配（原文的取舍判据）**
  - **前三步**：不管是已成为架构师还是立志成为架构师的人，研究开源项目时**都必不可少**。
  - **第四步**：可以在**准备采用**该项目时才实施。
  - **第五步**：根据时间**灵活安排**——「灵活安排」**不是省略不做**，而是在有一定时间和精力时做，因为只有这样才能真正理解和学到具体技术。
  - 时间不够时的策略：**与其蜻蜓点水每个项目都简单了解，不如集中精力把一个研究通透**；**就算每个季度只学习一个开源项目，积累几年数量也很可观**；而且**把一个项目研究透以后，再研究其他类似项目会非常快**——共性部分已掌握，只需学差异部分。

- **数字与阈值**

  **D. 问：架构师沟通能力的重要性**
  - 为什么重要：架构师是**业务和技术之间的桥梁**，通常还**确定整体项目的步骤**。
  - 三个沟通方向（判据）：**既要说得动老板**，让老板支持自己的设计决定；**又要镇得住技术人员**，让技术人员信服自己的设计选择；**还要能够理解业务**，结合业务不同发展阶段设计合适架构，**所以也要参与产品和项目决策**。
  - 为什么沟通难：架构设计过程中**存在很多判断和选择，且不一定都有明确量化的标准**，因此**不同的人有不同看法是普遍情况**；架构师要**专业能力过硬 + 良好沟通技巧**，促使**业务、项目、技术三方达成一致**。
  - **关键边界**：**「架构师的核心能力还是技术能力，过硬的技术才是良好沟通的基础」**；否则单纯靠沟通技巧甚至花言巧语，**一次两次可能奏效，但后面被打脸打多了，也就没人信任了**。

  **E. 问：甲方不顾业务需要、只要业界流行技术就要求采用，怎么符合三原则？（「架构约束」概念）**
  - 第一层：**业务第一，先把订单签下来**，才有后面的架构设计；硬说甲方要求不合理导致订单都拿不到，**那是没有意义的**。
  - 第二层（关键判据）：这种情况归为**「架构约束」**——**这不是架构师能够选择的，而是架构师必须遵守的**，因此**这里不需要使用「架构设计三原则」来判断**。
  - 第三层（约束之下仍可用原则）：架构师仍可应用三原则**指导设计**。例：客户要求用 **Docker**，Docker 网络模式有 **5 种**，**host 模式比 bridge 模式用起来简单** → 就用 host；客户再要求统一管理 Docker → 自研管理平台还是直接用 **Kubernetes**？**按简单原则，肯定用 Kubernetes**。
  - 结论性表述：**三原则「主要是指架构师在选择和判断时采取的指导原则」**；当**架构的基本需求或约束必须被满足**时，架构师的选择是「**采取什么样的方案能够更好地满足这些需求和约束**」。

### 架构师成长之路｜“华仔，放学别走！”第 4 期

> 文件：`08-特别放送 (7讲)__架构师成长之路丨“华仔，放学别走！”第4期.txt`

- **核心结论**
  专栏相当于一部《九阳真经》（招式），但「要成为高手，光知道招式还远远不够，更重要的是**内功和判断**」。架构师内功 = **判断力 + 执行力 + 创新力**，内功来源于 **经验 + 视野 + 思考**；从程序员到架构师的总原则是 **「积累经验，拓宽视野，深度思考」**。按此原则，成长分**六个典型阶段：工程师 → 高级工程师 → 技术专家 → 初级架构师 → 中级架构师 → 高级架构师**，每阶段的实践方法差别很大，**在正确的阶段采取错误的方法会事倍功半**。

- **完整判据/清单/步骤**

  **A. 为什么「只学招式」不够（以「合适原则」为例的论证）**
  - 专栏讲了「合适原则」、不要过度设计，能避免盲目超前设计；但**「到底什么是合适」专栏给不出放之四海皆准的标准**，因为「合适」和很多因素有关：**业务发展、团队规模、技术实力、领导的喜好**等。
  - 后果：**同一个团队，A 架构师认为 X 方案合适，B 架构师认为 Y 方案合适，原因就在于不同的架构师「内功」不一样**。
  - 定位：高手的差别在「**什么时候用什么招式**」「**遇到什么对手用什么招式**」。

  **B. 内功三部分（逐条定义）**
  | 内功 | 定义（原文） | 武侠类比 |
  |---|---|---|
  | **判断力** | 能够准确判断**系统的复杂度在哪里** | 像武侠高手一样，能准确看出对手的破绽和弱点 |
  | **执行力** | 能够使用**合适的方案解决复杂度问题** | 能选择合适的招式或方法打败对手 |
  | **创新力** | 能够**创造新的解决方案**解决复杂度问题 | 小创新是创新招式；武学宗师能创立新的武学或心法，如张三丰创立太极拳 |

  **C. 内功的三个来源（逐条 + 为什么）**
  1. **经验**：设计过的系统越多、系统越复杂，内功越强；**不管是成功的架构还是失败的架构，不管是踩坑的经验还是填坑的经验，都将成为内功的一部分**。
  2. **视野**：掌握的知识和技能越多、越深，内功越强；「**他山之石可以攻玉，站在巨人的肩膀上会看的更高更远**」。
  3. **思考**：经验和视野都是**外部输入**，类似我们吃的食物，**光吃还不行，还要消化**，将其变成自己的营养——**思考**能把经验与视野中的**模式、判断、选择、技巧**提炼出来为我所用，也能促使产生新的创意和灵感。

  **D. 六个阶段（阶段描述 / 典型特征 / 与前阶段区别 / 成长指导 / 年限）**

  **① 工程师（1~3 年）**
  - 典型特征：**在别人的指导下完成开发**。「别人」主要是高级工程师或技术专家——他们负责需求分析和讨论、方案设计，工程师负责编码实现，并由他们指导。
  - 定位：最原始的「**基础技能积累阶段**」，主要积累基础知识：编程语言、编程工具、各类系统的基本使用。
  - Java 后端需积累：Java 语法与基本数据结构；**Eclipse、IDEA、Maven、Linux 命令行**等工具；数据库 CRUD、缓存基本使用；业务系统的基本流程。
  - 成长指导：**最好的方法是找经典书籍系统学习**，而不要「遇到一个问题到网上搜搜然后就解决了事」；以 Java 为例，《Java 编程思想》《Java 核心技术》《TCP/IP 协议》这类**大部头一定要完整看一遍**，即使很多内容当前工作用不上。

  **② 高级工程师（2~5 年）**
  - 典型特征：**独立完成开发**——需求分析、方案设计、编码实现；其中需求分析与方案设计**已经包含「判断」和「选择」**，只是范围较小、**更多是在已有架构下设计**。
  - Java 后端要回答的问题例：MySQL 表**设计成两个表还是三个表**？是否用缓存、**缓存的 Key 和 Value 如何设计、更新策略是什么**？产品提出的需求**是否合理、是否有更好的方式满足**？
  - 成长指导：主要「**积累方案设计经验**」——表设计、缓存设计、业务流程设计、接口设计经验；接到需求时能**组合这些设计经验**完成。
  - 与工程师的**两个典型差异**：
    - **深度**：工程师知道 **How**，高级工程师要知道 **Why**（如 Java 各种数据结构的实现原理，只有掌握原理才能理解优缺点与使用场景，进而在方案设计时选对数据结构）。
    - **理论**：前人总结的成熟设计经验，如**数据库表设计的 3 个范式、面向对象的设计模式、SOLID 设计原则、缓存设计理论（缓存穿透、缓存雪崩、缓存热点）**。
  - 具体手段：技术深度靠**系统学习（看书 + 研究源码）**——研究 JVM 看《深入理解 Java 虚拟机》、研究 MySQL 看《MySQL 技术内幕：InnoDB 存储引擎》、研究 Memcache 看源码；设计理论**没有一本书能覆盖**，更多靠网上搜索，判据是「**假设每个设计环节都有设计理论，然后带着这种假设去搜索验证**」。

  **③ 技术专家（4~8 年）**
  - 典型特征：**某个领域的专家**——「只要这个领域的问题，技术专家都可以解决」，如 Java 开发专家、PHP 开发专家、Android/iOS/前端开发专家。
  - **领域粒度的判据**：「领域」范围**不能太小**——可以说「Java 开发专家」，但**不会说「Java 多线程专家」或「Java JDBC 专家」**。
  - 与高级工程师的典型区别：高级工程师在**已有架构框架下**设计；技术专家会**根据需要修改、扩展、优化架构**。例：同样 Java 开发，高级工程师关注**如何优化 MySQL 查询性能**，技术专家可能考虑**引入 Elasticsearch 完成搜索**。
  - 成长指导：主要「**拓展技术宽度**」，因为一个「领域」必然涉及众多技术面。Java 后端要掌握 Java 多线程、JDBC、JVM、面向对象、设计模式、Netty、Elasticsearch、Memcache、Redis、MySQL 等。
  - 拓展宽度的两种方法：**学习业界成熟开源方案**（Java 学 Redis/Memcache/Netty；Android 研究 Retrofit/Fresco/OkHttp）；**研究业界经验分享**（BAT、FANG 等大公司经验，可通过技术大会近距离了解）。
  - **判据（防伪）**：拓展宽度**不是只知道技术名词**，而要深入理解**原理、优缺点、应用场景**，否则就是「**PPT 技术专家**」。例：知道 Netty 是高性能网络库远远不够，还要学其原理以及如何用它开发高性能系统。

  **④ 初级架构师（5~10 年）**
  - 典型特征：**独立完成一个系统的架构设计**——可以是从 0 到 1 设计新系统，也可以是把架构从 1.0 重构到 2.0。负责的系统复杂度相对不高，如**后台管理系统、某个业务下的子系统、100 万 PV 量级的网站**。
  - 与技术专家的典型区别：**架构师基于完善的架构设计方法论指导设计，技术专家更多基于经验设计**。「即使是同样一个方案，初级架构师能够清晰地阐述架构设计的理由和原因，而技术专家可能就是因为自己曾经这样做过，或者看到别人这样做过而选择设计方案。」
  - 现实提醒：实践中二者**区别并不很明显**，很多技术专家实际承担了初级架构师角色——因为系统复杂度不高时**架构设计难度不高，不同备选方案最终都能较好完成**。例：设计日 PV 100 万的网站，**MySQL + Memcache + Spring Boot** 可以，**MongoDB + Redis + Nginx + php-fpm** 也可以，备选方案设计与选择并不太难，**更多是看团队熟悉哪个技术**。
  - 成长指导：最主要形成自己的「**架构设计方法论**」（架构设计目的、原则、步骤、模式）；同类方法论还有《**恰如其分的软件架构：风险驱动的设计方法**》和《**领域驱动设计**》。
  - 三个手段：① **系统学习架构设计方法论**（订阅专栏或读书）；② **深入研究成熟开源系统的架构设计**——与专家阶段关注点不同：专家阶段聚焦「**如何更好地应用**」，初级架构师阶段聚焦「**学习其架构设计原理和思想**」（如 Kafka 文档中关于消息队列架构设计的分析与取舍）；③ **结合方法论分析总结自己团队/公司各种系统的架构设计优缺点，尝试思考架构重构方案**；若能真推动重构更好——既实践方法论、积累经验，又展现实力、**拿到结果**。

  **⑤ 中级架构师（8 年以上）**
  - 典型特征：**能够完成复杂系统的架构设计**——含高性能、高可用、可扩展、海量存储等，例如**设计一个和 Kafka 性能匹敌的消息队列系统、将业务改造为异地多活、设计一个总共 100 人参与开发的业务系统**。
  - 与初级架构师的典型区别：**系统复杂度不同**。以开源项目为例：初级架构师**引入某个开源项目**就能完成设计；中级架构师可能发现**没有哪个开源项目合适，需要自己开发一个全新的项目**——「事实上很多开源项目就是这样诞生出来的」。
  - 成长指导：最关键的是「**技术深度和技术理论的积累**」：
    - **技术理论**：**CAP、BASE 是异地多活的设计理论基础；Paxos 是分布式一致性的基础算法；2PC、3PC 是分布式事务的基础算法**等。
    - **技术深度**：**Kafka 用磁盘存储还能高效是因为磁盘顺序写；Disruptor 高性能是结合 CPU 预读取机制、缓存行、无锁设计；Storm 的高效异或确认机制；Flink 的分布式快照算法**等。
  - 为什么这一阶段才关键（回答「不是早该学了吗」）：高级工程师/技术专家阶段即使学了也**较难理解透彻**、更**难以有机会应用**，多数时候只是「知道有这个技术点」；到中级架构师面对高复杂度系统时，**往往就是几个关键技术细节决定整个架构设计的成败**，或者**某个设计方案理论上就不可行**——不深刻理解理论与关键技术点，很难设计优秀架构。
  - 作者自证：很早「知道」CAP，但**仅仅知道几个概念**；真正做异地多活时**走了不少弯路**，试图做完美的异地多活系统，最终发现不可能，某天突然顿悟——**CAP 理论早已明确指出了这点**，但最初学习时很难有这样深刻的理解。

  **⑥ 高级架构师（10 年以上）**
  - 典型特征：**创造新的架构模式**。例：**谷歌大数据论文**创造分布式存储架构、分布式计算 MapReduce 架构、列式存储架构，开创大数据时代；在有 MapReduce 的背景下，**Storm 创造了流式计算架构**；在虚拟机很成熟的背景下，**Docker 创造了容器化的技术潮流**。
  - 与中级架构师的典型区别：**「创造性」**——能创造新架构模式、开创新的技术潮流。
  - 成长指导（作者坦承没有太好指导）：原因一是「我自我评价目前顶多算个中级架构师」；二是**一旦涉及「创造性」，其实和艺术就比较类似了，创造性实际上是很难学会的，也很难由老师教会，更多是天分，或者某种场景下灵感爆发**。
  - 但总结出**创造性架构可能诞生的四个背景条件**：
    1. **足够复杂的业务场景**——谷歌的大数据、阿里双十一、Facebook 的海量用户；业务越复杂，技术挑战越大，越可能产生创造性突破。
    2. **足够强大的技术团队**——绝大部分创造性架构来源于大公司或知名研究机构；**没有技术实力支撑，想突破也心有余而力不足**。
    3. **不满足于现状的态度**——虚拟机很成熟但资源占用太多，所以发明 Docker；MapReduce 难以实时运算，所以创造 Storm 流式运算。
    4. **尊重技术价值的文化**——创造性的东西往往需要投入大量人力和时间，且**刚开始一般都不会很成熟**；如果**完全结果导向、KPI 导向，创新技术很可能在萌芽阶段就被否定**。

  **E. 收束与自评动作**
  - 依据「**10000 小时定律**」：要成为某领域顶尖专业人才，需持续不断 10000 小时练习（小提琴、足球、国际象棋、围棋等领域无一例外）；作者认为**技术人员成长也基本遵循这个定律**。
  - 但最关键的仍是「**技术人员对技术的热情以及持续不断地投入**，包括学习、实践、思考、总结等」。
  - **自评动作（原文给的具体做法）**：统计自己**从头到尾认真读过的技术书籍数量**、**系统研究过的开源项目数量**，然后自我评估目前处于哪个层级，看是否有什么发现。

### 结束语｜坚持，成就你的技术梦想

> 文件：`09-结束语 (1讲)__结束语丨坚持，成就你的技术梦想.txt`

- **核心结论**
  专栏历经 **4 个月**结束，「这不是提升架构设计能力的结束，而是架构设计能力提升的开始」。成长路线图里的方法都遵循 **10000 小时理论**——**10000 小时 ≈ 10 年 × 每年 1000 小时 ≈ 每天 3 小时**，时间不短，因此「对于绝大部分人来说，也许理论、方法、技巧都知道，但最难的就是『坚持』」。作者给出**三个坚持：坚持梦想、坚持学习、坚持输出**。

- **完整判据/清单/步骤**

  **A. 10000 小时的换算（判据链）**
  - 10000 小时 → **10 年** → **每年 1000 小时** → **平均每天约 3 小时**；结论：时间不短，**最难的是坚持**。

  **B. 坚持梦想**
  - 背景：几乎每个技术人员心中都有架构师梦想，因为**架构师代表了技术路线发展的巅峰**；但「既然是巅峰，就像登山一样，必然会有一段很长的路，路途中也会有很多的障碍，也肯定会有很多的迷茫，甚至很多时候会感到痛苦」。
  - 心态判据：遇到这些问题时**一定要坚持梦想，因为所有这些问题都是正常的，也是必须的**。
  - 核心命题：**「所谓成长，其实就是不断学习、不断踩坑、不断填坑的过程。」**
  - 作者自证：曾遇到**自己开发的系统上线就回滚**、曾**为了异地多活方案而想破脑袋**；当时觉得困难，回头看「正是经历困难以后自己的收获才最大」。
  - 回报描述：成长为架构师、看到自己亲自设计的系统上线，「那种创造的感觉真的是让人感到喜悦和自豪」；**「前面的山路越崎岖，山顶的风景才会越美！」**

  **C. 坚持学习**
  - 依据「架构师成长之路」：从工程师到架构师**就是一个不断学习的过程**——学基础知识、学理论知识、学业界新技术、研究开源系统、研究业界实践；**既要有技术广度，又要有技术深度**，「总之就是学无止境」。
  - 态度转换：承认「求求各位大神别变了，学不动了」的真实感受，但**带着好奇心深入研究**时会感叹设计和技术确实厉害——「就像欣赏一幅优美的画作、观看一部震撼的电影、阅读一本精彩的书籍一样」。
  - 学习案例链（技术演进的自证）：谷歌大数据论文 → 觉得 **MapReduce** 好牛 → **Storm** 流式计算更厉害 → **Flink** 又创造了更厉害的流式计算架构。
  - 时间投入问题：另见文章《大牛养成指南：吃的草够多，你也能成为大牛》。

  **D. 坚持输出**
  - 定义：把学到的东西再传授给他人，包括**培训、演讲、写博客、写书**等，是**非常好的提升自己的手段**。
  - 机制（为什么有效）：很多东西「感觉自己学了也懂了」，但**一跟别人交流就可能回答不上来**，或**一写博客就发现还有很多细节没考虑**，需要重新研究或考证；作者写专栏时也一样——「很多知识点我原来以为自己掌握得很深刻了，但一旦写出来就发现还有很多地方没有考虑到或者没有想清楚」。
  - 附加收益：锻炼**表达能力、临场反应能力**——这是大多数技术人员**比较欠缺但又比较关键**的能力；技术人员要有更好职业发展，**不能只是埋头干活，也需要跟别人沟通交流**，而输出是**最方便的锻炼方法**：**不需要承担管理职责就可以锻炼，任何级别都可以**。
  - 门槛判据（很低）：**不一定需要长篇大论，也不一定需要篇篇 10W+**，只要觉得某个点其他人也可能遇到，**哪怕写 100 字的博客也是可以的，关键点在于持续地输出**。

  **E. 总收束**
  - 三个「坚持」是**除技术本身以外**，技术人员成长的几个关键点；从工程师到架构师是**个人综合修炼的过程**——既提升技术能力，也修炼综合素质。
