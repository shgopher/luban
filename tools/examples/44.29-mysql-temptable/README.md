# 44.29-mysql-temptable：临时表、内部临时表与 Memory 引擎

[44.29 临时表、内部临时表与 Memory 引擎](../../../v2/L4-组件与技术/44-数据库/44.29-临时表与Memory引擎.md) 的配套实验（MySQL 8.0.46，Docker）。

## 跑法

```bash
cd tools/examples/44.29-mysql-temptable
bash code/run.sh                 # 默认端口 33199
PORT=33310 bash code/run.sh      # 33199 被占用时换一个
```

- 只需要：`docker`（能拉 `mysql:8.0`）+ `bash`。**不需要本机装 MySQL 客户端**，所有 SQL 都通过 `docker exec` 在容器内执行（容器内用 TCP `-h127.0.0.1` 连接，避免撞上初始化阶段的临时实例）。
- 脚本自己 `docker run -d --rm` 起容器、`trap cleanup EXIT` 收尾（`docker rm -f`），不写卷、不留数据。
- 总耗时约 2–8 分钟，取决于机器负载（其中重启那一步固定等 15 秒左右）。
- 换镜像：`IMAGE=mysql:8.0.46 bash code/run.sh`。

### ① 用户临时表：同名共存、对别人不可见、断开即删

会话 A 自己看：`show create table t1` 返回的是**临时表**（注意 `CREATE TEMPORARY TABLE`），`select *` 只有 1 行；而服务端记的内部名字是 `#sql1_b_0`（`1` 是 `server_id`，`b` 是线程 id 的十六进制，本会话 `connection_id()=11`）。

```text
| t1 | CREATE TEMPORARY TABLE `t1` (
  `id` int NOT NULL, `a` int DEFAULT NULL, `b` int DEFAULT NULL,
  `note` varchar(20) DEFAULT NULL, PRIMARY KEY (`id`)
) ENGINE=InnoDB ... |

+-----+------+------+-------------+
| id  | a    | b    | note        |
+-----+------+------+-------------+
| 100 |  100 |  100 | temp-shadow |
+-----+------+------+-------------+

+----------+-----------+
| table_id | name      |
+----------+-----------+
|     1071 | #sql1_b_1 |
|     1070 | #sql1_b_0 |
+----------+-----------+
```

同一时刻会话 B：

```text
+-------------+          +----------------+
| Tables_in_d |          | normal_t1_rows |
+-------------+          +----------------+
| t1          |          |           1000 |
| t_big       |          +----------------+
+-------------+
ERROR 1146 (42S02) at line 14: Table 'd.t_tmp2' doesn't exist
```

A 断开后：

```text
+------------------+
| temp_tables_left |
+------------------+
|                0 |
+------------------+
```

临时表在 `information_schema.TABLES` 里查不到（0 行），只有 `innodb_temp_table_info` 能看到它（1 行）。

### ② 临时表与 binlog：ROW 不记、STATEMENT 才记

`binlog_format=ROW` 时建/写/删临时表，binlog 里一个事件都不多。切到 `STATEMENT` 后：

```text
| binlog.000003 |  448 | Query | 1 |  567 | use `d`; CREATE TEMPORARY TABLE temp_t LIKE t_normal_binlog             |
| binlog.000003 |  722 | Query | 1 |  824 | use `d`; INSERT INTO temp_t VALUES (1,1)                                 |
| binlog.000003 | 1056 | Query | 1 | 1175 | use `d`; INSERT INTO t_normal_binlog SELECT * FROM temp_t                |
| binlog.000003 | 1283 | Query | 1 | 1409 | use `d`; DROP TEMPORARY TABLE `temp_t` /* generated by server */          |
| binlog.000003 | 1486 | Query | 1 | 1620 | use `d`; DROP TABLE `t_normal_binlog` /* generated by server */ /* xid=3081 */ |
```

### ③ 内部临时表：UNION 要、UNION ALL 不要

```text
|  3 | UNION RESULT | <union1,2> | ... | Using temporary |      -- UNION

| Variable_name           | Value |
| Created_tmp_tables      | 1     |     -- UNION
| Created_tmp_tables      | 0     |     -- UNION ALL
```

`UNION ALL` 的 `EXPLAIN` 只有两行，没有 `UNION RESULT`。给它加外层 `ORDER BY`，`UNION RESULT` 行会重新出现，`Extra` 变成 `Using temporary; Using filesort`。

### ④ GROUP BY 的三种形态

```text
-- 无索引列分组：临时表
| ... | index | a | 1000 | Using index; Using temporary |

-- 生成列 + 索引
| ... | index | z | 1000 | Using index |

-- SQL_BIG_RESULT
| ... | index | z | 1000 | Using index; Using filesort |

-- 分组后再按聚合结果排序
EXPLAIN SELECT b, count(*) AS c FROM t1 GROUP BY b ORDER BY c DESC;
| ... | ALL | NULL | 1000 | Using temporary; Using filesort |
```

### ⑦ 案例：10 万行 GROUP BY 的改造前后

```text
-- 改造前：b 无索引
-> Table scan on <temporary>  (actual time=398..410 rows=50000 loops=1)
    -> Aggregate using temporary table  (actual time=398..398 rows=50000 loops=1)
        -> Table scan on t_big  (cost=10085 rows=100129) (actual time=2.15..94.7 rows=100000 loops=1)

-- 加 index(b) 之后
-> Group aggregate: count(0)  (cost=20098 rows=50220) (actual time=0.336..74.7 rows=50000 loops=1)
    -> Covering index scan on t_big using idx_b  (cost=10085 rows=100129) (actual time=0.312..43.1 rows=100000 loops=1)

-- SQL_BIG_RESULT（加了索引之后）
-> Group aggregate: count(0)  (cost=20098 rows=50220) (actual time=165..215 rows=50000 loops=1)
    -> Sort: t_big.b  (cost=10085 rows=100129) (actual time=165..175 rows=100000 loops=1)
        -> Index scan on t_big using idx_b  (cost=10085 rows=100129) (actual time=0.21..51.1 rows=100000 loops=1)
```

另一次运行的同一组数字是 750ms / 187ms / 228ms。

## 会浮动的数

| 数 | 浮动原因 | 正文写法 |
|---|---|---|
| `memory_wait_seconds` | A 的 `update` 里 `sleep(5)`，B 的 `SET @t0` 晚 1 秒左右；两次跑出 3.73 / 4.73 / 4.02 | 看量级：秒级 vs 毫秒级 |
| `innodb_wait_seconds` | `UPDATE` 本身的延迟，0.02–0.15 秒都正常 | 同上 |
| `EXPLAIN ANALYZE` 的 `actual time` | 受机器负载影响最大，本机两次跑 410ms / 750ms（改造前） | 正文给两次的值与区间 |
| 微基准（临时表插入、等值查询） | 差 2–3 倍很常见，只看"谁占优"不看绝对值 | 正文给两次的值 |
| `t_big` 造数耗时 | 10 万行 `INSERT ... SELECT` + 递归 CTE，2–20 秒 | 不影响结论 |
| `Created_tmp_files` | 只有把 `temptable_max_ram` 调到最小（2MB）才出现，默认 0 | 正文引用"3 个文件"那次是单独实验，不在 `run.sh` 里 |
| `table_id` / 内部临时表名字 | 每次起容器都变 | 只解释 `#sql1_<thread_id 十六进制>_<序号>` 的构成 |

`DATA_LENGTH`（`511008` / `4116992`）、`Created_tmp_*`、`mem_rows_*`、`innodb_temp_table_info` 的行数变化是确定性结果，多次跑一致。
