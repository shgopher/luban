# 24.10 事务对象怎么沿 ctx 传递 (可运行复现)

对应正文：[24.10 本地事务的工程落地](../../../v2/L1-分布式原理/24-分布式事务/24.10-本地事务的工程落地.md)

## 这段代码证明什么

用内存表模拟数据库，只依赖标准库，把 “事务对象传递” 的四种命运跑成可比的输出：

| 场景 | 写法 | 结果 |
|---|---|---|
| ① | 事务内两次写，第二次返回错误 | 全部回滚 |
| ② | 子函数把 ctx 换成 `context.Background()` | 子函数的写**逃出事务**，回滚后成孤儿行 |
| ③ | panic 且没有 `defer Rollback` | 数据未落库，但事务悬挂（`activeTx=1`，连接不归还） |
| ④ | 嵌套 `TX`（保存点） | 内层回滚，外层照常提交 |

## 跑法

```bash
cd tools/examples/24.10-txctx
go run .
```

无外部依赖、无数据库、无网络。

## 期望输出

```text
① 正确：事务内两次写，第二次失败 → 全部回滚
   已提交：[]  activeTx=0
② 子函数换成 Background → 事务丢失，留下孤儿行
   已提交：[uc_secret:s2]  activeTx=0
③ panic 且没有 defer Rollback → 事务悬挂
   已提交：[]  activeTx=1
④ 嵌套事务 = 保存点：内层回滚，外层提交
   已提交：[uc_user:u3]  activeTx=0
```

第 ② 行是本节的核心证据：`uc_secret` 落了库，而同一业务里的 `uc_user` 被回滚 —— 程序不报任何错。

## 假设与边界

- **这是结构模拟，不是 MySQL**：`Tx` / `Commit` / `Rollback` 被简化成 “暂存行追加进已提交列表”，用于说明事务对象必须一致；隔离级别、锁、MVCC 行为不在此例 (见 [44.10 事务与隔离级别](../../../v2/L4-组件与技术/44-数据库/44.10-事务与隔离级别.md))。
- **`activeTx` 是模拟的连接占用**：真实 GORM 里对应连接未归还连接池，长时间不释放会耗尽池子；这里只用来暴露 “既没提交也没回滚”。
- **输出完全确定**：无并发、无随机、无时间依赖，任何机器上输出一致。
- GORM 的真实行为 (`Transaction` 返回错误自动回滚、嵌套用保存点) 以 GORM 文档与本节代码摘录为准；本示例验证的是 “tx 是否同一个” 这个不依赖 ORM 的结构问题。
