# 36.5-cellfit：单元化可行性算账

[36.5 单元化 / Set 化架构](../../../v2/L3-质量属性/36-灾备/36.5-单元化-Set化架构.md) 的配套代码：把「该不该做单元化」算成五道门——**故障损失、P99 税、一次性投入、回本周期**，而不是靠“大厂都这么做”。

它不设计单元、不给路由算法（那是正文的事），只回答决策问题：这一刀现在砍不砍。

```bash
cd tools/examples/36.5-cellfit
go run .                        # 默认：日活 500 万、4 单元、RTO 240→5 分、跨单元 75%
go run . -ops                   # 补上“有单元级灰度与演练”这道门
go run . -cross 0.93 -cells 16 -hops 4 -ops   # 关系型业务硬切 16 单元
go test ./...                   # 爆炸半径 / P99 尾巴 / 两道门 / 回本 5 个用例
```

  增量基础设施 144 万/年；净年收益 811 万

  3 跳串联 → 页面 P99 ≈ 110 ms（预算 300 ms）

## 输出节选（关系型业务硬切 16 单元）

```text
  ✗ ③ 跨单元请求 < 90%          当前 93.0% ≥ 90%：改路由键或按关系聚类（同城/同商户/同群）打映射表，而不是继续加单元
```

## 模型与假设（都能改）

| 项 | 默认值 | 公式 / 来源 | 性质 |
|---|---|---|---|
| 故障损失 | 2 次/年 × 240 分 × 2 万元/分 | `次 × 分钟 × 每分钟损失 × 影响比例` | 每分钟损失必须由业务给 |
| 单单元影响比例 | `1/N` | 4 单元 = 25% | 与 [36.5](../../../v2/L3-质量属性/36-灾备/36.5-单元化-Set化架构.md) 的爆炸半径表一致 |
| 单元隔离后 RTO | 5 分 | 切流量 + 摘单元 | 假设已具备自动摘除与切流 |
| 页面 P99 | 110 ms | `(1−p)^K < 0.99` 时取 `slow + (K−1)×fast` | 单跳 1% 概率慢到 100ms；K=3 时全快概率 97.03% |
| 一次性投入 | 276 万 | `人月 × 人月单价 + 增量设施 × 3 个月` | 迁移期双跑 3 个月 |
| 净年收益 | 811 万 | `年减少损失 − 增量设施/年` | 不含研发效率与组织成本 |
| 回本 | 4.1 个月 | `一次性投入 ÷ (净年收益/12)` | 超过 24 个月判“先别做” |

- 60 人月、4 万元/人月、2000 元/分…都是**示例值**，换成你自己的数；结论只对这套数成立。
- P99 模型是**刻意简化**的：真实延迟分布有多个档位，这里只保留“快/慢”两档，用来说明“串联跳数会把尾巴放大”这一机制，不要拿它当压测结论。
- 回本月数不含停机迁移带来的业务损失，那笔账要单独算。

## 冷启动（只读一句话的人也能用）

1. 你的业务**真的**有跨地域写冲突吗？没有 → 停，去 36.4 买同城双活。
2. 算出年故障损失与一次性投入，回本 > 24 个月 → 停，先投备份与演练。
3. 跨单元请求 ≥ 90% → 停，先改路由键或聚类，别加单元。
4. 页面 P99 超预算 → 先降串联跳数（并发、本地缓存、异步化）。
5. 五道门全过，才谈“先搬读、再搬写、双写校验”。
