## marker 传播与一致性：一个小仿真

「记下通道状态就一致」只看四条算法步骤很难信服：通道里到底压着哪些消息、谁在什么时候记、漏记一条会怎样。用 3 个进程、3 条通道、5 笔消息把 marker 的传播跑一遍，把每个进程实际记录的内容和核对结果打出来，比背步骤有用。

**设定**：P0 初始余额 100（快照前的历史账，代表已入账的状态），拓扑 P0→P1（通道 c01）、P0→P2（c02）、P1→P2（c12）；5 笔数据消息 d1=10、d2=20、d3=5、d4=7、d5=8，初始余额加已发金额共 150。P0 在 t=5 发起快照；此时 P1 已消费 d1=10，d4=7 已在 c12 在途，d5=8 要到 P1 收到 marker 之前才发出。

| 时刻 | 事件 | 快照记录 |
|---|---|---|
| t=5 | P0 记录本地状态 100，向 c01、c02 各发 1 条 marker | 发起者完成 |
| t=6 | P1 消费 d2，余额变 30 | 计入本地状态 |
| t=6.5 | P2 消费 d3，余额变 5 | 计入本地状态 |
| t=7 | P1 收到 c01 的 marker：记录 30，向 c12 转发 marker | c01 通道状态记空 |
| t=7.5 | P2 收到 c02 的 marker：记录 5，c12 进入缓冲 | c02 通道状态记空 |
| t=8–9 | P2 收到 d4、d5：不加余额，改记 c12 通道状态 | c12 累计 7+8=15 |
| t=10 | P2 收到 c12 的 marker，定稿通道状态 [d4 d5] | 快照完成 |

三个进程最后记录的内容如下，注意「通道状态」只记在接收方名下，且第一条 marker 所在入边按定义记为空：

| 进程 | 本地状态 | 通道状态（入边） | 完成条件 |
|---|---|---|---|
| P0 | 100（发起时） | 无入边 | 发起即完成 |
| P1 | 30（d1+d2） | c01=[] | 唯一入边 marker 到齐 |
| P2 | 5（d3） | c02=[]；c12=[d4 d5]（15 元） | c02、c12 两条入边 marker 都到 |
| 合计 | 135 | 15 | 总额 150 |

**一致性怎么核对**，不是看「像不像同时刻」，而是三条可判定的账：

1. **每条消息恰好出现一次**：5 条消息在「各进程本地状态 ∪ 各通道状态」里命中 5 条，缺失 0、重复 0；
2. **总额守恒**：135 + 15 = 150 = 初始 100 + 已发 50；
3. **marker 数与边数相等**：3 条边各 1 条 marker，共 3 条，即 O(E)；本仿真里 5 条业务消息中有 2 条（40%）被记成通道状态。

```go
// 收到第一条 marker：记录本地状态，向所有出边转发 marker，其余入边进入“缓冲”状态。
func (s *sim) record(p *process, edge string) {
	p.recorded = true
	p.firstEdge = edge
	p.snapLocal = p.balance
	p.snapApplied = append([]string(nil), p.applied...)
	if edge != "" {
		p.snapChan[edge] = []string{} // 首条 marker 的入边，通道状态按定义记为空
		p.finished = 1
	}
	for _, e := range p.in {
		if e != edge {
			p.buffering[e] = true
			p.snapChan[e] = nil
		}
	}
	if edge == "" {
		p.finished = len(p.in) // 发起者：没有入边，直接视为完成
	}
	s.logf("%s 记录本地状态 balance=%d，此后沿出边转发 marker", p.name, p.balance)
	p.done = p.finished >= len(p.in)
	for _, e := range p.out {
		s.markerOf(p, e)
	}
}
```

本机仿真输出（`go1.27.1 / darwin/arm64 / Apple M1`，原始输出 `.cache/pilot2-25.5/raw.txt`）：

```text
运行 A（FIFO，算法前提成立）：
  P1 本地状态=30  已应用消息=[d1 d2]
     通道 c01 状态=[]（在途 0 条 / 0 元）
  P2 本地状态=5  已应用消息=[d3]
     通道 c02 状态=[]（在途 0 条 / 0 元）
     通道 c12 状态=[d4 d5]（在途 2 条 / 15 元）
      消息覆盖：已发 5 条，缺失=[]，重复=[]
      marker 数=3（= 边数 3）
      判定：一致（每条消息恰好出现一次，总额对得上）
运行 B（非 FIFO，marker 在 c02 上超过 d3）：
  P2 本地状态=0  已应用消息=[]
      消息覆盖：已发 5 条，缺失=[d3]，重复=[]
      判定：不一致（漏了 [d3]，快照缺 5 元）
```

同一套代码只改一个自由度——让 marker 在 c02 上超车——快照就从 150 掉到 145。这不是实现 bug，而是算法前提被拿掉的必然后果：P2 把 c02 的通道状态按定义记成空之后，d3 才到；按算法它只对「其余入边」缓冲，对第一条 marker 的入边不再回看，于是 d3 既不在本地状态、也不在通道状态。恢复时少入账 5 元，正好是那笔在途的钱。

把「错法」并排看，三种失败模式各自对应一笔明确的账：

| 错法 | 快照总额 | 与应得 150 的差 | 恢复后果 |
|---|---|---|---|
| 只记本地状态，不记通道 | 135 | 少 15 | 丢 c12 在途的 d4、d5 |
| 先消费在途再记状态，且仍记通道 | 165 | 多 15 | d4、d5 被重复入账 |
| 非 FIFO 仍用 marker | 145 | 少 5 | 丢 d3 |
| 记状态时机正确 + 通道状态正确 | 150 | 0 | 一致 |

拓扑也有讲究：如果把 3 个进程排成一条链，每个进程只有一条入边，那么每条入边都是「第一条 marker 的入边」，通道状态全部为空——快照退化成各进程各拍各的本地状态，根本看不出通道状态的作用。P2 同时有 c02、c12 两条入边，才有「第一条入边记空、第二条入边缓冲」的分工；这是能出现 15 元在途账的最小拓扑。通道状态记在接收方名下而不是发送方：发送方不知道自己发出的消息对方消费到哪，只有接收方能界定「我记状态之后、marker 之前到达的是哪些」。

为什么边界必须钉在「收到第一条 marker 的那一刻」？早记与晚记各错一边。若 P2 在 t=6 主动先记（d3 还没到），之后 d3 在 marker 之前到达，它既不在快照的本地状态里，也不在通道状态里——快照变成 145；若 P2 等 d4、d5 都消费完再记（晚记），同时又按 c12 的 marker 把 [d4 d5] 记进通道状态，同一笔 15 元就被算了两次——快照变成 165。只有「marker 到达即记」把分界线钉死：marker 之前到达的进本地状态，之后到达的进通道状态，两者互斥且穷尽。

P1 的转发也不是可选项：P2 的 c12 入边要等到 P1 的 marker 才知道「c12 上 marker 之前的数据到此为止」。P1 不转发，P2 的快照会一直挂起；P1 转发的 marker 排在 d4、d5 之后（FIFO），才让 P2 有机会把这两笔记进通道状态。

还有一个容易被忽略的开销结构：本仿真里 3 条 marker 对 5 条业务消息，看起来是 60% 的额外消息；但 marker 数只与边数 E 有关，与业务消息量无关。业务流量越大，这 3 条 marker 的占比越接近 0——所以「marker 贵不贵」不能拿小样本的消息比例判断，要按边数与快照频率算。

在工程实现里，「可靠且 FIFO」不是自动成立的：同一条 TCP 连接内的字节流有序，Kafka 同一分区内有序，跨分区、跨连接、经过重试队列的通道都可能乱序。用 marker 前先确认通道的序保证，乱序通道要么先做序号重排，要么退回同步快照。

同步快照与 Chandy-Lamport 的差别也就能算出来了——不是「谁更先进」，而是**用停顿换简单、还是用通道状态换不停顿**：

| 维度 | 同步快照（全局暂停） | Chandy-Lamport（marker） |
|---|---|---|
| 业务停顿 | 全集群停一次，时长 = 最慢节点保存状态的时间 | 无全局停顿，各进程收到 marker 才短暂记录 |
| 协调方式 | 中心协调者发暂停/恢复指令，两阶段 | 无中心，发起者只发 marker |
| 在途消息 | 暂停后全局无在途，通道状态恒为空 | 必须记录通道状态：本仿真 15/150 元，占 10% |
| 控制消息 | O(N)，N 为进程数 | O(E)，本仿真 E=3，共 3 条 marker |
| 快照体积 | 只含 Σ 本地状态（135） | Σ 本地状态 + Σ 通道在途（150） |
| 前提 | 能全局暂停（锁/GC/协调者） | 可靠 FIFO 通道；非 FIFO 示例丢 5 元 |
| 适用 | 小集群、可停业务、离线备份 | 在线流处理、大集群、抖动敏感的业务 |

> 🔑 判据：**通道状态的大小 = 快照时刻的在途消息量**。在途占比可忽略（低于 1%）时，同步暂停更简单；在途占比不可忽略或业务不能停时，才值得引入 marker。本仿真在途占比 10%，暂停一次要等最慢节点，CL 的 3 条 marker 更便宜。

> 🔑 快照一致性是**消息守恒**，不是「某一物理瞬间的复制」。核对时盯住「每条消息恰好一次」与「状态 + 在途 = 初始 + 已发」，两项对得上才叫一致；只看各进程余额加起来像不像，会把丢失与重复一起漏掉。

复现方式：源码在 `.cache/pilot2-25.5/main.go`，`go run main.go` 会依次跑 A、B 两组；把 `newSim(false)` 改成 `newSim(true)` 就是非 FIFO 组，其余事件序列不变，便于对照。

在真实流处理系统里，这个仿真的三个量可以直接变成监控指标：快照体积（Σ 状态 + Σ 通道）、对齐等待时长（marker 到齐的间隔）、在途消息占比。第三个指标一旦抬头，就该考虑非对齐快照——它把「等 marker 期间到达的数据」也写进快照，用更大的快照体积换掉对齐期的反压（[62.3 状态管理与容错](../../L4-组件与技术/62-实时计算与流处理/62.3-状态管理与容错.md)）。
