                                                                                                            01 为什么要学习网络协议？

                                                                                                            核心结论 协议的本质是三要素：语法、语义、顺序；计算机语言是人与一台机器的协议，网络协议则让一大片机器互相协作。一次下单依次穿过应用层、传输层、网络层、MAC 层，每层只加自己的头，交给下一层接力。TCP 的重试是传输层自己的事，不是浏览器重新下单。

                                                                                                            机制细节

                                                                                                            • 协议三要素：语法是内容要符合规则和格式，例如括号成对、结束使用分号；语义是内容要代表某种意义，例如数字减数字有意义、数字减文本一般没意义；顺序是先干啥后干啥，例如先加某个数值再减某个数值。
                                                                                                            • HTTP 返回样例的字段与结构：首行"HTTP/1.1 200 OK"，随后是 Date、Content-Type: text/html;charset=UTF-8、Content-Language: zh-CN 等首部，空行之后是 HTML 内容；顺序是先状态、再首部、再内容。
                                                                                                            • 下单链路：输入 URL https://www.kaola.com → 用 DNS 或 HTTPDNS 查地址簿 → 得到 IP 106.114.138.24 → 普通浏览用 HTTP、购物支付用 HTTPS，包内写明买什么、买多少 → 经 socket 交给传输层 → 支付多用 TCP（保证到达、不到就重发），也可用无连接的 UDP → TCP 头里有两个端口，一个浏览器监听、一个电商服务器监听，操作系统按端口把包交给进程 → IP 头写源 IP 与目标 IP → 判断目标是本地还是外地，外地走网关，网关 IP 由 DHCP 在启动时配置（例 192.168.1.1）→ 用 ARP 大吼"谁是 192.168.1.1"，取网关 MAC → 网卡从 MAC 层发出 → 网关按路由表定下一跳，路由协议常用 OSPF 和 BGP → 逐跳更换本地 MAC，最后一跳用 ARP 找到目标服务器 MAC → 目标服务器摘 MAC 头、摘 IP 头，按 IP 头里的协议标识交给 TCP → TCP 回一个"收到"的包，丢包则由发送端 TCP 重发 → 按目标端口找到监听该端口的进程（例如 Tomcat）→ 进程间用 RPC 通知订单、库存、支付 → 回一个 HTTPS 包，原路返回浏览器。

                                                                                                            判据·清单·步骤

                                                                                                            1. 用三要素检查报文：格式、含义约定、收发先后。
                                                                                                            2. 排一次下单经过的层：应用层（DNS/HTTP/HTTPS）→传输层（TCP/UDP）→网络层（IP）→MAC 层。
                                                                                                            3. 判断目标在不在本网段：不在就发给默认网关，而不是直接发目标主机。
                                                                                                            4. 网关选下一跳靠路由表，本网段定位靠 ARP 得到的 MAC 地址。
                                                                                                            5. 排查丢包先看 TCP 是否在重发，别急着重发业务请求。

                                                                                                            数字·阈值

                                                                                                            • 404：HTTP 状态码，表示不成功，即常见的"404"。
                                                                                                            • 106.114.138.24：示例中 www.kaola.com 解析出的 IP 地址。

                                                                                                            02 网络分层的真实含义是什么？

                                                                                                            核心结论 网络包就是一段有格式的 Buffer，处理它的程序按层摘头、按头里的信息决定丢弃、转发还是自己留着。分层的真实含义是层层封装，像套娃娃，而不是各层各自开会。判断一台设备是几层设备，只看它摘到第几层头。

                                                                                                            机制细节

                                                                                                            • 程序视角：想象自己有很多网口，从某个口拿进一个包，处理后再从另一个口发出；网口可配混杂模式，凡是经过的包全部拿进来。
                                                                                                            • 收包函数链：process_layer2(buffer) 摘掉二层头，看 MAC 地址是否与自己相符，相符才继续；process_layer3(buffer) 时 Buffer 里已无二层头（或偏移量已移动），摘掉三层头，IP 不是自己的就转发、是自己的就上交；再按 IP 头里的标识选择 process_tcp(buffer) 或 process_udp(buffer)；四层头里看这是发起、应答还是正常数据包，分别处理；没有 process_http，四层头里的端口号决定交给哪个应用。
                                                                                                            • 发包函数链：send_tcp(buffer) 加 TCP 头并记录源端口，目的端口一般由浏览器给出、常见为 80；send_layer3(buffer) 加 IP 头，记录源 IP 和目标 IP；send_layer2(buffer) 加 MAC 头，源 MAC 是本机，目标 MAC 知道就填、不知道就先通过协议解析出来，"反正要填一个，不能空着"；内容完整后从网口发出。
                                                                                                            • 封装次序：HTTP 头与内容 → TCP 头 → IP 头 → MAC 头，逐层套在外层。
                                                                                                            • 设备判据：二层设备收进整个网络包，只摘 MAC 头，决定丢弃、转发还是自己留着；三层设备摘完 MAC 头再摘 IP 头，再作同样判断。

                                                                                                            判据·清单·步骤

                                                                                                            1. 拿到一个包，先问它在哪一层被摘头。
                                                                                                            2. 二层看 MAC 是否匹配，不匹配按转发/丢弃处理。
                                                                                                            3. 三层看 IP 是否本机，不是就转发。
                                                                                                            4. 四层看端口，把载荷交给监听该端口的应用。
                                                                                                            5. 遇到二层设备的包里有没有 HTTP 这类问题，回到"只要是在网络上跑的包，都是完整的"这一条判断。

                                                                                                            04 DHCP与PXE：IP是怎么来的，又是怎么没的

                                                                                                            核心结论 IP 不能乱配：只有目标与某块网卡同网段才发 ARP，跨网段必须走网关，而网关必须与网卡同网段，否则包根本发不出去。DHCP 用四步广播把地址租出去，租期过半续租；PXE 把 DHCP 当引路人，靠 next-server 与 filename 找到服务器，再用 TFTP 拉启动文件。

                                                                                                            机制细节

                                                                                                            • 手工配置：ifconfig eth1 10.0.0.1/24 再 up；或 ip addr add 10.0.0.1/24 dev eth1 再 ip link set up eth1；正式环境把 CIDR、掩码、广播地址、网关写进配置文件。
                                                                                                            • 跨网段判断：Linux 先判断目标是否与本机某网卡同网段，同网段才发 ARP 求 MAC；不同网段则把包发给网关并取网关 MAC；没有网关，包压根发不出去。
                                                                                                            • DHCP 四包：①Discover，源 0.0.0.0、目的 255.255.255.255 广播，UDP 封 BOOTP，报出 MAC、说明还没有 IP；②Offer，仍用广播（新人没有 IP），给出可用 IP、子网掩码、网关、租用期，并保留该地址；③Request，广播它接受的租约，含 MAC、接受的 IP、提供租约的服务器地址，并请其他服务器撤销其提供的 IP；④ACK，广播确认，放入合法租用信息和其他配置。
                                                                                                            • 续租：租期过去 50% 时向提供该 IP 的服务器发 DHCP request，收到 ACK 后按新租期与更新后的 TCP/IP 参数更新配置。
                                                                                                            • PXE 启动链：BIOS 读硬盘 MBR 启动扇区 → 启动 GRUB → GRUB 加载内核与作为根文件系统的 initramfs → 权力交给内核 → 内核启动。装系统只能插在 BIOS 之后，因为没装系统时连启动扇区都没有；PXE 客户端只能先放在 BIOS 里，开机时调入内存。
                                                                                                            • PXE 五步：DHCP 拿到 IP、PXE 服务器地址、启动文件 pxelinux.0 → 用 TFTP 下载该文件 → 执行后向 TFTP 请求配置 pxelinux.cfg → 配置告知内核与 initramfs 在哪里，再请求这些文件 → 启动 Linux 内核。
                                                                                                            • DHCP 配置项：除地址段、子网掩码、网关、租期外，用 next-server 指向 PXE 服务器、用 filename 指定初始启动文件。

                                                                                                            判据·清单·步骤

                                                                                                            1. 配 IP 前先确认网段，向网络管理员申请一段正确地址。
                                                                                                            2. 同网段直接 ARP；跨网段先找网关，没有网关就不要指望能通。
                                                                                                            3. 用 DHCP 时按 Discover→Offer→Request→ACK 四步核对抓包。
                                                                                                            4. 租期过半就续租，不要等到到期。
                                                                                                            5. 要 PXE，就在 DHCP 里配 next-server 与 filename，并准备 TFTP 服务。

                                                                                                            05 从物理层到MAC层：如何在宿舍里自己组网玩联机游戏

                                                                                                            核心结论 两台电脑直连先过物理层：交叉线把一端发送对到另一端接收。三台以上用 Hub 只是把每个字节复制到所有口，于是引出包发给谁、谁先发、出错怎么办三个问题，后两个由 MAC 层多路访问解决；交换机再学会谁在哪个口，用转发表替代广播。

                                                                                                            机制细节

                                                                                                            • 物理层直连：电脑连电脑用一根两头水晶头的网线，普通网线不通，要做交叉线，即 1－3、2－6 交叉接法；水晶头第 1、2 和第 3、6 脚分别起收、发信号作用，把一端 1 号与 3 号、2 号与 6 号互换，就能一端发、另一端收。
                                                                                                            • 直连还要配 IP、子网掩码、默认网关，三项必须同网段（例 192.168.0.1/24 与 192.168.0.2/24），否则不通；此时构成最小局域网 LAN，包仍完整包含 MAC 层。
                                                                                                            • Hub 有多个口，完全在物理层工作，"没有大脑"，把收到的每一个字节复制到其他端口，是广播模式。
                                                                                                            • MAC 层三问：包发给谁；谁先发谁后发；出错怎么办。MAC 全称 Medium Access Control，即媒体访问控制，管的是往媒体上发数据时谁先发、谁后发，学名叫多路访问。
                                                                                                            • 三种方案：信道划分（分多个车道）、轮流协议（单号、双号出行）、随机接入协议（先出门、堵了就回），以太网用随机接入。
                                                                                                            • 以太网二层格式：最前是目标 MAC 与源 MAC，然后是类型（多为 IP 数据包），最后是 CRC（循环冗余检测），用 XOR 异或校验；原文未给字节数。
                                                                                                            • 收包：网卡比对目标 MAC，收进来再比对 IP，再比对端口（例 80，nginx 监听 80）；回包时源 MAC 变目标 MAC。
                                                                                                            • ARP：已知 IP 求 MAC，靠"吼"发广播，对应主机回答；本地存 ARP 缓存，因机器上下线、IP 会变，缓存过一段时间过期。
                                                                                                            • 交换机：摘下 MAC 头检查目标再按策略转发，是二层设备；不知目标口就泛洪到除来源口外的所有口，同时记住源 MAC 的口，之后直达；学习结果叫转发表，有过期时间。

                                                                                                            判据·清单·步骤

                                                                                                            1. 两台机直连：做交叉线，再配同网段 IP、掩码、网关。
                                                                                                            2. 只有 Hub 时：接受广播，靠 MAC 层规则定先后。
                                                                                                            3. 判断该不该收包：依次比对目标 MAC、IP、端口。
                                                                                                            4. 已知 IP 不知 MAC：发 ARP 广播，回答写入缓存。
                                                                                                            5. 换交换机后：泛洪起步，源 MAC 学习收敛，过期时间适应变化。

                                                                                                            06 交换机与VLAN：办公室太复杂，我要回学校

                                                                                                            • 核心结论：多台交换机互连后，二层网络会同时遭遇两个问题：拓扑成环让广播包无限循环，以及一个广播域过大导致广播风暴与嗅探泄密。前者的解法是用 STP 把“图”剪成“树”，后者的解法是用 VLAN 在物理交换机上切出逻辑局域网。交换机的转发能力全部来自它对源 MAC 与入端口的学习。

                                                                                                            • 机制细节：交换机收到广播帧时，策略是“除了广播包来的方向外，它还要转发给其他所有的网口”，并同时学习某 MAC 在某个网口。当两台交换机把两个局域网同时连起来形成环路，广播在两边来回转发，学习表被反复覆盖：交换机 B 先在右口收到 A 转来的、源自局域网一的广播，就误判机器 1 搬到了右边，清掉原记录；下一个包又从左边来，再刷一次。STP：每台交换机初始都自认掌门，每个网桥分配一个含管理员优先级字段的 Bridge ID；BPDU（网桥协议数据单元）只有根桥能发，已隶属某根桥的交换机只能转发掌门指示；比较用的 Priority Vector 是 [Root Bridge ID, Root Path Cost, Bridge ID, Port ID]，值越小越优，依次比根 ID、到根的路径开销、自身 ID。合并只有四种情形：掌门遇掌门（输者率小弟归顺）、同门相遇（发现环，把绕路的小弟提为直连，或让近的小弟当上司）、掌门遇别派小弟（小弟拿本帮掌门比，赢则对方掌门拜入）、不同门小弟相遇（各拿掌门比，输者改拜）。VLAN：在二层头前加 TAG，内含 12 位 VLAN ID；交换机取下二层头时能识别 VLAN ID，只有同 VLAN 的包才互相转发；端口可逐口设置所属 VLAN 并可随时改；交换机互连口设为 Trunk 口，可转发属于任何 VLAN 的帧。原文对不打 TAG 的普通接入口未使用 Access 这一名称，该术语原文未明确。

                                                                                                            • 判据·清单·步骤：① 数清交换机与网口规模，判断是否需多台互连；② 互连后先查是否有冗余链路，有则启用 STP；③ STP 收敛判据是全网只剩一个根桥、且互联关系收敛成一棵树；④ 需要隔离广播与安全域时，先按部门划 VLAN（程序员 10、人事 20、财务 30），再逐口配置，最后把交换机之间设为 Trunk；⑤ 人员流动时把该口从原 VLAN 移除、再设为新 VLAN。

                                                                                                            • 核心结论：ICMP 是 IP 层的控制面信使，被封装在 IP 包里，只负责报告与探测，不搬运业务数据。它分两类：主帅主动派出的查询报文（ping 用 8/0）与异常时回报的差错报文（3/4/11/5）。ping 判的是可达性与往返时延，Traceroute 则是故意制造错误、借差错报文反推路径与 MTU。

                                                                                                            09 路由协议：西出网关无故人，敢问路在何方

                                                                                                            • 核心结论：路由表是本地转发信息库，默认按目的 IP 查表；要按源 IP、入口设备、TOS 分流，就得建多张路由表加规则，即策略路由。网络简单可控时配静态路由即可，拓扑多变必须用动态路由，主流两族是距离矢量（Bellman-Ford）与链路状态（Dijkstra），分别长成 BGP 与 OSPF。

                                                                                                            • 机制细节：路由表每条规则至少三项——目的网络、出口设备、下一跳网关。策略路由按源 IP、入口设备、TOS 选表再查表，一条规则也可多路径并用 nexthop 加 weight 分流。距离矢量：每台路由器保存一张表，每行含到目标从哪条线出去、到目标的距离；每过几秒把自己所知的到所有路由器的距离告知邻居，更新规则是自己到目标的距离等于自己到邻居的 x 加上邻居到目标的 M。它有两个问题：好消息传得快、坏消息传得慢（失效后距离逐轮加一，直到超过阈值才判定真挂），以及每次要发送整个全局路由表。链路状态：先向邻居 say hello 发现邻居，再发 echo 要求立即返回、往返时间除以二即距离，然后把链路状态包广播到全网每个路由器，各路由器在本地建完整图并跑 Dijkstra；更新只广播变化了的拓扑，省带宽与 CPU，且邻居会广播某路由器挂掉，坏消息迅速收敛。OSPF 基于链路状态，属内部网关协议 IGP，用于数据中心内部路由决策，可发现多条等价最短路径做负载均衡即等价路由。BGP 用于 AS 之间，采用路径矢量（path-vector），是距离矢量的升级版：除下一跳外还带 AS 路径，从而避免坏消息传得慢；AS 间由边界路由器用 eBGP 广播路由，边界路由器再用 iBGP 导入内部，使内部路由器找到最佳边界路由器；把 AS 视为整体，自治系统数目非常有限。AS 分三类：Stub 对外只有一个连接、不替其他 AS 传包；Multihomed 有多个连接但大多拒绝替其他 AS 传包；Transit 多连接且愿意帮其他 AS 传包。原文未说明 BGP 运行于 TCP 之上，也未给报文格式，仅将其列为思考题，此两点原文未明确。

                                                                                                            10 UDP 协议：因性善而简单，难免碰到「城会玩」

                                                                                                            核心结论 UDP 只做一件事：靠端口把包交给应用，其余全继承 IP——不保证不丢、不保证按序、以数据报为单位，也不做拥塞控制。它是无状态服务，简单、快、谁都信，代价是可靠性与时延控制被推给应用层。判断用不用它，看应用能否自己兜底、场景是否值得。

                                                                                                            机制细节

                                                                                                            • 收包：MAC 匹配→交 IP 层→剥 IP 头、目标 IP 匹配→按 IP 头 8 位协议字段判断 TCP 还是 UDP→解析 UDP 头→按端口交应用；传输层做完，内核基本干完。
                                                                                                            • 头只有源端口、目标端口，「再没有其他的了」；头长度与字段位宽原文未明确。
                                                                                                            • 「面向连接」的实质是为双方交互维护数据结构与状态；UDP 没有，故为无状态服务。
                                                                                                            • 继承 IP 三点：不保证不丢、不保证按序；面向数据报，一包一发一收（TCP 是字节流）；无拥塞控制。
                                                                                                            • 三特点：沟通简单（不要大量数据结构、处理逻辑、包头字段，前提是相信通路容易送达）；轻信他人（不建连接，谁都能发、可同时发多人）；愣头青（不按网络状况做拥塞控制）。
                                                                                                            • 三场景：①资源少/内网/丢包不敏感——DHCP 是内网请求，一次拿不到还有下次；PXE 装机用 TFTP，客户端还没有 OS，不宜维护复杂状态机。②广播/多播——DHCP 本身即广播；多播用 D 类地址，监听组播要发 IGMP 让路由器转发以跨路由；VXLAN 需组播，也基于 UDP。③快、低时延、可容忍少数丢包——TCP 重传保序抬时延，弱网还主动降速等于「自断臂膀」。

                                                                                                            11 TCP 协议（上）：因性恶而复杂，先恶后善反轻松

                                                                                                            核心结论 TCP 的复杂来自「性恶论」：默认丢包、乱序、重传、拥塞是常态，于是在协议内部用序号、确认、窗口、状态机做可靠性，回答顺序、丢包、连接维护、流量控制、拥塞控制五问。连接维护的成果是三次握手、四次挥手两个时序与一张状态机，副产品是起始序号协商。

                                                                                                            机制细节

                                                                                                            • 头字段：源/目标端口（否则不知给哪个应用）；序号（解决乱序）；确认序号（没收到就重发，解决不丢包）；状态位（SYN 发起连接、ACK 回复、RST 重新连接、FIN 结束连接）；窗口大小（各声明当前处理能力，做流量控制）。字段位宽原文未明确。
                                                                                                            • 三次握手＝请求→应答→应答之应答。两次不行：A 的第一个请求可能丢、绕路超时、B 不响应，A 只能重发；迟到的重复请求若被 B 当新请求，会建立「纯属单相思」、无终结的连接。四次不必：B 的应答也可能丢、绕路、A 已挂，再加没有底——「只要双方的消息都有去有回，就基本可以了」。
                                                                                                            • 握手后立刻发数据可解残留：数据到达时 B 可认为连接已建立；B 若挂了 A 会收到不可达报错。连接空着应开 keepalive，服务端可主动关闭长期不发包的客户端。
                                                                                                            • 握手要沟通的第二件事是序号：每连接起始序号必须不同。若都从 1 开始：A 发 1、2、3，3 绕路，A 掉线重连又从 1 发 2，旧 3 回来会被 B 当下一包。起始序号随时间变化，可看成 32 位计数器、每 4ms 加一，重复一轮要 4 个多小时，绕路包早因 TTL 到期而死。
                                                                                                            • 建连状态：双方初始 CLOSED；服务端监听端口进 LISTEN；客户端发 SYN 进 SYN-SENT；服务端回 SYN 并 ACK 客户端 SYN，进 SYN-RCVD；客户端收后发 ACK 进 ESTABLISHED（一发一收成功）；服务端收到该 ACK 进 ESTABLISHED。
                                                                                                            • 四次挥手：A 说「不玩了」只表示 A 不再发数据，B 可能还有事、仍可发，故不能收到 ACK 就关，此即半关闭。A 发 FIN 进 FIN_WAIT_1；B 收后发 ACK 进 CLOSE_WAIT；A 收到该 ACK 进 FIN_WAIT_2；B 发 FIN 到 A，A 回 ACK 后离开 FIN_WAIT_2，但须进 TIME_WAIT 等待。B 侧最终状态名，原文未明确。
                                                                                                            • TIME_WAIT 等 2MSL 两个理由：①最后那个 ACK 若丢，B 会重发 FIN，A 还在等就能再回一次，并留足时间让 ACK 到达；②A 立刻跑路则端口空出被新应用占用，上个连接还在路上的包会串进新连接，虽序号重新生成，仍要双保险，等旧包全死再放端口。
                                                                                                            • 超过 2MSL 仍未收到 ACK 的 FIN 再来，A 直接回 RST，B 就知道 A 早跑了。
                                                                                                            • 两个时序图合成状态机：阿拉伯数字是建连顺序、大写中文数字是断开顺序，须对照看。

                                                                                                            判据·清单·步骤

                                                                                                            1. 需要可靠、有序、不重复的字节流 → 用 TCP。
                                                                                                            2. 握手够不够：双方消息是否都「有去有回」。
                                                                                                            3. 序号自查：同一四元组重连后是否会复用序号 → 起始序号须随时间变化。
                                                                                                            4. 挥手异常：A 发 FIN 后不能跑路（B 收不到 ACK 无从判断）；B 也不能跑路（A 不知 B 还有事还是稍后发 FIN）。
                                                                                                            5. FIN_WAIT_2 卡死：Linux 用 tcp_fin_timeout 设超时；TCP 协议本身不处理该状态。

                                                                                                            • 32 位：起始序号计数器宽度；4ms：每加一的间隔；4 个多小时：序号重复一轮。
                                                                                                            • MSL 协议规定 2 分钟：报文最大生存时间；实际常用 30 秒 / 1 分钟 / 2 分钟。

                                                                                                            12 TCP 协议（下）：西行必定多妖孽，恒心智慧消磨难

                                                                                                            核心结论 公网不可靠，TCP 靠「恒心」（重传）与「智慧」（算法）把不可靠通路包装成可靠字节流。顺序、丢包、流量控制统一由滑动窗口解决；拥塞控制另开 cwnd，管的是别把网络塞满，两者取小值决定发送速度。原文还批评「丢包即拥塞」的假设，并由此引出 BBR。

                                                                                                            机制细节

                                                                                                            • 累计确认：不必一包一 Ack，只应答某个之前的 ID，表示之前都收到了。
                                                                                                            • 发送端缓存按 ID 分四部分：已发已确认、已发未确认、未发待发、未发暂不发；分界为 LastByteAcked、LastByteSent、LastByteAcked + AdvertisedWindow。
                                                                                                            • 接收端分三部分：已收并确认、马上能收、无法收；NextByteExpected 是一、二之间，NextByteExpected + AdvertisedWindow 是二、三之间，也等于 LastByteRead + MaxRcvBuffer。
                                                                                                            • 窗口公式：AdvertisedWindow = MaxRcvBuffer − ((NextByteExpected−1) − LastByteRead)。乱序空档只有与第一部分连续的能马上回复，中间空着的要等。
                                                                                                            • 超时重传：每个已发未确认的包设定时器。超时须大于 RTT（否则不必要重传），也不能过长（访问变慢）。做法是采样 RTT 加权平均与波动范围算出超时时间，即自适应重传算法；每次超时重传，下次间隔翻倍。
                                                                                                            • 快重传：接收方收到序号大于期望的报文段即发现间格，发三个冗余 ACK；发送方收到 3 个便不等定时器立即重传。SACK 在 TCP 头加字段，把缓存「地图」发给发送方（ACK6、SACK8、SACK9），一眼看出丢的是 7。
                                                                                                            • 滑动窗口：确认到达窗口右移一格、可多发一个；发送过猛则可发部分为 0；接收慢可通过确认改窗口，最小到 0，发送方暂停并发窗口探测包。窗口缩小时是左边界右移、窗口变小（9→8→…→0），不是平行右移。
                                                                                                            • 低能窗口综合征：别空出一字节就通知、马上又填满；窗口太小时不更新，直到够大或缓冲一半为空才更新。
                                                                                                            • 拥塞控制：rwnd 怕塞满接收方缓存，cwnd 怕塞满网络，约束为 LastByteSent − LastByteAcked ≤ min{cwnd, rwnd}。网络是黑盒，只能靠丢包/超时反推。
                                                                                                            • 管道模型：通道容量 = 带宽 × 往返延迟；让「已发送未确认」等于通道容量即撑满管道。
                                                                                                            • 慢启动：cwnd 初始 1 个报文段，每收 1 个确认加 1，于是 2、4、8 指数增长。拥塞避免：超过 ssthresh = 65535 字节后，每确认 cwnd 加 1/cwnd，8 个确认共加 1，线性增长。
                                                                                                            • 拥塞发生：超时重传时 ssthresh = cwnd/2、cwnd = 1，重新慢启动。快恢复：三冗余 ACK 触发快重传，TCP 认为不严重，cwnd 减半、ssthresh = cwnd，三包返回后 cwnd = ssthresh + 3，仍在高位线性增长。
                                                                                                            • BBR：针对「丢包不等于通道满（管子漏水）」与「要等缓存填满才丢包、已经晚了」，不断加快把管道填满，但不填满中间设备缓存，在高带宽与低时延间找平衡。

                                                                                                            判据·清单·步骤

                                                                                                            1. 判断瓶颈：接收方处理不过来 → rwnd；网络堵 → cwnd；上限取较小值。
                                                                                                            2. 丢包类型：后续包已到、只缺中间一个 → 快重传/快恢复；整段无响应 → 超时重传、cwnd 归 1。
                                                                                                            3. 零窗口：定时发探测包；窗口太小不更新，够大或缓冲一半为空才更新。
                                                                                                            4. 后退策略：超时→回解放前；三冗余 ACK→减半不归零。

                                                                                                            数字·阈值

                                                                                                            • 65535 字节：ssthresh 初始阈值，超过即由慢启动转拥塞避免。
                                                                                                            • 3 个冗余 ACK：触发快重传的门槛。
                                                                                                            • cwnd 起始 1 个报文段；每确认 +1 / +1/cwnd：两种增长斜率。
                                                                                                            • cwnd = ssthresh + 3：快恢复三包返回后的窗口。
                                                                                                            • 窗口 9 → 8 → 0：接收方不读取而收缩。

                                                                                                            • MSS 1460、窗口 16 位、2MSL 60 秒：原文未明确。

                                                                                                            13 套接字 Socket：Talk is cheap, show me the code

                                                                                                            核心结论 Socket 是「一根网线两头插」的编程抽象，能设的参数只到网络层与传输层。TCP 服务端是 bind → listen → accept，客户端 connect，之后 read/write 像读写文件；UDP 只需 bind 与 sendto/recvfrom。Linux 里 Socket 就是文件，靠文件描述符访问。高并发演进主线是多进程、多线程、select、epoll。

                                                                                                            机制细节

                                                                                                            • 参数：网络层选 AF_INET（IPv4）或 AF_INET6；传输层选 SOCK_STREAM（TCP）或 SOCK_DGRAM（UDP）。
                                                                                                            • TCP 服务端：bind 赋 IP 与端口——端口让内核从 TCP 头找到应用，IP 让多网卡机器选择监听全部或某一张网卡；listen 使服务端进 LISTEN；accept 从已完成队列取连接处理，没有就等着。
                                                                                                            • 内核为每个 Socket 维护两个队列：已完成握手、处于 established 的；未完成握手、处于 syn_rcvd 的。
                                                                                                            • 客户端：connect 指明对端 IP 与端口并发起三次握手，内核分配临时端口；握手成功后服务端 accept 返回另一个 Socket。故「监听的 Socket」与「真正传数据的已连接 Socket」是两个。
                                                                                                            • 连接建立后用 read/write 读写，像往文件流里写。内核链：进程的 task_struct 指向文件描述符数组，下标即文件描述符；数组内容是指向内核打开文件列表的指针；文件有 inode，Socket 的 inode 不在硬盘而在内存；inode 指向 Socket 结构，核心是发送队列与接收队列，队列里存 sk_buff，能看到完整包结构。
                                                                                                            • UDP：无连接，不需三次握手，故不需 listen 与 connect，但仍需 IP 与端口，仍需 bind；不维护连接状态，一个 Socket 可与多个客户端通信；每次通信都用 sendto/recvfrom 并传入 IP 与端口。
                                                                                                            • 最大连接数：系统用四元组 {本机 IP, 本机端口, 对端 IP, 对端端口} 标识 TCP 连接；服务端本地端口固定，可变的只有客户端 IP 与端口，故最大连接数 = 客户端 IP 数 × 客户端端口数。真实上限远低于理论值：一是 fd 限制（ulimit），二是每连接占内存。
                                                                                                            • 多进程：fork 完全拷贝子进程（文件描述符列表、内存空间、执行位置），返回 0 为子进程、其他整数为父进程且即子进程 ID；因文件描述符指向内核统一打开文件列表，accept 得到的已连接 Socket 也被子进程继承。
                                                                                                            • 多线程：pthread_create 内部也调 do_fork，task 列表新增一项，但 fd 列表、进程空间共享，只多一个引用。
                                                                                                            • select：把要盯的 Socket 放进 fd_set，调用 select 监听集合变化；有变化就依次查看每个描述符，变化位置 1 表示可读/可写。缺点是要轮询全部、数量受 FD_SETSIZE 限制。
                                                                                                            • epoll：改为事件通知，内核注册 callback 而非轮询。epoll_create 创建 epoll 对象（也是文件、也有 fd），其中红黑树保存要监听的 Socket；epoll_ctl 添加即入红黑树，节点指向的结构挂到被监听 Socket 的事件列表；来事件时从该列表找到 epoll 对象并回调通知。监听数增加时效率不会大幅下降，上限为进程最大 fd 数。

                                                                                                            判据·清单·步骤

                                                                                                            1. 选类型：IPv4/IPv6 → AF_INET/AF_INET6；TCP/UDP → SOCK_STREAM/SOCK_DGRAM。
                                                                                                            2. TCP 服务端：socket → bind → listen → accept → read/write。
                                                                                                            3. TCP 客户端：socket → connect → read/write。
                                                                                                            4. UDP：服务端 socket → bind → recvfrom/sendto；客户端 socket → sendto/recvfrom（无 listen/connect）。
                                                                                                            5. 扩容：先 ulimit，再降每连接资源；上万连接时进程/线程模型不可行，转 IO 多路复用，再转 epoll。
                                                                                                            6. 是否同一连接：看四元组，任一元素不同即不同连接。

                                                                                                            数字·阈值

                                                                                                            • 2 的 32 次方：IPv4 客户端 IP 数上限；2 的 16 次方：客户端端口数上限。
                                                                                                            • 2 的 48 次方：服务端单机最大 TCP 连接数理论值。
                                                                                                            • 1 万：C10K 所指单机连接数；1 亿用户 / 10 万台服务器：其成本推算。
                                                                                                            • 返回值 0：fork 后子进程的判据。
                                                                                                            • FD_SETSIZE：select 可同时盯的上限（具体数值原文未明确）。

                                                                                                            案例·类比

                                                                                                            14 HTTP 协议：看个新闻原来这么麻烦

                                                                                                            核心结论 HTTP 几乎是人上网用的第一个协议，也最容易被忽略。它基于 TCP：先三次握手，再发请求行、首部、正文，返回带状态码。1.1 纯文本、每次带完整头、一来一回，实时性与并发性都差；2.0 用头压缩、分帧、二进制、多路复用解决队首阻塞，但仍在 TCP 上，一包丢失会阻塞同连接所有流；QUIC 换到 UDP 上自定义连接、重传、多路复用与流量控制。

                                                                                                            机制细节 准备：URL→DNS 解析成 IP→TCP 三次握手；1.1 默认 Keep-Alive，连接可复用。 请求＝请求行（URL、HTTP 1.1、方法）＋首部（key value，冒号分隔）＋正文。GET 取资源（HTML 或 JSON 由服务端定）；POST 主动告知服务端信息，放正文，常见 JSON；PUT 向指定位置上传最新内容；DELETE 删除。服务器往往不允许上传文件，故 PUT/POST 都成了"传东西"，POST 多创建、PUT 多修改。Accept-Charset 声明可接受字符集防乱码；Content-Type 声明正文格式。 缓存：max-age 小于缓存层中该资源的缓存时间即可接受缓存，max-age=0 时缓存层通常转发应用集群；If-Modified-Since 未更新则回 304，客户端不下载、省带宽；静态资源先进 Vanish 缓存层，过期才到 Tomcat 集群。 发送：以 stream 交 TCP 切成段，每段须回 ACK，否则重传（同包可能传多次，HTTP 层不必知道）；IP 层同网段 ARP 求目标 MAC，否则求网关 MAC，逐跳路由至目标网段；目标机核 MAC/IP、按序列号回 ACK、按端口交 HTTP 进程；返回含状态码、短语、首部、正文，Retry-After 告知多久后重试。 2.0：头压缩（两端索引表，相同头只发索引）；一连接切多流（有 ID、双向、有优先级，仅虚拟通道）；消息与帧二进制化（Header 帧传头并开新流，Data 帧传正文、多帧同属一流）；帧乱序发、按流标识重组、按优先级调度。Cookie/Session 流程原文未明确。 QUIC：①用 64 位随机数 ID 标识连接，不靠四元组，IP/端口变而 ID 不变不重连；②序号递增、每号只发一次，重发加一，故 RTT 采样比 TCP 准（TCP 重发同号会算短或算长），另用 offset 判重发与拼接；③同连接多 stream 互不依赖，stream2 丢包重传时 stream3 无需等待；④ACK 基于 offset，进缓存即应答、不再重发，窗口起点为已收最大 offset，另加整连接窗口；TCP 累计 ACK 使窗口不右移，后续包也可能超时重传。

                                                                                                            判据·清单·步骤

                                                                                                            1. DNS→三次握手（Keep-Alive 复用）；2. 拼请求行+首部+正文；3. 取数据 GET、提交创建 POST、修改 PUT、删除 DELETE；4. 判缓存：max-age 未过期可接受，回 304 则不下载；5. 看状态码：200 正常、404 无法响应、503 按 Retry-After 重试；6. 并发不足上 2.0，仍阻塞看 QUIC。

                                                                                                            数字·阈值

                                                                                                            • HTTP 1.1：当前大部分使用的版本，默认 Keep-Alive
                                                                                                            • 200：成功；404：服务端无法响应；304：资源未更新
                                                                                                            • 503：服务暂不可用，配合 Retry-After
                                                                                                            • max-age=0：缓存层通常转发应用集群
                                                                                                            • 64 位：QUIC 连接 ID 长度
                                                                                                            • 4：TCP 四元组元素数

                                                                                                            反例·坑

                                                                                                            • 用多条 TCP 连接跑 pipeline 实现并行，连接数拖累服务器。

                                                                                                            15 HTTPS 协议：点外卖的过程原来这么复杂

                                                                                                            核心结论 HTTP 明文在支付场景有风险：包被截获后黑客可抢先冒充外卖网站骗走卡号密码。对称加密效率高但密钥传不出去；非对称能解决分发却效率低，且只用服务端一对公私钥仍留"回复人人可解""黑客可伪造请求"两洞，须靠证书与 CA 层层背书验公钥。HTTPS 的思路：非对称只传对称密钥，大数据量通信用对称加密。

                                                                                                            机制细节 对称：加解密同一密钥，须保密；非对称：公私钥不同，公钥加密只有私钥能解，私钥加密只有公钥能解。原文明确对称效率高得多，故交互多用对称。 对称死循环：约密钥也要上网传、会被截获，如密码本只能线下传、口号本身又是密钥。 非对称两洞：你用公钥加密黑客解不开；但网站回复"那给我银行卡和支付密码吧"是私钥加密，人人可用公钥打开；它也不能改用公钥加密，因私钥只它有。黑客也有公钥，可伪造"我要定外卖"。解法：客户端自备一对公私钥并把公钥给网站，双方各用对方公钥加密。 证书：公钥可放公网或握手时传，但网民无法鉴别真假——人人能自建公私钥冒充。证书含公钥、所有者、发布机构、有效期。流程：openssl 生私钥→导出公钥→生成请求→交 CA（Certificate Authority）用自己私钥盖章。签名算法：对信息做不可逆 Hash，把 Hash 值加密作签名随信息同发。验证：用信任 CA 证书里的公钥解签名，成功且 Hash 对得上即可信；CA 公钥又需上级 CA 签，上溯到 root CA 背书。 握手：Client Hello（明文传 TLS 版本、加密套件与压缩算法候选＋随机数）→Server Hello（选定项＋随机数）→服务器证书＋Server Hello Done→客户端取信任 CA 公钥验证书→生成 Pre-master，用证书公钥加密经 Client Key Exchange 发出，服务器私钥解出→双方各有三个随机数（自己的、对端、Pre-Master），生成相同对称密钥→Change Cipher Spec＋Encrypted Handshake Message，服务器同样回→对称传输。除加解密外同 HTTP；此为单向认证。 重放：加密只让黑客打不开，但它能发 N 次；用 Timestamp 与 Nonce 做不可逆签名保证唯一，只接受一次；篡改则签名对不上。

                                                                                                            判据·清单·步骤

                                                                                                            1. 看新闻 HTTP 尚可，涉支付必须加密；2. 数据走对称，密钥分发走非对称；3. 公钥来自网络就必须验证书；4. 验证书：信任 CA 公钥解签名→Hash 对得上→可信，上溯不到 root CA 则不可信；5. 握手七步：Client Hello→Server Hello→证书→Server Hello Done→验证→送 Pre-master→Change Cipher Spec＋Encrypted Handshake Message→对称传输；6. 防重放：Timestamp＋Nonce 只认一次。

                                                                                                            数字·阈值

                                                                                                            • 2 种加密：对称、非对称
                                                                                                            • 3 个随机数：客户端、服务端、Pre-master 生成同一对称密钥
                                                                                                            • 1024：原文 openssl 命令中的私钥位数
                                                                                                            • N 次：黑客可重发次数，靠 Timestamp＋Nonce 限为一次

                                                                                                            案例·类比 点外卖：请求被截获，黑客抢先假扮外卖网站回"好啊好啊，来来来，银行卡号、密码拿来"，映射中间人劫持与冒充。户口本：简历谁都能印，只有公安局盖章的才算数，发布机构像区公安局、有效期像身份证年限。Self-Signed 是"我就是我，你爱信不信"。

                                                                                                            反例·坑

                                                                                                            • 把对称密钥放到互联网上传输，或指望线下接头约定。
                                                                                                            • 只用服务端一对公私钥：回复用私钥加密则人人可解，黑客还能用公钥伪造请求。
                                                                                                            • 公钥放公网下载或握手时直传却不验真假。

                                                                                                            16 流媒体协议：如何在直播里看到美女帅哥？

                                                                                                            核心结论 直播与点播本质都是视频数据传输，难点是原始数据量大到存不下传不动，故须先编码压缩，再组织成 NALU 序列，用 RTMP 打包推流，经转码与分发网络，最后观众拉流解码。编码吃空间、时间、视觉、编码四种冗余；传输靠 RTMP over TCP 加 Chunk 分块；分发靠中心层＋边缘层两级。

                                                                                                            机制细节 视频＝快速播放一连串图片，每张是一帧；每秒 30 帧人眼就分不出独立图片，即帧率 FPS。像素 1024×768、每像素 RGB 各 8 位共 24 位，每秒 566,231,040 Bits＝70,778,880 Bytes，一分钟 4,246,732,800 Bytes 已 4 个 G，故须编码：用尽量少的 Bit 保存而播放仍精美。 四种冗余：空间（相邻像素渐变，可隔几个存）、时间（相邻图像相似，可按已有图预测）、视觉（人眼对细节不敏感，可丢）、编码（概率高者字节少，类似霍夫曼编码）。 流派：ITU-T 的 VCEG 偏传输、ISO 的 MPEG 偏存储，合制 H.264/MPEG-4 AVC 为本讲重点；名词系列一是封装格式（AVI、MP4、FLV、MKV 等），规定各字节段含义，数据里存编码结果。 链路：主播推流→服务端接流→转码（适配不同客户端）→观众拉流→读 SPS/PPS→NALU 组帧解码播放。 帧与 NALU：I 帧完整图片，本帧即可解码；P 帧前向预测，记与之前关键帧或 P 帧的差别；B 帧双向内插，记与前后帧差别。原文：I 帧最完整，B 帧压缩率最高，压缩后按 IBBP 间隔出现，即时序编码。一帧分片、片分宏块。压成 NALU：起始标识符分隔、头配类型、Payload 是数据；0x07 是 SPS（序列参数集），0x08 是 PPS（图像参数集）；传输前必须先传这两类参数，否则无法解码，且每个 I 帧前都传一遍。 推流：RTMP 基于 TCP，先建 TCP，再调 Connect 建 RTMP 连接，商量版本号与时间戳。握手六条：C0 客户端版本号、C1 客户端时间戳、S0 服务器版本号（收到 C0 才回）、S1 服务器时间戳、C2 客户端 ACK、S2 服务器 ACK；之后传 Chunk 大小、窗口大小，再建 Stream 推流 publish。发送时去掉 NALU 起始标识符，SPS/PPS 先单独封包发，再发片 NALU；Message 拆 Chunk，一块发完才发下一块，各带 Message ID 供组装，原文说可减少低带宽拥塞。例：Message 307、Chunk 128 拆三块，首块 Type=0（Timestamp 1000、Length 307、类型 9 表视频、Stream ID 12346、Data 128 字节），次块 Type=3，末块 51 字节仍 Type=3。 分发：中心层流媒体集群转发，边缘层部署各地及横跨各大运营商、离用户近；就近选边缘节点；中心层也转码，如 RTMP 码流转 HLS。原文未明确 HLS 分片与索引，未提 DASH；直播延迟秒数原文未明确。

                                                                                                            判据·清单·步骤

                                                                                                            1. 算原始量判断是否必须编码；2. 用四种冗余编码，选 H.264/MPEG-4 AVC；3. 视频→帧（I/P/B）→片→NALU，每 I 帧前重复插 SPS（0x07）与 PPS（0x08）；4. TCP→RTMP Connect 协商版本号与时间戳→传 Chunk 大小→建 Stream→publish；5. 去起始标识符，SPS/PPS 单独成包先发，Message 按 Chunk 切块带 ID；6. 接流、转码、交分发网络。

                                                                                                            • 30 帧/秒：人眼分辨不出独立图片的帧率示例（FPS）
                                                                                                            • 1024×768：原文举例分辨率；24 位：每像素 RGB 各 8 位
                                                                                                            • 566,231,040 Bits／70,778,880 Bytes：每秒原始量
                                                                                                            • 4,246,732,800 Bytes：每分钟原始量，约 4 G
                                                                                                            • 0x07／0x08：NALU 类型 SPS／PPS

                                                                                                            17 P2P 协议：我下小电影，99% 急死你

                                                                                                            核心结论 HTTP 与 FTP 都是集中下载，难解单服务器带宽压力。P2P 把资源分散在多台 peer 上，就近点对点下载，下载者同时成为上传者，人越多越快。找 peer 两条路：依赖 tracker（元数据集中、文件数据分散）与 DHT（全分散）。DHT 用哈希定"谁该知道文件在哪"，用 XOR 距离与 k-bucket 折半查找，N 个节点最多 log2(N) 次找到。

                                                                                                            机制细节 FTP 用两条 TCP：控制连接连 21 传命令（list、reter、store），数据连接每传一个文件新建；主动模式 PORT 客户端开 N（>1024）连 21、N+1 监听并告知服务器，服务器从 20 端口连 N+1；被动模式 PASV 由服务器开端口 P（>1024）回 227，客户端用 N+1 连 P。 P2P：资源分散在多台 peer 上，拿到有该文件的 peer 列表建点对点连接就近下载，下完自己也成 peer，故 BT 既有下载也有上传。 .torrent 含 announce（tracker URL）与文件信息；文件信息含 info 区（几个文件、多长、目录结构与名字）、Name（顶层目录名）、每段大小（分段下载）、段哈希值（各段 SHA-1 拼一起）。流程：解析 .torrent→连 tracker→tracker 给其他下载者（含发布者）IP→互连，按 .torrent 互报已有块、换缺块。每块算 Hash 对比，不一致重下。tracker 故障或被屏蔽则 BT 无法工作。 DHT：人人分存一部分资源信息与成员联系信息，构成分布式数据库；著名协议 Kademlia。BT 两角色：peer 监听 TCP 端口上传下载，DHT node 监听 UDP 端口入网。每个 node 有长 ID，只掌握部分文件索引；哈希与 ID 同长度；哈希相同的 node 负责知道从哪下载，考虑其下线，ID 接近的 N 个 node 也应知道。加入：种子放 node 地址 list，任连一个入网，算哈希找匹配或接近的 node，逐跳问路（如六度分隔），拿持有者列表。 Kademlia：ID 与哈希同为 160bits（20 字节）；距离用异或：01010 与 01000 得 2、与 00010 得 8、与 00011 得 9；位置近不算近、ID 近才算近。k-bucket：只有最后 1 位不同的 1 个（距离 1）；从倒数第 i 位起不同的 2^(i-1) 个，距离 [2^(i-1), 2^i)，归 k-bucket i，直到倒数 160 位；差距越大陌生人越多，每层只放 K 个。查找折半收缩：A 找 B，异或落在 [2^4,2^5) 查 k-bucket 5，没有就找桶内 C，C 与 B 距离小于 2^4，缩短一半以上；最多 log2(N) 次。 四指令：PING 测在线、STORE 存一份、FIND_NODE 按 160 位 ID 找节点、FIND_VALUE 按 KEY（文件 160 位 ID）找数据。更新：按最后接触时间倒序，已在桶内挪最底；不在且满则 PING 最旧节点，通则留旧弃新、不通则删旧加新。 99%：原文未明确成因，可对应的只有块 Hash 不一致要重下、tracker 故障则无法工作。

                                                                                                            判据·清单·步骤

                                                                                                            1. 小文件用 HTTP/FTP，大文件多用户用 P2P 以免单服务器瓶颈；2. 走 tracker：解析 .torrent→取 announce URL→连 tracker 拿 peer IP→互报已有块→换缺块；3. 每块先算 Hash 对比，不一致重下；4. 走 DHT：种子放 node 列表→入网→算哈希→找 ID 相同或最近的 node→逐跳问路→拿持有者列表→建连接；5. 下完登记；6. 新节点入 bucket 前 PING 最旧节点，通则留旧、不通换新。

                                                                                                            18 DNS协议：网络世界的地址簿

                                                                                                            核心结论：DNS 是网络世界的地址簿，把域名换成 IP。域名服务器按树状分层，逐级指路，再靠缓存提速。它还能做负载均衡：既在一组 IP 间轮询，也按地域和运营商把用户送到最近机房。

                                                                                                            机制细节：

                                                                                                            • 三级分工：根 DNS 返回顶级域 DNS 的 IP；顶级域（.com/.net/.org）返回权威 DNS 的 IP；权威 DNS 返回主机 IP，是解析结果的原出处。
                                                                                                            • 解析八步：客户端把 www.163.com 的请求发给本地域名服务器（LocalDNS，常由 ISP 经 DHCP 分配、就在运营商机房）；LocalDNS 先查缓存表格，命中即返；否则问根，根见后缀 .com，给出顶级域地址；再问顶级域，得到 163.com 权威地址；再问权威，得 X.X.X.X；最后回客户端建连。
                                                                                                            • 递归：客户端视角是递归查询，LocalDNS 全权代办；LocalDNS 自己则从根逐级问到权威。原文未用“迭代查询”一词。
                                                                                                            • 记录类型：原文只明确 CNAME（起别名，把解析引向 GSLB）；A/MX/NS/TXT 原文未明确。
                                                                                                            • 内部负载均衡：应用配数据库域名而非 IP，换机只改映射；多实例时“这次返回第一个 IP，下次返回第二个 IP”。
                                                                                                            • 全局负载均衡：多机房各有 IP，可轮询；某机房挂了就删掉对应 IP，实现一定高可用；并让北京用户去北京机房、上海用户去上海机房。
                                                                                                            • 示例：全国多数据中心、多运营商，每中心三个可用区，对象存储跨可用区；每中心至少两个内部负载均衡器，后接多个 Proxy-server；权威 DNS 用 CNAME 指向 GSLB；第一层 GSLB 看 LocalDNS 所属运营商，再用 CNAME 转第二层；第二层按 LocalDNS 地址判地理位置，返回就近 Region 六个 SLB 地址；客户端随机或轮询，对象存储三备份支撑读写均衡。

                                                                                                            1. 先判要不要 GSLB：单地域简单应用，权威 DNS 直接返一个或多个 IP 供客户端轮询。
                                                                                                            2. 跨地域跨运营商时，业务域名配 CNAME 指向 GSLB 域名。
                                                                                                            3. 第一层按运营商分流，避免跨网。
                                                                                                            4. 第二层按地理位置选 Region，返回多个 SLB 地址。
                                                                                                            5. 客户端对多 IP 随机或轮询。
                                                                                                            6. 排障先看客户端与 LocalDNS 缓存，再看权威记录和 GSLB 策略。

                                                                                                            • 13 套：全球根域名服务器套数。

                                                                                                            • 2 个：每中心内部负载均衡器下限。
                                                                                                            • 6 个：第二层 GSLB 返回的 SLB 地址数。
                                                                                                            • 3 个：对象存储备份数。
                                                                                                            • 2 层：示例 GSLB 层数。

                                                                                                            19 HTTPDNS：地址簿也会指错路

                                                                                                            核心结论：传统 DNS 的解析权在运营商 LocalDNS 手里，缓存、转发、出口 NAT、忽略 TTL、递归延迟都会让地址簿指错路。HTTPDNS 用自建 HTTP 集群加客户端 SDK，把解析与调度权收回自己手中。

                                                                                                            机制细节：

                                                                                                            • 五个问题：①缓存——LocalDNS 缓存过就不问权威，过期不刷新，用户被带到已搬走的“饭店”；运营商还把静态页缓存在自己机房，解析指向缓存服务器，页面更新后用户看到老页面；旧地址也让全局负载均衡失效。②转发——A 运营商把解析转给 B，权威误判为 B 的用户，返回 B 机房地址，每次访问都跨网。③出口 NAT——网关换地址，权威 DNS 无法据出口 IP 判断真实运营商。④更新——各地实现不一，有的忽略 TTL，权威变更后全网生效漫长，容灾切换时用户长时间异常。⑤延迟——递归遍历多台服务器，可能超时。
                                                                                                            • 工作模式：不走传统 DNS，自建基于 HTTP 的 DNS 集群，分布多地多运营商；客户端直接用 HTTP 请求它拿就近地址。默认解析走 DNS，须绕过默认路径，故通常由 App 内嵌支持 HTTPDNS 的 SDK。
                                                                                                            • 取址：SDK 动态请求服务端，取得 HTTPDNS 服务器 IP 列表并缓存；解析域名时本地也缓存结果；未命中则从列表选一个发 HTTP 请求，返回目标站点 IP 列表。示例 curl http://106.2.xxx.xxx/d?dn=c.m.163.com，返回含 ips 与 ttl 的 JSON。原文未讲 Host 头处理，此处原文未明确。
                                                                                                            • 缓存设计：客户端、缓存、数据源三层，对应 Tomcat、Redis、MySQL；严格按过期时间，未命中或过期且不许用旧记录就发起解析；同步更新实时性好但并发过期会重复请求，对应 Cache-Aside；异步可合并请求、可预加载，对应 Refresh-Ahead，代价是可能用过期数据。
                                                                                                            • 调度设计：SDK 让服务端知道国家、运营商、省、市；多节点时综合错误率、请求时间、压力、网络状况排序，而非只看位置；节点宕机或变慢可快速切换；SDK 上报质量数据，服务端接口配优先级与权重，算出优质低时延 IP 的排序。
                                                                                                            • 兜底：都不工作时切回 LocalDNS，慢也比访问不到好。

                                                                                                            判据·清单·步骤：

                                                                                                            1. 判断是否具备条件：App 类、对时延与调度敏感、能改客户端。
                                                                                                            2. SDK 内置 HTTPDNS 服务器 IP 列表。
                                                                                                            3. 解析先查 SDK 本地缓存，命中即用；未命中或过期则同步调用或投异步任务，取回 IP 列表并写缓存。
                                                                                                            4. 按运营商/SSID 分维度缓存，防调度失真。
                                                                                                            5. 上报质量数据、配置权重，形成调度闭环；全链路失败降级回 LocalDNS。

                                                                                                            数字·阈值：

                                                                                                            • 500 米 / 5 公里：形容指错路的距离对比。
                                                                                                            • 8 年：形容懒导游“8 年前背的导游词就没换过”。
                                                                                                            • 300：示例响应 ttl 值（秒）。
                                                                                                            • 3 层：客户端、缓存、数据源。
                                                                                                            • 2 大问题：解析速度与更新速度的平衡、智能调度。

                                                                                                            20 CDN：你去小卖部取过快递么

                                                                                                            核心结论：CDN 把内容提前放到离用户近的节点，用三级缓存加 DNS 全局负载均衡把请求引到合适的边缘节点，能不回源就不回源。它最擅长静态资源与流媒体，动态内容走边缘计算或链路优化。

                                                                                                            机制细节：

                                                                                                            • 三级缓存：边缘节点多、集群小、缓存不全，可能不命中；其上是区域节点，更大、命中率更高；再上是中心节点，更大；仍不命中才回源。层层兜底，“北京局找不到，找华北局，华北局找不到，再找北方局”。
                                                                                                            • 调度：无 CDN 时，www.web.com 权威 DNS 直接返回站点 IP。有 CDN 后，web.com 权威 DNS 设 CNAME 指向 www.web.cdn.com，LocalDNS 继续解析，问到 CDN 自己的权威 DNS；后者再设 CNAME 指向 CDN 的全局负载均衡器；LocalDNS 请求 GSLB，GSLB 选一台缓存服务器返回其 IP；LocalDNS 缓存并回给客户端，客户端访问边缘节点下载。
                                                                                                            • 选点依据：用户 IP 判断哪台最近；用户所属运营商；URL 中的内容名称判断哪台有该内容；各服务器当前负载判断谁还有服务能力。
                                                                                                            • 回源与分发：边缘未命中就向上一级请求，直至追溯到源站拉到本地。静态页通常拉取（未命中再拉）；流媒体数据量大、回源压力大，常主动推送热点到边缘，并预处理——转不同码流、分片，终端按带宽选超清/标清/流畅。
                                                                                                            • 防盗链：最常用最简单的是 refer 字段，请求带 referer 说明来源页面，非本站就阻止或跳转；但 refer 易被破解，需配时间戳防盗链——管理员与 CDN 厂商约定加密字符串，客户端用时间戳、资源及路径、加密串做签名，链接带签名与截止时间戳；节点比对是否过期，再用同算法验签，一致才放行。
                                                                                                            • 动态 CDN 两模式：生鲜超市模式＝边缘计算，计算与存储放边缘，定时从源同步数据、在边缘算结果；冷链运输模式＝路径优化，数据仍在源站生成，下发走 CDN 规划的网络，选更可靠路径、类似专线；还可调整 TCP 参数更激进传输、多请求复用连接免临时三次握手、压缩数据。
                                                                                                            • 缓存对象：静态页面、图片等不易变的最适合；流媒体走 RTMP 等协议，相当于代理，从上一级缓存读内容转发。

                                                                                                            21 数据中心：我是开发商，自己拿地盖别墅

                                                                                                            核心结论：数据中心是网络知识的集散地：对外是多运营商边界路由器与多线 BGP，对内是接入、汇聚、核心三层，加安全与负载均衡设备。每段链路都要高可用；东西流量后来居上，演进为扁平的叶脊网络。

                                                                                                            机制细节：

                                                                                                            • 边界：出入口是边界路由器（Border Router），为高可用部署多台，并连多个运营商网络；数据中心往往是路由协议里的自治区域（AS），内外互通靠 BGP，即“多线 BGP”。
                                                                                                            • 三层：服务器放进机架（Rack），机架顶端是 TOR 交换机，即接入层（与应用侧接入层不是一个概念）；多机架用汇聚层交换机互联；多可用区再往上用核心交换机，需多组并全互连。
                                                                                                            • 高可用：服务器双网卡双线接 TOR，做网卡绑定（bond），需服务器与交换机支持 LACP；TOR 也需高可用：传统做法两接入两汇聚、层层双连，成环需 STP，代价是一主一备；另一条路是堆叠，多台成一台逻辑交换机，靠私有协议双活。
                                                                                                            • 二层与三层：汇聚层把大量节点连成集群，服务器间二层互通，该区域叫 POD，也叫可用区；避免二层环路可让不同可用区用不同网段，汇聚与核心走三层，广播域隔离，三层有环靠路由选路；核心与汇聚跑 OSPF，并用 ECMP 等价路由做多路径负载均衡与高可用。
                                                                                                            • 大二层与 TRILL：云与大数据要求大规模集群同处一个二层，二层互连上移到核心，即大二层。TRILL 的思路是“二层环有问题，三层环没有问题，那就把三层的路由能力模拟在二层实现”；跑 TRILL 的交换机叫 RBridge，按 MAC 而非 IP 路由，RBridge 间跑链路状态协议算路；TRILL 头里 Ingress/Egress RBridge 类似源/目的 IP，端到端不变，外层 MAC 逐跳改写，跳数每跳减 1；广播用分发树，不同树对应不同 VLAN。
                                                                                                            • 核心之上：挂入侵检测、DDoS 防护等安全设备，是整个数据中心的屏障；还挂负载均衡器。存储侧传统用 SAN/NAS 单独组网，新云计算改用 x86 软件定义存储，与计算同机架融合。
                                                                                                            • 南北与东西：三层结构利于外部请求进出，“上北下南”故称南北流量；节点间互拷数据、左右流动，称东西流量。为此演进为叶脊（Spine/Leaf）：leaf 直连服务器，L2/L3 分界在 leaf，leaf 之上是三层；spine 相当于核心，叶脊间用 ECMP 多路径；南北流量可不直接从 spine 出，而通过与 leaf 并行的交换机接边界路由器。

                                                                                                            判据·清单·步骤：

                                                                                                            1. 边界：多台边界路由器、多运营商、BGP，划 AS。
                                                                                                            2. 机架：服务器双网卡双线接 TOR，启 LACP bond。
                                                                                                            3. 接入与汇聚：双接入双汇聚，选 STP 主备或堆叠双活。
                                                                                                            4. 多可用区：不同网段、三层互通，核心多组全互连，跑 OSPF 加 ECMP。
                                                                                                            5. 大二层上 TRILL；东西流量大则改叶脊，leaf 接服务器、spine 做 L3。

                                                                                                            数字·阈值：

                                                                                                            • 3 层：接入、汇聚、核心（指网络层次，不是 IP 层）。
                                                                                                            • 2 个：服务器网卡与网线的最少数量。
                                                                                                            • 2 个：传统高可用方案中接入/汇聚交换机数量（一主一备）。

                                                                                                            22 VPN：朝中有人好做官

                                                                                                            • 核心结论：连接多个数据中心有三条路——公网不安全、专线太贵、VPN 折中。VPN 用隧道技术在公众网络上仿真一条点到点专线，让机构感觉只在一个数据中心里。IPsec VPN 完全基于软件，安全便宜但性能稍差；MPLS VPN 在 IP 转发上叠加标签转发，性能较好但需向运营商购买。

                                                                                                            • 机制细节：VPN 是用一种协议传输另一种协议的隧道技术，含乘客、隧道、承载三种协议。IPsec 三机制：私密性用对称加密（建立后要传大量数据）配 IKE 传密钥；完整性用 hash 摘要；真实性用预共享密钥对暗号或数字签名（私钥签、对方用证书里的公钥验）。协议簇含 AH（只摘要、不加密）、ESP（加密加摘要）、两类算法、IKE 与 SA 两组件。两阶段：阶段一建 IKE SA，用 DH 算对称密钥 K——约定公开质数 p、q，各持私钥 a、b，交换公钥 A、B 后各自算出相同的 K，K 从不在通道上传输；阶段二建 IPsec SA，用 K 加密传随机密钥 M，M 有生存周期、定期重生。SA 记 SPI、商定的算法与封装模式、生存周期。封装：IP 头里上层协议由 TCP 变成 ESP，ESP 头放 SPI 与序列号，其后全加密，末尾指明内层协议，出隧道逐层解封装。MPLS 前史：IP 无连接、逐跳查表效率差但抗断；ATM 面向连接、打标签走固定路径，效率高但一路由器坏就全断；MPLS 取二者之长在 IP 头外加标签头。LSR 有 FIB 与 LFIB 两表，标签转换出的路径叫 LSP，相邻 LSR 分上下游，标签由 LDP 从下游逐跳分发。MPLS VPN 分 PE/CE/P：P 之间在运营商管控下用标签没问题，客户接入则私网地址常重复，传统 BGP 只选一条会丢掉另一 VPN 的路由，故用 MP-BGP 在 32 位地址前加客户区分符成 VPN-IPv4；PE 上用 VRF 为每客户建一张路由表，像专属小路由器。转发两层标签：外层指示 PE 到对端 PE 的 LSP，内层在对端 PE 查 VRF 决定去哪个 CE。

                                                                                                            • 判据·清单·步骤：① 安全且预算有限→VPN；只求性能肯花钱→专线；公网明文→不可取。② 建隧道：定三层协议→阶段一 DH 算 K、建 IKE SA→阶段二下发 M、建 IPsec SA→ESP 封装→对端解封装。③ 只防篡改→AH；要防窃听→必须 ESP。④ 两端都用私网段→必须 VRF + MP-BGP。⑤ 排障先看外层标签（能否到对端 PE），再看内层标签（能否到 CE）。

                                                                                                            • 数字·阈值：

                                                                                                              • 32 位——IPv4 地址长度，前加区分符构成 VPN-IPv4
                                                                                                              • 20 位标签 / 3 位实验位 / 1 位栈底 / 8 位 TTL——MPLS 头

                                                                                                            23 移动网络：去巴塞罗那，手机也上不了脸书

                                                                                                            • 核心结论：从 2G 到 4G，移动网络从以打电话为主转向以上网为主，2G 上网走的其实是电话网 PSTN，4G 才是全 IP。4G 把控制面与数据面分离：MME/HSS 管鉴权与选路，SGW/PGW 管转发，手机每个包都由 GTP-U 隧道封装。异地上网时 SGW 是当地的、PGW/HSS/PCRF 是归属运营商的，策略仍由国内控制，故在巴塞罗那仍上不了脸书。

                                                                                                            • 机制细节：2G：手机是移动台 MS、需嵌 SIM；无线侧 BSS=BTS（对外无线）+BSC（对内连有线）合称接入网 RAN。入口 MSC 不让你直连互联网：AUC 与 EIR 做安全认证，VLR 看当前位置、HLR 看归属地（涉异地计费），合法且有钱才放行；出口 GMSC 连 PSTN。2.5G 加分组交换支持 IP：基站多 PCU，核心网多 SGSN 与 GGSN。3G 主要改进无线带宽，W-CDMA 理论最高 2M 下行，基站改为 Node B + RNC。4G：eNodeB 合并 Node B 与 RNC，下行向百兆迈进；控制面与数据面分离——原来 MSC/SGSN 既查合法性又转发数据，而控制面是命令小包、要时延，数据面是流量大包、要吞吐，合二为一灵活性差。网元：HSS 存签约信息；MME 是控制面核心，据 HSS 判是否合法，允许则选 SGW/PGW 并告诉 eNodeB，自己不转发数据；SGW 是数据面接待员；PGW 是出口网关，其上的 PCRF 控策略与计费。eNodeB 与 MME 之间 IP 层之上既非 TCP 也非 UDP 而是 SCTP：多宿主（"联合"把多接口多路径放一起，一条失效自动换路；TCP 建连即锁四元组）、多流（不因强制顺序阻塞）、四次握手防 SYN 攻击（收到 Cookie 才分配资源）、消息分帧、断开三次挥手。建通路仍属控制面，用基于 UDP 的 GTP-C：两段隧道，eNodeB–SGW 由 MME 经 S1-MME 与 S11 告知两端，SGW–PGW 由 SGW 经 S5 主动告知；GTP 头有隧道 ID 与序列号，序列号递增保证按序、便于检测重复包，每条信令启定时器、超时重发。打通后 PGW 分配隧道内 IP（类比 IPsec 内层 IP），手机经 S1-U 到 SGW、经 S8 到 PGW 再上互联网；GTP-U 同样是乘客协议（手机的包）、隧道协议（隧道 ID，不同手机不同隧道）、承载协议（SGW 与 PGW 的 IP）。Attach：找 eNodeB 发 Request→转 MME→认证问 HSS→让 SGW 建会话（t1）→SGW 让 PGW 建会话（t2、t3）→PGW 回（t4、t5）→SGW 回 MME（t6、t7）→MME 告 eNodeB 用 t7 接入→eNodeB 回 t8→MME 告 SGW。异地上网：SGW 归所在地运营商、PGW 归所属运营商；在巴塞罗那开机搜到当地 eNodeB，查国内 HSS，允许则手机与当地 SGW、当地 SGW 与国内 PGW 各建隧道，经国内 PGW 上网，判合法、控策略、分 IP、统计流量都在国内，当地只与国内结算。

                                                                                                            • 判据·清单·步骤：① 能否上网四问：卡是否合法→是否本地号→有没有钱→策略是否允许（PCRF）。② 读 4G 拓扑：控制面走 MME，数据面走 SGW→PGW，用户数据在 HSS，计费在 PCRF。③ 复述 Attach 并按隧道 ID 逐段核对。④ 排障先看控制面（GTP-C 序列号与定时器），再看数据面隧道 ID 两端是否配对。⑤ 漫游出口：SGW 在当地、PGW 在归属运营商。

                                                                                                              • 2M——W-CDMA 理论最高下行；百兆级别——4G 下行目标

                                                                                                            24 云中网络：自己拿地成本高，购买公寓更灵活

                                                                                                            • 核心结论：物理机有采购、运维、规格、复用四重不灵活，虚拟机与云计算正为解决它们而生：一点创建、一点销毁、想要多大就多大。虚拟化靠软件模拟硬件，虚拟网卡通过打开 TUN/TAP 字符设备连通内外。云中网络要解决共享、隔离、互通、灵活，互通有桥接与 NAT，隔离用 VLAN；但原生 VLAN 与网桥在大规模下不够用。

                                                                                                            • 机制细节：四重不灵活：采购（自采上架装系统周期长、不能退）、运维（扩容要进机房手动弄）、规格（买来几百 G 内存，应用只需 4 核 8G）、复用（换用户要重装系统）。数据中心用 qemu-kvm 在一台物理机里掏出多台小机器，靠软件模拟硬件：轮流用物理 CPU、内存经虚拟内存映射、硬盘是大文件上 N 个 G 的文件；虚拟化软件像“骗子”，向上骗应用说独享，其实靠向下从物理机弄。虚拟网卡：虚拟机打开 TUN/TAP 字符设备，物理机就出现虚拟 TAP 网卡；包转成文件流写入，内核驱动转回网络包交 TCP/IP 栈后从 TAP 发出。互通：物理机像宿舍、虚拟机像个人电脑，该买交换机——brctl addbr br0、addif br0 tap0 建网桥，两虚拟机配同网段即互通（host-only）。桥接：物理网卡也连虚拟交换机，虚拟机与笔记本同网段，"相当于这个网桥上有三台机器，是一个网段的，全部打平了"；数据中心每台机器建 br0、虚拟机与物理网卡都连 br0，同机跨机都通，但规模大时二层广播严重。NAT：虚拟机网络自成体系，出网 NAT 成物理机地址，笔记本内还内置 DHCP；简化做法是网关配到 br0、手配 IP、iptables -t nat -A POSTROUTING -o ethX -j MASQUERADE，再设 net.ipv4.ip_forward = 1 让物理机当路由器。隔离：同机靠网桥 VLAN tag；跨机因 tag 出桥失效，改用 vconfig 基于 eth0 建带 VLAN 的虚拟网卡，每用户分不同 VLAN（如 10、20）、用不同网桥，出物理机仍带 VLAN ID，交换机支持 VLAN 时只转给相同 VLAN 的网卡与网桥。局限：VLAN ID 只有 4096 个不够用，配置不灵活，谁和谁通、流量隔离都没实现。

                                                                                                            • 判据·清单·步骤：① 该不该虚拟化：采购周期长 / 要 4 核 8G 却买来几百 G / 复用要重装 / 扩容要进机房，命中即上。② 建虚拟网卡四步：开 TUN/TAP→出现 TAP 网卡→包转文件流写入→从 TAP 发出。③ 同机互通：addbr br0→addif tap0/tap1→同网段→互 ping。④ 桥接还是 NAT：与物理机同网段→桥接；自成体系、本地出口→NAT；只同机→host-only。⑤ 物理机当路由器：网关配 br0、手配 IP、MASQUERADE、ip_forward=1。⑥ 跨机隔离：分 VLAN→vconfig 建带 VLAN 网卡→每用户独立网桥→交换机须支持 VLAN。

                                                                                                            • 数字·阈值：

                                                                                                              • 4096——VLAN ID 总数，文中两处强调不够用
                                                                                                              • 几百 G / 4 核 8G——采购规格与应用实际所需
                                                                                                              • N 个 G——虚拟机硬盘对应的大文件
                                                                                                              • VLAN 10 / 20——按用户划分举例；3 台——桥接同网桥上的机器数
                                                                                                              • MTU、VNI 24 位——原文未明确

                                                                                                            • 案例·类比：自己拿地盖房子=物理机（成本高）；购买公寓=虚拟机（可买可卖、更灵活）。虚拟化软件=“骗子”，对上骗应用、对下取物理资源。宿舍=物理机，个人电脑=虚拟机，寝室长的电脑=虚拟网络的路由器与 DHCP。桥接=把两者放同一个网桥、全部打平。

                                                                                                            • 反例·坑：① 直接采购物理机扛业务：周期长、不能退、规格浪费。② 大规模下用桥接打平二层，广播严重。③ 桥接模式还自建 DHCP——打平后应由物理网络分配。④ 只用网桥 tag 做隔离并期望跨物理机生效——tag 出了网桥就不起作用。⑤ 用 VLAN 承载大规模多租户：4096 不够、配置不灵活。⑥ 不确认交换机支持 VLAN 就指望跨机隔离生效。

                                                                                                            • 原文金句："我们常把物理机比喻为自己拿地盖房子，而虚拟机则相当于购买公寓，更加灵活方面，随时可买可卖"；"虚拟化软件就像一个“骗子”，向上“骗”虚拟机里面的应用，让它们感觉独享资源，其实自己啥都没有，全部向下从物理机里面弄"；"VLAN ID 只有 4096 个，明显不够用"。

                                                                                                            • 可迁移主题：虚拟化与资源超卖、TUN/TAP 字符设备、虚拟网桥与二层打平、桥接 vs NAT、VLAN 的规模上限。

                                                                                                            25 软件定义网络：共享基础设施的小区物业管理办法

                                                                                                            • 核心结论：用原生 VLAN 加 Linux 网桥管云平台，灵活性与隔离性不足，且缺统一视图。SDN 把控制面从转发设备中抽出、逻辑上集中，经开放接口取全局视图再优化。OpenFlow 是控制器与设备间的南向接口协议，OpenvSwitch 是支持它的软件虚拟交换机，能对经过的包任意修改；引入云后配置简单灵活，并解耦物理与虚拟。

                                                                                                            • 机制细节：三特点：控制转发分离——转发平面是虚拟或物理设备（像小区一条条路），控制平面是统一控制中心（像物业监控室），原来管理员要出来到路上管设备；开放接口——向上给应用的是北向（像总控室的按钮），向下调设备的是南向（像远程控电梯）；逻辑集中控制——控制整个物理网络，取得全局视图再优化。OpenFlow 是控制器与设备互通的南向协议；OpenvSwitch 是支持它的软件虚拟交换机，也有硬件交换机支持。流表：包都经规则处理（接收、转发、放弃），每行一条、有优先级，满足匹配条件（哪个端口进来、包头有什么）则改包头、跳表、转到某网口或丢弃，覆盖四层：in_port、MAC、IP、端口号，各配 mod_* 动作。实验一 VLAN：access port 配 tag（进包打 tag，出包不带 VLAN ID）；trunk port 配 trunks（为空则所有 VLAN 都 trunk，否则仅列出的 ID 通过）。实验二 bond 三模式：active-backup、balance-slb、balance-tcp（须 LACP）。架构：内核态 OpenvSwitch.ko 即 Datapath，包到达即取各层信息；OVSDB 收 ovs-vsctl 的建交换机与端口命令、存拓扑到文件，vswitchd 收 ovs-ofctl 的流表放用户态 Flow Table。内核表命中即执行，未命中经 Netlink 进用户态，内核用 upcall 通知 vswitchd 查全量用户态表（内核规则会过期），命中后 reinject 回内核。云中：无 OpenvSwitch 时每租户要新建带 VLAN 的网卡加独立网桥，且两层 VLAN 强绑定；引入后所有虚拟机放一个 br0、按用户配 tag 即隔离，另建 br1 隔离物理与虚拟（一台机器上虚拟机不超过 4096 个，虚拟 VLAN 从 1 开始够用；两台机器上 A/B 用 1/2 与 7/6）；两层 VLAN 可不一致，靠 dl_vlan 匹配加 mod_vlan_vid 改写进出物理机的包。

                                                                                                            • 判据·清单·步骤：① 要不要上 SDN：逐台登录设备、缺统一视图、租户多到网桥爆炸、两层 VLAN 强绑定，命中即上。② 三面：转发面（路）、控制面（监控室）、应用面（北向）；上北下南。③ 配 VLAN：接终端且只需一个 VLAN→access 配 tag；需透传多个→trunk 配 trunks；要全通过→trunks 留空。④ 实验先关 MAC 学习、设 flood-vlans，否则广播掩盖隔离效果。⑤ 只要冗余→active-backup；按源 MAC+VLAN 分摊→balance-slb；有 LACP 且按 L2/L3/L4 分摊→balance-tcp。

                                                                                                            • 数字·阈值：

                                                                                                              • 3 个特点、2 个方向、4 层（流表覆盖）
                                                                                                              • 2 类端口、3 种 bond_mode
                                                                                                              • 4096——VLAN ID 上限，也是一台物理机上虚拟机数上界
                                                                                                              • tag 101/102/103——实验一 vnet0/1/2；trunks=101,102
                                                                                                              • tag 1/2 与 7/6——两台机器上用户 A、B 的 tag（可不一致）
                                                                                                              • VNI 24 位、VXLAN、OpenFlow 版本号——原文未明确

                                                                                                            • 反例·坑：① 继续逐台登录设备管云网络，缺统一视图。② 无 OpenvSwitch 时每租户建网卡加独立网桥，租户一多就崩。③ 让两层 VLAN 透传、规划期强绑定。④ 只靠 VLAN 扛规模不够。⑤ 只有 access port 出的包不带 VLAN ID，trunk port 不是。⑥ 以为 OpenvSwitch 只在用户态处理——内核 Datapath 先匹配。

                                                                                                            26 云中的网络安全：虽然不是土豪，也需要基本安全和保障

                                                                                                            核心结论 公有云不纯净，扫端口、探应用、找漏洞的行为到处都是。防法不是把每台机器加固到极致，而是"仅仅开放需要的端口，而将其他的端口一概关闭"，用一个入口守住全部风险。手段是 ACL 控 IP 与端口，规则集合在云上叫安全组，基座是 Netfilter 与 iptables。

                                                                                                            机制细节 包进机器：先看 MAC 头是不是自己的，是则取 IP 头做路由判断。判断前是 PREROUTING；给自己的上送传输层是 INPUT；要转发是 FORWARD；本机产生的结果发出是 OUTPUT；最后 POSTROUTING。Netfilter 能在这五点插 hook 函数：改包、ACCEPT 交回协议栈、DROP 丢弃、QUEUE 交用户态进程（QUEUE 常用于内部负载均衡，因目标地址与权重都可能变）。 实现是内核模块 ip_tables，分 conntrack、filter、nat、mangle 四类，conntrack 是基础功能、被其余依赖。用户态 iptables 对应表和链，四表优先级 raw→mangle→nat→filter 递减：filter 三链管 INPUT/FORWARD/OUTPUT，nat 在 PREROUTING 改目标地址、POSTROUTING 改源地址。 批量下发：两台 VM 经 tap 连到二层网桥、可随意互通，所以要另加一个网桥专放 iptables 规则，每台机器跑 Agent 把界面上的安全组翻译成规则下发。本讲只覆盖 ACL/安全组这层，WAF、DDoS 清洗原文未明确。

                                                                                                            判据·清单·步骤

                                                                                                            1. 全关：iptables -t filter -A INPUT -s 0.0.0.0/0.0.0.0 -d X.X.X.X -j DROP。
                                                                                                            2. ssh 被关在门外，用 -I 插到 DROP 之前补开 22。
                                                                                                            3. Web 补开 80，一旦打开必须单独防护。
                                                                                                            4. 多机改安全组：Tomcat 机入组 A（8080 对 0.0.0.0/0，22 仅管理员网段），MySQL 机入组 B（3306 只许组 A）。
                                                                                                            5. 出公网做 SNAT；被外网访问则显式配 DNAT + SNAT。

                                                                                                            数字·阈值

                                                                                                            • 5 个节点：PREROUTING/INPUT/FORWARD/OUTPUT/POSTROUTING。
                                                                                                            • 4 张表：raw→mangle→nat→filter，优先级递减。
                                                                                                            • 22 / 80 / 8080 / 3306：ssh、Web，示例中 Tomcat 与 MySQL 端口。

                                                                                                            27 云中的网络 QoS：邻居疯狂下电影，我该怎么办？

                                                                                                            核心结论 云上必有住户不自觉抢占带宽，需 QoS 保障多数人。入向与出向里，真正能控的只有出向——用 Shaping 把流量塑成想要的模样；入向无法控制，只能 Policy 丢包。Linux 用 TC 做 QoS，核心是队列，分无类别与基于类别两类，云里 OpenVSwitch 主用 HTB。

                                                                                                            机制细节 无类别规则不分类。pfifo_fast 分三个先入先出队列（三个 Band），按包内 TOS 决定入队，Band 0 优先级最高，发完才轮到 Band 1、2。SFQ 按 TCP Session 的 hash 分队列、另一端轮询取出，于是没有单个 Session 占满流量。TBF 令牌桶：包要拿到令牌才能发，令牌按设定速度生成，队列再长也只能按此速度发；队列空时令牌照常生成但不无限累积，放满桶为止，桶大小就是防"长期空闲攒满令牌、突发流量瞬间打爆"。 基于类别的典型是 HTB，往往是一棵树：给 eth0 建根规则付句柄 (1:)，下挂分支 (:10)(:11)(:12)，default 12 指默认分支。每个节点两个速度：rate 是一般速度、ceil 是最高速度，根节点两者相同；三个子类 30/10/60kbps，rate 之和等于网卡最大速度。叶子挂 fifo 或 sfq，再用 u32 filter 按源 IP、端口分流。关键特性：同一 root class 下的子类可相互借流量；不先建 root class 而直接建三个 class 则不能互借，空闲带宽就浪费了。 云里用 OVS：入向设 Ingress policy（ingress_policing_rate/burst），出向设 Egress shaping，支持 HTB。在 port 上建 QoS 规则，一条规则含多个 Queue，min-rate 对应 rate、max-rate 对应 ceil，再用流表把匹配的包 enqueue 到不同队列。

                                                                                                            判据·清单·步骤

                                                                                                            1. 先判方向：入向只能丢包，整形只能做出向。
                                                                                                            2. 单机整体限速用 TBF：设 rate 与桶大小。
                                                                                                            3. 多租户按比例分：先 root class 再子 class（否则不能借流量），子类 rate 之和 = 网卡总带宽，ceil 都设为总带宽。
                                                                                                            4. 叶子挂 pfifo（限长）或 sfq（防单流占满）。
                                                                                                            5. 云内：OVS port 建 qos（linux-htb）→ 多 queue 配 min/max-rate → 流表 enqueue。

                                                                                                            数字·阈值

                                                                                                            • 3 个 Band：pfifo_fast 的三个 FIFO 队列。
                                                                                                            • TOS 4 位 / 16 种：决定入哪个 Band；priomap 16 个数字（0–2）即映射表。
                                                                                                            • 100kbps：示例根节点 rate 与 ceil；子类 30/10/60kbps 相加即 100kbps。

                                                                                                            28 云中网络的隔离 GRE、VXLAN：虽然住一个小区，也要保护隐私

                                                                                                            核心结论 VLAN 只有 12 位、共 4096 个，现在绝对不够用。改协议不可行——标准形成后千千万万设备上的程序都按此规则跑，没法挨个通知。可行的是扩展：在原包格式上扩一个头装区分租户的 ID，外层尽量与传统一致以保持兼容。物理网络叫 Underlay，基于它虚拟化出的叫 Overlay。

                                                                                                            机制细节 GRE 是 IP-over-IP 隧道：IP 包封进 GRE 包、外面加 IP 头，一端封装、通路传输、另一端解封装，可视为虚拟点对点连接。GRE 头前 32 位必有、后续可选，前 4 位标识位说明有无可选项，关键是 32 位 key 字段，常放区分用户的 Tunnel ID；NVGRE 给网络 ID 24 位。封解封装落在路由器或有路由功能的 Linux 机器上；三个不足：点对点使隧道数随网络数指数增长、不支持组播、很多防火墙与三层设备解析不了 GRE。 VXLAN 从二层外面套 VXLAN 头，VNI 24 位，外面再封 UDP、IP、外层 MAC——比 GRE 多的是 24 位 VNI 与 UDP 承载。封装点叫 VTEP，相当于虚拟机网络的管家：每台物理机可有一个，VM 启动向它注册，跨 VTEP 通信由它代理。VXLAN 不是点对点：VTEP 用 IGMP 入组播组；VM1 不知 VM2 的 MAC 就发 ARP，VTEP1 把 ARP 封进 VXLAN 组播（等于群里 @all），管着 VM2 的 VTEP2 回应后双方各学到归属，之后走单播。 落云平台：宿舍分家后 br0 被一刀三断，用隧道把几段 br0 连起来，看起来还在同一个 br0 上；多一个 br1 是把虚拟机互联与物理机互联分成两层，中间怎么挖都行。OVS 支持 GRE、VXLAN、IPsec_GRE，此时虚拟交换机就是封装端点；流表全放 br1：入端口分类、Tunnel ID 转 VLAN ID、MAC 学习、未匹配丢弃。

                                                                                                            判据·清单·步骤

                                                                                                            1. 租户数超 4096 就必须上 Overlay，不能靠加 VLAN。
                                                                                                            2. 点到点、租户少、设备能解 GRE：可用 GRE，Tunnel ID 32 位。
                                                                                                            3. 要组播/广播域、要过普通设备：选 VXLAN（UDP 承载，VNI 24 位）。
                                                                                                            4. OVS 落地：br0 对接虚拟机、br1 对接隧道，每张流表写默认 drop。

                                                                                                            数字·阈值

                                                                                                            • VLAN 12 位 / 4096 个：现役隔离标识容量，已不够。
                                                                                                            • GRE key 32 位；NVGRE 网络 ID 24 位。
                                                                                                            • VNI 24 位：原文只说"也够用了"，1600 万这一数字原文未明确。
                                                                                                            • VXLAN 端口 4789、MTU 减 50：原文未明确（本讲只写外层封 UDP，未讨论 MTU 开销）。

                                                                                                            • VXLAN ID=101：示例中同用户三台虚机共用的 VNI。

                                                                                                            29 容器网络：来去自由的日子，不买公寓去合租

                                                                                                            核心结论 虚拟机是买公寓，容器是合租——有隔离，但没那么好。云计算解决了基础资源层的弹性伸缩，没解决 PaaS 层应用随之而来的批量快速部署，容器因此出现。容器思想是软件交付的集装箱：打包与标准。打包靠 namespace（看起来隔离）与 cgroup（用起来隔离），标准靠镜像。

                                                                                                            机制细节 namespace 让每个空间的应用看到不同的 IP、用户空间、进程号；cgroup 让整台机器有很多 CPU 内存而一个应用只能用其中一部分。镜像是把"焊好集装箱那一刻"的状态存成一系列文件。 用 namespace 造路由器：ip netns add routerns 产生独立空间→开 ip_forward→初始化 iptables 以备 NAT→用 OVS 建 internal 口 taprouter（接 br0）与 taprouterex（接外网桥）→ip link set ... netns 塞进去→配地址（内 192.168.1.1、外 16.158.1.100）→配路由→PREROUTING 做 DNAT（16.158.1.103→192.168.1.3）、POSTROUTING 做 SNAT（反向）。 cgroup 里相关的是 net_cls：用 classid 标记包让 tc 识别。挂 net_cls→建 a、b 目录→PID 写进 tasks→classid 写 0xAAAABBBB（AAAA 冒号前、BBBB 冒号后）→tc filter ... handle 1: cgroup，于是 a 的包打 1:10、b 打 1:11。 容器接物理网：容器内外各一张网卡，外卡连 docker0。容器没有虚拟化软件、不用 TUN/TAP，而用一对 veth：ip link add ... type veth peer name ...，一边发包另一边能收到；一端挂网桥并 up；另一端靠 namespace 名（docker 即 pid）塞进去——先 ln -s /proc/<pid>/ns/net /var/run/netns/<pid> 软链，再 ip link set veth2 netns <pid>、改名 eth0、配 172.17.0.2/24。 出公网：Docker 默认 NAT。宿主一句 -A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE，容器源 IP 换成物理网卡 IP，多容器共用一个外网 IP，连接记入 conntrack；回包按 conntrack 取回原私网 IP 做 DNAT 再经 docker0 进容器。对外服务用 -p 10080:80：docker-proxy 监听 10080 转 80，或在 PREROUTING 加 DNAT。四种模式里本讲只展开 bridge（docker0）与 NAT，host 与 overlay 模式原文未明确。

                                                                                                            判据·清单·步骤

                                                                                                            1. 判诉求：要"看起来隔离"用 namespace，要"用起来隔离"用 cgroup。
                                                                                                            2. 造 namespace 路由器：add netns→开 ip_forward→初始化 iptables→建 internal 口→set netns→配内外地址→写路由→配 SNAT/DNAT。
                                                                                                            3. cgroup 限带宽：挂 net_cls→建目录→PID 写 tasks→classid 写 0xAAAABBBB→tc filter。
                                                                                                            4. 单机互通：建 veth pair→一端挂网桥→取 pid→软链→另一端 set netns→改名 eth0→配 IP。
                                                                                                            5. 对外服务优先用 DNAT（少一层用户态转发）。

                                                                                                            数字·阈值

                                                                                                            • MTU 1500：veth pair 两端示例值。

                                                                                                            • 12065 / 12345 / 12346：示例容器 PID（即 namespace 名）、用户 a/b 的进程 ID。
                                                                                                            • 0x00010010 / 0x00010011：classid，对应 flowid 1:10、1:11。
                                                                                                            • 10080:80：端口映射示例。

                                                                                                            案例·类比

                                                                                                            30 容器网络之 Flannel：每人一亩三分地

                                                                                                            核心结论 NAT 在多主机下有两个硬伤：IP 重叠与端口冲突。注册中心里两台机器上的容器都叫 172.17.0.2，A 访问 B 变成"自己访问自己"。改注册物理机 IP 和映射端口也不行——容器内应用无从知道，还要求老框架适配、让容器感知外部环境。Kubernetes 只提出"网络模型要变平"，Flannel 负责落地：每台物理机抠一个不重叠小网段，跨主机靠 Overlay 打通。

                                                                                                            机制细节 冲突根因：每台装好 Docker 的物理机默认都分到 172.17.0.0/16，第一个容器一般 172.17.0.2。解法是在大网段里给每台抠一个小网段，如 A 用 172.17.8.0/24、B 用 172.17.9.0/24。 UDP 后端：容器默认路由指向 172.17.8.1（即 docker0 的 IP），物理机路由把对端容器网段指向 flannel.1，包就进了这块网卡。它来自每台机器上的 flanneld：打开 /dev/net/tun 时网卡出现，flanneld 把包读进用户态、封进 UDP，外层加两端物理机 IP。用 UDP 是不想在 flanneld 之间建两两连接——UDP 无连接概念，任何机器都能发给另一台。对端解包后从自己的 flannel.1 发出，按路由交给 docker0 再进容器。连通性没问题，但全程用户态，代价是性能差。 VXLAN 后端：不开 TUN，而用 netlink 通知内核建 VTEP 网卡 flannel.1。包经 docker0 转到 flannel.1 后由它封装：内层 MAC 为一对 flannel.1，外挂 VXLAN 头，外层 IP 为两端物理机 IP；对端解包后按路由进 docker0。代价是封装开销，收益是封装下沉内核。 host-gw 后端：正文只展开 UDP 与 VXLAN，host-gw 未在正文出现（原文未明确其细节）；留言区补充说它靠主机路由转发、要求宿主机与其他物理机同 VLAN 或局域网，不封包解包故更高效。

                                                                                                            判据·清单·步骤

                                                                                                            1. 单机玩票：NAT 够用，不必上 Flannel。
                                                                                                            2. 多主机 + 微服务 + 注册中心：必须解决 IP 重叠与端口冲突。
                                                                                                            3. 划网段：在 172.17.0.0/16 内给每台分配互不重叠的 /24。
                                                                                                            4. 要性能选 VXLAN（内核封装），要最简选 UDP（用户态）。
                                                                                                            5. 排障：容器默认路由→docker0 网关→flannel.1 路由→外层 IP 可达→对端解封装。

                                                                                                            数字·阈值

                                                                                                            • 172.17.0.0/16：Docker 默认网段；172.17.0.2 两台机器必撞；/24 是每台抠出的子网段长度。
                                                                                                            • 172.17.8.1 / 172.17.9.1：docker0 网桥 IP（容器默认网关）；容器 A、B 为 172.17.8.2 / 172.17.9.2。
                                                                                                            • flannel.1：UDP 模式由 /dev/net/tun 生成，VXLAN 模式由 netlink 建 VTEP。

                                                                                                            31 容器网络之 Calico：为高效说出善意的谎言

                                                                                                            核心结论 Flannel 走隧道，与虚拟机思路相近；但它有个虚拟机 Overlay 没有的好东西：不同物理机分不同网段。虚拟机里网段在各物理机之间"飘来飘去"，网段不同才有做路由策略的可能。Calico 建在这上面：不走 Overlay、不引入额外损耗，转发全用三层路由；代价是假设物理机可当路由器，跨网段靠 IPIP 兜底。

                                                                                                            机制细节 思路：两台物理机在同一二层、容器网段不同，就把物理机配成路由器、按容器网段配路由表：A 上写"访问 172.17.9.0/24 下一跳是 192.168.100.101"，B 上写"从 docker0 进去"，反向同理。全走三层不必每台都用 docker0，直接路由到 veth pair 在物理机这一端的网卡。 容器 A1 地址是 172.17.8.2/32——/32 不是 /24，把容器当单点局域网。默认路由 default via 169.254.1.1 dev eth0，而 169.254.1.1 在拓扑里没有任何网卡拥有：访问网关先 ARP 拿 MAC、把目标 MAC 换成网关 MAC，网关 IP 根本不进包头——"没有人在乎这个地址具体是什么，只要能找到对应的 MAC，响应 ARP 就可以了"。这个 MAC 是 Calico 硬塞的，而物理机 A 上 veth1 正是它，于是包第一跳就到了物理机 A 这台路由器。A 上三条路由：两个本机容器各一条 scope link，加对端网段 via 192.168.100.101；B 对称。全程无封装，性能好很多。 组件：容器不断增删、节点不断进出，手工配路由不行，所以每台要有 agent 自动改路由，叫 Felix；路由还要广播"我能到哪里、如何能到我"，Calico 用 BGP：每个 Node 跑 BIRD 作 BGP Speaker 全互连，规模再大改用 BGP Route Reflector 按机架分域。 跨网段：上述前提是两台物理机同网段同交换机。若不同网段，中间就要多一台路由器，B 的下一跳成了它，原逻辑失效——A 不可能知道 B 出来后的下一跳是谁；让中间路由器都适配 Calico"这在大部分情况下，是不可能的"。解法是打隧道：容器 IP 作乘客协议、物理机 IP 作承载协议，从两端看 A 的下一跳就是 B，即 IPIP 模式，路由变成 ... dev tun0。

                                                                                                            判据·清单·步骤

                                                                                                            1. 先确认物理机是否同网段同二层：是则纯路由无封装，否则 IPIP；容器网段每台一个、互不重叠（承第 30 讲）。
                                                                                                            2. 容器侧 /32 + 假网关，靠 ARP 把下一跳指到宿主 veth；物理机侧写"本机容器 scope link + 对端网段 via 对端物理机"。
                                                                                                            3. Felix 改路由、BIRD 广播；规模上去加 Route Reflector，跨网段改 IPIP。

                                                                                                            数字·阈值

                                                                                                            • /32：容器地址掩码，把容器当单点局域网。

                                                                                                            32 RPC 协议综述：远在天边，近在眼前

                                                                                                            • 核心结论：远程调用不是"会 Socket 就能干"，它必须同时解决协议约定、传输、服务发现三类问题。 Bruce Jay Nelson 的论文 Implementing Remote Procedure Calls 定义了 RPC 调用标准，此后所有框架照此模式；ONC RPC 与 NFS 是最早的示范实现。
                                                                                                            • 机制细节：
                                                                                                              • 五个问题：语法（用字符串 "add" 还是整数 1 表示加法、返回值正误怎么表达）、传参（先传参数还是先传操作符；TCP 是流，两次调用如何分界、怎么算读完）、数据表示（变长类型/结构体/类、各平台 int 长度不同、大端小端）、如何知道服务端有哪些调用及端口、错误重传丢包性能怎么办。前三问=协议约定，第五问=传输，第四问=服务发现。
                                                                                                              • 三层：用户层只管业务；Stub 层管语法语义与封装解封装；RPCRuntime 管高性能传输与网络异常。链路：调本地 Stub → 按约定编码接口/方法/参数 → RPCRuntime 发包 → 服务端 RPCRuntime 交提供方 Stub 解码 → 调方法 → 结果编码回传 → 客户端 Stub 解码返回。
                                                                                                              • ONC RPC：定义程序号/版本/方法号/参数 → 工具据协议定义文件生成两端 Stub → XDR（外部数据表示法）编解码，两端共享同一份；客户端 clnt_create 建连、调 add_1 这个 Stub、内部走 clnt_call。
                                                                                                              • 传输：每客户端一个传输管理层，每次调用是一个任务，内含队列与拥塞窗口；异步靠状态机——起始态查队列空位（无则结束或重试）→ 分配内存、取服务端口、连服务器（失败则结束或重试）→ 发请求 → 等结果（发送出错重发、连接断了重连、超时重传）→ 解码结束。
                                                                                                              • 服务发现靠 portmapper：RPC 程序启动时向它注册随机端口，客户端先查它拿端口再建连（mount 的 RPC 调用即如此）。
                                                                                                            • 判据·清单·步骤：①写协议描述文件，把程序号、版本号、方法号、参数、返回格式全部编号化；②用工具生成两端 Stub，业务只调 Stub；③写 XDR 编解码文件两端共享；④传输层做成状态机+队列+拥塞窗口，覆盖连接失败、发送失败、超时、断连；⑤起独立进程做服务发现。想让上层"像调本地"→ 上 RPC 框架；只要一次性字节收发 → 裸 Socket。
                                                                                                            • 数字·阈值：
                                                                                                              • 5 个问题——协议约定 3 + 传输 1 + 服务发现 1。
                                                                                                              • 3 层——用户层 / Stub / RPCRuntime。
                                                                                                              • 2 个 NFS 进程——mountd、nfsd。
                                                                                                              • 32 位 = 4 个 Byte——讲大小端时整数 1 的存放空间。
                                                                                                              • 0 / 1——XID 中请求为 0、回复为 1。
                                                                                                              • RPC_MISMATCH / PROG_UNAVAIL / PROG_MISMATCH / PROC_UNAVAIL / GABAGE_ARGS——版本不匹配 / 程序找不到 / 程序版本不匹配 / 方法找不到 / 参数无法解析。
                                                                                                              • 超时秒数、重试次数、队列长度——原文未明确（仅"如果超时，可以重新传输"）。
                                                                                                            • 案例·类比：本地调加法函数三下五除二，远程化后门槛陡增，"搞定 Socket 只是万里长征第一步"。最低位放最后一个位置叫 Little Endian，放第一个位置叫 Big Endian；TCP/IP 按 Big Endian 设计、X86 多按 Little Endian 设计，发出去要转换。NFS 把远程目录 mount 到本地，操作远程文件像操作本地——正是"远在天边，近在眼前"。
                                                                                                            • 反例·坑：以为建个 TCP 或 UDP 连接就能通信；以为 TCP 兜住一切——服务器崩溃重启后连接断开，TCP 就保证不了，须应用自己重新调用；用随机端口却不做服务发现；两端协议文件不一致还指望能解开。
                                                                                                            • 原文金句：
                                                                                                              • "这里处理了连接失败、重试、发送失败、超时、重试等场景。"
                                                                                                              • "不是大牛真写不出来，因而实现一个 RPC 的框架，其实很有难度。"
                                                                                                              • "当然无论是什么 RPC，底层都是 Socket 编程。"
                                                                                                              • "在网络上传输超过一个 Byte 的类型，还有大端 Big Endian 和小端 Little Endian 的问题。"
                                                                                                            • 可迁移主题：协议分层、Stub、XDR/IDL、服务发现、状态机、大小端

                                                                                                            33 基于 XML 的 SOAP：不要说 NBA，请说美国职业篮球联赛

                                                                                                            • 核心结论：二进制 RPC 把参数压成一个二进制串，代价是格式须一位不差、改字段要全员重发版、且面向函数而非对象，对"陌生人调用"不成立，于是转向文本。 SOAP 用 XML 写信封、HTTP 传输、WSDL 描述、UDDI 注册，把可读性换回来。
                                                                                                            • 机制细节：
                                                                                                              • ONC RPC 四痛点：压缩格式必须完全一致，多一位少一位错一位都可能无法解压缩；协议修改不灵活，增删字段若未及时通知或线上未升级就解压失败，还得按协议文件重新生成双方 Stub；版本问题——服务端已有 50 个客户端在调，一个新客户端要加字段却要所有客户端重写适配；明显面向函数而非对象。
                                                                                                              • XML 的好处：price 与 author 换位不影响解析，不会"把作者名字解析成 68"；客户端加一行 recommended，不需要的客户端不解析即可；且天然在描述一个订单对象。
                                                                                                              • 传输：POST /purchaseOrder，Content-Type: application/soap+xml; charset=utf-8，正文为 XML。
                                                                                                              • 信封三层：Envelope（带 encodingStyle）→ Header（<m:Trans soap:mustUnderstand="1">1234 标明这是一笔交易）→ Body（装 m:purchaseOrder 的 order 明细）。
                                                                                                              • 约定用 WSDL（本身也是 XML），五段递进：types（xsd:complexType 定义 order：date/className/Author 为 string、price 为 int）→ message → portType（含 operation 与 input/output）→ binding（soap:binding style="rpc"、transport 指向 soap/http、soap:body use="literal"）→ service（soap:address location）。
                                                                                                              • 发现用 UDDI（Universal Description, Discovery, and Integration）注册中心：提供方发布 WSDL，使用方查描述、封装成本地客户端调用。服务地址后加 ?wsdl 即可取到描述文件，再用工具生成客户端 Stub。
                                                                                                            • 判据·清单·步骤：对端是同一拨人、能天天开会 → 二进制即可；面向不确定外部客户 → 必须自描述文本。落地六步：用 XML 定义业务对象 → 塞进 Envelope 的 Body、交易号放 Header 并置 mustUnderstand → HTTP POST 发送并声明 application/soap+xml → 写 WSDL（类型/消息/端口/绑定/地址）→ 发布到 UDDI → 调用方取 ?wsdl 生成 Stub。判据：要机器可校验的契约选 WSDL，别写官网文档。
                                                                                                            • 数字·阈值：
                                                                                                              • 68——示例订单 price 值。
                                                                                                              • 4 个字段——date、className、Author、price。
                                                                                                              • 50 个客户端——改版本时要一起适配的存量调用方。
                                                                                                              • 1 位——二进制串多/少/错一位即可能解压失败的量级。
                                                                                                              • 1234——Header 中的 Trans 交易号。
                                                                                                              • 8080——WSDL 中 soap:address 的示例端口。
                                                                                                              • 1 个方法——SOAP 通常只用 POST。
                                                                                                              • 实际并发量、QPS、信封体积上限——原文未明确。
                                                                                                            • 案例·类比：缩略语贯穿全篇——对篮球爱好者说 "NBA" 立刻懂，对大妈说 NBA 就不知所云，所以要说"美国职业篮球联赛"。映射：二进制=缩略语，只在有大量共同语言的小圈子成立；文本=全称，陌生人也能懂。信封类比：请求和回复装进信封，信分抬头（Header）与正文（Body），像寄邮件。
                                                                                                            • 反例·坑：把接口文档放官网当契约——"文档不一定更新得那么及时""也不一定那么严谨"，于是常常调试不成功；二进制下增删字段不通知对方就上线；为一个字段让 50 个客户端全部重写（不需要该字段的客户端很"冤"）；要求面向对象设计却用二进制串传对象。
                                                                                                            • 原文金句：
                                                                                                              • "这一切的根源就在于压缩。"
                                                                                                              • "这就像平时我们爱用缩略语。"
                                                                                                              • "SOAP 将请求和回复放在一个信封里面，就像传递一个邮件一样。"
                                                                                                              • "SOAP 有三大要素：协议约定用 WSDL、传输协议用 HTTP、服务发现用 UDDL。"

                                                                                                            34 基于 JSON 的 RESTful：我不关心过程，请给我结果

                                                                                                            • 核心结论：REST 不是标准而是架构风格（Representational State Transfer，表述性状态转移），核心是把"以过程为中心"翻成"以资源为中心"，从而无状态、可横向扩展、可缓存。 无状态的真义：服务端只维护资源状态，客户端自己维护会话状态。
                                                                                                            • 机制细节：
                                                                                                              • HTTP 的 PUT/DELETE/GET/POST 恰好对应增删查改；SOAP 里创建与删除都用 POST、把动作写进 XML（CreateOrder/DeleteOrder），RESTful 则用 POST 放订单信息、DELETE 放订单 ID，正文换 JSON。
                                                                                                              • 状态之痛：NFS 中客户端 cd hello，服务端得记住它上次在 /root/liuchao，另一客户端同样 cd hello 却要显示 /var/lib/hello；next() 同理，A 在 20～30 页、B 在 100～110 页，服务端各记一份。
                                                                                                              • 以前不出问题是因为客户端/服务端比例没失衡：NFS 记得住，公司内部 ERP 用户不多、一台强物理机也记得过来；"双十一"彻底失衡，多台服务端分担时状态无法交接。
                                                                                                              • 于是服务端只记资源状态（文件、报表、库存），客户端记会话状态：不能再请求"当前目录下的 hello"，要先自知 /root/liuchao 再请求 /root/liuchao/hello；不能说"下一页"，要说"我要 110～120 页"。
                                                                                                              • 推论：只有资源状态变了才调 POST/PUT/DELETE；只是客户端状态变了对服务端都是统一 GET。读多写少因此受益，且资源状态不变就给了缓存可能——可缓存到接入层甚至 CDN 边缘节点。
                                                                                                              • API 转向以资源为核心：告诉服务端"资源最终变成什么样"而非"做什么动作"；库存不传"减去多少"，而传"目标库存数"（并校验当前库存数匹配）。必须幂等：重试要求同一调用多次结果一致，不能一次支付因调三次变支付三次、不能 cd a 做三次变 cd a/a/a、不能扣三次库存。
                                                                                                              • 与 SOAP 分野：SOAP 正文可放任何动作（<ADD>、<MINUS>），便于把大量动作塞进 API；RESTful 的 JSON 基本只描述资源状态，可触发动作只有 CRUD 四个。
                                                                                                              • 服务发现：Spring Cloud 的 Eureka 做注册中心；提供方注册、续约、下线，注册数据含服务名、机器 IP、端口号、域名；消费方拉取信息，提供方可注册多个做负载均衡与容错；RestTemplate 把请求对象转 JSON 发起调用、按返回 JSON 解析成对象。
                                                                                                            • 判据·清单·步骤：①先问"谁维护状态"，能推给客户端的一律推；②API 从动词改名词（资源+绝对路径/绝对区间），客户端先算好再请求；③只用 POST 增、DELETE 删、GET 查、PUT 改；④每个写接口验幂等：重试三次结果须等同一次；⑤资源未变的读请求全走 GET 以便接入层/CDN 缓存；⑥服务注册到 Eureka 并做客户端负载均衡。高并发、面向海量陌生客户端、读多写少 → RESTful。
                                                                                                            • 数字·阈值：
                                                                                                              • 4 个 HTTP 方法——POST/GET/PUT/DELETE 对应增查改删。
                                                                                                              • 20～30 → 30～40 页——客户端 A 调 next() 的区间跃迁。
                                                                                                              • 100～110 → 110～120 页——客户端 B 的区间跃迁。
                                                                                                              • 3 次——幂等要防的重复调用次数。
                                                                                                              • 1 个 next()——服务端有状态的典型反例。
                                                                                                              • QPS、并发连接数、缓存命中率、超时秒数——原文未明确（只用"双十一"描述量级）。
                                                                                                            • 案例·类比：NFS 的 cd hello 与 ERP 报表页码演示"服务端替每个客户端记状态"的旧模式，"双十一"演示比例失衡后旧模式崩溃。映射：本地调用=数据都在本地谁处理都一样；RPC=追求透明于是忘记状态归属；REST=把会话状态塞回客户端口袋，服务端只当资源仓库。
                                                                                                            • 反例·坑：在 RESTful 里用技巧塞入基于动作的有状态请求——原文直指"这属于反模式了"；库存传"减去多少"而非目标值；依赖服务端记住"当前目录""当前页"；写接口不幂等却允许重试；把 REST 当严格标准逐条比对（它只是风格）。

                                                                                                              • "所以，从接口角度，就让你死了这条心。"
                                                                                                              • "而且只要服务端的资源状态不变，就给了我们缓存的可能。"
                                                                                                              • "REST 不是一种严格规定的标准，它其实是一种设计风格。"

                                                                                                            35 二进制类 RPC：还是叫 NBA 吧，总说全称多费劲

                                                                                                            • 核心结论：数据中心内部调用量大、文本太占字节，于是回到二进制；但这次不回到"必须有协议文件"的老路——Hessian2 用自描述把 XML 的可读性与二进制的省空间合到一起。 Dubbo 三件套正是三大问题的答案：注册中心管服务发现、Hessian2 管协议约定、Netty 管传输。
                                                                                                            • 机制细节：
                                                                                                              • 分层：API 网关（Nginx/OpenResty + Lua，或 Spring Cloud 的 Zuul）管 API；API 实现在 Controller 层，对外多为 RESTful；资源状态不放业务逻辑层，放最底层持久化层（分布式数据库、ElasticSearch），前面必须有缓存层（Redis/memcached）拦截，"不能让所有的请求都进入数据库中军大营"；其上基础服务层提供用户/商品/订单/库存的原子化增删查改，把缓存与数据库对上屏蔽，扩容与分库分表都截止在这层；再上是组合层做复杂业务（下单要扣优惠券、扣库存）。三层相互调用都在数据中心内部，量大，用 RPC。
                                                                                                              • 二进制算术：数字 123 本来二进制 8 位就够，变成文本字符串 123，UTF-8 要 3 字节、UTF-16 要 6 字节——同样信息更占带宽、时延更高。
                                                                                                              • Dubbo 链路：客户端本地起 Proxy（即 Stub）→ 从注册中心取服务端列表 → 按路由与负载均衡规则选一个 → 编码序列化形成 Dubbo 头 + 序列化的方法和参数 → 网络客户端发送 → 服务端解码 → 分发线程 → 调服务端逻辑 → 返回。
                                                                                                              • 自描述：不需协议文件，不必靠"0 表示 add"这类事先约定；对方拿到二进制靠 Hessian2 规则本身就能解析出调哪个函数、参数是什么。
                                                                                                              • 编码：每个类型的起始数字独一无二以防歧义。add(2,3) 序列化为 H x02 x00（Hessian 2.0）→ C（RPC call）→ x03 add（方法名三字符）→ x92（两个参数）→ x92（2）→ x93（3）。2 编码成 0x92 而非 0x02，加 0x90 正为标明"这里一定是一个 int"。
                                                                                                              • 面向对象：先传类定义（x0b example.Car、x92 两字段、x05 color、x05 model），再传对象指向位置 0（O + x90 + x03 red + x08 corvette）；第二个同类对象只发 x60 表示同上。
                                                                                                              • 传输用 Netty（非阻塞、基于事件），服务端监听端口并注册四类事件：连接 connected(Channel)、可写 sent(Channel, Object)、可读 received(Channel, Object)、异常 caught(Channel, Throwable)；事件触发后可直接在函数内处理或分发线程池，异步读写一般另起线程池。
                                                                                                              • 序列化可选：Hessian2 是 Dubbo 默认，Dubbox 借鉴 Spark 的 Kryo 做高性能序列化。

                                                                                                            36 跨语言类 RPC：交流之前，双方先来个专业术语表

                                                                                                            • 核心结论：gRPC 用 Protocol Buffers 同时拿下"二进制（快）"与"跨语言（活）"，代价是仍要写 .proto 协议文件，也就是那份专业术语表。 传输用 HTTP/2 多路复用，治理交给 Envoy，最终把治理从应用里抽出来成为 Service Mesh。
                                                                                                            • 机制细节：
                                                                                                              • 前四讲取舍：二进制性能好、文本差些；二进制难跨语言、文本可跨语言；写协议文件严谨、不写灵活；都有服务发现，但有的能做治理、有的没有。微服务对 RPC 的五点要求：传输性能、跨语言、既严谨又灵活（加字段不用重新编译发布）、既有服务发现又有服务治理。
                                                                                                              • .proto：syntax = "proto3"、package、option java_package；message Order 四个字段各带唯一数字标识（date=1、classname=2、author=3、price=4）；message OrderResponse；service PurchaseOrder { rpc Purchase (Order) returns (OrderResponse) {} }。唯一数字标识使压缩时不必传字段名，只传数字。
                                                                                                              • 变长整数：int32 一般占 4 个 Byte；每 Byte 最高位是标志位，为 1 表示数字没完、后续 Byte 也属于它，为 0 表示到此结束，其余 7 位才是数值，故小于 128 一个字节，大于 128（如 130）用两个字节。
                                                                                                              • TLV：Tag = (field_num << 3) | wire_type。string author = 3 时 field_num=3、string 的 wire_type=2，(11000) | 10 = 11010 = 26，接着 Length，最后 Value "liuchao" 的 UTF-8 长度 7。
                                                                                                              • 兼容性：required 不能为空、必须有；optional 可选、不设则用默认值；repeated 可重复 0 到多次。字段数字标识一经发布不可改（"改变了就不认了"）；不要增删 required 字段，解析缺字段就报错；optional 与 repeated 可删可加。于是可先升服务端（客户端没带就置默认值），也可先升客户端（服务端忽略多余值）。
                                                                                                              • 传输：Java 栈下 gRPC 客户端与服务器经 Netty Channel 通信，每个请求封装成 HTTP/2 的 Stream。HTTP/2 把一个 TCP 连接切成多条流，各有 ID 与优先级，流是虚拟通道；又把信息分割为更小的消息与帧并二进制编码；多个请求分到不同流、拆帧乱序发送，再按帧首部流标识符重组，按优先级决定先处理哪条流。
                                                                                                              • 四种服务方法：单向 RPC（一发一收，像普通函数调用）；服务端流式（returns (stream HelloResponse)，客户端一直读到没有更多消息）；客户端流式（stream HelloRequest，写完一批等服务端读并应答）；双向流式（两边各自读写一个流，两个流操作相互独立、可任意顺序，每个流内消息顺序保持）。
                                                                                                              • 服务发现与治理：gRPC 本身没有服务发现机制，需借其他组件做容错与负载均衡。负载均衡本身简单（LVS、HAProxy、Nginx 都能做），关键是发现服务端并随其变化动态改配置。
                                                                                                              • Envoy：不只是负载均衡器，还是 C++ 写的高性能 Proxy 转发器，转发规则可极灵活。规则可静态（启动时加载，重载一般要重启，但支持热加载与热重启），更好是动态（放统一的服务发现 Discovery Service，定期去拉）。
                                                                                                              • Envoy 四要素：listener（监听端口接请求）、endpoint（目标 IP 与端口）、cluster（行为完全相同的多个 endpoint，cluster 到 endpoint 过程即负载均衡，可轮询）、route（多个 cluster 功能类似但版本不同，按规则选版本）。Envoy 与发现中心高频互推，控制面就用 gRPC，于是天然能在用户面支撑 gRPC。
                                                                                                              • 典型规则：route 按版本分流（如 99% 一个 cluster、1% 另一个）；cluster 内配负载均衡与健康检查，服务端新增或挂掉都能及时更新。节点变化上传注册中心、策略由注册中心下发，故更严格说注册中心应叫注册治理中心。
                                                                                                              • Service Mesh：让应用意识不到治理的存在，直接做 gRPC 调用，调用与治理全由 Envoy 代理，治理抽象到平台层——于是 Dubbo、Spring Cloud、Service Mesh 三种带治理的框架聚齐。
                                                                                                            • 判据·清单·步骤：①写 .proto（syntax、package、message 字段各带唯一数字、service 与 rpc 声明）；②各语言工具生成两端 Stub；③编码交给 Protobuf（变长整数 + TLV），字段标识发布后不可改；④兼容演进：新字段设 optional/repeated，不动 required；⑤传输用 HTTP/2，按需选四种流式之一；⑥前置 Envoy 配 listener/route/cluster/endpoint，规则从 Discovery Service 动态拉；⑦要彻底解耦就上 Service Mesh。跨语言+高性能+可治理选 gRPC；不能接受写协议文件的团队成本则退回 RESTful。
                                                                                                            • 数字·阈值：
                                                                                                              • 4 个 Byte——int32 常规存储长度。
                                                                                                              • 7 位——变长整数每 Byte 中真正表示数值的位数。
                                                                                                              • 128——一个字节能表示的上界；130——需两个字节的示例。
                                                                                                              • 26——author=3 的 Tag 值（(3<<3)|2）。
                                                                                                              • 7——"liuchao" 的 UTF-8 长度，即 Length 值。
                                                                                                              • 4 种服务方法——单向、服务端流、客户端流、双向流。
                                                                                                              • 99% / 1%——Envoy route 按版本分流的示例比例。
                                                                                                              • 4 个配置要素——listener、endpoint、cluster、route。
                                                                                                              • 实际 QPS、超时、重试退避参数——原文未明确。

                                                                                                              • 阶段 5 建连接：下单提供 RESTful 接口，需保密故走 HTTPS；HTTPS 基于 TCP，先建 TCP 连接，本例中连接是手机 App 与负载均衡器 SLB 之间的。中间虽经很多路由器与交换机，但 TCP 连接是端到端的，TCP 及更上层看不到中间转发过程。
                                                                                                              • 三次握手状态机：双方初始 CLOSED；服务端监听端口进入 LISTEN；客户端发 SYN 后进 SYN-SENT；服务端回 SYN 且 ACK 客户端的 SYN，进 SYN-RCVD；客户端收到后发 ACK，进 ESTABLISHED（它一发一收成功）；服务端收到该 ACK 后也进 ESTABLISHED。TCP 建好后，整个 HTTPS 交换过程中 TCP 层始终 ESTABLISHED。
                                                                                                              • TLS 握手：客户端发 Client Hello（明文传 TLS 版本、加密套件候选列表、压缩算法候选列表，另带一个随机数）→ 服务端回 Server Hello（选定版本、套件、算法，也带随机数）→ 服务端给证书并说 "Server Hello Done" → 客户端从信任的 CA 仓库取 CA 证书里的公钥解密网站证书，成功则可信（可能逐级往上追溯 CA 的 CA……直到授信 CA）→ 客户端生成 Pre-master 随机数，经 Client Key Exchange 用证书公钥加密发出，服务端用私钥解出 → 双方各有三个随机数（自己的、对端的、Pre-Master），据此产生相同对称密钥 → 客户端发 Change Cipher Spec 宣告改用协商密钥与算法，再发 Encrypted Handshake Message 供数据与握手验证 → 服务端同样发 Change Cipher Spec 与 Encrypted Handshake Message → 握手结束，此后用对称密钥加密传输。
                                                                                                              • 阶段 6 封装：用户层是 HTTP 报文：POST /purchaseOrder、Host: www.geektime.com、Content-Type: application/json; charset=utf-8、Content-Length: nnn，正文是 JSON 订单。报文三部分：请求行（URL、版本、方法；POST 需主动告诉服务端信息，信息放正文，常见格式 JSON）、首部（key: value，Content-Type 指明正文格式）、正文实体。
                                                                                                              • 交给传输层仍靠 Socket：浏览器已内置，移动 App 一般用 HTTP 客户端工具封装。HTTP 基于 TCP，用面向连接方式、以 Stream 二进制流传给对方；到 TCP 层会把二进制流变成一个个报文段。TCP 头含源端口与目标端口：目标是服务端监听端口，源端口在手机端往往随机分配，端口用于区分请求与返回、发给哪个应用。
                                                                                                              • IP 头加源地址（PGW 给手机分配的 IP）与目标地址（负载均衡器外网 IP）。IP 层用 CIDR 子网掩码判断目标是否与己同网段；本例不同网段，故发往默认网关，默认网关 IP 一般在 DHCP 分配 IP 时一并配置。但客户端不直接用网关 IP，而是发 ARP 取网关 MAC，再把网关 MAC 作目标 MAC、自己的 MAC 作源 MAC 填入 MAC 头发出。
                                                                                                            • 判据·清单·步骤：①静态资源分两类落位（varnish / 对象存储）并统一配 CDN；②DNS 侧配两级 CNAME（业务域名→cdn.com 权威 DNS→CDN 全局负载均衡器→边缘节点 IP）；③未命中逐级回源到源服务器；④敏感操作走 HTTPS：先三次握手，再 TLS 握手（Hello 换随机数与套件→校验证书→Pre-master→三随机数算对称密钥→Change Cipher Spec→Encrypted Handshake Message）；⑤组 HTTP 报文，Content-Type 必须与正文格式一致；⑥逐层封装 HTTP→TCP→IP（CIDR 判同网段）→ARP 取网关 MAC→MAC 头。
                                                                                                            • 数字·阈值：
                                                                                                              • 3 次握手——SYN / SYN+ACK / ACK。
                                                                                                              • 3 个随机数——自己的、对端的、Pre-Master。
                                                                                                              • 2 级 CNAME——业务域名→cdn.com，cdn.com→CDN 全局负载均衡器。
                                                                                                              • 3 大部分——HTTP 报文的请求行、首部、正文。
                                                                                                              • 4 层封装——HTTP、TCP、IP、MAC。
                                                                                                              • 1 个随机源端口——手机端往往随机分配。

                                                                                                            39 串讲（下）：过隧道、换 MAC、RPC 下单入库

                                                                                                            • 核心结论：第 7–10 阶段是包真正上路与落地：手机侧走两段隧道、出 PGW 做 NAT、跨 AS 靠 eBGP/iBGP 逐跳只换 MAC 不换 IP；进数据中心后公网 NAT 成私网、套 VXLAN 隧道、HAProxy 四层转发到 Controller，再由 Dubbo+Hessian2+Netty 一路 RPC 到库存与优惠券，最后 CAS 乐观锁落库。
                                                                                                            • 机制细节：
                                                                                                              • 阶段 7 隧道与转发：手机默认网关在 PGW；移动网络内手机→SGW→PGW 有隧道，上层包作为"乘客协议"被封装，外层是 SGW 与 PGW 在核心网机房的 IP，直到 PGW（隧道另一端）才解出内层包转发出去。手机发出时：源 MAC=UE 的 MAC、目标 MAC=PGW 隧道端点 MAC、源 IP=UE 的 IP、目标 IP=SLB 公网 IP。进 E-NodeB→SGW 隧道加外层（外层源/目标 MAC 为 E-NodeB/SGW 的 MAC，外层 IP 亦然）；SGW 切换到 SGW→PGW 隧道，外层换成 SGW/PGW，内层不变。
                                                                                                              • PGW 出口路由器部署 NAT，把手机 IP 转成公网 IP，返回时再 NAT 回来。PGW 之后相当于"欧洲十国游型"转发（源 IP 仍是 UE 的 IP）；到 NAT 网关则相当于"玄奘西游型"转发（源 IP 已是 UE 的公网 IP，目标 MAC 换 NAT 网关、再换 A2 路由器）。
                                                                                                              • AS 与 BGP：每个运营商网络是一个自治系统 AS，各有边界路由器。云平台可称 Multihomed AS（多连接连其他 AS，但大多拒绝帮别的 AS 传包）；运营商是 Transit AS（多连接且可帮别人传包，如主干网）。AS 之间、边界路由器之间用 eBGP 广播路由；边界路由器把学到的路由导入内部靠 iBGP，使内部路由器能找到到达外网目的地最好的边界路由器。
                                                                                                              • 逐跳：SLB 公网 IP 早被云平台边界路由器广播给全网，故下一跳选 A2 → 到 A2 查路由表下一跳 C1 → 到 C1 下一跳 C2 → 到 C2 下一跳边界路由器，每步只换目标 MAC 不换目标 IP，这就是"下一跳"。包经边界路由器→核心交换→汇聚交换→外网网关节点上的 SLB 公网 IP。手机到 SLB 是端到端连接，三次握手与 HTTPS 密钥交换的每个包都走同样复杂过程，且路径不一定一致。
                                                                                                              • 滑动窗口：TCP 要重传就要维护 Sequence Number，知道哪些到了、哪些没到、哪些要重传、速度控多少；一开始协商一个序号，此后每包有编号。接收方缓存分四部分：已接收已 ACK 已交应用层；已接收已 ACK 未交应用层；已接收尚未发 ACK；未接收尚有空闲缓存。发送方超时未收 ACK 就重发；只有 TCP 层 ACK 过的包才交应用层，且只交一份。
                                                                                                              • 同一 TCP 连接内不会因重传二次下单（收不到 ACK 才重发，窗口里只保存一份）；但连接会因信号不好等原因断掉，手机把动作重做一遍、新建连接、在 HTTP 层调两次 RESTful API，就可能下两单——故 RESTful API 需实现幂等。ACK 过的包交应用层后缓存空出，接收方可容纳总缓存（大三角）整体顺时针滑动，小三角是接收方告知发送方的窗口总大小，填满就不能再发。
                                                                                                              • 阶段 8 公网 NAT 成私网：包到 SLB 公网 IP 所在公网网口，匹配 MAC 与 IP 后收进来；虚拟网关节点外网网口的 NAT 规则把公网 IP 转成 VPC 私网 IP（即 HAProxy 所在虚拟机私网 IP）。虚拟网关节点有多个，物理网络把流量分发到不同节点；HAProxy 也是大集群，虚拟网关选一个分发，之后是 Controller 层。目标 IP 变私网后虚拟路由查规则从下方私网网口发出（源 MAC=网关 MAC、目标 MAC=HAProxy 虚拟机 MAC、源 IP=UE 公网 IP、目标 IP=HAProxy 私网 IP）。
                                                                                                              • 阶段 9 VXLAN + RPC：虚拟路由节点上的 OVS 把包封装进 VXLAN 隧道，VXLAN ID 就是创建 VPC 时分配的；外层是网关物理机与物理机 A 的 MAC/IP，内层是网关与 HAProxy 虚拟机的 MAC/IP。物理机 A 的 OVS 解隧道后交给 HAProxy 虚拟机，按其 TCP 端口交给 HAProxy 进程——HAProxy 就是这个 TCP 连接的服务端，客户端是手机，连接状态与滑动窗口都在 HAProxy 上维护。
                                                                                                              • HAProxy 是四层负载均衡，只解析到 TCP 层、不关心 HTTP，直接转发给后端多个 Controller 之一；它发出的包以自己为客户端（看不到手机端），源 IP=HAProxy 私网 IP、目标 IP=Controller 私网 IP；再被物理机 A 的 OVS 放进隧道到物理机 B，B 解隧道交给 Controller 虚拟机与进程。HAProxy 与 Controller 之间也维护一个 TCP 连接。
                                                                                                              • 阶段 10 RPC 下单：Controller 解开 HTTP 包发现是下单 POST；组合服务层有专门的下单服务，Controller 通过 RPC 调它，若用 Dubbo 则先读注册中心拿下单服务进程列表再选一个。Dubbo 默认 Hessian2，把下单调用序列化为二进制；Controller 与下单服务之间用 Netty（非阻塞、基于事件），其方式即 Socket 编程讲的 IO 多路复用（从派人盯着到有事通知）。Netty 工作在 Socket 层，包仍基于 TCP，下层仍封 IP 头与 MAC 头，跨物理机还要封 VXLAN，而这些底层封装 Netty 都不感知。
                                                                                                              • 下单服务收到请求先用 Hessian2 解压，再分发到线程；业务要调基础服务层的库存与优惠券服务，同样经 Dubbo、从注册中心拿列表选一个，统一 Hessian2 序列化 + Netty 传输 + 跨物理机走 VXLAN。
                                                                                                              • 幂等落库：库存若"谁调用谁减一"，应用层重试（非 TCP 重试）就会多扣。常用乐观锁 CAS，考虑三方面：当前库存数、预期原来的库存数与版本、新的库存数。操作前查出原库存数与版本，扣减时判断当前值与预期原值、版本是否匹配，匹配则更新为新值，否则不做任何操作。CAS 是基于状态而非基于动作的设计，符合 RESTful 原则、利于高并发：多线程同时 CAS 同一变量只有一个成功，失败线程不被挂起，而是被告知竞争失败、可再次尝试。下单更新到分布式数据库后，整个过程才算告一段落。
                                                                                                            • 判据·清单·步骤：①手机侧包进 UE→SGW→PGW 两段隧道，外层套核心网 MAC/IP，PGW 端点解出；②出 PGW 做 NAT（私网→公网），返回时反向 NAT；③跨 AS 用 eBGP 广播、iBGP 导入内部，逐跳只换 MAC；④靠 Sequence Number 与滑动窗口做重传与流控，应用层补幂等以覆盖"连接断了重做一遍"；⑤进数据中心网关 NAT 公网→私网，OVS 打 VXLAN 标签（ID=租户 VPC 的 ID）；⑥HAProxy 四层转发到 Controller；⑦Controller 解 HTTP→读注册中心→Dubbo/Hessian2/Netty 调下单服务→再调库存与优惠券；⑧扣库存用 CAS：查原值与版本→比对→匹配才写新值，否则不动、可重试。
                                                                                                            • 数字·阈值：
                                                                                                              • 2 段隧道——eNodeB→SGW、SGW→PGW；2 次 NAT——PGW 出口私转公、虚拟网关公转私。
                                                                                                              • 2 类 BGP——eBGP（AS 间）、iBGP（AS 内导入）。
                                                                                                              • 4 个窗口区段——已接收已 ACK 已交应用层 / 已 ACK 未交 / 已接收未发 ACK / 未接收有空闲缓存。
                                                                                                              • 3 方面——CAS 看的当前库存数、预期原值与版本、新库存数。
                                                                                                              • 2 次 RESTful 调用——TCP 断开重做时 HTTP 层可能调两次，故需幂等。
                                                                                                              • 1 份——同一 TCP 连接窗口内只保存一份，故不因重传二次下单。
                                                                                                              • 超时重传时长、窗口具体字节数、CAS 重试上限——原文未明确。
                                                                                                            • 案例·类比：隧道类比"乘客协议"坐在外层信封里；转发被形容为"欧洲十国游型"（源 IP 不变）与"玄奘西游型"（源 IP 已变）；"一座座城池一道道关"形容从手机到数据中心的层层转发；"大三角顺时针滑动、小三角是窗口"形容滑动窗口。映射：外层 MAC/IP=信封上的中转地址，内层=信封里的收件人；CAS=先看账本余额与版本，对得上才落笔。
                                                                                                            • 反例·坑：以为 TCP 重传会导致重复下单（原文明确不会）；只靠 TCP 可靠就省掉应用层幂等——连接一断重做一遍就下两单；库存用"谁调用谁减一"的减量接口；以为 Netty 能感知 VXLAN/IP/MAC 封装（原文明确"都不感知"）；把 HAProxy 当七层代理去解析 HTTP（它是四层）；CAS 冲突时把线程挂起。

                                                                                                            40 搭建一个网络实验环境：授人以鱼不如授人以渔

                                                                                                            • 核心结论：网络是实验性很强的学科，"一看觉得懂，一问就打鼓，一用就糊涂"，所以要把《TCP/IP 详解》的拓扑用 Docker + Open vSwitch 复现。一台 1 核 2G 的虚拟机就够；价值不在机器，而在能抓包、能改路由、能看见每一层封装。
                                                                                                            • 机制细节：
                                                                                                              • 推荐 Rechard Stevens 的《TCP/IP illustrated》，理论深入浅出且配大量上手实践与抓包；他是因为工作中有这么个环境、方便做实验才写出这本书。现代化替代：多台机器用 Docker 实现，多个网络用 Open vSwitch 实现，不必一台物理机。
                                                                                                              • 步骤 1 建 Ubuntu：笔记本上用 VirtualBox 创建，1 核 2G，从官网下载镜像安装。网络配两块网卡：Host-only，只有本机能登入、IP 只在本机有效，配置稳定，用于 SSH 操作，好处是笔记本搬来搬去、公司装一半回家接着装都没问题；NAT 网络，用于访问互联网，只要笔记本能上网虚拟机就能上网（装软件要联网）。Host-only 需要虚拟网桥，在"管理 > 主机网络管理"里配网桥 IP 并启用 DHCP 给新虚拟机配 IP。
                                                                                                              • Ubuntu 网卡配置在 /etc/network/interfaces：auto lo + iface lo inet loopback；NAT 网卡名 enp0s3、Host-only 网卡名 enp0s8，均配 inet dhcp，重启后 IP 就绪。
                                                                                                              • 步骤 2 装 Docker 与 OVS（root）：按官方文档先卸旧包（docker、docker-engine、docker.io），update，装 apt-transport-https、ca-certificates、curl、software-properties-common，下载并 apt-key add Docker 的 GPG，add-apt-repository 加源，再 update、用 apt-cache madison docker-ce 看版本、装指定版本；再装 openvswitch-common openvswitch-dbg openvswitch-switch python-openvswitch、bridge-utils、arping。
