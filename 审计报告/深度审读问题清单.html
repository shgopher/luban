                20.2 集中式互斥（代码：租约 + fencing 的最小实现） [代码正确性/伪代码当可运行（关键边界缺失）] ⚠️未核到

                • 原文：「last, _ := store.Get(ctx, "last_token:"+key)」
                • 问题：本节铁律是『存储侧拒绝旧 token』，但示例先读 last_token、再 token<last 判断、再 Put，校验与写入不是原子的：token=6 的新持有者与 token=5 的旧持有者可以先后读到同一个 last，双双通过检查，旧持有者的迟到写仍会落库，fencing 失效。另外 last, _ := 吞掉了 Get 错误——一旦读失败 last=0，所有 token 全部放行；token < last 还允许同一 token 重复写。这段代码被定位为『最小实现』，是本章唯一可抄的落点，照抄即失去保护，与 20.1/20.5 反复强调的『资源侧校验是最后一道闸』直接矛盾。
                • 建议：改为存储侧原子条件更新：UPDATE ... SET v=$data, token=$t WHERE token < $t（或 Redis Lua 里比较后写），影响行数为 0 时返回 ErrStaleOwner；校验失败必须硬失败而不是打日志；并把 token < last 改为 token <= last 拒绝同 token 重放；在代码块前一句写明『校验必须与写入同一条原子操作，先读后写等于没有 fencing』。

                33.7 [事实错误/数字不自洽] ✅

                • 原文：「cpu_thr = 1 / (c * SERVICE)」
                • 问题：CPU 型单实例吞吐被写成 1/(c×SERVICE)，随并发度 c 下降；实际 CPU 受限时每实例吞吐恒为 1/SERVICE，c 只把单请求墙钟拉长到 c×SERVICE。按真实公式，5000 QPS、SERVICE=0.2s 时实例数应为 ceil(5000×0.2)=1000 且与 c 无关，而非 c=10 时的 10000；10000 个实例意味着总并发 10 万，与本节场景 L=λW=5000×2s=10000 差 10 倍（34.2 恰好讲了 L=λW）。错误支撑了「CPU 型实例数不降反升、成本也翻倍」（一句话、反模式表「CPU 型函数的延迟翻 10 倍，成本也翻倍」、自检 Q2「实例数也要涨约 10 倍」、读法 2）：正确结论是成本不变、只有延迟×c，并额外占用并发配额。另外 IO 型曲线也未扣 CPU 上限（CPU 50ms/200ms，c=10 时单实例需 2.5 核），c>4 后实例数被低估。
                • 建议：改 cpu_thr = 1 / SERVICE（或 min(1/CPU, c/SERVICE) 统一两条曲线）并重跑输出；CPU 型实例数恒为 1000，结论改为「实例数不降、延迟 ×c、成本不变，但并发配额被白占、易撞平台限流」；同步修正一句话、反模式表、自检 Q1/Q2 与读法 2。

                16.6 [内容缺口（结论无实测依据）] ✅

                • 原文：「选第一个版本 ≥ token 的副本，否则读 leader」
                • 问题：token 模式的循环从 i=0 开始，而每轮 token= max(got,w)=w=vers[0]，因此 i=0 恒满足 vers[0]≥token，r 永远是 0（leader）：所谓 token 路由退化成『读 leader』，0 违例是平凡结果；代码也没有任何延迟/等待计时，正文『用延迟换保证，代价是等待或回源』没有实测支撑。
                • 建议：从 follower（i=1..n-1）开始找合格副本、找不到才回源 leader，并统计每轮的等待步数/回源比例，用数值证明『保证不是免费的』；或在输出里明确 token≈leader 读这一事实。

                16.7 一致性模型谱系图·六个常见误解 [一致性/同章矛盾] ⚠️未核到

                • 原文：「线性一致靠共识/租约，不靠时钟同步」

                16.7 决策表：从业务不变量出发（第一行） [技术结论错/与本章矛盾] ⚠️未核到

                17.4 [自检答案与正文矛盾] ✅

                • 原文：「必须等上海的第二个副本（同样约 30ms）」
                • 问题：Q1 场景是北京 2 + 上海 2、q=3：leader 在北京时只需再收 2 个 ack，最近的两个是『北京第二个副本』(0.5ms) 与『上海一个副本』(30ms)，取最大值 30ms；答案却说凑齐 3 票必须等上海的第二个副本，与本节 commitLatency 模型（并行发送、取第 q−1 近副本的 RTT 最大值）矛盾。结论 30ms 碰巧正确，但 quorum 组成讲错。
                • 建议：改为『leader + 北京第二个副本 + 上海一个副本即可满足 q=3，提交延迟由上海那次 30ms 决定』；并在答案里显式列出 q−1=2 个必需的 ack。

                17.4 PACELC·自检 Q1 [算术/自检答案与正文矛盾] ⚠️未核到

                • 原文：「本地 1 + 上海 1 = 2，还差 1，必须等上海的第二个副本」
                • 问题：同节 commitLatency 模型的注释是「leader 自己算 1 票」「还差几票 need = quorum - 1 = 2」。4 副本（北京 2 + 上海 2）、q=3 时，北京 leader + 北京另 1 副本 + 上海 1 副本已是 3 票，只需等 1 个上海副本（≈30ms），并不需要「上海的第二个副本」。结论数字 30ms 侥幸正确，但推理漏计 leader 票，读者按此推理去算 2+2/q=3 或 3+3/q=3 的部署会得出错误的容灾结论。
                • 建议：改为「leader(北京) + 北京另 1 副本 = 2 票，再等上海 1 个副本 → ≈30ms；北京机房整体故障后只剩上海 2 票 < 3，不可写」，并与第三节「两地三中心 q=2」表的判据统一口径。

                17.5 BASE 与柔性事务·六种机制表 [概念归类错] ⚠️未核到

                • 原文：「2PC | 协调者两阶段提交，同步阻塞，协调者故障会悬挂」
                • 问题：该表标题是「柔性事务：六种机制」，本节开头定义柔性事务为「不满足 ACID、靠业务手段收敛」的一类方案；而 2PC 是原子提交协议（原子性由协调者保证、失败走回滚、阻塞而非最终收敛），属刚性事务。把它并列为柔性事务，与本节 ACID vs BASE 表「原子性：数据库保证 / 业务保证」的划分自相矛盾，也会让团队在选型时把 2PC 当成 BASE 的兜底手段。
                • 建议：从「柔性事务：六种机制」移出，另起一行「对照：刚性事务 2PC → 24.2」，或在表内标注「2PC 属刚性事务，仅作对照，不计入柔性事务」。

                17.6 [事实错误（概念前后矛盾）] ✅

                • 原文：「去重计数 | ❌ | 不能：两边各数一遍再相加会重复计数」
                • 问题：表与 Q1 都断言『去重计数不是单调的、不能免协调』，但紧随其后的实测修复恰是『改成集合求并（幂等、可交换）→ 正确；这就是 CRDT 的并集』——并集合并本身就是免协调的单调运算；集合基数在 CALM 的单调性定义下（S⊆T ⇒ |S|≤|T|）也是单调的。真正非单调的是『把各分区的计数直接相加』这一错误合并，不是去重计数本身，结论与修复方案互相打脸。
                • 建议：把该行改为『各分区计数直接相加 ❌；改为并集合并（读取时取基数）✅，属单调、免协调，代价是搬运集合』；Q1 答案相应改为『直接相加的聚合方式非单调』，并给 HyperLogLog/OR-Set 的取舍。
