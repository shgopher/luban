## 0. 结论（全文精读后的修正）

1. **有借鉴价值，但“哲学”部分已经被借完了。** 37.9、44.19、44.14、41.3 四处成段吸收了本书的命题与结论；剩下没借的，是第 4–6 章的**机制链**、第 8 章的**实验过程**、第 11 章的**真实秒杀实现**，以及第 2–3 章里三个“讲清楚了但 luban 没讲”的技术点。
2. **这本书是博客合集，不是教材。** 逐页读下来，章节之间存在 7 处直接矛盾（第 7 节），产品事实停在 2023 年。**必须按“节”取用，不能按“章”照搬。**
3. **价值排序**（按可吸收且低风险）：第 4 章 Nginx > 第 5 章网关 > 第 6 章 L4/SDN > 第 8 章 B+ 树实验 > 第 11 章秒杀 > 第 12 章宏观 > 第 2–3 章的三个点 > 第 9–10 章（大部分已被 44.19 覆盖）。

## 3. 第一价值：Nginx 那一章的“因果链 + 一个事故”

### 3.1 书里讲了什么（p71–84）

| 环 | 书里的证据 | 数字/机制 |
|---|---|---|
| ① 需求侧 | 2000–2007 年美国头部站点 PV 从日均千万到亿级 | 4 年 14 倍 |
| ② 内核 | epoll 进内核 | select/poll 全量扫描；epoll 只取就绪 |
| ③ 产品 | Nginx 2004 开源，**为反向代理而设计** | 不是“又一个 Web 容器” |
| ④ 进程模型 | prefork/worker 用 select 扫“连接×进程”；event MPM 用 epoll 但被 mod_php 阻塞拖死 | 5000 连接时匹配烧掉一核 |
| ⑤ 实测 | 5000 线程 / 1000 QPS，三种配置 | Nginx+fpm 5 万成功、峰值 800；Nginx+Apache 5.2 万、峰值 1000；Apache prefork 错误率 **43%** |

结论不是“换 Nginx”，而是：**在前面加一个 Nginx，把 Apache 要维持的 5000 条 TCP 连接降到几十条**——这是“加一个软件反而省 CPU”的机制解释。

### 3.2 最值钱的是事故，不是 benchmark（p83）

```
配置：16 核 32G 云主机，PHP 单体，开团 3 分钟涌入约 4000 用户
现象：CPU 8%、内存 6%，但大量新用户连不上 TCP；进去之后又很丝滑
根因：ulimit -n 默认 1024；调到 65535 后仍只能到 5–6K 连接；
      Apache 把一整颗核的时间片花在“数据包 ↔ 进程”匹配上
处置：同机加 Nginx 反代，Apache 只需面对少量连接；Nginx 活跃连接仅 1K
```

价值在于**它推翻了“连不上 = CPU/内存不够”的直觉**。luban 8.9/47.1 有连接数算术，但没有“资源空闲却建连失败”的排查入口；11.11 的入口是“丢包”，不是“accept 不过来”。

### 3.3 可直接吸收的五条

| # | 书里的东西 | 进 luban 的位置 | 注意 |
|---|---|---|---|
| 1 | C10K 的历史约束：PID 16 位、`FD_SETSIZE=1024` | 11.11 “C10K→C1000K” | 书中“单进程 fd 上限 32767”不准确，别引 |
| 2 | prefork/worker/event 三模式 + 实测错误率 | 11.8 PPC/TPC 表 | 标条件：5000 线程、1000 QPS、PHP sleep 500ms |
| 3 | 低负载 Nginx 反而慢：14ms vs Apache 9ms | 47.1 选型代价 | “事件驱动用延迟换并发”的少见实测 |
| 4 | 秒杀事故的“低 CPU + 建连失败” | 8.9 症状表 / 47.1 案例 | 链到 11.11 accept 队列、8.3 TIME_WAIT |
| 5 | “Nginx 活跃 TCP 只有 Apache 的 1/5” | 8.9 | 条件：5000 客户端、1000 QPS |

### 3.4 不能照抄的两处

- **“epoll 复杂度 O(log n)”**（p74）：不准确。`epoll_wait` 是 O(就绪数)，`epoll_ctl` 才是 O(log n)；收益来自“不再全量扫描/拷贝”。11.4 已纠偏，必须用 luban 口径。
- **“Linux 下不存在真正的非阻塞 I/O”**（p76）：修辞过度。`O_NONBLOCK` 存在；作者想说的是“没有零等待”。改写为“非阻塞只是把等待从线程搬到事件循环”。

## 4. 第二价值：API 网关的“容量”与“控制面”

### 4.1 两段式容量算术（p86–p100）

```
单机基线：Kong 2 vCore → 2000 QPS @ 20% CPU
目标：50,000 QPS，CPU 水位 40%
第一段：核数 = (50000/2000) × (20%/40%) = 25 核
第二段：25 核意味着 10 万+ TCP 连接，而单机 Nginx/Kong 约 1 万 QPS 就到顶
结论：不是换更大的机器，是拆成 5 台 Kong（6 vCore）+ 前面加 L4
```

**可吸收的是“两段式否决”**：先算理论核数，再用连接数/单机上限否决“一台大机器”。47.2 有“单实例 1 万–5 万 QPS、N+1 配 6 个”的结论，没有这条推导，也没有“算完 25 核为什么还不能用”。

**不能照抄**：25 核是线性外推，忽略 NUMA、内存带宽、OpenResty 多 worker 锁竞争、插件成本；2 vCore@20% 也不可外推。进 luban 写成“方法 + 必须实测的三个系数”。

### 4.2 网关为什么能水平拆：数据面一致 + 控制面最终一致（p90）

书里的原话：多台机器装相同版本网关，连同一个 PostgreSQL，每 5 秒拉一次配置；DB 挂了就用内存里的旧配置继续跑。它解释了三件事：

| 现象 | 机制 | 工程后果 |
|---|---|---|
| 网关能水平扩 | 数据面无状态，行为由同一份配置决定 | 加机器不迁移连接状态 |
| 配置发布不是原子的 | 轮询周期内不同实例配置不同 | 灰度天然存在，但“全量生效”仍会一次改挂 |
| 控制面故障 ≠ 数据面故障 | DB 挂了用旧配置 | 代价是“配置冻结”，不是“全站 502” |

**2026 必须更新**：Kong 3.x 已有 hybrid（CP/DP）与 DB-less；书里“所有实例连同一 PG、5 秒轮询”是 Kong 1.x/2.x 的 DB 模式。但模式本身没过时——Envoy xDS 是同一问题的更强解：

| 方案 | 传播 | 一致性 | 错误配置 | 适合 |
|---|---|---|---|---|
| 轮询 DB（书里的 Kong） | 每 5s 拉全量 | 最终一致，窗口 5s | 坏配置也会被拉下去 | 小规模、无控制面 |
| xDS（Envoy/APISIX） | 长连接推送 + version/nonce | 最终一致，秒级 | **NACK：坏配置不下发** | 大规模、要灰度 |
| GitOps + 控制器 | 提交→渲染→下发 | 分钟级 | 可 review、可回滚 | K8s、强审计 |

### 4.3 网关五价值与一条“立场”

书里列了：解放后端架构、TLS 卸载、统一身份与安全、指标收集、压缩与转换。47.2 覆盖后四条，缺第一条的立场：

> “所有系统都应该放在应用网关的背后，包括开发环境。”

作为**立场**可收，作为**建议**不可收：全环境走网关会把调试链路、证书、鉴权一起变重，小团队会得到“每改一个接口都要动网关”的耦合。放进 47.2 的“什么时候该上网关”做对照。

两条小结论可收：低负载下网关和 LB 可以是同一个软件（<1Gbps）；网关拆分的前置条件是“多节点行为一致”，不是“装个集群”。

## 5. 第三价值：L4/SDN，luban 最大的空白

### 5.1 为什么 L4 便宜：一次包推演（p92–p100）

书里用“客户端 → 网关 → LVS VIP → RS”的五元组变化，把 NAT 讲成“改两个地址 + 两个端口 + 维护左右两张映射表”。教学价值：

- 让“四层只改包头”从口号变成可逐跳验证的过程；
- 解释了“300 块家用路由器能跑千兆 NAT，Kong 不行”——NAT 只需五元组表 + 改包，Kong 要建真 TCP、解析 HTTP、跑插件；
- 暴露一个 8.9 没写清的点：**书里 VIP 是私网地址，DR 前面仍有一层做“公网 IP→VIP”的 NAT 网关**。DR 只改目的 MAC，不是一级入口。自建也可以让 LVS 直接持公网 VIP（配合 ECMP/anycast），那是另一种拓扑。

### 5.2 从 20G 到 200G：luban 只有零散提及的技术层（p105–p116）

| 技术 | 书里的说法 | luban 现状 | 价值 |
|---|---|---|---|
| LVS/IPVS | 章文嵩 1998 年两周写出，2004 进内核 2.4；内核态避免切换 | 8.9 提了 LVS/IPVS，无原理与容量 | 中 |
| DPDK | 大页 + 轮询代替中断 + CPU 亲和 + NUMA；DPVS 是 LVS 的 5 倍 | 11.9/11.11/11.12 零散提及，无系统讲解 | **高** |
| NPU 卸载 | checksum、TSO、VxLAN 剥离/插入 | 无 | 中 |
| RSS/FDIR | 同一五元组固定同一 CPU，把 conntrack 分片，解除全局锁 | 11.6 有 NUMA/RSS 零散提及 | **高** |
| ECMP/OSPF | 多链路等价转发，不丢包多活 | 8.9 只有一句 ECMP | **高** |
| 全冗余拓扑 | DNS→路由→交换机→LVS 双网卡；任一台挂容量不变；200G/400G，18 万 BOM | 无 | **高** |
| Keepalived/VRRP | 三节点同城、<1 秒切换；机房进水损两台仍存活 | 8.9 一行、35.9 讲 STONITH 不讲 VRRP 实操 | 中 |

这一块是全书**最不像科普**的部分：有包、有核、有锁、有 BOM、有故障。**如果只吸收一个新技术节，就吸收这一块。**

### 5.3 最值得抄的“反直觉”

> 硬件负载均衡器卖 100 万，4 核 8 线程，40G L4 / 18G L7；用 18 万的通用 x86 + 开源软件，做出 200G 且全冗余。

重要的不是“便宜”，而是成本结构：路由 1 万×2 + 交换机 2 万×2 + LVS 3 万×4 = 18 万；以及“软件带来的可编程性才是核心价值”。可进 39 成本或 8.13 选型段。

### 5.4 NAT/DR 的条件表（书与 8.9 各说一半）

| 场景 | 合适模式 | 原因 |
|---|---|---|
| 同机房、同二层、回包量大 | DR | 回包不过 LB，带宽只花在入向 |
| 跨机房、公网入口、多活 | NAT/FullNAT | 不依赖同二层，可跨公网 |
| 云厂商 LB | 透明/NAT 取决于产品 | “保留客户端 IP”选错会让风控失效 |

## 6. 全文精读才发现的：此前抽查漏掉的八个可用点

### 6.1 第 2 章：三层兼容性 × 五类虚拟化（p33–36）

书里把“软件可移植性”拆成三层：**ISA 兼容 / ABI 兼容 / 环境兼容**；把虚拟化/仿真拆成五类：**硬件虚拟化、指令集仿真、运行库虚拟化、虚拟机语言、文本解释型**；容器坐在“运行库虚拟化”这一层——“容器内看自己是裸机进程，系统库调用被运行时劫持”（p33–35）。

luban 6.1 讲了 VM 与容器的边界（namespace/cgroup、共用内核），但没有这张“兼容性 × 虚拟化”的分类表。**建议在 6.1 补一张 3×5 表，只补表，不补历史。**

同章还有两条可收：

- 容器四步演进：chroot 1979 → pivot_root 2000（K2.3.41）→ namespaces 2002（K2.4.19，到 K5.6 共 8 类）→ cgroups 2008（K2.6.24，10 个子系统）→ LXC → Docker 2013（p36–40）。可作 6.3 的“一句话时间线”，不要展开。
- **K8s 在能力上超越虚拟机，靠的是软件定义网络，不是镜像可迁移**（p40–42）：VPC（AWS 2009/阿里云 2015）→ flannel → VxLAN → calico BGP + Istio sidecar。这是对“K8s 只是更轻的虚拟机”的纠偏，可进 7.8 开头。

**不能收**：`127 个镜像版本`（p40，实为 overlay2 lowerdir 上限）、`flannel IP-in-IP 让 Pod 进同一个二层网络`（p42，IP-in-IP 是三层）、`CMD ["sh","-c","php-fpm -F && nginx && mysqld"]`（p46，`php-fpm -F` 前台阻塞，后两个不会执行）、`容器内不能监听 80`（p50，容器 root 可以，受限的是宿主端口映射）。

### 6.2 第 3 章：Goroutine 的“内存同步灾难”与外援（p60–61）

书里的三级递进很清楚：全阻塞（PHP，I/O 期间占 TCP + 线程）→ 单线程非阻塞（Node，libuv + epoll，只吃满单核）→ 协程（Go，M:N、2KB 栈）。真正新的是**协程的弱点**：

> 一旦在单个 Go 进程内的海量协程之间做实时数据同步，CPU 吃完了并发量还是低；“线程 × 协程”的内存同步是灾难（`sync.Map` 尤甚）。这时唯一的“单点”就是这段进程内存，解法是找外援：Redis 或自写的单线程服务，用排队把同步变成网络 I/O。

luban 15.6 有 `sync.Map` 的微观实测（9.4ns vs 47.9ns），但没有这条**架构结论**：协程不是银弹，进程内共享状态是单点，应该外移。建议在 15.6 末尾或 37.9 的“拆不动时”补 3–4 行。

另外两条可作旁证：Node 的 `worker_threads` 是给 CPU 密集用的，I/O 密集用了反而更慢（p61–62）；PHP 的“每请求生命周期”反而带来“无内存泄漏、半微服务”的优点（p36），但**“每个 HTTP 请求开一个 PHP 进程”只适用于 PHP-CGI，不适用于 PHP-FPM**。

### 6.3 第 7 章：数据库的单点单在磁盘上（p120–p127）

这是全书最好的第一性开头之一：

> API 可以并发执行，而数据库必须逐个处理请求。数据库就是 Web 服务的“根”，是确保最终结果符合预期的那个“队列”。而数据库的单点，最终单在了磁盘上——它是计算机里唯一断电不丢数据的部件，redo log 也只是磁盘文件。

luban 44 章直接从引擎/索引讲起，缺这句“为什么必须有数据库”。建议放在 44.0 或 44.1 开头，一句话即可，不要展开成“磁盘决定论”。

同章可收的数字（p124）：十年前内存 100GB/s、60ns，SATA SSD 500MB/s、200μs（差 1/200 与 3000 倍）；今天内存 150GB/s、100ns，PCIe 5.0 NVMe 12.8GB/s、9μs（差 1/12 与 90 倍）。这组数字适合放 10.3 云盘性能模型或 44.1 的开头。

**不能收**：`400G 网卡超出八路内存带宽`（p126，400Gbps=50GB/s，8 通道 DDR4/DDR5 远高于此）、`65B 模型需 192GB 显存`（p126，训练/推理口径不同且已过时）、`NoSQL 连 ID 自增都要全表扫描`（p120，过度概括）。

### 6.4 第 8 章：B+ 树实验的完整读数（p134–145）

书里的实验条件：MySQL 8.0.28 / CentOS Stream 9 / ext4，`char(255)×4` 让单行恰好 1024B。

| 行数 | 结果 | 页/文件 |
|---|---|---|
| 1 | 1 层 | 112KB |
| 15 | 首次分裂为 2 层，页 5 存 7 行、页 6 存 8 行 | 页可用 14–15KB |
| 16500 | 仍 2 层 | 根页 1180 个指针 |
| 17000 | 转 3 层，只改 3 个页 | 27MB |
| 21,427,000 | 转 4 层，只改 3 个页 | 24GB |

由 `(14×1024/12)×14=16725` 与实测吻合，反推页指针 12B（int）/16B（bigint），页号 8B。生产“订单商品表”单行 0.9KB，三层极限 `1194²×15≈2138 万`；单行 5KB 时降到 285 万。结论：**2000 万是层数边界，不是性能悬崖；但行宽、varchar、删改变动、碎片、单文件过大仍会让大表变慢，所以“能不分就不分”是有条件的。**

luban 44.14 已有这些结论；缺的是**实验证据**与 Buffer Pool 的具体参数。44.3 可补：默认 128MB；冷热均衡 75%，冷数据多、短期扫全表则 50% 防 OOM；young/old = 5/8 : 3/8；预读只进 old 头；从 old 升 young 要“待得够久”，用 4B 时间戳而非访问次数（p142–145）。

### 6.5 第 9–10 章：44.19 已覆盖大半，只剩三样

- **PolarDB 的“共享 ibd + RDMA + ParallelRaft”**（p158–159）：共享的是 ibd 文件而非 redo log；跳过 TCP/IP 与内核调度，自研绑核状态机；ParallelRaft 允许部分乱序提交，把 Aurora 的 6 次网络 I/O 变成 1 次；代价是硬件贵、扩展有上限，“云时代的 RAC”。
- **OceanBase 的“取消每秒刷 redo、每天合并”**（p168–170）：白天只写 MemTable + redo，增量与基线每日合并，等于把内存当数据库；9 层缓存（Bloom、MemTable、Row、Block Index、Block、Fuse Row、Partition Location、Schema、Clog）；查询用 OBServer 协调 + M*N channel 并行。
- **两处定性错误**：`TiDB 放弃事务隔离`（p167，TiDB 用 Percolator 提供快照隔离/可重复读，书自己在 p166 也说“事务控制比较弱”）；`OceanBase 只能最终一致`（p170–171，单分区 Multi-Paxos 多数派提交是强一致，弱读是可配选项）。

**建议**：44.19 加一个“国内两强”小表（PolarDB/OceanBase 各 5 行），不重讲四代；两处错误不要引用。

### 6.6 第 11 章：缓存四策略 + 住范儿“令牌 + 两步事务”（p176–183）

缓存部分是全书最实操的：

| 策略 | 书里怎么做 | luban 现状 |
|---|---|---|
| 不过期悖论 | 不过期也要淘汰，淘汰后上游就查不到，再直连 DB 又回到原始架构 → 必须与自动过期配合 | 41.3 有逻辑过期，无“悖论”表述 |
| 双 key | 主 key 有过期、备 key 不过期，主失效读备，后台刷新；用一倍内存换不丢 | 无 |
| 队列解耦刷新 | 读时判断将失效 → 发消息 → 后台顺序更新；同一 key 的重复消息只执行一次 | 无 |
| 缓存宕机 | 作者主张直接返回错误，不做“假装高可用”的集群 | 与主流“缓存高可用”相反，只能作**立场**引用 |

秒杀实现（p181–183）：下单令牌（MySQL/Redis）→ 任务入队 → 3 个左右队列处理器 → **两个 MySQL 事务**（先扣 SKU 库存，再生成订单）→ 失败用新队列任务补库存 → 客户端轮询令牌。两个事务是为了“让最可能冲突的扣库存事务尽量短”。这套“令牌 + 两步事务 + 轮询”在 luban 67.6 里没有；67.6 有防刷 token，但不是异步下单令牌。

**注意**：3 个处理器能压住千级并发是作者经验，无压测条件；“缓存宕机直接报错”是取舍，不是最佳实践。

另外，ES 的三层缓存（页缓存、分片级请求缓存、查询缓存，p179–181）可以补 45.3 的读路径：分片请求缓存适合“旧数据查询条件不变、只追加新数据”的日志/Kibana 场景，查询缓存则吃“同一查询重复率高”的局部性。

### 6.7 第 12 章：三个可直接用的判据（p188–196）

- **微服务写集判据**（p188）：一次请求只应写一个微服务；如果头部 API 要写两个服务，说明边界画错了。37.9 已经有这条判据（“一个头部 API 要写两个服务 → 边界画错了”），无需再补；第 12 章的增量只剩预生成订单与 HA 悖论。
- **预生成订单**（p189）：大促前先生成订单，下单时只写用户信息，绕开“检查库存”这个单点。这是“用过去的时间换现在的时间”的最具体例子，可进 67.6 削峰段。
- **跨区四耦合**（p192）：用户自增 ID、库存检查、商家订单聚合、离线分析；逐点给解法（号段/奇偶、预分配库存、两边各拉一次、离线本已异步）。82.2 缺这套“先穷举、再逐点拆除”的模板。

### 6.8 附录三个系列：只取三样

- **搜索引擎工程**（p206–213）：MD5 前两位分 256 表；pages 仓库表 + status 影子表；Redis Hash 存 URL 存在性（利用局部性，定期清空）；每 20 秒从 status 表预取一批 URL 进 Redis 的 LPush/RPop；按 host 计数限速；4 秒超时、3 次失败拉黑、HTML 解析失败放弃、channel 必须回信号；MySQL 连接池 100；每批 2000 词、写入峰值 1.5GB/s；倒排索引格式与 BM25（log10、avgDocLength 13214）。**这套“非请求-响应型负载的背压与去重”在 luban 45/84 没有对应物**，可作 45.3 的一个“采集侧”小节或 84.4 的旁例。
- **性能之殇**（p225–241）：冯·诺依曼瓶颈（0.22ns 指令 vs 68.1ns 内存 = 300 周期）；事件驱动是 CPU 异常控制流的用户态暴露；“局部性 + 乐观”统一解释缓存/虚拟内存/分支预测/LRU/乐观锁；“分布式 = 以网络为总线的新计算机结构”（每台机器=运算器+存储器，master=控制器+I/O）。**取框架，不取硬件数字**（多数是 2018 年口径）。
- **网络知识**（p242–261）：铜线→以太网→IP→TCP→HTTP→TLS 的贯通叙事；“HTTPS 两层功能 = 加密 / 可信”；MITM 三类（HTTP→HTTPS 降级、合法证书、终端自馁）与 pinning。**取结构，不取物理层结论**（1000BASE-T 的“4 根正向 + 4 根反向”是错的：千兆是 4 对双向 + 回波消除）。
