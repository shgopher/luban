                3. 第一价值：Nginx 那一章的“因果链 + 一个事故”

                3.1 书里讲了什么（p71–84）

                环 书里的证据 数字/机制
                ① 需求侧 2000–2007 年美国头部站点 PV 从日均千万到亿级 4 年 14 倍
                ② 内核 epoll 进内核 select/poll 全量扫描；epoll 只取就绪
                ③ 产品 Nginx 2004 开源，为反向代理而设计 不是“又一个 Web 容器”
                ④ 进程模型 prefork/worker 用 select 扫“连接×进程”；event MPM 用 epoll 但被 mod_php 阻塞拖死 5000 连接时匹配烧掉一核
                ⑤ 实测 5000 线程 / 1000 QPS，三种配置 Nginx+fpm 5 万成功、峰值 800；Nginx+Apache 5.2 万、峰值 1000；Apache prefork 错误率 43%

                结论不是“换 Nginx”，而是：在前面加一个 Nginx，把 Apache 要维持的 5000 条 TCP 连接降到几十条——这是“加一个软件反而省 CPU”的机制解释。

                3.2 最值钱的是事故，不是 benchmark（p83）

                配置：16 核 32G 云主机，PHP 单体，开团 3 分钟涌入约 4000 用户
现象：CPU 8%、内存 6%，但大量新用户连不上 TCP；进去之后又很丝滑
根因：ulimit -n 默认 1024；调到 65535 后仍只能到 5–6K 连接；
      Apache 把一整颗核的时间片花在“数据包 ↔ 进程”匹配上
处置：同机加 Nginx 反代，Apache 只需面对少量连接；Nginx 活跃连接仅 1K

                价值在于它推翻了“连不上 = CPU/内存不够”的直觉。luban 8.9/47.1 有连接数算术，但没有“资源空闲却建连失败”的排查入口；11.11 的入口是“丢包”，不是“accept 不过来”。

                3.3 可直接吸收的五条

                # 书里的东西 进 luban 的位置 注意
                1 C10K 的历史约束：PID 16 位、FD_SETSIZE=1024 11.11 “C10K→C1000K” 书中“单进程 fd 上限 32767”不准确，别引
                2 prefork/worker/event 三模式 + 实测错误率 11.8 PPC/TPC 表 标条件：5000 线程、1000 QPS、PHP sleep 500ms
                3 低负载 Nginx 反而慢：14ms vs Apache 9ms 47.1 选型代价 “事件驱动用延迟换并发”的少见实测
                4 秒杀事故的“低 CPU + 建连失败” 8.9 症状表 / 47.1 案例 链到 11.11 accept 队列、8.3 TIME_WAIT

                3.4 不能照抄的两处

                • “epoll 复杂度 O(log n)”（p74）：不准确。epoll_wait 是 O(就绪数)，epoll_ctl 才是 O(log n)；收益来自“不再全量扫描/拷贝”。11.4 已纠偏，必须用 luban 口径。
                • “Linux 下不存在真正的非阻塞 I/O”（p76）：修辞过度。O_NONBLOCK 存在；作者想说的是“没有零等待”。改写为“非阻塞只是把等待从线程搬到事件循环”。

                4. 第二价值：API 网关的“容量”与“控制面”

                4.1 两段式容量算术（p86–p100）

                单机基线：Kong 2 vCore → 2000 QPS @ 20% CPU
目标：50,000 QPS，CPU 水位 40%
第一段：核数 = (50000/2000) × (20%/40%) = 25 核
第二段：25 核意味着 10 万+ TCP 连接，而单机 Nginx/Kong 约 1 万 QPS 就到顶
结论：不是换更大的机器，是拆成 5 台 Kong（6 vCore）+ 前面加 L4

                可吸收的是“两段式否决”：先算理论核数，再用连接数/单机上限否决“一台大机器”。47.2 有“单实例 1 万–5 万 QPS、N+1 配 6 个”的结论，没有这条推导，也没有“算完 25 核为什么还不能用”。

                不能照抄：25 核是线性外推，忽略 NUMA、内存带宽、OpenResty 多 worker 锁竞争、插件成本；2 vCore@20% 也不可外推。进 luban 写成“方法 + 必须实测的三个系数”。

                4.2 网关为什么能水平拆：数据面一致 + 控制面最终一致（p90）

                书里的原话：多台机器装相同版本网关，连同一个 PostgreSQL，每 5 秒拉一次配置；DB 挂了就用内存里的旧配置继续跑。它解释了三件事：

                现象 机制 工程后果
                网关能水平扩 数据面无状态，行为由同一份配置决定 加机器不迁移连接状态
                配置发布不是原子的 轮询周期内不同实例配置不同 灰度天然存在，但“全量生效”仍会一次改挂
                控制面故障 ≠ 数据面故障 DB 挂了用旧配置 代价是“配置冻结”，不是“全站 502”

                2026 必须更新：Kong 3.x 已有 hybrid（CP/DP）与 DB-less；书里“所有实例连同一 PG、5 秒轮询”是 Kong 1.x/2.x 的 DB 模式。但模式本身没过时——Envoy xDS 是同一问题的更强解：

                方案 传播 一致性 错误配置 适合
                轮询 DB（书里的 Kong） 每 5s 拉全量 最终一致，窗口 5s 坏配置也会被拉下去 小规模、无控制面
                xDS（Envoy/APISIX） 长连接推送 + version/nonce 最终一致，秒级 NACK：坏配置不下发 大规模、要灰度
                GitOps + 控制器 提交→渲染→下发 分钟级 可 review、可回滚 K8s、强审计

                4.3 网关五价值与一条“立场”

                书里列了：解放后端架构、TLS 卸载、统一身份与安全、指标收集、压缩与转换。47.2 覆盖后四条，缺第一条的立场：

                “所有系统都应该放在应用网关的背后，包括开发环境。”

                作为立场可收，作为建议不可收：全环境走网关会把调试链路、证书、鉴权一起变重，小团队会得到“每改一个接口都要动网关”的耦合。放进 47.2 的“什么时候该上网关”做对照。

                两条小结论可收：低负载下网关和 LB 可以是同一个软件（<1Gbps）；网关拆分的前置条件是“多节点行为一致”，不是“装个集群”。

                5. 第三价值：L4/SDN，luban 最大的空白

                5.1 为什么 L4 便宜：一次包推演（p92–p100）

                书里用“客户端 → 网关 → LVS VIP → RS”的五元组变化，把 NAT 讲成“改两个地址 + 两个端口 + 维护左右两张映射表”。教学价值：

                • 让“四层只改包头”从口号变成可逐跳验证的过程；
                • 解释了“300 块家用路由器能跑千兆 NAT，Kong 不行”——NAT 只需五元组表 + 改包，Kong 要建真 TCP、解析 HTTP、跑插件；
                • 暴露一个 8.9 没写清的点：书里 VIP 是私网地址，DR 前面仍有一层做“公网 IP→VIP”的 NAT 网关。DR 只改目的 MAC，不是一级入口。自建也可以让 LVS 直接持公网 VIP（配合 ECMP/anycast），那是另一种拓扑。

                5.2 从 20G 到 200G：luban 只有零散提及的技术层（p105–p116）

                技术 书里的说法 luban 现状 价值
                LVS/IPVS 章文嵩 1998 年两周写出，2004 进内核 2.4；内核态避免切换 8.9 提了 LVS/IPVS，无原理与容量 中

                ECMP/OSPF 多链路等价转发，不丢包多活 8.9 只有一句 ECMP 高

                6.1 第 2 章：三层兼容性 × 五类虚拟化（p33–36）

                书里把“软件可移植性”拆成三层：ISA 兼容 / ABI 兼容 / 环境兼容；把虚拟化/仿真拆成五类：硬件虚拟化、指令集仿真、运行库虚拟化、虚拟机语言、文本解释型；容器坐在“运行库虚拟化”这一层——“容器内看自己是裸机进程，系统库调用被运行时劫持”（p33–35）。

                luban 6.1 讲了 VM 与容器的边界（namespace/cgroup、共用内核），但没有这张“兼容性 × 虚拟化”的分类表。建议在 6.1 补一张 3×5 表，只补表，不补历史。

                • 容器四步演进：chroot 1979 → pivot_root 2000（K2.3.41）→ namespaces 2002（K2.4.19，到 K5.6 共 8 类）→ cgroups 2008（K2.6.24，10 个子系统）→ LXC → Docker 2013（p36–40）。可作 6.3 的“一句话时间线”，不要展开。

                6.2 第 3 章：Goroutine 的“内存同步灾难”与外援（p60–61）

                书里的三级递进很清楚：全阻塞（PHP，I/O 期间占 TCP + 线程）→ 单线程非阻塞（Node，libuv + epoll，只吃满单核）→ 协程（Go，M:N、2KB 栈）。真正新的是协程的弱点：

                一旦在单个 Go 进程内的海量协程之间做实时数据同步，CPU 吃完了并发量还是低；“线程 × 协程”的内存同步是灾难（sync.Map 尤甚）。这时唯一的“单点”就是这段进程内存，解法是找外援：Redis 或自写的单线程服务，用排队把同步变成网络 I/O。

                luban 15.6 有 sync.Map 的微观实测（9.4ns vs 47.9ns），但没有这条架构结论：协程不是银弹，进程内共享状态是单点，应该外移。建议在 15.6 末尾或 37.9 的“拆不动时”补 3–4 行。

                另外两条可作旁证：Node 的 worker_threads 是给 CPU 密集用的，I/O 密集用了反而更慢（p61–62）；PHP 的“每请求生命周期”反而带来“无内存泄漏、半微服务”的优点（p36），但**“每个 HTTP 请求开一个 PHP 进程”只适用于 PHP-CGI，不适用于 PHP-FPM**。

                6.3 第 7 章：数据库的单点单在磁盘上（p120–p127）

                这是全书最好的第一性开头之一：

                API 可以并发执行，而数据库必须逐个处理请求。数据库就是 Web 服务的“根”，是确保最终结果符合预期的那个“队列”。而数据库的单点，最终单在了磁盘上——它是计算机里唯一断电不丢数据的部件，redo log 也只是磁盘文件。

                luban 44 章直接从引擎/索引讲起，缺这句“为什么必须有数据库”。建议放在 44.0 或 44.1 开头，一句话即可，不要展开成“磁盘决定论”。

                同章可收的数字（p124）：十年前内存 100GB/s、60ns，SATA SSD 500MB/s、200μs（差 1/200 与 3000 倍）；今天内存 150GB/s、100ns，PCIe 5.0 NVMe 12.8GB/s、9μs（差 1/12 与 90 倍）。这组数字适合放 10.3 云盘性能模型或 44.1 的开头。

                不能收：400G 网卡超出八路内存带宽（p126，400Gbps=50GB/s，8 通道 DDR4/DDR5 远高于此）、65B 模型需 192GB 显存（p126，训练/推理口径不同且已过时）、NoSQL 连 ID 自增都要全表扫描（p120，过度概括）。

                行数 结果 页/文件

                缓存宕机 作者主张直接返回错误，不做“假装高可用”的集群 与主流“缓存高可用”相反，只能作立场引用
