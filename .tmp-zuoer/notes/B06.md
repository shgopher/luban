## 38｜编程范式游记（9）- 编程的本质
> 源文件 `.tmp-zuoer/txt/38丨编程范式游记（9）-编程的本质.txt`，8136 字

### 一句话结论
程序 = Logic + Control + Data Structure；Logic 决定程序的复杂度下限，Control 只影响效率且可以标准化（靠泛型标准化 Data、靠接口/协议适配 Logic），因此**把 Logic 与 Control 缠在一起写，才是绝大多数代码混乱难维护的根本原因**。

### 知识点全清单（A1 零丢失）
1. 承上：前八篇讲过 C 泛型、C++ 泛型、函数式 Map/Reduce/Filter、Pipeline/Decorator、OOP 桥接/策略/代理、IoC、JS 原型、Go 委托——这些范式背后有共性。
2. 论文一：1976 年瑞士计算机科学家 Niklaus Emil Wirth（Algol W、Modula、Oberon、Pascal 的设计师）著《Algorithms + Data Structures = Programs》（1985 年版），即「算法 + 数据结构 = 程序」；该书主要写算法与数据结构的关系，对计算机科学教育影响深远。
3. 论文二：1979 年英国逻辑学家与计算机科学家 Robert Kowalski 发表论文 **Algorithm = Logic + Control**，并主要开发「逻辑编程」相关工作；他 20 世纪 70 年代末到整个 80 年代致力于数据库研究，在用计算机证明数学定理等应用上颇有建树，在逻辑、控制、算法方面提出革命性理论，影响了数据库、编程语言直至今日的人工智能。
4. Kowalski 原文四层意思（作者给了中文翻译）：① 算法由 logic component（规定解题所用的知识）与 control component（决定知识如何被使用的求解策略）组成；② **logic 决定算法的意义，control 只影响效率**；③ 常常可以只改进 control 而不改 logic 就提高效率；④ **若在程序文本中把 logic 与 control 明确分开，程序会更常正确、更容易改进与修改**——作者点明「最后一句话是重点」。
5. 两个表达式的差异：Wirth 那条倾向「数据结构 + 算法」的拆分，认为数据结构设计好算法就简单、好算法应能用于不同数据结构；Kowalski 那条认为**数据结构不复杂，复杂的是算法（业务逻辑）**，算法由两种逻辑组成——真正的业务逻辑 + 控制逻辑；程序里也有两种代码——业务逻辑代码 + 控制代码，后者根本不是业务逻辑。
6. 三个等式的关系：`Program = Logic + Control + Data Structure`，`Programs = Algorithms + Data Structures`，`Algorithm = Logic + Control`。
7. 阶乘例子：`X(n)! = X(n)*X(n-1)*…*3*2*1`；logic 部分只定义两条——(1) 1 是 0 的阶乘；(2) 若 v 是 x 的阶乘且 u=v*(x+1)，则 u 是 x+1 的阶乘。用这份定义既可自上而下递归（recursive），也可自下而上遍历（iteration）；control 描述「如何使用 logic」，同一 logic 配不同 control 得到的算法本质等价（解决同样问题、得同样结果）。
8. 效率优化的正确姿势：只改 control 不改 logic——「自上而下」改「自下而上」可能更快；「顺序执行」改「并行执行」也会更快。
9. 三个例子的映射：函数式 Map/Reduce/Filter 是 Control，传进去的 Lambda 是 Logic；Go 委托模式的 Undo 示例中「要 Undo」是 Logic、「Undo 的流程」是 Control；OOP 依赖接口而非实现时，接口是对逻辑的抽象，真正的逻辑在具现类里，多态/依赖注入是 Control。
10. **Control 可以标准化**：遍历数据、查找数据、多线程、并发、异步等都能标准化。
11. 标准化 Control 的两条腿：① Control 要处理数据 → 需标准化 Data Structure，用**泛型编程**解决；② Control 要适配用户业务逻辑 → 用**标准化接口/协议**解决，这样一套 Control 模式可适配任何 Logic。
12. 结论句（原文重复三遍）：**有效地分离 Logic、Control 和 Data 是写出好程序的关键所在！**
13. 复杂度模型：Logic 是程序复杂度的**下限**；为了控制程序还要写很多控制代码，于是 **Logic + Control 相互交织 = 最终的程序复杂度**。
14. 案例一（反面）：LeetCode 通配符匹配，8 条用例 `isMatch("aa","a")→false`、`("aa","aa")→true`、`("aaa","aa")→false`、`("aa","*")→true`、`("aa","a*")→true`、`("ab","?*")→true`、`("aab","c*a*b")→false`；作者给的 23 行 C 实现用 `last_s/last_p` 双指针回溯，为性能而写，判断分支（`*p=='*'`、`'?'`、`last_s!=NULL`）全是控制逻辑；作者自评「有多乱」「两三天后我自己也不懂」。
15. 案例一（重构方向）：① 用通用状态机（NFA 非确定有限自动机 / DFA 确定性有限自动机）维护匹配开始与结束状态——属 Control；② 做得好可抽象出类似文法分析的东西——也是 Control；③ 把匹配 `*` 与 `?` 的算法做成不同匹配策略——属 Logic。另推荐论文《Regular Expression Matching Can Be Simple And Fast》。
16. 案例二（反面）：`check_form_x()` 表单校验，name 长度 ≤3 报 status 1、password ≤8 报 status 2、两次密码不一致报 status 3、email 格式错报 status 4、全过返回 status 0；每个字段一段 if + 一个 return 对象，控制与业务混写。
17. 案例二（重构方向）：用 `meta_create_user` 这种 DSL 描述字段（id/type/min_length，name≥3、password≥8、repeat-password≥8、email），再调 `check_form(meta_create_user)`；**DSL 描述是 Logic，check_form 是 Control**。
18. 代码复杂度的三条小结：业务逻辑的复杂度决定了代码的复杂度；控制逻辑的复杂度 + 业务逻辑的复杂度 ⇒ 程序代码混乱不堪；绝大多数程序复杂混乱的根本原因是业务逻辑与控制逻辑的耦合。
19. 分离 Control 与 Logic 的三类技术：① **State Machine**（状态定义、状态变迁条件、状态的 action）；② **DSL**（HTML、SQL、Unix Shell Script、AWK、正则表达式……）；③ **编程范式**（面向对象：委托、策略、桥接、修饰、IoC/DIP、MVC；函数式：修饰、管道、拼装；逻辑推导式编程：Prolog）。
20. 收尾判据：**Logic 部分才是真正有意义的（What），Control 部分只是影响 Logic 部分的效率（How）**。
21. 作者把这个道理外推到系统架构：逻辑是业务逻辑与逻辑过程的抽象，加一个由术语表示的数据结构定义；控制逻辑与业务无关——**程序执行方式（并行/串行、同步/异步）、调度不同执行路径或模块、数据之间的存储关系**，都属于 Control。

## 39｜编程范式游记（10）- 逻辑编程范式
> 源文件 `.tmp-zuoer/txt/39丨编程范式游记（10）-逻辑编程范式.txt`，3234 字

### 一句话结论
Prolog 把「规则 + 事实 + 提问」变成程序：你只声明世界里成立什么，求解器自己匹配与回溯，**控制与算法实现都被语言接管**——这正是 Logic/Control 分离的极端形态（也是它性能不可预测的根源）。

### 知识点全清单（A1 零丢失）
1. 定义：Prolog = Programming in Logic 的缩写，一种逻辑编程语言；建立在逻辑学理论基础上，最初用于自然语言研究，现广泛用于人工智能（专家系统、自然语言理解、智能知识库）。
2. 起源：最早由艾克斯马赛大学（Aix-Marseille University）的 Alain Colmerauer 与 Philippe Roussel 等人于 20 世纪 60 年代末研究开发（原文印作"20 年代 60 年代末"，属明显笔误）；**1972 年被公认为 Prolog 正式诞生年份**，此后分支多种方言。
3. 两大方言：Edinburgh 与 Aix-Marseille；最早的 Prolog 解释器由 Roussel 建造，第一个 Prolog 编译器由 David Warren 编写。
4. 采用史：北美与欧洲广泛使用；日本政府曾为建造智能计算机用 Prolog 开发 **ICOT 第五代计算机系统**；早期机器智能研究领域 Prolog 曾是主要开发工具。
5. 1980 年代 Borland 开发 **Turbo Prolog**，进一步普及；**1995 年确定 ISO Prolog 标准**。
6. 与函数式语言的区别：Prolog 程序基于**谓词逻辑**理论；最基本写法是订立对象与对象之间的关系，再用「询问目标」的方式查询对象间关系；**系统自动进行匹配及回溯**找出答案。
7. 语法约定：以**大写字母**开头的元素是变量；字符串、数字或以**小写字母**开头的元素是常量；下划线 `_` 是**匿名变量**。
8. 逻辑编程靠推理——三步走示例（哲学家与凡人）：① 定义规则 `mortal(X) :- philosopher(X).`；② 陈述事实 `philosopher(Socrates). / philosopher(Plato). / philosopher(Aristotle).`；③ 问"谁是人类"，输出苏格拉底、亚里士多德、柏拉图（示例还给了 `mortal_report` 用 `write/nl/fail` 强制回溯枚举全部解）。
9. 逻辑编程范式的四个特征：① 把正规的逻辑风格带入计算机程序设计之中；② 建立描述一个问题里的世界的**逻辑模型**；③ 目标是对这个模型建立**新的陈述**；④ 通过陈述事实——因果关系，**程序自动推导出相关的逻辑**。
10. 经典问题：地图着色（四色）。规则前提「任何一个地图，相邻区域不能用相同颜色，只要用四种不同颜色就够了」。
11. 步骤一：定义四种颜色 `color(red/green/blue/yellow)`。
12. 步骤二：定义相邻规则 `neighbor(StateAColor, StateBColor) :- color(StateAColor), color(StateBColor), StateAColor \= StateBColor.`；前两个条件绑定两个变量为颜色，第三个条件 `\=`（不等运算符）保证颜色不同。
13. 步骤三：描述德国 16 个州的相邻事实 `germany(SH, MV, HH, HB, NI, ST, BE, BB, SN, NW, HE, TH, RP, SL, BW, BY) :- neighbor(...), ...`（原文列出约 28 条 neighbor 子句，覆盖 SH-NI/HH/MV、MV-NI/BB、NI-HB/BB/ST/TH/HE/NW、ST-BB/SN/TH、BB-BE/SN、NW-HE/RP、SN-TH/BY、RP-SL/HE/BW、HE-BW/TH/BY、TH-BW、BW-BY 等）。
14. 步骤四：直接提问 `?- germany(SH, MV, HH, HB, NI, ST, BE, BB, SN, NW, HE, TH, RP, SL, BW, BY).`，Prolog 推导出各地区颜色。
15. 小结：Prolog 把业务逻辑/算法抽象成「只关心规则、事实与问题推导」的标准方式，**不需要关心程序控制，也不需要关心具体实现算法**——给出可用于推导的规则与事实，问题即被逻辑推导解决。
16. 学习资源：Prolog Tutorial、Learn Prolog Now!。

## 41｜弹力设计篇之"认识故障和弹力设计"
> 源文件 `.tmp-zuoer/txt/41丨弹力设计篇之“认识故障和弹力设计”.txt`，4353 字

### 一句话结论
弹力（Resiliency）设计的目标不是避免故障，而是**把 MTTR 压下来**：故障是常态且不可预测，所以要把"处理故障"当正常功能写进架构（Design for Failure），并用可用性公式与"几个 9"给设计立一条可测量的基准线。

### 知识点全清单（A1 零丢失）
1. 定位：前作《分布式系统架构的本质》系列讲的是"纲"（业务层/中间件层/数据库层的高并发、异地多活、容器化、微服务、高可用、弹性化）；本系列讲"关键设计模式"，分容错、性能、管理三块。
2. 容错设计又叫**弹力设计**，着眼于分布式系统的各种"容忍"能力，四类归口：① 容错能力（服务隔离、异步调用、请求幂等性）；② 可伸缩性（有/无状态的服务）；③ 一致性（补偿事务、重试）；④ 应对大流量的能力（熔断、降级）。"在确保系统正确性的前提下，系统的可用性是弹力设计保障的重点。"
3. Resiliency（弹力）的语义：系统在不健康、不顺、甚至出错的情况下有能力 hold 得住、挺得住，还能在逆境下力挽狂澜。
4. 为什么先讲测量：做设计需要设计目标/基准线，否则设计"非常不明确、不可预测、不可测量"；**可测试和可测量性是软件设计中非常重要的事情**。
5. 可用性公式：`Availability = MTTF / (MTTF + MTTR)`。
6. **MTTF** = Mean Time To Failure，平均故障前的时间，即系统平均能正常运行多久才发生一次故障；可靠性越高 MTTF 越长。作者特别提醒："从字面上来说，看上去有 Failure 的字样，但其实是正常运行的时间。"
7. **MTTR** = Mean Time To Recovery，平均修复时间，即从故障出现到故障修复的这段时间，越短越好。
8. 提高可用性的两条路：要么提高无故障时间（MTTF），要么减少故障恢复时间（MTTR）。原文的"几个 9"对照表是图片，**正文无具体数值（原文未展开）**。
9. 但分布式系统"要不出故障简直是太难了"。
10. 故障诱因不止软件设计：还有硬件、第三方服务（如电信联通的宽带 SLA），当然包括**"建筑施工队的挖掘机"**。
11. SLA 的定位：正如 SLA 的定义，它不只是技术指标，而是服务提供商与用户之间的 **contract / 契约**；这种工业级玩法"就像飞机一样，并不是把飞机造出来就好了，还有大量的无比专业的配套设施、工具、流程、管理和运营"。
12. 几个 9 = 能持续提供可用服务的级别；工业界把服务不可用的因素分两种：**有计划**与**无计划**（两图均来自 Oracle 的《High Availability Concepts and Best Practices》）。
13. 无计划宕机原因三类：① 系统级故障（主机、操作系统、中间件、数据库、网络、电源、外围设备）；② 数据和中介的故障（人员误操作、硬盘故障、数据乱了）；③ 自然灾害、人为破坏、供电问题。
14. 有计划宕机原因三类：① 日常任务（备份、容量规划、用户和安全管理、后台批处理应用）；② 运维相关（数据库维护、应用维护、中间件维护、操作系统维护、网络维护）；③ 升级相关（数据库、应用、中间件、操作系统、网络，包括硬件升级）。
15. 再按"诱因"归成六类：① **网络问题**（链接出问题、带宽拥塞）；② **性能问题**（数据库慢 SQL、Java Full GC、硬盘 IO 过大、CPU 飙高、内存不足）；③ **安全问题**（被网络攻击，如 DDoS）；④ **运维问题**（系统总在被更新修改、架构不断调整、监控问题）；⑤ **管理问题**（没梳理出关键服务及依赖关系、运行信息没和控制系统同步）；⑥ **硬件问题**（硬盘损坏、网卡、交换机、机房掉电、挖掘机问题）。
16. 故障不可避免：大规模分布式系统出故障基本是常态，甚至有些地方你根本不知道会出问题；今天的故障是**分布式的、多米诺骨牌式的**。
17. 复杂度放大器：上云、用微服务、面对大量 IoT 设备与不受控的用户流量，故障会更复杂更变态。
18. 两个必须认清的事实：① 故障是正常的，而且是常见的；② 故障是不可预测突发的，而且相当难缠。
19. AWS 把 **Design for Failure 作为其七大 Design Principle 的重点**；含义是不要尝试避免故障，而是**把处理故障的代码当成正常的功能做在架构里、写在代码里**。
20. 为什么这么做：因为要干的事就是**想尽一切手段降低 MTTR——故障的修复时间**，这就是把它叫弹力（Resiliency）的原因。
21. 弹力的两种表现：① 好的情况下，对用户和内部运维完全透明，系统自动修复不需人干预；② 修不了时，系统能自我保护，不让事态变糟。
22. "弹力——能上能下"，作者联想到三国杀赵云技能"**能进能退乃真正法器**"。
23. 系列全景（文末目录）：弹力设计篇（认识故障、隔离 Bulkheads、异步 Asynchronous、幂等 Idempotency、服务状态 State、补偿事务、重试 Retry、熔断 Circuit Breaker、限流 Throttle、降级 degradation、弹力总结）；管理设计篇（分布式锁、配置中心、边车、服务网格、网关、部署升级策略）；性能设计篇（缓存、异步处理、数据库扩展、秒杀、边缘计算）。管理篇含"网关、边车、刚开始流行的 Service Mesh"；性能篇含"缓存、CQRS、索引表、优先级队列、业务分片"。

### 一句话结论
隔离（Bulkheads，船舱隔板）只有两种切法——**按服务种类切**和**按用户切（多租户）**；切完之后故障不会消失，只会换成性能、数据合并、跨版块交互、分布式事务、业务不可跨版块这五种新代价，所以隔离的粒度必须用"成本 × 复杂度 × 粒度"来折衷。

### 知识点全清单（A1 零丢失）
1. 词源：隔离设计的英文是 **Bulkheads**，中文译"隔板"；术语来自造船——船舱里防漏水的隔板，大船会把船舱隔成若干空间，一舱漏水只进一个小空间，不会整船沉没。
2. 软件同理："我们的软件设计当然也'漏水'"，为不让故障蔓延，要用隔板技术把架构分成多个"船舱"。
3. 反例细节：泰坦尼克号也有 Bulkheads 设计，但**设计有缺陷**——撞冰山漏水后因船体倾斜，**水漫过了隔板**，从而下沉。
4. 两种分离方式：① 按服务的种类分离；② 按用户（请求）分离。
5. 按服务种类：示例把系统分成**用户、商品、社区**三个版块，三版块分别使用**不同的域名、服务器和数据库**，做到**从接入层到应用层再到数据层三层完全隔离**；物理上一版块故障不影响另一版块。
6. 亚马逊的做法：每个服务都有自己的一个数据库，库里保存该业务相关的数据和相应处理状态；每个服务从一开始就准备好对外暴露；这也是微服务推荐的架构方式。
7. 「按服务种类隔离」的五个代价之一：同时取多个版块数据要调多个服务，**性能下降——注意这里指的是响应时间，不是吞吐量（相反，这种架构下吞吐量可以得到提高）**。
8. 代价之二：有大数据平台就要把数据抽取到一个数据仓库计算，**增加数据合并的复杂度**，需要一个框架或中间件做抽取。
9. 代价之三：跨版块交互变复杂，需要**类似 Pub/Sub 的、高可用且可持久化的消息订阅通知中间件**来打通各版块的数据与信息交换。
10. 代价之四：多版块间的**分布式事务**问题；需要"二阶段提交"这样的方案；**亚马逊用的是 Plan – Reserve – Commit/Cancel 模式**——先做一个 plan 的 API 调用，各子系统 reserve 住相应资源，全成功则 Commit，任一失败则整体 Cancel；**这很像阿里的 TCC（try confirm/cancel）**。
11. 代价之五：业务逻辑/流程跨版块时，**一个版块故障会导致整个流程走不下去**，同样造成整体业务故障。
12. 对应的解：保证业务流程中各子系统的高可用 + 把业务流程做成 **Step-by-Step**，用户交互的每一步都可以保存，故障恢复后可继续执行而不是从头执行。
13. 作者经验判断：隔离了的系统在具体业务场景中问题很多，"这样的系统通常会引入大量的异步处理模型"。
14. 一个产品侧约束：要小心设计用户交互，最好不要让用户在一个页面上获得所有数据；手机端屏幕小，也不可能一屏展示太多内容。
15. 按用户隔离：把用户分成不同组，把后端的同一个服务按这些组分成不同实例，让同一服务对不同用户冗余与隔离；某实例挂掉只影响一部分用户。
16. 这就是**多租户**模式：大客户给专门独立实例/集群与他人隔离，小客户共享实例以省资源；两种切法（按功能、按用户）**可以融合**。
17. 多租户的复杂度：完全隔离则资源浪费，共享则程序设计复杂。
18. 多租户三种做法：① **完全独立的设计**（每租户有自己完全独立的服务和数据）；② **独立的数据分区，共享的服务**（服务共享、数据分开隔离）；③ **共享的服务，共享的数据分区**（数据和服务都共享）。
19. 三方案权衡：完全独立——开发实现与资源隔离度非常好，但成本高、计算资源有浪费；完全共享——资源利用与成本非常好，但开发难度非常大、数据与资源隔离非常不好。
20. 折衷结论：一般用中间方案——服务共享、数据通过分区隔离；对重要的租户（需要好的隔离性）用完全独立的方式。
21. 虚拟化带来的变化：在虚拟化非常成熟的今天完全可以走"完全独立"，通过 Hypervisor（如 KVM）或 Linux Container（如 Docker）实现**物理资源共享与成本节约**。
22. 隔离设计的五个重点：① 定义好隔离业务的大小和粒度，过大过小都不好，需要认真做业务需求与系统分析；② 无论系统版块还是多租户，都要在复杂度、成本、性能、资源之间找均衡或分步实施方案，关键是**定义好要什么和不要什么**（不可能做一个什么都满足的系统）；③ 隔离模式需要**配置高可用、重试、异步、消息中间件、流控、熔断等设计模式配套使用**；④ 别忘了分布式系统运维复杂度的提升，需要大量自动化运维工具（容器/虚拟机有助于管理并更好利用资源），否则"做出来了也管理不好"；⑤ 需要一个**非常完整的、能看到所有服务的监控系统**，这点非常重要。

## 43｜弹力设计篇之"异步通讯设计"
> 源文件 `.tmp-zuoer/txt/43丨弹力设计篇之“异步通讯设计”.txt`，5758 字

### 一句话结论
同步调用有四个结构性缺陷（吞吐被最慢者决定、占住调用方资源、只能一对一、故障多米诺），异步是唯一解法；异步有三种耦合度递减的形态（**请求响应 → 直接订阅 → Broker**），**Broker 是解耦最彻底也最需要高可用的那一种**，事件驱动（EDA）就是它的产物。

### 知识点全清单（A1 零丢失）
1. 起因：前面说的隔离设计需要做解耦，而把单体系统解耦不只是把业务功能拆出来，拆完还要面对系统间通讯问题。
2. 同步 vs 异步的比喻：同步像**打电话**，需要实时响应；异步像**发邮件**，不需要马上回复；各有千秋，很难说谁比谁好。
3. 但在**超高吞吐量**场景下异步优势明显："这就好像一个人不可能同时接打很多电话，但是他可以同时接收很多的电子邮件一样。"
4. 同步调用的四个问题：
   ① 同步调用需要被调用方吞吐不低于调用方吞吐，否则被调用方会因性能不足**拖死调用方**；换句话说，**整个同步调用链的性能由最慢的那个服务决定**。
   ② 调用方要一直等待，一层层同步调用下去所有参与方有相同等待时间；调用方需要**保存现场（Context）**等远端返回，高并发下这种等待极其消耗资源。
   ③ 同步调用**只能一对一，很难做到一对多**。
   ④ 最糟的是被调用方有问题时调用方跟着出问题，出现**多米诺骨牌效应**，故障一下蔓延开。
5. 异步的两个好处：除增加系统吞吐量外，**最大的好处是让服务间解耦更彻底**——调用方与被调用方可以按自己的速率而不是步调一致，从而更好地保护系统、让系统更有弹力。
6. 异步三种方式之一 **请求响应式**：发送方（sender）直接请求接收方（receiver），被请求方收到后直接返回"收到请求，正在处理"。
7. 取结果的两种办法：① 发送方时不时**轮询**问干没干完；② 发送方注册一个**回调**方法，接收方处理完回调请求方。典型场景是早期网上支付：页面从商家跳转到支付宝或银行，商家把回调 URL 传给支付页面，支付完再跳回商家 URL。
8. 请求响应式的缺陷：**仍有耦合**——发送方依赖接收方，还要把自己的回调发给接收方。
9. 方式之二 **通过订阅**：接收方订阅发送方的消息，发送方把消息/数据放到接收方订阅的队列，接收方从队列取；**发送方不关心订阅方的处理结果**，只告诉对方有事要干，收完给个 **ACK** 就好。
10. 订阅式的典型用法：MVC（Model-View-Control）这类设计模式；例子是下单支付完成后把事件通知订单处理与物流——订单处理变更状态、物流从仓库分配库存准备配送，**后续这些处理结果无需告诉支付服务**。
11. 为什么订阅式更好（原文标注"重点来了"）：请求响应式像函数调用，**有数据有状态的往来**（要有请求数据、返回数据，服务里还可能保存调用状态），所以**服务是有状态的**；如果通过第三方状态服务把服务状态去掉，服务间的依赖就**只剩事件**了。
12. 推论：分布式系统服务设计要**向无状态服务（Stateless）努力**，无状态意味着运维非常方便，所以**事件通讯成为异步通讯中最重要的设计模式**。
13. 支付例子的对照：商家只需订阅一个"支付完成"事件（带订单号），不必让支付方知道自己的回调 URL，"这样的异步是不是更干净一些"。
14. 订阅式的缺陷：接收方需要向发送方订阅事件，所以是**接收方依赖发送方**，仍有耦合。
15. 方式之三 **通过 Broker**：Broker 就是中间人，发送方与接收方互相看不到对方，只看得到 Broker；发送方向 Broker 发消息，接收方向 Broker 订阅。
16. Broker 的价值：**完全解耦**，所有服务不相互依赖而依赖一个中间件；Broker 像个**数据总线**，所有收发数据都发到这个总线上，**"这个总线就像协议一样，让服务间的通讯变得标准和可控"**。
17. Broker 必须具备三个特性：① **高可用**（它成了整个系统的关键）；② **高性能且可水平扩展**；③ **可持久化、不丢数据**。作者承认"要做到这三条还是比较难的"，好在开源软件或云平台的 Broker 已很成熟。
18. EDA：上述第二种与第三种方式就是**事件驱动架构（EDA – Event Driven Architecture）**；事件驱动最好用 Broker 方式，服务间通过交换消息完成交流与流程驱动。
19. 订单流程示例：下单服务通知订单服务有订单要处理；订单服务生成订单后发通知；库存服务与支付服务收到通知后，一边占住库存、另一边让用户支付；支付完成后通知配送服务配送。
20. 每个服务是**"自包含"**的（没有和别人产生依赖）；把整个流程串起来需要一系列**"消息通道（Channel）"**——各服务做完自己的事发事件，另一些服务订阅某些事件来联动。
21. 事件驱动的**五个好处**：① 服务间依赖没有了，服务间平等，每个服务高度可重用并可替换；② 服务的开发、测试、运维、故障处理高度隔离；③ 通过事件关联，服务间**不会相互 block**；④ 在服务间增加 Adapter（日志、认证、版本、限流、降级、熔断等）相当容易；⑤ 服务间吞吐解开，各服务按自己的处理速度处理。
22. 事件驱动的**三个坏处**：① 业务流程不再那么明显和好管理，架构变复杂，需要有可视化工具呈现整体业务流程；② **事件可能乱序**，会带来非常 Bug 的事，解决需要很好地管理一个**状态机**的控制；③ **事务处理变复杂**，需要两阶段提交做强制一致性，或退缩到最终一致性。
23. 异步通讯设计重点（"首先需要知道为什么要异步通讯"）：① 解耦服务间依赖，最佳解耦方式是 Broker；② 解耦目的是让各服务隔离性更好，不出现"一倒倒一片"；③ 获得更大吞吐量，各服务性能不受干扰相对独立；④ 用 Broker/队列可以把**抖动的吞吐量变成均匀的吞吐量——即"削峰"**，对后端是很好的保护；⑤ 服务相对独立，部署、扩容、运维都可独立不受其他服务干扰。
24. 需要付出的注意：① 用于异步通讯的 Broker 成为关键，要设计成**高可用不丢消息**；② 分布式下**很难保证消息顺序**，设计**最好不依赖于消息顺序**；③ 异步会让业务处理流程不直观（像接力），Broker 上需要有**服务消息跟踪机制**，否则出问题不易调试；④ 服务间只通过消息交互，**业务状态最好由一个总控方管理**，总控方维护业务流程的状态变迁逻辑，以便故障后知道处理到哪一步、故障清除后继续处理。
25. 总控方的真实原型：银行**对账系统**。银行有大量外部系统通讯（跨行交易、跨企业交易），为保证整体数据一致、避免漏处理与处理错，需要有对账系统；**这也是为什么银行有的交易是 T+1（隔天结算）——因为要对个账，确保数据是对的**。
26. 消息传递中的 send/ACK：业务逻辑可能像 TCP 那样，A 服务发出消息后等处理方 ACK，等不到就**重传**；此时处理方必须**幂等**——同一条消息无论收到多少次都只处理一次。

### 数字 / 公式 / 阈值

## 44｜弹力设计篇之"幂等性设计"
> 源文件 `.tmp-zuoer/txt/44丨弹力设计篇之“幂等性设计”.txt`，5785 字

### 一句话结论
服务调用只有三种结果（成功/失败/**超时**），超时是唯一"不知道"的状态，因此要么"超时后回查"，要么让下游接口幂等；分布式幂等的落地支点是**全局唯一交易 ID（Snowflake）+ 共享去重存储**，靠"插入冲突"而不是"先查后写"来判重。

### 知识点全清单（A1 零丢失）
1. 定义：幂等性设计 = **一次和多次请求某一个资源应该具有同样的副作用**；数学表达 `f(x) = f(f(x))`。
2. 直观例子：求绝对值 `abs(x) = abs(abs(x))`。
3. 为什么需要：系统解耦隔离后，服务间调用有**三个状态**——成功（Success）、失败（Failed）、**超时（Timeout）**；前两者明确，**超时则完全不知道是什么状态**。
4. 超时的成因链：可能是请求时就没请求到（网络丢包），也可能请求到了但返回结果时没正常返回；于是**完全不知道下游是否收到请求、收到后是否处理、成功/失败状态在返回时是否遇到网络问题**——"总之，请求方完全不知道是怎么回事"。
5. 三个真实后果：① 订单创建接口第一次超时、调用方重试，是否多创建一笔订单？② 订单创建要扣库存，接口超时重试，是否多扣一次库存？③ 支付请求发出后服务端已扣钱、接口响应超时、调用方重试，是否多扣一次钱？
6. 两种处理方式：① **下游提供查询接口**，上游 timeout 后去查，查到就说明做了——成功了不用再做，失败了走失败流程；② **下游提供幂等性的交易接口**，上游只管重试，下游保证一次和多次结果一样。
7. 全局 ID 的必要性：要做幂等交易接口，必须有唯一标识来标志"同一笔交易"；而这个 ID **由谁分配很头疼**——因为它要全局唯一。
8. 中心分配的问题：每次交易都要找中心系统，**增加程序的性能开销**。
9. 上游分配的问题：上游可能是集群、同时承担相同工作，**会出现 ID 分配重复**。
10. UUID 方案的四个缺点：① 冲突非常小（可解分配冲突）；② 字符串占用空间比较大；③ **索引效率非常低**；④ 生成 ID 太随机、完全不是人读的，且**没有递增，无法按前后顺序排序**。
11. Snowflake（Twitter 开源分布式 ID 生成算法）：核心思想是产生一个 **long 型 ID**，其中——
    - **41 bits 毫秒数，大概可以用 69.7 年**；
    - **10 bits 机器编号（5 bits 数据中心 + 5 bits 机器 ID），支持 1024 个实例**；
    - **12 bits 毫秒内序列号，一毫秒可以生成 4096 个序号**。
12. 迁移性：Redis 或 MongoDB 的全局 ID 生成都与这个算法大同小异；可以按实际情况加上业务编号。
13. 幂等处理流程：本质是**过滤已经收到的交易**，需要一个**存储**记录收到的交易；收到请求先查存储——查到就不再处理并**返回上次做的结果**，没查到就记录下来。
14. 该流程的性能问题：绝大多数请求不是重发的，让 **100% 请求都去存储查一次**会让处理流程变得很慢。
15. 优化思路：让存储在**出现冲突时报错**——收到请求直接去存储记录这个 ID（相当于 Insert），如果出现 ID 冲突异常，就知道之前已经有人发过来了，不用再做。例如数据库 `insert into … values … on DUPLICATE KEY UPDATE …`。
16. 更新场景的幂等写法：只是状态更新时用条件更新，如 `update table set status = "paid" where id = xxx and status = "unpaid";`——出错只可能是非法操作/已被更新/状态不对，**多次调用不会有副作用**。
17. 对 MVCC/版本号方案的点评：网上还有用 MVCC 版本号等方式，"我觉得这些都不标准"，希望有一个标准方式，**最好还是用一个 ID**。
18. 存储的定位：因为幂等服务也是分布式的，所以存储必须**共享**，这样每个服务就变成没有状态的了；但**这个存储成了非常关键的依赖**，其扩展性和可用性也成了非常关键的指标。
19. 存储选型：关系型数据库，或 key-value 的 NoSQL（如 MongoDB）。
20. HTTP 幂等性逐方法（原文的判断口径是"一次和 N 次具有相同的副作用"，不是"每次结果相同"）：
    - **GET**：取资源，不应有副作用，幂等。`GET http://www.bank.com/account/123456` 不改变资源状态；强调"一次和 N 次副作用相同"而非结果相同——`GET http://www.news.com/latest-news` 可能每次结果不同，但没有副作用，仍满足幂等。
    - **HEAD**：与 GET 本质一样，区别是不含呈现数据、只有 HTTP 头信息，无副作用、幂等。用途："评判某个资源是否存在"时用 HEAD 意义更明确，**HEAD 可用来做探活**。
    - **OPTIONS**：获取当前 URL 所支持的方法，幂等。请求成功时会在 HTTP 头里带 `Allow`，值为所支持的方法（如 "GET, POST"）。
    - **DELETE**：删除资源，有副作用，但**应满足幂等**。`DELETE http://www.forum.com/article/4231` 调一次和 N 次副作用相同（删掉 ID 4231 的帖子），调用者可多次调用或刷新页面而不担心出错。
    - **POST**：创建资源，URI 并非创建的资源本身而是"执行创建动作的操作者"，有副作用、**不满足幂等**。两次相同 POST 会创建两份资源、有不同 URI。
    - **PUT**：创建或更新，URI 就是要创建或更新的资源本身，有副作用、**应满足幂等**。对同一 URI 多次 PUT 的副作用与一次相同。
21. POST 多次提交的表单幂等设计（三段式）：① 表单隐藏一个 **token**（前端生成的唯一 ID），防用户多次点击而让后端收到多次请求却分不清；token 是表单的唯一标识——**这种情况其实是通过前端生成 ID 把 POST 变成了 PUT**；② 用户点击提交后，后端把数据与该 token 存数据库，重复提交时**数据库中的 token 做排它限制**，从而实现幂等；③ 更稳妥：后端成功后向前端返回 **302 跳转**，把页面跳到 GET 请求展示刚 POST 的数据；Web 上还把之前的表单设置成过期，让用户不能靠浏览器后退重新提交——这个模式叫 **PRG（Post/Redirect/Get）**。
22. 小结：幂等含义=发送多次与发送一次的副作用相同；三结果=成功/失败/超时，超时是要解决的问题；手段=超时后查询 或 下游实现幂等；分布式实现幂等需要全局 ID（Snowflake 好用）；最后给了幂等接口的处理流程。

## 45｜弹力设计篇之"服务的状态"
> 源文件 `.tmp-zuoer/txt/45丨弹力设计篇之“服务的状态”.txt`，5156 字

### 一句话结论
"无状态"是分布式服务的最佳实践，但它的真实动作是**把状态搬到别处**（Redis/MySQL/ZooKeeper/Etcd/分布式文件系统），代价是多一层依赖与网络开销；而**有状态服务并非落后**——它换来数据本地化（低延迟）与更强的 A+C，代价是必须靠 Sticky Session 把请求钉在同一实例上。

### 知识点全清单（A1 零丢失）
1. 承接：幂等设计里为过滤已处理请求需要保存处理过的状态，为把服务做成无状态，引入了第三方存储；本讲专谈"服务的状态"。
2. 判断：**只有清楚地了解了状态这个事，才有可能设计出更好、更有弹力的系统架构**。
3. 状态的定义：**为了保留程序的一些数据或是上下文**。三个例子：① 幂等设计要保留每一次请求的状态；② 用户登录的 Session（用来判断请求合法性）；③ 一个业务流程中让多个服务组合成业务逻辑的运行上下文 Context。
4. 现状判断：**我们的代码中基本上到处都是这样的状态**。
5. 无状态服务（Stateless）的地位：**一直以来被当作分布式服务设计的最佳实践和铁律**。
6. 无状态的三重好处：① 对扩展性与运维极其方便——可随意增加/减少结点，也可随意搬迁；② 大幅降低代码复杂度与 Bug 数——因为没有状态，也就没有明显的"副作用"。
7. 与函数式编程的同构：无状态服务与函数式思维方式如出一辙；函数式铁律是函数无状态、immutable，只描述逻辑与算法，**根本不保存数据、也不修改输入数据**，而是把计算好的结果返回出去，哪怕要把输入数据重新拷贝一份只做少量修改。
8. 转折：**现实世界是一定会有状态的**。
9. 状态的三种表现：① **程序调用的结果**；② **服务组合下的上下文**；③ **服务的配置**。
10. 状态往哪放（按重要性分级）：不太重要的数据 → Redis；重要的数据 → MySQL；需要高可用强一致 → ZooKeeper/Etcd 这类存储；或分布式文件系统。
11. 无状态的代价一：服务**耦合第三方有状态存储**——一方面是有依赖，另一方面**增加网络开销，导致响应时间变慢**。
12. 代价二：第三方存储必须做成**高可用高扩展**。
13. 代价三：为减少网络开销要在无状态服务里**加缓存**，但下次请求不一定落在同一台机器，所以**缓存会在所有机器上都创建，也算是一种浪费**。
14. 宏观影响："这种'转移责任'的玩法也催生出了对分布式存储的强烈需求"；而数据层 scheme 众多，**很难做出一个放之四海皆准的分布式存储系统**。
15. 因此无状态服务依赖：ZooKeeper/Etcd 这类高可用强一致服务，或底层分布式文件系统（开源如 **Ceph、GlusterFS**）；现在分布式数据库开始将**服务与存储分离**，也是为了让系统更有弹力。
16. 有状态服务（Stateful）的处境：在今天看上去"的确比较反动"，但需要比较优劣。
17. 无状态的短板（再次确认）：程序 Bug 与水平扩展表现优秀，但状态存第三方增加了网络开销；服务内缓存需在**所有实例**上都有（因为请求不会都落同一实例），**比较浪费资源**。
18. 有状态的两个好处：① **数据本地化（Data Locality）**——状态和数据本机保存，不但延迟更低，对**数据密集型应用**更快；② **更高的可用性和更强的一致性**——即 CAP 原理中的 A 和 C。
19. 有状态的代价/机制：客户端请求**必须保证落在同一个实例上**，这叫 **Sticky Session 或 Sticky Connection**；这样完全不需要考虑数据被加载到不同结点，模型更容易理解和实现。
20. 最本质的区别：**无状态服务需要把数据同步到不同结点，有状态服务通过 Sticky Session 做数据分片**——"同步有同步的问题，分片也有分片的问题，这两者没有谁比谁好，都有 trade-off"。
21. Sticky Session 的两种实现：① **持久化的长连接**（就算 HTTP 协议也要用长连接）；② 简单的**哈希算法**，比如通过 uid 求模，走**一致性哈希**的玩法，也可以方便地水平扩展。
22. 长连接的问题：**结点的负载和数据并不会很均匀**，尤其长连接"连上了就不断了"；所以长连接玩法一般会有一种叫 **"反向压力（Back Pressure）"** 的机制——如果服务端成为热点，就**主动断连接**；这种玩法也比较危险，需要客户端配合，否则容易出 Bug。
23. 要负载与数据都均匀：需要一个**元数据索引**来映射后端服务实例与请求的对应关系，还需要一个**路由结点**按元数据索引路由，而这个元数据索引表会根据后端服务压力**重新组织映射**。
24. 去掉路由结点、让有状态服务直接路由的两种方式：① **直接用配置**——节点启动时把元数据读到内存，但增删结点都要更新配置，导致其它结点也一同重新读入；② **Gossip 协议**——各节点互相散播消息来同步元数据，增删结点时集群内部可以很容易重新分配（"听起来要实现好真的好复杂"）。
25. 有状态服务自动伸缩的真实案例：① **Facebook 的 Scuba**——分布式内存数据库，用**静态配置**（即上面第一种方式）；② **Uber 的 Ringpop**——开源 Node.js 库，**根据地理位置分片**来路由请求（github.com/uber-node/ringpop-node）；③ **微软的 Orleans**——Halo 4 基于其开发，用 **Gossip + 一致性哈希 + DHT** 结合：用户通过 ID 的一致性哈希映射到一个节点，该节点保存该用户的 DHT，再通过 DHT 定位到处理用户请求的位置（github.com/dotnet/orleans，开源）。
26. 延伸阅读：Twitter 工程师 **Caitie McCaffrey** 的演讲《Building Scalable Stateful Service》（Youtube 视频 + PPT），文字版是 High Scalability 上的《Making the Case for Building Scalable Stateful Services in the Modern Era》。
27. 服务状态的容错设计：在容错设计中服务状态**非常复杂**，尤其对运维——**要调度服务就需要调度服务的状态，迁移服务的状态就需要迁移服务的数据**；数据量大时更困难。
28. 作者判断：Sticky Session 这种调度方式"理论上虽然可以这么干"，但实际运维中"还是件挺麻烦的事儿，不是很好的玩法"。
29. 主流高可用做法：**数据在运行时就复制**——ZooKeeper、Kafka、Redis、ElasticSearch 等；运行时复制就要考虑一致性，**强一致系统一般使用两阶段提交**，要求所有结点有一致结果，这是 CAP 里的 **CA 系统**；也有系统采用**大多数人一致就够了**，比如 **Paxos**，这是 **CP 系统**。
30. 复制解决不了的：一个结点挂掉后在另一个地方恢复时，**必须先把数据同步过来才能提供服务**；数据量过大时这个过程很漫长，**影响系统可用性**。
31. 终极手段：使用**底层的分布式文件系统**——有状态数据不仅在运行时多结点复制，还要**持久化在硬盘**上（可以是挂载到本地硬盘的一个外部分布式文件卷）；结点挂掉后在新宿主机启动新实例时，**从远程把之前的文件系统挂载过来**，启动过程中就装载好了大多数数据，只需从网络其它结点同步少量数据，从而**快速恢复和提供服务**。
32. 结论句：**这一点对有状态的服务非常关键，所以，使用一个分布式文件系统是调度有状态服务的关键**。

## 46｜弹力设计篇之"补偿事务"
> 源文件 `.tmp-zuoer/txt/46丨弹力设计篇之“补偿事务”.txt`，6182 字

### 一句话结论
分布式业务一致性多数只需要 **BASE（基本可用 + 软状态 + 最终一致）**，而 BASE 的落地方式就是**补偿事务**：用工作流引擎把正向流程与反向补偿一起设计，靠幂等 + 重试把流程"拟合"到目标状态，拟合不了就回滚到事先定义好的起始状态。

### 知识点全清单（A1 零丢失）
1. 问题起点：分布式系统一个业务流程要组合一组服务，微服务下更明显，需要业务上的一致性保证；**一个步骤失败，要么回滚到以前的服务调用，要么不断重试保证所有步骤都成功**。
2. 强一致的代价：需要业务层用"两阶段提交"；但很多情况并不需要这么强的一致性，而且**强一致性的最佳保证基本都在底层完成**，或像 Stateful 的 Sticky Session 那样在一台机器上完成；"在我们接触到的大多数业务中，其实只需要最终一致性就够了"。
3. ACID 四属性逐条（传统关系型数据库事务）：
   - **原子性**：事务中所有操作要么全部完成、要么全部失败，不可能停在中间某环节；执行中出错会被回滚（Rollback）到开始前状态，像从没执行过。
   - **一致性**：事务开始前与结束后，数据库的完整性约束没有被破坏。
   - **隔离性**（又称独立性）：两个事务的执行互不干扰，一个事务不可能看到另一个事务运行中间某一刻的数据，两个事务不会发生交互。
   - **持久性**：事务完成后，对数据库的更改持久保存在数据库中，不会被回滚。
4. 银行转账例子：从原账户扣款 + 向目标账户加款，两个操作总和构成一个完整逻辑过程，是不可拆分的原子操作，**从而保证整个系统中的总金额没有变化**。
5. 但这对分布式/微服务很难满足高性能要求；CAP 理论——一致性、可用性、分区容忍性现实中不能都满足，最多满足两个。
6. 所以为提高性能出现了 ACID 的变种 **BASE**：
   - **Basic Availability 基本可用**：系统可以出现暂时不可用的状态，后面会快速恢复。
   - **Soft-state 软状态**：是"有状态"和"无状态"服务的**一种中间状态**；为提高性能可以让服务暂时保存一些状态或数据，这些状态和数据**不是强一致性的**。
   - **Eventual Consistency 最终一致性**：系统在一个短暂时间段内不一致，但最终整个系统看到的数据一致。
7. BASE 与弹力的关系：BASE 允许/容忍系统出现暂时性问题，系统就更有弹力；因为故障不可避免，能做的就是**把故障处理当成功能写入代码中，这就是 Design for Failure**。
8. BASE 的设计特点：保证短时间内**就算有数据不同步的风险，也应该允许新的交易发生**，后面再在业务上把可能出问题的事务处理掉，以保证最终一致性。
9. 网上卖书例子（ACID 玩法）：买同一本书时每个用户的购买请求都要**锁住库存**，减完库存再释放锁，后面的人才能买；于是同一时间不可能有多个用户下单，订单流程需要排队——**不可能做出性能比较高的系统**。
10. 网上卖书例子（BASE 玩法）：大家都可以同时下单，**下单时不真正分配库存**，系统异步地、**批量地**处理订单；因为下单时没真扣库存，**有可能超卖**，后台异步处理时发现库存没了，才告诉用户没购买成功。
11. 这就是亚马逊的玩法：因为要**根据用户的地址去不同仓库查看库存**，这个操作非常耗时，"不想做成异步的都不行"。
12. 亚马逊的邮件体感：先收到"系统收到你的订单了"邮件，过一会儿收到"订单被确认"邮件（**这时才真正分配了库存**）；所以有时会先收到下单邮件、过一会又收到"没有库存"的致歉邮件。
13. 命名梗：**ACID 是酸，BASE 是碱**，因此这是一个对立的东西；本质上**酸（ACID）强调 CAP 中的 C，碱（BASE）强调 CAP 中的 A**。
14. 业务补偿的前提判断：很多情况下做不到强一致 ACID，**特别是需要跨多个系统、而且这些系统还不是由一家公司提供**的时候。
15. 旅游例子（四件事）：① 向公司请假拿到假期；② 订飞机票或火车票；③ 订酒店；④ 租车。**前三件必须完全成功才能出行**，第四件只是锦上添花，**但第四件一旦确定，也会成为整个事务的一部分**；这些事要向不同组织/系统请求，可以并行做，某个有变化其它都会跟着变。
16. 三种变化情况：① 没订到返程机票 → 去不了，要把去程机票、酒店、租到的车都取消，**并且把请的假也取消**；② 假也请好、机票酒店也订好，只是车没租到 → 不影响出行，整个事可以继续；③ 飞机因天气取消或晚点 → 被迫调整修改酒店预订和租车预订。
17. 结论：这些情况天天在发生，分布式系统也一样——**当条件不满足或有变化时，需要从业务上做相应的整体事务补偿**。
18. 工作流引擎：业务的事务补偿一般都需要一个工作流引擎；**亚马逊是超级喜欢工作流引擎的公司**，引擎把各式各样的服务串联在一起，并在工作流上做相应的业务补偿，整个过程设计成最终一致性的。
19. 补偿的三个动作：① 首先要把服务做成**幂等**；② 事务失败或超时，需要**不断重试**，努力达到最终想要的状态；③ 如果达不到，需要**把整个状态恢复到之前的状态**；④ 如果有变化的请求，需要**启动整个事务的业务更新机制**。
20. 好的业务补偿机制三点：① 要能**清楚描述出要达到什么样的状态**（请假/机票/酒店三个都必须成功，租车可选），以及条件不满足时**回退到哪一个状态**——这是所谓**整个业务的起始状态定义**；② 整条业务跑起来时可以**串行或并行**（旅游订票可以并行，网购流程"下单、支付、送货"不能并行），系统要努力通过一系列操作达到想要的状态，达不到就通过补偿机制回滚——这是所谓的**状态拟合**；③ 对**已经完成的事务进行整体修改**，可以考虑成一个**修改事务**。
21. 纯技术世界的同构案例：线上运维系统发布新服务或对已有服务水平扩展——**找机器 → 初始化环境 → 部署应用 → 健康检查 → 接入流量**，这一系列动作要完全成功，所以部署系统需要管理好整个过程和相关运行状态。
22. 业务补偿主要做两件事：① 努力把一个业务流程执行完成；② 执行不下去时启动补偿机制、回滚业务流程。
23. 设计重点五条：① 需要流程中**所涉及的服务方支持幂等性**，并且**上游有重试机制**；② 要小心维护和监控整个过程状态，**千万不要把这些状态放到不同的组件中**，最好由一个业务流程的控制方（工作流引擎）来做，这个引擎需要**高可用和稳定**——"这就好像旅行代理机构一样，我们把需求告诉它，它会帮我们搞定所有的事，如果有问题，也会帮我们回滚和补偿"；③ **补偿的业务逻辑和流程不一定非得是严格反向操作**，有时候可以并行、有时候可能更简单；总之**设计业务正向流程的时候，也需要设计业务的反向补偿流程**；④ 要清楚**业务补偿是强业务相关的，很难做成通用的**；⑤ **下层的业务方最好提供短期的资源预留机制**——就像电商把库存预先占住等用户在 **15 分钟**内支付，没收到支付则释放库存，然后回滚到之前的下单操作，等用户重新下单。
24. 小结：ACID 一致性更强但可伸缩性非常差，仅在必要时用；BASE 一致性较弱但可伸缩性很好、还可以异步批量处理；**大多数分布式事务适合 BASE**；实现 BASE 需要补偿逻辑（事务可能失败，需协调各方撤销）；补偿各步骤可按业务定串行或并行；补偿与业务强相关，**必须实现在业务逻辑里**。

## 47｜弹力设计篇之"重试设计"
> 源文件 `.tmp-zuoer/txt/47丨弹力设计篇之“重试设计”.txt`，5516 字

### 一句话结论
重试的前提是"**这个故障是暂时的**"，所以先要按错误类型决定能不能重试；能重试的用**指数退避**拉开间隔（2 的指数、封顶），并且必须配**最大次数 + 幂等**，否则重试就是把一次故障放大成一场雪崩。

### 知识点全清单（A1 零丢失）
1. 背景：单体应用服务化、尤其微服务化后，进程内函数调用变成远程调用，就涉及网络问题。
2. 网络链路上的不稳定组件：**DNS 服务、网卡、交换机、路由器、负载均衡**等设备都不一定稳定；数据传输整个过程中**只要一个环节出问题，都会导致问题**。
3. 重试的语义（原文强调）：**"重试"的语义是我们认为这个故障是暂时的，而不是永久的**，所以才会去重试。
4. 需要定义"什么情况下重试"：① **调用超时**；② 被调用端返回某种**可以重试的错误**——如繁忙中、流控中、维护中、资源不足等。
5. 不该重试的两类：① **业务级错误**（没有权限、非法数据等）；② **技术上的错误**（如 HTTP 的 **503** 等，"这种原因可能是触发了代码的 bug，重试下去没有意义"）。
6. 重试策略的两条基本要求：① 需要一个**重试的最大值**，不断重试一段时间后就没必要再试，应该报故障；② 每次重试失败都应**休息一会儿再试**，避免重试过快加重网络负担。
7. **Exponential Backoff（指数级退避）**：每一次重试所需的休息时间**成倍增加**；机制目的是让被调用方有更多时间从容处理请求；"这其实和 **TCP 的拥塞控制** 有点像"。
8. 代码骨架（Java）：返回枚举 `Results { SUCCESS, NOT_READY, TOO_BUSY, NO_RESOURCE, SERVER_ERROR }`——共 **5 种**返回。
9. 退避函数：`getWaitTimeExp(int retryCount) { long waitTime = (long) Math.pow(2, retryCount); return waitTime; }`，返回 2 的指数，"这样每多一次重试就需要多等一段时间"；正文给的例子是**第一次等 200ms、第二次 400ms、第三次 800ms**（⚠️ 注意：代码只算了 `2^n`，没有乘 200ms 基数，与正文示例不一致——**原文自身的瑕疵**）。
10. 主循环 `doOperationAndWaitForResult()`：先 `asyncOperation()` 拿 token；循环里 `getAsyncOperationResult(token)`；**SUCCESS 不重试**；`NOT_READY / TOO_BUSY / NO_RESOURCE / SERVER_ERROR` 四种置 retry=true；其它（未列出的）一律不重试；需要重试时 `waitTime = Math.min(getWaitTimeExp(retries), MAX_WAIT_INTERVAL)` 后 `Thread.sleep`；循环条件 `retry && (retries++ < MAX_RETRIES)`。→ 两个关键参数：**MAX_WAIT_INTERVAL（封顶）** 与 **MAX_RETRIES（次数上限）**。
11. Spring Retry：独立项目，可用 Annotation 方式；示例 `@Retryable(value = { SQLException.class }, maxAttempts = 2, backoff = @Backoff(delay = 5000))`——**只对 SQLException 重试、重试 2 次、每次延时 5000ms**。
12. Spring 的 **RetryPolicy** 六种：
    - **NeverRetryPolicy**：只允许调用 RetryCallback 一次，不允许重试。
    - **AlwaysRetryPolicy**：允许无限重试直到成功，**逻辑不当会导致死循环**。
    - **SimpleRetryPolicy**：固定次数，**默认最大 3 次**，是 RetryTemplate 默认使用的策略。
    - **TimeoutRetryPolicy**：超时时间重试，**默认超时 1 秒**，在指定超时时间内允许重试。
    - **CircuitBreakerRetryPolicy**：有熔断功能的重试策略，需设置 **openTimeout、resetTimeout、delegate** 三个参数。
    - **CompositeRetryPolicy**：组合策略；**乐观组合**=只要有一个策略允许重试即可，**悲观组合**=只要有一个不允许即不可；但**不管哪种组合，组合中的每一个策略都会执行**。
13. Spring 的 **BackoffPolicy** 五种：
    - **NoBackOffPolicy**：无退避，重试时立即重试。
    - **FixedBackOffPolicy**：固定时间退避，参数 **sleeper**（默认 Thread.sleep）与 **backOffPeriod**（**默认 1 秒**）。
    - **UniformRandomBackOffPolicy**：随机时间退避，参数 sleeper、minBackOffPeriod、maxBackOffPeriod，在 `[min, max]` 间取随机休眠时间，**默认 500ms / 1500ms**。
    - **ExponentialBackOffPolicy**：指数退避，参数 sleeper、initialInterval（**默认 100ms**）、maxInterval（**默认 30 秒**）、multiplier（乘数，下一次休眠=当前×multiplier）。
    - **ExponentialRandomBackOffPolicy**：随机指数退避，**引入随机乘数**——"之前说过固定乘数可能会引起很多服务同时重试导致 DDoS，使用随机休眠时间来避免这种情况"。
14. 重试设计的四个重点：
    ① **要确定什么样的错误下需要重试**；
    ② **重试的时间和次数**——不同情况不同考量；对一些不太重要的问题，**应该更快失败而不是重试若干次**（如前端交互要用后端服务，遇到错误应快速失败报错"网络错误请重试"）；而对流控这类错误，**应该用指数退避，避免造成更多流量**；
    ③ 超过重试次数或一段时间后重试就没意义了，说明不是短暂错误，**对新请求直接返回错误**；但这样"后端恢复了我们怎么知道呢"——此时需要**熔断设计**；
    ④ 重试**还需要考虑被调用方是否有幂等的设计**；如果没有，**重试是不安全的**，可能导致同一操作被执行多次。
15. 不侵入业务的两种落法：① **代码级**——Java 用 Annotation（Spring），没有注解也可包装在底层库/SDK 里不让上层业务感知；② **走 Service Mesh 的方式**。
16. 长事务重试的做法：对有事务相关的操作，可能希望重试成功而不走业务补偿那样复杂的回退流程，于是**可能需要一个比较长的时间来做重试**；但**需要保存请求的上下文**，这对程序运行有比较大的开销，所以有些设计**先把上下文暂存在本机或数据库**，然后腾出资源做别的事，过一会再回来把之前的请求从存储里捞出来重试。

### 数字 / 公式 / 阈值
- 退避公式：`wait = min(2^retryCount, MAX_WAIT_INTERVAL)`；正文示例 **200ms → 400ms → 800ms**。
- 错误枚举 **5 种**（SUCCESS / NOT_READY / TOO_BUSY / NO_RESOURCE / SERVER_ERROR）。
- Spring 示例：`maxAttempts=2`、`delay=5000ms`。
- Spring 默认值：SimpleRetryPolicy **3 次**；TimeoutRetryPolicy **1 秒**；FixedBackOffPolicy `backOffPeriod` **1 秒**；UniformRandom `[500ms, 1500ms]`；Exponential `initialInterval=100ms`、`maxInterval=30s`、`multiplier` 可配。

### 一句话结论
熔断是"下游已经坏了先别打"的自动开关：用 **Closed / Open / Half-Open 三态机 + 失败率阈值 + 超时时钟** 把"等超时再失败"换成"立即失败"，半开只放少量探测防止二次雪崩；但熔断只省资源，不改善体验，必须配降级。

### 知识点全清单（A1 零丢失）
1. 灵感来源：**电闸上的"保险丝"**——电压有问题（如短路）时自动跳闸、电路断开、电器受保护；否则会烧坏电器，如果人没在家或熟睡中，还会导致火灾。所以电路世界通常都有这样的自我保护装置。
2. 为什么要熔断：前面讲过重试机制，**如果错误太多、或短时间内得不到修复，重试也没有意义**，此时应开启熔断；尤其**后端太忙时，熔断可以保护后端不过载**。
3. 熔断器模式的作用（原文定义）：防止应用程序不断尝试执行可能失败的操作，使应用继续执行而不用等待修正错误，或浪费 CPU 时间去等长时间的超时；**它也可以使应用能够诊断错误是否已经修正，如果已修正则再次尝试调用**。
4. 核心比喻：**熔断器模式就像是那些容易导致错误的操作的一种代理**——这个代理能记录最近调用发生错误的次数，然后决定允许操作继续，还是**立即返回错误**。（配图来自 Martin Fowler 的 Circuit Breaker）
5. 三态机之 **闭合（Closed）**：需要一个调用失败计数器，调用失败则失败次数 +1；**如果最近失败次数超过了在给定时间内允许失败的阈值，则切换到断开（Open）**，此时**开启一个超时时钟**；时钟超时后切换到**半断开（Half-Open）**。该超时时间的设定是**给系统一次机会来修正导致调用失败的错误**，以回到正常工作状态。
6. Closed 状态下**错误计数器是基于时间的**：在特定时间间隔内会自动重置——这能防止由于某次的偶然错误就导致熔断器进入断开状态；**也可以基于连续失败的次数**（两种统计口径）。
7. **断开（Open）**：对应用的请求**立即返回错误响应，而不调用后端服务**；这样也许比较粗暴，所以有时可以 **cache 住上次成功请求直接返回缓存**（**这个缓存放在本地内存就好了**），没有缓存再返回错误。缓存的使用边界：**最好用在全站一样的数据，而不是用在不同的用户间不同的数据**，因为后者需要缓存的数据可能会很多。
8. **半开（Half-Open）**：允许应用程序**一定数量的请求**去调用服务；如果这些请求调用成功，认为之前导致失败的错误已修正，**切换到闭合状态并重置错误计数器**；如果这一定数量的请求有失败，认为问题仍然存在，**切回断开状态，然后重置计时器**给系统时间修正错误。半开能**有效防止正在恢复中的服务被突然而来的大量请求再次拖垮**。
9. 熔断带来的四类收益：使系统更稳定、更有弹性；在系统从错误中恢复时提供稳定性；减少错误对系统性能的影响；**快速拒绝那些可能失败的服务调用，而不去等待操作超时或永远不返回结果，从而提高响应时间**。
10. 可观测性：如果熔断器**在每次状态切换时发出一个事件**，这种信息可用于监控服务运行状态，**通知管理员在切换到断开状态时处理**。
11. Netflix Hystrix 的开源实现逻辑（配流程图），四个要点：
    ① 有请求来了，首先 `allowRequest()` 判断是否在熔断中；不是则放行；是的话还要看**有没有到达一个熔断时间片**，到了也放行，否则直接返回出错；
    ② 每次调用都有两个函数 `markSuccess(duration)` 与 `markFailure(duration)`，统计一定 duration 内多少调用成功/失败；
    ③ 判断是否熔断的条件 `isOpen()`：计算 **`failure / (success + failure)`** 的当前错误率，**高于一个阈值就打开熔断，否则关闭**；
    ④ Hystrix 会在**内存中维护一个数组**，记录每一个周期的请求结果统计，**超过时长长度的元素会被删除**。
12. 熔断设计重点七条：
    ① **错误的类型**——请求失败原因有很多种，要按错误情况调整策略；熔断和重试一样**需要对返回的错误进行识别**；一些错误先走重试策略（如限流、超时），重试几次后再打开熔断；**一些错误是远程服务挂掉、恢复时间比较长，这种不必走重试就可以直接打开熔断**。
    ② **日志监控**——熔断器应能记录所有失败请求，以及一些可能会尝试成功的请求，使管理员能监控熔断器保护服务的执行情况。
    ③ **测试服务是否可用**——在断开状态下，熔断器可以**采用定期 ping 一下远程服务的健康检查接口**来判断服务是否恢复，**而不是使用计时器来自动切换到半开状态**；好处是服务恢复时**不需要真实用户流量**就能从半开切回闭合，否则即便服务已恢复也要靠用户真实请求来恢复，**这会影响用户的真实请求**。
    ④ **手动重置**——系统中失败操作的恢复时间很难确定，提供手动重置功能能让管理员**强制把熔断器切到闭合**；同样，如果受保护服务暂时不可用，管理员也能**强制把熔断器设置为断开**。
    ⑤ **并发问题**——同一熔断器可能被大量并发请求访问，实现**不应阻塞并发请求或增加每次请求调用的负担**；尤其对调用结果的统计一般是**共享数据结构**，会导致有锁；最好用**无锁数据结构或 atomic 原子操作**，性能更好。
    ⑥ **资源分区**——有时资源分布在不同的分区上（如数据库的**分库分表**），某个分区出问题而其它分区仍可用；此时**单一熔断器会把所有分区访问混为一谈**，一旦熔断所有分区都受影响，或出现"一会儿熔断一会儿又好"来回震荡的情况；所以**只对有问题的分区熔断，而不是整体**。
    ⑦ **重试错误的请求**——有时错误和请求的数据、参数有关，**记录下出错的请求，在半开状态下重试**能准确知道服务是否真的恢复；但**需要被调用端支持幂等**，否则会出现一个操作被执行多次的副作用。
13. 小结：熔断受电路保险丝启发；需实现三个状态（闭合、断开、半开），分别对应正常、故障、故障后检测是否修复；介绍了 Hystrix 的实现；最后是七个设计重点。

### 反例 / 坑 / 作者明确反对的做法
- 错误太多还继续重试（"重试也没有意义了"）。
- 断开时粗暴地只返回错误、不给缓存兜底（原文给了 cache 退路）。
- 把缓存用于"不同用户间不同的数据"（缓存量会爆炸）。
- 用计时器硬切半开、不主动探活（会让恢复依赖真实用户流量）。
- 统计用有锁的共享结构（高并发下熔断器自己成为瓶颈）。
- **一个熔断器管所有分区**（分库分表场景下一次故障全库熔断，或反复震荡）。
- 半开重放出错请求但不要求幂等（"否则会出现一个操作被执行多次的副作用"）。
