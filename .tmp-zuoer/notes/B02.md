## 10｜如何成为一个大家愿意追随的 Leader？
> 源文件 `.tmp-zuoer/txt/10丨如何成为一个大家愿意追随的Leader？.txt`，正文约 3300 字（含留言 4430 字）

### 一句话结论
Leader 与 Boss 的分水岭不在职位而在"人是否愿意跟"——影响力来自技术领导力 + 被信任 + 以身作则；原文用 **7 组行为对照** 和 **5 条非技术素质** 把"愿意追随"拆成了可观察的判据，最后一条硬指标是"终身写代码"。

### 知识点全清单（A1 零丢失）
1. 定义：Leader 不是管理者、不是经理、更不是职称，而是**领头人**。Leader 的影响力来自"大家愿意跟随的现象"，Boss 的领导力来自**职位和震慑**。
2. 通俗版：Leader 是"大家跟我一起上"，Boss 是"大家给我上"——一个在团队**前面**，一个在团队**后面**。
3. 7 组对照（原文逐条，缺一不可）：
   - **驱动 vs 指导**：Boss 制定时间计划、推动（push）和鞭策员工完成工作；Leader 和员工一起讨论工作细节、指导关注重点、一起规划出（work out）方向和计划，并在工作中一起解决细节难题、帮员工完成工作。
   - **制造畏惧 vs 制造热情**：Boss 用职位级别压人、用绩效考核制造威慑；Leader 通过**描绘远景、制造激动人心的目标**鼓舞团队。
   - **人事惩罚 vs 找方法**：Boss 不懂技术也不懂细节，只能用惩罚；Leader 是解决问题的技术型人才，深入技术细节，找**既治标又治本**的技术方案或管理方式。
   - **知道怎么做 vs 展示怎么做**：好 Leader 的最大特点是 Lead by Example，用**身教**而不是言传；Boss 只在大道理上说一套又一套，从不管技术细节。
   - **用人 vs 发展人**：Boss 把人当劳动力；Leader 看到潜力和特长，通过**授权、指导、制定成长计划**让员工成长。所以 Boss 总说员工有这个问题那个问题，Leader 总说如何让员工成长以解决其个人问题。
   - **收割成绩 vs 给予成绩**：Boss 把团队成绩占为己有（嘴上说团队功劳，但一句带过）；Leader 让团队成员站到台前，自己甘当**绿叶和铺路石**——只有每个人成功，团队才会成功。
   - **命令和控制 vs 沟通和协作**：Boss 用 Command + Control 让团队运转；Leader 用 Communication + Cooperation 增加**参与感**，让员工觉得"这是自己的事"。
4. "愿意追随"的三个征兆：① 有**技术领导力**——人们想跟随的通常是比自己强、比自己出色、能跟他学到东西、能跟他成长的人；② **帮人解决问题**——大家都在问"这个问题怎么办？"，你总能站出来告诉大家该怎么办；③ **被人依赖**——大家做较关键决定时会来找你咨询意见和想法。
5. 信任的两种含义：信任是人类一切活动的基础，人与人关系好不好完全基于信任。信任不只是"别人相信你能做到某个事"，还有"**别人愿意向你打开心扉，和你说他心里面最柔软的东西**"——后者才是真正的信任，它需要人格魅力、真诚、可信、价值观、情怀等诸多因素。
6. 案例一（信任的证据：猎头挖人）：下属被猎头或别的公司挖时会告诉作者并征求意见。作者除帮分析利弊，有时还**帮他们准备面试**，甚至**为下属介绍其它公司的工作机会**；并强调"不要误会我，我并不是不站在公司利益的角度，我这样做完全是站在公司利益的角度"。
7. 案例一的逻辑：世界很大，一个公司或 Leader 很难把人留一辈子，优秀的人更需要不同经历。"**既然做不到把人留一辈子，那么不妨把这件事做得漂亮一些**"——会让要离开的员工觉得这个 Leader / 公司的胸怀不一般，反而会想留下，或离开后又想回来。
8. 案例二（信任的证据：吐槽公司）：下属会来分享难处、彷徨、吐槽公司。下属一般不会找老板吐槽，因为这是办公室禁忌；但老板和经理其实都知道员工一定会吐槽。既然做不到不让吐槽，"**那么不妨让这件事做得更漂亮一些——可以公开透明地说，而不是在背后说**"，因为背后说对团队伤害更大。
9. 素质一：**开放的心态 + 倾向性的价值观**。看似矛盾其实不矛盾——对新生事物、对每个人的观点都要开放，但不是认同所有观点、不做油腔滑调的人；可以听进不同观点，再**根据自己的价值观做判断**，而不是不加判断全部采用。
10. 为什么 Leader 必须有倾向性：要做 Leader 就需要**明确的方向和观点**，而不是说"放之四海皆准的完全正确的废话"。作者自己的倾向：**不加班的文化、全栈、按职责分工而不是按技能分工、做 Leader 而不是 Boss、技术是第一生产力、OKR 而不是 KPI**。
11. 倾向性的作用：让别人更清楚你是什么样的人，不会对你琢磨不透；"一会东一会西只会让人觉得你太油了，反而会产生距离感和厌恶感"。**倾向性的价值观是别人是否可以跟随你的一个基础。**
12. 素质二：**Lead by Example**。用自己的行为展示 Leadership，给大家做示范。"道理人人都知道，但未必人人都会做，知易行难，以身示范，一个示例会比讲一万遍道理都管用。"
13. 由 Lead by Example 推出的硬结论：**"对于软件开发来说，不写代码的架构师是根本不靠谱的。"** 要做一个有人愿意跟随的技术 Leader，需要**终身写代码**，即 **ABC – Always Be Coding**。
14. ABC 的因果链：写代码 → 更多实际经验 → 非常明白一个技术方案的优缺点、实现复杂度、知道什么是 Best Practice → 方案更具执行力和实践性 → 获得更多成就 → 反过来让更多人跟随你。
15. 素质三：**保持热情和冲劲**。世界上有太多东西让人沮丧、不满、彷徨、迷茫、疲惫，而几乎所有人都不喜欢在这样的情绪里生活。
16. 热情的**反面清单**（作者明确划线）：保持热情不是自欺欺人，不是文过饰非；"掩耳盗铃、掩盖问题、强颜欢笑的方式根本不是热情"。**真正的热情是：正视问题、正视不足、正视错误，从中反思和总结得到更好的解决方案，不怕困难，迎难而上。**
17. 引用：鲁迅《记念刘和珍君》——"真的猛士，敢于直面惨淡的人生，敢于正视淋漓的鲜血"。
18. 素质四：**能够抓住重点，看透事物的本质**。世界太复杂，太多因素和杂音影响判断，绝大多数人会在多重因素中迷失或纠结；Leader 要能抓住**主要矛盾**、给出清楚的观点或方向、**简化复杂的事情**、传道解惑、开启民智，让人豁然开朗、醍醐灌顶。
19. 素质五：**描绘令人激动的方向，提供令人向往的环境**。每个人心中都有激动和理想，哪怕被现实摧残得最凶的人也只是暂时忘却；好的 Leader 一定会把每个人心中**最真善美的东西呼唤出来**，并让人相信这有机会有可能做到。
20. 素质六：**甘当铺路石，为他人创造机会**。别人愿意跟随你，部分原因是你能给别人带来更多可能性和机会，觉得和你在一起能成长、能进步、能被带到更远的地方。
21. 铺路石的哲学与类比："帮助别人其实就是帮助自己，成就他人其实也是在成就自己。这就像一个好的足球队一样，球队中的人都互相给队友创造机会，整个团队成功了，球队的每个人也就成功了。" Leader 要在团队中创造这种文化和风气。
22. 代价清单（原文结尾）：做一个好 Leader 真的不容易——你需要比大家强很多、比大家付出更多；需要**容天下难容之事**、保持热情和朝气；需要带领团队守护理想、直面困难迎刃而上。
23. 结尾态度：也许你不必做一个 Leader，但**如果你有想跟随的人，你应该去跟随这样的 Leader**。

## 11｜程序中的错误处理：错误返回码和异常捕捉
> 源文件 `.tmp-zuoer/txt/11丨程序中的错误处理：错误返回码和异常捕捉.txt`，正文约 4350 字（含留言 5781 字）

### 一句话结论
错误处理只有两种原语——返回码与异常；选型判据不是"底层还是上层"，而是"**这个错误该不该发生**"；无论选哪种，资源释放都必须绑在**作用域**上（goto fail / RAII / defer 三种写法一条判据），而 try-catch 的致命伤是**跨线程失效**。

### 知识点全清单（A1 零丢失）
1. 立论：把错误处理写好并不容易；任何稳定程序里都有**大量代码在处理错误**，所以值得系统讲（两篇）。
2. 传统方式（错误码）：C 语言用**函数返回值**标识是否有错，再配合**全局 `errno`** 变量 + 一个 `errstr` 数组告诉你为什么出错。
3. 为什么这样设计（两条动机，原文明确）：① **可以共用一些错误**码；② 更重要的是**这其实是一种妥协**——`read()` / `write()` / `open()` 的返回值本身要返回有业务逻辑的值。
4. 双语义问题：`open()` 成功返回文件句柄指针 `FILE*`，失败返回 `NULL`；调用者并不知道原因，必须**再查 `errno`** 才能正确处错。
5. 一般情况这样没问题，**例外**是"返回值空间被占满"的函数：`atoi()` 把字符串转整型，若传入非法字符串（如 `"ABC"`）或整型溢出，"这个函数应该返回什么呢？出错返回，返回什么数都不合理"——返回 0 会和正常的 `"0"` 完全混淆。
6. C99 规格说明书 §7.20.1 原文：`atof` / `atoi` / `atol` / `atoll` 这类函数"**need not affect the value of the integer expression errno on an error**"，且若结果无法表示，行为是 **undefined**。（原文引了英文原文）
7. libc 的补救：新增 `long strtol(const char *restrict str, char **restrict endptr, int base)`，出错时会设置全局变量 `errno`；用法 `long val = strtol(in_str, &endptr, 10); // 10 的意思是 10 进制`。作者评价："虽然 strtol() 解决了 atoi() 的问题，但我们还是能感觉到不是很舒服和自然。"
8. `strtol` 调用侧的三分支判据（原文代码，缺一不可）：① `if (endptr == str)` → `"No digits were found"` + exit；② `if (errno == ERANGE && (val == LONG_MAX || val == LONG_MIN))` → `"number out of range for LONG"` + exit；③ `if (errno != 0 && val == 0)` → `perror("strtol")` + exit。
9. 返回值 + errno 的**两个问题**：① 程序员一不小心就会忘记检查返回值，从而造成 Bug；② 函数接口**非常不纯洁**，正常值和错误值混淆在一起，语义有问题。
10. Windows 的 HRESULT：用统一错误返回值，可明确"成功还是错误"；代价是函数 input 和 output 只能通过参数完成，于是出现**入参 / 出参**之分——接口语义变得更复杂，"依然没有解决函数的成功或失败可以被人为忽略的问题"。
11. Go 的多返回值：很多函数返回 `result, err` 两个值；参数基本上就是入参，返回把结果和错误分离，**接口语义清晰**；error 要忽略必须**显式**用 `_`；`error` 是接口（只有一个 `Error()` 方法返回 string），所以可扩展自定义错误。
12. 自定义错误类型示例：`type SyntaxError struct { msg string; Offset int64 }` + `func (e *SyntaxError) Error() string { return e.msg }`（`Offset` 是"error occurred after reading Offset bytes"）。
13. Go 使用端（原文两段代码）：① 类型断言取位置——`if serr, ok := err.(*json.SyntaxError); ok { line, col := findLine(f, serr.Offset); return fmt.Errorf("%s:%d:%d: %v", f.Name(), line, col, err) }`；② 多类型分派——`switch err.(type) { case *json.SyntaxError: ...; case *ZeroDivisionError: ...; case *NullPointerError: ...; default: ... }`（这段示例来自 Go 官方文档《Error Handling and Go》）。
14. Go 的痛：`if err != nil` 简直是写到吐，只能在 IDE 里定义自动写这段代码的快捷键；正常的业务逻辑代码会被大量错误处理**打得比较凌乱**。
15. 资源清理三模式之一 `goto fail`：每一步错误都去清理前面已分配的资源，用 `#define FREE(p) if(p) { free(p); p = NULL; }` + 末尾 `fail:` 标签统一 `FREE(fname)/FREE(lname)/FREE(mname)` + `ReportError(ERR_NO_MEMORY)`。
16. `goto fail` 的**潜在问题**：你**不能在中间的代码中有 return 语句**，因为你需要清理资源；维护这类代码要格外小心，一不注意就会导致**资源泄漏**。
17. 资源清理三模式之二 C++ **RAII**（Resource Acquisition Is Initialization）：用 C++ 类机制，**构造函数中分配资源、析构函数中释放资源**。
18. RAII 的**反例**（原文完整代码，这是本节最有价值的一段）：`std::mutex m; void bad(){ m.lock(); f(); /* 若 f() 抛异常，则互斥绝不被释放 */ if(!everything_ok()) return; /* 提早返回，互斥绝不被释放 */ m.unlock(); }` —— 函数第三条语句提前返回，直接导致 `m.unlock()` 没被调用，**引起死锁**。
19. RAII 的正例：`class LockGuard { public: LockGuard(std::mutex &m):_m(m){ m.lock(); } ~LockGuard(){ m.unlock(); } private: std::mutex& _m; };` 使用 `LockGuard lg(m); f(); if(!everything_ok()) return;` —— 抛异常释放互斥、提早返回析构时释放、正常返回也释放。
20. 资源清理三模式之三 Go `defer`：`func Close(c io.Closer){ if err := c.Close(); err != nil { log.Fatal(err) } }`，主函数里 `r, err := Open("a"); defer Close(r)`，中间出错 `log.Fatalf` 也照样关闭。
21. 作者的偏好排序（就代码易读和干净而言）：**C++ 的 RAII > Go 的 defer > C 的 goto fail**。
22. try-catch-finally 的形态：正常的业务代码 / 每种异常的处理代码 / `finally` 里的资源清理代码，分门别类，"看上去非常干净"。
23. 反方：**有一些人明确表示不喜欢 try-catch 这种错误处理方式，比如著名的软件工程师 Joel Spolsky。**（原文仅此一句，未展开理由）
24. try-catch-finally 的 5 条好处（原文逐条）：① 函数接口在 input（参数）、output（返回值）以及错误处理上的**语义比较清楚**；② 正常逻辑代码与错误处理、资源清理代码**分开**，提高可读性；③ **异常不能被忽略**（要忽略也必须 catch 住，这是显式忽略）；④ 面向对象语言（如 Java）里异常是**对象**，可以实现**多态式的 catch**；⑤ 与状态返回码相比，异常让函数可以**嵌套调用或链式调用**（`int x = add(a, div(b,c));`、`Pizza p = PizzaBuilder().SetSize(sz).SetPrice(p)...;`）。
25. 异常的性能："这句话也对也不对"。**对**：一旦异常被抛出，函数也就跟着 return 了，程序需要处理**函数栈的上下文**，栈比较深时性能变得很慢。**不对**：异常抛出基本表明程序出错，程序绝大多数情况应在无异常下运行，异常是少数情况，**不影响正常处理的性能**。
26. 致命问题：try 语句块里的函数运行在**另外一个线程**，抛出的异常**无法在调用者线程被捕捉**——"这个问题就比较大了"。
27. 错误三大类之一——**程序的错误**：空指针、非法参数等，是我们自己程序的错误；要**记录下来、写入日志，最好触发监控系统报警**。
28. 三大类之二——**用户的错误**：Bad Request、Bad Format 等由用户不合法输入带来的错误，基本出现在用户 API 层（解析 XML/JSON、字段不合法）；需要**向用户端报错**让用户自己修正，然后正常执行，但**要做统计**（错误率），有利于改善软件或侦测恶意请求。
29. 三大类之三——**资源的错误**：请求资源时导致的错误（打开无权限文件、写文件出错、发文件到网络端发现网络故障）；属**程序运行环境**的问题；有的能处理有的不能（内存耗尽、栈溢出或关键性资源不能满足 → 只能停止运行甚至退出整个程序）。
30. 三类错误的期望差异：程序 Bug 是我们希望**杜绝**的；用户输入是我们**杜绝不了**的；环境错误是我们希望**可以恢复**的——通过**重试或妥协**（重建网络连接、重新打开一个新的文件）。
31. 由此得出的逻辑分类（判据）：**对于我们并不期望会发生的事，我们可以使用异常捕捉；对于我们觉得可能会发生的事，使用返回码。**
32. 落到三类上：程序中的错误 → 异常比较合适；用户的错误 → 返回码比较合适；资源类的错误 → **要分情况**，看这事是"不应该出现"还是"经常出现"。
33. 举例：函数参数传入的对象不应为 null，一旦传入 null 就可以抛异常（因为不期望总发生）；需要检查用户输入（如电子邮箱格式）用返回码更好。
34. 作者明确**反驳**的说法：有人说"偏底层的错误（空指针、内存不足）用返回码，上层业务逻辑错误用异常"——"这么说有一定道理，因为偏底层的函数可能用得更多一些。**但是我并不这么认为**"；正确姿势是**从场景上讨论**，先把错误分好类以简化问题。
35. 补充维度：除分类外还要从**程序设计角度**考虑——异常捕捉在编程上的好处比返回值好很多，用异常的代码更易读也更健壮；**返回码容易被忽略，所以用返回码的代码需要做好测试**才能得到更好的软件质量。
36. "某些情况下你只能使用其中一个"（三条硬约束）：① **C++ 重载操作符**时很难使用错误返回码，只能抛异常；② **异常捕捉只能在同步下使用**，异步模式下抛异常不行，需要通过检查**子进程退出码**或**回调函数**解决；③ **分布式**情况下调用远程服务只能看错误返回码（如 HTTP 返回码）。
37. 现实必然是混用：有时把**异常转成错误码**（如 HTTP 的 RESTful API），也会把**错误码转成异常**（如对系统调用的错误）。
38. 分层处置原则："报错的类型"和"错误处理"紧密相关；有些底层错误需要**自己处理掉**（如底层模块自动重建网络连接），有些错误需要**更上层业务逻辑**处理（如重建连接不成功后，降级用本地缓存还是直接报错给用户？）。
39. 最终结论：不同错误类型 + 不同错误处理 → 代码组织层面不同 → 用错误码还是异常，"主要还是看我们的错误处理流程以及代码组织怎么写会更清楚"。
40. 收尾：以上只在**同步编程世界**适用；异步世界两个主角（返回码、异常）都难以发挥威力（引出第 12 讲）。

## 12｜程序中的错误处理：异步编程以及我的最佳实践
> 源文件 `.tmp-zuoer/txt/12丨程序中的错误处理：异步编程以及我的最佳实践.txt`，正文约 3100 字（含留言 4178 字）

### 一句话结论
异步世界把返回码和异常**同时废掉**（返回语义变了、栈跨了线程），错误只能沿数据流传播：回调 → Promise → async/await → CompletableFuture，五条演进路径收敛到同一个机制——**让错误短路后续步骤**；而 16 条最佳实践里真正撑住质量的是"错误字典 + 严重程度 + 日志用错误码 + 不在高频/大范围 try"。

### 知识点全清单（A1 零丢失）
1. 异步的两个前提变化（原文逐条）：① **无法使用返回码**——函数"被"异步运行，"所谓的返回只是把处理权交给下一条指令，而不是把函数运行完的结果返回"，返回的语义完全变了；② **无法使用抛异常**——除了函数立马返回，抛出的异常也在**另外一个线程**中，**不同线程中的栈是完全不一样的**，主线程的 catch 完全看不到。
2. 最常用的解法：**callback** 方式——做异步请求时注册几个 `OnSuccess()`、`OnFailure()` 这样的函数，让在另一个线程中运行的异步代码回调过来。
3. JS 示例：`function successCallback(result){...}` / `function failureCallback(error){...}` / `doSomething(successCallback, failureCallback);`；作者评价：出错语义"从返回码、异常捕捉到了**直接耦合错误出处函数**的样子，挺好的"。
4. 回调的问题：当需要把几个异步函数**顺序执行**时（异步程序执行顺序**不可预测、不确定**，而有时函数被调用的上下文**相互依赖**，所以希望它们按一定顺序处理），就出现 **Callback Hell**：`doSomething(function(result){ doSomethingElse(result, function(newResult){ doThirdThing(newResult, function(finalResult){...}, failureCallback); }, failureCallback); }, failureCallback);`。
5. Callback Hell 的代价：层层嵌套中需要注册的错误处理函数**也有可能是完全不一样的**，代码非常混乱，难以阅读和维护。
6. Promise 的形态（箭头表达式）：`doSomething().then(result => doSomethingElse(result)).then(newResult => doThirdThing(newResult)).then(finalResult => {...}).catch(failureCallback);`；`then()` 把各异步函数**串联**起来，`catch()` 是出错处理。
7. Promise 的实现要求：`doSomething()` 要**返回 Promise 对象**。示例内部用 `XMLHttpRequest`（`xhr.open('GET', url, true)`）：`xhr.onload` 里 `if (this.status === 200) { results = JSON.parse(this.responseText); promise.resolve(results); }`；`xhr.onerror` 里 `promise.reject(e);`；最后 `xhr.send(); return promise;`。
8. Promise 的错误传播语义（关键）：成功要调 `Promise.resolve()`，对象会**继续调用下一个 `then()`**；出错就调 `Promise.reject()`，**忽略后面的 `then()` 直到 `catch()`**。"`Promise.reject()` 就像是抛异常一样"——这个模式让代码组织方便很多。
9. Promise 并发：同时等待两个不同异步方法——`promise1 = doSomething(); promise2 = doSomethingElse(); Promise.when(promise1, promise2).then(function(result1, result2){...}, handleError);`。
10. ECMAScript 2017 的 `async/await`：函数定义前加 `async` 就能在函数内使用 `await`；`await` 某个 Promise 时，**函数暂停执行直至该 Promise 产生结果，并且暂停不会阻塞主线程**；若 Promise resolve 则返回值，若 reject 则**抛出拒绝的值**。
11. async/await 的意义：异步代码完全可以放进一个 `try - catch` 语句块，"在有语言支持了以后，我们又可以**使用 try-catch** 语句块了"。
12. pipeline：把一串函数**编排**起来形成更强大的功能（函数式编程常用）。递进四步：① `[func1, func2].reduce((p, f) => p.then(f), Promise.resolve());` ② 等同于 `Promise.resolve().then(func1).then(func2);` ③ 抽象成 `let applyAsync = (acc,val) => acc.then(val); let composeAsync = (...funcs) => x => funcs.reduce(applyAsync, Promise.resolve(x));` ④ 使用 `let transformData = composeAsync(func1, asyncFunc1, asyncFunc2, func2); transformData(data);`。
13. async/await 下的 pipeline 退化：`for (let f of [func1, func2]) { await f(); }`——"这事儿就变得更简单了"。
14. Java（JDK 1.8）的 Promise：`CompletableFuture` 提供大量异步编程中 Promise 的各种方式。
15. 链式处理：`CompletableFuture.supplyAsync(this::findReceiver).thenApply(this::sendMsg).thenAccept(this::notify);`——`supplyAsync()` 执行一个异步方法，`thenApply()` 成功后串联另一个异步方法，`thenAccept()` 处理最终结果。
16. 合并两个异步结果：`String result = CompletableFuture.supplyAsync(() -> "hello").thenCombine(CompletableFuture.supplyAsync(() -> "world"), (s1, s2) -> s1 + " " + s2).join(); System.out.println(result);`。
17. Java 的异常处理方式一 `exceptionally()`：`CompletableFuture.supplyAsync(Integer::parseInt).thenApply(r -> r * 2 * Math.PI).thenApply(s -> "apply>> " + s).exceptionally(ex -> "Error: " + ex.getMessage());`，与 JS Promise 的 `catch()` 相似。运行输出：`Error: java.lang.NumberFormatException: For input string: "ILLEGAL"`。
18. Java 的异常处理方式二 `handle()`：`handle((result, ex) -> { if (result != null) return result; else return "Error handling: " + ex.getMessage(); })`——**同时**拿结果与异常。
19. Go 的 Promise（纯示例）：结构体三成员——`wg sync.WaitGroup`（多线程同步）、`res string`（执行结果）、`err error`（错误）。
20. `NewPromise(f func() (string, error)) *Promise`：`p.wg.Add(1)` → `go func(){ p.res, p.err = f(); p.wg.Done() }()` → 返回 p。
21. `Then(r func(string), e func(error)) *Promise`：`go func(){ p.wg.Wait(); if p.err != nil { e(p.err); return }; r(p.res) }()`——被唤醒后**第一件事检查上一个方法有没有错误**，有错就调错误处理函数，成功则把结果以参数传给下一个函数。
22. 测试用异步方法 `exampleTicker()`：循环 3 次打印 i 并 `<-time.Tick(time.Second * 1)`；`rand.Seed(time.Now().UTC().UnixNano())`；`r := rand.Intn(100)%2`；`r != 0` 返回 `("hello, world", nil)`，否则返回 `("", fmt.Errorf("error"))`——即**约一半概率出错**。
23. 使用示例：`main()` 里 `doneChan := make(chan int)`、`p := NewPromise(exampleTicker)`、`p.Then(func(result string){ fmt.Println(result); doneChan <- 1 }, func(err error){ fmt.Println(err); doneChan <- 1 })`、`<-doneChan`。
24. 作者自评：Go 这个实现"比较简陋，仅仅是为了说明问题"；想要更好的代码可去 GitHub 搜 Go 语言 Promise 相关库。
25. **最佳实践 1：统一分类的错误字典**——无论用错误码还是异常，都要认真并统一地做好错误分类，**最好在一个地方定义**相关的错误（如 HTTP 4XX 表示客户端有问题、5XX 表示服务端有问题）。
26. **实践 2：同类错误的定义最好可扩展**——"这一点非常重要"，通过面向对象的继承或 Go 那样的接口多态可以很好做到，方便重用已有代码。
27. **实践 3：定义错误的严重程度**——**Fatal** 表示重大错误；**Error** 表示资源或需求得不到满足；**Warning** 表示并不一定是个错误但还是需要引起注意；**Info** 表示不是错误只是一个信息；**Debug** 表示这是给内部开发人员用于调试程序的。
28. **实践 4：错误日志的输出最好使用错误码，而不是错误信息**——打印错误日志应该用统一格式；错误码**不一定是数字**，也可以是一个能从错误字典里找到的、唯一的、让人读懂的关键字，这样**非常有利于日志分析软件做自动化监控**，而不是要从错误信息中做语义分析。例：HTTP 日志里有返回码 404，但"我更推荐使用像 `PageNotFound` 这样的标识，这样人和机器都很容易处理"。
29. **实践 5：忽略错误最好有日志**——不然会给维护带来很大的麻烦。
30. **实践 6：对于同一个地方不停的报错，最好不要都打到日志里**——会导致其它日志被淹没、日志文件太大；最好的实践是"**打出一个错误以及出现的次数**"。
31. **实践 7：不要用错误处理逻辑来处理业务逻辑**——不要用异常捕捉处理业务逻辑，而应用**条件判断**；"如果一个逻辑控制可以用 if-else 清楚地表达，那就不建议使用异常方式处理"；异常处理不期望发生的事，错误码处理可能发生的事。
32. **实践 8：对于同类的错误处理，用一样的模式**——如 null 对象的错误，要么都返回 null + 条件检查，要么都抛 `NullPointerException`，**不要混用**，有助于代码规范。
33. **实践 9：尽可能在错误发生的地方处理错误**——这样会让调用者变得更简单。
34. **实践 10：向上尽可能地返回原始的错误**——如果一定要把错误返回到更高层处理，应该返回**原始的错误**，而不是重新发明一个错误。
35. **实践 11：处理错误时，总是要清理已分配的资源**——"这点非常关键"，用 RAII、try-catch-finally 或 Go 的 defer 都容易做到。
36. **实践 12：不推荐在循环体里处理错误**（指 try-catch）——"绝大多数的情况你不需要这样做"，最好把整个循环体放在 try 语句块内，在外面做 catch。
37. **实践 13：不要把大量的代码都放在一个 try 语句块内**——一个 try 块内的语句应该是**完成一个简单单一的事情**。
38. **实践 14：为你的错误定义提供清楚的文档以及每种错误的代码示例**——做 RESTful API 用 **Swagger** 会很容易搞定。
39. **实践 15：对于异步的方式，推荐使用 Promise 模式处理错误**——JavaScript 中有很好的实践。
40. **实践 16：对于分布式的系统，推荐使用 APM 相关的软件**——尤其是用 **Zipkin** 这样的服务调用跟踪的分析来关联错误。

## 13｜魔数 0x5f3759df
> 源文件 `.tmp-zuoer/txt/13丨魔数0x5f3759df.txt`，正文约 2850 字（含留言 3502 字）

### 一句话结论
那段 `// what the fuck?` 的代码不是魔法，而是三件事的拼接——**IEEE 754 的位表示** + **对数在 [0,1] 上的线性近似** + **牛顿迭代精化**；魔数 `0x5f3759df` 只是 σ≈0.0450465 的编码，它的"最优性"至今无人能证明，作者是谁也查不清。

### 知识点全清单（A1 零丢失）
1. 代码出处：《雷神之锤 III 竞技场》（Quake III Arena）源代码中的一个函数（已剥离 C 语言预处理器指令），即 `Q_rsqrt(float number)`。
2. 传播史：最早在 **2002 年（或 2003 年）** 就出现在 Usenet 与其他论坛上，在程序员圈子里引起热烈讨论。
3. 完整代码（12 行，逐行保留）：`float Q_rsqrt(float number){ long i; float x2, y; const float threehalfs = 1.5F; x2 = number * 0.5F; y = number; i = * ( long * ) &y; // evil floating point bit level hacking; i = 0x5f3759df - ( i >> 1 ); // what the fuck?; y = * ( float * ) &i; y = y * ( threehalfs - ( x2 * y * y ) ); // 1st iteration; // 2nd iteration, this can be removed; // y = y * ( threehalfs - ( x2 * y * y ) ); return y; }`
4. 初读体验（作者自述）："完全不知所云，尤其是那个魔数 0x5f3759df，根本不知道它是什么意思，所以，注释里也是 What the fuck。"
5. 函数作用：求**平方根倒数**，即 `x^(-1/2)` = `1/√x`；算的是**近似值**，但精度很高，计算成本比传统的浮点数平方根算法低太多。
6. 场景：以前计算资源不充分的年代，3D 游戏计算机图形学求**照明和投影的光照与反射**效果，需要大量计算平方根倒数——对曲面上很多点算 `1/√(x²+y²+z²)`（x,y,z 是 3D 坐标的三个坐标值）。
7. 量级：一个 3D 游戏里**每秒钟都需要做上百万次**平方根倒数运算；计算硬件不成熟时代这些计算都要软件完成，速度非常慢。
8. 时代背景：上世纪 **90 年代**，多数浮点数操作的速度远远滞后于整数操作——所以这段代码带来的作用非常大。
9. IEEE 754 单精度：把一个 **32 bits** 分成三段——**S 符号位 1 bit**、**E 指数位 8 bits**、**M 尾数位 23 bits**。
10. 取值公式：`(-1)^S * (1 + M/2^23) * 2^(E-127)`（原文图示公式）。
11. 符号位：正数 S = 0（原文"对于这一段，我相信应该没有人不能理解"）。
12. 指数位：对任何数 x 都能找到 n 使 `2^n <= x <= 2^(n+1)`（例：2 < 3 < 4 故 n=1）；8 bits 本可表示 0–255，为了表示 0.00x 的小数需要负数，所以取值放在 **[-127, 128]** 区间——这就是公式里 `2^(E-127)` 的由来；即 `n = E - 127`，n=1 时 E=128。
13. 尾数位：取值 `[0, 2^23]`；可以认为把 `[2^n, 2^(n+1)]` 这条线分成 **8388608（2^23）个线段**，存储的 M 就是"从 2^n 到 x 经过了多少段"，即 `(x - 2^n) / (2^(n+1) - 2^n)` 的比例乘以 2^23。
14. 例 3.14（完整算例）：S=0（正数）；`2^1 < 3.14 < 2^2` → n=1 → E=128；`(3.14 - 2)/(4 - 2) = 0.57`，`0.57 * 2^23 = 4781506.56`，四舍五入 **M = 4781507**；回算 `1 * (1 + 0.5700000524520874) * 2 = 3.1400001049041748046875`——"你看，浮点数的精度问题出现了。"
15. 例 0.015（完整算例）：S=0；`2^-7 < 0.015 < 2^-6` → n=-7 → E=120（二进制 `01111000`）；`(0.015 - 2^-7)/(2^-6 - 2^-7) = 0.0071875/0.0078125 = 0.92`；`0.92 * 2^23 = 7717519.36` → 四舍五入 **M = 7717519**（二进制 `11101011100001010001111`）；回算 `(1 + 0.919999957084656) * 0.0078125 = 0.014999999664724`——"浮点数的精度问题又出现了。"
16. lldb 验证（作者在 Mac 上实测）：`x = 3.1400001` → `0b01000000010010001111010111000011`；`y = 0.0149999997` → `0b00111100011101011100001010001111`，"从结果上，完全验证了我们的方法"。
17. 公式简化：令 `m = M/2^23`、`e = E - 127`，符号位在正数两端都是 0 可去掉 → `y = (1 + m) * 2^e`。
18. 32 bits 整型算式：`I = M + E * 2^23`；例 0.015 的二进制 `00111100011101011100001010001111`（首位符号位去掉后）对应整型 **1014350479 = 0x3C75C28F**。
19. 推导起点：`y = 1/√x = x^(-1/2)`；两边取以 2 为基的对数 → `log2(y) = -(1/2) * log2(x)`。
20. 代入浮点简化式：把 x、y 分别写成 `(1+m)*2^e` 的形式，得 `log2(1+m_y) + e_y = -(1/2)[log2(1+m_x) + e_x]`。
21. 关键近似：`m` 是 [0,1] 区间内的小数，此时 `log2(1+m)` **接近一条直线**，于是 `log2(1+m) ≈ m + σ`（σ 是待定常数）。
22. 代入并移项：`M_y/2^23 + σ + E_y - 127 ≈ -(1/2)(M_x/2^23 + σ + E_x - 127)`；把 σ 和 127 移到右边，整个表达式乘以 **3/2 * 2^23**，得 `M_y/2^23 + E_y ≈ -(1/2)(M_x/2^23 + E_x) - (σ - 127) * (3/2) * 2^23`。
23. 得到线性关系：把 `(127 - σ) * (3/2) * 2^23` 记作常量 **R**，则 `I_y ≈ R - (1/2) * I_x`——"这就是我们上面推导出来的那个公式"。
24. 代码对应一：`i = *(long*)&y` 就是把浮点数的 32 bits 二进制**转成整型**（例：3.14 → 1078523331；0.015 → 1014350479）。
25. 代码对应二：`i = 0x5f3759df - (i >> 1)` 即 `i = 0x5f3759df - i/2`，也就是 `I_y ≈ R - I_x/2`，其中 **R = 0x5f3759df**。
26. 反解 σ：由 `R = (127 - σ) * (3/2) * 2^23` 代入魔数得 **σ ≈ 0.0450465**——"这个数是个神奇的数字，这个数是怎么算出来的，现在还没人知道"。
27. 牛顿求根法（原理）：为找到 `f(x) = 0` 的根，用不断逼近的方式——初始值 X0，求 `Y0 = f(X0)`，在 `(X0, Y0)` 点做**切线**，与 X 轴交于 X1；再用 X1 迭代得 X2，如此下去直到 y=0。
28. 牛顿法通用公式：`x_{n+1} = x_n - f(x_n) / f'(x_n)`（`f'(x_n)` 是 f 关于 x 的导数）。
29. 迁移到平方根倒数：对固定的 x（常数）求 y 使 `1/y² - x = 0`，即 `f(y) = 1/y² - x`，`f'(y) = -2y^(-3)`。
30. 代入通用公式化简：`y_{n+1} = y_n - (1/y_n² - x)/(-2/y_n³) = y_n(3 - x*y_n²)/2 = y_n(1.5 - 0.5*x*y_n²)`——"正好就是我们上面的代码"（`y * (threehalfs - (x2 * y * y))`，`x2 = number * 0.5`）。
31. 两段式结构：**整数操作产生首次近似值**，再把首次近似值送进最后两句做**精化（牛顿迭代）**；两次迭代是为了进一步提高精度，但 QtIII 图形计算不需要太高精度，所以代码只做**一次**迭代，第二次被注释掉。
32. 历史一：据 Wikipedia，QtIII 代码直到 **QuakeCon 2005** 才正式放出；但 2002（或 2003）年平方根倒数速算法已在 Usenet 和其他论坛出现。
33. 历史二（作者归属链）：最初人们猜是 Qt 创始人 **John Carmack**，他在回邮件时**否定了这个观点**，并猜测可能是曾帮 id Software 优化 Qt 的资深汇编程序员 **Terje Mathisen**。
34. 历史三：Mathisen 邮件表示 1990 年代初他只做过**类似的实现**，确切来说这段代码亦非他所作。
35. 历史四：现在所知**最早的实现**是由 **Gary Tarolli** 在 **SGI Indigo** 中实现的，但他亦坦承仅对常数 R 的取值做了**一定改进**，实际也不是作者。
36. 历史五：向以发明 MATLAB 闻名的 **Cleve Moler** 查证后，**Rys Sommefeldt** 认为原始算法是 **Ardent Computer** 公司的 **Greg Walsh** 所发明，但也没有任何确定性证据。
37. 魔数之谜一：不仅原作者不明，"人们也仍无法确定当初选择这个魔术数字的方法"。
38. 魔数之谜二（Chris Lomont 的两次搜索）：他推算出误差函数，先找**使误差最小的最佳 R = 0x5f37642f**（与 0x5f3759df 相当接近）；但代入算法做**一次**牛顿迭代后，精度**仍略低于** 0x5f3759df。于是他把目标改为"查找在进行 **1–2 次**牛顿迭代后能得到最大精度的 R"，**暴力搜索**得出最优 R = **0x5f375a86**，以此代入做牛顿迭代，结果都比原值更精确。
39. Lomont 的追问（原话）："如果可能我想询问原作者，此速算法是以数学推导还是以反复试错的方式求出来的？"
40. 双精度对应魔数：Lomont 指出 64 位 IEEE754（双精度）对应魔数是 **0x5fe6ec85e7de30da**；但后来研究表明代入 **0x5fe6eb50c7aa19f9** 结果精确度更高；**McEniry** 得出的结果是 **0x5fe6eb50c7b537aa**（精度介于两者之间）。
41. McEniry 的方法与结论：用类似 Lomont 但**更复杂**的方法优化 R；最初穷举搜索，结果与 Lomont 相同；后来改用**带权二分法**，所得结果**恰是代码中的 0x5f3759df**。因此他认为这一常数最初或许是以"**在可容忍误差范围内使用二分法**"的方式求得。
42. 收尾："这可能是编程世界里最经典的魔数的故事"；数学是需要努力学好的一门功课，尤其在人工智能火热的今天。

## 14｜推荐阅读：机器学习 101
> 源文件 `.tmp-zuoer/txt/14丨推荐阅读：机器学习101.txt`，正文约 3450 字（含留言 4476 字）

### 一句话结论
机器学习只有两条路——**有标签的监督式**与**无标签的非监督式**，方法论都是"找特征点 → 抽象成向量 → 建模（或配权重）"；这篇是**入门资源清单**（4 课 + 6 书 + 若干博客），技术含量集中在前 1/3 的范式与方法论。

### 知识点全清单（A1 零丢失）
1. 作者背景与立场：2012 年在亚马逊第一次接触机器学习（一个关于预测商品需求的 **Demand Forecasting** 项目），此后一直用零星时间学习；"在机器学习方面，我也只是一个新手，也在入门阶段"。
2. 写作动机：评论区有网友希望写大数据和机器学习的文章，"老实说，有点为难我了"，所以只写一篇**入门级**文章，希望得到高手指教。
3. 两大方法：**监督式学习（Supervised Learning）** 与 **非监督式学习（Unsupervised Learning）**。
4. 监督式定义：需要提供一组**学习样本**，包括相关的**特征数据**以及相应的**标签**；程序通过样本学习规律或模式，再用规律/模式判断**没有被打过标签**的数据是什么。
5. 手写数字例子：找尽可能多的手写体数字图像样本，人工或通过算法明确标注谁是 1、2、3……这组数据叫**样本数据**，又叫**训练数据（training data）**；算法找到每个数字在不同手写体下的特征 → 规律和模式 → 识别未打标签的手写数据。
6. 常见监督式用途：从历史数据获得数据走向趋势来**预测未来**——用历史股票走势预测股价涨跌；用历史垃圾邮件样本识别新垃圾邮件。
7. 监督式的**问题**：需要有样本数据或历史数据才能学习；**如果一个事物没有历史数据，就不好做了**。
8. 变通解法：通过**和其类似事物**的历史数据。作者做过的需求预测即此类——新上市商品（如 **iPhone X**）完全没有历史数据，就要从类似商品（如 **iPhone 7** 或其他智能手机）上找历史数据。
9. 噪音数据必须过滤，一般靠**人工判断和标注**。两个对照例子：
   - **噪音（要去掉）**：某名人在微博或演讲上推荐一本书导致销量上升——这段时间的历史数据不是规律性的，不能作为样本数据。
   - **不是噪音（要保留并标注）**：某名人（如 **Michael Jackson**）去世导致相关商品销量很好——因为每年这个名人**忌日**时出现销量上升的可能性非常高，所以需要标注"这是有规律的样本"，可以放入样本学习。
10. 非监督式定义：数据**没有被标注过**，算法需要找到这些数据中的**共性**；因为大量数据没有被标识，这种方式可以让大量未标识的数据更有价值。
11. 非监督式的两个价值：① 能找到**人类很难发现**的数据里的规律或模型，所以也有人称之为"**特征点学习**"；② 可以让我们**自动为数据分类**，并找到分类的模型。
12. 非监督式应用一（交易型数据）：一堆用户购买数据，人类很难找到"用户属性"与"购买商品类型"之间的关系，非监督算法可以帮助找到。例：某年龄段区间的女生购买了某种肥皂，有可能说明这个女生在**怀孕期**；某人购买儿童用品，有可能说明这个人的**关系链中有孩子**——这些信息被用于**精准市场营销**，从而增加销量。
13. 一句话对比（原文金句）："监督式学习是在**被告诉过正确的答案之后**的学习，而非监督式学习是在**没有被告诉正确答案时**的学习。"非监督式是在大量非常混乱的数据中找寻潜在关系，**成本也比较高**。
14. 非监督式应用二：检测不正常的事情发生（**信用卡诈骗、盗刷**）；推荐系统（买了这个商品的人又买了别的什么；喜欢某篇文章/音乐/餐馆的人可能喜欢某款车/明星/地方）。
15. 狗照片类比：监督式下用一组"狗"的照片确定某张照片中的物体是不是狗；非监督式下通过一张照片找到**与其相似事物**的照片。两种方式各有适用场景。
16. 数学基础：需要一定数学知识，但入门者学好**高数、线性代数、概率论、数据建模**等本科数学应该就够用。作者感慨："以前上大学时，总觉得这些知识没什么用处，原来只不过是自己太 low，还没有从事会运用到这些知识的工作。"
17. 基本方法论（三步）：① 要找到数据中的规律，需要找到数据中的**特征点**；② 把特征点**抽象成数学中的向量**，也就是坐标轴（一个复杂的学习可能有**成十上百**的坐标轴）；③ 抽象成向量后，用某种**数学公式**表达这类数据（就像 `y=ax+b` 是直线的公式），这就是**数据建模**——"这个数据公式就是我们找出来的规律"，通过规律才能关联类似的数据。
18. 更简单粗暴的玩法（三步）：① 把特征点抽象成向量；② **每个向量一个权重**；③ 写个算法来找各个向量的权重。有人叫它"**数据搅拌机**"；据说这种简单粗暴的方式**超过了**那些明确的数学公式或规则——"这种'土办法'有时候会比高大上的数学更有效"。
19. 延伸阅读：**Machine Learning is Fun!** 及其中文翻译版。
20. 监督式经典算法 6 个（含用途）：① **决策树（Decision Tree）**——自动化放贷、风控；② **朴素贝叶斯分类（Naive Bayesian classification）**——判断垃圾邮件、新闻类别分类（科技/政治/运动）、判断文本情感（积极/消极）、人脸识别；③ **最小二乘法（Ordinary Least Squares Regression）**——算是一种线性回归；④ **逻辑回归（Logistic Regression）**——强大的统计学方法，用一个或多个变量表示**二项式结果**，用于信用评分、计算营销活动成功率、预测产品收入；⑤ **支持向量机（SVM）**——基于图像的性别检测、图像分类；⑥ **集成方法（Ensemble methods）**——构建一组分类器，根据它们的预测结果**加权投票**对新的数据点分类；原始的集成方法是**贝叶斯平均**，近期算法包括**纠错输出编码、Bagging、Boosting**。
21. 非监督式经典算法 4 个：① **聚类算法（Clustering Algorithms）**——有很多种，目标是给数据分类；② **PCA 主成分分析**——应用包括压缩、简化数据、便于学习和可视化；③ **SVD 奇异值分解**——"实际上 PCA 是 SVD 的一个简单应用"；计算机视觉中**第一个人脸识别算法**用 PCA + SVD 把面部表示为"**特征面**"的线性组合、进行降维，再通过简单方法匹配身份；现代方法更复杂，但很多方面仍依赖类似技术；④ **ICA 独立成分分析**——统计技术，主要用于揭示随机变量、测量值或信号集中的**隐藏因素**。

## 15｜时间管理：同扭曲时间的事儿抗争
> 源文件 `.tmp-zuoer/txt/15丨时间管理：同扭曲时间的事儿抗争.txt`，正文约 3470 字（含留言 4908 字）

### 一句话结论
时间管理的第一性问题不是"挤时间"，而是**夺回主动权**——主动管理（让别人知道你的日程、把信息收进邮件）、**学会说"不"**（Never Say No，但要"有条件地说是"）、把会议从"议题"改成"议案"；而在恶劣环境里，"优雅地行动"本身是不可能的。

### 知识点全清单（A1 零丢失）
1. 前提：时间是人生中最宝贵的财富；作者在外企受过**专门的时间管理培训**，后来也总结了自己的方式。
2. 痛点：时间过得太快，"看似忙碌的我们似乎在这一年中也没有做太多事，尤其是让自己能成长的事情"。
3. 公平性论点："老天很公平，给了所有人同样多的时间"，有的人能把时间用好、有的人没有；**日积月累，人和人的差距就越来越大了**。
4. 环境对比（作者成长的"比较好的环境"）：那个年代**没有智能手机**，工作中也不用实时聊天工具。
5. 那个年代的工作流：别人要找你开会需要**先发会议邀请**，且会先找你**日历上空闲的时间段**来确定会议时间；你可以把很多工作安排在日历上，通过邮箱（**Outlook 或 Gmail** 都有此功能）**共享出去**，别人会自觉绕开你有安排的时间段。
6. 今天的落差（三条批评）：① 很多公司直接在微信上联系，回复慢了电话直接打过来、直接叫你去开会；② 不像那个年代，**老板临时给员工开会也要问一下员工有没有时间**，现在"连问都不问，直接一句，你来一下"；③ 很多公司有若干聊天群，**所有人都可以把信息发给所有人**，而不管这个事是否与你相关。
7. 信息环境恶化的机制：这些信息**无法像邮件那样根据标题聚合**，或通过设置规则**自动分类**——于是你工作在"一个信息杂乱无章的环境里，而且还在不断地被人打扰，不断地被人打断"。
8. 组织级时间管理（路透）：管理者说"你工作时如果有 **70%** 的时间能花在项目开发上，算是很高效了，一般来说，正常值也就是 **50%** 左右"。
9. 组织级时间管理（亚马逊会议法）：每次开会把会议中要讨论的事**打印出来**，**前 10 分钟大家都在读文档**，然后直接讨论，所以会议基本保持在**半小时左右**。
10. 外企从上到下的共识：都认为时间管理很重要，从管理层到执行层都会想方设法帮程序员专注做好开发——**尽可能不开会、不开长会**；需求和设计要**论证很久**才决定做不做；项目管理会把你处理**额外工作**的时间也算进去，还会把你在**学习**上花的时间计算进去。
11. 作者的对比判断："时间在整个组织上能够被有效地管理和安排着。完全不像今天国内的互联网公司。"
12. 主动管理总原则：**无论什么事情，如果你发现你持续处于被动的状态下，那么你一定要停下来想一想如何把被动变为主动**；"因为在被动的方式下工作，你是不可能做好工作的，无论什么事"。作者自称非常不喜欢被动，对任何被动状态都要"**反转控制**"，想尽一切方式变成主动。
13. 主动管理手段 1：如果你发现时间老是被别人打断，就告诉大家"我什么时间段在做什么事，请大家不要打扰我"。
14. 主动管理手段 2（条幅）：作者在国外看到有个老外在自己工位上挂条幅，写着"**正在努力写代码中，请勿打断……**"。
15. 主动管理手段 3（WFH）：亚马逊允许员工想沉浸于工作时**不用来公司、可以在家办公（work from home）**。
16. 主动管理手段 4（换工位）：作者在阿里时怕被打断，会**跑到别的楼里找个空的工位**工作。
17. 主动管理手段 5（群里声明 + 人肉 Mute）：在群里事先告诉大家"我在几点到几点要无间断地做某个事，这个期间不会看任何微信或是钉钉的群聊，也不会接任何的电话"，并可以学那个老外挂条幅——"**人肉 Mute 掉所有的打扰**"。
18. 主动管理手段 6（共享日历）：仿照 Outlook 里设置工作日程的方式，把工作安排预先设置到一个**可以共享的日历**上分享给大家，让同事和老板"能事先有个谱儿，而不至于想打断你就打断你"。
19. 主动管理手段 7（渠道升级）：甚至可以要求同事"**重要的事，不要发微信，而是要发邮件**"，因为微信有很大概率看不到；这样你就再也不用在一大堆聊天信息中做"**人肉的大数据挖掘**"来找到和你有关的信息。
20. 信息管理的价值：信息做好分类，才方便检索、方便按自己的优先级处理；"而目前看来，这些**只有邮件**才能够更好地完成"（按标题聚合、设置规则自动分类、自动回复）。
21. 核心翻转（金句）："换句话说，你要**主动管理的不是你的时间，而是管理你的同事，管理你的信息**。"
22. 说"不"的必要性：主动管理只能让你有大块专注工作的时间，**并不能解决时间不够的问题**；现在很多公司把工作安排得非常紧，"今天提的需求，恨不得明天就上线"，这也是为什么今天加班比作者那时候更严重。
23. 尖锐批评："我认为，现在的很多公司已经不尊重科学和客观规律了，如果让他来管理孕妇，我觉得他们恨不得要把 **10 个月**的产期缩短成 **2 个月**。"
24. 定位：你要学会对某些事说"不"，甚至要学习**对老板说不**——"这其实是一种'**向上管理**'的能力"。
25. 培训悖论：外企管理培训有一条"**Never Say No**——永不说不"。的确，说"不"会让人产生距离和不信任，所以永远不要说不；但明明做不到还不能说不怎么办？诀窍如下。
26. 诀窍 1（做不到的需求）：**不要说这个需求做不到，尤其不要马上说做不到**；要先想一下（让别人觉得你是想做的），认真思考过后觉得做不到，再给出一个你觉得能做到的方案。**诀窍是——给出另一个你可以做到的方案，而不是把对方的方案直接回绝掉。**
27. 诀窍 2（过于复杂的需求）：不要说不；**反问一下：为什么要这样做？这样做的目的是什么？**了解目的后，给出自己的方案，或和对方讨论一个**性价比更好**的方案。可以回复："这个需求好复杂，我们能不能先干这个，再做那个，这样会更经济一些。"**诀窍是——我不说我不能完全满足你，但我说我可以部分满足你。**
28. 诀窍 3（时间完全不够的需求）：也不要说不；**既然对方把压力给你，你要想办法把这个压力还回去，或是让对方来和你一同分担这个压力**。
29. 诀窍 3 的具体话术（三个选择，原文原样）：a. 我可以加班加点完成，但是**我不保证好的质量**，有 bug 你得认，而且事后你要给我 **1 个月**的时间还债；b. 我可以加班加点，还能保证质量，但**我没办法完成这么多需求**，能不能减少一些？c. 我可以保质保量地完成所有需求，但是**能不能多给我 2 周**时间？
30. 诀窍 3 的本质：**我不能说不，但是我要有条件地说是**；而且要把对方给的压力**反过来还给对方**——"看似我给了需求方选择，实际上，我掌握了主动"。
31. 说"不"的方法论总结："说白了，你要学会在'**积极主动的态度下对于不合理的事讨价还价**'。只有学会了说'不'，你才能够控制好你的时间。"
32. 加班与会议（现象）：国内的公司和国外公司还有一个很不同的事——**大量的加班和大量冗长的会议**；无论大公司还是小的创业公司都这样。
33. 对加班"能理解"的一面：主要原因是**管理者在管理上只会使用低级的、通过劳动密集型的方式来做事**。
34. 对加班"不能理解"的一面：国外公司的加班和会议长度根本不像国内公司，人家做得也比中国公司好得多；**国内老板看到团队拼命加班会很高兴，国外老板看到团队拼命加班会觉得这个团队一定哪里出了问题，会比较焦虑**。
35. 现实态度："对于身处于这样环境中的我们……老实说，在**恶劣的环境中优雅的行动，基本上是一件不可能的事情**。我也经历过这样的事，但我也没有太好的办法。"
36. 加班的**恶性循环**（原文链条）：加班 → 干出来质量不好的软件 → 线上故障很多、要花时间处理 → 后面的需求也过来了 → 发现复杂代码的扩展性很差 → 越干越慢、越干越烂、越干故障越多 → 你会被抱怨得越来越多。
37. 两害相权：如果怎么做都要受伤害，那么**两害相权取其轻**——要学会比较"**项目延期的伤害**"与"**线上故障的伤害**"，"**先苦后甜**"还是"**积压问题**"。
38. 会议的问题："今天大多数的会都开错了"——在会上抛出问题，还是**开放性问题**，然后公说公有理、婆说婆有理，任大家自由发挥、各种跑题跑偏，最后还没有任何答案。
39. 会议金句："**开会，不是讨论问题，而是讨论方案；开会不是要有议题，而是要有议案。**"
40. 作为与会者的两种应对：① **跳出来帮大家理一理**；② 说一下"如果会上讨论不清，要不**先线下讨论，有了方案再来评审**"。
41. 可行性提示：也许在一些会上你不敢这么干，但**有些会你是可以这么干的**——能影响这些就能为你争取到很多时间。
42. 总结：分享了几个为自己争取更多时间的方法（主动管理时间、学会说"不"、面对高强度加班和冗长会议如何应对）；"只有将使用时间的**主动权**掌握在自己手上，才能更好地利用时间，才能更为高效率的工作。所以，这才是时间管理的关键点。"
43. 置顶留言（作者补充，标注来源）：回应"专栏太杂"的批评——专栏涉及技术、管理（含自我管理）、发展三方面，三者相辅相成但有时感觉不相干；他们还在摸索文章组织顺序，怕只发一类会过早定性专栏性质。

## 16｜时间管理：如何利用好自己的时间？
> 源文件 `.tmp-zuoer/txt/16丨时间管理：如何利用好自己的时间？.txt`，正文约 2760 字（含留言 3792 字）

### 一句话结论
时间要像钱一样**投资**（基础/文档、自动化、成长、环境），执行上按**最短作业优先**排、按"**将军赶路不追小兔**"聚焦、靠**习惯 + 正反馈 + 每周复盘**固化——"做"比"做好"更重要。

### 知识点全清单（A1 零丢失）
1. 总比喻：时间就像金钱一样，你得学会**投资时间**，把时间投资在有价值有意义的地方，你就会"有更多的时间"。
2. 投资方向 1：**花时间学习基础知识，花时间读文档**。参加工作 **20 年**的观察：很多程序员把时间**浪费在查错上**，究其根本原因是**基础知识不完整**、没有把技术相关的用户文档读完就仓促上手做事情；"其实只要把基础打扎实，认真读一下文档，你会省出很多很多的时间"；**系统地学习一门技术非常关键**，这个时间值得投资。
3. 投资方向 2：**花时间在解放自己生产力的事上**——在**自动化、可配置、可重用、可扩展**上多花时间。能自动化的事，就算多花点时间也要自动化，因为下次就不用花了；让软件模块可以更灵活地配置和扩展，需求变更或新需求来时**可以不用改代码，或就算改也很容易**。
4. 对"不要过度设计"的态度（原文明确"既同意，也反对"）：过度设计的确不好，但"**只要是能在未来节省时间的，宁可这个项目延期，我也会做的**"；"花时间在解放自己的事上是最有意义的了"。
5. 投资方向 3：**花时间在让自己成长的事上**。关键区分：**晋升并不代表成长**；成长不应该只看在一个公司内，而是要看在**行业内**，"在行业内的成长才是真正的成长"；把时间花在能让自己有更强竞争力、更大视野、更多可能性的事上，这样的时间投资才有价值。
6. 投资方向 4：**花时间在建立高效的环境上**。"工欲善其事，必先利其器"，程序员做事前都喜欢把工作环境整理到自己喜欢的状态（趁手的开发工具、趁手的设备）。
7. 投资方向 4 的扩大版：**花时间影响你身边的人**——同事、产品经理、老板，去影响他们、让他们理解你、配合你建立更好的流程和管理方法；"在这个方向上花时间也是很值得的"。
8. 规划 1：**定义好优先级**。无论你写不写出来，你一定都会有一个自己的 **to-do list**；有 to-do list 并不高深，更重要的是知道**什么事是重要的、什么事是紧急的、什么事重要但不紧急、什么事又重要又紧急**——这有利于划分优先级（四象限）。
9. 规划 2：**最短作业优先**。对相同优先级的事，作者喜欢"最短作业优先"的调度算法。理由三条：① 先把能快速做完的做完，看到 to-do list 划掉一个任务、看到数据在减少，对自己是正反馈；② **老板可以看到你的工作进度飞快**，"老板只有在你有 **Deliver** 的时候才愿意给你更多的时间"，有利于为后面复杂工作争取时间；③ 看到任务列表减少会让心态更积极。
10. 规划 2 的反面（长作业的坑）：花太多时间在长作业上，长作业**通常很容易出现"意外情况"**让你花更多时间；此时你发现还有很多别的事没做，会产生**焦虑感**、更多压力，进而导致**更慢的生产效率**。
11. 规划 3：**想清楚再做**。很多时候没想清楚就开干了、边干边想，"这样的工作方式其实很糟糕"；没想清楚就总是要对**已完成的工作进行返工**，返工好几次非常浪费时间。
12. 规划 3 的做法：对没想清楚的事或自己不太有信心的事，**先看看有没有已有的成熟解决方案**，或**找更牛的人来把把关、帮你出出主意**，看看有没有更好、更简单的方式。
13. 规划 4：**关注长期利益规划**。要多关注**长远可以节省多少时间**，而不是当前会花费多少时间；**长期成本会比短期成本大得多**；"宁可在短期延期，也不要透支未来"；逻辑是"工作上的事你永远也做不完的，长痛不如短痛"。
14. 规划 4 的算账例子：一年要做 **10 个项目**，宁可**第 1 或第 2 个项目被老板骂**，但可以赢得**后面 8 个项目**，从后面 8 个项目上把之前失去的找回来；反过来，虽然一开始得到老板信任，但后面越来越玩不动，最终"**搬起一块大石头砸了自己的脚**"。而且，不关注长远利益的人基本上很难有成长。
15. 规划 5：**按季度规划**。要学会规划自己的**行动计划**，不是短期的，而是**中长期**的；作者建议按**季度**规划——这个季度做什么、达到什么目标，"**一年往前走四步**"，而不是只考虑眼下。
16. 用好时间 1：**将军赶路不追小兔**。这个世界有太多东西会让我们分心和跑偏；能专注地把时间投入到一个有价值的事上非常重要；"确定自己的目标，专注达到这个目标，而不是分心。**将军的目标是要攻城，而不是追兔子**"；要学会**过滤掉与自己目标无关的事**。
17. "不追小兔"的三个具体：① **不要让别人来影响自己的心情**——"心情被影响了，你一下就会什么都不想干了。**做自己心情的主人，不要让别人 hack 了你的心情**"；② 知道哪些是自己**可以控制**的事、哪些是**控制不了**的，在自己能控制的地方花时间；③ 知道哪些是**更有效的路径**——是花时间**改变别人**，还是花时间去**寻找志同道合的人**。
18. 用好时间 2：**不与不如自己的人争论**，也不要尝试花时间去**叫醒那些装睡的人**——"这些都是非常浪费时间的事"；多花时间在有产出的事上，少花时间在**说服别人**的事上。
19. 用好时间 3：**形成习惯**。再好的方法，如果没有形成习惯、不能在实际工作和生活中解决实际问题，"都将成为空谈"；追求上进的人一定看过很多时间管理文章和书籍，看的时候还会振奋、内心想"这个方法不错，正是我需要的"，但**很多时候都坚持不了几天就抛之脑后**。
20. 习惯的关键数字与做法：养成一个好习惯通常需要 **30 天左右**的时间，**尤其在最初的几天就更为重要**；不妨把文章中提到的方法和几个要点**写在某本书或笔记本的扉页上**，方便查看、时刻提醒自己。
21. 习惯的个性化：可以结合自己的实际情况**适当做出调整**——"我的方法是我根据自己的情况总结的，不一定完全适合你"；基于原则发掘更适合自己的方法，才更有利于形成习惯。
22. 用好时间 4：**形成正反馈**。正反馈就是**成就感**，有助于完成一些看似难以完成的事；学习是**逆人性**的事，但过程中不断有正反馈就更利于坚持；要让自己有正反馈，就需要把时间花在有价值的地方，比如**解决自己和他人的痛点**，这样你会收获别人的**赞扬和鼓励**。
23. 用好时间 5：**反思和举一反三**。可以尝试**每周末**花点时间思考：本周做了哪些事？时间安排是否合理？还有哪些可以优化提高的地方？（有点像"**复盘**"）然后思考**下周的主要任务**是什么，并根据优先级规划完成这些任务的顺序（做下周的工作规划）。
24. 反思的收益：这样每周都能及时得到自己做时间管理之后的**反馈**，有助于持续优化；通常坚持一段时间后，每次复盘都能得到**正反馈**，有利于形成时间管理习惯。
25. 一个重要的宽容条款：**也要允许偶尔的"负反馈"**——"因为人的状态总是会有高潮和低谷的，控制好一个合理的度就可以了"。
26. 结语："人最宝贵的财富就是时间，把时间用在刀刃上，必将让你的人生有更多收获。"

## 17｜故障处理最佳实践：应对故障
> 源文件 `.tmp-zuoer/txt/17丨故障处理最佳实践：应对故障.txt`，正文约 2530 字（含留言 3624 字）

### 一句话结论
故障发生时第一目标**不是 debug，而是止血**——快速定位故障源、控制影响范围、尽快恢复；而"快"不来自现场聪明，来自**故障前的六件准备**（全视图、应急包、分级、演练、灰度、降级/紧急更新能力），组织前提是**按 Service 分工 + 全员 oncall**。

### 知识点全清单（A1 零丢失）
1. 立场：线上故障是技术人员成长中**必须经历**的事；从故障中能吸取很多教训、学到书本上学不到的知识；"坑踩多了，我们会变得越来越有经验，也就成为老司机了"。
2. 问题意识：很多公司处理线上故障的方式**并不科学**、存在很多问题；本文经验主要来自**亚马逊和阿里**两家公司 + 作者个人总结。
3. 故障发生时最重要的事：**快速恢复故障**；前提是**快速定位故障源**。
4. 为什么定位难：分布式系统中一旦发生故障会出现"**多米诺骨牌效应**"——系统会随着一个故障开始一点一点地波及其它系统，而且这个过程**可能会很快**；一旦很多系统都在报警，快速定位到故障源就不是件简单的事。
5. 亚马逊 oncall 制度：每个开发团队**至少有一位 oncall 工程师**；oncall 时要**专心处理线上故障**；**轮换周期为每人一周**。
6. 何时升级为工单：发生比较大的故障——比如 **S1 全部不可用**，或 **S2 某功能不可用且找不到替代方案**——故障会被提交到一个**工单系统**里；几乎所有相关团队 oncall 的工程师都会被叫到线上处理问题。
7. 工作流：工程师先**线上签到** → **自查自己的服务** → 如果自己的服务没问题，就在旁边**待命（standby）**，以备需要时配合 → 如果问题没有被及时解决，就会**自动升级到高层，直到 SVP 级别**。
8. 组织前提：亚马逊**不是按技能分工，而是按职责分工**——一个团队不是按前端、后端、运维分工，而是按所负责的 **Service** 分工；所以亚马逊开发人员**前端、后端、测试、运维全部都要干**。
9. 为什么要全员上线：亚马逊内部有很多服务，一旦出问题，**为了避免一个工单在各个团队流转**，需要所有团队上线处理，"这样是最快的"。
10. 分布式服务化的代价：一个用户的请求可能会经过很多服务，开发和运维起来非常麻烦；此时**跨团队跨部门的开发和运维就变得非常重要**。
11. 对亚马逊的评价：故障发生时亚马逊的处理过程**比较有效和快速**，尤其能快速定位故障源；对**被影响的其他团队**也可以做一定的处理（如**降级**），从而**控制故障的范围不被扩散**。
12. 恢复手段 1：**重启和限流**——主要解决**可用性**的问题，不是功能性的问题；重启还好说，但**限流需要相关的流控中间件**。
13. 恢复手段 2：**回滚操作**——一般用来解决**新代码的 bug**，把代码回滚到之前的版本是快速的方式。
14. 恢复手段 3：**降级操作**——并不是所有的代码变更都是能够回滚的，如果无法回滚，就需要降级功能；"也就是说，需要挂一个停止服务的故障公告，主要是不要把事态扩大"。
15. 恢复手段 4：**紧急更新**——常用手段，需要**强大的自动化系统**，尤其是**自动化测试和自动化发布系统**；"假如你要紧急更新 **1000 多台**服务器，没有一个强大的自动化发布系统是很难做到的"。
16. 核心原则（原文加粗）："**出现故障时，最重要的不是 debug 故障，而是尽可能地减少故障的影响范围，并尽可能快地修复问题。**"
17. 国内专职运维团队的问题：国内很多公司由**专职的运维团队**处理线上问题；但运维团队通常只能处理**基础设施**方面的问题，或**非功能性**问题；对**功能性**问题完全没有能力处理，只能通过相应的联系人把开发人员叫到线上。
18. 传递链的浪费：而这个开发人员看到的可能是**别的系统**有问题，又会叫上其它团队的人；"所以，一级一级地传递下去，会浪费很多时间"。
19. 为什么要做准备：为了在面临故障时**有条不紊**；准备工作做得越细，故障处理起来越有条理；"我们知道，故障来临时，一切都会变得混乱。此时，对于需要处理故障的我们来说，**事可以乱，但人不能乱**。如果人跟着事一起乱，那就是真正的混乱了"。
20. 准备项 1：**以用户功能为索引的服务和资源的全视图**——需要一个系统记录**前端用户操作界面 ↔ 后端服务 ↔ 服务使用到的硬件资源**之间的关联关系；这个系统有点像 **CMDB（配置管理数据库）**，但**比 CMDB 大得多**，是**以用户端的功能来做索引**的；然后把后端服务、服务的调用关系、服务使用到的资源都关联起来做成一个视图。
21. 全视图的生成方式与价值：这个视图**最好由相应的自动化监控系统生成**；有了资源图后，就很容易找到处理故障的路径——"这就好像一张**地图**，如果没有地图，我们只能像个**无头苍蝇**一样乱试了"。
22. 准备项 2：**为地图中的各个服务制定关键指标，以及一套运维流程和工具，包括应急方案**——以用户功能为索引，为每个用户功能的服务制定一个服务故障的**检测、处理和恢复手册**，以及相关的检测、查错或恢复的**运维工具**；对**基础层和通用中间件**也需要有相应的最佳实践。
23. 举例（Redis）：怎样检查其是否存在问题、怎样查看其健康和运行状态？哪些是**关键指标**？面对常见故障应该怎么应对？服务不可用的服务方案是什么？服务需要回滚了应该怎么操作？
24. 导航仪类比："这就好像一个**导航仪**，能够告诉你怎么做。而没有导航仪，就没有章法，会导致混乱。"
25. 准备项 3：**设定故障的等级 + 不同等级的处理方式**。亚马逊一般分 **4 级**：**1 级**是全站不可用；**2 级**是某功能不可用且无替代方案；**3 级**是某功能不可用但有替代方案；**4 级**是非功能性故障，或是用户不关心的故障。**阿里**内的分类更多样一些，**有时会根据影响多少用户来定故障等级**。
26. 分级的作用：主要是为了确定该故障要**牵扯进多大规模的人员**来处理；故障级别越高，牵扯进来的人就越多、参与进来的**管理层级别也就越高**（就像亚马逊的全员上线 oncall）。
27. 分级的类比："这就好像是我们社会中常用的'**红色警报**'、'**橙色警报**'、'**黄色警报**'之类的，会触发不同的处理流程。"
28. 准备项 4：**故障演练**——故障并不会时常发生，但我们需要不断提升处理故障的能力，所以需要经常演练。大公司案例：**Netflix** 有一个叫 **Chaos Monkey** 的东西，**随机地在生产线上乱来**；**Facebook** 也会有一些故障演习，比如**随机关掉线上的一些服务器**。
29. 演练的价值判断："要提升故障处理水平，最好的方式就是实践。见得多了，处理得多了，才能驾轻就熟。故障演练是一个非常好的实践。"
30. 准备项 5：**灰度发布系统**——要减少线上故障的影响范围，通过灰度发布系统来发布是很不错的方式；毕竟在测试环境中很难模拟出线上环境的所有情况，所以在生产线上进行**灰度发布或 A/B 测试**是一件很好的事。
31. 亚马逊的灰度实践：发布系统中有一个叫 **Weblab** 的系统用来做灰度发布；另外亚马逊全球会有**多个站点**，一般会**先发中国区**，如果中国区没什么问题了，就发**日本区**，然后发**欧洲区**，最后是美国区。
32. 没有多站点怎么办：那么你就需要一个**流量分配系统**来做这个事。
33. 结语："只要能做好上面的几点，你处理起故障来就一定会比较游刃有余了。"
