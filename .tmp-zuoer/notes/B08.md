## 60｜性能设计篇之“数据库扩展”
> 源文件 `.tmp-zuoer/txt/60丨性能设计篇之“数据库扩展”.txt`，汉字 4,385 字

### 一句话结论
业务层的数据库扩展只有两条路——读写分离（含 CQRS/事件溯源）与分库分表，而真正治本的不是在任何一条上做深，而是**先把服务与库一起拆开（一个服务一个库），再在这个小库上做读写分离或分片**；分片要按业务分，哈希散列是最后手段。

### 知识点全清单（A1 零丢失）
1. **读写分离**：一个写库 + 多个读库，所有服务写同一个库；读操作按业务分配到不同从库（原文示例：服务 A、B 走从库 A，服务 D、E 走从库 B，服务 C 在从库 A/B 间**轮询**）。
2. 好处三条：①比较容易实现（数据库 master-slave 配置与框架里的读写分离都比较成熟，应用快）；②可以很好地把各个业务隔离开，不会一个业务把数据库拖死导致所有业务都死；③可以很好地分担读负载——**读操作是最耗数据库 CPU 的操作**。
3. 坏处三条：①**写库有单点故障**，写库出性能问题所有业务一样不可用，交易型业务要高的写速度这种方式不行；②数据库同步不实时，需要强一致性的读写操作还是得落在写库上。原文这句总结：「这样的读写分离看上去有点差强人意」。
4. 定位：读写分离主要就是为了**减少读操作的压力**。
5. **CQRS**：全称 Command and Query Responsibility Segregation，命令与查询职责分离。
6. 原理：用户对应用的操作分成两种——**Command**（增删改，写操作，业务逻辑更重）与 **Query**（查，读操作，基本是在做数据整合显现）；分离开可以在语义上做好区分。
7. CQRS 四条好处：①分工明确，可以负责不同的部分；②提高系统的性能、可扩展性和安全性，在系统演化中保持高度灵活，**防止 CRUD 模式中改查询坏修改、改修改坏查询**；③逻辑清晰，能看到系统中哪些行为或操作导致了状态变化；④可以从数据驱动（Data-Driven）转到任务驱动（Task-Driven）以及事件驱动。
8. **Command 不会返回结果数据，只返回执行状态，但会改变数据；Query 返回结果数据，但不改变数据，对系统没有副作用**。
9. Command 可以进一步变成 **Event Sourcing（事件溯源）**：只记录不可修改的事件，通过回溯事件得到数据状态；于是写操作被完全简化、也变成无状态的，大幅降低系统副作用，得到更大的并发和性能。
10. 影响数据库性能的两件大事：**对数据库的操作**、**数据库中数据的大小**。
11. 对「操作」从业务上优化：简化业务，不在数据库上做太多关联查询；报表/搜索类复杂操作移到更合适的地方——用 ElasticSearch 做查询，用 Hadoop 或别的数据分析软件做报表分析。
12. 对「数据大小」：数据越多操作越慢；后端服务能分布式，数据库最好也能拆成分布式；读写分离也会因数据太多而变慢，于是**分库分表成为必须用的手段**。
13. 分库策略：按地理位置、按日期、按某个范围、按哈希散列算法（原文示例分成三个库）。
14. **数据访问层**中间件：为了不让前面的服务感知数据库变化，引入它做数据路由；但它**很不好写**——要有解析 SQL 语句的能力，还要按解析结果做路由。
15. 数据访问层的三类麻烦：①分页要读一组顺序数据；②Max/Min/Count 要到三个库分别求值再回中间件合计返回；③**跨库事务要走 XA 这样的两阶段提交，会把数据库性能降到最低**。
16. 四种分片策略（原文最推荐到最不推荐）：①**按多租户**——用租户 ID 分，把租户隔离开（例：电商平台的商家中心按商家 ID 分）；②**按数据种类**——按类目分、商家按地域分；③**通过范围分**——同分片数据连续，分页查询更高效，多数情况用时间（例：订单中心按月份分表，便于快速检索统计连续数据）；④**通过哈希散列算法分**（例：主键 id % 3）——目的是降低形成**热点**（接收不成比例负载的分片）的可能，但带来两个问题：跨库跨表查询与事务、**扩容要重新哈希部分或全部数据**。
17. **铁律（原文加粗）：「请只考虑业务分片。请不要走哈希散列的分片方式，除非有个人拿着刀把你逼到墙角，你马上就有生命危险，你才能走哈希散列的分片方式。」**
18. 扩展设计重点（原文明确边界）：没有讲数据库引擎的水平扩展，只讲业务层；引擎级扩展要看 AWS Aurora 与 Google Spanner 的相关论文。
19. **先服务化拆分，再做分片**：数据库和应用服务一同拆开，一个服务一个库（Amazon 玩法：服务间只能通过服务接口通讯，不能访问对方数据库；每个服务有自己的地址库、银行卡库等），数据库就被「天生地」拆成服务化的，而不是单体库。
20. 关键判断：**在单体库上做读写分离或分片都是治标不治本，真正治本的方法是要和服务一起拆解**；数据库服务化后，才在这个小服务库上做读写分离/分片获得更多性能与吞吐。原文称其为「整个设计模式的原则」。
21. **水平分片 vs 垂直分片**：水平分片是前面说的按行拆；垂直分片是把一张表的一些字段放一张表、另一些放另一张表。
22. 垂直分片的用途：把经常修改的数据与不经常修改的数据分离，改某字段时不会导致其它字段被锁而影响性能；电商例：商品描述信息不常改，库存和价格经常改，分成两张表后**商品描述信息的查询更快**。
23. 术语说明：sharding 更多指水平分片。
24. 水平分片五条注意事项：①**定期重新平衡分片**保证均匀分布、降低热点，但重平衡是**昂贵操作**；减少频率要靠每个分片预留足够可用空间，并开发快速重平衡的工具和脚本；②**分片是静态的而数据访问不可预期**，频繁调整成本太高 → 最好用**索引表**动态记录数据位置，数据搬到别的节点只需改索引表里的位置；③跨分片检索可用**并行任务**从各分片提取再聚合到单个结果，但会增加数据访问逻辑的复杂性；④分片后很难保持引用完整性和一致性（跨分片事务），**应尽量减少影响多个分片数据的操作**，必须跨分片修改时要评估一致性以及是否采用两阶段提交；⑤**配置和管理大量分片是挑战**，做变更一定要先从生产线上拉出数据、按数据计划好新的分片方式、做好相应测试，否则出问题是灾难性的。
25. 索引表为什么能哈希分片（作者回复留言）：索引表没有业务属性，就是 KV，没有 join、没有 group，所以非常容易用哈希分片。
26. 强一致怎么办（作者回复留言）：业务层上只有两阶段提交，数据层上只有 Paxos。

### 数字 / 公式 / 阈值
- 读写分离拓扑：**1 个写库 + 2 个读库**；服务 A/B→从库 A，D/E→从库 B，C 轮询 A/B。
- 分库示例：按某种规则分成**三个库**。
- 哈希散列示例算法：**主键 id % 3**。
- 跨库聚合的三种典型操作：**分页 / Max / Min / Count**；跨库事务用**两阶段提交（XA）**。
- 订单中心分表粒度：**按月份分表**。
- 数据访问层的中间件要求：能**解析 SQL** 并据此路由。

## 61｜性能设计篇之“秒杀”
> 源文件 `.tmp-zuoer/txt/61丨性能设计篇之“秒杀”.txt`，汉字 3,373 字

### 一句话结论
秒杀不需要"硬扛 100 万并发"，而是**用 CDN 边缘节点把 100 万人拦在数据中心之外，只按一个可调的概率值（如 0.02%）放行极少数人到中心抢库存**——技术含量不在中心，在"在哪一层过滤"。

### 知识点全清单（A1 零丢失）
1. 作者先破除认知：「一说起秒杀，大家都觉得这事很有技术含量。实际上，并不是这个样子的。」
2. 秒杀的业务定义：商家为促销，用非常低的价格销售商品，例如 **1 元卖 iPhone，100 台，来了一百万人抢购**。
3. 流程第 1 步：需要一个秒杀的 **landing page**，页上有一个**倒计时按钮**。
4. 倒计时按钮上的时间、以及按钮可被点击的时间，**都需要后台服务器来校准**。
5. 前端要不断向后端请求「开没开始，开没开始……」；每次询问后端都返回一个时间以校准前端时间。→ 100 万人不停轮询，后端扛不住。
6. 一旦后端表示 OK 可以开始，后端会返回一个 **URL**，这个 URL 被安置在按钮上，按钮就可以点击了。
7. 下单时一般要填一个**校验码**，防止机器来抢。
8. 点击后：抢到库存 → 进入支付页面；没抢到 → 返回「秒杀已结束」。
9. 技术挑战一：100 万人同时下单 → **网络带宽不够**；理论上要扛 **100 万 TPS** 需要非常多的机器。
10. 技术挑战二（原文称"最恐怖"）：**所有请求都集中在同一条数据库记录上**，无论怎么分库分表、用不用分布式数据库都无济于事，因为面对的是**单条热点数据**。原文：「这几乎是一件无法解决的技术问题。」
11. 解决第一步：让 100 万人在同一时间打开一个页面，必须用 **CDN**——数据中心肯定扛不住。100 万用户被**几十个甚至上百个 CDN 边缘节点**分担。
12. 解决第二步：在 CDN 节点上做"小文章"——**把一个小服务部署到 CDN 节点上**。这个小服务除了回答"开没开始"，还能**统计有多少人在线**，并每隔一段时间把在线等待人数回传数据中心，于是中心知道全网在线人数。
13. 解决第三步：快开始时，由**数据中心向各 CDN 节点上的小服务下发一个概率值**，例如 **0.02%**。
14. 解决第四步：秒杀开始时 100 万人都点下单，请求先到 CDN 上的服务；小服务按 0.02% 的比例放行到后面的数据中心——**1 万个人放过去两个，剩下的 9998 个直接返回「秒杀已结束」**。
15. 结果：100 万人只放行约 **200 人**到中心抢 **100 台** iPhone，即 **200 TPS**，怎么都应该扛得住。
16. 作者自评：「这就是整个'秒杀'的技术细节，是不是有点不敢相信？」
17. 案例辨析一：**2008 年奥运会抢票**把服务器抢挂，是**可以**用秒杀这套方案的。
18. 案例辨析二：**12306 不行**——「因为他们完全不知道用户来是要买哪张火车票的」，不知道这个信息就**很不好过滤用户**；而且用户买票前有很多查询操作，要在查询中选车票。
19. 12306 的可行应对：不要一次把票全放出来，**分批在不同时间段放票**，让人不要集中在一个时间点抢，做到**人肉分流**，降低并发度。
20. 12306 的作者主张：最好用**预售**方式，让大家把购票需求先输入系统；系统不真正放票，而是把需求收集好做**整体统筹安排**——该加车次加车次、该加车厢加车厢，确保大家都能走；实在不行就**抽签**。
21. 双 11 与秒杀的本质不同：双 11 要**尽可能多地收订单**（不是"少放人进来"），但又不能超过库存；其中还有大量银行支付、各大仓库的库存查询与分配（都是非常慢的操作），还要保证一致性、扛住大规模并发。
22. 因此：**双 11 用秒杀这套方案基本不科学**，必须认认真真做高并发架构和测试——各系统把性能调上去、小心做性能规划、做好分布式弹力设计、不停做性能测试找架构瓶颈、不断水平扩展。
23. 普适性反思（本篇的真正落点）：用边缘节点解决秒杀，**是否有普适性？作者答"一定是有的"**。
24. 普适场景：有**地域特征**的业务，如外卖、共享单车、打车；把一些简单的业务逻辑放在边缘，比放数据中心**不但性能更好，成本还更便宜**。
25. 趋势判断：请求量越来越大、数据越来越多，**数据中心有点到瓶颈了**，需要边缘节点帮忙；边缘化方案的趋势会越来越有优势。（作者注明这是他的创业方向，下一篇详述。）

### 数字 / 公式 / 阈值
- 促销标的：**1 元 iPhone，100 台**；参与人数 **100 万**。
- 理论并发：**100 万 TPS**。
- CDN 节点数：**几十个到上百个**。
- 下发概率值：**0.02%**。
- 放行结果：100 万 × 0.02% ≈ **200 人**；抢 **100 台** → **200 TPS**。
- 原文另一处口径：「1 万个人放过去两个，剩下的 9998 个直接返回秒杀已结束」（与 0.02% 自洽：1 万 × 0.02% = 2）。
- 时间锚点：**2008 年**奥运会抢票。

## 62｜性能设计篇之“边缘计算”
> 源文件 `.tmp-zuoer/txt/62丨性能设计篇之“边缘计算”.txt`，汉字 4,190 字

### 一句话结论
边缘计算不是"IoT 的附属品"，而是**数据中心成本超线性增长 + 数据量与实时性双刚需**逼出来的必然产物；它的现实形态是"以数据中心为主的云计算的补充"，用边缘节点接高峰流量，中心就不必按峰值建设。

### 知识点全清单（A1 零丢失）
1. 常见误解：网上大多数文章说边缘计算是和 **IoT** 相关的技术；作者认为「只说对了边缘计算的一部分」，边缘计算能做的事还有很多。
2. 定义：边缘计算是**相对于数据中心**而言的。
3. 数据中心的两个好处（客观承认）：集中式部署便于管理和运维；便于服务间通讯有比较好的网络保障。
4. 但依然需要 CDN 这样的边缘式内容分发网络，把静态内容推到离用户最近的地方以获得更好性能。
5. 核心命题：**如果让 CDN 的边缘节点拥有可定制的计算能力**，就能像秒杀那样在边缘处理很多事，给数据中心带来更好的性能、扩展性、稳定性，用户也觉得响应飞快。
6. 趋势论证（一）：我们处在信息化/数字化革命时代，本质是**人类生活信息化建设的过程**。
7. 硬件背景：CPU 处理速度、硬盘大小与速度、网络带宽与速度都在拼命升级和降价；用越来越低成本获得越来越快速度、越来越大带宽、越来越快存储。作者参加工作 **20 年**来这个过程没停止过，且不认为未来会停。
8. 数据时代四段演进：**MB 时代**（只有内容服务提供商在提供内容，主要是新闻资讯，数据不多，几百兆硬盘就够）→ **UGC 时代**（用户写博客、发帖子、拍照片、拍视频，数据进入 **GB** 时代，硬件与网络基础设施升级）→ **大数据/移动互联网时代**（以前要开电脑才能上网，现在手机有电就在线；大量线下服务走到线上，如外卖、叫车；各种 App 收集行为与数据）→ **吞噬线下**（通过摄像头识别车牌等线下活动，通过传感器收集农业、水利等线下数据）。
9. 由此推出：这么大量数据都拿到数据中心做分析和计算，**一个数据中心顶得住吗**？作者已接到好几个用户说"数据量太大、不知道怎么架构数据中心，各种慢、各种贵、各种痛苦"。
10. 趋势论证（二）：**实时**成为刚需——不能实时处理、实时响应就跟不上时代。举例：苹果手机的人脸识别如果要到服务器算再返回，用户体验很糟糕，**所以苹果在手机里直接植入了神经网络的芯片**。
11. 结论：「数量越来越大，分析结果的速度需要越来越快，这两个需求，只会把我们逼到边缘计算上去」；继续在中心处理，成本只会越来越高，到一定时候完全玩不下去。
12. 成本论证：几十万用户时没什么感觉；要支撑上千万乃至上亿用户时，**几十万用户的架构和上千万用户的架构在成本上完全不是一个数量级**。
13. 成本曲线：数据/请求规模越大，成本是**快速上升的曲线，不是线性上升**。
14. 四档经验值（作者服务过 **40 多家公司**的观察）：几十万用户只需处理**百级 QPS**，约 **10 台**服务器；上百万用户处理**千级 QPS**，约 **50 台**；上千万用户处理**万级到十万级 QPS**，约 **700 台**；上亿用户处理**百万级 QPS**，需要**上万台**。
15. 原文的倍数表述：「十万用户到上亿用户，也就多了 100 倍，为什么服务器需要 1000 倍？完全不是呈线性的关系。」（注：十万到一亿实为 1000 倍，读者在留言区指出这处数字自相矛盾；原文如此，照录。）
16. 非线性的原因：**架构变复杂后要做很多非功能的东西**——缓存、队列、服务发现、网关、自动化运维、监控等。
17. 思想实验（脑洞）：把上亿用户拆成 **100 个百万级**，就只需 **5000 多台**（100 × 50 台）；同样服务这么多用户，成本下降得很快；代价是要运维 100 个小数据中心，但「运维 100 个 50 台服务器的小数据中心的难度应该远远低于运维一个 10000 台服务器的数据中心」。
18. **作者的自我否证**（关键，别只抄前半段）：1 亿用户的业务形态和 100 万用户完全不同、复杂得多；1 亿用户可能有上百个服务，**50 台服务器不够部署**；「我上面那种多个数据中心的理想只存在于理论上，而实际上不会发生」。
19. 转折结论：沿着这条路想下去——**可以用边缘节点处理高峰流量，这样数据中心就不需要花那么大的成本来建设**。
20. 定位：边缘计算会作为**以数据中心为主的云计算的一个非常好的补充**。
21. 边缘计算三类业务场景：①**处理实时响应的业务**（离用户近，可实时响应本地请求，例如某公司的人脸门禁系统、共享单车开锁）；②**处理简单的业务逻辑**（如秒杀、抢红包）；③**收集并结构化数据**（如把视频中的车牌信息抠出来转成文字传回数据中心）。
22. 另有两类延伸场景：**线下设备的数据采集和监控**；**P2P 的去中心化应用**（边缘节点作为服务发现的服务器，让本地设备之间 P2P 通讯）。
23. 关键技术一：**API Gateway**（管理设计篇有专篇，不展开）。
24. 关键技术二：**Serverless / FaaS**。
25. Serverless 词源考据：**2012 年 Ken Form** 的文章《Why The Future of Software and Apps is Serverless》，讲的是持续集成及源代码控制等，**并不是今天特指的这种架构模式**。
26. 转折点：**Amazon 2014 年发布 AWS Lambda**，把 Serverless 范式提到全新层面；此后**再也不需要在服务器上持续运行进程以等待 HTTP 请求或 API 调用**，而是通过某种事件机制触发代码执行——通常只需在 AWS 某台服务器上配置一个简单的功能。
27. **2015 年 7 月 Ant Stanley** 的文章《Server are Dead…》，围绕 AWS Lambda 及刚发布的 AWS API Gateway 解释他心目中的 Serverless：「Server are dead…they just don't know it yet」。
28. FaaS 定义：如果微服务是以专注单一责任与功能的小型功能块为基础、模块化组合出复杂大型应用，那么 Serverless 提供一种更「**代码碎片化**」的软件架构范式，称为 **Function as a Services（FaaS）**；所谓"函数"是比微服务**更细小**的程序单元。
29. 当时流行的开源项目（原文列举）：**Serverless Framework、Fission（Serverless Functions for Kubernetes）、Open Lambda、Open FaaS、IronFunction**。
30. 关键技术三：**云资源调度**——边缘节点因为是流量接入方，所以可以调度流量；例如允许用户使用不同厂商的云存储服务、使用不同厂商但功能相同的 API 服务（如支付 API）。
31. 关键技术四：**云资源聚合**——例如把语音转文字的 API 与语义识别的 API 相结合，聚合出一个"识别语音语义"的 API，简化开发成本。

### 数字 / 公式 / 阈值
- 作者从业 **20 年**；服务过 **40 多家**公司。
- 四档规模—服务器经验值：**几十万用户 / 百级 QPS / 10 台**；**上百万 / 千级 QPS / 50 台**；**上千万 / 万级到十万级 QPS / 700 台**；**上亿 / 百万级 QPS / 上万台**。

## 63｜区块链技术的本质
> 源文件 `.tmp-zuoer/txt/63丨区块链技术的本质.txt`，汉字 5,051 字

### 一句话结论
区块链的"不可篡改"不是一种加密魔法，而是**"内容哈希成链（一处改处处改）+ 工作量证明（把改造成本抬到不可能）"两件事叠出来的成本壁垒**；它要解决的是"节点不可信"前提下的数据一致性，而这个前提正是它与公司内分布式系统的根本分野。

### 知识点全清单（A1 零丢失）
1. 写作缘起：专栏开更时就有读者要求谈区块链，作者当时认为「区块链相关的技术相对比较简单，没什么好说的」，且专栏目标是主流关键技术，所以把区块链文章**降级处理**；后来因为热度不得不写。
2. 2010 年在国外技术网站看到讨论 bitcoin，有人说**用几万个换了个披萨**；作者看了白皮书——**不到 10 页**、读起来很容易，建议读一读。
3. 作者亲历：在一台电脑上安装，像用 BT 或电驴下载一样连入**没有服务器的 P2P 网络**，下载账本，尝试"挖矿"；花了不少时间收到系统奖励的 **50 个比特币**；觉得又耗硬盘又吃 CPU、太难用，**删除了**（50 个币也不知去哪了）。

9. 比特币号称的三个特性：①**去中心化**——没有中心服务器，不受某个人控制，整个系统直接由用户端电脑构成；技术难度非常大，不像 App/小网站想发布就发布，**需要有人来跟你一起玩**；②**数据防篡改**——所有交易记录**全量保存**并公开给所有人，还被加密和校验；「**并不是数据不能被篡改，而是数据被篡改的成本非常大**」；有人借此说能解决人类的信任问题，「**这个并不一定**」；③**固定的发行量**——不会像国家央行那样乱印钞票造成通货膨胀。
10. 三者叠加的效果（信仰者观点）：让想作弊的人——尤其是有权有势有钱的大公司大组织——很难作恶；「去中心化」本质上让系统不再需要这些大公司和组织，人民达到真正意义上的自治，这些大公司都会倒闭。
11. 信仰者的完整主张：不再需要银行、中介机构、电商平台、支付宝等中间机构；人们可以通过一个不受任何人控制和操作的 P2P 金融系统，进行完全自由和可信的交易。

16. **前提假设**：「网络中的任何节点都是不能信任的，它们中的任何一个都可能会作恶」。
17. 由前提推出的设计约束：任何人都可以拿到所有数据 → 数据要**很容易被验证是合法的、没有被修改过**，而且**很难被人修改** → 比特币用了两个大技术：**区块链技术** + **工作量证明共识机制**。
18. 区块链结构：一个一个的区块，每个区块包括一组交易信息；每个区块有一个 **ID（或地址）**，通过记录**前一个区块的 ID** 形成一条链。
19. 链式哈希三个要点：①每个块的 ID **通过其内容生成**，内容有一丁点儿变化 ID 就完全不一样；②生成 ID 的内容中**还包括上一个块的 ID**，所以上一个块内容变 → 它的 ID 变 → 后面指向它的 ID 也要变 → 形成**连锁效应**：一个块被修改，后续所有块都要跟着改，于是**修改成本提升**；③「这种一处改，处处改的方式，并不代表不能篡改，而只是让修改面比较大，让你的改动麻烦一点」。
20. **真正让区块链非常难篡改的是工作量证明的共识机制**（原文明确把功劳从"链"挪到"PoW"）。
21. 中心化与去中心化分布式系统的本质差别：一个公司内的分布式系统节点**被假设成可信任的**；去中心化网络下节点**要被假设成不可信任的**——在一堆不可信节点上做一致性非常难。
22. 需要解决的四个"数据一致性"问题：
    - ①**以谁的数据为准？**任何节点都可以改自己下载的账本，即任何人都可以伪造账本；只能认为"大多数人认识的数据是对的"；只要控制一半以上节点，让"大多数人"伪造同一份账本，整个账本就等于被改过来了——「在没有服务器的去中心化的网络下，所谓的真理只不过是大多数人同意的东西」。
    - ②**"大多数人"是人数吗？**在网络世界可以用程序模拟出无穷多的"人"来投票；在分不清是人还是狗、是生物还是程序的计算机世界里，用人数解决去中心化问题「是一件很愚蠢的事」。
    - ③**意见分歧问题**：同一时刻多个人宣称账应该这么记（左耳朵转 10 元 / 转 20 元 / 根本没花钱是陈皓花的），且数据都合法，网络该听谁的？
23. PoW 的三条作用（对应上面三个问题）：
    - ①**修改几乎变得不可能**——生成一个区块要大量长时间计算（世界上最好的电脑集群算 **10 分钟**才打好一个包）；伪造一个块就要改后面所有块，改整条链的成本非常高；
    - ②**掌握 51% 算力的人变得几乎不可能**——除伪造链成本高，还要控制大多数人算力，需巨额资金投入；两个难度加起来几乎不太可能；
    - ③**解决分歧**——大工作量已降低意见冲突概率；即使出现合法冲突区块（同时多个合理区块 = **分叉**，即多个合法账本），因挖矿成本太高不可能同时跟进多个账本，矿工只能**赌跟其中一个**；大多数人选择的分支越来越长，另一边无人问津从而作废。
24. 安全性随时间单调：**越旧的区块越不容易篡改，越安全；越新的区块越不安全**。
25. 作者总评：PoW 成本高、耗电、不环保，但「这是目前去中心化系统中最安全的玩法」。

## 64｜区块链技术细节：哈希算法
> 源文件 `.tmp-zuoer/txt/64丨区块链技术细节：哈希算法.txt`，汉字 3,936 字

### 一句话结论
区块链在数据结构上就是一条**单向链表**：块 ID = 对（本块数据 + 前块 ID）做哈希，于是"改一个 bit 就要改后面所有块"；而**Merkle 树**把"校验一组交易"的成本从 O(n) 降到 O(log n)，**UTXO** 则用"未花费输出"替代余额，换来并行与无状态。

### 知识点全清单（A1 零丢失）
1. 结构类比：对计算机来说，区块链就像一个**单向链表**，一个数据块保存三个信息：**真正的数据、自己的地址（或 ID）、前一个数据块的地址**；通过追溯前一个块的地址把所有块存成一条链，所以叫 BlockChain。
2. 地址编码用的是 **Secure Hash**（音译"安全哈希"，意译"安全散列"）。
3. hash 算法的四个功能：①生成唯一标识一个数据块的 **ID（身份证）**，几乎不能重复；②做**数据特征码**——数据中一个 bit 改动整个 hash 值就完全不一样，且数学上保证**无法通过 hash 值反推原数据**；③发布信息/软件时带 **Checksum（校验码）**，与官方不一致就说明被改或残缺；④用于**数字签名**。
4. 两个著名 hash 算法：**MD5**、**SHA-2**；**区块链用的是 SHA-256**。
5. 数字签名做法：把"数据"和其"签名"（hash 计算值）一起发布，收到方可验证数据有没有被修改。
6. MD5 示例：「chen hao」→ `9824df83b2d35172ef5eb63a47a878eb`（16 进制数）；把字母 o 改成数字 0 得「chen ha0」→ `d521ce0616359df7e16b20486b78d2a8`，与之前完全不一样。
7. 链式构造示例：第一块把"数据集"和"前数据块的 hash 值 `00000a6cba`"一起做 hash，得到本区块地址 `000007cabfa`；下一个区块再把自己的数据和 `000007cabfa` 一起 hash 得 `000008acbed`……如此往复。
8. 篡改的连锁后果（两条）：①前置数据改了 → 它的 hash 完全不一样 → 你的 ID/地址变了 → **别人就找不到这个数据块**；②你还要改别人数据块中指向你的地址，但那个地址一变，**他自己的地址也随之变化**（因为他用你的地址生成了自己的地址），于是要把其他人的地址全部改掉。
9. 结论：在这样的连锁反应下，偷偷改一个 bit 的难度提高很多；**越老的区块越安全、越不容易被篡改，越新的区块越不安全**。
10. 比特币区块协议格式：**Version、Previous Block Hash、Merkle Root、Timestamp、Difficulty Target（Bits）、Nonce 六个字段是区块头**；后面是交易数据——本块交易笔数 H 与交易列表（**最多不能超过 1MB**）。
11. 六个字段含义与长度：
    - **Version**：当前区块链协议版本号，**4 个字节**，升级会变；
    - **Previous Block Hash**：前面那个区块的 hash 地址，**32 个字节**；
    - **Merkle Root**：可简单理解为后面交易信息的 hash 值，**32 个字节**；
    - **Timestamp**：区块生成时间，**不能早于前面 11 个区块的中位时间，不能晚于"网络协调时间"——你所连接的所有节点时间的中位数**，**4 个字节**；
    - **Bits**：即图上的 Difficulty Target，表明当前 hash 生成难度，**4 个字节**；
    - **Nonce**：一个随机值，用于找到满足条件的 hash 值，**4 字节**。
12. 块 hash 计算方式：**对区块头做两次 SHA-256**，即 `SHA-256(SHA-256(Block Header))`。（原文一处笔误写作"对这五字段进行 hash"，读者指出前面介绍了 6 个；照录并标注为原文笔误。）
13. 挖矿的引子：比特币对这个 hash 值有要求（由 Bits 字段控制），你可以调整 **Nonce** 这个 32 位整型的值去找符合条件的 hash——这事叫"挖矿"（下一篇详述）。
14. **Merkle Root 计算**：每笔交易有三个字段——**转出方、转入方、金额**；对每笔交易的三个字段求 hash，然后把交易的 hash **两两合并再求 hash**，直到算出最后一个 hash 值，就是 Merkle Root。
15. 四笔交易的例子：A、B 的 hash 成 Hash-AB，C、D 的 hash 成 Hash-CD，再做 Hash-AB + Hash-CD 的 hash 得 Hash-ABCD = Merkle Root；**整个过程就像一棵二叉树**。
16. 为什么不把所有交易放一起做一次 hash（原文自问自答）：这样做把交易数据分成若干组，可以不断把树分成左右分支，因为都算过 hash，所以**可以很快校验其中内容有没有被修改**。至少三个好处：
    - ①大量交易数据可被分成**各种尺寸的小组**，有利于整合数据和校验数据；
    - ②这样的开销**在存储和内存上并不大**，却可以提高"校验一组数据"的难易程度；
    - ③在 P2P 无中心化网络上，可以把大量数据拆成一个个小数据片传输，**提高网络传输速度**。
17. 以太坊有**三个不同的 Merkle Root 树**（因为要玩智能合约，需要更多 Merkle Root）：①做交易 hash 的；②表示**状态 State** 的——一个智能合同从初始状态走到最终状态要若干步（若干笔交易），每步都让合同状态变化，所以要保存合同状态；③做**交易收据**的——记录智能合约中最终发生的交易信息。以太坊称其为 **Merkle Patricia Tree**。
18. 比特币交易模型：需要两个术语——**input（交易的支出方）与 output（交易收入方）**。
19. 规则：一个交易可以有**多个 output**（可以把一笔钱汇给多个人）；但**一个 output 只能对应一个源的 input**；且 **output 与 input 的总数要吻合**。
20. UTXO 例子：Fred 给 Alice 2 个币、Ted 给 Alice 3 个币 → Alice 名义上有 5 个；但**比特币世界里没有余额**，她只有两个"没有花出去的交易"（2 个的和 3 个的），这在比特币中叫 **UTXO（Unspent Transaction Output）**。
21. 转账例子：Alice 要转给 Bob 4 个，两个交易都不够，也**不能拆开**之前的交易，只能把"交易 2"和"交易 3"当成 input，把自己和 Bob 当成 output——Bob 分 4 个，自己分 1 个，这样交易才平衡。
22. 由此：一笔交易可能包含**大量的 Input 和 Output**；因为**没有"余额"概念**，需要通过多个 input 来凑，output 这边还要**给自己找零、给矿工小费**。
23. 交易链：你把钱给我、我又给张三、张三给李四……传递下去形成交易链；因为还没花出去所以成为 UTXO；**系统计算你有没有钱可汇，只需查看你的 UTXO**。
24. UTXO 的优点：①**因为没有账户和余额概念，可以并行进行多笔交易**——有多个 UTXO 就可以多笔交易而**不需要并行锁**；②**匿名性**——可以隐藏交易目的地（通过设置多个 output）；③**无状态**——想知道有多少比特币，统计 UTXO 的交易记录即可。
25. UTXO 的缺点：让人比较费解，**不利于应用上的开发**；以太坊则使用了**余额**的方式。
26. 本篇没录音频的原因：图片很多，很难用音频体现。

## 65｜区块链技术细节：加密和挖矿
> 源文件 `.tmp-zuoer/txt/65丨区块链技术细节：加密和挖矿.txt`，汉字 4,313 字

### 一句话结论
哈希解决"内容没被改"，**非对称加密 + 数字签名**解决"这笔交易确实是你发的"（比特币因此**不需要 CA**，代价是只认私钥不认人）；而**挖矿就是把"找到一个小于 Target 的哈希"变成一个只能用暴力穷举求解、且难度每 2016 块自动调整的抽奖**。

### 知识点全清单（A1 零丢失）
1. 本篇要解决的问题：上一篇解决了"交易信息不能被篡改"，但还有——**我们每个人只能发起和自己有关的交易**（能发起自己付钱给别人，不能发起别人付钱给我、或别人向别人付钱）。
2. **密钥对**：一种非对称加密技术，加密与解密用两个不同密钥；可把其中一个公布出去称**公钥**，另一个私密保管称**私钥**。
3. 用法有两个方向：有人用公钥加密、私钥解密，也有反过来用私钥加密、公钥解密，**得看具体场景**；比特币使用 **ECDSA** 密钥对技术。
4. 公钥加密场景：我把加密的公钥发布给所有人，大家用公钥加密信息，只有我能用私钥解密、看懂密文。
5. 该场景的漏洞：每个人都有我的公钥，别人可以截获 Mike 发给我的信息，然后自己用我的公钥加密另一个信息伪装成 Mike 发给我 → **需要对 Mike 的身份进行验证**，于是需要"数字签名"。
6. 数字签名四步（原文顺序）：
   - ①Mike 对自己想发的信息做 **SHA 或 MD5 的 hash**，得到一个 hash 串，又叫 **Digest**；
   - ②Mike 用自己的**私钥**把 Digest 加密，得到一段 Digest 的密文，这叫**数字签名（Signature）**；
   - ③Mike 把"想发给我的信息用我的公钥加密后的密文"连同他的数字签名一起发给我；
   - ④我用我的私钥解密 Mike 的密文，然后用 **Mike 的公钥解密其数字签名得到 Digest**；再用 SHA/MD5 对解开的密文做 hash，**如果结果和 Digest 一致，就说明这个信息是 Mike 发的、没人改过**。
7. **中间人攻击**：黑客偷偷把 Jack 电脑上 Mike 的公钥换成自己的，然后截获 Mike 发出的信息，用自己的密钥加密一段自己的信息 + 自己的数字签名；对 Jack 来说他以为信息来自 Mike（因为他用的是黑客的公钥），于是黑客可伪装成 Mike 与 Jack 通信，反之亦然。
8. **证书**：Mike 找一个大家都相信的、永不作恶的权威可信机构，由该机构**用自己的私钥**把 Mike 的公钥和相关信一起加密，生成一个**证书**；Jack 用**权威机构的公钥解密证书**得到 Mike 的公钥，再用 Mike 的公钥验证 Mike 的数字签名。
9. 比特币用**公钥做交易账户**：每一笔交易的 From 和 To 都是用户的公钥。
10. 比特币为什么不需要证书机构：如果黑客想伪造别人的交易，需要**换掉半数以上节点上被攻击者的公钥**，这不太现实；与其这样，还不如去偷被攻击者的私钥可能还简单一些。
11. 交易链 A→B→C→D 共 3 笔交易；**交易的发起方只能是支付方**，支付方需用自己的私钥加密交易信息并制作交易签名。
12. 验证方式：网络上其他人用你的公钥（即交易的支出方）解密交易签名，得到交易 hash 值；把交易信息与地址做 hash，比对是否与签名解密后的 hash 一致。
13. 一个细节：**比特币地址由公钥生成，生成规则比较复杂**（可参考 Bitcoin Wiki 的 Technical background of version 1 Bitcoin addresses）。
14. 挖矿公式：**`SHA-256(SHA-256(Block Header)) < Target`**。
15. 区块头里**可以完全自由修改的只有 Nonce**；Timestamp 可以在特定范围内修改；Merkle Root 与你需要记录的交易信息有关（矿工可自由地从待确认交易列表中挑选自己想要的交易打包）。
16. Target 的作用：它决定算出来的 hash 字符串**最前面有几个零**；hash 值本身是相对随机的字符串，要让随机字符串有规律很难，**除了暴力破解没有其他办法**——计算机里把这叫**哈希碰撞（hash collision）**，即碰撞出前几位都是 0 的哈希值。
17. 示例程序：`data="ChenHao"`，循环 `n`，`str = data + n`，两次 sha256，`if hash.startswith('00000')` 则打印并 break；在作者的 MacBook Pro 上**基本要 10 秒钟**才跑得出来。
18. 解：`n = 1192481` 时得到第一个解 → `ChenHao1192481` → `00000669e0eeb33ee5dbb672d3bd2deb0c32ef9879ef260f0debbdcb80121160`。
19. 难度来源：控制前面有几个 0 的是 **Target**，由 **Bits** 字段控制（也就是难度系数）；**前面需要的 0 越多，难度越大**；算法见 Bitcoin Wiki 的 Difficulty 词条。
20. 难度调整：**每出 2016 个区块后调整一次**；当时难度要求**前面有 18 个零**（原文给了真实区块 hash：`000000000000000000424118cc80622cb26c07b69fbe2bdafe57fea7d5f59d68`）。
21. 概率计算：一个 SHA-256 哈希值有 **2^256** 种可能；前面 18 个零意味着前面有 **72 个 bits 是零**；满足条件的哈希值有 **2^184** 种可能，概率是 **2^-72**。
22. 穷举完 Nonce 还找不到怎么办：**调整 Timestamp 和 Merkle Root**（调整不同的记账交易）。
23. 挖矿流程五步：①从网络上取得之前的区块信息；②从"待记账区"获取一组交易数据（**有优先级，比如成长时间、矿工小费等**）；③形成区块头（计算 Merkle Root 并设计记账时间 Timestamp 等）；④开始穷举 Nonce 计算区块头 hash——如果前面有 18 个零（小于 Target）则记账成功，否则**从第一步重新开始**；⑤一旦某矿工成功打包一个区块，就告诉其他矿工；收到消息的矿工**停下手上的工作开始验证**，验证通过后广播给其他矿工。
24. 难度为什么要调整：为了让全网产生区块的时间**平均 10 分钟一块**；比特币是无中心服务器架构，挖矿机器**想来就来想走就走**，算力会变；所以算力不足时难度下降、算力充足时难度提高。
25. 现实门槛：今天的 18 个零，一般的电脑和服务器就不用想了，必须算力非常高的机器；**挖矿已经不是一般老百姓能玩的了**。
26. 能耗数字：截至 **2017 年 11 月 20 日**，比特币过去一年挖矿的电力总消耗累计达 **29.51 TWh**，约占**全球总电力消耗的 0.13%**；该数字甚至已超过**近 160 个国家或地区**一年的电力消耗（包含冰岛和尼日利亚）；若全球比特币矿工自成一国，电力消耗排名可排到**全球第 61 名**。
27. 收尾：为什么要挖矿——为了系统说明，下一篇讲去中心化的共识机制。

### 数字 / 公式 / 阈值
- 公式：**`SHA-256(SHA-256(Block Header)) < Target`**。
- 可自由修改字段：**Nonce（32 位整型）**；Timestamp 可在特定范围改。

### 一句话结论
去中心化共识要解的是**拜占庭将军问题**（叛徒 <1/3 才有解），而 PoW/PoS/DPoS 是三种"给投票权定价"的不同方案——**PoW 用算力（蛮荒）、PoS 用财富（资本主义）、DPoS 用选票（政治）**；三者共同暴露了那条铁律：**去中心化、安全、高性能只能选两个**。

### 知识点全清单（A1 零丢失）
1. 去中心化的共识机制要解决**拜占庭将军问题（The Byzantine Generals Problem）**：**莱斯利·兰伯特（Leslie Lamport）于 1982 年**提出，用来解释一致性问题的**虚构模型**，同时也是分布式领域**最复杂、最严格的容错模型**。
2. 故事设定：将军们没有中心化领导机构，要攻击某城市需对任何将军提出的攻击时间达成共识；只有所有将军达成共识、同一时间攻击才有大胜率；但可能有多个将军同时发出不同计划，且其中有叛徒。
3. **Lamport 证明：叛变者不超过 1/3 时存在有效算法**——不论叛徒如何折腾，忠诚将军总能达成一致；叛徒过多则无法保证一致性。
4. 拜占庭问题难解的两个原因：①任何时候系统中都可能存在**多个提案**（因为**提案成本很低**）；②完成最终一致性确认过程十分困难、容易受干扰。但**一旦确认，即为最终确认**。
5. 比特币的两条设计对策（对应上面两个难点）：①**限制一段时间内整个网络中出现提案的个数**（增加提案成本）；②**放宽对最终一致性确认的需求**，约定大家都确认并沿着**已知最长的链**进行拓宽。
6. 分叉处理：某时刻同时出现两个都合法的区块，**两个都承认** → 区块链出现两个合法分支（术语"分叉"）；矿工可选任一分支继续，**某个分支长度超过另一个时，短的那个马上作废**。
7. 为什么不用 Paxos / Raft（它们资源消耗比 PoW 小得多）——四点本质不同：
   - ①Paxos/Raft **需要 Leader 选举**；比特币/以太坊这样的无中心化方式**没有 leader**；
   - ②Paxos/Raft 加入网络的节点**前提假设都是受信的**；比特币/以太坊**假设都不受信**，只相信**超过一半节点所同意的东西**；
   - ③Paxos/Raft **需要事先对整个集群的节点数有定义**；去中心化网络节点**想来就来、想走就走**，Paxos/Raft 在此环境下会处于"要能随时伸缩"的尴尬境地；
   - ④Paxos/Raft **并不适合在非常大的网络中玩**（比如上百万节点）。
8. 相同点三条：①都是**一致性算法**；②**对系统的修改总是需要一个人来干**（区块链用 PoW 消耗资源让提案变困难，Paxos/Raft 用领导选举）；③**系统中暂时的不一致是可以被修正的**（区块链考虑最长链，牺牲强一致性保证可用性；Paxos/Raft 若没有超过半数节点在线会停止工作，牺牲可用性保证强一致性）。
9. 总判断：区块链面对的无中心化 P2P 网络比 Paxos/Raft 面对的相对中心式网络**复杂得多**，所以不太可能用 Paxos/Raft 替代 PoW——「除非你想干一个相对中心化的区块链，然而这就成了区块链的一个悖论」。
10. 搞区块链或分布式都必须知道的**三个重要理论：CAP、FLP、DLS**。
11. **CAP**：网络发生阻断（partition）时只能在数据一致性（C）与可用性（A）中选一个。直观论证：网络分隔为二，一边送出"把我的十元给 A"，另一边送出"把我的十元给 B"——系统要么 a）无可用性（至少一笔不被接受），要么 b）无一致性（一半看到 A 多十元、另一半看到 B 多十元）。**CAP 与扩展性（scalability）无关，分片或非分片系统皆适用**。
12. **FLP impossibility**：在异步环境中，如果节点间网络延迟**没有上限**，只要有一个恶意节点存在，**就没有算法能在有限时间内达成共识**。
13. FLP 的出路——**"Las Vegas" algorithms**（又叫**撞大运算法**）：保证结果正确，只是在运算时所用资源上进行赌博；简单例子是**随机快速排序**（pivot 随机选，但排序结果永远一致）；这类算法**每一轮皆有一定机率达成共识，随时间增加机率越趋近 1**，这也是许多成功共识算法采用的解决办法。
14. **DLS 给出的容错上限三条**：
    - ①**同步**网络（延迟有上限且上限**已知**）：协议可容忍 **100%** 的拜占庭故障；但超过 **1/2** 节点为恶意节点时会有一些限制条件；注意这里考虑的是"**具认证特性的拜占庭模型（authenticated Byzantine）**"而非"一般的拜占庭模型"——具认证特性指把已过大量研究且**成本低廉的公私钥加密机制**应用到算法中。
    - ②**部分同步**（延迟有上限但**无法事先知道上限是多少**）：可容忍最多 **1/3** 的拜占庭故障。
    - ③**异步**：具确定性质的协议**无法容忍任何错误**；但这篇论文并未提及 randomized algorithms 在这种情况下可容忍最多 1/3 的拜占庭故障。
15. **PoW 的前身 Hashcash**：最初由**哈佛大学女计算机科学家辛西娅·德沃克（Cynthia Dwork）、加州伯克利的 Moni Naor 和 Eli Ponyatovski** 于 **1992 年**的论文 "Pricing via Processing or Combatting Junk Mail" 提出；**一开始是用来限制垃圾邮件**。
16. Hashcash 机制：要求邮件发送方对**邮件头**（其中包括**时间和收件人地址**）计算一个 **160bit 的 SHA-1** 哈希值，其前面需要有 **5 个零**（即 **20bit 的 0**）；接收端会检查这件事。
17. 为什么有效：发垃圾邮件时这点算力对发送方没什么，但对**需要大量发送**的人就是很大成本；就算是控制僵尸网络的黑客，发垃圾邮件导致 **CPU 使用率过高**会马上引起电脑所有者警觉，而且很容易定位恶意程序。
18. 白名单例外：对受信的邮件服务器可放进白名单，不需要它们接受 Hashcash 挑战、不用付出成本。
19. PoW 定义：这种玩法叫 **Proof-of-Work**，用**消耗对手能源**的手段阻止恶意攻击或对服务的滥用（如垃圾邮件）。
20. **PoW 有两种协议**：①**Challenge-Response**，用于 Client-Server——Client 需要使用服务就要被 Challenge 去花费一些资源，证明资源已被花费则通过认证、授权使用；②**Solution-Verification**，用于验证使用，**Hashcash 就是这种**。
21. PoW 在区块链里的另一个功能：让不受控制的分布式 P2P 网络里的节点**统一思想**，即分布式一致性——这对分布式系统中的交易系统非常重要。
22. **PoW 三件事（原文编号总结）**：①**提高对数据篡改的成本**（数据相互依赖导致"一处改处处改"，完全修改要付大量算力）；②**提高网络中有不同声音的成本**（伪造账本成本极大、校验账本成本很小）；③**解决分歧**（分叉时所有矿工只能选一个分支，因为没人有算力同时发出两个不同声音；多数人选择的分支成为事实，少数被遗忘）→ **让整个去中心化系统的一致性不再以"人数多认可的数据"为准，而是以"算力多的人认可的数据"为准**。
23. 作者对"51% 不可能"的怀疑：「只要网络越来越大，能掌握半数以上算力的人基本上是不可能的。是这样的吗？我表示怀疑。」
24. **PoW 的两个严重问题**：①**越来越中心化地记账**——本来要大众一起参与去中心化，现在因为算力问题、因为 **GPU** 出现，一般人几乎无法参与；②**越来越跑不动**——链越来越长，验证数据是否正确的成本越来越高，一般人电脑快跑不起来。
25. 由此比特币社区分裂成好几个衍生品、用不同手段解决；但作者「没有看到什么比较好的方式」——「因为这世界上不存在完美的解决方案，你要一头，另一头就没了」。
26. **PoS（Proof of Stake，股权证明协议）**：为了让每个 Block 更快生成而出现；矿工不再叫矿工，叫 **Validator（校验者）**。
27. PoS 机制：假设有 4 个 Validator，每个以**"交押金"**方式取得记账权；假如 A 押金占 **38%**、B **25%**、C **21%**、D **16%**，就按股权比例获得记账权——A 有 38% 概率获得记账权（**不是由系统随机分配，仍要算 hash，只是财富越多挖矿难度越小**）；若发起恶意攻击，**钱会被系统没收充公**；Validator 记账后**没有奖金，只有手续费**。
28. PoS 的本质：记账权不再由算力大小决定，而由**财富多寡**决定，按财富比例分配。
29. 以太坊的具体口径：根据拥有**以太币的总量**决定成为 Validator 的机率。
30. PoS 两个好处：①**不需要那么费劲挖矿**，解决了浪费电力、不环保的问题；②控制网络的门槛从 **51% 算力**变成 **51% 财富**——今天 51% 算力成本很大，但从全球比特币算力图看「只要前四家公司联合起来作弊，就可以完成对比特币的攻击」（据说中国有 **60%** 左右算力）；而 51% 财富需要更多成本，且「如果你有 51% 的财富，你为什么要黑了这个系统、自己把自己干死呢？这就是博弈论」。
31. **PoS 的潜在问题（本讲最硬的一段）**：
    - ①**Nothing-At-Stake（原文写作 Nothin-At-Stake）攻击**：PoW 下算力有限，矿工只能赌一个分支；PoS 不需要算力，记账人可以**在两个分支上同时进行**以最大化利益（无论哪个分支胜出都有利）。
    - ②**双重支付（Double Spend）**：99% 的人同时发展 A 与 B 两个分支，1% 股份的人在 A 分支写一笔交易、B 分支没有；在 A 上达成合约（如收到商品）后加入 B，B 胜出则这笔交易不存在；也可以 Bob 把 10 元同时借给 Alice 和 Marry（不同分支）——这就是"双重支付"问题。
    - ③与 CAP 的对应：无中心化下**通过分叉来牺牲数据一致性**（一个分叉上 Bob 给 Alice，另一个分叉上 Bob 给 Marry）。
    - ④**贿赂攻击（Bribe Attack）**：攻击者在一个分支上声称购买商品，收货后以提高手续费的方式**只养另一个没有该交易的链**，把它养得足够长，长到系统最终选择没有交易的这条链。
    - ⑤在 PoW 下这种"分叉攻击"基本不可能，在 PoS 下很有可能；以太坊发现有人同时养分叉会惩罚，但**攻击者可以用多个账户（马甲）**绕过。
    - ⑥**可预计算**：PoS 按财富占比决定记账概率，节点可以预先算出下一个 hash 值，相当于可以**偷偷养分叉**。
32. **DPoS（Delegated Proof of Stake，委托股权证明）**：PoS 的进化方案。
33. DPoS 优化的问题：常规 PoW/PoS 中，任何新加入的区块都要被**整个网络所有节点**确认，这是效率的一大影响处。
34. DPoS 做法：通过不同策略，**不定时地选中一小群节点**，由这一小群节点做新区块的**创建、验证、签名和相互监督**，大幅减少区块创建和确认所需的时间与算力成本。
35. DPoS 类比：像**选举人团代议制度**，和美国选总统一样；每个 token 都是选票，大家票选 **20 个选举人团 + 1 个随机选举人 = 21 个**选举人代表网络；每隔一段时间在这 21 人中挑一个出来维护账本并获得收益。
36. EOS 案例（原文带明确时点）：推崇 DPoS 的 EOS 开始 21 个超级节点选举；超级节点获得 EOS **每年增发 5%** 收益中的大部分，约每节点每年 **238 万个 EOS**；按当时价格（EOS/RMB **￥34**）一个节点每年可分到约 **1 亿元人民币**奖励。
37. EOS 定位：以准备颠覆以太坊及整个区块链生态的姿态，打着**提高交易吞吐量到百万级 TPS** 的技术口号；**本文成稿时 EOS 还没有正式发布**。
38. 竞选格局：主要竞选节点来自**中国、美国、韩国**——韩国拥有最大 EOS 交易量，中国拥有更多 EOS 之外的资本，美国有规则制定权；「美国有政治权力，韩国有经济权力，中国这边有外围经济权」，像三国演义式的制衡。
39. **贿选**：中国竞选人把当选后每年应得的"巨额工资"**返还给每一位投自己票的人**；这样搞下去，21 个超级节点很可能被一家公司控制。
40. 反制：创始人 **BM（Dan Larimer）**现身表示不支持节点对投票人分红；**Thomas Cox** 在社区发帖《为什么付费投票是坏的》谴责贿选，并陆续发布 EOS.IO **0.1 版本"宪法"第一条款《不说谎》**。
41. BM 履历（原文八卦但有关"治理"）：**2014 年**创建比特股（打"超级比特币"概念，因 Bug 太多、体验差，后与公司不合离开）；**2016 年**创建社交平台 Steemit（想颠覆传统媒体，也失败）；**2017 年**创建 EOS 瞄准以太坊，想做区块链基础设施（并行运算、数据库、账户系统等）；作者判断「这个对他来说更难」。
42. 作者的两点"变味"观察：①DPoS 已经开始把区块链**去中心化的初衷向中心化方向演进**；②**政治在未来区块链世界里是必不可少的技能**，意味着不可控的复杂性，「我感觉这些技术宅是一定 Hold 不住的」。
43. 小结判断：**PoW 目前仍是比较稳健的共识方式**；PoS/DPoS 还需要更多实践和改进；也许**混合 PoW 和 PoS/DPoS** 也不错；「'去中心化'和'高吞吐'这两个事，我觉得是很难协调的」。
44. 三个社会类比（原文金句）：①**PoW 就是蛮荒社会**——谁的拳头大谁说话，真正意义上的无政府去中心化社会；②**PoS 就是资本主义社会**——谁的钱多谁说话，还是无政府，但是资本家控制的；③**DPoS 就是政治主义社会**——谁的选票多谁说话（"我也不知道怎么个选举，竞选活动吗？有电视辩论吗？"），但感觉又回到了中心化架构中的 **Leader 选举**。
45. 由此的逻辑问题：如果"去中心化的社会"本质上是在**重复一遍"中心化"的演进过程**，那还有什么意义？（留到最后）
46. **三选二（本讲的总纲）**：区块链 P2P 网络下类似 CAP，在**去中心化、安全、高性能**中只能选两个：
    - 要**安全 + 高性能** → 放弃去中心化架构（如 DPoS 这样的中心化系统），干脆走传统中心化架构；
    - 要**去中心化 + 安全** → 主要去挖矿，**放弃高性能**（这就是目前的比特币架构）；
    - 要**去中心化 + 高性能** → **放弃安全**，「没有安全的系统，基本上来说是不会有人用的」。

## 67｜区块链技术细节：智能合约
> 源文件 `.tmp-zuoer/txt/67丨区块链技术细节：智能合约.txt`，汉字 3,296 字

### 一句话结论
智能合约的本质是**"把托管 + 条件释放写成代码，交给一群互不信任的机器执行"**——它替代的是"公证人/银行资金托管"这个角色，但代价是**Bug 也会被无条件执行、且无法协商补救**，所以作者说「还是不要叫'智能合约'，至少现在还不是」。

### 知识点全清单（A1 零丢失）
1. 案例一（打赌）：张三和李四赌周末**拜仁 vs 皇马**谁赢；拜仁赢则张三给李四 **100 元**，反之李四给张三 100 元，**平局不输不赢**。
2. 两人都怕对方不认账，于是找一个都信得过的**公证人**，两人各把 100 元交给公证人；拜仁赢则公证人把全部 **200 元**给李四，皇马赢则全给张三，平局各退 100。
3. 这个模型的问题：**公证人跑路怎么办**？只赌 100 元时犯不着为 200 元跑路；但**一万人**把赌金交给公证人、或赌金是 **100 万**时，「公证人的人性会受到极大的挑战」。
4. 结论：**业务大到一定程度时，个人信用不足以当中间公证人**，要找更靠谱的机构——银行。
5. **银行的信用等级更高的三个方面**：①银行是机构，受政府监管、受法律约束；②银行的钱很多，就算有员工作案，银行也赔得起；③银行里有比较安全的资金管理流程和措施。
6. 银行案例（二手房交易"资金托管"）：房屋交易金额太大，买家怕交了钱卖家不过户，卖家怕过了户买家不给钱；而链家/我爱我家这类中介**没有能力做大额交易担保**（政府也不会让它们做）。
7. 托管流程：买家先到银行开户、把购房款全额存进去；这个账户和一般账户不一样，叫**资金托管账户**，**钱一旦进入就取不出来，除非满足某个条件**；开户时买卖双方和银行**三方约定**：一旦房产证从卖家过户到买家 **30 天**后没有纠纷，钱就划给卖家。
8. 类比淘宝/支付宝：买家把钱转给支付宝，确认收到货后点确认，钱划给商家；**唯一不一样的是支付宝没有资格担保房屋交易这么大的金额**——这是国家为防范金融风险采取的措施。
9. **以太坊智能合约的定义**：其实就是**一段可执行的程序片段**，由发布人用一种**类似于 JavaScript 或 Python 的编程语言**编写。
10. 原文给的合约代码骨架：`Contract MyContract{ function transferFrom(address _from, address _to, uint256 _value) { if (isBayernWin) { blanceOf[_from] += _value; blanceOf[_to] -= value } else if (isRealMadridWin) { ... } } }`（原文代码有拼写/正负号错误：`blanceOf`、`value` 少下划线、赢家加减方向相反；照录并标注）。
11. 作者调侃：「合同都要用代码来写了。看来，我们程序员离统治世界又近了一步。」
12. **部署**：把合约代码在本地编译成功后**发布到区块链上**，可以理解为一个**特殊的交易**（包括可执行代码），然后会被**矿工打包记录在某一个区块中**。
13. **调用**：需要调用合约方法时，只需**向这个智能合约的地址发送一笔交易**即可。
14. **执行**：每个节点的电脑都要安装以太坊客户端，客户端自带一个**和 JVM 类似的 EVM**；通过交易触发智能合约后，合约代码就在 **EVM** 中执行。
15. 本质：这相当于把程序**部署到非常非常多的电脑上**，随时可通过交易触发执行，从而完成了**分布式程序的部署和调用**。
16. 作者定性：「这感觉就是 **Function-as-a-Service** 的一种实现。」
17. 愿景设问：如果人与人之间的交易条件（合约）像代码一样被严格执行，世界会变成什么样？「是不是会少一些无赖，少一些扯皮，多了很多效率，多了很多确定性呢？」
18. 案例二（国际贸易）：中国出口商与美国进口方做生意会遇到货币不一样的问题；没有货币兑换就只能用大家都认可的**黄金**交易（发一船货、发一船黄金），风险高、效率非常低。
19. 有银行协调时（中美两家银行签了互信协议）的**11 步流程**：①出口商与进口商签买卖合同；②美国进口方向美国银行**申请信用证**；③美国银行向中国银行开信用证；④中国银行收到后向出口商发**通知信用证**，告之可以发货；⑤出口商发货，承运人把货运到美国；⑥出口商把**提货单**交给中国银行；⑦中国银行向美国银行发出"**寄单索汇**"；⑧美国银行收到提货单后通知进口方**到单**；⑨进口方把货款补完（如补 **300 万美金**）"**赎回**"提货单；⑩美国银行向中国银行付款；⑪美国进口方到承运人处提货。
20. 信用证的价格属性：**信用证需要用钱来开**——比如 **200 万美金**的信用证，就需要用 200 万美金来申请。
21. 关键点（第 3 步）：中国银行**根本不关心进口方有没有把钱给美国银行**，反正你开了 200 万美金面额的信用证，我以后要问你要钱。
22. 智能合约版的三步：①进口方把钱垫到区块链上；②出口方发货；③进口方验货后钱就到了出口方。「好像可以写得很简单。」
23. 但有四件事必须写进程序：①进口方的钱垫到区块链上**需要被冻结**；②**需要物流信息**，否则进口方说没收到不好验证——但**物流信息要是造假怎么办**？③需要把**进口方验货的标准**写进来——代码不知道条件怎么满足，也许需要进口方点个确认；**如果不点确认，则有个过期时间，时间一到就自动确认**；④如果进口方觉得有问题要退货或重新议价，**需要相关的关联合同**。
24. 最难办的是第 ② 步：**需要其他方也进入区块链**，「如果不进来，这事就不好玩了」。
25. 物流真实性的两难：需要双方选一个都相信的**中心化的物流公司**，还是搞一个**去中心化的物流公司**？「去中心化的物流公司是个什么形态，你能想像得出来吗？我想象不出来。」
26. **合同的 Bug**：有程序的地方就会有 Bug；现实生活中有 Bug 可以相互协商、给合同**打补丁**（附加条款或重新签合同）；但**代码合同不一样——Bug 也会被残酷无情地执行，一旦执行就很难补救了**。
27. **The DAO 案例**：一个去中心化的风险投资基金，以智能合约形式运行在以太坊区块链上；也是盈利性的**去中心化自治组织**，用自己掌控的以太币投资以太坊上的应用为成员创造价值；创建期任何人都可以向它的众筹合约发送以太币、获得 **DAO 代币**。
28. 事故：因为 The DAO 程序写得不好，黑客在智能合约里找到 Bug 把所有的钱调走，**约 7000 多万美刀**；这是**有史以来最大宗的数字劫案**，而且 **FBI 也找不到人**；项目因钱被偷而倒闭后，**引起以太坊强行分叉成 ETH 和 ETC**。
29. **Parity 案例（2017）**：智能钱包（多签名钱包）Parity 被盗；它号称智能合约被很多很厉害的安全人员审查过、都认为没问题，但最后还是被黑客利用一个叫 **initwallet 的函数反复调用**，转走 **3000 万美金**。
30. 作者的最终判断：任何合同都会有 Bug（现实或代码）；唯一不同是现实合同出 Bug 可自行协商，也可通过法律或仲裁解决，而**数字社会里代码无论好坏都会被计算机残酷无情地严格执行**。
31. 立场的两面性：当你是利益方时觉得是好事，当你是受害方时还是想有挽回余地；「现实生活中可以做到，但我不知道代码世界中的合同如何解决这些 Bug」。
32. 结论金句：**「所以还是不要叫'智能合约'，至少现在还不是。」**

## 68｜区块链技术 - 传统金融和虚拟货币
> 源文件 `.tmp-zuoer/txt/68丨区块链技术 - 传统金融和虚拟货币.txt`，汉字 6,659 字

### 一句话结论
金融的本质是**"促进交易完成、实现价值提升"**，为此它必须解决信用、资金不足、大额拆分三个问题，并靠监管平衡"资"与"债"；虚拟货币既没有经济体背书、也没有风控与评级，**它的繁荣只是"支出驱动"的又一轮泡沫**——用作者的话说，「这就是一个高级赌场罢了」。

### 知识点全清单（A1 零丢失）
1. **金融的本质（作者观点）**：金融行业最大的本质就是——**促进交易完成，实现价值提升**；整个社会的交易能更快更高效更安全地完成，社会就有更好的运作效率、更低的成本、更多的价值，这对促进社会经济发展相当关键。
2. **金融要解决的三个问题**：①**交易中的信用问题**（所以银行来做中间人担保）；②**交易中的资金不足问题**（通过借贷让交易完成）；③**交易中的大额问题**（把一个大额金融事件以股份的方式拆碎进行大众投资）。
3. **金融行业的四个重要属性**：①**效率提升**——加快货币、股票、债券的流通性，快速促成交易；②**价值提升**——通过金融产品的流通性，让实际价值得到充分体现并升值；③**激励机制**——为实体经济添砖加瓦，激励社会持续付出和成长；④**信用评级**——建立信用社会、评估信用等级，从而改善社会。
4. 但金融机构不是高枕无忧：「主要是钱不够多，只要钱多到一定数量的时候，什么事都可能发生。因为**逐利是人性中非常疯狂的一个特征**。」
5. **经济是什么**：说白了就是整个社会的交易；每笔交易中买方付出**货币和信用**，卖方支付**商品、服务或金融资产**；**支出方是整个经济的驱动力**，经济状况好坏受支出方影响。
6. 需要"**贷款机构**"：把钱贷给想花钱且有偿还能力的人，这会增加整个社会的支出。
7. 循环机制：**你的支出成为别人的收入**；别人收入多了也会增加支出；支出越来越多，某些人收入越来越多 → 钱花不完 → 想用钱生钱 → 更多人借钱给别人（即**投资**）→ 又增加更多支出 → 整个社会运作起来。所以「**支出是经济的原动力**」。
8. 两条提升价值的路径：①提高**生产率**——但生产率不容易提高，是长期过程；②通过**借贷**短期提高经济价值——借贷发生时消费超过产出，还贷时消费低于产出。
9. **影响经济波动的东西就是"借贷"**：为购买现在买不起的东西，向未来的自己借钱、或由未来的自己还债；这种未来消费不一定是坏事——**能还就是良性，还不了就成了恶性**。
10. 泡沫的形成机制：支出变多 → 一片繁荣 → **大多数人目光短浅**，觉得经济形势很好 → 更多借贷 → 借钱买其他金融产品 → 金融产品上涨 → 觉得该花更多钱投资 → 借更多钱 → 巨大泡沫。
11. 推荐材料：网易公开课《经济机器是怎样运行的》。
12. **2008 年次贷危机**：自 **2003 年**来美国房价不停上涨，买房贷款的人基本上都有比较稳定的工作来每月偿还房贷；于是这些人的信用记录导致**房贷成了比较好的金融产品**。
13. 三级市场：美国房地产贷款系统分为**优质贷款市场、次优级贷款市场、次级贷款市场**；消费者信用等级分为**优级、次优级、次级**——能按时付款的是优级，不能按时付款的是次级。
14. 次级贷款市场：面向**收入信誉程度不高**的客户，**贷款利率通常比一般抵押贷款高出 2%～3%**；尽管占美国整体房贷市场比重不大（**约 7%～8%**），但**利润最高、风险最大**。
15. 当时的"安全逻辑"：供房人能还款就是优质贷款；不能还了就把房子收回来**卖个高价**——毕竟房价一直在涨。
16. 证券化链条：资本家觉得房贷回报优秀，就把这些**债权出售**（债权转让可让资金快速回来，但挣得不够多）→ 把房贷**打包**成优质金融产品 → 在**二级市场发行 IPO**，让更多人来投资和炒作 → 挣一大笔；只要供房人按时供房这个产品就没问题，于是再**衍生更多金融产品、各种"杠杆"**，再加上**保险公司为其保险**。「全世界都疯了。」
17. 放贷标准崩坏：银行开始乱放贷款，放给好多根本没有能力还款的人；在"房价将继续升值"的假设下，鼓励许多次级借款人去取得**浮动利率抵押贷款**——这些贷款以在预先确定的期限内**低于市场利率**引诱借款人，期限过后按市场利率计算。
18. 评级失真：**美国最权威的评级机构也错误地把风险比较高的金融产品评成最优质的级别**，这样在二级甚至三级市场上套更多的人进入。
19. 崩塌链条：底层越来越多人不还贷款 → 越来越多房子被拍卖 → 一方面**房价下跌**、另一方面**银行坏账** → 最终像**多米诺骨牌**一样倒了一片。
20. 救市与后果：因为玩得太大，**美国政府拿出 7000 亿美金**救那些贪婪的银行；一些投资机构破产；对国内经济造成巨大打击。
21. 监管的必要性：银行业过于快速地促成交易、加快流通性，导致各种"杠杆"以及"多杠杆"；当整个社会为之疯狂时，**信用评级、风险控制都被抛到脑后**，最终投资大大超过与实际价值完全不等价的局面；实际价值无法支撑投资时，风险发生就会出现连锁反应、一发不可收拾。
22. 核心平衡：经济活动要平衡**"资"与"债"**，不平衡风险就出现——对个人、企业、银行都一样；但总有人被财务窟窿或巨大利诱冲昏头脑，**所以需要监管机构审查金融机构的资债风险、制定政策和条例**。
23. 监管的两难：有时**管得过死**导致经济不能充分发展，于是出现「**不管就乱，一管就死**」的局面；所以政府/央行常通过**调节货币利率、发行更多货币**等手段引导或调整市场、控制风险。
24. 经济学派别（原文点到）：主张政府强干预的**凯恩斯经济学**；**马克思主义的政治经济学**（均表示对市场经济没有信心、需政治干预）；**亚当·斯密**的以市场为主导的经济学。
25. 作者立场：经济还是需要**自由**的，政府应该控制的是**风险**和**保证经济实体的产权**；只有自由的市场经济才会回归金融本质、促进交易提升、激励大众提升价值；而政府的风控措施可以对整体金融风险进行调节，**这是市场经济不能完成的**；政府还要**保护私人产权**——「产权保护是经济活动的根本基础」。
26. **虚拟货币要成为货币的条件**：首先要**保持稳定**——这个稳定**不仅仅是不增发**（看过经济原理就知道**增发货币并不一定是个坏事**），其**价值最好也稳定**，因为它要代表某种经济体的稳定性（就像美金、欧元、英镑要比非洲某些国家的货币更硬）。
27. 现实判断：目前**虚拟货币没有一个经济体为其背书**，所以**远远达不到货币的功能**。
28. 退化为"股票"：股票需要后面**实体公司的经营情况**来背书，流通性好的股票一般需要**透明公开**公司经营情况并受行情和政策影响；而虚拟货币的交易所市场**完全在售卖概念**，到目前**还没有一个真正成功的、能有颠覆性的项目**，然而**靠发布白皮书就可以变成一个几十亿规模的公司**。
29. 泡沫的动力学：区块链里的经济靠**二级市场**撑着；只要有不停的支出就会造就繁荣景象；这种繁荣对绝大多数不明真相的人很容易心动，因为**人性是想不劳而获且趋利避害**；于是更多人进入 → 更大的繁荣。
30. 破灭条件：这种**后台没有价值体现**的玩法总有一天达到瓶颈——**支出不再能够维持下去**的时候，也就是**没有新人入场**、**老人因为钱投进去了不会再有更多钱投入**的时候，那时就是泡沫破灭的时候。
31. 作者的结论：就算是虚拟货币、数字货币，本质也一样；如果**不能提高效率、降低成本，没有风控和评级**，这样完全自由地发展，风险非常大——「说白了，这就是一个**高级赌场**罢了，人类历史上已经有过无数这样的案例」。
32. **比特币的三个问题**：
    - ①**交易成本上升**：PoW 消耗大量算力；约 **10 分钟**产生一个区块；区块大小只有 **1MB**，仅能包含**三四千笔**交易；平均每秒只能处理 **5~7（个位数）笔**交易；网络拥堵非常严重——有时一笔交易确认的小费已经很高（**并不见得比银行便宜**），确认时间很长，**拥塞时需要好几天**。
    - ②**个人无法参与**：链已经非常长，个人电脑跑不动，算力很难校验账本；**记账的人也越来越趋于巨大的大公司**——本来是全民参与的去中心化的事，现在成了大众无法参与的事，「那么，这还是去中心化吗？」
    - ③**社区的利益纷争**：上述两个技术问题急待解决，否则「这一两年比特币也就快玩完了」；但自从中本聪把工作交给核心团队（core team）并消失后，核心团队和矿工就这些技术问题如何解决的谈判**就没有谈好过**——「其中的利益纷争和中心化的组织结构没什么两样」。
33. 作为标杆的比特币尚且如此，其他数字货币更甚；但要解决这些问题，「**就会像前面所说的那样，你就需要适当去中心化了**」。
34. **三个功能问题**（作者认为不解决同样有很大风险）：
    - ①**交易时的身份验证**：银行对网上交易的验权相当复杂，**不同金额有不同验证**；虚拟代币**只关心私钥，而不关心是不是这个人**。
    - ②**资金归属权保护**：银行体系里卡丢了、密码丢了、U 盾丢了，可以**申请冻结账户**，并能到柜面把财产声明回来；虚拟代币**密码和私钥丢了就真的丢了**。
    - ③**损失赔偿问题**：作者表妹在英国 ATM 取款时接了个电话、忘取卡就走，被后面的人取走 **2000 英镑**；报警后银行向警方确认，**把失窃的钱全部赔给了她**。
35. 作者的补救判断：第一个问题还好解决；**第二个问题在区块链上没有解**；想解决第三个问题需要**一整套社会运行机制**，区块链技术更显得无能为力。
36. **技术驾驭能力问题**：这种去中心化的技术难题并不是什么人都能 Hold——一方面是**节点是不可信任的假设**，另一方面其中有**太多政治上的博弈问题不是技术能解的**；所以说用区块链解决各种业务问题并颠覆现有大公司的人或公司，「我觉得他们无论是在业务上还是技术上的水份都很大」——「这是不是一个概念炒作远远大于实际能力的乌托邦？」
37. **逻辑问题一：比特币颠覆了什么？**有人说「比特币本来应该要证明一个真正的自由市场力量，结果却充满了诈骗者、投机者和小偷，而且对真实世界的交易没有帮助，还消耗了这么多的社会资源」；中本聪本意是建立避开政府、银行家和企业的支付系统以避免通胀或金融腐败，但相反，比特币现在是**一堆快速膨胀的投机泡沫**，创造了**另一个和传统世界一样的金融体系**。追问：数字货币是在颠覆传统金融，还是建立另一个一模一样但充满更多泡沫和投机的体系？
38. **逻辑问题二：是否消除了中间商？**如今比特币已有各种中间商（如把零碎比特币存储成账户的**钱包服务**）；这些中间商**破坏了比特币的隐私特性**（像 **Coinbase** 这种中间商会搜集跟用户有关的大量信息）；这不能怪中间商贪婪，而是**比特币本身的设计让交易变得非常复杂**，对非技术背景用户，没有中间商或应用简化，使用起来不便利。追问：比特币原意是建立无需银行和中间商、无交易费的系统，现在却**反过来复制了原本想破坏的体系**。
39. **逻辑问题三：大公司参与的区块链？**看到高盛、蚂蚁金融这样的公司参与区块链，「你有没有觉得有点奇怪？」有人评论"区块链就是需要大公司来参与"——「我不知道中本聪会怎么想？反正我感觉有很强烈的喜感」；类比：「**我造了一列火车，而要用这些马车来拉**」。
40. **逻辑问题四：投资人投资去中心化的公司？**如果投资人看好去中心化能颠覆大公司，就把钱投给"去颠覆中心化的大公司的这些公司"，而这些公司又会成为中心化的大公司——「这看起来好奇怪啊。因为**真正的去中心化是完全找不到主体的**」。追问：去中心化需要有公司吗？有公司还能叫去中心化吗？投资人不傻，他们想来这里面干什么？是投机吗？
41. **逻辑问题五："有挣大钱的机会，你会共享出来？"**——**传销组织的三个阶段**：①让你觉得你很穷困，告诉你致富的捷径；②**模糊掉具体细节**，用各种高大上的**类比和比喻**来取得你的信任；③通过**发展下线**制造虚假繁荣，让你信以为真；虚拟货币中绝大多数都有这样的特征，与骗子的技巧如出一辙——「我有一个挣大钱的机会，但是我想和你共享出来，只需要你对我投资一点钱，未来你可以得到百倍的分红」。追问：在区块链中你有没有发现这样的身影？为什么他们要把这样超级革命性、可以挣大钱的项目在这么早的时候就分享给这么多人？
42. **最后的哲学问题**：一个社会出问题时，民众抱怨发泄需要一个**目标**——有人告诉大家"你们穷、苦、不公，是因为中间商玩弄了你们，是因为政府不可信，是因为有坏人"；这是**最好被民众理解的**，因为有明确目标、简单粗暴，这也是人们容易被煽动的原因。
43. 但社会运作其实是**一种协同**，由多方带着不同利益或诉求形成；问题的出现是**多方造成的、是社会协同出了问题造成的、是机制造成的**，并不是其中某个实体造成的。
44. 机制的铁律：**无论你制定出什么样的机制或规则，都会有好的一面和不好的一面，这一面有多好另一面就有多不好**；所以「如果一件事完全只有好的，而没有不好的，那么，你有绝大可能是在被人在忽悠中」。
45. 三个终极追问：**去中心化就是好吗？我们不需要权威机构了吗？技术可以解决信任问题吗？**
46. 最后一个价值选择：是继续改善我们现在这个社会，还是直接毁了再建一个？是「**破坏性的建设（Disruptive Construction）**」，还是「**建设性的破坏（Constructive Disruption）**」？——「我不知道你喜欢哪个，而我喜欢后者。」

  2. `76.5 合规审计与多活` 增补 **「监管为什么存在：资债失衡的连锁反应」**：只取**因果结构**（杠杆放大 → 评级失真 → 抵押品价格反转 → 多米诺），**不取** 2008 具体金额与机构名（时效 + 政治敏感）；并保留"不管就乱、一管就死"这条两难，作为合规设计必须承认的边界（对应 76.5 现有的"留痕/报送"要求）。
  3. `85.5 容量与成本事故` **不适用**（那是技术容量事故，不是金融风险），不要硬塞。
  4. 虚拟货币的 5 个逻辑问题、传销三阶段、徐小平/李笑来/薛蛮子、币价与 EOS 竞选：**整体不取**。理由：①强时效（2018 年事件与人物）；②强观点（属于价值判断，不是技术原理）；③与书稿"架构与工程"的定位不符，放进去会让 76 章变成评论集。唯一值得留的一句是 **"如果一件事只有好没有坏，你多半在被忽悠"**——可放在 `86.1 术语表` 或某节"反模式"的开场，作为**评估新技术的通用启发式**（它跟区块链无关也成立）。

## 区块链 6 讲（63–68）的总判断：哪些可迁移、哪些是时效

**可迁移（进书，且能脱离"币"独立成立）**
1. **哈希链 = 把"不可篡改"降级成"改动有连锁成本"**（63/64）。这是内容寻址存储、审计日志、增量校验的通用手法，与币无关——**书里 3.5 已经在审计日志里用了，但缺"为什么是它"的说明**。
2. **Merkle 树 = O(log n) 的集合校验**（64）。书里 18.1 已用它做反熵找差异，缺的是"作为交易集合承诺"的第二种用法（改一笔交易根就变）——同一结构、两种目的，值得并置。
3. **UTXO vs 余额 = 两种账本建模范式**（64，**书里 0 命中**）。无状态/可并行/匿名 vs 有状态/易用，是数据建模层面的取舍，不是币圈知识——也是本批最干净的一块增量。
4. **签名四步 + 中间人→CA 的成本论证**（65）。任何做鉴权的系统都用得上。
5. **拜占庭容错与三种"投票权定价"**（66）：算力/质押/选票，以及"去中心化-安全-高性能三选二"。这是分布式原理，书里 21/22 章正要它。
6. **托管状态机 + 条件不可判定性 + Bug 不可回滚**（67）。这是金融与交易系统的常青问题。
7. **金融的动机层：促进交易、解决信用/资金/大额三问题、资债平衡与监管两难**（68）。这是 76 章现在最缺的"为什么"。

**不可迁移（时效性内容，建议不取或只留一句）**
1. **币价、市值、ICO 监管、徐小平截图、李笑来/薛蛮子/BM 履历、EOS 21 超级节点竞选与贿选、￥34 与 238 万 EOS**（63/66/68）——2018 年事件与价格，2026 年读者无信息增益，且带强观点。
2. **"固定发行量 = 不通胀"**（63）——货币政策主张，与技术原理无关，且与 68 自己"增发不一定坏"冲突，取之会把书稿拖进争论。
3. **比特币区块头 6 字段的字节长度、1MB 上限、当年"18 个零"、29.51 TWh/第 61 名**（64/65）——版本与年份快照。可留**量级**（"百 TWh 级"、"约 7 TPS"），不留具体数字；21.14 已经这么处理了，照它的口径。
4. **以太坊/Solidity/EVM 代码、Parity 的 `initwallet`、The DAO 的 7000 万美元**（67）——技术栈与事故金额都过期；但**"Bug 会被无情执行且不可回滚"这条结论要留**，事故只作一句脚注。
5. **"去中心化必然让大公司倒闭""虚拟货币是高级赌场""传销三阶段"**（63/68）——价值判断，不是原理。若要保留，只保留**可判定的那句**："如果一件事只有好没有坏，你多半在被忽悠"，且放在"评估新技术"的语境里，而不是"批判区块链"的语境里。
