## 33｜编程范式游记（4）- 函数式编程
> 源文件 `.tmp-zuoer/txt/33丨编程范式游记（4）-函数式编程.txt`，32,031 字符

### 一句话结论
函数式编程的本质是把「怎么做」从代码里抽走，只留「做什么」：以 stateless + immutable 为地基，用函数组合（高阶函数、柯里化、递归、map/reduce、pipeline）替代带状态的流程描述，从而换来并行无伤害、拷贝重构无伤害、执行无序依赖与确定性。

### 知识点全清单（A1 零丢失）
1. **历史定位**：函数式编程比计算机还古老，基础模型来自 λ 演算；λ 演算并非为在计算机上执行而设计，是 Alonzo Church 与 Stephen Cole Kleene 在 **20 世纪 30 年代**引入的、研究函数定义/函数应用/递归的形式系统。
2. **Alonzo 的判断**：booleans、integers 或其他数据结构都可以被函数取代掉。
3. **理念来自数学代数**：给 f(x)、g(x) 就能组合出 h(x)，还能递归定义斐波那契；函数式只关心「输入数据与输出数据的关系」，数学表达式本质是**映射（mapping）**。
4. **两大核心特征（表格）**：
   - `stateless`：函数不维护任何状态，核心精神就是不能存在状态——"你给我数据我处理完扔出来，里面的数据是不变的"。
   - `immutable`：输入数据不能动，动了就有危险，所以要返回**新的数据集**。
5. **四条收益**（原文逐字）：没有状态就没有伤害 / 并行执行无伤害 / Copy-Paste 重构代码无伤害 / 函数的执行没有顺序上的问题。理由：状态是并行与 copy-paste 时 bug 概率高的根源，"没有状态就没有伤害，就像没有依赖就没有伤害一样"。
6. **惰性求值**：需要编译器支持；表达式不在绑定到变量时立即求值，而在值被取用时求值。`x := expression;` 只是登记，直到后续表达式引用 x 产生需求才计算，且后续表达式自身的求值也可被延迟，最终为生成外界可见的符号去计算这棵**快速增长的依赖树**。
7. **确定性**：如数学中 f(x)=y 在任何场景都得同样结果；程序里同一个参数在不同场景算出不同结果，就是因为函数依赖了运行中的状态信息。
8. **纯函数的语言支持分档（三档）**：完全纯函数式 = **Haskell**；容易写纯函数 = **F#, Ocaml, Clojure, Scala**；纯函数需要花点精力 = **C#, Java, JavaScript**。
9. **纯函数写法要旨**：传进来的数据不改，改完复制一份拷出去，且没有状态。
10. **思维门槛**：过程式是在把具体流程描述出来，可以不假思索；函数式的抽象度更大，"函数套函数，函数返回函数，函数里定义函数"，容易把人搞糊涂。
11. **函数式用到的七项技术**：
    - `first class function`（头等函数）：函数可像变量一样被创建、修改、传递、返回，或在函数中嵌套。
    - `tail recursion optimization`（尾递归优化）：递归深了 stack 受不了、性能大幅下降；尾递归每次递归重用 stack。需要语言/编译器支持，**Python 不支持**。
    - `map & reduce`：对集合做 Map/Reduce，比过程式的 for/while + 变量倒来倒去更易读；很像 C++ STL 的 `foreach`、`find_if`、`count_if`。
    - `pipeline`（管道）：把函数实例成一个个 action，放进数组/列表，数据像 pipeline 一样顺序被各函数操作。
    - `recursing`（递归）：简化代码，把复杂问题用极简代码描述；"递归的精髓是描述问题，而这正是函数式编程的精髓"。
    - `currying`（柯里化）：把一个函数的多个参数分解成多个函数、多层封装，每层返回接收下一个参数的函数；C++ 里类似 STL 的 `bind1st` / `bind2nd`。
    - `higher order function`（高阶函数）：函数当参数，把传入的函数封装后返回这个封装函数；现象上是"函数传进传出，就像面向对象对象满天飞"；**这个技术用来做 Decorator 很不错**。
12. **非函数式 vs 函数式最小对照**：`int cnt; void increment(){cnt++;}`（有状态、多线程不安全）对 `int increment(int cnt){return cnt+1;}`（纯函数、随便拷、与线程无关、并行不用锁）。
13. **柯里化示例**：`def inc(x): def incx(y): return x+y; return incx` → `inc2 = inc(2)`、`inc5 = inc(5)`，`inc2(5)=7`、`inc5(5)=10`；用 inc() 构造出各种版本的 inc 函数。
14. **Lisp/Scheme**：所有操作都是函数（含加减乘除），表达式形式为 `(函数名 参数1 参数2)`；`(define (plus x y) (+ x y))` 用内置 `+` 定义新函数；`lambda` 匿名函数可定义 f2 = 5x²+10；阶乘两版（普通递归 `(if (<= x 1) 1 (* x (factoral (- x 1))))` 与尾递归 `iter` 版）；`(plus 10 (times 5 (times x x)))`。
15. **范式更名**：过程式 = Imperative Programming（指令式）；函数式 = Declarative Programming（声明式），核心是 describe what to do, rather than how to do it。
16. **声明式三步演进（三辆车例子）**：3 辆车、每辆 **70%** 概率前进一步、共 **5 次**机会，打印每次前行状态。
    - 第 1 版（纯过程式）：`while time` + `for i in range(len(car_positions))` + `random() > 0.3` + `print '-' * car_positions[i]`，两个循环一个函数。
    - 第 2 版（拆函数但仍共享状态）：`move_cars()` / `draw_car()` / `run_step_of_race()`（`global time`）/ `draw()`；好处是主干清晰、函数自解释、读代码要考虑的上下文变少；坏处是**函数靠共享变量同步状态**，读到一个外部变量就要在大脑里推演它的状态。
    - 第 3 版（函数式）：`move_cars(car_positions)` 用 `map(lambda x: x+1 if random() > 0.3 else x, ...)`；`run_step_of_race(state)` 返回新 dict `{'time': state['time']-1, 'car_positions': ...}`；`race(state)` 用递归替代 for。
    - 函数式的三个特点：**没有共享变量 / 通过参数与返回值传数据 / 函数里没有临时变量**。
17. **函数式三套件**：Map、Reduce、Filter（谈 C++ 泛型时已介绍）。
    - 字符串转大写：非函数式 `for i in range(len(upname)): lowname.append(upname[i].lower())`；函数式 `map(toUpper, [...])`。C++ 对照 `transform(s.begin(), s.end(), back_inserter(out), ::toupper)`。
    - 正数平均值：非函数式要 `positive_num_cnt` / `positive_num_sum` 两个累加器 + `if num[i] > 0`；函数式 `filter(lambda x: x>0, num)` 再 `reduce(lambda x,y: x+y, positive_num)/len(positive_num)`。
    - 三条好处：数据集/操作/返回值放在一起；没有循环体就少了控制变量与"数据倒来倒去"；代码变成描述"要干什么"而非"怎么干"。
18. **map/reduce 的哲学**：map 和 reduce 不关心源输入数据，"它们只是控制，并不是业务"——**控制是描述怎么干，业务是描述要干什么**。配图：面包和蔬菜 map 到切碎操作，再 reduce 成汉堡。
19. **pipeline 借鉴 Unix Shell**：前面命令的输出成为后面命令的输入，完成流式计算。设计哲学是 **KISS：让每个功能只做一件事并做到极致**，影响 Web Service、云计算、大数据流式计算。示例 `ps auwwx | awk '{print $2}' | sort -n | xargs echo`（进程列表→取第二列 PID→排序→显示）。抽象 `xargs(echo, sort(n, awk('print $2', ps(auwwx))))`，或 `for_each(result, [ps_auwwx, awk_p2, sort_n, xargs_echo])`。
20. **pipeline 与分布式架构的类比**：把函数比作微服务，管道就是在做**服务编排**；Unix 这类经典实践的方法论与分布式架构相通，"一个好的分布式架构师，通常都是对这些传统的微观上的经典技术有非常深刻的认识"。
21. **process() 三步**：① 找出偶数 ② 乘以 3 ③ 转成字符串返回。非函数式版本对奇数 return（打印 None），输出 `None / The Number: 6 / None / … / The Number: 30`。
22. **pipeline 三种实现**：
    - ① generator 版：`even_filter` / `multiply_by_three` / `convert_to_string` 各用 `yield`；`yield` 返回 Generator（可迭代对象），**并未真正执行函数**，被迭代时才跑到 yield 处停住，这就是 lazy evluation（懒惰加载）。
    - ② map/reduce 版：三个函数用 `filter`/`map` 实现，再嵌套调用 `convert_to_string(multiply_by_three(even_filter(nums)))`；本质是"对一堆函数做一个 reduce"，于是 `def pipeline_func(data, fns): return reduce(lambda a, x: x(a), fns, data)`，调用 `pipeline_func(nums, [even_filter, multiply_by_three, convert_to_string])`。
    - ③ decorator/Pipe 版：`class Pipe` 实现 `__ror__`（`|` 运算符重载）产出 generator，`@Pipe` 装饰三个函数，再 `force(nums | even_filter | multiply_by_three | convert_to_string | echo)`；`force(sqs)` 只是 `for item in sqs: pass` 触发求值。
23. **小结口径**：函数式 = 把运算过程尽量写成一系列嵌套函数调用，关注做什么而非怎么做，故称声明式；特点是无状态、不可变、代码简洁、易理解、便于并行、易于重构、执行无顺序问题、支持惰性求值、有确定性。

## 34｜编程范式游记（5）- 修饰器模式
> 源文件 `.tmp-zuoer/txt/34丨编程范式游记（5）-修饰器模式.txt`，19,919 字符

### 一句话结论
修饰器模式的本质不是"加注解"，而是**用一个函数构造另一个函数**，从而把日志、计时、路由、缓存这类"控制型代码"从业务函数里抽出来；Python 的 `@` 只是把 `func = decorator(func)` 写成语法糖，Java/C# 的 Annotation 只是打标签（还要另一套类扫描），Go 没有语法糖只能靠函数值或 reflect。

### 知识点全清单（A1 零丢失）
1. **三种叫法**：Decorator 模式 = 修饰器模式 = 装饰器模式；承接上一讲的 `decorator` + `Generator` 组合出的管道。
2. **与 Java Annotation / C# Attribute 的对照**：使用上相似（方法名前加 `@XXX` 装饰）；但 Java/C# 的 Annotation "太过于复杂"，要玩它得先了解一堆 Annotation 类库文档，"感觉几乎就是在学另外一门语言"。
3. **Python 的优雅之处**：不需要掌握复杂 OO 模型或 Annotation 的各种类库规定，**完全是语言层面的玩法：一种函数式编程的技巧**。
4. **本质一句话**：这个模式动用了函数式编程的一个技术——**用一个函数来构造另一个函数**。
5. **Hello World 三要素**：① `@hello` 的 hello 就是前面定义的函数 hello；② hello 需要 `fn` 参数（用来做回调的函数）；③ hello 返回 inner 函数 `wrapper`，wrapper 回调 `fn` 并在前后各加两条语句。输出 `hello, Hao / i am Hao Chen / goodbye, Hao`。
6. **语法糖展开式（核心机制）**：`@decorator\ndef func(): pass` 被解释器解释成 `func = decorator(func)`。三个要点：函数当参数传进另一个函数、被回调、**还有一个赋值语句把 decorator 的返回值赋回原来的 func**（这一步最容易被忽略）。
7. **带参数的修饰器（两层结构）**：`makeHtmlTag(tag, *args, **kwds)` 必须返回一个 `real_decorator`，才能让 `hello = makeHtmlTag(arg1, arg2)(hello)` 成立；real_decorator 再返回 `wrapped`，wrapped 里回调 hello。示例双装饰 `@makeHtmlTag(tag="b", css_class="bold_css")` + `@makeHtmlTag(tag="i", css_class="italic_css")`，输出 `<b class='bold_css'><i class='italic_css'>hello world</i></b>`（内层先作用）。
8. **memoization（缓存修饰器）**：`cache = {}`、`miss = object()` 作哨兵；`wrapper(*args)` 先 `cache.get(args, miss)`，miss 才 `fn(*args)` 并写回。效果：fib 递归里 fib(3)、fib(2)、fib(1) 在整个过程中至少被调用两次，加缓存后"从二叉树式的递归成了线性的递归"。
9. **`@wraps(fn)` 的作用**：保证 fib 的函数名不被 wrapper 取代（`from functools import wraps`）。
10. **类方式的 decorator**：`__init__()` 在"给某个函数 decorate 时"被调用（需 fn 参数）；`__call__()` 在"调用被 decorate 的函数时"被调用。输出顺序：`inside myDecorator.__init__()` → `Finished decorating aFunction()` → `inside aFunction()` → `inside myDecorator.__call__()`；作者评价"看上去要比『函数式』的方式更易读一些"。
11. **注册表式用法（URL 路由）**：`MyApp` 持有 `func_map`，`register(name)` 返回 `func_wrapper(func)`，`call_method(name)` 查表调用；`@app.register('/')` / `@app.register('/next_page')`。
    - **作者自注的坑**：这个 decorator 类"不是真正的 decorator"，没有 `__call__()`，且 wrapper 返回了原函数，所以**原函数没有发生任何变化**。
12. **Go 版 Hello World**：`func decorator(f func(s string)) func(s string)` 返回匿名函数，匿名函数里先打 Started、调 `f(s)`、再打 Done；调用 `decorator(Hello)("Hello, World!")` 或用 `hello := decorator(Hello); hello("Hello")` 变好看一点。说明 **Go 不支持 `@decorator` 语法糖**，玩法与 Python 异曲同工。
13. **Go 计时修饰器**：`type SumFunc func(int64, int64) int64`；`timedSumFunc(f SumFunc) SumFunc` 用 `defer func(t time.Time){...}(time.Now())` 打耗时；`getFunctionName` 用 `runtime.FuncForPC(reflect.ValueOf(i).Pointer()).Name()` 反射取函数名。两个被测函数：`Sum1` 简单循环，`Sum2` 用求和公式 `(end-start+1)*(end+start)/2`；注意 start/end 可能为负，需先交换。
14. **Go 的 HTTP 中间件式修饰器**：`WithServerHeader`（写 `Server: HelloServer v0.0.1`）、`WithAuthCookie`（写 `Auth=Pass` cookie）、`WithBasicAuth`（校验 cookie，失败 `StatusForbidden`）、`WithDebugLog`（`r.ParseForm()` 后打 path/scheme/Form）。可嵌套：`/v1/hello`、`/v2/hello`、`/v3/hello` 三种拼装。
15. **pipeline 化**：写工具函数 `type HttpHandlerDecorator func(http.HandlerFunc) http.HandlerFunc`，`Handler(h, decors ...HttpHandlerDecorator)` **逆序遍历** `decors[len(decors)-1-i]` 逐层包裹，于是 `/v4/hello` 可以 `Handler(hello, WithServerHeader, WithBasicAuth, WithDebugLog)`。
16. **Go 修饰器的硬伤**：**无法做到泛型**——计时函数那样的代码"耦合了需要被修饰的函数的接口类型"，不够通用。原因是 Go 是静态语言，类型要在编译时搞定；Python 是动态语言、Java 有虚拟机，所以能"干许多比较变态的事儿"。
17. **reflect 通用修饰器**：`Decorator(decoPtr, fn interface{}) (err error)`——`decoratedFunc = reflect.ValueOf(decoPtr).Elem()`、`targetFunc = reflect.ValueOf(fn)`、`reflect.MakeFunc(targetFunc.Type(), func(in []reflect.Value) (out []reflect.Value){...})` 里 `targetFunc.Call(in)`，最后 `decoratedFunc.Set(v)`。两个参数：出参 `decoPtr` 是装饰后的函数，入参 `fn` 是被装饰的函数。
18. **使用代价**：需先声明函数签名 `type MyFoo func(int,int,int) int; var myfoo MyFoo; Decorator(&myfoo, foo)`——作者自评"还需要先声明一个函数签名，感觉好傻啊""一点都不泛型"；也可 `mybar := bar; Decorator(&mybar, bar)`。参考官方文章《The Laws of Reflection》。
19. **小结（修饰器到底做了什么）**：表面上是扩展现有函数的功能；深入看，**Decorator 这个函数可以修饰几乎所有函数**，于是能把"非业务功能的、属于控制类型的代码"抽象出来——**控制型代码 = for-loop、打日志、函数路由、求函数运行时间之类的非业务功能性代码**。
20. **读者留言中的 AOP 说法**：最高赞留言"越看越觉得装饰器模式是属于 AOP 思想的一种实现"；另一条留言区分了 Java 装饰器与 Python 装饰器（Java 的只是打标签，还要另外的类来检查特定标签）。**原文正文并未出现 AOP 一词**，引用时必须注明出自留言而非作者。

## 35｜编程范式游记（6）- 面向对象编程
> 源文件 `.tmp-zuoer/txt/35丨编程范式游记（6）-面向对象编程.txt`，20,630 字符

### 一句话结论
面向对象是"状态的收容所"：它用封装把数据与方法绑在一起，用继承获得多态（而非重用），用接口把双方依赖换成"都依赖标准"——所以 OOP 的精髓既是从"面向实现"到"面向接口"，也是从"我调用你"到"你按我的接口来"（IoC/DIP）。

### 知识点全清单（A1 零丢失）
1. **问题起点**：函数式要求无状态，但"这天下并不存在没有状态没有数据的代码"，状态总得有地方放——这就是 OOP 的位置。
2. **OOP 定义**：一种具有对象概念的程序编程范型，也是一种抽象的方針；对象是类的实例；以对象为程序基本单元，把程序和数据封装其中，以提高可重用性、灵活性和可扩展性；对象里的程序可以访问及修改对象关联的数据。
3. **与传统思想的差别**：传统把程序看作一系列函数的集合或一系列对计算机下达的指令；OOP 里每个对象都能接收数据、处理数据、把数据传给其它对象，可看作一台小型"机器"。
4. **已被证实的收益**：推广了程序的灵活性和可维护性，在大型项目设计中广为应用；支持者声称比以往更便于学习、设计、维护、分析、理解。
5. **主流语言清单**：Common Lisp、Python、C++、Objective-C、Smalltalk、Delphi、Java、Swift、C#、Perl、Ruby、PHP。
6. **GoF 之书**：Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides 合著《设计模式：可复用面向对象软件的基础》，收录 **23 种**设计模式。
7. **23 个模式背后的两个核心理念**：
   - `"Program to an 'interface', not an 'implementation'."` —— 使用者不需要知道数据类型、结构、算法细节；不需要知道实现细节，只需知道接口；利于抽象、封装、动态绑定、多态；符合 OO 特质。
   - `"Favor 'object composition' over 'class inheritance'."` —— 继承要给子类暴露父类的设计与实现细节；父类实现改变会造成子类也要改；**我们以为继承是为了代码重用，实际子类要重新实现很多父类方法**；继承更多应该是为了多态。
8. **示例一：拼装对象（桥接模式）**：4 个物体（木头桌子、木头椅子、塑料桌子、塑料椅子）、4 个属性（燃点、密度、价格、重量）。左边"材质类" `Material`（燃点、密度），右边"家具类" `Furniture`（价格、体积），`Furniture` 中耦合 `Material`，具体是 Wood 还是 Plastic 在**构造对象时注入**；家具类用"材料密度 × 家具体积"算出重量属性。优点：与现实世界对应、材料类可重用、"喜欢组合而不是继承"。
9. **范式对照一句**：函数式强调**动词**，面向对象强调**名词**；OO 更关注接口间的关系，通过多态适配不同实现。
10. **示例二：拼装功能（策略模式）**：电商订单计价。接口 `BillingStrategy { double GetActPrice(double rawPrice); }`；实现 `NormalStrategy`（原价返回）与 `HappyHourStrategy`（`rawPrice * 0.5`，即 5 折）。`OrderItem` 封装 Name/Price/Quantity/**Strategy**；`Order` 封装 `List<OrderItem>` 与默认 `NormalStrategy`，`Add(...)` 时传入策略，`PayBill()` 遍历算 `item.Strategy.GetActPrice(item.price * item.quantity)` 并累加。
    - 收益：定价策略与订单处理流程分开，可随时给不同商品注入不同策略，灵活度交给运营配置。
    - 边界自注：现实还有会员价、打折卡、打包价，且可**叠加不同策略**——"叠加策略用前面说的函数式的 pipeline 或 decorator 就可以实现"。
    - 作者评价：这就是**策略模式**，"我认为，这是设计模式中最为经典的模式了，它充分体现了面向对象编程的方式"。
11. **示例三：资源管理（代理模式 + RAII）**：坏代码 `m.lock(); Func(); if(!everythingOk()) return; ... m.unlock();` —— if 返回时没 unlock，锁不释放；正确但要"在所有函数退出的地方都加 m.unlock()"，难以维护。
    - 解法：`class lock_guard { private: mutex &_m; public: lock_guard(mutex &m):_m(m){_m.lock();} ~lock_guard(){_m.unlock();} };`，业务里只写 `lock_guard guard(m);`。
    - 技术名 **RAII（Resource Acquisition Is Initialization）**，模式名**代理模式**：把资源分配/释放的控制逻辑交给代理类，业务代码只关注业务。
12. **从示例三看出的 OO 四件事**：① 用类封装资源生命周期；② 用构造/析构把"进入与离开作用域"绑定；③ 业务代码里不再有与业务无关的控制代码；④ 抽象出可复用的代理。
13. **IoC 控制反转**：先技术后管理。开关控制灯的最土实现是"开关直接操作灯泡"；后来把灯泡抽象成基类/接口，其它类耦合接口而非实现 —— **这就是多态，增加了可扩展性**。
14. **接口即协议（核心论证）**：接口就是一种"协议"，就像 HTTP——浏览器与后端都依赖这一协议而不是具体实现（否则浏览器要依赖后端的编程语言或中间件，"这就太恶心了"）。"这就是面向对象的编程范式的精髓！同样也是 IoC/DIP（控制反转 / 依赖倒置）的本质。"
15. **控制反转的定义**：开关从"设备的专用开关"变成"控制电源的开关"，设备反过来依赖开关厂声明的电源连接接口；即"从依赖设备"变成"设备反过来依赖开关定义的接口"。
16. **五个 IoC 现实投影**：
    - **钱**：以前以物易物，一头羊换 2 袋米、一袋米换一斤猪后腿肉，换算太复杂；"钱"就是一种交易协议，所有商品依赖它而不再互相依赖。
    - **银行担保**：买卖双方原本必须强耦合（必须见面）；银行让买家先垫钱、卖家发货、验货后银行把钱打给卖家——这就是反转控制；股票交易同理，证交所是标准交易模型接口。
    - **海尔分销**：渠道越多越耦合，每加一个渠道就要新增一批人和一个新流程；于是制定业务标准 + 分销信息化系统，只有符合标准的渠道商才能成为分销商，"反转了控制，倒置了依赖"。
    - **云计算平台**：底层团队只交底层技术，上层为每个云资源开发生产/控制台/监控，完全干不过来；于是要求各云产品线按标准定义资源生命周期、提供控制台、接入整体监控、通过标准协议开发控制系统。
    - **集中式电商订单平台**：垂直业务线个性化需求太多，技术平台应接不暇、各种变态需求干扰系统、技术决策越来越难做、需求排期排不过来；解法是插件模型 + 工作流引擎 + Pub/Sub，业务方数据在自己库、逻辑不侵入系统、可用工作流引擎或 Pub/Sub 协议自定义步骤（甚至把 decider 交给业务方）。
17. **这些例子要说什么**：① 我们每天都在标准化和定制化中纠结，痛苦于"哪些应该是平台要做的，哪些应该要甩出去的"；② 这里会出现大量与业务无关的软件或中间件（协议、数据、接口）；③ 通过 OO 的这些方式，可以用抽象解耦、用中间件解耦，降低软件复杂度；④ 总而言之，就是通过一种标准让业务更规范。
18. **OOP 优点（五条）**：能和真实世界交相辉映、符合人的直觉；和数据库模型设计类型，更多关注对象间的模型设计；强调"名词"而非"动词"，更多关注对象与对象间的接口；按业务特征形成一个个高内聚对象，有效分离抽象与具体实现，增强可重用性与可扩展性；拥有大量优秀的设计原则与模式（**S.O.L.I.D**：单一功能、开闭、里氏替换、接口隔离、依赖反转；以及 IoC/DIP）。
19. **OOP 缺点（四条）**：好多人并不喜欢 OOP，尤其是喜欢函数式和泛型的人；通过对象达到抽象、把代码分散在不同类里，执行时就要把这些类粘合起来，**鼓励相当厚重的"代码黏合层"**；Java 里很多注入方式（Spring）鼓励黏合，导致大量封装，"完全不知道里面在干什么事情"，封装屏蔽细节；代码都要附着在类上，某种意义上**鼓励了类型**；太多封装与对状态的鼓励，导致大量不透明并在并发下出现很多问题。

## 36｜编程范式游记（7）- 基于原型的编程范式
> 源文件 `.tmp-zuoer/txt/36丨编程范式游记（7）-基于原型的编程范式.txt`，13,800 字符

### 一句话结论
原型范式是"没有 class 的面向对象"：对象直接以对象为模板，属性沿 `__proto__` 链向上查找，靠**委托**而不是分类获得复用；它把灵活性（运行时改原型）推到极致，代价是没有静态契约，执行确定性只能靠使用者自己保证。

### 知识点全清单（A1 零丢失）
1. **定义**：基于原型（prototype）的编程也是面向对象编程的一种方式；**没有 class 化的，直接使用对象**；又叫**基于实例的编程**；主流语言是 JavaScript。
2. **与基于类的 OOP 的对比**：基于类的系统里对象有两种"类型"——**类**定义对象的基本布局和函数特性，**接口**是"可以使用的"对象（基于特定类的样式）；类表现为行为和结构的集合，对所有接口来说这些行为和结构都相同；因此**区分规则首先是基于行为和结构，而后才是状态**。
3. **关注点差异**：原型编程主张者认为基于类的语言提倡"关注分类和类之间关系"的开发模型；原型编程提倡"关注一系列对象实例的行为"，之后再把这些对象划分到"最近的使用方式相似的原型对象"，而不是分成类。
4. **运行时可变性**：很多基于原型的系统提倡**运行时修改原型**；只有极少数基于类的系统允许运行时改类，第一个动态面向对象系统 **Smalltalk** 是其一；动态语言允许运行时改类的还有 Common Lisp、Dylan、Objective-C、Perl、Python、Ruby、Smalltalk。
5. **构造对象的两种方法**：**复制已有对象**，或**扩展空对象**；基于类的语言则通过类构造器 + 可选参数构造实例。
6. **`__proto__` 最小示例**：`var foo = {name:"foo", one:1, two:2}`、`var bar = {three:3}`；`bar.__proto__ = foo` 后 `bar.one` 解析为 1、`bar.three` 为 3；**自有属性遮蔽原型属性**：`bar.name = "bar"` 后 `foo.name` 仍为 "foo"、`bar.name` 为 "bar"。
7. **`__proto__` 与 `prototype` 的区别（核心）**：
   - JS 里对象有两种表现形式：`Object`（ES5 Object 文档）与 `Function`（ES5 Function 文档）。
   - `__proto__` 是**所有对象**用于链接原型的指针，在实际对象中产生链接、构成原型链，用于寻找方法名或属性。
   - `prototype` 是 **Function 对象**的属性，是 `new` 一个对象时用来构造 `__proto__` 指向的地方，即"构造函数的一个属性"。
   - 对超级对象 Function 而言，`Function.__proto__` 就是 `Function.prototype`。
8. **原型链示例**：`a = {x:10, calculate(z){return this.x+this.y+z}}`；`b = {y:20, __proto__: a}`、`c = {y:30, __proto__: a}`；`b.calculate(30)` = 60、`c.calculate(40)` = 80（this.x=10、this.y=20/30、z=30/40）。
9. **ES5 规范写法**：原型继承要用 `Object.create()`——`var b = Object.create(a, {y:{value:20}})`、`var c = Object.create(a, {y:{value:30}})`。
10. **构造函数写法与内存布局**：`function Foo(y){this.y=y}`；`Foo.prototype.x = 10`；`Foo.prototype.calculate = function(z){return this.x+this.y+z}`；`var b = new Foo(20); var c = new Foo(30);` → `b.calculate(30)`=60、`c.calculate(40)`=80。
11. **四条恒等式（自测题）**：`b.__proto__ === Foo.prototype`（true）、`c.__proto__ === Foo.prototype`（true）、`b.constructor === Foo`（true）、`c.constructor === Foo`（true）、`Foo.prototype.constructor === Foo`（true）、`b.calculate === b.__proto__.calculate`（true）、`b.__proto__.calculate === Foo.prototype.calculate`（true）。
12. **constructor 的来源**：`Foo.prototype` 自动创建了一个 `constructor` 属性，是指向函数自己的 reference；于是实例 b、c 能访问到这个继承来的 constructor。
13. **空函数对象实验**：`function Person(){}` → `var p = new Person()`（先生成空的函数对象，再 new 出 p）；改 `Person.prototype.name = "Hao Chen"` 与 `Person.prototype.sayHello` 后，`p.name` 输出 "Hao Chen"、`p.sayHello()` 输出 "Hi, I am Hao Chen"——**已创建的 p 也跟着变**。三条指针说明：创建 `function Person(){}` 时 `Person.__proto__` 指向 `Function.prototype`；`var p = new Person()` 时 `p.__proto__` 指向 `Person.prototype`；改了 `Person.prototype` 的内容，`p.__proto__` 的内容随之改变。
14. **"方法也是属性"**：`var Person = function(fullName, email){ this.fullName; this.email; this.speak=function(){...}; this.introduction=function(){...} }` 中，对象包含属性 fullName/email 与方法 speak()/introduction()——"其实，所谓的方法也是属性"。
15. **原型继承的标准两步**（不要简单粗暴赋 `__proto__`）：
    - `Student.prototype = Object.create(Person.prototype);` —— 建立继承
    - `Student.prototype.constructor = Student;` —— 把 constructor 指回自己
    - 作者明确反对 `Student.__proto__ = Person.prototype` 的写法："这太粗暴了"。
16. **借用父构造**：`Student = function(fullName, email, school, courses){ Person.call(this, fullName, email); ... }`；`call()` / `apply()` 都是为了**动态改变 this 所指向的对象的内容**而出现，这里 this 就是 Student。子类可**重载**（override）`introduction()` 并新增 `takeExams()`。
17. **验证**：`new Student(...)` 后 `student.introduction()` / `student.speak()` / `student.takeExams()` 均可用；`student instanceof Person` 与 `student instanceof Student` 都为 true。
18. **ES 标准演进**：ECMAScript 第四版开始寻求提供基于类的构造；**ECMAScript 第六版提供 `class` 作为原有原型架构之上的语法糖**（构建对象与处理继承的另一种语法）。
19. **委托的本质（小结核心）**：这种玩法就是**委托**的方式；使用委托的基于原型的语言，运行时可以"仅仅通过序列的指针找到匹配"来定位属性或寻找正确数据；创建行为共享的行为需要的是**委托指针**。
20. **结构自由度**：不像基于类的语言中类与接口的关系，原型与其分支之间**不要求子对象有相似的内存结构**，因此子对象可继续修改而无需像基于类系统那样整理结构；**不仅数据、方法也能被修改**；因此大多数基于原型的语言把数据和方法统称 **"slots"**。
21. **代价（作者的关键判断）**：在对象里直接修改带来运行时灵活性（可增删属性和方法），但带来**执行的不确定性、安全性问题、代码不可预测**，"这有点黑科技的味道了"；因为不像静态类型系统那样有**不可变的契约**保证确定性，所以需要使用者自己保证。

### 数字 / 公式 / 阈值
- `b.calculate(30)` = **60**；`c.calculate(40)` = **80**（x=10、y=20/30、z=30/40）。
- `Foo.prototype.x = 10`；`new Foo(20)` / `new Foo(30)`。
- `Object.create(a, {y: {value: 20}})` / `{value: 30}`。
- ECMAScript **第四版**开始求类构造、**第六版**提供 `class` 语法糖；Smalltalk 是**第一个**动态面向对象系统。
- 恒等式 **7** 条全为 true（见知识点 11）。

### 原话（可逐字引用）
- "原型编程看起来提倡程序员关注一系列对象实例的行为，而之后才关心如何将这些对象划分到最近的使用方式相似的原型对象，而不是分成类。"
- "其实，所谓的方法也是属性。"

- "因为这些不像静态类型系统，没有一个不可变的契约对代码的确定性有保证，所以，需要使用者来自己保证。"

### 反例 / 坑 / 作者明确反对的做法

- 坑：改 `Person.prototype` 会让**已经创建**的实例 p 一起改变——"另外那个 p 的对象也跟着一起改变了"，这是灵活性也是危险源。

## 37｜编程范式游记（8）- Go 语言的委托模式
> 源文件 `.tmp-zuoer/txt/37丨编程范式游记（8）-Go语言的委托模式.txt`，11,837 字符

### 一句话结论
Go 用"把一个 struct 嵌进另一个 struct"实现编译期的委托：嵌入给方法、聚合给字段、同名即覆盖（重名要手动消歧），再配接口就同时拿到 OOP 的多态与原型式的灵活；而"包装改 N 个方法 vs 内部依赖一个 Undo 接口只改 1 处注册"是控制反转最硬的一条判据。

### 知识点全清单（A1 零丢失）
1. **起点**：Go 声明 struct 与 C 一样，可以**直接把这个 struct 类型放到另一个 struct 里**。
2. **三种关系的注释级区分（Widget/Label）**：`type Widget struct{X, Y int}`；`type Label struct { Widget /* Embedding (delegation) */; Text string /* Aggregation */; X int /* Override */ }`。
3. **三步说明**：声明 Widget（有 X,Y）→ 用它声明 Label，**直接把 Widget 委托进去**→ 再给 Label 声明并实现 `Paint()` 方法。
4. **字段访问与遮蔽**：`label := Label{Widget{10,10}, "State", 100}` → `label.X` = **100**（外层覆盖）、`label.Y` = **10**、`label.Text` = State、`label.Widget.X` = **10**；`%+v` 打印 `{Widget:{X:10 Y:10} Text:State X:100}`，`%v` 打印 `{{10 10} State 100}`。
5. **重名冲突必须手动解决**：原文"For Label 里既有 Widget.X 又有自己的 X"——"如果有成员变量重名，则需要手动地解决冲突"。
6. **继续扩展**：`type Button struct { Label }`（嵌入 Label）；`NewButton(x,y int, text string) Button { return Button{Label{Widget{x,y}, text, x}} }`；给 Button 加 `Paint()`（Override）与 `Click()`。
7. **第二个分支**：`type ListBox struct { Widget; Texts []string; Index int }` + `Paint()` / `Click()`。
8. **接口定义多态**：`type Painter interface { Paint() }`、`type Clicker interface { Click() }`。
9. **两种泛型遍历（关键）**：
   - `for _, painter := range []Painter{label, listBox, button1, button2} { painter.Paint() }` —— 直接按接口调用。
   - `for _, widget := range []interface{}{...} { if clicker, ok := widget.(Clicker); ok { clicker.Click() } }` —— **类型断言**做可选能力探测（label 没有 Click，被跳过）。
10. **作者对这套玩法的定位**：这是 Go 里"委托 + 接口多态"的编程方式，"其实是**面向对象和原型编程综合**的玩法"。
11. **Undo 案例——第一版（被作者标注 Poor style）**：`type IntSet struct { data map[int]bool }`，方法 `Add` / `Delete` / `Contains` / `String`（`String` 满足 `fmt.Stringer`，要 `sort.Ints` 后 `strings.Join`）。
    - 加 Undo：`type UndoableIntSet struct { IntSet /* Embedding (delegation) */; functions []func() }`，**几乎重写了所有与"写"相关的方法**（`Add`/`Delete`），每次记录反操作闭包（Add 记 `func(){set.Delete(x)}`、Delete 记 `func(){set.Add(x)}`）；已存在则压入 `nil` 占位，保证栈位与操作一一对应。
    - `Undo()`：空栈返回 `errors.New("No functions to undo")`；取 `index := len-1`，闭包非 nil 才执行，执行后 `set.functions[index] = nil`（**Free closure for garbage collection**），再 `slice[:index]` 弹栈。
12. **第一版的问题（作者原话）**：别的类也需要 Undo 功能时，是不是要重写所有需要这个功能的类？"这样的代码类似，就是因为数据容器不一样，我就要去重写它们，这太二了。"
13. **Undo 案例——第二版（IoC 版）**：抽出通用栈 `type Undo []func()`，`func (undo *Undo) Add(function func()) { *undo = append(*undo, function) }`，`Undo()` 同样取栈顶、执行、置 nil、弹栈。
    - `IntSet` 改为 `struct { data map[int]bool; undo Undo }`；`Add` 里 `set.undo.Add(func(){set.Delete(x)})`，`Delete` 里 `set.undo.Add(func(){set.Add(x)})`，`Undo()` 直接 `return set.undo.Undo()`。
14. **控制反转的判据（作者小结）**：Undo 接口把 **Undo 的流程**抽象出来，**怎么 Undo 交给业务代码**通过注册方法来维护；Undo 时回调这个方法做与业务相关的操作。
15. **三重类比（作者收尾）**：① 和最开始 C++ 的泛型编程很像；② 和 map/reduce/filter 这种"只关心控制流程、不关心业务逻辑"的做法很像；③ 从"用 `UndoableIntSet` 包装 `IntSet`"到"反过来在 `IntSet` 里依赖 `Undo`"，**这就是控制反转 IoC**。
16. **读者总结的三条判据（留言，非作者正文）**：依赖的东西要可靠、稳定，也就是接口；业务与控制分离，控制就可以复用；把变化频率不同的事物分开。

### 反例 / 坑 / 作者明确反对的做法
- 明确标注反例：第一版 `UndoableIntSet` 的注释就是 `// Poor style`，理由是为一个能力重写所有写方法，换数据容器就要重写一遍。
- 坑：撤销栈里**必须压 `nil` 占位**，否则某次操作没记录反操作时栈会错位，Undo 会撤错对象。
- 坑：执行完闭包要 `functions[index] = nil` 释放闭包，否则撤销栈持有引用导致 `GC` 回收不了。
- 坑：嵌入导致**重名字段/方法要手动消歧**（`label.X` 与 `label.Widget.X`），不写清楚就是隐式选择。
- 坑（隐藏）：`%+v` 与 `%v` 打印结构不同，示例输出里的地址值随运行变化，不能当断言。
