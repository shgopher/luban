## 49｜弹力设计篇之"限流设计"
> 源文件 `.tmp-zuoer/txt/49丨弹力设计篇之“限流设计”.txt`，6,619 字

### 一句话结论
限流的目的是"系统过载时不让它崩"，手段只有两条正交的轴：**在入口拒绝/排队（计数器、队列、漏桶、令牌桶）**，以及**把阈值从静态数字改成跟随响应时间的反馈量（P90/P99 + 类 TCP 的减半慢启动）**；而且限流必须从架构早期就留位置。

### 知识点全清单（A1 零丢失）
1. 需要限流的入口例子：数据库访问的连接池、线程池、Nginx 的 `limit_conn`（限制**瞬时并发连接数**）、`limit_req`（限制**每秒平均速率**）、限制 MQ 的生产速率。
2. 限流策略 = 达到限制速率后触发的行为，原文列了 5 种：
   1. **拒绝服务**：把多出来的请求拒掉；好的限流系统在流量暴增时会统计"当前哪个客户端来的请求最多"，直接拒掉这个客户端，把不正常或恶意的高并发挡在门外。
   2. **服务降级**：关闭或把后端服务降级，让服务有资源处理更多请求。降级有三种程度：停掉不重要的服务把 CPU/内存/数据资源让给重要功能；不再返回全量数据只返回部分（全量要 SQL Join，部分不用，SQL 更快）；最快的是直接返回预设的缓存，**牺牲一致性换吞吐**。
   3. **特权请求**：资源不够时把有限资源分给重要用户（VIP）；多租户系统限流时应保大客户，非特权用户让路。
   4. **延时处理**：用队列缓冲大量请求；队列满则只能拒绝；队列里的任务超时也要返回"系统繁忙"；缓冲队列只是减缓压力，**一般用于应对短暂的峰刺请求**。
   5. **弹性伸缩**：用自动化运维对服务自动伸缩。前提是一个能感知"目前最繁忙的 TOP 5 服务是哪几个"的应用性能监控系统，以及一个够快的自动化发布、部署、服务注册系统（越快越好，否则系统已被压死）；**如果是数据库压力过大，弹性伸缩没用，这时还是应该限流**。
3. 实现方式一：**计数器**。维护一个 Counter，请求来加一、处理完减一，超过阈值就拒绝以保护负载——"足够简单粗暴"。
4. 实现方式二：**队列**。请求速度可以波动，处理速度非常匀速，本质是 FIFO。
   1. 扩展出**优先级队列**：先处理高优先级，高优先级处理完才处理低优先级；风险是低优先级长期得不到处理（饿死）。
   2. 为避免饿死，扩展出**带权重的队列**：三个队列权重 3:2:1，则在权重 3 的队列处理 3 个请求、再去权重 2 的处理 2 个、再去权重 1 的处理 1 个，如此反复。
   3. 队列流控用**队列长度**控制流量，配置上很难操作：队列过长会导致后端服务在队列没满时就挂掉；这种模型**不能做 push，pull 方式会好一些**。
5. 实现方式三：**漏斗算法（Leaky Bucket）**。像漏斗：进水量=访问流量，出水量=系统处理；流量过大就在漏斗里积水，水太多就溢出。一般用队列实现：请求过多时队列积压，队列满了就拒绝。很多系统都有这种设计，比如 TCP 在请求过多时有 sync backlog 队列缓冲，TCP 的滑动窗口也是用于流控的队列。**本质是在队列请求中加一个限流器，让 Processor 以均匀速度处理请求**。
6. 实现方式四：**令牌桶算法（Token Bucket）**。桶内按一定速率放入 token，处理请求前必须拿到 token，拿不到则不处理。
   1. 与漏斗的理论差异：漏斗以**恒定速度**处理；令牌桶在流量小时**"攒钱"**，流量大时可以快速处理。
   2. 共同上限：因为队列的存在，Processor 总能以最大处理能力处理请求，所以**令牌桶和漏斗都受制于 Processor 的最大处理能力**——无论桶里有多少令牌、队列里还有多少请求，大流量来临时 Processor 总是按自己的最大处理能力处理。
   3. 什么时候两者真的不同：当 Processor 只是**简单的任务分配器**（如 Nginx 这种几乎没有业务逻辑的网关，处理很快、没有瓶颈，只负责转发）时——漏斗以稳定速度转发，令牌桶平时攒钱、流量大时可一次把队列里的请求发出去，之后才受令牌速率限制。
   4. 令牌桶还可以**做成第三方服务**，从而在分布式系统中做**全局流控**。
7. **基于响应时间的动态限流**：上面算法的通病是需要一个确定的限流值，这要求每次发布服务都做性能测试找出最大性能值（性能测试不容易做，但仍应该做）。
8. 拿不到合适限流值的具体原因（原文列举）：不同用户请求操作不同数据集（如时间线 Feed 流，各人关心的主题不同）；数据库数据不断变化，前两天性能还行、数据量增加后变差，**关系型数据库同一条 SQL 的执行时间不可预测**（NoSQL 的可预测性比 RDBMS 好）；不同 API 性能不同，要为每个 API 在线上配不同限流值，太难配也太难管；服务能自动伸缩，不同大小集群性能不同，阈值要动态调整，太难做到。
9. 动态限流的典范是 **TCP 拥塞控制**：用 RTT（Round Trip Time）探测网络延时和性能，据此设定滑动窗口大小，让发送速率与网络性能匹配——"非常精妙，完全可以借鉴到流控技术中"。
10. 动态限流的做法：记录每次调用后端的响应时间，在一个时间区间内（**比如过去 10 秒**）计算响应时间的 **P90 或 P99**（把区间内响应时间排序，看 90%/99% 位置的值），从而知道有多少请求大于某个响应时间；P90/P99 超过设定阈值就自动限流。
11. 该设计的要点一（算分位数太贵）：大量请求下算 P90/P99 非常耗内存、耗 CPU（要对大量数据排序）。两种解法：不记录所有请求、**采样**；或用**蓄水池（Reservoir Sampling）近似算法**（《编程珠玑》讲过，可自行 Google）。
12. 该设计的要点二（像 TCP 那样调 QPS）：记录当前 QPS；发现后端 P90/P99 太慢就把 QPS **减半**，然后像 TCP 一样**慢启动**，直到又开始变慢，再减 **1/4** 的 QPS，再慢启动，再减 **1/8**……整个过程像**阻尼运行**，限流流量最终在某个值上下**小幅振动**。目的是：后端扩容伸缩后性能变好时，系统能自动适应后端的最大性能。作者明确说"这种动态限流实现起来并不容易"，参考 TCP 算法。
13. **限流的四个目的**：
    1. 向用户承诺 SLA（保证某个速度下的响应时间和可用性）；
    2. 阻止多租户下某一用户耗尽资源导致所有用户无法访问；
    3. 应对突发流量；
    4. 节约成本——不为了一个不常见的尖峰把系统扩到最大尺寸，而是在有限资源下承受较高流量。
14. 设计考量（原文 6 条）：
    1. 限流应在**架构早期**考虑，架构形成后限流不容易加入；
    2. 限流模块性能必须好、对流量的变化必须灵敏，太迟钝的限流会让系统早已因过载挂掉；
    3. 要有一个**手动开关**，应急时可手动操作；
    4. 限流发生时要有**监控事件通知**，运维能及时跟进，并可自动化触发扩容或降级；
    5. 被拒的请求要返回**特定的限流错误码**，与其他错误区分；客户端看到限流可以调整发送速度或走重试；
    6. 限流应该**让后端服务感知**：在协议头里塞标识（如 HTTP Header 放入限流级别），后端据此决定是否降级。

### 数字 / 公式 / 阈值
- Nginx：`limit_conn` 限瞬时并发连接数；`limit_req` 限每秒平均速率（原文未给具体数值）。
- 权重队列示例：3:2:1 → 处理 3 个 → 2 个 → 1 个，循环。

### 原话（可逐字引用）
- "限流模块性能必须好，而且对流量的变化也是非常灵敏的，否则太过迟钝的限流，系统早因为过载而挂掉了。"
- "这个过程有点像个阻尼运行的过程，然后整个限流的流量会在一个值上下做小幅振动。"
- "漏斗算法中，处理请求是以一个常量和恒定的速度处理的，而令牌桶算法则是在流量小的时候'攒钱'，流量大的时候，可以快速处理。"
- "如果是数据库的压力过大，弹性伸缩应用是没什么用的，这个时候还是应该限流。"

### 反例 / 坑 / 作者明确反对的做法
- 用队列长度做流控：配置难，且队列过长会导致后端在队列没满时先挂；这种模型用 push 会出问题，宜 pull。
- 为省事给全站配一个静态限流值：每个 API 性能不同、集群大小会变、SQL 执行时间不可预测，静态值必然错。
- 过载时靠弹性伸缩救：数据库压力型过载时无效，必须限流。
- 限流拒绝返回一个和普通错误一样的码（原文主张必须给专用限流错误码，否则客户端无法区分"该退避"还是"该重试"）。
- 把限流留到架构定型后再加。

## 50｜弹力设计篇之"降级设计"
> 源文件 `.tmp-zuoer/txt/50丨弹力设计篇之“降级设计”.txt`，4,573 字

### 一句话结论
降级是"资源和访问量矛盾时，主动牺牲一部分东西（一致性、次要功能、功能完整性）换整站平稳"，并且它必须**事先把业务功能分级、把预案写成可自动执行的代码**，因为降级很难不侵入业务地临时加上去。

### 知识点全清单（A1 零丢失）
1. 定义：降级（Degradation）本质是解决**资源不足和访问量过大**的问题；资源与访问量矛盾时，暂时牺牲掉一些东西，以保障整个系统平稳运行。
2. 生活比喻：伦敦诺丁山狂欢节、看阿森纳英超比赛散场时人太多，所有公交系统（公交车、地铁）**完全免费**，且散场前场外就备好了一堆公交和地铁，为的是最短时间疏散人流。虽然亏了钱，但相比人员拥塞造成的道路拥塞与意外带来的社会成本，免费是明智的——系统应对突发情况也需要这样的降级流程。
3. 降级要牺牲的东西有三类：**降低一致性**（简化流程的一致性 / 降低数据的一致性）、**停止次要功能**、**简化功能**。
4. 降低一致性之一：**用异步简化流程**。电商下单在强一致下要：结算账单 → 扣库存 → 扣账户余额（或发起支付）→ 发货，非常慢；支付环节还依赖银行接口性能（双 11 银行出问题会导致支付不成功、订单流程走不下去）。降级做法：把这一系列操作做成异步——快速结算订单、**不占库存**、把在线支付降级成**用户到付**（省掉支付环节）、批量处理订单并向用户发货、用户货到付款。
5. 降级后的一致性形态（配图结论）：全同步变全异步；库存从**单笔强一致**变**多笔最终一致**（库存不够时只能按先来后到取消订单）；支付从下单时的强一致变**到付的最终一致**。
6. 功能降级会损害体验，**最好给出友好的用户提示**，例如"系统当前繁忙，您的订单已收到，我们正努力为您处理订单中，我们会尽快给您发送订单确认通知……还请见谅"。
7. 降低一致性之二：**降低数据的一致性**。常用缓存，或直接去掉数据——比如页面上不显示库存具体数字，只显示"有/没有库存"两种状态。缓存能有效降低数据库压力，把数据库资源交给更重要的业务。
8. 降级后系统不再从数据库取数、而是从缓存取数。缓存设计模式参考作者 CoolShell 的《缓存更新的套路》；**功能降级中一般用 Cache Aside 模式或 Read Through 模式**。
9. Read Through 定义：在查询操作中更新缓存，即缓存失效时（过期或 LRU 换出），**Cache Aside 由调用方负责把数据加载到缓存，Read Through 则由缓存服务自己加载**，从而对应用方透明。
10. Cache Aside 三步（原文照录）：失效——应用先从 cache 取数据，没取到则从数据库取，成功后放入缓存；命中——从 cache 取到后返回；更新——**先把数据存到数据库，成功后，再让缓存失效**。
11. **停止次要的功能**：把不重要的功能暂时停掉（如电商的搜索、用户评论），峰值过后再恢复。
12. 停止功能的渐进次序（原文明确）：**最好不要直接停**——先限制次要功能的流量，或把次要功能退化成简单功能，量太大时才进入"停止功能"状态。
13. 停止功能会带来体验问题（尤其停掉用户认为很重要的功能），**如果可能最好给用户补偿**：把用户切换到一个送积分卡、或红包抽奖的网页上，有限地补偿一下。
14. **简化功能**：下单流程已是例子；从缓存返回数据也是其中一种。另一个例子：**一个 API 有两个版本**，一个返回全量数据，另一个只返回部分或最小可用数据。
15. 简化功能的具体例子：一篇文章的 API 原本返回文章内容 + 所有评论；降级时只返回商品信息/文章内容，不返回用户评论（评论涉及更多数据库操作），从而释放数据库资源；而商品/文章信息可放缓存，进一步把资源让给交易系统这类更耗数据库的业务。
16. 降级设计的要点（原文 8 条）：
    1. 降级要牺牲业务功能/流程/一致性，因此必须对业务做**非常仔细的梳理和分析**；**很难通过不侵入业务的方式做到功能降级**。
    2. 要明确定义**降级的关键条件**：吞吐量过大、响应时间过慢、失败次数过多、有网络或服务故障等；并做好相应应急预案，预案**最好写成代码，可快速自动化或半自动化执行**。
    3. 要梳理哪些是 **must-have** 功能、哪些是 **nice-to-have**；哪些必须死保、哪些可以牺牲；并事先设计好可简化/应急的业务流程，出问题时走简化流程。
    4. 降级要牺牲一致性或业务流程：**读操作使用缓存，写操作使用异步调用**；且必须**以流水账的方式记录下来，方便对账**，以免漏掉或与正常流程混淆。
    5. 降级开关可以是**系统配置开关**（降级时推送配置）；另一种方式是**在对外服务 API 上区分**（方法签名或开关参数），由上游调用者驱动。
    6. 举例：网关限流时在协议头中加入限流程度参数，让后端知道正在限流；当限流程度达到某个值、或限流时间超过某个值时，**自动开始降级**，直到限流好转。
    7. 数据方面的降级需要**前端配合**：前端根据后端传来的数据决定展示哪些界面模块（收不到评论就不展示）；为了区分"本来就没数据"和"因为降级没数据"，**协议头中也应加上降级的标签**。

## 51｜弹力设计篇之"弹力设计总结"
> 源文件 `.tmp-zuoer/txt/51丨弹力设计篇之“弹力设计总结”.txt`，4,159 字

### 一句话结论
整套弹力设计可以压缩成一张三块的总图——**冗余服务（消除单点）、服务解耦（隔离故障）、服务容错（接受失败）**；而没有自动化运维（至少 APM + 服务调度两套系统）时，这些设计在故障来时根本来不及生效，等于空有。

### 知识点全清单（A1 零丢失）
1. 总图第一块：**冗余服务**（服务不能是单点，架构中要有多个副本）。需要的具体技术：
   1. **负载均衡 + 服务健康检查**：如 Nginx 或 HAProxy；
   2. **服务发现 + 动态路由 + 服务健康检查**：如 Consul 或 ZooKeeper；
   3. **自动化运维**：Kubernetes 的服务调度、伸缩和故障迁移。
2. 总图第二块：**服务解耦/隔离**（要隔离服务就得解耦和拆分）。
   1. **bulkheads 模式**：业务分片、用户分片、数据库拆分；
   2. **自包含系统**：所谓自包含系统是**从单体到微服务的中间状态**，把一组密切相关的微服务拆出来，**只需要做到没有外部依赖**就行；
   3. **异步通讯**：服务发现、事件驱动、消息队列、业务工作流；
   4. **自动化运维**：需要一个服务调用链和性能监控的监控系统。
3. 总图第三块：**服务容错**（让架构能"接受失败"）。用到的技术：
   1. **错误方面**：调用重试 + 熔断 + 服务的幂等性设计；
   2. **一致性方面**：强一致性用两阶段提交，最终一致性用异步通讯方式；
   3. **流控方面**：限流 + 降级；
   4. **自动化运维方面**：网关流量调度、服务监控。
4. 总图读法：三大块——**冗余服务**（通过副本数消除单点故障，需要服务发现、负载均衡、动态路由、健康检查四个功能/组件）、**服务解耦**（水平层面把业务或用户分片分区：业务做隔离、用户做多租户；垂直层面用异步通讯；服务被拆成一个一个后，编排和聚合需要**工作流**，如 Spring 的 Stream、Akka 的 flow、AWS 的 Simple Workflow；一致性问题又需要业务补偿机制做反向交易）、**服务容错**（重试会带来幂等要求；熔断、限流、降级都是为了保护系统稳定性，并在出错时**在可用性和一致性上做一部分妥协**）。
5. 前提条件：除了架构设计，还需要一个或多个自动运维工具，否则人肉运维在故障时不能及时决策，"也就空有这些弹力设计了"；例如监控到服务性能不够，就自动或半自动地开始限流或降级。
6. 运维工具**至少需要两个系统**：一个是像 **APM** 这样的服务监控；另一个是服务调度系统，如 **Docker + Kubernetes**。
7. 开发架构：如需让整个团队在同一标准下开发上面这些东西，**Spring Cloud 是不二之选**。
8. Spring Cloud 与 Kubernetes **没有可比性**：前者偏开发，后者偏运维。
9. Spring Cloud 的定位：有一套丰富且集成良好的 Java 库，作为**应用栈的一部分**解决所有运行时问题；微服务本身可通过库和运行时代理解决客户端服务发现、负载均衡、配置更新、统计跟踪等；**工作模式就像单实例服务集群**（集群中 master 工作、master 挂掉后 slave 被选举顶替）；一批工作也在 **JVM 中被管理**。
10. Kubernetes 的定位：**不针对语言，而针对容器**，以通用方式为所有语言解决分布式计算问题；提供配置管理、服务发现、负载均衡、跟踪、统计；是**单实例、平台级、应用栈之外**的调度工作；应用不需要任何客户端逻辑的库或代理程序，可用任何语言编写。
11. 两者相似处：依靠相似的第三方工具，如 ELK / EFK stacks、tracing libraries；Hystrix、Spring Boot 等库在两个环境都表现良好。
12. 互补关系：很多情况下 Spring Cloud 与 Kubernetes 可形成互补，组建更强方案（例如 **KubeFlix**、**Spring Cloud Kubernetes**）。
13. 微服务关键技术覆盖面的图（原文配图，来自 *Deploying Microservices: Spring Cloud vs Kubernetes*）：红色 = 运维层面且两者不相关；绿色 = Spring Cloud 提供的开发框架；蓝色 = Kubernetes 相关的重要功能。
14. 结论/判断：要做出可运维的分布式系统，除了架构设计还需要一整套管控系统（运维系统），"不是靠几个人几天就可以完成的"，需按自己的业务特点规划实施路径；**从今天看，微服务的最佳实践在未来有可能成为 SpringCloud 和 Kubernetes 的天下**。
15. 作者态度：不敢保证这些技术能解决所有问题，但只要设计得当，绝大多数问题应该能扛住。

### 数字 / 公式 / 阈值
- 冗余服务需要的 4 个功能/组件：服务发现、负载均衡、动态路由、健康检查。
- 弹力设计三大块：冗余服务 / 服务解耦 / 服务容错。

## 52｜管理设计篇之"分布式锁"
> 源文件 `.tmp-zuoer/txt/52丨管理设计篇之“分布式锁”.txt`，7,656 字

### 一句话结论
分布式锁可以从数据库、Redis、ZooKeeper 三种实现里挑，但真正的坑不在"怎么加锁"，而在**"锁过期了持有者还以为自己持锁"**——所以正确性最终要靠 fence/版本号（乐观锁）或 CAS 来兜底，而一旦你能在数据上做 CAS，很多场景**根本不需要分布式锁**。

### 知识点全清单（A1 零丢失）
1. 引子：多线程访问共享资源要加锁，否则数据写乱；分布式系统同理，只是需要一个**分布式的锁服务**。一般可用**数据库 DB、Redis、ZooKeeper** 等实现。
2. 分布式锁服务的三特点：
   1. **安全性（Safety）**：任意时刻只有一个客户端能获得锁（排他性）。
   2. **避免死锁**：客户端最终一定能获得锁，**即使锁住资源的客户端在释放锁之前崩溃或网络不可达**。
   3. **容错性**：只要锁服务集群中的**大部分节点存活**，Client 就能进行加锁/解锁操作。
3. Redis 加锁命令：`SET resource_name my_random_value NX PX 30000`
   1. `SET NX`：只有在 key 不存在时才设置成功——多个进程并发设置同一 key，只有一个成功，其余失败（即获得锁失败）。
   2. `PX`：通知 Redis 保存这个 key **30000ms**；这个参数是 **key 的存活时间，称作锁过期时间**；资源被锁定超过这个时间，锁自动释放。
   3. `my_random_value` 必须是**全局唯一的值**，它在释放锁时保证释放操作的安全性。
   4. 风险：获得锁的客户端如果没在这个时间窗口内完成操作，就可能有别的客户端获得锁，引起争用问题。
4. Redis 解锁脚本（Lua）：`if redis.call("get",KEYS[1]) == ARGV[1] then return redis.call("del",KEYS[1]) else return 0 end`——**如果 key 的 value 一致，则删除这个 key**；目的是**避免 Client 释放了其他 Client 申请的锁**。
5. 不区分 Client 会导致的 7 步问题链（原文照录）：
   1. Client A 获得了一个锁；
   2. A 尝试释放锁的请求发送给 Redis 时被阻塞，没有及时到达；
   3. 锁定时间超时，Redis 认为锁的租约到期，释放了这个锁；
   4. Client B 重新申请到了这个锁；
   5. Client A 的解锁请求到达，将 Client B 锁定的 key 解锁；
   6. Client C 也获得了锁；
   7. Client B 和 Client C 同时持有锁。
6. `my_random_value` 的生成方式：官方推荐从 **`/dev/urandom` 取 20 个 byte** 作随机数；或用 RC4 在 `/dev/urandom` 取一个种子（Seed）生成伪随机流；或用**时间戳 + 客户端编号**（官方说"安全性较差一些，但对于绝大多数场景已经足够安全"）。
7. 分布式锁服务的真正问题：Redis 文档说他们的分布式锁没问题，"但其实还是很有问题的"，尤其是"为了避免 Client 占住不释放而在超时后把锁释放掉"这件事"听起来就有点不靠谱"。
8. 坑的推演：A 取得锁 → B 等待 → A 被某个外部阻塞调用、CPU 被别的进程吃满、或不巧碰上 **Full GC**，花了超过平时几倍的时间 → 锁服务因为怕死锁在一定时间后把锁释放 → B 获得锁并更新资源 → A 缓过来也去更新资源，**把 B 的更新冲掉** → 数据出错。
9. 这不是脑补：**HBase 曾经遇到过这样的问题**，见其 PPT《HBase and HDFS: Understanding FileSystem Usage in HBase》。
10. 解法：引入 **fence（栅栏）技术**，一般来说就是**乐观锁机制，需要一个版本号排它**。图中三点：
    1. 锁服务需要有一个**单调递增的版本号**；
    2. 写数据的时候也要带上自己的版本号；
    3. 数据库服务保存数据版本号，并对请求做检查。
11. 用 ZooKeeper 做锁服务时，可用 **zxid 或 znode 的版本号**做 fence 版本号。
12. **从乐观锁到 CAS**：如果数据库里也保留版本号，就完全可以用数据库做锁服务。数据版本（Version）机制：为数据库表增加数字类型的 `version` 字段；读数据时把 version 一同读出；数据每更新一次 version 加一；提交更新时把"表当前版本"与"第一次取出的 version"比对，相等才更新，否则认为是过期数据。
    1. 更新 SQL：`UPDATE table_name SET xxx = #{xxx}, version=version+1 where version =#{version};`
    2. "这不就是乐观锁吗？是的"——用版本号或 fence token，就**不需要使用分布式锁服务了**。
    3. fence token 在数据库那边一般用 **timestamp 时间戳**：更新提交时检查当前数据时间戳与自己更新前取到的时间戳是否一致，一致则 OK，否则版本冲突。
13. 连版本字段都不用的写法（库存）：先查出 `stock`，更新时检查是否仍是上次读出的库存；不是则说明别人更新过，我的 UPDATE 失败、得重来。`UPDATE tb_product SET stock=stock-#{num} WHERE product_id=#{product_id} AND stock=#{stock}`。
14. 归纳："这不就是汇编指令中的原子操作 **CAS（Compare And Swap）**嘛，大量无锁的数据结构都需要用到这个"（作者另有一篇《无锁队列的实现》）。
15. **分布式锁服务的初衷与概念问题**（原文的重点清单）：
    1. 先分清：我是用来**修改某个共享源**的，还是用来**不同进程间的同步或互斥**的。
    2. 如果用 **CAS 这样的无锁方式**更新数据，就**不需要**分布式锁服务。
    3. 获得锁的进程挂掉怎么办？锁还不回来会导致死锁——一般在锁服务加**过期时间**，超时自动解锁。
    4. 自动解锁后新进程拿到锁，但之前的进程以为自己还有锁，于是两个进程拿到同一把锁、更新数据出问题——解法见下条。
    5. 像 Redis 那样用 **Check and Set** 保证数据一致性（改值前先检查是不是自己读出的值），类似 CAS，"如果通过 CAS 这样的操作，我们还需要分布式锁服务吗？的确是不需要了"。
    6. 但现实中有**不更新数据、只为同步/互斥不同机器上的线程**的场景，此时 Redis 这类分布式锁服务**就有意义**。
    7. 所以第一个要问的问题是：**我们是否需要（分布式锁）**。
16. 如果确定要用，需要考虑的 5 个设计点：
    1. 需要给锁一个**释放方式**避免死锁：**Redis 用超时时间，ZooKeeper 可依靠自身的 sessionTimeout 删除节点**。
    2. 锁服务应该**高可用且需要持久化**——可看 Redis 的 **RedLock** 文档看它怎么做高可用。
    3. 要提供**非阻塞方式**的锁服务。
    4. 还要考虑**锁的可重入性**。
    5. 实现选型：数据库/Redis/ZooKeeper 都可以；"我认为 Redis 也是不错的，ZooKeeper 在使用起来需要有一些变通的方式，好在 Apache 有 **Curator** 帮我们封装了各种分布式锁的玩法"。
17. 分布式锁的特点：保证在一个集群中，**同一个方法在同一时间只能被一台机器上的一个线程执行**（分布式互斥）；做法是大家都去一个服务上请求一个标识，请求到就操作，操作完把标识还回去。
18. 小结要点：单机多线程用操作系统锁/数据库锁互斥共享资源，分布式程序同理；分布式锁服务一般通过 Redis 和 ZooKeeper 实现；锁超时后的风险可由**版本号**解决；数据库本身若用 CAS 支持版本控制，就**没必要**独立锁服务；**分布式锁服务还能用来做同步，这是数据库锁做不了的事**。

## 53｜管理设计篇之"配置中心"
> 源文件 `.tmp-zuoer/txt/53丨管理设计篇之“配置中心”.txt`，6,421 字

### 一句话结论
配置中心的难点不在"存"，而在**分类（静态/动态、环境、依赖、层次）+ 变更通道（通知用 Pub/Sub、取数用反向拉 API）+ 变更事务（控制器落在每台主机上）**，以及把"应用怎么被通知改配置"标准化——否则公司越大，配置越是一团无法治理的复杂度。

### 知识点全清单（A1 零丢失）
1. 什么是软件配置：数据库用户名密码；不想写死在代码里的东西（线程池大小、队列长度等运行参数；日志级别、算法策略）；软件运行环境参数（Java 内存大小、应用启动参数、操作系统参数配置）。
2. 以前配置写在配置文件里（Windows 的 ini、Linux 的 conf）；**分布式系统下这种方式非常不好管理、容易出错**，于是引入集中式配置管理系统——配置中心的由来。
3. 现状判断：配置中心已是分布式系统的**必要组件**；听起来简单但其实不是，"我见过好多公司的配置中心，但我觉得做得都不好"。
4. 区分方式一：**静态配置 vs 动态配置**。
   1. 静态配置：软件启动时的配置，运行时基本不改，可理解为环境或软件初始化时用的配置（如操作系统的网络配置、Docker 进程配置）。
   2. 动态配置：运行时会被修改的配置（如日志级别、降级开关、活动开关）。
   3. 本文内容**主要针对动态配置的管理**。
5. 动态配置管理的**三个区分维度**：
   1. **按运行环境分**：开发、测试、预发、生产；各环境配置不完全一样，但理论上是**大同小异**的。
   2. **按依赖区分**：依赖配置（外部依赖的 MySQL / Redis 连接配置）vs 完全自己内部的配置。
   3. **按层次分**：像云计算一样分 **IaaS / PaaS / SaaS** 三层——基础层是操作系统配置，中间平台层是中间件配置（如 Tomcat），上层软件层是应用自己的配置。
   4. 为什么要分类：小公司无所谓，公司变大后如果没管理好，会大幅增加系统维护复杂度。
6. 配置模型：每个配置项基本是 **key/value** 模型；配置分三层，**操作系统层和平台层的配置项由专门的运维人员或架构师配置**，其 value **应该是选项而不是让用户自由输入**，最好有模板来初始化全套配置参数；应用层的配置项需要**命名规范**，最好有像 C++ 那样的**名字空间**管理，确保不同应用的配置项不冲突。
7. 强建议：**外部服务依赖的配置不要放在配置中心里，而要放在服务发现系统中**——语义更清楚，且能减少因运行环境不同导致的配置差异（测试 vs 生产）。
8. 环境差异示例：开发/测试环境日志级别是 Debug，生产是 Warning 或 Error。
9. 配置需要**整体版本管理**，每次变动都能记录版本差异；如果可能，**最好和软件版本号做关联**。
10. 需要一个配置管理工具（CLI 或 Web），其界面模型：用户按不同机器型号和环境直接调出后台配置好的**标准配置模板**；用户需要自己调整的参数也可在模板上调整（但为方便运维管理**最好不要调整**）；然后在表格里填写自己的应用要用的参数和各环境的值。
11. 配置中心还要提供 **API** 让应用获取配置，API 上至少要有三个参数：**服务名、配置的版本号、配置的环境**。
12. 配置中心的架构（原文四问四答，是本节核心）：
    1. **为什么需要"变更通知"组件，而不是配置中心直接推送？** 因为分布式环境下服务器太多，推送不太现实；采用一个 **Pub/Sub 的通知服务**可以让数据交换经济一些。
    2. **为什么不直接 Pub 数据过去，还要订阅方反向拉数据？** 直接推数据当然可以，但反过来用 API 读配置的好处是：API 可以**校验请求者的权限**；有时候还需要调用配置中心的基本 API（比如下载最新的证书）；以及**服务启动时需要从配置中心拉一份配置下来**。
    3. **配置变更控制器部署在哪里——每台服务器上还是中心？** 因为变更配置有很多步骤，**这些步骤算是一个事务**；为了执行效率更好、事务成功率更大，建议**把这个配置变更的控制放在每一台主机上**。
    4. **平台层配置有的在服务启动命令行上，怎么变更？** 一般通过 **Shell 环境变量**把命令行参数做成配置项，然后更改系统环境变量，并重启服务达到配置变更。
13. 配置中心的设计重点：
    1. 配置中心主要用处是**统一和规范化管理所有服务配置**，也算一种**配置上的治理活动**；重点应放在**如何统一和标准化软件的配置项**（涉及软件版本、运行环境、平台、中间件等一系列参数）。如果觉得配置非常复杂，应静下心梳理/治理现有配置参数并简化，**使用模块**是一种比较好的简化手段。
    2. 按《编程范式游记》的观点，编程的本质是 **logic 和 control 的分离**；配置也一样，有**控制面上的配置**和**业务逻辑面上的配置**，控制面上的配置最好标准统一。
    3. **操作系统的配置变更和平台层的配置变更最好模块化掉**，就像云服务中不同尺寸的主机型号一样，有利于维护、减少配置复杂性。
    4. **应用服务配置更新的标准化**（一个公司应用由不同团队完成，配置因应用属性不同而不一样；有的在配置文件里，有的通过调用 Admin API 变更，完全无法统一）。三个方案：
       1. **开发框架 / SDK**：应用代码向 SDK 要配置，并通过 observer 模式订阅配置修改事件，或直接提供配置变更的 Admin API。好处是**在开发期标准化**、可规范开发；坏处是**耦合语言**。
       2. **标准应用运维脚本**：让应用方自己提供应用变更时的脚本动作。好处是通过运维方式把"配置变更接口"标准化，可由配置控制器统一操作；坏处是各应用内部仍用各自的方式变更配置，不耦合语言、灵活，但**不利于标准化建设**，且"使用或者调用脚本是 Bug 很多的东西，容易出问题"。
       3. **每个应用一个 Agent**（结合前两者）：不把 SDK 嵌入应用，而是为每个应用单独做 Agent；Agent 对外以 Admin API 服务，背后适配该应用的配置变更手段（更新配置文件、或调用应用 API）。"这种方式在落地方面是很不错的"（原文注明这是另一种设计模式，后面会讲）。
    5. 配置更新是一个**事务**处理：如果变更不能继续，需要**回滚到上个版本的配置**；配置版本最好和软件版本对应上。
    6. 配置更新控制器需要应用服务配合：配置的 reload、服务的优雅重启、服务的 Admin API、或通过环境变量——最好由一个**统一的开发框架**搞定。
    7. 配置更新控制器还**担任服务启动的责任**：由它启动服务——从配置中心拉取所有配置 → 更新操作系统 → 设置启动时用的环境变量 → 更新服务需要的配置文件 → 启动服务。（也可以在服务启动脚本里、真正启动前放一段让控制器更新配置的脚本；这些都能在运维层实现，不需要业务开发人员知道。）

## 54｜管理设计篇之"边车模式"
> 源文件 `.tmp-zuoer/txt/54丨管理设计篇之“边车模式”.txt`，4,899 字

### 一句话结论
边车就是给服务加一个"同生命周期、同结点、走标准网络协议"的代理进程，把监视/日志/限流/熔断/服务注册/协议转换这些**控制面**的东西从业务代码里搬出去——好处是不侵入、跨语言、老系统能低风险改造，代价是资源、延迟和运维复杂度都上升。

### 知识点全清单（A1 零丢失）
1. 命名与比喻：边车模式对应生活中的**边三轮摩托车**——给摩托车加一个边车来扩展现有服务和功能；很容易做到**"控制"和"逻辑"的分离**。
2. 目的：服务中不需要实现控制面上的东西（监视、日志记录、限流、熔断、服务注册、协议适配转换），只需专注业务逻辑相关代码，由"边车"实现这些与业务逻辑无关的控制功能。
3. 具体理解：边车有点像服务的 **Agent**，服务所有对外的进出通讯都通过这个 Agent 完成，于是可以在 Agent 上做很多文章；但必须保证**这个 Agent 要和应用程序一起创建、一起停用**。
4. 别名：边车模式有时也叫**搭档模式、伴侣模式、跟班模式**。
5. 理论依据：像《编程范式游记》所说，编程的本质是**将控制和逻辑分离和解耦**，边车模式异曲同工，是在分布式架构中做到逻辑和控制分离。
6. 实现控制面功能的两种方式（各有优缺点）：
   1. **SDK / Lib / Framework 软件包**：开发时与真实应用服务集成。
      - 优点：可以和应用密切集成，有利于资源利用和应用性能。
      - 缺点：**对应用有侵入**，受应用编程语言和技术限制；软件包升级时需要**重新编译并重新发布应用**。
   2. **Sidecar**：运维时与真实应用服务集成。
      - 优点：对应用服务**没有侵入性**，不受语言和技术限制，可做到**控制和逻辑的分开升级和部署**。
      - 缺点：增加了每个应用服务的**依赖性**，增加了**应用延迟**，也**大大增加管理、托管、部署的复杂度**。
7. 最有价值的场景：**老系统改造**——代码太老（如银行里用 C 或 **COBAL** 写的子系统）没有能力重写，又想变成分布式系统、需要协议改造与监控管理；因为**没有侵入性**，可以很快、低风险地改造。
8. Sidecar 的部署与生命周期语义：**逻辑上和应用服务部署在一个结点中，有相同的生命周期**；对比应用程序的每个实例，都**有一个 Sidecar 实例**；Sidecar 可以很快很方便地为应用服务扩展，而不需要应用改造。例如：
   1. 帮服务注册到服务发现系统并做健康检查；服务不健康就从服务发现中移除该实例；
   2. 应用调用外部服务时，帮它从服务发现中找到外部服务地址并做服务路由；
   3. 接管进出流量后做日志监视、调用链跟踪、流控熔断——都可以放在 Sidecar 里；
   4. 于是应用服务可以完全专注业务逻辑。
9. 同机部署的两个后果：①Sidecar 进程理论上可以访问应用服务进程能访问的资源（比如能监控到应用服务的进程信息）；②两个进程同机，通信**不存在明显的延迟**，服务响应延迟虽因跨进程调用增加，但"这个增加完全是可以接受的"。
10. 强烈建议：这种部署方式**最好与 Docker 容器一起使用**——Docker 简化了架构的部署和管理，否则这么多分布式架构模式实施起来会有很多麻烦。
11. 边车模式重点解决的两个问题：①**控制和逻辑的分离**；②**服务调用中上下文的问题**。
12. 服务控制系统可以通过**控制 Sidecar** 来控制应用服务（如流控、下线）。
13. 为什么必须用 Sidecar（论证）：熔断、路由、服务发现、计量、流控、监视、重试、幂等、鉴权这些控制面功能及其配置更新，本质与服务关系不大；传统做法在开发层完成，导致各种维护问题并受特定语言/框架约束；随着架构复杂化与扩张，需要更统一地管理控制面，传统做法变得极难维护——所以需要 Sidecar 来架构系统。
14. 工程实现的注意点（原文 5 条）：
    1. **进程间通讯机制是重点**：千万不要用任何对应用服务有侵入的方式（如信号、共享内存）；**最好是网络远程调用**（都在 `127.0.0.1` 上通讯，开销并不明显）。
    2. **协议要标准统一**，且有两层：Sidecar 到 service 的**内部协议**、Sidecar 到远端 Sidecar 或 service 的**外部协议**；内部协议要尽量靠近和兼容本地 service 的协议，外部协议要尽量开放和标准；**无论哪种都不应使用与语言相关的协议**。
    3. 使用这种模式，需要在服务的**整体打包、构建、部署、管控、运维**上设计好；用 Docker 容器技术可以全面降低复杂度。
    4. Sidecar 中实现的应该是**控制面**功能而不是业务逻辑，尽量不要把业务逻辑设计进 Sidecar。
    5. **小心在 Sidecar 中包含通用功能带来的影响**：例如重试操作可能不安全，**除非所有操作都是幂等的**。
15. 还需要考虑**应用服务与 Sidecar 的上下文传递机制**：例如包含 HTTP 请求标头以选择退出重试、或指定最大重试次数；或 Sidecar 告诉应用服务"限流发生""远程服务不可用"，让两者配合得更好。
16. **适用场景**（原文 4 条）：
    1. 对老应用系统的改造和扩展（比较明显的场景）；
    2. 由多种语言混合出来的分布式服务系统的管理和扩展；其中应用服务由不同供应商提供；
    3. 把控制和逻辑分离、标准化控制面上的动作和技术，从而提高系统整体稳定性和可用性；
    4. 有利于分工——"并不是所有的程序员都可以做好控制面上的开发"。
17. **不适用场景**（原文 3 条）：
    1. 架构并不复杂时不需要这个模式，直接使用 **API Gateway** 或 **Nginx / HAProxy** 即可；
    2. 服务间的**协议不标准且无法转换**；
    3. 不需要分布式的架构。

### 数字 / 公式 / 阈值
- 生命周期：每个应用实例 **1 个** Sidecar 实例。
- 通信地址：`127.0.0.1`。
- 协议层次：**2 层**（内部协议 / 外部协议）。
- 工程注意点：**5 条**；适用场景 **4 条**；不适用场景 **3 条**。
- 本讲无量化延迟/资源数字（原文只说"开销并不明显""增加可以接受"）。

## 55｜管理设计篇之"服务网格"
> 源文件 `.tmp-zuoer/txt/55丨管理设计篇之“服务网格”.txt`，5,379 字

### 一句话结论
服务网格 = 把 Sidecar 标准化成一个集群 + 一个控制面，让服务像"放进 PaaS"一样只写业务；它在架构中的位置相当于**七层模型里的 TCP 第四层**，但代价是——它是唯一一个"自己挂了会让全站挂"的控制面，所以网格本身必须高可用、要有 workaround。

### 知识点全清单（A1 零丢失）
1. 承接 Sidecar 的结论：Sidecar 能有效分离系统控制与业务逻辑，让控制面可集中管理，显著提高整体控制与管理效率，让业务开发更快速。
2. "think big"推演：如果在一个分布式系统里已经把标准 Sidecar（熔断、限流、重试、幂等、路由、监视）部署在每个计算结点，真实业务服务只需要往集群里放、和本地 Sidecar 通信、由 Sidecar 代理与其它系统交互——业务开发和运维"岂不是简单之极"。
3. 云厂商设想：如果某云服务提供商提供带各种分布式设计模式 Sidecar 的集群，用户就只用写业务逻辑相关的 service，"写好一个就往这个集群中部署"，开发与运维工作量都会巨大降低。
4. 这就是 **CNCF（Cloud Native Computing Foundation，云原生计算基金会）** 目前主力推动的新一代微服务架构——**Service Mesh（服务网格）**。
5. 官方定义（引 What's a service mesh? And why do I need one?，原文照录英文）：a dedicated infrastructure layer for handling service-to-service communication；负责通过现代云原生应用的复杂拓扑可靠地交付请求；实践中通常实现为**一组部署在应用代码旁边的轻量级网络代理，应用无需感知**。
6. 中文转述：Service Mesh 专注处理**服务和服务间的通讯**，负责构造稳定可靠的服务通讯基础设施，让架构更先进、更 Cloud Native；工程上基本是一组轻量级服务代理与应用逻辑部署在一起，**对应用服务透明**。
7. 四个特点：
   1. Service Mesh 是一个**基础设施**；
   2. Service Mesh 是一个**轻量的服务通讯的网络代理**；
   3. Service Mesh 对应用服务**透明无侵入**；
   4. Service Mesh 用于**解耦和分离分布式系统架构中控制层面上的东西**。
8. 核心类比：Service Mesh 就像网络七层模型中的**第四层 TCP 协议**——把底层很难控制的网络通讯控制面都管了（丢包重传、拥塞控制、流量控制），更上面的应用层协议只需关心自己的业务（如 HTTP 的 HTML 协议）。
9. 出现是必然（引 Pattern: Service Mesh），演化路径（原文 6 步）：
   1. 最原始：两台主机间的进程直接通信；
   2. 分离出网络层，服务间远程通信通过底层网络模型完成；
   3. 因为两边服务接收速度不一致，需要在**应用层实现流控**；
   4. 后来发现流控基本可交给网络层实现，于是 **TCP/IP** 成了世界上最成功的网络协议；
   5. 之后认识到分布式系统的 **8 个谬论（The 8 Fallacies of Distributed Computing）**，需要在分布式系统中做"弹力设计"，于是在更上层加入限流、熔断、服务发现、监控等功能；
   6. 发现这些弹力模式都可**标准化**，写成 SDK/Lib/Framework 在开发层集成；又发现 SDK 不能跨语言、改动要重新编译发布，于是出现了**专门的层**——Sidecar；Sidecar 组成平台后加上**集群管理控制面板**，就是完整的 Service Mesh 架构。
10. 组成：绿色模块是真实业务应用服务，蓝色模块是 Sidecar，二者组成一个**网格**；应用服务完全独立自包含，只需依赖本机 Sidecar，剩下的事全交给 Sidecar。
11. Sidecar 平台 = 一个 **Cloud Native 的服务流量调度平台**（呼应《分布式系统的本质》里说的关键技术：流量调度与应用监控，都可通过 Service Mesh 完成）。
12. 开源软件现状：
    1. 比较流行的是 **Istio** 和 **Linkerd**，都可在 Kubernetes 中集成；
    2. 新成员 **Conduit**，由 Linkerd 作者出来自己做，用 **Rust 和 Go** 写成：**Rust 负责数据面，Go 负责控制面**；号称吸取了 Linkerd 的 **Scala** 教训，比 Linkerd 更快、更轻、更简单；
    3. 作者判断：不是语言偏好者，但不可否认 **Rust/Go 在性能上比 Scala 好得多**，尤其做网络通讯相关的基础设施时性能比较重要；
    4. 推荐：用 Rust/Go 实现的 Istio 和 Conduit，**后者比前者轻很多**；可按需求挑选或自己实现。
13. Istio 架构（原文指名三个组件）：
    1. 核心 Sidecar 叫 **Envoy（使者）**，协调服务网格中所有服务的出入站流量，提供服务发现、负载均衡、限流熔断，并收集大量与流量相关的性能指标；
    2. 控制面上有一个叫 **Mixer** 的收集器，从 Envoy 收集被监控到的流量特征和性能指标；
    3. 通过 **Pilot** 控制器把相关规则发送到 Envoy，让 Envoy 应用新规则；
    4. 还有为安全设计的 **Istio-Auth** 身份认证组件，做服务间的访问安全控制。
14. 设计重点一（关键风险，原文最强的一条）：Kubernetes 和 Docker 也是分布式系统管理面的技术方案，同样对应用透明，且**对应用服务的干扰比较少**——它们的服务进程失败**不会**导致应用服务异常运行；但 **Service Mesh 不是**：因为它调度了流量，**如果 Service Mesh 有 bug，或 Sidecar 组件不可用，就会导致整个架构出现致命问题**。
15. 设计重点二（兜底）：必须小心考虑"Sidecar 出问题怎么办"，网格一定要**高可靠**，或出现故障时有 **workaround**。一种较好的方式是：除了本机 Sidecar，再部署**稍微集中一点的 Sidecar**（比如为某个服务集群部署一个集中式 Sidecar），本机的有问题就走集中的。
16. 设计重点三（粒度与 Gateway 的想象空间）：Sidecar 本来就是调度流量的，粒度可以细到每个服务实例、粗到一组服务、还可以粗到整体接入——"这看来看去都像是一个 **Gateway** 的事"，所以**用 Gateway 来干这个事应该最合适**，Service Mesh 的想象空间一下大很多。
17. 设计重点四（部署形态）：Service Mesh 不像 Sidecar 需要和 Service 一起打包部署，它**完全独立部署**，于是成了一个**基础设施**、像一个 **PaaS 平台**；所以**能不能和 Kubernetes 密切结合**成为非常关键的因素。

## 56｜管理设计篇之"网关模式"
> 源文件 `.tmp-zuoer/txt/56丨管理设计篇之“网关模式”.txt`，7,415 字

### 一句话结论
一个一个服务配 Sidecar 太贵，把"进入系统的唯一入口"收敛成一个可粗可细的 Gateway 更划算：它承担路由、注册、负载均衡、弹力、安全、灰度、API 聚合与编排等治理职责，但设计上必须守住三条——**高性能不成为瓶颈、高可用不成单点、高扩展能二次开发**，以及一条铁律：**业务松耦合、协议紧耦合（只碰协议头，不碰协议体）**。

### 知识点全清单（A1 零丢失）
1. 承接：Sidecar 与 Service Mesh 都在不侵入业务的情况下解耦控制面与数据面，但**都让运维成本变得特别大**——每个服务都要一个 Sidecar，让本就复杂的分布式架构更难管理。
2. 作者判断：**不需要为每个服务实例配一个 Sidecar**；一个服务集群配一个 Gateway 就可以了，或一组类似服务配一个 Gateway。
3. 粒度弹性：Gateway 可细到每个服务实例一个、可粗到一组服务一个、甚至粗到整个架构一个接入 Gateway，于是**整个系统架构的复杂度变得简单可控**。
4. 多层 Gateway 架构：一个总 Gateway 接入所有流量并分发给不同子系统，还有第二级 Gateway 做各子系统接入；网关管理的服务粒度可粗可细。
5. 拓扑可能性：通过网关可把分布式架构组织成**星型结构**（由网络对服务请求进行路由和分发），也可架构成 **Service Mesh 那样的网格**，或只为适配某些服务做 Sidecar。
6. 代价：这样一来 **Sidecar 不再那么轻量，而且很有可能变得比较重**。
7. 定位：Gateway 是一个服务器，也可以说是**进入系统的唯一节点**；和面向对象设计模式中的 **Facade 模式**很像——封装内部系统架构、对外提供 API；还可能有授权、监控、负载均衡、缓存、熔断、降级、限流、请求分片和管理、静态响应处理等功能。
8. 网关的 **8 项功能**：
   1. **请求路由**：不再是 Sidecar，网关必须有路由功能；对调用端很方便，调用端不需要知道其它服务地址，全交给 Gateway。
   2. **服务注册**：为代理后端服务并把请求路由到正确位置，网关要有服务注册功能，后端服务实例可注册/取消注册其服务地址；一般注册的是 API 接口——比如 HTTP Restful 请求可注册 API 的 URI、方法、HTTP 头，Gateway 据此决定路由到哪个后端服务。
   3. **负载均衡**：一个网关可接收多个服务实例，需要在各对等实例上做负载均衡；简单是 Round-Robin 轮询，复杂点可设权重分发，再复杂可做 **session 粘连**。
   4. **弹力设计**：把异步、重试、幂等、流控、熔断、监视都实现进去，让应用服务只关心业务逻辑（数据面）而非控制逻辑（控制面）。
   5. **安全方面**：SSL 加密及证书管理、Session 验证、授权、数据校验、对请求源恶意攻击的防范；"错误处理越靠前的位置就是越好"，网关可做成全站接入组件来保护后端服务。
   6. **灰度发布**：可对相同服务的不同版本实例导流并收集数据，对软件质量提升甚至产品试错都有积极意义。
   7. **API 聚合**：微服务变小后客户端可能要多次请求才能拿到全部数据，频繁通信对性能和规模不利；可让网关帮客户端请求多个后端服务（有些场景可并发），把响应结果拼装后回传（也可做成异步，但需客户端配合）。
   8. **API 编排**：走完完整业务流程要调一系列 API，像工作流，可通过网页编排，用 **DSL** 定义和编排不同 API，或像 **AWS Lambda** 那样串联不同 API。
9. **Gateway / Sidecar / Service Mesh 三者的区别**（原文明确对比）：
   1. **Sidecar 主要用来改造已有服务**：架构变更需要业务方配合改造，而业务方事情多、架构变更优先级低，导致"**政治复杂度**"太高；Sidecar 可适配应用服务、成为进出请求的代理，从而做很多对业务方完全透明的事。
   2. **Service Mesh**：Sidecar 越来越多时需要统一管理，于是给 Sidecar 加一个**全局中心控制器**，就成了 Mesh；有了中心控制器后，可把非业务功能全部实现在 Sidecar 和 Controller 中，业务方只需把服务放进网格，通讯与弹力都不用管，"像一个服务的 PaaS 平台"。
   3. **Gateway**：Mesh 的架构和部署**太过于复杂**，会让运维层复杂度变大；作者认为 Sidecar 粒度应可粗可细，但 **Gateway 更为适合**——而且 Gateway **只负责进入的请求**，不像 Sidecar 还要负责对外请求；因为 Gateway 可把一组服务聚合，服务对外请求可交给对方服务的 Gateway，于是只需一个负责进入请求的 Gateway 来简化"同时负责进出请求"的 Sidecar 的复杂度。
   4. 结论：**Gateway 的方式比 Sidecar 和 Service Mesh 更好**，当然具体问题具体分析。
10. 设计重点一 **高性能**：网关不应也不能成为性能瓶颈。①最好用高性能语言实现，如 **C、C++、Go 和 Java**；②对后端和对前端的请求一定要用**异步非阻塞 I/O**，确保后端延迟不会导致性能问题——C/C++ 可参考 Linux 的 **epoll** 和 Windows 的 **I/O Completion Port**，Java 如 **Netty、Vert.x、Spring Reactor** 的 NIO 框架，"我还是更喜欢 Go 语言的 **goroutine 加 channel** 玩法"。
11. 设计重点二 **高可用**：所有流量或调用都经过网关，网关必须是高可用技术组件，它的稳定直接关系所有服务的稳定；**网关如果没设计好，就会变成一个单点故障**。好的网关至少要做到：
    1. **集群化**：网关要能自己组成集群、自己同步集群数据，**不依赖第三方系统同步数据**；
    2. **服务化**：做到**不间断修改配置**——一种像 Nginx `reload` 那样不停服务，另一种最好做到服务化，即有自己的 **Admin API** 在运行时改配置；
    3. **持续化**：优雅重启（像 Nginx），有**主管请求分发的主进程**，重启时新请求分到新进程，老进程处理完正在处理的请求后退出。
12. 设计重点三 **高扩展**：网关承接所有业务流量，必然会有或多或少业务逻辑，而业务逻辑多变不确定，所以网关要可扩展、能二次开发。像 Nginx 通过 **Module** 二次开发固然可以，但"我还是觉得应该做成像 **AWS Lambda** 那样的方式，也就是所谓的 **Serverless 或 FaaS（Function as a Service）**"。
13. 运维方面的设计原则（原文 4 条）：
    1. **业务松耦合，协议紧耦合**：网关不应与后面服务形成服务耦合，也不应有业务逻辑；网关是**网络应用层**的组件，**不应该处理通讯协议体，只应该解析和处理通讯协议头**；除服务发现外，网关不应有第三方服务依赖。
    2. **应用监视，提供分析数据**：网关上要有应用性能监控，除后端服务高可用统计外，还要用 **Tracing ID** 做分布式链路跟踪，统计一定时间内每个 API 的吞吐量、响应时间和返回码，以便启动弹力策略。
    3. **用弹力设计保护后端服务**：网关一定要实现熔断、限流、重试和超时；如果一个或多个服务调用耗时过长，可接受超时并返回一部分数据，或返回网关里缓存的**上一次成功请求的数据**。
    4. **DevOps**：网关太关键，需要 DevOps 把故障概率降到最低——软件要经过精良测试，包括功能、性能测试，还有**浸泡测试**；还需要一系列自动化运维管控工具。
14. 整体架构方面的注意事项（原文 5 条）：
    1. **不要在网关代码里内置聚合后端服务的功能**，而应把聚合服务放在网关核心代码之外——可用 **Plugin**，也可放在网关后面形成一个 **Serverless 服务**。
    2. **网关应该靠近后端服务**，和后端服务用同一个内网，保证低延迟并减少网络问题；"网关处理的**静态内容应该靠近用户（放到 CDN 上）**，而网关和此时的动态服务应该靠近后端服务"。
    3. 网关也需要**容量扩展**，要成为集群分担前端流量：要么 DNS 轮询，要么 CDN 做流量调度，要么更底层性能更高的负载均衡设备。
    4. **服务发现可做一个时间不长的缓存**，避免每次请求都查；系统不复杂时可把服务发现直接集成进网关。
    5. **为网关考虑 bulkhead 设计**：用不同的网关服务不同的后端服务，或用不同的网关服务前端不同的客户。
15. 安全方面的三件事：
    1. **加密数据**：把 SSL 相关证书放到网关上，由网关做统一的 SSL 传输管理；
    2. **校验用户请求**：基本用户验证（是否已登录、token 是否合法）可放网关；但要权衡**是否校验用户输入**——那会让网关从"只关心协议头"变成"要关心协议体"，而协议体不像协议头是标准的，解析协议体还耗费大量运行时间、降低性能。结论：看具体需求——协议体是标准的可以干；对解析带来的性能问题要做**相应的隔离**；
    3. **检测异常访问**：如一段比较短的时间内请求次数超过一定数值、同一客户端的 **4xx 请求出错率太高**；网关一方面要屏蔽这些请求，另一方面要发出警告（可能是被黑客攻击等重大安全问题）。
16. 小结：网关能代替边车，区别是把分布在各个服务边上的边车换成**集中式网关**；网关不必管理所有服务节点，可按需为指定服务集群配网关，也可在网关前加更高层网关，构造出**星型结构**。

## 57｜管理设计篇之"部署升级策略"
> 源文件 `.tmp-zuoer/txt/57丨管理设计篇之“部署升级策略”.txt`，4,013 字

### 一句话结论
部署升级只有 5 种策略（停机、蓝绿、滚动、灰度/金丝雀、AB 测试），选型的判据不是"哪个先进"，而是**你到底对什么没信心**：蓝绿是为了不停机、金丝雀是对"质量"没信心、AB 测试是对"功能"没信心。

### 知识点全清单（A1 零丢失）
1. 背景：分布式系统下一个服务有多个实例，部署/升级一个服务会变得比较麻烦。
2. **原文只列了 5 种策略**（不是 7 种）：
   1. **停机部署（Big Bang / Recreate）**：把现有版本的服务停机，然后部署新版本。
   2. **蓝绿部署（Blue/Green / Stage）**：部署好新版本后，把流量从老服务那边切过来。
   3. **滚动部署（Rolling Update / Ramped）**：一点一点地升级现有的服务。
   4. **灰度部署（Canary）**：把一部分用户切到新版本，看有没有问题，没问题就继续扩大升级直到全部升级完成。
   5. **AB 测试（A/B Testing）**：同时上线两个版本，然后做相关的比较。
3. **停机部署**细节：
   1. 最简单粗暴；有时**不得不**用：比如新版本用到和老版本**完全不兼容的数据表设计**，此时对生产有两个变更（数据库 + 服务）且新老互不兼容，只能停机部署。
   2. 优势：部署过程中**不会出现新老版本同时在线**，所有状态完全一致；**停机部署主要是为了新版本的一致性问题**。
   3. 问题：会停机，对用户影响很大；一般需要**事前挂公告**，并选择**用户访问少的时间段**来做。
4. **蓝绿部署**细节：
   1. 与停机部署最大的不同：在生产线部署**相同数量**的新服务，新服务测试确认 OK 后把流量切过来；**无需停机**。
   2. 这就是常说的**预发环境**：作者在以前的金融公司经常用——生产线上两套相同集群，一套 Prod 是真实服务、另一套 Stage 是预发环境；发布发 Stage，然后把流量切到 Stage，于是 **Stage 成了 Prod，之前的 Prod 成了 Stage，"有点像换页似的"**。
   3. 优点：没有停机、实时发布升级、避免新旧版本同时在线。
   4. 问题：**有点浪费**，需要**双倍资源**（"不过，这只是在物理机时代，在云计算时代没事，因为虚拟机部署完就可以释放了"）。
   5. 附加问题：**如果服务中有状态**（比如一些缓存），停机部署和蓝绿部署**都会有问题**。
5. **滚动部署**细节：
   1. 做法：逐个替换应用的所有实例来缓慢发布新版本。典型过程：负载调度后有一个版本 A 的实例池，一个版本 B 的实例部署成功、可以响应请求时被加入池中，然后版本 A 的一个实例从池中删除并下线。
   2. 优点：直接对现有服务升级，便于操作；**在缓慢更新过程中对有状态的服务也比较友好，状态可以在更新中慢慢重建起来**。
   3. 问题（原文列 5 条）：
       1. 发布过程中会出现**新老两个版本同时在线**，同一用户的请求可能在新老版中切换而导致问题；
       2. **新版程序没有在生产线上经过验证就上线了**；
       3. 整个过程生产环境处于**新老更替的中间状态**，有问题要回滚就有点麻烦；
       4. 升级过程中若还要做别的运维工作，**要判断哪些结点是老版本、哪些是新版本**，"这太痛苦了"；
       5. 新老代码同时在线，**其依赖的服务需要同时处理两个版本的请求**，可能带来兼容性问题。
6. **灰度部署（金丝雀）** 细节：
   1. 得名：来源于矿井中的金丝雀。**17 世纪**英国矿井工人发现金丝雀对**瓦斯**十分敏感：空气中哪怕有极微量瓦斯，金丝雀也会**停止歌唱**；瓦斯超过一定限度时，虽然鲁钝的人类毫无察觉，金丝雀**早已毒发身亡**。当时采矿设备简陋，工人每次下井都会带一只金丝雀作为"**瓦斯检测指标**"，以便危险时紧急撤离。
   2. 做法：逐渐把生产环境流量从老版本切到新版本，**流量按比例分配**——例如 **90% 的请求流向老版本、10% 流向新版本**；没问题就逐步扩大新版本流量、减少老版本流量。
   3. 多租户平台（如云计算）还可以先把新版本**部署给一些用户**，没问题再扩大，直到全部用户；**一般策略是从内部用户开始，然后一般用户，最后大客户**。
   4. 适用：**缺少足够测试、缺少可靠测试、或对新版本稳定性缺乏信心**的情况。
   5. 用户选择技术（原文 5 种）：**浏览器 cookie**、**查询参数**、**地理位置**、**技术支持（浏览器版本、屏幕尺寸、操作系统）**、**客户端语言**。
   6. 与滚动部署的差别（原文点睛）：灰度是"把一部分用户切到新版上来，看有没有问题，没问题继续扩大升级直到全部完成"——**按用户切**，不是按实例滚。
7. **AB 测试** 细节：
   1. 与蓝绿、金丝雀**完全不一样**：AB 测试是**同时上线两个版本，然后做相关的比较**；它是用来测试**应用功能表现**的方法，例如可用性、受欢迎程度、可见性等。
   2. 三者动机的精确区分：**蓝绿部署是为了不停机，灰度部署是对新版本的质量没信心，而 AB 测试是对新版的功能没信心**——"注意，一个是质量，一个是功能"。
   3. 适用例子：网站 UI 大改版、推荐算法更新、流程改变——不知道新版本是否会得到用户青睐或更好的体验，需要收集用户数据才能知道。
   4. 做法：在生产线上发布两个版本，拉一部分用户当"小白鼠"，通过科学的观测得出结论。
   5. AB 测试的严谨性要求：旨在通过**科学的实验设计、采样样本代表性、流量分割与小流量测试**等方式获得具有代表性的实验结论，并确信该结论推广到全部流量时可信。
   6. 与灰度的包含关系：**AB 测试包含了灰度发布的功能**——观测如果只是观测有没有 bug，那就是灰度；复杂一点要观测用户数据指标，完全可以做成自动化：新版本数据好就自动切一点流量过来，不行就换一批用户（样本）再试。
8. **选型建议**（原文逐条）：
   1. 部署方法很多，实际采用哪种**取决于需求和预算**；
   2. 发布到**开发或模拟环境**时，**停机或滚动部署**是好选择，因为干净和快速；
   3. 发布到**生产环境**时，**滚动部署或蓝绿部署**通常是好选择，但**新平台的主流程测试是必须的**；
   4. **蓝绿部署也不错，但需要额外的资源**；
   5. 如果应用**缺乏测试**、或对软件的**功能和稳定性影响缺乏信心**，可用**金丝雀部署或 AB 测试**发布；
   6. 如果业务需要**根据地理位置、语言、操作系统或浏览器特征**等参数给特定用户测试，可采用 **AB 测试技术**。
9. 小结：常见部署升级策略有停机、蓝绿、滚动、灰度和 AB 测试这几种；每种都讲了含义与优缺点；并做了放在一起的比较。

## 58｜性能设计篇之"缓存"
> 源文件 `.tmp-zuoer/txt/58丨性能设计篇之“缓存”.txt`，6,005 字

### 一句话结论
分布式系统最慢的是数据库的 select，而缓存是"用一致性换性能"最划算的一招；工程上真正要决策的只有三件事——**用哪种更新模式（谁维护缓存、写库还是写缓存）、命中率够不够、以及缓存放在进程外还是进程内**。

### 知识点全清单（A1 零丢失）
1. 前提：分布式系统中最耗性能的地方是**最后端的数据库**。
2. 数据库四种操作（select、update、insert、delete）中，**三个写操作一般不会出现性能问题**：insert 一般没问题，update 和 delete 一般有主键所以也不会太慢；**除非索引建得太多、且数据太多**，这三个操作才会变慢。
3. 绝大多数情况下 **select 是性能问题最大的地方**：①select 有很多像 **join、group、order、like** 这样丰富的语义，非常耗性能；②大多数应用**读多写少**，加剧了慢查询问题。
4. 分布式系统中**远程调用**也消耗很多资源，网络开销会导致整体响应时间下降；为了挽救这种性能开销，在业务允许（**不需要太实时的数据**）时，使用缓存是非常必要的事情。
5. 移动互联网视角：缓存是必不可少的一部分——网络质量不一定永远最好，所以前端也会为所有 API 加缓存，否则网络不通畅时没数据、前端都不知道怎么展示 UI；既然必须容忍数据不实时，那么业务上大多数情况下就可以用缓存。
6. **缓存更新的三种模式（原文标题即"三种"）**：
   1. **Cache Aside**（最常用）：
      - 三步：失效（先从 Cache 取，没取到从数据库取，成功后放入缓存）、命中（从 Cache 取到后返回）、**更新（先把数据存到数据库，成功后，再让缓存失效）**。
      - 出处：标准设计模式，**Facebook 的论文《Scaling Memcache at Facebook》**也用了这个策略。
      - 为什么是"删除缓存"而不是"写完库更新缓存"：见 Quora 问答《Why does Facebook use delete to remove the key-value pair in Memcached instead of updating the Memcached during write request to the backend?》，**主要是怕两个并发的写操作导致脏数据**。
      - 它仍有并发问题：一个读操作没命中缓存要去数据库取；此时来一个写操作，写完库后让缓存失效；然后之前那个读操作再把**老数据**放进去 → 脏数据。
      - 这个案例**理论上会出现，实际概率非常低**：需要"读缓存时缓存失效 + 有一个并发的写操作"，而**数据库的写操作比读操作慢得多、还要锁表**，读操作必须在写操作前进入数据库、又要晚于写操作更新缓存，所有条件都具备的概率并不大。
      - 官方（Quora 答案）的两条出路：要么用 **2PC 或 Paxos** 保证一致性，要么**拼命降低并发时脏数据的概率**；Facebook 选了后者，因为 **2PC 太慢、Paxos 太复杂**。当然，**最好还是为缓存设置好过期时间**。
   2. **Read/Write Through**：
      - 动机：Cache Aside 里应用代码要维护两个数据存储（cache 和 repository），应用比较啰嗦；Read/Write Through 把**更新数据库的操作由缓存自己代理**，对应用层就简单很多——"应用认为后端就是一个单一的存储，而存储自己维护自己的 Cache"。
      - **Read Through**：在查询操作中更新缓存——缓存失效时（过期或 LRU 换出），Cache Aside 由调用方负责把数据加载进缓存，**Read Through 则由缓存服务自己加载**，对应用方透明。
      - **Write Through**：与 Read Through 相仿，但发生在**更新数据**时——没有命中缓存则直接更新数据库然后返回；**命中了缓存则更新缓存，然后由 Cache 自己更新数据库（这是一个同步操作）**。
   3. **Write Behind Caching**（又叫 **Write Back**）：
      - 类比：熟悉 Linux 内核的人会认出这就是 Linux 文件系统的 **page cache** 算法——"基础知识全都是相通的。所以，基础很重要"。
      - 做法：更新数据时**只更新缓存、不更新数据库**，缓存会**异步地批量更新数据库**。
      - 好处：数据 I/O 飞快（直接操作内存）；因为异步，还能**合并对同一个数据的多次操作**，性能提高相当可观。
      - 问题：**数据不是强一致性，而且可能会丢失**（Unix/Linux 非正常关机会丢数据就是这个原因）。
      - 设计哲学："在软件设计上，我们基本上不可能做出一个没有缺陷的设计，就像算法设计中的时间换空间、空间换时间一个道理。有时候，强一致性和高性能、高可用和高性能是有冲突的。软件设计从来都是 **trade-off（取舍）**。"
      - 实现代价：**实现逻辑比较复杂**，需要 **track 哪些数据被更新了**、需要刷到持久层；操作系统的 Write Back 只在 Cache 需要失效时才真正持久化（内存不够、进程退出等），这又叫 **lazy write**。
7. 缓存设计的重点（原文 7 条）：
   1. 缓存更新模式如上，但**缓存已成为高并发高性能架构的关键组件**；很多公司用 **Redis** 搭缓存系统，一是因为 **Redis 的数据结构比较丰富**。
   2. **不能在 Service 内放 Local Cache**：①每台机器内存不够大；②Service 有多个实例，负载均衡器会把请求随机分布到不同实例；③缓存需要在所有实例上都建好，这**让 Service 有了状态、更难管理**。
   3. 所以分布式架构下一般需要**外部缓存集群**；对缓存集群要保证**内存足够大、网络带宽也要好**，因为缓存本质是**内存和 IO 密集型**应用。
   4. 如果内存需要很大，还要动用**数据分片**技术把不同缓存分布到不同机器上，保证缓存集群可以不断 **scale**。
   5. **缓存的好坏要看命中率**：命中率高说明缓存有效；**一般来说命中率到 80% 以上就算很高**；有的系统为追求更高性能要做到 **95% 以上**，甚至把数据库里的数据几乎全部装进缓存——"这当然是不必要的，也是没有效率的，因为通常来说，**热点数据只会是少数**"。
   6. 缓存是**通过牺牲强一致性来提高性能**的，"这世上任何事情都不是免费的"，不是所有业务都适合用缓存，需要仔细调研需求；用缓存提性能就**会有数据更新的延迟**。
   7. **缓存数据的时间周期要好好设计**，太长太短都不好：**过期期限不宜太短**，否则会导致应用不断从数据存储检索数据并添加到缓存；**也不宜太长**，否则没人访问的数据还在内存里不过期，浪费内存。
   8. 一般使用 **LRU 策略**：内存不够需要清出数据时找**最不活跃**的数据（最长时间没有被访问过）；LRU 会在每次数据访问时把其**调到前面**，淘汰时从**最后面**开始。
   9. LRU 的隐藏代价：需要在 key-value 这种**非顺序**的数据结构中维护一个**顺序**的数据结构，并在读缓存时改变被访问数据在顺序结构中的排位；于是 **LRU 在读写时都需要加锁**（除非单线程无并发），因此 **LRU 可能导致更慢的缓存存取时间**，"这点要小心"。
   10. **爬虫问题**：很多网站会被爬虫爬，爬虫可能爬到一些很古老的数据，程序把这些数据加入缓存，导致**真实的热点数据被挤出去**（因为机器速度足够快）；一般需要**爬虫保护机制**，或引导这些人去用你提供的外部 API，在那边有针对性地做**多租户的缓存系统**（把用户和第三方开发者的缓存系统分离开）。

## 59｜性能设计篇之"异步处理"
> 源文件 `.tmp-zuoer/txt/59丨性能设计篇之“异步处理”.txt`，5,677 字

### 一句话结论
异步处理的本质不是"变快"，而是**把被动的任务处理变成主动的任务调度**：前台只追加记录、派发器用推拉结合把任务统筹批发，配合事件溯源与"交易凭证 + 对账 + 补偿"，用最终一致性换吞吐。

### 知识点全清单（A1 零丢失）
1. 承接：弹力设计篇讲过异步通讯有助于提高稳定性与容错；其实异步通讯还能**增加整个系统的吞吐量**，面对更高并发，并从容利用现有系统资源。
2. 为什么：工作中很多人找你做事，若你是**请求响应式**工作方式，本质上是被动工作、被别人驱动；做一件事时别人来找你做别的，你被打断；而且**没办法统筹安排**——本来五件事只需 **2 小时**，不能统筹可能要 **5 小时**。异步处理可以更好地利用时间和资源，利用好了性能自然提升。
3. 邮递业务比喻：寄东西时，邮递公司会把大量**去往同一方向**的订单合并处理，并统一调配物流交通工具，整体上更节省资源和时间。分布式架构中被拆成很多子系统，要合理用好并更快处理大量任务，就需要**统一规划和统筹整体**，达到整体最优——和邮递公司同理。
4. 计算机世界的异步例子一：程序读写文件时，操作系统**不会真正同步操作硬盘**，而是把硬盘读写请求先在内存中 **hold 上一小会儿（几十毫秒）**，然后对读写请求做 **merge 和 sort**。
   1. **merge**：把相同的操作合并——相同的读操作只读一次，相同的写操作**只写最后一次**；
   2. **sort**：把不同的操作排序，这样硬盘**向一个方向转一次**就能把所有数据读出来，而不是来来回回地转；
   3. 效果：极大地提高硬盘吞吐率。
5. 异步例子二：**TCP 协议**向网络发包时，会先把要发的数据在缓冲区里囤积，**囤积到一定尺寸（MTU）** 才向网络发送，从而最大化利用网络带宽，传输速度和性能都变快。
6. 结论一：这就是异步系统带来的好处——**让系统可以统一调度**。
7. 结论二（纠正误解）："我们可能会觉得异步通讯慢，其实并不然，我们同样也可以把异步做得比较实时。"
8. 附带好处：就算有延时，异步处理在用户体验上也能带来一个不错的效果——**用户可以有机会反悔之前的操作**。
9. 与弹力设计篇的分工：那里讲的是**异步通讯**（怎么把系统连接起来），这里讲的是**异步任务处理**（怎么处理任务），两者不冲突。
10. 异步处理的架构（原文三段）：
    1. **前台系统**：把用户发来的请求**一一记录下来**（有点像请求日志），这样对数据库/存储**只有追加操作**，性能很高；收到请求后给客户端返回"**收到请求，正在处理中**"。
    2. **任务处理系统**：真正处理这些请求；为了解耦需要**任务派发器**，于是引出**推模型 Push** 与**拉模型 Pull**。
    3. **Push**：把任务派发给相应的人去处理，像工头调度者；**Pull**：由处理的人来拉取任务处理。
11. Push / Pull 的取舍（原文判据）：
    1. Push 可以做调度，但**需要知道下游工作结点的情况**——不仅要知道哪些活着，还要知道**忙闲程度**；下游扩容缩容、或故障维护时，Push 结点都需要知道，**这会增加一定的系统复杂度**。
    2. Pull 的好处是让上游**不用关心下游状态**，自己忙得过来就来拿任务，减少复杂度，**但少了整体任务调度**。
    3. 一般来说构建的是**推拉结合**系统：Push 端做一定任务调度——像物流那样把**相同商品的订单合并**打成一个包交给下游一次处理，也可把同一用户订单中的不同商品**拆成多个订单**；Pull 端订阅 Push 端发出的异步消息，处理相应任务。
12. **事件溯源（Event Sourcing）**：
    1. 要解决的问题：数据库里只能看到数据的**值（状态）**，但完全不知道这个值是怎么得出的。
    2. 存折比喻：银行存折能看到收支的所有记录，也能看到每一笔记录后的余额。
    3. 核心思路：如果有了所有收支流水账记录，**完全不需要保存余额**，只要**回放所有收支事件**就能得到最终数据状态。
    4. 收益一：系统变得非常简单——只需**追加不可修改的数据操作事件**，而不是保存最终状态；除提高性能和响应时间外，还提供**事务数据一致性**，并保留可启用**补偿操作**的完整记录与历史记录。
    5. 收益二（bug 修复）：记录状态的系统里，修完 bug 还要做**数据修正**；Event Sourcing 系统里只需把所有事件**重新播放一遍**，因为整个系统没有状态了。
    6. 原文列的四条性质：
       1. 事件**不可变**，并可使用**只追加**操作存储；用户界面、工作流或启动事件的进程可继续，处理事件的任务可在**后台异步运行**；处理事务期间**不存在争用**，这两点可极大提高性能和可伸缩性。
       2. 事件是**描述已发生操作的简单对象**以及描述该操作所需的相关数据。
       3. 事件**不会直接更新数据存储**，只会记录，以便在合适的时间处理——这简化实施和管理。
       4. 事件溯源不需要直接更新存储中的对象，因而有助于**防止并发更新造成冲突**。
    7. 最重要的组合：**异步处理 + 事件溯源**，可以让整个系统进行任务的统筹安排、批量处理，让整体处理过程达到性能和资源的最大化利用。
    8. 关联：Event Sourcing 一般会和 **CQRS** 一起提；另有 GitHub 示例项目可看。
13. **异步处理的分布式事务**：
    1. 前提（引《分布式系统的本质》）：分布式事务在强一致下，业务层只能做**两阶段提交**，数据层面需用 **Raft/Paxos**。
    2. 判断：现实生活中需要强一致性的场景**实在不多**，不是所有场景都必须强一致事务。
    3. 餐馆比喻：先付钱拿小票去领餐——把"交钱"和"取货"两个动作分开，餐馆有更高并发和接客能力；若做成两阶段提交（顾客锁定钱、餐馆锁定食材、最后一手交钱一手交餐），"那是一件非常恐怖的事"。
    4. 现实里到处都是"先付钱拿小票领货"或"先消费拿账单去付钱"的场景，**完全不需要两阶段提交**；可以用异步方式达到一致性——当然是**最终一致性**。
    5. 达到最终一致性的机制：需要一个**交易凭证**——一个事务要做 A 和 B 两件事（比如把钱转给朋友），先做扣钱交易、记录下扣钱的**凭证**，拿这个凭证去给朋友账号加钱。
    6. 达成事务的三点注意：①凭证需要**非常好地保存**起来，不然事务做不下去；②凭证处理要**幂等**，不然重试时会出现多次交易；③如果事务完成不了，需要做**补偿事务**处理。
14. 异步处理的设计要点（原文 6 条）：
    1. 异步处理中 **事件驱动** 和 **事件溯源** 是两个比较关键的技术。
    2. 异步处理可能因故障导致任务没被处理：**消息丢失、没有通知到、或通知到了没有处理**；因此异步通知方式需要**任务处理方完成后给发起方回传状态**，确保不会漏掉。
    3. 发起方还需要一个**定时任务**，把一些**超时没有回传状态**的任务重新做一遍——"你可以认为这是异步系统中的**'对账'功能**"；要重做就需要处理方支持**幂等性**处理。
    4. 异步处理处理任务时并不知道能否成功，会一步步处理，若最后一步不能成功就需要**回滚**——这时要走弹力设计里说的**补偿事务**流程。
    5. 并不是所有业务都可以用异步：需要**强一致性**的业务不适合，需要小心分析；"我相信绝大多数的业务场景都用不到强一致性，**包括银行业务**"；需要性能时要牺牲强一致性、变为最终一致性。
    6. 运维时要**监控任务队列里的任务积压情况**：有积压要能快速扩容；如果不能扩容且积压太多、可能导致整个系统挂掉，就要开始**对前端流量进行限流**。
15. 收尾强调：异步处理系统的本质是**把被动的任务处理变成主动的任务处理**，其本质是在**对任务进行调度和统筹管理**。

### 数字 / 公式 / 阈值
- 统筹的收益示例：五件事 **2 小时**（能统筹）vs **5 小时**（不能统筹）。
- 文件系统：hold **几十毫秒**。
- 网络：缓冲区囤积到 **MTU** 才发送。
- 分布式事务两条路：业务层 **2PC**；数据层 **Raft/Paxos**。
- 交易凭证的三条要求：保存好 / 幂等 / 补偿。
- 异步设计要点：**6 条**。
- 本讲无 QPS/延迟阈值（原文未展开）。

### 原话（可逐字引用）
- "异步处理系统的本质是把被动的任务处理变成主动的任务处理，其本质是在对任务进行调度和统筹管理。"
- "我们可能会觉得异步通讯慢，其实并不然，我们同样也可以把异步做得比较实时。"
- "如果要做成两阶段提交，顾客锁定好钱，餐馆锁定好食材，最后一手交钱一手交餐，那么这是一件非常恐怖的事。"
- "你可以认为这是异步系统中的'对账'功能。"

### 反例 / 坑 / 作者明确反对的做法
- 用请求响应式的被动方式串行处理任务、不统筹（5 件事从 2 小时变 5 小时）。
- 用 Push 却不知道下游的存活与忙闲（复杂度失控）；只 Pull 又失去整体调度。
- 在没有持久化/幂等/监控的情况下上异步（原文反面即"消息丢失/没通知到/通知到了没处理"）。
- 用 Event Sourcing 却不接受"回放成本/无状态"的取舍（原文未展开代价，书稿 32.4 补了）。
- 所有业务都上强一致两阶段提交（"非常恐怖"）。
- 异步任务不设超时重做（无对账）→ 漏任务。
- 任务积压了只扩不控（扩不动时要对入口限流）。
- 只把异步当"性能技巧"，不做任务编排与批量（丢掉异步最大的收益）。
