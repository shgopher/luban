### 一句话结论
分布式系统的门槛不在"知道几个组件"，而在四条理论地基（CAP / 8 条错误假设 / FLP / 共识原语）加一份"读哪本、读到什么程度"的书单；**错误不可避免，正确做法是把错误处理当功能写进代码**。

### 知识点全清单（A1 零丢失）
1. 立论：分布式系统技术栈巨大无比，所以学习资料多；本文只覆盖"基础理论 + 图书资料"，后续按主题逐步推荐。
2. CAP 定理地位：分布式系统设计中最基础、最关键的理论；分布式数据存储不可能同时满足 C、A、P。
3. 三个字母的准确含义（原文给的定义）：
   - 一致性 C：每次读取要么获得最近写入的数据，要么获得一个错误；
   - 可用性 A：每次请求都能获得一个（非错误）响应，但不保证返回的是最新写入的数据；
   - 分区容忍 P：尽管任意数量的消息被节点间网络丢失（或延迟），系统仍继续运行。
4. CAP 的正确读法：**存在网络分区时 C 与 A 必须二选一；没有网络故障（正常运行）时 C 与 A 可以同时满足**。CAP 中的一致性 ≠ ACID 事务中的一致性。
5. CA 模型：关注 C + A，需要非常严格的全体一致协议（如两阶段提交 2PC）；不能容忍网络错误或节点错误，一旦出现就拒绝写请求——因为它不知道对端是挂了还是网络问题，**唯一安全的做法是把自己变成只读的**。
6. CP 模型：关注 C + P，走"大多数人的一致性协议"，如 Paxos（Quorum 类算法）；只保证多数结点数据一致，少数未同步到最新版本的结点变成不可用，因此只提供**一部分**可用性。
7. AP 模型：关注 A + P，不能达成一致性，必须给出数据冲突；给出冲突就要维护数据版本；Dynamo 就是这类系统。
8. 业务取舍判据：多数互联网应用（如门户）机器数量庞大、部署节点分散、网络故障是常态 → 必须保可用性，只能舍一致性走 AP；银行等需确保一致性的场景 → 在 CA 与 CP 间权衡（CA 在网络故障时完全不可用，CP 具备部分可用性）。
9. CAP 常见误用：Cloudera 工程博客《CAP Confusion: Problems with 'partition tolerance'》有详细阐述；谷歌《Transaction Across DataCenter》视频里有 CAP 在具体工程中的体现图。
10. 8 条错误假设（Fallacies of Distributed Computing）来源：Sun 公司的劳伦斯·彼得·多伊奇（Laurence Peter Deutsch）等人 **1994~1997** 年提出，讲刚进入分布式计算领域的程序员常犯的一系列错误假设；每条都会随时间被证明是错的，并导致严重问题与痛苦的学习体验。
11. 8 条原文清单：① 网络是稳定的；② 网络传输的延迟是零；③ 网络的带宽是无穷大；④ 网络是安全的；⑤ 网络的拓扑不会改变；⑥ 只有一个系统管理员；⑦ 传输数据的成本为零；⑧ 整个网络是同构的。
12. 多伊奇背景（原文用一整段讲，属"知识钩子"）：1946 年生于美国波士顿；创办阿拉丁企业（Aladdin Enterprises）并写出著名开源软件 Ghostscript，1988 年首次发布；学生时代与艾伦·凯（Alan Kay）等年长者一起开发 Smalltalk，其成果激发了后来 Java 的 JIT 编译技术；后入 Sun 成为公司院士；1994 年成为 ACM 院士。
13. 延伸阅读：阿尔农·罗特姆-盖尔-奥兹（Arnon Rotem-Gal-Oz）2006 年长文《Fallacies of Distributed Computing Explained》，讲这 8 条被提出十多年后的影响——为什么当今系统仍要避免、在当今软硬件环境下这些错误意味着什么（谈"延迟为零"时还提到 2005 年开始流行的 AJAX）；加勒思·威尔逊（Gareth Wilson）的文章用日常生活例子做更通俗解释。
14. 8 条的重要性边界：对中间件/底层系统开发者及架构师重要，对网络应用开发者也同样重要；容错、备份、分片、微服务等对应用开发者可能部分透明，**但这 8 点必须知道**。
15. 为什么必须深刻认识这 8 条：让人清楚认识到分布式系统中错误不可避免；能做的不是避免错误，而是把错误处理当成功能写进代码。
16. 《Distributed systems theory for the distributed systems engineer》观点：给新手推荐大量理论论文是**错误方法**（除非这是博士课程），因为论文难度大又复杂、需认真学习，还要理解成果产生的时代背景才能领悟精妙。作者给出"分布式工程师必须掌握"的知识列表，并断言掌握这些足够设计新的分布式系统。
17. 其 4 份入门材料：① Lamport 时钟 + Vector 时钟 + Dynamo 论文；② 小书《Distributed Systems for Fun and Profit》（讲时间的作用与不同复制策略）；③《Notes on distributed systems for young bloods》（无理论，适合新手的实践笔记）；④ 论文《A Note on Distributed Systems》（为什么远程交互不能像本地对象那样进行）；⑤（同列）8 条错误假设一文。
18. 六个关键点之一"失败和时间"：分布式系统工程师的很多困难可归为两个根因——进程可能会失败；没有好方法表明进程失败。由此牵出系统时钟设置、进程间通讯机制，以及"没有任何共享时钟时如何确定一个事件发生在另一个事件之前"。
19. 关键点之二"最终一致性"：以系统行为弱保证为代价试图避免上述压力；读 Dynamo 论文与帕特·赫尔兰（Pat Helland）经典论文《Life Beyond Transactions》可获得大启发。
20. 关键点之三"容错的压力"：能不降级容错的系统一定要像没有错误发生那样运行 ⇒ 某些部分必须冗余地工作 ⇒ 在性能与资源消耗两方面带来成本。
21. 关键点之四"基本原语"：分布式系统里几乎没有一致认同的基本构建模块，但正在越来越多出现；Leader 选举可参考 Bully 算法；分布式状态机复制可参考维基百科与 Lampson 的论文（后者更权威，只是有些枯燥）。
22. 关键点之五"基本结论"三条：进程间可能丢消息 ⇒ 不可能在实现一致性存储的同时响应所有请求（这就是 CAP）；一致性不可能同时满足"总是正确"与"异步系统中只要一台机器故障系统总能终止"（FLP）；一般而言消息交互少于两轮都不可能达成共识。
23. 关键点之六"真实系统"：学分布式架构最重要的是结合真实系统描述，反复思考和点评其背后的设计决策——谷歌 GFS、Spanner、Chubby、BigTable、Dapper，以及 Dryad、Cassandra、Ceph 等非谷歌系统。
24. 共识问题定义：让网络上的分布式处理者最后都对同一个结果值达成共识；方案对错误有恢复能力，处理者一旦崩溃就不再参与计算。
25. 同步环境下的解法：每个操作步骤的时间与网络通信延迟都是有限的，因此可能解决——方式是**等待一个完整步长**来检测某个处理者是否已失败，没收到回复就假定它已崩溃。
26. 共识的强/弱关系：共识问题有几个变种，强度不同；通常更"强"问题的解决方案同时也能解决比它更"弱"的问题。
27. 较强形式的共识三特性（= 终止、一致同意、有效性；具备这三点即被认为解决了共识问题）：① 所有无错误的进程（处理过程）最终都将决定一个值；② 所有会做决定的无错误进程决定的都将是同一个值；③ 最终被决定的值必须被至少一个进程提出过。
28. FLP 名字来源与定位：Fischer、Lynch、Paterson 三人；讨论"理论上能做出的功能最强的共识算法会受到怎样的限制"。
29. FLP 两条主要结论：① 异步模型下不存在完全正确的共识算法——不仅较强形式不可能，比它弱、只需一些无错误进程做决定的算法也不可能；② 异步模型下存在部分正确的共识算法，前提是所有无错误进程都总能做出决定、没有进程在执行过程中死亡、初始情况下超过半数进程都存活。
30. FLP 的总结论：异步模型中**仅一个处理者可能崩溃**，就已没有分布式算法能解决共识问题——这是该问题的理论上界。原因：异步模型下"处理者完成工作再回复消息"所需时间没有上界，无法判断它到底是崩了、在慢慢回复、还是网络延迟很大。
31. FLP 的两个工程启发：① 网络延迟很重要，网络不能长时间拥塞，否则共识算法会因延迟过长超时失败；② 计算时间也很重要，分布式数据库提交这类过程要在短时间算出能否提交，需保证内存容量、磁盘空闲时间、CPU 时间充足，并在软件层面确保计算不超时。
32. Paxos 为何可行：它并不属于 FLP 所说"完全正确"的算法，正确性会受超时值影响；但这不妨碍它在实践中有效，因为可通过避免网络拥塞等手段保证超时值合适。
33. 《An introduction to distributed systems》：分布式系统基础课的课程提纲，几乎涵盖所有知识点并配简洁切中要害的说明，适合初学者提纲挈领地形成知识体系；也可当"分布式系统知识图谱"，按列出的知识点一一搜索。
34. 《Distributed Systems for fun and profit》：免费电子书；目的是以更易理解的方式讲亚马逊 Dynamo、谷歌 BigTable、MapReduce 背后的核心思想；只着力关键概念、详实但不陷细节。全书五章：扩展性/可用性/性能/容错基础 → FLP 与 CAP → 大量一致性模型 → 时间与顺序及时钟的各种用法 → 复制问题（如何防止差异、如何接受差异）；每章末附扩展阅读。
35. 塔能鲍姆（Andrew S. Tanenbaum）与马丁·范·斯蒂恩（Martin van Steen）《Distributed Systems: Principles and Paradigms》：经典教材，语言简洁通俗，介绍分布式系统七大核心原理并给大量例子；系统讲述通信、进程、命名、同步化、一致性与复制、容错、安全；讨论分布式应用开发方法（即范型）。**不是"如何做"的手册**，只适合系统性学基础；中文版《分布式系统原理与范型》（第二版）。
36. 《Scalable Web Architecture and Distributed Systems》：免费在线小册子（中文版《可扩展的 Web 架构和分布式系统》）；面向公网分布式系统，但原理可迁移；观点是"了解大型网站分布式架构原理，小型网站构建也能受益"；从高可用、高性能、高可靠、易管理出发，引出类似 Flickr 的典型大型图片网站例子。
37. 该书脉络 A（SOA 与读写）：从程序模块化易组合引出面向服务架构（SOA）；引出读写性能问题——当今软硬件架构上写入几乎总是比读取更慢，包括软件层面（数据库一致性要求、B 树的修改）与硬件层面（如 SSD）；网络提供商的下载带宽通常也比上传带宽大；读可异步、可 gzip 压缩，写往往要保持连接直到数据上传完成 ⇒ 往往想把服务做成读写分离；再由 Flickr 例子介绍服务器分片式集群做法。
38. 该书脉络 B（冗余）：数据冗余异地备份（如 master-slave）、服务多版本冗余、避免单点故障。
39. 该书脉络 C（横向扩容的代价）：多分区扩容即横向扩容，是单机容量无法满足需求时不得不做的设计；代价一是数据局域性变差（本可同机的数据被迫分散，潜在降低性能、主要是延长响应时间），代价二是多份数据的不一致。
40. 该书脉络 D（缓存三级演进）：抛出 TB 级以上大数据的存储问题——内存都缓存不了该数据量，性能会大幅下降，所以要缓存；先是每节点各自缓存，但负载均衡把请求分得很随机、命中率大降 ⇒ 全局缓存 ⇒ 分布式缓存 ⇒ 介绍 Memcached 与 Facebook 的缓存设计方案。
41. 该书脉络 E（代理、索引、负载均衡、会话）：代理服务器可把多个重复请求合并成一个，对公网公共服务能大大减少对数据层的访问，Squid 与 Varnish 可用于生产；知道所读数据的元信息（图片 URL、要全文搜索的单词）时，索引用来找存有该信息的服务器；再谈负载均衡器与典型拓扑；用户会话数据（电商购物车在下单前必须保持有效）——让会话与服务器关联会较难实现自动故障转移，节点少时用轮换式 DNS 即可，且负载均衡会让在线性能问题的检测变得更麻烦。
42. 该书脉络 F（写队列）：写负载可用队列减少服务器压力、保证效率；开源实现很多（RabbitMQ、ActiveMQ、BeanstalkD），也有方案用 Zookeeper 甚至 Redis 这类存储服务。
43. 该书立场：只讲了皮毛，但这是令人兴奋的设计领域，现在与将来创新都很多。
44. 《Principles of Distributed Systems》：苏黎世联邦理工学院教材；讲分布式系统会用到的多种算法；不同场景用不同算法、并不表示都会用到；学生掌握算法设计精髓即可举一反三，得到架构设计所需算法。覆盖：顶点涂色（解决互相冲突的任务分配）、分布式树算法（广播、会聚、BFS 树、最小生成树）、容错与 Paxos（最经典共识算法之一）、拜占庭协议（节点可能没完全宕机而是输出错误信息）、全互联网络（服务器两两互联时的算法复杂度）、多核计算工程实践（事务性存储、资源争用管理）、主导集（又一个用随机化算法打破对称性的例子，可用于路由器建立路由）。
45. 《Making reliable distributed systems in the presence of software errors》：Erlang 之父乔·阿姆斯特朗（Joe Armstrong）力作；源自 1981 年开始的研究项目——寻找更好的电信应用编程方式；当时电信应用都是大型程序，虽经仔细测试，投产后仍有大量错误；作者假设程序中确实有错误，再设法在错误存在下构建可靠系统；测试了所有编程语言，**没有一门拥有电信行业所需的所有特性**，于是催生 Erlang 及配套的 OTP 设计方法论与库集。
46. 该书内容：抽象电信应用的所有需求、定义问题域、讲系统构建思路（模拟现实、简单通用）并给指导规范；阿姆斯特朗认为"在存在软件错误下构建可靠系统"的核心问题可通过编程语言或其标准库解决，所以大篇幅讲 Erlang 与容错电信应用；虽以 20 世纪 80 年代电信系统为背景，但其大规模分布式开发思路与容错核心需求与互联网时代出奇一致。
47. 《Designing Data Intensive Applications》：作者马丁·科勒普曼（Martin Kleppmann）；主题是分布式世界里数据结点扩展这件非常麻烦的事，用很多工程案例深入浅出讲如何扩展。
48. 该书价值：完整梳理各类纷繁复杂设计背后的技术逻辑、不同架构之间的妥协与超越；深入到 B-Tree、SSTables、LSM 这类存储结构，并从外部视角审视它们对 NoSQL 与关系型数据库的影响；能让人清楚了解真实世界大数据架构中数据分区、数据复制的坑并给出解决方案；最赞是把各种技术的本质关联起来帮人触类旁通，按"提出问题 → 解决问题 → 解决方案 → 优化方案 → 对比不同方案"展开；每章后面有几百个 Reference。
49. 出版信息：2017 年 3 月出版，当时还没有中译版，英文也不难读。
50. 小结（作者自述）：2002 年开始接触分布式计算系统，到写文的 2018 年已学 15 年，仍觉很多东西要继续学；书单看着望而却步，但花时间看一定能上一个新台阶，再加工程实践"一定能达到大多数人难以企及的技术境界"。

### 反例 / 坑 / 作者明确反对的做法
- 把 CAP 当"三选二"、或误以为 CA 系统能容忍网络故障（CA 遇错只能变只读）。
- 把 CAP 的一致性等同于 ACID 的一致性。

## 29｜推荐阅读：分布式数据调度相关论文
> 源文件 `.tmp-zuoer/txt/29丨推荐阅读：分布式数据调度相关论文.txt`，8355 字

### 一句话结论
数据调度的难点只有一个——**副本之间的一致性**；工程上真正可用的路线是 Paxos/Raft（共识）、逻辑钟/向量钟（定因果）、Gossip（反熵收敛）三件套，而数据库的终局是 Aurora/Spanner 那种"存储计算分离 + 一致性协议在上层"的形态，分库分表 + 数据访问代理会成为历史。

### 知识点全清单（A1 零丢失）
1. 问题定位：分布式系统关键技术之一是"数据调度"；因为要扩充节点、提高高可用性，必须冗余数据结点；建立副本看上去容易，**最大的难点是分布式一致性问题**。
2. Paxos 的地位与出处：莱斯利·兰伯特（Lesile Lamport）**1990 年**提出，基于消息传递、具有高度容错特性的一致性算法；有人说"分布式下真正的一致性算法只有 Paxos"。
3. 为什么 Paxos 长期停留在论文里：算法太晦涩，一直属于理论上的论文性质的东西。
4. 进入工程圈的源头：Google 的 **Chubby lock**——一个分布式锁服务，用在了 Bigtable 中；直到 Google 发布相关论文，Paxos 才进入工程界视野。
5. Google 的四篇（原文并列）：《Bigtable: A Distributed Storage System for Structured Data》《The Chubby lock service for loosely-coupled distributed systems》《The Google File System》《MapReduce: Simplifed Data Processing on Large Clusters》。
6. 关键提醒：这几篇论文并没有讲太多 Paxos 算法细节；**细节在《Paxos Made Live – An Engineering Perspective》**——讲 Google 实现 Paxos 时遇到的各种问题与解决方案，讲"从理论到实际应用二者之间巨大的鸿沟"。为什么建议读：它不讨论算法本身，而讨论如何把理论应用到实践、如何弥补理论在实践中的不足、如何取舍、如何测试——"这些在实践中的各种问题才是工程的魅力"。
7. Paxos 入门替代读物（原版太晦涩不易懂）：《Neat Algorithms - Paxos》（配小动画帮助读懂）、《Paxos by Examples》。
8. 自己实现 Paxos 的参考四篇：《Paxos Made Code》（作者马克罗·普里米 Marco Primi，实现了开源库 libpaxos）、《Paxos for System Builders》（从系统实现者角度讨论 Leader 选举、数据及消息类型、流控等具体问题）、《Paxos Made Moderately Complex》（2011 年发表，较新，给很多实现细节与伪代码，既助理解也可据此实现）、《Paxos Made Practical》（主要讲如何用 Paxos 实现 replication）。
9. 现成实现：GitHub 上的《Plain Paxos Implementations Python & Java》、《A go implementation of the Paxos algorithm》。
10. ZooKeeper 的正确定位：有和 Paxos 非常相似的特征（领导选举、提案号等），但**本质上不是 Paxos 协议，而是自己发明的 Zab 协议**；论文《Zab: High-Performance broadcast for primary-backup systems》。
11. "谷三篇"：GFS、MapReduce、Bigtable 并称；整个世界工程系统因这三篇开始向分布式系统演化，云计算中很多关键技术也因它们才成熟；后来雅虎基于这三篇开发了开源软件 Hadoop。
12. Raft 的动机：Paxos 太晦涩、实际实现坑太多、不容易写对 ⇒ 有人搞出另一个一致性算法 Raft。原始论文《In search of an Understandable Consensus Algorithm (Extended Version)》（寻找一种易于理解的 Raft 算法），InfoQ 有《Raft 一致性算法论文译文》。
13. Raft 与 Paxos 的关系：性能与功能一样，但结构不一样，因此更容易理解、更容易实现。
14. Raft 的四分解：领导选举（Leader Selection）、日志复制（Log Replication）、安全性（Safety）、成员变化（Membership Changes）；对一般人学习曲线更低更平滑。
15. Raft 三态状态机：Leader、Candidate、Follower。Follower 只响应其他服务器请求，若没收到任何信息就成为 Candidate 并开始选举；收到大多数人同意选票的人成为新 Leader。
16. 写路径全流程：选出 Leader 后由它服务客户端请求；每个客户端请求包含一条要被复制状态机执行的指令；Leader 先把指令追加到 log 形成新 entry，再通过 **AppendEntries RPC 并行**发给其他 server；其他 server 没发现问题、复制成功后回一个表示成功的 ACK；Leader 收到**大多数 ACK** 后才应用该日志、返回客户端执行结果；若 Follower 崩溃或丢包，Leader 会**不断重试** AppendEntries RPC。
17. Raft 动画三件套：《Raft – The Secret Lives of Data》《Raft Consensus Algorithm》《Raft Distributed Consensus Algorithm Visualization》。
18. Dynamo 论文《Dynamo: Amazon's Highly Available Key Value Store》：影响力很大；讲 DynamoDB 如何满足高可用、高扩展、高可靠，并展示系统架构如何做到数据分布与数据一致性。
19. 数据分布两派：**GFS 是查表式**的数据分布；**DynamoDB 是计算式**的，具体是"改进版的、通过虚拟结点减少增删结点带来数据迁移的一致性哈希"。
20. Dynamo 的三个机制要点：**NRW 模式**让用户可灵活地在 CAP 系统中选取其中两项；用 **Vector Clock（向量时钟）**检测数据冲突；用 **Handoff 机制**提升可用性。
21. 两个关键概念：Vector Clock 与 Gossip 协议。
22. 逻辑时钟的动因：分布式系统要解决消息有序问题；不同机器有不同本地时间，本地时间同步很难搞，会导致消息乱序。
23. 逻辑时钟的做法：每个系统维护一个本地计数器；每执行一个事件（向网络发送消息、或交付到应用层）就对计数器 **+1**；跨系统时在消息体上附着本地计数器；接收端收到消息时取"对端传来的计数器"与"自己计数器"的**最大值**更新自己的计数器，即调整自己的时钟。
24. 逻辑时钟的能力边界（原文核心判据）：若事件 A 先于事件 B，则 A 的时钟一定小于 B 的时钟；**反过来无法保证**，因为反过来没有因果关系。向量时钟因此能解释因果关系；向量时钟维护数据更新的一组版本号（版本号其实就是使用逻辑时钟）。
25. 向量时钟的具体示例（原文给的完整算例）：数据存在 A、B、C 三个结点 ⇒ 向量维度为 3；初始化时所有结点对该数据的版本是 `[A:0, B:0, C:0]`；从 A 结点更新一次 ⇒ 变成 `[A:1, B:0, C:0]`，再向其他结点复制该版本；语义上表示"当前数据是由 A 更新的"，逻辑上可让数据更新顺序找到相关因果关系。
26. 时钟学习材料：马萨诸塞大学课程《Distributed Operating System》第 10 节《Clock Synchronization》讲议；《Why Vector Clocks are Easy》与《Why Vector Clocks are Hard》。
27. Gossip 的用途与出处：DynamoDB 用它做数据同步；原始论文《Efficient Reconciliation and Flow Control for Anti-Entropy Protocols》；也是 Cassandra 使用的数据复制协议；传播像八卦谣言，"一传十、十传百"。
28. Gossip 的性格：协议看似简单，细节上却非常麻烦。
29. 三种通信方式（原文逐条给定义）：
   - push：A 把 `(key,value,version)` 及对应版本号推给 B，B 更新 A 中比自己新的数据；
   - pull：A 仅把 `key,version` 推给 B，B 把本地比 A 新的 `(key,value,version)` 推给 A，A 更新本地；
   - push/pull：与 pull 类似，只多一步——A 再把本地比 B 新的数据推给 B，B 更新本地。
30. 通信次数的量化对比：把两个节点数据同步一次定义为一个周期，则一个周期内 **push 通信 1 次、pull 通信 2 次、push/pull 通信 3 次**；效果上 push/pull 最好，理论上一个周期内可使两节点完全一致，直观感觉收敛速度也最快。
31. 通信方式 vs 协调机制：push/pull 等是**通信方式**；协调是通信方式之下的**数据交换机制**，即"如何交换数据能达到最快的一致性、消除节点的不一致性"。
32. 协调面临的两个最大问题：① 要找到经济的方式（不可能每次都把一个节点上的数据全发给另一个节点）；② 要考虑容错（网络问题不可达时怎么办）。
33. 两种协调机制对比：**Anti-Entropy**（以固定概率传播）有完备容错性，但需要更多网络与 CPU 资源；**Rumor-Mongering**（仅传播新到达的数据）反过来，不耗资源但容错性难以保证。
34. Anti-Entropy 又分两种：
   - Precise Reconciliation（精确协调）：希望每次通信周期内都非常精确地消除双方不一致，具体表现是互发对方需要更新的数据；因为每个结点都可读写，所以需要**每个数据都独立维护自己的版本号**；
   - Scuttlebutt Reconciliation（整体协调）：不为每个数据维护单独版本号，而是每个节点上的数据统一维护一个版本号（一致的全局版本）；交换时只比较**节点版本**而非数据个体版本，因此更经济；若版本不一样，再做精确协调。
35. Cassandra 的实现定位：基于**整体协调的 push/pull 模式**；可看原始论文、看 Cassandra 源码、到 GitHub 搜其他人的实现；图示化材料可看动画 gossip visualization。
36. Aurora 论文《Amazon Aurora: Design Considerations for High Throughput Cloud –Native Relation Databases》：AWS 把 MySQL 的**计算与存储分离**，计算节点 scale up、存储节点 scale out；把 redo log 独立设计成一个存储服务，把分布式数据方面的东西全部甩给底层存储系统，从而提高整体吞吐量与水平扩展能力。
37. Aurora 的写路径数字：要写 **6 份拷贝**，但只需把一个 Quorum 中的日志写成功即可；把存储服务做成跨数据中心的服务，提高数据库容灾、降低性能影响。
38. Aurora 的核心原理：**latency 一定要低**（写 6 个 copy 开销很大）⇒ 基本用异步模型，然后拼命做并行处理，其中用到 Gossip 协议。
39. Aurora 六步写流程（原文图注）：① 数据在本地落地；② 完成前两步就可以 ACK 回调用方（只要本地落地就返回成功）；③ log 同时发送到 6 个存储结点，只需**大于 4 个**成功 ACK 就算写成功；④ 用 Gossip 协议；⑤ 产生 cache 页便于查询；⑥ 在 S3 做 Snapshot（类似 Checkpoint）。
40. Spanner 论文《Spanner: Google's Globally-Distributed Database》：谷歌全球分布式数据库；扩展性达到全球级——可扩展到**数百万台机器、数以百计的数据中心、上万亿的行**；除扩展性外还能同时通过**同步复制 + 多版本**满足外部一致性，可用性也很好。
41. Spanserver 架构：每个数据中心都有一套 **Colossus**（第二代的 GFS）；每台机器有 **100–1000 个 tablet**（相当于数据库表中的行集，物理存储就是数据文件）；举例：一张表 2000 行、20 个 tablet ⇒ 每个 tablet 100 行。
42. tablet 上层的共识：通过 Paxos 做跨数据中心的分布式一致性数据同步；Paxos 选出一个 replica 做 Leader，**Leader 寿命默认 10s，10s 后重选**；Leader 相当于复制数据的 master，其他 replica 从它复制；**读请求可走任意 replica，写请求只能去 Leader**；这些 replica 统称为一个 **Paxos Group**。
43. Group 之间的数据交互：Google 定义了最小传输复制单元 **directory**——一些有共同前缀的 key 记录，这些 key 也有相同的 replica 配置属性。
44. Spanner 的开源实现两个：CockroachDB（Google 自己的人出来做）、TiDB（国人做的）。
45. 小结（作者判断）：服务调度需要分布式存储系统来支持服务的数据调度；各大公司都在分布式数据库上创新——底层用分布式文件系统做存储引擎、把存储与计算分离、上层用分布式一致性数据同步协议提供高可用高扩展。
46. 明确的趋势判断：过去"分库分表 + 一个数据访问代理服务"的玩法，应该不久就会过时、成为历史；真正的现代化分布式数据存储就是 Aurora 与 Spanner 这样的方式。

### 数字 / 公式 / 阈值
- Paxos 提出 **1990 年**；Paxos Made Moderately Complex **2011 年**发表。
- Gossip 一个周期通信次数：**push 1 次 / pull 2 次 / push/pull 3 次**（push/pull 理论上一周期完全一致）。
- 向量维度 = 副本数（例：3 结点 ⇒ 维度 3，`[A:0,B:0,C:0]` → `[A:1,B:0,C:0]`）。

## 30｜编程范式游记（1）- 起源

### 一句话结论
C 是"高级语言中的汇编语言"，它把底层控制做到极致，却把"通用算法要适配数据类型/数据结构"这个包袱甩给调用者——void* 与宏这两条泛型路子都不安全、都不便宜，**这正是后来所有语言的起点，也是泛型编程的由来**。

### 知识点全清单（A1 零丢失）
1. 写作动机：现在文章和演讲都在谈架构，很少谈编程范式；但这些基础性、本质性的话题非常重要——一方面语言争论里很多人对编程语言认识不深，另一方面通过范式能知道语言发展史、提高编程技能写出更好代码。
2. 系列语言面：C、C++、Python、Java、Scheme、Go、JavaScript、Prolog；读者需对这些主流语言多少有了解，并在一线写代码**大概 5 年以上**才能体会内涵。
3. 系列的四个部分：① 泛型编程（第 1~3 章）：从 C 到 C++ 的泛型编程方法 + 系统总结类型系统与泛型本质；② 函数式编程（第 4~5 章）：函数式技术、思维方式、Python 与 Go 修饰器展示代码扩展能力与函数拼装；③ 面向对象（第 6~8 章）：与"传统编程思想相反"——每个对象都应能接受数据、处理数据并把数据传达给其它对象；含 OOP 优缺点、基于原型的范式、Go 的委托模式；④ 编程本质和逻辑编程（第 9~11 章）：编程的本质是"逻辑部分才真正有意义，控制部分只能影响逻辑部分的效率"，再结合 Prolog 讲逻辑编程，最后总结对比各种范式。
4. 编程范式定义（原文定义）：英语 programming paradigm，"范"即模范之意，"范式"即模式、方法，是**一类典型的编程风格**，指从事软件工程的一类典型风格（可对照"方法学"一词）。
5. 共性目标：语言发展出很多编写方式，但不同方式解决的是同一个问题——**如何写出更为通用、更具可重用性的代码或模块**。
6. 为何从 C 讲起：C 历史悠久，几乎现在所有编程语言都以 C 为基础拓展——C++、Java、C#、Go、Python、PHP、Perl、JavaScript、Lua、Shell；C 问世 **40 多年**仍被广泛使用；但大多数 C Like 语言其实是在**改善 C 语言带来的问题**。
7. C 的七条特性：① 静态弱类型语言，使用变量需声明类型，但类型间可以有隐式转换；② 不同变量类型可用结构体（struct）组合，以此声明新的数据类型；③ 可用 typedef 定义类型别名，达到变量类型的抽象；④ 有结构化程序设计、变量作用域、递归功能的过程式语言；⑤ 传递参数一般以值传递，也可以传递指针；⑥ 通过指针可容易地对内存做低级控制，然而引入非常大的编程复杂度；⑦ 编译预处理让编译更具弹性（比如跨平台）。
8. C 特性的两面：让人在微观层面写出非常精细精确的编程操作，在底层和系统细节上自由、灵活、精准地控制代码；但在**代码组织和功能编程**上就不那么美妙了。
9. swap 例子与"为什么传指针"：不用指针则参数是传值，函数形参是调用实参的一个拷贝，函数里对形参的修改无法影响实参；要达到调用后实参内容交换，必须把实参地址传进来。`void swap(int* x,int* y){int temp=*x; *x=*y; *y=tmp;}`（原文代码如此，`tmp` 应为 `temp`）。
10. int 版 swap 的死穴：只能给 int 用，世界上还有 double、float——"这就是静态语言最糟糕的一个问题"。
11. 数据类型与现实世界的类比（原文核心比喻）：数据类型就像**螺帽**，有多种接口方式（平口、十字、六角等）；**螺丝刀**就像函数，或用来操作这些螺丝的算法/代码；不同类型的螺帽需要我们为之适配一堆不同的螺丝刀；而且它们还有不同尺寸（尺寸代表单字节还是多字节，如整型 int、long，浮点 float、double），复杂度一下提高，最终导致"电工（程序员）"工作时要带一堆工具。
12. 优化过的螺丝刀观察：手柄一样、拧螺丝的动作一样，只是接口不一样；"这密密麻麻的看着有 **40 多种**接口，不知道为什么人类世界要干出这么多的花样"。
13. 抽象的统一结论：无论传统世界还是编程世界，我们都在干一件事——**通过使用一种更为通用的方式（抽象和隔离），让复杂的"世界"变得简单一些**。
14. 抽象的第一步：对 C 这样的类型语言，首当其冲是抽象类型，这就是所谓的**泛型编程**。
15. 类型转换的"一点点泛型"：C 世界里类型还可以转换，编译器会用一切方式做类型转换；有时让编程更方便，也让相近类型做到一点点的泛型。
16. 类型转换的坑（原文算例）：传一个本来是 double 或 long 64 位的数组，强转成 int 会出很多问题，因为**遍历数组的步长不一样了**；`double a[10]` 中 `a[2]` 意味着 `a + sizeof(double)*2`，强转 int 后 `a[2]` 意味着 `a + sizeof(int)*2`；`sizeof(double)=8`、`sizeof(int)=4` ⇒ 访问到不同地址和内存空间，导致严重问题。
17. C 的泛型两条路：基本上就是使用 **void\*** 关键字，或是使用**宏定义**。
18. void* 版 swap 全文：`void swap(void* x, void* y, size_t size){ char tmp[size]; memcpy(tmp,y,size); memcpy(y,x,size); memcpy(x,tmp,size); }`。
19. void* 版的三个重点（原文逐条）：① 函数接口增加 **size 参数**——用了 void* 后类型被"抽象"掉，编译器不能通过类型得到尺寸，需手动加类型长度标识；② 实现改用 **memcpy()**——类型被抽象掉，不能用赋值表达式，且传进来的可能是结构体，要交换复杂类型只能内存复制；③ 增加 **`temp[size]` buffer** 做临时空间存储。三者都增加了编程复杂度，这就是 C 语言类型抽象带来的复杂度提升。
20. void* 的天花板（原文追问）：想交换两个字符串数组、类型是 `char*`，那 x、y 参数是不是要用 `void**`？"这样一来，接口就没法定义了。"
21. 宏版 swap 全文：`#define swap(x,y,size){ char temp[size]; memcpy(temp,&y,size); memcpy(&y,&x,size); memcpy(&x,temp,size); }`。
22. 宏的代价：编译器做字符串替换 ⇒ 代码膨胀 ⇒ 编译出的执行文件比较大；对 swap 这种简单函数，void* 与宏都能达到泛型。
23. 换成 min()/max() 就暴露更多问题：`#define min(x,y) ((x)>(y)?(y):(x))`；最大问题是**可能重复执行**——`min(i++, j++)` 本意比较后累加，因宏替换导致 i 或 j 被累加两次；`min(foo(), bar())` 本意比较两个返回值，替换后 foo() 或 bar() 会被调用两次，"这会带来很多问题"。
24. 对"这种泛型"的定性（原文原话级判断）：太宽松，完全不做类型检查，就是在内存上对拷、直接操作内存，"感觉是不是比较危险，而且就像一个定时炸弹一样，不知道什么时候，在什么条件下就爆炸了"。
25. 两条路共同的接口恶化：无论哪种方式接口都变复杂——都加入了 size；不加入 size 则函数内部要自己检查 size，而 void* 这种地址方式根本没法得到 size。
26. 宏方式的残留优势与残留麻烦：宏不隐藏类型，可用 `sizeof(x)` 得 size；但若类型是 `char*`，`sizeof` 只能得到**指针类型的 size** 而不是值的 size；不同如 double 与 int，该用谁的 size？是否先转型？"这些都是问题"。
27. 归因结论：这种泛型让人**根本没有办法检查传入参数的 size**，只能增加接口复杂度（加 size 参数），把问题**抛给调用者**。
28. search 的 int 版：`int search(int* a,size_t size,int target)`，for 遍历、相等返回下标、否则返回 **-1**。
29. 泛型化 search 需要两项改动：① 接口增加 **element size**（数组里每个元素的 size），遍历时据此正确移动指针到下一个元素；② 增加 **cmpFn**——不同类型比较实现不一样（整型用 `==` 即可；字符串数组要用 strcmp 这类函数；结构体数组如 Account 账号，比较两个数据对象是否一样更复杂），所以必须自定义比较函数。
30. 泛型 search 全文：`int search(void* a,size_t size,void* target,size_t elem_size,int(*cmpFn)(void*,void*))`，循环内 `if (cmpFn((unsigned char*)a + elem_size*i, target)==0) return i;`，否则 -1。
31. 为什么不用 memcmp()（原文明确解释）：如果数组是指针数组，或结构体数组里有指针成员，我们想比较的是**指针指向的内容**而不是指针这个变量；用 memcmp 会比较指针（内存地址）而不是所指的值。
32. 三种调用方比较函数的写法：`int int_cmp(int* x,int* y){ return *x - *y; }`；`int string_cmp(char* x,char* y){ return strcmp(x,y); }`；`typedef struct _account{ char name[10]; char id[20]; } Account;` + `account_cmp` 先比 name 再比 id（`strcmp` 两次，返回值传递）。
33. C 到此的上限：泛型 search 只能用于数组这样的**顺序型数据容器**；若要支持非顺序型（堆、栈、哈希表、树、图），用 C"基本上干不下去了"——数据类型的自适应已把事情搞得很复杂，**数据结构的自适应会把复杂度搞上几个数量级**。
34. 小结四条（以"程序 = 算法 + 数据"为纲）：
    - ① 通用算法要对所处理数据的数据类型做适配；C 只能用 void* 或宏替换，两种方式都导致类型过于宽松并带来很多其它问题；
    - ② 适配数据类型需在泛型中加一个类型的 size，因为我们识别不了被泛型后的数据类型，而 **C 语言没有运行时的类型识别**，只能把这个工作抛给调用泛型算法的程序员；
    - ③ 算法其实是在操作数据结构，数据则放在数据结构中，所以真正的泛型除了适配数据类型还要**适配数据结构**，复杂度急剧上升——容器内存的分配和释放（不同数据体可能有非常不同的模型）、对象之间的复制（还涉及深拷贝还是浅拷贝）；
    - ④ 实现泛型算法时会纠结"哪些抛给调用者、哪些可封装"，如何平衡和选择**并没有定论，也不好解决**。
35. C 的设计目标：提供一种能以简易方式编译、处理低层内存、产生少量机器码、不需要任何运行环境支持便能运行的编程语言；很适合搭配汇编语言使用。
36. C 的四条设计理念（原文列出）：相信程序员；不会阻止程序员做任何底层的事；保持语言的最小和最简的特性；保证 C 语言最快的运行速度，哪怕牺牲移植性。
37. C 的伟大之处：使用 C 的程序员在高级语言特性之上还能简单地做任何底层上的微观控制；"也有人说，C 语言是高级语言中的汇编语言"。
38. C 的短板：以上只针对底层指令控制和过程式编程方式；对更高阶、更抽象的编程模型，C 基于过程和底层的初衷设计方式就成了短板，因为编程世界里更多工作是解决业务上的问题而不是计算机的问题，所以需要更贴近业务、更抽象的语言。
39. 交接：C 并没有解决这些问题，所以才有 C++ 等其他语言（下一篇讲 C++ 如何解决）；C 诞生于 **1972 年**，至今 **45 年**。
40. 范式的定位：编程范式其实就是程序的**指导思想**，也代表这门语言的设计方向；不能说哪种范式更超前，只能说各有千秋。
41. C 的定位细化：C 是过程式语言，优点是底层灵活且高效，特别适合开发运行较快、对系统资源利用率要求较高的程序；但它对我上面抛出的问题后来也没有试图去解决，因为**编程范式的选择基本已经决定了它的"命运"**。

  3. 补 **C 的四条设计理念**（相信程序员/不阻止底层/最小最简/最快哪怕牺牲移植性）作为"范式选择决定语言命运"的证据；补 1972/45 年与"高级语言中的汇编语言"这句钩子。
  4. 若要更完整：`0.13` 末尾"关联"加一条指向 `15.x 语言运行时` 的跨界引用（C 无运行时类型识别 → 泛型只能抛给调用者，正好对上 Go 的 `interface{}` 断言成本）。

## 31｜编程范式游记（2）- 泛型编程
> 源文件 `.tmp-zuoer/txt/31丨编程范式游记（2）-泛型编程.txt`，11337 字

### 一句话结论
C++ 用"类 + 模板 + 虚函数/运行时识别"三招把 C 的泛型难题接了过去，而真正的分水岭是**迭代器把"容器的遍历"标准化成一组最小操作符约定**，于是算法从"操作数组"升级为"操作区间"，再升级为 `reduce`——这一步直接通到函数式编程。

### 知识点全清单（A1 零丢失）
1. 承接：上一篇从 C 讲面向过程范式；C 是语言史重要里程碑，但面向过程的 C 已无法满足更高层次编程需要，于是 C++ 出现。
2. C++ 诞生：**1980 年**，AT&T 贝尔实验室的 **Bjarne Stroustrup** 创建；既全面兼容 C，又巧妙揉和一些面向对象编程理念；"不得不佩服 Stroustrup 的魄力"。
3. 推荐书：《C++ 语言的设计和演化》，作者就是 Stroustrup 本人，系统介绍 C++ 诞生的背景与初衷，可从语言创建者角度了解设计思路与创新之旅；C++ 今天仍有很多争议，可看作者早年酷壳文章《C++ 的坑真的多吗？》。
4. 早期 C++ 的定位：许多工作是对 C 的强化和净化，并把**完全兼容 C 作为强制性要求**——这也是 C++ 复杂晦涩的原因（这点 Java 干得比 C++ 彻底得多）；C89、C99 两个标准中许多改进都是从 C++ 引进的。
5. C++ 对 C 的贡献清单（原文逐条，属"九项改进"）：
   - 用**引用**解决指针的问题；
   - 用 **namespace** 解决名字空间冲突的问题；
   - 通过 **try-catch** 解决"检查返回值编程"的问题；
   - 用 **class** 解决对象的创建、复制、销毁，从而在结构体嵌套时达到**深度复制**的内存安全；
   - 通过**重载操作符**达到操作上的泛型（消除上一篇的 cmpFn；用 `>>` 消除 `printf()` 数据类型不够泛型的问题）；
   - 通过**模板 template + 虚函数的多态 + 运行时识别**达到更高层次的泛型和多态；
   - 用 **RAII、智能指针**解决 C 中因需要释放资源而出现的 ugly 且易错代码；
   - 用 **STL** 解决 C 中算法与数据结构的 N 多种坑。
6. C++ 的范式地位：是**支持编程范式最多**的一门语言；虽解决很多 C 的问题，但作者认为它最大的意义是解决了 C 的**泛型编程**问题——C++ 标准规格说明书里**一半以上**都在说明 STL 的标准规格应该是什么样，说明泛型是重点中的重点。
7. 泛型的理想判据：算法应与数据结构及类型无关；各种特殊数据类型应做好自己分内的工作；算法只关心一个标准的实现。
8. 泛型抽象要回答的核心问题：**如果数据类型符合通用算法，那么对数据类型的最小需求是什么？**
9. C++ 解决泛型的三点：① 通过**类**的方式（让用户自定义类型与内建类型保持一致）；② 通过**模板**达到类型和算法的妥协（模板很好地取代了 C 时代宏定义带来的问题）；③ 通过**虚函数和运行时类型识别**（写出基于抽象接口的泛型）。
10. 良好泛型编程要解决三个泛型问题：算法的泛型、类型的泛型、数据结构（数据容器）的泛型。
11. search 的遍历局限：`for(int i=0;i<len;i++)` 只适用于顺序型结构（array、set、queue、list、link），不适用于非顺序型（hash table、binary tree、graph）；**如果找不到一种泛型的数据结构操作方式（遍历、查找、增加、删除、修改……），任何算法或程序都不可能做到真正意义上的泛型**。
12. search 的返回值局限：整型索引下标对顺序结构没问题，对非顺序结构在语义上就存在问题；在 hash table 中查一个 key 返回"索引下标"没有意义——数据存放位置不顺序，而且容量不够会 rehash 改变位置；更靠谱的是"找到就返回该元素的一个**指针（地址）**"。
13. 解决泛型需动用的两个 C++ 技术：① 用模板抽象类型，写出类型无关的数据结构（容器）；② 用一个**迭代器**遍历或操作容器内元素。
14. C++ 版 search（原文）：`template<typename T,typename Iter> Iter search(Iter pStart,Iter pEnd,T target){ for(Iter p=pStart;p!=pEnd;p++){ if(*p==target) return p; } return NULL; }`。
15. 该版本的五个要点（原文逐条）：① `typename T` 抽象数据结构中存储数据的类型；② `typename Iter` 是不同数据结构需自己实现的"迭代器"，从而抽象掉不同类型的数据结构；③ 遍历用 Iter 的 `++`，这是容器需重载的操作符，操作符重载泛型掉了遍历；④ 入参用 `pStart`/`pEnd` 表示遍历的起止；⑤ 用 `*Iter` 取"指针"内容，也是通过重载 `*` 取值操作符达到的泛型。
16. 为什么用重载操作符而不用 `Iter.Next()`/`Iter.GetValue()`：**为了兼容原有 C 语言的编程习惯**。
17. Iter 的真实身份：实际代码里就是 `vector<int>::iterator` 或 `map<int,string>::iterator` 这样的东西，由相应的数据容器实现和提供。
18. STL `find()` 原文：`template<class InputIterator,class T> InputIterator find(InputIterator first,InputIterator last,const T& val){ while(first!=last){ if(*first==val) return first; ++first; } return last; }`。
19. sum 的 C 版：`long sum(int *a,size_t size){ long result=0; for(int i=0;i<size;i++) result += a[i]; return result; }`。
20. sum 的朴素泛型版：`template<typename T,typename Iter> T sum(Iter pStart,Iter pEnd){ T result=0; for(Iter p=pStart;p!=pEnd;p++) result += *p; return result; }`。
21. 该版的**两个假设就是两个 bug**（原文明确点出）：`T result = 0` 里的 **0 假设了类型是 int**；`T` **假设了从 Iter 中出来的类型是 T**；两者不一致就会导致转型问题，带来"非常 buggy 的代码"。
22. 修复思路：Iter 在调用者那里是具体的 `vector<int>::iterator`，int 已传入 Iter 中；所以定义 result 的类型应从 Iter 中来，这样既能保证类型一致、又不会有转型问题——但这要求"精心地实现一个迭代器"。
23. 精简版迭代器（原文代码结构，语义无问题但省略细节）：`template<class T> class container { public: class iterator { public: typedef iterator self_type; typedef T value_type; typedef T* pointer; typedef T& reference; reference operator*(); pointer operator->(); bool operator==(const self_type&); bool operator!=(const self_type&); self_type operator++(); self_type operator++(int); private: pointer _ptr; }; iterator begin(); iterator end(); };`
24. 迭代器的五个关键点（原文逐条）：① 迭代器需要和一个容器在一起（里面是对该容器的具体实现）；② 需重载操作符——取值 `*`、成员 `->`、比较 `==`/`!=`、遍历 `++` 等；③ 需 typedef 一些类型，如 `value_type`，告诉容器内数据的实际类型；④ 需 `begin()`/`end()` 基本操作；⑤ 内部有 `pointer _ptr` 指向当前数据（**pointer 就是 T\***）。
25. 最终 sum：`template<class Iter> typename Iter::value_type sum(Iter start,Iter end,T init){ typename Iter::value_type result = init; while(start!=end){ result = result + *start; start++; } return result; }`（原文代码中 `T init` 的 T 未声明，属原文笔误，照录）；关键句是 **`typename Iter::value_type result = init`**——"我们解决了所有的问题"；0 的问题算法没法搞定，最好由**用户传入**（即 init）。
26. 调用示例：`container<int> c; container<int>::iterator it = c.begin(); sum(c.begin(), c.end(), 0);`。
27. STL 泛型方法的三件套：泛型的数据容器 + 泛型数据容器的迭代器 + 然后泛型算法就很容易写了。
28. 更高需求案例：`struct Employee { string name; string id; int vacation; double salary; };` + `vector<Employee> staff;`；`sum(staff.begin(),staff.end(),0)` 完全不知道怎么搞——要累加的是 Employee 中的不同字段，**即便重载了 `+` 也不知道要加哪个字段**。
29. 同族需求：求平均值 average、最小值 min、最大值 max、中位数 mean 等，算法写出来基本一样，只是"累加"换成了另一个操作；业务问的是"薪水最高/休假最少/总共休假多少天"，面对这么多需求要更泛型。
30. 更高维度抽象的主张：**算法只管遍历，具体干什么由外面的调用方定义**，这样代码重用度更高；这个版本不该再叫 sum，应叫 **reduce**——把一个数组 reduce 成一个值。
31. reduce 原文：`template<class Iter,class T,class Op> T reduce(Iter start,Iter end,T init,Op op){ T result=init; while(start!=end){ result = op(result,*start); start++; } return result; }`；说明：需传一个函数进来，STL 中是"函数对象"；result 不再是加，而是把整个迭代器值交给 operation。
32. STL 对应函数是 `accumulate()`，有两个版本：版本一 `template<class InputIt,class T> T accumulate(InputIt first,InputIt last,T init){ for(;first!=last;++first) init = init + *first; return init; }`（与上面同构，只是用 for 而非 while）；版本二更抽象 `template<class InputIt,class T,class BinaryOperation> T accumulate(InputIt first,InputIt last,T init,BinaryOperation op){ for(;first!=last;++first) init = op(init,*first); return init; }`——需传"二元操作函数"，**accumulate 的语义比 sum 更抽象**。
33. 使用示例（C++ lambda）：`double sum_salaries = reduce(staff.begin(),staff.end(),0.0,{return s + e.salary;});` `double max_salary = reduce(staff.begin(),staff.end(),0.0,{return s > e.salary ? s : e.salary;});`。
34. reduce 的语义价值：更通用——"具体要干什么样的事情呢？放在匿名函数里面"，它只做 reduce；更抽象地说，把数组/集合变成一个值，怎么变由函数决定。
35. Reduce 组合出更复杂功能：定义函数对象 `counter`，它需要一个 `Cond` 条件判断对象——满足条件加 1，否则加 0：`template<class T,class Cond> struct counter { size_t operator()(size_t c,T t) const { return c + (Cond(t) ? 1 : 0); } };`。
36. 用 counter + reduce 打造 `count_if`（统计满足条件的个数，"就是一行代码的事"）：`template<class Iter,class Cond> size_t count_if(Iter begin,Iter end,Cond c){ return reduce(begin,end,0,counter<Iter::value_type,Cond>(c)); }`。
37. 条件属于**业务逻辑而非流程控制**，应交给使用方；因此统计"薪资超过 1 万元"的员工数只需：`size_t cnt = count_if(staff.begin(),staff.end(),{ return e.salary > 10000; });`。
38. Reduce 的裁剪能力：可以只对结构体中的某些值做 reduce（如只对 `salary>10000` 的人）；"只要传不同的方式给它，你就可以又造出一个新的东西出来"。
39. 通到函数式：函数式编程里可以用很多像 reduce 这样的函数，完成更多像 STL `count_if()` 这样有具体意义的函数。
40. 小结：C++ 通过泛型解决 C 遇到的问题，其中主要是泛型编程与函数式编程的基本方法细节；解决类型问题可能有多种方式，不一定非要 C++ 这条路。
41. 为何仍从 C/C++ 开始：它们比较偏底层，从底层原理上可以更透彻地了解"从 C 到 C++ 演进带来的编程方式变化"，看到静态类型语言解决泛型的技术与方法；**形式是多样的，但是原理是相通的**，这有助于理解后面更多范式。
42. 读者勘误（可作坑）：`counter` 结构体原样跑不通——有读者补了 `Cond cond;` 成员并把 `Cond(t)` 改成 `cond(t)`；另有读者指出"最终泛型 sum 函数貌似缺少相关代码"（原文确实只给了残缺版）。

## 32｜编程范式游记（3）- 类型系统和泛型的本质
> 源文件 `.tmp-zuoer/txt/32丨编程范式游记（3）-类型系统和泛型的本质.txt`，7635 字

### 一句话结论
类型是对**内存布局的抽象**，所以类型系统天然是"安全"与"灵活"的 trade-off；泛型的本质不是语法糖，而是**把类型的内存分配/释放/访问、类型的操作、容器操作、类型特有操作四件事标准化掉**——动态类型没有消除类型系统，只是把检查推迟到运行期。

### 知识点全清单（A1 零丢失）
1. 承接与转折：前两篇讨论 C 到 C++ 的泛型并初探函数式；泛型方式并不只有 C++ 一种，只是借它了解底层静态类型语言的泛型原理。
2. 动态语言/语法糖语言里，swap 或 search 的泛型可以非常简单：`b, a = a, b;`（包括 Go 也有这种语法）。
3. 编程世界必须处理好两件事：① 编程语言中的**类型问题**；② 对真实世界业务代码的**抽象、重用和拼装**。
4. 类型系统定义（原文）：在计算机科学中，类型系统用于定义如何将编程语言中的数值和表达式归类为许多不同的类型，以及如何操作这些类型，还有这些类型如何互相作用；类型可以确认一个值或者一组值具有特定的意义和目的。
5. 两类类型：内建类型（int、float、char 等）与抽象类型（struct、class、function 等）；抽象类型在程序运行中可能不表示为值；类型系统在各语言间差异非常大，**最主要的差异存在于编译时期的语法，以及运行时期的操作实现方式**。
6. 编译器如何用类型：可能使用值的静态类型以最优化所需存储区，并选取数值运算时的最佳算法；例如许多 C 编译器中"浮点数"以 **32 比特**表示、与 **IEEE 754** 规格一致的单精度浮点数，因此 C 在数值运算上应用了浮点数规范（浮点加法、乘法等）。
7. 类型理论的来源：类型的约束程度与评估方法影响语言类型；语言可能就类型多态性对每个类型对应一个针对于该类型的算法运算；类型理论研究类型系统，但实际语言的类型系统起源于计算机架构的实际问题、编译器实现以及语言设计。
8. 类型系统的四项功能（原文四条，每条都带例子）：
   - **程序语言的安全性**：用类型让编译器侦测一些代码错误，例如识别出无效表达式 `"Hello, World" + 3` 这类不同数据类型间操作；强类型语言提供更多安全性，但**并不能保证绝对的安全**；
   - **利于编译器的优化**：静态类型声明让编译器明确程序员意图，从而做很多优化；例如指定类型是 int，编译器就知道该类型会以 **4 个字节的倍数**对齐，可更有效利用更有效率的机器指令；
   - **代码的可读性**：有类型的语言让代码更易读易维护，语义更清楚，代码模块的接口（如函数）更丰富清楚；
   - **抽象化**：允许程序设计者以较高层次方式思考而非烦人的低层次实现；如用整型/浮点型取代底层字节实现、把字符串设计成一个值而不是底层字节数组；高层上类型可定义模块间交互协议（函数入参类型与返回类型），让接口更有语义、模块数据交换更直观易懂。
9. 类型带来的问题：作用于不同类型的代码虽然长得非常相似，却要按类型写不同版本的算法；要做到泛型就得涉及比较底层的玩法。
10. 两类语言划分：静态类型语言（C、C++、Java）与动态类型语言（Python、PHP、JavaScript）。
11. 动态类型示例：`x = 5; x = "hello";`——静态类型语言会在编译期出错；动态类型语言会以"类型标记"维持程序所有数值的标记，并在运算任何数值之前检查标记；变量类型由运行时解释器动态标记，从而可动态对应底层计算机指令或内存布局。
12. JS 异构数组示例：`var a = new Array(); a[0]=2017; a[1]="Hello"; a[2]={name:"Hao Chen"};`——元素可以是各式各样的类型，静态类型语言很难做到；原文注：这其实不是数组而是 key:value（动态语言类型动态，key 与 value 类型都可随意，还可写成 `a["key"]="value"`）。
13. 弱类型/动态类型下的不确定结果（原文三例）：`x=5; y="37"; z=x+y;` → **Visual Basic 得 42**（系统把字符串 "37" 转成数字 37 以匹配运算直觉）；**JavaScript 得 "537"**（把数字 5 转成字符串 "5" 再串接）；**Python 则产生一个运行时错误**。
14. 强/弱类型的判据：静态类型检查在编译器做语义分析时进行；如果一个语言强制实行类型规则（即通常只允许以不丢失信息为前提的自动类型转换），称强类型，反之称弱类型。
15. 动态检查的代价：动态类型检查系统更多在运行时期做动态类型标记和相关检查，所以动态语言必然要给出一堆诸如 `is_array()`、`is_int()`、`is_string()` 或 `typeof()` 这样的运行时类型检查函数。
16. 类型的两面性：类型是对底层内存布局的一个抽象，会让代码关注非业务逻辑的东西；代码又需要在不同类型间做处理；如果类型检查得过于严格，写出来的代码就不能那么随意。
17. 静态语言的"小后门"：类型转换，以及 C++、Java 运行时期的类型测试；小后门也会带来相当讨厌的问题——C 示例 `int x=5; char y[]="37"; char* z = x + y;` 结果可能和你想的完全不一样：由于 C 的底层特性，z 会指向**超过 y 地址 5 个字节**的内存地址，相当于指向 y 字符串指针之后的两个空字符处。
18. 静态派 vs 动态派的争论：前者主张编译时较早发现错误、还可增进运行时期性能；后者主张更动态的类型系统使分析代码更简单、减少出错机会、更轻松快速编写程序，并主张类型推断语言通常不需手动声明类型、额外开销自动降低。
19. 作者的中立判断：前两篇用 C/C++ 做泛型示例，似乎动态类型能较好规避"同逻辑多版本代码"的问题、更关注业务；但要清楚**任何语言都有类型系统**，只是动态语言在运行时做类型检查；动态语言代码复杂度低、更易关注业务，"在某些场景下是对的，但有些情况下却并不见得"。
20. JS 转型函数 ToNumber 全文：`function ToNumber(x){ switch(typeof x){ case "number": return x; case "undefined": return NaN; case "boolean": return x ? 1 : 0; case "string": return Number(x); case "object": return NaN; case "function": return NaN; } }`。
21. 动态语言的普遍现象：代码中大量类似 `typeof` 的类型检查；这是动态类型带来的另一个问题——**运行时识别（比较耗性能）**。
22. 动态语言的真实痛点：代码量一大，"类型问题"引发整个程序出错的情况太多，而且会让整个程序崩溃掉，"太恐怖了"，这时就很希望提前发现类型问题。
23. 争论的收尾（作者判据）：静态派说编译器能帮找问题，动态派说编译器也无法找到所有问题、真正提前发现只能靠测试——"其实他们都对"。
24. 泛型的前提：要了解泛型的本质，就需要了解类型的本质；类型是对内存的一种抽象，**不同的类型会有不同的内存布局和内存分配的策略**；不同的类型有不同的操作，所以对特定类型有特定的一组操作。
25. 做到泛型要做的四件事（原文四条）：
   - 标准化掉类型的内存分配、释放和访问；
   - 标准化掉类型的操作（比如比较操作、I/O 操作、复制操作……）；
   - 标准化掉数据容器的操作（比如查找算法、过滤算法、聚合算法……）；
   - 标准化掉类型上特有的操作（需要有标准化的接口来回调不同类型的具体操作……）。
26. C++ 为达到泛型动用的技术（原文六条，与 31 篇的九项改进互为表里）：通过类中的构造、析构、拷贝构造、重载赋值操作符标准化（隐藏）类型的内存分配/释放/复制；通过重载操作符标准化类型的比较等操作；通过 iostream 标准化类型的输入输出控制；通过模板技术（**包括模板的特化**）为不同类型生成类型专属代码；通过迭代器标准化数据容器的遍历操作；通过面向对象的接口依赖（虚函数技术）标准化特定类型在特定算法上的操作；通过函数式（函数对象）标准化对于不同类型的特定操作。
27. 学习路径价值：通过学习 C++ 可看到一个比较完整的泛型编程所涉及的编程范式，这些范式在其它语言中都会或多或少体现；例如 **JDK 5 引入的泛型类型就源自 C++ 的模板**。
28. 泛型的正式定义（原文引 1985 年论文《Generic Programming》，Musser, David R.; Stepanov, Alexander A.）："Generic programming centers around the idea of abstracting from concrete, efficient algorithms to obtain generic algorithms that can be combined with different data representations to produce a wide variety of useful software."
29. 作者自己的本质概括：**屏蔽掉数据和操作数据的细节，让算法更为通用，让编程者更多地关注算法的结构，而不是在算法中处理不同的数据类型**。
30. 类型系统的起源与负面作用：类型系统出现主要是对容许混乱的操作加上严格限制，避免代码以无效的数据使用方式编译或运行（整数运算不可用于字符串、指针操作不可用于整数等）；但类型的产生和限制虽对底层代码安全，对更高层次的抽象产生了负面因素——C++ 里为同时满足静态类型和抽象，就导致**模板技术出现，带来语言的复杂性**。
31. 语言的根本 trade-off：编程语言本质是帮程序员屏蔽底层机器代码实现、让我们更关注业务逻辑；但作为机器代码与业务逻辑之间的**粘合层**，是"让程序员控制更多底层灵活性"还是"屏蔽底层细节让程序员关注业务"，是很难两全、需要 trade-off 的事。
32. 三种语言的取舍（原文结论句）：C 偏向让程序员控制更多底层细节；Java 和 Python 让程序员更多关注业务功能的实现；**C++ 则是两者都想要，导致语言在设计上非常复杂**。

### 反例 / 坑 / 作者明确反对的做法
- 以为"动态类型就没有类型系统"（只是检查时机从编译期挪到运行期）。
- 把"强类型"与"静态类型"混为一谈（作者在评论区回复读者 lostsquirrel 明确："强类型和动态类型是两码事，前者是判断不同的类型是否可以互转，后者是变量的类型可以动态调整"）。
- 依赖隐式类型转换（VB 42 / JS "537" / Python 报错，同一段代码三种结果）。
- C 里做跨类型指针算术（`char* z = x + y` 直接指到越界 5 字节处）。
- 在动态语言里靠 `typeof`/`is_*` 做类型分派（运行时识别耗性能，且代码量一大就崩）。
- 把泛型当语法糖（本质是四类标准化）；为同时要静态类型与抽象而无节制堆模板（C++ 复杂性的来源）。
