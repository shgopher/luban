## 76｜程序员练级攻略：软件设计
### 一句话结论
软件设计是「品味」问题（Linus 语：程序员高下之分在于品味），而品味 = 一组可命名的判据（编程范式 + 设计原则）+ 反复回炉的实践，不是读一遍书能教会的。

### 知识点全清单
- 范式：①《编程范式游记》11 篇（起源/泛型/类型系统/函数式/修饰器/OO/原型/Go 委托/本质/逻辑/程序世界的范式）；②「六个改变你看法的范式」——默认并发、依赖类型、连接性语言（Forth/cat/joy；concatenation is composition）、声明式、符号式、基于知识；③Peter Van Roy 的语言演进 + 4 种分布式语言（Erlang / E / Distributed Oz / Didactic Oz）；④斯坦福公开课 5 语言（C、C++、并发、Scheme、Python）。
- 通用原则：DRY、KISS、Program to an interface not an implementation、Composition over inheritance、YAGNI、迪米特法则 LoD（1987 年荷兰 Demeter 项目；Craig Larman 称「不要和陌生人说话」；正式表述 4 类可访问对象：O 自身／与 O 直接相关的组件／M 创建或实例化的对象／M 的参数）、高内聚低耦合、CoC、SoC、DbC、ADP。
- SOLID + 两条包原则：SRP / OCP / LSP（"Subtypes must be substitutable for their base types"；代码中不应出现对子类类型的 if/else）/ ISP（电脑接口拆成工作学习、编程开发、上网娱乐、计算数据服务）/ DIP（墙面开关 vs 电灯开关）/ CCP / CRP。
- 好莱坞原则 = "don't call us, we'll call you"：组件被动，初始化与调用归容器 → IoC/DI 的基础（不创建对象，只描述创建方式）。
- SoC 的两种实现手段：**标准化**（造螺丝钉的只管螺丝钉，按标准一定配得上螺帽）、**抽象与包装**（函数 → 类 → 组件/分层/面向服务）。
- DbC 三要素：先验条件（客户义务、供应商权利——所以模块不必处理不满足先验的情况）、后验条件（供应商义务）、不变式（进入时假定、退出时保持）。
- ADP 破环两法：抽公共类到新包 D（C→D、A→D）；或用 DIP + ISP。
- 读物：DDD、UNIX 编程艺术、Clean Architecture、12-Factor、Avoid Over Engineering、Instagram 三法则（用稳定可靠的技术／不重造轮子／keep it simple；Amazon 两条：自动化 + 简化）、Joshua Bloch《How To Design A Good API》、6 份 REST API 规范、The Problem With Logging。

### 数字 / 公式 / 阈值
- LoD 起源 1987 年；SOLID 5 条、GoF 23 个模式；Rails 号称开发效率是 Java 的 10 倍；CCP 让包变大、CRP 让包变小（两者出发点不同但不冲突）。

### 原话（≤2 句）
- "如果你想成为一名优秀的程序员，软件设计定是你的必修课。"／"软件开发是一场 trade-off 的博弈。"

### 反例 / 坑
- 职责过多 → 引起变化的原因变多 → 职责依赖 → 内聚与耦合双输。
- 把功能全声明进抽象类 → 上网本/PC/服务器/笔记本都不得不实现全部接口（ISP 反例）。
- 过度设计 = 把系统带到另一个复杂度上。

### 与 luban 的关系
- 覆盖判定：**部分覆盖** — `0.11` 已讲 SOLID 五条 + KISS + LKP + 组合优于继承（更深，带 Go 落点与 52.7% 实测）；`26.6` 已讲 CCP/CRP/ADP/SDP/SAP + I/A/D 度量；`0.12` 已讲过度设计（信号可量化，强于 Instagram 三法则）；`0.13` 已讲六范式（集合不同但更深，原文的「连接性语言」可判不取）。**书稿没有**：DbC（`契约式设计`/`DbC` 零命中；`前置条件/后置条件` 只在 `需求/1.2` 的用例语境出现）、CoC（`约定优于配置` 零命中）、SoC（`关注点分离` 零命中）。
- 落点建议：①`0.11` 增补「契约式设计 DbC」小节：先验=导出函数校验参数并返 error、不变式=私有字段 + 构造函数守门、后验=测试断言；②`0.11` 增补「CoC 惯例优于配置」一条判据：Go 版惯例是 gofmt/`internal/`/`cmd/`/`_test.go`，判据是「约定省掉几个配置项」；③SoC 只写「标准化 vs 抽象包装」两手段，并进 `26.6` 的切包判据，不新增节。

## 77｜程序员练级攻略：Linux 系统、内存和网络
### 一句话结论
系统底层是唯一能「反哺架构设计」的内功，但学法是先在上层读文档、不要一上来扎内核源码；本篇的价值是一份**已过滤到 30% 的最小索引**，不是教程。

### 知识点全清单
- 高手成长篇 6 大板块：系统底层 / 数据库 / 分布式架构 / 微服务 / 容器化与自动化运维 / 机器学习与 AI / 前端（H5 + JS + React/Vue + 浏览器原理）；末尾是信息源（各大公司技术 Blog、论文集散地）。
- 容器选型判据：只学 Docker + Kubernetes，**不要** Salt / Puppet / Chef / Ansible。理由：自动化部署根本不够，还需要对**环境和运行时**的管理与运维。
- Linux 资源：RHEL 官方文档、Linux Insides（内核如何启动/初始化/管理）、LWN kernel page、Learn Linux Kernel from Android Perspective、Linux Kernel Doc，加 Kernel Planet / IBM 红皮书 / TLK（2.0.33 内核）/ Linux Performance / Dropbox《Optimizing web servers for high throughput and low latency》。
- 内存系列（What every programmer should know about memory）9 部分：①简介 ②CPU caches ③虚拟内存 ④NUMA ⑤cache 优化 ⑥多线程优化 ⑦性能工具 ⑧未来技术 ⑨附录与参考。
- 三篇内存模型论文：①Memory Barriers: a Hardware View for Software Hackers（屏障是程序、编译器、CPU 三者都要遵守的规范；SMP 上还含复杂缓存一致性策略）②ARM/POWER Relaxed Memory Models（为功耗与性能选了比 x86 的 TSO 更宽松的模型）③x86-TSO。
- 三种内存分配器：ptmalloc（glibc）／tcmalloc（Google，Thread-Caching malloc，比 ptmalloc 快两倍以上）／jemalloc（BSD，可并行；论文 A Scalable Concurrent malloc(3) Implementation for FreeBSD）。工程案例：jemalloc 可扩展分配、Python+Celery 用 jemalloc 省 40% 内存。
- 网络学习：教材自下而上 6 层（物理层/数据链路层/介质访问控制层/网络层/传输层/应用层）；读 RFC 的双重收益——学技术 + 学「好的技术文档怎么写」。
- Linux 网络调优：iproute2 + 流量整形 + netfilter 的 HOWTO、RHEL Network Performance Tuning Guide、PackageCloud 的收包/发包两篇内核栈分析、Awesome Pcap Tools。

### 数字 / 公式 / 阈值
- 只保留 30% 最经济的信息；日进一步 **3-5 年**甩开多数人；tcmalloc 比 ptmalloc **快 2 倍以上**；jemalloc 省 **40%** RAM；内存系列 **9** 部分；网络教材 **6** 层；HTTP/2 于 **2015** 年批准；RFC 2616 是 **1999 年 6 月**，2014 年后被 7230–7235 取代；TLK 讲的是 **2.0.33** 内核。

### 原话（≤2 句）
- "你千万不要一下子扎到源代码里去，那样没用——你还是要在上层先通过读一些不错的文档来学习。"
- "绝大多数人是坚持不下来的。"

### 反例 / 坑
- 一上来就啃内核源码（没上层模型打底，读不出东西）。
- 把「收藏了书单」当成「学会了」；只读不实践。
- 只学 Ansible/Chef 一类配置管理工具，不学运行时的管理（作者的明确取舍）。

### 与 luban 的关系
- 覆盖判定：**部分覆盖** — `8.1/8.2`（TCP、拥塞控制）、`8.5`（HTTP/1.1→2→3 + HPACK）、`11.6`（cache line/伪共享/NUMA，带延迟表）、`11.11`（包内核路径）都比原文深，RFC 逐条清单与 2018 年的书单**判不取**（纯索引、时效强）。**书稿没有**：C 侧分配器三家对比（`15.3` 只提「TCMalloc 式三级结构」，无 ptmalloc/tcmalloc/jemalloc 取舍）、x86-TSO 与 ARM/POWER 松弛模型（`内存屏障` 仅 2 处旁及）。

## 78｜程序员练级攻略：异步 I/O 模型和 Lock-Free 编程
### 一句话结论
I/O 模型与无锁编程是「所有程序员必学」的方法论，且其设计模式可以直接搬到分布式架构；但本篇仍只是路线图——真正的判据是**演进链每一步被什么问题逼出来**，以及**锁的代价大到什么程度才值得上无锁**。

### 知识点全清单
- 五种 I/O 模型（Stevens《UNIX 网络编程》6.2）：阻塞、非阻塞、I/O 多路复用（select/poll）、信号驱动（SIGIO）、异步（POSIX aio_functions）。
- 演进链（原文唯一的技术判断）：**select → poll → epoll → aio → libevent → libuv**；作者观点：Unix/Linux 走了几十年这些变迁，都不如 Windows **I/O Completion Port** 设计得好（原文自标「纯属个人观点」）。
- 事件驱动的问题线：C10K 已读过 → 本篇推向 C10M（"The Secret To 10 Million Concurrent Connections — The Kernel Is The Problem, Not The Solution"）。
- Reactor 模式 = 读完各种实现后的共同抽象（原文给 3 篇「读这三篇就够了」）；反例三篇：Select is fundamentally broken、Epoll is fundamentally broken 1/2 与 2/2。
- Lock-Free：动因是**锁对性能影响太大**；三个必读概念词条 Non-blocking algorithm / Read-copy-update / Seqlock；McKenney《Is Parallel Programming Hard, And, If So, What Can You Do About It?》号称并行编程经典。
- 无锁队列两篇论文：Implementing Lock-Free Queues（作者自译《无锁队列的实现》）、Simple, Fast, and Practical Non-Blocking and Blocking Concurrent Queue Algorithms（同时给阻塞与非阻塞版本）。
- 库生态：Boost.Lockfree、ConcurrencyKit、Folly（MPMC 队列）、Junction、MPMCQueue（多生产者-多消费者，有界）、SPSCQueue（单生产者-单消费者，无等待）、Seqlock、Userspace RCU(liburcu)、libcds、liblfds。
- 事务内存（TM）：用 STAMP 基准评估；HTM 见于 IBM Blue Gene/Q 与 Intel Haswell；结论是限制来自「写基准用的编程模型与数据结构」，换对了模型可有 10 多倍提升。
- 其它：64 位编程（28 节课程合集）、OpenSSL 性能、压缩（eBay 购物车用压缩解网络 I/O 瓶颈；LinkedIn 2017 用 Brotli 换 gzip）、SSD 性能测试、Butler Lampson《Hints for Computer System Design》、Jim Gray 的 5 分钟法则与 5 字节法则。

### 数字 / 公式 / 阈值
- 5 分钟法则：内存 vs 磁盘的权衡；5 字节法则：内存 vs CPU 的权衡（Jim Gray & Franco Putzolu，**1986**）；**1997** Gray & Graefe 重审；**2009**《The Five-Minute Rule 20 Years Later (and How Flash Memory Changes the Rules)》因闪存改写规则。
- TM 实测：Blue Gene/Q **64 线程**，HTM 中值加速 **1.4×**、STM **4.1×**。
- 64 位编程合集含 **28** 节课程。

### 原话（≤2 句）
- "如果想开发出一个高性能的程序，你就非常有必要学习 Lock-Free 的编程方式。"
- "Unix/Linux 用了好几十年走过这些技术的变迁，然而，都不如 Windows I/O Completion Port 设计得好。"

### 反例 / 坑
- 把 epoll 当异步 I/O（原文未展开，但演进链把 aio 单列，说明二者不同层）。
- 无脑上无锁：锁的代价大是动机，不是「无锁一定快」的证明（原文未给对比数据，属**原文未展开**）。
- 只读论文不动手：本篇所有条目都是资料，没有一行代码。

### 与 luban 的关系
- 覆盖判定：**已覆盖（客场引用）** — `11.3` 五种模型（并点明前四种的拷贝仍同步、真异步是 io_uring）、`11.4` select/poll 三瓶颈 + epoll 三件套 + 「epoll 不是异步」+ 单实例锁竞争（对应 Epoll is broken）、`11.8` PPC/TPC/Reactor/Proactor + 三种 Reactor + 创建成本实测、`11.5` 零拷贝，全部比原文深。**书稿零命中**：libevent/libuv、HTM/STM、5 分钟法则。
- 落点建议：①`11.8` 在 Reactor 演进链后补一行「库的分层」：epoll 是接口、libevent/libuv 是把 epoll/kqueue/IOCP 抹平成跨平台事件循环的**库**（Go 的 netpoller 是自己实现这一层，见 `15.11`）；②`41.5` 或 `10.3` 增补「5 分钟法则/5 字节法则」作为缓存与存储分层的**定量判据**（页访问间隔 > 5 分钟就不值得常驻内存），并注明闪存时代需重算；③C/C++ 无锁库清单**不取**：Go 侧对应物是 channel/atomic（`15.6` 已覆盖），列库只会变成无效索引。

## 79｜程序员练级攻略：Java 底层知识
### 一句话结论
Java 最「黑科技」的玩法是字节码编程——运行时改字节码做**无侵入**的监控与代码注入（Java Agent + Instrumentation API），而 JVM 的规范、内存模型与 GC 是该路的必修底子。

### 知识点全清单
- 字节码入门 3 篇（Java Zone: Introduction to Java Bytecode、IBM DeveloperWorks: Java bytecode、以及系列文章）；结论：**Java 字节码相当于汇编**。
- 三个生成/修改库：asmtools（生产环境 .class 工具）、Byte Buddy（运行时创建 Class，无需编译器；2015 年获 Oracle "Duke's Choice" 奖）、Jitescript（同类 BiteScript 系）；一般不直接用 JVMTI。
- 最高级玩法：运行时字节码修改与代码注入 → 不埋点就注入监控代码 → 业务逻辑与代码控制分离（呼应《编程范式游记》）。
- Java Agent：基于 **Java Instrumentation API**，实现 `premain()`（原文比喻：一个比 `main()` 还要超前执行的 main 函数），打包成 jar，`java -javaagent:yourAgent.jar -jar App.jar` 引入。
- JVM：Java 8 虚拟机规范（系统了解 JVM 的最佳文档）、JVM Anatomy Park 系列、JSR 133（Java 内存模型）、William Pugh 的 JMM 文献集、Doug Lea 的两篇内存文章。
- GC：The Garbage Collection Handbook（原理/设计/算法，难啃）、Garbage Collection Tuning Guide（HotSpot 调优，给「只想调优」的人）。
- 内存序：The JSR-133 Cookbook for Compiler Writers（多处理器下 volatile 与读写屏障怎么实现）、Using JDK 9 Memory Order Modes（VarHandle 的 plain / opaque / release-acquire / volatile 四种共享内存访问模式）。
- 性能：Quick Tips for Fast Code on the JVM。

### 数字 / 公式 / 阈值
- 字节码入门 **3** 篇、生成库 **3** 个；Byte Buddy 获奖年份 **2015**；GC Handbook 豆瓣 **9.9** 分（评价人数不多）；**4** 种内存访问模式（plain/opaque/release-acquire/volatile）；规范版本 **Java SE 8**。

### 原话（≤2 句）
- "Java 的字节码相当于汇编。"
- "一个比 main() 函数还要超前执行的 main 函数。"

### 反例 / 坑
- 直接用 JVMTI 手写字节码操作（应改用高层库）。
- 读《垃圾回收算法手册》中文版（原文：翻译得很一般，有人说很烂）——应读英文版。
- 动态生成的代码用 IDE 调试很费劲（留言区共同痛点，作者未给方案，属**原文未展开**）。

### 与 luban 的关系
- 覆盖判定：**缺失，但判「不取」** — `字节码`/`Java Agent`/`premain`/`JSR-133`/`Byte Buddy` 在 `v2/` 均 0 命中（`0.13`/`0.14`/`11.7` 出现「字节码」只是词面）。不取的三条理由：①Go 没有字节码、没有 `premain`，运行时注入这套机制**无处落地**；②Go 侧的同构答案是**编译期代码生成 + eBPF**（`11.7` 已讲，且是内核态、零侵入、无需重启，更强）；③JVM 的内存模型与 GC 在书里已有 Go 口径的更贴主线版本（`15.3` 逃逸分析、`15.4` GC 调优、`15.6` Go 1.19 内存模型），再写 Java 版只是重复。
- 落点建议：①不新增节；②只在 `11.7` 加一句对照：「无侵入监控的两条路——内核态 eBPF（通用）／运行时字节码注入（仅 JVM 系）」，让读者知道此路存在且为何不走；③若将来要写「多语言运行时对照」，可把 VarHandle 四种内存序作为 `15.6` 的**客场引用**一句话，不展开。

## 80｜程序员练级攻略：数据库
### 一句话结论
数据库是**程序员/架构师自己的事，不是 DBA 的事**；学习重点只有两条线——以 MySQL 为代表的关系型（索引 + 复制 + 高可用 + 分片）与以 NoSQL 为代表的非关系型（因 Schema 多样与 ACID 拖累扩展而生）。

### 知识点全清单
- 两大方向：SQL 关系型（代表 Oracle、MySQL、Postgres；另有 SQL Server、DB2）与 NoSQL；本篇只深谈 MySQL。
- **NoSQL 的两个原始动因**：①数据的 Schema 非常多，用关系模型表达不同 Schema 非常笨拙 → 于是分出时序型/键值对型/搜索型/文档型/图结构型；②ACID 是件很讨厌的事，极大影响性能与扩展性 → NoSQL 在此妥协以换取大规模伸缩。
- 责任判据：程序要与数据打交道，架构师不仅要设计数据模型，还要保证整体系统的稳定性和可用性，**数据是关键中的关键**。
- MySQL 路径：官方手册 → 官方 PPT（查询分析与调优、Tuning 101、Performance Schema & Sys Schema、Demystified Tuning、安全、Cluster 部署、InnoDB Cluster 高可用）→ 分支 Percona/MariaDB（各自的 Resources 与 Blog）→《高性能 MySQL》→《MySQL 技术内幕：InnoDB》+ MySQL Internals Manual。
- 索引：《数据库的索引设计与优化》——虽不讲 MySQL 但原理相通，**对索引性能有清楚的估算**，不像其它书只有模糊描述；作者强调索引技术不只用于数据库，**系统架构与分布式架构同样要用**（如分片键、二级索引）。
- 高可用与复制实践：Pinterest 的 MySQL 分片、Booking.com 的 MySQL 设计演化、Airbnb 财务报告扩展、Uber 从 Postgres 转 MySQL、freno 缓解复制延迟、Booking 的并行复制系列（含 Slave Group Commit）。
