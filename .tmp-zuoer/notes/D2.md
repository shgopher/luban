## 81｜程序员练级攻略：分布式架构入门
> 源 `.tmp-zuoer/txt/81丨程序员练级攻略：分布式架构入门.txt`，17,735 B

### 一句话结论
分布式系统的复杂度不在"技术多"，而在"错误是常态"——所以八条进领域须知里，前三条就是成本与心态，而 P90、自动化运维平台是这套认知的工程落点。

### 知识点全清单
- 六个调度域：①服务调度（服务发现 / 配置管理 / 弹性伸缩 / 故障恢复）②资源调度（计算 / 网络 / 存储）③流量调度（路由 / 负载均衡 / 流控 / 熔断）④数据调度（复本 / 一致性 / 分布式事务 / 分库分表）⑤容错处理（隔离 / 幂等 / 重试 / 业务补偿 / 异步 / 降级）⑥自动化运维（持续集成 / 持续部署 / 全栈监控 / 调用链跟踪）
- 入门三件套：Scalable Web Architecture and Distributed Systems、Scalability/Availability/Stability Patterns（PPT）、GitHub《System Design Primer》（CAP / 一致性模型 / 可用性模式 / DNS / CDN / 负载均衡 / 反向代理 / 服务发现 / RDBMS 与 NoSQL / 缓存 / 异步通讯 / 安全）
- 八条"进领域须知"：①把处理错误的代码当正常功能代码写 ②自研健壮分布式成本是单体几百倍甚至几万倍，需要能力很强的开发者 ③健壮的开源分布式系统"基本没有"，用就得 hold 住源码 ④协调多服务/多机器极难，要去读大量论文 ⑤debug 极难，需要好监控跟踪 + 经常演练测试 ⑥要更科学地分析和统计，用 P90 这类指标而非平均值，还要做容量计划 ⑦需要应用服务化，要有 SOA 或微服务框架 ⑧故障不可怕，影响面过大、时间过长才可怕 → 要花时间做自动化运维平台
- 拜占庭：Lamport 1982 提出的虚构模型（多位将军靠信使传令、其中可能有叛徒向不同将军报不同消息）；N ≥ 3F+1 时才有解，即 BFT；PBFT（Castro & Liskov 1999）是第一个广泛应用的 BFT，2/3 节点正常即可保证一致性，三阶段：预准备 Pre-Prepare / 准备 Prepare / 提交 Commit（本节后述三大理论：CAP / FLP / DLS）
- CAP 正解：P 是必选项，"三选二"于是退化成 C/A 二选一——但这是强一致性的口径；现实中 P 很少遇到，C 与 A 都有程度分级，放宽约束可兼顾，可在时间允许范围内交替取舍，不是非此即彼；CAP 与 scalability 无关，分片与非分片系统都适用
- FLP：异步环境 + 网络延迟无上限 + 一个恶意节点 ⇒ 没有算法能在有限时间内达成共识；出路是 Las Vegas（"撞大运"）算法，每轮有一定机率达成、随时间趋近 1，如随机快排随机选 pivot 但结果永远正确
- DLS 容错上限三档：部分同步（延迟有上界但事先未知）≤ 1/3 拜占庭故障；异步环境下确定性协议 0 容忍，但随机化算法可容忍 1/3；同步环境（上界已知）可容忍 100% 拜占庭故障，但当恶意节点 > 1/2 时有限制条件；以上均针对"认证拜占庭（authenticated Byzantine）"——即把公私钥机制用进算法
- 8 条荒谬的分布式假设：网络稳定 / 延迟为零 / 带宽无穷 / 网络安全 / 拓扑不变 / 只有一个系统管理员 / 传输数据成本为零 / 整个网络同构（Arnon Rotem-Gal-Oz 长文解释；Gareth Wilson 用生活例子解释）
- 一致性四篇：CAP Twelve Years Later（2012，最大问题是 P）、Harvest & Yield and Scalable Tolerant Systems、BASE: An Acid Alternative（eBay 架构师 2008 ACM）、Eventually Consistent（AWS CTO Werner Vogels 2008 ACM Queue，NoSQL 理论基石）

### 数字 / 公式 / 阈值
- 拜占庭可解条件 **N ≥ 3F + 1**；PBFT 正常节点 **2/3**；三阶段：Pre-Prepare / Prepare / Commit
- DLS 三档容错上限：部分同步 **1/3**、异步确定性 **0**、同步 **100%**（恶意 > **1/2** 时受限）
- 自研成本：健壮分布式 ≈ 单体 × **几百倍 ~ 几万倍**
- 入门资源覆盖度：足够世上 **90% 以上公司**用，只有超级巨型公司才需更高层技术
- 统计口径：用 **P90**，不用平均值；另需容量计划
- 年份：拜占庭 1982、PBFT 1999、CAP 12 年后 2012、BASE 2008、Vogels 2008
- ⚠️ 本讲**未给**服务拆分 / 微服务化的任何量化判据（那是书稿 30.2 的增量，不在本讲）

### 原话（≤2 句）
- "在分布式环境下，故障不可怕，可怕的是影响面过大，时间过长。"
- "分布式系统之所以复杂，就是因为它太容易出错了。这意味着，你要把处理错误的代码当成正常功能的代码来处理。"

### 反例 / 坑
- 把 CAP 当"三选二"选择题、以为 P 可选 → 误读；把 C/A 看成非此即彼 → 误读
- 用平均值做容量与 SLA 判断（长尾被抹平）
- 指望开源分布式系统拿来即用（"非常健壮的开源分布式系统并不多，或者说基本没有"）
- 把优化重点放在"避免故障"而非"缩小影响面/缩短时长"
