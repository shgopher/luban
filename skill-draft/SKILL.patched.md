# 鲁班写作法（Luban Writing Method）

> **一句话**：把「知识 / 概念 / 主题」写成**可扫读、可自测、信息零丢失**的技术讲解。
> 单篇按此法写；多篇按「铁律 6」拼——**先读目录，主场讲透，客场只引用**。
> 命名寓意：像鲁班做木工一样，每一处都有章法，宁可慢，不出废料。

- `references/example-testing.md` —— 演示：多概念对比表、Go 代码、反模式表、自检题（测试金字塔 / 单元测试 / 集成测试）
- `references/example-release-strategy.md` —— 演示：四方案对比、决策表、铁律、自检题（滚动 / 蓝绿 / 金丝雀）
- `references/cross-refs.md` —— 跨篇协作详解：判主场、切边界、层间分工、接缝、反模式、自检题（摘要不够时读）
- `scripts/make-index.py` —— 抽每节「一句话」+ 引用图：辅助读目录后的筛选与下游查询
- `scripts/linkify-refs.py` —— 把「编号 + 标题」批量转成相对路径链接（跑完再校验）
- `scripts/check-refs.py` —— 全书引用校验器：死链 / 裸编号 / 方向代词 / 悬空 / 编号错配，交付前必跑

## 一、六条铁律（按优先级，不可违反）

1. **知识零丢失。** 原文中每个知识点都必须出现：定义、原理、步骤、数字、优缺点、适用场景、结论、坑。**删的是水，不是肉。**
2. **先结论，后论证。** 读者扫读只靠加粗和表格，也能拿走 80% 信息。
3. **讲得比原文更清楚，而不是更短。** 原文啰嗦就合并；原文没讲透就补一句"本质上就是……"——但**不得编造原文没有的事实、数据、结论**。
4. **数字说话。** 禁用"更好 / 更快 / 更优 / 非常重要"这类无信息量的词。要么给比例、给时长、给阈值，要么删掉。
5. **原汁原味的类比要保留。** 类比是记忆钩子（"掐指一算""大禹治水""国不可一日无君"），但要转述得更利落，不硬凑谐音梗。
6. **全书一体化：先读目录，再动笔；主场讲透，客场只给结论 + 编号。** 同一知识点全书只设一个主场。目录必读（10k，占全书 4.7%），正文只精读相关的那几篇——**读什么由目录定，读多深由一句话定**。铁律 1 管「不掉肉」（相对原文），本条管「不重复」（相对全书）——**零丢失 ≠ 到处重复**。

## 二、全书视角：定位与跨篇协作

> **一句话**：单篇是构件，引用是榫卯——动笔前**读全目录**、只精读相关的那几篇；主场讲透，客场只给结论 + 编号，500 节才像一件家具，而不是一堆木料。

### 为什么这条要单独立成铁律（来自本书的实测）

书的规模一旦超过「一个人一次能看完」，**文笔就不再是瓶颈，结构才是**。本书 v2 现状：目录 11 篇 / 83 章 / 524 节，已有正文 38 节（覆盖率 7.3%），31.0 万字，平均 8,166 字/节。

| 病 | 实测证据 | 后果 |
|---|---|---|
| **悬空是主态** | 56 条引用边里 23 条（41%）指向未写的节，涉及 20 个目标 | 按图索骥落空；不标「待补」，读者以为已经写完 |
| **引用缺标题** | 67 处引用里 46 处（69%）是括号式 `(24.6)`，只给编号 | 读者要翻目录才知道是什么；脚本也验不了标题 |
| **孤岛** | 5 节出入皆 0：1.2、4.1、26.2、53.2、53.3 | 从别处永远到不了：53.1 讲了金字塔三层，却没链 53.2 单元测试、53.3 集成测试 |
| **双向缺失** | 56 条边里只有 3 对互引（6 条，11%） | 被引方不知道谁依赖它，改结构时踩空 |
| **主场重叠** | 「幂等」25.4 三十五处 / 24.4 二十二处 = 1.6 : 1（分工线 3 : 1） | 两篇各讲一版，读的人不知道信谁 |
| **编号错配** | 40.1 写「见 26.3 依赖倒置」，而依赖倒置是 26.2、26.3 是整洁架构 | 比断链更毒：读者跳过去也能读，只是读错了那一节 |

密度也不够：**1.47 处引用/节**，目标是 3–8 处（差 2–5 倍）。这六条没有一条是「文笔」问题——单篇 95 分，全书可能是 60 分。

### 榫卯模型：把「关联」拆成四个可检查的部位

鲁班做家具不用钉子，靠榫卯：每个构件自己成形，接缝处一凸一凹，对不上就装不起来。

| 榫卯部位 | 写作对应 | 做错的后果 |
|---|---|---|
| **榫头（凸）** | 主场给出的可复述结论 + 编号 | 结论含糊 → 别处无从引用 → 只能就地重讲 |
| **榫眼（凹）** | 客场预留的引用位（编号 + 标题） | 没留引用位 → 复述 → 长出第二个主场 |
| **划线定位** | 动笔前读全目录，确认本节坐标 | 位置错，读者跳转落空 |
| **公差** | 编号 / 标题 / 术语全书一致 | 差 0.5mm 还硬敲，构件就裂 |

> 🔑 **铁律 6：先读目录，再动笔；一篇只讲一层，全书只讲一遍。** 同一知识点全书只设一个主场；客场只给一句自足的结论 + 编号。

它和铁律 1 不冲突，管的是两头：**铁律 1 管「不掉肉」（相对原文），铁律 6 管「不重复」（相对全书）。** 丢失和重复是同一个病的左右两端——都是「信息没被有效组织」。

### 第一步：先读全文目录，再挑相关的读

目录是全书唯一权威的地图，**必读，不省这个钱**：14,754 字 ≈ 10.3k token，只占全书正文（22 万 token）的 4.7%。省它省不下多少，漏掉它的代价是撞车返工。

真正贵的是**正文**：31 万字 ≈ 22 万 token，绝不能通读。所以顺序是四步：**目录全读 → 圈出相关 → 逐篇筛选 → 只精读几篇**。

| 步 | 做什么 | 成本 |
|---|---|---|
| ① **读目录** | 从头到尾看一遍全文目录（篇 → 章 → 节），在脑子里建地图 | 10.3k |
| ② **圈相关** | 边看边标：哪些节与这次要写的东西有关（含兄弟节、上下游、可能重复的） | 0 |
| ③ **筛选** | 每个候选先看它的「一句话」，决定要不要精读 | ~0.4k |
| ④ **精读** | 只对真正相关的 1–3 篇读全文 | 5.7k/篇 |

> 🔑 **目录必读，正文精读。「读什么」由目录决定，「读多深」由一句话决定。**

**每篇成本（实测口径）**：

| 读法 | 每篇 token | 相对基线 |
|---|---|---|
| 基线：只读素材，不看目录 | 13.5k | — |
| **目录 + 精读 1 篇相关** | 26.3k | **+94%** |
| 目录 + 精读 3 篇相关 | 37.8k | +179% |
| 目录 + 通读全书正文 | 237k | +1655% |

**目录成本可以按会话摊薄**：一次会话连写 5 节，目录只读一次，摊到每节 2.1k，总增量降到 **+33%**。所以能连着写的别拆成五次会话。

**脚本的定位：辅助读目录，不替代读目录。**

```bash
python3 scripts/make-index.py .                    # 建索引：把每节「一句话」抽出来，供 ③④ 用
python3 scripts/make-index.py . -q 幂等 去重         # ③ 筛选：一次看多节的一句话，顺带兜同义词
python3 scripts/make-index.py . -d 24.6            # 查下游：谁引用了我（入度只能算，看不出来）
python3 scripts/check-refs.py . --quiet            # 收尾校验：悬空 / 裸编号 / 方向代词 / 编号错配
```

用它，是因为三件目录做不到的事：

1. **标题看不出内容**：「优化手段」这名字看不出里面有没有讲缓存，得看一句话；
2. **同义词兜底**：目录里搜「缓存」不会命中「L1/L2」，一句话检索能兜住；
3. **入度和校验**：谁引用了我、引用是否可达，只能靠脚本算。

> ⚠️ 但**不要用 `-q` 代替读目录**。grep 只找得到你想到的词；目录能让你看到你没想到的节——这是它在全书层面唯一不可替代的价值，也是它必须每篇都读的原因。

> ⚠️ **一次性生成、每次只读骨架之外的东西**：索引文件不要 `cat`（524 节 ≈ 5 万 token）。查一次只付命中那几行。

> ⚠️ 唯一不能省的手工动作：**目录先行**。概念在目录里找不到主场时，先补目录条目再写正文——这一步决定「这本书该讲什么」。

### 引用：跨篇指向怎么写

#### 四类关系，各有位置

引用不是「相关阅读」，是有方向的依赖。

| 关系 | 语义 | 写法 | 放哪 |
|---|---|---|---|
| **前置** upstream | 不读它读不懂我 | `见 [24.6 本地消息表](…)` | 概念首次出现处 |
| **并列** sibling | 同一问题的另一解，要选型 | 对比表末列 `详见 24.4` | 对比表 / 决策表下 |
| **下游** downstream | 我的结论被谁消费 | `### 关联` 块 | 文末、自检前 |
| **修正** supersede | 我取代它，或它取代我 | 「本篇取代 44.3 的做法：……」 | 开头第二段 |

**修正关系最难写，也最不能省**：两篇讲同一件事而结论相反，读者会各信一半。显式写清「谁取代谁、为什么」，冲突才变成演进。

#### 三种合法形态（都带链接）

| 形态 | 例 | 用在哪 |
|---|---|---|
| **行内引用** | `见 [24.6 本地消息表](../../L1-分布式原理/24-分布式事务/24.6-本地消息表.md)` | 正文提到别节结论 |
| **括号引用** | `（[34.4 优化手段](34.4-优化手段.md)）` | 表格单元格、句子尾巴 |
| **前文已说标题** | `本地消息表（[24.6](24.6-本地消息表.md)）` | 链接文字只留编号，避免「本地消息表（24.6 本地消息表）」 |

链接文字用**短标题**（去掉括号注解，≤ 12 字），别把整句标题塞进去。

#### 一条特殊形态：指向还没写的节

目录 524 节、正文 38 节，引用跑在正文前面是常态。没有文件就没有链接：

| 做法 | 判定 |
|---|---|
| `见 44.8 索引原理（待补）` | ✅ 节还没写，标待补；写完补链接 |
| `见 [44.8 索引原理](44.8-索引原理.md)` 但文件不存在 | ❌ 死链，比没链接更糟 |

#### 五条禁止

| ❌ 禁止 | 原因 |
|---|---|
| `详见上文` `见前文` `后面会讲` `前文提到` | 无编号 → 不可定位；导出 PDF、打印、单页分享时全部失效 |
| `见 24.6`（裸编号） | 读者要先翻目录才知道 24.6 是什么 |
| **有标题没链接**（`(34.4 优化手段)`） | 站点里点不动，读者只能手工翻目录——这等于没做协作 |
| 标题与目录不一致（`见 26.3 依赖倒置`） | 标题是接口签名；改了名却不全局替换，读者跳到「整洁架构」才发现不对 |
| 一页 8 个长链接（链接文字超过 12 字） | 链接变噪音，打断阅读——用短标题 |

> ⚠️ **密度：每节 3–8 处引用**（按 8,166 字/节 ≈ 每 1000–2700 字一处）。现状 1.47 处/节，差 2–5 倍。超过 10 处通常暴露两件事：要么在替别人写主场，要么这节该拆成两节。

> 🔑 **引用必须自带结论。** 只写「详见 25.4」，读者跳过去才发现讲的是通用幂等、对不上 TCC 的语境——这叫踢皮球。正确写法是「Confirm 重复到达时必须幂等（判据：`affected rows = 0` 且返回成功），通用设计见 25.4」。

#### 悬空引用：引用一个还没写的节

目录 524 节、正文 38 节，**引用跑在正文前面是常态，不是错误**（现在 23/56 = 41% 的引用边指向未写的节）。但悬空必须标记：

| 做法 | 判定 |
|---|---|
| `见 44.8 索引原理（待补）` | ✅ 编号 + 标题 + 待补标记 |
| `见 44.8 索引原理，按 range 分片，路由表放配置中心` | ❌ 替未写的节下结论 |
| 因为没写就不引用，自己讲一段 | ❌ 制造第二个主场 |
| `见 44.99 分库分表` | ❌ 目录里没有这个编号，纯笔误 |

规则：**可以引用不存在的节，不可以替它下结论。** 你替它写的那一句，将来要么被推翻（返工），要么把它锁死（写不出更好的）。

### 索引：目录就是全书的接口定义

#### 编号 / 标题 / 正文，等价于 ID / 签名 / 实现

| 目录部件 | 等价于 | 改动代价 |
|---|---|---|
| 编号 `24.6` | 全局唯一 ID | 改编号 = 断掉所有引用（**禁止改、禁止重排**） |
| 标题「本地消息表」 | 接口签名 | 改标题 = 所有引用里的标题过期（必须全局替换） |
| 正文 | 实现 | 随便改，引用不受影响 |
| 一句话 | 函数注释 | 被别节直接摘录（这是它被写成一句话的原因） |

> ⚠️ **编号只能废弃，不能复用。** 弃用 44.3 时保留编号 + 一句「44.3 已并入 44.8」，否则旧引用会指到一篇新内容上——**断链读者能发现，指错读者发现不了**，这是全书最毒的一类错误。

#### 反向索引：谁在用我（入度 / 出度）

不要手写「本文被 X 引用」——手写的反向索引 100% 会腐化。改为从引用图算：`make-index.py . -d 24.6` 一条命令出结果。

| 指标 | 阈值 | 含义与动作 |
|---|---|---|
| **入度**（被几篇引用） | 0 且主题重要 | 结论没被接住：要么位置太靠后，要么缺一句可复述的 🔑 结论，要么它本该是别节的客场 |
| | ≥ 3 | 你是枢纽节，改动要通知所有引用方 |
| **出度**（引用了几篇） | ≥ 10 | 可能越界了，在写别人的主场 |
| | 0 | 可能困在孤岛里写作，先回第 ① 问 |

**实测**：38 节里有 5 节出入皆 0（1.2、4.1、26.2、53.2、53.3）。其中 53.2 单元测试、53.3 集成测试 成孤岛的原因很直观——**53.1 测试金字塔讲了「单元/集成/E2E 三层比例」，正文却一次也没链到下面两节**。这在目录上看着完整，在阅读路径上是断的。

#### 术语索引：一个概念一个名字

同一概念多种写法（幂等 / 去重 / idempotent）会直接废掉索引——grep 不到，读者搜不到，反向索引也算不准。

- 术语表里登记「标准名 + 别名」，全书正文只用标准名。
- 标题里同现两个名字（如「幂等设计与去重」）时，必须说明二者关系，否则读者以为是一门新东西。

### 配合：分工与接缝

#### 主场 / 客场——全书唯一硬规则

| 情况 | 展开写 | 只给一句 + 引用 |
|---|---|---|
| 本节核心命题 | ✅ | |
| 别节的主题，但本节需要它才能成立 | | ✅ |
| 同一张表 / 同一段代码 / 同一组数字 | ✅ 只在主场 | ✅ |
| 本节独有的失败模式、参数、取舍 | ✅ | |
| 通用术语定义 | ✅ 首次 | ✅ 后续 |

**可自动度量的判据**：同一术语在「主场篇 : 客场篇」的出现处数应 ≥ **3 : 1**；低于 2 : 1 说明客场已经长成第二个主场。

- 现在 25.4 : 24.4 = 32 : 22 = **1.5 : 1** → 幂等的客场写得过多，通用实现应部分迁回主场。

**例外条款（允许客场展开的三处）**：

| 例外 | 理由 |
|---|---|
| **自检题答案** | 自测必须自足，读者不该为了对答案再翻一篇 |
| **一句话 / 🔑 结论** | 结论就是用来被复述的，重复是设计 |
| **对比表的单元格** | 十来个字，是索引不是讲解 |

铁律 3 说的「补一句本质上就是……」也受此约束：补的必须是**本层语境下的翻译**。判据是「删掉它，本层论证是否断链」——断链就留，不断链就换成引用。

#### 层间分工：同一主题在不同层只讲本层视角

| 层 | 讲什么 | 例：缓存 |
|---|---|---|
| L0 运行时底座 | 机制、协议、系统调用 | 8.x：一次 RTT 的真实成本（回环 0.15ms，真实链路 30ms） |
| L3 质量属性 | 指标、建模、取舍 | 34.x：命中率 80%→90% 延迟只降 1.66 倍，99% 时剩余 1% 未命中主导 P99 |
| L4 组件与技术 | 结构、实现、运维 | 41.2：L1/L2 两级结构、失效广播三通道 |
| L5 工程效能 | 流程、发布、回滚 | 55.x：发布期间新旧版本与缓存的兼容（Expand-Contract） |

四层各写一遍「缓存是什么」，就是四倍的维护成本；各写一层视角，才是四倍的覆盖。

#### 接缝：本节留榫头，下节接住

- 本节末尾留一句能被下一节**直接接住**的结论（榫头）；
- 下一节开头一句话接住它（榫眼），而不是从零开始讲；
- 禁止用「接下来我们看看」做接缝——那是过渡词，不是结论。

#### 案例复用：一个案例只给一次全量数据

同一个案例（如 24.9 的下单链路）在全书多处出现时：

- **一处**给全量数字与推演（它的主场）；
- 别处写「以 24.9 的下单链路为例（数据见该节）」，只引用结论；
- 同一个案例两套数字，是最难被发现的错误——比空白更有害。

#### 文末「关联」块（接口声明）

```markdown
### 关联
- 前置：[24.4 TCC](24.4-TCC.md)、[24.6 本地消息表](24.6-本地消息表.md)
- 并列：[24.5 Saga](24.5-Saga.md)（补偿型，无冻结）
- 下游：[24.9 事务模型选型](24.9-事务模型选型.md)
- 待补：44.8 索引原理（未写，无链接）
```

四条规矩：≤ 4 行；每行「编号 + 短标题 + 链接」（待补项不写链接）；**必须与正文行内引用一一对应**（脚本可校验，不许出现只在块里、正文没引的项）；不写长句评论（会腐化）。

### 一次真实改写（24.4 TCC 的幂等段）

**改前**（客场展开，与 25.4 撞车）：

> 幂等是指同一操作执行多次与执行一次的结果相同。常见实现有唯一键、状态机 CAS、去重表、Token……（约 300 字通用讲解）

**改后**（主场讲透，客场给自足结论 + 编号）：

> TCC 的 Confirm 天然会被重复调用（协调者超时重试必然发生），所以**每个分支接口都必须幂等**。判据只有一条：重复到达时 `affected rows = 0` 且返回成功——裁判权交给数据库的条件更新，不交给应用层的「先查后改」。通用幂等设计（幂等键、去重窗口、存储成本）见 [25.4 幂等设计与去重](…)，本节只讲它在 TCC 里的形态：状态机 CAS。

- **保留了什么**：① 「TCC 里为什么必须幂等」的因果链（协议导致的约束，只有本节能讲）；② 一条不跳转也能用的判据。
- **删掉了什么**：可移植到任何场景的通用实现（那是 25.4 的主场）。
- **判据**：把 25.4 整篇删掉，本节是否仍成立？成立 → 切点对了。

### 反模式

| 反模式 | 后果 |
|---|---|
| 不读目录直接写 | 与别节撞车，写完才发现，返工 |
| 为「保证完整」复述别节 | 两个主场重叠，两版漂移，维护成本 ×N |
| 引用只写「详见上文」 | 读者跳不到，导出后失效 |
| 引用未写的节却不标记 | 读者落空，全书失信 |
| **只给引用、不给结论** | 读者被踢皮球：到了那边才发现语境不对 |
| 只写单向引用 | 被引方不知道谁依赖它，改结构踩空 |
| 替未写的节下结论 | 要么被推翻，要么把它锁死 |
| 复用废弃节的编号 | 旧引用指到新内容，读者发现不了 |
| **有标题但没链接** | 站点里点不动，读者只能手工翻目录 |
| 一页 10 个长链接 | 导航变成噪音 |
| 手写反向索引 | 必然腐化，比没有更糟 |
| 同一个案例两套数字 | 最难被发现的错误 |

### 30 秒 SOP（每篇动笔前跑一遍）

1. **读全文目录**：从头到尾看一遍（10.3k，必做，一次会话只需一次）
2. **圈相关**：标出 3–8 个可能相关的节（含兄弟、上下游、可能重复的）
3. **筛选**：`make-index.py . -q 核心词 同义词` 看候选的一句话，决定读哪几篇
4. **精读**：真正相关的 1–3 篇读全文（其余只看一句话）
5. **列概念清单**：每个概念标一个主场编号；找不到 → 先补目录
6. **写正文**：主场展开；客场一句自足结论 + 编号
7. **收尾**：写「关联」块，与行内引用对齐；核心术语再 `-q` 反查一遍防同义词漏检
8. **跑校验**：`check-refs.py . --quiet` → 裸编号 0、方向代词 0、悬空引用全带「待补」

### 自检

**Q1** 你写了 800 字讲幂等，而 25.4 已经讲透。保留哪一句、删哪 700 字？为什么不能全删？

▸ 答案：保留「Confirm 为什么必然重复到达 → 所以 TCC 必须幂等」这条因果链（由协议决定，只有本节能讲），加一条自足判据（`affected rows = 0` 且返回成功）。删掉的是可移植到任何场景的通用实现（幂等键、去重表、窗口与存储成本）——那是 25.4 的主场，两处讲必然漂移。不能全删：读者读 TCC 时需要闭环的因果，纯引用等于把理解成本推回给读者。

**Q2** 目录里有 44.8 索引原理，正文还没写。能引用吗？怎么写？

▸ 答案：能，而且应该引（否则本节会重写一遍索引原理）。写 `见 44.8 索引原理（待补）`：编号 + 标题 + 待补标记。不能替它下结论（「按 range 分片」这类话留给它自己），否则将来要么推翻你、要么被你那句话锁死。

**Q3** 24.4（TCC）和 25.4（幂等）都想讲幂等，怎么切？

▸ 答案：按「约束 vs 设计」切。24.4 只讲「TCC 协议为什么强制幂等」（空回滚、悬挂、Confirm 重试），25.4 讲「幂等怎么实现」（幂等键、状态机 CAS、去重窗口与成本）。判据是单向可删性：删掉 25.4，24.4 是否仍成立（成立）；删掉 24.4 的幂等段，25.4 是否变差（不会）——两问都过，切点就在对的位置。

**Q4** 为什么「详见上文」是错的，「见 24.6 本地消息表」是对的？

▸ 答案：三条理由都只在编号形态下成立：① **定位性**——编号全目录唯一，代词依赖「读者从哪个入口进来」；② **可校验性**——脚本能查 24.6 是否存在、标题是否一致，代词查不了；③ **载体无关**——导出 PDF、打印、单页分享时页码与顺序都会变，编号不变。

**Q5** 某节入度为 0（没人引用它），说明它不重要吗？

▸ 答案：说明它的结论没被接住，三种可能：① 它没给出一句可复述的 🔑 结论，别处想引也无从引；② 它在目录里位置太靠后，下游章节已写完；③ 它本该是别节的客场，应合并。按 ①→②→③ 顺序排查。入度为 0 从来不是「不重要」的证据。

**Q6** 引用越多越好吗？给出上限和依据。

▸ 答案：不是。每篇 3–8 处（1.4 万字/篇 ≈ 每 2000–4000 字一处）。超过 10 处通常暴露两件事：边界不清（在替别人写主场），或这一篇该拆成两篇。引用是导航，不是内容——导航太多等于没有导航。

**Q7** 有人主张「为保证协作，每篇动笔前通读全书」。用数字说明为什么不行，以及替代方案贵不贵。

▸ 答案：31 万字正文 ≈ 22 万 token，写 100 篇就是 2170 万 token，且随书稿增长线性放大——这不是纪律问题，是成本不可行。替代方案是索引：一次生成（0 token），每篇读 83 行骨架（0.9k）+ 3–5 次查询（~1k）+ 命中节的「一句话」（~0.2k），合计 ≈2.5k/篇，且**与书稿规模无关**。差 85 倍，而判定标准（唯一主场、客场引用）一点没降。

**Q8** 为什么「通读目录」这条规则本身就是设计缺陷？

▸ 答案：它规定的是**过程**（怎么知道），不是**结果**（能否说出编号）。过程规定的代价随规模变化，书越大越不可执行，最后被跳过；结果规定可以换实现方式——小书直接读目录，大书查索引，判定标准不变。规范要钉住不变量（唯一主场、编号可定位、悬空有标记），不要钉住手段。

**Q9** 为什么「编号只能废弃、不能复用」，而标题可以改（配全局替换）？

▸ 答案：编号是引用里的唯一定位符，复用会让旧引用静默指向新内容——读者跳得到、也读得通，所以永远发现不了，这是最毒的错误。标题是描述，改了只要全局替换，脚本能查出不一致（正文一级标题可比对）；也就是说标题错了可被发现，编号错了不可被发现，二者的容错等级不同。

## 五、语言风格

- **中文技术白话**，句子短。能用一句说清，不用三句。
- **先结论后论证**，不铺垫、不卖关子。
- **不写空话**："非常重要""极其关键""众所周知"——删。
- **不写自指**："本文""这一讲""接下来我们看看"——删。
- **术语照抄原文**：Raft、Paxos、CAP、2PC 等保持原拼写，不翻译。
- **表格优于长段落**，列表优于长句。

## 六、压缩与深度标准

- 输出字数 ≈ 原文清洗后字数的 **55%–70%**。
- **判断标准（唯一）**：一个没读过原文的工程师，读完能**通过相关岗位面试**、能**在选型时说出所以然**。
- 宁可偏全，不可偏短——知识零丢失（铁律 1）优先于压缩比。
