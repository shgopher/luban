# 第 4 章 技术选型：四问定生死

> **本章一句话**：选型不是选「最强」的，是选「团队能维护、三年不后悔、退出成本可接受」的；默认选团队最熟的那个。

**读完你会：**
- 用四个问题快速排除不合适的技术
- 在数据库、缓存、消息、网关之间做出有依据的选择
- 算清「买」和「建」的账
- 避开六个最常见的选型坑

---

## 4.1 选型四问

**结论先行**：团队会不会、生态活不活、能不能托管、退出难不难；四问答完，候选通常只剩一两个。

| 问题 | 要确认的事 | 一票否决 |
|---|---|---|
| 团队会不会？ | 有没有人用过、出问题能不能修 | 全团队没人碰过，且没有外部支持 |
| 生态活不活？ | 版本节奏、文档、社区、招聘 | 两年没发版、issue 没人回 |
| 能不能托管？ | 云厂商/第三方是否提供 | 必须自建且团队没有运维 |
| 退出难不难？ | 数据怎么迁、接口是否标准 | 私有协议、数据无法导出 |

给四个维度打分（1–5），总分相同就选**团队更熟**的那个。技术选型的成本，一半在「学」和「修」上。

---

## 4.2 数据库选型决策表

**结论先行**：默认 MySQL；复杂查询和 JSON 多选 PostgreSQL；全文检索用 Elasticsearch；聚合分析用 ClickHouse；文件用对象存储。

| 场景 | 首选 | 备选 | 什么时候别用 |
|---|---|---|---|
| 交易、订单、账务 | MySQL 8.0 | PostgreSQL | 数据量超十亿且无法分片时 |
| 复杂查询、GIS、JSONB | PostgreSQL 16 | MySQL | 团队完全没经验 |
| 缓存、会话、计数、排行榜 | Redis 7 | Memcached | 需要持久化主存储时 |
| 全文检索、日志分析 | Elasticsearch 8 | OpenSearch | 数据量小、只需 LIKE |
| 亿级聚合分析 | ClickHouse | Doris / StarRocks | 高频点更新、事务写入 |
| 图片、视频、备份 | S3 / OSS | MinIO | 需要低延迟随机读写 |
| 文档型、schema 多变 | MongoDB | PostgreSQL JSONB | 需要多表事务 |

| 你的情况 | 选什么 |
|---|---|
| 团队只会 MySQL，业务是标准 OLTP | MySQL，别换 |
| 需要强事务 + 复杂报表 | PostgreSQL |
| 单表将超 2000 万行、写入高 | MySQL + 分库分表，或 TiDB |
| 日志/检索，写入每秒几万条 | Elasticsearch + 冷热分层 |

## 4.3 缓存与检索选型

**结论先行**：缓存默认 Redis；检索默认 Elasticsearch；两者都不是「数据库」，不能当唯一数据源。

| 需求 | 选型 | 注意 |
|---|---|---|
| 分布式缓存 | Redis 7 集群 | 大 key、热 key、内存上限 |
| 纯 KV、多线程 | Memcached | 无持久化、无数据结构 |
| 全文检索 | Elasticsearch | 需要维护索引与 mapping |
| 轻量搜索、中小规模 | Meilisearch / OpenSearch | 生态与托管可用性 |
| 向量检索 | Milvus / pgvector | 数据量小优先 pgvector |

## 4.4 消息队列选型

**结论先行**：日志与流处理选 Kafka；业务消息（延迟、事务、重试）选 RocketMQ；复杂路由选 RabbitMQ；轻量场景选 NATS。

| 产品 | 吞吐 | 延迟 | 顺序 | 事务消息 | 运维难度 | 适用 |
|---|---|---|---|---|---|---|
| Kafka | 极高 | ms | 分区内 | 需自行实现 | 高 | 日志、埋点、流计算 |
| RocketMQ | 高 | ms | 分区内 | 支持 | 中 | 订单、支付、业务解耦 |
| RabbitMQ | 中 | μs–ms | 队列内 | 不支持 | 中 | 复杂路由、任务队列 |
| NATS | 高 | μs | 弱 | 不支持 | 低 | 内部轻量通信 |
| Pulsar | 高 | ms | 分区内 | 支持 | 高 | 多租户、分层存储 |

| 你的情况 | 选什么 |
|---|---|
| 已有 Kafka，团队会运维 | Kafka，别再引入第二套 |
| 需要延迟消息、事务消息 | RocketMQ |
| 只想做异步任务、量不大 | RabbitMQ 或 Redis Stream |
| 团队 < 10 人、无专职运维 | 云托管 MQ，别自建 |

## 4.5 网关、RPC、配置中心

**结论先行**：入口用 Nginx/APISIX，内部调用优先 gRPC，配置中心选团队已有或云托管；不要为了「统一」一次换三样。

| 类别 | 首选 | 备选 | 选择依据 |
|---|---|---|---|
| 入口网关 | Nginx Ingress | APISIX / Kong | 是否需要鉴权、限流、灰度 |
| 内部 RPC | gRPC | HTTP/JSON | 性能、IDL、跨语言 |
| 配置中心 | Nacos / Apollo | etcd / Consul | 是否要灰度、审计、多环境 |
| 服务发现 | K8s Service | Nacos / Consul | 是否已在 K8s |

gRPC 与 HTTP 的取舍：

| 维度 | gRPC | HTTP/JSON |
|---|---|---|
| 性能 | 高（二进制、多路复用） | 中 |
| 可读性/调试 | 需要工具 | 浏览器/curl 直接看 |
| 跨语言 | 强（IDL） | 强 |
| 浏览器直连 | 需 grpc-web | 原生支持 |

对外 API 用 HTTP/JSON，内部高频调用用 gRPC，是大多数团队的稳态。

## 4.6 买还是建：托管服务的账

**结论先行**：小团队优先买；只有当「规模足够大」或「有特殊合规/性能要求」时，自建才划算。

```text
自建年成本 = 机器 + 存储 + 人力(至少 0.5 人) + 故障损失
托管年成本 = 服务费 × 溢价系数(通常 1.5–3 倍自建机器成本)
```

| 情况 | 建议 |
|---|---|
| 团队 < 20 人、无专职运维 | 买（RDS、云 Redis、云 Kafka） |
| 核心业务、数据敏感 | 买合规托管，或私有化部署 |
| 规模大、成本占比高 | 自建 + 专业运维 |
| 只是临时/低频使用 | Serverless / 按量 |

一个常被忽略的数：一个能值班的运维，年成本往往超过中小团队一年的数据库托管费。

## 4.7 选型反模式

**结论先行**：选型翻车，通常不是技术不行，是「忽略了人和退出」。

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 选最新的、最热的 | 踩坑没人问，文档少 | 选落后一个版本、社区成熟的 |
| 只看 benchmark | 生产负载与 benchmark 完全不同 | 用自己的数据和流量压测 |
| 一次换多个组件 | 出问题无法定位是谁的锅 | 一次只换一个，灰度验证 |
| 忽略运维成本 | 上线后没人会扩容/备份 | 先问「谁来做、怎么做」 |
| 忽略退出成本 | 数据迁不走，被厂商锁定 | 选标准协议、可导出格式 |
| 为了简历选型 | 团队维护不了，最终重写 | 选团队能长期维护的 |

## 本章自检

**Q1** 两个方案评分相同，怎么选？
▸ 答案：选团队更熟悉的、托管选项更多的、退出成本更低的；长期维护成本比首年性能更重要。

**Q2** 为什么小团队不该自建 Kafka？
▸ 答案：Kafka 的价值在吞吐与生态，但运维（磁盘、分区、副本、升级）需要专职经验；小团队用云托管或 RocketMQ/RabbitMQ 更稳。

**Q3** 什么情况下值得为「性能」换数据库？
▸ 答案：现有库已经成为明确的瓶颈（写入打满、查询无法优化）、且业务增长可预期时；否则优先加缓存、读写分离、归档，换库的迁移与回滚成本通常被低估。
