# 第 3 章 写方案：文档、图、决策记录

> **本章一句话**：好方案不是「写得多」，是「别人看完能判断该不该批、开发看完知道怎么干、半年后能看懂为什么这么干」。

**读完你会：**
- 用六段式写出可评审的方案
- 只画两张图把系统讲清楚
- 用 ADR 记录关键取舍
- 在评审会上 10 分钟讲完并接住质疑

---

## 3.1 方案文档的六段式

**结论先行**：背景与目标、约束与假设、方案总览、关键设计、风险与兜底、排期与验收；顺序不能乱，因为评审是按这个顺序做判断的。

| 段落 | 写什么 | 评审关注 |
|---|---|---|
| 1 背景与目标 | 解决什么问题、成功标准 | 值不值得做 |
| 2 约束与假设 | 量级、预算、期限、存量 | 假设是否成立 |
| 3 方案总览 | 架构图 + 一次请求的路径 | 整体是否合理 |
| 4 关键设计 | 数据模型、接口、容量、一致性 | 细节是否站得住 |
| 5 风险与兜底 | 最坏情况、降级、回滚 | 出事能不能退 |
| 6 排期与验收 | 分几期、谁来做、怎么验 | 能不能落地 |

第 2 段最容易被跳过，也最容易导致返工。把「假设」写成可验证的句子，例如「峰值 1000 QPS，按压测单机 400 QPS 规划」，而不是「预计流量较大」。

## 3.2 C4 只画两张图

**结论先行**：系统上下文图回答「和谁交互」，容器图回答「由哪些部分组成」；组件图和代码图等真正需要时再画。

**图一：系统上下文**

```text
        ┌──────────┐        ┌──────────┐
        │  用户 App │        │  运营后台 │
        └────┬─────┘        └────┬─────┘
             │ HTTPS             │ HTTPS
        ┌────▼───────────────────▼─────┐
        │        订单系统（本系统）      │
        └──┬──────────┬──────────┬─────┘
           │          │          │
      ┌────▼───┐ ┌────▼───┐ ┌────▼────┐
      │ 支付平台 │ │ 库存系统 │ │ 消息推送 │
      └────────┘ └────────┘ └─────────┘
```

**图二：容器图**

```text
App ──▶ SLB ──▶ API Gateway ──▶ order-api (Deployment ×4)
                                     │
                     ┌───────────────┼───────────────┐
                     ▼               ▼               ▼
                  MySQL 8.0       Redis 7.x       Kafka
                  (主从)          (集群)          (3 broker)
```

| 图 | 元素 | 不该出现 |
|---|---|---|
| 上下文图 | 人、本系统、外部系统、关系 | 数据库、缓存、内部服务 |
| 容器图 | 服务、存储、中间件、协议 | 类、函数、表结构 |

## 3.3 一张请求链路图

**结论先行**：把一次核心请求从入口到落库画成一条线，标上每跳的耗时预算和失败点；这张图比十页文字更能暴露问题。

```text
客户端 3s
  └─ DNS 50ms ─▶ SLB 5ms ─▶ 网关 20ms ─▶ order-api 200ms
                                          ├─ Redis 5ms
                                          ├─ MySQL 20ms
                                          └─ 支付 RPC 150ms
```

| 跳 | 预算 | 失败时怎么办 |
|---|---|---|
| DNS | 50ms | 本地缓存、多 IP |
| SLB | 5ms | 多可用区 |
| 网关 | 20ms | 限流、熔断 |
| 应用 | 200ms | 超时、降级 |
| Redis | 5ms | 回源 DB，限流保护 |
| MySQL | 20ms | 重试一次、读写分离 |
| 下游 RPC | 150ms | 熔断、异步补偿 |

画完问自己：哪一跳挂了会影响核心链路？哪一跳没有超时？哪一跳没有降级？答案就是方案的风险清单。

## 3.4 ADR：一个决策一页纸

**结论先行**：每个「以后可能被推翻」的决策写一页 ADR：背景、选项、决定、后果；不写过程，只写判断依据。

```markdown
# ADR-007 订单查询缓存用 Redis 而不是本地缓存

状态：已采纳（2026-11-02）
背景：订单详情 QPS 8000，DB 压力大；多实例部署，要求 5 分钟内一致。
选项：
  A. 本地缓存（bigcache）：延迟最低，但多实例不一致，失效靠 TTL。
  B. Redis 集群：集中失效，一致性好，多一次网络往返。
  C. 不缓存：简单，但 DB 撑不住。
决定：选 B。订单状态变更时必须删缓存，接受 5ms 网络开销。
后果：多一个 Redis 依赖；缓存故障时降级为直查 DB，并限流。
```

ADR 的价值在「后果」那一段：它逼你想清楚「选了这个，我失去了什么」。

## 3.5 方案评审：怎么讲、怎么答

**结论先行**：10 分钟讲完：问题 → 方案 → 取舍 → 风险 → 计划；剩下的时间留给质疑。

| 顺序 | 内容 | 时长 |
|---|---|---|
| 1 | 问题与目标（一句话） | 1 分钟 |
| 2 | 方案总览（一张图） | 3 分钟 |
| 3 | 关键取舍（为什么不用 X） | 3 分钟 |
| 4 | 风险与回滚 | 2 分钟 |
| 5 | 排期与验收 | 1 分钟 |

提前准备五个问题：

1. 为什么不用现成的方案/开源组件？
2. 流量翻 10 倍会先坏在哪？
3. 数据库挂了怎么办？
4. 这个方案最复杂的部分是什么，谁来维护？
5. 如果只能做一半，先做哪一半？

被质疑时先确认「你担心的是哪一类问题」，再回答；不要急着辩护，评审的价值就是把盲区提前暴露。

## 3.6 技术方案的六个扣分项

**结论先行**：评审被否，通常不是因为方案不高级，而是因为「没取舍、没数字、没退路」。

| 扣分项 | 表现 | 修法 |
|---|---|---|
| 没有取舍 | 只讲优点，不讲代价 | 加一节「为什么不选 X」 |
| 没有数字 | 「性能较好」「量比较大」 | 换成 P99、QPS、存储量 |
| 没有失败路径 | 默认一切正常 | 加故障场景与降级 |
| 图画成拓扑 | 只有框和箭头，没有协议与职责 | 标协议、标同步/异步、标数据流 |
| 容量拍脑袋 | 「应该够用」 | 压测或经验值 + 冗余系数 |
| 没有回滚 | 只能往前修 | 写清代码/配置/数据三层回退 |

## 本章自检

**Q1** 为什么方案的第一页要写「约束与假设」？
▸ 答案：评审的所有判断都建立在约束上；假设不写出来，评审就无法判断方案是否成立，后面所有设计都可能建立在错误前提上。

**Q2** 上下文图和容器图最容易混的地方是什么？
▸ 答案：把数据库、缓存画进上下文图，或把类图画进容器图。上下文图只画「人和外部系统」，容器图才画「服务与存储」。

**Q3** ADR 里「后果」为什么比「决定」更重要？
▸ 答案：决定只说明选了什么，后果说明「为此付出了什么代价、什么情况下要推翻它」；后者才是未来做判断的依据。
