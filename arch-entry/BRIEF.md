# 《入门架构师实战手册》写作规范（所有撰稿人必读）

## 0. 这本书是什么

一本给**刚转架构师 / 要承担架构职责的 3–5 年工程师**的实战手册。
读者明天上班就要用：接需求、写方案、选型、画图、定部署、上线、排障。

**不是**原理书、不是面试八股、不是产品文档搬运。**每一页都要能落到“明天怎么做”。**

三条铁律：

1. **不講原理。** 只讲“是什么、怎么选、怎么配、怎么验、出事怎么办”。
   - 反例：GMP 调度、GC 三色标记、Raft 选举、CAP 证明、epoll 就绪队列、cgroups 实现。
   - 正例：Go 服务怎么设 GOMEMLIMIT、K8s 探针怎么配、Redis 大 key 怎么查。
2. **可抄。** 凡是配置/命令/代码，读者能直接复制到公司项目里改两个值就用。
3. **具体。** 给数字、给阈值、给默认值、给检查项。禁止“根据实际情况调整”这种废话——要给判断依据。

## 1. 读者画像

- 写过 3 年代码，熟悉 Go / Java 之一，用过 MySQL、Redis。
- 知道 Docker，但没独立管过 K8s 集群。
- 第一次要以“架构师”身份参加需求评审、写技术方案、拍板选型。
- 时间紧：老板要的是“下周的方案”，不是“三个月后的领悟”。

要求：
- 每章 5–8 个小节（`## N.x`），**不要**用 `###` 三级标题做小节（会撑爆目录）。三级标题只用于 `### 可直接抄`、`### 坑` 这种固定块，每章最多各出现 2 次。
- 小节标题用**名词短语 + 落点**，例如“6.3 索引：三个必会”“11.4 探针：两个探针别配反”。
- 本章自检固定 3 题。
- 该章若涉及组件（MySQL / Redis / Kafka / K8s / Nginx / Go），必须有至少 1 组**可直接抄**的命令或配置，并写清版本或前提。
- 每章至少 2 张表，至少 1 个“坑”表。

## 3. 语言风格

- 中文技术白话，句子短。一句话能说清就别用两句。
- **先给结论，再给理由。** 段落第一句就是结论。
- 用“你”称呼读者，不用“笔者”“我们”。
- 术语保留官方拼写：Kubernetes、Pod、Redis、Kafka、gRPC、OpenTelemetry，不硬翻译。
- 数字要落地：`P99 < 200ms`、`连接池 20–50`、`maxSurge: 1`、`5 分钟内`。
- 表格列数 ≤ 6，列名短。
- 每章正文 **2800–3800 字**（中文字符计），宁少勿水。
- 全文只允许出现这些符号：🔑（关键结论，≤3 次/章）、⚠️（坑，≤3 次/章）、💡（补充，≤3 次/章）。不要用其他 emoji。

**禁用句式**：“众所周知”“不言而喻”“非常重要”“极大提升”“随着业务的发展”“在当今互联网时代”“本文”“接下来我们”“综上所述”。
**禁用内容**：历史起源、论文引用、算法推导、源码分析、性能对比 benchmark（除非是自己跑的真实输出）、产品营销话术。

## 4. 代码与命令规范

- 代码块必须标语言：```go ```bash ```yaml ```sql ```json ```text
- Go 代码要能编译（`go vet` 过），用标准库优先，import 完整，不要 `...` 省略关键逻辑。
- 命令要能在标准环境跑：写清镜像版本或工具版本，例如 `redis:7.2`、`kubectl 1.29+`、Go 1.22+。
- 配置片段要完整可粘贴：YAML 缩进正确，不要“示意”。
- 数字若来自经验估算，写成“经验值：约 X”；不要伪造精确 benchmark。
- Shell 命令不要用需要交互的（如 `redis-cli` 交互模式），用 `-c` / `--no-auth-warning` 这类参数。

## 5. 内容边界（写之前先看）

**必须写**（只要该章涉及）：
- 怎么选（决策表：你的情况 → 选什么）
- 怎么配（参数、默认值、推荐值、公式）
- 怎么验（命令 + 预期输出）
- 怎么退（回滚/降级开关）
- 出什么事（坑表 + 处置动作）

**禁止写**：
- 原理推导、协议握手细节、内核机制、调度算法、共识算法、存储引擎内部结构
- 微服务治理原理（服务网格数据面原理、注册中心一致性）
- 语言运行时内部（GMP、GC 标记、内存分配器、逃逸分析）
- 大段产品对比的历史和生态介绍
- 与“明天能用”无关的前瞻趋势

**判断标准**：一个架构师在周一晨会上会不会用到这句话？不会，删掉。

## 6. 示例：合格的小节

```markdown
## 6.4 慢查询：先看执行计划，再改索引

**结论先行**：慢查询 90% 是索引问题，剩下 10% 是数据量问题。顺序不能反——先 `EXPLAIN`，再决定加索引、改 SQL，还是归档数据。

看三列就够了：

| 列 | 看什么 | 危险信号 |
|---|---|---|
| `type` | 访问类型 | `ALL`（全表扫）、`index`（全索引扫） |
| `rows` | 预估扫描行数 | 超过结果集 100 倍 |
| `Extra` | 额外动作 | `Using filesort`、`Using temporary` |

```sql
EXPLAIN SELECT id, status FROM orders
WHERE user_id = 10086 AND created_at > '2026-01-01'
ORDER BY created_at DESC LIMIT 20;
```

预期：`type=ref`、`key=idx_user_created`、`rows` 在几十到几百、`Extra` 不含 `Using filesort`。
如果 `type=ALL` 且 `rows` 是几十万，别犹豫，先加联合索引 `(user_id, created_at)`。

⚠️ 加了索引仍然慢，先看**回表**：`SELECT *` 会把回表行数放大，改成只取需要的列，或者用覆盖索引。
```
