# 附录 C 术语表

> 只收「开会时会被问到、答不上来会尴尬」的词；解释给入门架构师，不追求学术严谨。

| 术语 | 含义 | 一句话判断 |
|---|---|---|
| QPS / TPS | 每秒请求数 / 每秒事务数 | 容量规划的基本单位 |
| P99 | 99% 的请求快于该值 | 比平均值更能反映体验 |
| SLA | 服务等级协议，对客户的承诺 | 写进合同的可用性 |
| SLO | 服务等级目标，内部目标 | 通常比 SLA 更严 |
| SLI | 服务等级指标，实际测量值 | 用数据说话的那一个 |
| 错误预算 | 1 − SLO，允许的失败额度 | 花超了就暂停发布 |
| RTO | 故障后恢复所需时间 | 「多久能好」 |
| RPO | 允许丢失的数据时间窗 | 「会丢多少数据」 |
| 单点 | 挂掉会导致整体不可用的组件 | 问「它挂了会怎样」 |
| 雪崩 | 一个故障引发连锁失败 | 通常由重试放大 |
| 熔断 | 下游持续失败时快速失败 | 保护自己，不再打下游 |
| 限流 | 超过阈值直接拒绝 | 保护系统不被打垮 |
| 降级 | 用更便宜的方式提供不完整服务 | 有损但可用 |
| 幂等 | 同一操作执行多次结果相同 | 重试与消息消费的前提 |
| 最终一致 | 短时间不一致，最终会一致 | 大多数业务可接受 |
| 强一致 | 任何时刻读到的都是最新值 | 成本高，交易场景才需要 |
| 读写分离 | 主库写、从库读 | 注意主从延迟 |
| 分库分表 | 把数据按规则拆到多个库表 | 单表过千万再考虑 |
| 热点 | 访问集中在少数 key/行 | 会打爆单个分片 |
| 缓存穿透 | 查不存在的数据，绕过缓存 | 空值缓存/布隆过滤器 |
| 缓存击穿 | 热点 key 过期瞬间大量回源 | 互斥锁/singleflight |
| 缓存雪崩 | 大量 key 同时过期 | TTL 加随机抖动 |
| 消息积压 | 生产速度大于消费速度 | 先看消费者是否存活 |
| 死信队列 | 多次消费失败的消息去处 | 必须有人处理 |
| 灰度 | 只让部分用户用新版本 | 按用户/地域/比例 |
| 金丝雀 | 先给 1%–5% 流量的灰度 | 观察后再放量 |
| 蓝绿 | 两套环境，流量一次切换 | 回滚最快，成本 2 倍 |
| 滚动发布 | 逐台替换实例 | 新旧版本会共存 |
| 优雅停机 | 停止接新请求并处理完在途请求 | 发布不丢请求的关键 |
| 探针 | K8s 检查容器状态的机制 | readiness 管流量，liveness 管重启 |
| HPA | 按指标自动扩缩 Pod | 扩 Pod 不等于扩节点 |
| QoS | K8s 资源保障等级 | 决定资源紧张时谁先被杀 |
| Sidecar | 与主容器同 Pod 的辅助容器 | Service Mesh 的实现方式 |
| Trace / Span | 一次请求的调用链 / 其中一段 | 跨服务定位耗时的基础 |
| 指标基数 | 标签组合的数量 | 太高会打爆监控系统 |
| 告警风暴 | 一个故障触发大量告警 | 需要分组、抑制、静默 |
| 技术债 | 未来每次改动都要多付的成本 | 按影响面排优先级 |
| 绞杀者模式 | 新系统逐步替换旧系统 | 不重写，一点点切流量 |
| ADR | 架构决策记录 | 一页纸写清为什么这么选 |
| C4 | 架构图分层模型 | 入门只需上下文图+容器图 |
| 单元化 | 按用户分片到独立单元 | 超大规模与容灾手段 |
| 冗余系数 | 容量规划时额外留的倍数 | 单机房 1.3，双机房 2.0 |
