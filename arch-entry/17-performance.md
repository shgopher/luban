# 第 17 章 性能与容量：先测量，再优化

> **本章一句话**：性能问题 80% 不是「代码不够快」，而是「调用次数太多、数据量太大、资源没上限」；先量出瓶颈，再动手。

**读完你会：**
- 给接口定出可验收的性能目标
- 做一次能说明问题的压测
- 按性价比排出优化顺序
- 算出明年大促要几台机器、花多少钱

---

## 17.1 三个指标与目标设定

**结论先行**：延迟看 P99 不看平均，吞吐看峰值不看日均，资源看最紧的那一项；三个数一起看才有意义。

| 指标 | 定义 | 为什么要看 |
|---|---|---|
| 延迟 P99 | 99% 的请求快于这个值 | 平均值会被少量快请求拉低，掩盖长尾 |
| 吞吐 QPS/TPS | 每秒成功处理的请求数 | 决定容量与成本 |
| 资源 | CPU、内存、IO、连接数 | 决定瓶颈在哪、还能撑多久 |

目标怎么定：

| 接口类型 | P99 目标 | 可用性 | 说明 |
|---|---|---|---|
| 内部管理后台 | < 1s | 99.9% | 人能等，优先省成本 |
| To C 查询接口 | < 200ms | 99.95% | 超过 300ms 用户能感知卡顿 |
| 下单 / 支付 | < 500ms | 99.99% | 涉及钱，宁慢勿错 |
| 批量导出 | 异步任务 | — | 不同步等待，给任务 ID |

> 💡 目标必须写成「P99 < 200ms，错误率 < 0.1%」，不能写「尽量快」。没有数字的目标无法验收，也无法告警。

---

## 17.2 压测：怎么压、看什么

**结论先行**：压测要回答三个问题——单机能扛多少、瓶颈在哪、扩容是否线性；压不出瓶颈的压测等于没压。

```bash
# wrk：8 线程、200 并发、持续 60 秒，输出延迟分布
wrk -t8 -c200 -d60s --latency http://127.0.0.1:8080/api/orders

# POST 场景用 Lua 脚本带 body
wrk -t8 -c200 -d60s --latency -s post.lua http://127.0.0.1:8080/api/orders

# vegeta：固定速率，更适合看「稳定在 500 QPS 时」的表现
echo "GET http://127.0.0.1:8080/api/orders" | \
  vegeta attack -rate=500 -duration=60s | vegeta report
```

wrk 输出这样读：

```text
Latency Distribution
     50%   12.31ms
     90%   38.02ms
     99%  121.44ms
  99.99%  380.10ms
Requests/sec:  1842.33
Transfer/sec:    412.10KB
```

- `Requests/sec` 是吞吐，`99%` 是 P99；
- 如果 P99 是 P50 的 20 倍，说明有慢请求或锁竞争，别急着扩容；
- 必须同时看错误率，`Non-2xx` 占比超过 0.1% 的压测结果无效。

| 压测项 | 要求 | 不满足的后果 |
|---|---|---|
| 环境 | 与生产同规格、同中间件版本 | 压出来的数字不能用 |
| 数据量 | 与生产同数量级 | 小表全缓存，压不出慢查询 |
| 流量模型 | 读写比例、参数分布接近真实 | 只压到最简单的路径 |
| 观察项 | P99、错误率、CPU、GC、连接池等待、下游 | 只知道「扛不住」，不知道「为什么」 |
| 时长 | 至少 10 分钟 | 短时压测看不到内存增长与连接泄漏 |

## 17.3 优化顺序：缓存、异步、批处理、池化

**结论先行**：优化的性价比从高到低是：减少调用次数 → 加缓存 → 改异步 → 批处理 → 池化 → 索引/SQL → 扩容；先做前面，后面往往就不用做了。

| 症状 | 先查什么 | 常见解法 |
|---|---|---|
| 接口慢，CPU 不高 | 下游调用次数、SQL 条数 | 合并查询、批量接口、缓存 |
| CPU 打满 | 火焰图，看热点函数 | 减少重复计算、降序列化开销、限流 |
| P99 抖动 | GC、锁、连接池等待 | 对象池、减少大对象、调大池 |
| 吞吐上不去，CPU 有余 | 连接数、线程/协程阻塞 | 异步化、批处理、扩并发 |
| 数据库慢 | 慢查询日志、执行计划 | 索引、改写 SQL、归档、读写分离 |
| 内存持续涨 | 堆 profile、goroutine 数 | 缓存上限、修泄漏、限流 |

一个典型的「循环里查库」：

```go
// 反例：1000 个订单，1000 次查询
for _, o := range orders {
	u, _ := userRepo.Get(ctx, o.UserID)
	o.UserName = u.Name
}

// 正例：一次批量查，再在内存里拼
ids := make([]int64, 0, len(orders))
for _, o := range orders {
	ids = append(ids, o.UserID)
}
users, _ := userRepo.BatchGet(ctx, ids) // WHERE id IN (...)
m := make(map[int64]*User, len(users))
for _, u := range users {
	m[u.ID] = u
}
for i := range orders {
	orders[i].UserName = m[orders[i].UserID].Name
}
```

## 17.4 容量规划与冗余系数

**结论先行**：机器数 = 峰值 QPS ÷ 单机容量 × 冗余系数；单机容量靠压测，冗余系数看故障域，余量留 30%。

```text
单机容量 = 压测稳定值 × 70%（留安全边界）
机器数   = 峰值 QPS ÷ 单机容量 × 冗余系数
冗余系数 = 1.3（单机房）～2.0（双机房/双活）
```

算例（数字自洽）：

| 项 | 值 | 说明 |
|---|---|---|
| 峰值 QPS | 3000 | 大促预估，不是日均 |
| 单机压测稳定值 | 600 QPS | P99 < 200ms、错误率 < 0.1% |
| 单机容量 | 600 × 70% = 420 | 留 30% 余量 |
| 冗余系数 | 1.5 | 允许挂一个机房的一部分 |
| 机器数 | 3000 ÷ 420 × 1.5 ≈ 10.7 | 按 3 个可用区打散，每区 4 台，取 12 |
| 并发 | 3000 × 0.2s = 600 | 利特尔法则：并发 = QPS × 延迟 |

扩容触发线：CPU 持续 5 分钟 > 60%，或 P99 超过目标的 80%，或错误率 > 0.1%。

> ⚠️ 扩容只能解决「无状态层」的容量。数据库连接数、单表数据量、缓存带宽这些瓶颈，加机器反而更糟。

## 17.5 成本优化十招

**结论先行**：降本先降「闲置」和「规格过大」，再谈架构；前者当天见效，后者按月见效。

| # | 手段 | 预期节省 | 风险 |
|---|---|---|---|
| 1 | 按实际用量右 sizing（CPU/内存降一档） | 20%–40% | 峰值不够，需压测验证 |
| 2 | 弹性伸缩（低峰缩到 1/3） | 30%–50% | 冷启动慢的服务不适合 |
| 3 | 存储分级（冷数据转低频/归档） | 40%–70% | 取回延迟与费用 |
| 4 | 预留实例 / 节省计划 | 30%–60% | 锁定期，业务可能迁移 |
| 5 | CDN 与静态化 | 带宽降 50%+ | 缓存刷新与一致性 |
| 6 | 日志采样与保留期分层 | 日志成本降 50% | 排障时缺样本 |
| 7 | 离线任务错峰 | 峰值资源降 30% | 影响时效性 |
| 8 | 回收闲置资源（未挂载磁盘、旧镜像、僵尸实例） | 5%–15% | 误删风险，先打标签 |
| 9 | 架构简化（去掉不必要的中间件/副本） | 10%–30% | 可用性下降 |
| 10 | 按需转托管（自建 ES/Redis 转云托管） | 人力成本降 | 长期单价可能更高 |

成本要按月看「单位成本」：每万次请求成本、每订单成本、每活跃用户成本。只看总账单，会漏掉「业务涨了 10%，成本涨了 50%」这种问题。

## 本章自检

**Q1** 压测显示 QPS 上不去，但 CPU 只有 40%，先查什么？
▸ 答案：先查阻塞点——连接池是否打满、下游是否成为瓶颈、是否有全局锁或串行队列。CPU 没满说明不是算力问题，扩机器没用。

**Q2** 平均延迟 50ms、P99 800ms，这个服务健康吗？
▸ 答案：不健康。1% 的请求要等 800ms，按每天百万请求算就是一万次糟糕体验。先定位长尾来源（慢 SQL、锁、GC、下游超时），而不是看平均值。

**Q3** 峰值 QPS 3000、单机压测 600、冗余 1.5，为什么算出来要 12 台而不是 8 台？
▸ 答案：单机不能按 600 算，要留 30% 余量得 420；3000 ÷ 420 ≈ 7.1，乘冗余 1.5 ≈ 10.7。取整后还要按 3 个可用区打散、每区 4 台，所以是 12 台而不是 11 台。
