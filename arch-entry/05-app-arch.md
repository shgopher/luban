# 第 5 章 应用架构：从单体开始

> **本章一句话**：先做一个边界清楚的单体，等「协作成本」真的超过「分布式成本」再拆；拆的时候一次只拆一块，并且能退回去。

**读完你会：**
- 判断当前规模该不该用单体
- 用三条规则把单体做成「模块化单体」
- 识别该拆服务的五个信号
- 按正确顺序拆，并补齐最小配套

---

## 5.1 单体优先：什么规模该用单体

**结论先行**：团队 10 人以内、日请求百万级以下、发布不冲突，单体是更优解；它不是「落后」，是「用最低成本获得一致性」。

| 条件 | 单体更优 | 服务化更优 |
|---|---|---|
| 团队规模 | < 10 人 | > 30 人，多团队并行 |
| 发布频率 | 每天几次，互不阻塞 | 多团队独立发布 |
| 事务 | 大量跨模块事务 | 边界清晰、可最终一致 |
| 流量 | 单点可水平扩展 | 模块伸缩差异大 |
| 运维能力 | 无专职运维 | 有 SRE / 平台团队 |

单体的三个隐藏优势：本地事务、调用零网络开销、排查只需看一个进程。这三个优势在服务化后都要用复杂度换回来。

---

## 5.2 分层与目录结构

**结论先行**：handler 管协议、service 管业务、repo 管存储、model 管数据；依赖只能从上往下，不能反向。

```text
internal/
├── handler/      # HTTP/gRPC：参数校验、协议转换
├── service/      # 业务编排、事务边界
├── repo/         # SQL、缓存、外部 API 封装
├── model/        # 领域对象、错误定义
└── platform/     # 配置、DB、Redis、MQ 初始化
```

| 层 | 可以依赖 | 禁止 |
|---|---|---|
| handler | service、model | repo、SQL |
| service | repo 接口、model | net/http、具体 DB 驱动 |
| repo | model、DB 客户端 | service |
| model | 标准库 | 任何内部层 |

```bash
# CI 门禁：handler 不允许直接依赖 repo
if go list -deps ./internal/handler | grep -q 'internal/repo'; then
  echo "handler 不允许依赖 repo"; exit 1
fi
```

## 5.3 模块化单体的三条边界规则

**结论先行**：按业务分包、跨模块只走接口、禁止跨模块读表；三条做到，单体就不会烂成大泥球。

| 规则 | 做法 | 违反的后果 |
|---|---|---|
| 按业务分包 | `internal/order`、`internal/inventory`、`internal/payment` | 按技术分层，改一个功能动五个包 |
| 跨模块只走接口 | `order` 调 `inventory.Service`，不碰它的 repo | 内部实现互相渗透，无法独立演进 |
| 禁止跨模块读表 | 表归属于唯一模块，其他模块走接口 | 表结构一改，全站编译不过 |

```text
internal/
├── order/
│   ├── handler.go
│   ├── service.go
│   ├── repo.go
│   └── model.go
├── inventory/
│   ├── service.go     # 对外只暴露 Service 接口
│   └── repo.go
└── payment/
```

判断边界是否清楚：**删掉一个模块，其他模块要改几处？** 超过 3 处，说明边界没划好。

## 5.4 什么时候该拆服务：五个信号

**结论先行**：拆服务的信号来自「协作与伸缩」，不来自「代码行数」；五个信号出现两个以上，才值得拆。

| 信号 | 具体表现 |
|---|---|
| 独立伸缩 | 某个模块流量是其他的 10 倍，扩容被迫整体扩 |
| 独立发布 | 一个模块改动要全量回归、全量发布 |
| 故障隔离 | 一个模块 OOM 拖垮整个进程 |
| 团队边界 | 两个团队改同一仓库，天天冲突 |
| 技术异构 | 某个模块必须用不同语言/运行时 |

不该拆的信号：

- 「代码太多了」——先模块化；
- 「微服务是趋势」——不是理由；
- 「想用新技术」——可以在单体里试点；
- 「某个模块很简单」——简单模块拆出去，只增加运维成本。

---

## 5.5 拆的顺序：先拆什么，后拆什么

**结论先行**：先拆「边缘的读」，再拆「核心的读」，最后拆「写」；先同步调用，再改异步；数据先共享，最后才分库。

| 阶段 | 拆什么 | 风险 | 回滚 |
|---|---|---|---|
| 1 | 通知、导出、报表等边缘读 | 低 | 切回原接口 |
| 2 | 商品/订单查询等核心读 | 中 | 双读比对后切回 |
| 3 | 非核心写（日志、积分） | 中 | 双写 + 开关 |
| 4 | 核心写（下单、支付） | 高 | 需要事务/对账方案 |

拆一个服务的检查表：

- 接口契约先定，双方契约测试通过；
- 数据归属明确：谁写、谁只能读；
- 调用方全部登记，切流有开关；
- 监控、日志、链路先接好；
- 回滚方案写进发布单。

## 5.6 微服务的最小配套清单

**结论先行**：拆出第一个服务前，这七样必须有；少一样，运维成本会吃掉拆分收益。

| 配套 | 作用 | 没有会怎样 |
|---|---|---|
| 服务发现 | 找到对方实例 | 硬编码 IP，扩缩容即失联 |
| 配置中心 | 环境与开关 | 改配置要重新发版 |
| 统一网关 | 入口、鉴权、限流 | 每个服务重复实现 |
| 链路追踪 | 跨服务定位 | 出问题不知道哪个服务慢 |
| 集中日志 | 聚合检索 | 登录每台机器 grep |
| 指标监控 | 告警与容量 | 故障靠用户反馈 |
| CI/CD | 独立构建发布 | 手工部署，发布即事故 |

Service Mesh 不在最小清单里：团队 < 30 人、服务 < 20 个时，SDK 方案足够，Mesh 的收益抵不过运维复杂度。

---

## 5.7 分布式单体：最常见的事故源

**结论先行**：拆了服务但没拆数据、没拆发布、没拆团队，就得到「分布式单体」——比单体更慢、更脆、更难改。

| 症状 | 根因 | 修法 |
|---|---|---|
| 改一个功能要同时发 3 个服务 | 边界按技术层拆，不按业务 | 按业务能力重新划边界 |
| 服务之间共享数据库 | 图省事，直接读对方的表 | 表归属唯一，走接口 |
| 一个请求同步调 6 个服务 | 编排放在最上游 | 改异步/事件，或合并服务 |
| 发布必须一起发 | 契约不稳定、强耦合 | 版本兼容、契约测试 |
| 出故障全站挂 | 没有超时/熔断/隔离 | 补齐稳定性五件套 |

判断方法：**能不能只发布一个服务而不影响其他服务？** 不能，就还是分布式单体。

## 本章自检

**Q1** 团队 8 人、单体、模块边界清晰，产品要求「上微服务」，你怎么判断？
▸ 答案：先看是否有五个拆分信号。8 人团队通常协作成本低，拆了只会增加运维与分布式复杂度；可以先做模块化 + 独立部署流水线，等团队或流量真正增长再拆。

**Q2** 为什么先拆「读」后拆「写」？
▸ 答案：读没有副作用，切流和回滚都简单；写涉及数据归属与一致性，需要双写、对账、补偿，风险和成本都高得多。

**Q3** 共享数据库为什么是分布式单体的标志？
▸ 答案：共享库意味着服务之间仍通过表结构强耦合，任何 schema 变更都会同时影响多个服务，服务无法独立演进，只是把单体拆成了多个进程。
