# 第 8 章 消息与异步：解耦、削峰、最终一致

> **本章一句话**：该不该上 MQ、消息怎么不丢不重、积压怎么救、延迟与事务怎么选。

**读完你会：**
- 判断一个需求该用同步调用还是消息，并在评审会上说出理由
- 用本地消息表加幂等消费，写出不丢不重的生产端和消费端
- 按 SOP 处置 MQ 积压，选对延迟消息与事务方案

---

## 8.1 什么时候该上 MQ

**结论先行**：三个理由成立才上 MQ——解耦、削峰、异步最终一致。「强一致」和「团队没人运维」任一条成立就别上。

**该用的三个理由：**

1. **解耦。** 一次下单要通知库存、积分、发券、推送、数仓。同步调用每加一个下游就发一次版；发消息则谁需要谁订阅，上游不动。
2. **削峰。** 峰值 QPS 是均值 5 倍、下游单次 200ms 时，同步调用在峰值被压死。队列把脉冲摊平，下游按自己节奏消费。
3. **异步 / 最终一致。** 用户点完提交就该看到成功页，发积分、发短信晚 3 秒没人感知。这类动作全丢给消息，主链路 RT 从 800ms 降到 120ms。

**不该用的两个理由：**

1. **强一致场景。** 扣库存和扣余额必须同时成功或失败。消息只给最终一致，中间几百毫秒数据不一致，对账会疯。这类逻辑留在同一个本地事务里。
2. **团队没有运维能力。** Kafka 要人管磁盘、分区、rebalance、lag 告警、升级。没这个人，一次积压就是三小时故障。要么买托管服务，要么先别上。

| 你的情况 | 选什么 | 为什么 |
|---|---|---|
| 下游失败必须让上游一起回滚 | 同步调用 | 消息发出去撤不回，上游已提交 |
| 一个动作要通知 2 个以上下游 | 消息 | 加下游不改上游代码 |
| 峰值 QPS 是均值 3 倍以上，单次处理 > 200ms | 消息 | 用队列把脉冲摊平 |
| 下游可以晚几秒到几分钟 | 消息 | 用户不感知 |
| 下游是外部系统，可能长时间不可用 | 消息 + 重试 | 同步调用会把自己拖死 |
| 需要强一致（扣库存与扣款同时成功） | 同步 + 本地事务 | MQ 只给最终一致 |

💡 消息量小于 10 万条/天时，一张表加定时任务（8.2 的本地消息表）比 Kafka 划算：少一个中间件，少一半故障面。

## 8.2 可靠投递：本地消息表

**结论先行**：生产端不丢消息只有一条路——业务数据和消息在**同一个数据库事务**里落库，再由后台任务扫表投递。

| 写法 | 丢消息的窗口 | 结论 |
|---|---|---|
| 先发消息，再写库 | 写库失败，消息已发出，下游多一条脏数据 | 不可用 |
| 先写库，再发消息 | 发消息前崩溃或超时，消息永久丢失 | 不可用 |
| 同事务写业务表 + 消息表 | 无，两表同生共死 | 用这个 |

消息表就是「待发件箱」（outbox），状态改成已发送才算发出去。最坏情况是**重复投递**，不会是**丢失**。

### 可直接抄

```sql
-- MySQL 8.0，业务库内新增待发件箱表
CREATE TABLE outbox_message (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  message_id    VARCHAR(64)     NOT NULL COMMENT '业务唯一号，如 order_id；消费端幂等键',
  topic         VARCHAR(128)    NOT NULL,
  biz_key       VARCHAR(64)     NOT NULL COMMENT '分区键，一般与 message_id 相同',
  payload       JSON            NOT NULL COMMENT 'MySQL 8.0 会校验 JSON 格式',
  status        TINYINT         NOT NULL DEFAULT 0 COMMENT '0待投递 1已投递 2已废弃',
  retry_count   INT             NOT NULL DEFAULT 0,
  next_retry_at DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  created_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_message_id (message_id),
  KEY idx_status_retry (status, next_retry_at)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '本地消息表';
```

`uk_message_id` 两用：重复提交时挡住第二次插入；消费端拿它当幂等键。`idx_status_retry` 是扫描的驱动索引，缺了它扫描会全表扫。

```go
package outbox

import (
	"context"
	"database/sql"
	"encoding/json"
	"fmt"
	"log/slog"
	"math"
)

const (
	statusPending = 0 // 待投递
	statusSent    = 1 // 已投递
	statusDead    = 2 // 超重试上限，等人工
	maxRetry      = 8
	leaseSeconds  = 30
)

// Publisher 返回 nil 表示 broker 已确认。
type Publisher interface {
	Publish(ctx context.Context, topic, key string, value []byte) error
}

type Outbox struct {
	db  *sql.DB
	pub Publisher
}

// CreateOrder：同一事务写业务表和消息表。
func (o *Outbox) CreateOrder(ctx context.Context, orderID, userID string, amount int64, topic string) error {
	tx, err := o.db.BeginTx(ctx, nil)
	if err != nil {
		return fmt.Errorf("begin: %w", err)
	}
	defer tx.Rollback() // 已 Commit 时返回 ErrTxDone，忽略

	if _, err := tx.ExecContext(ctx,
		`INSERT INTO orders (order_id, user_id, amount, status) VALUES (?, ?, ?, 'CREATED')`,
		orderID, userID, amount); err != nil {
		return fmt.Errorf("insert order: %w", err)
	}

	payload, err := json.Marshal(map[string]any{"order_id": orderID, "user_id": userID, "amount": amount})
	if err != nil {
		return fmt.Errorf("marshal: %w", err)
	}
	if _, err := tx.ExecContext(ctx,
		`INSERT INTO outbox_message (message_id, topic, biz_key, payload, status, next_retry_at)
		 VALUES (?, ?, ?, ?, 0, NOW(3))`,
		orderID, topic, orderID, payload); err != nil {
		return fmt.Errorf("insert outbox: %w", err)
	}
	return tx.Commit()
}

// Dispatch：扫一批待投递消息发出，返回成功条数。
func (o *Outbox) Dispatch(ctx context.Context, batch int) (int, error) {
	rows, err := o.db.QueryContext(ctx,
		`SELECT id, topic, biz_key, payload, retry_count
		   FROM outbox_message
		  WHERE status = 0 AND next_retry_at <= NOW(3)
		  ORDER BY id
		  LIMIT ?`, batch)
	if err != nil {
		return 0, fmt.Errorf("scan: %w", err)
	}
	type job struct {
		id    int64
		topic string
		key   string
		body  []byte
		retry int
	}
	var jobs []job
	for rows.Next() {
		var j job
		if err := rows.Scan(&j.id, &j.topic, &j.key, &j.body, &j.retry); err != nil {
			rows.Close()
			return 0, fmt.Errorf("scan row: %w", err)
		}
		jobs = append(jobs, j)
	}
	rows.Close()
	if err := rows.Err(); err != nil {
		return 0, err
	}

	sent := 0
	for _, j := range jobs {
		// 租约抢占：把 next_retry_at 推后 30 秒，多实例只有一方改得动；
		// 进程挂掉 30 秒后自动重扫。
		res, err := o.db.ExecContext(ctx,
			`UPDATE outbox_message
			    SET next_retry_at = DATE_ADD(NOW(3), INTERVAL ? SECOND)
			  WHERE id = ? AND status = 0 AND next_retry_at <= NOW(3)`,
			leaseSeconds, j.id)
		if err != nil {
			return sent, fmt.Errorf("lease: %w", err)
		}
		if n, _ := res.RowsAffected(); n == 0 {
			continue // 别的实例抢到了
		}

		if err := o.pub.Publish(ctx, j.topic, j.key, j.body); err != nil {
			o.fail(ctx, j.id, j.retry, err)
			continue
		}
		if _, err := o.db.ExecContext(ctx,
			`UPDATE outbox_message SET status = 1 WHERE id = ? AND status = 0`, j.id); err != nil {
			return sent, fmt.Errorf("mark sent: %w", err)
		}
		sent++
	}
	return sent, nil
}

// fail：退避 1s、2s、4s…上限 300s，超上限置死信。
func (o *Outbox) fail(ctx context.Context, id int64, retry int, cause error) {
	next := int(math.Min(math.Pow(2, float64(retry)), 300))
	status := statusPending
	if retry+1 >= maxRetry {
		status = statusDead
	}
	if _, err := o.db.ExecContext(ctx,
		`UPDATE outbox_message
		    SET retry_count = retry_count + 1,
		        status = ?,
		        next_retry_at = DATE_ADD(NOW(3), INTERVAL ? SECOND)
		  WHERE id = ?`, status, next, id); err != nil {
		slog.Error("outbox mark fail", "id", id, "err", err)
		return
	}
	if status == statusDead {
		slog.Error("outbox dead letter", "id", id, "retry", retry, "cause", cause)
	}
}
```

三条运维约定：发送语义是**至少一次**，发成功但改状态前崩溃就会重发，所以消费端必须幂等；`status = 2` 的行数做成指标，超过 0 就告警；历史数据按天清，`DELETE FROM outbox_message WHERE status = 1 AND created_at < NOW() - INTERVAL 7 DAY LIMIT 1000;` 循环到影响行数为 0。

⚠️ 别把扫描和发送写成一个长事务：一边持行锁一边等网络，队列一抖就把连接池占满。先提交事务，再发消息。

## 8.3 幂等消费：五种做法

**结论先行**：幂等要做在数据库上，不能只做在 Redis 上。五种按可靠性排，选第一个能用的，再拿 Redis 挡在最前面。

**① 唯一索引。** 加唯一键，重复插入报 1062，捕获就当成功。

```sql
ALTER TABLE payment_flow ADD UNIQUE KEY uk_biz (biz_type, biz_id);
```

一行 DDL，成本最低，并发下也不漏。前提是有业务唯一键。

**② 状态机。** 只允许合法跃迁，判断写进 `WHERE`。

```sql
UPDATE orders SET status = 'PAID', paid_at = NOW(3)
 WHERE order_id = ? AND status = 'UNPAID';
```

影响行数 0 就是已处理或不合法，直接 ACK。所有状态变更都写成「从 A 到 B」，禁止无条件 `SET status = ?`。

**③ 去重表。** 没有业务唯一键时用：先插去重表，再执行业务，**同一事务**提交。

```sql
CREATE TABLE consumed_message (
  message_id  VARCHAR(64)  NOT NULL,
  topic       VARCHAR(128) NOT NULL,
  consumed_at DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (message_id),
  KEY idx_consumed_at (consumed_at)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

保留 7 天足够覆盖重试窗口，按 `consumed_at` 定期清。

**④ Redis SETNX + 过期。** 一行命令挡住绝大多数重复。

```bash
# 返回 OK = 第一次；返回 nil = 重复。TTL 要覆盖最大重试窗口
redis-cli -h 10.0.1.20 -p 6379 --no-auth-warning SET consume:order:20261102001 1 NX EX 86400
```

只能当第一道闸：主从切换可能丢写，TTL 短了漏、长了占内存。经验值 24 小时，后面**必须**有唯一索引或状态机兜底。

**⑤ 业务版本号。** 消息带版本，更新时校验，适合有并发写的聚合根。

```sql
UPDATE user_points SET balance = balance + ?, version = version + 1
 WHERE user_id = ? AND version = ?;
```

影响行数 0 表示版本已变，重读再试，最多 3 次。

| 做法 | 成本 | 可靠性 | 适用 |
|---|---|---|---|
| 唯一索引 | 最低，一行 DDL | 最高，数据库兜底 | 插入型：支付流水、积分明细 |
| 状态机 | 低，改 WHERE 条件 | 高，天然防重 | 有状态单据：订单、退款单、工单 |
| 去重表 | 中，多一张表加清理 | 高，同库同事务 | 没有业务唯一键的消费 |
| Redis SETNX | 低，一行命令 | 中，可能丢、会过期 | 高频去重的第一道闸 |
| 业务版本号 | 中，加字段改所有写路径 | 高，但要求消息带版本 | 有并发更新的余额、库存 |

🔑 幂等键用生产端生成的 `message_id`，重试时保持不变；不要用消息内容的哈希，字段一改就是新键。

## 8.4 积压处置 SOP

**结论先行**：先分清「消费者根本没在跑」还是「跑得太慢」，顺序反了就是白扩容。

lag = 分区最新 offset 减去消费者组已提交 offset，即还没被消费的条数。`--describe` 里的 LAG 是瞬时值，要看 5 分钟趋势。

| 指标 | 警告 | 严重 |
|---|---|---|
| lag 条数 | > 1 万且持续 5 分钟 | > 10 万，或持续增长 30 分钟 |
| 消息年龄（最老未消费消息写到现在） | > 1 分钟 | > 10 分钟 |
| 消费速率 vs 生产速率 | 消费 < 生产，持续 10 分钟 | 持续 30 分钟 |

消息年龄比条数更准：100 万条小消息 1 分钟消费完，1 万条大消息能卡 1 小时。

### 可直接抄

```bash
# Kafka 3.6+，看消费者组每个分区的真实堆积
# 关键三列：CURRENT-OFFSET / LOG-END-OFFSET / LAG
kafka-consumer-groups.sh --bootstrap-server kafka-1:9092 \
  --describe --group order-consumer

# 看分区数与保留策略，判断能不能靠扩分区救
kafka-topics.sh --bootstrap-server kafka-1:9092 \
  --describe --topic order-created

# 停掉消费者后跳过全部堆积（最后手段，消息等于丢弃）
kafka-consumer-groups.sh --bootstrap-server kafka-1:9092 \
  --group order-consumer --topic order-created \
  --reset-offsets --to-latest --execute
```

预期输出（数值为示例，只看列名和关系）：

```text
GROUP           TOPIC          PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG     CONSUMER-ID  HOST
order-consumer  order-created  0          812340          812340          0       consumer-1   10.0.1.11
order-consumer  order-created  1          790112          918004          127892  consumer-2   10.0.1.12
```

`CONSUMER-ID` 为空说明该分区没有消费者，先查服务起没起、组 ID 写错没有。`reset-offsets` 要求组内**没有活跃成员**，先停消费者再执行。

| 步 | 看什么 | 动作 | 判断 |
|---|---|---|---|
| 1 活着吗 | CONSUMER-ID 是否为空、是否反复 rebalance、Pod 是否重启 | 为空 → 起服务、查组 ID；反复 rebalance → 调大 `max.poll.interval.ms` | 5 分钟内解决 |
| 2 能扩吗 | 分区数 vs 消费者实例数 | 消费者 < 分区 → 扩到与分区数相等；已相等 → 只能扩分区 | lag 应在一个消费周期内开始降 |
| 3 单条多慢 | 消费耗时 P99 | > 100ms 就是慢：改批量写、去掉同步 RPC、补索引 | 速率翻倍才继续 |
| 4 能降级吗 | 消息重不重要 | 非核心转死信表后 ACK；核心链路降级为只落库 | 30 分钟内必须见效 |
| 5 转存跳过 | lag 是否超过 1 小时的消费量 | 转存到备份 topic，重置 offset，事后回放 | 最后手段，要有人签字 |

**扩消费者不能超过分区数。** 12 个分区最多 12 个有效消费者，第 13 个空转；扩分区只能加不能减，还会让同 key 的新消息落到新分区、顺序断掉。

**积压会写满磁盘**，磁盘满就是生产者和消费者一起挂。保留时长按容量算：`可用磁盘 ÷ (峰值写入速率 × 副本数)`。磁盘 1 TB、其他数据 500 GB、副本 2、峰值 20 MB/s → 250 GB ÷ 20 MB/s ≈ 3.5 小时。小于排障所需时间就设 `retention.bytes` 硬上限，磁盘 80% 告警。

### 坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 只扩消费者不扩分区 | 多出来的消费者空转，lag 一条不降 | 消费者数 ≤ 分区数，先扩分区 |
| 为了吞吐随手扩分区 | 同 key 旧消息在老分区、新消息在新分区，顺序全乱 | 扩之前确认业务不依赖顺序 |
| 用 reset-offsets 跳过积压 | 数据永久丢，对账出现缺口 | 先转存到备份 topic，保住回放能力 |
| 消费逻辑里同步调 RPC | 单条 200ms，单消费者只有 5 条/秒 | 消费只落库，下游动作再发一条消息 |

## 8.5 顺序消息：分区键怎么选

**结论先行**：只有「同一实体的事件必须严格按顺序」时才谈顺序。绝大多数业务只需要分区有序，全局有序等于把吞吐锁死在一个消费者上。

| 类型 | 怎么实现 | 吞吐 | 代价 | 适用 |
|---|---|---|---|---|
| 全局有序 | 单分区 + 单消费者 | 上限即单消费者能力（经验值 1000–3000 条/秒） | 无法水平扩展 | 配置下发、全局序列号 |
| 分区有序 | 按 key 哈希到分区 | 随分区数近似线性扩 | key 选错就倾斜 | 订单、用户、设备 |

| 业务 | 分区键 | 理由 |
|---|---|---|
| 订单事件（创建、支付、发货、关单） | `order_id` | 同一订单的事件必须串行 |
| 用户积分、余额变动 | `user_id` | 同一用户不能并发改同一行 |
| 设备告警 | `device_id` | 同一设备的告警要按时序展示 |
| 千万别用 | 时间戳、随机数、UUID | 打散到所有分区，等于无序 |

⚠️ key 为 null 时 Kafka 用粘性分区，同一批可能同分区，下一批就换——顺序没有保证。生产端必须显式设 key。

**rebalance 一定破坏顺序。** 分区从 A 换到 B：A 已拉未提交的消息被 B 重放（重复），A 没处理完的又和 B 的新消息交错。三个对策：

1. **按 key 哈希到固定 worker。** 同一 key 永远进同一个内存队列，串行处理。

```go
// 消费循环里：同一 key 永远落到同一个 worker
func pick(key string, n int) int {
	h := fnv.New32a()
	h.Write([]byte(key))
	return int(h.Sum32() % uint32(n))
}
```

2. **减少 rebalance。** 设静态成员 `group.instance.id`，`max.poll.interval.ms` 调到 600000，`max.poll.records` 调到 100。
3. **处理完再提交，版本号兜底。** 不开自动提交；消息带 `version`，`WHERE version < ?` 不成立就跳过，旧状态盖不回去。

## 8.6 延迟消息：三种做法

**结论先行**：能用 MQ 自带的就用自带，没有就用 Redis ZSET 加轮询，进程内时间轮只做「丢了也无所谓」的短延迟。

| 做法 | 精度 | 可靠性 | 成本 | 适用 |
|---|---|---|---|---|
| RabbitMQ TTL + DLX | 秒级，但受队头阻塞影响 | 高，消息落盘 | 中，每档一个队列 | 已有 RabbitMQ、档位少 |
| RocketMQ 延迟等级 | 固定档位 | 高 | 低 | 已有 RocketMQ |
| Redis ZSET + 轮询 | ±1 秒 | 中，内存数据靠 AOF | 低 | 档位多、量不大 |
| 进程内时间轮 | 毫秒 | 低，重启即丢 | 最低 | 短延迟、可丢的本地任务 |

**RabbitMQ TTL + DLX 有队头阻塞。** 队列 FIFO，只有队头到期才投到死信交换机：先塞 30 分钟的、再塞 10 秒的，后者要等 30 分钟。解法是每档一个队列（10s/30s/1m/5m/30m），或装 `rabbitmq_delayed_message_exchange` 插件——不阻塞，但百万级存量吃内存。

**RocketMQ 延迟等级固定。** 开源 4.x 只有 18 档：1s、5s、10s、30s、1m、2m、3m、4m、5m、6m、7m、8m、9m、10m、20m、30m、1h、2h，发消息设 `delayTimeLevel`（1–18）。要 45 分钟只能选 1h 或自己补一次；5.0 起支持任意时间。

**Redis ZSET 加轮询**，档位随便定：

```bash
# 投递：score 用到期毫秒时间戳
redis-cli -h 10.0.1.20 -p 6379 --no-auth-warning ZADD delay:order 1793600000000 "order:20261102001"
# 拉取到期任务；多实例靠 ZREM 返回 1 抢占，抢不到就跳过
redis-cli -h 10.0.1.20 -p 6379 --no-auth-warning ZRANGEBYSCORE delay:order 0 1793600000000 LIMIT 0 100
redis-cli -h 10.0.1.20 -p 6379 --no-auth-warning ZREM delay:order "order:20261102001"
```

要点：轮询 1 秒一次、单次取 100 条；AOF 必须 `appendfsync everysec`；失败把 score 改成 `now + 30s` 再 `ZADD` 回去。**时间轮**在 Go 里就是 `time.AfterFunc`，重启即丢、多实例重复执行，只配做本地缓存预热这类可丢任务。

**订单 30 分钟未支付关单，推荐这么做：** 有 RocketMQ 就用 `delayTimeLevel=16`（30m）；没有就用 Redis ZSET 存 `order_id → now+30min`，1 秒轮询一次。两种都加一道每分钟一次的兜底扫描，只扫最近 2 小时的单，走 `(status, created_at)` 索引：

```sql
UPDATE orders SET status = 'CLOSED', closed_at = NOW(3)
 WHERE status = 'UNPAID' AND created_at < NOW(3) - INTERVAL 30 MINUTE
 LIMIT 500;
```

条件更新本身幂等，重复执行无副作用。💡 扫描只做兜底：主路径靠延迟消息保证准时，扫描保证最多晚 1 分钟。

## 8.7 分布式事务：只留三个能落地的

**结论先行**：生产上能落地的只有三个——本地消息表（最终一致）、TCC（强一致但侵入大）、Saga（长流程补偿）。先问「能不能放进一个库」，再问「用哪个框架」。

| 方案 | 一致性 | 侵入性 | 适用 | 失败处理重点 |
|---|---|---|---|---|
| 本地消息表 | 最终一致，秒级到分钟级 | 低，加一张表 | 同库操作 + 下游可异步：发券、加积分 | 重试退避、死信告警、消费幂等 |
| TCC | 强一致（业务层） | 高，每个参与方写 Try/Confirm/Cancel | 资源必须预留：库存、余额、优惠券 | 空回滚、悬挂、幂等 |
| Saga | 最终一致（补偿完成后） | 中，每步配一个补偿 | 跨 3 个以上服务的长流程：下单→履约→结算 | 补偿幂等、补偿重试、人工兜底 |

本地消息表就是 8.2 那套，生产端一次事务加消费端幂等就够了。

**TCC 的三个必答题**，答不上就别用：

| 问题 | 怎么发生 | 怎么防 |
|---|---|---|
| 空回滚 | Try 超时或丢包，Cancel 先到，没有资源可释放 | Cancel 查 Try 记录，不存在就写一条已回滚标记并返回成功 |
| 悬挂 | Cancel 先执行完，延迟的 Try 才到，资源被冻住没人管 | Try 前查同一事务 ID 的控制记录，已是 CANCELLED 就拒绝 |
| 幂等 | Confirm / Cancel 被重复调用（超时重试） | 控制表条件更新，影响行数 0 即已处理 |

一张控制表同时解决三个问题：

```sql
CREATE TABLE tcc_transaction (
  tx_id      VARCHAR(64) NOT NULL,
  status     VARCHAR(16) NOT NULL COMMENT 'TRIED / CONFIRMED / CANCELLED',
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (tx_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

- **Try**：`INSERT INTO tcc_transaction (tx_id, status) VALUES (?, 'TRIED')`。主键冲突说明重复 Try 或已回滚（悬挂），本地事务回滚。
- **Cancel**：`INSERT ... VALUES (?, 'CANCELLED') ON DUPLICATE KEY UPDATE status = IF(status = 'TRIED', 'CANCELLED', status)`。不存在就插入（空回滚安全），TRIED 就改，已 CANCELLED 幂等返回。
- **Confirm**：只允许 `TRIED` 变 `CONFIRMED`，其余状态不动并返回成功。

**Saga 四条铁律：** 每步配补偿，补偿是反向操作（扣款对应退款）而不是删记录；补偿必须幂等，复用 8.3 的做法；补偿失败要重试并进人工队列；没有隔离性，中间态要用 `PROCESSING` 这类未生效状态挡住查询。

🔑 选型口诀：能同库就同库（本地事务）；不能同库看下游能否异步（本地消息表）；下游必须预留资源用 TCC；跨 3 个以上服务的长流程用 Saga。

## 本章自检

**Q1** 业务方要求「下单成功后必须立刻在积分账户看到积分」，你怎么回？
▸ 答案：先问「立刻」是 1 秒还是 1 分钟。同步写把积分和下单绑死在一条链路上，积分一抖下单就失败。推荐发消息加前端轮询，中间态显示「发放中」。坚持强一致就只能合库合事务。

**Q2** 本地消息表已经保证消息不丢了，为什么消费端还必须幂等？
▸ 答案：它给的是至少一次，不是恰好一次。「发送成功但改状态前崩溃」和「broker 已收但客户端超时」都会重发，再加 rebalance 重放、提交 offset 失败，重复是常态。幂等键用 `message_id`。

**Q3** lag 突然涨到 20 万，你第一件事是扩消费者吗？
▸ 答案：不是。先 `--describe` 看 CONSUMER-ID 是否为空、是否反复 rebalance——没在消费时扩多少都没用。确认在消费再看分区数：已等于分区数就只能扩分区，并确认业务对顺序不敏感。最后才看单条耗时、降级、转存。
