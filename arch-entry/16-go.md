# 第 16 章 Go 工程实践：能上生产的服务长什么样

> **本章一句话**：生产级 Go 服务 = 清晰的目录边界 + 可追踪的错误 + 能取消的 context + 有上限的并发 + 能观测的运行时；这五件事和语言底层无关，和工程习惯有关。

**读完你会：**
- 搭出一个别人接手不用问你的项目骨架
- 写出能定位问题、不会吞错的错误处理
- 用 context 管住超时与取消
- 避开五个最常见的 Go 生产事故

---

## 16.1 项目骨架：cmd / internal / pkg

**结论先行**：按「谁调用谁」分层，不按「技术类型」堆目录；`internal/` 放业务，`pkg/` 只放真的要被外部引用的东西。

```text
order-service/
├── cmd/
│   └── api/main.go          # 只做装配：读配置、连依赖、起服务
├── internal/
│   ├── handler/             # HTTP / gRPC 入口，只做参数校验与协议转换
│   ├── service/             # 业务编排，事务边界在这里
│   ├── repo/                # 存储访问，SQL 只出现在这里
│   ├── model/               # 领域对象与错误定义
│   └── platform/            # mysql.go / redis.go / mq.go / config.go
├── api/                     # openapi.yaml / proto
├── deploy/                  # Dockerfile / k8s manifest
├── migrations/              # 数据库变更脚本，按版本号命名
├── go.mod
└── Makefile
```

三条依赖规则，用 `go vet` 和 CI 卡住：

| 规则 | 含义 | 违反的后果 |
|---|---|---|
| handler 不碰 repo | 入口层不能直接写 SQL | 业务逻辑散落，改一处漏三处 |
| service 不 import net/http | 业务不依赖协议 | 换 gRPC/消息入口时要重写 |
| model 不依赖任何层 | 领域对象是叶子 | 循环依赖，编译都过不了 |

```bash
go mod init example.com/order-service
go build ./...
go list -deps ./internal/service | grep internal   # 看依赖有没有越界
```

> 💡 `main.go` 只做装配，不超过 80 行。它越长，说明业务逻辑漏进了入口层。

## 16.2 错误处理：包装、哨兵、别 panic

**结论先行**：错误要么被处理，要么被包装后往上抛；用 `errors.Is/As` 判断，永远不要比较错误字符串。

```go
package service

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
)

// 哨兵错误：调用方用 errors.Is 判断
var (
	ErrNotFound = errors.New("order not found")
	ErrConflict = errors.New("order status conflict")
)

// 带字段的业务错误：调用方用 errors.As 取出细节
type ValidationError struct {
	Field  string
	Reason string
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("invalid %s: %s", e.Field, e.Reason)
}

func (s *Service) Get(ctx context.Context, id int64) (*Order, error) {
	o, err := s.repo.FindByID(ctx, id)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			// %w 保留错误链，上层还能 errors.Is(err, ErrNotFound)
			return nil, fmt.Errorf("get order %d: %w", id, ErrNotFound)
		}
		return nil, fmt.Errorf("get order %d: %w", id, err)
	}
	return o, nil
}
```

handler 层统一翻译成 HTTP：

```go
func (h *Handler) GetOrder(w http.ResponseWriter, r *http.Request) {
	o, err := h.svc.Get(r.Context(), orderID(r))
	switch {
	case err == nil:
		writeJSON(w, http.StatusOK, o)
	case errors.Is(err, service.ErrNotFound):
		writeError(w, http.StatusNotFound, "ORDER_NOT_FOUND", "订单不存在")
	default:
		// 只在边界打日志，且带上 trace_id
		slog.ErrorContext(r.Context(), "get order failed", "err", err)
		writeError(w, http.StatusInternalServerError, "INTERNAL", "系统繁忙")
	}
}
```

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| `if err.Error() == "not found"` | 改一个字就失效 | `errors.Is` |
| `_ = err` 吞错 | 线上静默失败 | 处理或包装后返回 |
| 每层都 `log.Println(err)` | 同一条错误打 5 遍 | 只在边界打一次 |
| `panic` 处理业务错误 | 一个请求打挂整个进程 | 只用于不可恢复的编程错误 |
| 返回裸 `err` 不带上下文 | 不知道是哪一步失败 | `fmt.Errorf("...: %w", err)` |

`panic` 只在启动阶段（配置非法、依赖连不上）使用；HTTP 入口用 recover 中间件兜住漏网之鱼。

## 16.3 context：超时与取消

**结论先行**：context 是请求的生命周期，不是配置容器；它必须是函数的第一个参数，并且一路传到最底层的 IO 调用。

```go
func (s *Service) Charge(ctx context.Context, orderID int64) error {
	// 给这次下游调用单独设 2 秒预算，父 ctx 取消时也会立即返回
	ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
	defer cancel()

	if err := s.pay.Charge(ctx, orderID); err != nil {
		if errors.Is(err, context.DeadlineExceeded) {
			return fmt.Errorf("charge order %d: payment timeout: %w", orderID, err)
		}
		return fmt.Errorf("charge order %d: %w", orderID, err)
	}
	return nil
}
```

| 规则 | 说明 |
|---|---|
| 第一个参数，命名 `ctx` | 不要塞进 struct 字段 |
| 只传请求级数据 | trace_id、user_id 可以；数据库连接不行 |
| 每层都检查 `ctx.Err()` | 长循环、批量处理必须检查 |
| 不要用 `context.Background()` 起下游调用 | 会丢掉上游的取消与超时 |
| `defer cancel()` 不能省 | 否则计时器泄漏到超时为止 |

⚠️ 最常见的错：在 goroutine 里用 `context.Background()`，父请求已经超时返回了，后台还在跑，资源越积越多。

## 16.4 并发：errgroup、限并发、防泄漏

**结论先行**：并发要有三个上限——goroutine 数量上限、下游 QPS 上限、等待时间上限；没有上限的并发就是事故。

```go
func (s *Service) LoadHome(ctx context.Context, uid int64) (*Home, error) {
	g, ctx := errgroup.WithContext(ctx)
	g.SetLimit(3) // 最多 3 个并发，防止下游被打挂

	var (
		user    *User
		orders  []Order
		coupons []Coupon
	)
	g.Go(func() error {
		u, err := s.user.Get(ctx, uid)
		if err != nil {
			return fmt.Errorf("load user: %w", err)
		}
		user = u
		return nil
	})
	g.Go(func() error {
		os, err := s.order.ListByUser(ctx, uid, 10)
		if err != nil {
			return fmt.Errorf("load orders: %w", err)
		}
		orders = os
		return nil
	})
	g.Go(func() error {
		cs, err := s.coupon.ListAvailable(ctx, uid)
		if err != nil {
			return fmt.Errorf("load coupons: %w", err)
		}
		coupons = cs
		return nil
	})

	if err := g.Wait(); err != nil { // 任一失败，ctx 被取消，其余请求尽快返回
		return nil, err
	}
	return &Home{User: user, Orders: orders, Coupons: coupons}, nil
}
```

没有 errgroup 时，用带缓冲 channel 做信号量：

```go
sem := make(chan struct{}, 8) // 并发上限 8
for _, id := range ids {
	sem <- struct{}{}
	go func(id int64) {
		defer func() { <-sem }()
		process(ctx, id)
	}(id)
}
```

### 坑

| 坑 | 现象 | 修复 |
|---|---|---|
| goroutine 泄漏 | 内存与 goroutine 数持续上涨 | 每个 goroutine 都要有退出路径；测试用 `go.uber.org/goleak` |
| 在循环里 `defer` | 资源直到函数结束才释放 | 拆成小函数，或显式关闭 |
| `time.After` 在热循环里 | 定时器堆积 | 用 `time.NewTimer` + `Stop` |
| 并发写 map | 进程直接 `fatal error: concurrent map writes` | 加锁或用 `sync.Map` |
| 等一个永远不会关闭的 channel | 请求卡死直到超时 | 用 `select` + `ctx.Done()` |

## 16.5 配置与日志：slog 起步

**结论先行**：配置从环境变量进、启动时校验、非法就退出；日志用 `log/slog` 输出 JSON，字段固定，别拼字符串。

```go
type Config struct {
	Addr        string        `env:"ADDR"         default:":8080"`
	MySQLDSN    string        `env:"MYSQL_DSN"`
	RedisAddr   string        `env:"REDIS_ADDR"   default:"127.0.0.1:6379"`
	LogLevel    slog.Level    `env:"LOG_LEVEL"    default:"info"`
	ShutdownTTL time.Duration `env:"SHUTDOWN_TTL" default:"20s"`
}

func Load() (*Config, error) {
	cfg := &Config{ /* 从环境变量读取并填默认值 */ }
	if cfg.MySQLDSN == "" {
		return nil, errors.New("MYSQL_DSN is required")
	}
	return cfg, nil
}

func NewLogger(level slog.Level) *slog.Logger {
	h := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
		Level:     level,
		AddSource: true,
	})
	return slog.New(h).With("service", "order-api")
}
```

日志规范：

| 字段 | 示例 | 说明 |
|---|---|---|
| `level` | `ERROR` | 固定五级，不要自创 |
| `msg` | `create order failed` | 动词 + 对象，别写中文长句 |
| `trace_id` | `4bf92f3577b34da6` | 全链路透传 |
| `user_id` | `u_123` | 脱敏后 |
| `duration_ms` | `37` | 慢日志必备 |
| `err` | `...: context deadline exceeded` | 错误链，不丢上下文 |

> 💡 日志级别不是「心情」：`ERROR` 只给需要人介入的问题，`WARN` 给可自愈的异常，`INFO` 给关键状态变化。`ERROR` 太多等于没有告警。

## 16.6 HTTP 服务模板

**结论先行**：一个能上生产的 HTTP 服务，最少要有四个超时、一个 recover、一个 request id 和优雅停机。

```go
// cmd/api/main.go —— 完整可运行的最小生产骨架（仅标准库）
package main

import (
	"context"
	"errors"
	"log/slog"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

type Config struct {
	Addr        string
	ShutdownTTL time.Duration
}

func Load() (*Config, error) {
	return &Config{Addr: ":8080", ShutdownTTL: 20 * time.Second}, nil
}

func main() {
	cfg, err := Load()
	if err != nil {
		slog.Error("load config", "err", err)
		os.Exit(1)
	}
	slog.SetDefault(slog.New(slog.NewJSONHandler(os.Stdout, nil)).With("service", "order-api"))

	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	})
	mux.HandleFunc("GET /orders/{id}", func(w http.ResponseWriter, r *http.Request) {
		// 真实项目里委托给 handler 层，这里只演示路由参数
		w.Header().Set("Content-Type", "application/json")
		_, _ = w.Write([]byte(`{"id":"` + r.PathValue("id") + `"}`))
	})

	srv := &http.Server{
		Addr:              cfg.Addr,
		Handler:           Chain(mux, Recover(), RequestID(), AccessLog()),
		ReadHeaderTimeout: 5 * time.Second, // 防慢速攻击
		ReadTimeout:       10 * time.Second,
		WriteTimeout:      15 * time.Second,
		IdleTimeout:       60 * time.Second,
	}

	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)
	defer stop()
	go func() {
		if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			slog.Error("listen", "err", err)
			os.Exit(1)
		}
	}()
	<-ctx.Done()

	// 给在途请求 20 秒，必须小于 K8s 的 terminationGracePeriodSeconds
	shutdownCtx, cancel := context.WithTimeout(context.Background(), cfg.ShutdownTTL)
	defer cancel()
	if err := srv.Shutdown(shutdownCtx); err != nil {
		slog.Error("shutdown", "err", err)
	}
}
```

三个中间件一并给出，补上 `context`、`crypto/rand`、`encoding/hex`、`log/slog`、`net/http`、`time` 六个 import 即可用：

```go
type Middleware func(http.Handler) http.Handler

// Chain 按声明顺序执行：Chain(h, A, B) 等价于 A(B(h))
func Chain(h http.Handler, mw ...Middleware) http.Handler {
	for i := len(mw) - 1; i >= 0; i-- {
		h = mw[i](h)
	}
	return h
}

func Recover() Middleware {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			defer func() {
				if v := recover(); v != nil {
					slog.ErrorContext(r.Context(), "panic recovered", "panic", v)
					http.Error(w, "internal error", http.StatusInternalServerError)
				}
			}()
			next.ServeHTTP(w, r)
		})
	}
}

type ctxKey string

const requestIDKey ctxKey = "request_id"

func RequestID() Middleware {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			id := r.Header.Get("X-Request-ID")
			if id == "" {
				var b [8]byte
				_, _ = rand.Read(b[:])
				id = hex.EncodeToString(b[:])
			}
			w.Header().Set("X-Request-ID", id)
			next.ServeHTTP(w, r.WithContext(context.WithValue(r.Context(), requestIDKey, id)))
		})
	}
}

func AccessLog() Middleware {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			start := time.Now()
			next.ServeHTTP(w, r)
			slog.InfoContext(r.Context(), "http request",
				"method", r.Method, "path", r.URL.Path,
				"duration_ms", time.Since(start).Milliseconds(),
				"request_id", r.Context().Value(requestIDKey))
		})
	}
}
```

| 超时 | 不设的后果 | 建议值 |
|---|---|---|
| ReadHeaderTimeout | Slowloris 攻击拖死连接 | 5s |
| ReadTimeout | 请求体读不完占着连接 | 10s |
| WriteTimeout | 慢客户端拖住 goroutine | 15s |
| IdleTimeout | 空闲连接长期占用 | 60s |

## 16.7 pprof：线上怎么开、怎么看

**结论先行**：pprof 单独开一个内网端口，不要暴露在公网；排查时先看 CPU 和 goroutine，再看内存和锁。

```go
// 独立端口，只监听内网；不要挂到业务 mux 上
go func() {
	mux := http.NewServeMux()
	mux.HandleFunc("/debug/pprof/", pprof.Index)
	mux.HandleFunc("/debug/pprof/cmdline", pprof.Cmdline)
	mux.HandleFunc("/debug/pprof/profile", pprof.Profile)
	mux.HandleFunc("/debug/pprof/symbol", pprof.Symbol)
	mux.HandleFunc("/debug/pprof/trace", pprof.Trace)
	slog.Info("pprof listening", "addr", "127.0.0.1:6060")
	_ = http.ListenAndServe("127.0.0.1:6060", mux)
}()
```

```bash
# CPU：采样 30 秒，看谁在烧 CPU
go tool pprof -seconds=30 http://127.0.0.1:6060/debug/pprof/profile
(pprof) top -cum 20
(pprof) list 函数名

# 内存：看当前堆里谁占着
go tool pprof http://127.0.0.1:6060/debug/pprof/heap
(pprof) top -cum 20

# goroutine：看有没有泄漏（数量只涨不跌）
curl -s http://127.0.0.1:6060/debug/pprof/goroutine?debug=2 | head -50

# 阻塞与锁：找“等在哪”
go tool pprof http://127.0.0.1:6060/debug/pprof/block
go tool pprof http://127.0.0.1:6060/debug/pprof/mutex
```

| 现象 | 先看什么 | 常见原因 |
|---|---|---|
| CPU 高、QPS 不高 | CPU profile | 死循环、正则回溯、JSON 大对象 |
| 内存持续涨 | heap + goroutine | 缓存无上限、goroutine 泄漏 |
| 请求卡住 | goroutine + block | 等锁、等 channel、下游无超时 |
| 延迟抖动 | trace + GC 指标 | 大对象分配、STW 变长 |

## 16.9 五个高频 Go 生产事故

**结论先行**：Go 的坑不在语法，在「共享」和「生命周期」；下面五类占了线上事故的大头。

| 事故 | 现象 | 根因 | 修复 |
|---|---|---|---|
| goroutine 泄漏 | 内存涨、goroutine 数只增不减 | 向无人接收的 channel 发送、无退出条件 | `select` + `ctx.Done()`，goroutine 数打点 |
| map 并发读写 | 进程直接崩溃，堆栈指向 mapassign | 多 goroutine 写同一个 map | `sync.RWMutex` 或分片锁 |
| slice 共享底层数组 | 改了 A，B 也变了；内存不释放 | `s2 := s1[:2]` 仍引用原数组 | `append([]T(nil), s1[:2]...)` 复制 |
| HTTP body 未关闭 | 连接耗尽、TIME_WAIT 暴涨 | 忘记 `defer resp.Body.Close()` | 每次请求后关闭并读空 |
| 定时器泄漏 | 内存缓慢上涨 | 循环里 `time.After` | `time.NewTimer` + `Stop` |

一个真实的排查顺序：

```bash
# 1. 先看 goroutine 数量和堆栈
curl -s localhost:6060/debug/pprof/goroutine?debug=1 | head -20
# 2. 再看内存 top
go tool pprof -top localhost:6060/debug/pprof/heap | head -20
# 3. 最后确认是不是连接没关
ss -s | head -5
```

## 本章自检

**Q1** 为什么 `main.go` 要尽量短？
▸ 答案：它只做装配（配置、依赖、启动），业务逻辑放 internal。main 越长，说明入口层混入了业务与存储逻辑，测试和复用它都很难。

**Q2** `context.WithTimeout` 之后为什么必须 `defer cancel()`？
▸ 答案：不取消会直到超时才释放计时器和关联资源；在循环或高频调用里会持续泄漏，且子 goroutine 无法提前退出。

**Q3** 线上 goroutine 数持续上涨，第一步看什么？
▸ 答案：抓 `goroutine?debug=2` 的堆栈，按相同栈帧聚合，看大多数卡在哪一行；通常是向无人接收的 channel 发送、等锁，或下游调用没设超时。
