# 第 2 章 接需求：把一句话变成可做的指标

> **本章一句话**：需求评审不是「听产品讲功能」，是把「一句话」翻译成「量级、延迟、一致性、期限」四个可计算的约束。

**读完你会：**
- 用六个问题把模糊需求问清楚
- 填出一份可落地的非功能需求清单
- 把 DAU 换算成 QPS、存储和机器数
- 在评审会上问出真正影响方案的问题

---

## 2.1 需求澄清的六个问题

**结论先行**：谁用、解决什么、多大量、什么不能错、什么时候要、怎么算成功；六个问题答不上来，方案一定返工。

| 问题 | 为什么问 | 答不上来的风险 |
|---|---|---|
| 谁用？多少角色？ | 决定权限模型与界面复杂度 | 做完发现少了两类用户 |
| 解决什么问题？现在怎么凑合的？ | 判断真实价值与替代方案 | 做了个没人用的功能 |
| 多大量？峰值多少？ | 决定架构与成本 | 上线即崩，或过度设计 |
| 什么不能错？ | 决定一致性与容灾等级 | 该强一致的地方用了最终一致 |
| 什么时候要？能分期吗？ | 决定范围与取舍 | 赶工砍掉关键的非功能 |
| 怎么算成功？ | 决定验收标准 | 上线后无法证明价值 |

追问技巧：不要问「大概多少」，要问「去年峰值是多少、今年预计涨多少、大促是平时的几倍」。

---

## 2.2 非功能需求清单

**结论先行**：功能需求决定「做什么」，非功能需求决定「做成什么样」；每一项都必须有数字，否则无法验收。

| 维度 | 必须问到的数字 | 常见默认值 |
|---|---|---|
| 性能 | P99 延迟、峰值 QPS | 查询 < 200ms，写入 < 500ms |
| 可用性 | 几个 9、允许停机多久 | 内部 99.9%，交易 99.99% |
| 一致性 | 能否接受最终一致、延迟多久 | 订单强一致，Feed 可 5s |
| 容量 | 数据量、增长速度、保留期 | 按 3 年增长规划 |
| 安全 | 谁能访问、是否含个人信息 | 最小权限 + 脱敏 |
| 可观测 | 要哪些指标、日志保留多久 | 核心链路全链路追踪 |
| 成本 | 每月预算上限 | 按单请求成本核算 |
| 合规 | 等保、数据出境、审计 | 按行业要求 |

> 💡 非功能需求不是「越多越好」：把可用性从 99.9% 提到 99.99%，成本可能翻倍。要和业务一起定「够用」的档位。

---

## 2.3 从业务量到技术指标

**结论先行**：DAU → 日请求量 → 日均 QPS → 峰值 QPS，经验系数是「峰值 = 日均 × 3~5」，大促再 × 10。

算例：

| 步骤 | 计算 | 结果 |
|---|---|---|
| DAU | — | 100 万 |
| 人均日请求 | — | 20 次 |
| 日请求量 | 100 万 × 20 | 2000 万 |
| 日均 QPS | 2000 万 ÷ 86400 | ≈ 231 |
| 峰值 QPS | 231 × 4 | ≈ 925 |

存储估算：

```text
年数据量 = 日增量 × 365 × 行大小 × 副本数 × (1 + 索引膨胀 30%)
```

例：每天 30 万订单 × 2KB × 365 天 ≈ 219GB，3 副本 + 索引 ≈ 850GB/年。这还没算 binlog、备份和归档。

---

## 2.4 容量速算：一台机器能扛多少

**结论先行**：先用经验值估，再用压测校准；没有压测数据时，按保守值算，宁可多留余量。

| 接口类型 | 单机 QPS 经验值 | 说明 |
|---|---|---|
| 纯内存计算 | 3000–8000 | Go，简单 JSON |
| 单次 Redis 查询 | 1000–3000 | 连接池充足 |
| 单次 MySQL 主键查询 | 500–1500 | 命中索引 |
| 多表 JOIN / 聚合 | 50–300 | 随数据量下降 |
| 调用外部 API | 受下游限制 | 按下游配额算 |

```text
并发 ≈ QPS × 平均延迟(s)          # 利特尔法则
连接数 ≈ 并发 × 1.2               # 留 20% 余量
机器数 = 峰值 QPS ÷ 单机 QPS × 冗余系数(1.5)
```

按上面的 925 QPS、单机 500 QPS 算：925 ÷ 500 × 1.5 ≈ 2.8，取 3 台；再按两个可用区打散，实际 4 台。

## 2.5 约束盘点：钱、人、时间、合规

**结论先行**：约束不是「限制」，是方案的一部分；不盘约束，方案会在评审时被一句「预算没有」否掉。

| 约束 | 具体表现 | 对方案的影响 |
|---|---|---|
| 钱 | 预算上限、云账单归属 | 决定用托管还是自建、几副本 |
| 人 | 团队会不会 Go/K8s、有没有运维 | 决定技术栈与运维模式 |
| 时间 | 上线日期、能否分期 | 决定做多少、先做哪块 |
| 存量 | 老系统、老数据、老接口 | 决定迁移与兼容成本 |
| 合规 | 等保、隐私、审计 | 决定部署地域、加密、日志 |
| 供应商 | 已有合同、采购周期 | 决定能不能换组件 |

把这些写进方案的第一页「约束与假设」，评审时先对齐约束，再讲方案。

---

## 2.6 需求评审必问的十个问题

**结论先行**：这十个问题覆盖了 80% 的返工原因；会上没问，开发阶段一定会以「返工」的形式补回来。

| # | 问题 | 想确认什么 |
|---|---|---|
| 1 | 这个需求不做会怎样？ | 优先级与真实价值 |
| 2 | 峰值量级是多少？ | 容量与架构 |
| 3 | 延迟要求是多少？ | 同步/异步、缓存 |
| 4 | 能接受最终一致吗？延迟多久？ | 事务模型 |
| 5 | 失败了怎么办？能重试/补偿吗？ | 幂等与对账 |
| 6 | 数据保留多久？要删除吗？ | 存储与合规 |
| 7 | 谁有权限看/改？ | 权限模型 |
| 8 | 依赖哪些外部系统？他们可靠吗？ | 降级与熔断 |
| 9 | 能否分期上线？第一阶段最小是什么？ | 范围与节奏 |
| 10 | 怎么验收？谁来验？ | 成功标准 |

把答案直接写进方案，不要只留在会议纪要里。

## 本章自检

**Q1** 产品说「用户量很大」，你怎么把它变成可计算的指标？
▸ 答案：追问 DAU、人均请求数、峰值系数、增长预期，换算成峰值 QPS 与存储量；再按经验值和压测校准单机容量，得出机器数。

**Q2** 为什么非功能需求也要业务方确认？
▸ 答案：可用性、延迟、一致性都对应成本；业务不确认，架构师单方面拔高会浪费预算，单方面降低会在事故时背锅。

**Q3** 评审时对方说「先做出来再说，性能后面优化」，你怎么回应？
▸ 答案：可以接受分期，但要先定「第一期的性能底线」和「什么时候必须补」；架构上预留扩展点（缓存、异步、分表），避免后期推倒重来。
