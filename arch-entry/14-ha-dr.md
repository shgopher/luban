# 第 14 章 高可用与容灾：把 9 算成钱

> **本章一句话**：每加一个 9，成本大约翻一倍；先算清业务值几个 9，再决定花多少钱。

**读完你会：**
- 把「几个 9」换算成年/月允许停机时间，反推该投多少钱
- 用一张 12 项清单把架构里的单点排干净
- 在同城主备、同城双活、两地多活之间拍板，并说清代价
- 写出带 RTO/RPO、备份与季度恢复演练的容灾方案
- 用模板在 30 分钟内产出一份能执行的应急预案

---

## 14.1 可用性 9 的换算

**结论先行**：9 不是技术指标，是钱。算不出停机一小时损失多少的团队，最后都在 99.9 和 99.99 之间拍脑袋，然后为一个用不上的 9 多买一倍机器。

| 可用性 | 年停机 | 月停机 | 周停机 |
|---|---|---|---|
| 99% | 3.65 天 | 7.3 小时 | 1.68 小时 |
| 99.9% | 8.77 小时 | 43.8 分钟 | 10.1 分钟 |
| 99.95% | 4.38 小时 | 21.9 分钟 | 5.05 分钟 |
| 99.99% | 52.6 分钟 | 4.38 分钟 | 1.01 分钟 |
| 99.999% | 5.26 分钟 | 26.3 秒 | 6.05 秒 |

这三列是同一笔时间换了单位。月度复盘时老板问的是「这个月抖了多久」，所以用月停机那一列沟通。

🔑 可用性是串联相乘的。链路上每段独立，端到端 = 各段相乘：

```text
0.999 × 0.999 × 0.999 = 0.997002 ≈ 99.7%（年停机 26.3 小时）
```

三个「三个 9」串起来，只剩两个 9 多一点。网关 + 应用 + 数据库 + 缓存 + DNS，五段各 99.99%，整体只有 99.95%。要提升端到端，先找**最长的那一段**，别在已经 99.99% 的段上加机器。

**冗余不解决「同一条链路」。** 两个实例在同一台宿主机、同一个机柜、同一个可用区、同一个 LB 后端、同一个 DNS 服务商——这种「双份」的可用性就是 1 份。判断只有一句：**断掉它上游的那一个东西，两个实例会不会同时不可用？** 会，就是单点。

**你的业务该定几个 9：**

| 业务类型 | 目标 | 年停机预算 | 判断依据 |
|---|---|---|---|
| 内部系统、后台、报表 | 99.9% | 8.77 小时 | 停 1 小时只影响同事，没人报警 |
| 一般 to C 业务 | 99.95% | 4.38 小时 | 停机直接掉单，可容忍分钟级抖动 |
| 交易、支付、登录 | 99.99% | 52.6 分钟 | 停 1 分钟就有资损或客诉工单 |

99.999%（年停机 5.26 分钟）不建议自建：需要跨城多活 + 专职 SRE，成本约 5–10 倍。经验值：每提升一个 9，基础设施与人力成本约 2–3 倍。**先定目标，再谈方案**；目标写不出来的需求，不要接。

## 14.2 单点排查清单

**结论先行**：单点不是「有没有备用」，是「坏了之后 30 秒内有没有东西自动接住」。有备用但需要人登机器手动切，那也叫单点。

下面 12 项逐项过，任何一项答不出「自动接住」，就是待办。

| 单点 | 坏了的后果 | 消除方式 |
|---|---|---|
| 入口 DNS | 全站解析失败，比机房挂更彻底 | 两家 DNS 服务商 + 健康检查，TTL ≤ 60s |
| 负载均衡 / Ingress | 入口整体不可用 | 至少 2 实例、跨可用区；云 LB 开多可用区 |
| 应用实例数 | 单实例扛全量，重启即全站 5xx | 副本 ≥ 2，且 `PodDisruptionBudget` ≥ 1 |
| 数据库主库 | 写入全停，只剩只读 | 主备 + 自动切换（Orchestrator / 云 RDS 高可用版） |
| 缓存 | 打穿到数据库，引发雪崩 | 集群模式 ≥ 3 主 3 从，本地缓存兜底 |
| MQ | 异步链路停，订单状态不动 | 3 副本 + `min.insync.replicas=2` |
| 配置中心 | 新实例起不来、老实例改不了配置 | 本地兜底配置 + 客户端缓存快照 |
| 证书 | 到期当天全站 HTTPS 报错 | 自动续期 + 到期前 30 天告警 |
| 定时任务 | 双跑重复扣款，或全都不跑 | 分布式调度加锁单点执行，任务侧幂等 |
| 第三方依赖 | 对方挂你也挂 | 超时 + 熔断 + 降级开关，别裸调 |
| 同城机房 | 整个可用区失联 | 跨可用区部署 + 异地备份 |
| 运维权限 | 只有一个人有 root，他休假 | 至少 2 人有权限，操作留审计 |

口径：**「自动接住」= 不需要人登机器、不需要改配置、30 秒内流量自动切走。**

### 可直接抄

```bash
# 单点体检：5 分钟跑完，输出里读不满的行就是单点（kubectl 1.29+）
NS=prod
# 1) 可用副本数：READY 小于 2 即单点
kubectl -n $NS get deploy -o custom-columns='NAME:.metadata.name,READY:.status.readyReplicas'
# 2) 是否挤在同一节点：同一 NODE 出现两次即单点
kubectl -n $NS get pod -o custom-columns='NAME:.metadata.name,NODE:.spec.nodeName' --no-headers | sort -k2
# 3) 入口 TTL：大于 60 表示切流要等这么久才生效
dig +noall +answer www.example.com | awk '{print $1, $2}'
# 4) 证书到期时间：少于 30 天就安排续期
echo | openssl s_client -connect www.example.com:443 -servername www.example.com 2>/dev/null \
  | openssl x509 -noout -enddate
```

## 14.3 主备、双活、多活怎么选

**结论先行**：90% 的团队停在「同城双可用区主备 + 自动切换」就是性价比拐点；双活和多活只有交易类业务才值得，且必然在一致性上让步。

| 档位 | 资源倍数 | 数据一致性 | 切换时间 | 改造成本 | 什么时候停在这一档 |
|---|---|---|---|---|---|
| 单可用区单实例 | 1× | 强一致 | 挂了就挂了 | 0 | 内部工具、POC |
| 同城双可用区主备 | 2× | 强一致（同步/半同步） | 30 秒–5 分钟 | 2–4 人周 | 一般 to C、绝大多数业务 |
| 同城双活（单边写） | 2.5× | 强一致，写只在一个中心 | 1–5 分钟 | 2–3 人月 | 读多写少，能接受切换时只读 |
| 同城双活（双写） | 3× | 最终一致，要冲突合并 | 秒级 | 6 人月以上 | 极少，除非写入必须就近 |
| 两地三中心 / 多活 | 4–6× | 最终一致或分区可用 | 分钟级到小时级 | 10 人月以上 | 支付、金融、监管要求异地 |

**双活不是免费的，只有两种做法，选一种就要认它的账：**

- **双写**：同一笔业务两个中心都能写，冲突靠时间戳或业务规则合并。代价是「同一订单在两中心各生成一条」这类问题只能靠对账兜。改造量最大。
- **单边写**：写固定在一个中心，另一个中心只读，切换时才把写切过去。代价是切换窗口内写入被拒（返回「系统繁忙」），且要保证跨中心读延迟可接受。

拍板口径：**写入 QPS < 2000、且业务要求强一致的，不要做双写。** 停在同城双可用区主备，把钱投到演练和监控上，收益更高。

⚠️ 「双活」最常见的翻车是**做成了双写却没做对账**：两边都能写，冲突规则没写，最后靠人工改数据。要么补对账任务（按业务主键比对 + 差异告警），要么退回单边写。

## 14.4 RTO / RPO 与备份策略

**结论先行**：RTO 是「多久能恢复服务」，RPO 是「最多能丢多少数据」。这两个数必须由业务方书面确认，不能由 DBA 拍。

| 分级 | RTO | RPO | 典型系统 | 手段 |
|---|---|---|---|---|
| L0 | ≤ 5 分钟 | 0 | 支付、账务、清结算 | 同城双活 + 同步复制 + 自动切换 |
| L1 | ≤ 30 分钟 | ≤ 1 分钟 | 交易主链路、下单 | 主备热切 + 半同步 + binlog 实时同步 |
| L2 | ≤ 4 小时 | ≤ 15 分钟 | 一般业务、用户中心 | 主备冷备 + binlog 增量恢复 |
| L3 | ≤ 24 小时 | ≤ 1 天 | 报表、日志、归档 | 每日全量备份，可接受重跑 |

**备份策略四条：**

1. **全量 + 增量**：每周日全量，周一到周六增量，binlog 保留 7 天，才能恢复到任意时间点。
2. **3-2-1 原则**：至少 3 份副本、2 种介质（本地磁盘 + 对象存储）、1 份异地。
3. **异地备份**：跨地域对象存储，开版本控制与防删除，避免被误删或勒索一起带走。
4. **备份加密**：静态加密 + 密钥单独管理，**密钥不能和备份放同一个桶**。

**恢复演练每季度一次，必须记录实际 RTO**——从决定恢复到服务可用的墙钟时间，不是理论值。步骤固定五步：选一个 7 天前的备份集 → 起临时实例（端口 3307，不碰生产）→ 恢复 → 核对行数与校验和 → 把实测耗时写回预案。

### 可直接抄

```bash
# MySQL 8.0 + Percona XtraBackup 8.0，物理备份与恢复（生产推荐）
export DB_PASS='***'
# 1) 全量备份 + 解压 + prepare（不做 prepare，恢复出来的实例起不来）
xtrabackup --backup --compress --target-dir=/backup/full/2026-11-02 \
  --user=backup --password="$DB_PASS" --host=127.0.0.1 --port=3306
xtrabackup --decompress --remove-original --target-dir=/backup/full/2026-11-02
xtrabackup --prepare --target-dir=/backup/full/2026-11-02

# 2) 恢复到目标实例（datadir 必须为空，目标不能是生产主库）
systemctl stop mysqld && rm -rf /var/lib/mysql/*
xtrabackup --copy-back --target-dir=/backup/full/2026-11-02
chown -R mysql:mysql /var/lib/mysql && systemctl start mysqld

# 3) 逻辑备份与恢复（单库搬家、跨版本，MySQL 8.0）
mysqldump -uroot -p"$DB_PASS" --single-transaction --set-gtid-purged=OFF \
  --routines --triggers --events app > /backup/app_2026-11-02.sql
mysql -uroot -p"$DB_PASS" -e "CREATE DATABASE IF NOT EXISTS app_restore"
mysql -uroot -p"$DB_PASS" app_restore < /backup/app_2026-11-02.sql

# 4) 验证：物理恢复查 app.orders，逻辑恢复查 app_restore.orders；
#    行数与校验和必须与备份前一致，不一致就当这次备份失败
mysql -uroot -p"$DB_PASS" -e "SELECT COUNT(*) FROM app.orders; CHECKSUM TABLE app.orders;"
```

预期：恢复后 `COUNT(*)` 与备份时刻相同，`CHECKSUM TABLE` 一致。用 `time` 包住第 2、3 步，输出的 `real` 就是这次演练的 RTO 基线。

## 14.5 故障演练：从桌面推演到真拔网线

**结论先行**：没演练过的高可用等于没有高可用。演练只产出两张单子：发现了几个真问题、实测 RTO 是多少。

| 阶段 | 时长 | 做法 | 通过判定 | 风险 |
|---|---|---|---|---|
| L1 桌面推演 | 1 小时 | 白板 + 值班人，随机抽场景口头走处置 | 5 分钟内说得出止血动作和具体命令 | 无 |
| L2 单实例 kill | 30 分钟 | 生产或预发随机 kill 一个 Pod / 进程 | 错误率 < 0.1%，30 秒内副本补齐 | 低 |
| L3 依赖超时注入 | 1 小时 | 注入 500ms 延迟 / 10% 丢包 / 连接拒绝 | 熔断降级生效，P99 不超基线 2 倍 | 中，需限流兜底 |
| L4 机房级切换 | 2–4 小时 | 真拔网线、关 LB、切 DNS 到备用中心 | 实测切换 ≤ RTO，数据丢失 ≤ RPO | 高，需低峰 + 终止条件 |

```bash
# L2：随机干掉一个实例，看 30 秒内是否自愈（kubectl 1.29+）
POD=$(kubectl -n prod get pod -l app=order -o jsonpath='{.items[0].metadata.name}')
kubectl -n prod delete pod "$POD" && kubectl -n prod rollout status deploy/order --timeout=60s

# L3：给容器注入 500ms 延迟 + 10% 丢包（Pod 需 NET_ADMIN），撤销换 del
tc qdisc add dev eth0 root netem delay 500ms loss 10%
tc qdisc del dev eth0 root
```

**桌面推演 1 小时怎么开**：15 分钟讲清链路，30 分钟抽 2 个场景（一个依赖故障、一个机房故障）让值班人逐步说出「先做什么、敲什么命令、找谁决策」，15 分钟收敛成待办。不写代码、不改配置。第一次做，80% 的团队会在这一步发现预案里的命令根本不存在。

**演练方案模板要素**（8 项，缺一项就别开）：目标与通过判定、范围与时间窗（哪些集群、几点到几点）、参与人与决策人（谁有权喊停）、故障注入清单（逐条命令）、回滚与终止条件、观测看板与告警群、对外沟通话术、复盘时间。

**演练不通过的判定**，命中任一条即不通过：

1. 实际恢复时间超过该系统的 RTO。
2. 数据丢失超过 RPO，或需要人工补数据。
3. 需要临时改代码、手工改配置才能恢复。
4. 5 分钟内没人说得清「现在什么状态、影响哪些用户」。
5. 关键告警没触发，或触发了没人认领。

## 14.6 应急预案模板

**结论先行**：预案的唯一验收标准是——半夜三点，一个没参与过设计的人照着它，能把服务拉起来。

模板七段，顺序不能换：**触发条件 → 影响面 → 决策人 → 处置步骤（止血→定位→恢复→复盘）→ 对外沟通话术 → 回滚/切流命令 → 联系方式**。

下面是填好的示例（数据库主库故障）：

```text
【预案】订单库主库故障     版本 v3   更新 2026-11-02   负责人 张三

1. 触发条件（命中任一即启动）
   - 主库连接失败率 > 50% 持续 1 分钟
   - 告警 mysql_master_down，或订单接口 5xx > 5%

2. 影响面
   - 下单、支付回调、退款写入全停；查询走从库仍可用
   - 影响全量 C 端；资损风险：回调积压导致重复支付

3. 决策人
   - 一级（5 分钟内）：值班 SRE 李四，可直接切流
   - 二级（涉及数据取舍）：技术负责人 张三
   - 对外公告：产品 王五，超过 10 分钟未恢复必须发

4. 处置步骤
   止血 0–5 分钟：确认主库进程/磁盘/连接数；停掉非核心写入（对账、报表）
   定位 5–15 分钟：看 error log 最后 50 行、df -h、SHOW PROCESSLIST
   恢复 15–30 分钟：首选切备库（命令见第 6 段）；备库不可用时用备份 + binlog 恢复到新实例
   复盘 T+24 小时：输出时间线、根因、3 条改进项与 Owner

5. 对外沟通话术
   「订单系统正在紧急维护，预计 30 分钟内恢复。已提交的订单不受影响，请勿重复下单。」
   内部：每 10 分钟在 #incident 群更新「当前状态 + 下一步 + 预计时间」

6. 回滚 / 切流命令
   kubectl -n prod set env deploy/order DB_HOST=10.0.2.11
   kubectl -n prod rollout status deploy/order --timeout=120s
   回退：DB_HOST 改回原主库地址，同样等 rollout status 完成

7. 联系方式
   值班 SRE 李四 138**** / DBA 赵六 139**** / 云厂商：控制台 → 工单 → 紧急
```

三条硬要求：**命令要能复制粘贴**，别写「登录数据库执行切换」；**人要写名字和电话**，别写「值班同学」；**每季度演练后升版本号**，超过半年没更新的预案视为失效。

### 坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 备份没验证 | 真出事时发现文件损坏或缺表，RTO 变成无限 | 每季度恢复一次并核对行数与校验和，记录实测 RTO |
| 切换没演练 | 文档写 30 秒自动切，实际要 40 分钟手工改配置 | 每季度做一次真切换，实测时间写回预案 |
| 双活变双写 | 两中心各写一份，订单重复、库存对不上 | 双写必须配按主键的对账任务 + 差异告警，否则退回单边写 |
| DNS TTL 太长 | 切流后旧 IP 还被缓存 30 分钟，等于没切 | 核心域名 TTL 设 60s，切换前一周调低 |
| 容灾环境配置漂移 | 备中心少一个配置项、版本差两个月，切过去起不来 | 备中心与生产同源发布（同镜像、同配置仓库），每月对账一次 |
| 预案只有文档没有命令 | 出事时没人会敲，现场翻文档现查 | 每条处置动作后面直接跟可复制的命令 |
| 演练没有判定标准 | 演练变参观，年年做年年不知道能不能用 | 演练前写死 5 条不通过判定 |

## 本章自检

**Q1** 你的服务由「DNS + LB + 应用 + MySQL + Redis」五段组成，每段都做到 99.99%。端到端是多少？这时该往哪投钱？
▸ 答案：0.9999⁵ ≈ 99.95%，年停机约 4.4 小时。串联相乘已经吃掉一个 9，该补最弱的一段（通常是数据库切换与演练），而不是给已达标的段继续堆机器。

**Q2** 老板要求「双活」，你的写入 QPS 800、业务要强一致、团队 5 人。怎么答？
▸ 答案：停在同城双可用区主备 + 自动切换。双活要么双写（要冲突合并与对账，6 人月以上），要么单边写（切换时写入被拒）。这个量级多花的钱买不到对应可用性，投到演练与监控更值。

**Q3** 备份任务每天成功、监控全绿，为什么季度演练还是挂了？
▸ 答案：备份成功 ≠ 能恢复。三个常见原因：文件损坏或不完整、恢复步骤没人跑过、备库配置与生产漂移。唯一判定标准是能在临时实例上恢复并核对行数与校验和，同时记录实测 RTO。
