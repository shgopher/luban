# 13.5 系统基线加固

## 一句话

> 基线加固不是 “打补丁” 一件事，而是把 **“安全的默认值”固化下来**：关掉不需要的服务、收紧账号与权限、限制内核暴露面、记录审计——然后用脚本持续检查，而不是靠人记。

## 基线项（按收益排序）

| 类别 | 关键项 | 判据 |
|---|---|---|
| 账号 | 禁用 root 远程登录、强制密钥、最小 sudo | `/etc/ssh/sshd_config`、`visudo` |
| 服务 | 只开必要端口、关掉 telnet/ftp | `ss -tlnp` 对照白名单 |
| 内核 | `randomize_va_space=2`、`kptr_restrict=2`、禁 IP 转发 | `sysctl -a` |
| 文件 | 关键目录权限（600/700）、`noexec` 挂载 | `find / -perm -o+w` |
| 日志 | `auditd`/集中日志、留存 ≥6 个月 | 见 [3.5 审计与取证](../../需求/3-行业合规与外部约束/3.5-审计与取证.md) |
| 容器 | 非 root 运行 | 见下方 `docker inspect` 命令（输出非空且不为 `root`/`0`） |

## 脚本：一次检查、输出得分

```bash
#!/usr/bin/env bash
# 最小基线检查：每项 0/1 分，最后给百分比
score=0; total=0
check(){ total=$((total+1)); if eval "$2" >/dev/null 2>&1; then score=$((score+1)); printf "✓ %s\n" "$1"; else printf "✗ %s\n" "$1"; fi; }

check "禁止 root 远程登录" "! grep -qiE '^PermitRootLogin\s+yes' /etc/ssh/sshd_config"
check "禁止密码登录"       "grep -qiE '^PasswordAuthentication\s+no' /etc/ssh/sshd_config"
check "关闭 IP 转发"       "[ \"\$(sysctl -n net.ipv4.ip_forward)\" = 0 ]"
check "地址随机化开启"     "[ \"\$(sysctl -n kernel.randomize_va_space)\" = 2 ]"
check "无全局可写目录"     "! find /etc /usr /bin -xdev -perm -o+w 2>/dev/null | grep -q ."
echo "基线得分: $score/$total"
```

（脚本为通用写法，**未在本机对生产机执行**；不同发行版路径略有差异。）

## 基线可抄清单与验收命令

> 结论：基线只有落到“**一条可复制命令 + 一个能自动判定的输出**”才算落地；顺序必须是**先开审计、再封口子**——不先弄清谁在用，封禁就是在赌运气。

把基线写成人能背的句子没用，验收时机器要能判。判据的写法只有两种：**能 grep 出固定字符串**，或**能比较数字**。“密码认证已关闭”不是判据，`sshd -T | grep '^passwordauthentication no'` 有输出才是；“开启了审计”不是判据，`auditctl -l` 里至少 4 类关键事件各有规则才是。下面 12 条覆盖 SSH、内核、审计、账号、容器五类，命令可直接抄，判据可直接接进脚本：

| 类别 | 基线项 | 检查命令（root 执行） | 通过判据 |
|---|---|---|---|
| SSH | 关闭密码登录 | `sshd -T 2>/dev/null` | 输出里 `passwordauthentication` 那行为 `no` |
| SSH | 禁止 root 登录 | `sshd -T 2>/dev/null` | 输出里 `permitrootlogin` 那行为 `no`；`prohibit-password` 只算过渡态 |
| SSH | 空闲会话超时 | `sshd -T 2>/dev/null` | 输出含 `clientaliveinterval 300`（或更小）与 `clientalivecountmax 3`（或更小） |
| 内核 | 非路由器禁转发 | `sysctl -n net.ipv4.ip_forward` | 输出 `0`（网关/容器节点除外，见例外审批） |
| 内核 | 地址随机化 | `sysctl -n kernel.randomize_va_space` | 输出 `2` |
| 内核 | 禁 ICMP 重定向 | `sysctl -n net.ipv4.conf.all.accept_redirects` | 输出 `0` |
| 审计 | auditd 运行 | `systemctl is-active auditd` | 输出 `active` |
| 审计 | 关键事件有规则 | `auditctl -l` | 命令执行、账号文件、提权、SSH 四类各至少 1 条规则 |
| 账号 | 无空密码账号 | `awk -F: '$2==""{print $1}' /etc/shadow` | 输出 0 行 |
| 账号 | UID 0 只有 root | `awk -F: '$3==0{print $1}' /etc/passwd` | 输出只有 `root` |
| 容器 | 非 root 运行 | 见下方 `docker inspect` 命令 | 输出非空且不为 `root`/`0`；K8s 侧看 `runAsNonRoot: true` |
| 容器 | 根文件系统只读 | 见下方 `docker inspect` 命令 | 输出 `true`；K8s 侧 `readOnlyRootFilesystem: true` |

```bash
# 容器基线的两条 docker inspect（放在代码块里，避免 Vue 把 {{ }} 当插值）
docker inspect -f '{{.Config.User}}' <容器>
docker inspect -f '{{.HostConfig.ReadonlyRootfs}}' <容器>
```

几个判据数字的来源要说清：`clientaliveinterval ≤ 300`（5 分钟无操作断连）是运维规范与等保检查表的常见口径；审计的四类事件分别对应“谁执行了命令、谁动了账号、谁提了权、谁登了 SSH”，少一类，事后复盘就缺一段证据链；日志留存 180 天与审计取证的要求对齐（见 [3.5 审计与取证](../../需求/3-行业合规与外部约束/3.5-审计与取证.md)）。另外 `sshd -T` 在没生成 host key 的主机上会报错退出，先确认 `/etc/ssh/` 下有 `ssh_host_*` 文件，再谈判据。

这 12 条不是平均权重，验收要设门禁，否则“95 分”里可能藏着没关的 root 登录：

| 类别 | 权重 | 阻断项（失败即不允许上线） |
|---|---|---|
| SSH | 30% | 关闭密码登录、禁止 root 登录（两项必过） |
| 账号 | 20% | 无空密码账号、UID 0 只有 root（两项必过） |
| 审计 | 20% | auditd 运行且有 4 类规则（缺失即无法追责，必过） |
| 内核 | 20% | 三项至少过两项 |
| 容器 | 10% | 非 root 必过，只读根文件系统建议过 |

权重按“失败后能造成什么”排：SSH 与账号直接决定“能不能进来”，各占 30% 与 20% 且必过；审计决定“进来后查不查得到”，20% 且必过；内核与容器更多决定“进来后能扩多大”，按建议项处理，容器只占 10% 是因为镜像与主机基线同源，容器项漏掉通常也意味着镜像构建里没固化。

门禁判据：**总分 ≥ 90% 且阻断项零失败**才允许上线；任一项失败就回滚镜像并开单，而不是“下个版本再修”。

顺序为什么是“先审计后封禁”：基线加固最常见的翻车不是配置写错，而是**封禁把一个还在用的通道关掉了**。典型事故：直接禁掉密码登录，结果唯一可用的登录方式就是密码；或者关了 2022 端口，三天后才发现某备份任务还在用。审计先行，才能把“封禁会打断谁”变成可查的数字（登录来源、账号、密码登录占比）。可抄的加固顺序：

1. **留退路**：先备份 `/etc/ssh`、`sysctl -a`、`ss -tlnp` 的输出到变更单，确认每台机器至少还有一条不经过本次变更的登录路径（另一个会话、控制台、串口）。
2. **先开审计**：auditd 上线并补齐 4 类规则（命令执行、账号文件、提权、SSH），日志集中留存 ≥ 180 天；此阶段不改任何访问控制。
3. **统计谁在用**：从审计日志取近 7–30 天的登录账号、来源 IP、密码登录占比；来源不在清单里的，先找归属人再做决定。
4. **建替代通道并验证**：普通账号 + sudo、密钥登录、堡垒机三者至少两条可用，且用**新会话**验证过——不能在同一条 SSH 会话里改完就宣布成功。
5. **灰度封禁**：先关密码登录（保留现有 root 密钥或普通账号），观察一个发布窗口的鉴权失败率；再禁 root 登录。顺序反了会把运维锁在门外。
6. **并行封网络面**：`ss -tlnp` 对照白名单，逐个关掉非白名单端口；管理面收敛到堡垒机（见 [13.3 网络隔离与最小暴露面](13.3-网络隔离与最小暴露面.md)），避免“SSH 关了但 8443 还开着”。
7. **复测与回滚演练**：用同一批命令复跑，得分过门禁；再故意回滚一项、确认能退回，然后改回——没演练过的回滚等于没有回滚。

本机容器复测（Docker 29.9.2 / `alpine:3.20` 默认配置，非生产主机；原始输出见 `.cache/pilot2-13.5/raw.txt`）：可判定的 9 项里 **5 项通过、4 项不通过，审计 1 项容器内不可判定**——不通过的四项分别是 SSH 密码登录（默认 `yes`）、root 登录（默认 `prohibit-password`，未显式 `no`）、`net.ipv4.ip_forward=1`（容器网络需要，宿主上要单独看）、容器内 `id -u=0`。显式改 `PasswordAuthentication no` 后复查通过，换 `--user 1000:1000` 运行后容器项通过，`kernel.randomize_va_space=2`、空密码账号 0、UID 0 仅 root 三项本来就过。

这条复测的意义不在“容器不安全”，而在**默认值永远不会自己变安全**：同一张镜像不加任何加固跑出来是 5/9，加固动作只改两处就变成 7/9。把表里的命令塞进镜像构建、启动脚本与巡检任务，基线才会留在“加固后”的状态；否则新扩的节点会按发行版默认值回来，这正是本节自检 Q1 说的“加固一次没用”。基线清单也不是越全越好——CIS 类基准动辄上百项，一刀切会关掉网关的转发、容器的网络能力等业务必需项，所以按角色分层并保留书面例外，比追求 100% 更可持续。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只做一次加固，之后不复测 | 新装机/新镜像又回到默认值 |
| 用 “手工 checklist” 检查 | 人一换就忘，无法持续 |
| 为了排障方便开 root 登录 | 暴露面回到解放前 |
| 基线不考虑业务（一刀切） | 关掉必要服务，业务受损后被回滚 |
| 加固不做变更记录 | 出问题无法回滚到 “加固前” |
| 只加固主机、不管镜像 | 容器里仍是宽松默认值 |

## 三条铁律

> 🔑 **基线要脚本化、可复测**；手工 checklist 不算基线。

> 🔑 **加固必须可回滚**（记录变更、保留旧配置）。

> 🔑 **镜像基线 = 主机基线**；容器不是法外之地。

## 自检

**Q1** 为什么 “加固一次” 没用？

▸ 答案：因为环境会**持续产生新的默认配置**：新装机、新镜像、新扩缩容节点都会回到 “发行版默认”。只有把基线写进镜像/启动脚本 + 定期复测，才能保持在 “加固后” 的状态。

**Q2** “禁 root 远程登录” 为什么是收益最高的一项？

▸ 答案：因为互联网上的暴力破解**主要打 root**：禁用后攻击面立即缩小，且强制使用普通账号 + sudo 后，操作可审计、权限可细分。成本很低（配置一行），收益很高（阻断大部分自动化爆破）。

**Q3** 内核参数加固的常见项有哪些？

▸ 答案：`randomize_va_space=2`（ASLR）、`kptr_restrict=2`（隐藏内核符号）、`net.ipv4.ip_forward=0`（非路由器不转发）、`net.ipv4.conf.all.accept_redirects=0`（禁 ICMP 重定向）、`kernel.dmesg_restrict=1`（限制 dmesg 读取）。

**Q4** 容器基线要额外注意什么？

▸ 答案：四条：**非 root 运行**（`runAsNonRoot`）、**只读根文件系统**（`readOnlyRootFilesystem`）、**禁止特权/提权**（`allowPrivilegeEscalation: false`、`privileged: false`）、**能力最小化**（`drop: [ALL]`）。容器默认的宽松配置和主机一样危险。

**Q5** 一刀切基线会带来什么问题？

▸ 答案：会**误伤业务**：比如关掉 IP 转发导致容器网络不通、限制文件权限导致应用起不来。正确做法是 “基线分层”：所有主机共用的最小集 + 按角色（数据库/网关/容器节点）的额外项，并允许 “有评审的例外”。

**Q6** 加固后如何验证 “真的生效”？

▸ 答案：三条：**脚本复测得分**（应接近 100%）、**外部扫描**（端口/漏洞扫描对照）、**攻击面复核**（从外网能否访问管理端口）。只看 “配置文件改了” 不够，要看 “实际行为”。

**Q7** 基线与等保/合规是什么关系？

▸ 答案：基线是**合规的技术落地**：等保的 “身份鉴别、访问控制、入侵防范” 等控制项，最终都要落到具体配置。先把基线做扎实，测评时 “技术项” 才有证据；反之，只写制度不改配置，测评过不了（见 [3.1 等级保护与网络安全法](../../需求/3-行业合规与外部约束/3.1-等级保护与网络安全法.md)）。
