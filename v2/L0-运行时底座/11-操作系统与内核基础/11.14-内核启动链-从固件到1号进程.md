# 11.14 内核启动链：从固件到 1 号进程

## 一句话

> 从按下电源到能接系统调用，中间是五段接力——固件找引导器、引导器装内核、内核建起内存与调度、initramfs 换到真根、1 号进程拉起 target；每段失败的长相不同，排障第一步是认出停在哪一段，而容器共享宿主内核，这五段一段都没有。

## 定位：五段接力，五种失败长相

切段的意义不在背流程，而在故障现场：屏幕、串口、`dmesg` 停在哪个痕迹上，就只查那一段。把 `dracut` 超时当磁盘坏、把 `grub>` 当内核崩，是这类事故里最常见的两次误判。

| 段 | 谁在执行 | 关键动作 | 失败表现 | 现场证据 |
|---|---|---|---|---|
| 固件 | 主板 ROM 里的 BIOS，或主板上的 UEFI 固件 | 上电自检、枚举设备、按启动顺序找第一个可引导设备 | 黑屏无输出、蜂鸣、卡厂商 logo、`No bootable device` | 只有显示器或带外控制台，此时还没有 `dmesg` |
| 引导器 | `boot.img` → `core.img` → `grub.cfg` | 把内核与 initramfs 读进内存、把 cmdline 交给内核 | 停在 `grub>`/`grub rescue>`、`error: unknown filesystem`、`file not found`、菜单超时后不动 | 屏幕停在 GRUB 菜单或 `grub>` 提示符 |
| 内核 | vmlinuz 的自解压头 + `start_kernel` | 解压、`setup_arch` 解析 cmdline 与内存布局、建内存/调度/VFS、`rest_init` 造 0/1/2 号进程 | 卡在 `Loading Linux ...`、`Kernel panic - not syncing`、始终没有 `Linux version` 行 | `dmesg` 第一条时间戳仍是 `[ 0.000000]` |
| initramfs 与根切换 | initramfs 里的 `/init`（通常由 dracut 生成） | 加载存储与网络驱动、按 `root=` 找到真根、`switch_root` 过去 | `dracut-initqueue timeout`、`Cannot open root device`、停在 `dracut:/#` | `Warning: /dev/disk/by-uuid/... does not exist` 加一个 `dracut:/#` 提示符 |
| 1 号进程与 target | 真根上的 `/sbin/init`（systemd） | 并行拉起 unit、走到 `default.target`、起 getty 与 sshd | `emergency mode`、`Failed to start ...`、login 循环、起来但服务没起 | `systemctl --failed`、`systemd-analyze` |

三条分界判据，按顺序套：

- 有没有 `Linux version` 这一行？没有，问题在固件、引导器或解压段，内核还没接管。
- 有没有 `dracut` 字样或 `dracut:/#` 提示符？有，问题在根切换段，内核已经跑起来了。
- 有没有 `Reached target` 或 login 提示？有，五段都过了，问题在 unit 配置或应用本身。

`dmesg` 的第一条时间戳恒为 `[ 0.000000]`，那是内核自己的时钟起点——固件与引导器花掉的时间根本不在 `dmesg` 里，只出现在 `systemd-analyze` 的 firmware 与 loader 两段。

## x86：开机那几秒跑在实模式里

上电复位把 `CS` 置 `0xFFFF`、`IP` 置 `0x0000`，合成地址 `0xFFFF0`。x86 把 1MB 空间最上面 `0xF0000`–`0xFFFFF` 这 64KB 映射给 ROM，这条地址正好落在 ROM 里，那里只有一条 `JMP`，跳到 BIOS 的初始化代码。

实模式的寻址规则是「段基址 ×16 + 偏移」：段寄存器 16 位、偏移 16 位，左移四位拼出 20 位，地址总线只有 20 根，能区分的地址就是 `2^20 = 1MB`；偏移只有 16 位，单段最大 `2^16 = 64KB`。这套规则是为 8086 留的兼容层，现代 CPU 上电仍从这里开始。

保护模式换掉的是「段基址从哪来」：段寄存器不再存基址，而是存 GDT 里的选择子（描述符下标），真基址在描述符里，取到后缓存在 CPU 的描述符高速缓存器；同时打开分页，地址总线放到 32 位（`2^32 = 4GB`），并打开 Gate A20 让第 21 根地址线真正生效——不打开，超过 1MB 的访问会绕回低端。特权级也在这里落地：内核跑 ring 0，用户程序跑 ring 3，用户态执行特权指令被硬件拒绝。

32/64 位内核必须先做模式切换，原因有三条：实模式只有 1MB，压缩内核加解压后的映像放不下；没有分页，就给不出每个进程独立的地址空间；64 位还要再进 long mode（PAE + `EFER.LME` + 开分页）。GRUB 的 `lzma_decompress.img` 在解压前调用 `real_to_prot`，切完保护模式才敢把 `kernel.img` 摊开——这是引导器的活，不是内核的活。

UEFI 把前面这段「实模式 + 中断调用」整体换成了固件里的应用环境：

| 维度 | BIOS（Legacy） | UEFI |
|---|---|---|
| 固件接口 | `INT 10h`/`INT 13h` 等实模式中断 | EFI 协议与运行期服务，引导器是个 `.efi` 程序 |
| 分区表 | MBR：446 字节引导代码 + 4 个主分区，32 位 LBA 卡在 2TiB | GPT：默认约 128 个分区项，大盘不受 2TiB 限制 |
| 引导物 | 第一个扇区 512 字节，末尾 `0xAA55` | ESP（FAT32）上的 `.efi` 文件，路径登记在 NVRAM |
| GRUB 形态 | `boot.img` + `core.img` | `grubx64.efi` + `grub.cfg` |
| 判断方法 | `/sys/firmware/efi` 不存在 | `/sys/firmware/efi` 存在；`efibootmgr` 有输出 |
| 安全启动 | 无 | Secure Boot 只加载签名过的 shim 与 grub |

判断一台机器是不是 UEFI 启动，看 `/sys/firmware/efi` 在不在，比看分区表可靠。实测（Alpine 3.20 容器，宿主内核 `7.0.14-linuxkit`，aarch64）：

```console
$ ls /sys/firmware/efi 2>&1
ls: /sys/firmware/efi: No such file or directory
$ ls /sys/firmware
devicetree
fdt
$ efibootmgr
EFI variables are not supported on this system.
```

这台宿主是 aarch64 虚拟机，用设备树而不是 UEFI，所以 `/sys/firmware` 下只有 `devicetree` 和 `fdt`。容器里读到的设备树同样是宿主的，与容器自身无关。

## 引导器：512 字节的门卫和它叫来的管理处

BIOS 干完自检只认一件事：第一个扇区 512 字节、最后两字节是 `0xAA55`，就把这 512 字节读到 `0x7C00` 执行。GRUB2 把自己切成刚好能塞进这个约束的几块：

| 组件 | 大小与位置 | 谁加载 | 干什么 |
|---|---|---|---|
| `boot.img` | 512 字节，MBR 第一个扇区，由 `boot.S` 编译 | BIOS 读到 `0x7C00` | 只干一件事：加载 `core.img` 的第一个扇区 |
| `diskboot.img` | `core.img` 的第一个扇区，代码在 `diskboot.S` | `boot.img` | 把 `core.img` 的其余部分搬进内存 |
| `lzma_decompress.img` | `core.img` 内，代码在 `startup_raw.S` | `diskboot.img` | 解压前调用 `real_to_prot` 切实模式→保护模式、开 Gate A20 |
| `kernel.img` + 模块 | `core.img` 内，`startup.S` 加一堆 C 文件 | `lzma_decompress.img` | 这是 GRUB 自己的内核：`grub_main` 读配置、显示菜单、执行条目 |
| `grub.cfg` | `/boot/grub2/grub.cfg`（RHEL 系） | `grub_load_config()` | 菜单项、内核路径、cmdline、initramfs 路径 |

`grub.cfg` 里真正干活的是两行：

```ini
menuentry 'RHEL 9' {
  linux /vmlinuz-5.14.0-362.el9.x86_64 root=/dev/mapper/rl-root ro crashkernel=1G-4G:192M
  initrd /initramfs-5.14.0-362.el9.x86_64.img
}
```

`linux` 行的第一个参数是内核镜像路径（相对 `/boot`），后面所有内容原样进 `/proc/cmdline`；`initrd` 行只给路径，内核把那个文件解到内存里的 rootfs。原案例机器是 2019 年的 CentOS 7、内核 `3.10.0-862.el7`，同一份配置里写的是 `linux16`/`initrd16`——BIOS 下走 16 位入口的旧写法，EFI 下是 `linux`/`initrd`。

改启动项有四条路，别用错工具：

| 工具 | 改什么 | 生效时机 | 适用场景 |
|---|---|---|---|
| `grub2-mkconfig -o /boot/grub2/grub.cfg` | 读 `/etc/default/grub` 与 `/etc/grub.d/*`，重生成整个 `grub.cfg` | 下次启动 | 改全局默认参数（`GRUB_CMDLINE_LINUX`） |
| `grubby` | RHEL 8/9 上改 BLS 条目 `/boot/loader/entries/*.conf` | 下次启动 | 给某个或全部内核加删参数、换默认内核 |
| `efibootmgr` | 改 NVRAM 里的启动项顺序与下一个启动项 | 下次启动 | 多系统、换启动盘、固件把 Windows 排到前面 |
| `update-grub` | Debian/Ubuntu 的包装脚本，等价于生成 `/boot/grub/grub.cfg` | 下次启动 | Debian 系 |

RHEL 8/9 上有个容易踩的层叠：`grub.cfg` 由 `grub2-mkconfig` 生成，但真正的内核条目在 BLS 目录里，`grubby` 改的是 BLS。直接手改 `grub.cfg` 能被下一次 `grub2-mkconfig` 覆盖，也能被 BLS 条目的优先级压掉。

改坏了怎么救，按坏的程度分三档：

```console
grub> linux /vmlinuz-5.14.0-362.el9.x86_64 root=/dev/mapper/rl-root ro
grub> initrd /initramfs-5.14.0-362.el9.x86_64.img
grub> boot
```

这就是「`grub>` 手敲三行」：`linux` 给内核与参数，`initrd` 给初始内存盘，`boot` 交棒。路径用 Tab 补全，`ls (hd0,gpt2)/boot/` 先确认内核文件名；提示找不到文件时先补一句 `set root=(hd0,gpt2)` 再敲这三行。菜单都出不来、直接掉到 `grub rescue>` 时，还差一步重建环境：`set prefix=(hd0,gpt2)/boot/grub`、`insmod normal`、`normal`，回到 `grub>` 再敲上面三行。

更彻底的两档：用 Live CD 或安装介质进 Rescue 模式，`chroot /mnt/sysroot` 后跑 `grub2-install /dev/sda` 加 `grub2-mkconfig -o /boot/grub2/grub.cfg`，把引导器整个重装；只想进系统改配置，就在 `linux` 行末加 `rd.break`，启动停在 initramfs，依次 `mount -o remount,rw /sysroot`、`chroot /sysroot`、改文件、SELinux enforcing 时补 `touch /.autorelabel`、`exit` 两次继续启动。

## 内核：从 start_kernel 到 execve("/sbin/init")

vmlinuz 前头挂着自解压头，解压完跳进 `init/main.c` 的 `start_kernel`——内核的 main 函数。里面是一串 `XXXX_init`：

| 阶段 | 函数 | 关键动作 | 起不来时看到什么 |
|---|---|---|---|
| 解压 | 自解压头 | 校验并解压内核到内存 | 卡在 `Loading Linux ...`，永远没有 `Linux version` |
| 入口 | `start_kernel` | 用 `init_task` 立起 0 号进程，`set_task_stack_end_magic(&init_task)` | 极早期 panic，只有串口能看到 |
| 架构 | `setup_arch` | 解析 cmdline、读 e820 或设备树拿内存布局、建早期页表 | 内存识别错，后续表现为找不到设备或莫名 OOM |
| 中断 | `trap_init` | 建中断门；`set_system_intr_gate(IA32_SYSCALL_VECTOR, entry_INT80_32)` 就是 32 位系统调用的门 | 系统调用打到错误入口，表现为段错误 |
| 内存 | `mm_init` | 物理页分配器、SLUB、vma 缓存 | 分配器起不来，后面全部失败 |
| 调度 | `sched_init` | 运行队列、调度类、0 号进程的上下文 | 卡死在一个核上 |
| 文件系统 | `vfs_caches_init` | `mnt_init` → `init_rootfs` → `register_filesystem(&rootfs_fs_type)`，建 rootfs | 没有 rootfs，initramfs 无处可挂 |
| 收尾 | `rest_init` | `kernel_thread(kernel_init, ...)` 造 1 号，`kernel_thread(kthreadd, ...)` 造 2 号 | `Kernel panic: No init found` |

三个特殊进程的身份要分清：0 号 `init_task` 是唯一没经过 `fork` 或 `kernel_thread` 的，是进程列表的第一项；1 号是用户态所有进程的祖先；2 号 `kthreadd` 是所有内核线程的祖先。

启动日志的第一行时间戳就是内核时钟的零点，格式是 `[ 秒.微秒 ]`，从内核接管那一刻开始单调计数：

```console
$ dmesg | head -5
[    0.000000] Booting Linux on physical CPU 0x0000000000 [0x610f0000]
[    0.000000] Linux version 7.0.14-linuxkit (root@buildkitsandbox) (gcc (Alpine 15.2.0) 15.2.0, GNU ld (GNU Binutils) 2.45.1) #1 SMP PREEMPT Fri Oct 16 11:55:50 UTC 2026 ()
[    0.000000] OF: reserved mem: Reserved memory: No reserved-memory node in the DT
[    0.000000] psci: probing for conduit method from DT.
[    0.000000] psci: PSCIv1.1 detected in firmware.
$ dmesg | grep -m1 'Linux version'
[    0.000000] Linux version 7.0.14-linuxkit (root@buildkitsandbox) (gcc (Alpine 15.2.0) 15.2.0, GNU ld (GNU Binutils) 2.45.1) #1 SMP PREEMPT Fri Oct 16 11:55:50 UTC 2026 ()
```

方括号里是「距内核启动」而不是墙钟时间，所以固件与引导器耗掉的那十几秒在 `dmesg` 里看不见；`dmesg -T` 会换算成墙钟，但它对早期日志只能按当前时间倒推，误差随运行时长变大。`Linux version` 这一行同时带出编译机、编译器版本与编译时间——判断「线上跑的是不是你以为的那个内核」，看这行比看 `uname -r` 更全。

一个常被忽略的接缝：`kernel_init` 里会调 `kernel_init_freeable()`，而驱动初始化（`do_basic_setup` → `do_initcalls`）就跑在这条路径上。也就是说「内核初始化」的尾巴和 1 号进程是同一个上下文，1 号进程先以内核线程的身份把驱动 initcall 跑完，才 execve 到用户态。

从内核态跨到用户态的那一步，走的是系统调用的后半段：`run_init_process` → `do_execve` → `do_execveat_common` → `exec_binprm` → `search_binary_handler` → `load_elf_binary` → `start_thread`。`start_thread` 把 `pt_regs` 里的 `CS` 设成 `__USER_CS`、`DS` 设成 `__USER_DS`，填好 `IP` 与 `SP`，`force_iret` 一执行，下一条指令就在用户态了。`kernel_init` 的候选顺序是 `/init`（ramdisk）、`/sbin/init`、`/etc/init`、`/bin/init`、`/bin/sh`，起来一个就算成功。

initramfs 存在的理由很朴素：init 程序在文件系统上，文件系统在存储设备上，访问存储设备要驱动。把所有存储驱动都编进内核，内核就太大了。解法是先给一个基于内存的文件系统——内存访问不需要驱动——把它当临时根，运行里面的 `/init`；`/init` 按存储类型加载驱动，找到真根，切过去。

根切换有个容易记错的细节：设计上叫 `pivot_root`，实现上 dracut 用的是 `switch_root`。原因是 initramfs 是 rootfs（内核自己挂的内存文件系统），`pivot_root` 不允许把 rootfs 当新根，只能先 `mount --move` 把真根挪到 `/`、再 `chroot` 加 `exec` 换掉 1 号进程。

`root=` 这个参数也常被误解成「内核自己去挂根」。有 initramfs 时，内核只把 `root=` 留在 cmdline 里交给 `/init` 去解析；没有 initramfs 时，内核才在 `prepare_namespace` 里按 `root=` 自己挂。所以 `root=UUID=...` 写错，报错的是 initramfs 的 `/init`，不是内核的挂载代码。

排障入口就是 dracut 的 shell：`dracut:/#` 下能 `cat /proc/cmdline`、`ls /dev/disk/by-uuid/`、`blkid`；`rd.break` 停在切根之前，`rd.break=pre-mount` 停在挂真根之前，`rd.debug` 打开脚本级日志。想看 initramfs 里到底装了什么，在正常系统上跑 `lsinitrd /boot/initramfs-$(uname -r).img | head`，缺 `lvm`、`multipath`、`nvme` 这类模块就是超时的根因。

版本错配是另一类高频事故：内核升级了，initramfs 还是旧的。新内核里编进了新的存储驱动，旧 initramfs 里没有，启动就停在 `dracut-initqueue timeout`。判据是 `uname -r` 与 `lsinitrd` 里那个文件名对不对得上；另一种是升级时 `/boot` 写满，`vmlinuz` 被截断，表现成选完菜单就黑屏。`/boot` 单独分区给 1GB 是常见建议（经验值），装三四个内核再加大体积 initramfs 就会紧张。

## 启动的最后一步是能接系统调用

内核态与用户态之间没有函数调用，只有一道硬件门。用户态要访问核心资源，唯一合法入口是系统调用：请求进办事大厅，内核态代跑，跑完把结果和寄存器还回去。

| 维度 | 32 位 | 64 位 |
|---|---|---|
| 陷入指令 | `int $0x80` | `syscall` |
| 入口 | `entry_INT80_32`，由 `trap_init` 里的 `set_system_intr_gate` 注册 | `entry_SYSCALL_64`，地址写在 MSR `MSR_LSTAR`（`syscall_init` 里 `wrmsrl`） |
| 调用号 | `eax` | `rax` |
| 参数寄存器 | `ebx`/`ecx`/`edx`/`esi`/`edi`/`ebp` | `rdi`/`rsi`/`rdx`/`r10`/`r8`/`r9` |
| 入口动作 | `SAVE_ALL` 把用户态寄存器存进 `pt_regs` | 先把 `ss`/`sp`/`flags`/`cs`/`ip` 压栈，构造 `pt_regs` |
| 分发 | `do_syscall_32_irqs_on` 查 `ia32_sys_call_table` | `do_syscall_64` 查 `sys_call_table` |
| 返回 | `iret` | `sysretq` |

两边的表都来自同一处：`arch/x86/entry/syscalls/syscall_32.tbl` 与 `syscall_64.tbl` 经脚本生成 `unistd_*.h`，再被 `syscall_32.c`/`syscall_64.c` include 成函数指针数组。参数最多六个，所以内核侧只有 `SYSCALL_DEFINE1` 到 `SYSCALL_DEFINE6`。glibc 那层是中介：`syscalls.list` 记名字与参数，`syscall-template.S` 生成桩代码，桩里最后一条 `ENTER_KERNEL` 就是 `int $0x80` 或 `syscall`。

实测一次真实调用（Alpine 3.20 容器，`strace` 需临时安装）：

```console
$ strace -o /tmp/t -e trace=openat cat /proc/cmdline
$ head -2 /tmp/t
openat(AT_FDCWD, "/proc/cmdline", O_RDONLY|O_LARGEFILE) = 3
+++ exited with 0 +++
```

读一个启动参数，用户态只发了一条 `openat`，权限级别在 `syscall` 那条指令上换了一次。启动完成的判据也在这里：`/sbin/init` 自己就是 `execve` 出来的，它的第一条指令已经在用户态；此后 systemd 做的每件事——`clone`、`execve`、`mount`、`socket`、`bind`——都是系统调用。所以能打印 `Failed to start` 就说明门是通的，问题在 unit 配置或依赖，不在内核。

## 1 号进程与 systemd：启动链的最后一棒

1 号进程有三代实现，换代的动力都是「串行太慢」：

| init | 配置 | 启动方式 | 依赖怎么表达 | 代表系统 |
|---|---|---|---|---|
| SysVinit | `/etc/inittab` + `/etc/rc.d/rcN.d` | 按 runlevel 顺序执行脚本 | 脚本名里的 `S`/`K` 编号 | RHEL 5、Debian 7 之前 |
| Upstart | `/etc/init/*.conf` | 事件驱动，设备或网络事件触发 | `start on`/`stop on` | Ubuntu 6.10–14.10 |
| systemd | `/usr/lib/systemd/system/*.unit` + `/etc/systemd/system` | 按依赖图并行拉起，socket 与 dbus 可延迟激活 | `Requires=`/`Wants=`/`After=` | RHEL 7+、Debian 8+、Ubuntu 15.04+ |

unit 是 systemd 的配置单元，按后缀分类型：`.service` 是进程，`.socket` 是监听端口（有人连才拉起服务），`.target` 是「一组 unit 的锚点」，`.timer` 是定时器，`.mount` 是挂载点，`.slice` 是 cgroup 切片。target 替代了 runlevel：

| target | 近似旧 runlevel | 拉起什么 | 什么时候用 |
|---|---|---|---|
| `multi-user.target` | 3 | 多用户、无图形、sshd 与常规服务 | 服务器默认 |
| `graphical.target` | 5 | `multi-user.target` 加显示管理器 | 桌面 |
| `rescue.target` | 1 | 挂本地文件系统、基本服务、`sulogin` | 单用户排障 |
| `emergency.target` | 无对应 | 只读根、只有 `sulogin` | 根文件系统坏到不能正常挂 |

三个读法各管一件事：

```bash
systemd-analyze                      # 五段时间：firmware / loader / kernel / initrd / userspace
systemd-analyze blame | head -10     # 按耗时倒序的 unit 榜，回答「谁最慢」
systemd-analyze critical-chain       # 关键路径链，回答「谁挡在 default.target 前面」
```

| 输出段 | 从哪到哪 | 数字大了说明什么 |
|---|---|---|
| firmware | 上电到交棒给引导器 | 固件自检、RAID 卡初始化、网卡 PXE 超时 |
| loader | 引导器读到内核与 initramfs | 内核或 initramfs 太大、`/boot` 在慢盘上 |
| kernel | 内核入口到 `init` | 驱动 probe、大内存清零、页表初始化 |
| initrd | initramfs 起到 `switch_root` | 等设备、多路径、网络根（iSCSI/NFS） |
| userspace | 1 号进程起到 `default.target` | unit 依赖串行、网络等待、cloud-init |

1 号进程还有两个与容器直接相关的特殊性：它要回收所有孤儿进程（别人 `exit` 后父进程不在了，就挂到它名下），并且它收到的信号默认不按常规处理——给 PID 1 发 `SIGTERM` 而不装处理器，进程不会退出。应用进程当 PID 1 时常常既不回收僵尸也不响应信号，所以 `docker run --init` 会塞一个 tini 进去补这两件事。

实测（Alpine 3.20 容器里 PID 1 就是被 exec 的那个程序，不是 systemd）：

```console
$ cat /proc/1/comm
sh
$ cat /proc/1/cgroup
0::/
$ ps -p 1 -o pid,comm,args
    PID COMMAND         COMMAND
      1 sh              sh -c  apk add --no-cache procps util-linux ...（参数列已截断）
$ ls -l /sbin/init
lrwxrwxrwx    1 root     root            12 Apr 15  2026 /sbin/init -> /bin/busybox
$ systemd-analyze 2>&1 | head -2
sh: systemd-analyze: not found
```

Alpine 用 busybox init 或 OpenRC，没有 systemd，`systemd-analyze` 在这里必然缺席；`systemd-analyze` 的五个数字只存在于 systemd 主机上，容器里既没有 systemd 在跑，也没有那次启动可量。

## 一次启动的时间预算（量级）

下表是量级参考，不是实测：同一段在不同硬件上能差一个数量级，带 RAID 卡加 PXE 的机器光固件就能吃掉半分钟。

| 段 | 典型量级 | 什么会让它翻倍 | 怎么看 |
|---|---|---|---|
| 固件 | 5–30 秒 | RAID 卡初始化、PXE 超时、内存自检 | 带外控制台；`systemd-analyze` 的 firmware 段 |
| 引导器 | 1–3 秒 | 内核与 initramfs 在慢盘、菜单等待时间过长 | 菜单超时设置；loader 段 |
| 内核 | 1–5 秒 | 驱动 probe、大内存清零、`crashkernel` 预留 | `dmesg` 时间戳；kernel 段 |
| initramfs | 3–40 秒 | 等设备、多路径、网络根、`udev` 收敛慢 | `rd.debug` 日志；initrd 段 |
| 1 号进程 | 5–60 秒 | unit 串行、等网络、cloud-init 超时、包管理锁 | `blame` 与 `critical-chain`；userspace 段 |

「启动 10 分钟」这类抱怨，第一步是拿到五段的拆分数据：systemd 机器上一行 `systemd-analyze` 就够；没有 systemd 的（Alpine/OpenRC、嵌入式）用 `dmesg` 首末时间戳加 `rd.debug` 手工分段。拿着总分去猜，猜错的概率比猜对高。

## 七个启动参数：真正影响线上架构的那几个

内核参数写在 `linux` 行里，最终都汇总到 `/proc/cmdline`。下面七条是架构层面真正会改变行为、而不是只影响观感的：

| 参数 | 写什么值 | 影响什么 | 在哪验证 | 风险与注意 |
|---|---|---|---|---|
| `systemd.unified_cgroup_hierarchy` | `=1`，配 `cgroup_no_v1=all` | 切到 cgroup v2 统一层级；k8s 的 Pod 配额、`memory.max`、`cpu.weight` 都依赖它 | `mount \| grep cgroup` 看到 `cgroup2`；`/sys/fs/cgroup/cgroup.controllers` | 老监控脚本读 v1 路径会全空；容器运行时与 kubelet 的 cgroup driver 要一起切 |
| `intel_iommu` / `iommu` | `intel_iommu=on iommu=pt` | 开 DMA 重映射，是 VFIO 直通与 SR-IOV 的前置；`pt` 让未分配给虚拟机的设备走恒等映射，少一层翻译 | `ls /sys/kernel/iommu_groups/` 有编号目录；`dmesg \| grep -i DMAR` | 某些老设备 DMA 不规矩，开了会报 `DMAR fault`；`pt` 只对宿主设备降开销，直通设备仍走完整翻译 |
| `numa` / `numa_balancing` | `numa=off`，或 `numa_balancing=0` | 关掉 NUMA 感知（当成单节点）或关掉自动迁移；影响容量评估口径与跨节点访问 | `numactl --hardware` 的 node 数；`/proc/sys/kernel/numa_balancing` | `numa=off` 会让大机型的内存延迟变均匀但变差，压测基线要重做；云主机的 vNUMA 与物理 NUMA 不是一回事 |
| `transparent_hugepage` | `=never` 或 `=madvise` | 关掉或收窄透明大页；THP 的 `khugepaged` 与内存规整会造成延迟尖刺 | `/sys/kernel/mm/transparent_hugepage/enabled` 与 `defrag` | 直接 `never` 会让 TLB 覆盖变差、某些负载反而变慢；数据库一般用 `madvise` 加显式 HugePages |
| `mitigations` | `=off`，或 `=auto,nosmt` | 关掉 Spectre/Meltdown 一类侧信道缓解（PTI、IBRS、retpoline 等） | `/sys/devices/system/cpu/vulnerabilities/*` 从 `Mitigation: ...` 变成 `Vulnerable` | 这是拿安全换性能：同机多租户、能跑不可信代码的环境不能用；收益随 CPU 代际与负载变化，必须实测 |
| `panic` / `panic_on_oops` | `panic=0`（默认不重启）或 `panic=10`；`panic_on_oops=1` | 内核崩溃后是否自动重启、oops 是否升级为 panic | `/proc/sys/kernel/panic`、`/proc/sys/kernel/panic_on_oops` | `panic=0` 加无人值守等于宕机不自愈；`panic=10` 遇启动期崩溃会变成重启循环，要配引导器的回退项 |
| `console` / `loglevel` | `console=ttyS0,115200n8 loglevel=7`，排障时加 `ignore_loglevel` | 内核日志往哪写、控制台打到什么级别 | `cat /proc/consoles`；`dmesg` 里的 `Kernel command line:` 行 | `loglevel` 只影响控制台输出，不改 `dmesg` 缓冲区；云上要确认串口控制台真的开了，否则等于没配 |

实测的 cmdline 来自宿主 VM，不是容器自己配的：

```console
$ cat /proc/cmdline
init=/initd loglevel=1 root=/dev/vdb rootfstype=erofs ro vsyscall=emulate panic=0 eth0.dhcp eth1.dhcp linuxkit.unified_cgroup_hierarchy=1 console=hvc0   virtio_net.disable_csum=1 slub_min_order=2 page_reporting.page_reporting_order=2 vpnkit.connect=connect://2/1999 com.docker.VMID=5b071a28-f327-4853-9055-2faed38d9e9f
$ dmesg | grep -i -m2 "command line"
[    0.000000] Kernel command line: init=/initd loglevel=1 root=/dev/vdb rootfstype=erofs ro ...
[    0.000000] Unknown kernel command line parameters "vsyscall=emulate", will be passed to user space.
```

这一行本身就是一份教学样本：`root=/dev/vdb` 指向一块 566484 KiB 的只读 erofs 映像（`rootfstype=erofs ro`），`init=/initd` 是 Docker Desktop 自己的 init，`console=hvc0` 是虚拟化串口，`loglevel=1` 把控制台压到只剩紧急消息，`panic=0` 表示崩了不自动重启，`linuxkit.unified_cgroup_hierarchy=1` 是它切 cgroup v2 的方式。最后那条 `Unknown kernel command line parameters` 说明内核不认识 `vsyscall=emulate`，把它原样传给用户态——cmdline 是不校验的字符串通道，写错不报错，只是静默无效。

cgroup v2 这条值得单独说：k8s 1.25 起（KEP-2254）cgroup v2 支持 GA，前提是节点内核与 systemd 都按 v2 跑。验证不要只看 `stat -f`，busybox 的 `stat` 会给出 `UNKNOWN`，直接看挂载类型：

```console
$ mount | grep cgroup
cgroup on /sys/fs/cgroup type cgroup2 (rw,nosuid,nodev,noexec,relatime)
$ cat /sys/fs/cgroup/cgroup.controllers
cpuset cpu io memory hugetlb pids rdma
```

THP 与 panic 的现场值（同一个容器）：

```console
$ cat /sys/kernel/mm/transparent_hugepage/enabled
[always] madvise never
$ cat /sys/kernel/mm/transparent_hugepage/defrag
always defer defer+madvise [madvise] never
$ cat /proc/sys/kernel/panic /proc/sys/kernel/panic_on_oops
0
1
$ cat /proc/consoles
hvc0                 -W- (EC  p  )  229:0
```

方括号是当前生效值：这台 VM 的 THP 是 `always`，`defrag` 是 `madvise`；`panic=0` 而 `panic_on_oops=1`，即不自动重启但一 oops 就 panic。四个 `/sys` 或 `/proc` 读数都在容器里读到了宿主的值——参数作用在内核上，内核是共享的。

`panic=` 只管「崩了之后机器怎么办」，不管「崩了之后谁取证」。要拿到 vmcore，得靠 kexec：panic 时在内存里直接启动第二个内核（捕获内核），由它把第一个内核的内存写出去。这就是引导器那行 `crashkernel=1G-4G:192M` 的来历——给捕获内核预留 192MB，内存 1–4GB 的机型按这个尺寸留。验证看 `cat /sys/kernel/kexec_crash_loaded` 是否为 1、`systemctl status kdump` 是否正常；没配 kdump 的机器上，`panic=10` 只会安静地重启，事故现场一次丢光。

反过来，这台机器上 IOMMU 与 NUMA 的验证点是缺失的：

```console
$ ls /sys/kernel/iommu_groups
ls: /sys/kernel/iommu_groups: No such file or directory
$ cat /proc/sys/kernel/numa_balancing
cat: can't open '/proc/sys/kernel/numa_balancing': No such file or directory
```

arm64 虚拟机没开 IOMMU、也没有 NUMA 拓扑，对应接口就不存在。这提醒一件事：验证启动参数是否生效，要在宿主或机型上做，容器只提供只读的一瞥。

## 容器为什么没有这一段

容器共享宿主内核，五段里后四段（引导器、内核、initramfs、1 号进程）一段都没有，第一段固件更不存在。逐条对照实测：

```console
$ uname -r
7.0.14-linuxkit
$ ls /boot
ls: /boot: No such file or directory
```

`uname -r` 报的是宿主内核，`/boot` 在容器里连目录都不存在——启动链要的 `vmlinuz`、`initramfs`、`grub.cfg` 一个都不在容器的文件系统里。

| 问题 | 容器里的答案 | 说明 |
|---|---|---|
| `/proc/cmdline` 是谁的 | 宿主 VM 的 | `init=/initd root=/dev/vdb ...` 那行就是证据 |
| `/proc/uptime` 是谁的 | 宿主 VM 的，`35.77` 秒 | 容器刚起不到一秒，读到的却是 VM 的运行时长 |
| 有没有固件 | 没有 | `/sys/firmware` 下只有宿主设备树 `devicetree`/`fdt`，无 `efi` |
| 有没有 `/boot` | 没有 | `ls /boot` 直接 `No such file or directory` |
| 1 号进程是谁 | 被 exec 的那个程序 | 本次是 `sh`，`/proc/1/cgroup` 为 `0::/` |
| `/` 是什么 | overlay | `mount` 第一行是 `overlay on / type overlay`，lowerdir 指向镜像层 |
| 能不能看到块设备 | 能，但不拥有 | `/proc/partitions` 有 `vda`/`vda1`/`vdb`，`/` 仍是 overlay |

容器的启动是三步：解镜像层并用 overlay 挂成根、`clone` 出 namespace、`exec` entrypoint。没有自检、没有 MBR、没有解压、没有 `switch_root`。所以「容器启动慢」这个问题的排查面完全不同：镜像层数与大小、存储驱动与解压、cgroup 配额（`--cpus`/`--memory`）、entrypoint 里的等待逻辑。[11.12 虚拟化开销](11.12-虚拟化开销-CPU-内存-IO的三处损耗.md) 里那个 Tomcat 冷启动 22 秒的案例，根因是 `--cpus 0.1` 让线程 `%wait` 到 97%，与 BIOS、GRUB、内核初始化没有任何关系。

有三件事在容器里做不到，只能回到节点：改内核参数（改完要重启节点）、换 IO 调度器或 THP 策略（节点级）、修内核 CVE（共享内核，只能换节点内核或换运行时）。唯一有自己启动链的容器形态是 microVM——Kata、Firecracker 这类给每个 Pod 一个极简 guest 内核，启动链被砍到毫秒级，但那是虚拟化，不是容器。

## 症状 → 卡在哪一段

| 症状 | 卡在哪段 | 第一步看什么 | 常见根因 |
|---|---|---|---|
| 按电源键无输出、蜂鸣、卡厂商 logo | 固件 | 显示器、带外管理口、主板诊断灯 | 内存/显卡没插好、RAID 卡自检、固件设置被改 |
| `No bootable device` | 固件→引导器 | 启动顺序、`lsblk` 看盘在不在 | 启动盘顺序错、盘掉线、装机后没写引导 |
| 直接掉进 `grub>` 或 `grub rescue>` | 引导器 | `ls (hd0,gpt2)/boot/` 能否列出内核 | `grub.cfg` 写坏、升级内核后路径变了、`/boot` 分区没挂上 |
| 选完菜单黑屏，始终没有 `Linux version` | 内核解压段 | 串口输出、`vmlinuz` 大小与校验 | 内核映像损坏、`/boot` 分区满导致写入截断 |
| `Kernel panic - not syncing: VFS: Unable to mount root fs` | 内核→根切换 | `root=` 的值与 `/dev/disk/by-uuid/` | `root=` 写错、根分区换过 UUID、initramfs 缺存储驱动 |
| 卡 `dracut-initqueue timeout`、`/dev/disk/by-uuid/... does not exist` | initramfs | `dracut:/#` 下 `blkid`、`lsinitrd` 看模块 | initramfs 缺 `lvm`/`multipath`/`nvme` 模块、多路径没起、盘序变了 |
| 停在 `Give root password for maintenance` 或 `emergency mode` | 1 号进程 | `systemctl --failed`、`journalctl -xb` | `/etc/fstab` 有挂不上的条目、根分区只读、unit 依赖失败 |
| 起来了但没网、服务没起 | 1 号进程（target 之后） | `systemctl status <unit>`、`ip addr` | unit 没 enable、网卡改名、防火墙、依赖顺序 |
| 启动要 10 分钟 | 分段计时 | `systemd-analyze` 与 `blame` | 等网络（`NetworkManager-wait-online`）、`cloud-init` 超时、`/boot` 在慢盘 |
| 起来了但 cgroup 只有 v1 | 启动参数 | `mount \| grep cgroup`、`/proc/cmdline` | 没加 `systemd.unified_cgroup_hierarchy=1`、systemd 太旧、容器运行时没切 driver |
| 容器里读到的 cmdline 是别人的 | 不是故障 | `/proc/cmdline`、`/proc/1/cgroup` | 架构事实：共享宿主内核，要改参数得改节点 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 在容器里 `cat /proc/cmdline` 判断「这台机器的内核参数」 | 读到的是宿主 VM 的，改错对象；容器里改不了，也验证不了节点配置 |
| 直接编辑 `/boot/grub2/grub.cfg` 加参数 | 下一次 `grub2-mkconfig` 或 BLS 条目覆盖，重启后参数消失，排查方向被带偏 |
| 为了性能随手加 `mitigations=off` 且不记录 | 侧信道面扩大，同机不可信负载可直接利用；合规审计时说不清 |
| 无人值守机器保留 `panic=0` | 内核崩了不重启，服务一直躺到有人发现；监控只看到「进程没了」 |
| 只在当前 shell 里 `echo never > .../enabled` 就以为关了 THP | 重启即失效；容量与延迟基线按错的假设做 |
| 看到 `dracut` 超时就换盘、重建 RAID | 多数超时是 initramfs 缺模块或 `root=` 错，换盘不解决，还多一次数据风险 |
| 在容器里装 `systemd-analyze` 量启动时间 | 容器里没有那次启动可量，读到的数字属于宿主；装了也只是 `not found` 或读不到 |

## 三条铁律

> 🔑 **排障先定位段，再查段内。** 判据只有三个：有没有 `Linux version`、有没有 `dracut` 提示、有没有 `Reached target`。段判错，后面所有命令都是白跑。

> 🔑 **启动参数属于内核，内核属于宿主或节点。** `/proc/cmdline`、`/sys/kernel/mm/*`、`/proc/sys/kernel/panic` 在容器里读到的是宿主值；要改就在节点上改，改完重启，再在节点上验。

> 🔑 **改启动参数必须同时准备回滚。** 备份 `grub.cfg`、保留旧内核、知道 `grub>` 三行怎么敲、知道 `rd.break` 怎么进——没有这四样，不要动 `linux` 行。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：RHEL 9 / CentOS Stream 9 上用 `grubby` 改参数、`grub2-mkconfig` 重生成、`systemd-analyze` 计时、`dracut` 重做 initramfs、`efibootmgr` 管 NVRAM；Debian/Ubuntu 用 `update-grub` 加 `/etc/default/grub`，配置在 `/boot/grub/grub.cfg`；容器场景不用这些工具，改节点。

**可抄**（RHEL 9，root 权限，`/boot` 可写）：

```bash
# 1. 留底：当前参数与配置文件
cat /proc/cmdline
cp -a /boot/grub2/grub.cfg /boot/grub2/grub.cfg.bak.$(date +%F)

# 2. 加参数：grubby 改 BLS 条目，不动 grub.cfg
grubby --update-kernel=ALL --args="intel_iommu=on iommu=pt"
grubby --default-kernel
grubby --info=ALL | grep -E '^(kernel|args)' | head -4

# 3. 只在改了 /etc/default/grub 或 /etc/grub.d 时才重生成
grub2-mkconfig -o /boot/grub2/grub.cfg

# 4. 重做 initramfs（改了存储/多路径驱动才需要）
dracut -f /boot/initramfs-$(uname -r).img $(uname -r)

# 5. 重启后验证：参数、THP、panic、cgroup
cat /proc/cmdline | tr ' ' '\n' | grep -E 'iommu|mitigations|transparent|panic'
cat /sys/kernel/mm/transparent_hugepage/enabled
cat /proc/sys/kernel/panic_on_oops
mount | grep cgroup

# 6. 计时
systemd-analyze
systemd-analyze blame | head -10
systemd-analyze critical-chain
```

**可验**：下面这段是在 Alpine 3.20 容器里真跑的输出（宿主内核 `7.0.14-linuxkit`，aarch64，8 vCPU），能验的只有「读」这一半——参数是否落到内核上，读 `/proc` 与 `/sys` 就能看见：

```console
$ cat /proc/cmdline
init=/initd loglevel=1 root=/dev/vdb rootfstype=erofs ro vsyscall=emulate panic=0 ... console=hvc0 ...（中间省略）
$ cat /sys/kernel/mm/transparent_hugepage/enabled
[always] madvise never
$ cat /proc/sys/kernel/panic /proc/sys/kernel/panic_on_oops
0
1
$ systemd-analyze 2>&1 | head -2
sh: systemd-analyze: not found
$ grub-mkconfig -o /tmp/grub.cfg 2>&1 | head -2
/usr/sbin/grub-probe: error: failed to get canonical path of `overlay'.
```

最后两条正是「启动链不在容器里」的实证：容器里没有 systemd 可量，也没有 `/boot` 与真实块设备可探测，`grub-probe` 连 `/` 的规范路径都拿不到（`/` 是 overlay）。

参数落地之后还有一件常被漏掉的事：把 `/proc/cmdline` 纳入节点基线巡检。它与 `/etc/default/grub` 里的期望值不是一回事——BLS 条目、`grubby` 的历史改动、发行版大版本升级都可能让两者分叉。巡检断言 `tr ' ' '\n' < /proc/cmdline | grep -qx 'iommu=pt'` 这类条件，比对着配置文件做 diff 可靠，也能顺手发现「参数写进了配置但根本没重启」。

**未验证**（容器内跑不了，需在 systemd 主机上执行）：`grubby`、`grub2-mkconfig`、`dracut`、`systemd-analyze` 这四样工具。缺的条件是：一台 RHEL 9 或同族、systemd 作为 1 号进程、`/boot` 可写且存在 BLS 条目的机器。预期输出形状：`grubby --default-kernel` 打印一个 `/boot/vmlinuz-*` 路径；`systemd-analyze` 打印一行 `Startup finished in ... (firmware) + ... (loader) + ... (kernel) + ... (initrd) + ... (userspace) = ...`；`systemd-analyze blame` 打印按耗时倒序的 unit 列表。

**可退**：

```bash
# 撤销参数：grubby 删除同名参数后重启
grubby --update-kernel=ALL --remove-args="intel_iommu iommu"
# 回滚配置：用留底覆盖，再重生成
cp -a /boot/grub2/grub.cfg.bak.$(date +%F) /boot/grub2/grub.cfg
# NVRAM 启动顺序改坏了：按原顺序重排（efibootmgr -v 里看四位编号）
efibootmgr -o 0001,0002,0000
```

引导器彻底起不来时，回退路径是安装介质的 Rescue 模式加 `chroot /mnt/sysroot`，或 `grub>` 手敲那三行；只改了内核参数进不去系统时，`rd.break` 进 initramfs，`mount -o remount,rw /sysroot` 后 `chroot /sysroot` 改回配置，SELinux enforcing 时补 `touch /.autorelabel`。改参数前给节点打快照或至少确认带外控制台可用——串口不通又改坏了 `console=`，就只能到机房接显示器。

## 自检

**Q1** 一台机器启动停在 `dracut-initqueue timeout`，屏幕上还有 `Warning: /dev/disk/by-uuid/... does not exist`。最可能的原因是什么？为什么此时改 `grub.cfg` 里的 `root=` 往往不是第一步？

▸ 答案：最常见的是 initramfs 里缺根设备需要的驱动或工具（`lvm`、`multipath`、`nvme`、`iscsi`），其次是根设备的 UUID 变了（重装、换盘、LVM 重建），再次是多路径或 SAN 链路没起来。改 `root=` 之前先确认「设备名字对不对」：在 `dracut:/#` 里 `blkid` 与 `ls /dev/disk/by-uuid/` 一看就知道是 UUID 变了还是设备根本没出现。设备没出现，改 `root=` 只会把错误换一种写法；要重做的是 `dracut -f` 补模块。

**Q2** 容器里 `cat /proc/cmdline` 读到 `root=/dev/vdb`、`console=hvc0`，能据此判断这台宿主的内核参数吗？能据此修改吗？

▸ 答案：能读，不能改，而且读到的确实是宿主（Docker Desktop 的 LinuxKit VM）的 cmdline——容器没有自己的内核，`/proc` 是宿主内核的视图。但「读到」不等于「这台业务节点的配置」：容器跑在哪个节点，就读到哪个节点的参数。修改必须回到节点改 `grubby`/`grub.cfg` 并重启；容器里既没有 `/boot`，也没有权限重建引导器。

**Q3** 容器冷启动要 8 秒，为什么不该去查 BIOS、GRUB 和内核初始化？该查什么？

▸ 答案：容器共享宿主内核，启动只有解镜像层、建 namespace、exec 三步，BIOS/GRUB/内核初始化在容器启动之前早已完成（它们是节点启动时的事）。8 秒该查：镜像层数与大小、是否要拉取、存储驱动与解压、cgroup 配额（`--cpus` 给小了线程在排队）、entrypoint 里的等待（连数据库、等配置中心）。[11.12 虚拟化开销](11.12-虚拟化开销-CPU-内存-IO的三处损耗.md) 的案例就是 `--cpus 0.1` 导致 `%wait` 97%，与固件无关。

**Q4** 为了把 p99 压下去，有人建议 `mitigations=off`。代价是什么？什么环境下直接否决？

▸ 答案：代价是关掉 Spectre/Meltdown 一类侧信道缓解（PTI、IBRS、retpoline 等），同机可运行的不可信代码可以利用这些通道读取本不该读的内存；收益随 CPU 代际与负载类型变化，量级从几个百分点到一成以上，必须在自己机型上实测。能跑多租户容器、能执行用户提交代码、或有过等保/合规要求的机器应直接否决；单租户、纯内网、性能瓶颈已定位在系统调用路径上的批处理机器才可以评估，并且要把这项写进变更记录。

**Q5** 假设某台机器 `systemd-analyze` 打出 `Startup finished in 12.1s (firmware) + 2.3s (loader) + 5.4s (kernel) + 40.2s (initrd) + 18.6s (userspace) = 78.6s`。哪一段最该先动，为什么不是 kernel 那段？

▸ 答案：先动 initrd 的 40.2 秒。initrd 段是 initramfs 从启动到 `switch_root`，时间几乎都花在等设备或等网络根上（多路径、iSCSI、SAN 链路、udev settle），这段长说明根设备出现得慢，与内核本身的初始化无关；kernel 5.4 秒在带大量驱动与内存的机器上属正常量级。firmware 12.1 秒也值得看（RAID 卡、PXE 超时），但它的可改空间通常小于 initrd。判据是「谁在等」：initrd 等在设备，userspace 等网络与 unit 依赖，kernel 在跑 probe。
