# 11.12 虚拟化开销：CPU、内存、IO 的三处损耗

## 一句话

> 同规格云主机比物理机慢，慢在三处可命名的损耗：CPU 慢在 **VM exit**（一次 IO、一次中断、一条敏感指令都要进出客户机一趟），内存慢在 **多一层地址翻译**（影子页表或 EPT 让 TLB 必须记两套映射），IO 慢在 **路径变长**（guest 协议栈 → virtio → 宿主协议栈 → 网卡）；判断该改代码还是该换机型，先看 `st` 和 exit 次数，别看 `%CPU`。

## 定位：三处损耗各在哪一层留下痕迹

先把三处损耗钉在具体机制上。三处各回答同一个问题的三个侧面：这处损耗怎么产生、在哪个指标上现形、什么负载被它伤得最重。

| 损耗点 | 机制 | 主要观测指标 | 受影响最大的负载 | 缓解手段 |
|---|---|---|---|---|
| CPU | VM exit 固定成本 + 宿主调度 | `st`、`sy`、`/proc/interrupts` 增量 | 高频小 IO、短连接、频繁中断 | 批处理、vhost、直通、绑核 |
| 内存 | 二级页表 + TLB 覆盖变小 | TLB miss、缺页次数、`st` 之外的延迟尖刺 | 大内存随机访问（JVM、数据库 buffer pool） | 大页、EPT、不跨 NUMA |
| IO | 路径长度 + 通知往返 | 每次 IO 的固定成本 × IOPS、`%sys` | 小包网络、4K 随机读 | virtio、vhost、SR-IOV |

> 🔑 虚拟化损耗的形态是「**每次操作加一笔固定成本**」，不是「整体乘一个折扣系数」。固定成本被操作次数放大：每秒 5 万次小 IO，每次只算 5 µs 的出入成本（量级推算），乘起来就是每秒 250 ms，相当于 0.25 个核被固定成本吃掉；而同一条链路上跑一次 1 GB 的顺序读，几乎感觉不到这笔成本。

## 虚拟化的本质问题：有一批指令不许你执行

操作系统上的程序分两种：用户态程序和内核态程序。为了区分两者，CPU 设置了四个特权等级 0、1、2、3。写 Linux 内核的时候，四级的富余被用得很大方：**内核态跑在第 0 级，用户态跑在第 3 级，中间两级空着**。用户态要动资源，就把扳手掰到第 0 级，用完再掰回去。

现在要在物理机上同时跑多个操作系统。站在 guest 内核的角度，问题就荒诞起来了：**按代码，它是内核，该在 ring 0；按硬件事实，它只是宿主上的一个普通应用，只能在 ring 3**。guest 里的应用要访问网络，向它请求，它努力去操作网卡——做不到，没有权限。它分裂了。

把一群功能塞进同一个大机器，会得「大公司病」：规格不灵活（只想试 4 核 8G，采购只能买大规格）、申请不灵活（每次都要重新采购）、复用不灵活（共享一台机器会撞端口、带历史包袱）。解法是**成立子公司**：独立决策、独立运营，一个命令就能拉起一套新操作系统。虚拟化就是那个「成立子公司」的动作，代价就是这笔账。

x86 原本不是为虚拟化设计的，它有一批**敏感指令**：在用户态（或被降级的非根态）执行会失败、报异常，或者行为和物理机上不一样。

| 敏感指令类别 | 典型例子 | 直接执行的后果 | 不拦截会怎样 |
|---|---|---|---|
| 读写特权寄存器 | CR0/CR3/CR4、IDTR/GDTR、MSR | 触发 #GP 异常，或读到假值 | guest 改页表基址等于改宿主的 |
| 改页表基址 | `mov %cr3`、`invlpg` | 权限不足，或改到错误的表 | 两个 guest 互相踩内存 |
| IO 端口指令 | `in` / `out`（IDE 的 PIO 读写） | 直接指挥真实设备 | guest 绕过宿主操作磁盘 |
| 特权与查询类 | `CPUID`、`HLT`、部分 `IRET` 用法 | 暴露物理机的真实信息 | guest 看到宿主的核数、型号，行为错乱 |

要跑多个 OS，就必须把这些指令**拦截**下来，由中间那层——hypervisor——代跑或改写。三代方案，本质上就是「用什么手段拦」的三次换招。

## 三代方案：翻译指令、改内核、加硬件

| 方案 | 拦截手段 | 要改 guest 吗 | 兼容性 | 开销 | 代表 |
|---|---|---|---|---|---|
| 全虚拟化 + 二进制翻译 | 运行时扫描并改写指令，特权操作转给宿主代跑 | 不改 | 最好，任何 OS 可装 | 最大，指令逐条过手 | VMware 早期、纯 qemu（`accel=tcg`） |
| 半虚拟化（PV） | 改 guest 内核，敏感操作改成显式 hypercall | 要改 | 只支持改过的 OS | 小 | Xen PV、virtio 驱动 |
| 硬件辅助 | CPU 新增根/非根两种模式，敏感指令触发 VM exit | 不改 | 好 | 接近原生，成本落在 exit 上 | Intel VT-x、AMD SVM（KVM） |

**第一代：全虚拟化 + 二进制翻译。** 说白了是「骗人」：虚拟化软件模拟出假的 CPU、内存、网卡、硬盘，让 guest 自我感觉良好，觉得自己又像个内核了。真实工作模式是传话筒——guest 内核说「我要在 CPU 上跑一条指令」，虚拟化软件转头对物理机内核说「我管的虚拟机要跑条指令，借我一小段 CPU 时间代它跑一下」。内存同理：虚拟化软件告诉 guest「0、1、2、3 号房间都是你的，你是内核嘛，独占资源，从 0 编号的就是你的」，转头去找物理机内核要了 90、91、92、93 四个房间，然后在中间做房间号翻译——guest 要往 2 号房间放东西，实际落在 92 号。网卡和硬盘也是同一个套路，每件事都要虚拟化软件转一遍。**坏处是慢，而且往往慢到不能忍受。**

**第二代：半虚拟化。** 换思路：不当传话筒，让 guest 正视自己的身份——「别说你是内核，你还真喘上了。你不是物理机，你是虚拟机！」guest 一旦承认自己没那么高权限、可能和很多虚拟机共享物理资源，就会发现大量可优化点：写硬盘其实是写宿主上的一个文件，缓存方式可以换；发网络包根本不是发给真网卡，而是给虚拟设备，数据可以直接在内存里拷过去。代价是 **guest 必须改**：加载特殊驱动，从代码层面重新定位自己。

**第三代：硬件辅助。** Intel 的 VT-x、AMD 的 SVM 从硬件层面解决问题。当初让写内核的大牛用等级用得那么奢侈，用完 0 就是 3，中间不省着点儿用；硬件只好另起炉灶加一个标志位，表示当前处于虚拟机状态还是真正的物理机内核状态。于是 CPU 有了**根模式（root，跑 hypervisor）与非根模式（non-root，跑 guest）**两种特权级：guest 的大部分指令直接在 CPU 上跑，不需要中间转述；只有遇到敏感指令，才切回根模式由 hypervisor 处理。安装虚拟机务必打开物理 CPU 的这个标志位：Intel 查 `grep vmx /proc/cpuinfo`，AMD 查 `grep svm /proc/cpuinfo`。没打开就只能退回纯模拟（`accel=tcg`），性能差一个量级。

硬件辅助要保存和恢复的状态比普通进程切换多得多：可能是两个虚拟机之间切换，也可能是虚拟机切给内核，而虚拟机里还装着一整个操作系统。这份上下文放在 **VMCS（Virtual Machine Control Structure）**里。

| VMCS 区域 | 存什么 | 何时被用 |
|---|---|---|
| Guest-state area | vCPU 的寄存器等基本运行环境 | VM entry 时载入 |
| Host-state area | 物理 CPU 的状态 | VM exit 时载入 |
| VM-execution control fields | 中断怎么办、是否启用 EPT | hypervisor 预先配置 |
| VM-exit control fields | exit 时 guest 保存哪些 MSR、host 恢复哪些 | hypervisor 预先配置 |
| VM-entry control fields | entry 时保存和恢复哪些 MSR | hypervisor 预先配置 |
| VM-exit information fields | 退出原因与必要信息 | CPU 硬件在 exit 时写入 |

两个动作由此定义：**VM entry** 是从根模式切到非根模式，CPU 上开始跑虚拟机；**VM exit** 是从非根模式切回根模式，把 CPU 还给宿主机。后者是全部开销的来源。

## VM exit：CPU 虚拟化的成本中心

KVM 的运行循环极短，短到能背下来：`kvm_cpu_exec` 里调 `kvm_vcpu_ioctl(cpu, KVM_RUN, 0)`，此时 CPU 进入 VM entry；只要 guest 一直占着 CPU，这一行就不返回；一旦返回，说明发生了 VM exit，接着按 `run->exit_reason` 分派处理，处理完再进下一次 entry，如此循环。真正的机器码层面，`vmx_vcpu_run` 做的四件事是：保存宿主寄存器 → 载入 guest 寄存器 → `VMLAUNCH`/`VMRESUME` 进入 guest → 退出时保存 guest 寄存器、载入宿主寄存器，并把 `exit_reason` 写回。

一次 exit 意味着：保存/恢复两套寄存器、走一遍分派、很可能还要读 VMCS。**量级在微秒级**（数量级判断，不是本机实测）。单看一次不多，但它按次数乘。

| 常见 exit 原因 | 触发动作 | 谁处理 | 能否减少 |
|---|---|---|---|
| `KVM_EXIT_IO` | guest 读写 IO 端口（virtio 的 notify 就是一次端口写） | `kvm_handle_io` → 设备后端 | 批量提交、vhost、直通 |
| 外部中断注入 | 网卡中断要送进 guest | `handle_external_interrupt` | 中断合并、posted interrupt |
| `EXIT_REASON_EPT_VIOLATION` | EPT 里没有这条映射 | `handle_ept_violation` | 大页、预映射 |
| `CPUID` 等特权指令 | guest 查询或执行敏感指令 | 逐条模拟后返回 | 一般无法减少，属固定成本 |
| 信号与调度 | 宿主有信号待处理、`need_resched()` 成立 | 回到宿主调度 | 绑核、隔离 CPU |

> 🔑 **减少 exit 的次数，比优化 exit 内部的代码有效得多。** 一次 exit 的固定成本压不下去多少，但把「每个请求一次 exit」改成「每 32 个请求一次 exit」，成本直接除 32。这也解释了为什么设备直通与 SR-IOV 效果显著：数据路径上根本不产生 exit，guest 直接 DMA 到真实设备，代价是牺牲迁移能力和超卖能力。

## CPU 调度：vCPU 只是宿主上的一个普通线程

每个虚拟 CPU 在 qemu 里对应**一个宿主线程**：`qemu_thread_create` 创建，执行体是 `qemu_kvm_cpu_thread_fn`，里面 `kvm_init_vcpu` 建好内核侧的 `struct vcpu_vmx`（含 VMCS），然后进一个 `do-while` 循环反复调 `kvm_cpu_exec`。这个线程和宿主的其他进程一样排进 CFS 就绪队列，一样可能被抢占。

内核侧也明确承认这一点：`vcpu_run` 的无限循环里，除了 `vcpu_enter_guest`，还检查 `signal_pending(current)`（虚拟机可以被 kill 掉）和 `need_resched()`（这个 vCPU 可以被从当前物理 CPU 上赶下来，换成别的虚拟机或其他进程）。创建 vCPU 时还注册了 `preempt_notifier`——被抢占是要被通知的。

**vCPU 数超过物理核数，就是超卖。** 超卖之后，guest 内核看到的现象是：自己的任务明明是 runnable，CPU 却没分给它。这份时间在 guest 里被记成 **st（steal time）**——原文定义是「当系统运行在虚拟机中的时候，被其他虚拟机占用的 CPU 时间」；从机制上说，就是**你的 vCPU 可运行、但宿主没给它物理 CPU 的那段时间**。

| st 水位（单核口径） | 含义 | 该怎么办 |
|---|---|---|
| ≈ 0–1% | 宿主基本没抢你的时间 | 不用管，作为基线 |
| 1–5% | 有轻微争抢 | 记录基线，看业务 p99 是否同步抖动 |
| 5–10% | 明显超卖，或邻居很吵 | 延迟敏感型开始准备换独享型 / 绑核 |
| > 10–15% | 每 100 ms 里有 10–15 ms 你的 vCPU 在排队 | 优化代码几乎无效，换机型或错峰 |

`st` 与 `us`/`sy`/`wa`/`hi`/`si` 同属 CPU 时间去向的九个字段，字段口径与四个常见误读见 [11.9 中断、软中断与 CPU 时间去向](11.9-中断-软中断与CPU时间去向.md)；虚拟化只额外加了 `st` 与 `guest` 两个字段。

vCPU 被切走时，guest 内部还有一个更隐蔽的现象：**时钟跳变与延迟尖刺**。guest 读 TSC 或时钟中断的间隔，会发现自己「凭空少了一段时间」；对 guest 里的定时器、超时判定、日志时间戳来说，那段时间就是消失了。表现是 p99 突然比 p50 高一个数量级，而 CPU 使用率、内存、磁盘指标全都正常。

「8 vCPU 的云主机跑不满 8 核」，原因有四层，每一层都在不同指标上留痕：

| 原因 | 机制 | 留痕 |
|---|---|---|
| vCPU 是线程，不绑物理核 | 8 个 vCPU 线程可能有两个落在同一物理核的两个超线程上 | 8 个 vCPU 都接近 100%，实际算力只有 4–5 个物理核 |
| 宿主超卖 | 别的租户分走时间片 | `st` 上升，guest 里 `%idle` 变多但延迟变差 |
| VM exit 固定成本 | IO、中断、CPUID 都要进出 | `%sys` 偏高，单请求延迟下不去 |
| guest 内串行点 | 锁、单线程初始化、启动阶段 | 1 个核 100%、7 个核闲着 |

第三层容易被误判：**exit 处理花的是 vCPU 线程的 CPU 时间，在 guest 里通常表现为 `sy` 偏高或被当成「CPU 跑了但活没干」**，而不是 st。st 只统计「根本没轮到物理 CPU」。两个指标混着看，方向就会错。

`-smp` 那一串参数正是这层混乱的来源：`-smp 1,sockets=1,cores=1,threads=1` 表示 1 个 vCPU、1 路、1 核、1 线程；而 socket 是主板上插 CPU 的槽数（常说的「路」），core 是核，thread 是每核的硬件线程（超线程）。某台服务器 2 路 4 核超线程（一般默认 2 线程），`cat /proc/cpuinfo` 看到 2×4×2 = 16 个 processor，很多人习惯直接叫它「16 核」——**报价单上的核数和物理核数是两个口径**。核数口径的误会，是「8 vCPU 跑不满 8 核」的第一层来源。

什么时候必须独享或绑核：p99 敏感（交易、实时风控）、st 的 p95 已超过 5%、以及 vCPU 数接近物理核数时还想保延迟稳定。绑核的额外收益是 NUMA 局部性——vCPU 与它的内存、网卡队列落在同一个 NUMA 节点上，跨节点访问的代价见 [11.6 CPU Cache 与 NUMA](11.6-CPU-Cache与NUMA.md)。

## 内存虚拟化：四类地址，两层页表

有了虚拟机，内存从两类变成四类：

| 缩写 | 全称 | 是谁眼里的内存 |
|---|---|---|
| GVA | Guest Virtual Memory | guest 里的进程看到的虚拟地址空间 |
| GPA | Guest Physical Memory | guest 操作系统以为的「物理内存」 |
| HVA | Host Virtual Memory | 宿主上 qemu 进程看到的虚拟地址空间 |
| HPA | Host Physical Memory | 宿主操作系统看到的真物理内存 |

一次访问要连过 GVA→GPA、GPA→HVA、HVA→HPA 三道翻译，性能会很差。qemu 侧的管理框架是：`AddressSpace address_space_memory` 表示虚拟机的系统内存，由若干 `MemoryRegion` 组成树形结构，指向 `mmap` 分配出来的虚拟内存；添加内存区域时，`KVMMemoryListener.region_add` → `kvm_region_add` → `kvm_set_phys_mem` 把用户态的 `KVMSlot`（可以理解成用户态模拟出来的内存条）通过 `KVM_SET_USER_MEMORY_REGION` 通知内核，内核侧对应 `kvm_memory_slot`，记下起始页号与页数。这只是元数据对齐，页面本身在被访问之前并没有真分配。

翻译这一层有两条路线：

| 维度 | 影子页表（Shadow Page Table） | EPT / NPT（硬件二级页表） |
|---|---|---|
| 谁维护 | hypervisor 为 guest 每个进程各维护一套 | 硬件查表，KVM 只维护一套 EPT |
| guest 改页表 | 要 trap 进 hypervisor 同步影子页表 | 不 trap，guest 页表直接指向 GPA |
| 内存占用 | 大（每进程一套） | 小（每虚拟机一套） |
| 缺页代价 | 同步页表，路径复杂 | 一次 EPT violation，建映射 |
| TLB | 缓存 GVA→HPA，条目效率尚可 | 需缓存两级映射，覆盖范围变小 |

影子页表的思路是「让 guest 用一份替身页表」：guest 通过 CR3 找到自己的页表完成 GVA→GPA，宿主通过 CR3 找到宿主的页表完成 HVA→HPA；KVM 为 guest 每个进程维护一套对应的影子页表，guest 访问内存时用的不是原来那份页表，而是影子页表，从而直接完成 GVA→HPA。TLB 和 CPU 缓存上缓存的也是影子页表的映射，效率因此提高。代价是内存占用大，而且 guest 页表与影子页表要实时同步——**guest 每次改页表都是一次 trap**。

EPT 换了个位置：在原有 guest 页表（GVA→GPA）之上，再引入一层 EPT 页表做 GPA→HPA。guest 运行时，guest 页表载入 CR3，EPT 页表载入专门的 EPTP 寄存器。GVA→GPA 这一段完全按传统方式走，EPT 只负责 GPA→HPA，所以它又叫 TDP（two-dimensional paging，二维分页）。EPTP 指向 PML4 首址，EPT 页表同样是四层。

缺页路径是这样的：guest 访问一个没建立映射的页 → 触发 EPT 缺页异常 → 发送 VM exit（`EXIT_REASON_EPT_VIOLATION`）→ `handle_ept_violation` 从 VMCS 读出没解析成功的 GPA → `kvm_mmu_page_fault` → `tdp_page_fault` 用 GPA 算出 gfn，`try_async_pf` 经 `__gfn_to_pfn_memslot` 拿到 pfn（内部走 `hva_to_pfn` → `get_user_pages` → `handle_mm_fault`，也就是普通的缺页分配）→ `__direct_map` 把 gfn 与 pfn 关联起来，必要时往下逐级建页表项。

即便有 EPT，仍然有代价，而且代价的形状很特别：

1. **TLB 要记两级映射。** 一条 GVA→HPA 的最终映射背后是两套页表，能缓存的条目覆盖范围被摊薄，同一工作集的 TLB 压力上升。
2. **缺页更贵。** 一次 EPT violation 是「exit + 查表 + 分配 + 建表」的完整流程，比普通缺页多一整套出入成本。
3. **大页的收益被放大。** 一个 2 MB 大页让一条 TLB 条目覆盖 2 MB，一个 1 GB 大页覆盖 1 GB——在两级翻译下，这直接按倍数减少所需条目数与页表级数。源材料的 qemu 参数里那个 `+pdpe1gb`（1 GB 页支持位）不是装饰，正是为这件事准备的。

**内存超卖**比 CPU 超卖更危险，因为内存不能被「时间片」摊平。两种回收手段的取舍：

| 手段 | 做法 | 省下什么 | 付出什么 | 什么时候别用 |
|---|---|---|---|---|
| ballooning（气球驱动） | guest 内加载气球驱动，按宿主指令占住并归还页面 | 真实可回收的 guest 空闲内存 | guest 内的分配延迟、驱动依赖 | guest 内已接近满载，气球一充就 OOM |
| KSM（页合并） | 宿主扫描相同内容的页，合并为一份 COW | 同质 guest 的重复页（同一镜像批量部署） | 持续扫描的 CPU、COW 后的写放大 | CPU 已是瓶颈，或页内容差异大 |

取舍的判断只有一句：**看哪边先到瓶颈**。CPU 打满而内存有余，关掉 KSM；内存吃紧而 CPU 有余，开 KSM 并把 `pages_to_scan` 调高，同时监控合并率。两者都不是「开了就更好」的开关。

## 存储虚拟化：一次写要付几次 exit

virtio 是这场演化的分水岭。早期不同虚拟化技术针对不同硬盘、网卡各写一套驱动，guest 也要按虚拟化技术和物理设备挑驱动，驱动数量爆炸。virtio 的作用是**统一接口**：guest 里统一加载 virtio 驱动，宿主侧实现不同的 virtio 后端去适配不同硬件。它的架构分四层——guest 内的前端驱动（硬盘 `virtio_blk`、网络 `virtio_net`，接口统一）、virtio 层（虚拟队列接口）、virtio-ring 层（队列的具体实现）、宿主 qemu 里的后端（真正操作硬件）。队列数目随设备类型不同：**virtio-net 用两个队列（收、发各一），virtio-blk 只用一个队列**。guest 要发数据，就把 buffer 加进 virtqueue，然后**写寄存器通知**宿主。

| 形态 | guest 看到的设备 | 一次 IO 的 exit 次数 | 数据通道 | 主要代价 |
|---|---|---|---|---|
| 全模拟（IDE/SATA、e1000） | 一模一样的真实控制器 | 多次（每条 PIO/MMIO 寄存器访问） | qemu 逐寄存器模拟 | 最慢，兼容性最好 |
| virtio-blk / virtio-scsi | virtio PCI 设备 | 约 1 次 notify + 1 次完成中断 | 共享内存 vring，可批量 | 要装 virtio 驱动 |
| vhost / vhost-user | 同上 | notify 由内核或独立进程直接消费，少一次 qemu 唤醒 | vring 直接由后端消费 | 配置复杂，排障难 |
| 设备直通 / VFIO | 真实设备（如 NVMe） | 数据路径 0 次（中断注入仍可能有少量） | 设备 DMA | 牺牲迁移与超卖 |

一次写落在哪条链路上，源材料给得很具体：应用 `write` → guest 内核 VFS → 通用块层 → I/O 调度 → `virtio_blk` 驱动的 `request_queue`（`make_request_fn` 是 `blk_mq_make_request`）→ `virtqueue_add` 把请求塞进 vring（`desc`/`avail`/`used` 三件套）→ `virtqueue_notify` → `vp_notify` 里一次 `iowrite16` 写 notify 寄存器 → **触发 VM exit** → qemu 的 `kvm_cpu_exec` 收到 `KVM_EXIT_IO` → `virtio_blk_handle_output` → `virtio_blk_handle_vq` 里 `while` 循环取请求 → `blk_aio_pwritev` 经 `BlockBackend` 写宿主的 qcow2 文件（用协程做异步，避免线程切换带 VM 状态的高代价）→ 写完后 `virtqueue_push` 更新 used、`virtio_notify` 发中断 → guest 侧 `vp_interrupt` → `vring_interrupt` → `virtblk_done` → `virtqueue_get_buf` 里 `last_used_idx++` 回收空间。

这条链路里能省的只有两处，也就对应上表的后两行：

- **省 exit 次数**：`virtio_blk_handle_vq` 是「关通知 → 循环取空队列 → 合并多个请求（`virtio_blk_submit_multireq`）→ 开通知」，一次 exit 处理一批。
- **省唤醒与切换**：vhost 把后端从 qemu 用户态挪进宿主内核（`vhost=on`），notify 不再需要把 qemu 主循环叫醒。

云盘是另一层叠加：它对外是虚拟块设备，对内是网络存储，一次 IO 的延迟是「网络往返 + 存储处理」两段相加，还要加上虚拟化那笔固定成本。三段叠加的模型见 [10.3 云盘性能模型 (IOPS / 吞吐 / 延迟)](../10-存储基础设施/10.3-云盘性能模型.md)。

## 网络虚拟化：每个包都要付一次固定成本

guest 发一个包：进程 `write` socket → VFS → guest 协议栈 → 网络设备层。但这里不是普通网卡，而是 `virtio_net` 驱动：`start_xmit` → `xmit_skb` → `virtqueue_add_outbuf` → `virtqueue_kick`/`virtqueue_notify` → **VM exit** → qemu 的 `virtio_net_handle_tx_bh` 调度 `virtio_net_flush_tx` → 循环 `virtqueue_pop` 取包 → `qemu_sendv_packet_async` → `tap_receive_iov` → `writev` 写入 `/dev/net/tun` → 宿主内核 `tun_chr_write_iter` → `tun_get_user` 把包从用户态拷进内核 → `netif_rx_ni` 交给宿主协议栈 → 经 tap 虚拟网卡、网桥/OVS、物理网卡出去。

为什么要绕到 `/dev/net/tun`？因为包必须变成「正常的网络包」才能被转发，而那需要一整套协议栈；qemu 自己没有协议栈，现实现一个也不可能。于是它把包转成文件流写进字符设备，内核的 TUN/TAP 驱动再把文件流转回网络包。和 KVM 一样，这是一次「打开字符设备 + ioctl 使用内核能力」的操作。

| 方案 | 数据路径 | 每包 exit | 隔离与迁移 | 适用 |
|---|---|---|---|---|
| qemu 用户态 virtio-net | guest → qemu → tap → 宿主栈 | notify 1 次 + 完成中断 | 好 | 通用 |
| vhost-net | guest → 宿主内核 vhost → tap | notify 由内核直接消费，少一次唤醒 | 好 | 通用高吞吐 |
| SR-IOV VF 直通 | guest → VF → 物理网卡 | 数据路径 0 次 | 差（绑硬件、难迁移） | 低延迟、高包率 |
| DPDK / AF_XDP 轮询 | guest → 用户态 PMD 直接取包 | 不经过宿主协议栈，轮询取包 | 差 | NFV、专用网关 |

> 🔑 网络开销的形态是「**每包固定成本**」，所以它惩罚的是 PPS，不是带宽。同样 1 Gbps，按 20 字节固定开销（前导码 + 帧间隙）折算，1470 字节的大包约 8.4 万 PPS，64 字节的小包约 148 万 PPS——同一份带宽，包数被乘了约 17 倍。小包场景里，虚拟化开销占比高到能决定架构选型，这也是 DPDK 与 SR-IOV 存在的理由。

## 三处损耗一张表

| 损耗点 | 成本形态 | 量级 | 谁受伤最重 | 谁几乎无感 |
|---|---|---|---|---|
| CPU | 每次 exit 一笔固定成本 + 被偷走的时间片 | exit 微秒级；`st` 15% 即每 100 ms 少 15 ms | 高频小 IO、短连接、频繁中断 | 长时间纯计算的 CPU 密集任务 |
| 内存 | 多一层翻译，TLB 覆盖变小，缺页更贵 | 4 KB 页与 2 MB 大页的单条目覆盖差 512 倍，两级翻译再摊薄一次 | 大内存随机访问（JVM 堆、buffer pool） | 小工作集、顺序访问 |
| IO | 路径长度 + 通知往返，按次数乘 | 每 IO 一笔固定成本：5 万 IOPS × 5 µs 就是 0.25 核 | 小包网络、4K 随机读写 | 大块顺序 IO |

结论可以直接背：**CPU 密集受影响最小，IO 密集与小包网络受影响最大，内存居中但表现最隐蔽（延迟尖刺而非吞吐下降）。** 判断顺序也由此确定：先看 `st`（是不是被超卖），再看 IO 次数与队列（是不是在付固定成本），最后才看 TLB 与大页。

## 案例：容器化后启动慢，根因不在虚拟化

原案例机器：2 CPU、8GB 内存的 Ubuntu 18.04 虚拟机，跑一个 Tomcat 官方镜像，应用逻辑只有「分配 256 MB 内存并输出 Hello, world!」。启动命令带 `--cpus 0.1 -m 512M`。

现象与排查链条：

1. `curl` 反复报 `Connection reset by peer`，随后是 `Empty reply from server`、`Connection refused`——不是「慢」，是容器反复退出。
2. `docker inspect tomcat -f '{{json .State}}' | jq` 显示 `"OOMKilled": true`、`"ExitCode": 137`。
3. `dmesg` 里被杀的进程 PID 27281，`total-vm:4613208kB`、`anon-rss:517316kB`、页内存约 19 MB，容器内存用量与限制都是 512 M（524288kB）。
4. `docker exec tomcat java -XX:+PrintFlagsFinal -version | grep HeapSize`：`InitialHeapSize` 126 MB，`MaxHeapSize` 1.95 GB——远超容器的 512 M。原因是容器内看不到 Docker 设置的内存限制，`docker exec tomcat free -m` 看到的仍是主机内存。
5. 修掉堆内存（`JAVA_OPTS='-Xmx512m -Xms512m'`）后容器不再退出，但启动要 22–24 秒。
6. `top` 看着一切正常：两个 CPU 使用率 3% 和 5.7%，可用内存 7 GB。`pidstat -t -p $PID 1` 才露出真相：`%CPU` 只有 10%，而 `%wait` 最高到 97%——线程大部分时间在等调度。
7. 把 `--cpus 0.1` 改成 `--cpus 1`，启动时间从 22 秒降到 2 秒。

结论要如实写：**这个案例的根因是 cgroup 的 CPU 配额（0.1 核 = 10%）与 JVM 堆配置，不是虚拟化。** 它给的启发是排查顺序——同一条命令链（`top` → `pidstat -t` → 看 `%wait` 而不是 `%CPU`）在虚拟机里同样成立，只是虚拟机里多两个变量：`st`（宿主不给 CPU）与 exit（进出客户机的固定成本）。至于「容器比虚拟机启动快」的对比，差的不是虚拟化开关，而是「有没有一个内核要引导」，边界见 [6.1 容器与虚拟机的本质差异](../6-容器技术/6.1-容器与虚拟机的本质差异.md)。

## 决策表：这笔损耗该不该付

| 场景 | 选型 | 为什么 | 资源策略 |
|---|---|---|---|
| 异构内核、Windows 负载 | 虚拟机 | guest 自带内核，容器做不到 | 按需，不必超卖 |
| 强隔离、合规要求 | 虚拟机 / 裸金属 | 隔离维度的对比见 [6.1 容器与虚拟机的本质差异](../6-容器技术/6.1-容器与虚拟机的本质差异.md) | 1:1 |
| 短生命周期、CI、构建 | 容器 | 少一次内核引导 | 密度优先 |
| 高频小包、低延迟交易 | 独享型 + 绑核 / 直通 | exit 与 st 都不许有 | 1:1 或 SR-IOV |
| 大内存随机访问（缓存、数据库） | 大页 + 内存不超卖 | 二级页表让 TLB 更吃紧 | 内存 1:1，开大页 |
| 稳态吞吐型 Web | 通用型可超卖 | CPU 密集受影响小 | 从 1:2 起压测 |

超卖比怎么定，不看宣传口径的「vCPU : 物理核」，看三个可测的量：**guest 内 `st` 的 p95、业务延迟的 p99、以及宿主是否已经用上 vhost 与大页**。定法是逐档压：先在 1:1 下压出 p99 基线，再按 1:2、1:3 逐步提高密度，直到 `st` 的 p95 或 p99 越过约定阈值，回退一档。CPU 密集业务可以把档位抬高，内存密集与小包网络密集必须压低——具体档位以压测为准，不引用厂商数字。部署形态的取舍见 [5.2 部署模型](../5-云计算基础/5.2-部署模型.md)。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 `%CPU` 判断云主机是否被超卖 | `%CPU` 只说明进程在跑；`st` 才说明宿主拿走了多少 |
| 看到应用慢就先优化代码 | `st` 15% 时，能优化的只是剩下那 85% 里的几个点 |
| 用全模拟设备（IDE、e1000）跑数据库 | 每次 IO 多次 exit，IOPS 上不去，还误判成磁盘差 |
| 把报价单的 vCPU 数当物理核数 | socket/core/thread 加超线程混算，容量评估直接偏高 |
| 内存超卖却不看 balloon 状态 | 气球一充就 OOM，或宿主 swap 抖动带来延迟尖刺 |
| CPU 已是瓶颈还开着 KSM | 扫描线程抢 CPU，换来用不上的内存节省 |
| 拿启动时间比较 VM 与容器 | 差的是「有没有内核要引导」+ 配额，不是虚拟化开关 |

## 三条铁律

> 🔑 **VM exit 的次数是 CPU 损耗的第一变量。** 一次 exit 的代码优化空间有限，把「每请求一次」改成「每批一次」才是数量级的改变；直通与 SR-IOV 之所以立竿见影，是因为它把次数降到了 0。

> 🔑 **`st` 是宿主给你的答案，不是你代码的问题。** `st` 高说明 vCPU 可运行却没拿到物理 CPU，改代码改不动它；要动就动机型、绑核、超卖比。反过来，`%sys` 高而 `st` 低，才轮到查 exit 与中断。

> 🔑 **内存看 TLB 覆盖，IO 看路径长度。** 大内存随机访问先上大页、别跨 NUMA；小包与随机 IO 先数「一次操作要付几笔固定成本」，再谈优化那条路径上的代码。

## 生产落地：指名 → 可抄 → 可验 → 可退

工具指名：`systemd-detect-virt`（systemd 自带）、`sysstat`（`mpstat`/`pidstat`/`sar`）、`util-linux`（`lscpu`）、`ethtool`、`libvirt`（`virsh dommemstat`）。**实测环境**：Docker Desktop 29.9.2 → LinuxKit 虚拟机 → Alpine 3.20 容器，内核 `7.0.14-linuxkit`，8 vCPU；带「实测」的是本机真实粘贴，其余为格式示意。

**① 判断当前是不是虚拟机**

```bash
systemd-detect-virt                 # 输出 kvm / vmware / xen / none
lscpu | grep -i virtualization      # Hypervisor vendor / Virtualization type
lscpu | grep -o hypervisor          # flags 里的 hypervisor 标志
grep -c -w -E 'vmx|svm' /proc/cpuinfo   # >0 说明硬件辅助可用（在 guest 里通常不可见）
cat /sys/hypervisor/type 2>/dev/null
cat /sys/class/dmi/id/product_name 2>/dev/null   # 容器里通常读不到，返回空
```

本机实测（Alpine 容器里 `systemd-detect-virt` 不可用，退化为看 `/proc` 与 `lscpu`）：

```
$ uname -r
7.0.14-linuxkit          # 内核名带 linuxkit，本身就是“跑在 VM 里”的证据
$ grep -m1 Features /proc/cpuinfo | cut -c1-60
Features : fp asimd evtstrm aes pmull sha1 sha2 crc32 atomics ...
```

判据：`/proc/cpuinfo` 的 `Features` 里**没有 `vmx`/`svm`**（容器里也不该有），而 `/proc/interrupts` 出现 `GICv3  virtio*`，两条合起来就能确认“这是一台 virtio 虚拟机”。

**② 看 `st`：先分核，再看趋势**

```bash
top -d 1                 # 在 top 里按数字 1，展开每个 CPU，看 st 列
mpstat -P ALL 1 5        # 每核一行，看 %steal 与 %sys
vmstat 1 5               # us sy id wa st 五列
awk '/^cpu /{print "st_ticks=" $9}' /proc/stat   # 第 9 个字段是 st（累计节拍，USER_HZ=100）
```

本机实测（`/proc/stat` 的 `cpu` 行是 10 个数字，第 9 位 `st` 与第 10 位 `guest` 都是 0）：

```
$ head -1 /proc/stat
cpu  3138 0 448 312262 118 0 133 0 0 0
$ top -b -n1 | grep '%Cpu'
%Cpu(s): 12.8 us,  0.0 sy,  0.0 ni, 87.2 id,  0.0 wa,  0.0 hi,  0.0 si,  0.0 st
```

> ⚠️ **容器里 `st` 恒为 0 不代表宿主没偷你的时间**。`/proc/stat` 来自 LinuxKit 这层 VM 的内核，它对“被 macOS 抢走的时间”没有视图；真实的 steal 只在该 VM 的宿主（或云厂商的 hypervisor）侧才有意义。**在容器里判断云主机节流是错的**——要么进 VM/宿主看，要么直接看业务 P99 与 `cpu.stat` 的 `throttled_usec`（那是配额节流，不是 steal）。

判据：某一核 `st` 持续 >5% 就该记下来；>10% 直接进换机型流程。注意 `top` 默认 3 秒间隔，和其他工具对比时要保持同一间隔——否则同一台机器的数字都对不上。

**③ 看 vCPU 与物理核的对应关系**

```bash
lscpu -e                     # CPU NODE SOCKET CORE ONLINE MAXMHZ MINMHZ MHZ
lscpu | grep -E 'Socket|Core|Thread|NUMA'
cat /sys/devices/system/cpu/cpu0/topology/thread_siblings_list   # 超线程兄弟核
nproc
```

实测（本机 `nproc` = 8，`lscpu -e` 的 `CORE` 列按 vCPU 一一对应，没有超线程兄弟）：

```
$ nproc
8
$ cat /sys/devices/system/cpu/cpu0/topology/thread_siblings_list
0
```

判据：`SOCKET`/`CORE` 两列相同的两行是同一物理核的两个超线程。8 个 vCPU 若只落在 4 个 `CORE` 上，容量评估就必须按 4 核算；`thread_siblings_list` 只剩自己一个号，说明这个 vCPU 独占一个核（没有超线程）。

**④ 看 virtio 队列与中断**

```bash
ethtool -l eth0                       # 队列数（Combined / RX / TX）
cat /proc/interrupts | grep -i -E 'virtio|vhost'
ls /sys/block/vda/mq | wc -l          # 块设备的多队列数
cat /sys/block/vda/queue/nr_requests  # 队列深度
```

实测（veth 网卡 + virtio 块设备）：

```
$ ethtool -l eth0
Channel parameters for eth0:
Pre-set maximums:
RX:             8
TX:             8
Other:          n/a
Combined:       n/a

$ cat /proc/interrupts | head -4
 14:   6635   0   0   0   0   0   0   0   GICv3  65 Level  virtio0
 16:   3595   0   0   0   0   0   0   0   GICv3  70 Level  virtio2
```

判据：`virtio0`/`virtio2` 的中断计数只在 CPU0 增长，就是“单队列把多核压成一个核”的现场；`ethtool -l` 里 `Combined: n/a` 而 `RX/TX` 各有 8，说明这是分离队列而不是合并队列，调优时要分别看 `rx-*` 与 `tx-*`。

**⑤ 看 balloon 与 KSM**

```bash
ls /sys/kernel/mm/ksm/
cat /sys/kernel/mm/ksm/run
cat /sys/kernel/mm/ksm/pages_shared /sys/kernel/mm/ksm/pages_sharing
virsh dommemstat <domain>             # actual / available / rss / swap_in
# qemu monitor 里看气球：info balloon
```

## 自检

**Q1** 买了 8 vCPU 的云主机，压测时 8 个 vCPU 的 `%CPU` 都接近 100%，但吞吐只有预期的六成。列出三个可验证的原因，并说明每个原因在哪个指标上留痕。

▸ 答案：① vCPU 是宿主线程，不绑核——8 个线程可能有两个落在同一物理核的两个超线程上，`lscpu -e` 的 `CORE` 列会暴露，算力按 `CORE` 去重后只有 4–5 核；② 宿主超卖，物理 CPU 被邻居分走，留痕在 `st`（>5% 就说明有）；③ exit 与串行点：`%sys` 偏高说明在付 exit 固定成本，`pidstat -t` 里 `%wait` 高而 `%CPU` 低说明线程在排队而不是在算。加上 `-smp` 的 socket/core/thread 混算，报价单的「核」和物理核本来就不同口径。

**Q2** 一台云主机 `st` 持续 15%，业务 p99 从 20 ms 涨到 90 ms。先优化代码还是先换机型？

▸ 答案：先换机型或绑核。`st` 15% 的定义是「vCPU 可运行但宿主没给物理 CPU」，这段时间由宿主的调度器决定，代码一行都不影响它；在剩下的 85% 里做优化，最多拿回几个百分点，还盖不住 p99 的 4 倍劣化。动作顺序：确认 `st` 是分核看的而不是均值（单核 15% 与平均 15% 差很多）→ 换独享型或绑核 → 观察 p99 与 `st` 的 p95 一起回落。只有当 `st` 降下来而 p99 仍然高，才轮到优化 exit 次数与 IO 路径。

**Q3** virtio 相比全模拟，到底省了什么？是省了数据拷贝，还是省了别的？

▸ 答案：省的是**exit 次数与寄存器级模拟**，不是数据拷贝。全模拟下 guest 访问一个真实的 IDE 控制器，每条 PIO/MMIO 寄存器读写都可能是一次 exit，qemu 还要逐寄存器模拟设备行为；virtio 把数据放在共享内存的 vring（`desc`/`avail`/`used`）里，guest 只写一次 notify 寄存器就触发一次 exit，qemu 一次把整批请求取走（`virtio_blk_handle_vq` 的循环 + 多请求合并）。数据本身仍然要跨 guest/host 边界搬运，真正把这次搬运也省掉的是 vhost（后端挪进内核）与直通（DMA 直达设备）。

**Q4** 开启 EPT 之后，为什么大页变得更有价值？

▸ 答案：EPT 让一次地址翻译要走两级页表（guest 页表 + EPT 页表），TLB 能缓存的最终映射覆盖范围被摊薄，同一工作集需要的 TLB 条目更多、miss 率更高；一个大页让单条 TLB 条目覆盖 2 MB 或 1 GB，直接按倍数减少所需条目数，同时减少页表级数与 EPT violation 的次数——而每一次 EPT violation 都是「exit + gfn→pfn + 建表」的完整流程。源材料里 qemu 的 `-cpu` 参数带 `+pdpe1gb`，就是 1 GB 大页的支持位，不是装饰。

**Q5** 案例里容器启动慢到 22 秒，如果换成一台同规格虚拟机跑同样的 Tomcat，慢在哪几段？这个案例本身的根因是什么？

▸ 答案：案例根因不在虚拟化——是 cgroup 的 `--cpus 0.1`（10% CPU）让线程 `%wait` 高达 97%，以及 JVM 看不到容器内存限制把最大堆设成 1.95 GB 导致 OOMKilled（退出码 137）。换成虚拟机后，慢会分成三段：固件 + guest 内核引导（秒级起步，容器没有这一段）+ 虚拟化固定成本（IO 与中断的 exit）+ 配额导致的排队。排查手法完全一致：先看 `st`（宿主不给 CPU）与 `%wait`（配额不够），再看 exit 与 IO 路径。
