# 11.13 进程间通信选型

## 一句话

> IPC 选型只看四件事：**要拷几次、唤醒多贵、谁负责背压、能不能跨机**；同机最快的是共享内存 + 自旋通知（实测 125ns），但同步与崩溃一致性全得自己扛；管道 2.4μs 且自带背压；unix socket 6.5μs 换来 fd 传递与多路复用；一旦要跨机，只剩 socket。

## 实测：四种同机通道的延迟与吞吐

环境：Docker Desktop 29.9.2 → Alpine 3.20 容器，内核 `7.0.14-linuxkit`，8 vCPU；**全部是 fork 出来的两个真实进程**，父进程计时，1 字节往返 20000 次取中位数，64KB 消息 2000 次算吞吐。

| 通道 | 往返 p50（1B） | 往返 p50（8KB） | 吞吐（64KB 块） | 谁在做拷贝 |
|---|---|---|---|---|
| 匿名管道 | **2.42μs** | 3.04μs | 3.9 GB/s | 内核两次（写进 ring + 读到用户） |
| unix socket（SOCK_STREAM） | **6.50μs** | 8.54μs | 5.6 GB/s | 内核两次 + socket 层校验 |
| TCP loopback | **6.75μs** | — | 5.6 GB/s | 内核两次 + 完整协议栈 |
| 共享内存（mmap 文件 + 原子量） | **125ns** | — | 12.5 GB/s | **零次**（两边直接读写同一页） |

三条读数提示：

1. **共享内存的 125ns 是“通知”的价，不是“通信”的价**：数据一致性、读写顺序、对端崩溃后的处理，全要自己做（下面的代码用 `seq/ack` 两个原子量 + 内存屏障）。
2. 共享内存吞吐两次运行在 7.7–12.5 GB/s 间波动，其余三项在 3.9–5.6 GB/s；**跨机之前，先问“真的需要内核参与吗”**。
3. TCP loopback 和 unix socket 打平（6.75 vs 6.50μs）——同机场景用 TCP 的唯一理由是“以后可能拆到另一台机器”，不是性能。

## 六个机制一张表

| 机制 | 数据单元 | 是否有消息边界 | 背压 | 生命周期 | 跨机 | 典型用途 |
|---|---|---|---|---|---|---|
| 匿名管道 `pipe()` | 字节流 | 无（靠约定） | **有**（满 64KB 阻塞） | 随进程消失 | 否 | 父子进程、shell 竖线管道、stdin/stdout |
| 命名管道 `mkfifo` | 字节流 | 无 | 有 | 文件系统里的节点 | 否 | 无亲缘关系的本机进程 |
| 信号 `kill`/`sigqueue` | 一个编号（可带 sivalue） | — | 无 | 瞬时 | 否 | 通知“出事了”，不传数据 |
| 共享内存 `shmget`/`mmap` | 任意结构 | 由使用者定义 | **无** | 手动/引用计数 | 否 | 大块数据、低延迟、手写同步 |
| unix socket | 字节流/数据报 | stream 无、dgram/seqpacket 有 | socket 缓冲 | 随 fd | 否 | 本机服务、传 fd、网关 |
| TCP socket | 字节流 | 无（要自己分帧） | socket 缓冲 | 四元组 + TIME_WAIT | **是** | 跨机、可迁移 |

> 🔑 **“有没有消息边界”比“快不快”更容易踩坑**：管道、TCP、unix stream 都是字节流，一次 `write(4096)` 可能被读成 `1000 + 3096`。要么自己加长度前缀，要么用 `SOCK_SEQPACKET`/`SOCK_DGRAM`。

## 逐个拆：选择时真正起作用的细节

### 管道：内核里的一个环形缓冲

`pipe()` 创建两个 `file` 对象，指向同一个 `pipe_inode_info`；内核按页分配环形缓冲。实测本机默认容量：

```
$ cat /proc/sys/fs/pipe-max-size
1048576
$ ./pipesize            # F_GETPIPE_SZ
pipe capacity = 65536 bytes
```

- **默认 64KB（16 页）**，可 `fcntl(F_SETPIPE_SZ)` 调大，上限是 `pipe-max-size`（实测 1MB）。
- **`PIPE_BUF` = 4096**：小于它的写是原子的（不会与其他写交错），大于它的写可能被拆开——多进程写同一管道时这是硬约束。
- 自带背压：写满就阻塞（或用 `O_NONBLOCK` 拿到 `EAGAIN`），这是它相对共享内存最大的优势。
- 只能靠 fork 继承 fd，**没有名字**（命名管道补上这一点）。

### 信号：只通知，不传数据

信号由内核投递到目标进程 `task_struct` 的 pending 位图，进程**从内核态返回用户态时**检查并调用处理函数——这就是为什么信号处理函数里能用的 API 极少（`async-signal-safe`）。

| 事实 | 后果 |
|---|---|
| 标准信号不排队（同种信号多次发送只记 1 个） | 用它计数必然丢事件 |
| 处理函数在用户态栈上异步执行 | 里面 `printf`/`malloc` 可能死锁 |
| `SIGKILL`/`SIGSTOP` 不可捕获 | 不能用它做“优雅退出”的兜底 |
| 实时信号（`SIGRTMIN`~）排队 | 需要计数时才用它 |

> ⚠️ 把信号当业务消息总线是经典反模式：丢事件、难测试、处理函数里不能做正经事。

### 共享内存：把拷贝省到 0，把复杂度全留给自己

两条实现路径：SysV `shmget/shmat`（老接口，`ipcs -m` 可见）与 POSIX `shm_open` + `mmap`（挂在 `/dev/shm`，本质 tmpfs）。实测通知成本：

```go
// 两个进程映射同一个文件，seq/ack 做握手；父进程写 seq，子进程回 ack
seq := (*uint32)(unsafe.Pointer(&m[0]))
ack := (*uint32)(unsafe.Pointer(&m[4]))
data := m[8:]

t0 := time.Now()
data[0] = byte(i)
atomic.StoreUint32(seq, uint32(i))   // 发布：写数据在前，写序号在后
for atomic.LoadUint32(ack) != uint32(i) {   // 等对方确认
}
elapsed := time.Since(t0)            // 实测 p50 = 125ns
```

必须自己解决的四个问题：

| 问题 | 不处理的后果 | 做法 |
|---|---|---|
| 内存序 | 对端看到序号更新、数据还是旧的 | 写数据 → 屏障/原子写序号（release） |
| 唤醒方式 | 自旋烧 CPU（本实测就是自旋，两个核跑满） | 用 `eventfd`/futex 做阻塞唤醒，延迟升到 μs 级 |
| 生命周期 | 一方崩溃，另一方永远等 | 超时 + 心跳 + `pthread_mutex` 的 robust 属性 |
| 边界与扩容 | 结构变更后旧段被新版本误读 | 头部放 magic/version/size，双端校验 |

### unix socket：本机通信的“全能选手”

| 能力 | 说明 |
|---|---|
| `SOCK_STREAM` / `SOCK_DGRAM` / `SOCK_SEQPACKET` | 要边界就用 seqpacket |
| `SCM_RIGHTS` 传 fd | 本机唯一能跨进程传“打开的文件/连接”的机制（systemd socket activation、Envoy 热重启都靠它） |
| `SO_PEERCRED` 拿对端 uid/pid/gid | 本机零信任鉴权 |
| 抽象命名空间 `@name` | 不落文件系统，进程退出自动释放 |
| 可被 epoll 管 | 大量本机连接时和网络 IO 用同一套事件循环（见 [11.4 epoll 与 IO 多路复用](11.4-epoll与IO多路复用.md)） |

实测同机 `wmem_default = 212992`（约 208KB），`net.unix.max_dgram_qlen = 10`（数据报排队深度）——**dgram 模式在突发流量下很容易丢**，要边界又不想丢，用 seqpacket。

### 消息队列与信号量：别在现代系统里新建

POSIX `mq_*` 与 SysV `msgget/semget` 提供“带优先级的内核队列”和“跨进程计数信号量”。它们能做的事，`unix socket + 文件锁/原子变量` 或共享内存都能做，而且更快、更好调试。**新系统里出现 SysV IPC 的 `ipcs` 输出，通常意味着在维护遗留代码。**

## 选型决策表

| 你的情况 | 选什么 | 理由 |
|---|---|---|
| fork 出来的父子进程，传流式数据 | 管道 | 2.4μs，自带背压，代码最短 |
| 两个无亲缘进程，要传 fd 或做鉴权 | unix socket | `SCM_RIGHTS` + `SO_PEERCRED` |
| 大块数据（MB 级）、要求最低延迟 | 共享内存 + eventfd | 少两次拷贝；先想清楚崩溃恢复 |
| 只是“通知一下”，不带数据 | eventfd / 管道 / 信号（仅兜底） | 信号会丢事件，别做计数 |
| 以后可能拆到另一台机器 | 直接 TCP（+ 长度前缀） | 迁移成本最低，同机性能并不差 |
| 需要广播、持久化、削峰 | 消息队列（broker） | 见 [43.1 消息模型 (点对点 / 发布订阅)](../../L4-组件与技术/43-消息队列/43.1-消息模型.md) |
| 高并发本机连接（>1 万） | unix socket + epoll | 和网络连接共用事件循环 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 TCP 做同机通信只为“统一” | 多一次协议栈与 TIME_WAIT；6.75μs vs 2.42μs |
| 共享内存不加内存屏障 | 偶发读到半条数据，压测难复现 |
| 共享内存自旋等对端 | 两个核 100%，容器配额下直接节流 |
| 用信号传业务事件 | 同种信号合并、异步执行、不可测试 |
| 管道传大对象 | 64KB 缓冲反复阻塞，吞吐被切成小块 |
| 忽略 `PIPE_BUF` | 多写者时消息交错，逻辑错乱 |
| 认为 unix dgram 不会丢 | 队列深度 10，突发即丢 |

## 三条铁律

> 🔑 **先问边界，再问速度**：字节流协议不定义分帧，快 10 倍也会在第一次粘包时崩。

> 🔑 **共享内存省的是拷贝，不是同步**：省下的两次拷贝，会用内存屏障、超时、崩溃恢复还回来。

> 🔑 **跨机能力是架构约束，不是性能优化**：同机 unix socket 与 TCP 打平，所以“以后可能拆”就该一开始用 TCP。

## 生产落地：指名 → 可抄 → 可验 → 可退

指名：**Go 标准库 `os.Pipe` / `net.Listen("unix")` / `syscall.Mmap`**（替代品：`golang.org/x/sys/unix` 的 `ShmOpen`；C 侧 `pipe(2)`/`shm_open(3)`）。

**可抄**（完整可运行，两个进程由程序自己 fork）：

```go
// 共享内存 ping-pong：父进程写 seq，子进程回 ack
fd, _ := os.OpenFile("/dev/shm/ipcbench", os.O_RDWR|os.O_CREATE, 0600)
fd.Truncate(8 + 64)
m, _ := syscall.Mmap(int(fd.Fd()), 0, 8+64, syscall.PROT_READ|syscall.PROT_WRITE, syscall.MAP_SHARED)
seq := (*uint32)(unsafe.Pointer(&m[0]))
ack := (*uint32)(unsafe.Pointer(&m[4]))
atomic.StoreUint32(seq, 1)
for atomic.LoadUint32(ack) != 1 {
}
```

**可验**（本机实测输出，不是「形如」）：

```
$ ./ipcbench -kind pipe -mode lat -size 1 -n 20000
kind=pipe size=1 n=20000 mean=2.739µs p50=2.417µs p90=2.584µs p99=5.709µs
$ ./ipcbench -kind unix -mode lat -size 1 -n 20000
kind=unix size=1 n=20000 mean=7.25µs p50=6.5µs p90=8.667µs p99=16.375µs
$ ./ipcbench -kind shm -mode lat -size 1 -n 20000
kind=shm size=1 n=20000 mean=108ns p50=125ns p90=125ns p99=125ns
$ ./ipcbench -kind tcp -mode tput -size 65536 -n 2000
kind=tcp size=65536 n=2000 bytes=131072000 elapsed=0.024s tput=5566.0 MB/s
```

**可退**：共享内存段用 `shm_unlink`/删 `/dev/shm/<name>` 回收（本实测程序退出前 `defer` 删除）；切换到 socket 的过渡期可以两个通道并存，用配置开关切流，观察 `p99` 与 CPU 自旋占比后再摘掉旧通道。

> 💡 语言选择说明：本机 Go 工具链可用（`go1.27.1`），用 `GOOS=linux GOARCH=arm64 CGO_ENABLED=0` 交叉编译出静态二进制，在 `alpine:3.20` 容器里跑；容器 `--rm`，跑完即删。

## 自检

**Q1** 共享内存比 unix socket 快 50 倍，为什么大多数本机服务还是用 unix socket？

▸ 答案：因为 125ns 只是**通知**的成本，不含同步与容错。共享内存需要自己做内存序、阻塞唤醒（否则自旋烧核）、对端崩溃检测、版本与边界校验；而 unix socket 把这些交给内核，还额外给你 fd 传递、鉴权、可被 epoll 管理。**只有数据量足够大（拷贝成本压过同步成本）或延迟要求到 μs 以下时，共享内存才划算。**

**Q2** 两个进程用 TCP loopback 通信，`p99` 抖动大，可能是什么原因？

▸ 答案：先看是不是**同机却走了完整协议栈**：Nagle/延迟确认、`TIME_WAIT` 端口耗尽、`accept` 队列溢出都会放大抖动；同机场景换 unix socket 能直接消掉这一层（实测 6.5μs vs 6.75μs，但抖动更小）。如果必须保留 TCP，检查 `ss -ti` 的重传与 `cwnd`，以及 `somaxconn`/backlog。

**Q3** 管道传 1MB 消息，吞吐只有几十 MB/s，瓶颈在哪？

▸ 答案：在**64KB 的环形缓冲**（实测 `F_GETPIPE_SZ = 65536`）。写满就阻塞，等于每 64KB 一次完整往返；而且 1MB 写会被拆成多次非原子写（`PIPE_BUF = 4096`）。要么把消息切块并把读端做批量读，要么换共享内存/大 socket 缓冲。

**Q4** 服务用 `SIGUSR1` 通知 worker “配置变了”，压测时偶尔丢更新，为什么？

▸ 答案：**标准信号不排队**：同种信号在 pending 位图里只占 1 位，连续两次只会记 1 次；且处理函数异步执行、能用的 API 极少。正确做法是用 eventfd/管道写一个字节（自带排队与背压），或让 worker 定期检查版本号。

**Q5** 什么时候必须用 `SOCK_SEQPACKET` 而不是 `SOCK_STREAM`？

▸ 答案：当**消息边界是协议的一部分**、又不接受丢包时：stream 需要自己写长度前缀与粘包处理，dgram 保边界但队列满会丢（实测 `max_dgram_qlen = 10`）。seqpacket 同时给你“保边界 + 不丢（背压）”，代价是只能本机。
