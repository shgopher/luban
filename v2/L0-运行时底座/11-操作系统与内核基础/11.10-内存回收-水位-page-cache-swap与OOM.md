# 11.10 内存回收：水位、page cache、swap 与 OOM

## 一句话

> 内存回收是一台**有水位线的泵**：剩余内存跌到 `low` 就由 `kswapd` 异步抽水，跌到 `min` 就让分配者自己下场同步抽水（direct reclaim），抽不动才轮到 OOM——看懂水位和「页面能不能丢」，就不再把 `free` 变小误判成内存不足。

## free 的五个数：先把「free 少就是内存不足」拆掉

`free` 一张表六列，最容易读错的是第三列和最后一列。原案例机器（2 CPU / 8GB）的输出：

```
# 注意不同版本的 free 输出可能会有所不同
$ free
              total        used        free      shared  buff/cache   available
Mem:        8169348      263524     6875352         668     1030472     7611064
Swap:             0           0           0
```

| 列 | 口径 | 常见误读 |
|---|---|---|
| `total` | 物理内存总量 | —— |
| `used` | 已用内存，**包含共享内存**（共享内存由 tmpfs 实现，所以也包含 tmpfs 占用的那部分） | 以为 `used` 只有进程堆 |
| `free` | **完全未使用**的页 | 以为它等于「还能用多少」 |
| `shared` | 共享内存，实质就是 tmpfs 使用的内存；tmpfs 本身是一种特殊缓存 | 以为它一定是进程间真共享 |
| `buff/cache` | `Buffers` 与 `Cache` 之和；`Cache` = `Cached` + `SReclaimable` | 以为它是「被浪费的内存」 |
| `available` | **新进程可用内存**：剩余内存 + 可回收缓存 | 完全忽略这一列 |

两个口径关系可以直接用上面这组数字验算：

- `total - used - buff/cache = free`：`8169348 - 263524 - 1030472 = 6875352`，对得上。所以 `used` 里既没有 `free`，也没有 `buff/cache`，但**把 `shared` 包了进去**。
- `available - free = 7611064 - 6875352 = 735712`，而 `buff/cache` 有 `1030472`。这两个数不相等，说明内核**只把一部分缓存算成「可回收」**——正在使用中的缓存不能回收。

> 🔑 `free` 少、`available` 多，是**健康**状态而不是内存不足。判断「还能不能再起一个进程」只看 `available`。

还有一处连带的口径差：因为 `used` 把 `shared`（tmpfs）算进去了，所以**把各进程的 RSS 相加，永远不会等于 `used`**。tmpfs 上的文件内容既算「进程用掉的」，又算「页缓存」，只存在于内存里、没有磁盘后端。用 tmpfs 当缓存目录（`/dev/shm`、`/run`）的服务，`used` 会凭空高一截，容量规划时要把这部分算进「不可回收」。

`available` 的直觉公式是 `free + 可回收的 page cache/slab`，再扣掉不可回收的 slab、以及内核为自己保留的低水位余量。

## buffer 与 cache：一个管裸块，一个管文件页

`free` 手册只说了三个值来自 `/proc/meminfo`，真正定义要去 `man proc`：

| 指标 | `man proc` 的定义 | 中文口径 |
|---|---|---|
| `Buffers` | 原始磁盘块的临时存储，不该变得特别大 | 块设备**裸数据**的缓存；元数据、超级块、目录项也走这里 |
| `Cached` | 从磁盘读取文件的页缓存（page cache），不含 SwapCached | **文件页**缓存 |
| `SReclaimable` | Slab 中可回收的部分 | 可回收的内核对象缓存 |
| `SUnreclaim` | Slab 中在内存压力下也回收不了的部分 | 不可回收，只能靠释放对象 |

`Buffers` 通常不会特别大，量级在 20MB 左右——它的作用是**把分散的小写攒成一次大写**。

四个 `dd` 场景把两者的分工钉死了（`vmstat` 的 `buff`/`cache` 单位是 KB，`bi`/`bo` 单位是块/秒，Linux 块大小 1KB，所以等价于 KB/s）：

| 场景 | 命令 | `buff` | `cache` | 结论 |
|---|---|---|---|---|
| 写文件 | `dd if=/dev/urandom of=/tmp/file bs=1M count=500` | 基本不变 | 持续增长 | 写文件进 page cache |
| 写磁盘 | `dd if=/dev/urandom of=/dev/sdb1 bs=1M count=2048` | 涨得快 | 也涨 | 写裸块进 `Buffers` |
| 读文件 | `dd if=/tmp/file of=/dev/null` | 保持不变 | 持续增长 | 读文件进 page cache |
| 读磁盘 | `dd if=/dev/sda1 of=/dev/null bs=1M count=1024` | 涨得快 | 也涨 | 读裸块进 `Buffers` |

由此可见，**`Buffer` 与 `Cache` 在读和写里都用得上**：文档只说 `Cache` 是「从文件读」，但写文件同样占 `Cache`；文档没说 `Buffer` 管读，但读裸磁盘同样占 `Buffer`。

两者还有两个共同点，决定了它们在回收里的地位：

- 都由内核统一按页管理，页面大小 4KB；文件页在 `struct page` 里靠 `mapping` 的最低位区分——1 是匿名页，0 是文件映射。
- **都可被回收**，所以 `free` 把它们合并成一列 `buff/cache`，不再区分谁是谁。

## page cache 的双刃：读加速，写甩锅

**读的一侧是纯收益。** 原案例机器上，同一个 512MB 文件用 `dd` 读两次：

| 轮次 | 耗时 | 读命中率 | 结果 |
|---|---|---|---|
| 第一次（先 `echo 3 > /proc/sys/vm/drop_caches`） | 16.05s | 49.8% | 33.4 MB/s |
| 第二次（缓存已热） | 0.118s | 100% | **4.5 GB/s** |

`pcstat file` 的 `Cached`/`Percent` 从 0 / 000.000 变成 131072 / 100.000，页数正好是 512MB / 4KB = 131072。同一份数据，差 100 倍以上——这就是命中即零 IO 的含义。**代价是 `dd` 不能当文件系统性能测试工具**，不清缓存测出来的数字严重失真。

**写的一侧是延迟。** `write()` 只是把数据拷进 page cache，脏页由内核稍后回写，应用可以在数据真正落盘前返回。这带来两个后果：

1. 进程看到的「写成功」不等于「已落盘」，掉电会丢。要落盘得显式 `fsync`。
2. 脏页攒多了，总得有人付账——付账的人可能是内核线程 `pdflush`，也可能是**发起写的那个进程自己**（见「脏页回写」一节的 `vm.dirty_ratio`）。

**回收优先级不同，这是理解 swap 的前提。** 文件页（page cache、`Buffer`、内存映射页）**可以直接丢弃**，下次访问再从文件读；被改过的脏页必须先写回磁盘再释放。匿名页（堆、栈）背后没有文件，丢了就真丢了，**只能写进 swap**。所以内存紧张时，内核先动文件页，实在不够才动匿名页。

能不能命中缓存，用 `cachestat`（整机）和 `cachetop`（按进程）看：

```
$ cachestat 1 3
   TOTAL   MISSES     HITS  DIRTIES   BUFFERS_MB  CACHED_MB
       2        0        2        1           17        279
```

| 列 | 含义 |
|---|---|
| `TOTAL` / `MISSES` / `HITS` | 总 IO 次数 / 未命中 / 命中 |
| `DIRTIES` | 新增到缓存中的脏页数 |
| `BUFFERS_MB` / `CACHED_MB` | `Buffers` 与 `Cache` 的 MB 数 |

这两个工具都来自 bcc，靠内核的 eBPF 跟踪页缓存，所以**只在 Linux 上有**，且需要较新的内核（bcc-tools 要求 4.1 以上）。`cachetop` 默认按 `HITS` 排序，输出多两列 `READ_HIT%` / `WRITE_HIT%`。这里有个必须知道的坑：**`cachetop` 不统计直接 IO**。原案例里一个用 `O_DIRECT` 读盘的程序，每秒读 32MB，但 `cachetop` 只显示 1024 次命中——因为一次命中是一页 4KB，`1024 × 4KB / 5s = 0.8MB/s`，跟 32MB/s 差了 40 倍。用 `strace` 看到 `openat(..., O_RDONLY|O_DIRECT)` 才定性。去掉 `O_DIRECT` 后单次 32MB 读取从 0.9 秒降到 0.03 秒，`HITS` 变成 40960（`40960 × 4KB / 5s = 32MB/s`）。

## 水位 min / low / high：三条分配路径

每个 zone 有三个水位，单位是页。`pages_low` 与 `pages_high` 都由 `pages_min` 推算：

```
pages_low  = pages_min * 5 / 4
pages_high = pages_min * 3 / 2
```

`pages_min` 由 `/proc/sys/vm/min_free_kbytes` 间接设置。原案例机器（2 CPU / 8GB）的 `/proc/zoneinfo`：

```
Node 0, zone   Normal
  pages free     227894
        min      14896
        low      18620
        high     22344
     nr_free_pages 227894
     nr_zone_inactive_anon 11082
     nr_zone_active_anon 14024
     nr_zone_inactive_file 539024
     nr_zone_active_file 923986
```

验算：`14896 × 5/4 = 18620`，`14896 × 3/2 = 22344`。`min` 换算成容量约 `14896 × 4KB ≈ 58MB`，`high` 约 87MB。此时 `pages free 227894` 远高于 `high`，所以 `kswapd` 不干活。

| 剩余内存位置 | 含义 | 谁去回收 |
|---|---|---|
| `> high` | 余量充足，无压力 | 没人 |
| `low ~ high` | 有一定压力，但还能满足新请求 | 不触发回收 |
| `min ~ low` | 压力较大，剩余不多了 | **`kswapd` 异步回收**，一直回收到 `> high` 才停 |
| `< min` | 进程可用内存基本耗尽 | **直接回收 direct reclaim**：分配路径上同步回收 |
| 回收后仍不够 | 无内存可给 | **OOM killer** |

三条路径的差别决定了你看到的现象：

| 路径 | 触发条件 | 谁在等 | 用户可见现象 |
|---|---|---|---|
| **快速分配** | 剩余 > `low` | 没人等 | 分配是微秒级，无感 |
| **`kswapd` 异步回收** | `low` ~ `min` 之间 | 内核线程在后台等 | CPU 的 `sys` 升高、`wa` 升高，请求延迟略抖 |
| **直接回收** | 低于 `min` | **发起分配的进程自己** | 延迟尖刺、吞吐塌陷，极端时整机「假死」 |

`kswapd` 是一个在系统初始化时就创建的内核线程，进一个无限循环：内存不紧张就睡，紧张了就检查要不要换出页面。它的调用链是 `balance_pgdat -> kswapd_shrink_node -> shrink_node`，**以内存节点为单位**。直接回收走的是另一条链：分配页时 `get_page_from_freelist` 找不到空闲页，就 `node_reclaim -> __node_reclaim -> shrink_node`，同样以节点为单位。两条链最终都落到 `shrink_node`，所以「谁在回收」只影响**谁阻塞**，不影响回收算法。

`shrink_node` 往下是 `shrink_node_memcg`，遍历 LRU 链表。页面分两类——匿名页与文件映射页——**每类都有 active 与 inactive 两个链表**，页会在两者间迁移；要换出时，从不活跃链表里挑最不活跃的。`shrink_active_list` 先把活跃页降级，`shrink_inactive_list` 才真正回收：文件映射页把修改回写文件，匿名页要分配 swap 空间再写出去。所以 `/proc/zoneinfo` 里的 `nr_zone_active_anon` / `nr_zone_inactive_anon` / `nr_zone_active_file` / `nr_zone_inactive_file` 是判断「回收会往哪边走」的第一手材料。

再往下就是物理内存的组织方式：节点 → zone（`DMA` / `DMA32` / `NORMAL` / `HIGHMEM` / `MOVABLE`）→ 页，页由伙伴系统按 2 的 order 次方成块分配（最大 1024 页 = 4MB），小于一页的对象交给 slub 切成小块。`ZONE_MOVABLE` 的存在是为了把可移动与不可移动的分配分开、减少碎片；32 位系统 `ZONE_HIGHMEM` 是超过 896MB 的那一段，64 位不需要。这与 [11.2 内存管理与虚拟内存](11.2-内存管理与虚拟内存.md) 讲的地址转换是同一套物理页的两种视角。

伙伴系统按 2 的 order 次方分配，这带来一个容易误判的失败模式：**碎片化可以让高 order 的分配失败，尽管空闲页总数看起来还很多**。内核自己的处理是降级——先按正常 order 申请，失败就退到该缓存的最小 order（`kmem_cache_order_objects` 里的 `min`），再不行才走回收。所以「`available` 还很充裕却报分配失败」不是矛盾，而是连续大块没了；判断看 `/proc/buddyinfo` 里各 order 的空闲块数量，而不是 `free`。

**观测三个计数器就能判断有没有发生直接回收**（`/proc/vmstat`）：

| 字段 | 含义 | 读法 |
|---|---|---|
| `pgscan_direct` / `pgscan_kswapd` | 直接回收 / 后台回收扫描的页数 | `pgscan_direct` 持续增长 = 已经掉到 `min` 以下 |
| `pgsteal_direct` / `pgsteal_kswapd` | 真正回收成功的页数 | `pgscan` 远大于 `pgsteal` 说明扫了很多但回收不动（典型是全是匿名页且 swap 不足） |
| `allocstall`（及各 zone 的 `allocstall_*`） | 分配被迫等待回收的次数 | 非零且在涨 = 延迟尖刺的硬件证据 |

## 脏页回写：`write()` 什么时候变成慢调用

page cache 把「写」变成「攒」，攒到阈值就得还账。三个旋钮分工不同：

| 参数 | 作用 | 触发的后果 |
|---|---|---|
| `vm.dirty_background_ratio` | 脏页占总内存的比例达到它，唤醒后台回写 | 后台线程开始刷，**应用不受影响**（本机实测默认 10） |
| `vm.dirty_ratio` | 达到它，**写进程自己同步回写** | `write()` 从微秒级变成毫秒级甚至更久（本机实测默认 20） |
| `vm.dirty_expire_centisecs` | 脏页「年龄」超过它就该回写 | 控制数据最多在内存里待多久，影响丢数据窗口而非延迟 |

> 🔑 **突发大量写把 `write()` 变成慢调用，元凶几乎总是 `vm.dirty_ratio`**：脏页一旦顶到这个比例，内核不再替你攒，直接在 `write()` 里同步刷盘。

这个机制解释了一类非常迷惑的现象：某个服务平时 P99 是 2ms，每隔一段时间冒出一个 200ms 的写延迟尖刺，CPU 不高、GC 正常、磁盘 util 也没满。原因不是磁盘慢，而是**脏页攒过头了，那一批 `write()` 被摊上了同步回写**。判断方法：`/proc/vmstat` 的 `nr_dirty` / `nr_writeback` 在尖刺时刻冲高，`sar -r` 的 `kbdirty` 同步抬高。

写延迟和回收还会互相放大：回写把脏页变干净页，干净文件页最容易回收；但如果磁盘本身已经满了，回写变慢，脏页回收不动，`kswapd` 扫了也白扫（`pgscan` 涨、`pgsteal` 不涨），最终滑向直接回收。文件系统与 IO 栈的分层见 [11.3 文件系统与 IO 模型 (阻塞 / 非阻塞 / 异步)](11.3-文件系统与IO模型.md)。

## swap：只换匿名页，`swappiness` 不是开关

swap 把一块磁盘空间或一个本地文件当成内存用，包含**换出**（写盘、释放内存）与**换入**（读回内存）两个过程，实质是把可用内存变大。

它只对**匿名页**有效——堆、栈这些背后没有文件的页，丢掉就没了，只能挪到 swap 里；文件页不需要 swap，直接丢缓存即可。这也解释了为什么明明剩余内存还很多，swap 却在涨：**回收是按 zone 判断的，不是按整机判断的**（跨节点回退与 `zone_reclaim_mode` 见 [11.6 CPU Cache 与 NUMA](11.6-CPU-Cache与NUMA.md)）。

`/proc/sys/vm/swappiness` 调的是**倾向**，不是开关：

- 范围 0–100，**不是内存百分比**，是「回收匿名页 vs 回收文件页」的权重。
- 数值越大越积极用 swap，也就是越倾向回收匿名页；数值越小越倾向回收文件页。
- 即使设成 0，当「剩余内存 + 文件页」小于页高阈值时，**仍然会发生 swap**。原案例机器上这个默认值是 60，属于相对中性的配置。

同一个 `dd` 大文件读的案例（2 CPU / 8GB），能看清这套配合：`dd if=/dev/sda1 of=/dev/null bs=1G count=2048` 跑起来后 `sar -r -S 1` 显示 `%memused` 从 23% 一路涨到 98.13%，其中 `kbbuffers` 涨到 6530440 KB，而 swap 只用了 4096 KB（`%swpused 0.05`）。用 `cachetop` 一看，`dd` 的读命中率只有 50%，`MISSES` 41022 页——缓冲区就是它吃掉的。

那为什么 swap 也动了？因为 `watch -d grep -A 15 'Normal' /proc/zoneinfo` 显示 `pages free` 在 `low` 附近来回抖：一低于 `low`，内核就同时回收文件页和匿名页——缓存被回收导致 `kbbuffers` 下降，匿名页被回收导致 swap 上升；接着 `dd` 继续跑，剩余内存又变成缓存。多次重跑还会发现「有时 swap 用得多，有时缓冲区波动更大」，因为 60 的 `swappiness` 让内核两种都回收。

| 现象 | 指标 | 结论 |
|---|---|---|
| `pswpin` / `pswpout` 持续非零 | `/proc/vmstat` | 有真实换入换出，不是「曾经用过一次」 |
| `SwapUsed` 涨但 `pswpout` 不动 | `/proc/meminfo`、`vmstat` 的 `si/so` | 可能是历史遗留，看趋势不看快照 |
| `si`/`so` 每秒都在动 | `vmstat 1` | **swap 抖动（thrashing）**：页刚换出又被访问，来回搬 |
| `%swpcad` 高 | `sar -S` | 换出的页里有大量被缓存共享的部分，回收效率低 |

**swap 抖动为什么是延迟灾难**：内存访问是纳秒级，SSD 是约 100 微秒级，机械盘更慢。一次换入就是一次 major page fault，进程被阻塞等磁盘。抖动意味着这不是偶发一次，而是每秒多次——延迟从微秒直接跳到毫秒级，且 CPU 大量时间耗在 `sys` 与 `wa` 上。这类问题扩容内存能解，调参数只能缓解。

**谁被换出了？** 看 `/proc/<pid>/status` 的 `VmSwap`，按它排序：

```
$ for file in /proc/*/status ; do awk '/VmSwap|Name|^Pid/{printf $2 " " $3}END{ print ""}' $file; done | sort -k 3 -n -r | head
dockerd 2226 10728 kB
docker-containe 2251 8516 kB
snapd 936 4020 kB
networkd-dispat 911 836 kB
polkitd 1004 44 kB
```

**容器里的 swap**：cgroup v2 用 `memory.swap.max` 限制可用的 swap 量，设成 0 等于对这部分内存关闭 swap。Kubernetes 默认要求节点关闭 swap（kubelet 的 `failSwapOn` 默认生效时，带 swap 的节点会启动失败），原因是：swap 让「内存超卖」变得不可预测，QoS 分级与驱逐判断都建立在「内存是真的」这个前提上，详见 [7.9 资源限制与 QoS](../7-容器编排/7.9-资源限制与QoS.md)。

## OOM killer：杀谁、日志在哪

触发条件只有一个：**回收失败后仍然无法满足这次分配**。顺序是「先回收（缓存 → swap），回收不动才杀进程」。所以 OOM 不是第一现场，而是最后现场——真到 OOM，前面通常已经经历了一轮 `kswapd` 与直接回收带来的延迟恶化。

选择依据是 `oom_score`：进程消耗内存越大分越高，占用 CPU 越多分越低。管理员可以通过 `/proc` 手动调整：老接口是 `oom_adj`，范围 `[-17, 15]`，数值越大越容易被杀，`-17` 表示禁止 OOM：

```
echo -16 > /proc/$(pidof sshd)/oom_adj
```

新内核用 `oom_score_adj` 取代 `oom_adj`，取值更细（以 `man proc` 的本机定义为准）。`/proc/<pid>/oom_score` 是只读的当前得分。

日志在 `dmesg` 里，形态是 `Out of memory: Kill process <pid> (<name>) score <n> ...`，用 `dmesg -T | grep -i "out of memory\|oom"` 捞。

> 🔑 **被杀的不一定是内存大户**。触发 OOM 的是**那一次分配**，不是「谁用得最多」——一个刚 `malloc` 了大块内存的小进程可能第一个死；cgroup 限制下，记账是**按 cgroup 算的**，同一个 cgroup 里谁分配谁倒霉。

容器里要分清两种 OOM：

| 类型 | 触发点 | 证据 | 影响面 |
|---|---|---|---|
| 整机 OOM | 整机 zone 回收失败 | `dmesg` 有 `Out of memory` | 可能杀掉任意进程，宿主机重伤 |
| cgroup OOM | 该 cgroup 的 `memory.max` 触顶 | `/sys/fs/cgroup/<path>/memory.events` 的 `oom` / `oom_kill` 计数增加 | 只杀该 cgroup 内的进程，能查到确切计数 |

```
$ cat /sys/fs/cgroup/<path>/memory.events
low 0
high 0
max 12
oom 3
oom_kill 3
```

`oom_kill` 和 `oom` 计数一致通常说明每次触顶都真的杀了人；`max 12` 说明有 12 次触到硬上限。配合 `memory.current`、`memory.stat` 的 `anon` / `file` 判断是匿名页超了还是 page cache 占着（容器里 page cache 也算进 cgroup 记账，这是「机器内存充足但容器被杀」的最常见原因）。cgroup 的记账与隔离机制见 [6.3 namespace (隔离) 与 cgroups (限制)](../6-容器技术/6.3-namespace与cgroups.md)。

## 内存泄漏与「假泄漏」

**真泄漏的判据不是「涨」，而是「释放后不回落」。**

| 判据 | 真泄漏 | 假泄漏 |
|---|---|---|
| 业务空闲、触发一轮释放后 | RSS 不降或只轻微下降 | RSS 明显回落 |
| `smaps_rollup` 的 `Anonymous` | 持续单调增长 | 平稳或周期性回落 |
| `smaps_rollup` 的 `Pss` | 与 `Anonymous` 同向增长 | 远小于 RSS（差在 page cache 与共享库） |
| `/proc/<pid>/status` 的 `VmRSS` vs `VmSwap` | `VmRSS` 涨、`VmSwap` 不动 | 两者交替，总量稳定 |
| heap profile / 分配栈 | 同一调用栈的未释放分配持续累积 | 分配点分散、无稳定栈 |

定位手法有三层，从粗到细：

1. **看趋势**：`vmstat 3` 看 `free` 是否单调下降，而 `buff`/`cache` 基本不变。原案例的斐波那契程序就是这样被抓住的——`free` 一直掉，`buff`/`cache` 不动，说明吃内存的是进程而不是缓存。注意「`free` 下降」只能证明**有人在用**，不能证明**泄漏**，动态增长的数组也会这样。
2. **抓分配栈**：`memleak -a -p $(pidof app)`（bcc 提供，默认 5 秒汇总一次未释放的分配与调用栈）。原案例看到 `fibonacci+0x1f` 反复分配 `8192` 字节不释放，`40960 bytes in 5 allocations`。坑是容器里跑的程序会报 `Couldn't find .text section in /app`，因为 `memleak` 在容器外访问不到 `/app`；`docker cp app:/app /app` 复制出来后就能解析符号。同类工具还有 `valgrind --leak-check=full`（需要重启进程、开销大，适合测试环境）。
3. **看进程内部**：`pmap` 看地址空间分布，`smaps`/`smaps_rollup` 看每段的 `Rss`/`Pss`/`Anonymous`/`Private_Dirty`。注意**不能把各进程 SHR 相加**统计总内存，会重复计算共享库与页缓存；要按 `Pss` 归纳。

**四类高频「假泄漏」**：

| 假泄漏 | 表现 | 为什么不是泄漏 |
|---|---|---|
| page cache | `free` 掉了、`buff/cache` 涨了 | 可回收，`available` 没怎么变 |
| glibc arena 不归还 | 多线程 `malloc` 后 RSS 不降 | `brk` 的小块内存（<128K）释放后缓存复用，属于分配器保留；`mallopt(M_ARENA_MAX)` / `M_TRIM_THRESHOLD` 可调 |
| Go 的堆保留 | GC 后 RSS 不降 | 运行时向 OS 要了内存就不急着还，用 `GOMEMLIMIT` 与 `debug.FreeOSMemory` 约束，见 [15.4 GC 原理与调优 (GOGC / GOMEMLIMIT)](../15-语言运行时/15.4-GC原理与调优.md) |
| JVM 未设上限 | RSS 缓慢爬升、无 OOM | 堆按宿主机而非 cgroup 设上限，`-Xmx` 没配或配太大；GC 日志里堆稳定就不是泄漏 |

大块内存（>128K）走 `mmap`，释放时**直接归还系统**，代价是每次 `mmap` 都伴随缺页异常；小块走 `brk`，释放后缓存复用，减少缺页但会留碎片——这条 128K 分界线是判断「RSS 为什么不还」的第一把尺。栈不需要管：栈内存由系统自动分配回收，超出作用域就没了，不会泄漏；只读段（代码、常量）与数据段（全局、静态变量）在定义时大小就定了，也不会泄漏。**只有堆和文件映射段（共享内存）需要应用自己管。**

## NUMA 与回收：一段结论

NUMA 下每个节点有自己的本地内存，**本地节点分配失败时可以跨节点回退**（`node_zonelists` 就是备用节点与区域列表），代价是访问延迟更高。于是会出现「整机 `available` 还很充裕，但某个节点的 `pages_free` 已经低于 `low`」——回收与 swap 是按节点/zone 触发的，所以**必须按节点看，不能只看整机 `free`**。本地内存不足时怎么办由 `/proc/sys/vm/zone_reclaim_mode` 决定：默认 `0` 表示既可以从其他节点找空闲内存、也可以从本地回收；`1`/`2`/`4` 都表示只回收本地内存，其中 `2` 允许回写脏数据回收，`4` 允许用 swap 回收。用 `numactl --hardware`（原案例机器只有 1 个节点：`node 0 cpus: 0 1`、`node 0 size: 7977 MB`、`node 0 free: 4416 MB`）看拓扑，策略取舍见 [11.6 CPU Cache 与 NUMA](11.6-CPU-Cache与NUMA.md)。

## 排障总表：症状 → 指标 → 工具 → 常见根因

| 症状 | 关键指标 | 工具 | 常见根因 |
|---|---|---|---|
| 可用内存骤降 | `available` 而不是 `free`；`buff/cache` 是否同步涨 | `free`、`vmstat 1`、`/proc/meminfo` | 大文件读/拷贝把 page cache 撑起来；或进程匿名页真涨了 |
| swap 持续上涨 | `pswpin`/`pswpout`、`si`/`so`、`%swpused` | `vmstat 1`、`sar -r -S 1`、`/proc/zoneinfo` | 匿名页多且内存紧；`swappiness` 偏大；本地节点不足跨节点回退失败 |
| swap 抖动 | `si`/`so` 每秒非零，`wa` 高 | `vmstat 1`、`sar -B`、`/proc/<pid>/status` 的 `VmSwap` | 工作集大于物理内存，刚换出就被访问 |
| OOM 重启 | `dmesg` 的 `Out of memory`、`oom_score` | `dmesg -T`、`journalctl -k` | 真泄漏；堆未按 cgroup 设上限；缓存把可用内存挤没 |
| 延迟尖刺（周期性） | `nr_dirty`/`nr_writeback` 与尖刺时刻对齐 | `sar -r`、`/proc/vmstat`、`iostat -x` | 脏页顶到 `vm.dirty_ratio`，写进程被迫同步回写 |
| 延迟尖刺（随机） | `pgmajfault`、`allocstall` | `perf`、`/proc/vmstat`、`pidstat -r` | major fault 读盘；或直接回收在分配路径上同步扫页 |
| direct reclaim | `pgscan_direct`、`pgsteal_direct`、`allocstall` 增长 | `/proc/vmstat`、`/proc/zoneinfo` 的 watermark | 剩余内存跌破 `min`；`min_free_kbytes` 设置不当；匿名页不可回收 |
| cache 命中率低 | `HITS`/`MISSES`、`READ_HIT%`、`pcstat` 的 `Percent` | `cachestat`、`cachetop`、`pcstat` | 工作集大于可用缓存；用了 `O_DIRECT`；每次读完就换文件 |
| 容器被杀但机器内存充足 | `memory.events` 的 `oom`/`oom_kill`、`memory.current` | cgroup 文件系统、`crictl`/`kubectl describe` | 容器内 page cache 与匿名页合计触到 `memory.max`；堆按宿主机设上限 |
| 频繁 major fault | `pgmajfault`、`%vmeff`、`bi` | `vmstat`、`sar -B`、`/proc/<pid>/stat` | swap 抖动；文件未预热；内存不足导致缓存被反复丢弃 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 `free` 第三列判断内存是否够用 | 把可回收缓存当已耗尽，盲目扩容或重启服务 |
| 看到 swap 非零就 `swapoff -a` | 匿名页无处可去，直接滑向 OOM Kill |
| 把 `swappiness=0` 当「关闭 swap」 | 剩余内存 + 文件页跌破页高阈值时照样换出 |
| 靠调大 `min_free_kbytes` 解决 OOM | 可用内存更少，回收更早触发，OOM 来得更快 |
| 用 `dd` 不清缓存测磁盘性能 | 测到的是 page cache 的 4.5 GB/s，不是磁盘的 33 MB/s |
| 把 `memleak` 的 `[unknown]` 栈当无泄漏 | 容器路径不可见导致符号解析失败，漏掉真问题 |
| 把各进程 SHR 相加算总内存 | 共享库与页缓存被重复计算，得出天文数字 |
| 容器堆上限按宿主机内存设 | 触到 `memory.max` 被 cgroup OOM Kill，机器却「很空」 |

## 三条铁律

> 🔑 **只看 `available`**：`free` 少不代表不够用，`available` 才是「新进程还能拿到多少」。

> 🔑 **先看 `pgscan_direct` 与 `allocstall`**：它们非零，说明内存压力已经落到分配路径上，延迟问题一定跟着来。

> 🔑 **swap 是「延迟换容量」**：省下的是内存，付出的是毫秒级 major fault；抖动一旦发生，调参无用，只能加内存或减工作集。


失败判据：`memory.events` 里 `oom_kill` 大于 0，而宿主机 `dmesg` 没有 `Out of memory` —— 这是 cgroup OOM，不是整机 OOM。

**cgroup OOM 实测**：用 `--memory=64m --memory-swap=64m` 起容器，挂一个 256MB 的 tmpfs 再 `dd` 写 200MB（tmpfs 页同样计入 cgroup 记账）。

```bash
$ cat /sys/fs/cgroup/memory.max
67108864          # 64MiB
$ dd if=/dev/zero of=/mnt/hog/f bs=1M count=200
Killed            # dd 被 cgroup OOM 杀掉，shell 打印的是这一行

$ cat /sys/fs/cgroup/memory.events
low 0
high 0
max 128          # 触顶次数
oom 1
oom_kill 1       # 真的杀了一个进程
```

`dmesg` 里的铁证（注意 `constraint=CONSTRAINT_MEMCG` 与 `oom_memcg=/docker/<容器id>`，说明是**这个容器**超了，不是整机）：

```
oom-kill:constraint=CONSTRAINT_MEMCG,nodemask=(null),oom_memcg=/docker/7ca3a575...,task=dd,pid=1135
Memory cgroup out of memory: Killed process 1135 (dd) total-vm:2740kB, anon-rss:1068kB,
file-rss:940kB, shmem-rss:0kB, UID:0 pgtables:44kB oom_score_adj:0
```

三个可复现细节：① `memory.peak` 正好顶到 `67108864`；② 被杀的是 `dd`，不是占内存最多的那个进程（谁触发那次分配谁倒霉）；③ `oom_group_kill 0` 表示只杀单进程，设了 `memory.oom.group=1` 才会整组杀。

**④ 调脏页阈值与回滚（默认值已实测，改动未实测）**

```bash
# 调前先留档，这是回滚的唯一依据
sysctl -a 2>/dev/null | grep -E "^vm\.(dirty_ratio|dirty_background_ratio|dirty_expire_centisecs|swappiness|min_free_kbytes)" | tee /tmp/vm.before

# 降低同步回写的上限，让尖刺变平（代价：更早、更频繁地回写，总写带宽略降）
sysctl -w vm.dirty_background_ratio=5
sysctl -w vm.dirty_ratio=10

# 验证：观察 nr_dirty 是否被压在更低的水位，同时记录应用写延迟
watch -n 1 'grep -E "^(nr_dirty|nr_writeback)" /proc/vmstat'
```

回滚（调到比现值更大是危险方向，先回滚再评估）：

```bash
sysctl -w vm.dirty_background_ratio=10
sysctl -w vm.dirty_ratio=20
# 或用调前留档的值逐个还原：sysctl -w vm.dirty_ratio=<留档值>
```

永久生效写 `/etc/sysctl.d/99-vm.conf` 后 `sysctl --system`；回滚就是删掉该文件再 `sysctl --system`。**没跑过的机器不要把这两个比例调到比默认更低还叠加 `min_free_kbytes` 调大**，两件事同向会加速 OOM。

**⑤ swap 空间清理（可回滚）**

```bash
swapoff -a && swapon -a    # 关掉再打开，等于把 swap 里的页全部换入并重开
```

这是常用的 swap 清理手法，但前提是**剩余内存装得下 `SwapUsed`**；装不下时 `swapoff` 本身就会触发 OOM。清理前先 `grep SwapUsed /proc/meminfo` 确认。

## 自检

**Q1** 一台 8G 机器 `free` 只剩 100M，`available` 还有 3G，正常吗？

▸ 答案：正常。`free` 只统计完全未使用的页，`buff/cache` 里的干净文件页随时可丢。`available = free + 可回收的 page cache/slab`（扣掉不可回收部分与内核保留），3G 才是新进程能拿到的量。原案例机器的验算：`available - free = 735712KB`，而 `buff/cache` 有 `1030472KB`——内核只把其中一部分算成可回收。要说异常，异常的是「`available` 也在快速下降」，那才是真在吃内存。

**Q2** 服务 `write()` 偶发卡 200ms，CPU 不高、GC 正常、`iostat` 的 util 也没满，最可能是什么？

▸ 答案：脏页顶到 `vm.dirty_ratio`，那一批 `write()` 被强制同步回写。判定证据是尖刺时刻 `/proc/vmstat` 的 `nr_dirty`/`nr_writeback` 冲高、`sar -r` 的 `kbdirty` 同步抬高。修法是把 `vm.dirty_background_ratio` 调低让后台更早介入，而不是换更快的盘——盘没问题，是攒太多了。如果尖刺伴随 `pgscan_direct` 与 `allocstall` 上涨，那就不是脏页，是直接回收在分配路径上同步扫页。

**Q3** swap 用了 2G，一定是问题吗？

▸ 答案：不一定，看两个东西。第一看**趋势**：`pswpout` 早就不动了 = 历史遗留，进程冷下来的匿名页躺在 swap 里，不产生任何延迟；`si`/`so` 每秒都在动 = 抖动，每次访问都是毫秒级 major fault，这是真问题。第二看**是否可回收**：`swappiness=0` 时，当「剩余内存 + 文件页」小于页高阈值照样会换出，说明当时确实紧张过。判断标准是延迟，不是 `SwapUsed` 这个数字本身。

**Q4** 容器 OOM 了，但宿主机 `free` 还有一半内存，为什么？

▸ 答案：因为记账单位是 cgroup 不是整机。容器的 page cache 也算进 `memory.current`，一旦合计触到 `memory.max`，就在**该 cgroup 内**触发 OOM，只杀这个 cgroup 的进程。判定要同时看两处：`memory.events` 里 `max`/`oom`/`oom_kill` 增长；`dmesg` 里出现的是 **`Memory cgroup out of memory`** 且带 `constraint=CONSTRAINT_MEMCG`、`oom_memcg=/docker/<id>`，而不是整机那条 `Out of memory: Kill process`（实测两者格式不同）。根因通常是堆上限按宿主机内存设的（比如 8G 机器给 JVM `-Xmx6g`），没给 page cache、栈、堆外留余量。另外要记住：被杀的不一定是内存大户，谁触发那次分配谁倒霉（实测杀的是正在 `dd` 的那个进程）。

**Q5** 服务 RSS 只涨不降，怎么判断是真泄漏还是缓存/arena/堆保留？

▸ 答案：做「释放后是否回落」的实验，再看拆分。①业务空闲或主动触发一轮释放后，`VmRSS` 是否回落；②`smaps_rollup` 的 `Anonymous` 是否单调增长（真泄漏通常是），`Pss` 与 `RSS` 是否差得很多（差在 page cache 与共享库）；③`VmSwap` 是否同步增长；④用 `memleak` 看是否有同一调用栈的未释放分配在累积——这一步才定性。另外先排除四个最常见的假泄漏：page cache（`buff/cache` 涨、`available` 没怎么掉）、glibc arena 不归还（<128K 走 `brk`，释放后缓存复用）、Go 的堆保留（GC 后不还给 OS）、JVM 未按 cgroup 设 `-Xmx`。
