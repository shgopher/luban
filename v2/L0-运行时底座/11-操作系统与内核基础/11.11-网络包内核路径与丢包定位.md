# 11.11 网络包的内核路径与丢包定位

## 一句话

> 一个包发出要过五关（VFS → socket → TCP → IP/netfilter → qdisc → 驱动），收进也要过五关（ring → NAPI → L2/L3 → netfilter → socket 队列）；**丢包必然发生在其中某一层，定位就是拿计数器把它指出来**，不是靠猜。

## 两级数据结构：socket 管进程，sock 管协议栈

`socket()` 系统调用按 `family → type → protocol` 三级索引找操作表：`sock_create` → `__sock_create` 里 `sock_alloc()` 分配 `struct socket`，再以 `family` 为下标查 `net_families[]` 得到 `inet_family_ops`，调 `inet_create`；`inet_create` 再以 `type` 为下标遍历 `inetsw[type]` 链表，按 `protocol` 匹配到 `struct inet_protosw`（TCP 命中的是 `tcp_prot` + `inet_stream_ops`），随后 `sk_alloc()` 分配 `struct sock`，`sock_init_data` 把两者互指，`sock_map_fd` 把 socket 挂到一个 fd 上。

| 维度 | `struct socket` | `struct sock` |
|---|---|---|
| 面向谁 | 进程、VFS、文件描述符 | 内核网络协议栈 |
| 怎么创建 | `sock_alloc()`，再由 `sock_map_fd` 关联 fd | `sk_alloc()`，`sock_init_data` 绑定 |
| 操作表 | `sock->ops = inet_stream_ops` | `sk->sk_prot = tcp_prot` |
| 典型成员 | `state`、等待队列、`file` | `sk_state`、`sk_write_queue`、`sk_receive_queue`、`sk_rcvbuf` |
| 谁调它 | `bind/listen/accept/connect/sendmsg/recvmsg` 系统调用入口 | `inet_bind`、`inet_csk_get_port`、`tcp_sendmsg`、`tcp_recvmsg` |

同一个结构被反复"套娃"扩展：`struct inet_sock` 开头是 `struct sock`，`struct inet_connection_sock` 开头是 `inet_sock`，`struct tcp_sock` 开头是 `inet_connection_sock`。所以 `tcp_sk(sk)`、`inet_sk(sk)` 只是强制类型转换，零成本。**TCP 的连接状态、拥塞窗口、滑动窗口全在 `tcp_sock` 里，不在 `socket` 里。**

### 五个队列，两套记账

| 队列 | 挂在哪 | 放什么 | 满了的后果 |
|---|---|---|---|
| `sk_write_queue` | `sock` | 已拷进内核、未被确认的 skb | `sk_stream_memory_free` 失败 → 阻塞或 `EAGAIN` |
| `sk_receive_queue` | `sock` | 序号连续、可交付给应用的 skb | 通告窗口收窄，对端停发 |
| `prequeue` | `tcp_sock` | 进程正在 `read` 时，软中断暂存的包 | 由 `tcp_low_latency` 决定是否启用 |
| `sk_backlog` | `sock` | socket 被用户态持锁时暂存的包 | `tcp_add_backlog` 失败即丢 |
| `out_of_order_queue` | `tcp_sock` | 乱序到达、还不能交付的包 | 等缺口补上，`tcp_ofo_queue` 搬走 |

记账靠两个计数器：发送侧 `sk_wmem_queued`（已占用发送缓冲的字节数），接收侧 `sk_rmem_alloc`（接收队列占用）。上限是三层叠加：`setsockopt(SO_SNDBUF/SO_RCVBUF)` → `net.core.wmem_default/rmem_default`（新建 socket 的初值）与 `net.core.wmem_max/rmem_max`（setsockopt 的上限）→ `net.ipv4.tcp_wmem`、`net.ipv4.tcp_rmem`。后两者是**三段式 min/default/max**，内核在这区间里按往返时延和接收速率自动调节，`default` 只是起点，手改 `SO_SNDBUF` 反而会关掉自动调节。

还有两个不在 `struct sock` 里、专管建连的队列：`icsk_accept_queue` 放已完成三次握手的连接，`accept()` 就是从它里面摘一个 `struct sock` 交给新 fd——`inet_csk_accept` 取不到时就走 `inet_csk_wait_for_connect`，`schedule_timeout` 让出 CPU 并置 `TASK_INTERRUPTIBLE`；收到 SYN、回了 SYN-ACK 的半连接（状态 `TCP_SYN_RECV`）挂在另一个队列里。`listen()` 传入的 `backlog` 先被 `somaxconn` 截断（`if ((unsigned int)backlog > somaxconn) backlog = somaxconn;`），再写进 `sk_max_ack_backlog`，这就是后面 ⑤ 里 `Send-Q` 的来源。TCP 状态机里并没有"是否被 accept"这个状态，所以服务端一旦 `listen`，不调 `accept` 也能完成握手，直到队列被塞满为止。

阻塞与 `EAGAIN` 的来源就在这两个计数器上：`tcp_sendmsg` 里先查 `if (!sk_stream_memory_free(sk)) goto wait_for_sndbuf;`，阻塞 socket 睡在 `sk_stream_wait_memory`，非阻塞 socket 直接返回 `-EAGAIN`；读侧 `tcp_recvmsg` 三个队列都空就 `sk_wait_data`，非阻塞则 `-EAGAIN`。epoll 的 `EPOLLOUT`/`EPOLLIN` 通知的就是"这个条件解除了"（见 [11.4 epoll 与 IO 多路复用](11.4-epoll与IO多路复用.md)）。

## 发送路径：从 `send()` 到网卡 DMA

| 层 | 入口 | 干了什么 | 卡住时的表现 |
|---|---|---|---|
| VFS | `write()`/`send()` → `sock_write_iter` → `sock_sendmsg` | 从 `file->private_data` 取回 socket | 无 |
| Socket | `inet_sendmsg` → `sk->sk_prot->sendmsg` | 从 socket 拿到 sock，转协议实现 | 无 |
| TCP 拷贝 | `tcp_sendmsg` | `tcp_send_mss` 算 MSS 与 `size_goal`；`sk_stream_alloc_skb` + `skb_entail` 入 `sk_write_queue`；数据经 `skb_add_data_nocache`（连续区）或 `skb_copy_to_page_nocache`（page frag，配合 SG）拷入 | 缓冲区满 → 阻塞/`EAGAIN` |
| TCP 发送 | `tcp_write_xmit` | `tcp_cwnd_test`（拥塞窗口）、`tcp_snd_wnd_test`（滑动窗口）、`tcp_mss_split_point` 决定在哪分段，`tcp_transmit_skb` 填 TCP 头与校验和 | 窗口为 0 → 停发等待 |
| IP | `ip_queue_xmit` | `ip_route_output_ports` → `fib_lookup` 在 `RT_TABLE_MAIN` 里做 Trie 最长前缀匹配，定网卡与源地址；`skb_push` 填 IP 头；`ip_local_out` 进 OUTPUT 链 | 无路由 → 直接失败 |
| IP 出口 | `ip_output` → `ip_finish_output2` | POSTROUTING 链；查 ARP（`__neigh_create` 未命中就 `neigh_probe` 发 ARP，原包挂 `arp_queue`） | ARP 未解析 → 包暂存排队 |
| L2/qdisc | `__dev_queue_xmit` | `netdev_pick_tx` 选发送队列，`q->enqueue` 入队，`__qdisc_run` 按配额出队 | `NETDEV_TX_BUSY` → `dev_requeue_skb` 回队 |
| 软中断 | `net_tx_action` → `qdisc_run` → `sch_direct_xmit` → `dev_hard_start_xmit` | 调驱动 `ndo_start_xmit`（`ixgb_xmit_frame`）把 skb 放进网卡 ring | ring 满 → `ixgb_maybe_stop_tx` |
| 硬件 | 网卡 DMA | 从 ring 读描述符，把帧发上线 | 无 |

MSS 的来路要记牢：MTU 是二层概念，以太网 1500 字节，加上 6+6 字节 MAC、2 字节类型、4 字节 CRC 共 1518 字节；MSS = MTU − IP 头 − TCP 头。分段由谁做决定 CPU 成本：协议栈里分段费 CPU，`TSO` 把分段推迟到网卡；`tcp_mss_split_point` 里 `max_len = mss_now * max_segs`，多数情况下 `tso_fragment` 不会被调用，等网卡切。

`sk_buff` 是这一切的载体：它本身是个双向链表节点（`next`/`prev`），`headers_start` 到 `headers_end` 之间放着二层 `mac_header`、三层 `network_header`、四层 `transport_header` 的位置；`head` 指向内存块起点，`data` 随层次上下移动（收包时增大 `data` 剥头，发包时减小 `data` 加头），`tail` 是数据尾，`end` 是内存块尾。`__alloc_skb` 分配的数据区后面还跟一个 `skb_shared_info`，里面的 `skb_frag_t frags[]` 指向离散页面——这就是分散聚合 I/O（Scatter/Gather）的基础：不必为拼一个 IP 包把分散数据拷成连续内存，交给网卡聚合即可。`tcp_sendmsg` 里的 `if/else` 两条路就来自这里：`skb_add_data_nocache` 拷进连续区，`skb_copy_to_page_nocache` 拷进 page frag。

滑动窗口把发送方缓冲切成四段，这段划分直接对应 `ss -ti` 里的几个数字：已发送且已确认（可回收）、已发送未确认（必须留着等重传）、未发送但对端窗口允许（可以立刻发）、未发送且超出对端窗口（发不出去）。接收方同理分三段：已收且已确认（可交付应用）、可收但还没到、超出能力。`tcp_snd_wnd_test` 拿 skb 的 `end_seq` 与 `tcp_wnd_end(tp)` 比较，超了置 `is_rwnd_limited`；`tcp_cwnd_test` 拿 `snd_cwnd` 减在途包数算配额。拥塞窗口从 1 个 MSS 起翻倍（慢启动），到 `ssthresh` 转线性（拥塞避免），丢包后退回——细节在 [8.2 拥塞控制、Nagle 与延迟](../8-网络/8.2-拥塞控制-Nagle与延迟.md) 展开，这里只需记住：**发送快慢由 `min(cwnd, rwnd)` 决定，而 `rwnd` 就是接收方 socket 缓冲的余量**。

排队规则决定"第几个包先走"：`pfifo` 纯粹先入先出；`pfifo_fast` 是三个 band，band 0 优先级最高，按 IP 头里的 TOS 分派，`tc qdisc show dev eth0` 输出的 `priomap` 就是 16 个 TOS 到 band 的映射。原案例机器（2018 年环境，内核 4.x）上 `ip addr` 显示 `qdisc pfifo_fast`，较新的发行版常见默认 `fq_codel`，看 `ip addr` 或 `tc qdisc show` 确认，不要背。

> 🔑 **发送侧的阻塞点只有两个**：socket 发送缓冲区满（`sk_wmem_queued` 顶到上限），和 qdisc/ring 满（包留在 qdisc 里，`tc -s qdisc show dev eth0` 的 `backlog` 持续增长）。应用层看到的"发不出去"，九成是前者。

## 接收路径：从网卡 DMA 到 `read()`

| 阶段 | 入口 | 干了什么 |
|---|---|---|
| DMA 入 ring | 网卡硬件 | 把帧写进 `rx_ring` 的 `buffer_info[]`，置描述符 DD 位 |
| 硬中断 | `ixgb_intr` → `napi_schedule_prep` → `__napi_schedule` | 关中断、屏蔽该队列中断，把 napi 挂到本 CPU 的 `softnet_data.poll_list`，`__raise_softirq_irqoff(NET_RX_SOFTIRQ)` |
| 软中断收包 | `net_rx_action` → `napi_poll` → `ixgb_clean_rx_irq` | `while (rx_desc->status & DD)` 批量取包，`skb_put` 定长、`ixgb_rx_checksum` 校验、`eth_type_trans` 定协议 |
| 二层 | `netif_receive_skb` → `__netif_receive_skb_core` | VLAN 处理；按 `skb->protocol` 在 `ptype_all`/`ptype_base` 链表匹配，命中 `ip_packet_type` → `ip_rcv` |
| 三层 | `ip_rcv` → `ip_rcv_finish` | `NF_INET_PRE_ROUTING`（PREROUTING 链）；查路由，`dst_input` |
| 本机投递 | `ip_local_deliver` | 分片重组 `ip_defrag`；`NF_INET_LOCAL_IN`（INPUT 链）；再按 `iph->protocol` 查 `inet_protos[]` |
| 四层 | `tcp_v4_rcv` | `__inet_lookup_skb(&tcp_hashinfo)` 用四元组找 sock；按连接状态分派 |
| 入队/直拷 | `tcp_data_queue` | 序号连续 → `tcp_queue_rcv` 入 `sk_receive_queue`（进程正在读就 `skb_copy_datagram_msg` 直拷）；乱序 → `out_of_order_queue` |
| 唤醒与读 | `tcp_recvmsg` | 依次收 `sk_receive_queue` → `prequeue` → `sk_backlog`，全空就 `sk_wait_data` |

为什么一个包要在三个队列之间倒手？因为它要在三个主体之间交接：软中断（`tcp_v4_rcv` 此刻就跑在软中断里，不能长时间占用 CPU）、用户态进程（`read` 时从队列里取数据）、内核协议栈（进程没在读，包也得有地方待着）。`sock_owned_by_user` 问的就是"现在有没有进程正持着这把锁在读"。

`tcp_v4_rcv` 里那个三选一分支，是全篇最能解释"缓冲区在哪"的一段代码：

| 条件 | 走向 | 为什么 |
|---|---|---|
| `sock_owned_by_user(sk)` 为真（有进程正持锁读写） | `tcp_add_backlog` 放 `sk_backlog`，立刻退出软中断 | 锁被别人拿着，不能在软中断里死等 |
| 为假且 `tcp_low_latency = 0` | `tcp_prequeue` 放 `prequeue` | 不阻塞软中断、把协议处理推迟到进程上下文，代价是多一段时延 |
| 其余 | 直接 `tcp_v4_do_rcv` → `tcp_rcv_established` | 低时延路径 |

`sk_receive_queue` 与 `out_of_order_queue` 的分工用序号就能说清：客户端发 5、6、7、8、9，5 丢了只到了 7、8。服务端 `rcv_nxt = 5`，7、8 不能进 `sk_receive_queue`（TCP 语义要求按序交付），只能进乱序队列；5、6 到达后 `tcp_ofo_queue` 把 7、8 搬过去。第四种情形更绕：`seq < rcv_nxt < end_seq`，说明前半段是重传、后半段是新数据，前半段进 DSACK 记账，后半段允许入队。

## NAPI、软中断与 offload：把中断成本摊平

每包一次硬中断是不可行的：中断要保存/恢复上下文、关中断，包越密集，"进出中断"本身越吃 CPU，真正干活的时间被挤没，这就是中断风暴。NAPI 的折中是**中断 + 轮询**：第一个包触发硬中断，中断处理只做"关中断 + 挂 poll_list + 抛 `NET_RX_SOFTIRQ`"三件事，随后在软中断里按预算批量收（`napi_poll` 有 budget），收完再开中断。N 次中断被压成 1 次，代价是首个包的时延略增。

软中断不等于 `ksoftirqd`：软中断优先在硬中断返回路径上就地执行，跑不完或超预算才唤醒每 CPU 一个的 `ksoftirqd/N`。所以同一个收包动作，可能记在 `si`（软中断）里，也可能以 `ksoftirqd` 进程形态出现在 `top` 里，两者是同一件事的两种落地方式。软中断自身的调度细节见 [11.9 中断、软中断与 CPU 时间去向](11.9-中断-软中断与CPU时间去向.md)。

| 开关 | 在哪看 | 作用 | 注意 |
|---|---|---|---|
| `RSS` 多队列 | `ethtool -l eth0` | 每个队列一个中断号，可绑不同 CPU | 队列数受硬件限制 |
| 中断合并 | `ethtool -c eth0` | 攒够 N 个包或等 T 微秒再中断 | 合并越狠，时延越大 |
| `RPS` | `/sys/class/net/eth0/queues/rx-*/rps_cpus` | 单队列网卡在软件层把包散到多核 | 吃一点 CPU 换并行 |
| `RFS` | `rps_flow_cnt` | 让处理该流的 CPU 与跑应用的 CPU 一致 | 提升缓存命中率、降时延 |
| `TSO/GSO` | `ethtool -k eth0` | 大包交给网卡分段，省协议栈 CPU | 丢包时重传的是分段后的小包 |
| `LRO` | `ethtool -k eth0` | 收侧由网卡合并小包 | **做 IP 转发时不能开**，头不一致会校验错 |
| `GRO` | `ethtool -k eth0` | LRO 的软件通用版，支持 TCP/UDP | 转发场景用它而不是 LRO |
| checksum offload | `ethtool -k eth0` | 校验和交网卡算 | 抓包会看到"校验和错误"，是正常现象 |

收包侧的三级缓冲按顺序承接压力：驱动 ring（`ethtool -g`）→ 每 CPU 的 backlog 队列（`netdev_max_backlog`，`/proc/net/softnet_stat` 第二列记 dropped）→ socket 接收队列（`sk_rmem_alloc` 顶到上限）。哪一级先满，计数器就记在哪一级。

## 零拷贝与发送缓冲

`sendfile`/`splice` 省掉的是"内核缓冲 ↔ 用户缓冲"那两次拷贝与两次系统调用，数据不进用户态，直接由页缓存送到 socket 缓冲（细节见 [11.5 零拷贝](11.5-零拷贝.md)）。发送方向还有一条 `MSG_ZEROCOPY`，让用户态页直接挂在 skb 上发出去，代价是完成通知与页回收复杂，只在超大包高频发送时才值得。

发送缓冲区大小的取舍是吞吐与延迟的对赌：吞吐上限约等于窗口/RTT（见 [8.2 拥塞控制、Nagle 与延迟](../8-网络/8.2-拥塞控制-Nagle与延迟.md)），缓冲区小于带宽时延积就填不满管道；缓冲区过大则排队变长，交互型请求的尾延迟先烂。一条可用的估算口径是：发送缓冲区理想值约为**吞吐量 × 延迟**。

## netfilter 与 conntrack：五条链的过路费

netfilter 是内核在网络路径关键节点上埋的钩子，`iptables` 只是它的用户态配置工具。

| 链 | hook 点 | 在哪个函数里触发 | 典型用途 |
|---|---|---|---|
| PREROUTING | `NF_INET_PRE_ROUTING` | `ip_rcv`（收包，路由判断前） | DNAT、端口映射 |
| INPUT | `NF_INET_LOCAL_IN` | `ip_local_deliver`（收包，投递本机前） | 过滤进本机的包 |
| FORWARD | `NF_INET_FORWARD` | 转发路径 | 网关/容器转发 |
| OUTPUT | `NF_INET_LOCAL_OUT` | `__ip_local_out`（本机发包，路由后） | 过滤本机发出的包、本机 DNAT |
| POSTROUTING | `NF_INET_POST_ROUTING` | `ip_output`（出网卡前） | SNAT、MASQUERADE |

连接跟踪（conntrack）是 NAT 和 `-m state` 状态过滤的地基：它把每个连接记进一张哈希表。表的大小由两个参数决定，`nf_conntrack_max` 是能记多少条，`nf_conntrack_buckets` 是哈希桶数，**每个桶挂一条链表，平均链长 = max / buckets**。内存估算只需要两个系数：连接跟踪对象 376 字节、链表项 16 字节。

```
# 原案例机器：Ubuntu 18.04，2 CPU
net.netfilter.nf_conntrack_count   = 180
net.netfilter.nf_conntrack_max     = 1000
net.netfilter.nf_conntrack_buckets = 65536
# 1000*376 + 65536*16 B ≈ 1.4 MB
```

`nf_conntrack_max = 1000` 撞上 `ab -c 5000` 的并发，结果就是内核日志刷屏：

```
[104235.156774] nf_conntrack: nf_conntrack: table full, dropping packet
[104243.800401] net_ratelimit: 3939 callbacks suppressed
[104243.800401] nf_conntrack: nf_conntrack: table full, dropping packet
```

表满的行为是**丢新连接**（`dropping packet`），不是绕过去或降级，所以症状是"老连接好好的，新连接建不上"，而且 `net_ratelimit` 还会把日志压掉，容易漏看。同样的路径上还有两个热点：容器场景下网桥转发走 `br_nf_pre_routing`，DNAT 走 `iptable_nat_ipv4_in`，原案例用 `perf report` 看到 `nf_hook_slow` 主要就调用这三处。

NAT 的成本是双份的：DNAT 只改去程目的地址，回程必须再做一次 SNAT 才能把源地址换回公网 IP，所以一条连接在 conntrack 上至少两次查表 + 两次改写。原案例在同一台机器上比的：

| 场景 | 每秒请求数 | 每请求延迟 | 建连延迟 |
|---|---|---|---|
| 不用 NAT | 6576 | 760 ms | 177 ms |
| 用 DNAT，`nf_conntrack_max = 1000` | 大量 `table full` 丢包 | — | — |
| 用 DNAT，`nf_conntrack_max = 131072` | 6315 | 791 ms | 355 ms |

即便把表调够，NAT 仍要比直连多约 4% 的 QPS 损失和翻倍的建连延迟。可观测项四个：`conntrack -S`（每 CPU 的 found/insert_failed/drop/early_drop 等统计）、`/proc/sys/net/netfilter/nf_conntrack_count`（当前条数）、`dmesg | tail`（表满告警）、`conntrack -L -o extended | wc -l`（实际条数，可与内核计数交叉验证）。NAT 规则的写法与选型见 [8.8 NAT 与端口映射](../8-网络/8.8-NAT与端口映射.md)。

## 丢包的六个位置与判据

| # | 位置 | 判据 | 命令 | 典型线索（原案例） |
|---|---|---|---|---|
| ① | 物理/链路 | `errors`、`overruns`、`carrier`、`collisions` 增长 | `ip -s link`、`netstat -i` | 线坏、双工不匹配、MTU 配错 |
| ② | 驱动 ring | 驱动私有丢包计数增长 | `ethtool -S eth0`（筛 drop 计数）、`ethtool -g eth0` | veth 无统计，得用 `netstat -i` 的 RX-DRP |
| ③ | 内核 backlog / 软中断预算 | `softnet_stat` 第二列 dropped、第三列 time_squeeze 增长 | `cat /proc/net/softnet_stat` | 单核收包、预算不够 |
| ④ | 协议栈 / netfilter | 协议栈丢包计数与规则计数增长 | `nstat -az`、`netstat -s`、`iptables -nvL`、`dmesg` | `iptables` 两条 30% 随机 DROP，各命中 6 个包 |
| ⑤ | socket 接收队列满 | 监听 socket 的 `Recv-Q` 顶到 `Send-Q`，ListenOverflows 增长 | `ss -lnt`、`netstat -s` 的 listen 段 | `backlog=10`，溢出 290566 → 344440 |
| ⑥ | 应用读得慢 | 已连接 socket 的 `Recv-Q` 持续非零 | `ss -tn state established` | event loop 被阻塞，队列只涨不消 |

①的细节：`ip -s link` 的 `RX: bytes packets errors dropped overrun mcast` 里，`dropped` 是"已进 ring 但因内存不足等原因丢"，`overruns` 是"ring 被写满、来不及取"。原案例的致命线索就藏在这一行——容器 `eth0` 的 `RX-DRP` 从 0 涨到 344，而 `RX-ERR`、`RX-OVR` 都是 0，说明不是线的问题，是包太大进不去。

②的坑：Docker 容器的虚拟网卡是 veth pair，veth 驱动不实现统计，`ethtool -S` 拿不到汇总，只能退到 `netstat -i`。另外 `tc` 配的 qdisc（如 netem）丢的包**不计入网卡统计**，要单独 `tc -s qdisc show dev eth0` 看 `dropped`。

③的读法：`/proc/net/softnet_stat` 每行一个 CPU，字段是十六进制，第一列是处理过的包数，第二列是 dropped（backlog 满），第三列是 time_squeeze（预算用完还没收完）。第二列涨 = backlog 不够或收包太慢；第三列涨 = 软中断被预算掐断，包在 ring 里等下一轮。

④的读法：`nstat -az` 给的是单调递增的协议栈计数器，看差值不看绝对值。最该盯的三个是 `TcpExtListenDrops`（accept 队列溢出丢的 SYN）、`TcpExtTCPBacklogDrop`（`sk_backlog` 满）、`UdpRcvbufErrors`（UDP 接收缓冲满）。`netstat -s` 是同一批数据的另一种排版，`iptables -nvL` 的 `pkts` 列能直接指出哪条 DROP 在吃包。

⑤与⑥必须分开看：监听 socket 的 `Recv-Q` 是**半连接队列当前长度**，`Send-Q` 是该队列上限（即 backlog 与 `net.core.somaxconn` 的较小值，`listen()` 里 `if ((unsigned int)backlog > somaxconn) backlog = somaxconn;`）；已连接 socket 的 `Recv-Q` 是**应用还没取走的字节数**。前者满 → 三次握手就被丢，客户端看到建连超时；后者持续非零 → 服务端读得慢，`tcp_abort_on_overflow = 1` 会让内核在 accept 队列满时回 RST，把"悄悄重试"变成"立刻报错"，便于暴露问题，但也会拒掉本可重试成功的连接。

层定位到之后，若还想知道具体死在哪个内核函数，就得上动态追踪：原案例用 SystemTap 的 `dropwatch.stp` 跟踪 `kfree_skb()` 的调用点，一次压测直接给出 `10031 packets dropped at nf_hook_slow` 与 `676 packets dropped at tcp_v4_rcv`；再用 `perf record -a -g` 展开 `nf_hook_slow` 的调用栈，就锁定了 `ipv4_conntrack_in`、`br_nf_pre_routing`、`iptable_nat_ipv4_in` 三处热点。这类工具的用法见 [11.7 eBPF 与内核态观测](11.7-eBPF与内核态观测.md)。

## tcpdump 看不到什么

抓包不是"看真相"，是"在协议栈的某一个点装了个摄像头"。收方向的抓包点在 `__netif_receive_skb_core` 里 `ptype_all` 那条链表上，位置在**软中断中、三层之前**；发方向的抓包点在 `dev_hard_start_xmit` 之前的 `dev_queue_xmit_nit`，位置在**qdisc 之后、驱动之前**。由此得到三条硬结论：

| 现象 | 能不能抓到 | 说明 |
|---|---|---|
| ring 满、驱动丢的包（收） | 抓不到 | 还没进协议栈，摄像头装在下游 |
| 被 `iptables` PREROUTING/INPUT DROP 的包（收） | **抓得到** | 先被摄像头看到，再被协议栈丢掉——最易误判的一类 |
| 被 qdisc（netem、limit）丢的包（发） | 抓不到 | qdisc 在摄像头之前 |
| 被 `iptables` OUTPUT/POSTROUTING DROP 的包（发） | 抓不到 | 同上，netfilter 在 qdisc 之前 |

所以"服务端 tcpdump 全收到了"只能证明**包到了协议栈二层之后**，不能证明应用收到了。反过来说，"tcpdump 里一个包都没有"也要先分清是没到网卡（① ② 层丢）还是被更前面的设备拦了。交叉验证的方法是拿三份计数对账：`netstat -i` 的 `RX-OK/RX-DRP` 看网卡收了多少、丢了多少；`ethtool -S` 看驱动内部计数；`nstat -az` 看协议栈收了多少。三者对不上，差额就丢在对应的那一段。

## 延迟先拆三段，再谈优化

延迟不是"网络慢"三个字。可测的延迟分两种：网络延迟（单向，或往返 RTT）与应用延迟（从收到请求到发回响应，等于网络传输时间加数据处理时间）。动手前先确认自己在测哪一段：

| 段 | 怎么测 | 看到什么说明什么 |
|---|---|---|
| 链路 RTT | `ping -c3`、`hping3 -c3 -S -p 80`、`traceroute --tcp -p 80 -n` | RTT 稳定但高 = 距离/路由绕行；抖动大 = 拥塞或丢包重传 |
| 内核协议栈 | 抓包看 SYN→SYN-ACK、数据→ACK 的时间差 | 两端"该发就发"却慢，问题不在线路上 |
| 应用处理 | `strace -c`、`pidstat -u 1`、应用自身埋点 | 请求已到、响应迟迟不出 = 应用内部 |

工具链的边界要清楚：`ping` 走 ICMP，服务禁 ICMP 时它给的是假结论，换 `hping3 -S -p 80` 或 `traceroute --tcp`；`hping3` 只发 SYN，验证的是"端口在听"，不代表 HTTP 能通；要测应用层吞吐得用 `wrk`/`ab`。

原案例的两个数字值得记住：官方 Nginx 在 100 并发下平均延迟 9.19ms（99% 分位 50.53ms），案例 Nginx 是 43.60ms（99% 分位 48.88ms）。差值 34ms 落在 TCP 延迟确认最小超时 40ms 这一档上——服务端开着 Nagle（`tcp_nodelay off`），客户端只设了 `TCP_NODELAY`、没设 `TCP_QUICKACK`，于是"服务端等 ACK、客户端等下一个包"互相卡住，每个来回白等 40ms。`strace -f wrk` 只能看到 `setsockopt(SOL_TCP, TCP_NODELAY)`、看不到 `TCP_QUICKACK`，这就是证据。改法一句话：服务端 `tcp_nodelay on`。

## 基准与压测：先把标尺定下来

判断"慢"之前得有基准线。压测按协议层从下往上做，低层能力决定上层天花板：

| 层 | 指标 | 工具 | 原案例数字 |
|---|---|---|---|
| 网络接口层/网络层 | PPS，尤其 64B 小包 | `pktgen`（内核模块，需 `CONFIG_NET_PKTGEN`） | 100 万包 64B：12 万 pps、61 Mb/s |
| 传输层 | TCP/UDP 吞吐 | `iperf3 -s`、`iperf3 -c 192.168.0.30 -b 1G -t 15 -P 2`、`netperf` | 新机器上手第一件事就是跑 iperf3 |
| 应用层 | QPS 与延迟分布 | `ab -c 1000 -n 10000`、`wrk -c 1000 -t 2 --latency`、Jmeter | `wrk` 9641 req/s、平均 65ms |

12 万 pps 是高还是低？拿千兆交换机当标尺：线速转发时 PPS = 1000Mbps / ((64+20)×8bit) ≈ 150 万 pps，比原案例测出值高一个数量级——所以"网卡标称千兆"和"你能转发多少包"是两件事，64B 小包场景差距最大。同类工具的差异同理：`ab` 与 `wrk` 打同一台机器 QPS 不同，说明压测工具本身先成了瓶颈，报数字时要连工具、连包长、连并发一起报。

## C10K → C1000K：瓶颈从线程搬到内核

| 阶段 | 环境（2018 年原案例） | 真瓶颈 | 手段 |
|---|---|---|---|
| C10K | 1999 年提出；32 位、Linux 2.2/2.4/2.6、2GB 内存、千兆网卡 | 每请求一线程/进程：1 万个线程的调度、上下文切换、内存开销；`select` 位图 32 位系统默认上限 1024，且是 O(n²) | 非阻塞 I/O + I/O 多路复用：`select`/`poll` → `epoll`（2.6 引入，红黑树管 fd 集合 + 事件驱动只返回就绪项） |
| C100K | 同代硬件放大 | 资源与 fd 数量 | epoll + 线程池 + CPU/内存/网卡升级 |
| C1000K | 百万连接 | 内存、fd 数、conntrack 表、socket/TCP 缓冲；中断处理成本 | 多队列网卡、中断负载均衡、CPU 绑定、RPS/RFS、TSO/GSO、LRO/GRO、VXLAN offload |
| C10M | 千万连接 | 内核协议栈路径本身太长 | DPDK（用户态轮询，跳过内核栈）或 XDP（4.8+，eBPF，进栈前处理） |

资源账算得很干脆：2GB 内存、千兆网卡撑 1 万请求，每个请求只要不到 200KB 内存（2GB/10000）和 100Kbit 带宽（1000Mbit/10000）——**物理资源够，问题是 I/O 模型**。到 C10M 反过来：每个请求 16KB 就要约 15GB 内存，假设 20% 活跃连接、每连接 1KB/s，也要 1.6Gb/s 吞吐，千兆网卡不够，得上万兆或多网卡 Bonding。

多进程模型的两个补丁值得记住：`accept()` 的惊群在 2.6 解决，`epoll_wait()` 的惊群要到 4.5 的 `EPOLLEXCLUSIVE`；Nginx 的绕法是 worker 抢全局锁 `accept_mutex`，另一条路是 `SO_REUSEPORT`（3.9+）让内核把连接均衡到各监听进程。

> 🔑 **C10K 靠加机器解决不了**：它是"单机每请求一线程"的模型问题，加机器只是把问题复制到 N 台；C1000K 之后加机器更不划算，因为瓶颈在每台机器内核路径的固定成本上。真正的分界是：C10K 换 I/O 模型，C1000K 换软硬件协同，C10M 换数据路径。

## 一张排障总表

| 症状 | 先看什么 | 命令 | 常见根因 |
|---|---|---|---|
| 时不时丢包，抓包看起来正常 | ring / backlog / netfilter 计数 | `netstat -i`、`cat /proc/net/softnet_stat`、`iptables -nvL` | qdisc 或 iptables 规则丢包、backlog 太小 |
| 小包通、大包不通 | MTU | `ip -s link`、`ip link show`、`ping -M do -s 1472` | 容器/隧道 MTU 配小，大包被丢（原案例 MTU=100） |
| 建连慢、`curl` 超时但端口在监听 | accept 队列 | `ss -lnt`、`netstat -s` 的 listen 段、`sysctl net.core.somaxconn` | backlog 太小、应用 `accept` 太慢、`tcp_abort_on_overflow` 配置 |
| 新连接建不上，老连接正常 | conntrack | `dmesg -T` 看最后几行、`/proc/sys/net/netfilter/nf_conntrack_count` | `nf_conntrack_max` 太小，表满丢新连接 |
| 吞吐上不去，CPU 花在 `si` | 软中断分布 | `top`、`mpstat -P ALL 1`、`/proc/softirqs`、`ethtool -l` | 单队列网卡、未开 RPS、中断集中在一个核 |
| 单请求延迟高，并发后更高 | 缓冲、Nagle/延迟确认 | `ss -ti`、`tcpdump` + Wireshark 时序图 | 服务端 Nagle 开着而客户端延迟确认，40ms 一档 |
| 发送阻塞、写超时 | socket 发送缓冲 | `ss -tn`（Send-Q）、`sysctl net.ipv4.tcp_wmem` | `sk_wmem_queued` 顶满、对端窗口为 0 |
| UDP 丢包，抓包看不到 | 接收缓冲与 ring | `nstat -az` 筛 rcvbuf 项、`ethtool -S` | `UdpRcvbufErrors`、ring 太小、应用读得慢 |
| `ss` 显示大量 `Recv-Q` 堆积 | 应用处理速度 | `ss -tn state established`、`pidstat -u 1` | event loop 被阻塞、GC 停顿、下游依赖慢 |
| 压测数字远低于线速 | PPS 与包长 | `sar -n DEV 1`、`ethtool eth0` 的 Speed 行 | 64B 小包 PPS 受限（原案例 12 万 pps vs 千兆交换机 150 万 pps） |

## 反模式

| 反模式 | 后果 |
|---|---|
| 一出丢包就调大所有缓冲和 `somaxconn` | 掩盖真实丢包点，延迟变差，问题换个形态复现 |
| 只信 tcpdump 结论 | 抓不到 ring、qdisc、netfilter 丢的包，容易把"没抓到"当成"没发" |
| 用 `netstat -s` 的绝对值判断 | 计数器单调递增，不看差值等于没看 |
| 把 `nf_conntrack_max` 调到百万却不看内存 | 每条约 376 字节，百万条就是数百 MB 常驻 |
| 在转发网关上开 LRO | 头部不一致时合并导致校验错误，转发流量被静默丢弃 |
| 手工 `setsockopt(SO_SNDBUF)` 覆盖自动调节 | 关掉内核的窗口自适应，长肥管道上吞吐反而下降 |
| 用 ICMP `ping` 判断服务可用性 | 服务禁 ICMP 时误判为网络不通，应用层问题被漏掉 |
| 只看平均延迟 | 延迟是长尾分布，原案例 90% 在 9ms 内而 99% 已到 50ms |

## 三条铁律

> 🔑 **丢包必有一层计数器在涨**：先按 ①→⑥ 的顺序把层定位出来，再谈优化；定位不到层的"优化"都是猜。

> 🔑 **发送慢看缓冲与 qdisc，接收慢看 Recv-Q 与软中断**：发送侧只有 socket 缓冲、qdisc 两个阻塞点；接收侧只有 ring、backlog、socket 队列三级缓冲。

> 🔑 **抓包与计数器必须交叉**：抓包证明"包到过这个点"，计数器证明"包没被这一点丢掉"，两者缺一，结论就不成立。

## 生产落地

两套数据并存：**原案例机器**（Ubuntu 18.04、2 CPU、2018 年）给的是“配小了会怎样”的对照；**本机实测**（Docker Desktop → Alpine 3.20 容器，内核 `7.0.14-linuxkit`，8 vCPU）给的是新内核上的真实默认值与输出形态。标「未验证」的是本机环境不具备条件或未复现的项。

**第一屏：看队列有没有堆**

```bash
ss -lnt                      # 监听队列：Recv-Q 当前、Send-Q 上限
ss -tn state established     # 已连接：Recv-Q 是应用没取走的字节
# 原案例机器输出（backlog 配小了的样子）
# State   Recv-Q  Send-Q   Local Address:Port   Peer Address:Port
# LISTEN  10      10       0.0.0.0:80           0.0.0.0:*
# LISTEN  7       10       *:9000               *:*
```

本机实测（`nc -l -p 9098` 只传了 backlog=1，于是 `Send-Q` 就是 1——**`Send-Q` 是 `listen(backlog)` 与 `net.core.somaxconn` 取小后的结果，不是“发送队列”**）：

```
State  Recv-Q Send-Q Local Address:Port Peer Address:Port
LISTEN 0      1      *:9098            *:*
```

同一台机器上 `net.core.somaxconn = 4096`（实测），所以瓶颈不在内核上限，而在应用传的 backlog。

`LISTEN` 行 `Recv-Q` 顶到 `Send-Q` = accept 队列在溢出；`ESTABLISHED` 行 `Recv-Q` 持续非零 = 应用读得慢。

**第二屏：看丢在哪一层**

```bash
ip -s link show eth0         # ① 网卡层：errors/dropped/overrun
# 原案例机器
# RX: bytes  packets  errors  dropped  overrun  mcast
#     9542432350 40809397 0     0        0        193
netstat -i                   # ① 的另一种排版，容器里 ethtool -S 无效时用它
# Iface  MTU  RX-OK RX-ERR RX-DRP RX-OVR  TX-OK TX-ERR TX-DRP TX-OVR Flg
# eth0   100  157   0      344    0       94    0      0      0      BMRU

ethtool -S eth0 | grep -i drop   # ② 驱动内部丢包
ethtool -g eth0                  # ② ring 大小
cat /proc/net/softnet_stat       # ③ 每 CPU 一行，十六进制；第2列 dropped、第3列 time_squeeze
nstat -az | grep -E 'ListenDrops|BacklogDrop|RcvbufErrors'   # ④ 协议栈
```

本机实测（容器 veth，空闲态）：

```
$ ip -s link show eth0
    RX:  bytes packets errors dropped  missed   mcast
       7714880    2805      0       0       0       0
    TX:  bytes packets errors dropped carrier collsns
        180272    2561      0       0       0       0

$ ethtool -S eth0 | head -3
NIC statistics:
     peer_ifindex: 21
     rx_queue_0_drops: 0        # veth 也有 per-queue 丢包计数，但字段名和物理网卡不同
```

`/proc/net/softnet_stat` 实测首行（**十六进制**，`000010c0` = 4293 个包，第 2 列 `00000000` = 丢 0 个，第 3 列 `00000001` = time_squeeze 1 次）：

```
000010c0 00000000 00000001 00000000 00000000 00000000 00000000 00000000 00000000 0000045a ...
```

`nstat -az` 实测（空闲容器里五个关键计数都是 0；要点是**看差值不看绝对值**）：

**调整与回滚**（先记原值，再改，改完立刻验证）

```bash
# 记原值
sysctl net.core.somaxconn net.netfilter.nf_conntrack_max net.netfilter.nf_conntrack_buckets

# 放行监听队列：原案例从 10 调到 65536，应用侧 backlog 同步调到 8192
sysctl -w net.core.somaxconn=65536
# 放行 conntrack：原案例把 max 调到 buckets 的 2 倍
sysctl -w net.netfilter.nf_conntrack_max=131072
sysctl -w net.netfilter.nf_conntrack_buckets=65536

# 验证：溢出计数应停止增长
netstat -s | grep -i listen      # ListenOverflows / ListenDrops 不再涨
dmesg | tail                     # 不再出现 nf_conntrack: table full

# 回滚
sysctl -w net.core.somaxconn=<原值>
sysctl -w net.netfilter.nf_conntrack_max=<原值>
```

改 `conntrack_buckets` 需要重载模块才彻底生效，线上环境以 `sysctl -w nf_conntrack_max` 为主，改桶数前先在灰度机验证。原案例调完后的对照：QPS 4683 → 6185，且 `netstat -s` 里的套接字丢包归零。

## 自检

**Q1** 客户端说丢包，但服务端 `tcpdump` 把每个请求都抓到了，这说明什么？下一步查什么？
▸ 答案：说明包已经穿过网卡、ring 和软中断，到达了协议栈二层之后——丢点在**服务端协议栈内部**（iptables DROP、`sk_backlog` 满、`sk_receive_queue` 满）或**回程方向**（回程被丢、客户端侧丢）。抓包点比 netfilter 早，所以"抓到"和"应用收到"是两件事。下一步按 ④ ⑤ ⑥ 查：`iptables -nvL` 的 DROP 计数、`nstat -az` 的 `TCPBacklogDrop`/`ListenDrops`、`ss -tn` 的 `Recv-Q`。

**Q2** `ss -lnt` 里监听端口的 `Recv-Q` 持续等于 `Send-Q`，和已连接端口的 `Recv-Q` 持续非零，是同一个问题吗？
▸ 答案：不是。监听 socket 的 `Recv-Q` 是半连接队列当前长度、`Send-Q` 是上限（`backlog` 与 `net.core.somaxconn` 取小），顶满意味着完成握手的连接没被 `accept` 取走，内核开始丢 SYN，客户端表现为建连超时；已连接 socket 的 `Recv-Q` 是应用还没 `read` 走的字节数，持续非零意味着服务端读得慢（event loop 阻塞、GC、下游慢），对端会被窗口收紧逼停。前者要调 `somaxconn`/`backlog` 或加快 `accept`，后者要查应用。

**Q3** `dmesg` 里出现 `nf_conntrack: table full, dropping packet`，此时已经建立的连接会断吗？
▸ 答案：不会。表满的行为是丢弃**新**连接，已有连接在表里，继续正常工作，所以典型症状是"老连接好好的，新连接建不上、日志被 `net_ratelimit` 压缩"。注意这不是路由问题也不是带宽问题，调 `nf_conntrack_max` 才能解，但每条约 376 字节内存，调大前先算内存，并同步考虑桶数（平均链长 = max/buckets）。

**Q4** C10K 问题靠加机器能不能解决？
▸ 答案：不能解决"问题本身"。C10K 的根因是每请求一线程/进程的模型 + `select` 的 O(n²) 轮询，加机器只是把同样的模型复制 N 份，单机 1 万连接的调度与上下文切换成本原样存在。epoll 换掉的是模型：红黑树管 fd 集合、只返回就绪项，单机成本从"跟 fd 数成正比"降到"跟活跃事件数成正比"。真正靠加机器能拖过去的是 C100K 量级，到 C1000K 又要回到内核参数与软硬件协同。

**Q5** 发送方"卡住不返回"，怎么判断是 socket 缓冲满还是网卡/qdisc 满？
▸ 答案：看阻塞点和队列。socket 缓冲满时，`sk_wmem_queued` 顶到上限，进程睡在 `sk_stream_wait_memory`（非阻塞则 `EAGAIN`），此时 `ss -tn` 的 `Send-Q` 很大而 `tc -s qdisc show dev eth0` 的 `backlog` 很小；qdisc/ring 满时正好相反，qdisc 的 `backlog` 和 `dropped` 在涨，而 socket 缓冲还有余量，`ip -s link` 的 TX dropped 也可能在涨。两个计数器一起看，才能分清是"应用把内核塞满了"还是"网卡把内核堵住了"。
