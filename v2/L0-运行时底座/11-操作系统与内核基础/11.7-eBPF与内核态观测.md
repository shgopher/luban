# 11.7 eBPF 与内核态观测

## 一句话

> eBPF 让你**在不改内核、不重启、不装模块**的前提下，把小程序挂到内核的钩子上（系统调用、函数入口、网络包），从而回答 “延迟花在内核哪里”；它的代价是**验证器限制、内核版本依赖与不能阻塞**。

## 四种钩子

| 钩子 | 挂在哪 | 典型用途 | 开销 |
|---|---|---|---|
| **kprobe / kretprobe** | 任意内核函数入口/返回 | 函数耗时、参数、调用链 | 中（每调用一次触发） |
| **tracepoint** | 内核预置的稳定点 | 调度、syscall、TCP 事件 | 低（稳定，推荐） |
| **XDP** | 网卡驱动收包最早处 | DDoS 清洗、负载均衡 | 极低（可线速） |
| **tc / cgroup / uprobe** | 流量控制、cgroup、用户态函数 | 限速、容器级观测、应用函数 | 低–中 |

## 能回答的典型问题

| 问题 | 手段 |
|---|---|
| `read` 到底卡在哪 | kprobe 打 `vfs_read` + 返回值耗时直方图 |
| 进程为什么 CPU 不高但很慢 | off-CPU 分析（调度进出打点） |
| 谁在发大量 TCP 重传 | tracepoint `tcp_retransmit_skb` + 进程栈 |
| 哪个容器在扫端口 | cgroup 维度统计 connect 失败 |
| 延迟 P99 的尾部在哪 | 内核–用户态全链路耗时分布 |

## 工具链

| 层次 | 工具 | 适合 |
|---|---|---|
| 现成命令 | `bpftrace`、`bcc`（如 `execsnoop`、`biolatency`） | 90% 的排查 |
| 库 | libbpf（C）、cilium/ebpf（Go） | 写常驻工具 |
| 平台 | Cilium、Pixie、Falco | 网络策略、可观测、安全 |

```bash
# 一次典型的 bio 延迟分布（需 root）
bpftrace -e 'tracepoint:block:block_rq_complete { @ns = hist(args->nr_sector); }'
```

## 限制（决定 “能不能上生产”）

| 限制 | 影响 |
|---|---|
| 验证器（verifier） | 循环必须有界、不能越界、栈有限；复杂逻辑会被拒 |
| 不能睡眠（多数程序） | 不能做磁盘/网络等待，只能打点与聚合 |
| 内核版本依赖 | 新特性（BTF、CO-RE、ringbuf）需要较新内核 |
| 开销 | kprobe 挂在高频函数上会拖慢系统；需限流与采样 |
| 安全 | 需要 CAP_BPF/root；映射与程序本身是攻击面 |

内核数据结构与缓存影响的解释见 [11.6 CPU Cache 与 NUMA](11.6-CPU-Cache与NUMA.md)；IO 等待的定位见 [11.3 文件系统与 IO 模型 (阻塞 / 非阻塞 / 异步)](11.3-文件系统与IO模型.md)。

## 落到数字：钩子的开销

| 钩子 | 相对开销 | 适用频率 |
|---|---|---|
| tracepoint | 低 | 高频（syscall、调度） |
| kprobe | 中（每调用一次触发） | 中低频函数 |
| XDP | 极低（驱动层） | 每包 |
| uprobe | 中高（用户态断点） | 少量关键函数 |

```bash
bpftrace -l 'tracepoint:syscalls:*' | head -5      # 列出可用稳定点
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm]=count(); }'   # 谁在 open（需 root）
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 生产环境随手挂 kprobe 到热点函数 | 性能下降 10%–30%，难以定位 |
| 不设采样，全量统计 | 环形缓冲溢出，数据丢失 |
| 依赖未导出符号的 kprobe | 内核升级即失效 |
| 用 eBPF 做业务逻辑（如鉴权） | 验证器限制 + 维护成本高 |
| 无回滚方案 | 出问题只能重启机器 |

## 三条铁律

> 🔑 **优先 tracepoint，其次 kprobe**；前者稳定且开销低。

> 🔑 **观测本身有成本**：采样 + 限流 + 明确退出条件。

> 🔑 **eBPF 是 “观测与轻量拦截”**，不是通用业务运行时。

## 自检

**Q1** 服务 “CPU 不高但请求很慢”，eBPF 能怎么定位？

▸ 答案：做 **off-CPU 分析**：在调度器 `sched_switch`（进程让出 CPU / 被唤醒）处打点，统计 “任务不在 CPU 上” 的时间与阻塞栈。能直接看出是等锁、等 IO、还是等网络，这是 `perf top`（只看得见 on-CPU）给不了的视角。

**Q2** 为什么 XDP 能做线速 DDoS 清洗？

▸ 答案：因为 XDP 程序挂在**驱动收包的最早位置**，在分配 `sk_buff`、走协议栈之前就能丢弃或重定向包，开销极低（每包几十纳秒量级）。代价是只能访问很有限的元数据，且需要网卡/驱动支持。

**Q3** eBPF 程序为什么不能随便写循环？

▸ 答案：因为验证器必须**静态证明程序会终止**（有界循环），否则可能挂死内核。这带来实际限制：不能按数据长度动态循环，需要改成固定上界 + 提前退出。这也是 “用 eBPF 写复杂业务逻辑很痛苦” 的根因。

**Q4** 生产上用 eBPF 观测，最该防的是什么？

▸ 答案：**观测开销与影响面**。挂在高频路径（如每个 syscall）的探针会把系统拖慢；环形缓冲不够会丢数据；程序 bug 可能影响被观测进程。实践是：先在预发验证、用采样与限流、设明确的 `--duration`、并准备好卸载/重启方案。

**Q5** eBPF 与 `perf`、`strace` 的分工是什么？

▸ 答案：`strace` 看**单个进程的 syscall 序列**（开销极大，适合短时定位）；`perf` 看 **on-CPU 的采样与硬件事件**（火焰图基础）；eBPF 补足两者：**内核内任意打点 + 低开销聚合 + off-CPU 视角**。排查顺序通常是 perf 找热点 → eBPF 看内核路径/阻塞 → strace 验证具体参数。

**QQ6** 为什么生产上更推荐 tracepoint 而不是 kprobe？

▸ 答案：因为 tracepoint 是内核**稳定接口**，有明确的字段与语义，内核升级后不易失效；kprobe 依赖具体函数名与参数布局，一旦内核版本变化就可能挂不上或读到错位数据。
