# 11.1 进程、线程与调度

## 一句话

> 进程是**资源与隔离**的单位（地址空间、fd、权限），线程是**调度**的单位（共享同一地址空间）；上下文切换本身只要 1–3μs，真正贵的是 **cache 与 TLB 被污染**，所以调度器的目标不是 “切得勤”，而是 “切得值”。

## 进程与线程

| 维度 | 进程 | 线程 |
|---|---|---|
| 隔离 | 独立地址空间、fd 表、信号处理 | 共享地址空间与 fd |
| 创建成本 | 高（fork + COW 页表） | 低（clone 共享） |
| 通信 | IPC（管道、共享内存、socket） | 直接读写共享内存 |
| 崩溃影响 | 互不影响 | 一个线程崩 = 整个进程崩 |
| 调度单位 | 线程（Linux 上进程/线程都是 task） | 线程 |

Linux 不区分 “进程 / 线程” 的实现：都是 `task_struct`，差别只在 `clone()` 时共享哪些资源（`CLONE_VM`、`CLONE_FILES`、`CLONE_THREAD`）。

## task_struct：一个结构装下进程的全部状态

排障时你看到的 `ps`、`/proc/<pid>`、cgroup、namespace，背后都是同一个结构里的字段：

| 字段 | 含义 | 现场怎么用 |
|---|---|---|
| `state` | 运行状态 | `ps -eo state,pid,cmd \| grep -E '^D\|^Z'` |
| `pid` / `tgid` / `group_leader` | 线程 id、线程组 id（= 进程 id）、组长 | 同一 `tgid` 下的多个 `pid` 就是一个进程的线程 |
| `mm` | 用户地址空间与页表 | 线程共享同一个 `mm`，进程各有一份 |
| `files` | 打开的文件描述符表 | `ls -l /proc/<pid>/fd` |
| `fs` / `nsproxy` | 根目录、cwd、namespace | 容器隔离的落点（见 [6.3 namespace (隔离) 与 cgroups (限制)](../6-容器技术/6.3-namespace与cgroups.md)） |
| `signal` / `sighand` | 信号队列与处理函数表 | `CLONE_SIGHAND` 决定是否共享 |
| `se` / `rt` / `dl` | 调度实体，挂在对应调度队列上 | 决定被哪个调度类管 |
| `cred` | uid/gid/capabilities | 权限问题第一现场 |
| `cgroups` | 所属 cgroup | 资源限制按它记账 |

> 🔑 **“进程”在 Linux 里只是“共享同一个 `mm` 的一组 task”**：`tgid` 相同即同进程。这也解释了 `ps -L` 为何能看到多行、为什么 `kill <pid>` 杀的是整个线程组。

## 进程状态：R / S / D / T / Z

| 状态 | 含义 | 常见成因 | 观测 |
|---|---|---|---|
| R | 可运行（在队列里或正在跑） | 正常 | `vmstat 1` 的 `r` 列 = 运行队列长度 |
| S | 可中断睡眠 | 等事件、等 IO、等锁 | 绝大多数进程的常态 |
| D | 不可中断睡眠 | 等硬件：磁盘、NFS、驱动 | 长时间 D = 块设备或网络存储卡住 |
| T | 停止 | `SIGSTOP`、调试器 | `kill -CONT` 恢复 |
| Z | 僵尸 | 已退出但父进程没 `wait()` | 占 pid 与内核栈，不占 CPU |

> 🔑 **D 状态是保护机制，不是 bug**：内核保证硬件交互不被信号打断。短时间 D 正常；持续数秒的 D 一定指向 IO 路径——这是“CPU 不忙但服务不可用”的典型来源（见 [11.9 中断、软中断与 CPU 时间去向](11.9-中断-软中断与CPU时间去向.md)）。

## 一次切换到底花了什么

| 成本 | 量级 | 说明 |
|---|---|---|
| 保存/恢复寄存器 + 切栈 | 1–3μs | 直接成本，看起来很小 |
| TLB 失效 | 数 μs – 数十 μs | 换地址空间（跨进程）时更贵 |
| Cache 污染 | 数十 μs | 新任务的工作集把旧任务的缓存挤掉 |
| 调度器开销 | 亚 μs | 选下一个任务 |

推论：**切换频率比切换耗时更值得关注**。每秒 10 万次切换，即使每次 2μs，也吃掉 20% 的 CPU——这类系统通常表现为 “CPU 高但吞吐不涨”。

## CFS：按 “已经跑了多久” 排队

| 概念 | 含义 | 观测 |
|---|---|---|
| `vruntime` | 虚拟运行时间（按权重折算） | `/proc/<pid>/sched` |
| 权重 | nice 值 → 权重（nice 每 +1 约减 10% CPU 份额） | `cpu.weight`（cgroup v2） |
| 调度延迟 | 一个周期内所有可运行任务至少各跑一次 | 老 CFS 约 6–24ms（随任务数调整） |
| 最小粒度 | 单次运行下限 | 老 CFS 约 0.75ms |

> ⚠️ **上面这两个参数是 CFS 时代的，6.6 之后内核换成了 EEVDF**（Earliest Eligible Virtual Deadline First）：仍然用 `vruntime` 与权重，但不再有 `sched_latency_ns` / `sched_min_granularity_ns` / `sched_wakeup_granularity_ns` 这套旋钮，改为按“资格时间 + 虚拟截止期”挑任务，并引入 `base_slice` 概念。本机实测（内核 `7.0.14-linuxkit`）的 `/proc/sys/kernel` 下确实**只剩** `sched_cfs_bandwidth_slice_us`、`sched_deadline_period_*`、`sched_rr_timeslice_ms`、`sched_rt_*`，`sched_min_granularity_ns` 已不存在——照抄老文章的调参命令会直接 `No such file or directory`。

两个常见误解：

- **“nice 是绝对优先级”**：不是，它只在**竞争时**决定 CPU 份额；CPU 空闲时大家都能跑满。
- **“线程越多越快”**：CPU 密集任务超过核数只是增加切换；IO 密集任务才靠并发掩盖等待。

### 实现：vruntime + 红黑树

CFS 的全部机制可以压成三行：

```
vruntime += delta_exec × NICE_0_LOAD / weight    // 同样跑 1ms，权重高的加得少
cfs_rq.tasks_timeline = 按 vruntime 排序的红黑树    // rb_leftmost 就是下一个该跑的
min_vruntime = 单调递增的下界                     // 防止新唤醒任务"插队"
```

- **红黑树**：插入/删除 O(log n)，取最小 O(1)（缓存了 `rb_leftmost`）。选下一个任务就是“取最左节点”，不需要遍历。
- **权重**：nice 只是接口，内核查表转成 `load.weight`；`NICE_0_LOAD / weight` 是折算系数。
- **`min_vruntime`**：单调递增，保证老任务的 vruntime 不会因为新任务不断唤醒而被无限推高。

### 调度类：一条链，从最“急”找到最“闲”

每个 CPU 有一个 `struct rq`，里面同时挂着实时队列 `rt_rq`、CFS 队列 `cfs_rq`、deadline 队列 `dl_rq`。选任务时按 `sched_class` 链表顺序试：

| 调度类 | 覆盖的策略 | 优先级区间 | 用途 |
|---|---|---|---|
| `stop_sched_class` | 内核内部（停机、迁移） | 最高 | 不可被抢占 |
| `dl_sched_class` | `SCHED_DEADLINE`(6) | 按 deadline | 硬实时任务 |
| `rt_sched_class` | `SCHED_FIFO`(1) / `SCHED_RR`(2) | 0–99 | 实时任务 |
| `fair_sched_class` | `SCHED_NORMAL`(0) / `SCHED_BATCH`(3) / `SCHED_IDLE`(5) | 100–139 | 绝大多数业务进程 |
| `idle_sched_class` | 空闲 | 最低 | 没活干时跑 |

> 🔑 **实时任务一定先于普通任务**：只要 `rt_rq` 里有可运行任务，CFS 队列就轮不到。给业务进程挂 `SCHED_FIFO` 是“用稳定性换确定性”，一个死循环就能锁死整台机器。

## 调度时机：主动让出，还是被标记后抢占

| 方式 | 触发点 | 关键动作 |
|---|---|---|
| 主动调度 | 进程自己调 `schedule()`：等锁、等 IO、`sleep`、`yield` | 直接进 `__schedule` |
| 抢占（用户态） | 从**系统调用返回**、从**中断返回**用户态那一刻 | 检查 `TIF_NEED_RESCHED` |
| 抢占（内核态） | `preempt_enable()` 让 `preempt_count` 归零时 | `preempt_schedule() → __schedule` |

抢占分两步：**先标记，后切换**。`resched_curr()` 只给目标任务打上 `TIF_NEED_RESCHED` 标志，真正切换必须等一个安全点（返回用户态或重新开抢占）——因为内核栈上的中间状态不能随便换人。

`__schedule()` 只做两件事：**选下一个任务**（`pick_next_task`，按上面那条 `sched_class` 链找）+ **上下文切换**（`context_switch`，切页表、切栈、切寄存器）。

## 创建：fork 便宜在 COW，clone 决定共享什么

`fork()` → `_do_fork()` → `copy_process()`，顺序是：`dup_task_struct`（复制 `task_struct` 与内核栈）→ `copy_files` → `copy_fs` → `copy_sighand` / `copy_signal` → `copy_mm`（**复制页表，不复制物理页**）→ 分配 pid。

地址空间那一步只是把父子进程的所有页标成只读共享；任一方写入触发缺页，内核才复制那一页——这就是 **COW（写时复制）**。所以 `fork()` 的开销与地址空间大小**不成正比**，只与页表规模相关。

`clone(flags)` 是 `fork` 的通用形式，glibc 的 `pthread_create` 最终就是带一长串标志的 `clone`：

| 调用 | 地址空间 | fd 表 | 信号处理 | 结果 |
|---|---|---|---|---|
| `fork()` | 复制（COW） | 复制 | 复制 | 新进程 |
| `pthread_create()` | 共享（`CLONE_VM`） | 共享（`CLONE_FILES`） | 共享（`CLONE_SIGHAND`） | 新线程 |
| `vfork()` | 共享，父进程挂起 | 复制 | 复制 | 只为紧跟 `exec` 用 |

> ⚠️ `vfork` 后子进程若在 `exec` 前改内存，会破坏父进程；`posix_spawn` 在多数 libc 里用 `CLONE_VM|CLONE_VFORK` 实现，比 `fork + exec` 少一次页表复制。

## 落到数字：切换成本与线程数

| 项 | 量级 | 说明 |
|---|---|---|
| 同进程线程切换 | 1–2μs | 不换地址空间，TLB 基本保留 |
| 跨进程切换 | 2–5μs + TLB 失效 | 页表切换更贵 |
| 每秒 10 万次切换 | 吃掉 10%–20% CPU | “CPU 高但吞吐不涨” 的典型 |
| 线程数与核数比 | 建议 ≤ 2–4×（IO 密集可更高） | 再高只是增加切换 |

```bash
vmstat 1 5 | awk 'NR==1 || NR>2 {print $1, $13, $14}'   # cs 列 = 上下文切换/秒
pidstat -w -p <pid> 1 3                                  # cswch/nvcswch 分清自愿/非自愿
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 用进程做高并发（每连接一进程） | 内存与切换成本爆炸 |
| 线程数 = 请求数（无池化） | 切换风暴，P99 抖动 |
| 依赖 `nice` 做 “实时保障” | 只是相对份额，关键任务仍可能被饿 |
| 忽略 CPU 亲和 | 跨 NUMA 访问与 cache 失效（见 [11.6 CPU Cache 与 NUMA](11.6-CPU-Cache与NUMA.md)） |
| 在容器里按物理核数开线程 | 受 `cpu.max` 限制，线程多反而互相抢配额（见 [6.3 namespace (隔离) 与 cgroups (限制)](../6-容器技术/6.3-namespace与cgroups.md)） |

## 三条铁律

> 🔑 **进程管隔离、线程管并发**；跨进程共享状态必须有明确协议。

> 🔑 **切换的代价在缓存与 TLB**，不在寄存器保存。

> 🔑 **并发度按 “核数 × 阻塞率” 定**，不按 “请求数” 定。

## 自检

**Q1** 一台机器 `top` 显示 CPU 使用率 90%、系统态占比很高、吞吐却不涨，最可能是什么问题？

▸ 答案：**上下文切换或系统调用过多**。常见来源：线程数远超核数、锁竞争导致频繁阻塞/唤醒、每次请求都做多次 syscall（日志、时间、序列化）。查 `vmstat 1` 的 `cs`（context switch）列与 `pidstat -w`，再对照业务的线程池配置。

**Q2** 为什么 “每连接一进程” 的模型撑不住高并发？

▸ 答案：因为每个进程都有独立地址空间与页表：内存开销（栈 + 页表 + 内核结构）、切换时 TLB 与 cache 全部失效、创建/销毁成本高。高并发需要 “少量线程 + 事件驱动”（见 [11.4 epoll 与 IO 多路复用](11.4-epoll与IO多路复用.md)）或 “协程”（见 [15.8 并发编程模型 (线程 / 协程 / Actor / CSP)](../15-语言运行时/15.8-并发编程模型.md)）。

**Q3** nice 调到 -20 能让任务 “绝对优先” 吗？

▸ 答案：**不能**。CFS 里 nice 只影响**权重**（相对份额），CPU 空闲时低优先级任务照样能跑满；即使权重差距很大，也只是 “分到的比例不同”，不是 “独占”。要绝对保障需要实时调度类（`SCHED_FIFO`）或 cgroup 的 CPU 配额，代价是可能饿死其他任务。

**Q4** 容器里 `nproc` 显示 64，但 `limits.cpu` 是 2，开 64 个线程会怎样？

▸ 答案：会造成**严重节流**：64 个线程抢 2 核的配额（`cpu.max`），每个线程都被调度周期切断，P99 抖动剧烈。正确做法是按 “配额 × 阻塞率” 设线程数（如 2–8），并监控 `nr_throttled` 比例（见 [6.3 namespace (隔离) 与 cgroups (限制)](../6-容器技术/6.3-namespace与cgroups.md)）。

实测佐证：`--cpus=0.1` 起一个容器（`cpu.max` = `10000 100000`），里面跑两个 `while :;` 忙循环 3 秒，`/sys/fs/cgroup/cpu.stat` 的 `nr_periods` 从 927 涨到 960、`nr_throttled` 从 89 涨到 122——**3 秒里的 33 个周期，33 个都被节流**；`throttled_usec` 同步从 6.64s 涨到 13.18s。这就是“线程数按核数开、配额却只有 0.1 核”的代价。

**Q5** 什么情况下该用多进程而不是多线程？

▸ 答案：需要**强隔离与故障不扩散**时：不同租户的代码、会崩溃的第三方库、需要独立 GC/内存上限（如每个 worker 一个进程）、以及能利用 “多核 + 独立地址空间” 避免锁竞争的场景。代价是 IPC 与内存开销。典型例子：Nginx（多 worker 进程）、PostgreSQL（每连接一进程）。

**Q6** `nvcswch`（非自愿切换）很高说明什么？

▸ 答案：说明任务**被抢占**：可运行但没抢到 CPU（通常是线程数远超核数，或存在高优先级任务）。它和 `cswch`（自愿，等 IO/锁）含义不同——前者指向 “CPU 不够”，后者指向 “在等待”。

**Q7** 进程处于 `D` 状态、`top` 里 `wa` 很高、但业务日志显示“服务卡住不动”，问题出在哪一层？

▸ 答案：**在块设备或网络存储的 IO 路径**。`D` 是不可中断睡眠，专门用于等硬件；`wa` 高说明 CPU 空闲但仍有任务在等 IO。两者同时出现，基本可以把“CPU 不够”“线程不够”排除，去看 `iostat -x` 的 `await` 与具体设备（见 [11.3 文件系统与 IO 模型 (阻塞 / 非阻塞 / 异步)](11.3-文件系统与IO模型.md)）。

**Q8** `fork()` 一个占 8GB 内存的进程要多久？为什么 Redis 做 RDB 快照时 `fork` 能瞬间返回？

▸ 答案：**与内存大小基本无关，只与页表规模相关**。`fork` 只复制 `task_struct`、fd 表、页表，物理页靠 COW 共享；写入时才按页复制。所以 Redis 的 `BGSAVE` 能快速 `fork` 出子进程。代价在后面：父进程大量写入时会产生持续的 COW 缺页，表现为延迟抖动。

**Q9** 内核里看到一个任务频繁进入 `__schedule`，但没有 CPU 打满，可能是什么原因？

▸ 答案：**主动调度占主导**：任务在等锁、等 IO、频繁 `sleep`，而不是被抢占。区分方法：`pidstat -w` 看 `cswch`（自愿）与 `nvcswch`（非自愿）——自愿高说明在“等待”，非自愿高才是“抢不到 CPU”。
