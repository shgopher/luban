# 11.9 中断、软中断与 CPU 时间去向

## 一句话

> 中断把「等硬件」从轮询改成异步通知，代价是 CPU 时间被切成 us/sy/wa/hi/si/st 若干块：**CPU 不闲时先分清这块时间是用户态在算、内核在替谁干活、还是在等 I/O**——si 高就去看 `/proc/softirqs` 的类型与跨 CPU 分布，load 高就去看 R 和 D 各占多少。

## 中断：一次「打电话取外卖」的异步约定

中断是系统用来响应硬件设备请求的机制：它打断进程的正常调度和执行，转去调用内核中的中断处理程序，响应设备的请求。

为什么需要它？订一份外卖，不知道什么时候送到，配送员又不等人，到了没人取就直接走人——只能守在门口隔一会儿看一眼，别的事都干不成。如果下单时约定「送到打个电话」，就可以去忙别的事情，电话一响再去取。电话就是中断：没接到电话时你在做别的事，接到电话才触发另一个动作。

由此得到两个结论：**中断是异步事件处理机制**，作用是提高系统的并发处理能力；**中断处理程序会打断其他进程**，它的运行时长和被它打断的进程是竞争关系。

那为什么硬中断处理程序必须「快」？两层原因叠在一起：

1. 它打断的是正常进程的调度与执行，跑得越久，被抢占的进程等得越久；
2. 更要命的是，**处理程序在响应中断时会临时关闭中断**。上一次中断处理完成之前，其他中断都不能响应，也就是中断有可能丢失。

还是取外卖：这次订了两份，一份主食一份饮料，两个配送员，都约定了电话取餐。第一份送到时，配送员打了个长长的电话商量发票怎么处理；与此同时第二个配送员也到了，也想打电话——电话占线（等于关闭了中断响应），第二个配送员试几次打不通，很可能就走了，也就是丢了一次中断。

**「快」是硬中断的第一性要求，不是风格偏好。**它决定了后面所有的设计：把活劈成两半。

| 维度 | 轮询（守在门口看） | 中断（等电话） |
|---|---|---|
| 谁发起 | CPU 主动反复检查 | 设备主动通知 |
| 空转开销 | 无事件也一直耗 CPU | 无事件时零开销 |
| 响应延迟 | 取决于轮询间隔 | 取决于关中断窗口 |
| 丢事件风险 | 漏看一次就错过 | 关中断期间会丢 |
| 典型场景 | 极低延迟、事件密集（DPDK 轮询网卡） | 通用外设、网卡收包 |

## 上半部与下半部：把处理劈成两段

为了解决「处理程序执行过长」和「中断丢失」这对矛盾，Linux 把中断处理分成两个阶段：

| 维度 | 上半部（硬中断） | 下半部（软中断） |
|---|---|---|
| 谁触发 | 硬件打断 CPU | 上半部发的软中断信号、内核自定义事件 |
| 运行上下文 | 中断禁止模式，打断当前任务立即执行 | 以内核线程 `ksoftirqd/CPU编号` 方式延迟执行 |
| 干什么 | 与硬件紧密相关、时间敏感的事 | 上半部没做完的、可以推迟的事 |
| 网卡收包 | 把数据读到内存、更新硬件寄存器状态、发一个软中断信号 | 从内存找到数据，按协议栈逐层解析，直到交给应用程序 |
| 观测文件 | `/proc/interrupts` | `/proc/softirqs` |
| 设计约束 | 必须短，关中断期间会丢中断 | 可以长，但积压会挤占正常调度 |

用取外卖的类比对齐：**上半部是接电话**，告诉配送员「知道了，别的事见面再说」，然后挂断；**下半部才是取外卖**，以及见面后商量发票。这样第一个配送员不占用你太多时间，第二个配送员过来时照样能打通。

每个 CPU 都对应一个软中断内核线程，名字是 `ksoftirqd/CPU编号`，0 号 CPU 对应的就是 `ksoftirqd/0`。软中断事件频率过高时，这个内核线程自己就会把 CPU 吃满，处理不及时，进而引发网络收发延迟、调度缓慢。

三个容易漏掉的事实：

- **软中断不等于「硬件中断的下半部」。**内核调度、RCU 锁、定时器这些内核自定义事件也走软中断，`/proc/softirqs` 里的 `SCHED`、`RCU`、`TIMER` 就是它们。
- **tasklet 是软中断的一种实现机制**，最常用、写法最简便：每个 tasklet 只运行一次就结束，并且**只在调用它的函数所在的 CPU 上运行**。代价是调度不均衡（同类型计数在多个 CPU 上差几个数量级），以及**不能在多个 CPU 上并行**，带来性能上限。
- **允许睡眠的下半部要用工作队列（workqueue），不能用软中断/tasklet。**软中断与 tasklet 跑在中断上下文里，不能睡眠；工作队列交给内核线程在进程上下文执行，才可以阻塞。选型只有一条判据：这段下半部会不会睡。

## 观测接口：先看类型，再看分布

两个只读文件，各管一半：

- `/proc/softirqs`：软中断的运行情况，按类型、按 CPU 给出**开机以来的累计次数**；
- `/proc/interrupts`：硬中断的运行情况，格式相同，每行一个中断号或中断类型。

`/proc/softirqs` 一共 10 类软中断：

| 类型 | 负责什么 | 偏高通常意味着 |
|---|---|---|
| `HI` | 高优先级 tasklet | 极少见，特定驱动 |
| `TIMER` | 低分辨率定时器 | 定时器密集，通常平稳增长 |
| `NET_TX` | 网络发送 | 发包压力 |
| `NET_RX` | 网络接收 | **收包压力，生产上最常见的元凶** |
| `BLOCK` | 块设备 | 磁盘 I/O 完成处理密集 |
| `IRQ_POLL` | 中断轮询（NVMe 多队列） | 高性能盘 poll 模式 |
| `TASKLET` | tasklet | 驱动下半部；分布不均本身是常态 |
| `SCHED` | 内核调度 | 调度频繁，常与上下文切换同向上涨 |
| `HRTIMER` | 高分辨率定时器 | 高精度定时需求 |
| `RCU` | RCU 锁 | 读多写少的临界区回收压力 |

看这个文件要抓两件事，缺一不可：

1. **类型。**哪一类在涨？`NET_RX` 涨和 `BLOCK` 涨是两条完全不同的排查路线。
2. **同类型在多个 CPU 上的分布。**正常运行下，同一种中断在各 CPU 上的累计次数应该差不多（同一数量级）。某一行在 CPU0 特别高、其他 CPU 几乎不动，说明这类中断没有摊开。

第 2 点还有一个前提：**中断处理在同一 CPU 上是串行的。**一个 CPU 的软中断由它自己的 `ksoftirqd/N` 一根线程处理，所以「集中」直接等于「单核成为瓶颈」，核数再多也用不上。

`ps` 也能看到这些内核线程：

```bash
$ ps aux | grep softirq
root         7  0.0  0.0      0     0 ?        S    Oct10   0:01 [ksoftirqd/0]
root        16  0.0  0.0      0     0 ?        S    Oct10   0:01 [ksoftirqd/1]
```

名字外面带中括号，说明 `ps` 拿不到它们的命令行参数（cmdline）——**`ps` 输出里名字被中括号括起来的，一般都是内核线程**，它们没有用户态地址空间，VIRT/RES 都是 0。这条规则在排查「CPU 高但找不到应用」时是分水岭：高 CPU 的进程可能根本不是应用。

> ⚠️ **在容器（PID namespace）里看不到这些线程**。本机在容器内执行 `ps aux | grep softirq` 只匹配到 `grep` 自己；`/proc/softirqs` 却能正常读。要验证 `ksoftirqd`，得在**宿主**或 `--pid=host` 的容器里看；否则会误以为“系统里没有软中断线程”。

⚠️ 文件里是累计值，直接 `cat` 只能看到历史总量，对当下问题没有参考意义。要看的是**变化速率**，所以要用 `watch -d`。

## 平均负载：R + D 的指数衰减平均，不是 CPU 使用率

`uptime` 最后三个数，是过去 1 分钟、5 分钟、15 分钟的平均负载：

```bash
$ uptime
02:34:03 up 2 days, 20:14,  1 user,  load average: 0.63, 0.83, 0.88
```

定义：**单位时间内，处于可运行状态和不可中断状态的平均进程数**，也就是平均活跃进程数。它是活跃进程数的**指数衰减平均值**（越近的时刻权重越大），计算方式只是内核为了算得快，直接当成「活跃进程数的平均值」理解即可。

两个状态各是什么：

- **可运行（R，Running / Runnable）**：正在使用 CPU，或正在等待 CPU；
- **不可中断（D，Uninterruptible Sleep，也叫 Disk Sleep）**：正处在内核态关键流程中，且流程不可打断，最常见的是等硬件设备的 I/O 响应。进程读写磁盘时，为保证数据一致性，在拿到磁盘回复前不能被其他进程或中断打断，否则会出现磁盘数据与进程数据不一致——**不可中断状态是系统对进程和硬件设备的一种保护机制**。

所以平均负载里既有「正在吃 CPU 的」，也有「在等 CPU 的」和「在等 I/O 的」。**CPU 使用率只统计 CPU 繁忙情况，两者不一定对应**——这是全部误读的源头。

怎么判断高低？先知道有几个 CPU：

```bash
$ grep 'model name' /proc/cpuinfo | wc -l
2
```

最理想的情况是**平均负载等于 CPU 个数**：每个 CPU 上刚好跑一个进程。负载为 2 时：

- 2 核机器：所有 CPU 刚好被完全占用；
- 4 核机器：CPU 有 50% 空闲；
- 1 核机器：有一半进程竞争不到 CPU。

三个值都要看，它们给的是趋势：

- 三个值差不多：负载平稳；
- 1 分钟远小于 15 分钟：最近在降，但过去 15 分钟压力很大；
- 1 分钟远大于 15 分钟：最近在涨，可能只是临时尖峰，也可能继续涨，要持续观察；一旦 1 分钟值接近或超过 CPU 个数，就是正在过载。

一个单核例子：`1.73, 0.60, 7.98` 意味着过去 1 分钟超载 73%，过去 15 分钟超载 698%，整体趋势在缓解。

**经验阈值：平均负载高于 CPU 数量的 70% 就该开始排查。**这是原作者的经验判断，不是硬标准；更稳的做法是把负载纳入监控，看历史趋势，比如发现负载翻倍再动手。

三种典型形态，决定了完全不同的排查方向：

| 形态 | load | us | wa | 说明 |
|---|---|---|---|---|
| CPU 密集型 | 高 | 高 | 低 | 进程真的在算，load 与 CPU 使用率同向 |
| I/O 密集型 | 高 | 低 | 高 | 进程卡在硬件上，CPU 大量空闲 |
| 进程多、抢 CPU | 高 | 高 | 低 | 可运行进程数超过核数，每个都在等时间片 |
| 进程多、都等锁/等 IO | 高 | 低 | 可能低 | 自愿上下文切换飙升，CPU 反而不忙 |

**「load 高但 CPU 不高」的判定路径**（原案例机器为 2 核 8GB）：

1. `uptime` / `top` 看三个负载值与核数比；
2. `mpstat -P ALL 5` 看 `%usr`、`%sys`、`%iowait` 落在哪一列——`wa` 高就往 I/O 走，`us` 高就往进程走；
3. `vmstat 1` 看 `r`（就绪队列长度）与 `b`（不可中断进程数）：`r` 大是抢 CPU，`b` 大是等 I/O；
4. `pidstat -u 5 1` 找具体进程，`pidstat -d 1` 看谁在读盘。

原案例的三个场景正好覆盖三种形态：`stress --cpu 1` 让 1 分钟负载涨到 1.00，某一个 CPU 的 `us` 到 100%、`iowait` 为 0；`stress -i 1`（不停 `sync`）让负载到 1.06，一个 CPU 的 `sys` 到 23.87%、`iowait` 高达 67.53%；`stress -c 8` 在 2 核机器上把负载推到 7.97，每个 stress 进程只有 25% 的 CPU、`%wait` 高达 75%。

## 上下文切换：三类场景，成本在缓存不在寄存器

Linux 是多任务操作系统，支持远大于 CPU 数量的任务同时运行——靠的是把 CPU 在极短时间片里轮流分配。任务运行前，CPU 需要知道从哪里加载、从哪里开始运行，这依赖 **CPU 寄存器**（内置的、容量小但速度极快的内存）和**程序计数器 PC**（存正在执行或下一条指令的位置）。这两样合起来就是 **CPU 上下文**。

上下文切换就是：保存前一个任务的上下文 → 加载新任务的上下文 → 跳到 PC 指向的新位置运行。保存下来的上下文存在内核里，任务再次被调度时重新加载，于是任务看起来是连续运行的。

按「任务是什么」分三类：

| 类型 | 切的是什么 | 触发点 | 是否换进程 |
|---|---|---|---|
| 进程上下文切换 | 虚拟内存、栈、全局变量等用户空间资源 + 内核堆栈、寄存器等内核空间状态 | 进程调度（时间片耗尽、资源不足、主动 sleep、高优先级抢占、硬件中断） | 是 |
| 线程上下文切换 | 同进程内只切私有数据（栈、寄存器）；跨进程则等同进程切换 | 线程调度 | 同进程内不换 |
| 中断上下文切换 | 只含内核态中断服务所需状态：CPU 寄存器、内核堆栈、硬件中断参数 | 硬件中断打断当前任务 | 不涉及用户态 |

调度的具体规则（时间片怎么分、优先级怎么排、就绪队列怎么组织）见 [11.1 进程、线程与调度](11.1-进程-线程与调度.md)，这里只关心它的代价。

系统调用要单独说清：从用户态陷入内核态，寄存器里用户态的指令位置要先保存，再更新为内核态指令位置，返回时恢复——**一次系统调用发生了两次 CPU 上下文切换**，但它不涉及虚拟内存等用户态资源，也不切换进程。所以它通常叫**特权模式切换**，不算进程上下文切换，可成本依然存在。

线程切换比进程切换便宜的原因很直接：同进程的两个线程共享虚拟内存，切换时虚拟内存这些资源保持不动，只切私有数据。多线程替代多进程的优势就来自这里。反过来，**跨进程的线程切换和进程切换一样贵**。

为什么贵？两个来源，第二个才是大头：

1. 寄存器、内核栈的保存与恢复，需要内核在 CPU 上跑才能完成；
2. **虚拟内存更新后 TLB 要刷新，内存访问随之变慢**；多处理器系统上缓存被多个处理器共享，刷新缓存不只影响当前处理器的进程，还会影响共享缓存的其他处理器上的进程。缓存层次、跨核污染与 NUMA 局部性见 [11.6 CPU Cache 与 NUMA](11.6-CPU-Cache与NUMA.md)。

成本量级：据 Tsuna 的测试报告，每次上下文切换需要**几十纳秒到数微秒**的 CPU 时间。切换次数一多，CPU 大量时间耗在保存和恢复上，真正运行进程的时间被压缩——这正是平均负载升高的重要来源之一。

**自愿与非自愿，指向两种完全不同的病因：**

| 指标 | 含义 | 变多说明什么 |
|---|---|---|
| `cswch/s` | 每秒自愿上下文切换：进程拿不到所需资源（I/O、内存等）而主动让出 CPU | 进程都在**等资源**，往 I/O 方向查 |
| `nvcswch/s` | 每秒非自愿上下文切换：时间片到、被系统强制调度 | 进程都在**抢 CPU**，CPU 确实是瓶颈 |

观测入口：

```bash
$ vmstat 5
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 0  0      0 7005360  91564 818900    0    0     0     0   25   33  0  0 100  0  0
```

四列必须记住：`cs` 每秒上下文切换次数、`in` 每秒中断次数、`r` 就绪队列长度（正在运行 + 等待 CPU 的进程数）、`b` 不可中断睡眠的进程数。

进程级用 `pidstat -w`；**注意它默认只输出进程级指标，加 `-t` 才输出线程级**。原案例里 `pidstat -w` 加起来的切换次数只有几百，而 `vmstat` 报的是 139 万——不是工具错了，是漏了线程：`pidstat -wt` 之后能看到 sysbench 的子线程 `cswch/s` 约 1.9 万、`nvcswch/s` 约 10 万。

原案例的完整读数（2 核机器）：空闲时 `cs=35`、`in=19`；`sysbench --threads=10` 压起来后 `cs` 涨到 139 万、`r=8`（远超 2 个 CPU）、`us=16`、`sy=84`、`in` 涨到 1 万左右。`in` 上涨对应哪类中断，去 `/proc/interrupts` 看：变化最快的是 RES（重调度中断，也叫处理器间中断 IPI，作用是唤醒空闲 CPU 去调度新任务），还是同一个调度问题。

**多少次算正常？**原作者的经验判断：稳定在数百到一万以内都算正常；超过一万，或出现数量级增长，很可能已有性能问题。这个数字与机器性能相关，不能当常量用。

## CPU 使用率：十个字段的口径与四个误读

CPU 使用率的底座是节拍：内核用事先定义的节拍率 `HZ` 触发时间中断，全局变量 `Jiffies` 记录开机以来的节拍数，每来一次时间中断就加 1。`HZ` 是可配项，可以是 100、250、1000，用 `grep 'CONFIG_HZ=' /boot/config-$(uname -r)` 查（原案例机器是 250，即每秒 250 次时间中断）。用户空间程序不能直接读 `HZ`，内核另给一个固定为 100 的 `USER_HZ`，也就是 1/100 秒 = 10ms，`/proc/stat` 里所有 CPU 时间都以它为单位。

```bash
$ cat /proc/stat | head -1
cpu  3138 0 448 312262 118 0 133 0 0 0
```

上面是本机实测（容器内 8 vCPU，只截了聚合的 `cpu` 行）：**一共 10 个数字**，顺序固定；`cpu0`、`cpu1`… 每行一个 CPU，字段与聚合行相同。

> ⚠️ **`top` 显示的 `%Cpu(s)` 只有 8 列**（us/sy/ni/id/wa/hi/si/st），`mpstat` 是 10 列（多 `%guest`/`%gnice`）。对不上不是工具错了，是有的列被合并或省略——`us` 在 `top` 里**已包含 guest**，所以把 `top` 的 us 与 `/proc/stat` 的 `user` 直接相减会得到假差值。

不带编号的 `cpu` 行是所有 CPU 的累加，其余每行一个 CPU。列的含义（按顺序）：

| 字段 | 缩写 | 含义 | 误读 |
|---|---|---|---|
| `user` | us | 用户态 CPU 时间，**不含 nice，含 guest** | 高就是应用在算——基本成立，但要先排除 guest |
| `nice` | ni | nice 值被调成 1–19 的低优先级用户态时间（nice 范围 -20 到 19，值越大优先级越低） | 常被忽略，其实是「被降权的用户态」 |
| `system` | sys | 内核态 CPU 时间 | 高一般是系统调用/内核线程，不是业务逻辑慢 |
| `idle` | id | 空闲时间，**不含 iowait** | 用 id 算占用率时别把 wa 算成忙 |
| `iowait` | wa | 等待 I/O 的 CPU 时间 | **CPU 空闲但至少有一个任务在等 I/O**，不是 CPU 在干活 |
| `irq` | hi | 处理硬中断的时间 | 高要查网卡多队列与中断亲和 |
| `softirq` | si | 处理软中断的时间 | 高基本等于网络收发压力 |
| `steal` | st | 虚拟化下被其他虚拟机占用的 CPU 时间 | 云主机性能不达标的头号证据 |
| `guest` / `guest_nice` | guest / gnice | 运行虚拟机的时间 / 以低优先级运行虚拟机的时间 | 宿主机上看到 guest 高，说明压力来自虚拟机内部 |

CPU 使用率 = 除空闲时间外的其他时间占总时间的百分比。但**直接拿 `/proc/stat` 的累计值算出来的，是开机以来的平均使用率**，一般没有参考价值。工具都是取间隔一段时间的两次值作差再算：

```
CPU 使用率 = 1 - (idle_2 - idle_1) / (total_2 - total_1)
```

这就是各种工具显示的 CPU 使用率的实际算法。由此带来一个实操坑：**不同工具的间隔不同，数字不可直接对比**。`top` 默认 3 秒间隔，`ps` 用的是进程整个生命周期，两者默认结果不一样很正常；多工具交叉验证时必须统一间隔。

四个误读，逐条纠正：

- **`wa` 高不是 CPU 在忙。**它表示 CPU 空闲着，只是有任务卡在 I/O 上。而且**`wa` 高不等于 I/O 有瓶颈**：当系统里只有 I/O 型进程在跑时，`wa` 也会很高，磁盘远没到瓶颈。要用 `dstat`、`pidstat -d` 确认是不是真在读写。
- **`si` 高不是「进程慢」。**它是 CPU 在替内核跑软中断，业务进程反而拿不到 CPU。原案例里两个 CPU 的 si 只有 3.3% 和 4.4%，负载全 0，但系统已经卡到敲回车都要等——**使用率低不等于没问题，要看这块钱花在哪**。
- **`st` 高不是自己代码的问题。**物理机不会出现，只有虚拟机才有；持续非零说明宿主把 CPU 分给了别人，扩容自己这台没用。
- **进程 `%CPU` 不等于它占用的物理 CPU。**`top` 的进程 `%CPU` 是用户态 + 内核态的总和，还包括在就绪队列里等待运行的时间，虚拟化下还包括运行虚拟机的 CPU。所以进程列加起来小于系统总使用率是正常的。要看细分，用 `pidstat`：

```bash
$ pidstat 1 5
15:56:02      UID       PID    %usr %system  %guest   %wait    %CPU   CPU  Command
15:56:03        0     15006    0.00    0.99    0.00    0.00    0.99     1  dockerd
```

`%usr`、`%system`、`%guest`、`%wait`（等待 CPU）、`%CPU` 分开给，还带 `CPU` 列告诉你它跑在哪个核上——**`%wait` 是判断「抢 CPU」还是「算得慢」的关键列**。

## 软中断升高：五步定位链

现象是 `si` 高，或 `ksoftirqd/N` 挤进 CPU 排行前列，或系统整体响应变慢但使用率不高。按固定链路走：

| 步 | 命令 | 看什么 | 判据 |
|---|---|---|---|
| 1 | `top` 按 `1` | 每个 CPU 的 `si`、进程里的 `ksoftirqd` | si 高，且集中在少数 CPU |
| 2 | `watch -d -n 1 cat /proc/softirqs` | 哪一类涨得最快 | `NET_RX` 涨 → 收包压力；`BLOCK` 涨 → 块设备 |
| 3 | `sar -n DEV 1` | `rxpck/s`、`txpck/s`（PPS）与 `rxkB/s`、`txkB/s`（BPS） | PPS 大而 BPS 小 → 小包问题 |
| 4 | `mpstat -P ALL 1` | 是否只有一两个 CPU 的 `%soft` 高 | 只有 CPU0 高 → 中断没摊开 |
| 5 | `tcpdump -i eth0 -n tcp port 80` | 包的类型与来源 | 全是 `Flags [S]` → SYN FLOOD |

第 3 步的算法很实用：`sar` 的输出里，`rxkB/s × 1024 ÷ rxpck/s` 就是平均每帧字节数。原案例是 `664 × 1024 ÷ 12607 ≈ 54` 字节，典型的**小包**——网卡收的是「数量」而不是「流量」，每帧都要走一次硬中断 + 一次协议栈处理，PPS 才是压垮 CPU 的量。

第 4 步的结论决定了对策方向：**如果只有一两个 CPU 的 si 高，说明中断集中在少数 CPU，而不是总量太大。**这时扩容没用，要把处理摊开，或者把每帧的成本降下来。

| 对策 | 怎么做 | 代价 / 边界 |
|---|---|---|
| RPS（接收包分发） | 写 `/sys/class/net/<dev>/queues/rx-*/rps_cpus`（十六进制 CPU 掩码），配合 `rps_flow_cnt` 与 `net.core.rps_sock_flow_entries` | 把软中断分到多核，但跨 CPU 传包会打 cache，收益有上限 |
| RFS（流级别分发） | `rps_flow_cnt` + `rps_sock_flow_entries`，让同一连接固定在同一 CPU | 需要按连接数调参，表项满了退化 |
| 多队列网卡 + 中断亲和 | 开 `irqbalance` 服务，或手写 `/proc/irq/<N>/smp_affinity` | 单队列网卡无解——硬件只有一个队列，只能靠 RPS 软分摊 |
| 减少小包 | 应用侧合并写（Nagle 已默认开）、批量提交、协议上减少往返 | 会增加延迟，交互型业务要权衡 |
| 把协议栈挪出内核 | DPDK、XDP 一类方案 | **超出本节范围的进阶手段**：DPDK 要独占一个 CPU 和一定数量的大页内存，并总是以 100% 的 CPU 使用率运行，核数少时得不偿失 |

## 案例：Nginx 反向代理的软中断（原案例机器 2 核 8GB）

**现象。**两台虚拟机，一台跑 `docker run -itd --name=nginx -p 80:80 nginx`，另一台用 `hping3 -S -p 80 -i u100 192.168.0.30` 施压（`-S` 设 SYN，`-i u100` 表示每 100 微秒发一帧）。压上去后，Nginx 那台机器敲几个回车都要等很久。`top` 按 `1`：

```
top - 10:50:58 up 1 days, 22:10,  1 user,  load average: 0.00, 0.00, 0.00
Tasks: 122 total,   1 running,  71 sleeping,   0 stopped,   0 zombie
%Cpu0  :  0.0 us, 0.0 sy, 0.0 ni, 96.7 id,  0.0 wa,  0.0 hi,  3.3 si,  0.0 st
%Cpu1  :  0.0 us, 0.0 sy, 0.0 ni, 95.6 id,  0.0 wa,  0.0 hi,  4.4 si,  0.0 st
```

三个数字都不大：负载全 0、就绪队列只有 1 个进程、最高使用率的进程只有 0.3%。**异常只能从「这块钱花在哪」看出来**——两个 CPU 的使用率都落在 `si` 上，进程列表里靠前的正是 `ksoftirqd/0`、`ksoftirqd/1`。

**命令链与读数。**

1. `watch -d cat /proc/softirqs`：`TIMER`、`NET_RX`、`SCHED`、`RCU` 都在动，其中 `NET_RX` 变化最快。后三类是调度、时钟、临界区保护的正常开销，`NET_RX` 才是嫌疑。
2. `sar -n DEV 1`：`eth0` 的 `rxpck/s=12607`、`txpck/s=6304`、`rxkB/s=664.86`、`txkB/s=358.11`。算出平均每帧 54 字节，是小包。`docker0` 与 `veth9f6bbcd` 的收发数字与 `eth0` 基本镜像（网桥把包转给 Nginx 容器），可以忽略。
3. `tcpdump -i eth0 -n tcp port 80`：`192.168.0.2.18238 > 192.168.0.30.80: Flags [S]`，全是 SYN 包，来自施压机。结合 PPS 超过 12000，确认是 SYN FLOOD。

下半部把协议栈逐层解析完，数据才挂到对应 socket 的就绪队列上，应用才可能被唤醒——这一步与 [11.4 epoll 与 IO 多路复用](11.4-epoll与IO多路复用.md) 的唤醒链路首尾相接：软中断处理不过来时，epoll 侧看到的就是「连接在、数据不来」。

**根因。**两条叠加：一是**每秒上万个小包**，每帧都要走中断 + 协议栈，单帧收益极低；二是**软中断在单个 CPU 上是串行的**，中断落在哪个 CPU，就由那个 CPU 的 `ksoftirqd` 独自消化。原案例这台 2 核机器上 `NET_RX` 两侧还在同一数量级（1550643 / 1916776），分摊尚可；但在多核 + 单队列网卡的机器上，硬中断全部落到 CPU0，就退化成「CPU0 的 si 独高、其他核围观」——同一病症的另一种形态，也是生产上更常见的那一种。

**处置。**SYN FLOOD 最直接的办法是在交换机或硬件防火墙上封掉来源 IP，网络帧到不了服务器，问题就消失。注意原案例的 `NET_RX` 数字来自一个**伪造源的攻击流量**，属于「要么在入口拦掉，要么无解」的类别；而 RPS/RFS、多队列、减少小包这些手段，对付的是正常的收包压力。

## D 状态与僵尸：iowait 的两个来源

`top` 的 `S` 列（Status）和 `ps` 的 `STAT` 列是同一套状态：

| 状态 | 含义 | 是否计入 load |
|---|---|---|
| `R` | Running / Runnable：在就绪队列里，正在跑或等 CPU | 是 |
| `S` | Interruptible Sleep：等某个事件被挂起，事件到了回 `R` | 否 |
| `D` | Uninterruptible Sleep（Disk Sleep）：与硬件交互中，不允许被其他进程或中断打断 | **是** |
| `I` | Idle：空闲的内核线程。硬件交互导致的不可中断用 `D`，但有些内核线程其实没负载，用 `I` 区分 | **否** |
| `Z` | Zombie：进程已退出，父进程还没回收其资源 | 否 |
| `T` / `t` | Stopped / Traced：`SIGSTOP` 暂停，或调试器断点跟踪 | 否 |
| `X` | Dead：已消亡，`top`/`ps` 里看不到 | 否 |

**`D` 是一种保护。**进程读磁盘时，为保证数据与硬件状态一致，在拿到回复前不能被别的进程或中断打断，否则磁盘数据和进程数据会不一致。所以短时间的 `D` 完全正常；但**长时间 `D` 或大量 `D`，说明硬件交互卡住了**——磁盘、网络存储（NFS/iSCSI）是最常见的两类。`D` 状态的进程会计入平均负载，所以 load 高而 CPU 闲，第一嫌疑就是它。

**`Z` 是回收漏了。**正常情况下父进程用 `wait()`/`waitpid()` 等子进程结束并回收资源，子进程退出时会给父进程发 `SIGCHLD`，父进程也可以注册该信号的处理函数异步回收。如果父进程没这么做，或者子进程退出太快、父进程来不及处理，子进程就变成僵尸。僵尸进程只剩一个 `task_struct` 和 PID，**不占 CPU，但占 PID 与内核栈**；大量僵尸会耗尽 PID，导致新进程创建失败。父进程退出后由 init 回收，所以短命僵尸可以不管；父进程一直活着且一直不 `wait`，僵尸就会一直堆着。

```bash
$ ps -eo state,pid,ppid,cmd | grep -E '^D|^Z'
```

**原案例的完整链条**（2 核 8GB，`docker run --privileged --name=app feisky/app:iowait`）：

1. `top` 看到 `iowait` 高达 60.5%（CPU0）和 94.6%（CPU1），load `2.00, 1.68, 1.39`（1 分钟值已等于核数），`115 zombie`，最高 CPU 的进程只有 0.3%，另有两个 `app` 处于 `D`。
2. `dstat 1 10` 同时看 CPU 与磁盘：每次 `wai` 升高，`read` 都在几十 MB 量级，说明 iowait 与磁盘读强相关。
3. `pidstat -d -p 4344` 看那两个 `D` 进程：`kB_rd/s`、`kB_wr/s`、`iodelay` 全是 0，不是它们。
4. `pidstat -d 1` 去掉进程号看全部：某个 `app` 进程 `kB_rd/s=32768.00`（即 32 MB/s）、`iodelay` 170 上下。
5. 想 `strace -p` 抓系统调用，报 `ptrace(PTRACE_SEIZE): Operation not permitted`——`ps` 一看，该进程已变成 `Z`（`[app] <defunct>`），已经退出，抓不到了。
6. 改用 `perf record -g` 采 15 秒再 `perf report`：调用栈里出现 `sys_read()`、`new_sync_read`、`blkdev_direct_IO`——**直接 I/O，绕过 page cache**，每次读都直落磁盘。源码里确认 `open(disk, O_RDONLY|O_DIRECT|O_LARGEFILE, 0755)`。采样事件与调用栈的读法见 [34.3 性能分析方法 (火焰图 / pprof / perf)](../../L3-质量属性/34-性能/34.3-性能分析方法.md)。
7. 去掉 `O_DIRECT` 换成缓存 I/O，iowait 降到 0.3%；但 `12 zombie` 还在涨。
8. `pstree -aps 3084` 找到僵尸的父进程是 4009（app 本体）。源码里 `while(wait(&status)>0);` **被放在了 `for` 死循环外面**，实际一次都没执行到；挪进循环内，僵尸归零。

这个案例的教学点在于：**`D` 会变 `Z`**。等 I/O 的进程如果随后退出而父进程不回收，就从「不可中断」直接跳到「僵尸」，`strace` 这类 attach 型工具就失效了，只能靠 `perf` 这类采样工具看调用栈。另外，iowait 高不必然等于 I/O 瓶颈，必须用 `dstat`/`pidstat` 落到具体进程和具体设备上。绕过 page cache 的代价，以及它和内存回收、swap 之间的拉扯，见 [11.10 内存回收：水位、page cache、swap 与 OOM](11.10-内存回收-水位-page-cache-swap与OOM.md)。

## 排障总表：症状 → 指标 → 工具 → 根因

| 症状 | 先看哪个指标 | 用什么工具 | 常见根因 |
|---|---|---|---|
| load 高，us 也高 | `us`、`r`、进程 `%CPU` | `uptime`、`mpstat -P ALL`、`pidstat -u` | CPU 密集型进程、死循环、计算量本身大 |
| load 高，us 低，wa 高 | `wa`、`b`、`kB_rd/s` | `mpstat`、`vmstat`、`dstat`、`pidstat -d` | 磁盘慢、直接 I/O、网络存储卡住 |
| load 高，CPU 都低，`b` 大 | `b`、`D` 状态进程数 | `vmstat 1`、`ps -eo state,pid,cmd` | 大量进程卡在硬件交互上 |
| CPU 高但找不到高 CPU 进程 | `Tasks` 行的 running 数、`R` 状态进程 | `top`、`pidstat -p`、`pstree`、`execsnoop` | 短时进程（应用 exec 外部命令）、进程反复崩溃重启 |
| `si` 高，`hi` 也可能高 | `softirq`、`NET_RX` 速率 | `top`、`watch -d cat /proc/softirqs` | 小包/收包压力、SYN FLOOD、单队列网卡中断集中 |
| `si` 只在一两个 CPU 高 | 各 CPU 的 `%soft` | `mpstat -P ALL 1`、`/proc/interrupts` | 中断亲和没配、网卡队列数少于核数 |
| `hi` 高 | `irq`、每 CPU 中断计数 | `/proc/interrupts`、`/proc/irq/*/smp_affinity` | 中断全落一个核、没开 `irqbalance` |
| `sy` 高，`cs` 也高 | `cs`、`sy`、`nvcswch/s` | `vmstat 1`、`pidstat -w -t` | 线程数过多、锁竞争、系统调用密集 |
| 吞吐上不去，`st` 非零 | `steal` | `top`、`mpstat` | 云主机被超卖，宿主抢走 CPU |
| 僵尸进程持续增长 | `zombie` 计数、`Z` 状态 | `top`、`ps -eo state,pid,ppid`、`pstree -aps` | 父进程没 `wait()`、`SIGCHLD` 没处理 |

表里「短时进程」这一行最容易误判：`top` 隔几秒才刷一次，短命进程可能一次都没落进采样窗口。`execsnoop` 靠 ftrace 实时监控 `exec()`，直接给出 PID、父 PID、命令行与返回值——这类「按事件记录」的思路与 [11.7 eBPF 与内核态观测](11.7-eBPF与内核态观测.md) 是同一套机制，区别只是挂载点。

## 反模式

| 反模式 | 后果 |
|---|---|
| 把平均负载当 CPU 使用率 | load 高就扩容或换 CPU，实际瓶颈在磁盘，钱花了问题还在 |
| 只看 `top` 的第一屏就下结论 | si 只有几个百分点时被当成「机器很闲」，忽略 `ksoftirqd` 和 `%soft` 列 |
| 只用 `pidstat`（不加 `-t`）查上下文切换 | 线程级切换全部漏掉，计数差几个数量级也发现不了 |
| 直接 `cat /proc/softirqs` 判断当下问题 | 看到的是开机以来累计值，与当前压力无关 |
| 看到 `NET_RX` 同量级就认为「分布均衡没问题」 | 忽略了「同 CPU 内串行」这一层，多核机器上仍可能单核打满 |
| `wa` 高就断定磁盘有瓶颈 | 只有 I/O 型进程在跑时 `wa` 也会高，误判会引导去换盘 |
| 云主机上 `st` 高却继续优化应用代码 | 时间被宿主拿走，应用侧任何优化都拿不回这部分 CPU |
| 用 `strace` 去追已经变成 `Z` 的进程 | `ptrace` 附着失败，白跑一轮；应改用 `perf` 采样 |
| 僵尸进程用 `kill -9` 处理 | 僵尸已死，信号无效；必须让父进程 `wait` 或先停掉父进程 |
| 单队列网卡上只调 `smp_affinity` | 硬件只有一个队列，中断无处可摊，必须配合 RPS |

## 三条铁律

> 🔑 **CPU 使用率是「时间的去向」，不是「忙不忙」。**100% 可能是业务在算，也可能是内核在收包，还可能是 CPU 闲着等磁盘——先分清 us/sy/wa/hi/si/st，再谈优化。

> 🔑 **软中断的问题永远先看分布，再看总量。**`/proc/softirqs` 里同一行跨 CPU 差一个数量级，说明瓶颈在「集中」而不在「多」；这时候加核无用，摊开才有用。

> 🔑 **load 里混着 R 和 D 两种完全不同的等待。**R 多去查 CPU 争抢（`nvcswch`、`%wait`），D 多去查硬件（`wa`、`kB_rd/s`、`iodelay`）；把两者混为一谈，排查方向必然错一半。

## 生产落地：指名 → 可抄 → 可验 → 可退

工具指名：`sysstat`（提供 `mpstat`/`pidstat`/`sar`）、`irqbalance`、`dstat`、`perf`。

**实测环境**：Docker Desktop 29.9.2 → LinuxKit 虚拟机 → Alpine 3.20 容器，内核 `7.0.14-linuxkit`，8 vCPU / 4GB 内存。下文带「实测」的输出是本机真实粘贴，未标注的仍是格式示意；容器里看不到的（内核线程、宿主 `st`）单独注明。

**① 看软中断分布（第一步永远是这个）**

```bash
# 累计值：只看类型对不对，别用它判断当下压力
cat /proc/softirqs
# 速率：高亮变化区域，哪一行的数字跳得最快就是它
watch -n 1 -d cat /proc/softirqs
```

实测输出（8 vCPU，节选；注意 `BLOCK` 全压在 CPU0）：

```
                    CPU0       CPU1       CPU2       CPU3       CPU4       CPU5       CPU6       CPU7
          HI:          0          0          0          0          0          0          0          0
       TIMER:       1018        622        827        775        410        466        781        956
      NET_TX:          5          2          1          1          2          2          3          2
      NET_RX:       6759         45        138        464         96        133       1828       2198
       BLOCK:       4036          0          0          0          0          0          0          0
    IRQ_POLL:          0          0          0          0          0          0          0          0
     TASKLET:          0          0         57          0          0          0          0          0
       SCHED:       3085       1722       1127       1355       1064       1115       1757       2662
     HRTIMER:          0          0          0          0          0          0          0          0
         RCU:       1495       1338       1258       1518       1249       1260       1522       1365
```

判据：`NET_RX` 每秒增量在万级，且某一行在 CPU 之间差一个数量级 → 收包压力 + 分布不均。本机 `BLOCK` 是 4036 : 0 的极端分布，来源是 virtio 单队列：这类“集中”在虚拟机上几乎必然出现，加 vCPU 无用。

**② 看硬中断与中断亲和**

```bash
cat /proc/interrupts | head -20          # 每 CPU 一列，看哪个核在扛
cat /proc/irq/<N>/smp_affinity_list      # 十进制 CPU 列表，如 0-3
cat /proc/irq/<N>/smp_affinity           # 十六进制掩码，如 ff 表示 CPU0-7
systemctl status irqbalance              # 是否在跑
```

实测输出（虚拟机 + virtio 设备，中断号 11–23）：

```
           CPU0       CPU1       CPU2       CPU3       CPU4       CPU5       CPU6       CPU7
 11:       6244       6464       5760       6980       5627       5672       6978       8767    GICv3  27 Level     arch_timer
 14:       6635          0          0          0          0          0          0          0    GICv3  65 Level     virtio0
 16:       3595          0          0          0          0          0          0          0    GICv3  70 Level     virtio2
```

`virtio0`/`virtio2` 只落在 CPU0，`arch_timer` 均匀分散——**“哪些中断必须手动摊开”从这一屏就能读出来**。实测 `cat /proc/irq/14/smp_affinity_list` 是 `0-7`、`smp_affinity` 是 `ff`：亲和性配置允许全部 8 个核，但 virtio 单队列的连接仍是单点，允许 ≠ 摊开。

**③ 打开 RPS（单队列网卡把软中断摊到多核）**

```bash
# 前提：确认队列存在，且是单队列（只有 rx-0）
ls /sys/class/net/eth0/queues/
# 把 rx-0 的软中断分给 CPU0-3：f = 0b1111
echo f > /sys/class/net/eth0/queues/rx-0/rps_cpus
# 流表容量（4096 / 32768 是示例值，按实际连接数调）：每队列流数上限 + 全局 socket 流表项
echo 4096 > /sys/class/net/eth0/queues/rx-0/rps_flow_cnt
sysctl -w net.core.rps_sock_flow_entries=32768
# 验证
cat /sys/class/net/eth0/queues/rx-0/rps_cpus
```

实测：`rps_cpus` 原值 `00`，写 `f` 后读回 `0f`，**veth 上也能写成功**（队列 `rx-0`/`tx-0` 各一条）。但同一台机器上 `net.core.rps_sock_flow_entries` **不存在**（`cannot stat ... No such file or directory`），说明该内核没启用 RFS 的 socket 流表——**写之前先 `ls` 确认参数在不在**，别照抄教程。回滚：`echo 0 > /sys/class/net/eth0/queues/rx-0/rps_cpus`，即关闭该队列的 RPS。

**④ 看 D 状态与僵尸**

```bash
ps -eo state,pid,ppid,cmd | grep -E '^D|^Z'
# 统计各状态数量，比 grep 稳
ps -eo stat | awk '{print substr($1,1,1)}' | sort | uniq -c | sort -rn
# 僵尸的父进程链
pstree -aps <PID>
```

实测（空闲容器里只有 S 和 R，没有 D/Z，所以下面这段是**格式示意**，不是本机数据）：

```
D             620     1 /app
Z            3084  4009 [app] <defunct>
```

**⑤ 上下文切换与中断次数**

```bash
vmstat 1            # r / b / in / cs 四列
mpstat -P ALL 1     # 每核 %usr/%sys/%iowait/%irq/%soft/%steal
pidstat -w -t 1     # -w 切换指标，-t 展开到线程
```

实测（起 4 个 `while :;` 忙循环后，8 vCPU）：`mpstat` 显示其中 4 个核 `%usr` 100%、其余核接近空闲；`pidstat -w` 里忙循环所在的 `sh` 出现 `nvcswch/s ≈ 5`（非自愿切换，被抢占），而 `pidstat`/`tail` 这类短命进程只有 `cswch/s`（自愿）。**“非自愿”才是 CPU 不够的信号**。

**⑥ 验证优化是否生效（可退）**

```bash
mpstat -P ALL 1     # 看各核 %soft 是否被摊平
watch -n 1 -d cat /proc/softirqs   # 看 NET_RX 增量是否从单核变成多核
ethtool -l eth0     # 队列数：RX/TX 各几条
```

判据：优化前 `%soft` 只有一个核高、其余接近 0；优化后多个核的 `%soft` 都在同一量级。若没有变化，先确认网卡队列数（实测本机 veth 的 `ethtool -l eth0` 报 `Pre-set maximums: RX: 8 / TX: 8`，`Combined: n/a`）与 `irqbalance` 状态，再回退 RPS 配置以免留下无效参数。

## 自检

**Q1** 某 4 核机器 `uptime` 显示 `8.20, 7.90, 7.60`，`top` 里 `us=3%`、`wa=85%`、`si=1%`，`vmstat 1` 的 `r=1`、`b=12`。这属于哪种问题？下一步查什么？

▸ 答案：load 约 8 等于核数的 2 倍，但 CPU 几乎不忙——负载不是被 CPU 抢出来的，而是被 `D` 撑起来的（`b=12` 正是不可中断进程数）。这是 I/O 密集型/硬件卡住，不是 CPU 瓶颈。下一步：`dstat 1` 对齐 `wai` 与磁盘读写，`pidstat -d 1` 找具体进程的 `kB_rd/s` 与 `iodelay`，再看是本地盘还是网络存储；扩容 CPU 在这里完全无效。

**Q2** `wa` 高达 90%，能不能说「CPU 在拼命干活」？为什么 `wa` 高不一定代表磁盘到了瓶颈？

▸ 答案：不能。`wa` 的定义是 CPU 空闲、但至少有一个任务在等 I/O 的时间——CPU 恰恰没在干活。`wa` 高也不等于磁盘到瓶颈：当系统里只有 I/O 型进程在跑时（比如原案例 `stress -i` 不停 `sync`，或一个进程用 `O_DIRECT` 直读），`wa` 会很高而磁盘远未饱和。判定必须落到 `dstat`（`wai` 与 `read/writ` 是否同向）和 `pidstat -d`（谁的 `kB_rd/s`、`iodelay` 大）上。

**Q3** `/proc/softirqs` 里 `NET_RX` 在 CPU0 是 500 万级，CPU1–CPU7 都只有几万，`si` 总量并不高。这说明什么？该加机器还是改配置？

▸ 答案：说明软中断**集中在 CPU0**，不是总量过大。同一 CPU 上的软中断由它自己的 `ksoftirqd/0` 串行处理，所以 CPU0 会先饱和，其余 7 个核围观——加核一点用没有。改配置：确认网卡队列数（单队列就开 RPS，把 `rx-0` 的 `rps_cpus` 摊到多核）；有多队列就配 `smp_affinity` 或开 `irqbalance`，同时评估是否是小包（`rxkB/s×1024÷rxpck/s` 很小）。

**Q4** 一台机器 `cs` 从 3 万涨到 120 万，`sy=80%`，但 `pidstat -w` 里所有进程的 `cswch/s` 加起来只有几百。哪里错了？

▸ 答案：漏了线程。Linux 调度的基本单位是线程，`pidstat` 默认只输出进程级指标，必须加 `-t` 才展开到线程（`pidstat -wt`）。原案例就是这个坑：进程级几百，线程级单个数万。另外要用 `nvcswch/s` 与 `cswch/s` 分流：非自愿多 = 抢 CPU，自愿多 = 等资源。

**Q5** 云主机上业务 `us` 只有 20%，但吞吐只有本地机器的三分之一，`st` 长期在 15% 上下。该优化代码还是换机器？怎么一句话向上解释？

▸ 答案：都不是代码问题。`st`（steal）是虚拟化下被其他虚拟机占用的 CPU 时间，物理机上不存在这一列；持续非零说明宿主把 CPU 分给了别人，本机拿不到那 15%，再怎么优化应用也拿不回来。换独享型实例/物理机，或按 `st` 调整容量模型。一句话解释：`us` 低说明我们没在算，`st` 高说明该给的时间没给到，瓶颈在宿主不在应用。
