# 9.6 边缘计算模型

## 一句话

> 边缘计算把 “几毫秒就能做完的决策” 放到离用户最近的地方；但它有三条硬约束——**无状态、有时限、存储小**——凡是超出这三条的逻辑，都应该放回中心。

## 三种模型：从 “改请求” 到 “跑代码”

| 模型 | 能力 | 典型用途 | 约束 |
|---|---|---|---|
| **边缘函数**（请求/响应钩子） | 改写请求、生成响应、鉴权、A/B | 重写 URL、灰度分流、JWT 校验、返回 302 | CPU 时间毫秒–几十毫秒、内存几十 MB |
| **边缘 KV / 配置** | 读小数据（配置、名单、路由表） | 灰度名单、租户路由、机器人名单 | **最终一致**，写入延迟高 |
| **边缘容器** | 跑较完整的服务 | 图片处理、轻量 SSR、边缘网关 | 冷启动更慢、成本更高、运维更接近中心 |

选择顺序：**能用配置/规则解决的，不要写函数；能写函数的，不要上容器。**

## 四条硬约束，决定了 “什么能放边缘”

| 约束 | 具体限制 | 越界的后果 |
|---|---|---|
| **无状态** | 不保证本地磁盘/内存持久化，实例随时换 | 把会话放边缘 → 用户随机掉线 |
| **时限** | 单次执行有 CPU/墙钟上限（常见几十毫秒–几秒） | 重计算被中断，返回 5xx |
| **存储小** | KV 有大小与读写频率限制 | 当数据库用 → 延迟飙升、写入丢失 |
| **一致性弱** | 配置与 KV 是最终一致（秒级传播） | 用边缘做过期判断 → 放行了已封禁用户 |

一条判据：**这段逻辑在 “不知道其他节点发生了什么” 的前提下，还能得出正确结论吗？** 不能，就别放边缘。

## 适合 / 不适合

| 适合（毫秒级、无状态、读多） | 不适合（有状态、重计算、强一致） |
|---|---|
| URL 重写、A/B 分流、灰度 | 订单创建、库存扣减 |
| JWT/签名校验、bot 名单 | 复杂风控（需要全量特征） |
| 图片/视频的缩放裁剪 | 视频转码（CPU 与时长都不够） |
| 边缘 SSR / 静态拼装 | 依赖数据库事务的渲染 |
| 地理位置路由（按国家/城市） | 需要精确全局计数（限购、防刷） |

## 一致性与运维：两个被低估的成本

| 问题 | 现实 | 应对 |
|---|---|---|
| 配置传播延迟 | 改一条规则，全球节点几秒–几分钟才一致 | 关键规则要有版本号，客户端可回退 |
| 调试困难 | 无法 SSH，日志分散在几百个节点 | 依赖 trace_id + 采样日志 + 本地模拟器 |
| 部署风险 | 一次错误规则影响全球 | 先灰度 1% 节点，再全量；保留一键回滚 |
| 计费复杂 | 按请求/CPU 时间/流量组合计费 | 先算 “每万次请求成本”，再对比中心处理 |

## 一个典型的组合：在边缘做 “鉴权 + 分流”，在中心做 “业务”

```
用户 → 边缘（验签、判灰度、重写 URL、命中缓存则直接返回）
          ├─ 命中：直接响应（不经过中心）
          └─ 未命中：带身份头回源 → 中心做业务与数据
```

这样边缘只承担 “几毫秒的判定”，不碰数据；中心仍是唯一真相。**边缘负责快，中心负责对。**

## 边缘 vs 回源的延迟/成本模型

> 🔑 **把下沉决策写成两个式子**：延迟 = 本地路径 × 本地完成比例 + 回源路径 × 回源比例；成本 = 边缘增量费 − 省下的中心计算 − 省下的回源字节。算完会得到三个判据：**临界响应 35.4 KiB、p99 的 1% 拐点、前置拦截的拦截率阈值**。

**参数先定死**（示例单价，照自己账单替换）：

| 参数 | 取值 | 说明 |
|---|---|---|
| 峰值 QPS | 1 万 | 259.2 亿请求/月 |
| 边缘请求费 | 3.0 元/百万 | 边缘函数按请求计费 |
| 边缘 CPU | 0.175 元/百万 | 执行 4ms × 128MB 的 CPU 计价 |
| 中心处理摊销 | 1.0 元/百万 | 服务器、DB、内网带宽摊到每请求 |
| 回源流量 | 0.06 元/GB | 边缘 → 中心 |
| RTT | 客户端↔边缘 10ms，边缘↔中心 40ms | 同城 / 跨区各取一档 |
| 处理时间 | 中心 25ms，边缘 4ms | 只算 CPU 执行段 |
| 冷启动 | 0.2% 请求 +200ms | 低频路径首次执行 |

**四条口径**：① `s` = 本地完成比例（下沉命中率），回源比例 = 1−s；② 不走边缘的基线延迟 = 10+40+25 = 75ms；③ 走边缘后，本地 = 10+4ms，回源 = 10+4+40+25 = 79ms（比基线多一跳边缘执行）；④ 回源字节成本 = 响应字节 × 0.06 元/GB，20KB 响应 = 1.20 元/百万请求。

```go
// 边缘下沉 vs 全量回源：延迟 / 回源带宽 / 月成本模型（示例单价，按自身账单替换）
// 口径：1 万 QPS = 259.2 亿请求/月；成本单位先算“元/百万请求”，再乘 2.592 得“万元/月”。
package main

import "fmt"

const (
	qps       = 10000.0
	reqMonth  = qps * 86400 * 30 // 259.2 亿
	edgeFee   = 3.0              // 元/百万请求：边缘函数请求费
	edgeCPU   = 0.175            // 元/百万请求：4ms × 128MB（CPU 计价）
	centerCPU = 1.0              // 元/百万请求：中心处理摊销（示例）
	originGB  = 0.06             // 元/GB：边缘→中心回源流量
	rttCE     = 10.0             // ms：客户端↔边缘 RTT
	edgeExec  = 4.0              // ms：边缘执行
	rttEO     = 40.0             // ms：边缘↔中心 RTT
	originPrc = 25.0             // ms：中心处理
	coldRate  = 0.002            // 冷启动比例
	coldMs    = 200.0            // 冷启动额外延迟
)

// 每百万请求的回源字节成本（元）
func bytesCostPerM(sizeB float64) float64 { return sizeB * 1e6 / 1e9 * originGB }

// 本地完成比例 s、响应大小 sizeB 时的三类成本（元/百万请求）
func costs(s, sizeB float64) (edge, center, origin float64) {
	edge = s * (edgeFee + edgeCPU)
	center = (1 - s) * centerCPU
	origin = (1 - s) * bytesCostPerM(sizeB)
	return
}

// 平均延迟：s 走本地（含冷启动），其余走回源；s=0 的基线不走边缘=75ms
func avgLatency(s float64) float64 {
	local := rttCE + edgeExec + coldRate*coldMs
	viaEdgeFallback := rttCE + edgeExec + rttEO + originPrc
	return s*local + (1-s)*viaEdgeFallback
}

func p99(s float64) float64 {
	if 1-s > 0.01 {
		return rttCE + edgeExec + rttEO + originPrc // 回源比例 >1%，p99 落在回源路径
	}
	return rttCE + edgeExec
}

func main() {
	fmt.Println("== 1. 延迟与回源带宽（响应 20KB，边缘执行 4ms，回源 RTT 40ms） ==")
	fmt.Println("本地完成 | 平均延迟ms | p99 ms | 回源带宽TB/月")
	base := rttCE + rttEO + originPrc
	fmt.Printf("0%%（不走边缘） | %.1f | %.0f | %.1f\n", base, base, reqMonth*20000/1e12)
	for _, s := range []float64{0.3, 0.5, 0.8, 0.95, 1.0} {
		fmt.Printf("%.0f%% | %.1f | %.0f | %.1f\n", s*100, avgLatency(s), p99(s), (1-s)*reqMonth*20000/1e12)
	}

	fmt.Println("\n== 2. 月成本（万元；20KB 小响应 vs 200KB 大响应） ==")
	fmt.Println("响应 | 本地完成 | 边缘费 | 中心费 | 回源费 | 月合计 | 对比基线")
	for _, size := range []float64{20000, 200000} {
		bEdge, bCenter, bOrigin := costs(0, size)
		baseline := (bEdge + bCenter + bOrigin) * reqMonth / 1e10
		for _, s := range []float64{0, 0.5, 0.8, 1.0} {
			e, c, o := costs(s, size)
			total := (e + c + o) * reqMonth / 1e10
			tag := "基线"
			if s > 0 {
				tag = fmt.Sprintf("%+.2f", total-baseline)
			}
			fmt.Printf("%.0fKB | %.0f%% | %.2f | %.2f | %.2f | %.2f | %s\n",
				size/1000, s*100, e, c, o, total, tag)
		}
	}

	fmt.Println("\n== 3. 临界响应大小：下沉何时开始省带宽 ==")
	thr := (edgeFee + edgeCPU - centerCPU) / (1e6 / 1e9 * originGB)
	fmt.Printf("临界值 = (边缘费+CPU-中心计算) / 单位字节回源成本 = %.0f B ≈ %.1f KiB\n", thr, thr/1024)
	fmt.Println("响应大小 | 回源字节成本元/百万 | 下沉增量元/百万 | 结论")
	for _, size := range []float64{1000, 20000, 64000, 200000, 1048576} {
		bc := bytesCostPerM(size)
		delta := edgeFee + edgeCPU - centerCPU - bc
		verdict := "省钱"
		if delta > 0 {
			verdict = "更贵（买延迟）"
		}
		fmt.Printf("%.0fKB | %.2f | %+.2f | %s\n", size/1000, bc, delta, verdict)
	}

	fmt.Println("\n== 4. 只做前置拦截（不省中心计算）：拦截率阈值 ==")
	fmt.Println("响应大小 | 回源字节成本元/百万 | 需要拦掉的比例")
	for _, size := range []float64{1000, 20000, 200000} {
		bc := bytesCostPerM(size)
		r := (edgeFee + edgeCPU) / (centerCPU + bc)
		fmt.Printf("%.0fKB | %.2f | %.1f%%\n", size/1000, bc, r*100)
	}
}
```

**读法一：延迟不是「下沉就降」。** 延迟与回源带宽表里 s=30% 时平均延迟 59.6ms，但 **p99 = 79ms**，比不走边缘的 75ms 还高 4ms——p99 由「回源那部分请求」决定，只要回源比例 >1%，p99 就落在回源路径上。所以「下沉后 p99 没改善」不是错觉：要么把 s 做到 99% 以上（能力覆盖与数据新鲜度都够），要么别指望 p99。冷启动 0.2% 让平均多 0.4ms、p99.9 抬到 214ms。

**读法二：小响应下沉是买延迟，不是省钱。** 20KB 全下沉 8.23 万元/月，比基线 5.70 万元/月**贵 2.53 万**；200KB 全下沉 8.23 万元/月，比基线 33.70 万元/月**省 25.47 万**。原因在成本结构：20KB 的回源费只有 1.20 元/百万，而边缘费 3.17 元/百万 > 中心 1.0 + 回源 1.20 = 2.20 元/百万；200KB 的回源费涨到 12.00 元/百万，结论反转。

**读法三：临界响应大小 35.4 KiB。** 解 `3.175 = 1.0 + size × 6e-5` 得 36,250 B。响应小于 35.4 KiB，下沉更贵；大于它，下沉才开始省：64KB 省 1.67 元/百万，200KB 省 9.82，1MB 省 60.74。把固定人力算进去临界还会抬高：2 人年运维 ≈ 86 万元/年 ≈ 3.3 万元/月，折 1.273 元/百万分摊在 259.2 亿请求上，临界变成 `(2.175+1.273)/6e-5 ≈ 57,467 B ≈ 56 KiB`。**临界值不是一个物理常数，它随团队人数、单价、月请求量一起动**。

**读法四：前置拦截只看拦截率。** 若边缘只做鉴权、请求仍要回源，那么每个请求白付 3.17 元/百万并多 4ms；要抵消，必须挡掉足够比例的请求。20KB 响应需要拦掉 **144.3%**（不可能），1KB 需要 299.5%——所以「小响应 + 边缘鉴权」纯属成本；200KB 响应需要拦掉 **24.4%**，拦掉四分之一才划算。边缘鉴权的价值在挡攻击、降中心负载，不在省钱。

**什么负载适合下沉**（按上面算出的判据归档）：

| 负载 | 单请求回源字节 | 本地完成比例 | 平均延迟 | 增量成本（按该比例，元/百万） | 结论 |
|---|---|---|---|---|---|
| URL 重写 / 灰度分流 | <1KB | 100% | 75 → 14.4ms | +2.11 | 买延迟与卸载，不省钱 |
| JWT 验签 / 租户路由 | 1KB | 100% | 75 → 14.4ms | +2.11 | 适合做安全前置；别当省钱手段 |
| 静态小文件 | 20KB | ~95% | 75 → 17.6ms | +0.93 | 先缓存（[9.1 边缘缓存原理](9.1-边缘缓存原理.md)），别用函数替代缓存 |
| JSON 聚合 / 边缘 SSR | 200KB | ~90% | 75 → 20.9ms | −8.84 | 既快又省，优先候选 |
| 图片缩放 / 裁剪 | 200KB 原图 | 100% | 75 → 14.4ms | 省（按输出图摊薄） | 适合，但要盯 CPU 时限 |
| 实时风控（全量特征） | 200KB | 0% | 75 → 79ms | +3.17 | 不适合：必须回源，多一跳 |
| 订单创建 / 库存扣减 | — | 0% | 75 → 79ms | +3.17 | 不适合：强一致（见 [67.6 秒杀与抢购](../../L4-组件与技术/67-交易与账务/67.6-秒杀与抢购.md)） |
| 视频转码 | >1MB | 0% | 超时 | — | 不适合：超 CPU/墙钟上限 |

**两张边界**：① 如果下沉逻辑虽然无状态、但每个请求仍要回源取数（例如查中心库存），它既拿不到「省中心计算」也拿不到「省回源字节」，只剩多一跳——这类逻辑应该留在中心，或先做缓存/连接复用；② 能靠缓存解决的部分不要交给边缘函数：缓存命中率提升 1 个百分点省的是回源流量（[9.2 回源策略与回源率](9.2-回源策略与回源率.md)），而边缘函数是给「不能缓存、必须算」的请求用的。边缘函数与中心 FaaS 的取舍见 [33.3 Serverless / FaaS](../../L2-架构风格/33-部署形态/33.3-Serverless与FaaS.md)。

## 反模式

| 反模式 | 后果 |
|---|---|
| 在边缘做完整业务逻辑 | 一致性、调试、部署三重成本，且难以回滚 |
| 把边缘 KV 当数据库 | 写入受限、延迟高、数据丢失 |
| 边缘做重计算（转码、加密大包） | 超时被中断，成本反而更高 |
| 忽略冷启动 | 低频路径首次请求慢几百毫秒 |
| 一套规则全量直推 | 一次错误规则全球生效 |
| 不做本地模拟 | 只能上线后才发现语法/权限错误 |

## 三条铁律

> 🔑 **边缘只做 “无状态、毫秒级、读多写少” 的判定**；有状态与强一致的逻辑留在中心。

> 🔑 **配置即代码**：版本化、灰度、一键回滚，缺一不可。

> 🔑 **先算成本再上边缘**：请求数 × 单价 + 回源流量，往往不比中心便宜。

## 自检

**Q1** 团队想把 “库存扣减” 放到边缘函数，为什么不可行？

▸ 答案：因为库存扣减需要**强一致的读-改-写**与全局计数，而边缘是无状态、最终一致、且各节点互不可见。放在边缘会出现超卖：两个节点各自看到 “还有 1 件”，各扣一次。正确做法是边缘只做 “预校验/限流/排队”，真正的扣减回到中心（见 [67.6 秒杀与抢购 (库存 / 限购 / 防刷 / 削峰)](../../L4-组件与技术/67-交易与账务/67.6-秒杀与抢购.md)）。

**Q2** 为什么 “JWT 校验” 适合放边缘，而 “封禁名单” 要谨慎？

▸ 答案：JWT 校验是**无状态的本地计算**（验签 + 过期时间），边缘完全能独立完成，收益是把无效请求挡在边缘。封禁名单依赖 “最新状态”，而边缘 KV 是最终一致的——刚封禁的用户可能在几秒内仍被放行。若必须放边缘，要接受这个窗口，或在中心再做一次校验。

**Q3** 边缘函数常见的时间限制会导致什么设计变化？

▸ 答案：**把 “长任务” 拆成 “短判定 + 异步”**：边缘只做 “要不要处理、转发到哪”，重活交给中心或异步队列。同时要设超时与降级（超时就直接回源，而不是返回错误），否则边缘的抖动会变成用户的 5xx。

**Q4** 怎么验证一条边缘规则是安全的？

▸ 答案：四步：① **本地模拟**（多数厂商提供 CLI/模拟器）跑通语法与匹配；② **灰度 1% 节点或 1% 流量**，观察错误率与回源率；③ 准备好 **一键回滚**（规则版本化）；④ 观察 **配置传播** 是否完成（不同地域抽样验证）。跳过第 ② 步的团队，通常会在第一次全量时学到同一个教训。

**Q5** 什么情况下 “边缘计算” 反而更贵？

▸ 答案：三种：① **请求量大但命中率低**，每次都要回源，边缘只增加一跳；② **逻辑重**（CPU 时间超限被中断重试），单位成本高于中心；③ **运维成本**（调试、灰度、回滚、观测）没被计入。判断方法：算 “每万次请求的边缘费用 + 回源流量 + 人力”，与 “中心扩容成本” 对比，而不是只看单价表。
