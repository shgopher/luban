# 8.13 入口容量工程

## 一句话

> 入口容量不是“买一台更大的负载均衡”，而是把**包处理、连接状态、流量分配**三件事分别拆开：L4 用 DR/NAT 省掉回包，DPDK/RSS 把包处理从内核搬到用户态，ECMP/多机把单机上限变成集群上限；算容量时先算三笔账，再用单机上限否决“一台大机器”。

## 入口的三笔账

LB 不是“无成本的转发器”，它有三笔账：

| 账 | 量级 | 算例 |
|---|---|---|
| **包速率** | 10 Gbps 线速、64B 小包 = **14.88 Mpps**（84B 线上：64 + 8 前导 + 12 帧间隙） | 纯转发（DPDK/XDP）每核 5–10 Mpps；走内核协议栈 + conntrack 每核 1–2 Mpps |
| **连接状态** | conntrack 条目约 300B + 每连接 socket 缓冲约 4KB | 100 万并发连接 ≈ **4.4 GB** 内存 |
| **请求处理（L7）** | 每请求 CPU 预算 | 10 万 QPS / 8 核 = 每核 12500 rps → 每请求 **80µs**（含 TLS 记录加解密与 HTTP 解析） |

三笔账里先打满的那一笔，才是入口的真实上限：小包场景先撞 PPS，长连接场景先撞内存/fd，HTTPS 场景先撞 L7 CPU。**不要用一个“QPS 上限”概括三种完全不同的瓶颈。**

## 入口故障先看症状，不要先看 CPU

| 症状 | 先查 | 判据 |
|---|---|---|
| CPU/内存都低，但新连接超时 | `ulimit -n`、`ss -lnt` 的 Recv-Q、LB 的匹配开销 | 资源空闲却建连失败，通常是 fd/accept 队列/每包匹配打满，不是算力不够 |
| 已建立的连接正常，新连接失败 | listen backlog、`TcpExtListenOverflows`、SYN queue | 增量失败、存量正常 = 入口队列问题 |
| 偶发 502/连接被重置 | 代理 `idle timeout` 与上游 keepalive 是否反了 | 代理收得比上游晚，就会拿到一批死连接 |
| 全部超时、内核日志 `nf_conntrack: table full` | `nf_conntrack_count/max` | NAT 表打满，内核直接丢包 |

> 📌 一个真实症状（书里 p83 的一手案例）：16 核 32G、CPU 8%、内存 6%，开团 3 分钟约 4000 用户却大量连不上；`ulimit -n` 默认 1024，调到 65535 后仍只到 5–6K 连接——因为 Apache 把一整颗核花在“数据包 ↔ 进程”匹配上。加一层 Nginx 后，Nginx 活跃连接只有 1K。**结论：入口先看连接与队列，再看 CPU。**

```bash
# conntrack 水位与上限：打满的表现是内核日志 "nf_conntrack: table full, dropping packet"
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max     # 默认值常见在 6.5 万–26 万之间，随发行版/内存而变
conntrack -C                                    # 需要 conntrack-tools

# 四层转发与端口层面的观测
ss -s                                           # 各状态连接数汇总
nstat -az TcpExtListenOverflows TcpExtTCPReqQFullDrop
```

## LB 自己怎么高可用

按故障切换时间排序：

| 方案 | 切换时间 | 特点 |
|---|---|---|
| 主备 + VRRP（keepalived） | 秒级（3× advert） | 备机平时闲置，容量浪费一半 |
| ECMP + 多台同时工作 | 路由收敛秒级 | 需要一致性哈希或连接同步，否则连接断 |
| anycast（BGP 宣告同一 IP） | 秒级，但**断连接** | 天然就近接入，适合无状态入口 |
| DNS / GSLB | TTL 级（分钟级） | 客户端缓存不遵守 TTL，切换最慢 |

> ⚠️ 三层故障的恢复时间不同：路由收敛是分钟级（公网路由表更新慢），交换机/ECMP 是秒级，Keepalived 是秒级。做容量规划时要把“切换窗口内剩余节点能否接住”算进去，不能只看稳态容量。

## 一次包推演：NAT 改 L3/L4，DR 改 L2

把“四层只改包头”拆成逐跳动作，才知道每一步谁在改什么：

```
客户端 123.123.123.123:52387
   │  目的 IP 110.242.68.3:443
   ▼
公网网关（NAT）
   │  DNAT：目的 IP → VIP 10.0.0.100:443，源 IP/端口不变
   ▼
LVS（DR 模式）
   │  只改目的 MAC → RS 10.0.0.1 的 MAC；目的 IP 仍是 VIP 10.0.0.100
   ▼
RS 10.0.0.1
   │  发现目的 IP 是自己 lo 上的 VIP，接受；回包源 IP 是 VIP
   ▼
公网网关（NAT 回程）
   │  SNAT：源 IP 改回 110.242.68.3:443
   ▼
客户端
```

| 设备 | 改什么 | 不改什么 | 代价 |
|---|---|---|---|
| 公网网关（NAT） | 源/目的 IP、端口，并维护五元组映射 | 应用数据 | 回包也走网关，带宽翻倍 |
| LVS（DR） | 目的 MAC | IP、端口、TCP 头 | 必须同二层；RS 要抑制 VIP 的 ARP |
| RS | 无（正常回包） | — | 回包直接回客户端，不经过 LVS |

> ⚠️ 两个常见误解：① **LVS 不和客户端做三次握手**，它只看包、改 MAC 就转发，所以“LVS 的连接数”与“客户端的连接数”不是一回事；② **DR 不是一级入口**——书里这张图的 VIP 是私网地址，前面还有一层做“公网 IP→VIP”的 NAT 网关。自建也可以让 LVS 直接持公网 VIP（配合 ECMP/anycast），那是另一种拓扑，回包路径也不同。

## 从 20G 到 200G：把“包处理”和“流量分配”继续拆

单机 LVS 的 NAT 模式大约 20G 就到 Linux 网络栈的顶（书里口径，未复现）；想上 200G，不是换一台更大的机器：

| 技术 | 解决哪一段 | 代价/边界 |
|---|---|---|
| **DPDK/DPVS** | 绕过内核协议栈，用户态轮询收包；大页 + CPU 亲和 + NUMA | 独占核与大页，空转也 100% CPU；核少时得不偿失（见 [11.9](../11-操作系统与内核基础/11.9-中断-软中断与CPU时间去向.md)） |
| **RSS/FDIR** | 同一五元组固定到同一 CPU，把 conntrack 分片，解除全局锁 | 需要网卡多队列与流表；配错会让同一连接跨核乱跑 |
| **ECMP/OSPF** | 多台 LVS 同时工作，路由层做等价多路径 | 路由收敛秒级；要一致哈希/连接同步，否则断连接 |
| **NPU 卸载** | checksum、TSO、VxLAN 剥离/插入 | 依赖网卡能力；VxLAN offload 是云 VPC 的常态 |
| **Keepalived/VRRP** | 同城三节点主备，VIP 漂移 | 秒级切换；备机闲置一半容量 |

> 🏭 同样的思路，硬件厂商早就做了：H3C Comware V7 把网络管理进程放在用户态，用单播/组播/热迁移的 IPC、多进程主备选举、进程级内存热备来换可靠性与性能——这和 DPDK 把转发搬出内核、Keepalived 做 VRRP 主备、ECMP 做多活，是同一组取舍的三种实现。差别只是“谁写软件”，不是“要不要软件”。

一条可复算的容量链（书里 p110–115，均为作者/厂商口径）：单 LVS NAT ≈ 20G → DPVS 小包实测约 5 倍，保守取 2.5 倍 ≈ 50G/网卡 → 双网卡 50G×2 → 两台入口 ×2 = **200G**；四台 LVS（2 主 2 备）+ 2 路由 + 2 交换机 ≈ **18 万**，对比 F5 100 万设备只有 40G L4 / 18G L7。**真正值钱的不是便宜，是“可编程”**：路由、交换机、LVS 都能被软件编排，才能给上层做多租户和自定义调度。

### 一个可复算的容量模型

不用先买 DPDK 机器，先用下面的模型判断“单机够不够、要几台、BOM 量级”：

```python
#!/usr/bin/env python3
"""入口容量模型：PPS / 连接 / L7 QPS 三笔账，取最紧的那一项。"""

# 单机能力（按你的实测替换；下面是保守量级）
CORE_PPS_KERNEL = 1_500_000      # 走内核 + conntrack，每核 1–2 Mpps
CORE_PPS_DPDK = 6_000_000        # DPDK/XDP 纯转发，每核 5–10 Mpps
L7_QPS_PER_CORE = 12_500         # 10 万 QPS / 8 核，含 TLS 与 HTTP 解析
CONN_PER_GB = 250_000            # 100 万连接 ≈ 4.4GB，按 4KB/连接估

def nodes(pps, conns, l7_qps, cores=16, mem_gb=64, dpdk=False):
    by_pps = pps / (CORE_PPS_DPDK if dpdk else CORE_PPS_KERNEL) / cores
    by_conn = conns / (CONN_PER_GB * mem_gb)
    by_l7 = l7_qps / (L7_QPS_PER_CORE * cores)
    return max(by_pps, by_conn, by_l7), {"pps": by_pps, "conn": by_conn, "l7": by_l7}

for name, args in {
    "小包纯转发 10Mpps / 50 万连接": (10_000_000, 500_000, 0),
    "HTTPS 10 万 QPS / 100 万连接": (2_000_000, 1_000_000, 100_000),
    "DPDK 40Mpps / 200 万连接": (40_000_000, 2_000_000, 0),
}.items():
    n, detail = nodes(*args, dpdk=("DPDK" in name))
    print(f"{name}: {n:.1f} 台  {detail}")
```

读法：三个比值里最大的那个决定机器数；如果 `conn` 先到 1，说明该加内存/拆长连接，而不是加 CPU。真实采购前把四个常量换成你的实测值——**这个脚本只替代“拍脑袋”，不替代压测**。

## 什么时候别自建

- 入口 < 1Gbps、团队没有网络运维、只需要 TLS 卸载：直接用云 NLB/ALB 更便宜。
- DPDK 方案要先回答三个问题：有没有独占核、能不能接受空转、谁来维护流表。
- Keepalived 主备要定期演练切换；不演练的“高可用”只是两台机器。

## 反模式

| 反模式 | 后果 |
|---|---|
| 入口只看 CPU 水位扩容 | CPU 低但 fd/accept/conntrack 先打满，加机器不解决 |
| 核数少时硬上 DPDK | 独占核 + 空转，挤掉业务 CPU，吞吐反而降 |
| 200G 只堆网卡不拆交换机 | 单机 PCIe/内存带宽与 HA 都不成立，故障域没变小 |
| 主备 Keepalived 从不演练 | 真故障时 VIP 抢不到/脑裂，备机等于没有 |
| 把厂商 BOM 当报价 | 18 万是书里 2023 年的量级，不含运维、带宽、机房与备件 |
| 用“QPS 上限”概括所有入口 | 小包撞 PPS、长连接撞内存/fd、HTTPS 撞 L7 CPU，瓶颈不是同一个 |

## 自检

**Q1** 入口 CPU 8%、内存 6%，监控一切正常，但用户大量“连不上”。你的排查顺序是什么？

▸ 答案：先排除“算力不足”，按入口链路查四件事：① `ulimit -n` 与进程 fd 数（默认 1024 是经典坑）；② `ss -lnt` 的 Recv-Q 与 `TcpExtListenOverflows`（accept 队列满）；③ LB 的连接表/conntrack 水位；④ 七层代理是否把一整颗核花在“包↔线程”匹配上（Apache prefork 的经典症状）。这四样都不看就扩 CPU，通常无效。

**Q2** 单机 LVS 20G，想做到 200G，为什么不是“插四块 100G 网卡”？

▸ 答案：因为流量不会自动四等分，且单机四网卡仍是一个故障域。可行的是三层拆分：DNS/ECMP 把流量分给多台路由/交换机，LVS 用双网卡双口接两台交换机（50G×2），再用 Keepalived 做 2 主 2 备；容量是“入口数 × 单机网卡数 × 单口线速”，不是“网卡数 × 线速”。同时要接受：路由收敛分钟级、交换机秒级、Keepalived 秒级，三层故障恢复时间不同。

**Q3** 什么时候不该上 DPDK？

▸ 答案：核数少（没有独占核）、入口带宽不高（<10G）、团队没有用户态网络运维能力时都不该上。DPDK 的收益来自“绕过内核协议栈 + 轮询”，代价是独占核、大页、空转 100% CPU、自己维护流表与网卡驱动；核少时它会挤掉业务 CPU，吞吐反而下降。先用 RSS/多队列/内核参数把单机榨到 20G，再考虑 DPDK。

**Q4** 书里的 200G 集群 18 万 BOM，能直接当采购报价吗？

▸ 答案：不能。18 万是 2023 年书里的量级（路由 1 万×2 + 交换机 2 万×2 + LVS 3 万×4），不含带宽、机房、备件、运维与软件许可；而且 200G 的实际上限取决于包长、会话数、网卡型号与路由收敛。正确用法是拿它做“自建 vs 买 F5”的数量级对比，再按当前报价重算。

**Q5** 为什么 Keepalived 主备的“容量”只有单机的一半，却仍然常被用？

▸ 答案：因为它买的是“秒级切换”而不是“容量”。备机平时不接流量，资源利用率 50%，但故障时能在秒级接管 VIP，避免分钟级停机；对入口这种“挂了全站不可用”的位置，这笔钱通常值。要提升容量利用率，就上 ECMP/多活（多台同时工作），代价是一致哈希/连接同步与路由收敛；两者不是替代关系，常组合使用。
