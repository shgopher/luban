# 8.19 Overlay 与隧道：GRE、VXLAN、VPN

## 一句话

> 租户数一旦超过 4096，改协议是死路、加 VLAN 也是死路，唯一活路是**在原包外面再套一层头**——这叫 Overlay；GRE、VXLAN、IPsec、MPLS VPN 只是同一套「乘客 / 隧道 / 承载」骨架的四种外壳。

## VLAN 的天花板：4096 个，为什么不能改协议

VLAN 用二层头里一个 **12 位** 字段标识广播域，上限 **4096**。TAG 怎么打、交换机怎么按 VLAN 转发见 [8.14 二层](8.14-二层-ARP-交换机与VLAN.md)；这里只回答一件事：**为什么扩容不能靠改这个字段**。

> 「VLAN 只有 12 位，共 4096 个。当时设计的时候，看起来是够了，但是现在绝对不够用，怎么办呢？」

| 扩容思路 | 可行性 | 原因 |
|---|---|---|
| 改 VLAN 协议，把 12 位字段加长 | **不可行** | 「当这个协议形成一定标准后，千千万万设备上跑的程序都要按这个规则来。」改一个字段要通知全网设备 |
| 为每个租户单独建网卡 + 独立网桥 | **不可行** | 没有虚拟交换机时的老做法：租户一多，网卡与网桥数量爆炸，配置极不灵活 |
| **在原包外面加一层新头，装更宽的租户 ID** | **可行** | 中间设备只按外层转发、不必认识内层；封解封装只在两端做 |

> 🔑 结论是**扩展，不是修改**：在原包格式上扩一个头装区分租户的 ID，外层尽量与传统协议保持一致以保持兼容。

## 隧道的通用骨架：乘客、隧道、承载

先把两个词钉死：**底层物理网络叫 Underlay**（真实设备、真实链路、真实路由，只负责把外层包从一台机器送到另一台），**基于它虚拟化出来的网络叫 Overlay**（谁和谁同网段、租户怎么隔离、广播域多大），代表技术 GRE 与 VXLAN。物理侧怎么搭见 [8.18 数据中心网络](8.18-数据中心网络-从三层到叶脊.md)。

| 角色 | 管什么 | 琼州海峡类比 | 本节例子 |
|---|---|---|---|
| **乘客协议** | 两端真正想说的语言，端到端一个字节都不改 | 广州的「红灯停绿灯行」 | 内层 IP（VM 发出来的原始包） |
| **隧道协议** | 给乘客打标识、排队、封装，让承载层整块搬运 | 车开上轮渡、关进船舱按规则排列 | GRE 头 / VXLAN 头 / ESP 头 |
| **承载协议** | 在公网上真正跑的那一层 | 海上按航道走、看灯塔 | 外层 IP + 外层 MAC |

自驾过琼州海峡上轮渡这个类比最贴切：**车上高速的规则在海上失效，船按航道走，到岸开舱把车开出来。** 两端私网协议照旧，中间公网只认外层隧道；出隧道逐层摘头，内层包原样交出来。

> 🔑 **内层 IP 头不变，变的是外层**。这正是隧道能骗过两端主机的原因：它以为自己在直连，其实中间换了三套规矩。

## GRE：最简单，也最容易踩三个坑

GRE 是 **IP-over-IP** 隧道：IP 包封进 GRE 包、外面再加一个 IP 头，一端封装、通路传输、另一端解封装，逻辑上是一条虚拟点对点专线。封解封装落在路由器或有路由功能的 Linux 机器上。

GRE 头**前 32 位必有**（开头 4 位是标识位，说明后面有没有可选项），**后面可选**；关键是其中 **32 位 key 字段**，通常放区分用户的 Tunnel ID。NVGRE 把网络 ID 做成 **24 位**。

> 💡 「32 位，够任何云平台喝一壶的了！」——单看标识空间 GRE 完全够用，它的问题不在位数，在拓扑与可解析性。

| 维度 | 事实 | 后果 |
|---|---|---|
| 能力 | IP-over-IP 点对点接起两个网络；key 32 位放 Tunnel ID | 实现最简单，区分租户够用，设备开销小 |
| 限制① 隧道数量 | 点对点：每**两个**网络之间各建一条 | 网络一多，隧道数呈**指数增长**，配置与状态一起爆炸 |
| 限制② 组播 | **不支持组播** | 一台虚机发广播帧会被广播到所有与它有隧道的节点——浪费带宽，还漏隔离 |
| 限制③ 可解析性 | 很多防火墙与三层设备**无法解析 GRE** | 做不了过滤与负载均衡，安全策略只能绕着走 |

## VXLAN：把二层塞进 UDP

GRE 是**三层外套三层**；VXLAN 换了个位置——从**二层外面**套一层新头，再封 UDP、IP、外层 MAC。相比 GRE，它多出来的正是 **24 位 VNI** 与 **UDP 承载**。

```text
[外层 MAC][外层 IP][UDP][VXLAN 头：VNI 24 位][内层 MAC][内层 IP][内层 TCP/UDP][数据]
   ← 承载协议，公网逐跳改写 →     ← 隧道协议 →      ←——— 乘客协议，端到端不变 ———→
```

- **虚拟机发出来的整个以太网帧当载荷**，所以广播/组播帧也能被搬过公网——这是它比 GRE 强的根本原因。
- **VNI 24 位**：标识租户的虚拟网络；24 位的总量足够云平台用，具体上界不必背。
- **UDP 承载**：外层再封 UDP，端口号按 IANA 标准取 4789（下面的命令用它，仅为可执行）。

**VTEP** 是封装端点——「VTEP 相当于虚拟机网络的管家」：每台物理机可以有一个，每台 VM 启动都要向它注册，跨 VTEP 通信全由它代理封解封装。它靠**组播**找到对方，五步：

1. VTEP 启动时用 **IGMP** 加入一个组播组——像加入一个微信群。
2. VM1 不知道 VM2 的 MAC，发 **ARP 广播**。
3. VTEP1 把这个 ARP 封进 VXLAN 发到组播组——等于在群里 **@all** 一下。
4. 管着 VM2 的 VTEP2 收到，在自己本地广播，VM2 给出应答。
5. 应答走**单播**回源 VTEP1；一来一回双方各自学到「对方归谁管」，之后**全走单播**。

```bash
# 环境：Linux 宿主机（非 VM）、iproute2 带 vxlan 类型、root；4789 取 IANA 标准端口
sudo ip link add vxlan0 type vxlan id 101 dstport 4789 remote 172.17.10.10 dev eth0
sudo ip link set vxlan0 up
# 看 id（=VNI）与 remote；要让 VTEP 靠组播自动学 ARP，把 remote 换成 group <组播地址>
ip -d link show vxlan0
# 看 FDB（谁归谁管）：容器内实测输出为 dst 172.17.10.10 ... self permanent；为空 = 没学到，跨机首包必丢
bridge fdb show dev vxlan0
```

> 🔑 判据只有一条：**fdb 里有没有 `dst <对端 VTEP IP>`**。有，隧道通了；没有，别查路由，先查 IGMP 入组与组播可达性。

### 云平台怎么落地：br0 管虚拟机，br1 管隧道

宿舍分家后原来的 br0 被一刀三断，做法是用隧道把几段 br0 连起来，让虚拟机看起来还在同一个 br0 上；**多出一个 br1** 是把「虚拟机互联」与「物理机互联」分成两层，中间怎么挖都行。此时 OVS 虚拟交换机就是封装端点，流表全放 br1：

按表分工：**Table 0** 入口分类（这包来自虚拟机还是来自隧道）；**Table 1** 分出向单播/多播；**Table 3** 入向把 **Tunnel ID 转成 VLAN ID**；**Table 10** 做 MAC 学习、结果存进 **Table 20**；**Table 20** 已知单播按 MAC 表转发；**Table 21** 广播与未知单播往隧道口泛洪。

> ⚠️ **每张表都要写默认 drop**。少写一条，匹配不上的包就被放行，前面所有隔离设计一起作废。匹配-动作模型本身见 [8.20 SDN 与网络 QoS](8.20-SDN与网络QoS.md)。

## VPN：公网、专线之外的第三条路

| 路线 | 代价 | 安全性 | 结论 |
|---|---|---|---|
| 公网直连 | 最便宜 | 明文，「隐私可能被别人偷窥」 | 不可取 |
| 专线 | 「这是土豪的做法，需要花很多钱」 | 高 | 只求性能且肯花钱才选 |
| **VPN** | 折中 | 「VPN 通过隧道技术在公众网络上仿真一条点到点的专线」 | 安全且预算有限时选它 |

IPsec 用四个机制凑齐三个安全目标（外加一个前置的密钥交换）：

| 目标 | 靠什么 | 关键细节 |
|---|---|---|
| 私密性 | **对称加密** | 隧道建好后要传大量数据，非对称加密扛不住这个量 |
| 密钥交换 | **IKE** | 对称密钥怎么安全地送到对端 |
| 完整性 | **hash 摘要** | 改一个字节，摘要就对不上 |
| 真实性 | **预共享密钥**对暗号，或**数字签名** | 签名用私钥签，对方拿证书里的公钥验 |

两阶段各自建一个 SA：

| 阶段 | 建什么 | 怎么建 |
|---|---|---|
| 阶段一 | **IKE SA** | 用 **DH** 算出对称密钥 K：约定公开的 p、q，各持私钥 a、b，交换公钥 A、B 后各自算出同一个 K。「对称密钥从来没有在通道上传输过，只传输了生成密钥的材料」 |
| 阶段二 | **IPsec SA** | 用 K 加密的通道下发随机密钥 M 来加密业务数据；M 有生存周期、定期重生。SA 里记 **SPI**、商定的算法、封装模式、生存周期 |

封装形态一句话：IP 头里的上层协议由 TCP 变成 ESP，ESP 头放 SPI 与序列号，其后全部加密，末尾指明内层协议，出隧道逐层解封装。

> ⚠️ **AH 只能摘要、不能加密；ESP 既能加密又能摘要**。目标是防窃听就必须 ESP——「以为上了 AH 就有加密」是最常见的误解。

> 💡 「完全基于软件的 IPsec VPN 可以保证私密性、完整性、真实性，简单便宜，但是性能稍微差一些」——差在每一跳都要查路由，见下一节。

## MPLS VPN：多租户的三件套

前史两句：IP 是**无连接**的，每个包逐跳查路由，效率差但抗断；ATM 是**面向连接**的，打标签走固定路径，效率高但一台路由器坏就全断。MPLS 取二者之长——在 IP 头外再加 MPLS 头打标签。标签头：**20 位标签 + 3 位实验 + 1 位栈底 + 8 位 TTL**。

| 角色 | 站在哪 | 干什么 |
|---|---|---|
| **CE** | 客户侧 | 客户的边缘设备，跑客户自己的路由 |
| **PE** | 运营商侧、贴近客户 | 接 CE，按客户区分路由，给每个客户一张独立路由表 |
| **P** | 运营商骨干 | 只做标签转发、不碰客户路由，客户地址重叠与它无关 |

LSR 有 **FIB** 与 **LFIB** 两张表；标签由 **LDP** 从下游往上游逐跳分发，串成 **LSP**。撑起多租户的是三件套：

| 件 | 解决什么 | 少了它会怎样 |
|---|---|---|
| **VRF** | PE 上给每个客户建一张独立路由表，像一台专属小路由器 | 地址重叠的客户互相污染路由 |
| **MP-BGP** | 在 32 位 IPv4 地址前加客户区分符成 VPN-IPv4，在 PE 之间传 | 传统 BGP 只选一条最优，另一个 VPN 的路由被丢掉 |
| **两层标签** | 外层走 PE 到 PE 的 LSP，内层在对端 PE 查 VRF 定去哪个 CE | 一层标签只能到对端 PE，不知道该交给哪个客户 |

> 🔑 排障顺序固定：**先看外层标签**（能不能到对端 PE），**再看内层标签**（能不能到 CE）。反过来查一定白忙。

## 选型表：什么时候用哪一种

| 技术 | 封装层次 | 租户标识 | 组播 | 过防火墙 | 典型场景 |
|---|---|---|---|---|---|
| **GRE** | 三层外套三层（IP-over-IP） | key **32 位** Tunnel ID | 不支持 | 差：很多防火墙与三层设备无法解析 | 点对点、租户少、两端设备能解 GRE |
| **VXLAN** | 二层外套二层，再封 UDP/IP/外层 MAC | VNI **24 位** | 支持：IGMP 入组，组播学 ARP | 好：外层是 UDP，普通设备能处理 | 多租户云平台、需要广播域的虚拟网络 |
| **IPsec** | 三层外套 ESP（隧道模式） | SA / SPI | 不涉及 | 纯软件，需两端都支持 | 多个数据中心互联，纯软件、便宜 |
| **MPLS VPN** | 标签交换（IP 头外 MPLS 头） | VRF + VPN-IPv4 区分符 | 不涉及 | 需运营商网络支持 | 运营商卖给企业的多站点专网 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 想改 VLAN 字段扩到 4096 以上 | 标准已成、千万设备，「是一项不可能的工程」 |
| 用 GRE 组网却不算隧道数 | 点对点导致隧道数指数增长，配置与状态一起爆炸 |
| 指望 GRE 承载广播/组播 | 它不支持组播，虚机广播被泛到所有有隧道的节点 |
| 在只能做五元组过滤的防火墙上放 GRE | 很多设备无法解析 GRE，过滤与负载均衡都做不了 |
| VXLAN 只配单播 remote、不做组播或控制面 | ARP 广播进不了隧道，跨 VTEP 第一个包必失败 |
| OVS 流表不写默认 drop | 匹配不上就放行，隔离形同虚设 |
| 在 VPN 里用非对称加密传业务数据 | 性能被非对称拖垮，它只该用来交换密钥 |
| 两个客户地址重叠还只用传统 BGP | 只选一条最优，另一个 VPN 的路由被丢掉 |

## 自检

**Q1** VLAN 只有 12 位不够用，为什么不能像 IP 那样「升一版」把字段扩长？

▸ 答案：**代价在存量设备，不在协议设计**。IPv6 能落地，是因为它作为一套新协议与 IPv4 并行部署，两端愿意谈才谈；VLAN 字段长在二层头里，中间每台交换机、网卡、虚拟化层都要同时认识新格式，任何一台不认识就把包当脏数据丢，而升级窗口里新旧设备必然共存。所以解法是**扩展**：不动原包，在外面加一个装更宽 ID 的新头。

**Q2** GRE 的 key 是 32 位、VXLAN 的 VNI 只有 24 位，为什么云平台反而选位数更小的 VXLAN？

▸ 答案：**位数不是瓶颈，拓扑与可解析性才是**。① GRE 点对点，每两个网络一条隧道，网络一多隧道数指数增长；VXLAN 靠组播定位，不需要两两建隧道。② GRE 不支持组播，虚机广播得逐隧道复制，既浪费又漏隔离；VXLAN 把整个二层帧封进 UDP，广播帧能过公网。③ 很多防火墙与三层设备无法解析 GRE，过滤与负载均衡做不了；VXLAN 外层是 UDP，普通设备能处理。代价是每包多一层封装开销。

**Q3** 一台 VTEP 收到本机虚机的 ARP 请求，怎么决定发给谁？为什么第二个包就不用再问了？

▸ 答案：**不知道就组播，知道就单播**。VTEP 启动时已 IGMP 入组；收到 ARP 后封进 VXLAN 发到组播组（群里 @all），管着目标的 VTEP 本地广播、拿到应答，应答**单播**回源 VTEP。一来一回两端各自把「某 MAC 归某 VTEP 管」记进 FDB，之后同 VNI 内直接单播封装。

**Q4** IPsec 阶段一已经算出 K 了，阶段二为什么还要再下发一个 M？

▸ 答案：**两把钥匙的用途与寿命不同**。K 保护的是 IKE 通道本身（密钥协商这条通道），不直接加密业务数据；阶段二在这条受保护的通道里下发业务密钥 M，由 M 加密真正的流量。M 带生存周期可定期重生，换业务密钥不必重跑阶段一——把「慢而重的身份与密钥协商」和「快而频繁的密钥轮换」解耦，这就是两阶段设计的全部意义。另外：K 从未在通道上传输，只传了生成它的材料。

**Q5** 一台物理机上的虚机要跨机通信，哪一段是 Overlay、哪一段是 Underlay？MTU 按哪层算？

▸ 答案：虚机到本机 VTEP 是**内层（Overlay）**，内层 IP 头全程不变；VTEP 封装后到对端 VTEP 是**外层（Underlay）**，走物理网络、逐跳改写外层 MAC；对端解封装后回到内层。MTU 必须按**最外层**算，多出来的头都占字节；具体减多少别凭记忆写，以集群 CNI 配置的 `mtu` 为准，见 [7.8 网络模型](../7-容器编排/7.8-网络模型.md)。
