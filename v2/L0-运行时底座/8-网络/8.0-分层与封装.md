# 8.0 分层与封装：一个包的一生

## 一句话

> 网络分层不是“各层各自开会”，而是**层层套娃**——上层整个被装进下层；所以线上跑过的每一个包都是完整的，二层设备里也带着 HTTP。

## 协议三要素：语法、语义、顺序

“协议”不是“约定”这么含糊的词。它拆开是三件事，缺一条就通不了：

| 要素 | 管什么 | 生活里的对应 | 网络里的例子 |
|---|---|---|---|
| **语法** | 内容要符合规则和格式 | 括号成对、结尾分号 | 以太网帧以目标 MAC 开头、以 CRC 结尾 |
| **语义** | 这段内容代表什么意义 | “减”只能对数字做 | IP 头第 9 字节写 6 表示 TCP、写 17 表示 UDP |
| **顺序** | 先干什么、后干什么 | 先签字再盖章 | 先三次握手，再发数据 |

> 🔑 只有通过网络协议，才能使一大片机器互相协作、共同完成一件事。

## 把包当成一段 Buffer：收包与发包各一条链

理解协议最省力的视角，不是背 OSI 七层，而是**把自己想象成一个处理网络包的程序**：有很多网口，从某个口拿进一段 Buffer，处理完从另一个口发出去。

收包：

1. `process_layer2(buffer)`：摘掉二层头，看目标 MAC 是不是自己；是就继续，不是就丢弃或转发。
2. `process_layer3(buffer)`：摘掉三层头，看目标 IP；不是自己就转发，是自己就上交。
3. 按 IP 头里的协议标识分派：`process_tcp(buffer)` 或 `process_udp(buffer)`。
4. 看四层头：这是发起、应答，还是普通数据。
5. **没有 `process_http(buffer)`**——四层头里有端口号，内核按端口把载荷交给监听该端口的应用。应用怎么解析，与内核无关。

发包是反过来的：

```text
send_tcp(buffer)     # 加 TCP 头，写源端口；目的端口由应用给（Web 一般是 80）
  └ send_layer3(buffer)   # 加 IP 头，写源 IP、目的 IP
      └ send_layer2(buffer)  # 加 MAC 头，写源 MAC、目的 MAC
```

最后一步有个容易被忽略的细节：目标 MAC **知道就直接填，不知道就先解析出来再填，“反正要填一个，不能空着”**。没有 MAC 地址，消息是发不出去的——这也是“我知道 IP 了为什么还要 MAC”的标准答案。

各层头部是逐层套上去的，典型长度如下（以太网 + IPv4 + TCP）：

| 层 | 头部典型长度 | 里面最关键的两个字段 |
|---|---|---|
| 以太网 MAC | 14 字节 | 目标 MAC、源 MAC |
| IP | 20 字节（不含选项） | 源 IP、目标 IP |
| TCP | 20 字节（不含选项） | 源端口、目的端口 |
| UDP | 8 字节 | 源端口、目的端口 |

> 💡 这就是“封装”的全部含义：**上层是下层的载荷**。一个 HTTP 请求在网线上，是 `[MAC][IP][TCP][HTTP 报文]` 这样一叠。

## 分层是套娃，不是总经理开会

教科书常用的比喻是“公司分层”：总经理和总经理沟通、经理和经理沟通、组长和组长沟通。这个比喻是错的，而且错得很要命：

| 错误比喻 | 为什么错 | 真实图景 |
|---|---|---|
| 总经理之间握手，不需要员工在场 | 网络里上层**从来不能**甩开下层单独沟通 | 总经理被经理装进兜里，经理被组长装进兜里，组长被员工装进兜里 |
| 员工说一句、组长补两句、经理补两句、总经理补两句 | 这是“各自加一句”，不是封装 | **总经理先说话**，经理把它整个装起来补两句，组长再整个装起来补两句，员工最后整个装起来补两句 |
| 每层只管自己那一段链路 | 分层成了“分段负责”，链路就不连续了 | 每一层都是端到端的逻辑，只是被下一层搬运 |

> 🔑 所有不能表示出“层层封装”含义的比喻，都是不恰当的。

## 一条铁律：可以有下层没上层，不可能有上层没下层

这条规则能一次解释掉很多“看着懂、一问就糊涂”的问题：

| 常见困惑 | 用这条铁律怎么解释 |
|---|---|
| 我知道对方 IP 了，直接发过去不行吗？ | 不行。IP 包必须装进帧里才能上线，没有 MAC 就没有帧 |
| 二层设备处理 HTTP 包时，HTTP 还在吗？ | 在。二层设备收进去的是**整个包**，只是它只摘到 MAC 头就做决定 |
| TCP 三次握手时，IP 层和 MAC 层在干什么？ | 每发一个 TCP 消息，IP 与 MAC 的机制都要完整跑一遍；你只看见三次握手，下面两层已经忙了很久 |
| 抓包抓到的是不是“半个包”？ | 不是。抓到的永远是完整帧，只是解析工具按层展开给你看 |

## 二层设备、三层设备、七层 LB 的判据

判据只有一句：**它摘到第几层头做决定**。

| 设备 | 摘到哪一层 | 看什么做决定 | 典型例子 |
|---|---|---|---|
| 一层设备 | 都不摘 | 电信号/比特，复制到所有口 | Hub（集线器） |
| 二层设备 | 摘 MAC 头 | 目标 MAC 在哪个口 | 交换机（见 [8.14 二层](8.14-二层-ARP-交换机与VLAN.md)） |
| 三层设备 | 再摘 IP 头 | 目标 IP 走哪条路由 | 路由器、三层交换机（见 [8.15 网关与路由](8.15-网关与路由协议.md)） |
| 四层 LB | 再摘 TCP/UDP 头 | 端口、连接 | LVS（见 [8.9 四层与七层负载均衡](8.9-四层与七层负载均衡.md)） |
| 七层 LB | 再解开应用层 | URL、Header、Cookie | Nginx、Envoy（见 [8.10 反向代理](8.10-反向代理与转发策略.md)） |

> ⚠️ “几层设备”描述的是**它处理到多深**，不是“它只能承载那一层的流量”。任何一层设备收进来的都是完整包。

## 一次下单，把整章串起来

把一次下单过程串起来，就是本章的地图：

```text
输入 https://www.kaola.com
  → DNS / HTTPDNS 查到 IP                       见 8.4
  → 包交给 socket，进传输层（TCP，端口区分进程）  见 8.1、8.3
  → 网络层写源 IP、目的 IP；不同网段就发网关      见 8.15
  → ARP 问“谁是网关”，拿到网关 MAC              见 8.14
  → MAC 层组帧发出                              见 8.14
  → 网关按路由表选下一跳，每过一个城关换一次 MAC   见 8.15
  → 对端逐层摘头，按端口交给监听进程（如 Tomcat）
  → 进程间用 RPC 通知订单、库存、支付             见 42.1
  → 回包沿原路返回
```

排障时这条链就是检查顺序：**解析 → 建连 → 路由 → 二层 → 端口 → 应用**。绝大多数“网络不通”，都能在这条链上找到第一个断点。

```bash
# 在发起请求的机器上抓 5 个包，-e 打印 MAC 头，-nn 不做名字解析
# macOS 网卡是 en0，Linux 一般是 eth0；-i any 两者都可用
sudo tcpdump -i any -nn -e -c 5 'tcp port 80'
# 看三件事：① 每个包的 MAC 头是否在变（过网关会变）
#           ② IP 头里的源/目的地址是否全程不变（转发网关不变）
#           ③ 有没有 SYN 发出但回不来（对端或中间设备丢包）
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 用“各层各自沟通”理解分层 | 一旦遇到“上层怎么被下层搬运”就答不上，排查时找不到层 |
| 认为二层设备“不处理 HTTP” | 误判抓包与丢包位置，把应用问题当链路问题 |
| 以为知道 IP 就能发包 | 忽略 ARP 与网关，现象是“配了 IP 就是不通” |
| 把“封装”当成“每层各加一句话” | 理解不了 MSS、MTU、分片为什么按最外层算 |
| 在七层 LB 上排查 TCP 重传 | 七层设备已重组请求，看不到原始重传 |
| 只背 OSI 七层名字，不记“摘到第几层” | 分不清四层与七层 LB 的能力边界 |
| 排障从应用日志开始，不看解析与建连 | 在错误的一层里翻日志，耗时且无结论 |
| 把“包完整”理解成“包不被修改” | NAT、代理都会改包，完整指的是封装结构，不是内容不变 |

## 自检

**Q1** 一个 HTTP 请求经过一台二层交换机，交换机“看到”了 HTTP 内容吗？为什么？

▸ 答案：**结构上在，逻辑上不解析**。收进去的是完整帧，HTTP 报文确实在载荷里；但交换机只摘到 MAC 头就做转发决定，不会解析 IP 以上的内容。这就是“可以有下层没上层”的另一种说法：包永远完整，设备只处理到自己那一层。

**Q2** “TCP 三次握手”期间，IP 层和 MAC 层做了什么？

▸ 答案：每个 TCP 消息都要完整走一遍 IP 与 MAC 的封装与转发——查路由、ARP 取 MAC、组帧、逐跳改 MAC。握手是传输层看到的三次交互，下面两层为这三个包各自跑了全套机制。

**Q3** 为什么“总经理—员工”的分层比喻会误导排障？

▸ 答案：它暗示各层可以独立沟通，于是人会去找“哪一层自己出了问题”。但真实是套娃：上层的每个包都被下层完整搬运，任何一层不通，上层连一个字节都发不出去。排障因此要沿“封装链”自下而上找第一个断点，而不是按层各查一遍。

**Q4** 一台设备号称“三层设备”，它能不能转发只有 MAC 头、没有 IP 头的帧？

▸ 答案：不能。三层设备的判据是“摘完 MAC 头再摘 IP 头”，没有 IP 头就没有它要查的路由信息。这类帧只能在二层域内由交换机处理。

**Q5** 为什么说“抓包抓到的永远是完整包”，但 Wireshark 里却只显示 HTTP？

▸ 答案：完整指的是**封装结构完整**，不是“所有层都必须被展示”。解析工具默认从最内层协议开始展示，你可以展开任意一层看头部。反过来说，如果帧被截断（snaplen 太小），那才是真的不完整。
