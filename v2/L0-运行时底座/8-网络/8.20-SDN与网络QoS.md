# 8.20 SDN 与网络 QoS：控制面集中之后

## 一句话

> SDN 把“每台设备登录一次”换成“一个控制面看全局”，代价是把爆炸半径也集中了；QoS 则是这套集中控制里唯一能兑现的承诺——**能控的只有出方向，入方向只能丢**。

## 边界的转变：从“逐台登录”到“一个视图”

用 VLAN + Linux 网桥管云网络，租户一多必然崩。典型症状有四类，每一类都是架构问题而不是运维问题：

| 症状 | 传统做法 | 后果 |
|---|---|---|
| **配不完** | 登录这台机器配这个、再登录另一台设备配那个 | 变更靠人肉，规则不一致时没人说得清现状 |
| **看不到全貌** | 每台设备只有自己的表 | 排障靠猜，容量规划靠拍脑袋 |
| **规模爆炸** | 每个新租户建一张带 VLAN 的虚拟网卡 + 一个独立网桥 | 租户上百后，网卡与网桥数量本身成为故障源 |
| **两层强绑定** | 虚拟 VLAN 直接透传到物理网络 | 物理网段规划与租户规划互相锁死，谁都改不动 |

> 🔑 前三条都是“缺一个统一视图”，第四条是“缺一层解耦”。SDN 就是同时解决这两件事。

## SDN 的三个特点

| 特点 | 内容 | 生活类比 |
|---|---|---|
| **控制与转发分离** | 转发面是一台台虚拟或物理设备；控制面是统一控制中心 | 转发面是小区里的一条条路，控制面是物业的监控室 |
| **开放接口** | 向上给应用调用的是**北向**，向下控制设备的是**南向** | 北向像总控室给管理员的按钮，南向像远程控电梯速度 |
| **逻辑集中控制** | 一个控制面管多个转发设备，从而拿到全局视图 | 管理员在监控室看到整个小区，再优化出入方案 |

> 💡 「上北下南」是记接口方向的唯一口诀：**北向给应用，南向控设备**。

## OpenFlow 与流表：把包当 Buffer

OpenFlow 是控制器与设备之间的**南向接口协议**；OpenvSwitch 是支持 OpenFlow 的**软件虚拟交换机**。两者合起来，让一台普通 Linux 机器具备可编程交换机的行为。

流表的模型极简：每行一条规则，有优先级，先高后低；满足匹配条件就执行动作（改包头、跳表、转发到某口、丢弃），都不匹配则默认丢弃。

| 层 | 匹配字段 | 典型动作 |
|---|---|---|
| 物理/端口 | `in_port` | 从某个口出去 |
| MAC | `dl_src`、`dl_dst`、`dl_vlan` | `mod_dl_src`、`mod_dl_dst`、`mod_vlan_vid`、`strip_vlan` |
| IP | `nw_src`、`nw_dst` | `mod_nw_src`、`mod_nw_dst` |
| 传输层 | `tp_src`、`tp_dst` | `mod_tp_src`、`mod_tp_dst` |

> 🔑 「网络包到了我手里，就是一个 Buffer，我想怎么改怎么改，想发到哪个端口就发送到哪个端口」——这句话是 SDN 数据面的全部哲学。它也让“虚拟网络”第一次可以脱离物理设备独立演进。

## OpenvSwitch 落地：access/trunk 与 bond

| 端口类型 | 配置 | 行为 |
|---|---|---|
| **access port** | 配 `tag` | 进来的包打上该 tag；带相同 VLAN ID 的包才从这个口出；**出去的包不带 VLAN ID** |
| **trunk port** | 配 `trunks` | 为空则所有 VLAN 都透传（没设 VLAN 就属 VLAN 0）；不为空则只放行列出的 VLAN |

bond（网卡绑定）三档，按需要选：

| 模式 | 做什么 | 前提 |
|---|---|---|
| `active-backup` | 一条 active、其余 backup，active 挂了顶上 | 无（默认） |
| `balance-slb` | 按源 MAC 与 output VLAN 分摊 | 无 |
| `balance-tcp` | 可按 L2/L3/L4 分摊 | 对端必须支持 LACP |

数据面要记住一条：**内核 Datapath 先匹配，未命中才 upcall 到用户态**。所以排障顺序是“先看用户态全量规则，再看内核缓存是否过期”，反过来查会一直查到旧规则。

```bash
# 建一个虚拟交换机与两个端口（需要 root；ovs-vswitchd 在跑）
ovs-vsctl add-br br0
ovs-vsctl add-port br0 vnet0 tag=101
ovs-vsctl add-port br0 eth1 trunks=101,102

# 看流表与端口配置：table=0 的规则是否命中、端口 tag/trunks 是否符合预期
ovs-ofctl dump-flows br0
ovs-vsctl list port vnet0
```

## QoS 的第一原则：只能控出方向

| 方向 | 能做什么 | 手段 | 结果 |
|---|---|---|---|
| **出方向** | 整形（shaping） | 队列 + 令牌桶 + 优先级 | 流量被塑成想要的模样，可以“攒”可以“借” |
| **入方向** | 只能丢（policing） | 超过速率直接丢包 | 丢得早不如丢得对；TCP 会因此退避 |

> ⚠️ 想“限制下载速度”却只配了入向策略，本质是在**丢包**而不是限速；TCP 会把丢包解读为拥塞，速度曲线是锯齿而不是平滑的。

三种无类别队列，各解决一类问题：

| 队列 | 解决什么 | 关键参数 | 失效场景 |
|---|---|---|---|
| **pfifo_fast** | 按优先级排队 | TOS **4 位 → 16 种**，`priomap` 16 个数字（0–2）映射到 3 个 Band | 高优先级流会饿死低优先级 |
| **SFQ** | 防单条流占满 | 按 TCP session 的 hash 分流，`perturb` 定期换 hash | hash 相同的流共享队列、互相影响 |
| **TBF** | 整体限速 | 令牌按速率生成，`limit` 是桶大小 | 桶不设上限 → 空闲攒满令牌，突发瞬间打爆 |

## HTB：用一棵树分配带宽

HTB 是云里最常用的方案（OpenVSwitch 的 `linux-htb` 也是它）。结构是一棵树：根规则付句柄 `1:`，下面挂分支 `:10`、`:11`、`:12`，`default` 指定不匹配时走哪个分支。

每个节点有两个速度：`rate`（一般情况下的速度）与 `ceil`（最高速度），根节点两者相同。示例：根 `rate=ceil=100kbps`，三个子类 `30/10/60kbps`，**rate 之和正好等于网卡允许的最大速度**。

```bash
# 1) 根队列（1:），rate 与 ceil 都设成网卡上限
tc qdisc add dev eth0 root handle 1: htb default 12
tc class add dev eth0 parent 1: classid 1:1 htb rate 100kbps ceil 100kbps

# 2) 三个子类：30 / 10 / 60，ceil 都放到 100 以便互相借
tc class add dev eth0 parent 1:1 classid 1:10 htb rate 30kbps ceil 100kbps
tc class add dev eth0 parent 1:1 classid 1:11 htb rate 10kbps ceil 100kbps
tc class add dev eth0 parent 1:1 classid 1:12 htb rate 60kbps ceil 100kbps

# 3) 叶子挂 sfq（防单流占满），再按源 IP/端口分流
tc qdisc add dev eth0 parent 1:10 handle 10: sfq perturb 10
tc filter add dev eth0 protocol ip parent 1:0 prio 1 u32 \
  match ip src 10.0.0.5 match ip dport 80 0xffff flowid 1:10

# 4) 验证：看队列与计数器，确认包真的进了对应分支
tc -s qdisc show dev eth0
```

两个关键细节：

- **必须先建 root class**，再建三个子 class；否则子类之间**不能互借流量**，空闲带宽直接浪费。
- **借流量**是 HTB 最有用的特性：某个分支空闲时，它的带宽可以借给忙的分支（实测三流并发比例为 3:1:6，与配置比例一致；某分支空闲时被借走约 60%）。

云上用 OVS 做 QoS 是同一套东西：入向设 `ingress_policing_rate` / `ingress_policing_burst`，出向建 `type=linux-htb` 的 QoS 规则、多个 Queue（`min-rate` 对应 rate、`max-rate` 对应 ceil），再用流表 `actions=enqueue:<port>:<queue>` 指路。

## 对架构的三条含义

| 含义 | 具体影响 |
|---|---|
| **控制面集中 = 变更速度与爆炸半径同时变大** | 一次下发错误可以瞬间影响所有租户；必须配灰度、审计与回滚 |
| **QoS 是租户隔离的最后一道** | 隔离做了 VLAN/Overlay 只解决“能不能通”，不解决“抢不抢得到”；共享带宽必须有队列兜底 |
| **标识与策略要一起设计** | VLAN 4096 不够用、VNI 24 位够用，标识空间决定了多租户上限（见 [8.19](8.19-Overlay与隧道-GRE-VXLAN-VPN.md)） |

## 反模式

| 反模式 | 后果 |
|---|---|
| 用“逐台登录改配置”管云网络 | 规则漂移、排障靠猜，规模一大就无法收敛 |
| 为每个租户新建网卡 + 独立网桥 | 租户上百后网卡与网桥本身成为故障源 |
| 让虚拟 VLAN 与物理 VLAN 透传强绑定 | 两层规划互相锁死，任何一层调整都要动另一层 |
| 在 trunk port 上期望发出的包不带 VLAN ID | 只有 access port 出的包才剥 tag，抓包会“多一个标签” |
| 用 `balance-tcp` 但对端不支持 LACP | 绑定起不来，链路反而只剩一条 |
| 以为 OpenvSwitch 只在用户态处理 | 忽略内核 Datapath 与 upcall，按旧规则排障 |
| 只配入向策略就宣称“限速完成” | 实际是丢包，TCP 退避后表现为吞吐锯齿与重传 |
| 不建 root class 直接建子 class | 子类无法互借，空闲带宽白白浪费 |
| 子类 rate 之和超过网卡上限 | 承诺兑现不了，忙时所有分支一起掉速 |
| 流表不写默认 drop | 不匹配的流量被放行，隔离形同虚设 |

## 自检

**Q1** 为什么说“SDN 把爆炸半径也集中了”？

▸ 答案：因为控制面是**逻辑集中**的：一个控制器管多个转发设备，一次策略下发可以同时改掉整个网络的转发行为。好处是拿到全局视图、配置一致；坏处是控制器或配置出错时，影响面不是一台设备而是全网。所以集中控制必须配灰度、审计、回滚，以及控制面自身的高可用。

**Q2** 同一套“只放行 VLAN 101”的意图，为什么 access port 与 trunk port 的配置完全不同？

▸ 答案：因为两者的**标签边界**不同。access port 面向终端：进来的包没有 tag，交换机替它打上 tag；出去的包要还原成终端能认的格式，所以剥掉 tag。trunk port 面向交换机：两端都要靠 tag 判断归属，所以 tag 必须原样透传，`trunks` 列的是允许通过的集合。

**Q3** 想限制某租户“下载不超过 10Mbps”，为什么只配入向 policing 达不到效果？

▸ 答案：入向只能丢包，丢包会被 TCP 解读为拥塞，触发重传与退避，实际吞吐是锯齿状且伴随大量重传；你控制了速率，却牺牲了效率与稳定性。正确做法是在**出方向**（也就是对端的发送侧，或自己的出口整形点）做 shaping，让流量被平滑地塑形，而不是打散重传。

**Q4** HTB 里 `rate` 与 `ceil` 分别约束什么？为什么子类 `rate` 之和要等于网卡上限？

▸ 答案：`rate` 是保证速率（一般情况下的份额），`ceil` 是上限（空闲时可借到的最高速率）。`rate` 之和等于网卡上限，意味着“所有分支同时满负荷”时正好用满、不超卖；如果之和超过上限，承诺就无法同时兑现，忙时每个分支都拿不到自己的 `rate`。

**Q5** 为什么“先 root class 再子 class”不是形式要求？

▸ 答案：借流量发生在**同一个 root class 之下**的兄弟节点之间。没有 root class 时，三个 class 是并列的顶层节点，调度器不认为它们属于同一棵可借用的树，于是空闲分支的带宽不会被借给忙的分支——配置看起来一样，效果差一半。
