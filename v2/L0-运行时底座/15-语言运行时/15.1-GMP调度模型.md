# 15.1 GMP 调度模型

## 一句话

> Go 运行时把 “M 个内核线程” 与 “N 个 goroutine” 之间插了一层 **P（逻辑处理器）**：P 持有本地可运行队列与内存缓存，让调度在**用户态**完成，从而既避免每次切换都陷入内核，又能用 work stealing 保持负载均衡。

## 三个角色

| 角色 | 是什么 | 关键点 |
|---|---|---|
| **G** | goroutine（2KB 初始栈 + 状态） | 创建成本极低，可百万级 |
| **M** | 内核线程（machine） | 真正执行代码；阻塞时会被换下 |
| **P** | 逻辑处理器（数量 = `GOMAXPROCS`） | 持有本地队列（上限 256）与 mcache |

```
M ←绑定→ P ←取 G→ 执行
         └→ 本地队列；空了就去全局队列或偷别的 P 的（work stealing）
```

## 三种 “卡住” 的处理方式

| 情况 | 运行时动作 | 后果 |
|---|---|---|
| 网络 IO 阻塞 | 交给 netpoller，M 去跑别的 G | 不占线程 |
| 系统调用阻塞 | P 与 M 解绑（handoff），另找/新建 M | 线程数可能上涨 |
| 长时间纯计算 | sysmon 触发**抢占**（Go 1.14+ 异步抢占） | 避免饿死其他 G |

`GOMAXPROCS` 决定 “同时跑用户代码的 P 数量”。**Go 1.25 起，Linux 上默认会读 cgroup 的 CPU bandwidth limit，并在配额/核数变化时周期性更新**；显式设置环境变量 `GOMAXPROCS` 或调用 `runtime.GOMAXPROCS` 会关闭这种自动更新（可用 `runtime.SetDefaultGOMAXPROCS()` 恢复）。它不看 CPU requests，只看 limit。旧版本或特殊场景才需要 `automaxprocs`。

## 调度器内部：G、M、P 各自记什么

| 结构 | 关键字段 | 你要记住的 |
|---|---|---|
| `runtime.g` | `stack`、`stackguard0`、`atomicstatus`、`sched`（sp/pc）、`m`、`goid`、`_defer`/`_panic` | 一个待执行任务 + 它的栈、状态、调度上下文 |
| `runtime.m` | `g0`（调度栈）、`curg`（当前用户 G）、`p`、`nextp`、`oldp` | 真正被 OS 调度的线程；`g0` 跑运行时调度代码 |
| `runtime.p` | `runq[256]` 环形队列、`runqhead/runqtail`、`runnext`、`mcache`、`status` | 用户态调度器；本地队列 + 分配缓存都挂在 P 上 |

G 的状态不止 “运行/阻塞” 两种，常见的有：

| 状态 | 含义 |
|---|---|
| `_Grunnable` | 可运行，在本地/全局队列里排队，没有栈所有权 |
| `_Grunning` | 正在 M 上执行，拥有栈所有权，绑定 P |
| `_Gsyscall` | 正在执行系统调用，绑定 M，但 P 可能被 handoff |
| `_Gwaiting` | 因 channel/锁/网络等阻塞，不在运行队列 |
| `_Gpreempted` | 被抢占挂起，等待重新调度 |
| `_Gdead` | 未使用，可被复用 |

> 🔑 P 的 `runnext` 只有一个槽：它让 “刚创建的 G” 优先于队列里已有的 G 运行，降低 `go f()` 后的启动延迟；但它是**偏好**，不是不公平的插队机制（每 61 次调度会从全局队列取一个，防止全局饥饿）。

## 一个 goroutine 从 `go` 到运行

```text
go f(args)
  → 编译器把参数拷到栈上，调用 runtime.newproc
  → newproc1 从 P 的 gFree / 全局 gFree 取一个 G（没有就 malg 新建 2KB 栈）
  → 把参数整块 memmove 到新 G 的栈
  → 设置 sched.sp / sched.pc = goexit，状态 _Gdead → _Grunnable
  → runqput：优先放 P.runnext，其次放本地 runq[256]
  → 本地队列满：runqputslow 把一半 G 搬到全局队列
```

几个反直觉点：

- **`go` 不是系统调用**，也不创建线程；它只在用户态取一个 G、拷参数、入队。
- **G 会被复用**：执行完的 G 进入 P 的 `gFree` 列表，下次 `go` 直接取，不需要重新分配栈。
- **参数在入队前就拷到 G 的栈上**，所以 `go func(x int)` 的 `x` 是值拷贝；循环变量在 Go 1.22 后每轮独立，不再需要 `x := x`。

## 调度循环：先本地，再全局，最后偷

`runtime.schedule` 的选择顺序可以记成一句话：**本地队列 → 全局队列（每 61 次）→ netpoll → 偷别的 P**。

```text
schedule()
  ├─ 本地 runq / runnext 有 G？ → execute
  ├─ 全局队列有 G？             → 取一批（每 61 次调度强制看一次全局）
  ├─ findrunnable():
  │    ├─ 再查本地/全局
  │    ├─ netpoll(0) 看网络就绪的 G
  │    ├─ 随机挑一个 P，偷它一半的 G（runqsteal）
  │    └─ 都没有 → 休眠，等待唤醒
  └─ execute(gp) → gogo 恢复 gp 的 sp/pc
```

工作窃取的关键数字：

| 参数 | 值 | 作用 |
|---|---|---|
| 本地队列容量 | 256 | 满了溢到全局队列 |
| 偷取比例 | 约一半 | 避免频繁偷、平衡负载 |
| 全局队列检查 | 每 61 次调度 | 防止全局队列饿死 |
| 空闲 P 上限 | = `GOMAXPROCS` | 不是无限加线程 |

> ⚠️ **“P 空闲” 不等于 “CPU 空闲”**：G 可能都卡在锁、channel、网络或系统调用上。`schedtrace` 里 `idleprocs` 高但吞吐低，先查阻塞画像，不要盲目加 P。

## 抢占：协作式 + 信号式

Go 的抢占走了两步：

| 阶段 | 机制 | 局限 |
|---|---|---|
| Go 1.2–1.13 | 编译器在函数调用前插入 `morestack`，检查 `stackguard0 == StackPreempt` | 纯计算循环没有函数调用，无法抢占 |
| Go 1.14+ | 向线程发 `SIGURG`，在信号处理里把 G 挂起（`asyncPreempt`） | 仍需安全点；不是任意指令都能停 |

触发抢占的常见来源：

- **sysmon** 发现 P 运行同一个 G 超过约 10ms，调用 `preemptone`；
- **GC 栈扫描** 需要挂起 G，使用 `suspendG`/`resumeG`；
- **`runtime.Gosched()`** 主动让出，把 G 放回全局队列。

> 🔑 纯计算循环在 Go 1.14+ 能被异步抢占，但**不要依赖它做实时性保证**：抢占是 “毫秒级最终会停”，不是硬实时。长任务仍应主动检查 `ctx.Done()`。

## 调度器演进：每一版在修什么

| 版本 | 模型 | 解决的问题 | 留下的问题 |
|---|---|---|---|
| 0.x | G-M，单线程 | 能跑 | 只能用一个线程 |
| 1.0 | G-M，多线程 + 全局锁 | 多线程 | 全局锁竞争，14% 时间在 futex |
| 1.1 | G-M-P + work stealing | 本地队列、减少锁竞争 | 长循环不让出、STW 长 |
| 1.2 | 协作式抢占 | 函数调用点可抢占 | 纯计算循环仍饿死 |
| 1.14 | 信号式异步抢占 | 长循环可被 GC/sysmon 打断 | 仍非硬实时 |

## 落到数字：调度参数与观测

| 项 | 默认/量级 | 说明 |
|---|---|---|
| `GOMAXPROCS` | = CPU 核数 | 应改为 cgroup 配额 |
| 本地队列 | 256 个 G | 满了溢到全局队列 |
| sysmon 检查周期 | 约 10ms 量级 | 触发抢占与网络轮询 |
| 异步抢占 | Go 1.14+ | 纯计算循环也能被切 |
| 创建 goroutine | 约 0.2–0.4μs | 比线程便宜两个量级 |

```bash
GODEBUG=schedtrace=1000 ./app      # 每秒打印：gomaxprocs、idle P、runqueue 长度
GODEBUG=scheddetail=1,schedtrace=1000 ./app | head -30
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 在容器里不设 `GOMAXPROCS` | 按宿主机核数开 P，配额下大量节流 |
| 用 goroutine 池 “省创建” | 创建成本本就极低，池反而增加复杂度 |
| CPU 密集循环不检查取消 | 抢占粒度内其他 G 被延迟 |
| 无限制地 `go func()` | goroutine 泄漏，内存与调度双爆 |
| 看到 `idleprocs` 高就扩 CPU | G 都卡在锁/IO/channel 上，加 P 无用，真正要看阻塞画像 |
| 指望纯计算循环靠协作式抢占让出 | 没有函数调用点就没有检查点，其他 G 被饿到秒级（Go 1.14 之前） |

## 三条铁律

> 🔑 **P 的存在是为了 “用户态调度 + 本地缓存”**，不是 “多一层线程”。

> 🔑 **`GOMAXPROCS` 要跟 cgroup 配额对齐**，不是跟物理核数。

> 🔑 **CPU 密集任务要能被打断**（检查 context / 让出），否则拖慢全局。

## 自检

**Q1** 为什么 Go 需要 P，而不是让 M 直接从全局队列取 G？

▸ 答案：因为**全局队列要加锁**，高并发下锁竞争会毁掉扩展性。P 让每个 M 有独立的本地队列与 mcache，大多数调度与分配都在无锁路径上完成；只有本地队列空/满时才碰全局结构。

**Q2** 一个 goroutine 做了阻塞式系统调用，其他 goroutine 会被卡住吗？

▸ 答案：**不会**。运行时会把这个 M 与 P **解绑**（handoff），P 交给其他 M 继续跑本地队列；阻塞的那个 M 回来后尝试获取一个 P，拿不到就把 G 放回全局队列并休眠。代价是线程数可能增加。

**Q3** 容器 `limits.cpu=2`，`GOMAXPROCS` 却是 16，会怎样？

▸ 答案：16 个 P 抢 2 核的配额，CFS 周期内被反复节流，表现为**延迟抖动与吞吐下降**。Go 1.25+ 默认会按 cgroup limit 设置并更新 `GOMAXPROCS`，通常不再需要手工设；旧版本或显式设过环境变量时，才用 `GOMAXPROCS=2` / `automaxprocs` 对齐。注意它只看 CPU limit，不看 requests。

**Q4** 什么情况下会出现 “goroutine 数量持续上涨”？

▸ 答案：常见三类：① 每次请求 `go func()` 但没有退出条件（泄漏）；② channel 写入阻塞且无人消费；③ 网络连接未关闭导致读循环挂住。用 goroutine profile 按栈聚合，能直接看出泄漏点。

**Q5** 抢占在 Go 1.14 之前为什么有问题？

▸ 答案：早期只有**协作式抢占**（在函数调用检查点让出），纯计算的循环没有函数调用，就无法被打断，导致调度延迟可达秒级。Go 1.14 引入基于信号的异步抢占，使长循环也能在毫秒级被切走。

**Q6** `schedtrace` 里 `runqueue` 长期大于 0、`idleprocs` 为 0 说明什么？

▸ 答案：说明 **CPU 已饱和**：P 全在跑、还有 G 排队。此时加机器/加 P 有意义；如果 `idleprocs` 很高但吞吐上不去，问题在 “G 都在阻塞”（锁、IO、channel），要查阻塞画像而不是扩 CPU。

**Q7** P 的 `runnext` 与 work stealing 各自解决什么问题？为什么还要每 61 次看全局队列？

▸ 答案：`runnext` 让刚 `go` 出来的 G 优先执行，降低启动延迟；work stealing 让空闲 P 从别的 P 偷一半 G，保持负载均衡。每 61 次调度强制看一次全局队列，是防止全局队列里的 G 被本地队列长期饿死——`runnext` 是偏好，不是无限插队。

**Q8** 为什么不能省掉 sysmon？它和调度器的分工是什么？

▸ 答案：调度器只在 G 主动让出/阻塞时切换；sysmon 负责“没人让出”的兜底：抢占运行超过 10ms 的 P、handoff 系统调用超过 10ms 的 P、运行到期 timer、每 10ms 轮询 netpoll、每 2 分钟强制 GC。没有它，长循环、卡住的系统调用、长时间不分配都会失控。详见 [15.11 定时器、网络轮询与系统监控](15.11-定时器网络轮询与系统监控.md)。
