# 15.6 并发原语 (channel / context / sync)

## 一句话

> Go 的并发原语只有两组——**channel 传递数据的所有权**、**sync 保护共享状态**——外加 **context 传播取消**；选错的典型症状是死锁、泄漏、以及 “看起来并发实际上串行”。

## 怎么选

| 你的需求 | 用什么 | 理由 |
|---|---|---|
| 数据在 goroutine 间 “交接” | **channel**（有缓冲优先） | 所有权随消息转移，无需锁 |
| 保护共享状态（计数器、map） | **sync.Mutex / atomic** | 简单、开销低 |
| 读多写少 | **sync.RWMutex** | 读并发，写互斥 |
| 只初始化一次 | **sync.Once** | 避免重复初始化竞态 |
| 等一组任务完成 | **sync.WaitGroup** / `errgroup` | 后者带错误与取消 |
| 传递取消与超时 | **context** | 标准做法，贯穿调用链 |
| 复用临时对象 | **sync.Pool** | 只在热点路径、对象较大时 |

## channel 的四条语义

| 写法 | 行为 |
|---|---|
| 无缓冲 `make(chan T)` | 发送与接收**必须同时就绪**，否则阻塞 |
| 有缓冲 `make(chan T, n)` | 缓冲未满可发、未空可收 |
| `close(ch)` | 关闭后 **接收返回零值 + ok=false**；再发送会 panic |
| `nil` channel | 收发永久阻塞（常用于 `select` 里禁用分支） |

`select` 的 `default` 让 “非阻塞尝试” 成为可能；`time.After` 做超时，但**循环里用它要小心**（Go 1.23 前会累积定时器）。

## context 的三件事

| 能力 | API | 纪律 |
|---|---|---|
| 取消 | `WithCancel` | **必须调用 cancel**，否则泄漏 |
| 超时/截止 | `WithTimeout` / `WithDeadline` | 超时值应从外层传，不在每层重设 |
| 传值 | `WithValue` | **只放请求域元数据**（trace_id、用户身份），不放业务参数 |

调度层的支撑见 [15.1 GMP 调度模型](15.1-GMP调度模型.md)；模型层面的取舍见 [15.8 并发编程模型 (线程 / 协程 / Actor / CSP)](15.8-并发编程模型.md)；竞态检测见 [15.7 竞态检测与数据竞争](15.7-竞态检测与数据竞争.md)。

## 落到数字：原语的开销量级

| 原语 | 无竞争成本 | 有竞争时 | 备注 |
|---|---|---|---|
| `atomic` 加减 | ~10ns | 缓存行争用，可退化 | 适合计数器 |
| `Mutex` 加解锁 | ~20ns | 竞争时进入 futex 睡眠（μs 级） | 临界区要短 |
| 无缓冲 channel 收发 | ~100ns | 需要调度配合 | 本质是一次握手 |
| 有缓冲 channel | ~50ns | 满/空时阻塞 | 常用作流水线 |
| `select` 多路 | 略高于直接收发 | 分支越多越慢 | 避免在热路径开 10 个分支 |

```bash
go test -race ./...            # 竞态检测（见 15.7）
go test -bench=. -benchmem -cpuprofile=cpu.out   # 用 benchmark 验证 “锁是否真的成为瓶颈”
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 channel 当锁（令牌） | 死锁难查，且比 Mutex 慢 |
| `context.Value` 传业务参数 | 依赖隐式、类型不安全、无法静态检查 |
| 忘记 `cancel()` | goroutine 与定时器泄漏 |
| 在 goroutine 内 `wg.Add` | 与 `Wait` 竞态，可能提前返回 |
| 关闭 channel 后再发送 / 多处关闭 | panic |
| 无缓冲 channel 做 “广播” | 只能被一个接收者拿到，语义错 |

## 三条铁律

> 🔑 **channel 传所有权，Mutex 护共享状态**；两者不要混用来解决同一问题。

> 🔑 **每个 `WithCancel` 都要 `defer cancel()`**。

> 🔑 **`context.Value` 只放元数据**；业务参数走函数签名。

## 自检

**Q1** 关闭一个已关闭的 channel 会怎样？向已关闭的 channel 发送呢？

▸ 答案：**关闭已关闭的 channel 会 panic**；向已关闭的 channel 发送也会 panic。从已关闭的 channel **接收**是安全的，会立即返回零值且 `ok=false`。所以 “关闭” 应由**发送方唯一负责**，接收方永远不关。

**Q2** 为什么 `context.Value` 不适合传业务参数？

▸ 答案：因为它绕过类型系统（`interface{}`）、依赖字符串 key、调用链上任何一层都可以覆盖，导致 “这个值从哪来” 无法静态追踪。它适合**横切元数据**（trace_id、租户、超时预算），这些值天然随请求传播且不参与业务逻辑。

**Q3** `sync.WaitGroup` 的 `Add` 为什么不能放在 goroutine 里？

▸ 答案：因为 `Wait` 可能在 `Add` 之前执行（`Add` 还没跑，计数器为 0，`Wait` 立即返回），导致 “任务还没跑完就继续”。正确做法是**在启动 goroutine 之前** `Add`，或者用 `errgroup` 的 `Go`（内部已处理）。

**Q4** 有缓冲 channel 的容量怎么定？

▸ 答案：按 “**生产者突发量 / 消费者处理速率 × 可接受延迟**” 估：容量太小退化成同步（阻塞生产者），太大则掩盖下游故障并堆积内存。常见做法是设为 “一批次的大小”，并配监控（channel 长度接近容量即告警）。

**Q5** 什么时候该用 `atomic` 而不是 `Mutex`？

▸ 答案：当操作是**单个字的读改写**（计数器、标志位、指针替换）时，`atomic` 无锁、开销更低。但一旦需要 “多个字段一起更新” 或 “读-判断-写” 的复合逻辑，就必须用 `Mutex`（或用 `atomic.Pointer` 指向不可变结构做整体替换）。

**QQ6** 什么时候 “加锁” 比 “用 channel 传数据” 更快？

▸ 答案：当操作只是**保护一小段共享状态**（几个字段的读改写）时：Mutex 是一条原子指令加临界区，而 channel 需要两次调度配合与缓冲管理。判据是 “数据是否需要交接所有权”——只是同步访问，就用锁。
