# 15.6 并发原语 (channel / context / sync)

## 一句话

> channel 管「所有权与事件」，锁管「共享状态」；三组原语最终只回答四个问题——**谁持有、谁释放、谁关闭、谁取消**——答错会炸，线上并发事故几乎都能归到「锁没成对 / 锁被复制 / 等待点不可取消 / 关闭与发送撞车」。

## 怎么选

| 你的需求 | 用什么 | 每次操作代价（本机实测，8 核） | 失败方式 |
|---|---|---|---|
| 数据在 goroutine 间交接所有权 | **channel**（有缓冲优先） | 74ns 交接（cap=1024）；无缓冲 186ns | 死锁、泄漏、关闭竞态 |
| 限制并发数 / 做背压 | **带缓冲 channel 当信号量** / `errgroup.SetLimit` | 一次收发 + 排队 | 槽位不归还、排队无界 |
| 保护共享状态（计数器、缓存） | **sync.Mutex** | 13.8ns 无竞争 / 83ns 8 核争用 | 死锁、漏解锁、复制 |
| 读多写少、临界区有实际工作 | **sync.RWMutex** | 77ns（8 核只读）/ 55ns（9:1 混合） | 写饥饿、递归读死锁 |
| 单字读改写（计数、标志、指针） | **atomic** | 7.1ns → 38ns（8 核） | 误以为能保护复合逻辑 |
| 等一组任务结束 | **sync.WaitGroup** / `errgroup` | 归零唤醒 | Add 晚了、复用早了 |
| 只初始化一次 | **sync.Once** | 一次原子读 | 初始化 panic 后永远不重试 |
| 等待某个条件成立 | **sync.Cond** | 挂起/唤醒 | 丢信号、不复查条件 |
| 键集合稳定、读多写少 | **sync.Map** | 9.4ns（9:1 混合） | 当通用 map 用、频繁增删 |
| 复用临时对象 | **sync.Pool** | 8.9ns vs 直接 make 448ns（4KB） | 当缓存用，GC 后被清空 |
| 传递取消、截止时间、请求域元数据 | **context** | 55ns（WithCancel）/ 241ns（WithTimeout，含 timer） | 忘 cancel、Value 塞业务参数、中途换 Background 断链 |

判据只有一句：**这是「状态」还是「消息」**——状态用锁/原子，消息用 channel。再补一条：**channel 不是「更高级的锁」**，拿它保护共享状态，等于用一条消息协议模拟一个变量，代价是 5 倍起步的单价和一整套新的死锁形态。

## channel：先把语义钉死

### 操作 × 状态：发送、接收、关闭

| 操作 | `nil` channel | 无缓冲 | 有缓冲（未满 / 未空） | 有缓冲（已满 / 已空） | 已关闭 |
|---|---|---|---|---|---|
| 发送 `ch <- v` | **永久阻塞** | 阻塞到接收者就绪，交接后继续 | 入队 | **阻塞**，等接收者腾位置 | **panic** |
| 接收 `<-ch` | **永久阻塞** | 阻塞到发送者就绪，交接后继续 | 从队首取 | **阻塞**，等发送者 | 先取完缓冲，再返回零值 + `ok=false` |
| 关闭 `close(ch)` | **panic** | 成功 | 成功 | 成功 | **panic** |

四条语义记住就够：

- **无缓冲**是「手递手」：发送与接收必须同时就绪，否则先到的一方阻塞。
- **有缓冲**是「放快递柜」：柜子没满就能发，没空就能收。
- **`nil` channel 永久阻塞**，所以它在 `select` 里等价于「这个分支不存在」。
- **关闭后缓冲里的数据仍可读完**，读完才返回零值；`ok=false` 只表示「不会再有新数据」，不是「当前这条无效」。

`close` 三定律：

1. **谁发送谁关闭**，接收方永远不关——接收方不知道还有没有别的发送者；
2. **只关一次**，重复 close 直接 panic；
3. **关闭后不再发送**，发送到已关闭的 channel 直接 panic——这是运行时主动暴露错误，不是未定义行为。

类型系统还能再挡一层：`<-chan T`（只收）上的 `close` 编译不过；`chan<- T`（只发）可以 `close`。把函数参数写成单向 channel，能把「谁能关闭」从口头约定变成编译期约束。

底层结构一句话：环形缓冲 `buf` + 两个等待队列 `sendq`/`recvq` + 一把保护所有字段的锁。所以 channel 不是「无锁队列」，它是一条**带调度的同步通道**：每次收发都要进一次锁，必要时把 goroutine 挂起再唤醒。本机实测一次有缓冲交接 74ns、无缓冲 186ns，而一次无竞争 `Mutex` 只要 13.8ns——**channel 的单价是锁的 5–14 倍**，它的价值在语义，不在性能。

两个直接推论：

- **信号用 `chan struct{}`，不用 `chan bool`**：`struct{}` 不占空间，读代码的人一眼知道「只关心事件发生」，而不是「true 还是 false 表示停止」。
- **`len(ch)` 是缓冲里当前元素个数**，不是「还剩多少任务没处理」。拿它判断「发完了吗」必然错——发送者可能还没开始发。

缓冲容量按「**生产者突发速率 × 可接受的排队延迟 − 消费者在这段时间内能处理掉的量**」估。太小退化成同步（阻塞生产者），太大则掩盖下游故障、把故障期变成内存增长。常见做法是设成「一批次的大小」，并对 `len(ch)` 做监控——持续接近容量就是背压信号，而不是「加大缓冲」。

> ⚠️ `select` 在多个分支同时就绪时**随机均匀**选一个，没有优先级；`default` 只在所有分支都不就绪时执行。别用「case 顺序」表达优先级。

## channel 的七个用法

channel 的坑一半来自语义，另一半来自「用错场景」。先把场景和写法对上：

| 场景 | 写法 | 一句话约束 |
|---|---|---|
| 交接所有权 | 发送后不再碰；接收方成为唯一持有者 | channel 复制值；指针/slice 仍共享底层 |
| 限并发 | `sem <- struct{}{}` / `<-sem` | 容量 = 并发上限，归还必须 `defer` |
| 非阻塞尝试 | `select` + `default` | `default` 会让循环空转，要配退避或阻塞分支 |
| 超时 / 取消 | `select` + `ctx.Done()` + `NewTimer` | 每个等待点都必须有出口 |
| 关闭广播 | `close(ch)` | 只由发送方关；多发送者交给一个 closer |
| 合并通知 | `cap=1` + `select`/`default` | 只保证「至少通知一次」，不排队 |
| 禁用分支 | 把 channel 置 `nil` | 扇入结束后置 nil，防止读零值空转 |

### ① 交接所有权：发完就放手

channel 传的是值的副本；如果值里带指针（slice、map、结构体指针），传过去的是**共享底层数据**。所谓「通过通信共享内存」，真正的纪律是：

```go
// 生产者：构造完、发出去之后，不再读写 buf
func produce(ch chan<- []byte) {
	buf := build()
	ch <- buf
	// 从这里开始，buf 归接收方所有；再改就是数据竞争
}

// 接收方：收到即独占，不需要加锁
func consume(ch <-chan []byte) {
	buf := <-ch
	use(buf)
}
```

有缓冲也一样——数据放进缓冲那一刻，所有权就已经转移。**「发送后还留着改」是 channel 版的数据竞争**，race detector 能抓到，但 code review 往往看不出来。

### ② 信号量：带缓冲 channel 限并发

```go
sem := make(chan struct{}, 3) // 容量 = 同时最多 3 个

for _, task := range tasks {
	sem <- struct{}{} // 满了就在这里阻塞：背压发生在提交侧
	go func(task Task) {
		defer func() { <-sem }() // 任何返回路径都要归还槽位
		run(task)
	}(task)
}
```

两个细节决定它是不是真的限住了：

- **先占槽位再起 goroutine**，goroutine 数量也被限住；把 `sem <- struct{}{}` 挪进 goroutine，只限住了「同时运行数」，排队中的 goroutine 仍然无限增长。
- **`defer` 归还**，否则 `run` panic 或提前 return 就永久漏掉一个槽位，最终整个池子卡死。

`errgroup.SetLimit(n)` 内部就是这套机制；需要「一个任务占多个槽位」（比如大查询占 4 个连接）时用 `golang.org/x/sync/semaphore` 的加权版本。标准库没有信号量类型，**带缓冲 channel 就是最便宜的实现**。

### ③ 非阻塞收发：`select` + `default`

```go
select {
case ch <- v: // 有空位：投递成功
default:      // 满了：走降级路径，绝不阻塞
	dropped.Add(1)
}
```

接收侧同理：

```go
select {
case v, ok := <-ch:
	if !ok {
		return // 已关闭且缓冲已空
	}
	handle(v)
default:
	// 本轮没有数据，去做别的事
}
```

这就是 `TrySend`/`TryRecv`。两个坑：

- **在 `for` 里裸写 `default` 会 100% 占一个核**——没有数据时立刻转下一轮。要么加 `time.Sleep`/ticker 退避，要么保留一个阻塞分支（比如 `<-ctx.Done()`）。
- **`ok=false` 的接收永远「就绪」**，所以关闭后的 channel 放在 `select` 里会一直命中；把它置 `nil` 才是「下线」。

`default` 也常用来做**合并通知**：通知只需要「至少一次」，不需要排队。

```go
type Notifier struct{ ch chan struct{} }

func NewNotifier() *Notifier { return &Notifier{ch: make(chan struct{}, 1)} }

func (n *Notifier) Notify() {
	select {
	case n.ch <- struct{}{}: // 第一次：占住唯一的槽位
	default:                 // 已有未读通知：合并，不排队
	}
}

func (n *Notifier) C() <-chan struct{} { return n.ch }
```

配置热更新、缓存失效这类「短时间多次事件只需处理一次」的场景，用 `cap=1` + 合并，比无界队列稳。

### ④ 超时与取消：给每个等待点装出口

```go
var ErrTimeout = errors.New("timeout")

func waitResult[T any](ctx context.Context, ch <-chan T, d time.Duration) (T, error) {
	var zero T
	t := time.NewTimer(d)
	defer t.Stop()

	select {
	case r := <-ch:
		return r, nil
	case <-ctx.Done():
		return zero, ctx.Err()
	case <-t.C:
		return zero, ErrTimeout
	}
}
```

`time.After` 在一次性等待里没问题；**放在长跑循环里**就要换 `NewTimer` + `Reset`：Go 1.23 之前未被触发的 timer 不会被 GC，每轮都在堆上留一个；Go 1.23 起未引用的 timer 可以被回收，但每轮仍然有分配和调度成本。复用 timer 的标准写法是先 `Stop`、排空 `C`、再 `Reset`：

```go
if !t.Stop() {
	select {
	case <-t.C: // 已经触发但还没读：排空
	default:
	}
}
t.Reset(d)
```

> ⚠️ 不要用 `time.Sleep` 当等待：它不感知 `context`，取消后还要睡满。要睡就写一个 `select` 版睡眠（`case <-time.After(d)` 或 `NewTimer` + `ctx.Done()`），让取消能立刻打断。

### ⑤ 关闭广播：`close` 是唯一能「一次叫醒所有人」的操作

```go
// 单发送者：自己关，语义最清楚
go func() {
	defer close(ch)
	for _, v := range data {
		ch <- v
	}
}()

// 多发送者：谁都不关，交给一个专门的 closer
var wg sync.WaitGroup
for _, src := range srcs {
	wg.Add(1)
	go func(src <-chan int) {
		defer wg.Done()
		for v := range src {
			out <- v
		}
	}(src)
}
go func() {
	wg.Wait() // 所有发送者都退出后，才允许关
	close(out)
}()
```

**接收方永远不关闭**：它不知道其他发送者是否还在发；接收方一关，其他发送者下一次发送就 panic。多发送者场景的标准解法不是「协商谁关」，而是**把关闭权收拢到一个知道「全部发送者都结束了」的 goroutine**——上面的 closer。

`close` 同时是广播：所有阻塞在 `<-ch` 的接收者会同时被唤醒并拿到零值。这就是「关闭信号」的底层机制——`context` 的 `Done()` 也是这么实现的。

### ⑥ 禁用分支：`nil` channel 是开关，不是坑

需要「永久阻塞」时，`select{}` 比 `for{}` 好：前者让当前 goroutine 进入阻塞、释放 P，后者会空转烧 CPU。

`nil` channel 的收发永久阻塞，在 `select` 里等价于「删掉这个 case」。扇入多个输入时，某个输入关闭后如果继续留在 `select` 里，会立刻返回零值，循环空转、CPU 打满；标准做法是读完就置 `nil`：

```go
// a、b 两个输入，谁关闭就把谁置 nil，从 select 里摘掉
for a != nil || b != nil {
	select {
	case v, ok := <-a:
		if !ok {
			a = nil
			continue
		}
		out <- v
	case v, ok := <-b:
		if !ok {
			b = nil
			continue
		}
		out <- v
	}
}
```

输入个数在编译期未知（N 个下游）时，用切片或 `reflect.Select`；编排细节见 [15.8 并发编程模型 (线程 / 协程 / Actor / CSP)](15.8-并发编程模型.md)。这里只记一条：**`nil` 是「禁用」，`close` 是「叫醒」，两者别混**。

### ⑦ 别把 channel 当队列

channel 有缓冲，于是很容易被当成「免费的消息队列」：容量开大一点、消费者慢一点、积压就堆在内存里。它没有持久化、没有消费位点、没有死信、没有容量治理；缓冲再大也会满，满了以后要么阻塞生产者，要么（配 `default`）丢消息。**channel 适合「交接 + 背压」，不适合「囤积」**；需要囤积时，队列深度、拒绝策略、监控指标都得显式设计，见 [15.8 并发编程模型 (线程 / 协程 / Actor / CSP)](15.8-并发编程模型.md) 的背压一节。

信号量限并发、非阻塞收发、`chan struct{}` 传信号、合并通知、可取消 sleep 这几条实践，参考了 [Go 语言编程技巧](https://colobu.com/gotips/) 的 Tip #25 / #29 / #70 / #77 / #78；锁的位置、嵌入 `Mutex` 的取舍、`context.Value` 与协程生命周期见 Tip #45 / #58 / #61 / #62 / #63。

## channel 在大型项目里的三个案例

小例子只证明语法，生产案例才暴露「关闭权、背压、慢消费者、取消」这四件事。下面三个结构都能在 [15.6-channel-production](../../../tools/examples/15.6-channel-production/README.md) 里直接跑。

### 案例一：任务导出 / 转码（有界队列 + 固定 worker）

场景：后台导出 10 万个订单、批量转码图片、给每个商品重算索引。共同点是**任务数远大于核数，且不能无限堆内存**。

```go
jobs := make(chan Job, 4)       // 有界：满了阻塞生产者，形成背压
results := make(chan Result, 16)
var wg sync.WaitGroup

for i := 0; i < 3; i++ {
	wg.Add(1)
	go func(id int) {
		defer wg.Done()
		for job := range jobs {           // jobs 关闭后自然退出
			select {
			case <-ctx.Done():
				return
			default:
			}
			results <- Result{ID: job.ID, Worker: id}
		}
	}(i)
}

go func() {
	defer close(jobs)                     // 生产者关闭 jobs
	for _, job := range allJobs {
		jobs <- job
	}
}()
go func() {
	wg.Wait()
	close(results)                        // 所有 worker 退出后，由 closer 关闭 results
}()

for r := range results {                  // 主 goroutine 只读结果
	collect(r)
}
```

三个角色的关闭权必须分清，错一个就是 panic 或泄漏：

| channel | 谁关闭 | 为什么 |
|---|---|---|
| `jobs` | 生产者 | 只有生产者知道「不会再有任务」 |
| `results` | 单独的 closer（`wg.Wait()` 后） | worker 不知道其他 worker 是否还在发 |
| worker | 不关闭任何 channel | 只消费、只发送 |

生产上还要补三样：

- **错误通道**：`results` 里带 `Err`，或单独 `errCh`；第一个错误 `cancel()`，其余 worker 尽快退出；
- **进度与背压指标**：`len(jobs)/cap(jobs)`、单任务排队时间、worker 忙碌率；持续接近容量说明该加消费者或降速，不是「把 cap 调大」；
- **部分失败**：已写出的结果要不要回滚、断点能否续跑；channel 只负责传，事务边界要另设计。

### 案例二：行情 / SSE / 聊天室（一对多广播，隔离慢消费者）

场景：一个行情源，几百个 WebSocket 连接；一个客户端网络慢，不能拖住所有人。**每个订阅者一个独立 channel**：

```go
type Hub struct {
	subs []chan int
}

func (h *Hub) Publish(v int) (dropped int) {
	for _, ch := range h.subs {
		select {
		case ch <- v:       // 有空位：投递
		default:            // 满了：丢弃或标记踢下线
			dropped++
		}
	}
	return dropped
}
```

这段代码的取舍要写进设计文档：

| 策略 | 行为 | 适用 |
|---|---|---|
| 丢弃新消息 | 保留旧值，丢最新 | 行情快照、可容忍丢帧 |
| 丢最旧（ring） | 保留最新 | 实时性优先的指标 |
| 断开慢消费者 | 连接重建，客户端补拉 | 强一致、不能丢的消息 |
| 阻塞发布者 | 一个慢客户端拖住全部 | 几乎总是错的 |

**广播用「每订阅者一个 channel」，负载均衡用「共享一个 channel」**——这是生产里最常见的结构混淆：共享 channel 时，一条消息只会被一个消费者拿到，不是所有人都收到。

### 案例三：多副本取最快（hedged request / fan-in）

场景：读服务有 3 个副本，P99 长尾明显；同时发给 3 个副本，谁先回用谁，其余取消。关键是**结果通道要带足缓冲**：

```go
ch := make(chan result, len(replicas)) // 容量 = 副本数
for _, r := range replicas {
	go func(r Replica) { ch <- call(ctx, r) }(r)
}

first := <-ch
cancel() // 第一个成功，取消其余副本
for i := 1; i < len(replicas); i++ {
	<-ch // 收完，确保每个 goroutine 都退出
}
```

如果 `ch` 是无缓冲的：赢家返回后主 goroutine 不再接收，输掉的副本会永久阻塞在 `ch <- ...`，每个请求泄漏 2 个 goroutine。**「第一个成功就返回」的代码，必须让所有输家也能把结果写出去**——要么缓冲 = 副本数，要么用 `select` 带 `ctx.Done()`。

生产约束：

- 副本数不是越多越好：N 个副本 = N 倍下游流量，通常 2–3 个；
- 每个副本要有独立超时和取消，避免一个慢副本拖住整组；
- 记录「哪个副本赢、其余副本耗时」，否则长尾只是被掩盖，不是被解决。

### 关闭顺序：一条能抄的清单

```
停止接收新任务（关入口 / 摘流量）
  → close(jobs) 或 cancel(ctx)
  → worker 把手里任务做完
  → wg.Wait()
  → close(results)
  → 关闭下游资源（DB、文件、连接）
```

顺序反了会出两类事：先关资源，worker 还在写；先关 `results`，worker 还在发。**关闭是发送方的承诺，不是接收方的清理动作。**

## channel 的事故清单

| 事故 | 触发方式 | 后果 |
|---|---|---|
| 向已关闭的 channel 发送 | 接收方提前 close；多发送者各关各的 | 立即 panic，栈上指不到「谁关的」 |
| 重复 close | 两个 goroutine 都执行 `close(ch)` | panic |
| 接收方 close | 「我读完了，关掉通知发送者」 | 其他发送者下一次发送 panic |
| 同 goroutine 自收自发 | 无缓冲 channel 上先 `ch <- v` 再 `<-ch` | 永久阻塞，死锁 |
| 只发不收 / 只收不发 | 启动协程后没人负责另一端 | goroutine 永久阻塞 → 泄漏 |
| 关闭后仍留在 `select` | 已关闭 channel 永远就绪 | 读到零值、循环空转 |
| 用 `len(ch)` 判断进度 | 把缓冲占用量当剩余任务数 | 提前退出、任务漏跑 |
| 缓冲开太大 | 用 channel 囤积任务 | 掩盖下游故障，积压变内存增长 |
| 用 channel 当锁 | 令牌 channel 保护共享变量 | 比 Mutex 贵 5 倍，死锁形态还更难查 |
| 长循环里 `time.After` | 每轮新建 timer | 分配与调度开销，Go 1.23 前还会积累 |
| `close(nil)` | 把未初始化的 channel 关掉 | panic |
| 发送大对象 | channel 传结构体副本 | 复制 + 逃逸；传指针并明确所有权 |
| 「取最快」结果通道无缓冲 | 赢家退出后输家阻塞在发送 | 每个请求泄漏 N−1 个 goroutine |
| 广播共用一条 channel | 一条消息只被一个订阅者拿到 | 不是广播，是负载均衡；订阅者收不到全量 |

> 💡 `main` 返回时进程结束，所有 goroutine 一起消失；所以「发送没人收」的泄漏在 `main` 里看不出来，只会在长驻服务、库、测试里暴露。排查泄漏要在长跑进程里看 goroutine profile。

## sync 家族：一张表看全

| 原语 | 零值可用 | 一句话语义 | 典型误用 | 版本注意 |
|---|---|---|---|---|
| `Mutex` | 是 | 互斥进入临界区 | 复制、重入、漏解锁 | `TryLock` 自 Go 1.18；实现已下沉到 `internal/sync`，`sync.Mutex` 现在只是包装 |
| `RWMutex` | 是 | 多读单写，写优先 | 递归读锁、读锁里申请写锁 | `TryLock`/`TryRLock` 自 Go 1.18 |
| `WaitGroup` | 是 | 计数归零才放行 | `Add` 晚于 `Wait`、提前复用 | Go 1.25 增加 `Go(f)` |
| `Cond` | 否（要 `NewCond`） | 条件不满足就挂起 | 用 `if` 不复查、丢 Signal | API 二十年未变 |
| `Once` | 是 | 只执行一次 | 递归 `Do`、f 里 panic | Go 1.21 增加 `OnceFunc`/`OnceValue` |
| `Map` | 是 | 并发安全 map | 当通用 map、频繁增删 | **Go 1.24 换了实现**（见下） |
| `Pool` | 是 | 临时对象复用 | 当缓存、当连接池 | 结构自 Go 1.13 未变 |
| `atomic.*` | 是 | 单字原子读改写 | 保护多字段不变量 | Go 1.19 起类型化 API + 正式内存序保证 |

### 把锁放在被保护的数据旁边

结构体里字段一多，「这把锁保护谁」就开始靠猜。可维护的写法是**用空行把锁和被保护字段分到一组**，组外的字段明确不受保护：

```go
type Session struct {
	id string // 只读，不参与加锁

	// mu 保护 cart 与 prefs；别在持锁时调用外部代码
	mu    sync.Mutex
	cart  []Item
	prefs Prefs
}
```

反例是「锁在结构体最上面，字段散落在下面」：review 时必须读完全部方法才能确认哪个字段受保护，漏一个就是数据竞争。字段按大小排序（减少 padding）是次要优化，**可读性优先**。

### 别为了省一行而嵌入 `Mutex`

```go
type Cache struct {
	sync.Mutex // 错：Lock/Unlock 被提升为 Cache 的公开方法
	m map[string]string
}
```

嵌入之后，调用方可以绕过 `Cache` 的任何不变量直接 `c.Lock()`；而且将来想换锁实现、加指标、改成 `RWMutex`，都会破坏公开 API。用命名字段 `mu sync.Mutex`，把「进入临界区」的权力留在类型内部——**锁是实现细节，不是接口**。

## Mutex：两种模式，牺牲的东西不同

`Mutex` 的实现已经移到 `internal/sync`，结构只有两个字：`state` 与 `sema`。`state` 按位复用：

| 位 | 含义 |
|---|---|
| bit0 `mutexLocked` | 已加锁 |
| bit1 `mutexWoken` | 已有唤醒者，Unlock 不必再唤醒别人 |
| bit2 `mutexStarving` | 饥饿模式 |
| bit3 起 | 等待者数量（`state >> 3`） |

| 模式 | 谁能拿到锁 | 触发/退出 | 牺牲了什么 |
|---|---|---|---|
| **正常模式** | 被唤醒的等待者与新来的 goroutine **重新竞争**，新来的通常赢（它正在 CPU 上跑） | 默认 | 尾部延迟：等待者可能被反复插队 |
| **饥饿模式** | 锁**直接交接**给队首，新来的不自旋、不抢，直接排队尾 | 等待超过 `starvationThresholdNs = 1e6`（1ms） | 吞吐：交接要求严格排队 |
| 退出饥饿 | — | 队首等到锁后发现「队里只剩自己」或「等待 < 1ms」 | — |

> 🔑 **正常模式优化吞吐，饥饿模式保护 P99**；1ms 是 Go 认定「你被饿着了」的阈值，不是调度精度。

这也解释了为什么 `Mutex` **不记录持有者**：它的语义只有「进入/离开临界区」，没有「谁进来了」。所以它天生不可重入，也校验不了「你是不是持有者」。

## Mutex 的四类事故

| 事故 | 触发方式 | 后果 |
|---|---|---|
| **Lock/Unlock 不成对** | 多分支提前 return 漏写；重构删掉 Unlock；把 Unlock 误写成 Lock | 锁永不释放 → 死锁；或 Unlock 未加锁的锁 → `fatal error` |
| **复制已使用的 Mutex** | 值接收者、按值传参、写进 struct 字面量 | 副本带着「已加锁」状态各锁各的，保护完全失效 |
| **重入** | 持锁函数调用同样要加锁的函数 | 永久阻塞（自己等自己） |
| **环路死锁** | 两个 goroutine 各持一把再请求对方的锁 | 双方永久等待 |

**事故一：用 `defer` 把「成对」变成结构约束**

```go
func (s *Store) Add(k string, v int) {
	s.mu.Lock()
	defer s.mu.Unlock() // 成对、紧凑；分支再多也不会漏
	if s.closed {
		return // 关键：提前返回也有 defer 兜底
	}
	s.m[k] = v
}
```

> ⚠️ Go 1.27 实测：`mu.Unlock()` 未加锁时输出 `fatal error: sync: unlock of unlocked mutex`，**不是可 recover 的 panic**。早期资料里写的「panic」已经过时——它无法被 `recover` 接住，进程直接退出。

**事故二：值接收者把锁复制了**

```go
type counter struct {
	mu sync.Mutex
	n  int
}

func (c counter) Inc() { // 值接收者：每次调用复制一份 counter，包括锁
	c.mu.Lock()
	c.n++
	c.mu.Unlock()
}
```

本机实测：1000 个 goroutine 各调一次 `Inc`，`c.n` 仍是 **0**（期望 1000）——每次都在副本上自增。`go vet` 能直接抓住：

```
main.go:60:9: Inc passes lock by value: demo.counter contains sync.Mutex
```

同一个包里复制 `WaitGroup` 也会被同一条检查抓住（`copies lock value ... contains sync.noCopy`）。

**事故三与四：重入与环路**，本质都是「等待一个不可能到来的释放」。公开事故清单里 Docker #34881（swarm 初始化提前 return 漏解锁）、Docker #36114（持 `svm` 锁再调加锁的 `hotRemoveVHDsAtStart`，重入死锁）、etcd #10419（`Store` 持锁调 `Compact`，而 `Compact` 内部又加锁）都是这两类的实例。

破坏死锁四条件（互斥、持有并等待、不可剥夺、环路等待）最便宜的一条：**全局锁序**——任何路径都按固定顺序加锁；其次是「持锁不调用外部代码」。

## RWMutex：一个字段两用

| 字段 | 取值 | 含义 |
|---|---|---|
| `readerCount` | 正 | 当前活跃读者数 |
| `readerCount` | 负 | 有写者在排队或持有：值 = 活跃读者数 − `rwmutexMaxReaders`（常量为 `1<<30`） |
| `readerWait` | ≥ 0 | 写者还需等多少个活跃读者退出 |

加写锁时把 `readerCount` 减去 `1<<30` 变负，此后**新读者一律阻塞**；最后一个 `RUnlock` 把 `readerWait` 减到 0 才唤醒写者。

三条重入死锁，一条比一条隐蔽：

| 形态 | 场景 | 结果 |
|---|---|---|
| 写锁重入 | 持 `Lock` 的函数再调 `Lock` | 死锁（内部是 Mutex） |
| 读锁升级 | 持 `RLock` 时调 `Lock` | 读者等写者、写者等读者 → 死锁 |
| **递归读锁** | `RLock` 里再 `RLock`，中间有写者插队 | 第二个 `RLock` 被排队的写者挡住，而第一个 `RLock` 等它返回 → 死锁 |

第三条是 Go 文档明写禁止的：**`RWMutex` 不允许递归读锁**，也不允许升降级。它有写优先（write-preferring）语义，所以「写饥饿」被避免，代价是「读饥饿」可能反转——高写频率下读者会被持续挡在门外。

> 🔑 **RWMutex 只在「临界区里有实际工作」时才划算**：本机 8 核实测，空临界区的只读场景 RWMutex 77ns、Mutex 85ns（差距不大，因为 `readerCount` 的原子加同样争用同一缓存行）；9:1 读写混合才拉开到 55ns vs 105ns。临界区越短，RWMutex 的额外记账越难赚回来。

## WaitGroup / Cond / Once：三个等待原语

### WaitGroup：Add 必须发生在 Wait 之前

```go
var wg sync.WaitGroup
for _, u := range urls {
	wg.Add(1) // 在启动 goroutine 之前
	go func(u string) {
		defer wg.Done()
		fetch(u)
	}(u)
}
wg.Wait()
```

把 `Add(1)` 写进 goroutine 里，`Wait` 可能先看到计数 0 而直接返回。本机实测：100 个任务，`Wait` 返回时只完成了 **87 个**（每次运行的数字不同）；`go vet` 会报 `WaitGroup.Add called from inside new goroutine`。Go 1.25 增加 `wg.Go(f)`，把「Add + 启动 + Done」收进一个方法，从 API 上消灭这个错误。

复用规则：**上一轮 `Wait` 返回之后**才能开始下一轮 `Add`；交叉复用会 panic（`sync: WaitGroup is reused before previous Wait has returned`）。官方建议是干脆不重用——新建一个 `WaitGroup` 只有 16 字节，开销可以忽略。

### Cond：唤醒只是「一次复查机会」

```go
mu.Lock()
for len(queue) == 0 { // 必须 for，不能 if
	cond.Wait() // 内部先 Unlock，被唤醒后再 Lock
}
v := queue[0]
queue = queue[1:]
mu.Unlock()
```

`Signal`/`Broadcast` **不排队**：没有等待者时通知直接丢弃。所以「先 Signal 后 Wait」必然丢信号，等的人永久挂起。`Wait` 返回时仍持锁，条件可能已被别人改掉——因此必须用 `for` 反复检查。需要通知全部等待者（关闭队列、配置变更）用 `Broadcast`，且关闭路径上必须广播一次，否则所有等待者饿死。

### Once：只保证「执行一次」，不保证「成功一次」

```go
var once sync.Once
once.Do(func() { initDB() }) // 并发调用时，其余调用者阻塞到 f 返回
```

实现是「一次原子读 + 慢路径加锁 + 双检查」：`done` 只有 0/1 两态，`defer` 在 `f` 返回后置 1。由此推出两个坑：

- `f` **panic 了，`done` 照样置 1**：后续调用直接返回，资源永远是空的（Go 1.21 的 `OnceValue` 同样如此，只是把 panic 值转发给每个调用者）；
- `f` 里**递归调用自己**的 `Do`：第二次 `Do` 在等第一次释放内部锁 → 死锁，不是无限递归。

需要「失败可重试」就别用 `Once`：`OnceValue`/`OnceValues` 也会把返回的 error 一起缓存，同样不重试。要么让 `f` 只做不会失败的事，要么自己用 `Mutex + 状态机`（记录 `done` 与 error，失败时允许重来）。

## sync.Map 与 sync.Pool：两个被误解的类型

### sync.Map：2020 年的经典讲解已经作废

2020 年前后的资料会花一整讲讲 `read` + `dirty` 双 map、`amended` 标志、`misses` 提升——**这套实现从 Go 1.24 起已被替换**为哈希 trie（`internal/sync.HashTrieMap`），release notes 当时给的开关是 `GOEXPERIMENT=nosynchashtriemap`。今天 `sync.Map` 的类型定义只剩：

```go
type Map struct {
	_ noCopy
	m isync.HashTrieMap[any, any] // isync = internal/sync
}
```

结论层面的变化：

| 维度 | 旧实现（≤1.23） | 新实现（≥1.24） |
|---|---|---|
| 读路径 | 命中 `read` 无锁 | 哈希 trie，无锁读 |
| 新 key 写入 | 可能要 O(n) 复制 `read` 到 `dirty` | 无全量复制，写不相交键几乎不争用 |
| 删除 | 延迟删除（`nil`/`expunged` 三态） | 直接删 |
| 适用面 | 只在「只增不删」的缓存里划算 | 读多写少、**写不相交键**都划算 |

本机实测（8 核，1024 个 key）：9:1 读写混合 `sync.Map` 9.4ns vs `map + RWMutex` 47.9ns；每个 goroutine 只写自己的 key 时 108.8ns vs 242.2ns。

> 🔑 但选型建议没变：`sync.Map` 仍是「特化容器」，没有 `Len`，键值都是 `any`，丢了类型安全；**能用普通 map + 锁就别用它**，用它就要说得出「为什么这里的锁争用是瓶颈」。

### sync.Pool：它是池，不是缓存

三层结构：每个 P 一个 `private`（无锁，只有本 P 能取）+ 一个 `shared`（本地 `pushHead`/`popHead`，别的 P 从尾部 `popTail` 偷）+ `victim`（上一轮的副本）。

```go
var bufPool = sync.Pool{New: func() any { b := make([]byte, 0, 4096); return &b }}

func encode(w io.Writer, v any) error {
	bp := bufPool.Get().(*[]byte)
	defer bufPool.Put(bp) // 用完放回；放回的不是「保留」，只是「下次可能还在」
	*bp = append((*bp)[:0], v.(fmt.Stringer).String()...)
	_, err := w.Write(*bp)
	return err
}
```

**每轮 GC 会先丢弃旧 `victim`，再把 `local` 整体降级为 `victim`**——所以一个对象最多跨两轮 GC 存活，之后无声消失。这就是「不能当缓存」的机制原因：不保证命中、没有容量上限、没有淘汰策略。连接池、会话缓存、LRU 都不能用它实现。

本机实测（4KB 缓冲）：每次 `make` 448ns / 4120B / 2 allocs，从 `Pool` 取复用缓冲 8.9ns / 0 allocs——**快约 50 倍、分配归零**。0 alloc 的前提是缓冲没有跨 goroutine 发布；一旦交给会长期持有它的对象，逃逸开销会回来。

## context：一棵可取消的树，不是传值容器

> context 的四个方法只服务一件事：**把「取消 / 截止时间」沿调用树向下传播**；`Value` 是附带的请求域元数据，不是依赖注入，也不是业务参数通道。

### 接口只有四个方法

| 方法 | 返回什么 | 关键事实 |
|---|---|---|
| `Deadline() (time.Time, bool)` | 截止时间；没有则 `ok=false` | 父的 deadline 更早时，子只能更早，不能更晚 |
| `Done() <-chan struct{}` | 取消时关闭的 channel | 可能为 `nil`（`Background`/`WithoutCancel`），`<-nil` 永久阻塞 |
| `Err() error` | `Canceled` / `DeadlineExceeded` / `nil` | 只有 `Done` 关闭后才非 nil |
| `Value(key any) any` | 沿父链查找的值 | 查找是 O(链深)，不是哈希表 |

```go
ctx, cancel := context.WithTimeout(context.Background(), 300*time.Millisecond)
defer cancel() // 必须：释放 timer、把自己从父节点摘掉

select {
case <-ctx.Done():
	return ctx.Err()
case v := <-work:
	return v, nil
}
```

### 取消树：向下传播，不向上

```
Background
  └── WithCancel (请求 A)
        ├── WithTimeout 300ms (查订单)
        │     └── WithValue (trace_id)
        └── WithCancel (查库存)
```

- **父 cancel，所有子都 cancel**：父节点在 `children` 里保存了每个子节点，取消时逐个调用；
- **子 cancel，父不受影响**：子只是把自己从父的 `children` 里删掉；
- `close(done)` 是广播：所有阻塞在 `<-ctx.Done()` 的 goroutine 同时被唤醒。

`Done` 关闭只有四种原因：**手动 `cancel()`、到点、父 context 被 cancel、父 context 到点**。`Context` 本身是并发安全的（`cancelCtx` 用锁和原子变量保护状态），但 `Value` 里放的对象不是——多 goroutine 读写同一个值，仍要自己保证只读或加锁。

### 内部结构：三种 Context，各管一段

Go 1.27 的 `context` 包只有三种核心节点：

| 类型 | 关键字段 | 管什么 |
|---|---|---|
| `cancelCtx` | `done atomic.Value`、`children map[canceler]struct{}`、`err`、`cause`、`mu` | 手动取消、子节点登记与向下传播 |
| `timerCtx` | 内嵌 `cancelCtx` + `timer *time.Timer` + `deadline` | 到点自动 cancel；`cancel()` 会 `timer.Stop()` |
| `valueCtx` | 内嵌 `Context` + `key, val any` | 沿父链查找键值 |

三个实现细节值得知道：

1. **`done` 是懒创建的**：第一次调用 `Done()` 才 `make(chan struct{})`；没人监听就不分配。
2. **取消只发生一次**：`cancelCtx.cancel` 先看 `err` 是否已设置，已取消就直接返回；重复 `cancel()` 安全。
3. **`children` 用 `sync.Mutex` 保护**：取消一个节点要持锁遍历子节点；所以 context 树越宽，一次取消的临界区越长。

`propagateCancel` 决定子节点怎么挂到父节点上：

```go
done := parent.Done()
if done == nil {
	return // 父永远不会取消（Background/WithoutCancel）
}
select {
case <-done:
	child.cancel(false, parent.Err(), Cause(parent)) // 父已取消，子立即取消
	return
default:
}
// 父是 cancelCtx：把自己加进 children
// 父不是：用 AfterFunc 或起一个 goroutine 等父取消
```

> 🔑 **`context` 的取消是「协作式」的**：它只关闭 `Done`、设置 `Err`；不会杀 goroutine、不会中断系统调用、不会终止远端请求。被取消方必须自己监听 `ctx.Done()` 并退出。

### 创建方式：按「谁来决定结束」选

| 构造函数 | 结束条件 | 额外代价（本机实测） | 什么时候用 |
|---|---|---|---|
| `Background()` / `TODO()` | 永不结束 | 0 | 只在 `main`、`init`、测试入口；`TODO` 表示「还没想好放哪个」 |
| `WithCancel(parent)` | 手动 `cancel()` | 55ns，96B，2 allocs | 请求入口、需要提前收工的编排 |
| `WithTimeout(parent, d)` | 到点或手动 | 241ns，272B，4 allocs（含 timer） | 单次下游调用、请求总预算 |
| `WithDeadline(parent, t)` | 到点或手动 | 同上 | 已有绝对截止时间（如上游 header） |
| `WithCancelCause` | 手动，带原因 | 约同 `WithCancel` | 需要区分「用户取消 / 超时 / 上游失败」 |
| `WithTimeoutCause` | 到点，带原因 | 约同 `WithTimeout` | 超时要能查出是谁设的 |
| `WithoutCancel(parent)` | 永不结束 | 极小 | 请求取消后仍要跑完的收尾（审计、释放） |
| `AfterFunc(ctx, f)` | ctx 取消时执行 `f` | 一次注册 | 取消回调（关连接、上报指标），替代「起个 goroutine 等 Done」 |

### 六条使用范式

1. **`ctx` 是第一个参数**：`func Do(ctx context.Context, req *Request) error`。不要塞进 struct、不要存全局。
2. **不要传 `nil`**：没有上下文就传 `context.Background()`；`nil` 会在下游 `ctx.Done()` 时 panic。
3. **谁创建谁 cancel**：`WithCancel`/`WithTimeout` 的调用方负责 `defer cancel()`；即使超时已触发也要调，否则 timer 和父子登记不会释放。
4. **沿调用链传同一个 ctx**：HTTP handler 用 `r.Context()`，下游 DB 用 `QueryContext`，RPC 用同一个 ctx；不要在中途换 `Background()`，否则上游取消传不下去。
5. **长循环里检查 `Done`**：每轮 `select` 一下，或把 ctx 传给阻塞调用；只检查一次不够。
6. **`Value` 只放请求域元数据**：trace_id、租户、调用方 IP；key 用未导出的自定义类型，别用 `string`。

### 超时预算：只能收紧，不能放宽

`WithDeadline` 的语义是「不晚于 d」：如果父的 deadline 更早，子直接继承父的 deadline，**内层设更长的时间不会延长寿命**。这带来两条工程规则：

- **在请求入口算总预算**，往下传剩余时间；不要每层都 `WithTimeout(3s)`，否则最内层可能比总预算还长；
- **区分三种超时**：客户端 `http.Client.Timeout`（含重定向/读 body）、ctx deadline（可被上游取消）、下游自己的超时。三者取最早，别互相替代。

```go
func (h *Handler) GetOrder(ctx context.Context, id string) (*Order, error) {
	ctx, cancel := context.WithTimeout(ctx, 300*time.Millisecond)
	defer cancel()

	// 同一个 ctx 传给 DB / 缓存 / RPC；任何一层慢了，整条链一起收工
	return h.repo.Get(ctx, id)
}
```

### `Value` 的边界：能不用就不用

`Value` 的问题不是性能，是**隐式依赖**：调用方看不到参数，只能靠文档和约定。它的合法用途只有「跨 API 边界、请求域、进程内」的元数据：

| 可以放 | 不要放 |
|---|---|
| trace_id / span_id | 业务实体（order、payment） |
| 租户 / 用户身份 | 可选配置、开关 |
| 调用方 IP、路由 | logger、DB 连接、RPC 客户端 |
| 请求开始时间 | 「为了少传一个参数」的任何东西 |

性能上，`Value` 是沿父链线性查找，链越深越慢（本机实测）：

| 链深 | `Value` 耗时 |
|---|---|
| 1 层 | 3.2 ns/op |
| 4 层 | 11.8 ns/op |
| 16 层 | 46.7 ns/op |

所以：**不要在每个中间件里无脑 `WithValue`**；能合并的合并，能在入口取出来放局部变量的就取出来。高频路径上反复 `ctx.Value` 同一个 key，应该在函数开头取一次。

### 服务端、客户端、存储：接入点在哪

| 场景 | 用什么 | 常见错误 |
|---|---|---|
| HTTP server | `r.Context()` | 自己 `context.Background()`，客户端断开后还在跑 |
| HTTP client | `http.NewRequestWithContext(ctx, ...)` | 只设 `Client.Timeout`，上游取消传不进去 |
| 数据库 | `QueryContext` / `ExecContext` | 用 `Query`，请求取消后 SQL 还在跑 |
| gRPC | 方法第一个参数 `ctx` | 服务端另起 `Background` 调下游 |
| 消息消费 | 消费循环的 ctx（进程级 + 消息级） | 消费协程没有退出路径，停机靠杀进程 |
| CLI / 后台任务 | `signal.NotifyContext` | 用 `os.Exit` 直接退出，收尾不执行 |

### 取消之后：收尾要用「不被取消」的 ctx

请求被取消后，审计日志、释放锁、回滚事务仍然要跑完。这时不能复用已取消的 ctx（下游会立刻返回 `context.Canceled`），要派生一个：

```go
cleanupCtx := context.WithoutCancel(ctx) // 保留 value，不继承取消和 deadline
defer func() {
	_ = audit.Write(cleanupCtx, auditEvent) // 请求失败也要留下记录
}()
```

进程退出时同理：`signal.NotifyContext` 的 ctx 在收到 SIGTERM 时已经取消，`Shutdown` 必须换一个新的超时 ctx：

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
<-ctx.Done()

shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
_ = srv.Shutdown(shutdownCtx) // 不能用上面那个已经取消的 ctx
```

需要「取消时顺手关连接 / 上报指标」时，用 `context.AfterFunc` 注册回调，不用一个常驻 goroutine 等 `Done`：

```go
stop := context.AfterFunc(ctx, func() {
	_ = conn.Close()
})
defer stop()
```

### 优化手段：context 本身也有成本

| 做法 | 收益 | 代价 / 边界 |
|---|---|---|
| 一个请求只建一次 timeout，往下传 | 省掉每层 timer（241ns/4 allocs → 一次） | 内层不能延长，只能收紧 |
| `WithValue` 链保持浅 | 查找从 46.7ns（16 层）降到 3.2ns（1 层） | 别把 Value 当参数包 |
| 循环外取 `done := ctx.Done()` | 少一次 atomic load / 锁 | `Done()` 可能为 nil，先判 |
| 用 `AfterFunc` 代替等待 goroutine | 少一个 goroutine 常驻 | 回调要短，别阻塞 |
| 只在错误路径调 `Cause` | 正常路径零开销 | `Cause` 要 Go 1.20+ |
| `WithoutCancel` 只用于收尾 | 避免「取消后什么都干不了」 | 它不继承 deadline，收尾要自己设超时 |

### context 反模式

| 反模式 | 后果 |
|---|---|
| `func F(ctx context.Context)` 里又 `context.Background()` | 上游取消断链，请求泄漏 |
| `WithTimeout` 后不 `cancel` | timer 不释放，父子登记不摘除，长跑进程内存上涨 |
| 把 ctx 存进 struct / 全局变量 | 生命周期混乱，无法按请求取消 |
| 把 ctx 序列化 / 存 DB / 放缓存 | context 是运行时对象，不可持久化；value 也不保证可序列化 |
| `WithValue` 塞业务参数 | 隐式依赖、类型不安全、review 看不到 |
| `WithValue` 用 `string` key | 跨包冲突，A 包覆盖 B 包的值 |
| 内层 `WithTimeout` 比外层还长 | 以为延长了，实际仍受父 deadline 约束 |
| `select { case <-ctx.Done(): default: }` | 没取消时立刻走 default，变成忙轮询 |
| 用已取消的 ctx 做收尾 | 审计/回滚直接失败，故障现场丢失 |
| 认为 cancel 会杀远端请求 | 远端还在跑，只是本地不再等 |
| `Background().Done()` 直接 `<-` | `Done()==nil`，永久阻塞 |

## atomic：单字、顺序与缓存行

atomic 的保证只有一句：**这一次读或写不可分割，并且所有原子操作排成一个全序**。它不提供事务，也不保护多字段之间的不变量。

### 六个操作，一张表

| 操作 | 典型签名 | 语义 | 什么时候用 |
|---|---|---|---|
| `Add` | `AddInt64(addr *int64, delta int64) int64` | 原子加，返回新值 | 计数器、序号 |
| `CompareAndSwap` | `CompareAndSwapInt64(addr *int64, old, new int64) bool` | 相等才换，返回是否成功 | 无锁状态机、乐观更新 |
| `Swap` | `SwapInt64(addr *int64, new int64) int64` | 换入新值，返回旧值 | 交换配置、取走计数 |
| `Load` | `LoadInt64(addr *int64) int64` | 原子读 | 读标志、读指针 |
| `Store` | `StoreInt64(addr *int64, val int64)` | 原子写 | 发布不可变对象 |
| `Value` / `Pointer` | `Value.Load/Store`、`Pointer[T].Load/Store` | 原子存取任意值 / 类型化指针 | 配置快照、懒初始化 |

Go 1.19 起有类型化 API，优先用它，别再写 `atomic.LoadInt64(&x)`：

```go
var n atomic.Int64
n.Add(1)
n.Store(42)
old := n.Swap(7)
n.CompareAndSwap(7, 8)
```

### CAS：唯一能表达「条件更新」的操作

```go
// 状态机：只有小于 closed 才允许 +1，一次 CAS 决定迁移
for {
	old := state.Load()
	if old >= closed {
		return false
	}
	if state.CompareAndSwap(old, old+1) {
		return true
	}
}
```

CAS 循环的三条纪律：

1. **重读放在循环里**：`old` 必须在每次失败后重新 `Load`，不能复用；
2. **失败要能退出**：加最大重试次数或 ctx 检查，否则高争用下可能长时间空转；
3. **副作用放在 CAS 成功之后**：CAS 只负责状态迁移，别在失败分支里写共享数据。

### 内存序：Go 1.19 之后有正式保证

2020 年前后的资料常说「atomic 没有规范层面的顺序保证，别用它传递多变量顺序」。**这条在 Go 1.19 修订内存模型后已经改变**：原子操作现在表现为某个顺序一致（sequentially consistent）的顺序，并建立 synchronizes-before 关系。

但这不等于「atomic 能保护多字段」：

```go
// 错：两个字段各自原子，合起来仍然不是原子的
balance.Add(-100)
version.Add(1)
// 另一个 goroutine 可能看到「钱扣了、版本没变」
```

要整体替换多字段状态，用「不可变结构体 + `atomic.Pointer[T]` 一次换指针」：

```go
type Config struct {
	Timeout time.Duration
	Retries int
}

var cfg atomic.Pointer[Config]

func update(c *Config) { cfg.Store(c) }
func load() *Config  { return cfg.Load() }
```

读者拿到的是某一版完整快照，不会看到「新 Timeout + 旧 Retries」。前提是 `Config` 发布后不再修改。

### 同一段 atomic，在 ARM64 上更贵

Go 1.19 的 “顺序一致” 是**语言层面的承诺**，不是硬件免费送的。x86 的 TSO 模型里，硬件已经替大部分顺序兜了底，同步开销主要落在缓存行争用上；ARM/POWER 为了功耗与性能选了比 TSO 更**宽松**的模型，普通读写可以乱序得更自由。后果很直接：**Go 的 seq-cst 原子在 ARM64 上要编译成屏障指令**，同一段 `atomic.Add` / `atomic.CompareAndSwap`，在 Apple Silicon、Graviton 这类 ARM64 机器上的指令序列和 x86 不是一回事。

本节所有数字都来自 Apple M1（arm64）：单原子 7.1ns（P=1）→ 38.3ns（P=8）、分片对齐 5.8ns。它们**不能直接搬到 x86 服务器**，也不能假设方向不变——x86 上松散内存序的代价小，但缓存行争用、NUMA 距离、主频又各不相同。

> 🔑 判据：**跨架构的性能结论必须重测**。同一份 benchmark 至少要在目标架构上跑一次 `-cpu=1,2,4,8`；把 M1 的 ns/op 当 “ARM 通用值”、把 x86 的当 “服务器通用值”，两种都不成立。内存序假设错不是慢一点，而是正确性问题，见 [15.7 竞态检测与数据竞争](15.7-竞态检测与数据竞争.md)；优化的先后顺序见 [34.4 优化手段](../../L3-质量属性/34-性能/34.4-优化手段.md)。

### 对齐与撕裂：什么时候普通赋值不是原子的

单核机器上，对齐地址的普通写通常一条指令完成；多核机器还要解决缓存一致性、指令重排、可见性，普通读写不再够用。两个实践结论：

- **64 位原子操作要求 8 字节对齐**：在 32 位平台（386/ARM）用 `*int64` 做原子操作时，要把它放在分配结构体/切片/数组的第一个字；类型化 `atomic.Int64` 已经处理了对齐；
- **不要混用原子和普通读写**：同一个变量，一部分代码 `atomic.Load`，另一部分直接 `x++`，仍然是 data race，`-race` 会报。

### 性能：原子不是「免费」，缓存行才是单位

本机 8 核实测：

| 操作 | P=1 | P=8 |
|---|---|---|
| 单个 `atomic.Int64` 自增 | 7.1 ns/op | 38.3 ns/op |
| 8 分片、每片 64B 对齐 | — | **5.8 ns/op** |
| 8 分片、原子变量紧挨着 | — | 42.9 ns/op |
| `sync.Mutex` 保护自增 | 16.8 ns/op | 83.0 ns/op |

两个反直觉点：

- **分片不 padding，可能比单变量还慢**：8 个独立原子变量落在同一缓存行，每次写都让其他核的缓存行失效（false sharing），42.9ns 比单原子 38.3ns 还差；
- **对齐后差 6.6 倍**：38.3ns → 5.8ns。优化共享写入的第一步不是换原语，是**让不同核写不同缓存行**。

```go
type padded struct {
	_ [56]byte // 56 + 8 = 64B，按缓存行隔开
	n atomic.Int64
}

type ShardedCounter struct {
	shards [8]padded
}

func (c *ShardedCounter) Inc(shard int) { c.shards[shard&7].n.Add(1) }
```

> ⚠️ 64B 是常见缓存行大小；部分 CPU 是 128B。跨平台库要么按 `cpu.CacheLinePad` 的思路留足，要么用 benchmark 验证，不要拍脑袋写 56。

### atomic 的反模式

| 反模式 | 后果 |
|---|---|
| 用 `atomic` 保护多字段不变量 | 单字原子 ≠ 代码块原子，仍会读到中间态 |
| 原子变量混普通读写 | 仍是 data race；`-race` 会报 |
| `atomic.Value` 先后存不同类型 | 第二次 `Store` 直接 panic（类型必须一致） |
| 把 `atomic.Int64` 复制来复制去 | 复制后各改各的，和复制 Mutex 同类问题 |
| 对未对齐的 `*int64` 做 64 位原子 | 32 位平台可能撕裂；用类型化原子或保证首字对齐 |
| 用 atomic 做「先检查再修改」的多步逻辑 | 检查和修改之间会被插入；要 CAS 或锁 |
| 认为 atomic 一定比 Mutex 快 | 高争用下同样退化（7.1→38.3ns）；分片才是数量级手段 |

## 并发优化：从减少共享开始

并发优化有一条固定顺序，跳步就会白忙。第 0 条不是性能手段，是成本判断：**能不并发就不并发**。

- `http.ListenAndServe` 直接在主 goroutine 里跑，不需要「起一个 goroutine + `select{}` 阻塞」；后者的唯一效果是让代码更难读、更难优雅退出。
- 库函数不要偷偷起 goroutine 再返回 channel：调用方无法决定要不要并发、无法暂停/恢复、也拿不到 error。`filepath.Walk(root, fn)` 这种「普通函数 + 回调」的形态，让调用方自己决定是否把回调放进 goroutine，才是可组合的。

| 顺序 | 手段 | 本机效果 | 边界 |
|---|---|---|---|
| 1 | **减少共享**：分片、线程本地聚合、批量合并 | 单原子 38.3ns → 分片对齐 5.8ns（6.6×） | 分片要 padding，否则 false sharing |
| 2 | **缩小临界区**：锁内只留内存操作，IO/序列化移到锁外 | 取决于临界区占比 | 锁外操作要保证不破坏不变量 |
| 3 | **换原语**：atomic / RWMutex / channel | atomic 7.1（P=1） vs Mutex 16.8（P=1） vs channel 74（P=8 交接） | 换原语通常只快 2–5 倍，且改变语义 |
| 4 | **池化 / 批处理**：`sync.Pool`、合并写 | 4KB 分配 448ns → 8.9ns | 池不是缓存；批处理增加延迟 |

> ⚠️ 协程之间的“实时共享”是另一种单点：协程再轻，只要它们要同步同一段内存，就会退化成“线程 × 协程”级别的锁竞争；`sync.Map` 不是解药，只是把锁换成了更复杂的并发结构。**如果业务必须让海量协程看到同一份实时状态，正确的方向往往不是换更快的锁，而是把这份状态移出进程**——用 Redis/单线程服务做“排队 + 串行化”，让协程只做网络 I/O，不再共享内存。这也是“找出单点、进行拆分”在运行时层的投影：进程内共享内存是单点，拆法是把协调外移。

### 先定位，再动手

```bash
go test -run '^$' -bench . -benchmem -benchtime=300ms -count=3
go test -run '^$' -bench . -mutexprofile=mutex.out
go tool pprof -top -sample_index=contentions mutex.out
```

- 先看 `benchstat`/中位数，确认「真的慢」；
- 再看 mutex profile：是锁等待、还是 CPU 本身；
- 最后才决定「减少共享 / 缩小临界区 / 换原语」。

> 🔑 **不要用 channel 做锁，也不要用 atomic 做事务**；两者都是「用错语义换性能」，最后问题会从性能变成正确性。

## 落到数字：本机实测

环境：Go 1.27.1、Apple M1（8 核）、macOS 15.6；`go test -bench . -benchmem -benchtime=300ms -count=3`，取三次中位数。

先说清楚 `CounterMutex` 是什么——它就是配套示例里的这个结构体和基准函数：

```go
type CounterMutex struct {
	mu sync.Mutex
	n  int64
}

func (c *CounterMutex) Inc() {
	c.mu.Lock()
	c.n++
	c.mu.Unlock()
}

func BenchmarkCounterMutex(b *testing.B) {
	var c CounterMutex
	b.RunParallel(func(pb *testing.PB) { // -cpu=N 决定这里的并发 goroutine 数
		for pb.Next() {
			c.Inc()
		}
	})
}
```

同一份自增，三种同步方式随核数退化（`-cpu=1,2,4,8`，中位数）：

| P | `CounterMutex` | `CounterAtomic` | `CounterChannel` |
|---|---|---|---|
| 1 | 16.8 ns/op | 7.1 ns/op | 28.7 ns/op |
| 2 | 47.3 ns/op | 16.6 ns/op | 37.7 ns/op |
| 4 | 74.4 ns/op | 21.3 ns/op | 54.0 ns/op |
| 8 | 83.0 ns/op | 38.3 ns/op | 70.3 ns/op |

`CounterChannel` 是「一个 goroutine 独占计数器、channel 只负责送自增指令」：所有权交接是对的，但单消费者把所有写操作又串回一个核。它的退化比 Mutex 平缓（28.7→70.3ns），因为竞争被转成了排队；但绝对单价更高，上限也由那个消费者决定——**channel 解耦的是执行，不是吞吐**。

其余原语的单价（默认 8 核）：

| 基准 | 结果 | 说明 |
|---|---|---|
| `Mutex` 无竞争 | 13.8 ns/op | 单 goroutine 成对 Lock/Unlock |
| 有缓冲 channel 交接（cap=1024） | 74 ns/op | 生产者、消费者各付一次收发 |
| 无缓冲 channel 交接 | 186 ns/op | 双方必须同时就绪 |
| `RWMutex` 只读 vs `Mutex` 只读 | 77 vs 85 ns/op | 空临界区，差距有限 |
| `RWMutex` 9:1 混合 vs `Mutex` | 55 vs 105 ns/op | 读多写少才划算 |
| `sync.Map` vs `map+RWMutex`（9:1） | 9.4 vs 47.9 ns/op | 1024 个 key |
| `sync.Map` vs `map+RWMutex`（各写各 key） | 108.8 vs 242.2 ns/op | 写不相交，无全量复制 |
| 4KB 缓冲 `make` vs `sync.Pool` | 448 vs 8.9 ns/op；4120B vs 0B | 缓冲不跨 goroutine 发布 |
| `context.WithCancel` + cancel | 55 ns/op；96B；2 allocs | 创建后立即取消 |
| `context.WithTimeout` + cancel | 241 ns/op；272B；4 allocs | 含一个 timer，必须 cancel |
| `ctx.Value` 链深 1 / 4 / 16 | 3.2 / 11.8 / 46.7 ns/op | 沿父链线性查找 |
| 8 分片计数（64B 对齐） | 5.8 ns/op（P=8） | 对比单原子 38.3ns |
| 8 分片计数（紧挨着） | 42.9 ns/op（P=8） | false sharing，比单原子还慢 |

完整代码与原始输出在仓库 [tools/examples/15.6-concurrency](../../../tools/examples/15.6-concurrency/README.md)，`go run .` 跑 channel 用法，`go test -bench ...` 复现上面的数字。

```bash
cd tools/examples/15.6-concurrency
go test -run '^$' -bench CounterMutex -cpu=1,2,4,8 -benchtime=300ms -count=3
go test -run '^$' -bench . -benchmem -benchtime=300ms -count=3
go test -race ./...                          # 竞态检测，见 15.7
go vet ./...                                 # copylocks：抓「复制带锁结构体」
```

观察到的四条规律：

1. **无竞争时锁很便宜**（13.8ns），争用时贵 6 倍——优化方向是减少共享，不是换更快的锁；
2. **同一变量的原子操作同样会被缓存行争用拖慢**（7.1→38ns），分片（striped）才是数量级手段，见 [34.4 优化手段](../../L3-质量属性/34-性能/34.4-优化手段.md)；
3. **channel 的单价是锁的 5 倍以上**（74ns vs 14ns），它买的是「所有权交接 + 背压 + 广播」，不是吞吐；
4. **`sync.Map` 的优势来自「读不加锁、写不相交」**，键集合频繁变化或需要遍历时优势消失。

## 反模式

| 反模式 | 后果 |
|---|---|
| 多分支函数里手写 `Unlock` | 某条路径漏写即死锁；用 `defer` |
| 值接收者 / 按值传参带锁结构体 | 锁被复制，保护失效；`go vet` 能抓 |
| 持锁调用会再加锁的函数 | 重入死锁，压测不长跑发现不了 |
| 两把锁在不同路径上乱序获取 | 环路死锁，必现于高并发 |
| `wg.Add(1)` 写在 goroutine 里 | `Wait` 提前返回，任务漏跑 |
| `Cond` 用 `if` 复查条件 | 被唤醒后条件已变，继续执行错逻辑 |
| `Once` 里递归 `Do` / 在 `Do` 里 `defer once.Do` | 自我等待，死锁 |
| 用 `sync.Pool` 当缓存/连接池 | GC 后对象无声消失，拿到失效连接 |
| `context.Value` 传业务参数 | 依赖隐式、类型不安全、无法静态检查 |
| 用 `atomic` 保护多字段不变量 | 单字原子 ≠ 代码块原子，竞争仍在 |
| 用 channel 当锁（令牌） | 比 Mutex 慢 5 倍且死锁难查；需要超时/背压就用信号量，别拿令牌保护状态 |
| 海量 goroutine 共享一份状态，指望 `sync.Map` 救 | 锁竞争与缓存行争用把 CPU 吃满，吞吐反降；应分片或把状态移出进程 |
| 接收方 `close` channel | 其他发送者下一次发送直接 panic |
| 关闭后的 channel 留在 `select` 里 | 永远就绪，读到零值、循环空转 |
| `nil` channel 上执行 `close` | 直接 panic，且与「nil 用来禁用分支」的用法混淆 |
| 用无缓冲 channel 在同 goroutine 自收自发 | 永久阻塞，死锁 |
| 把 channel 当无界队列囤任务 | 积压变内存增长，故障时雪崩 |
| 下游函数里重新 `context.Background()` | 上游取消断链，请求继续跑 |
| `WithTimeout` 后不 `cancel` | timer 不释放，长跑进程资源上涨 |
| `WithValue` 塞业务实体 / 用 string key | 隐式依赖、跨包冲突 |
| 分片计数不做 padding | false sharing，可能比单变量还慢 |

## 五条铁律

> 🔑 **谁持有谁释放，成对紧凑写**；能用 `defer` 就别手写，能封装成方法就别把锁暴露给调用方。

> 🔑 **每个等待点都必须可取消**：channel 收发、`Lock`、`Wait`、`Acquire` 都可能永久阻塞——没有超时/取消的等待点，会把「慢」升级成「挂」。

> 🔑 **有状态的原语不可复制**：`Mutex`、`RWMutex`、`WaitGroup`、`Cond`、`Once`、`Pool` 都是指针语义；`go vet` 进 CI 是底线，不是可选项。

> 🔑 **锁保护的是不变量，不是代码行**：先写下「哪个不变量被保护」，再决定临界区边界；说不出来，就说明这把锁只是安慰剂。

> 🔑 **channel 谁发送谁关闭，接收方永不关闭**；多发送者就把关闭权收拢到一个 closer——关闭是发送方对「不会再有数据」的承诺。

## 自检

**Q1** `Mutex` 为什么需要「正常/饥饿」两种模式？1ms 这个数字在防什么？

▸ 答案：正常模式下被唤醒的等待者要和新来的 goroutine 重新竞争，而新来的正在 CPU 上跑、通常赢，于是等待者被反复插队——吞吐高但尾延迟无界。等待超过 1ms（`starvationThresholdNs = 1e6`）就切到饥饿模式：锁直接交接给队首，新来的不许抢、不许自旋，只排队尾。1ms 是「你已经被饿着了」的判定阈值，用来在吞吐和 P99 之间做取舍。

**Q2** 复制一个含 `sync.Mutex` 的结构体，为什么是「保护失效」而不是「变成两把锁各自保护」？

▸ 答案：复制发生时锁可能正处于「已加锁」状态，副本继承了这个状态；更根本的是两个副本此后保护的是**两份不同的数据**（字段也一起被复制了）。于是原对象的写入没有任何互斥、副本上的修改丢失（本机实测 1000 次自增结果是 0）。`go vet` 的 `copylocks` 检查会报 `passes lock by value`，CI 里必须开。

**Q3** `RWMutex` 为什么禁止「读锁升级成写锁」和「递归读锁」？写优先又带来什么代价？

▸ 答案：升级时读者持有 `RLock` 等写者释放，而写者要等所有读者（包括它）退出——互等死锁。递归读锁更隐蔽：`RLock` 里再 `RLock`，若中间有写者排队，`readerCount` 已为负，第二个 `RLock` 阻塞，而第一个还在等第二个返回。写优先（阻塞的写者挡住新读者）消除了写饥饿，代价是高频写时读者被持续挡住，可能反转为读饥饿。

**Q4** `WaitGroup.Add` 为什么不能放在 goroutine 里？Go 1.25 的 `wg.Go` 解决了什么？

▸ 答案：`Wait` 只判断「计数是否为 0」，`Add` 还没执行时计数为 0，`Wait` 立即返回（本机实测 100 个任务只等到 87 个）。`wg.Go(f)` 把 `Add(1)`、`go`、`Done` 收进一个方法，调用点就不可能把顺序写反；`f` panic 时它**故意不调用 `Done`** 而直接重新 panic——让 panic 先杀死进程，避免 `Wait` 与致命 panic 竞争；代价是计数不会归零。

**Q5** `Cond.Signal` 为什么会「丢」？为什么 `Wait` 必须放在 `for` 里？

▸ 答案：通知不排队——没有等待者时 `Signal` 什么也不做，所以「先 Signal 后 Wait」的等待者永远等不到下一次通知。而 `Wait` 返回只代表「被叫醒了一次」，条件可能已被别的 goroutine 改回不成立，所以必须用 `for` 重新检查；用 `if` 就会在条件不满足时继续往下跑。

**Q6** 2020 年那套「`sync.Map` 用 read/dirty 双 map」的讲解，今天还能照搬吗？选型结论变了吗？

▸ 答案：实现已经变了：Go 1.24 起 `sync.Map` 是 `internal/sync.HashTrieMap`，`read`/`dirty`/`amended`/`misses`/`expunged` 全部不存在，「新 key 写入要 O(n) 复制」这个缺点也随之消失（本机实测「各写各 key」108.8ns vs `map+RWMutex` 242.2ns）。但选型结论没变：它仍是特化容器、没有 `Len`、键值是 `any`，只有在「读多写少 / 写不相交键」且锁争用确实是瓶颈时才值得用。

**Q7** `sync.Pool` 为什么不能当缓存用？「对象最多活两轮 GC」是什么意思？

▸ 答案：每轮 GC 的 `poolCleanup` 先丢弃旧 `victim`，再把 `local` 降级为 `victim`——所以对象经历「local → victim → 被丢弃」两轮后必然消失，且全程没有通知。它没有容量上限、没有淘汰策略、不保证命中率；连接、会话这类「必须还在」的对象一旦被清掉就是故障。它的定位是「降低分配次数与 GC 压力」，不是「保留对象」。

**Q8** `atomic` 能替代 `Mutex` 保护「余额 + 版本号」这种多字段状态吗？Go 1.19 之后它的保证有什么变化？

▸ 答案：不能。原子操作保护的是「这一次读或写」不可分割，多字段之间的不变量仍会被打破（`atomic` 没有事务语义）。要整体替换就改成「不可变结构体 + `atomic.Pointer` 一次换指针」。Go 1.19 修订内存模型后，原子操作有了正式的顺序一致语义与 synchronizes-before 保证——「看不见」的问题解决了，但「不变量」的问题并没有。

**Q9** `close(ch)` 之后，缓冲里的数据还在吗？接收方拿到的 `ok=false` 到底表示什么？

▸ 答案：还在，而且**必须先读完**。关闭只改变「还能不能发」，不改变「还能不能收」：接收方会先取完缓冲里的元素，全部取完后才返回零值 + `ok=false`。所以 `ok=false` 表示「发送方已承诺不再发送、且缓冲已空」，不是「刚收到这条无效」。关闭权必须留在发送方：接收方提前关闭，仍在发送的发送者下一次发送就会 panic。

**Q10** 用带缓冲 channel 做信号量，为什么「先占槽位再起 goroutine」和「在 goroutine 里占槽位」不是一回事？

▸ 答案：前者把**排队也挡在 goroutine 之外**：槽位满了，提交侧就阻塞，系统里最多只有 `cap` 个任务 goroutine。后者每个任务都先起 goroutine 再去抢槽位，运行数虽然被限住，但排队中的 goroutine 数量没有上限——高并发下先把内存和调度器压垮，限流形同虚设。

**Q11** 为什么已关闭的 channel 必须从 `select` 里拿掉（置 `nil`），而不是留着 `case v, ok := <-ch` 判断 `ok`？

▸ 答案：因为已关闭的 channel **永远就绪**：如果 `select` 里还有别的阻塞分支，`select` 会随机在「已关闭的零值接收」和其他就绪分支之间选，业务逻辑会被零值污染；如果只有它一个分支，就会立刻返回、循环空转。判断 `ok` 只能拦住「把零值当数据用」，拦不住「空转」和「随机命中」。置 `nil` 让这个分支永久不就绪，才是真正的「从集合里删除」。

**Q12** `time.After` 在长跑循环里为什么被诟病？Go 1.23 之后还成立吗？

▸ 答案：`time.After` 每调用一次就新建一个 `Timer`。Go 1.23 之前，未触发的 timer 不会被 GC，循环里每轮都留一个，长跑进程内存持续上涨；Go 1.23 起未引用的 timer 可以被回收，内存问题缓解，但「每轮一次分配 + 调度」的成本仍在，超时精度也依旧受调度影响。所以长循环仍推荐 `NewTimer` + `Stop`（排空）+ `Reset` 复用同一个 timer。

**Q13** 子 context 被 cancel，父 context 会怎样？反过来呢？`Done()` 关闭代表什么？

▸ 答案：子 cancel 只影响自己和自己的后代，父不受影响；父 cancel 会沿 `children` 向下取消所有子节点。`Done()` 关闭只代表「这个 context 结束了」，不代表远端工作停止——被调用方必须自己监听 `ctx.Done()` 才会退出。

**Q14** `WithTimeout` 已经会自动取消，为什么还必须调用 `cancel()`？

▸ 答案：超时只覆盖「到点」这一条路径；如果操作提前完成，timer 仍然活着，子节点仍挂在父的 `children` 里。`cancel()` 会停止 timer、把自己从父节点摘除，并保证重复调用安全。本机创建 + 立即 cancel 一个 `WithTimeout` 约 241ns、272B、4 allocs，比 `WithCancel` 的 55ns/96B 贵，所以更不该在循环里随手创建。

**Q15** `context.Value` 为什么越深越慢？什么数据才该放进去？

▸ 答案：`valueCtx` 只保存一个键值对，查找时沿父链逐层比较，是 O(链深)；本机 1/4/16 层分别约 3.2/11.8/46.7ns。它只适合请求域元数据（trace_id、租户、身份、调用方 IP），key 用未导出的自定义类型；业务实体、配置、logger、DB 连接都应该显式传参。

**Q16** worker pool 里 `jobs` 和 `results` 分别该由谁关闭？为什么？

▸ 答案：`jobs` 由生产者关闭——只有它知道「不会再有任务」；`results` 由单独的 closer 在 `wg.Wait()` 之后关闭——worker 不知道其他 worker 是否还在发。接收方永远不关闭；worker 只消费和发送。关闭顺序反了，就会「资源先关、worker 还在写」或「results 先关、worker 还在发」。

**Q17** 「多副本取最快」为什么结果 channel 要设置成 `cap = 副本数`？无缓冲会怎样？

▸ 答案：第一个成功后主 goroutine 取消其余副本并不再接收；无缓冲时输掉的副本会永久阻塞在 `ch <- result`，每个请求泄漏 N−1 个 goroutine。容量 = 副本数（或发送时 `select` 带 `ctx.Done()`）保证输家也能把结果写出去并退出；主 goroutine 最好把剩余结果收完再返回。

**Q18** 一个发布者、多个订阅者的广播，为什么不能共用一个 channel？慢消费者该怎么处理？

▸ 答案：共享一个 channel 是「负载均衡」：一条消息只会被一个订阅者拿到，不是广播。广播要给每个订阅者一个独立 channel。慢消费者不能阻塞发布者：按业务选丢弃新消息、丢最旧、断开重连或落盘补拉，并暴露 `len(ch)`、丢弃数、最后投递延迟；「阻塞发布者」几乎总是错的。

**Q19** 同一段 `atomic.Add`，能在 Apple M1 和一台同代 x86 服务器上共用一份 ns/op 结论吗？

▸ 答案：不能。x86 是 TSO，硬件替大部分顺序兜了底；ARM/POWER 是更宽松的模型，Go 的 seq-cst 原子在 ARM64 上要编译成屏障指令——同一段源码在两种架构上的指令序列本就不同，价格自然不同。本节所有数字都带架构标签（M1/arm64），跨架构引用必须先在同一份 benchmark 上重测 `-cpu=1,2,4,8`。
