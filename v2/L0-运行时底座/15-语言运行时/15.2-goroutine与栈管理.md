# 15.2 goroutine 与栈管理

## 一句话

> goroutine 的关键不是 “轻量线程” 这个比喻，而是**用户态栈可以按需增长**：初始只有 2KB，不够就把整个栈复制到更大的位置并修正指针——代价是复制，收益是百万级并发。

## 栈的一生

| 阶段 | 大小 | 动作 |
|---|---|---|
| 创建 | 2KB | 偷懒到极致，只够跑一个简单调用 |
| 增长 | 翻倍（4KB → 8KB …） | 分配新栈、复制旧内容、**调整所有指向栈的指针**、释放旧栈 |
| 上限 | 1GB（64 位，默认） | 超过即 `stack overflow` 崩溃 |
| 收缩 | GC 时 | 栈过大且利用率低会缩回 |

栈复制的成本与栈大小成正比，所以 “在热路径里创建超大局部变量” 会让每次增长都变贵。栈太大还会直接逃逸到堆（编译器判断）。

## 状态机：G 不是 “要么跑要么睡”

| 状态 | 什么时候进入 | 谁把它移走 |
|---|---|---|
| `_Grunnable` | `go` 创建后、`gopark` 被唤醒、系统调用返回 | 调度器 `execute` |
| `_Grunning` | 被 M 选中执行 | 阻塞/抢占/让出/退出 |
| `_Gsyscall` | 进入阻塞系统调用 | 系统调用返回或 handoff |
| `_Gwaiting` | channel、锁、netpoll、timer 等阻塞 | 条件满足后 `goready` |
| `_Gpreempted` | 被异步抢占 | 重新放回运行队列 |
| `_Gdead` | 函数执行完（`goexit`） | 进入 `gFree` 复用 |

三个容易混淆的边界：

- **`_Gwaiting` 不是 “永远不跑”**：channel 有数据、锁释放、网络可读，都会把它改回 `_Grunnable`；
- **`_Gsyscall` 的 G 仍占着 M，但不占 P**：P 被 handoff 给其他 M，所以阻塞系统调用不会拖住整个 P；
- **`goexit` 不是 `os.Exit`**：它只结束当前 G，跑完 defer，然后回到调度循环；进程退出是 `main` 返回或 `os.Exit`。

## 创建与退出：从 `go` 到 `gFree`

```text
go f(args)
  → newproc → newproc1
  → 从 P.gFree / sched.gFree 取 G；没有就 malg 新建（2KB 栈）
  → 参数 memmove 到新 G 栈；sched.pc = goexit，sched.sp = 栈顶
  → 状态 _Gdead → _Grunnable；runqput 入队
  → 被调度执行 f；f 返回后跳到 goexit
  → goexit1 → mcall(goexit0)
  → 状态 _Grunning → _Gdead；清理字段；放回 P.gFree；schedule()
```

两个工程含义：

- **G 复用是常态**：短任务不会反复分配栈，`go` 的成本主要是取 G、拷参数、入队；
- **`goexit0` 会清空 `param`、`labels`、`timer` 等字段**：所以不要把 “G 结束后还想保留” 的东西挂在 G 上（业务也拿不到 G）。

## 与线程栈的对比

| 维度 | goroutine | OS 线程 |
|---|---|---|
| 初始栈 | 2KB | 1–8MB（预留） |
| 增长方式 | 复制（连续栈） | 固定或 guard page |
| 切换成本 | 用户态 ~百 ns | 内核态 1–3μs + cache/TLB |
| 数量级 | 十万–百万 | 千–万 |

## 栈的实现：分配、扩容、缩容

`runtime.stack` 只有两个字段：`lo`、`hi`，表示 `[lo, hi)` 的栈内存。栈内存本身**分配在堆上**，但由运行时按栈的方式管理：

| 场景 | 做法 |
|---|---|
| 分配 < 32KB | 从 P 的 `stackcache` 或全局 `stackpool` 取固定大小块（按 2KB 的幂次分档） |
| 分配 ≥ 32KB | 从全局 `stackLarge` 或堆上按页分配 |
| 扩容 | `newstack`：新栈 = 旧栈 × 2，`copystack` 复制并修正指针 |
| 缩容 | GC 时 `shrinkstack`：使用不足 1/4 才缩到一半，最低 2KB |
| 上限 | 64 位 1GB、32 位 250MB；超过 `throw("stack overflow")` |

扩容的触发点是编译器在函数入口插入的 `morestack` 检查：它比较 SP 与 `stackguard0`，空间不足就进 `newstack`。`newstack` 先检查 `stackguard0 == stackPreempt`：

- 是抢占请求 → 走 `gopreempt_m`/`preemptPark`，让出；
- 不是 → 分配新栈、`copystack`、修正 `sudog`/`defer`/`panic`/`ctxt` 里的指针，再 `gogo` 回去继续执行。

> 🔑 **连续栈的代价是 “复制 + 改指针”，收益是避免分段栈的热分裂**：老版本的分段栈在栈边界反复扩缩容，函数调用会抖动；连续栈用 “使用不足 1/4 才缩容” 把这个抖动压下去。

## 逃逸分析与栈的两条不变性

编译器做逃逸分析，本质上是在维护两条不变性：

1. **指向栈对象的指针不能存在于堆中**；
2. **指向栈对象的指针不能在栈对象回收后存活**。

违反任何一条，变量就必须分配到堆。常见触发：

| 写法 | 为什么逃逸 |
|---|---|
| `return &T{}` | 返回后栈帧失效，指针必须指向堆 |
| 把指针/接口存进全局、channel、闭包外部 | 生命周期可能超过当前栈帧 |
| 赋给 `interface{}` 或调用接口方法 | 编译器难以证明具体类型与生命周期 |
| 栈放不下的大对象 | 直接走堆分配 |

逃逸分析是 “保守但安全” 的：它可能把本可留在栈上的变量放到堆（多一点 GC），但不会把该在堆上的放到栈（避免悬垂指针）。所以优化顺序是 **先看 `-m` 确认逃逸，再决定是否改写法**，而不是靠猜。

## 观测

| 想看什么 | 手段 |
|---|---|
| goroutine 数量 | `runtime.NumGoroutine()`、`/sched/goroutines:goroutines` |
| 谁在泄漏 | `pprof` goroutine profile，按栈聚合（见 [15.5 pprof (CPU / 内存 / 阻塞 / 互斥)](15.5-pprof.md)） |
| 栈大小分布 | `runtime/metrics` 相关指标 |

## 落到数字：栈的成长与成本

| 项 | 量级 | 说明 |
|---|---|---|
| 初始栈 | 2KB | 约 100 万 goroutine ≈ 2GB |
| 增长方式 | 翻倍（4KB、8KB…） | 每次增长复制全部栈帧 |
| 栈上限 | 1GB（64 位默认） | 递归过深即崩溃 |
| 单次栈复制 | 微秒级（栈越大越慢） | 热路径大局部变量会放大它 |

```bash
go tool pprof -top -sample_index=goroutine http://localhost:6060/debug/pprof/goroutine
go tool pprof -list 'pkg.Func' ./app cpu.prof     # 看某函数是否触发了栈增长/逃逸
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 每次请求 `go func()` 无退出条件 | goroutine 泄漏，内存线性上涨 |
| 深递归 | 反复栈复制，最坏 `stack overflow` |
| 在 goroutine 里 panic 不 recover | 整个进程崩溃（不是 “只挂一个协程”） |
| 用无缓冲 channel 做 “同步点” 却忘了对方可能不读 | 永久阻塞 |
| 在函数里声明 1MB 局部数组 | 编译器直接判逃逸到堆，每次调用一次大分配，GC 与 P99 抖动上升 |
| 看到 `NumGoroutine` 短暂上涨就判泄漏 | 稳定负载下它本随 QPS 波动；单调上升且压测后不回落才是泄漏 |

## 三条铁律

> 🔑 **goroutine 不是免费的**：每个至少 2KB + 调度开销，泄漏比线程泄漏更隐蔽。

> 🔑 **栈复制是 “指针调整”**，所以栈上的指针不能被外部长期持有（逃逸分析会处理）。

> 🔑 **panic 会杀进程**：goroutine 里的 panic 必须 recover，或确保不会发生。

## 自检

**Q1** 为什么 goroutine 的初始栈只有 2KB 却不影响功能？

▸ 答案：因为栈是**可增长的连续栈**：函数调用需要的空间超过当前栈时，运行时会分配一块更大的栈、复制内容并修正指针。初始小只是为了让 “创建 10 万个 goroutine” 的内存成本可接受（2KB × 10 万 = 200MB，而不是 8MB × 10 万）。

**Q2** 栈增长为什么需要 “调整指针”，而不是简单扩容？

▸ 答案：因为栈上可能存有指向栈内其他位置的指针。栈地址变化后，这些指针必须同步改写，否则会指向旧地址。Go 的连续栈方案在复制时遍历栈帧修正指针，这是 “栈复制比堆分配贵” 的原因。

**Q3** 一个函数里创建 1MB 的局部数组，会发生什么？

▸ 答案：通常**直接分配到堆**（编译器判断栈放不下，触发逃逸），而不是先栈后复制。结果是每次调用都产生一次大分配，GC 压力上升。正确做法是用 `sync.Pool` 复用、或改成流式处理（见 [15.3 内存分配与逃逸分析](15.3-内存分配与逃逸分析.md)）。

**Q4** 如何确认 goroutine 泄漏，而不是 “正常波动”？

▸ 答案：看**趋势**：在稳定负载下，goroutine 数应随 QPS 波动并回落；若长时间单调上升、且压测停止后不下降，就是泄漏。再抓两份 goroutine profile 做 diff，能直接看到 “哪一行创建后一直阻塞”。

**Q5** goroutine 里的 `panic` 会怎样？怎么防？

▸ 答案：**会终止整个进程**（除非被 recover）。所以：① 每个由外部输入驱动的 goroutine（请求、消息消费）都要 `defer recover`；② 用 `errgroup`/中间件统一兜底；③ 单测里加 `-race` 与 panic 注入，验证兜底生效。

**Q6** 为什么 “把大数组声明在函数里” 会让延迟抖动，而不只是变慢？

▸ 答案：因为大局部变量会触发**栈增长（复制）或直接逃逸到堆**：前者每次调用都要复制栈，后者增加分配与 GC。两者都把 “稳定的微秒级调用” 变成 “偶发的毫秒级抖动”，在 P99 上尤其明显。

**Q7** 栈缩容的触发条件是什么？为什么不是“用完就缩”？

▸ 答案：GC 时如果栈使用不足 1/4，才把栈缩到一半，最低 2KB。这样避免“刚缩完又扩”的热分裂：只有明显浪费时才缩，扩容/缩容不会在边界反复抖动。

**Q8** 为什么 G 执行完不销毁，而是放回 `gFree`？

▸ 答案：G 的结构和栈可以复用；短任务反复创建/销毁会带来分配与初始化成本。`goexit0` 把 G 置为 `_Gdead`、清理字段后放回 P 的 `gFree`（或全局），下次 `go` 直接取。业务拿不到 G，也不该依赖 G 的“身份”。
