# 15.11 定时器、网络轮询与系统监控

## 一句话

> 调度器只管「哪个 G 上哪个 P」；真正让 `Sleep`、`SetDeadline`、`Accept`、`GC` 按时发生的是三条后台生命线——**定时器堆、网络轮询器、系统监控**；它们把「时间」和「I/O 就绪」翻译成「把 G 放回运行队列」。

## 三个组件，一张图

```text
time.After / Ticker / SetDeadline
        │
        ▼
┌──────────────┐     到期      ┌──────────────┐
│ 定时器堆      │──────────────▶│ 唤醒 G        │
│ (每个 P 一个) │               │ goready      │
└──────┬───────┘               └──────▲───────┘
       │ 最近到期时间                  │
       ▼                              │
┌──────────────┐    epoll/kqueue    │
│ 网络轮询器    │────────────────────┘
│ netpoll      │   I/O 就绪的 G
└──────┬───────┘
       │ 被调度器/系统监控调用
       ▼
┌──────────────┐
│ sysmon       │  每 10ms 轮询：定时器、netpoll、抢占、强制 GC
└──────────────┘
```

## 一、定时器：不是 `sleep` 线程，是堆

`time.Timer`、`time.Ticker`、`time.After`、`time.Sleep`、网络 deadline 最终都落到运行时的 `runtime.timer`：

| 字段 | 含义 |
|---|---|
| `when` | 何时触发（纳秒） |
| `period` | 周期（Ticker 用） |
| `f` / `arg` | 到期执行的函数与参数 |
| `seq` | 重置/删除时防止旧事件误触发 |
| `status` | 运行状态（待触发/已触发/已停止等） |

Go 1.14 起，定时器不再由一个全局堆管理，而是**每个 P 一个最小堆**（`p.timers`）。好处是：

- 添加/删除定时器大多数时候只碰本地 P，减少锁竞争；
- 到期检查由调度循环和 sysmon 就近完成；
- 定时器数量多时，扩展性明显好于全局堆。

```text
addtimer → 放到当前 P 的 timer heap → 调整堆
调度循环 / sysmon → checkTimers → 取堆顶
堆顶到期 → 执行 f（把等待的 G 变 _Grunnable）→ 若是 Ticker，按 period 重新入堆
```

### 三个容易踩的坑

1. **`time.After` 在长循环里每轮新建 timer**：Go 1.23 起未引用的 timer 可被 GC，但每轮仍有分配与调度成本；长循环用 `NewTimer` + `Stop`/`Reset`。
2. **`Ticker` 不 `Stop` 会泄漏**：Ticker 会一直留在 P 的堆里，直到被停止或程序结束。
3. **`Reset` 前要排空**：对已触发的 Timer 直接 `Reset`，旧值可能还在 channel 里；标准写法是 `if !t.Stop() { select { case <-t.C: default: } }; t.Reset(d)`。

> ⚠️ Go 1.23 起 timer channel 改为**无缓冲/同步**；Go 1.27 永久移除 `asynctimerchan` 开关。依赖「timer channel 有缓冲、可以先发后收」的老代码需要重新检查。

### 定时器不是硬实时

定时器到期只保证「不早于」，不保证「精确在」。到期后还要等：

- 当前 P 的调度循环或 sysmon 检查到堆顶；
- G 被放回运行队列；
- 有 M 取到它。

所以 `time.Sleep(10ms)` 实际可能 10–11ms 甚至更久；对精度敏感的场景要用 `runtime.nanotime` 自旋 + 让步，而不是调小 Sleep。

## 二、网络轮询器：把 I/O 就绪变成 G 就绪

阻塞 I/O 会让线程卡住；Go 的做法是**非阻塞 fd + I/O 多路复用**：

| 模型 | 行为 | 代价 |
|---|---|---|
| 阻塞 I/O | 线程卡在 read/write | 一个连接一个线程 |
| 非阻塞 + 轮询 | 返回 EAGAIN，反复试 | 空转烧 CPU |
| I/O 多路复用 | 一个线程监听多个 fd | 需要 epoll/kqueue/IOCP |

Go 在 Linux 用 `epoll`，macOS/BSD 用 `kqueue`，Windows 用 `IOCP`；运行时用一组同名函数把它们抽象成同一接口：

```text
netpollinit()                 初始化（epoll_create + 唤醒管道）
netpollopen(fd, pd)           注册 fd 的可读/可写事件（边缘触发）
netpoll(delay)                等待事件，返回就绪的 G 列表
netpollBreak()                往管道写一个字节，打断 epoll_wait
```

### `pollDesc`：一个 fd 的等待状态

```go
type pollDesc struct {
    fd      uintptr
    rseq    uintptr // 读事件序号，防旧事件误唤醒
    rg      uintptr // 读等待：pdReady / pdWait / 等待的 G
    rd      int64   // 读 deadline
    rt      timer   // 读 deadline 定时器
    wseq    uintptr
    wg      uintptr
    wd      int64
    wt      timer
}
```

读/写各有一套：`rg`/`wg` 记录等待者，`rd`/`wd` 是截止时间，`rt`/`wt` 是截止时间对应的 timer。

### 一次 `conn.Read` 发生了什么

```text
net.Conn.Read
  → internal/poll.FD.Read
  → syscall read 返回 EAGAIN
  → runtime.poll_runtime_pollWait(pd, 'r')
  → netpollblock: 把当前 G 放进 pd.rg，gopark 让出
  → 网卡收到数据，epoll_wait 返回可读
  → netpollready: 把 pd.rg 里的 G 取出，goready
  → G 回到运行队列，重新执行 read
```

关键点：**G 阻塞在 I/O 上时，M 并没有被卡住**；M 继续跑别的 G。只有当 fd 就绪，G 才被放回队列。

### deadline 与 netpollBreak

`SetReadDeadline` 不是内核 socket 的超时，而是运行时的 timer：

- 把 `pd.rd` 设为绝对时间，注册 `pd.rt`；
- 到期时 `netpollDeadline` 把等待的 G 唤醒，`Read` 返回 `i/o timeout`；
- 如果你把 deadline 改早/改晚，需要 `netpollBreak` 打断正在 `epoll_wait` 的线程，让它重新计算等待时间。

所以 **deadline 精度同样受调度影响**，不是内核级硬超时。

## 三、系统监控：运行时的「巡检员」

`sysmon` 是一个不绑定 P 的特殊线程（`newm(sysmon, nil)`），启动后进入永不返回的循环：

| 阶段 | 间隔 | 做什么 |
|---|---|---|
| 初始 | 20μs | 检查死锁、定时器、网络 |
| 稳定 | 最长 10ms | 空闲 50 轮后间隔翻倍，封顶 10ms |
| 每次循环 | — | 运行到期 timer、netpoll(0)、retake、必要时强制 GC |

### 四件固定工作

| 工作 | 触发条件 | 作用 |
|---|---|---|
| **检查死锁** | 每次 | 没有可运行 G、没有 timer、没有网络事件 → `all goroutines are asleep - deadlock!` |
| **运行定时器** | 堆顶到期 | 唤醒等待的 G；必要时启动新 M 避免偏差 |
| **轮询网络** | 距上次 ≥10ms | `netpoll(0)` 非阻塞取就绪 G，`injectglist` 入全局队列 |
| **抢占 / handoff** | P 运行同一 G >10ms；P 在系统调用 >10ms | `preemptone` 发抢占；`handoffp` 把 P 交给别的 M |
| **强制 GC** | 距上次 ≥2 分钟 | 防止长时间不分配导致 GC 饥饿 |

> 🔑 `sysmon` 是「最终会检查」的兜底：它让长循环、卡住的系统调用、长时间不分配的进程都能被拉回正轨；但它不是硬实时，10ms 是量级不是承诺。

## 观测：三条命令

```bash
GODEBUG=schedtrace=1000 ./app          # 每秒看 P/G/runqueue
GODEBUG=gctrace=1 ./app                # 看 GC 与堆目标
go tool trace ./trace.out              # 看 goroutine 阻塞、timer、netpoll 时序
```

`go tool trace` 里最值得看的三类事件：

- **Network blocking profile**：G 等网络等了多久；
- **Sync blocking profile**：G 等锁/channel 等了多久；
- **Timer goroutines**：定时器唤醒是否堆积。

## 反模式

| 反模式 | 后果 |
|---|---|
| 循环里 `time.After` | 每轮新建 timer，分配与堆操作堆积 |
| `Ticker` 不 `Stop` | timer 永久留在 P 堆，泄漏 |
| 用 `time.Sleep` 等取消 | 取消后还要睡满，退出变慢 |
| 把 deadline 当硬超时 | 到期后还要等调度，长尾仍可能超 |
| 在热路径做阻塞系统调用 | M 被占，P 被 handoff，线程数上涨 |
| 认为 `netpoll` 会轮询所有 fd | 它是事件驱动，没事件就睡 |
| 以为 `sysmon` 能保证 10ms 精度 | 它是巡检，不是实时调度器 |

## 自检

**Q1** `time.Sleep(10ms)` 为什么可能睡 11ms 甚至更久？

▸ 答案：定时器只保证「不早于」；到期后要等 P 的调度循环或 sysmon 检查堆顶，再把 G 放回运行队列，最后由某个 M 取到执行。中间有调度延迟，所以 10ms 是下限，不是精确值。

**Q2** 一个 goroutine 阻塞在 `conn.Read`，为什么不会拖住整个 P？

▸ 答案：fd 是非阻塞的；`read` 返回 `EAGAIN` 后，G 被放进 `pollDesc.rg` 并 `gopark`，M 继续跑其他 G。数据到达时 `epoll_wait` 返回，`netpollready` 把 G 变回 `_Grunnable`，再由调度器安排执行。

**Q3** `SetReadDeadline` 的底层是什么？为什么改 deadline 需要 `netpollBreak`？

▸ 答案：它是运行时的 timer，不是内核 socket 超时；到期时唤醒等待的 G 并返回 `i/o timeout`。如果 `epoll_wait` 正在按旧的最近到期时间阻塞，改早/改晚 deadline 必须通过 `netpollBreak` 写唤醒管道，让它重新计算等待时间。

**Q4** 系统监控多久跑一次？它做哪几件事？

▸ 答案：初始 20μs，空闲 50 轮后翻倍，封顶 10ms；每次检查死锁、运行到期 timer、每 10ms 轮询网络、抢占运行超过 10ms 的 P / handoff 系统调用超过 10ms 的 P，并每 2 分钟触发一次强制 GC。

**Q5** 为什么说 `sysmon` 不是实时调度器？

▸ 答案：它是周期性巡检，10ms 是量级，不是硬承诺；抢占、timer 唤醒、网络就绪都要等它或调度循环检查。对延迟敏感的任务不能依赖「sysmon 一定在 X ms 内处理」，而要主动让出/检查取消。

**Q6** `Ticker` 为什么必须 `Stop`？`time.After` 呢？

▸ 答案：Ticker 会按 period 反复入堆，不 Stop 就一直留在 P 的 timer heap 里，造成泄漏；`time.After` 是一次性 timer，触发后可被回收（Go 1.23 起未引用可 GC），但在长循环里每轮新建仍有分配与堆操作成本，应改用 `NewTimer` + `Reset`。
