# 15.10 给新时代的 Go 编程

## 一句话

> 新时代的 Go 编程不是「把所有 API 换成最新」，而是三条纪律：**代码跟着 `go.mod` 的版本走、并发 bug 用清单查而不是靠 `-race`、性能先测量再优化**；`go fix` / `stdversion` / `goroutineleak` / pprof 把它们变成命令，Go 专属 Skill 让 Agent 按同一套纪律干活——**工具是手，Skill 是流程，CI 是闸门**，缺一个都不算新时代。

## 先破除五个误区

| 误区 | 现实 |
|---|---|
| 新版本 = 全部换新 API | `go.mod` 的 `go` 指令是契约；越级用 API 编译不过，库代码还会把升级成本转给下游 |
| 能跑 = 并发安全 | `-race` 只抓「实际发生的数据竞争」，锁泄漏、重入死锁、goroutine 泄漏一个都不管 |
| 新 API = 更快 | 多数新 API 买的是表达力与可维护性；快不快只能测，不能从版本号推 |
| 工具有了，人就不用判断 | `go fix` 只做能证明等价的机械改写；接口、错误契约、命名，仍然要人定 |
| 装了 Skill = 自动写出好 Go | Skill 给的是默认流程和检查清单；仓库自己的约定优先，效果必须在**你的仓库**上评估 |

本节的四条线分别对应：版本基线、并发诊断、性能决策、Agent 接入（Skill）。取材于 [《AI 时代的软件工程》第 24 章](https://se.rpcx.io/24.html) 的 Go Skill 思路；版本行为以 [Go 1.25](https://go.dev/doc/go1.25)、[Go 1.26](https://go.dev/doc/go1.26)、[Go 1.27](https://go.dev/doc/go1.27) 的 release notes 为准。

## 一、版本基线：`go.mod` 是契约

`go` 指令不是「建议」，它同时决定三件事：

1. **语言版本**：`for range n`、循环变量语义、泛型方法能不能用；
2. **标准库可见性**：比声明版本新的符号直接不可见；
3. **下游的升级成本**：库把 `go 1.21` 抬到 `go 1.27`，使用者的工具链也得跟上。

所以升级顺序永远是「先确认要用什么 → 再抬 `go.mod` → 再改代码」，不是反过来。

### 一张表：哪些写法已经过时

| 版本 | 旧写法 | 新写法 | 性质 |
|---|---|---|---|
| 1.13 | `err == io.EOF` | `errors.Is(err, io.EOF)` | 错误链 |
| 1.18 | `interface{}`；`strings.Index` + 手动切片 | `any`；`strings.Cut` | 语言 / 库 |
| 1.19 | `atomic.StoreInt32(&v, 1)` | `var v atomic.Int32; v.Store(1)` | 类型化原子 |
| 1.20 | `fmt.Errorf("%v: %w", e1, e2)`（丢掉 e1 的链） | `errors.Join(e1, e2)` | 多错合一 |
| 1.21 | 手写循环找元素 / 比大小 | `slices.Contains` / `min`、`max` | 库 |
| 1.21 | `var once sync.Once; once.Do(f)` | `sync.OnceFunc(f)` | 库 |
| 1.22 | `for i := 0; i < n; i++` | `for i := range n` | 语言 |
| 1.24 | `for i := 0; i < b.N; i++` | `for b.Loop()` | 测试 |
| 1.25 | `wg.Add(1); go f(); defer wg.Done()` | `wg.Go(f)` | 库 |
| 1.26 | `p := new(int); *p = v` | `p := new(v)` | 语言 |
| 1.26 | `var e *MyErr; errors.As(err, &e)` | `errors.AsType[*MyErr](err)` | 库 |
| 1.27 | `strings.LastIndex` + 手动切片 | `strings.CutLast` | 库 |

> 🔑 这张表只回答「能不能换」，不回答「该不该换」。换之前先看 `go.mod`，再看团队支持的最低版本。

一段把这些写法串起来的代码：

```go
id, amountText, ok := strings.Cut(line, ",") // 1.18
if !ok {
	return Order{}, errors.New("want id,amount")
}
amount, err := strconv.ParseInt(amountText, 10, 64)
if err != nil {
	return Order{}, fmt.Errorf("parse amount %q: %w", amountText, err)
}

var errs []error
if id == "" {
	errs = append(errs, errors.New("empty id"))
}
if err := errors.Join(errs...); err != nil { // 1.20
	return err
}

var done atomic.Int64 // 1.19
var wg sync.WaitGroup
for range 3 { // 1.22
	wg.Go(func() { done.Add(1) }) // 1.25
}
wg.Wait()
```

完整可运行版本在 [tools/examples/15.10-modern-go](../../../tools/examples/15.10-modern-go/README.md)，`go run .` 可看到输出。

### `go fix`：Go 1.26 起是官方 modernizer

Go 1.26 重写了 `go fix`，把它变成「版本感知的机械改写器」。Go 1.27 本机 `go tool fix help` 列出的 analyzer 包括：

```
any            interface{} → any
atomictypes    sync/atomic 函数 → 类型化原子类型
errorsastype   errors.As → errors.AsType[T]
minmax         if/else → min、max
newexpr        new(T) + 赋值 → new(expr)
rangeint       三段式 for → for range n
slicescontains 手写循环 → slices.Contains
stringscut     strings.Index → strings.Cut
waitgroupgo    Add/go/Done → wg.Go
...
```

关键是它**跟着 `go.mod` 的版本走**。同一个 `for i := 0; i < 10; i++`：

```console
$ cd tools/examples/15.10-modern-go/migration   # go.mod: go 1.21.0
$ go fix -diff ./...
（无输出：rangeint 规则被版本门控挡住）

$ go mod edit -go=1.27.1
$ go fix -diff ./...
--- migration/main.go (old)
+++ migration/main.go (new)
@@ -4,7 +4,7 @@
 
 func main() {
 	total := 0
-	for i := 0; i < 10; i++ {
+	for i := range 10 {
 		total += i
 	}
 	fmt.Println(total)
```

（`go fix` 打印的是绝对路径，上面缩成 `migration/main.go`；diff 内容原样。）

> ⚠️ 不要为了让 `go fix` 生效而先抬 `go.mod`。顺序反了，等于先改合同再想条款；正确做法是确认要升级后，才改 `go.mod`，然后跑 `go fix`。

`go fix` 的三条使用纪律：

1. **先 `-diff`**：看它要改什么，再决定落不落盘；
2. **在分支上跑**：它一次改很多文件，混进业务提交就不可 review；
3. **跑完必须 `go test`**：机械改写声称等价，但依赖构建标签、生成代码的项目仍可能出意外。

### `stdversion`：Go 1.27 的版本门禁

Go 1.27 起，`go test` 默认跑 `stdversion` vet 检查；编译器本身也会按文件版本拦住过新的标准库符号。两条线合起来，版本门控就不靠人记：

```console
$ go test -tags demo_toonew ./...
./toonew.go:10:20: strings.CutLast requires go1.27 or later (file is go1.21)
FAIL	github.com/shgopher/luban/tools/examples/15.10-modern-go/migration [build failed]
```

两条修法，二选一：

- **不用这个 API**：库代码保持对旧工具链的兼容；
- **抬 `go.mod`**：确认下游能接受，再升级，并跑完整 CI。

> 🔑 `go.mod` 的 `go` 版本是给「使用者」看的承诺，不是给自己用的开关。

## 二、并发五必查：`-race` 管不到的那一半

`-race` 很强，但它只回答一个问题：**这次执行里有没有观察到数据竞争**。它不回答：

| 必查项 | 工具 / 判据 | `-race` 能报吗 |
|---|---|---|
| 数据竞争 | `go test -race` | 能 |
| 锁获取/释放顺序 | 全局锁序、锁依赖图 | **不能** |
| 锁重入 | 持锁调用同锁函数 | **不能** |
| 复制 sync 原语 | `go vet` 的 `copylocks` | **不能** |
| WaitGroup 计数 / goroutine 泄漏 | 计数配对、goroutine / goroutineleak profile | **不能** |

这张表就是一份并发 review 清单：race 绿了，只说明第一行通过，后面四行还得人看。

### 锁泄漏与重入：race 永远抓不到

```go
func (f *Foo) Bar() {
	f.mu.Lock()
	if f.count < 1000 {
		f.count += 3
		return // 漏了 Unlock：锁永不释放
	}
	f.count++
	f.mu.Unlock()
}
```

这段没有数据竞争，`-race` 不会报；它会在某个时刻把所有 goroutine 一起卡死。重入同理：Go 的 `Mutex` 不可重入，持锁再 `Lock` 就是自己等自己。两类都不是 race detector 的职责。

### `goroutineleak`：Go 1.27 的泄漏 profile

Go 1.26 把 goroutine 泄漏检测作为实验特性引入（`GOEXPERIMENT=goroutineleakprofile`），**Go 1.27 转为 GA**。它是一个 profile，不是「运行时自动报警」：

```go
func leak() {
	ch := make(chan int)
	go func() { ch <- 1 }() // 永远等不到接收者
}

func main() {
	leak()
	time.Sleep(10 * time.Millisecond)
	runtime.GC() // 泄漏检测依赖 GC 的可达性分析

	pprof.Lookup("goroutineleak").WriteTo(os.Stdout, 1)
}
```

本机输出（地址会漂，`total 1` 和函数名稳定）：

```text
goroutineleak profile: total 1
1 @ 0x1022fbf18 0x102296224 0x102295e38 0x10234f818 0x102302024
#	0x10234f817	main.leak.func1+0x27	.../leakdemo/main.go:15
```

原理：goroutine 阻塞在并发原语上，而该原语从所有可运行 goroutine 都不可达，运行时就能判定它「永远醒不过来」。盲区也在这里：

- 阻塞原语被**全局变量**持有时，检测不到；
- 被**仍在运行的 goroutine 的局部变量**持有时，检测不到；
- 它只覆盖「永久阻塞」这一类，不覆盖锁顺序错误、活锁、CPU 空转。

生产上对应 `/debug/pprof/goroutineleak` 端点；测试里可以先 `runtime.GC()`，再 `pprof.Lookup("goroutineleak")` 取快照。完整示例在 [tools/examples/15.10-modern-go](../../../tools/examples/15.10-modern-go/README.md) 的 `leakdemo`。

### 确定性并发测试

Go 1.25 起 `testing/synctest` 转正：把测试放进「气泡」，`time` 用假时钟，所有 goroutine 持久阻塞时才推进时间。超时、防抖、重试这类依赖时间的并发逻辑，可以用它写成毫秒级、无 sleep 的确定性测试。用法与边界见 [53.9 竞态检测与并发测试](../../L5-工程效能/53-测试与质量保障/53.9-竞态检测与并发测试.md)。

## 三、性能：先测量，再谈选型

「atomic 比 Mutex 快」「channel 比锁慢」都是半句话；完整的话必须带数字。本机 8 核、Go 1.27.1 的实测：

| 操作 | P=1 | P=8 |
|---|---|---|
| `atomic.Int64` 自增 | 7.1 ns/op | 38.3 ns/op |
| `sync.Mutex` 保护自增 | 16.8 ns/op | 83.0 ns/op |
| 有缓冲 channel 交接（cap=1024） | — | 74 ns/op |
| 无缓冲 channel 交接 | — | 186 ns/op |
| `RWMutex` 只读 / `Mutex` 只读 | — | 77 / 85 ns/op |

同一份基准、完整代码与原始输出在 [tools/examples/15.6-concurrency](../../../tools/examples/15.6-concurrency/README.md)，复现命令：

```bash
cd tools/examples/15.6-concurrency
go test -run '^$' -bench CounterMutex -cpu=1,2,4,8 -benchtime=300ms -count=3
go test -run '^$' -bench . -benchmem -benchtime=300ms -count=3
```

由此得到的选型顺序，只是**起点**，不是结论：

| 你的情况 | 先用什么 | 什么时候换 |
|---|---|---|
| 只保护一个整数/布尔/指针 | `atomic` 类型 | 需要多字段不变量时，换锁 |
| 临界区有实际工作、读远多于写 | `RWMutex` | 临界区极短时，`RWMutex` 的记账赚不回来（77 vs 85） |
| 读写均衡、临界区短 | `Mutex` | 争用成瓶颈时，先分片/减少共享，不是换更快的锁 |
| 交接所有权、背压、广播 | channel | 只是保护状态时，别用 channel（单价 5 倍起） |
| 只初始化一次 | `sync.OnceFunc` | 需要失败重试时，换 `Mutex + 状态机` |

两个常被抄错的数字：

- **「atomic 1–2ns」**：那是无竞争、特定架构的乐观值。本机无竞争 7.1ns，8 核争用 38.3ns；
- **「channel 50–200ns」**：量级对得上（74/186ns），但它买的是所有权交接与背压，不是吞吐。

> 🔑 任何「X 比 Y 快」的说法，没有 `-benchmem -count=3` 和机器信息，都只能当假设。

## 四、工具链：一条最小闭环

本地现代化（改代码）：

| 步 | 命令 | 抓什么 |
|---|---|---|
| 1 | `go fix -diff ./...` | 机械现代化；先看 diff |
| 2 | `go fix ./...` | 确认后落盘 |
| 3 | `gofmt -l .` | 格式漂移 |
| 4 | `go test ./...` | 单测 + `stdversion` + 编译期版本检查 |
| 5 | `go test -race ./...` | 数据竞争 |
| 6 | `go test -run '^$' -bench . -benchmem -count=3` | 性能回归（有基准时） |

CI 门禁（不改代码，只判断）：

```bash
gofmt -l .          # 有输出就失败
go vet ./...        # copylocks、printf、waitgroup、hostport
go test ./...       # 单测 + stdversion
go test -race ./... # 数据竞争（核心包至少跑）
```

顺序不是仪式，是成本：格式 0.1 秒、vet 1 秒、单测十秒、race 分钟级；便宜的先跑，贵的放后面或夜间，与 [52.2 静态检查](../../L5-工程效能/52-持续集成/52.2-静态检查.md) 的四层漏斗是同一套经济学。

## 五、Skill：让 Agent 按 Go 的规矩干活

工具链解决「怎么做」，Skill 解决「什么时候做、按什么顺序做、什么时候不许做」。新时代的 Go 项目，不是「接了个大模型」就算数，而是把 Go 的版本知识、并发诊断、性能方法论、工程契约写成 Agent 能反复执行的流程。

### 为什么 Go 特别需要 Skill

| 原因 | 具体表现 | 没有 Skill 时 Agent 的默认行为 |
|---|---|---|
| 地道写法绑版本 | 同一件事，Go 1.10 和 Go 1.22 的标准答案不同 | 训练数据里新旧写法都有，随手写一个十年前的化石 |
| 并发坑静默 | map 并发写、复制 Mutex、goroutine 泄漏不会立刻崩 | 能跑就交，不主动跑 `-race` / `go vet` |
| 性能靠测量 | 「加个 `sync.Pool`」既没 benchmark 也没 pprof | 看一眼代码就给优化方案，猜对的概率很低 |

### 五张牌：谁管什么

| Skill | 作者 | 定位 | 覆盖面 |
|---|---|---|---|
| `/modern-go` | smallnest | 代码现代化 | 35 条版本门控规则，Go 1.0→1.26+；被 `goal-workflow` 收录 |
| `chao-go-perf` | smallnest | 性能分析 | CPU / 内存 / GC / 编译器 / 缓存 / 并发，含 PGO；8 份参考 |
| `chao-go-sync` | smallnest | 并发专家 | 全部 sync 原语 + 13+ 模式 + 分布式同步 |
| `go-style-guide` | madflojo | 工程契约 | 包 / 接口 / 错误 / 日志 / 布局 / 测试，10 份 reference |
| `cc-skills-golang` | samber | 全家桶 | 28+ 原子 Skill，交叉引用，带评估与 token 预算 |

安装（命令摘自[原文](https://se.rpcx.io/24.html)，执行前以各仓库 README 为准）：

```bash
npx skills add smallnest/goal-workflow --skill modern-go
npx skills add smallnest/chao-go-perf
npx skills add smallnest/chao-go-sync
npx skills add -g -y madflojo/go-style-agent-skill
# cc-skills-golang：按仓库 README 整套安装；作者明确提醒不要只装一部分
```

仓库入口：[goal-workflow](https://github.com/smallnest/goal-workflow)、[chao-go-perf](https://github.com/smallnest/chao-go-perf)、[chao-go-sync](https://github.com/smallnest/chao-go-sync)、[go-style-agent-skill](https://github.com/madflojo/go-style-agent-skill)、[cc-skills-golang](https://github.com/samber/cc-skills-golang)。

### 五张牌怎么打

| 你要解决的问题 | 首选 | 备选 | 但别跳过 |
|---|---|---|---|
| 老代码升级到新 Go 写法 | `/modern-go` | `cc-skills-golang` 的 modernize | 先跑官方 `go fix -diff`，再看 Skill 补的非机械规则 |
| 代码慢、要优化 | `chao-go-perf` | `cc-skills-golang` 的 performance/benchmark | 先出 benchmark / pprof，否则它只会拒绝给方案 |
| 并发 Bug 或并发设计 | `chao-go-sync` | `cc-skills-golang` 的 concurrency | 先跑 `-race`、`go vet`，再按五必查过一遍 |
| 包设计、接口、错误契约 | `go-style-guide` | `cc-skills-golang` 的 code-style | 仓库已有约定优先；Skill 只给默认值 |
| 想一站式、要评估数据 | `cc-skills-golang` 整套 | —— | 它的 eval 不是你的仓库，仍要自己跑基线 |

重叠不可怕，怕的是「装了就信」。`/modern-go` 与官方 `go fix` 的规则高度相似，前者的价值是**读到 `go.mod` 后严格门控**、以及官方没覆盖的风格规则；`cc-skills-golang` 的 `golang-modernize` 也做现代化，但没有「绝不越级」这层保护。选哪个，看你要的是「规则多」还是「不越界」。

### 接入一个真实 Go 项目：五步

**第一步：仓库先有契约。** Skill 不是项目事实的来源；`AGENTS.md`（或 `CLAUDE.md`）要写清版本、命令、禁区：

```markdown
## Go
- Go 1.27.1；go.mod 的 go 指令是 1.27.0
- 提交前：gofmt -l . / go vet ./... / go test ./... / go test -race ./...
- 未经批准不要改 go.mod 的 go 指令
- 性能改动必须附 before/after benchmark
- 不要自动合并；先展示 diff 和测试结果
```

**第二步：装 Skill，并固定版本。** 不要 `latest` 漂移；把 Skill 仓库的 commit/tag 写进项目文档，升级走 review。

**第三步：按任务路由，而不是「全都加载」。** 让 Agent 先判断任务类型：现代化、性能、并发、风格，再调用对应 Skill；一次只用一个主 Skill，避免规则互相打架。

```text
先用 chao-go-sync 审查 pkg/worker 的并发改动：
只出诊断和复现命令，不改代码；按五必查逐项给结论。
```

**第四步：护栏先于生成。** Skill 的输出必须过：

```bash
go fix -diff ./...        # 机械改写先看 diff
gofmt -l .
go vet ./...
go test ./...             # 含 stdversion
go test -race ./...       # 并发改动必跑
go test -run '^$' -bench . -benchmem -count=3  # 性能改动必跑
```

**第五步：在你自己的仓库评估。** 选 20 个真实 PR，比较「装 / 不装 Skill」的 review 轮次、测试失败率、回滚率；别看别人的 98%。

### token 预算：为什么不能把 28 个 Skill 全塞进去

`cc-skills-golang` 把渐进式信息披露做成了明账，每个 Skill 标三档：

| 层级 | 什么时候进上下文 | 例子（token） |
|---|---|---|
| `description` | 常驻，用于触发 | `golang-code-style` 115；`golang-security` 84 |
| `SKILL.md` | 触发后加载 | 2069；3036 |
| `Directory` | 需要细节时加载 | 2685；21472 |

（数字来自[原文](https://se.rpcx.io/24.html)，会随仓库版本变化。）

这就是「小而可组合」的工程实现：**常驻的只有触发词，知识按需加载**。把 28 个 Skill 全量塞进系统提示，既贵又会互相冲突；正确做法是「一个主 Skill + 按需 reference」。

### 评估数据：98% vs 56% 怎么读

`cc-skills-golang` 作者给每个 Skill 跑了 eval，总体通过率：

| | 装了 Skill | 没装 | 差距 |
|---|---|---|---|
| 总体 | 3315/3395（98%） | 1915/3395（56%） | **+41 个百分点** |

单项错误率下降最猛：modernize −61%、CI −59%、safety −58%、dependency management −54%。

**这组数字能说明方向，不能当定理**：

- 任务是作者选的、评分标准是作者定的，不是独立复现；
- 98% 是「在这些任务上」，不是「在你的代码库上」；
- 真正该做的是在自己的仓库跑基线，而不是把 98% 写进选型 PPT。

### Skill 的风险：它是代码，不是免责声明

| 风险 | 后果 | 护栏 |
|---|---|---|
| 供应链 | Skill 仓库被篡改 / 依赖被投毒 | 固定 commit、审阅 SKILL.md、最小权限、沙箱 |
| 规则过期 | 用旧版本 API 规则「现代化」 | 以 `go.mod` 为准，官方 `go fix` + `stdversion` 兜底 |
| 过度信任 | Agent 说「已优化」但没有数据 | 强制 benchmark / pprof / diff |
| 提示注入 | 仓库文件里的指令让 Agent 关测试、泄密钥 | 把 Skill 和仓库内容都当不可信输入；工具权限最小化 |
| 自动合并 | 看似通过，边界条件没覆盖 | 永不 auto-merge；CI + 人审 |
| 规则冲突 | 多个 Skill 给出相反建议 | 一次一个主 Skill；仓库约定优先 |

> 🔑 **Skill 是「资深工程师的检查清单」，不是「资深工程师」**：它能让 Agent 不跳过该跑的测试、该看的 profile、该守的版本门控；最终判断仍然是人。

## 反模式

| 反模式 | 后果 |
|---|---|
| 为了让新 API 编译，直接把 `go.mod` 抬到最新 | 下游工具链被迫升级；库的兼容承诺被单方面撕毁 |
| `go fix` 全量应用、不看 diff | 机械改写混进业务变更，review 失效 |
| `-race` 绿了就认为并发安全 | 锁泄漏、重入、goroutine 泄漏全部漏网 |
| 把 `goroutineleak` 当自动检测 | 它是 profile，要主动查；全局变量可达的泄漏还查不到 |
| 抄博客的 `ns/op` 做选型 | 机器、负载、Go 版本一变，结论就反转 |
| 库代码用最新 API，却保持低 `go` 版本 | 编译不过；或迫使使用者升级工具链 |
| 认为新 API 一定更快 | 多数只是更清楚；性能必须 benchmark |
| 安装 Skill 不锁版本 | 规则随上游漂移，昨天能过的今天报错 |
| 把 28 个 Skill 全塞进系统提示 | token 贵、规则互相冲突；应按任务加载 |
| 让 Agent 自动合并 | 通过率不是正确率；必须人工 review + CI |
| 用 Skill 替代 benchmark / `-race` | Skill 是流程，不是证据；证据仍要自己跑 |
| 把「98% 通过率」当自己的数据 | 任务与评分标准都不是你的仓库 |

## 自检

**Q1** 模块声明 `go 1.21`，代码里有一个三段式 `for` 循环。`go fix` 会把它改成 `for range n` 吗？为什么？

▸ 答案：不会。`rangeint` 规则要求 Go 1.22，`go fix` 按模块声明的版本门控；本机实测 `go fix -diff` 无输出。把 `go.mod` 改到 1.27.1 后，同一条命令才会给出 `for i := range 10` 的 diff。顺序必须是「先决定升级，再改 `go.mod`，再跑 `go fix`」，不能为了用工具先抬版本。

**Q2** `go test -tags demo_toonew` 报 `strings.CutLast requires go1.27 or later (file is go1.21)`，这说明哪条契约？有哪两种修法？

▸ 答案：说明 `go.mod` 的 `go` 指令决定了该模块文件能看见哪些标准库符号；`strings.CutLast` 是 Go 1.27 新增，对 `go 1.21` 的文件不可见。修法二选一：① 不用这个 API，保持对旧工具链兼容；② 把 `go.mod` 抬到 1.27，确认下游能接受并跑完整 CI。没有第三种「偷偷用」。

**Q3** `-race` 通过，为什么仍可能有并发 bug？举两类它抓不到的问题。

▸ 答案：`-race` 只检测「同一内存、至少一次写、无 happens-before」的数据竞争，而且只对本次执行实际发生的交错负责。它抓不到：① 锁泄漏——某条分支 `Lock` 后提前 `return`，没有数据竞争，但锁永不释放，最终所有 goroutine 卡死；② 重入死锁——持锁调用同锁函数，Go 的 `Mutex` 不可重入，自己等自己。锁顺序环路、goroutine 泄漏同理。

**Q4** `goroutineleak` profile 的检测原理是什么？两个盲区是什么？

▸ 答案：运行时用 GC 的可达性分析：goroutine 阻塞在并发原语 P 上，而 P 从所有可运行 goroutine 都不可达，就判定它永远醒不过来。盲区：① P 被全局变量持有；② P 被仍在运行的 goroutine 的局部变量持有——这两种情况下 P 可达，检测不到。另外它只覆盖「永久阻塞」，不覆盖活锁与 CPU 空转。它是 profile，要主动取快照，不是自动报警。

**Q5** 为什么不能直接抄「atomic 1–2ns/op」做选型？

▸ 答案：这个数字通常是无竞争、特定架构、特定基准下的乐观值。本机实测无竞争 7.1ns，8 核争用 38.3ns；Mutex 从 16.8ns 退化到 83ns，说明争用才是主导因素。选型要看「你的负载、你的核数、你的临界区」，并用 `-benchmem -count=3` 复现；抄绝对值等于把别人的机器当成自己的。

**Q6** 库作者什么时候该抬高 `go.mod` 的 `go` 版本？

▸ 答案：当且仅当「需要的新能力」值得「下游的升级成本」时。判断顺序：① 这个 API 是否不可替代；② 项目支持的最低 Go 版本是否真的可以放弃；③ CI 是否覆盖了最低版本；④ 是否按语义化版本发布（通常伴随 minor/major，而不是 patch）。只是为了「写法新」而抬版本，是把维护成本转给使用者。

**Q7** 官方 `go fix` 和 `/modern-go` 是什么关系？有了前者还需要后者吗？

▸ 答案：`go fix` 是官方版本感知的机械改写器，Go 1.26 起重写、1.27 已有几十个 modernizer，能覆盖大多数「等价改写」；`/modern-go` 在此之上补了 35 条规则、显式的 `go.mod` 门控和一部分官方没覆盖的风格规则。日常先跑 `go fix -diff`，需要更细的规则或团队约定时再用 `/modern-go`；两者都不该绕过测试。

**Q8** 为什么不能把 `cc-skills-golang` 的 28+ Skill 全部加载进上下文？它的 token 预算是怎么设计的？

▸ 答案：全量加载既贵又会规则冲突。它把每个 Skill 分三档：常驻的 `description`（几十到一百多 token，用于触发）、触发后加载的 `SKILL.md`（约两千到三千 token）、需要细节才加载的 `Directory`（可到两万多 token）。这就是渐进式信息披露：**平时只留触发词，用时才加载知识**。项目里也应「一个主 Skill + 按需 reference」，而不是把所有规则塞进系统提示。

**Q9** 「装了 Skill 通过率 98%、没装 56%」这组数据能直接当选型依据吗？

▸ 答案：不能直接当。它来自 Skill 作者自己的 eval：任务集、评分标准、模型版本都由作者选定，也没有独立复现；98% 只代表「在这些任务上」。正确用法是把它当方向性证据，然后在自己的仓库选 20 个真实 PR 跑「装 / 不装」对比，看 review 轮次、测试失败率、回滚率。

**Q10** 把 Agent + Skill 接进 Go 项目，合并前至少要有哪些护栏？

▸ 答案：① 固定 Go 版本与 Skill 版本；② `go fix -diff` 先看机械改写；③ `gofmt` / `go vet` / `go test`（含 `stdversion`）/ `go test -race`；④ 性能改动附 before/after benchmark；⑤ 人工 review diff，绝不 auto-merge；⑥ 把 Skill 和仓库内容都当不可信输入，工具权限最小化，防提示注入。

**Q11** 一次并发改动来了，应该让 Agent 先用哪个 Skill、按什么顺序做？

▸ 答案：先用 `chao-go-sync`，顺序是「先诊断，后改代码」：跑 `-race` 与 `go vet`，再按五必查过数据竞争、锁顺序、重入、复制、WaitGroup/泄漏；确认问题后再给最小改动。性能问题才转 `chao-go-perf`（先 benchmark/pprof），版本迁移转 `/modern-go`（先读 `go.mod`）。不要让一个 Skill 同时干三件事。
