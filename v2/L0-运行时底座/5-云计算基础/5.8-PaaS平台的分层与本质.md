# 5.8 PaaS 平台的分层与本质

## 一句话

> PaaS 不是「一堆中间件加个控制台」，而是软件工程三个本质（提 SLA / 可复用 / 过程自动化）在分布式架构上的物化：**服务化是本质、分布式是根本特性、自动化是灵魂**；而它今天能建成，是因为 Docker + K8s 先当了「技术缓冲层」。

**来源**：三本质、iPaaS/aPaaS 分层、技术缓冲层、五部分与生产运维闭环，来自陈皓《左耳听风》第 27 讲（2018）。本节只讲「PaaS 内部怎么分层」；责任边界与计费见 [5.1 服务模型](5.1-服务模型.md)，组织怎么把内部平台建起来见 [78.5 平台工程](../../组织/78-技术组织设计/78.5-平台工程.md)。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 「PaaS 就是中间件堆 + 一个控制台」 | 那是**组件清单**，不是平台。判据是三句话：服务化（对外提供能力）、分布式（多租户/高可用/编排）、自动化（部署与伸缩）——缺一条就只是机柜里多装了几个中间件 |
| 「自研一套才贴合业务」 | 你会发现自己造出来的东西跟 Docker/K8s 越来越像，**最终还是会放弃自己的轮子**。缓冲层的价值就是「别重造通用件」 |
| 「有了 K8s 就是 PaaS」 | K8s 只到「调度与编排」这一层；上面还缺能力层（aPaaS）、流量调度接入、以及把监控事件接回控制器的生命周期管理 |

## 一、三个本质：软件工程要的，正好是分布式要的

一家公司的软件工程能力，原文认为主要体现在三处，每处各有两个子项。把它们与分布式技术对齐，会发现是同一件事：

| 软件工程本质 | 具体做法 | 分布式上的对应能力 | PaaS 里的落点 |
|---|---|---|---|
| **提高服务的 SLA** | ① 高可用的系统 ② 自动化的运维 | 分布式多层的系统架构 | iPaaS 调度层：高可用与自动化运维 |
| **能力和资源的复用** | ① 软件模块重用 ② 运行环境与资源重用 | 服务化的能力供应 | aPaaS 能力层 + 服务治理 |
| **过程的自动化** | ① 软件生产流水线 ② 运维自动化 | 自动化的运维能力 | DevOps + 控制器（把变更拟合到集群） |

两个补充判据，原文说得很硬：

- **每提高一个 9 的可用性，都是对整个系统架构的重新洗礼**。所以「提 SLA」不是一个指标，而是重构的理由；
- 复用需要两种能力：**软件抽象**（找出可复用的模块/服务）与**软件标准化**（统一协议、统一开发运维方法）。少了标准化，抽象出来的东西只能自己用；
- 自动化也分两层：**CI/CD 的流水线**，以及**对正在运行的生产系统做自动化运维**。只做前者，故障来了还是靠人。

> 🔑 三句话记住 PaaS 与传统中间件的差别：**服务化是本质**（模块重用、服务治理、对外提供能力）、**分布式是根本特性**（多租户隔离、高可用、服务编排）、**自动化是灵魂**（自动部署安装运维、自动伸缩调度）。

## 二、iPaaS 与 aPaaS：两层，缺一不可

Docker/K8s 之上是两个 PaaS 层，名字容易混，职责很清楚：

| 层 | 别称 | 管什么 | 缺了它会怎样 |
|---|---|---|---|
| **PaaS 调度层** | **iPaaS** | PaaS 的自动化，以及分布式架构下的高可用、高性能管理 | 能力层很难被管理和运维，等于一堆没人调度的服务 |
| **PaaS 能力层** | **aPaaS** | 真正提供给用户的服务和能力 | PaaS 失去业务价值，只剩一个空调度器 |

两层之上还有一个**流量调度接入模块**，它常被漏掉，但流控、路由、降级、灰度、聚合、串联都在这里，连 FaaS 那种小函数也可以挂进来。原文给了一条部署判据：**这个模块应该像 CDN 那样部署**——靠近用户、按入口分散，而不是只放在中心机房。

再往外是两侧：

| 侧 | 面向 | 管什么 |
|---|---|---|
| **运营** | 对外 | 软件资源库（类似 Docker Hub / CMDB）、外部接入与开放平台 |
| **运维** | 对内 | DevOps 相关的一切 |

> 🔑 分层的必要性是一句话：**没有调度层，能力层管不动；没有能力层，PaaS 没有业务价值。** 两层不是可选项，是互相成全。

## 三、「技术缓冲层」：为什么是 Docker + K8s

原文用「技术缓冲层」形容 Docker + Kubernetes 的位置：**没有它，构建 PaaS 会复杂很多**。

| 没有缓冲层，这些都得自己造 | 有缓冲层之后 |
|---|---|
| 服务调度、发布、回滚、自愈 | K8s 的控制器模式已经给了 |
| 资源隔离与多租户的基础边界 | 容器 + namespace / cgroup 给了 |
| 健康检查、滚动更新、扩缩容原语 | Deployment / HPA 给了 |
| 一套自己的 API 与生态 | 标准 API + 现成生态 |

「缓冲」缓冲的是**通用难题**：把调度、发布、自愈、隔离这些每个平台都要解决的问题沉淀成标准接口，PaaS 只写自己差异化的那部分。这也是自研轮子最终会放弃的原因——你写的每一条通用逻辑，都在和 K8s 重复。

三处章节的分工要分清，否则同一个问题会在三个地方各答一半：

| 章节 | 回答的问题 |
|---|---|
| [5.1 服务模型](5.1-服务模型.md) | **责任边界与计费**：内核补丁谁打、进程谁拉起、扩容谁决定、按什么计费 |
| 5.8（本节） | **PaaS 内部怎么分层**：iPaaS / aPaaS / 技术缓冲层 / 流量接入各自管什么 |
| [78.5 平台工程](../../组织/78-技术组织设计/78.5-平台工程.md) | **组织怎么建平台**：三阶段演进、规模效应、自服务 |

## 四、一个完整 PaaS 的五个部分

| # | 部分 | 管什么 |
|---|---|---|
| 1 | **PaaS 调度层** | 自动化 + 分布式下的高可用、高性能管理 |
| 2 | **PaaS 能力服务层** | 真正提供给用户的服务与能力 |
| 3 | **PaaS 流量调度** | 与流量调度相关的一切，含高并发管理 |
| 4 | **PaaS 运营管理** | 软件资源库、软件接入、认证、开放平台门户 |
| 5 | **PaaS 运维管理** | DevOps 相关 |

这张图「大而全」是故意的：**很多组件可以按需简化、裁剪**，大量开源软件能替你省掉一大半工作。原文的原话是「虽然构建 PaaS 看上去很麻烦，但其实并不是很复杂，不要被我吓到了」。

## 五、闭环：监控事件 → 生命周期管理 → 控制器

PaaS 真正在跑的是一条闭环，不是一张静态架构图：

```text
正向：软件构建 → 资产库（Docker Registry + 软件定义）→ DevOps → 整体架构控制器 → Docker/K8s 集群
回环：K8s 集群 → 服务运行数据 → 应用监控 → 监控事件 → 生命周期管理 → 控制器（驱动下一轮拟合）
```

| 环节 | 输入 | 动作 | 做错了会怎样 |
|---|---|---|---|
| **应用监控** | 服务运行时数据 | 产出指标与**监控事件**；发现流量变化时要求强制伸缩 | 扩容靠人肉，峰值来了才反应 |
| **生命周期管理** | 运行状态 + 监控事件 | 判断当前状态与目标状态的差距，**决定往哪拟合** | 状态漂移没人管，实例掉了不补 |
| **整体架构控制器** | 目标状态（清单/架构版本） | **一步步行进**式下发命令，直到达到目标 | 只发一次命令就完事，中途失败不回退 |

当监控发现流量变化、需要**强制伸缩**时，它也是走这条回环：应用监控 → 生命周期管理 → 通知控制系统执行伸缩——而不是监控系统直接去调 K8s。

生命周期管理维护的是**运行状态**（Status，不是数据状态 State），至少包括 Provision、Ready、Run、Update、Rollback、Scale、Destroy、Failed 八个；控制器干的活就是「**拟合**」——把集群从一个状态一步步挪到另一个状态，并且持续检测漂移、强行拉回。这套思路在 K8s 里叫 reconcile（[7.1 声明式 API 与控制器模式](../7-容器编排/7.1-声明式API与控制器模式.md)），在弹性场景里就是 [37.6 弹性伸缩](../../L3-质量属性/37-扩展性/37.6-弹性伸缩.md)。

> 🔑 判断一个「平台」是不是真平台，看这条闭环通不通：**监控能不能把事件送到生命周期管理、生命周期管理能不能驱动控制器、控制器能不能把集群真的拟合过去。** 断在任何一段，平台就退化成「发布工具 + 监控面板」。

## 反模式

| 反模式 | 后果 |
|---|---|
| 自研调度/发布/自愈去替代 Docker + K8s | 重复造通用件，最终放弃轮子，白付一遍迁移成本 |
| 只有 aPaaS 能力层、没有 iPaaS 调度层 | 能力层管不动、运维不了，服务上得去下不来 |
| 有能力层但没有流量调度接入 | 缺流控、路由、灰度、聚合、串联，所有流量问题都堆到网关配置里 |
| 把 PaaS 做成「中间件堆 + 控制台」 | 服务化、分布式、自动化三件事一件没答，规模一大就散 |
| 只做 CI/CD 自动化，不做运行时自动化运维 | 发布很快，故障恢复还是靠人，SLA 上不去 |
| 控制器只下发一次命令 | 中途失败、外部漂移都发现不了，实际状态与期望长期不一致 |
| 平台一次做全五大块 | 交付周期拉长、价值说不清；应按业务先裁剪出最小闭环 |

## 自检

**Q1** 有人说「我们买了 K8s，PaaS 就建好了」。按本节的分层，还缺哪几块？

▸ 答案：缺四块——① **iPaaS 调度层**（自动化与高可用管理）；② **aPaaS 能力层**（真正对外提供的能力）；③ **流量调度接入**（流控/路由/灰度/聚合）；④ **闭环**：监控事件 → 生命周期管理 → 控制器。K8s 只覆盖「调度与编排」这一段，其余四块不补，平台就只是个容器集群。

**Q2** 为什么说 Docker/K8s 是「技术缓冲层」，而不是 PaaS 本身？

▸ 答案：因为它是**通用件的沉淀层**：调度、发布、自愈、隔离这些每个平台都要的能力被标准化成接口，PaaS 只在它上面写差异化部分。判据是「自研会不会造出同样的东西」——原文的判断是最终一定会放弃自己的轮子。PaaS 是在缓冲层之上的两层（iPaaS + aPaaS）加流量接入与两侧管理。

**Q3** 「每提高一个 9 都是对整个系统架构的重新洗礼」这句话，对平台设计意味着什么？

▸ 答案：意味着 SLA 不是运维指标，而是**架构约束**：多一个 9 就要多一层冗余、多一套自动故障恢复，原来能凑合的单点、手工流程全部要重做。所以平台设计要先定 SLA 目标，再决定 iPaaS 层要做到什么程度的自动化——而不是先堆组件再谈可用性。

**Q4** 一个平台有监控大盘、能一键发布，但没有「生命周期管理」。它会缺什么能力？

▸ 答案：缺**状态拟合**。一键发布只完成一次动作；没有生命周期管理，就没人维护「当前处于 Provision/Ready/Run/Update/Scale/Failed 哪个状态」，也不知道该往哪个目标状态走。表现是：实例挂了不自动补、发布失败不回滚、流量涨了不强制伸缩——监控看到了，但没有人把它翻译成控制器的动作。

**Q5** 为什么流量调度接入模块要「像 CDN 那样部署」，而不是只放在中心机房？

▸ 答案：因为它承载流控、路由、降级、灰度、聚合、串联这些**入口侧**职责，离用户越近，越能就地拦截、分流和降级，避免所有流量先回中心再被拒绝。放中心机房的结果是：入口层自己成为瓶颈与单点，且跨地域访问的延迟无法优化。
