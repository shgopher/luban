# 10.6 元数据管理与副本放置

## 一句话

> 元数据决定 “**能不能找到数据**”、副本放置决定 “**坏了能不能恢复**”：元数据要能水平扩展且低延迟，副本必须**跨故障域**——否则 “3 副本” 只是 “同一机架里的 3 份拷贝”。

## 元数据的两种架构

| 架构 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| **集中式**（单 Master） | HDFS NameNode、GFS Master | 简单、强一致、易实现 | 内存受限、单点（靠 HA 补） |
| **分布式**（分片 KV） | 对象存储、Ceph MON+OSD map | 可扩展、无单点 | 一致性与路由更复杂 |

集中式的天花板很清楚：**每个对象/文件/块在内存里占一条记录（约 150 字节量级）**。

## 实测：元数据内存账

| 对象数 | 元数据内存（150B/对象） |
|---|---|
| 100 万 | ≈ **0.14 GB** |
| 1000 万 | ≈ **1.40 GB** |
| 1 亿 | ≈ **13.97 GB** |

1 亿对象就要 14GB 堆——这还没算索引、缓存与副本。所以 “小文件/海量对象” 对集中式元数据是致命的；分布式元数据（分片 + 前缀树）才是解法。

## 副本放置：跨故障域才算副本

3 机架、3 副本，若**随机放置**：

| 放置方式 | 同一对象 3 副本全在 1 个机架的概率 |
|---|---|
| 随机（可重复） | ≈ **11.1%** |
| 机架感知（每机架 ≤ 1 副本） | **0%** |

11.1% 意味着 “约每 9 个对象就有 1 个，其全部副本在同一机架”——机架断电就永久丢数据。**副本数不等于可靠性，故障域分布才是**。

```text
可靠性的三个层次：
  副本数（3）→ 故障域（跨机架/跨 AZ）→ 修复速度（重建带宽/限速）
少任何一层，另外两层都会被浪费
```

## 代码：机架感知放置的判据

```python
# 放置策略：同一对象的副本必须落在不同机架（再要求不同 AZ）
def place(obj, racks, replicas):
    chosen = []
    for r in racks:                       # 机架优先
        if len(chosen) == replicas: break
        if r.az in {c.az for c in chosen} and len({c.az for c in chosen}) < len({x.az for x in racks}):
            continue                      # 先保证跨 AZ
        chosen.append(r)
    assert len({c.rack for c in chosen}) == replicas, "副本集中在同一机架"
    return chosen
```

## 副本放置：机架感知与故障域

> 🔑 **「3 副本全在同一机架的对象比例」不等于「机架故障丢数据率」**：前者 11.11% 是暴露面，还要乘「故障恰好落在这个机架」的概率（3 机架时 1/3），才是 3.70%。副本数给的是「能坏几份」，故障域数才决定「坏 1 个域之后还剩几份」。

**先把概率拆开**（3 机架 × 5 节点，随机放置，数学推导）：

| 指标 | 定义 | 数值 | 算法 |
|---|---|---|---|
| 脆弱对象比例 | 3 副本全在同一机架 | 11.11% | 3 × (1/3)³ |
| 机架故障丢数据率 | 故障机架恰好是那个机架 | 3.70% | 11.11% × 1/3 |
| 机架故障降级率 | 故障后仅剩 1 份 | 22.22% | 3 × (2/9) × 1/3 |
| 机架故障健康率 | 故障后仍有 ≥2 份 | 74.07% | 100% − 3.70% − 22.22% |

「降级」不是丢数据，但它是**下一次故障的放大器**：降级期间再坏 1 份就丢，而修复要几十分钟到几小时——故障窗口就是这么被拉长的。

**仿真设定**：每个场景 15 个节点、10 万个对象、随机种子固定；机架故障 = 等概率断一个机架；关联故障 = 先坏 1 个节点，再在**同机架**内坏 1 个节点（电源、ToR、交换机这类共因故障）。

```go
// 3 副本放置仿真：机架故障 vs 同机架关联故障，比较随机放置与机架感知放置。
// 口径：每个场景 15 个节点、10 万个对象、固定随机种子；机架故障等概率取一个机架；
// 关联故障 = 先随机坏 1 节点，再在同机架内随机坏 1 节点（电源 / ToR / 交换机相关）。
package main

import (
	"fmt"
	"math/rand"
)

type cluster struct {
	name  string
	racks []int // 每个机架的节点数
}

func (c cluster) total() int {
	n := 0
	for _, r := range c.racks {
		n += r
	}
	return n
}

// 节点编号连续：机架 0 占 [0,r0)，机架 1 接着排……
func (c cluster) rackOf(node int) int {
	s := 0
	for i, r := range c.racks {
		s += r
		if node < s {
			return i
		}
	}
	return len(c.racks) - 1
}

type obj struct {
	nodes [3]int
	racks [3]int
}

func newObj(c cluster, nodes [3]int) obj {
	o := obj{nodes: nodes}
	for i, n := range nodes {
		o.racks[i] = c.rackOf(n)
	}
	return o
}

// 随机放置：3 个副本各自独立均匀选节点（允许重复）——典型的“不校验故障域”
func placeRandom(c cluster, rng *rand.Rand) obj {
	var ns [3]int
	for i := range ns {
		ns[i] = rng.Intn(c.total())
	}
	return newObj(c, ns)
}

// 机架感知：先选互不相同的机架，再在机架内随机选节点；机架不足 3 个时退化为“尽量分散”
func placeRackAware(c cluster, rng *rand.Rand) obj {
	var ns [3]int
	if len(c.racks) >= 3 {
		order := rng.Perm(len(c.racks))[:3]
		for i, r := range order {
			start := 0
			for j := 0; j < r; j++ {
				start += c.racks[j]
			}
			ns[i] = start + rng.Intn(c.racks[r])
		}
		return newObj(c, ns)
	}
	// 只有 1~2 个机架：机架数用满，多出来的副本放到副本数少的机架
	used := make([]int, len(c.racks))
	for i := range ns {
		best := -1
		for r := range c.racks {
			if best == -1 || used[r] < used[best] {
				best = r
			}
		}
		start := 0
		for j := 0; j < best; j++ {
			start += c.racks[j]
		}
		ns[i] = start + rng.Intn(c.racks[best])
		used[best]++
	}
	return newObj(c, ns)
}

// 机架 r 整体故障：返回 (丢数据, 仅剩 1 份)
func (o obj) loseRack(c cluster, r int) (lost, degraded bool) {
	alive := 0
	for _, node := range o.nodes {
		if c.rackOf(node) != r {
			alive++
		}
	}
	return alive == 0, alive == 1
}

// 两个节点同时故障：alive 统计未被这两个节点覆盖的副本数
func (o obj) loseNodes(a, b int) (lost, degraded bool) {
	alive := 0
	for _, node := range o.nodes {
		if node != a && node != b {
			alive++
		}
	}
	return alive == 0, alive == 1
}

// 组合数：随机放置时“3 副本全在同一机架”的概率
func sameRackProb(c cluster) float64 {
	n := float64(c.total())
	p := 0.0
	for _, r := range c.racks {
		p += (float64(r) / n) * (float64(r) / n) * (float64(r) / n)
	}
	return p
}

func main() {
	rng := rand.New(rand.NewSource(42))
	const objects = 100000
	clusters := []cluster{
		{"3 机架 × 5 节点", []int{5, 5, 5}},
		{"2 机架（8+7 节点）", []int{8, 7}},
		{"单机架 15 节点", []int{15}},
	}
	placers := []struct {
		name string
		fn   func(cluster, *rand.Rand) obj
	}{
		{"随机", placeRandom},
		{"机架感知", placeRackAware},
	}

	fmt.Println("== 1. 组合数核对（3 机架，随机放置） ==")
	c3 := clusters[0]
	fmt.Printf("P(3 副本同机架) = %.2f%%；机架故障等概率（每次 1/3）→ 理论丢数据率 = %.2f%%\n",
		sameRackProb(c3)*100, sameRackProb(c3)/3*100)
	// 仿真核对
	cnt := 0
	same := 0
	for i := 0; i < objects; i++ {
		o := placeRandom(c3, rng)
		if o.racks[0] == o.racks[1] && o.racks[1] == o.racks[2] {
			same++
		}
	}
	for r := 0; r < 3; r++ {
		for i := 0; i < objects; i++ {
			o := placeRandom(c3, rng)
			if lost, _ := o.loseRack(c3, r); lost {
				cnt++
			}
		}
	}
	fmt.Printf("10 万对象仿真：3 副本同机架 %.2f%%；机架故障丢数据 %.2f%%\n\n",
		float64(same)/objects*100, float64(cnt)/(3*objects)*100)

	fmt.Println("== 2. 机架故障（整机架断电） ==")
	fmt.Println("部署 | 放置 | 丢数据率 | 降级率(仅剩1份) | 健康率(≥2份)")
	for _, c := range clusters {
		for _, p := range placers {
			objs := make([]obj, objects)
			for i := range objs {
				objs[i] = p.fn(c, rng)
			}
			lost, deg := 0, 0
			for r := range c.racks {
				for _, o := range objs {
					l, d := o.loseRack(c, r)
					if l {
						lost++
					} else if d {
						deg++
					}
				}
			}
			total := objects * len(c.racks)
			l, d := float64(lost)/float64(total)*100, float64(deg)/float64(total)*100
			fmt.Printf("%s | %s | %.2f%% | %.2f%% | %.2f%%\n", c.name, p.name, l, d, 100-l-d)
		}
	}

	fmt.Println("\n== 3. 同机架双节点故障（关联故障：电源/ToR/交换机） ==")
	fmt.Println("部署 | 放置 | 丢数据率 | 降级率(仅剩1份)")
	for _, c := range clusters {
		for _, p := range placers {
			objs := make([]obj, objects)
			for i := range objs {
				objs[i] = p.fn(c, rng)
			}
			lost, deg, total := 0, 0, 0
			// 事件分布：先等概率选 1 个节点，再在同机架内等概率选 1 个不同节点
			for r := range c.racks {
				start := 0
				for j := 0; j < r; j++ {
					start += c.racks[j]
				}
				size := c.racks[r]
				for a := start; a < start+size; a++ {
					for b := start; b < start+size; b++ {
						if a == b {
							continue
						}
						total += objects
						for _, o := range objs {
							l, d := o.loseNodes(a, b)
							if l {
								lost++
							} else if d {
								deg++
							}
						}
					}
				}
			}
			l, d := float64(lost)/float64(total)*100, float64(deg)/float64(total)*100
			fmt.Printf("%s | %s | %.2f%% | %.2f%%\n", c.name, p.name, l, d)
		}
	}

	fmt.Println("\n== 4. 年化：机架故障 1 次/年时，3 年累计遇到丢数据的对象比例 ==")
	fmt.Println("部署 | 放置 | 单次故障 | 3 年累计")
	for _, c := range clusters {
		for _, p := range placers {
			objs := make([]obj, objects)
			for i := range objs {
				objs[i] = p.fn(c, rng)
			}
			lost := 0
			for r := range c.racks {
				for _, o := range objs {
					if l, _ := o.loseRack(c, r); l {
						lost++
					}
				}
			}
			pct := float64(lost) / float64(objects*len(c.racks))
			fmt.Printf("%s | %s | %.2f%% | %.2f%%\n", c.name, p.name, pct*100,
				(1-(1-pct)*(1-pct)*(1-pct))*100)
		}
	}
}
```

**读法一：机架感知在 3 机架上是「0 丢数据 + 0 降级」。** 随机放置的 3 机架：3.69% 丢数据、22.25% 降级，只有 74.06% 的对象在机架故障后仍健康；机架感知（每机架 1 份）则是 0% / 0% / 100%。仿真与组合数对得上：同机架 11.07% vs 11.11%，丢数据 3.75% vs 3.70%，差值来自 10 万对象的抽样误差。

**读法二：2 机架是分水岭。** 鸽笼原理：3 副本分 2 个机架，必有 1 个机架放 ≥2 份。机架感知能做到「丢数据 0%」，但做不到「故障后健康」：丢数据 0%、降级 **50%**、健康 50%。也就是说 2 机架的 3 副本只能容忍「1 个机架故障」，故障后有一半对象只剩 1 份，修复窗口里再出一次故障就丢。随机放置更差：12.70% 直接丢数据、37.30% 降级、只剩 50% 健康。

**读法三：单机架的「3 副本」等于 1 副本。** 机架一断，随机与机架感知都是 100% 丢数据——没有第二个故障域，「机架感知」退化成一个空函数。单机架 3 副本只能防单盘、单节点故障，不能写进「机房级高可用」的承诺里。

**读法四：关联故障的杀伤面小，但正好打在「降级窗口」上。** 同机架双节点故障下：3 机架随机 0.23% 丢、4.60% 降级；机架感知 0% / 0%；2 机架机架感知 0% 丢、3.57% 降级；单机架 0.24% / 4.64%。绝对值不大，但它发生在「另一次故障之后、修复完成之前」时，丢数据概率会被放大——所以修复必须限速并优先修「只剩 1 份」的对象。

**年化一下**（假设机架故障 1 次/年）：3 机架随机 3.67%/次 → 3 年累计 **10.62%** 的对象会遇到丢数据；2 机架随机 12.58% → **33.19%**；机架感知的 3 机架与 2 机架都是 0%。差一个放置策略，差出「3 年 10.62%」和「0%」的差距。

**放置策略表**：

| 部署形态 | 独立故障域 | 单机架故障丢数据 | 同机架双节点故障丢数据 | 故障后剩余副本 | 结论 |
|---|---|---|---|---|---|
| 单机架 3 副本 | 1 | 100% | 0.24% | 0 | 只防盘/节点，不防机房 |
| 2 机架 + 随机 | 2 | 12.70% | 0.24% | 0–2 | 不可接受 |
| 2 机架 + 机架感知 | 2 | 0% | 0% | 1–2（50% 只剩 1） | 可容忍 1 机架故障，但必须加速修复 |
| 3 机架 + 随机 | 3 | 3.69% | 0.23% | 0–2 | 靠概率，等于没做 |
| 3 机架 + 机架感知 | 3 | 0% | 0% | 2 | 推荐基线：坏 1 机架仍健康 |
| 3 AZ + 机架感知 | 3 AZ（每 AZ ≥1 机架） | 0%（单 AZ 故障） | 0% | 2 | 要防 AZ 级故障，副本必须跨 AZ |

**机架感知怎么落地**（四步，缺一步就退化成「随机 + 口号」）：① **拓扑上报**：节点启动时从配置或元数据服务拿到 rack / AZ id，而不是从主机名猜；② **放置校验**：放置器选点后校验副本所在机架集合大小 = 副本数，不满足就重选；③ **修复保持约束**：重建的新副本必须落到「当前没有该对象副本的机架」，否则修复会把副本重新挤到一起；④ **审计**：定期统计「3 副本同机架」的对象比例，非 0 就报警——这个比例是可以直接查出来的硬指标。

**一条边界**：同一 AZ 内的 3 个机架仍共享 AZ 级故障域（电力入口、网络出口、控制面）。要承诺「AZ 故障不丢数据」，副本必须跨 3 个 AZ；跨 AZ 的代价是带宽费用与写延迟（见 [36.3 冷备-温备-热备](../../L3-质量属性/36-灾备/36.3-冷备-温备-热备.md)）。另外，故障域不是越多越好：故障域数量决定副本数的**有效上限**（副本数超过故障域数，多出来的副本不增加隔离）；副本数决定成本——3 副本配 3 个故障域是「刚好」，2 个故障域配 3 副本则等于浪费 1/3 存储。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只数副本数、不看故障域 | 机架/ AZ 故障时全部副本一起丢 |
| 元数据放单机内存且不做 HA | NameNode 挂 = 集群不可用 |
| 1 亿小对象用集中式元数据 | 内存爆、GC 停顿、启动慢 |
| 副本修复不限速 | 重建流量抢带宽，前台延迟飙升 |
| 只按 “磁盘利用率” 放置 | 热点节点先满，扩容也救不了 |
| 不做 “副本一致性校验” | 静默损坏（bit rot）长期不被发现 |

## 三条铁律

> 🔑 **副本要跨故障域**；同机架的 3 份等于 1 份。

> 🔑 **元数据规模决定架构**：1 亿对象别用单 Master。

> 🔑 **修复要限速 + 可观测**；否则 “修数据” 变成 “拖垮业务”。

## 自检

**Q1** 为什么 “3 副本” 在随机放置下只有约 89% 的对象是安全的？

▸ 答案：因为随机放置允许 “3 个副本落在同一机架”（概率约 11.1%）。这些对象在 “该机架故障” 时会同时失去所有副本，等于单副本。**副本数的意义依赖 “故障域独立性”**。

**Q2** 元数据内存怎么估？

▸ 答案：按 “对象数 × 每对象字节数” 估：本机按 150B/对象算，1 亿对象 ≈ 14GB。再加上索引、缓存与副本，实际需求更高。估算时要留 2 倍余量，并考虑 GC 停顿对延迟的影响。

**Q3** 集中式元数据（NameNode）为什么难扩展？

▸ 答案：因为所有元数据要在**内存里维护并保持一致**：单机内存有限，且每次变更都要走同一个入口。HDFS 的解法是 “联邦（多 NameNode 分命名空间）” 与 “更大堆 + 调优”，但本质仍是 “按命名空间分片”。

**Q4** 机架感知放置的实现关键是什么？

▸ 答案：关键是**拓扑信息**：节点要上报 “机架/AZ”，放置器按拓扑选点，并校验 “副本的故障域互不相同”。没有拓扑信息，“机架感知” 只是口号；有了它，才能把 “3 副本” 变成 “3 个独立故障域”。

**Q5** 副本修复为什么要限速？

▸ 答案：因为重建是**读放大**：修 1 块要读 k 块（EC）或 1 份（副本），并写入新副本；如果不限速，重建流量会与前台业务抢带宽，造成 “修数据把业务拖慢”。常见做法是 “限速 + 低峰优先 + 监控重建队列”。

**Q6** “bit rot”（静默损坏）怎么发现？

▸ 答案：靠**校验和 + 定期扫描**：每个块存校验和，后台定期读取校验；发现不匹配就用其他副本修复。没有校验和，损坏只会在 “读到时” 才暴露，且可能已经传染到备份。

**Q7** 对象存储的元数据为什么常用 “分片 KV”？

▸ 答案：因为对象数量可以到千亿级：单机内存放不下，且需要**水平扩展与高并发**。分片 KV（按 bucket + key hash）把元数据分散到多节点，配合一致性协议保证 “同一 key 的元数据只有一个主”，从而既扩展又不冲突。
