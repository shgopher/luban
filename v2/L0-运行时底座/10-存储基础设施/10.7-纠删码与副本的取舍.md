# 10.7 纠删码与副本的取舍

## 一句话

> 副本用 “**空间换简单**”（3 份、读任意一份、修复只拷一份），纠删码用 “**计算换空间**”（1.4–1.5 份、重建要读 k 块、CPU 参与）；选型只看两个数：**存储成本**与**重建代价**。

## 实测：几种方案的空间与重建代价

| 方案 | 空间开销 | 可容错 | 重建 1 块需读 |
|---|---|---|---|
| **3 副本** | **3.00×** | 2 块 | **1 份** |
| EC 4+2 | **1.50×** | 2 块 | 4 块 |
| EC 6+3 | 1.50× | 3 块 | 6 块 |
| EC 8+3 | **1.38×** | 3 块 | **8 块** |
| EC 10+4 | 1.40× | 4 块 | 10 块 |

例：1PB 原始数据 → 3 副本 **3PB**；EC 8+3 约 **1.375PB**（省 **54%**）。

```text
空间开销 = (k + m) / k
重建读放大 ≈ k（修 1 块要读 k 块参与解码）
可容错 = m 块
```

## 三者的真实代价对比

| 维度 | 3 副本 | 纠删码 |
|---|---|---|
| 存储成本 | 3× | 1.4–1.5× |
| 读延迟 | 低（任一副本） | 中（正常读也读多块/或从一块读） |
| 重建网络 | 1 份 | **k 份** |
| 重建 CPU | 无 | 有（解码） |
| 小对象效率 | 差（3 倍空间） | **更差**（分块开销占比高） |
| 适用 | 热数据、低延迟、小对象 | 温/冷数据、大对象、归档 |

## 代码：算一算 “该用哪个”

```python
def cost(size_pb, k, m, price_per_tb_month=20, rebuild_gbps=1):
    overhead = (k + m) / k
    stored = size_pb * overhead
    monthly = stored * 1024 * price_per_tb_month
    rebuild_hours = (size_pb * 1024) / (rebuild_gbps * 3600) * k   # 重建读 k 份
    return dict(overhead=round(overhead, 2), stored_pb=round(stored, 2),
                monthly_usd=round(monthly), rebuild_hours=round(rebuild_hours, 1))

print("3 副本:", cost(1, 1, 2))   # 近似 3x
print("EC 8+3:", cost(1, 8, 3))
```

判据：**热数据用副本（延迟与小对象友好），冷数据用 EC（空间省 50%+）**；重建带宽与 CPU 要单独评估，否则 “省下的存储费” 会被 “重建时间/业务影响” 吃掉。

## EC(k,m) 的存储开销与重建代价算例

> 🔑 **EC 的两个数要分开算**：`空间开销 = (k+m)/k` 决定省多少钱，`重建读放大 = k` 决定修复要读多少字节；把它们混成一个「EC 更省」的结论，就会在故障那天才发现修复窗口比预期长 3–7 倍。

**先把口径钉死**（后面所有数都从这五条推）：

| 量 | 公式 | 例（条带 128MiB，EC 8+3） |
|---|---|---|
| 空间开销 | `(k+m)/k` | 11/8 = 1.375× |
| 块大小 | `条带/k` | 128/8 = 16MiB |
| 重建 1 块读多少 | 读 k 个块 = **1 份条带** | 读 8 块 = 128MiB |
| 读放大（读/修） | `读字节 / 修复字节 = k` | 修 16MiB 读 128MiB = 8× |
| 年修复流量 | `实存 × 年故障块比例 × k` | 相对 3 副本 = (k+m)/3 |

> ⚠️ 「重建读放大 ≈ k」是**字节比**（读 k 倍于被修的块），不是「读回 k 份原始数据」——修 1 块读的是 1 条带（128MiB），不是 128×k MiB。把这两个口径混用，重建时间会被高估 k 倍。

**算例参数**：1PB 原始数据 = 1024TB；条带 128MiB；存储 20 元/TB/月；年故障块比例 1%；单节点读 100MB/s、共享出口 125MB/s、单核解码 500MB/s。单价与带宽都是示例，替换成自己的再算。

```go
// EC(k,m) vs 3 副本：存储开销 / 容错 / 重建代价算例（单位：TB、MiB、秒）
// 口径：1PB 数据 = 1024TB；条带 stripe = 128MiB；单价与带宽均为示例，按自身账单替换。
package main

import "fmt"

const (
	dataTB       = 1024.0 // 1PB 原始数据
	stripeMiB    = 128.0  // 一个条带的原始数据量
	priceTBMonth = 20.0   // 元/TB/月，存储单价
	failRate     = 0.01   // 每年故障的块比例（示例）
	nodeBW       = 100.0  // MB/s，单节点读带宽
	sharedBW     = 125.0  // MB/s，共享出口带宽（1Gbps）
	decodeBW     = 500.0  // MB/s，单核解码速度
)

type cfg struct {
	name string
	k, m int
}

func (c cfg) overhead() float64   { return float64(c.k+c.m) / float64(c.k) }
func (c cfg) chunkMiB() float64   { return stripeMiB / float64(c.k) }
func (c cfg) rebuildMiB() float64 { return c.chunkMiB() * float64(c.k) } // 读 k 块 = 1 份条带
func (c cfg) readAmp() float64    { return float64(c.k) }                // 读字节 / 修复字节

func main() {
	ecs := []cfg{{"EC 4+2", 4, 2}, {"EC 6+3", 6, 3}, {"EC 8+3", 8, 3},
		{"EC 10+4", 10, 4}, {"EC 12+4", 12, 4}, {"EC 16+4", 16, 4}}

	fmt.Println("== 1. EC(k,m) 参数扫描（1PB 原始数据，条带 128MiB） ==")
	fmt.Println("方案 | 空间开销 | 实存TB | 允许失效 | 块大小MiB | 重建读块数 | 重建读MiB | 读放大")
	for _, c := range ecs {
		fmt.Printf("%s | %.3f | %.1f | %d | %.1f | %d | %.0f | %.0fx\n",
			c.name, c.overhead(), dataTB*c.overhead(), c.m, c.chunkMiB(), c.k, c.rebuildMiB(), c.readAmp())
	}
	fmt.Println("3 副本 | 3.000 | 3072.0 | 2 | 128.0 | 1 | 128 | 1x")

	fmt.Println("\n== 2. 重建代价：年修复流量与修复时间（年故障块比例 1%） ==")
	fmt.Println("方案 | 年故障存储TB | 年修复读TB | 修复流量比 | 单块修复s(单节点瓶颈) | 单块修复s(共享瓶颈) | 年修复小时")
	type row struct {
		name             string
		ov               float64
		rep              float64 // 每修复 1 字节需读的字节数
		chunkMiB, decMiB float64
	}
	rows := []row{{"3 副本", 3.0, 1.0, 128, 0}}
	for _, c := range ecs {
		rows = append(rows, row{c.name, c.overhead(), c.readAmp(), c.chunkMiB(), c.rebuildMiB()})
	}
	// 以 3 副本为基准的修复流量比 = (实存 × 放大) / (3 副本实存 × 1)
	baseRepair := dataTB * 3.0 * failRate
	for _, r := range rows {
		repairTB := dataTB * r.ov * failRate * r.rep
		// 单节点瓶颈：每块从各自节点并行读，时间 = 块大小/单节点带宽 + 解码
		tNode := r.chunkMiB/nodeBW + r.decMiB/decodeBW
		if r.rep == 1.0 {
			tNode = r.chunkMiB / nodeBW // 副本只拷 1 份，无解码
		}
		tShared := r.decMiB/sharedBW + r.decMiB/decodeBW // 共享带宽下先搬完整条带再解码
		if r.rep == 1.0 {
			tShared = r.chunkMiB / sharedBW
		}
		hours := repairTB * 1e6 / sharedBW / 3600 // 1TB = 1e6 MB
		fmt.Printf("%s | %.2f | %.2f | %.2fx | %.2f | %.2f | %.1f\n",
			r.name, dataTB*r.ov*failRate, repairTB, repairTB/baseRepair, tNode, tShared, hours)
	}

	fmt.Println("\n== 3. 小对象账：EC 4+2 vs 3 副本（元数据/IOPS 是每对象固定开销） ==")
	fmt.Println("对象大小 | 3副本实存KiB | EC4+2实存KiB | 元数据条目(副本/EC) | 写块数 | 读整对象块数 | 1万对象年省存储费元")
	for _, sizeKiB := range []float64{64, 1024, 16384, 1048576} {
		repStored := sizeKiB * 3
		ecStored := sizeKiB * 1.5
		savedTB := (repStored - ecStored) * 1024 / (1024.0 * 1024 * 1024 * 1024)
		fmt.Printf("%.0fKiB | %.0f | %.0f | 3/6 | 3/6 | 1/4 | %.4f\n",
			sizeKiB, repStored, ecStored, savedTB*priceTBMonth*12*10000)
	}

	fmt.Println("\n== 4. 随机更新 16MiB：EC 8+3 的读-改-写放大 ==")
	fmt.Println("方案 | 更新单位 | 读块数 | 写块数 | 读MiB | 写MiB | 总IO/更新字节")
	// EC 8+3：更新 1 个数据块(16MiB) → 读其余 7 块、重算 3 个校验、写 1 数据 + 3 校验
	ecIO := 7*16 + 4*16
	fmt.Printf("EC 8+3 | 16MiB | 7 | 4 | %d | %d | %.2fx\n", 7*16, 4*16, float64(ecIO)/16)
	// 3 副本：更新 128MiB 数据 = 写 3 份
	fmt.Printf("3 副本 | 16MiB | 0 | 3 | 0 | %d | %.2fx\n", 3*16, 3.0)
}
```

**读法一：空间账——k 越大越省，但边际收益递减。** EC 4+2 与 6+3 都是 1.5×（省 50%）；8+3 是 1.375×（省 54.2%）；16+4 是 1.25×（省 58.3%）。1PB 数据：3 副本实存 3072TB，EC 8+3 实存 1408TB，按 20 元/TB/月算，一年省 `(3072−1408)×20×12 = 39.9 万元`。注意 4+2 与 6+3 空间一样，但 6+3 多容 1 块，代价是年修复流量从 2.00× 涨到 3.00×、重建读从 4 块变 6 块——**同样的空间预算，容错和修复代价在互相换**。

**读法二：重建代价——慢了 3.67 倍的是「总流量」，不是「单块时间」。** EC 8+3 年修复读 112.64TB，是 3 副本 30.72TB 的 3.67 倍；按共享出口 125MB/s，年修复时长 250.3 小时 vs 68.3 小时。但单块修复时间反而可能更快：单节点瓶颈下 EC 8+3 是 0.42s（8 个节点并行读 16MiB 再解码），3 副本是 1.28s；共享瓶颈下两者都约 1.28s。所以「EC 重建慢」准确说法是：**聚合修复流量放大 (k+m)/3 倍，单块时间取决于瓶颈在哪**；集群越大、共享带宽越紧，这个倍数越致命。

**读法三：小对象是 EC 的死穴。** 64KiB 对象：3 副本存 192KiB，EC 4+2 存 96KiB，省一半空间——但元数据条目从 3 变 6、写块数从 3 变 6、读整对象从 1 块变 4 块（要解码）。1 万个 64KiB 对象一年只省 **0.21 元**存储费，而 IOPS 与元数据翻倍；对象到 16MiB 时 1 万个一年省 54.9 元、到 1GiB 才省 3515.6 元。**空间优势要按对象大小乘出来，小对象乘完约等于零**。

**读法四：随机写让 EC 直接出局。** EC 8+3 更新一个 16MiB 数据块，要读其余 7 块、重算 3 个校验块、写 1 数据块 + 3 校验块，总 IO 176MiB / 16MiB = **11×**；3 副本更新 16MiB 只需写 48MiB = **3×**。EC 只适合「写一次、读多次」的对象/冷数据；块存储、数据库这类原地随机更新的负载用 EC，写放大先把它拖死。

**什么时候 EC 不划算**（判据用本算例的数，不靠感觉）：

| 场景 | 判据 | 后果 |
|---|---|---|
| 小对象（<1MiB） | 1 万个 64KiB 对象年省 0.21 元；元数据 3→6、读块 1→4 | 省的钱为 0，IOPS/元数据翻倍 |
| 随机写 / 原地更新 | 16MiB 更新的总 IO 是 3 副本的 3.7 倍（11× vs 3×） | 写放大吃掉容量收益 |
| 高 churn 热数据 | 年修复流量 3.67×，修复时长 250h/年 | 修复与前台抢带宽 |
| 故障域不足 | 8+3 需要 11 个独立节点/机架放 11 块 | 机架一坏可能超 m 块，冗余失效 |
| 数据量小 | 1 人年 ≈ 43.2 万 ≈ 1.1PB 的存储节省；2 人年 ≈ 2.2PB | 小集群省的钱不够养运维 |
| 延迟敏感 / 跨 AZ | 降级读要读 k 块（k 路 fan-in），跨 AZ 更慢 | 尾延迟上升，RTO 变长 |

**结论**：EC 不是「省 50% 存储」的免费午餐，而是**用修复代价、写放大、故障域数量和实现复杂度换空间**。对象大（≥16MiB）、写一次读多次、数据量到 PB 级、故障域 ≥k+m 个、且能接受较高的修复期带宽占用时，EC 划算；反过来——小对象、随机写、高 churn、故障域不足、数据量不到 PB——用 3 副本更稳。分层策略（热数据副本、冷数据 EC）与存储选型的完整口径见 [10.6 元数据管理与副本放置](10.6-元数据管理与副本放置.md)、[44.5 存储引擎：读写放大与空间放大](../../L4-组件与技术/44-数据库/44.5-读写放大与空间放大.md)。

## 反模式

| 反模式 | 后果 |
|---|---|
| 全部数据用 3 副本 | 存储成本 2–3 倍，账单难看 |
| 热数据用 EC | 读放大 + 解码 CPU，延迟上升 |
| 小对象用 EC | 分块与元数据开销占比过高 |
| 只看空间、不看重建 | 集群越大，重建越慢，故障窗口越长 |
| 重建不限速 | 重建流量挤占前台，业务抖动 |
| 不做过 “同时坏 2 块” 的演练 | 真坏 2 块时才发现恢复不了 |

## 三条铁律

> 🔑 **热数据副本、冷数据 EC**；按访问频率分层。

> 🔑 **EC 的重建读放大 ≈ k**，要按 RTO 反推 k 与带宽。

> 🔑 **空间省下来的钱，要扣掉重建与 CPU 成本** 再比较。

## 自检

**Q1** 为什么 EC 8+3 的空间开销是 1.375×，而不是 8/3？

▸ 答案：因为公式是 `(k+m)/k`：8 个数据块 + 3 个校验块 = 11 块存 8 块的数据，`11/8 = 1.375`。`8/3` 是 “每 3 个数据块配 1 个校验块” 的另一种配比（3+1），不是 8+3 的算法。

**Q2** EC 的 “重建读放大 ≈ k” 意味着什么？

▸ 答案：意味着修 1 个块要**读取 k 个块**参与解码：k 越大，重建占用的网络与磁盘带宽越多，重建时间越长。所以 “k 大省空间” 的代价是 “重建更贵、故障窗口更长”。

**Q3** 为什么热数据不用 EC？

▸ 答案：因为 EC 在正常读时也可能要读多块并解码（取决于实现），带来**读放大与 CPU 开销**；而热数据对延迟敏感、访问频繁，3 副本 “读任意一份” 更简单更快。EC 的优势（省空间）在热数据上被 “延迟成本” 抵消。

**Q4** 小对象为什么不适合 EC？

▸ 答案：因为 EC 要把对象切成 k 块并生成 m 个校验块：对象越小，**分块与元数据开销占比越高**，甚至 “校验块比数据还大”。小对象通常用副本或 “打包成大对象再 EC”。

**Q5** 重建速度怎么估？

▸ 答案：`重建时间 ≈ (数据量 × k) / 可用带宽`：例如 1PB、EC 8+3、重建带宽 1Gbps，理论约 `1PB×8 / 1Gbps ≈ 8×10^15×8/(1.25×10^8) 秒` 量级（约数天）。所以大规模集群必须限速并规划 “故障窗口”。

**Q6** 3 副本真的能容 2 块故障吗？

▸ 答案：**能，但仅在故障域独立时**：3 副本分布在 3 个不同机架，坏 2 个机架仍剩 1 份；如果 3 份都在同一机架，坏 1 个机架就全丢（见 [10.6 元数据管理与副本放置](10.6-元数据管理与副本放置.md)）。所以 “容错数” 必须和 “故障域” 一起说。

**Q7** 怎么决定 “哪些数据用 EC”？

▸ 答案：按 “访问频率 × 对象大小 × 延迟要求” 分层：**热 + 小 + 低延迟 → 副本**；**温/冷 + 大 + 可容忍延迟 → EC**；归档可以更激进（如 EC 10+4 + 更高压缩）。分层策略要写进生命周期规则，而不是靠人工判断。
