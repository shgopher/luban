# 10.9 存储选型

## 一句话

> 选型不是选 “最快” 或 “最便宜”，而是按四问落到某一层：**数据形态（块/文件/对象）× 访问模式（随机/顺序、读写比）× 一致性（谁能看到谁）× 规模（GB 还是 PB）**；绝大多数生产系统最终是 “块 + 对象” 两层，文件层只在需要共享目录时出现。

## 四问决策

| 问 | 答案 → 选择 |
|---|---|
| 要原地随机写吗？要 fsync 吗？ | 要 → **块**（数据库、WAL、系统盘） |
| 多台机器要共享同一批目录吗？ | 要 → **文件**（NFS/SMB），但要接受元数据瓶颈 |
| 一次写、多次读，按 URL 取？ | 是 → **对象**（图片、备份、数据湖） |
| 规模是 PB 级、增长不可预测？ | 是 → **对象**（扁平命名空间，近乎无限扩展） |

## 量级对比（用于排除，不用于精算）

| 维度 | 块 | 文件 | 对象 |
|---|---|---|---|
| 延迟 | 0.1–1ms | 0.5–5ms | 10–100ms |
| IOPS | 万–百万 | 千–万（元数据受限） | 低（按请求） |
| 单位成本 | 高 | 中 | 最低 |
| 共享 | 单机 | 多机 | 天然 HTTP |
| 扩展上限 | 单卷容量 | 元数据节点 | 近乎无限 |

## 分层：热、温、冷

| 层 | 介质 | 典型数据 | 策略 |
|---|---|---|---|
| 热 | 本地 NVMe / 云盘 | 数据库、索引 | 高 IOPS、低延迟 |
| 温 | 文件存储 / 标准对象 | 上传文件、日志近期 | 生命周期 30–90 天 |
| 冷 | 归档对象 / 磁带 | 备份、合规留存 | 取回有延迟，成本最低 |

分层的判据是 “**访问频率 × 延迟要求**”，不是 “数据重要程度”。重要但不常读的数据，应该待在冷层 + 独立备份。

对象存储的内部结构（元数据/数据分离、EC）见 [10.8 对象存储系统设计](10.8-对象存储系统设计.md)。

## 判据表：三问定层

| 你的情况 | 结论 |
|---|---|
| 需要 fsync / 随机写 / 事务 | 块（本地盘或云盘），不要跨网络 |
| 多机共享目录、需要 rename/flock | 文件（NFS），并接受元数据瓶颈 |
| 一次写多次读、按 URL 取、PB 级 | 对象 + CDN |
| 冷数据、合规留存 7 年 | 归档对象 + 独立备份 |

## 选型算例：同样 100TB，块/文件/对象/库差多少钱

> 先给结论：同样 100TB，四种存法的月成本能差近 10 倍；但选型不是挑最便宜——**先用访问模式排掉两个根本不通的方案，再对剩下的算 3 年 TCO**。只看「元/GB·月」，会把请求费、出口费和实例费全部漏在账外。

### 成本模型：四个方案、四类计费项

| 方案 | 容量单价（元/GB·月） | 请求费（元/万次） | 最小计费 / 起收 | 流量费（元/GB） | 最容易漏的成本 |
|---|---|---|---|---|---|
| 块（云盘 SSD） | 1.0 量级 | 无（按卷） | 按卷容量、小时折算 | 跨 AZ 复制另计，同区免费 | 计算实例、文件系统、快照 |
| 文件（托管 NAS） | 0.4 量级 | 无（按容量） | 按预配容量，不能按用多少付多少 | 同区免费，跨区计费 | 元数据性能、小文件开销 |
| 对象（标准层） | 0.12 量级 | 0.01 量级 | 标准层无最短存储期；低频 30 天、归档 60–180 天 | 公网出 0.5 量级，内网免费 | 取回费、list 请求、旧版本容量 |
| 库（托管数据库） | 1.5 量级 | 无（按实例） | 实例最小规格 + 存储，按小时 | 跨区备份 / 公网计费 | 计算节点、备份、HA 副本 |

> ⚠️ 表里每个数只保证量级（2026 年中国区公开价目表量级，**不是报价**）：区域、购买方式、阶梯用量不同，差 2–3 倍。精算时必须换成当期报价重跑，四类计费维度的拆法见 [5.6 云成本结构](../5-云计算基础/5.6-云成本结构.md)。

四类计费项决定了「便宜」的方向不同：块与文件按容量收，请求再多也不加钱；对象按容量 + 请求 + 出口收，小文件与高频读会把单价优势吃回去；库按容量 + 实例收，**实例是与数据量弱相关的固定成本**，数据量越小它占比越高。

口径说明：四个方案只比「存储侧」账单。块方案还要另配应用服务器与文件系统，但四方案都需要应用服务器，故不计入；库方案的实例是存储跑起来的必需项，计入。所有单价为公开量级，结论只用于比较**量级关系**，不能直接当采购预算。

### 代码：输入容量、请求量、访问频率，输出四种存法

```python
#!/usr/bin/env python3
# 同样 100TB：块 / 文件 / 对象 / 库 的月成本与 3 年 TCO（本机计算，单价为公开量级，不是报价）。
# 环境：macOS 15.6 / Apple M1 / Python 3.14.8
import math

CAP_TB0 = 100          # 起始容量 TB
GROWTH = 1.5           # 每年容量与请求量的增长倍数
REQ_WAN0 = 20_000      # 每月请求量，单位：万次（2 亿次）
READ_RATIO = 0.30      # 每月读取的数据占总容量的比例
EGRESS_RATIO = 0.30    # 读流量中走公网出口的比例

BLOCK_PRICE = 1.0      # 元/GB·月（云盘 SSD，含 3 副本）
FILE_PRICE = 0.4       # 元/GB·月（托管 NAS）
OBJ_PRICE = 0.12       # 元/GB·月（标准层）
OBJ_REQ = 0.01         # 元/万次
EGRESS = 0.5           # 元/GB（公网出口）
DB_PRICE = 1.5         # 元/GB·月（托管数据库存储）
DB_NODE_HOUR = 5.0     # 元/节点·小时
DB_TB_PER_NODE = 25    # 每个实例节点承载 25TB
TIERS = (("热", 0.10, 0.12), ("温", 0.60, 0.08), ("冷", 0.30, 0.033))


def monthly(cap_tb, req_wan, kind):
    gb = cap_tb * 1024
    if kind == "块":
        return gb * BLOCK_PRICE
    if kind == "文件":
        return gb * FILE_PRICE
    if kind == "对象":
        egress = gb * READ_RATIO * EGRESS_RATIO * EGRESS
        return gb * OBJ_PRICE + req_wan * OBJ_REQ + egress
    if kind == "对象+生命周期":
        storage = sum(gb * ratio * price for _, ratio, price in TIERS)
        egress = gb * READ_RATIO * EGRESS_RATIO * EGRESS
        # 冷数据只承担 1% 的回读量，按 0.06 元/GB 取回费粗算
        retrieval = gb * READ_RATIO * 0.01 * 0.06
        return storage + req_wan * OBJ_REQ + egress + retrieval
    if kind == "库":
        nodes = math.ceil(cap_tb / DB_TB_PER_NODE)
        return gb * DB_PRICE + nodes * DB_NODE_HOUR * 730
    raise ValueError(kind)


BASE_KINDS = ["块", "文件", "对象", "库"]
ALL_KINDS = BASE_KINDS + ["对象+生命周期"]
print("输入：容量 %dTB，请求 %d 万次/月，月读取占比 %.0f%%，公网出口占读流量 %.0f%%"
      % (CAP_TB0, REQ_WAN0, READ_RATIO * 100, EGRESS_RATIO * 100))
print("单价（公开量级，不是报价）：块 %.2f / 文件 %.2f / 对象 %.2f / 库 %.2f 元/GB·月，出口 %.2f 元/GB，请求 %.2f 元/万次"
      % (BLOCK_PRICE, FILE_PRICE, OBJ_PRICE, DB_PRICE, EGRESS, OBJ_REQ))

print("\n[1] 当前 100TB 的月成本（四种存法）")
for k in BASE_KINDS:
    m = monthly(CAP_TB0, REQ_WAN0, k)
    print("%-8s 月成本=%10.0f 元" % (k, m))

print("\n[2] 3 年 TCO（容量与请求每年 ×%.1f；按每年初容量计 12 个月）" % GROWTH)
totals = {}
for k in ALL_KINDS:
    total, cap, req = 0.0, CAP_TB0, REQ_WAN0
    for y in range(3):
        total += monthly(cap, req, k) * 12
        cap *= GROWTH
        req *= GROWTH
    totals[k] = total
for k in ALL_KINDS:
    print("%-8s 3年TCO=%12.0f 元   vs 对象标准层=%.2fx" % (k, totals[k], totals[k] / totals["对象"]))

print("\n[3] 第一步排除后，剩下的两个方案 + 对象分层（一次性改造成本 30000 元）")
for k, once in [("文件", 0), ("对象", 30_000), ("对象+生命周期", 30_000)]:
    print("%-8s 3年TCO=%10.0f + 改造=%6d = 合计%10.0f 元"
          % (k, totals[k], once, totals[k] + once))
print("对象+生命周期 比文件省 %.0f%%"
      % ((1 - (totals["对象+生命周期"] + 30_000) / totals["文件"]) * 100))

print("\n[4] 请求费与出口费占对象标准层账单的比例")
obj = monthly(CAP_TB0, REQ_WAN0, "对象")
fees = REQ_WAN0 * OBJ_REQ + CAP_TB0 * 1024 * READ_RATIO * EGRESS_RATIO * EGRESS
print("对象标准层月成本=%.0f，其中请求+出口=%.0f（占 %.0f%%）" % (obj, fees, fees / obj * 100))
print("若出口比例升到 100%%：出口费=%.0f 元，已超过容量费 %.0f 元"
      % (CAP_TB0 * 1024 * READ_RATIO * EGRESS,
         CAP_TB0 * 1024 * OBJ_PRICE))
```

三个数值得记住：**块是对象的 6.0 倍、库是 9.8 倍、文件是 2.4 倍**（均按月成本对对象标准层比）。但这是「同样 100TB 存一年」的静态比较，真实决策还要过下面两步。

### 两步法：先排除，再精算

**第一步：不看价格，按访问模式排掉 2 个。** 假设这 100TB 是用户上传的图片/视频：一次写多次读、按 URL 取、每月 2 亿次读取。

| 候选 | 结论 | 判据 |
|---|---|---|
| 块 | 出局 | 单节点挂载（RWO），多台应用服务器不能同时读；要自己搭文件系统与网关，容量单价约对象的 8 倍（1.0 vs 0.12） |
| 库 | 出局 | 取图片不需要 SQL、事务与范围索引；1.5 元/GB·月 买的是「能查询」，这个负载用不上 |
| 文件 | 待算 | 目录语义、挂载即用；按预配容量付费，元数据随对象数增长 |
| 对象 | 待算 | 一次写多次读 + HTTP 直出，按实际用量付费 |

语义判据的完整版在 [10.1 块存储 / 文件存储 / 对象存储](10.1-块存储-文件存储-对象存储.md)：**先确认这个用法存在，再比较价格**。块与库在「图片」这个负载上不是慢，而是用法不成立或代价结构错配——这正是第一步不精算的原因：给一个注定出局的方案做 3 年 TCO 是浪费。

**第二步：对剩下的两个算 3 年 TCO。** 假设容量与请求每年 ×1.5，对象侧套生命周期（热 10% 标准层、温 60% 低频、冷 30% 归档），一次性改造成本按 20 人日 × 1,500 元 = 30,000 元：

| 方案 | 第 1 年月成本 | 3 年 TCO | 一次性改造 | 3 年合计 |
|---|---|---|---|---|
| 文件（NAS） | 40,960 | 2,334,720 | 0（挂载即用） | 2,334,720 |
| 对象（全标准层） | 17,096 | 974,472 | 30,000 | 1,004,472 |
| 对象 + 生命周期 | 11,984 | 683,099 | 30,000 | 713,099 |

对象 + 生命周期比文件省 **69%**，但结论不是「一律选对象」：

- 一次性改造 30,000 元 ÷ 月差价 28,976 元（40,960 − 11,984）≈ 1.04 个月回本；数据量越小回本越慢，但规模上到几十 TB 后，一次性成本不再是决定项；
- 应用强依赖目录、`rename`、多机并发写时，对象方案要重写上传链路，改造成本会超过存储差价——回到文件；
- 分层不是越冷越好：取回费与解冻时间要一起算，归档层放进在线路径会打穿 RTO（见 [39.3 存储分级](../../L3-质量属性/39-成本/39.3-存储分级.md)）。

### 选型反例：看着便宜，账在别处

| 反例 | 为什么有人这么选 | 后果（量化） |
|---|---|---|
| 把对象存储当数据库 | 0.12 元/GB·月，比块便宜约 8 倍 | 每次更新重传整个对象：10MB 对象改 1KB，写放大约 1 万倍（10,240 倍）；无事务与范围索引，并发写要靠条件请求自己实现 |
| 把块存储当共享盘 | 延迟最低，多挂一台就像共享盘 | 无集群文件系统时两节点写同一卷会互相踩坏，需停机 fsck；K8s 的 RWO 卷也只有单节点可写 |
| 用文件存储存海量小文件 | 按容量计价，看起来和对象差不多 | 元数据先撑不住：1 亿对象约 14GB 内存量级（见 [10.6 元数据管理与副本放置](10.6-元数据管理与副本放置.md)）；小文件在对象侧同样被请求费咬 |
| 标准对象层存 7 年不读的数据 | 0.12 元/GB·月，省心 | 比归档层 0.033 贵约 3.6 倍；100TB 一年多付约 10.7 万元 |
| 只看容量单价，不算请求与出口 | 容量费 12,288 元/月，看着很便宜 | 请求 + 出口 4,808 元/月，占对象账单 28%；公网出口比例升到 100%，出口费 15,360 元反超容量费 |
| 把归档层放进在线读取路径 | 0.033 元/GB·月，容量最便宜 | 取回约 0.06 元/GB + 解冻小时级：100TB 读一遍约 6,144 元（约 1.8 个月容量费），RTO 被解冻时间打穿 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 “最快” 的块存储存所有东西 | 成本 3–10 倍，且没换来收益 |
| 用对象存储跑数据库 | 无随机写/fsync，事务不可用 |
| 文件存储存海量小文件 | 元数据操作打满 |
| 不做生命周期 | 冷数据一直按热数据计费（见 [5.6 云成本结构](../5-云计算基础/5.6-云成本结构.md)） |
| 只选一种存储 | 所有场景都妥协，成本与性能双输 |
| 只看单价不看请求/取回费用 | 账单超预期，小文件场景尤甚 |

## 三条铁律

> 🔑 **先按访问语义排除，再按成本择优**；语义不匹配的存储，性能再好也用不了。

> 🔑 **分层看访问频率**，不看数据 “重要性”。

> 🔑 **备份与存储是两件事**：同一种介质上的两份拷贝，不叫备份（见 [10.4 快照与备份](10.4-快照与备份.md)）。

## 自检

**Q1** 一个图片社区要存 500TB 用户上传，怎么选？

▸ 答案：**对象存储 + CDN**。理由：一次写多次读、按 URL 取、规模大且增长快、成本敏感。需要 “缩略图/裁剪” 时在写入时生成派生对象，而不是运行时改原图。访问热点用 CDN 挡住，对象层的请求费与延迟都能降下来（见 [9.1 边缘缓存原理](../9-CDN与边缘/9.1-边缘缓存原理.md)）。

**Q2** 为什么数据库不选文件存储（NFS）？

▸ 答案：因为数据库依赖严格的 POSIX 语义（`fsync`、文件锁、`rename` 原子性），而 NFS 的缓存与锁是弱语义，多客户端下可能出现 “以为落盘实际没有”，崩溃恢复即损坏。数据库要么用块设备，要么用支持 POSIX 的本地文件系统。

**Q3** 分层存储里最容易被忽略的成本是什么？

▸ 答案：**取回成本与请求费**。归档层单价很低，但取回有延迟与按 GB 的取回费；对象存储的 GET/LIST 也按请求计费。很多团队把日志放冷层省了容量费，却因为频繁回捞把请求费花超（见 [5.6 云成本结构](../5-云计算基础/5.6-云成本结构.md)）。

**Q4** “数据很重要，所以放最贵的存储” 错在哪？

▸ 答案：错在把 **重要性** 与 **访问频率/延迟要求** 混为一谈。重要性应该体现为 “多副本 + 独立备份 + 权限与审计”，而不是 “放在最快的介质上”。一份一年读一次的合规数据，放在归档层 + 异地备份，比放在 NVMe 上更安全也更便宜。

**Q5** 什么时候值得上分布式文件系统（自建/托管）？

▸ 答案：需要**多机共享目录 + POSIX 语义**，且规模超过单机 NFS 的能力时（如渲染农场、HPC、AI 训练读取海量小文件）。代价是运维复杂度与元数据瓶颈。若只是 “共享上传目录”，NFS 或对象存储 + 应用层适配更简单（见 [10.5 分布式文件系统 (GFS / HDFS 架构)](10.5-分布式文件系统.md)）。

**Q6** 为什么 “先把数据放对象存储，以后需要再迁到块” 通常不划算？

▸ 答案：因为迁移要**全量搬运**（时间 + 出口流量费），且应用要改访问方式（文件语义 → HTTP API）。更常见的路径是反过来：热数据在块/文件上跑，冷数据生命周期下沉到对象存储，方向与访问频率一致。
