                  10.3 云盘性能模型 (IOPS / 吞吐 / 延迟)

                  一句话

                  云盘性能由三个数共同决定：IOPS（每秒操作数）、吞吐（MB/s）、延迟；它们不是独立的——小块卡 IOPS、大块卡带宽，选规格时要同时满足两者，而不是只看 “最大 IOPS”。

                  三个指标的关系

                  吞吐 = IOPS × 块大小
例：3000 IOPS × 4KB  = 12 MB/s
    3000 IOPS × 1MB  = 3000 MB/s（实际被带宽上限截断）
                  块大小 IOPS 3000 时的吞吐 瓶颈
                  4KB 12 MB/s IOPS
                  16KB 47 MB/s IOPS
                  64KB 188 MB/s 过渡区
                  256KB 750 MB/s 带宽
                  1MB 3000 MB/s（理论） 带宽

                  本机实测（仅示意量级）

                  4K 写 + fsync 的延迟（本机 NVMe，50 次）：

                  指标 值
                  P50 0.02ms
                  P99 0.22ms
                  单线程 IOPS ≈ 48,000（P50 口径）

                  云盘通常远低于这个数（网络存储、多租户共享），所以 “本机测出来的 IOPS” 不能直接当云盘规格；必须按云厂商的规格表 + 实测校准。

                  选型：先看 “访问模式”，再看规格

                  负载 关键指标 规格建议
                  数据库（OLTP） IOPS + 低延迟 高 IOPS 型，块 4–16KB
                  日志/顺序写 吞吐 高吞吐型，块 64KB–1MB
                  大数据扫描 吞吐 高吞吐型 + 多盘并行
                  小文件随机读 IOPS + 延迟 高 IOPS + 缓存
                  # 用 fio 量真实 IOPS/延迟（云上务必在业务时段测，避免被“突发额度”骗）
fio --name=randread --rw=randread --bs=4k --iodepth=32 --numjobs=4 \
    --filename=/data/fio.test --size=4G --runtime=60 --time_based \
    --output-format=json | jq '.jobs[0].read.iops, .jobs[0].read.clat_ns.percentile'

                  换算：IOPS、块大小、吞吐与延迟的四则运算

                  先给结论：云盘规格表上的「IOPS 上限 / 吞吐上限 / 延迟」不是三个独立旋钮，而是同一台设备的三个投影。给定块大小与队列深度，另外两个就被确定——你只能选「先撞哪堵墙」，不能三个都要。

                  两个公式，四个变量

                  吞吐(MB/s) = IOPS × 块大小(KB) / 1024
IOPS      = 队列深度 QD / 平均延迟(s)

                  第二行是 Little 定律 L = λ × W 的存储版：在途 IO 数 = 完成速率 × 停留时间。连接池里算「并发 = QPS × 延迟」用的是同一个式子（8.3 连接复用与 TIME_WAIT），通用推导与四个前提见 34.2 性能建模。换成存储口径只改三个名字：并发 → 队列深度，QPS → IOPS，延迟不变。

                  两个公式合起来是一个闭环：延迟决定「每个 IO 占队列多久」，队列深度决定「同时有多少 IO 在途」，两者相除就是 IOPS；IOPS 乘块大小才是吞吐。 任何一环被固定，另外两个就被反推出来。

                  单位上只有一个坑：云厂商说的 4KB 是 4KiB（4096 字节），换算用 1024；标称吞吐的 MB/s 与文件系统里 dd 报的 MiB/s 差 4.9%，对不上时先统一单位再判断。另一个坑是厂商标称的 IOPS 必须带「块大小 + 队列深度」才有意义：只写「最大 20 万 IOPS」而不写测试条件的，通常是缓存命中或极小块的营销数字，不能拿来算吞吐。

                  这道算术的用途不是预测性能，而是排雷：拿到规格先算 B*，就知道自己的块大小会先撞哪堵墙；压测数字与「QD ÷ 延迟」对不上，说明测的是缓存、突发额度，或者根本没跑到稳态。

                  四组参数：同一块盘，四种命

                  取一组公开量级的规格：IOPS 上限 20,000、吞吐上限 500MB/s、空载单次延迟 0.20ms。用「IOPS 上限、队列能供的 IOPS、带宽换算的 IOPS」三者取小算有效值：

                  块大小 QD 有效 IOPS 吞吐 MB/s 平均延迟 ms 先撞的墙
                  4KB 1 5,000 19.5 0.20 队列深度
                  4KB 32 20,000 78.1 1.60 IOPS
                  16KB 32 20,000 312.5 1.60 IOPS
                  64KB 32 8,000 500.0 4.00 带宽

                  把四组参数摆在一起，三者的互斥就清楚了：要 0.20ms 的单次延迟，QD=1 只能供出 5,000 IOPS；要 20,000 IOPS，平均延迟必然到 1.6ms；要 500MB/s 吞吐，块得取 64KB，延迟到 4ms。规格表把三个数并列写，不等于能同时拿到。

                  五个读法：

                  • QD=1 那行的 0.20ms 最漂亮，吞吐却只有 19.5MB/s：单线程一次只让一个 IO 在途，延迟再低也换算不出并发。5,000 × 4KB = 19.5MB/s。
                  • 4KB/QD=32 的 1.6ms 不是厂商标的延迟：厂商标的是空载单次延迟，1.6ms 是 32 个 IO 排队后每个 IO 的平均停留时间，用 Little 反推 32 ÷ 20,000 = 1.6ms。延迟随队列深度上涨是排队，不是故障。
                  • 64KB/QD=32 只有 8,000 IOPS，却已跑满 500MB/s：500MB/s ÷ 64KB = 8,000。带宽封顶时，规格里的高 IOPS 被块大小除没了。
                  • QD 不是越大越好：QD 从 1 加到 32，IOPS 从 5,000 涨到 20,000（4 倍），但延迟从 0.20ms 涨到 1.60ms（8 倍）。Little 定律保的是平均值，不保尾部——继续压 QD，平均 IOPS 不再涨，P99 先崩。数据库盘的 QD 该按「目标 IOPS × P99 延迟」反推，而不是照抄压测脚本的 32/64。
                  • 延迟有三个口径：空载单次（厂商规格，0.20ms）、平均值（Little 反推，1.60ms）、P99（业务真正感知的尾部）。三者能差 5–10 倍，监控只看平均延迟，等于没看。

                  先撞哪堵墙：一张判断表

                  把块大小与「吞吐上限 ÷ IOPS 上限」的比值一比，墙的位置就定了：

                  平衡块大小 B* = 吞吐上限 ÷ IOPS 上限 × 1024
例：500MB/s ÷ 20,000 IOPS × 1024 = 25.6KB
                  你的负载 判据 先撞的墙 现象 先动什么
                  4K/8K 随机读写 块 < B* IOPS 墙 吞吐远低于规格，IOPS 先满 换高 IOPS 盘型，或读缓存、合并小 IO
                  64KB+ 顺序读写 块 > B* 带宽墙 IOPS 只用四成，吞吐先满 换高吞吐盘型，或加条带并列
                  单线程压测 QD < IOPS 目标 × 空载延迟 队列深度墙 数字只有规格的 1/4 加并发（多线程 / io_uring / 多队列）
                  延迟敏感型 P99 超过目标 延迟墙 IOPS、吞吐都没满，P99 先超 查邻居与突发额度，换低延迟盘型或做缓存

                  🔑 换盘型还是加条带，判据只有一条：随机 IO 看「IOPS 是否封顶」，顺序 IO 看「带宽是否封顶」。用顺序压测的结果去证明随机负载够用，是最常见的自证陷阱。

                  换盘型还是加条带：先算条带数

                  换盘型与加条带都是「把单盘上限叠上去」，但算法不同：

                  随机 IO：条带数 N ≥ 目标 IOPS ÷ 单盘同块大小 IOPS
顺序 IO：条带数 N ≥ 目标吞吐 ÷ 单盘顺序吞吐

                  例：目标 60,000 IOPS（4K 随机读），单盘 20,000 → N=3；若这 60,000 是 RAID5 的随机写，每逻辑写要 4 个物理 IO（读-改-写 + 校验），N 要 12 才够。目标 2GB/s 顺序读、单盘 500MB/s → N=4。

                  先换盘型、后上条带：单盘升规格只改一个参数；条带会同时放大故障域、运维复杂度与重建风险（重建读放大见 10.7 纠删码与副本的取舍）。只有当「单盘规格已封顶」或「容量单盘给不了」时才上条带。

                  反向用这两个公式，能回答日常最常问的三类问题：

                  • 目标 200MB/s、块 64KB → 需要 200 × 1024 ÷ 64 = 3,200 IOPS，对照规格表就知道够不够；
                  • 目标 P99 1ms、QD 32 → 最多撑 32 ÷ 1ms = 32,000 IOPS，再高必然排队；
                  • 已知 IOPS 18,000、QD 24 → 平均延迟至少 24 ÷ 18,000 = 1.33ms，应用超时阈值要按这个数设，而不是按规格表的 0.20ms。

                  代码：给三个数，反推两个数并标出撞墙点

                  #!/usr/bin/env python3
# 云盘三数换算：IOPS / 块大小 / 队列深度 → 吞吐、延迟、先撞哪堵墙。
# 本机计算（macOS 15.6 / Apple M1 / Python 3.14.8），规格上限为公开量级。
IOPS_SPEC = 20_000          # 规格：IOPS 上限
TPUT_SPEC_MB = 500.0        # 规格：吞吐上限 MB/s
LAT_IDLE_MS = 0.20          # 规格：空载单次延迟 ms


def q(iops_target, kb, qd):
    # 规格允许的有效 IOPS = 四个上限里最小的那个
    iops_by_tput = TPUT_SPEC_MB * 1024 / kb          # 吞吐封顶换算出的 IOPS
    iops_by_qd = qd / (LAT_IDLE_MS / 1000)           # 队列深度 / 空载延迟 能供出的 IOPS
    iops = min(iops_target, IOPS_SPEC, iops_by_tput, iops_by_qd)
    tput = iops * kb / 1024                          # 吞吐 = IOPS × 块大小
    lat_ms = qd / iops * 1000                        # Little: 延迟 = QD / IOPS
    wall = ("带宽" if iops == iops_by_tput else
            "队列深度" if iops == iops_by_qd else
            "IOPS" if iops == IOPS_SPEC else "目标")
    return iops, tput, lat_ms, wall


print("规格：%d IOPS / %.0f MB/s / 空载单次延迟 %.2fms" % (IOPS_SPEC, TPUT_SPEC_MB, LAT_IDLE_MS))
for kb, qd in [(4, 1), (4, 32), (16, 32), (64, 32)]:
    iops, tput, lat, wall = q(10**9, kb, qd)   # IOPS 目标设得足够大，让规格上限生效
    print("%2dKB  QD=%-3d IOPS=%-6.0f 吞吐=%6.1fMB/s 平均延迟=%.2fms 先撞=%s"
          % (kb, qd, iops, tput, lat, wall))

bstar = TPUT_SPEC_MB * 1024 / IOPS_SPEC
print("\n平衡块大小 B* = %.1fKB（块小于它先撞 IOPS，大于它先撞带宽）" % bstar)
print("在 %.2fms 下跑满 %d IOPS，至少需要 QD = %.0f"
      % (LAT_IDLE_MS, IOPS_SPEC, IOPS_SPEC * LAT_IDLE_MS / 1000))

# 单独问一个：目标 20000 IOPS + 64KB + QD=32 会发生什么
iops, tput, lat, wall = q(20_000, 64, 32)
print("\n示例：目标 20000 IOPS / 64KB / QD=32")
print("  实际 IOPS=%.0f，吞吐=%.1fMB/s，平均延迟=%.2fms，先撞=%s"
      % (iops, tput, lat, wall))
print("  64KB 跑满 %.0fMB/s 只需 %.0f IOPS，规格里的高 IOPS 在这个块大小下用不上"
      % (TPUT_SPEC_MB, TPUT_SPEC_MB * 1024 / 64))

                  本机计算输出（规格上限为公开量级）：

                  规格：20000 IOPS / 500 MB/s / 空载单次延迟 0.20ms
 4KB  QD=1   IOPS=5000   吞吐=  19.5MB/s 平均延迟=0.20ms 先撞=队列深度
 4KB  QD=32  IOPS=20000  吞吐=  78.1MB/s 平均延迟=1.60ms 先撞=IOPS
16KB  QD=32  IOPS=20000  吞吐= 312.5MB/s 平均延迟=1.60ms 先撞=IOPS
64KB  QD=32  IOPS=8000   吞吐= 500.0MB/s 平均延迟=4.00ms 先撞=带宽

平衡块大小 B* = 25.6KB（块小于它先撞 IOPS，大于它先撞带宽）
在 0.20ms 下跑满 20000 IOPS，至少需要 QD = 4

示例：目标 20000 IOPS / 64KB / QD=32
  实际 IOPS=8000，吞吐=500.0MB/s，平均延迟=4.00ms，先撞=带宽
  64KB 跑满 500MB/s 只需 8000 IOPS，规格里的高 IOPS 在这个块大小下用不上

                  落成动作：

                  1. 显示「队列深度墙」→ 先加并发，别换盘：单线程 4K 随机读只能到 5,000 IOPS，换再贵的盘还是 5,000。
                  2. 显示「IOPS 墙」或「带宽墙」→ 按上面的条带公式算 N；N=1 说明该换盘型，N>1 说明该加条带。
                  3. 三种墙都不撞、业务仍慢 → 不是盘的问题，去查文件系统、锁与串行化。

                  反模式

                  反模式 后果
                  只看 “最大 IOPS” 不看块大小 实际吞吐被 IOPS 卡死（4K → 12MB/s）
                  用突发额度评估容量 额度耗尽后性能断崖
                  单盘跑数据库 + 备份 备份把 IOPS 吃光，事务延迟飙升
                  忽略队列深度 单线程测不出云盘真实能力
                  把 “本机 NVMe” 数据当云盘 高估 10–100 倍
                  不做 P99 延迟监控 只看平均，尾部卡顿被掩盖

                  三条铁律

                  🔑 吞吐 = IOPS × 块大小；两者要同时满足。

                  🔑 小块看 IOPS、大块看带宽；按访问模式选型。

                  🔑 规格表 ≠ 实测；上云后必须用真实负载校准。

                  自检

                  Q1 为什么 “3000 IOPS 的盘” 在 4K 随机写下只有 12MB/s？

                  ▸ 答案：因为每次操作只搬 4KB：3000 × 4KB = 12MB/s。这不是盘 “慢”，而是 “操作数上限” 限制了小块的吞吐。要更高吞吐，必须增大块（批量合并）或换更高 IOPS 的规格。

                  Q2 队列深度为什么影响测出来的 IOPS？

                  ▸ 答案：因为单线程串行请求时，IOPS 受 “单次延迟” 限制（IOPS ≈ 1/延迟）；增加队列深度可以让多个请求并行，逼近设备的并发能力。云盘通常需要 iodepth ≥ 32 才能测出标称 IOPS。

                  Q3 “突发额度（burst）” 会带来什么误判？

                  ▸ 答案：短时间压测会消耗突发额度，读出 “很高的 IOPS”；额度耗尽后跌回基线，生产上表现为 “跑一会儿就变慢”。评估容量必须持续压测（超过额度恢复周期），而不是跑 10 秒。

                  Q4 数据库盘为什么不能和备份共用？

                  ▸ 答案：因为备份是大块顺序读/写，会占满带宽与 IOPS 队列；数据库需要低延迟的小块随机 IO，两者争抢时数据库延迟飙升。常见做法是 “数据盘 + 日志盘分离 + 备份走独立盘/对象存储”。

                  Q5 P99 延迟为什么比平均延迟重要？

                  ▸ 答案：因为云盘是多租户共享，尾部延迟受邻居影响：平均值可能很漂亮，P99 却高一个数量级。数据库/在线服务的超时是按 “最慢请求” 触发的，所以要看 P99/P999，而不是平均。

                  Q6 什么时候该 “多盘并行” 而不是 “换更大规格”？

                  ▸ 答案：当单盘规格到了上限（IOPS/带宽封顶）而需求继续增长时：用多盘做 RAID0/条带，把 IOPS 与带宽叠加。代价是 “单盘故障影响面” 与 “运维复杂度”，需要配合副本/纠删码保证持久性。

                  Q7 如何判断 “盘是不是瓶颈”？

                  ▸ 答案：看三个信号：await/延迟上升（排队）、%util 接近饱和（机械盘）、应用 P99 与 IO 延迟同步恶化。如果 CPU 不高、IO 延迟高，基本就是盘；如果 CPU 高、IO 不高，先查计算与锁。
