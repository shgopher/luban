# 14.3 配置管理与漂移检测

## 一句话

> 配置管理的目标不是 “有个地方存配置”，而是 **“声明的配置 = 实际运行的配置”**；两者一旦分叉就是**漂移**——漂移不会自己消失，只会在下次发布时把线上改回旧值，或把手工修复悄悄抹掉。

## 配置的三种形态

| 形态 | 例子 | 风险 |
|---|---|---|
| 代码内配置 | 常量、feature flag 默认值 | 改配置要发版 |
| 配置中心 | etcd/Nacos/Apollo | 需权限与审计，否则谁都能改 |
| 环境变量/挂载文件 | K8s ConfigMap/Secret | 与代码版本不同步，易漂移 |

原则：**配置要版本化、可审计、可回滚**；密钥不进配置（见 [13.4 密钥与凭证管理](../13-基础设施安全/13.4-密钥与凭证管理.md)）。

## 实测：漂移检测的最小实现

对 “期望配置” 与 “实际配置” 做规范化后比对（哈希/逐字段）：

| 检查 | 结果 |
|---|---|
| 期望哈希 vs 实际哈希 | 不一致 → 漂移 |
| 差异字段 | 如 `replicas: 3 → 5`、`image: v1.2 → v1.3` |
| 漂移数量 | 本次 2 个字段，其中 1 个是 “手工扩容” |

```bash
# 声明式对比：期望（Git）vs 实际（集群）
kubectl diff -f deploy/            # 直接给出将发生的变更（含漂移）
# 只看漂移（不含本次要发布的变更）：先 apply --dry-run，再 diff
terraform plan -detailed-exitcode  # 0=无变化 1=有错误 2=有差异
```

判据：**`plan`/`diff` 长期不为空 = 有漂移**，必须查明来源（手工改？其他工具？云厂商默认值？）。

## 漂移的三种来源与对策

| 来源 | 例子 | 对策 |
|---|---|---|
| 手工改控制台 | 紧急扩容、改安全组 | 变更回写 IaC；或明确 “临时变更需登记 + 到期回收” |
| 其他工具/脚本 | 运维脚本改了配置 | 收敛到单一入口（IaC 或配置中心） |
| 云侧默认值/自动行为 | 托管服务自动升级、默认参数 | 显式声明，不依赖默认值 |

## 漂移检测的三种实现与告警阈值

漂移检测要同时回答三个问题：**多久能发现**、**能覆盖哪些偏离**、**发现之后做什么**。三个答案不同，选型就不同：定时全量 diff 覆盖广但发现慢；事件驱动快，却看不见“没有事件源”的变更；定期 reconcile 最快、还能自动纠正，但它的覆盖面与全量 diff 一样——**都只看得见被 IaC 声明过的资源**。

### 三种实现对比

| 实现 | 发现延迟 | 检测成本（每轮） | 漏报率 | 发现后 |
|---|---|---|---|---|
| 定时全量 diff | 周期 15min → 平均 7.5min，最坏 15min | O(N) 次读取，N = 受管资源数 | 25% | 只报告；纠正靠下一次 `apply` 或人工 |
| 事件驱动（webhook / audit log） | 入库 1s + 聚合窗口 5s → 平均 3.5s | O(变更数) 次读取 | 40% | 只报告 |
| 期望态定期 reconcile | 周期 30s → 平均 15s，最坏 30s | O(N)，控制器缓存全量状态 | 25% | **直接收敛**：发现即纠正 |

定时全量 diff 就是定期跑 `terraform plan -detailed-exitcode` 或 `kubectl diff`，退出码为 2 即存在差异（判据见 [14.2 Terraform 与声明式基础设施](14.2-Terraform与声明式基础设施.md)）。它的成本与资源数成正比，周期只能取“分钟级”；事件驱动的成本与变更数成正比，可以做到秒级，但**依赖事件源存在**。

漏报率不是行业统计，而是“哪些漂移来源有信号”的加权结果：

| 漂移来源（示例权重） | 定时全量 diff | 事件驱动 | reconcile |
|---|---|---|---|
| 控制台手改（有审计事件）35% | ✓ | ✓ | ✓ |
| 脚本直调 API（无事件）15% | ✓ | ✗ | ✓ |
| 资源删除（有事件）10% | ✓ | ✓ | ✓ |
| 云厂商默认值变化（未声明）15% | ✗ | ✗ | ✗ |
| 权限变更（不在 IaC 内）10% | ✗ | ✗ | ✗ |
| 应急 hotfix 未回写（有事件）15% | ✓ | ✓ | ✓ |
| **加权漏报率** | **25%** | **40%** | **25%** |

换成自家审计数据，数字会变，但排序不变：**事件驱动漏在“没有事件源”的变更，另外两种漏在“根本没被声明”的资源**。这也解释了为什么 reconcile 不能替代全量 diff——它只是把“发现 → 纠正”的延迟从一轮发布压到一轮巡检，覆盖面一点没扩。

三种实现不是三选一，而是叠放：**事件驱动做秒级快报，定时全量做兜底，reconcile 只对“允许自动纠正”的分级开启**。把 reconcile 开到权限与资源删除上，等于给平台配一把自动撤权、自动重建的刀。

### 漂移分级：哪些告警，哪些自动纠正

自动纠正的充要条件只有三条：**可逆（改回不丢数据）、可重放（重建不会用错版本）、不碰安全边界（权限、密钥）**。三条把四类漂移切得很干净：

| 分级 | 典型漂移 | 检测信号 | 默认动作 | 判据 |
|---|---|---|---|---|
| 手工 hotfix | `replicas: 3 → 5`、`image: v1.2.0 → v1.2.1` | 与 Git 不一致，且有审计事件 | **告警 P2，不自动纠正** | 正在生效的应急修复被抹掉 = 二次故障；24h 未回写升 P1 |
| 配置项新增/修改 | `LOG_LEVEL: info → debug`、多出 `TRACE_SAMPLE` | 规范化 diff 出现 added / modified | **自动纠正 P3** | 可逆、改回不丢数据；键名含 `SECRET`/`PASSWORD`/`TOKEN` 时转告警 |
| 资源删除 | 定时任务、命名空间从集群消失 | removed 且对象确实不存在 | **告警 P1，不自动重建** | 重建可能用错镜像版本或丢数据，先查事件单 |
| 权限变更 | `iam.role: orders-read → orders-admin` | IAM 策略与基线不一致 | **告警 P0，不自动撤权** | 自动撤权可能打断合法的应急授权，交安全值班确认 |

反直觉的一条：**手工 hotfix 恰恰不能自动纠正**。它的名字已经说明它是“为止血而临时偏航”——平台在事故进行中把期望态改回去，等于把止血带松掉。正确动作是告警 + 限期回写，而不是收敛。

```python
#!/usr/bin/env python3
"""14.3 漂移检测：desired vs actual 规范化 diff + 分级动作（Python 3.14）"""
IGNORE = {"deployment.creation_timestamp", "deployment.resource_version", "deployment.status.ready"}
MISSING = object()

# 期望态来自 Git；实际态从集群 API 读回（含服务端自动生成字段）
DESIRED = {
    "deployment": {"replicas": 3, "image": "registry.internal/orders:v1.2.0",
                   "env": {"LOG_LEVEL": "info", "DB_POOL": "20"},
                   "resources": {"cpu": "500m", "memory": "512Mi"}},
    "service": {"type": "ClusterIP", "port": 8080},
    "job_backfill": {"schedule": "0 3 * * *", "enabled": True},
    "iam": {"role": "orders-read", "bindings": ["team-orders"]},
}
ACTUAL = {
    "deployment": {"replicas": 5,                      # 手工 hotfix 扩容
                   "image": "registry.internal/orders:v1.2.1",   # 绕过流水线热修
                   "env": {"LOG_LEVEL": "debug", "DB_POOL": "20", "TRACE_SAMPLE": "0.1"},
                   "resources": {"cpu": "500m", "memory": "512Mi"},
                   "creation_timestamp": "2026-11-20T10:00:00Z",  # 服务端字段
                   "resource_version": "88421", "status": {"ready": 5}},
    "service": {"type": "ClusterIP", "port": 8080},
    # job_backfill 在集群里已不存在（资源删除）
    "iam": {"role": "orders-admin", "bindings": ["team-orders"]},   # 权限变更
}

# 分级策略：分级 -> (级别, 默认动作, 理由)
POLICY = {
    "权限变更": ("P0", "告警", "禁止自动纠正：自动撤权可能中断合法应急授权"),
    "资源删除": ("P1", "告警", "禁止自动重建：可能用错版本或丢数据，先查事件单"),
    "手工 hotfix": ("P2", "告警", "不自动纠正：可能抹掉正在生效的应急修复，24h 未回写升 P1"),
    "配置项新增/修改": ("P3", "自动纠正", "非敏感键：恢复 desired 并写审计"),
}
SENSITIVE = ("SECRET", "PASSWORD", "TOKEN", "KEY")


def normalize(node, prefix="", dropped=None):
    """递归删除服务端自动生成字段，避免“假漂移”"""
    dropped = [] if dropped is None else dropped
    if not isinstance(node, dict):
        return node, dropped
    out = {}
    for key, val in node.items():
        path = f"{prefix}.{key}" if prefix else key
        if path in IGNORE:
            dropped.append(path)
            continue
        normalized, _ = normalize(val, path, dropped)
        if not (isinstance(val, dict) and normalized == {}):   # 整棵子树都是服务端字段
            out[key] = normalized
    return out, dropped


def walk(desired, actual, prefix="", diffs=None):
    """逐字段比对，产出 (kind, path, desired, actual)"""
    diffs = [] if diffs is None else diffs
    for key in sorted(set(desired) | set(actual)):
        path = f"{prefix}.{key}" if prefix else key
        d, a = desired.get(key, MISSING), actual.get(key, MISSING)
        if d == a:
            continue
        if isinstance(d, dict) and isinstance(a, dict):
            walk(d, a, path, diffs)
            continue
        kind = "added" if d is MISSING else "removed" if a is MISSING else "modified"
        diffs.append((kind, path, None if d is MISSING else d, None if a is MISSING else a))
    return diffs


def classify(kind, path):
    if path.startswith(("iam.", "rbac.")):
        return "权限变更"
    if kind == "removed" and "." not in path:
        return "资源删除"
    if path.endswith((".image", ".replicas")):
        return "手工 hotfix"
    return "配置项新增/修改"


def verdict(kind, path):
    grade, action, why = POLICY[classify(kind, path)]
    if action == "自动纠正" and any(s in path.upper() for s in SENSITIVE):
        return grade, "告警", "敏感键不自动纠正：改回可能导致密钥失效"
    return grade, action, why


clean_desired, _ = normalize(DESIRED)
clean_actual, dropped = normalize(ACTUAL)
diffs = walk(clean_desired, clean_actual)
print(f"== 1. 规范化：剔除 {len(dropped)} 个服务端字段：{', '.join(sorted(dropped))}")

print(f"\n== 2. 差异：desired -> actual，共 {len(diffs)} 项 ==")
for kind, path, d, a in diffs:
    print(f"{kind:<9} | {path:<32} | {d} -> {a}")

print("\n== 3. 分级与动作 ==")
for kind, path, _, _ in diffs:
    grade, action, why = verdict(kind, path)
    print(f"[{grade}][{action}] {path:<32} {classify(kind, path)}：{why}")

alerts = sum(1 for kind, path, _, _ in diffs if verdict(kind, path)[1] == "告警")
print(f"\n== 4. 统计 ==\n{len(diffs)} 项漂移：告警 {alerts} 项，自动纠正 {len(diffs) - alerts} 项，忽略 {len(dropped)} 项")
```

本机运行（macOS 15.6 / Apple M1 / Python 3.14.8）：

```
== 1. 规范化：剔除 3 个服务端字段：deployment.creation_timestamp, deployment.resource_version, deployment.status.ready

== 2. 差异：desired -> actual，共 6 项 ==
modified  | deployment.env.LOG_LEVEL         | info -> debug
added     | deployment.env.TRACE_SAMPLE      | None -> 0.1
modified  | deployment.image                 | registry.internal/orders:v1.2.0 -> registry.internal/orders:v1.2.1
modified  | deployment.replicas              | 3 -> 5
modified  | iam.role                         | orders-read -> orders-admin
removed   | job_backfill                     | {'schedule': '0 3 * * *', 'enabled': True} -> None

== 3. 分级与动作 ==
[P3][自动纠正] deployment.env.LOG_LEVEL         配置项新增/修改：非敏感键：恢复 desired 并写审计
[P3][自动纠正] deployment.env.TRACE_SAMPLE      配置项新增/修改：非敏感键：恢复 desired 并写审计
[P2][告警] deployment.image                 手工 hotfix：不自动纠正：可能抹掉正在生效的应急修复，24h 未回写升 P1

```

输出里有三处要对照代码看：

1. **先规范化再比对**：`creation_timestamp`、`resource_version`、`status` 被剔除，否则每轮巡检都多 3 条假漂移——这是“告警没人看”的头号来源。
2. **分级靠路径 + 操作类型**，不靠关键词猜：`iam.` 前缀 → 权限变更；顶层 removed → 资源删除；`.image`/`.replicas` → 手工 hotfix；其余配置项 → 自动纠正。
3. **自动纠正只落 P3**：6 项漂移只纠正 2 项，4 项进告警。比例反了（自动纠正占多数）就说明分级写宽了。

### 告警阈值与误报抑制

| 触发条件（任一成立） | 级别 | 响应时限 | 动作 |
|---|---|---|---|
| 权限变更或资源删除（1 项即触发） | P0 / P1 | 15min | 冻结发布 + 人工确认，禁止自动纠正 |
| 漂移项 ≥ 10 项，或影响 ≥ 2 个命名空间 | P1 | 15min | 暂停 reconcile 自动收敛，先止血 |
| 单类漂移持续 ≥ 2 个巡检周期（30min） | P2 → P1 | 1h | 升级并指派 owner |
| 手工 hotfix 1–5 项，且有进行中的事件单 | P2 | 24h 内回写 | 告警；到期未回写升 P1 |
| 配置项新增/改值（非敏感、单资源、≤ 5 项） | P3 | 24h | 自动纠正 + 审计记录 |
| 白名单 / 维护窗口内的其它漂移 | 降 1 级（最低 P3） | 按原级 | 只降级不静默，窗口结束自动恢复 |

阈值数字都有出处：15min 巡检对应平均 7.5min 发现，30min 恰好 2 个周期；10 项是“一次 `apply` 的影响面超过人工逐条核对上限”的经验线；24h 是 hotfix 回写的自然期限（跨一个工作日）；P0 的 15min 响应对齐值班的首次确认节奏。

**误报抑制的三条判据**，不满足就不许抑制：

1. **维护窗口**：必须带变更单号、起止时间、owner；窗口内只降级（P2 → P3）不静默，结束自动恢复；资源删除与权限变更不适用。
2. **白名单**：只匹配字段路径前缀（如 `deployment.env.DEBUG_*`），必须带到期日（≤ 30 天）和 owner，到期自动失效；禁止匹配 `*.image`、`*.replicas`、`iam.*`。
3. **永久忽略**：只能进规范化忽略列表（服务端默认值、时间戳），要有代码评审记录；“先别报了”不是忽略，是关告警。

> 🔑 **抑制规则自己也要被检测**：统计每条白名单/窗口的命中次数，命中率 > 80% 的规则说明“该字段本来就不该比对”，应改成规范化规则而不是长期白名单；否则白名单会从例外变成默认，漂移检测名存实亡。

## 反模式

| 反模式 | 后果 |
|---|---|
| 配置只存在控制台 | 无法版本化、无法回滚、无法审计 |
| 漂移不告警 | 下次 apply 把手工修复抹掉 |
| 配置与代码分开发布 | 版本不匹配，出现 “只有旧代码能跑” |
| 密钥写进 ConfigMap | 明文泄露（见 [13.4 密钥与凭证管理](../13-基础设施安全/13.4-密钥与凭证管理.md)） |
| 不记录 “谁改了什么” | 出事无法追责/回滚 |
| 环境间复制配置文件 | 一处改动扩散到所有环境 |

## 三条铁律

> 🔑 **配置必须有唯一来源**（Git 或配置中心），不能 “两处都能改”。

> 🔑 **漂移即告警**；`plan/diff` 长期不为空就是问题。

> 🔑 **密钥与配置分离**，配置可公开评审，密钥不可。

## 自检

**Q1** 为什么 “手工改控制台” 会造成漂移事故？

▸ 答案：因为 IaC 的 “期望状态” 没变：下次 `apply` 会把手改**改回去**。如果手改是应急修复，就会被静默抹掉，表现为 “修好的问题又回来了”。正确流程是 “改代码 → 再 apply”，临时变更要登记并限期回收。

**Q2** `terraform plan -detailed-exitcode` 的退出码怎么用？

▸ 答案：`0` 表示无变化、`1` 表示出错、`2` 表示有差异。CI 里可以 “定期跑 plan，退出码为 2 就告警”，从而把 **漂移检测自动化**；发布流水线里则用它确认 “本次变更与预期一致”。

**Q3** 配置中心与 IaC 的分工是什么？

▸ 答案：**IaC 管 “基础设施与部署形态”**（网络、副本数、资源规格），**配置中心管 “运行期可变参数”**（开关、阈值、名单）。两者都要版本化与审计，但变更频率与审批级别不同；不要用配置中心去改 “本该 IaC 管” 的东西。

**Q4** 为什么 “配置与代码分开发布” 容易出事？

▸ 答案：因为会出现**版本不匹配**：新配置配旧代码（字段不认）、旧配置配新代码（缺默认值）。解法是 “配置随制品版本化”（同一 commit 生成配置与镜像），或让代码对缺失配置有安全默认。

**Q5** 漂移检测会不会产生大量噪音？

▸ 答案：会，如果没做**规范化**：云厂商默认值、自动生成的字段、时间戳都会造成 “假漂移”。先把 “可忽略字段” 排除（如 `status`、`creationTimestamp`），再比对；否则团队会很快忽略告警。

**Q6** 多环境配置怎么避免 “复制粘贴”？

▸ 答案：用**同一份模板 + 环境 values**（如 Helm values / Terraform tfvars），模板里不写死环境差异；差异只允许出现在 values 文件里，并进代码评审。复制整份配置会在某次改动后 “三套环境不一致”。

**Q7** 怎么证明 “配置管理真的有效”？

▸ 答案：三条：**`plan/diff` 长期为空**（无漂移）、**任何一次线上变更都能追溯到 Git/配置中心的记录**、**回滚能在分钟级完成**。三者都成立，才算 “配置被管理”，而不是 “配置有个地方存着”。
