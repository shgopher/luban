# 14.1 多环境隔离 (dev / staging / prod)

## 一句话

> 多环境的目的不是 “有三套机器”，而是 **“让变更在低风险环境里暴露问题，同时保证生产环境不被误操作”**；隔离的维度是 **网络、数据、密钥、权限、配额** 五件事，少一件就会 “测试事故打到生产”。

## 五维隔离

| 维度 | dev | staging | prod |
|---|---|---|---|
| 网络 | 可访问公网、共享 VPC | 独立 VPC、可访问生产只读副本（可选） | 独立 VPC、默认拒绝入站 |
| 数据 | 假数据/脱敏 | 生产同构的脱敏数据 | 真实数据（加密 + 审计） |
| 密钥 | 测试凭证 | 测试凭证（与生产不同） | 生产密钥（KMS/Vault） |
| 权限 | 开发者可写 | 发布流水线可写 | 仅流水线 + 值班可写 |
| 配额 | 小 | 中（接近生产） | 按容量规划 |

关键：**staging 要 “像生产”**（同构、同依赖版本），否则 “测试通过” 没有意义；但 **staging 不能连生产库写**，只能读脱敏副本。

## 环境矩阵与常见配置错误

| 配置 | 常见错误 | 后果 |
|---|---|---|
| 数据库连接串 | dev 指向 staging、staging 指向 prod | 测试数据写进生产 |
| 消息队列 topic | 共用同一 topic | 测试消息被生产消费 |
| 密钥 | 三套环境同一把 key | 泄露即全线沦陷（见 [13.4 密钥与凭证管理](../13-基础设施安全/13.4-密钥与凭证管理.md)） |
| 域名/回调地址 | staging 回调打到生产 | 支付/通知串环境 |
| 定时任务 | staging 也开定时任务 | 重复跑批、重复发券 |

```yaml
# 环境配置用“同一份声明 + 不同 values”，避免手工改
# values-staging.yaml
database: {host: pg-staging.internal, name: app_staging}
features: {payment_mock: true}
cron: {enabled: false}          # staging 默认关掉定时任务
```

## 隔离成本/风险矩阵

> 结论：隔离不是“越独立越好”，每加一档都要按月付费；真正决定风险的是**故障爆炸半径**——一次凭证或主机失陷能触达几个环境。它由“网络可达”和“凭证可达”两条路径里**更差的那条**决定：任一条还共享，半径就不降。

先定义四档，每档只加一个“隔离杠杆”：

| 档位 | 做法 | 隔离强度（爆炸半径） | 月成本（n=3，示例） | 适用 |
|---|---|---|---|---|
| 共享账号 + 共享 VPC | 环境靠命名/前缀区分 | **n**（全部环境） | 2.7 万 | 个人项目、早期 dev；隔离成本高于事故损失时 |
| 独立账号（同 VPC） | 每环境一个云账号，网络仍互通 | **n**（网络可横向） | 2.9 万 | 要账单/配额/权限隔离，但网络暂时不动 |
| 独立 VPC（共享账号） | 网络不互通，云账号仍共享 | **n**（账号可操作全部） | 3.1 万 | 合规要求网络隔离、数据不出域 |
| 独立集群 + 独立账号 | 网络与凭证都独立 | **1**（只影响自身） | 3.9 万 | prod 与 staging 严格隔离；出过跨环境事故 |

中间两档经常被当成“安全投入”，但按爆炸半径它们**一分风险都没降**：独立账号只切断了“账号→其他环境”的路径，网络这条腿还通着；独立 VPC 只切断了网络，共享账号的凭证仍能操作所有环境。买到的其实是“误操作半径、账单归属、合规条款”，这些有价值，但评估标准不是“少多少事故损失”。只有最后一行把两条腿都切掉，半径才从 n 掉到 1。

把这张矩阵算成钱，就是下面的程序。参数是**示例值**（每环境资源 8,000 元/月、共享管理面 3,000 元/月、独立账号 +500、独立 VPC +1,500、独立集群 +3,000，单位均为元；单环境年事故概率 25%、单次事故损失 30 万元），换成自己的数字就能重算。环境 `go1.27.1 / darwin/arm64 / Apple M1`，`go run main.go`：

```go
// 14.1 多环境隔离 · 隔离成本/风险计算器
// 四档隔离（共享 / 独立账号 / 独立 VPC / 独立集群+独立账号）在给定环境数下的
// 年成本、故障爆炸半径、年期望损失与年总成本，并给出盈亏平衡环境数。
// 所有金额单位：元/月（月成本）或 元/年（年成本）；参数为示例值，可替换后重算。
package main

import (
	"fmt"
	"math"
)

// 示例参数（单位：元）
const (
	envCost     = 8000.0   // 每环境基础资源（计算/存储/带宽）
	sharedMgmt  = 3000.0   // 共享管理面（堡垒机/日志/监控/镜像仓库）
	accountCost = 500.0    // 每环境“独立账号”增量
	vpcCost     = 1500.0   // 每环境“独立 VPC”增量（NAT/VPN/对等连接）
	clusterCost = 3000.0   // 每环境“独立集群”增量
	pYear       = 0.25     // 单环境每年发生一次“凭证/主机失陷”事故的概率
	lossPerEnv  = 300000.0 // 单环境一次事故的直接损失
)

// 每环境年风险 = 概率 × 单环境损失
var riskPerEnv = pYear * lossPerEnv

type tier struct {
	name    string
	fixed   float64 // 与环境数无关的月成本
	perEnv  float64 // 每环境月成本
	radiusF func(n int) int
	note    string
}

// 四档：每档只加一个“隔离杠杆”
var tiers = []tier{
	{"共享账号+共享VPC", sharedMgmt, envCost, func(n int) int { return n }, "网络与凭证都共享"},
	{"独立账号（同VPC）", sharedMgmt, envCost + accountCost, func(n int) int { return n }, "凭证独立，网络仍通"},
	{"独立VPC（共享账号）", sharedMgmt, envCost + vpcCost, func(n int) int { return n }, "网络独立，凭证仍共享"},
	{"独立集群+独立账号", 0, envCost + accountCost + vpcCost + clusterCost, func(n int) int { return 1 }, "网络与凭证都独立"},
}

func monthly(t tier, n int) float64 { return t.fixed + t.perEnv*float64(n) }

// annualTotal：年成本 + 年期望损失（期望损失 = 每环境风险 × 爆炸半径）
func annualTotal(t tier, n int) float64 {
	r := t.radiusF(n)
	return monthly(t, n)*12 + riskPerEnv*float64(r)
}

func wan(v float64) float64 { return v / 10000 } // 元 → 万元

func main() {
	fmt.Println("== 参数（示例值，单位：元） ==")
	fmt.Printf("  每环境资源 %.0f/月；共享管理面 %.0f/月；独立账号 +%.0f/月；独立 VPC +%.0f/月；独立集群 +%.0f/月\n",
		envCost, sharedMgmt, accountCost, vpcCost, clusterCost)
	fmt.Printf("  单环境事故概率 %.0f%%/年；单次事故损失 %.0f 元/环境 → 每环境年风险 %.0f 元\n",
		pYear*100, lossPerEnv, riskPerEnv)

	n := 3 // 以 3 套环境（dev/staging/prod）为例
	fmt.Printf("\n== 四档隔离矩阵（环境数 n=%d） ==\n", n)
	fmt.Printf("%-18s %-10s %-10s %-8s %-12s %-12s %s\n",
		"档位", "月成本/万", "年成本/万", "爆炸半径", "年期望损失/万", "年总成本/万", "相对共享档")
	base := annualTotal(tiers[0], n)
	for _, t := range tiers {
		m := monthly(t, n)
		r := t.radiusF(n)
		total := annualTotal(t, n)
		fmt.Printf("%-18s %-10.1f %-10.1f %-8d %-12.1f %-12.1f %+.1f 万\n",
			t.name, wan(m), wan(m*12), r, wan(riskPerEnv*float64(r)), wan(total), wan(total-base))
	}

	fmt.Println("\n== 环境数敏感表：共享档 vs 全隔离档（年总成本/万） ==")
	fmt.Printf("%-6s %-14s %-14s %-10s %s\n", "环境数", "共享账号+共享VPC", "独立集群+独立账号", "更优档位", "差额/万")
	for k := 2; k <= 8; k++ {
		a := annualTotal(tiers[0], k)
		b := annualTotal(tiers[3], k)
		better, diff := "共享档", a-b
		if b < a {
			better, diff = "全隔离", a-b
		}
		fmt.Printf("%-6d %-14.1f %-14.1f %-10s %.1f\n", k, wan(a), wan(b), better, wan(diff))
	}

	// 盈亏平衡：全隔离档与共享档的年总成本相等时的环境数
	// 年成本差 = 12*(perEnv3 - perEnv0)*n + 12*fixed3 - 12*fixed0；风险节省 = riskPerEnv*(n-1)
	costPerEnvDiff := 12 * (tiers[3].perEnv - tiers[0].perEnv)
	fixedDiff := 12 * (tiers[3].fixed - tiers[0].fixed) // 为负：全隔离没有共享管理面
	breakEven := (riskPerEnv + fixedDiff) / (riskPerEnv - (tiers[3].perEnv-tiers[0].perEnv)*12)
	if breakEven < 0 {
		breakEven = 0
	}
	fmt.Printf("\n== 盈亏平衡 ==\n")
	fmt.Printf("  每多一套环境，全隔离档比共享档每年多花 %.0f 元，但少担 %.0f 元期望损失\n",
		costPerEnvDiff, riskPerEnv)
	fmt.Printf("  解得盈亏平衡环境数 n* = %.2f → 环境数 ≥ %d 时，全隔离档的年总成本更低\n",
		breakEven, int(math.Ceil(breakEven)))

	// 反推：n=3 时，单次事故损失要多大，全隔离才划算？
	// 风险节省 = 2*P*loss，需 > 年成本差
	costDiff3 := annualTotal(tiers[3], 3) - annualTotal(tiers[0], 3) + 2*riskPerEnv
	needLoss := costDiff3 / (2 * pYear)
	fmt.Printf("  n=3 时：单次事故损失超过 %.0f 元（概率 %.0f%%/年）全隔离才开始划算\n", needLoss, pYear*100)
}
```

三个读法：

1. **盈亏平衡环境数 n\* ≈ 2.6**：环境数 ≥ 3 时，全隔离档的年总成本已经低于共享档（示例参数下每年省 0.6 万）；2 套环境时共享档更省（0.9 万）。把参数换掉，结论会移动——公式在程序里：`n* = (R − 12×共享管理面) / (R − 12×(全隔离单价 − 基础单价))`，其中 `R` 是每环境年风险（概率 × 损失）。
2. **中间两档被完全支配**：独立账号每年多花 1.8 万、独立 VPC 多花 5.4 万，期望损失一分不减，所以纯经济账上不如不做；但“合规要求网络隔离”这类硬约束不看期望值，此时该做，只是别把它记到“安全收益”账上。
3. **反推单次事故损失阈值**：n=3 时，单次事故损失超过 28.8 万元（年概率 25%）全隔离才开始划算。如果你们的单次事故损失在百万级（核心交易、用户数据泄露），这个阈值在 1–2 套环境时就已越过。

**我的判断**（不是算出来的结论）：落地不必全有或全无，按环境角色分三档最经济——prod 从“独立账号 + 独立 VPC”起步（必要时再独立集群），staging 独立账号但网络单向（只允许拉取脱敏数据），dev 共享档但用配额与命名隔离。决策依据不是“我们有几个环境”，而是两个问题：**单次事故损失是否超过 10 万**（决定经济性），**是否有合规条款要求**（一票否决）。

这套模型有三处简化，说清楚才能用：① 只算单位经济，没算合规罚款、客户流失、声誉损失这些非线性尾部——真实事故损失通常比“直接损失”高一个量级；② 没算隔离带来的运维复杂度（每环境一套 IaC、观测、值班、密钥，见 [14.2 Terraform 与声明式基础设施](14.2-Terraform与声明式基础设施.md)），环境一多这部分会反超机器成本；③ 参数是示例值不是云厂商报价，同一套公式代入自己的账单才有意义。最后，隔离是否生效只能靠演练验证——在 staging 故意写一次生产连接串，看它被账号、网络、审计中的哪一层拦住，这一步比算出来的任何数字都硬。

## 反模式

| 反模式 | 后果 |
|---|---|
| 环境靠 “手工配置” 维护 | 漂移成 “三套不同系统”，问题复现不了 |
| staging 连生产库（可写） | 测试数据污染生产 |
| 三套环境共用一个数据库/账号 | 隔离形同虚设 |
| staging 与生产依赖版本不同 | 测出来的结论不成立 |
| 没有 “生产变更审批/双人” | 误操作直接打生产 |
| 环境太多（dev1/dev2/qa/uat…） | 维护成本爆炸，没人管得过来 |

## 三条铁律

> 🔑 **staging 要像生产，但不能连生产写**。

> 🔑 **五维隔离缺一不可**；只隔离网络等于没隔离。

> 🔑 **环境靠声明式配置生成**，不靠手工。

## 自检

**Q1** 为什么 “staging 像生产” 很重要？

▸ 答案：因为很多问题只在**真实规模与真实依赖**下才出现：数据量大后的慢查询、依赖版本差异、并发下的竞态。如果 staging 数据量小、依赖版本不同，测试通过也证明不了生产可用。

**Q2** staging 连生产只读副本有什么风险？

▸ 答案：两个：**读到敏感数据**（未脱敏则违规，见 [3.2 个人信息保护与 GDPR](../../需求/3-行业合规与外部约束/3.2-个人信息保护与GDPR.md)）；**误写**（权限没管住，只读变可写）。若要连，必须只读账号 + 脱敏视图 + 审计。

**Q3** 为什么 “三套环境共用一把密钥” 是严重问题？

▸ 答案：因为**泄露面变成全线**：dev 的开发者、测试环境的日志、CI 缓存都可能泄露这把 key，一旦泄露，生产也沦陷。正确做法是每环境独立密钥 + 轮换，生产密钥只对生产工作负载可见。

**Q4** “环境太多” 为什么反而危险？

▸ 答案：因为维护成本与**漂移概率**随环境数增长：每个环境都要配网络/密钥/数据，没人能保证一致；最终出现 “只有某台机器能复现” 的困境。通常 dev / staging / prod 三套足够，临时环境用 “按需创建、用完销毁”。

**Q5** 如何避免 “测试消息被生产消费”？

▸ 答案：**topic/队列按环境隔离**（前缀或独立实例），消费组同理；用 IaC 生成名字（如 `app-staging-orders`），而不是手工建。共用 topic 是最典型的 “隔离漏洞”。

**Q6** 定时任务在 staging 该怎么处理？

▸ 答案：默认**关闭**，需要时手动触发或用 “mock 外部副作用” 的运行。否则 staging 会重复发券/重复对账，甚至因为连了生产下游而影响真实用户。

**Q7** 怎么证明 “环境隔离有效”？

▸ 答案：做**故障演练**：在 staging 制造 “写生产” 的尝试（如误配连接串），验证它被拦住（权限/网络/审计）；再验证 “生产变更必须经流水线 + 审批”。隔离不是文档，是能被攻击验证的边界。
