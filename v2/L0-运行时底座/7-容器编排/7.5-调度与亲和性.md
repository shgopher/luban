# 7.5 调度与亲和性

## 一句话

> 调度是 “**过滤 + 打分**” 的两段式：`nodeSelector` / `affinity` / `taints` 决定 “能不能放”，`topologySpread` / `priority` 决定 “放哪更好”；但调度只是**初始放置**，跑起来之后还可以被驱逐、抢占、OOM 推翻。

## 六种机制：谁在过滤，谁在打分

| 机制 | 阶段 | 强/软 | 典型用途 |
|---|---|---|---|
| `nodeSelector` | 过滤 | 强 | “只用 GPU 节点” |
| `nodeAffinity.required…` | 过滤 | 强 | 按可用区/机型/标签精确限定 |
| `nodeAffinity.preferred…` | 打分 | 软 | “尽量放在 SSD 节点” |
| `podAffinity` / `podAntiAffinity` | 过滤或打分 | 强/软（看后缀） | 与某类 Pod 同置 / 分散 |
| `topologySpreadConstraints` | 打分（可升级为过滤） | 软/强 | 副本均匀分布到 AZ / 节点 |
| `taints` + `tolerations` | 过滤（NoExecute 还会驱逐） | 强 | 专用节点池、隔离故障节点 |

一个常被忽略的事实：**调度只看 `requests`，不看 `limits`**。`requests` 是 “我要预留多少”，节点按它算可分配量；`limits` 只在运行时生效。

## 三阶段：过滤 → 打分 → 绑定（绑定是乐观的）

| 阶段 | 做什么 | 失败/代价 |
|---|---|---|
| **过滤**（Predicates） | 排除不满足硬约束的节点：资源是否够、`hostPort` 是否冲突、亲和性、污点、PVC 是否可绑 | 全被排除 → Pending，事件写明每个节点被排除的原因 |
| **打分**（Priorities） | 给剩下的节点打分：资源均衡、拓扑分散、镜像本地性、软亲和 | 只影响 “更愿意放哪”，不产生失败 |
| **绑定**（Bind） | 选定一个节点 | 见下方 “乐观” 说明 |

绑定的关键细节：调度器**先只改本地缓存**（这一步叫 **Assume**），再起一个 Goroutine 异步写 apiserver；异步写失败问题也不大，缓存同步后会自愈。

> 🔑 正因为绑定是 “乐观假设”，**kubelet 启动容器前要再跑一遍准入检查**（`GeneralPredicates`：资源够不够、`hostPort` 是否冲突、`nodeSelector`/`nodeAffinity` 是否匹配）。所以看到 `spec.nodeName` 已经填上、Pod 却起不来，故障不在调度器，在节点侧。

## 优先级与抢占：先占位，下个周期才决定

高优先级 Pod 调度失败时才触发抢占，流程不是 “立刻把它塞上去”：

1. 挑一个牺牲者集合，用**标准的 DELETE** 删除它们（不是偷偷挪走）；
2. 把抢占者的 `spec.nominatedNodeName` 指向被抢的节点——**只是占位声明**；
3. 牺牲者默认有 **30 秒**优雅退出期，这期间集群可调度性会变；
4. 抢占者重新进入**下一个调度周期**，届时再决定放哪——**不保证**最终落在该节点。

排队队列的语义也跟着变：调度失败的 Pod 进 `unschedulableQ`，只有 “自身被更新” 或 “集群发生变化”（`MoveAllToActiveQueue`）才回到 `activeQ`。中途来了更高优先级的抢占者，会**清空**原抢占者的 `nominatedNodeName`。

> ⚠️ 这就是 “高优 Pod 明明有资源却先 Pending 一会儿” 的全部原因：它在等牺牲者退出，再重新排队。

## PriorityClass 的两个数字

| 规则 | 数值 |
|---|---|
| `priority` 是 **32 bit 整数** | 上限 **1000000000**（10 亿） |
| 超过 10 亿的区间 | **保留给系统 Pod**，正是为了系统组件不被业务抢占 |
| 不声明 PriorityClass | 优先级为 **0** |
| 只有 `globalDefault: true` 的 PriorityClass | 才会成为全局默认值 |

提交后 `PriorityAdmissionController` 把 `priorityClassName` 解析成 `spec.priority` 写进对象，调度队列按这个值决定出队顺序。

## GPU：调度器只数 “个数”，挑哪张卡由 kubelet 定

GPU 走**扩展资源**（`nvidia.com/gpu: 1`），和 CPU/内存不是一条路：

| 环节 | 谁做 | 具体行为 |
|---|---|---|
| 调度 | 调度器 | **不理解这个 key 的业务含义**，只把缓存里该资源的可用量减去声明的值，然后绑定 |
| 上报 | Device Plugin | 通过 `ListAndWatch` 汇报本机 GPU 的 **ID 列表**——不含算力、显存等属性 |
| 选卡 | kubelet | 从上报的列表里挑一块，发 `Allocate`，拿回设备路径（如 `/dev/nvidia0`）与驱动目录（如 `/usr/local/nvidia/*`） |
| 挂载 | kubelet | 把上一步的结果**追加进创建容器的 CRI 请求** |

> ⚠️ 这套机制只能表达 “要几张”，表达不了 “要算力最强的那张”。异构 GPU、按显存挑卡、MIG 切片，都必须在调度器之外另做（自定义调度器、节点池标签、或厂商 device plugin 的上层扩展）。

## 亲和性：四个后缀决定行为

| 写法 | 调度时 | 运行中标签变了 |
|---|---|---|
| `requiredDuringSchedulingIgnoredDuringExecution` | 必须满足，否则 Pending | **不驱逐**（Ignored） |
| `preferredDuringSchedulingIgnoredDuringExecution` | 尽量满足，不满足也能跑 | 不驱逐 |
| `requiredDuringSchedulingRequiredDuringExecution`（部分版本未实现） | 必须满足 | 会驱逐 |

这就是为什么 “节点打错了标签，Pod 还在跑”：`IgnoredDuringExecution` 只影响调度那一刻。

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - {key: topology.kubernetes.io/zone, operator: In, values: [az-a, az-b]}
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:   # 软：资源不足时允许同置
        - weight: 100
          podAffinityTerm:
            topologyKey: kubernetes.io/hostname
            labelSelector:
              matchLabels: {app: web}
```

## 分散副本：antiAffinity 还是 topologySpread

| 方案 | 表达 | 坑 |
|---|---|---|
| `podAntiAffinity`（required） | “不要和同类 Pod 同节点” | 节点数少于副本数时，多出来的 Pod **永远 Pending** |
| `podAntiAffinity`（preferred） | “尽量不同节点” | 资源紧张时静默挤在一起，你以为分开了 |
| `topologySpreadConstraints` + `whenUnsatisfiable: DoNotSchedule` | “每个 AZ 的副本数差不超过 maxSkew” | `maxSkew` 设太大等于没约束；`minDomains` 不设时少一个 AZ 也能满足 |
| `topologySpreadConstraints` + `ScheduleAnyway` | 软约束，调度器给高分 | 极端情况下仍会偏斜 |

> 🔑 副本数与节点数的关系必须对上：**required anti-affinity 下，副本数 ≤ 可用节点数**，否则扩容就是在制造 Pending。

## 污点与容忍：专用节点池的标准做法

| 污点效果 | 对新 Pod | 对已在跑的 Pod |
|---|---|---|
| `NoSchedule` | 不调度（除非容忍） | 不驱逐 |
| `PreferNoSchedule` | 尽量不调度 | 不驱逐 |
| `NoExecute` | 不调度 | **驱逐不容忍的 Pod**（可按 `tolerationSeconds` 延迟） |

典型组合：GPU 节点打 `nvidia.com/gpu=present:NoSchedule`，只有声明了对应容忍的推理服务能上去；节点故障时由 node controller 打 `node.kubernetes.io/unreachable:NoExecute` 触发驱逐（默认容忍 300 秒）。

## Pending 的排查顺序（照这个顺序查，别乱试）

1. `kubectl describe pod` 的 **Events**：`0/5 nodes are available: 3 Insufficient cpu, 2 node(s) had untolerated taint`。
2. 资源：`requests` 是否超过任何单节点的可分配量（一个 8C 的 request 在 4C 节点上永远放不下）。
3. 亲和性/反亲和性：required 类约束是否与现有节点矛盾。
4. 污点：节点池是否有未容忍的 taint。
5. PVC：`WaitForFirstConsumer` 的 StorageClass 需要先有 Pod 才绑定，但若 PV 供应失败会一直 Pending（见 [7.7 存储卷与持久化](7.7-存储卷与持久化.md)）。
6. 配额：命名空间的 `ResourceQuota` 是否已满（这时事件是 `exceeded quota`，不是 “资源不足”）。
7. **`spec.nodeName` 已填却起不来**：这不是调度问题，是 kubelet 的准入复检（`GeneralPredicates`）没过——资源、`hostPort`、`nodeSelector` 任一不匹配都会被拒；此时看 kubelet 日志，而不是等调度器。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 `nodeSelector` 实现 “高可用” | 所有副本被钉在一个节点/一个 AZ，故障全灭 |
| required anti-affinity + 副本数 > 节点数 | 永远有 Pod Pending，扩缩容卡住 |
| 给业务 Pod 加 `NoExecute` 容忍 3600 秒 | 节点故障后一小时才迁移，RTO 直接超标 |
| 只看 `limits` 不看 `requests` | 调度按 0 算，节点超卖后集中 OOM |
| 把 “节点标签” 当不可变事实 | 标签改了旧 Pod 不迁移（IgnoredDuringExecution） |
| 忽略 `topologySpreadConstraints` 的 `maxSkew` | 名义上分散，实际可以 3:0 |
| 认为 “抢占成功 = 已落到该节点” | 抢占只是写 `nominatedNodeName`，下个周期还可能落别处 |
| 按 GPU 型号/显存写 `nodeAffinity` 之外的调度规则 | 扩展资源只表达个数，属性信息根本没上报 |

## 三条铁律

> 🔑 **调度只看 requests**；limits 是运行时的事，不参与放置。

> 🔑 **强约束要有 “放不下” 的预案**：required 类约束 + 副本数超过可用域 = 永久 Pending。

> 🔑 **分散副本优先用 topologySpread**；antiAffinity 的 required 版本只在节点数确定够用时才用。

## 自检

**Q1** 一个 Deployment 有 5 个副本，集群 3 个节点，配了 required 的 podAntiAffinity（按 hostname）。会发生什么？

▸ 答案：**2 个 Pod 永远 Pending**。required anti-affinity 要求每个节点最多一个同类 Pod，3 个节点只能放 3 个；其余 2 个找不到满足条件的节点，事件里会写 “didn't match pod anti-affinity rules”。修法：改成 `preferred`，或用 `topologySpreadConstraints` 表达 “尽量均匀”，或增加节点。

**Q2** 节点打了新标签，Pod 没有迁移过去，是调度坏了吗？

▸ 答案：**不是**。绝大多数亲和性规则是 `IgnoredDuringExecution`：只在调度那一刻检查，运行中标签变化不会触发重调度。想让 Pod 跟随标签变化，需要 `RequiredDuringExecution`（多数版本未实现）或主动重建（`kubectl rollout restart`）。同理，删掉节点标签也不会驱逐已在跑的 Pod。

**Q3** `requests.cpu: 8` 的 Pod 在 4 核节点集群里永远 Pending，为什么调 `limits` 没用？

▸ 答案：因为调度器按 **requests** 计算节点剩余可分配量：8 核 request 在任何 4 核节点上都放不下，即使 `limits` 写成 1 也一样。修法是降 `requests`（按实际 P95 用量），而不是动 `limits`。这也是 “requests 虚高导致扩容失败” 的典型成因。

**Q4** 什么时候该用 `NoExecute` 污点，而不是 `NoSchedule`？

▸ 答案：当你要**驱逐已经在跑的 Pod** 时。`NoSchedule` 只挡新 Pod，旧 Pod 会一直留着；`NoExecute` 会把不容忍的 Pod 赶走（可用于节点下线、专用化改造）。代价是驱逐会造成中断，必须配合 `tolerationSeconds` 与 PDB（PodDisruptionBudget）控制节奏。

**Q5** 一个服务要求 “三个副本分到三个 AZ”，你会怎么写，怎么验证？

▸ 答案：写 `topologySpreadConstraints`：`maxSkew: 1`、`topologyKey: topology.kubernetes.io/zone`、`whenUnsatisfiable: DoNotSchedule`，并设 `minDomains: 3`（否则只有 2 个 AZ 时也能满足）。验证：`kubectl get pods -o wide` 看 NODE 列，再对照节点所属 AZ；或用 `kubectl get pod -o custom-columns` 直接输出 zone 标签。只写 YAML 不抽查，等于没做。

**Q6** 一个高优先级 Pod 把低优 Pod 抢占后，`kubectl get pod` 里它还是 Pending，`spec.nominatedNodeName` 却有值。是抢占失败了吗？

▸ 答案：**不是，这是抢占的正常中间态**。调度器只做了两件事：DELETE 牺牲者、把抢占者的 `nominatedNodeName` 指向目标节点。牺牲者默认有 30 秒优雅退出期，期间集群状态在变，所以抢占者要**重新进入下一个调度周期**才真正绑定——而且不保证最后落在那个节点。如果中途来了更高优先级的抢占者，这个 `nominatedNodeName` 还会被清空。
