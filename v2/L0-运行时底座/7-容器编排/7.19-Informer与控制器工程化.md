# 7.19 Informer 与控制器工程化

## 一句话

> Informer 不是“一个 watch”，而是一条流水线：**Reflector（ListAndWatch）→ DeltaFIFO → Indexer/Store → EventHandler**；它和你的控制循环之间还隔着一个 **WorkQueue**——这条链决定了控制器能不能扛住事件洪水、断线重连与失败重试。

**来源**：Informer 的部件与工作流程来自张磊《深入剖析 Kubernetes》第 25 讲（极客时间，2018）；代码按 client-go 的通用骨架整理。

## 一张图看全

```text
                 LIST + WATCH
   apiserver ◄──────────────────► Reflector
                                      │ 增量（Delta）
                                      ▼
                                 DeltaFIFO
                                      │ Pop
                                      ▼
                    ┌───────────  Informer  ───────────┐
                    │  更新本地缓存 Store（Indexer 建索引）│
                    │  触发 AddFunc / UpdateFunc / DeleteFunc │
                    └───────────────┬──────────────────┘
                                    │ 只入队 key
                                    ▼
                                WorkQueue  ──► worker（N 个）
                                                  │
                                                  ▼
                                          reconcile(key)
```

## 五个部件，各管一段

| 部件 | 职责 | 关键事实 |
|---|---|---|
| **Reflector** | 用 `ListAndWatch` 与 apiserver 保持同步 | 先 LIST 全量，再 WATCH 增量；断线重连，`resourceVersion` 过期（410 Gone）时重新 LIST |
| **DeltaFIFO** | 按对象累积“增量事件” | 保证同一对象的变更按发生顺序被消费；它不做业务重试 |
| **Store / Indexer** | 本地缓存 + 索引 | key 是 `<namespace>/<name>`；Lister 从它读对象 |
| **EventHandler** | 收到 Add/Update/Delete 后决定做什么 | **只入队 key，不做业务**；resync 也会触发 Update |
| **WorkQueue** | 解耦生产与消费 | 去重、限速、失败重排；worker 可并发 |

> 🔑 最容易混的是“两个队列”：**DeltaFIFO 在 Informer 内部，负责把 apiserver 的变更搬进缓存；WorkQueue 在控制器侧，负责把 key 搬给业务逻辑。** 前者不重试业务，后者才管退避。

## Reflector：ListAndWatch 到底在做什么

1. **LIST**：拿到某类对象的全量列表与当前 `resourceVersion`；
2. **WATCH**：从该 `resourceVersion` 开始监听增量；
3. 断线后重连，带上最后看到的 `resourceVersion` 继续 watch；
4. 如果服务端已经丢弃了这段历史（压缩），返回 `410 Gone`，Reflector 重新 LIST 全量。

这解释了控制器启动时的报错：

```text
Failed to list *v1.Network: the server could not find the requested resource
```

不是网络坏了，而是 **CRD 还没创建**——Reflector 要 LIST 的资源类型在 apiserver 里不存在。先 `kubectl apply` CRD，控制器日志才会恢复。

## Store 与 Indexer：本地缓存不是“可选优化”

Informer 的缓存是控制器能水平扩展的前提：没有缓存，每个 reconcile 都要打 apiserver，几百个对象就能把 apiserver 打满。缓存带来两个直接结果：

- **读走 Lister，不走 API**：`c.networksLister.Networks(ns).Get(name)` 读的是本地 Store，微秒级；
- **写走 client，读回缓存**：写成功后不要立刻假设缓存已更新，下一次 reconcile 会从缓存读到新版本。

缓存的 key 固定是 `<namespace>/<name>`，所以事件入队也只传这个字符串，不传对象。

## EventHandler：为什么只入队 key

```go
networkInformer.Informer().AddEventHandler(cache.ResourceEventHandlerFuncs{
	AddFunc: controller.enqueueNetwork,
	UpdateFunc: func(oldObj, newObj interface{}) {
		oldN := oldObj.(*v1.Network)
		newN := newObj.(*v1.Network)
		if oldN.ResourceVersion == newN.ResourceVersion {
			return // resync 触发的“假更新”，对象没变
		}
		controller.enqueueNetwork(newN)
	},
	DeleteFunc: controller.enqueueNetworkForDelete,
})
```

三个细节：

1. **Update 要判 `ResourceVersion`**。周期性 resync 会把缓存里的对象重新投递一遍，新旧版本相同；不判等就会产生大量无意义调谐（甚至热循环）。
2. **入队的是 key，不是对象**。事件里的对象是“事件发生那一刻的快照”，排队期间可能已经被改过；worker 必须从缓存重读最新对象。
3. **Handler 里不做重活**。Handler 在 Informer 的消费协程里执行，阻塞它就会拖住整个缓存更新。

## WorkQueue：四个理由

| 理由 | 说明 |
|---|---|
| **速度解耦** | Informer 产出快、业务处理慢；队列做缓冲，避免拖死缓存 |
| **去重** | 同一对象在排队期间被改多次，队列里只保留一个 key |
| **失败重试** | `AddRateLimited` 做指数退避；`Forget` 清掉重试计数 |
| **并发** | 多个 worker 消费同一个队列，靠 key 去重保证同一对象不被并发处理 |

这也回答了一个常见疑问：**为什么不在 EventHandler 里直接调业务逻辑？** 因为那样没有重试、没有去重、没有并发控制，任何一个慢调用都会阻塞事件流。

## 控制器启动骨架

```go
func main() {
	cfg, _ := clientcmd.BuildConfigFromFlags("", kubeconfig)
	kubeClient, _ := kubernetes.NewForConfig(cfg)
	networkClient, _ := clientset.NewForConfig(cfg)

	factory := informers.NewSharedInformerFactory(networkClient, 30*time.Second)
	controller := NewController(kubeClient, networkClient, factory.Samplecrd().V1().Networks())

	stopCh := signals.SetupSignalHandler()
	go factory.Start(stopCh)          // 启动 Reflector 与 Informer
	if err := controller.Run(2, stopCh); err != nil { // 2 个 worker
		log.Fatal(err)
	}
}

func NewController(kubeClient kubernetes.Interface, networkClient clientset.Interface,
	networkInformer informers.NetworkInformer) *Controller {
	c := &Controller{
		kubeClient:    kubeClient,
		networkClient: networkClient,
		lister:        networkInformer.Lister(),
		synced:        networkInformer.Informer().HasSynced,
		queue:         workqueue.NewNamedRateLimitingQueue(workqueue.DefaultControllerRateLimiter(), "networks"),
	}
	networkInformer.Informer().AddEventHandler(cache.ResourceEventHandlerFuncs{
		AddFunc:    c.enqueue,
		UpdateFunc: func(oldObj, newObj interface{}) { c.enqueue(newObj) },
		DeleteFunc: c.enqueue,
	})
	return c
}
```

`NewSharedInformerFactory` 的第二个参数是 **resyncPeriod**：每隔 30 秒，把 Store 里的对象重新投递给 EventHandler。它**不是重新 LIST**，只是重放缓存；真正的重新 LIST 由 Reflector 在断线/过期时触发。

## 控制循环：从 key 到 reconcile

```go
func (c *Controller) Run(workers int, stopCh <-chan struct{}) error {
	defer c.queue.ShutDown()
	if !cache.WaitForCacheSync(stopCh, c.synced) {
		return fmt.Errorf("cache 未同步")
	}
	for i := 0; i < workers; i++ {
		go wait.Until(c.runWorker, time.Second, stopCh)
	}
	<-stopCh
	return nil
}

func (c *Controller) runWorker() {
	for c.processNextItem() {
	}
}

func (c *Controller) processNextItem() bool {
	key, quit := c.queue.Get()
	if quit {
		return false
	}
	defer c.queue.Done(key)

	if err := c.syncHandler(key.(string)); err != nil {
		c.queue.AddRateLimited(key) // 失败：退避后重试
		return true
	}
	c.queue.Forget(key) // 成功：清掉重试计数
	return true
}

func (c *Controller) syncHandler(key string) error {
	ns, name, err := cache.SplitMetaNamespaceKey(key)
	if err != nil {
		return nil // 非法 key 直接丢弃
	}
	obj, err := c.lister.Networks(ns).Get(name)
	if errors.IsNotFound(err) {
		// 缓存里没有 → 对象已被删；如果外部还有资源，在这里清理
		return c.cleanupExternal(ns, name)
	}
	if err != nil {
		return err
	}
	return c.reconcile(obj) // 对比期望与实际，执行动作
}
```

完整可跑示例在 [tools/examples/7.19-informer](../../../tools/examples/7.19-informer/README.md)：用 fake clientset 写了两条断言——`Run` 在缓存同步前不处理任何对象；失败 `AddRateLimited` 后 `NumRequeues=1`，成功 `Forget` 后归零、队列清空。本机 `go test` 两条均通过（0.22s / 0.12s）。

三个必须遵守的点：

| 点 | 原因 |
|---|---|
| 启动前 `WaitForCacheSync` | 缓存没同步完就处理，会把“还没看到”误判成“不存在”，误删外部资源 |
| 失败 `AddRateLimited`，成功 `Forget` | 不退避会打爆下游；不 Forget 会让重试计数永远累积 |
| `syncHandler` 只读缓存、只写 API | 读 API 会放大压力；写缓存不会持久化 |

## 反模式

| 反模式 | 现象 | 根因 | 修法 |
|---|---|---|---|
| **Handler 做重活** | 事件延迟、缓存更新滞后 | 阻塞了 Informer 的消费协程 | Handler 只入队，业务放 worker |
| **用事件对象做决策** | 刚扩容又被缩回 | 快照过期 | worker 从 Lister 重读 |
| **忘记 Forget** | 重试间隔越来越长、日志刷屏 | 失败计数不清零 | 成功后 `Forget` |
| **启动即处理** | 误删外部资源 | 缓存未同步 | `WaitForCacheSync` |
| **resync 热循环** | 每 30 秒全量调谐一次 | UpdateFunc 没判 `ResourceVersion` | 版本相同直接 return |
| **RBAC 不足** | Reflector 反复报 `forbidden` | ServiceAccount 没有 list/watch 权限 | 补 Role/ClusterRole（见 [7.14 认证与 RBAC](7.14-认证与RBAC.md)） |

> ⚠️ `forbidden` 与 `not found` 是两类完全不同的启动失败：`forbidden` 是权限问题（RBAC），`not found` 是资源类型不存在（CRD 未建）。看 Reflector 日志的第一行就能区分。

## 自检

**Q1** Informer 已经有本地缓存了，为什么控制器还要一个 WorkQueue？

▸ 答案：两者解决不同问题。缓存解决“读得快”，WorkQueue 解决“处理得稳”：它把事件生产与业务消费解耦，提供去重（同一对象排队期间只留一个 key）、失败退避重试、并发 worker 与限速。没有队列，Handler 里任何一个慢调用都会阻塞 Informer 的事件流。

**Q2** `UpdateFunc` 里为什么要比较新旧对象的 `ResourceVersion`？

▸ 答案：resync 会周期性地把缓存中的对象重新投递为 Update 事件，但对象本身没有变化，新旧 `ResourceVersion` 相同。不判等就会每 30 秒把所有对象重新调谐一遍，形成周期性热循环；判等后直接 return。

**Q3** 控制器启动时报 `Failed to list *v1.Network: the server could not find the requested resource`，最可能是什么原因？

▸ 答案：**CRD 还没创建**。Reflector 要 LIST 的 `Network` 资源类型在 apiserver 里不存在，所以返回 404。这不是网络问题，也不是控制器 bug；先 apply CRD，再重启控制器即可。

**Q4** 为什么事件处理器只把 key 放进队列，而不是把整个对象放进去？

▸ 答案：对象是事件发生时的快照，排队期间可能已被修改；用旧快照做决策会导致“刚扩到 5 又被缩回 3”。只传 key，worker 处理时从 Informer 缓存重读最新对象，才能保证决策基于当前状态。

**Q5** 一个控制器部署了 3 个副本，结果同一个对象被创建了两次。最可能的原因是什么？

▸ 答案：**没有 leader election**。3 个副本各自跑一个控制循环，同时看到“缺一个”，于是都去创建。控制器必须通过 `leader-election` 选主，或者用资源版本/幂等创建（`AlreadyExists` 视为成功）兜底；前者是标准做法。
