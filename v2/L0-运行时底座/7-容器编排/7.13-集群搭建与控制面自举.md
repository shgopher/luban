# 7.13 集群搭建与控制面自举

## 一句话

> kubeadm 的每个设计都被两个硬约束逼出来：**kubelet 必须裸跑在宿主机上**、**apiserver 还不存在时得有人把它启动起来**（Static Pod）；理解了这两条，才知道改控制面该动哪个文件、`NotReady` 到底缺什么。

## 约束一：kubelet 不能容器化

“把整个 K8s 都跑在容器里” 这个想法失败在一个具体动作上：**挂载**。

| 组件 | 能不能容器化 | 原因 |
|---|---|---|
| apiserver / controller-manager / scheduler / etcd | 能 | 纯用户态进程，只跟网络和磁盘文件打交道 |
| **kubelet** | **不能** | 它要替 Pod 做宿主机级挂载：`mount -F nfs` 这类操作一旦发生在容器的 Mount Namespace 里，就**不会传播到宿主机**，PV 根本挂不上 |

网络侧反而不是问题——控制面容器用 `hostNetwork: true` 直接共享宿主机网络栈就行。社区讨论过两条路：让容器 `setns()` 进宿主机的 Mount Namespace，或让 Docker 支持 `--mnt=host`，但都没有可用的落地方式。**结论：kubelet 直接跑在宿主机上，其余组件全部容器化**——这就是 kubeadm 的取舍。

> 🔑 判断依据不是 “架构好不好看”，而是 “这个组件有没有必须在宿主机上生效的副作用”。

## 约束二：apiserver 不存在时，谁来起 apiserver

`kubeadm init` 那一刻集群还不存在：没有 apiserver，所以**没法用 Pod API 提交任何东西**。解法是 **Static Pod**：

kubeadm 把控制面清单写进 `/etc/kubernetes/manifests`，本机 kubelet 启动时会扫描这个目录，看到 YAML 就自己创建 Pod——**不经过 apiserver**。

```
/etc/kubernetes/manifests/
├── etcd.yaml
├── kube-apiserver.yaml
├── kube-controller-manager.yaml
└── kube-scheduler.yaml
```

apiserver 那份清单里有几个字段是设计要点，不是随手写的：

| 字段 | 值 | 为什么 |
|---|---|---|
| `hostNetwork: true` | 真 | CNI 还没装，Pod 网络还不存在，必须先监听宿主机端口 |
| `priorityClassName` | `system-cluster-critical` | 控制面不能被普通 Pod 抢占挤掉 |
| `resources.requests.cpu` | `250m` | 给调度器一个下限，避免控制面被压到 “资源不足” |
| `command` 里的授权参数 | `--authorization-mode=Node,RBAC` | 同时启用 RBAC 与 Node 授权（kubelet 的节点身份） |

> 🔑 直接后果：**改已有集群的 apiserver 参数，正确做法是改 `/etc/kubernetes/manifests/kube-apiserver.yaml`**，不是找 systemd 服务、也不是 `kubectl edit`（它没有对应的 API 对象可编辑）。改完 kubelet 会检测到文件变化并重建该 Pod。

## 四个接口边界：kubelet 只认契约，不认产品

| 接口 | 管什么 | 谁实现 | 传输 |
|---|---|---|---|
| **CRI** | 容器生命周期、镜像 | containerd / CRI-O / docker shim | gRPC |
| **CNI** | Pod 网络（建 veth、配 IP、加网桥） | Flannel / Calico / Cilium | 可执行文件 + 环境变量 + stdin |
| **CSI** | 存储的创建、挂载、扩容 | 云厂商 / 分布式存储插件 | gRPC（三段调用，见 [7.7 存储卷与持久化](7.7-存储卷与持久化.md)） |
| **Device Plugin** | GPU 等物理设备 | NVIDIA 等厂商 | gRPC，kubelet 直连 |

对照点：CRI/CNI/CSI 都有 “中间层” 的痕迹（shim、CNI 二进制、External Components），而 **Device Plugin 没有**——kubelet 直接与它 gRPC 通信，所以设备资源只能上报 “个数”（见 [7.5 调度与亲和性](7.5-调度与亲和性.md)）。

## `kubeadm init` 具体做什么

### 第一步：Preflight 会拦掉这些硬条件

| 检查 | 判据 |
|---|---|
| 内核版本 | **3.10 以上** |
| cgroups 模块 | 可用 |
| hostname | 必须是**标准 DNS 名**（RFC 1123），否则对象名非法 |
| kubeadm / kubelet 版本 | 必须匹配 |
| 端口 | **10250 / 10251 / 10252** 未被占用 |
| 命令存在 | `ip`、`mount` |
| 容器运行时 | 已安装 |

机器规格（课程口径）：**2 核 8 GB、30 GB 可用磁盘**（磁盘是留给镜像与日志的）。再小不是不能跑，而是能调度的 Pod 数会非常有限。

### 第二步：证书与 kubeconfig 的分工

```
/etc/kubernetes/pki/
├── ca.crt / ca.key                      集群根
├── apiserver.crt / .key                 服务端
├── apiserver-kubelet-client.crt / .key  ← 专门用于 logs / exec 这类 streaming
└── ...

/etc/kubernetes/
├── admin.conf              给管理员（拷到 $HOME/.kube/config）
├── kubelet.conf / controller-manager.conf / scheduler.conf
```

`apiserver-kubelet-client` 那张证书容易被忽略：`kubectl logs` / `exec` 的请求要由 apiserver **反向打到 kubelet**（10250 端口），这段回程也必须双向 TLS（细节见 [6.5 容器运行时](../6-容器技术/6.5-容器运行时.md) 的 Streaming 重定向链路）。

装完如果不把 `admin.conf` 拷成 `$HOME/.kube/config`，后面的每条命令都得 `--kubeconfig` 指路。

### 第三步：默认值都在 kubeadm 配置里

```yaml
apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
kubernetesVersion: v1.31.0
networking:
  serviceSubnet: 10.96.0.0/12          # 默认
  podSubnet: 10.244.0.0/16             # 要跟 CNI 的网段对齐
  dnsDomain: cluster.local
```

| 项 | 默认值 | 注意 |
|---|---|---|
| `serviceSubnet` | `10.96.0.0/12` | 与公司网络重叠时必须在 init 前改，事后改很痛 |
| `dnsDomain` | `cluster.local` | 跨集群联邦时才有必要动 |
| `imageRepository` | `registry.k8s.io`（早期是 `k8s.gcr.io`） | 国内环境先换成镜像站 |
| `criSocket` | 随版本变化（1.24 前常是 `/var/run/dockershim.sock`） | **写错直接 init 失败**，用 `kubeadm config images list` 前的 `crictl info` 确认 |

`apiServerExtraArgs` / `controllerManagerExtraArgs` 里写的参数，最终会被用来**替换 `/etc/kubernetes/manifests/*.yaml` 的 `command` 字段**——所以 “改 kubeadm.yaml 重装” 与 “直接改 manifests” 作用在同一处。

> ⚠️ 配置 API 也带版本：`v1alpha1` / `v1alpha2` 这类旧版本会被新 kubeadm 拒绝，需要先 `kubeadm config migrate`。

## 加节点：token 只为换一张 CA

新节点必须先向 apiserver 注册，而注册要先信任集群 CA。为了不让人上控制面手工拷证书，kubeadm 允许 join 时发起**一次 “不安全模式”** 的访问，从 etcd 里名为 `cluster-info` 的 ConfigMap 取回 apiserver 的地址、端口与证书。

**bootstrap token 就是这次不安全访问的唯一凭据**；拿到 cluster-info 之后，kubelet 才以安全模式连 apiserver。

| 推论 | 说明 |
|---|---|
| token 泄露 = 入场券泄露 | 拿到它就能把自己的节点加进集群 |
| `kubeadm init` 结束必须保存 join 命令 | token 有有效期（默认 24 小时），过期要重新 `kubeadm token create` |
| 加节点失败先看 token | `kubeadm token list` + `kubeadm join --discovery-token-unsafe-skip-ca-verification` 只在调试时用 |

## 装完必然 `NotReady`：缺的不是 kubelet，是 CNI

`kubeadm init` 成功后 `kubectl get nodes` **一定**显示 NotReady，这不是安装失败：

```bash
kubectl get nodes
# NAME     STATUS     ROLES           AGE   VERSION
# node-1   NotReady   control-plane   1m    v1.31.0

kubectl describe node node-1 | grep -A3 Conditions
# Ready  False  KubeletNotReady  runtime network not ready:
#        NetworkReady=false reason:NetworkPluginNotReady message:Network plugin returns error
```

同一时刻 `kubectl get pods -n kube-system` 里：静态 Pod（etcd / apiserver / controller-manager / scheduler）是 Running，而**两个 CoreDNS 副本全是 Pending**（它们依赖 Pod 网络）。

装上任意 CNI（一条 `kubectl apply -f <CNI 清单>`）后，节点转 Ready，CoreDNS 与 kube-proxy 才开始 Running。

> ⚠️ 这也解释了 CNI 的 DaemonSet 为什么必须显式容忍 `node.kubernetes.io/network-unavailable` 污点——节点在 “网络没就绪” 时正是带这个污点的（见 [7.2 K8s 对象模型](7.2-K8s对象模型.md)）。

## 三条自查（有集群时按这个顺序验证）

```bash
# 1) 控制面是不是 Static Pod 起来的：Pod 名会带节点后缀
kubectl -n kube-system get pods -o wide | grep -E 'etcd|apiserver|scheduler|controller-manager'
# etcd-node-1   1/1  Running   ...   node-1
# 预期：四个 Pod 的 NAME 以 -<节点名> 结尾，NODE 列就是本机

# 2) manifests 目录与运行中的参数是否一致（改完必须能在这里看到）
grep -n 'authorization-mode\|service-cluster-ip-range' /etc/kubernetes/manifests/kube-apiserver.yaml

# 3) 节点为什么 NotReady：先看 Conditions 的 reason，不要先看 kubelet 日志
kubectl describe node | grep -A2 'Ready '
```

> **验证边界（已跑到哪一步，缺什么条件）**
>
> **跑通的那一半**：在 Alpine 容器里跑 k3s v1.31.5（`--flannel-backend=none`，故意不装 CNI），`kubectl -n kube-system get pods` 实测：
>
> ```text
> NAME                                      READY   STATUS    RESTARTS   AGE
> coredns-ccb96694c-h2j77                   0/1     Pending   0          12s
> local-path-provisioner-5cf85fd84d-7qsqr   0/1     Pending   0          12s
> ```
>
> **依赖 Pod 网络的组件确实卡在 Pending**——这一条不用真机也成立。
>
> **没跑通的那一半**：`Node` 的 `NotReady` 与 Static Pod 的 `-<节点名>` 后缀。kubelet 在 Docker Desktop 的容器里初始化 cgroup 就失败：
>
> ```text
> E kubelet.go:1566] "Failed to start ContainerManager" err="cannot enter cgroupv2
>   "/sys/fs/cgroup/kubepods" with domain controllers -- it is in an invalid state"
> ```
>
> 原因是这个容器不是 systemd PID 1，根 cgroup 没有把 domain controllers 委托下来（kind 能跑是因为它的 node 镜像自带 systemd）。要在容器里跨过这一步，代价大于收益；这两段输出请以**真机/VM 上 `kubeadm init` 之后**的观测为准。

## 反模式

| 反模式 | 后果 |
|---|---|
| 把 kubelet 也塞进容器 “全容器化” | PV 挂载无法传播到宿主机，存储类工作负载全废 |
| 用 `systemctl restart kube-apiserver` 改参数 | 没有这个服务；控制面是 Static Pod，改了也在重启后丢失 |
| 事后改 `serviceSubnet` | Service IP 全部变化，存量访问全断 |
| `podSubnet` 与 CNI 网段不一致 | 节点 Ready、Pod 也跑，但跨节点不通 |
| 把 join token 提交进 git | 任何拿到仓库的人都能往集群里加节点 |
| 装完看到 NotReady 就去重装 kubelet | 真因是没装 CNI，重装一遍还是 NotReady |
| 用 root 直连控制面节点跑 kubectl 且不清理 admin.conf | 集群最高权限凭据散落在多人机器上 |

## 三条铁律

> 🔑 **kubelet 在宿主机，其余在容器**；判断标准是 “有没有必须在宿主上生效的副作用”。

> 🔑 **控制面是 Static Pod**：改配置改 `/etc/kubernetes/manifests`，不是 systemd，也不是 `kubectl edit`。

> 🔑 **init 之后必 NotReady**，那是缺 CNI；先看 Node 的 Conditions reason，再去看 kubelet 日志。

## 自检

**Q1** 为什么 kubelet 不能像 apiserver 那样跑在容器里？只说 “权限不够” 是不对的。

▸ 答案：因为 **mount 的作用域**。kubelet 替 Pod 准备 PV 时要执行宿主机级的挂载（典型是 `mount -F nfs`），一旦它自己在一个容器的 Mount Namespace 里，这次挂载**只对该 namespace 可见**，不会传播到宿主机，于是卷目录是空的。网络不是障碍（用 host network 就行），文件系统才是。社区讨论过 `setns()` 进宿主 mnt namespace、Docker `--mnt=host` 等方案，都没有落地——这才是 “kubelet 裸跑” 的真实理由。

**Q2** `kubectl edit` 能改 apiserver 的启动参数吗？该怎么做？

▸ 答案：**不能**。控制面在 kubeadm 集群里是 **Static Pod**，由本机 kubelet 扫描 `/etc/kubernetes/manifests/*.yaml` 创建，没有 “可编辑的 API 对象”（即使能查到镜像名带节点后缀的 Pod，改了也会被 kubelet 用文件内容覆盖）。正确做法：改 `/etc/kubernetes/manifests/kube-apiserver.yaml`，kubelet 检测到文件变化后自动重建该 Pod。用 `kubeadm.yaml` 的 `apiServerExtraArgs` 重装，最终也是改这个文件。

**Q3** 节点 `NotReady`，`describe node` 的 reason 是 `KubeletNotReady`，消息里有 `NetworkReady=false`。装 CNI 还是查 kubelet？

▸ 答案：装 CNI。这是 “没有网络插件” 的标准信号：kubelet 在等 CNI 就绪，节点被打了 `node.kubernetes.io/network-unavailable` 污点，CoreDNS 等依赖 Pod 网络的组件全部 Pending。重装 kubelet 不会有任何变化。判据是 reason 与 message 的具体文字——如果是 `NodeStatusUnknown`，那才是 kubelet 与 apiserver 失联（查 kubelet 与网络）。

**Q4** 加节点时 `kubeadm join` 用的 token，泄露了会怎样？

▸ 答案：泄露者可以把**自己的节点**加进集群（第一次 join 会以 “不安全模式” 访问 apiserver 换取 `cluster-info` 里的 CA，token 就是这次访问的凭据）。所以 token 必须短命且不入库：默认 24 小时有效，可用 `kubeadm token create --ttl` 控制；发现泄露就 `kubeadm token delete` 并对集群做审计（看有没有陌生节点与陌生 SA）。

**Q5** 同一份 kubeadm 配置，A 集群装完就 Ready，B 集群一直 Pending/NotReady，最先怀疑什么？

▸ 答案：先怀疑 **`podSubnet` 与 CNI 实际网段不一致**，以及 CNI 装没装。`serviceSubnet` 另有一个坑：默认 `10.96.0.0/12` 与公司内网重叠时，Service IP 与真实网络冲突，表现为 “某些服务访问必然超时”。两者都是 “配置看着对、网络就是不通”，判据是 `kubectl describe node` 的 reason 与 `ip route` 里的实际网段。
