# 7.8 网络模型 (CNI / NetworkPolicy)

## 一句话

> K8s 的网络模型只有三条要求——**每个 Pod 一个 IP、Pod 之间不用 NAT 就能直通、节点也能直接访问 Pod IP**；CNI 决定 “怎么实现这三条”，NetworkPolicy 决定 “谁能连谁”，Service 只是在这之上加的一层虚拟 IP。

## 三条要求，三套实现

| 要求 | 谁实现 | 实现方式 |
|---|---|---|
| 每个 Pod 一个独立 IP | CNI 插件 + IPAM | 从节点 PodCIDR 里分配，或直接用 VPC 子网（云 CNI） |
| 跨节点直通、不 NAT | 路由或隧道 | VXLAN/IPIP 封装，或 BGP 宣告 Pod 网段（underlay） |
| 节点与 Pod 互通 | CNI + 路由 | 节点上装路由/iptables 规则，或云路由表 |

**CNI 是一个规范**：容器运行时调用 `ADD`/`DEL`/`CHECK`，插件返回网卡与 IP。所以 “换网络方案” 通常只是换一个 CNI 二进制 + 一套 IPAM，Pod 清单不用改。

## 三条路径，各自的 NAT 与坑

| 路径 | 实际转发 | 常见坑 |
|---|---|---|
| **Pod → Pod（同节点）** | veth → 网桥（或 eBPF）→ veth | 网桥被 `net.bridge.bridge-nf-call-iptables` 影响，策略失效 |
| **Pod → Pod（跨节点）** | 封装（VXLAN/IPIP）或 BGP 路由 | MTU 未减封装开销 → 大包不通（见 [6.7 容器存储与网络](../6-容器技术/6.7-容器存储与网络.md)） |
| **Pod → Service** | DNAT 到某个 Endpoint + conntrack 记录 | conntrack 表满、会话粘滞、Endpoints 摘除竞态 |
| **外部 → Service** | NodePort / LB → SNAT → Pod | 源 IP 丢失（除非 `externalTrafficPolicy: Local`） |

conntrack 是最容易被忽略的容量项：每个连接占一条表项，`nf_conntrack_max` 打满会丢包且日志稀少。高连接数场景（网关、长连接）要单独调大并监控。

## CNI 的调用约定：环境变量 + stdin + delegate

说 “CNI 是一个规范” 太空，落到实处是这样的：

| 项 | 内容 |
|---|---|
| 谁调 | 容器运行时（dockershim 时代是 kubelet 侧的 shim） |
| 插件二进制 | `/opt/cni/bin/<type>` |
| 传参方式 | 环境变量 + 标准输入 |
| 关键环境变量 | `CNI_COMMAND=ADD/DEL`、`CNI_IFNAME=eth0`、`CNI_NETNS=/proc/<pid>/ns/net`、`CNI_CONTAINERID`、`CNI_ARGS`（自定义） |
| 配置 | 从 **stdin** 读入一段 JSON（Network Configuration） |
| 输出 | 向 stdout 打印结果 JSON（拿到 IP、网关、路由） |

`/etc/cni/net.d` 的加载规则有两条必须记住：

1. 目录里放了**多个**配置文件时，只加载**按字母顺序排第一**的那个——换插件时旧文件没删，新插件会被静默忽略，表现为 “装了却没生效”。
2. 允许的是**单个**文件里用 `plugins` 数组做链式调用（Flannel 就是 `flannel` + `portmap` 两个，按定义顺序依次执行 “配网络”“配端口映射”）。

### 最常被误解的一点：Flannel 插件自己不建网卡

Flannel 的 CNI 插件只做**改写**，真正的设备操作交给内置插件：

```json
// 它把 delegate 补全为：type=bridge、ipam=host-local
{"type": "bridge", "ipam": {"type": "host-local"}, "mtu": 1410, "hairpinMode": true}
```

- 子网从 `/run/flannel/subnet.env` 读，不是从 apiserver 读；
- 补全后的 delegate 存到 `/var/lib/cni/flannel/<容器ID>`，`DEL` 时复用（所以这个目录丢了，回收会不干净）；
- 因此 “换 CNI 方案” 常常只是换一层配置改写器，建 veth、配 IP、挂网桥仍是内置 `bridge` 插件干的。

> ⚠️ 该 delegate 里的 `mtu` 默认值是 **1410**，比 “1500 − VXLAN 50 = 1450” 的常见推算要小。排 MTU 问题时以集群里 CNI 配置的 `mtu` 字段为准，别照搬 1450。

顺带说清网桥的分工：K8s 用 CNI 自己的网桥 `cni0`，**只接管由 CNI 插件负责的 Pod**；`docker run` 单独起的容器仍然接在 `docker0` 上，IP 一定落在 `172.17.0.0/16`。所以 `route -n` 里同时看到 `cni0`、`flannel.1`、`docker0` 三条是正常的。

## 跨节点数据面：四套做法的代价

| 方案 | 封装/转发 | 性能损失 | 硬约束 |
|---|---|---|---|
| **UDP（flannel tun0）** | 用户态 `flanneld` 封 UDP | 每包 **3 次**用户/内核态拷贝，最差 | 已弃用 |
| **VXLAN（flannel.1）** | 内核封 VXLAN | 隧道类普遍 **20%~30%** | 无（三层可达即可） |
| **host-gw** | 直接改写下一跳 MAC，二层直发 | **约 10%** | 宿主机之间必须**二层连通** |
| **Calico（BGP 路由）** | 不建网桥，纯路由 + BGP 宣告 | 无封装开销 | 需要 BGP 可达；跨子网要开 IPIP |

### VXLAN：靠三张表把包送到对端

`flanneld` 在节点加入时下发三条信息，缺一条就跨不了节点：

```bash
ip route   # ① 路由：目的 Pod 网段走 flannel.1，网关是目的宿主机的 VTEP IP
# 10.1.16.0/24 via 10.1.16.0 dev flannel.1
ip neigh   # ② ARP/neigh：目的 VTEP IP 对应的 MAC（节点启动时直接下放，不靠学习）
# 10.1.16.0 lladdr 5e:f8:4f:00:e3:37 PERMANENT
bridge fdb # ③ FDB：VTEP 的 MAC → 目的宿主机 IP
# 5e:f8:4f:00:e3:37 dev flannel.1 dst 10.168.0.3 self permanent
```

内核随后给原始包加 VXLAN 头（**VNI 默认 1**，设备名 `flannel.1` 里的 “1” 就是它）、封 UDP、再加外层 IP（目的 = 宿主机 IP）与外层 MAC（靠宿主机自己的 ARP 表，Flannel 不管）。**内层 IP 头始终是容器 IP**——封包只加二层头，不改原始 IP 包。

### UDP 模式为什么被淘汰：三次拷贝

`flannel0` 是 **TUN（三层）** 设备，只负责在内核与用户态进程之间搬 IP 包：

```
内核 → flannel0(TUN) → 用户态 flanneld（封 UDP）→ eth0
   ①内核态        ②回用户态              ③再进内核态
```

`flanneld` 靠 etcd 里的 “子网 → 宿主机” 映射决定发往哪台机器（如 `/coreos.com/network/subnets/100.96.2.0-24 = {"PublicIP":"10.168.0.3"}`），UDP 打到对端 **8285** 端口。还有一条隐含约束：`docker0` 的网段必须等于 Flannel 分配的子网，用 `dockerd --bip=$FLANNEL_SUBNET` 对齐，否则路由与网卡对不上。

### host-gw：省掉封装，换来二层约束

规则形如 `10.244.1.0/24 via 10.168.0.3 dev eth0`：下一跳就是目的宿主机，封装成帧时用下一跳的 MAC 当目的 MAC，二层直达。转发层的开销只剩路由查表，实测损失 **约 10%**，而隧道类在 **20%~30%**。

> 🔑 但它的门票是 **宿主机之间二层连通**：宿主机分在不同 VLAN / 子网时，下一跳不在同一二层域，这个模式直接不可用。这条限制对 Calico 的纯 BGP 模式同样成立。

### Calico：不建网桥，靠 BGP 分发路由

| 组件 | 角色 |
|---|---|
| CNI 插件 | 对接 K8s，为容器建 `cali*` veth pair，并给每个容器写一条**入向**路由 |
| **Felix**（DaemonSet） | 写内核的 FIB 路由表与网络设备 |
| **BIRD** | BGP 客户端，在集群内部分发 Pod 网段路由 |

因为没有网桥，宿主机上的路由条目比 Flannel 多得多（每个容器一条 `10.233.2.3 dev cali5863f3 scope link`）。

宿主机跨子网时打开 IPIP：Felix 把路由改指 `tunl0`（IP tunnel 设备）——注意它**不是** Flannel UDP 模式的 `tun0`，两者功能完全不同。IPIP 的性能与 Flannel VXLAN 大致相当；没有硬需求就让所有宿主机同子网、**别开 IPIP**。

BGP 的规模问题：默认是 Node-to-Node Mesh，每个节点都要与其他所有节点建 BGP 连接，连接数随节点数按 **N²** 增长，官方建议这种模式用在**少于 100 个节点**的集群。更大规模改用 Route Reflector：指定少数节点与所有节点建 BGP、学习全局路由，连接数从 N² 压到 N 量级。

## NetworkPolicy：默认全通，且需要 CNI 支持

| 事实 | 含义 |
|---|---|
| **默认全通** | 不写任何 NetworkPolicy 时，所有 Pod 互相可达 |
| **策略是白名单** | 一旦某个 Pod 被某条策略的 `podSelector` 选中，它的对应方向就变成 “只允许策略里写的” |
| **需要 CNI 支持** | Flannel 默认不支持（会静默忽略），Calico / Cilium 支持 |
| **分方向** | 只写 `Ingress` 时，出站仍然全通；出站管控要单独写 `Egress` |

“默认拒绝 + 按需放行” 的标准模板（注意先放行 DNS，否则域名解析全挂）：

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny}
spec:
  podSelector: {}                    # 本命名空间所有 Pod
  policyTypes: [Ingress, Egress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: allow-dns-and-web}
spec:
  podSelector: {matchLabels: {app: api}}
  policyTypes: [Egress]
  egress:
    - to:                            # 先放行 DNS（kube-system 的 CoreDNS）
        - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: kube-system}}
      ports: [{protocol: UDP, port: 53}, {protocol: TCP, port: 53}]
    - to:
        - podSelector: {matchLabels: {app: db}}
      ports: [{protocol: TCP, port: 5432}]
```

### `from` / `to` 的 OR 与 AND：外观几乎一样，效果相反

| 写法 | 语义 | 后果 |
|---|---|---|
| `from:` 下写**两个** `-` 条目 | 条目之间是 **或**（OR），命中任一即放行 | 放得宽 |
| 把 `namespaceSelector` 与 `podSelector` 写进**同一个** `-` 条目 | 是 **与**（AND），必须同时满足 | 几乎放不进任何流量 |

```yaml
# OR：来自 app=a 的，或者来自 app=b 的
from:
  - podSelector: {matchLabels: {app: a}}
  - podSelector: {matchLabels: {app: b}}
---
# AND：既要在 app=a 的 Pod 里，又要在 prod 命名空间里
from:
  - podSelector: {matchLabels: {app: a}}
    namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: prod}}
```

> ⚠️ 这是写 NetworkPolicy 最容易错的一处：两种写法只差一个换行缩进，一个 “等于没隔离”，一个 “把自己锁死”。而失败方式都是**没有报错**，只能靠实测。

### 隔离是怎么落到 iptables 的

支持策略的 CNI 都常驻一个 NetworkPolicy Controller，用控制循环响应对象增删改，把策略翻译成宿主机 iptables：

1. **FORWARD 链**按目的地址 `-d $podIP` 拦截，两条规则都跳向 `KUBE-POD-SPECIFIC-FW-CHAIN`：
   - 带 `-m physdev --physdev-is-bridged`：抓**同宿主机**经 CNI 网桥进来的包（Calico 这类无网桥模式没有这种情况）；
   - 不带：抓**跨主机**路由转发来的包。
2. `KUBE-POD-SPECIFIC-FW-CHAIN` 第一条跳到 `KUBE-NWPLCY-CHAIN` 做白名单匹配：`-s 源IP`、`-d 目的IP`、`-p 协议`、`--dport 端口`——四个参数全部从策略对象读出。
3. 匹配不上，落到第二条 `-j REJECT --reject-with icmp-port-unreachable`。

> 🔑 所以 “NetworkPolicy 隔离” 的本质是**在宿主机上生成一组安全组规则**：它不加密、不做二层隔离，也拦不住针对内核的攻击（[7.12 何时不该用 K8s](7.12-何时不该用K8s.md) 里说的 “弱多租户” 就是这个意思）。

### 集群只有 Flannel 怎么办

| 场景 | 做法 |
|---|---|
| 只有 Flannel | 策略**空转**——它不在支持清单里（支持的是 Calico、Weave、kube-router、Cilium） |
| 要用策略又不想换 CNI | 再叠一个 Calico：策略由 Calico 落成 iptables，Flannel 只负责连通 |
| 想要更轻的组合 | kube-router：同样用 BGP 维护路由，但用 CNI 的 `bridge` 插件与 K8s 交互，可看作简化版 Calico |
| 集群外地址（固定 IP 的数据库） | `ipBlock`：`cidr: 172.17.0.0/16` 配 `except: [172.17.1.0/24]`，与 selector 并列、可混用 |

> ⚠️ `policyTypes` 一旦把某方向纳入管理，**未被白名单覆盖的流量即被拒绝**。`egress` 最易漏：Pod 被选中后，原本默认放行的出站全部断掉，表现是 “Pod 起来了、连不上外部依赖”，而 ingress 看起来一切正常。

**验证方式是实测，不是看 YAML**：从源 Pod 里 `nc -zv <目标IP> <端口>`，通了就是没生效（或策略写错），不通才算隔离成立。

## DNS：集群里最常被忽略的延迟源

| 现象 | 原因 | 修法 |
|---|---|---|
| 首次调用外部域名慢 100–300ms | `/etc/resolv.conf` 的 `ndots:5`：外部域名先试 5 个搜索域 | 设 `dnsConfig.options: [{name: ndots, value: "2"}]` |
| 解析随机失败 | CoreDNS 副本不足或被打满（限流/连接数） | 加副本、开 NodeLocal DNSCache |
| 跨命名空间解析失败 | 用了短名（`db`），只在本命名空间生效 | 用 FQDN：`db.ns.svc.cluster.local` |
| Egress 策略后解析全挂 | 没放行到 CoreDNS 的 53 端口 | 见上例的第一条 egress 规则 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 以为配了 NetworkPolicy 就隔离了 | CNI 不支持时策略被静默忽略，集群实际全通 |
| 只写 Ingress 不写 Egress | 出站全通，横向移动不受限 |
| “默认拒绝” 后忘了放行 DNS | 所有域名解析失败，表现为 “服务全挂” |
| 用 ICMP/ping 验证 Service 连通 | Service IP 是虚拟地址，ICMP 通常被丢，误判故障 |
| 忽略 conntrack 上限 | 高并发下随机丢包，日志里几乎没有线索 |
| 跨节点 MTU 未调整 | 小包通、大包不通（传文件/上传必现） |
| 用 Pod IP 做服务发现 | Pod 重建后 IP 变化，调用方全挂 |
| 把多个 selector 塞进同一个 `from` 条目 | 变成 AND 语义，几乎放不进任何流量 |
| 在只有 Flannel 的集群上写策略 | 策略空转，实际全通，安全评估结论全错 |
| 换 CNI 后不删 `/etc/cni/net.d` 里的旧文件 | 加载字母序第一个，新插件被静默忽略 |

## 三条铁律

> 🔑 **默认全通**：不做策略就是全开；做了策略要实测，不能只看 YAML。

> 🔑 **策略先放行 DNS 与探针**，再收紧业务流量；顺序反了会把自己锁在门外。

> 🔑 **Service 只是虚拟 IP**：连通性排查看 Endpoint 与 conntrack，不要用 ping 判断。

## 自检

**Q1** 从 Pod A `curl` Pod B 的 IP 超时，但 `curl` B 的 Service 正常，为什么？

▸ 答案：说明**Pod IP 直连被策略或路由挡住**，而 Service 路径（DNAT → Endpoint）是通的。常见原因：① NetworkPolicy 只放行了 Service 网段/端口，没放行 Pod 网段；② 跨节点路由/BGP 未宣告该 PodCIDR；③ 目标 Pod 的容器端口只监听在 localhost。按 “策略 → 路由 → 监听地址” 三步查。

**Q2** 配了 “默认拒绝所有入站” 之后，服务全部 502。最先查什么？

▸ 答案：先查**探针与 DNS**。默认拒绝会连 kubelet 的健康检查（来自节点 IP）一起拒掉，导致 Pod 一直 NotReady、Endpoint 为空 → 502；同时如果没放行 DNS（Egress 方向），所有域名解析失败。这两条是 “默认拒绝” 的第一批受害者，模板里必须显式放行。

**Q3** 为什么 `ping <ClusterIP>` 不通，但服务是好的？

▸ 答案：因为 ClusterIP 是 kube-proxy/eBPF 在数据面实现的虚拟地址，只对 **TCP/UDP** 做 DNAT；ICMP 通常不被处理，所以 ping 无响应。正确验证方式是 `nc -zv <ClusterIP> <port>` 或 `curl`，再看 `endpointslices` 是否有地址。

**Q4** 一个外部域名解析要 200ms，怎么把它降到个位数？

▸ 答案：根因通常是 `ndots:5`：`api.example.com` 只有 2 个点，会先被拼成 `api.example.com.<ns>.svc.cluster.local` 等 5 个候选，全部失败后才走真实域名，每次多 5 次查询。把 `dnsConfig.options` 的 `ndots` 调到 2，并在热点路径用 NodeLocal DNSCache，通常能把首次解析压到 10ms 内。

**Q5** 两个团队都说 “网络不通”，你怎么在 10 分钟内定位到层？

▸ 答案：按四层问：① **DNS**：`nslookup`/`getent hosts` 能否解析；② **Service**：`endpointslices` 有没有地址；③ **策略**：`kubectl get networkpolicy -A` 有没有选中这两端；④ **数据面**：同节点直连 Pod IP 是否通（排除封装/MTU/路由）。四步定位把 “网络不通” 拆成具体一层，避免在 “是不是 CNI 坏了” 上空转。

**Q6** 你要 “只允许 prod 命名空间里 app=api 的 Pod 访问数据库”。为什么两条规则写法只差一个缩进，一条放得太宽、一条完全不放？

▸ 答案：差别在 **`from` 列表的层级**。写成两个 `-` 条目时，条目之间是 **OR**：来自 prod 命名空间的任何 Pod 都放行，**或者**任何命名空间里 app=api 的 Pod 都放行——“或” 把两个条件各自独立满足了。把 `namespaceSelector` 与 `podSelector` 写进**同一个** `-` 条目才是 **AND**，才表达 “prod 里的 api”。判别方法：看 `-` 的数量与缩进层级，而不是看字段名是否都出现过。
