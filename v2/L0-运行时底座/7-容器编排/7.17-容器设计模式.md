# 7.17 容器设计模式：Sidecar 与 Init Container

## 一句话

> Pod 不是“把几个容器打成一个包”，而是把操作系统里的**进程组**搬进编排：必须同生共死、共享 netns 或卷的进程放一个 Pod；组合只有两种基本手法——**Init Container 做启动前的一次性闸门，Sidecar 做与主容器并行的长期辅助**。

**来源**：成组调度、Infra 容器、WAR + Tomcat、日志 Sidecar 来自张磊《深入剖析 Kubernetes》第 13 讲（极客时间，2018）；Ambassador / Adapter 的分类是社区通行归纳，本文只做对照，不展开实现。

## 为什么最小单位不是容器：一次成组调度的算术

容器的本质是进程，Kubernetes 的目标是当“云计算的操作系统”。操作系统里进程从不孤零零地跑，而是以**进程组**协作：`rsyslogd` 的 main、imklog、imuxsock 三个模块必须在一台机器上，靠 Socket 与文件交换数据。

把 `rsyslogd` 容器化，受“容器单进程模型”限制，三个模块只能做成三个容器。假设集群有两台机器：

| 节点 | 可用内存 | 三个容器各要 | 结果 |
|---|---|---|---|
| node-1 | 3 GB | 1 GB | 刚好放得下 |
| node-2 | 2.5 GB | 1 GB | 放得下前两个，第三个只剩 0.5 GB |

用 Docker Swarm 跑，就得给后两个容器加 `affinity=main`。调度顺序是 main → imklog → imuxsock：前两个都落到 node-2，轮到 imuxsock 时，node-2 只剩 0.5 GB，而约束又要求它必须在 node-2——**成组调度（gang scheduling）失败，三个容器一个都跑不成**。

前人给过两种解法，都不完美：

| 方案 | 做法 | 代价 |
|---|---|---|
| Mesos 资源囤积 | 等所有带 Affinity 的任务都到齐，再统一调度 | 调度效率损失，可能死锁 |
| Omega 乐观调度 | 先并发调度，冲突后靠回滚解决 | 复杂到常规团队驾驭不了 |

Kubernetes 的答案是把“组”提升为一等公民：**调度器按 Pod 而不是容器算资源**。三个容器组成一个 Pod，需求 3 GB，调度器只会选 node-1，根本不会看 node-2。

> 🔑 这就是 Pod 的第一层意义：**它是原子调度单位**。Pod 里的容器不是“恰好一起部署”，而是“必须一起成功或一起失败”。

## 哪些容器该放进同一个 Pod：超亲密关系

| 关系 | 是否同 Pod | 原因 |
|---|---|---|
| 通过 `localhost` 或 Unix Socket 通信 | ✅ | 共享 Network Namespace |
| 直接交换本地文件 | ✅ | 可共享同一个 Volume |
| 需要共享某个 Namespace（如加入对方 netns） | ✅ | Pod 级共享 |
| 调用非常频繁、跨节点延迟不可接受 | ✅ | 同节点、同 netns，路径最短 |
| 只是偶尔发几个 HTTP 请求（如 PHP ↔ MySQL） | ❌ | 应拆成两个 Pod + Service，故障域隔离 |
| 需要独立扩缩容 | ❌ | Pod 是最小伸缩单位，绑在一起就一起扩 |

> 🔑 判据不是“部署方便”，而是“**是否必须同生共死**”。把 5 个无关服务塞进一个 Pod，等于让它们共享同一条命。

## Pod 只提供“共享”，不提供“顺序”

Pod 的实现是一个 **Infra 容器**持有 Network Namespace，用户容器通过 `setns()` 加入；Volume 定义在 Pod 级，容器各自声明挂载。细节见 [7.2 K8s 对象模型](7.2-K8s对象模型.md)。

这带来一个必须记住的事实：**`spec.containers` 里的容器完全平等，没有启动顺序**。Kubernetes 会并行拉起它们，谁也不等谁。所以：

- Sidecar 不能假设主容器已经启动；
- 需要“先做一件事，再启动主容器”的，必须用 Init Container；
- 主容器也不能假设 Sidecar 已就绪（比如 Istio 的流量拦截规则可能还没下发）。

## Init Container：启动前的一次性闸门

`spec.initContainers` 与 `spec.containers` 是两组容器，语义完全不同：

| 维度 | Init Container | 普通容器（含 Sidecar） |
|---|---|---|
| 启动顺序 | **按定义顺序逐个启动** | 无顺序，并行 |
| 何时结束 | 必须**成功退出**（exit 0） | 长期运行 |
| 与下一个的关系 | 前一个成功退出，才启动下一个 | 互不等待 |
| 全部完成后 | 才开始启动 `spec.containers` | — |
| 失败时 | 按 Pod 的 `restartPolicy` 重试；`Never` 则 Pod 失败 | 同上 |
| 探针 / 生命周期钩子 | 不支持 `livenessProbe` / `readinessProbe` / `lifecycle` | 支持 |

最经典的用法是“WAR 包与 Tomcat”：WAR 包和 Tomcat 分别做镜像，用一个 Init Container 把 WAR 拷进共享卷，Tomcat 容器再从同一个卷里读。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: javaweb
spec:
  initContainers:
    - name: war
      image: registry.example.com/sample:v2   # 镜像里只有 /sample.war
      command: ["cp", "/sample.war", "/app"]
      volumeMounts:
        - name: app-volume
          mountPath: /app
  containers:
    - name: tomcat
      image: registry.example.com/tomcat:7.0
      command: ["sh", "-c", "/opt/tomcat/bin/start.sh"]
      volumeMounts:
        - name: app-volume
          mountPath: /opt/tomcat/webapps
      ports:
        - containerPort: 8080
  volumes:
    - name: app-volume
      emptyDir: {}
```

这个例子的价值不在 WAR 包，而在**它把“两个东西必须一起出现、但生命周期不同”拆成了两个镜像**：升级 WAR 只换 Init Container 的镜像，升级 Tomcat 只换主容器镜像，互不牵连。

### Init Container 的三条纪律

| 纪律 | 原因 | 违反后的症状 |
|---|---|---|
| **必须幂等** | Pod 重建、容器重启都会再跑一遍 | 重复初始化、重复写数据、启动变慢 |
| **必须能退出** | 它是“闸门”，不是服务 | Pod 永远停在 `Init:0/1`，主容器永不启动 |
| **只做启动前的事** | 它没有探针，也不该常驻 | 把守护进程放进去，kubelet 会一直等它退出 |

> ⚠️ 排查“Pod 卡在 `Init`”时，先 `kubectl logs <pod> -c <init-name>`，再 `kubectl describe pod` 看 Init 容器的退出码。`Init:CrashLoopBackOff` 与 `Init:0/2` 是两类不同的问题：前者是初始化脚本自己失败，后者是前一个还没跑完。

## Sidecar：与主容器并行的长期辅助

Sidecar 是“在同一个 Pod 里再跑一个辅助容器”，它与主容器共享网络和卷，但生命周期并行。三种最常见形态：

| 形态 | 主容器做什么 | Sidecar 做什么 | 关键共享 |
|---|---|---|---|
| **日志收集** | 把日志写到 `/var/log/app` | `tail -f` 读同一个卷，转发到 ES / Loki | Volume |
| **网络代理** | 只管监听本地端口 | 接管 Pod 进出流量（Istio / Envoy） | Network Namespace |
| **配置/证书刷新** | 读本地文件 | 监听配置中心，原子替换文件 | Volume |

日志 Sidecar 的最小骨架：

```yaml
spec:
  containers:
    - name: app
      image: registry.example.com/app:1.4.2
      volumeMounts:
        - {name: logs, mountPath: /var/log/app}
    - name: log-shipper
      image: registry.example.com/fluent-bit:3.1
      volumeMounts:
        - {name: logs, mountPath: /var/log/app, readOnly: true}
  volumes:
    - name: logs
      emptyDir: {}
```

它的代价很具体：应用写一份文件，Sidecar 读出来后写自己的 stdout，容器运行时又为这份 stdout 生成一份 JSON 日志——**同样的内容在宿主机上存了两份**。节点级 DaemonSet 采集没有这个问题，所以“能改应用就写 stdout，不能改才用 Sidecar”，详见 [7.15 监控与日志](7.15-监控与日志.md)。

网络 Sidecar 的代表是 Istio：Envoy 与业务容器共享 netns，通过 Pod 内的 iptables 规则把进出流量劫持到 Envoy，控制面 Pilot 再调 Envoy 的 API 下发路由。业务容器完全不知道代理存在——这是“用组合代替侵入”的典型。

### Sidecar 与 Init Container 的分工

| 需求 | 用什么 | 判据 |
|---|---|---|
| 启动前准备配置、拷文件、等依赖 | Init Container | 做完就退出 |
| 与主进程并行、长期提供服务 | Sidecar | 不退出 |
| 必须按顺序执行的初始化 | Init Container | 顺序由数组保证 |
| 不能假设主容器已启动的辅助逻辑 | Sidecar + 自旋检查 | 容器之间无顺序 |

> 🔑 一句话：**有顺序、会退出 → Init；无顺序、常驻 → Sidecar。**

## Ambassador 与 Adapter：两种更细的 Sidecar

社区把 Sidecar 进一步分成三种角色（Brendan Burns 等的归纳）：

| 模式 | 代理方向 | 做什么 | 例子 |
|---|---|---|---|
| **Sidecar** | 辅助本容器 | 扩展主容器的能力 | 日志收集、Envoy |
| **Ambassador** | 出站 | 把“访问外部”变成“访问 localhost”，由它转发 | 本地 Redis 代理、数据库连接代理、出口网关 |
| **Adapter** | 入站/观测 | 把主容器的输出**标准化**成平台要的接口 | 把应用的私有指标转成 Prometheus 格式 |

Ambassador 的价值是**把服务发现与重试从应用里挪走**：应用只连 `127.0.0.1:6379`，由 Ambassador 决定真实后端、做分片与故障转移。Adapter 的价值是**不动应用代码就接入平台**：应用暴露私有格式的统计，Adapter 转成 `/metrics`。

这两种模式在书稿里不单独展开，遇到时按“Sidecar 的两种特化”理解即可。

## 从虚拟机迁移：把“一台机器”翻译成“一个 Pod”

| 虚拟机里的东西 | Kubernetes 里对应 |
|---|---|
| 整台虚拟机 | 一个 Pod |
| 虚拟机里的每个进程/组件 | 各自一个容器 |
| 有启动顺序的初始化脚本 | Init Container（按数组顺序） |
| 本地共享目录 | `emptyDir` 或 PVC |
| `localhost` 通信 | 同 Pod（共享 netns） |
| 外部数据库 | 独立 Pod + Service |
| 用 `supervisord` 管多进程 | 拆成多容器；不要用 DinD 硬塞 |

> 🔑 容器不是“更快的虚拟机”，它没有能力管理多个进程：PID 1 就是应用本身，其他进程都是它的子进程，退出后没人回收。硬把多个进程塞进一个容器，等于把进程管理、信号处理、日志收集的烂摊子重新捡回来。

## 反模式

| 反模式 | 后果 |
|---|---|
| 一个容器里用 `supervisord` 跑多个进程 | 信号无法正确传递、PID 1 不回收僵尸、日志混在一起 |
| 把“必须顺序执行”的初始化写成 Sidecar | 主容器先启动，读到空配置直接崩 |
| Init Container 里跑常驻服务 | Pod 永远停在 `Init`，主容器永不启动 |
| Sidecar 假设主容器已就绪 | 连接被拒、初始化 SQL 执行失败（必须自旋 `SELECT 1`） |
| 用 Sidecar 采集日志却不改应用 | 宿主机日志存两份，磁盘翻倍 |
| 把 5 个无关服务塞进一个 Pod | 一起调度、一起重建、无法独立扩缩容 |
| 用 `hostPath` 给每台机器预置 WAR 包 | 需要维护一套分布式存储，正是 Init Container 要消灭的耦合 |
| 用 Docker in Docker 解决“容器里要跑容器” | 特权、存储驱动、网络全是坑，生产后患无穷 |

## 三条铁律

> 🔑 **同生共死才同 Pod**：共享 netns/卷、必须一起成功失败，才放一个 Pod；只是“有调用关系”的，用 Service 连。

> 🔑 **有顺序用 Init，常驻用 Sidecar**：Init 是闸门，必须退出；Sidecar 是邻居，不许假设顺序。

> 🔑 **容器之间没有顺序**：任何“我等另一个容器起来”的逻辑，都要写成自旋检查，不能靠 YAML 数组位置猜。

## 自检

**Q1** 三个容器各要 1 GB 内存，node-1 有 3 GB、node-2 有 2.5 GB。用 Swarm 加 `affinity` 为什么可能三个都起不来？Kubernetes 为什么不会？

▸ 答案：Swarm 按容器逐个调度，前两个落到 node-2 后只剩 0.5 GB，第三个既放不下、又被 affinity 钉在 node-2，形成死局。Kubernetes 按 Pod 原子调度，三个容器合计 3 GB，只会选 node-1；要么三个都上去，要么都不上，不存在“上去两个、卡一个”。

**Q2** 一个 Pod 里主容器启动时要读 `/etc/app/config.yaml`，这个文件由另一个容器从配置中心拉取。应该用 Sidecar 还是 Init Container？

▸ 答案：用 **Init Container**。主容器启动前必须拿到文件，这是“有顺序、做完就退出”的一次性工作。用 Sidecar 的话，两个容器并行启动，主容器大概率读到空文件；除非主容器自己实现“等待文件出现”的自旋逻辑，但那会把依赖管理推给应用。

**Q3** 为什么“容器只能跑一个进程”这个说法不准确？准确的说法是什么？

▸ 答案：容器里可以跑多个进程，但没有**管理多进程的能力**：PID 1 是应用本身，后续进程都是它的子进程；应用不会像 systemd 那样回收僵尸、转发信号、拉起崩溃的子进程。所以准确说法是“一个容器只有一个主进程，且它必须负责自己的子进程”。

**Q4** Sidecar 日志方案为什么会让宿主机日志量翻倍？什么情况下仍然值得用？

▸ 答案：应用先把日志写到文件（第一份），Sidecar `tail` 后写到自己的 stdout，容器运行时又为 stdout 生成 JSON 日志（第二份）。只有“应用完全不可改、且必须写文件”时才值得用；能改应用就写 stdout，由节点级 DaemonSet 采集。

**Q5** 把一个运行着 Nginx、PHP-FPM、Cron 的虚拟机迁到 K8s，最合理的拆法是什么？

▸ 答案：整台虚拟机对应一个 Pod 的思路只在“这些进程必须共享 netns/文件”时成立。更合理的拆法是：Nginx 与 PHP-FPM 若通过 `localhost` 通信，可同 Pod（各自容器）；Cron 独立成 CronJob；数据库等外部依赖独立成 Pod + Service。有启动顺序的初始化（如生成配置、等 DB）用 Init Container。
