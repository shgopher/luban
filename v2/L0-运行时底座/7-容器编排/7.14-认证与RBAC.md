# 7.14 认证与 RBAC

## 一句话

> 「你是谁」由认证决定（用户 / ServiceAccount / 组件身份），「你能做什么」由 RBAC 的 Role 绑定决定；**Namespace 与 RBAC 都不是隔离机制**——它们只约束 API 操作，管不住 Pod 之间的网络。

## 一个请求要过三道门

| 阶段 | 回答什么 | 失败表现 | 谁管 |
|---|---|---|---|
| **认证**（Authentication） | 你是谁 | `401 Unauthorized` | 证书、token、OIDC、webhook |
| **授权**（Authorization） | 你能对什么资源做什么动作 | `403 Forbidden` | RBAC（也可用 ABAC / webhook / Node） |
| **准入**（Admission） | 这个请求要不要被改写/拒绝 | 自定义拒绝信息 | 内置插件 + webhook（见 [7.1 声明式 API 与控制器模式](7.1-声明式API与控制器模式.md)） |

> 🔑 401 与 403 是两条完全不同的故障线：**401 = 身份没被认出来**（证书过期、token 错、kubeconfig 指错集群），**403 = 身份认出来了但没权限**（RBAC 没绑）。看到 401 去查 RBAC 是白费功夫。

## 三种身份，只有一种能“发”

| 身份类型 | 例子 | 怎么创建 | 存在哪 |
|---|---|---|---|
| **普通用户** | 人、CI 机器人 | 没有任何 API 对象代表它，靠证书 CN / OIDC subject | 集群外（证书、IdP） |
| **ServiceAccount** | Pod 里的进程 | `kubectl create sa` | 集群内的 API 对象 |
| **组件身份** | kubelet、controller-manager、scheduler | 启动参数里的 kubeconfig / 证书 | 集群内证书 |

> ⚠️ 普通用户**不是 K8s 对象**：没有 `kubectl get users`。这解释了为什么 “删掉某个人的访问权限” 只能靠证书吊销或 IdP 侧停用，而不是删一个对象。

### ServiceAccount 的身份字符串是硬编码约定

授权系统看到的不是 “名字”，而是两组字符串，**直接决定 `subjects` 怎么写**：

| 项 | 值 |
|---|---|
| 用户名 | `system:serviceaccount:<namespace>:<name>` |
| 内置组 | `system:serviceaccounts:<namespace>`（该命名空间全部 SA） |
| 内置组（全集） | `system:serviceaccounts`（所有命名空间的全部 SA） |

```yaml
# 想让 “所有命名空间的 default SA” 都拿到只读权限：绑一个 Group，而不是逐个建 RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata: {name: default-sa-view}
roleRef: {apiGroup: rbac.authorization.k8s.io, kind: ClusterRole, name: view}
subjects:
  - {kind: Group, name: "system:serviceaccounts", apiGroup: rbac.authorization.k8s.io}
```

> ⚠️ 网上大量示例把用户名写成 `system:serviceaccount:<name>`（漏了命名空间），那匹配不上任何 SA。**三段式不能省中间那段。**

## Pod 里的凭据是从哪来的

| 版本 | 注入方式 |
|---|---|
| 早期（≤ 1.23 常见） | 自动挂一个 `default-token-xxxxx` 的 **Secret 卷**，类型 `kubernetes.io/service-account-token`，annotation 里带 `kubernetes.io/service-account.name=<sa>` |
| 1.24 起（推荐） | 走 **TokenRequest** 投影卷：短期 token（默认 1 小时，可配），kubelet 负责轮转 |

两种方式挂的路径一样：

```bash
ls /var/run/secrets/kubernetes.io/serviceaccount
# ca.crt  namespace  token
```

`client-go` 的 `rest.InClusterConfig()` 就是读这个目录，所以 Pod 里访问 apiserver **零配置**。反过来说：

- 每个 Pod 天然携带一张 API 凭据，**容器被攻破 = 这张凭据泄露**；
- 不需要访问 apiserver 的 Pod 应显式关掉：`automountServiceAccountToken: false`（Pod 级或 SA 级）；
- 忘了写 `serviceAccountName` 的 Pod 用的是 `default` SA——而很多集群里它被放得很宽（见下）。

## 四个对象，一张表说清作用域

| 对象 | 作用域 | 作用 |
|---|---|---|
| **Role** | 单个命名空间 | 定义 “能对哪些资源做哪些动作” |
| **ClusterRole** | 全集群 | 同上；也可被 RoleBinding 引用以复用权限集 |
| **RoleBinding** | 单个命名空间 | 把 Role/ClusterRole 绑到 subject 上，权限**只在自身命名空间生效** |
| **ClusterRoleBinding** | 全集群 | 把 ClusterRole 绑到 subject 上，权限覆盖所有命名空间 + 非命名空间资源 |

两条硬规则：

1. **`roleRef` 不能跨命名空间**：RoleBinding 里的 `roleRef` 只能引用**当前命名空间**的 Role，跨 ns 引用等于 “找不到对象”，绑定建不上。
2. **非命名空间资源只能用 ClusterRole**：`nodes`、`persistentvolumes`、`customresourcedefinitions` 都不属于任何 ns，Namespace 级 Role 表达不了。

### rules 怎么写才够窄

```yaml
rules:
  - apiGroups: [""]                 # "" = 核心组（Pod/Service/ConfigMap…）
    resources: ["configmaps"]
    resourceNames: ["app-config"]   # 收窄到单个对象
    verbs: ["get"]                  # 只读一个对象
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch"]
```

| 字段 | 取值要点 |
|---|---|
| `apiGroups` | 核心组写**空字符串 `""`**；`apps`、`batch`、自定义组写全名 |
| `resources` | 支持子资源：`pods/log`、`pods/exec`、`deployments/scale` |
| `verbs` | 全集：`get` / `list` / `watch` / `create` / `update` / `patch` / `delete` / `deletecollection` |
| `resourceNames` | 把 “能读所有 ConfigMap” 压到 “只能读一个”，但不支持 `create`（创建时还不知道名字） |

> 🔑 `list` 与 `get` 是两种权限：只能 `get` 的 SA 用 `kubectl get pods`（其实发的是 list）会被拒。这是 “明明给了权限却 403” 的高频原因。

## 默认放开的那扇门：`default` SA

| 事实 | 后果 |
|---|---|
| 不声明 `serviceAccountName` 的 Pod 自动用 `default` SA | 大量业务 Pod 共用同一身份 |
| 很多发行版/教程让 `default` SA 绑了宽权限 | 任何一个 Pod 被攻破就拿到对应权限 |
| 收敛方案 | 给所有命名空间的 `default` SA 绑一个只读 ClusterRole（`view`），并**按业务新建专用 SA** 按需授权 |

## 排障与验证

```bash
# 我（或某个身份）能做什么
kubectl auth can-i --list
kubectl auth can-i create pods -n prod
kubectl auth can-i --list --as=system:serviceaccount:prod:api

# 绑定是否真的生效：看 RoleBinding 的 subjects 拼写
kubectl get rolebinding -n prod api-rb -o yaml | sed -n '/subjects/,/roleRef/p'

# 已有 YAML 声明了 RBAC，让集群对齐（不会删多余的绑定）
kubectl auth reconcile -f rbac.yaml --dry-run=server
```

> ⚠️ `kubectl auth can-i` 判断的是**当前身份**；换身份必须加 `--as`，而且你本人需要有 `impersonate` 权限，否则会得到误导性的 `no`。

## 反模式

| 反模式 | 后果 |
|---|---|
| 给业务 SA 绑 `cluster-admin` | 一个 Pod 被攻破等于整个集群易主 |
| `subjects` 里写 `system:serviceaccount:<name>`（漏命名空间） | 绑定看似成功，实际匹配不到任何 SA，权限静默不生效 |
| RoleBinding 里 `roleRef` 跨命名空间引用 Role | 绑定建不上，报错却容易被当成 “RBAC 不生效” |
| 用 `list` 需求却只给 `get` | `kubectl get pods` 403，因为 CLI 实际发的是 list |
| 把 ClusterRole 的 `secrets` `get` 授给业务 SA | 等于全集群密钥可读（见 [7.4 配置与密钥](7.4-配置与密钥.md)） |
| 用 Namespace 当租户隔离 | Namespace 只是名字空间 + 权限作用域，**不做网络隔离**（见 [7.12 何时不该用 K8s](7.12-何时不该用K8s.md)） |
| 不需要 apiserver 的 Pod 保留 token 卷 | 容器被攻破即泄露 API 凭据 |
| 从不清理离职人员/CI 的证书 | 权限长期悬空，审计时才发现 |

## 三条铁律

> 🔑 **401 查身份，403 查 RBAC**；两条线不要混着查。

> 🔑 **SA 用户名是 `system:serviceaccount:<ns>:<name>`**，三段缺一段就静默失效。

> 🔑 **RBAC 只管 API 操作，不管网络与内核**；真正的隔离要么 NetworkPolicy（见 [7.8 网络模型](7.8-网络模型.md)），要么强隔离运行时。

## 自检

**Q1** 同样是 Pod 里调 apiserver，一个报 `401`、一个报 `403`。分别该查什么？

▸ 答案：**401 是身份没被认出来**——token 文件缺失/过期、SA 不存在、kubeconfig 指错集群、证书被吊销；**403 是身份认出来了但没有对应权限**——RBAC 的 Role/RoleBinding 没绑、绑错命名空间、verbs 不够（只给了 `get` 却用了 list）。判据是 `kubectl auth can-i --list --as=<那个身份>`：能列出权限清单说明认证通过，问题在授权。

**Q2** 一个 RoleBinding 创建成功、`kubectl describe` 里 subjects 也有内容，但这个 SA 依然 403。最可能的原因？

▸ 答案：**`subjects` 里的名字拼错**，最常见是漏掉命名空间段。SA 的真实用户名是 `system:serviceaccount:<ns>:<name>`，写成 `system:serviceaccount:<name>` 不会有任何报错——它只是一个不存在的用户，绑定成立但匹配不到。第二可能是 `roleRef` 引用了别的命名空间的 Role（跨 ns 引用在建绑定时就失败，或在老版本上表现为静默无效）。

**Q3** 为什么说 “给每个 Namespace 建一个 RoleBinding” 这种做法在租户隔离上并不可靠？

▸ 答案：因为 **RBAC 只约束对 apiserver 的操作，完全不约束 Pod 之间的网络**。两个命名空间的 Pod 默认可以互相直连；共享宿主内核意味着没有内核级边界；`cluster-admin` 的 SA 能读所有 Secrets。真正的隔离要靠 NetworkPolicy（还要求 CNI 支持）+ 强隔离运行时 + 独立集群，具体边界见 [7.12 何时不该用 K8s](7.12-何时不该用K8s.md)。

**Q4** 一个 SA 只被授了 `get configmaps`（带 `resourceNames`），为什么 `kubectl get configmaps` 还是 403，但 `kubectl get configmap app-config` 可以？

▸ 答案：因为 `kubectl get` 不带名字时发的是 **list** 请求，`resourceNames` 对 **list 不生效**（list 的结果集合无法预先按名字过滤），而且你也没给 `list` verb。`resourceNames` 只对单个对象的 `get` / `update` / `patch` / `delete` 有效，且不支持 `create`（创建时名字在 URL 里还没有）。

**Q5** 1.24 之后 Pod 里 “没有 default-token Secret 了”，还能连 apiserver 吗？

▸ 答案：能。注入方式从 “长期 Secret 卷” 换成 **TokenRequest 投影卷**：kubelet 通过 TokenRequest API 拿到**短期** token（默认 1 小时）并负责轮转，挂载路径还是 `/var/run/secrets/kubernetes.io/serviceaccount`，所以 `InClusterConfig()` 照旧可用。安全上这是改进（token 会过期、可绑定 audience），但 “Pod 里有一张 API 凭据” 这个事实没变——不需要访问 apiserver 的 Pod 仍应设 `automountServiceAccountToken: false`。
