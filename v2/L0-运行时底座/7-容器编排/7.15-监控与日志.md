# 7.15 监控与日志

## 一句话

> 指标有两条路——**聚合层代理**（metrics-server / custom metrics 都是 apiserver 后面的后端）与**独立抓取**（Prometheus）；日志只有一条路——**应用写 stdout，节点上的 agent 收集**。搞错这两条路的边界，`kubectl top` 报错会去查 apiserver，日志丢了会去查 Pod。

## 监控：三个后端，一条聚合链

| 后端 | 提供什么 API | 数据从哪来 | 典型用途 |
|---|---|---|---|
| **metrics-server** | `metrics.k8s.io/v1beta1` | 从 kubelet 的 **Summary API**（`/stats/summary`）采集 | `kubectl top`、HPA 的 CPU/内存指标 |
| **custom metrics adapter**（如 prometheus-adapter） | `custom.metrics.k8s.io` | 从 Prometheus 查 | HPA 按 QPS / 队列长度扩缩 |
| **Prometheus（独立抓取）** | 自己的 HTTP API | 主动 scrape `:9100` / `/metrics` | 看板、告警、长期存储 |

### 聚合层：`kubectl top` 的数据到底经过谁

```
kubectl top ──► kube-apiserver ──► kube-aggregator ──► metrics-server ──► kubelet Summary API
                                  （按 URL 选后端）      （不抓 cAdvisor，读 Summary）
```

关键结论：

| 事实 | 含义 |
|---|---|
| metrics-server **不是** apiserver 的一部分 | 它是通过 **Aggregator** 插件机制注册进来的一个后端 |
| 聚合器按 URL 选后端 | `…/apis/metrics.k8s.io/v1beta1` 这条路径被代理到 metrics-server，其他路径仍由 apiserver 自己处理 |
| metrics-server 自己不抓 cAdvisor | 它读 kubelet 的 **Summary API**，那里既有 cAdvisor 指标也有 kubelet 自己的汇总 |

> 🔑 所以 `kubectl top` 报错而 `kubectl get pods` 正常时，故障点在**聚合层之后**（metrics-server 挂了 / APIService 不可达 / 证书不匹配），不在 apiserver 本身。

### 自己 DIY 集群时，apiserver 必须带的聚合参数

kubeadm 与官方脚本默认已开启。手工搭的集群至少要配齐下面这些，否则 metrics-server 起得来但永远 `Unavailable`：

| 参数 | 作用 |
|---|---|
| `--requestheader-client-ca-file` | 校验聚合后端（metrics-server）出示的客户端证书 |
| `--requestheader-allowed-names=front-proxy-client` | 只允许这个 CN 的证书做前置代理 |
| `--requestheader-username-headers=X-Remote-User` | 把代理传来的用户身份透传进授权链 |
| `--requestheader-extra-headers-prefix=X-Remote-Extra-` | 透传附加属性（组、scopes） |
| `--proxy-client-cert-file` / `--proxy-client-key-file` | apiserver 反向访问后端时用的客户端证书 |
| `--enable-aggregator-routing` | 按 APIService 的 Endpoints 直连后端 Pod |

自查方式（比翻文档快）：`kubectl get apiservice v1beta1.metrics.k8s.io -o yaml` 看 `status.conditions`，`Available=False` 时 message 会直接写 “no endpoints / x509: certificate signed by unknown authority” 之类。

## 指标怎么规划：USE 与 RED 别混用

| 框架 | 三个维度 | 用在哪 |
|---|---|---|
| **USE** | **U**tilization（利用率）、**S**aturation（饱和度，如工作队列长度）、**E**rrors（错误数） | 节点、容器等**资源** |
| **RED** | **R**ate（每秒请求数）、**E**rrors（每秒错误数）、**D**uration（响应时间） | kube-apiserver、业务**服务** |

> ⚠️ 混用的后果很具体：拿 RED 的 “每秒请求数” 去描述一个节点，算不出饱和度；拿 USE 的 “利用率” 去描述 API，算不出 P99。选框架先问 “被描述的是一个资源，还是一个服务”。

## Custom Metrics：返回的是**速率**，不是累计值

这是 HPA 配错的第一大原因。

应用 `/metrics` 暴露的通常是**累计计数**（`http_requests_total`）。Prometheus 侧要用 `rate()` 把它折算成 “每秒请求数”，adapter 再按固定格式返回给聚合层。课程里的真实取值：

```text
value: 501484m
```

`m` 是 milli（千分之一），**501484m ≈ 501.484**，含义是 **过去两分钟内平均每秒 501 个请求**——不是 “累计 501484 次请求”。

| HPA 写法 | 真实含义 | 配错的后果 |
|---|---|---|
| `targetValue: 100`（custom metric = 请求速率） | 每秒 100 请求就扩容 | 按 “累计值” 理解，就永远觉得 “还没到 100” 或瞬间超限 |
| 把 `xxx_total` 直接当 metric 用 | 单调递增的计数器 | 扩到 `maxReplicas` 之后再也不缩容 |

采集侧的落地链路是 Prometheus Operator 的 `ServiceMonitor`：

```yaml
spec:
  selector:
    matchLabels: {app: sample-metrics-app}   # 选中哪个 Service
  endpoints:
    - port: web                              # Service 里哪个端口暴露 /metrics
```

三个对象 apply 完就能用：`prometheus-operator.yaml`、`custom-metrics.yaml`（adapter）、`sample-metrics-app.yaml`（被采集的应用）。

## 日志：先认一条事实

**应用把日志写到 stdout/stderr，容器运行时把它落到宿主机的 JSON 文件里，`kubectl logs` 读的就是这个文件。**

| 推论 | 说明 |
|---|---|
| 日志只写容器内文件，`kubectl logs` 什么也看不到 | 这直接让 “集群级日志” 方案失效 |
| 日志轮转由运行时做（很多部署默认超过 **10 MB** 就 rotate） | 但它**只控单文件大小，不控总量** |
| 总量随容器数线性增长 | 日志默认落在宿主机磁盘上，涨满主分区 = **整个节点不可用** |
| cluster-level logging 与容器/Pod/Node 生命周期无关 | 所以 Pod 删了、节点宕了，后端仍能查到日志 |

> 🔑 「10 MB 轮转」是最容易被误读的数字：它是**单个文件**的上限，不是目录上限。一台跑 40 个容器的节点，每容器 10 MB × 若干份就是几百 MB 的常态占用，加上故障时的日志风暴，节点磁盘打满是节点级事故，不是某个 Pod 的事故。

### 三种收集方案

| 方案 | 做法 | 成本 / 坑 | 什么时候用 |
|---|---|---|---|
| **① 应用写 stdout + 节点 DaemonSet agent** | agent（Fluent Bit / Filebeat）读宿主机的容器日志目录，转发到 ES/Loki | 最省资源、与业务解耦；需要节点级权限 | **默认选它** |
| **② sidecar 用 `tail -f` 转发** | 应用写文件，sidecar 把文件内容重放到自己的 stdout | **宿主机上留两份相同日志**（应用一份 + sidecar 的 stdout 一份），纯磁盘浪费；sidecar 崩溃期间的行可能丢 | 应用完全不可改、且必须写文件 |
| **③ 应用直接写后端** | SDK 直连 ES/Kafka | 业务耦合、升级要改代码 | 特殊合规场景 |

方案 ② 的具体浪费值得算一遍：应用写 `/var/log/1.log`，sidecar `tail -n+1 -f` 把内容打到自己的 stdout，运行时又为这份 stdout 生成一份 JSON 日志文件——**同样的内容在宿主机上存了两份**。

### 必须做的两件事

```bash
# 1) 给日志目录单独挂盘（或至少独立分区），别和系统盘共用
df -h /var/log/pods /var/lib/docker

# 2) 让 agent 侧配保留与清理策略（按天/按大小），而只依赖运行时轮转
```

> ⚠️ 只依赖容器运行时的 logrotate，等于把 “节点会不会挂” 交给 “日志量会不会涨”。

## 反模式

| 反模式 | 后果 |
|---|---|
| `kubectl top` 报错就去重启 apiserver | 真因在聚合层之后（metrics-server / APIService / 证书） |
| 手工集群不配 requestheader 参数 | metrics-server 永远 `Available=False` |
| 拿 `xxx_total`（累计）当 HPA 的 custom metric | 指标单调递增，扩容后不缩容 |
| 用 RED 指标描述节点、用 USE 指标描述 API | 算不出饱和度 / 算不出 P99，看板建了等于没建 |
| 应用只写容器内文件 | `kubectl logs` 空、集群日志方案全失效 |
| 加 sidecar tail 转发却不接受两份磁盘 | 存储成本翻倍，且 sidecar 挂时丢日志 |
| 只靠运行时的 10 MB 轮转 | 单文件受限、总量失控，节点磁盘打满 |
| 日志目录与系统盘同盘 | 日志风暴直接把节点打成 NotReady |

## 三条铁律

> 🔑 **指标走聚合层，日志走宿主目录**；两条链的故障域完全不同，别互相套。

> 🔑 **custom metric 的量纲是 “速率”**；HPA 的 `targetValue` 说的是 “每秒多少”，不是 “累计多少”。

> 🔑 **日志上限是 “目录总量”，不是 “单文件 10 MB”**；不单独挂盘 + 不配保留策略，等于留了个定时炸弹。

## 自检

**Q1** `kubectl get pods` 正常，`kubectl top pods` 报 `error: Metrics API not available`。你会按什么顺序查？

▸ 答案：从**聚合层往后**查，而不是从 apiserver 往前。① `kubectl get apiservice v1beta1.metrics.k8s.io -o yaml`，看 `status.conditions` 的 `Available` 与 message（`no endpoints` = metrics-server 没起或没有 Endpoint；`x509` = 证书不被 requestheader CA 认可）；② `kubectl -n kube-system get pods | grep metrics-server` 看它是否在 CrashLoop；③ 若手工集群，回头确认 apiserver 的 `--requestheader-*` 与 `--proxy-client-*` 参数。**apiserver 本身正常是前提，不要从它开始查。**

**Q2** HPA 按 custom metric 扩容，`targetValue: 100`。指标返回 `501484m`，现在会怎么扩？如果团队把 `http_requests_total` 直接暴露成 custom metric 呢？

▸ 答案：`501484m` 是 **501.484 请求/秒**（`m` = 千分之一），远超 100，会按比例扩容——这是对的。若直接拿 `http_requests_total`（累计计数）当指标，它只增不减，算出的 “利用率” 永远在涨，HPA 会一路扩到 `maxReplicas` 且**永不缩容**。正确做法是在 Prometheus 侧用 `rate()` / `irate()` 折算成速率，再交给 adapter。

**Q3** 一个 Pod 的日志在 `kubectl logs` 里完全看不到，但进容器 `cat /app/logs/app.log` 有一大堆。哪里出了问题？

▸ 答案：应用把日志写到了**容器内文件**，而不是 stdout/stderr。K8s 的日志链路起点是 “运行时把 stdout 写到宿主机 JSON 文件”，`kubectl logs` 读的是那个文件，所以容器内文件它读不到。修法按优先级：① 应用改成写 stdout（最省事）；② 不可改就用 sidecar `tail -f` 转发（接受宿主机两份日志的代价）；③ 应用直写日志后端。同时注意 `emptyDir` 的 `sizeLimit`，否则容器内文件会先把节点磁盘写满。

**Q4** 团队说 “我们开了 logrotate，10 MB 就轮转，所以磁盘安全”。这个论证漏了什么？

▸ 答案：漏了**总量**。10 MB 限制的是**单个日志文件**，与 “节点上所有日志总共占多少” 无关：容器数 × 保留份数 × 单文件上限 = 实际占用，再叠加故障时的日志风暴（一秒几百 MB）。要真的安全，得给日志目录单独挂盘（或独立分区）+ agent 侧配置按天/按大小的保留策略，并监控 `nodefs.available` 与 `imagefs.available`（低于阈值节点就会开始驱逐，见 [7.9 资源限制与 QoS](7.9-资源限制与QoS.md)）。

**Q5** 为什么说 “cluster-level logging 与 Pod 生命周期无关” 是个有用的结论？

▸ 答案：因为它决定了**日志方案能不能救事故**：Pod 被删、节点宕机后，容器日志文件随节点消失，只有已经被 agent 转发到后端的部分能查。反推两条实践：① 日志必须尽快离开节点（agent 实时转，不要等轮转）；② “查事故时日志已经丢了” 的根因通常在 agent 停止转发或后端写入失败，而不是 Pod 删得太快。
