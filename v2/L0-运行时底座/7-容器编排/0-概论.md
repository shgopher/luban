# 第 7 章 容器编排 · 概论

## 一句话

> 这一章回答一个问题：**机器从 1 台变成 100 台、容器从 1 个变成 1000 个之后，谁负责“让每个容器都待在它该在的机器上、并且一直是活的”**——答案是「声明式 API + 控制器」，其余十几节都是这句话的展开。

## 5 分钟入门：先记住这 8 个词

| 词 | 一句话解释 | 类比 |
|---|---|---|
| **容器** | 一个被限制了“视野（namespace）”和“额度（cgroup）”的普通进程 | 一间带独立门牌和电表的房间 |
| **Pod** | K8s 的最小调度单位，一组共享网络与卷的容器 | 一间房里合租的几个人（共用一个门牌） |
| **声明式 API** | 你只写“我要 3 个副本”，不写“怎么起这 3 个” | 点外卖（要一份饭），不是给厨师写菜谱 |
| **控制器** | 一个永不停歇的循环：看现状 → 比期望 → 动手 | 恒温器：低于 26 度就开空调 |
| **节点（Node）** | 一台跑着 kubelet 的机器 | 一栋楼里的一个房间 |
| **Service** | 给一组随时会变的 Pod 一个不变的名字/IP | 公司的总机号码（换人不用换号） |
| **调度器** | 决定“这个 Pod 放哪台机器”的组件 | 酒店前台给客人分房 |
| **Operator** | 把“人类运维知识”写成控制器 | 请了个会自己巡检的管家 |

> 只要记住 **“声明式 + 控制器 = 自愈”** 这一条，本章后面的对象模型、滚动更新、Operator 都是它的不同外壳。

## 3 个最常见误解

| 误区 | 现实 |
|---|---|
| “Pod 就是一个容器换个名字” | Pod 是**一组共享 netns 的容器**，由 `pause` 容器持有网络命名空间；所以一个 Pod 只有一个 IP、里面的容器只能靠 localhost 通信 |
| “上了 K8s 就自动高可用、自动扩缩容” | 高可用要你自己配多副本 + PDB；扩缩容要装 HPA 且指标可用；**单副本照样挂，节点照样会 OOM** |
| “服务跑起来就不需要管了” | 不配 readiness 就接不到流量、不配 limits 就会被邻居踩、不配 PDB 就会在节点维护时全灭——K8s 只保证“回到期望状态”，不保证“期望状态是对的” |

## 读完自检（入门级 3 题）

**Q1** 用一句话说清：为什么 K8s 用“声明式”而不是“命令式”？

▸ 答案：因为**机器会坏、事件会丢**。命令式（`start`、`scale 3`）执行完就结束，失败了没人重试；声明式只保存“我要什么”，控制器每隔一会儿就对比一次“现在是什么”，不一致就动手修——所以重启、漂移、误删都能自己补回来。代价是**收敛有延迟**，`kubectl apply` 成功不等于服务可用。

**Q2** 一个 Pod 里的两个容器，共享什么、不共享什么？

▸ 答案：**共享网络（同一个 IP、localhost 互通）与挂载的卷**；**不共享文件系统**（各自镜像的 rootfs）、**默认不共享进程空间**（要看 `shareProcessNamespace`）。生命周期上它们是“同生共死”的：一起调度、一起被删。

**Q3** 用户请求 `https://app.example.com/api`，在 K8s 里大致经过哪几层才到你的进程？

▸ 答案：**Ingress（按 host/path 路由）→ Service（稳定 VIP）→ Endpoint（真正就绪的 Pod IP 列表）→ Pod（容器端口）**。所以 404 先查 Ingress 规则，超时先查 Endpoint 是否为空，再查网络策略与端口。
