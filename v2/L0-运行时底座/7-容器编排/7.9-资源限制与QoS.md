# 7.9 资源限制与 QoS

## 一句话

> `requests` 决定 “**调度**”，`limits` 决定 “**运行时上限**”，两者组合决定 **QoS 等级与驱逐顺序**；最贵的错误是把 `requests` 设成 0、`limits` 设成峰值——前者让节点超卖到 OOM，后者让服务在日常波动里被节流。

## requests 与 limits 的四个组合

| requests | limits | 实际行为 | 风险 |
|---|---|---|---|
| 不设 | 不设 | 完全不限量，BestEffort | 一个 Pod 能吃掉整台机器 |
| 设了 | 不设 | 调度按 requests，运行可超用 | 节点超卖，高负载时互相踩踏 |
| 设了 | 设了（limit > request） | 典型 Burstable | 超用被节流（CPU）或被杀（内存） |
| 相等 | 相等 | Guaranteed | 稳但贵，且 `limit` 会变成硬顶 |

## QoS 三档：不是标签，是驱逐顺序

| QoS | 判据 | 驱逐顺序 | 适合 |
|---|---|---|---|
| **Guaranteed** | 每个容器都设了 CPU/内存的 request 与 limit **且相等** | 最后被驱逐 | 核心交易、延迟敏感 |
| **Burstable** | 至少一个容器设了 request/limit，但不满足 Guaranteed | 中间 | 大多数业务 |
| **BestEffort** | 全部容器都没设 request/limit | **最先被驱逐** | 批处理、可中断任务 |

驱逐不是随机的：节点内存压力（`memory.available < 100Mi` 之类的默认阈值）时，kubelet 按 **QoS 等级 + 超出 request 的程度** 排序，先杀 BestEffort，再杀 “用得比 request 多” 的 Burstable。

### Guaranteed 的两个 “你以为”

| 你以为 | 实际 |
|---|---|
| 只写 `limits`、不写 `requests` 就不算 Guaranteed | Kubernetes **自动把 requests 补成与 limits 相同**，仍判为 Guaranteed——更稳，也更贵 |
| Guaranteed 绝不会被驱逐 | 只有两种情况会：**用量超过 limits**，或宿主机本身已处于 `MemoryPressure` |

> ⚠️ 由第二条推出一条实践：**DaemonSet 的 Pod 应该设为 Guaranteed**。否则它被驱逐后立刻会在同一节点重建，“驱逐回收” 这个动作完全白做。

### 真 “独占 CPU 核” 要三个条件同时成立

| 条件 | 说明 |
|---|---|
| QoS 是 **Guaranteed** | 不满足就进不了 cpuset 路径 |
| `requests.cpu == limits.cpu` | 且必须是**整数**（如 `2`，不能是 `1500m`） |
| 由 kubelet 分配具体核 | 绑哪几个核不确定，但绝不会与别的容器共享 |

满足后该 Pod 被**绑定在 N 个独占的 CPU 核**上（走 `cpuset.cpus`，不是抢 `cpu.shares` 权重），核间上下文切换大幅减少——这是在线服务上生产环境的常用手法。

> 🔑 反过来说：只把 `limits.cpu` 设成核数**不构成独占**，它仍然只是一个上限，超了照样被节流。

## CPU 与内存：两种失败方式

| 资源 | 超限后果 | 观测指标 | 缓解 |
|---|---|---|---|
| CPU | **节流**（变慢，不杀） | `container_cpu_cfs_throttled_periods_total` 比例 | 提高 limit、留 30% 余量 |
| 内存 | **OOM Kill**（直接杀） | `container_memory_working_set_bytes`、`OOMKilled` 次数 | 提高 limit、排查泄漏、给 page cache 留空间 |
| ephemeral-storage | **驱逐** | `container_fs_usage_bytes` | 日志走 stdout、`emptyDir.sizeLimit` |

内存的坑在于 `limits.memory` 统计的是 **cgroup 用量（含 page cache）**：容器读写文件多时，page cache 会吃掉额度，触发 OOM 时 RSS 看起来还很低。机制见 [6.3 namespace (隔离) 与 cgroups (限制)](../6-容器技术/6.3-namespace与cgroups.md)。

## 从 YAML 到内核文件：换算口径

这两个数不是抽象概念，它们被 kubelet 翻译成具体的 cgroup 文件值：

| YAML | 内核文件 | 值 |
|---|---|---|
| `requests.cpu: 250m` | `cpu.shares` | **(250/1000) × 1024 = 256** |
| 不写 `requests.cpu` | `cpu.shares` | **1024**（默认，所以 “不设 requests” 并不是 0） |
| `limits.cpu: 500m` | `cpu.cfs_quota_us` | **(500/1000) × 100ms = 50000μs** |
| （固定） | `cpu.cfs_period_us` | **100000μs = 100ms**，不随配置变 |
| `limits.memory: 128Mi` | `memory.limit_in_bytes` | **128 × 1024 × 1024** |

```bash
# 在节点上直接看某个容器的实际值（cgroup v1 路径）
cat /sys/fs/cgroup/cpu/kubepods/.../cpu.shares          # 256
cat /sys/fs/cgroup/cpu/kubepods/.../cpu.cfs_quota_us    # 50000
cat /sys/fs/cgroup/cpu/kubepods/.../cpu.cfs_period_us   # 100000
```

> 🔑 由此能解释两个 “反直觉”：① 不设 requests 的容器仍然能分到 **1024 份**权重，和 `requests.cpu: 1000m` 的容器权重相同——这就是 BestEffort 也能吃到 CPU 的原因；② CPU limit 是**每 100ms 结算一次**，所以短时突发会被硬切成 “等下一周期”，表现为 P99 尖刺。

## 驱逐阈值：四个默认值 + 软硬两档

节点压力驱逐不是 “内存快满了就杀”，而是按可配置阈值触发：

| 信号 | 默认阈值 | 数据来源 |
|---|---|---|
| `memory.available` | **< 100Mi** | cgroup 读取值 |
| `nodefs.available` | **< 10%** | cAdvisor 监控 |
| `nodefs.inodesFree` | **< 5%** | cAdvisor 监控（`inodes` 常被漏掉） |
| `imagefs.available` | **< 15%** | cAdvisor 监控（镜像层写满也会驱逐） |

两档模式：

| 模式 | 行为 | 例子 |
|---|---|---|
| **Hard** | 达阈值**立刻**驱逐 | `--eviction-hard=memory.available<500Mi,nodefs.available<5%` |
| **Soft** | 达阈值后**持续一段时间**才驱逐 | `imagefs.available=2m` 表示持续 2 分钟才动手 |

阈值触发后节点进入 `MemoryPressure` / `DiskPressure` 状态，**新 Pod 不再被调度到该节点**。

> ⚠️ 只盯 `memory.available` 是最常见的疏漏：`inodesFree < 5%` 与 `imagefs.available < 15%` 会让 “内存还有很多” 的节点照样驱逐 Pod。

## 怎么定这两个数（可抄的方法）

```text
requests.memory ≈ P95 工作集 × 1.2
limits.memory   ≈ P99 工作集 × 1.5   （或 P95 × 2，视 GC/缓存策略）
requests.cpu    ≈ 常态用量（P50–P75），用于调度与 HPA 基准
limits.cpu      ≈ 峰值用量 × 1.5，或干脆不设（用节点层共享，换取弹性）
```

三条经验：

- **requests 定得太小**：节点超卖，扩容时 “看起来还有余量” 实际已经 OOM。
- **limits 定得太小**：CPU 长期节流，P99 抖动；内存频繁 OOMKilled 且查不出泄漏。
- **requests = limits（Guaranteed）**：稳定但成本最高；只给核心链路，不要全站标配。

## 命名空间的两道闸

| 对象 | 管什么 | 典型配置 |
|---|---|---|
| **ResourceQuota** | 命名空间总量（`requests.cpu`、`limits.memory`、Pod 数、PVC 数） | 防止一个团队吃掉整个集群 |
| **LimitRange** | 单个 Pod/容器的**默认值**与上下限 | 没写 requests 时给默认值，避免 BestEffort 泛滥 |

```yaml
apiVersion: v1
kind: LimitRange
metadata: {name: defaults, namespace: team-a}
spec:
  limits:
    - type: Container
      default:        {cpu: "500m", memory: "512Mi"}   # 没写 limits 时的默认
      defaultRequest: {cpu: "200m", memory: "256Mi"}   # 没写 requests 时的默认
      max:            {cpu: "4", memory: "8Gi"}        # 上限，防止“一个大 Pod 吃满”
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 全站不写 requests | 调度按 0 算，节点超卖，集中 OOM |
| `limits.cpu` 设成核数就以为独占 | 只有 Guaranteed + requests=limits=整数才绑核；否则只是上限 + 节流 |
| 用 `limits.cpu` 当 “保底” | 保底是 requests 的事，limit 只会限制上限 |
| 给所有服务设 Guaranteed | 成本翻倍，且峰值被硬顶住，扩不出来 |
| 没有 LimitRange 的命名空间 | 新服务默认 BestEffort，最先被驱逐 |
| 只看 CPU 不看内存工作集 | 内存 OOM 被误判为 “代码 bug” |
| 日志写容器层且不设 `emptyDir.sizeLimit` | 节点磁盘被写满，Pod 被驱逐 |
| 只监控 `memory.available` 就以为覆盖了驱逐 | `inodesFree < 5%`、`imagefs.available < 15%` 同样触发驱逐 |
| DaemonSet 用 Burstable | 被驱逐后原地重建，回收动作白做 |

## 三条铁律

> 🔑 **requests 管调度、limits 管运行时**；两者都不设 = 把节点交给运气。

> 🔑 **CPU 超限变慢、内存超限被杀**；排查方向由这条区分决定。

> 🔑 **Guaranteed 只给核心链路**；全站 Guaranteed 的账单通常没人愿意付。

## 自检

**Q1** 一个 Pod 的 `requests.cpu` 是 `100m`、`limits.cpu` 是 `100m`，压测时 P99 飙升但节点 CPU 只有 30%。为什么？

▸ 答案：**被自己的 quota 节流**。`limits.cpu: 100m` 表示每 100ms 周期最多 10ms CPU 时间，节点再空闲也不能超用；多线程场景下周期末会等下一周期，表现为 P99 尖刺。验证看 `nr_throttled` 比例；修法是提高 limit 或降低单实例并发。

**Q2** 节点 OOM 了，但被杀的 Pod `RSS` 只有 200Mi，limit 是 1Gi。怎么解释？

▸ 答案：可能是 **page cache 吃掉了额度**：`memory.max` 统计 cgroup 的总用量（含页缓存），容器大量读写文件时缓存上涨，触到 1Gi 就 OOM，而 RSS 只反映匿名内存。另一个可能是**节点级 OOM**（不是 cgroup OOM）：多个 Pod 加起来超过节点内存，内核选 “oom_score 最高” 的进程杀，此时看的是节点而非单个 limit。

**Q3** 为什么 BestEffort 的 Pod 最先被驱逐？

▸ 答案：因为它没有声明任何 requests，调度时按 0 计入，对节点的 “贡献” 最小；kubelet 驱逐时按 “QoS 等级 + 是否超出 request” 排序，BestEffort 排在最前。设计意图是 “让没申请资源的负载先让位给有申请的负载”。所以关键服务至少要设 requests（哪怕很小），避免落到 BestEffort。

**Q4** HPA 按 CPU 利用率扩缩容，为什么 requests 设得不准会导致 HPA 失效？

▸ 答案：因为 CPU 利用率的分母是 **requests**。requests 设得过高，同样的实际用量算出来的利用率偏低，HPA 永远不扩容；设得过低，利用率虚高，频繁触发扩容甚至抖动。正确做法是让 requests 接近常态用量（P50–P75），并给 HPA 配 `behavior`（扩容快、缩容慢）与稳定窗口。

**Q5** 团队把所有服务都设成 Guaranteed，账单涨了 80%，怎么优化？

▸ 答案：按 “链路重要性” 分层：核心交易保 Guaranteed（少量），其余改 Burstable（request 按 P95、limit 按 P99×1.5），批处理改 BestEffort + Spot。再用 HPA 把 “峰值冗余” 换成弹性。Guaranteed 的本质是 “用钱买确定性”，全站买确定性等于为所有服务付冗余费。

**Q6** 团队给核心服务写了 `limits.cpu: 4`，期望 “独占 4 核”，但压测时仍然被节流。差哪几步？

▸ 答案：差**两个前提**。要真正绑核（走 cpuset）必须同时满足：QoS 是 **Guaranteed**（每个容器的 CPU/内存 request 与 limit 相等），且该资源是**整数**（`4` 成立，`3500m` 不行）。只写 `limits.cpu: 4` 而没有配平的 requests，Pod 是 Burstable，`limits` 只是每 100ms 的上限，超了就被 `cfs_quota` 节流——节点再空闲也一样。
