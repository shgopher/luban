# 7.3 Service 与 Ingress

## 一句话

> Service 是 “一个稳定的虚拟 IP + 一组随时变化的 Endpoint”，Ingress 是 “一张七层路由表”；前者解决 “Pod IP 会变”，后者解决 “一个入口怎么分发给多个 Service”——两者都**不做流量治理**（限流、熔断、鉴权在别处）。

## Service 的四种类型

| 类型 | 可从哪访问 | 代价 | 典型用途 |
|---|---|---|---|
| **ClusterIP** | 集群内 | 无 | 服务间调用（默认） |
| **NodePort** | 节点 IP + 30000–32767 端口 | 端口有限、暴露节点、无健康检查 | 调试、临时暴露 |
| **LoadBalancer** | 云 LB 的公网/内网地址 | 每个 Service 一个 LB，成本随服务数涨 | 少量需独立 IP 的服务 |
| **Headless**（`clusterIP: None`） | 直接返回 Pod IP 列表 | 客户端自己做负载均衡与发现 | StatefulSet、客户端分片 |
| **ExternalName**（`externalName: db.example.com`） | 集群内一个 CNAME 名字 | 无代理、无负载均衡 | 给外部依赖起个稳定别名 |

> ⚠️ **ExternalName 只加一条 CNAME 记录**，不做转发：访问 `my-svc.default.svc.cluster.local` 等价于直接访问那个外部域名，没有后端 Pod 可均衡。把它当 “集群内反向代理” 用，是最常见的误读。

## DNS：四套 A 记录，决定你能按什么名字找到 Pod

Service 的发现能力一半在 kube-proxy，另一半在 kube-dns。四种记录格式对应四种 “我能不能被按名字找到”：

| 对象 | 记录格式 | 解析结果 |
|---|---|---|
| ClusterIP Service | `<svc>.<ns>.svc.cluster.local` | 那个 VIP |
| Headless Service | 同格式 | 被代理 Pod 的**全部 IP 集合**（客户端得自己处理这组地址） |
| Headless + Pod 声明了 `hostname` + `subdomain` | `<hostname>.<subdomain>.<ns>.svc.cluster.local` | 该 Pod 的 IP |
| 普通 Service 代理的 Pod | `<dashed-pod-ip>.<ns>.pod.cluster.local` | 该 Pod 的 IP |

```bash
# 第三个格式的实例：一个 hostname=busybox-1、subdomain=default-subdomain 的 Pod
nslookup busybox-1.default-subdomain.default.svc.cluster.local
# Name: busybox-1.default-subdomain.default.svc.cluster.local
```

> 🔑 有状态副本之间只能按 **DNS 名**互访，不能缓存 Pod IP：Headless 记录本身不变，但它解析出的地址会随 Pod 重建而变。同理，Pod 的 `/etc/hosts` 由 kubelet 单独挂载（这就是 6.2 里 “commit 之后 hosts 丢失” 的那一层），所以 Pod 重建后 hostname 仍然有效。


## Endpoint 才是真相：Service 只是引用

```
Service(selector: app=web) ──► EndpointSlice ──► [10.1.2.3:8080, 10.1.3.7:8080]
                                     ▲
                          只收 readiness 通过的 Pod
```

| 现象 | 原因 |
|---|---|
| Service 有 IP，但请求超时 | Endpoint 为空：没有 Pod 通过 readiness，或 selector 拼错 |
| 部分请求失败 | Endpoint 里有**未就绪**的 Pod（没配 readinessProbe） |
| 滚动更新时零星 502 | 摘除 Endpoint 与进程退出存在竞态（优雅下线没做对） |
| 改了 Pod 标签后流量断 | Service 按标签挑 Pod，改标签等于换成员 |

排查顺序固定为：`kubectl get endpointslices -l kubernetes.io/service-name=<svc>` → 有没有地址 → 再查 Pod readiness。

按**域名**访问不通时，先分清是 Service 配错还是集群 DNS 挂了——在任意 Pod 里打一条：

```bash
nslookup kubernetes.default
# Server:  10.0.0.10          ← kube-dns 的 ClusterIP，这一行有值说明 DNS 链路活着
# Name:    kubernetes.default.svc.cluster.local
```

## kube-proxy 三种转发模式

| 模式 | 机制 | 特点 |
|---|---|---|
| **iptables** | 每条 Service 生成 DNAT 规则，随机选 Endpoint | 通用；连接多时规则多、更新慢；**无真正负载均衡**（概率均分） |
| **IPVS** | 内核哈希表 + 多种调度算法 | 大规模更稳、支持 rr/lc 等算法；需要内核模块 |
| **eBPF（Cilium 等）** | 绕过 iptables，用 eBPF 程序转发 | 性能最好、可观测性强；排错要换工具链 |

### iptables 的 “负载均衡” 是一条概率阶梯

三个 Endpoint 各占 1/3，靠的不是 “抛硬币三次”，而是一串**命中率递减**的 random 规则：

```bash
# KUBE-SVC-<hash> 链，从上到下逐条匹配
-m statistic --mode random --probability 0.33333333349 -j KUBE-SEP-A
-m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-B
                                                   -j KUBE-SEP-C
```

第一条约 1/3 命中；没中时只剩两条候选，所以第二条填 **1/2**；剩下的自然落到第三条（不写 probability，即 100%）。命中后进 `KUBE-SEP-<hash>` 做 DNAT，在**路由决策之前**把目的地址改写成 `Pod IP:port`。

> ⚠️ 想当然地三条都填 `1/3`，实际分布会严重偏向前面的规则——这也是 “短连接场景下 Service 负载不均” 的一个真实根因。

### 源 IP 为什么会丢：一个 0x4000 标记

NodePort 下，包在 POSTROUTING 阶段会被 SNAT 一次，源地址变成节点的 CNI 网桥地址（没有网桥就用节点 IP）。触发条件是包上带着 **DNAT 之前打上的 `0x4000` 标志**——所以它只影响 Service 转发出来的流量，普通流量不受牵连。

必须 SNAT 的原因是非对称路径：

```
client ──► node2 ──(转发)──► node1 上的 Pod
              ▲                    │
              └──── 直接回 client ◄─┘   ← client 看到“请求发 node2、回复来自 node1”，丢弃
```

`externalTrafficPolicy: Local` 能保留源 IP，正是因为它**只转发本机 Pod**：回复可原路返回，无需 SNAT；代价是无 Pod 的节点直接丢包。

### IPVS 并不更快，它省的是 “规则维护”

IPVS 模式会先在节点上建一块虚拟网卡 `kube-ipvs0`，把每个 Service VIP 以 **/32** 挂上去，再用 `ipvsadm` 为每个 Endpoint 建虚拟主机（默认 `rr` 轮询）：

```bash
ip addr show kube-ipvs0
# inet 10.0.1.175/32 scope global kube-ipvs0
```

它的转发**同样基于 Netfilter 的 NAT 模式**，所以在转发这一层上并没有显著性能提升。真正省下的是：不必为每个 Pod 维护 iptables 规则，把匹配放进内核哈希表。包过滤与 SNAT 仍由 iptables 完成，只是这类辅助规则数量固定、不随 Pod 数增长。

> 🔑 大规模集群用 `--proxy-mode=ipvs` 的理由是 **规则数量不随 Pod 数线性增长**，不是 “转发更快”。


两种 “保留客户端 IP” 的开关要分清：

- `externalTrafficPolicy: Local`：只把流量转给**本节点**上的 Pod，源 IP 得以保留，但流量分布不均（节点上没 Pod 就丢）。
- `sessionAffinity: ClientIP`：同一客户端固定到同一 Pod，代价是负载不均、Pod 重启后粘性失效。

## Pod 访问不了自己的 Service：hairpin 模式

症状很有辨识度：**别的 Pod 访问这个 Service 正常，只有 Pod 自己经 Service 访问自己不通**（典型是容器内打本机 NodePort）。根因是网桥的一条默认规则：**网桥不允许一个包从同一端口进来后再从该端口发出**。而 “自己访问自己” 恰好要求这样——包经 DNAT 转回同一个容器，必须从同一个 veth 端口进又出。

修法是 kubelet 的 `--hairpin-mode`：

| 取值 | 做法 | 验收命令（应全部为 1 / 出现 PROMISC） |
|---|---|---|
| `hairpin-veth` | 给每个 veth 端口开 hairpin | `for d in /sys/devices/virtual/net/cni0/brif/veth*/hairpin_mode; do echo "$d = $(cat $d)"; done` |
| `promiscuous-bridge` | 让网桥进混杂模式 | `ifconfig cni0 \| grep PROMISC` |

> ⚠️ 这类故障最容易被误判成 “网络插件坏了”：抓包能看到 SYN 到了 Pod、SYN-ACK 却没回程——回程被网桥端口规则丢了。

## Ingress：只做七层路由

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: nginx            # 必须有，否则会被忽略
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend: {service: {name: api, port: {number: 8080}}}
          - path: /
            pathType: Prefix
            backend: {service: {name: web, port: {number: 80}}}
  tls:
    - hosts: [app.example.com]
      secretName: app-tls
```

```bash
kubectl get ingress web
# NAME  CLASS  HOSTS             ADDRESS       PORTS  AGE
# web   nginx  app.example.com   10.0.0.12     80,443 5m
kubectl describe ingress web | tail -5     # 看后端 Endpoint 是否解析出来
```

四条判据：`ingressClassName` 是否匹配、`pathType` 是否写清（`Prefix` / `Exact`）、TLS Secret 是否在同命名空间、后端 Service 是否有 Endpoint。四条都过，剩下才是 Ingress Controller 自身配置。

**Ingress 的表达力天花板**：它只覆盖 “host + path → service”，做不了 header/权重/重试/超时（各控制器用自己的注解补，互不兼容）。需要这些能力时，方向是 **Gateway API**（HTTPRoute 等）或服务网格，而不是继续堆注解。

## 反模式

| 反模式 | 后果 |
|---|---|
| 不给 Pod 配 readinessProbe | Endpoint 包含未就绪 Pod，滚动更新必炸 |
| 用 NodePort 当生产入口 | 无健康检查、暴露节点、端口冲突难管 |
| 每个服务一个 LoadBalancer | 云账单随服务数线性上涨 |
| Ingress 里做鉴权与限流 | 注解碎片化，换控制器就重写；治理逻辑应在网关/网格 |
| 客户端硬编码 Service IP | Service 重建后 IP 变化（ClusterIP 也可能变），调用全挂 |
| 用 `ping` 测 ClusterIP | ClusterIP 是虚拟 IP，ICMP 通常不转发，ping 不通不代表服务不通 |
| 忘了 `ingressClassName` | Ingress 被静默忽略，表现为 “404 但配置看着没问题” |
| Pod 自访问自己的 Service，但 `hairpin-mode` 没配 | 自访问不通，被误判成 CNI 故障 |
| 缓存 Headless 解析出的 Pod IP | Pod 重建后 IP 变，连接打到已经消失的地址 |
| 把 ExternalName 当反向代理用 | 它只有一条 CNAME，不转发、不负载均衡 |

## 三条铁律

> 🔑 **Service 靠 Endpoint 转发**：先看 Endpoint 再看 Service，顺序反了会浪费半小时。

> 🔑 **readiness 决定 “能不能接流量”**；没有它，Service 只是把流量赌在运气上。

> 🔑 **入口治理分层**：Service 管连通、Ingress 管路由、网关/网格管限流鉴权；混在一起必然碎片化。

## 自检

**Q1** Service 的 ClusterIP 能 ping 通吗？为什么？

▸ 答案：**通常不能**，而且这不说明服务坏了。ClusterIP 是 kube-proxy（或 eBPF）在数据面实现的**虚拟地址**，不落在任何网卡上；ICMP 一般不被 DNAT 规则处理，所以 ping 无响应。验证连通性要用 `curl`/`nc` 打具体端口，或看 `endpointslices` 是否有地址。

**Q2** 滚动更新时出现零星 502，Service/Endpoint 层面最可能的原因是什么？

▸ 答案：**摘除与退出存在竞态**：kubelet 在收到删除请求时，Endpoints 摘除与 `SIGTERM` 几乎同时发生，而 kube-proxy 的规则更新有延迟，于是 “流量还在进来，进程已经开始退出”。修法三件套：`preStop` 里 sleep 几秒、`terminationGracePeriodSeconds` 留足、应用收到 `SIGTERM` 后先停止接新连接再优雅关闭。

**Q3** `externalTrafficPolicy: Local` 有什么代价？

▸ 答案：**流量分布不均**：只有本节点上有 Pod 时才转发，没有就丢弃（不会跨节点转）。好处是保留客户端源 IP（否则经过 SNAT 后只能看到节点 IP），对风控与审计很重要。取舍是：要么用 LB 的 “节点本地健康检查” 配合，要么接受部分节点没有 Pod 时的可用性下降。

**Q4** 为什么 Ingress 的 YAML 看起来正确，访问却是 404？

▸ 答案：四查：① `ingressClassName` 与集群里实际安装的 Controller 不匹配（最常见的静默忽略）；② `pathType` 写成 `Prefix` 但 Controller 是老版本不认；③ 后端 Service 在同命名空间但没有 Endpoint；④ TLS Secret 缺失导致整条规则不生效。判断方法：`kubectl describe ingress` 看 Address 是否被 Controller 填上，以及后端 Endpoint 是否列出。

**Q5** 什么时候该从 Ingress 换到 Gateway API？

▸ 答案：当需求出现 **header/query 级路由、按权重灰度、重试与超时策略、跨命名空间的路由归属** 时。Ingress 用注解实现这些，导致 “换控制器即重写”；Gateway API 把这些变成一等字段（HTTPRoute 的 matches/filters/backendRefs），且支持角色分离（基础设施 owner 管 Gateway，应用管 Route）。只是 “host + path” 的话，Ingress 足够且更简单。
