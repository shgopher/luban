# 7.2 K8s 对象模型 (Pod / ReplicaSet / Deployment / StatefulSet / DaemonSet / Job)

## 一句话

> 对象模型不是 “一堆 YAML”，而是**五件套**：`spec`（你要什么）、`status`（现在是什么）、控制器（谁负责拉平）、`ownerReferences`（谁能级联删）、标签选择器（谁跟谁一组）；看懂 `Deployment → ReplicaSet → Pod` 的三层套娃，就解释了 90% 的 “我改了怎么不生效”。

## 五种工作负载：差别在 “身份” 与 “终止语义”

| 对象 | 管什么 | 能不能有稳定身份 | 谁创建它下面的 Pod |
|---|---|---|---|
| **Pod** | 一个或多个容器的运行单元 | 名字随机，重建即换 | 你自己（或用下面的对象） |
| **Deployment** | 无状态副本 + 版本滚动 | **不能**，Pod 可互换 | Deployment → ReplicaSet → Pod |
| **StatefulSet** | 有状态副本 + 固定身份与顺序 | **能**（`web-0`、`web-1` 与独立 PVC） | StatefulSet → Pod（逐个创建） |
| **DaemonSet** | 每个节点一个副本 | 跟节点走，节点加/减自动增删 | DaemonSet → Pod |
| **Job / CronJob** | 跑到成功为止 / 按计划跑 | 无（可重试，`completions` 计数） | Job → Pod |

三句判据：

- **要不要稳定名字与独立存储**？要 → StatefulSet。
- **要不要 “每个节点都有一份”**（日志、网络、监控）？要 → DaemonSet。
- **跑完就该退出**？是 → Job；周期性 → CronJob。

## Pod 的真相：一个 Infra 容器 + 一组共享的 Namespace

K8s 真正操作的只有宿主机上的 **Namespace** 与 **Cgroups**，内核里并没有 “Pod” 这个对象。Pod 之所以成立，是因为它先起一个 **Infra 容器**：

- 镜像 `k8s.gcr.io/pause`（汇编编写、永远处于暂停状态），**解压后只有 100~200 KB**；
- 它是 Pod 里**第一个被创建**的容器，唯一职责是**持有 Network Namespace**；
- 其余容器以 `--net=container:<infra>` 的方式 join 进来（本质是 `setns()`）。

| 现象 | 原因 |
|---|---|
| 一个 Pod 只有一个 IP | 所有容器共用 Infra 容器的 netns |
| 进出 Pod 的流量都记在 Infra 容器上 | 同上；CNI 插件**只**配置这一个 netns |
| 别指望往 pause 的 rootfs 里装东西 | 它几乎是空的 |
| 用户容器反复重启，Pod 依然存在 | Pod 的生命周期只跟 Infra 容器一致 |

Pod 级还提供四个 “共享宿主机” 的开关（必须是 Pod 级字段，因为它们描述的是 “机器” 而不是 “程序”）：

| 字段 | 效果 |
|---|---|
| `spec.shareProcessNamespace: true` | Pod 内容器共享 PID 命名空间，互相 `ps` 得到 |
| `hostNetwork: true` | 整个 Pod 直接用宿主机网络栈 |
| `hostIPC: true` | 与宿主机 IPC 通信 |
| `hostPID: true` | 看到宿主机全部进程 |

```bash
kubectl exec -it shell -- ps ax     # 前提：shareProcessNamespace: true
# PID  1 /pause                                  ← Infra 容器
#       8 nginx: master process nginx -g daemon off;
#      14 nginx: worker process
#      15 sh                                     ← 你 exec 进来的 shell
```

> 🔑 看到 PID 1 是 `/pause` 而不是你的应用，是 “这个 Shell 看到的是整个 Pod” 的直接证据。

## restartPolicy 决定 Pod 会不会 “失败”

单容器退出码非 0，Pod **不一定**变 Failed：

| 场景 | `Always`（默认） | `OnFailure` | `Never` |
|---|---|---|---|
| 单容器非 0 退出 | 重启容器，Pod 仍 Running | 重启容器，Pod 仍 Running | **Pod 变 Failed** |
| 多容器之一异常退出 | 只重启该容器 | 只重启该容器 | **Pod 仍 Running**（READY 显示正常容器数，如 `1/2`） |

判定规则只有两条：**策略允许重启 → Pod 保持 Running；只有所有容器都进入异常状态，Pod 才 Failed。**

另外两个易错点：

1. K8s 没有 Docker 的 Stop 语义，所谓 “重启” 是**重建容器**，不是把进程拉起来。
2. 恢复永远发生在**当前节点**：Pod 一旦绑定节点，宿主机宕机也不会漂移到别的机器。要有 “换机器” 的能力，得用 Deployment 管（哪怕 1 个副本）。

> 🔑 这正是 **Deployment 只允许 `restartPolicy=Always`** 的原因：ReplicaSet 靠 “数 Pod 个数” 保证副本数，只有容器总能回到 Running，`spec.replicas` 才等于可用副本数。允许 `Never` / `OnFailure`，这两个数就不是一回事了。

## 四种控制器的硬语义：不是 “设个副本数” 那么简单

### Job：按差额补齐，再被并行度封顶

每轮调谐算的是：

```
需创建数 = completions − Running 数 − 已 Succeeded 数
再取 min(需创建数, parallelism)
```

`completions: 4` + `parallelism: 2`：先并发建 2 个，每完成 1 个补 1 个，直到 4 个成功。`kubectl get job` 的 **DESIRED 列就是 `completions`**，不是 `parallelism`。

| 字段 | 默认 / 允许值 | 语义 |
|---|---|---|
| `restartPolicy` | 只允许 `Never` / `OnFailure` | `Never` 失败**新建 Pod**，`OnFailure` 只**重启容器** |
| `backoffLimit` | **6** | 重试上限；重建间隔指数增长 **10s、20s、40s…** |
| `activeDeadlineSeconds` | 无 | 到期终止该 Job 全部 Pod，Pod 的 reason 为 `DeadlineExceeded` |

Job 还有一处与众不同：**不需要用户写 `spec.selector`**。它创建时自动给 Pod 模板打上 `controller-uid=<随机 UID>`，自己再拿同一个值当 selector，因此不同 Job 的 Pod 不会互相认领——`kubectl describe job` 的 Selector 行就能看到这串 UID。

### DaemonSet：不数副本，给每个 Pod 钉一个节点

DaemonSet Controller 拿不到 `replicas`，它的循环是 “遍历所有 Node”：

| 该节点上的 Pod 数 | 动作 |
|---|---|
| 0 | 建一个 |
| 1 | 跳过（哪怕标签被改过） |
| >1 | 删到 1 个 |

提交前它会给生成的 Pod 注入两样东西：**`nodeAffinity`（`metadata.name In <当前遍历的节点>`）** 和 **容忍 `node.kubernetes.io/unschedulable` 的 toleration**。v1.11 之前它干脆直接写 `spec.nodename` 绕过调度器，之后才交还给调度器统一决策。

> ⚠️ 节点没装网络插件会被自动打上 `node.kubernetes.io/network-unavailable` 污点（NoSchedule），普通 Pod 调度不上去。所以 CNI 插件的 DaemonSet 模板**必须显式写容忍**（同 key、`operator: Exists`、`effect: NoSchedule`）——这才是 “先装 K8s、再装网络插件” 能成立的机制原因。

### CronJob：三种并发策略 + 一个写死的 100

按 Unix Cron 五段（分 / 时 / 日 / 月 / 周）创建 Job。两个 Job 撞车时由 `concurrencyPolicy` 决定：

| 取值 | 行为 |
|---|---|
| `Allow`（默认） | 允许并存，两个一起跑 |
| `Forbid` | 上一轮没结束，本轮**直接跳过** |
| `Replace` | 用新 Job **取代**未跑完的旧 Job |

创建失败记一次 **miss**；在 `startingDeadlineSeconds` 窗口内 miss 累计到 **100 次**，CronJob 就彻底停止再创建这个 Job。**100 是写死的，不可配置**——这是 “CronJob 悄无声息不跑了” 的根因。

### StatefulSet：正序有 Ready 门，滚动反序

- 按 0、1、2… **正序创建**，且必须等前一个 **Running 且 Ready** 才创建下一个：`web-0` 没 Ready，`web-1` 一直 Pending，`kubectl get sts` 停在 `CURRENT=1`。
- **滚动更新反序**：从最大编号往小更新，任一 Pod 更新失败，整次滚动即停止。
- **灰度靠 `partition`**：`rollingUpdate.partition=N` 时只有序号 ≥N 的 Pod 升级；序号 <N 的 Pod 即使被删掉重建，**仍用旧版本**。

```bash
kubectl patch statefulset mysql -p '{"spec":{"updateStrategy":{"type":"RollingUpdate","rollingUpdate":{"partition":2}}}}'
# 之后只升级 mysql-2、mysql-3；mysql-0、mysql-1 连重建都保持旧模板
```

> ⚠️ 卡在 `CURRENT=1/N` 时，先查 `web-0` 的 readinessProbe，而不是查调度——它不是被调度卡住的。

## 改了不生效的另一半：三个 “写了也没用” 的字段

| 写法 | 真实行为 |
|---|---|
| 直接 `exec` 进容器改 `/etc/hosts` | Pod 删除重建后 **kubelet 会覆盖回去**；要改只能用 `spec.hostAliases`（ip + hostnames 列表，追加到 hosts 末尾） |
| 手填 `spec.nodeName` | 一旦赋值，Pod 即被视为 “已经过调度”，调度结果就是这个节点名；这能绕过调度器，只建议在测试调试时用 |
| `image: nginx:latest`（或省略 tag）且不写策略 | 被当作 `imagePullPolicy: Always`，每次创建 Pod 都重新拉——**浮动 tag 命中不了本地缓存** |

镜像拉取策略三值对照：

| 策略 | 行为 |
|---|---|
| `Always` | 每次创建 Pod 都拉 |
| `IfNotPresent` | 本地有就不拉 |
| `Never` | 只用本地，没有就 `ErrImagePull` |

> ⚠️ 默认值的口径随版本变过（早期文档写 `Always`，现行文档在 tag 非 `latest` 时是 `IfNotPresent`）。**引用这条要带版本**；生产结论与版本无关：别用浮动 tag。

## 排障第一步：describe 的 Events 是一条证据链

```bash
kubectl describe pod app-0
# Events:
#   Normal  Scheduled  1m    default-scheduler   Successfully assigned default/app-0 to node-1
#   Normal  Pulled     17s   kubelet, node-1     Container image "nginx:1.25" already present
#   Normal  Created    17s   kubelet, node-1     Created container app
#   Normal  Started    16s   kubelet, node-1     Started container app
```

`From` 列直接暴露组件分工，链条断在哪一步，故障域就在哪：

| 断在哪 | 故障域 |
|---|---|
| 没有 `Scheduled` | 调度：资源不足、亲和性、污点、PVC 未绑定 |
| `Pulling` 卡住 / `ErrImagePull` | 镜像：仓库地址、`imagePullSecrets`、节点出网 |
| `Created` 之后没有 `Started` | 运行时：入口命令不存在、权限、挂载失败 |
| `Started` 之后反复重启 | 应用：crash、探针失败、`OOMKilled` |

## 套娃关系与 “改了不生效”

```
Deployment (声明副本数 3、镜像 A)
└── ReplicaSet (A-7d9f)   ← 每次换模板就新建一个 RS
    ├── Pod A-7d9f-1
    ├── Pod A-7d9f-2
    └── Pod A-7d9f-3
```

| 现象 | 真实原因 |
|---|---|
| 改了 Deployment 的 `selector`，报 `field is immutable` | 选择器决定 “这个 Deployment 拥有哪些 ReplicaSet”，改了会切断所有权，API server 直接拒绝 |
| `kubectl set image` 之后旧 Pod 还在 | 旧 ReplicaSet 被缩到 0 但保留（`revisionHistoryLimit`），用于回滚 |
| 手工 `kubectl edit pod` 改了镜像，一会儿又变回来 | Pod 由 RS 管理，模板一收敛就覆盖；要改模板 |
| 删了 Deployment，Pod 还在 | 级联删除策略（`--cascade=orphan`）或 ownerReferences 被清掉 |
| 副本数是 3，实际跑了 5 个 | 有另一个控制器（HPA/RS/StatefulSet）也在写 `spec.replicas` |

## 五个字段决定了 “谁拥有谁”

| 字段 | 作用 | 常见坑 |
|---|---|---|
| `metadata.ownerReferences` | 父对象删除时级联删除子对象 | 手写的对象没这个引用，删除父对象会留下垃圾 |
| `metadata.labels` | 被选择器匹配、被策略匹配 | 用作业务分组，却被 `NetworkPolicy`/`Service` 意外命中 |
| `spec.selector` | 控制器认领 Pod 的依据 | 手写 Pod 的 labels 与控制器的 selector 重叠 → 被 “抢走” 再删掉 |
| `metadata.finalizers` | 删除前的拦截器（清理外部资源） | 控制器挂了，对象永远 `Terminating` |
| `status.conditions` | 结构化的 “现在是什么状态” | 只看 `Ready` 不看 `observedGeneration`，读到过期状态 |

四个 “号” 容易混：

| 字段 | 含义 |
|---|---|
| `metadata.resourceVersion` | 乐观并发的令牌，每次写入自增 |
| `metadata.generation` | **spec** 的版本号（模板改动才 +1） |
| `status.observedGeneration` | 控制器**已经处理到**的 spec 版本；小于 generation 表示还在收敛 |
| `metadata.managedFields` | 哪个字段由谁（kubectl / 控制器）管理，SSA 的账本 |

排 “改了不生效” 的第一步：比 `generation` 与 `observedGeneration`。相等说明控制器已处理，问题在别处；不等说明控制器还没跟上（或卡住）。

```bash
kubectl get deploy app -o jsonpath='{.metadata.generation} {.status.observedGeneration}{"\n"}'
# 3 2   → 控制器还在处理第 2 代，不要急着怀疑“没生效”
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 手写 Pod（不用工作负载对象） | 节点故障后不会重建，“自愈” 只是传说 |
| 用 `kubectl edit` 改线上 Pod | 与控制器打架，改动随时被覆盖且不可追溯 |
| Deployment 的 selector 写成 “过宽” 的标签 | 认领了别人的 Pod，滚动更新时误删 |
| 把有状态服务塞进 Deployment | 重启丢身份、PVC 挂错、顺序不可控 |
| 忽略 `observedGeneration` | 把 “还在收敛” 误判成 “配置错” |
| 一个对象塞 40 个 container | 调度与探针粒度失真，一个挂了全换 |
| `exec` 进容器改 `/etc/hosts` 或配置文件 | 重建即丢；声明式源头与实际状态分叉 |
| 给 DaemonSet 的 Pod 手改 `nodeName` | 下次调谐被覆盖，且丢掉容忍污点的能力 |
| 用 `:latest` 又期待命中本地镜像缓存 | 浮动 tag 按 `Always` 拉取，发布会卡在拉镜像 |
| 只看 `kubectl get pod` 判断 Job 成败 | 成功后 Pod 可能已被清理，要看 Job 的 `SUCCESSFUL` |

## 三条铁律

> 🔑 **只改模板，不改实例**：实例（Pod）是控制器的产物，改它没用。

> 🔑 **选对象看两件事**：要不要稳定身份（StatefulSet）、要不要每节点一份（DaemonSet）。

> 🔑 **`generation ≠ observedGeneration` 就是 “还没生效”**，先等收敛，再查配置。

## 自检

**Q1** 手工创建一个 Pod，打上与某 Deployment 相同的标签，会发生什么？

▸ 答案：**会被 Deployment 的 ReplicaSet 认领，然后被杀掉**。RS 按 selector 统计 “我有几个 Pod”，多出来的（未被它创建但匹配标签的）会被删除以收敛到期望副本数。这也解释了一个常见事故：手写的调试 Pod 用了通用标签 `app=web`，几分钟后消失。解法是加一个不匹配的标签，或用 `kubectl run` 的独立标签。

**Q2** 为什么 Deployment 的 `spec.selector` 不可变，而 `spec.template` 可变？

▸ 答案：因为 selector 定义了**所有权边界**：控制器用它认领 Pod 与 ReplicaSet。改变它等于 “把已有的子对象全部抛弃并认领一批新的”，语义上不是更新而是重建，容易造成孤儿对象与业务中断。所以 API server 直接禁止；要换 selector，只能新建 Deployment 再迁移。

**Q3** StatefulSet 的 `web-0` 被删了，重建后为什么还能挂回原来的数据？

▸ 答案：因为 StatefulSet 用 `volumeClaimTemplates` 为每个序号生成**固定名字的 PVC**（`data-web-0`），PVC 独立于 Pod 生命周期。新 Pod 复用同名 PVC 就接上了原数据。反过来说：**删 StatefulSet 默认不会删 PVC**，这是保护数据的设计，也常导致 “以为清理干净了，其实磁盘还在计费”。

**Q4** `kubectl get pods` 显示 3 个 Running，但业务报 502。对象模型层面最该先看什么？

▸ 答案：看 **`status.conditions` 的 `Ready`** 与 **Endpoints 是否为空**。`Running` 只说明进程在，不代表就绪；没有 readiness 通过就不会进 Endpoints，Service 转发不到它。其次是 `observedGeneration`（是否收敛完）与容器 `restartCount`（是否在反复重启）。这就是 “看对象不看日志” 的典型盲区。

**Q5** 为什么 “把 5 个服务放进一个 Pod” 通常是错的？

▸ 答案：因为 Pod 是**调度与生命周期的最小单位**：同一个 Pod 内的容器总是一起调度、一起重建、共享网络与卷。放 5 个服务意味着：一个崩溃/升级会带走全部、无法独立扩缩容、端口冲突只能靠 localhost 协调。正确的组合原则是 “**是否必须同生共死**”（如 sidecar 代理），而不是 “部署方便”。

**Q6** 一个 Pod 已经是 Running，但容器退出码一直是 1、`RESTARTS` 显示 40，为什么它没有变成 Failed？

▸ 答案：**判据是 `restartPolicy`，不是退出码**。默认 `Always` 下容器退出就重启，Pod 始终是 Running；只有 `Never` 才会把它判成 Failed，多容器 Pod 还要等所有容器都异常才 Failed。所以要判断 “这个 Pod 到底好不好”，看的是 `RESTARTS`、`lastState.terminated.exitCode` 与 `waiting.reason=CrashLoopBackOff`，而不是 `STATUS` 列。反过来说，看到 Failed 就该意识到：这个 Pod 的策略不是 `Always`，或者它所有容器都死了。

**Q7** Job 设了 `completions: 4`、`parallelism: 2`，`kubectl get job` 的 `COMPLETIONS`/`DESIRED` 是几？同时会有几个 Pod 在跑？

▸ 答案：目标是 **4**（`completions` 才是 DESIRED，`parallelism` 只是封顶），任一时刻**最多 2 个**在跑：控制器算 `需创建 = completions − Running − 已成功 = 4−0−0 = 4`，再被 `parallelism=2` 压成 2；之后每成功 1 个补 1 个。所以 “并行度” 影响的是速度，不是完成数。
