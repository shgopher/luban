# 7.16 自定义 API 的完整生命周期

## 一句话

> 给 K8s 加一个自定义 API，不是“写个 CRD + 一个控制器”两件事，而是**六环一条链**：types → 生成 → 准入 → 注册 → 控制器 → 对账；缺任何一环，症状都会长成同一句话——**“数据对不上”**，但修法完全不同。

## 一条链，六环，六个产出物

```
① types        pkg/apis/apps/v1beta1/types.go        带 deepcopy 标记的 Go 结构体
      │ codegen
② 生成          pkg/generated/{...}                   deepcopy/defaulter/conversion/openapi/client
      │ 注册 scheme
③ 准入          admission/plugin/<res>/               默认值、删除保护、跨字段校验
      │ 注册 APIGroupInfo
④ 存储与 REST   registry/{<res>/strategy, storage, rest}   /apis/<group>/<ver>/<res> 与 <res>/status
      │ watch
⑤ 控制器        controller/<res>/                     把实际状态收敛到 spec
      │ 对账
⑥ 清理          resourceclean/cleaner_<res>.go        删掉另一个存储里的残留
```

| # | 环 | 产出物 | 缺了这一环，症状是 |
|---|---|---|---|
| ① | types | 类型定义 + 注册（`SchemeGroupVersion`、`AddToScheme`） | 无 |
| ② | 生成 | `pkg/generated/` 全套 | 手写 client 与 deepcopy，**每次改字段都漏一处** |
| ③ | 准入 | `admission/plugin/<res>/admission.go` | 用户能改本该系统填的字段；删除保护失效 |
| ④ | 注册 | `registry/<res>/strategy.go` + `rest/storage_*.go` | 资源存在但没有 `/status` 子资源，控制器与用户抢同一个字段 |
| ⑤ | 控制器 | `controller/<res>/` | 期望状态永远不收敛，`kubectl get` 里 status 一直空 |
| ⑥ | 对账 | `resourceclean/cleaner_<res>.go` | K8s 对象已删，数据库里还剩一行，报表与配额全错 |

> 🔑 这六环里只有 ③ 和 ⑤ 是“业务逻辑”，其余四环是**契约与管道**。项目出问题时，九成的“数据对不上”其实死在 ①③④⑥，而大家第一反应永远是去查 ⑤ 的控制器——因为只有它有代码量。

## ① types：契约的唯一真相

一个自定义 API 的 types 包通常长这样（onex 的 `pkg/apis/apps/`，[源码](https://github.com/shgopher/onex)）：

```text
pkg/apis/apps/
├── register.go            # GroupName、SchemeGroupVersion
├── miner_types.go         # Miner、MinerSpec、MinerStatus
├── minerset_types.go
├── common_types.go        # 共享的 Condition / Phase
├── validation/            # 跨字段校验（比 OpenAPI schema 表达力强）
├── install/               # 把 versions 加进 scheme
├── fuzzer/                # roundtrip fuzz：v1beta1 → v1 → v1beta1 必须完全相等
└── v1beta1/               # 对外版本：types + register.go（含 AddToScheme）
```

三个结构决定：

| 结构 | 为什么 |
|---|---|
| **spec 与 status 分成两个结构体** | 用户写 spec、控制器写 status；物理分开后，`/status` 子资源才有意义 |
| **内部版 + 对外多版本**（`apps` 与 `apps/v1beta1`） | 转换的中间态。所有版本都能转成内部版，就不用写 N×N 个转换函数 |
| **`validation/` 与 OpenAPI schema 并存** | OpenAPI 只能表达单字段约束；"A 字段只在 B 为某值时合法"这类规则必须写 Go |

> 💡 `fuzzer/` 是这套结构里最容易被忽略的一环：**转换的正确性不能靠读代码**，要靠"随机造一个对象、转过去再转回来、断言完全相等"的 roundtrip 测试。

## ② 生成：一次生成一整套，缺一个都别上线

| 产物 | 用来做什么 | 漏生成的后果 |
|---|---|---|
| `deepcopy` | 控制器缓存拷贝对象 | 深层结构被共享，改一处全家脏 |
| `defaulter` | 服务端默认值 | 同一份 YAML 在不同版本下得到不同对象 |
| `conversion` | 多版本互转 | 老版本对象读不出来 |
| `openapi` | `kubectl explain`、API 文档 | 用户不知道字段怎么填 |
| `clientset` / `informers` / `listers` | 类型化 client + 本地缓存 + 只读视图 | 手写 client，字段一改就漏 |
| `applyconfigurations` | server-side apply 的 patch 体 | 只能用非结构化 map 打补丁 |

入口只有一个（`scripts/make-rules/generate-k8s.mk`）：

```make
generated.files: tools.verify.code-generator gen_prerelease_lifecycle gen_deepcopy \
                 gen_defaulter gen_conversion gen_openapi gen_client
```

| 纪律 | 原因 |
|---|---|
| **一次生成全部** | 分开跑会出现"client 新、deepcopy 旧"的半新状态，比不生成更难查 |
| **锁生成器版本** | 版本不同产物会漂移，PR diff 全是噪音 |
| **生成物入库** | API 变更的影响面在 PR 里可见；也告别"本地生成、CI 不生成"的漂移 |

CI 里判断“生成物是否最新”，一条命令就够：

```bash
make generated.files && git diff --exit-code && echo "生成物是最新的"
```

## ③ 准入：整条链上唯一能“拒绝”的一环

```go
// 改：补默认值、派生字段
func (p *Plugin) Admit(ctx context.Context, attributes admission.Attributes, o admission.ObjectInterfaces) error {
	if shouldIgnore(attributes) {   // 只管主资源，子资源放过
		return nil
	}
	if !p.WaitForReady() {          // 缓存没同步完就拒绝（fail-closed）
		return admission.NewForbidden(attributes, fmt.Errorf("not yet ready"))
	}
	ms := attributes.GetObject().(*apps.MinerSet)
	ms.Spec.Template.Spec.DisplayName = fmt.Sprintf("miner-for-%s-minerset", ms.Name)
	addMinerSetSelector(ms)
	return nil
}

// 拦：删除保护必须先把对象取出来（DELETE 没有对象体）
func (p *Plugin) Validate(ctx context.Context, attributes admission.Attributes, _ admission.ObjectInterfaces) error {
	if attributes.GetOperation() == admission.Delete {
		ms, err := p.lister.MinerSets(attributes.GetNamespace()).Get(attributes.GetName())
		if err != nil {
			if apierrors.IsNotFound(err) {
				return nil
			}
			return apierrors.NewInternalError(err)
		}
		if ms.GetAnnotations()[apps.AnnotationDeletionProtection] == "true" {
			return admission.NewForbidden(attributes, fmt.Errorf("deletion protection is on"))
		}
	}
	return nil
}
```

| 要点 | 说明 |
|---|---|
| Mutation 与 Validation 分开实现 | 你自己改出来的字段不该再被自己校验；框架允许一个插件实现两个接口 |
| 删除类拦截必须 `Get` | DELETE 请求没有对象体，所有“看内容再决定”的逻辑都得先查 |
| `WaitForReady()` 挡在最前 | 缓存没同步完就放行，等于用空数据做安全判断（fail-open） |
| 依赖用 `Wants*` 注入 | `WantsExternalInformerFactory` / `WantsExternalClientSet`，与巡检插件同款（见 [56.4 告警治理](../../L5-工程效能/56-稳定性工程/56.4-告警治理.md)） |

> 🔑 准入门与控制器门的分工是硬的：**准入只能“当场拒绝”或“当场改字段”，不能“稍后处理”**。要建 Pod、调云 API、等外部资源的，只能放控制器。

## ④ 注册：Strategy / Store / REST 三层

这一环的完整实现在 [7.10 Operator 与 CRD](7.10-Operator与CRD.md) 里讲过，这里只记住它的**验收点**：

```bash
kubectl api-resources | grep minersets                      # 资源在
kubectl get --raw /apis/apps.onex.io/v1beta1 | jq '.resources[].name'
# 期望能看到 minersets 与 minersets/status（子资源必须单独注册）
```

`storage["minersets"] = ...` 与 `storage["minersets/status"] = ...` 是两次注册（见 [7.10 Operator 与 CRD](7.10-Operator与CRD.md)）——**少注册 `/status`，控制器就只能整对象 `Update`，与用户抢 spec**。

## ⑤ 控制器：level-triggered 收敛

这一环的通用规则在 [7.1 声明式 API 与控制器模式](7.1-声明式API与控制器模式.md) 里；放到这条链上看，它只负责一件事：**让 status 追平 spec**。

| 检查点 | 判据 |
|---|---|
| 是否从缓存读最新对象 | 事件处理器只入队 key，worker 从 informer 缓存重读（不是用事件里的快照） |
| 是否只写 status | 控制器 `Update` 整对象 = 与用户抢字段；应走 `UpdateStatus` / 子资源 |
| 是否收敛可见 | `kubectl get <res> -o jsonpath='{.metadata.generation} {.status.observedGeneration}'` 两个数相等才算处理完 |
| 失败是否可重试 | 返回 error 走 workqueue 指数退避；不要 `sleep` 在调谐里 |

onex 的控制器框架用的是 `sigs.k8s.io/controller-runtime`（`internal/controller/alias.go` 里把 `ctrl` 与 `cluster`、`controller` 等重新导出），好处是不必自己拼 informer + workqueue。

## ⑥ 对账：承认“双写”就一定会残留

只要你的服务在 K8s 之外还写了一份（DB 表、计费账本、配额计数），删除就必然有只成功一半的时刻：

```text
kubectl delete minerset ms-1
  ├─ K8s：MinerSet 与 Miner 级联删除 ✅
  └─ MySQL：minersets 那一行还在 ❌
```

兜底的是常驻对账（onex 的 `internal/controller/resourceclean/`，[源码](https://github.com/shgopher/onex)）：

```go
type Cleaner interface {
	Name() string
	Delete(ctx context.Context) error                       // 清一个资源在“另一个存储”里的残留
	Initialize(client client.Client, storeClient store.IStore)
}

// 每小时跑一遍全部 cleaner
func (r *CleanReconciler) Start(ctx context.Context) error {
	ticker := time.NewTicker(1 * time.Hour)
	defer ticker.Stop()
	for {
		select {
		case <-ctx.Done():
			return nil
		case <-ticker.C:
			r.SyncAll(ctx)
		}
	}
}
```

| 设计 | 为什么 |
|---|---|
| 每资源一个 cleaner | 判断逻辑独立可测，坏一个不牵连其他 |
| 周期而非事件驱动 | 它兜的是“事件已经丢了”的场景，事件驱动没有意义 |
| 同时拿 K8s client 与 store | 清理必然跨两个存储：先查 K8s 侧还在不在，再删 DB 侧 |

## 同一条链，两条路线

| 环 | CRD 路线 | Aggregated apiserver 路线（onex） |
|---|---|---|
| ① types | CRD 的 OpenAPI schema（YAML） | Go types + `register.go` |
| ② 生成 | `controller-gen` 生成 CRD YAML 与 deepcopy | `code-generator` 生成 client/informers/listers/applyconfigurations |
| ③ 准入 | **validating / mutating webhook**（独立服务，有网络调用） | **内置 admission 插件**（进程内，微秒级） |
| ④ 注册 | apiserver 自动服务该 CRD | 自己写 `APIGroupInfo` 注册进聚合层 |
| ⑤ 控制器 | 完全相同 | 完全相同 |
| ⑥ 对账 | 完全相同 | 完全相同 |
| 版本转换 | conversion webhook | 进程内 `conversion`（且可被 fuzz roundtrip 测） |

> 🔑 两条路线的差别集中在 **②③④**：CRD 把“schema 与转换”外包给 webhook，aggregated apiserver 把“类型与校验”留在自己的 Go 代码里。⑤⑥ 与路线无关——**所以“先写好控制器”不等于“整条链就通了”**。

## 验收清单：每环一条命令

| # | 环 | 命令 | 期望 |
|---|---|---|---|
| ① | types | `grep -rn "k8s:deepcopy-gen" pkg/apis \| wc -l` | > 0（类型上有生成标记） |
| ② | 生成 | `make generated.files && git diff --exit-code` | 干净（生成物最新） |
| ③ | 准入 | `kubectl apply` 一份最小 YAML 后 `kubectl get -o yaml` | 默认字段已被填上；带删除保护的资源 `kubectl delete` 被拒 |
| ④ | 注册 | `kubectl get --raw /apis/<group>/<ver>` | 资源列表里有 `<res>/status` |
| ⑤ | 控制器 | `kubectl get <res> -o jsonpath='{.metadata.generation} {.status.observedGeneration}'` | 两个数相等 |
| ⑥ | 对账 | 对数：`kubectl get <res> --no-headers \| wc -l` vs `SELECT COUNT(*)` | 一致（抽查即可，长期靠对账任务） |

> ⚠️ 这六条里最容易长期跳过的是 ② 与 ⑥：两者都“不跑也没报错”，直到某天 API 换了版本、或报表突然对不上，才发现生成物早就过期、幽灵记录已经堆了几万行。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只手写 controller，不生成 client | 字段一改，漏改的地方在运行期才炸 |
| 生成物不入库、CI 也不校验 | 每个人的本地产物不同，没人知道哪份是“对”的 |
| 控制器 `Update` 整对象 | 与用户抢 spec；`unexpected field` 与随机回滚 |
| 只注册主资源，不注册 `/status` | 冲突只能靠“谁先写”解决 |
| 用准入做异步动作（建 Pod、调云 API） | 请求被阻塞几十秒，超时后状态未知 |
| 删除保护写在控制器里 | 对象已经被删了才执行到控制器，拦不住 |
| 双写却不做对账 | 幽灵记录永远在，且随时间线性增长 |
| 只跑 fuzz 不做断言（或干脆不跑） | 转换丢字段，只在老版本对象上出现 |

## 三条铁律

> 🔑 **六环是链不是清单**：任何一环缺失，症状都叫“数据不一致”，所以排障要按链走一遍，而不是先怀疑控制器。

> 🔑 **改 types 之后必须重跑生成**；判断“跑过没”只有一条命令：`git diff --exit-code`。

> 🔑 **准入管“这次请求合不合规”，控制器管“现实有没有收敛”，对账管“另一个存储有没有残留”**——三者的职责不能互换。

## 自检

**Q1** 有人报“我改了 `minersets` 的 spec，控制器没反应”。按六环的顺序，你会怎么定位？

▸ 答案：不要把“没反应”直接归给控制器。① **types/生成**：字段有没有加进类型、生成物是否最新（`make generated.files && git diff --exit-code`）；② **准入**：是不是被 mutating 插件改写或拦掉了（看 apiserver 审计日志里的请求体与最终落盘对象）；③ **注册**：`kubectl get --raw /apis/<group>/<ver>` 里资源与子资源是否都在；④ **控制器**：`generation` 与 `observedGeneration` 是否相等——不等是控制器没跟上，相等但状态没变，才是控制器逻辑错。判据是“两个数相等”，不是“日志没报错”。

**Q2** 为什么 `Validate` 里的删除保护必须先用 lister `Get` 一次，而不能像 `Admit` 那样直接从 `attributes.GetObject()` 拿对象？

▸ 答案：因为 **DELETE 请求没有对象体**。`Admit` 处理的是 create/update，`attributes.GetObject()` 拿得到完整对象；而 delete 只带名字与命名空间，想判断“这个对象上有没有 `deletion-protection` 注解”，只能去 informer 缓存里 `Get` 出来。顺带一个坑：`Get` 返回 `NotFound` 时要**放行**（对象已经没了，删除本就该成功），而不是报错——否则会造出删不掉的对象。

**Q3** 团队把生成物从仓库里移除了，改成 CI 里生成。三个月后出现“同一个 YAML 在 A 环境正常、B 环境报字段不存在”。最可能是哪一环断了？

▸ 答案：**② 生成环的版本不一致**。生成器（code-generator / controller-gen）版本不同，产物就不同：A 环境的 CI 用旧版本生成了不含新字段的 client，B 环境用新版本。这类问题在“生成物入库”的仓库里会表现为可见的 diff，在“CI 现场生成”的仓库里则完全隐形。修法两条：锁生成器版本（`tools.verify.code-generator`）+ 把“生成物是否最新”做成 CI 门禁。

**Q4** 一个资源已经加了 `ownerReferences`，为什么还需要 ⑥ 对账清理？

▸ 答案：`ownerReferences` 只保证 **K8s 对象之间**的级联删除，管不到你的数据库。一旦服务在 DB 里也存了一份（列表缓存、计费、配额），删除就必然有“K8s 已删、DB 未删”的窗口；而且这个窗口不是异常，是**双写的常态**。所以对账不是补丁，是双写方案的一部分——判据是“是否存在第二个存储”，而不是“是否出现过 bug”。

**Q5** 只把控制器写得非常健壮，能不能弥补 ③ 准入缺失？

▸ 答案：不能。两者的时间点与职责都不同：准入发生在**写入 etcd 之前**，能拒绝请求；控制器发生在**对象已经落盘之后**，只能事后纠正——而“事后纠正”意味着脏数据已经被人读到、被下游消费。典型例子：没有准入时用户可以随手改 `status`，控制器要么覆盖用户改动（打架），要么放弃收敛（更糟）。控制器能保证“最终一致”，保证不了“从未写过错的”。
