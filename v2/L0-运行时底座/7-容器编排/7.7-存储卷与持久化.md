# 7.7 存储卷与持久化

## 一句话

> K8s 的存储只有两种语义——**Pod 内临时**（emptyDir，Pod 删就没）与**跨 Pod 持久**（PVC，独立生命周期）；PVC 的关键不是 “能挂上”，而是 “绑定到哪个 PV、能不能扩容、Pod 漂移时多久能挂回来”。

## 五种卷，先分清生命周期

| 类型 | 生命周期 | 数据在哪 | 用途 |
|---|---|---|---|
| `emptyDir` | Pod | 节点磁盘（或内存） | 同 Pod 共享、缓存、临时落盘 |
| `hostPath` | 节点 | 节点目录 | 读节点信息；**业务数据禁用** |
| `configMap` / `secret` | 对象 | apiserver / etcd | 配置注入（见 [7.4 配置与密钥 (ConfigMap / Secret)](7.4-配置与密钥.md)） |
| **PVC** | 独立 | 云盘 / NFS / 分布式存储 | 数据库、消息队列、上传文件 |
| `projected` | Pod | 组合多个来源 | 把 SA token + config 合成一个目录 |

## PV / PVC / StorageClass：三者的账

```
Pod ──挂载──► PVC（我要 100Gi、RWO）
                 │  绑定
                 ▼
              PV（一块真实的云盘/目录）
                 ▲  由谁创建
        StorageClass（动态供给：参数化创建 PV）
```

| 概念 | 是 “谁” 的抽象 | 谁创建 |
|---|---|---|
| **PVC** | 使用者的**需求声明** | 开发者（或 StatefulSet 模板） |
| **PV** | 集群里的**一块存储** | 管理员手工，或 StorageClass 动态创建 |
| **StorageClass** | 存储的**模板与参数**（类型、IOPS、回收策略） | 管理员 |

两个高频开关：

| 设置 | 作用 | 坑 |
|---|---|---|
| `volumeBindingMode: WaitForFirstConsumer` | Pod 调度后再创建/绑定卷，保证卷与 Pod 同 AZ | 没有 Pod 就一直 `Pending`，看起来像 “卷坏了” |
| `reclaimPolicy: Delete` / `Retain` | 删 PVC 后是否删底层存储 | Delete 是默认，**误删 PVC = 云盘被删**；数据库务必用 Retain |

### “绑定” 到底做了什么

PersistentVolumeController 是个控制循环：不断检查每个 PVC 是否 `Bound`，没绑就遍历可用 PV 尝试撮合。**撮合成功只是把 PV 对象名填进 PVC 的 `spec.volumeName`** ——这是控制器补的字段，你手写的 YAML 里看不到它。

| 疑点 | 真相 |
|---|---|
| 我的 PVC YAML 里没有 `volumeName` | 它是绑定结果，不是输入 |
| 没写 `storageClassName` 会怎样 | 取决于 `DefaultStorageClass` 这个**准入插件**：开启则自动补默认 SC；未开启则为**空字符串 `""`**，且只能与同样为 `""` 的 PV 绑定 |
| StorageClass 只服务于动态供给吗 | 不是。PV 与 PVC 都写 `storageClassName: manual`，而集群里根本不存在名为 `manual` 的 SC 对象，静态绑定照样成立 |

> ⚠️ “同一份 PVC YAML，在 A 集群能跑、在 B 集群一直 Pending” 的第一嫌疑就是 `DefaultStorageClass` 插件开没开。

### `WaitForFirstConsumer` 不是优化，是必需

假设绑定发生在调度之前：Volume 控制循环看到 `pv-1` 属性匹配，把 `pvc-1` 绑给了它——可 `pv-1` 在 node-1，而 Pod 因亲和性只能跑 node-2。此时调度器按 “要考虑 Volume 分布” 只能把 Pod 往 node-1 送，**调度必然失败**。

`WaitForFirstConsumer` 就是告诉控制循环：**看到可绑定也先别写 `volumeName`**，等第一个 Pod 进调度器后再统一决定。调度器自己维护一个绑定控制循环，PVC 未绑定时不阻塞等待，而是把 Pod 放回待调度队列下轮再试。

## 两阶段处理：Attach 归 master，Mount 归 kubelet

Pod 调度到节点后，kubelet 要在宿主机上把卷准备好。这一步被拆成两个阶段，而且**分属两个不同组件**：

| 阶段 | 做什么 | 谁做 | 接口参数 |
|---|---|---|---|
| **Attach** | 把远程磁盘挂到这台虚拟机（等价 `gcloud compute instances attach-disk`） | kube-controller-manager 的 `AttachDetachController`（在 **master** 上） | 只给 `nodeName` |
| **Mount** | `lsblk` 取设备 → `mkfs.ext4` 格式化 → 挂到卷目录 | kubelet 的 `VolumeManagerReconciler`（在**节点**上） | 只给 `dir` |

两个设计要点：

- **Attach 不要求在宿主机上执行**，它只是调云厂商 API，所以放在 master 的 controller-manager 里；Mount 必须在节点上做，归 kubelet。
- Mount 跑在**独立于 kubelet 主循环的 Goroutine** 里，目的就是不让耗时的远程挂载阻塞主控制循环（主循环一堵，整台节点停摆，见 [6.5 容器运行时](../6-容器技术/6.5-容器运行时.md)）。

NFS 这类文件存储没有 “设备” 概念，**直接跳过 Attach，从 Mount 开始**。

卷在宿主机上的落点是有约定的，排障可以直接去第一现场：

```
/var/lib/kubelet/pods/<Pod ID>/volumes/kubernetes.io~<Volume类型>/<Volume名字>
# 例：.../volumes/kubernetes.io~nfs/data-web-0
# FlexVolume 类型会变成 k8s~nfs
```

> 🔑 所谓 “持久化卷”，最终就是宿主机上的一个目录，再通过 CRI 的 `Mounts` 参数交给运行时的 `-v` 挂载。目录空了 = 挂载没成功，别往应用层查。

## 存储插件：CSI 的三段调用链

CSI 把 “谁在什么位置调谁” 定死了，排 CSI 故障时按这条链定位：

| 段 | 触发者 | 调到哪 | 在哪执行 |
|---|---|---|---|
| 动态创建 | External Provisioner（sidecar，Watch PVC） | CSI 插件的 **Controller** 服务 `CreateVolume` | master 侧逻辑 |
| Attach | `AttachDetachController` 创建一个 `VolumeAttachment` 对象 → External Attacher 看到 | CSI 的 `ControllerPublishVolume` | master 侧逻辑 |
| Mount | `VolumeManagerReconciler` 经 `pkg/volume/csi` **直接调** | CSI 的 `NodePublishVolume` | 节点上 |

关键差别：**Mount 不经过任何 External Component**——kubelet 自己就是调用方。所以 “卷创建了、attached 了，但容器里看不到数据”，问题在 Node 段，不在 provisioner。

CSI 插件是单个二进制，用 gRPC 暴露三个服务：`Identity`（版本与能力探测）、`Controller`（创/删/扩/挂载声明）、`Node`（节点侧挂载）。注意 CSI 自己的 Volume 概念 ≠ K8s 的 PV。

### 顺便记住 FlexVolume 的契约（老集群还会遇到）

| 项 | 规则 |
|---|---|
| 驱动名 | `driver: k8s/nfs` 会被解析成目录 `k8s~nfs` |
| 插件路径 | 每个节点 `/usr/libexec/kubernetes/kubelet-plugins/volume/exec/k8s~nfs/nfs` |
| 调用形式 | `nfs mount <mount dir> <json params>`，子命令固定为 `init` / `mount` / `unmount` / `attach` / `detach` |
| 成功判据 | 脚本必须向 stdout 打印 `{"status":"Success"}`，这是 kubelet 判断成功的唯一依据 |
| 致命缺陷 | 每次调用都是独立进程，插件**无法在 mount 与 unmount 之间保留状态**，只能写宿主机临时文件；也不支持动态供给 |

> ⚠️ 自己写 FlexVolume 插件时返回格式错，表现是 “挂载静默失败”——日志里看不到报错，只有卷目录是空的。

## Local PV：一个 PV 必须独占一块盘

本地盘性能好、成本低，但有一条铁律：**绝不要把宿主机的一个目录当 PV 用**。

| 理由 | 后果 |
|---|---|
| 本地目录写入行为不可控 | 一个 Pod 写满磁盘，整台宿主机一起挂 |
| 不同目录之间没有 I/O 隔离 | 相邻业务互相打爆 IOPS |
| 数据在节点上 | 节点永久宕机，数据可能直接丢，必须自带备份 |

正确的 Local PV 长这样：

```yaml
apiVersion: v1
kind: PersistentVolume
metadata: {name: pv-local-1}
spec:
  capacity: {storage: 500Gi}
  accessModes: [ReadWriteOnce]
  storageClassName: local-storage
  local: {path: /mnt/disks/ssd1}        # 必须是一块独立磁盘/块设备
  nodeAffinity:                          # 调度器据此知道这块盘在哪
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - {key: kubernetes.io/hostname, operator: In, values: [node-1]}
  persistentVolumeReclaimPolicy: Retain
---
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: {name: local-storage}
provisioner: kubernetes.io/no-provisioner
volumeBindingMode: WaitForFirstConsumer   # 必须
```

手工创建的 Local PV 删除有硬顺序，错一步就卡在 `Terminating`：

1. 删使用它的 Pod；
2. 从宿主机 `umount` 本地磁盘；
3. 删 PVC；
4. 删 PV。

嫌手工建 PV 麻烦，用 **Static Provisioner**（以 DaemonSet 部署）：它检查每台宿主机 `/mnt/disks` 下的每个挂载点并自动调 API 建 PV，删除方向也由它负责。

## StatefulSet 的存储身份

| 机制 | 效果 |
|---|---|
| `volumeClaimTemplates` | 为每个序号生成**固定名字**的 PVC：`data-web-0`、`data-web-1` |
| 缩容 | 只缩 Pod，**PVC 保留**（默认不删） |
| 扩容 | 新序号自动创建新 PVC 并绑定 |
| 重建 | `web-0` 重建后挂回 `data-web-0`，数据接上 |

> ⚠️ 删 StatefulSet **不会**删 PVC，这是保护数据的设计，也常导致 “以为清理干净了，磁盘还在计费”。清理要显式删 PVC。

## 扩容、快照与备份

| 能力 | 前提 | 边界 |
|---|---|---|
| 在线扩容 | StorageClass `allowVolumeExpansion: true` + 驱动支持 | 只能增不能减；文件系统扩容可能要求重启 Pod |
| 快照 | `VolumeSnapshot` CRD + CSI 驱动支持 | 快照 ≠ 备份：同账号同区域，误删会连快照一起没 |
| 跨区恢复 | 快照复制到另一区域 | 有延迟与流量费，RPO 取决于复制频率 |

备份要按 “独立副本” 设计：跨账号/跨区/离线，并**做过恢复演练**，方法与 RPO/RTO 的关系见 [10.4 快照与备份](../10-存储基础设施/10.4-快照与备份.md)。

## 挂载失败的四类原因

| 现象 | 原因 | 查法 |
|---|---|---|
| PVC 一直 `Pending` | 无匹配 PV / StorageClass 不存在 / 等待首个消费者 | `kubectl describe pvc` 看事件 |
| Pod `ContainerCreating` 很久 | attach/detach 中（跨节点漂移 30 秒–2 分钟） | `kubectl describe pod` 看 `AttachVolume` 事件 |
| `Multi-Attach error` | RWO 卷还挂在旧节点 | 确认旧 Pod 已终止；必要时等节点侧摘除 |
| 权限错误（Permission denied） | 卷的 fsGroup/UID 与容器用户不匹配 | 设 `securityContext.fsGroup` 或用 initContainer 修权限 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 数据库数据目录不挂 PVC | 重建即丢数据（机制见 [6.7 容器存储与网络](../6-容器技术/6.7-容器存储与网络.md)） |
| 用 hostPath 存业务数据 | Pod 漂移后数据留在旧节点 |
| `reclaimPolicy: Delete` 用于生产数据库 | 误删 PVC 直接删盘，无法恢复 |
| 用 RWO 卷给多副本共享写 | 文件损坏（RWO 是单节点，不是单 Pod） |
| 把快照当备份 | 同区域同账号，账号被封/误删时一起消失 |
| StatefulSet 缩容后忘了清理 PVC | 存储持续计费，且再扩容时挂到旧数据 |
| 忽略 `WaitForFirstConsumer` | 误判 “卷创建失败”，实际在等 Pod |
| 把宿主机目录当 Local PV | 没有 I/O 隔离，一个 Pod 写满盘带死整个节点 |
| 手工删 Local PV 时顺序颠倒 | PV 卡在 `Terminating`，只能改 finalizer 强删 |
| 自己写 FlexVolume 插件却返回非 JSON | 挂载静默失败，卷目录为空但无报错 |

## 三条铁律

> 🔑 **数据要活过 Pod 就挂 PVC**；容器可写层永远只放临时数据。

> 🔑 **生产数据库用 `Retain`**；`Delete` 让一次误删变成不可恢复事故。

> 🔑 **快照 ≠ 备份**；备份必须是独立副本，并且恢复演练过。

## 自检

**Q1** 一个 StatefulSet 有 3 个副本，缩到 1 再扩回 3，数据还在吗？

▸ 答案：**在**。缩容只删 Pod，`data-web-1`、`data-web-2` 两个 PVC 保留；扩回 3 时新 Pod 按序号复用同名 PVC，数据接上。但这意味着 “缩容不省钱”（存储仍计费），也意味着**缩容后重新扩容可能读到旧数据**——如果要 “干净重建”，得手工删 PVC。

**Q2** PVC 一直 Pending，你会按什么顺序查？

▸ 答案：① `kubectl describe pvc` 的事件（`no persistent volumes available` / `waiting for first consumer` / `storageclass not found`）；② StorageClass 是否存在且 `volumeBindingMode` 是 `WaitForFirstConsumer`（需要先有 Pod）；③ 云侧配额（云盘数量上限、容量配额）；④ 可用区是否匹配（Pod 被调度到没有该类存储的 AZ）。四步能覆盖 90% 的 Pending。

**Q3** 为什么 `reclaimPolicy: Delete` 在生产数据库上是危险默认？

▸ 答案：因为它把 “删 PVC” 与 “删底层云盘” 绑在一起。一次误操作（改错命名空间、清理脚本写错）就会让数据不可恢复，连快照也可能同账号一起没。生产数据库应显式设 `Retain`，让删除 PVC 后底层盘保留，人工确认后再清理——多一步人工，换回可恢复性。

**Q4** Pod 从节点 A 漂到节点 B，为什么恢复时间比 “启动进程” 长很多？

▸ 答案：因为要多一步 **attach/detach**：云盘先从 A 摘除、再挂到 B，典型 30 秒–2 分钟，叠加镜像拉取与启动。这就是 RTO 里最容易被漏掉的一段。优化：用 `nodeAffinity` 尽量回到原节点、选支持快速重挂的存储类型、把这段时长计入 RTO 目标。

**Q5** 快照和备份到底差在哪？给一个反例。

▸ 答案：快照是**同一份存储的时间点视图**，通常与源共享故障域（同区域、同账号）；备份是**独立副本**（跨账号/跨区/离线）。反例：某团队每天做快照，觉得万无一失；攻击者拿到账号权限后先删云盘再删快照，两条一起没。正确做法是快照解决 “误操作/回滚”，备份解决 “账号级/区域级灾难”，两者都要，且备份要演练恢复。

**Q6** 卷明明 `Bound` 了、`VolumeAttachment` 也是 attached，但容器里目录是空的。链路该往哪一段查？

▸ 答案：往 **Node 段**查，也就是 kubelet 的 Mount 阶段。CSI 的三段里，前两段（Provisioner 建卷、Attacher 做 `ControllerPublishVolume`）都成功了，而 Mount（`NodePublishVolume`）**不经过任何 External Component**，是 kubelet 经 `pkg/volume/csi` 直接调的——所以它出错不会有 sidecar 日志。第一现场是宿主机路径：`/var/lib/kubelet/pods/<Pod ID>/volumes/kubernetes.io~<类型>/<卷名>`，看目录是否存在、是否挂上；再查节点侧 CSI Node 服务的日志与文件系统挂载点。
