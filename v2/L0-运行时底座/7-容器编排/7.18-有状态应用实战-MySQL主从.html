                                    7.18 有状态应用实战：StatefulSet 跑 MySQL 主从

                                    一句话

                                    StatefulSet 只负责三件事——固定身份、启动顺序、每个 Pod 一块独立的盘；主从复制的“三座大山”（不同配置、传备份、初始化 SQL）得靠 Init Container + Sidecar 自己翻。这就是“有状态应用上 K8s”与“无状态 Deployment”的分水岭。

                                    来源：MySQL 主从案例、三座大山、人格分裂/阅后即焚/容器无序三条铁律来自张磊《深入剖析 Kubernetes》第 20 讲（极客时间，2018）。原文镜像是 MySQL 5.7 + XtraBackup 2.4，本文保留其结构，并在末尾标注现代替换点。

                                    目标拓扑

                                    要部署的是一个最简主从集群：

                                    • 1 个 Master，多个 Slave，Slave 可水平扩展；
                                    • 所有写只能走 Master，读可以走任意节点；
                                    • 每个节点有独立数据盘，Pod 重建后能接回原数据；
                                    • 节点有稳定名字：mysql-0、mysql-1、mysql-2。
                                                    写
   client ───────────────► mysql-0.mysql (Headless，固定到 Pod 0)
                读
   client ───────────────► mysql-read (普通 Service，负载到全部 Pod)
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
     mysql-0               mysql-1               mysql-2
     (Master)              (Slave)               (Slave)
     data-mysql-0          data-mysql-1          data-mysql-2

                                    两个 Service：把“读写分离”写成 DNS 约定

                                    Service 类型 作用 客户端怎么用
                                    mysql Headless（clusterIP: None） 给每个 Pod 一条稳定 DNS：mysql-0.mysql、mysql-1.mysql 写请求固定连 mysql-0.mysql
                                    mysql-read 普通 ClusterIP 把读请求负载到所有 Pod 读请求连 mysql-read

                                    关键点：StatefulSet 里所有 Pod 的标签都一样，Service 的 selector 无法区分主从。所以“写主库”不能靠 Service 的标签选择，只能靠 Headless + 固定序号 DNS。这也解释了为什么 MySQL 这种应用必须用 StatefulSet：它需要一个“名字不变、指代不变”的入口。

                                    apiVersion: v1
kind: Service
metadata: {name: mysql}
spec:
  clusterIP: None          # Headless：不分配 VIP，直接返回 Pod IP
  selector: {app: mysql}
  ports: [{name: mysql, port: 3306}]
---
apiVersion: v1
kind: Service
metadata: {name: mysql-read}
spec:
  selector: {app: mysql}
  ports: [{name: mysql, port: 3306}]

                                    三座大山：StatefulSet 不替你做的那部分

                                    # 难点 普通环境怎么做 K8s 里用什么
                                    1 Master 与 Slave 需要不同的 my.cnf 手工改配置文件 ConfigMap + Init Container 按序号选
                                    2 Slave 首次启动前要拿到 Master 的备份 XtraBackup 备份 + scp Init Container 从前一个 Pod 拉取
                                    3 Slave 启动前要执行 CHANGE MASTER TO 人工登录执行 SQL Sidecar 等 mysqld 起来后执行

                                    三座大山对应三种“容器设计模式”：配置选择用 Init，数据拷贝用 Init，常驻初始化与备份服务用 Sidecar（模式本身见 7.17 容器设计模式）。

                                    第一座山：ConfigMap 存两份配置

                                    apiVersion: v1
kind: ConfigMap
metadata: {name: mysql}
data:
  master.cnf: |
    [mysqld]
    log-bin                 # 开二进制日志，主从复制的前提
  slave.cnf: |
    [mysqld]
    super-read-only         # 从库对用户只读，但允许复制线程写入

                                    log-bin 让 Master 记录所有写操作；super-read-only 让 Slave 拒绝普通用户的写，但复制线程仍有权限——这是 MySQL 主从的标准配置，不是 K8s 特有的。

                                    StatefulSet 骨架：身份、顺序、盘

                                    apiVersion: apps/v1
kind: StatefulSet
metadata: {name: mysql}
spec:
  serviceName: mysql            # 必须指向 Headless Service
  replicas: 3
  selector: {matchLabels: {app: mysql}}
  template:
    metadata: {labels: {app: mysql}}
    spec:
      # initContainers / containers 见下
  volumeClaimTemplates:
    - metadata: {name: data}
      spec:
        accessModes: [ReadWriteOnce]
        resources: {requests: {storage: 10Gi}}

                                    两个字段决定它是不是“有状态”：

                                    • serviceName: mysql：把 Pod 序号映射成 DNS 记录 mysql-<ordinal>.mysql。没有它，Pod 名字稳定但 DNS 不稳定。
                                    • volumeClaimTemplates：为每个 Pod 生成固定名字的 PVC，命名规则是 <模板名>-<StatefulSet 名>-<序号>，即 data-mysql-0、data-mysql-1。Pod 删了 PVC 不删，重建时同名 PVC 接回原盘——这是“数据还在”的全部机制。

                                    第二座山（上）：init-mysql 按序号分角色

                                    同一个 Pod 模板要同时扮演 Master 和 Slave，第一步是从主机名里读出序号，再决定用哪份配置。

                                    initContainers:
  - name: init-mysql
    image: mysql:5.7
    command:
      - bash
      - -c
      - |
        set -ex
        # 从 hostname 末尾取序号：mysql-0 → 0
        [[ `hostname` =~ -([0-9]+)$ ]] || exit 1
        ordinal=${BASH_REMATCH[1]}
        # server-id 不能为 0（0 有特殊含义），统一加 100
        echo [mysqld] > /mnt/conf.d/server-id.cnf
        echo server-id=$((100 + $ordinal)) >> /mnt/conf.d/server-id.cnf
        # 序号 0 是 Master，其余是 Slave
        if [[ $ordinal -eq 0 ]]; then
          cp /mnt/config-map/master.cnf /mnt/conf.d/
        else
          cp /mnt/config-map/slave.cnf /mnt/conf.d/
        fi
    volumeMounts:
      - {name: conf, mountPath: /mnt/conf.d}
      - {name: config-map, mountPath: /mnt/config-map}

                                    conf 是一个 emptyDir，config-map 是 ConfigMap 卷。Init Container 把选好的配置写进 emptyDir 后退出，后面的 MySQL 容器直接挂 conf 就能读到——这与 WAR + Tomcat 的套路完全一样。

                                    🔑 server-id 必须全局唯一。用序号推导是最省事的做法，但要注意 server-id=0 在 MySQL 里有特殊含义，所以加一个偏移量。

                                    第二座山（下）：clone-mysql 从前一个节点拷数据

                                    Slave 第一次启动前，要先有一份 Master（或前一个 Slave）的数据。这里用 ncat 从上一个 Pod 的 3307 端口拉 XtraBackup 流：

                                      - name: clone-mysql
    image: registry.example.com/xtrabackup:2.4
    command:
      - bash
      - -c
      - |
        set -ex
        # 幂等：数据目录已存在就跳过（重启不会重复拷）
        [[ -d /var/lib/mysql/mysql ]] && exit 0
        # Master 不需要拷数据
        [[ `hostname` =~ -([0-9]+)$ ]] || exit 1
        ordinal=${BASH_REMATCH[1]}
        [[ $ordinal -eq 0 ]] && exit 0
        # 从上一個 Pod 的 3307 拉流，解到数据目录
        ncat --recv-only mysql-$(($ordinal-1)).mysql 3307 | xbstream -x -C /var/lib/mysql
        # 让拷贝来的数据进入一致性状态，否则不能直接启动
        xtrabackup --prepare --target-dir=/var/lib/mysql
    volumeMounts:
      - {name: data, mountPath: /var/lib/mysql, subPath: mysql}
      - {name: conf, mountPath: /etc/mysql/conf.d}

                                    两个细节：

                                    • [[ -d /var/lib/mysql/mysql ]] && exit 0 是幂等开关。Pod 重启会再跑一次 Init Container，没有这行就会把已有数据覆盖掉。
                                    • xtrabackup --prepare 不能省。拷贝来的文件是“热备”状态，必须回放日志到一致点，MySQL 才能用它启动。

                                    第三座山：Sidecar 等 MySQL 起来，再执行 CHANGE MASTER

                                    Pod 里的容器没有顺序，所以这个 Sidecar 不能假设 MySQL 已启动。它的第一件事是自旋等 SELECT 1 成功，第二件事是拼出并执行复制初始化 SQL，第三件事是常驻 3307 为下一个 Slave 提供备份流。

                                    containers:
  - name: xtrabackup
    image: registry.example.com/xtrabackup:2.4
    ports: [{name: xtrabackup, containerPort: 3307}]
    command:
      - bash
      - -c
      - |
        set -ex
        cd /var/lib/mysql
        # 备份来自 Slave：文件里已经带 CHANGE MASTER 语句
        if [[ -f xtrabackup_slave_info ]]; then
          mv xtrabackup_slave_info change_master_to.sql.in
          rm -f xtrabackup_binlog_info
        # 备份来自 Master：解析 binlog 文件名与位点，拼 SQL
        elif [[ -f xtrabackup_binlog_info ]]; then
          [[ `cat xtrabackup_binlog_info` =~ ^(.*?)[[:space:]]+(.*?)$ ]] || exit 1
          rm xtrabackup_binlog_info
          echo "CHANGE MASTER TO MASTER_LOG_FILE='${BASH_REMATCH[1]}', MASTER_LOG_POS=${BASH_REMATCH[2]}" > change_master_to.sql.in
        fi
        # 有初始化文件才执行，且必须等 mysqld 可连接
        if [[ -f change_master_to.sql.in ]]; then
          until mysql -h 127.0.0.1 -e "SELECT 1"; do sleep 1; done
          mv change_master_to.sql.in change_master_to.sql.orig   # 阅后即焚：防重启重放
          mysql -h 127.0.0.1 <<EOF
        $(<change_master_to.sql.orig),
          MASTER_HOST='mysql-0.mysql',
          MASTER_USER='root',
          MASTER_PASSWORD='',
          MASTER_CONNECT_RETRY=10;
        START SLAVE;
        EOF
        fi
        # 常驻：给下一个 Slave 提供备份流
        exec ncat --listen --keep-open --send-only --max-conns=1 3307 -c \
          "xtrabackup --backup --slave-info --stream=xbstream --host=127.0.0.1 --user=root"
    volumeMounts:
      - {name: data, mountPath: /var/lib/mysql, subPath: mysql}
      - {name: conf, mountPath: /etc/mysql/conf.d}

                                    三个“阅后即焚”的动作缺一不可：删 xtrabackup_binlog_info、把 change_master_to.sql.in 改名成 .orig、执行完不再保留触发文件。否则容器重启时会认为“还需要初始化”，重复执行 CHANGE MASTER。

                                    主容器与探针

                                      - name: mysql
    image: mysql:5.7
    env:
      - {name: MYSQL_ALLOW_EMPTY_PASSWORD, value: "1"}
    ports: [{name: mysql, containerPort: 3306}]
    volumeMounts:
      - {name: data, mountPath: /var/lib/mysql, subPath: mysql}
      - {name: conf, mountPath: /etc/mysql/conf.d}
    resources:
      requests: {cpu: 500m, memory: 1Gi}
    livenessProbe:
      exec: {command: ["mysqladmin", "ping"]}
      initialDelaySeconds: 30
      periodSeconds: 10
    readinessProbe:
      exec: {command: ["mysql", "-h", "127.0.0.1", "-e", "SELECT 1"]}
      initialDelaySeconds: 5
      periodSeconds: 2

                                    liveness 用 mysqladmin ping 判断进程是否还活着；readiness 用 SELECT 1 判断能否接受查询。readiness 失败的 Pod 会从 Service 摘除，但不会被重启——这正是“活着”和“能服务”的区别（探针细节见 7.6 自愈、滚动更新与回滚）。

kubectl run mysql-client --image=mysql:5.7 -i --rm --restart=Never -- \

                                    现代替换：MySQL 8 + mysqldump 的可运行版

                                    上面的代码保留课程原版（MySQL 5.7 + XtraBackup），便于对照原理。实际要跑时，2018 年的镜像与工具已经过时；本机在 kind v1.31.0 上用 MySQL 8.0.46 + mysqldump 跑通了一版，完整 YAML 与输出见 tools/examples/7.18-mysql-sts。

                                    三处必须改：

                                    原版 现代版 原因
                                    mysql:5.7 + xtrabackup:2.4 mysql:8.0 + mysqldump 5.7 已 EOL；mysqldump 在镜像里就有，不用额外拉备份镜像
                                    xtrabackup --slave-info 记录主库位点 每个 Slave 都从 Master dump mysqldump 记录的是被 dump 节点的 binlog 位点；从 Slave dump 却让新节点指向 Master，I/O 线程会失败
                                    脚本里的 `hostname` $HOSTNAME mysql:8.0 镜像没有 hostname 二进制，会直接 command not found

                                    核心改动只有两段：

                                    # Init：从 Master 取一份一致性快照，并确认 dump 里带 binlog 位点
mysqldump -h mysql-0.mysql -uroot \
  --single-transaction --source-data=2 --set-gtid-purged=OFF \
  --databases test > /seed/dump.sql
grep -q 'CHANGE MASTER TO' /seed/dump.sql   # 8.0.46 仍输出 CHANGE MASTER TO

                                    # Sidecar：导入后把 dump 里的位点补上 host/user/password，再 START REPLICA
LINE=$(grep -m1 '^-- CHANGE MASTER TO ' /seed/dump.sql | sed 's/^-- //')
STMT=$(printf '%s' "$LINE" | sed "s/CHANGE MASTER TO /CHANGE MASTER TO MASTER_HOST='mysql-0.mysql', MASTER_USER='repl', MASTER_PASSWORD='replpass', /")
{ echo "SET GLOBAL super_read_only=OFF;"; echo "$STMT"; echo "START REPLICA;"; echo "SET GLOBAL super_read_only=ON;"; } | mysql -h127.0.0.1 -uroot

                                    验证结果（真实输出）：

                                    $ kubectl -n mysql-verify exec mysql-1 -c mysql -- mysql -uroot -e "SHOW REPLICA STATUS\G" | grep -E 'Source_Host|Replica_(IO|SQL)_Running'
                  Source_Host: mysql-0.mysql
           Replica_IO_Running: Yes
          Replica_SQL_Running: Yes

$ # 在 mysql-0 写入后，mysql-1 / mysql-2 都能读到
# 1  hello
# 2  verified

                                    ⚠️ 两个实测坑：① 默认 1 秒的探针超时在资源紧张的机器上会把 MySQL 打死（liveness 失败 → 重启 → 复制中断），示例把 timeoutSeconds 调到 5、failureThreshold 调到 6；② super_read_only 会挡住 dump 导入，必须在导入前 OFF、导入并配置完再 ON。

                                    三条铁律

                                    铁律 含义 违反后的故障
                                    人格分裂 同一个模板要按序号思考“我是 Master 还是 Slave” 所有节点用同一份 my.cnf，主从不分
                                    阅后即焚 只在第一次启动做初始化，做完删标记/改名 容器重启重复初始化，数据被覆盖
                                    容器平等无序 不要假设 Sidecar 先于/后于主容器启动 Sidecar 抢跑，连不上 mysqld

                                    🔑 这三条不只适用于 MySQL。任何“一个模板、多种角色”的系统（Operator、分片集群、消息队列）都要过这三关。

                                    StatefulSet 不够的时候

                                    这个方案有一个硬限制：角色由序号固定。mysql-0 挂了，重建后它还是 Master；它不会自动把 Slave 提升为 Master。真实的故障转移需要选主与角色切换：

                                    需求 方案
                                    只要主从复制、能接受人工切换 StatefulSet + 本文的 Init/Sidecar
                                    要自动 failover Operator（如 MySQL Operator、Vitess）或外部 HA 组件（Orchestrator、MHA）
                                    主从镜像/配置差异很大 拆成两个 StatefulSet，或直接 Operator
                                    读写分离 + 分片 引入代理层（ProxySQL、Vitess）

                                    判据：StatefulSet 能表达“第几个”，表达不了“谁现在是主”。后者是运行时状态，必须由控制器持续调谐。

                                    反模式

                                    反模式 后果
                                    用 Deployment 跑 MySQL Pod 重建换名字、PVC 挂错、启动顺序不可控
                                    多个 Pod 共享同一个 RWO PVC 多数存储只允许单节点挂载，第二个 Pod 卡在 ContainerCreating
                                    假设 mysql-0 永远是主 Master 故障后不会自动升主，写入全挂
                                    Init Container 不幂等 Pod 重启把已有数据重新覆盖，恢复变灾难
                                    Sidecar 不等待 mysqld CHANGE MASTER 在 mysqld 未就绪时执行，初始化失败
                                    删了 StatefulSet 就以为清理干净 PVC/PV 默认保留，云盘继续计费
                                    缩容后不清理 PVC 孤儿盘越积越多，且名字可预测、容易误挂
                                    把 StatefulSet 当备份 它只保证盘还在，不保证数据可恢复；误删、损坏照样丢
                                    直接照抄 2018 年的镜像与 SQL MySQL 8 的复制语法与 XtraBackup 版本都已变化

                                    ⚠️ 时代注记：本文的 mysql:5.7、xtrabackup:2.4、CHANGE MASTER TO 是原文示例。MySQL 8.0.23+ 推荐 CHANGE REPLICATION SOURCE TO ... SOURCE_HOST=...，但本机实测 8.0.46 的 mysqldump 仍输出 CHANGE MASTER TO，解析脚本要同时兼容两种写法；生产应使用当前受支持的镜像，并用 CSI StorageClass 替代原文的 Rook/Ceph 写法。

                                    自检

                                    Q1 为什么写请求必须连 mysql-0.mysql，而不能连 mysql-read？

                                    ▸ 答案：mysql-read 是普通 Service，会把请求负载到所有 Pod，包括 Slave；Slave 开了 super-read-only，写会被拒绝。写必须走 Headless Service 给 mysql-0 的固定 DNS 记录。根因是 StatefulSet 所有 Pod 标签相同，Service 无法按角色筛选。

                                    Q2 clone-mysql 里的 [[ -d /var/lib/mysql/mysql ]] && exit 0 去掉会怎样？

                                    ▸ 答案：Pod 重启时 Init Container 会再跑一遍，从上一个节点重新拉备份并覆盖 /var/lib/mysql，已有数据丢失，且可能把已经同步到的位点回退。这行是幂等开关，也是“阅后即焚”在数据侧的实现。

                                    Q3 Sidecar 为什么要先 until mysql -h 127.0.0.1 -e "SELECT 1"，不能直接执行 CHANGE MASTER？

                                    ▸ 答案：同一个 Pod 里的容器没有启动顺序，Sidecar 可能先于 mysqld 就绪。直接执行会连接失败，初始化 SQL 丢失；而 Sidecar 退出重启后，触发文件可能已被改名，初始化就永远不会再执行。自旋等待是唯一可靠的顺序保证。

                                    Q4 mysql-0 所在节点宕机，StatefulSet 会做什么、不会做什么？

                                    ▸ 答案：会在其他节点重建 mysql-0，并挂回 data-mysql-0（如果存储支持跨节点挂载）；不会把 mysql-1 提升为 Master。角色切换是 StatefulSet 能力之外的，需要 Operator/HA 组件。

                                    Q5 为什么这个案例要用 volumeClaimTemplates，而不是在 Pod 里直接写 volumes？

                                    ▸ 答案：volumeClaimTemplates 会为每个序号生成固定名字的 PVC（data-mysql-0），PVC 生命周期独立于 Pod；Pod 重建后仍能挂回同一块盘。直接写 volumes（如 hostPath 或共享 PVC）要么把数据绑死在节点上，要么让多个 Pod 抢同一块盘，都保不住“每个副本独立身份”。
