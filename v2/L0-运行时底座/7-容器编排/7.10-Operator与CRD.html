                          7.10 Operator 与 CRD

                          一句话

                          CRD 是 “给 API server 加一种新对象”，Operator 是 “为这个对象写一个专用控制器”；要不要写 Operator，看 “这套运维知识能否写成状态机”，而不是 “别人都有”——写不好就是一个会误删数据的脚本。

                          CRD：给集群加一个 “名词”

                          apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata: {name: databases.example.com}
spec:
  group: example.com
  scope: Namespaced
  names: {kind: Database, listKind: DatabaseList, plural: databases, singular: database}
  versions:
    - name: v1
      served: true
      storage: true
      subresources: {status: {}}            # 关键：status 独立子资源
      additionalPrinterColumns:              # kubectl get 时显示什么
        - {name: Ready, type: string, jsonPath: .status.conditions[?(@.type=="Ready")].status}
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: [version, storageGB]
              properties:
                version:   {type: string, pattern: "^[0-9]+\\.[0-9]+$"}
                storageGB: {type: integer, minimum: 10}

                          三个必设项，缺一个后患无穷：

                          设置 为什么
                          subresources.status 让 controller 改 status 时不会覆盖用户的 spec（否则两边互相覆盖）
                          additionalPrinterColumns 否则 kubectl get 只能看到名字，运维体验倒退十年
                          结构化 schema + 校验 没有校验的 CRD 等于 “任何字段都接受”，错误延后到运行期才爆

                          Operator：把运维动作写成调谐循环

                          组件 作用 常见错误
                          Reconcile 读 spec → 读现状 → 算出差异 → 执行 只处理 “创建”，不处理 “外部被改动”
                          Finalizer 删除前清理外部资源（云盘、DNS、账号） 清理失败不返回错误 → 对象永远 Terminating
                          ownerReferences 级联删除子对象 子对象在别的命名空间 → 跨命名空间不生效
                          status.conditions 结构化状态（Ready/Progressing/Degraded） 只写 phase: Running，无法表达 “部分就绪”
                          事件（Events） 面向人的 “发生了什么” 不写事件，排错只能看日志

                          能力分级（Operator Framework 的公开模型，用来判断 “值不值得写”）：

                          级别 能做什么 大致工作量
                          1. Basic Install 一键装起来 小
                          2. Seamless Upgrade 版本升级与回滚 中
                          3. Full Lifecycle 备份、恢复、扩缩容、故障切换 大
                          4. Deep Insights 指标、告警、日志约定 大
                          5. Auto Pilot 自动调优、自动扩缩、自愈决策 很大

                          大多数团队需要的是 1–2 级；宣称做到 5 级但没人维护的 Operator，比手工运维更危险（它会在凌晨自动做决定）。

                          一个真实 Operator 的内部结构（以 Etcd Operator 为例）

                          理论看多了容易写成 “学院派控制器”，看一个真跑过的实现更有用：

                          它没用工作队列

                          常规写法（推荐） Etcd Operator 的做法
                          EventHandler 只把 key 塞进 workqueue，worker 干活 EventHandler 里直接跑业务（源码里留着 TODO: use workqueue to avoid blocking）
                          队列天然去重、可限速、可退避 无去重，业务耗时直接拖慢 Informer 的 watch 周期
                          一个共享 worker 池 为每个 EtcdCluster 对象起一个独立控制循环，并发响应

                          它用 “N 个 goroutine” 换掉了 “一个共享队列”：实现简单、响应快，代价是业务逻辑一旦慢，就会把 Informer 拖住。这不是反面教材，而是说明 7.1 的 workqueue 铁律是为了 “不被单个对象卡住全局”，绕过它就得自己承担这个风险。

                          启动参数里写的是 Pod 的 DNS，不是 IP

                          生成 etcd 启动命令时 Pod 还没创建，IP 根本不存在，所以 initial-cluster / advertise 参数里全部填 DNS 记录：

                          <pod-name>.<headless-svc>.<ns>.svc.cluster.local

                          前提是每个 Cluster 对象都会预先创建一个同名的 Headless Service。种子 Pod 里还带一个 InitContainer：先检查本 Pod 的 DNS 记录是否正常，通过后才启动 etcd 容器。这就是 “用 DNS 当稳定身份” 的落地方式，也是它不用 StatefulSet 编号也能组集群的原因。

                          etcd 静态集群只有三个参数

                          看懂了这三个参数，就知道 Operator 到底要生成什么：

                          参数 含义
                          --initial-cluster 名字=peerURL 的列表，告诉新成员“集群里还有谁”
                          --initial-cluster-token 集群唯一 token，防止别的集群的成员误加入
                          --initial-cluster-state 种子节点用 new，后加入的成员用 existing

                          扩容不是“改 replicas 等控制器拉起”，而是三步：

                          1. etcdctl member add <pod名> <peerURL>——先让现有集群登记新成员；
                          2. 用“已有成员 + 新成员”拼出更长的 --initial-cluster，启动新 Pod；
                          3. 重复到成员数等于期望值；缩容走 member remove。

                          🔑 拓扑信息存在 etcd 自己的成员表里，不在 Pod 名字里。所以 Operator 完全可以用随机名（example-etcd-cluster-v6v6s6stxd），这是它与“StatefulSet 靠编号定身份”最根本的分水岭。

                          CRD 的性能边界：JSON 换 protobuf 的那部分

                          内置对象在 apiserver 与 etcd 之间走 protobuf；自定义对象（CR）存的是 JSON。这意味着：

                          • 对象数量多、单个对象大时，序列化/反序列化与存储开销都更高；
                          • CRD 适合“描述期望状态 + 控制器调谐”，不适合当业务数据库（高频写入、大列表、复杂查询都不划算）。

                          ⚠️ 判断“该不该用 CRD”时，先问“这是不是 K8s 对象”，而不是“能不能塞进 CRD”。业务数据该进数据库，CRD 只存“控制器需要看到的那部分期望状态”。

                          权限清单是三段式，天然是 “上帝 Operator”

                          上线前必须先执行 create_role.sh，它一次授三类权限：

                          类别 范围 为什么需要
                          工作负载 Pod、Service、PVC、Deployment、Secret 全权限 要代用户创建这些对象
                          CRD 全权限 Operator 启动时自己创建 etcdclusters.etcd.database.coreos.com
                          自家 CR 属于 etcd.database.coreos.com 的 CR 全权限 读写被它管理的对象

                          🔑 结论很直接：Operator 的 RBAC 天然跨命名空间、且带 CRD 写权限。这就是 “上帝 Operator” 风险的来源，也说明它必须用独立的 ServiceAccount，绝不能复用 default。

                          自治有硬边界：调谐 “进程”，不调谐 “数据”

                          Etcd 基于 Raft，失效容忍度直接决定 Operator 能不能救：

                          失效节点数 集群状态 Operator 能做什么
                          ≤ 1（半数以下） 仍可读写 调谐：建新 Pod、加回集群，自愈完成
                          ≥ 2（半数以上） 丧失写入能力，进入不可用 无能为力：即使建出新 Pod 也恢复不了，只能用备份重建

                          所以备份是另一个 Operator 的活：每创建一个 EtcdBackup 对象等于做一次备份（etcdEndpoints 指向被备份集群），建议包成 CronJob 定时跑；恢复则创建 EtcdRestore，恢复出新集群后交回 Etcd Operator 接管。

                          🔑 Operator 只调谐副本数与进程，不调谐数据。 任何 “它会把数据救回来” 的期待都是错的——这正是 7.7 存储卷与持久化 里 “快照 ≠ 备份” 的同一条结论在 Operator 世界的重演。

                          第三条路：自己写一个 aggregated apiserver

                          CRD 之外还有一条更重、但更强的路：用 k8s.io/apiserver 写一个独立 apiserver，注册进主 apiserver 的聚合层（也就是 7.13 集群搭建与控制面自举 里 kube-aggregator 的另一侧）。

                          维度 CRD + Operator Aggregated apiserver（如 onex-apiserver）
                          存储 主 etcd 里的 CR 可独立 etcd / 数据库，容量与生命周期解耦
                          校验 OpenAPI schema 任意 Go 代码（admission 插件、跨字段校验）
                          版本转换 conversion webhook 进程内 registry 转换
                          升级 改 CRD 可能影响存量对象 自己发版，可灰度
                          成本 低（YAML + 控制器） 高（registry / store / admission 三件套）
                          适合 绝大多数扩展场景 平台级 API（多租户、独立存储、强校验）

                          一条真实实现的形状（onex 的 cmd/onex-apiserver/app/aggregator.go，源码 (opens new window)）：直接复用 k8s.io/apiserver/pkg/server 的 genericapiserver，用 BuildHandlerChainFunc 定制请求链，再把自有 API Group 注册进去，最后由 internal/controlplane/apiserver 组装成控制面。

                          🔑 判断标准：你的对象要不要"独立存储、独立发版、任意校验"？不要 → CRD；要，且你有平台团队 → aggregated apiserver。为了显得复杂而选后者，是纯负债。

                          一个 aggregated apiserver 的内部三层：Strategy / Store / REST

                          自己写 apiserver 时，"注册一个资源"不是写一个 handler，而是三个文件各管一件事（onex 的真实目录）：

                          internal/apiserver/registry/apps/
├── miner/strategy.go              # ① Strategy：对象的"规矩"
├── miner/storage/                 # ② Store：怎么落到 etcd
└── rest/storage_apps.go           # ③ REST：把资源与子资源注册进 API
                          层 回答什么 典型方法
                          Strategy 什么能改、什么由系统填 PrepareForCreate / Validate / NamespaceScoped / GetResetFields
                          Store 怎么读写 etcd、怎么做乐观并发 NewStorage / Create / Update（带 resourceVersion 检查）
                          REST 暴露成哪些路径与子资源 NewRESTStorage 返回 APIGroupInfo

                          Strategy 里最能说明"用户写 spec、系统写 status"的两段（registry/apps/miner/strategy.go）：

                          // 声明哪些字段会被系统重置，用户改不了
func (minerStrategy) GetResetFields() map[fieldpath.APIVersion]*fieldpath.Set {
	return map[fieldpath.APIVersion]*fieldpath.Set{
		"apps.onex.io/v1beta1": fieldpath.NewSet(fieldpath.MakePathOrDie("status")),
	}
}

// 创建时把用户不该决定的东西清掉
func (minerStrategy) PrepareForCreate(ctx context.Context, obj runtime.Object) {
	miner := obj.(*apps.Miner)
	miner.Status = apps.MinerStatus{}   // status 由控制器写
	miner.Generation = 1                // 期望状态的第 1 代
	dropMinerDisabledFields(miner, nil)
}

                          ③ 层则决定"这个资源对外长什么样"。注意子资源是分开注册的：

                          storage["miners"]        = minerStorage.Miner      // 主资源
storage["miners/status"] = minerStorage.Status     // 状态子资源：只有控制器该写
storage["minersets/scale"] = minerSetStorage.Scale // 扩缩容子资源：只有 HPA 该写

                          🔑 这解释了 7.1 声明式 API 与控制器模式 里那条铁律在代码里是怎么做到的：不是靠规矩，而是靠把它拆成不同的子资源——kubectl apply 打的是 miners，控制器打的是 miners/status，两者走不同的 REST 端点、可以分别授权（见 7.14 认证与 RBAC）。

                          准入插件：在写 etcd 之前改字段、拦删除

                          Strategy 管的是"这个对象该怎么",准入插件管的是"这次请求该不该、要不要补"。onex 给自有 API 组写了一个（internal/apiserver/admission/plugin/minerset/，源码 (opens new window)）：

                          // 一个插件可以同时是"改"与"校验"
var (
	_ admission.MutationInterface   = &Plugin{}
	_ admission.ValidationInterface = &Plugin{}
)

func (p *Plugin) Admit(ctx context.Context, attributes admission.Attributes, o admission.ObjectInterfaces) error {
	if shouldIgnore(attributes) {          // 只管 minersets 主资源，子资源一律放过
		return nil
	}
	if !p.WaitForReady() {                 // 缓存没同步完就拒绝（fail-closed）
		return admission.NewForbidden(attributes, fmt.Errorf("not yet ready to handle request"))
	}
	ms := attributes.GetObject().(*apps.MinerSet)
	ms.Spec.Template.Spec.DisplayName = fmt.Sprintf("miner-for-%s-minerset", ms.Name)  // 填默认值
	addMinerSetSelector(ms)                // 补 label selector
	return nil
}

                          Validate 里有一处最容易被做错的地方——删除保护：

                          if attributes.GetOperation() == admission.Delete {
	// 删除请求没有对象体，只能先用 lister 把对象取出来，再看注解
	ms, err := p.lister.MinerSets(attributes.GetNamespace()).Get(attributes.GetName())
	if apierrors.IsNotFound(err) {
		return nil
	}
	if v, ok := ms.GetAnnotations()[apps.AnnotationDeletionProtection]; ok && v == "true" {
		return admission.NewForbidden(attributes, fmt.Errorf("minerset has deletion protection turned on"))
	}
}

                          三条可复用的经验：

                          经验 原因
                          改（Mutation）与校验（Validation）分开实现 两者语义不同：改出来的字段不该被自己再校验一遍；框架允许一个插件实现两个接口
                          删除要 Get 出来再判断 DELETE 请求里没有对象体，所有"基于对象内容"的拦截都必须在 Validate 里先 Get
                          WaitForReady() 必须挡在最前 插件的 lister 是异步同步的；缓存还没好就放行，等于用空数据做安全判断（fail-open）

                          依赖怎么进来？还是那套 Wants* 按需注入（与 56.4 告警治理 的巡检插件同款）：

                          func (i pluginInitializer) Initialize(plugin admission.Interface) {
	if wants, ok := plugin.(WantsExternalInformerFactory); ok {
		wants.SetExternalInformerFactory(i.informers)
	}
	if wants, ok := plugin.(WantsExternalClientSet); ok {
		wants.SetExternalClientSet(i.client)
	}
}

                          🔑 注意它和 Operator 的分工：准入插件只能拒绝或补字段，不能"稍后处理"。需要异步收敛的逻辑（建 Pod、调云 API）仍然只能放控制器里。两者一个管"请求是否合规"，一个管"现实是否收敛"。

                          扩展 API 之后：客户端代码是生成的，不是手写的

                          自己写 apiserver 之后，你还需要一套能跟它对话的客户端。onex 的做法是全部生成（pkg/generated/，源码 (opens new window)）：

                          产物 干什么
                          deepcopy 每个类型一个 DeepCopy()，控制器缓存拷贝时必需
                          defaulter 服务端默认值（与准入插件配合）
                          conversion 多版本之间互转（v1beta1 ↔ v1）
                          openapi 给 kubectl explain 与文档用
                          clientset / informers / listers 类型化客户端 + 本地缓存 + 只读视图
                          applyconfigurations server-side apply 的类型化入口（Apply 时用它构造 patch 体）

                          入口只有一个 make 目标（scripts/make-rules/generate-k8s.mk）：

                          generated.files: tools.verify.code-generator gen_prerelease_lifecycle gen_deepcopy \
                 gen_defaulter gen_conversion gen_openapi gen_client
                          设计点 说明
                          一个入口聚合全部生成 生成物必须成套更新，分开跑就会出现"client 新、deepcopy 旧"的半新状态
                          tools.verify.code-generator 锁工具版本 生成器版本不同，产物会漂移，diff 里全是噪音
                          生成物入库 PR 里能看到 API 变更的影响面；对比"运行时反射"方案，编译期就能挡住不兼容

                          ⚠️ 该文件头注释已写明它被 scripts/update-codegen.sh 取代（保留只为参考）。抄这套的时候，先确认你要抄的是活的那份脚本，而不是历史遗留的 mk。

                          什么时候不需要 Operator

                          情况 更简单的做法
                          无状态应用 Deployment + HPA 已经够了
                          运维逻辑只有 “改配置 + 重启” Helm chart + runbook
                          中间件用托管服务 厂商已经替你写了 Operator
                          团队没人能维护控制器 手工 + 定时任务，至少出错时有人看得懂

                          判据一句话：这套中间件的运维知识，能否写成 “读状态 → 判断 → 动作” 的确定状态机？ 能，且重复频率高，才值得；否则就是给自己造一个必须长期维护的服务。

                          反模式

                          反模式 后果
                          CRD 设计成 “万能对象”（塞 60 个字段） 校验失效、版本升级无法兼容、用户不会用
                          改 CRD schema 时删字段/改类型 存量对象校验失败，集群升级卡住
                          Finalizer 清理失败却不报错 对象永久 Terminating，只能手工 patch 去掉 finalizer
                          Operator 里用轮询全量 List 代替 watch apiserver 压力大，收敛慢
                          控制器把用户 spec 改掉 用户改一次被覆盖一次，最终没人敢改
                          只写 phase，不写 conditions 无法表达并发状态，上层无法做判断
                          用 Operator 管 “本该由 Helm 管” 的部署 两套控制器抢同一批对象，互相打架
                          让 Operator 复用 default ServiceAccount 它需要跨命名空间 + CRD 写权限，等于给所有 Pod 发了全权
                          指望 Operator 在 “多数节点失效” 时把数据救回来 它只能调谐进程；数据恢复必须靠备份
                          在 EventHandler 里直接跑秒级业务 watch 周期被拖住，全集群对象更新变慢（除非像 Etcd Operator 那样按对象分循环）

                          三条铁律

                          🔑 CRD 先定 schema 与 status 子资源；没有校验和状态分离的自定义对象，长期一定失控。

                          🔑 Finalizer 必须 “要么成功清理，要么报错”；静默失败会制造永远删不掉的对象。

                          🔑 只写你能维护的 Operator；1–2 级能力覆盖大多数场景，5 级的承诺通常没人兑现。

                          自检

                          Q1 为什么必须开 subresources.status？

                          ▸ 答案：因为不开时，controller 更新 status 会走整对象更新，与用户更新 spec 冲突（后写覆盖先写），导致 “用户刚改的 spec 被 status 写回旧值”。开了子资源后，status 与 spec 分开写，并发安全，也让 RBAC 能区分 “谁能改状态、谁能改期望”。

                          Q2 一个自定义对象删不掉，一直 Terminating，怎么处理？

                          ▸ 答案：先看 metadata.finalizers 与 controller 日志：通常是 finalizer 对应的清理逻辑失败却返回了 nil（不再重试），或 controller 已经不在运行。临时解法是 kubectl patch <obj> -p '{"metadata":{"finalizers":null}}' --type=merge（有丢外部资源的风险）；根本解法是让 finalizer 在失败时返回错误，持续重试并上报事件。

                          Q3 团队想给一个 “只有读多写少” 的 Redis 写 Operator，做自动扩缩与故障切换。你会怎么劝？

                          ▸ 答案：先问三件事：① 用托管 Redis 行不行（厂商已写好 Operator，成本最低）；② 运维知识是否是确定状态机（哨兵/集群模式的切换逻辑很复杂，写错会脑裂）；③ 谁长期维护它。若三者都没有好答案，答案就是 “不写”，用托管服务或标准 chart + runbook，把精力放在业务上。

                          Q4 CRD 加了一个新版本 v2，怎么保证存量对象不坏？

                          ▸ 答案：三件事：① 不删不改 v1 已有字段（只加可选字段），保证 v1 对象在 v2 schema 下也合法；② 配 conversion webhook 做 v1 ↔ v2 转换，并保证往返无损；③ 先让 served: true 的 v1 与 v2 并存一段时间，等所有客户端升级后再把 v1 从 storage 里退役。跳过任何一步，升级时都会出现 “对象读不出来”。

                          Q5 为什么说 “Operator 会误删数据” 不是危言耸听？

                          ▸ 答案：因为 Operator 拥有写权限：它能删 PVC、删云盘、改配置、触发主从切换。如果状态机逻辑有漏洞（比如 “副本数变 0 就清理所有卷”），一次配置错误就会执行成 “删除全部数据”。这正是 “只写你能维护的 Operator” 的原因——它的权限与数据库管理员相当，但往往没有同等的测试与演练。

                          Q6 一个 etcd Operator 给节点生成的启动参数里全是 xxx.svc.cluster.local，为什么不直接用 Pod IP？如果 3 节点集群同时挂了 2 个，Operator 还能自愈吗？

                          ▸ 答案：用 DNS 是因为生成参数时 Pod 还没创建，IP 还不存在；而 Headless Service 的 DNS 记录在 Pod 创建前就能确定（所以每个 Cluster 都要预先建同名 Headless Service）。至于 2/3 挂掉：不能自愈。Raft 在失去半数以上节点后丧失写入能力进入不可用，Operator 只能重建 Pod（调谐 “进程数”），无法重建多数派与数据；此时必须用备份（EtcdBackup）恢复。判据是 “失效节点数 vs 半数”，不是 Operator 的版本或配置。
