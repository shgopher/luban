# 6.3 namespace (隔离) 与 cgroups (限制)

## 一句话

> namespace 回答 “**你能看见什么**”，cgroups 回答 “**你最多能用多少**”；容器 = 一组 namespace + 一棵 cgroup 子树，只做一半都不算容器——只隔离不限流，一个进程能拖垮整机；只限流不隔离，进程之间互相看得见。

## 八种 namespace：各管一段视野

| namespace | 隔离什么 | 不隔离什么（容易误解） |
|---|---|---|
| **mnt** | 挂载点视图（自己的 rootfs） | 底层块设备仍共享 |
| **pid** | 进程号空间（容器内 PID 1 是应用） | 宿主的真实 PID 仍可见（`/proc` 视角受限） |
| **net** | 网卡、IP、端口、路由表、防火墙规则 | 物理网卡与宿主网络 |
| **uts** | 主机名与域名 | — |
| **ipc** | System V IPC、POSIX 消息队列 | 共享内存页仍在内核里 |
| **user** | UID/GID 映射（容器 root ≠ 宿主 root） | 内核漏洞仍可跨 namespace |
| **cgroup** | 进程看到的 cgroup 视图 | 限额本身由宿主设置 |
| **time**（Linux 5.6+） | `CLOCK_MONOTONIC` / `CLOCK_BOOTTIME` 的偏移 | 墙钟时间（`CLOCK_REALTIME`）不隔离 |

三个最常被搞混的点：

- **pid namespace 里 “PID 1” 有特殊语义**：它接收 `SIGTERM` 的默认行为不同、不会自动被回收孤儿进程。所以容器里跑 `bash` 当 1 号进程会导致信号处理不对（用 `tini`/`dumb-init` 或直接 exec 应用进程）。
- **net namespace 是 “一个容器一个网络栈”**，这也是 “一个 Pod 一个 IP” 的内核基础。
- **user namespace 是 rootless 容器的前提**：容器内 root 映射为宿主的普通 UID，逃逸后拿不到宿主 root。

### namespace 不是「容器设施」，是 `clone()` 的一个可选参数

内核里没有 “容器” 这个对象，也没有 “创建容器” 的系统调用。所谓容器，就是在 `clone()` 时多带一个 flag：

```c
// 带 CLONE_NEWPID：新进程在自己的 PID namespace 里看到自己是 1 号
clone(child_func, stack, CLONE_NEWPID | SIGCHLD, NULL);
```

于是出现 “障眼法”：新进程认为自己是 **PID 1**，而在宿主的真实 PID 空间里它还是原来的编号（比如 100）。**只改进程看到的编号视图，不改进程本身。**多次带 `CLONE_NEWPID` 调用，就得到多个互不可见的 PID 空间。

> 🔑 Docker 做的事，只是创建容器进程时指定一组 `CLONE_NEW*` 参数。理解这一点，“容器” 的神秘感就没了。

### mnt namespace 的两个陷阱：不 mount 就没变化，shared 还会漏出去

`mnt` 常被当成 “容器有自己的文件系统”，实际有两个坑：

| 陷阱 | 现象 | 根因 |
|---|---|---|
| 只 `clone(CLONE_NEWNS)` 不 `mount` | 新进程 `ls /tmp` 看到的**和宿主完全一样** | mnt namespace 改的是 “对挂载点的认知”，**只有 mount 发生后视图才变** |
| 宿主的根挂载是 **shared** | 容器内 mount 会**传播回宿主机** | 挂载传播属性被继承了 |

所以 rootfs 不是 namespace 自动给的，必须显式换根：Docker 优先 `pivot_root`，系统不支持才退回 `chroot`（且 chroot 后进程自己感知不到根被换了）。

修法是在容器内先把根改成 private，再挂载：

```c
mount("", "/", NULL, MS_PRIVATE, "");        // 关掉挂载传播
mount("none", "/tmp", "tmpfs", 0, "");       // 这次只在容器内可见
```

自建虚拟机或云主机的根目录常以 shared 方式挂载——**实验泄漏到宿主的真实原因不是 namespace 失效，而是挂载传播**。判断方法：实验后在宿主 `mount -l | grep tmpfs`，还能看到容器里那个 tmpfs 就是没关传播。

### `docker exec` 靠 `setns()`「加入」而不是「穿透」

每个进程的每种 namespace 在宿主上都有实体文件：

```bash
ls -l /proc/<PID>/ns/
# net -> 'net:[4026532281]'   ← 指向 inode 号的符号链接
```

`docker exec` 的原理是 `open` 这个文件拿到 fd，`setns(fd, 0)` 让当前进程加入该 namespace，再 `execvp` 起一个 shell。**它不是从外面 “钻进去”，而是加入同一个 namespace。**

验证两个容器是否共享网络栈：

```bash
docker inspect --format '{{ .State.Pid }}' c1   # 取宿主 PID，比如 100
ls -l /proc/100/ns/net                          # net -> 'net:[4026532281]'
ls -l /proc/200/ns/net                          # 同样是 net:[4026532281] → 共享
```

顺带两个用法：`docker run --net container:<id>` 让新容器加入已有容器的 netns；`--net=host` 干脆不建 netns，直接共用宿主网络栈。

## cgroups：两类资源，两种失败方式

| 资源类型 | 代表 | 超限后果 | 特点 |
|---|---|---|---|
| **可压缩**（compressible） | CPU、IO 带宽 | 变慢（节流 / 排队） | 不会杀进程，但长尾会恶化 |
| **不可压缩**（non-compressible） | 内存 | **OOM Kill** | 直接杀进程，往往杀掉整个容器 |

这条区分决定了两类故障的排查方向：CPU 打满 → 看 throttling；内存打满 → 看 `dmesg` 的 OOM 记录与 `container_memory_working_set_bytes`。

### cgroups v1 与 v2

| 维度 | v1 | v2 |
|---|---|---|
| 层级 | 每个控制器一棵树（cpu、memory 各自挂载） | **一棵统一树**，控制器按需启用 |
| CPU 限额 | `cpu.cfs_quota_us` / `cpu.cfs_period_us` | `cpu.max`（如 `50000 100000`） |
| CPU 权重 | `cpu.shares` | `cpu.weight`（1–10000） |
| 内存硬限 | `memory.limit_in_bytes` | `memory.max` |
| 内存软限 | `memory.soft_limit_in_bytes` | `memory.high`（更实用：限速而非杀） |
| 进程数 | `pids.max` | `pids.max` |
| 统计 | 分散在各子树 | `memory.stat` / `cpu.stat` 统一 |

Kubernetes 从 1.25 起把 cgroup v2 的支持转为稳定（GA）。v2 的实际好处是 `memory.high` 可以做 “软限流” 而不是直接 OOM，这对延迟敏感服务比硬限更友好。

### 手搓一个 cgroup：`mkdir` 就是建组

cgroups 暴露给用户的接口**就是文件系统**。`mount -t cgroup` 能看到 cpuset / cpu / cpuacct / blkio / memory 各挂一棵树；在某个子系统目录里 `mkdir` 一个目录，内核立刻在其中生成 `cpu.cfs_quota_us`、`tasks` 等文件——**这个目录就是一个控制组**。

```bash
# 默认值：quota=-1（不限）、period=100000μs（100ms）
cat /sys/fs/cgroup/cpu/mygroup/cpu.cfs_quota_us     # -1
echo 20000 > /sys/fs/cgroup/cpu/mygroup/cpu.cfs_quota_us   # 每 100ms 只用 20ms
echo 226   > /sys/fs/cgroup/cpu/mygroup/tasks       # 把 PID 226 放进去
```

实测效果（课程原文）：`top` 里该进程的 `%Cpu0` 从 **100.0** 掉到 **20.3** —— 20/100 的配额直接生效。Docker 也不过是替每个容器在子系统下建目录、把 PID 写进 `tasks`。

### requests / limits 落在哪

| K8s 字段 | 落到 cgroup | 语义 |
|---|---|---|
| `requests.cpu` | `cpu.weight`（按比例换算） | 调度与竞争时的**相对份额**，不是保底独占 |
| `limits.cpu` | `cpu.max`（quota/period） | 硬上限，超了被节流 |
| `requests.memory` | 调度依据（不写 cgroup） | 只影响调度，**不影响运行时** |
| `limits.memory` | `memory.max` | 硬上限，超了 OOM Kill |

> ⚠️ **`requests.memory` 不设限**：它只用于调度，容器实际可以用到节点全部内存（直到 `limits.memory` 或节点压力）。所以 “设了 requests 就安全” 是误解。

## 容器里 `top` 为什么在说谎：`/proc` 不认 cgroups

cgroups 限了额度，但容器里 `top` / `free` / `nproc` 显示的仍然是**整台宿主机**的 CPU 核数与内存总量：

| 数据源 | 实际内容 | 为什么不按 cgroup 折算 |
|---|---|---|
| `/proc/meminfo` | 宿主内存总量 | `/proc` 文件系统**不了解 cgroups 限制的存在** |
| `/proc/cpuinfo`、`/proc/stat` | 宿主 CPU 核数与用量 | 同上 |
| `/proc/self/status` 的部分字段 | 宿主视角 | 同上 |

本机实测（Docker Desktop 29.9.2 / linux-arm64，2026-10，容器限 256 MiB + 0.5 核）：

```text
$ docker run --rm --memory=256m --cpus=0.5 alpine:3.20 sh -c \
    'head -1 /proc/meminfo; cat /sys/fs/cgroup/memory.max; nproc; cat /sys/fs/cgroup/cpu.max'
MemTotal:        4010356 kB     ← 读到的是宿主 3.8 GiB
268435456                        ← cgroup 的真实上限 256 MiB
8                                ← 读到 8 核
50000 100000                     ← 真实配额 = 0.5 核
```

一个按 “核数 × 2” 算并发的程序，在这里会起 16 个 worker，而实际只有 0.5 核可用——**它读到的每个数都是错的，而且错得很有方向性（系统性偏大）**。

真实事故链（很常见，且极难第一时间想到）：容器 `limits.memory` 设 4Gi，宿主机 60 多 GiB；JVM 默认按宿主内存算堆大小，还没等到 full GC 就被 cgroup **OOM Kill**。日志里只有 `OOMKilled`，而 `-Xmx` 看起来 “很正常”。

修法是把真实的限制 “喂” 给 `/proc`：

```bash
# lxcfs：用 FUSE 从该容器的 cgroup 读出真实限制，再挂到容器的 /proc
/var/lib/lxcfs/proc/meminfo    →  容器的 /proc/meminfo
/var/lib/lxcfs/proc/cpuinfo    →  容器的 /proc/cpuinfo
```

应用侧还有更省事的做法：Java 用 `-XX:MaxRAMPercentage`（容器感知）、Go 用 `GOMEMLIMIT`、或直接显式设 `-Xmx` 为 limit 的 60%~75%。

> ⚠️ 这条坑的判据很简单：**应用只要读 `/proc` 或 “机器核数” 来算并发/堆大小，就必须检查它在容器里读到了什么值。**

## CPU 节流的隐藏代价：P99 抖动

CPU 配额按 **CFS 周期**（默认 100ms）结算：一个 `limits.cpu = 1` 的容器，每 100ms 只有 100ms 的 CPU 时间。如果它在 40ms 内用完了配额，剩下的 60ms 只能等下一周期——对平均延迟影响不大，对 **P99 是灾难**。

| 现象 | 原因 | 缓解 |
|---|---|---|
| 平均延迟正常、P99 尖刺 | 周期末配额耗尽，线程被节流 | 提高 limit、拆分热点线程、调小 period |
| 压测达标、线上偶发超时 | 多线程在周期边界争抢配额 | 留 30% CPU 余量，别按 100% 设 limit |
| 节点 CPU 空闲但容器变慢 | 容器自己的 quota 用完了 | 看 `cpu.stat` 的 `nr_throttled` |

判断方法很直接：看 `container_cpu_cfs_throttled_periods_total` 占 `container_cpu_cfs_periods_total` 的比例，超过 10% 就说明配额是瓶颈。

## 隔离 ≠ 安全：共享内核的逃逸面

namespace 与 cgroups 是**资源与视野**的隔离，不是安全边界。三层加固手段：

| 手段 | 作用 | 代价 |
|---|---|---|
| **capabilities** | 去掉不需要的 root 能力（默认已是受限集） | 某些工具需要显式加回（如 `NET_BIND_SERVICE`） |
| **seccomp** | 限制可用的系统调用（Docker 默认 profile 已拦一批） | 误拦会导致应用启动失败，需要调 profile |
| **LSM**（AppArmor / SELinux） | 文件与进程的强制访问控制 | 策略编写成本高，容易 “关掉算了” |

想真正做到 “强隔离”，只能换边界：用户态内核（gVisor）或轻量 VM（Kata），取舍见 [6.5 容器运行时 (containerd / runc)](6.5-容器运行时.md)。共享内核的后果在 [6.1 容器与虚拟机的本质差异](6.1-容器与虚拟机的本质差异.md) 里有完整推导。

## 实测：限制与隔离长什么样

```text
$ docker run --rm --memory=256m --cpus=1 alpine:3.20 sh -c \
    'echo memory.max=$(cat /sys/fs/cgroup/memory.max); \
     echo cpu.max=$(cat /sys/fs/cgroup/cpu.max); ls /proc/self/ns'
memory.max=268435456          # 256MiB → 字节
cpu.max=100000 100000         # 每 100ms 周期最多 100ms CPU = 1 核
cgroup ipc mnt net pid pid_for_children time time_for_children user uts
```

两点值得记：① 宿主用的是 **cgroup v2**（统一层级、`memory.max` / `cpu.max` 单文件）；② 容器内能看到 **9 个 namespace 项**（`pid`、`time` 各有 `*_for_children` 视图），而 “隔离” 只是这些视图的边界，**不是安全边界**。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只配 `limits.memory`，不配 `requests` | 调度按 0 算，节点被超卖后集中 OOM |
| 把 `limits.cpu` 设成核数并期待 “独占” | 只是上限；竞争时仍按 weight 分配 |
| 容器里用 `bash` 当 PID 1 | 信号处理异常，`docker stop` 等 10 秒后强杀 |
| 用 root 跑容器并挂载宿主目录 | namespace 不是安全边界，等于把宿主交出去 |
| 认为设了 requests 就不会被 OOM | requests 不落 cgroup，只影响调度 |
| CPU limit 按峰值 100% 设 | 长期在周期边界被节流，P99 抖动 |
| 关掉 seccomp / AppArmor “为了跑通” | 逃逸面回到默认全开 |
| 让 JVM/Go 按宿主机核数与内存自算参数 | 4Gi 的容器按 60Gi 算堆，没到 full GC 就 OOMKilled |
| 在 shared 根挂载的宿主机上做 mount 实验 | 挂载点传播回宿主机，污染宿主环境 |

## 三条铁律

> 🔑 **namespace 管视野，cgroups 管额度**；缺一半就不是容器，只是 “进程 + 包装”。

> 🔑 **CPU 超限变慢、内存超限被杀**；排查方向由这条区分决定。

> 🔑 **隔离不是安全边界**；要强隔离只能换内核（gVisor / Kata），不能靠调参数。

## 自检

**Q1** 一个容器 `limits.cpu = 2`，节点有 16 核且几乎空闲，但应用 P99 明显高于裸机。可能是什么原因？

▸ 答案：**被 CFS 节流**。limit 2 表示每 100ms 周期最多用 200ms CPU 时间；节点再空闲，容器也不能超用。多线程在周期内抢配额，末段线程要等到下个周期，于是出现 “平均正常、P99 尖刺”。验证看 `nr_throttled` 比例；缓解是提高 limit（或去掉）、减少热点线程数。

**Q2** 容器 `limits.memory = 2Gi` 被 OOM Kill 了，但 `docker stats` 显示 RSS 只有 1.2Gi。为什么？

▸ 答案：因为 `memory.max` 统计的是 **cgroup 的内存用量，包含 page cache**（工作集）。容器读写文件时 page cache 会涨；当总量触到 2Gi，内核回收不掉就 OOM。判断要看 `container_memory_working_set_bytes` 而不是 RSS，并区分 “应用真的需要 2Gi” 与 “page cache 把额度吃掉了”。

**Q3** 为什么说 “容器内 root 等于宿主 root” 是默认情况，而 rootless 能改变它？

▸ 答案：默认情况下容器与宿主共享 user namespace，容器内 UID 0 就是宿主 UID 0，只是被 capabilities 与 LSM 削弱。启用 **user namespace** 后，容器内 UID 0 映射到宿主的一个普通 UID（如 100000），逃逸后拿到的也只是普通权限。代价是：绑定 <1024 端口受限、部分文件系统（含 overlay）需要内核支持、性能略有损失。

**Q4** 一个服务平时 CPU 只用 0.3 核，大促时到 2 核，`limits.cpu` 设 1 会怎样？

▸ 答案：大促时**被硬性限流到 1 核**，剩下的请求排队，表现为延迟飙升与超时，而不是 “自动多用”。因为 limit 是上限不是弹性值。正确做法是 `requests` 按常态（0.3–0.5）设用于调度，`limits` 按峰值留余量（2.5–3），或干脆不设 CPU limit 只设 request（让节点层面共享，但要接受争抢）。

**Q5** 为什么 `requests.memory` 设了 512Mi，容器还能吃到 3Gi 才被杀？

▸ 答案：因为 `requests.memory` **只参与调度**（K8s 用它算节点可分配量），不写进 cgroup；真正的运行时上限是 `limits.memory` → `memory.max`。没设 limit 时，容器可以一直用到节点内存压力触发驱逐或 OOM。这也是 “requests 齐全但节点仍然 OOM” 的常见原因：超卖了内存却没有 limits。
