# 12.7 集中式与非集中式：控制面放在哪

## 一句话

> 集中式把 “全局视图” 放在一个点，非集中式把它摊给所有节点，混合形态在 “谁持有全局状态” 上折中；选型只看三个量——**决策频率、状态变化率、故障域**。

## 三种形态：一张表看全

| 形态 | 谁做决定 | 代表 | 优点 | 代价 |
|---|---|---|---|---|
| **集中式** | 一个 master / 一个调度器 / 一个注册中心 | Borg 单体调度、ZooKeeper 的 leader、单实例 Nacos | 无冲突、强一致、易调试 | 单点、吞吐上限、跨地域一次 RTT |
| **非集中式**（P2P） | 每个节点本地决定，靠 gossip / 一致性哈希收敛 | Dynamo、Cassandra、work stealing | 无单点、水平扩展 | 最终一致、冲突、观测困难 |
| **混合** | 分片多主 / 两层 offer / 共享状态 | Mesos 两层、Omega 共享状态、K8s 多集群 | 兼顾规模与一致性 | 两套模型、复杂度上移 |

> ⚠️ [12.2 单体调度](12.2-单体调度.md)、[12.3 两层调度](12.3-两层调度.md)、[12.4 共享状态调度](12.4-共享状态调度.md) 讲的是**混合形态里的三个代表**；本节讲更上层的结构轴：**控制面到底放在哪**。

## 集中式的账：吞吐被单点锁死，延迟随利用率爆炸

集中式的吞吐上限就是**单点的处理能力**：`1 / 单次决策耗时`。加机器只能加只读副本，不能加写吞吐。排队延迟则按 M/M/1 恶化：

| 利用率 `ρ` | 平均延迟（服务时间的倍数） | P99 近似 |
|---|---|---|
| 0.5 | 2 | 9 |
| 0.8 | 5 | 23 |
| 0.9 | **10** | 46 |
| 0.95 | 20 | 92 |
| 0.99 | **100** | 460 |

> 🔑 控制面最危险的时刻不是 “挂了”，而是 **利用率 90% 还活着**：延迟已经 10 倍，超时触发重试，重试把利用率推得更高，最后雪崩。

跨地域再叠一层：每次决策都要一次 RTT，30ms 的跨城往返意味着单 key 串行决策上限只有约 33 次/秒（见 [21.12 共识算法对比](../../L1-分布式原理/21-共识与选主/21.12-共识算法对比.md)）。所以集中式适合的是**低频、强一致、同地域**的控制面：配置变更、选主、服务注册。

| 集中式的故障 | 表现 | 对策 |
|---|---|---|
| 单点宕机 | 控制面全停，数据面可能仍活着 | 多副本 + 共识选主（Raft） |
| 脑裂 | 两个 master 各自发号施令 | 租约 + fencing token（见 [18.6 脑裂与防护](../../L1-分布式原理/18-数据复制/18.6-脑裂与防护.md)） |
| 跨地域延迟 | 每次决策多一个 RTT | 分片 / 单元化，把决策拉到本地 |
| 热点 | 某个 key 打满单点 | 拆 key、加本地缓存、读写分离 |

## 非集中式的账：收敛是概率，冲突是常态

非集中式没有单点，但有三个必须接受的事实：

1. **收敛需要时间**：gossip 的传播是 `O(log N)` 轮（见 [18.1 复制模型](../../L1-分布式原理/18-数据复制/18.1-复制模型-单主-多主-无主.md)），“最终一致” 的 “最终” 是一个分布，不是一个时刻；
2. **冲突必须有人解决**：LWW 会静默丢写，CRDT 只适用于特定结构，业务规则需要逐场景设计；
3. **观测困难**：没有全局日志，只能逐节点看视图，排障从 “查一条链路” 变成 “对 N 份状态”。

冲突不是 “偶发 bug”，是可以算出来的：

| 并发决策的调度器数 `k` | 一轮内至少一次冲突的概率（`λ=10/s, τ=5ms`） |
|---|---|
| 2 | 9.5% |
| 4 | 45.1% |
| 8 | **93.9%** |
| 16 | ≈ 100% |

> 🔑 冲突率随 `k²` 增长：**乐观并发能救正确性，但救不了吞吐**——冲突重试吃掉的那部分容量，就是非集中式为 “无单点” 付的钱。

```go
// k 个调度器、状态变更率 λ、决策窗口 τ：一轮内至少一次冲突的概率
func conflictProb(k int, lambda, tau float64) float64 {
	pairs := float64(k * (k - 1) / 2)       // 两两组合数，k² 量级
	p := 1 - math.Exp(-2*lambda*tau)        // 每一对在窗口内撞车的概率
	return 1 - math.Pow(1-p, pairs)         // 至少一对撞车
}
```

## 混合形态：三种折中，各有各的漏

| 折中 | 做法 | 数字上的代价 |
|---|---|---|
| **分片多主** | 把数据切成 `N` 片，每片一个 “小集中式” | 吞吐线性涨，跨分片事务比例 `1-1/N` 同步涨 |
| **两层调度** | 分配器给 offer，框架自己决定用不用 | offer 在思考期间过期：`1-e^(-λτ)` |
| **共享状态** | 多个调度器基于同一份状态快照乐观并发 | 冲突随 `k²` 涨，重试放大延迟 |

分片的账最容易被低估：

| 分片数 `N` | 总吞吐（相对） | 单分片负载 | 跨分片比例 |
|---|---|---|---|
| 1 | 1.0 | 1.00 | 0 |
| 2 | 2.0 | 0.50 | 50% |
| 4 | 4.0 | 0.25 | 75% |
| 8 | 8.0 | 0.12 | 88% |
| 16 | 16.0 | 0.06 | 94% |

吞吐确实线性涨，但**跨分片操作的比例也同步涨**。当 `N=16` 时，94% 的随机操作要跨片，跨片就要分布式事务或两阶段提交（见 [24.2 2PC 与恢复协议](../../L1-分布式原理/24-分布式事务/24.2-2PC与恢复协议.md)）——分片键设计得好，这个比例才会显著低于 `1-1/N`。

完整数字在仓库 [tools/examples/12.7-controlplane/](../../../tools/examples/12.7-controlplane/README.md)，`go run .` 可复现。

本机实测（macOS，Apple M1，Go 1.27.1）：

```text
=== 两层调度：offer 过期率 = 1 - e^(-λτ) ===
状态变化λ/s    τ=0.5s   τ=1s       τ=2s       τ=5s
1          0.39     0.63       0.86       0.99
5          0.92     0.99       1.00       1.00
10         0.99     1.00       1.00       1.00
20         1.00     1.00       1.00       1.00
→ 1 次/秒的变更、思考 2 秒，86% 的 offer 到手就过期；10 次/秒时几乎必然过期
```

## 怎么选：三问定形态

| 你的情况 | 选什么 | 理由 |
|---|---|---|
| 集群 < 100 节点、变更低频、要强一致 | 集中式（etcd / ZooKeeper） | 无冲突，排障简单，成本最低 |
| 多地域、写必须本地完成 | 分片多主 / 单元化（见 [36.5 单元化 Set 化架构](../../L3-质量属性/36-灾备/36.5-单元化-Set化架构.md)） | 把决策拉回本地，跨域只做异步复制 |
| 调度频率高、状态变化快 | 共享状态 + 乐观并发 | 串行决策的吞吐上限顶不住 |
| 冲突可合并（计数、集合、点赞） | CRDT + gossip | 无需协调，天然收敛 |
| 跨分片事务占比高 | **先改分片键**，别加协调者 | 协调者会把分片收益吃回去 |
| 团队没有分布式运维经验 | 集中式 + 托管服务 | 非集中式的排障成本被严重低估 |

> 💡 判断 “能不能非集中式”，只问一句：**这个决策能不能只看本地状态就做对？** 能（如 “本节点接不接受这个 Pod”），就本地决定；不能（如 “全局唯一 ID 分配”），就需要一个协调点，只是可以按 ID 段分片。

## 反模式

| 反模式 | 后果 |
|---|---|
| 单 master 跑满 90% 利用率还加只读副本 | 写路径依旧排队，延迟雪崩 |
| 把 “无中心” 当成 “无协调” | 冲突解决、成员管理、时钟问题一个都没少 |
| 分片后不设计分片键，随机打散 | 跨分片比例逼近 `1-1/N`，事务成本吃光收益 |
| 用 gossip 做 “强一致配置” | 收敛有窗口，读到旧配置是常态 |
| 乐观并发不设重试上限 | 冲突风暴下重试放大流量，打挂下游 |
| 混合形态两套一致性模型混用 | 一半服务强一致、一半最终一致，故障时互相甩锅 |
| 只看吞吐选形态，不看故障域 | 一个 AZ 挂掉，集中式控制面全灭 |

## 自检

**Q1** 为什么集中式的利用率到 90% 比 “挂掉” 更危险？

▸ 答案：M/M/1 下利用率 90% 时平均延迟已是空载的 10 倍，超时触发重试，重试抬高利用率，形成正反馈，最终雪崩；挂掉至少是确定的失败。

**Q2** 两层调度的 offer 为什么会过期？用哪两个参数估算过期率？

▸ 答案：分配器把资源报价给框架后，集群状态仍在变（别的框架抢占、节点故障）；框架思考时间 `τ` 内状态变更率 `λ` 越高，过期率 `1-e^(-λτ)` 越大。

**Q3** 为什么共享状态的冲突率随调度器数量平方增长？

▸ 答案：冲突发生在 “两两之间”，`k` 个调度器有 `k(k-1)/2` 对；每对在决策窗口内至少一次状态变更的概率固定时，至少一对冲突的概率随对数增长，近似 `k²`。

**Q4** 分片把吞吐从 1 提到 16，为什么不一定划算？

▸ 答案：跨分片操作比例同步涨到 94%，跨片需要分布式事务或协调，延迟与失败率上升；只有分片键让大多数操作落在单片的系统才真正拿到线性收益。

**Q5** 什么情况下 “非集中式” 是错的？

▸ 答案：决策需要全局不变量（全局唯一、全局配额、强一致配置）时；此时要么保留协调点，要么接受 “按段分片 + 段内集中”。

**Q6** 集中式控制面怎么做高可用，又不引入双主？

▸ 答案：多副本 + 共识选主（Raft/ZAB），写只走 leader；租约 + fencing token 防止旧主继续发号施令。
