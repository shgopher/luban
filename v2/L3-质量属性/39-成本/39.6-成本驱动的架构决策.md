# 39.6 成本驱动的架构决策

## 一句话

> 成本驱动的架构决策不是「选便宜的方案」，而是**把成本折成单位成本与 TCO，和延迟、可用性、复杂度放进同一张表里比**——只有当「省下的年化金额」大于「迁移成本 + 复杂度利息 + 风险」时，才值得为成本改架构。

## 收口：成本怎么进入架构决策

成本这件事，[39.1](39.1-成本模型与单位经济.md)–[39.5](39.5-FinOps与账单治理.md) 各管一段，最后都要落到一次架构决策上：

| 已经算清的 | 在哪 | 在决策里怎么用 |
|---|---|---|
| 单位成本与规模效应 | [39.1 成本模型与单位经济](39.1-成本模型与单位经济.md) | 判断「贵不贵」的基准 |
| 容量买多满、超配与欠配 | [39.2 容量规划](39.2-容量规划.md) | 决定容量是成本项还是风险项 |
| 存储分层 | [39.3 存储分级](39.3-存储分级.md) | 冷数据换层 vs 删除 |
| 承诺与弹性 | [39.4 弹性与预留实例](39.4-弹性与预留实例.md) | 确定性折价买多少 |
| 账单归因与预算 | [39.5 FinOps 与账单治理](39.5-FinOps与账单治理.md) | 判断这笔钱该由谁、按什么口径负责 |
| **成本作为架构约束参与选型** | **本节** | 改不改架构、改哪一层 |

## 四个误区，先拆掉

| 误区 | 现实 |
|---|---|
| 成本是运维的事，架构只管性能 | 每一个架构选择都在定价：副本数、分片数、缓存层数、是否多活、实时还是批处理。**架构决定成本的结构，运维只能决定它的价格。** |
| 云上按量计费就便宜 | 按量是「没买承诺」的证据，不是便宜的证据。规模上来后，按量与承诺的差价会变成单位成本里最稳定的一块 |
| 为省 10% 加一层缓存/中间件 | 省下的是线性项，引入的是**复杂度利息**：一套组件 = 部署 + 监控 + 值班 + 一致性 bug + 升级。多数时候利息高于省下的钱 |
| 降本就要改架构 | 顺序是先删需求、再压线性项、再摊薄固定项，最后才动架构（[39.1 成本模型与单位经济](39.1-成本模型与单位经济.md)）；反着做通常花了钱没降本 |

## 决策框架：四步，缺一步就是拍脑袋

| 步 | 做什么 | 产出 | 常见错误 |
|---|---|---|---|
| ① 量化基线 | 当前单位成本（每单/每千请求）、成本结构（固定/阶梯/线性占比）、增长曲线 | 一个可对比的数 | 拿总账单当基线（无法判断效率） |
| ② 列全生命周期成本 | 资源 + 人力 + 一次性 + 风险 + 复杂度，许可/合规/退出成本按 [4.2 成本-收益分析](../../需求/4-技术决策与ROI/4.2-成本-收益分析.md) 的 TCO 六层清单补齐 | 各方案的成本项清单 | 漏人力、迁移与退出成本，只比机器价 |
| ③ 折成年化 / TCO 与不可量化项并列 | 折现、摊销、敏感度（折现与敏感度口径见 [4.2 成本-收益分析](../../需求/4-技术决策与ROI/4.2-成本-收益分析.md)） | 一张决策表 | 把「便宜」当唯一列，忽略延迟与锁定 |
| ④ 设可回退的里程碑 | POC 指标、退出条件、复查日期 | 一份 ADR | 一次性全量切换，错了退不回来 |

成本项清单（第 ② 步的检查表），少一项结论就会偏：

| 成本项 | 例子 | 最容易漏 |
|---|---|---|
| 资源 | 实例、存储、网络出口、请求费 | 网络与请求费 |
| 人力 | 建设、运维、值班、培训 | 值班与培训（经验值：0.1–0.5 FTE） |
| 一次性 | 迁移、双跑、数据校验 | 双跑期（经验值 1–3 个月） |
| 风险 | 故障损失 × 概率、SLO 违约赔付 | 概率被估成 0 |
| 复杂度 | 多一套组件、多一种故障模式、多一层排查 | 排障时间 |
| **许可与合规** | 商业软件许可、等保/审计 | 合规是强制项，往往一次性 + 每年复检 |
| **退出成本** | 数据迁出、流量费、自建成本的一部分 | 「哪天想走」的代价常年不在表里（见 [5.7 云厂商锁定与迁移](../../L0-运行时底座/5-云计算基础/5.7-云厂商锁定与迁移.md)） |

## 七个架构决策的成本账

下表是「成本视角」的速查表——**它不替代各专题的完整论证，只回答「这一刀大概值多少钱、代价是什么」**：

| 决策 | 默认/常见做法 | 成本更优的选择 | 量级 | 代价与判据 |
|---|---|---|---|---|
| 单体 vs 微服务 | 按团队/领域拆成一堆微服务 | 模块化单体，到发布瓶颈再拆 | 每多一个服务约 +1,200 元/月固定分摊（示例），20 个服务每年 +28.8 万，另加平台人力 | 团队规模与发布频率是唯一判据，见 [33.2 微服务部署](../../L2-架构风格/33-部署形态/33.2-微服务部署.md) |
| 单库 vs 分库分表 | 数据一大就分片 | 先索引、归档、读写分离、分区表 | 分片后运维与一致性成本上升，单均成本不降反升 | 分片是最后手段，见 [44.14 分库分表](../../L4-组件与技术/44-数据库/44.14-分库分表.md) |
| 自建 vs 托管 | 自建「可控、便宜」 | 资源规模小于约 8 台等效时，托管更省 | 示例 3 年 TCO：自建 102.5 万 vs 托管 67.7 万（+51%） | 规模门槛约 8 台等效资源；人力是主变量 |
| 加不加缓存 | 有性能问题就加一层缓存 | 先算「省下的 DB 容量」是否大于「中间件资源费 + 一致性成本」 | 多数情况下两者打平，靠命中率才能拉开 | 一致性 bug 的排查成本常被低估，判据见本节误区表 |
| 单活 vs 多活 | 为「高可用」上多活 | 按 SLO 倒推，别为「越稳越好」买单 | 跨 3 AZ 容量约 ×1.5、两地三中心约 ×3（容量系数见 [57.3 冗余系数](../../L5-工程效能/57-容量与成本治理/57.3-冗余系数.md)） | 判据是 SLO 与 RTO/RPO，见 [36.4 两地三中心与多活](../36-灾备/36.4-两地三中心与多活.md) |
| 热存 vs 分层 | 全部放热层 | 冷数据下沉，但要算取回费 | 存储费降 40%–70%（示例 64%） | 取回费会改写结论，见 [39.3 存储分级](39.3-存储分级.md) |
| 实时 vs 批处理 | 所有链路都做实时 | 能批就批，实时只留给真正需要的链路 | 实时链路的资源与运维成本通常是批处理的数倍 | 判据是业务对「延迟」的真实需求，不是技术偏好 |

> 🔑 这张表只有一个用法：**先看你的成本结构落在哪一行，再决定动哪一刀**。成本 80% 在出口流量的业务，去优化数据库分片是白忙；成本 80% 在计算且利用率只有 25% 的业务，去加缓存也是白忙。

## 算一遍 TCO：自建、托管、按量

以「消息队列」这类自建/托管都成立的组件为例，示例参数如下（单价为演示口径，不是报价）：自建 3 台 8C32G（2,400 元/台·月）+ 3 TB SSD（500 元/TB·月）+ 0.5 FTE + 监控；托管按资源 1.8 倍溢价 + 0.1 FTE；按量托管 22,000 元/月用量 + 0.05 FTE。

```go
package main

import (
	"fmt"
	"math"
)

// 单实例折算：自建消息队列 vs 托管服务 vs 按量托管。示例参数，用于演示口径。
type option struct {
	name     string
	oneTime  float64 // 一次性投入（建设、迁移、培训）
	monthly  float64 // 月度运营成本（资源 + 人力 + 工具）
	riskPerM float64 // 每月期望风险成本（故障损失 × 概率）
}

func pvMonthly(monthly float64, months int, annualRate float64) float64 {
	r := annualRate / 12
	af := (1 - math.Pow(1+r, -float64(months))) / r // 年金现值系数
	return monthly * af
}

func main() {
	const (
		months     = 36
		annualRate = 0.08
	)

	// 自建：3 台 8C32G（2400 元/台·月）+ 3TB SSD（500 元/TB·月）+ 0.5 FTE + 监控
	selfMonthly := 3*2400 + 3*500 + 0.5*35000 + 800
	// 托管：资源按 1.8 倍溢价，人力 0.1 FTE
	managedMonthly := 1.8*(3*2400+3*500) + 0.1*35000
	// 按量托管：忙时用量计费，人力 0.05 FTE
	serverlessMonthly := 22000 + 0.05*35000

	opts := []option{
		{"自建（IaaS 上自己运维）", 30500, selfMonthly, 4167}, // 30,500 = 15 人日 × 2,000 元/人日 + 培训；4,167 = 年故障期望损失 5 万 ÷ 12
		{"全托管服务", 40000, managedMonthly, 800},            // 40,000 = 迁移 + 双跑一个月；风险 800/月为示例
		{"按量托管（Serverless）", 5000, serverlessMonthly, 1200}, // 5,000 = 初期接入，风险略高于全托管
	}

	fmt.Println("=== 一、三年 TCO：一次性 + 月成本折现 + 风险成本 ===")
	fmt.Printf("折现率 %.0f%%/年，36 个月年金现值系数 %.2f\n\n", annualRate*100, pvMonthly(1, months, annualRate))
	fmt.Printf("%-26s %10s %10s %12s %10s %s\n", "方案", "一次性", "月运营", "风险/月", "三年TCO", "相对最省")
	var best, bestCost float64 = 0, math.Inf(1)
	for i, o := range opts {
		tco := o.oneTime + pvMonthly(o.monthly+o.riskPerM, months, annualRate)
		fmt.Printf("%-26s %10.0f %10.0f %12.0f %10.0f\n", o.name, o.oneTime, o.monthly, o.riskPerM, tco)
		if tco < bestCost {
			bestCost, best = tco, float64(i)
		}
	}
	for _, o := range opts {
		tco := o.oneTime + pvMonthly(o.monthly+o.riskPerM, months, annualRate)
		fmt.Printf("  %-26s 比最省方案多 %+.0f 元（%+.0f%%）\n", o.name, tco-bestCost, (tco/bestCost-1)*100)
	}
	fmt.Printf("→ 最省：%s\n", opts[int(best)].name)

	fmt.Println("\n=== 二、结论对哪个假设最敏感 ===")
	fmt.Printf("%-18s %-14s %-14s %-14s %s\n", "假设变化", "自建TCO", "托管TCO", "差额", "仍选托管?")
	type sens struct{ name string; selfM, managedM float64 }
	for _, s := range []sens{
		{"基准", selfMonthly, managedMonthly},
		{"人力单价 -50%", 3*2400 + 3*500 + 0.5*17500 + 800, 1.8*(3*2400+3*500) + 0.1*17500},
		{"人力单价 +50%", 3*2400 + 3*500 + 0.5*52500 + 800, 1.8*(3*2400+3*500) + 0.1*52500},
		{"托管溢价 1.5 倍", selfMonthly, 1.5*(3*2400+3*500) + 0.1*35000},
		{"托管溢价 2.5 倍", selfMonthly, 2.5*(3*2400+3*500) + 0.1*35000},
		{"运维人力降到 0.2 FTE", 3*2400 + 3*500 + 0.2*35000 + 800, managedMonthly},
	} {
		selfTCO := 30500 + pvMonthly(s.selfM+4167, months, annualRate)
		manTCO := 40000 + pvMonthly(s.managedM+800, months, annualRate)
		pick := "是"
		if selfTCO < manTCO {
			pick = "否，自建更省"
		}
		fmt.Printf("%-18s %-14.0f %-14.0f %+14.0f %s\n", s.name, selfTCO, manTCO, selfTCO-manTCO, pick)
	}

	fmt.Println("\n=== 三、多拆一个微服务的固定成本 ===")
	perService := 1200.0 // 网关/注册/监控/值班/CI 的月分摊（示例）
	fmt.Printf("每个服务每月固定分摊 %.0f 元 → 每年 %.0f 元；拆 20 个服务每年多 %.0f 元\n",
		perService, perService*12, perService*12*20)
	fmt.Printf("若为此多养 0.5 FTE 平台团队（%.0f 元/月），每年再加 %.0f 元\n", 0.5*35000, 0.5*35000*12)
	fmt.Printf("对照：单体的发布效率收益通常要“每周多发布 N 次 × 每次事故损失减少”才摊得平\n\n")

	fmt.Println("=== 四、规模门槛：多少台等效资源时自建才开始更省 ===")
	selfFixed := 0.5*35000 + 800 + 4167 // 人力 + 工具 + 风险
	manFixed := 0.1*35000 + 800
	selfPer, manPer := 2400.0+500.0, 1.8*(2400.0+500.0)
	selfOne, manOne := 30500.0, 40000.0
	// 把一次性差额摊进 36 个月
	amort := (selfOne - manOne) / pvMonthly(1, months, annualRate)
	be := (manFixed - selfFixed + amort) / (selfPer - manPer)
	fmt.Printf("自建：固定 %.0f 元/月 + %.0f 元/台·月；托管：固定 %.0f 元/月 + %.0f 元/台·月\n", selfFixed, selfPer, manFixed, manPer)
	fmt.Printf("规模门槛：约 %.1f 台等效资源。低于它自建更贵，高于它自建才开始摊薄人力\n", be)
	fmt.Printf("%-8s %-14s %-14s %s\n", "规模", "自建/月", "托管/月", "更省")
	for _, n := range []float64{3, 5, 8, 20, 50, 100} {
		selfM := selfFixed + selfPer*n
		manM := manFixed + manPer*n
		pick := "托管"
		if selfM < manM {
			pick = "自建"
		}
		fmt.Printf("%-8.0f %-14.0f %-14.0f %s\n", n, selfM, manM, pick)
	}
}
```

逐条读这份输出：

1. **自建贵 51%，贵的不是机器，是人力与风险**。自建月运营 27,000 元里，0.5 FTE（17,500）占 65%；再加每月 4,167 元的期望故障成本。这正是「自建便宜」最常见的漏项：**只算了资源，没算人。**
2. **敏感度分析比结论更重要**。人力单价 ±50%、托管溢价 1.5–2.5 倍，结论都不变；只有「运维人力降到 0.2 FTE」时差距才收窄到 13,062 元。**所以决策的关键不是「托管贵不贵」，是「你到底要投多少人力」**——如果团队本来就有闲置运维、且规模够大，自建才可能翻盘。
3. **规模门槛约 8 台等效资源**。低于 8 台，自建一定更贵（固定人力摊不开）；高于它，自建开始有优势。**小团队自建的真正成本不是资源，是「用不起专职运维，只能让开发兼职」**——那部分成本通常不写在预算里。
4. **多拆一个服务是有固定成本的**。每服务约 1,200 元/月固定分摊，20 个服务每年 28.8 万，再叠加 0.5 FTE 平台团队 21 万/年。**微服务化的成本账必须先算出这个数，再谈「发布效率收益」能不能覆盖。**

> ⚠️ 上表的「一次性」只含建设与迁移，不含组织学习成本（培训、排障习惯、值班流程）。**这类成本往往是资源成本的 1–2 倍，但几乎不会被写进任何 TCO 表**——写决策文档时至少单列一行「组织成本（估）」。

## 决策表：你的情况该动哪一刀

| 你的情况 | 该做什么 | 别做什么 |
|---|---|---|
| 单位成本占收入 < 2%（经验线）且增长可控 | 做低垂果实：删闲置、降规格、关非生产（[5.6 云成本结构](../../L0-运行时底座/5-云计算基础/5.6-云成本结构.md)） | 为省 2% 重构架构 |
| 成本主要在线性项（出口流量、日志、请求费） | 压单价：CDN、压缩、采样、协议优化 | 加缓存/换数据库（动不到线性项） |
| 固定项占比高、规模还小 | 摊薄：合并服务、共享集群、提高密度 | 分片/多活（先把固定项用满） |
| 线性项压到头、单库确实到瓶颈 | 才考虑分库分表、读写分离（[44.14 分库分表](../../L4-组件与技术/44-数据库/44.14-分库分表.md)） | 一上来就分片 |
| 团队 < 10 人、无专职运维 | 托管优先（本节规模门槛约 8 台） | 自建中间件「为了可控」 |
| SLO 已达标、成本可接受 | **不改也是决策**：写进 ADR，标复查日期 | 为了「降本 KPI」硬改 |

> 🔑 「不改架构」是一个需要被记录的决策，不是不作为。它的判据是：**预计省下的钱 < 迁移成本 + 复杂度利息 + 风险，或成本占收入比已经低到不值得投入工程时间。** 不写下来，下个季度还会有人重新提一遍。

## ADR 里的成本项模板

任何因成本而起的架构变更，决策记录里至少要有这六行：

| 字段 | 示例 | 作用 |
|---|---|---|
| 成本基线 | 当前 20,000 元/月，单位成本 0.40 元/单 | 变更前的对照 |
| 变更后预估 | 16,000 元/月，单位成本 0.32 元/单（月省 4,000） | 要有算式，不是「大约省 20%」 |
| 一次性投入 | 迁移 30,000 + 双跑 10,000 | 回本周期 = 40,000 ÷ 4,000 = 10 个月 |
| 敏感度 | 人力 ±50%、单价 ±30% 时结论是否翻转 | 暴露最脆弱的假设 |
| 不可量化代价 | 多一套组件、值班多一类故障、锁定加深 | 写出来才能被权衡 |
| 复查日期与退出条件 | 3 个月后看单位成本；若延迟 P99 +20% 则回滚 | 决策要有「撤回键」 |

**回本周期的判据（经验值）**：`一次性投入 ÷ 月省金额 < 12 个月` → 直接做；12–24 个月 → 必须写 ADR 并设复查点，因为「省的钱还没回来，前提可能已经变了」；> 24 个月 → 不做。**这三个档位是经验起点，不是公式推导出来的真理**——用它逼出「你到底凭什么认为这笔投入值得」。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只比机器价，不算人力与风险 | 自建「便宜」的结论通常是漏了 0.5 FTE 与故障成本（示例差 51%） |
| 为省 10% 加一层中间件 | 复杂度利息（部署/监控/值班/一致性）高于省下的钱 |
| 没到瓶颈就分库分表 | 换来跨分片查询、分布式事务、扩容迁移三笔长期债 |
| 用「高可用」当多活的理由 | 每加一层拓扑成本约 ×1.5–3，而 SLO 可能只需要 N+1（容量系数见 [57.3 冗余系数](../../L5-工程效能/57-容量与成本治理/57.3-冗余系数.md)） |
| 成本占比很低还大动架构 | 投入几个月，省下的钱抵不上一次发布的工时（经验线：单位成本占收入 < 2% 时先别动架构） |
| 改完不记 ADR、不设复查 | 半年后没人知道当初为什么改，也没人敢改回去 |
| 把「优化 KPI」当目标 | 数字好看、系统变差；必须配质量反指标（[39.5 FinOps 与账单治理](39.5-FinOps与账单治理.md)） |

## 自检

**Q1** 自建方案「机器更便宜、还可控」，为什么三年 TCO 反而贵 51%？哪一项是决定性的？

▸ 答案：因为资源只是成本的一部分：自建月运营 27,000 元里 0.5 FTE 人力占 65%（17,500 元/月），再加每月 4,167 元期望故障成本；托管把这两项都摊薄了（0.1 FTE、800 元/月风险）。敏感度分析显示：人力单价 ±50%、托管溢价 1.5–2.5 倍都不翻转结论，**只有运维人力降到 0.2 FTE 才接近持平**——所以决定性变量是「你要投入多少人力」，不是机器单价。

**Q2** 规模门槛「约 8 台等效资源」是怎么算出来的？它对小团队意味着什么？

▸ 答案：令自建月成本 = 托管月成本：`固定人力+工具+风险 + 单台成本 × n` 与 `托管固定 + 托管单价 × n` 相交，解出 n ≈ 8（把一次性差额摊进 36 个月后）。含义是：**低于 8 台等效资源，自建的固定人力摊不开，一定更贵**；小团队自建的真实成本是「用不起专职运维，只能让开发兼职」，那部分通常不写进预算。**规模不够时，托管不是贵，是把固定成本变成可变成本。**

**Q3** 一个团队成本 80% 花在出口流量上，他们决定「加一层缓存 + 换更快的数据库」。这个决策错在哪？

▸ 答案：错在**动的层与成本结构不匹配**：出口流量是线性成本项（按 GB 计），加缓存和换数据库优化的是计算与存储，动不到流量的计价基础。正确的顺序是：先压流量单价（CDN 回源率、压缩、编码优化），再压流量总量（缓存命中率、按需加载、边缘缓存），最后才看计算。判据是 [39.1 成本模型与单位经济](39.1-成本模型与单位经济.md) 的成本结构分类——**先确定钱花在哪一类成本上，再决定动哪一刀。**

**Q4** 什么时候「不改架构」才是正确决策？给出三个判据。

▸ 答案：① **成本占比低**：单位成本占收入 < 2%（或成本项本身很小），投入的工程时间远超省下的钱；② **不划算**：`一次性投入 ÷ 月省 > 12–24 个月`，回本周期长过业务与架构的稳定期；③ **风险/复杂度不划算**：省下的钱 < 迁移成本 + 复杂度利息 + 故障风险，尤其当 SLO 已达标时。**「不改」必须写进 ADR 并标复查日期**，否则下个季度会被重新提一遍。

**Q5** 为什么「为省成本加一层中间件」经常是负收益？用什么方式把它量化出来？

▸ 答案：因为中间件成本有两部分：显性的资源费（通常不大）+ **隐性的复杂度利息**——部署、监控、值班、升级、一致性 bug、多一种故障模式、排障时间变长。量化方式：把「多一套组件的年化运维人力（按 0.1–0.2 FTE 估）+ 故障风险期望 + 迁移一次性」加进 TCO，再和「它省下的资源费」比。多数情况下省下的是线性项的一部分，而利息是持续的固定项——**线性收益换固定成本，是架构决策里最典型的一笔亏本买卖。**
