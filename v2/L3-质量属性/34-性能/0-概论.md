## 5 分钟入门：先记住这 7 个词

| 词 | 一句话解释 | 生活类比 |
|---|---|---|
| **延迟** | 请求从发出到收到响应用了多久 | 外卖下单到敲门 |
| **吞吐** | 单位时间处理完的请求数 | 奶茶店一小时出多少杯 |
| **P99** | 按耗时排队后第 99 个的耗时 | 100 人体检，第 99 位等多久 |
| **利用率** | 资源有多少时间在忙；过 70% 延迟就暴涨 | 一条车道几成时间是满的 |
| **利特尔法则** | 在途请求数 = 到达速率 × 停留时间 | 店里同时在吃的人 = 每小时进店人数 × 吃多久 |
| **开环 / 闭环** | 按固定速率发，还是按固定并发发 | 按时刻表发车，还是坐满才发车 |
| **多级分流** | 到最慢单点前，被一层层便宜地挡掉 | 小区门、单元门、电梯口 |

## 3 个最常见误解

| 误区 | 现实 |
|---|---|
| 「平均延迟达标就说明快」 | 97 个 20ms 加 3 个 500ms，平均 34.4ms 很漂亮，P99 是 500ms |
| 「优化手段能上的都上」 | 手段按瓶颈类别查表；没定位就上，等于优化了不忙的资源 |
| 「压测工具越强，容量越可信」 | 取决于负载模型；闭环压测在系统变慢时自动降速，删掉没发出去的请求 |

## 读完自检（入门级 3 题）

**Q1** 一个接口平均 20ms、P99 800ms，问题出在哪，下一步先做什么？
▸ 答案：平均只说明多数请求快，800ms 是那 1% 的长等。下一步不是加机器：先算对分位数（样本够、别混接口），再按 [34.2](34.2-性能建模.md) 找先饱和的资源，最后按 [34.3](34.3-性能分析方法.md) 归因到函数。

**Q2** 只压测不建模，最容易犯什么错？
▸ 答案：把一次压测的数字当成容量上限。建模先给理论上限和瓶颈方向，压测只给真实数字；模型不像真流量或闭环压测，容量都会偏高。

**Q3** 缓存、异步、批处理都能提速，为什么不能一起上？
▸ 答案：它们分别对应重复计算、等待、往返、固定开销、扫描、串行这几类瓶颈。没定位就一起上，可能优化了不忙的资源。
