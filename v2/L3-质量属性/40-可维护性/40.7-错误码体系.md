# 40.7 错误码体系：把错误变成可依赖的契约

## 一句话

> 错误码不是"给错误起名字"，而是三条同时成立的承诺：**机器能分支的稳定标识、人看得懂的文案、不随实现变化的 HTTP 语义**——三者混成一条字符串，客户端就只能猜，猜错的每一次都是线上告警。

> 来源：三个真实 Go 项目的实现——fastgo 的 `internal/pkg/errorsx`（三字段 `ErrorX`）、iam 的 `internal/pkg/code`（整数分段码 + `codegen` 生成码表）、onex 的 HTTP 层（kratos errors）与控制器层（K8s 风格 Status 错误）。对比、取舍与可运行验证为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| "错误码就是 HTTP 状态码" | 一个 400 背后可能有"用户名非法 / 密码错 / 参数缺失"十几种原因，客户端无法靠 400 决定是重填还是换账号 |
| "错误信息给人看，码给机器看，两者可以混" | 混用后文案一改，客户端的字符串匹配就全断；文案是"可变字段"，码是"兼容性资产" |
| "码越细越好" | 码发出去就删不掉：每加一个码都是一份长期兼容承诺。判据是**客户端要不要分支**，不是内部异常有多少种 |
| "统一错误码 = 一个 const 列表" | 缺了包装、边界渲染、码表文档与生成，最后每个 handler 自己拼 HTTP 状态，列表形同虚设 |
| "错误码只影响前端提示" | 码还决定重试策略、告警聚合维度、审计口径；它是客户端、网关、监控三方共用的契约 |

## 一个错误码由四个字段定死

| 字段 | 例子 | 谁消费 | 能不能改 |
|---|---|---|---|
| **稳定标识**（数值码或 `Reason`） | iam：`110001`；fastgo：`NotFound.UserNotFound` | 客户端分支、监控聚合、告警 | **不能改**（只增不减，不复用） |
| **HTTP 状态** | 404 / 400 / 500 | 网关、重试中间件、通用 SDK | 一个标识只能对应一个状态 |
| **用户文案** | `User not found.` | 前端展示、客服话术 | 可以改（改文案不改码） |
| **参考文档 / 追踪 ID** | iam 的 `Ref` 字段、日志里的 `trace_id` | 排查、对账、工单 | 随版本演进 |

> 🔑 **判据只有一条：客户端拿到它，能不能不猜就决定下一步。** 能，四个字段就够；不能，说明缺的是"语义"而不是"更多码"。

## 三种流派：同一件事的三种落地

| 维度 | iam（整数分段码） | fastgo（三字段 ErrorX） | onex（kratos errors + 资源状态） |
|---|---|---|---|
| 标识形态 | 6 位整数，`1xxxxx` 公共、`11xxxx` 业务模块 | `Reason` 层级串，如 `InvalidArgument.UsernameInvalid` | HTTP 层用 kratos `errors`（code+reason+message+metadata） |
| HTTP 映射 | `ErrCode{C, HTTP, Ext, Ref}`，`HTTPStatus()` 兜底 500 | `ErrorX.Code` 直接就是 HTTP 状态码 | `errors.Code(err)` 直接作为响应状态 |
| 文案 | 生成器从注释 `// - 404: User not found.` 里取 | `Message` 字段，可 `WithMessage` 覆盖 | `Message` 字段 + `pkg/i18n` 做多语言 |
| 码表文档 | `codegen -doc` 生成 `docs/.../error_code_generated.md` | 无生成，靠 `errorsx` 目录内约定 | 无独立码表 |
| 资源状态错误 | 不涉及 | 不涉及 | 控制器用 `MinerStatusError` 字符串写进 `status.failureReason`（K8s 风格），与 HTTP 码是两套 |
| 适合 | 多模块、多团队、要对外承诺码表 | 小团队、单服务、快速起步 | 云原生、已有 kratos/K8s 生态 |

三种写法殊途同归：**标识（机器）与文案（人）必须分离**，HTTP 状态是标识的映射而不是标识本身。

## 编号：分段 + 只增不改

iam 的码表是"段位制"：`internal/pkg/code` 下 27 个错误码，按 7 个段位分配（实测统计）：

| 段位 | 含义 | 例子 |
|---|---|---|
| `100001` 起 | 公共基础错误 | `ErrSuccess`(200)、`ErrUnknown`(500)、`ErrBind`(400) |
| `100101` 起 | 数据库 | `ErrDatabase`(500) |
| `100201` 起 | 认证鉴权 | `ErrSignatureInvalid`(401)、`ErrPasswordIncorrect`(401) |
| `100301` 起 | 编解码 | `ErrInvalidJSON`(500)、`ErrEncodingYaml`(500) |
| `110001` 起 | 用户模块 | `ErrUserNotFound`(404)、`ErrUserAlreadyExist`(400) |
| `110101` 起 | 密钥模块 | `ErrReachMaxCount`(400)、`ErrSecretNotFound`(404) |
| `110201` 起 | 策略模块 | `ErrPolicyNotFound`(404) |

fastgo 走另一条路：13 个预定义错误（`errorsx/code.go` 8 个 + `user.go` 4 个 + `post.go` 1 个），`Reason` 用 `类.原因` 的两段式：

```go
ErrUserNotFound = &ErrorX{Code: 404, Reason: "NotFound.UserNotFound", Message: "User not found."}
ErrBind         = &ErrorX{Code: 400, Reason: "BindError", Message: "..."}
```

两条路都遵守同一条铁律：

| 规则 | 违反的后果 |
|---|---|
| 码/Reason **只增不改**，已上线的含义永不重用 | 老客户端按旧码分支，改含义=静默错乱 |
| 一个模块一个段位，新模块先申请段位 | 码撞车后只能靠文案区分，等于没有码 |
| 文案随版本改，码不随文案改 | 前端把文案当码用，改一次文案全线崩 |
| 删除的码不能再分配给别人 | 灰度期间新旧版本并存，同一码两种含义 |

## 错误链：别把底层错误换成字符串

错误从数据库一路走到 HTTP 响应，要经过四层，每层职责不同：

| 层 | 该加什么 | 不该加什么 |
|---|---|---|
| store | 操作上下文：表名、SQL 动作（`%w` 包装） | 面向用户的文案 |
| biz | 业务判据：为什么拒绝（返回预定义 `ErrorX`） | HTTP 状态、JSON |
| handler | 参数绑定错误 → `ErrBind`（`errors.As` 取原错误） | 自己拼响应体 |
| 边界（响应函数） | 渲染状态码 + `Reason`/`Message`、打一条日志（含 cause） | 二次改写 message |

Go 1.13 之后，包装用 `%w`、判断用 `errors.Is/As`，`errors.As` 是"契约穿透分层"的关键：store 包得再深，`FromError` 依然能取到最外层的 `*ErrorX`。

```go
// 最小契约：提炼自 fastgo/internal/pkg/errorsx
type ErrorX struct {
	Code    int    `json:"code"`    // HTTP 状态码
	Reason  string `json:"reason"`  // 稳定业务码（客户端分支用）
	Message string `json:"message"` // 用户文案（可改）
	cause   error  // 底层原因：只进日志，不出响应
}

func FromError(err error) *ErrorX {
	if err == nil {
		return nil
	}
	var e *ErrorX
	if errors.As(err, &e) {
		return e
	}
	// 不认识的错误：固定 500 契约，绝不透传 err.Error()
	return &ErrorX{Code: 500, Reason: "InternalError", Message: "Internal server error."}
}

// render 是边界取 (status, body) 的唯一入口。
func render(err error) (int, map[string]string) {
	e := FromError(err)
	if e == nil {
		return 0, nil
	}
	return e.Code, map[string]string{"reason": e.Reason, "message": e.Message}
}

var (
	ErrUserNotFound  = &ErrorX{Code: 404, Reason: "NotFound.UserNotFound", Message: "User not found."}
	ErrPasswordWrong = &ErrorX{Code: 401, Reason: "Unauthenticated.PasswordIncorrect", Message: "Password is incorrect."}
)
```

> ⚠️ fastgo 原实现是 `New(ErrInternal.Code, ErrInternal.Reason, err.Error())`——把内部错误字符串塞进了 `Message` 返回给客户端。这是三个项目里唯一要"改掉再抄"的地方：数据库地址、SQL 片段会泄露，且文案每天在变。正确做法是固定 `Message`，把 `err.Error()` 留给日志。

## 边界只渲染一次，日志只打一次

渲染与打日志是两件事，但都必须**只做一次**：

```go
// 响应函数是唯一写 HTTP 错误的地方（结构同 fastgo/internal/pkg/core）
func WriteResponse(c *gin.Context, data any, err error) {
	if err != nil {
		errx := FromError(err)
		c.JSON(errx.Code, gin.H{"reason": errx.Reason, "message": errx.Message})
		return
	}
	c.JSON(200, data)
}
```

实测三条判据（前两条由下面的测试真实跑出，第三条是纪律）：

| 现象 | 正确行为 |
|---|---|
| `fmt.Errorf("query user: %w", ErrUserNotFound)` | 仍是 404 + `NotFound.UserNotFound`（穿透两层包装） |
| `errors.New("dial tcp 10.0.0.8:3306: connection refused")` | 500 + `InternalError`（内部细节不进响应） |
| 同一个错误在 biz 打了日志、handler 又打一条 | 日志里两条同错不同层，告警按错误数翻倍——**只允许边界打一条** |

## 可运行：把契约跑出来

把上面的最小实现（`ErrorX` + `FromError` + `render`，约 60 行）配一张表驱动测试，五个断言覆盖"直接返回、包装、401、未知错误、nil"；两段代码拼进一个 `package main`、补上 `errors`/`fmt`/`net/http` 三个 import 即可直接 `go test`：

```go
func TestContract(t *testing.T) {
	cases := []struct {
		name       string
		err        error
		wantStatus int
		wantReason string
	}{
		{"直接返回业务错误", ErrUserNotFound, 404, "NotFound.UserNotFound"},
		{"包装后仍是 404", fmt.Errorf("query user: %w", ErrUserNotFound), 404, "NotFound.UserNotFound"},
		{"未鉴权", ErrPasswordWrong, 401, "Unauthenticated.PasswordIncorrect"},
		{"未知错误不外泄内部信息", errors.New("dial tcp 10.0.0.8:3306: connection refused"), 500, "InternalError"},
	}
	for _, c := range cases {
		t.Run(c.name, func(t *testing.T) {
			status, body := render(c.err) // render = FromError + 取 (Code, Reason)
			if status != c.wantStatus || body["reason"] != c.wantReason {
				t.Fatalf("got (%d,%s), want (%d,%s)", status, body["reason"], c.wantStatus, c.wantReason)
			}
		})
	}
}

// 已发布的 reason 是兼容性资产：空、重复都算违约。
func TestReasonStability(t *testing.T) {
	seen := map[string]bool{}
	for _, e := range []*ErrorX{ErrInternal, ErrBind, ErrUserNotFound, ErrPasswordWrong} {
		if e.Reason == "" || seen[e.Reason] {
			t.Fatalf("reason 缺失或重复: %q", e.Reason)
		}
		seen[e.Reason] = true
	}
}
```

真实运行结果（Go 1.27.1，macOS/arm64）：

```text

=== RUN   TestContract/包装后仍是_404

    --- PASS: TestContract/直接返回业务错误 (0.00s)

    --- PASS: TestContract/未鉴权 (0.00s)
    --- PASS: TestContract/未知错误不外泄内部信息 (0.00s)
```

那张表里最值得记的是第二行：**包装一次，404 还在**。这就是"错误链 + 统一收口"的全部价值——分层不会把语义弄丢。

## 多语言：把文案从代码里赶出去

文案属于"界面层"，不属于业务层。onex 把它推到了终点：**业务层返回的不是文案，而是 message ID**。

```go
// 定义（onex/internal/usercenter/locales/locales.go）
RecordNotFound    = "record.not.found"
IncorrectPassword = "login.incorrect.password"

// 业务层只返回 ID，不拼字符串（onex/internal/usercenter/biz/auth/auth.go）
return nil, i18n.FromContext(ctx).E(locales.RecordNotFound)

// 翻译文件（locales/en.yaml）
// record.not.found: 'Record not found'
// 中间件按请求语言选择 bundle（internal/pkg/middleware/i18n 的 Translator）
```

三种做法的代价差一个量级：

| 维度 | 文案写死在代码里 | 码 + 文案字段（iam/fastgo） | 码 = message ID + 翻译文件（onex） |
|---|---|---|---|
| 新增一种语言 | 改所有代码 | 加一份码→文案映射 | 加一个 `xx.yaml`（两个组件共 4 份文件） |
| 业务层依赖什么 | 中文文案 | 文案字符串 | 只依赖 ID |
| 改文案的发布成本 | 改代码、发版 | 改代码、发版 | 只发翻译文件（可热更） |
| 排障与聚合 | 只能搜文案 | 按码聚合 | 按 ID 聚合，天然稳定 |
| 翻译缺失时 | 不可能缺 | 不可能缺 | **回退成 ID 本身**（go-i18n 的默认行为，会露给用户） |

> ⚠️ 翻译缺失是这条路的唯一新坑：`LocalizeT` 找不到 key 时返回 ID 本身，用户会看到 `record.not.found`。必须在 CI 里校验"代码引用的 ID ⇔ 每份 yaml 都有条目"；带参数的文案（"用户 {name} 不存在"）用模板占位符，不要让业务层 `fmt.Sprintf` 拼好再翻译——那样翻译器只能看到成品。

## 码表文档：让码与文档同源

iam 的 `internal/pkg/code/base.go` 里，码的定义和 HTTP 状态、文案写在同一条注释里：

```go
//go:generate codegen -type=int
//go:generate codegen -type=int -doc -output ../../../docs/guide/zh-CN/api/error_code_generated.md

// ErrUserNotFound - 404: User not found.
ErrUserNotFound int = iota + 110001
```

`make gen.errcode` 一次产出两份东西：`code_generated.go`（注册代码）与 `error_code_generated.md`（对外码表，文件头写着"不要对此文件做任何更改"）。这条流水线的实现与取舍见 [52.6 代码生成](../../L5-工程效能/52-持续集成/52.6-代码生成.md)。

> 🔑 **码表必须是生成物**：手写码表在码数超过二三十个之后必然漂移（我的判断：20 个码是手写维护的上限，再多人一定会漏改）。判据是 CI 里跑一次生成、`git diff` 必须为空。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用中文文案当码（`"用户不存在"`） | 文案一改客户端全断，多语言无法做 |
| 把 HTTP 状态码当业务码 | 400 背后十几种原因无法区分，客户端只能统一提示 |
| 5xx 原样返回 `err.Error()` | 泄露库名、表名、内网 IP；文案每天变，监控无法聚合 |
| 已发布码改含义或复用 | 灰度期新旧版本并存，同一码两种语义 |
| 每个 handler 自己拼响应 | 同一错误三种状态码，网关重试策略失效 |
| 每层都渲染、都 log | 告警条数翻倍，真正根因被同一错误的重复日志淹没 |
| 用 `panic` 表达业务错误 | 业务错误变成 500，熔断器按错误率误判 |

## 自检

Q1 同一个 400 背后有五种原因，只有 HTTP 状态码会出什么问题？
▸ 答案：客户端无法分支——它分不清"重填参数""换账号""重试"哪个动作；监控也只能看到"400 变多"，无法定位是哪条业务规则在拒绝。

Q2 为什么 `fmt.Errorf("query user: %w", ErrUserNotFound)` 仍然能返回 404？换成 `%v` 会怎样？
▸ 答案：`%w` 保留错误链，`errors.As` 能穿透包装取到 `*ErrorX`；换成 `%v` 后语义丢失，统一收口只能走 fallback 500——错误分类信息在包装这一步就丢了。

Q3 码表为什么要生成而不是手写？
▸ 答案：码是"代码里的 const + 注释里的 HTTP 状态与文案"两处真相，手抄必然漂移；生成物让"改代码"成为唯一入口，CI 校验生成前后 diff 为空，才能保证文档与实现同步。

Q4 三个项目的错误码实现不同，为什么都算"对"？
▸ 答案：因为都守住了同一条底线——稳定标识与展示文案分离、HTTP 状态由标识映射、边界统一渲染。整数码与层级 Reason 只是编号法不同；选哪种看团队规模与是否对外承诺码表。

Q5 为什么错误日志只允许在边界打一次？
▸ 答案：同一错误每层打一条，告警按错误条数统计就会翻倍，还会把根因淹没在重复日志里；边界拿到 cause 与 trace_id，具备打出完整上下文的条件。

Q6 业务层只返回 message ID（如 `record.not.found`）而不是文案，收益与风险各是什么？
▸ 答案：收益是业务层与语言解耦、加语言只加翻译文件、排障按稳定 ID 聚合；风险是翻译缺失时 go-i18n 回退成 ID 本身、直接把 `record.not.found` 露给用户——所以要 CI 校验 ID 与每份 yaml 一一对应。
