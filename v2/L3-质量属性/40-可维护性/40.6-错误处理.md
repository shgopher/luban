# 40.6 错误处理：把「意外」和「常态」分开

## 一句话

> 错误处理只有两种原语——返回码与异常；选哪个不看语言支不支持，看两件事：这个错误**该不该发生**、它是否要跨**线程或进程边界**——该发生用返回码，不该发生用异常；一旦跨线程、跨进程，异常就失效，只剩返回码与回调。

## 先分清：三种原语各自的代价

| 原语 | 长什么样 | 买到了什么 | 代价 |
|---|---|---|---|
| **错误码** | 返回值 + 全局 `errno`（C） | 兼容所有语言、开销最低 | ① 返回值**双语义**：`open()` 返回 `FILE*` 或 `NULL`，原因还得查 `errno`；② 调用者**一不留神就忘检查** |
| **统一返回码** | `HRESULT`（Windows） | 成功/失败一眼可判 | 结果只能走**出参**，接口里入参出参混在一起；仍然**可以被忽略** |
| **多返回值** | `result, err`（Go） | 结果与错误分离，语义干净；忽略要显式写 `_` | `if err != nil` 写到手软，正常逻辑被打散 |
| **异常** | `try / catch / finally` | 语义清楚、逻辑分离、**不可被忽略**、可多态捕获、支持链式嵌套 | 抛出时要做栈展开，深栈下慢（见下） |

C 语言那个坑值得单独记一笔：`atoi()` 在字符串非法或整型溢出时**返回什么数都不合理**（返回 0 会和正常的 "0" 混淆）。C99 的规格说明写得很直白——`atof / atoi / atol / atoll` **不保证设置 `errno`**，结果无法表示时行为是 **undefined**。所以 libc 后来补了 `strtol()`：用返回值 + `endptr` + `errno` 三件套区分"没数字 / 溢出 / 其他错误"。**返回值一旦要同时表达"结果"和"有没有错"，就必然有一类错误无法表达。**

Go 的多返回值把这件事修好了一半：

```go
val, err := strconv.Atoi(s)
if err != nil {
	return 0, fmt.Errorf("parse %q: %w", s, err) // 原文要求：向上返回原始错误，不要重新发明
}
```

`error` 是个接口，只有一个 `Error() string` 方法，所以可以扩展出自定义类型：

```go
type SyntaxError struct {
	msg    string
	Offset int64 // 出错位置
}

func (e *SyntaxError) Error() string { return e.msg }
```

### 异常的代价，测出来

异常的"贵"不是传说：抛出时要展开函数栈、保存上下文，栈越深越慢。本机实测（`go1.27.1 darwin/arm64`）三种"传播一次错误"的写法：

```go
var errBoom = errors.New("boom")

func byError() (int, error) { return 0, errBoom }              // 返回 error

func byPanicPlain() (n int, err error) {                        // panic + recover
	defer func() { if recover() != nil { err = errBoom } }()
	panic("boom")
}

func byPanic() (n int, err error) {                             // panic + recover + 包成 error
	defer func() {
		if r := recover(); r != nil { err = fmt.Errorf("recovered: %v", r) }
	}()
	panic("boom")
}
```

```text
BenchmarkError        1000000000     0.9702 ns/op
BenchmarkPanicPlain    7926078     148.1  ns/op
BenchmarkPanicRecover  5416059     218.6  ns/op
```

**约 150–225 倍。**但这不构成"别用异常"的理由——异常是少数情况，正常路径上没有这笔开销。它真正的含义是：**不要把异常当流程控制**（见最佳实践第 7 条），高频路径上抛异常等于把 1 ns 的账做成 200 ns。

## 资源清理：三种写法，一条判据

| 写法 | 代表 | 释放时机绑定在 | 风险 |
|---|---|---|---|
| `goto fail` | C | **某一行**（清理标签） | 中间不能有 `return`，维护时一不留神就泄漏 |
| **RAII** | C++ | **对象生命周期**（构造分配、析构释放） | 依赖语言有确定析构 |
| `defer` | Go | **函数返回** | 循环里 defer 会堆积（要到函数结束才执行） |

作者的偏好很明确：**RAII > defer > goto fail**。三者共用的那条判据是：**资源释放必须和"离开作用域"绑定，不能和"走到某一行"绑定**——因为错误会让控制流从任何位置离开，只有作用域是必然经过的。

```go
r, err := Open("a")
if err != nil {
	return err
}
defer Close(r) // 不管后面从哪条路返回，都会关
```

## 关键判据：按错误分类选原语

错误很多，但按"该不该发生"只有三类：

| 类别 | 例子 | 期望 | 处理动作 | 原语 |
|---|---|---|---|---|
| **程序的错**（Bug） | 空指针、非法参数 | 杜绝 | 记日志、写进监控、**触发报警** | 异常 |
| **用户的错** | Bad Request、Bad Format、邮箱格式不对 | 一定会发生 | 报给用户修正；**统计错误率**（还能发现恶意请求） | 返回码 |
| **资源的错**（环境） | 打开无权限文件、写盘失败、网络故障、内存耗尽 | 希望恢复 | 能重试就重试，恢复不了就降级或退出 | **分情况**：不该出现 → 异常；经常出现 → 返回码 |

压缩成一句：

> 🔑 **不期望发生的事用异常，可能发生的事用返回码。** 判据是"概率 + 期望"，不是"底层还是上层"——"底层错误一律用返回码"这个流行说法，作者明确不同意。

## 三个"只能二选一"的硬约束

| 场景 | 为什么没得选 |
|---|---|
| **C++ 重载操作符** | 返回值被操作符语义占满，没法再塞错误码 → 只能抛异常 |
| **异步调用** | 返回码语义失效（"返回"只是把处理权交出去）；异常也看不到（代码跑在另一个线程，两个线程的栈完全不同）→ 只能回调 / Promise |
| **分布式调用** | 只能看返回码（如 HTTP 状态码）；异常过不了网络 |

所以现实里必然是**混用**：RESTful API 把内部异常**转成错误码**（HTTP 4xx/5xx），调用系统调用时又把**错误码转成异常**。判断标准不是"哪种更先进"，而是"这一层的错误处理流程怎么组织更清楚"。

## 异步世界：从回调到 async/await

异步世界没有返回码、没有异常，错误只能"**沿数据流传播**"：

| 阶段 | 错误怎么传 | 代价 |
|---|---|---|
| **回调** | 注册 `OnSuccess` / `OnFailure`，异步线程回调过来 | 顺序执行时层层嵌套，`OnFailure` 各不相同 → **Callback Hell** |
| **Promise** | `then()` 串联，`catch()` 收口；失败调 `reject()`，**像抛异常一样短路后面所有 `then()`** | 要把函数都改成返回 Promise |
| **async/await** | `await` 一个 reject 的 Promise 会抛值，于是 **`try-catch` 又回来了** | 语法糖，本质还是 Promise |
| **Java `CompletableFuture`** | `exceptionally()` 对应 `catch()`，`handle()` 同时拿结果和异常 | API 多，容易用错 |
| **Go 的 Promise** | `wg` + `res` + `err`；`Then` 里先查 `err`，有错就调错误处理函数并 `return` | 得自己实现，标准库没有 |

关键不是"怎么捕获"，而是**让错误短路后续步骤**：Promise 的 `reject` 之所以好用，就是因为它让后面所有 `then` 自动跳过，直到 `catch`——这正是异常的语义，只是搬到了异步链上。

## 16 条最佳实践

| 组 | # | 条款 | 一句话解释 |
|---|---|---|---|
| 分类与定义 | 1 | **统一分类的错误字典** | 错误码集中定义（HTTP 4XX 客户端、5XX 服务端） |
| | 2 | **同类错误定义可扩展** | 继承或接口多态，便于复用 |

| | 11 | **处理错误时清理已分配资源** | RAII / `try-finally` / `defer` |
| | 12 | **不在循环体里 `try-catch`** | 把循环放进 `try`，外面 `catch` |
| | 13 | **一个 `try` 块只做一件简单的事** | 大 `try` 里出错，你不知道是哪一步 |
| 边界与工具 | 14 | **错误定义要有文档和示例** | RESTful 用 Swagger 生成 |
| | 15 | **异步用 Promise 模式** | 别手写回调金字塔 |
| | 16 | **分布式用 APM 关联错误** | Zipkin 这类调用链追踪，把错误串起来 |

## Go 的落地（本书补充）

原文写于 2017 年，下面三条是 Go 1.13（2019）之后才有的标准做法，对应第 10 条"返回原始错误"：

```go
var ErrNotFound = errors.New("not found") // 哨兵错误：调用方用 errors.Is 判断

type ValidationError struct{ Field, Msg string } // 类型错误：调用方用 errors.As 取细节

func (e *ValidationError) Error() string { return e.Field + ": " + e.Msg }

func Load(id string) error {
	if id == "" {
		return &ValidationError{"id", "empty"} // 用户的错 → 返回码（error）
	}
	return fmt.Errorf("load %s: %w", id, ErrNotFound) // %w 保留错误链
}

// 调用方
if errors.Is(err, ErrNotFound) { /* 走 404 */ }
var ve *ValidationError
if errors.As(err, &ve) { /* 取字段做提示 */ }
```

| 落点 | 规则 |
|---|---|
| `panic` 只用于**程序的错**（真正不可恢复的 Bug） | 用户的错、资源的错一律走 `error` |
| 每个 goroutine 入口 `recover` | 子 goroutine panic 没人接 = 整个进程退出 |
| 错误码用常量字符串 | 对应第 4 条：`code = "order_not_found"`，而不是中文描述 |
| 包装用 `%w`，判断用 `errors.Is/As` | 对应第 10 条：能拿到原始错误，才能分类处理 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 用返回值同时表达"结果"和"错误" | 总有一类错误无法表达（`atoi` 的 0 与 "0" 混淆） |
| 忽略错误不写日志 | 异常黑洞，线上问题永远定位不到 |
| 高频路径上 `panic/recover` 做流程控制 | 本机实测 0.97 ns → 148 ns，涨 150 倍 |
| 一个 `try` 块包 200 行 | 出错时不知道是哪一步，也让清理逻辑变复杂 |
| 循环里逐条 `try-catch` | 性能与可读性双输；应该整段包住 |
| 重新发明错误（把底层错误换成自己的字符串） | 上层无法按类型/错误码分类，只能做字符串匹配 |
| 同一处错误每秒打一万条日志 | 真问题被淹，磁盘被写满 |
| 异步里靠 `try-catch` 捕获另一个线程的异常 | 捕获不到，错误直接消失 |

## 自检

**Q1** 为什么 `atoi()` 是个反面教材，而 `strtol()` 修好了它？

▸ 答案：`atoi()` 只有返回值一个出口，"非数字"和"溢出"都无法用一个整数表达（返回 0 与合法的 0 混淆），且 C99 明确它**不保证设置 `errno`**，结果不可表示时行为未定义。`strtol()` 把三件事分开：返回值给结果、`endptr` 指出解析停在哪、`errno`（如 `ERANGE`）说明是否溢出——**结果、位置、错误各占一个通道**。

**Q2** "底层错误用返回码、上层业务错误用异常"这个说法，作者为什么不同意？

▸ 答案：因为它按"层次"分，而正确的判据是"**该不该发生**"。空指针这种底层错误恰恰是程序的错（不该发生）→ 适合异常；邮箱格式这类上层错误恰恰一定会发生 → 适合返回码。按层次分会出现"底层空指针也返回错误码"这种与判据相反的结果。

**Q3** 为什么异步编程里 `try-catch` 抓不到被调函数的异常？

▸ 答案：因为被调函数在**另一个线程**里运行，两个线程的栈完全独立；异常沿栈展开只发生在抛出它的那个线程，主线程的 `catch` 看不到。同理，返回码也失效——"返回"只是把处理权交给下一条指令，不是函数执行完的结果。

**Q4** Promise 的 `reject()` 本质上模拟了什么？为什么这个设计让代码变干净？

▸ 答案：模拟**抛异常**——`reject` 之后，后面所有 `then()` 被短路，直到最近的 `catch()`。它把"错误传播"从"每层手动判断"变成"沿链自动跳过"，于是正常的串联逻辑（`doSomething().then(...).then(...)`）不必被 `if err != nil` 打断。`async/await` 只是把这层语义还原成同步写法，于是 `try-catch` 又可用。

**Q5** 为什么"同一处反复报错只打一条 + 次数"是硬要求，而不是优化项？

▸ 答案：错误日志的作用是**让人和机器都能发现异常**。同一个错误每秒刷一万条，会淹没其他日志、撑爆磁盘，还会让基于日志的监控失效——真正的新错误反而看不见。打出"错误 + 出现次数"既保留了"发生了"，又保留了"规模"。

**Q6** 本机实测里，`panic + recover` 比返回 `error` 慢约 150 倍。这是否意味着"Go 里应该永远不用 panic"？

▸ 答案：不是。150 倍是**传播一次**的代价，只有真的出错才付；正常路径一次都不付。结论应该是"**不要在会频繁出错的路径上用 panic 做控制流**"，而不是"禁用 panic"。程序的错（不可恢复的 Bug）用 panic 仍然是合理的，前提是每个 goroutine 入口有 `recover`，否则一个子协程 panic 会带走整个进程。
