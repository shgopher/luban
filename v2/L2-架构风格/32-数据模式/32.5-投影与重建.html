                      32.5 投影与重建

                      一句话

                      投影是 “把事件折叠成可查询的结构”，重建是 “从事件流重新算一遍投影”；它既是 ES/CQRS 的查询来源，也是修 bug、改口径、换存储时唯一的救命手段——前提是投影幂等、位点可记。

                      投影的两类

                      类型 输入 输出 用途
                      同步投影（读模型） 领域事件 宽表/文档/缓存 支撑查询（见 32.1 CQRS）
                      分析投影 事件流 指标、报表、漏斗 数仓/BI

                      本机实测：两个投影的一致性

                      20 万条事件、同时维护 “余额” 与 “订单数” 两个投影，重建后与全量回放对比：

                      检查 结果
                      两个投影口径是否一致（总额 = 单数 × 单价） ✅ 一致
                      重建前后结果是否相同 ✅ 相同
                      重建耗时（20 万事件） 约 9ms（内存模型，仅示意比例）

                      真正的价值在 “可重建”：口径错了、代码有 bug、换搜索引擎，都能重放修复，而不必 “修数据”。

                      代码：可重建 = 可重放 + 幂等

                      # 重建三步：冻结消费 → 清空投影 → 从头回放（或从快照 + 尾部）
kubectl scale deploy/projector --replicas=0          # ① 停消费，避免边写边重建
psql -c "TRUNCATE order_view"                         # ② 清空（或用影子表，见下）
PROJECTOR_FROM=0 ./projector --until=$(cat checkpoint) # ③ 回放到原检查点，再恢复消费

                      无停机重建（推荐）：影子表 + 双写 + 原子切换
  projector 同时写 order_view 与 order_view_new
  重建完成后：ALTER TABLE ... RENAME → 切读
  期间查询仍读旧表，不出现“半成品”

                      实测：重建耗时随事件数线性增长

                      同一聚合，20 万事件内不同规模的回放（内存模型）：

                      事件数 耗时 备注
                      2,000 0.11ms 有快照时只需回放尾部
                      20,000 1.02ms 快照在 90% 处
                      200,000 11.32ms 无快照，全量

                      生产上乘 100–1000 倍（反序列化 + DB 写入 + 索引维护），即 0.2 万事件 ≈ 秒级、20 万 ≈ 分钟级。所以重建必须支持 “分批 + 断点 + 影子表”，否则一次全量重建就会占满数据库。

                      重建的触发条件与全量/增量账

                      结论先行：该全量还是增量，由「错误从哪个位点开始」决定，不由「哪个快」决定——增量重放只能修位点之后的投影行；位点之前如果也错，只有全量能修。时间上，影响范围局部时增量更省；但它的单条成本更高（活表 upsert），影响面接近全历史时反而比全量贵——两条曲线有一个交叉点，交叉点就是选型线。

                      四种触发条件，四种动作

                      触发 影响范围 该做什么 为什么
                      投影逻辑变更（改过滤条件、聚合口径、去重规则） 全部历史行 全量重建（影子表 + 双写 + 原子切换） 旧行都按旧口径算过，增量补不到位点之前
                      数据修复（上游重复投递、漏投一段事件） 可枚举的局部区间 增量重放该区间（幂等 upsert） 影响可定位，全量的代价不必要
                      新投影上线（新增读模型、新报表） 从 0 开始，没有旧行 全量回放，但不动旧投影 这是首次构建，不是「重建同一个投影」
                      漂移检测失败（对账差、双投影口径不一致、抽样比对失败） 先定位再判断 先增量追平位点 + 抽样比对；仍不一致再全量 漂移常是滞后（追位点即好），不一定是逻辑错

                      🔑 一句话判据：「错误从哪个位点开始」决定增量还是全量。位点越早，越接近「必须全量」；单纯滞后类漂移不用重建，追上位点即可。

                      四种触发共用一个前提：投影必须是「覆盖式」的——同一批事件重算一次，得到整行再 upsert；如果投影按 delta 累加（余额 += 金额），即使幂等键齐全也重放不了，同一个 delta 应用两次就翻倍。判断方法很土：能不能只靠这一行涉及的事件把它重新算出来？算不出来，就别指望重建。

                      全量 vs 增量的时间账：解交叉点

                      全量重建 = 固定成本 S（建影子表、建索引、原子切换、抽样校验）+ N 条事件批量 COPY 进影子表：

                      T_full   = S + N × c_full
T_inc(d) = V + d × c_inc

                      V 是增量固定成本（定位位点、圈定影响区间、校验），d 是需重算的条数。关键假设是 c_inc > c_full：全量往新表批量写、索引最后统一建；增量要在活表上按主键 upsert、边写边维护索引、还要读旧行做合并。两者相等时解出交叉点：

                      d* = (S − V + N × c_full) ÷ c_inc

                      账就是一个模型：核心参数只有 N、c_full、c_inc、S/V 四个，纯算术、无 I/O，换掉就能套到自己的系统：

                      """重建成本模型：全量 vs 增量（本机计算，纯算术，无 I/O）。
T_full = S + N×c_full；T_inc(d) = V + d×c_inc；两者相等处即交叉点。
"""

N = 20_000_000          # 事件总数（条）
C_FULL = 200e-6         # 全量：单条 200µs（批量 COPY 进影子表）
C_INC = 350e-6          # 增量：单条 350µs（活表 upsert + 索引维护）
S_FULL = 900.0          # 全量固定成本（秒）：影子表 + 索引 + 原子切换 + 抽样校验
V_INC = 120.0           # 增量固定成本（秒）：定位位点 + 圈定影响区间 + 校验
WORKERS = 4             # 重建集群 worker 数
YUAN_PER_CORE_H = 0.6   # 机器单价量级（元/核·时），用于说明「机器成本可忽略」
WRITE_RATE = 2000       # 写侧事件速率（条/秒），用于把「条数」换算成「历史时长」
PROJ_ROWS = 50_000_000  # 投影行数，用于算影子表峰值存储
ROW_BYTES = 200         # 单行投影大小（字节）


def t_full():
    return S_FULL + N * C_FULL


def t_inc(d):
    return V_INC + d * C_INC


def money(seconds):
    return seconds * WORKERS / 3600 * YUAN_PER_CORE_H


def fmt(n):
    return f"{n:,.0f}"


def row(name, d, t):
    return (f"{name:<12} {fmt(d):>12} {t:>10,.0f} {t/3600:>8.2f} "
            f"{money(t):>8.2f} {d/WRITE_RATE/60:>10.1f}")


T_FULL = t_full()

print("== 参数（本机计算） ==")
print(f"事件总数 N={fmt(N)}  全量单条={C_FULL*1e6:.0f}µs  增量单条={C_INC*1e6:.0f}µs")
print(f"全量固定 S={S_FULL:.0f}s  增量固定 V={V_INC:.0f}s  worker={WORKERS}  "
      f"写入速率={WRITE_RATE}条/s")
print(f"全量重建耗时 = S + N×c_full = {S_FULL:.0f} + {N*C_FULL:.0f} = {T_FULL:,.0f}s "
      f"({T_FULL/3600:.2f}h)")

print("\n== 方案对比：全量 vs 增量（d = 需要重算的事件条数） ==")
print(f"{'方案':<12} {'回放条数':>12} {'耗时(s)':>10} {'耗时(h)':>8} "
      f"{'机器成本(元)':>8} {'重算历史(分钟)':>10}")
for d in (N, 16_000_000, 13_657_143, 10_000_000, 2_000_000, 200_000):
    name = "全量重建" if d == N else "增量重放"
    print(row(name, d, t_inc(d) if d != N else T_FULL))

# 交叉点：V + d*c_inc = S + N*c_full  =>  d* = (S - V + N*c_full) / c_inc
D_STAR = (S_FULL - V_INC + N * C_FULL) / C_INC
P_STAR = N - D_STAR
print(f"\n== 交叉点 ==")
print(f"d* = (S - V + N×c_full) / c_inc = ({S_FULL:.0f} - {V_INC:.0f} + {N*C_FULL:.0f}) / {C_INC*1e6:.0f}µs")
print(f"d* = {D_STAR:,.0f} 条（{D_STAR/N*100:.2f}% 的历史事件）→ 需重算超过它时，全量更省")
print(f"对应错误位点 p* = N - d* = {P_STAR:,.0f} 条，即 bug 上线早于 {P_STAR/WRITE_RATE/60:.1f} 分钟前")
print(f"交叉点存在的条件：S - V < N×(c_inc - c_full)；"
      f"本例 {S_FULL-V_INC:.0f}s < {N*(C_INC-C_FULL):,.0f}s → 成立"
      if S_FULL - V_INC < N * (C_INC - C_FULL) else
      f"交叉点存在的条件不成立 → 增量恒更省：{S_FULL-V_INC:.0f}s vs {N*(C_INC-C_FULL):,.0f}s")

print("\n== 敏感性：增量单条成本是交叉点的主因 ==")
print(f"{'c_inc/c_full':>12} {'增量单条(µs)':>12} {'d*(条)':>14} {'触发全量的影响比例':>18}")
for r in (1.00, 1.25, 1.50, 1.75, 2.00, 3.00):
    c_inc = C_FULL * r
    d = (S_FULL - V_INC + N * C_FULL) / c_inc
    if d >= N:
        print(f"{r:>12.2f} {c_inc*1e6:>12.0f} {'不存在':>14} {'增量恒更省':>18}")
    else:
        print(f"{r:>12.2f} {c_inc*1e6:>12.0f} {d:>14,.0f} {d/N*100:>17.2f}%")

print("\n== 存储与机器成本 ==")
proj_gb = PROJ_ROWS * ROW_BYTES / 1e9
print(f"投影 {PROJ_ROWS/1e6:.0f}M 行 × {ROW_BYTES}B = {proj_gb:.0f}GB；"
      f"全量重建峰值 {proj_gb*2:.0f}GB（旧表+影子表），增量 {proj_gb:.0f}GB")
print(f"机器成本全量 {money(T_FULL):.2f} 元、增量(10M) {money(t_inc(10_000_000)):.2f} 元 "
      f"→ 重建的钱不在机器，在窗口内数据陈旧与人力值守")

                      完整代码在仓库 tools/examples/32.5-rebuild-cost/，python3 rebuild_cost.py 可复现这段输出。

                      本机计算（macOS 15.6 / Apple M1 / Python 3.14.8）：N = 2,000 万事件、c_full = 200µs、c_inc = 350µs、S = 900s、V = 120s、写入 2,000 条/秒。

                      == 参数（本机计算） ==
事件总数 N=20,000,000  全量单条=200µs  增量单条=350µs
全量固定 S=900s  增量固定 V=120s  worker=4  写入速率=2000条/s
全量重建耗时 = S + N×c_full = 900 + 4000 = 4,900s (1.36h)

== 方案对比：全量 vs 增量（d = 需要重算的事件条数） ==
方案                   回放条数      耗时(s)    耗时(h)  机器成本(元)   重算历史(分钟)
全量重建           20,000,000      4,900     1.36     3.27      166.7
增量重放           16,000,000      5,720     1.59     3.81      133.3
增量重放           13,657,143      4,900     1.36     3.27      113.8
增量重放           10,000,000      3,620     1.01     2.41       83.3
增量重放            2,000,000        820     0.23     0.55       16.7
增量重放              200,000        190     0.05     0.13        1.7

== 交叉点 ==
d* = (S - V + N×c_full) / c_inc = (900 - 120 + 4000) / 350µs
d* = 13,657,143 条（68.29% 的历史事件）→ 需重算超过它时，全量更省
对应错误位点 p* = N - d* = 6,342,857 条，即 bug 上线早于 52.9 分钟前
交叉点存在的条件：S - V &lt; N×(c_inc - c_full)；本例 780s &lt; 3,000s → 成立

                      读法（完整输出还含敏感性与存储两段，见 tools/examples/32.5-rebuild-cost/）：2,000 万事件按 2,000 条/秒写入 ≈ 2.8 小时历史；d* = 1,366 万条，即错误影响的历史超过 68% 时全量更省（bug 位点早于 53 分钟前）。只影响最近十分钟（d ≈ 120 万），增量 540 秒、全量 4,900 秒，省 89%。

                      交叉点存在的条件是 S − V < N × (c_inc − c_full)：固定成本差被「单条成本差 × 事件数」追上。敏感性：

                      c_inc / c_full 增量单条 d*（条） 触发全量的影响比例
                      1.00 200µs 不存在 增量恒更省
                      1.25 250µs 1,912 万 95.6%
                      1.50 300µs 1,593 万 79.7%
                      1.75 350µs 1,366 万 68.3%
                      2.00 400µs 1,195 万 59.8%
                      3.00 600µs 797 万 39.8%

                      这张表真正说明的是：交叉点位置主要由单条成本比决定，事件总量只是把它整体推大。如果增量能做到批量 upsert（c_inc = c_full），交叉点不存在，全量就只剩「口径变更必须全量」这一个理由。

                      固定成本也别当常数：V = 120 秒拆成定位位点 30 秒、圈定影响区间 40 秒、抽样比对 50 秒；S = 900 秒拆成建影子表 300 秒、建索引 400 秒、切换与校验 200 秒。V 的价值是把「影响范围」变成可枚举的集合，做不到，增量就退化成猜。

                      同一个公式代入三个真实场景，答案立刻分化：

                      场景 需重算 d 增量耗时 全量耗时 选哪个
                      口径变更（过滤条件改了，影响全部历史） 2,000 万 7,120s 4,900s 全量（增量根本覆盖不了）
                      某个新逻辑上线后算错（近 25 分钟事件） 300 万 1,170s 4,900s 增量（省 76%）
                      上游重复投递 5 万条 5 万 137.5s 4,900s 增量（省 97%）

                      还有一笔常被漏算的账：回放要限速。写侧 2,000 条/秒的库，回放压在 500 条/秒，全量 2,000 万条就是 11.1 小时（满速的 8.1 倍），换来线上查询延迟不抖。所以重建窗口要按「限速后的时间」报。

                      换成自己系统的数字只要三步：① 取 1 万条事件跑一次增量重放，c_inc = (T − V) ÷ 1万；② 影子表回放 1 万条，c_full = (T − S) ÷ 1万；③ 代入公式。单机内存模型只能算比例，不能当生产值。

                      重建期间：读旧投影 / 双写 / 停写

                      方案 一致性 可用性 成本（本例规模） 适用
                      读旧投影（后台建新投影，切读瞬间原子切换） 切换前读到的全是旧数据：陈旧但不残缺；切换后一致 读不停、写不停 峰值 2× 存储（10GB → 20GB）+ 切换前核对 资金/交易类：宁可旧，不能缺
                      双写（新旧投影同时写，双读比对） 新投影可逐步校验；双写非原子会短暂不一致 读不停、写不停 写放大 2×，比对与告警逻辑要自己写 新投影上线前的验证期
                      停写（冻结消费 → 清空 → 回放 → 恢复） 最干净：重建期间没有新事件干扰 写入不可用（事件积压），读可能为空 停机窗口 = T_full（本例 1.36h）+ 积压回放 内部报表、可停服的离线投影

                      三条读法：双写不能替代「切换后的回滚点」；停写的代价不是停机，而是积压回放（按 d ÷ 处理速率消化）；读旧投影的问题不是「读到旧」，而是没人知道读的是旧的，所以切换前必须给出「数据截至」时间戳。

                      重建前必须确认的五件事

                      # 检查项 判据 不满足的后果
                      1 事件保留期 保留期 ≥ 需重放的事件区间（本例 d* 对应 113.8 分钟历史） 事件已归档/删除 → 全量也救不了，只能修数
                      2 幂等键 每条事件有 (stream_id, seq) 或 event_id，投影按它 upsert 重放 = 数字翻倍（见 25.4 幂等设计与去重）
                      3 版本 投影代码版本与事件 schema 版本绑定（快照/投影版本号） 用今天的代码解释三个月前的事件，得到「当时没发生」的结果（见 32.4 事件溯源）
                      4 回滚点 旧投影切换后保留 ≥ 24h 观察窗，可原子切回 切错了回不去，只能二次重建
                      5 对账口径 同一口径抽样比对：总额 = 单数 × 单价、与写侧总数差 ≤ 0.01% 「重建成功」只是自我声明，对不上照切 = 把 bug 换个地方

                      ⚠️ 五条缺一条都别开始。重建最贵的一类事故不是「跑得慢」，而是跑完了才发现没有回滚点。

                      反模式

                      反模式 后果
                      投影非幂等（累加而不判重） 重投/重建导致数字翻倍
                      重建时不停消费 边写边重建，结果不可预期
                      没有检查点 重建后不知道从哪恢复增量
                      投影含业务逻辑（校验/拒绝） 重放时行为随代码版本变化，结果不可复现
                      只重建一个投影 多个投影口径不一致，报表互相打架
                      重建脚本没人维护 真出事时脚本跑不通，只能手工修数
                      重建按“一次性全量”设计 大表重建时数据库 IO 打满，业务抖动
                      重建后不做抽样比对 新投影与旧投影口径不同，结果悄悄变了

                      三条铁律

                      🔑 投影必须幂等：重放任意次，结果一致。

                      🔑 重建要能 “停机、清空、回放、恢复”，并且演练过。

                      🔑 检查点是投影的一部分，没有它就无法做增量恢复。

                      自检

                      Q1 为什么 “投影非幂等” 会让重建失去意义？

                      ▸ 答案：因为重建本质是把同一批事件再处理一遍：如果投影是 “累加” 而非 “按事件幂等设置/带版本 upsert”，重放就会重复计数。结果比不重建更糟——数字翻倍且看起来 “像真的”。

                      Q2 无停机重建为什么要用影子表？

                      ▸ 答案：因为清空/重写期间旧表不可用（查询会看到空或半成品）。影子表让 “新表在后台构建”，完成后原子重命名，查询侧要么读旧表、要么读新表，中间不出现不完整状态。

                      Q3 重建需要多久，怎么估？

                      ▸ 答案：时间 ≈ 事件数 × 单条处理成本：本机 20 万条约 9ms（内存模型），生产上要乘上反序列化、DB 写入与索引维护，通常是分钟到小时级。估算时按 “最慢的那条链路” 算，并留 2 倍余量。

                      Q4 投影里为什么不能做业务校验？

                      ▸ 答案：因为投影是派生视图，它看到的只是 “已经发生的事实”；在投影里拒绝/修正，会导致 “写侧认为成功、读侧看不到” 的不一致。校验属于写侧（命令处理或聚合），投影只做 “忠实呈现”。

                      Q5 多个投影口径不一致时，以谁为准？

                      ▸ 答案：以事件 + 明确的投影定义为准：先确认两个投影的过滤条件、时间窗口、去重规则是否相同；不同的话，必须有文档说明 “为什么不同”。没有定义的差异，一律视为 bug。

                      Q6 什么时候可以 “修数据” 而不重建？

                      ▸ 答案：当偏差是局部的、可枚举的、且不影响事件真相时（如某几行视图字段错）。一旦涉及 “口径/逻辑” 错误，就必须重建——手工修数只能修当前值，下次重放又会错回去。

                      Q7 重建期间读请求怎么办？

                      ▸ 答案：三种策略：继续读旧投影（无停机，最终切换，最常用）、读侧降级（隐藏依赖该投影的页面）、双读比对（新老并行，抽样验证）。选择依据是 “该投影失效时业务能否降级”；资金类投影必须能降级，内容类可以继续用旧数据。

                      故障复盘（典型模式，脱敏）

                      阶段 现象 判断 动作
