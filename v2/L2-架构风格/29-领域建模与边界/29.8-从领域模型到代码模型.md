# 29.8 从领域模型到代码模型

## 一句话

> 领域模型只管「业务怎么说」，落地还差一张**映射表**：聚合、聚合根、实体、值对象、领域服务、领域事件、仓储逐一对到「哪一层、哪个包、哪个类、哪个方法」；代码模型的验收标准不是目录好看，而是**一个聚合能不能整包搬走而不动别的聚合**。

**来源**：代码模型的一二级目录、领域对象映射表、四类数据对象与逐层封装来自欧创新《DDD 实战课》第 13、14、16 讲（2019）；分层检查器与样例工程为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “有 `controller/service/dao` 三个包就是 DDD 代码模型” | 那只是三层架构换名字。DDD 的分包单位是**聚合**，不是技术层；判断依据是“一个业务规则变了，改的是几个包” |
| “DTO 是脱裤子放屁，实体直接传到前端多省事” | 每层转换是**契约隔离**。省掉它，表结构一改就同时打断接口、前端和测试；更隐蔽的版本是反过来——为了省映射，给领域对象挂 `gorm`/`json` tag，让内层依赖外层格式（[26.3 整洁架构](../26-分层与依赖/26.3-整洁架构.md)） |
| “仓储实现必须放基础层才标准” | 标准不是重点，**聚合整体搬迁**才是。放哪两种都有人用，代价不同（对比表在「仓储放哪」一节），先想清楚要不要搬迁 |
| “应用层顺手写点业务逻辑没关系” | 应用层一胖，领域层就退化成数据袋，服务最终退回三层架构——代码看起来还是四层，行为已经不是 |

## 第一步：把领域对象整理成一张映射表

事件风暴结束时，墙上是一堆便签；到了代码里，必须变成可查的清单。这张表七列，一行一个领域对象：

| 层 | 领域对象 | 领域类型 | 依赖的领域对象 | 包名 | 类名 | 方法名 |
|---|---|---|---|---|---|---|
| 领域层 | 个人客户 | 聚合根 | 地址、电话、银行账号 | `domain/customer` | `Customer` | `Create` / `Update` |
| 领域层 | 地址 | 实体 | — | `domain/customer` | `Address` | `Add` / `Modify` |
| 领域层 | 客户证件类型 | 值对象 | — | `domain/customer` | `CertType` | —（整体替换） |
| 领域层 | 客户创建 | 领域事件 | 个人客户 | `domain/customer` | `CustomerCreated` | — |
| 领域层 | 创建客户信息 | 领域服务 | 个人客户、地址 | `domain/customer` | `CustomerService` | `CreateCustomer` |
| 领域层 | 客户仓储 | 仓储 | 个人客户 | `domain/customer` | `CustomerRepository` | `Save` / `FindByID` |
| 应用层 | 创建客户 | 应用服务 | 创建客户信息（领域服务） | `application/service` | `CustomerAppService` | `Create` |
| 接口层 | 客户创建接口 | Facade | 创建客户（应用服务） | `interfaces/facade` | `CustomerFacade` | `Create` |

> 🔑 这张表是**模型与代码的双向索引**：业务人员按对象名能查到代码位置，开发按代码能反查它对应哪条业务规则。没有它，“模型与代码一致”就是一句口号。

整理表时会逼出两类设计问题，正好在此时解决：

| 问题 | 判据 |
|---|---|
| 某个属性是实体还是值对象？ | 生命周期由**别的聚合**维护、且只允许整体替换 → 值对象；本身多条、需要基于它查询统计 → 实体 |
| 某个业务动作放实体方法还是领域服务？ | 单个实体（含聚合根）能完成 → 实体方法；跨多个实体/值对象 → 领域服务 |

## 第二步：代码模型——聚合即包

分层是四个一级目录，聚合是领域层里的二级包：

```text
order-service/                 # 一个服务 = 一个代码库 / 一个部署单元
├── interfaces/                # 用户接口层
│   ├── dto/                   # 出入参，无业务逻辑
│   ├── assembler/             # DTO ⇄ 领域对象 的转换
│   └── facade/                # 粗粒度入口：一个 Facade 调一个或多个应用服务
├── application/               # 应用层（必须是薄的一层）
│   ├── service/               # 应用服务：编排、事务、鉴权、幂等、结果拼装
│   └── event/                 # publish/ + subscribe/：事件统一出入口
├── domain/                    # 领域层
│   ├── order/                 # 一个聚合 = 一个包（可整包迁移）
│   │   ├── entity.go          # 聚合根 + 实体 + 值对象（充血模型）
│   │   ├── event.go           # 事件实体
│   │   ├── service.go         # 领域服务：跨实体的规则
│   │   └── repository.go      # 仓储接口（实现放哪：见「仓储放哪」一节）
│   └── inventory/
└── infrastructure/            # 基础层：贯穿所有层
    ├── persistence/           # 仓储实现、DAO、PO
    ├── config/
    └── util/
```

四条纪律，比目录结构本身更重要：

1. **聚合包内自洽**：聚合根、实体、值对象、领域服务、仓储接口、事件实体都在同一个包；包外只能通过聚合根或领域服务访问。
2. **聚合之间禁止直连**：`domain/order` 不允许 import `domain/inventory`；跨聚合协作走应用层（这条可以用脚本卡住，脚本在「可运行：把分层依赖卡在 CI 里」）。
3. **事件统一在应用层发布/订阅，事件实体与处理逻辑在领域层**：统一出入口才查得到“谁发了什么”，核心逻辑仍归领域层。
4. **应用层不许出现领域规则**：应用服务只做编排、事务边界、权限、幂等、结果拼装——它是“薄薄的一层”，胖了就退化成三层架构。

## 第三步：四类数据对象，四个转换点

| 对象 | 住在哪层 | 作用 | 转换发生在 | 典型误用 |
|---|---|---|---|---|
| **PO**（持久化对象） | 基础层 | 与表结构一一映射 | 仓储实现内 `DO ⇄ PO` | PO 上写业务方法；直接用 PO 当接口返回 |
| **DO**（领域对象） | 领域层 | 实体 + 值对象，承载行为与不变量 | — | 把 DO 直接返回给前端，字段变更穿透所有层 |
| **DTO**（传输对象） | 接口层 / 跨服务 | 契约载体，无业务逻辑 | `interfaces/assembler` 或跨服务调用前 | DTO 里放校验逻辑与业务规则 |
| **VO**（视图对象） | 前端 | 页面/组件展示 | 前端组装 | 后端为每个页面造一个 VO |

转换点只有四处，记住这四处就不会乱：

```text
前端 ──DTO──▶ Facade ──(assembler)──▶ DO ──▶ 应用服务 ──▶ 领域服务 ──▶ 仓储
                                                                    │
                                       PO ◀──(仓储实现)◀── DO ◀─────┘
                                                                    │
                       跨服务调用：DO ──(assembler)──▶ DTO ──▶ 对方服务的应用服务
```

两条容易踩的细节：

- **一对多要重组**：一个 DTO 常常来自多个聚合的 DO。正确做法是应用服务分别取回各自 DO，在 assembler 里组装成一个 DTO；不要为了省事让 A 聚合去查 B 聚合的表。
- **跨服务要重建类型**：A 服务把 B 服务的值对象拿来用，不能 import B 的类/结构体，要在 A 里重建一份——这就是最轻量的防腐层（[29.2 上下文映射 (七种关系)](29.2-上下文映射.md)）。

## 第四步：服务逐层封装

严格分层下，每层只能调紧邻的下一层，于是「一个实体方法想被前端调到」必须逐层封装：

| 起点 | 封装成 | 再封装成 | 谁能调 |
|---|---|---|---|
| 实体方法（聚合根上的行为） | 领域服务（跨实体时） | 应用服务 | 接口层 |
| 领域服务 | — | 应用服务 | 接口层 |
| 应用服务 | — | — | 接口层 / 网关 |

命名上留个一致的约定，读代码时能一眼看出层级：`*DomainService`、`*AppService`、`*Facade`、`*Repository`。

严格分层 vs 松散分层（[26.1 分层架构](../26-分层与依赖/26.1-分层架构.md) 有完整对比），在 DDD 里的差别很具体：

| 维度 | 严格分层 | 松散分层 |
|---|---|---|
| 谁都能调 | 每层只调紧邻下层 | 下层可被任意上层直接调 |
| 跨层调用 | 必须逐层封装 | 直接调，快 |
| 服务变更影响面 | 只需通知紧邻上层 | 不知道谁组合过你，容易漏改 |
| 核心逻辑泄露风险 | 低（对外只见粗粒度服务） | 高（实体方法直接暴露） |

> ⚠️ 松散分层不是“简单版”，它把成本从**写代码时**挪到了**改代码时**：一次方法签名变更，你要翻遍所有上层调用方。团队 ≥ 8 人、服务生命周期 > 1 年时，严格分层通常更便宜。

## 仓储放哪：一个取舍，不是教条

| 放法 | 好处 | 代价 | 适合 |
|---|---|---|---|
| **实现放聚合包内**（`domain/order/repository_impl.go`） | 聚合连同持久化逻辑**整包搬走**，微服务重组几乎零改动 | 领域包依赖了基础设施细节（驱动、SQL） | 预期会频繁做服务重组/拆分的系统 |
| **实现放基础层**（`infrastructure/persistence`） | 分层纯粹：领域层只有接口，依赖倒置干净 | 搬迁聚合时要同步搬实现、改装配 | 边界稳定、拆分不频繁的系统 |

两种都能工作，选之前先回答一个问题：**未来一年，这个聚合有多大概率被搬走？** 概率高就把实现带上，概率低就保持分层纯粹。欧创新《DDD 实战课》的取舍是“聚合整体迁移优先”，所以选了前者——这是判断，不是标准。

## 演进：聚合是搬迁单位

代码模型的复利在演进时才兑现：

| 场景 | 动作 | 成本 |
|---|---|---|
| 某聚合被高频访问、拖累整个服务 | 把聚合包整体剥离为独立服务 | 低：搬包 + 改装配 |
| 某聚合更适合另一个服务的领域模型 | 聚合包整体搬回 | 低：同上 |
| 两个领域服务总被同一顺序组合 | 合并成一个新领域服务，应用服务变薄 | 低：删编排代码 |
| 跨聚合的应用服务需要拆走 | 要从“基于 DO 的本地调用”改成“基于 DTO 的跨服务调用” | 高：这是代码模型最容易卡住的地方 |

> 🔑 所以拆聚合时，**跨聚合的应用服务要提前分好类**：一个应用服务类只服务一个聚合的，将来能整类搬走；跨多个聚合的，注定要改写。欧创新的实践是前者优先。

## 可运行：把分层依赖卡在 CI 里

代码模型最容易被破坏的方式是“顺手 import 一下”。下面这个检查器零依赖，扫描 Go 源码的 import 边，用两张规则表卡住违规。

```python
#!/usr/bin/env python3
"""layering.py —— DDD 分层依赖检查器：把「哪层能依赖哪层」变成 CI 里的一条命令。

规则（严格分层）：
  interfaces      → interfaces, application
  application     → application, domain
  domain          → domain 内部（且同层不跨聚合）
  infrastructure  → infrastructure, domain
用法: python3 layering.py shop/order
退出码: 0 合规 / 1 违规
"""
import os
import re
import sys

LAYER = ("interfaces", "application", "domain", "infrastructure")
ALLOW = {
    "interfaces": {"interfaces", "application"},
    "application": {"application", "domain"},
    "domain": {"domain"},
    "infrastructure": {"infrastructure", "domain"},
}
MODULE = "shop/order/"          # 换成你自己的模块前缀

def walk(root):
    for dirpath, _, files in os.walk(root):
        for f in files:
            if f.endswith(".go") and not f.endswith("_test.go"):
                yield os.path.join(dirpath, f)

def layer_of(path, root):
    parts = os.path.relpath(path, root).split(os.sep)
    return parts[0] if parts[0] in LAYER else None

def imports(path):
    src = open(path, encoding="utf-8").read()
    block = re.search(r"import\s*\((.*?)\)", src, re.S)
    decls = re.findall(r'"([^"]+)"', block.group(1)) if block else \
            re.findall(r'import\s+"([^"]+)"', src)
    return decls

def main(root):
    bad = 0
    for path in sorted(walk(root)):
        src_layer = layer_of(path, root)
        if src_layer is None:
            continue
        pkg_dir = os.path.dirname(os.path.relpath(path, root))
        for imp in imports(path):
            if not imp.startswith(MODULE):
                continue
            target = imp[len(MODULE):]
            dst_layer = target.split("/")[0]
            if dst_layer not in LAYER:
                continue
            where = f"{os.path.relpath(path, root)} → {imp}"
            if dst_layer not in ALLOW[src_layer]:
                print(f"ILLEGAL  {where}\n          {src_layer} 不能依赖 {dst_layer}（严格分层）")
                bad += 1
                continue
            if src_layer == "domain" and dst_layer == "domain":
                a, b = pkg_dir.split("/")[-1], target.split("/")[-1]
                if a != b:
                    print(f"CROSS-AGG {where}\n          聚合 {a} 直接依赖聚合 {b}：跨聚合必须走应用层")
                    bad += 1
    print(f"\n结论：{'发现 ' + str(bad) + ' 处违规' if bad else '分层依赖全部合规'}")
    return 1 if bad else 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1]))
```

**本机实测输出**（Python 3.14.8，样例工程 `shop/order`：`interfaces/` `application/` `domain/order`、`domain/inventory`、`infrastructure/persistence`）：

领域层反向依赖基础设施（有人为了打日志在实体里 import 了 `persistence`）：

```text
ILLEGAL  domain/order/entity.go → shop/order/infrastructure/persistence
          domain 不能依赖 infrastructure（严格分层）

结论：发现 1 处违规
```

聚合之间直接依赖（`order` 的领域服务 import 了 `inventory`）：

```text
CROSS-AGG domain/order/service.go → shop/order/domain/inventory
          聚合 order 直接依赖聚合 inventory：跨聚合必须走应用层

结论：发现 1 处违规
```

修完两处后的合规态：

```text
结论：分层依赖全部合规
```

读法三条：

1. **规则表就是架构决策的可执行版本**。哪层能依赖哪层，写在 `ALLOW` 里，比写在 wiki 里有效——wiki 没人看，CI 会红。
2. **跨聚合检查只对 `domain` 生效**：`application` 本来就要跨聚合编排，把它也算进去会全是误报。
3. **先跑 warn 再跑 fail**：存量项目一次全开会红成一片，先按目录白名单逐步收紧。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：不想自己写检查器，可以用现成工具——Java 用 **ArchUnit**（单元测试里断言分层规则），Go 用 **go-arch-lint** 或 golangci-lint 的 **depguard**，Python 用 **import-linter**。这些工具**未在本机验证**，按各自文档执行；本节脚本的价值是零依赖、规则可读。

**可抄**：CI 里加一行，违规即失败。

```bash
python3 tools/layering.py shop/order || exit 1
```

**可验**：输出三态固定——`ILLEGAL`（跨层）、`CROSS-AGG`（跨聚合）、`分层依赖全部合规`；退出码 0/1。把上面的样例工程放进去跑一遍，应当得到同样的三行结论。

**可退**：规则表改成 warn（只打印不返回非 0），或按目录加白名单；最差情况删掉这条 CI 步骤——检查器只读源码，不产生任何副作用，退回零成本。

## 边界：什么时候别搞这套

| 场景 | 原因 | 替代 |
|---|---|---|
| 纯 CRUD 服务（字段进出，无业务不变量） | 没有领域规则可保护，四层只剩样板 | 三层结构，但把校验集中到一个只依赖标准库的包（[26.3 整洁架构](../26-分层与依赖/26.3-整洁架构.md)） |
| 团队 < 5 人、系统寿命 < 1 年 | 转换与分层的维护成本高于收益 | 模块化单体（[27.2 模块化单体](../27-单体与模块化/27.2-模块化单体.md)） |
| 模型还没稳定 | 边拆边改，包结构一周一变 | 先按上下文分模块，稳定后再落四层 |
| 复杂查询/报表为主 | 查询本就绕开聚合（走 CQRS） | 读模型单独一条路径，不套写模型的四层（[32.1 CQRS](../32-数据模式/32.1-CQRS.md)） |

## 反模式

| 反模式 | 后果 |
|---|---|
| 按数据库表建领域包 | 包边界跟着表走，聚合永不成立，事务边界无从谈起 |
| 聚合之间互相 import | 聚合耦合，拆服务时要连坐改一轮，模型演进能力归零 |
| 应用层写业务规则 | 领域层空心化，四层退化成三层，DTO 与领域对象都成摆设 |
| 领域对象挂 ORM/JSON tag | 内层依赖外层格式，换存储或改接口都要动核心模型 |
| DTO 直接暴露领域对象引用 | 前端字段变更一路穿透到领域层 |
| 仓储实现放聚合包却忘了边界 | 领域包直接拼 SQL、依赖具体数据库驱动，单测必须连库 |
| 用 PO 当接口返回值 | 表结构即对外契约，加一列就是一次破坏性变更 |
| 不写映射表，靠“大家心里有数” | 新人找不到规则在哪，模型与代码半年后各说各话 |

## 自检

**Q1** 一个服务的目录是 `controller/ service/ dao/ model/`，有人说“我们已经分了四层，就是 DDD 了”。按本节判据，缺的是什么？

▸ 答案：缺的是**分包单位**。DDD 的领域层按聚合分包（`domain/order`、`domain/inventory`），业务规则与不变量落在聚合内；`service/` 按技术职责分包，规则照样散在一层里。判据：改一条业务规则，动的是一个聚合包，还是横跨四个技术包。

**Q2** 为什么“聚合之间禁止直接 import”要用脚本卡，而不是靠代码评审？

▸ 答案：评审只能看到 diff 里新增的那一行，看不到依赖图的变化；而跨聚合依赖是**累积形成**的——第一处通常合理（“就查一下”），第十处就让两个聚合不可分割。脚本看的是全图，每次提交都算一遍，成本接近零。

**Q3** 团队把仓储实现放进了聚合包，有人反对：“这违反了依赖倒置”。怎么回应？

▸ 答案：依赖倒置保护的是**领域层不依赖具体基础设施**，接口仍然在领域层，实现被装配进来；把实现文件放在聚合包里，破坏的是“物理分层的纯粹性”，换取的是“聚合整体搬迁”的能力。这是取舍：预期频繁重组就选它，并接受领域包会间接依赖驱动；预期稳定就放基础层。

**Q4** 应用服务里出现了一段“满 100 减 10”的计算，问题在哪？怎么改？

▸ 答案：这是业务规则，属于领域层。放在应用服务里，第二个入口（定时任务、另一个 Facade）就会复制一遍，两处规则迟早不一致。改法：移到聚合根方法或领域服务，应用服务只保留“取聚合 → 调方法 → 保存 → 发事件”的编排。

**Q5** 一个 DTO 需要同时包含订单和库存的信息。让订单聚合去查库存表，行不行？

▸ 答案：不行，那是跨聚合直连数据库。正确做法：应用服务分别调用订单与库存的领域服务（或仓储接口）取回两个 DO，在 assembler 里组装成一个 DTO。代价是多一次查询，换来的是两个聚合可以独立演进。

**Q6** 严格分层要逐层封装，一个简单查询要写三层，值得吗？什么时候不值得？

▸ 答案：值得的前提是“服务会被多个上层复用、且会频繁变更”——这时逐层封装让影响面可枚举。不值得的情况是：服务只有 CRUD 语义、生命周期短、团队小；此时松散分层或三层更快，但要接受“改方法签名时翻遍调用方”的成本。判断依据是**变更频率 × 调用方数量**。

**Q7** 代码模型的复利体现在哪个动作上？

▸ 答案：体现在**搬迁**。聚合包整体搬走（独立成服务或并入别的服务）时，只要包内自洽、跨聚合依赖走应用层，搬迁就是“移动目录 + 改装配”；反过来，聚合之间互相 import，搬一个就要连坐改一圈，模型演进能力归零。

**Q8** 检查器报了 200 条 `ILLEGAL`，团队决定关掉它。更好的做法是什么？

▸ 答案：分三步：① 先把规则改成 warn（只报警不失败），让数据可见；② 按目录/包加白名单，从新代码开始强制；③ 每季度收紧一档，把白名单里已修完的目录移除。一次性全开的检查器，结局一定是被关掉——这和门禁的“渐进式管控”是同一条规律（[52.5 流水线平台](../../L5-工程效能/52-持续集成/52.5-流水线平台十大特征.md)）。
