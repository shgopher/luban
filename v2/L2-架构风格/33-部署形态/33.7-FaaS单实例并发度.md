# 33.7 FaaS 的单实例并发度

## 一句话

> FaaS 里最值钱的旋钮是**单实例并发度**：它把“实例数”和“延迟”绑在一起——IO 型函数调大它，实例数按比例下降、延迟不变；CPU 型函数调大它，实例数不变、延迟按倍数上涨（成本不变，但并发配额被白占）。判断只有一个问题：**这段时间是在等，还是在算？**

**来源**：单实例并发度、扩缩容与 Queue Proxy 的关系、以及层/版本别名等平台特性，来自极客时间《Serverless 进阶实战课》第 3、5 讲；并发度—实例数—延迟的模型与配置策略为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “并发度越大越省钱” | 只对 IO 型成立。CPU 型调大并发度，等于让 c 个请求争一份 CPU，延迟 ×c，为维持 QPS 反而要更多实例 |
| “并发度 = 1 最安全” | 最贵的一种配法：每个并发请求占一个实例。一个等数据库 150ms 的函数，90% 的实例时间在空转 |
| “FaaS 会自动扩缩容，不用管这个参数” | 自动扩缩容扩的是**实例**，它解决不了**单实例内的排队**；并发度决定了要扩多少个实例 |
| “冷启动只跟包体和语言有关” | 并发度高 → 实例少 → 每个实例的请求更密集 → `λT` 变大 → 冷启动概率下降（模型见 [33.3 Serverless 与 FaaS](33.3-Serverless与FaaS.md)） |

## 一个旋钮，三个后果

| 指标 | IO 型（等待可重叠） | CPU 型（计算不能重叠） |
|---|---|---|
| 实例数 | 按 c 倍**下降** | **不变**（CPU 只有一份，吞吐不随 c 变，只把墙钟拉长） |
| 单请求延迟 | 不变 | 约 **×c** |
| 冷启动概率 | 下降（实例更热） | 下降，但延迟已经不可接受 |
| 成本 | 下降 | **不变**（实例数不变；延迟变差、并发配额被白占） |

原因只有一句：**并发度让请求进同一个实例，但 CPU 只有一份**。等 I/O 时可以让出，做计算时只能排队。

## 可运行：5000 QPS 下的两条曲线

```python
#!/usr/bin/env python3
"""concurrency.py —— 同一份负载，单实例并发度改动后：实例数、延迟、成本的走向。

场景：目标 QPS 5000；单请求 = CPU 50ms + 等待 150ms。
  IO 型函数：等待期间可以让出，c 个请求真正并行 → 单实例吞吐 ≈ c / 0.2
  CPU 型函数：计算不能并行，c 个请求排队 → 单实例吞吐 ≈ 1 / 0.2（与 c 无关），延迟 ×c
实例数 = ceil(目标QPS / 单实例吞吐)；成本与实例数成正比（同规格）。
"""
QPS, CPU, WAIT = 5000, 0.05, 0.15
SERVICE = CPU + WAIT          # 单请求墙钟时间（串行时）

print(f"{'并发度':>6}{'IO型实例数':>12}{'IO型延迟':>10}{'CPU型实例数':>13}{'CPU型延迟':>11}")
for c in (1, 2, 5, 10, 20):
    io_thr = c / SERVICE                       # 等待可重叠
    io_inst = -(-QPS // io_thr)                # 向上取整
    cpu_thr = 1 / SERVICE                      # 计算排队：单实例吞吐与 c 无关，c 只把墙钟拉长
    cpu_inst = -(-QPS // cpu_thr)
    print(f"{c:>6}{int(io_inst):>12}{SERVICE*1000:>9.0f}ms{int(cpu_inst):>13}{c*SERVICE*1000:>10.0f}ms")
print()
print("IO 型：并发度 1→10，实例数 1000→100（省 10 倍），延迟不变")
print("CPU 型：并发度 1→10，实例数 1000（不变），延迟 200ms→2000ms")
```

**本机实测输出**（Python 3.14.8）：

```text
   并发度      IO型实例数     IO型延迟      CPU型实例数     CPU型延迟
     1        1000      200ms         1000       200ms
     2         500      200ms         1000       400ms
     5         200      200ms         1000      1000ms
    10         100      200ms         1000      2000ms
    20          50      200ms         1000      4000ms
```

三条读法：

1. **IO 型的实例数严格按 1/c 下降，延迟一动不动**。这是 FaaS 上少见的“白捡”：不改代码，只改一个参数，成本降一个数量级。
2. **CPU 型每加一档并发度，延迟同步翻倍，实例数不变**——成本不变、体验单输，并发配额还被白占。所以“并发度调到 10”不是优化，是选错了函数类型还不自知。
3. **真实函数在中间**：一半时间等 Redis、一半时间算。此时并发度仍能省，但省的比例 ≈ 等待占比。判据还是那句：**等得多就调大，算得多就调 1**。

## 怎么判断你的函数是哪一型

| 信号 | 结论 |
|---|---|
| 并发度调大后 p99 **基本不变** | IO 型 → 继续调大，别犹豫 |
| 并发度调大后 p99 **随 c 线性上涨** | CPU 型 → 退回 1，改用水平扩实例 |
| 火焰图里时间在 `syscall`/网络等待 | IO 型 |
| 火焰图里时间在用户态计算、CPU 打满 | CPU 型 |
| 单实例内存随并发度线性上涨 | 每请求有独立缓冲 → 调大前先确认内存上限 |

> 🔑 一句话判据：**调大并发度，p99 不动就是赚；p99 跟着 c 涨就是在拿延迟换“假省钱”。**

## 和冷启动的关系

[33.3](33.3-Serverless与FaaS.md) 给过冷启动概率模型 `P(冷启动) = e^(−λT)`：λ 是请求率、T 是空闲回收时间。并发度通过**减少实例数**间接提高了单实例的 λ——实例更“热”，自然更少冷启动。

| 并发度 | 实例数 | 单实例请求率 | 冷启动 |
|---|---|---|---|
| 1 | 多 | 低（每实例一个并发） | 多 |
| 10 | 少 | 高 | 少 |

所以对 IO 型函数，调大并发度是**双赢**（省钱 + 少冷启动）；对 CPU 型函数，“少冷启动”的收益远抵不上延迟翻倍的损失。

## 配置策略

| 场景 | 并发度 | 预置并发 | 理由 |
|---|---|---|---|
| 短请求、以等待为主（鉴权、查库、调第三方） | 大（10–50） | 少量 | 等待可重叠，实例数直接降一个量级 |
| 图片/视频处理、编解码、加密 | 1 | 0 | CPU 密集，并发只会互相拖慢 |
| 定时批处理 | 中（5–10） | 0 | 吞吐优先，延迟不敏感 |
| 多租户 / 有状态缓存 | 1 | — | 需要隔离，避免串数据（全局变量复用的坑见 [33.3](33.3-Serverless与FaaS.md)） |
| 关键路径且延迟敏感 | 中 | **足量** | 用预置并发保底，别让冷启动进入 p99 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 所有函数统一设并发度 = 10 | CPU 型函数的延迟翻 10 倍；实例数不变（成本不变），但并发配额被白占 |
| 为了省钱把所有函数并发度拉到最大 | 内存与 CPU 上限被打满，p99 抖动，重试风暴 |
| 并发度 = 1 却不设预置并发 | 实例数最多、冷启动最多，成本与体验双输 |
| 用平均延迟判断并发度效果 | 平均值被短请求拉平，要看 p99 |
| 忽略单实例内存上限 | 并发 10 × 每请求 200MB → 实例 OOM，平台直接杀 |
| 在多租户函数里复用全局客户端 | 并发度调大后租户间串数据 |
| 只看账单不看延迟 | 省下的钱可能是用 p99 换的，业务未必接受 |

## 自检

**Q1** 一个函数 90% 的时间在等数据库，单实例并发度从 1 调到 10，会发生什么？

▸ 答案：实例数降到约 1/10，延迟基本不变，冷启动概率下降——因为等待期间可以让出，10 个请求真正并行。这是 FaaS 上最划算的一次参数调整，不需要改代码。

**Q2** 同一个函数如果把那 90% 改成 CPU 计算，并发度 10 会怎样？

▸ 答案：10 个请求争一份 CPU，每个请求的墙钟时间涨到约 10 倍；为维持同样 QPS，实例数不变（CPU 吞吐不随 c 变），但延迟涨约 10 倍。成本不变、体验单输，并发配额被白占。此时应把并发度退回 1，靠水平扩实例。

**Q3** 为什么“并发度调大后 p99 不变”可以作为 IO 型的判据？

▸ 答案：p99 不变说明请求之间没有争夺同一份资源——等待（网络、磁盘、下游）被真正重叠了。反之，如果 p99 随并发度线性上涨，说明瓶颈在同一实例的 CPU 或内存上，并发只是把排队从实例外搬到了实例内。

**Q4** 并发度与冷启动是什么关系？

▸ 答案：间接关系。并发度高 → 实例数少 → 每个实例的请求率 λ 高 → `λT` 大 → 冷启动概率 `e^(−λT)` 小。所以 IO 型函数调大并发度同时改善成本和冷启动；CPU 型函数虽然也少冷启动，但延迟损失更大。

**Q5** 单实例并发度 1 就等于“最安全”吗？

▸ 答案：不等于。它隔离性最好，但最贵、冷启动最多。对 IO 型函数，1 意味着 90% 的实例时间在空转。安全取决于“是否有共享状态”，不取决于并发度数字。

**Q6** 调大并发度前必须先确认什么？

▸ 答案：两件事——① 单实例的内存上限能否容纳 c 个请求的峰值内存（否则 OOM）；② 函数是否用了全局可变状态（客户端、缓存、租户上下文），并发度高会让它们互相污染。两个都确认了，再调参数。

**Q7** 关键路径函数既要低延迟又想省钱，怎么配？

▸ 答案：并发度取中等（让 IO 重叠），同时给足**预置并发**保底——预置并发负责把冷启动挡在 p99 之外，并发度负责把弹性部分摊薄。两者一个保体验、一个保成本，不能互相替代。

**Q8** 团队说“我们把并发度统一设成 20，账单降了 40%”。该继续推吗？

▸ 答案：先看 p99 和错误率。如果 p99 不变、错误率不变，说明这些函数确实是 IO 型，可以继续；如果 p99 上涨或出现超时重试，说明里面有 CPU 型函数被误伤——应按函数分类配置，而不是全局统一。
