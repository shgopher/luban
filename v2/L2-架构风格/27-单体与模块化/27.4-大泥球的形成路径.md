# 27.4 大泥球的形成路径

## 一句话

> 大泥球不是 “一次设计失败”，而是**五个可识别阶段的连续滑坡**：共享数据库 → 跨模块事务 → 循环依赖 → “公共模块” 黑洞 → 无人敢改；每一阶段都有可观测信号，抓早一步，成本差一个数量级。

## 五个阶段

| 阶段 | 症状 | 可观测信号 | 阻断动作 |
|---|---|---|---|
| ① 共享数据库 | 所有模块读写同一批表 | 任意 schema 变更都要全量回归 | 每模块独立 schema |
| ② 跨模块事务 | 一次请求改 6 张表 | 事务耗时 > 100ms、锁等待上升 | 聚合边界 + 领域事件 |
| ③ 循环依赖 | 改 A 必改 B | `jdeps`/`go list` 出现环 | 提取接口 + 依赖倒置 |
| ④ 公共模块黑洞 | `common` 有 300 个类 | 任何改动都触碰 common | 限制为纯工具，业务下沉 |
| ⑤ 无人敢改 | 新需求一律 “加 if” | 需求评审出现 “这块不能动” | 绞杀者式重构（见 28.5 遗留系统集成 (绞杀者 / 防腐层)（待补）） |

## 代码：把 “环” 找出来

```bash
# Go：列出包依赖图，找环
go list -f '{{.ImportPath}} {{join .Imports " "}}' ./... > deps.txt
# 人工或用工具找环
go run github.com/loov/goda@latest graph ./... | head -30

# Java：包级依赖
jdeps -verbose:package build/classes | grep -- "->" | sort | uniq -c | sort -rn | head
# 判据：出现 A -> B 且 B -> A，或某个包被 20+ 包依赖（公共黑洞）
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 “重构大爆炸” 治理泥球 | 风险与工期不可控，通常半途而废 |
| 只拆目录不拆数据 | 表仍是公共契约，边界无效 |
| 把泥球整体包成微服务 | 分布式泥球：更难查、更慢 |
| 用 “加一层” 掩盖耦合 | 抽象层自身变成新的耦合点 |
| 没有度量就宣称 “在改善” | 循环依赖数、变更影响面都没降 |

## 两条铁律

> 🔑 **先立规则、再动结构**；没有 CI 规则的重构会被下一次 “赶需求” 打回原形。

> 🔑 **一次只治理一类信号**：先把环清零，再处理共享表。

## 自检

**Q1** 为什么 “共享数据库” 排在滑坡的第一位？

▸ 答案：因为它是**所有后续问题的放大器**：表一旦成为公共契约，跨模块事务、循环依赖、公共模块都会随之出现——改表要协调所有使用方，于是大家倾向于 “加字段而不是改结构”，泥球开始堆积。

**Q2** “只拆目录不拆数据” 为什么是假重构？

▸ 答案：因为编译期边界可以被绕过（跨 schema 直接查），而数据模型才是运行期的真实耦合。判断重构是否有效，看 “改一张表要动几个模块”，而不是看目录多整齐。

**Q3** 泥球整体包成微服务会发生什么？

▸ 答案：得到**分布式泥球**：原来的本地调用变成网络调用，延迟与失败模式变多，但循环依赖与共享数据一个没少——只是从 “编译不过” 变成 “运行时报错”。拆分前必须先理清边界。

**Q4** 怎么向管理层证明 “泥球在恶化”？

▸ 答案：用三个可量化指标：**循环依赖数**、**单次变更平均影响模块数**、**回归测试耗时**。三者同向上升时，“需求交付变慢” 就有了归因，而不是 “开发不努力”。
