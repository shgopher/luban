# 30.1 微服务的定义与前提

## 一句话

> 微服务不是“把单体拆小”，而是**用网络边界换独立部署**：它把编译期耦合换成运行期耦合，因此必须先有“发现、可观测、自动发布、幂等重试、独立数据”这五件基础设施——否则拆出来的一定是分布式单体（[30.3 分布式单体反模式](30.3-分布式单体反模式.md)）。

## 定义：四个“独立”

| 维度 | 微服务 | 模块化单体 |
|---|---|---|
| 部署 | 独立进程 / 独立镜像，可单独发布、单独回滚 | 一个制品，整体发布 |
| 数据 | 独占数据库或 schema，只有自己能写 | 共享库，跨模块可有本地事务 |
| 通信 | 网络（RPC / 事件），必须处理超时、重试、幂等、部分失败 | 进程内函数调用，失败即异常 |
| 团队 | 一个小团队端到端拥有（含值班） | 按技术分层，多人共有一个制品 |

四条里**只有“部署独立”和“数据独立”是定义性的**，另外两条是结果。用这个判据看，很多“微服务系统”其实只有第一条：进程分开了，库还是一个——那不是微服务，是分布式单体。

## 网络边界到底贵多少：实测

“用网络换独立”不是免费的。下面这段程序在同机测两种调用的延迟：进程内函数调用，与 loopback 上的 HTTP 调用（进程边界的最小代价模型）。

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sort"
	"time"
)

func addOne(x int) int { return x + 1 }

func main() {
	const N = 20000

	// ① 进程内调用：纳秒级
	start := time.Now()
	s := 0
	for i := 0; i < N; i++ {
		s += addOne(i)
	}
	inProcNs := float64(time.Since(start).Nanoseconds()) / float64(N)

	// ② 本机 loopback 上的 HTTP 调用：只测进程边界，不含跨机网络
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprint(w, "ok")
	}))
	defer srv.Close()

	client := &http.Client{} // 默认 Transport 会复用连接，相当于带连接池的 RPC
	lat := make([]time.Duration, 0, N)
	for i := 0; i < N; i++ {
		t0 := time.Now()
		resp, err := client.Get(srv.URL)
		if err != nil {
			panic(err)
		}
		resp.Body.Close()
		lat = append(lat, time.Since(t0))
	}
	sort.Slice(lat, func(i, j int) bool { return lat[i] < lat[j] })
	p50 := lat[N/2]
	p99 := lat[N*99/100]

	fmt.Printf("进程内调用   %8.2f ns/次（累加和 %d，防止循环被编译器优化掉）\n", inProcNs, s)
	fmt.Printf("HTTP 调用    p50=%8v  p99=%8v\n", p50, p99)
	fmt.Printf("p50 倍数     %.0f×\n", float64(p50.Nanoseconds())/inProcNs)
	fmt.Printf("p99 倍数     %.0f×\n", float64(p99.Nanoseconds())/inProcNs)
	fmt.Println("（本机 loopback，不含跨机网络与序列化；跨机还要再加一个网络往返）")
}
```

本机实测（macOS，Apple M1，Go 1.27）：

```
进程内调用       1.90 ns/次（累加和 200010000，防止循环被编译器优化掉）
HTTP 调用    p50=53.708µs  p99=109.875µs
p50 倍数     28267×
p99 倍数     57829×
（本机 loopback，不含跨机网络与序列化；跨机还要再加一个网络往返）
```

读数：

| 对比项 | 量级 | 含义 |
|---|---|---|
| 进程内调用 | 纳秒 | 一次函数调用的成本可以忽略，所以单体里的“分层/抽象”几乎不花钱 |
| 本机 HTTP | 几十微秒 | 只多了进程边界与协议栈，已经慢近 3 万倍（4 个数量级） |
| 跨机 RPC | 再加网络往返 | 同可用区通常是零点几毫秒的量级（取决于网络，本节未测） |

> 🔑 这个差距决定了后面所有设计的形状：**一次跨服务调用等于几百次函数调用**。所以“多拆一个服务”不是多一个文件夹，是给每一次交互加一笔固定成本；拆分只有在“独立部署带来的收益（发布解耦、独立伸缩、故障隔离）”能覆盖这笔成本时才成立。

## 前提清单：五件基础设施，缺一件就别拆

（部署形态怎么选——容器、编排、Serverless——是 [33.2 微服务部署](../33-部署形态/33.2-微服务部署.md) 的主场，这里只列“有没有”。）

| # | 前提 | 没有它会怎样 | 主场 |
|---|---|---|---|
| 1 | **自动化发布**：一条命令构建 + 部署 + 回滚，无需人工 | 服务数从 1 变 10，发布从“一天一次”变“一天十次人工”，团队被发布拖死 | [55.1 发布策略](../../L5-工程效能/55-发布与回滚/55.1-发布策略.md) |
| 2 | **可观测性**：trace 贯穿、指标按服务打标签、日志带 trace_id | 线上一次超时，要在 10 个服务的日志里手工拼因果，平均定位时间从分钟变小时 | [50.3 链路](../../L4-组件与技术/50-可观测性/50.3-链路.md) |
| 3 | **服务发现 + 配置中心**：实例上下线自动生效，配置不改镜像 | 改一个 IP 要重新发布，扩容要人工改配置；配置漂移无人发现（见 [30.4 服务治理 (注册、发现、熔断、限流)](30.4-服务治理.md)） | [48.2 服务发现](../../L4-组件与技术/48-配置与协调/48.2-服务发现.md) |
| 4 | **幂等与重试语义**：调用方可安全重试，消费方可去重 | 网络超时后重试 → 重复下单、重复扣款；不重试 → 偶发失败变成业务失败 | [25.4 幂等设计与去重](../../L1-分布式原理/25-并发、冲突与幂等/25.4-幂等设计与去重.md) |
| 5 | **数据所有权**：一个服务一份库，禁止跨库 join | 库一共享，任何表结构变更都要多方协调，独立部署立刻失效 | [30.7 跨服务查询与数据聚合](30.7-跨服务查询与数据聚合.md) |

> ⚠️ 这五条是**前置条件**，不是“以后再补”的优化项。第 1、2 条没有时拆微服务，团队会同时失去“快速定位”和“快速修复”两个能力——这是最危险的状态：**故障变多了，排查变慢了**。

## 组织前提：一条比技术更硬的判据

微服务真正的门槛是**团队能不能端到端负责一个服务**：需求、开发、测试、发布、值班、容量，全在同一个小组内闭环。做不到这一点，拆出来的服务会变成“开发团队写、运维团队背”的交接物，发布流程反而更长。

| 组织形态 | 适合 | 不适合 |
|---|---|---|
| 一个 5 人小组端到端拥有 1–3 个服务 | 微服务 | — |
| 前端组 / 后端组 / DBA 组按技术分层 | 模块化单体 | 微服务（每次改接口要跨三个组） |
| 一个团队维护 10 个服务 | 过度拆分（见 [30.2 服务粒度](30.2-服务粒度.md)） | — |

判断方法见 [74.1 康威定律及其逆定律](../../组织/74-康威定律与团队拓扑/74.1-康威定律及其逆定律.md)：**架构边界最终会长成团队边界**，所以先问“我能不能把团队切到服务粒度”，再问“代码怎么切”。

## 源头实践：亚马逊 2002 年的那次会议

微服务不是 2014 年才发明的。2002 年，贝索斯给全公司下过六条硬要求（转引自 Steve Yegge 对 Google 平台的吐槽）：

| # | 要求 |
|---|---|
| 1 | 所有团队的程序模块，都要通过 **Service Interface** 把数据与功能开放出来 |
| 2 | 团队间的信息通信，必须走这些接口 |
| 3 | 除此之外**没有别的通信方式**：不能链接别人的程序、不能直接读别人的数据库、不能用共享内存、不能走后门 |
| 4 | 技术不限：HTTP、CORBA、Pub/Sub、自定义协议都行 |
| 5 | 接口必须从骨子里设计成**能对外界开放**的，为将来开放给全世界程序员做准备，没有例外 |
| 6 | **不这样做的人会被炒鱿鱼** |

这六条把“微服务”的四个前提一次性钉死了：**接口是唯一契约**（对应本节的“通信”）、**数据不能共享**（对应“数据独立”）、**接口要按对外标准设计**、**组织要跟着服务走**。

配套的组织与运维实践，同样比技术更值得看：

| 实践 | 内容 | 与本节的关系 |
|---|---|---|
| **Two Pizza Team** | 一个服务一个小团队，**不超过 16 人**（两张披萨能喂饱），从前端到数据、从需求到上线运维端到端负责 | 对应“组织前提”：服务边界要能装进一个小团队 |
| **按职责分工，而不是按技能分工** | 不是“前端组/后端组/DBA”，而是“订单团队/支付团队” | 与 [74.1 康威定律](../../组织/74-康威定律与团队拓扑/74.1-康威定律及其逆定律.md) 同源 |
| **无专职测试、无专职运维** | 开发自己测试、自己值班，“吃自己的狗粮” | 对应“可观测性”与“幂等重试”为什么是前置条件 |
| **内部服务当外部服务做** | 安全、接口、运维、故障流程全部按对外标准 | 好处是内部服务随时可开放，第一天就具备对外服务能力 |
| **运维优先，拼命自动化** | 简化 + 自动化到能轻松运维上千万台虚机 | 对应“自动化发布”这条前提 |

但原文也没有粉饰代价，列了四条分布式难点：

| 难点 | 表现 | 对策 |
|---|---|---|
| **异构不标准** | API 出错返回 200、body 里写 error（“反人类”，监控没法做）；配置只有一个 key-value，命名与值不规范 | 统一协议、错误码、配置规范（[47.6 API 设计规范](../../L4-组件与技术/47-网关与入口/47.6-API设计规范.md)） |
| **服务依赖** | 依赖链上一环挂掉就多米诺；非关键业务被关键业务依赖，就变成了关键业务；整体 SLA 由最差的服务决定 | 定义服务关键程度与关键调用路径（[30.4 服务治理](30.4-服务治理.md)） |
| **故障概率更大** | 机器与服务多，故障频率更高；几万个监控指标是“使蛮力”，**信息太多等于没有信息** | 定义 Key Metrics；Design for Failure，防火胜于救火 |
| **多层架构运维更复杂** | 基础层/平台层/应用层/接入层任一层出问题都会传导；同一个 KeepAlive 参数在四层里全不一致，行为与文档不符 | 统一规范 + 统一视图，而不是各自为政 |

> 🔑 原文里最狠的一句是“**人管代码，代码管机器，人不管机器**”。它解释了为什么“自动化发布”不是效率优化，而是微服务的前提：服务数一多，人一旦开始管机器，就再也管不过来。

## 破除四个误区

| 误区 | 现实 |
|---|---|
| 微服务 = 服务很小 | “小”不是判据。一个 2 万行、只做发票的服务完全可能是好微服务；一个 2000 行、和另外 5 个服务共享数据库的“小服务”是分布式单体 |
| 微服务 = 用了 Docker / K8s | 容器解决的是打包与调度，不解决数据所有权、幂等、可观测性。上了 K8s 但共用一个库，等于给单体换了个部署方式 |
| 拆得越细越“微” | 粒度是成本函数：每个服务固定成本 6 类资产（见 [29.7 从模型到服务边界](../29-领域建模与边界/29.7-从模型到服务边界.md)），收益随拆分递减 |
| 微服务能解决团队协作问题 | 它只会把协作问题**显性化**：原来一次代码评审能解决的事，变成一次跨服务发布协调 |

## 什么时候别上微服务

| 情况 | 替代方案 |
|---|---|
| 团队 < 10 人、单产品线 | 模块化单体（[27.1 单体架构的适用性](../27-单体与模块化/27.1-单体架构的适用性.md)），用包边界强制上下文 |
| 领域边界还在剧烈变化 | 先做 [29.1 领域、子域、限界上下文](../29-领域建模与边界/29.1-领域-子域-限界上下文.md) 的建模，边界稳定前拆分会反复返工 |
| 没有自动化发布 | 先补流水线，这是“一天发布多次”的前提 |
| 强一致事务为主（资金、库存扣减） | 单体 + 本地事务；拆开就要付分布式事务的成本（[24.9 事务模型选型](../../L1-分布式原理/24-分布式事务/24.9-事务模型选型.md)） |
| 一次性项目、交付即结束 | 单体；微服务的运维投资需要长期摊薄 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 拆了服务，还共享一个库 | 数据不独立，独立部署立刻失效——这就是分布式单体（[30.3](30.3-分布式单体反模式.md)） |
| 接口按“内部调用、先跑通”设计 | 永远不具备对外能力，开放时只能在外面糊一层协议转换 |
| 用“服务很小/代码很少”判断粒度 | 粒度看的是**变化边界与团队边界**，不是行数（[30.2 服务粒度](30.2-服务粒度.md)） |
| 五件前提没齐就开拆 | 故障变多、排查变慢，团队同时失去定位与修复能力 |
| 组织按技能分层，服务按职责拆 | 康威定律反噬：一个改动要跨三个团队协调 |
| 服务上线后丢给“运维” | 开发不懂线上，故障时没人能定位，MTTR 被拉长 |
| 靠人肉管机器（手工扩容、手工改配置） | 服务数一多就管不过来，自动化发布成了空话 |

## 自检

**Q1** 一个 8 人团队把系统拆成 12 个微服务，共用一个 MySQL 库，服务之间用 RPC 互调。用本节的定义判断：这是微服务吗？

▸ 答案：**不是**，是分布式单体。四条定义里“部署独立”成立，“数据独立”不成立——共用一个库意味着任何表结构变更都要 12 个服务协调，且一个服务的慢查询会拖垮全部。它已经付出了微服务的全部成本（网络调用、跨服务排查、12 套部署），却没有拿到任何收益（独立演进、故障隔离）。修复顺序是先拆数据所有权（[30.3](30.3-分布式单体反模式.md)），不是先拆更多服务。

**Q2** 为什么“本机 HTTP 调用比进程内调用慢 3–4 个数量级”这件事，会直接决定服务粒度的上限？

▸ 答案：因为每次拆分都会把一部分原本零成本的交互变成有固定成本的交互。一个业务流程如果原本是 20 次函数调用，拆成 3 个服务后可能变成 2 次 RPC + 18 次函数调用；如果拆成 8 个服务，可能变成 7 次 RPC。按本节实测（本机 loopback 已经是 2.8 万倍，跨机再加网络），7 次 RPC 就足以让一个原本 1ms 的接口变成 5–10ms，并且把可用性从 99.9% 拉到 `0.999^7 ≈ 99.3%`。所以粒度的上限不是“代码还能切多细”，而是“这条链路上能容忍几次跨进程跳转”。

**Q3** 五件前提里，为什么“可观测性”排第二，而不是排在“服务发现”之后？

▸ 答案：因为拆分把**失败模式变多了、定位路径变长了**：一次请求经过 5 个服务，任何一跳超时都表现为“用户说慢”，而你在单个服务的日志里看不到完整因果。没有 trace，排障时间不是线性增长而是指数级（要在 N 个服务里做笛卡尔积式的排查）。服务发现缺失的后果是“改 IP 要重新发布”，痛苦但可绕过；可观测性缺失的后果是“故障无法定位”，不可绕过。

**Q5** 亚马逊 2002 年的六条要求里，哪一条最容易被今天的团队忽略？忽略的后果是什么？

▸ 答案：第 5 条——**接口必须按“将来要开放给全世界”的标准设计**。今天的团队常常按“内部调用、先跑通”来设计接口：错误码随意、字段随手加、鉴权靠内网。后果是这些服务永远不具备对外能力，一旦要开放（给合作方、给前端 BFF、给开放平台），要么重写，要么在外面糊一层网关做协议转换——而协议转换层恰恰是最难维护的那种代码。

**Q4** 一个团队说“我们的服务都很小，每个只有 3000 行，所以粒度很合理”。用本节的判据指出这句话缺了什么。

▸ 答案：缺三个判据：① **数据所有权**——3000 行的服务如果和别的服务共库，仍然耦合；② **端到端归属**——谁值班、谁能独立发布、需求进来后要跨几个团队；③ **调用深度**——12 个 3000 行的服务串成一条链，可用性与延迟都由链长决定，跟单个服务大小无关。代码行数只反映“服务内复杂度”，完全不反映“服务间耦合”，而后者才是微服务的主要成本。
