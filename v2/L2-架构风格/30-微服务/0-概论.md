# 第 30 章 微服务 · 概论

## 一句话

> 微服务不是“把单体拆小”，而是**用网络边界换独立部署**：收益只在“一次变更只发一个服务”时兑现。

## 5 分钟入门：先记住这 8 个词

| 词 | 一句话解释 | 生活类比 |
|---|---|---|
| **微服务** | 几个能各自上线的小程序，靠网络通话 | 一栋大办公室改成几栋小楼 |
| **分布式单体** | 部署分开，改一次仍要几个服务同发 | 共用一本总账 |
| **服务粒度** | 改一次动几个服务，而非单个多大 | 流水线上的工位数 |
| **服务治理** | 找到谁、限多少、失败快点放弃 | 门禁 + 限流栏杆 |
| **Sidecar** | 超时重试搬进同 Pod 的代理 | 店门口统一站一个保安 |
| **共存窗口** | 新旧版本同时在线的那段时间 | 换号期新旧号都能接通 |
| **读模型** | 几个服务的数据拼成查询副本 | 几份报纸剪成一份要闻 |
| **路由** | 先筛候选，再让负载均衡挑 | 先留浦东的店再挑最近 |

> 记住一条：**拆开是拿“调用变贵”换“发布变独立”**，其余小节都在算这笔账。

## 3 个最常见误解

| 误区 | 现实 |
|---|---|
| “服务小就是微服务” | 共库的两千行服务是分布式单体，两万行只做发票的可以是好微服务 |
| “上了 K8s 就是微服务” | 容器只解决打包调度，不解决数据所有权、幂等、观测 |
| “拆开后协作变少” | 只会显性化：代码评审变成跨服务发布协调 |

## 读完自检（入门级 3 题）

**Q1** 12 个服务部署分开，但共用一个 MySQL 库。这是微服务吗？

▸ 答案：**不是**，是分布式单体：共库让表结构变更要 12 个服务协调，成本付满、收益没拿到。

**Q2** 为什么“跨服务调用比进程内调用贵几个数量级”直接限制了能拆多细？

▸ 答案：每次拆分都把近乎零成本的交互换成固定成本；链路串 7 跳，延迟与可用性就按这 7 跳累加（可用性 `p^n`）。

**Q3** 灰度怎么只让 10% 流量打到新版本？

▸ 答案：落在**路由**层：先按版本标签筛出候选，负载均衡再挑，按权重切一部分即灰度——加机器改的是候选集。
