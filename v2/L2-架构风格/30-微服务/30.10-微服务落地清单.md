# 30.10 微服务落地清单

## 一句话

> 微服务不是「拆完就完事」，而是**两张表**：方法篇决定**怎么拆**（粒度、拆分理由、接口风格），基础设施篇决定**拆完靠什么活**（配置、注册、网关、调用、监控、追踪、安全）——**七项基础设施缺一项，微服务就从「灵活」变成「运维地狱」**。

## 先分清：方法篇管设计期，基础设施篇管运行期

| | 方法篇 | 基础设施篇 |
|---|---|---|
| 回答 | 拆成几个、按什么理由拆、接口长什么样 | 拆开之后，服务怎么找到彼此、怎么配、怎么看 |
| 产出 | 服务清单 + 边界 + 接口契约 | 七项平台能力 + 每项的接入方式 |
| 出错的症状 | 拆得太细（跨网络调用爆炸）、拆得太粗（分布式单体） | 一出故障只能靠登机器 `grep` 日志；发一次版要改 20 个配置文件 |

## 方法篇：服务的粒度与拆分理由

**粒度**：本库的主判据是 [30.2 服务粒度](30.2-服务粒度.md) 的「五个数一起看」，以及「三个火枪手」的反向算法：**一个服务 3 个人**，即 6 人团队约 2 个服务、12 人约 4 个，10 人团队约 4 个、100 人约 40 个。为什么是 3 而不是 2 或 4：

| 人数 | 结果 | 原因 |
|---|---|---|
| 1 人 | 单点 | 请假/离职即停摆，没有人 review |
| 2 人 | 偏紧 | 没有第三人打破僵局 |
| **3 人** | **健康** | 规模可被完整理解、可分工、有备份、讨论能收敛 |
| 4 人以上 | 偏松 | 容易出现「只完成任务、不关心设计」的人 |

**拆分理由**：本库认三种**合法**理由（[30.2](30.2-服务粒度.md) 的「拆分的三种合法理由」），行业里常说的五种可以映射到它们：

| 常见说法 | 本库的合法理由 | 判据 |
|---|---|---|
| 按业务逻辑拆 | **不单独构成理由** | 「业务逻辑粗拆细拆都说得通」，必须落到变更/伸缩/隔离 |
| 按可扩展拆 | 独立变更节奏 | 两块发布频率差 ≥ 10 倍 |
| 按性能拆 | 独立伸缩 | 峰值 QPS 差 ≥ 10 倍，或资源类型不同（CPU / GPU / 内存） |
| 按可靠性拆 | 故障隔离 | 一块挂掉不能拖垮另一块 |
| 按安全拆 | 故障隔离 / 合规 | 数据必须物理隔离、独立审计 |

**接口风格**：同步 RPC（强依赖、要立即结果）／异步消息（可最终一致、要削峰）／REST（对外、要通用）。选择依据不是喜好，而是**这条调用能不能接受「等」和「丢」**：不能等 → 同步；能等但不能丢 → 异步 + 重试 + 幂等。

## 基础设施篇：七项，缺一项就退化

| 能力 | 解决什么 | 没有它会怎样 | 本库去哪读 |
|---|---|---|---|
| **配置中心** | 配置与代码分离、按环境/灰度下发 | 改一个超时要重新打包发布；20 个服务 20 份配置 | [48.1 配置中心](../../L4-组件与技术/48-配置与协调/48.1-配置中心.md) |
| **接口框架** | 序列化、超时、重试、熔断、上下文透传的统一实现 | 每个团队自己写一套 RPC，超时语义各不相同 | [42 章 远程调用](../../L4-组件与技术/42-远程调用/0-概论.md) |
| **API 网关** | 统一入口：认证、限流、路由、灰度 | 每个服务各自做鉴权，口径不一；客户端直连几十个域名 | [47.2 API 网关](../../L4-组件与技术/47-网关与入口/47.2-API网关.md) |
| **服务注册发现** | 实例地址动态变化时还能找到对方 | 地址硬编码，扩容要改配置并重启调用方 | [48.2 服务发现](../../L4-组件与技术/48-配置与协调/48.2-服务发现.md) |
| **服务监控** | 指标、告警、容量与 SLO | 只能等用户投诉才知道挂了 | [50.4 度量](../../L4-组件与技术/50-可观测性/50.4-度量.md)、[50.7 SLO 与错误预算](../../L4-组件与技术/50-可观测性/50.7-SLO与错误预算.md) |
| **服务跟踪** | 跨服务的一次请求串起来 | 一个慢请求经过 8 个服务，不知道慢在哪一跳 | [50.3 链路](../../L4-组件与技术/50-可观测性/50.3-链路.md) |
| **服务安全** | 身份、鉴权、传输加密、密钥管理 | 内网裸奔：任一服务被拿下即可横向访问全部数据 | [49 章 身份与访问管理](../../L4-组件与技术/49-身份与访问管理/0-概论.md)、[38 章 安全](../../L3-质量属性/38-安全/0-概论.md) |

另有一项容易被漏掉但同样必需：**数据边界**。每个服务独立持有数据，跨服务只能通过接口拿——共享库是「分布式单体」的入场券（[32.6 共享数据库反模式](../../L2-架构风格/32-数据模式/32.6-共享数据库反模式.md)、[30.3 分布式单体反模式](30.3-分布式单体反模式.md)）。

## 一张可勾选的落地顺序

```text
第 0 步（拆之前，必做）
  [ ] 团队规模 → 反推服务数量（3 人/服务）
  [ ] 每个服务能说出一条合法拆分理由（变更/伸缩/隔离）
  [ ] 关键路径上的服务数 n ≤ 3（可用性 p^n 的账）

第 1 步（先有地基，再拆第一个服务）
  [ ] 配置中心        [ ] 注册发现        [ ] 网关
  [ ] 链路追踪        [ ] 指标与告警      [ ] 统一鉴权

第 2 步（拆的过程中）
  [ ] 每个服务独立数据源，不跨库 join
  [ ] 同步调用有超时 + 重试上限 + 幂等
  [ ] 每个服务有 SLO 与值班 owner

第 3 步（拆完自检）
  [ ] 一次发布不需要同时改 3 个以上服务的配置
  [ ] 任一服务挂掉，能在 5 分钟内定位到是它
  [ ] 新增一个服务，接入成本 ≤ 1 天
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 七项基础设施没到位就开拆 | 拆完没有注册发现与追踪，故障定位靠登机器 grep |
| 按「业务逻辑」拆完就宣布完成 | 粒度没有判据，拆出来的服务边界随组织变动反复改 |
| 先拆服务、后补网关与鉴权 | 每个服务自己做认证，口径不一且重复 |
| 共享数据库「省事」 | 分布式单体：部署分开了，变更还绑在一起 |
| 一个服务 1–2 个人 | 单点：请假、离职、评审都无人兜底 |
| 只上监控不上追踪 | 知道「整体慢」，不知道「哪一跳慢」 |
| 网关承担业务聚合 | 网关一挂即全站挂；聚合应放 BFF（[33.6 BFF 与 API 组合](../33-部署形态/33.6-BFF与API组合.md)） |
| 拆分后没有 SLO | 没人知道「多慢算故障」，告警阈值靠拍脑袋 |

## 自检

**Q1** 10 人的团队，按「三个火枪手」应该有几个服务？
▸ 答案：约 **4 个**（10 ÷ 3 ≈ 3.3，向上取整到 4）。这个数字是**起点不是终点**：再按「三种合法理由」检查每个边界是否站得住；若某个服务找不到合法理由，说明它应该被合并。

**Q2** 为什么「按业务逻辑拆」不算一条独立理由？
▸ 答案：因为业务逻辑**粗拆细拆都说得通**——同一个电商，可以拆成 3 个服务也可以拆成 30 个，两种都能自圆其说。粒度必须落到可验证的判据上：变更频率差、伸缩倍率差、故障隔离要求。否则边界会随组织架构和争论反复变动。

**Q3** 七项基础设施里，哪一项最容易被跳过、后果最严重？
▸ 答案：**服务跟踪**（链路追踪）。它不影响功能上线，所以最容易被推迟；但一旦出故障，「8 个服务里哪一跳慢」无法回答，MTTR 直接从分钟级变成小时级。监控只能告诉你「整体坏了」，追踪才能告诉你「坏在哪」。

**Q4** 为什么「共享数据库」是微服务的红线？
▸ 答案：共享库把服务间的**数据契约**变成了**实现耦合**：任一服务改表结构，其他服务可能被连带改坏，于是所有服务必须一起发布——部署分开了，变更没分开，这就是分布式单体。正确做法是每个服务独立持有数据，跨服务只走接口。

**Q5** 接口风格该选同步 RPC 还是异步消息？
▸ 答案：看这条调用能不能接受「等」和「丢」。**不能等**（用户要立即结果）→ 同步 RPC，并配超时 + 重试上限 + 幂等；**能等但不能丢**（下单后发积分）→ 异步消息 + 重试 + 幂等 + 死信；**对外要通用** → REST/OpenAPI。

**Q6** 微服务到底有没有降低复杂度？
▸ 答案：没有，它只是**把复杂度从代码搬到了基础设施**。原来一个进程内的函数调用，现在变成网络调用，于是必须补上注册发现、超时重试、熔断、链路追踪、配置管理——这些正是七项基础设施。所以「微服务更简单」是错觉，「微服务更适合大团队并行」才是它真正买到的东西。
