# 79.6 OKR：目标管理，不是绩效管理

## 一句话

> OKR 与 KPI 的分水岭不在“有没有数字”，而在**它是不是考核依据**：OKR 靠“对齐”把上下级目标接起来、靠“自评”让承诺兑现；一旦与奖金挂钩，下个季度所有人都会把挑战调到最低——这不是道德问题，是激励设计的必然。

**来源**：OKR 与 KPI 的五维对比、评分四档与信心指数映射、复盘四步法、十个坑，以及「技术目标从产品竞争力识别」来自黄勇《黄勇的 OKR 实战笔记》（极客时间，2019）；检查器与样例为本节补充。

## 先破除五个误区

| 误区 | 现实 |
|---|---|
| “OKR 就是更高级的 KPI” | 核心原理不同：OKR 是**目标对齐**（下级目标达成推动上级目标），KPI 是**指标分解**（下级背上级的数字）。形式上都带数字，机制上完全不同 |
| “KR 全是数字就是好 OKR” | 数字是底线，不是全部。KR 还必须是**结果**，不是任务：“输出 3 份架构文档”有数字，但它是待办事项 |
| “OKR 和 KPI 只能二选一” | 两者正交：**KPI 兜底线**（必须交付的不打折），**OKR 攻上限**（探索与突破）。判据是工作类型：推算型用 KPI，探索型用 OKR |
| “自评太松，要互评 + 排名” | 黄勇《黄勇的 OKR 实战笔记》里记录的一次翻车：自评 + 同事评分 + 主管评分，再按 A/B/C 排名发奖金 → 反馈是“挑战越大分越低”，**下个季度 O 从 3 个变 1 个、KR 全变保守** |
| “目标写不出数字就是没写好” | 有些技术目标一个季度内兑现不了外部结果。此时**诚实写“暂不能衡量”**，比编一个过程指标好——编出来的指标会把团队带向错误方向 |

## OKR 与 KPI：五个维度

| 维度 | OKR | KPI |
|---|---|---|
| **关注对象** | 目标是否达成（野心勃勃） | 指标是否达标（可考核） |
| **核心原理** | 目标对齐：下级达成 → 推动上级 | 指标分解：下级背上级的数 |
| **实操过程** | 员工自己定目标，领导当教练 | 领导下达指标，中间讨价还价 |
| **用户行为** | 主动挑战 | 被动执行 |
| **利益关联** | 不直接挂钩 | 直接挂钩奖惩 |

一句话：**OKR 以过程论成败，KPI 以结果论英雄。**

“不直接挂钩”不等于“无关”。作者给的解耦链条是：

```text
绩效 → 目标 → 成长/贡献 → 岗位级别 → 薪资
```

OKR 管的是“目标 → 成长/贡献”这一段；薪资由岗位级别决定，级别又由长期成长与贡献决定。**钱不是主菜，是甜点**——甜点不是人人有，差异本身就是激励。

> 🔑 一旦把 OKR 评分直接换成奖金，激励方向就反了：**分数高的不再是做得好的，而是把目标定得最低的**。

## 什么时候用哪个：先分清两种工作

| 工作类型 | 特征 | 适合 | 例子 |
|---|---|---|---|
| **推算型** | 有现成指令和方法，按路径达到结果 | KPI | 拧螺丝：一天 1000 颗，合格就发奖金 |
| **探索型** | 没有现成路径，要试各种可能性 | OKR | 做一款用户愿意留下的产品 |

技术团队的现实是**两种混在一起**，所以实践形态是“以 OKR 为主、KPI 为辅”：

| 用途 | 放哪 | 例子 |
|---|---|---|
| 必须交付、不得打折 | KPI（只抓结果，不看过程） | 上线不延期、无 P0 事故、覆盖率不低于 60% |
| 要突破、要看过程 | OKR（既看结果也看过程） | 交付前置时间中位数从 4 天降到 1 天 |

一个可抄的做法（作者团队）：季度末用茶话会做评估，季度初用“一对一”过一遍每个人的 OKR。把团队反复出问题的点（延期、莫名其妙的 Bug、覆盖率低、缺 API 文档、代码不规范、性能差、安全漏洞）**作为 KPI 兜住**，把“怎么变好”交给 OKR。

## 怎么写：O 三条、KR 三条、两个上限

| 对象 | 三条要求 | 反例 |
|---|---|---|
| **O（目标）** | ① 方向明确，人人看得懂；② 对齐（向上对齐 + 水平对齐）；③ 有时间边界 | “做一家成功的企业” → 改成“做一家 102 年的企业” |
| **KR（关键结果）** | ① 有挑战：跳一跳够得着（约五成把握）；② 容易度量；③ **不是任务**，要对 O 产生直接影响 | “每周做一次代码评审”是任务；“评审一次通过率从 62% 提到 85%”才是结果 |

两个上限：**O 最多 3 个，每个 O 的 KR 最多 3 个**。要绝对聚焦就只留 1 个 O——作者的原话是“其他的 O 通常都是多余的”。

“对齐”的准确定义常被误解：**下级目标的达成，能推动上级目标的完成度**。它是“我达成 → 你能往前走”，不是“你把你的数分我一半”。这也是 OKR 与 KPI 在机制上的根本差别。

## 技术团队的 O 从哪来

这是 OKR 在技术团队最容易走偏的一步：把公司销售目标层层分解下来，技术部门分到“交付 X 个版本、消除 Y 个缺陷”——**看起来对齐了，实际上没有任何聚焦作用**。

产品型公司（软硬件与互联网服务）有一条共同的发展路径，技术目标应该从**产品竞争力**里识别，而不是从销售目标里分解：

| 阶段 | 企业目标 | 技术团队该抓的 OKR |
|---|---|---|
| ① 产品原型 | 验证能不能做出来 | 产品试制成功、核心链路跑通 |
| ② 早期用户 | 拿到第一批用户 | 获取早期用户、验证性能与需求满足度 |
| ③ 基本验证 | 验证商业设想 | 用户留存能力、放弃“盲目坚持”的动作 |
| ④ 产品市场适配（PMF） | 找到主流用户 | **识别标杆客户、提升销售转化率、完善关键产品特性、消除量产缺陷、偿还技术债务** |
| ⑤ 增长模式确定 | 找到可复制的增长 | 打造中后台系统、提供数据分析能力、赋能业务团队、提升运营效率 |
| ⑥ 规模化成长 | 放量 | ④⑤ 两阶段目标的放大版：稳定性、成本、产能 |

几条判断经验：

- **外包/交付型团队不需要 OKR**：目标由客户合同给定，本质是交付目标，最合适的管理手段是瀑布式项目管理。
- **PMF 之前，把企业目标定在非产品技术环节上，通常是最令人后悔的决定**——因为此时企业靠产品竞争力推动，不靠销售牵引。
- **成本中心的破法**：技术目标要挂到客户/业务指标上（留存、转化、单位成本），而不是挂在“做了多少功能”上（投入产出视角见 [4.1 技术投入的收益模型](../../需求/4-技术决策与ROI/4.1-技术投入的收益模型.md)）。

### 量化不了怎么办

三步，按顺序：

1. **追问“为谁”**：这个技术目标是为了更好满足哪一类客户/哪个细分市场？该细分市场里证明价值的最佳指标是什么（常是转化率与留存）。
2. **季度内兑现不了外部结果，就不要硬凑过程指标**。过程指标对实现目标往往没有帮助，还会制造“看起来很努力”的假象。
3. **坦诚写“暂时不知道 / 暂时不能衡量”**。作者的原话：OKR 的实际聚焦价值、执行自律度、团队坦诚程度，比它的形式要求更重要。

## 执行与评估：自评 + 四档 + 信心指数

评分只有四档，标准固定死，每个人心里那把尺子才一致：

| 分值 | 含义 |
|---|---|
| **1.0** | 不可能做到，但实际做到了 |
| **0.7** | 希望做到，实际也做到了 |
| **0.3** | 肯定能做到，实际也做到了 |
| **0** | 肯定能做到，但实际没做到 |

分值与“信心指数”对应，这把主观感受变成了可对齐的刻度：

| 定 KR 时的信心 | 完成后的自评 |
|---|---|
| 约 50%（五成把握） | 0.7 |
| 大于 80%（几乎笃定） | 0.3 |
| 小于 10%（几乎不可能） | 1.0 |

两条纪律：

- **只自评，不互评、不排名**。同事与主管并不了解你定这个目标的原因与过程，所谓评分基本是跟着自评分走，只会产生“感情分”。
- **评分不用于比较**。OKR 是“和自己过去比”，不是“和别人比”；排名一出现，挑战就会被系统性调低（《黄勇的 OKR 实战笔记》里的真实后果：下季度 O 数量 3 → 1，KR 全部变成力所能及）。

> ⚠️ 管理者最容易犯的错，是觉得“自评太松”。松不松不在评分环节解决，在**定 KR 环节**解决：定的时候就要把挑战拔到“五成把握”，定完再要求大家自评严格，是本末倒置。

## 复盘：四步，一个都不能少

评估是“给上个周期打分”，复盘是“让下个周期更好”。两者常被合并，结果就是作者说的“有始无终”。

| 步 | 要回答的问题 | 时间盒 |
|---|---|---|
| ① 审视目标 | 为什么定这个目标而不是别的？达成了吗？差距在哪？ | 每人 3 分钟（提前 1 分钟思考） |
| ② 回顾过程 | 分几个阶段？每阶段发生了什么重要事件？ | 每人 5 分钟（提前 3 分钟写要点） |
| ③ 分析得失 | 哪些做得好、为什么好？哪些不够好、为什么？ | 每人 ≤ 10 分钟 |
| ④ 总结规律 | 再做一次会怎么做？沉淀出什么原则与方法论？ | 集体，主持人做分类聚合 |

三条会议纪律：**面对面、总时长 ≤ 3 小时、中间留 10 分钟茶歇**；发言顺序正/逆时针交替，防止互相带节奏；**会前三天发邀请邮件并附上四个问题**，主持人事先自己答一遍做示范——领导不先示范，这场会就会变成一次汇报。

## 可运行：把“KR 是结果不是任务”变成检查规则

“KR 不是任务”这条最容易在评审时被放过，因为它看起来很像样。下面这个检查器把它变成可执行规则：O 数量、KR 数量、是否可度量、是否以行动动词开头、是否缺基线与信心指数。

```python
#!/usr/bin/env python3
"""okr_check.py —— 检查一份 OKR 是否可进入评审。

用法: python3 okr_check.py okr.json
退出码: 0 可评审 / 1 需要修改
"""
import json
import re
import sys

MAX_O, MAX_KR = 3, 3
TASK_VERBS = ("完成", "开发", "输出", "推动", "建设", "实现", "梳理", "编写", "牵头", "落地")
MEASURABLE = re.compile(r"\d")          # 至少有一个数字（数量/比例/阈值/时间）

def check(okr):
    bad, warn = [], []
    if not okr.get("period"):
        bad.append("缺少周期（period）：OKR 必须有时间边界")
    if not okr.get("owner"):
        warn.append("缺少责任人（owner）")
    objs = okr.get("objectives", [])
    if len(objs) > MAX_O:
        bad.append(f"O 有 {len(objs)} 个，超过 {MAX_O}：一个季度能真正推动的目标不超过 3 个")
    for i, o in enumerate(objs, 1):
        krs = o.get("krs", [])
        if not 1 <= len(krs) <= MAX_KR:
            bad.append(f"O{i}「{o.get('o','')}」有 {len(krs)} 个 KR，应在 1–{MAX_KR} 之间")
        for j, kr in enumerate(krs, 1):
            text = kr.get("kr", "")
            tag = f"O{i}.KR{j}「{text}」"
            if text.startswith(TASK_VERBS):
                bad.append(f"{tag} 是任务不是结果：以行动动词开头，写成结果（有数字、可验收）")
            if not MEASURABLE.search(text):
                bad.append(f"{tag} 无法度量：没有数字/比例/阈值")
            if kr.get("baseline") is None or kr.get("target") is None:
                warn.append(f"{tag} 缺少基线或目标值：无法判断「从哪到哪」")
            c = kr.get("confidence")
            if c is None or not 0 < c < 1:
                warn.append(f"{tag} 信心指数缺失或不在 (0,1)：挑战程度无法判断")
    return bad, warn

def main(path):
    bad, warn = check(json.load(open(path)))
    for w in warn:
        print(f"WARN  {w}")
    for b in bad:
        print(f"FAIL  {b}")
    print(f"\n结果：{len(bad)} 条硬问题、{len(warn)} 条提醒 → "
          f"{'需要修改' if bad else '可以评审'}")
    return 1 if bad else 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1]))
```

**本机实测输出**（Python 3.14.8）。一份典型的问题 OKR（4 个 O、两个 KR 其实是任务）：

```text
WARN  O1.KR2「完成灰度发布平台二期建设」 缺少基线或目标值：无法判断「从哪到哪」
WARN  O2.KR2「输出 3 份技术方案文档」 缺少基线或目标值：无法判断「从哪到哪」
FAIL  O 有 4 个，超过 3：一个季度能真正推动的目标不超过 3 个
FAIL  O1.KR2「完成灰度发布平台二期建设」 是任务不是结果：以行动动词开头，写成结果（有数字、可验收）
FAIL  O1.KR2「完成灰度发布平台二期建设」 无法度量：没有数字/比例/阈值
FAIL  O2.KR2「输出 3 份技术方案文档」 是任务不是结果：以行动动词开头，写成结果（有数字、可验收）

结果：4 条硬问题、2 条提醒 → 需要修改
```

按提示改完（删掉第 4 个 O，两个任务型 KR 改成“从 X 到 Y”）：

```text
结果：0 条硬问题、0 条提醒 → 可以评审
```

读法三条：

1. **`FAIL` 里最有价值的是“是任务不是结果”**。这条把评审时最常见的一句争论（“这也算结果吧？”）变成了一次自动判定。
2. **`WARN` 不要忽略**：缺基线意味着“到哪算达成”没说清，缺信心指数意味着“挑战够不够”无法判断，正好是定 KR 环节要补的。
3. **规则要能被团队改写**。`TASK_VERBS` 就是团队的语言习惯，加几个词就能适配自己的团队；规则写死在文档里没人看，写在脚本里每次评审都跑。

## 反模式：十个最常见的坑

| 坑 | 后果 |
|---|---|
| 把 OKR 用于绩效考核、决定奖金涨薪 | **最大的坑**：挑战被系统性调低，OKR 退化成 KPI 的替身 |
| 用 KPI 思维做 OKR | 把绩效指标塞进 KR，只抓结果不看过程 |
| O 数量太多 | 一个季度定 15 个目标，最后完成 1 个 |
| KR 不够量化 | “提高性能/增强安全/改善质量”无法评估，等于没定 |
| KR 写成行动计划或待办 | “每周做一次评审”“输出一张架构图”——做完也不代表目标推进 |
| KR 挑战过高或过低 | 过高注定失败、打击信心；过低拿不到成长 |
| 忽略向上对齐与水平对齐 | 各自发力，聚焦力量被浪费，跨团队协作卡住 |
| 不更新、不追踪 | 定完一周没进度、一月没问题，OKR 变成墙上的海报 |
| 跳过评分环节 | “有始无终”，无法判断目标是否达成 |
| 认为 OKR 可以取代 KPI | 底线失守：该交付的还是没交付 |

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：需要工具承载“公开透明 + 定期更新 + 复盘留痕”时，可选飞书 OKR、Worktile、Tita 一类产品；不想买工具，用共享文档 + 上面的 `okr_check.py` 就够起步。这些产品**未在本机验证**，按各自文档执行。

**可抄**：一份可以直接填的 OKR 模板（也是检查器的输入格式）：

```json
{
  "period": "2026-Q4",
  "owner": "交易平台组",
  "objectives": [
    {
      "o": "把订单链路的交付速度做到团队历史最好",
      "krs": [
        {"kr": "订单服务 P99 从 800ms 降到 200ms", "baseline": 800, "target": 200, "confidence": 0.5},
        {"kr": "订单链路的变更前置时间中位数从 4 天降到 1 天", "baseline": 4, "target": 1, "confidence": 0.5}
      ]
    }
  ]
}
```

**可验**：评审会前跑一次 `python3 okr_check.py okr.json`，判据是 `0 条硬问题`；复盘会前对照四步法逐项确认（四步是否都走完、每步是否有时间盒）。基线与目标值直接从度量体系取数（[59.6 度量体系与数据平台](../../L5-工程效能/59-研发效能度量/59.6-度量体系与数据平台.md)），不要拍脑袋填。

**可退**：OKR 是纯管理动作，最坏情况是“停掉，回到原有方式”，没有技术债。真正的不可逆决策只有一个：**要不要把 OKR 与考核挂钩**——挂上去再撤回，会引发信任问题，所以这条要当成不可逆决策来评估。

## 边界：这些情况别用 OKR

| 场景 | 原因 | 替代 |
|---|---|---|
| 外包/交付型团队 | 目标由客户合同给定，本质是交付目标 | 瀑布式项目管理 + 验收标准 |
| 推算型工作占主导（流水线式重复劳动） | 目标已知、路径明确，OKR 的探索价值用不上 | KPI |
| 组织不透明、不敢说真话 | OKR 要求公开透明（所有人能看到所有人的 OKR） | 先做 [81.1 工程文化](../81-技术文化与知识管理/81.1-工程文化.md)，再谈 OKR |
| 团队 < 10 人、目标每周都在变 | 正式 OKR 的仪式成本高于收益 | 每周目标对齐 + 看板 |
| 把 OKR 当“管理升级”的政绩工程 | 会变成“为 OKR 而 OKR”，团队体验极差 | 先找一个问题，用 OKR 解决它，再推广 |

## 自检

**Q1** 团队把 OKR 评分直接接进绩效奖金，第一个季度效果很好，第二个季度所有人都超额完成。该高兴吗？

▸ 答案：警惕。这是激励设计的必然结果：奖金按分数发，理性选择就是把挑战调低（《黄勇的 OKR 实战笔记》里的真实后果是 O 从 3 个变 1 个、KR 全变保守）。判断信号是**目标本身变保守**，不是完成率变高。要验证，就看 KR 的基线与目标差距是否在缩小。

**Q2** “对齐”与“分解”差在哪？举一个技术团队的例子说明。

▸ 答案：分解是“上级 1 亿 → 你 1000 万”，把你的数当成上级数的一部分；对齐是“你达成，能推动上级往前走”。例：上级 O 是“把获客成本降 30%”，技术的对齐目标可以是“首页首屏从 2.4s 降到 1.2s”（更快 → 转化更高 → 获客成本降），而不是“承担 30% 的成本下降指标”。

**Q3** 一个 KR 写成“完成灰度发布平台二期建设”，问题在哪？怎么改？

▸ 答案：它是任务（行动），不是结果。改法是把“完成之后业务上会怎样”写出来，例如“灰度发布覆盖率达到 80%，发布回滚耗时从 30 分钟降到 5 分钟”，并给出基线与目标值。若确实说不出结果，说明这个 O 还没想清楚。

**Q4** 为什么 OKR 只自评，而不做同事 + 主管互评？

▸ 答案：互评的两个前提不成立：同事不了解你定这个目标的原因与取舍；评分标准各人不同。结果是“跟着自评分走”的感情分，还引入了排名压力。自评把责任放回承诺者身上——**自己的承诺自己兑现**。

**Q5** 技术目标一个季度内看不到业务结果（比如重构），KR 该怎么写？

▸ 答案：三步——① 追问“为哪类客户/哪个细分市场重构，那个市场里证明价值的最佳指标是什么”；② 若季度内确实兑现不了外部结果，不要硬凑过程指标；③ 坦诚写“暂不能衡量”，用里程碑管理交付节奏，但别把它当 KR。作者的原话是：坦诚程度比形式要求更重要。

**Q6** 团队 KPI 已经覆盖了交付质量，还需要 OKR 吗？

▸ 答案：看工作类型。KPI 兜底线（不延期、无 P0、覆盖率达标），OKR 攻上限（把某条链路的交付速度做到历史最好、把团队从被动接需求变成能提案）。只有 KPI 时，团队会停在“不出错”；只有 OKR 时，底线容易失守。两者正交，组合使用才是常态。

**Q7** 复盘会开成“汇报会”，每个人念一遍完成率就结束。缺了哪几步？

▸ 答案：缺“审视目标”（为什么定这个目标）与“总结规律”（再做一次会怎么改）。只回顾过程与得失，会议就退化成汇报。补法：会前三天发四个问题、主持人自己先答一遍做示范、给每步设时间盒（3/5/10 分钟）、最后一步必须产出可复用的原则。

**Q8** 老板要求“这个季度所有部门都上 OKR”。作为技术负责人，你该先问什么？

▸ 答案：先问三个前提：① 我们的目标能否从产品竞争力识别（而不是从销售目标分解）；② 组织是否愿意公开透明、允许挑战失败；③ OKR 会不会被拿去考核。三条有任何一条不成立，就先别全面铺开——用一个小团队跑一个季度，验证“目标真的更聚焦了”，再推广（同 [81.5 DevOps 转型](../81-技术文化与知识管理/81.5-DevOps转型.md) 的试点逻辑）。
