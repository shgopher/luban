# 76.4 冲突处理与共识建立

## 一句话

> 技术冲突多数不是“人对人”，而是**事实不一致或目标不一致**——事实冲突用实验解决，目标冲突用优先级解决，关系冲突用规则解决；共识不是“没人反对”，而是**反对者愿意执行**。

## 先分清：冲突只有三类

| 类型 | 典型表现 | 判据 | 解法 |
|---|---|---|---|
| **事实冲突** | “这个接口是幂等的”“不是” | 有唯一正确答案 | **做实验 / 查文档 / 看代码**，5 分钟定输赢 |
| **目标冲突** | “要快” vs “要稳” | 双方对同一件事的优先级不同 | **由更高层的目标排序**，不是辩论 |
| **关系冲突** | “他上次就坑过我” | 争论内容与议题无关 | **规则**（会议规则、决策机制、升级路径） |

> 🔑 大部分“技术争论”是**被误认的目标冲突**：两个人吵架构，实际是一个人的 KPI 是上线速度，另一个人的 KPI 是稳定性。不把目标摆到桌面上，技术层面永远吵不出结果。

## 一、事实冲突：用实验，不用音量

| 做法 | 例 |
|---|---|
| 把断言变成可验证的命题 | “这个查询走索引吗？” → `EXPLAIN` |
| 谁主张谁举证 | 说“会慢 10 倍”的人，给出压测数据 |
| 承认不确定性 | “我不知道，需要 30 分钟验证” |

事实冲突最忌讳“我觉得”。本书反复用的一条判据：**能算出数的，就不要用形容词**（[58.8 架构优劣的判据](../../L5-工程效能/58-架构治理/58.8-架构优劣的判据.md)）。

## 二、目标冲突：把优先级摆上桌

目标冲突的正确处理不是“谁说服谁”，而是**找到共同的上一级目标**：

```text
争论：这个功能要不要做灰度？
上一级：本季度目标是“零重大事故”还是“抢在竞品前上线”？
        ↑ 这个答案由业务负责人给，不是技术团队内部投票
```

一个可操作的动作：**让双方各自写下“如果只能保一个，保什么”**。写出来的答案往往一致，分歧只是“都想要”。

## 三、关系冲突：用规则，不用情绪

| 规则 | 作用 |
|---|---|
| 会议有议题、有时限（每个议题 15 分钟） | 防止跑题变成人身攻击 |
| 有明确的决策人 | 防止“讨论到最后没人拍板” |
| 反对意见必须记录 | 让反对者感到被听见，也让未来可复盘 |
| 僵持 30 分钟就升级 | 避免消耗战（经验值） |
| 对事不对人：评价方案，不评价提出者 | 降低防御 |

陈皓列的沟通三方式——**尊重、倾听、情绪控制**——解决的是同一件事：**情绪是自己的，别被别人 hack**。捍卫对方说话的权利，不等于同意他的观点。

## 四、共识有五个层次，别把“服从”当“承诺”

“没人反对”不等于共识。用投票快速判断共识层次（本机 `go1.27.1 darwin/arm64`）：

```go
// 共识度判定：支持 / 中立 / 反对 三票，输出共识层次与下一步动作。
func level(support, neutral, oppose int) (string, string) {
	total := support + neutral + oppose
	switch {
	case oppose > 0 && oppose*2 >= total:
		return "分裂", "停：先解决反对者的顾虑，或升级决策人"
	case oppose > 0:
		return "服从", "记录反对意见与理由，约定复盘点"
	case support*10 >= total*8:
		return "承诺", "直接执行，写明负责人与截止时间"
	case support*10 >= total*6:
		return "认同", "执行，但把中立者拉进试点"
	default:
		return "观望", "补证据（试点/数据）后再决策"
	}
}
```

```text
支持=5 中立=0 反对=0 → 承诺：直接执行，写明负责人与截止时间
支持=4 中立=1 反对=0 → 承诺：直接执行，写明负责人与截止时间
支持=3 中立=2 反对=0 → 认同：执行，但把中立者拉进试点
支持=2 中立=3 反对=0 → 观望：补证据（试点/数据）后再决策
支持=1 中立=1 反对=3 → 分裂：停：先解决反对者的顾虑，或升级决策人
```

| 层次 | 含义 | 能不能直接执行 |
|---|---|---|
| 承诺 | 认同目标，愿意投入 | 能 |
| 认同 | 同意方向，但不够投入 | 能，但要拉进试点 |
| 服从 | 不同意但接受决定 | 能，但必须记录反对意见 |
| 观望 | 信息不足，暂不表态 | 不能，先补证据 |
| 分裂 | 明显对立 | 不能，升级或重开议题 |

“服从”是最容易被误判的一层：会上没人反对，执行时却处处拖延——那不是执行力问题，是共识只到“服从”。

## 五、X/Y 问题：别在手段上吵

陈皓提过一个很实用的区分：**真实的问题是 X，大家吵的都是手段 Y**。

| 现象 | 真实问题 X | 手段 Y |
|---|---|---|
| 吵“用 Kafka 还是 RabbitMQ” | 消息要可靠、要能回放 | 具体中间件 |
| 吵“微服务还是单体” | 团队能不能独立部署 | 部署形态 |
| 吵“要不要上 K8s” | 运维人力与弹性需求 | 编排平台 |

处理方式：**先把 X 写出来，确认双方对 X 的理解一致**，再讨论 Y。X 一致时，Y 的分歧通常能用数据解决；X 不一致时，吵 Y 永远没有结论。

### 配套工具：反驳用低维度，说服用高维度

陈皓给的这条规则，正好补上 X/Y 的另一半：

| 目标 | 维度 | 做法 | 例子 |
|---|---|---|---|
| **反驳** | 低维度（越细越好） | 指出具体哪一行、哪个数、哪个假设不成立 | “你说的 500 QPS 是按峰值算的，但压测用的是均值” |
| **说服** | 高维度（越宏观越好） | 从共同的大目标出发，求同存异 | “我们都希望大促不出事故，所以这条链路要不要做双活？” |

为什么要分开？因为**高维度用来找共同点，低维度用来定胜负**。在细节上纠缠“谁对”，永远拉不拢人；只谈大目标不谈细节，又说服不了工程师。正确顺序是：先用高维度确认“我们目标一致”，再用低维度把具体分歧摆清楚。

> ⚠️ 反过来的用法最常见：用低维度反驳去否定对方的**动机**（“你就是不想做”），用高维度说服去回避**具体代价**（“这是公司战略”）。这两招都会让对话迅速崩掉。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用投票解决事实问题 | 少数服从多数，把错的说成对的 |
| 用辩论解决目标问题 | 谁都赢不了，因为目标根本没对齐 |
| 把“没人反对”当共识 | 执行时消极拖延，比明确反对更难处理 |
| 会上不说、会后拉群反对 | 决策被架空，团队信任受损 |
| 升级太早 | 上级被迫做技术判断，且团队失去自主权 |
| 升级太晚 | 30 分钟的争执拖成两周的僵局 |
| 在手段 Y 上争到人身攻击 | 真问题 X 从未被讨论 |

## 自检

**Q1** 两个人吵“这个方案性能不行”，你怎么判断这是哪类冲突？

▸ 答案：先问“性能不行”是可验证命题吗？如果是（能压测、能算 QPS），就是事实冲突，做实验即可；如果双方对“多快算行”标准不同，那是目标冲突，要先对齐 SLO；如果争论中开始出现“你上次就……”，那就是关系冲突，要回到规则。

**Q2** 为什么“服从”不等于共识？

▸ 答案：服从是“我不同意但接受决定”，执行时缺少主动性：遇到问题不会主动解决，而是“等指令”；遇到风险不会预警，而是“按说的做”。它不会立刻失败，但会让决策的执行质量打折。判据：会后他会不会主动补充风险与细节。

**Q3** 什么时候该升级？升级时要带什么？

▸ 答案：同一议题僵持超过 30 分钟、或触及不可逆决策（数据迁移、组织调整）时升级。升级不是“告状”，要带三样：双方观点与依据、已经尝试过的方案、需要上级决定的具体问题（最好给 A/B 选项）。

**Q4** 什么叫“X/Y 问题”？举一个你身边的例子。

▸ 答案：X 是真实要解决的问题，Y 是双方各自坚持的手段。例子：团队吵“要不要引入 GraphQL”（Y），真实问题可能是“前端要减少多次请求”（X）——如果 X 用 BFF 也能解决，那 Y 的争论就是伪争论。识别方法：问“如果 X 被解决了，你还在意 Y 吗？”

**Q5** 会议规则里，“反对意见必须记录”为什么重要？

▸ 答案：它同时服务三件事：让反对者感到被尊重（减少关系冲突）、让决策可复盘（三个月后知道当时担心什么）、让未来有据可查（如果反对的理由成真，能快速定位）。记录不等于采纳，但不记录等于假装没发生。

**Q6** 什么时候该用低维度、什么时候该用高维度？

▸ 答案：**反驳用低维度**——指出具体哪一行、哪个数、哪个假设不成立，越细节越有说服力；**说服用高维度**——从共同的大目标出发，求同存异，越宏观越能拉拢人。顺序上先用高维度确认目标一致，再用低维度摆清分歧；反过来（用高维度压人、用低维度否定动机）只会让对话崩掉。
