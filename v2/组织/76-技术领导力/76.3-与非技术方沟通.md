# 76.3 与非技术方沟通

## 一句话

> 非技术方不关心实现，只关心**成本、风险、时间、收益**四件事——所以跨部门沟通的动作只有一个：把技术指标翻译成这四样，并附上“不做会怎样”。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 把技术讲清楚就行 | 对方不需要理解 QPS，只需要知道“多花多少钱、会不会挂” |
| 对方不懂技术，所以要“简化” | 不是简化，是**换维度**——换成他做决策用的维度 |
| 一次汇报就够 | 跨部门沟通是**持续同步**，不是一次性宣讲 |

## 一、翻译：把技术指标换成四个词

| 技术说法 | 业务语言 | 怎么算出来 |
|---|---|---|
| “QPS 8000，需要扩容” | “大促期间多花 **24 万/年**，否则高峰期会慢到不可用” | 机器数 × 单价 + 存储 |
| “延迟 P99 50ms” | “用户点一下，**半秒内出结果**” | P99 ≈ 用户可感知的卡顿阈值 |
| “要做双活” | “机房挂一个，**业务不停**；代价是多一套机房和 3 人运维” | RTO/RPO → 停机损失 |
| “技术债要还” | “现在每次改需求 **多花 2 天**，一年约 40 人天” | 变更成本 × 频次 |

这条翻译要能跑出来。下面的小工具把 QPS/存储换算成年成本（本机 `go1.27.1 darwin/arm64`）：

```go
// 把技术指标翻译成业务语言：QPS、存储、机器数 → 月成本与年度预算。
for _, p := range plans {
	nodes := p.qps/500*2 + 2            // 单机压 500 QPS，按 2 倍冗余
	storageYear := p.gb / 1000 * 3000   // 每 TB 云盘约 3000 元/年
	year := nodes*10000 + storageYear   // 每台 4C8G 约 1 万/年
	fmt.Printf("%-8s QPS=%-5.0f 机器=%-3.0f 存储=%-5.0fGB 年成本≈%.1f 万\n",
		p.name, p.qps, nodes, p.gb, year/10000)
}
```

```text
现网       QPS=2000  机器=10  存储=500  GB 年成本≈10.2 万 延迟预算=50ms
大促预估     QPS=8000  机器=34  存储=2000 GB 年成本≈34.6 万 延迟预算=50ms
```

有了这两个数，对话就变成：“大促要多花 **24.4 万/年**，换来的是高峰期不卡；不扩容的话，预计 8 倍流量下 P99 会从 50ms 涨到 2s 以上。”——**这是业务方能直接拍板的句子**。

## 二、永远给三个选项

| 选项 | 内容 | 代价 | 收益 |
|---|---|---|---|
| A | 现在扩容 | +24.4 万/年 | 大促无风险 |
| B | 只做限流 + 降级 | 约 2 人周 | 大促部分用户被限流，但不崩 |
| **不做** | 维持现状 | 0 | 大促有较大概率雪崩（给出概率与影响） |

“不做”必须作为一个正式选项写出来。它的作用是**把风险显性化**：选“不做”不是没成本，而是把成本推迟到事故那天。

## 三、风险沟通：用区间，不用点估计

| 做法 | 反例 | 为什么 |
|---|---|---|
| 给区间 | “3–5 天” | 点估计（“4 天”）会被当成承诺，晚一天就是失信 |
| 给概率 | “约 30% 概率出现” | “可能有问题”无法用于决策 |
| 坏消息早说 | 上线前一天才说做不完 | 早说 3 周，对方还有 B 计划；晚说 3 天，只能背锅 |
| 带方案 | “做不完，建议先上 A 功能” | 只报问题等于把问题丢给对方 |

负面信息不隐瞒，而且要**带着解决方案一起说**——这是陈皓列的沟通规则里最实用的一条。

## 四、节奏：1-2-3 反馈

跨部门沟通的响应速度，直接影响信任：

| 响应时限 | 对方是谁 | 说明 |
|---|---|---|
| 1 小时内 | 高级工程师 / 直接合作方 | 不给回音，对方就当你没看到 |
| 2 小时内 | 一线 leader | 他需要拿你的答复去同步别人 |
| 3 小时内 | 上级 / 跨部门负责人 | 超过这个时间，他会绕过你找别人 |

这三档不是教条，而是一个原则：**响应时限要与对方的不确定性成正比**。你越晚回，对方越会自己做假设，而假设通常是悲观的。

## 对客户与对老板：同一套期望管理

客户和老板有同一个特征：**他们不关心实现，只关心自己的目标能不能达成**。所以沟通套路高度相似。

### 先做功课，再开口

| 对象 | 开口前必须知道 | 为什么 |
|---|---|---|
| **客户** | 他的**痛点与 KPI**、行业当下的处境 | 你说“我们技术很强”没用，说“我知道你下半年放贷难”才有用 |
| **老板** | 他的**做事风格**、他的**目标与 KPI**、**他的老板是谁**（风格与 KPI） | 老板的目标来自他的老板；不了解上一层，就会做“正确但没用”的事 |

原文有个细节：见客户前把行业趋势、对方的痛处摸清楚，**不到 20 分钟就能把对方的兴趣拉回来**——靠的不是口才，是功课。

### 先帮他发现问题，再谈方案

客户说的问题，通常是**表面问题**。原文的做法很像定位 Bug：往下挖根因，问“你之前试过什么”，他讲不清楚就请他举例确认。这里同样是 **X/Y**：他说的是手段 Y，真问题是 X；可以质疑 Y、改良 Y，也可以直接给一个 Z 方案。

另外，**报价与方案至少给三套**：低配 / 高配 / 高性价比，并各配一个参照案例。只给一套，对方只能砍价；给三套，他才能比较。

工期被压得太紧时，只有两条路，要当面说清：**保质量就减功能**，或**保主要功能但不全保质量**。还有个常被忽略的事实：**测试与修 bug 的时间，通常比开发本身还多**——把这条摆到桌面上，比事后延期更容易被接受。

### 期望管理的五条原则

| # | 原则 | 说法 |
|---|---|---|
| 1 | **给选择权，永远不要直接说“不”** | “这件事现在做不了，但 A 或 B 可以，你选哪个？” |
| 2 | 降低期望时，**给别的补偿** | “这个版本上不了，但我可以先给你一个临时脚本顶着” |
| 3 | 提高期望时，**附加条件** | “能提前，但需要你帮我协调测试资源” |
| 4 | 大期望**分步骤**达成 | 先给 60%，再给 100%，每步可验收 |
| 5 | **不替对方做决定**，只提供选项并引导 | 你给的是判断依据，不是替他签字 |

这五条与前面的“三个选项”（[二、永远给三个选项](#二永远给三个选项)）是同一件事的两种说法：**选项是形式，期望管理是目的**。

### 跟老板：赢得信任，再谈条件

| 阶段 | 做法 |
|---|---|
| **赢得信任** | 成为骨干：自己的事搞不定叫失职，**别人搞不定的事你能搞定**才叫议价能力；只靠拍马屁，永远只是跟班 |
| **管理期望** | 每次交流都确认“你要的到底是什么”，有偏差立刻反馈；不替老板做决定，给几种方案引导他选 |
| **有分歧时** | 原文给了一个反直觉的招：**沉默是金**——不怒、不硬顶，先不说话；对方会先打破沉默并开始让步，这时再谈条件 |

> ⚠️ 最后这条要慎用：它成立的前提是**你有议价能力**（前面那条信任）。没有能力做底牌的沉默，只会被读成“消极抵抗”。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 QPS/延迟跟业务方对话 | 对方无法判断，只能回“你们技术定” |
| 只报“做不完”，不带方案 | 问题原地反弹，信任下降 |
| 用点估计承诺时间 | 一次延期就被记很久 |
| 隐瞒风险，指望“应该没事” | 出事时连带责任更大 |
| 只给一个方案 | 对方只能同意或拒绝，决策卡住 |
| 越级汇报绕过对接人 | 对接人从合作者变成阻力 |
| 坏消息拖到最后一刻 | 失去所有补救窗口 |

## 自检

**Q1** 为什么“QPS 8000”对业务方没有意义，而“多花 24 万/年”有意义？

▸ 答案：因为决策需要**可比较的量纲**。业务方的预算、人力、时间都是钱和天，QPS 不在他的量纲里；一旦换算成钱/时间/风险，他才能和其他投入比较。换算的依据（单机 500 QPS、2 倍冗余、1 万/台/年）要一并给出，否则数字不可信。

**Q2** 为什么“不做”必须作为正式选项？

▸ 答案：因为“不做”也有成本，只是被推迟到未来（事故、用户流失、加班）。不写出来，风险就被隐性地转嫁给执行团队；写出来，决策者才在知情的情况下承担选择。它还能防止“假装讨论、实则内定”。

**Q3** 为什么给区间而不是点估计？

▸ 答案：点估计会被听成承诺，而工程估算天然有方差；区间把方差显性化，让对方按最坏情况做计划。经验做法：给“最可能值 + 最坏值”，例如“3 天，最坏 5 天”，并说明最坏情况触发条件。

**Q4** 1-2-3 反馈时限的意义是什么？超时了怎么办？

▸ 答案：它对应“对方多久会开始自己猜”。超过时限没回复，对方就会做悲观假设或绕过你。超时的正确处理不是事后解释，而是**先给一个“已收到，X 点前给结论”的短回复**——这能把不确定性关掉。

**Q5** 为什么“带方案报问题”比“如实汇报”更受欢迎？

▸ 答案：因为跨部门沟通的目标是**让对方能做决定**，而不是让他替你解决问题。只报问题，等于把决策成本转移给对方；带方案（哪怕是“A 不行，建议 B，代价是延 2 天”），对方只需选择，沟通效率高一个量级。
