# 76.5 技术愿景与路线沟通

## 一句话

> 愿景不是口号，是**三句话 + 一张分波路线图**：三年后我们在哪、为什么值得去、下一步做什么——讲不清“下一步”的愿景是许愿。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 愿景 = 一句响亮的口号 | 口号解决“听着激动”，愿景要解决“明天做什么” |
| 愿景讲一次就够 | 愿景是**反复对齐**的工具，不是年会节目 |
| 技术愿景只是技术团队的事 | 它要能翻译成业务的钱与时间，否则拿不到资源 |

## 一、三句话：位置、理由、下一步

| 句子 | 要回答 | 反例 | 好例子 |
|---|---|---|---|
| **① 三年后在哪** | 目标状态，可被验证 | “成为一流的研发团队” | “核心交易链路 100% 单元化，单机房故障不影响下单” |
| **② 为什么值得去** | 对团队/业务的具体收益 | “为了技术先进性” | “大促不再靠人肉扩容，故障恢复从 30 分钟到 5 分钟” |
| **③ 下一步做什么** | 未来 3 个月的动作 | “持续优化架构” | “Q1 把订单库拆分，P99 从 200ms 降到 80ms” |

检验方法很土：**让听众复述一遍**。如果三个人复述出三个版本，说明愿景还没成形。

## 二、同一愿景，三种讲法

| 听众 | 关心 | 讲什么 | 时长 |
|---|---|---|---|
| **团队** | 我要做什么、能学到什么 | 目标 + 分工 + 成长机会 | 10 分钟 |
| **老板** | 投入产出、风险 | 成本 + 收益 + 里程碑 + 退路 | 5 分钟 |
| **业务方** | 我的业务会不会受影响 | 上线节奏 + 影响面 + 兜底 | 3 分钟 |

同一件事讲三遍不是重复，是**翻译**。给老板讲“单元化”他听不懂，讲“单机房故障不影响下单，代价是 3 个人 6 个月”，他能立刻判断值不值（[76.3 与非技术方沟通](76.3-与非技术方沟通.md)）。

## 三、路线图：每一波都要能验收

愿景落到执行，就是分波路线图。每一波必须有四样东西，缺一样就会变成“永远在路上的大项目”：

```go
// 路线图分波检查：每一波必须有「可交付物 + 退出标准 + 回滚点」，且时长 ≤ 6 个月。
func check(ws []wave) {
	for _, w := range ws {
		var errs []string
		if w.deliver == ""  { errs = append(errs, "缺可交付物") }
		if w.exit == ""     { errs = append(errs, "缺退出标准") }
		if w.rollback == "" { errs = append(errs, "缺回滚点") }
		if w.months > 6     { errs = append(errs, "单波超过 6 个月") }
		// 有错就打印，无错标 ✓
	}
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
W1 拆读写       ✓ 通过（3 个月）
W2 拆订单       ✓ 通过（5 个月）
W3 数据迁移      ✗ [缺退出标准 单波超过 6 个月]
```

W3 的错误很典型：**9 个月、没有退出标准**——这种“波”实际是一个没有验收点的项目，做到一半没人敢停。拆波的具体方法见 [58.4 演进路线图](../../L5-工程效能/58-架构治理/58.4-演进路线图.md)。

| 要素 | 判据 | 反例 |
|---|---|---|
| 可交付物 | 上线后能被用户感知 | “完成架构升级” |
| 退出标准 | 一个可测的数 | “基本可用” |
| 回滚点 | 出问题时怎么退 | “应该不会出问题” |
| 单波时长 | ≤ 6 个月 | 一年一个里程碑 |

## 四、Leader 与 Boss：愿景靠什么被相信

陈皓把两者的差别列得很清楚：

| Boss | Leader |
|---|---|
| 驱动 | 指导 |
| 让人畏惧 | 让人有热情 |
| 用人事惩罚 | 找方法 |
| 只说 | 展示 |
| 用人 | 发展人 |
| 收割成果 | 给予机会 |
| 命令控制 | 沟通协作 |

一句话：**Leader 是大家跟我一起上，Boss 是大家给我上。**

愿景要被人相信，靠的不是讲得好，而是三件事：

1. **Lead by Example**：陈皓的说法是 *Always Be Coding*——自己不写代码、不看线上，讲的技术愿景没有说服力。
2. **甘当铺路石**：把机会让给下属，把风险留给自己。
3. **描绘方向、提供环境**：告诉团队“去哪”，然后给他们“能去”的条件（工具、时间、权限）。

还有一条常被忽略：**技术领导力的判据是“总是在提供解决问题的思路和方案”**，不是职位。职位给你的是决策权，领导力给的是“别人愿意跟你走”。

## 五、领导力从哪来：四根基与五特征

陈皓把“怎么获得技术领导力”拆成四根基，每一条都能落到动作上：

| 根基 | 具体内容 | 可执行动作 |
|---|---|---|
| **扎实的基础技术** | C、汇编、编程范式、算法与数据结构；系统原理、操作系统、网络、数据库、分布式架构 | 一两年内把书/论文看完，但“用一生来学习” |
| **非同一般的学习能力** | 好信息源、与高手交流、举一反三、不怕困难、开放心态 | 每周一次输出（[78.3 技术分享与成长机制](../78-技术文化与知识管理/78.3-技术分享与成长机制.md)） |
| **坚持做正确的事** | 时间管理、把重复工作写成自动化、掌握前沿技术 | 每季度砍掉一件“手工活”改成脚本 |
| **不断提高要求标准** | 用评分卡自评、技术嗅觉、学以致用、永远在编程 | 每季度自评一次，取最低项补 |

“五特征”是这套根基的外在表现：**尊重技术、追求核心基础技术；用高效自动化工具、避开无效率的架构；解放生产力（把人从劳动密集型转向知识密集型）；沉淀可重用组件；标准高于主流**。这五条不是口号，是五个可观察的判断：你的团队在买“更快的机器”，还是在买“更少的人工”？

### 0–10 分自评卡

陈皓建议用一张 0–10 共 11 档的评分卡定期自评。把它做成一张能填的表：

| 维度 | 0 分 | 5 分 | 10 分 | 本季自评 |
|---|---|---|---|---|
| 基础技术 | 只会用框架 | 懂原理，能排障 | 能改/造轮子，能预判边界 | __ |
| 学习能力 | 靠别人讲 | 能自己找源头 | 能建立知识地图并输出 | __ |
| 做正确的事 | 被需求推着走 | 能排优先级 | 能砍掉不该做的事 | __ |
| 标准 | 随大流 | 有明确标准 | 标准高于主流且能落地 | __ |

> 🔑 评分卡的用法是**取最低项、定下季度动作**，不是算平均分。平均分会让人心安，最低项才会让人进步。

## 反模式

| 反模式 | 后果 |
|---|---|
| 愿景只有形容词，没有可验证目标 | 三年后没人说得清做成了没有 |
| 只有愿景，没有下一步 | 团队激动三天，然后回到原来的节奏 |
| 同一套话讲给所有人 | 老板听不懂收益，团队听不懂分工 |
| 路线图没有退出标准 | 大项目永远差最后 20% |
| 单波超过 6 个月 | 中途需求一变就重排，最后既没交付也没方向 |
| 讲愿景的人自己不写代码 | 团队不信，“你自己都不碰” |
| 把愿景当 KPI 压下去 | 变成口号考核，失去自愿投入 |

## 自检

**Q1** 为什么“三年后在哪”必须可验证？举一个不可验证的反例。

▸ 答案：不可验证的目标无法判断是否达成，也无法拆解成路线图。“成为一流的研发团队”就是反例——什么叫一流？谁评判？可验证的写法是“单机房故障不影响下单”“P99 从 200ms 降到 80ms”，它们都能用监控数据验收。

**Q2** 同一愿景为什么要准备三个版本？

▸ 答案：因为三类听众的决策变量不同：团队要“我做什么、能学到什么”，老板要“花多少、赚多少、风险多大”，业务方要“我的业务会不会断”。同一套话讲给所有人，等于对谁都没讲清。三个版本不是撒谎，是**同一事实的不同投影**。

**Q3** 路线图里“退出标准”和“可交付物”有什么区别？

▸ 答案：可交付物是“交付了什么”（订单服务独立上线），退出标准是“凭什么判定这一波成功”（回归通过率 100%、P99 ≤ 80ms）。只有可交付物没有退出标准，就会出现“上线了但没人敢说成了”的状态，下一波也不敢开始。

**Q4** 为什么单波要限制在 6 个月以内？

▸ 答案：超过 6 个月，中途的需求变化、人员变动、优先级调整几乎必然发生，而长周期项目没有中间验收点，无法判断“该继续还是该停”。拆成 ≤ 6 个月的多波，每波都有退出标准与回滚点，风险被切碎，团队也能持续拿到正反馈。

**Q5** “技术领导力”和“管理职位”是什么关系？

▸ 答案：职位给的是**决策权与资源**，领导力给的是**别人愿意跟随**。有职位没领导力，团队执行但不投入；有领导力没职位，也能推动事情（靠方案与信誉）。判据是陈皓那句：总是在提供解决问题的思路和方案的人，才是有技术领导力的人。

**Q6** 为什么自评卡要“取最低项”，而不是看平均分？

▸ 答案：因为领导力的短板会**直接限制你能推动的事**：基础技术弱，方案会被质疑；学习能力弱，跟不上下一个技术周期；不做取舍，团队会被需求拖死；标准低，产出会持续平庸。平均分高只说明“没有明显缺陷”，但不足以支撑“带方向”；取最低项才能把有限的时间投到回报最大的地方。
