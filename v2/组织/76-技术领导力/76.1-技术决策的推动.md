# 76.1 技术决策的推动

## 一句话

> 技术决策推不动，通常不是方案不够好，而是**没把“技术问题”翻译成“谁的什么损失”**——推动一件事只需要三样：找对决策人、给可验证的证据、留一条退路。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 好方案自然会通过 | 方案再好，也要过“谁出钱、谁背锅、谁被影响”三关 |
| 找最高领导拍板最快 | 越级拍板会绕过受影响的人，落地时被无声抵制 |
| 开会讨论就能形成共识 | 没有决策人与截止时间的会，只是信息交换 |

## 一、先给决策分级：不是每件事都值得走重流程

把所有决策都拿去过评审，团队会被流程拖死；所有决策都自己拍，则迟早踩到大坑。给决策打一个“权重”，按权重选流程：

```go
// 决策可逆性打分：影响面 / 可逆性 / 成本 / 时间压力，各 1–5 分。
// 分数越高 = 越该走轻流程（自己拍板）；越低 = 越该走重流程（评审 + 记录 + 退路）。
func weight(d decision) float64 {
	// 影响面与成本越大、越不可逆，越该慎重
	return float64(d.impact*2 + (6-d.reversible)*2 + d.cost) / 5.0
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
换一个日志库         权重=1.2 → 轻流程：负责人拍板
订单表加索引         权重=1.8 → 轻流程：负责人拍板
拆出支付服务         权重=4.0 → 重流程：ADR + 评审 + 试点 + 回滚预案
自研分布式存储        权重=5.0 → 重流程：ADR + 评审 + 试点 + 回滚预案
```

| 权重 | 流程 | 典型决策 |
|---|---|---|
| < 2.5 | 负责人拍板，事后知会 | 换日志库、加索引、改命名 |
| 2.5–3.5 | 写 ADR + 一次评审 | 换框架、加中间件、拆分模块 |
| ≥ 3.5 | ADR + 评审 + 试点 + 回滚预案 | 拆服务、换存储、自研基础设施 |

判据的核心是**可逆性**：能一天回退的决策，走重流程是浪费；一年都回不去的决策，走轻流程是赌博。

## 二、找对决策人：三类人，缺一不可

| 角色 | 关心什么 | 你要给的 | 找错的后果 |
|---|---|---|---|
| **拍板人** | 预算、风险、优先级 | 选项 + 代价 + 建议 | 方案通过但没人执行 |
| **受影响者** | 我的工作会怎么变 | 迁移计划 + 过渡期安排 | 落地时消极抵制（最贵的一种失败） |
| **否决者** | 合规、安全、稳定性 | 边界条件与兜底方案 | 上线前一刻被叫停 |

> 🔑 推动决策的实际工作量，**80% 花在“受影响者”身上**。拍板人只花 10 分钟，受影响的人会花三个月和你较劲。

## 三、给证据：三级证据，可信度递增

| 级别 | 形式 | 能说服谁 | 成本 |
|---|---|---|---|
| 一级 | 类比 / 大厂案例 | 已经认同你的人 | 1 小时 |
| 二级 | 原型 / Demo / 压测数据 | 技术同行 | 1 天–1 周 |
| 三级 | 小范围试点 + 数据对比 | 拍板人与受影响者 | 2–4 周 |

**能用三级就不用一级**：大厂案例在“规模前提”不同时常被推翻（[58.6 架构设计流程与三原则](../../L5-工程效能/58-架构治理/58.6-架构设计流程与三原则.md) 里的反面案例就是照搬）。试点是最强的说服工具，因为它同时解决“可不可行”和“值不值得”。

## 四、留退路：没有回滚方案的决策，不算决策

| 退路 | 适用 | 成本 |
|---|---|---|
| 特性开关 | 功能级变更 | 低（一个 flag） |
| 灰度发布 | 流量级变更 | 中（需要分流能力） |
| 双写 / 双读 | 存储迁移 | 高（要处理一致性） |
| 保留旧实现 | 大重构过渡期 | 中（双份维护） |

退路要在**决策文档里写清楚**，而不是出事时再想。写退路还有个副作用：它会逼你把方案想得更具体（[55.3 回滚设计](../../L5-工程效能/55-发布与回滚/55.3-回滚设计.md)）。

## 五、把决策留下来

推完决策只做了一半，另一半是**让它可追溯**：背景、备选、为什么选它、代价是什么、什么条件下重开。这就是 ADR（[58.1 ADR 实践](../../L5-工程效能/58-架构治理/58.1-ADR实践.md)）。

没有 ADR 的后果非常具体：三个月后新人问“为什么不用 RabbitMQ”，没人答得上，于是同样的讨论重开一遍——**你为同一个决策付了两次成本**。

## 反模式

| 反模式 | 后果 |
|---|---|
| 所有决策都上评审 | 团队时间被流程吃掉，重要决策反而没人认真看 |
| 只找拍板人、不找受影响者 | 方案通过，落地时被无声抵制 |
| 用大厂案例当唯一证据 | 规模前提不同，试点一做就崩 |
| 决策不留 ADR | 同一问题反复重开，成本翻倍 |
| 没有回滚方案就上线 | 出事只能硬扛或回滚整个版本 |
| 决策会没有截止时间 | 议而不决，团队空转 |
| 用“技术最优”说服业务方 | 对方关心的是成本、风险、时间 |

## 自检

**Q1** 为什么“可逆性”比“影响面”更该决定流程轻重？

▸ 答案：影响面决定“错了有多疼”，可逆性决定“错了能不能改回来”。影响大但可逆（比如灰度中的功能），错了 10 分钟能退；影响中等但不可逆（比如数据格式迁移），错了要修几个月。流程的作用是买“纠错机会”，所以纠错成本越高，流程越该重。

**Q2** 为什么“受影响者”比“拍板人”更值得花时间？

▸ 答案：拍板人只需被说服一次，受影响者要**执行三个月**。他们的阻力不会以反对的形式出现，而是以“最近比较忙”“这个需求要不再评估一下”的形式出现——这类软阻力比明确反对更难处理。提前把他们纳入设计（哪怕只是听意见），阻力会变成动力。

**Q3** 三级证据里，为什么“试点”的说服力最强？

▸ 答案：因为试点同时回答两个问题——“技术上可行吗”和“业务上值得吗”，而且用的是**对方能验证的数据**，不是你的类比。大厂案例只能回答“别人做成过”，无法回答“在我们这里成不成”。试点还有个副作用：它本身就是灰度上线，把风险提前释放了。

**Q4** 一个决策没有回滚方案，还能推吗？

▸ 答案：可以推，但要当作“不可逆决策”对待：流程升级（评审 + 试点 + 备份 + 演练），并且明确写下“最坏情况是什么、出了事怎么办”。没有回滚方案又不肯升级流程，本质是把风险转嫁给值班的人。

**Q5** 为什么“技术最优”往往说服不了业务方？

▸ 答案：因为业务方不在你的目标函数里。他关心的是成本、风险、上线时间、能带来多少收益；你关心的是延迟、扩展性、维护成本。两者不是对错关系，是**维度不同**——正确做法是把技术指标翻译成他的四个维度（[76.3 与非技术方沟通](76.3-与非技术方沟通.md)）。
