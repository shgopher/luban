# 76.2 与技术团队沟通

## 一句话

> 对工程师，沟通的目标不是“我说清楚了”，而是**双方用同一套术语与事实做了同一个决定**——三个动作：统一术语、结论先行、把答案变成问题。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 说清楚就行了 | 没说清的是“对方要做什么决定”，不是“你的方案多好” |
| 写个文档就完成了沟通 | 文档是异步沟通的起点，没有交互确认就不算完成 |
| 技术人不用练沟通 | 陈皓的说法是：**Talk 并不 cheap，Code 才是其中比较 cheap 的** |

## 一、统一术语：同一概念只用一个词

这是最便宜、也最容易被忽略的一条。看本书自己的数据（命令与真实输出）：

```bash
for pair in "幂等:idempotent" "熔断:circuit breaker" "灰度:canary"; do
  a=${pair%%:*}; b=${pair##*:}
  ca=$(grep -ro "$a" --include=*.md v2 | wc -l | tr -d ' ')
  cb=$(grep -roi "$b" --include=*.md v2 | wc -l | tr -d ' ')
  printf "%-8s 中文=%-4s 英文=%-3s\n" "$a" "$ca" "$cb"
done
```

```text
幂等       中文=942  英文=10
熔断       中文=264  英文=2
灰度       中文=379  英文=116
```

读法：幂等、熔断基本统一（混杂率 < 4%），**灰度/canary 混用率约 23%**——同一个概念两个词，检索时就会漏一半。

三条规则：

| 规则 | 做法 | 反例 |
|---|---|---|
| 一个概念一个词 | 团队术语表（[83.1 术语表](../../附录/83-附录/83.1-术语表.md)），首次出现标英文 | 一会儿“灰度”一会儿“canary” |
| 到源头取信息 | 转发别人“嚼过”的结论前，先找当事人确认 | 三层转述后意思已经反了 |
| 术语要能检索 | 英文名写进注释或标题 | 代码里叫 `Gray`，文档里叫 `canary` |

## 二、结论先行：信息太多等于没信息

对工程师，最有效的结构是 **BLUF（Bottom Line Up Front）**：

```text
① 结论/请求：需要你决定什么（一句话）
② 依据：3 条以内，带数字
③ 备选：A / B / 不做，各自代价
④ 截止：什么时候要答复
```

为什么？因为 **信息太多等于没有信息**。一封三千字的邮件，读者只会记住最后一句话；一份没有结论的设计文档，评审会变成“大家还有问题吗”。

## 三、反馈闭环：复述与提问

| 动作 | 做法 | 作用 |
|---|---|---|
| 复述确认 | “我的理解是 X，对吗？” | 确认解码一致，避免各说各话 |
| 不懂就问 | 当场问，别装懂 | 效率的关键不在快，而在**准确** |
| 没有交互就止损 | 讲了三分钟对方没反应，停下来问 | 把独白变成对话 |
| 把答案变成问题 | 不问“怎么办”，问“你觉得 A 和 B 哪个更合适，为什么” | 让对方参与决策 |

最后一条尤其重要，它同时是**带人**的方法：**永远不要直接给答案，要让对方给答案，而且要多个**。给答案只能解决这一次，逼他思考能解决下一次。

## 四、技术沟通的三个场景

| 场景 | 目标 | 关键动作 |
|---|---|---|
| 需求对齐 | 确认“做什么、不做什么” | 用边界说话（清单比描述清楚） |
| 方案评审 | 暴露风险，而不是比谁对 | 先讲失败模式，再讲方案（[58.3 架构评审](../../L5-工程效能/58-架构治理/58.3-架构评审.md)） |
| 故障沟通 | 让所有人知道现状与下一步 | 事实、影响、动作、下次更新时间 |

故障沟通最容易出问题：技术人习惯先解释原因，而对方只想知道“现在怎么样、什么时候好”。四段式模板见 [56.5 事故响应](../../L5-工程效能/56-稳定性工程/56.5-事故响应.md)。

## 向下沟通：一对一与绩效

带人之后，沟通对象从“同事”变成“下属”，难点集中在五件事上。陈皓给的这套做法可以直接照做：

### 一对一：以员工为中心

| 项 | 做法 |
|---|---|
| **频率与时长** | 每半个月一次，每次 30–60 分钟，不要太长 |
| **谁为中心** | **员工**，不是管理者；管理者的动作是倾听，不是教育 |
| **聊什么** | 四块：工作状态、个人发展、公司/组织、**Leader 自己**（请员工评价你） |
| **找谁聊** | 直接下属；另外可以跳过层级，找团队里的**骨干**（团队不愿意失去的人）聊 |
| **气氛** | 将心比心，让他敢说真话——**“直言不讳”的员工是宝**，因为不用你猜 |

> 🔑 一对一最常见的失败，是把它开成“进度汇报会”。进度在站会上讲，一对一讲的是**状态、成长和不满**。

### 绩效：平时给反馈，别秋后算账

原文里有个“翻车现场”：转岗员工被原负责人当面说“你程序写得不好”，她当场反问：“你当时为什么不说？你接受了，就说明我达标了。”

| 错误做法 | 后果 | 正确做法 |
|---|---|---|
| 年底一次性算总账 | 员工震惊、对抗，绩效会变成吵架 | **平时就给反馈**：哪段代码松、哪个 bug 是低级错误 |
| 以指责的姿态反馈 | 激起情绪，听不进内容 | **帮助的姿态**：我是在帮你，不是在审判你 |
| 只谈结果不谈改进 | 员工知道差，但不知道怎么做 | 给具体改进方案，并共情、用高维度沟通 |

### 特立独行、挽留、劝退

| 场景 | 做法 | 判据 |
|---|---|---|
| **能力强但特立独行** | ① 给他匹配的人（更强的或旗鼓相当的）一起干；② 给独立、有挑战的工作（IC，Individual Contributor） | 反复沟通无效、又特别矫情时，**明确、无二义地说清要求** |
| **要不要换掉他** | 算一笔账 | **你在他身上花的精力与时间成本，大于到外面找更好或相当的人时，坚决替换** |
| **想挽留** | 先让他吐槽，认同他、甚至说点公司的坏话，降低心理界限，让他讲真原因；挽留不成做朋友，帮他介绍工作 | 前兆是**变得不积极、开始抱怨**——抱怨说明还在乎，这时才是挽留时机；摊牌或漠不关心时，机会很小 |
| **要劝退** | 给 1 个月缓冲期 + 明确目标；用“职责 vs 成绩”的**无可辩驳的证据**；给面子（让他被“挖走”） | 分手那天谈事实，不谈情绪；事儿是事儿，人是人 |

> 💡 原文还有一个观察：**任何员工、任何事，干两年就是一个大限**，离职率极高——所以关键岗位的交接与文档，要按“两年一换人”来准备。

## 反模式

| 反模式 | 后果 |
|---|---|
| 同一概念中英混用 | 检索漏一半，新人学两套词 |
| 转发未经求证的二手结论 | 三层转述后语义反转 |
| 文档没有结论段 | 评审会变成提问会，决策无限期推迟 |
| 讲话以背景开头讲十分钟 | 听众不知道你要什么，注意力早已耗尽 |
| 用“你可能不懂技术”开场 | 对方立刻进入防御状态 |
| 只给一个方案 | 要么被否，要么被拖着 |
| 会上不说、会后抱怨 | 决策已定，只能执行或消极抵抗 |

## 自检

**Q1** 为什么“统一术语”是技术沟通里性价比最高的一条？

▸ 答案：因为术语是**检索与复用的入口**。同一个概念两个词，搜索就漏一半，新人要学两套，文档之间无法互相引用；而统一的成本极低（一次术语表 + 一次评审约定）。本书的数据：幂等/idempotent 混杂率 < 3%，灰度/canary 约 23%——后者的检索体验明显更差。

**Q2** 「信息太多等于没有信息」在工程上怎么落地？

▸ 答案：每份文档/邮件强制一段“结论与请求”，放在最前面；正文按“依据 → 备选 → 截止时间”组织；超过两页的文档先给一页摘要。判据：**读者只看第一段，能不能做出你要他做的决定**。

**Q3** 为什么“把答案变成问题”既能沟通又能带人？

▸ 答案：给答案会让对话终止（他照做，但不知道边界）；提问会让对方暴露自己的推理过程，你能看到他在哪一步想错了，也能让他自己发现漏洞。长期效果是：他下次能自己判断，而不是每次都来问你。

**Q4** 故障沟通为什么不能先讲原因？

▸ 答案：因为听众在信息不全时最需要的是“我现在该做什么”。原因分析需要时间且容易反复（先说是 A，后来说是 B），只会制造不信任。正确顺序是：影响 → 已采取的动作 → 下次更新时间；原因等定位清楚再给。

**Q6** 一对一会议为什么强调“以员工为中心”，而不是“以管理者为中心”？

▸ 答案：因为一对一是**员工唯一能安全表达状态与不满的场合**。以管理者为中心，它会退化成进度汇报（站会已经做了）；以员工为中心，才能听到“最近状态不好”“想换方向”“对某件事有意见”这些在公开场合不会说的话。前兆信息只能在这种场合拿到，而它决定了你是提前介入，还是等人提离职。

**Q5** 为什么“只给一个方案”在技术沟通里是劣势？

▸ 答案：一个方案把对方逼进“同意/不同意”的二选一，不同意就得罪人，于是最常见的反应是“再评估一下”——决策被无限期推迟。给 A/B/不做三个选项，对方的反对就有了落点（他可以选 B），决策反而更快。
