# 75.2 平台团队与中台

## 一句话

> 平台是**产品**，不是项目——判据是有没有内部用户、SLA、自助入口与采用率；中台失败的根本原因不是技术，是“为共享而共享”，把业务差异硬塞进一个中间层。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 平台 = 把运维工具打包 | 平台的用户是**开发**，交付物是“自助 + SLA + 文档”，不是一堆工具 |
| 中台 = 更高级的平台 | 中台是**共享范围**的描述，不是团队类型；共享错了就是灾难 |
| 平台要靠“强制接入”推广 | 强制只能带来“形式接入”，采用率与体验才是真的 |

## 平台 vs 项目 vs 中台

| 维度 | 项目 | 平台 | 中台 |
|---|---|---|---|
| 用户 | 甲方/业务方 | **内部开发者** | 多条业务线 |
| 交付物 | 一次交付、验收即结束 | 持续演进的产品 + SLA | 共享能力 + 接入规范 |
| 成功判据 | 按时验收 | **采用率 + 自助率 + 满意度** | 业务线复用带来的边际成本下降 |
| 失败形态 | 延期 | 没人用（成本中心） | 为共享而共享，业务差异被强塞 |

> 🔑 平台的第一个用户是**自己公司的开发**；没有内部用户的“平台”，本质是一个没有客户的项目。

## 平台必须交付的四样东西

| 交付物 | 判据 | 没有会怎样 |
|---|---|---|
| **SLA** | 可用性、延迟、支持时间写清楚 | 业务不敢依赖，绕过自建 |
| **自助入口** | 一条命令/一个页面完成接入 | 每次接入都提工单，平台变成瓶颈 |
| **文档与示例** | 30 分钟内跑通第一个例子 | 学习成本转嫁给业务，采用率上不去 |
| **路线图** | 用户能提需求、知道优先级 | 平台闭门造车，做出来的没人用 |

## 采用率：平台的唯一硬指标

```go
// 平台采用率 = 已接入服务 / (全部服务 − 明确豁免)
rate := 100 * float64(on) / float64(total-exempt)
if rate < 70 {
	fmt.Println("结论：平台不是默认路径——先修 DX（文档/自助/错误信息），再谈强制")
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
服务=6 已接入=3 豁免=1 采用率=60%
结论：平台不是默认路径——先修 DX（文档/自助/错误信息），再谈强制
```

读法：

- **豁免要有理由与期限**，否则豁免会变成“永久不接入”的通道；
- 采用率低于 70% 时，先修 **DX（开发者体验）**：文档、自助、错误信息、接入耗时；
- 高于 90% 且稳定后，才值得设“准入门槛”（比如新服务必须走平台）。

## 中台为什么会失败

| 失败原因 | 表现 | 根因 |
|---|---|---|
| **为共享而共享** | 把不同业务线的差异抽象成一个“通用能力” | 共享的前提是**共性足够大**，不是“组织上想共享” |
| 边界画错 | 中台管到业务逻辑，业务线无法差异化 | 中台应停在“能力”，不进入“策略” |
| 组织没配套 | 中台没有定价、没有 SLA、没有退出机制 | 业务线用脚投票，绕过去 |
| 考核错位 | 中台考核“接入数量”，不考核“业务效果” | 数字好看，业务变慢 |

> 🔑 判断一个中台该不该存在，只问一句：**去掉它，两条业务线会重复造多少东西？** 如果答案是“几乎不重复”，它就不该叫中台，最多是一个共享库。

## 反模式

| 反模式 | 后果 |
|---|---|
| 平台没有 SLA | 业务不敢依赖，自建替代 |
| 接入要提工单排队 | 平台成为交付瓶颈，采用率下滑 |
| 用“强制接入”代替体验改进 | 形式接入，实际绕开（在平台外写脚本） |
| 中台把业务策略也收上来 | 业务线失去差异化能力，创新停滞 |
| 平台团队按“功能数量”考核 | 做了一堆没人用的功能 |
| 平台与业务共用同一套排期 | 平台需求永远排在业务之后，越拖越烂 |
| 没有豁免与退出机制 | 遗留系统被永久卡住，采用率永远上不去 |

## 自检

**Q1** 怎么判断一个“平台团队”是真平台还是伪平台？

▸ 答案：看三件事：**有没有内部用户名单**（谁在用）、**有没有 SLA**（敢不敢依赖）、**接入是不是自助**（要不要提工单）。三样缺一样，它就更像一个运维项目：用户是被指派的，故障没有承诺，接入靠人。

**Q2** 采用率 60% 时，为什么不该先“强制接入”？

▸ 答案：因为低采用率通常是**体验问题**（文档缺失、接入要两周、错误信息看不懂），强制只会让团队“形式接入、实际绕过”——在平台外写脚本、把服务注册进去但不用它的能力。正确顺序是先修 DX，把采用率做到 70% 以上，再设门槛。

**Q3** 中台与平台的核心区别是什么？

▸ 答案：**共享范围与服务对象**。平台服务的是“内部开发者”，目标是让交付更快；中台服务的是“多条业务线”，目标是让共性能力只造一次。区别不在技术，而在“共享的边界是否成立”——共性不够大时，中台就是强行把差异塞进一个中间层。

**Q4** 中台该管到哪一层为止？

▸ 答案：管到**能力**，不管**策略**。比如“支付能力”（下单、退款、对账）可以做中台；“这款商品该不该打折”是业务策略，必须留在业务线。越过这条线，业务线就失去差异化能力，中台也会被业务变化拖着频繁改。

**Q5** 平台团队该怎么被考核？

▸ 答案：考核**采用率、自助率、接入耗时、满意度**，而不是功能数量。功能数量会诱导团队做“看起来厉害但没人用”的东西；采用率与接入耗时直接反映“平台有没有让业务更快”，也逼团队去修文档与自助。
