# 75.4 跨团队协作与接口人

## 一句话

> 跨团队协作的成本不在“沟通”，在**交接**——每交接一次就丢一次上下文；接口人的作用不是传话，而是**持有契约**：谁改、谁验收、出问题找谁。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 接口人 = 传话筒 | 传话筒会把信息衰减成“转述”；接口人要能**对契约拍板** |
| 多开会就能对齐 | 会越多，决策越分散；对齐靠契约，不靠会议数量 |
| 有文档就能异步协作 | 文档会腐烂；能自动验证的契约才靠得住 |

## 三种协作模式，按成本排序

| 模式 | 做法 | 成本 | 什么时候用 |
|---|---|---|---|
| **同步协作** | 两个团队一起干一段时间 | 最高（会议 + 互相等待） | 新边界探索、复杂特性 |
| **异步契约** | 一方提供接口/文档/SLA，另一方自助接入 | 中 | 稳定的能力复用 |
| **接口人** | 每个团队指定一人持有契约、处理变更与仲裁 | 低 | 多团队、频繁变更 |

> 🔑 顺序是：能异步就不协作，能自助就不找接口人。**接口人是异步契约的兜底，不是默认通道。**

## 接口人到底持有什么

| 职责 | 具体内容 | 不做的后果 |
|---|---|---|
| **契约 owner** | 接口/IDL 的变更由他确认，字段只加不删 | 消费方各自改，联调时全对不上 |
| **变更评审** | 破坏性变更要走版本与迁移计划 | 悄悄改字段，消费方线上报错 |
| **验收** | 消费方接入后由他确认“按契约工作” | 接了但用错，出问题互相推 |
| **升级路径** | 争议升级到谁、多久内答复 | 争议卡在中间层，项目停摆 |
| **台账** | 谁在用、用在什么场景、什么版本 | 下线时不知道谁在用 |

## 契约要写成能验证的东西

许式伟对“共识”的要求是**精确、无歧义**；接口用代码表达，是唯一能被机器验证的共识。跨团队契约最小可以写成这样：

```yaml
# contracts/order-to-payment.yaml
provider: order-team          # 谁提供
consumer: payment-team        # 谁消费
interface: POST /v1/payments  # 接口
sla:
  latency_p99_ms: 200
  availability: 99.95
errors:                       # 错误码也是契约
  - code: PAYMENT_DUPLICATED
    meaning: 幂等键重复，消费方可安全重试
  - code: PAYMENT_LIMIT_EXCEEDED
    meaning: 超限，不可重试
versioning: additive-only     # 只加不删；破坏性变更需新版本
owner: 张三（order-team）      # 接口人
```

这份契约同时解决了三件事：**字段与语义**（不会联调才发现对不上）、**错误码与重试语义**（消费方知道什么能重试）、**责任人**（出问题找谁）。

## 交接次数：先把成本数出来

跨团队协作的代价可以近似成“交接次数”。沿着调用链数一数：

| 链长 | 一次改动要协调的团队 | 典型现象 |
|---|---|---|
| 1–2 跳 | 1–2 个 | 一个 PR 搞定 |
| 3 跳 | 3 个 | 上线前要三方对齐 |
| **4 跳以上** | 4+ 个 | 每次发布都要开会，故障定位靠群聊 |

链长的算法与判据见 [74.3 团队边界与架构边界的对齐](../74-康威定律与团队拓扑/74.3-团队边界与架构边界的对齐.md)（本机实测：4 跳链意味着四个团队要协同发布）。**接口人能降低单次交接的成本，但降不了交接次数**——次数要靠边界重画解决。

## 反模式

| 反模式 | 后果 |
|---|---|
| 接口人由不参与技术决策的人担任 | 只会传话，契约变更照样失控 |
| 接口人同时是 5 个团队的接口人 | 变成瓶颈，响应时间以天计 |
| 契约没有错误码与重试语义 | 消费方猜着重试，重复扣款 |
| 契约变更只发通知不评审 | 破坏性变更悄悄上线 |
| 用“协作”代替边界重画 | 两个团队长期耦合，等于没拆 |
| 只维护消费方名单，不维护版本 | 下线时才发现还有人用旧版本 |
| 争议没有升级路径 | 卡在接口人之间，项目停摆 |

## 自检

**Q1** 接口人最重要的职责是什么？为什么不是“传话”？

▸ 答案：**持有契约并对契约拍板**：确认变更、评审破坏性变更、验收接入、维护台账。传话只传递信息，不承担决策；而跨团队协作的失败大多不是“没听到”，是“听到后各自理解”。接口人要能把分歧收敛成一个可执行的契约。

**Q2** 什么时候该用接口人，什么时候该直接重画边界？

▸ 答案：接口人降低的是**单次交接成本**（沟通、评审、验收），适合“边界合理但变更频繁”的情况；如果交接**次数**本身就多（链长 4 跳、一个需求跨 3 个团队），接口人只会让每次交接更规范，却不会让交付更快——这时该重画边界，把一条业务流收进一个团队。

**Q3** 为什么契约里必须写错误码与重试语义？

▸ 答案：因为跨团队调用失败是常态，而“能不能重试”决定了消费方是重试、降级还是报错。没有错误码语义，消费方只能猜：猜“超时”可重试，可能重复扣款；猜“超限”不可重试，可能丢单。错误码是契约的一部分（[40.6 错误处理](../../L3-质量属性/40-可维护性/40.6-错误处理.md) 讲过同一原则）。

**Q4** 为什么说“有文档就能异步协作”不完全对？

▸ 答案：文档会腐烂，且无法被自动验证；跨团队契约需要**能被 CI 校验**的东西（OpenAPI、protobuf、contract test）。文档适合解释“为什么”，契约适合约束“必须怎样”——两者分工，不能互相替代。

**Q5** 接口人制度最容易退化成什么？

▸ 答案：退化成**传话筒 + 审批岗**：所有跨团队沟通都必须经过他，他不在就卡住；他不拍板只转达，问题在两边来回。避免方式是明确他的三项权力（变更否决、验收、升级），并限制他同时负责的团队数——超过 2–3 个，就应该拆成多个接口人或重画边界。
