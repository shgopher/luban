# 75.1 组织形态（职能型 / 项目型 / 矩阵 / 部落）

## 一句话

> 四种形态没有优劣，只有**代价落在哪**：职能型优化专业深度、项目型优化交付速度、矩阵两头都要但两头都贵、部落制优化端到端但要求平台能力——选形态就是选“你愿意付哪种协调成本”。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 组织形态有“最佳实践” | 形态要匹配业务的不确定性；稳定业务用项目型，会被反复重组拖死 |
| 矩阵制是“既要又要”的先进方案 | 矩阵把协调成本做成常态，**双线汇报**是它最贵的部分 |
| 抄 Spotify 的部落制就行 | Spotify 自己后来也说“那不是模板”；部落制依赖成熟的平台与工程文化 |

## 四种形态：优化什么、代价是什么

| 形态 | 结构 | 优化 | 代价 | 适合 |
|---|---|---|---|---|
| **职能型** | 按专业分组（后端/前端/测试/运维） | 专业深度、资源利用率 | 交付要跨部门协调，责任分散 | 稳定产品、专业稀缺 |
| **项目型** | 按项目组队，项目结束解散 | 交付速度、目标单一 | 专业退化、人员归属感弱 | 项目制交付、外包 |
| **矩阵** | 职能线 + 项目线双线 | 资源可复用 + 项目可控 | **双线汇报、决策慢** | 多项目共享稀缺资源 |
| **部落（Team Topologies 式）** | 长期团队端到端拥有业务流 | 交付快、责任清晰 | 需要平台与工程能力托底 | 持续演进的互联网产品 |

## 交接次数：把“哪种形态更贵”算出来

同一条跨职能需求，在四种形态下要交接几次？假设要走产品 / 后端 / 测试 / 运维四个职能：

```go
// 假设：需求要走 4 个职能；矩阵制每条线还要双线确认。
forms := []struct{ name string; handoffs int; note string }{
	{"职能型", funcs, "每个职能交接一次"},
	{"项目型", 1, "项目内闭环，转专业时找职能"},
	{"矩阵", funcs * 2, "4 个职能 × 双线确认"},
	{"部落", 1, "团队内闭环；跨团队只经接口人 1 次"},
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
职能型    交接=4 次（每个职能交接一次）
项目型    交接=1 次（项目内闭环，转专业时找职能）
矩阵     交接=8 次（4 个职能 × 双线确认）
部落     交接=1 次（团队内闭环；跨团队只经接口人 1 次）
```

| 形态 | 交接次数 | 买到什么 | 付出什么 |
|---|---|---|---|
| 职能型 | 4 | 专业深度、资源利用率 | 每次交付都跨 4 个部门 |
| 项目型 | 1 | 交付速度 | 专业不沉淀，项目结束人散 |
| 矩阵 | **8** | 资源复用 + 项目可控 | 每条边双线确认，决策慢 |
| 部落 | 1 | 端到端速度 + 责任清晰 | 需要平台与工程能力托底 |

数字说明一件事：**矩阵的成本不在“人多”，在“每条边都要过两次”**。

## 判据：三问选形态

| 问题 | 若是 | 选 |
|---|---|---|
| 业务与需求是否高度不确定、需要持续演进？ | 是 | 部落制（先补平台能力） |
| 是否多个项目共享少量稀缺专家？ | 是 | 矩阵（并给专家设明确的时间分配） |
| 交付是否以一次性项目为主、结束后解散？ | 是 | 项目型 |
| 是否专业深度优先、交付节奏稳定？ | 是 | 职能型 |

> 🔑 一个常见的错误顺序：**先改组织形态，再补工程能力**。部落制没有平台与自动化托底，会退化成“每个小团队都是一家小公司”。

## 部落制：Spotify 模型与它的边界

| 单元 | 规模 | 作用 |
|---|---|---|
| **Squad**（小队） | 6–12 人 | 端到端负责一条流，类似流对齐团队 |
| **Tribe**（部落） | < 100 人 | 若干小队，共享业务域 |
| **Chapter**（分会） | 跨小队同职能 | 专业标准与人员发展 |
| **Guild**（协会） | 跨部落自愿 | 知识分享，无管理权 |

它的价值在于把“职能深度”与“端到端交付”同时装下；代价是需要 chapter/guild 这种**软机制**真的运转，否则专业能力会随小队自治而退化。Spotify 后来公开表示“这不是一个可复制的模板”，原因也在这里：**它是一套配套实践的结果，不是一张组织图**。

## 反模式

| 反模式 | 后果 |
|---|---|
| 组织形态一年一改 | 每次重组都有 3–6 个月磨合期，团队一直在磨合 |
| 矩阵制不给“双线”定优先级 | 员工被两个老板同时安排，冲突升级到高层 |
| 抄组织图不抄配套实践 | 名字叫 squad，实际还是职能汇报 |
| 项目型团队长期化 | 项目结束人无处可去，专业能力断层 |
| 部落制没有平台团队 | 每个小队自建基础设施，重复浪费 |
| 用组织调整代替技术决策 | 架构问题被当成“人的问题”，换人后照旧 |

## 自检

**Q1** 矩阵制最贵的成本是什么？怎么缓解？

▸ 答案：**双线汇报**带来的决策成本——同一件事，职能线看专业标准、项目线看交付进度，冲突时没人能拍板。缓解方式不是取消矩阵，而是给每条边定规则：谁对“做什么”拍板、谁对“怎么做”拍板、冲突升级到谁，且写进 ADR 或组织手册。

**Q2** 什么情况下职能型反而优于部落制？

▸ 答案：专业稀缺、交付节奏稳定、需求变化慢的场景。比如编译器、数据库内核、芯片验证：深度比速度重要，跨专业协调少。职能型能把专家聚在一起互相 review；拆成小队反而让每个小队只有一个半懂的人。

**Q3** 为什么“先改组织、再补工程能力”通常失败？

▸ 答案：因为部落制的效率来自**平台与自动化把外源负荷接走**（[74.4 认知负荷与团队规模](../74-康威定律与团队拓扑/74.4-认知负荷与团队规模.md)）。没有平台托底，小队要自己部署、自己监控、自己值班，端到端就变成了“什么都自己干”，效率反而低于职能型。

**Q4** Spotify 模型为什么“不可复制”？

▸ 答案：因为它是一组配套实践的结果：成熟平台、强工程文化、自治传统、chapter/guild 的软机制。只抄组织图（squad/tribe）而不抄配套，得到的是“被切成小块的职能组织”——汇报线还在，自治没有，跨队协调反而更多。

**Q5** 一个 30 人团队，6 个项目共享 3 个数据库专家，该选什么形态？

▸ 答案：矩阵（或“部落 + 专家作为 X-as-a-Service”）。关键不是形态名字，而是给专家定**明确的时间分配与接入方式**：比如每人 60% 时间在项目、40% 做平台化工具，项目通过工单/自助接入。否则专家会被 6 个项目同时拉扯，变成瓶颈。
