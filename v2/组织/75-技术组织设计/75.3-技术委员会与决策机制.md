# 75.3 技术委员会与决策机制

## 一句话

> 委员会的价值不是“审批”，而是**把决策的规则与记录固定下来**——谁拍板、依据什么、记录在哪、什么条件下重开；没有规则的委员会，会退化成“最资深的那个人一个人拍”。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 委员会 = 审批会 | 审批只是它最不重要的一项；定标准、仲裁冲突、留记录才是 |
| 人越多越权威 | 人多只增加路径数；**决策需要的是明确的责任人，不是更多听众** |
| 会议纪要就是记录 | 纪要记“说了什么”，决策记录要记“为什么选它、代价是什么、何时重开” |

## 委员会的三种职能

| 职能 | 处理什么 | 产出 | 频率 |
|---|---|---|---|
| **定标准** | 技术栈、接口规范、数据模型、命名与错误码 | 标准文档 + 例外流程 | 季度 |
| **评审不可逆决策** | 拆服务、换存储、自研基础设施 | ADR + 评审结论 | 按需 |
| **仲裁跨团队冲突** | 边界争议、优先级冲突、契约变更争议 | 裁决 + 责任归属 | 按需 |

> 🔑 三条里最容易被忽略的是“**例外流程**”：标准如果没有例外通道，团队会绕过标准；有了例外通道但没人记录，标准就没有约束力。

## 决策规则：先定规则，再开会

| 决策类型 | 谁拍板 | 必须谁在场 | 记录 | 什么条件下重开 |
|---|---|---|---|---|
| 可逆、成本低 | 负责人 | 无 | 一句话知会 | 出问题随时回退 |
| 跨团队接口变更 | 契约 owner | 消费方代表 | 契约变更记录 + 版本号 | 兼容性出问题 |
| 不可逆、成本高 | 委员会 | 受影响团队代表 | **ADR** | 前提变化 / 三个月复盘 |
| 标准与规范 | 委员会 | 标准 owner | 标准文档 | 年度复审 |

规则必须在**开会之前**定好，否则每次都要先吵“这次谁说了算”。

## 共识不是“通知”：许式伟的五层

许式伟把团队共识拆成五层，委员会要盯的正是前四层：

| 层 | 内容 | 委员会的作用 |
|---|---|---|
| 1 | 有没有**共同目标** | 目标不共识，委员会只能做裁判 |
| 2 | 有没有共同的**行事准则（价值观）** | 准则不一致，“道不同不相为谋” |
| 3 | 对产品与市场的**要与不要**是否一致 | 决定技术投入的方向 |
| 4 | 对**执行路径**有没有共同认知 | 决定排期与边界 |
| 5 | 团队默契 | 靠日常协作积累，不靠会议 |

他还有两条判断，直接可用于委员会：

- **“共识大于能力”**：能力强但价值观不一致的人，能力越大破坏性越大；
- **“越聪明的负责人越容易忽视达成共识的难度”**：开会讲半小时，兄弟迷茫地回去——这是小团队；规模一大就失效。更好的方式不是“传达决策”，而是**让影响落地的关键角色参与决策形成的过程（共创）**，并同步足够充分的信息。

## 记录：用 ADR，不用纪要

```yaml
# docs/adr/0021-order-sharding.md
id: 0021
title: 订单库按用户 ID 分片
status: accepted        # proposed / accepted / superseded
context: 单库写入 QPS 已达 8k，预计半年翻倍
options:
  - 分库分表（sharding-jdbc）
  - 换分布式数据库（TiDB）
decision: 分库分表
consequences: 跨片查询要走聚合层；运维复杂度上升
reopen_if: 单表写入回落到 3k 以下，或跨片查询占比超过 20%
deciders: [架构组, 订单团队, DBA]
date: 2026-10-30
```

`reopen_if` 是最容易被漏掉的一行：没有它，决策会变成“永远正确”，也没人敢重开。ADR 的完整实践见 [58.1 ADR 实践](../../L5-工程效能/58-架构治理/58.1-ADR实践.md)。

## 一张“精确的共识”长什么样

许式伟的原话很重：**架构图不是好的共识表达**，因为它不精确；更精确的是**定义模块接口，用代码表达**——“规格高于实现”。

| 表达方式 | 精确度 | 适合作什么 |
|---|---|---|
| 口头/会议 | 低 | 同步信息 |
| 架构图 | 中 | 说明模块关系 |
| 接口 / IDL / 代码 | **高** | 契约、验收、联调依据 |
| ADR | 高（决策维度） | 记录为什么、代价、重开条件 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 委员会变成审批瓶颈 | 所有变更排队，团队绕开委员会自己干 |
| 没有决策规则 | 每次开会先吵“谁说了算” |
| 只记录结论、不记录备选与代价 | 三个月后原样重开争论 |
| 委员会成员全是管理者 | 决策脱离现场，落地时被抵触 |
| 用“通知”代替“共创” | 会上没人反对，会后消极执行 |
| 没有例外通道 | 标准被绕过，且没人知道绕了多少 |
| 决策没有重开条件 | 过时的决策永远有效，成为技术债来源 |

## 自检

**Q1** 委员会最重要的产出是什么？为什么不是“审批意见”？

▸ 答案：是**可追溯的决策规则与记录**（谁拍板、依据、代价、重开条件）。审批意见只影响一次；规则与记录会让后续同类决策更快、更一致，也避免“三个月后原样重开争论”。审批是副产品，不是目的。

**Q2** 为什么“让关键角色参与决策形成”比“开会通知”更有效？

▸ 答案：因为通知只传递结论，不传递**约束与取舍**；参与者没经历权衡，执行时遇到偏差就会各自解读。共创让关键角色带着自己的约束进入讨论，结论里包含他们的让步，执行时才会真正投入。许式伟的说法是“同步足够充分的信息，让结论自然产生”。

**Q3** 为什么架构图不能作为契约？

▸ 答案：因为图不精确：字段类型、错误码、超时、幂等语义都画不出来，而这些恰恰是联调时对不上的地方。契约要用代码/IDL 表达，能被编译与测试验证；图只用来辅助说明关系。这就是“规格高于实现”。

**Q4** ADR 里的 `reopen_if` 有什么用？

▸ 答案：它给决策设了**失效条件**：当前提变化（写入量回落、跨片查询占比上升）时，团队有依据重开讨论，而不是把三年前的决策当永恒真理。没有这一行，决策会变成“谁都不敢动”的技术债。

**Q5** 委员会该不该有例外通道？

▸ 答案：该有，而且必须留痕。没有例外通道，团队会绕过标准，而且没人知道绕了多少；有通道但无记录，标准就失去约束力。正确做法是：例外要申请、要有期限、要进台账，季度复审。
