# 78.3 技术分享与成长机制

## 一句话

> 成长不是“多看书”，而是**输入有源头、输出有节奏、反馈有对象**——组织能做的只有三件事：给源头（一手资料与牛人）、给节奏（每周一次的固定动作）、给反馈（公开输出并接受批评）。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 学习 = 看书 / 看视频 | 被动输入留存极低；**输出**（讨论、实践、教别人）才把知识变成能力 |
| 分享 = 做一个 PPT 讲一遍 | 分享的价值在于**讲的人被逼着把知识结构化**，听众只是副产品 |
| 成长 = 熬时间 | 时间只保证“经历”，不保证“经验”；有节奏的刻意练习才复利 |

## 一、为什么必须“输出式学习”

学习金字塔（埃德加·戴尔，1946 年提出，常被引用；实验证据有争议，但方向被反复验证）：

| 方式 | 平均留存率 |
|---|---|
| 听讲 | 5% |
| 阅读 | 10% |
| 视听 | 20% |
| 演示 | 30% |
| **讨论** | **50%** |
| **实践** | **75%** |
| **教别人** | **90%** |

> 🔑 听讲与教别人的留存差 **18 倍**。所以“每周做一次分享”不是福利，是**最便宜的能力训练**：讲的人要能回答所有追问，才敢上台。

## 二、输入：只从源头拿

许式伟/陈皓都强调同一件事：**去源头看第一手资料**。二手的“代读、领读、听书”会给你“勤奋好学”的幻觉，却拿不到作者为什么这么想的上下文。

| 输入 | 例子 | 什么时候用 |
|---|---|---|
| **一手** | 官方文档、源码、规范、论文 | 要准确、要边界、要做决策时 |
| 二手 | 解读文章、视频课、别人的总结 | 建立初始印象、快速判断值不值得深入 |

三个可执行的输入动作：

1. **画知识地图，再顺藤摸瓜。** 学一门新语言，先问“它解决了什么、分几块”。陈皓 2010 年学 Go 时只看六件事：错误处理、内存管理、封装扩展、多态泛型、反射、并发。**六件事看完，语言地图就有了**，剩下的查文档即可。
2. **先补原理，再读实现。** “勿在浮沙筑高台”：懂 Socket 与多路复用模型，Node、Java NIO、Nginx 的底层就是同一件事；不懂 TCP 原理去读内核网络代码，只会得到误解。
3. **带问题学。** 没有问题就没有反馈，没有反馈就没有成就感，最后靠毅力硬撑——撑不过三周。

一个可参考的节奏量：**每周搞懂 1 个知识点，一年 50 个**。陈皓的原话口径是：坚持 2–3 年，可以超过国内至少 99 万程序员（这是他的经验判断，不是统计结论）。

## 三、节奏：每周一个 ARTS

ARTS 是一个四件套的周更动作，来源是陈皓的练级攻略：

| 字母 | 含义 | 产出 | 时间盒 |
|---|---|---|---|
| **A** Algorithm | 做一道算法题 | 思路 + 复杂度 + 代码 | 1 小时 |
| **R** Review | 读一段别人/开源的代码 | 一段点评（好在哪、坑在哪） | 1 小时 |
| **T** Tip | 学一个技巧 | 一条可直接用的技巧 | 30 分钟 |
| **S** Share | 写一篇分享 | 一篇短文 / 一次 15 分钟分享 | 1–2 小时 |

一年 52 周，52 次 R + 52 次 T 的复利，远大于“一年读 10 本书”。

团队层面加一个可跑的小工具：每周打卡，月底看完成率与连续周数（而不是看谁“学得多”）。

```go
// 统计 ARTS 打卡：每周 A/R/T/S 四项，输出完成率与「最长连续满勤」周数。
package main

import (
	"bufio"
	"fmt"
	"os"
	"strings"
)

func main() {
	f, _ := os.Open("arts.txt")
	defer f.Close()
	sc := bufio.NewScanner(f)
	var weeks, full, cur, best int
	for sc.Scan() {
		fields := strings.Fields(strings.TrimSpace(sc.Text()))
		if len(fields) < 5 {
			continue
		}
		weeks++
		done := 0
		for _, x := range fields[1:5] {
			if x != "-" {
				done++
			}
		}
		if done == 4 {
			full++
			cur++
			if cur > best {
				best = cur
			}
		} else {
			cur = 0
		}
	}
	fmt.Printf("周数=%d 满勤=%d 完成率=%.0f%% 最长连续满勤=%d 周\n",
		weeks, full, 100*float64(full)/float64(weeks), best)
}
```

输入与真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
2026-W01 A R T S
2026-W02 A R T S
2026-W03 A R T -
2026-W04 A R T S
2026-W05 A - - -
2026-W06 A R T S

周数=6 满勤=4 完成率=67% 最长连续满勤=2 周
```

**看“最长连续满勤”，不看总完成率**：断一次就归零的指标，才会真的形成节奏。

## 四、输出：三种形式，成本递增

| 形式 | 成本 | 谁受益最大 | 怎么做才有用 |
|---|---|---|---|
| 笔记 | 低 | 自己 | 用自己的话重写，附“我不同意的地方” |
| 分享会 | 中 | **讲的人** | 15 分钟 + 3 个预设问题 + 1 页 takeaway |
| 教别人 / 带新人 | 高 | 双方 | 让新人动手做，你只答疑；把问题写进文档 |

分享会有三条硬规则：

1. **讲的人必须是做事的人**，不能是“转述文章的人”。
2. **必须留 10 分钟被追问**；答不上来的问题就是下一周的 ARTS 题目。
3. **必须有产出**：一页 takeaway 或一段代码，落到仓库里；否则等于没发生。

## 五、反馈：没有批评的输出等于没输出

输出的价值取决于**有没有人真的看、真的挑错**：

| 反馈机制 | 频率 | 关键 |
|---|---|---|
| Code review | 每次合并 | 评审者要指出“为什么”，不只是“改一下” |
| 分享后的追问 | 每次分享 | 追问比鼓掌有价值 |
| 导师制 | 每周 1 次 30 分钟 | 导师只做两件事：指方向、挑毛病 |
| 公开复盘 | 每次事故 | 对事不对人（[78.1 工程文化](78.1-工程文化.md)） |

一个反直觉的结论：**新人成长最快的时刻，不是被夸奖时，是被具体指出“这里可以更好”时**。所以“好老板要善于提问”——提问逼对方自己想，比直接给答案有效。

## 六、面对枯燥与量大的知识

枯燥通常只有两个原因：**不感兴趣**，或**不知道学了有什么用**。两者都不是“毅力问题”，而是“入口问题”——换个入口，枯燥感会大幅下降。

| 方法 | 做法 | 适用 |
|---|---|---|
| 先找应用场景 | 先看它在真实系统里解决什么问题，再回来看理论 | 底层原理、协议、算法 |
| 带问题学 | 带着一个具体问题去读，读到能回答就停 | 大部头、规范 |
| 找牛人讲 | 听做过的人讲一遍，比读三遍快 | 陌生领域 |
| 换一本图解书 | 抽象的书读不下去，换图文并茂的（如《图解 TCP/IP》） | 入门阶段 |

面对“量大”，原则只有一条：**目的不是学完，而是学到本质**。原理性的东西不易变、经得起时间考验；工具与 API 会过期，用到再查。

陈皓给了八个具体技巧，按“输入—加工—输出”归一下类：

| 阶段 | 技巧 | 一句话 |
|---|---|---|
| 输入 | 多种方式学同一东西 | 书 + 视频 + 源码，互相印证 |
| 输入 | 不被打断 | 勿扰模式、关通知，一次只学一件 |
| 加工 | 总结压缩信息 | 表格 / 图示 / 笔记 / 脑图，把书读薄 |
| 加工 | 把未知关联到已知 | 用已学的语言类比新语言 |
| 加工 | 不要死记 | 找可推导的方法，记“为什么”而不是“是什么” |
| 输出 | 用教的方式学 | 讲给别人听，讲不通就是没懂 |
| 输出 | 学以致用 | 在真实项目里用一次，胜过读十遍 |
| 反馈 | 多犯错误 | 不犯低级错误、不重复犯同一个错 |

> 🔑 陈皓的原话：**人不怕笨，怕的是懒，怕的是找到各种理由放弃。**

## 反模式

| 反模式 | 后果 |
|---|---|
| 用“读完几本书”衡量成长 | 只统计输入，不统计输出，能力不变 |
| 分享会变成转述文章 | 讲的人没有结构化，听众也拿不到一手信息 |
| ARTS 只做 A（刷题） | 缺 R/T/S，成长退化成“面试准备” |
| 打卡按总次数排名 | 团队为刷次数注水，指标失真 |
| 只批评不示范 | 被批评者不知道“更好”长什么样 |
| 把成长完全外包给培训 | 培训只给地图，走路还得自己走 |

## 自检

**Q1** 为什么“教别人”的留存率能到 90%，而“听讲”只有 5%？

▸ 答案：因为教别人**强制你做三件事**：把知识压缩成结构（否则讲不清）、预判追问（否则会被问倒）、用对方能懂的语言重述（否则对方听不懂）。这三件事都在做“深度加工”，而听讲只做“接收”。注意：学习金字塔的具体数字证据有争议，但“输出强于输入”这个方向被大量实践验证。

**Q2** 学一门新语言，为什么要先画“知识地图”，而不是从语法第一页看起？

▸ 答案：因为语法是细节，地图是结构。有了地图（错误处理、内存管理、封装扩展、多态泛型、反射、并发这六块），新知识才有地方挂，遇到问题也知道去哪查；没有地图，学到的是一堆孤立知识点，遇到真实问题仍然不会用。**学习不是记知识点，是拿到一张能找答案的地图。**

**Q3** ARTS 里的 R（Review）和 S（Share）为什么不能省？

▸ 答案：A 训练的是解题，T 训练的是技巧，两者都在“输入/练习”一侧；R 逼你读别人的代码（获得他人经验），S 逼你输出（把经验结构化）。四个动作合起来才覆盖“输入—练习—借鉴—输出”的完整循环，只做 A 会退化成刷题。

**Q4** 为什么看“最长连续满勤周数”，而不是“总完成率”？

▸ 答案：总完成率可以被“集中补打卡”拉高，而连续满勤要求**每周都真的做了**，它测的是节奏而不是总量。成长的复利来自节奏：52 周每周 1 小时，远大于某两个月每周 10 小时、其余时间归零。

**Q5** 分享会“必须有产出”这条规则，是为了什么？

▸ 答案：为了把一次性的口头输出变成**组织的知识资产**。没有产出的分享，讲完即蒸发；有一页 takeaway 或一段代码，它就能被检索、被引用、被下一个人接着改——这也让分享从“表演”变成“贡献”。

**Q6** 面对“枯燥”和“量大”，各自的第一动作是什么？

▸ 答案：枯燥的第一动作是**换入口**——先找它的应用场景，或带一个具体问题去读，而不是硬啃；量大的第一动作是**改目标**——从“学完”改成“学到本质与原理”，工具类知识用到再查。两者的共同点是：不要用毅力对抗方法问题。
