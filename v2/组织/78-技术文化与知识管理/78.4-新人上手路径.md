# 78.4 新人上手路径

## 一句话

> 上手的目标不是“尽快干活”，而是**在 3–10 天内独立交付第一个可上线的改动**——路径分三段（看得懂 → 跑得起来 → 改得动），每段都有可验收的退出标准；量它的数是**上手阻塞时长**，不是“学得快不快”。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 上手 = 把文档读一遍 | 读是输入，改成输出；没跑起来、没改过一行代码，等于没上手 |
| 上手 = 跟着导师做一个需求 | 跟着做学到的是“这一步怎么做”，学不到“为什么这样分” |
| 上手越快越好 | 快而没跑通全链路（含发布、回滚），第一次独立上线就会出事 |

## 三段路径，每段有退出标准

### 第 1 段：看得懂（Day 1–3）

| 要拿到的东西 | 怎么拿 | 退出标准 |
|---|---|---|
| 系统边界 | 画一张上下文图（有哪些服务、谁调谁） | 能不看文档讲清 5 个服务的职责 |
| 责任地图 | 服务目录：每个服务归谁、值班是谁 | 能说出“这个服务出事找谁” |
| 决策背景 | 读 3 篇 ADR（[58.1 ADR 实践](../../L5-工程效能/58-架构治理/58.1-ADR实践.md)） | 能说出“为什么不选另一个方案” |
| 术语 | 读术语表、听 1 次团队周会 | 会上能听懂 80% |

**先读哪些文件**：不要按目录顺序读，按**变更频率**读——近 6 个月改得最多的文件，就是系统的“活心脏”。一条命令就能排出来：

```bash
git -c core.quotepath=false log --since="6 months ago" --name-only --pretty=format: -- internal/ \
  | sed '/^$/d' | sort | uniq -c | sort -rn | head -10
```

真实输出（拿一个仓库跑，结果会长这样）：

```text
  14 internal/order/service.go
   9 internal/payment/callback.go
   8 internal/common/config.go
   7 internal/order/repo.go
   7 internal/gateway/router.go
```

前三名就是新人第一周该读的核心路径；`common/config` 这类“谁都在改”的文件，往往是最该警惕的耦合点。

### 第 2 段：跑得起来（Day 1–5）

| 要拿到的东西 | 怎么拿 | 退出标准 |
|---|---|---|
| 本地环境 | 一条命令起服务（`make dev` 或 `docker compose up`） | 从零到服务可访问 ≤ 30 分钟 |
| 可观测 | 能看日志、能看指标、能追一次请求 | 用 Request ID 找到一次调用的完整日志 |
| 能发布 | 在 dev 环境完成一次“空变更”发布 | 发布成功且能自己回滚 |
| 能调试 | 断点或日志定位一次真实报错 | 独立定位并修掉一个 dev 环境的问题 |

⚠️ 最常见的上手事故，是**新人从来没走过发布与回滚**，第一次上线就是第一次发布。空变更发布（改一行注释、发一次、再回滚）是最便宜的演练。

### 第 3 段：改得动（Day 3–10）

第一个 PR 的选择有讲究：

| 选什么 | 为什么 | 反例 |
|---|---|---|
| 小 bug 修复（含测试） | 走完全链路：改代码 → review → CI → 发布 → 观察 | 一上来改核心逻辑 |
| 补一段缺失的日志/指标 | 逼他理解运行路径 | 只改文档（不碰代码） |
| 给现有功能加一个小参数 | 涉及接口、配置、测试三处 | 独立开发一个新服务 |

**退出标准**：PR 合并 + 上线 + 观察一个发布周期。到这一步，才算“上手完成”。

## 度量：上手阻塞时长

| 指标 | 怎么算 | 经验阈值（我的判断） |
|---|---|---|
| 上手阻塞时长 | 入职到第一个 PR 合并的**净被卡时长** | ≤ 3 天 |
| 第一个 PR 的返工轮次 | review 要求修改的次数 | ≤ 2 轮 |
| 环境搭建耗时 | 从零到服务可访问 | ≤ 30 分钟 |
| 30 天独立接需求 | 是否需要人盯着 | 是 / 否 |

这些数与 bus factor、文档腐烂率是同一套（[40.3 文档与知识传递](../../L3-质量属性/40-可维护性/40.3-文档与知识传递.md)）：**阻塞时长长，通常不是新人笨，是环境或文档有洞**。

## 读代码：用六步法、别从第一行读

新人最常犯的错是打开 IDE 从 `main.go` 开始顺序读。更快的顺序（详见 [40.3 文档与知识传递](../../L3-质量属性/40-可维护性/40.3-文档与知识传递.md)）：

1. `go doc` 导出公开实体规格 → 2. 读 example 与 unit test（使用方视角）→ 3. 推测职责与关系 → 4. 挑核心读源码印证 → 5. 找做过的人聊 1 小时 → 6. **把结论写进文档**。

最后一环最重要：**新人写的第一份文档，往往是这个系统最好的一份文档**——他还没有被“我们一直这样”驯化。

## 导师制：三件事，别多

| 事 | 频率 | 具体 |
|---|---|---|
| 给方向 | 第 1 周每天 15 分钟 | 今天该看什么、为什么看这个 |
| 挑毛病 | 每个 PR | 只挑 1–2 个最重要的，其余记下来下周讲 |
| 挡需求 | 前 2 周 | 不让业务方直接给新人派活 |

导师最常见的错误是**直接给答案**。更好的做法是提问：“你觉得这个请求会经过哪几个服务？”——让他自己走一遍，走错了再纠正。

## 反模式

| 反模式 | 后果 |
|---|---|
| 上手第一天就派需求 | 新人靠猜写代码，返工率极高 |
| 只读文档不跑环境 | 文档与实现脱节时，新人学到的是错的 |
| 第一个 PR 就改核心 | 影响面大、review 成本高，双方都受挫 |
| 从没走过发布/回滚 | 第一次独立上线就是第一次发布，风险最高 |
| 导师随时被打断 | 导师变客服，新人学不会自己找答案 |
| 上手期不记录问题 | 同样的阻塞每个新人重踩一遍 |
| 用“学得快不快”评价新人 | 掩盖了环境与文档的真实问题 |

## 自检

**Q1** 为什么上手路径要以“第一个可上线的改动”为终点，而不是“读完文档”？

▸ 答案：因为“读懂”无法验收，而“上线一个改动”能验收：它强制走完改代码、review、CI、发布、观察、回滚的完整链路，任何一环有洞都会暴露。文档读完只证明输入发生过，不证明能独立工作。

**Q2** 新人第一周该按什么顺序读代码？为什么不是按目录顺序？

▸ 答案：按**变更频率**（`git log --name-only` 统计）而不是目录顺序。改得最多的文件是系统当前真正活跃的核心路径，也是新人最可能马上要碰的地方；目录顺序反映的是历史结构，可能包含大量已死代码。

**Q3** 为什么第一个 PR 建议选“小 bug + 测试”，而不是“补文档”？

▸ 答案：补文档不碰代码，新人拿不到“改代码 → review → CI → 发布”的全链路经验，也不知道自己的理解对不对。小 bug 修复成本低、影响面可控，却能走完整条流水线，还能用测试证明自己真的理解了行为。

**Q4** “空变更发布”这种演练有必要吗？

▸ 答案：有。发布与回滚是上手路径里**唯一无法靠读代码获得**的能力，而它恰恰是风险最高的动作。用一行注释做一次“发布 + 回滚”，成本 10 分钟，却能让新人在真正紧急时知道按钮在哪、失败长什么样。

**Q5** 上手阻塞时长超标，应该先怀疑新人还是先怀疑系统？

▸ 答案：先怀疑系统。阻塞时长主要来自环境搭不起来、文档过期、没人可问、权限没开——这些都不是能力问题。正确顺序是：先修环境与文档（一次性投入，所有后来者受益），再谈个人方法。
