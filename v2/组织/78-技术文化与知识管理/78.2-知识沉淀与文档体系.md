# 78.2 知识沉淀与文档体系

## 一句话

> 知识沉淀不是“多写文档”，而是让**该留下的知识有唯一真相源、能被检索、有人负责**——组织级只做三件事：画知识地图（有什么）、定分层文档体系（放哪）、建沉淀机制（谁在什么时候写）。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 文档越多越好 | 没有 owner 的文档是**负资产**：读的人先学错的，再花时间纠正 |
| 沉淀 = 写 wiki | wiki 只是载体之一；**离代码越近的载体越不容易腐烂** |
| 知识留在脑子里最安全 | 那是**单点**，不是安全；人一走知识归零（bus factor = 1） |

## 一、知识地图：先分清四类知识

不同知识的载体、腐烂速度、owner 完全不同，混在一起写就是灾难：

| 类型 | 例子 | 真相源 | 腐烂速度 | owner |
|---|---|---|---|---|
| **事实** | 接口签名、表结构、配置项 | **代码 / schema** | 快（跟着代码变） | 模块 owner |
| **流程** | 怎么发布、怎么回滚、怎么扩容 | runbook | 中（跟着环境变） | 值班 owner |
| **决策** | 为什么选 Kafka、为什么不用分库 | ADR | 慢（只增不改） | 决策人 |
| **经验** | 踩过的坑、事故教训 | 复盘 / 案例库 | 慢 | 事故 owner |

> 🔑 判据只有一条：**一条信息只能有一个真相源。** 同一个事实出现在 wiki、README、注释、Confluence 各一份，等于四份都会过期，而且没有人负责删。

事实类的真相源必须是代码：接口文档从代码生成（`go doc`、OpenAPI），表结构从 DDL 生成。手写的接口文档三个月后一定与实现脱节（[28.3 服务契约设计](../../L2-架构风格/28-面向服务与集成/28.3-服务契约设计.md)）。

## 二、分层文档体系：按“离代码的距离”放

| 层 | 放什么 | 载体 | 谁写 | 更新时机 |
|---|---|---|---|---|
| **L1 代码内** | 为什么这么写、边界条件 | 注释、包文档 | 作者 | 改代码时 |
| **L2 仓库内** | 架构说明、ADR、runbook、测试说明 | `docs/`、`adr/` | 模块 owner | 决策时 / 事故后 |
| **L3 团队空间** | 规范、流程、新人路径 | wiki | 团队 lead | 季度 |
| **L4 个人笔记** | 学习笔记、临时记录 | 个人空间 | 个人 | 随时（**不进真相源**） |

判据：**能放进 L1/L2 的，不要放 L3。** 仓库内的文档跟代码一起 review、一起版本化、一起回滚；wiki 上的文档没有 review，腐烂速度高一个量级。

## 三、沉淀机制：三个必写时机

不设时机，沉淀就永远排在“下周”。三个时机一旦触发就必须写：

| 时机 | 写什么 | 不写的后果 |
|---|---|---|
| **做决策时** | ADR：背景、备选、代价、状态 | 三个月后原样重开争论 |
| **出事故后** | 复盘 + 行动项（5 个工作日内） | 同类事故再犯一次 |
| **新人问第三遍** | 把这个问题的答案写进文档 | 每个人都被问一遍，知识永远不留存 |

第三条是成本最低的沉淀信号：**同一个问题被问第三遍，说明它已经是组织级知识缺口**，而不是新人笨。

## 四、度量：文档腐烂率与引用可用性

“文档写得好不好”不可测，但**腐烂程度**可测。两个能跑的检查：

**① 引用校验（本书自己在用）。** 全书的跨篇引用用脚本校验，跑一次就知道有多少死链：

```bash
python3 ~/.dsh/skills/luban-writing/scripts/check-refs.py v2 --quiet
```

真实输出（写作时的一次运行）：

```text
扫描 574 个文件 · 385 个有跨篇引用 · 共 1782 处引用 · 目录收录 577 节 · 已有正文 502 节

✓ 无硬错误
```

**文档腐烂率 = 死链数 / 引用总数**。本书目前是 0 / 1782；一旦某节改名而引用没改，这个数立刻上升——它比“感觉文档旧了”可靠得多。

**② 作者集中度（bus factor）。** 对每个模块统计近 6 个月的提交作者数：

```bash
git log --since="6 months ago" --format='%an' -- internal/order | sort -u | wc -l
```

输出是 1，就意味着这个模块的文档只有一个人能写对——他休假，文档就停更。

| 指标 | 怎么算 | 经验阈值（我的判断） |
|---|---|---|
| 文档腐烂率 | 死链 / 引用总数 | < 2% |
| 模块 bus factor | 近 6 个月作者数 | ≥ 2 |
| 新人上手阻塞时长 | 从入职到第一个合并 PR 被卡的总时长 | ≤ 3 天 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 手写接口文档当真相源 | 三个月后与实现脱节，调用方按错的写 |
| wiki 里 300 页无 owner 的文档 | 新人先学错再纠正，成本高于从零教 |
| 把个人笔记放进团队知识库 | 半成品被当成结论引用 |
| 文档按团队组织而非按系统组织 | 跨团队找一个接口要翻三个空间，最后去问人 |
| 只让一个人写核心模块文档 | 文档与他脑子里的版本逐渐分叉，且他仍是单点 |
| 沉淀没有触发时机 | “等有空再写”= 永远不写 |
| 用文档字数考核沉淀 | 产出注水文档，检索质量反而下降 |

## 自检

**Q1** 为什么“接口文档”的真相源必须是代码，而“为什么选 Kafka”的真相源必须是 ADR？

▸ 答案：因为两者的**变化频率**和**变更触发点**不同。接口签名随代码每次提交而变，任何手写副本都必然滞后，只有从代码生成才能保证一致；而“为什么选 Kafka”是一次性决策，代码里不会记录备选方案与代价，只有 ADR 能承载，且它**只增不改**（要推翻就写新 ADR）。

**Q2** “新人问第三遍”为什么是文档缺口的信号，而不是新人能力问题？

▸ 答案：第一遍问是正常学习，第二遍问可能是记不住，**第三遍问说明这个答案根本不在任何可检索的地方**——否则他会自己查到。此时正确动作是把答案写进文档（并告诉他在哪），而不是再讲一遍。这个信号的好处是：它由新人免费提供，不需要额外的度量系统。

**Q3** 文档腐烂率怎么算？为什么它比“文档数量”更有意义？

▸ 答案：腐烂率 = 死链数 / 引用总数（或“与代码不符的文档数 / 文档总数”）。数量只反映投入，腐烂率反映**可用性**：1000 篇文档里 800 篇过期，比 50 篇准确文档更糟。本书用引用校验脚本把它变成每次可跑的数字，而不是季度大扫除时凭感觉判断。

**Q4** 为什么“能放进仓库的文档不要放 wiki”？

▸ 答案：因为仓库内的文档跟代码共享同一套机制：**一起 review、一起版本化、一起回滚、一起被引用检查**。wiki 没有 review 环节，也没有“改代码必须改文档”的强制关联，腐烂速度高一个量级。例外是跨仓库的规范、流程与新人路径——它们不属于任何一个代码库，放 L3 合理。

**Q5** 一个模块的 bus factor 是 1，最便宜的补救是什么？

▸ 答案：不是“让他写更多文档”，而是**制造第二个作者**：把一次小改动交给他之外的人做（结对或 review 驱动），过程中把关键路径写进 L2 文档。文档只是副产品；**第二个人真的改过一次代码**，知识才算转移。
