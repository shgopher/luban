# 77.4 认知负荷与团队规模

## 一句话

> 团队规模的上限不是人数，是**认知负荷**——系统数、技术栈数、服务数摊到每个人头上；超了要**减范围**，而不是加人（加人还会把沟通路径数翻倍）。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 忙不过来就加人 | 加人先增加沟通路径（`n(n-1)/2`），短期更慢；且新人不背历史上下文 |
| 认知负荷是“感觉累” | 它可以算：系统数 × 技术栈数 / 人数，再加服务数，是能排出来的数 |
| 团队负责的东西越多越重要 | 负责得多通常意味着**没有边界**，而不是重要 |

## 三类认知负荷

| 类型 | 含义 | 例子 | 能不能减 |
|---|---|---|---|
| **内在负荷** | 业务本身固有的复杂度 | 支付要处理对账、退款、汇率 | 减不了，只能拆 |
| **外源负荷** | 环境与工具带来的额外负担 | 部署要手工、文档过时、环境不一致 | **能减**：平台化、自动化 |
| **相关负荷** | 学习与迁移的成本 | 同时维护 3 门语言、2 套框架 | 能减：统一技术栈 |

> 🔑 绝大多数团队的“累”，来自**外源负荷**——不是业务太难，是环境和工具在拖后腿。先减外源，再谈拆团队。

## 把负荷算出来

```go
// 团队认知负荷：(系统数 × 技术栈数 + 服务数) / 人数
load := float64(t.systems*t.stacks+t.svc) / float64(t.people)
switch {
case load > 8:
	verdict = "超载：先减范围（还服务/还系统），再谈扩编"
case load > 4:
	verdict = "偏高：列出下周要碰的系统，砍掉不常碰的"
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
订单团队     负荷=  2.5  正常
全能小组     负荷= 15.0  超载：先减范围（还服务/还系统），再谈扩编
平台团队     负荷=  2.2  正常
```

“全能小组”5 个人管 9 个系统、7 套技术栈、12 个服务，负荷 15——它的典型症状不是“忙”，而是**谁都不敢改**：每个系统都只懂一点，改动靠猜。

阈值是经验起点（我的判断），用来触发讨论，不用来做考核。

## 团队规模：沟通路径先于人数

| 人数 | 路径数 `n(n-1)/2` | 组织现象 |
|---|---|---|
| 3 | 3 | 不需要流程 |
| 5 | 10 | 站会足够 |
| 8 | 28 | 需要看板与明确分工 |
| 12 | 66 | 开始出现“他们组在干什么” |
| 16 | 120 | 实际已是两个团队 |

亚马逊的“两个披萨”团队（不超过 16 人）与 Team Topologies 建议的 5–9 人，都在这个数量级：**规模的上限由沟通路径决定**。超过之后，团队需要的是拆分，不是“更努力地同步”。

## 减负荷的四种手段，按成本排序

| 手段 | 做什么 | 成本 | 效果 |
|---|---|---|---|
| **还服务** | 把不属于这条业务流的服务交给它的 owner | 低 | 立竿见影 |
| **统一技术栈** | 三套框架收敛成一套，边缘的允许例外但要有期限 | 中 | 减相关负荷 |
| **平台承接** | 把部署、监控、配置这些外源负荷收到平台 | 中高 | 减外源负荷 |
| **按流拆分** | 一条业务流一个团队 | 高 | 减内在负荷 |

顺序很重要：**先还、再统一、再平台、最后拆**。上来就拆，会把外源负荷一起复制到两个团队里。

## 沟通路径与团队规模

路径总数 n(n−1)/2 及其规模表已经算过（[77.1 康威定律及其逆定律](77.1-康威定律及其逆定律.md)、[77.2 四种团队类型](77.2-四种团队类型.md)），但它不能直接回答“该不该加人、什么时候拆”：总数只说明“贵”，不说明“多贵才算贵”。指导动作的是两笔边际账和一条产能曲线：

- **加第 n 个人，新增 n−1 条路径**：新人要和每个现有成员建立对齐；边际沟通成本随人数线性涨，总成本二次涨。
- **有效产能不随人数线性涨**：每人每周名义 40h、可深度工作 28h，每条路径每周维护 3h（一次 30 分钟同步 + 上下文切换与评审摊薄）；团队有效深度产能 = 人数 × (28 − 3(n−1)/2)。

代入本机算一遍（参数是假设值，输出由 `go run` 生成）：

| 人数 | 路径数 | 人均路径 | 人均协调 h | 剩余深度 h | 团队有效深度 h/周 | 建议结构 |
|---|---|---|---|---|---|---|
| 5 | 10 | 4 | 6.0 | 22.0 | 110.0 | 单团队，喊一声就同步 |
| 9 | 36 | 8 | 12.0 | 16.0 | 144.0 | 单团队上限：站会 + 看板 |
| 10 | 45 | 9 | 13.5 | 14.5 | 145.0 | 产能峰值，再加人净增趋零 |
| 15 | 105 | 14 | 21.0 | 7.0 | 105.0 | 拆 2 个 7–8 人团队 |
| 25 | 300 | 24 | 36.0 | 0（饱和） | 0 | 3 个 8 人团队 + 平台/接口人 |

```go
package main

// 74.4 沟通路径与团队规模：路径总数只是第二列，真正决定"该不该加人/拆分"的是
// 边际沟通成本与团队有效深度产能。模型参数（本机计算，假设值）：
// 名义每周 40h，其中可深度工作 28h；每条沟通路径每周维护 3h。

import "fmt"

const (
	workHours = 40.0 // 名义工时
	deepHours = 28.0 // 每人每周可用于深度工作的时间
	pathHours = 3.0  // 每条路径每周的维护工时（同步、对齐、评审摊薄）
)

func paths(n int) int { return n * (n - 1) / 2 }

// coordPerPerson 总协调工时 pathHours·n(n−1)/2 摊到每人头上
func coordPerPerson(n int) float64 { return pathHours * float64(n-1) / 2 }

// effective 团队每周有效深度产能（被协调压穿时按 0 计）
func effective(n int) float64 {
	left := deepHours - coordPerPerson(n)
	if left < 0 {
		left = 0 // 协调已经吃满全部深度工时，模型饱和
	}
	return float64(n) * left
}

// marginal 加第 n 个人带来的净增有效深度产能
func marginal(n int) float64 { return deepHours - pathHours*float64(n-1) }

func main() {
	fmt.Printf("参数：名义 %.0fh/周，可深度工作 %.0fh/周，每条沟通路径 %.0fh/周\n\n",
		workHours, deepHours, pathHours)
	fmt.Printf("%-6s %-8s %-10s %-12s %-8s %-14s %s\n",
		"人数", "路径数", "人均路径", "人均协调h", "深度h", "团队有效深度h", "建议结构")
	fmt.Println("--------------------------------------------------------------------------------")
	type row struct {
		n    int
		note string
	}
	rows := []row{
		{5, "单团队，喊一声就同步，不需要流程"},
		{9, "单团队上限：站会 + 看板，还能共享上下文"},
		{10, "产能峰值：再加人净增趋零"},
		{15, "拆 2 个 7–8 人团队，跨团队只留接口人"},
		{25, "3 个 8 人团队 + 平台/接口人，25 人已不是一个团队"},
	}
	for _, r := range rows {
		deepLeft := deepHours - coordPerPerson(r.n)
		if deepLeft < 0 {
			deepLeft = 0
		}
		fmt.Printf("%-6d %-8d %-10d %-12.1f %-8.1f %-14.1f %s\n",
			r.n, paths(r.n), r.n-1, coordPerPerson(r.n), deepLeft, effective(r.n), r.note)
	}

	fmt.Println("\n加第 n 个人的边际账：")
	fmt.Printf("%-6s %-10s %-12s %s\n", "n", "新增路径", "新增协调h", "净增有效深度h")
	for _, n := range []int{5, 9, 10, 11, 16} {
		fmt.Printf("%-6d %-10d %-12.0f %+.1f\n", n, n-1, pathHours*float64(n-1), marginal(n))
	}

	// 峰值：扫 2..40 人，找有效深度产能最高的人数
	bestN, bestEff := 0, 0.0
	for n := 2; n <= 40; n++ {
		if e := effective(n); e > bestEff {
			bestN, bestEff = n, e
		}
	}
	fmt.Printf("\n有效产能峰值：%d 人、%.1f h/周；第 %d 人起边际净增为负（%.1f h）\n",
		bestN, bestEff, bestN+1, marginal(bestN+1))
	fmt.Printf("对照：10 人 %.1f h，11 人 %.1f h，15 人 %.1f h，25 人 %.1f h（饱和）\n",
		effective(10), effective(11), effective(15), effective(25))

	// 拆分前后对比：sizes 是拆分后的团队人数；团队间只走接口人，
	// 所以团队间路径数 = k(k−1)/2，而不是把两个团队的人两两连线。
	split := func(sizes []int) (int, float64) {
		p, e := 0, 0.0
		for _, n := range sizes {
			p += paths(n)
			e += effective(n)
		}
		inter := len(sizes) * (len(sizes) - 1) / 2
		p += inter
		e -= pathHours * float64(inter)
		return p, e
	}
	p25, e25 := split([]int{8, 8, 9})
	p15, e15 := split([]int{7, 8})
	fmt.Printf("\n拆分账（团队间只走接口人，团队间路径 = k(k−1)/2）：\n")
	fmt.Printf("25 人单团队：路径 %d，有效深度 %.1f h/周 → 拆 8+8+9：路径 %d（含 3 条团队间），有效深度 %.1f h/周（路径 −%.0f%%）\n",
		paths(25), effective(25), p25, e25, 100*(1-float64(p25)/float64(paths(25))))
	fmt.Printf("15 人单团队：路径 %d，有效深度 %.1f h/周 → 拆 7+8：路径 %d（含 1 条团队间），有效深度 %.1f h/周（路径 −%.0f%%）\n",
		paths(15), effective(15), p15, e15, 100*(1-float64(p15)/float64(paths(15))))

	// 新人 ramp 账：把第 10 个人加进 9 人团队。
	// 前 8 周新人只产出 30%；同时老成员各多 1 条路径，每人少 1.5h 深度工时。
	newbieFactor := 0.30
	rampWeeks, lossPerWeek := 8, 9*1.5-14.5*newbieFactor
	fmt.Printf("\n加第 10 人的回本账：前 %d 周团队每周净少 %.1f h，之后每周净增 %.1f h\n",
		rampWeeks, lossPerWeek, marginal(10))
	fmt.Printf("回本周期 ≈ %.0f 周（%.1f 年），前提是新人 ramp 期产出 %.0f%%\n",
		float64(rampWeeks)*lossPerWeek/marginal(10),
		float64(rampWeeks)*lossPerWeek/marginal(10)/52, newbieFactor*100)

	// 拆分信号：边际净增 < 2h/周 的第一个人数
	for n := 2; n <= 40; n++ {
		if marginal(n) < 2 {
			fmt.Printf("\n拆分信号：加第 %d 人时边际净增只剩 %.1f h/周（< 2h），团队规模已经到顶\n",
				n, marginal(n))
			break
		}
	}
}
```

三个反直觉的结论：

- **第 10 人几乎白加，第 11 人开始拖慢**：第 10 人的边际净增 1h/周，第 11 人 −2h/周；有效产能峰值在 10 人（145h/周），11 人 143h、15 人 105h。Team Topologies 的 5–9 人与两个披萨团队的 16 人上限，分别对应“还能共享上下文的上限”与“必须靠层级和流程的极限”。
- **拆分不是摊薄，是换增长曲线**：25 人单团队路径 300 条、有效深度 0（协调吃满全部深度工时）；拆成 8+8+9、团队间只走接口人后，路径 95 条（−68%），有效深度 415h/周。10 人以内是 n² 的协调被摊薄，过了峰值则是把 n² 的底数从 25 改成 8。
- **加人的回本账比想象长**：把第 10 个人加进 9 人团队，新人前 8 周按 30% 产出计，团队每周净少 9.2h；ramp 期结束后每周只净增 1.0h——回本要约 73 周（1.4 年）。这个数字解释了为什么“先减范围、再拆团队、最后才加人”不是保守，而是算术。

**模型的三条边界，先说清楚再引用**（这是本机计算的假设，不是生产观测）：

| 假设 | 现实偏差 | 对结论的影响 |
|---|---|---|
| 全连接：每两人之间都要一条路径 | 真实团队靠层级、文档、接口把全连接打折 | 峰值人数会右移（可能到 12–15 人），但“边际净增转负”的机制不变 |
| 每条路径 3h/周，人人相同 | 新人、跨地、跨时区的路径更贵 | 分布式团队的 c 更大，峰值更靠左 |
| 协调工时从 28h 深度工时里扣 | 真实团队会加班或降低质量来补 | 数值偏乐观，方向不变 |

**现实中 25 人也能跑，为什么不矛盾。** 单团队模型里 25 人有效深度是 0，因为全连接假设下每人每周要花 36h 在协调上；现实中 25 人活下来的方式是**把全连接换成树**：加一层汇报，路径从 300 条降到 24 条（25−1），代价是信息要经过 2–3 次转述、决策要等层级。模型算的是“没有层级时的协调成本”，树算的是“用失真换路径数”——两者都是成本，区别只是你把成本记在沟通上还是记在决策延迟上。加人之前先问一句：**你要的是更多路径，还是更短的决策链？**

**拆分之后，路径靠什么变少。** 不是靠“少说话”，而是靠把人对人的路径换成契约与自助：接口人把 N×N 变成 1×1（[77.3 团队边界与架构边界的对齐](77.3-团队边界与架构边界的对齐.md)）；X-as-a-Service 把“求人”变成“调用 API”；平台把部署、监控、配置这些高频交互收走，业务团队与平台的交互从“每次都要找人”变成“一次接入 + SLA”（[78.2 平台团队与中台](../78-技术组织设计/78.2-平台团队与中台.md)）。三条路对应三种成本，顺序是先还、再统一、再平台、最后拆。

**拆分信号**（出现两条就该拆，不必等到上限）：

| 信号 | 判据 | 拆成什么 |
|---|---|---|
| 边际净增 < 2h/周 | 模型里加第 10 人时出现 | 拆两条端到端业务流 |
| 团队内出现稳定的 3–4 人小群 | 信息只在小群流转，站会退化成汇报 | 按业务流切，不按职能切 |
| 一次改动要 3 个以上团队签字 | 边界把业务流切碎了（[77.3](77.3-团队边界与架构边界的对齐.md)） | 合并业务流或重画边界，不是加协调人 |
| 系统数 × 技术栈数 / 人数 > 8 | 认知负荷超载 | 先还服务、统一技术栈，再谈拆分 |
| 需要专职协调人才能推进 | 协调成本已经制度化 | 拆团队，并把公共部分收给平台（[78.2](../78-技术组织设计/78.2-平台团队与中台.md)） |

**远程与异步会改写 c，但不改写结论。** 异地、跨时区团队每条路径的同步成本更高：会议要预约、答复要隔夜，c 从 3h/周涨到 5h/周，同样的公式下峰值人数从 10 人掉到 6 人（28 ÷ 5 + 0.5）。异步文档能降低“同步”的频次，但会把成本换成延迟与理解偏差——路径没消失，只是从会议搬到了文档评审。所以分布式团队的正确打法不是“多开会补回来”，而是更早拆团队、更少跨团队依赖、把接口写成契约。

**小于 5 人的团队不在本模型的射程内。** 3–5 人的团队瓶颈通常不是沟通，而是单点覆盖：一个人休假就没人能改、一个领域只有一个半懂的人。这个阶段要做的是把“必须两个人懂”的模块补上备份，而不是套用“人越多越慢”去反对补人。本模型针对的是 8 人以上、已经需要流程的团队。

> 🔑 团队规模的上限不是管理幅度，是**边际净产能转负的那一点**：本机模型里是第 10 人。超过它，正确动作是拆团队、或把一部分交互变成 X-as-a-Service；“加强沟通”只会把时间花在会上，而路径数不会因为多开会而减少。

## 反模式

| 反模式 | 后果 |
|---|---|
| 超载就加人 | 沟通路径先涨，交付更慢；新人 3 个月才产出 |
| 一个人同时是 5 个服务的 owner | 每个服务都是“能跑就行”，没人敢重构 |
| 用“全栈”要求掩盖技术栈失控 | 每人都在学新东西，每人都不深 |
| 平台没建好就拆团队 | 新团队各自造轮子，外源负荷翻倍 |
| 用负荷数给团队排名 | 团队开始藏系统、藏服务，数据失真 |
| 让一个团队同时负责“稳态”与“敏态” | 稳态排期总被敏态挤掉，最后两头欠债 |

## 自检

**Q1** 为什么“超载就加人”常常让交付更慢？

▸ 答案：因为加人先增加**沟通路径**（5 人 10 条，8 人 28 条，12 人 66 条），协调成本立刻上升；而新人要 3 个月才熟悉上下文，短期内是净负产出。正确顺序是先减范围（还服务、砍系统），确认真的需要更多人，再加。

**Q2** 三类认知负荷里，哪一类最该先减？为什么？

▸ 答案：**外源负荷**。内在负荷是业务固有的，减不掉；相关负荷要靠统一技术栈，周期长；外源负荷（手工部署、过时文档、环境不一致）是纯浪费，且平台化一次投入长期受益。先减外源，团队才有余力处理内在复杂度。

**Q3** 一个 5 人团队负责 9 个系统、7 套技术栈、12 个服务，负荷 15。你会先做什么？

▸ 答案：先列“上周实际碰过哪些系统”，把没碰过的还回去或归档——通常能砍掉一半；再把 7 套技术栈收敛到 2–3 套（边缘的设期限）；最后才谈拆分。直接拆成两个 2.5 人团队，会把外源负荷复制一份。

**Q4** 团队规模为什么不能靠“加强沟通”解决？

▸ 答案：因为沟通路径是**平方增长**的：12 人 66 条、16 人 120 条，靠“多同步”只会把时间全花在会上。规模的上限是结构性的，解法只有拆分、或者把一部分交互变成 X-as-a-Service（不需要人对人沟通）。

**Q5** 负荷数能不能用来考核团队？

▸ 答案：不能。它一旦与考核挂钩，团队会开始**藏系统、藏服务**（把服务合并成一个名字、把系统说成别人的），数据立刻失真；正确的用法是内部自查与触发讨论，判断标准仍是“这条业务流该不该由这个团队拥有”。
