# 77.1 技术岗位的能力模型

## 一句话

> 能力模型不是“给人才打分”，而是**把岗位要求拆成可观察的维度、给每一级写清准入线**——招聘、晋升、培养共用同一张表，讨论才有共同语言。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 能力 = 技术深度 | 只深不交付的人，高级岗撑不住；深度只是四维之一 |
| 模型 = 打分表 | 模型的价值在**准入线**（缺哪项就上不去），不是平均分 |
| 一套模型通用 | 业务开发、基础设施、数据岗位的权重完全不同 |

## 一、四栏：先描述“这个人在哪工作”

陈皓给的简历四栏很好用，它其实就是岗位的四个面：

| 栏 | 内容 | 面试怎么验证 |
|---|---|---|
| **技术栈** | 语言、框架、工具 | 写代码 + 追问实现细节 |
| **技术领域** | 分布式、存储、网络、编译 | 系统设计题 |
| **业务领域** | 电商、支付、音视频 | 项目追问（STAR） |
| **软技能** | 沟通、协作、推动力 | 行为面试 + 场景题 |

### 简历与自介：原文写给候选人，反过来就是筛选信号

陈皓给候选人的简历建议，每一条都能反过来当面试官的判据：

| 项 | 原文建议 | 面试官怎么用 |
|---|---|---|
| 篇幅 | 两页 A4 以内，最好中英文版，用 **PDF** 不用 Word | 超过两页：重点不突出，或不会取舍 |
| 亮点 | 只呈现 **2–3 个**亮点 | “样样精通”通常等于没有亮点，追问哪个最深 |
| 自介 | **不超过 200 字**，用最简单的话说明情况 | 200 字讲不清自己，多半抽象能力弱 |
| 邮箱 | 建议 Gmail，不用 QQ 邮箱（职业化考虑） | 与能力无关，别当判据 |
| 技能 | **四栏**：技术栈 / 技术领域 / 业务领域 / 软技能 | 缺哪一栏，就在面试里补问哪一栏 |

> ⚠️ 这些是**筛选信号，不是评分项**。简历写得漂亮但追问就露馅的人不少；反过来，简历粗糙但项目经历扎实的人也不少——简历只决定“问什么”，不决定“要不要”。

## 二、四个维度，每级写准入线

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| **技术深度** | 会用框架 | 懂原理，能定位线上问题 | 能改/造轮子，能预判边界 |
| **系统设计** | 能按设计写 | 能独立设计一个模块 | 能定边界、算代价、说清失败模式 |
| **交付** | 需要人盯 | 独立按时交付 | 带多人交付，能砍需求保上线 |
| **影响力** | 只影响自己 | 影响一个小组 | 影响一个方向（标准、平台、方法） |

等级不是平均分，而是**短板决定**：任何一项低于该级准入线就上不去。

```go
// 岗位等级判定：技术深度 / 系统设计 / 交付 / 影响力，各 1–5 分。
// 判级不看总分，看「短板」——任何一项低于该级最低要求就降级。
var levels = []level{
	{"P5 独立交付", [4]int{3, 2, 3, 1}},
	{"P6 模块负责", [4]int{3, 3, 4, 2}},
	{"P7 领域负责", [4]int{4, 4, 4, 3}},
	{"P8 方向定义", [4]int{4, 5, 4, 4}},
}
```

真实输出（本机 `go1.27.1 darwin/arm64`，候选人 `[深度4 设计3 交付4 影响力2]`）：

```text
候选人 [4 3 4 2] → P6 模块负责
```

他的深度与交付都够 P7，但**设计 3 < 4、影响力 2 < 3**，所以卡在 P6。这就是“短板决定”：如果按总分（4+3+4+2=13）算，很容易被误判成 P7。

## 三、能力与市场价：一个 2018 年的参照

陈皓在原文里给过一组口径（**2018 年的一线市场，绝对值早已变化，只看相对差距**）：

| 组合 | 原文口径 |
|---|---|
| 语言 + 系统知识吃透 | 进 BAT，年薪约 30 万 |
| 再加底层（OS、网络、编译） | 约 50 万 |
| 再加分布式架构 | “至少 60 万以上” |

它说明的不是“背知识点能涨薪”，而是**能力的稀缺度决定价格**：会写业务代码的人多，懂底层与分布式的人少。模型的用途正是识别“稀缺的那一项”，而不是把所有人拉成平均分。

## 四、同一张表，三种用途

| 用途 | 用法 | 关键 |
|---|---|---|
| 招聘 | 岗位先写准入线，面试按维度取证 | 达不到准入线就不招，别“先招进来再说” |
| 晋升 | 用同一张表对照，提前 6 个月告知差距 | 差距要具体到维度，不是“再努努力” |
| 培养 | 按缺口排学习计划（[78.3 技术分享与成长机制](../78-技术文化与知识管理/78.3-技术分享与成长机制.md)） | 补最短的那块板，而不是最长的那块 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 只看技术深度招人 | 招来的人不交付、不协作，团队整体效率下降 |
| 用总分排名定级 | 掩盖短板，P7 的人做不了 P7 的事 |
| 模型与实际工作脱节 | 表上要求“高并发”，实际工作全是 CRUD |
| 一套模型套所有岗位 | 数据岗被要求“系统设计”，基础设施岗被要求“业务理解” |
| 晋升标准不提前告知 | 到评审时才说差距，等于抽签 |
| 用模型给团队贴标签 | 成员被固化，没人愿意补短板 |

## 自检

**Q1** 为什么判级要看“短板”，而不是总分？

▸ 答案：因为岗位是一个**组合能力**，缺一项就会在真实场景暴露。设计能力不足的人，深度再强也会把模块边界切错；影响力不足的人，方案再对也推不动。总分把短板平均掉，结果就是“级别到了、事做不成”。用准入线（每项最低分）能直接暴露这一点。

**Q2** 同一个候选人，深度 5、设计 2、交付 5、影响力 1，你会招他做什么岗？

▸ 答案：先看岗位需要什么。他适合**深度型个人贡献者**（比如内核/存储方向的高级工程师），但不宜做模块负责人——设计 2 意味着边界会切错，影响力 1 意味着推不动跨团队协作。招进来后要么配一个设计强的搭档，要么明确“只做深不带队”的路径。

**Q3** 原文的“30 万 / 50 万 / 60 万”该怎么用？

▸ 答案：只能看**相对差距**，不能当报价依据——那是 2018 年一线城市的口径，通胀、行业周期、公司规模都会让绝对值大幅变化。它的有效信息是：底层与分布式能力稀缺，稀缺度体现在价格上；招聘时该按“稀缺项”定级，而不是按“工作年限”。

**Q4** 为什么招聘、晋升、培养要用同一张表？

▸ 答案：因为三者是同一件事的三个时点。招聘按准入线选人，晋升按同一准入线评估，培养按缺口补——如果三张表不一致，就会出现“招进来时按 A 标准、晋升时按 B 标准、培养时补 C”，员工无所适从，管理者也失去可信度。

**Q5** 能力模型会不会把人“框死”？

▸ 答案：会，如果拿它贴标签。避免的方法是把模型当**当前快照**而不是身份：每半年重评一次，明确“补上哪一项就能到下一级”，并给对应的机会（不是只给培训）。模型描述的是“现在能做什么”，不是“你是什么人”。
