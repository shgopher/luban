# 77.3 如何判断架构能力

## 一句话

> 架构能力不是“知道多少架构名词”，而是**在信息不全时做出可辩护的取舍**——判断它只看四件事：会不会拆边界、能不能算代价、说不说得清失败模式、落不落得了地。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 架构能力 = 会画图 | 图谁都能画；难的是**为什么这么切**、切开后**代价谁付** |
| 架构能力 = 技术选型 | 选型只是最后一步，前面还有边界、容量、失败模式 |
| 架构能力 = 大厂背景 | 大厂经验带着规模前提，换个规模常常失效 |

## 一、四个判据与对应的问法

| 判据 | 问什么 | 好回答长什么样 | 差回答长什么样 |
|---|---|---|---|
| **拆边界** | “给一个模糊需求（如企业网盘），你先切哪一刀？” | 先分核心/周边、最小核心是什么、哪些是全局性功能 | 直接列技术栈（Go + MinIO + K8s） |
| **算代价** | “1000 万文件、峰值 5000 QPS，存哪、多少钱？” | 给出数量级与假设（单文件大小、冗余倍数、单价） | “用对象存储就行” |
| **失败模式** | “这个方案最可能怎么坏？” | 单点、雪崩、数据不一致各说一个，并给检测与回滚 | “不会坏”“有监控” |
| **落地** | “分几步？第一步交付什么？怎么验证？” | 分波 + 每波退出标准 + 回滚点 | “重构完就上线” |

这四问的顺序不能乱：**边界没定就谈容量，容量没算就谈失败模式，都是空中楼阁**。

## 二、评分：短板决定“能不能独立负责架构”

```go
// 架构能力评估：拆边界 / 算代价 / 失败模式 / 落地路径，各 1–5 分。
// 输出最弱项与「是否具备独立架构能力」。
func assess(s [4]int) (string, string) {
	min, weak, sum := 5, 0, 0
	for i, v := range s {
		sum += v
		if v < min {
			min, weak = v, i
		}
	}
	avg := float64(sum) / 4
	switch {
	case min <= 2:
		return "不具备", "最弱：" + names[weak] + "（先补这一项）"
	case avg >= 4:
		return "强", "最弱：" + names[weak] + "（可独立负责架构）"
	default:
		return "一般", "最弱：" + names[weak] + "（需人带）"
	}
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
候选人1 [5 4 4 4] → 强，最弱：算代价（可独立负责架构）
候选人2 [4 2 4 4] → 不具备，最弱：算代价（先补这一项）
候选人3 [3 3 3 3] → 一般，最弱：拆边界（需人带）
```

候选人 2 最能说明问题：他能拆边界、能讲失败模式、也能落地，但**算代价只有 2 分**——这种人设计出来的方案常常“技术上对、经济上不可行”。架构能力的下限由最弱项决定，不是平均分。

## 三、三个“像架构师但不是”的信号

| 信号 | 听起来 | 实际缺什么 |
|---|---|---|
| 只讲选型，不讲取舍 | “我们用 Kafka 因为吞吐高” | 没说为什么不选 RabbitMQ、代价是什么 |
| 只画图，不讲数据 | 一张漂亮的架构图 | 没有 QPS、延迟、存储量、成本 |
| 只讲最佳实践，不讲约束 | “按 DDD 拆就行” | 没说团队规模、历史包袱、上线节奏 |

反过来，靠谱的架构师通常有三个特征：

1. **先问约束**：用户量、增长预期、团队能力、合规要求。
2. **给区间与假设**：“按 3 倍冗余算，年成本约 30 万，假设单价不变”。
3. **主动说“不确定”**：并给出验证方式（试点、压测、PoC）。

## 四、和书里的判据接上

- 取舍是否合理，用 [58.6 架构设计流程与三原则](../../L5-工程效能/58-架构治理/58.6-架构设计流程与三原则.md) 的“合适 > 演化 > 简单”检查；
- 核心被周边功能弄脏了多少，用 [58.8 架构优劣的判据](../../L5-工程效能/58-架构治理/58.8-架构优劣的判据.md) 的伤害值算；
- 边界切得对不对，用 [26.6 模块化与包设计](../../L2-架构风格/26-分层与依赖/26.6-模块化与包设计.md) 的“最小核心 + 正交周边”检查。

面试时带一个真实场景（最好是你自己的系统），让对方在 30 分钟内给出上面四问的答案，比任何八股题都有区分度。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只考名词（CAP、DDD、Service Mesh） | 选出会背概念、不会做取舍的人 |
| 只看图不看数 | 方案漂亮但成本失控 |
| 不问失败模式 | 招来的人上线后才发现没想过回滚 |
| 用“大厂经验”当能力证明 | 规模前提不同，经验不可迁移 |
| 只给一个方案就录用 | 没有比较，无法判断权衡能力 |
| 用难题代替场景题 | 难题考智力，场景题考判断 |

## 自检

**Q1** 为什么“算代价”是四个判据里最容易被忽略、却最致命的一项？

▸ 答案：因为它是**唯一直接连着钱和工期**的一项。边界切错可以调整，失败模式可以补监控，但代价算错会让方案在预算或时间上直接不可行——而这类错误往往在详细设计甚至上线后才暴露。它也是“技术自嗨”和“工程判断”的分水岭。

**Q2** 一个候选人能把系统拆得很清楚，但说不出失败模式。你怎么判断？

▸ 答案：让他就自己刚拆的方案回答“最可能怎么坏、怎么发现、怎么回滚”。如果三个问题都答不上来，说明他的设计是**静态结构**思维，缺少运行期视角；可以给机会引导（提示单点、雪崩、数据一致性三个方向），引导后仍答不出，就不具备独立负责架构的能力。

**Q3** “给区间与假设”为什么是架构能力的信号？

▸ 答案：因为它说明对方知道**估算的本质是不确定性**。点估计（“需要 20 台机器”）掩盖了假设；区间加假设（“按峰值 3 倍、单机 500 QPS 算，18–24 台；若单机只能压 300，则要 30 台”）让听的人能校验、能调整，也暴露了他在哪里不确定。

**Q4** 为什么用“真实场景 + 30 分钟”比用难题更能判断架构能力？

▸ 答案：难题考的是智力和熟练度，场景题考的是**在约束下做取舍**——这正是架构工作的日常。30 分钟足够看出他会不会先问约束、能不能算数量级、有没有失败模式意识；而这些能力与“刷过多少难题”几乎无关。

**Q5** 如果候选人四个维度都是 3 分，该不该给架构岗？

▸ 答案：不该直接给“独立负责”的岗。四项都 3 分说明他能配合、能执行，但没有任何一项达到“定义方向”的水准；更合适的安排是“架构岗 + 资深架构师带”，或者先做模块级设计（[77.1 技术岗位的能力模型](77.1-技术岗位的能力模型.md) 里的 P6），用 6–12 个月补最弱项。
