# 77.4 团队能力与技术的匹配

## 一句话

> 技术选型不只问“哪个好”，还要问**团队接不接得住**——同一套架构，A 团队能维护、B 团队维护不了；匹配看三件事：能力缺口、维护成本、补齐周期。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 选“业界最好”的技术 | 最好的技术配最弱的团队，等于给团队挖坑 |
| 团队可以边做边学 | 学习要时间，而线上故障不等人 |
| 缺人就招人 | 招人周期 2–3 个月，且新人也要 3 个月上手 |

## 一、先画能力矩阵，再谈匹配

| 能力 | 岗位需求 | 团队现状（最高分） | 达标人数 |
|---|---|---|---|
| Go | 4 | 5 | 2 |
| 分布式 | 4 | 4 | **1** |
| 数据库 | 4 | 5 | **1** |
| K8s | 3 | 4 | 2 |
| 可观测 | 3 | 3 | **1** |

```go
// 团队能力矩阵：每人 × 每项能力（1–5 分），算缺口与单点。
for skill, want := range need {
	best, holders := 0, 0
	for _, p := range team {
		if s := p[skill]; s > best { best = s }
		if p[skill] >= want { holders++ }
	}
	// holders < 2 → 单点/缺口
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
Go     需求=4 最高=5 达标人数=2
K8s    需求=3 最高=4 达标人数=2
分布式    需求=4 最高=4 达标人数=1 ← 单点/缺口
可观测    需求=3 最高=3 达标人数=1 ← 单点/缺口
数据库    需求=4 最高=5 达标人数=1 ← 单点/缺口
```

读法：**达标人数 = 1 的项就是单点**。这三项恰好是分布式系统最贵的三项——意味着这个团队现在只能“维持”，不能“演进”。

## 二、匹配三问：任何技术选型都要过

| 问题 | 不合格的信号 | 合格的标准 |
|---|---|---|
| **几个人能改？** | 只有 1 个人动过这套代码 | ≥ 2 人能独立改，且做过 code review |
| **出事谁能定位？** | 出事只能找原厂/外部顾问 | 团队内有人能从日志/指标定位到根因 |
| **三年后谁维护？** | 依赖一个即将离职的人 | 有 runbook、有轮值、有接班人 |

三问里最容易被忽略的是第二问。很多团队能“用”一套技术，但**不能修**——出故障只能重启或回滚，这就是能力不匹配的典型状态。

## 三、引入新技术的门槛

| 门槛 | 判据 | 反例 |
|---|---|---|
| 至少 2 人能独立维护 | 能改配置、能排障、能升级 | 只有一个人装过 |
| 有 runbook | 常见故障有处置步骤 | 出事靠群里问 |
| 有回滚路径 | 版本可退、数据可回 | 升级即单向 |
| 有培训与演练 | 团队做过一次故障演练 | 上线前没人碰过 |

四条全过，才叫“团队接得住”；过不了，就该选更简单的方案，或者先补人再上。

## 四、招聘、培养、外包：怎么选

| 情况 | 选择 | 理由 |
|---|---|---|
| 紧急缺口、项目 3 个月内上线 | **招聘 / 借调** | 培养来不及 |
| 长期能力、影响多个项目 | **培养** | 招聘只能解决一个点，培养能形成梯队 |
| 非核心、临时性工作 | **外包 / 托管服务** | 自建不经济 |
| 核心链路、长期演进 | **自建 + 至少 2 人** | 外包无法承担线上责任 |

陈皓在原文里有一个观点值得讨论：**测试、运维、项目管理是支持性工作，想做技术就要转到有产出的开发**。这个判断有它的时代背景（当时不少团队把这些岗位当“养老岗”），但在今天的 SRE/平台工程语境下并不完全成立——**好的 SRE 与平台工程师是稀缺的产出型角色**。我的判断是：判断标准不该是岗位名称，而是**这个岗位是否直接对系统质量与交付效率负责**。

## 五、团队能力决定演进节奏

同一个目标架构，能力强的团队可以一次跳两波，能力弱的团队只能一波一波走：

| 团队能力 | 演进策略 | 单波时长 |
|---|---|---|
| 有 2 人以上做过同类系统 | 可并行两波 | 3–4 个月 |
| 只有 1 人做过 | 串行 + 外部评审 | 4–6 个月 |
| 没人做过 | 先做试点/PoC，再立项 | 6 个月 + |

这也是 [58.4 演进路线图](../../L5-工程效能/58-架构治理/58.4-演进路线图.md) 里“单波 ≤ 6 个月”的另一种解释：不是时间本身，而是**团队在这段时间内能否形成维护能力**。

## 反模式

| 反模式 | 后果 |
|---|---|
| 按“业界最佳”选型，不看团队 | 系统上线即失控，故障只能回滚 |
| 单点能力不补 | 一个人休假，系统就没人敢动 |
| 只招人不培养 | 空降兵水土不服，老成员失去成长路径 |
| 用外包做核心链路 | 出事故无人负责，知识也留不下来 |
| 新技术的门槛只看“跑通 Demo” | 上线后才发现没人会排障 |
| 能力矩阵一年不更新 | 缺口判断失真，培训投错方向 |
| 把支持性岗位一律看低 | 平台/SRE 缺位，开发被迫人肉运维 |

## 自检

**Q1** 为什么“达标人数 ≥ 2”是引入新技术的硬门槛？

▸ 答案：因为 1 个人意味着单点：他休假、离职、或者只是忙，这项能力就断了。2 个人才能形成 review、交接与排障的冗余，也才能在出故障时互相校验判断。这个门槛与 [78.2 知识沉淀与文档体系](../78-技术文化与知识管理/78.2-知识沉淀与文档体系.md) 里的 bus factor 是同一件事。

**Q2** “能改”与“能修”有什么区别？为什么后者更难？

▸ 答案：“能改”是按文档改配置、加功能；“能修”是在信息不全时定位根因并恢复——需要理解内部机制、会看指标与日志、知道失败模式。前者可以靠培训获得，后者只能靠真实故障与演练积累，所以更难，也更稀缺。

**Q3** 什么时候该招人，什么时候该培养？

▸ 答案：看**时间窗**与**复用度**。3 个月内要上线、且缺口只影响一个项目 → 招人或借调；缺口影响多个项目、且时间窗在半年以上 → 培养（成本更低、留存更好）。两者不互斥：招来的人也要有培养路径，否则他会成为新的单点。

**Q4** 原文说“测试、运维、项目管理是支持性工作”，你怎么看？

▸ 答案：这句话有时代背景，今天不宜照搬。判断标准应是“这个岗位是否直接对系统质量与交付效率负责”：只会点按钮的运维是支持性的，能建平台、能定 SLO、能做容量规划的 SRE 是产出型的。用岗位名称代替职责判断，会既招不到好 SRE，也留不住。

**Q5** 团队能力弱，是不是就不该做架构演进？

▸ 答案：不是，但要改节奏与路径：先做试点/PoC 建立第一手经验，再串行推进，每波都要有退出标准与回滚点；同时把“培养 2 个能维护的人”写进这一波的退出标准。能力弱不是不做的理由，而是**不能一次跳两波**的理由。
