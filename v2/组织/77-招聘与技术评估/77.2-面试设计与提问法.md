# 77.2 面试设计与提问法

## 一句话

> 面试不是“考知识”，而是**用有限时间采集能预测工作表现的证据**——每个问题都对应能力模型里的一项，追问到细节，独立打分再合议。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 面试 = 考八股 | 背下来的知识不能预测工作表现，**追问出的细节**才能 |
| 感觉对就行 | 没有评分维度与锚点，面试官之间的“感觉”无法合议 |
| 题越难越好 | 难题测的是“做过没有”，不是“能不能做” |

## 一、题从哪来：写什么问什么

陈皓给准备者的建议，反过来就是面试官的出题原则：**简历写什么，就问什么**。

| 简历信号 | 该问什么 | 别问什么 |
|---|---|---|
| “负责订单系统重构” | 重构前后差在哪、怎么验证、回滚方案 | “讲一下 CAP” |
| “精通 Go 并发” | 写一段有竞争的代码，让他找 bug | “channel 有几种用法” |
| “主导过双活” | 数据冲突怎么解、切换失败怎么办 | “双活和主备的区别” |

面试官常犯的错，是拿自己的知识栈出题：候选人写 Java，你问 Go 的 GMP，测到的是“他有没有读过你读过的文章”。

## 二、三类题，各自测什么

| 题型 | 测什么 | 时间 | 判据 |
|---|---|---|---|
| **项目追问** | 真实经历、取舍能力 | 20 分钟 | 能不能说出“为什么没选另一个” |
| **编码** | 基本功、边界意识 | 30–45 分钟 | 先跑通再优化；边界与错误处理 |
| **设计** | 拆解与权衡 | 30 分钟 | 会不会问约束、说不说得清失败模式 |

项目追问用 STAR，但重点在 **R（Result）与反思**。陈皓建议准备“四问”，面试官可以直接借来问：**最自豪的项目、最难的、最痛的、最大的错误**。答“最痛”和“最大错误”时，人很难编。

编码题的三条规矩：

1. **必须真写**——白板或共享编辑器，不许“讲思路就行”。
2. **先跑通再优化**——写不出来却大谈最优解，是典型的背题信号。
3. **追问边界**——空输入、超时、并发、错误处理，各问一句。

设计题用 Problem Solving 的方式：给一个没见过的场景（例如“公路双向车流的调度”“按性格排座位”），**不要求最优解，看思路**。能问出约束条件的人，比直接给方案的人更值得要。

## 三、评分卡：先独立打分，再合议

| 维度 | 权重 | 门槛（1–5） | 看什么 |
|---|---|---|---|
| 编码 | 0.30 | 3 | 能写出可运行的代码，边界清楚 |
| 基础与系统 | 0.30 | 3 | 原理、排障、性能常识 |
| 设计 | 0.25 | 3 | 拆边界、算代价、说失败模式 |
| 沟通协作 | 0.15 | 2 | 听得懂问题、表达有条理 |

```go
// 面试评分卡：四个维度按权重折算，低于门槛直接不通过。
func decide(score map[string]float64) (float64, string) {
	var total float64
	for _, d := range dims {
		if score[d.name] < d.gate {
			return 0, "不通过： " + d.name + " 低于门槛"
		}
		total += score[d.name] * d.weight
	}
	switch {
	case total >= 3.8:
		return total, "strong hire"
	case total >= 3.2:
		return total, "hire"
	default:
		return total, "no hire"
	}
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
候选人1 加权=3.75 结论=hire
候选人2 加权=0.00 结论=不通过： 编码 低于门槛
候选人3 加权=3.00 结论=no hire
```

三条读数：

- 候选人 1 各项均衡，**3.75 差一点到 strong hire**——说明门槛设计合理，不是随便给高分。
- 候选人 2 基础与设计都是 5 分，但**编码 2 分低于门槛，直接不通过**——一票否决项必须先于加权。
- 候选人 3 四项都是 3 分，加权 3.00，**低于 hire 线**——“哪项都不差”不等于“值得招”。

流程上还有两条硬规则：**先独立打分再合议**（避免锚定），**一票否决项单独列出**（编码、诚信、合规）。

## 四、国内与国外：两套面试风格

| 维度 | 国内常见 | 国外常见 |
|---|---|---|
| 目标 | 招“马上能干活”的 | 招“超过现有团队同级 50%”的 |
| 内容 | 知识题为主，少追问 | 全方位：编码、设计、行为 |
| 轮次 | 2–3 轮，快进快出 | 至少 5 轮（3 技术 / 1 经理 / 1 HR） |
| 编码 | 常不写 | 必写，且看代码质量 |
| 风险 | “容易蒙混过关” | 成本高、周期长 |

陈皓的原话是“国内的公司是比较好面的，国外的公司是比较难面的”。对招聘方的启示不是“学国外”，而是：**轮次与深度要匹配岗位风险**——招一个改核心交易链路的人，2 轮聊天是不够的。

## 五、反问环节：面试官也在被面试

陈皓给候选人的建议，反过来就是面试官的信号：

| 候选人的反问 | 说明什么 |
|---|---|
| “你们一线经理还写代码吗？” | 他在意技术氛围，且做过功课 |
| “这个岗位半年内最重要的目标是什么？” | 他在意结果，不是混日子 |
| 什么都不问 | 要么没兴趣，要么没准备 |

面得好的人，反问会尖锐；面得差的人，通常只问薪资与加班。**反问环节的信息量，常常不低于正题。**

## 反模式

| 反模式 | 后果 |
|---|---|
| 拿自己的技术栈出题 | 测到的是“像不像我”，不是“能不能干” |
| 只问知识、不追问细节 | 背题者蒙混过关 |
| 不写代码就录用 | 编码能力靠猜，入职后返工成本高 |
| 先合议再打分 | 锚定效应，独立判断消失 |
| 没有门槛、只看总分 | 招进“样样及格、样样不行”的人 |
| 面试轮次与岗位风险不匹配 | 核心岗招错人，代价是几个季度 |
| 只招“超过同级 50%”却不给对应薪资 | 招不到，或招来很快走 |

## 自检

**Q1** 为什么“写什么问什么”比“统一题库”更能预测表现？

▸ 答案：因为简历上的经历是他真实做过的事，追问细节能验证深度与真实性；统一题库测的是“准备程度”，而准备程度与工作表现相关性弱。写什么问什么还有一个副作用：它会反向抑制简历造假——写上去的东西必须经得起追问。

**Q2** 编码题为什么要求“先跑通再优化”？

▸ 答案：因为真实工作里，先要正确、再要快。上来就谈最优解的人，往往写不出可运行代码（背题信号）；先写出能跑的版本、再逐步优化的人，展示了工程顺序感。追问边界（空输入、超时、并发）能进一步区分“能跑”与“能上线”。

**Q3** 评分卡为什么要设“门槛”而不只是加权？

▸ 答案：加权会把致命短板平均掉。编码 2 分的人，即使设计 5 分，也不能招来做需要天天写代码的岗位——本机演示里候选人 2 加权前就被门槛拦下。门槛对应“这个岗位绝不能让的底线”，加权对应“同等达标时的优先级”。

**Q4** 为什么必须“先独立打分再合议”？

▸ 答案：合议时先说的人会锚定其他人的判断，尤其是资历深的面试官。独立打分让每个人的证据先固化，合议时讨论的是“为什么你给 2 分、我给 4 分”，而不是“我觉得他行”。这也是结构化面试有效性的来源。

**Q5** 国内面试“快进快出”的风险是什么？

▸ 答案：快本身不是问题，风险在于**轮次与深度不匹配岗位风险**。招一个执行明确任务的工程师，2 轮足够；招一个要动核心链路、要做架构决策的人，2 轮聊天无法验证设计与失败模式思维——招错的成本（返工、事故、团队士气）远高于多面 3 轮的成本。
