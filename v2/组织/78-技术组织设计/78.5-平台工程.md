# 78.5 平台工程：从工具到平台的三个阶段

## 一句话

> 内部平台不是一次建成的，而是**从无到有（引入开源/商业）→ 从小到大（半自建 + 元数据治理）→ 从繁到简（整合 + 自服务）**；判据不是技术栈有多新，而是**每接入一个应用还要不要投人力**——线性增长的“平台”只是工具堆。

**来源**：三阶段、四化、产品五层次与平台三特征来自石雪峰《DevOps 实战笔记》第 21、22、3 讲（2019）；规模效应测算为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “自研才自主可控，效能才高” | DevOps 状态报告的观察相反：**倾向于完全自建工具的企业效能往往不高**，而大部分采用开源工具的企业反而不差。自研不是能力证明，是阶段性选择 |
| “平台 = 一堆工具接在一起” | 平台有三个硬特征：吸附效应、规模效应、积木效应。缺了规模效应（成本随接入方线性涨），它就是一个更大的工具 |
| “先把功能做出来，扩展性以后再说” | 扩展性欠账在平台上的利息极高：两处真实翻车（没预留租户、参数写死）都导致后期**推倒重来**，权限模型都得重设计 |
| “平台做出来自然有人用” | 用户不来通常只有一句话：**平台还不够简单**。Jenkins 社区专门发起过 “5 Click，5 Minutes” 项目，把建一个服务压到 5 次点击、5 分钟 |

## 三个阶段：一张表定位自己

| 阶段 | 现状特征 | 推荐策略 | 成功判据 | 典型失败 |
|---|---|---|---|---|
| **① 从无到有** | 交付链路上还有大量本地操作与重复劳动；没有专职工具团队 | 引入开源/商业工具，快速补齐**能力短板** | 高频、多人协作环节有系统支撑 | 选了冷门工具，评审/集成配套不全 |
| **② 从小到大** | 工具齐了；需求从“够用”转向“好用”；差异化与规模问题出现 | **半自建 + 定制商业工具**（二次开发/封装） | 平台能承载差异化需求且不改核心 | 参数写死、没预留租户 → 推倒重来 |
| **③ 从繁到简** | 平台太多、太复杂、价值说不清 | **整合工具 + 平台化治理 + 自服务** | 一件事在一个入口完成，且能自助 | 大一统平台与既有平台零和，落地失败 |

### ① 从无到有：引入，而不是自研

这个阶段唯一的目标是补齐短板，所以**选主流工具**，不做功能对比赛：

| 环节 | 主流选择 |
|---|---|
| 需求/缺陷 | Jira（+ Confluence 做知识管理） |
| 版本控制 | GitLab |
| 持续集成 | Jenkins |
| 代码质量 | SonarQube |
| 构建 | Maven / Gradle |
| 制品管理 | Artifactory / Harbor（开源常用 Nexus） |
| 配置管理与配置中心 | Ansible / Apollo |
| 测试 | Selenium / Appium / JMeter / TestNG |
| 安全合规 | Black Duck / Fortify |

“主流”的判据很实际：**可扩展性有接口、有插件生态、经验一搜一大把**。反例是一家大型金融机构迁 Git 时选了几乎没人听过的开源平台，操作流程与常规工具不同、评审与集成配套都不完善，最后还得迁回主流工具——迁移成本白付了两次。

商业工具同样是可选项，而且常常是**投资而非成本**：Artifactory 在制品类型、分布式部署、漏洞检查、外部集成上明显强于开源 Nexus；Gradle 商业版能把编译速度提升一个数量级。判断标准不是“贵不贵”，而是“省下来的时间值多少”——自研一套替代品的成本，通常一点不少。

### ② 从小到大：半自建，两个必须提前想的事

半自建的主流形态是**基于开源工具做二次开发或封装**：用 Jenkins API + 插件扩出一套打包平台，业务逻辑和交互都在上层，调度与执行仍交给 Jenkins。

两个必须提前想的点，都是作者踩过的坑：

**（1）设计时给扩展留空间**

| 翻车案例 | 后果 | 当时更好的做法 |
|---|---|---|
| 初期只为单一业务设计，没考虑租户 | 想对外开放时，要在更高维度插入租户，功能页面和**权限模型**都要重设计 | 一开始就把单一业务实现为平台的一个租户 |
| 为快速上线简单封装 Jenkins，参数写死在页面里；每接一个项目写一个页面 | 上百个应用接入时差异化需求爆炸，**平台推倒重来** | 参数从接口获取、配置化渲染 |

技术选型上也一样：前后端分离、主流技术栈、统一的语言与典型设计模式，都是为了“后来的人能快速进团队、功能能快速迭代”。但要区分**顶层规划**与**过度设计**：只预留可预见范围内的空间。

**（2）实现时关注元数据治理**

元数据（应用名、模块名、安全 ID 等）是串起整个平台数据结构的钥匙链。一旦进了数据模型，往往已经成了各种主键/外键约束，**改不动**。

| 单平台视角 | 多平台视角 |
|---|---|
| 怎么维护都行 | 元数据是平台间的**标准语言**；语言不通就要加大量翻译，系统耦合随之变大 |
| 例如：购物车叫 `cart` | 另一个平台叫 `shopping-cart-android`、还带 `-feature1` 维度 → 数据对不齐 |

所以元数据治理必须是**顶层规划**：建统一 CMDB 管应用信息，或用应用创建审批流程管控应用生命周期。这属于技术债，**做得越晚，还债越贵**（[58.2 技术债管理](../../L5-工程效能/58-架构治理/58.2-技术债管理.md)）。

### ③ 从繁到简：整合与自服务

到这个阶段，典型症状是三条：**平台太多**（做一件事要切来切去）、**平台太复杂**（要培训才能用对）、**价值说不清**（用了能带来什么）。

治理顺序不能反：

1. **找主路径**。用一个平台覆盖软件交付的主路径，把单点能力串起来。**持续交付流水线就是这条主路径**（[52.5 流水线平台](../../L5-工程效能/52-持续集成/52.5-流水线平台十大特征.md)）。
2. **区分平台与工具**。测试环境里散着大量工具，而一整套测试平台可以满足测试方方面面的需求——**用户在一个平台上工作就够了**。收敛到几个核心平台后，界面切换的场景才会减少。
3. **做自服务**。用户自己登录、自己操作、自己看数据；一键能完成才算真自服务。作者的原话很扎心：**当你埋怨“平台这么简单为啥还有人不会用”，只能说明平台依然不够简单。**

平台建设的四化，可以作为第三阶段的验收清单：

| 四化 | 含义 | 判据 |
|---|---|---|
| **标准化** | 一切皆有规则与标准 | 同一件事只有一种做法 |
| **自动化** | 干掉不必要的手工环节 | 能一键完成的绝不操作两次 |
| **服务化** | 面向用户设计，不面向专家设计 | 新人无外部依赖即可完成工作 |
| **数据化** | 收集、汇总、分析、展示 | 改进决策有客观数据支撑 |

## 平台 vs 工具：三个可检查的特征

| 特征 | 含义 | 反例（只是工具） |
|---|---|---|
| **吸附效应** | 不断吸收中小工具，成为能力集合体 | 每来一个新需求就再做一个新系统 |
| **规模效应** | 成本不随使用方扩展而线性增加 | 接入一个应用就定制一次页面、配一个专人 |
| **积木效应** | 有通用共享的基础能力，能快速搭新业务 | 每个业务从零写一遍 |

“平台就是搭台子，工具来唱戏”：平台提供场所、道具、数据，唱戏的专注把戏唱好。**如果平台去唱戏，就顾不上台子的质量；如果唱戏的天天琢磨建平台，戏本身也精进不了。** 做平台还是做工具无关好坏，只关乎选择。

## 可运行：把“规模效应”算出来

平台化最容易被含糊过去的一点是“值不值”。它其实可以算：两个方案的固定成本与每应用增量成本一旦确定，**盈亏平衡点**就是确定的。

```python
#!/usr/bin/env python3
"""scale.py —— 平台的规模效应可以算：成本随应用数线性还是准常数。

方案 A 手工接入：平台固定 60 人日，每个应用再定制 2.0 人日（页面/参数/联调）
方案 B 自助接入：平台固定 120 人日，每个应用只填 0.2 人日配置（模板 + 参数化）
"""
FIX = {"A": 60, "B": 120}
PER_APP = {"A": 2.0, "B": 0.2}

def cost(plan, n):
    return FIX[plan] + PER_APP[plan] * n

n = 1
while cost("A", n) < cost("B", n):
    n += 1
print(f"盈亏平衡点：接入 {n} 个应用时，自助接入的成本追平手工接入"
      f"（{cost('A', n):.0f} vs {cost('B', n):.0f} 人日）")
print(f"\n{'应用数':>6} {'手工接入':>10} {'自助接入':>10} {'差额':>8} {'每应用增量成本':>14}")
for k in (10, 50, 100, 200, 500):
    a, b = cost("A", k), cost("B", k)
    print(f"{k:>6} {a:>10.0f} {b:>10.0f} {a-b:>8.0f} {'2.0 / 0.2':>14}")
print("\n结论：固定成本高的方案，只有在规模足够大时才划算；")
print("      平台化真正的分水岭不是技术选型，是「每接入一个，还要不要投人力」。")
```

**本机实测输出**（Python 3.14.8）：

```text
盈亏平衡点：接入 34 个应用时，自助接入的成本追平手工接入（128 vs 127 人日）

   应用数       手工接入       自助接入       差额    每应用增量成本
    10         80        122      -42      2.0 / 0.2
    50        160        130       30      2.0 / 0.2
   100        260        140      120      2.0 / 0.2
   200        460        160      300      2.0 / 0.2
   500       1060        220      840      2.0 / 0.2
```

三条读法：

1. **34 个应用是这道题的平衡点**。低于它，先做手工接入（或直接买商业工具）更划算——这也是“阶段一别急着自研”的算术依据。
2. **差额随规模线性拉大**（100 应用省 120 人日，500 应用省 840 人日）。平台的收益不是“效率提升百分之几”，而是**每多一个应用，少投一个人**。
3. **参数要按自己的组织填**。把 2.0 换成 0.5、把 0.2 换成 0.3，平衡点会跳到 300 以上——此时结论会反转：**规模不够就别做自助平台**。

> ⚠️ 这张表只算接入成本，没算运维成本。作者在问答里强调过：如果“接入一个用户就要投一个人支持”，那也是线性增长——**看起来是平台，实际是人力外包**。

## 产品设计的五个层次

平台是产品，用产品设计的五层来查漏，从上往下依次回答：

| 层次 | 要回答的问题 | 流水线平台的答案 | 反例 |
|---|---|---|---|
| **战略存在层** | 解决谁的什么痛点 | 战略建立在**不变的事物**上：效率、质量、成本、安全；在某一点做到极致 | 照着竞品抄功能，抄完不知道为谁服务 |
| **能力圈层** | 做什么、不做什么 | 主航道（覆盖交付过程）+ 护城河（数据沉淀、外部能力接入）；**只做打通，不替换既有平台** | 一上来就做企业级端到端大平台，与既有平台零和 |
| **资源结构层** | 我有什么别人没有 | 机器资源池、审批入口、安全规则、用户习惯、数据积累、领导支持 | 以为用户会因为“功能多”而迁移 |
| **角色框架层** | 用户是谁、在什么场景下用 | 分支参数要能选历史、能自动关联；**好产品本身就是使用说明书** | 分支名靠手输复制粘贴，一天几十次 |
| **感知层** | 用起来什么感觉 | 一致、反馈、效率、可控（参考成熟设计体系） | 内部产品就可以“家丑不外扬” |

其中**能力圈层**那条最值钱：那支 4 人小队面对千人协同时，明确把能力圈划在“不替换现有平台，只做链路打通”——既有平台继续服务，同时以标准方式接入，结果是双赢：既有平台多了一个入口，自己拿到了能力和用户。**反过来做（替换）在用户总量固定的前提下必然是零和**。

**角色框架层**的例子也值得记：平台提供了“分支参数”功能，反馈全是负面的，但数据显示很多人在用。矛盾点在场景——分支名又长又容易错，每次都要从别处复制。场景出现一次是小事，每天几十次就是大问题；解法只需要一个历史下拉或自动关联，**基于核心场景的微创新就够**。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：平台门户（IDP）开源可参考 **Backstage**（服务目录 + 脚手架 + 插件）；流水线能力见 [52.5 流水线平台](../../L5-工程效能/52-持续集成/52.5-流水线平台十大特征.md)（GitLab CI / Jenkins LTS / Tekton / Argo Workflows / Azure DevOps）；制品与镜像用 Harbor；配置中心用 Apollo/Nacos。**Backstage 已真跑过**（2026-11-22，Backstage 1.57.0 / Node 26.13.0 / Yarn 4.13.0）：`create-app` 脚手架生成 → `yarn install`（2687 个包、**1.7 GB node_modules、2 分 30 秒**）→ `yarn start` 起前端 3000 + 后端 7007，首页 200（`<title>Scaffolded Backstage App</title>`），guest 登录拿到 495 字符的 token，服务目录 API 返回 **9 个实体**（`Component example-website`、`API example-grpc-api`、`Group guests` 等）。两个实测坑：① **新版只支持 Node 24.15+ / 26.13+**，Node 20 上 `create-app` 直接报 `Node version 20 is not a supported LTS version`；② 模板默认**没有** guest 登录，服务目录 API 不带 token 返回 `AuthenticationError: Missing credentials`，本地试跑要在 `app-config.yaml` 里显式开 `auth.providers.guest`。

**可抄**：先给平台做一张“阶段自评表”，三个问题各打 1–5 分，低于 3 分的先别进下一阶段。

```yaml
# platform-stage.yaml：季度复盘时填一次，分数决定本季度投入方向
- id: capability_gap        # 阶段一判据：高频/多人协作环节是否有系统支撑
  question: 需求、代码、构建、制品、测试，哪一环还在靠本地操作或口头流转？
  score: 4
- id: extension_room        # 阶段二判据：扩展是否靠配置而不是改代码
  question: 新增一个应用接入，需要改平台代码或前端页面吗？
  score: 2
- id: metadata_governance   # 阶段二判据：元数据是否统一
  question: 应用名/模块名/安全 ID 在各平台是否同一套？（有无 CMDB）
  score: 1
- id: self_service          # 阶段三判据：一件事能否在一个入口自助完成
  question: 一个新同学不看文档，能否在 10 分钟内完成一次构建与部署？
  score: 2
- id: scale_effect          # 阶段三判据：成本是否准常数
  question: 接入第 50 个应用时，还要不要新增人力？
  score: 2
```

**可验**：把 `score ≤ 2` 的项按上面的 `scale.py` 各算一次成本，得到“先补哪一块”的排序；`scale.py` 的输出就是基准（本例平衡点 34 个应用）。自服务是否达标，用最硬的判据：**不看文档，10 分钟内完成一次构建部署**。

**可退**：平台治理的本质是“收敛”，收敛的每一步都要可逆——保留既有平台的独立入口（打通而不替换），任何整合层出问题都能退回原入口；新平台上线先并行跑一个季度，采用率不达标就停，不删既有系统。

## 边界：什么时候别建平台

| 场景 | 原因 | 替代 |
|---|---|---|
| 应用 < 30 个、团队 < 50 人 | 平衡点不到（见上面的测算），固定成本摊不平 | 直接买商业工具或用 SaaS |
| 没有重复劳动可收敛 | 平台的价值来自规模化复用，一事一议的场景不适合 | 写脚本 + 文档 |
| 既有平台由其他部门把持、且不愿接入 | 整合会变成政治问题，技术方案再好也落不了地 | 先做数据打通，或从新业务切入 |
| 组织还没有稳定的交付流程 | 流程没标准化，平台只能固化混乱 | 先做 [59.5 价值流分析](../../L5-工程效能/59-研发效能度量/59.5-价值流分析.md) 与流程治理 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 一上来自研全家桶 | 效能反而不如用开源（状态报告的观察），且维护成本长期吃掉团队 |
| 按竞品功能清单做产品 | 抄完不知道为谁服务，战略层缺失，资源一撤就死 |
| 参数写死在页面、每接一个项目写一个页面 | 上百应用时推倒重来 |
| 元数据各平台各叫一套 | 打通时靠翻译层，耦合变大，连接变脆 |
| 平台替换既有工具 | 零和：动了别人的地盘，阻力大于收益 |
| 用“平台”包装人力服务 | 接入一个人投一个人，成本线性，规模效应为负 |
| 只做整合不做自服务 | 整合后更复杂，用户回到原来的工具 |
| 没有采用率指标 | 平台建成没人用，价值说不清，下一年预算被砍 |

## 自检

**Q1** 公司有 25 个应用，CTO 要求“自研一套 DevOps 平台，自主可控”。按本节的算术，应该怎么回应？

▸ 答案：先算平衡点。若手工接入 2.0 人日/应用、自助后 0.2 人日/应用、固定成本差 60 人日，平衡点在 34 个应用；25 个应用时自助方案反而更贵。更合理的路径是阶段一：用开源 + 商业工具补齐短板，把有限人力投在“减少重复劳动”的具体环节，等应用数过了平衡点再谈平台化。

**Q2** 为什么“完全自建工具的企业效能往往不高”？

▸ 答案：自建把资源从“解决交付问题”转移到“重建已有的东西”上；同时自建工具缺少外部用户与插件生态，能力扩展慢，维护成本长期占用团队。状态报告的观察是相关而非因果，但对多数企业，开源/商业工具在阶段一的投入产出比明显更高。

**Q3** 平台设计“预留扩展”与“过度设计”的界线在哪？

▸ 答案：看是否**可预见**。可预见的是：单一业务将来可能变多租户、接入应用会从个位数涨到百位数、参数会因项目差异而变多——这些要预留（租户维度、参数配置化、元数据结构）。不可预见的是：具体会接哪些平台、用户会提什么新功能——这些不预留，靠插件/接口/逃生舱承接。

**Q4** 为什么“元数据治理”被列为技术债，而且越晚越贵？

▸ 答案：元数据一旦进入各平台的数据模型，就成为主键/外键约束，改一次要动数据、接口、报表、权限。平台越多，同一实体在各处的叫法与维度越分散（`cart` vs `shopping-cart-android` vs `shopping-cart-feature1`），对齐成本随平台数增长。晚上一年，翻译层就多一层。

**Q5** 第三阶段的三个症状（平台太多、太复杂、价值说不清），哪个应该先解决？

▸ 答案：先解决“价值说不清”。它决定了后面两个动作有没有资源：说不出价值，收敛平台会被当成夺权，简化操作会被当成“功能缩水”。做法是用一条主路径（持续交付流水线）覆盖端到端，用它的采用率与交付周期变化说明价值，再谈整合。

**Q6** “只做打通、不替换既有平台”在什么情况下不成立？

▸ 答案：当既有平台本身是瓶颈、且无法通过接口改造解决时（例如它根本不提供 API、数据模型无法映射）。此时“只打通”会把瓶颈固化；正确做法是替换其中一段，但要先证明：替换的成本低于长期绕行的成本，并且替换后仍保留原平台的独立入口作为回退。

**Q7** 平台上线三个月，采用率 15%。团队认为是“推广不到位”，准备加大培训。按产品五层，应该先查哪一层？

▸ 答案：先查角色框架层与感知层——用户在真实场景里是否被卡住（例如分支名要手输、参数太多不知道填什么）。加大培训属于最弱的一招：培训能解决“不知道”，解决不了“不好用”。判据是“不看文档，10 分钟内能否完成一次构建部署”。

**Q8** 一个平台团队问：“我们该优先做插件生态，还是优先做自服务？”用本节的三特征判断。

▸ 答案：先做自服务。插件生态对应吸附效应（能力扩张），自服务对应规模效应（成本准常数）；没有规模效应，能力扩张只会让平台更复杂、支持成本更高。顺序是：先把主路径上的事做到自助，再让垂直能力以插件接入。
