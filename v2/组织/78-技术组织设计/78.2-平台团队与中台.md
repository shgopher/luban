# 78.2 平台团队与中台

## 一句话

> 平台是**产品**，不是项目——判据是有没有内部用户、SLA、自助入口与采用率；中台失败的根本原因不是技术，是“为共享而共享”，把业务差异硬塞进一个中间层。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 平台 = 把运维工具打包 | 平台的用户是**开发**，交付物是“自助 + SLA + 文档”，不是一堆工具 |
| 中台 = 更高级的平台 | 中台是**共享范围**的描述，不是团队类型；共享错了就是灾难 |
| 平台要靠“强制接入”推广 | 强制只能带来“形式接入”，采用率与体验才是真的 |

## 平台 vs 项目 vs 中台

| 维度 | 项目 | 平台 | 中台 |
|---|---|---|---|
| 用户 | 甲方/业务方 | **内部开发者** | 多条业务线 |
| 交付物 | 一次交付、验收即结束 | 持续演进的产品 + SLA | 共享能力 + 接入规范 |
| 成功判据 | 按时验收 | **采用率 + 自助率 + 满意度** | 业务线复用带来的边际成本下降 |
| 失败形态 | 延期 | 没人用（成本中心） | 为共享而共享，业务差异被强塞 |

> 🔑 平台的第一个用户是**自己公司的开发**；没有内部用户的“平台”，本质是一个没有客户的项目。

## 平台必须交付的四样东西

| 交付物 | 判据 | 没有会怎样 |
|---|---|---|
| **SLA** | 可用性、延迟、支持时间写清楚 | 业务不敢依赖，绕过自建 |
| **自助入口** | 一条命令/一个页面完成接入 | 每次接入都提工单，平台变成瓶颈 |
| **文档与示例** | 30 分钟内跑通第一个例子 | 学习成本转嫁给业务，采用率上不去 |
| **路线图** | 用户能提需求、知道优先级 | 平台闭门造车，做出来的没人用 |

## 采用率：平台的唯一硬指标

```go
// 平台采用率 = 已接入服务 / (全部服务 − 明确豁免)
rate := 100 * float64(on) / float64(total-exempt)
if rate < 70 {
	fmt.Println("结论：平台不是默认路径——先修 DX（文档/自助/错误信息），再谈强制")
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
服务=6 已接入=3 豁免=1 采用率=60%
结论：平台不是默认路径——先修 DX（文档/自助/错误信息），再谈强制
```

完整代码在仓库 [tools/examples/78.2-adoption/](../../../tools/examples/78.2-adoption/README.md)，`go run .` 可复现这段输出。

读法：

- **豁免要有理由与期限**，否则豁免会变成“永久不接入”的通道；
- 采用率低于 70% 时，先修 **DX（开发者体验）**：文档、自助、错误信息、接入耗时；
- 高于 90% 且稳定后，才值得设“准入门槛”（比如新服务必须走平台）。

## 中台为什么会失败

| 失败原因 | 表现 | 根因 |
|---|---|---|
| **为共享而共享** | 把不同业务线的差异抽象成一个“通用能力” | 共享的前提是**共性足够大**，不是“组织上想共享” |
| 边界画错 | 中台管到业务逻辑，业务线无法差异化 | 中台应停在“能力”，不进入“策略” |
| 组织没配套 | 中台没有定价、没有 SLA、没有退出机制 | 业务线用脚投票，绕过去 |
| 考核错位 | 中台考核“接入数量”，不考核“业务效果” | 数字好看，业务变慢 |

> 🔑 判断一个中台该不该存在，只问一句：**去掉它，两条业务线会重复造多少东西？** 如果答案是“几乎不重复”，它就不该叫中台，最多是一个共享库。

## 平台团队的自助率与 ROI

采用率回答“接没接”，自助率回答“接完还要不要人”。两者可以背离：采用率 90%、自助率 10% 的平台，每接入一个服务就多一条长期工单，平台团队随业务一起线性膨胀——**采用率越高，成本中心越大**。所以平台该不该建，不看功能做了多少，要算两道账：自助率过不过回本线，回本线由工单量与单次人工成本决定。

先把自助率的口径钉死，否则下面所有数字都会被“口径”玩坏：

```
自助率 = 无平台人员介入、10 分钟内完成的操作次数 ÷ 全部操作次数
```

分母是**操作次数**，不是服务数，也不是页面访问量；分子要满足“全程没有平台同事介入”，发消息问一句“这个参数怎么填”就不算。工单量的口径则相反，要把 IM 求助、审批、临时开权限都算进去——口径一旦偏向“少算工单”，自助率立刻好看，ROI 立刻转正，但业务方的等待时间不会骗人。

三种模式的账（月操作 2,000 次、单次人工 1.5h、平台建设 6 人）：

| 模式 | 自助率 | 月工单量 | 平台人力（建设+服务） | 净节省 h/月 | 结论 |
|---|---|---|---|---|---|
| 工单制 | 10% | 1,800 | 17.2 人 | −660 | 采用率越高越亏，平台=服务台 |
| 半自助 | 60% | 800 | 11.0 人 | +840 | 值得建，但服务人力随工单涨 |
| 全自助 | 90% | 200 | 7.2 人 | +1,740 | 值得建，人力近似固定 |

注意“平台人力”这一列的结构：工单制的 17.2 人 = 6 人建设 + 11.2 人服务；全自助的 7.2 人 = 6 人建设 + 1.2 人服务。**平台团队人数本身不是指标，建设与服务的比例才是**：服务人力占比超过一半，说明平台还没成为产品，只是把业务方的手工活搬进了平台团队。

回本公式只有一行：

```
回本自助率 = 平台建设工时 ÷ (月操作次数 × 单次人工工时)
```

代入本机算：`960 ÷ (2000 × 1.5) = 32.0%`。自助率 32% 时净节省为 0；60% 时每月省 840h；90% 时省 1,740h。**低于 32% 的平台不是平台，是把业务方的工单搬进了平台团队**——采用率越高，亏得越多。

```go
package main

// 78.2 平台团队的自助率与 ROI：把"平台值不值得建"落成一道算术题。
// 模型参数（本机计算，假设值）：
//   月操作 2000 次（接入 / 配置变更 / 发布 / 配额申请）
//   每次操作人工 1.5h（业务方手工，含排队与沟通）
//   平台处理一张工单 1.0h，业务方等待 0.5h（两者合计仍是 1.5h）
//   平台建设固定投入 6 人 × 160h/月 = 960h/月
// 结论形式：自助率要到多少，平台才回本。

import "fmt"

const (
	opsPerMonth  = 2000.0 // 每月操作次数
	manualHours  = 1.5    // 每次操作的人工工时（业务方手工）
	serviceHours = 1.0    // 平台处理一张工单的工时
	waitHours    = 0.5    // 业务方等工单/沟通的工时
	buildFTE     = 6.0    // 平台建设固定人力
	hoursPerFTE  = 160.0  // 每人每月工时
)

var buildHours = buildFTE * hoursPerFTE // 960h/月

// platformHours 平台侧工时 = 建设固定投入 + 非自助工单的服务工时
func platformHours(selfRate float64) float64 {
	return buildHours + opsPerMonth*(1-selfRate)*serviceHours
}

// orgHours 建平台后组织总工时 = 平台侧 + 业务方等待
func orgHours(selfRate float64) float64 {
	return platformHours(selfRate) + opsPerMonth*(1-selfRate)*waitHours
}

// saved 净节省工时 = 不建平台（全手工）− 建平台后的总工时
func saved(selfRate float64) float64 {
	return opsPerMonth*manualHours - orgHours(selfRate)
}

func main() {
	fmt.Printf("参数：月操作 %.0f 次，单次人工 %.1fh，平台处理每单 %.1fh，等待 %.1fh，建设 %.0f 人\n\n",
		opsPerMonth, manualHours, serviceHours, waitHours, buildFTE)
	fmt.Printf("不建平台（全手工）月工时 = %.0f × %.1f = %.0f h\n\n",
		opsPerMonth, manualHours, opsPerMonth*manualHours)
	fmt.Printf("%-8s %-8s %-9s %-16s %-14s %s\n",
		"模式", "自助率", "月工单量", "平台人力(建设+服务)", "净节省h/月", "节省/投入")
	fmt.Println("----------------------------------------------------------------------------------")
	modes := []struct {
		name string
		rate float64
	}{
		{"工单制", 0.10},
		{"半自助", 0.60},
		{"全自助", 0.90},
	}
	for _, m := range modes {
		tickets := opsPerMonth * (1 - m.rate)
		staff := platformHours(m.rate) / hoursPerFTE
		sv := saved(m.rate)
		roi := sv / platformHours(m.rate)
		fmt.Printf("%-8s %-8s %-9.0f %-16.1f %-14.0f %+.2f\n",
			m.name, fmt.Sprintf("%.0f%%", m.rate*100), tickets, staff, sv, roi)
	}

	// 回本点：净节省 = 0 → selfRate = buildHours / (ops × manualHours)
	breakeven := buildHours / (opsPerMonth * manualHours)
	fmt.Printf("\n回本自助率 = 平台建设工时 ÷ 全手工总工时 = %.0f ÷ %.0f = %.1f%%\n",
		buildHours, opsPerMonth*manualHours, breakeven*100)
	fmt.Printf("自助率 32%% 时净节省 %.0f h/月（正好回本）；60%% 时 %.0f h/月；90%% 时 %.0f h/月\n",
		saved(0.32), saved(0.60), saved(0.90))

	// 敏感度一：操作量 × 单次人工耗时 决定的回本自助率
	fmt.Printf("\n回本所需自助率（行=月操作次数，列=单次人工工时）：\n")
	fmt.Printf("%-12s %-10s %-10s %s\n", "操作/月", "1.0h", "1.5h", "2.0h")
	for _, ops := range []float64{500, 1000, 2000, 4000} {
		fmt.Printf("%-12.0f", ops)
		for _, a := range []float64{1.0, 1.5, 2.0} {
			r := buildHours / (ops * a)
			if r > 1 {
				fmt.Printf(" %-9s", ">100%")
			} else {
				fmt.Printf(" %-9s", fmt.Sprintf("%.0f%%", r*100))
			}
		}
		fmt.Println()
	}

	// 敏感度二：建设投入变化
	fmt.Printf("\n建设投入(人) → 回本自助率：")
	for _, fte := range []float64{2, 4, 6, 9, 12} {
		r := fte * hoursPerFTE / (opsPerMonth * manualHours)
		fmt.Printf("  %.0f人=%.1f%%", fte, r*100)
	}
	fmt.Println()

	// 折算成钱：全成本按 200 元/h 计（月薪 3.2 万 ÷ 160h）
	const hourlyCost = 200.0
	fmt.Printf("\n按 %.0f 元/h 折算：全手工月成本 %.0f 万元；全自助净省 %.0f h ≈ %.1f 万元/月\n",
		hourlyCost, opsPerMonth*manualHours*hourlyCost/1e4,
		saved(0.90), saved(0.90)*hourlyCost/1e4)

	// 临界操作量：给定目标自助率，需要多少月操作才能回本
	fmt.Printf("\n若自助率能做到 70%%，回本所需月操作量 = %.0f 次（当前 %.0f 次）\n",
		buildHours/(0.70*manualHours), opsPerMonth)
}
```

本机计算输出（`go1.27.1 darwin/arm64`，原始输出见同目录 raw.txt）：

```text

全自助      90%      200       7.2              1740           +1.50
```

完整代码在仓库 [tools/examples/78.2-platform-roi/](../../../tools/examples/78.2-platform-roi/README.md)，`go run .` 可复现这张表；模型参数都是文件顶部的常数，改一下就能重算自己的账。

折算成钱更直观：按全成本 200 元/h（月薪 3.2 万 ÷ 160h）计，不建平台每月人工成本 60 万元；全自助模式每月净省 1,740h ≈ 34.8 万元。这里有一条反直觉结论：**回本自助率与人力单价无关**——单价只决定“省多少钱”，不决定“过不过线”，因为公式两边都乘了同一个单价。所以“我们人力便宜，平台不划算”通常是错的，真正让平台不划算的是操作量太少或单次人工太低。

两条敏感度：

| 月操作次数 | 单次 1.0h | 单次 1.5h | 单次 2.0h |
|---|---|---|---|
| 500 | >100% | >100% | 96% |
| 1,000 | 96% | 64% | 48% |
| 2,000 | 48% | 32% | 24% |
| 4,000 | 24% | 16% | 12% |

建设投入 2 / 4 / 6 / 9 / 12 人，对应回本自助率 10.7% / 21.3% / 32.0% / 48.0% / 64.0%。若自助率能做到 70%，回本只需要 914 次操作/月。

读法：

- **自助率是一阶项，采用率是二阶项**：自助率从 10% 提到 60%，净节省从 −660h 变成 +840h；采用率从 60% 提到 90% 而自助率不动，净节省不变——采用率只决定“有没有人用”，自助率决定“用了之后省不省人力”。
- **建设投入决定回本线，不决定 ROI 上限**：6 人建设要 32% 自助率回本，12 人建设要 64%；后者几乎要求平台覆盖全部主路径，任何一条路径漏成工单就把 ROI 打回负值。所以平台要小步建：先用 2–4 人把一条主路径做到自助，回本后再扩。
- **自助率有上限，别拿 100% 当目标**：例外审批、安全事件、跨系统迁移这类操作天然需要人，把它们压到 10% 以下就够；把 100% 当目标，自助入口会被迫做得极复杂，反而把自助率做回去。
- **净节省为负时，推广采用率是加速亏损**：工单制 10% 自助率、每月亏 660h；把采用率强行推到 100%，工单量会随接入量继续涨，这就是“平台变瓶颈”的算术形态（[77.2 四种团队类型](../77-康威定律与团队拓扑/77.2-四种团队类型.md) 里“服务数 > 5 要按能力域拆分”说的是同一件事）。

**别用自助率单独考核平台团队。** 单一指标一定会被优化：把口径算松、把工单推回业务方、把“自助”定义成“点开页面就算”，都能让自助率好看，而业务方的等待时间不变。可行的组合是三条一起看：自助率（这次有没有人帮）、接入耗时（从提出到跑通多久）、工单满意度（被迫走工单的人怎么评价）。三条同向变好，才说明平台真的在变产品；只有自助率涨，多半是把分母做小了。

**从工单制走到全自助，路径是可拆的**：第一步自动化 Top 3 工单类型（通常占工单量 60–80%），自助率能到 50% 上下，刚好过 32% 的回本线；第二步把操作模板化、参数配置化，把“接入”变成“填表 + 一键”，自助率到 70–80%；第三步把策略写成代码（配额、审批、发布策略），自助率到 90% 以上。每一步的判据都是同一个式子，不需要重新发明指标。

**什么条件下平台团队值得建：**

| 条件 | 判据 | 不满足时的替代 |
|---|---|---|
| 重复操作足够多 | 月操作 ≥ 1,000 次，且 ≥ 70% 是同构操作 | 写脚本 + 文档，别建团队 |
| 自助率能过回本线 | 按上式计算，再留 20% 余量 | 先做一条主路径，2–4 人试半年 |
| 主路径可标准化 | 同一件事只有一种做法 | 先做流程治理，再谈平台 |
| 有产品能力 | 专职产品/文档/自助入口，不是运维兼职 | 用商业 IDP 或托管服务 |
| 建设人力可控 | 2–6 人能覆盖 70% 的操作 | 超过 12 人建设仍回不了本，说明共享范围不成立 |

> 🔑 平台值得建的判据不是“共享能省多少”，而是**自助率过不过回本线**：回本自助率 = 建设工时 ÷ 全手工工时。过线，平台是杠杆；不过线，平台只是把分散的工单集中成一个更大的成本中心。

## 反模式

| 反模式 | 后果 |
|---|---|
| 平台没有 SLA | 业务不敢依赖，自建替代 |
| 接入要提工单排队 | 平台成为交付瓶颈，采用率下滑 |
| 用“强制接入”代替体验改进 | 形式接入，实际绕开（在平台外写脚本） |
| 中台把业务策略也收上来 | 业务线失去差异化能力，创新停滞 |
| 平台团队按“功能数量”考核 | 做了一堆没人用的功能 |
| 平台与业务共用同一套排期 | 平台需求永远排在业务之后，越拖越烂 |
| 没有豁免与退出机制 | 遗留系统被永久卡住，采用率永远上不去 |

## 自检

**Q1** 怎么判断一个“平台团队”是真平台还是伪平台？

▸ 答案：看三件事：**有没有内部用户名单**（谁在用）、**有没有 SLA**（敢不敢依赖）、**接入是不是自助**（要不要提工单）。三样缺一样，它就更像一个运维项目：用户是被指派的，故障没有承诺，接入靠人。

**Q2** 采用率 60% 时，为什么不该先“强制接入”？

▸ 答案：因为低采用率通常是**体验问题**（文档缺失、接入要两周、错误信息看不懂），强制只会让团队“形式接入、实际绕过”——在平台外写脚本、把服务注册进去但不用它的能力。正确顺序是先修 DX，把采用率做到 70% 以上，再设门槛。

**Q3** 中台与平台的核心区别是什么？

▸ 答案：**共享范围与服务对象**。平台服务的是“内部开发者”，目标是让交付更快；中台服务的是“多条业务线”，目标是让共性能力只造一次。区别不在技术，而在“共享的边界是否成立”——共性不够大时，中台就是强行把差异塞进一个中间层。

**Q4** 中台该管到哪一层为止？

▸ 答案：管到**能力**，不管**策略**。比如“支付能力”（下单、退款、对账）可以做中台；“这款商品该不该打折”是业务策略，必须留在业务线。越过这条线，业务线就失去差异化能力，中台也会被业务变化拖着频繁改。

**Q5** 平台团队该怎么被考核？

▸ 答案：考核**采用率、自助率、接入耗时、满意度**，而不是功能数量。功能数量会诱导团队做“看起来厉害但没人用”的东西；采用率与接入耗时直接反映“平台有没有让业务更快”，也逼团队去修文档与自助。
