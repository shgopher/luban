# 78.4 跨团队协作与接口人

## 一句话

> 跨团队协作的成本不在“沟通”，在**交接**——每交接一次就丢一次上下文；接口人的作用不是传话，而是**持有契约**：谁改、谁验收、出问题找谁。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 接口人 = 传话筒 | 传话筒会把信息衰减成“转述”；接口人要能**对契约拍板** |
| 多开会就能对齐 | 会越多，决策越分散；对齐靠契约，不靠会议数量 |
| 有文档就能异步协作 | 文档会腐烂；能自动验证的契约才靠得住 |

## 三种协作模式，按成本排序

| 模式 | 做法 | 成本 | 什么时候用 |
|---|---|---|---|
| **同步协作** | 两个团队一起干一段时间 | 最高（会议 + 互相等待） | 新边界探索、复杂特性 |
| **异步契约** | 一方提供接口/文档/SLA，另一方自助接入 | 中 | 稳定的能力复用 |
| **接口人** | 每个团队指定一人持有契约、处理变更与仲裁 | 低 | 多团队、频繁变更 |

> 🔑 顺序是：能异步就不协作，能自助就不找接口人。**接口人是异步契约的兜底，不是默认通道。**

## 接口人到底持有什么

| 职责 | 具体内容 | 不做的后果 |
|---|---|---|
| **契约 owner** | 接口/IDL 的变更由他确认，字段只加不删 | 消费方各自改，联调时全对不上 |
| **变更评审** | 破坏性变更要走版本与迁移计划 | 悄悄改字段，消费方线上报错 |
| **验收** | 消费方接入后由他确认“按契约工作” | 接了但用错，出问题互相推 |
| **升级路径** | 争议升级到谁、多久内答复 | 争议卡在中间层，项目停摆 |
| **台账** | 谁在用、用在什么场景、什么版本 | 下线时不知道谁在用 |

## 契约要写成能验证的东西

许式伟对“共识”的要求是**精确、无歧义**；接口用代码表达，是唯一能被机器验证的共识。跨团队契约最小可以写成这样：

```yaml
# contracts/order-to-payment.yaml
provider: order-team          # 谁提供
consumer: payment-team        # 谁消费
interface: POST /v1/payments  # 接口
sla:
  latency_p99_ms: 200
  availability: 99.95
errors:                       # 错误码也是契约
  - code: PAYMENT_DUPLICATED
    meaning: 幂等键重复，消费方可安全重试
  - code: PAYMENT_LIMIT_EXCEEDED
    meaning: 超限，不可重试
versioning: additive-only     # 只加不删；破坏性变更需新版本
owner: 张三（order-team）      # 接口人
```

这份契约同时解决了三件事：**字段与语义**（不会联调才发现对不上）、**错误码与重试语义**（消费方知道什么能重试）、**责任人**（出问题找谁）。

## 交接次数：先把成本数出来

跨团队协作的代价可以近似成“交接次数”。沿着调用链数一数：

| 链长 | 一次改动要协调的团队 | 典型现象 |
|---|---|---|
| 1–2 跳 | 1–2 个 | 一个 PR 搞定 |
| 3 跳 | 3 个 | 上线前要三方对齐 |
| **4 跳以上** | 4+ 个 | 每次发布都要开会，故障定位靠群聊 |

链长的算法与判据见 [77.3 团队边界与架构边界的对齐](../77-康威定律与团队拓扑/77.3-团队边界与架构边界的对齐.md)（本机实测：4 跳链意味着四个团队要协同发布）。**接口人能降低单次交接的成本，但降不了交接次数**——次数要靠边界重画解决。

## 接口人机制的失效模式与替代

**接口人不是“设了就好”**：它把跨团队的等待从“找人”换成“排队”，一旦排队时间超过协调省下的时间，接口人本身就是新瓶颈。用排队模型算（本机仿真：每天 1.2 件跨团队请求、每个接口人每天处理 1.6 件、单件基础处理 0.15 天、跨接口人协调 1 天）：**一个过载的单接口人平均响应 2.02 天，比不设接口人、直接对接的 1.75 天还慢 0.27 天**。所以问题不是“要不要设接口人”，而是四种替代方案各花多少钱、什么条件下该取消。

### 六种失效模式

| 失效模式 | 触发条件 | 量化特征（本机仿真 / 判据） | 替代或修法 |
|---|---|---|---|
| **单点过载** | 只有 1 个接口人，且利用率 ρ = R/H > 0.7 | ρ=0.75 时响应 2.02 天，比直接对接的 1.75 天还慢 | 至少双人轮值；或先把请求量降下来 |
| **传话筒化** | 接口人没有变更否决权、验收权 | 每次变更多一跳，延迟 +0.5–1 天；破坏性变更没人拦 | 明确三项权力；不给权力就换人 |
| **多人碎片化** | N ≥ 4，且按团队而不是按业务域划分 | 跨接口人协调概率 (N−1)/N ≥ 75%，协调成本吃掉排队收益 | 一个业务域一个接口人，不按团队数配人 |
| **文档替代幻觉** | 只统计“文档写了”，不统计“按文档接成” | 自助率 0.6→0.2 时，响应 0.20→0.88 天，成本 0.97→2.61 人天/天 | 契约进 CI；文档只解释“为什么” |
| **审批岗化** | 所有变更都要接口人签字 | 接口人成为发布关键路径，产能 = 1 人 | 只审破坏性变更，其余自动放行 |
| **台账腐烂** | 消费方名单靠人工维护 | 下线时才发现还有 3 个团队在调旧版本 | 从网关/服务网格日志自动采集调用关系 |

### 四种替代方案，用同一把尺子量

基线参数：R=1.2 件/天，H=1.6 件/天，B=0.15 天，C=1 天，文档自助吸收 60%，提供方留 10% 工时接受直接咨询，找错人 0.25 天；等待成本 e=2 人天/天（一件请求多等一天，消费方折算损失 2 人天）。成本口径统一为「接口人 FTE + R×T×e」，单位人天/天。

| 模式 | 响应延迟（天） | 单点风险 | 成本（人天/天） |
|---|---|---|---|
| 单接口人 | 2.02 | 高：请假、离职即断线 | 5.26（0.4 FTE + 等待） |
| 双接口人 | 1.02 | 中：互为备份，但契约可能碎片化 | 3.26（0.8 FTE + 等待） |
| 接口人+文档 | 0.20 | 中：人可替代，文档会腐烂 | 0.97（0.5 FTE + 等待） |
| 直接对接 | 1.75 | 低（无人可断）但契约无 owner | 4.20（0 FTE + 等待） |

三处反直觉：

1. **单接口人是四种里最差的**：响应比直接对接慢 0.27 天，成本还高 25%。一个人扛 1.2 件/天、ρ=0.75，排队等待已经超过他省下的协调时间。
2. **加第二个人把响应砍半（2.02→1.02 天），成本只降到 3.26 人天/天**：边际收益大，边际成本也不小；再加到 N=3，响应持平（1.02 天），成本涨到 3.66。
3. **最省的是文档自助（0.97 人天/天）**，代价是它假设 60% 的请求真能自助；自助率掉到 20%，成本翻到 2.61 人天/天，见失效模式第四行。

双接口人怎么切，也决定它是不是真备份：**主备轮值**（一人持契约、一人备份）能扛请假，但契约认知仍是单点；**按域分工**（各持一个业务域）能并行处理，代价是跨域请求回到协调成本 C。两种切法都要求两人能互相验收对方的契约，否则备份只是名单上的备份。

### 响应时间 vs 接口人数量：模型与可复算代码

把每个接口人看成一个单服务台，模型只有五个式子：

- 到达率 λ = R/N，服务率 μ = H，利用率 ρ = λ/μ；
- 平均排队等待 W = ρ/(μ−λ)（M/M/1）；
- 两方请求落在不同接口人手里的概率 p_cross = (N−1)/N；
- 响应 T = B + W + p_cross·C；
- 直接对接：T = B/s + L（提供方只留 s 比例工时，单件总等待按服务率折算成 B/s）。

```go
// 接口人数量 n 与平均响应时间（天）：排队 + 跨接口人协调
func ifaceDelay(m model, n int, req float64) (float64, float64, bool) {
	lambda := req / float64(n)
	rho := lambda / m.H
	if rho >= 1 { // 到达率超过服务能力：队列无界，无有限解
		return math.Inf(1), rho, false
	}
	wait := rho / (m.H - lambda)        // M/M/1 平均排队等待（天）
	pCross := float64(n-1) / float64(n) // 两方请求落在不同接口人手里的概率
	t := m.B + wait + pCross*m.C
	return t, rho, true
}
```

三组负载下逐 N 扫描（真实输出，本机 `go1.27.1 darwin/arm64`，Apple M1；原始输出见 `.cache/pilot2-75.4/raw.txt`）：

```text
[负载 R=0.30 件/天] N=1:0.29 N=2:0.71 N=3:0.86 N=4:0.93 N=5:0.97 N=6:1.00 N=7:1.02 N=8:1.04 
  → 延迟最优 N=1（0.29天）；成本最优 N*=1 T=0.29天 ρ=0.19 成本=0.58人天/天
  → 文档自助模式：接口人 N=1，T=0.11天，成本=0.57人天/天
  → 直接对接：T=1.75天，成本=1.05人天/天

[负载 R=1.20 件/天] N=1:2.02 N=2:1.02 N=3:1.02 N=4:1.04 N=5:1.06 N=6:1.07 N=7:1.08 N=8:1.09 
  → 延迟最优 N=2（1.02天）；成本最优 N*=2 T=1.02天 ρ=0.37 成本=3.26人天/天
  → 文档自助模式：接口人 N=1，T=0.20天，成本=0.97人天/天
  → 直接对接：T=1.75天，成本=4.20人天/天

[负载 R=3.60 件/天] N=1:不可行 N=2:不可行 N=3:2.69 N=4:1.70 N=5:1.46 N=6:1.36 N=7:1.30 N=8:1.27 
  → 延迟最优 N=8（1.27天）；成本最优 N*=6 T=1.36天 ρ=0.37 成本=12.18人天/天
  → 文档自助模式：接口人 N=2，T=0.49天，成本=4.46人天/天
  → 直接对接：T=1.75天，成本=12.60人天/天
```

| 负载 | R（件/天） | 成本最优 N | 该 N 响应 | 文档自助模式 | 结论 |
|---|---|---|---|---|---|
| 低 | 0.30 | 1 | 0.29 天 | N=1，0.11 天 | 请求太稀，加人反被协调成本拖慢（N=2 升到 0.71 天） |
| 中 | 1.20 | 2 | 1.02 天 | N=1，0.20 天 | 单接口人 2.02 天，已经比直接对接慢 |
| 高 | 3.60 | 6 | 1.36 天 | N=2，0.49 天 | 6 人已是成本最优；加到 8 人只降到 1.27 天，成本反升 |

高负载那一行最值得看：从 6 人加到 8 人，响应只从 1.36 天再降 0.09 天，成本最优人数仍停在 6；同样的请求量，文档自助只需要 2 个接口人、0.49 天。**接口人的数量问题，多数时候是请求数量的问题**——减少请求靠契约收口、文档自助和边界重画，不靠加人。

模型本身有边界：M/M/1 假设请求按泊松到达、服务时间近似指数分布，真实变更请求是成簇来的（发版周集中爆发），实际等待会比算出来的更长；参数取值也是本机假设，换团队必须重算。它的价值不在绝对值，而在**同口径比较四种替代方案**和**看趋势**：排队项随 ρ 非线性上涨、协调项随 N 线性上涨，两者的剪刀差决定了最优人数。

### 什么时候该取消接口人

模型真正的用处是找临界点：把 R 从 0.01 扫到 3.0 件/天，找「直接对接总成本最低」的上界。

| 等待成本 e | 取消阈值 R* | 折算 | 怎么读 |
|---|---|---|---|
| 0.5 人天/天/件 | 0.61 件/天 | 3.1 件/周 | 等一天基本不卡人：周请求 <3 件就直接对接 |
| 1.0 | 0.27 件/天 | 1.4 件/周 | 等一天卡住一个人：周请求 <1.4 件才取消 |
| 2.0 | 0.12 件/天 | 0.6 件/周 | 等一天卡住两个人：几乎不该取消，缺的是拆域 |

四条判据：

1. **请求频率低于回本点**（上表）→ 取消专职接口人，交接给提供方 owner 兼契约 owner，外加每月一次对齐；争议仍走 [78.3 技术委员会与决策机制](78.3-技术委员会与决策机制.md) 的仲裁路径。注意是“取消专职”，不是“取消契约”。
2. **自助率 ≥0.8 且契约能自动验证**（字段、错误码有 contract test）→ 降级为 on-call，不设专职。反例是文档写了但接不成：自助率 0.6 时成本 0.97 人天/天，掉到 0.2 就涨到 2.61——文档腐烂比接口人缺席更贵。
3. **只有 1 个接口人且 ρ>0.7** → 不是取消，是“别只设一个”：2.02 天比直接对接的 1.75 天还慢，单点风险和响应时间双输。
4. **R ≥3 件/天** → 取消等于把队列搬回提供方：直接对接成本 12.60 人天/天，提供方 10% 的咨询窗口撑不住；正解是减少请求数或拆域，见 [77.3 团队边界与架构边界的对齐](../77-康威定律与团队拓扑/77.3-团队边界与架构边界的对齐.md)。

> 🔑 接口人只在“请求多到一个专职划算、团队少到一个人持得住”的窄区间里成立：每个接口人每天 0.3–1.0 件请求（每周 1.5–5 件）、服务 2–3 个团队。低于下界取消，高于上界拆域或重画边界；自助率跨过 0.8 则降级为 on-call——**取消的是岗位，不是契约**。

## 反模式

| 反模式 | 后果 |
|---|---|
| 接口人由不参与技术决策的人担任 | 只会传话，契约变更照样失控 |
| 接口人同时是 5 个团队的接口人 | 变成瓶颈，响应时间以天计 |
| 契约没有错误码与重试语义 | 消费方猜着重试，重复扣款 |
| 契约变更只发通知不评审 | 破坏性变更悄悄上线 |
| 用“协作”代替边界重画 | 两个团队长期耦合，等于没拆 |
| 只维护消费方名单，不维护版本 | 下线时才发现还有人用旧版本 |
| 争议没有升级路径 | 卡在接口人之间，项目停摆 |

## 自检

**Q1** 接口人最重要的职责是什么？为什么不是“传话”？

▸ 答案：**持有契约并对契约拍板**：确认变更、评审破坏性变更、验收接入、维护台账。传话只传递信息，不承担决策；而跨团队协作的失败大多不是“没听到”，是“听到后各自理解”。接口人要能把分歧收敛成一个可执行的契约。

**Q2** 什么时候该用接口人，什么时候该直接重画边界？

▸ 答案：接口人降低的是**单次交接成本**（沟通、评审、验收），适合“边界合理但变更频繁”的情况；如果交接**次数**本身就多（链长 4 跳、一个需求跨 3 个团队），接口人只会让每次交接更规范，却不会让交付更快——这时该重画边界，把一条业务流收进一个团队。

**Q3** 为什么契约里必须写错误码与重试语义？

▸ 答案：因为跨团队调用失败是常态，而“能不能重试”决定了消费方是重试、降级还是报错。没有错误码语义，消费方只能猜：猜“超时”可重试，可能重复扣款；猜“超限”不可重试，可能丢单。错误码是契约的一部分（[40.6 错误处理](../../L3-质量属性/40-可维护性/40.6-错误处理.md) 讲过同一原则）。

**Q4** 为什么说“有文档就能异步协作”不完全对？

▸ 答案：文档会腐烂，且无法被自动验证；跨团队契约需要**能被 CI 校验**的东西（OpenAPI、protobuf、contract test）。文档适合解释“为什么”，契约适合约束“必须怎样”——两者分工，不能互相替代。

**Q5** 接口人制度最容易退化成什么？

▸ 答案：退化成**传话筒 + 审批岗**：所有跨团队沟通都必须经过他，他不在就卡住；他不拍板只转达，问题在两边来回。避免方式是明确他的三项权力（变更否决、验收、升级），并限制他同时负责的团队数——超过 2–3 个，就应该拆成多个接口人或重画边界。
