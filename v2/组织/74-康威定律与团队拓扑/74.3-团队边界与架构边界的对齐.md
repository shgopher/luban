# 74.3 团队边界与架构边界的对齐

## 一句话

> 边界对齐只有一个判据——**一次改动的“接触面”是否落在同一个团队**；接触面有三样：代码所有权、接口契约、值班与 SLO。对齐不是让组织图和架构图长得像，而是让这三样指向同一条线。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 组织图与架构图长得像就叫对齐 | 图可以画得像，**所有权、契约、值班**没对齐就还是错位 |
| 对齐一次，管三年 | 业务在变，边界会漂移；对齐是**周期性动作**，不是一次性项目 |
| 边界越细越清晰 | 每加一条边界就多一次交接，交接成本会吃掉清晰带来的收益 |

## 三个接触面：对齐就是让它们同向

| 接触面 | 对齐的标志 | 错位的症状 |
|---|---|---|
| **代码所有权** | 一个仓库/目录只有一个团队有写权限；改动不需要别的团队 review | 一个 PR 要三个团队 approve |
| **接口契约** | 契约的 owner 是**提供方**，变更走版本与评审 | 消费方私自改契约、或提供方悄悄改字段 |
| **值班与 SLO** | 谁的服务谁值班，SLO 按服务归属定 | 报警发到“大群”，没人认领 |

> 🔑 判据一句话：**一次需求改动，要几个团队签字？** 超过 2 个，说明边界把一条业务流切碎了。

## 对齐的顺序：先架构，后组织

逆康威的落地顺序不能反（[74.1 康威定律及其逆定律](74.1-康威定律及其逆定律.md)）：

```
① 目标架构（边界画在哪）
      ↓
② 团队边界（谁拥有哪块）
      ↓
③ 依赖方向（谁调谁、谁不能调谁）
      ↓
④ 所有权（代码、发布、值班、SLO）
      ↓
⑤ 平台能力（公共部分收归平台）
```

只做 ② 不做 ④，团队只是换了名字；只做 ③ 不做 ⑤，每个团队都要自己造一遍基础设施。

亚马逊 2002 年的做法就是把这套顺序写成了硬要求：**团队间只能通过 Service Interface 通信，不能读对方数据库、不能链接对方程序**（详见 [30.1 微服务的定义与前提](../../L2-架构风格/30-微服务/30.1-微服务的定义与前提.md)）。它把“依赖方向”和“接口契约”同时钉死了。

## 交接链：把“跨团队”变成可数的长度

一条链路每跨一次团队，就多一次交接；交接链越长，一次改动的协调成本越高。用依赖图算一下最长链：

```go
// 沿服务依赖图找最长链；链上每一跳都可能是一次跨团队交接。
walk = func(node string, depth int, chain string) {
	if depth > best {
		best = depth
	}
	if depth > 6 { // 防环
		return
	}
	for _, e := range byFrom[node] {
		walk(e.to, depth+1, chain+" -> "+e.to)
	}
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
最长调用链长度=4 跳（每跳都可能跨团队）
经验判据：链长 > 4 跳，或跨 3 个以上团队，一次改动就要开会协调
```

链长 4 跳意味着：一个下单请求要经过 web → order → payment → risk → user 四个团队。**任何一个团队的发布，都要求另外三个团队配合验证**——这就是“分布式单体”的组织版本。

## 接口是唯一精确的共识

许式伟在《团队的共识管理》里把这件事说得很透：

| 观点 | 含义 |
|---|---|
| **共识是团队协作的契约** | 契约表达越精确、越无歧义，协作中主观能动性越高 |
| **架构图不是好的共识表达** | 图不精确，联调时才发现“牛头不对马嘴” |
| **更精确的方式是定义模块接口，用代码表达** | 代码无歧义；架构图只是辅助说明接口之间的关系 |
| **规格高于实现** | 设计谈“做成什么样”，架构谈“怎么实现”；规格是最高共识 |

落到团队边界上就是一句：**跨团队的那条线，必须有一份用代码（或 IDL）写死的契约**。只靠会议纪要与架构图，等于把风险留到联调那天。

## 什么时候该重新对齐

| 信号 | 说明 |
|---|---|
| 一个需求固定要 3 个以上团队参与 | 业务流被切碎 |
| 两个团队 6 个月内互相提交代码 | 边界画错了，要么合并要么重画 |
| 契约变更总在消费方发现 | 所有权没定清楚 |
| 报警没有明确 owner | 值班与 SLO 没对齐 |
| 组织刚调整完 | 架构会在 6–12 个月后被拉向新形状，要主动校正 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 只改组织、不改所有权 | 团队改名，代码、发布、值班还在原团队手里 |
| 用“协调人”解决边界错位 | 协调人变成新的瓶颈，根因未动 |
| 契约由消费方维护 | 提供方随时改，消费方疲于适配 |
| 边界按人名/资历划 | 人一走边界就塌 |
| 一条业务流被切成四段 | 每次改动四次交接，速度与责任双输 |
| 对齐后不做周期性复检 | 半年后边界漂移，回到原点 |
| 用架构图当契约 | 联调时才发现字段、错误码、超时全对不上 |

## 自检

**Q1** 怎么用一句话判断两个团队的边界是否合理？

▸ 答案：问“一次典型的需求改动，要几个团队签字、几次交接”。≤ 1 个团队 + 0 次交接最好；2 个团队是上限；3 个以上说明**一条业务流被切碎了**，该重画边界，而不是加协调人。

**Q2** 为什么架构图不能替代接口契约？

▸ 答案：因为架构图**不精确**：它画得出“订单调支付”，画不出字段类型、错误码、超时、幂等语义。联调时对不上的恰恰是这些细节；而接口用代码/IDL 表达是无歧义的，能被编译器和测试验证。许式伟的说法是“规格高于实现”，接口就是规格。

**Q3** 组织调整之后，为什么还要“主动校正”架构？

▸ 答案：因为康威定律是**被动**的：组织变了，架构会在半年到一年里被沟通结构慢慢拉成新形状——但这个形状是“沟通方便的形状”，不一定是你想要的形状。主动校正就是逆康威：先画目标架构，再确认新组织的边界与所有权是否指向它。

**Q4** 交接链 4 跳，最直接的后果是什么？

▸ 答案：**任何一次发布都变成多方协同**：一个团队改代码，另外三个团队要配合验证与回归；出故障时，责任在四个团队之间流转。它的直接症状是“发布越来越慢、故障越来越难定位”，而根因不在技术，在边界。

**Q5** 代码所有权对齐了，但值班没对齐，会怎样？

▸ 答案：出事时没人认领。代码 owner 只对“改代码”负责，值班与 SLO 才决定“半夜谁起来”；两者分开，报警会发到大群，最后变成“谁看见谁处理”。对齐的完整定义是三样（所有权、契约、值班）同向，缺一不可。
