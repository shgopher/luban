# 74.2 四种团队类型（流对齐 / 平台 / 赋能 / 复杂子系统）

## 一句话

> 团队不该按“前端 / 后端 / 运维”分，而该按**它交付的那条业务流、或它提供的那类能力**分；四种类型（流对齐 / 平台 / 赋能 / 复杂子系统）配三种交互模式，判据只有一个：**这个团队的认知负荷由什么构成**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| “全功能团队” = 什么都会 | 全功能指**端到端交付**（需求到上线值班），不是“什么都自己造”；基础设施仍该由平台提供 |
| 平台团队 = 运维部改名 | 平台团队的产出是**产品**（SLA + 自助 + 文档），运维只是其中一部分 |
| 赋能团队 = 内部培训 | 赋能是**带人做一遍**、限时退出，不是讲课；讲完不走的赋能团队会变成第二个审批层 |

## 四种类型，各自解决一类负荷

| 类型 | 交付什么 | 典型 | 判据 | 什么时候不该用 |
|---|---|---|---|---|
| **流对齐团队** | 一条业务流的端到端（需求→上线→值班） | 订单团队、支付团队 | 有自己的用户、能独立发布、服务数 ≤ 3 | 业务流还没稳定、需求还在剧烈变化时，先别固化 |
| **平台团队** | 内部能力（计算、存储、发布、可观测） | 容器平台、CI 平台 | 有内部用户、有 SLA、能自助接入 | 只有 1–2 个用户时，做成“服务”就够，别建团队 |
| **赋能团队** | 帮流对齐团队补上某种能力 | 安全、性能、SRE 专家小组 | 有明确的时间盒与退出标准 | 变成常设“审批岗”时，立刻撤 |
| **复杂子系统团队** | 需要长期深耕的复杂部件 | 风控引擎、存储引擎、编译器 | 专长稀缺、变化慢、接口稳定 | 业务代码别用这个名义圈起来 |

四类之外没有“第五类”。**一个团队同时是四种类型，等于没有类型**——它一定会被最紧急的那类需求占满。

## 三种交互模式

| 模式 | 含义 | 适合 | 代价 |
|---|---|---|---|
| **协作（collaboration）** | 两个团队一起干一段时间 | 新边界探索期、复杂特性 | 沟通成本高，必须有期限 |
| **X-as-a-Service** | 一方提供、另一方自助消费 | 平台与流对齐团队 | 平台必须做到“自助 + SLA”，否则退化成工单 |
| **赋能（facilitating）** | 专家团队进场带一段，然后退出 | 能力补齐、新技术引入 | 必须定退出标准，否则赖着不走 |

> 🔑 交互模式是**临时的**，团队类型是**相对稳定的**。最常见的组织病，是把“协作”当常态：两个团队常年一起改一个模块，说明边界画错了，该合并或该重画。

## 用代码把分类跑一遍

下面这个小工具按“面向谁 + 交付什么 + 复杂度 + 服务数”给出建议（本机 `go1.27.1 darwin/arm64`）：

```go
func classify(t team) (string, string) {
	switch {
	case t.deep:
		return "复杂子系统团队", "按稀缺专长组队，接口按 X-as-a-Service 提供"
	case t.internal && t.services > 5:
		return "平台团队（先拆）", "服务数 > 5，按能力域拆分，否则平台自己变成瓶颈"
	case t.internal && !t.users:
		return "平台团队", "把内部能力做成产品：SLA + 文档 + 自助"
	case t.services <= 3:
		return "流对齐团队", "端到端拥有一个业务流，独立部署"
	default:
		return "赋能团队（或拆分）", "服务数 > 3，先按业务流拆，再谈赋能"
	}
}
```

```text
订单       → 流对齐团队            端到端拥有一个业务流，独立部署
支付网关     → 流对齐团队            端到端拥有一个业务流，独立部署
容器平台     → 平台团队             把内部能力做成产品：SLA + 文档 + 自助
风控引擎     → 复杂子系统团队          按稀缺专长组队，接口按 X-as-a-Service 提供
数据中台     → 平台团队（先拆）         服务数 > 5，按能力域拆分，否则平台自己变成瓶颈
```

注意最后一行：**“中台”不是一种团队类型**，它只是“平台团队 + 服务数过多”的状态。服务数超过一个团队能认知的量，平台就会从“加速器”变成“瓶颈”。

## 团队规模：5–9 人是经验上限

| 规模 | 沟通路径数 `n(n-1)/2` | 现象 |
|---|---|---|
| 3–5 人 | 3–10 | 不需要流程，喊一声就行 |
| 6–9 人 | 15–36 | 需要站会与看板，但还能共享上下文 |
| 10–15 人 | 45–105 | 开始出现“我不知道他们在干什么” |
| > 15 人 | > 105 | 实际已经分裂成几个团队，只是没改名 |

亚马逊的“两个披萨”团队（不超过 16 人）与 Team Topologies 的 5–9 人，说的是同一件事：**团队规模的上限由沟通路径决定，不由管理幅度决定**。

## 反模式

| 反模式 | 后果 |
|---|---|
| 按技术分层建团队（前端组/后端组/DBA 组） | 一个需求跨三个团队，交接成本吃掉交付速度 |
| 给每个业务线配一个“全功能团队”，基础设施各自造 | 重复造轮子，且每个轮子都只有 60 分 |
| 平台团队没有内部用户与 SLA | 变成成本中心，被业务方绕过 |
| 赋能团队常设化 | 多一层审批，流对齐团队更慢 |
| 把“复杂子系统”当挡箭牌圈业务代码 | 边界僵化，业务变化时改不动 |
| 团队类型频繁切换 | 每个类型都没做深，成员无所适从 |
| 协作模式没有期限 | 两个团队长期耦合，等于没拆 |

## 自检

**Q1** 一个 8 人团队同时负责订单、支付、风控三个业务流，还维护一套自研网关。按本节判据，它该拆成什么？

▸ 答案：先按业务流拆成订单、支付两个流对齐团队；风控若专长稀缺且变化慢，独立成复杂子系统团队；自研网关若只服务内部，收归平台团队（或直接用成熟方案）。判据不是“人够不够”，而是**四类负荷是否混在一个团队里**——业务流、稀缺专长、基础设施三种节奏完全不同。

**Q2** 为什么“平台团队”必须有 SLA，而“运维部”可以没有？

▸ 答案：因为平台团队的产出是**被别的团队自助消费的产品**，没有 SLA 就无法被依赖：业务方不知道它什么时候会挂、挂了找谁；而运维部是被动接工单的职能，依赖关系是“调用”而不是“消费”。平台没有 SLA，业务方就会绕过它自己造，平台随即失去意义。

**Q3** 赋能团队和平台团队的本质区别是什么？

▸ 答案：**是否留下可自助消费的产物**。平台团队交付“能力 + 自助入口 + SLA”，用户不需要认识平台的人也能用；赋能团队交付“带人做一遍”的过程，产物是对方团队的能力，所以必须**限时退出**。把赋能做成常设，就会变成第二层审批。

**Q4** 为什么说“中台不是一种团队类型”？

▸ 答案：因为“中台”描述的是**平台的覆盖范围与共享程度**，不是团队的组织形式。它要么是平台团队（有内部用户、SLA、自助），要么是平台团队服务数过多需要拆分。把“中台”当类型，会导致一个团队既想服务全公司、又想保持小团队效率，最后两头不靠。

**Q5** 一个需求要跨 3 个团队、开 4 次会才能上线，最可能说明什么？

▸ 答案：说明**团队边界与业务流边界错位**：这个需求对应的业务流被切在三个团队里。解法不是加协调人，而是重画边界——把这条流收进一个流对齐团队，或者把其中一段做成 X-as-a-Service，让另外两个团队不必参与。
