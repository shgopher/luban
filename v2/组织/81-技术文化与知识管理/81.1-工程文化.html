                        81.1 工程文化（质量、复盘、透明）

                        一句话

                        工程文化不是“氛围好”，而是三件可检查的事：质量有门禁（不靠自觉）、复盘对事不对人（行动项可验收）、信息默认透明（决策与数据可查）——三件都能用数字验收，验收不了的就是口号。

                        先破除三个误区

                        误区 现实
                        文化 = 团建、氛围、口号 文化是没人看着时的默认行为；它由制度塑造，不由标语塑造
                        质量靠工程师自觉 靠自觉的边界，在第一次赶工期时就会破；能守住的只有门禁
                        复盘 = 追责会 追责让人隐瞒细节，隐瞒让同类事故必然复发

                        🔑 判断一家公司的工程文化，不用看墙上的标语，看三件事：能不能绕过门禁、复盘里有没有人名、决策能不能被新人查到。

                        一、质量：把标准变成门禁

                        “我们要写高质量代码”不是文化，“合并前必须过这四道门”才是。

                        门禁 工具/做法 经验阈值（我的判断） 破了怎么办
                        静态检查 go vet、golangci-lint 0 告警 阻塞合并
                        新增代码覆盖率 go test -coverprofile + diff 覆盖率 新增 ≥ 80% 阻塞合并
                        依赖方向 go list 脚本 / depguard 0 违规 阻塞合并
                        构建与测试时长 CI 计时 单次 ≤ 10 分钟 先修流水线，再谈覆盖率

                        三条硬规则：

                        1. 门禁只拦增量，不清算存量。 存量全量整改的结果通常是“一天 500 条告警，所有人学会无视”。
                        2. 门禁必须由机器执行。 人工 review 会漏，且标准随人漂移（40.4 代码可读性与一致性 讲的就是把“一种写法”变成 CI 规则）。
                        3. 门禁要有豁免通道，但豁免要留痕。 没有豁免通道，团队会绕过整套流水线；豁免不记录，等于没有门禁。

                        覆盖率怎么设阈值、怎么防“为覆盖率而覆盖率”，见 53.8 覆盖率与质量门禁。

                        二、复盘：对事不对人，行动项可验收

                        复盘的价值不在“开会”，在把一次事故变成一条机制。一场合格的复盘有四个必备产出：

                        产出 判据 反例
                        时间线 精确到分钟，写事实不写判断 “当时感觉不太对劲”
                        根因 追到机制（配置为何能直接生效），不追到人 “小王操作失误”
                        行动项 每条有 owner + 截止日 + 验证方式 “加强培训”“提高警惕”
                        复发检查 三个月后回看同类告警 复盘文档归档即结束

                        行动项能不能验收，可以用一条命令查：把复盘的行动项写成表格，缺 owner / 截止 / 验证的行直接标出来。

                        awk -F'|' 'NR>2 {
  for (i=2;i<=5;i++) gsub(/^ +| +$/,"",$i);
  if ($3=="" || $4=="" || $5=="") printf "✗ 行动项「%s」缺 owner/截止/验证\n", $2;
  else printf "✓ 行动项「%s」可验收\n", $2
}' postmortem.md

                        ✓ 行动项「发布前加配置校验」可验收
✗ 行动项「加强培训」缺 owner/截止/验证
✓ 行动项「补充监控告警」可验收

                        “加强培训”这种行动项，一进表格就露馅——它连验证方式都写不出来。

                        两个可以量化的数：

                        指标 怎么算 经验阈值（我的判断）
                        行动项按期完成率 按期完成数 / 行动项总数 ≥ 80%
                        同类事故复发率 12 个月内复发的同类事故 / 总事故 < 10%

                        “无指责”不是不追究，而是把追究对象从人换成机制：人一定会犯错，机制的作用是让错误不致命、可发现、可恢复。具体流程见 56.6 无指责复盘，事故响应的分级与时间线见 56.5 事故响应。

                        ⚠️ 最常见的坏复盘，是把“根因”写成“责任人”。一旦这么写，下一次事故你不会再听到真话。

                        三、透明：默认公开，例外才保密

                        透明不是“什么都公开”，而是默认公开、例外清单：

                        对象 默认 例外
                        决策 公开（ADR 进仓库） 未定稿的讨论可以留在小范围
                        数据 公开（看板、SLO、错误预算） 个人信息、客户数据
                        事故 公开（复盘全员可读） 安全事件按合规要求脱敏

                        透明的收益可以量化：同一个问题，从“问人”变成“查库”要多久。新人上手阻塞时长（40.3 文档与知识传递）就是它的代理指标——阻塞时长越短，说明信息越透明。

                        三个反例：

                        • 决策只存在于会议纪要和某个人脑子里 → 三个月后原样重开争论（58.1 ADR 实践）。
                        • 事故复盘锁在管理层目录 → 同类问题在另一个团队再犯一次。
                        • 监控看板只有值班能看 → 开发不知道自己的服务现在什么状态。

                        三个数：文化的验收表

                        指标 怎么算 经验阈值（我的判断） 说明
                        门禁绕过率 绕过次数 / 合并次数 < 5% 高了说明门禁不合理或文化不认
                        行动项完成率 按期完成 / 总数 ≥ 80% 低了说明复盘在走过场
                        同类事故复发率 12 个月内复发 / 总事故 < 10% 这是唯一能证明“机制真的改了”的数

                        这三个数都不该拿去给团队排名（59.3 度量的陷阱）：它们的用途是发现“制度是不是真的在运行”，不是评价谁优秀。

                        四、个人修养六件事

                        门禁是组织的底线，这六件事是个人的门槛——门禁拦得住团队，拦不住一个人的判断力。

                        陈皓把“程序员修养”定得很重：“如果你的技术修养不够的话，你学再多的知识也是没有用的。”六件事合起来，才是“个人侧”的工程文化：

                        修养 判据 最低动作 缺了会怎样
                        英文能力 能不能直接读一手资料 官网手册、StackOverflow、GitHub 只用英文；每天 5 分钟英文视频；用英文词典与教材 到不了信息源头，“可能无缘成为高手”
                        提问能力 能不能先自己解决 STFW / RTFM；分清 X 与 Y；给最小复现（见五、提问的四步） 做伸手党，问题问不到点上
                        写代码 有没有 CR 与单测 每次合并有人评审；关键逻辑有单测 “If it's not tested, it doesn't work.”
                        安全 有没有最低安全标准 按 OWASP Top 10 自查对外 Web 服务 把注入、越权这类低级漏洞带上线
                        上线规范 有没有测试 + 检查 + 监控 上线前 checklist、上线后监控告警 把上线当“拷个包上去”
                        编程规范 团队是否统一 选定一套规范，用工具执行 风格争论消耗协作，Bug 更多

                        几条原文判据可以直接抄：

                        • Code Review：“我认为没有 Code Review 的公司都没有必要呆（因为不做 Code Review 的公司一定是不尊重技术的）。”
                        • 单元测试：主流框架基本都从 JUnit 衍生；最好的入门方式是读 JUnit User Guide。
                        • 编程规范：风格问题（大括号换行、tab 还是空格）没有对错，只要团队统一；“效率来自于结构化，而不是杂乱”。
                        • 边界：防御性编程要做，但“也别太过度了”（Overly defensive programming）——过度防御是另一种缺陷（38.6 常见攻击 讲安全底线，53.8 覆盖率与质量门禁 讲怎么用机器守住测试门禁）。

                        🔑 修养是“没人检查时你还会不会做”的那部分。门禁能保证合并进主干的代码及格，保证不了你写代码时的判断。

                        五、提问的四步：把问题问到能被回答

                        提问不是“把困惑丢出去”，而是替回答者把上下文准备好——四步做完，很多问题自己就解决了。

                        步骤 动作 判据
                        ① 先自搜 STFW（Search The Web）/ RTFM（Read The Manual）：先搜、先读手册 搜索记录与手册相关段落能不能贴出来
                        ② 确认问的是 X 不是 Y X-Y Problem：你问的常常是自己想到的解法（Y），不是原始问题（X） 能否用一句话说清“我真正想达成什么”
                        ③ 给最小复现 去掉无关代码与数据，留下能稳定复现问题的最小例子 别人照着做能不能复现
                        ④ 列出已试过什么 写清试过哪些方案、结果如何、卡在哪 回答者不必重复你已排除的路径

                        两个缩写出自 Eric Steven Raymond 的《提问的智慧》（How To Ask Questions The Smart Way）；原文的态度很直接：作为一个程序员，不做伸手党。

                        ⚠️ 最常见的坏问题：“这个报错了，怎么办？”——没有环境、没有复现、没有已试方案。它不是问题，是把排查工作整体转包。一个问题的质量，取决于你为了让别人能回答它做了多少工作。

                        反模式

                        反模式 后果
                        文化靠口号与团建 赶工期时第一个被牺牲的就是“文化”
                        门禁清算存量 告警疲劳，团队学会批量忽略
                        门禁没有豁免通道 团队绕开流水线手工发布，比没有门禁更危险
                        复盘写“责任人” 信息被隐瞒，同类事故必然复发
                        行动项写成“加强培训” 无法验收，三个月后没人记得
                        决策只活在会议纪要里 新人反复重开已决的问题
                        事故复盘不公开 别的团队把同一个坑再踩一遍
                        把文化指标拿去排名 指标立刻失真（古德哈特定律）

                        自检

                        Q1 为什么“质量靠自觉”在工程上站不住？

                        ▸ 答案：自觉的强度随工期压力波动，而工期压力是常态。门禁把标准交给机器执行，不随人的状态漂移；同时门禁只在增量上生效，避免存量告警淹没信号。判据：这个标准在“明天必须上线”的那天还成立吗？不成立就说明它只是自觉。

                        Q2 无指责复盘和“追究责任”矛盾吗？

                        ▸ 答案：不矛盾，追究对象不同。追责追的是人（谁操作失误），无指责复盘追的是机制（为什么这个操作能直接生效、为什么没有拦截、为什么没被发现）。机制不改，换个人来还会犯同样的错；把人处理掉只会让下一次事故没人敢说真话。

                        Q3 行动项“加强培训”为什么是坏行动项？改成什么？

                        ▸ 答案：它没有 owner、没有截止日、没有验证方式，因此无法验收，也无法判断是否完成。改法示例：“把这次误操作的命令加入发布前检查脚本（owner：某某，截止：11-15，验证：故意执行错误命令，脚本必须拦截）”——可执行、可验证、可回滚才算行动项。

                        Q4 门禁绕过率低于 5% 说明什么？高于 20% 又说明什么？

                        ▸ 答案：低于 5% 说明门禁既被遵守、又有合理的豁免通道；高于 20% 通常不是“文化差”，而是门禁设计得不合理（太慢、太吵、误报多），团队只能用绕过自救。先修门禁，再谈纪律。

                        Q5 透明为什么能降低“新人上手阻塞时长”？

                        ▸ 答案：因为新人的阻塞大多来自“信息不在代码里”——为什么这么设计、这个服务归谁、出了事看哪个看板。这些信息如果能从 ADR、服务目录、看板直接查到，阻塞就从“等人回答”变成“自己查”；阻塞时长因此缩短，而它正是透明度的代理指标。
