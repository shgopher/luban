# 81.6 用 Agent 学会陌生代码库：/teach 与 /understand

## 一句话

> 让 Agent「讲一遍」，优化的是**流畅度**（当场听懂，关窗就忘）；用 `/teach` 把代码库做成有状态、可回看、带回忆测验的课，优化的是**存储强度**；`/understand` 则把「这段代码为什么存在」变成审查流水线里的一道固定工序。

## 先破除五个误区

| 误区 | 现实 |
|---|---|
| 让 Agent 总结一遍 = 学会 | 总结是二手转述，飘在代码之外；你记住了「有限流」，但不知道落在哪几行、为什么是滑动窗口 |
| 读代码 = 理解 | 读懂一行不等于建立心智模型；关掉窗口一周后还能复述，才算留下 |
| 测试通过 = 懂了 | 测试保证「代码没有错」，不保证「你知道它为什么这样写」 |
| 画了图 = 理解 | 图是压缩，能帮你建立全局，但细节仍要靠源码与追问 |
| 学习必须从 `main` 顺序读 | 从变更频率、入口、测试和示例切入，比从头读到尾快得多 |

## 生成与理解的速率差

AI 写代码是并发的：同时开几个 Agent，一天出几千行。人读代码是串行的：一个脑子、一行一行，一天真正搞懂几百行就不错。这个缺口会带来三个具体问题：

- **不敢动**：祖传区域碰都不敢碰；
- **答不上**：同事问起，只能去翻 AI 当时的回复；
- **背不动**：线上出问题，根因藏在哪完全没有概念。

测试能兜住「行为没坏」，兜不住「你理解了吗」；粗读 diff 三分钟就以为懂了，其实只是精神上易主；让 AI 写总结也靠不住，因为总结不带 `file:line`，无法验证。**理解没法并行、没法压缩、没法甩给别人，只能降成本**——让 AI 顺手把「备课」做了。

## 认知科学：流畅度 ≠ 存储强度

| 概念 | 表现 | 怎么获得 |
|---|---|---|
| **流畅度（fluency）** | 听讲解时觉得「懂了」，能复述 | 读一遍、听一遍 |
| **存储强度（storage strength）** | 一周后、下个项目还能想起来 | 合上书自己推、隔几天再考、交错练习 |

`/teach` 的设计地基是**合意困难（desirable difficulty）**：短小的课、回忆测验、间隔与交错、回指前面的课。它不追求「讲得顺」，而追求「你费劲回忆过」。

还有一个关键概念是**最近发展区（ZPD）**：下一课要「有点难，但够得着」。Agent 靠读学习记录判断你已经掌握什么，再结合 mission 挑边界上的内容——太简单浪费时间，太难吃光工作记忆。

## 一个真实样本的数字

`zero-learn` 是拿 Zero（一个终端 coding agent）练出来的教学工作区，可以作为「学到什么程度」的参照：

| 指标 | 数值 | 含义 |
|---|---|---|
| 被学项目规模 | 68 个 internal 包、主循环文件约 2700 行 | 陌生代码库的典型量级 |
| 课程 | 20 课、6 组 | 一课只讲一个架构决定 |
| 图的类型 | 17 种，默认 3 张 | architecture + sequence + flowchart |
| 理解外置案例 | 11 万行 Swift、3347 个 XCTest、测试约占 66% | Rules + 测试路线的成本 |

课程不是「把 68 个包讲一遍」，而是从主循环、工具分发、权限沙箱、上下文管理、TUI 这些要害里挑 20 个架构决定，每个都精确到 `file:line`。**广度靠图，深度靠课**，这是这类工作区的基本分工。

## `/teach`：把目录变成有状态的教学工作区

`/teach` 出自 Matt Pocock 的 skills 合集（`github.com/mattpocock/skills` 的 `productivity/teach/`）。它的 SKILL.md 第一句就点明区别：

> This is a stateful request - they intend to learn the topic over multiple sessions.

普通对话是一次性的，关掉就没了；`/teach` 把当前目录当成教学工作区，把学习状态沉淀成磁盘文件。下次进来，Agent 读这些文件就知道你学到哪、偏好什么、下一步教什么。

### 六类文件，各管一件事

| 文件 / 目录 | 作用 | 类比 |
|---|---|---|
| `MISSION.md` | 为什么学、学成什么样、边界在哪 | 北极星 |
| `RESOURCES.md` | 可信资源清单 | 参考书目 |
| `NOTES.md` | 学习者画像、教学偏好 | 老师的备课笔记 |
| `learning-records/` | 已被验证的关键理解 | ADR |
| `lessons/` | 一课一个 HTML，主产物 | 讲义 |
| `reference/` | 跨课复用的速查文档 | 术语表 / 速查卡 |

`MISSION.md` 是重中之重。每一课都要挂回 mission；mission 不清楚，Agent 第一件事不是开讲，而是**反问你为什么学**。

一个能用的 mission 不写「大致了解」，而写**可验证的能力**：

```markdown
## Why
理解一个现代终端 coding agent 的内部设计：turn loop、工具分发、
权限/沙箱、上下文管理、TUI。

## Success looks like
- 能把一个 prompt 端到端追踪：provider 流 → 工具调用 → 工具结果
  → 下一轮 → 最终答案，每一步叫得出具体函数名。
- 能解释一个回合「结束了」还是「再来一轮」的判断。
- 能画出可比的 agent 最小架构。

## Out of scope
- 贡献 PR、provider 的 wire 格式、构建发布工具链。
```

「叫得出具体函数名」直接决定课程深度必须到 `file:line`，不能停在「大概有个循环」。

### 课程怎么设计

- **一课一个架构决定**：工作记忆很小，一课塞一个就够；
- **每个论断带 `file:line`**：解释不能飘在代码之外；
- **回忆测验**：合上讲义从记忆里捞答案；选项长度尽量一致，不让你靠格式猜；
- **交错与回指**：后面的课引用前面的，相关概念混着练；
- **课程与参考文档分工**：课程负责「第一次学会」，可以长、有互动；`reference/` 是压缩精华，负责「日后速查」，要短、能打印。

学习记录像 ADR：只记**已验证的理解**，不记「看过」。下一次课从记录出发，避免重复教已经会的东西。

### 产出形态

课程是自包含 HTML，共享 `assets/course.css` 与 `assets/quiz.js`；20 课看起来像一门课，而不是 20 个一次性文件。整个工作区刻意放在被学仓库**之外**（如 `zero-learn/` 与 `zero/` 相邻），用相对路径引用源码，学习笔记不污染干净的 checkout。

## `/understand`：把「为什么」变成审查工序

`/teach` 解决从零学一个项目；日常更常见的是：AI 刚写完一段代码，你要审，却读不懂它为什么这么写。

`/understand` 与 `/review-it` 是一对：

| 工具 | 问什么 | 对谁负责 | 产出 |
|---|---|---|---|
| `/review-it` | 这段代码有没有问题？ | 代码质量 | 问题列表 + 修复建议 |
| `/understand` | 这段代码为什么存在？ | 你的理解 | 逐段讲解卡片 + 单文件 HTML |

工作方式三步：

1. **扫描变更**：以 merge-base 为基线，已提交、暂存、未暂存、未跟踪全扫；
2. **逐段写卡片**：相关需求（commit message、需求文档、issue 的真实出处）+ 大白话解释；
3. **渲染单文件 HTML**：左侧目录树、中间语法高亮 diff、右侧卡片流，点卡片跳真实行号并高亮。

四个设计决策值得抄：

- **推测意图显式标灰**：`inferred` 字段区分真实出处与 AI 脑补；
- **锚定真实行号**：解释必须能跳到代码；
- **注释密度克制**：每个重要文件 1–5 条，只讲核心逻辑、边界易错点、最体现需求的段落；
- **单文件离线**：能贴进 review 评论、群聊、`docs/`，三个月后考古还在。

日常顺序：AI 生成 → `/review-it` 筛问题 → `/understand` 生成审阅网页 → 你逐段过卡片 → `/ship-it`。理解不是「回头再看」，而是流水线里的一道工序。

## 图：先建立广度，再进细节

`/insight-diagram` 分析代码库，生成 17 种 UML/架构/流程图，默认推荐 **architecture + sequence + flowchart** 三张：一张看「长什么样」，一张看「一次请求怎么走」，一张看「业务怎么分支」。它把渲染交给 `/architecture-diagram`，输出单文件 HTML+SVG。

关键纪律是**先读示例再画**：skill 自带高质量示例，先提取布局、节点样式、信息密度，再换成目标项目的真实内容——**参考布局，不复制业务**。这和前端设计 Skill 的结论一致：约束比自由更能提升 AI 的下限。

图的使用顺序：先用三张图建立全局，再 `/teach` 逐课深入要害模块；不要一上来画 17 张，也不要指望图替代源码。图的具体工具与校验见 [83.7 用 Agent 画架构图：可 diff、可校验](../../附录/83-架构文档与表达/83.7-Agent画架构图.md)。

## 另一条路：把理解外置成规则

不是所有项目都值得「人逐行理解」。全 AI 主导的项目可以换一种做法：

- AI 写的代码让 AI 来测（大量 XCTest / 单测）；
- 修 bug 必须留下回归测试；
- 把「为什么这么改」写进按模块拆分的 Rules，只在改到相关代码时加载；
- 用 CI 做一致性检查兜底。

这相当于把「理解」外置成机器能用的资产：人不必理解每一行，只要理解规则和测试。代价是测试量必须够——有案例是 11 万行 Swift 配 3347 个 XCTest（测试代码约占产品代码 66%）；没有这个测试密度，Rules 就是空架子。

## 什么时候用哪个

| 你的目标 | 用什么 | 产物给谁 |
|---|---|---|
| 让 Agent 干活前先理解代码 | 知识图谱 / UML 反向生成 | Agent，当次任务 |
| 从现有代码逆向出规格 | `/code-to-spec` | 交付物、规格文档 |
| 快速理解一段改动 | `/understand` | 你，当下审查 |
| 下个月还记得、能带走的理解 | `/teach` | 你，长期留存 |
| 给项目补几张骨架图 | `/insight-diagram` + `/architecture-diagram` | 团队，文档/评审 |
| 全 AI 主导、人只看规则 | Rules + 测试 + CI | 机器资产 |

判据很简单：**产物给谁看、要不要留得住**。给 Agent 干活用前三类；给自己当下审查用 `/understand`；给未来的自己用 `/teach`。

## 反模式

| 反模式 | 后果 |
|---|---|
| 让 Agent「讲讲这个项目」就结束 | 得到即用即弃的概述，关窗就忘 |
| 没有 mission 就开课 | 课程飘，Agent 不知道下一步教什么 |
| 一课塞三个架构决定 | 工作记忆爆掉，什么都没留下 |
| 只听课不做回忆测验 | 流畅度错觉，一周后归零 |
| 把 `inferred` 当真实需求 | 脑补的意图被当成事实，审查被误导 |
| 只画图不读源码 | 图是压缩，细节和边界仍然不清楚 |
| 学习笔记写进被学仓库 | 污染 checkout，PR 里混进笔记 |
| 让「总结」替代「理解」 | 出事故时答不上根因 |

## 自检

**Q1** 为什么「让 Agent 讲一遍」不等于学会？流畅度和存储强度差在哪？

▸ 答案：讲一遍优化的是流畅度：当场能复述、感觉懂了，但这是「我懂了」的错觉。存储强度靠费劲回忆获得：合上讲义自己推、隔几天再考、交错练习。`/teach` 用短课、回忆测验、间隔与回指来制造合意困难，目标是一周后还能想起来。

**Q2** `/teach` 的工作区为什么要有 `MISSION.md` 和 `learning-records/`？

▸ 答案：`MISSION.md` 定义为什么学、学成什么样、边界在哪；没有它，课程会飘，Agent 不知道下一步教什么。`learning-records/` 记录已被验证的理解，像 ADR；Agent 靠它判断最近发展区，避免重复教已经会的内容。

**Q3** `/understand` 和 `/review-it` 是什么关系？为什么审查流水线里要有「理解」这道工序？

▸ 答案：`/review-it` 问「代码有没有问题」，对代码质量负责；`/understand` 问「代码为什么存在」，对理解负责。AI 生成速度远快于人理解速度，如果不把理解放进流水线，代码会变成没人敢动的考古现场；两者一个管质量、一个管理解，不能互相替代。

**Q4** 为什么 `inferred`（推测意图）要显式标灰？

▸ 答案：AI 很擅长脑补意图，而且脑补得特别像真的。标灰强制区分「有真实出处」和「AI 猜的」；审查者据此决定哪些结论可以直接信、哪些要回去查 commit/issue/需求文档。不标灰，猜测就会被当成事实。

**Q5** 图在「学会一个项目」里应该怎么用？

▸ 答案：先用三张骨架图（architecture + sequence + flowchart）建立广度：长什么样、一次请求怎么走、业务怎么分支；再 `/teach` 逐课深入要害模块。图不能替代源码：它给你全局和压缩，细节、边界、`file:line` 仍要读代码。画图时先读高质量示例，借布局不借业务。

**Q6** 什么情况下可以「不逐行理解」，改用 Rules + 测试？

▸ 答案：全 AI 主导、测试密度足够高的项目。把行为冻进测试、把约束写进按模块加载的 Rules、用 CI 兜底，人只理解规则和测试。前提是测试量真的够（案例是 11 万行配 3347 个测试）；测试不够，Rules 就是空架子，人既没理解代码也没安全网。
