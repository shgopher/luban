# 20.5 三种算法对比 (消息量 / 公平性 / 可用性)

## 一句话

> 三种互斥算法是三个固定的取舍：**集中式用中心换消息（2 条）**，**Ricart-Agrawala 用消息换去中心（2(N−1) 条）**，**令牌环用延迟换公平（O(N) 跳）**；没有最优，只有 “你的瓶颈是消息、延迟还是容错”。

## 一张表看完

| 维度 | 集中式（协调者 + 租约） | Ricart-Agrawala（全票） | 令牌环 |
|---|---|---|---|
| 每次进入消息数 | 2 + 1（释放） | 2(N−1) | 1（令牌传递） |
| 进入延迟 | 1 RTT | 1 RTT（等最慢回复） | 平均 N/2 跳 |
| 公平性 | 可做 FIFO，取决于实现 | **天然按时间戳 FIFO** | **严格轮转** |
| 容错 | 中心挂 = 不可用；有副本需共识 | 任一节点挂 = 卡住 | 任一环断 = 停摆 |
| 单点 | 有（可高可用化） | 无 | 无 |
| 实现复杂度 | **低** | 中 | 中高（环维护） |
| 规模 | 大（中心可扩展） | **小（N < 10）** | 中（依赖延迟） |
| 生产可用性 | **高**（租约 + fencing） | 低 | 低 |

## 选型判据

| 你的情况 | 选择 |
|---|---|
| 通用场景、要求可用性 | **集中式 + 租约 + fencing**（生产默认） |
| 节点少、要严格轮流、无中心 | 令牌环 |
| 学术/嵌入式、可接受零容错 | Ricart-Agrawala |
| 跨地域、网络分区频繁 | 集中式（区域中心）+ 分区内自治，不要全票算法 |

## 数字直觉

- N=5：集中式 3 条 vs RA 8 条 vs 环平均 2.5 跳。
- N=100：集中式 3 条 vs RA 198 条 vs 环平均 50 跳。

**消息量是 O(1)、O(N)、O(1) 但延迟 O(N)**——三个不同的增长曲线，决定了适用规模。

三种算法的细节分别在 [20.2 集中式互斥 (协调者)](20.2-集中式互斥.md)、[20.3 分布式互斥 (Ricart-Agrawala / 全票通过)](20.3-分布式互斥.md)、[20.4 令牌环互斥](20.4-令牌环互斥.md)。

## 代码：一次互斥的 “预算表”

```text
集中式：  acquire 1 RTT + release 1 RTT   ≈ 2 RTT，消息 3 条
RA：      广播 N-1 + 收 N-1              ≈ 1 RTT（等最慢），消息 2(N-1)
令牌环：  等令牌平均 N/2 跳 + 传递 1 跳     ≈ (N/2+1) 跳，消息 1 条

选型判据（把 N 代进去算）：
  N < 10 且要求严格公平 → 令牌环
  任意 N，要求可用性    → 集中式 + 租约 + fencing
  封闭环境、可接受零容错 → RA
```

## 按消息量算账

**结论**：每次进入的消息数由协议写死（集中式 3 条、RA `2(N−1)`、Lamport `3(N−1)`），真正拉开差距的是**每秒消息量**与**并发形态**：N=10、闭环跑 10s，Lamport 发约 9 万条、集中式 7,500 条；令牌环的 “每次进入 1 条” 只在满载时成立，K=1 时要空转 10 跳。选型不是比谁消息少，是看你的负载落在哪一段。

### 先把 Lamport 也算进来

RA 常被当作 “分布式互斥” 的代名词，但它其实是 Lamport 1978 算法的改良：Lamport 退出时要再广播一轮 RELEASE，共 `3(N−1)` 条；RA 让 “延迟回复” 兼任释放，降到 `2(N−1)`。并排看才知道省下的 1/3 从哪来——不是算法更聪明，是把 “释放” 藏进了本来就必需的回复里。

| 算法 | N=5 | N=10 | N=50 | 每次进入的消息构成 |
|---|---|---|---|---|
| 集中式 | 3 | 3 | 3 | 请求 + 授权 + 释放；外加 1 个协调者节点 |
| Lamport | 12 | 27 | 147 | 请求 N−1 + 回复 N−1 + 释放 N−1 |
| RA | 8 | 18 | 98 | 请求 N−1 + 回复 N−1（延迟回复兼任释放） |
| 令牌环（K=N 满载） | 1 | 1 | 1 | 令牌一圈服务 N 次，摊薄到 1 跳/次 |

集中式的 3 条是唯一与 N 无关的；代价是协调者必须自己高可用，且关键路径比 RA 多一个单程延迟——它在消息上省，在延迟与运维上加。

### 仿真：并发变，账本怎么变

公平的比法不是 “每条进入多少条”，而是**同样的时间窗内、各算法按自己的饱和吞吐跑，每秒发多少条**。闭环下 K 个客户端 “用完立刻再抢”，永远有请求在等；临界区 C=2ms、单程延迟 L=1ms，跑 10s。队列类算法按关键路径推进（集中式 C+2L，RA/Lamport C+L），令牌环逐跳推进：

```go
// 队列类算法：单临界区串行，按协议的关键路径推进
func queueAlgo(k int, entryCostUS int64, perEntry int64) (entries int64, msgs int64, throughput float64) {
    var now int64
    for now < simUS {
        now += entryCostUS
        entries++
    }
    msgs = entries * perEntry // 消息数 = 每次进入 × 完成次数
    return entries, msgs, float64(entries) / (float64(simUS) / 1e6)
}

// 令牌环：有等待请求就进临界区 C，没有就直接传下一跳；每传一跳计 1 条消息
for now < simUS {
    if pending[pos] {
        now += csUS // 进入临界区
        entries++
        pending[pos] = false
    }
    // 传令牌给下一个节点
    now += latUS
    hops++
    next := (pos + 1) % nodes
    // 刚服务的客户端重新排队（闭环：立刻再请求）
    if pos < k {
        pending[pos] = true
    }
    pos = next
}
```

本机仿真（`go1.27.1 / darwin/arm64 / Apple M1`）：

```text
参数：N=10 节点，临界区 C=2ms，单程延迟 L=1ms，闭环仿真 10s（K 个客户端一直有请求在等）

表 A：每条进入的消息数（与并发无关，只随 N 变）
算法              N=5       N=10      N=50      备注
集中式            3         3         3         请求+授权+释放；外加协调者节点
Lamport           12        27        147       请求+回复+释放 = 3(N−1)
Ricart-Agrawala   8         18        98        请求+回复 = 2(N−1)，延迟回复当释放
令牌环（K=N 满载）  1         1         1         令牌每绕一圈服务 N 次，摊薄到 1 跳/次

表 B：每秒消息量（N=10，不同并发 K；各算法按自己的吞吐跑满 10s）
并发 K    集中式 条/秒    Lamport 条/秒     RA 条/秒      环 进入/秒    环 条/秒      环 条/进入
1         750             9002              6001          83            833           10.0
2         750             9002              6001          143           714           5.0
5         750             9002              6001          250           500           2.0
10        750             9002              6001          333           333           1.0

校验：集中式 2500 次进入 × 3 = 7500 条；Lamport 3334 次 × 27 = 90018 条；RA 3334 次 × 18 = 60012 条（10s 累计）
      集中式吞吐 = 250 次/秒（关键路径 C+2L=4ms）；Lamport/RA = 333 次/秒（C+L=3ms）
断言通过：集中式 3 条/次、令牌环满载 1 跳/次
```

完整代码在仓库 [tools/examples/20.5-mutex-compare/](../../../tools/examples/20.5-mutex-compare/README.md)，`go run .` 可复现这段输出。

读数：

- **集中式**：750 条/秒，与 K 无关——3 条/次，吞吐 250 次/秒。消息账最便宜，但关键路径 4ms，比 RA/Lamport 的 3ms 慢 25%。
- **Lamport/RA**：吞吐最高（333 次/秒），消息量是集中式的 12 倍 / 8 倍；N 越大差距越大（N=50 时 147 条/次 vs 3 条/次）。
- **令牌环**：唯一随负载变化的账。K=1 时令牌要绕一圈才回到唯一客户端，10 跳/次、833 条/秒；K=10 满载摊薄到 1 跳/次、333 条/秒。**低负载时它最贵，高竞争时它最便宜**。
- 按每条消息 200B 换算：Lamport ≈ 1.8MB/s，RA ≈ 1.2MB/s，集中式 ≈ 150KB/s，令牌环 67–167KB/s。消息越宽、N 越大，O(N) 的算法越先撞到网卡与序列化上限。
- 环的便宜有前提：成员稳定。环维护（加入、离开、令牌丢失）本身要一轮协调消息，K 越小、切换越频繁，这笔额外账越重（[20.4 令牌环互斥](20.4-令牌环互斥.md)）。

「消息数」只是账的一半，另一半是消息大小。这些请求都带时间戳与节点 ID，回复是短包；可一旦 N=50，RA 每次进入 98 条 × 200B ≈ 19.6KB，按 1,000 次进入/秒算就是 19.6MB/s——还没算广播在交换机上的复制。O(N) 的算法通常先被带宽与序列化打穿，而不是先被 CPU 打穿。

也不能只比 “每次进入多少条”：K=1 时环是 10 条/次，比 Lamport 的 27 条少一半多，但它每秒只完成 83 次进入，Lamport 是 333 次。乘回吞吐，环 833 条/秒是 Lamport 9002 条/秒的约十一分之一，可它也只干了约四分之一的活。**正确的归一化是 “每完成一次互斥要多少条” 与 “每秒能完成多少次” 两个数一起看**——单看任一个，都会把最慢的算法算成最省的。

环与集中式的消息交叉点可以算出来：N=10 时环每条进入 = N/K 跳，K > N/3 ≈ 3.3 时低于集中式的 3 条；本仿真 K=2 是 5 条/次、K=5 是 2 条/次。但交叉点只说明 “消息更少”，不说明 “更快”：K=5 时环吞吐 250 次/秒、集中式也是 250 次/秒；到 K=10 环的 333 次/秒才反超，而延迟上环还要等令牌走到自己。**消息账、吞吐账、延迟账要分开算，再按业务最贵的那一项排序。**

### 结论：小规模 / 高竞争 / 低延迟

| 你的瓶颈 | 选谁 | 数字依据 |
|---|---|---|
| 小规模、低竞争、要严格先到先得 | **RA** | N=5 每条 8 条、1 RTT；N>10 每次进入 O(N)，去中心省的协调成本被消息吃光 |
| 高竞争、成员稳定、能忍延迟 | **令牌环** | 满载 1 跳/次；K=10 时 333 条/秒，低于集中式的 750 |
| 低延迟、通用、规模不限 | **集中式 + 租约 + fencing** | 3 条/次、关键路径 4ms、吞吐 250 次/秒；消息量是唯一与 N 无关的 |
| 无中心但规模很小 | RA；Lamport 只作对照 | 两者容错都是 0，节点故障要靠成员变更与共识补 |

一句话：小规模选 RA，买 “无中心 + 1 RTT”；高竞争选环，买 “消息随竞争摊薄”；低延迟/通用选集中式，买 “3 条 + 可高可用化”。三句话背后是三条增长曲线：RA 是 O(N) 消息、令牌环是 O(N) 延迟、集中式是 O(1) 消息 + 1 RTT；规模或竞争一变，压垮系统的成本项就换一个。任何一条都别忘了资源侧的 [48.3 分布式锁](../../L4-组件与技术/48-配置与协调/48.3-分布式锁.md) 那套租约与 fencing token——消息算得再清，锁本身不安全等于零。

> 🔑 每次进入的消息数看协议，每秒消息量看负载与并发；两者不是一回事。

> 🔑 令牌环的 1 条/次只在满载成立；低负载时它比 Lamport 还贵。

## 反模式

| 反模式 | 后果 |
|---|---|
| 不看规模直接选 RA | N 大了消息爆炸 |
| 用令牌环做高频互斥 | 延迟 O(N)，吞吐上不去 |
| 集中式不做高可用 | 锁服务挂 = 全站停写 |
| 任何方案都不做 fencing | 暂停进程的迟到写破坏互斥 |
| 只比较消息数就选算法 | 忽略延迟与容错，规模上来后返工 |
| 忽视 “算法外的工程” | 成员变更/失联处理才是事故来源 |

## 三条铁律

> 🔑 **消息量与延迟的增长曲线决定适用规模**，不是 “哪个更先进”。

> 🔑 **生产默认集中式**；它的单点可以用共识与租约解决，其他两者的容错更难补。

> 🔑 **无论哪种算法，资源侧都要有 fencing**。

## 自检

**Q1** 为什么生产上更偏爱集中式，尽管它有单点？

▸ 答案：因为**单点可以被工程手段消解**（多副本 + 共识 + 租约 + 客户端重试），而 RA 与令牌环的 “全票/环” 特性在**故障时直接失去活性**，且成员变更本身需要共识。集中式的复杂度是 “可运维的复杂度”。

**Q2** 令牌环 “消息最少” 为什么反而不常用？

▸ 答案：因为**延迟随 N 线性增长**，而且环维护（加入/离开/令牌丢失）的复杂度很高，任何一处故障都可能导致全局停摆。消息少的好处被 “延迟 + 运维” 抵消。

**Q3** 如果一定要在 N=50 的集群做互斥，选哪个？

▸ 答案：**集中式（带租约与 fencing）**：RA 要 98 条消息、令牌环平均 25 跳；集中式 1 RTT 且可水平扩展（按锁名分片到多个协调者）。只有在 “完全不能有中心” 的约束下才考虑其他两者。

**Q4** 三种算法的公平性差异体现在哪？

▸ 答案：RA 按**时间戳 FIFO**（先请求先进入）；令牌环**严格轮转**（每节点一次机会）；集中式取决于队列实现（可 FIFO，也可优先级）。公平性影响的是 “最坏等待时间”，在高竞争场景下比平均延迟更重要。

**Q5** 为什么说 “算法选对了但没配 fencing 依然会错”？

▸ 答案：因为所有算法都假设 “持有者会按时释放”。现实中进程会**暂停**（GC、缺页、调度），恢复后仍以为自己持有锁。fencing token 让资源侧能拒绝 “过期的持有者”，这是算法层面的互斥无法覆盖的工程漏洞。

**Q6** 为什么表中 RA 是 “1 RTT” 而令牌环是 “N/2 跳”？

▸ 答案：因为 RA 的请求/回复**并行广播**，延迟由最慢的一个回复决定（1 RTT）；令牌环的令牌必须**串行**逐跳传递，等待时间随环上节点数线性增长。两者消息量与延迟的增长曲线完全不同，这就是 “按规模选” 的数学依据。
