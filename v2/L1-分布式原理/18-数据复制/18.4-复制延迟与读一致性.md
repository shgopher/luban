# 18.4 复制延迟与读一致性

## 一句话

> 异步复制下，“写完立刻读” 有 **60% 概率读到旧值**（本机模拟）；读一致性不是 “把从库加个开关”，而是要在 **会话/版本** 层面设计——你要的是 “读己之写”，还是 “最终一致”，必须先说清。

## 四种读一致性

| 级别 | 保证 | 实现手段 | 代价 |
|---|---|---|---|
| **强一致** | 读到的必是最新已提交 | 读主库 / 多数派读 | 主库压力、延迟 |
| **读己之写** | 自己写的，自己一定读到 | 会话粘性、写后读主、版本等待 | 需会话/版本信息 |
| **单调读** | 不会读到 “更旧” 的版本 | 绑定副本/版本单调 | 副本切换要小心 |
| **最终一致** | 一段时间后一致 | 异步复制 | 窗口内可能读到旧值 |

## 实测：无粘性 vs 会话粘性

2 万次 “写后 0–200ms 读”、复制延迟 120ms：

| 策略 | 陈旧读 | 比例 |
|---|---|---|
| 无会话粘性（随机读副本） | **12,013** | **60.1%** |
| 会话粘性（写后读主库） | **0** | 0% |

60% 这个数字说明：只要 “读” 落在复制延迟窗口内，就大概率读到旧值——这不是 “偶发”，是**默认行为**。

```go
// 写后 N 秒内读主库（最简单可靠）
func (s *Service) GetAfterWrite(ctx context.Context, id string) (User, error) {
    if s.session.WroteRecently(id, 2*time.Second) {
        return s.master.Get(ctx, id)      // 读主
    }
    return s.replica.Get(ctx, id)
}
```

## 三种 “读己之写” 实现

| 实现 | 做法 | 适用 |
|---|---|---|
| 写后读主（时间窗） | 会话记录 “最近写过”，窗口内读主 | 简单、通用 |
| 版本等待 | 客户端带上 “我写到哪个版本”，副本等到 ≥ 该版本 | 精确、需版本号 |
| 会话粘性 | 同一会话固定路由到同一副本 | 负载均衡要支持 |

## 延迟的量化：从公式到「读到旧值概率」

**复制延迟不是一个数，是一条分布**；「写完立刻读」读到旧值的概率，等于“读发生在副本追上之前”的概率。把延迟拆成三段，才知道该压哪一段；把概率写成公式，才知道 60% 不是运气差，而是默认行为。

### 公式：L = 排队 + 传输 + 应用

| 段 | 由什么决定 | 典型值（同城 / 跨城） | 怎么压 |
|---|---|---|---|
| 排队 | 主库提交排队、binlog 落盘、大事务 | 1ms / 2ms | 拆大事务；权衡 `sync_binlog` |
| 传输 | 网络 RTT + 带宽 + 批量 | 2ms / 30ms | 就近副本、压缩与批量 |
| 应用 | 副本回放：`积压量 / 回放速率` | 8ms / 40ms | 并行回放、拆大事务 |

本机计算：同城 `1 + 2 + 8 = 11ms`，跨城 `2 + 30 + 40 = 72ms`；积压 6 万个事务、回放 2000 txn/s 时，应用段 = `60000 / 2000 = 30s`。

**排队与传输是毫秒到几十毫秒的常数，应用段却可以是秒级**——这就是“网络没问题、延迟却几分钟”的全部原因（回放与读写分离的细节见 [44.13 主从复制与读写分离](../../L4-组件与技术/44-数据库/44.13-主从复制与读写分离.md)）。

### 写后读旧值的窗口就是 L

写 W 在 t0 提交，读在 t0 + Δ 落到某个副本。读返回旧值 ⇔ 副本在 t0 + Δ 时还没可见这笔写 ⇔ **L > Δ**。于是：

`P(旧读) = P(L > Δ) = 1 - F_L(Δ)`

读在写后 `[0, T]` 内均匀分布时，期望合并成一式：`P(旧读) = E[min(L, T)] / T`。三种参数下本机计算的结果：

| 场景 | 参数 | 旧读概率 |
|---|---|---|
| 固定延迟 | L = 120ms，T = 200ms | `120 / 200 = 60%`，与 60.1% 的模拟结果吻合 |
| 有尾部的延迟 | L 中位数 120ms、p99 ≈ 770ms，T = 200ms | **62.3%**（中位数几乎不起作用，概率由尾部决定） |
| 拉长读窗口 | 同上，T = 1000ms | 16.4%（窗口越长，重叠比例越低） |

要把握“读己之写”失败率压到 1%，读主窗口应取 L 的 99 分位 = **769ms**；压到 0.1%，要 **1412ms**。这就是“写后读主 2 秒”这类经验值的数学来源：1.4s 再留一点余量。

### 三种复制模式的写延迟与旧读窗口

| 模式 | L 中位数 | 写延迟 p50 | 写延迟 p99 | 旧读窗口 | 200ms 后读旧值概率 |
|---|---|---|---|---|---|
| 异步 | 10ms | 1.0ms | 1.0ms | L（= 10ms） | 0.0% |
| 半同步 | 10ms | 5.2ms | 18.7ms | L（= 10ms） | 0.0% |
| 全同步 | 10ms | 19.2ms | 87.9ms | 0（回放后） | 0.0% |
| 异步 | 100ms | 1.0ms | 1.0ms | L（= 100ms） | 19.4% |
| 半同步 | 100ms | 52.0ms | 187.8ms | L（= 100ms） | 19.4% |
| 全同步 | 100ms | 192.4ms | 883.2ms | 0（回放后） | 0.0% |
| 异步 | 1s | 1.0ms | 1.0ms | L（= 1s） | 97.8% |
| 半同步 | 1s | 520.2ms | 1876.9ms | L（= 1s） | 97.8% |
| 全同步 | 1s | 1933.8ms | 8775.5ms | 0（回放后） | 0.0% |

三个读法：

- **异步**：写延迟 1ms 与 L 无关，旧读窗口 = L。L = 1s 时，写后 200ms 的读 97.8% 是旧值——用户看到的不是“偶发”。
- **半同步**：写延迟约为 L 的 0.52 倍（等最快的副本），但**旧读窗口与异步完全相同**。它买的是持久性（RPO = 0），不是读一致性（见 [18.2 同步、半同步、异步](18.2-同步-半同步-异步.md)）。
- **全同步**：写延迟 p50 是半同步的 3.7 倍、p99 是 4.7 倍，换来窗口 0；**前提是 `remote_apply` 级确认**，只到 `remote_write` 时窗口 = 回放延迟，仍不为 0。

### 可运行：从写速率与延迟分布算窗口

给定写速率、延迟分布与读窗口，脚本同时算出：无兜底时的旧读概率、把失败率压到目标值所需的粘性窗口、该窗口下的主库读比例，以及三种复制模式的写延迟。

```python
#!/usr/bin/env python3
"""18.4 复制延迟 -> 读到旧值概率、粘性窗口与三种复制模式的写延迟。
本机仿真：复制延迟 L ~ 对数正态(中位数, sigma=0.8 对数尺度)，N=200000。
运行：python3 ryw_prob.py
"""
import math
import random

N = 200_000
SIGMA = 0.8
rnd = random.Random(20261121)


def log_lag(median_ms, sigma=SIGMA):
    return math.exp(rnd.gauss(math.log(median_ms), sigma))


def pct(xs, p):
    return xs[min(int(p * len(xs)), len(xs) - 1)]


print("== 1. 延迟分解：L = 排队 + 传输 + 应用（输入为典型值，本机计算）==")
for name, queue, net, apply_ in [("同城", 1, 2, 8), ("跨城", 2, 30, 40)]:
    print(f"{name}: {queue}ms + {net}ms + {apply_}ms = {queue + net + apply_}ms")
backlog, replay_rate = 60_000, 2_000
print(f"回放积压：{backlog} txn / {replay_rate} txn/s = {backlog / replay_rate:.0f}s")

lag = [log_lag(120.0) for _ in range(N)]
print("\n== 2. 无兜底：写后立刻读到旧值的概率（L 中位数 120ms）==")
for read_window in (200.0, 1000.0):
    stale = sum(1 for l in lag if rnd.uniform(0, read_window) < l) / N
    print(f"读发生在写后 0~{read_window:.0f}ms：旧读概率 {stale:.1%}")

lag.sort()
print("\n== 3. 读己之写的粘性窗口：W(epsilon) = L 的 1-epsilon 分位 ==")
windows = {}
for eps in (0.05, 0.01, 0.001):
    w = pct(lag, 1 - eps) / 1000.0
    windows[eps] = w
    print(f"容忍失败率 {eps:.1%} -> 写后 {w * 1000:.0f}ms 内的读必须走主库")

w1 = windows[0.01]
print(f"\n== 4. 窗口 W={w1 * 1000:.0f}ms 的代价（读窗口 1s，本机仿真）==")
residual = sum(1 for l in lag if (d := rnd.uniform(0, 1000.0)) > w1 * 1000 and l > d) / N
print(f"残留旧读概率 {residual:.2%}（兜底前见第 2 节 1s 窗口）")
for rate in (0.1, 0.5, 2.0):
    ratio = 1 - math.exp(-rate * w1)
    print(f"写速率 {rate}/s/会话 -> 读主比例 {ratio:.1%}（公式 1-e^(-r*W)）")

print("\n== 5. 三种复制模式：写延迟与旧读窗口（3 副本，N=200000 次写）==")
print(f"{'模式':<4} | {'L中位数':>8} | {'写p50':>8} | {'写p99':>9} | {'旧读窗口':<12} | 200ms旧读")
for median in (10.0, 100.0, 1000.0):
    mins, maxs = [], []
    for _ in range(N):
        a, b, c = log_lag(median), log_lag(median), log_lag(median)
        mins.append(min(a, b, c))
        maxs.append(max(a, b, c))
    mins.sort()
    maxs.sort()
    stale200 = sum(1 for _ in range(N) if log_lag(median) > 200.0) / N
    rows = [
        ("异步", 1.0, 1.0, f"=L({median:.0f}ms)", stale200),
        ("半同步", pct(mins, 0.5), pct(mins, 0.99), f"=L({median:.0f}ms)", stale200),
        ("全同步", pct(maxs, 0.5), pct(maxs, 0.99), "0（回放后）", 0.0),
    ]
    for name, p50, p99, win, stale in rows:
        print(f"{name:<4} | {median:>6.0f}ms | {p50:>6.1f}ms | {p99:>7.1f}ms | {win:<12} | {stale:>8.1%}")

print("\n== 6. 尾部参数 sigma 的影响（中位数同为 120ms）==")
for sigma, xs in ((0.8, lag), (0.35, sorted(log_lag(120.0, 0.35) for _ in range(N)))):
    print(f"sigma={sigma}: W(1%) = {pct(xs, 0.99) / 1.0:.0f}ms")
```


脚本里最容易被忽略的参数是 **σ（尾部）**：中位数同为 120ms，σ = 0.8 时 99 分位窗口是 769ms，σ = 0.35 时只要 270ms——**同一句“复制延迟 120ms”，需要的兜底窗口差 2.8 倍**。所以监控只看平均延迟不够，必须看 p99。

### 三种兜底的成本与边界

「三种读己之写实现」那张表给的是**做法**；同一份延迟分布下，这里只算**代价**：

| 兜底 | 主库读比例 | 额外延迟 | 适用边界 | 失效场景 |
|---|---|---|---|---|
| 写后读主（时间窗 T） | `1 - e^(-r_w·T)`；r_w = 0.5 写/s、T = 769ms → **31.9%** | 主库 RTT − 副本 RTT | 会话状态可存（网关/本地），写频率低 | T < P99(L) 就漏；多实例共享会话丢状态即失效 |
| 粘性会话 | 粘主库 100%；粘随机副本 0%，但只保单调读 | 0 | 负载均衡支持一致性哈希、会话不漂移 | 扩缩容或故障重分配即失效；写走主时不解决“读己之写” |
| 版本号校验 | ≈ 0（仅落后副本繁忙时回退读主） | 等副本追上的时间，p99 由 L 尾部决定（769ms 量级） | 写返回值能透传版本、副本有回放位点 | 跨分片/跨地域版本不可比、缓存层不看版本、令牌丢失 |

「三种读己之写实现」那张表里的**会话粘性**默认指“粘到主库，或粘到写后已追上的副本”；只随机粘一个普通副本，保证的是单调读，读己之写仍会失败——这是它最常被误用的地方。

注意 `1 - e^(-r_w·T)` 的假设：读在时间轴上均匀到达。如果读总是紧跟写（典型用户操作流），比例会趋近 100%，兜底退化成“全读主”——那就该换版本号校验。本机仿真里，写速率从 0.1 写/s 涨到 2 写/s，同一个 769ms 窗口的读主比例从 7.4% 涨到 78.5%，**成本差 10 倍**。所以顺序是：先量会话写速率，再定窗口，最后才谈“读主扛不扛得住”。

> 🔑 **兜底窗口按分位数定，不按均值定**；兜底方式按“能接受多少主库读”选，不按“哪种实现更简单”选。

## 反模式

| 反模式 | 后果 |
|---|---|
| 写完立刻读从库，且不处理 | 用户看到 “刚改的没生效”，投诉 |
| 用 “复制延迟很小” 当理由 | 高峰期延迟变大，问题在高峰暴露 |
| 只做主从，不做会话一致性 | 60% 级别的陈旧读（见实测） |
| 用 “读主库” 解决所有读 | 主库压力翻倍，扩展性丢失 |
| 副本切换后不校验版本 | 单调读被破坏，用户看到 “回退” |
| 不监控复制延迟 | 不知道窗口有多长，无法设阈值 |

## 三条铁律

> 🔑 **先声明一致性级别**，再选实现；“最终一致” 也要写进契约。

> 🔑 **读己之写靠会话/版本**，不靠 “延迟很小”。

> 🔑 **复制延迟要监控**；它是 “陈旧窗口” 的唯一度量。

## 自检

**Q1** 为什么 “写完立刻读” 会读到旧值，而且概率这么高？

▸ 答案：因为异步复制的延迟窗口（本例 120ms）覆盖了 “写后读” 的时间范围（0–200ms）：只要读发生在 “主库已提交、备库还没重放” 的窗口里，就会读到旧值。实测 60% 正是这个窗口与读时间的重叠比例。

**Q2** “读己之写” 与 “强一致” 的区别？

▸ 答案：强一致要求**所有读者**都看到最新值；读己之写只要求**写的人自己**看到。前者成本高（多数派读/读主），后者可以用 “会话粘性/版本等待” 低成本实现。多数业务真正需要的是后者。

**Q3** 版本等待怎么实现？

▸ 答案：写成功时返回一个**版本号/位点**（如 LSN、GTID 或单调递增的版本），客户端后续读带上它；副本在 “已重放到 ≥ 该版本” 前不返回（等待或报错重试）。这样既不总是读主，也保证 “至少看到自己写的”。

**Q4** 为什么 “单调读” 也需要设计？

▸ 答案：因为多副本延迟不同：第一次读副本 A（较新）、第二次读副本 B（较旧），用户会看到 “数据回退”。单调读要求 “同一会话的读版本不倒退”，实现方式是 “绑定副本” 或 “记录已读版本，低于它的结果不接受”。

**Q5** 复制延迟多少算 “可接受”？

▸ 答案：取决于业务：**读己之写**要求窗口内能兜住（如 < 1s）；**报表/分析**可以分钟级；**资金/库存**通常不能容忍，必须读主或用共识。没有统一阈值，必须按 “读到旧值的后果” 定。

**Q6** 主库压力大，又不能接受陈旧读，怎么办？

▸ 答案：三条：**读写分离只用于可容忍陈旧的查询**（列表、详情可缓存）；**关键读走主库**（按接口分级）；**用共识/同步复制**（代价是写延迟）。先按业务分级，再决定哪类读必须强一致。

**Q7** 怎么衡量 “读一致性有没有做好”？

▸ 答案：两个指标：**陈旧读比例**（采样：写后读，比对版本）与 **P99 复制延迟**。前者告诉你 “用户是否真的看到旧值”，后者告诉你 “窗口有多长”。只看延迟不看陈旧读，容易自我感觉良好。
