# 18.5 故障检测与切换

## 一句话

> 切换 = **检测 + 决策 + 执行**（提升 + fence + 改路由）；检测的每一个 “更快” 都换来 “更多误判”：超时 100ms 时误判 13.6%，250ms 时 0.7%——选哪档，取决于 “误切的代价” 与 “停服的代价” 谁更大。

## 切换的四个动作

| 动作 | 做什么 | 失败后果 |
|---|---|---|
| 检测 | 心跳超时 / 健康检查 / 副本延迟 | 误判 → 不必要的切换 |
| 决策 | 谁当新主（多数派/优先级） | 选错 → 数据丢失或双主 |
| 提升（promote） | 备库停止重放、开启写入 | 未追平 → 丢最后一段 |
| **fence 旧主** | 阻止旧主继续写 | 没做 → 脑裂 |
| 改路由 | 客户端/DNS/VIP 指向新主 | 缓存 → 部分客户端仍打旧主 |

关键：**“提升” 不等于 “切换完成”**，最后两步（fence + 改路由）才决定是否真的安全。

## 实测：检测超时 vs 误判

3 副本、心跳 RTT 均值 50ms（重尾）、2 万次采样：

| 检测超时 | 误判率 | 真故障发现延迟 |
|---|---|---|
| 100ms（2×均值） | **13.61%** | ≈100ms |
| 250ms（5×均值） | **0.70%** | ≈250ms |

13.6% 的误判意味着：**每 7 次 “检测到故障”，就有 1 次是误判**——如果自动切换，就会频繁 “无故切主”，比不切更糟。

```text
切换代价 = 误判率 × 每次误切的代价（中断 + 脑裂风险）
         + 检测延迟 × 真故障的停机成本
选点：让两者之和最小，而不是“越快越好”
```

## 代码：一次安全切换的最小步骤

```bash
# 1) 确认备库已追平（位点差 < 阈值）
psql -c "SELECT client_addr, pg_wal_lsn_diff(sent_lsn, replay_lsn) FROM pg_stat_replication;"
# 2) 提升
pg_ctl promote -D /data/pg
# 3) fence 旧主（比“杀掉”更可靠：撤销其写入权限）
pg_ctl stop -m immediate -D /data/pg || true
# 4) 改路由（DNS/VIP/连接串），并让客户端刷新连接池
kubectl patch svc db -p '{"spec":{"selector":{"role":"primary"}}}'
```

判据：**第 1 步不达标就不许提升**（宁可不切，不可丢数据）；**第 3 步不可省**（旧主复活会写入）。

## 心跳超时与误判率

**结论**：超时不按 “RTT 均值的几倍” 拍，按 “每小时允许几次误报” 反算：`T = H + J·ln(1800/(H_s·F))`。误报对超时余量**指数敏感**——余量每多一个抖动尺度 J，误报除以 e；检测延迟则等于 “超时 − 死亡时距上次心跳已过的时长”，均值 ≈ `T − H/2`。两个公式一起，才能回答 “心跳周期与超时先调哪个”。

前面的 “检测超时 vs 误判” 只改了超时 T；这里把**心跳周期 H** 也放进来，因为工程上真正能省的是 H，不是 T。两套仿真的参数标定不同（前者按 RTT 均值 50ms，这里按 H=500ms、抖动 J=100ms），只比趋势、不比绝对值。

### 模型：误判与延迟各一个公式

节点每 H 毫秒发一条心跳；单程延迟 `d = 1ms + Exp(均值 J)`，用指数分布制造 “多数很快、偶发很慢” 的重尾抖动（对应 GC 停顿与排队）。检测器在 “距上一条心跳到达 > T” 时判定疑似失联。

- **误判**：节点活着，但相邻两条心跳的到达间隔 `H + d_i − d_{i−1} > T`。两个指数分布之差是拉普拉斯分布，上尾 `P(>x) = 0.5·e^(−x/J)`，于是余量 `m = T − H` 对应单次误判率 `p ≈ 0.5·e^(−m/J)`。
- **误报频次**：一秒 `1000/H` 次判定，`F = (3600/H_s)·p`；反解即得上面的超时公式。
- **检测延迟**：节点在两次心跳之间随机死亡，`age ~ U(0,H)`；判定发生在 “距上次心跳满 T” 时，所以 `延迟 = T − age ∈ [T−H, T]`，均值 `T − H/2`。

方向是相反的：**T 调大**，误报指数下降、检测变慢；**H 调小**，检测的量化误差 H/2 变小，但心跳数与每小时误报机会都按 1/H 上升。不存在 “一起调小就更好”。

系数 0.5 不是拍的：两条独立延迟之差落在正半轴的概率是一半，拉普拉斯上尾因此带 0.5；换成 “抖动有界” 的均匀分布，同样的余量会得到完全不同的 p——所以公式不是普适常量，而是 “把线上测得的抖动分布代进去” 的模板。J 用指数分布还隐含了 “抖动之间独立” 的假设；真实拥塞有自相关，连续多条心跳一起变慢，实际误报会比公式高，参数要留余量。

```go
// 误判：节点活着，但两条心跳的到达间隔 H + d_i − d_{i−1} > T
late := 0
for i := 0; i < trials; i++ {
    dPrev, dCur := 1+expSample(r, j), 1+expSample(r, j) // 单程延迟 = 1ms + Exp(J)
    interval := h + dCur - dPrev
    if interval > t {
        late++
    }
}
pFalse = float64(late) / trials
faPerHour = (3600 / (h / 1000)) * pFalse // 每小时误报次数

// 检测延迟：死亡时刻随机落在两次心跳之间，age ~ U(0,H)
lat := make([]float64, 2_000_000)
for i := range lat {
    age := r.Float64() * h
    lat[i] = math.Max(0, t-age) // 距上次心跳满 T 才判定
}
```

本机仿真（`go1.27.1 / darwin/arm64 / Apple M1`；完整程序 `.cache/pilot2-18.5/main.go`，`go run main.go`；每组 2000 万次采样，原始输出 `.cache/pilot2-18.5/raw.txt`）：

读数：

- 700ms（1.4H）：每次心跳误判 6.76%，每小时 486 次——自动切主会被抖动拖进 “切了又切”。
- 1000ms（2H）：3.38e-3、每小时 24.3 次，检测延迟 750ms。
- 2000ms（4H）：1.50e-7、每小时 0.001 次，检测延迟 1.75s。
- 超时从 1.4H 提到 2H（只多等 300ms），误报降 20 倍；再翻倍到 4H，再降 2.2 万倍——余量正好是 2J、5J、15J，指数关系不是巧合。
- 误判率必须带时间单位：“每次心跳 1.50e-7” 与 “每小时 0.001 次” 是同一件事，按条算和按小时算差 7200 倍。

### 心跳周期：先动哪个旋钮

固定余量 500ms（5J）只改 H，误判率恒为 3.38e-3：H 从 1000ms 降到 200ms，检测延迟从 1000ms 降到 600ms（省的是 H/2 量化误差），代价是心跳消息与每小时误报都变成 5 倍。因此顺序是：**先按带宽预算定 H，再按误报预算定 T**。想更快发现故障时，缩短 H 不动误判率；缩短 T 会同时抬高误判率——后者是拿准确性换速度。

### 判据：超时该设多长

| 场景 | 抖动 J | 心跳周期 H | 目标误报/小时 | 建议超时 T | 检测延迟均值 |
|---|---|---|---|---|---|
| 同机房自动切主 | 20ms | 200ms | 10 | 336ms | 236ms |
| 跨可用区自动切主 | 100ms | 500ms | 1 | 1319ms | 1069ms |
| 跨地域（人工闸门） | 300ms | 1000ms | 0.1 | 3939ms | 3439ms |
| 只告警、不摘除 | 300ms | 1000ms | 10 | 2558ms | 2058ms |
| STONITH 自动断电 | 150ms | 500ms | 0.01 | 2419ms | 2169ms |

用法是反算，不是查表：给定 H、J 与目标 F，代 `T = H + J·ln(1800/(H_s·F))`。三个可直接记住的推论：误报预算收紧 100 倍，超时只需加 `J·ln100 ≈ 4.6J`（跨可用区那行把目标从 1 次/小时收到 0.01 次/小时，T 从 1319ms 只涨到 1779ms）；目标误报从 10 降到 0.1（“只告警” → “人工闸门”）在 J=300ms 时多等 1.38s；J 翻倍比 H 翻倍更贵，跨地域的 J 是主项，缩短 H 几乎不改善检测延迟（延迟 ≈ J·ln(…) + H/2，前者占大头）。表里的前提是抖动平稳、心跳独立、检测连续；真实网络有突发拥塞，上线前要按突发窗口再抬一档。

F 不是技术参数，是业务参数：自动切一次主，代价 ≈ 30s 中断 + 客户端重连风暴 + 可能的数据核对。若业务只接受 “每月最多误切 1 次”，则 `F = 1/730 ≈ 0.00137 次/小时`；代入 H=500ms、J=100ms 得 `T ≈ 500 + 100×ln(2.63e6) ≈ 1978ms`，检测延迟均值约 1.73s——这才是 “误切代价 → 超时” 的完整链路。换成 “每天最多 1 次”，F=0.0417，T 降到约 1637ms，检测快 0.34s，代价是误报预算放大 30 倍。

去抖是另一条正交手段：要求 “连续 k 次超时才确认”，检测延迟增加约 `(k−1)·H`，误报显著下降——按独立近似 `p²` 估算，T=2H 那组会从 24.3 次/小时降到约 0.08 次/小时，但它只是**上界**：相邻两个判定区间共享同一条延迟样本，真值要用带自相关的抖动重算，不能直接抄 p²。去抖适合误切代价极高、又不愿把 T 拉长的场景；与 “直接拉长 T” 谁划算，得拿 `(k−1)·H` 的额外延迟和 T 增长换来的误报下降逐项比。多观察者则相反会放大：M 个副本各自独立检测、任一方报警即触发时，集群级误报约为 `M×p`。

### 与 18.6 的边界

检测器只产出 “疑似”：多久怀疑、怀疑多少次，由上面的误报预算决定；怀疑错了能不能兜住，取决于 [18.6 脑裂与防护](18.6-脑裂与防护.md) 的 quorum 与 fencing。两者独立：超时调得再准，也替代不了 fencing（旧主假死仍能写）；fencing 做得再好，也挡不住超时太短导致的频繁误切——误切伤可用性，漏 fence 伤数据。本节判据管 “多久怀疑”，18.6 管 “怀疑错了如何不扩大”。

> 🔑 超时按 “每小时误报预算” 反算，不按 RTT 倍数拍。

> 🔑 误报率必须带时间单位：1.50e-7/条心跳 = 0.001 次/小时。

> 🔑 想更快发现故障，先缩小 H；最后一个才动 T，因为 T 同时买速度与误判。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只做 “提升”，不做 fence 与改路由 | 旧主继续写 → 脑裂/双写 |
| 未追平就提升 | 丢失最后一批已提交事务 |
| 自动切换不设 “冷却期” | 抖动时反复切换，雪崩 |
| 检测只依赖单一路径（单心跳） | 网络抖动即误判 |
| 切换后不校验数据一致性 | 悄悄丢数据，很久后才发现 |
| 没有回切方案 | 新主有问题只能硬扛 |

## 三条铁律

> 🔑 **提升前必须确认追平**；宁可不切，不可丢数据。

> 🔑 **fence 旧主是切换的一半**；不做等于制造双主。

> 🔑 **自动切换要有冷却与人工闸门**，避免抖动放大。

## 自检

**Q1** 为什么 “检测越快” 不一定越好？

▸ 答案：因为快检测必然用更短超时，而短超时把 “慢” 判成 “死” 的概率更高（实测 100ms 超时误判 13.6%）。误切会带来中断、脑裂风险与客户端重连风暴，代价可能高于 “多等 150ms”。要按 “误判代价 vs 停机代价” 选点。

**Q2** 为什么 “追平” 是提升的前置条件？

▸ 答案：因为备库可能落后于主库（异步复制）。未追平就提升，意味着**主库已提交但备库没收到的数据永久丢失**（RPO 受损）。所以切换流程必须是 “先等位点差 < 阈值，再提升”，否则就是拿数据换速度。

**Q3** fence 旧主为什么比 “直接杀进程” 更可靠？

▸ 答案：因为进程可能 “假死”（网络分区、GC 停顿）：你以为杀了，其实它还在跑并继续写。fence 是**从外部撤销其写权限**（存储侧 token、VIP 摘除、只读挂载），即使进程活着也写不进去——这是防双主的最后一道闸。

**Q4** 自动切换的 “冷却期” 解决什么？

▸ 答案：解决**抖动放大**：网络抖动导致误判 → 切换 → 新主又抖 → 再切，形成雪崩。冷却期（如 5 分钟内不再自动切）给人工介入与状态稳定的时间，避免 “越切越坏”。

**Q5** 切换后最先验证什么？

▸ 答案：三件事：**数据位点**（新主是否包含最后已提交事务）、**写入可用**（应用能写、无只读锁）、**旧主已 fence**（无法再写）。前两个决定 “能不能用”，第三个决定 “会不会分叉”。

**Q6** 什么时候该 “人工切换” 而不是自动？

▸ 答案：当 **误判代价高、或状态判断复杂** 时：跨地域切换（网络分区难判定）、多副本一致性要求高（需确认多数派）、有明显 “抖动史” 的链路。人工切换慢，但不会因误判制造更大事故。

**Q7** 如何演练一次切换而不影响生产？

▸ 答案：三条：**影子环境**做全流程（含 fence 与改路由）、**生产只读演练**（切到备库只读，验证连接与延迟）、**混沌工程**注入 “主库失联” 看监控与自动化反应（见 [56.2 故障演练](../../L5-工程效能/56-稳定性工程/56.2-故障演练.md)）。
