                18.6 脑裂与防护

                一句话

                脑裂就是 “两个节点都以为自己是主”：分区期间各自接受写入，恢复后数据分叉；防护只有三条——quorum（没有多数派不许写）、fencing（旧主写不进去）、单点仲裁，缺一条都不算防住。

                实测：没有 quorum 会发生什么

                3 节点分成 2+1 两个分区：

                策略 接受写入 分歧 key
                无 quorum 300 条（两边都写） 100 个
                有 quorum（多数派才可写） 200 条（少数派拒绝） 0 个

                差别不在 “写入多少”，而在 “恢复后要不要人工合并”：300 条里有 100 个 key 出现两个值，合并意味着要么丢数据、要么人工裁决。quorum 用 “暂时不可用” 换 “永不冲突”。

                可写条件：节点数 ≥ ⌈(N+1)/2⌉
3 节点 → 至少 2 个；5 节点 → 至少 3 个
少数派分区：只读或拒绝写（取决于业务能否容忍）

                三道防线

                防线 做法 防住什么
                quorum 写前确认多数派在线 分区时少数派不能写
                fencing 存储侧只接受 “最新 token” 的写 旧主复活后写不进去
                仲裁者（witness） 第 3 个轻量节点参与投票 2 节点集群避免 1:1 平票
                // 写入前校验：拿不到多数派就拒绝（宁可不可用，不可分叉）
if len(alive) < (n+1)/2 {
    return ErrNoQuorum          // 客户端应降级为只读
}
// 存储侧：只接受更大的 token（防旧主）
if token < lastToken { return ErrStaleOwner }

                切换演练：fencing 检查单与一次故障注入

                演练要证明的不是 “切过去能写”，而是旧主切完就写不进去。做法是把故障主动注入：先让旧主“假死”，再提升新主，最后恢复网络，看旧主那几秒的写落到哪。整场演练的通过线只有一个——旧主的写被存储层拒绝，而不是“旧主自己停了”。

                切换前逐项打勾的 10 项检查单

                # 检查项 怎么查 通过判据
                1 旧主写权限 SELECT pg_is_in_recovery()；MySQL 看 @@read_only 与账号授权 旧主只能读，没有绕过只读的写路径
                2 token / epoch 切换脚本里 epoch 是否先 +1 再提升 旧主写返回 ErrStaleOwner，不是“未知错误”
                3 共享存储锁 etcdctl get --prefix /locks/，看持有者与租约 旧主的锁租约已过期且不可续
                4 VIP / 路由 ip -br addr、DNS TTL、网关后端列表 旧主已从上游摘除，TTL ≤ 30s
                5 客户端连接 连接串是否写死旧主 IP；连接池是否绕过 VIP 100% 实例走 VIP，重连后无旧主连接
                6 仲裁者 etcdctl endpoint status；witness 是否在线 3 节点里 2 个、5 节点里 3 个可投票
                7 脑裂检测 双主告警是否配置、阈值多少 两个“我是主”同时出现时 10s 内告警
                8 数据回滚预案 分区窗口怎么定界、有没有操作日志 能按时间窗圈出差异 key
                9 演练记录 时间线、每步判据、失败点与负责人 每条判据有通过 / 不通过 + 证据
                10 监控口径 客户端成功率与服务端 commit 成功率是否同时采 两者差值 > 0 才是“假双主”的有效信号

                第 2 项不通过，演练只能算“切换演练”：分叉没有任何东西拦得住，换个名字而已。顺序也有讲究：1–3 管存储侧（见效慢，但不可绕过），4–5 管入口侧（见效快，但会漏掉直连），6–7 管检测侧（决定分叉能暴露多快）。入口侧做得再干净，也替代不了存储侧的 token 校验。

                三种仲裁 / 防护方案：可用性、成本、误杀

                方案 分区时的可用性 成本 误杀风险
                多数派（quorum） 3 节点容忍 1 台故障；少数派只读或拒写 至少 3 节点 + 跨故障域部署 低：误判只造成不可用，不产生分叉
                外部锁（etcd / ZK 租约） 锁服务自身也要 3 节点，否则变成新单点 一套协调集群 + 每次切换 1 个 RTT 中：租约判断错就是两个持有者，必须靠 fencing 兜底
                STONITH（带外断电） 取决于 BMC / PDU 管理网；旧主被硬断电 每主机一条管理网 + 可编程 PDU 高：18.5 故障检测与切换 的 0.70% 误判率会直接变成“杀错机器”

                三者不是三选一，而是三层：多数派定“谁有资格”，外部锁定“谁在持锁”，STONITH 保证“机器真的停了”。但只有 fencing 回答“旧主还能不能写”——它不依赖旧主配合，也不依赖机器是否断电。

                🔑 租约到期 ≠ 写不进去：租约是旧主自己的纪律，会被 STW 暂停；fencing 是存储层的纪律，只认 token。租约机制本身见 21.11 领导者租约。

                故障注入：旧主恢复写入被拒的两种实现

                模型：3 节点，A 为旧主，持 T=10s 租约、token=1；t=10 注入分区，A 无法续约；t=11 B/C 达到多数派，提升 B 并把存储层 epoch 升到 2；A 的业务连接没断，每秒写一笔（+100 元），本地租约检查被 STW 拖到 t=13 才停写。两种存储层只差一行判断：到达即接受，或 token < epoch 就拒绝。

                #!/usr/bin/env python3
"""本机仿真：一次切换里旧主的「重复写」次数——无 fencing vs 有 fencing。"""
import unicodedata

LEASE_TTL, PROMOTE, T_END, TOKEN_NEW = 10, 11, 20, 2
A_STOP = LEASE_TTL + 3          # 租约到期后，本地检查还被 STW 拖了 3 秒


def w(s):                       # 终端显示宽度：中文按 2 列算
    return sum(2 if unicodedata.east_asian_width(c) in "WF" else 1 for c in s)


def pad(s, n):
    return s + " " * (n - w(s))


def simulate(name, fencing, epoch_bump_at=PROMOTE):
    r = {"name": name, "sent": 0, "accepted": 0, "rejected": 0, "dup": []}
    epoch, b_keys = 1, set()
    for t in range(1, T_END + 1):
        if t == epoch_bump_at:
            epoch = TOKEN_NEW                     # 先递增 epoch，再允许新主写
        if t >= PROMOTE:                          # 新主每秒写一笔
            b_keys.add(f"k_{t}")
        if t <= A_STOP:                           # 旧主在停写前每秒也写一笔
            r["sent"] += 1
            if fencing and 1 < epoch:             # 旧主 token=1，存储层只认 2
                r["rejected"] += 1
            else:
                r["accepted"] += 1
                if f"k_{t}" in b_keys:            # 新主已写过同一个 key
                    r["dup"].append(f"k_{t}")
    return r


rows = [
    simulate("无 fencing（到达即接受）", fencing=False),
    simulate("有 fencing（先 +token 再提升）", fencing=True),
    simulate("有 fencing（顺序写反：先提升）", fencing=True, epoch_bump_at=12),
]
COLS = [("实现", 30), ("旧主写请求", 10), ("被接受", 8), ("被拒", 6),
        ("重复写次数", 10), ("重复的 key", 18), ("重复入账", 8)]
print("  ".join(pad(c, n) for c, n in COLS))
for r in rows:
    dup = len(r["dup"])
    cells = [r["name"], r["sent"], r["accepted"], r["rejected"],
             dup, ",".join(r["dup"]) or "—", f"{dup * 100} 元"]
    print("  ".join(pad(str(c), n) for c, (_, n) in zip(cells, COLS)))

overlap = A_STOP - PROMOTE + 1           # 新主可写 与 旧主仍在写 的重叠秒数
print(f"\n校验：重叠窗口 = A_STOP({A_STOP}) - PROMOTE({PROMOTE}) + 1 = {overlap} 秒")
print(f"      无 fencing 的重复写应等于重叠窗口：{len(rows[0]['dup'])}")
assert len(rows[0]["dup"]) == overlap
assert len(rows[1]["dup"]) == 0 and len(rows[2]["dup"]) == 1
print("断言全部通过（3 行结果可复算）")

                读数：无 fencing 时 3 个 key 各被两个主写过，恢复后就是 3 笔重复入账（300 元）；有 fencing 时旧主 10 笔合法写之外全部被拒，重复写 0。第三行是演练最该抓的 bug：先提升、后 +token，旧主在中间那一秒仍是“合法主”，于是挤进 1 笔——fencing 的顺序比 fencing 本身更容易写错。

                把模型里的“每秒 1 笔”换成真实速率，这个窗口的代价立刻变大：一张 5,000 TPS 的热表，3 秒重叠窗口就是 15,000 笔分叉写；按每笔 100 元算，是 150 万元的待对账差额。窗口每多 1 秒，多 5,000 笔。

                演练五步：每步的判据

                阶段 动作 判据
                ① 注入网络分区 在旧主侧 DROP 到新主 / 仲裁者的复制与心跳端口（如 5432、2380），持续 90s 旧主心跳在检测超时后 1 个周期内告警；旧主仍能本地写（故意保留）
                ② 观察 同时看双主告警、客户端成功率、服务端 commit 成功率 双主告警 ≤ 10s 触发；两个成功率差值 > 0 = 假双主信号
                ③ 切换 token +1 → 存储层生效 → 提升新主 → 改 VIP/DNS → 客户端重连 旧主写返回 ErrStaleOwner；新主可写；VIP 收敛 ≤ 1 个 TTL
                ④ 恢复 撤销分区，旧主降级为从库，比对位点与分叉 key 旧主写 100% 被拒；分叉 key 数 = 0，对照组（无 fencing）= 3
                ⑤ 复盘 时间线 + 每步判据 + 改进项 每条判据有“通过 / 不通过 + 证据”，改进项有负责人与期限

                第 ④ 步故意保留无 fencing 的对照组：让参演的人亲眼看到 3 条重复写落进去。只跑通过版本，演练就变成了演示。

                演练最常失败的四件事：

                失败点 表现 后果
                只堵心跳端口 复制端口还通，旧主的写仍被复制到新主 看起来“分区了”，实际没隔离
                观察只看服务端 服务端 commit 正常，客户端却拿到假成功 假双主被整个漏掉
                恢复太早 还没确认旧主写不进就撤分区 合并过程中旧主继续制造新分叉
                复盘不闭环 记录写了，没人认领改进项 下次演练重复同一个失败

                反模式

                反模式 后果
                异步复制 + 自动切换，无 quorum 分区时双主，数据分叉
                只有 quorum，没有 fencing 旧主 “复活” 后仍能写（假死场景）
                2 节点集群无仲裁 1:1 平票，谁都选不出主
                少数派继续接受写 恢复后必须人工合并，通常丢数据
                用 “心跳恢复” 判断 “可以合并” 心跳恢复 ≠ 数据一致
                不做双主检测告警 分叉可能持续很久才被发现

                三条铁律

                🔑 没有多数派就不许写；可用性让位于一致性。

                🔑 fencing 是最后一道闸；quorum 挡不住 “假死复活”。

                🔑 双主是事故，不是配置；发现即告警、即止血。

                自检

                Q1 为什么 “两边都能写” 比 “少数派只读” 更糟？

                ▸ 答案：因为两边都能写会产生同一 key 的两个值，恢复后无法自动判定谁对——要么丢数据、要么人工裁决。少数派只读只是 “暂时不可用”，恢复后数据仍然一致。前者是数据事故，后者是可用性事故。

                Q2 有 quorum 就一定不会脑裂吗？

                ▸ 答案：不一定：quorum 只保证 “同一时刻只有一个多数派”，但如果旧主 “假死”（进程还在、网络分区），它可能仍持有写权限并继续写存储——这就要靠 fencing（存储侧拒绝旧 token）。quorum 防 “选主冲突”，fencing 防 “旧主写入”。

                Q3 2 节点集群为什么需要仲裁者？

                ▸ 答案：因为 2 节点在分区时是 1:1，没有多数派，谁都不能写（或两边都写，取决于配置）。加一个轻量 witness（不存数据、只投票）后变成 3 节点，多数派为 2，可以在 “一主一从 + witness” 侧继续服务。

                Q4 “假死” 场景下，光有 quorum 为什么不够？

                ▸ 答案：因为假死的节点可能仍能访问共享存储（网络分区只影响心跳，不影响存储路径）。它以为自己还是主，继续写；新主也在写 → 分叉。fencing（存储侧 token/租约）能让它的写失败，这才是根治。

                Q5 少数派应该 “只读” 还是 “完全拒绝”？

                ▸ 答案：看业务：只读能保住查询可用性（但可能读到旧值）；完全拒绝更安全但影响更大。金融类通常拒绝写、允许有限只读；内容类可以只读。无论哪种，都要在文档里写清 “分区期间的降级行为”。

                Q6 如何发现已经发生脑裂？

                ▸ 答案：三个信号：双主告警（两个节点都报 “我是主”）、数据校验不一致（同一 key 两个版本/时间戳）、复制冲突（双向复制报冲突）。发现后第一步是止血（停掉一方写入），再谈合并。

                Q7 脑裂恢复后怎么合并数据？

                ▸ 答案：按业务语义：有唯一键/版本号的（如订单号 + 单调版本）按版本取新；计数器类用 CRDT 合并（见 25.6 CRDT (计数 / 集合 / 寄存器)）；金额/库存必须人工对账，不能自动 “取一个”。自动合并只适用于可证明可交换的结构。
