# 21.13 PBFT：三阶段、视图切换与 `2f+1` 的用处

## 一句话

> PBFT 把拜占庭容错落成三个阶段：**pre-prepare 定序、prepare 确认同一视图内没人反对、commit 确认 “多数派已准备执行”**；第三阶段不是仪式，而是让视图切换后的新主，能从 `2f+1` 份证词里恢复出 “已经提交到哪”。

## 角色、假设与四个数字

| 角色 | 干什么 | 数量 |
|---|---|---|
| **primary（主）** | 给请求分配序号、发起 pre-prepare | 1 个 |
| **backup（备）** | 校验、发 prepare/commit、执行 | `n-1` 个 |
| **replica（副本）** | primary 与 backup 的统称 | `n` 个 |
| **client** | 发请求、等 `f+1` 个相同回复 | 任意 |

| 数字 | 值 | 用途 |
|---|---|---|
| 副本总数 `n` | `3f+1` | 容忍 `f` 个任意行为节点 |
| quorum | `2f+1` | prepare / commit / view-change 的通过门槛 |
| 每请求延迟 | 约 3 个 RTT | pre-prepare → prepare → commit |
| 每请求消息 | 渐近 `2n²` | `n=4` 时逐项精算 28 条 |

前提只有两条：**消息认证**（签名或 MAC，能确认发送者、能发现篡改）和 **弱同步**（超过某个未知时刻 GST 后，消息延迟有上界）。安全性不依赖同步；**活性依赖 GST**，这一点与 [22.4 部分同步模型](../22-故障模型与理论边界/22.4-部分同步模型.md) 完全相同。

## 三阶段各做什么

| 阶段 | 谁发 | 消息内容 | 收到什么才算过 | 达到的状态 |
|---|---|---|---|---|
| **pre-prepare** | primary | `⟨v, n, d(m)⟩` + 请求 `m` | 视图号一致、序号在水线内、`(v,n)` 没被别的摘要占用 | 请求被**定序** |
| **prepare** | 每个 backup | `⟨PREPARE, v, n, d(m), i⟩` | 自己 + `2f` 个不同副本的 prepare 摘要一致 | **prepared**（本视图内该序号只可能是这个请求） |
| **commit** | 每个副本 | `⟨COMMIT, v, n, d(m), i⟩` | 自己 + `2f` 个 commit | **committed-local**，可以执行并回复 |
| **view-change** | 怀疑主的 backup | `⟨VIEW-CHANGE, v+1, h, C, P⟩` | 新主收到 `2f+1` 份 | 进入新视图，恢复未完成请求 |

三个校验点，每一个都对应一类攻击：

| 校验 | 防的是什么 |
|---|---|
| `d(m)` 与请求内容一致 | 主偷偷换掉请求体（同序号不同内容） |
| `(v,n)` 只能对应一个摘要 | 主对不同的备发不同的请求（equivocation） |
| 序号在 `[h, H]` 水线内 | 主用超大序号把日志撑爆，或逼备无限缓存 |

`prepared` 与 `committed` 的区别是全节的关键：

- **prepared** 只说明 “在本视图 `v` 内，序号 `n` 绑定了这个请求”；
- **committed-local** 才说明 “多数派已经确认 prepared，这个请求不会再被换掉”。

> 🔑 只有 `committed-local` 之后才能回复客户端。提前回复等于把 “可能被回滚” 的结果告诉用户——这正是很多自研 BFT 实现最常犯的错。

## 为什么必须是三阶段

先看两阶段会漏什么。假设只保留 pre-prepare + prepare：

1. 请求 `m` 在视图 `v` 被 `2f+1` 个副本 prepared；
2. 但还没有任何副本执行/回复，主挂了；
3. 视图切换到 `v+1`，新主收集 `2f+1` 份 view-change。

此时 `m` 处于 “prepared 但未 commit” 的灰色状态。丢不丢它，取决于新主看到什么：

| 新主看到的证词 | 处理 | 结果 |
|---|---|---|
| 没有任何副本 prepared | 丢弃 `m` | 安全（客户端本来也没收到回复） |
| 有副本 prepared 且已执行 | 必须继承 `m` | 若新主不知道，就会丢已提交请求 |

两阶段的问题就在第二行：**“已执行” 这件事没有留下一个能被新主读到的多数派证据**。commit 阶段补的正是这个证据：副本执行前，先让 `2f+1` 个副本留下 commit 记录。于是：

```
commit 的 quorum：2f+1
view-change 的 quorum：2f+1
两者交集 ≥ (2f+1) + (2f+1) - (3f+1) = f+1 ≥ 1
→ 新主必然遇到至少一个“知道已提交”的诚实副本
```

这条不等式不是修辞，可以直接穷举验证。完整代码在仓库 [tools/examples/21.13-pbft/](../../../tools/examples/21.13-pbft/README.md)，`go run .` 可复现。

本机实测（macOS，Apple M1，Go 1.27.1）：

```text
=== 任意两个 quorum 的最小交集 ===
n    q    最小交集     可不相交       场景
4    3    2        false      任意两组必相交
7    5    3        false      任意两组必相交
4    2    0        true       反例 [0 1] 与 [2 3] 完全不相交
3    2    1        false      任意两组必相交

=== 视图切换：新主必须拿到哪些证据 ===
  n=4 f=1：commit quorum=[0 1 2]，view-change quorum=[1 2 3]
  交集=[1 2]（2 个），其中至少 1 个诚实 → 新主必能学到该请求
  ✓ 交集 ≥ f+1，满足 PBFT 的跨视图安全条件
```

这段检查的核心就是一个穷举：

```go
// 枚举所有大小为 q 的集合，返回最小交集、是否可不相交，以及一对反例
func check(n, q int) (int, bool, []int, []int) {
	ss := subsets(n, q)
	min, disjoint := q, false
	var d1, d2 []int
	for i := 0; i < len(ss); i++ {
		for j := i + 1; j < len(ss); j++ {
			c := intersect(ss[i], ss[j])
			if c < min {
				min = c
			}
			if c == 0 && !disjoint {
				disjoint, d1, d2 = true, ss[i], ss[j]
			}
		}
	}
	return min, disjoint, d1, d2
}
```

第三行是反面教材：`n=4` 却把 quorum 设成 `f+1=2`（照抄崩溃模型的多数派），两个 quorum 可以完全不相交——两个主各自凑齐 2 票，各自提交，双写就发生了。

有人会问：那 Zyzzyva 这类 “两阶段” 协议怎么解释？它们不是 “白省一阶段”，而是**把第三阶段的确认责任转移给了客户端**（客户端参与收集回复、确认后才算提交），前提是客户端参与、且无故障时走快速路径。省掉的阶段没有消失，只是换了承担者。

## 视图切换：换主时到底交换什么

| 步骤 | 谁做 | 关键内容 |
|---|---|---|
| ① 超时 | backup | 一段时间内没等到 primary 的请求，怀疑主失效 |
| ② 发 view-change | backup → 所有副本 | 新视图号 `v+1`、最新稳定 checkpoint `h`、`2f+1` 份 checkpoint 证明 `C`、所有 prepared 证书 `P` |
| ③ 收齐 | 新 primary | 收到 `2f+1` 份 view-change，才算有资格当主 |
| ④ 发 new-view | 新 primary → 所有副本 | 选最大的 `h`，把所有 `P` 里的请求按序号重放，进入 `v+1` |

两个容易忽略的机制：

- **checkpoint 与水线**：每执行 `K` 个序号（PBFT 论文取 100）做一次 checkpoint，`2f+1` 个副本确认后成为 “稳定 checkpoint”；水线 `[h, h+L]`（`L` 常取 200）限制主能分配的序号范围，防止日志无限增长。
- **view-change 是 `O(n²)`**：每份 view-change 都带着 `O(n)` 个 prepared 证书，新主再广播 `O(n²)` 的 new-view。节点一多，换主成本比正常路径高一个数量级——这就是 PBFT 集群通常只有 4–16 个节点的原因。

| 视图切换的失败模式 | 表现 | 对策 |
|---|---|---|
| 假超时 | 主只是慢，却被反复换掉 | 超时按 P99 × 2 设，配合退避 |
| 新主作恶 | 选择性丢弃 prepared 请求 | 新主必须广播 new-view，备可校验 `P` 的完整性 |
| quorum 不足 | 分区后两边都凑不齐 `2f+1` | 停止服务（保安全），不要降级凑数 |
| 水线失守 | 主分配超大序号，备缓存爆掉 | 严格校验 `[h, H]`，超界直接拒绝 |

## 工程上怎么用

| 产品 / 协议 | 特点 | 适用 |
|---|---|---|
| **BFT-SMaRt** | 研究级、Java、PBFT 完整实现 | 教学、原型、联盟链 PoC |
| **Tendermint / CometBFT** | 三阶段 + 轮次（round）推进，`+2/3` 投票 | Cosmos 生态、联盟链 |
| **HotStuff / DiemBFT** | 线性视图切换（`O(n)` 而不是 `O(n²)`），流水线 | 大规模 BFT、需要频繁换主 |
| **Hyperledger Fabric** | orderer 可选 Raft 或 BFT，按通道隔离 | 企业联盟链 |

选型只问三句：

1. **参与方互不信任吗？** 否 → 用 Raft，别付 `3f+1` 的钱（见 [21.12 共识算法对比](21.12-共识算法对比.md)）；
2. **需要频繁换主吗？** 是 → 看 HotStuff 类线性视图切换，不要用经典 PBFT；
3. **规模会超过 16 个节点吗？** 会 → `O(n²)` 的消息量会先于共识成为瓶颈，考虑分层或分片。

> ⚠️ 落地时最容易被忽略的不是算法，是**密钥与超时**：签名密钥轮换期间新旧密钥并存，会导致验签失败被当成拜占庭节点；超时设得太短，换主风暴比故障本身更伤可用性。

## 反模式

| 反模式 | 后果 |
|---|---|
| 收到 prepare 就执行并回复 | 视图切换后结果被回滚，客户端看到 “成功又消失” |
| 把 quorum 设成 `f+1` | 两个 quorum 可不相交，双主提交 |
| 忽略 `(v,n)` 的唯一性校验 | 主对不同的备发不同请求，同一序号两个值 |
| 不做 checkpoint，只靠日志 | 日志无限增长，恢复时间随运行时长线性上升 |
| 换主后不重放 prepared 请求 | 已 prepared 的请求被静默丢弃，客户端超时重试放大流量 |
| 在内部可信域上 PBFT | 为不存在的敌人付 3 倍副本与 `O(n²)` 消息 |
| 把 “能识别叛徒” 当成交付目标 | 识别不是共识的必要条件，安全性与活性才是 |

## 自检

**Q1** prepared 与 committed-local 差在哪？为什么不能提前回复客户端？

▸ 答案：prepared 只保证 “本视图内该序号绑定这个请求”，视图切换后仍可能被替换；committed-local 表示已收到 `2f+1` 个 commit，跨视图也不会被推翻。提前回复会把可能回滚的结果告诉用户。

**Q2** 为什么 commit 阶段也必须 `2f+1`，而不是 `f+1`？

▸ 答案：commit 的作用是给 “已提交” 留下多数派证据。只有 `2f+1` 才能保证与 view-change 的 `2f+1` 必交 `f+1`，从而让新主至少遇到一个知道该请求已提交的诚实副本。

**Q3** `n=4, f=1` 时，为什么 quorum 不能是 2？

▸ 答案：`2q - n = 0`，两个大小为 2 的集合可以完全不相交（如 `{0,1}` 与 `{2,3}`）。两个主各自凑 2 票就能各自提交，双写发生。

**Q4** 视图切换为什么比正常路径贵？贵多少？

▸ 答案：每份 view-change 带 `O(n)` 个 prepared 证书，新主再广播 `O(n²)` 的 new-view；经典 PBFT 换主是 `O(n²)` 消息、多个 RTT，比正常路径高一个数量级。HotStuff 用线性视图切换把这部分降到 `O(n)`。

**Q5** PBFT 的活性依赖什么假设？不满足会怎样？

▸ 答案：依赖弱同步（GST 之后消息延迟有界）。完全异步时无法区分 “主慢” 与 “主死”，换主可能永远选不出新主，活性丢失但安全性不受影响。

**Q6** 什么情况下应该直接用 Raft，而不是 PBFT？

▸ 答案：参与方属于同一信任域、故障模型是崩溃而非拜占庭时。Raft 用 `2f+1` 副本、`O(n)` 消息、1 个 RTT，成本和复杂度都低得多；PBFT 的额外成本只在 “节点可能作恶” 时才有回报。
