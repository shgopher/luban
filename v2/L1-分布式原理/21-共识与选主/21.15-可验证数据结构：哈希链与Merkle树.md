# 21.15 可验证数据结构：哈希链与 Merkle 树

## 一句话

> 哈希链让「改一处必须重算后面全部」——改动可检测，且成本随被改位置之后的块数**线性上升**；Merkle 树把一整个集合压成一个 32 字节的根，让「证明某项在集合里」从 **O(n) 降到 O(log n)**；两者都只解决「数据有没有被改」，不解决「谁有权写」——后者是共识（[21.14](21.14-PoW与中本聪共识.md)）的事。

**来源**：链式哈希、Merkle Root 构造、UTXO 记账，来自陈皓《左耳听风》第 63、64 讲（2018）；本节把书里两处已有用法（[3.5 审计与取证](../../需求/3-行业合规与外部约束/3.5-审计与取证.md) 的哈希链、[18.1 复制模型](../18-数据复制/18.1-复制模型-单主-多主-无主.md) 的 Merkle 反熵）收进同一张对照表；代码与实测为新增（[tools/examples/21.15-merkle](../../../tools/examples/21.15-merkle/README.md)）。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 「哈希不可逆，所以哈希链防篡改」 | 不可逆只保证**不能从哈希反推原文**，不保证不能改。改一块只需重算它之后所有块的哈希——重算本身很便宜，**贵的是让网络接受这条新链**，那要靠共识 |
| 「Merkle 树是为了省存储」 | 存储反而多了一层中间节点（n 个叶 + n-1 个内部节点）。它省的是**验证时传输的数据量**：证明一笔交易在不在块里，只需 `log2(n)` 个兄弟哈希，不必重传整块 |
| 「UTXO 是更先进的余额」 | 是另一种**账本范式**：没有余额、只有未花费输出。换来并行与无状态，代价是费解、不利应用开发——以太坊因此改回余额 |

## 一、哈希链：把「改动成本」写进结构

哈希链的构造只有一行：

```text
id₀ = H(data₀)
idᵢ = H(dataᵢ ‖ idᵢ₋₁)      // 本块 ID 由「本块数据 + 前块 ID」一起算出
```

| 性质 | 怎么来的 | 边界 |
|---|---|---|
| 内容一变 ID 就变 | SHA-256 的雪崩效应：一个 bit 不同，输出面目全非 | 只说明**能检测**，不说明不能改 |
| 一处改、处处改 | ID 里含前块 ID → 前块变则本块 ID 变 → 指向它的块也得改 | 连锁效应让「改动面」变大，不是让改动不可能 |
| 越旧的块越安全 | 改得越靠前，要重算的后继块越多 | 越新的块越容易被改，见 [21.14](21.14-PoW与中本聪共识.md) 的确认数 |

把「改哪一块要重算多少」算清楚，就知道安全性为什么随深度单调上升：

| 改哪一块 | 要重算的哈希 | 成本 |
|---|---|---|
| 最新一块 | 1 个 | 最低 |
| 第 i 块（链共 L 块） | 它自己 + 后面 `L-i` 块 = `L-i+1` 个 | 随深度**线性**上升 |
| 创世块 | 全部 L 个 | 最高 |

> 🔑 哈希链给的是**「可检测 + 有连锁成本」**，不是「不可修改」。真正把改造成本抬到「几乎不可能」的是工作量证明：重算完还得赢过全网的算力竞争（[21.14](21.14-PoW与中本聪共识.md)）。所以光有链不够——这是很多「区块链科普」漏掉的一步。

## 二、Merkle 树：把一个集合压成一个根

构造分三层，两两合并直到只剩一个：

| 层 | 内容 | 节点数（n 为 2 的幂） |
|---|---|---|
| 叶子 | 每笔交易的 SHA-256 | n |
| 中间 | 相邻两个摘要拼接后再哈希 | n/2、n/4、… |
| 根（Merkle Root） | 唯一的 32 字节摘要 | 1 |

四笔交易 A、B、C、D 走一遍：`Hash(A)` 与 `Hash(B)` 合成 `Hash(AB)`，`Hash(C)` 与 `Hash(D)` 合成 `Hash(CD)`，最后 `Hash(AB ‖ CD)` 就是 Merkle Root。**拼接顺序不可交换**：左在前、右在后，交换一下根就完全不同。

```go
// 完整实现见 tools/examples/21.15-merkle/main.go
for len(level) > 1 {                 // 逐层向上，直到只剩根
	next := make([][]byte, 0, (len(level)+1)/2)
	for i := 0; i < len(level); i += 2 {
		r := i + 1
		if r == len(level) {
			r = i                    // 奇数个：最后一个与自己配对
		}
		next = append(next, hashPair(level[i], level[r]))
	}
	level = next
}
```

完整代码在仓库 [tools/examples/21.15-merkle](../../../tools/examples/21.15-merkle/README.md)，`go run .` 可复现。本机实测（go1.27.1，Apple M1）：

```text
交易数 8，树高 4 层（含根）
merkle root = 00c44ac866986502024c56baf8a3fd1f010819c810c62746b0e85601039a478c
第 3 笔交易的证明路径长度 = 3 个哈希
篡改后 root = 4eb4b144c1d221df87422648a4bcc6160b4c2550fe7ec5c914acfa323a01bd25
检测到篡改 = true
每层变化的节点数 = [1 1 1 1]（对照：叶子总数 8）
```

读法：8 个叶子 → 4 层 → 证明路径 3 个哈希 = `log2(8)`；改一笔交易，每层只有 1 个节点变，**共 4 个哈希**，而不是 8 个叶子全部重算。这就是 `O(log n)` 与 `O(n)` 的差别。

同一个结构在书里已经出现三次，但每次都在解决不同的问题——这张表把三处缝起来：

| 用途 | 用链还是树 | 证明什么 | 一次校验要传/算多少 | 主场 |
|---|---|---|---|---|
| **审计日志防篡改** | 哈希链（每条带 `prev_hash`） | 第 k 条之后没有被改过 | 从改动点往后重算整条链 | [3.5 审计与取证](../../需求/3-行业合规与外部约束/3.5-审计与取证.md) |
| **反熵找副本差异** | Merkle 树（按 key 区间分片建树） | 哪个分片的数据不一致 | 只沿不一致的分支下钻，`O(log n)` 次比较 | [18.1 复制模型](../18-数据复制/18.1-复制模型-单主-多主-无主.md) |
| **区块对交易集合做承诺** | Merkle 树（一笔交易一个叶） | 某笔交易在不在这个块里 | 根 + `log2(n)` 个兄弟哈希 | [21.14](21.14-PoW与中本聪共识.md) |

> 🔑 三者共用一个判据：**把大对象压成小指纹，让「不一致」在小指纹上先暴露**。区别只在形状——链管「时间上的连续」，树管「集合内的成员」。

## 三、UTXO vs 账户余额：两种账本范式

比特币没有「余额」这个概念，只有一堆**未花费的交易输出（UTXO）**。Alice 收到 Fred 的 2 个币、Ted 的 3 个币，她不是「有 5 个币」，而是**持有两笔没花出去的 output**。要转给 Bob 4 个，不能把 2 和 3 拆开，只能把两笔都当 input，output 写成「Bob 4 个 + 自己找零 1 个」——input 与 output 总数必须吻合。

| 维度 | UTXO | 账户余额 |
|---|---|---|
| 记账单位 | 一笔笔未花费的输出 | 每个账户一个数字 |
| 「我有多少钱」 | 遍历我的 UTXO 求和 | 直接读余额字段 |
| 转账 | 选若干 input，凑出 output + 找零 | 扣减一个数、增加一个数 |
| 并发 | 多个 UTXO 可并行花，**不需要并行锁** | 同一账户的并发写要加锁或串行化 |
| 状态 | **无状态**：余额是算出来的 | 有状态：余额要持久化维护 |
| 匿名性 | 较强：可通过多个 output 隐藏去向 | 较弱：账户与身份绑定 |
| 开发友好度 | 费解，不利于应用开发 | 直观，合约与业务好写 |

> 🔑 这不是「币圈常识」，是两种可迁移的建模选择：**UTXO = 事件账本**（每笔都是不可变的「钱从哪来、到哪去」，余额是投影）；**余额 = 状态账本**（每次覆盖一个数，历史要靠流水）。选哪种看你要「并行 + 可审计」还是「易用 + 好查询」，账户模型与复式记账的关系见 [67.4 复式记账与账务模型](../../L4-组件与技术/67-交易与账务/67.4-复式记账与账务模型.md)。

## 反模式

| 反模式 | 后果 |
|---|---|
| 以为「上了哈希链就防篡改」 | 攻击者重算一条更长的链即可；没有共识，链只是一份自证的历史 |
| 把 Merkle 根当成「交易摘要」单独存 | 根是**整个集合**的承诺，改一笔交易根就变；脱离树单独存根，无法定位是哪笔变了 |
| 拼接左右子节点时顺序随意 | 交换顺序得到不同的根，两套实现永远对不上 |
| 用余额模型硬套「可并行、无状态」的场景 | 同一账户的并发扣减必须加锁，吞吐被单点锁住 |
| 用 UTXO 模型做需要频繁查余额的业务 | 每次查询都要遍历 UTXO，应用层复杂度陡增 |
| 审计日志只存哈希、不存 `prev_hash` | 单条记录被替换无法发现，链断不了 |

## 自检

**Q1** 只改链上**最后一块**，和改**创世块**，成本差在哪？为什么说「越旧的块越安全」？

▸ 答案：改最后一块只需重算 1 个哈希；改创世块要重算它之后的全部 L 个哈希。成本随「被改位置之后还剩多少块」线性上升，所以越靠前的块改动面越大、越安全。但要注意：**重算本身不贵**，真正贵的是重算后还要让网络接受这条新链——那是共识要解决的问题。

**Q2** 既然可以直接把「全部交易拼起来做一次哈希」，为什么还要 Merkle 树？

▸ 答案：一次哈希只能回答「整批数据变没变」，答不了「**哪一笔**变了」，也无法在不传输全部交易的前提下证明「某一笔在集合里」。Merkle 树把证明成本降到 `log2(n)` 个兄弟哈希，并且能沿不一致的分支逐层下钻定位到具体交易——这两点是审计、反熵、轻节点验证都需要的。

**Q3** 哈希链和 Merkle 树都只保证「能检测到改」，那「不可篡改」靠什么？

▸ 答案：靠**让改造成本高于收益**：哈希链提供连锁成本，共识（PoW 的算力、PoS 的质押）把「重写历史」的代价抬到经济上不划算。所以「不可篡改」是经济学结论，不是密码学结论；没有共识的哈希链，只是「改完能被发现」。

**Q4** Alice 持有 2 币和 3 币两个 UTXO，要付给 Bob 4 币。这笔交易的 input / output 各是什么？

▸ 答案：input = 那两笔 UTXO（2 + 3 = 5）；output = 给 Bob 4 币 + 给自己找零 1 币（还要给矿工小费的话从找零里再扣）。input 与 output 总额必须相等，且每个 output 只能对应一个来源——这就是「没有余额」带来的写法：钱不能被「拆开」，只能整笔进、拆开出。

**Q5** 为什么审计日志用哈希链、副本反熵用 Merkle 树，两者不能互换？

▸ 答案：审计要回答的是「**按时间排列的记录有没有被抽掉或改掉一条**」，链的 `prev_hash` 正好把顺序钉死；副本反熵要回答的是「**两个副本的 key 集合哪里不一样**」，这是集合成员问题，树能把比较成本从全量降到 `O(log n)`。换成树做审计会丢掉「顺序」这个承诺，换成链做反熵则每次都要全量比对。

**Q6** 一个系统宣称「我们用 Merkle 树存证，所以数据绝对安全」。这句话缺了哪两件事？

▸ 答案：缺 ① **谁持有根、根本身可信吗**（根要锚定到共识、可信时间戳或第三方，否则攻击者可以连根一起换）；② **谁能写入**（Merkle 只保证内容与根对应，不保证写入者有权写，权限要靠签名与准入）。两者都不在数据结构里，而在数据结构之外。
