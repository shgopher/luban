# 分布式技术全景 · 纲领

## 一句话

> 全书八十多章里，分布式只回答四类调度问题——**监控、资源与服务、数据、流量**；每一格都有 “必须守住的不变量 + 必须付的代价”，章节是格子的展开，不是并列的知识点。

## 为什么先读这一页

v2 按 L0–L5 分层：越往下越接近物理定律，越往上越接近业务与组织。好处是每层边界清楚；坏处是**组件看起来像并列的知识点**——Kafka、Redis、K8s、etcd 摆在一起，读者容易记住 “有什么”，却说不清 “为什么需要”。

这张图给三个用途：

| 用途 | 怎么用 |
|---|---|
| **定位** | 读任何一节前，先问：它在四格的哪一格？ |
| **查漏** | 四格 × 五条主线 = 20 个交叉点，逐个问 “我们这儿谁负责” |
| **排障** | 故障时按 “监控 → 流量 → 资源 → 数据” 的顺序查，不靠猜 |

## 四象限：所有分布式问题落在这四格

| 格子 | 回答什么问题 | 失败长什么样 | 必须守住的不变量 | 主场章节 |
|---|---|---|---|---|
| **全栈监控** | 出问题怎么知道、怎么定位 | MTTD 以小时计、告警风暴、事后才知道 | 每请求有 `trace_id`、每组件有指标、每告警有 runbook | [50 可观测性](../L4-组件与技术/50-可观测性/0-概论.md)、[35.2 SLO](../L3-质量属性/35-可用性/35.2-SLA-SLO-SLI-错误预算.md)、[56 稳定性工程](../L5-工程效能/56-稳定性工程/0-概论.md) |
| **资源与服务调度** | 进程放哪、谁先跑、何时扩缩 | 雪崩、热点节点、OOM、排队 | 申请 = 限制、有优先级与配额、有抢占与回退 | [12 集群调度](../L0-运行时底座/12-集群资源调度/0-概论.md)、[7.5 调度与亲和性](../L0-运行时底座/7-容器编排/7.5-调度与亲和性.md)、[35.8 故障隔离](../L3-质量属性/35-可用性/35.8-故障隔离.md)、[37.6 弹性伸缩](../L3-质量属性/37-扩展性/37.6-弹性伸缩.md) |
| **数据调度** | 数据放哪、存几份、怎么一致 | 丢数据、读旧值、双写冲突、分片倾斜 | 副本 × 故障域、`W+R>N`、分区键基数与热点 | [16 一致性](./16-一致性模型/0-概论.md)–[19 分区](./19-数据分区/0-概论.md)、[24 分布式事务](./24-分布式事务/0-概论.md)、[44 数据库](../L4-组件与技术/44-数据库/0-概论.md) |
| **流量调度** | 请求怎么进、怎么分、打满怎么办 | 过载、惊群、跨域延迟、灰度事故 | 超时预算、重试上限、限流在被保护侧、灰度可回退 | [8 网络](../L0-运行时底座/8-网络/0-概论.md)、[35.5 超时重试](../L3-质量属性/35-可用性/35.5-超时重试与退避.md)–[35.7 限流](../L3-质量属性/35-可用性/35.7-限流.md)、[47 网关](../L4-组件与技术/47-网关与入口/0-概论.md)、[55 发布与回滚](../L5-工程效能/55-发布与回滚/0-概论.md) |

> 🔑 四格不是四个团队，而是**四种预算**：监控买 “知道得多快”，资源买 “扛得住多少”，数据买 “错得多少次”，流量买 “进得来多少”。预算有限时，先保监控与流量——它们决定故障是 5 分钟还是 5 小时。

## L0–L5 各层回答什么

| 层 | 回答的问题 | 明确不管 | 章节 |
|---|---|---|---|
| **L0 运行时底座** | 单机与集群能提供哪些原语 | 业务语义 | 5–15 |
| **L1 分布式原理** | 什么做不到（物理定律） | 具体产品与参数 | 16–25 |
| **L2 架构风格** | 系统怎么切、怎么连 | 调优细节 | 26–33 |
| **L3 质量属性** | 做到什么程度、付多少代价 | 组件选型 | 34–40 |
| **L4 组件与技术** | 用什么产品、怎么配 | 业务建模 | 41–76 |
| **L5 工程效能** | 怎么持续交付与治理 | 运行时行为 | 51–59 |

> 💡 读法：**L1 决定 “能不能”，L3 决定 “值不值”，L4 决定 “用什么”，L5 决定 “怎么长期不烂”**。跳过 L1 直接背组件，面试能过、故障时抓瞎。

## 排障顺序：和建系统顺序相反

建系统是 “需求 → 架构 → 组件 → 流量 → 数据 → 监控”；排障必须倒过来：

| 步 | 看什么 | 常见结论 |
|---|---|---|
| ① 监控 | 错误率、P99、饱和度、变更时间点 | 故障是 “突然” 还是 “渐变”，范围是单实例还是全站 |
| ② 流量 | 入口 QPS、重试放大、灰度批次、超时预算 | 是不是一次发布 / 一次重试风暴 / 一个热点 |
| ③ 资源 | 节点、Pod、连接池、线程池、队列长度 | 是 “被打满” 还是 “自己泄漏” |
| ④ 数据 | 主从延迟、锁等待、慢查询、分片热点 | 前四步都正常时才轮到数据 |

> 🔑 多数 “分布式疑难” 在前两步就能定位。直接跳去查数据，通常是在用数据库解释一个流量问题。

## 常见误解

| 误区 | 现实 |
|---|---|
| “上了 K8s / 微服务就高可用” | 可用性来自冗余、隔离与快速失败；编排只让隔离变便宜 |
| “监控是最后补的” | 监控是唯一能缩短 “故障时长” 的格子，应该最先建 |
| “一致性是全局开关” | 一致性的粒度是 “一个操作 / 一个 key / 一个事务”，同系统可以分级 |
| “加机器就能扩容” | 写瓶颈在单点或单分区时，加机器只增加排队 |
| “抄大厂架构就对了” | 大厂的约束（规模、团队、预算）与你不同，架构是约束的解，不是答案 |

## 自检

**Q1** 一个接口 P99 从 50ms 涨到 2s，按四格顺序你先看哪三个数？

▸ 答案：① 监控：错误率与延迟曲线、最近一次变更；② 流量：入口 QPS 与重试量、是否灰度中；③ 资源：CPU/连接池/队列是否饱和。三步都排除后才查数据（锁、慢查询、主从延迟）。

**Q2** 为什么 “限流” 放在网关不够？

▸ 答案：网关只覆盖南北向入口；东西向调用不过网关。保护服务自身容量必须在被保护侧（服务端）做，否则 N 个调用方实例各自放行，合起来仍能打挂下游（见 [30.4 服务治理](../L2-架构风格/30-微服务/30.4-服务治理.md)）。

**Q3** 3 副本跨 3 个 AZ 与 3 副本同机房，哪个更可靠？为什么？

▸ 答案：跨 3 AZ。副本数买的是 “独立故障” 容忍度，副本分布买的是 “相关故障” 容忍度；同机房一次断电就让 3 个 “独立” 副本同时失效（见 [22.1 故障类型](./22-故障模型与理论边界/22.1-故障类型.md)）。

**Q4** 什么情况下 “加机器” 没有用？

▸ 答案：瓶颈在单点（单主库、单分区、单 key）、在串行资源（全局锁、单线程队列）、或在跨地域 RTT 上时。加机器只加并行度，加不了单点吞吐，也缩短不了 RTT。

**Q5** 这张图和 CAP 是什么关系？

▸ 答案：CAP 属于 “数据调度” 格的一条边界，不是全图。四格里只有数据调度直接受 CAP/PACELC 约束；监控、资源、流量各有自己的预算（MTTD、容量、RTT），不能被 CAP 解释。
