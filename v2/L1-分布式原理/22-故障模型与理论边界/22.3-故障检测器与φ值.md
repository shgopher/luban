# 22.3 故障检测器与 φ 值

## 一句话

> 故障检测器不可能又 “快” 又 “准”：**超时越短检测越快、误判越多**；φ accrual 把 “二值猜疑（死/活）” 换成 “连续怀疑度”，让上层按风险做决策，而不是被一个魔数超时绑架。

## 四种检测器（按能力分）

| 类型 | 保证 | 能否误判 | 典型实现 |
|---|---|---|---|
| **完美（P）** | 死了必报、活着不报 | 不能 | 同步系统 + 完美信道 |
| **最终完美（◇P）** | 最终不误判 | 中途可以误判 | 大多数超时检测器 |
| **强（S）** | 死了必报，活着的可能被报死 | 可以 | 广播心跳 |
| **最终弱（◇S）** | 最终能报出失败者 | 可以 | gossip/φ accrual |

关键：**实际系统都用 ◇P/◇S**——因为 “最终” 是最弱但可实现的要求；能否落地，取决于 “误判多久能纠正”。

## 实测：超时倍数与误判率（100 节点，RTT 均值 50ms 的重尾分布）

| 超时 | 误判率 | 平均检测延迟 |
|---|---|---|
| 2× 均值（100ms） | **13.63%** | 150ms |
| 3× 均值（150ms） | **5.05%** | 199ms |
| 5× 均值（250ms） | **0.66%** | 297ms |

这组数字是 “故障检测器的本质权衡”：**把误判从 13.6% 压到 0.66%，代价是检测延迟从 150ms 涨到 297ms**。没有 “又准又快” 的参数，只有 “按业务选一个点”。

```text
误判的代价 = 不必要的切主/迁移/告警
漏检的代价 = 请求打到死节点、延迟堆积
选择依据：哪一侧更贵
```

## φ accrual：把超时变成概率

```text
φ(t) = -log10(P(心跳间隔 ≥ t | 节点正常))
φ = 1  → 约 10% 把握“它还没死”
φ = 8  → 约 1e-8，几乎可以断定死亡
φ = 12 → 1e-12，通常作为“确认死亡”阈值
```

```go
// 简化实现：滑动窗口估计心跳间隔分布，输出 φ
func (d *Detector) Phi(elapsed time.Duration) float64 {
    p := d.window.Survival(elapsed)   // P(间隔 > elapsed | 正常)
    if p <= 0 { return math.Inf(1) }
    return -math.Log10(p)
}
// 上层策略：φ > 8 报警，φ > 12 摘除节点，而不是 timeout=3s 一刀切
```

好处：不同节点、不同网络条件下**同一个 φ 阈值含义一致**；坏处是需要估计分布（样本少时不准）。

## φ 值怎么算、阈值怎么定

**结论**：φ 的公式只有一行——`φ(t) = −log10(Q((t−μ)/σ))`；难的是 μ/σ 怎么估、阈值拿什么标定。阈值别按 “φ=8 就是 1e-8” 定，按 “每小时允许几次误报” 反推。本机重尾心跳下，φ=8 的名义误判（1e-8）与真实误判（2.51e-4）差约 2.5 万倍——**φ 的数值只能当排序与门限，不能当概率读**。

前文给了 φ 的定义与 8/12 两个常用档位；这里把它落成可运行算法，并回答 “阈值凭什么定”。

### 三步算出一个 φ

1. **估分布**：滑窗或 EWMA 保存最近若条心跳间隔，算均值 μ 与标准差 σ。
2. **算尾概率**：`z=(t−μ)/σ`，`P(间隔>t | 正常) ≈ Q(z) = 0.5·erfc(z/√2)`，`φ = −log10(Q(z))`。
3. **反解阈值**：φ 对 t 单调，二分求 `t_φ`；φ=3/8/12 对应 z=3.090/5.612/7.034（本机数值反解）。

```go
func upperTail(z float64) float64 { return 0.5 * math.Erfc(z/math.Sqrt2) }

// φ accrual：把「距上次心跳已过 t 毫秒」映射成怀疑度
func phi(t, mu, sigma float64) float64 {
    p := upperTail((t - mu) / sigma)
    if p <= 0 {
        return math.Inf(1)
    }
    return -math.Log10(p)
}

// 反解 φ(t)=target：φ 对 t 单调，二分即可
func timeAtPhi(target, mu, sigma float64) float64 {
    lo, hi := 0.0, mu+40*sigma
    for i := 0; i < 200; i++ {
        mid := (lo + hi) / 2
        if phi(mid, mu, sigma) < target {
            lo = mid
        } else {
            hi = mid
        }
    }
    return hi
}
```

本机仿真（`go1.27.1 / darwin/arm64 / Apple M1`；真实间隔按 LogNormal(中位数 500ms, σ_log=0.3) 生成，误判由 500 万次采样统计）：

```text
样本估计：n=10000  μ=523.6ms  σ=159.5ms（真实分布 LogNormal 中位数 500ms, σ_log=0.3）

φ 随时间（距上一条心跳到达的毫秒数 → 怀疑度）：
t(ms)    500      750      1000     1100     1200     1300     1400     1600     2000
φ(t)     0.25     1.11     2.85     3.82     4.95     6.25     7.71     11.13    19.98

φ 阈值    判定时刻    名义误判 10^-φ    本机 MC 误判率    经验 φ    每小时误报    平均检测延迟

  σ 高估 10%：φ = 6.77（从 8 掉到 6.77）
  μ 高估 10ms：φ = 7.84

```

完整代码在仓库 [tools/examples/22.3-phi/](../../../tools/examples/22.3-phi/README.md)，`go run .` 可复现这段输出。

读数：

- φ 是连续量：t=500ms 才 0.25，t=1200ms 到 4.95，t=1600ms 才 11.13。阈值只是 “在哪一档起疑”。
- **φ=3：每小时 65 次误报**、延迟 766ms——只配做慢节点观察，自动摘除会被噪声淹没。
- **φ=8：每小时 1.8 次**、延迟 1.17s——摘流量会每小时误伤近 2 次。
- **φ=12：每小时 0.24 次**（约 4 小时一次）、延迟 1.4s——才够自动切主的量级。
- 名义误判从 10^-3 到 10^-12 降了 9 个数量级，真实误判只降约 2.4 个数量级（9.07e-3 → 3.38e-5）。原因是心跳间隔长尾：对数正态在 z≈5.6 处仍有 2.5e-4 的尾巴，正态近似把它算成了 1e-8。
- 表的 “经验 φ” 一列最刺眼：同一时刻，按真实分布算只有 2.04/3.60/4.47，名义却是 3/8/12。**同一个 t 在另一套分布里 φ 完全不同，所以 φ 不能跨系统横比绝对值。**

把 φ 反过来用，能直接得到 “阈值该多少”：一次判定机会就是一条心跳，每小时 `3600/H_s` 次；目标误报 F 次/小时，要求单次误判 `p = F·H_s/3600`，于是 `φ_budget = −log10(p) = log10(3600/(F·H_s))`。H=500ms 时：F=10 次/小时 → φ≈2.86；F=1 → 3.86；F=0.01 → 5.86。这个预算只依赖 “心跳频率 + 误报预算”，与分布无关；分布只决定 “要等多久才到那个 φ”。

回头看 “经验 φ” 那一列：把真实误报 0.2434 次/小时代入预算公式，`log10(3600/(0.5×0.2434)) = 4.47`，正好等于表里的 4.47——它不是另一个指标，就是 “你实际买到的 φ”。所以 “设 φ=12” 的真实含义是 “预算按 φ≈4.5 兑现”，差距来自分布假设，不来自公式。想做严格标定，就得按经验分布反解，而不是照抄 8/12 这两个数字。

### 阈值怎么定

| 动作 | φ 阈值 | 本机仿真误报/小时 | 检测延迟均值 | 代价 |
|---|---|---|---|---|
| 只告警、人工看 | 3 | 65.3 | 766ms | 告警噪声大，值班会钝化 |
| 摘流量、保留探测 | 8 | 1.806 | 1169ms | 每小时约 2 次误伤 |
| 自动切主 | 12 | 0.2434 | 1396ms | 约 4 小时一次误切 |

三条落地规则：

1. **用 “每小时误报” 验收，不用 φ 数值验收**：上线后数摘除/切主次数，超预算就加权重或抬阈值；φ=12 本身不保证任何概率。
2. **先检验分布假设**：本机 σ_log=0.3 就让高 φ 失真 4 个数量级。要么在对数空间拟合（等价对数正态），要么直接用经验生存函数算 `φ = −log10(经验 P(间隔>t))`——把 “正态尾” 换成 “经验尾”，阈值才可信。
3. **阈值留余量**：σ 高估 10% 时 φ(8) 从 8 掉到 6.77；μ 偏 ±10ms 时 φ 在 7.84–8.16 间摆动。估计误差会直接挪动判定时刻，别贴着当前观测边界设阈值。

窗口长度是第二个误差源。σ 的相对标准误约 `1/√(2n)`：n=1000 条间隔时约 2.2%，在 φ=8 处（z=5.61、`dφ/dz ≈ z/ln10 ≈ 2.44`）会把 φ 挪约 ±0.3；n=100 条时约 7%，漂移可达 ±1。滑动窗口至少要覆盖几百条心跳；心跳 2 次/秒时 1000 条约 8 分钟，够覆盖一次 GC 抖动周期，又不至于把昨天的网络状态算进来。

检测延迟也别直接用 `t_φ`：节点在两次心跳之间随机死亡，死亡时距上次心跳的年龄 `age ~ U(0,H)`，判定要等 “距上次心跳满 t_φ”，所以 `延迟 = t_φ − age`，均值 `t_φ − H/2`、p99 ≈ `t_φ − 0.01H`。本机 H=500ms，φ=12 的平均延迟 1396ms = 1646 − 250；把 t_φ 当延迟会高估 250ms，这在自动切主的 RTO 预算里不是小数。

实现上还有两个近似要选：**滑窗**（固定 n 条，方差稳、对突发反应慢）与 **EWMA**（指数加权；α=0.1 的有效样本约 `(2−α)/α ≈ 20` 条，正好落在上段 “±1 φ” 的误差区）。工程折中是双窗：短窗（几十条）负责快速抬高 φ，长窗（上千条）负责判定是否越过阈值，两个都过才动作——单窗要么太抖，要么太钝。滑窗的 n 还要覆盖 “最慢一次例行抖动”（如一次 Full GC），否则每次 GC 都会把 σ 拉高、把 φ 压低，检测器在抖动后短暂失明。

恢复期同样要算：心跳一恢复 φ 会瞬间归零，但节点可能刚从停顿里出来、状态未稳。判定逻辑应要求 “连续 m 条心跳正常” 才把它从疑似名单移出（观察期），否则 φ 在阈值附近来回穿越，切主与摘流量会反复触发。φ 只描述 “现在多久没听到”，不描述 “恢复得稳不稳”。

若一定要用 φ 做告警分级，用 “经验 φ” 的分布划档更靠谱：上线先只记录不动作，统计 φ 的 P50/P99，把 “接近历史 P99” 设为观察档、“超出历史最大值” 设为动作档。这等价于按经验分位数标定，比照抄 8/12 稳；代价是要先跑一段观察期，不能开箱即用。

### 与相邻节的边界

[22.4 部分同步模型](22.4-部分同步模型.md) 回答的是 “为什么超时判定只在 GST 之后可靠”；φ 只是把二值超时换成连续怀疑度，不改变 “异步期不可判定” 的本质，GST 不到来时再高的 φ 也可能只是抖动。检测器类型（P/◇P/S/◇S）与前文一致，本节不再重复。

> 🔑 φ 是把 “死没死” 换成 “怀疑度”，不是给出概率真相。

> 🔑 阈值按 “每小时误报预算” 定；φ 数值只用来排序，不能跨系统比绝对值。

## 反模式

| 反模式 | 后果 |
|---|---|
| 全局固定 `timeout=3s` | 跨机房误判、同机房漏检 |
| 用 “一次超时” 就判定死亡 | 抖动导致频繁切主 |
| 不做 “检测延迟” 监控 | 只知道误判，不知道真故障发现得多慢 |
| φ 阈值只调不测 | 数字好看，实际误判未下降 |
| 心跳与业务共用连接 | 业务拥塞 → 心跳超时 → 误判雪崩 |
| 检测器无 “恢复” 路径 | 节点恢复后仍被当死节点，流量回不去 |

## 三条铁律

> 🔑 **检测器是 “概率判断”，不是 “事实”**；上层必须能容忍误判。

> 🔑 **超时/φ 阈值要按 “误判成本 vs 漏检成本” 选**。

> 🔑 **心跳通道与业务通道隔离**，否则拥塞会伪造 “大面积故障”。

## 自检

**Q1** 为什么 “完美检测器” 在异步系统里不存在？

▸ 答案：因为异步模型下 “慢” 与 “死” 不可区分：任何有限超时都可能把 “只是慢” 判成 “死”（误判），而要避免误判就得等无限久（无法检测）。完美检测器需要同步假设（延迟有界）。

**Q2** 实测里 2× 超时的误判率 13.63%，为什么这么高？

▸ 答案：因为 RTT 是**重尾分布**（本实验用指数分布模拟）：少数请求的延迟远超均值，2× 均值（100ms）覆盖不了尾部，于是这些 “只是慢” 的节点被误判。真实网络中跨机房、GC 停顿、重传都会制造长尾。

**Q3** φ 值比固定超时好在哪？

▸ 答案：好在 “**可比较、可解释**”：φ=8 在任何节点上都表示 “约 1e-8 的存活概率”，而 `timeout=3s` 在不同网络下含义完全不同。它把 “调参” 变成 “选风险阈值”，也让上层可以按业务分级（报警 8、摘除 12）。

**Q4** 误判为 “死” 之后，系统会付出什么代价？

▸ 答案：取决于系统动作：**切主**（短暂不可用 + 可能脑裂）、**迁移**（重启、缓存冷启动）、**摘除节点**（容量下降、流量重分布）。误判越频繁，这些动作越频繁，最终表现为 “系统在健康与故障之间反复横跳”。

**Q5** 如何降低 “心跳拥塞 → 误判” 的连锁？

▸ 答案：三条：**独立通道/独立线程**（心跳不排在业务队列后面）、**优先级标记**（DSCP/QoS）、**本地探测 + 多路径**（不要只依赖一条链路）。另外要给心跳留 “抖动预算”，不能按理论 RTT 设超时。

**Q6** 检测器如何做到 “最终正确”？

▸ 答案：靠 “**持续探测 + 状态机**”：节点被怀疑后不立即永久摘除，而是保留探测；一旦恢复心跳，经过 “观察期/半开” 再重新纳入。这样误判是临时的，系统最终收敛到正确状态（◇P 的 “最终”）。

**Q7** 为什么说 “检测器的参数是 SLO 的一部分”？

▸ 答案：因为参数直接决定 “故障发现多快、误判多少”，进而决定可用性与延迟：超时太短 → 误切主；太长 → 请求打到死节点。它应该和 SLO 一起评审，而不是留在某个配置文件里由个人经验决定。
