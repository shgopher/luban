# 22.6 拜占庭将军问题：3f+1 是怎么来的

## 一句话

> 拜占庭问题问的不是 “怎么投票”，而是 “**有人可以说谎时，多少人才够**”：口头消息要 `n ≥ 3m+1`，有签名只要 `n ≥ m+2`；工程上取 `3f+1` 副本配 `2f+1` quorum，是因为**签名只防伪造，不防 “持合法密钥的节点作恶”**。

## 先把故事翻译成系统

`n` 个将军围城，只靠信使通信，其中 `m` 个是叛徒。叛徒可以：不发消息、篡改内容、对不同人报不同的话。目标是——**所有忠诚将军在同一时间发起同一种进攻**，且叛徒不能让他们白送。

| 故事里的东西 | 系统里的对应物 | 关键约束 |
|---|---|---|
| 将军 | 节点 / 副本 | 叛徒 = 任意行为（崩溃、延迟、说谎） |
| 围城 | 一个需要共同决定的状态 | 进攻 / 撤退 = 值 `1` / `0` |
| 信使 | 网络 | 可延迟、可丢失，但**不会凭空造消息** |
| 口头消息 | 可认证来源、不可转发的消息 | 能确认 “谁说的”，不能确认 “他转述的是不是原话” |
| 签名消息 | 非对称签名 / MAC | 可验证内容未被篡改，可转交给第三方 |
| 叛徒 | 拜占庭节点 | 可以冒充、误导、选择性发送 |

要同时满足三条：

| 性质 | 含义 | 违反的后果 |
|---|---|---|
| **一致性 (IC1)** | 所有忠诚节点做出相同决定 | 两个节点一个进攻一个撤退，被各个击破 |
| **有效性 (IC2)** | 指挥官忠诚时，忠诚节点跟随他的命令 | 忠诚指挥官的合理命令被丢弃 |
| **终止性** | 有限步内做出决定 | 永远商量不完，等于没有共识 |

> 🔑 拜占庭共识**不要求 “找出叛徒”**，只要求 “叛徒不能破坏一致”。能定位叛徒是加分项，不是定义的一部分。

## 为什么 `n=3` 不够：两个场景，一个视角

三个将军 A、B、C，最多一个叛徒。看 B 的处境：

| 场景 | A 对 B 说 | C 对 B 说 | B 看到的证据 | B “正确”的动作 |
|---|---|---|---|---|
| **A**：A 忠诚，C 叛徒 | 进攻 | “A 让我告诉你撤退” | `[进攻, 撤退]` | 听 A（进攻） |
| **B**：A 叛徒，C 忠诚 | 进攻 | “A 让我告诉你撤退” | `[进攻, 撤退]` | 不听 A（不能跟着叛徒走） |

**B 在两种场景里收到的消息一模一样**，却要求两个不同的动作。任何确定性算法都只能给同一个答案：要么在场景 A 里违抗忠诚指挥官（破坏 IC2），要么在场景 B 里跟随叛徒（破坏 IC1）。这就是 `n=3, m=1` 无解的全部原因——不是算法不够聪明，是**信息不够**。

`n=4` 就够，因为 B 还能听到 D 的证词，多数派能压过单个叛徒：

| 节点 | 收到的值（自己的 + 其他下属的） | 多数结果 |
|---|---|---|
| 1 | `[1, 1（来自 2）, 0（来自 3，叛徒）]` | `1` |
| 2 | `[1, 1（来自 1）, 0（来自 3，叛徒）]` | `1` |
| 3（叛徒） | 任意 | 不影响忠诚节点的多数 |

把这两个场景跑出来，比画十张图都清楚。下面这段程序实现 `OM(1)`（`m=1` 的口头消息算法），三组配置分别对应 “n=4 能扛”“n=3 扛不住”“指挥官叛变”：

```go
// 指挥官先发值；每个下属再把自己听到的值广播给其他下属；最后各自取多数。
// 叛徒的行为：当指挥官时对奇数编号报反值，当下属时对所有听众报反值。
func (w *world) om1(commander, value int) (map[int]int, int) {
	heard := w.commanderSend(commander, value) // 第一轮：指挥官 → 下属
	msgs := len(heard)
	reports := map[int]map[int]int{}
	for j := 0; j < w.n; j++ { // 第二轮：下属之间互相转述
		if j == commander {
			continue
		}
		reports[j] = w.broadcast(j, commander, heard[j])
		msgs += len(reports[j])
	}
	decisions := map[int]int{}
	for i := 0; i < w.n; i++ { // 第三轮：各自对收到的值取多数
		if i == commander {
			continue
		}
		votes := []int{heard[i]}
		for j := 0; j < w.n; j++ {
			if j == commander || j == i {
				continue
			}
			if v, ok := reports[j][i]; ok {
				votes = append(votes, v)
			}
		}
		decisions[i] = majority(votes)
	}
	return decisions, msgs
}
```

完整代码在仓库 [tools/examples/22.6-byzantine/](../../../tools/examples/22.6-byzantine/README.md)，`go run .` 可复现下面这段输出。

本机实测（macOS，Apple M1，Go 1.27.1）：

```text
=== n=4, m=1：指挥官忠诚，3 号叛徒 ===
  忠诚下属 1 的决策 = 1
  忠诚下属 2 的决策 = 1
  忠诚下属是否一致：true；是否等于指挥官命令 (1)：true；消息数：9

=== n=3, m=1：指挥官忠诚，2 号叛徒 ===
  忠诚下属 1 的决策 = 0
  忠诚下属是否一致：true；是否等于指挥官命令 (1)：false；消息数：4

=== n=3, m=1：指挥官叛徒，对 1 报 1、对 2 报 0 ===
  忠诚下属 1 的决策 = 0
  忠诚下属 2 的决策 = 0
  忠诚下属是否一致：true；是否等于指挥官命令 (1)：false；消息数：4
```

三行输出对应三个结论：

1. `n=4` 时忠诚节点一致，且跟随忠诚指挥官；
2. `n=3` 时忠诚指挥官的 “进攻” 被叛徒搅成 “撤退”——**IC2 被破坏**；
3. `n=3` 且指挥官叛变时，忠诚节点倒是一致了，但一致到错的值上——**IC1 成立、IC2 被破坏**。

> 🔑 第 2、3 组合起来就是 `3m+1` 的证明骨架：同一个节点在两组消息里不可区分，而两组要求的正确动作相反。

## 口头消息算法 `OM(m)`：递归把 “证词” 传下去

Lamport 的 `OM(m)` 只有三步：

| 步 | 谁做 | 做什么 |
|---|---|---|
| ① | 指挥官 | 把值发给每个下属 |
| ② | 每个下属 `i` | 把自己收到的值 `v_i` 当作新命令，以 `i` 为指挥官执行 `OM(m-1)` |
| ③ | 每个下属 | 对第 ② 步里从各个渠道收到的 `n-1` 个值取多数 |

`m=0` 是递归出口：指挥官直接发，下属直接采纳。归纳证明的要点是：**叛徒最多 `m` 个，而每层递归会把 “叛徒数” 减一**，于是到第 `m` 层时所有值都来自忠诚节点，多数派必然正确。

代价在消息数：

| 层级 | 消息数 | 说明 |
|---|---|---|
| `m=1` | `(n-1) + (n-1)(n-2) = (n-1)²` | `n=4` → 9 条，`n=10` → 81 条 |
| 一般 `m` | `O(n^m)` | 递归深度 `m`，每层扇出 `n-1` |
| 延迟 | `m+1` 轮 | 每一轮都要等最慢的信使 |

`OM(m)` 在工程上几乎不可用，原因不是 “理论不优雅”，而是 `n=10, m=3` 就是 `10³` 量级的消息——**为了防 3 个叛徒，先把自己压垮**。

## 签名消息 `SM(m)`：把界降到 `m+2`

一旦消息可以签名，“口头” 的限制就变了：叛徒可以转发别人的签名消息，但**不能伪造**。`SM(m)` 因此简单得多：

1. 指挥官签名后把值发给所有下属；
2. 任何人收到一个**没见过的新签名**，就追加自己的签名再转发给其他人；
3. 每个人收集所有合法签名链，按 “签名数最多 / 值唯一” 决定。

| 维度 | 口头消息 `OM(m)` | 签名消息 `SM(m)` |
|---|---|---|
| 需要副本数 | `n ≥ 3m+1` | `n ≥ m+2` |
| 能否识别叛徒 | 不能（只能绕过） | 能（签名链暴露谁在编造） |
| 消息量 | `O(n^m)` | `O(n²)`（每条消息带一条签名链） |
| 前提 | 消息来源可认证 | 还需要**私钥不泄露** |
| 工程代表 | PBFT 的 prepare/commit | 联盟链的区块签名、Tendermint 的投票签名 |

`n ≥ m+2` 很反直觉：`m=1` 时 3 个节点就够（指挥官 + 2 个下属）？是的，**如果签名绝对不可伪造、且叛徒拿不到别人的私钥**。但这条前提在真实系统里最脆弱：

- 节点被入侵，攻击者**用合法私钥**签名——签名机制完全失效；
- 密钥管理出错（配置下发、KMS 越权），等于把叛徒升级成 “有身份的叛徒”；
- 签名只保证 “内容没被改”，不保证 “内容是真的”。

所以 **PBFT 仍然按 `3f+1` 副本、`2f+1` quorum 设计**，而不是按 `m+2`。它用签名做消息认证与视图切换的证据，但**不把安全性押在 “叛徒没有密钥” 上**（见 [21.13 PBFT](../21-共识与选主/21.13-PBFT.md)）。

## 从 `3f+1` 到 quorum：和 22.1 是同一笔账

拜占庭模型下，任意两个 `2f+1` 的 quorum 必须相交出至少 `f+1` 个节点，其中至少有 1 个诚实：

```
n = 3f+1，q = 2f+1
交集下界 = 2q - n = 2(2f+1) - (3f+1) = f+1 ≥ 1
```

这就是 [22.1 故障类型](22.1-故障类型.md) 里 `3f+1` 的另一种讲法：**副本数不是拍脑袋的 “多备几份”，而是让 “任意两个多数派必有一个诚实节点” 成立的最小整数**。`f=1` 时 4 个副本、3 个才够 quorum；`f=2` 时 7 个副本、5 个才够。

> ⚠️ `n=3f+1` 里的 `f` 是**假设**，不是观测值。真实系统里你无法知道现在有几个叛徒；一旦实际叛徒数超过 `f`，协议不会 “温柔降级”，而是可能停止出块（活性丢失）或在极端情况下破坏安全性。BFT 的 “容错” 是**在假设内**的保证。

## 什么时候值得付这笔钱

| 场景 | 成员是否开放 | 信任假设 | 该用什么 | 副本成本 |
|---|---|---|---|---|
| 公司内网微服务 | 封闭 | 崩溃 | Raft / ZAB，`2f+1` | 3 副本扛 1 个故障 |
| 跨机构对账、联盟链 | 半开放 | 互不信任 | PBFT / Tendermint / HotStuff，`3f+1` | 4 副本扛 1 个叛徒 |
| 公网匿名、无身份 | 全开放 | Sybil 攻击 | PoW / PoS | 算力或质押，不是副本数 |
| 供应链、审计留痕 | 半开放 | 抵赖 | 签名 + 对账，不一定要 BFT | 先上密码学，再谈共识 |

判断只需要问两句：

1. **参与方会不会主动作恶？** 不会 → 崩溃模型，Raft 足够；
2. **成员身份能不能被批量伪造？** 能 → 先解决 Sybil（见 [21.14 PoW 与中本聪共识](../21-共识与选主/21.14-PoW与中本聪共识.md)），BFT 解决不了 “一个人开一万个号”。

> 💡 拜占庭容错最贵的不是副本数，是**视图切换**：换主时要让 `2f+1` 个节点对 “新主是谁、日志到哪” 达成一致，这段窗口通常比正常路径慢一个数量级。这也是 PBFT 类协议集群规模普遍只有 4–16 个节点的原因。

## 反模式

| 反模式 | 后果 |
|---|---|
| 以为 “多复制几份” 就是拜占庭容错 | 3 副本只能扛崩溃；1 个叛徒就能让两个忠诚节点分裂 |
| 上了签名就按 `m+2` 配副本 | 密钥一旦泄露，安全性直接归零，且没有任何降级信号 |
| 在内部可信域用 PBFT | 为不存在的敌人付 3 倍副本、`O(n²)` 消息与视图切换的复杂度 |
| 用 BFT 解决公网 Sybil | 叛徒可以无限开号，`f` 的假设永远被突破 |
| 把 `f` 当成 “实测叛徒数” | 超过 `f` 时协议不保证安全，也不会提前告警 |
| 只测正常路径，不演练视图切换 | 真出故障时卡在换主，可用性比崩溃模型还差 |
| 把 “能识别叛徒” 当成交付目标 | 识别不是共识的必要条件；安全性与活性才是 |

## 自检

**Q1** 用 “不可区分” 解释：为什么 `n=3, m=1` 一定无解？

▸ 答案：构造两个场景——A 忠诚 + C 叛徒，与 A 叛徒 + C 忠诚——让 B 收到完全相同的两条消息。B 的确定性算法对相同输入只能输出相同决定，但两个场景要求的正确动作相反（一个该听 A，一个不该听 A），所以无论怎么选都会违反 IC1 或 IC2。

**Q2** 有签名之后为什么只要 `m+2` 个节点？

▸ 答案：签名让 “转述” 可验证且不可伪造，忠诚节点能把叛徒的伪证直接排除；`m` 个叛徒最多污染 `m` 条证词，再加 2 个诚实节点就能形成多数。代价是必须假设私钥不泄露。

**Q3** 既然 `SM(m)` 只要 `m+2`，PBFT 为什么还用 `3f+1`？

▸ 答案：PBFT 不把安全性押在 “叛徒没有合法密钥” 上；节点被入侵后用合法私钥作恶，签名完全无效。`3f+1` + `2f+1` quorum 保证任意两个 quorum 的交集里至少有一个诚实节点，这个论证不依赖密钥假设。

**Q4** `OM(1)` 在 `n=10` 时要多少条消息？`m=3` 时量级是多少？

▸ 答案：`OM(1)` 是 `(n-1)² = 81` 条；`OM(m)` 是 `O(n^m)`，`n=10, m=3` 就是 `10³` 量级，且延迟 `m+1` 轮。这就是工程上不用 `OM(m)` 的原因。

**Q5** 3 副本 Raft 与 4 副本 PBFT，各扛几个故障？成本差在哪？

▸ 答案：3 副本 Raft 扛 1 个崩溃；4 副本 PBFT 扛 1 个拜占庭节点。成本差在副本数（4 vs 3）、消息量（`O(n²)` vs `O(n)`）和视图切换的复杂度，不只是机器钱。

**Q6** 区块链为什么用 PoW 而不是 PBFT？

▸ 答案：前提不同。公网匿名、成员可任意加入，先要解决 Sybil（一人多号），PoW 用算力给 “投票权” 定价；PBFT 假设成员已知且身份有成本，`f` 才有意义。两者不是同一层工具。
