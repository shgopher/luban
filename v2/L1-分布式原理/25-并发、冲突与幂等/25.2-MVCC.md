# 25.2 MVCC

## 一句话

> MVCC 让 “**读不阻塞写、写不阻塞读**”：每次写产生新版本，读按自己的快照挑可见版本；代价是**旧版本要清理**，而长事务会让清理永远等不到——于是表膨胀。

## 机制：版本 + 可见性

| 概念 | 说明 |
|---|---|
| 版本标记 | 每行带创建事务 ID / 删除事务 ID（或 undo 指针） |
| 快照 | 读操作开始（或语句开始）时的 “活跃事务集合” |
| 可见性规则 | 创建者已提交且不在活跃集合 → 可见；否则看 undo/旧版本 |
| 清理 | 无人可见的旧版本由后台回收（vacuum / purge） |

## RC 与 RR 的快照差别

| 隔离级别 | 快照时机 | 现象 |
|---|---|---|
| Read Committed | **每条语句**取一次快照 | 同一事务内两次查询可能不同（不可重复读） |
| Repeatable Read | **事务开始**取一次快照 | 同事务内一致，但可能写偏斜（见 [24.1 ACID 与本地事务](../24-分布式事务/24.1-ACID与本地事务.md)） |

## 代价：清理被长事务挡住

| 现象 | 原因 | 处理 |
|---|---|---|
| 表/索引膨胀 | 旧版本无法回收 | 查 `pg_stat_activity` 的长事务 / InnoDB 的 `history list length` |
| 磁盘暴涨 | 同上 | 终止长事务、调 vacuum 参数 |
| 查询变慢 | 扫描要跳过大量死版本 | 清理后恢复 |

数字直觉：一个开了几小时的大事务，可能让**几小时的更新都无法清理**；在高写入表上，膨胀速度是 “写入量 × 阻塞时长”。

## 代码：快照读与版本可见性

```sql
-- PostgreSQL：RR 事务内两次读到同一个快照
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id=1;   -- 快照在第一条语句时确定
-- 其他事务此时更新了 id=1 并提交
SELECT balance FROM accounts WHERE id=1;   -- 仍然读到旧值（同快照）
COMMIT;

-- 查看“谁挡住了清理”
SELECT pid, state, xact_start, now()-xact_start AS age, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 5;
```

## 版本链与可见性：一个可手算的例子

把 RC 与 RR 的差别落到一条版本链上，只需要三个事务。结论先给：**同一条版本链、同一个读时刻，快照点不同，读到的值就不同；RC 每条语句换一次快照点，RR 每个事务只取一次快照点**。下面这套时间线不依赖任何数据库，手算就能复现。

### 三个事务：一条版本链怎么长出来

| 时刻 | 发生什么 | 版本链 |
|---|---|---|
| t=0 | 基线 | v1: A=1 |
| t=1 | T1 开始 | 不变 |
| t=2 | T1 当前读 A=1，写 A=2（未提交） | 悬挂，不落链 |
| t=3 | T3 开始 | 不变 |
| t=5 | T1 提交 | v2: A=2 |
| t=6 | T2 开始，当前读 A=2，写 A=3（未提交）；T5 开始 | 不变 |
| t=8 | T2 提交 | v3: A=3 |

先记住一条纪律：**未提交的写不落链**。T2 能“写 A=3”的前提是当前读到了 A=2——它必须等 T1 释放行锁，所以 T2 的写天然排在 T1 之后，版本链的提交时刻一定单调递增。

| 写事务 | 动作 | 读到 | 说明 |
|---|---|---|---|
| T1 | t=2 写 A=2 之前 | 1 | 当前读（写的前提），不是快照读 |
| T2 | t=6 写 A=3 之前 | 2 | T1 已在 t=5 提交，所以它读到 2 |

### 可见性规则：一行公式

```text
visible(snapshot) = max{ v ∈ chain | commit_ts(v) ≤ snapshot }
RC：snapshot = 语句执行时刻（每条语句重取一次）
RR：snapshot = 事务开始时刻（整个事务复用）
```

公式里只有两样东西：版本有提交时刻，快照是一个提交时刻上限。**“可重复读”不是把行锁住，而是把快照点钉在事务开始那一刻**；所以 RR 的读永远不阻塞写，也永远看不到快照点之后的提交。

### RC 与 RR 的读数对照

| 读事务 | 读时刻 | RC 快照点 | RR 快照点 | RC 读到 | RR 读到 |
|---|---|---|---|---|---|
| T3（t=3 开始） | 4 | 4 | 3 | 1 | 1 |
| T3 | 6 | 6 | 3 | 2 | 1 |
| T3 | 9 | 9 | 3 | 3 | 1 |
| T5（t=6 开始） | 7 | 7 | 6 | 2 | 2 |
| T5 | 9 | 9 | 6 | 3 | 2 |

T1、T2 是写事务，本身不产生快照读：各自只做一次当前读，写前提见本节的写事务小表，版本链由它们的提交推进。**可见性差异只体现在读事务的读数上**；额外放一个 T5 作对照，说明 RR 的“旧”取决于起点，而不是“永远读最旧”。

读数三句话：

1. T3 在 RC 下看到 `{1, 2, 3}` 三个值，RR 下只有一个 `1`——差别不在数据，只在快照点。
2. T5 比 T3 晚 3 秒开始，RR 就看到了 2——**RR 不是“总读旧值”，而是“读你开始那一刻的值”**。
3. RR 读到的都是过去的值，但这不等于更安全：T3 若基于 `1` 做判断再写回，就会覆盖 T2 已提交的 `3`（先查后改的窗口，见 [25.1 乐观并发与悲观并发](25.1-乐观并发与悲观并发.md)）。

### 代码：版本链 + 快照读

```python
#!/usr/bin/env python3
"""本机仿真：简化版本链 + 快照读，看清 RC / RR 的可见性差别。"""
import unicodedata

CHAIN = [(1, 0, "基线")]          # (值, 提交时刻, 写入事务)


def commit(value, ts, txn):
    CHAIN.append((value, ts, txn))


def visible(snapshot):
    """版本链里 commit_ts <= 快照点 的最新一版。"""
    best = None
    for val, ts, txn in CHAIN:
        if ts <= snapshot:
            best = (val, ts, txn)
    return best


def w(s):                          # 终端显示宽度：中文按 2 列算
    return sum(2 if unicodedata.east_asian_width(c) in "WF" else 1 for c in s)


def pad(s, n):
    return s + " " * (n - w(s))


def row(cells, widths):
    return "  ".join(pad(str(c), n) for c, n in zip(cells, widths))


# ---- 写事务：先当前读（写前提），再悬挂写，最后提交 ----
t1_base = visible(2)                    # T1 在 t=2 的当前读
commit(2, 5, "T1")
t2_base = visible(6)                    # T2 在 t=6 的当前读（T1 已提交）
commit(3, 8, "T2")

# ---- 读事务：T3 在 t=3 开始读 3 次；T5 在 t=6 开始读 2 次 ----
READS = [("T3", 3, [4, 6, 9]), ("T5", 6, [7, 9])]

W1 = [8, 6, 12, 10]
print("版本链（按提交时刻）：")
print("  " + row(["版本", "值", "提交时刻", "写入事务"], W1))
for i, (val, ts, txn) in enumerate(CHAIN, start=1):
    print("  " + row([f"v{i}", val, ts, txn], W1))

print("\n写事务的当前读（写的前提，不是本事务的快照读）：")
print(f"  T1 在 t=2 当前读 A={t1_base[0]} -> 写 A=2（悬挂，t=5 提交）")
print(f"  T2 在 t=6 当前读 A={t2_base[0]} -> 写 A=3（悬挂，t=8 提交）")

W2 = [6, 6, 8, 12, 12, 8, 8]
print("\n读事务的可见性（快照点相同则读数相同）：")
print("  " + row(["事务", "开始", "读时刻", "RC 快照点", "RR 快照点",
                  "RC 读到", "RR 读到"], W2))
for txn, start, ticks in READS:
    for t in ticks:
        rc, rr = visible(t), visible(start)   # RC 按语句取，RR 按事务开始取
        print("  " + row([txn, start, t, t, start, rc[0], rr[0]], W2))

t3_rc = sorted({visible(t)[0] for t in [4, 6, 9]})
t3_rr = sorted({visible(3)[0] for _ in [4, 6, 9]})
print(f"\nT3 一个事务里看到的值的集合：RC={t3_rc}，RR={t3_rr}")

# ---- 长事务的清理代价：版本链长度 -> 清理延迟 ----
WRITE_TPS, BYTES_PER_VER = 5000, 200      # 假设：热行 5000 写/s，每版本约 200B
PURGE_RATES = {"清理@20万/s": 200_000, "清理@5万/s": 50_000}

print("\n长事务的清理代价（本机计算：写入 5000 版本/s、每版本 200B）：")
W3 = [16, 18, 16, 15, 12]
print("  " + row(["版本链长度", "对应长事务时长", "清理@20万/s", "清理@5万/s", "占用磁盘"], W3))
for n in [10_000, 100_000, 1_000_000, 10_000_000]:
    disk = n * BYTES_PER_VER / 1e9
    disk_s = f"{disk:.2f} GB" if disk >= 1 else f"{disk * 1000:.0f} MB"
    print("  " + row([f"{n:,}", f"{n / WRITE_TPS:.0f} s",
                      f"{n / PURGE_RATES['清理@20万/s']:.2f} s",
                      f"{n / PURGE_RATES['清理@5万/s']:.2f} s", disk_s], W3))

assert (1_000_000 / 200_000) == 5.0 and (10_000_000 / 5000) == 2000.0
print("\n断言通过：清理耗时 = 版本链长度 ÷ 清理速率；长事务时长 = 版本链长度 ÷ 写入速率")
```

### 长事务的清理代价：版本链长度 × 清理延迟

清理只能回收“对所有活跃快照都不可见”的版本，所以版本链长度由**写入速率 × 最长事务时长**决定：

```text
保留版本数 = 写入速率（版本/秒） × 最长活跃事务时长（秒）
清理耗时   ≈ 保留版本数 ÷ 清理速率（版本/秒）
```

本机计算（写入 5,000 版本/秒、每版本约 200B；清理速率取 20 万/秒与 5 万/秒两档）：

| 版本链长度 | 对应长事务时长 | 清理 @20 万版本/秒 | 清理 @5 万版本/秒 | 占用磁盘 |
|---|---|---|---|---|
| 10,000 | 2 s | 0.05 s | 0.20 s | 2 MB |
| 100,000 | 20 s | 0.50 s | 2.00 s | 20 MB |
| 1,000,000 | 200 s | 5.00 s | 20.00 s | 200 MB |
| 10,000,000 | 2,000 s | 50.00 s | 200.00 s | 2 GB |

读法：一条 200 秒的长事务（200 × 5,000 = 100 万版本、约 200MB）在跑的时候只是慢；它结束后，清理还要 5–20 秒才追平。**长事务的账单不在它运行的那 200 秒，而在它结束后那 5–20 秒**，以及这期间所有查询都要跳过这些死版本做可见性判断。

## 反模式

| 反模式 | 后果 |
|---|---|
| 应用里开长事务（等用户输入） | 清理停摆，表膨胀 |
| 用 RR + 大批量更新 | undo/history 暴涨，IO 压力大 |
| 查询不设 `statement_timeout` | 慢查询把自己变成 “长事务” |
| 认为 MVCC 等于 “无锁” | 写仍要行锁/冲突检测，只是读不阻塞 |
| 大事务里做批量 `UPDATE` | undo/history 暴涨，复制延迟飙升 |
| 用 RR 做“跨请求”快照 | 事务边界过长，清理停摆 |

## 三条铁律

> 🔑 **事务要短**；长事务是 MVCC 系统的头号杀手。

> 🔑 **读不阻塞写 ≠ 没有竞争**；写与写仍会冲突。

> 🔑 **监控 “最老快照” 与清理滞后**，不是只看磁盘使用率。

## 自检

**Q1** 为什么 MVCC 下 “读不阻塞写”？

▸ 答案：因为读用的是**快照**：它按自己的可见性规则去读 “当时应该看到的那一版”，不需要等待正在写的新版本。写只追加新版本，不修改旧版本，所以读永远有数据可看。

**Q2** 长事务为什么会让表膨胀？

▸ 答案：因为清理只能删除 “**对所有活跃快照都不可见**” 的旧版本。长事务持有旧快照，意味着它之后的旧版本都 “可能还有人要读”，于是清理被迫停止，死版本不断堆积。

**Q3** RC 与 RR 的快照差别会导致什么业务问题？

▸ 答案：RC 下同一事务内两次查询可能看到不同数据（别人已提交），适合 “单语句一致性”；RR 下事务内一致，适合 “读-判断-写” 的复合逻辑。选错会出现 “校验通过但写入时数据已变” 的错觉——本质是需要 RR 或显式加锁。

**Q4** MVCC 能完全替代锁吗？

▸ 答案：**不能**。MVCC 只解决 “读-写” 冲突；**写-写**冲突仍要靠行锁/冲突检测（先写者持有行锁），唯一约束也要靠索引与锁。所谓 “无锁读” 是读侧的优化，不是全局无锁。

**Q5** 怎样发现 “清理被挡住”？

▸ 答案：PostgreSQL 看 `pg_stat_activity` 里 `xact_start` 最老的事务、`pg_stat_user_tables.n_dead_tup`；MySQL 看 `SHOW ENGINE INNODB STATUS` 的 `History list length` 与长事务列表。阈值化告警比 “看磁盘” 更早发现问题。

**Q6** 为什么 RR 下 “第二次读不到新值” 有时反而是 bug 的来源？

▸ 答案：因为业务常把它当成 “最新数据”：在 RR 事务里先查询余额、再基于它扣减，中间别人已改了余额。要分两种情形：① **同一行**的并发更新是「丢失更新」——PG 的快照隔离会在提交时报 `could not serialize access due to concurrent update`（first-updater-wins），InnoDB 的 `UPDATE` 是当前读 + 行锁，也不会静默覆盖；解法是版本号 CAS 或捕获报错重试。② **不同行**各读各写、组合后违反约束，才是「写偏斜」——SI 检测不到，需要 Serializable 或 `SELECT ... FOR UPDATE` 加锁读。别指望 RR 的快照读 “帮你看到最新”。
