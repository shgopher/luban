# 25.3 冲突检测与解决策略

## 一句话

> 冲突处理分两步：**检测**（怎么知道两个写打上了架）与**解决**（谁赢、怎么合）；而第一步之前还有个更关键的问题——**这个冲突在业务上意味着什么**，答案不同，策略完全不同。

## 检测手段

| 手段 | 原理 | 适用 |
|---|---|---|
| 版本号/时间戳 | 提交时比对基线 | 单键、单行（见 [25.1 乐观并发与悲观并发](25.1-乐观并发与悲观并发.md)） |
| 版本向量 | 记录 “见过哪些副本的哪些版本” | 多主/离线编辑，能识别并发写 |
| 约束冲突 | 唯一键、外键、检查约束 | 由数据库直接拒绝 |
| 因果依赖 | 依赖的写尚未可见 | 需要因果一致性支持 |

## 解决策略

| 策略 | 语义 | 风险 |
|---|---|---|
| **LWW**（最后写入胜） | 按时间戳覆盖 | 静默丢更新；时钟漂移会让 “更早” 的写赢 |
| **合并（merge）** | 字段级/业务级合并 | 需要业务语义（如购物车取并集） |
| **CRDT** | 数学上可交换合并 | 只能表达特定结构（见 [25.6 CRDT (计数 / 集合 / 寄存器)](25.6-CRDT.md)） |
| **拒绝 + 重试** | 冲突即失败，客户端重来 | 高冲突下重试风暴 |
| **人工仲裁** | 提示用户选择 | 体验差，但正确性最高 |

## 选择的判据

| 业务语义 | 策略 |
|---|---|
| 覆盖型（头像、昵称） | LWW 可接受 |
| 累加型（计数、余额） | 需要原子操作或 CRDT 计数器，**不能 LWW** |
| 集合型（标签、购物车） | 取并集（OR-Set） |
| 互斥型（库存、座位） | 拒绝 + 重试（乐观）或锁（悲观） |
| 金额/账务 | 拒绝 + 人工/对账，绝不 LWW |

## 代码：三种冲突策略的落地形态

```sql
-- ① 拒绝 + 重试（库存、座位）：CAS 语义
UPDATE stock SET n = n - 1 WHERE sku = ? AND n >= 1;   -- 影响 0 行 = 冲突

-- ② 合并（购物车/标签）：取并集，天然幂等
INSERT INTO cart_items(user_id, sku) VALUES (?, ?)
ON CONFLICT (user_id, sku) DO NOTHING;

-- ③ LWW（仅限可覆盖字段）：需要版本号，不能用墙钟
UPDATE profile SET nickname = ?, ver = ? WHERE id = ? AND ver < ?;
```

## 版本向量与 LWW 的取舍

**结论**：版本向量回答 “两个写是否并发”，LWW 回答 “留哪个”——这是 “检测” 与 “解决” 两件事，不能互相替代。3 副本各写一次同一 key 的固定时间线里，LWW 静默丢掉 2 次写，还把 “因果上更晚” 的 C 输给时间戳更大的 A；版本向量一条不丢，但必须由业务决定 A 与 C 怎么合。元数据也不免费：N=100 时版本向量每次写 800B，100B 的值光元数据就是 8 倍。

### 固定时间线：三次写，两种结局

| 物理时刻 | 副本 | 动作 | 版本向量 | LWW 时间戳 |
|---|---|---|---|---|
| 1000ms | R2 | 写 B（基线） | {0,1,0} | 1000ms |
| 1000ms | R1 | 写 A（分区内并发） | {1,0,0} | 1020ms（R1 时钟 +20ms） |
| 1001ms | R3 | 收到 B | — | — |
| 1002ms | R3 | 写 C（因果晚于 B） | {0,1,1} | 962ms（R3 时钟 −40ms） |

| 策略 | 最终值 | 保留版本数 | 检出冲突 | 静默丢写 | 因果逆序 |
|---|---|---|---|---|---|
| 版本向量 | A / C | 2 | 1 | 0 | 0 |
| LWW | A | 1 | 0 | 2 | 1 |

读数：

- **版本向量**：C 的 {0,1,1} 支配 B 的 {0,1,0}，说明 B 已被 C 吸收，不是冲突；A 与 C 互不支配，是唯一真正的冲突。检测是精确的：不把因果当冲突，也不漏并发。
- **LWW**：时间戳 A(1020) > B(1000) > C(962)，留 A、丢 B 与 C。C 是 “收到 B 之后” 写的，却因 R3 时钟慢 40ms 排在 B 前面——LWW 用墙钟近似因果，时钟一歪就逆序。
- 这不是极端设定：跨机房的 NTP 偏差几十毫秒很常见，偏移还会随负载漂移（[23.1 物理时钟与漂移](../23-时间、顺序与因果/23.1-物理时钟与漂移.md)）。

为什么用 3 个副本：2 个副本只能产生一对并发写，3 个才能在同一条时间线上同时放下 “因果链（B→C）” 与 “并发分支（A）” 两种关系——LWW 的错序，正是发生在这两种关系被压成一根时间轴的时候。副本继续增加只会加宽版本向量，不改变结论。

折中还有第三条路：**HLC（混合逻辑时钟）**。时间戳取 `(物理时间, 逻辑计数)`，收到消息时把逻辑部分抬到 “见过的最大值 + 1”，于是因果上更晚的写必然拿到更大的时间戳，LWW 不再逆序；代价是并发写依然会丢一个（只是丢得 “不冤”），物理部分仍要 NTP 兜底。HLC 适合 “只关心因果、不关心保留冲突分支” 的覆盖型场景，是 LWW 与版本向量之间的工程折中。

### 检测能力不是免费的：蒙特卡洛与元数据

核心判定只有两个操作：向量比较（判断是否因果）与向量合并（写入时累积）。`join` 是逐副本取最大：

```go
type vv [replicas]int

// a 是 b 的祖先或相等：每项都不大于 b
func (a vv) leq(b vv) bool {
    for i := range a {
        if a[i] > b[i] {
            return false
        }
    }
    return true
}

func (a vv) join(b vv) vv {
    var c vv
    for i := range a {
        if a[i] > b[i] {
            c[i] = a[i]
        } else {
            c[i] = b[i]
        }
    }
    return c
}

// 每次写：合并本副本已见的版本向量，再把自己的计数器 +1
var v vv
for _, idx := range seen[rep] {
    v = v.join(vs[idx].vv) // join 逐项取 max
}
v[rep]++
```

本机仿真（`go1.27.1 / darwin/arm64 / Apple M1`；500 轮 × 100 次写）：

```text
② 蒙特卡洛（3 副本 × 同一 key × 100 次写 × 500 轮；写入轮流落到各副本）
场景                            VV 检出并发率  VV 需合并分支   LWW 选错率    VV 误用丢写   LWW 丢写
无分区、无时钟偏移              0%            1.0 个          0%            0.0 次        99 次
随机丢复制 30%、无偏移          100%          1.4 个          0%            0.4 次        99 次
随机丢复制 30%、偏移 ±50ms      100%          1.4 个          39%           0.4 次        99 次

③ 元数据开销（每个 key 每次写都要带）
副本数 N    版本向量（8B×N）    LWW 时间戳      100B 值时的元数据占比   1000B 值时的占比
3           24B                 8B              24%                     2%
10          80B                 8B              80%                     8%
100         800B                8B              800%                    80%
```

完整代码在仓库 [tools/examples/25.3-conflict/](../../../tools/examples/25.3-conflict/README.md)，`go run .` 可复现这两组统计。

读数：

- **LWW 的丢写是结构性的**：无论有没有分区，它最终只保留一个值，99/100 次写从其它副本的视角消失；分区只是让 “丢弃哪 99 次” 变随机。
- **偏移 ±50ms 时，LWW 有 39% 的轮次把 “因果更晚的版本” 丢掉**（winner 被别的版本支配）；版本向量 0%——不发生并发时检出率 0%（不假报），有并发时 100%（不漏报）。
- 版本向量的代价是 “需合并分支” 平均 1.4 个/100 次写；冲突率不高时合并可控，热点 key 会把成本推给业务。
- 元数据账：N=3 是 24B、N=10 是 80B、N=100 是 800B；100B 的值在 N=100 时元数据是值的 8 倍。“大集群热点行不要用全量版本向量” 是算术结论，不是经验之谈。

### 取舍：检测能力 / 元数据开销 / 适用场景

| 维度 | 版本向量 | LWW |
|---|---|---|
| 检测能力 | 区分 “并发” 与 “因果”，无假阳性 | 不能，冲突不可见 |
| 元数据开销 | 8B×N/写（稀疏、dotted 编码可压） | 8B（+ tie-break） |
| 冲突时行为 | 保留多分支，交业务合并或人工 | 静默覆盖，取时间戳最大 |
| 一致性能力 | 可支撑因果一致 | 最终一致，可能丢更新 |
| 适用场景 | 多主、离线编辑、协同文档、购物车 | 覆盖型字段、低冲突、大集群热点 |
| 不适用 | N 大且热点、金额与库存 | 金额、库存、计数（累加语义） |

| 你的情况 | 选 |
|---|---|
| N≤10、多主或离线、冲突需要人看 | 版本向量 + 合并策略（字段级 merge 或人工仲裁） |
| 覆盖型字段（头像、昵称）、冲突概率 <1% | LWW，但时间戳用服务端版本号，不用客户端墙钟 |
| N=100 的热点行 | 别用全量版本向量：dotted/suffix VV、按字段 LWW，或直接上 CRDT |
| 金额 / 库存 | 两者都不行：拒绝 + CAS + 对账 |

折中方案是 **LWW + 冲突日志**：仍取时间戳最大，但把被覆盖的值记进日志，兼顾吞吐与可观测——正确性依然靠业务兜底。而版本向量只回答 “谁也没见过谁”，不回答 “谁对”；如果业务能定义可交换的合并（计数、集合），直接用 [25.6 CRDT (计数 / 集合 / 寄存器)](25.6-CRDT.md) 在数据结构层消掉冲突，比 “先检测再人工” 更省。另有两个工程细节：删除必须用 tombstone（否则 “删掉的值” 会因向量更旧而复活）；稀疏 VV 或 dotted version vector 只记录实际写入涉及的副本，能把 N=100 的 800B 压到与真实并发规模相称。

最后要区分 “检测” 与 “解决”：版本向量的 100% 检出率只保证 “冲突被看见了”，后续是字段级 merge、保留多版本给用户，还是人工对账，仍要按业务语义写代码。检出率再高，没有合并策略也只是把 “静默丢写” 换成了 “报错等人”；冲突处理的产品决策，往往比选哪种算法更影响用户。

> 🔑 版本向量检测并发，LWW 决定胜负；前者不能自动解决，后者不能发现问题。

> 🔑 元数据随 N 线性增长，是选版本向量之前必须先算的账。

## 反模式

| 反模式 | 后果 |
|---|---|
| 一律用 LWW | 丢更新（尤其金额、库存） |
| 用客户端时间戳做 LWW | 时钟不可信，旧写覆盖新写（见 [23.1 物理时钟与漂移](../23-时间、顺序与因果/23.1-物理时钟与漂移.md)） |
| 冲突只在 “写” 时检测 | 读到中间态，业务判断错 |
| 不记录冲突 | 无法复盘，也不知道丢了多少 |
| 冲突解决策略不告诉用户 | 数据被覆盖却无人知晓 |
| 只在客户端解决冲突 | 服务端仍可能互相覆盖 |

## 三条铁律

> 🔑 **先问业务语义，再选策略**；没有通用解。

> 🔑 **金额与库存禁止 LWW**；它们需要 “拒绝 + 对账”。

> 🔑 **冲突要可观测**：计数、采样、告警，否则丢更新无人知道。

## 自检

**Q1** 为什么金额绝不能用 LWW？

▸ 答案：因为 LWW 会**静默丢弃**一次更新：两笔并发扣款只保留时间戳更晚的那笔，另一笔消失，且账面上看不出来。金额必须走 “原子扣减 + 幂等 + 对账”，冲突时拒绝而不是覆盖。

**Q2** 版本向量相比单一版本号，多解决了什么？

▸ 答案：它能判断两个写是 “**并发**” 还是 “**有因果先后**”：单一版本号只能比大小，无法区分 “B 在 A 之后发生” 与 “B 与 A 并发”。多主/离线场景必须用版本向量才能正确合并。

**Q3** 库存扣减该用哪种策略？

▸ 答案：**拒绝 + 重试**（乐观）或**行锁**（悲观），核心是 “不允许超卖”。常见做法是 `UPDATE stock SET n=n-1 WHERE sku=? AND n>=1`，影响行数 0 即失败；高并发下配合队列削峰（见 [67.6 秒杀与抢购 (库存 / 限购 / 防刷 / 削峰)](../../L4-组件与技术/67-交易与账务/67.6-秒杀与抢购.md)）。

**Q4** 合并策略的难点在哪？

▸ 答案：在**业务语义**：字段能不能相加？列表取并集还是取最新？删除与新增如何交互？技术只能提供 “可合并的数据结构”（CRDT/OT），但 “怎么合才符合业务” 必须由领域专家定义，否则合并结果在业务上仍是错的。

**Q5** 冲突检测的成本从哪来？

▸ 答案：两处：**存储**（版本号/版本向量要随行保存）与**计算**（每次提交要比较、每次合并要遍历）。版本向量随副本数增长，大集群下元数据可能比数据还大——所以要按 “冲突概率” 决定是否值得精确检测。

**Q6** 为什么 “② 合并” 在跨设备场景比 “① 拒绝” 体验更好，但在库存场景是灾难？

▸ 答案：因为合并的语义是 “**两个写都保留**”：购物车加同一件商品取并集很自然；库存扣减若 “两次都保留”，结果是两次扣减都生效——对买家是好事，对卖家是超卖。冲突策略必须匹配业务语义，不能用一套逻辑套所有场景。

**Q7** 冲突检测的 “成本” 具体花在哪？

▸ 答案：三处：**存储**（版本号/版本向量随每行保存）、**计算**（每次提交比较、每次合并遍历）、**协调**（多副本时要交换版本信息）。版本向量随副本数线性增长，大集群里元数据可能超过数据本身——所以要先评估 “冲突概率”，再决定是否值得精确检测。

**Q8** 为什么 “冲突解决策略” 必须写进产品文档？

▸ 答案：因为它决定了**用户看到什么**：LWW 会让 “后写的覆盖先写的”（用户可能丢掉刚输入的内容），合并会让 “两边都保留”（用户看到重复项），拒绝会让 “操作失败”（用户需要重试）。这些都不是纯技术决策，必须让产品与用户知情，否则会被当成 bug 反复投诉。
