# 24.11 最终一致的三条工程载体：内存队列、CDC、MQ

## 一句话

> “最终一致” 不是一个方案，而是**把待办事件存在哪**的三种选择：进程内存、数据库日志、消息中间件。三者的业务骨架完全一样，区别只在**可靠性来自哪一层**、以及重复投递要谁去挡。

## 它们共用的三步骨架

```
① 事务主动方：先写「事件」到载体（内存队列 / DB 日志 / MQ）
② 监测服务：取出事件 → 回查「关键事务」是否真的成功 → 失败就丢弃
③ 监测服务：按顺序执行子事务；失败则标记进度、重写回载体
```

第 ② 步是这类方案的灵魂：**事件只是 “可能要做什么”，业务表才是 “到底做成了没有”**。少了这次回查，业务回滚后事件还在，下游就会执行一笔不存在的业务。

| 步骤 | 保证 | 失败后果 |
|---|---|---|
| ① 先写事件 | 有事件才可能执行 | 业务还没做，事件先到 → 靠 ② 过滤 |
| ② 回查关键事务 | 事件与业务对得上 | 不回查 → 幽灵事件，下游多做一次 |
| ③ 顺序执行子事务 | 子事务按业务顺序推进 | 乱序 → 库存扣成负数、状态倒退 |

> 🔑 这三种载体都不是 “事务”，是**事件的可靠寄存处**。真正的原子性仍然来自 “关键事务” 那一次本地写。

## 三条载体总表

| 维度 | ① 本地共享内存 | ② 数据库日志（CDC） | ③ MQ 事件源 |
|---|---|---|---|
| 事件存在哪 | 进程内存队列 | MySQL binlog / MongoDB oplog / Oracle redo | Broker |
| 可靠性来源 | 进程活着 | 数据库日志（提交才可见） | Broker 的持久化与重试 |
| 额外组件 | 无 | Debezium / Canal / Maxwell + Kafka | MQ |
| 进程崩溃 | **事件丢失** | 不丢（日志还在） | 不丢 |
| 多节点重复投递 | 各自为政，无时序 | 会重复，需锁或选主 | 天然多消费者，需分区键保序 |
| 延迟 | 内存级 | 通常 < 100ms | 毫秒到秒级 |
| 运维复杂度 | 最低 | 中（权限、位点、schema 变更） | 中 |
| 适合 | 单机、可重放、非资金 | 已有 CDC 平台、不想改业务库 | 已有 MQ、下游多、要削峰 |

## ① 本地共享内存队列：最轻，也最脆

事务主动方收到请求后，先把事件写进**本机共享内存**，写入成功后执行关键事务；监测服务不停出队，回查业务存储，再顺序执行子事务。

```text
请求 ──► 写内存队列 ──► 执行关键事务（本地事务）──► 返回
                │
                ▼
        监测服务：出队 → 查关键事务表
                ├─ 业务失败 → 丢弃事件
                └─ 业务成功 → 按序执行子事务
                              └─ 子事务失败 → 记进度、重写回队列
```

优点三条：

| 优点 | 含义 |
|---|---|
| **实现简单** | 事件队列与业务存储隔离，子事务流程集中在一个服务里管 |
| **扩展性强** | 加一个子事务就是加一段流程，不用动业务主链路 |
| **松耦合** | 子事务之间没有强关联，符合微服务 “各自演进” 的诉求 |

缺点四条，条条致命：

| 缺点 | 后果 |
|---|---|
| **单点丢消息** | 事件只在本机内存，进程一挂，待办全没 |
| **性能受争抢** | 主动方与监测服务共享资源；为保顺序不能并行，子事务一多吞吐上不去 |
| **异常退出丢事件** | 数据已读出、还没写回进度时崩溃，这条事件就消失了 |
| **多节点无时序** | 事件按单机存储，多副本部署时无法保证子事务顺序 |

> ⚠️ 判断能不能用它，只问一句：**这条事件丢了，业务能不能从别处重建？**能 (如可全量重算的统计、可重放的索引) 就可以；不能 (资金、库存、订单状态) 就别用。

## ② 订阅数据库日志：让 “写库成功” 等价于 “事件一定在”

数据库把每次写操作记进日志 (MySQL binlog、MongoDB oplog、Oracle redo log)，并对外提供 watch 能力。监测服务订阅日志，把变更转成事件投给 MQ，下游异步消费。

| 存储 | watch 手段 |
|---|---|
| MySQL | Binlog API（Canal / Maxwell / Debezium 都基于它） |
| MongoDB | oplog + Change Streams |
| Oracle | OEM 的 RESTful API，可查 Redo Log、归档日志 |

```text
业务 ──► 写业务表（本地事务提交）──► binlog 落盘
                                      │
                              监测服务订阅 binlog
                                      │
                                      ├─ 转成事件 → MQ（至少一次）
                                      └─ 位点推进（崩溃后从这里续）
```

这套方案的好处是**解耦得彻底**：事务主动方只管写库，完全不用关心事件怎么发；下游加消费者随便加。

代价在多节点：监测服务一多，同一条日志会被多个实例各投一次。规避手段只有两类：

| 手段 | 做法 | 要解决的问题 |
|---|---|---|
| **分布式锁** | 抢到锁的实例才能投递（Redis / ZooKeeper / etcd，乐观锁或悲观锁） | 锁释放、死锁、脑裂 |
| **共识选举** | Raft / Paxos 选出唯一 leader 去 watch | 选举期间的不可用窗口 |

即便这样，投递语义仍是 **at-least-once**：监测服务至少把事件送到 MQ 一次，重复由**被动方幂等**兜住 (见 [25.4 幂等设计与去重](../25-并发、冲突与幂等/25.4-幂等设计与去重.md)；消费侧的重试与死信见 [43.6 可靠投递与幂等消费](../../L4-组件与技术/43-消息队列/43.6-可靠投递与幂等消费.md))。

有一个真实案例：QQ 音乐部分业务用这套机制监测 MySQL 与 MongoDB 的变更，保障最终一致。它的局限也写得很清楚——**业务关键路径的存储必须支持 watch**；多节点监测又引入了数据一致性、竞争冲突、性能与资源消耗等新问题。

> 💡 与 [24.6 本地消息表](24.6-本地消息表.md)的关系：outbox 是 “业务自己写一行待发消息”，CDC 是 “从数据库日志里读出这次写”。前者要改表结构，后者不改业务代码但依赖日志格式。两者都吃同一个前提：**binlog 只在事务提交后可见**，业务回滚了，日志里也没有。

## ③ 把 MQ 当事件源：先写消息，再执行业务

和本地内存队列同一套流程，只是把 “写内存” 换成 “写 MQ”：

1. 事务主动方先把事件写进 MQ，写入成功后执行关键事务；
2. 监测服务消费事件，回查关键事务存储，失败就丢弃这条事件；
3. 按预期顺序执行子事务，失败可以退避重试或进重试队列。

它和 [24.7 事务消息 (半消息 / 回查)](24.7-事务消息.md) 的区别只有一个：

| | MQ 事件源 | 事务消息 |
|---|---|---|
| 是否需要 MQ 支持半消息 | **不需要** | 需要 |
| 事件何时对消费者可见 | 写入即可能被消费 | 本地事务成功后才转正 |
| 谁来过滤 “业务没成功” 的事件 | **监测服务的回查** | Broker 的半消息 + 回查 |
| 适合 | MQ 不支持事务消息，或想统一走自建监测服务 | RocketMQ 这类原生支持的 MQ |

优点四条：

| 优点 | 含义 |
|---|---|
| **简单成熟** | MQ 本身高可用、高性能，不用自己造轮子 |
| **松耦合** | 关键事务与子事务彻底解耦，串行/并行由业务定义 |
| **缓冲削峰** | 生产与消费速率不一致时，MQ 顶住峰值 |
| **时序保障** | 按分区/队列保序，子事务按消息顺序推进 |

缺点两条：

| 缺点 | 后果 |
|---|---|
| **存储压力大** | 每个子事务执行前都要回查关键事务存储，热点库被读放大 |
| **排障复杂** | 消息流转、处理状态、错误定位都要额外工具，链路比本地调用长 |

> ⚠️ 最容易忽略的是第 1 步的顺序：**先写 MQ、后执行关键事务**。中间崩溃就会留下 “有事件、没业务” 的孤儿事件——这正是第 2 步回查存在的理由。如果 MQ 支持事务消息，把顺序反过来 (半消息 → 本地事务 → 转正) 能少一次回查。

## 三条载体与本章其它方案的分工

| 载体 | 事件存在哪 | 谁保证不丢 | 什么时候选 |
|---|---|---|---|
| 本地共享内存 | 进程内存 | 没人保证 | 单机、可重放、丢了能重算 |
| 数据库日志（CDC） | 数据库日志 | 数据库 | 不想改业务代码、已有 CDC 平台 |
| MQ 事件源 | Broker | MQ | 已有 MQ、下游多、要削峰 |
| [24.6 本地消息表](24.6-本地消息表.md) | 业务库的 outbox 表 | 本地事务 | 想用一次本地事务把事件和业务绑死 |
| [24.7 事务消息](24.7-事务消息.md) | Broker 的半消息 | MQ 的回查 | MQ 原生支持，想省掉自建监测服务 |

> 🔑 它们解决的是同一个问题的不同切面：**“业务提交了，事件一定在”**。选哪个取决于你愿意把可靠性押在进程、数据库还是 Broker 上。

它们也都不解决 “对方只能收 HTTP 通知” 的场景——那属于 [24.8 最大努力通知](24.8-最大努力通知.md)。在 [24.9 事务模型选型](24.9-事务模型选型.md)的决策树里，这三条载体连同 outbox 都落在 “只需本地写 + 通知下游” 那一支；把载体排进一条真实链路的演练见 [24.12 综合演练：抢购下单](24.12-综合演练-抢购下单.md)。

## 幂等：三条载体共同的底线

三种载体全是 at-least-once，重复一定会发生。重复的来源有三类：前端重复提交、接口超时重试、消息重复消费。常用五种挡法：

| 挡法 | 做法 | 适用 |
|---|---|---|
| **更新前检查** | 先查前置状态 / 唯一 ID 是否已执行，已成功就直接返回 | 有天然状态可查（关注列表、订单状态） |
| **token 机制** | 上游先领 token，执行时校验并删除，删不到即重放 | 防前端重复提交 |
| **锁** | 悲观锁 / 乐观锁 / 分布式锁，抢不到就不执行 | 同一资源的并发互斥 |
| **去重表** | 唯一 ID + 唯一索引，重复插入直接失败 | 通用，最稳 |
| **状态机** | 每个子事务记进度，已完成的跳过 | 长流程、多子事务 |

这五种各自的边界、代价与实测，主场在 [25.4 幂等设计与去重](../25-并发、冲突与幂等/25.4-幂等设计与去重.md)，本节只保留结论：**幂等键必须由业务生成、并且和业务结果同库同事务落库**，否则挡住的是 “重复请求”，挡不住 “重复执行”。

## 反模式

| 反模式 | 后果 |
|---|---|
| 把内存队列当可靠队列用（资金、库存） | 进程一挂，待办全丢，且无法追 |
| 事件写入后不回查关键事务 | 业务回滚了，下游照做，幽灵订单 |
| 多节点监测服务不加锁 / 不选主 | 同一条 binlog 被投 N 次，下游被打爆 |
| 指望 CDC 保证 “恰好一次” | 位点回退、重复投递必然发生 |
| 把 MQ 事件源当成事务消息 | 少了回查，孤儿事件无人清理 |
| 子事务并行执行还假设有序 | 状态倒退、库存扣负 |
| 只挡 “重复请求”，不挡 “重复执行” | 幂等键与业务结果不在同一事务，仍会重复扣款 |

## 自检

**Q1** 三条载体都要 “回查关键事务是否成功”，这一步能不能省？

▸ 答案：不能 (除非用的是事务消息的半消息机制)。因为事件是先于业务写的：业务可能回滚、可能还没提交，事件却已经存在。回查是唯一能把 “幽灵事件” 过滤掉的依据。省掉它，补偿逻辑就要处理 “下游做了一笔上游根本不存在的业务”。

**Q2** 本地共享内存队列和本地消息表看起来都是 “先写事件再做业务”，差在哪？

▸ 答案：**事件存在哪、谁保证它活到被消费**。内存队列在进程里，崩溃即丢；本地消息表把事件写进业务库，由本地事务保证 “业务成功 ⇔ 事件存在”，再由 relay 搬运。前者是单机玩具，后者才是生产方案。

**Q3** 用 CDC 订阅 binlog，为什么还必须给下游做幂等？

▸ 答案：因为投递语义是 at-least-once：位点提交前崩溃会重放、多实例 watch 会重复、MQ 重投也会重复。CDC 只保证 “不丢”，不保证 “不重”。幂等必须落在消费侧 ([25.4](../25-并发、冲突与幂等/25.4-幂等设计与去重.md))。

**Q4** 多节点部署的 CDC 监测服务，为什么非要分布式锁或选主？

▸ 答案：不加约束时，每个实例都会从自己的位点读同一段日志并各自投一次，同一条事件被放大 N 倍。锁/选主把 “投递权” 收敛到单点。代价是要处理锁释放、死锁、脑裂 (选主还要处理不可用窗口)。

**Q5** “MQ 事件源” 和 “事务消息” 都能让业务与消息对上，选型看什么？

▸ 答案：看 MQ 是否支持半消息与回查。支持 (RocketMQ) 就用事务消息，少一个自建监测服务、少一次业务库回查；不支持就用 MQ 事件源 + 监测服务回查，代价是热点库被读放大、排障链路更长。

**Q6** “分布式事务没有万能钥匙，极小概率的不一致可以用告警 + 人工”——这句话的边界在哪？

▸ 答案：边界是**损失的期望值**与**可发现性**。概率再小，只要单次损失巨大 (资损、合规)，就必须做对账与自动修复；概率小、损失小、且能被定时对账发现 (如同一统计口径差几条)，用告警 + 人工比再引入一套机制更划算。前提永远是 “能发现”，不是 “赌它不发生”。
