# 24.10 本地事务的工程落地：GORM 三种写法与事务对象

## 一句话

> 事务不是 “在仓储层包一段 `Transaction()`”，而是**同一个事务对象 (GORM 里是 `*gorm.DB`) 沿着调用链传下去**：边界写在业务层，实现留在仓储层，靠 ctx 传 tx 才不用污染每个方法的签名。

## 会留脏数据的那类接口

一个创建用户的接口要写两张表：

1. 往 `uc_user` 插一行用户；
2. 给这个用户生成默认密钥对，插 `uc_secret`。

```go
if err := b.ds.Users().Create(ctx, &userM); err != nil {
    return v1.ErrorUserCreateFailed("create user failed: %s", err.Error())
}

secretM := &model.SecretM{UserID: userM.UserID, Name: "generated"}
if err := b.ds.Secrets().Create(ctx, secretM); err != nil {
    return v1.ErrorSecretCreateFailed("create secret failed: %s", err.Error())
}
```

第二步失败时，第一步已经落库：

| 失败点 | 残留 | 后续后果 |
|---|---|---|
| 第二步插入失败 | 一个没有密钥的用户 | 调用方重试撞唯一键，用户永远拿不到密钥 |
| 第二步超时但实际成功 | 两条都在，看起来没事 | 重试再插一次，密钥重复 |
| 进程在两步之间崩溃 | 半条业务数据 | 对账查不出来源，只能人工清 |

脏数据不只是 “占磁盘”：它会进统计口径、被下游当成真实用户、让 “用户数” 和 “密钥数” 永远对不上。**事务不能 100% 消除不一致** (跨库、提交后崩溃、补偿失败它都管不了)，但它把 “两步之间出错” 这个最高频的窗口关掉了，概率从 “每次故障都中” 降到 “只剩极端情况”。

## 事务能保证什么、管不到什么

| 能保证 | 管不到 |
|---|---|
| 同一事务内的多条写**全成或全败** | 跨库、跨服务（见 [24.9 事务模型选型](24.9-事务模型选型.md)） |
| 并发写冲突由锁 / MVCC 隔离，避免互相踩 | 提交成功但消息没发出去（见 [24.6 本地消息表](24.6-本地消息表.md)） |
| 一次提交代替 N 次往返，省网络与 fsync | 业务规则错误：约束没写，数据 “合法” 但业务是错的 |

> 💡 有一种常见说法把 “提高性能” 列为事务的好处。准确说，事务省的是**网络往返与 fsync 次数** (N 条写合成 1 次提交)，代价是**持锁时间变长**。批量导入收益明显；高频小事务如果包进长事务，反而会成为吞吐瓶颈 (见 [24.1 ACID 与本地事务](24.1-ACID与本地事务.md)的长事务反模式)。

> 🔑 事务里只放 “必须一起成功” 的写。RPC、发消息、长计算一律放事务外。

## GORM 的三种写法

| 写法 | 谁控制提交 | 异常时 | 代码量 | 适合 |
|---|---|---|---|---|
| **手动事务** | 你，显式 `Commit` / `Rollback` | 每条错误都要自己判、自己回滚 | 多 | 需要在事务中途做分支判断 |
| **自动事务** | `db.Transaction(fn)` | `fn` 返回非 nil 即回滚 | 少 | 绝大多数业务（企业里的默认选择） |
| **嵌套事务** | 外层 `Transaction` | 内层返回错误只回滚到**保存点** | 中 | 大事务里允许局部失败 |

### 手动事务：控制力最强，也最容易漏

```go
tx := db.Begin()                 // ① 开事务，后续所有操作必须用 tx，不能用 db
defer func() {                   // ② Panic 也要回滚，否则事务悬挂、连接不归还
    if r := recover(); r != nil {
        tx.Rollback()
        panic(r)                 // 回滚后继续向上抛：recover 不 re-panic 会把故障吞掉
    }
}()

if err := tx.Create(&user).Error; err != nil {
    tx.Rollback()                // ③ 每个错误分支都要回滚并 return
    return err
}
user.Phone = "1812884yyyy"
if err := tx.Save(&user).Error; err != nil {
    tx.Rollback()
    return err
}
if err := tx.Commit().Error; err != nil { // ④ 提交本身也会失败，同样要判
    return err
}
```

三个容易漏的点：`Begin` 之后**继续用 `db`** (那条 SQL 在事务外，回滚撤不掉)、错误分支**只 return 不回滚** (连接被占住直到超时)、**`recover` 之后不 re-panic** (Panic 被吞掉，上层以为成功)。

优点与代价：

| 优点 | 缺点 |
|---|---|
| 精确控制开始、提交、回滚的位置 | 编码复杂度高，每个分支都要写对 |
| 能在事务中途做条件判断（部分提交 / 提前结束） | 漏一处 `Rollback` 就是连接泄漏或脏数据 |

> ⚠️ 常见说法里 “手动事务支持跨多个数据库的事务” 要打折：一个 `*gorm.DB` 事务仍绑定一个连接、一个库；你可以在代码里同时开多个事务对象，但那已经是多个独立事务，跨库原子性还得靠 [24.2 2PC 与恢复协议](24.2-2PC与恢复协议.md)或补偿。

### 自动事务：企业里默认选它

```go
err := db.Transaction(func(tx *gorm.DB) error {
    if err := tx.Create(&user).Error; err != nil {
        return err // 返回任何错误 → GORM 自动回滚
    }
    user.Phone = "1812884yyyy"
    if err := tx.Save(&user).Error; err != nil {
        return err
    }
    return nil // 返回 nil → 自动提交
})
```

| 优点 | 缺点 |
|---|---|
| 开、提交、回滚三件事由框架包办，不会漏 | 事务边界就是整个闭包，中途想 “提前提交一部分” 做不到 |
| 错误即回滚，代码短 | 闭包里塞了 RPC / 慢查询时，事务被悄悄拉长 |
| 回调签名强制你用 `tx`，不容易误用 `db` | — |

### 嵌套事务与保存点

```go
db.Transaction(func(tx *gorm.DB) error {
    tx.Create(&user1)
    tx.Transaction(func(tx2 *gorm.DB) error {
        tx2.Create(&user2)
        return errors.New("rollback user2") // 只回滚 user2
    })
    tx.Transaction(func(tx2 *gorm.DB) error {
        tx2.Create(&user3)
        return nil
    })
    return nil // 提交 user1、user3
})
```

GORM 的嵌套事务用**保存点**实现，也可以手写：

```go
tx := db.Begin()
tx.Create(&user1)
tx.SavePoint("sp1")
tx.Create(&user2)
tx.RollbackTo("sp1") // 撤销 user2，user1 还在
tx.Commit()          // 只提交 user1
```

> ⚠️ 嵌套事务**不是独立事务**：内层返回 nil 只是释放保存点，真正落盘仍要等最外层 `Commit`。把嵌套当 “内层自己提交了” 写业务，会在最外层回滚时一起消失。

## 事务边界该放在哪一层

整洁架构的四层里，事务天然横跨两层：

| 层 | 放什么 | 与事务的关系 |
|---|---|---|
| **Model** | 数据结构 | 无 |
| **Controller** | 参数解析、校验、返回 | 无（不该出现事务） |
| **Biz** | 业务规则、用例编排 | **决定事务边界**：哪几步必须同生共死 |
| **Store** | CURD、外部调用 | **提供事务能力**：开、提交、回滚 |

结论：**事务操作在 Store，事务边界在 Biz。**

### 反例：在 Store 里自己开事务

```go
func (d *userStore) Create(ctx context.Context, user *model.UserM) error {
    return d.db(ctx).Transaction(func(tx *gorm.DB) error {
        if err := tx.Create(user).Error; err != nil {
            return err
        }
        return tx.Create(&model.SecretM{UserID: user.UserID, Name: "generated"}).Error
    })
}
```

三个问题：

1. **方法爆炸**：换个场景要 “只建用户不建密钥”，就得再来一个 `CreateUserWithSecret`，再换组合又要一个；
2. **参数膨胀**：复杂事务需要的开关、上下文只能一路塞进 Store 的签名；
3. **业务下沉**：把 “建用户就该配密钥” 这条业务规则写进了仓储层，违背整洁架构的依赖规则 (见 [26.3 整洁架构](../../L2-架构风格/26-分层与依赖/26.3-整洁架构.md))。

### 正解：Store 暴露 TX，Biz 决定边界

```go
// Store 层：把「开事务」做成一个通用能力，回调里交出一个绑定了 tx 的 ds
type IStore interface {
    TX(context.Context, func(ctx context.Context, ds IStore) error) error
    Users() UserStore
    Secrets() SecretStore
}

func (ds *datastore) TX(ctx context.Context, fn func(ctx context.Context, ds IStore) error) error {
    return ds.core.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        return fn(ctx, &datastore{core: tx}) // 交出去的是同一个 tx
    })
}
```

```go
// Biz 层：只写「哪几步必须一起成功」
err := b.ds.TX(ctx, func(ctx context.Context, ds store.IStore) error {
    if err := ds.Users().Create(ctx, &userM); err != nil {
        return v1.ErrorUserCreateFailed("create user failed: %s", err.Error())
    }
    if err := ds.Secrets().Create(ctx, &secretM); err != nil {
        return v1.ErrorSecretCreateFailed("create secret failed: %s", err.Error())
    }
    return nil
})
```

> 🔑 **必须保证 Biz 与 Store 用的是同一个 `*gorm.DB` 实例。**最容易的破法是回调里又用 `b.ds` (根对象) 而不是参数 `ds`——两条 SQL 各自跑在独立连接上，事务形同虚设，而且不报错。

### 再进一步：把 tx 放进 ctx

回调里多一个 `ds` 参数，事务调用和非事务调用写起来就不一样 (`ds.Users()` vs `b.ds.Users()`)。两步改进把它抹平：

| 形态 | 做法 | 剩什么问题 |
|---|---|---|
| ① 传 `ds` | `TX(ctx, func(ctx, ds IStore) error)` | 两种调用风格不一致 |
| ② ctx 存 `IStore` | `ctx = context.WithValue(ctx, txKey{}, &datastore{tx})`，Biz 里 `ctx.Value(...)` 取 | Biz 要显式提取，风格仍分裂 |
| ③ **ctx 存 tx** | Store 内部 `Core(ctx)` 先查 ctx 有没有 tx，有就用、没有就用根连接 | 隐式：读代码看不出在事务里 |

```go
// Store 层：取连接时先问 ctx
func (ds *datastore) Core(ctx context.Context) *gorm.DB {
    if tx, ok := ctx.Value(transactionKey{}).(*gorm.DB); ok {
        return tx
    }
    return ds.core
}

func (ds *datastore) TX(ctx context.Context, fn func(ctx context.Context) error) error {
    return ds.core.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        return fn(context.WithValue(ctx, transactionKey{}, tx))
    })
}

// Biz 层：事务与非事务都写 b.ds.Users().Create(ctx, ...)，签名不变
err := b.ds.TX(ctx, func(ctx context.Context) error {
    if err := b.ds.Users().Create(ctx, &userM); err != nil { return err }
    return b.ds.Secrets().Create(ctx, &secretM)
})
```

形态 ③ 就是多数 Go 企业项目的终态 (onex、Zero 都是这套)。**代价是隐式**：一行 `Users().Create(ctx, ...)` 到底在不在事务里，只由 ctx 决定，读代码看不出来。分层与装配的完整落地、以及这套机制在真实仓库里的三种命运 (有机制没调用点最常见)，见 [26.3 整洁架构](../../L2-架构风格/26-分层与依赖/26.3-整洁架构.md)。

## 五个必踩的坑

| 坑 | 症状 | 对策 |
|---|---|---|
| **tx 不是同一个** | 第二条 SQL 没回滚，数据半截 | 事务内只用回调给出的 `tx` / 带 tx 的 ctx，禁止用根 `db` |
| **ctx 换成了 Background** | 子函数成功落库，事务回滚后成了孤儿行，**且不报错** | 事务内所有子调用传原 ctx；起 goroutine 更要显式传 |
| **Panic 没 `defer Rollback`** | 事务悬挂，连接不归还，池子慢慢耗尽 | 手动事务必须 `defer Rollback`；自动事务由 GORM 的 `defer` 兜住，但 panic 仍会向上抛 |
| **事务里做 RPC / 发消息** | 持锁时间 = 下游耗时，超时即回滚风暴 | 先本地事务、后异步投递（[24.6 本地消息表](24.6-本地消息表.md)） |
| **错误被吞** | 日志里 “成功”，库里半个事务 | 回调里任何错误都必须 `return`，不要 `_ =` |

## 可运行的最小复现

`tx` 传丢这件事，用内存表就能稳定复现 (不依赖数据库)：

```go
func (s *Store) TX(ctx context.Context, fn func(context.Context) error) (err error) {
    tx := s.db.Begin()
    defer func() {
        if r := recover(); r != nil { tx.Rollback(); panic(r) }
        if err != nil { tx.Rollback(); return }
        tx.Commit()
    }()
    return fn(context.WithValue(ctx, txKey{}, tx))
}
```

四种写法的真实输出：

```text
① 正确：事务内两次写，第二次失败 → 全部回滚
   已提交：[]  activeTx=0
② 子函数换成 Background → 事务丢失，留下孤儿行
   已提交：[uc_secret:s2]  activeTx=0
③ panic 且没有 defer Rollback → 事务悬挂
   已提交：[]  activeTx=1
④ 嵌套事务 = 保存点：内层回滚，外层提交
   已提交：[uc_user:u3]  activeTx=0
```

第 ② 行是关键证据：**`uc_secret` 落库了，事务里的 `uc_user` 回滚了**——一个没有用户的密钥，程序还全部返回成功。第 ③ 行的 `activeTx=1` 就是连接泄漏。

完整代码在仓库 [tools/examples/24.10-txctx/](../../../tools/examples/24.10-txctx/README.md)，`go run .` 可复现这段输出。

## 反模式

| 反模式 | 后果 |
|---|---|
| 在 Store 里按业务组合开事务（CreateUserWithSecret） | 方法组合爆炸，业务规则漏进仓储层 |
| 事务回调里用根 `db` / 根 `b.ds` | 部分 SQL 在事务外，回滚不干净 |
| 手动事务只在错误分支回滚，不 `defer recover` | Panic 时连接悬挂 |
| 把 `context.Background()` 传进事务内子调用 | 写操作逃出事务，且无任何报错 |
| 事务里调用 HTTP / MQ / 第三方 | 锁持有时间被网络放大，超时雪崩 |
| 用嵌套事务当 “内层独立提交” | 外层回滚时内层一起消失 |
| 认为自动事务能解决跨库一致 | 跨库仍要 2PC / Saga / 消息表 |
| 事务包住整个 handler | 参数校验、鉴权耗时长，锁窗口无谓变大 |

事务解决的是 “半步失败”，不解决 “同一笔做两次”；后者属于幂等设计 (见 [25.4 幂等设计与去重](../25-并发、冲突与幂等/25.4-幂等设计与去重.md))。

## 自检

**Q1** 为什么 “事务写在 Store 层” 看起来最自然，却是错的？

▸ 答案：因为它把**业务规则** (“建用户必须建密钥”) 写进了仓储方法，导致每个业务组合都要一个新仓储方法 (方法爆炸)，复杂事务的参数也要塞进 Store 签名。正确分工是：**Store 提供事务能力 (TX)，Biz 决定事务边界 (哪几步必须一起成功)**。事务的 “边界” 是业务语义，不是数据访问细节。

**Q2** 用了 `db.Transaction` 就一定在同一事务里吗？什么情况下不是？

▸ 答案：不一定。事务是否生效取决于**每条 SQL 用的是不是同一个事务对象**。三种破法：① 回调里用外部 `b.ds` / 根 `db`；② 子函数里把 ctx 换成 `context.Background()`；③ 事务内起 goroutine 传了新 ctx。这三种都不会报错——数据只是 “部分落库”。判据：事务内的所有写都必须用回调给出的 `tx` (或带 tx 的 ctx)。

**Q3** 手动事务和自动事务，什么时候真的该选手动？

▸ 答案：需要**在事务中途做控制流**时：条件满足提前提交、分段提交、或对同一事务做多次独立保存点回滚。绝大多数业务只是 “若干写要么全成要么全败”，自动事务足够且不会漏回滚。选手动的代价是每个错误分支、每次 Panic 都要自己兜底。

**Q4** GORM 的嵌套事务，内层返回 nil 意味着数据已经提交了吗？

▸ 答案：没有。GORM 的嵌套事务用**保存点**实现：内层返回 nil 只是释放保存点，数据仍在最外层事务里；最外层 `Commit` 才真正落盘。所以 “内层成功、外层回滚” 时，内层的数据会一起消失。要真的独立提交，必须另开一个事务 (另一条连接)，那就已经是两个事务了。

**Q5** 事务能不能替代对账？

▸ 答案：不能。事务只保证**一个库内、一个事务对象里**的原子性；提交成功之后进程崩溃、消息没发出去、下游处理失败，它都管不到。跨系统的一致性要靠消息表 / 事务消息 ([24.6](24.6-本地消息表.md)、[24.7](24.7-事务消息.md)) 加对账兜底。事务关掉的是 “两步之间” 的窗口，不是 “提交之后” 的窗口。
