# 24.12 综合演练：抢购下单

## 一句话

> 抢购的难点不是 “选哪个事务模型”，而是**把 5 个事务排出一个失败可退、不白占库存、不被黑产薅的顺序**——顺序错了，再强的模型也救不回来。

## 需求：5 个事务，两条硬约束

商场线上一批数量有限的商品促销：每种商品数量有限，每位用户限购 **2 件**，还要记录每种商品的已售数量与用户的购买历史。

| 事务 | 管什么 | 关键约束 |
|---|---|---|
| **A 商品库存** | 每种商品的剩余可售量 | 不能超卖 |
| **B 用户购买次数** | 每个用户已买几件 | 不能超限购 |
| **C 用户支付** | 扣款 | 第三方扣费，退款麻烦 |
| **D 商品已售数量** | 展示 / 统计用 | 允许延迟 |
| **E 用户购买历史** | 我的订单 | 允许延迟 |

五个事务分属不同服务。放进一个本地事务当然最省事，但抢购是**高并发**场景：长事务持锁会把瞬时流量变成排队，可用性先垮。所以目标不是 “强一致”，而是**最终一致 + 每一笔都能退**。

## 顺序定生死：三种排列的失败模式

| 顺序 | 看起来的好处 | 实际失败模式 |
|---|---|---|
| **先扣库存** | 先保证不超卖 | 没有购买资格的用户（黄牛、黑产）先把库存锁死，正常用户买不到，商品售卖受影响 |
| **先支付** | 钱先到手 | 没库存时用户体验极差，且支付是第三方扣费，退款流程复杂、有手续费 |
| **先扣购买次数** | 先挡掉没资格的人 | 需要保证 “次数扣了、库存没扣” 时能退回来 |

结论：**先扣用户购买次数 → 再扣商品库存 → 再支付 → 支付成功后补已售数量与购买历史**。这样黑产在第一步就被限购挡住，不会污染库存；而 “次数扣了库存没扣” 是最容易补偿的一种中间态——把次数加回去即可。

> 🔑 排序原则：**把最便宜、最能挡住无效流量的校验放最前；把不可逆、要花钱的步骤放最后。**

## 全链路七步

“事件放在哪” 这一步用的是订单 MQ，它和内存队列、CDC 的取舍见 [24.11 最终一致的三条工程载体](24.11-最终一致的三条工程载体.md)。

```text
① 领 token ──► ② 创建订单（拿全局唯一 orderID）──► 写订单 MQ
                                                        │
③ 扣购买次数 ◄──────────────────────────────────────────┘
      │
④ 扣商品库存
      │
⑤ 支付（成功后必须把“支付成功”写进 MQ）
      │
⑥ 已售数量 +1、写购买历史（都按 orderID 幂等）
      │
⑦ 对账服务消费订单 MQ 流水，逐单追踪终态
```

| 步 | 做什么 | 幂等 / 一致性手段 |
|---|---|---|
| ① | 请求 token 服务领一次性 token | token 消费即失效，挡住前端重复提交 |
| ② | 订单服务落订单，拿全局唯一 `orderID`，并写订单 MQ | 本地消息表或事务消息，保证 “订单落库 ⇔ 订单事件在”（[24.6](24.6-本地消息表.md)、[24.7](24.7-事务消息.md)） |
| ③ | 扣用户购买次数（限 2 件） | 按 `orderID` 幂等；失败可回滚（次数加回） |
| ④ | 扣商品库存 | 按 `orderID` 幂等；失败需回滚 ③ |
| ⑤ | 调支付，成功后写 “支付成功” MQ | 支付结果必须可靠落事件，否则 ⑥ 永远不触发 |
| ⑥ | 已售数量 +1、写购买历史 | 更新前检查 `orderID` 是否已处理，可重放 |
| ⑦ | 对账服务消费订单流水 | 兜住 ③④⑤ 的所有异常分支 |

② 里那句 “订单落库 ⇔ 订单事件在” 是整个演练的支点：后面所有步骤都靠 `orderID` 串起来，订单事件丢了，后面的补偿就无从谈起。

## 每一步的失败与回滚

| 失败点 | 已发生的 | 补偿动作 | 谁来做 |
|---|---|---|---|
| ③ 扣次数失败 | 订单已建 | 订单置为失败 / 关闭 | 订单服务（同步返回） |
| ④ 库存不足 | 次数已扣 | 次数加回 | 订单服务或异步补偿任务 |
| ⑤ 支付失败 | 次数、库存已扣 | 库存加回 + 次数加回 | 补偿流程 |
| ⑤ 支付超时 / 用户取消 | 次数、库存已扣 | 同上，且必须先查支付终态再退 | 对账 + 补偿 |
| ⑥ 已售 +1 失败 | 钱已付 | 重试（按 `orderID` 幂等） | 消息消费重试 |
| ⑥ 购买历史写失败 | 钱已付 | 重试 + 对账补写 | 消息消费重试 |

> ⚠️ **“超时” 不等于 “失败”**：支付超时后必须先查支付渠道的终态，确认没扣钱才能退库存与次数。直接按超时回滚，会出现 “钱扣了、货退了” 的双输。

## 状态机：订单号是唯一的串联线索

所有参与方都用同一个 `orderID` 做幂等键，订单本身就是状态机：

| 状态 | 含义 | 允许的下一跳 |
|---|---|---|
| `INIT` | 订单已创建 | 次数已扣 / 已取消 |
| `TIMES_DEDUCTED` | 购买次数已扣 | 库存已扣 / 已回滚 |
| `STOCK_DEDUCTED` | 库存已扣 | 支付中 / 已回滚 |
| `PAYING` | 支付中（结果未知） | 支付成功 / 已回滚 |
| `PAID` | 支付成功 | 完成 / 异常待人工 |
| `DONE` | 已售与历史都已写 | 终态 |
| `CANCELLED` / `ROLLED_BACK` | 已回滚 | 终态 |

状态机带来的两个好处 (幂等键设计的通用规则见 [25.4 幂等设计与去重](../25-并发、冲突与幂等/25.4-幂等设计与去重.md))：

1. **幂等有依据**：重复消息进来，先看状态，已推进过的步骤直接跳过；
2. **补偿有方向**：任何时刻都知道 “已经做了什么、还差什么”，回滚按反向顺序执行。

## 对账服务：最后一道闸

对账服务消费订单 MQ 流水，按 `orderID` 拉取支付终态与各服务状态，分三种情况处理：

| 情况 | 处理 |
|---|---|
| 库存不足 | 直接返还购买次数；也可以走异步回滚（先记待回滚，再由任务执行） |
| 用户取消 / 超时未支付 | 回滚库存与购买次数，订单置 `ROLLED_BACK` |
| 支付成功但 ⑥ 没完成 | 重推 “已售 +1 / 购买历史” 消息，直到终态 |

这套东西不能省：③④⑤ 的补偿失败、消息丢失、消费重复，最终都靠它收敛。[24.9 事务模型选型](24.9-事务模型选型.md)的结论在这里同样成立——**对账不是可选优化，是最终一致方案的组成部分** (见 [24.9 事务模型选型](24.9-事务模型选型.md))。

## 边界：哪些不一致值得用人工兜底

这类方案的收尾值得记住：**分布式事务没有万能钥匙**。有些概率极低的不一致，再引入一套机制去消灭它，带来的复杂度、故障面和维护成本，可能远大于它造成的损失。

判据是两条，缺一不可：

| 判据 | 通过才可用人工 |
|---|---|
| **可发现** | 有定时对账 / 告警能在小时级发现差异 |
| **损失可控** | 单笔损失小、可赔付、不涉及合规 |

两条都过，就用 “告警 + 人工修数” 换掉一套补偿框架；有一条不过 (资损、合规、无法发现)，就必须把自动对账与修复做全。

## 反模式

| 反模式 | 后果 |
|---|---|
| 先扣库存再校验限购 | 黑产用无资格账号锁死库存，正常用户买不到 |
| 超时即回滚 | 钱可能已扣，出现 “扣款 + 退货” 双输 |
| 各服务各用各的幂等键 | 同一订单在 A 服务被当新单、在 B 服务被当重复 |
| 补偿不查支付终态 | 重复退款或该退未退 |
| 只做正向流程，不做对账 | 中间态永远停在 “处理中”，无人发现 |
| 所有步骤塞进一个长事务 | 抢购峰值下锁等待排队，可用性先崩 |
| 为极低概率差异硬上一套框架 | 复杂度与故障面上升，维护成本超过损失 |

顺序排错造成的真实损失，复盘见 [85.1 超卖与资损](../../附录/85-故障案例与复盘/85.1-超卖与资损.md)。

## 自检

**Q1** 为什么抢购要先扣 “购买次数”，而不是先扣库存？

▸ 答案：因为库存是**共享的稀缺资源**，次数是**每用户私有的准入资格**。先扣库存时，无资格用户 (黄牛小号) 可以反复锁库存，把商品卖光却没人能付款；先扣次数等于先做准入过滤，进入库存环节的都是有资格的人。并且 “次数扣了、库存没扣” 是最容易补偿的中间态。

**Q2** 第 ⑤ 步支付成功，为什么还要求 “把支付成功写进 MQ”？

▸ 答案：因为 ⑥ 的已售数量与购买历史是异步的，它们唯一可靠的触发源就是这条事件。支付成功但事件丢失，用户就会 “付了钱、订单没完成”。用本地消息表或事务消息保证 “支付落库 ⇔ 事件存在”，才能让 ⑥ 有重试的依据。

**Q3** 支付超时，为什么不能直接回滚库存和次数？

▸ 答案：超时只说明 “没拿到结果”，不说明 “没扣款”。第三方支付可能已经扣款只是回包丢了。必须先查支付终态：确认失败才回滚；确认成功则继续推进 ⑥；仍未知则挂起并交给对账，绝不能默认失败。

**Q4** 整条链路里，`orderID` 只在第 ② 步出现一次，为什么说它是支点？

▸ 答案：因为它是所有参与方唯一的**共同幂等键与关联键**：③④ 用它去重，⑥ 用它做 “更新前检查”，⑦ 用它把订单、支付、库存、历史串成一条可对账的记录。没有全局唯一 ID，重复消息就无法判断 “这一步做过没有”，补偿也无从定位。

**Q5** 什么情况下，这个抢购链路可以不用对账服务？

▸ 答案：只有当差异**不可能发生**或**损失可忽略且可发现**时才能省。实际上 ③④⑤ 的补偿失败、消息丢失、消费重复必然存在，所以对账不能省；能省的是 “实时对账”，退化成 T+1 对账 + 告警 + 人工。判据是损失期望与可发现性，不是 “概率小”。
