      55.1 发布策略 (滚动 / 蓝绿 / 金丝雀 / AB 测试)

      一句话

      发布策略决定 “新版本怎么替换旧版本”，核心权衡是风险 ↔ 成本 ↔ 速度。 没有最好的策略，只有最适合你回滚能力的策略。

      五种策略一张图看全

      策略 做法 停机 风险 回滚速度 资源成本 实现难度
      停机发布 停服务 → 更新 → 启动 有 中 慢 1× 最低
      滚动发布 逐台替换，边更新边服务 无 中 慢（逐台滚回） 1× 低
      蓝绿发布 备一套全新环境，流量一次切换 无 低 秒级 2× 中
      金丝雀发布 新版本先给 1–5% 流量，观察后放量 无 最低 快（切走流量） 略 >1× 高
      AB 测试 两版同时在线，按用户分组，用数据判哪个更好 无 低（不是替换问题） 快（关掉一组） ≥2× 高（要统计）

      逐个拆解

      ① 停机发布 (Big Bang / Recreate)

      做法：停掉旧版本 → 部署新版本 → 启动。

      • 优点：最简单，没有 “新旧共存” 的问题，不用考虑兼容。
      • 缺点：有停机窗口 (哪怕 10 秒)。
      • 适合：内部系统、半夜低峰可停机的服务、早期产品。
      • 现实：K8s 里的 Recreate 策略就是它——先杀光旧 Pod，再起新 Pod。

      💡 别瞧不起它。“能停机” 是一种巨大的奢侈——它意味着你可以不做任何兼容性设计。很多系统为了 “不停机”，付出了远超停机窗口价值的复杂度。

      ② 滚动发布 (Rolling Update)

      做法：一台一台地替换。更新完一个实例、验证通过，再更新下一个，直到全部换成新版本。

      • 优点：不停机、不需要额外资源。
      • 缺点：发布期间新旧版本同时在线 (这是关键，见下面的铁律)；回滚也是滚动的 (慢)。
      • 适合：无状态服务。这是 K8s 的默认策略。

      K8s 里控制滚动速度的两个参数：

      spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 滚动期间最多多起几个新 Pod（腾挪空间）
      maxUnavailable: 0  # 滚动期间最多允许几个 Pod 不可用（0 = 不中断服务）

      🔑 滚动发布的命门是 “新旧共存窗口”：发布过程中，一部分请求打到新版本，一部分打到旧版本。 如果新旧版本不兼容 (接口变了、数据格式变了)，这个窗口里就会随机报错——而且是 “时好时坏” 的随机报错，最难查。

      ③ 蓝绿发布 (Blue-Green)

      做法：备一套完整的新环境 (绿)，旧环境 (蓝) 继续服务；新环境验证通过后，把流量一次性从蓝切到绿。

              ┌─────┐  切换  ┌─────┐
用户 ──▶│ 蓝  │ ─────▶ │ 绿  │
        │旧版本│        │新版本│
        └─────┘        └─────┘
      • 优点：回滚是秒级的 (把流量切回蓝即可)，风险低。
      • 缺点：资源成本翻倍 (两套环境同时存在)。
      • 关键问题——数据库怎么办：
      方案 做法 代价
      共享一个数据库 蓝绿只切应用，不切数据库 简单，但数据库 schema 变更必须向后兼容（否则绿的代码读不懂蓝的数据）
      各自独立数据库 蓝绿各带一套库 切流量前要处理数据同步/迁移，复杂
      • 适合：核心链路、对 “回滚要快” 有强要求的场景。但先想清楚数据库，再谈蓝绿。

      ⚠️ 蓝绿最大的坑：只做了应用蓝绿，没做数据库兼容。结果一切到绿，绿代码读不懂旧表结构报错；想切回蓝，蓝代码也读不懂绿改过的数据——卡死，两头都不是。

      ④ 金丝雀发布 (Canary)

      做法：新版本先只接 1–5% 流量，盯着指标看；没问题再逐步放量 (5% → 25% → 50% → 100%)。

      用户流量 ──┬── 95% ──▶ 旧版本
           └── 5%  ──▶ 新版本（金丝雀）← 出了问题只炸这 5%
      • 优点：风险最小——真出了问题，只影响一小撮用户，且能立刻切走。
      • 缺点：需要流量治理能力 (按比例 / 按用户路由)；实现和运维成本高。
      • 怎么分流：
      方式 做法
      权重路由 网关/Ingress 按 95:5 比例分发
      用户分片 按 userID % N 或 hash 把固定用户导到新版本
      Service Mesh Istio 的 traffic shifting，按权重切
      • 看什么指标再放量 (不是 “看看没报错”)：
      指标 看什么
      错误率 金丝雀版本错误率是否显著高于旧版
      延迟 P99 是否恶化
      业务指标 下单成功率、支付成功率
      • 适合：有流量治理能力、流量足够大的服务 (流量太小，5% 样本没意义)。

      ⑤ AB 测试 (A/B Testing)

      上表是四种“替换版本”的策略，AB 测试是第五种，但和它们不在同一坐标上：前四种回答“新版本怎么替换旧版本”，AB 回答“两个版本同时在线，哪个更好”。原文明确只有这 5 种，没有第六、第七种。

      做法：同时上线两个版本，拉一部分用户当“小白鼠”，用科学的观测比较两个版本的表现（可用性、受欢迎程度、可见性），再决定推广哪个。

      判据：三种策略的动机经常被混为一谈，原文的分法最锋利：

      策略 你担心什么 两版怎么共存 什么时候结束
      蓝绿 停机（切换风险） 两套环境，只有一套接流量 流量切完即结束
      金丝雀 新版本的质量（有没有 bug） 新旧按比例同时服务 全量即结束
      AB 测试 新版本的功能（用户喜不喜欢） 两版同时在线，按用户分组 拿到统计结论才结束

      🔑 原文原话：“蓝绿部署是为了不停机，灰度部署是对新版本的质量没信心。而 AB 测试是对新版的功能没信心。注意，一个是质量，一个是功能。”

      适合：网站 UI 大改版、推荐算法更新、流程改变——不知道新版本是否会得到用户青睐或更好的体验，必须收集用户数据才能判断。

      严谨性五要素（原文）：科学的实验设计、采样样本代表性、流量分割、小流量测试、结论可推广到全部流量时可信。少任何一条，AB 就退化成“上了一个新版本，然后各说各话”。

      与灰度的关系：AB 测试包含了灰度发布的功能——如果观测的只是“有没有 bug”，那就是灰度；如果还要观测用户数据指标，就可以做成自动化：新版本数据好就自动多切一点流量，不行就换一批样本再试。

      金丝雀的两个经典细节：90/10 与“按什么选人”

      经典起点是 90/10：原文的示例是 90% 请求走老版本、10% 走新版本，没问题再逐步放大、缩小老版本。它与上面 1–5% 起手的差别不是对错，而是流量规模与信心：流量足够大时 10% 也能很快积累样本；流量小的时候 10% 等于把更多风险一次放出去，所以先 1–5%。

      放量顺序按用户类型走（多租户 / SaaS 常用）：内部用户 → 一般用户 → 大客户。前两档用来暴露问题，大客户放到最后，因为他们的故障成本最高。

      “按什么选人”有五种维度（原文列举）：

      维度 怎么用 注意
      浏览器 cookie 给命中标记的用户持续分配同一版本 清 cookie / 换设备会换组，实验组不纯净
      查询参数 URL 带参数决定分组（如 ?v=b） 用户可手改，只适合体验类实验，不能用于权限或计费
      地理位置 按国家 / 城市 / 机房分流 不同地区用户行为差异大，结论不能直接外推
      浏览器版本 / 屏幕尺寸 / OS 按客户端特征选人 特征随升级变化，样本会漂
      客户端语言 按语言 / 地区版本选人 与地理位置相关但不等价（同一地区多语言）

      ⚠️ 别把“按实例滚”当金丝雀：金丝雀是按用户切（同一批用户始终看到同一版本），按实例滚是滚动发布——同一用户会在两个版本间跳。

      三条铁律

      1. **回滚能力比发布能力更重要。**判断发布策略好不好，先问 “回滚要几秒、演练过没”。
      2. **滚动 / 金丝雀期间，新旧版本必须兼容。**因为两者会同时在线——兼容不是可选项，是前提。
      3. 数据库变更必须走 Expand-Contract (先加列 → 迁移 → 再删列)。否则一旦改了表，新旧两个版本都没法回滚。(详细见 55.4 数据库变更管理 (Expand-Contract))

      怎么选：一张决策表

      你的情况 选
      内部系统、能接受停机 停机发布（别为它过度设计）
      无状态服务、要不停机、想简单 滚动发布（K8s 默认）
      核心链路、回滚必须秒级、能接受双倍成本 蓝绿发布（先解决数据库）
      流量大、有流量治理、要风险最小 金丝雀发布

      🔑 现实里最常见的是组合：滚动 + 金丝雀——先放 5% 金丝雀，再滚动全量。既拿了金丝雀的低风险，又不用长期养两套环境。

      设备固件的“发布”比服务发布多两个约束：设备可能永远不回来（要靠 A/B 分区 + 试启动计数自动回滚），且下载要能断点续传——见 69.5 固件升级 (OTA)。

      反模式

      反模式 后果
      蓝绿只切应用、不处理数据库 切过去报错，切回来也报错，卡死
      金丝雀放量不看指标，只"看看没报错" 5% 时的隐性 bug 在 100% 时爆炸
      滚动期间新旧接口不兼容 随机报错，时好时坏，最难查
      没有演练过回滚 真出事的回滚，大概率失败
      能停机却为“不停机”硬上蓝绿/金丝雀 付出远超停机窗口价值的复杂度，还要长期养两套环境、维护兼容性
      流量太小的服务用 5% 金丝雀放量 5% 样本太少、指标噪声大，好坏判断不出来，发布只是被拖慢

      落到数字：批次、观察窗口与阈值

      策略 批次 观察窗口 自动回滚阈值
      滚动 25% × 4 每批 2–5min 错误率 > 1% 或 P99 > 基线 1.5×
      蓝绿 0% → 100% 切换后 5–15min 同上，回滚 = 切回旧池
      金丝雀 1% → 5% → 25% → 100% 每档 5–30min 错误率 / 延迟 / 业务指标三选二
      停机 — — 有维护窗口才用
      # Argo Rollouts 风格（示意）
strategy:
  canary:
    steps:
      - setWeight: 1
      - pause: {duration: 10m}
      - setWeight: 5
      - pause: {duration: 10m}
      - analysis: {templates: [{templateName: error-rate}]}
      - setWeight: 25

      关键不在 “怎么切”，而在 “切多少、看多久、什么指标算坏”——这三件事没有数字，金丝雀就只是 “慢一点的滚动”。

      自检

      Q1 你选蓝绿发布，但应用绿环境读旧数据库时一直报错。根因是什么？怎么提前避免？

      ▸ 答案：只做了应用蓝绿，没做数据库兼容。根因是数据库 schema 变更没走 Expand-Contract——绿代码读不懂旧表结构。避免方法：先做向后兼容的 schema 变更 (先加列)，再切换；回滚时蓝代码也能读懂绿改过的数据。

      Q2 滚动发布期间，监控显示错误率 “时好时坏”、随机波动。最可能的原因是什么？

      ▸ 答案：新旧版本不兼容。发布窗口里一部分请求落到新版本、一部分落到旧版本，接口或数据格式不一致导致随机报错。滚动发布的前提就是 “新旧兼容”——这个前提没满足，滚动就是事故。

      Q3 金丝雀的 “坏” 用什么指标判定？

      ▸ 答案：至少两类：技术指标（错误率、P99、CPU）与业务指标（下单成功率、支付转化）。只看技术指标会漏掉 “接口 200 但业务失败”；只看业务指标则反应太慢。常见做法是 “错误率 1% 或业务成功率下降 2% 即回滚”。

      Q4 蓝绿发布最大的隐性成本是什么？

      ▸ 答案：双倍资源与数据兼容：绿环境要完整跑起来，资源翻倍；更贵的是数据库要同时兼容新旧代码（Expand-Contract），否则切换瞬间就报错。蓝绿不是 “点一下切流量”，而是 “两套兼容性都要维护”。

      Q5 数据库变更怎么和发布策略配合？

      ▸ 答案：走 Expand → Migrate → Contract：先加列/加表（新旧都能跑），再双写/回填，最后删旧列。任何 “先删后发” 的做法，都会让滚动/蓝绿在切换窗口里直接失败——回滚也没用，因为旧代码已经读不到数据了。

      Q6 蓝绿、金丝雀、AB 测试各自回答什么问题？把三者混用会出什么错？

      ▸ 答案：蓝绿回答“怎么不停机地把流量交给新版本”（担心停机与切换风险）；金丝雀回答“新版本质量行不行”（担心 bug）；AB 回答“新功能用户喜不喜欢”（担心功能）。混用的典型错法：用 AB 的名义做金丝雀——只看错误率不设对照指标，最后既证明不了功能好坏，也浪费了两版并存的成本；反过来用金丝雀的名义做 AB——全量后才发现用户不买账。

      Q7 同一节里既写“金丝雀先 1–5%”，又写原文的“90/10”，两者矛盾吗？

      ▸ 答案：不矛盾，起点取决于流量规模与样本速度。90/10 是多租户 / 大流量场景的经典切法：10% 已经能快速积累足够样本，且可以先只对内部用户开。流量小的服务 10% 风险太大、样本又不够，先从 1–5% 起步更稳。关键是“先小后大 + 每档看指标”，不是那个具体百分比。

      Q8 用查询参数（如 ?v=b）做 AB 分组有什么风险？什么场景不该用？

      ▸ 答案：参数在用户手里，可以手改、可以分享链接把别人带进同一组，实验组会被污染且不可复现。所以它只适合“体验类、无副作用”的实验；涉及权限、计费、库存、风控的分流不能用查询参数，要用 cookie / 用户 ID / 网关注入的标签，并且保证同一用户稳定落在同一组。
