# 55.8 应用框架：把启动七步和退出三步写成模板

## 一句话

> 应用框架不是"又一个 Web 框架"，它固化的是**每个进程都要重写一遍的启动/退出顺序**——解析参数、读配置、补默认值、校验、装日志、起组件、报就绪，退出时反过来；业务只实现一个 `RunFunc`，顺序由框架保证。顺序错一次，就是一次"日志还没初始化就 panic"或"数据库先关了、请求还在飞"的线上事故。

> 来源：三个真实 Go 项目的实现——iam 的 `pkg/app` + `pkg/shutdown`（回调式退出）、onex 的 `pkg/app`（k8s `component-base` 风格，`SetupSignalHandler` + `stopCh`）、fastgo 的 `cmd/fg-apiserver/app`（最简版）。对比、坑与可运行实测为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| "应用框架 = Web 框架" | 路由与中间件只是最外层；真正难的是装配顺序、配置来源、组件生命周期 |
| "main 里多写几行就行" | 一个服务可以，三个服务必漂移：日志初始化位置、退出顺序、默认值补全各写各的 |
| "优雅关闭是框架自动给的" | 框架只负责"顺序 + 超时"；DB 连接池、消息消费者、后台 goroutine 必须显式注册 |
| "先起服务，日志慢慢补" | 启动阶段（读配置、连 DB）恰恰是最容易失败的一段，没日志等于盲飞 |
| "组件越多越该手写 main" | 恰恰相反：组件越多，越需要模板固定顺序，否则每个二进制都是一次新的排列组合 |

## 同一个骨架的三种规模

| 维度 | fastgo | iam | onex |
|---|---|---|---|
| 代码位置 | `cmd/fg-apiserver/app/`（`main.go` 31 行 + `server.go` 149 行） | `pkg/app/`（`app.go` 310 行 + `cmd.go` 131 行 + `config.go` 96 行） | `pkg/app/`（`app.go` 317 行 + `options.go` 95 行） |
| 启动编排 | `run()` 里顺序写死 7 步 | `App` 结构体 + `Option` 函数 | `App` 结构体 + k8s `cli.Run` 风格 |
| 配置 | cobra + viper（`onInitialize`） | cobra + viper + `CliOptions` | cobra + viper + `CliOptions` |
| 退出 | `signal.Notify` + `http.Server.Shutdown(ctx 10s)` | `shutdown.Manager`（回调 + 并行 + `os.Exit`） | `genericapiserver.SetupSignalHandler()` + `stopCh` |
| 适合 | 单二进制、教学与起步 | 多进程、多组件企业项目 | 云原生、K8s 生态、operator 类项目 |

## 七步模板：三步定义，四步由框架执行

fastgo 的 `run()` 就是最小可用的七步（真实代码，删去错误分支注释）：

```go
func run(opts *options.ServerOptions) error {
	version.PrintAndExitIfRequested()          // 1. 版本：--version 直接退出
	initLog()                                  // 2. 日志：必须早于一切组件
	if err := viper.Unmarshal(opts); err != nil { // 3. 配置：把 flag/env/file 合进 opts
		return err
	}
	if err := opts.Validate(); err != nil {    // 4. 校验：非法配置不许启动
		return err
	}
	cfg, err := opts.Config()                  // 5. 转成运行期配置
	if err != nil {
		return err
	}
	server, err := cfg.NewServer()             // 6. 装配：DB → store → 路由 → HTTP Server
	if err != nil {
		return err
	}
	return server.Run()                        // 7. 运行 + 等信号 + 优雅退出
}
```

onex/iam 把这七步搬进 `App`，变成**模板方法**：`NewApp(name, opts...)` 固定执行顺序，业务只传 `WithRunFunc`：

| 步 | 框架做什么 | 典型失败 | 失败后谁兜底 |
|---|---|---|---|
| 1 版本 | `PrintAndExitIfRequested` | 无 | 退出码 0 |
| 2 参数 | cobra 解析、`SilenceUsage` | 未知 flag | 打印错误，退出码 1 |
| 3 配置 | `viper.BindPFlags` + `Unmarshal` | YAML 格式错 | 返回 error，日志已可用 |
| 4 Complete | 补默认值（端口、目录、超时） | 默认值依赖环境 | 返回 error |
| 5 Validate | 校验并**聚合全部错误** | 只报第一条 | iam 用 `errors.NewAggregate`；onex 自定义命令用 `utilerrors.NewAggregate` |
| 6 日志 | `log.Init` + `defer log.Sync` | 输出路径不可写 | 返回 error |
| 7 运行 | 健康检查 → `RunFunc` | 端口占用 | 返回 error，退出码 1 |

## 三段式选项：Flags / Complete / Validate

onex 的 `pkg/app/options.go` 把"可配置组件"抽象成三个方法（真实代码）：

```go
// CliOptions abstracts configuration options for reading
// parameters from the command line.
type CliOptions interface {
	// Flags 把选项按"段"注册成命令行参数（global/generic/...）
	Flags() cliflag.NamedFlagSets
	// Complete 补齐默认值：可能依赖其它字段或环境（home 目录、主机名）
	Complete() error
	// Validate 校验：返回聚合错误，一次把配置问题报全
	Validate() error
}
```

三个方法各有存在理由，少一个都会出问题：

| 方法 | 为什么单独存在 | 缺了它的后果 |
|---|---|---|
| `Flags()` | 选项要能"按段展示"（`--help` 分组），且 flag 名与 YAML key 要对齐 | 帮助信息一坨，用户不知道改哪个 |
| `Complete()` | 默认值可能依赖**其它字段**（如 `--config-dir` 决定证书路径） | 默认值散在 `NewServer` 里，校验时还是空 |
| `Validate()` | 配置错误要**一次性报全**，且必须在建连接池之前 | 启动到一半才发现端口非法 |

`App` 本身用**选项模式**（`Option func(*App)`）而非几十个参数：`WithOptions`、`WithRunFunc`、`WithHealthCheckFunc`、`WithWatchConfig`——加一个能力不改构造签名。与 [26.3 整洁架构](../../L2-架构风格/26-分层与依赖/26.3-整洁架构.md) 里的 `wire` 分工不同：**wire 管"构造依赖图"（编译期），App 管"运行时顺序"（进程生命周期）**，两者不是竞品。

## 配置三层来源：谁覆盖谁

viper 的优先级是固定的一条链：**显式 `Set` > flag > env > 配置文件 > 默认值**。三个项目都把这条链焊死在同一处：

| 项目 | 配置入口 | 搜索路径 | 环境变量规则 |
|---|---|---|---|
| fastgo | `onInitialize()` | `$HOME/.fastgo/`、`.` | 前缀 `FASTGO`，`.`/`-` 转 `_` |
| iam / onex | `AddConfigFlag(fs, name, watch)` | `.`、`$HOME/.<前缀>/`、`/etc/<前缀>/` | 前缀 = 二进制名大写（`ONEX_APISERVER`） |

onex 还多了 `WithWatchConfig()`：`viper.WatchConfig()` + `fsnotify`，配置文件变更时打一条日志（注意：**viper 只负责重新读进内存，不会自动重建组件**；热更新要自己挂 `OnConfigChange` 回调，见 [54.5 配置注入](../../L5-工程效能/54-制品与部署/54.5-配置注入.md)）。

## 退出：三条路线，三个坑

退出比启动难，因为它有**时间预算**（K8s 的 `terminationGracePeriodSeconds`）和**顺序依赖**（先停入口，再排空，再关资源）。三个项目正好是三条路线：

```go
// 路线一：fastgo —— 内联，单组件够用（真实代码，删去日志）
quit := make(chan os.Signal, 1)
signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
<-quit
ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
return s.srv.Shutdown(ctx) // 排空在途请求，超时强制返回
```

```go
// 路线二：iam —— 回调式，多组件统一管理（pkg/shutdown）
gs := shutdown.New()
gs.AddShutdownManager(posixsignal.NewPosixSignalManager()) // 信号源
gs.AddShutdownCallback(shutdown.ShutdownFunc(func(string) error {
	mysqlStore.Close()        // 组件关闭：注册即执行
	s.gRPCAPIServer.Close()
	s.genericAPIServer.Close()
	return nil
}))
gs.Start() // 监听 SIGINT/SIGTERM
```

```go
// 路线三：onex —— 上下文式，K8s 组件通用（cmd/onex-apiserver/app/server.go）
return Run(completedOptions, genericapiserver.SetupSignalHandler())
// Run(opts, stopCh) 内部把 stopCh 传给 GenericAPIServer，
// ctx 取消后各组件按框架约定的顺序停止，defer 正常执行。
```

三条路线的差别不在"能不能停"，而在**顺序、超时、defer** 三件事：

| 维度 | fastgo 内联 | iam 回调式 | onex/ctx 式 |
|---|---|---|---|
| 信号捕获 | 自己的 `signal.Notify` | `posixsignal` 管理器 | `SetupSignalHandler`（k8s） |
| 关闭顺序 | 单组件，无所谓 | **并行且无序** | 由 Run 内部顺序决定 |
| 超时 | `Shutdown(ctx, 10s)` 自带 | **没有**，靠外部宽限期 | 由 `stopCh` + 上层超时 |
| main 的 defer | 正常执行 | **`os.Exit(0)` 直接退出，defer 不执行** | 正常执行 |
| 适合 | 单 HTTP 服务 | 已有多组件、想统一注册 | 云原生项目 |

> ⚠️ **iam 回调式的三个坑**（读源码确认，不是猜的）：① `StartShutdown` 对每个 callback 起一个 goroutine 再 `wg.Wait()`——并行意味着"关 DB"和"停 HTTP"同时发生，DB 可能先于在途请求关闭；② 管理器本身没有超时，某个 callback 卡住，进程就卡到 K8s 强杀；③ `posixsignal.ShutdownFinish` 里是 `os.Exit(0)`，主 goroutine 里的 `defer log.Sync()` 不会执行——**日志刷盘必须做成 callback 之一**。

> 🔑 新项目我选 ctx 式（路线三）：顺序写在 `Run` 里、超时来自部署侧、defer 不被跳过。已有回调式框架的项目，至少要补三件事：**关闭顺序 = 反向依赖顺序**（先摘流量 → 排空 → 停后台任务 → 关 DB）、**总超时 < 宽限期**、**日志刷盘进 callback**。

## 可运行：最小 App 骨架 + SIGTERM 实测

下面是一个能直接跑的骨架（本机实现约 150 行，含七步、三段式选项、并行/串行两种退出、超时兜底；此处贴核心，`logf`/`runHook`/`main` 等辅助函数略）：

```go
type App struct {
	name    string
	opts    CliOptions
	run     func() error
	hooks   []ShutdownFunc
	timeout time.Duration
	serial  bool
	start   time.Time
}

// Run 是模板方法：七步顺序固定，业务只填 run 和 hook。
func (a *App) Run() error {
	a.logf("phase 1/7 parse flags")
	a.logf("phase 2/7 read config")
	if err := a.opts.Complete(); err != nil { // 3
		return err
	}
	if err := a.opts.Validate(); err != nil { // 4
		return fmt.Errorf("validate: %w", err)
	}
	a.logf("phase 5/7 init logger")
	a.logf("phase 6/7 start health server")
	a.logf("phase 7/7 run business")
	if err := a.run(); err != nil {
		return err
	}
	quit := make(chan os.Signal, 1)
	signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
	a.logf("received %s, shutting down", <-quit)
	return a.shutdown()
}

func (a *App) shutdown() error {
	ctx, cancel := context.WithTimeout(context.Background(), a.timeout)
	defer cancel()
	var wg sync.WaitGroup
	for i, h := range a.hooks {
		wg.Add(1)
		if a.serial {
			a.runHook(ctx, i, h, &wg) // 串行：按注册顺序
		} else {
			go a.runHook(ctx, i, h, &wg) // 并行：同 iam
		}
	}
	done := make(chan struct{})
	go func() { wg.Wait(); close(done) }()
	select {
	case <-done:
		return nil // 全部关完，exit 0
	case <-ctx.Done():
		return fmt.Errorf("shutdown timeout") // 超时兜底，exit 1
	}
}
```

三个组件用 30ms / 80ms / 120ms 模拟"关 DB / 停在途 / 刷缓存"，`kill -TERM` 触发退出，实测（Go 1.27.1，macOS/arm64，每模式 3 次）：

| 模式 | 3 次实测耗时 | 结果 | 说明 |
|---|---|---|---|
| 并行（默认） | 122.4 / 122.3 / 120.9 ms | 全部 hook 完成，exit 0 | 总耗时 = 最慢 hook，不是三者之和 |
| 串行（`-serial`） | 233.5 / 233.7 / 243.0 ms | 全部 hook 完成，exit 0 | 总耗时 = 三者之和，比并行慢 **111 ms（47.6%）** |
| 并行 + 100ms 预算 | 100.2 / 101.7 / 101.1 ms | **强制退出，exit 1** | 120ms 的 hook 没跑完——超时保护生效，但代价是缓存没刷 |

真实输出（并行模式，节选）：

```text
[   0.1ms] phase 5/7 init logger
[   0.1ms] phase 7/7 run business
[ 816.1ms] received terminated, shutting down
[   0.1ms] hook 0 start
[   0.2ms] hook 1 start
[   0.2ms] hook 2 start
[  30.4ms] hook 0 done
[  85.6ms] hook 1 done
[ 120.2ms] hook 2 done
[ 120.3ms] all hooks done, exit code 0
```

结论从数字里来，不靠感觉：**并行把退出耗时压到最慢组件，代价是失去顺序**；超时必须大于最慢 hook，否则"排空"变成"强杀"。组件之间若存在依赖（DB 必须最后关），只能串行或分组——两条都做不到时，说明退出设计本身有问题。

## 反模式

| 反模式 | 后果 |
|---|---|
| `main` 里手写几百行启动逻辑，每个二进制复制一份 | 六个组件的日志初始化位置各不相同，排查靠猜 |
| 日志初始化晚于第一个组件 | 读配置/连 DB 失败时没有任何输出，启动失败无从下手 |
| 配置校验散落在 `NewServer` 各层 | 校验失败时半启动：连接池建了、goroutine 起了，却没人收 |
| 按"注册顺序"关闭组件 | 先关 DB 再停 HTTP，在途请求全部 500 |
| 只 `Close()` listener，不等在途请求 | 灰度发布期间 5xx 尖刺，回滚误判成新版本 bug |
| 在退出 hook 里做慢操作（导出快照、等 MQ flush 十分钟） | 超过宽限期被 SIGKILL，日志都没来得及刷 |
| 在业务代码里调用 `os.Exit` | defer 全部跳过，最难查的一类"日志丢失" |

## 自检

Q1 七步里为什么"日志初始化"必须早于"读配置"和"建连接池"？
▸ 答案：前两步正是最容易失败的环节（YAML 写错、DB 连不上）；日志没就绪时，框架只能 panic 或静默退出，排障没有入口。日志是启动阶段唯一的观测手段。

Q2 `Complete()` 为什么不能并进 `Validate()`？
▸ 答案：默认值可能依赖其它字段或环境（`--config-dir` 决定证书路径、home 目录决定配置搜索根），必须在"全部字段就位"后、校验前补；合并后校验看到的是空值，报错反而误导。

Q3 iam 的回调式退出有三个坑，分别对应哪行代码？
▸ 答案：① `StartShutdown` 里每个 callback 一个 goroutine + `wg.Wait()`——并行无序；② 管理器只有 `Wait`、没有 context 超时——hook 卡住则进程卡住；③ `posixsignal.ShutdownFinish` 的 `os.Exit(0)`——主 goroutine 的 defer（如 `log.Sync`）被跳过。

Q4 并行退出比串行快 111ms，为什么不能一律并行？
▸ 答案：并行只适合互不依赖的组件；DB/连接池必须等 HTTP 排空之后才能关，否则在途请求拿到已关闭的连接。有依赖就串行或分组，快 111ms 不值得一次 5xx 尖刺。

Q5 超时预算怎么定？为什么实测里 100ms 预算会让 120ms 的 hook 没跑完？
▸ 答案：总预算 < 部署侧宽限期（留摘流量与刷日志的余量），且 > 最慢 hook；100ms < 120ms 时超时兜底先触发，最后那个组件只能被强杀——这就是"排空失败"的真实形态。

Q6 App 框架和 wire 到底分工在哪？
▸ 答案：wire 解决"对象怎么造出来"（编译期依赖图，构造顺序静态确定）；App 解决"进程先做什么后做什么"（运行时顺序：配置→日志→组件→信号→退出）。两者互补，不能互相替代。
