# 55.7 优雅停机：发布不丢请求的五个动作

## 一句话

> 发布丢请求的根因通常不是新版本有 bug，而是**旧实例在“摘流量生效”之前就退出了**：摘除延迟（1–3s）与 `SIGTERM` 几乎同时发生，而流量还在往它身上打。优雅停机 = 等摘除 → 停收新连接 → 排空在途 → 关资源 → 超时兜底，五步缺一步就是 5xx。

> 来源：优雅关闭的五个动作、`preStop`/宽限期与排空在途的配合来自极客时间《手把手带你写一个 Web 框架》第 6 讲「重启：如何进行优雅关闭」；丢请求模型与参数公式为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “K8s 会处理好，不用管” | `SIGTERM` 与 Endpoints 摘除**同时**发生，而 kube-proxy/Ingress 的规则更新有 1–3s 延迟；这段时间流量还在进来（[7.3 Service 与 Ingress](../../L0-运行时底座/7-容器编排/7.3-Service与Ingress.md) 的解析里已经指出这个竞态） |
| “`preStop` 里 sleep 几秒就行” | sleep 只覆盖“摘除延迟”，不覆盖“在途请求”：进程退出时正在处理的那批请求会被直接掐断 |
| “关了 listener 就没有新请求了” | keep-alive 长连接上，新请求会复用**已建立**的连接；只关 listener 拦不住它们 |
| “优雅停机是框架的事” | 它是三方配合：**部署编排**给宽限期、**负载均衡**负责摘除、**应用框架**负责排空；只做一头都白搭 |

## 一次 SIGTERM 之后，到底发生了什么

```text
控制面                                    数据面
─────────────────────────────────────────────────────────────
t=0   删除 Pod / 滚动更新
      ├─ Endpoints 标记 terminating
      └─ 容器收到 SIGTERM          ┐
                                    │  这两个几乎同时发生
                                    ▼
t=0..D  kube-proxy / Ingress 规则同步（D ≈ 1–3s）
                                    ┌── 这段时间流量仍然打到旧实例
                                    └── 应用如果已退出 → 请求全部失败

t=D    流量真正停止
t=D..  应用排空在途请求（≤ P99），关闭 DB 连接池、消息通道、注册中心
t=grace 宽限期到，进程若还活着 → SIGKILL
```

**丢请求的窗口就是 `[0, D]`**：它由摘除机制决定，不由代码质量决定。这也是为什么“新版本明明没问题，发布却 5xx”。

## 五个动作

| 动作 | 谁负责 | 典型做法 | 不做会怎样 |
|---|---|---|---|
| ① **等摘除** | 部署编排 / 应用 | `preStop: sleep 3`，或应用内收到信号后先延迟 D 秒再动 | `[0, D)` 内进来的请求全失败 |
| ② **停收新连接** | 应用 | 关闭 listener、把健康检查置为不健康 | 新连接持续涌入，永远排不空 |
| ③ **排空在途** | 应用 | `server.Shutdown(ctx)` / 等待 in-flight 计数归零 | 处理到一半的请求被掐断，出现“写了一半”的脏数据 |
| ④ **关资源** | 应用 | 关 DB 连接池、提交/关闭消息通道、从注册中心摘除 | 连接池被杀导致下游报错；消息丢失 |
| ⑤ **超时兜底** | 部署编排 | `terminationGracePeriodSeconds` > D + 排空时间 + 余量 | 卡住的实例永远不退，滚动更新被拖死；或被 SIGKILL 强杀 |

顺序不能乱：**先停收，再排空，最后关资源**。反过来做，会在排空阶段发现依赖已经没了。

## 参数怎么定：三个数，一条公式

| 参数 | 怎么定 | 常见坑 |
|---|---|---|
| **D（摘除延迟）** | 实测：从发删除到该实例 QPS 归零的时间；或取上游 LB 健康检查间隔 × 失败阈值 | 拍脑袋填 1s，实际规则同步要 3s |
| **drain（排空上限）** | 取 P99 延迟或“最大请求超时”，不是平均值 | 用均值会让 1% 的长请求被掐断 |
| **grace（宽限期）** | `D + drain + 余量(30%)` | 等于 `D + drain` 时，边界抖动就会 SIGKILL |

一个自检公式：

```text
terminationGracePeriodSeconds ≥ D + P99(或最大超时) × 1.3
```

**长连接要单独处理**：WebSocket / SSE / gRPC stream 的连接不会因为“停收新连接”而结束。做法是主动发关闭帧（或 `GOAWAY`），并给客户端重连退避；否则宽限期到点，连接被强杀，用户看到的是“突然断线”。

## 可运行：算一下“立刻退出”丢多少

```python
#!/usr/bin/env python3
"""drain.py —— 滚动发布时，「立刻退出」到底会丢多少请求。

模型（参数是假设，按自己集群改）：
  实例数 3，总 QPS 2000 → 每个实例约 667 QPS
  摘除生效延迟 D = 2.0s（kube-proxy 规则同步，量级 1–3s）
  P99 延迟 200ms（排空在途请求需要的上限）
  naive  ：收到 SIGTERM 立刻关 listener 并退出
  graceful：先继续服务 D，再停止接新连接、排空在途（≤P99）
"""
INSTANCES, QPS, D, P99 = 3, 2000, 2.0, 0.2

per_instance = QPS / INSTANCES          # 每实例每秒请求数


def naive():
    """退出瞬间起、摘除生效前，打到本实例的请求全部失败。"""
    return per_instance * D


def graceful():
    """继续服务到摘除生效；之后排空在途，窗口内请求都已正常返回。"""
    return 0.0


for name, fn in (("立刻退出", naive), ("优雅停机", graceful)):
    lost = fn()
    print(f"{name:<8} 单实例丢失请求 ≈ {lost:>7.0f} 个；"
          f"按 {QPS} QPS 算，错误率 {lost / (QPS * D):.1%}（本次发布窗口）")
print()
print(f"参数：{INSTANCES} 实例、{QPS} QPS、摘除延迟 {D}s、P99 {P99}s")
print(f"排空在途只需要 {P99}s；真正决定丢不丢的是「摘除延迟 D」这 {D}s 里你还接不接流量。")
```

**本机实测输出**（Python 3.14.8）：

```text
立刻退出     单实例丢失请求 ≈    1333 个；按 2000 QPS 算，错误率 33.3%（本次发布窗口）
优雅停机     单实例丢失请求 ≈       0 个；按 2000 QPS 算，错误率 0.0%（本次发布窗口）

参数：3 实例、2000 QPS、摘除延迟 2.0s、P99 0.2s
排空在途只需要 0.2s；真正决定丢不丢的是「摘除延迟 D」这 2.0s 里你还接不接流量。
```

三条读法：

1. **排空在途只要 200ms，摘除延迟要 2s**——丢请求的大头在“等摘除”，不在“处理得慢”。很多人优化了 P99，却没解决 D。
2. **33% 的错误率是按“该实例承担的流量”算的**：整个发布窗口里总请求 4000 个，其中约 1/3 打到这个实例，全部失败。单看总错误率会被摊薄，看“实例视角”才看得出严重性。
3. **D 是可测的**：发布时观察单实例 QPS 归零的时间，就是真实的 D。把它填进 `preStop`，比抄别人的“sleep 5”靠谱。

## 怎么验证做对了

| 信号 | 期望 | 说明 |
|---|---|---|
| 发布期间 5xx 曲线 | 无尖峰 | 有尖峰说明 `[0,D)` 窗口没盖住 |
| 单实例 QPS | 平滑归零，而非瞬间断崖 | 断崖 = 没等摘除 |
| 在途请求计数 | 发布时短暂上升后归零 | 归零后才退出，说明排空生效 |
| 进程退出码 | 0 且耗时 < grace | 被 SIGKILL 是 137，说明宽限期不够 |
| 长连接数 | 发布时按预期断开并重连 | 断崖式全断 = 没发关闭帧 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 收到 `SIGTERM` 立刻 `os.Exit` | `[0,D)` 窗口内请求全丢，每次发布固定的错误峰值 |
| 只加 `preStop: sleep`，不做排空 | 摘除对了，但处理中的请求被掐断，出现“写一半”的脏数据 |
| 宽限期 = `D + drain`（没余量） | 边界抖动直接 SIGKILL，退出码 137 |
| 只关 listener，不管 keep-alive 连接 | 长连接继续复用，新请求照样进来 |
| 排空时先关 DB 连接池 | 在途请求拿不到连接，报错比不排空还多 |
| 长连接不发关闭帧 | 用户侧“突然断线”，重连风暴 |
| 优雅停机只在框架里做，编排层没配 | 框架在等，SIGKILL 已经来了 |
| 从不演练 | 参数是拍的，只有出事那天才知道 D 是多少 |

## 自检

**Q1** 发布时出现尖峰 5xx，但新版本代码完全没问题。最可能的原因是什么？

▸ 答案：旧实例在 `[0, D)` 窗口内已退出，而摘除还没生效——流量继续打到已关闭的实例上。这与代码质量无关，是退出时序问题。修法是“等摘除（preStop 或应用内延迟）+ 停收 + 排空”。

**Q2** `preStop: sleep 3` 和 `server.Shutdown()` 分别解决什么？只做一个行不行？

▸ 答案：前者解决“摘除延迟 D”——让应用在流量停止前继续服务；后者解决“在途请求”——让已经进来的请求跑完。只做 sleep，处理中的请求会被掐断；只做 Shutdown，`[0,D)` 里新进来的请求仍会打到正在退出的实例。

**Q3** 为什么“关了 listener”还不够？

▸ 答案：HTTP keep-alive 与 gRPC 的长连接是**已建立**的连接，新请求会复用它们，不经过 listener。只关 listener 挡不住这些复用请求，必须同时发关闭信号（`Connection: close` / `GOAWAY`）并设置连接空闲超时。

**Q4** 宽限期该设多少？

▸ 答案：`D + drain + 30% 余量`。D 是摘除延迟（实测 1–3s），drain 取 P99 或最大请求超时。设成 `D + drain` 时，任何抖动都会让进程被 SIGKILL（退出码 137），表现为“偶发发布失败”。

**Q5** 排空在途时，为什么不能先关数据库连接池？

▸ 答案：在途请求还要用连接池。先关池，正在处理的请求拿不到连接，直接报错——错误量比“不排空”还大。正确顺序是：停收 → 等在途归零 → 关池 → 退出。

**Q6** 长连接服务（WebSocket/SSE）的优雅停机和普通 HTTP 有什么不同？

▸ 答案：普通 HTTP 靠“停收 + 排空”就能结束；长连接不会自己结束，必须主动通知（关闭帧 / `GOAWAY`），让客户端重新连接，并在服务端设置最大等待时间。否则宽限期一到，连接被强杀，用户看到断线。

**Q7** 怎么测出自己集群的 D？

▸ 答案：发布一次，记录“发出删除请求”到“该实例 QPS 归零”的时间差（监控上看单实例 QPS 曲线），多次取最大。也可以直接看 kube-proxy/Ingress 的同步延迟指标。把测出来的值写进 `preStop`，别抄别人的默认值。

**Q8** 优雅停机做对了，发布就一定不丢请求吗？

▸ 答案：不一定。它只覆盖“退出”这一侧；另一侧是“进入”——新实例还没就绪就被打流量（readiness/健康检查配置不当）、或滚动更新时副本数不足导致过载。完整的不丢请求 = 优雅停机 + 就绪探针 + 容量余量三件事一起。
