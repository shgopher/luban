# 59.5 价值流分析（VSM）

## 一句话

> 价值流分析只干三件事——**把交付过程画成阶段、标出每段的增值与等待、算出流动效率**；它第一眼看的是“等待占了多少”，不是“谁干得慢”。三个要素里最容易失真、也最常被跳过的是**数据怎么采**：状态靠人手拖，算出来的前置时间可能只有几秒。

> 来源：三要素、两种开展方式、五大价值与访谈六问来自石雪峰《DevOps 实战笔记》第 5 讲（2019）；事件日志、分析脚本与实测输出为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “VSM 是制造业的东西，软件用不上” | VSM 起源于精益制造，但它分析的是「一个需求从提出到交付」的流动；软件开发同样有排队、返工、交接，而且**看不见**，所以更需要画出来 |
| “先把平台和工具建好，效率自然就上来了” | 局部优化会让你在错误的环节上加速。等待占 70%–95% 时，把编码提速一倍对总周期的影响通常不到 5% |
| “增值时间没法量化，所以先不统计” | 初期**不要求精细**：先统计等待（等排期、等评审、等环境、等窗口），增值时间用一个粗粒度估数即可；比例关系已经足够指路 |
| “画完一张图，转型就开始了” | 图只是产物之一。VSM 的另外四个价值——识别问题、促进沟通、驱动度量、价值展现——没有一个是靠那张图自动发生的 |

## 三个要素：口径先写死

| 要素 | 定义 | 怎么算 | 最常见的坑 |
|---|---|---|---|
| **前置时间 LT** | 一个需求从提出到上线交付的墙钟时长 | 上线时间 − 需求提出时间 | 起点选错（用「产品经理写 PRD」还是「业务方录入需求」）会让结果差几天；口径必须写进看板说明 |
| **增值 / 不增值**（VAT / NVAT） | 增值：真正在加工需求的时间；不增值：等待、返工、无意义会议、反复变更 | 按**状态**归类，不按人归类 | 把「就绪但没排期」算成增值，流动效率立刻虚高（见下面的实测） |
| **完成度与准确度**（%C/A） | 有多少工作因为质量不合格被下游打回 | 被打回的需求数 / 已交付需求数 | 只在流程里记“通过”，不记“打回”，这个数永远是 0 |

前置时间有两个常用口径，**不要混用**：

| 口径 | 起点 | 终点 | 回答什么 |
|---|---|---|---|
| **需求前置时间** | 业务方提出/录入需求 | 上线并验收通过 | 用户等多久；业务方最关心的那一个 |
| **开发前置时间** | 需求进入「开发中」 | 上线并验收通过 | 研发团队从动工到交付的能力 |

> ⚠️ 注意与 DORA 的「变更前置时间」区分：DORA 从**代码提交**算起（[59.1 DORA 四指标](59.1-DORA四指标.md)），开发前置时间从**需求动工**算起。三个起点不同的指标放在一张图上比趋势，结论必然错（三种周期的口径对照见 [59.2 交付周期与吞吐](59.2-交付周期与吞吐.md)）。

一个真实的翻车场景：某团队对外报“前置时间一周”，追问后才发现算的是「开发开始 → 功能测试完成」；业务方从提需求到上线实际要**两个月**。指标本身没错，错在只报了最短的那一段。

## 数据从哪来：三种采集方式的失真程度

| 采集方式 | 做法 | 数据质量 | 代价 |
|---|---|---|---|
| **手工拖状态** | 人在需求管理工具里拖卡片 | 差：习惯性批量拖拽，迁移时间与真实时间脱钩 | 0 |
| **平台自动流转** | 提测/合并/发布事件触发状态变更 | 好：时间戳来自系统事件 | 要打通需求平台与流水线 |
| **双源校验** | 需求状态 + 流水线时间戳交叉验证 | 最好：能发现“状态对了但时间是补填的” | 要写采集脚本 |

课程作者给的做法是**让流程驱动状态**：研发发起提测后，关联需求自动从「开发中」变成「待测试」；测试验收通过后自动流转到「测试完成」。通过代码把流水线和需求平台绑定，避免人为因素。

> 🔑 判断数据能不能用，只看一条：**状态迁移的时间戳，是人点出来的还是系统事件产生的**。人点出来的，前置时间就是“人什么时候想起去点”，不是“活什么时候干完”。

## 两种开展方式

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **工作坊 / 会议**（推荐） | 选一个核心业务模块，把交付全链路的角色请到一起，一轮画完 | 一次拿到全貌；跨团队当场对齐；**同理心**最强 | 关键角色凑齐难；面对面会“留面子”，真问题被藏起来 |
| **内部走访** | 转型小组逐团队访谈 | 时间灵活；一对一更容易说真话 | 对走访人要求高（懂 DevOps + 是内部老人）；拼全貌慢 |

工作坊的参会人要求：**覆盖交付的所有环节**（含工具平台提供方），且尽量是相对资深的成员——他们对上下游的理解足够深，能分辨问题背后的根因。如果凑不齐，退而求其次：挂在已有的敏捷回顾会或版本发布总结会上，只额外邀请几个平时不参会的人。

访谈只问六个问题就够了，问多了会散：

1. 你们团队在价值交付中负责什么？
2. 上游、下游分别是谁？
3. 一个需求在你们这一环，**处理方式**和**时长**是怎样的？
4. 有哪些系统支撑了这项工作？
5. 是否存在等待，或其他类型的浪费？
6. 工作流转到下游后，**被打回的比例**是多少？

第 6 问是很多人会漏的：它同时给出 %C/A 和返工成本，而返工往往是最贵、最不可见的那部分浪费。

## VSM 的五个价值

| 价值 | 具体表现 | 怎么验收 |
|---|---|---|
| **看见全貌** | 单点再强，割裂和浪费也会吃掉收益；画完才知道瓶颈在哪一段 | 图上能指出“哪一段最长且在下游造成排队” |
| **识别问题** | 前置时间、增值/等待、%C/A 都是可量化的，替代“感觉慢” | 每个问题都能挂一个数字，而不是形容词 |
| **促进沟通** | 很多团队是在画图时**第一次**知道上下游在干什么、卡在哪 | 参与者能说出“我们多做一步，就能改善下游什么” |
| **驱动度量** | 访谈里问不出交付周期，说明这一环根本没有可信度量；数据要人工数，说明平台能力不足 | 每个环节的关键指标能自动取数 |
| **价值展现** | 对高层讲价值时，用“流动效率从 15% 提到 30%，等价于总周期减半”比讲工具清单有力 | 能用一条曲线说明改前改后 |

这五条里，**促进沟通**常被当成软性收益而忽略，但它恰恰是 VSM 用工作坊而非问卷的根本原因：跨团队对同一件事形成共同事实，后面所有改进的阻力都小一半。

## 可运行：20 个需求的流动效率测算

下面这份日志模拟一个团队 8 周、20 个需求的状态流转（每次迁移一行），分析脚本按**迁入状态**归类增值与等待。

```python
#!/usr/bin/env python3
"""vsm.py —— 从状态迁移日志算价值流三要素。

口径（口径不写死，换个人就算出另一个数）：
  每个区间按「迁入状态」归类：待在 分析/开发中/评审中/测试中 = 增值；
  待在 就绪/待评审/待测试/待发布/已发布 = 等待（等排期、等评审、等环境、等窗口）。
"""
import csv
import sys

VAT_STATES = {"分析", "开发中", "评审中", "测试中"}
DONE = "已发布"


def load(path):
    ev = {}
    with open(path) as f:
        for row in csv.DictReader(f):
            ev.setdefault(int(row["id"]), []).append(
                (float(row["ts"]), row["from"], row["to"]))
    for e in ev.values():
        e.sort()
    return ev


def pct(xs, p):
    xs = sorted(xs)
    k = (len(xs) - 1) * p
    lo = int(k); hi = min(lo + 1, len(xs) - 1)
    return xs[lo] + (xs[hi] - xs[lo]) * (k - lo)


def main(path):
    ev = load(path)
    rows, tv, tl, rework = [], 0.0, 0.0, 0
    for rid, es in ev.items():
        start, end = es[0][0], next(t for t, _, to in es if to == DONE)
        vat = wait = 0.0
        for (t0, _, to), (t1, _, _) in zip(es, es[1:]):
            dt = t1 - t0
            if to in VAT_STATES:
                vat += dt
            else:
                wait += dt
        rows.append((rid, (end - start) / 86400, vat / 3600, wait / 3600))
        tv += vat; tl += end - start
        rework += any(f == "测试中" and to == "开发中" for _, f, to in es)

    lts = [r[1] for r in rows]
    print(f"需求 {len(rows)} 个；前置时间（天）：P50 {pct(lts,.5):.1f}  "
          f"P85 {pct(lts,.85):.1f}  均值 {sum(lts)/len(lts):.1f}  最长 {max(lts):.1f}")
    fe = tv / tl
    print(f"汇总：增值 {tv/3600:.0f}h，等待 {(tl-tv)/3600:.0f}h，合计 {tl/3600:.0f}h"
          f"（{tl/86400:.1f} 天）")
    print(f"流动效率 = 增值 / 总时长 = {fe:.1%}；等待占 {1-fe:.1%}")
    print(f"%C/A（被打回比例）= {rework}/{len(rows)} = {rework/len(rows):.0%}")


main(sys.argv[1])
```

**本机实测输出**（Python 3.14.8，样例日志 194 条迁移）：

```text
需求 20 个；前置时间（天）：P50 9.7  P85 10.3  均值 9.6  最长 11.3
汇总：增值 943h，等待 3651h，合计 4594h（191.4 天）
流动效率 = 增值 / 总时长 = 20.5%；等待占 79.5%
%C/A（被打回比例）= 7/20 = 35%
```

三条读法：

1. **等待占 79.5%，增值只占 20.5%**。此时“开发再快一点”的上限是把 20.5% 压到更小——即使开发时间归零，总周期也只从 9.7 天降到 7.7 天。改等待才是杠杆。
2. **%C/A = 35%**：超过三分之一的需求被打回过一次，这部分返工时间是纯浪费，而且它同时拉长了增值段与等待段（重做要重新排队）。
3. **P50 9.7 天、P85 10.3 天**：分布不算长尾——说明这不是“个别需求卡住”，而是**每一票都稳定地等 8 天**，这种形态的根因几乎一定是流程里的固定等待（等排期、等窗口），不是个体效率。

### 对照组：同一批需求，换成“批量拖拽”记录

把同一份数据改成上线后一次性把卡片从「提出」拖到「已发布」（真实过程没变，只改记录方式）：

```text
需求 20 个；前置时间（天）：P50 0.0  P85 0.0  均值 0.0  最长 0.0
汇总：增值 2h，等待 0h，合计 2h（0.1 天）
流动效率 = 增值 / 总时长 = 100.0%；等待占 0.0%
%C/A（被打回比例）= 0/20 = 0%
```

**流动效率 100%、前置时间 0 天、返工 0**——这三个结论都荒谬，但只要状态靠人手拖，它们就会出现在真实的度量平台上，而且没人会怀疑：数字这么漂亮，为什么要改？

> ⚠️ 这一对对照组是本节最重要的内容。VSM 的第一步不是画图，是**让状态迁移由系统事件驱动**；否则你画的是一张“人的操作习惯图”，不是价值流。

## 从 VSM 到改进

VSM 只负责“看清”，不负责“改对”。画完之后按 [59.4 效能改进方法](59.4-效能改进方法.md) 走：用约束理论（TOC）挑一个约束、一次只改一个、用同口径数据验证、把有效动作标准化。流动效率的计算公式与等待清单也在那一节。

一个提醒：**第一次画不要贪全**。范围先定在 `commit → deploy` 或者“某个核心业务模块的需求交付”，一周内能画完的才做；一上来画全公司，会陷进“需求该谁负责”的争论里出不来。

## 边界：什么时候别做 VSM

| 场景 | 为什么不划算 | 替代做法 |
|---|---|---|
| 团队 < 10 人、链路短 | 画图与访谈成本高于收益 | 每周看板对话 + 直接改 |
| 0 → 1 阶段，系统还没跑通 | 流程本身在剧烈变化，画出来下周就失效 | 先保证能交付，再谈流动效率 |
| 约束在组织外部（合规、供应商、商店审核） | 团队改不动，画出来只会挫败 | 做“隔离 + 并行”，别把外部约束算进团队指标 |
| 准备裁员或重组 | 任何度量都会被解读为裁员依据，数据必然失真 | 只做对话，不做度量 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 状态靠人手拖、批量改 | 前置时间变成“人什么时候想起来点”，流动效率可以算出 100% |
| 只统计已完成的需求 | 卡住不动的那批被排除，周期看起来很好，实际长尾全被藏起来 |
| 增值时间统计到分钟级 | 投入巨大、精度虚假；初期估到小时级就够 |
| 用「就绪」状态当增值 | 等排期被算成干活，流动效率虚高（本节样例就踩过这个口径） |
| 工作坊只请本团队 | 上下游缺席，画出来的是局部流程，瓶颈永远在“别人的环节” |
| 访谈只问时长、不问打回 | %C/A 永远是 0，返工这块最贵的浪费完全不可见 |
| 画完直接上平台/上工具 | 局部优化，等待一点没动，J 型曲线的坑见 [78.5 DevOps 转型](../../组织/78-技术文化与知识管理/78.5-DevOps转型.md) |
| 每次改进都换一次口径 | 趋势线失去意义，无法证明改进有效（[59.3 度量的陷阱](59.3-度量的陷阱.md)） |

## 自检

**Q1** 团队算出的流动效率是 100%，应该先怀疑什么？

▸ 答案：先怀疑口径与数据，而不是先庆祝。两种最常见的原因：①把「就绪」「待评审」这类等待状态算成了增值；②状态靠人手拖，迁移时间戳与真实时间脱钩（对照组的 P50 = 0 天就是极端情况）。真正的流动效率在多数组织里是 10%–30% 区间。

**Q2** 需求前置时间 60 天，开发前置时间 8 天。改进该投在哪一段？

▸ 答案：投在 60 天里那 52 天的等待。即使把开发段从 8 天压到 4 天，总周期也只从 60 降到 56（−7%）；而把等排期压掉一半，总周期立刻降 20% 以上。判断依据是哪一段的**等待**最长，不是哪一段最容易改。

**Q3** 为什么 VSM 推荐用工作坊，而不是给每个团队发一张问卷？

▸ 答案：问卷只能拿到“每个环节自己说的数”，拿不到环节之间的依赖与事实冲突；而工作坊能让上下游当场对齐同一件事——很多团队是在画图时才第一次知道下游卡在哪。这个共同事实本身就是后续改进的前提，问卷给不了。

**Q4** 访谈里对方说“我们的交付周期大概两周”，怎么判断这句话能不能用？

▸ 答案：追问三件事：口径（起点终点各是什么）、数据来源（系统取数还是凭印象）、分布（P50 还是最好情况）。答不上口径、只能给模糊数字的，说明这一环没有可信度量——这本身就是 VSM 要暴露的问题之一，正好写进“驱动度量”的价值清单。

**Q5** %C/A 一直是 0，是真的没有返工，还是别的原因？

▸ 答案：多数是记录问题——流程里只记“通过”，不记“打回”，返工发生在系统之外（口头打回、私聊催改）。验证办法：看测试提测记录、看是否有一条“测试中 → 开发中”的回流迁移。没有迁移记录却有返工事实，说明流程缺一条状态，而不是质量好。

**Q6** 老板要求“一周内把全公司的价值流画出来”。按本节的纪律，应该怎么回应？

▸ 答案：先窄后全。第一次只画一条核心业务模块的需求交付（或 `commit → deploy`），一周内能完成并产出可验证的结论：等待占比、最长等待段、%C/A。全公司版本放到第二、三轮——第一轮的目的是验证“画法能产出决策”，不是产出覆盖面。

**Q7** VSM 画完，团队立刻决定把 CI 构建时间从 20 分钟压到 5 分钟。这个决定的问题在哪？

▸ 答案：CI 只在开发完成之后发生，而等待占 79.5%——省下的 15 分钟对 9.7 天的周期影响不到 0.1%，还可能是把瓶颈挪到了“等评审队列”（构建快了，待评审堆积更快）。正确顺序：先按 VSM 找到最长等待段，再决定改什么（[59.4 效能改进方法](59.4-效能改进方法.md)）。
