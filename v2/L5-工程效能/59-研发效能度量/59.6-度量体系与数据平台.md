# 59.6 度量体系与数据平台

## 一句话

> 度量体系 = **一套少而精的指标 + 每条指标细化到可复算 + 一个只做呈现的平台**。平台建得再漂亮，只要口径没共识、数据靠人补，出来的就是“另一个没人看的数字”；而同一个数字，拿去改进就是正向度量，拿去考核就变成数字游戏。

**来源**：指标特征与五原则、三组八项、平台建设三段来自石雪峰《DevOps 实战笔记》第 19、25 讲（2019）；指标定义卡与口径复算脚本为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “度量就是考核” | 一旦与个人绩效绑定，指标立刻被优化：卡片改拖法、需求拆两半、缺陷转内部单。[59.3 度量的陷阱](59.3-度量的陷阱.md) 讲的就是这条 |
| “指标越多越全面” | 宜少不宜多、宜精不宜烂。十个指标没人看，不如把一个指标的流向追到底；作者的说法是“指标贵精不贵多” |
| “先把平台建起来，指标边建边定” | 返工点在指标：平台建好、数据出来，才发现口径不对，于是重定指标 + 重算数据。**数据校准与指标对齐的时间，常常超过开发平台本身** |
| “有了 DORA 四指标就够了” | 四指标是**对外可比的标准口径**（部署频率、变更前置时间、失败率、恢复时长）；内部体系还要覆盖交付能力（吞吐、发布前置时间）与交付质量（缺陷密度、缺陷等级、修复时长） |

## 好指标的四个特征

| 特征 | 含义 | 反例 |
|---|---|---|
| **明确受众** | 定义指标时同时定义“给谁看” | 给非技术老板看单元测试覆盖率——他既不能判断也不该判断 |
| **直指问题** | 一看就知道该干什么 | 构建失败率高 → 提交质量有问题 → 加强事前验证，链路是通的 |
| **量化趋势** | 客观数据、能看出变好还是变差 | 用户满意度、手工填写的“项目达成率”，很难用数据自证 |
| **充满张力** | 向上能归并到业务结果，向下能分解到细节 | 只度量“需求交付个数”：把一个需求拆成两个，速度就“翻倍”了 |

“充满张力”最容易被误解成“多设几层指标”，其实它的判据是**同一个数字能不能上下贯通**：老板看的“交付速度”和团队看的“待评审队列长度”，要能通过 `W = L/λ`（[59.2 交付周期与吞吐](59.2-交付周期与吞吐.md)）连起来。

一个经典的反面教材是人造的百分制指标：准时提测得 100 分、延期一天 90 分、两天 70 分、五天以上 0 分。听起来客观，但延期 1 天 1 小时和延期 1 天 23 小时同分——**分数高低不反映真实情况**，只反映打分规则。

## 定义指标的五条原则

| 原则 | 理由 | 违反的后果 |
|---|---|---|
| **全局优于局部** | 局部最优可能对整体无意义 | 每个环节都“达标”，总周期没变 |
| **综合优于单一** | 单维度必然只见树木 | 用覆盖率单一指标，写出不验证断言的测试 |
| **结果优于过程** | 过程指标要能归到结果指标 | 一堆过程指标都在变好，交付速度没动 |
| **团队优于个人** | 团队共享指标形成合力 | 个人指标让协作变成零和，帮忙的人吃亏 |
| **灵活优于固化** | 指标随能力提升要调整 | 三年前的目标值今天还在用，团队要么躺平要么造假 |

> 🔑 前两条是**方向**，后三条是**防走偏**。评审一套指标体系时，逐条问“这条违反了哪一条”，比争论具体数值有效得多。

## 三组八项：一套可用的骨架

| 组 | 指标 | 定义要点 | 参考值怎么来 |
|---|---|---|---|
| **交付效率** | 需求前置时间 | 需求提出 → 上线发布（可再拆需求侧/业务侧两段） | 用自身 P85 定基线，不抄别人 |
| | 开发前置时间 | 需求进入开发 → 上线发布 | 同上 |
| | 发布频率 | 单位时间发布次数 | 与架构和团队自治能力挂钩，越高不代表越好 |
| **交付能力** | 发布前置时间 | **提交一行代码** → 上线发布 | 业界口径：一天内算不错，精英团队一小时以内 |
| | 交付吞吐量 | 单位时间交付的需求点数（需求数 × 颗粒度） | 必须先锁定颗粒度，否则不可比 |
| **交付质量** | 线上缺陷密度 | 平均每个需求产生的缺陷数 | 按业务形态定，没有通用值 |
| | 线上缺陷分布 | 致命/严重等级缺陷占比 | 越低越好，反映质量可控性 |
| | 故障修复时长 | 缺陷提出 → 修复上线 | 受发布前置时间制约 |

**与 DORA 四指标的映射**（避免两套体系打架）：

| DORA 四指标 | 本节对应项 | 差异 |
|---|---|---|
| 部署频率 | 发布频率 | 同义，DORA 强调按应用统计 |
| 变更前置时间 | 发布前置时间 | 同义，起点都是提交 |
| 变更失败率 | —（无直接对应） | 本节用“线上缺陷密度/分布”近似，但口径不同，**不要混着比** |
| 恢复时长 | 故障修复时长 | 本节算到“修复上线”，DORA 算到“恢复服务” |

> ⚠️ 参考值一定要结合业务：无人车业务和普通互联网业务的单测覆盖率参考值可以差一倍以上。参考值还要有**定期更新机制**，否则团队能力上去了，指标还在原地。

## 指标定义卡：细到“能复算”

一个完整指标除了名字，至少要写清七件事：

| 字段 | 作用 | 缺失的后果 |
|---|---|---|
| 指标名 | 唯一标识 | 同义词满天飞（“交付周期/前置时间/开发周期”） |
| 指标描述 | 一句话说清算什么 | 各人理解不同 |
| 指标级别 | 团队级 / 组织级 | 拿组织级指标考核团队 |
| 指标类型 | 效率 / 能力 / 质量 | 混在一张图里比 |
| 适用场景与目标用户 | 给谁看、解决什么决策 | 指标长了没人用 |
| 采集方式与数据源 | 从哪个系统、哪个字段、什么频率取 | 无法复算，也没法校验 |
| 参考值 | 达标线或基线 | 数据无好坏判断，看了等于没看 |

一张合格的卡长这样（以“开发交付周期”为例）：

```yaml
name: dev_lead_time
desc: 研发把任务拖到「开发中」起，到状态变为「已发布」止的墙钟时长
level: team            # team | org
type: efficiency       # efficiency | capability | quality
audience: [研发负责人, 团队自己]
scene: 判断本周交付是否比上周慢；不用于个人考核
source:
  system: 需求管理平台（任务状态迁移表）
  field: status_changed_at
  filter: 任务类型 ∈ {特性, 缺陷, 改进}，排除史诗与技术预研；仅统计已发布
  schedule: 每日 02:00 增量
caliber:
  percentile: [P50, P85]
  window: 与吞吐取同一时间窗
reference:
  p85_hours: 96        # 基线：近 8 周 P85
  review_cycle: 季度
```

字段里的 `caliber.window` 是最容易被忽略、又最要命的一条：三个量取了不同窗口，`W = L/λ` 就会“失效”，得出“降 WIP 没用”的错误结论（[59.2 交付周期与吞吐](59.2-交付周期与吞吐.md) 有实测）。

## 四步开启度量

| 步 | 动作 | 判据 |
|---|---|---|
| ① 细化指标 | 每个指标写全七要素，**细到能用人工复算** | 两个人数同一周的数据，结果一致 |
| ② 采集数据 | 多平台口径对齐 + 准确性校验 | 关键指标能自动取，不靠人数 |
| ③ 建可视化平台 | 多维度视图、对接多系统、可自助编排 | 不同角色能看到自己关心的视图 |
| ④ 识别瓶颈并改进 | 数据 → 问题 → 改进项 → 复测 | 每个指标都能追到一个已落地的改进（[59.4 效能改进方法](59.4-效能改进方法.md)） |

第 ① 步的标准值得强调：**手工能算出来，才算定义清楚**。如果只能在平台上算，那说明大家还不知道它到底怎么算。

## 数据度量平台：事前、事中、事后

### 事前：指标共识

同一个词在不同系统里有不同算法，这是平台建设期最大的坑。真实例子：

- 需求管理平台里的「测试流转周期」= 需求卡片从「待测试」到「待发布」的停留时长；
- 测试平台里的「测试流转周期」= 每个测试任务的平均执行时长。

两个都没错，但一个是**含排队的墙钟时间**，一个是**纯执行时间**。下面这段模拟用同一批事件演示差距（4 名测试、每需求 4 个任务、执行均值 1 天）：

```python
#!/usr/bin/env python3
"""caliber.py —— 同一批测试事件，两种观察粒度算出两个数。

口径 A（需求卡片）：进入「待测试」→ 离开「待发布」（含排队）
口径 B（测试任务）：单个任务「开始执行 → 结束」（不含排队）
"""
import random

random.seed(59)
TESTERS, MEAN_ARRIVE, TASKS_PER_REQ, MEAN_TASK, N_REQ = 4, 1.2, 4, 1.0, 200
free, cards, tasks = [0.0] * TESTERS, [], []
t = 0.0
for _ in range(N_REQ):
    t += random.expovariate(1 / MEAN_ARRIVE)       # 需求按泊松流到达
    enter, ends = t, []
    for _ in range(TASKS_PER_REQ):                 # 每个任务抢最早空闲的测试位
        k = min(range(TESTERS), key=lambda x: free[x])
        start = max(free[k], enter)
        dur = random.expovariate(1 / MEAN_TASK)
        free[k] = start + dur
        tasks.append(dur)
        ends.append(start + dur)
    cards.append(max(ends) - enter)

card, task = sum(cards) / len(cards), sum(tasks) / len(tasks)
print(f"口径 A（需求卡片 待测试 → 待发布）：均值 {card:.1f} 天"
      f"（P50 {sorted(cards)[len(cards)//2]:.1f}）")
print(f"口径 B（单个测试任务执行时长）    ：均值 {task:.1f} 天")
print(f"两口径差 {card - task:.1f} 天；卡片口径里 {1 - task/card:.0%} 的时间在排队，没人在测")
print("同一份数据、同一周，两个平台各报一个数 —— 谁都没说谎")
```

**本机实测输出**（Python 3.14.8）：

```text
口径 A（需求卡片 待测试 → 待发布）：均值 3.6 天（P50 3.5）
口径 B（单个测试任务执行时长）    ：均值 1.0 天
两口径差 2.6 天；卡片口径里 72% 的时间在排队，没人在测
同一份数据、同一周，两个平台各报一个数 —— 谁都没说谎
```

所以在平台开工之前，先把指标口径写到**可落地、能出数**的颗粒度，再开会确认。会上盯着指标定义看，通常看不出问题；等数据出来才发现不对，返工就是重算历史数据。

### 事中：平台建设

| 挑战 | 做法 | 说明 |
|---|---|---|
| **大量数据源接入** | **采集器插件**：每个数据源实现一个采集器，对外统一格式化上报；上面加一层 Operation 调度频率与范围 | 新平台接入只写一个采集器，架构不变；数据量大可再接 Kafka |
| **存储** | 元数据（未加工）+ 加工数据（清洗聚合后）分开存 | 元数据量大、结构不统一、访问频繁 → 非关系型（如 HBase）；加工数据供图表查询 → 关系型（如 MySQL） |
| **视图定制** | 预置 Dashboard（管理层/技术经理/个人）+ 可拖拽的自助视图 | 预置视图永远满足不了所有人；“千人千面”靠前端组件（如网格布局 + 图表库） |

采集器的接口要够窄，实现才好写：

```java
// 一个采集器只做一件事：把某个平台的数据建模后交给框架
@Override
public void collect(FeatureCollector collector) {
    try {
        projectData.updateProjectInformation();     // 拉取并入库
    } catch (Exception e) {
        LOGGER.error("Failed to collect jira information", e);  // 单源失败不拖垮整轮采集
    }
}
```

> 🔑 采集器的价值不在“能取数”，在**隔离**：某个平台挂了、接口变了，只影响它那一个采集器，其他数据照常产出。

### 事后：规则落地

平台建成只是第 1 步，“剩下的 99 步”在运营：

1. **数据准确性是第一挑战**。最常见的偏差来源不是算法，是**研发操作不规范**：上线后一次性把卡片拖到“已发布”，算出来的交付周期可能只有几秒钟；提交代码不关联需求，行数统计全失真。这些脏数据**会一直留在数据池里，事后很难修复**。
2. **用平台能力减少人工操作**：提测关联需求 → 卡片自动流转；发布流水线触发 → 状态自动变更。不靠自觉，靠机制。
3. **让数据能判断好坏**：给每个指标设参考值（如单测覆盖率 ≥ 50%），或在同类团队中标注分位（前 10% / 后 10%）。只给绝对值的看板，看完不知道该干什么。
4. **建立审计与规则**：对不规范操作定规则、对恶意操作留审计；度量发现的问题要进改进清单，不能只停留在图表上。

## 正向度量：同一个数字的两种用法

石雪峰《DevOps 实战笔记》里反复强调的一句话：**度量是手段，不是目的**；所谓“正向度量”，是通过度量**激起团队自发的改进意愿**。

| 用法 | 团队行为 | 结果 |
|---|---|---|
| 用来改进 | 主动暴露问题，一起找瓶颈 | 数据越用越准，改进越来越快 |
| 用来考核 | 藏问题、改口径、挑容易的活 | 数据先变漂亮，然后失效，最后整套体系推倒重来 |

“推倒重来”不是夸张：很多大公司反反复复建度量体系，就是因为上一套被人摸透、变成数字游戏。判断自己处在哪一边，只看一个问题：**指标变差时，团队第一反应是解释原因，还是解释口径？**

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：

| 需求 | 产品 | 备注 |
|---|---|---|
| 想要开箱 DORA 看板 | **Apache DevLake**（开源，自托管） | 内置 DORA 指标与多源采集器 |
| 只需要基线自评 | **DORA Quick Check**（免费问卷） | 不采集数据，适合转型前摸底 |
| 已有数据，只想做图 | **Grafana** / **Superset** / **Metabase** | 直接连库或 API，视图自由 |
| 商业方案 | LinearB、Sleuth | 按应用接入，成本随规模上升 |

两个平台都已在 1 vCPU / 1.9 GB 的 Ubuntu 24.04 上真实部署过：

- **DevLake**（见 [59.4](59.4-效能改进方法.md)）：`v1.0.3-beta19`，4 容器，`compose up` 5 秒拉起、**API 199 秒就绪**，Config UI **4000**、Grafana **3002**，11 个 DORA 看板，内存峰值 914 MiB。**注意版本差异**：这一版 REST 在根路径（`GET /blueprints`，不是 `/api/blueprints`）。
- **Superset 6.1.0**（`apache/superset@sha256:16b50bbe…`，`--memory 700m` + `postgres:16-alpine` 元数据库 300m）：`db upgrade` **17 s**、建管理员 **11 s**、`init` **19 s**、`run` 后 **5 s** 出 `/health` 200；`/login/` 200；API 依次建 database→dataset→chart 均 **201**，`POST /api/v1/chart/data` 真实取数 **7 行**（7 天共 26 次部署、平均交付周期 21.17 h）；内存峰值 **436 MiB + 258 MiB**。三个版本坑：① `latest` 是 **6.1.0 不是 4.x**；② 镜像**不含 Postgres 驱动**（不装 `psycopg2-binary` 直接 `ModuleNotFoundError`）；③ 写 API 必须带 CSRF（`GET /api/v1/security/csrf_token/` + `X-CSRFToken`），只带 Bearer 会 400。

本节验证的是口径算法本身（见上）；平台只负责呈现。

**可抄**：无论用哪个平台，先落一张指标定义卡（上面的 YAML），再让采集脚本只输出卡片里声明的字段。字段多一个都不加——**平台只呈现，不发明指标**。

**可验**：`caliber.py` 的输出就是验证基准。接入平台后，用同一周数据手工复算一次「测试周期」，若平台报 1.0 天而手工卡片口径是 3.6 天，说明平台用的是任务口径，要么改口径、要么改名，不能两个都叫“测试周期”。

**可退**：度量平台天然可退——只读数据源，不改业务系统；回退 = 停容器 + 撤看板，业务零影响。**不可退的是考核绑定**：一旦指标进了绩效，撤回会引发信任问题，所以绑定前要当成不可逆决策来评估。

## 边界：什么时候别急着建平台

> 💡 本节讲的是**研发效能**指标（交付周期、吞吐、质量）。业务经营指标（GMV/DAU/留存/转化）的指标字典、口径治理与血缘，主场在 [60.4 元数据管理与数据目录](../../L4-组件与技术/60-数据平台与数仓/60.4-元数据管理与数据目录.md) 的「指标字典」与 [46.5 数据治理与血缘](../../L4-组件与技术/46-数据架构/46.5-数据治理与血缘.md)，不在这里重复。

| 场景 | 原因 | 替代 |
|---|---|---|
| 应用 < 5 个、部署系统统一 | 手工采集成本低于平台建设 | 脚本 + 表格跑 4–8 周，先验证“数据会被用来做决策” |
| 还没有改进议程 | 不知道拿数据做什么，平台必然闲置 | 先用 [59.5 价值流分析](59.5-价值流分析.md) 找出一个约束 |
| 团队 < 10 人 | 度量成本高于收益，且容易变成互相盯 | 每周看板对话 |
| 组织正在裁员/重组 | 任何度量都被解读为裁员依据，数据必然失真 | 只做对话，不做度量 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 先买/先建平台，再想指标 | 平台建成没人看；返工点全在指标 |
| 同一指标在两个平台各有一套算法 | 开会先吵“谁的数据对”，改进无从谈起 |
| 指标与个人绩效绑定 | 数据被优化，一两年后整套体系作废 |
| 预置 Dashboard 当终态 | 每个人的关注点不同，最后都回去手工拉数做 PPT |
| 只给绝对值、不给参考值或分位 | 看完不知道好坏，数据不驱动任何动作 |
| 采集器与业务系统强耦合 | 一个平台改接口，整条数据链断掉 |
| 脏数据先入库、以后再清洗 | 不规范操作产生的偏差**不可修复**，会永久污染数据池 |
| 拿任务口径的“1 天”去汇报需求交付周期 | 汇报漂亮、体验糟糕，业务方信任一次性耗尽 |

## 自检

**Q1** 老板问“我们的测试周期是多久”，两个平台给出 1 天和 3.6 天。该回答哪个？

▸ 答案：先问“你要用它做什么决策”。管排期与交付承诺，用卡片口径（3.6 天，含排队）；管测试团队产能与自动化收益，用任务口径（1 天，纯执行）。但**两个指标不能同名**，必须分别命名为“需求测试流转周期”和“测试任务执行时长”，否则每次开会都会重吵一遍。

**Q2** 为什么“指标定义要细到能用人工复算”？这看起来是低效的要求。

▸ 答案：因为它是唯一能验证“大家理解一致”的办法。只能由平台算出来的指标，意味着没人能独立验证，口径漂移无法发现；而两个人数同一周数据能得到同一个结果，说明定义、数据源、过滤条件都对齐了。人工复算是**校验手段**，不是长期运行方式。

**Q3** 团队把“线上缺陷密度”纳入个人绩效后，三个月内缺陷密度下降 60%。该怎么解读？

▸ 答案：先怀疑数据，再庆祝。下降可能来自：缺陷被改成“内部优化单”、严重等级被下调、跨团队缺陷不再登记。验证办法是看**外部信号**——客户投诉量、故障数、恢复时长是否同向变化。指标与绩效绑定后，单看指标本身已经没有信息量（[59.3 度量的陷阱](59.3-度量的陷阱.md)）。

**Q4** 平台的预置 Dashboard 已经覆盖管理层、技术经理、个人三种视图，为什么还要做自助视图？

▸ 答案：预置视图解决“看得见”，自助视图解决“看得对”。不同角色关注的切片不同（某团队 vs 某应用 vs 某需求类型），预置视图的组合永远不够；结果是大家把数据导出去做 PPT，平台反而成为数据的“中转站”而不是“决策入口”。

**Q5** 采集器为什么要做成插件，而不是写一个统一的大脚本，按平台类型分支？

▸ 答案：隔离与扩展成本。插件化后，新增平台只写一个采集器，不动主流程；某个平台接口变更或挂掉，只影响它自己那一路数据。大脚本方案下，任何一次变更都要回归全部数据源，采集链最容易在这里断掉。

**Q6** 指标卡里为什么必须有“受众”和“不用于什么”？

▸ 答案：受众决定指标的粒度与呈现方式（给老板看趋势，给团队看队列）；“不用于什么”防止误用——同一张卡可以写“用于判断本周是否变慢，不用于个人考核”。这句话在争议发生时是最有力的依据，因为它是**在指标被使用时就已经约定好的**，不是事后解释。

**Q7** 团队说“我们的数据都在平台上了，为什么还要指标定义卡？”两者不是重复吗？

▸ 答案：平台上的字段是“实现”，指标卡是“契约”。实现会变（加字段、换系统、改过滤），契约不变；没有契约，平台改一次代码，历史趋势就断一次。契约也是交接材料：新人看卡就知道这个数字怎么来的，不用读代码。

**Q8** 一个 8 人团队想上 DORA 平台，你建议怎么做？

▸ 答案：先别上平台。用脚本从 git 与发布记录算四周（[59.1 DORA 四指标](59.1-DORA四指标.md) 给了采集脚本），验证两件事：数据算得出来、算出来有人用来改。两条都成立再考虑 DevLake 之类的平台；否则平台会变成本节第一条反模式（先建平台，再想指标）。
