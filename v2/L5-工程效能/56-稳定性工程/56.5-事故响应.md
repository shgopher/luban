# 56.5 事故响应

## 一句话

> 事故响应是一套**在信息不全时仍能推进的流程**：先分级、再定角色、按节奏通报、以止血为第一目标；恢复之后再谈根因。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “事故 = 故障” | 故障是技术事实，事故是**需要协调与通报的事件**。一个自动恢复的故障可以不是事故；一个没影响用户但引发信任危机的事件可能是 S1 |
| “先查根因，再处理” | 根因可能要几小时；用户每分钟都在受损。响应阶段的第一目标是**止血**，根因放到恢复之后 |
| “响应靠自觉” | 没有角色、没有时间盒、没有通报节奏，响应会退化成“几个人在群里各查各的” |
| “通报 = 甩锅” | 通报是让干系人知道“影响、动作、下次更新时间”，避免重复询问与谣言；写事实，不写猜测 |

## 分级：先定“多大”，再定“怎么办”

| 级别 | 触发条件（满足任一） | 响应 | 通报间隔 | 状态页 | 复盘 |
|---|---|---|---|---|---|
| **S1** | 核心功能不可用；资损；数据丢失/错乱；安全事件；≥30% 用户受影响；燃烧率 ≥ 14.4 | 立即，全员 | 15 分钟 | 是 | 必须 |
| **S2** | 部分用户受影响（≥5%）；资损 ≥ 20 万/小时；燃烧率 ≥ 6 | 15 分钟 | 30 分钟 | 是 | 必须 |
| **S3** | 可感知但可降级；≥1% 用户受影响；燃烧率 ≥ 1 | 工作时间/30 分钟 | 60 分钟 | 否 | 轻量 |
| **S4** | 无用户感知；内部指标异常 | 下一工作日 | 按需 | 否 | 否 |

> ⚠️ 表里的数字（30%/5%/1%、100 万/20 万、燃烧率 14.4/6）是**示例阈值**，必须按业务规模、资损承受力与 SLO 改写；照抄别人的阈值，等于用别人的风险偏好做自己的决策。

分级要**就高不就低**：拿不准时先按高一级响应，10 分钟后可以降级；反过来（先低后高）会浪费最宝贵的止损窗口。

## 角色：谁负责什么

| 角色 | 职责 | 不该做什么 |
|---|---|---|
| **IC（事故指挥）** | 定级、定节奏、拍板止血方案、对外代表事故 | 亲自排查（会失去全局视角） |
| **OL（运维/技术 lead）** | 组织排查与执行止血 | 绕过 IC 直接对外承诺 |
| **CL（沟通 lead）** | 写通报、维护状态页、对接业务/客服/高管 | 猜测原因、承诺未确认的恢复时间 |
| **Scribe（记录）** | 记时间线、决策、动作、指标 | 参与排查（会漏记） |
| **SME（领域专家）** | 提供根因线索与修复方案 | 各自为战、不汇报进展 |

小团队可以一人多角，但**IC 与 OL 不能是同一个人**：一个负责“决定做什么”，一个负责“怎么做”。

## 时间线：每个阶段都有目标

| 阶段 | 目标 | 关键动作 |
|---|---|---|
| 发现 → 认领 | ≤ 5 分钟 | 告警路由、ack（见 [56.3 on-call (值班 / 升级路径 / runbook)](56.3-on-call.md)）；告警质量决定发现速度（见 [56.4 告警治理](56.4-告警治理.md)） |
| 认领 → 宣布事故 | ≤ 5 分钟 | 定级、拉群、指定 IC/CL/Scribe |
| 宣布 → 止血 | ≤ 30 分钟（S1） | 回滚/降级/限流/切流（见 [55.3 回滚设计](../55-发布与回滚/55.3-回滚设计.md)） |
| 止血 → 确认恢复 | ≤ 30 分钟 | 验证核心链路、清脏数据、确认无二次故障 |
| 恢复 → 复盘 | ≤ 5 个工作日 | 见 [56.6 无指责复盘](56.6-无指责复盘.md) |

下面的程序把“分级”和“S1 时间线”跑出来：

```go
package main

import "fmt"

type impact struct {
	usersPct float64 // 受影响用户比例
	revenue  float64 // 预计资损（万元/小时）
	burn     float64 // 错误预算燃烧倍率
	dataLoss bool
	security bool
}

type plan struct {
	sev        string
	ic         string
	commsMin   int
	statusPage bool
	execNotify bool
	postmortem bool
}

func classify(i impact) (plan, string) {
	switch {
	case i.security:
		return plan{"S1", "必须", 15, true, true, true}, "安全事件"
	case i.dataLoss:
		return plan{"S1", "必须", 15, true, true, true}, "数据丢失/错乱"
	case i.usersPct >= 30 || i.revenue >= 100 || i.burn >= 14.4:
		return plan{"S1", "必须", 15, true, true, true}, "影响面/资损/燃烧率触顶"
	case i.usersPct >= 5 || i.revenue >= 20 || i.burn >= 6:
		return plan{"S2", "必须", 30, true, true, true}, "部分用户受影响或快速燃烧"
	case i.usersPct >= 1 || i.revenue > 0 || i.burn >= 1:
		return plan{"S3", "建议", 60, false, false, true}, "可感知但可降级/慢烧"
	default:
		return plan{"S4", "不需要", 120, false, false, false}, "无用户感知"
	}
}

func main() {
	cases := []struct {
		name string
		i    impact
	}{
		{"支付成功率 99.9% → 90%", impact{usersPct: 40, revenue: 200, burn: 20}},
		{"某地域错误率 5%", impact{usersPct: 8, revenue: 30, burn: 7}},
		{"消息积压，用户无感", impact{usersPct: 0.5, revenue: 0, burn: 1.2}},
		{"订单表被误删", impact{usersPct: 2, revenue: 5, burn: 3, dataLoss: true}},
	}

	fmt.Println("== 事故分级 ==")
	fmt.Printf("%-26s %-4s %-6s %-9s %-8s %-8s %-6s %s\n", "场景", "级别", "IC", "通报间隔", "状态页", "通知高管", "复盘", "依据")
	for _, c := range cases {
		p, why := classify(c.i)
		fmt.Printf("%-26s %-4s %-6s %-9s %-8v %-8v %-6v %s\n",
			c.name, p.sev, p.ic, fmt.Sprintf("%d 分钟", p.commsMin), p.statusPage, p.execNotify, p.postmortem, why)
	}

	// S1 的时间线：每一步都有目标，超出就是流程问题
	type phase struct {
		name       string
		target, at int
	}
	phases := []phase{
		{"发现→认领", 5, 6},
		{"认领→宣布事故", 5, 9},
		{"宣布→止血", 30, 38},
		{"止血→确认恢复", 30, 95},
	}
	fmt.Println("\n== S1 时间线（支付故障）==")
	total := 0
	breach := 0
	for _, ph := range phases {
		status := "ok"
		if ph.at > ph.target {
			status = fmt.Sprintf("超 %d 分钟", ph.at-ph.target)
			breach++
		}
		fmt.Printf("  %-16s 目标 %3d 分钟  实际 %3d 分钟  %s\n", ph.name, ph.target, ph.at, status)
		total += ph.at
	}
	fmt.Printf("  从发现到确认恢复：%d 分钟（%d 个阶段超时）\n", total, breach)
	fmt.Println("  注意：'止血' 与 '恢复' 是两个里程碑；对用户报 '已恢复' 之前，必须先验证核心链路")
}
```

最刺眼的是“止血→确认恢复 95 分钟”：止血只用了 38 分钟，但确认恢复多花了 95 分钟。常见原因是：**核心链路验证脚本缺失、数据校验没有基线、或者不敢对外说恢复**。这一段往往不被当成“响应时间”，但它决定用户真正受苦多久。

## 通报模板：三段，别写小说

```
【S1 支付故障】影响：约 40% 用户支付失败（10:02 起）
当前动作：已回滚 10:00 的发布，错误率从 30% 降到 2%，正在验证核心链路
下次更新：10:45（每 15 分钟更新；无进展也更新）
```

三条纪律：

1. **只写事实**：已确认的影响、已执行的动作、下一次更新时间；不写“可能”“大概”“正在排查”。
2. **按节奏更新**：即使没有进展，也要在承诺时间点发一条“仍在处理，下次 X 点更新”——沉默会引发更多询问。
3. **恢复要验证**：对用户说“已恢复”之前，先跑核心链路冒烟 + 数据校验；错误地宣布恢复比晚宣布更伤信任。

## 止血优先：先选手段，再谈根因

| 手段 | 适用 | 代价 | 何时用 |
|---|---|---|---|
| 回滚 | 最近有发布/配置变更 | 可能丢新功能 | 第一优先（见 [55.3 回滚设计](../55-发布与回滚/55.3-回滚设计.md)） |
| 降级 | 非核心功能拖垮核心 | 功能缺失 | 回滚不确定时 |
| 限流 | 流量超过容量 | 部分用户被拒 | 容量问题、攻击 |
| 切流 | 单地域/单机房故障 | 切换风险 | 故障域隔离（见 [36.4 两地三中心与多活](../../L3-质量属性/36-灾备/36.4-两地三中心与多活.md)） |
| 修数据 | 脏数据已产生 | 二次错误风险 | 先停写，再补偿 |
| 改代码 | 明确的小 bug | 发布风险 | 以上都不可行时 |

顺序原则：**能回滚先回滚，能降级先降级，能限流先限流；改代码是最后手段**，因为它引入新的不确定性。

## 亚马逊式：故障源团队与影响范围控制

原文对亚马逊的评价是：“在故障发生时……尤其是能够快速定位故障源。”它的做法不是更聪明的排查，而是**把组织与流程设计成能快速收敛**：

| 机制 | 做法 | 解决什么问题 |
|---|---|---|
| **值班轮换** | 每个团队至少 1 名 on-call，**每人轮一周**，专心处理故障 | 避免“谁都管、谁都不专” |
| **群签到** | 故障发生后所有相关团队上线签到，**自查自己的服务**，没事也在线 standby | 分布式系统会连锁报警，先排除自己 |
| **提工单升级** | S1/S2 且**没有替代方案**时提工单，相关团队 on-call 全部上线；未解决**自动升级至 SVP** | 防止“卡在某个团队手里” |
| **受影响方自保** | 被影响的团队先做**降级**，控制故障范围不扩散 | 止血优先于定位 |
| **恢复手段三件套** | 重启、限流（需要流控中间件）、回滚（针对新代码 bug） | 大多数故障用这三招就能恢复 |

> 🔑 一句话原则：**出现故障时，最重要的不是 debug，而是尽可能减少影响范围，并尽快修复。**

还有一条容易被忽略的组织前提：**按 Service 分工，而不是按“前端/后端/运维”分工**，开发把所有事干完。服务一多，工单在团队之间转来转去，比技术问题更致命。

### 故障前的准备清单

| 准备项 | 具体做法 |
|---|---|
| 降级预案 | 不能回滚就降级，并挂出“停止服务”公告 |
| 紧急更新能力 | 靠自动化测试与自动化发布；**上千台服务器**时没有它根本发不出去 |
| 全视图 | 用户功能 → 服务 → 资源的全链路视图（比 CMDB 更细），最好由监控自动生成——“没有地图，只能像无头苍蝇一样乱试” |
| 每个服务的应急包 | 关键指标、处理流程、应急预案；中间件（Redis 等）要有最佳实践 |
| 分级 | 亚马逊分 **4 级**（1 全站不可用、2 无替代方案、3 有替代、4 非功能问题）；分级越高牵扯越广 |
| 演练 | Chaos Monkey 随机搞破坏；Facebook 随机关服务器 |
| 灰度 | 测试环境很难模拟线上；亚马逊用 Weblab，没有多站点就用流量分配 |

## 止血之后：根因分析的五个动作

止血（把用户影响消掉）和定位（搞清楚为什么）是两件事，但只有定位做对了，[56.6 无指责复盘](56.6-无指责复盘.md) 才有东西可复盘。许式伟把根因分析定义成一个循环：

> 针对系统的观察结果 + 对运行机制的理论认知 → 提出一个失败假设 → 测试并排除 → 再假设……

它不是灵光一现，而是**可教、可练的流程**。落地成五个动作：

| # | 动作 | 具体做法 | 常见错误 |
|---|---|---|---|
| 1 | **先固化现场** | 恢复动作会破坏现场：先把相关指标时间段、日志、慢查询、堆栈、变更记录各存一份 | 一边止血一边把日志滚动覆盖掉，事后只能靠回忆 |
| 2 | **从指标找怀疑对象** | 看基于时间序列的报表，用几个指标的相关性缩小范围 | 把**相关当因果**：网络丢包和硬盘不可访问可能同由一次断电引起，两者不是彼此的原因 |
| 3 | **问题分解** | 多层系统从一端开始，逐个组件查到底（入口 → 网关 → 服务 → 依赖 → 内核/网络） | 跳着查，哪层看着可疑查哪层，最后每层都"看着正常" |
| 4 | **用日志与链路收敛** | 日志是广义的：指标时序 + 程序日志 + 链路。用 Request ID 把一次请求的所有日志串起来 | 日志里没有 Request ID，跨服务只能靠时间戳猜 |
| 5 | **验证假设** | 两条路：① 拿观察到的证据与假设对比；② 做一次**可控的**"治疗"再观察。第二条要谨慎，别把小故障治成大故障 | 验证时顺手改了配置/环境，验证逻辑本身被破坏 |

日志这一层怎么做才有用（细节见 [50.2 日志](../../L4-组件与技术/50-可观测性/50.2-日志.md) 与 [50.3 链路](../../L4-组件与技术/50-可观测性/50.3-链路.md)）：

| 能力 | 为什么是排查的前提 |
|---|---|
| **结构化日志** + 时序存储 | 能按字段过滤、按时间对齐；文本日志只适合实时调试 |
| **Request ID 贯穿全链路** | 跨组件检索同一个请求的全部日志，不用人工对齐上游与下游 |
| **可在线调整日志级别** | 需要时临时开 debug，不用重新发版；平时保持低级别控成本 |
| **采样**（如每 1000 次记 1 次） | 高流量下把日志成本压到可承受，同时保留统计意义 |
| **轻量追踪头**（如 `X-RequestTrace`） | 现场还在时最快的概览；缺点是只能在线看，不留历史 |

还有第三种手段常被忽略：**状态查询 API / 监控页面**。它能直接显示"这个实例正在和谁通信、各类 RPC 的错误率与延迟直方图"，不用翻架构文档——前提是现场还在。

### 排查为什么总是低效

| 低效原因 | 表现 |
|---|---|
| 在错误的方向上浪费时间 | 盯着一个不相关的指标查了半天 |
| 把巧合当原因 | 数据库压力大导致机房局部温度上升，于是去修空调 |
| 过早归因 | "肯定是上次那个老问题"，或者把原因归到极不可能的因素上 |
| 验证时动了环境 | 改配置、改输入，导致假设无法被安全验证 |
| 对系统不够了解 | 只知道通用流程，不知道这个系统怎么构建、怎么失败 |

最后一条是根因：故障排查**同时需要**"通用流程"和"对这个系统机制的理解"。前者可以学，后者只能靠平时积累——所以许式伟说，不碰线上环境的人成不了最理解系统的专家。

> 🔑 事前准备比事后排查便宜得多：**每个组件在上线时就配白盒指标 + 结构化日志 + 贯穿全链路的 Request ID**，比故障时临时加日志快一个数量级。

## 长事故：交接与轮换

超过 2 小时的事故，IC 和主要排查人必须轮换：

| 项 | 要求 |
|---|---|
| 交接内容 | 当前影响、已排除的假设、当前动作、下一步、未处理的风险 |
| 交接方式 | 书面（事故群置顶/文档），不只口头 |
| 节奏 | 每 2 小时或按值班班次轮换 |
| 记录 | 交接时间与接手人写进时间线 |

不轮换的后果是判断力下降：凌晨 4 点的 IC 做的决定，往往不如 8 点接班的 IC。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：事故编排用 **PagerDuty**（事件时间线、升级、状态页）或 **incident.io**（Slack 原生、角色分配）；小团队用“事故群 + 置顶模板 + 计时器”也能跑。关键不是工具，是**角色与节奏写死**。

**可抄**（本机无账号，以下命令**未验证**）：

```bash
# PagerDuty：手动创建事件（S1）
curl -s -X POST https://events.pagerduty.com/v2/enqueue \
  -H 'Content-Type: application/json' \
  -d '{"routing_key":"'"$PD_KEY"'","event_action":"trigger",
       "payload":{"summary":"S1 支付成功率下降","source":"manual","severity":"critical",
                  "custom_details":{"impact":"40% 用户支付失败","commander":"oncall-lead"}}}'

# 事故群置顶模板（三段）
# 影响：…  当前动作：…  下次更新：…
```

**可验**：本节分级器**真跑过**，输出如上；它验证的是“分级规则与时间线判定”，不依赖工具。线上至少验证：一次演练中能否在 5 分钟内定级并指定 IC、15 分钟内发出第一条对外通报、恢复前跑完核心链路冒烟。

**可退**：

- 定级过高：10 分钟内可降级，并在群里说明“降级原因”，避免团队长期紧绷。
- 止血失败：按 [55.3 回滚设计](../55-发布与回滚/55.3-回滚设计.md) 的“回滚失败预案”走，不要连续试错。
- 通报出错：立即更正并说明“哪条信息错了、现在的正确信息是什么”；不要删消息假装没发生。

## 反模式

| 反模式 | 后果 |
|---|---|
| 没有 IC，所有人各查各的 | 决策慢、重复劳动、对外口径不一致 |
| 先查根因再止血 | 用户受损时间被拉长 |
| 通报写“正在排查” | 干系人反复询问，CL 被拖垮 |
| 承诺“很快恢复” | 未兑现会透支信任 |
| 恢复未验证就宣布 | 二次故障，用户信任受损 |
| 长事故不轮换 | 判断力下降，错误决策 |
| 把复盘开成追责会 | 信息隐藏，下次更糟（见 [56.6 无指责复盘](56.6-无指责复盘.md)） |
| 只处理不记录 | 复盘无时间线，改进无依据 |

发布类事故的分级与止损顺序，可对照 82.4 发布事故（待补）的案例复盘。

## 自检

**Q1** 为什么事故响应要先止血、后根因？

▸ 答案：用户按分钟受损，根因可能要几小时。先止血（回滚/降级/限流/切流）能把影响面与持续时间压到最小；根因分析放在恢复之后，且不影响止血决策。例外：如果止血手段本身有数据风险（如修数据），要先停写、评估后再动。

**Q2** IC 为什么不能同时做排查？

▸ 答案：IC 的职责是全局：定级、定节奏、协调资源、对外代表事故。一旦亲自排查，就会陷入细节、失去全局视角，忘记通报与升级。IC 可以懂技术，但响应期间要“动手不动手，只做决策与协调”。小团队可以让 IC 兼记录，但不能兼主要排查人。

**Q3** 为什么“已恢复”必须验证后才能宣布？

▸ 答案：“止血”只表示指标暂时回落，不代表数据正确、依赖恢复、二次故障消失。未验证就宣布，常见后果是几分钟后再次故障，用户与干系人的信任被透支。验证至少包括：核心链路冒烟、关键数据校验、错误率/P99 稳定一段时间。

**Q4** 长事故为什么要强制轮换 IC？

▸ 答案：人在长时间高压下判断力下降，容易固执于一个假设、忽略新信息。轮换让新的 IC 带着新鲜视角接手，同时通过书面交接保留上下文。轮换不是“换人背锅”，是保持决策质量的组织手段。

**Q5** 通报里为什么不能写“正在排查”？

▸ 答案：“正在排查”没有信息量，干系人无法判断影响与下一步，只会反复询问。有效通报必须包含：已确认的影响、已执行的动作、下一次更新时间。没有进展也要按节奏更新，沉默比坏消息更伤人。

**Q6** 监控显示“网络丢包”和“硬盘不可访问”同时发生。为什么不能直接把前者当成后者的原因？

▸ 答案：相关不等于因果。两者可能是同一个原因的两个结果（比如一次断电同时导致网络设备与存储掉线），也可能纯属时间上的巧合；随着部署规模变大、指标变多，巧合同步出现的概率还会上升。正确的用法是：**相关性只用来挑怀疑对象**，再用日志、分解和可控实验去验证。

**Q7** 为什么很多团队的故障排查总是慢在“假设—验证”这一步？

▸ 答案：根因有两个。① **对系统机制不够了解**——只有通用流程，没有这个系统怎么构建、怎么失败的知识，提不出可验证的假设；② **验证动作本身被污染**——排查时顺手改了配置或环境，或者一次改多个变量，导致结果无法归因。对应的解法是平时积累白盒指标与结构化日志，排查时一次只动一个变量。
