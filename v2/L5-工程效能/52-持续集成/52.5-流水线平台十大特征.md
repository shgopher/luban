# 52.5 流水线平台：现代流水线的十个特征

## 一句话

> 流水线平台只做四件事——**编排、执行、可视化、记录**，专业能力由垂直平台以「原子」接入；十个特征里前五个定义「它是什么」，后五个定义「它怎么长大」，验收判据不是自带多少功能，而是**接入一个新能力要几天、要改几处代码**。

**来源**：十个特征与两处细节（Xcode 步骤 53 个参数、5 Click 5 Minutes）来自石雪峰《DevOps 实战笔记》第 23–24 讲（2019），内建质量部分来自第 14 讲；门禁求值器与 CI 骨架为本节补充。

## 先破除五个误区

| 误区 | 现实 |
|---|---|
| “要建一条从提交到发布的大流水线” | 真正跑起来的是**多条分阶段流水线**：开发、集成、部署各一条，业务目标和触发方式都不同；一条大而全的流水线既编排不动，也没人敢改 |
| “测试、扫描、审批的能力都做进流水线最省事” | 每一个能力背后都是一支专业团队。全做进平台 = 平台臃肿 + 垂直能力做不深 + 与既有平台抢地盘（零和），而大企业的既有平台是拆不掉的 |
| “参数越多越灵活” | Jenkins 原生的 Xcode 编译步骤暴露 **53 个参数**，结果仍然有人不够用、有人看不懂。满足所有场景等于一个都不满足 |
| “有 Jenkinsfile 就是流水线即代码” | 只做到第 3 个特征。缺实例快照、参数化、并发隔离中的任何一项，重跑一次历史构建就复现不出当时的结果 |
| “人工审批是落后的，应该全自动” | 人工确认不是流程债，是**爆炸半径开关**。微软每次生产部署都要过五环、且每环设人工确认（[84.7 万人组织的分级测试与部署环](../../附录/84-典型案例/84.7-万人组织DevOps转型.md)） |

## 十个特征：一张表看完

| # | 特征 | 它解决什么 | 判据（可检查） |
|---|---|---|---|
| 1 | 平台而非能力中心 | 能力从哪来、边界在哪 | 接入新能力是否**不改平台代码** |
| 2 | 可编排与可视化 | 不同技术栈走不同流程 | 用户能否自己增删步骤，且看板显示的就是真实执行 |
| 3 | 流水线即代码 | 变更可追溯、可评审 | 流水线配置是否在版本库里、能否被 PR 评审 |
| 4 | 流水线实例化 | 重跑、并发、历史回溯 | 是否有参数、快照、独立工作区 |
| 5 | 有限支持原则 | 复杂度失控 | 参数是否只覆盖 90% 的常见场景 |
| 6 | 流程可控 | 什么时候跑、谁放行 | 是否支持定时/手动/事件触发 + 人工审批 |
| 7 | 动静分离配置化 | 加个参数要改前端 | 新增参数是否只改配置、不改页面代码 |
| 8 | 快速接入 | 能力图谱长不快 | 接一个平台是几天还是几个月 |
| 9 | 内建质量门禁 | 质量在哪里拦 | 门禁是否离数据产生点足够近、是否有一级处置规则 |
| 10 | 数据聚合采集 | 结果散在 N 个系统 | 一次执行的结果能否在一个页面看完 |

> 🔑 前五个特征决定平台**能不能被复用**，后五个特征决定平台**能不能长大**。第 1 和第 8 是最容易被跳过、也最贵的两条：跳过了，平台会退化成一台“只有自己会改的机器”。

## 前五个：定义「它是什么」

### ① 打造平台而非能力中心

流水线是唯一贯穿端到端交付的平台，于是最常见的做法是把所有能力都做进去。这条路在企业里走不通，原因有三：专业能力靠团队长期投入，平台团队组不起来；平台会臃肿；既有平台拆不掉。

正确的切法是**把流水线平台与垂直业务平台分开，并显式定义边界**：

| 维度 | 流水线平台 | 垂直业务平台 |
|---|---|---|
| 定位 | 任务的**调度者、执行者、记录者** | 专业能力的**实现者** |
| 负责 | 流程编排、过程可视化、运行资源池、权限、调度 | 测试执行、代码质量、发布、数据库变更… |
| 不负责 | 不侵入垂直平台内部逻辑 | 不负责跨平台编排 |
| 接入方式 | 提供原子与接口规范 | 以插件或接口形式暴露能力 |

三个来源都指向同一句话：**平台只编排，不替代**。Jenkins 插件中心、GitHub Marketplace 都是这个结构。反过来，只要平台开始实现某个垂直能力，接入生态就开始萎缩——因为提供该能力的团队失去了“被接入”的动机。

### ② 可编排与可视化

多技术栈并存是常态：前后端分离后前后端流水线不同、微服务下每个模块都要能独立交付。写死「构建 → 测试 → 发布」三个阶段的平台，会逼出各种畸形用法——有团队把「生成版本标签」塞进上线检查阶段，只因为别处没地方放。**看板显示的和实际做的对不上，可视化就失效了。**

可编排的最小模型是三层：

```text
流水线（pipeline）
└── 阶段（stage）：按顺序执行
    └── 步骤（step）：可串行、可并行，由一个「原子」实现
```

编排结果一般是 JSON，前端存、后端流程引擎翻译成执行计划，再交给执行器。真正的难点不在前端画图，而在**原子**：

| 原子的要求 | 判据 | 反例 |
|---|---|---|
| **只做一件独立任务** | 输入参数 → 输出结果，无隐式上下文 | “构建并部署并通知” |
| **与业务无关** | 换一个项目仍能复用 | “给购物车服务打特定 tag” |
| **参数化** | 行为差异全部由参数表达 | 不同分支各写一个原子 |
| **可观测** | 有日志、有状态、有结果数据 | 只 echo 一句 ok |

拉代码是最典型的合格原子：无论前端后端，本质都是「按地址 + 分支 + 凭据拉一份代码」。把它做成原子，全公司只维护一份。

### ③ 流水线即代码

流水线配置进版本库，和业务代码一样走评审、有提交历史。收益不止“可追溯”：

- 异常时能回答“这次构建用的到底是哪版流水线”；
- 流水线变更可以写进 Release Notes，和业务变更加在一起看；
- 配置本身能被 review，改门禁规则不再靠“谁有权限谁改”。

石雪峰《DevOps 实战笔记》给了一个替代方案：配置存数据库，每次执行记录当时的版本号。它同样能追溯，但**配置本身失去了评审入口**——一条没人 review 的规则改动，和一次没人 review 的数据库变更，风险同级。

> ⚠️ 这里最容易踩的坑：把凭据写进流水线文件。用平台凭据库或在运行时注入环境变量，别让密码进 git 历史。

### ④ 流水线实例化

流水线之于实例，等价于类之于对象：

| 能力 | 做法 | 没有会怎样 |
|---|---|---|
| **参数化** | 用统一格式声明参数（如 `#branch`），模板复用 | 每个分支复制一条流水线，改一次改十处 |
| **快照** | 每次执行固化当次的流水线配置 | 改了配置后重跑，结果对不上，无法定责 |
| **并发** | 同一模板触发多次，各自独立工作区 | 并发任务互相覆盖产物，出现“随机失败” |

并发做不了，根因通常不是调度器，而是**工作区没有隔离**：两个实例共用一份源码目录，后跑的覆盖先跑的。解法是每个实例一个独立工作区，并把静态数据（依赖缓存、构建缓存）以只读挂载的方式共享，既省时间又不互相污染。

### ⑤ 有限支持原则

目标是**满足多数常见场景的快速使用**，外加一层定制逃生舱，而不是穷举所有变量。这就是奥卡姆剃刀在平台上的版本：如无必要，勿增实体。

一个可操作的准入标准：**新增参数，先问“是不是 90% 的用户都会用到”**。不是，就放进逃生舱，而不是放进原子。

逃生舱只需要三类原子，就能覆盖绝大多数差异：

1. **执行自定义脚本**（任意 shell）
2. **调用 HTTP 接口**（对接任何有 API 的系统）
3. **用户自定义原子**（平台提供 SDK/模板）

安卓构建就是现成例子：通用命令两步（`gradle clean` + `gradle assembleRelease/Debug`），但应用 A 要装 npm、应用 B 要装 git-lfs、应用 C 要走 patch 打包。把这些都做成参数，配置就会长成没人看得懂的怪物；而给一个“执行自定义脚本”的原子，三行就解决。

## 后五个：定义「它怎么长大」

### ⑥ 流程可控

“覆盖端到端”不等于“一条流水线跑完全程”，而是**多条流水线 + 多种触发方式**，共同覆盖交付过程：

| 触发方式 | 用在哪 | 典型坑 |
|---|---|---|
| 事件触发（push/MR） | 提交级验证 | 注册 webhook 需要仓库 **Master 级权限**，权限不够会静默失败 |
| 定时触发 | 夜间全量、每日构建 | 与提交级任务抢 runner，把排队时间拉长 |
| 手动触发 | 发布、回滚 | 缺少权限管控时，谁都能点 |

事件触发的完整闭环是：仓库事件 → webhook → 流水线平台按规则过滤（最常见的是过滤分支）→ 执行 → 结果**写回代码仓库**。写回这一步很值钱：每次提交都关联一条流水线记录，评审时直接看到“这条 MR 的检查结果”，不用跳系统。

人工审批的实现有个细节值得抄：不要把审批逻辑塞进每个原子，而是把原子执行抽象成 `before()` / `execute()` / `after()` 三段，把审批写在 `before()` 或 `after()` 里，由基类统一执行，是否启用由原子配置里的参数控制。

```groovy
// 抽象基类：所有原子自动获得「阶段前审批 + 阶段后门禁」的能力
abstract class AbstractAtom extends AtomExecution {
  def atomExecution() {
    beforeAtomExecution()
    before()      // 通用前置逻辑：人工审批、权限校验
    execute()     // 原子主体
    after()       // 通用后置逻辑：质量门禁、结果上报
    afterAtomExecution()
  }
}
```

### ⑦ 动静分离配置化

原子的功能要持续迭代，但不该每加一个参数就要改前端页面。做法是**动静分离**：变化的部分（参数定义）放进静态配置文件，系统启动/加载时读接口，按约定类型动态渲染控件。

```json
// 原子参数的数据结构（节选）：前端按 type 渲染，按 required/default 校验
{
  "atom": "maven-build",
  "params": [
    {"key": "branch",  "type": "string", "required": true,  "default": ""},
    {"key": "profile", "type": "select", "required": false, "default": "release",
     "options": ["release", "debug", "patch"]},
    {"key": "timeout", "type": "int",    "required": false, "default": 30,
     "min": 5, "max": 240}
  ]
}
```

不这么做的代价是双份维护：前端一份渲染逻辑，后端一份校验逻辑；要同时兼容两个原子版本，前端就得存两套页面。上百个应用接入后，这套结构会自己塌掉。

### ⑧ 快速接入

能力图谱的扩张速度 = 接入成本的反比。经典做法是插件机制（Jenkins 的生态就是这么长出来的），但**每个平台都要企业内部自己写插件**时，接入意愿会断崖式下降。

更轻的路子是**只依赖三个接口**，把接入标准化成流水线平台发工具、平台方填三个实现：

| 接口 | 谁定义 | 作用 |
|---|---|---|
| 任务调用 | 接入平台 | 流水线触发一次任务，参数直接映射成原子参数 |
| 状态查询 | 接入平台 | 查执行进度、拿日志 |
| 数据上报 | 流水线平台 | 按标准结构回传结果，供门禁和聚合使用 |

有了标准接口，再给一个本地执行的 Scanner 式工具（SonarQube 的 Scanner 是同款思路），接入就变成「配置 + 实现三个接口」。按石雪峰的经验，一套平台接入基本可以在**几天内**完成。同步还是异步调用是接入方的选择，平台不假设。

### ⑨ 内建质量门禁

先看两个故事，它们解释了为什么门禁要内建而不是外挂：

- **丰田安灯（Andon）**：产线工人发现质量问题可以拉绳停线。停线不是目的，**及时暴露问题**才是。停线后相关人立刻聚到一起解决，经验再沉淀进组织能力。
- **亚马逊 2012 年引入安灯**：一线客服收到客户反馈或发现商品有质量风险，可以直接发告警邮件并把商品置为“不可购买”（强制下架），**不需审批**。偶尔误操作被视为可接受的学习成本。

戴明 14 条原则第 3 条讲的是同一件事：不要依赖检验来保证质量，检验既贵又不可靠，而且不提升质量，只能证明有缺陷。由此得到内建质量的两条原则：

> 🔑 ① 问题发现得越早，修复成本越低；② 质量是每个人的责任，不是质量团队的责任。

落地分五步，顺序不能乱：

| 步 | 动作 | 关键判据 |
|---|---|---|
| ① 选检查类型 | 先上投入产出比高的：缺陷/漏洞 > 代码风格 | 一次全上 = 研发不用干活了 |
| ② 定义指标与参考值 | 指标项（行/类/函数覆盖率选哪个）+ 参考值 | 与研发负责人**达成一致**，否则执行不下去 |
| ③ 建立自动化执行 | 门禁进流水线，或进提测/发布平台 | 生效点尽量靠近数据产生环节 |
| ④ 定义处置方式 | 失败 / 告警 / 人工确认 | 三态缺一，要么全拦要么全放 |
| ⑤ 持续优化 | 指标、参考值、处置方式都可调 | 目标不是通过门禁，是质量提升 |

存量债的处理办法是**只用增量指标**：只卡新增代码的覆盖率、只卡“不增加”的基线（`≤ 100`），存量先记账（[58.2 技术债管理](../58-架构治理/58.2-技术债管理.md)）。参考值怎么定、阈值怎么算，见 [53.8 覆盖率与质量门禁](../53-测试与质量保障/53.8-覆盖率与质量门禁.md)。

生效点前移的方向是固定的：

```text
IDE（本地） → 版本库（pre-push/MR） → 流水线（CI） → 提测 → 发布
越靠左，修复成本越低；越靠右，拦截越彻底但代价越大
```

> ⚠️ 门禁最大的失败不是规则不严，是**规则被绕过**：有多少正常流程走了特殊审批、多少发布走了紧急通道、多少人抱怨“开了门禁就没法交付”。这三个数字比门禁通过率更能说明它是否活着。

### ⑩ 数据聚合采集

系统没打通时，看测试结果要去测试平台、看数据库变更要去变更平台，**没有一个地方能看完这次发布的全貌**。所以接入时务必要求子系统实现数据上报接口。

上报粒度有个反直觉的取舍：**元级数据进平台，明细靠报告链接**。以单元测试为例，平台要收的是“总用例数、执行数、成功/失败数、各维度覆盖率”；至于每个文件的覆盖率明细，数据量太大，生成报告给链接即可。

流水线的目标是**客观呈现**，不是挖掘分析。企业开始建数据度量平台后，流水线退化为数据源之一（[59.6 度量体系与数据平台](../59-研发效能度量/59.6-度量体系与数据平台.md)）。

## 可运行：把门禁拆成「规则 + 结果」

十个特征里最能立刻验证的是第 9 条。下面这个求值器把门禁拆成两个文件：`rules.json`（规则，可热改）和 `report.json`（各子系统上报的结果）。规则改动不需要改代码，这正是第 7 条动静分离的最小实现。

```python
#!/usr/bin/env python3
"""gate.py —— 质量门禁求值器：规则与执行结果分离。

用法: python3 gate.py rules.json report.json
退出码: 0 放行 / 1 阻断 / 2 配置错误
"""
import json
import sys

OPS = {
    ">=": lambda v, t: v >= t,
    ">":  lambda v, t: v > t,
    "<=": lambda v, t: v <= t,
    "<":  lambda v, t: v < t,
    "==": lambda v, t: v == t,
}

def main(rules_path: str, report_path: str) -> int:
    rules = json.load(open(rules_path))["rules"]
    report = json.load(open(report_path))

    fails = warns = 0
    for r in rules:
        rid, level = r["id"], r.get("level", "fail")
        v = report.get(r["metric"])
        if v is None:                       # 数据没上报，等于没检查——按失败处理
            print(f"MISS  {rid:<14} 指标缺失（{r['metric']} 未上报），按失败处理")
            fails += 1
            continue
        if OPS[r["op"]](v, r["value"]):
            print(f"PASS  {rid:<14} {v:<6.1f} {r['op']} {r['value']:<5.1f}")
        elif level == "warn":               # 告警值：只标记，不阻断
            print(f"WARN  {rid:<14} {v:<6.1f} {r['op']} {r['value']:<5.1f}  （只告警，不阻断）")
            warns += 1
        else:
            print(f"FAIL  {rid:<14} {v:<6.1f} {r['op']} {r['value']:<5.1f}")
            fails += 1
    print(f"结果：{fails} 条失败、{warns} 条告警 → {'门禁阻断' if fails else '放行'}")
    return 1 if fails else 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1], sys.argv[2]))
```

规则与上报数据：

```json
{
  "rules": [
    {"id": "unit_line_cov", "metric": "unit.line_coverage", "op": ">=", "value": 50, "level": "fail"},
    {"id": "blocker",       "metric": "sonar.blocker",      "op": "<=", "value": 0,  "level": "fail"},
    {"id": "diff_cov",      "metric": "diff.coverage",      "op": ">=", "value": 80, "level": "warn"}
  ]
}
```

```json
{"unit.line_coverage": 47.3, "sonar.blocker": 0, "diff.coverage": 91.2}
```

**本机实测输出**（Python 3.14.8）：

```text
FAIL  unit_line_cov  47.3   >= 50.0 
PASS  blocker        0.0    <= 0.0  
PASS  diff_cov       91.2   >= 80.0 
结果：1 条失败、0 条告警 → 门禁阻断
```

只改规则、不改代码（门槛从 50 降到 45，模拟存量债期的一次豁免）：

```text
PASS  unit_line_cov  47.3   >= 45.0 
PASS  blocker        0.0    <= 0.0  
PASS  diff_cov       91.2   >= 80.0 
结果：0 条失败、0 条告警 → 放行
```

告警值 + 数据缺失两条路径（规则里把 `diff_cov` 门槛提到 95 并标 `warn`，同时不报 `sonar.major`）：

```text
WARN  diff_cov       91.2   >= 95.0   （只告警，不阻断）
MISS  sonar.major    指标缺失（sonar.major 未上报），按失败处理
PASS  unit.line_coverage 47.3   >= 40.0 
结果：1 条失败、1 条告警 → 门禁阻断
```

读法有三条：

1. **`MISS` 必须算失败**。数据没上报时如果默认放行，等于给了所有人一个“不上报就通过”的后门——这也是特性 ⑩ 要求强制上报的原因。
2. **告警值让门禁可分阶段收紧**。存量债先用 `warn` 观察两周，再改 `fail`，比一上来就阻断更容易推。
3. **退出码就是接口**。CI 里只需要 `python3 gate.py rules.json report.json`，非 0 即失败，不需要平台支持任何特殊功能。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**。按十个特征挑产品，先看第 1 与第 8 条：

| 产品 | 编排模型 | 接入方式 | 适合 |
|---|---|---|---|
| **GitLab CI** | `.gitlab-ci.yml` + stage/job | 引用其他仓库的 yml、`trigger` 子流水线 | 已用 GitLab 的团队，开箱即用 |
| **Jenkins LTS + 插件** | Jenkinsfile（Groovy）+ 插件 | 插件中心，支持自定义原子 | 存量系统多、需要深度定制 |
| **Tekton** | CRD（Pipeline/Task） | Task 复用、Catalog | Kubernetes 原生，与 Argo CD 配合 |
| **Argo Workflows** | DAG/步骤模板 | 模板库、Artifact | 复杂依赖、批处理任务 |
| **Azure DevOps** | YAML + 任务市场 | 市场扩展 | 已用 Azure 生态 |

平台门户（把流水线、文档、服务目录收进一个入口）可参考开源 Backstage；**Backstage、Tekton、Argo 三者都在真集群/本机部署过**：

- **Backstage 1.57.0**：`create-app` 脚手架 + `yarn install`（2687 包 / 1.7 GB / 2 分 30 秒）+ `yarn start`，首页 200，服务目录返回 9 个实体（详见 [78.5](../../组织/78-技术组织设计/78.5-平台工程.md)）。
- **Tekton Pipelines v1.6.0**（k3s v1.37.2，3 个控制面 Pod）：`Task` 里写一个覆盖率门禁，TaskRun 传 `0.86` → `Succeeded True`、日志 `GATE PASSED`；传 `0.61` → 条件 `Failed`、日志 `GATE FAILED`；`PipelineRun` 引用该 Task → `Succeeded True`。**门禁在流水线里真的会拦失败**，不是纸面配置。
- **Argo CD v2.13.3**：`app sync` 1 秒完成、`history` 两次部署、`rollback` 回到 id 0 后 `Synced Healthy`（详见 [54.3](../54-制品与部署/54.3-部署编排.md)）。

**可抄**：门禁接进任意 CI，只需要三步——产出指标文件、生成 `report.json`、跑求值器。

```yaml
# .gitlab-ci.yml（骨架：编排 + 门禁；gate.py 与 rules.json 放在仓库根）
stages: [test, gate, deploy]

unit:
  stage: test
  script:
    - go test ./... -coverprofile=cover.out
    - go tool cover -func=cover.out | tail -1 | awk '{gsub("%","",$3); print "unit.line_coverage=" $3}' > metrics.env
  artifacts:
    when: always
    paths: [cover.out, metrics.env]

gate:
  stage: gate
  needs: [unit]
  script:
    # ① 把各子系统上报的指标（metrics.env）合成一份 report.json
    - python3 -c 'import json;d=dict(l.split("=") for l in open("metrics.env").read().split());d={k:float(v) for k,v in d.items()};d.setdefault("sonar.blocker",0);json.dump(d,open("report.json","w"))'
    # ② 求值器：退出码非 0 直接让 job 失败
    - python3 gate.py rules.json report.json

deploy:
  stage: deploy
  needs: [gate]
  script: ["./deploy.sh"]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

**可验**：上面 `gate.py` 的三段输出是真实跑出来的（Python 3.14.8，工作目录里只有 `gate.py`/`rules.json`/`report.json`），判据是退出码：阻断场景 `exit=1`、放行场景 `exit=0`。GitLab CI 的 yml 只做了本地语法骨架整理，**没有在真实 GitLab 实例上跑过**——缺一台 GitLab Runner，这是本节唯一未验证的部分。

**可退**：三层回退，由快到慢——

| 层级 | 动作 | 生效时间 |
|---|---|---|
| 规则级 | 把该条 `level` 改成 `warn`，或临时删除该 rule | 下一次执行 |
| 任务级 | 关掉流水线模板里的 gate job 开关（变量 `SKIP_GATE=1` 时跳过） | 改配置即生效 |
| 平台级 | 回滚流水线模板到上一版本（模板即代码，在第 3 条特征里） | 一次提交 |

> 🔑 可退不是“留后门”，而是**让门禁能被安全地收紧**。没有快速回退门禁的组织，第一次误拦就会把门禁永久关掉。

## 反模式

| 反模式 | 后果 |
|---|---|
| 把测试、扫描、审批都做进流水线平台 | 平台臃肿，垂直能力做不深，既有平台团队失去接入动机 |
| 写死三个固定阶段 | 不需要编译的技术栈也被迫跑构建；畸形用法把步骤塞到错误阶段，可视化失真 |
| 参数穷举所有特例 | 平台复杂度指数上升，没人搞得懂怎么配（Xcode 步骤 53 个参数即样本） |
| 流水线配置存数据库且不评审 | 门禁规则可以被静默修改，出事故查不到谁改的 |
| 不记录执行时快照 | 重跑复现不出当时结果，故障复盘归因失败 |
| 并发实例共用工作区 | 产物互相覆盖，出现“随机失败”，最后被当成 flaky 忽略 |
| 接入一个新平台要写插件并改平台代码 | 能力图谱停止扩张，平台变成少数人的工具 |
| 门禁只在发布前拦 | 发现太晚，修复成本指数上升，团队最终要求绕过 |
| 数据没上报时默认放行 | 门禁形同虚设：不上报即通过 |

## 自检

**Q1** 团队要把自动化测试平台的功能“全部集成进流水线”，说这样用户只用一个系统。按第 1 条特征，这个决定的问题在哪？怎么改？

▸ 答案：问题不在“集成”，在“替代”。把垂直能力实现进流水线平台，等于让平台同时承担调度与专业能力：平台会臃肿、垂直能力做不深、原平台团队失去动机。改法是反向集成——垂直平台以原子/三个接口接入，流水线只负责编排与记录，用户看到的入口仍然是一个。

**Q2** 平台已经有 Jenkinsfile 了。为什么作者说这还不算“流水线即代码”的全部？

▸ 答案：Jenkinsfile 只满足了“配置进版本库、可评审、可追溯”。还缺实例化三件事：参数化（一条模板服务多分支）、执行时快照（重跑能复现当时配置）、并发隔离（多实例各自独立工作区）。缺其中任一条，出问题时都无法定位“当时跑的是哪套配置”。

**Q3** 一个原子要不要支持“构建时顺带把镜像推送到仓库并通知企业微信”？用第 5 条原则判断。

▸ 答案：不要。原子应该只做一件独立任务，“构建 + 推送 + 通知”是三件事，混在一起后无法被别的流水线复用、失败也无法分辨在哪一步。用三段编排替代一个复合原子；推送和通知各自是独立原子，通知还能用“调用 HTTP 接口”逃生舱实现。

**Q4** 门禁上线一周，通过率 99%，作者却说要警惕。为什么？

▸ 答案：通过率高可能意味着门禁没真正拦住东西——或者规则太松，或者大量流程走了特殊审批/紧急通道，或者数据没上报被当成通过。要看的不是通过率，而是：绕过次数、紧急通道次数、MISS（指标缺失）次数、门禁触发后是否真的有人处理。

**Q5** 为什么 `MISS`（指标未上报）要按失败处理，而不是“跳过检查”？

▸ 答案：跳过等于奖励不接入：不上报就能通过，团队就没有动力去实现数据上报接口，特性 ⑩ 直接失效。把缺失当失败，是用门禁倒逼数据打通——代价是上线初期要给出上报模板，否则门禁会因为“没数据”而全员失败。

**Q6** 并发实例互相覆盖产物的根因是什么？加锁能解决吗？

▸ 答案：根因是工作区没有隔离（两个实例共用同一份源码/构建目录）。加锁只是把并发变成串行，白白牺牲吞吐。正确解是每实例独立工作区 + 静态数据（依赖缓存、构建缓存）只读共享。

**Q7** 新人问：“我们已经有持续交付平台了，为什么还要数据度量平台？”用第 10 条回答。

▸ 答案：流水线的职责是把一次执行的结果**客观呈现**，不具备跨应用、跨时间的分析能力；度量平台要做的是跨系统采集、口径统一、趋势对比。流水线是度量平台的一个数据源，不是它的替代品。两者混在一起的结果是：流水线越来越重，而度量仍然算不准。

**Q8** 平台要接入第 30 个垂直系统。用第 8 条特征估一下：什么情况下这是“五天”的活，什么情况下是“五个月”？

▸ 答案：五天——对方已有任务调用/状态查询 API，只缺标准的数据上报格式，用 Scanner 式本地工具补上即可。五个月——对方没有 API（只能连库或订阅消息）、鉴权模型不兼容、数据模型要翻译（同一个“购物车”在两边叫法与维度都不同）。第 8 条的真实成本由对方的接口成熟度决定，不由平台侧决定。
