# 51.6 AI 代码审查：从 diff 到证据

## 一句话

> AI 审查不是「多一个 reviewer」，而是把审查拆成**广度、深度、证据**三层：广度靠清单，深度靠跨模块上下文，证据靠 `file:line` + 测试 + 复现；人仍然只做最后那层判断——**哪些问题值得修、这个 PR 能不能合**。

## 先破除五个误区

| 误区 | 现实 |
|---|---|
| AI 能替代人审 | 它扩大覆盖、降低漏检，但不承担取舍；「哪些必须修、哪些可以放」仍是人的责任 |
| 审查工具越多越好 | 每个工具都有 token、延迟、误报和维护成本；先加确定性门禁，再加 AI |
| AI 说 LGTM 就能合 | 没有证据的 LGTM 是噪音；审查结论必须能落到代码位置、测试或复现步骤 |
| 大 PR 让 AI 看就行 | 上下文窗口不等于理解；先拆小 PR，AI 才看得清，人也才审得动 |
| 自动修复 = 自动合并 | 修复越自动，越要人审；「AI 动手，人类拍板」是底线 |

## 先分层：哪些活不该交给 AI

代码审查不是一件事，是一条流水线。**便宜、确定、可自动化的先跑**；AI 放在「需要理解语义」的位置，而不是替代 lint/test。

| 层 | 看什么 | 谁来做 | 典型输出 |
|---|---|---|---|
| 确定性门禁 | 格式、编译、单测、race、SAST、依赖漏洞 | `gofmt` / `go vet` / `go test` / `-race` / Semgrep | 通过 / 失败 + 行号 |
| Diff 审查 | 命名、结构、重复、错误处理、测试缺口 | AI 审查 Skill | 分级 finding |
| 规格审查 | 是否实现需求、验收条件、边界 | AI + 人 | 需求遗漏 / 偏离 |
| 语义审查 | 跨模块调用链、根因、影响面 | 语义级工具 + 人 | 证据链 + 修复建议 |
| 架构审查 | 依赖方向、循环依赖、腐化趋势 | `/smell` 一类工具 + 架构师 | 坏味道报告 + 路线图 |
| 人工决策 | 值不值得修、能否上线 | 人 | 合并 / 打回 / 跟进 |

> 🔑 先让确定性门禁全绿，再让 AI 审查。否则 AI 会把时间花在「少个分号」上，真正的问题反而被淹没。

## 两条轴：质量与规格分开

Matt Pocock 的 `/code-review` 把审查拆成两条互不干扰的轴：

| 轴 | 问什么 | 输入 | 典型发现 |
|---|---|---|---|
| **Standards** | 代码写得好不好 | diff + 仓库规范 + Fowler 坏味道基线 | 命名、重复、特性依恋、过长函数 |
| **Spec** | 代码做得对不对 | issue / spec / 验收标准 | 漏需求、偏离行为、边界没覆盖 |

两条轴**并行跑、不合并排名**：Standards 发现再多问题，也不能掩盖 Spec 的一条需求遗漏；反过来也一样。很多 AI 审查只做 Standards，因为 diff 里能看到代码，却看不到需求——**没有 spec 的审查，只能审「写得像不像好代码」，审不了「做没做对」**。

## 审查契约：七个必须回答的问题

无论用哪个工具，AI 审查的输出至少能回答这七个问题（来自 `github-deep-review` 的审查契约）：

1. 正在修的 bug / 行为是什么？
2. 根因在哪？不能定位时，缺什么证据？
3. 回归是谁、哪个 commit / PR 引入的？
4. 当前修复是读完相邻代码后的最佳修复吗？
5. 更大规模的重构会改善正确性 / 可维护性吗，还是只是扩大范围？
6. 证据是什么：测试、复现、CI、文档、依赖源码、线上行为？
7. 还有什么风险或未验证项？

答不出第 3、6、7 条时，结论必须写「未证明」，而不是编一个自信的总结。

## 范围控制：AI 审查最大的坑是「顺便重构」

AI 审查最常见的失败不是漏报，是**范围蔓延**：发现一个小问题，顺手重构，重构到一半要改 API，改 API 又要改配置——50 行的 PR 变成 800 行。

autoreview 的 Scope Governor 把发现分成三类：

| 分类 | 判据 | 动作 |
|---|---|---|
| **In-scope blocker** | 当前 diff 引入、同一归属边界、修它不改任务契约 | 本轮必须修 |
| **Follow-up** | 确实是问题，但在相邻模块 / 关联 bug | 另开任务，不在本轮修 |
| **Stop-and-escalate** | 需要新协议、新配置、新公共 API、跨归属边界 | 停，上报，等人决策 |

五条停止条件，触发任何一条就停：

- 小改动变成了架构变更；
- diff 规模翻倍且没拿到扩大范围的许可；
- 两轮修复后还没收敛；
- 最佳修复是先定规范/契约，而不是本地打补丁；
- 修完之后，PR 描述的已经不是同一个行为。

> 🔑 **审查的目标是「让这个 PR 可以安全合并」，不是「把代码库改成你喜欢的样子」**。

## 证据分级：别把推断说成实测

AI 很擅长把「看起来对」说成「已验证」。审查结论必须标证据等级：

| 等级 | 含义 | 例子 |
|---|---|---|
| **已实测** | 真跑过，有输出 | `go test -race ./...` 全绿；复现脚本输出 |
| **代码推断** | 读代码/测试得出，未执行 | 「这条分支在 `err != nil` 时提前返回」 |
| **未验证** | 都没有，必须明说 | 「本机没有该依赖，跨服务行为未验证」 |

严重度与置信度分开：`critical/high/medium/low` 是影响，`high/medium/low` 是把握。**高影响 + 低置信**的发现要标出来，让人去验证，而不是直接当 blocker。

## 接入流程：一条能落地的流水线

```text
提交前：格式化 + 编译 + 单测（本地/钩子）
   ↓
PR：确定性门禁（lint / vet / test / race / SAST / 依赖扫描）
   ↓
AI diff 审查（Standards + Spec）
   ↓
分级：blocker / follow-up / 建议 / 拒绝（附理由）
   ↓
人审：看证据、做取舍、决定合并
   ↓
合并后：定期架构审查（/smell）、大 PR 可视化（PR Lens）
```

四条纪律：

1. **AI 输出只作建议**：每条 finding 必须读真实代码路径和相邻文件验证；不切实际的边缘案例直接拒。
2. **修复要小**：不做大规模重构，除非它从根上改善这类 bug；修完重跑测试和审查。
3. **不自动 push / 不自动合并**：审查是本地或 PR 活动，push 只在人明确要求时发生。
4. **两个模型交叉审关键 PR**：Claude 和 Codex 的盲区不同，交叉能提高覆盖率；日常小改动不必。

## 工具选型：按「审查深度」而不是「热度」

| 需求 | 首选 | 特点 | 边界 |
|---|---|---|---|
| 日常功能收尾 | `/code-review` / `/review-it` | 轻、快、diff 级；双轴或八方向 | 跨模块架构问题看不到 |
| 合并前质量门禁 | agent-skills `/review` | 五轴：正确性/安全/性能/可维护性/风格 | 维度多，耗时长 |
| 深度语义审计 | Clawpatch | 先把仓库映射成语义特征，再按功能单元审 | 慢、token 贵，适合重点功能/定期审计 |
| 关键 PR / 根因 | `github-deep-review` | 七问契约、调用链、出处追踪 | 日常小改动不值得 |
| 自动化循环 | autoreview | 改了就审、审了修，带 Scope Governor | 需要模型与 token 预算 |
| 架构腐化 | `/smell` | 8 类 60+ 坏味道，定期跑 | 不是每次提交都跑 |
| 大 PR 理解 | PR Lens | 把变更画成爆炸半径 + 数据流 | 不查对错，只帮看懂 |
| 交付说明 | walkthrough | 先讲人话、标证据等级、写爆炸半径 | 是审查前的准备，不是审查本身 |

> ⚠️ 工具名、安装方式与能力以各自仓库 README 为准；本节引用的是 [《AI 时代的软件工程》第 34 章](https://se.rpcx.io/34.html) 的整理，版本会漂。

## 反模式

| 反模式 | 后果 |
|---|---|
| 让 AI 审查一个 2000 行 PR | 它只能看开头；先拆到 200–400 行 |
| 没有 spec 就审「做得对不对」 | 只能审风格，审不了需求 |
| 把 AI 的「建议」直接当 blocker | 误报消耗人的注意力，团队开始忽略审查 |
| 让 AI 自动修完自动合 | 范围蔓延 + 无证据；事故责任无法追溯 |
| 只看 finding 数量 | 数量与质量无关；看 blocker 与证据 |
| 审查跑在 lint/test 之前 | 把最贵的注意力花在最便宜的判断上 |
| 用截图/摘要代替真实代码路径 | 漏掉跨文件影响；结论不可复核 |
| 工具装一堆，没有流程 | 每个工具都跑一遍，最后没人看结果 |

## 自检

**Q1** 为什么 AI 审查不能替代人审？它到底扩大了什么？

▸ 答案：AI 扩大的是**覆盖面和一致性**：它能按同一套清单检查每个 diff、跨文件读调用链、不因疲劳降标；但它不承担「哪些问题值得修、这个 PR 能不能合」的责任，也不理解业务取舍。人审的价值在判断与授权，不在逐行找茬。

**Q2** Standards 轴和 Spec 轴为什么要分开？只跑一条会漏什么？

▸ 答案：Standards 审「代码写得好不好」，Spec 审「需求做得对不对」。只跑 Standards，会漏掉需求遗漏/行为偏离；只跑 Spec，会漏掉结构、命名、错误处理。分开跑还能避免一条轴的问题掩盖另一条轴的问题。

**Q3** AI 审查发现「这里可以顺便重构」，为什么不能直接让它改？

▸ 答案：这是范围蔓延。审查目标是让当前 PR 安全合并，不是改造代码库。发现应分为 in-scope blocker、follow-up、stop-and-escalate；跨模块/新 API/新协议要先停、上报，另开任务，否则 50 行 PR 会变成 800 行，风险和 review 成本都失控。

**Q4** 「已实测 / 代码推断 / 未验证」三级证据为什么重要？

▸ 答案：AI 容易把推断说成事实。三级标签让审查者知道哪些结论可以直接信、哪些要复现、哪些只是假设；尤其「高影响 + 低置信」的发现，必须显式标出，避免把猜测当 blocker 或把未验证当已通过。

**Q5** 日常开发、合并前、关键 PR、定期审计，分别该用什么？

▸ 答案：日常用 `/review-it` 或 `/code-review`（轻量 diff）；合并前用 agent-skills `/review` 五轴门禁；关键 PR / 根因用 `github-deep-review`（七问 + 证据链）；定期用 Clawpatch 深度语义审计 + `/smell` 架构坏味道。大 PR 先用 PR Lens 画出来再读。

**Q6** 如果团队只能先做一件事，应该做什么？

▸ 答案：先把确定性门禁做扎实：格式化、编译、单测、`-race`、SAST、依赖扫描全绿，再谈 AI 审查。确定性门禁的误报最低、成本最低，能挡掉大部分机械问题；没有这层，AI 审查只会把噪音放大。
