# 51.5 依赖治理：MVS 与可复现构建

## 一句话

> 依赖治理不是“定期升级”，而是**把版本选择规则写死**：Go 用 MVS（选所有声明里要求的最高值），主版本号是模块路径的一部分；再配上 `GOPROXY` / `GOSUMDB` / `GOPRIVATE` 与 `go.sum`，同一个提交才能在任何机器上装出**同一份依赖树**。

> 来源：`go.mod`/`go.sum`、`GOPROXY`/`GOSUMDB`/`GOPRIVATE`、`replace` 与 vendor 的用法来自 aceld《深入理解 Go 语言》第 8 篇「精通 Golang 项目依赖 Go modules」；MVS 的规则推演、影响面估算与可复现清单为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “`go get -u` 升到最新最安全” | 最新版是别人刚发布的东西，风险最高。升级应当是**显式决策**，不是构建时的副作用 |
| “MVS 就是选最旧的版本” | 选的是**所有声明里要求的最大值**——它比任何单个声明要求的版本都不旧，只是不会额外往上跳 |
| “主版本号只是个数字” | Go 里主版本号是**模块路径的一部分**（`github.com/x/y/v2`），表示不兼容承诺；`v1` 与 `v2` 是两个模块，互不比较 |
| “有 `go.sum` 就安全” | `go.sum` 只保证“下载到的内容和记录一致”，不保证“内容本身没有漏洞”。防篡改与查漏洞是两条独立防线 |

## MVS：三行规则

| 规则 | 含义 |
|---|---|
| ① 只声明**最低要求** | `require` 写的是“至少需要这个版本”，不是“锁定这个版本” |
| ② 最终选中 = **所有要求的最大值** | 依赖图里所有模块对同一个包的要求，取最高者 |
| ③ 主版本不同 = **不同模块** | `v1` 与 `v2` 是两个模块路径，不参与版本比较 |

第 ② 条是最反直觉的：它既不是“用最新”，也不是“用最旧”。它保证的是**确定性**——只要依赖图不变，结果就唯一；而且**加一个依赖不会把已有依赖降级**，只会可能把它升级。

## 可运行：MVS 到底在算什么

```python
#!/usr/bin/env python3
"""mvs.py —— 最小版本选择（Minimal Version Selection）在算什么。

规则（Go modules）：
  1. 每个模块只在 go.mod 里声明「至少需要」依赖的哪个版本
  2. 最终选中的版本 = 所有声明里要求的**最大值**——不是最新版，也不是最小值
  3. 主版本号不同 = 不同模块路径（C 与 C/v2 是两个模块，互不比较）
本例简化：同一模块的不同版本，依赖声明相同；版本号按 x.y 字符串比较即可。
"""
GRAPH = {
    "app": {"A": "1.2", "B": "1.1"},
    "A":   {"C": "1.3"},
    "B":   {"C": "1.4"},
    "C":   {"D": "1.0"},
    "D":   {},
}


def requirements(root):
    """收集每个模块被谁、以什么最低版本要求过。"""
    req = {}

    def walk(mod):
        for dep, ver in GRAPH[mod].items():
            req.setdefault(dep, set()).add((mod, ver))
            walk(dep)

    walk(root)
    return req


def mvs(root):
    return {m: max(v for _, v in pairs) for m, pairs in requirements(root).items()}


req = requirements("app")
sel = mvs("app")
print(f"{'模块':<6}{'被要求':<26}{'选中'}")
for m in sorted(sel):
    print(f"{m:<6}{', '.join(f'{src}→{v}' for src, v in sorted(req[m])):<26}{sel[m]}")

print("\n把 B 从 1.1 升到 1.2（它 require C@1.5）之后：")
GRAPH["B"]["C"] = "1.5"
print(f"  C 的选中版本：{sel['C']} → {mvs('app')['C']}——A 仍只要 1.3，但整体升到 1.5")
```

**本机实测输出**（Python 3.14.8）：

```text
模块    被要求                       选中
A     app→1.2                   1.2
B     app→1.1                   1.1
C     A→1.3, B→1.4              1.4
D     C→1.0                     1.0

把 B 从 1.1 升到 1.2（它 require C@1.5）之后：
  C 的选中版本：1.4 → 1.5——A 仍只要 1.3，但整体升到 1.5
```

三条读法：

1. **C 被选中 1.4**，因为 A 要 1.3、B 要 1.4，取最大值。如果只按“A 的要求”装 1.3，B 就会坏——MVS 用“取最高”避免了“装了个别人要求更高的小版本”。
2. **升级 B 会连带升级 C**。这条是依赖治理里最容易被低估的：你在 `go.mod` 里改了一行，实际影响面是这个节点的**传递闭包**，而不是那一行本身。
3. **MVS 永远不会自动跨主版本**。想要 `v2`，必须在代码里改 import 路径（`/v2`），这是语言层面强制的“不兼容就要看得见”。

## 升级一个依赖，影响面怎么估

| 你改的 | 实际影响 | 怎么估 |
|---|---|---|
| 升一个直接依赖的次版本 | 可能连带升级它依赖的模块（如上例 C） | 跑 `go mod graph` / `go list -m all`，对比前后两份清单 |
| 升一个直接依赖的主版本 | 模块路径变了，所有 import 都要改 | 按“换一个库”来评估，不是“升个版本” |
| 加一个新依赖 | 不会降级任何已有依赖，但可能升级它们 | 看 `go.sum` 的 diff 条数 |
| 用 `replace` 指到本地/fork | 构建结果与 `require` 声明不一致，别人复现不了 | 只允许临时用，提交前删掉 |

## 供应链配置：三个环境变量定生死

| 变量 | 作用 | 典型设置 | 坑 |
|---|---|---|---|
| `GOPROXY` | 从哪下载模块（可列多个，逗号分隔，`direct` 表示直连） | 内网用自建代理；无外网时设 `off` 并依赖 vendor | 只写一个代理且它挂了 → 构建全断 |
| `GOSUMDB` | 校验模块哈希是否被篡改（默认连官方校验库） | 内网需镜像或自建 | 关掉它等于放弃防篡改 |
| `GOPRIVATE` | 私有模块前缀：这些模块**不走代理、不做校验** | `GOPRIVATE=git.mycorp.com/*` | 不设 → 私有库拉取失败；设太宽 → 公共库也失去校验 |

`GOPRIVATE` 会同时设置 `GONOPROXY` 与 `GONOSUMDB`，一般不需要再单独配后面两个。私有库的鉴权走 `~/.netrc` 或 SSH key，别把 token 写进 URL。

## 可复现构建：五条清单

| # | 做法 | 判据 |
|---|---|---|
| 1 | `go.mod` 与 `go.sum` **都入库** | 换一台机器、`git clean -xdf` 后能构建 |
| 2 | 固定 Go 版本（`toolchain` 指令或 CI 镜像） | 本地与 CI 的 `go version` 一致 |
| 3 | CI 用 `-mod=readonly`（Go 1.16+ 默认） | 构建不会偷偷改 `go.mod` |
| 4 | 依赖变更走 PR，看 `go.sum` diff | 一次提交里依赖变化可审计 |
| 5 | 制品构建只依赖已提交的 `go.mod`/`go.sum`/vendor | 构建产物可复现（[54.1 不可变制品](../54-制品与部署/54.1-不可变制品.md)） |

`vendor` 还是代理仓库？两者的取舍：

| 方案 | 优点 | 代价 | 适合 |
|---|---|---|---|
| **vendor 目录入库** | 完全不依赖网络与代理；构建最快最稳 | 仓库变大；每次升级产生大量 diff | 内网、CI 无外网、要极致可复现 |
| **模块代理 + go.sum** | 仓库干净；升级 diff 只有几行 | 依赖代理可用性；CI 需缓存 | 常规团队 |

## 与漏洞扫描的分工

依赖治理有两件事，别混：

- **本节**：选哪个版本、能不能复现、私有库怎么进——决定“依赖树长什么样”。
- **[52.3 依赖与漏洞扫描](../52-持续集成/52.3-依赖与漏洞扫描.md)**：这棵树里有没有已知漏洞、是否可达——决定“这棵树能不能上线”。

顺序是：先锁树（本节），再扫树（52.3）。反过来做，扫描结果第二天就因为依赖漂移而失效。

## 反模式

| 反模式 | 后果 |
|---|---|
| CI 里跑 `go get -u` 再构建 | 每次构建的依赖树都不同，故障无法复现 |
| `go.sum` 不入库 | 各机器装出的依赖可能不同，甚至被投毒 |
| 私有库用 `GOPRIVATE=*` 图省事 | 公共库也失去校验，供应链防线整体失效 |
| 用 `replace` 指向本地路径并提交 | 别人构建时路径不存在；声明与实际不符 |
| 依赖升级与业务改动混在一个 PR | 出问题时无法判断是依赖还是代码 |
| 从不升级，等“有空再说” | 一次跨多个主版本升级，风险指数级上升 |
| 认为 `go.sum` 能防漏洞 | 防篡改与查漏洞是两条线，缺一条都不安全 |

## 自检

**Q1** A 依赖 C@1.3，B 依赖 C@1.4，最终会装哪个版本？为什么不是 1.3？

▸ 答案：装 1.4。MVS 取**所有声明里的最大值**。装 1.3 会让 B 的“至少 1.4”不成立；装 1.4 对 A 仍然兼容（A 只要求“至少 1.3”）。这就是“最低要求 + 取最高”的组合：既尊重声明，又保证一致。

**Q2** 团队为了用上一个新特性，把某个依赖从 v1 升到 v2。为什么这不是“改个版本号”？

▸ 答案：Go 里主版本号是模块路径的一部分，v2 的路径是 `.../v2`，与 v1 是两个模块。升级意味着所有 import 路径都要改、API 可能不兼容、并且 v1 的传递依赖可能同时存在（两个模块并存）。要按“换库”的工作量评估。

**Q3** `go.sum` 入库了，为什么还需要 `GOSUMDB`？

▸ 答案：`go.sum` 是“我信任第一次下载的那份”的本地记录；如果第一次下载就被投毒，`go.sum` 会把恶意版本记成合法。`GOSUMDB` 提供独立的校验源（校验和数据库），用来验证“这份代码确实是官方发布的”，两者互补。

**Q4** 内网 CI 无法访问外网，依赖治理该怎么配？

▸ 答案：三条路——① 自建模块代理并把依赖缓存在内网；② 把依赖 `vendor` 进仓库，CI 只用 vendor；③ 用 `GOPROXY=off` 配合 vendor，明确禁止联网拉取。无论哪条，`go.sum` 都要入库并校验。

**Q5** 为什么“先扫描漏洞、后锁依赖”的顺序是错的？

▸ 答案：扫描结论只对当时那棵树成立。如果依赖没锁，下一次构建可能装到不同版本，昨天的扫描结论今天就失效，甚至出现“扫的是 A 版本、跑的是 B 版本”。正确顺序是先锁（`go.mod`+`go.sum` 稳定），再扫，并且扫描结果与提交绑定。

**Q6** 一个 PR 同时改了业务代码和三个依赖的版本，会带来什么问题？

▸ 答案：出故障时无法归因——是业务逻辑错了，还是依赖行为变了？依赖升级应当单独成 PR，并且用 `go.sum` 的 diff 作为审计材料；这样回滚也可以只回滚依赖。

**Q7** `replace` 指向本地路径并用它调试，提交前必须做什么？

▸ 答案：删掉 `replace`。它让“声明”和“实际构建”不一致，别人在你机器之外根本构建不出来；CI 也会因为路径不存在而失败。如果确实需要 fork，就把 fork 发布成可寻址的模块版本，再用 `replace` 指向那个版本（而不是本地路径），并在 PR 里写清原因。

**Q8** 怎么判断一次依赖升级的影响面到底有多大？

▸ 答案：对比升级前后的完整依赖清单（`go list -m all` 或 `go mod graph`），看有多少模块的版本发生变化、`go.sum` 的 diff 有多长。只看 `go.mod` 里改的那一行，会漏掉被连带升级的传递依赖——那才是线上事故的常见来源。
