# 58.9 遗留系统现代化：先织网，再动刀

## 一句话

> 屎山的决定性特征不是技术旧，是**没有行为快照**；正确的顺序是「先补特征测试织网 → 用 `/teach`、`/understand`、图读懂 → 长芽/绞杀者/棘轮小步走 → 规格能完整复述后再谈重写」；机械转换交给确定性工具，语义判断交给 LLM，验证交给测试。

## 先破除五个误区

| 误区 | 现实 |
|---|---|
| 重写比重构快 | 旧代码里沉淀着无数次线上事故换来的修复；重写把这笔遗产清零，风险通常被低估 |
| 代码丑 = 没救 | Feathers 的定义：遗留代码是**没有测试**的代码；丑但行为可冻结，就还能改 |
| AI 能直接改屎山 | 没有行为快照，AI 改得越快，错得越隐蔽；先织网，再动刀 |
| 覆盖率越高越安全 | 覆盖率只说明「跑过」，不说明「断言了正确行为」；特征测试要冻行为，不是凑行数 |
| 大规模现代化 = 语法翻译 | 机械转换、语义判断、行为验证是三件事；少了验证就是批量生产新屎山 |

## 为什么屎山动不了

Michael Feathers 在《Working Effectively with Legacy Code》里给了一个反直觉定义：**遗留代码就是没有测试的代码**。技术旧、代码丑都只是表象；决定性是**没有行为快照**——没有快照，任何改动都可能悄悄改变系统行为，改对改错全凭运气。

帮凶还有三个：

- 作者离职，没人知道某个分支为什么这么写；
- 文档停留在三个大版本之前；
- 模块互相纠缠，改一处崩一片。

于是团队形成共识：别碰，能跑就行。屎山因此越长越大。

AI 时代给这个循环加了一台鼓风机：生成速度远快于人理解速度，一夜之间堆出的模块没有测试就进主干。但天平另一端也在动：**AI 是最有耐心的读者**，800 行的方法、switch 嵌 switch，人绕着走，Agent 读十遍都一样。理解的人力瓶颈下降，维护屎山从纯苦力活变成有方法论的工程。

## 第一步：先织安全网

**没有安全网，不动手**。安全网是**特征测试（characterization test）**，也叫黄金快照（golden master）：

```text
先不评判对错，把系统现状原样冻住：
输入 X → 输出 Y，全部记录。
之后任何改动跑一遍快照，行为变了就报警。
```

它和 TDD 的方向相反：TDD 先写测试定义「期望行为」；特征测试把「既有行为」原样冻结，哪怕它本身是错的。AI 时代关于 TDD 的争论不影响它——**冻结现状**恰恰是 AI 最擅长的活：读代码推出行为、批量生成快照，人只抽查关键几份。

测试之后要装**棘轮（ratchet）**：质量基线只许升，不许降。覆盖率和规则只进不退。公开案例里，GStack / GBrain 约 97 万行代码、665 个测试文件、90% 覆盖率，靠 Agent 写代码时顺手写测试做到；每个 Agent 踩过的坑变成一条永久规则。数字是作者披露的口径，不是独立审计，但方向可复现：**补测试不追求一次到位，它给之后所有改动上保险**。

## 第二步：画地图，读懂没人懂的代码

屎山最大的未知数是「它现在到底做了什么」。文档早过期，唯一事实来源是代码本身。上一章的方法在这里直接复用：

| 工具 | 回答什么 | 产物 |
|---|---|---|
| [81.6 `/teach`](../../组织/81-技术文化与知识管理/81.6-用Agent学习陌生代码库.md) | 这个系统怎么运作、为什么这么设计 | 有状态课程 + 学习记录 |
| `/understand` | 这段改动为什么存在 | 逐段卡片 + 行号锚点 |
| `/insight-diagram` | 系统长什么样、一次请求怎么走 | architecture + sequence + flowchart |
| 知识图谱 / UML | 调用关系、类型结构 | 可查询/可画的图 |

读屎山时，提问方式要换成考古式：**这段逻辑是在防什么？** 每一个怪分支背后，通常都有一个没人记得的坑。

## 第三步：三种小步走法

| 走法 | 做法 | 适合 | 风险 |
|---|---|---|---|
| **长芽法（sprout）** | 新逻辑写成独立方法/类，长在旧代码外面，只在接缝处嫁接；旧代码一行不动 | 往屎山里加小功能 | 低；注意别让新芽反向依赖旧全局 |
| **绞杀者（strangler）** | 沿旧系统边缘盖新系统，新功能只写新系统，旧功能按块搬迁，门面衔接，搬完拆旧壳 | 服务级、可切流量 | 中；双写/双读一致性、回滚 |
| **棘轮（ratchet）** | 覆盖率和规则只进不退，每次改动只许变好 | 所有渐进改造 | 低；需要基线，别用覆盖率自欺 |

具体动刀时，用 [58.7 重构三式](58.7-重构三式.md) 的排序与协作方法，加 [51.6 AI 代码审查](../51-版本与协作/51.6-AI代码审查.md) 的范围控制：**每次只改一个可验证的行为，diff 不扩大，改完就跑快照**。

## 大规模现代化：确定性工具 + LLM + 测试

单个屎山靠流程，几千个屎山要靠工厂。公开案例：

- **Amazon Q Developer**：亚马逊内部 3 万个生产应用从 Java 8/11 升到 17，披露节省超过 4500 个开发人年、每年 2.6 亿美元（2024 Q2 财报电话会口径）；
- **IBM watsonx Code Assistant for Z**：把 COBOL 服务翻译成 Java，让主机工程师带着 AI 迁移；
- **OpenRewrite**：把重构写成 AST 级 recipe，一次跑遍成千上万个仓库，Spring/Quarkus 升级有官方配方；
- **codemod**：把迁移做成可分享 CLI，内置 ast-grep。

共同规律只有一句：**机械转换交给确定性工具，语义判断交给 LLM，验证交给测试**。三者缺一，翻新工厂就会批量生产新屎山。

> ⚠️ 厂商数字是公开披露/财报口径，不是独立复现；用它们判断方向，不要直接当自己项目的 ROI。

## 重写还是重构：先挖规格，再决定

Joel Spolsky 2000 年那篇《Things You Should Never Do》反对 Netscape 从零重写浏览器：旧代码里沉淀着无数次事故换来的修复，重写等于把遗产清零。AI 时代重写成本降了一个量级，但**领域知识埋在旧代码里**这一点没变。

AI 给出的新解法是**先挖后写**：

```text
让 Agent 读透旧代码
  → 把行为抽成特征测试
  → 把规则抽成文档 / 规格
  → 规格能完整复述
  → 再决定重构还是重写
```

判断依据从「感觉写不动了」变成「规格是否已经能完整复述」：

| 现状 | 选择 |
|---|---|
| 行为有测试兜底 | 渐进重构（长芽/绞杀者/棘轮） |
| 行为说不清、测试织不起来 | 先补测试，再动手 |
| 新旧技术栈完全不兼容、代码量级可控、规格已完整 | 带着规格重写 |
| 没测试、没规格、没人懂 | **先别重写**；先织网、画地图 |

## 落地清单

- [ ] 选 3 条最关键业务路径，先写特征测试（不是全量覆盖）；
- [ ] 建立覆盖/规则基线，装棘轮，只许升不许降；
- [ ] 用 `/teach` 立 mission，用 `/understand` 逐段理解关键改动；
- [ ] 用三张骨架图建立全局，图与代码同 PR；
- [ ] 选一个接缝做长芽或绞杀，限定 diff 与回滚方案；
- [ ] 每次改动跑快照；行为变化必须能解释；
- [ ] 重写前先产出可复述的规格；规格不完整就不重写。

## 反模式

| 反模式 | 后果 |
|---|---|
| 没测试就大改 | 行为漂移无法发现，改对改错靠运气 |
| 先重写再补测试 | 旧代码里的领域知识被清零，新系统重复踩坑 |
| 用覆盖率凑数 | 跑过不等于断言了正确行为 |
| 让 AI 一次重写整个模块 | 范围失控、review 不动、回滚不了 |
| 绞杀者没有双写/回滚设计 | 新旧系统数据不一致，切流变事故 |
| 只做语法翻译，不做语义验证 | 批量生产「能编译的新屎山」 |
| 图与代码分两个 PR | 图过期，没人再信 |
| 把厂商 ROI 当自己的 ROI | 预算与周期判断失真 |

## 自检

**Q1** 为什么说「遗留代码就是没有测试的代码」？技术旧、代码丑为什么不是决定性的？

▸ 答案：技术旧和代码丑只是表象；真正决定「敢不敢改」的是有没有行为快照。没有快照，任何改动都可能悄悄改变行为，改对改错无法验证，团队只能选择不碰。只要行为能被特征测试冻住，丑代码也可以安全地渐进改造。

**Q2** 特征测试和 TDD 的区别是什么？为什么 AI 更适合批量写特征测试？

▸ 答案：TDD 先写测试定义期望行为；特征测试把既有行为原样冻结，哪怕它是错的。AI 擅长读代码推出行为、批量生成快照，人只抽查关键几份；这正好匹配「先织网」的需求，不需要先判断业务对错。

**Q3** 长芽法、绞杀者、棘轮分别解决什么问题？

▸ 答案：长芽法解决「往旧代码里加新功能」——新逻辑独立生长，只在接缝嫁接，旧代码不动；绞杀者解决「服务级替换」——新系统沿边缘生长，按块搬功能，门面衔接，搬完拆旧；棘轮解决「节奏」——覆盖率和规则只升不降，保证每次改动只许变好。

**Q4** 大规模现代化为什么不能只用 LLM？

▸ 答案：LLM 擅长语义判断，但机械转换需要确定性（AST recipe 可重复、可审计），行为验证需要测试。正确分工是：确定性工具做机械转换，LLM 做语义判断与迁移计划，测试做行为验证；缺一就会批量生产新屎山。

**Q5** 「先挖后写」具体挖什么？挖到什么程度才可以重写？

▸ 答案：挖三样：行为（特征测试）、规则（文档/规格）、边界（接口与依赖）。挖到「规格能完整复述旧系统行为」才算够；此前重写是赌博，此后重写才是工程。判断依据不是「感觉写不动了」，而是规格完整性。

**Q6** 如果团队只能先做一件事，应该做什么？

▸ 答案：选 3 条最关键业务路径写特征测试，并建立覆盖/规则基线装棘轮。没有行为快照，读代码、画图、重构、重写都没有安全网；先有网，后面的工具才有意义。
