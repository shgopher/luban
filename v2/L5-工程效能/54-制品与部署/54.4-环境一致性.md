# 54.4 环境一致性

## 一句话

> 环境一致性不是“配置抄得一样”，而是**同一个制品 + 同一份编排定义 + 只有白名单内的参数不同**；无法枚举的差异，就是下一次“测试环境好的、生产挂了”。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “测试通过，生产就没问题” | 差异至少五条轴：制品、编排、配置、依赖、数据。任意一条都能单独制造事故，且往往只在生产规模下暴露 |
| “环境不一致是因为机器不同” | 机器可以同规格；中间件大版本、schema 版本、网络策略、权限模型照样不同 |
| “一致性 = 完全一样” | 生产规模必然是 staging 的 N 倍。要一致的是**结构**（拓扑、版本、契约），不是容量 |
| “复制一份生产数据最真实” | 合规与泄露风险先不论，数据量本身也拖慢环境。正确做法是**脱敏子集 + 同 schema** |

## 五个差异轴

| 轴 | 必须一致 | 允许不同 | 检查方式 |
|---|---|---|---|
| 制品 | digest | 无 | 部署清单比对（见 [54.1 不可变制品](54.1-不可变制品.md)） |
| 编排 | base 模板、探针、资源请求、网络策略 | 副本数、资源量、节点池 | `kustomize build` 后 diff（见 [54.3 部署编排](54.3-部署编排.md)） |
| 配置 | key 集合、类型、默认值 | 白名单内的值 | schema 校验 + 生效配置 diff（见 [54.5 配置注入](54.5-配置注入.md)） |
| 依赖 | 中间件大版本、拓扑、认证方式 | 容量、实例数 | 版本清单 + 连接串检查 |
| 数据 | schema 版本、约束、索引 | 行数、内容、脱敏程度 | migration 版本 + 脱敏子集 |

> 🔑 一致性的最小判据：**制品 digest 相同、schema 版本相同、其余差异能逐条列在白名单里**。列不出来的差异，就是下一次事故的候选。

多环境怎么隔离（账号、VPC、数据边界）是另一层问题，见 14.1 多环境隔离（待补）；这一节只管“结构是否等价”。

## 最小等价集：staging 凭什么叫 staging

| 项 | 必须一致 | 可以不一致 |
|---|---|---|
| 中间件大版本 | 是（Redis 7 / MySQL 8） | 小版本最多差 1 个 patch，且要记录 |
| schema 版本 | 是（migration 版本号相同） | 数据量、索引统计信息 |
| 网络路径 | 是（同网关、同 mTLS、同鉴权链路） | 带宽、副本数 |
| 部署方式 | 是（同 chart / 同 base） | 资源配额 |
| 第三方 | 沙箱 vs 生产端点可不同 | 账号、密钥、限额 |
| 数据 | 同 schema、同约束 | 行数、内容（必须脱敏） |

**规模差异不能靠“环境”补**：容量、排队、热点、长尾这些只在规模上暴露的问题，staging 永远测不出。它们要靠压测与容量模型（[34.5 性能测试与负载模型](../../L3-质量属性/34-性能/34.5-性能测试与负载模型.md)、[57.2 容量模型](../57-容量与成本治理/57.2-容量模型.md)），而不是把 staging 扩到和生产一样大。

## 漂移从哪来

| 来源 | 症状 | 消除手段 |
|---|---|---|
| 手工 SSH 热修 | 重启后问题复现/消失；“只有这台机器能跑” | 禁止手改；紧急修改必须回写 IaC 并限期 |
| 手工装依赖 | 新节点起不来，旧节点还活着 | 依赖进镜像（见 [54.1 不可变制品](54.1-不可变制品.md)） |
| 配置复制粘贴 | 少一个 key，静默走默认值 | key 集合校验 + 启动时打印生效配置 |
| 数据没迁移 | 新代码读旧表，报“列不存在” | Expand-Contract（[55.4 数据库变更管理 (Expand-Contract)](../55-发布与回滚/55.4-数据库变更管理.md)） |
| 依赖版本漂移 | staging Redis 7.0、prod 7.2 | 版本清单纳入部署与检查 |
| 云资源手点 | 安全组多开一个口、LB 超时不同 | IaC + 漂移检测（14.3 配置管理与漂移检测（待补）） |

## 数字：手工步骤的复利

假设每次发布 20 个手工步骤，每步 1% 的失误率（漏一步、填错一个值）：

| 环境数 | 手工动作 | 整体成功率 | 至少错一步的概率 |
|---|---|---|---|
| 1 | 20 | `0.99^20 ≈ 81.8%` | **18.2%** |
| 4 | 80 | `0.99^80 ≈ 44.8%` | **55.2%** |

这是算术示例，不是实测；结论与参数无关：**步骤越多、环境越多，靠“小心一点”就越不可能一致**。一致性要靠“把步骤变成声明 + 检查”，不是靠流程纪律。

## 一个能跑的漂移检查器

检查器只做一件事：把两个环境的结构化快照对比，按“致命 / 警告”分级，致命则退出码 1，直接卡住发布。

```go
package main

import (
	"fmt"
	"os"
	"sort"
	"strings"
)

type snapshot struct {
	artifact string
	chart    string
	schema   int
	config   map[string]string
	deps     map[string]string
}

// 只允许这些 key 的值在不同环境间不同；其余必须一致。
// 地址类天然按环境不同，容量/日志级别属于“允许的规模差异”。
func allowValueDiff(k string) bool {
	return k == "db.pool" || k == "log.level" ||
		strings.HasSuffix(k, ".host") || strings.HasSuffix(k, ".addr")
}

type finding struct {
	level, item, detail string
}

func major(v string) string {
	if i := strings.Index(v, "."); i > 0 {
		return v[:i]
	}
	return v
}

func diff(staging, prod snapshot) []finding {
	var fs []finding
	add := func(level, item, detail string) {
		fs = append(fs, finding{level, item, detail})
	}

	if staging.artifact != prod.artifact {
		add("FATAL", "artifact", fmt.Sprintf("staging=%s prod=%s（不是同一份字节）", short(staging.artifact), short(prod.artifact)))
	}
	if staging.schema != prod.schema {
		add("FATAL", "schema", fmt.Sprintf("staging=%d prod=%d（迁移版本不同）", staging.schema, prod.schema))
	}
	if staging.chart != prod.chart {
		add("WARN", "chart", fmt.Sprintf("staging=%s prod=%s（编排模板不同）", staging.chart, prod.chart))
	}
	for _, k := range unionKeys(staging.deps, prod.deps) {
		sv, sok := staging.deps[k]
		pv, pok := prod.deps[k]
		switch {
		case !sok || !pok:
			add("FATAL", "dep."+k, "只在一个环境里声明")
		case major(sv) != major(pv):
			add("FATAL", "dep."+k, fmt.Sprintf("staging=%s prod=%s（大版本不同）", sv, pv))
		case sv != pv:
			add("WARN", "dep."+k, fmt.Sprintf("staging=%s prod=%s（小版本不同）", sv, pv))
		}
	}
	for _, k := range unionKeys(staging.config, prod.config) {
		sv, sok := staging.config[k]
		pv, pok := prod.config[k]
		switch {
		case !sok:
			add("WARN", "config."+k, "staging 缺失，将走默认值："+pv)
		case !pok:
			add("WARN", "config."+k, "只在 staging 存在："+sv)
		case sv != pv && !allowValueDiff(k):
			add("WARN", "config."+k, fmt.Sprintf("staging=%s prod=%s（不在允许差异白名单）", sv, pv))
		}
	}
	return fs
}

func short(d string) string {
	if len(d) > 14 {
		return d[:14]
	}
	return d
}

func unionKeys(a, b map[string]string) []string {
	set := map[string]bool{}
	for k := range a {
		set[k] = true
	}
	for k := range b {
		set[k] = true
	}
	out := make([]string, 0, len(set))
	for k := range set {
		out = append(out, k)
	}
	sort.Strings(out)
	return out
}

func main() {
	prod := snapshot{
		artifact: "sha256:9f1c2ab77d0011223344", chart: "order-1.4.0", schema: 42,
		config: map[string]string{"db.host": "db.prod", "db.pool": "50", "log.level": "info", "timeout": "3s", "redis.addr": "redis.prod:6379"},
		deps:   map[string]string{"redis": "7.2.4", "mysql": "8.0.36"},
	}
	staging := snapshot{
		artifact: "sha256:4ae90c1d77cc99887766", chart: "order-1.4.0", schema: 41,
		config: map[string]string{"db.host": "db.staging", "db.pool": "20", "log.level": "debug", "redis.addr": "redis.staging:6379", "debug.profiling": "on"},
		deps:   map[string]string{"redis": "7.0.15", "mysql": "8.0.36"},
	}

	fs := diff(staging, prod)
	fmt.Println("环境一致性检查：staging vs prod（基准 prod）")
	fmt.Printf("%-6s %-24s %s\n", "LEVEL", "CHECK", "DETAIL")
	fatal, warn := 0, 0
	for _, f := range fs {
		fmt.Printf("%-6s %-24s %s\n", f.level, f.item, f.detail)
		if f.level == "FATAL" {
			fatal++
		} else {
			warn++
		}
	}
	checks := 3 + len(unionKeys(staging.deps, prod.deps)) + len(unionKeys(staging.config, prod.config))
	fmt.Printf("\n合计：%d 项检查，FATAL %d，WARN %d\n", checks, fatal, warn)
	if fatal > 0 {
		fmt.Println("结论：不一致，禁止发布；先对齐 artifact 与 schema")
		os.Exit(1)
	}
	fmt.Println("结论：结构一致，允许发布")
}
```

本机运行结果（退出码 1）：

```console
环境一致性检查：staging vs prod（基准 prod）
LEVEL  CHECK                    DETAIL
FATAL  artifact                 staging=sha256:4ae90c1 prod=sha256:9f1c2ab（不是同一份字节）
FATAL  schema                   staging=41 prod=42（迁移版本不同）
WARN   dep.redis                staging=7.0.15 prod=7.2.4（小版本不同）
WARN   config.debug.profiling   只在 staging 存在：on
WARN   config.timeout           staging 缺失，将走默认值：3s

合计：11 项检查，FATAL 2，WARN 3
结论：不一致，禁止发布；先对齐 artifact 与 schema
```

注意两点：

1. **`db.pool=20 vs 50`、`log.level=debug vs info`、地址不同，都没有报**——它们在白名单内，属于“允许的规模差异”。一致性检查必须允许合理的不同，否则会被当成噪音关掉。
2. **`timeout` 缺失是最隐蔽的一条**：它不会报错，只会静默用默认值（这里是 3s）。测试环境看起来正常，生产可能因为默认值不同而超时。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：清单差异用 **Kustomize**（base + overlay）控制，基础设施用 **Terraform**（或云厂商等价物），CI 里跑一致性门禁（本节程序或等价脚本）。替代：Helm 的 values per env 也能做到，但“哪些 key 允许不同”更需要显式白名单。

**可抄**（本机未安装 kustomize / yq / terraform，以下命令**未验证**）：

```bash
# 1) 两个环境的清单：结构 diff 应该是“只有白名单字段不同”
kustomize build overlays/staging > /tmp/staging.yaml
kustomize build overlays/prod    > /tmp/prod.yaml
diff <(yq '.. | select(has("image")) | .image' /tmp/staging.yaml | sort -u) \
     <(yq '.. | select(has("image")) | .image' /tmp/prod.yaml    | sort -u)
# 预期：无输出（digest 相同）；有输出就是制品不一致

# 2) 基础设施漂移：靠 exit code 判断
terraform plan -detailed-exitcode -out=tfplan
echo "exit=$?"     # 0=无变化  2=有漂移  1=出错
```

**可验**：本节 Go 程序**真跑过**，输出与退出码如上，把上面的程序存成 `check_env.go` 放进 CI：`go run check_env.go || exit 1`，不一致就直接卡住发布。基础设施侧至少要验证一次 `terraform plan -detailed-exitcode` 在“手点一个安全组”后返回 2——这条本机无 terraform，未验证。

**可退**：

- 门禁先以“报告”模式跑两周，确认白名单不会误杀，再切“阻断”。
- 发现漂移：先 `diff` 定位，能重建的就用 IaC 重建（不要手工改回去）；有状态资源要人工确认。
- 回滚：重新 apply 上一版 overlay / 上一版 Terraform state 对应的配置；保留“上次一致”的快照用于对比。

## 反模式

| 反模式 | 后果 |
|---|---|
| 手工 SSH 改配置“先救火” | 雪花服务器；下次部署被覆盖，问题复现 |
| staging 直连生产库（只读也不行） | 一次误写就是生产事故，且违反合规 |
| 只对齐镜像、不对齐 schema | 新代码读旧表，报列不存在；回滚时旧代码读新表也可能挂 |
| 用“同一个 commit”证明一致 | 构建环境不同，字节可能不同（见 [54.1 不可变制品](54.1-不可变制品.md)） |
| 每个环境各写一份完整 YAML | 三份漂移，没人知道哪份是标准 |
| 用生产数据全量复制到测试 | 泄露 + 合规风险；数据量大时环境不可用 |
| 差异没有白名单，靠人记 | 评审靠猜，检查器被噪音淹没后关掉 |
| 把 staging 当“缩小版生产”却不测容量 | 容量/热点类问题只在生产爆发（见 [57.2 容量模型](../57-容量与成本治理/57.2-容量模型.md)） |

## 自检

**Q1** 测试环境全绿、生产 5xx，最先查哪五条轴？

▸ 答案：按“最近变更”排序查：① 制品 digest 是否与测试时一致；② 编排（探针、资源、网络策略、副本数）是否同 base；③ 配置 key 与值（尤其是缺失后走默认值的项）；④ 依赖（中间件大版本、连接串、认证方式）；⑤ 数据（schema 版本、数据形状、脱敏方式）。不要先怀疑“代码逻辑”——代码在两个环境是同一份，差异在环境。

**Q2** 为什么“同一个 commit 构建”不能证明环境一致？

▸ 答案：commit 只标识源码。构建环境（工具链版本、构建目录、依赖解析、参数）会改变产物字节，本机实测同源码换目录构建 sha256 就不同（见 [54.1 不可变制品](54.1-不可变制品.md)）。一致性要拿 digest 证明，不是拿 commit 证明。

**Q3** staging 规模只有生产 1/10，哪些问题它永远测不出？

▸ 答案：所有随规模非线性变化的问题——连接池/队列排队、缓存命中率、热点 key、长尾延迟、批量任务的 GC 与内存峰值、下游限流阈值。这些要靠压测与容量模型（[34.5 性能测试与负载模型](../../L3-质量属性/34-性能/34.5-性能测试与负载模型.md)、[57.2 容量模型](../57-容量与成本治理/57.2-容量模型.md)），不能指望 staging。

**Q4** 每次发布 20 个手工步骤、每步 1% 失误，4 个环境的整体一致性概率是多少？

▸ 答案：`0.99^(20×4) = 0.99^80 ≈ 44.8%`，也就是**超过一半的概率至少错一步**。这不是“人不小心”，是步骤数与环境数乘出来的。解法只有两个方向：减少步骤（声明式、自动化）、增加检查（一致性门禁），而不是加强培训。

**Q5** 漂移检测应该自动修复吗？

▸ 答案：默认**先报告、不自动改**。无状态、可重建的资源（副本数、镜像、探针）可以自动收敛；有状态/数据类资源（存储、网络、数据库参数）自动改可能扩大事故。自动修复的前提是：IaC 覆盖完整、变更可回滚、修复动作有审计。否则“自动修漂移”只是把人为错误变成系统性的。
