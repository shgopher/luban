# 0.1 复杂度分析：把 “快慢” 变成可谈判的数

## 一句话

> 大 O 只回答 “n 翻 10 倍、工作量翻几倍”，不回答 “这个接口几毫秒”；能拿去评审的只有三个数——**这个 n 下的绝对值、均摊还是最坏、P99 而不是均值**，三缺一，复杂度就只是背诵。

## O(n²) 的 5 万倍差距，全在次数，不在单价

同一台机器、同一份数据、同一个循环体风格，把 O(n) 累加和 O(n²) 两两比较各跑 3 次取最小（`/tmp/luban-a/b01`，go1.27.1 darwin/arm64，Apple M1）：

| n | O(n) 累加 | O(n²) 两两比较 | 平方/线性 | 线性增长 | 平方增长 |
|---|---|---|---|---|---|
| 1 000 | 375 ns | 177 084 ns | 472× | — | — |
| 10 000 | 3 375 ns | 16 793 958 ns | 4 976× | 9.0× | 94.8× |
| 100 000 | 32 291 ns | 1 659 263 625 ns | 51 385× | 9.6× | 98.8× |

n=1e5 时要 1.66 秒。只是 8 字节 int 的两两比较，没有任何 IO、没有分配。

把这张表换算成单价：

- 线性：375 ns / 1 000 个元素 = **0.38 ns/元素**
- 平方：177 084 ns / 499 500 对 = **0.35 ns/对**

一次元素访问和一次两两比较，单价都是 0.35–0.38 ns。**5 万倍差距 100% 来自次数，不来自 “平方的代码更慢”。**

> 🔑 复杂度只数次数，单价由硬件决定。所以 “把 O(n²) 改成 O(n log n)” 的收益也是次数级的；想再快，只能动单价（缓存、批处理、预取），那是另一类优化。

“增长” 两列是相对上一档的倍数：n 涨 10 倍，线性涨 9.0–9.6 倍，平方涨 94.8–98.8 倍。**实测永远不是整数倍**——线性那 9.0 倍里，缺的 1 倍是 n 变大后缓存开始失效；平方那 94.8 倍里，少的 5 倍是循环次数固定但分支预测更准。按 110% 留余量，别按公式留。

## 常数项：出了缓存，单价按量级跳

复杂度公式里没有 “一次访问多少钱”，但硬件有：

| 访问目标 | 延迟量级 | 本机是否实测 |
|---|---|---|
| L1/L2、顺序读 int64 | ~1 ns | ✅ 0.52 ns/元素（64 MB 数组顺序求和） |
| 主存随机读 | ~100 ns | ⚠️ 量级；本机独立随机读吞吐 4.1 ns/次（乱序执行把延迟重叠了） |
| NVMe SSD 随机读 4 KB | ~100 µs | ❌ 只用量级 |
| 同机房网络 RTT | ~0.5 ms | ❌ 只用量级 |
| 机械盘寻道 | ~10 ms | ❌ 只用量级 |

第二行 4.1 ns 值得单独说：1e6 次独立随机读只花 4.1 ms，是顺序读（0.52 ns/元素）的 8 倍。**不是主存变快了，是这些读互不依赖，CPU 能把几十个未完成的读叠在一起。** 一旦变成依赖链（链表 `p = p.next`、递归指针），后一次读要等前一次结果，延迟就还原成 ~100 ns 量级。

> 🔑 批量/并发的随机读 ≈ 顺序读的 8 倍；串行的依赖读 ≈ 顺序读的 200 倍（量级推算）。**“随机访问慢” 这句话只在有依赖时成立**——这就是为什么并发查库、批量取数能把性能拉回来，而链表遍历不能。

这条结论直接决定两件事：一次查 100 个 key，应该并发或流水线；遍历一个链表，没有救。

## 均摊：append 均摊 3.5 ns，最坏一次 0.65 ms

slice 的 append 是 “均摊 O(1)” 的教科书例子：扩容时翻倍，n 次 append 总共复制 O(n) 个元素。

实测 cap 跳变（n=1200，取前 8 次与最后 2 次）：

| 第几次扩容 | 触发时 len | cap 旧 → 新 | 倍数 |
|---|---|---|---|
| 1 | 0 | 0 → 4 | 首次分配 |
| 2 | 4 | 4 → 8 | 2.00× |
| 7 | 128 | 128 → 256 | 2.00× |
| 8 | 256 | 256 → 512 | 2.00× |
| 9 | 512 | 512 → 848 | 1.66× |
| 10 | 848 | 848 → 1280 | 1.51× |

cap 到 512 之前每次翻倍，之后增长因子降到约 1.25（512→848→1280，含分配器 size class 取整，所以看到的是 1.66 与 1.51，不是 1.25）。翻倍对时间友好、对内存不友好：1e6 元素时瞬间要 2 倍空间。运行时用 “小步增长 + 多复制几次” 换 “少浪费内存”。

累计复制量（同一程序）：**n=1e6 时每个元素平均被复制 4.15 次，最终 cap=1 055 744**。4.15 是常数，所以仍是均摊 O(1)。

单次最坏：把 slice 填到 `len == cap`，再 append 一个元素，触发一次真实扩容——

```text
第 1 次：扩容耗时 0.671 ms（拷 1055744 个元素 = 8.4 MB），新 cap=1319936
第 2 次：扩容耗时 0.684 ms
第 3 次：扩容耗时 0.557 ms
```

对比均摊值：1e6 次 append 用 3.48 ms，即 **3.5 ns/次**；扩容那一次 **0.65 ms**，差 **18 万倍**。

> 🔑 均摊成本用来算容量，最坏成本用来定超时。**把 3.5 ns 写进 SLO，P99 就会在某次扩容上开一个 0.65 ms 的洞**——415 万次元素复制摊进 100 万次调用，均值里看不见，那个刚好撞上的请求看得见。

## 预分配：append 快 4.9 倍，map 只快 1.78 倍

benchmark（1e6 元素，`-benchmem`，3 次取中位）：

| 操作 | ns/op | 分配字节/op | 分配次数/op | 相对不预分配 |
|---|---|---|---|---|
| append 不预分配 | 3 477 191（3.48 ms） | 41.7 MB | 38 | 1.0× |
| append 预分配 `make([]int, 0, n)` | 709 338（0.71 ms） | 8.0 MB | 1 | **4.9× 快，5.2× 省内存** |
| map 不预分配 | 64 357 525（64.4 ms） | 75.6 MB | 8 210 | 1.0× |
| map 预分配 `make(map[int]int, n)` | 36 190 708（36.2 ms） | 37.8 MB | 4 098 | **1.78× 快，2.0× 省内存** |

差别在机制，不在 “预分配” 三个字：

- **slice**：不预分配要复制 415 万个元素（4.15 次/元素）+ 37 次数组分配。预分配把这两项一起清零，所以是 4.9 倍。
- **map**：grow 是**渐进式搬桶**——翻倍时不是一次性拷完，而是每次写操作顺带搬一两个桶。复制成本本来就被摊进后续写入了，预分配省下的是桶分配次数（8 210 → 4 098）与峰值内存。

> 🔑 同样叫 “预分配”，slice 省的是**复制**，map 省的是**桶分配与迁移**。别指望 `make(map, n)` 有 slice 那样的加速比，也别因为没有 4.9 倍就说 map 预分配没用。

## 均值 vs P99：两个不同的问题

一次 200 ms 的超时，在 1 万次请求的均值里只占 0.02 ms，用户感受到的却是那一次。

| 成本来源 | 平均表现 | 尾部表现 | 复杂度公式里有吗 |
|---|---|---|---|
| slice 扩容 | 3.5 ns/次 | 单次 0.65 ms | ❌ 只写 O(1) |
| map grow | 36 ns/次 | 迁移窗口内写入变慢 | ❌ 只写 O(1) |
| GC | 与分配字节数成正比 | 标记辅助触发尖刺 | ❌ |
| 缓存未命中/回源 | 命中率平均值 | 一次回源 100 µs 量级 | ❌ |
| 排队 | 利用率 50% 时几乎不排队 | 利用率 90% 时等待 ×10（推导） | ❌ |

最后一行是推导不是实测：M/M/1 的等待时间 `W = Ws / (1-ρ)`，ρ=0.8 → 5 倍，ρ=0.9 → 10 倍，ρ=0.95 → 20 倍。**同一份代码，利用率从 80% 抬到 90%，等待时间直接翻倍**——这跟算法无关。

P99 与 P999 的取舍见 [34.1 性能指标 (延迟 / 吞吐 / P99)](../../L3-质量属性/34-性能/34.1-性能指标.md)；利用率和等待时间的换算见 [34.2 性能建模 (利特尔法则、排队论)](../../L3-质量属性/34-性能/34.2-性能建模.md)。

> 🔑 用均值做容量规划，利用率过了 70% 就会系统性低估延迟；用 P99 做容量规划，才知道还剩多少余量可卖。

## 空间换时间：先换算成 “核”，再决定

| 手段 | 额外空间 | 换来的时间 | 什么时候划算 |
|---|---|---|---|
| 位图（存在性） | 1 bit/元素：1e6 元素 = 125 KB | 判存在从查表 100 ns 量级到 1 ns 量级 | 编号连续、只判存在 |
| 内存哈希索引 | 30.3 B/条：1e7 条 = 303 MB（实测） | 全扫 3.91 ms → 13 ns（实测） | 读远多于写、key 集合稳定 |
| 预聚合 / 物化视图 | 与维度基数成正比 | 聚合从扫 1e7 行到读 1 行 | 查询形状固定 |
| 多级缓存 | 只存热数据 | 一次回源 100 µs 量级 → 内存 100 ns 量级 | 读多写少、能容忍不一致 |

账要这样算，两个例子都用上面的实测数：

```text
方案 A：把全表扫描换成索引
  每次省 3.91 ms；QPS 1e4 → 1e4 × 3.91e-3 s = 39 核

方案 B：把二分换成哈希
  每次省 117 ns（130 → 13 ns）；QPS 1e4 → 1e4 × 1.17e-7 s ≈ 0.0012 核
```

两个都叫 “加索引”，差 3 万倍。**索引的价值是 “把扫描换成定位”，不是 “把 log n 换成 1”。** 一次查询本来只有 24 次比较时，省下那 24 次在核数上几乎不可见；只有当它顶着全表扫描或一次磁盘 IO，索引才值钱。

> 🔑 判据：`QPS × 每次省下的秒数` 换算成核，再和内存的价格比。省不出 0.01 核的优化，不值得占 300 MB。

## 可运行代码与真实输出

环境：go1.27.1 darwin/arm64，Apple M1，macOS。代码放 `/tmp/luban-a/b01`（不在书稿仓库里留 `.go`）。

```go
package main

import (
	"fmt"
	"time"
)

// linear 是 O(n)：每个元素只读一次后累加。
func linear(a []int) int64 {
	var s int64
	for _, v := range a {
		s += int64(v)
	}
	return s
}

// quadratic 是 O(n²)：两两比较，比较次数固定为 n(n-1)/2。
// 这里不用排序来对比，因为排序是 O(n log n)，看不出平方的增长曲线。
func quadratic(a []int) int64 {
	var c int64
	for i := 0; i < len(a); i++ {
		ai := a[i] // 提到内层循环外：让比较发生在寄存器里，不重复读内存
		for j := i + 1; j < len(a); j++ {
			if ai < a[j] {
				c++
			}
		}
	}
	return c
}

func build(n int) []int {
	a := make([]int, n)
	for i := range a {
		a[i] = (i * 2654435761) & 0xffff
	}
	return a
}

// capJumps 返回每次扩容的 (触发时的 len, 旧 cap, 新 cap)。
func capJumps(n int) [][3]int {
	var s []int
	var out [][3]int
	for i := 0; i < n; i++ {
		if len(s) == cap(s) {
			old := cap(s)
			s = append(s, i)
			out = append(out, [3]int{old, old, cap(s)})
			continue
		}
		s = append(s, i)
	}
	return out
}

// copyCost 统计「不预分配」追加 n 个元素时，总共有多少个元素被复制过。
// 触发扩容时，运行时会把旧数组里的 len 个元素逐个搬到新数组。
func copyCost(n int) (copied int64, finalCap int) {
	var s []int
	for i := 0; i < n; i++ {
		if len(s) == cap(s) {
			copied += int64(len(s))
		}
		s = append(s, i)
	}
	return copied, cap(s)
}

// minOf 跑 f 三次取最小值：第一次带冷缓存与初始化开销，不能直接当结果。
func minOf(f func()) time.Duration {
	best := time.Duration(1 << 62)
	for i := 0; i < 3; i++ {
		t0 := time.Now()
		f()
		if d := time.Since(t0); d < best {
			best = d
		}
	}
	return best
}

func main() {
	_ = linear(build(1000)) // 预热：让 heap、栈、代码页先热起来
	fmt.Println("go1.27.1 darwin/arm64")
	fmt.Println()
	fmt.Println("== ① O(n) vs O(n²)：同机、同数据、各跑 3 次取最小 ==")
	fmt.Printf("%8s %12s %15s %8s %9s %9s\n",
		"n", "linear_ns", "quadratic_ns", "q/l", "线性增长", "平方增长")
	var prevL, prevQ float64
	for _, n := range []int{1000, 10000, 100000} {
		a := build(n)
		tl := float64(minOf(func() { linear(a) }).Nanoseconds())
		tq := float64(minOf(func() { quadratic(a) }).Nanoseconds())
		gl, gq := "-", "-"
		if prevL > 0 {
			gl = fmt.Sprintf("%.1fx", tl/prevL)
			gq = fmt.Sprintf("%.1fx", tq/prevQ)
		}
		fmt.Printf("%8d %12.0f %15.0f %8.0f %9s %9s\n", n, tl, tq, tq/tl, gl, gq)
		prevL, prevQ = tl, tq
	}

	fmt.Println()
	fmt.Println("== ② append 扩容：n=1200 时的 cap 跳变 ==")
	for i, p := range capJumps(1200) {
		factor := "首次分配"
		if p[1] > 0 {
			factor = fmt.Sprintf("%.2f 倍", float64(p[2])/float64(p[1]))
		}
		fmt.Printf("第 %2d 次扩容：len=%-4d cap %4d → %-5d %s\n", i+1, p[0], p[1], p[2], factor)
	}

	fmt.Println()
	fmt.Println("== ③ 不预分配追加 n 个元素：累计复制量 ==")
	fmt.Printf("%10s %14s %14s %10s\n", "n", "累计复制元素", "均摊复制/元素", "最终 cap")
	for _, n := range []int{1000, 100000, 1000000} {
		copied, c := copyCost(n)
		fmt.Printf("%10d %14d %14.2f %10d\n", n, copied, float64(copied)/float64(n), c)
	}

	fmt.Println()
	fmt.Println("== ④ 均摊 vs 单次最坏：在满容量点上 append 一次 ==")
	for r := 0; r < 3; r++ {
		// len == cap，下一次 append 必须扩容：分配新数组 + 拷 1055744 个 int
		s := make([]int, 1055744)
		t0 := time.Now()
		s = append(s, 1)
		d := time.Since(t0)
		fmt.Printf("第 %d 次：扩容耗时 %.3f ms（拷 1055744 个元素 = 8.4 MB），新 cap=%d\n",
			r+1, float64(d.Nanoseconds())/1e6, cap(s))
	}

}
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 拿大 O 当性能结论：“O(log n) 一定比 O(n) 快” | n=10 时 10×0.4 ns 的线性扫赢过 24 次比较的二分，还少一个边界 bug |
| 忽略常数：把 24 次比较的二分当优化点 | 每次省 117 ns，QPS 1e4 才 0.0012 核，白改一遍 |
| 忽略 n 的真实范围：给 100 条配置上跳表 | 复杂度赢了，代码量、内存、bug 全输 |
| 拿微基准当生产结论 | 热工作集 130 ns，线上冷分布叠加 GC 是另一回事 |
| 把 O(1) 当 “快” | 哈希要算哈希、要访存：map 13 ns vs 数组下标 0.4 ns，差 30 倍 |
| 只看分配次数不看字节数 | 38 次分配 = 41.7 MB；GC 压力按字节算，不按次数算 |
| 用均摊成本给单次请求定价 | 某次扩容 0.65 ms 砸中那个用户，P99 直接超时 |
| 按 “现在的 n” 做设计 | n 一年涨 10 倍，平方项涨 100 倍，扩容计划全部作废 |
| 在利用率 85% 的机器上做压测并外推 | 排队项非线性，压测结论在 70% 以上全部失真 |

性能反模式的完整清单见 [34.6 性能反模式](../../L3-质量属性/34-性能/34.6-性能反模式.md)；把 benchmark 结论落到生产要靠采样剖析，见 [34.3 性能分析方法 (火焰图 / pprof / perf)](../../L3-质量属性/34-性能/34.3-性能分析方法.md)。

## 自检

**Q1** 一个接口里有 O(n²) 的两两比较，n 从 10 000 涨到 20 000，QPS 不变，CPU 大约怎么变？如果只有均值监控，你会漏掉什么？

▸ 答案：涨约 3.9 倍（理想是 4 倍）。本机实测 10 倍 n 是 94.8 倍，折算每次翻倍 94.8^(1/3.32) ≈ 3.94 倍——**低于 4 是因为大 n 下分支更可预测、常数项略降**，做容量规划按 4 倍算、按 110% 留余量。均值监控会漏掉两件事：平方项把 CPU 打满后**排队时间**开始非线性上涨（不是 CPU 本身），以及 GC/扩容这类尾尖刺；这两项在均值里都会被摊平，所以要同时看 P99 与利用率。

**Q2** append 均摊 3.5 ns，为什么 P99 上能看到毫秒级尖刺？要求单次 ≤1 ms 时，1e6 元素的 slice 该怎么写？

▸ 答案：均摊是 “总成本 ÷ 次数”，扩容那一次的 0.65 ms 真实发生在一个请求里（拷 1 055 744 个元素 = 8.4 MB）。要求单次 ≤1 ms 时：① 能预估就 `make([]T, 0, n)` 一次分够；② 不能预估就用分块（每块固定 4096，块指针放 slice），单次扩容只拷 4096 个元素；③ 复用 `sync.Pool` 或环形缓冲，避免每次请求都从 nil 开始长。判据不是 “均摊够快”，而是 **最坏单次 ≤ 预算**。

**Q3** 为什么 append 预分配快 4.9 倍，而 map 预分配只快 1.78 倍？两个都叫 “省掉扩容”。

▸ 答案：省的东西不同。slice 不预分配要**复制 415 万个元素**（4.15 次/元素）并做 37 次数组分配，这两笔在预分配后归零。map 的 grow 是渐进式搬桶——翻倍时每次写只搬一两个桶，复制成本早已摊进写入；预分配省的是 4 096 次桶分配和峰值内存（75.6 → 37.8 MB）。所以 **slice 的预分配是消除了一次性大拷贝，map 的预分配只是减少了分配次数**。

**Q4** 一个 1000 条数据的请求处理里，你把线性查找换成 map，P99 反而变差了。为什么？

▸ 答案：多半是**每个请求都重建了一次 map**。1e6 条插入要 36 ms，1000 条约 36 µs；而被替换掉的线性扫是 1000 × 0.4 ns = 0.4 µs——建表比扫描贵 90 倍。只有 “同一份数据被查很多次”（进程启动建一次、请求只读）时 map 才划算。判据：**建表成本 ÷ 查询次数** 要远小于单次线性扫的成本。

**Q5** “随机访问比顺序访问慢 100 倍”，为什么本机只测出 8 倍？

▸ 答案：因为那 1e6 次随机读**互不依赖**，乱序执行把几十个未完成读的延迟重叠了：单次延迟仍是 ~100 ns 量级，但吞吐只有 4.1 ns/次（顺序是 0.52 ns）。一旦有依赖（链表 `p = p.next`、递归下降、逐跳查表），重叠不成立，就还原成 200 倍量级。所以问 “随机访问慢不慢” 之前要先问：**这些访问之间有依赖吗？能不能批量或并发？**

**Q6** 团队要给一个 P99 已经 300 ms 的接口加内存索引，理由是 “能省 3.9 ms”。这个判断错在哪？

▸ 答案：3.9 ms 只占 300 ms 的 1.3%，而且加索引省的是 CPU，不是排队、不是下游等待、不是锁。先看 300 ms 花在哪：如果 P99 由 GC、锁竞争或下游 RT 造成，索引只白占 303 MB。反过来说，如果这个接口每秒有 1e4 次调用、每次都全表扫，那 3.9 ms×1e4 ≈ 39 核，加索引立刻值——**同一个动作，值不值取决于它省的是不是瓶颈**。

**Q7** 一个 n=1e5 的 O(n log n) 处理今天要 30 ms，3 年后数据涨到 1e7。按本机实测的倍增关系推算 3 年后是多少？该做什么？

▸ 答案：n 涨 100 倍，n log n 涨 100 × log₂(1e7)/log₂(1e5) = 100 × 23.3/16.6 ≈ **140 倍 → 4.2 秒**。这不是 “扩容几台机器” 能解决的（4.2 秒 × QPS 直接打满）。三条路：① 把 O(n log n) 换成 O(n)（预排序/桶/哈希）；② 把 n 降下来（分区、只算增量、按时间窗切片）；③ 把计算移出请求路径（离线预聚合）。**先算增长曲线，再决定买机器还是换算法。**
