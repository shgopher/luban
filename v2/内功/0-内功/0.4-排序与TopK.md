# 0.4 排序与 Top-K：先问 “要不要全序”

## 一句话

> 比较排序的 O(n log n) 只在「靠两两比较定序」这一条路上是硬下界；动手前先问要不要全序——只要前 k 个就上堆（1e6 条取 Top-100 实测 0.5ms，全排序 71.1ms，差 142 倍），键是窄整数就换计数排序（1e7 个年龄快 28.7 倍），装不下内存就 k 路归并；跳过这三问直接调 `sort`，是架构里最常见的一笔冤枉账。

## 先问需求，再选结构

排序从来不是目的。把「我要排序」翻译成需求，答案只有五种，代价差两个数量级：

| 你真正的需求 | 该选什么 | 复杂度 | 1e6 条本机实测 |
|---|---|---|---|
| 只要最大/最小的 1 个 | 一次线性扫描 | O(n) | ~0.3ms（比较 1e6 次） |
| 只要前 k 个（k=100） | 大小 k 的最小堆 | O(n log k) | **0.5ms** |
| 前 k 个还要有序 | 堆 + 排这 k 个 | O(n log k + k log k) | 0.5ms + 微秒级 |
| 必须完整有序 | 比较排序 | O(n log n) | **71.1ms** |
| 键是 0–120 这种窄整数 | 计数排序 | O(n + V) | 1e7 条 **7.9ms** |
| 数据比内存大 | k 路归并 | O(n log R) | 见「装不下内存」 |
| 只要去重，不要求有序 | map | O(n) | 41.6ms / 37.8MB |

> 🔑 表格里最贵的一行是「必须完整有序」。绝大多数「排序需求」其实只是「Top-K 需求」或「去重需求」，被一句话写成了全排序。

## `n log n` 是硬下界，但下界只管「比较」

比较排序可以看成一棵决策树：n 个元素有 n! 种排列，每个叶子对应一种，树高就是最坏比较次数，所以

```text
最少比较次数 ≥ log2(n!) ≈ n·log2(n) - 1.44n
n = 1e6 → log2(1e6!) ≈ 1.85e7 次比较
```

本机 `slices.Sort` 排 1e6 个随机 int 用 71.1ms，折合**每元素 71ns**——已经贴着这个下界在跑，没有优化空间。想更快只有一条路：**别比较**。

非比较排序靠「直接算出元素该在第几位」绕开下界，代价是必须能枚举键：

| 算法 | 时间 | 额外内存 | 硬前提 | 真实落点 |
|---|---|---|---|---|
| 计数排序 | O(n + V) | O(V) | 键是 [0,V) 的整数，V 可控 | 年龄、评分、状态码、延迟分桶做 P99 直方图 |
| 基数排序 | O(d·n) | O(n) | 键可拆成固定长度的段 | 定长 ID、IPv4、时间戳 |
| 桶排序 | O(n) 期望 | O(n + k) | 键在值域上近似均匀 | 分数、金额分段统计 |
| 比较排序 | O(n log n) | O(log n) | 只要有序关系存在 | 字符串键、复合键、任意类型 |

判断口诀：**值域是「小整数」才考虑计数/基数；值域一大（用户 ID、UUID、金额到分），立刻回到比较排序。** 拿 1e12 值域硬上计数排序，等于申请 8TB 内存。

## Go 里有三个入口，差 1.7 倍

同一个 1e6 随机 int 数组，本机实测：

| 入口 | 类型 | 稳定性 | 1e6 实测 | 什么时候用 |
|---|---|---|---|---|
| `sort.Slice` | 任意，`less` 闭包 | 否 | 121.4ms | 只在老代码里见到，新代码别写 |
| `slices.Sort` | `~[]E`，`cmp.Ordered` | 否 | **71.1ms** | 排基本类型，默认选它 |
| `slices.SortFunc` | 任意，`cmp` 函数 | 否 | 52.9ms（排 8 字节记录） | 排结构体、要自定义序 |
| `slices.SortStableFunc` | 任意，`cmp` 函数 | **是** | 177.9ms | 同键必须保持原顺序 |
| `sort.SliceStable` | 任意，`less` 闭包 | 是 | 324.6ms | 同键必须保序的老代码 |

`sort.Slice` 慢在实现方式，不在算法：Go 1.19 起 `sort` 包底层已经是 pdqsort，但 `sort.Slice` 要用 `reflect.Swapper` 交换元素、用接口/闭包调 `less`，每次比较多一次间接调用，元素搬运也走反射。`slices.Sort` 在编译期单态化，比较函数能内联——**算法相同，差 1.7 倍，全在常数上。**

> 💡 pdqsort（pattern-defeating quicksort）的关键改进是「认数据」：检测到已排序、逆序、大量重复键时自动切策略，避免快排在这三类输入上退化。这条特性下面还会用到。

## 稳定性：贵 3.4 倍，但不额外吃内存

1e6 条记录（key 只有 1000 种取值，必然大量打平）实测：

```text
不稳定 slices.SortFunc        52.9 ms
稳定   slices.SortStableFunc 177.9 ms（3.4×）
稳定   sort.SliceStable      324.6 ms（6.1×）
稳定排序的额外分配：0 B
```

最后一行和教科书不同：Go 的稳定排序是**原地 symMerge**，不申请临时数组，代价全在时间（多出来的旋转拷贝）。所以「稳定排序要多一份内存」在 Go 里不成立，别拿它当拒绝稳定的理由——真正的理由是 3.4 倍时间。

必须付这 3.4 倍的三种情况：

| 场景 | 为什么非稳定不可 |
|---|---|
| 多级排序（先按时间，再按优先级） | 第二次排序会把第一次的序打乱，看起来「随机」 |
| 分页合并（多次查询结果拼接） | 同键顺序抖动会导致跨页重复/漏项 |
| 审计、对账、diff 输出 | 同键乱序让两次运行的输出不可比，噪声掩盖真差异 |

其他情况一律用 `slices.SortFunc`。判断标准很简单：**同键元素互换位置，会不会改变业务语义？** 会，才付 3.4 倍。

## Top-K：堆在 k 小时赢，快选在 k 大时赢

`topKHeap` 的全部逻辑就这几行，思路是「维护一个只装 k 个元素的小顶堆，堆顶是当前第 k 名」：

```go
h := make(minHeap, k) // 前 k 个直接入堆
copy(h, a[:k])
heap.Init(&h)
for _, v := range a[k:] { // 只读遍历剩下的 n-k 个
	if v > h[0] {          // 打不过第 k 名就直接跳过，一次比较搞定
		h[0] = v
		heap.Fix(&h, 0)    // 偶尔替换，下滤 O(log k)
	}
}
```

1e6 个随机 int，堆 vs 快选 vs 全排序：

| k | 堆 O(n log k) | 快选 O(n) | 全排序 O(n log n) | 赢家 |
|---|---|---|---|---|
| 100 | **0.5ms** | 6.5ms | 71.1ms | 堆，比全排序快 142× |
| 1 000 | **1.2ms** | 6.6ms | 71.1ms | 堆 |
| 10 000 | 6.4ms | 7.0ms | 71.1ms | 打平（交叉点在 1e4 附近） |
| 100 000 | 43.6ms | **11.6ms** | 71.1ms | 快选，反超 3.8× |
| 单次堆分配 | **1 816 B** | 8 003 584 B | 0 B（原地） | 堆省 4 400× 内存 |

为什么「O(n) 的快选」会输给「O(n log k) 的堆」？三点，全是常数：

- **堆每元素只做一次比较、几乎不写内存**。1e6 次比较在 0.5ms 内完成，说明它基本是纯顺序读。
- **快选必须搬数据**。分区要对元素做交换（写内存），还要先把原数组拷一份（8MB，实测 0.2ms，但翻倍了内存占用）。它的 6.5ms 里绝大部分是内存写，不是比较。
- **k 越大，堆的 log k 越贵**。k=1e5 时每元素平均要下滤十几次，堆的优势被吃掉，而快选的分区次数几乎不随 k 变。

> 🔑 生产选型：**k ≤ 1e4 用堆**（0.5–6ms 已经够快，且内存 O(k)、只读输入）；**k 大到要看前 10% 的数据时才考虑快选**，但要接受两个风险——必须拷贝或破坏调用方数据，以及最坏 O(n²)（大量重复键 + 坏 pivot 时）。堆的 0.5ms 已经比一次 RPC 便宜三个数量级，为省 5ms 引入 O(n²) 尾部风险不值得。这是我的判断，不是定理。

判断依据还有个更粗的口径：**k 小于 n 的 1% 时，堆是唯一合理选择**；k 超过 1% 再讨论。

两个真实落点：热榜、排行榜这类需求只要 Top-K，算一次存进缓存、按时间窗口失效，比每次请求都全量排序便宜几个数量级（缓存在架构里的位置见 [34.4 优化手段 (缓存 / 异步 / 批处理 / 池化 / 索引 / 并发)](../../L3-质量属性/34-性能/34.4-优化手段.md)）；搜索的 Top-10 也不是「把全部结果排一遍」，而是倒排索引求交后按打分取前 k（[45.1 倒排索引与分词](../../L4-组件与技术/45-检索与搜索引擎/45.1-倒排索引与分词.md)）。

## 部分有序：pdqsort 认得出，但只认一次

同一份 1e6 数据，只改有序度：

| 输入形态 | `slices.Sort` 耗时 | 相对随机 |
|---|---|---|
| 完全随机 | 71.1ms | 1× |
| 近似有序（随机打乱 100 对） | 8.53ms | **8.3× 更快** |
| 已排好序 | 0.65ms | **109× 更快** |

这解释了「为什么重跑一次排序会突然变快」：数据没变、算法没变，是 pdqsort 检测到有序片段后改走插入排序。**但这只是检测，不是增量维护**——它省的是常数，不是复杂度，仍然是 O(n)。

所以落点很明确：

| 场景 | 做法 | 别做 |
|---|---|---|
| 一次性批处理，数据近似有序 | 直接 `slices.Sort`，pdqsort 已经帮你省了 8 倍 | 手写插入排序 |
| 每隔 1 分钟追加一批，每次都要「全量有序」 | 保持一个有序切片，新数据用二分定位插入 | 每次全量重排 |
| 只需要反复取最小值/最早到期 | `container/heap` 或时间轮 | 每次都排一遍取第一个 |

定时任务、延迟消息的到期队列就是第三行：1 万个任务的队列，每次取最早到期的那个，用堆是 O(log n)，用「排一遍取头」是每秒 1 万次 × O(n log n)——这就是 [43.7 延迟消息与定时消息](../../L4-组件与技术/43-消息队列/43.7-延迟消息与定时消息.md) 里时间轮/堆存在的理由。

## 定值域：计数排序快 28.7 倍，但有两个硬前提

1e7 个年龄（0–120），原地计数排序 vs 比较排序：

```text
计数排序   7.9 ms
比较排序 228.5 ms（28.7×）
```

代价是那个 `[121]int` 的桶数组（约 1KB）——**内存是 O(V) 不是 O(n)**。两个硬前提缺一不可：

- **键必须是可索引的整数**。字符串、UUID、复合键直接出局。
- **值域必须可控**。年龄 121 个桶；用户 ID 值是 1e12 量级，桶数组就是 8TB，直接淘汰。

真实落点不是「排业务数据」，而是**统计**：算 P99 延迟时把 1e7 个耗时按毫秒分桶（0–5000ms 只要 5001 个桶），再从头累加找分位点——比排序快一个数量级，而且结果就是直方图本身。延迟指标的完整口径见 [34.1 性能指标 (延迟 / 吞吐 / P99)](../../L3-质量属性/34-性能/34.1-性能指标.md)。

## 装不下内存：k 路归并

10 亿行数据装不进 2GB 内存时，只有一条路：**切块排好（run），再多路归并**。

代价的算法是三句话：

```text
run 个数        R = ⌈N·s / M⌉            （N 行、每行 s 字节、可用内存 M）
归并趟数        P = ⌈log_k R⌉            （k = 归并路数）
k 的上限        k ≤ M / 每路读缓冲        （每路至少要一个页大小的缓冲）
总 IO 量        ≈ (2 + 1) × 数据量       （写 run + 读 run + 写结果）
```

具体算一遍：80GB 数据、2GB 内存、每路 64MB 缓冲 → `R = 40` 个 run，`k ≤ 32`，**一趟归并即可完成**（40 路需要 40×64MB=2.5GB，超了，改成每路 40MB 或分两趟）。按 500MB/s 顺序读写估，总 IO 约 240GB ≈ 480 秒；换成 3GB/s 的 NVMe 约 80 秒。**归并的 CPU 几乎不花钱，全部成本在 IO 次数上**——这就是为什么数据库的 `ORDER BY` 慢、而内存排序快，两件事不在一个量级。

本机用内存块模拟（不含磁盘 IO）：1e7 个 int64（80MB），单次全排序 850ms，切 20 块再归并 825ms——**只慢 3%，甚至更快**。这个数字的正确读法是：归并的 CPU 代价可以忽略，真实的外部排序耗时基本等于「数据量 ÷ 磁盘带宽 × 3 趟」。反过来说，任何号称「外部排序很慢」的优化，收益都在减少 IO 趟数，而不是换排序算法。

数据库的 `ORDER BY` 走的就是这套（索引有序时直接免排，见 [44.8 索引原理 (B+ 树 / 哈希 / 覆盖索引 / 最左前缀)](../../L4-组件与技术/44-数据库/44.8-索引原理.md)）；LSM 树的 compaction 更是标准的 k 路归并——[44.1 存储引擎：B+ 树与 LSM 树](../../L4-组件与技术/44-数据库/44.1-存储引擎B+树与LSM.md) 里那个「多层 SSTable 合并」的图，本质就是本节的多路归并。

## 可运行实测

`go run` 直接跑，环境 `go1.27.1 darwin/arm64`，Apple M1、8 核。**耗时取 7 次最快值**（不是平均）：每次重建数据，把系统抖动、GC、调度抢占挡在结论之外。

```go
package main

import (
	"container/heap"
	"fmt"
	"math/rand"
	"runtime"
	"slices"
	"sort"
	"time"
)

// bench：跑 reps 次取最快值。每次先重建数据（否则上一轮已排好序会让下一轮变快），
// 取最快而不是平均，是为了把系统抖动、GC、调度抢占这些噪声挡在结论之外。
func bench[T any](reps int, newData func() T, f func(T)) time.Duration {
	best := time.Duration(1<<62 - 1)
	for i := 0; i < reps; i++ {
		d := newData()
		t := time.Now()
		f(d)
		if el := time.Since(t); el < best {
			best = el
		}
	}
	return best
}

// alloc：用 TotalAlloc 差值量一次调用的堆分配（单调累加，不受 GC 回收影响）
func alloc(f func()) uint64 {
	var a, b runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&a)
	f()
	runtime.ReadMemStats(&b)
	return b.TotalAlloc - a.TotalAlloc
}

func dur(d time.Duration) float64 { return float64(d.Microseconds()) / 1000 }

// ---------- Top-K 之一：k 大小的最小堆 ----------
type minHeap []int

func (h minHeap) Len() int           { return len(h) }
func (h minHeap) Less(i, j int) bool { return h[i] < h[j] }
func (h minHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *minHeap) Push(x any)        { *h = append(*h, x.(int)) }
func (h *minHeap) Pop() any          { o := *h; v := o[len(o)-1]; *h = o[:len(o)-1]; return v }

// topKHeap：堆顶是当前第 k 名。更大的元素来了就替掉堆顶并下滤。
// 只读输入、内存 O(k)、时间 O(n log k)，且每个元素通常只花一次比较。
func topKHeap(a []int, k int) []int {
	h := make(minHeap, k)
	copy(h, a[:k])
	heap.Init(&h)
	for _, v := range a[k:] {
		if v > h[0] {
			h[0] = v
			heap.Fix(&h, 0)
		}
	}
	out := slices.Clone(h)
	slices.Sort(out) // 堆内无序，输出前补一次 O(k log k)
	return out
}

// ---------- Top-K 之二：快选 ----------
// topKQuick：只把「第 k 大」放到最终位置，它右边就是前 k 大。
// 期望 O(n)，但必须改数组 —— 所以要么拷贝（内存放大），要么破坏调用方数据。
func topKQuick(a []int, k int) []int {
	b := slices.Clone(a)
	target := len(b) - k
	lo, hi := 0, len(b)-1
	for lo < hi {
		pivot := b[(lo+hi)/2]
		i, j := lo, hi
		for i <= j {
			for b[i] < pivot {
				i++
			}
			for b[j] > pivot {
				j--
			}
			if i <= j {
				b[i], b[j] = b[j], b[i]
				i++
				j--
			}
		}
		// 不变式：<=pivot 落在 [lo,j]，>=pivot 落在 [i,hi]
		if target <= j {
			hi = j
		} else if target >= i {
			lo = i
		} else {
			break
		}
	}
	out := b[len(b)-k:]
	slices.Sort(out)
	return out
}

// ---------- 窄值域：计数排序 ----------
// 原地版：先数每个值出现几次，再按下标把值写回去。零分配，时间 O(n+V)。
func countingSortAges(a []uint8) {
	var cnt [121]int // 值域 0..120，121 个桶
	for _, v := range a {
		cnt[v]++
	}
	i := 0
	for v := 0; v <= 120; v++ {
		for k := 0; k < cnt[v]; k++ {
			a[i] = uint8(v)
			i++
		}
	}
}

// ---------- 装不下内存：k 路归并（这里用内存块模拟磁盘块） ----------
func externalMerge(a []int64, chunk int) []int64 {
	var runs [][]int64
	for i := 0; i < len(a); i += chunk {
		run := slices.Clone(a[i:min(i+chunk, len(a))])
		slices.Sort(run) // 每块内部排序 = 生成一个有序 run
		runs = append(runs, run)
	}
	for len(runs) > 1 { // 两两归并，直到只剩一个 run
		var next [][]int64
		for i := 0; i < len(runs); i += 2 {
			if i+1 == len(runs) {
				next = append(next, runs[i])
				continue
			}
			next = append(next, mergeTwo(runs[i], runs[i+1]))
		}
		runs = next
	}
	return runs[0]
}

func mergeTwo(x, y []int64) []int64 {
	out := make([]int64, 0, len(x)+len(y))
	i, j := 0, 0
	for i < len(x) && j < len(y) {
		if x[i] <= y[j] {
			out = append(out, x[i])
			i++
		} else {
			out = append(out, y[j])
			j++
		}
	}
	return append(append(out, x[i:]...), y[j:]...)
}

func main() {
	const n = 1_000_000
	rng := rand.New(rand.NewSource(42))
	base := make([]int, n)
	for i := range base {
		base[i] = rng.Intn(n)
	}
	fmt.Printf("环境 go1.27.1 darwin/arm64 · Apple M1 · GOMAXPROCS=%d\n", runtime.GOMAXPROCS(0))
	fmt.Printf("数据：%d 个 [0,%d) 随机 int，每项 7 次取最快值\n\n", n, n)

	// ① 三个排序入口
	cp := func() []int { return slices.Clone(base) }
	dSlice := bench(7, cp, func(x []int) { sort.Slice(x, func(i, j int) bool { return x[i] < x[j] }) })
	dSlices := bench(7, cp, func(x []int) { slices.Sort(x) })
	dClone := bench(7, func() []int { return base }, func(x []int) { _ = slices.Clone(x) })
	fmt.Printf("① 全排序 sort.Slice        %7.1f ms\n", dur(dSlice))
	fmt.Printf("   全排序 slices.Sort      %7.1f ms\n", dur(dSlices))
	fmt.Printf("   仅 slices.Clone(8MB)    %7.1f ms\n", dur(dClone))

	// ② Top-K：堆 vs 快选，k 从 100 到 10 万
	full := slices.Clone(base)
	slices.Sort(full)
	for _, k := range []int{100, 1_000, 10_000, 100_000} {
		dh := bench(7, cp, func(x []int) { topKHeap(x, k) })
		dq := bench(7, cp, func(x []int) { topKQuick(x, k) })
		fmt.Printf("   Top-%-6d 堆 %6.1f ms / 快选 %6.1f ms\n", k, dur(dh), dur(dq))
	}
	want := full[n-100:]
	fmt.Printf("   对账：堆==全排序 %v，快选==全排序 %v\n",
		slices.Equal(topKHeap(base, 100), want), slices.Equal(topKQuick(base, 100), want))
	fmt.Printf("   单次分配：堆 %d B / 快选 %d B\n",
		alloc(func() { topKHeap(base, 100) }), alloc(func() { topKQuick(base, 100) }))

	// ③ 数据有序度对 pdqsort 的影响
	nearly := func() []int {
		x := slices.Clone(full)
		for i := 0; i < 100; i++ {
			a, b := rng.Intn(n), rng.Intn(n)
			x[a], x[b] = x[b], x[a]
		}
		return x
	}
	dNear := bench(7, nearly, func(x []int) { slices.Sort(x) })
	dSorted := bench(7, func() []int { return slices.Clone(full) }, func(x []int) { slices.Sort(x) })
	fmt.Printf("\n② slices.Sort：随机 %5.1f ms / 近似有序 %5.2f ms / 已排序 %5.2f ms\n",
		dur(dSlices), dur(dNear), dur(dSorted))

	// ④ 1e7 个窄值域整数：计数排序 vs 比较排序
	const m = 10_000_000
	r2 := rand.New(rand.NewSource(7))
	freshAges := func() []uint8 { // 每次都造一份新的乱序数据：计数排序不吃有序度，比较排序吃
		x := make([]uint8, m)
		for i := range x {
			x[i] = uint8(r2.Intn(121))
		}
		return x
	}
	dCnt := bench(5, freshAges, countingSortAges)
	dCmp := bench(5, freshAges, func(x []uint8) { slices.Sort(x) })
	fmt.Printf("③ 1e7 个年龄[0,120]（原地）：计数 %5.1f ms / 比较 %6.1f ms（%.1f×）\n", dur(dCnt), dur(dCmp), float64(dCmp)/float64(dCnt))

	// ⑤ 稳定性代价
	type rec struct{ key, seq int32 }
	mk := func() []rec {
		x := make([]rec, n)
		r3 := rand.New(rand.NewSource(9))
		for i := range x {
			x[i] = rec{int32(r3.Intn(1000)), int32(i)}
		}
		return x
	}
	byKey := func(a, b rec) int { return int(a.key) - int(b.key) }
	dU := bench(3, mk, func(x []rec) { slices.SortFunc(x, byKey) })
	dS := bench(3, mk, func(x []rec) { slices.SortStableFunc(x, byKey) })
	dSS := bench(3, mk, func(x []rec) { sort.SliceStable(x, func(i, j int) bool { return x[i].key < x[j].key }) })
	fmt.Printf("④ 1e6 条(key 1000 种)：不稳定 %5.1f ms / 稳定 %5.1f ms（%.1f×）/ SliceStable %5.1f ms（%.1f×）\n",
		dur(dU), dur(dS), float64(dS)/float64(dU), dur(dSS), float64(dSS)/float64(dU))
	recs := mk()
	fmt.Printf("   稳定排序额外分配 %d B（原地 symMerge，不申请临时数组）\n",
		alloc(func() { slices.SortStableFunc(recs, byKey) }))

	// ⑥ 外部排序：1e7 个 int64 切成 20 块再归并
	const total = 10_000_000
	big := make([]int64, total)
	r4 := rand.New(rand.NewSource(11))
	for i := range big {
		big[i] = r4.Int63()
	}
	dIn := bench(5, func() []int64 { return slices.Clone(big) }, func(x []int64) { slices.Sort(x) })
	dExt := bench(5, func() []int64 { return big }, func(x []int64) { externalMerge(x, 500_000) })
	out := externalMerge(big, 500_000)
	fmt.Printf("⑤ 1e7 个 int64（%.0f MB）：单次全排序 %4.0f ms / 20 块+归并 %4.0f ms（纯内存，未计磁盘 IO）\n",
		float64(total*8)/1e6, dur(dIn), dur(dExt))
	fmt.Printf("   归并结果有序 %v，长度 %d\n", slices.IsSorted(out), len(out))

	// ⑦ 去重：sort+Compact vs map
	dSort := bench(7, cp, func(x []int) { slices.Sort(x); _ = slices.Compact(x) })
	dMap := bench(7, func() []int { return base }, func(x []int) {
		seen := make(map[int]struct{}, n)
		for _, v := range x {
			seen[v] = struct{}{}
		}
	})
	fmt.Printf("⑥ 1e6 个 int 去重：sort+Compact %5.1f ms / %d B  vs  map %5.1f ms / %d B（结果 %d 个）\n",
		dur(dSort), alloc(func() { x := slices.Clone(base); slices.Sort(x); _ = slices.Compact(x) }),
		dur(dMap), alloc(func() {
			seen := make(map[int]struct{}, n)
			for _, v := range base {
				seen[v] = struct{}{}
			}
		}), len(slices.Compact(full)))
}
```

## 反模式

这些坑的共同点是「把结构选错当成参数调优」，和 [34.6 性能反模式](../../L3-质量属性/34-性能/34.6-性能反模式.md) 里那类「用更大机器解决选型错误」同源。

| 反模式 | 后果 |
|---|---|
| 为 Top-10 把百万行全排序 | 71ms 变 0.5ms 的机会被浪费 142 倍；QPS 一高就是全站延迟 |
| 比较函数里做 IO、加锁、算哈希 | 一次排序触发 n log n 次调用，1e6 就是 2000 万次网络/锁，秒级变分钟级 |
| 多级排序用不稳定排序 | 第二级把第一级的序打乱，跨页数据重复/漏项，且难复现 |
| 排序键含可变字段（`time.Now()`、指针地址） | 同一条数据两次排序结果不同，分页直接错乱 |
| 用全量排序去重，却不接受 O(n) 内存 | 8MB 变 37.8MB（map）或 8MB 额外数组（sort+Compact），大结果集上直接 OOM |
| 把 1e6 行拉到应用层排序 | 网络传输 + 反序列化 + 内存峰值，比数据库里带索引的 `ORDER BY` 贵两个数量级 |
| `k` 用 1e5 还硬上堆 | 43.6ms vs 快选 11.6ms，慢 3.8 倍，且 CPU 全花在下滤上 |
| 排序后取 `[:k]` 但没校验 `len < k` | 小数据量时静默返回全部，边界条件在生产才暴露 |
| 用计数排序排用户 ID | 值域 1e12，桶数组申请 8TB，进程直接 OOM |
| 缓存里存「排好序的全量列表」 | 每次写入都要重排 O(n log n)，缓存变成 CPU 黑洞 |

## 自检

**Q1** 1e6 个随机 int，全排序 71.1ms、取 Top-100 只要 0.5ms，差 142 倍。这个差距里，复杂度贡献了多少，常数贡献了多少？

▸ 答案：复杂度只贡献了一部分——`O(n log n)` 与 `O(n log k)` 的比值是 `20/7 ≈ 2.9`（log2(1e6)=20，log2(100)≈7），最多解释 3 倍。剩下的 47 倍来自三个常数：① 堆每元素通常只做**一次比较**，几乎不写内存，而排序要搬动整个数组；② 排序的比较函数是间接调用（`slices.Sort` 已内联，`sort.Slice` 更是走反射），堆里是直接的 `<`；③ 堆只碰 k=100 个元素的内存（全部在 L1），排序要把 8MB 全扫一遍并写回。**所以「复杂度更优」不等于「更快」，两个数量级以内的差距基本都由常数决定。**

**Q2** 快选的复杂度是 O(n)，堆是 O(n log k)，为什么 k=100 时快选反而慢 13 倍，k=10 万时又快 3.8 倍？

▸ 答案：k 小时，堆的 `log k` 很小（7 次），而快选有两笔固定开销：必须先把 8MB 数组拷一份（否则破坏调用方数据），分区时还要对元素做交换（写内存）。它的 6.5ms 里绝大多数是内存读写，不是比较——而堆是纯顺序读。k 变大后，堆要对每个「打过第 k 名」的元素做一次下滤（约 log k 次交换），k=1e5 时平均下滤十几次，成本随 log k 线性上涨到 43.6ms；快选的分区次数几乎与 k 无关，所以反超。**交叉点在 k≈1e4，这个数字和机器强相关，换机器要重测。**

**Q3** 稳定排序贵 3.4 倍，什么情况下必须付？Go 的稳定排序会不会额外吃内存？

▸ 答案：必须付的判据只有一条——**同键元素互换位置会改变业务语义**：多级排序（先时间后优先级）、分页合并（跨查询拼接）、审计 diff（两次运行输出要可比）。不会改变的，一律用 `slices.SortFunc`。内存方面，Go 的 `sort.Stable` / `slices.SortStableFunc` 用原地 symMerge，实测额外分配 **0 B**，不像教科书说的「稳定排序要一份临时数组」——代价全在时间上（多出来的旋转拷贝）。这是 Go 实现特有的，换语言要重新确认。

**Q4** 计数排序快 28.7 倍，为什么线上几乎见不到有人拿它排业务数据？

▸ 答案：因为它要求**键是 [0,V) 的整数且 V 可控**，而业务数据的主键是 UUID、字符串订单号、分布式 ID，值域 1e12 起——桶数组直接申请 TB 级内存。它真正的主场是**统计**而不是排序：按毫秒分桶算 P99、按年龄分桶做人群分布、按状态码分桶做错误率，这些场景值域天然小（几百到几千），而且直方图本身就是结果。记住判据：**值域是「小整数」才用；值域一大就回比较排序**，这不是性能取舍，是能不能跑的问题。

**Q5** 本机外部排序（20 块归并）只比内存全排序慢 3%，那为什么数据库的 `ORDER BY` 会慢十倍？

▸ 答案：因为那次实测是**纯内存模拟**，20 个 run 都在 RAM 里，归并的 CPU 代价可以忽略（只慢 3%，甚至因为分块后缓存更友好而略快）。真实外部排序的成本几乎全在 IO 趟数：写 run、读 run、写结果，约 3 倍数据量。80GB 数据按 500MB/s 算就是 240GB IO ≈ 480 秒，CPU 那点时间忽略不计。**所以外部排序的优化方向永远是减少 IO 趟数（增大 k、减少 run 数）和顺序读写，而不是换排序算法**——同理，数据库里带索引的 `ORDER BY` 之所以快，是它根本不需要排序。

**Q6** `sort.Slice` 和 `slices.Sort` 算法一样（都是 pdqsort），为什么差 1.71 倍？

▸ 答案：差在「比较」这一层怎么被调用。`sort.Slice` 通过 `reflect.Swapper` 交换元素、通过接口/闭包调 `less`，每次比较多一次间接跳转且**无法内联**，元素搬运也走反射；`slices.Sort` 是泛型单态化，比较直接用 `<`，能被内联成一条指令。1e6 个元素要比较约 2×10⁷ 次，每次多几纳秒就是几十毫秒。**这条差异的量级和算法选择在同一档（1.7 倍），却几乎没人检查**——新代码里出现 `sort.Slice`，先换成 `slices.Sort` 再说。

**Q7** 去重：`sort+Compact` 是 72.0ms / 8MB，`map` 是 41.6ms / 37.8MB。怎么选？

▸ 答案：先问输出要不要**有序**——要，只有 `sort+Compact` 一条路（map 出来是无序的，再排一次等于两份成本）；再问**内存预算**——37.8MB 对 8MB 是 4.7 倍，1e8 条数据时 map 要 3.7GB，直接不可行。还要看数据形态：`sort+Compact` 是 O(n log n) 且吃有序度（近似有序时快 8 倍），map 是 O(n) 但对 cache 不友好。我的默认选择是 `sort+Compact`——内存可控、输出有序、后续还能二分查找；只有当内存充裕且明确不要顺序时才用 map。
