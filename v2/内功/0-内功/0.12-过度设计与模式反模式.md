# 0.12 过度设计与模式反模式：什么时候不该用模式

## 一句话

> 过度设计是**为想象中的变化提前付费**：判断标准不是用了几个模式，而是**这层抽象有没有第二个实现、加一层有没有让下一次变更加便宜**；同一需求三版实测 if-else 2.5 ns/0 alloc、函数值策略 10.9 ns/0 alloc、抽象工厂 15.1 ns/1 alloc——**抽象不是免费的，先证明变化存在，再付钱**。

## 五个过度设计信号，全都能数出来

| 信号 | 怎么量 | 阈值 | 本机实测例 |
|---|---|---|---|
| 抽象层比业务代码还长 | `wc -l` 比 | 抽象 LOC / 业务 LOC > 1.0 | 工厂版 29 行 vs if 版 18 行 = 1.6 |
| 接口实现数 = 1 | `gopls` 的 Implementations | 数量 = 1 且存在 >6 个月 | 只有 `*ratePricer` 一个实现 |
| 每加 1 个需求新增类型数 | 一次真实需求的 diff | ≥2 个新类型 | 加 employee 规则：工厂版 +21 行、+2 类型 |
| 变更频率为 0 的抽象 | `git log --since=6.months -- <file> \| wc -l` | 0 次 | 抽象了的规则半年没改过 |
| 配置项比规则还多 | 数配置项 / 数分支 | 配置项 > 分支 | 4 条规则配了 6 个开关 |

> 🔑 五个信号里最硬的是**实现数**和**变更频率**：一个接口只有一个实现、且这个文件半年没改过一次，它就只是一层跳转。这两个数字都能直接从仓库里查，不靠争论。表里的阈值是经验起点（我的判断），用来触发讨论，不用来一票否决。

## 复杂度预算：YAGNI 与「预留扩展点」的边界

「以后可能要支持多种支付方式」这句话不值钱。值钱的是**变化已经可度量**：需求池里有排期、git 历史里有反复修改、调用方已经出现第二种用法。

| 变化频率（近 6 个月） | 影响面（改一次动几处） | 可逆性（去掉这层要改几处） | 团队认知 | 决策 |
|---|---|---|---|---|
| 0 次 | 任意 | 任意 | 任意 | 直接 if，不抽象 |
| 1 次 | ≤2 处 | 1 处 | 熟悉 | if + 1 个测试守住边界 |
| ≥2 次 | 3–5 处 | ≤3 处 | 有共识 | 函数值策略 + 注册表 |
| ≥4 次 | >5 处 | >3 处 | 需要文档 | 接口 + 注册表 + 显式契约 |
| 已确定 2 个实现且都已排期 | 任意 | 任意 | 任意 | 值得抽象（这时抽象是刚需） |

> 🔑 判据只有一句：**这次抽象有没有让下一次变更加便宜**。测法很土——拿上一次真实的需求改动，分别在「有抽象」和「没抽象」的版本上量改动行数。如果两版都是 +7 行，那这层抽象现在就是纯成本。

层数每加一层，跨层调用就多一跳，耦合度跟着涨——耦合怎么度量见 [40.2 耦合与内聚度量](../../L3-质量属性/40-可维护性/40.2-耦合与内聚度量.md)，包和层的边界怎么切见 [26.6 模块化与包设计](../../L2-架构风格/26-分层与依赖/26.6-模块化与包设计.md)。

## 同一需求三版实测：18 / 18 / 29 行

需求：订单计价，4 种折扣（无、vip 9 折、coupon 8 折、season 8.5 折）。三版实现，`wc -l` 计量。

```go
// ① if-else：18 行
package plain

func Price(kind string, cents int) int {
	if kind == "none" {
		return cents
	}
	if kind == "vip" {
		return cents * 90 / 100
	}
	if kind == "coupon" {
		return cents * 80 / 100
	}
	if kind == "season" {
		return cents * 85 / 100
	}
	return cents
}
```

```go
// ② 函数值策略：18 行
package strategy

type Rule func(cents int) int

var rules = map[string]Rule{
	"none":   func(c int) int { return c },
	"vip":    func(c int) int { return c * 90 / 100 },
	"coupon": func(c int) int { return c * 80 / 100 },
	"season": func(c int) int { return c * 85 / 100 },
}

func Price(kind string, cents int) int {
	if r, ok := rules[kind]; ok {
		return r(cents)
	}
	return cents
}
```

```go
// ③ 抽象工厂：29 行，规则 -> 工厂 -> 产品三层
package factory

type Pricer interface{ Price(cents int) int }

type Factory interface{ Create() Pricer }

type ratePricer struct{ rate int }

func (p *ratePricer) Price(c int) int { return c * p.rate / 100 }

type rateFactory struct{ rate int }

func (f *rateFactory) Create() Pricer { return &ratePricer{rate: f.rate} }

var factories = map[string]Factory{
	"none":   &rateFactory{rate: 100},
	"vip":    &rateFactory{rate: 90},
	"coupon": &rateFactory{rate: 80},
	"season": &rateFactory{rate: 85},
}

func Price(kind string, cents int) int {
	f, ok := factories[kind]
	if !ok {
		return cents
	}
	return f.Create().Price(cents) // 每次调用都造一个产品
}
```

三版都经过一层 `//go:noinline` 包装（防止内联把分派优化掉），压测代码：

```go
package bencher

import (
	"testing"

	"price/factory"
	"price/plain"
	"price/strategy"
)

var kinds = []string{"none", "vip", "coupon", "season"}
var sink int

//go:noinline
func callPlain(k string, c int) int { return plain.Price(k, c) }

//go:noinline
func callStrategy(k string, c int) int { return strategy.Price(k, c) }

//go:noinline
func callFactory(k string, c int) int { return factory.Price(k, c) }

func BenchmarkPlain(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink = callPlain(kinds[i&3], 20000)
	}
}

func BenchmarkStrategy(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink = callStrategy(kinds[i&3], 20000)
	}
}

func BenchmarkFactory(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink = callFactory(kinds[i&3], 20000)
	}
}
```

| 版本 | 代码量 | ns/op（3 次） | B/op | allocs/op | 相对最直白版 |
|---|---|---|---|---|---|
| if-else | 18 行 | 2.45 / 2.46 / 2.74 | 0 | 0 | 1.0× |
| 函数值策略 | 18 行 | 10.71 / 10.73 / 10.97 | 0 | 0 | 4.4× |
| 抽象工厂 | 29 行 | 14.83 / 14.88 / 15.16 | 8 | 1 | 6.1× |

> 这组数比订单号那组稳定：不同时段重测只差约 10%。原因是它一半以上是分支与 map 查找，不吃时钟频率；订单号那组每生成一个都要读一次时钟，机器状态一变就差 30%。

三个结论，每个都能从数字里读出来：

1. **策略版没有变长**（都是 18 行）。「策略模式让代码变多」在函数值版上不成立，它只多了 map 查找的 8.3 ns。
2. **工厂版的税是 1 次分配**。`f.Create()` 返回接口，`&ratePricer{}` 逃逸到堆——每次计价都新建一个只需要 `rate` 的产品，8 B/次。
3. **绝对差很小，但不是零**。单次 8.3–12.7 ns，一次下单算一次价可以忽略；但报价网关每秒 100 万次分派，就是 8–13 ms 的 CPU，这时才需要把分派移出热路径——这属于性能优化，手段与取舍见 [34.4 优化手段 (缓存 / 异步 / 批处理 / 池化 / 索引 / 并发)](../../L3-质量属性/34-性能/34.4-优化手段.md)。

变化成本也要算。加第 5 条规则（employee 7 折，单笔优惠上限 5000 分，逻辑与现有规则不同），实测 diff：

| 版本 | 改动行数 | 删除行 | 改后总行数 | 改动的形态 |
|---|---|---|---|---|
| if-else | +7 | 0 | 25 | 在已有函数体里追加分支（回归面 = 整个函数） |
| 函数值策略 | +7 | 0 | 25 | 在已有 map 里追加一项（回归面 = 新项） |
| 抽象工厂 | +21 | 0 | 49 | 新增 2 个类型 + 1 项注册（回归面 = 新类型） |

> 🔑 成本不在「今天多几行」，在**回归面**：改已有函数体，意味着这个函数的所有已有分支要重新验证；纯追加一行，只验证新增那一项。所以「纯追加」是唯一值得为模式付钱的地方。

## 什么时候不该用模式

| 你的情况 | 别用 | 直接写 | 代价对比 |
|---|---|---|---|
| 分支 ≤3、半年没变 | 策略 + 工厂 | `if` / `switch` | 29 行 + 1 alloc vs 18 行 + 0 alloc |
| 只有一个实现、也没排期 | 接口 + DI | 具体类型 | 少一层跳转，少一个 fake |
| 只是想把函数拆短 | 命令模式 | 拆成小函数 | 命令队列 + 撤销栈全是白写的 |
| 只是遍历一个切片 | 迭代器模式 | `for range` | 0 成本 vs 一个闭包 + 一个函数值 |
| 两个对象互相调用 | 中介者 | 直接调用 | hub 是第 3 个要维护的东西 |
| 只想给 3 个类型加个方法 | 访问者 | `type switch` | 55 行 vs 38 行，加类型时 8 条编译错误 |

## 删除模式：从模式退回直白代码

删除顺序从外往里，每一步都能编译：

| 步 | 动作 | 判据 | 实测收益 |
|---|---|---|---|
| ① 去接口 | `Pricer` 接口 → 具体函数 | 实现数 = 1 且无测试替身需求 | 少一层间接 |
| ② 内联工厂 | 工厂 + 产品 → 直接算 | 只有 1 个产品类型 | 29 行 → 18 行（-38%） |
| ③ 合并策略 | 注册表 → if / switch | 规则 ≤3 且无外部注册需求 | 15.1 ns → 2.5 ns（-83%），1 alloc → 0 |

顺序不能反：接口在最外层，工厂依赖接口，策略依赖注册表。**先删接口会让工厂和策略同时编译不过**，一次要改 3 个文件；从外往里删，每次只动一层，`go build` + 测试绿 + 基准不变差，随时可停。

「从模式退回直白代码」是重构的一种，判据、分段和验收标准在 [58.7 重构三式（有的放矢 / 合纵连横 / 运筹帷幄）](../../L5-工程效能/58-架构治理/58.7-重构三式.md)，这里只补一条模式专属的：**删掉一层后，把当初写它的理由（注释、ADR、commit message）一起删掉**，否则半年后有人照着旧理由再建一遍。

删掉的抽象要在技术债账本上销账——「已删除」和「从未存在」是两种状态，账本里留着一条没人用的接口，下个季度还会有人来问它为什么没人用（[58.2 技术债管理](../../L5-工程效能/58-架构治理/58.2-技术债管理.md)）。

## 重构演算：订单号生成器，三步加、一步删

> 一句话：重构不是把代码改成模式，是**一次修一个硬伤**——9 行雪花号先撞上「同毫秒回绕 + 数据竞争 + 测不了」，三步修到可测只贵约 10 ns，第四步把顺手加出来的接口再删掉。

这类演算的经典版本是 Java 的 ID 生成器重构（王争《设计模式之美》第 34–37 讲）；Go 版多两个坑：`-race` 能直接抓到的数据竞争，和 `time.Now` 的注入方式。

### 起点：能跑，三个硬伤都能复现

```go
// v0：全局状态 + 真实时钟 + 无锁，净代码 9 行
const (
	epoch    int64 = 1700000000000 // 2023-11-15 00:00:00 UTC
	nodeBits       = 10
	seqBits        = 12
	seqMask  int64 = 1<<seqBits - 1
)

var (
	v0seq  int64
	v0node int64 = 1
)

func NextV0() int64 {
	ms := time.Now().UnixMilli() - epoch
	v0seq = (v0seq + 1) & seqMask // 数据竞争：多 goroutine 同时写
	return ms<<(nodeBits+seqBits) | v0node<<seqBits | v0seq
}
```

| 硬伤 | 复现方式 | 本机结果 |
|---|---|---|
| 同毫秒序列回绕 | 单线程连续生成 2 万个，断言递增 | 第 4096 个就倒退（`400029978298683392 <= 400029978298687487`） |
| 并发写竞争 | 8 goroutine × 500，`go test -race` | 3/3 次 `WARNING: DATA RACE`，且出现重复 ID |
| 不可测 | 想测回绕、回拨 | 没有注入点，只能 `time.Sleep(1ms)` 等真实时钟 |

三条都不是风格问题：第一条是**同毫秒超过 4096 个就会重复/倒退**，第二条是 `-race` 直接判死刑。

### 第一步：状态搬进结构体，加一把锁

```go
type Gen struct {
	mu   sync.Mutex
	node int64
	last int64
	seq  int64
}

func New(node int64) *Gen { return &Gen{node: node & nodeMask} }

func (g *Gen) Next() int64 {
	g.mu.Lock()
	defer g.mu.Unlock()
	// ...生成逻辑见第三步
}
```

改动只做了两件事：全局变量 → 结构体字段，`Next` 首尾加锁。`-race` 从 3 次报错变成 PASS，**并发导致的重复 ID 消失**（同毫秒回绕还在，下一步修）。锁本身不贵：同机独立测得 `sync.Mutex` 一次加解锁 22–26 ns（[15.6 并发原语 (channel / context / sync)](../../L0-运行时底座/15-语言运行时/15.6-并发原语.md)）。

### 第二步：时钟和节点变成构造参数

时钟写死，测试就只能等真实毫秒；节点写死，多副本扩容就得改代码。结构体加一个 `now` 字段，两个都改成构造参数，注意**时钟用函数值，不是接口**：

```go
type Gen struct {
	mu   sync.Mutex
	now  func() time.Time // 新增：注入点
	node int64
	last int64
	seq  int64
}

func NewWithClock(node int64, now func() time.Time) *Gen {
	return &Gen{now: now, node: node & nodeMask}
}

// 生产：New(7) 内部就是 NewWithClock(7, time.Now)
// 测试：NewWithClock(7, fake.Now)
```

到这里，1 万个 ID 的唯一性测试已经 0 等待；但同毫秒回绕和时钟回拨还没处理，下一步一起修。

### 第三步：回拨与回绕，用逻辑毫秒

```go
func (g *Gen) Next() int64 {
	g.mu.Lock()
	defer g.mu.Unlock()
	ms := g.now().UnixMilli() - epoch
	if ms <= g.last { // 同一毫秒，或时钟回拨：沿用逻辑毫秒
		g.seq++
		if g.seq > seqMask { // 本毫秒用尽：向未来借 1 ms
			g.last++
			g.seq = 0
		}
		ms = g.last
	} else {
		g.seq = 0
		g.last = ms
	}
	return ms<<(nodeBits+seqBits) | g.node<<seqBits | g.seq
}
```

三种时钟注入下的测试，**一次 sleep 都不需要**：

| 测试 | 注入的时钟 | 结果 |
|---|---|---|
| 1 万个 ID 唯一且递增 | 每次读前进 1 µs | PASS，`go test` 显示 0.00 s |
| 序列回绕 4096 → 0 | 冻结不走 | PASS，自动借下一毫秒 |
| 时钟回拨 1 s | 隔一次回拨 1 s | PASS，1000 个 ID 仍单调 |

> 🔑 回绕不是 `& seqMask` 就能糊过去的：取模会让 ID 在同毫秒内倒退。要么等下一毫秒（热路径里加一个自旋循环，实测把单次从约 54 ns 拖到 245 ns：4096 个 ID 要等约 0.8 ms，摊到每个就是 +195 ns），要么像这里**借下一毫秒**——没有等待，代价是 ID 的毫秒部分会暂时领先真实时间，回拨持续越久、写入越快，领先越多。

### 第四步：删掉顺手加的 `Clock` 接口

第二步很容易「顺手」抽一个接口，因为"以后可能要接逻辑时钟 / NTP 校时"：

```go
type Clock interface{ Now() time.Time }

type clockFunc func() time.Time

func (f clockFunc) Now() time.Time { return f() }
```

实测这层接口买到的是 **0 ns**（函数值 53.8 / 54.2 / 62.5，接口 49.1 / 52.8 / 63.6，两段区间重叠，差异落在噪声里），代价是多一个类型 + 一层包装。时钟在这里是无状态单方法，函数值已经能注入、能 fake，接口没有额外能力。什么时候接口才成立：**替身有状态或多方法**（比如要同时提供 `Now()` 和 `Advance()`），或者真实实现会分叉。

> 🔑 函数值能注入的，别升成接口；接口留给「有状态 / 多方法 / 真会分叉」的替身。这条与 [0.7 模式解决的是 "变化点"：23 种模式的 Go 取舍索引](0.7-模式解决的是变化点.md) 里 1.3 ns vs 2.3 ns 的实测一致。

### 账：约 10 ns 买三个硬伤

| 版本 | 净代码行 | ns/op（3 次） | B/op | 并发安全 | 可测性 |
|---|---|---|---|---|---|
| v0 全局 + 无锁 | 9 | 42.8 / 44.2 / 50.0 | 0 | 否（3/3 重复 + DATA RACE） | 只能 sleep |
| v1 锁 + 函数值时钟 | 28 | 53.8 / 54.2 / 62.5 | 0 | 是（`-race` PASS） | 冻结 / 回拨都能测，0 等待 |
| v2 锁 + `Clock` 接口 | 30 | 49.1 / 52.8 / 63.6 | 0 | 是 | 同 v1 |

+19 行、+10 ns（约 1.2 倍）、0 分配，换来的是「并发正确 + 可测 + 能处理回拨」。这笔账在任何要生成 ID 的服务里都划算；不划算的场景写在下面。

> ⚠️ 绝对值随机器状态浮动：同一台 M1 在高负载时段测到的是 57.5 / 75.6 / 76.0 ns，空闲时是 42.8–62.5 ns，能差 30%。**看比值与量级**：正确性成本约 1.2 倍、接口与函数值无差别，这两条在两次测量里都成立。

复现命令：`go test -race -run TestGen`、`go test -run '^$' -bench . -benchmem -count=3`（go1.27.1 darwin/arm64，Apple M1）。

### 什么时候别这么改

- **单 goroutine、每秒不到 4096 个**：v0 的回绕不会触发，加锁加注入是纯成本——但只要多一个 goroutine，或者上游突发超过 4096/ms，它立刻出错。
- **已经有唯一 ID 来源**：数据库自增、Redis `INCR`、ULID 都能用，没必要自己实现雪花号；自己实现的唯一理由是"不依赖外部存储且要按时间排序"。
- **节点号靠人配**：10 位节点上限 1024 个，扩容时漏配一个环境变量就会撞号；节点号该由配置中心/注册中心分配，并把它当启动时的硬校验（配错直接退出，别带病上线）。

## 反模式

| 反模式 | 后果 |
|---|---|
| 先用模式、再找需求 | 抽象按想象设计，第二个真实需求一到就推倒重来 |
| 每加一个需求加一个类（含工厂 + 接口） | 4 条规则 29 行 → 5 条规则 49 行，+21 行、+2 类型 |
| 抽象层没有第二个实现，还留着 | 多一层跳转、多一个 fake；实现数永远是 1 |
| 命名暴露实现（`PGRepo`、`RedisCache` 出现在业务包） | 换存储时调用方要改，抽象白做 |
| 把模式数量当 KPI / 评审时数用了几个设计模式 | 团队开始为用而用，代码量与分配次数一起涨 |
| if-else 换皮成策略类（一个规则一个 struct + 接口 + 工厂） | 行数翻倍，分派从 2.5 ns 变 15 ns，可读性反而下降 |
| 单例当全局变量（`GetInstance()` 到处取） | 隐式依赖、测试之间互相污染、并发初始化难查 |
| 过度分层：handler→service→domain→repo→dao 每层只透传 | 加一个字段要在 5 层各改一次，一个需求 5 次 DTO 转换 |
| mock 驱动的接口（只有测试用的接口） | 产品代码为测试让路，多一层没人替换的间接 |
| 循环依赖靠 `interface{}` / `any` 绕过 | 类型安全丢失，问题从编译期推迟到运行时 |

## 自检

**Q1** 三版代码量是 18 / 18 / 29 行，那「策略模式让代码变多」这句话错在哪？

▸ 答案：错在把「策略」和「策略 + 接口 + 工厂」当成一件事。函数值策略只多一个 map 和一次查找，LOC 与 if-else 完全一样（都是 18 行）；真正变多的是工厂版（29 行，+61%），多出来的是 `Pricer`、`Factory`、`ratePricer`、`rateFactory` 四个类型。所以「模式让代码变多」精确说法是：**为模式配套的接口和工厂让代码变多，模式本身不一定**。

**Q2** 策略版慢 4.4 倍（2.5 → 10.9 ns），为什么还常推荐它？什么时候不该推荐？

▸ 答案：4.4 倍听着吓人，绝对值只有约 8 ns，而一次计价相比一次 DB 查询可以忽略。不该推荐的场景是可算的：**分派次数 × 8 ns 占总预算的比例**——每秒 100 万次分派就是 8 ms CPU，每秒 100 次不到 1 µs，后者毫无意义。另一个不该用的场景是规则 ≤3 且稳定：这时 map 查找换来的「可扩展性」一次也没用上。

**Q3** 工厂版多出来的 1 次分配（8 B/op）具体从哪来？怎么消掉？

▸ 答案：`f.Create()` 每次返回一个新的 `&ratePricer{rate: ...}`，接口值持有指针，指针逃逸到堆，于是每次调用 1 次分配。消掉的办法是改变「谁持有产品」：产品在初始化时创建一次、注册表里存的是 `Pricer` 本身而不是 `Factory`，或者干脆让工厂返回函数值。**只要 `Create()` 还在热路径上被调用，这个分配就消不掉**。

**Q4** 团队说「以后可能要支持多种支付方式，现在先抽象好」。你拿哪些数据决定现在要不要做？

▸ 答案：三个可查的数字：① `git log --since=6.months -- <file> | wc -l`，这个文件半年改过几次；② 需求池里第二个实现有没有排期（有排期 = 变化已发生）；③ 影响面与可逆性——现在不做抽象，等第二个实现来了要改几处，改回来的成本是多少。**没有排期的「以后」不算变化**；如果三个数字都指向「没有变化」，正确做法是写 if + 一个测试守住边界，等第二个实现真的进排期再抽。

**Q5** 加第 5 条规则，if 版 +7 行、工厂版 +21 行，都是「纯追加」吗？这个区别为什么比行数重要？

▸ 答案：两版都是 0 删除行，但回归面不同：if 版的 7 行加在**已有函数体内部**，已有的 4 个分支要跟着重新验证（改错一个已有分支是常见事故）；工厂版是新增类型 + 注册表加一行，已有分支一行没动，回归面只有新类型。所以「纯追加 vs 改已有代码」比「+7 还是 +21」更能决定这次改动的风险——后者只是 review 时间，前者是线上事故概率。

**Q6** 「过度分层」怎么度量？给出能直接在仓库里查的指标。

▸ 答案：四个：① 抽象层 LOC / 业务 LOC，>1 就是抽象比业务重；② 一个需求跨几层（handler→service→domain→repo），每层只做透传就是层数过多，>3 层且无逻辑要警惕；③ 加一个字段要改几个文件（DTO 转换的次数）；④ `gopls` 查接口实现数 = 1 的接口有几个。这四个都能用命令或一次真实 diff 量出来，不靠感觉。

**Q7** 删除模式为什么必须「从外往里」？顺序反了会怎样？

▸ 答案：依赖是单向的——接口在最外层，工厂依赖接口，策略依赖注册表。从外往里删：先删接口变具体类型，工厂的 `Create()` 返回值跟着改一处，编译能过；再内联工厂，调用点从 `factory.Create().Price()` 变成直接函数；最后把注册表合并成 if。每一步只动一层，`go build` + 测试 + 基准都能验证。反过来先删注册表，工厂和接口会同时失去调用点，一次要改 3 个文件，中间态编译不过，只能一把梭——那就变成重写了。

**Q8** 订单号生成器为什么用 `sync.Mutex` 而不是原子操作？锁的 22 ns 不心疼吗？

▸ 答案：一次生成要同时读时钟、比较 `last`、写 `seq`、必要时改 `last`，四个字段必须一起成立；原子变量只能保住单个字段，组合语义得靠 CAS 重试循环，代码更难读、竞争下更慢。锁的代价是 14–15 ns，而一次生成总成本约 54 ns（见上面的账），锁约占四分之一。**判据是"要原子的是不是一个复合状态"**：单计数器用 atomic，复合状态用锁。

**Q9** 时钟回拨时，为什么选「沿用逻辑毫秒」而不是直接返回错误或阻塞等待？

▸ 答案：三条路的代价不同。报错 = 回拨期间拒绝服务；阻塞 = 把时钟问题变成可用性问题；借用未来毫秒 = 服务不停，代价是 ID 的毫秒部分暂时领先真实时间（每 4096 个 ID 前进 1 ms，回拨越久、写入越快，领先越多）。选哪条取决于下游：如果 ID 只用于唯一性，借用最划算；如果下游按 ID 反解时间做分片或排序，就得记录这个偏差并告警。**没有普适答案，但必须显式选一个并写进注释**，默认的 `& seqMask` 是三个选项里最差的那个——它会悄悄产生重复 ID。
