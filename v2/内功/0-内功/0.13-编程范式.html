                      0.13 编程范式：Logic、Control 与 Data 的分离

                      一句话

                      程序 = Logic（做什么）+ Control（怎么做）+ Data；过程、OOP、泛型、函数式、原型、逻辑这些范式，本质都是在回答"把哪一部分标准化、把哪一部分留给业务"——架构上真正用得上的只有三条：Logic 决定复杂度的下限，Control 可以沉淀成框架与中间件，Data 的形态决定前两者能怎么组合。

                      先立两个等式

                      来源 等式 说明
                      Wirth 算法 + 数据结构 = 程序 经典的教科书口径
                      Kowalski 算法 = 逻辑 + 控制 把"算法"拆成两半

                      合起来就是：程序 = Logic + Control + Data。

                      两个等式的出处值得记住：Wirth 出自 1976 年的《Algorithms + Data Structures = Programs》，Kowalski 出自 1979 年的《Algorithm = Logic + Control》。后者原本是用来解释"逻辑程序"的——同一段逻辑配上不同的控制策略（比如深度优先还是广度优先回溯），算法效率会差好几个数量级，但答案应当相同。

                      部分 回答 能否标准化 举例
                      Logic 做什么（What） 不能——每个业务不同 "满 100 减 20"、"按件数收物流费"
                      Control 怎么做（How） 能——与业务无关 遍历、查找、并发、异步、重试、事务、调度
                      Data 操作什么 能（结构一旦定下） 订单、用户、事件、消息

                      两条推论，直接决定后面的所有判据：

                      🔑 同一 Logic 换一种 Control，算法的本质不变，变的只是效率。 所以"把 for 循环改流式"、"把同步改异步"这类动作，不该改变业务语义。

                      🔑 绝大多数程序混乱的根因，是业务逻辑与控制逻辑耦合。 业务逻辑只决定复杂度的下限，多出来的复杂度全是 Control 没被抽走。

                      六个范式，一张谱系

                      范式 一句话 你把什么标准化了 代表 架构上的投影
                      过程式 一步步写怎么做 没有（控制流即业务） C、Pascal 业务与流程混在一个函数里，改流程=改业务
                      面向对象 名词 + 消息，封装/继承/多态 名词的边界与契约 Java、C++ 接口即协议；但也容易长出厚重的"代码粘合层"
                      泛型 类型参数化，算法与类型解耦 类型 + 容器操作 C++ 模板、Go 泛型 容器与算法库；迭代器是最小契约
                      函数式 无状态 + 不可变，声明式 控制流（用组合代替步骤） Haskell、Clojure 并行无伤害；事件溯源、流处理
                      原型 对象直连，委托而非分类 对象间的查找链 JavaScript 运行时灵活，但缺静态契约
                      逻辑 规则 + 事实，求解器匹配回溯 求解过程 Prolog 规则引擎、风控、策略引擎

                      谱系的一端是声明式（只说要什么：函数式、逻辑式），另一端是指令式（说怎么做：过程式、OOP）。越靠声明式，Control 被语言/运行时接管得越多；越靠指令式，Control 越留在你手里。

                      三条架构判据

                      判据一：Logic 不能标准化，Control 必须标准化

                      这是整套范式观里最有用的一条。业务逻辑千变万化，不可能做成通用库；但"遍历、重试、超时、事务、并发、调度"与业务无关，可以且应该沉淀到框架/中间件里。

                      做法 结果
                      每个业务自己写重试、超时、幂等 同一套 Control 被实现 N 遍，行为还不一致
                      Control 下沉到框架/中间件，业务只提供 Logic 与 Data 业务代码只剩"做什么"，Control 改一次全局生效

                      对照书里的章节：重试与退避（35.5 超时、重试与退避）、幂等（25.4 幂等设计与去重）、事务（24.9 事务模型选型）——它们都是 Control，都不该由每个业务自己发明。

                      判据二：标准化 Control 的前提，是标准化 Data

                      想复用"遍历"，先要有统一的容器契约；想复用 RPC，先要有统一的消息格式；想复用存储，先要有统一的数据模型。

                      泛型就是这条判据最纯粹的形态。它的本质不是"语法糖"，而是标准化四件事：

                      标准化的对象 具体内容
                      类型的内存访问 分配、释放、读写
                      类型的操作 加法、比较、拷贝
                      容器操作 插入、删除、遍历
                      类型特有操作 哈希、排序、序列化

                      C++ 的迭代器把这件事做到极简：容器自带 iterator，重载 *、++、==、!=，再 typedef value_type；算法只依赖这组最小约定，于是 find、sort、accumulate 能用于所有容器。算法与容器的解耦，靠的不是继承，是一组最小的公共协议。

                      判据三：接口即协议——让双方依赖标准，而不是互相依赖

                      OOP 的两个核心理念是"面向接口而非实现"和"优先对象组合而非类继承"，但它们经常被讲成口号。落到系统上，这句话是：

                      🔑 接口即协议。 浏览器与后端之所以能各自演进，是因为双方都依赖 HTTP 这个标准，而不是互相依赖对方的实现。系统内部同理：通过抽象解耦、通过中间件解耦，本质都是把"双方直连"换成"双方接标准"。

                      对照 26.2 依赖倒置：IoC/DIP 的本质就是"双方都依赖一个标准接口"，接口由使用方定义。平台与业务的边界之争（哪些平台做、哪些甩给业务），争的也是这条标准画在哪。

                      类型系统：两个维度、四个收益

                      维度 取值 判据
                      检查时机 静态（编译期）/ 动态（运行期） 错误什么时候暴露给你
                      类型强度 强（只允许不丢失信息的自动转换）/ 弱 会不会静默截断、丢精度

                      两者是独立的两个维度：C 是静态弱类型，Go 是静态强类型，Python 是动态强类型。

                      类型系统买到四件事：安全性、编译器优化、可读性、抽象化。这里有一个反常识：

                      🔑 动态类型并没有让编程更简单。 任何语言都有类型系统，动态类型只是把检查从编译期推迟到运行期——错误还在，只是更晚发现。

                      泛型的收益也必须用数字说话。同样是对 1000 个 int64 求和，重复 100 万次（本机 go1.27.1 darwin/arm64）：

                      func sumConcrete(xs []int64) int64 { /* for 累加 */ }
func sumGeneric[T int64 | int32 | float64](xs []T) T { /* for 累加 */ }
func sumAny(xs []any) int64 {
	var s int64
	for _, v := range xs {
		s += v.(int64) // 每个元素一次类型断言
	}
	return s
}

                      具体类型 []int64     3284612    334.2 ns/op
泛型     []T         3642961    334.3 ns/op
interface{} []any    2128970    601.2 ns/op

                      完整代码在仓库 tools/examples/0.13-genbench/，go run . 可复现；基准随机器波动，多次运行大致是具体/泛型 330–360 ns、[]any 490–600 ns（比值 1.4–1.8×）。

                      读法：

                      • 泛型与具体类型同为 334 ns——Go 的泛型在编译期按类型/GC shape 实例化，没有反射式的运行时开销，"泛型一定慢"是误读；
                      • interface{} 贵 80%（601 对 334 ns）——每个元素一次类型断言，且 []any 本身要多一层装箱；
                      • 结论不是"永远用泛型"，而是：用 interface{} 换通用性，是拿 80% 的 CPU 换一行代码的类型妥协。

                      泛型的抽象阶梯：每上一级，契约多一条

                      "泛型"不是一步到位的，它是一条阶梯。以 C++ STL 的演进为例，同一个"在集合里找东西"的诉求，四级写法各自把不同的东西标准化了：

                      级 函数形态 返回值 元素类型从哪来 比较/操作从哪来 能用在
                      ① 具体 find_int(int* a, int n, int v) 下标 int 写死 int 写死 == 一种类型、一种容器
                      ② 迭代器 find(It first, It last, T v) 迭代器位置 It::value_type 写死 == 所有提供迭代器的容器
                      ③ 算法 + 操作 accumulate(first, last, init, op) 累积值 模板参数推导 由调用方传入 Op 任意类型、任意"累积"语义
                      ④ 函数对象 / 谓词 count_if(first, last, pred) 计数 同上 由调用方传入谓词 任意判定条件

                      上每一级，调用方少写一点、算法多通用一层，代价是多一条隐含契约。第 ③ 级的经典 bug 是这一行：

                      template <typename T, typename It>
T accumulate(It first, It last, T init) {
    for (; first != last; ++first) init = init + *first;
    return init;
}

// 调用方常这么写：
int sum = accumulate(v.begin(), v.end(), 0);       // 0 是 int：T 被推成 int，不是元素类型

                      0 同时假设了两件事：T 能从 0 构造，且 T 与 + 兼容。当元素是 double 时，T 被推成 int，结果被截断；当元素是自定义类型、没有"从 0 构造"时，直接编译失败。修法是把初值的类型说清楚：

                      typename It::value_type init = typename It::value_type(); // 零值构造：不假设 0，只假设"可默认构造"

                      Go 的等价写法天然规避了这个坑——var s T 拿的是 T 的零值，类型由切片元素决定，不会被"字面量 0"带偏：

                      func Sum[T int64 | int32 | float64](xs []T) T {
    var s T          // 零值，类型跟着 T 走
    for _, v := range xs { s += v }
    return s
}

                      🔑 抽象的代价不在"多写几个类型参数"，而在隐式契约：初值从哪来、零值是什么意思、单位是谁、为空时返回什么。阶梯上得越高，越要把这些契约写进文档，否则调用方每用一次就踩一次。

                      三个反常识结论

                      结论 出处 为什么重要
                      继承首先是为了多态，不是为了重用代码 OOP 那一篇 这直接解释了"组合优于继承"（0.11 原则优先于模式）：为了重用而继承，会把父类的实现细节焊死在子类里
                      函数式的"数据复制严重"不一定慢 函数式那一篇 无状态就不用锁，可以把机器堆满并发；而加锁的共享状态，延迟随核数上升
                      业务逻辑只决定复杂度的下限 编程的本质那一篇 多出来的复杂度几乎都来自 Control 没被抽走——这是"重构先抽控制逻辑"的依据

                      修饰器与委托：两个"轻"范式

                      修饰器的本质是"用一个函数构造另一个函数"；Python 的 @ 只是语法糖，等价于"传参再回调"。它真正解决的问题是把控制型代码抽出来：

                      被抽走的 Control 例子
                      循环 对每个元素执行一次
                      日志 / 计时 进出各打一条
                      路由 按 URL 分派到处理器
                      重试 / 限流 失败重来、超限拒绝

                      Go 没有语法糖，静态类型又让"修饰任意函数"很难通用，所以通常退化成两种写法：函数值显式包装（func(http.Handler) http.Handler 这种中间件），或者用 reflect 做通用装饰——后者只在写框架时值得。

                      装饰器：改的是函数值，不是函数体

                      装饰器的本质一句话：decorator(f) 返回一个新的 f'，f 一行都不改。Python 的 @ 是纯语法糖——@log def f() 等价于 f = log(f)；带参数的 @retry(times=3) 是两层：f = retry(times=3)(f)。这个"两层"结构是很多人第一次写装饰器时卡住的地方。

                      最能量化收益的例子是 memoization——同一份递归代码，套一层装饰器就从指数级退回线性级：

                      // 装饰器：接收函数，返回同签名的新函数
func memoize(f func(int) int) func(int) int {
    cache := map[int]int{}
    return func(n int) int {
        if v, ok := cache[n]; ok { return v }
        v := f(n); cache[n] = v
        return v
    }
}

// 用法一（错）：fibNaive 内部调用的是它自己，不是被装饰后的函数，cache 永远不命中
wrong := memoize(fibNaive)

// 用法二（对）：让递归调用也走被装饰后的函数（自引用）
var fib func(int) int
fib = memoize(func(k int) int {
    if k < 2 { return k }
    return fib(k-1) + fib(k-2)
})

                      本机实测（go1.27.1 darwin/arm64，fib(32)，三次运行取区间）：

                      写法 耗时 说明
                      朴素递归 25.4 – 31.1 ms 调用次数按黄金比例指数增长
                      memoize(fibNaive) 22.1 – 30.0 ms 白套：递归绕过了 cache，与朴素版同量级
                      自引用 memoize 61.9 – 106.0 µs 线性，快 250–500 倍

                      完整代码在仓库 tools/examples/0.13-genbench/，go run . 可复现。

                      ⚠️ 这个坑值得单独记：装饰器只能包住"从外部进入函数"的调用，包不住函数内部的自我调用。凡是"用装饰器给递归加缓存/加日志/加重试"的场合，都要先问一句：递归走的是哪个函数值？

                      还有两个边界：

                      你以为 实际
                      Java 的注解 @Transactional 是装饰器 注解本身只是标签，没有任何行为；真正生效靠 AOP/字节码增强在运行时织入。没有织入器，注解等于注释
                      装饰器叠加顺序无所谓 log(auth(f)) 与 auth(log(f)) 行为不同：前者先鉴权后打日志（未授权请求不留日志），后者先打日志再鉴权。顺序就是语义

                      原型与委托：对象直连，没有类

                      原型范式（JavaScript 为代表）把"分类"换成了"链接"：对象不隶属某个类，而是通过内部链接指向另一个对象，找不到属性就沿链往上找——是委托，不是分类。三个容易混的概念：

                      概念 是什么 怎么产生
                      __proto__ 对象上的内部链接（[[Prototype]]），属性查找沿着它走 Object.create(proto) 直接指定；或由 new 设置
                      prototype 函数上的一个普通属性，是个对象 声明函数时自动创建，new F() 时被拿来当实例的 __proto__
                      方法也可改 属性是"槽"（slot），方法只是值为函数的槽 运行时赋值即可替换
                      const base = { greet() { return "hi"; } };
const obj = Object.create(base);   // obj.__proto__ === base，没有类，也没有构造过程
obj.greet();                        // "hi"，沿链委托到 base

function Counter() { this.n = 0; }
Counter.prototype.inc = function () { this.n++; };
const a = new Counter();            // a.__proto__ === Counter.prototype
a.inc();                            // n = 1
Counter.prototype.inc = function () { this.n += 10; }; // 运行时换实现
a.inc();                            // n = 11：所有实例立刻改用新实现

                      代价很直接：没有静态契约。拼错方法名、传错参数类型，都要到运行时才炸；工程上的补法是 TypeScript 的类型层、Object.freeze 防篡改、以及把"可改"收敛到少数扩展点。

                      Go 的嵌入是编译期委托：把一个 struct 嵌进另一个 struct，外层就"提升"了内层的方法，但没有虚函数表、没有运行时多态——要改行为只能定义同名方法覆盖，重名还得手动消歧。委托 + 接口，就是 OOP 与原型两种玩法的综合。

                      委托落地时有个不起眼但常见的坑：撤销栈的 nil 占位。撤销时如果把元素从切片里删掉，后面记录的下标全部错位；正确做法是置 nil 占位，并顺手释放闭包：

                      type UndoStack struct{ ops []func() }

func (s *UndoStack) Do(op func()) { s.ops = append(s.ops, op) }

func (s *UndoStack) Undo() bool {
    for i := len(s.ops) - 1; i >= 0; i-- {
        if s.ops[i] == nil { continue }   // 已撤销过的位置，跳过而不是删除
        s.ops[i]()
        s.ops[i] = nil                     // 释放闭包，否则整条历史都留在内存里
        return true
    }
    return false
}

                      一个真实取舍（Undo 案例）：要给一个集合加 Undo，最直觉的做法是包一层 UndoableIntSet，把每个写方法都重写一遍记录反操作——改的是"所有方法"；更好的做法是让它内部依赖一个 Undo 接口，业务在关键点注册回调——改的是"一次注册"，控制反转了，包装层也就不需要了。判据：包装改 N 个方法，IoC 改 1 处注册。

                      逻辑编程：把求解交给机器，但要付调试成本

                      逻辑编程（Prolog）只描述事实 + 规则，然后提问，由求解器匹配与回溯。它不关心控制，也不关心算法的具体实现。

                      架构上的投影是规则引擎、风控策略、权限策略：业务方写规则，引擎负责匹配。它的边界很硬：

                      适合 不适合
                      规则少（几十条以内）、稳定、需要频繁改动 规则上千条、互相冲突、要求毫秒级确定延迟
                      判定逻辑可枚举、可解释 需要复杂计算与外部调用
                      出问题能接受"回溯爆炸" 需要可调试的确定路径

                      Prolog 的语法只有三样东西：事实（philosopher(socrates).）、规则（mortal(X) :- philosopher(X).）、提问（?- mortal(X).）。大写开头是变量、小写开头是常量、_ 是匿名变量、\= 是不等。经典例子是四色地图——只陈述"相邻区域颜色不同"和"哪些区域相邻"，染色方案由求解器搜索出来：

                      color(red). color(green). color(blue). color(yellow).
neighbor(A, B) :- color(A), color(B), A \= B.

germany(SH, MV, HH, HB, NI, ST, BE, BB, SN, NW, HE, TH, RP, SL, BW, BY) :-
    neighbor(SH, NI), neighbor(SH, HH), neighbor(SH, MV),
    neighbor(HH, NI), neighbor(MV, NI), neighbor(MV, BB),
    neighbor(NI, HB), neighbor(NI, BB), neighbor(NI, ST), neighbor(NI, TH),
    neighbor(NI, HE), neighbor(NI, NW), neighbor(ST, BB), neighbor(ST, SN),
    neighbor(ST, TH), neighbor(BB, BE), neighbor(BB, SN), neighbor(NW, HE),
    neighbor(NW, RP), neighbor(SN, TH), neighbor(SN, BY), neighbor(RP, SL),
    neighbor(RP, HE), neighbor(RP, BW), neighbor(HE, BW), neighbor(HE, TH),
    neighbor(HE, BY), neighbor(TH, BY), neighbor(BW, BY).

?- germany(SH, MV, HH, HB, NI, ST, BE, BB, SN, NW, HE, TH, RP, SL, BW, BY).

                      工程里更常见的是它的"廉价版"——有序规则表 + 首条命中即返回。Go 里二十行就够：

                      type Rule struct {
    Name  string
    Match func(order Order) bool
    Apply func(order Order) Decision
}

func Decide(rules []Rule, o Order) Decision {
    for _, r := range rules {          // 顺序即优先级：越靠前越优先
        if r.Match(o) {
            return r.Apply(o)          // 首条命中即返回，不继续匹配
        }
    }
    return Decision{Action: "review"}  // 兜底：没有规则命中就转人工
}

                      两者都要付同一笔代价：规则之间可能冲突，而且没有编译器帮你查。所以规则引擎落地必须补三件事——冲突检测（同一条件命中多条时报警）、决策表（把规则摊平成可评审的表）、审计日志（每次命中哪条、为什么）。

                      三个落地形态：状态机 / DSL / 规则引擎

                      把"Logic 与 Control 分离"落到工程上，绝大多数时候是这三种形态之一：

                      形态 抽走的是什么 Control 典型场景 判据 主场
                      状态机 合法的状态迁移（什么时候能从 A 到 B） 订单、工单、审批、支付 状态数有限、迁移条件能枚举 83.4 时序图与状态图
                      DSL / 文法 格式与语法的解析 配置、协议、查询、模板 格式会长出新分支、有嵌套 0.14 文本处理范式
                      规则引擎 匹配与判定 风控、定价、权限、路由 规则频繁改动、由业务方维护 本节

                      三者的共同点是：把"变化的那部分"从代码里搬到数据里。状态机的迁移表、DSL 的文法、规则引擎的规则集，都是数据；代码只留"执行器"。代价也一样——数据里的错误没有编译期检查，必须靠校验、测试与审计补回来。

                      范式怎么选：学习曲线 × 复用率

                      范式争论最后都会落到一个很朴素的权衡上：

                      范式 学习曲线 代码复用率 采用门槛 适合的层级
                      过程式 平缓 低（复制粘贴为主） 无 脚本、一次性任务
                      面向对象 中等 中（接口 + 组合） 需要设计能力 业务主体
                      泛型 中等偏陡 高（算法与类型解耦） 需要理解类型约束 容器、算法、基础设施
                      函数式 陡（无状态、不可变、组合子） 高（组合代替步骤） 团队要改思维方式 数据管道、并发、事件处理
                      原型 平缓 中（链上复用） 无 前端、需要运行时灵活的场合
                      逻辑 陡（声明式、回溯调试） 高（规则即数据） 需要可解释性与调试工具 规则引擎、策略

                      结论有两层：

                      1. 越声明式的范式，学习曲线越陡，采用率越低——这是工程现实，不是品味问题。团队不熟的语言特性会变成维护成本，最终抵消它带来的复用收益。
                      2. 折中做法是分层使用：业务主干（Logic）用团队最熟的命令式/OOP，把声明式的部分收敛到 Control 层（流处理、规则表、状态机）。这样"陡"的部分被限制在少数几个组件里，而不是扩散到全部业务代码。

                      反模式

                      反模式 后果
                      把范式当宗教（"必须 OOP"/"必须函数式"） 团队为此付出学习与维护成本，业务没变好
                      业务代码里手写重试/并发/事务（Control 不上浮） 同一套逻辑实现 N 遍，行为不一致，改一处漏九处
                      为了"通用"过早泛型化 约束写半天，调用方还要理解类型参数，收益为 0
                      继承复用代码（而不是为了多态） 父类实现一改，所有子类跟着坏
                      用 interface{} 换"通用" 本机实测慢 80%，类型安全也没了
                      用异常/回调做控制流 正常路径被错误处理打散，调试困难
                      规则引擎装下所有业务逻辑 规则冲突无法静态检查，出问题只能靠日志回溯
                      用装饰器给递归加缓存/重试 递归调用绕过了被装饰的函数值，cache 永不命中（本机实测与朴素版同量级）
                      把 Java 注解当装饰器 注解只是标签，没有织入器就什么也不做
                      泛型初值写成字面量 0 / "" 同时假设了"能从 0 构造"和"与 + 兼容"，元素类型一变就截断或编译失败
                      撤销/回放用"删除元素"实现 后续下标全部错位；应置空占位并释放引用
                      用规则表却不做冲突检测与审计 规则一多就互相覆盖，出问题只能靠日志回溯

                      自检

                      Q1 Logic、Control、Data 各指什么？为什么说"业务逻辑只决定复杂度的下限"？

                      ▸ 答案：Logic = 做什么（业务语义），Control = 怎么做（遍历/并发/重试/事务/调度），Data = 操作的对象。业务本身有多复杂是客观的（下限），但你怎么组织控制流、有没有把控制逻辑重复实现 N 遍，决定了在此之上再加多少复杂度。所以"抽 Control"是降复杂度的主要手段。

                      Q2 为什么 Control 可以标准化，Logic 不能？

                      ▸ 答案：Control（遍历、重试、超时、事务）与业务语义无关，输入输出形态固定，所以能做成库/框架/中间件；Logic 每个业务都不同，一旦试图做成通用配置，就会变成"配置里写代码"的泥潭。判断标准：这段代码换个业务还成立吗？成立就是 Control。

                      Q3 泛型的本质是什么？迭代器为什么是"最小契约"？

                      ▸ 答案：泛型的本质是标准化——把类型的内存分配/释放/访问、类型的操作、容器操作、类型特有操作标准化。迭代器把这四件事压到最小：* 取值、++ 前进、==/!= 判边界、value_type 告诉算法元素类型。算法只依赖这几个符号，就能用于所有容器——解耦靠的是最小公共协议，不是继承体系。

                      Q4 "继承首先是为了多态"，这句话怎么推出"组合优于继承"？

                      ▸ 答案：如果继承的目的是多态（让调用方面向接口），那么"复用父类实现"就只是副产品；一旦为了复用而继承，子类就绑定了父类的实现细节，父类一改全体受影响。组合把"复用"和"多态"分开：能力用组合拿到，多态用接口表达——两者不再互相牵连。

                      Q5 同一个求和，泛型 334.3 ns、interface{} 601.2 ns。为什么泛型没有变慢？

                      ▸ 答案：Go 的泛型在编译期按实际类型实例化（单态化/GC shape 共享），生成的机器码与手写具体类型几乎一致，所以 334.2 与 334.3 没有差别；interface{} 则要为每个元素做接口调用 + 类型断言，还多一层装箱，成本落在每次循环里。

                      Q6 装饰器为什么"改了函数却不用改函数体"？递归 + 装饰器最容易踩什么坑？

                      ▸ 答案：装饰器的输入是函数值、输出是新的函数值，原函数的字节码一行没动，所以不用改函数体。坑在递归：函数体内部调用的是它自己的名字，指向的是原函数而不是装饰后的函数，于是缓存/日志/重试全部被绕过。本机实测 memoize(fibNaive) 与朴素递归同为 20–30 ms，只有把递归也写成自引用（var fib func(int) int; fib = memoize(...)）才降到 60–106 µs。

                      Q7 泛型抽象阶梯上，最容易被忽略的隐含契约是什么？

                      ▸ 答案：初值与零值。accumulate(first, last, 0) 里的 0 同时假设了"元素类型能从 0 构造"和"0 与 + 兼容"，元素换成 double 就截断；typename It::value_type() 与 Go 的 var s T 都是把这条契约显式化。同类隐含契约还有：单位、为空时的返回、错误如何表达。

                      Q8 什么时候该引入函数式或逻辑编程？

                      ▸ 答案：三种情况。① 团队不熟：范式带来的抽象收益 < 学习与维护成本；② 规模太小：一个 if-else 或一个 for 就能说清，用管道/组合反而绕；③ 需要确定路径与毫秒级延迟：逻辑编程的回溯、函数式的惰性求值都可能让性能不可预测。判据回到第一条——控制逻辑是否真的被标准化了，没有就别为了范式而范式。
