# 0.15 正则的代价：回溯、ReDoS 与可终止性

## 一句话

> 正则不是「又快又便宜的字符串工具」：主流的 NFA 引擎在**量词与多选分支**处回溯，一条写错的表达式配一段 28 字符的输入，就能让单核跑满 16 秒——这是**输入驱动的算法复杂度**，必须按「输入可不可控」分别设防。

**来源**：NFA/DFA 引擎差异与回溯机制、八条优化建议来自涂伟忠《正则表达式入门课》（极客时间，2020）第 2、11 讲；指数级耗时的实测与「输入可控性」判据为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “正则很快，随便用” | 快的是平均情况。最坏情况可以是指数级，而且**输入长度根本不用长**：28 个字符就能把耗时放大到 16 秒 |
| “限制了输入长度就安全” | 长度只把爆炸推后几步。`(a+)+$` 每多两个字符耗时乘 4，长度上限设 100 只是让单次请求从 16 秒变成天文数字 |
| “换成 RE2 就万事大吉” | RE2 确实线性时间、无回溯，但它只支持正则的一个子集：**不支持反向引用**，部分断言也不支持；迁移前要确认现有表达式没用到 |
| “这种写法不会出现在生产（看起来像玩具）” | 真正危险的是长得正常的表达式：`^(\w+\s?)*$`、`(.*)*`、多层嵌套的可选组，都是校验里顺手就会写出来的形状 |

## 代价从哪来：两类引擎，两种复杂度

| 引擎 | 工作方式 | 最坏复杂度 | 功能 |
|---|---|---|---|
| **DFA**（确定性有穷自动机） | 以**文本**为主导：读一个字符、推进一次状态 | 线性 `O(n)` | 子集受限（通常不支持反向引用/捕获语义的完整行为） |
| **传统 NFA**（多数语言默认） | 以**正则**为主导：拿表达式去试文本，失败就退回去换一种走法 | **指数 `O(2ⁿ)`** | 功能最全（分支、捕获、反向引用） |
| **POSIX NFA** | 同 NFA，但要找「最左最长」匹配，会继续回溯 | 指数，且比传统 NFA 更慢 | 少数 Unix 工具 |

> 🔑 关键区别只有一句：**NFA 会「试错再退回」，DFA 不会。** 回溯是 NFA 的灵活性的代价，也是性能灾难的来源。

传统 NFA 还有一个容易踩的语义：它**急于返回第一个匹配**。正则 `pos|posix` 去匹配文本 `posix`，传统 NFA 返回 `pos`（最左分支优先），POSIX NFA 才返回 `posix`。所以写分支时，**左边放什么会改变结果**，不只是性能问题。

## 回溯只在两类结构上发生

1. **量词**：`*`、`+`、`?`、`{m,n}`
2. **多选分支**：`a|b|c`

没有这两样，正则基本是线性的。有了它们，引擎就可能「先吞下全部、再一个个吐出来重试」。

最小例子：正则 `a+ab` 匹配 `aab`。`a+` 贪婪地吃掉两个 `a`，接着正则还要求一个 `a`，但文本只剩 `b`——只能让 `a+` **吐出一个 `a`**，再试一次。

灾难版本：`(a+)+$`。外层组可以重复，组内 `a+` 又可以重复，两种切分方式让引擎在失配时枚举**所有可能的切分组合**，复杂度 `2ⁿ`。`.*ab` 是同一个病：`.*` 先吃掉整段，再一个字符一个字符吐出来。

涂伟忠《正则表达式入门课》里有一个能说明问题的实测：一段很短的店铺名文本，用带重复元素的多选分支匹配，引擎尝试了 **9021 次**；把分支里重复的字符类去掉后，只尝试了 **57 次**——同一个语义，差了两个数量级。

## 可运行：把指数爆炸测出来

```python
#!/usr/bin/env python3
"""re_cost.py —— 同一段输入，三种写法的实际耗时（度量「回溯」的代价）。

每次匹配加 20 秒看门狗，防止某一行把整台机器拖住。
"""
import re
import signal
import time

PATTERNS = [
    ("嵌套量词 (a+)+$", r"(a+)+$"),
    ("原子组 (?>a+)+$", r"(?>a+)+$"),
    ("线性   a+$", r"a+$"),
]

class TooSlow(Exception):
    pass

def on_alarm(signum, frame):
    raise TooSlow

signal.signal(signal.SIGALRM, on_alarm)

print(f"{'输入长度':>8}" + "".join(f"{name:>20}" for name, _ in PATTERNS))
for n in (16, 20, 24, 26, 28):
    text = "a" * n + "!"          # 结尾加感叹号：必然失配，逼出全部回溯
    cells = []
    for name, pat in PATTERNS:
        rx = re.compile(pat)
        signal.setitimer(signal.ITIMER_REAL, 20.0)
        t0 = time.perf_counter()
        try:
            rx.match(text)
            cells.append(f"{(time.perf_counter() - t0) * 1000:>17.2f}ms")
        except TooSlow:
            cells.append(f"{'>20s':>19}")
        finally:
            signal.setitimer(signal.ITIMER_REAL, 0)
    print(f"{n:>8}" + "".join(cells))
```

**本机实测输出**（Python 3.14.8，macOS arm64）：

```text
    输入长度         嵌套量词 (a+)+$        原子组 (?>a+)+$            线性   a+$
      16             3.71ms             0.00ms             0.00ms
      20            67.82ms             0.00ms             0.00ms
      24          1160.31ms             0.01ms             0.00ms
      26          4221.69ms             0.05ms             0.00ms
      28         16332.24ms             0.04ms             0.00ms
```

三条读法：

1. **每多两个字符，耗时约 ×4**（3.71 → 67.82 → 1160 → 4221 → 16332 ms），这就是 `2ⁿ` 的形状。它不是“慢一点”，而是**多两个字符就翻一倍**。
2. **同一段输入，原子组快四个数量级**（16.3 s vs 0.04 ms）。`(?>a+)+` 的 `?>` 告诉引擎「这里不要吐回来」，从源头砍掉了回溯。
3. **`a+$` 一直是 0.00ms**：没有嵌套量词就没有组合爆炸。**复杂度是写法带来的，不是正则本身的。**

> ⚠️ 一个真实含义：如果这段正则跑在网关或校验层，攻击者只需要给你发 28 个 `a` 加一个 `!`，就能占满一个核 16 秒；并发几十个请求，服务就没了。这就是 **ReDoS**（Regular Expression Denial of Service）。

## 四种修法，按代价从低到高

| 手段 | 做法 | 代价 / 限制 |
|---|---|---|
| **① 精确化写法** | `.*` 换成 `[^"]+`；避免嵌套量词 `(a+)+`；分支去掉重复元素、提取公共前缀（`(abcd|abxy)` → `ab(cd|xy)`）；高概率分支放左边 | 只在**你能改表达式**且改得对时有效，需要理解语义 |
| **② 原子组 / 占有量词** | `(?>…)` 或 `a++`：匹配上就不吐回 | 会改变语义（某些本该匹配的会失败）；Python 3.11+、PCRE、Java、Perl 支持，JS 旧环境不支持 |
| **③ 换引擎** | 用 RE2（Go 标准库 `regexp` 就是它）或 Rust 的 `regex`：无回溯、线性时间 | 功能子集：不支持反向引用、部分断言；迁移要逐个验证表达式 |
| **④ 边界设防** | 输入长度上限 + 字符集白名单 + 超时（Python `regex` 的 `timeout`、Java 的中断、或进程隔离）+ 网关层兜底 | 只能降低影响面，不能修正错的表达式；超时机制不是所有语言都有 |

四条不是互斥的：**能改表达式就改（①），改不动就换引擎或加超时（③④），改完用 ② 兜底**。

另外三条工程侧的优化，来自《正则表达式入门课》第 11 讲总结，成本都极低：

1. **预编译**：`re.compile` 之后复用，不要每次调用都重新构造自动机。
2. **只在必要时用捕获组**：不给后续使用就不要捕获，用 `(?:…)`；捕获组要额外保存内容，会拖慢匹配。
3. **先测再优化**：用 `timeit` 或 regex101 的 debugger 看尝试次数，别凭感觉。

## 判据：输入可不可控，决定你能写多“野”的正则

| 输入来源 | 可控性 | 允许的正则 | 必须加的防线 |
|---|---|---|---|
| 用户输入、URL、Header、日志内容、搜索词 | **不可控** | 保守子集：无嵌套量词、无 `.*` 套 `.*` | 长度上限 + RE2/超时 + 拒绝复杂回溯 |
| 配置、自有常量、内部枚举 | 可控 | 常规写法 | 预编译 |
| 内部生成的结构化串（有 schema） | 可控 | 常规写法 | 长度上限即可 |
| 第三方回调/开放接口 | **不可控** | 与用户输入同标准 | 同用户输入 |

> 🔑 判据一句话：**只有当输入完全由你生成时，才允许写“会回溯的正则”。** 其余情况，要么换线性引擎，要么保证表达式不会产生组合爆炸。

## 与 0.14 的分工

- [0.14 文本处理范式](0.14-文本处理范式.md) 回答「**该不该用正则**」：格式会长出新分支、有嵌套结构，就上文法（词法 → 语法 → 语义）。
- 本节回答「**既然用了正则，怎么保证它不炸**」：控制回溯、选对引擎、在边界设防。

两节的判断可以串起来用：先问“要不要文法”，再问“这条正则的最坏复杂度是多少”。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 `(.*)*` / `(a+)+` 这类嵌套量词 | 输入一长就指数爆炸，单请求可打满 CPU |
| 多选分支里写重复元素（`(A-Za-z\|A-Za-z0-9)`） | 尝试次数放大到几千次，同语义表达式只要几十次 |
| 用 `.*` 代替精确字符类 | 贪婪吞掉全文再逐个吐出，回溯量随文本长度线性累加 |
| 在网关/校验层对用户输入跑复杂正则 | ReDoS：28 个字符即可拖住一个核 16 秒 |
| 每次请求都重新编译正则 | 白付自动机构造成本，高频路径上放大明显 |
| 盲信“换 RE2 就安全” | 现有表达式用到反向引用/断言时直接失效，或用不了而回退 |
| 用长度限制当唯一防线 | 只把爆炸点推后几步，长度上限内的最坏情况仍然致命 |

## 自检

**Q1** 为什么 `(a+)+$` 是指数级，而 `a+$` 是线性的？两者差的到底是什么？

▸ 答案：差在**切分方式的数量**。`a+$` 对一段 `a` 只有一种匹配方式（全吃）；`(a+)+` 允许把同一串 `a` 切成任意多个组，每组任意长，失配时要枚举所有切分组合——数量是 `2ⁿ`。回溯的本质是“枚举备选路径”，路径数决定了复杂度。

**Q2** 输入长度上限设成 64 字节，能防住 ReDoS 吗？

▸ 答案：不能，只能把爆炸点推后。按本节实测，每两个字符 ×4，28 字符已经 16 秒；64 字符在最坏情况下是天文数字。长度限制的价值在于**降低最坏情况的量级**，并与引擎/超时配合使用，不能单独作为防线。

**Q3** 团队把正则从 Python `re` 换成 Go `regexp`，为什么可能“更安全但功能变少”？

▸ 答案：Go 的 `regexp` 基于 RE2，无回溯、线性时间，因此天然免疫 ReDoS；代价是它只支持正则的子集——不支持反向引用，部分 lookaround 也不支持。迁移时必须逐条验证表达式，否则会出现“跑得快了但匹配不上”的静默错误。

**Q4** `(?>a+)+$` 为什么能把 16 秒变成 0.04 毫秒？代价是什么？

▸ 答案：`?>` 是原子组，匹配成功后**不吐回**字符，于是引擎不再枚举切分组合，直接失败返回（实测 16 s → 0.04 ms）。代价是语义变化：那些“本该通过回溯才能匹配”的字符串会匹配失败。所以它只能用在“确定不需要回溯”的位置。

**Q5** 一段正则写得又长又乱，但测试用例都过了。还要不要管它的复杂度？

▸ 答案：要。测试用例覆盖的是**正确性**，不是**最坏输入**。复杂度要看结构：有没有嵌套量词、有没有 `.*` 套量词、分支之间有没有重复元素。结构有问题，任何测试都测不出灾难输入，因为灾难输入恰好是你没写的那个用例。

**Q6** 网关要对 200 条路径规则做正则匹配，应该怎么设防？

▸ 答案：三件事——① 预编译成自动机，别每次请求重新构造；② 路径规则只用保守子集（避免 `.*` 与嵌套量词），或改用前缀树/精确匹配；③ 对路径长度设上限，并在网关层对异常匹配耗时做熔断。参见 [47.3 路由与灰度](../../L4-组件与技术/47-网关与入口/47.3-路由与灰度.md)。

**Q7** 为什么说“回溯次数”比“耗时”更适合用来评估正则的性能？

▸ 答案：耗时受机器、负载、缓存影响，不同环境不可比；回溯次数是表达式与输入的函数，换台机器也一样。regex101 的 debugger、《正则表达式入门课》里“9021 次 → 57 次”的对比，用的都是尝试次数——它才是可移植的判据。

**Q8** 一条正则要解析“带嵌套引号的表达式”，既慢又难维护。这时候该优化正则，还是换方案？

▸ 答案：换方案。嵌套结构意味着需要**文法**（词法 → 语法 → 语义），正则既表达不了，也无法保证复杂度。判据是 [0.14 文本处理范式](0.14-文本处理范式.md) 的那句：格式会不会长出新分支、有没有嵌套——有，就上文法。
