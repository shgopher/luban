# 0.2 数据结构选型：数组、链表、哈希、树、堆、跳表

## 一句话

> 选型不看 “谁的复杂度数字更小”，看三件事：访问模式（顺序 / 随机 / 范围）、每元素的内存与 GC 成本、以及是否有并发与有序要求；落到 Go 上是三句话——**能连续就不指针，能预分配就不追加，要范围就上树或跳表而不是 map**。

## Go 里能直接用的只有五种，其余自己写

| 结构 | Go 实现 | 查找 | 插入 | 删除 | 有序遍历 | 内存/元素（1e6 条实测） | 缓存友好 |
|---|---|---|---|---|---|---|---|
| slice | `[]T` 连续数组 + 扩容 | 无序 O(n)；有序可二分 O(log n) | 尾部均摊 O(1)；中间 O(n) | O(n) | ✅ 排序后 | 16 B | ✅✅ |
| map | `hmap` + 8 槽 bucket | 均摊 O(1) | 均摊 O(1) | O(1) | ❌ 遍历顺序随机 | 37.8 B | ⚠️ |
| container/list | 双向链表，每元素一次分配 | O(n) | O(1) | O(1) | ✅ 插入序 | 64 B | ❌ |
| container/heap | 二叉堆，底层是 slice | 只看堆顶 O(1) | O(log n) | 取顶 O(log n) | ❌ 只有堆序 | 16 B + 底层数组 | ✅ |
| 跳表 | 无标准库（Redis zset 用它） | O(log n) | O(log n) | O(log n) | ✅ | ~1.33 指针/元素（p=0.25） | ⚠️ |
| 环形缓冲 | `[]T` + head/tail，手写 | O(n) | O(1) | O(1) | ✅ FIFO 序 | 16 B | ✅✅ |

内存那一列是本机 1e6 条 `{id, score}`（两个 int）的堆增量：slice 16.0 MB、list 64.0 MB、map[int]int 37.8 MB。**同一份数据，容器换一下内存差 4 倍。**

> 🔑 标准库里没有 “有序 map”。Go 的 map 遍历顺序是随机的（运行时故意打散），要按 key 有序遍历只能自己维护有序结构，或者取出 key 排序后回查。

## 链表在 Go 里为什么基本不用

1e6 元素的实测（3 次取中位）：

| 操作 | 耗时 | 折算每次 | 额外分配 |
|---|---|---|---|
| `[]item` 顺序求和 | 494 438 ns | 0.49 ns/元素 | 0 |
| `container/list` 遍历求和 | 1 936 330 ns | 1.94 ns/元素（**3.9×**） | 0 |
| 环形缓冲 push + pop 1e6 次 | 3 155 796 ns | 3.2 ns/对 | 0 |
| `container/list` push + pop 1e6 次 | 39 121 069 ns | 39.1 ns/对（**12.4×**） | 2 000 000 次分配，64.0 MB |

三个原因，都能量化：

1. **内存 4 倍**：`Element` 是 next + prev 两个指针（16 B）+ `Value any`（16 B）= 32 B，分配器 size class 取整到 48 B；`Value` 里装的 `item` 只有 16 B，但装箱到堆又要一块，合计 64 B/元素。slice 是纯数据 16 B，没有每元素头部、没有装箱。
2. **每次入队一次分配、出队一次回收**：1e6 次 push/pop 就是 200 万次分配。GC 的标记成本跟**活对象数**成正比，不是跟字节数。
3. **指针追逐**：下一个节点地址要从当前节点里读出来，CPU 无法预取。本机测到的 1.94 ns/元素还是**最好的情况**——测试里按顺序 `PushBack`，分配器把节点连续放下去了；真实业务反复增删后节点散落在堆里，每次跳转就是一次随机访存（量级 100 ns），差两个数量级。

> 🔑 需要 FIFO 就用环形缓冲或 `[]T` 双端索引。**链表只在 “已持有节点指针 + O(1) 摘除” 这个极窄场景里赢**，而 `container/list` 连这个场景都要先遍历找节点。

替代方案：

| 你以为需要链表 | 实际该用 | 为什么 |
|---|---|---|
| 有界 FIFO 队列 | 环形缓冲（`[]T` + head/tail） | 零分配、内存连续，实测快 12.4 倍 |
| 无界队列 | `[]T` + 定期整理；或分块链表（每节点存 64 个元素） | 保持连续，扩容仍均摊 O(1) |
| LRU（O(1) 命中 + 淘汰） | map + 双向链表（这里用 `container/list` 合理） | 需要 “已持有节点指针 + O(1) 摘除”，这是链表唯一主场（[41.5 淘汰策略与 TTL](../../L4-组件与技术/41-缓存/41.5-淘汰策略与TTL.md)） |
| 频繁中间插入的有序表 | 跳表 / 分块 / B+ 树 | 链表插入 O(1)，但要先 O(n) 找到位置 |

## 堆：Top-K、定时器、优先级队列

Top-100 / 1e6 条数据：

| 方案 | 耗时 | 额外内存 | 复杂度 |
|---|---|---|---|
| 最小堆（`container/heap`，堆顶是 Top-K 里最小的） | 0.76 ms | O(K) = 100 条 | O(n log K) |
| 全量排序（`sort.Slice` 后取前 100） | 182.89 ms | O(n) = 1e6 条（先拷一份） | O(n log n) |

**240 倍**，不是复杂度比值那 3 倍。拆开看两层：

- 比较次数：全量排序约 1e6 × 20 = 2e7 次；堆只做 1e6 次比较 + 约 900 次下沉（`log(1e6/100) × 100`）。约 20 倍。
- 单次比较的单价：堆里 1e6 次比较只花 0.76 ms → **0.76 ns/次**；`sort.Slice` 的 `Less` 是 `func(i, j int) bool` 闭包，比较走函数调用 → 2e7 次花 182.89 ms → **9.1 ns/次**。12 倍。

20 × 12 ≈ 240。**“换算法” 和 “换实现” 各占一半**，只做一件只能拿到 1/12 到 1/20。

定时器与延迟队列是堆的另一个主场：

- 最小堆按 “到期时间” 排，取最近到期 O(1)、插入 O(log n)。
- 但**删除任意一个定时器是 O(n)**（要先在堆里找到它）。所以生产实现要么配 `map[taskID]heapIndex` 记位置（删除时 swap 到末尾再 `heap.Fix`，O(log n)），要么用时间轮（插入/删除 O(1)，精度按槽位取整）。Go 运行时自己的定时器就是按 P 维护小顶堆。

百万级延迟消息的取舍见 [43.7 延迟消息与定时消息](../../L4-组件与技术/43-消息队列/43.7-延迟消息与定时消息.md)：最小堆精度到毫秒、但删除要补索引；时间轮插入删除 O(1)、精度按槽位取整。

> 🔑 堆只保证 “堆顶最优”，不保证全序。要 Top-K 用堆，要全序用排序；**别遍历堆的底层 slice 当有序结果用**，那是堆序，不是有序。

## 跳表 vs 平衡树：差在实现复杂度与并发

| 维度 | 跳表 | 红黑树 | B+ 树 |
|---|---|---|---|
| 单点查找 | O(log n) | O(log n) | O(log n)，树高 3–4 |
| 范围查询 | ✅ 底层有序链表顺序扫 | ✅ 中序后继 | ✅ 叶子链表 + 页内有序 |
| 实现难度 | 低（随机层高，无旋转） | 高（旋转 + 变色） | 中高（分裂合并、页管理） |
| 并发改造 | 改局部指针 + CAS，可做无锁 | 旋转牵动多节点，要锁整条路径 | 页锁 / 闩，粒度细 |
| 内存开销 | ~1.33 指针/元素（p=0.25） | 2 指针 + 1 bit 颜色 | 页填充率 70% 左右 |
| 谁在用 | Redis zset、LevelDB memtable | Java TreeMap、C++ std::map | InnoDB、PostgreSQL |

Redis 选跳表做 zset 的三个理由：范围查询要顺序扫（跳表底层就是链表）、实现比红黑树短、每层存 span 还能 O(log n) 算排名。代价是内存：p=0.25 时平均每个元素 1.33 个指针。

> 🔑 树和跳表是客场（存储引擎主场见 [44.1 存储引擎：B+ 树与 LSM 树](../../L4-组件与技术/44-数据库/44.1-存储引擎B+树与LSM.md)）：**内存里要范围查询 → 跳表；磁盘上要范围查询 → B+ 树；只要等值 → 哈希表。**

## 并发：map 的报错不能 recover

- `map` 并发读写会触发 `fatal error: concurrent map read and map write` / `concurrent map writes`。这是 runtime 的 `throw`，**不是 panic**，`recover` 不住，进程直接退出。
- 更麻烦的是**检测是尽力而为**：靠 `hmap` 里的 `hashWriting` 写标志位，竞态窗口没撞上就不报错，只把 bucket 写坏。表现是 “数据莫名丢失 / 串号”，比崩溃难查十倍。
- 三个可用方案，见 [15.6 并发原语 (channel / context / sync)](../../L0-运行时底座/15-语言运行时/15.6-并发原语.md)：

| 场景 | 选 | 理由 |
|---|---|---|
| 读多写少，key 会增删 | `sync.RWMutex` + 普通 map | 写独占、读并发，实现最直白 |
| key 一次写入、之后只读（路由表 / 配置） | `sync.Map` | 读路径无锁，写走 dirty map |
| 高并发写、热点分散 | 分片 map（N=32 或 64 个带锁小 map） | 锁竞争降到 1/N，内存略增 |
| 只是计数 | `sync/atomic` 或分片计数 | 连锁和哈希都省了 |

## 实测代码与输出

环境：go1.27.1 darwin/arm64，Apple M1，macOS。代码在 `/tmp/luban-a/b02`。

内存与 Top-K（`main.go`）：

```go
package main

import (
	"container/heap"
	"container/list"
	"fmt"
	"math/rand"
	"runtime"
	"sort"
	"time"
)

type item struct {
	id    int
	score int
}

// minHeap 是「大小为 K 的最小堆」：堆顶是 Top-K 里分数最小的那个。
// 新元素只要比堆顶大，就替换堆顶再下沉。内存 O(K)，不是 O(n)。
type minHeap []item

func (h minHeap) Len() int           { return len(h) }
func (h minHeap) Less(i, j int) bool { return h[i].score < h[j].score }
func (h minHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *minHeap) Push(x any)        { *h = append(*h, x.(item)) }
func (h *minHeap) Pop() any {
	old := *h
	n := len(old)
	it := old[n-1]
	*h = old[:n-1]
	return it
}

// topKHeap：只维护 K 个元素，复杂度 O(n log K)，额外内存 O(K)。
func topKHeap(data []item, k int) []item {
	h := make(minHeap, 0, k)
	for _, it := range data {
		switch {
		case h.Len() < k:
			heap.Push(&h, it)
		case it.score > h[0].score:
			h[0] = it // 直接覆盖堆顶，比 Pop+Push 少一次交换
			heap.Fix(&h, 0)
		}
	}
	out := make([]item, h.Len())
	for i := len(out) - 1; i >= 0; i-- { // 反复取最小值，倒着填 → 从大到小
		out[i] = heap.Pop(&h).(item)
	}
	return out
}

// topKSort：全量排序后取前 K，复杂度 O(n log n)，额外内存 O(n)。
func topKSort(data []item, k int) []item {
	cp := append([]item(nil), data...)
	sort.Slice(cp, func(i, j int) bool { return cp[i].score > cp[j].score })
	return cp[:k]
}

var keep any

// heapBytes 测构建阶段新增的堆内存。GC 后再读 MemStats，避免把垃圾算进去。
func heapBytes(f func() any) float64 {
	runtime.GC()
	var a, b runtime.MemStats
	runtime.ReadMemStats(&a)
	keep = f() // 必须持有引用，否则会被下一轮 GC 回收
	runtime.ReadMemStats(&b)
	return float64(b.HeapAlloc-a.HeapAlloc) / 1e6
}

func minOf(f func()) time.Duration {
	best := time.Duration(1 << 62)
	for i := 0; i < 5; i++ {
		t0 := time.Now()
		f()
		if d := time.Since(t0); d < best {
			best = d
		}
	}
	return best
}

const n = 1_000_000

func main() {
	fmt.Println("go1.27.1 darwin/arm64 / Apple M1")
	fmt.Println()
	fmt.Println("== ① 100 万条 {id,score}：三种容器的堆内存与遍历耗时 ==")
	fmt.Printf("%-28s %10s %14s %12s\n", "容器", "堆内存 MB", "B/元素", "遍历 100 万 ns")
	mb := heapBytes(func() any {
		s := make([]item, n)
		for i := range s {
			s[i] = item{i, i * 7919 % 100003}
		}
		return s
	})
	fmt.Printf("%-28s %10.1f %14.1f %12s\n", "[]item（连续内存）", mb, mb*1e6/n, "见 bench ②")

	var listData *list.List
	mb = heapBytes(func() any {
		l := list.New()
		for i := 0; i < n; i++ {
			l.PushBack(item{i, i * 7919 % 100003})
		}
		listData = l
		return l
	})
	fmt.Printf("%-28s %10.1f %14.1f %12s\n", "container/list（每元素一块）", mb, mb*1e6/n, "见 bench ②")

	mb = heapBytes(func() any {
		mm := make(map[int]int, n)
		for i := 0; i < n; i++ {
			mm[i] = i
		}
		return mm
	})
	fmt.Printf("%-28s %10.1f %14.1f %12s\n", "map[int]int（hmap）", mb, mb*1e6/n, "见 bench ②")

	_ = listData

	fmt.Println()
	fmt.Println("== ② Top-100 / 100 万：最小堆 vs 全量排序 ==")
	data := make([]item, n)
	r := rand.New(rand.NewSource(42))
	for i := range data {
		data[i] = item{i, r.Intn(1_000_000)}
	}
	var hk, sk []item
	th := minOf(func() { hk = topKHeap(data, 100) })
	ts := minOf(func() { sk = topKSort(data, 100) })
	// 分数有并列，id 不必相同；只校验 Top-100 的分数序列一致
	same := true
	for i := range hk {
		if hk[i].score != sk[i].score {
			same = false
			break
		}
	}
	fmt.Printf("最小堆   O(n log K)：%8.2f ms，额外内存 O(K)=%d 条\n", float64(th.Nanoseconds())/1e6, 100)
	fmt.Printf("全量排序 O(n log n)：%8.2f ms，额外内存 O(n)=%d 条（拷贝一份）\n", float64(ts.Nanoseconds())/1e6, n)
	fmt.Printf("两者 Top-100 完全一致：%v；堆法快 %.1f 倍\n", same, float64(ts)/float64(th))
	fmt.Printf("Top-1 分数=%d，Top-100 分数=%d（第 100 名比第 1 名低 %d）\n",
		hk[0].score, hk[99].score, hk[0].score-hk[99].score)
}
```

遍历与队列的 benchmark（`bench_test.go`，用 `-count 3` 跑，下表取中位）：

```go
package main

import (
	"container/list"
	"testing"
)

var (
	benchSlice []item
	benchList  *list.List
	benchMap   map[int]int
	benchSum   int
	benchHit   int
)

const N = 1_000_000

func init() {
	benchSlice = make([]item, N)
	for i := range benchSlice {
		benchSlice[i] = item{i, i * 7919 % 100003}
	}
	benchList = list.New()
	for i := 0; i < N; i++ {
		benchList.PushBack(item{i, i * 7919 % 100003})
	}
	benchMap = make(map[int]int, N)
	for i := 0; i < N; i++ {
		benchMap[i] = i
	}
}

// 顺序遍历：每个元素都在同一块连续内存里，预取器能一路顺推。
func BenchmarkSliceSum1e6(b *testing.B) {
	b.ReportAllocs()
	s := 0
	for i := 0; i < b.N; i++ {
		for _, v := range benchSlice {
			s += v.score
		}
	}
	benchSum = s
}

// 链表遍历：每个 element 是一次独立分配，next 指针指向哪块内存不可预测。
func BenchmarkListSum1e6(b *testing.B) {
	b.ReportAllocs()
	s := 0
	for i := 0; i < b.N; i++ {
		for e := benchList.Front(); e != nil; e = e.Next() {
			s += e.Value.(item).score
		}
	}
	benchSum = s
}

// map 查 100 万次：每次一次哈希 + 一个桶内比较，指针跳 1–2 次。
func BenchmarkMapLookup1e6(b *testing.B) {
	b.ReportAllocs()
	hits := 0
	for i := 0; i < b.N; i++ {
		for j := 0; j < N; j++ {
			if _, ok := benchMap[j]; ok {
				hits++
			}
		}
	}
	benchHit = hits
}

// 环形缓冲：固定容量数组 + 头尾下标，不用分配就能当队列用。
func BenchmarkRingPushPop1e6(b *testing.B) {
	b.ReportAllocs()
	const cap = 1024
	buf := make([]item, cap)
	head, tail := 0, 0
	total := 0
	for i := 0; i < b.N; i++ {
		for j := 0; j < N; j++ {
			if (tail+1)%cap != head { // 留一个空位区分满/空
				buf[tail] = item{j, j}
				tail = (tail + 1) % cap
			}
			if head != tail {
				total += buf[head].score
				head = (head + 1) % cap
			}
		}
	}
	benchSum = total
}

// 同样的队列语义，用 container/list：每次入队一次分配，出队一次释放。
func BenchmarkListPushPop1e6(b *testing.B) {
	b.ReportAllocs()
	l := list.New()
	total := 0
	for i := 0; i < b.N; i++ {
		for j := 0; j < N; j++ {
			if l.Len() < 1024 {
				l.PushBack(item{j, j})
			}
			if e := l.Front(); e != nil {
				total += e.Value.(item).score
				l.Remove(e)
			}
		}
	}
	benchSum = total
}
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 默认用 `container/list` 当队列 | 每个元素一次分配、64 B 内存、遍历慢 3.9 倍，队列操作慢 12.4 倍 |
| 把 map 当有序集合用（要范围时遍历再排序） | 每次查询都要取出全部 key 排序，O(n log n) 换掉本该 O(log n) 的范围扫 |
| 知道 1e6 条还从 nil 开始 append | 3.48 ms / 41.7 MB，预分配只要 0.71 ms / 8.0 MB |
| map 的 value 放整条记录 | 从 37.8 B/条涨到几百 B/条，GC 扫描与拷贝一起变慢；应存指针或拆成并行数组 |
| 并发读写 map | `fatal error`，进程退出且不能 recover；没触发检测时静默写坏数据 |
| 小集合（n < 32）也上 map | 哈希 13 ns vs 线性扫 0.4 ns/元素，反而更慢，还多一次分配 |
| 用 `container/heap` 做全排序 | 遍历顺序不是有序，还得再排一遍，白忙 |
| 用 slice 做需要 O(1) 中间删除的队列 | 每次删除 copy 挪动，退化成 O(n)，队列越长越慢 |
| 依赖 map 的 range 顺序写测试 | 顺序每次不同，测试偶发失败；要稳定顺序必须先取 key 排序 |

## 自检

**Q1** 1e6 元素时 list 遍历是 1.94 ns/元素，slice 是 0.49 ns/元素，只差 3.9 倍。为什么正文里说 “链表可能差两个数量级”？

▸ 答案：3.9 倍是链表的**最好情况**——测试按顺序 `PushBack`，分配器把节点连续放置，遍历等价于顺序访存。真实业务反复增删后节点散落，`e.Next()` 每跳一次就是一次随机访存（~100 ns 量级），此时 1.94 ns 会涨到几十 ns，相对 0.49 ns 就是两个数量级。**链表的实测数字对分配模式极度敏感**，要证明它快或慢，得先说明节点是怎么分配出来的。

**Q2** `container/list` 的 64 B/元素是怎么算出来的？

▸ 答案：`Element` = next + prev（16 B）+ `Value any`（16 B）= 32 B，size class 取整到 48 B；`Value` 里装的 `item`（两个 int，16 B）装箱到堆再占一块 16 B → 48 + 16 = 64 B。slice 的 16 B 是纯数据，没有每元素头部、没有接口装箱。**接口字段不是免费的，每个 `any` 都是一次可能的堆分配。**

**Q3** Top-100 / 1e6 快 240 倍，其中多少来自复杂度、多少来自常数？

▸ 答案：各占一半量级。比较次数 2e7 → 1e6 是 20 倍；单次比较 9.1 ns → 0.76 ns 是 12 倍；20 × 12 ≈ 240。前者靠换算法（`sort.Slice` → 堆），后者靠换实现（闭包比较器 → 内联整数比较）。**只做一件只能拿到 1/12 到 1/20。**

**Q4** 为什么 `make([]int, 0, 1e6)` 能省 4.9 倍时间，`make(map[int]int, 1e6)` 只省 1.78 倍？

▸ 答案：slice 不预分配要**复制 415 万个元素**（4.15 次/元素）并做 37 次数组分配；map 的 grow 是渐进搬桶，复制成本早就摊进后续写入。预分配给 map 省的是桶分配次数（8 210 → 4 098）与峰值内存（75.6 → 37.8 MB），省不掉哈希与桶内比较。**同一个词 “预分配”，在两种容器里省的是不同的东西。**

**Q5** 定时器用最小堆，为什么 “删除任意一个定时器” 是 O(n)？生产上怎么补？

▸ 答案：堆只知道堆顶最小，要删中间某个任务得先找到它在堆数组里的下标，只能线性扫。补法两种：① `map[taskID]int` 记下标，删除时与末尾交换再 `heap.Fix`，O(log n)；② 时间轮，插入/删除都 O(1)，代价是精度按槽位取整（例如 1 秒一格，最多晚 1 秒触发）。**“最大堆/最小堆只擅长取顶”，其余操作要自己补索引。**

**Q6** 并发写 map 会怎样？能 `recover` 吗？为什么它比崩溃更危险？

▸ 答案：`fatal error: concurrent map writes`，runtime 直接 `throw`，不可 `recover`，进程退出。危险在于检测是尽力而为：没撞上检查就不报错，只把 bucket 链写坏，表现为数据丢失或串号——**崩溃还能定位，静默损坏不能**。所以要么全链路加锁（`RWMutex` / 分片锁），要么用 `sync.Map`，不能靠 “跑了一年没出事”。

**Q7** 一张 1000 条的路由表，每个请求查一次。用 map 还是 slice 线性扫？

▸ 答案：看建表成本除以查询次数。**每个请求重建**：1e6 条插入 36 ms，1000 条约 36 µs，而线性扫 1000 × 0.4 ns = 0.4 µs——map 慢 90 倍。**进程启动建一次、之后只读**：map 13 ns/次（热）vs 线性扫平均 500 条 × 0.4 ns = 0.2 µs——map 快 15 倍。判据不是 “n 多大”，而是 **建表次数 × 建表成本 vs 查询次数 × 单次扫描成本**。
