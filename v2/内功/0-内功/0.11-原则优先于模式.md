# 0.11 原则优先于模式：SOLID 与 “组合优于继承” 的 Go 投影

## 一句话

> 模式是「某类变化的标准答案」，原则是「判断这个答案该不该抄的判据」；Go 只有三件工具——隐式接口、结构体嵌入、包边界，SOLID 投影到这三件工具上就三句话：**接口由消费方定义、能小不大；依赖只朝稳定方向；嵌入只用来组合接口，不用来复用实现**。

## 先分清：模式给答案，原则给判据

| 维度 | 原则 | 模式 |
|---|---|---|
| 回答的问题 | 这里**该不该**引入抽象 | 这里**怎么**组织代码 |
| 数量 | 5 条（SOLID）+ 几条通用原则 | 23 种（GoF），常用的 8 种 |
| 判据形态 | 可证伪（依赖方向、方法数、实现数） | 可套用（结构、角色、时序） |
| 用错的后果 | 抽象过度或抽象泄漏，慢一点但能改 | 结构与需求不匹配，改起来更贵 |
| 与 Go 的关系 | 直接落成语言特性 | 一半要退化（函数值、表、channel） |

判断顺序不能反：**先用原则问「变化发生过几次」，再用模式决定「怎么隔离」**。反过来做，就是先背答案再找题，最后用一层抽象去接一个还不存在的问题。

## SOLID 五条，每条只留一个 Go 落点

| 原则 | 一句话 | Go 落点 | 违反后的可观测症状（典型） |
|---|---|---|---|
| S 单一职责 | 一个类型只对一个角色负责 | 按「谁会要求它改」切包和类型 | 改一个需求动 5 个文件、3 个包 |
| O 开闭 | 加功能不改老代码 | 注册表 + 函数值（策略） | 每加一种类型，switch 长一行 |
| L 里氏替换 | 实现方不能收窄契约 | 接口约定 + 统一的 `error` 语义 | 某个实现返回 `nil, nil`，调用方 panic |
| I 接口隔离 | 接口要小，只放调用方用到的 | 单方法接口，消费方声明 | 一个 fake 要写 39 行（见下节实测） |
| D 依赖倒置 | 依赖抽象，抽象不依赖细节 | 接口定义在消费方包，import 指向内层 | 存储层 import 了业务层，换个库要改业务 |

> 🔑 依赖倒置的完整推导（DIP / IoC / DI 三个词的区别、接口为什么必须定义在消费方、循环依赖为什么是礼物）主场在 [26.2 依赖倒置](../../L2-架构风格/26-分层与依赖/26.2-依赖倒置.md)，这里只留一条可执行判据：**看 import 方向**——如果「具体的实现包」被「业务包」import，方向就是对的；反过来就是倒置没做成。

## 接口最小化：标准库自己是最大证据

扫一遍 `$GOROOT/src`（`go1.27.1 darwin/arm64`，命令 `go run .`，跳过 `testdata`、`vendor`、`_test.go`，含嵌入接口的不计入方法数）：

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
	"io/fs"
	"path/filepath"
	"runtime"
	"sort"
	"strings"
)

func main() {
	dist := map[int]int{}
	total, embedded := 0, 0
	filepath.WalkDir(filepath.Join(runtime.GOROOT(), "src"), func(p string, d fs.DirEntry, err error) error {
		if d.IsDir() {
			if n := d.Name(); n == "testdata" || n == "vendor" || strings.HasPrefix(n, ".") {
				return fs.SkipDir
			}
			return nil
		}
		if !strings.HasSuffix(p, ".go") || strings.HasSuffix(p, "_test.go") {
			return nil
		}
		f, err := parser.ParseFile(token.NewFileSet(), p, nil, parser.SkipObjectResolution)
		if err != nil {
			return nil
		}
		ast.Inspect(f, func(n ast.Node) bool {
			ts, ok := n.(*ast.TypeSpec)
			if !ok {
				return true
			}
			it, ok := ts.Type.(*ast.InterfaceType)
			if !ok || it.Methods == nil {
				return true
			}
			total++
			k := 0
			for _, m := range it.Methods.List {
				if len(m.Names) == 0 { // 嵌入接口：方法数不可静态判定
					embedded++
					return true
				}
				k++
			}
			dist[k]++
			return true
		})
		return nil
	})

	keys, sum := []int{}, 0
	for k, v := range dist {
		keys = append(keys, k)
		sum += v
	}
	sort.Ints(keys)
	over3, cum, median := 0, 0, 0
	for _, k := range keys {
		if k > 3 {
			over3 += dist[k]
		}
		if cum += dist[k]; cum*2 >= sum && median == 0 {
			median = k
		}
	}
	fmt.Printf("接口声明 %d 个，可静态计数 %d 个，含嵌入接口 %d 个\n", total, sum, embedded)
	for _, k := range keys {
		if k <= 3 {
			fmt.Printf("  %d 个方法：%3d 个（%5.1f%%）\n", k, dist[k], 100*float64(dist[k])/float64(sum))
		}
	}
	fmt.Printf("  >3 个方法：%3d 个（%5.1f%%）\n", over3, 100*float64(over3)/float64(sum))
	fmt.Printf("单方法接口占比 %.1f%%，中位数 %d 个方法\n", 100*float64(dist[1])/float64(sum), median)
}
```

真实输出：

```text
接口声明 448 个，可静态计数 298 个，含嵌入接口 150 个
  0 个方法：  4 个（  1.3%）
  1 个方法：157 个（ 52.7%）
  2 个方法： 53 个（ 17.8%）
  3 个方法： 27 个（  9.1%）
  >3 个方法： 57 个（ 19.1%）
单方法接口占比 52.7%，中位数 1 个方法
```

| 方法数 | 接口数 | 占比 | 代表 |
|---|---|---|---|
| 0 | 4 | 1.3% | 空接口 / `any` 类型的别名声明 |
| 1 | 157 | 52.7% | `io.Reader`、`io.Writer`、`http.Handler`、`fmt.Stringer` |
| 2 | 53 | 17.8% | `net.Addr`、`flag.Value` |
| 3 | 27 | 9.1% | `driver.Conn`、`sort.Interface`、`fmt.State` |
| >3 | 57 | 19.1% | `net.Conn`(8)、`testing.TB`(24)、`reflect.Type`(41) |

> 🔑 中位数是 **1 个方法**。接口每多一个方法，可满足它的类型就少一个数量级：1 个方法的接口几乎所有类型都能满足，10 个方法的接口基本只有你自己写的那一个实现——**大接口等于没有抽象，只是多了一层间接**。

## 隐式实现：所以「先写实现、后抽接口」才是常态

Go 的接口是结构化满足：类型不需要写 `implements`，只要方法集对得上就自动满足。这带来一个反直觉的工程结论——**接口应该在第二个实现出现时才抽，而不是在第一个实现之前**。

```go
// ① 先有具体实现（存储层自己的包）
type PGStore struct{ db *sql.DB }

func (s *PGStore) Get(ctx context.Context, id string) (*Order, error) { /* ... */ }

// ② 消费方在自己的包里，只声明它用到的那一个方法
type OrderGetter interface {
	Get(ctx context.Context, id string) (*Order, error)
}

type Service struct{ orders OrderGetter } // 依赖自己定义的抽象

func (s *Service) Detail(ctx context.Context, id string) (*Order, error) {
	return s.orders.Get(ctx, id) // 不知道、也不需要知道背后是 PG 还是内存
}
```

`PGStore` 一行代码都没改，就满足了 `OrderGetter`——这是 Go 允许「接口后置」的语言基础。

| 做法 | 谁定义接口 | 加一个方法的影响 | 适合 |
|---|---|---|---|
| 实现方定义大接口，消费方使用 | 存储层 | 所有 fake 和所有实现都要补 | 早期、只有一个消费者 |
| 消费方各自声明小接口 | 业务层 | 新需求声明新接口，老代码 0 改动 | 有 2 个以上消费者，或需要测试替身 |
| 先抽接口再写实现 | 谁都不清楚 | 接口通常一次改 3 次 | 已经明确有 2 个实现时 |

编译期断言值得写，而且它把「隐式」变成「显式」：

```go
var _ OrderGetter = (*PGStore)(nil) // 编译期确认：PGStore 还满足契约
```

第二列那个「0 改动」是隐式实现的红利，代价是**你不知道还有谁实现了它**——找实现用 `gopls` 的 Implementations、`go doc`，或者一个 `var _` 断言清单。测试替身的取舍见 [53.6 测试替身 (mock / stub / fake)](../../L5-工程效能/53-测试与质量保障/53.6-测试替身.md)。

## 组合优于继承：嵌入的三个坑，都有编译期/工具链信号

Go 没有继承，只有嵌入。嵌入是**编译期的字段与方法提升**，不是运行期的父子分派——这条区别决定了下面三个坑。

### 坑一：方法或字段歧义

```go
package main

import "fmt"

type Notifier struct{ ID int }

func (Notifier) Name() string { return "notifier" }

type Logger struct{ ID string }

func (Logger) Name() string { return "logger" }

// 两个嵌入类型都带 Name() 和 ID
type Service struct {
	Notifier
	Logger
}

func main() {
	var s Service
	fmt.Println(s.Name()) // 两个嵌入类型都有 Name
}
```

真实编译输出：

```text
./main.go:21:16: ambiguous selector s.Name
```

字段同理：两个嵌入类型都有 `ID` 时，`s.ID` 也是 `ambiguous selector s.ID`。**解决方式不是调换嵌入顺序**（那只是让一个字段赢），而是显式转发，把选择写出来：

```go
func (s Service) Name() string { return s.Notifier.Name() }
```

> ⚠️ 歧义只发生在**同一层**。如果 `Notifier` 自己还嵌了 `Base`，那 `s.Name()` 会优先用浅层的 `Notifier.Name`，深层的不会再报歧义——「就近原则」会让一个本该报错的设计静默通过。

### 坑二：意外满足接口

```go
type Session struct {
	bytes.Buffer // 本意：内部拼一下报文
	UserID       string
}

func Audit(w interface{ Write([]byte) (int, error) }, msg string) {
	fmt.Fprintf(w, "audit: %s\n", msg)
}

func main() {
	s := &Session{UserID: "u1"}
	Audit(s, "login") // Session 意外实现了 io.Writer
	fmt.Printf("会话内部缓冲区被写入：%q\n", s.String())
}
```

真实输出：

```text
会话内部缓冲区被写入："audit: login\n"
```

嵌入 `bytes.Buffer` 把 `Write`、`Read`、`String` 一起提升了，`Session` 从此满足 `io.Writer`、`io.Reader`、`fmt.Stringer`——任何一个接受 `io.Writer` 的函数都能往会话内部写字节。**嵌入具体类型 = 把它整个方法集借出去**，这是 Go 里最常见的抽象泄漏入口。

### 坑三：复制锁

```go
package main

import (
	"fmt"
	"sync"
)

type Counter struct {
	sync.Mutex // 本意：复用 Lock/Unlock
	n          int
}

func (c *Counter) Inc() { c.Lock(); c.n++; c.Unlock() }

func main() {
	c := Counter{}
	c.Inc()
	c2 := c // 复制了一个可能已加锁的互斥量
	fmt.Println(c.n, c2.n)
}
```

真实输出（`go vet ./...`）：

```text
main.go:18:8: assignment copies lock value to c2: vet2.Counter
```

嵌入 `sync.Mutex` 还把 `Lock`/`Unlock` 提升成了 `Counter` 的公开方法，于是 `Counter` 意外满足 `sync.Locker`，任何人都能锁它。**互斥量应该是命名字段（`mu sync.Mutex`），不是嵌入。**

| 误区 | 现实 | 正确做法 |
|---|---|---|
| 嵌入 = 继承 | 无动态分派，父方法调不到子方法覆写 | 钩子函数字段或接口注入 |
| 嵌入能复用代码 | 只提升方法/字段，且与宿主共享同一份状态 | 命名字段 + 显式转发 |
| 嵌入接口能自动实现 | 只在你显式赋值给该接口时才有意义 | `var _ I = (*T)(nil)` 断言 |
| 嵌入越深越「抽象」 | 每多一层，字段歧义与方法提升的搜索范围就大一倍 | 嵌入不超过 1 层 |

嵌入层数越深，读代码时越要逐层往上找字段和方法是谁的——命名和一致性规则见 [40.4 代码可读性与一致性](../../L3-质量属性/40-可维护性/40.4-代码可读性与一致性.md)。

## 稳定依赖、包循环、抽象泄漏

| 问题 | Go 里的表现 | 判据 |
|---|---|---|
| 依赖方向反了 | 业务包 import 了 `pg`、`redis` 这种具体实现包 | 换一个存储要改业务代码 = 倒置没做 |
| 包循环依赖 | 编译器直接报 `import cycle not allowed` | 这是礼物：Go 不允许循环 import，问题在编译期暴露 |
| 抽象泄漏 | 接口方法名带实现细节（`Query`、`Exec`、`BeginTx`） | 换实现要改调用方 = 泄漏 |
| 不稳定依赖 | 依赖了一个每周改 3 次的包 | 用 git 历史统计包的变更频率，见 [40.2 耦合与内聚度量](../../L3-质量属性/40-可维护性/40.2-耦合与内聚度量.md) |

**稳定依赖**的量化做法：对每个包统计近 6 个月的提交次数，依赖只允许指向「变更频率 ≤ 自己」的包。业务包每周改，就不该被工具包依赖；反过来，业务包依赖一个天天改的工具包，等于把自己的构建稳定性交给别人。包边界怎么切、`internal/` 怎么用，见 [26.6 模块化与包设计](../../L2-架构风格/26-分层与依赖/26.6-模块化与包设计.md)。

**抽象泄漏**的 Go 版判据很硬：接口方法签名里出现 `sql.NullString`、`http.Header`、`*redis.Pipeliner`，就是泄漏——换实现时调用方必须改。泄漏不是错，是**必须显式承认的边界**：`io.Reader` 也泄漏了「流」这个模型（不支持随机访问），但它只泄漏一个概念，代价可控。

## 实测：小接口 vs 大接口的 mock 成本

同一份业务（订单查询），两种接口设计，各写 3 个测试替身，`wc -l` 实测：

| 设计 | 接口方法数 | 接口文件 | 每个 fake | 3 个 fake 合计 |
|---|---|---|---|---|
| 实现方定义的大接口 `OrderRepo` | 10 | 19 行 | 39 行 | 136 行 |
| 消费方声明的小接口 `OrderGetter` | 1 | 10 行 | 9 行 | 37 行 |

大接口的 39 行里，真正被测试用到的只有 `Get`，其余 9 个方法是 27 行 `return nil` 的摆设——**69% 的 mock 代码是噪音**，10 个方法里 9 个和这个测试无关。

改造成本更悬殊。给大接口加第 11 个方法（前提是写了编译期断言）：

```text
mockbig/fake1.go:8:19: cannot use (*Fake1)(nil) (value of type *Fake1) as OrderRepo value in variable declaration: *Fake1 does not implement OrderRepo (missing method Archive)
mockbig/fake2.go:8:19: cannot use (*Fake2)(nil) (value of type *Fake2) as OrderRepo value in variable declaration: *Fake2 does not implement OrderRepo (missing method Archive)
mockbig/fake3.go:8:19: cannot use (*Fake3)(nil) (value of type *Fake3) as OrderRepo value in variable declaration: *Fake3 does not implement OrderRepo (missing method Archive)
```

3 个文件、3 条错误，全部要改——而其中 2 个 fake 根本不需要归档能力。小接口的做法是让需要归档的消费方声明 `OrderArchiver`，只有真正要归档的那一个 fake 去满足它，**已有 3 个文件 0 改动**。

> 🔑 接口大小直接决定 mock 成本，而 mock 成本决定测试愿不愿意写。一个 10 方法接口 + 39 行的 fake，会让人选择「不测了」。接口怎么定，最终是测试成本问题（[53.6 测试替身 (mock / stub / fake)](../../L5-工程效能/53-测试与质量保障/53.6-测试替身.md)）。

## 反模式

| 反模式 | 后果 |
|---|---|
| 接口先行：第一个实现还没写完就抽 10 方法接口 | 接口按「想象的需求」设计，落地时反复改签名，所有 fake 跟着改 |
| 大接口一把梭（`OrderRepo` 10 方法） | 每个 fake 39 行、69% 是 `return nil` 噪音，测试直接不写 |
| 为 mock 而生接口（产品代码里只有测试用） | 多一层间接、0 个真实替换，产品代码为测试让路 |
| 把嵌入当继承用 | 方法歧义编译失败、或「就近原则」静默选错实现 |
| 嵌入 `sync.Mutex` / `bytes.Buffer` 等具体类型 | 意外满足 `Locker`/`io.Writer`，`go vet` 报 copylocks，内部状态被外部写 |
| 业务包 import 具体存储包 | 换库要改业务代码，依赖倒置没做 |
| 接口方法签名带 `sql.NullString` / `*redis.Pipeliner` | 抽象泄漏，换实现时调用方跟着改 |
| 把 SOLID 当教条：每个类型必配一个接口 | 类型数翻倍、跳转多一层，实际只有 1 个实现 |

## 自检

**Q1** 标准库里 52.7% 的接口只有 1 个方法，可 `reflect.Type` 有 41 个方法、`testing.TB` 有 24 个。这两件事矛盾吗？

▸ 答案：不矛盾。大接口都出现在**边界与反射层**（`reflect`、`testing`、`net`），它们描述的是一个完整的类型系统或后端能力，由少数几个实现方整体实现，调用方不 mock 它。业务代码里的接口是另一个物种：调用方要替换、要测试、要多个实现，所以必须小。**判据不是「接口该有几个方法」，而是「谁实现它、有几个实现、要不要被替换」**。

**Q2** 「先写实现、后抽接口」和「接口先行」的差别在哪？什么情况下接口先行是对的？

▸ 答案：差别在接口的输入从哪来。后抽接口的输入是**已经存在的调用点和已经发生的第二个实现**，签名是被使用方式逼出来的；接口先行的输入是「以后可能要换」，签名靠想象。接口先行只在一种情况下成立：**第二个实现已经确定并且已经在排期**（比如同时要支持 MySQL 和内存版做测试）。否则等第二次用到再抽，成本几乎为零——Go 的隐式满足让「后抽」不需要改实现方一行代码。

**Q3** `Service` 嵌了 `Notifier` 和 `Logger`，两者都有 `Name()`，`s.Name()` 编译失败。除了显式转发，还有别的解法吗？为什么不建议「调整嵌入顺序」？

▸ 答案：还可以给其中一个改成命名字段（`logger Logger`），或者把 `Name` 从嵌入类型里拿掉。但**调整嵌入顺序不可取**：它只是让浅层字段在「同一深度」的竞争中胜出，把「设计冲突」变成「顺序约定」，下一个人重排字段就静默改变了行为；而且如果两者本来就该各自有名字，顺序方案会把 `Logger` 的 `Name` 彻底藏起来。

**Q4** 嵌入 `bytes.Buffer` 的 `Session` 为什么会被审计函数写进去？如果确实需要缓冲区，怎么写？

▸ 答案：嵌入把 `Buffer` 的 `Write` 提升成 `Session` 的方法，于是 `Session` 自动满足 `io.Writer`，任何接受 `io.Writer` 的函数都能写它——审计函数不知道也不关心写的是谁。正确写法是命名字段 `buf bytes.Buffer`，需要暴露写入能力时显式开一个方法（`func (s *Session) Append(p []byte)`），**把「内部结构」和「公开契约」分开**。

**Q5** 给一个 10 方法接口加第 11 个方法，改完 `go build` 可能一条错误都没有。为什么？怎么让错误暴露出来？

▸ 答案：因为 Go 是结构化满足，只有在**赋值给接口类型**时才做检查。如果 fake 只是被 `&Fake1{}` 直接传进某个 `OrderRepo` 参数，而调用点恰好没编译到（另一个包、另一个测试文件），就没有检查点。加 `var _ OrderRepo = (*Fake1)(nil)` 编译期断言后，实测 3 个 fake 立刻报 3 条 `missing method Archive`。这就是「隐式实现的代价」——你必须自己造一个检查点。

**Q6** 都说「组合优于继承」，Go 里最容易被误读成什么？嵌入和组合的分界线在哪？

▸ 答案：最容易被误读成「多用嵌入」。嵌入确实是组合的一种，但它是**最紧的一种**：提升整个方法集、共享同一份状态、引发歧义、意外满足接口。分界线是「我需不需要把对方的方法集公开出去」——需要（例如用装饰器包一个 `http.RoundTripper`）就嵌入接口；只需要用它的能力，就命名字段。**嵌入接口比嵌入具体类型安全**，因为方法集是你选的。

**Q7** 抽象泄漏的判据是什么？`io.Reader` 算不算泄漏？

▸ 答案：判据是「换实现时调用方要不要改」。`io.Reader` 泄漏了「流式、只能顺序读」这个模型——想随机访问就得换接口（`io.ReaderAt`），所以它算泄漏，但只泄漏一个概念、边界清楚、代价可接受。反例是接口方法签名里出现 `sql.NullString`、`http.Header`、`*redis.Pipeliner`：换存储或换框架时，调用方必须改代码，泄漏的是**实现细节**而不是**能力模型**。前者可接受，后者是设计事故。
