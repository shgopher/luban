# 0.9 结构型 7 种：适配器、装饰器、代理、门面、组合、桥接、享元

## 一句话

> 结构型只做三个动作——**换接口**（适配器）、**套一层**（装饰器 / 代理）、**改形状**（组合成树、门面收敛、桥接拆轴、享元共享）；这三个动作在 Go 里的代价都可测：一层中间件约 2.4 ns，一次零分配适配 2.2 ns，一次享元查询 14–16 ns 但省下每次 24 B。

## 先分清：适配器、装饰器、代理长得很像

三者都是“包一层”，区别只在**接口变不变**和**为什么包**：

| 维度 | 适配器 | 装饰器 | 代理 |
|---|---|---|---|
| 接口 | **变**（源接口 → 目标接口） | 不变 | 不变 |
| 目的 | 让不兼容的两边能对接 | 叠加职责（增强） | 控制访问（拦截、延迟、鉴权） |
| 调用方感知 | 感知（拿到的是另一个接口） | 无感 | 无感 |
| 典型 Go 实现 | 函数类型 + 一个方法 | `http.Handler` 中间件链 | 同接口包装 + 懒加载 / 限流 |
| 失败语义 | 转换失败要报错 | 透传下游错误 | **可能自己拒绝**（这才是坑） |
| 一个例子 | `[]string` → `io.Reader` | 加日志、加耗时 | 缓存代理、鉴权代理 |

> 🔑 一句话区分：**接口变了 = 适配器；接口没变、行为叠加 = 装饰器；接口没变、行为替换或拦截 = 代理。**

代理最容易被误用成装饰器，因为代码形状完全一样。区别在“失败语义”：装饰器不应该改变调用的成败（加了日志不该让请求失败），代理可以（限流代理会直接返回 429）。一个代理如果悄悄把下游错误换成默认值，它就从“控制访问”变成了“掩盖故障”——熔断与降级的边界见 [35.6 熔断与降级](../../L3-质量属性/35-可用性/35.6-熔断与降级.md)。

## 装饰器 = 中间件：每层约 2.4 ns

Go 里装饰器的标准形态就是 `func(http.Handler) http.Handler`。不需要 `Decorator` 基类，函数类型自己就是抽象。

```go
package main

import "net/http"

// Middleware 是 Go 里装饰器的标准形态：吃一个 Handler，吐一个 Handler。
type Middleware func(http.Handler) http.Handler

// Chain 把中间件按声明顺序叠起来：Chain(a,b,c) 的执行顺序是 a→b→c→handler。
func Chain(h http.Handler, mws ...Middleware) http.Handler {
	for i := len(mws) - 1; i >= 0; i-- { // 反向包裹，保证第一个最先执行
		h = mws[i](h)
	}
	return h
}

// counter 是一个「有状态」的装饰器：统计请求数。
type counter struct{ n int }

func WithCount(c *counter) Middleware {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			c.n++
			next.ServeHTTP(w, r)
		})
	}
}

// WithNoop 是「什么都不做」的装饰器：用来单独测量一层包装本身的成本。
func WithNoop(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		next.ServeHTTP(w, r)
	})
}

// okHandler 是链条末端的业务处理器。
var okHandler = http.HandlerFunc(func(rw http.ResponseWriter, r *http.Request) { rw.WriteHeader(200) })

// Tag 记录进入/离开顺序，用来观察装饰器的顺序依赖。
func Tag(name string, trace *[]string) Middleware {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			*trace = append(*trace, name+">")
			next.ServeHTTP(w, r)
			*trace = append(*trace, "<"+name)
		})
	}
}

// nopWriter 是零分配的 ResponseWriter，避免测试桩自身分配污染数字。
type nopWriter struct{}

func (nopWriter) Header() http.Header         { return http.Header{} }
func (nopWriter) Write(p []byte) (int, error) { return len(p), nil }
func (nopWriter) WriteHeader(int)             {}

var req = &http.Request{Method: http.MethodGet, RequestURI: "/x"}
```

装配与顺序，跑一遍就能看清：

```go
package main

import "fmt"

func main() {
	// ① 装饰器 = 中间件：包一层，计数
	c := &counter{}
	h := Chain(okHandler, WithCount(c), WithNoop)
	for i := 0; i < 3; i++ {
		h.ServeHTTP(nopWriter{}, req)
	}
	fmt.Printf("① 3 次请求后计数=%d\n", c.n)

	// ② 装饰器顺序依赖：Chain(a,b) 先 a 后 b
	var t1, t2 []string
	Chain(okHandler, Tag("auth", &t1), Tag("log", &t1)).ServeHTTP(nopWriter{}, req)
	Chain(okHandler, Tag("log", &t2), Tag("auth", &t2)).ServeHTTP(nopWriter{}, req)
	fmt.Printf("② Chain(auth,log)=%v\n", t1)
	fmt.Printf("   Chain(log,auth)=%v\n", t2)
}
```

`go run .` 的真实输出（go1.27.1 darwin/arm64）：

```text
① 3 次请求后计数=3
② Chain(auth,log)=[auth> log> <log <auth]
   Chain(log,auth)=[log> auth> <auth <log]
```

`Chain(auth, log)` 是 auth 包住 log，所以 auth 先进入、最后退出。**换一下声明顺序，进入顺序就反了**——这就是“装饰器顺序依赖”：加日志和加鉴权哪个在外，直接决定“被拒绝的请求有没有日志”。鉴权、限流、熔断这类中间件是服务治理的落点，链的顺序就是治理策略的执行顺序，见 [30.4 服务治理 (注册、发现、熔断、限流)](../../L2-架构风格/30-微服务/30.4-服务治理.md)。

层数成本实测（`go test -bench 'Chain' -benchmem -count=3`，零分配的 noop 中间件）：

| 层数 | ns/op | 每层均摊 | allocs/op |
|---|---|---|---|
| 0（裸 handler） | 3.08–3.18 | — | 0 |
| 3 | 8.62–8.88 | 约 1.9 | 0 |
| 10 | 27.1–31.0 | 约 2.4 | 0 |
| 15 | 36.5–39.6 | 约 2.4 | 0 |
| 20 | 61.2–68.1 | 约 2.9 | 0 |
| 22 | 57.3–63.1 | 约 2.5 | 0 |
| 24 | 318.7–364.3 | 约 13 | 0 |
| 30 | 345.8–351.0 | 约 11 | 0 |
| 40 | 386.7–395.9 | 约 9.6 | 0 |

三点读数：

- **20 层以内，每层约 2.4 ns，全程零分配。** 一次 handler 干活是微秒到毫秒级，60 ns 的链开销是 0.01% 量级。所以“中间件太多拖慢服务”基本是伪命题，真问题是**顺序依赖**和**读代码时要跳 10 个文件**。
- **22 层到 24 层出现一次 5–6 倍跳变**（57 ns → 319 ns），之后稳定在 320–400 ns。这个跳变在三次重复测量、两次独立构建里都复现。
- **纯函数嵌套到 40 层没有这个跳变**（10 层 10.65 ns、20 层 24.0 ns、24 层 36.9 ns、40 层 86.3 ns，基本线性）。所以它不是“调用深了就慢”的普适规律，而是 `http.Handler` 这条链特有的现象。

> ⚠️ 我的判断（**未验证**）：跳变与 goroutine 栈在 8 KB 边界上的增长/复制有关，24 层 × 每层数百字节刚好越界；但我没有做进一步归因，所以不要把“24 层”当成阈值记。能带走的是：**20 层以内成本可预测，再往上成本不可预测**——这已经足够说服你控制在 10 层上下。

## 适配器：只搬数据，不做业务

适配器的价值全在“接口不兼容但语义兼容”。Go 里最轻的适配器是一个函数类型：

```go
package main

import (
	"io"
	"strings"
)

// writerFunc：把「一个函数」适配成 io.Writer —— 零分配、零结构体。
type writerFunc func([]byte) (int, error)

func (f writerFunc) Write(p []byte) (int, error) { return f(p) }

// countingWriter 只数字节，不做任何转换。
type countingWriter struct{ n int }

func (c *countingWriter) Write(p []byte) (int, error) { c.n += len(p); return len(p), nil }

// sliceReader：把 []string 适配成 io.Reader（源接口与目标接口不兼容）。
type sliceReader struct {
	parts []string
	buf   []byte
}

func (r *sliceReader) Read(p []byte) (int, error) {
	for len(r.buf) == 0 {
		if len(r.parts) == 0 {
			return 0, io.EOF
		}
		r.buf = append(r.buf, r.parts[0]...) // 每次拼接都会分配
		r.parts = r.parts[1:]
	}
	n := copy(p, r.buf)
	r.buf = r.buf[n:]
	return n, nil
}

// joinAdapter 是「带转换」的适配器：每次 Write 都做一次 string 分配。
type joinAdapter struct{ w io.Writer }

func (a joinAdapter) Write(p []byte) (int, error) {
	return a.w.Write([]byte(strings.ToUpper(string(p))))
}
```

三种适配的成本差 80 倍，全部来自“适配器里做了什么”：

| 适配器 | ns/op | B/op | allocs/op | 慢在哪 |
|---|---|---|---|---|
| `writerFunc`（只转发） | 2.14–2.18 | 0 | 0 | 一次间接调用，没有别的 |
| `joinAdapter`（每次 `ToUpper`） | 177–185 | 144 | 3 | `string(p)` + `[]byte(...)` + 结果 |
| `sliceReader`（每次拼接） | 91.3–97.2 | 72 | 4 | 逐段 `append` 到 `buf` |

> 🔑 适配器的铁律：**它只做类型搬运，不做语义加工**。一旦你在 `Write` 里做 `ToUpper`、脱敏、压缩，它就不是适配器了，而是装饰器——而且是一个每次调用分配 144 B 的装饰器。要转换就单独一层，让它可测、可关。

`writerFunc` 的 2.2 ns / 0 分配值得单独记：这是 Go 里“给函数补一个方法”的通用手法，`io.Writer`、`http.Handler`、`sort.Interface`（`sort.Slice` 之前）都能这么接。它的成本只有一个间接调用，比定义结构体再实现方法更轻。

## 组合：树形结构用同一个接口

组合模式解决“容器与叶子要一视同仁”。文件系统、菜单、组织架构、表达式树都是这个形状：**叶子与容器实现同一接口，容器递归调用子节点**。

```go
package main

import "fmt"

// Node 是组合模式的统一节点：叶子与容器实现同一接口。
type Node interface {
	Name() string
	Size() int
}

type file struct {
	name string
	size int
}

func (f *file) Name() string { return f.name }
func (f *file) Size() int    { return f.size }

type dir struct {
	name     string
	children []Node
}

func (d *dir) Name() string  { return d.name }
func (d *dir) Add(n ...Node) { d.children = append(d.children, n...) }

// Size 递归聚合：容器不需要知道子节点是文件还是目录。
func (d *dir) Size() int {
	t := 0
	for _, c := range d.children {
		t += c.Size()
	}
	return t
}

func demoComposite() {
	root := &dir{name: "/"}
	etc := &dir{name: "etc"}
	etc.Add(&file{"nginx.conf", 4096}, &file{"hosts", 220})
	root.Add(&file{"vmlinuz", 12 << 20}, etc)
	fmt.Printf("组合：%s 总大小 %d 字节（其中 /etc %d）\n", root.Name(), root.Size(), etc.Size())
}
```

真实输出：

```text
组合：/ 总大小 12587228 字节（其中 /etc 4316）
```

12587228 = 12582912（12 MiB）+ 4096 + 220，递归聚合对上了。组合模式的坑不在实现，在**递归深度与环**：目录树可能有环（符号链接），`Size()` 会栈溢出。工业实现要么限制深度（`filepath.WalkDir` 的 `maxDepth`），要么维护 visited 集合。Go 里另一个隐藏成本是**接口调用阻止内联**：`Size()` 每个节点一次动态派发，10 万个节点的树比具体类型版本慢一截，这也是 `filepath.WalkDir` 用 `fs.DirEntry` 而不是让调用方自己递归的原因之一。

## 流式管道：把“组合”用在数据流上

结构型模式里最容易被忽略的是**组合一个处理器链**。onex 的 `pkg/streams`（[源码](https://github.com/shgopher/onex)）用 **36 行接口**把这件事抽象干净：

```go
type Inlet  interface{ In() chan<- any }
type Outlet interface{ Out() <-chan any }

type Source interface{ Outlet; Via(Flow) Flow }
type Flow   interface{ Inlet; Outlet; Via(Flow) Flow; To(Sink) }
type Sink   interface{ Inlet }
```

四种角色一条链：`Source —Via→ Flow —Via→ Flow —To→ Sink`。每个算子只认"上游给我一个 channel、我给下游一个 channel"，彼此不知道对方是谁。

| 维度 | 继承式写法（BaseProcessor） | 管道写法（Source/Flow/Sink） |
|---|---|---|
| 加一个算子 | 改基类或加子类 | 写一个 `Map`/`Filter` 函数，链上插一段 |
| 开关与清理 | 基类里 try/finally 统一管 | 每个算子自己管 goroutine 与 `close` |
| 单算子测试 | 要起整条链 | 喂一个 channel、读一个 channel |

同形实现本机跑通（`go run .`）：

```text
链式管道输出: [11 21 31 41 51]      # FromSlice(1..5) → Map(×10) → Map(+1)
算子复用输出: [a! b!]               # 同一个 Map，换个组合方式直接复用
```

三个一写就会撞上的约束：

| 约束 | 后果 |
|---|---|
| 每个算子一个 goroutine | 10 个算子的链 = 10 个 goroutine；谁 close 必须想清楚，否则泄漏 |
| 末端必须有缓冲或并发消费 | 我第一版就 deadlock 了：`To` 同步阻塞、sink 无缓冲且没人读 → `all goroutines are asleep - deadlock`；给 sink 加 `cap 64` 即解 |
| 接口里没有 error 通道 | 算子里出错只能 panic 或提前关流；生产实现要自己加 err channel 或 `context` |

> 🔑 判据：数据是"流"（无限、大、逐条处理）→ 用管道；一次性小集合 → 普通 `for` 循环，省掉 N 个 goroutine 与 N 次调度。


## 门面：包级 API 就是 Go 的门面

Go 没有 `Facade` 类型，因为**包就是门面**。一个 `internal/order` 包对外只暴露 `Place(ctx, req)`、`Cancel(ctx, id)`，里面五个子系统（库存、价格、风控、支付、消息）都不导出——这就是门面，而且是最便宜的那种：零运行时开销、编译期强制。

| 判据 | 没门面 | 有门面 |
|---|---|---|
| 调用方要 import 几个包 | 5 个 | 1 个 |
| 调用方要认识几个类型 | 12 个 | 3 个 |
| 换内部实现时改几处 | 所有调用点 | 门面内部 |
| 误用内部 API 的可能 | 有（都导出了） | 无（不导出） |

门面的边界是**别让它变成上帝对象**：门面只做“编排 + 转发”，业务规则留在子系统里。判断方法很简单——如果门面文件超过 800 行、开始出现 `if 订单状态 == ...` 这种分支，它已经吃掉子系统了，这时该拆的是门面而不是再加一层。这条与 [34.4 优化手段 (缓存 / 异步 / 批处理 / 池化 / 索引 / 并发)](../../L3-质量属性/34-性能/34.4-优化手段.md) 里“收敛入口才能做批量与缓存”是同一件事的两面。

## 桥接：两条轴，两个接口

桥接解决“一个维度用继承表达不够用”的问题：形状（圆、方）× 渲染（ASCII、SVG）。用继承要写 4 个类，加一种渲染要写 2 个类；用桥接写 2 个接口 + 组合，加一种渲染只写 1 个类型。

```go
package main

import "fmt"

// 两条独立的轴：形状（抽象）与渲染方式（实现）。各自可以独立扩展。
type Renderer interface {
	DrawCircle(r int) string
}

type Shape interface {
	Draw() string
}

type asciiRenderer struct{}

func (asciiRenderer) DrawCircle(r int) string { return fmt.Sprintf("(ascii r=%d)", r) }

type svgRenderer struct{}

func (svgRenderer) DrawCircle(r int) string { return fmt.Sprintf("<circle r=%d/>", r) }

// Circle 持有 Renderer，组合而不是继承 —— 这就是桥接在 Go 里的全部。
type Circle struct {
	r int
	d Renderer
}

func (c Circle) Draw() string { return c.d.DrawCircle(c.r) }

func demoBridge() {
	for _, r := range []Renderer{asciiRenderer{}, svgRenderer{}} {
		fmt.Printf("桥接：%s\n", Circle{r: 3, d: r}.Draw())
	}
}
```

真实输出：

```text
桥接：(ascii r=3)
桥接：<circle r=3/>
```

桥接与策略的区别常被问：**策略替换的是一个算法，桥接连接的是两个都会独立扩展的维度**。代码形状一样（都是持有一个接口），差别在意图与扩展方向：策略是“同一个操作的多种实现”，桥接是“抽象 A 的多种实现 × 实现 B 的多种实现”的笛卡尔积。如果只有一个维度在变，用策略；两个维度都在变且组合有意义，用桥接。

## 享元：共享不可变状态，别和池化搞混

享元的定义很窄：**把对象里“可共享的不可变部分”抽出来复用，把“每个实例不同的部分”留在外面**。文本编辑器里的字符是典型：字形（glyph）只有几百个，位置有几百万个。

```go
package main

import "sync"

// glyph 是不可变享元：一旦创建就不再修改，因此可以安全共享。
type glyph struct {
	ch   rune
	font string
}

// 享元工厂：按 key 复用实例，内部用锁保护 map。
type glyphFactory struct {
	mu    sync.Mutex
	cache map[rune]*glyph
	hits  int
}

func newGlyphFactory() *glyphFactory { return &glyphFactory{cache: map[rune]*glyph{}} }

func (f *glyphFactory) get(ch rune) *glyph {
	f.mu.Lock()
	defer f.mu.Unlock()
	if g, ok := f.cache[ch]; ok {
		f.hits++
		return g
	}
	g := &glyph{ch: ch, font: "NotoSans"}
	f.cache[ch] = g
	return g
}

// rune 是「内在状态」；位置/颜色是「外在状态」，由调用方自己拿着，不进享元。
type placedGlyph struct {
	g    *glyph
	x, y int
}
```

10 万个字符位置跑一遍：

```text
④ 100000 个字符位置，glyph 实例 3 个，命中 99997 次
```

10 万个位置、3 个 glyph 实例。**省的是内存，不是时间**——实测每次 `get` 14.05–16.44 ns（带锁），而不共享、直接 `&glyph{}` 只要 9.12–10.80 ns，但每次多 24 B / 1 次分配。所以享元的收益要用“实例数 × 单实例大小”算，不是用 ns 算：

| 方案 | ns/op | B/op | 10 万实例的内存 |
|---|---|---|---|
| 享元（3 个共享实例） | 14.05–16.44 | 0 | 3 × 24 B ≈ 72 B |
| 不共享（每个位置 new） | 9.12–10.80 | 24 | 100000 × 24 B ≈ 2.4 MB |

### 享元、对象池、缓存，三者不是一回事

这是本节最容易被糊在一起的地方：

| | 享元（Flyweight） | 对象池（`sync.Pool`） | 缓存（LRU / TTL） |
|---|---|---|---|
| 共享的是什么 | **不可变**的内在状态 | **可变**的可复用对象 | 计算结果 |
| 拿走后能改吗 | 不能改（改了污染所有人） | 能改（用完要还） | 不能改（只读） |
| 生命周期 | 与进程同寿 | 随时可能被 GC 清掉 | 按 TTL / 容量淘汰 |
| 目的是 | 省内存 | 省分配 | 省计算 |
| Go 代表 | `map[key]*immutable` | `sync.Pool` | `41.5` 里的淘汰策略 |

`sync.Pool` 的实测最能说明“池化省的是分配”：

| 写法 | ns/op | B/op | allocs/op |
|---|---|---|---|
| 每次 `make([]byte, 0, 4096)` | 418–462 | 4096 | 1 |
| `sync.Pool` 存 `[]byte`（值） | 20.7–21.8 | 24 | 1 |
| `sync.Pool` 存 `*[]byte`（指针） | 9.15–10.12 | 0 | 0 |

三种写法差 45 倍。第三行值得单独说：**把 slice 直接 `Put` 进 `sync.Pool` 会多一次 24 B 的装箱分配**（slice 头要被塞进 `any`），存指针就没有。这不是理论——第一行和第二行之间那 24 B 就是它。`sync.Pool` 里的对象随时可能被 GC 回收，所以它只能放“可重建的临时缓冲”，不能当缓存用，更不能放连接。缓存淘汰与 TTL 的算法见 [41.5 淘汰策略与 TTL](../../L4-组件与技术/41-缓存/41.5-淘汰策略与TTL.md)。

## 反模式

| 反模式 | 后果 |
|---|---|
| 中间件叠到十几层，顺序靠“记得” | 换一次声明顺序就改变鉴权与日志的先后，事故复盘找不到原因 |
| 装饰器里吞掉错误、返回默认值 | 下游故障被伪装成正常响应，监控全绿而用户拿到空数据 |
| 代理里做重试但不设上限 | 一次下游抖动放大成雪崩（重试风暴） |
| 在适配器里塞业务转换（脱敏、压缩） | 每次调用多 100+ ns 与 3 次分配，且转换逻辑无法单独测试 |
| 适配器返回 `nil` 而不是错误 | 调用方拿到“成功但空”，问题延后到下游才暴露 |
| 门面长成上帝对象（800 行 + 业务分支） | 全公司改一个需求都要动这个文件，合并冲突天天有 |
| 享元里放可变字段 | 一处修改污染所有引用者，bug 表现为“随机串数据” |
| 用 `sync.Pool` 当缓存/连接池 | 对象被 GC 清掉，命中率随机，延迟抖动 |
| 桥接用在只有一个维度会变的地方 | 多一个接口、多一层组合，读者要追两条线才看懂 |
| 组合结构不防环 | 树里有环时递归爆栈，进程直接崩 |

## 自检

**Q1** 一个包装层：给下游调用加指标、加日志。它是装饰器还是代理？如果它在下游超时时返回上一次的缓存值呢？

▸ 答案：加指标、加日志是装饰器——它不改变调用的成败，只观测。超时返回缓存值就变成代理（控制访问/替换行为），而且是**必须显式命名**的那种：调用方要知道“这次结果可能来自缓存”，否则会把陈旧数据当实时数据用。判断依据不是代码形状（一模一样），而是“失败与新鲜度语义有没有被改变”。一旦改变，就必须在类型名、日志字段、指标标签里体现出来。

**Q2** 10 层中间件实测 27–31 ns，20 层 61–68 ns，那“中间件太多影响性能”错在哪？

▸ 答案：错在把纳秒级开销当成瓶颈。每层约 2.4 ns，20 层 60 ns，而一次 handler 通常会做 DB 查询（毫秒级）或 RPC（几十微秒到毫秒），链开销占比 0.01% 以下。真正的成本是**可读性**（读一个请求要跳 10 个文件）和**顺序依赖**（auth 与 log 谁在外，决定了被拒请求有没有日志）。该控制的理由是这两个，不是性能。

**Q3** 实测 22 层到 24 层出现 5–6 倍跳变，为什么不能把它当“阈值”记住？

▸ 答案：因为它是**单一链路的单次观察**，不是一个有解释的规律。我做了两个对照：① 三次重复测量、两次独立构建都复现（说明不是噪声）；② 纯函数嵌套到 40 层仍线性（40 层 86 ns），说明不是“调用深就慢”。所以它是 `http.Handler` 这条链特有的现象，成因我没有坐实。把没归因的数字当阈值，下次换 Go 版本或换个 handler 结构就会失效——这就是“背过但没懂”的典型：记住 24，不知道 24 从哪来。

**Q4** 适配器 `writerFunc` 是 2.2 ns / 0 分配，`joinAdapter` 是 177–185 ns / 3 次分配。多出来的成本该记在谁头上？

▸ 答案：记在**适配器里做的转换**头上，不是“适配器”这个模式头上。`writerFunc` 只做一次间接调用；`joinAdapter` 每次做 `string(p)` + `ToUpper` + `[]byte(...)`，三次分配与两次全量拷贝都是转换产生的。所以正确做法是拆开：适配器只搬类型，转换单独一层（可测、可关、可换）。把两件事塞进一个 `Write` 里，是结构型模式最常见的越界。

**Q5** 享元查询 14–16 ns，不共享只要 9–11 ns，那享元是不是“用时间换内存”？在什么规模下划算？

▸ 答案：是“用一点时间和一次锁换内存”，而且**只在实例数远大于种类数时划算**。判据是压缩比：本例 10 万个位置 / 3 种 glyph ≈ 33333:1，省 2.4 MB，多付的那 5 ns 完全值；如果种类数和实例数同量级（比如每个请求一个唯一 key），享元就是纯亏——多一次加锁、多一张 map，还省不下内存。另外要注意：享元的对象必须**不可变**，一旦共享了可变字段，省下的内存会以数据串号的形式还回来。

**Q6** 团队用 `sync.Pool` 缓存“用户配置对象”，命中率时高时低。问题在哪？

▸ 答案：`sync.Pool` 不是缓存：它没有 key、没有淘汰策略、对象会在 GC 时被清空（Go 1.13 之后还有 victim cache，但仍是“随时可能没了”）。用它存“用户配置”这种有身份、有生命周期的数据，命中率就取决于 GC 时机——所以时高时低。正确的三层分工是：**享元**存不可变共享状态（按 key）、**缓存**存可重算的结果（有 TTL / LRU）、**`sync.Pool`** 存可重建的临时缓冲（无身份）。配置对象属于第二层，见 [41.5 淘汰策略与 TTL](../../L4-组件与技术/41-缓存/41.5-淘汰策略与TTL.md)。

**Q7** 门面与“上帝对象”的界线在哪？给一个可检查的判据。

▸ 答案：界线是**门面里有没有业务判断**。门面只做编排与转发（“先扣库存、再下单、再发消息”），业务规则留在子系统；一旦门面里出现 `if 订单状态 == ...`、`switch 渠道`、金额计算，它就开始吃子系统了。可检查的判据有两条：① 门面文件行数与子系统行数的比例（门面应该只占小头）；② 改一个子系统的内部实现，是否需要动门面（需要就是漏了抽象）。800 行是我给的告警线，不是标准。
