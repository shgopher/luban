# 0.5 算法思想：分治、贪心、DP、回溯的架构落点

## 一句话

> 四种思想不是「面试题库」，而是四个**判据**：分治要「子问题独立且可合并」，贪心要「每步局部最优能推出全局最优」，DP 要「最优子结构 + 重叠子问题」，回溯要「约束能把搜索树砍到能跑」；判据不成立就换思想，换不了就接受近似——**同一个 1000 件物品的背包：DP 846ms，贪心 66µs（差 1.3 万倍）但最差少赚 12.5%，架构决策就是在这两个数之间签字。**

## 四种思想，四个判据

| 思想 | 成立判据 | 得到的保证 | 代价 | 判据不成立时 |
|---|---|---|---|---|
| 分治 | 子问题**互相独立**，结果**可合并** | 可并行、可水平扩展 | 合并成本 + 分片倾斜 | 退化成串行，或结果错 |
| 贪心 | 每步局部最优 ⇒ 全局最优（要能证明） | O(n log n) 甚至 O(n) | 无回溯，一步错到底 | 得到一个「看起来合理」的次优解 |
| DP | **最优子结构** + **重叠子问题** | 全局最优 | 时间/空间 = 状态数 | 状态爆炸，比暴力还慢 |
| 回溯 | 约束足够强，剪枝能砍掉大部分分支 | 精确解，能找到全部解 | 最坏指数级 | 搜索树爆炸，跑不完 |

> 🔑 顺序不能颠倒：**先问「有没有最优子结构」，再问「能不能贪」**。反过来（先贪心、后被业务发现算错了）是线上最常见的算法事故来源。

## 分治：判据是「子问题可合并、无跨片依赖」

分治在架构里的名字叫**分片**。判断一段逻辑能不能分片，只问一句：**每个分片只用自己的数据，能不能算出最终结果的一部分？**

```text
可合并     sum / count / max / min / topk(分片各取 k 个再归并) / 去重(分片各去重再合并)
不可合并   去重的「全局唯一」、P99、中位数、JOIN、全局排序
```

求和是最干净的例子：切片切成 p 段、各段独立累加、最后加一次。

```go
func sumParallel(a []int64, p int) int64 {
	part := (len(a) + p - 1) / p
	res := make([]int64, p)
	var wg sync.WaitGroup
	for i := 0; i < p; i++ {
		lo, hi := i*part, min((i+1)*part, len(a))
		if lo >= hi {
			continue
		}
		wg.Add(1)
		go func(i int, seg []int64) {
			defer wg.Done()
			var s int64
			for _, v := range seg {
				s += v
			}
			res[i] = s // 每个分片只写自己的槽，合并时不需要锁
		}(i, a[lo:hi])
	}
	wg.Wait()
	var s int64
	for _, v := range res { // 合并就是一个加法
		s += v
	}
	return s
}
```

本机实测（8 核 M1）：16MB 数据单协程 0.64ms，8 片并行 **2.2–2.4×**（多次运行落在 2.18–2.37）；160MB 数据单协程 6.38ms，8 片只有 **2.1–2.3×**，通常还不如 4 片（2.29–2.34×）。

**8 核只有 2 倍多**，这个数字比任何「分治能线性扩展」的说法都重要：求和是纯内存带宽活，单核 0.64ms 读 16MB 已经是 25GB/s，四个核就把内存控制器吃满了，第 5–8 个核只是在排队。所以：

| 瓶颈 | 加核能到几倍 | 判断依据 |
|---|---|---|
| CPU 计算（加密、压缩、正则） | 接近核数（6–7×） | 每字节的计算量 > 内存访问量 |
| 内存带宽（求和、扫描、过滤） | **2–3×** | 每字节只做 1–2 次运算 |
| 下游依赖（DB、RPC） | **0×**（只是把压力转移） | 分片后仍打同一个下游 |

这就是为什么分治的收益要按「瓶颈」估，不能按核数估。分片的物理形态——数据怎么落到哪个节点、扩容时怎么少搬——是另一件事，见 [19.4 一致性哈希](../../L1-分布式原理/19-数据分区/19.4-一致性哈希.md)：一致性哈希解决的正是「分片边界会变」时如何让分治继续成立（只搬 1/N，而不是全量重排）。

## 贪心：先做交换论证，再上线

贪心的正确性不是「看起来对」，而是要能证明：**每一步选局部最优，不会把最优解排除掉**（交换论证：把最优解的第一步换成贪心的第一步，解不会变差）。

区间调度是最经典的例子：给一堆区间，选最多的互不重叠区间。三种「显然合理」的贪心键，结果差一倍：

| 贪心键 | 1000 个随机实例的平均选中数 | 是否最优 |
|---|---|---|
| 按**结束时间**最早 | **8.14** | ✅ 可证明最优 |
| 按开始时间最早 | 6.99 | ❌ 少 14% |
| 按区间长度最短 | 3.03 | ❌ 少 63% |

三个键都「说得通」，只有第一个能证明。证明只需要一句交换论证：设最优解的第一个区间是 A，贪心选的结束最早的是 B，则 `B.e ≤ A.e`，把 A 换成 B 不会和后面任何区间冲突，所以最优解里可以包含 B——归纳下去，贪心不劣于最优。

而 **0/1 背包的贪心会直接失效**，因为它有「后效性」：装了 A 就装不下 B，而 B 可能更值。

| 物品（重量, 价值） | 单位价值 | 容量 50 时 |
|---|---|---|
| (10, 60) | 6.0 | 贪心先拿 |
| (20, 100) | 5.0 | 贪心再拿（已用 30） |
| (30, 120) | 4.0 | 装不下，跳过 |
| 贪心结果 | | 价值 **160** |
| DP 最优 | | 后两件，价值 **220** |

贪心比最优少 **27%**。这个反例只有 3 件物品，但足够推翻「按性价比贪心是对的」。

更危险的是**统计上看不出来**：500 个随机实例的平均差距只有 0.1%–1.3%，最差也不过 12.5%——也就是说，压测、灰度、A/B 都发现不了，只有遇到那个特定实例（大促的某个组合）才暴露，而且事后无法复现。

| 件数 | 容量 | 平均少拿 | 最差少拿 |
|---|---|---|---|
| 20 | 100 | 1.29% | **12.5%** |
| 30 | 150 | 1.02% | 8.0% |
| 60 | 400 | 0.44% | 2.4% |
| 100 | 200 | 0.60% | 4.1% |
| 500 | 800 | 0.10% | 0.5% |

规律：**「每件物品的重量 / 容量」越大，贪心越容易错**（20 件装 100 容量，单件占 1/5，替换空间大；500 件装 800 容量，单件占比小，贪心接近最优）。所以判据要落到数值上：**单件占总容量的比例超过 5% 时，贪心的最差误差会到 10% 量级，必须验证或换 DP。**

架构里的贪心到处都是，按「能不能证明」分两类：

| 场景 | 贪心键 | 是否可证最优 |
|---|---|---|
| 定时任务、延迟消息的到期处理 | 到期时间最早 | ✅（同区间调度）——这也是 [43.7 延迟消息与定时消息](../../L4-组件与技术/43-消息队列/43.7-延迟消息与定时消息.md) 用最小堆/时间轮的原因 |
| 公平调度（MMF / DRF） | 每步把资源给「当前占比最小」的用户 | ✅（max-min 公平性可证），见 [12.5 公平调度算法 (MMF / DRF)](../../L0-运行时底座/12-集群资源调度/12.5-公平调度算法.md) |
| 缓存淘汰 LRU / LFU | 淘汰最久未用 / 最少使用 | ❌ 已知有反例：Belady 最优需要「未来的访问序列」，LRU 只能近似（见 [41.5 淘汰策略与 TTL](../../L4-组件与技术/41-缓存/41.5-淘汰策略与TTL.md)） |
| 装箱、任务打包到机器 | 先放大件（FFD） | ❌ 近似比 11/9·OPT+1，不最优但可接受 |

> 🔑 LRU 是「无法证明最优但仍被全网使用」的典型：它每天在几十万台机器上跑，却知道自己在某些访问模式下比最优差得多。**这不算错，因为架构允许近似——但你必须知道自己在近似，而不是以为它最优。**

## DP：状态设计比递推重要

DP 的唯一门槛是「状态」：**状态 = 你在推进过程中真正需要记住的最小信息**。状态定下来，递推式和复杂度都是机械推导：

```text
0/1 背包：dp[c] = 前 i 件物品、容量 c 下的最大价值
         → 状态数 n × W，每状态 O(1) 转移 → O(n·W)
一维滚动：dp[c] = max(dp[c], dp[c-w[i]] + v[i])，容量倒序遍历
```

```go
func knapDP(w, v []int, capacity int) int {
	dp := make([]int, capacity+1)
	for i := range w {
		for c := capacity; c >= w[i]; c-- { // 倒序：正序会让同一件物品被装多次
			if cand := dp[c-w[i]] + v[i]; cand > dp[c] {
				dp[c] = cand
			}
		}
	}
	return dp[capacity]
}
```

那个 `c--` 是最容易写错的一行：**正序遍历 = 完全背包**（同一件物品能重复装），倒序才是 0/1。这类 bug 不会崩，只会算出偏大的值，在容量规划和预算分配里就是「预算超支但没人发现」。

DP 的复杂度等于状态数乘以转移代价，所以**状态数是唯一要盯的数字**：

| 问题 | 状态 | 状态数 | 本机耗时 |
|---|---|---|---|
| 0/1 背包 n=200，容量 1e4 | 200 × 10 001 | 2.0e6 | 1.6ms |
| 0/1 背包 n=1000，容量 1e6 | 1000 × 1e6 | **1.0e9** | **846ms** |
| 编辑距离（两条 1e4 长文本） | 1e4 × 1e4 | 1.0e8 | 百毫秒级 |
| 容量规划（4 个维度各 1000 档） | 1000⁴ | 1e12 | 跑不完 |

1e9 个状态 ≈ 1 秒，这是本机的经验换算。**容量一旦按「亿」算，DP 就死了**——而业务里的容量常常是钱：预算 100 亿分到 50 个团队，按「分」做 DP 就是 1e12 状态。三条出路：

- **压缩值域**：按「万元」而不是「元」做单位，状态数直接降 1e4 倍（精度损失可接受就行）；
- **换状态定义**：容量换成「价值」做维度（`dp[价值] = 最小重量`），状态数由价值总和决定；
- **接受近似**：贪心 + 局部修复，或 LP 松弛取整。

这就是贪心的诱惑：同一个 n=1000 的背包，**DP 846ms、贪心 66µs，差 1.3 万倍**。用 66µs 换 12.5% 的最差误差，很多业务愿意——但前提是你知道自己在换，而不是以为贪心就是最优解。

DP 在架构里真正的落点不是「写个递推」，而是**容量规划**：多级库存、预算分配、副本数与队列长度的取整权衡，本质都是带约束的最优化。估算容量本身用的不是 DP，而是利特尔法则和排队论——那是 [34.2 性能建模 (利特尔法则、排队论)](../../L3-质量属性/34-性能/34.2-性能建模.md) 的主场，本节只负责「状态怎么定」。

## 回溯：剪枝决定生死

回溯 = 深度优先枚举 + 约束检查。它跑不跑得完，完全取决于**冲突判定被放在第几层**。

N 皇后是干净的实验：把「冲突检查」放在放满一整行之后（等价于先枚举 n! 个排列再筛选），和「边放边查」，节点数差三个数量级：

| N | 剪枝节点数 | 不剪枝叶数（n!） | 剪枝耗时 | 不剪枝耗时 | 倍数 |
|---|---|---|---|---|---|
| 8 | 2 057 | 40 320 | 0.34ms | 3.97ms | 12× |
| 9 | 8 394 | 362 880 | 0.87ms | 26.14ms | 30× |
| 10 | 35 539 | 3 628 800 | 2.61ms | 123.35ms | 47× |
| 11 | 166 926 | 39 916 800 | 6.77ms | 1 224.21ms | 181× |
| 12 | 856 189 | 479 001 600 | 36.55ms | 15 022.92ms | **411×** |
| 13 | 4 674 890 | 6 227 020 800 | 205.32ms | 算不完（≈4 小时） | — |

```go
for c := 0; c < n; c++ {
	if cols[c] || d1[row+c] || d2[row-c+n] {
		continue // 剪枝点：这一句砍掉的不是一格，是一整棵子树
	}
	cols[c], d1[row+c], d2[row-c+n] = true, true, true
	rec(row + 1) // 只在「已放的部分合法」的枝上继续
	cols[c], d1[row+c], d2[row-c+n] = false, false, false
}
```

三个 bool 数组把冲突判定从 O(n) 降到 **O(1)**，所以剪枝本身几乎不花钱：N=13 时 205ms 里绝大部分是 467 万次递归调用，而不是判定。这就是剪枝的杠杆率——**判定越便宜、越早，砍得越多**。

剪枝的三类手段，按收益排序：

| 手段 | 做法 | 典型收益 |
|---|---|---|
| **冲突前置** | 把校验从「叶子」挪到「每一层」，O(1) 判定 | N 皇后 411× |
| **对称性消除** | 第一行只试前一半列、固定旋转/镜像代表元 | 2–8× |
| **界剪枝** | 当前代价 + 下界估计 > 已有最优解就砍 | 依赖下界质量，常常 10×+ |

架构里真正用到回溯的地方，约束都来自业务规则：**配置合法性校验**（依赖关系 + 互斥组）、**排班**（人 × 班次 × 技能 × 工时上限）、**权限组合**（角色 × 资源 × 条件）。这些问题的共同点是「约束多、可行解稀少」——正好是剪枝能发挥的条件；反过来，如果约束很松（几乎任何组合都合法），回溯会退化成暴力枚举，这时该换成约束求解器或直接改成规则引擎。

> ⚠️ 排班/权限这类问题的完整版是 NP-hard。工程上的正确姿势不是「写个更聪明的回溯」，而是**限制规模**（一次只排一个团队、权限只算到二级资源）或**接受启发式**。回溯能用，前提是你能给规模设上限。

## 架构落点：问题长什么样，就用什么思想

| 问题类型 | 算法思想 | 关键判据 | 书中对应 |
|---|---|---|---|
| 求和/计数/极值的水平扩展 | 分治 | 结果可合并 | [19.4 一致性哈希](../../L1-分布式原理/19-数据分区/19.4-一致性哈希.md) |
| 任务/请求的分配顺序 | 贪心 | 每步最优可证 | [12.5 公平调度算法 (MMF / DRF)](../../L0-运行时底座/12-集群资源调度/12.5-公平调度算法.md) |
| 缓存淘汰 | 贪心（近似） | 接受次优 | [41.5 淘汰策略与 TTL](../../L4-组件与技术/41-缓存/41.5-淘汰策略与TTL.md) |
| 到期任务的处理顺序 | 贪心（可证） | 按到期时间 | [43.7 延迟消息与定时消息](../../L4-组件与技术/43-消息队列/43.7-延迟消息与定时消息.md) |
| 预算/容量/副本数分配 | DP | 状态数可控 | [34.2 性能建模 (利特尔法则、排队论)](../../L3-质量属性/34-性能/34.2-性能建模.md) |
| 限流窗口切分 | 分治（分桶）+ 贪心（令牌补充） | 时间窗可切 | [35.7 限流 (漏桶 / 令牌桶 / 滑动窗口 / 自适应)](../../L3-质量属性/35-可用性/35.7-限流.md) |
| 配置/排班/权限的可行解 | 回溯 | 约束强、规模小 | 本节 |

判断链路可以压成三句：**能合并就分治；能证明就贪心；都不行就问状态数，状态数可控就 DP，不可控就回溯 + 限规模。**

### 图：两种存法、两种遍历、两个最短路

四种思想在图上一次全用上：BFS 是分治式的按层扩展，DFS 是回溯的骨架，拓扑排序和 Dijkstra 都是贪心（一个用队列，一个用堆）。依赖、构建顺序、路由、调用链、状态机都是图，但判据和前四节完全一样，所以这里只补差异最大的三处：**存法、遍历归位、最短路**。

#### 存法：邻接表 vs 邻接矩阵，同规模差 280 倍

| 维度 | 邻接表（CSR） | 邻接矩阵 | 谁赢 |
|---|---|---|---|
| 内存 | O(V+E)：V=1e5、E=1e6 实测 **4.40 MB** | O(V²)：同规模 **1.25 GB**（bitmap）/ **10 GB**（bool） | 表，差 **280 倍** |
| 判断 u→v 是否相邻 | O(deg(u))；度数大就先排序二分 O(log deg) | **O(1)** 一次寻址 | 矩阵 |
| 遍历 u 的所有邻居 | O(deg(u))，边在同一段连续内存里 | O(V)，要扫一整行 | 表 |
| 稠密图（E≈V²） | 每条边 4 字节 | 每格 1 bit，**省 32 倍** | 矩阵 |
| 加边/删边 | 追加容易，删除要重建 | 改一格，O(1) | 矩阵 |
| 典型场景 | 依赖图、调用链、路由、社交 | 小图、Floyd 全源最短路、位运算加速 | — |

判据一句话：**拿 E 和 V² 比，差一个数量级以上就用表**。V=1e5 时完全图有 50 亿条边，按表存要 20GB，这时矩阵那 1.25GB 反而是省的那个——**「稀疏用表、稠密用矩阵」不是习惯，是算出来的**。

实测的 4.40 MB 是 CSR（压缩稀疏行）的持久占用：`offsets` 0.40 MB + `to` 4.00 MB；建表期间临时数组还要 5.2 MB。用 `[][]int32` 的写法会多出每个节点 24 字节的切片头（1e5 个点就是 2.4 MB）和 n 次小分配，BFS 时 cache 命中率也差——所以生产代码里的图基本都用 CSR 或链式前向星。

#### 遍历：BFS 是按层扩展，DFS 是回溯的骨架

定义不用背，只要记住它们各自对应哪个思想、产出什么：

| 遍历 | 容器 | 对应思想 | 产出 | 复杂度 |
|---|---|---|---|---|
| BFS | 队列（FIFO） | 分治式按层扩展：一层是一次完整的「边界推进」 | 无权图最短路、层数、连通分量 | O(V+E) |
| DFS | 栈 / 递归 | 回溯骨架：一条路走到底，再退回上一层 | 环检测、拓扑序、强连通分量、连通分量 | O(V+E) |

BFS 能给「无权最短路」，是因为它第一次碰到某点时走的边数一定最少——按层推进保证了任何人都不可能更早到达。DFS 能当回溯骨架，是因为它的「退回上一层」就是回溯的撤销动作，剪枝点在「这个邻居访问过没有」。两者共同的复杂度前提：**每个点只进容器一次**，所以是 O(V+E)，不是 O(V·E)。

#### 拓扑排序：Kahn 是贪心，DFS 后序是回溯

| 写法 | 做法 | 对应思想 | 环检测 | 输出顺序 |
|---|---|---|---|---|
| **Kahn（入度法）** | 反复取入度为 0 的点出队，删掉它的出边 | 贪心：每步取「现在就能做」的 | 输出节点数 < V 即有环 | 由队列决定，换成小顶堆可得到字典序最小 |
| **DFS 后序** | 深搜到底，回溯时入栈，最后逆序输出 | 回溯：后序 = 依赖全部完成 | 需三色标记，遇「灰色」点即有环 | 由邻接表顺序决定 |

Kahn 的贪心为什么对：入度为 0 意味着「前置全部完成」，此刻做它不违反任何依赖；做完删边，又让新的点变成可做。这是「每步局部最优 ⇒ 全局可行」少数能证明的实例之一。

实测（5 个点的 DAG）：入度 `[0 1 1 2 2]` → 拓扑序 `[0 1 2 3 4]`；加一条 `4→2` 造出环 `2→3→4→2` 后，Kahn 只输出 2 个点 `[0 1]`——**长度不足本身就是环检测**，不需要额外代码。DFS 后序就没这么便宜，必须额外维护三种颜色。

落点是三件事，本质同一张图：

| 场景 | 图里的点/边 | 为什么必须是拓扑序 |
|---|---|---|
| 服务启动顺序 | 服务 / 依赖 | 缓存先于网关，DB 先于缓存，顺序错就是启动即失败 |
| 构建顺序（make、Bazel） | 目标 / 依赖 | 边决定谁先编译，有环就是「循环依赖」 |
| 配置加载顺序 | 配置项 / 引用 | A 引用 B 的值，必须先解析 B |

**资源调度是同一个问题的加权版本**——每步选「当前最该跑」的任务，判据从「入度为 0」换成「资源占比最小」，见 [12.5 公平调度算法 (MMF / DRF)](../../L0-运行时底座/12-集群资源调度/12.5-公平调度算法.md)。

> ⚠️ 有环的依赖图不会「变慢」，它会**静默丢节点**。所以构建/启动前必须校验 `len(order) == V` 并把剩下的点打印出来，而不是等线上少启一个服务才发现。

#### 最短路：Dijkstra = 贪心 + 优先队列

Dijkstra 只做两件事：每步从「未确定集合」里取 dist 最小的点（贪心），再用它的出边松弛邻居（候选塞进堆）。这正是 [0.2 数据结构选型：数组、链表、哈希、树、堆、跳表](0.2-数据结构选型.md) 里那个堆的经典用途——堆把「取最小」从 O(V) 压到 O(log V)，总复杂度 O((V+E)·log V)。

同一张 V=1e5、E=1e6 的图：BFS（无权）2.5–3.2ms，Dijkstra（带权 + 堆）60–64ms，差约 20 倍，多出来的全是堆操作和权重加法。不用堆、每次线性扫最小值是 O(V²)=1e10 次比较，这张图上根本跑不动。

**负权为什么会坏**：Dijkstra 的贪心承诺是「出堆即定死，它的距离不会再变小」。非负权下这成立——任何绕路都要再加一段非负代价；有负权就不成立：

```text
边：0→1:2  0→2:5  2→1:-4  1→3:1
过程：出堆 1（dist=2）→ 立刻把 3 算成 2+1=3
      之后发现「绕 2 走」只要 1，但 3 不会再重算
结果：Dijkstra 给出 [0 1 5 3]，正确答案是 [0 1 5 2]
```

最阴的地方是：数组里节点 1 那格最后看着是对的（被顺手改成了 1），**错误转移到了下游节点 3 上**。这类 bug 不崩、不报错，只是结果偏大，偏移量取决于图的形状。

三个替代，各一句话：

| 算法 | 一句话 | 复杂度 | 负权 |
|---|---|---|---|
| Dijkstra | 贪心 + 堆，单源最短路的事实标准 | O((V+E)·log V) | ❌ |
| Bellman-Ford | 对所有边松弛 V 轮，第 V 轮还能松弛就是有负环 | O(V·E) | ✅ 且能检测负环 |
| A* | Dijkstra + 启发式 h，按 f = g + h 出堆 | 取决于 h 的质量 | ❌ |

A* 的全部价值在 h：h≡0 就退化成 Dijkstra，h 恰好等于真实剩余距离就是直奔答案。地图导航、游戏寻路用它，判据是「能不能给出一个不高估剩余距离的启发式」。

```go
package main

import (
	"container/heap"
	"fmt"
	"math/rand"
	"runtime"
	"time"
)

// ---------- 存法一：CSR（压缩稀疏行）邻接表 ----------
// offsets[i]..offsets[i+1] 是节点 i 的出边在 to 里的下标区间。
// 比 []][]int 省：省掉每个节点 24 字节的切片头，边全在一段连续内存里，BFS 时 cache 友好。
type graph struct {
	offsets []int32
	to      []int32
}

func buildCSR(v int, from, to []int32) *graph {
	deg := make([]int32, v+1)
	for _, u := range from {
		deg[u+1]++
	}
	for i := 0; i < v; i++ { // 前缀和 → 每个节点的起始下标
		deg[i+1] += deg[i]
	}
	off := make([]int32, v+1)
	copy(off, deg)
	adj := make([]int32, len(to))
	cursor := make([]int32, v)
	copy(cursor, deg[:v])
	for i, u := range from {
		adj[cursor[u]] = to[i]
		cursor[u]++
	}
	return &graph{offsets: off, to: adj}
}

func (g *graph) neighbors(u int32) []int32 { return g.to[g.offsets[u]:g.offsets[u+1]] }

// ---------- Kahn 拓扑排序：每步取入度为 0 的节点 = 贪心 ----------
func kahn(v int, g *graph, indeg []int32) []int32 {
	deg := append([]int32(nil), indeg...)
	queue := make([]int32, 0, v)
	for i := 0; i < v; i++ {
		if deg[i] == 0 {
			queue = append(queue, int32(i)) // 入度 0 = 「现在就能做」
		}
	}
	order := make([]int32, 0, v)
	for len(queue) > 0 {
		u := queue[0]
		queue = queue[1:] // 贪心：谁先变成 0 就先出队
		order = append(order, u)
		for _, w := range g.neighbors(u) {
			deg[w]--
			if deg[w] == 0 {
				queue = append(queue, w)
			}
		}
	}
	return order // 长度 < v 说明有环
}

// ---------- Dijkstra：贪心 + 优先队列 ----------
type item struct {
	node int32
	dist int64
}
type pq []item

func (p pq) Len() int           { return len(p) }
func (p pq) Less(i, j int) bool { return p[i].dist < p[j].dist }
func (p pq) Swap(i, j int)      { p[i], p[j] = p[j], p[i] }
func (p *pq) Push(x any)        { *p = append(*p, x.(item)) }
func (p *pq) Pop() any          { o := *p; v := o[len(o)-1]; *p = o[:len(o)-1]; return v }

// dijkstra 用带权邻接表 wg[u] = [{v, w}]，权为负时结果无意义（见 main 的反例）
func dijkstra(v int, wg [][]item, src int32) []int64 {
	const inf = int64(1) << 60
	dist := make([]int64, v)
	for i := range dist {
		dist[i] = inf
	}
	dist[src] = 0
	done := make([]bool, v) // 已「定死」的节点：Dijkstra 的贪心承诺
	h := &pq{{src, 0}}
	for h.Len() > 0 {
		cur := heap.Pop(h).(item)
		if done[cur.node] {
			continue // 堆里的过期副本
		}
		done[cur.node] = true // 出堆即定死：负权会让这一句成为错误来源
		for _, e := range wg[cur.node] {
			if nd := cur.dist + e.dist; nd < dist[e.node] {
				dist[e.node] = nd
				heap.Push(h, item{e.node, nd})
			}
		}
	}
	return dist
}

// bellmanFord：允许负权，O(V·E)，能报出负环
func bellmanFord(v int, edges [][3]int64, src int64) ([]int64, bool) {
	const inf = int64(1) << 60
	dist := make([]int64, v)
	for i := range dist {
		dist[i] = inf
	}
	dist[src] = 0
	neg := false
	for i := 0; i < v; i++ {
		changed := false
		for _, e := range edges {
			u, to, w := e[0], e[1], e[2]
			if dist[u] == inf {
				continue
			}
			if dist[u]+w < dist[to] {
				dist[to] = dist[u] + w
				changed = true
				if i == v-1 {
					neg = true // 第 V 轮还能松弛 → 有负环
				}
			}
		}
		if !changed {
			break
		}
	}
	return dist, neg
}

func bfsTime(g *graph, v int, src int32, reps int) time.Duration {
	best := time.Duration(1<<62 - 1)
	visited := make([]bool, v)
	q := make([]int32, 0, v)
	for r := 0; r < reps; r++ {
		for i := range visited {
			visited[i] = false
		}
		q = q[:0]
		t := time.Now()
		q = append(q, src)
		visited[src] = true
		for len(q) > 0 {
			u := q[0]
			q = q[1:]
			for _, w := range g.neighbors(u) { // 按层扩展：先入先出
				if !visited[w] {
					visited[w] = true
					q = append(q, w)
				}
			}
		}
		if el := time.Since(t); el < best {
			best = el
		}
	}
	return best
}
```

## 可运行实测 A：贪心与 DP

```go
package main

import (
	"fmt"
	"math/rand"
	"slices"
	"time"
)

func dur(d time.Duration) float64 { return float64(d.Microseconds()) / 1000 }

// greedyKnap 按「单位重量价值」从高到低装，装不下就跳过。
// 注意：装不下时它不会回头换掉已装的，这正是贪心失效的根源。
func greedyKnap(w, v []int, capacity int) int {
	idx := make([]int, len(w))
	for i := range idx {
		idx[i] = i
	}
	slices.SortFunc(idx, func(a, b int) int {
		l, r := v[a]*w[b], v[b]*w[a] // 交叉相乘比较 v/w，避免浮点误差
		if l != r {
			return r - l // 降序
		}
		return 0
	})
	total := 0
	for _, i := range idx {
		if w[i] <= capacity {
			capacity -= w[i]
			total += v[i]
		}
	}
	return total
}

// knapDP 一维滚动数组，dp[c] = 容量 c 下能装的最大价值。
// 容量必须倒序：正序会让同一件物品被装多次（那就变成了完全背包）。
func knapDP(w, v []int, capacity int) int {
	dp := make([]int, capacity+1)
	for i := range w {
		for c := capacity; c >= w[i]; c-- {
			if cand := dp[c-w[i]] + v[i]; cand > dp[c] {
				dp[c] = cand
			}
		}
	}
	return dp[capacity]
}

// ============ 区间调度：三种贪心键 ============
type iv struct{ s, e int }

func maxNonOverlap(x []iv, key func(iv) int) int {
	y := slices.Clone(x)
	slices.SortFunc(y, func(a, b iv) int { return key(a) - key(b) })
	cnt, last := 0, -1
	for _, t := range y {
		if t.s >= last {
			cnt++
			last = t.e
		}
	}
	return cnt
}

func main() {
	fmt.Printf("环境 go1.27.1 darwin/arm64 · Apple M1\n")

	// ① 贪心失效的最小反例
	w := []int{10, 20, 30}
	v := []int{60, 100, 120}
	fmt.Printf("\n① 容量 50，物品 (重量,价值)=(10,60) (20,100) (30,120)，v/w 分别为 6/5/4\n")
	fmt.Printf("   贪心拿 %d，DP 拿 %d（差 %.0f%%）\n",
		greedyKnap(w, v, 50), knapDP(w, v, 50),
```

## 可运行实测 B：剪枝与分治

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func dur(d time.Duration) float64 { return float64(d.Microseconds()) / 1000 }

func bench(reps int, f func()) time.Duration {
	best := time.Duration(1<<62 - 1)
	for i := 0; i < reps; i++ {
		t := time.Now()
		f()
		if el := time.Since(t); el < best {
			best = el
		}
	}
	return best
}

// queensPruned 边放边查冲突，冲突就砍掉整棵子树。
// 三个 bool 数组分别管「同列」「主对角」「副对角」，判定 O(1)，所以剪枝本身几乎不花钱。
func queensPruned(n int) (nodes, sols int) {
	cols := make([]bool, n)
	d1 := make([]bool, 2*n) // 主对角：row+col 恒定
	d2 := make([]bool, 2*n) // 副对角：row-col+n 恒定
	var rec func(row int)
	rec = func(row int) {
		nodes++
		if row == n {
			sols++
			return
		}
		for c := 0; c < n; c++ {
			if cols[c] || d1[row+c] || d2[row-c+n] {
				continue // 剪枝点：这一句砍掉的不是一格，是一整棵子树
			}
			cols[c], d1[row+c], d2[row-c+n] = true, true, true
			rec(row + 1)
			cols[c], d1[row+c], d2[row-c+n] = false, false, false
		}
	}
	rec(0)
	return
}

// queensNaive 只枚举「每行恰好一个皇后」的全排列，放到最后一行才校验冲突。
// 冲突判定晚了 n 层，等价于不剪枝。
func queensNaive(n int) (leaves, sols int) {
	perm := make([]int, n)
	used := make([]bool, n)
	var rec func(row int)
	rec = func(row int) {
		if row == n {
			leaves++
			ok := true
			for i := 0; i < n && ok; i++ {
				for j := i + 1; j < n; j++ {
					if perm[i]-perm[j] == i-j || perm[i]-perm[j] == j-i {
						ok = false
						break
					}
				}
			}
			if ok {
				sols++
			}
			return
		}
		for c := 0; c < n; c++ {
			if !used[c] {
				used[c], perm[row] = true, c
				rec(row + 1)
				used[c] = false
			}
		}
	}
	rec(0)
	return
}

func sumSerial(a []int64) int64 {
	var s int64
	for _, v := range a {
		s += v
	}
	return s
}

// sumParallel 切成 p 片各自求和再合并：片与片之间没有依赖，合并只要一次加法。
func sumParallel(a []int64, p int) int64 {
	part := (len(a) + p - 1) / p
	res := make([]int64, p)
	var wg sync.WaitGroup
	for i := 0; i < p; i++ {
		lo, hi := i*part, min((i+1)*part, len(a))
		if lo >= hi {
			continue
		}
		wg.Add(1)
		go func(i int, seg []int64) {
			defer wg.Done()
			var s int64
			for _, v := range seg {
				s += v
			}
			res[i] = s // 每个分片只写自己的槽，合并时不需要锁
		}(i, a[lo:hi])
	}
	wg.Wait()
	var s int64
	for _, v := range res {
		s += v
	}
	return s
}

func main() {
	fmt.Printf("环境 go1.27.1 darwin/arm64 · Apple M1 · GOMAXPROCS=%d\n", runtime.GOMAXPROCS(0))

	// ⑤ 剪枝砍掉多少：节点数只由剪枝策略决定，样本间无噪声
	fmt.Printf("\n⑤ N 皇后：剪枝 vs 只在叶子校验（节点数确定，耗时单次）\n")
	fmt.Printf("   %-4s %12s %14s %10s %12s %s\n", "N", "剪枝节点数", "不剪枝叶数", "剪枝耗时", "不剪枝耗时", "解数")
	for _, N := range []int{8, 9, 10, 11, 12} {
		t0 := time.Now()
		np, sp := queensPruned(N)
		dp := time.Since(t0)
		t1 := time.Now()
		nl, _ := queensNaive(N)
		dn := time.Since(t1)
		fmt.Printf("   %-4d %12d %14d %8.2fms %9.2fms %6d\n", N, np, nl, dur(dp), dur(dn), sp)
	}
	t0 := time.Now()
	np, sp := queensPruned(13)
	fmt.Printf("   %-4d %12d %14s %8.2fms %9s %6d\n", 13, np, "6227020800", dur(time.Since(t0)), "算不完", sp)

	// ⑥ 分治 → 并行：加速比被什么卡住
	fmt.Printf("\n⑥ 分片求和（9 次取最快，已预热）\n")
	for _, sz := range []int{2_000_000, 20_000_000} {
		big := make([]int64, sz)
		for i := range big {
			big[i] = int64(i % 1000)
		}
		d1 := bench(9, func() { sumSerial(big) })
		fmt.Printf("   %d 个 int64（%2.0f MB）单协程 %5.2f ms", sz, float64(sz*8)/1e6, dur(d1))
		for _, p := range []int{2, 4, 8} {
			sumParallel(big, p) // 预热：先付掉首次调度的钱
			dp := bench(9, func() { sumParallel(big, p) })
			fmt.Printf(" / %d 片 %.2f×", p, float64(d1)/float64(dp))
		}
		fmt.Printf("（与单线程结果一致 %v）\n", sumParallel(big, 8) == sumSerial(big))
	}
}
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 见递归就加 memo / 见递推就说是 DP | 没有重叠子问题时分治被降级成「带缓存的深搜」，多花 O(状态数) 内存还慢 |
| 贪心不做验证就上线 | 平均差 0.44%，最差差 12.5%——压测和灰度都测不出来，大促才炸 |
| 回溯不剪枝、把校验放在叶子 | N=12 从 36.55ms 变 15 022.92ms，411 倍；规模稍大直接跑不完 |
| DP 状态数不估算就动手 | 容量按「元」而不是「万元」，状态数从 1e6 涨到 1e12，永远跑不完 |
| 用精确算法硬解 NP-hard 大实例 | TSP/装箱/排班上了真实规模就是指数爆炸，正确做法是限规模或近似 |
| 把算法复杂度当分布式复杂度 | O(n log n) 优化掉 30ms，跨机房一次 RTT 就 5ms × 调用次数，主次颠倒 |
| 分片聚合时假设「结果可合并」 | 合并分片的 P99 得不到全局 P99，中位数、去重、全局 Top-K 同理 |
| 贪心键选「看起来合理」的那个 | 区间调度按开始时间排会少选 14%，按长度排少选 63% |
| 并行度直接取核数 | 内存带宽型任务 8 核只有 2.4 倍，多出的线程只增加调度开销 |

## 自检

**Q1** 分治的判据是什么？为什么「求全局 P99」不能像求和那样分片合并？

▸ 答案：判据是**子问题独立 + 结果可合并**。求和可合并，因为加法满足结合律，分片的和加起来就是全局和。P99 不可合并：分片的 P99 只描述「这个分片里最慢的 1%」，它丢掉了分布形状——一个分片 99% 都是 10ms、另一个分片 99% 都是 100ms，合并后的 P99 不是任何一个。正确做法是分片各自返回**直方图或分位数草图（t-digest）**，合并分布后再算分位点。同理不可合并的还有：去重的全局唯一性、中位数、全局 Top-K（要先各取 k 个再归并才成立）。

**Q2** 贪心在 500 个随机实例上平均只比最优差 0.44%，为什么还必须给出反例？

▸ 答案：因为**贪心的失效是结构性的，不是统计性的**。平均值 0.44% 意味着压测、灰度、A/B 全都发现不了；而最差 12.5%、手工构造的 3 件物品反例差 27%——这些实例一定会在某个业务组合上出现，且事后无从复现。所以验证贪心只有两条路：要么给出交换论证（证明它不会错），要么把最坏情况量化出来并接受（比如 FFD 装箱的 11/9 近似比）。**「跑了很多数据都对」不是证据**，它只说明你没构造出反例。

**Q3** 背包 DP 在容量 1e6 时要 846ms，为什么说它是「伪多项式时间」？工程上怎么救？

▸ 答案：O(n·W) 里的 W 是**数值大小**而不是输入的位数——容量写成二进制只要 20 bit，但状态数要 1e6 个，所以它是「关于数值多项式、关于输入长度指数」。业务含义很直接：**容量单位选得越细，跑得越慢**。三条救法：① 把单位从「元」改成「万元」，状态数降 1e4 倍；② 换状态定义（`dp[价值] = 最小重量`，让状态数由价值总和决定）；③ 接受近似（贪心 + 局部修复，或 LP 松弛后取整）。**先问「这个精度真的需要吗」，比优化递推有用得多。**

**Q4** N 皇后剪枝把节点数从 4.79e8 砍到 8.6e5（559 倍），这个倍数从哪来？如果约束更松会怎样？

▸ 答案：来自**冲突判定被提前了 n 层**。不剪枝版本要枚举全部 n! 个排列（每行恰好一个皇后），最后一个位置才检查对角线冲突；剪枝版本在放第 r 行时就能判定「同列/同主对角/同副对角」，一冲突就整棵子树丢弃。因为三个判定都是 O(1) 的 bool 数组查表，剪枝的额外开销几乎为零，所以省下的全是纯收益。**约束越松，剪枝越弱**：如果冲突只在很深的位置才出现（比如约束是「全局代价不超过 X」），前面几层全是合法分支，剪枝就退化成暴力枚举——这时要换「界剪枝」（用下界估计提前砍）或直接换算法。

**Q5** 8 核跑分片求和只有 2.2–2.4 倍，160MB 时甚至 8 片不如 4 片。钱花在哪了？

▸ 答案：花在**内存带宽**上，不是 CPU 上。求和每读 8 字节只做一次加法，单核 0.64ms 读完 16MB 相当于 25GB/s——这已经接近单核的内存读取上限，4 个核就把内存控制器吃满，第 5–8 个核在排队等数据。160MB 时更明显：数据超出 LLC，全部走主存，8 片的 2.11× 反而不如 4 片的 2.29×，多出的线程只增加调度和缓存争用。**所以「并行度 = 核数」是错的**，正确做法是先判断瓶颈类型（计算密集 → 接近核数；带宽密集 → 2–3 倍；下游依赖 → 0 倍）。

**Q6** 同样是「枚举所有可能」，什么时候该用 DP，什么时候该用回溯？

▸ 答案：看**有没有最优子结构、状态能不能压缩**。DP 要求「到某个状态为止的最优解只依赖状态本身，不依赖怎么走到这里」——背包的 `dp[c]` 只关心「容量 c 下最多装多少」，不关心装了哪几件，所以能把指数级枚举压成 n×W 个状态。回溯适合「约束复杂、可行解稀少、要输出具体方案」的问题：排班要输出每个人的具体班次，权限要输出具体组合，这些信息塞不进一个标量状态。判据一句话：**只要最终值（用 DP），要具体方案（用回溯）；状态数可控（DP），不可控（回溯 + 限规模）。**

**Q7** V=1e5、E=1e6 的依赖图，为什么不能用邻接矩阵？Dijkstra 在这张图上为什么必须用堆？

▸ 答案：矩阵要 V²=1e10 个格子——按 bool 是 **10 GB**，按 bitmap 也要 **1.25 GB**，而 CSR 邻接表只要 **4.40 MB**（实测），差 280 倍；这张图平均度数只有 10，矩阵里 99.99% 的格子是空的，纯浪费。必须用堆是因为「每步取 dist 最小的未确定点」：线性扫是 O(V) 每次、总共 O(V²)=1e10 次比较跑不动；堆把它压到 O(log V)，总体 O((V+E)logV)≈2×10⁷ 量级。实测 1e6 条边上 Dijkstra 约 60ms、BFS 约 3ms，差的就是这 20 倍的堆开销。**反过来说：如果是稠密图（E≈V²），矩阵的 O(1) 判邻接反而值那 1.25GB，判据永远是 E 与 V² 的比例，不是习惯。**
