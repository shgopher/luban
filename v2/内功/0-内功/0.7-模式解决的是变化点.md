# 0.7 模式解决的是 “变化点”：23 种模式的 Go 取舍索引

## 一句话

> 设计模式只有一句话有用——把**会变的东西**挪到**稳定的接口**后面，代价是多一层间接；Go 里最轻的隔板是函数值（实测 1.3 ns/op、0 分配），接口贵约 1 ns，每次 map 查找贵 6.7 ns，对象逃逸贵 24 B——所以手段顺序永远是「函数值 → 接口 → 抽象工厂」，反过来用就是给自己加工资以外的活。

## 判据：变化点在哪，才决定要不要加那层间接

模式不描述代码形状，描述「哪里会变」。三个真实需求，变化点标出来：

| 需求原话 | 变化点 | 不隔离的后果 | 隔离后多出来的东西 |
|---|---|---|---|
| “下单按会员等级打折，运营下周再加一档” | 折扣算法 + 档位数量 | 每加一档改 switch、发版、全链路回归 | 一张规则表 |
| “日志要能切到文件 / ES / Kafka” | 输出去向 | 业务代码里长出 3 个 if，删一个都不敢 | 一个 2 方法的接口 |
| “灰度期间按比例走新逻辑” | 走哪条路径 | 灰度代码烂在业务里，半年后没人敢删 | 一层装饰器 |

> 🔑 判据一句话：**把“会变”的部分抽走以后，稳定那部分的代码是不是变短了**。变短了，模式成立；变长了，你在为模式而模式。

变短的含义要具体到行数与改动点，不是“看起来清爽”。判据的可操作版本是三个问题：

| 问题 | 答“是”才继续 | 答“否”的处置 |
|---|---|---|
| 过去 12 个月，这里改过 ≥2 次吗 | 有变化史，值得隔离 | 记录在案，等第二次改动再抽 |
| 下次变化能不能只改配置 / 只加一个文件 | 隔离点选对了 | 换个切法，别急着加接口 |
| 加完这层，调用方要认识的名字变多了吗 | 变少或不变，可接受 | 抽象漏了，重新切 |

## 23 种模式一张表（Go 视角）

按 GoF 分类列全，重点看最后两列：变化点是什么、Go 里能用什么更轻的东西顶掉它。

| 模式 | 分类 | 意图 | 变化点 | Go 里最轻的替代 |
|---|---|---|---|---|
| 单例 | 创建型 | 全进程一个实例 | 创建时机与次数 | sync.Once + 包级变量 |
| 工厂方法 | 创建型 | 由子类决定实例化谁 | 具体类型的选择 | 返回接口的构造函数 + 注册表 |
| 抽象工厂 | 创建型 | 创建一整族相关对象 | 产品族整体替换 | 一个接口 + 一组构造函数 |
| 建造者 | 创建型 | 分步拼装复杂对象 | 可选参数的组合 | functional options |
| 原型 | 创建型 | 克隆现有对象 | 初始状态 | Clone() 方法 / 值拷贝 |
| 适配器 | 结构型 | 转换接口 | 源接口与目标接口不兼容 | 函数类型 + 一个方法 |
| 装饰器 | 结构型 | 运行时叠加职责 | 横切逻辑与顺序 | http.Handler 中间件链 |
| 代理 | 结构型 | 控制对对象的访问 | 访问时机、权限、位置 | 同接口包装 + 懒加载 |
| 门面 | 结构型 | 子系统收敛成一个入口 | 调用方要认识的类型数 | 包级 API / 一个 Service |
| 组合 | 结构型 | 树形“部分-整体” | 节点层级与类型 | 叶子与容器实现同一接口 |
| 桥接 | 结构型 | 抽象与实现分两条轴 | 两个维度独立变化 | 两个接口 + 组合 |
| 享元 | 结构型 | 共享不可变内在状态 | 实例数量与内存 | 按 key 缓存不可变值 |
| 责任链 | 行为型 | 请求沿链传递 | 处理步骤与顺序 | 中间件链 / 函数切片 |
| 命令 | 行为型 | 把请求封装成对象 | 排队、撤销、审计 | 闭包 func() |
| 解释器 | 行为型 | 给定文法的解释 | 规则表达式 | 表达式树 / 解析器生成 |
| 迭代器 | 行为型 | 顺序访问聚合元素 | 遍历方式 | range over func（Go 1.23+） |
| 中介者 | 行为型 | 交互集中到中介 | 交互拓扑 | 事件总线 / 一个协调器 |
| 备忘录 | 行为型 | 保存与恢复状态 | 状态快照 | 结构体值拷贝 |
| 观察者 | 行为型 | 一对多通知 | 订阅者集合 | channel / 回调切片 |
| 状态 | 行为型 | 状态决定行为 | 状态迁移 | 表驱动 + 接口 |
| 策略 | 行为型 | 算法可替换 | 算法的选择 | 函数值（首选）/ 接口 |
| 模板方法 | 行为型 | 骨架固定、步骤可变 | 步骤实现 | 高阶函数（把函数传进来） |
| 访问者 | 行为型 | 不改元素加新操作 | 操作种类 | type switch / 泛型 |

> 🔑 23 种里在 Go 服务端代码中真正高频的只有 7 种：**functional options、中间件（装饰器 + 责任链）、适配器、门面、组合、单例、代理**。策略基本被函数值吃掉，模板方法被高阶函数吃掉，访问者被 type switch 吃掉。

## Go 自己长出来的“模式”

把 GoF 的招式翻译成 Go 的惯用法，省掉的是命名类型与继承层级：

| GoF 的写法 | Go 惯用法 | 省掉的抽象 | 代价 |
|---|---|---|---|
| 建造者 + Director | functional options | Builder 类型、Build() | 每次构造多 3–4 次间接调用 |
| 策略 + Context | 函数值 / 方法值 | Strategy 接口与工厂 | 无法按类型断言分派 |
| 模板方法 + 抽象类 | 高阶函数传步骤 | 继承 | 步骤多时参数列表变长 |
| 单例 + 双重检查锁 | sync.Once | 锁、volatile 语义 | 测试隔离要靠重置钩子 |
| 对象池 | sync.Pool | Pool 接口 | 对象会被 GC 清掉，不能当缓存 |
| 空对象模式 | 零值可用 | NullObject 类型 | 要求设计时就想清楚零值语义 |
| 观察者 + 订阅表 | channel / 回调切片 | Observer 接口族 | 背压与生命周期要自己管 |
| 责任链 + Handler 链 | 中间件 | 链表节点 | 顺序依赖变隐式 |
| 迭代器 + hasNext | range over func | Iterator 接口 | 无法中途快照 |
| 依赖注入容器 | 构造函数显式传参 | 容器、反射、标签 | 装配代码变长 |

最后一行值得单独说：Go 社区把 DI 容器当成反模式的主力论据不是“反射慢”，而是**依赖关系从类型签名里消失了**——读 `NewOrderService(a, b, c)` 你能看到它要什么，读 `NewOrderService()` 你只能去翻容器配置。这条在 [26.2 依赖倒置](../../L2-架构风格/26-分层与依赖/26.2-依赖倒置.md) 里有完整推演。

## 判别流程：三步，别跳步

```text
① 变化点在哪？        —— 指出“哪一行代码会因为需求变化而改”，指不出就别动
② 它真的会变吗？      —— 12 个月内改过几次？git log 是证据，直觉不是
③ 用最轻的手段        —— 函数值(1.3ns) → 接口(2.3ns) → 抽象工厂(一层新类型体系)
```

三档手段的成本对照（详细数字见下一节实测）：

| 档位 | 形态 | 派发成本 | 新增概念 | 什么时候升档 |
|---|---|---|---|---|
| 一档 | 函数值 / 方法值 | 1.3 ns | 一个签名 | 默认选它 |
| 二档 | 接口（1–2 个方法） | 2.3 ns | 一个接口 + N 个类型 | 需要状态、需要 mock、实现会分叉 |
| 三档 | 抽象工厂 / 插件注册 | 一次查找 8 ns | 接口族 + 注册表 + 生命周期 | 一整族对象必须同时替换 |

“必须同时替换”是升到三档的唯一硬理由。像“MySQL 与 PostgreSQL 两套 repository 不能混用”这种约束，才配得上抽象工厂；只是“以后可能换存储”，一档函数值就够，换的时候再改。

## 同一需求三种写法：实测

需求：按会员档位算结算金额，档位参数（折扣率、满减、门槛）来自配置，运营会加档。

```go
package main

import "fmt"

type discount struct{ rate, off, min int }

var cfg = map[string]discount{
	"normal": {rate: 100},
	"vip":    {rate: 90},
	"svip":   {rate: 80},
	"promo":  {rate: 100, off: 30, min: 200},
}

// 写法 A：if-else / switch。规则常量写在代码里，改规则 = 改代码 + 重新发版。
func priceIfElse(kind string, amount int) int {
	switch kind {
	case "normal":
		return amount
	case "vip": // 9 折
		return amount * 90 / 100
	case "svip": // 8 折
		return amount * 80 / 100
	case "promo": // 满 200 减 30
		if amount >= 200 {
			return amount - 30
		}
		return amount
	}
	return amount
}

// 写法 B：函数值。变化点是一个签名 ruleFunc，规则从配置装配，改规则 = 改配置。
type ruleFunc func(amount int) int

func buildFuncRules(cfg map[string]discount) map[string]ruleFunc {
	out := make(map[string]ruleFunc, len(cfg))
	for kind, d := range cfg {
		out[kind] = func(a int) int { // 闭包捕获 d
			if d.min > 0 && a < d.min {
				return a
			}
			return a*d.rate/100 - d.off
		}
	}
	return out
}

// 写法 C：接口。变化点是一个方法集，规则是带状态的对象。
type Rule interface {
	Apply(amount int) int
}

type rateRule struct{ rate, off, min int } // 有字段：接口装箱时才有东西可逃逸

func (r rateRule) Apply(a int) int {
	if r.min > 0 && a < r.min {
		return a
	}
	return a*r.rate/100 - r.off
}

func buildIfaceRules(cfg map[string]discount) map[string]Rule {
	out := make(map[string]Rule, len(cfg))
	for kind, d := range cfg {
		out[kind] = rateRule{rate: d.rate, off: d.off, min: d.min}
	}
	return out
}

// NewRule 每次调用现造一个 —— 规则参数来自请求（例如渠道实时配置）。
func NewRule(rate int) Rule { return rateRule{rate: rate} }

func main() {
	fr := buildFuncRules(cfg)
	ir := buildIfaceRules(cfg)
	for _, k := range []string{"normal", "vip", "svip", "promo"} {
		fmt.Printf("%-6s if-else=%3d funcval=%3d iface=%3d\n",
			k, priceIfElse(k, 300), fr[k](300), ir[k].Apply(300))
	}
}
```

`go run .` 的真实输出（go1.27.1 darwin/arm64）：

```text
normal if-else=300 funcval=300 iface=300
vip    if-else=270 funcval=270 iface=270
svip   if-else=240 funcval=240 iface=240
promo  if-else=270 funcval=270 iface=270
```

三种写法结果一致，差别在成本与改动面。基准测试（同一包内 `*_test.go`，`go test -bench . -benchmem -count=3`）：

```go
package main

import "testing"

var (
	kind   = "vip"
	amount = 300
	sink   int

	funcRules  = buildFuncRules(cfg)
	ifaceRules = buildIfaceRules(cfg)
	lastRule   Rule // 接口逃逸到包级变量
)

// A：switch，编译期就把分支排好
func BenchmarkSwitch(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink = priceIfElse(kind, amount)
	}
}

// B1：函数值已解析好，只测「调用」本身
func BenchmarkFuncResolved(b *testing.B) {
	f := funcRules[kind]
	for i := 0; i < b.N; i++ {
		sink = f(amount)
	}
}

// C1：接口已解析好，只测「动态派发」本身
func BenchmarkIfaceResolved(b *testing.B) {
	r := ifaceRules[kind]
	for i := 0; i < b.N; i++ {
		sink = r.Apply(amount)
	}
}

// B2：每请求一次 map 查找 + 函数值调用
func BenchmarkFuncLookup(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink = funcRules[kind](amount)
	}
}

// C2：每请求一次 map 查找 + 接口派发
func BenchmarkIfaceLookup(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink = ifaceRules[kind].Apply(amount)
	}
}

// C3：每请求现造接口，并逃逸到包级变量
func BenchmarkIfaceEscape(b *testing.B) {
	for i := 0; i < b.N; i++ {
		lastRule = NewRule(90)
		sink = lastRule.Apply(amount)
	}
}
```

实测数字（本机，`-count=2` 两轮的区间）：

| 写法 | 净代码行 | ns/op | B/op | allocs/op | 加一档规则要改几处 |
|---|---|---|---|---|---|
| if-else / switch | 17 | 1.36–1.44 | 0 | 0 | 1 处（switch 加 case） |
| 函数值（已解析） | 18 | 1.28–1.46 | 0 | 0 | 1 处（配置加一行，不改代码） |
| 接口（已解析） | 39 | 2.25–2.34 | 0 | 0 | 2 处（新类型 + 注册） |
| 函数值 + map 查找 | 18 | 8.0–9.0 | 0 | 0 | 同上 |
| 接口 + map 查找 | 39 | 8.2–10.0 | 0 | 0 | 同上 |
| 接口每请求新建并逃逸 | 39 | 10.6–11.6 | 24 | 1 | 同上 |

净代码行 = 去掉空行、注释、package 行；接口版那 39 行里有 7 行是 `NewRule` 工厂，配置装配的话可以删。

三条读数，每条都推翻一个常见判断：

- **派发本身几乎不要钱。** 函数值 1.3 ns 对接口 2.3 ns，差 1 ns。在 P99 200 µs 的接口里，这个差别是 50 万分之一。用“接口慢”当理由选型，站不住。
- **查找才是大头。** 函数值版从 1.3 ns 涨到 8.0–9.0 ns，多出来的 6.7–7.7 ns 全是那一次 map 查找，是派发成本的 5 倍以上。所以热路径优化第一刀应该砍“每次请求查一次表”：启动时把规则解析好，或按路由 resolve 一次后往下传，而不是在 handler 里再查一遍。
- **逃逸按次收费。** 接口每请求新建并挂到对象上，多 24 B / 1 次分配（`rateRule` 三个 int 装箱）。10 万 QPS 下是 2.4 MB/s 的垃圾，GC 周期会明显变短。这就是“策略对象不要每请求 new”的量化理由。

> ⚠️ 别把这三条读成“接口不要用”。它读成的是：**用接口可以，但别在热路径上查表、别让策略对象逃逸**。Go 编译器的去虚拟化还能在部分场景把接口调用直接内联（`go build -gcflags=-m` 会打印 `devirtualizing`），这也是接口版有时测不出差距的原因。

## 边界：什么时候别加那层间接

| 情形 | 判断 | 处置 |
|---|---|---|
| 只有一个实现，也没有测试替身需求 | 接口是纯成本 | 直接用具体类型，等第二个实现出现 |
| 变化点 12 个月没动过 | 属于“设想的未来” | 记一条注释，别写抽象 |
| 只有 2 个分支、且分支里只有 1 行 | switch 更好读 | 保留 switch，别抽策略 |
| 变化的是数据结构而不是行为 | 接口帮不上忙 | 用泛型或值类型 |
| 团队里没人读得懂你的模式名 | 沟通成本 > 收益 | 用平铺的函数，命名说人话 |
| 加抽象是为了“以后换数据库” | 以后可能不来 | 等真要换时再抽，那时你已知真实接口形状 |

最后一条是经验判断，不是事实：**“以后可能要换”是最贵的四个字**。它让每一层都多一个接口，而真正换的时候，接口形状往往和当初设想的不一样，还得再改一遍。

模式不是唯一的隔板：**包的边界**往往比接口更早挡住变化——导出什么、不导出什么，决定了调用方能不能绕过你的抽象（见 [26.6 模块化与包设计](../../L2-架构风格/26-分层与依赖/26.6-模块化与包设计.md)）。模式用得对不对，最终体现在耦合度而不是模式名上，度量口径见 [40.2 耦合与内聚度量](../../L3-质量属性/40-可维护性/40.2-耦合与内聚度量.md)；能否被后来者读懂，见 [40.4 代码可读性与一致性](../../L3-质量属性/40-可维护性/40.4-代码可读性与一致性.md)。已经上线的坏抽象怎么拆是重构问题，不是设计模式问题，见 [58.7 重构三式（有的放矢 / 合纵连横 / 运筹帷幄）](../../L5-工程效能/58-架构治理/58.7-重构三式.md)。

## 反模式

| 反模式 | 后果 |
|---|---|
| 为模式而模式：先选模式再看需求 | 代码里全是 Factory / Strategy / Visitor，改一个字段要动 5 个文件 |
| 一个接口只有一个实现且无测试替身 | 多一层跳转、多一个文件，读者要在两个类型间来回跳 |
| 用模式名词当沟通语言（“这里上个责任链”） | 听的人点头，做的人各写各的，评审时才发现理解不一致 |
| 忽略 Go 惯用法，照搬 Java 23 类 | 出现 `AbstractSingletonProxyFactoryBean` 式命名，团队没人愿意维护 |
| 把 switch 硬改成策略，只为一个分支 | LOC 翻倍、性能不变，改动面反而更大 |
| 策略对象每请求 new 并挂到订单上 | 每次多 24 B / 1 次分配，高 QPS 下 GC 压力上升 |
| 抽象工厂表达“可能换存储” | 接口族膨胀，新增一个产品要改 3 个接口，最后没人敢加 |
| 用接口包一切，包括纯函数 | 调用方要构造对象才能算一个数，测试也得先 new |
| 变化点判断靠直觉，不看 git log | 抽了 5 个抽象，4 个从没变过，第 5 个变化点切错了位置 |

## 自检

**Q1** 同事说“这个 switch 必须换成策略模式”，LOC 会从 17 涨到 39。你用什么证据决定同意还是拒绝？

▸ 答案：证据是**变化频率**，不是代码美观。查 `git log -p` 里这段 switch 的提交次数：过去 12 个月改过 2 次以上、且每次都要发版回归，那 22 行买的是“加档不改代码”，划算；12 个月没动过，那 22 行就是负债。还要看第二个证据：**加档时改动点会不会外溢**——如果加一档要同时改 switch、改文档、改前端枚举，说明真正该抽的是配置格式，而不是把 switch 换成接口。

**Q2** 三种写法都在 1–2 ns，那选型到底该看什么数字？

▸ 答案：看的是**查找**和**逃逸**，不是派发。派发差 1 ns，在 200 µs 的接口里可以忽略；而每次请求查一次 map 要 6.7–8.7 ns（是派发的 4–6 倍），接口每请求新建并挂到对象上多 24 B / 1 次分配。所以优化顺序是：先把查找移出热路径（启动期解析、按路由 resolve 一次往下传），再消掉策略对象的逃逸，最后才轮到“接口还是函数值”。

**Q3** “一个接口只有一个实现”什么时候是成本，什么时候是必需的？

▸ 答案：成本是固定的——多一层间接、多一个文件、读者多一次跳转。必需的只有两种：① **要测试替身**（fake 比真依赖便宜，见 [53.6 测试替身 (mock / stub / fake)](../../L5-工程效能/53-测试与质量保障/53.6-测试替身.md)）；② **实现已经分叉或确定要分叉**（本周就要接第二种存储）。反例是“为了将来可能有的第二种实现”：将来没来，接口留下了，而且形状多半是错的。

**Q4** GoF 里有哪几种在 Go 里基本不落地？各自被什么替代？

▸ 答案：模板方法被**高阶函数**替代（Go 没有继承，把步骤作为参数传进来）；访问者被 **type switch / 泛型**替代（Go 的接口实现是开放的，加操作不必改元素）；备忘录被**结构体值拷贝**替代（值语义天然可快照）；迭代器被 **range over func**（Go 1.23 起）替代；解释器只在写 DSL 时出现，普通规则用它属于过度设计。

**Q5** functional options 属于 23 种里的哪一种？它为什么比建造者更适合 Go？

▸ 答案：属于**建造者**的变体——把“分步构建”压成“一组高阶函数”，省掉 Builder 类型和 `Build()`。它更适合 Go 的三个原因：可选参数**无序**（链式调用顺序固定）、**零值有意义**（不传就是默认值，不用构造中间态）、**没有中间对象**（实测选项固定时 24–26 ns / 1 次分配，和位置参数同级，见 [0.8 创建型 5 种：单例、工厂、建造者、原型、依赖注入](0.8-创建型模式.md)）。它的代价是每次构造多几次间接调用，以及选项多到 20 个时读者要跳 20 次。

**Q6** 抽象工厂在 Go 里为什么很少见？什么情况下才真的需要它？

▸ 答案：因为 Go 里“产品族”通常用**一个接口 + 一组构造函数**就表达了，族切换靠配置。引入 `AbstractFactory` 接口的代价是：新增一个产品要同时改三个接口和所有实现。真正需要它的场景只有一种——**整族对象必须同时替换、且混搭会出错**（例如云厂商 SDK 套装：OSS 客户端和签名器不能一个阿里一个腾讯）。判断句是“混搭会不会错”，不是“以后可能换”。

**Q7** `BenchmarkIfaceEscape` 每次多出的 24 B 是什么？如果规则类型是零字段结构体，还会分配吗？

▸ 答案：24 B 是 `rateRule`（3 个 int）被**装箱**后复制到堆上的那三个字；接口值本身只是 (itab, data) 两个机器字，`data` 指向堆上的副本。如果类型是零字段结构体（如 `type vipRule struct{}`），装箱指向运行时的 `zerobase`，**不产生分配**——这就是“空结构体实现接口不分配”的由来。反过来说，一旦给策略加了字段（阈值、比例），每个请求的分配就回来了。
