# 0.13 编程范式：Logic、Control 与 Data 的分离

## 一句话

> 程序 = Logic（做什么）+ Control（怎么做）+ Data；过程、OOP、泛型、函数式、原型、逻辑这些范式，本质都是在回答"把哪一部分标准化、把哪一部分留给业务"——架构上真正用得上的只有三条：**Logic 决定复杂度的下限，Control 可以沉淀成框架与中间件，Data 的形态决定前两者能怎么组合**。

## 先立两个等式

| 来源 | 等式 | 说明 |
|---|---|---|
| Wirth | **算法 + 数据结构 = 程序** | 经典的教科书口径 |
| Kowalski | **算法 = 逻辑 + 控制** | 把"算法"拆成两半 |

合起来就是：**程序 = Logic + Control + Data**。

| 部分 | 回答 | 能否标准化 | 举例 |
|---|---|---|---|
| **Logic** | 做什么（What） | **不能**——每个业务不同 | "满 100 减 20"、"按件数收物流费" |
| **Control** | 怎么做（How） | **能**——与业务无关 | 遍历、查找、并发、异步、重试、事务、调度 |
| **Data** | 操作什么 | 能（结构一旦定下） | 订单、用户、事件、消息 |

两条推论，直接决定后面的所有判据：

> 🔑 **同一 Logic 换一种 Control，算法的本质不变，变的只是效率。** 所以"把 for 循环改流式"、"把同步改异步"这类动作，不该改变业务语义。
>
> 🔑 **绝大多数程序混乱的根因，是业务逻辑与控制逻辑耦合。** 业务逻辑只决定复杂度的**下限**，多出来的复杂度全是 Control 没被抽走。

## 六个范式，一张谱系

| 范式 | 一句话 | 你把什么标准化了 | 代表 | 架构上的投影 |
|---|---|---|---|---|
| **过程式** | 一步步写怎么做 | 没有（控制流即业务） | C、Pascal | 业务与流程混在一个函数里，改流程=改业务 |
| **面向对象** | 名词 + 消息，封装/继承/多态 | 名词的边界与契约 | Java、C++ | **接口即协议**；但也容易长出厚重的"代码粘合层" |
| **泛型** | 类型参数化，算法与类型解耦 | 类型 + 容器操作 | C++ 模板、Go 泛型 | 容器与算法库；迭代器是最小契约 |
| **函数式** | 无状态 + 不可变，声明式 | 控制流（用组合代替步骤） | Haskell、Clojure | 并行无伤害；事件溯源、流处理 |
| **原型** | 对象直连，委托而非分类 | 对象间的查找链 | JavaScript | 运行时灵活，但缺静态契约 |
| **逻辑** | 规则 + 事实，求解器匹配回溯 | 求解过程 | Prolog | 规则引擎、风控、策略引擎 |

谱系的一端是**声明式**（只说要什么：函数式、逻辑式），另一端是**指令式**（说怎么做：过程式、OOP）。越靠声明式，Control 被语言/运行时接管得越多；越靠指令式，Control 越留在你手里。

## 三条架构判据

### 判据一：Logic 不能标准化，Control 必须标准化

这是整套范式观里最有用的一条。业务逻辑千变万化，不可能做成通用库；但"遍历、重试、超时、事务、并发、调度"与业务无关，**可以且应该沉淀到框架/中间件里**。

| 做法 | 结果 |
|---|---|
| 每个业务自己写重试、超时、幂等 | 同一套 Control 被实现 N 遍，行为还不一致 |
| Control 下沉到框架/中间件，业务只提供 Logic 与 Data | 业务代码只剩"做什么"，Control 改一次全局生效 |

对照书里的章节：重试与退避（[35.5 超时、重试与退避](../../L3-质量属性/35-可用性/35.5-超时重试与退避.md)）、幂等（[25.4 幂等设计与去重](../../L1-分布式原理/25-并发、冲突与幂等/25.4-幂等设计与去重.md)）、事务（[24.9 事务模型选型](../../L1-分布式原理/24-分布式事务/24.9-事务模型选型.md)）——它们都是 Control，都不该由每个业务自己发明。

### 判据二：标准化 Control 的前提，是标准化 Data

想复用"遍历"，先要有统一的容器契约；想复用 RPC，先要有统一的消息格式；想复用存储，先要有统一的数据模型。

泛型就是这条判据最纯粹的形态。它的本质不是"语法糖"，而是**标准化四件事**：

| 标准化的对象 | 具体内容 |
|---|---|
| 类型的内存访问 | 分配、释放、读写 |
| 类型的操作 | 加法、比较、拷贝 |
| 容器操作 | 插入、删除、遍历 |
| 类型特有操作 | 哈希、排序、序列化 |

C++ 的迭代器把这件事做到极简：容器自带 `iterator`，重载 `*`、`++`、`==`、`!=`，再 `typedef value_type`；算法只依赖这组最小约定，于是 `find`、`sort`、`accumulate` 能用于所有容器。**算法与容器的解耦，靠的不是继承，是一组最小的公共协议。**

### 判据三：接口即协议——让双方依赖标准，而不是互相依赖

OOP 的两个核心理念是"面向接口而非实现"和"优先对象组合而非类继承"，但它们经常被讲成口号。落到系统上，这句话是：

> 🔑 **接口即协议。** 浏览器与后端之所以能各自演进，是因为双方都依赖 HTTP 这个标准，而不是互相依赖对方的实现。系统内部同理：**通过抽象解耦、通过中间件解耦**，本质都是把"双方直连"换成"双方接标准"。

对照 [26.2 依赖倒置](../../L2-架构风格/26-分层与依赖/26.2-依赖倒置.md)：IoC/DIP 的本质就是"双方都依赖一个标准接口"，接口由使用方定义。平台与业务的边界之争（哪些平台做、哪些甩给业务），争的也是这条标准画在哪。

## 类型系统：两个维度、四个收益

| 维度 | 取值 | 判据 |
|---|---|---|
| **检查时机** | 静态（编译期）/ 动态（运行期） | 错误什么时候暴露给你 |
| **类型强度** | 强（只允许不丢失信息的自动转换）/ 弱 | 会不会静默截断、丢精度 |

两者是**独立**的两个维度：C 是静态弱类型，Go 是静态强类型，Python 是动态强类型。

类型系统买到四件事：**安全性、编译器优化、可读性、抽象化**。这里有一个反常识：

> 🔑 **动态类型并没有让编程更简单。** 任何语言都有类型系统，动态类型只是把检查从编译期推迟到运行期——错误还在，只是更晚发现。

泛型的收益也必须用数字说话。同样是对 1000 个 `int64` 求和，重复 100 万次（本机 `go1.27.1 darwin/arm64`）：

```go
func sumConcrete(xs []int64) int64 { /* for 累加 */ }
func sumGeneric[T int64 | int32 | float64](xs []T) T { /* for 累加 */ }
func sumAny(xs []any) int64 {
	var s int64
	for _, v := range xs {
		s += v.(int64) // 每个元素一次类型断言
	}
	return s
}
```

```text
具体类型 []int64     3284612    334.2 ns/op
泛型     []T         3642961    334.3 ns/op
interface{} []any    2128970    601.2 ns/op
```

读法：

- **泛型与具体类型同为 334 ns**——Go 的泛型在编译期按类型/GC shape 实例化，没有反射式的运行时开销，"泛型一定慢"是误读；
- **`interface{}` 贵 80%**（601 对 334 ns）——每个元素一次类型断言，且 `[]any` 本身要多一层装箱；
- 结论不是"永远用泛型"，而是：**用 `interface{}` 换通用性，是拿 80% 的 CPU 换一行代码的类型妥协**。

## 三个反常识结论

| 结论 | 出处 | 为什么重要 |
|---|---|---|
| **继承首先是为了多态，不是为了重用代码** | OOP 那一篇 | 这直接解释了"组合优于继承"（[0.11 原则优先于模式](0.11-原则优先于模式.md)）：为了重用而继承，会把父类的实现细节焊死在子类里 |
| **函数式的"数据复制严重"不一定慢** | 函数式那一篇 | 无状态就不用锁，可以把机器堆满并发；而加锁的共享状态，延迟随核数上升 |
| **业务逻辑只决定复杂度的下限** | 编程的本质那一篇 | 多出来的复杂度几乎都来自 Control 没被抽走——这是"重构先抽控制逻辑"的依据 |

## 修饰器与委托：两个"轻"范式

**修饰器**的本质是"用一个函数构造另一个函数"；Python 的 `@` 只是语法糖，等价于"传参再回调"。它真正解决的问题是把**控制型代码**抽出来：

| 被抽走的 Control | 例子 |
|---|---|
| 循环 | 对每个元素执行一次 |
| 日志 / 计时 | 进出各打一条 |
| 路由 | 按 URL 分派到处理器 |
| 重试 / 限流 | 失败重来、超限拒绝 |

Go 没有语法糖，静态类型又让"修饰任意函数"很难通用，所以通常退化成两种写法：**函数值显式包装**（`func(http.Handler) http.Handler` 这种中间件），或者用 `reflect` 做通用装饰——后者只在写框架时值得。

**委托**是原型范式的影子：原型里对象靠 `__proto__` 连成链，属性沿链查找，**是委托不是分类**；Go 里把一个 struct 嵌进另一个 struct，就是编译期的委托（嵌入、聚合、覆盖，重名要手动解决冲突）。委托 + 接口，就是 OOP 与原型两种玩法的综合。

一个真实取舍（Undo 案例）：要给一个集合加 Undo，最直觉的做法是包一层 `UndoableIntSet`，把每个写方法都重写一遍记录反操作——**改的是"所有方法"**；更好的做法是让它内部依赖一个 `Undo` 接口，业务在关键点注册回调——**改的是"一次注册"**，控制反转了，包装层也就不需要了。判据：**包装改 N 个方法，IoC 改 1 处注册。**

## 逻辑编程：把求解交给机器，但要付调试成本

逻辑编程（Prolog）只描述**事实 + 规则**，然后提问，由求解器匹配与回溯。它不关心控制，也不关心算法的具体实现。

架构上的投影是规则引擎、风控策略、权限策略：业务方写规则，引擎负责匹配。它的边界很硬：

| 适合 | 不适合 |
|---|---|
| 规则少（几十条以内）、稳定、需要频繁改动 | 规则上千条、互相冲突、要求毫秒级确定延迟 |
| 判定逻辑可枚举、可解释 | 需要复杂计算与外部调用 |
| 出问题能接受"回溯爆炸" | 需要可调试的确定路径 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 把范式当宗教（"必须 OOP"/"必须函数式"） | 团队为此付出学习与维护成本，业务没变好 |
| 业务代码里手写重试/并发/事务（Control 不上浮） | 同一套逻辑实现 N 遍，行为不一致，改一处漏九处 |
| 为了"通用"过早泛型化 | 约束写半天，调用方还要理解类型参数，收益为 0 |
| 继承复用代码（而不是为了多态） | 父类实现一改，所有子类跟着坏 |
| 用 `interface{}` 换"通用" | 本机实测慢 80%，类型安全也没了 |
| 用异常/回调做控制流 | 正常路径被错误处理打散，调试困难 |
| 规则引擎装下所有业务逻辑 | 规则冲突无法静态检查，出问题只能靠日志回溯 |

## 自检

**Q1** Logic、Control、Data 各指什么？为什么说"业务逻辑只决定复杂度的下限"？

▸ 答案：Logic = 做什么（业务语义），Control = 怎么做（遍历/并发/重试/事务/调度），Data = 操作的对象。业务本身有多复杂是客观的（下限），但你怎么组织控制流、有没有把控制逻辑重复实现 N 遍，决定了在此之上再加多少复杂度。所以"抽 Control"是降复杂度的主要手段。

**Q2** 为什么 Control 可以标准化，Logic 不能？

▸ 答案：Control（遍历、重试、超时、事务）与业务语义无关，输入输出形态固定，所以能做成库/框架/中间件；Logic 每个业务都不同，一旦试图做成通用配置，就会变成"配置里写代码"的泥潭。判断标准：这段代码换个业务还成立吗？成立就是 Control。

**Q3** 泛型的本质是什么？迭代器为什么是"最小契约"？

▸ 答案：泛型的本质是**标准化**——把类型的内存分配/释放/访问、类型的操作、容器操作、类型特有操作标准化。迭代器把这四件事压到最小：`*` 取值、`++` 前进、`==`/`!=` 判边界、`value_type` 告诉算法元素类型。算法只依赖这几个符号，就能用于所有容器——**解耦靠的是最小公共协议，不是继承体系**。

**Q4** "继承首先是为了多态"，这句话怎么推出"组合优于继承"？

▸ 答案：如果继承的目的是多态（让调用方面向接口），那么"复用父类实现"就只是副产品；一旦为了复用而继承，子类就绑定了父类的实现细节，父类一改全体受影响。组合把"复用"和"多态"分开：能力用组合拿到，多态用接口表达——两者不再互相牵连。

**Q5** 同一个求和，泛型 334.3 ns、`interface{}` 601.2 ns。为什么泛型没有变慢？

▸ 答案：Go 的泛型在编译期按实际类型实例化（单态化/GC shape 共享），生成的机器码与手写具体类型几乎一致，所以 334.2 与 334.3 没有差别；`interface{}` 则要为每个元素做接口调用 + 类型断言，还多一层装箱，成本落在每次循环里。

**Q6** 什么时候不该引入函数式或逻辑编程？

▸ 答案：三种情况。① 团队不熟：范式带来的抽象收益 < 学习与维护成本；② 规模太小：一个 `if-else` 或一个 `for` 就能说清，用管道/组合反而绕；③ 需要确定路径与毫秒级延迟：逻辑编程的回溯、函数式的惰性求值都可能让性能不可预测。判据回到第一条——**控制逻辑是否真的被标准化了**，没有就别为了范式而范式。
