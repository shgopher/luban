# 0.8 创建型 5 种：单例、工厂、建造者、原型、依赖注入

## 一句话

> 创建型只回答四个问题——**造几个**（单例：`sync.Once`）、**谁来造**（工厂：返回接口的构造函数）、**可选参数怎么传**（functional options）、**已有对象怎么复制**（`Clone` + 深拷贝）；第五种“依赖注入”在 Go 里不是框架，是把依赖写进构造函数签名。

## 5 种一张表

| 模式 | 适用场景 | Go 实现 | 代价（实测口径） | 什么时候别用 |
|---|---|---|---|---|
| 单例 | 连接池、配置、注册表 | `sync.Once` + 包级变量 | 读路径 2.4 ns（比 `RWMutex` 快 6 倍） | 有测试需要隔离状态时 |
| 工厂 | 调用方不该知道具体类型 | 返回接口的 `NewX` | 内联时 0 分配，逃逸时 3 次分配 | 只有一个实现且无替身需求 |
| 建造者 | 参数多、必填项要校验 | functional options（首选）/ 链式 Builder | options 比位置参数多 7–15 ns | 参数 ≤4 个时 |
| 原型 | 从模板复制出对象 | `Clone()` + 手写深拷贝 | 一次 `make` + 逐元素复制 | 只是值拷贝时（赋值就行） |
| 依赖注入 | 组件装配 | 构造函数注入 / wire 代码生成 | 构造函数注入 0 运行时开销 | 装配代码不到 100 行时上容器 |

> 🔑 五个里只有「单例」有并发语义，只有「原型」有内存共享语义，剩下三个都是**参数与依赖的摆放问题**——摆对了不需要任何模式名。

## 单例：`sync.Once` 是唯一正确写法

单例的难点不是“只创建一个”，是**并发下只创建一个、且其他 goroutine 不拿到半成品**。`sync.Once` 同时给这两件事：`Do` 内部有互斥与完成标志，后来的 goroutine 阻塞到函数返回。

```go
package main

import (
	"sync"
	"sync/atomic"
	"time"
)

type fakeDB struct{ conns int }

var (
	dbOnce  sync.Once
	dbInst  *fakeDB
	dbOpens int32 // 真实打开了多少次（真实系统里 = 建了多少条连接 / 读了几次配置）
)

// DB 返回进程内唯一实例。无论多少 goroutine 同时进来，初始化只做一次，
// 其余 goroutine 阻塞到初始化完成 —— 不会拿到半成品。
func DB() *fakeDB {
	dbOnce.Do(func() {
		atomic.AddInt32(&dbOpens, 1)
		time.Sleep(10 * time.Millisecond) // 模拟建连接池：慢，窗口足够宽
		dbInst = &fakeDB{conns: 10}
	})
	return dbInst
}

// DBUnsafe 是「先看看是不是 nil」的经典写法：检查与赋值之间有窗口。
var dbUnsafe *fakeDB

func DBUnsafe() *fakeDB {
	if dbUnsafe == nil {
		atomic.AddInt32(&dbOpens, 1)
		time.Sleep(10 * time.Millisecond)
		dbUnsafe = &fakeDB{conns: 10}
	}
	return dbUnsafe
}
```

用 1000 个 goroutine 同时起跑，把竞争窗口拉到最宽：

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"testing"
)

func TestOnceOnlyOnce(t *testing.T) {
	const n = 1000
	var wg sync.WaitGroup
	start := make(chan struct{})
	for i := 0; i < n; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			<-start // 同时起跑，制造最坏竞争
			if DB() == nil {
				t.Error("拿到 nil 实例")
			}
		}()
	}
	close(start)
	wg.Wait()
	fmt.Printf("sync.Once：%d 个 goroutine 并发，初始化执行 %d 次\n", n, atomic.LoadInt32(&dbOpens))
}

func TestNaiveNilCheck(t *testing.T) {
	const n = 1000
	var wg sync.WaitGroup
	start := make(chan struct{})
	for i := 0; i < n; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			<-start
			DBUnsafe()
		}()
	}
	close(start)
	wg.Wait()
	// 第一个测试已把 dbOpens 加到 1，这里减掉
	fmt.Printf("if nil 检查：%d 个 goroutine 并发，初始化执行 %d 次\n", n, atomic.LoadInt32(&dbOpens)-1)
}
```

`go test -v -run 'TestOnce|TestNaive'` 的真实输出（go1.27.1 darwin/arm64）：

```text
sync.Once：1000 个 goroutine 并发，初始化执行 1 次
if nil 检查：1000 个 goroutine 并发，初始化执行 1000 次
```

`if x == nil` 版本不是“偶尔重复”，是**几乎必然全量重复**——1000 个 goroutine 全在 sleep 期间通过了 nil 检查。真实后果是 1000 条连接、1000 次配置拉取，或者 1000 次 metric 注册 panic。

初始化完成后的读路径成本，三种写法差一个数量级：

| 写法 | ns/op | 说明 |
|---|---|---|
| `atomic.Pointer[T].Load()` | 0.90–0.98 | 最便宜，但要求实例**发布后不可变** |
| `sync.Once.Do(func(){})` | 2.35–2.48 | 通用写法，已完成时只做一次原子加载 |
| `sync.RWMutex` + `RLock` | 15.28–15.37 | 贵 6 倍，单例读路径不该用它 |

```go
package main

import (
	"sync"
	"sync/atomic"
	"testing"
)

var (
	doneOnce  sync.Once
	onceVal   *Client
	plainVal  = &Client{addr: "x"}
	rwmu      sync.RWMutex
	atomicPtr atomic.Pointer[Client]
	sink      *Client
)

func init() { doneOnce.Do(func() { onceVal = plainVal }); atomicPtr.Store(plainVal) }

func BenchmarkReadOnce(b *testing.B) {
	for i := 0; i < b.N; i++ {
		doneOnce.Do(func() {})
		sink = onceVal
	}
}

func BenchmarkReadMutex(b *testing.B) {
	for i := 0; i < b.N; i++ {
		rwmu.RLock()
		sink = plainVal
		rwmu.RUnlock()
	}
}

func BenchmarkReadAtomic(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink = atomicPtr.Load()
	}
}
```

### `init` 的四个坑

`init` 也能做单例，而且更短。但它把“创建”从调用图里挪走了，代价是四件事一起消失：

| 坑 | 具体后果 |
|---|---|
| 不能返回 error | 连不上 DB 只能 `panic`，或吞掉错误让第一次请求失败 |
| 测试无法控制 | 只想测一个纯函数，也会触发 `init` 去连 Kafka |
| 顺序是隐式的 | 同包内按**文件名字典序**初始化，改文件名可能改变行为 |
| 起 goroutine 无法回收 | 测试进程退不出、`-race` 报泄漏 |

可查证的部分是第二、三条：Go 规范规定同一包内变量的初始化顺序按文件名顺序呈现给编译器，`init` 函数按该顺序执行。所以“把 `init` 挪到 `main` 里显式调用”几乎总是净收益——代价只是 `main` 多几行。并发原语本身的细节见 [15.6 并发原语 (channel / context / sync)](../../L0-运行时底座/15-语言运行时/15.6-并发原语.md)。

单例的**测试隔离**要说清：`sync.Once` 一旦完成就无法重置，所以带单例的代码只能靠“替换接口”来测，不能靠“重置单例”。正确做法是把单例降级为依赖，注入进去：

```go
type OrderService struct{ db *fakeDB }         // 生产：NewOrderService(DB())
func NewOrderService(db *fakeDB) *OrderService { return &OrderService{db: db} }
```

测试里 `NewOrderService(&fakeDB{})`，生产里 `NewOrderService(DB())`。单例只剩“谁来提供默认实例”这一个职责。替身的选择（mock / stub / fake）见 [53.6 测试替身 (mock / stub / fake)](../../L5-工程效能/53-测试与质量保障/53.6-测试替身.md)。

## 工厂：返回接口，但别拿“性能”当理由

工厂要解决的问题只有一个：**调用方需要对象，但不该知道（也不该依赖）它是哪个具体类型**。Go 的写法是返回接口的构造函数，扩展点用注册表。

```go
package main

import "fmt"

// Store 是调用方依赖的窄接口（只有 2 个方法）。
type Store interface {
	Get(k string) (string, bool)
}

type memStore struct{ m map[string]string }

func (s *memStore) Get(k string) (string, bool) { v, ok := s.m[k]; return v, ok }

// NewStore 工厂方法：返回接口，调用方拿不到具体类型。
func NewStore(kind string) Store {
	switch kind {
	case "mem":
		return &memStore{m: map[string]string{"a": "1"}}
	}
	panic("unknown store: " + kind)
}

// NewStoreConcrete 对照：返回具体类型，能内联、能在栈上分配。
func NewStoreConcrete() *memStore { return &memStore{m: map[string]string{"a": "1"}} }

// useConcrete 只在本地用，不返回、不外传。
func useConcrete() string { s := NewStoreConcrete(); v, _ := s.Get("a"); return v }

// 注册表版：扩展时不用改 switch。
type Factory func() Store

var registry = map[string]Factory{}

func Register(kind string, f Factory) { registry[kind] = f }

func Open(kind string) (Store, error) {
	f, ok := registry[kind]
	if !ok {
		return nil, fmt.Errorf("未注册的 store: %s", kind)
	}
	return f(), nil
}
```

三级工厂的区别，一句话一层：

| 级别 | 做法 | 扩展时改哪里 | Go 里的必要性 |
|---|---|---|---|
| 简单工厂 | 一个 `switch` 返回接口 | 改 switch（违反开闭） | 够用，最常见 |
| 工厂方法 | 每种类型一个 `NewXxx() Store`，注册进表 | 新增文件 + `Register` | 插件化、驱动化时值 |
| 抽象工厂 | 一组 `NewXxx` 组成接口族 | 新增族要改所有接口 | 只在“族不能混搭”时需要 |

性能上有个反直觉的实测结论——**返回接口不等于多分配**：

| 场景 | ns/op | B/op | allocs/op |
|---|---|---|---|
| `NewStore("mem")` 被内联 | 22.8–23.0 | 0 | 0 |
| `NewStoreConcrete()` 被内联 | 20.9–24.3 | 0 | 0 |
| 两者把结果存进包级 `Store` 变量（逃逸） | 91–144 | 344 | 3 |

依据是 `go build -gcflags=-m` 的输出：内联现场打印 `factory.go:44:50: &memStore{...} does not escape`，逃逸现场打印 `factory.go:18:10: &memStore{...} escapes to heap`；同一次编译还会打印 `devirtualizing s.Get to *memStore`，说明编译器把接口调用直接换成了具体方法。

所以“工厂返回接口慢”是错的，正确的说法是：**分配只跟逃逸有关，跟用不用接口无关**。把 `Store` 存进结构体字段、放进池、跨 goroutine 传，才会 3 次分配、344 B。注意具体类型版逃逸后**同样是 3 次 344 B**，所以这 3 次是「对象 + map 头 + 首个桶」，跟用不用接口无关。反过来，如果确实不需要多态，返回具体类型的好处是**可内联**，不是“省分配”。

## 建造者：functional options 是 Go 的首选

参数一多，位置参数就变成一堵墙：`NewClient(addr, timeout, retries, tls)` 里哪个是秒、哪个是次数，只能靠记。建造者把这个顺序问题变成命名问题，Go 的答案是函数选项。

```go
package main

import "time"

type Client struct {
	addr    string
	timeout time.Duration
	retries int
	tls     bool
	tags    []string
}

// ---- 写法 A：位置参数 ----
func NewClientArgs(addr string, timeout time.Duration, retries int, tls bool) *Client {
	return &Client{addr: addr, timeout: timeout, retries: retries, tls: tls}
}

// ---- 写法 B：functional options ----
type Option func(*Client)

func WithTimeout(d time.Duration) Option { return func(c *Client) { c.timeout = d } }
func WithRetries(n int) Option           { return func(c *Client) { c.retries = n } }
func WithTLS() Option                    { return func(c *Client) { c.tls = true } }
func WithTags(t ...string) Option        { return func(c *Client) { c.tags = append(c.tags, t...) } }

func NewClient(addr string, opts ...Option) *Client {
	c := &Client{addr: addr, timeout: 3 * time.Second} // 默认值只写一次
	for _, o := range opts {
		o(c)
	}
	return c
}

// ---- 写法 C：链式 Builder ----
type Builder struct{ c Client }

func NewBuilder(addr string) *Builder {
	return &Builder{c: Client{addr: addr, timeout: 3 * time.Second}}
}

func (b *Builder) Timeout(d time.Duration) *Builder { b.c.timeout = d; return b }
func (b *Builder) Retries(n int) *Builder           { b.c.retries = n; return b }
func (b *Builder) TLS() *Builder                    { b.c.tls = true; return b }
func (b *Builder) Build() *Client                   { return &b.c }
```

三种写法实测（`go test -bench . -benchmem -count=3`）：

| 写法 | ns/op | B/op | allocs/op | 备注 |
|---|---|---|---|---|
| 位置参数 | 19.2–21.6 | 64 | 1 | 参数顺序靠记，加参数破坏兼容 |
| options（选项启动时建好） | 26.5–35.2 | 64 | 1 | 不传切片选项时，无额外分配 |
| options（带 `WithTags`） | 54.7–56.1 | 96 | 2 | 多出的 32 B 是 tags 的底层数组 |
| options（选项热路径现造） | 56.9–59.3 | 96 | 2 | 闭包没多分配，多的是 tags |
| 链式 Builder | 20.2–21.0 | 64 | 1 | Builder 本身被内联到栈上 |
| Builder（不带 tags） | 17.4–19.5 | 64 | 1 | 同上 |

两条结论都反直觉：

- **闭包不额外分配。** `WithTimeout(5*time.Second)` 返回的闭包在选项切片不逃逸时会被分配在栈上，所以“options 会造一堆闭包、很浪费”是错的。真正多出来的 32 B 是 `WithTags` 的切片扩容，跟 options 无关。
- **options 比位置参数贵约 7–15 ns**，贵在 3–4 次间接调用。这个数是确定的成本，不是“差不多”。换来的东西是：可选参数无序、零值有默认、新增参数不破坏调用方。

什么时候仍然用链式 Builder：**你需要在 `Build()` 里做一次集中校验**（必填项、互斥项），或者**需要在 Build 前把“半成品”传出去**（分两步装配）。这两种情况下 Builder 的 `Build() error` 是位置参数和 options 都没有的位置。除此之外，options 更短。

> 🔑 选择顺序：参数 ≤4 → 位置参数；参数多、有可选 → functional options；需要集中校验或分阶段装配 → 链式 Builder。

## 原型：Go 里最能骗人的一个 `clone`

原型模式在 Go 里用得少，因为结构体赋值就是浅拷贝、字面量重建就是深拷贝。但它有一个必须讲清的地方：**浅拷贝在含 slice/map/指针的结构体上会静默共享内存**，而 Go 不会报错。

```go
package main

import "fmt"

type Template struct {
	Name string
	Tags []string          // 引用类型：浅拷贝会共享底层数组
	Meta map[string]string // 同上
}

// CloneShallow 只复制结构体头，Tags/Meta 仍指向同一份底层数据。
func (t *Template) CloneShallow() *Template { c := *t; return &c }

// Clone 深拷贝：切片与 map 都重新分配。
func (t *Template) Clone() *Template {
	c := *t
	c.Tags = append([]string(nil), t.Tags...)
	c.Meta = make(map[string]string, len(t.Meta))
	for k, v := range t.Meta {
		c.Meta[k] = v
	}
	return &c
}

func newBase() *Template {
	return &Template{Name: "svc", Tags: []string{"prod"}, Meta: map[string]string{"team": "infra"}}
}

func demoClone() {
	s := newBase()
	sc := s.CloneShallow()
	sc.Tags[0] = "dev"
	sc.Meta["team"] = "growth"
	fmt.Printf("浅拷贝改 clone 后，原对象：Tags=%v Meta=%v\n", s.Tags, s.Meta)

	d := newBase()
	dc := d.Clone()
	dc.Tags[0] = "canary"
	dc.Meta["team"] = "sre"
	fmt.Printf("深拷贝改 clone 后，原对象：Tags=%v Meta=%v\n", d.Tags, d.Meta)
}
```

`go run .` 的真实输出：

```text
浅拷贝改 clone 后，原对象：Tags=[dev] Meta=map[team:growth]
深拷贝改 clone 后，原对象：Tags=[prod] Meta=map[team:infra]
```

第一行就是事故现场：**改克隆体，原件跟着变**。按字段类型把坑列全：

| 字段类型 | 浅拷贝的后果 | 正确做法 |
|---|---|---|
| `[]T` | 共享底层数组，`append` 未扩容时互相覆盖 | `append([]T(nil), src...)` |
| `map[K]V` | 共享同一张表，增删互见 | `make` + 逐 key 复制 |
| `*T` | 两个指针指向同一对象 | 递归 `Clone` 或重新构造 |
| `interface{}` | 只复制接口值，底层对象仍共享 | 按动态类型分派后再 Clone |
| `sync.Mutex` | 复制出一个“锁住状态”的锁，临界区保护错乱 | 用指针字段，或 `Clone` 里清零 |
| `time.Time` | 值拷贝，`*Location` 只读共享 | 直接复制，安全 |

最后一行是常见的过度担心：`time.Time` 里的指针指向只读时区数据，复制安全。真正危险的是**可变**的引用字段。工业级做法是代码生成（Kubernetes 的 `DeepCopy()` 就是生成出来的），因为手写深拷贝最容易漏字段——加了新字段忘了改 `Clone`，测试也测不出来。

## 依赖注入：显式比容器好，除非装配代码过了 100 行

依赖注入不是模式，是**把依赖写成参数**。Go 里三种做法：

| 方式 | 代表 | 依赖可见性 | 启动开销 | 编译期检查 | 适合 |
|---|---|---|---|---|---|
| 构造函数注入 | 手写 `NewX(a, b, c)` | 看签名就知道 | 0 | 有 | 绝大多数服务 |
| 代码生成 | google/wire | 生成代码可读 | 0（编译期） | 有 | 装配代码上百行 |
| 反射容器 | uber-go/dig、fx | 藏在容器里 | 启动期解析（本机未实测） | 无，运行时报错 | 插件化框架 |

构造函数注入的取舍是明确的：**装配代码变长，依赖关系变清楚**。一个 50 个组件的服务，`main` 里会有 50 行 `NewXxx(...)`——这 50 行是资产，不是负债：读它就知道谁依赖谁，删一个组件编译器会告诉你哪里断。

容器把 50 行换成 5 行注册，代价是三条：① 依赖关系从类型签名里消失，改一个构造函数参数，编译期不报错、启动才报错；② 循环依赖变成运行时问题；③ 单测要构造容器才能拿到对象。

代码生成（wire）是折中：写 provider 集合，生成 `wire_gen.go` 里的显式构造函数——**运行时零反射、依赖关系仍可见**，代价是多一个构建步骤。我的判断是：装配代码不到 100 行就用构造函数注入，超过 100 行再考虑 wire，反射容器只在写框架时用。这条判断的依据不是性能，是**排障成本**：启动失败时，`main` 里第 37 行的构造函数比容器里一句 “no provider found for *sql.DB” 好查得多。装配方式还会直接决定单测的成本——依赖从签名来，测试就能用一个构造函数换掉一个替身，整体做法见 [53.2 单元测试](../../L5-工程效能/53-测试与质量保障/53.2-单元测试.md)。依赖倒置的原则层面见 [26.2 依赖倒置](../../L2-架构风格/26-分层与依赖/26.2-依赖倒置.md)。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用包级单例当全局变量传参 | 任何包都能改它，测试之间互相污染，改一处影响全进程 |
| `if inst == nil { inst = new() }` 做单例 | 并发下初始化 1000 次（实测），连接池被打爆 |
| 在 `init` 里建连接、拉配置 | 连不上就 panic，单测跑不起来，顺序靠文件名 |
| 工厂返回具体类型却叫“工厂” | 调用方绑死实现，想换时改所有调用点 |
| 以为“返回接口一定多分配” | 内联后 0 分配；真凶是逃逸，优化错方向 |
| 用 options 表达必填参数 | 漏传时静默取零值，错误在运行时才暴露 |
| 建造者套建造者（`Build()` 里再 `NewBuilder`） | 两层默认值互相覆盖，谁生效说不清 |
| `Clone` 只做 `*t` 浅拷贝 | 改克隆体污染原件，且没有任何编译/运行时报错 |
| 加字段忘了更新 `Clone` | 新字段在克隆体里是零值，bug 表现为“偶发丢配置” |
| 为了 DI 引入反射容器 | 启动失败信息变成容器内部报错，排障时间翻倍 |

## 自检

**Q1** 用 1000 个 goroutine 测单例，`sync.Once` 版执行 1 次；把 `Do` 换成 `if x == nil` 执行 1000 次。为什么是 1000 而不是“几次”？

▸ 答案：因为被检查的写操作发生在**慢操作之后**（例子里是 10 ms 的建连接），1000 个 goroutine 几乎同时通过 nil 检查，然后一起进入慢操作，最后各自赋值。窗口宽度约等于慢操作的耗时，所以只要 goroutine 起跑时间差小于这个窗口，就是全量重复。结论：`if nil` 只在“初始化极快且无并发”时偶然正确，它不是“弱一点的单例”，是错的单例。

**Q2** 单例初始化完成后，读路径用 `sync.Once`、`RWMutex`、`atomic.Pointer` 分别是多少 ns？为什么不该用 `RWMutex`？

▸ 答案：实测 2.4 ns / 15.3 ns / 0.95 ns。`RWMutex` 贵 6 倍的原因是要改 reader 计数（一次原子加 + 一次原子减），而 `Once.Do` 完成后只做一次原子加载。`atomic.Pointer` 最便宜但有额外约束：**发布后对象必须不可变**，否则你就是用手写原子操作绕过了锁，而没得到任何内存序保证。

**Q3** 工厂返回接口和返回具体类型，实测分配次数一样。那“返回接口”的真实代价是什么？

▸ 答案：代价不是分配，是**失去内联**。具体类型被内联后，编译器能做逃逸分析、栈分配、去虚拟化（`-gcflags=-m` 里的 `devirtualizing`）；接口在跨包、多实现时会退化成动态派发，每次多约 1 ns，并且阻止后续优化。真正的分配差异来自**逃逸**：只要对象被存进包级变量、结构体字段、池或跨 goroutine，接口版和具体版都是 3 次分配、344 B。所以选接口的理由应该是“调用方不该依赖实现”，不是“性能”。

**Q4** functional options 每次都创建闭包，为什么实测没有多分配？那 32 B 是哪来的？

▸ 答案：选项切片在 `NewClient` 内部消费完就死掉，不逃逸，闭包被分配在**栈**上，所以不计入 `allocs/op`。多出来的 32 B 来自 `WithTags("blue","canary")` 里 `append` 到 nil 切片产生的底层数组——这是切片语义的成本，不是 options 的成本。验证方法：把 `WithTags` 去掉，同一个构造函数回到 64 B / 1 次分配。

**Q5** 链式 Builder 在实测里比 options 还便宜（20 ns vs 26 ns），那为什么说 options 是首选？

▸ 答案：因为那 6 ns 买的东西不一样。Builder 的 `Build()` 能返回 error、能做集中校验、能分阶段装配；options 换来的是**可选参数无序、默认值只写一次、新增选项不破坏调用方**。20 ns 对 26 ns 的差别在真实构造频率下（每秒几次到几千次）可以忽略，而“加一个参数要不要改 300 个调用点”是每天都要付的成本。只有当构造发生在热路径（每请求一次）时才需要重新算这笔账——那时两者都该挪出热路径。

**Q6** `CloneShallow` 改完克隆体，原件的 `Tags` 变了。如果结构体里只有 `time.Time` 和 `string`，还需要写 `Clone` 吗？

▸ 答案：不需要。`string` 不可变，`time.Time` 虽是结构体但内部指针只指向只读时区数据，值拷贝完全安全。需要深拷贝的判据是**字段里有没有可变的引用类型**（slice / map / 指针 / 含这些字段的结构体）。反过来说，如果结构体全是不可变字段，“原型模式”就退化成一次赋值，写 `Clone` 只是多一个要维护的函数——以及一个加字段时会忘掉的地方。

**Q7** 团队要把 50 个组件的装配从 `main` 里的构造函数改成 dig 容器，说“少 45 行代码”。你怎么判断该不该同意？

▸ 答案：看三条成本谁更大。① **排障**：构造函数版启动失败直接指向第 37 行；容器版是运行时的 “missing dependency”，要读容器日志。② **编译期**：改构造函数签名，构造函数版立刻编译失败；容器版启动才炸。③ **测试**：容器版要先建容器才能拿到一个对象。省下的 45 行是一次性成本，这三条是每天的成本。**同意的前提**是装配规模继续增长（上百个组件、多套环境组合），或者需要插件化动态注册；否则 wire 这类代码生成是更好的中间态。
