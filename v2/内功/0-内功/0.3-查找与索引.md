# 0.3 查找与索引：二分、B+ 树、LSM、跳表、倒排

## 一句话

> 查找只有四种加速原理——**有序（二分 / 树 / 跳表）、哈希（等值）、分区（把 n 变小）、摘要（先否决）**；选型不看结构名字，看查询形状：等值、范围、前缀、全文、排序各只有一个正确答案，选错的代价是 “索引白建 + 写放大”。

## 四种原理，一张表看清

| 原理 | 代表结构 | 支持的查询形状 | 代价 |
|---|---|---|---|
| 有序 | 二分、红黑树、B+ 树、跳表 | 等值、范围、前缀、排序、Top-K | 维护有序 O(log n)，写放大 |
| 哈希 | 哈希表、哈希索引 | 等值、`IN` | 范围与排序彻底无能 |
| 分区 | 分片、分区表、一致性哈希 | 把 n 从 1e9 降到 1e6 | 跨分区要 scatter-gather |
| 摘要 | 布隆过滤器、位图 | 存在性 / 否决 | 假阳性，取不回原值 |

后两行常被忽略：**很多 “查找慢” 不是结构选错，是 n 根本没降下来**。1e9 行先按用户分区成 1e4 个 1e5 行的分区，再在分区里做任何查找，都比 “给 1e9 行加一个更强的索引” 便宜。

> 🔑 选索引就是选 “支持哪种查询形状”，每种结构都在这个维度上做减法。**没有一个索引能同时做好等值、范围、前缀、全文。**

## 二分：`sort.Search` 返回的是插入点，不是 “找到的下标”

`sort.Search(n, pred)` 返回**第一个让谓词为真的下标**；`sort.SearchInts(a, x)` 是 “第一个 `a[i] >= x` 的位置”，也就是插入点。

同一份含重复元素的数据 `[1, 3, 3, 3, 5, 8]`，四种写法的对比（本机实测）：

| x | lowerBound | upperBound | sort.SearchInts | 找到就返回（教科书写法） | 真的存在吗 |
|---|---|---|---|---|---|
| 0 | 0 | 0 | 0 | -1 | 否 |
| 1 | 0 | 1 | 0 | 0 | 是 |
| 3 | 1 | 4 | 1 | **2** | 是 |
| 4 | 4 | 4 | 4 | -1 | 否 |
| 5 | 4 | 5 | 4 | 4 | 是 |
| 8 | 5 | 6 | 5 | 5 | 是 |
| 9 | 6 | 6 | 6 | -1 | 否 |

三个必须记住的点：

- **找不到时返回 `len(a)`**：x=9 时返回 6，而数组长度也是 6。直接 `a[sort.SearchInts(a, 9)]` 会 panic：`index out of range [6] with length 6`（本机实测）。返回值语义没错，错在把它当有效下标。
- **x=3 时 “找到就返回” 返回 2**，不是第一个 3。做范围查询左边界必须用 lowerBound，否则 `[3, 5)` 会被算成 `[2, 5)`，多算一个元素。
- **出现次数 = upperBound - lowerBound** = 4 - 1 = 3。要 “去重后的区间” 就靠这两个边界，不能靠 “找到一个就算”。

正确写法只有两行，两个条件缺一不可：

```go
i := sort.SearchInts(a, x)
found := i < len(a) && a[i] == x
```

## 1e7 实测：二分 130 ns，map 13 ns，线性扫 3.9 ms

同一份 1e7 个 int64 的有序数组（每元素 = 2×下标），查 1000 个存在的 key：

| 方案 | 每次查询 | 额外内存 | 说明 |
|---|---|---|---|
| 线性扫描 | 3 907 160 ns（3.9 ms） | 0 | 平均扫 500 万元素 = 40 MB，带宽受限 |
| 手写二分 | 130.4 ns | 0（数组本体 80 MB） | 24 次比较 |
| `sort.Search` | 97.4 ns | 0 | 闭包被内联，反而快 25% |
| `map[int64]int32` | 12.6 ns | 303 MB（30.3 B/条） | 只支持等值 |

三个反直觉的读数：

1. **二分比 map 慢 10 倍**，不是慢 100 倍。因为 1000 个 key 的工作集很小，二分路径顶端的十几层节点一直待在缓存里，24 次比较里大部分是命中。
2. **`sort.Search` 比手写快 25%**。同一个算法，常数由编译器决定：闭包被内联后循环更紧凑。**别凭直觉认为 “手写一定更快”**，Go 的标准库 `sort.Search` 是二分查找的正确起点。
3. **冷热差 3–5 倍**。同一进程连跑 6 轮、每轮 1000 次：

| 轮次 | 二分 ns/次 | map ns/次 |
|---|---|---|
| 1 | 442 | 81 |
| 2 | 177 | 21 |
| 3 | 184 | 27 |
| 4 | 169 | 21 |
| 5 | 161 | 20 |
| 6 | 157 | 18 |

第一轮是真实的冷态（页表、TLB、cache 全空），后面趋于 157/18。线上的机器重启、缓存刷新、进程迁移都会回到 “第一轮”。

> 🔑 索引的收益在稳态下测（跑热、缓存命中），容量规划按冷态算。**拿第一轮的数做容量、拿稳态的数做 SLO，都会偏。**

## 有序数组的代价：插入要挪 40 MB

二分的前提是有序，而维护有序不便宜：

- 往 1e7 个 int64 的中间插一个元素，平均要挪 500 万个元素 = **40 MB**。按本机 10 GB/s 量级的拷贝带宽估算，单次约 4 ms——比一次线性扫（3.9 ms 实测）还贵。
- 所以 “有序数组 + 二分” 只适合**写少读多、批量重建**的场景：配置表、字典、只读快照、离线数据。
- 要频繁插入又要范围查询 → 跳表或 B+ 树。

## B+ 树 vs LSM：三个放大（客场，只给结论）

| 指标 | B+ 树 | LSM 树 | 谁更差 |
|---|---|---|---|
| 读放大 | 一次查找 = 树高 3–4 次页读 | 每层都要查，10–30 个 SSTable（配布隆可砍掉大部分探测） | LSM |
| 写放大 | 页内更新 + WAL + doublewrite，约 2–3 倍 | compaction 反复重写，10–30 倍 | LSM |
| 空间放大 | 页填充率 ~70% 加碎片 | 多版本 + tombstone，1.1–2 倍 | 相当 |
| 写延迟形态 | 随机写 + fsync，P99 抖动大 | 顺序写，P99 稳但 compaction 有尖刺 | 看负载 |
| 范围查询 | 叶子链表顺序扫，天然友好 | 要合并多层，memtable + 多个 SSTable | B+ 树 |

判据（我的判断）：读多写少、要事务 / 范围 / 二级索引 → B+ 树；写多读少、能接受读放大（配布隆过滤器 + block cache）→ LSM。两边的机制见 [44.1 存储引擎：B+ 树与 LSM 树](../../L4-组件与技术/44-数据库/44.1-存储引擎B+树与LSM.md)；LSM 的读放大靠的就是 “先否决”，见 [41.8 布隆过滤器](../../L4-组件与技术/41-缓存/41.8-布隆过滤器.md)。

## 哈希索引：等值 O(1)，范围彻底无能

- 支持：`=`、`IN`。不支持：`>`、`<`、`BETWEEN`、`ORDER BY`、前缀 `LIKE 'abc%'`——哈希把顺序打散了，相邻 key 落在不同桶。
- 现实里的哈希索引：MySQL 的 MEMORY 引擎默认哈希索引；InnoDB 的自适应哈希索引（AHI）只对热点等值查询自动加，范围查询仍走 B+ 树。
- 低基数列（性别、状态）建哈希索引没有意义：桶内还是几百万行，等于没索引。

## 倒排：term → posting list

- 结构：term dictionary（有序，可二分、可前缀匹配）+ posting list（按 docID 升序）。
- **posting list 必须按 docID 有序**：AND 求交用归并或跳表跳跃；无序就只能哈希求交，内存翻几倍。
- 前缀查询、拼写纠错、短语匹配都建立在 term dictionary 的有序性上。
- 全文检索的主场是 [45.1 倒排索引与分词](../../L4-组件与技术/45-检索与搜索引擎/45.1-倒排索引与分词.md)。

## 选型表：查询形状决定结构

| 查询形状 | 首选 | 次选 | 别用 |
|---|---|---|---|
| 等值（内存） | 哈希表 / map | 有序数组二分 | 跳表（多付内存与实现） |
| 等值（磁盘、单点） | B+ 树唯一索引 | 哈希索引 | 全表扫 |
| 范围 `>` `<` `BETWEEN` | B+ 树 | 有序数组 / 跳表 | 哈希索引 |
| 前缀 `LIKE 'abc%'` | B+ 树最左前缀 | 有序数组二分 | 哈希、`%abc%` |
| 全文 / 模糊 | 倒排（分词 / ngram） | 倒排 + 前缀树 | `LIKE '%x%'` |
| Top-K 排序 | 有序索引 + LIMIT | 内存堆 | 全量排序后取前 K |
| 海量存在性判断 | 布隆过滤器 / 位图 | 哈希表 | 任何树 |

回表、覆盖索引、最左前缀的完整规则见 [44.8 索引原理 (B+ 树 / 哈希 / 覆盖索引 / 最左前缀)](../../L4-组件与技术/44-数据库/44.8-索引原理.md)。

## 实测代码与输出

环境：go1.27.1 darwin/arm64，Apple M1，macOS。代码在 `/tmp/luban-a/b03`。

```go
package main

import (
	"fmt"
	"runtime"
	"sort"
	"time"
)

// lowerBound 手写二分：返回第一个 a[i] >= x 的下标，全小于 x 时返回 len(a)。
func lowerBound(a []int, x int) int {
	lo, hi := 0, len(a)
	for lo < hi {
		mid := int(uint(lo+hi) >> 1) // 无符号右移，避免 lo+hi 溢出成负
		if a[mid] < x {
			lo = mid + 1
		} else {
			hi = mid
		}
	}
	return lo
}

// upperBound：返回第一个 a[i] > x 的下标。两者相减 = x 的出现次数。
func upperBound(a []int, x int) int {
	lo, hi := 0, len(a)
	for lo < hi {
		mid := int(uint(lo+hi) >> 1)
		if a[mid] <= x {
			lo = mid + 1
		} else {
			hi = mid
		}
	}
	return lo
}

// buggyEqual 是教科书式「找到就返回」：重复元素时可能返回中间那个。
func buggyEqual(a []int, x int) int {
	lo, hi := 0, len(a)-1
	for lo <= hi {
		mid := (lo + hi) / 2
		if a[mid] == x {
			return mid
		}
		if a[mid] < x {
			lo = mid + 1
		} else {
			hi = mid - 1
		}
	}
	return -1
}

// sortSearchInt64 用标准库 sort.Search 写同一个 lowerBound，作为对照。
func sortSearchInt64(a []int64, x int64) int {
	return sort.Search(len(a), func(i int) bool { return a[i] >= x })
}

// buildMap 建「值 → 下标」的哈希索引；main 与 benchmark 共用。
func buildMap() {
	idxMap = make(map[int64]int32, n)
	for i := 0; i < n; i++ {
		idxMap[sortedArr[i]] = int32(i)
	}
}

func readHeap() uint64 {
	runtime.GC()
	var s runtime.MemStats
	runtime.ReadMemStats(&s)
	return s.HeapAlloc
}

const n = 10_000_000

var (
	sortedArr []int64         // 已排序：sortedArr[i] = 2*i
	keys      []int64         // 1000 个用来查的 key，全部存在
	idxMap    map[int64]int32 // 值 → 下标，在 main 里建，便于测它的内存
)

func init() {
	sortedArr = make([]int64, n)
	for i := 0; i < n; i++ {
		sortedArr[i] = int64(2 * i)
	}
	keys = make([]int64, 1000)
	for i := range keys {
		keys[i] = int64(2 * (i * 9973 % n)) // 9973 与 n 互质，打散分布
	}
}

func main() {
	fmt.Println("go1.27.1 darwin/arm64 / Apple M1")
	fmt.Println()
	fmt.Println("== ① 边界语义：同一份数据，四种写法给出不同答案 ==")
	a := []int{1, 3, 3, 3, 5, 8}
	fmt.Printf("%4s %10s %10s %14s %12s %6s\n", "x", "lowerBound", "upperBound", "sort.SearchInts", "buggyEqual", "存在")
	for _, x := range []int{0, 1, 3, 4, 5, 8, 9} {
		lb := lowerBound(a, x)
		ub := upperBound(a, x)
		si := sort.SearchInts(a, x)
		exists := "否"
		if lb < len(a) && a[lb] == x {
			exists = "是"
		}
		fmt.Printf("%4d %10d %10d %14d %12d %6s\n", x, lb, ub, si, buggyEqual(a, x), exists)
	}
	fmt.Println("注：lowerBound 与 sort.SearchInts 都是插入点；还要再判 a[i]==x 才算存在")
	fmt.Printf("x=3 出现次数 = upperBound-lowerBound = %d\n", upperBound(a, 3)-lowerBound(a, 3))

	fmt.Println()
	fmt.Println("== ② 越界：把插入点当下标用 ==")
	func() {
		defer func() {
			if r := recover(); r != nil {
				fmt.Printf("a[sort.SearchInts(a,9)] 直接 panic：%v\n", r)
			}
		}()
		_ = a[sort.SearchInts(a, 9)] // 9 比所有元素都大 → 返回 6，越界
	}()

	fmt.Println()
	fmt.Println("== ③ 同一份 1e7 数据，连跑 6 轮、每轮 1000 次查询 ==")
	var p, q int
	base := readHeap()
	buildMap()
	mapMB := float64(readHeap()-base) / 1e6
	fmt.Printf("%4s %14s %14s\n", "轮次", "二分 ns/次", "map ns/次")
	for round := 1; round <= 6; round++ {
		t0 := time.Now()
		p = 0
		for i := 0; i < 1000; i++ {
			lo, hi := 0, n
			for lo < hi {
				mid := int(uint(lo+hi) >> 1)
				if sortedArr[mid] < keys[i] {
					lo = mid + 1
				} else {
					hi = mid
				}
			}
			p += lo
		}
		bin := time.Since(t0)

		t0 = time.Now()
		q = 0
		for i := 0; i < 1000; i++ {
			q += int(idxMap[keys[i]])
		}
		mp := time.Since(t0)
		fmt.Printf("%4d %14.0f %14.0f\n", round,
			float64(bin.Nanoseconds())/1000, float64(mp.Nanoseconds())/1000)
	}
	fmt.Printf("校验命中位置一致：二分 %d，map %d\n", p/1000, q/1000)
	fmt.Printf("数组本体 %.0f MB；map 建表额外占 %.0f MB（%.1f B/条）\n",
		float64(n*8)/1e6, mapMB, mapMB*1e6/float64(n))
}
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 低基数列建 B+ 树索引（性别 / 状态 / 是否删除） | 选择性 1% 时要回表几百万行随机 IO，优化器直接放弃索引，只剩写放大 |
| 想用索引加速 `LIKE '%abc%'` | 最左前缀失效，退化成全表扫 + 逐行匹配，索引白建 |
| 把索引当缓存（“加了索引就该快”） | 索引只省 “定位”，不省 “取数”；回表与网络往返才是大头 |
| `SELECT *` 走二级索引，忽略回表 | 每行一次随机回表，1 万行就是 1 万次随机 IO；该用覆盖索引 |
| 盲目加索引，一张表 12 个 | 每次写要维护 12 个索引页，写放大 3 倍以上，空间翻倍 |
| 用哈希索引做范围查询 | `>`、`BETWEEN`、`ORDER BY` 全部失效，只能全扫 |
| `a[sort.SearchInts(a, x)]` 不加边界判断 | 找不到时返回 `len(a)`，直接 panic |
| 用 “找到就返回” 的二分做范围左边界 | 重复元素时返回中间某个位置，范围多算或漏算 |
| 1e7 行有序数组频繁中间插入 | 每次插挪 40 MB，比全表扫还慢 |

## 自检

**Q1** `sort.SearchInts` 返回 6，而数组长度正好是 6。返回值错了还是你的用法错了？

▸ 答案：返回值没错，语义是 “插入点”：x 比所有元素都大，插在末尾，下标 6。错在把它当有效下标用，`a[6]` 越界 panic。正确判断是 `i < len(a) && a[i] == x` 两步——**第一个条件防越界，第二个条件防 “找错位置”（返回的是第一个 ≥x 的位置，可能不等于 x）**。

**Q2** 1e7 有序数组二分 130 ns、map 13 ns，为什么数据库还用 B+ 树而不是哈希索引？

▸ 答案：三条。① 范围与排序：哈希不支持 `>`、`BETWEEN`、`ORDER BY`，这是 B+ 树的看家本领；② 内存：1e9 行时有序数组要 8 GB 常驻，B+ 树只把热页放内存，3–4 次页读就能定位；③ 更新：B+ 树页内更新，有序数组插中间要挪 40 MB。**内存等值 → map；磁盘 + 范围 → B+ 树。**

**Q3** LSM 的读放大更差，为什么写更快？给一个能拍板的业务判据。

▸ 答案：LSM 的写全是顺序追加 + 批量 compaction，B+ 树是随机页写 + 页分裂 + WAL。判据：写多读少、能接受读放大（用布隆砍掉大部分 SSTable 探测、用 block cache 兜住热数据）、不需要跨行事务 → 选 LSM；读多写少、要事务与二级索引 → 选 B+ 树。**别看单次读的延迟，看 “读写比 + 能否容忍 P99 的 compaction 尖刺”。**

**Q4** 一张 1e7 行的表，`status` 只有 3 个值，建了索引为什么还是全表扫？

▸ 答案：选择性 = 1/3，每个值约 333 万行。走索引要 333 万次随机回表，比全表顺序扫（40 MB 带宽）慢得多，优化器按代价估算主动放弃索引。低基数列的正确用法：放进组合索引的非首列（配合高基数列）、用位图索引（OLAP 场景）、或者干脆预聚合。**索引的选择性低于 10% 时，基本不要指望优化器用它。**

**Q5** 哈希索引做不了 `LIKE 'abc%'`，B+ 树为什么可以？

▸ 答案：哈希把 key 打散到桶里，字典序信息在哈希那一刻就丢了，`abc%` 只能全桶扫。B+ 树的叶子按 key 有序，`abc%` 等价于区间 `[abc, abd)`，一次范围扫即可。**“前缀” 本质是范围查询，凡是破坏顺序的索引都做不了前缀。**

**Q6** 为什么 1e7 的有序数组不适合频繁插入，即使查找只要 130 ns？

▸ 答案：插入要挪后半段，平均 500 万元素 = 40 MB 内存搬移（按 10 GB/s 量级估算约 4 ms），比一次线性扫（3.9 ms 实测）还贵。查找快不能抵消写入慢。要 “范围查询 + 频繁写” 就用跳表或 B+ 树——它们把 “挪动” 换成 “局部改指针 / 页分裂”。

**Q7** 查询是 “按用户 ID 取最近 20 条订单”，该建什么索引？为什么不是 “只建 user_id 然后内存排序”？

▸ 答案：建组合索引 `(user_id, created_at DESC)`。这样一次 B+ 树定位 + 叶子链表顺序取 20 行就结束，代价 O(log n + 20)。只建 `user_id` 会把该用户全部订单（可能几万条）取出来再排序，代价随订单数线性增长，还要占内存与网络。**“取前 K 条” 的查询，索引里必须带上排序字段，否则排序一定发生在内存里。**
