# 0.14 文本处理范式：把格式从代码里赶出去

## 一句话

> 凡是“从字节流还原结构、再按结构做动作”的问题，都该走同一条流水线——**词法 → 语法 → 语义**；把格式写成**文法**、把动作写成**回调**，格式的增删就只改文法，不改核心代码。

## 一、先划清问题域

许式伟说的“文本”，不是“纯文本文件”，而是**写入磁盘的非结构化数据**：既包括 HTML、CSS 这种文本，也包括 Word、Excel 这种二进制。

| 需求 | 输入 | 输出 | 例子 |
|---|---|---|---|
| **数据验证** | 用户输入 | 是否合法 | 表单校验、配置校验 |
| **数据抽取** | 页面 / 日志 | 结构化字段 | 从 HTML 抽机票信息 |
| **编译器** | 语言代码 | 机器码 / 字节码 / 直接执行 | 编程语言、模板引擎 |
| **协议解析** | 网络字节流 | 消息结构 | RTMP、MongoDB wire protocol |

这四类的形状一模一样：**字节流 → 结构 → 动作**。差别只在“结构长什么样、动作做什么”。所以它们能共用一套范式。

## 二、三阶段流水线

```
字节流 --Scanner--> Token 流 --Parser--> 结构(AST/DOM) --语义--> 动作
        (词法)                  (语法)                  (执行/生成/校验)
```

| 阶段 | 职责 | Go 里的现成实现 |
|---|---|---|
| **Scanner（词法）** | 字节流 → Token 流 | `go/scanner`：`Scan() (pos, tok, lit)` |
| **Parser（语法）** | Token 流 → AST / DOM | `go/parser`：`ParseFile` 输出 `*ast.File` |
| **语义** | 遍历结构，执行/生成/校验 | 自己写（visitor 或 walk） |

`go/scanner` 的用法就是范式本身：

```go
for {
	pos, tok, lit := s.Scan()
	if tok == token.EOF {
		break
	}
	_ = pos // 位置，用于报错
	_ = lit // 文本内容
}
```

Parser 有两种模型，书里前面已经出现过（[26.6 模块化与包设计](../../L2-架构风格/26-分层与依赖/26.6-模块化与包设计.md) 的 Visitor 案例）：

| 模型 | 接口形态 | 优点 | 缺点 |
|---|---|---|---|
| **SAX（事件）** | `StartElement / Characters / EndElement` | 内存小、可流式 | 使用方要自己维护状态、拼装结构 |
| **DOM（结构）** | 先建树，再遍历 | 直观、可随机访问 | 内存大 |

> 🔑 结论和前面几章一致：**默认选 DOM**。SAX 只在“数据量极大、必须流式”时才值得。许式伟自己的 IO 子系统第一版用了 SAX 风格的 Visitor，事后评价是“失败的设计”——心智负担大、事件次序要写长文档说明。

## 三、文法即格式

真正让这套范式“可复用”的，不是 Scanner，而是**把格式表达成文法**。TPL 用一套类 EBNF 的写法：

| 写法 | 含义 | 类比 |
|---|---|---|
| `*G` / `+G` | 重复 0 次以上 / 1 次以上 | 正则的 `G*` / `G+` |
| `?G` | 可选 | 正则的 `G?` |
| `G1 G2` | 串接 | 顺序 |
| `G1 % G2` / `G1 %= G2` | 非空列表 / 可为空列表 | `1,2,3` / 空也行 |
| `G/action` | 匹配成功后执行动作 | 语义动作 |

一个计算器的文法（原文例子）：

```text
doc    = term *('+' term/add | '-' term/sub)
term   = factor *('*' factor/mul | '/' factor/quo | '%' factor/mod)
factor = FLOAT/push | '-' factor/neg | '(' doc ')' |
         (IDENT '(' doc %= ','/ARITY ')')/call | IDENT/ident | '+' factor
```

它厉害的地方在于：**格式（文法）与动作（action）是分开的**。加一种运算符，只改文法与一个回调；解析器、错误处理、位置信息全都不用动。

TPL 还有一个更妙的开关：`G/action` 在默认模式是“动作”（SAX），在 **extractor 模式**下被视为“标记”，于是同一份文法变成 **DOM**——先建树、再取数。也就是说，**SAX 与 DOM 不是两套实现，是同一套文法的两种执行模式**。

## 四、二进制：同一条流水线，只是 Token 不同

二进制文档看起来更难，因为格式里常带**条件判断**（长度字段决定后面读多少字节）。但结构上仍是三阶段，只是“Token”变成了带类型的字段：

```go
type Foo struct {
	N    uint16
	Bars []Bar // [N]Bar：长度由前一个字段决定
}
```

用文法写出来就是：

```text
Foo = {
    N    uint16
    Bars [N]Bar
}
```

BPL（Binary Processing Language）就是把这套文法扩展到二进制，并且**不破坏 TPL 的任何语义**——许式伟的比喻是“TPL 像 C，BPL 像 C++”。它的文法与 MongoDB 官方协议的伪代码几乎一致（`{…}` 表示 Go 结构体，`{/C …}` 表示 C 结构体），所以**协议文档可以直接翻译成解析器**。

这里有一条反过度设计的判断：

> 🔑 **文件 I/O 最重要的是定义严谨的数据格式，而不是提供任何出于便捷性考虑的“智能”。** Object 动态序列化看起来省事，代价是使用者放弃了对格式的思考——这是不正确的指导思想。

（原文写于 2019 年，当时 Go 还没有泛型，作者在文末呼唤泛型；Go 1.18 之后泛型有了，但这条判断不变：**序列化代码应该由文法生成，而不是靠运行时反射猜格式**。）

## 五、什么时候别用这套

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 格式只有一种、且几乎不变 | 手写解析 | 引入文法的成本大于收益 |
| 简单提取（一行日志、一个 URL） | 正则 | 正则在这个规模最方便 |
| 复杂结构、需要回溯/嵌套 | **文法** | 正则的可读性与可伸缩性都不够 |
| 极致性能（每秒百万条） | 手写状态机 | 通用解析器有抽象开销 |

许式伟对正则的评价很克制：简单场景方便，但**可伸缩性和可读性都不行**。判断标准是“格式会不会长出新分支”——会长，就上文法；不会，就别过度设计。

## 六、可跑的最小实现

一个 60 行的最小流水线：解析 `a=1; b=hello;` 这种配置。注意它**严格分成 Scanner 与 Parser 两段**——这就是范式的骨架。

```go
type token struct{ kind tokKind; lit string }

// Scanner：字节流 → Token 流
func scan(src string) []token {
	var ts []token
	rs := []rune(src)
	for i := 0; i < len(rs); {
		switch c := rs[i]; {
		case unicode.IsSpace(c):
			i++
		case c == '=':
			ts = append(ts, token{tAssign, "="}); i++
		case c == ';':
			ts = append(ts, token{tSemi, ";"}); i++
		case unicode.IsDigit(c):
			j := i
			for j < len(rs) && unicode.IsDigit(rs[j]) { j++ }
			ts = append(ts, token{tNumber, string(rs[i:j])}); i = j
		case unicode.IsLetter(c):
			j := i
			for j < len(rs) && (unicode.IsLetter(rs[j]) || unicode.IsDigit(rs[j])) { j++ }
			ts = append(ts, token{tIdent, string(rs[i:j])}); i = j
		}
	}
	return append(ts, token{tEOF, ""})
}
```

Parser 只做“Token 流 → 结构”：

```go
func parse(ts []token) []kv {
	var out []kv
	i := 0
	for ts[i].kind != tEOF {
		key := ts[i].lit; i++          // ident
		i++                            // =
		val, num := ts[i].lit, ts[i].kind == tNumber; i++
		i++                            // ;
		out = append(out, kv{key, val, num})
	}
	return out
}
```

真实输出（本机 `go1.27.1 darwin/arm64`，输入 `a=1; b=hello; port=8080;`）：

```text
a      = 1 (int)
b      = "hello" (string)
port   = 8080 (int)
```

加一种新语法（比如 `#` 注释）时，只改 `scan` 的 switch；加一种新结构（比如数组）时，只改 `parse`——**两段互不影响**，这就是“把格式从业务代码里赶出去”的实际收益。

## 反模式

| 反模式 | 后果 |
|---|---|
| 在业务代码里手写 `strings.Split` 解析 | 格式一变，改动散落各处，回归面巨大 |
| 用正则解析嵌套结构 | 越写越长、无法回溯，最后变成不可维护的“正则程序” |
| SAX 用在需要随机访问的场景 | 使用方被迫缓存拼装，心智负担大 |
| 让解析器“智能”地猜格式 | 猜错时无法定位，格式演进失控 |
| 二进制格式只写 Reader、不写 Viewer | 下次没人能独立理解格式，只能读带业务逻辑的 Reader |
| 解析失败只返回 nil | 没有位置信息，排错靠猜 |
| 为一种永不变化的格式引入完整文法 | 过度设计，维护成本高于收益 |

## 自检

**Q1** 为什么“文本处理”要把词法与语法分成两段？合成一段不行吗？

▸ 答案：因为两者的**变化原因不同**。词法处理的是“字符怎么组成词”（空格、注释、数字、标识符），语法处理的是“词怎么组成结构”（顺序、嵌套、可选）。合成一段的后果是：加一个注释符号要动结构代码，改一条语法要碰词法——两件不相关的事被绑在一起，回归面翻倍。

**Q2** TPL 里 `G/action` 在不同模式下含义不同，这带来什么好处？

▸ 答案：同一份文法可以当两种模型用。默认模式下 action 是**执行动作**（SAX 式，边解析边做）；extractor 模式下 action 只是**标记**，用来建输出树（DOM 式，先建树再取数）。好处是格式描述只写一遍，用法按场景切换——SAX 与 DOM 不再是两套实现。

**Q3** 为什么“让序列化机制更智能”是过度设计？

▸ 答案：智能意味着**运行时猜格式**（反射、动态类型、自动推断）。它省了写代码，却让使用者不再思考“这个格式到底长什么样、边界在哪”；而文件格式一旦上线就是长期资产，猜错或演进时的代价远高于当初省下的几十行。正确做法是**用文法把格式定义清楚，再生成序列化代码**。

**Q4** 什么时候该用正则，什么时候必须上文法？

▸ 答案：看格式**会不会长出新分支**。一行日志、一个 URL、一个固定格式的时间戳——正则够用且最方便；一旦出现嵌套、可选、重复、需要回溯的结构，正则的可读性与可伸缩性都会崩，这时必须上文法。判据不是“复杂不复杂”，而是“未来加一种情况，改动落在几处”。

**Q5** 这套范式对一个业务后端工程师有什么用？他平时不写编译器。

▸ 答案：用处在于**把“格式”从业务代码里剥离**。配置解析、协议编解码、日志提取、规则引擎、导入导出、SQL/DSL 解析——都是同一形状的问题。一旦用“词法→语法→语义”切开，加一种格式只改文法、加一个动作只加回调，核心业务代码不再被 `if format == ...` 污染。
