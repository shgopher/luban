# 第 79 章 架构设计方法 · 概论

## 一句话

> 这一章回答：**从一句模糊需求到一份可评审的方案，中间要经过哪几步**——需求还原 → 容量估算 → 方案对比 → 原型验证；四步都有可验收的产出，缺一步，方案就靠拍脑袋。

## 5 分钟入门：先记住这 6 个词

| 词 | 一句话解释 | 生活类比 |
|---|---|---|
| **根源需求** | 剥掉用户自带的技术方案，只留问题 | 病人说“开点止痛药”，先问哪疼 |
| **稳定点** | 长期不变、构成最小功能集 | 房子的承重墙 |
| **变化点** | 会持续发散的方向 | 可拆改的隔断 |
| **关键资源** | 最先耗尽的那一个（CPU/连接/IO） | 木桶最短的那块板 |
| **硬门槛** | 不能牺牲的 1–2 个维度 | 招聘的硬性条件 |
| **时间盒** | 原型到点就停，没结论也停 | 试吃一小口，不是吃一顿 |

## 3 个最常见误解

| 误区 | 现实 |
|---|---|
| “需求分析是产品经理的事” | 架构师至少三分之一精力在需求分析上 |
| “容量算个峰值 QPS 就行” | 容量由最先耗尽的关键资源决定，QPS 只是入口 |
| “原型就是先写个能跑的版本” | 原型只有一个问题、一个时间盒，然后被丢掉 |

## 读完自检（入门级 3 题）

**Q1** 用户说“加个缓存就好了”，怎么还原？

▸ 答案：剥掉“缓存”这个方案，问“哪个接口、在什么负载下、要多少毫秒”。根源需求可能是查询没走索引、也可能是热点 key；缓存未必是答案。

**Q2** 三个接口 QPS 差 15 倍，为什么并发可能差不多？

▸ 答案：并发 = QPS × 延迟。慢接口 QPS 低但占用时间长，并发照样高；容量看的是并发与单请求资源，不是 QPS。

**Q3** 两个方案前提不同，还能比吗？

▸ 答案：不能。先对齐规模、团队、时间、预算四项；前提不同时比的不是方案，是两个不同问题的答案。
