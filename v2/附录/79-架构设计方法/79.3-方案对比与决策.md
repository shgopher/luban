# 79.3 方案对比与决策

## 一句话

> 方案对比不是“列优缺点”，而是先把方案**拉到同一前提**再比——前提不同（规模、团队、时间、成本）时任何对比都是假的；可比之后，用**硬门槛 + 优先级**筛，而不是数优点。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 列一张优缺点表就能决策 | 优缺点没有权重，等于把“性能”和“好维护”等权 |
| 加权打分更科学 | 权重没有客观依据，谁定权重谁赢；致命短板会被平均掉 |
| 选最先进/大厂在用的 | 前提不同：规模、团队、时间、预算，一个不匹配就翻车 |

## 第一步：可比性检查

两个方案只有在**同一组前提下**才可比。先逐项对齐：

| 前提 | 为什么必须对齐 |
|---|---|
| 目标规模 | 1 万用户和 1000 万用户的方案，优化目标不同 |
| 团队规模与能力 | 5 人团队维护不了需要专职 SRE 的方案 |
| 交付时间窗 | 3 个月和 1 年，能选的方案完全不同 |
| 预算 | 自研与买服务的分水岭 |

```go
// 方案可比性检查：两个方案若前提不同，任何对比都是假的。
for _, f := range fields {
	if f.va != f.vb {
		diff++
		fmt.Printf("不可比：%s A=%.0f B=%.0f\n", f.name, f.va, f.vb)
	}
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
不可比：目标规模倍数 A=1 B=5
不可比：团队人数 A=1 B=4
不可比：交付月数 A=1 B=2
不可比：成本倍数 A=1 B=6
结论：4 项前提不同，先把两方案拉到同一前提再比
```

这条检查能挡掉大量“关公战秦琼”式的争论：**B 方案不是更好，是它假设了一个更大的规模与更多的资源。**

## 第二步：硬门槛淘汰，不数优点

| 做法 | 结果 |
|---|---|
| 七个维度等权求和 | 致命短板被平均掉（[58.6 架构设计流程与三原则](../../L5-工程效能/58-架构治理/58.6-架构设计流程与三原则.md) 的实测：单库方案总分第一，但性能根本不达标） |
| **先定 1–2 个不可牺牲的维度当门槛** | 直接淘汰不达标方案，剩下的再比优先级 |

门槛怎么定？从需求推导里拿（[79.1 从需求到架构的推导](79.1-从需求到架构的推导.md)）：稳定点与变化点决定“哪个维度不能牺牲”。比如支付系统，门槛是“一致性与可回滚”，不是“吞吐”。

## 第三步：把代价量化

| 代价 | 怎么量 | 出处 |
|---|---|---|
| 核心被污染的程度 | 伤害值 `Σ log₂(每处修改行数+1)` | [58.8 架构优劣的判据](../../L5-工程效能/58-架构治理/58.8-架构优劣的判据.md) |
| 关键资源的容量 | 并发 = QPS × 延迟；机器 = QPS/单机 × 冗余 | [79.2 容量估算](79.2-容量估算.md) |
| 年成本 | 机器 × 单价 + 存储 × 单价 | [39.1 成本模型与单位经济](../../L3-质量属性/39-成本/39.1-成本模型与单位经济.md) |
| 交付周期 | 分波路线图，每波 ≤ 6 个月 | [58.4 演进路线图](../../L5-工程效能/58-架构治理/58.4-演进路线图.md) |

量化的目的不是“算出一个总分”，而是让分歧变成**可讨论的具体数**：“B 方案多花 24 万/年，换来发布频率 4 倍”——这句话能被拍板，而“B 更先进”不能。

## 第四步：决策与记录

决策必须有明确的**拍板人、依据、代价、重开条件**四样：

| 要素 | 反例 | 正例 |
|---|---|---|
| 拍板人 | “大家讨论决定” | 架构组 + 订单团队负责人 |
| 依据 | “业界主流” | “门槛是 P99 ≤ 200ms，A 达标、B 不达标” |
| 代价 | 不写 | “多 24 万/年，运维复杂度 +1 人” |
| 重开条件 | 不写 | “单表写入回落到 3k 以下时重开” |

记录用 ADR（[58.1 ADR 实践](../../L5-工程效能/58-架构治理/58.1-ADR实践.md)）；决策分级与推动方法见 [76.1 技术决策的推动](../../组织/76-技术领导力/76.1-技术决策的推动.md)。

## 反模式

| 反模式 | 后果 |
|---|---|
| 前提不同还硬比 | 选了个“在别人规模下才好”的方案 |
| 数优点/加权打分 | 致命短板被平均掉，选中不达标的方案 |
| 只比技术、不比代价与周期 | 方案对但做不完、养不起 |
| 只给一个方案 | 评审因一个缺点全盘否决，没有退路 |
| 决策不记录重开条件 | 过时决策变成教条 |
| 用“大厂都在用”当依据 | 规模与团队前提不同，不可迁移 |
| 两套方案揉在一篇文档 | 评审无法逐条对比，结论模糊 |

## 自检

**Q1** 为什么“前提不同”会让方案对比失效？举一个例子。

▸ 答案：因为方案的优劣依赖前提。比如 B 方案（微服务 + 单元化）在 1000 万用户、20 人团队下更优；但在 1 万用户、3 人团队下，它的运维与协调成本会压垮团队。前提不对齐，比较的其实是“两个不同问题的答案”。

**Q2** 为什么“数优点”会选出性能不达标的方案？

▸ 答案：因为等权求和把致命短板平均掉了。便宜、简单、好实施这三项能拿高分，性能与可用性各 2 分也能被总分掩盖。正确做法是先设硬门槛（性能 ≥ 4），不达标的直接淘汰，再在通过者里按优先级比较。

**Q3** 硬门槛怎么定，才不是拍脑袋？

▸ 答案：从需求推导里来：稳定点与变化点决定“什么不能牺牲”。支付系统的门槛是一致性与可回滚；内容feed 的门槛是延迟与成本。门槛要写成可验证的数（P99 ≤ 200ms、可用性 ≥ 99.95%），而不是形容词。

**Q4** 量化代价时，为什么不必算出一个“总分”？

▸ 答案：因为不同代价的量纲不同（钱、人月、故障风险），相加没有意义；量化的价值是让分歧变成**具体的数**，供拍板人权衡。“多 24 万/年换发布频率 4 倍”可以被判断，“B 更先进”不能。

**Q5** 一份合格的决策记录必须包含哪四样？

▸ 答案：拍板人、依据、代价、重开条件。缺拍板人，决策无人负责；缺依据，三个月后原样重开；缺代价，后续维护者不知道欠了什么；缺重开条件，决策会变成不可质疑的教条。
