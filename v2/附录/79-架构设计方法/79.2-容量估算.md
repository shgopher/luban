# 79.2 容量估算

## 一句话

> 容量估算不是“算峰值 QPS”，而是回答三个问题：**关键资源是哪个、现在能撑多少、多久会用完**——用**资源用量**而不是 QPS 做指标，用利特尔法则把 QPS 换成并发，用冗余系数把故障算进去。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| 算出峰值 QPS 就算完了 | QPS 只是入口，真正先耗尽的是某类资源（连接、内存、IO、数据库） |
| 用“QPS > 阈值”做告警 | 维护成本高，且指标会漂移：新版本让某些请求的资源消耗大减，旧的 QPS 阈值立刻失真 |
| 扩容能解决过载 | 数据库这类关键资源随数据量增长而变慢，加机器救不了 |
| 做了双机房 = 有容量冗余 | 架构容灾不等于资源储备；双机房要按 **2 倍容量** 规划 |

## 过载的四种成因

| 成因 | 表现 | 对策 |
|---|---|---|
| 用户增长超预期 | 各项资源同步吃紧 | 容量规划 + 弹性扩容 |
| 部分资源故障下线 | 剩余节点过载 | 冗余系数（双机房 2 倍） |
| 关键资源随数据量变慢 | 数据库、索引、缓存命中率下降 | 分库分表、归档、加缓存 |
| **重试放大** | 一个小故障瞬间变成雪崩 | 限制重试 + 全局重试预算 |

最后一类最隐蔽：原文的算例是——单实例正常 QPS 10000，自然请求 11000，1000 个失败被重试放大 **9 倍**，瞬间变成 20000 QPS，是正常负荷的 2 倍。**故障不是被“修好”的，是被重试压垮的。**

## 两个公式：从 QPS 到机器数

| 步骤 | 公式 | 说明 |
|---|---|---|
| 并发 | `并发 ≈ QPS × 平均延迟(s)` | 利特尔法则：同时在处理中的请求数 |
| 机器 | `机器 ≈ 峰值 QPS / 单机 QPS × 冗余系数` | 冗余：双机房 2 倍、单机房 1.3–1.5 |
| 关键资源 | `CPU / 内存 / 连接数 / IOPS` 取最紧的那个 | 容量由**最先耗尽**的资源决定 |

```go
// 并发 = QPS × 平均延迟；机器数 = 峰值 QPS / 单机 QPS × 冗余系数。
conc := s.qps * s.delayMs / 1000
nodes := s.qps / s.perNodeQPS * s.redundancy
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
下单       峰值QPS=8000   并发≈240   机器≈24 台（含冗余 1.5）
支付回调     峰值QPS=2000   并发≈240   机器≈15 台（含冗余 1.5）
查询       峰值QPS=30000  并发≈300   机器≈20 台（含冗余 1.3）
```

读法：三个接口的 QPS 差 15 倍，但**并发都在 240–300**——因为慢接口（支付回调 120ms）的并发 = 2000 × 0.12 = 240。这解释了为什么“QPS 不高但很慢”的接口照样能把线程池打满：**容量看的是并发 × 单请求资源，不是 QPS**。

## 过载保护：服务端与客户端各管一半

| 端 | 手段 | 关键参数 |
|---|---|---|
| **服务端** | 主动拒绝、尽早标记失败 | 粒度：全局 → 每用户配额 → 特殊客户单独调 |
| | 依据**资源利用率**而非 QPS | 倾向资源，因为更稳定 |
| | 由负载均衡做（双保险） | 与业务层限流叠加 |
| | 优雅降级 | 按请求重要性分级 |
| | 定期小流量压测 | 让降级分支真的被执行过 |
| **客户端** | 限制重试次数、不无限重试 | 重试 2 次 = 最多放大 **3 倍** |
| | 随机化 + 指数递增 | 例：3s / 6s / 12s，避免同时重试 |
| | **全局重试预算** | 每进程每分钟只允许 **60 次** 重试，耗尽即失败 |
| | 重要性级别 | **1–4 级**：可丢弃 / 可延后 / 重要 / 非常重要 |
| | 小超时 + deadline 传递 | 每个阶段开始前检查剩余 deadline |
| | 自适应节流 | 统计过去 **2 分钟** 的 requests 与 accepts，`requests = K × accepts`；K=2 → 50% 处理率，K=1.1 → 90% |

> 🔑 重试的放大倍数是最该背下来的数：**单侧重试 2 次 = 3 倍；两端都重试 = 9 倍；内部再重试 3–9 次 = 9–81 倍**。一个 1% 的失败率，经过三层重试就能把下游打挂。

## 判据：什么时候扩、什么时候限、什么时候降

| 现象 | 先做什么 | 为什么 |
|---|---|---|
| CPU/内存逼近水位，但延迟正常 | 扩容 | 资源还有余量，扩了就能接住 |
| 关键资源（DB）变慢，机器不缺 | **限流 + 降级 + 归档**，不是加机器 | 加机器会把更多请求打到同一个库 |
| 重试率异常升高 | 先关重试放大（预算 + 抖动），再查根因 | 重试是雪崩的放大器 |
| 降级频繁被触发 | 回头做容量规划 | “优雅降级不应该经常被触发，否则就是规划失误” |
| 双机房单边下线就扛不住 | 补到 **2 倍容量** | 架构容灾 ≠ 资源冗余 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 只算 QPS、不看关键资源 | 扩了机器，数据库先挂 |
| 用 QPS 阈值做过载告警 | 指标漂移，误报与漏报都多 |
| 无限重试 / 重试不随机 | 一次抖动被放大 9–81 倍 |
| 把优雅降级当常规手段 | 降级分支平时不执行，真用时才发现坏的 |
| 双机房只做架构、不做容量 | 单边故障即全站过载 |
| 只做压测、不做容量模型 | 知道“能压到多少”，不知道“什么时候用完” |
| 以为容量规划能消除连锁反应 | 计划内外的大面积下线仍会发生，必须配过载保护 |

## 自检

**Q1** 两个接口 QPS 差 15 倍，为什么并发可能差不多？

▸ 答案：因为并发 = QPS × 延迟。8000 QPS × 30ms = 240，2000 QPS × 120ms 也是 240。容量看的是**并发 × 单请求资源**：慢接口的单位时间吞吐低，但每个请求占用资源的时间长，照样能把线程池占满。

**Q2** 为什么用 CPU 使用率做容量指标，比用 QPS 更可靠？

▸ 答案：因为资源消耗会随代码变化而变化：新版本可能让某些请求的 CPU 消耗大减，或让另一些请求翻倍；QPS 阈值不会自动跟着变，于是要么误报要么漏报。CPU/内存这类**基础资源用量**直接反映“还能不能撑”，与代码版本的关系更稳定。

**Q3** 重试为什么会把一次小故障放大成雪崩？给出数字。

▸ 答案：因为重试是乘性的：单侧重试 2 次最多 3 倍，两端都重试 9 倍，内部再重试 3–9 次就是 9–81 倍。原文算例：正常 10000 QPS，11000 请求里 1000 个失败，9 倍放大后回到系统的是 20000 QPS——是正常负荷的 2 倍，本来就紧张的系统直接被压垮。

**Q4** 双机房容灾，为什么容量要按 2 倍规划？

▸ 答案：因为一个机房下线后，全部流量要由另一个机房承接。若平时两边各承载 50%，单边故障时剩下的一边要扛 100%——没有 2 倍容量就会过载。架构上的“双活”只保证流量能切，不保证切过去能扛住。

**Q5** 降级频繁触发，说明什么问题？

▸ 答案：说明容量规划失误——系统长期在超负荷边缘运行，只能靠牺牲功能维持。正确顺序是：先补容量（扩容/优化关键资源），再把降级作为**兜底**；兜底手段变成常态，等于承认主路径已经不可用。
