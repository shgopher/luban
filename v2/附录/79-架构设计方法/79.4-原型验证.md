# 79.4 原型验证

## 一句话

> 原型的目的不是“做一个能用的版本”，而是**用一个时间盒回答一个具体问题**——问题、时间盒、成功判据、丢弃计划四样缺一不可；缺一样，原型就会变成“一个没人敢删的半成品”。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 原型 = 小版本 | 小版本要维护、要上线；原型只回答一个问题，然后被丢掉 |
| 原型可以“顺便上线” | 原型代码没有错误处理、没有测试、没有安全边界，上线就是事故 |
| 原型不用计划 | 没有时间盒与成功判据的原型，会无限期拖下去 |

## Spike 的四要素

| 要素 | 要写成什么样 | 反例 |
|---|---|---|
| **问题** | 一个可回答的疑问句 | “研究一下新架构” |
| **时间盒** | 1–3 天，最多 1 周，超时即停 | “做到能跑为止” |
| **成功判据** | 一个可测的数或结论 | “感觉还行” |
| **丢弃计划** | 明确不合入、不进主干、到期删除 | “先留着，以后可能有用” |

```go
// 原型（Spike）计划检查：有没有问题、时间盒、成功判据、丢弃计划。
if s.q == "" { errs = append(errs, "缺问题") }
if s.box == "" { errs = append(errs, "缺时间盒") }
if s.done == "" { errs = append(errs, "缺成功判据") }
if s.drop == "" { errs = append(errs, "缺丢弃计划") }
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
✓ 分库分表后跨片查询能否 <200ms
✗ 新技术选型                    [缺成功判据 缺丢弃计划]
✓ 消息队列能否支撑 5w TPS
```

第二行是典型的失败原型：“新技术选型”是个话题，不是问题；没有判据就无法结束，没有丢弃计划就会留下一个吃维护成本的玩具。

## 两类原型，别混用

| 类型 | 回答什么 | 产物 | 寿命 |
|---|---|---|---|
| **技术验证（Spike）** | 这条路走不走得通（性能、兼容、可行性） | 压测数据、结论、几段丢弃的代码 | 天级，用完即删 |
| **体验原型（Prototype）** | 用户会不会用、流程顺不顺 | 可点击的界面 / 假数据页面 | 周级，被正式版本替换 |

混用的后果：用 Spike 去做体验验证（用户看不懂），或用 Prototype 去验证性能（假数据没有参考价值）。

## 时间盒：超时即停，结论照写

| 情况 | 处理 |
|---|---|
| 时间盒内得到明确结论 | 采纳/放弃，写进 ADR |
| 时间盒内没得到结论 | **照样停**，写下“已知什么、还缺什么、下一步怎么验证” |
| 越做越觉得有意思 | 这是最危险的状态——立刻停，它已经变成了项目 |

> 🔑 原型最贵的不是代码，是**它带来的沉没成本**：一旦有人开始“顺手完善”，它就会以“临时方案”的身份长期留在生产环境里。

## 什么时候该做原型

| 信号 | 该做 | 不该做 |
|---|---|---|
| 关键假设没被验证过（性能、兼容性） | ✅ Spike 1–3 天 | — |
| 需求本身还没想清楚 | — | ❌ 原型救不了模糊需求（先回 [79.1](79.1-从需求到架构的推导.md)） |
| 两个方案差距不大 | — | ❌ 选一个直接做，用真实反馈决定 |
| 方案不可逆且成本高 | ✅ 必须验证 | — |

许式伟在概要设计里还有一条相关实践：**系统设计阶段就应该有代码产出**——框架代码 + 原型/mock，用来验证“架子搭得起来”。这比后期发现“接口对不上”便宜得多（[58.6 架构设计流程与三原则](../../L5-工程效能/58-架构治理/58.6-架构设计流程与三原则.md) 里“详细设计才发现不可行”的案例就是这个坑）。

## 反模式

| 反模式 | 后果 |
|---|---|
| 原型没有时间盒 | 无限期拖，变成“影子项目” |
| 原型代码合入主干 | 无测试、无错误处理，事故源头 |
| 原型结论只停留在口头 | 三个月后没人记得验证过什么 |
| 用原型验证模糊需求 | 需求不清时，原型只会放大分歧 |
| 原型做完直接上线 | 跳过了设计、评审、压测，风险最高 |
| 为原型建完整 CI/监控 | 成本超过收益，且暗示它会长期存在 |
| 同时开 5 个原型 | 每个都做不完，团队注意力被切碎 |

## 自检

**Q1** 为什么原型必须有“丢弃计划”？

▸ 答案：因为原型的代码质量（无测试、无错误处理、无边界检查）不适合长期存在；不写丢弃计划，它就会以“先这样吧”的方式留在生产里，变成没人敢删、没人敢改的技术债。写下来还有一层作用：让人在动手前就想清楚“这是要丢的”。

**Q2** “时间盒到了没结论”该怎么办？

▸ 答案：照样停，并写下结论：已知什么、还缺什么、下一步用什么方式验证（换方案、加人手、做正式 PoC）。继续做下去会把“验证”变成“开发”，沉没成本开始累积。

**Q3** 技术验证（Spike）和体验原型（Prototype）能混用吗？

▸ 答案：不能。Spike 用假数据、只看性能与可行性，产物是数据与结论；Prototype 用真实交互、假后端，产物是流程与反馈。用 Spike 验证体验，用户看不懂；用 Prototype 验证性能，假数据没有参考价值。

**Q4** 什么情况下**不该**做原型？

▸ 答案：三种：需求本身没想清楚（先做需求分析）；两个方案差距不大（直接选一个，用真实反馈迭代更便宜）；改动可逆且成本低（做完再回滚，比验证便宜）。

**Q5** 为什么说“概要设计阶段就该有代码产出”？

▸ 答案：因为接口是否成立、架子是否搭得起来，只有写代码才能验证。只画图的概要设计，会把“接口不匹配”的风险推到联调阶段；一段框架代码 + mock 能在设计阶段就把这类风险暴露出来，且它本身就是最精确的文档（代码即文档）。
