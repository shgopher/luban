# 79.5 读懂既有系统：模型 → 接口 → 实现

## 一句话

> 接手一个系统，第一份要产出的不是代码笔记，而是**设计地图**：模型（有哪些概念、什么关系）→ 接口（能力怎么暴露）→ 实现（内部怎么做）；三层稳定度依次下降，讨论时不混层——**架构图里出现 Kafka，通常说明把实现画进了模型**。

> 来源：模型 / 接口 / 实现的三层划分、「三层稳定度」与「架构图混层」的判据来自郑晔《软件设计之美》（极客时间，2020）第 4–7 讲；阅读清单、检查器与实测为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “读设计就是读源码” | 一头扎进代码，很快就迷失。先建地图（模型），再找入口（接口），最后才进实现——**没有地图，读得越多越乱** |
| “我们讨论的就是架构/模型” | 很多“架构图”画的是实现：把 Kafka、Redis 横在模块之间。模型层根本不该出现这些名字 |
| “Redis 6.0 改成多线程了，它变了” | 模型与接口没变，变的只是实现。判断“还是不是同一个软件”，看的是模型 |
| “模型只是文档里的概念” | 模型变了，软件就不是这个软件了；接口通常反映模型；**只有实现是可以随时换的** |

## 三层各回答什么

| 层 | 回答的问题 | 例子 | 稳定度 | 变了意味着 |
|---|---|---|---|---|
| **模型** | 有哪些概念、什么关系、遵守什么规则 | MapReduce 的 map/reduce；订单 / 支付 / 物流 | **最高** | 软件换了内核 |
| **接口** | 能力如何暴露、契约是什么 | 程序库 API、命令行、REST/RPC、消息 topic 契约 | 中 | 调用方要改 |
| **实现** | 内部怎么做：并发、存储、协议、调度、部署 | 单线程还是多线程；Kafka 还是 Pulsar；MySQL 还是 PG | **最低** | 换一个实现即可，上层不动 |

用“看代码”的动作为例，三层分别对应：**先看有哪些类以及它们的关系（模型）→ 打开一个类看它提供什么方法（接口）→ 打开一个方法看它怎么写的（实现）**。顺序反了，就会在细节里失去方向。

抽象层次还会随技术演进而升高：同样做分布式计算，早期要操心“怎么在节点间调度”，MapReduce 只需想“怎么拆开再汇总”，Spark 只需想“要做怎样的计算”。**模型越接近要解决的问题，理解门槛越低。**

## 为什么必须分：三条判据

1. **稳定度不同 → 变更成本不同**。改模型是换内核，改接口是改契约（调用方全要动），改实现只是换零件。
2. **讨论不混层**。技术评审最常见的混乱，是有人在谈模型、有人在谈实现，谁也说服不了谁。发言顺序应当是：先模型，再接口，最后实现。
3. **实现必须可替换 → 必须封装**。实现既然是可换的，就不能散落在各处；散落之处，就是未来替换时的雷区。

## 用三层读一个陌生系统

| 步 | 问什么 | 产出 | 时间盒 |
|---|---|---|---|
| ① 模型 | 系统里反复出现的名词是什么？它们之间什么关系？一条主流程经过哪些概念？ | 领域词表 + 上下文图（概念与依赖） | 2–4 小时 |
| ② 接口 | 外部怎么进来（API / CLI / 事件 / Webhook）？契约长什么样？谁在调？ | 接口清单（入口、协议、鉴权、版本） | 半天 |
| ③ 实现 | 存储、并发、协议、部署各选了什么？为什么这么选？ | 实现层架构图（技术选型 + 取舍） | 1–2 天 |

三个纪律：

- **每层内部再按三层展开**。到了子系统、模块、类、甚至一个数据结构，都能继续套：操作系统进程管理，模型是进程模型与调度算法，接口是进程创建/销毁/触发调度，实现是各种调度算法；HashMap 也能这么拆。
- **模型阶段不要打开 IDE**。先画概念与关系，再进代码验证；带着问题读代码，比无目的浏览快一个数量级。
- **模型层禁止出现产品名**。Kafka、Redis、MySQL 这些名字属于实现层；它们出现在模型图里，等于把“可替换”说成了“不可替换”。

## 架构图的经典错法

```text
❌ 混层（把实现当成模型的一部分）
订单 ──Kafka──▶ 支付 ──Kafka──▶ 物流

✅ 模型图（只画概念与依赖）
订单 ──▶ 支付 ──▶ 物流

✅ 实现图（单独一张，画技术选型与部署）
订单服务 ──发布──▶ 事件总线(Kafka) ──订阅──▶ 支付服务
```

判据一句话：**把 Kafka 换成 Pulsar，模型图要不要改？要改，就是画错了。**

错法的真实代价：一旦 Kafka 被画进模型层，替换它就会被当成“架构变更”，而不是“换实现”——于是没人敢动，最后所有业务逻辑都长在了 Kafka 的语义上。

> 🔑 分清模型还有一个直接好处：**它会限制实现的使用范围**。知道了哪些概念是核心、哪些只是技术选择，才知道哪些地方必须隔离、哪些地方可以随便换。

## 可运行：把“混层”变成一条检查

设计图能不能自动查？能查一部分：节点标上层（模型/接口/实现），边连起来，规则只有两条——**模型与实现不许直连**，**每个实现必须挂在某个接口上**。

把设计图存成一个小文件（节点标层、边连依赖）：

```json
{
  "nodes": [
    {"id": "订单", "layer": "model"},
    {"id": "支付", "layer": "model"},
    {"id": "物流", "layer": "model"},
    {"id": "Kafka", "layer": "implementation"},
    {"id": "MySQL", "layer": "implementation"}
  ],
  "edges": [
    ["订单", "Kafka"], ["Kafka", "支付"],
    ["支付", "Kafka"], ["Kafka", "物流"],
    ["订单", "MySQL"]
  ]
}
```

```python
#!/usr/bin/env python3
"""layer_check.py —— 设计图层检查：模型 / 接口 / 实现 不许混层。

规则（来自「模型 > 接口 > 实现」的稳定度顺序）：
  1. 模型 与 实现 不能直连——中间必须有接口；否则等于把可替换的技术选型焊进模型
  2. 每个实现节点必须至少连一个接口节点——裸实现迟早散落各处
用法: python3 layer_check.py design.json
"""
import json
import sys

LAYER_CN = {"model": "模型", "interface": "接口", "implementation": "实现"}


def main(path):
    spec = json.load(open(path))
    layer = {n["id"]: n["layer"] for n in spec["nodes"]}
    bad = 0
    impl_linked = set()

    for a, b in spec["edges"]:
        la, lb = layer.get(a), layer.get(b)
        if la is None or lb is None:
            print(f"FAIL  边 {a} → {b} 引用了不存在的节点")
            bad += 1
            continue
        if {la, lb} == {"model", "implementation"}:
            print(f"FAIL  {a}({LAYER_CN[la]}) → {b}({LAYER_CN[lb]})：模型与实现直连，"
                  f"中间缺一层接口")
            bad += 1
        if lb == "interface":
            impl_linked.add(a)
        if la == "interface":
            impl_linked.add(b)

    for n, l in layer.items():
        if l == "implementation" and n not in impl_linked:
            print(f"FAIL  {n}(实现) 没有挂到任何接口上：裸实现，改了没人知道影响面")
            bad += 1

    print(f"\n结论：{'发现 ' + str(bad) + ' 处混层' if bad else '三层分离，可以进评审'}")
    return 1 if bad else 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1]))
```

**本机实测输出**（Python 3.14.8）。先输入一张“标准错图”——订单、支付、物流三个模型，中间横着 Kafka，订单还直连了 MySQL：

```text
FAIL  订单(模型) → Kafka(实现)：模型与实现直连，中间缺一层接口
FAIL  Kafka(实现) → 支付(模型)：模型与实现直连，中间缺一层接口
FAIL  支付(模型) → Kafka(实现)：模型与实现直连，中间缺一层接口
FAIL  Kafka(实现) → 物流(模型)：模型与实现直连，中间缺一层接口
FAIL  订单(模型) → MySQL(实现)：模型与实现直连，中间缺一层接口
FAIL  Kafka(实现) 没有挂到任何接口上：裸实现，改了没人知道影响面
FAIL  MySQL(实现) 没有挂到任何接口上：裸实现，改了没人知道影响面

结论：发现 7 处混层
```

改成“模型 + 事件契约 + 事件总线 / 仓储接口 + 数据库”之后：

```text
结论：三层分离，可以进评审
```

读法三条：

1. **7 处混层里有 5 处是同一类错误**：模型和实现直连。这也是架构图最常犯的错——把技术选型当成模块。
2. **“裸实现”那条最有价值**：Kafka、MySQL 没有挂到任何接口上，意味着它们的使用散落在业务代码里，将来替换就是全量改造。
3. **规则只有两条就能拦住大半问题**。真要在评审里用，把这张图存成文件、进 CI，比在会上盯着图找问题有效得多。

## 判据：你的问题该停在哪一层

| 你的问题 | 停在哪层 | 因为 |
|---|---|---|
| “这个系统是干什么的、边界在哪” | 模型 | 概念与关系决定边界 |
| “我要接入它 / 替换它” | 接口 | 契约决定你能不能换 |
| “它为什么慢、为什么贵” | 实现 | 并发、存储、协议、部署 |
| “能不能把 Kafka 换掉” | 先看接口 | 有没有契约接住；没有契约，换不动 |
| “这个改动会不会影响别的团队” | 接口 + 模型 | 实现改动通常不外溢 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 接手就读源码、不做模型 | 读得越多越乱，改一处不知道影响面 |
| 模型图里写满产品名 | 技术选型被当成架构约束，没人敢替换 |
| 把“实现讨论”当“设计讨论” | 会议开成选型辩论，模型问题始终没解决 |
| 讨论时混层发言 | 各说各话，结论不可比 |
| 实现不封装、散落各处 | 替换时全量改造，最后选择“将就着用” |
| 只在文档里分层，代码里不分 | 文档与代码两张皮，新人信文档就被坑 |
| 模型频繁变更 | 等于每隔半年换一次内核，团队永远在重建认知 |

## 自检

**Q1** 为什么“先读源码”是接手系统的错误起点？

▸ 答案：源码是实现的集合，信息密度高但缺少结构。没有模型地图，你无法判断哪些代码是核心概念、哪些只是一次技术选择，于是把时间花在细节上。正确顺序是模型（概念与关系）→ 接口（入口与契约）→ 实现（内部做法），逐层建立认知。

**Q2** 一张架构图上画着“订单 → Kafka → 支付”，问题出在哪？怎么改？

▸ 答案：Kafka 是实现层的东西，被画进了模型层，等于把可替换的技术选型说成不可替换。改法：模型图只画“订单 → 支付”（概念依赖）；另起一张实现图，画“订单服务 → 发布事件 → 事件总线(Kafka) → 订阅 → 支付服务”。

**Q3** Redis 从 6.0 开始支持多线程，它的“设计”变了吗？

▸ 答案：变的是实现，不是模型与接口。它依然是键值存储、接口依然是那些命令，所以“还是那个 Redis”。判断标准就是本节的三层：模型/接口稳定，实现可换。

**Q4** 评审会上有人说“这个方案不行，Redis 扛不住”，有人说“先把模型理清”。谁对？

▸ 答案：不冲突，但要按顺序。先确认模型（到底需要什么能力、什么一致性），再定接口（契约允不允许换存储），最后才是实现选型（Redis 还是别的）。跳过前两层直接吵实现，结论无法比较，也无法回溯。

**Q5** “每个实现必须挂在接口上”这条规则，实际防的是什么？

▸ 答案：防“裸实现”——某个技术组件被业务代码到处直接调用，没有一层契约隔开。后果是替换或升级时影响面不可枚举，只能全量改。规则落地成 CI 检查，就能在合并前拦住。

**Q6** 为什么说“分清模型会限制实现的使用范围”？

▸ 答案：模型告诉你哪些概念是核心、哪些只是当前的技术选择。核心部分不允许绑定具体实现；非核心部分可以随便换。没有这个区分，实现的选择就会反向塑造模型（例如业务逻辑长在 Kafka 的语义上），最后想换也换不动。

**Q7** 接手一个系统，只有两天时间，三层怎么分配？

▸ 答案：模型 1 天（画概念与主流程，和业务方核对），接口半天（列出所有入口与契约，标出谁在调），实现半天（只看存储/并发/部署三件事，画出实现图）。**宁可实现看不全，也要把模型和接口看全**——前两层决定你后面所有判断的方向。

**Q8** 这套三层法，和 DDD 的“战略设计/战术设计”是什么关系？

▸ 答案：正交。DDD 的产出主要是模型层（限界上下文 + 聚合 + 领域事件），它不关心你用什么消息中间件；本节的三层是阅读与评审的框架，适用于任何系统（包括不是 DDD 设计的系统）。两者可以叠用：用 DDD 建模型，用三层法检查模型有没有被实现污染。
