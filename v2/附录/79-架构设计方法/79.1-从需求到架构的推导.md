# 79.1 从需求到架构的推导

## 一句话

> 从需求推导架构不是“画图”，而是三步：**把需求还原成不带技术假设的根源需求 → 分出稳定点与变化点（即核心与扩展） → 用接口把变化点挡在核心之外**；判据是“变化点有没有被产品边界接住”，而不是“图画得漂不漂亮”。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 用户说的就是需求 | 用户带来的往往是**二次加工过的需求**——已经自带一个技术方案，要先还原 |
| 需求分析是产品经理的事 | 许式伟的说法：架构师**至少花三分之一精力**在需求分析上 |
| 架构 = 画模块图 | 架构是“对需求做正交分解”的产物；图只是表达方式（[80.2 架构图规范](../80-架构文档与表达/80.2-架构图规范.md)） |

## 第一步：把需求还原成根源需求

用户提需求时，常常已经替你想好了方案。还原的动作是**把技术假设剥掉，只留要解决的问题**：

| 用户说的 | 里面藏的技术假设 | 根源需求 |
|---|---|---|
| “给我一个固定 IP” | 用 IP 直达主机 | 人能记住、能访问你的服务 → 有了域名 + DNS |
| “报表要导出 Excel” | 用 Excel 承载数据 | 数据要能被二次分析 → CSV/API 都可以 |
| “加个缓存就好了” | 用缓存解决慢 | 这个接口在什么负载下要多少毫秒？可能是查询没走索引 |
| “要支持私有化部署” | 一套代码到处装 | 客户的数据不能出他的机房 |

> 🔑 判据：**去掉这个方案，问题还在吗？** 在，说明你找到的是根源需求；不在，说明你拿到的是别人的解法。

## 第二步：分稳定点与变化点

这是“需求 → 架构”的核心动作。稳定点对应**核心能力**，变化点对应**扩展性设计**：

| 判断 | 含义 | 设计动作 |
|---|---|---|
| **稳定点** | 长期不变、构成业务最小功能集 | 放进核心，做厚、做稳，尽量不改 |
| **变化点** | 会持续增加、发散的方向 | 用接口/插件挡在核心外（[26.6 模块化与包设计](../../L2-架构风格/26-分层与依赖/26.6-模块化与包设计.md)） |

两个真实推导（许式伟的案例）：

| 案例 | 稳定点 | 变化点 | 结论 |
|---|---|---|---|
| **对象存储** | 数据要能按账号存取、要可靠、要便宜 | 文件越来越大、类型越来越多（90% 以上是非结构化数据） | 文件系统那棵“树”撑不住规模（改一个节点要锁整棵树）→ 换成 **Key-Value**：Bucket 是逻辑划分，Key 定位对象 |
| **互联网** | 开放、可互联 | 应用形态（Email、WWW…） | 只定协议与骨干网，应用层留给生态 |

判据：**变化点必须绑定“我们要做的产品”这个坐标系**。同样是“外设多样化”，做计算机时它是变化点（要扩展），做显示器时它根本不在问题域里。

## 第三步：把变化点落到接口上

分解到最后一定要落到**接口**，否则“稳定/变化”只是口头判断：

| 落点 | 做法 | 反例 |
|---|---|---|
| 变化点 → 接口 | 核心定义稳定接口，变化点实现它 | 核心 import 了具体实现 |
| 参数 → 泛化 | 发现“多余约束”就提高通用性（`*os.File` → `io.Reader`） | 接口参数写死具体介质 |
| 新功能 → 周边系统 | 新功能当独立业务写，只留最少的桥接代码 | 新功能直接改核心 |

“多余约束”怎么发现？把**所有用户故事逐条过一遍**（[26.6 模块化与包设计](../../L2-架构风格/26-分层与依赖/26.6-模块化与包设计.md) 的 IO 案例：只想着“存到文件”，参数自然写死 `*os.File`；把“剪贴板”也列进来，就会发现“文件”是多余假设）。

## 覆盖矩阵：需求有没有被模块接住

推导完要自查：每个需求是不是都有模块承接？

```go
// 需求 → 模块 覆盖矩阵：找出没有被任何模块承接的需求。
covered := map[string]bool{}
for _, fs := range modules {
	for _, f := range fs {
		covered[f] = true
	}
}
// 未覆盖的需求 = 架构缺口，或需求本身该砍
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
需求=5 已承接=4 未承接=1 [优惠券]
```

一条未承接的需求，只有两种解释：**架构漏了**，或**这个需求不该做**。两种情况都该在评审前处理掉，而不是留到开发时“顺手加进去”。

## 过度设计：只差一个判据

原文给得极干脆：**不会发生的事情，你考虑了并且为它做足了准备，就是过度设计。**

| 情况 | 该不该准备 |
|---|---|
| 变化点已经有 2 个以上真实实现 | 该，抽接口 |
| 变化点只会来 1 个，且时间未知 | 不该，先写死 |
| 需求方明确说“明年要做” | 该，但只留接口，不实现 |
| “以后可能要支持多租户” | 不该，除非有客户合同 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 直接照抄用户给的方案 | 把一个技术假设当需求，做出来的东西不解决真问题 |
| 不做稳定/变化判断就画模块 | 模块按名词切，变化点全落在核心里 |
| 变化点不定坐标系 | 为“不存在的产品”设计扩展性 |
| 需求没被任何模块承接就开工 | 开发期“顺手加”，架构被撑破 |
| 为“以后可能”预留扩展点 | 过度设计：多一层抽象，没有任何真实实现 |
| 需求分析只做一次 | 需求会变，稳定/变化判断要跟着复核 |

## 自检

**Q1** 用户说“给我一个固定 IP”，怎么还原成根源需求？

▸ 答案：剥掉“IP 直达”这个技术假设，问“你要解决什么”：如果是“让人能访问”，根源需求是**可寻址**，域名 + DNS 就够；如果是“白名单放行”，根源需求是**固定出口**，那要的是 NAT 网关或固定 EIP。同一个说法，两种根源需求，架构完全不同。

**Q2** 稳定点与变化点分别怎么处理？

▸ 答案：稳定点进核心，做厚做稳、尽量不改；变化点用接口/插件挡在核心外，核心只依赖稳定接口。判据是“这个方向会不会持续增加”——会，就是变化点；不会，就不要为它预留抽象（过度设计）。

**Q3** 为什么“变化点必须绑定产品坐标系”？

▸ 答案：因为同一个现象在不同产品里，可能是变化点，也可能根本不在问题域。做计算机时“外设多样化”是变化点（要扩展接口）；做显示器时外设与你无关。不绑定产品，就会为别人的问题设计扩展性。

**Q4** 覆盖矩阵查出一条需求没有模块承接，该怎么处理？

▸ 答案：二选一：要么补进架构（新增模块或明确挂在哪个模块下），要么砍掉这条需求。**不能留到开发时“顺手加”**——那意味着架构没有承接它，最后一定是在核心里打补丁。

**Q5** 怎么判断一个“预留扩展点”是不是过度设计？

▸ 答案：用原文那句判据：这件事**会不会发生**？已经有 2 个以上真实实现、或需求方明确排期，就该留；只是“以后可能”，就不该。可以留接口不实现，但不能为想象中的变化写一套完整机制（[0.12 过度设计与模式反模式](../../内功/0-内功/0.12-过度设计与模式反模式.md)）。
