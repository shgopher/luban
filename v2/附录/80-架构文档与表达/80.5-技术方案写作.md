# 80.5 技术方案写作

## 一句话

> 技术方案不是“作文”，是按**评审会要问的顺序**把问题答完：**现状与需求 → 使用界面（接口）→ 实现原理（数据结构 + 算法）**——现状与需求写短，接口与实现写透。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 写得越长越认真 | 现状与需求长篇累牍，评审的人会直接跳到结论；重点被稀释 |
| 技术方案 = 架构图 + 实现说明 | 缺了“使用界面”这一节，团队共识就没有落到可验收的规格上 |
| 一份文档塞两套方案 | 两套方案优势不显著时该写两套，但必须**分成两篇独立文档** |

## 骨架：按评审会要问的顺序写

| 小节 | 回答什么 | 写多长 |
|---|---|---|
| **1 现状与需求** | 现在在哪里、遇到什么问题、要做何改进 | **短**：只写与“要做的改变”相关的事实 |
| **2 使用界面（接口）** | 要做成什么样：交付物的规格 | **长**：这是团队共识确认的关键 |
| **3 实现原理** | 怎么做到 | **长**：按 `程序 = 数据结构 + 算法` 展开 |
| 3.1 数据结构 | 表结构（Table/Collection）、类图 | 中 |
| 3.2 算法 | 每个 UserStory 背后的实现机制 | 长 |

> 🔑 判据：**读者只看第 2 节，能不能判断“这东西做出来是不是我要的”**。答不出，说明方案还没写到可评审的程度。

> 💡 概要设计与详细设计的差别，就在**接口的完备度**：概要设计只列最核心的接口（够确认边界），详细设计要求接口完备（够照着实现）；两者都要求“需求满足方式”详写，区别只在写到多细。

## 把接口写透：三类接口 + 伪代码

接口不止“函数调用”，原文把它分成三类，容易漏的是后两类：

| 类型 | 例子 | 容易漏掉的点 |
|---|---|---|
| **常规 DOM API** | 模块功能调用 | 错误码与超时语义 |
| **事件（Event）** | 发送与监听 | 谁保证送达、重复怎么办 |
| **插件（Plugin）** | 注册与生命周期 | 插件失败会不会拖垮核心 |

伪代码是“精确”的关键（原文要求语义精确、团队内形成默契）：

```text
# 请求
post /v1/orders
json {"user_id": "u1", "items": [{"sku": "s1", "qty": 2}]}

# 返回
{"code": 0, "order_id": "o1", "amount": 12800}

# 错误
{"code": 40001, "msg": "库存不足", "retryable": false}
```

## 写“详细设计”时，数据结构先行

原文的顺序是：先数据结构，再算法。

| 部分 | 写什么 | 反例 |
|---|---|---|
| 表结构 | 字段名、类型、含义、**是否指向另一张表的字段**、索引 | 只写字段名，不写外键与索引依据 |
| 类图 | 类多或表复杂时用 UML 类图 | 几十个类全靠文字描述 |
| 索引 | **由算法决定**：算法用到哪些数据访问特征、频次预期 | 先拍脑袋建索引，再写算法 |
| 算法 | 每个 UserStory 的实现机制，用时序图或伪代码 | 只写“调用 XXX 服务” |

## 写完自查：章节齐不齐

评审会问的问题，基本都能映射到固定的几节。用一条命令自查：

```bash
for sec in 背景 需求 方案对比 接口 数据 容量 失败模式 回滚 里程碑; do
  grep -q "$sec" design.md && echo "✓ $sec" || echo "✗ 缺 $sec"
done
```

真实输出（拿一份合格的方案跑）：

```text
✓ 背景
✓ 需求
✓ 方案对比
✓ 接口
✓ 数据
✓ 容量
✓ 失败模式
✓ 回滚
✓ 里程碑
```

缺哪一节，评审就会在哪一节上花时间追问——**与其被问，不如先写**。

## 两套方案：分开写，别揉在一起

原文的态度很明确：两套方案优势不显著时，**应该被鼓励**写成两套；但必须分成两篇独立文档，而不是揉在一起。

| 做法 | 结果 |
|---|---|
| 一篇里写“方案 A…方案 B…” | 评审无法逐条对比，结论模糊 |
| 两篇独立文档 + 一篇对比结论 | 每篇可独立评审，对比有据 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 现状与需求写三页 | 评审直接跳过，重点没人看 |
| 只写实现、不写使用界面 | 团队对“做成什么样”没有共识，联调才发现差异 |
| 用模块调用流程图代替接口定义 | 没有抽象，读者只能看到“谁调谁” |
| 两套方案揉一篇 | 无法逐条对比，决策靠印象 |
| 伪代码语义含糊 | 实现时各自理解，返工 |
| 索引不写依据 | 索引与查询不匹配，白建还添写放大 |
| 对使用界面做不兼容调整 | 调用方编译失败/系统崩溃，客户流失 |

## 自检

**Q1** 为什么“现状与需求”要写短，“使用界面”要写透？

▸ 答案：现状与需求是**共识确认**，读者只需要知道“问题是什么、要改什么”；写长会稀释重点。使用界面是**交付规格**，是团队对“做成什么样”的唯一精确共识，写不透就会出现“各做各的，联调对不上”。原文的说法是：接口这一部分是团队共识确认的关键。

**Q2** 接口有哪三类？为什么事件与插件容易漏？

▸ 答案：常规 DOM API、事件、插件。函数调用最直观，所以容易被写；事件涉及“谁保证送达、重复怎么办”，插件涉及“注册与失败隔离”，这两类不写清，集成时就会出问题——而它们恰恰是跨模块协作的主要通道。

**Q3** 为什么详细设计要先写数据结构，再写算法？

▸ 答案：因为 `程序 = 数据结构 + 算法`，而索引与访问方式由算法决定、算法又依赖数据结构。先定表结构（含外键与索引依据），再写每个 UserStory 的流程，顺序反了就会出现“先建索引再找查询”的浪费。

**Q4** 两套方案为什么必须分成两篇文档？

▸ 答案：因为评审需要**逐条对比前提、代价与风险**。揉在一篇里，两套方案的假设会互相污染，读者无法独立判断；分成两篇，每篇可独立评审，再配一篇对比结论（[79.3 方案对比与决策](../79-架构设计方法/79.3-方案对比与决策.md)）。

**Q5** 一份方案写完后，怎么快速判断它“能不能上评审会”？

▸ 答案：跑一遍章节自查（背景/需求/方案对比/接口/数据/容量/失败模式/回滚/里程碑），再问一句“读者只看接口那节，能不能判断这是不是他要的”。两关都过，才值得占评审会的时间；否则被问的问题，都是自己本该写清楚的。
