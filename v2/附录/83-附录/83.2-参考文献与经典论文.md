# 83.2 参考文献与经典论文

## 一句话

> 论文清单的价值不在「读过」，而在**知道每个结论的出处、它成立的前提、以及它在工程里被谁修正过**——引用一个 2007 年的结论去解决 2026 年的问题，比不引用更危险。

## 三条读法（先学会不浪费时间）

| 读法 | 具体做法 | 为什么 |
|---|---|---|
| **只读三处** | 摘要 → 第一张架构图 → 实验设置（硬件、负载、数据分布） | 90% 的引用只需要这三处；方法细节等你真要复现再读 |
| **分清 claim 层级** | 论文证明的是「在它的假设下、它的负载上、它的硬件里」的界 | 「论文说 P99 是 10ms」和「你的系统 P99 是 10ms」之间隔着你的数据分布 |
| **只追一条链** | 问题 → 前作不行在哪 → 论文改了什么 → **代价是什么** | 读不出代价 = 没读懂。所有系统论文的贡献都可以写成「用 X 换 Y」 |

> 🔑 一句话判据：**读完一篇论文，你要能说出「它在什么情况下会失效」**。说不出失效条件，等于只记住了结论。

## 按问题找论文（比按年份找更有用）

不要从 1978 年读到 2026 年。**带着你手上这个问题去查**，一次只读 1–2 篇。

| 你手上的问题 | 先读这几篇 | 为什么是它们 |
|---|---|---|
| 到底能不能既一致又高可用 | Brewer《CAP》2000 / Gilbert & Lynch 证明 2002 / Brewer《CAP Twelve Years Later》2012 / Abadi《PACELC》2012 | 先看原始表述，再看「三选二」是怎么被误读的，最后拿到「平时也在取舍」的补充，见 [17.1 CAP 的由来与准确表述](../../L1-分布式原理/17-CAP与PACELC/17.1-CAP的由来与准确表述.md) |
| 为什么我的主从切换会丢数据 | Ongaro & Ousterhout《Raft》2014 / Lamport《Paxos Made Simple》2001 | Raft 把「选举安全 + 日志匹配 + 提交规则」讲成可实现的算法，是读共识的最小入口 |
| 分布式事务怎么选 | Gray & Reuter 的 2PC 传统 / Garcia-Molina & Salem《Sagas》1987 | Saga 原始论文就写清了「补偿不是回滚」，这是今天 TCC/Saga 之争的源头 |
| 缓存该由谁管 | DeCandia 等《Dynamo》2007 | 一致性哈希 + 向量时钟 + 最终一致读写，一个系统里把「可用优先」的代价全展示了 |
| 全球强一致到底要付什么 | Corbett 等《Spanner》2012 | TrueTime 的「不确定区间 + 等待」是拿硬件（原子钟/GPS）换外部一致性 |
| 时钟不可信时怎么排序 | Lamport 1978 / Fidge & Mattern 1988（向量时钟）/ Kulkarni 等《HLC》2014 | 从偏序 → 并发判定 → 近似物理时间的演进链 |
| 为什么尾延迟比均值重要 | Dean & Barroso《The Tail at Scale》2013 | 扇出放大长尾 + 缓解手段（ hedged request、微分区）一次讲完 |
| 副本放几个、纠删码省多少 | Ghemawat 等《GFS》2003 / O'Neil 等《LSM-Tree》1996 | 前者是副本与 cheap 机器的经典权衡，后者解释了写放大从哪来 |
| 数据湖上怎么做 ACID | Armbrust 等《Lakehouse》2021 /《Delta Lake》2020 | 表格式 = 元数据 + 文件 + 事务日志，这是「湖仓一体」的底座 |
| 检索为什么不能只靠向量 | Malkov & Yashunin《HNSW》2016 / Lewis 等《RAG》2020 / Liu 等《Lost in the Middle》2023 | 从索引结构 → 检索增强 → 「塞多了反而漏」的实证 |
| 推理服务怎么把 GPU 吃满 | Kwon 等《PagedAttention / vLLM》2023 | 显存碎片是推理吞吐的第一瓶颈，分页管理是这代推理引擎的起点 |
| Agent 应该做成什么样 | Yao 等《ReAct》2022 / Anthropic《Building effective agents》2024 /《12-Factor Agents》2025 | 从「想与做交替」到「workflow 优先于自主 Agent」的工程收敛 |
| 大模型为什么能「涌现」 | Vaswani 等《Attention Is All You Need》2017 / Kaplan 等 2020 / Hoffmann 等《Chinchilla》2022 | 架构 → 规模定律 → 「参数与数据要同比例涨」的修正 |
| 对齐是怎么做的 | Ouyang 等《InstructGPT》2022 / Rafailov 等《DPO》2023 | RLHF 的工程化版本与它的简化替代 |
| 我该怎么评测一个 AI 功能 | Zheng 等《LLM-as-a-judge / MT-Bench》2023 / 各家的 eval 指南 | 概率系统的验收必须靠「固定集 + 通过率 + 抽样人工」 |

## 一、分布式与共识：不可绕过的十四篇

| 年份 | 论文 / 文章 | 一句话结论 | 对本知识体系的含义 |
|---|---|---|---|
| 1978 | Lamport《Time, Clocks, and the Ordering of Events》 | 没有全局时钟也能定义「先后」：靠消息传递的偏序 | 一切「分布式顺序」讨论的起点，见 23.3 Lamport 逻辑时钟（待补） |
| 1985 | Fischer, Lynch, Paterson《Impossibility of Distributed Consensus》 | 完全异步 + 允许一个崩溃 ⇒ 无终止共识 | 「共识不可能」是限定条件下的结论，工程用超时绕开，见 22.2 FLP 不可能性（待补） |
| 1988 | Fidge / Mattern《Vector Clocks》 | 每个节点一维计数，可判定因果与并发 | 冲突检测、多主复制的理论工具，见 23.4 向量时钟（待补） |
| 1987 | Garcia-Molina & Salem《Sagas》 | 长事务拆成局部事务 + 补偿动作 | 补偿不是回滚，这个区分决定了今天所有 Saga 实现，见 [24.5 Saga (编排 / 协同 / 补偿)](../../L1-分布式原理/24-分布式事务/24.5-Saga.md) |
| 2000 / 2002 | Brewer《CAP》/ Gilbert & Lynch 形式化证明 | 分区时 C 与 A 不可兼得 | 「三选二」是误读；P 不是选项，见 [17.2 为什么 “三选二” 是错的](../../L1-分布式原理/17-CAP与PACELC/17.2-为什么三选二是错的.md) |
| 2001 | Lamport《Paxos Made Simple》 | 用多数派 + 提案号把共识讲清楚 | 读懂 Raft 之前先读它，理解「为什么需要两阶段」 |
| 2003 | Ghemawat 等《The Google File System》 | 大文件 + 追加写 + 廉价机器 + 单主 | 「假设硬件会坏」的设计范式 |
| 2006 | Chang 等《Bigtable》 | 稀疏多维有序 Map，按行分片 | 列族模型的源头；也解释了「LSM + 单主」的组合 |
| 2007 | DeCandia 等《Dynamo》 | 一致性哈希 + 向量时钟 + 最终一致读写 | 「永远可写」的代价清单：冲突要应用层解决 |
| 2010 | Hunt 等《ZooKeeper》 | 用「等待无关」的线性一致写 + FIFO 客户端顺序做协调 | 注意：读可能陈旧，「ZK 强一致」是误读，见 [48.6 产品 (etcd / Consul / ZooKeeper / Nacos)](../../L4-组件与技术/48-配置与协调/48.6-产品.md) |
| 2011 | Kreps 等《Kafka》 | 追加日志 + 分区 + 消费位点，把消息当可重放的日志 | 「日志即事实源」的工程化，见 [43.1 消息模型](../../L4-组件与技术/43-消息队列/43.1-消息模型.md) |
| 2012 | Corbett 等《Spanner》 | TrueTime 的不确定区间 + 等待，换外部一致性 | 全球强一致的物理成本：原子钟、GPS、提交等待 |
| 2012 | Abadi《Consistency Tradeoffs in Modern Distributed Database Design》(PACELC) | 无分区时仍在 L 与 C 之间取舍 | 补上 CAP 的「平时」，见 [17.4 PACELC：无分区时的延迟-一致性权衡](../../L1-分布式原理/17-CAP与PACELC/17.4-PACELC.md) |
| 2014 | Ongaro & Ousterhout《In Search of an Understandable Consensus Algorithm》(Raft) | 强 leader + 日志匹配 + 任期号 | 今天 etcd / TiKV / Consul 的共同底座，见 [21.5 Raft：选主](../../L1-分布式原理/21-共识与选主/21.5-Raft选主.md) |
| 2019 | Pang 等《Zanzibar》 | 用关系元组 + 快照令牌做全球授权 | 「权限系统也要一致性模型」的范本，见 [49.3 权限中心与权限矩阵](../../L4-组件与技术/49-身份与访问管理/49.3-权限中心与权限矩阵.md) |

> 💡 补两篇「读起来不累但改变判断」的：Vogels《Eventually Consistent》(2008) 讲清了「最终」到底承诺了什么；Brewer《CAP Twelve Years Later》(2012) 亲手纠正了「三选二」。

## 六、标准、规范与治理（比论文更该常查）

论文告诉你「可以怎么做」，标准告诉你「必须怎么做、别人会怎么接」。

## 八、把论文变成架构决策：三问

读完不等于用得上。落到决策前，必须能回答这三问：

| 问题 | 不合格的回答 | 合格的回答 |
|---|---|---|
| **它的假设和我的现状差多少？** | 「论文的负载是均匀的，我们也是」 | 「论文假设单机房内网 RTT < 1ms，我们是跨地域 30ms，所以它的租约时长要按比例放大」 |
| **它换掉了什么？** | 「它更快」 | 「它用写放大换读延迟，我们的写 QPS 是读的 3 倍，所以这个交换对我们不利」 |
| **退出成本多少？** | 「社区很大，不会锁死」 | 「数据模型绑定了它的表格式，迁移要么重写 ETL，要么双写 3 个月」 |

配合 [4.3 技术选型的评估维度](../../需求/4-技术决策与ROI/4.3-技术选型的评估维度.md) 一起用：论文回答「可能性」，评估维度回答「该不该」。

## 反模式

| 反模式 | 后果 |
|---|---|
| 收藏夹式阅读（存 200 篇，读 3 篇） | 产生「我知道」的错觉，评审时说不出前提 |
| 把论文里的性能数字当容量规划输入 | 硬件、数据分布、负载模型都不同，误差可达数量级 |
| 只读结论，不读实验设置 | 引用了一个「在 SSD + 单机房 + 均匀 key」下成立的结论去论证跨云方案 |
| 引用 2010 年前的基准数据论证今天的选择 | 存储介质与网络带宽已经换了两代 |
| 分不清文献类型（论文 / 官方文档 / 工程博客 / 营销稿） | 把厂商博客的跑分当独立评测 |
| 用「最新论文」否定工程常识 | 论文常省略运维成本，而运维成本占生命周期大头 |
| 同一篇论文引用时不带版本（如 MCP 规范） | 协议在两年内改了四版，行为可能完全不同 |

> 🔑 引用文献的纪律：**给结论、给前提、给版本**。缺一个，读者就无法判断该不该信。

## 自检

**Q1** 有人说「Dynamo 论文证明了最终一致性够用，所以我们的库存系统也可以最终一致」。请指出这个推理在哪一步断了。

▸ 答案：断在「业务语义」这一步。Dynamo 面对的是**购物车**——冲突可以合并（并集），丢一件商品不会造成资损；库存扣减面对的是**不可逆的资源让渡**，冲突的后果是超卖。论文给出的是「在可合并的冲突上，最终一致够用」，不是「所有场景够用」。正确做法：库存要么走强一致（如单行条件更新 + 乐观锁），要么在最终一致之上加**预留/冻结**与对账，把不可逆操作收敛到一处。

**Q2** 团队要选型推理引擎，理由是「vLLM 论文说吞吐提升 24 倍」。请给出三个必须追问的问题。

▸ 答案：① **基线是什么**——24 倍是相对 HuggingFace `generate()` 的朴素实现，不是相对你现在的 SGLang/TensorRT-LLM；② **负载是什么**——论文用的是共享前缀 + 长输出的合成负载，你的真实负载如果是短输入短输出、前缀各不相同，PagedAttention 的收益会大幅缩水；③ **代价是什么**——分页管理增加了调度复杂度，且显存换吞吐意味着**单请求延迟可能上升**，要先确认你的 SLO 是 TTFT 还是总吞吐。三个问题都指向同一件事：**先在自己的负载上跑 A/B，再谈倍数**。

**Q3** 为什么「ZooKeeper 是强一致的」这句话会被写进很多架构文档？请从论文原文的角度纠正它，并说明这个误读会导致什么工程后果。

▸ 答案：论文的准确承诺是「**写**是线性一致的（走 ZAB 多数派），且客户端看到的是 FIFO 顺序，**读**可以读本地副本、可能陈旧」。误读的后果很具体：① 用 ZK 做「配置即时生效」的保证，改了配置后立刻读，可能读到旧值——正确做法是依赖 watch 通知，或在关键读之前 `sync()`；② 用它当分布式锁后，以为「拿到锁 = 看到最新数据」，实际上锁与数据可见性是两个问题；③ 在跨机房场景假设读也是线性的，导致切流后短暂脏读。

**Q4** 你在评审里看到「参考 Spanner，我们用 TrueTime 实现全球强一致」。请用一句话指出最可能的漏洞，并给出替代方案的方向。

▸ 答案：漏洞是**没有 TrueTime 的硬件前提**——Spanner 依赖 GPS + 原子钟把时钟不确定区间压到个位数毫秒，并在提交时**等待**这个区间过去。没有这套硬件，你只能得到「带不确定区间的物理时钟」，无法给出外部一致性。替代方向：① 放弃全球强一致，改**分区内强一致 + 跨区最终一致**（多数业务的实际需求）；② 用 HLC + 单主写 + 会话保证，把「读己之写」这类真实需求单独满足；③ 如果确实要全球强一致，先算清提交等待带来的延迟代价（跨洲 RTT 本身就是几十毫秒）。

**Q5** 为什么「LLM-as-judge」不能直接替代人工评审？请给出一个能暴露 judge 偏差的实验设计。

▸ 答案：judge 有系统性偏差：偏好更长的答案、偏好与自己风格相近的输出、对位置敏感（先出现的候选得分更高）、对自家模型有隐性偏好。暴露偏差的实验：**把同一份答案分别放在 A/B 两个位置各评一次**（位置偏差），**把正确答案人为扩写 30% 但内容不变**（长度偏差），**用两个不同厂商的模型做 judge 评同一批样本并算一致性（Cohen's κ）**。如果位置互换后结论翻转、或扩写后分数显著上升，judge 就只能当**筛选器**，最终判定仍需人工抽样校准。
