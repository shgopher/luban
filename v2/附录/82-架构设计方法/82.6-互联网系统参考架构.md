# 82.6 互联网系统参考架构

## 一句话

> 抛开业务差异，互联网公司的技术架构其实**基本一样**：存储层 / 开发层 / 服务层 / 网络层 / 用户层 / 业务层六层，外加运维、测试、数据、管理四类**平台**。参考架构**不是设计，是检查表**——先按它问「这一层我需要吗」，答「不需要」也要写进文档。

## 全景：六层 + 平台

| 层 | 组件清单 | 解决什么问题 |
|---|---|---|
| **存储层** | SQL：MySQL / PostgreSQL + 分库分表中间件（DBProxy、TDDL、MySQL Router、Atlas、UMP）；NoSQL：Memcache / Redis / MongoDB；小文件：TFS / JFS / Haystack（底层 HBase / Hadoop / Hypertable / FastDFS）；大文件：Hadoop / HBase / Storm / Hive（云梯、TDW） | 数据拆分后的「怎么拆、怎么组合」；重复造轮子；海量小数据与海量日志的存与取 |
| **开发层** | 开发框架（SSH / SpringMVC / Play、Rails、ThinkPHP、Django）；Web 服务器（Tomcat / JBoss / Resin / Nginx / Apache、Tengine）；容器（Docker） | 多团队技术栈不统一 → 语言不通、人力不能流动；服务器自研成本高；虚拟化太重 |
| **服务层** | 配置中心；服务中心（服务名字系统 / 服务总线系统）；消息队列（Notify / MetaQ / Kafka / ActiveMQ / RocketMQ） | 系统间依赖随数量**平方级**膨胀带来的「配置」「调度」「异步通知」复杂度 |
| **网络层** | 负载均衡（DNS、HTTP-DNS、Nginx、LVS、F5、SLB/ULB）；CDN；多机房（同城 / 跨城 / 跨国）；多中心 | 单系统高可用 ≠ 整体业务高可用；「最后一公里」；单机房是全局网络单点 |
| **用户层** | 用户管理（SSO / CAS、OAuth 2.0）；消息推送（短信 / 邮件 / 站内信 / APNS / GCM / 厂商推送 / 第三方推送）；存储云、图片云（CDN + 小文件存储） | 分散用户的连接与身份；触达用户；用户上传文件的存与取 |
| **业务层** | **无公共组件**。手段只有两个：**拆**（分层 / 微服务 / 微内核）与**合**（虚拟业务域 + 网关，类 Facade） | 业务复杂度：系统越来越庞大、业务越来越多 |
| **平台** | 运维平台、测试平台、数据平台、管理平台 | 运维 / 测试 / 数据分析 / 权限各自为政导致的重复工作与不规范 |

> 🔑 这张表的价值不在「照抄」，而在**逐层自问**：每一层都要能回答「我为什么需要它 / 我为什么不需要它」。答不出就是漏了设计点。

## 四条演进主线

| 主线 | 演进路径 | 触发条件 |
|---|---|---|
| **存储平台化** | 单库 → 分库分表 → 中间件化（DBProxy / TDDL）→ 存储平台（UMP：资源分配、备份、迁移、容灾、读写分离、分库分表对业务透明） | 实例数量多到「各自为政」：利用率低 + 维护成本高 |
| **服务去中心化** | 硬编码调用 → 配置中心 → 服务注册发现 → 服务网格 | 系统数 $n$ 时依赖数约 $n(n-1)/2$，人工配置不可维护 |
| **网络多层化** | 单机房 → 同城多机房 → 两地三中心 → 异地多活；DNS → 硬件 LB → 软件 LB → CDN | 单机房成为全局单点；「最后一公里」延迟 |
| **支撑平台化** | 运维 / 测试 / 数据 / 管理各自造轮子 → 四类平台 | 同类工作被重复做第 3 次 |

## 存储层的四个分支与各自判据

| 分支 | 判据 | 典型做法 | 关键数字 |
|---|---|---|---|
| **SQL** | 有事务、有强一致、有复杂查询 | 开源库 + 分库分表中间件 + 平台化 | MySQL 单表 **5000 万**行是参考线（复杂表 1000 万、简单表 1 亿） |
| **NoSQL** | 高并发、简单结构、可接受最终一致 | 用其自带集群，起步阶段**不必**平台化 | 平台化门槛：**几十台**收益不大，**上千到几千节点**才值得 |
| **小文件** | 用于展示的数据：**1 MB 以下**、数量巨大、访问量巨大 | 开源存储封装成与业务无关的平台 | Facebook 2013 年每天 **3.5 亿**张照片、**10 亿**次访问 |
| **大文件** | 视频、日志：几百 MB 到几 TB | 基本没得选：Hadoop / HBase / Storm / Hive | 源头是 Google 三篇论文（GFS / MapReduce / Bigtable） |

**平台化的投入产出算例**：2000 台 NoSQL 机器，平台把利用率提升 **10%** ＝ 省下 **200 台** ≈ 一年省**几十万元**。这条算法决定了「该不该做平台」，而不是「平台听起来更高级」。

## 怎么裁剪：三种典型系统的层数

| 系统 | 需要哪几层 | 可以砍掉什么 | 砍掉的理由 |
|---|---|---|---|
| 学生信息管理系统（1–2 万人） | 存储层 + 开发层 | 服务层、网络层、用户层、平台 | 无跨系统依赖（不需要服务层）；宕机 2 小时可接受（不需要多机房）；校内账号体系简单（不需要 SSO） |
| 内容 / 社区站（十万级 DAU） | 存储层 + 开发层 + 网络层（CDN）+ 用户层（SSO、推送） | 服务层（单体够用）、平台 | 读多写少靠 CDN；有 UGC 需要登录与推送；系统数少，消息队列可后置 |
| 交易类系统（百万级订单） | 全六层 + 平台 | 无（但每层可分期） | 跨系统依赖多（服务层必需）；资金不可丢（多机房）；对账与风控需要数据平台 |

> 裁剪的判据永远是 [58.6 架构设计流程与三原则](../../L5-工程效能/58-架构治理/58.6-架构设计流程与三原则.md) 那条：**目标规模 ＝ 当前规模 × 2~4**，超过 10 倍就是在为想象中的流量付费。

## 骨架图（画系统架构图时的起点）

```text
[用户层]   App / Web / 小程序 ── SSO ── 推送
              │
[网络层]   DNS → CDN → LB(Nginx/LVS) → 多机房
              │
[服务层]   网关 ── 服务注册发现 ── 配置中心 ── 消息队列
              │
[业务层]   业务服务（按域拆：交易 / 会员 / 商品 / 营销）
              │
[存储层]   MySQL(分库分表) / Redis / ES / 对象存储 / 大数据
              │
[开发层]   框架 + Web 容器 + 镜像（贯穿以上各层的运行底座）
[平台]    运维 / 测试 / 数据 / 管理（横向支撑）
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 把参考架构当设计直接照抄 | 小系统背上服务层与平台，上线推迟数月 |
| 只有 1 个业务系统就建服务层（注册中心 + 配置中心 + MQ） | 运维成本翻倍，收益为零 |
| 几十台 NoSQL 就上存储平台 | 投入远大于收益（平台门槛是上千节点） |
| 每个业务各自实现分库分表 | 重复造轮子；应由中间件统一下沉 |
| 用几十台机器撑「亿级」目标 | 层级齐了，但每层都撑不住，等于只有图没有架构 |
| 文档里「不需要某层」直接不写 | 评审会认为遗漏设计点；应写「无」并给出理由 |
| 认为 NoSQL 是「不要 SQL」 | 它是 Not Only SQL，是关系库的补充而非替代 |

## 自检

**Q1** 一个 1–2 万用户的学生系统，参考架构里哪几层可以砍掉？为什么？
▸ 答案：砍掉服务层、网络层（多机房部分）、用户层、平台。理由：系统数少，跨系统依赖不存在（服务层无价值）；宕机 2 小时可接受（不需要多机房）；账号体系单一（不需要 SSO）；没有重复造轮子（不需要平台）。只保留存储层 + 开发层，并在存储层做**主备 + 跨机房同步**（数据丢失不可接受）。

**Q2** 参考架构为什么叫「检查表」而不是「设计」？
▸ 答案：因为它的用途是**逐层自问是否需要**，而不是逐层照搬。设计要求回答「这层的具体方案是什么、为什么这样选」；检查表只回答「有没有漏掉某一类复杂度」。跳过自问直接照抄，就是 [58.6](../../L5-工程效能/58-架构治理/58.6-架构设计流程与三原则.md) 里批评的「照搬大厂架构」。

**Q3** 什么时候值得做存储平台？判据是什么？
▸ 答案：看**实例规模**。几十台 NoSQL 做平台收益不大；上千到几千节点才值得——算例：2000 台提升 10% 利用率 ＝ 省 200 台 ≈ 一年几十万元。SQL 侧的门槛更低一些，因为分库分表逻辑一旦被每个业务各写一遍，重复成本立刻出现。

**Q4** 服务层解决的核心复杂度是什么？为什么是「平方级」？
▸ 答案：解决系统间的**配置、调度、异步通知**。系统数为 $n$ 时，两两之间都可能有依赖，最多约 $n(n-1)/2$ 条连接：10 个系统 45 条、100 个系统 4950 条——硬编码配置不可能维护，必须下沉到注册发现与配置中心。

**Q5** 小文件和大文件的选型判据分别是什么？
▸ 答案：小文件看「**1 MB 以下 + 数量巨大 + 访问量巨大**」，业务起步阶段就该做统一存储（否则每个业务重复实现）；大文件看体积（几百 MB 到几 TB），不能复用小块存储，且开源方案已成熟，「没有太多选择」，直接用 Hadoop / HBase 系。

**Q6** 业务层为什么「没有公共组件」？
▸ 答案：业务逻辑天然因公司而异，抽象不出通用组件；能复用的只有**手段**——拆（分层 / 微服务 / 微内核）与合（虚拟业务域 + 网关）。所以业务层的能力体现在「怎么拆、怎么合」，而不是「有什么现成组件」。
