                    82.4 原型验证

                    一句话

                    原型的目的不是“做一个能用的版本”，而是用一个时间盒回答一个具体问题——问题、时间盒、成功判据、丢弃计划四样缺一不可；缺一样，原型就会变成“一个没人敢删的半成品”。

                    先破除三个误区

                    误区 现实
                    原型 = 小版本 小版本要维护、要上线；原型只回答一个问题，然后被丢掉
                    原型可以“顺便上线” 原型代码没有错误处理、没有测试、没有安全边界，上线就是事故
                    原型不用计划 没有时间盒与成功判据的原型，会无限期拖下去

                    Spike 的四要素

                    要素 要写成什么样 反例
                    问题 一个可回答的疑问句 “研究一下新架构”
                    时间盒 1–3 天，最多 1 周，超时即停 “做到能跑为止”
                    成功判据 一个可测的数或结论 “感觉还行”
                    丢弃计划 明确不合入、不进主干、到期删除 “先留着，以后可能有用”
                    // 原型（Spike）计划检查：有没有问题、时间盒、成功判据、丢弃计划。
if s.q == "" { errs = append(errs, "缺问题") }
if s.box == "" { errs = append(errs, "缺时间盒") }
if s.done == "" { errs = append(errs, "缺成功判据") }
if s.drop == "" { errs = append(errs, "缺丢弃计划") }

                    真实输出（本机 go1.27.1 darwin/arm64）：

                    ✓ 分库分表后跨片查询能否 &lt;200ms
✗ 新技术选型                    [缺成功判据 缺丢弃计划]
✓ 消息队列能否支撑 5w TPS

                    完整代码在仓库 tools/examples/82.4-spike/，go run . 可复现这段输出。

                    第二行是典型的失败原型：“新技术选型”是个话题，不是问题；没有判据就无法结束，没有丢弃计划就会留下一个吃维护成本的玩具。

                    两类原型，别混用

                    类型 回答什么 产物 寿命
                    技术验证（Spike） 这条路走不走得通（性能、兼容、可行性） 压测数据、结论、几段丢弃的代码 天级，用完即删
                    体验原型（Prototype） 用户会不会用、流程顺不顺 可点击的界面 / 假数据页面 周级，被正式版本替换

                    混用的后果：用 Spike 去做体验验证（用户看不懂），或用 Prototype 去验证性能（假数据没有参考价值）。

                    时间盒：超时即停，结论照写

                    情况 处理
                    时间盒内得到明确结论 采纳/放弃，写进 ADR
                    时间盒内没得到结论 照样停，写下“已知什么、还缺什么、下一步怎么验证”
                    越做越觉得有意思 这是最危险的状态——立刻停，它已经变成了项目

                    🔑 原型最贵的不是代码，是它带来的沉没成本：一旦有人开始“顺手完善”，它就会以“临时方案”的身份长期留在生产环境里。

                    什么时候该做原型

                    信号 该做 不该做
                    关键假设没被验证过（性能、兼容性） ✅ Spike 1–3 天 —
                    需求本身还没想清楚 — ❌ 原型救不了模糊需求（先回 82.1）
                    两个方案差距不大 — ❌ 选一个直接做，用真实反馈决定
                    方案不可逆且成本高 ✅ 必须验证 —

                    许式伟在概要设计里还有一条相关实践：系统设计阶段就应该有代码产出——框架代码 + 原型/mock，用来验证“架子搭得起来”。这比后期发现“接口对不上”便宜得多（58.6 架构设计流程与三原则 里“详细设计才发现不可行”的案例就是这个坑）。

                    原型的时间盒与放弃判据

                    时间盒的长度不该由“做完要几天”决定，而由“最早哪天能下结论”决定；放弃判据必须在动手前写成数字，否则盒子到期时没人有勇气喊停。把原型当一次赌注算期望：技术验证的回本点是 30% 的验出率，性能验证 40%，交互验证 48%；时间盒翻倍，回本点同步翻倍——交互原型做到 10 天，回本点涨到 95%，那已经不是原型，是“必须验出问题才不亏”的开发。

                    三类原型：先分清验什么

                    除了按产物分成 Spike 与 Prototype，还可以按验证对象再切三类：技术验证、性能验证、交互验证，其中性能验证是技术验证的子类。三类的时间盒都用同一把尺子定：盒内必须能测出放弃判据里的那个数。

                    类型 时间盒（天） 产出 放弃条件（动手前写死） 回本点 p*（本机计算）
                    技术验证（兼容/可行性） 3（上限 5） 一条能跑通的最小链路 + 阻断点清单 盒内关键链路仍有 ≥1 个阻断点无解 → 放弃该技术路线 0.30
                    性能验证（压测） 2（上限 2.5） 压测曲线 + 与目标差距的倍数 压测值距目标 ≥2 倍（目标 P99 200ms，压测 >400ms）→ 放弃“优化现有架构” 0.40
                    交互验证（可用性测试） 5（上限 5.2） 主任务完成率 + 卡点清单 5 名目标用户中 ≥3 名无法独立完成主任务（完成率 <60%）→ 放弃该交互方案 0.48

                    “上限”由下面的回本点模型反推：目标验出率 50% 时，盒子上限 = q×0.5×R/(人数+V)。超过上限，即使有一半把握验出问题也不回本。性能验证的阈值也不是拍脑袋：延迟目标要跟容量一起算——82.2 容量估算 用「并发 ≈ QPS × 延迟」把吞吐和延迟绑在一起，原型只负责测量，不负责重新定目标。

                    三类原型的放弃条件形状相同：一个可观测的数 + 一个阈值 + 一个动作。反例是“效果不好就放弃”——“不好”不是数，盒子到期只会得到一句“再给我两天”。

                    回本点：原型这笔账怎么算

                    把原型当一次赌注，期望收益 = q×p×R − 成本 − 延期：

                    • 成本 C = 时间盒天数 × 投入人数（人天）；
                    • 延期 Delay = 时间盒天数 × V（占关键路径 1 天的机会成本，人天/天；并行验证 V=0）；
                    • q = 不做原型时问题真实存在的概率；
                    • p = 时间盒内能把问题验出来的概率（原型团队唯一能提升的变量）；
                    • R = 问题留到联调/上线才发现的返工成本（人天）。

                    令期望收益为 0，得回本点 p* = (C + Delay)/(q × R)：p 要达到多少，这笔赌注才不亏。

                    回本点 p* 判定 含义
                    ≤0.4 值得做 收益 ≥2.5 倍成本：盒子小、返工贵
                    0.4–0.8 有条件做 必须先写死放弃判据，否则盒子会通胀
                    0.8–1.0 边界 只有判据极硬、q 估得准才做
                    >1 直接上 即使 100% 验出问题也不回本

                    另一种问法更实用：如果只能做到 p=0.6（六成概率验出问题），后期返工要多大才回本？技术验证 20 人天、性能验证 16.7 人天、交互验证 11.9 人天。换成倍数是一条经验判据：p=0.5、q=0.5 时，返工成本至少是原型成本的 4 倍才值得做（推导：p* = C/(qR) ≤ 0.5 ⇒ R ≥ 2C/(q×0.5) = 4C）。

                    // 回本点：p* = (时间盒×人数 + 时间盒×V) / (q×R)
func (p proto) breakEvenP() float64 {
	return p.total() / (p.q * p.R) // total() = box*people + box*V
}

                    真实输出（本机 go1.27.1 darwin/arm64，Apple M1；完整代码在 tools/examples/82.4-prototype-roi/）：

                    == 回本点：p* = (时间盒×人数 + 时间盒×V) / (q×R) ==
原型类型                         盒子     人天     延期      q      R    回本点p*  判定
技术验证（兼容/可行性）                  3    6.0    0.0   0.50     40     0.30  值得做（回本点 ≤0.4，收益 ≥2.5 倍成本）
性能验证（压测）                      2    4.0    2.0   0.60     25     0.40  值得做（回本点 ≤0.4，收益 ≥2.5 倍成本）

反例：可逆小改动                      3    3.0    6.0   0.30      8     3.75  直接上（回本点 >1，验出问题也不回本）
反例：需求模糊的交互原型                  5    5.0    0.0   0.80      5     1.25  直接上（回本点 >1，验出问题也不回本）

                    两个反例值得记住：可逆小改动占关键路径 3 天（Delay=6 人天），回滚却只要 8 人天，回本点 3.75；需求模糊的交互原型 q 高达 0.8，但返工只有 5 人天，回本点 1.25。回本点大于 1 说明问题问错了——要么验证这件事本身太贵，要么要验的结论对决策没有影响。

                    时间盒：从“想做完”改成“能下结论”

                    时间盒通胀的代价是可算的（同一程序的时间盒敏感性输出）：

                    技术验证（兼容/可行性）              box=1.5天→p*=0.15  box=3.0天→p*=0.30  box=6.0天→p*=0.60
性能验证（压测）                  box=1.0天→p*=0.20  box=2.0天→p*=0.40  box=4.0天→p*=0.80
交互验证（可用性测试）               box=2.5天→p*=0.24  box=5.0天→p*=0.48  box=10.0天→p*=0.95

                    同一程序还输出时间盒上限（目标 p=0.5）：技术验证 5.0 天、性能验证 2.5 天、交互验证 5.2 天——超过上限即回不了本。

                    同一个原型，时间盒翻倍后回本点翻倍：技术验证从“三成把握就赚”变成“六成把握才不亏”，交互原型到 10 天时几乎要求“必定验出问题”。时间盒不是给团队的缓冲，是给判据的预算。

                    三条定盒规则：

                    1. 从判据倒推：先写“要测出 P99 是 200ms 还是 400ms”，再估“搭出能测这个数的环境要几天”。性能验证 2 天够，是因为 2 天能测出“差一个数量级”，不是 2 天能把系统优化到目标。
                    2. 超过上限就拆盒：一个 6 天的技术验证不如拆成两个 3 天的盒子——第一个盒子若撞上阻断点，只花 3 人天就止损（回本点 0.30 而非 0.60）；代价是两次准备成本，换的是“更早否决”的权利。
                    3. 关键路径上的盒子再砍半：性能验证与开发串行时 V=1，盒子上限从 5 天掉到 2.5 天；若每晚一天上线损失 5 人天（V=5），上限再降到约 1.1 天。占关键路径的原型，上限不是“几天能做完”，是“几天亏得起”。

                    什么该做原型，什么直接上

                    “什么时候该做原型”的信号表回答必要性；回本点回答可负担性——两问都过才动手。可负担性看六个判据：

                    情形 判断 依据（本机计算）
                    返工成本 ≥4×原型成本，且 q≥0.3 做 p=0.5、q=0.5 时回本点 ≤0.5，毛收益 ≥2 倍成本
                    返工成本 <2×原型成本 直接上 q=0.5、p=0.5 时回本点 >1：返工比原型还便宜
                    q<0.2（问题大概率不存在） 直接上 q 在分母：q 减半，回本点翻倍
                    搭不出能测出判据的环境（p 上不去） 不做 p 上不去时，盒子再短也回不了本
                    占关键路径（V≥1） 盒子上限减半，或改并行 性能验证上限 2.5 天；V 翻倍则上限减半；可逆小改动（C=3、Delay=6）回本点 3.75
                    q 高但 R 小（问题真存在，修起来也便宜） 直接上 交互反例：q=0.8、R=5，回本点 1.25

                    最后一条最容易反着做：团队常把“问题确实存在”当成做原型的理由，但回本点看的是 q×R，问题存在不等于修起来贵。需求模糊时 q 很高、R 却很低，原型只会确认“用户确实不会用”，然后你仍然不知道正确的方案是什么（82.1 从需求到架构的推导 处理的是这一步）。

                    🔑 原型不是“小一号的正式版”，是用最小装置买一条信息。这条信息的价钱上限 = 返工成本 × 问题存在概率 × 能达到的验出率；超过上限就停手，把预算留给真实交付。时间盒由判据定，生死由回本点定。

                    反模式

                    反模式 后果
                    原型没有时间盒 无限期拖，变成“影子项目”
                    原型代码合入主干 无测试、无错误处理，事故源头
                    原型结论只停留在口头 三个月后没人记得验证过什么
                    用原型验证模糊需求 需求不清时，原型只会放大分歧
                    原型做完直接上线 跳过了设计、评审、压测，风险最高
                    为原型建完整 CI/监控 成本超过收益，且暗示它会长期存在
                    同时开 5 个原型 每个都做不完，团队注意力被切碎

                    自检

                    Q1 为什么原型必须有“丢弃计划”？

                    ▸ 答案：因为原型的代码质量（无测试、无错误处理、无边界检查）不适合长期存在；不写丢弃计划，它就会以“先这样吧”的方式留在生产里，变成没人敢删、没人敢改的技术债。写下来还有一层作用：让人在动手前就想清楚“这是要丢的”。

                    Q2 “时间盒到了没结论”该怎么办？

                    ▸ 答案：照样停，并写下结论：已知什么、还缺什么、下一步用什么方式验证（换方案、加人手、做正式 PoC）。继续做下去会把“验证”变成“开发”，沉没成本开始累积。

                    Q3 技术验证（Spike）和体验原型（Prototype）能混用吗？

                    ▸ 答案：不能。Spike 用假数据、只看性能与可行性，产物是数据与结论；Prototype 用真实交互、假后端，产物是流程与反馈。用 Spike 验证体验，用户看不懂；用 Prototype 验证性能，假数据没有参考价值。

                    Q4 什么情况下不该做原型？

                    ▸ 答案：三种：需求本身没想清楚（先做需求分析）；两个方案差距不大（直接选一个，用真实反馈迭代更便宜）；改动可逆且成本低（做完再回滚，比验证便宜）。

                    Q5 为什么说“概要设计阶段就该有代码产出”？

                    ▸ 答案：因为接口是否成立、架子是否搭得起来，只有写代码才能验证。只画图的概要设计，会把“接口不匹配”的风险推到联调阶段；一段框架代码 + mock 能在设计阶段就把这类风险暴露出来，且它本身就是最精确的文档（代码即文档）。
