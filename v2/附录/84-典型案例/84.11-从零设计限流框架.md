# 84.11 从零设计一个限流框架：分析 → 设计 → 实现

## 一句话

> 限流框架的价值不在算法（四种算法的主场是 [35.7 限流 (漏桶 / 令牌桶 / 滑动窗口 / 自适应)](../../L3-质量属性/35-可用性/35.7-限流.md)），而在把**「按什么维度限、限流器坏了怎么办、拒绝时说什么、key 怎么回收」**四个决定固化成配置；这篇用 155 行 Go 走完分析→设计→实现，代价是单机语义与全局 map 的约 1.9 倍争用。

[84.9 onex 生态九仓](84.9-onex生态九仓的可抄零件.md) 拆的是别人做好的零件，这篇反过来：**从零装一台**，每个决定都给备选、代价和实测。

## 规模前提卡

| 项 | 值 | 说明 |
|---|---|---|
| 入口 QPS | 5 万常态 / 15 万峰值 | 合成值，按历史峰值 ×2 留余量 |
| 实例数 | 40 | 每实例平均 1250 QPS，峰值 3750 |
| 限流维度 | IP、用户、租户、接口 | 4 类 key，登录前只能按 IP |
| 硬约束 | 过载不崩 > 误杀少 > 实现简单 | 三条排序决定后面所有取舍 |
| 误杀预算 | 正常流量 ≤0.1% | 超过就要放宽阈值或改维度 |
| 团队 | 6 人，无专职中间件 | 不引入需要长期维护的组件 |

## 分析：先划边界

框架类需求最容易一上来就写全，结果半年后没人敢改配置。先列「必须有」和「明确不做」：

| 必须有（v1） | 明确不做（v1） | 为什么 |
|---|---|---|
| 按 key 隔离，一个 key 打满不影响别人 | 分布式精确配额 | 先解决单机过载保护；跨实例一致性是第二轮 |
| 令牌桶（允许突发） | 多算法插件 | 一种算法先跑通，插件点是第二轮 |
| 拒绝返回 429 + `Retry-After` | 控制台 / 热更新 | 配置改一次要发版，v1 可接受 |
| 启动时校验配置，非法直接退出 | 按接口分级配置 | 先全局一套，按接口细分配置等有真实需求 |
| 空闲 key 自动回收 | 自适应阈值 | 自适应需要延迟反馈，先有人工阈值 |
| 可观测钩子（当前 key 数、拒绝数） | 内置 Prometheus 依赖 | 框架不绑监控库，留回调 |

> 🔑 边界的判据不是「以后会不会用」，是**不做会不会出事**：不做 key 回收会 OOM，必须做；不做分布式配额只会多放一点流量，可以等。

## 设计：三个关键取舍

### 取舍一：本地限流，还是每请求问一次 Redis

| 方案 | 单次成本 | 全局精度 | 依赖 | 结论 |
|---|---|---|---|---|
| 本地令牌桶 | 114–116 ns | 单机精确，全局最多超发 N 倍 | 无 | ✅ v1 |
| 每请求 Redis | 本地成本 + 1 次 RTT（同机房约 0.3–1 ms） | 精确 | Redis 可用性 | ❌ 热门接口扛不住 |
| 本地配额 + 定期校准 | 本地成本 + 秒级同步 | 秒级误差 | Redis（弱依赖） | 第二轮 |

40 个实例、全局配额 1 万 QPS，本地阈值就该设 250；但流量不会均分，实际会有的实例先打满、有的闲着——**本地限流限的是单机，不是全局**。N 倍陷阱的量化与「分布式限流三种实现」在 [35.7 限流 (漏桶 / 令牌桶 / 滑动窗口 / 自适应)](../../L3-质量属性/35-可用性/35.7-限流.md)，这里只做选型：v1 接受超发，因为它保护的是「单机不被打穿」，而全局配额属于计费/风控，不是可用性。

**代价**：全局超发上限是 N 倍（N = 实例数），扩缩容时阈值要跟着调；这不是 bug，是必须写进 runbook 的已知误差。

### 取舍二：一把全局锁，还是按 key 分片

先测再选。同一个框架，两种存 key 的方式，8 核并行、1024 个 key：

| 实现 | ns/op（3 次） | 说明 |
|---|---|---|
| 全局 map + 一把锁 | 195.7 / 198.5 / 200.2 | 所有 key 抢同一把锁 |
| 8 个分片 + 每片一把锁 | 104.5 / 105.3 / 108.6 | 约 **1.9 倍** |
| 全局 map，同一个热点 key | 203.2 / 204.2 / 208.2 | 锁争用依旧 |
| 8 个分片，同一个热点 key | 202.6 / 202.6 / 207.4 | 分片救不了热点 |

> 🔑 分片只在 key 分散时有效：哈希把 key 打散到不同锁上，但**所有请求都打同一个 key 时，8 个分片里还是只有 1 个在工作**。分片数经验值是 8–64，超过 CPU 核数收益递减；热点 key 要靠本地聚合或拆 key，不是加锁。

v1 先用全局 map（实现里的 `Keyed`），并行压测出现锁争用再换 `Sharded`（另加 84 行）；两者实现同一个 `Limiter` 接口，切换不碰调用方。

**代价**：分片后 `Len()` 要遍历所有分片，回收也要逐片扫；key 分布不均时仍会出现单分片热点。

### 取舍三：限流器自己坏了，放行还是拒绝

| 接口类型 | 故障时 | 理由 |
|---|---|---|
| 登录、支付、下单 | **fail-closed**（503） | 宁可少卖，不可超卖/被刷 |
| 商品详情、Feed、搜索 | **fail-open**（放行 + 标记） | 限流器故障的损失小于全站不可用 |
| 内部服务互调 | fail-open，但降级到并发限流 | 保护下游的是在途数，不是 QPS |

实现上把选择做成参数，不放行时回 `X-RateLimit-Degraded: 1`——**降级必须是显式的**，否则排障时没人知道这一秒的流量没被限。熔断与隔舱的边界见 [35.6 熔断与降级](../../L3-质量属性/35-可用性/35.6-熔断与降级.md) 与 [35.8 故障隔离 (线程 / 进程 / 资源 / 集群)](../../L3-质量属性/35-可用性/35.8-故障隔离.md)。

## 实现：155 行骨架

完整代码在仓库 `tools/examples/84.11-limitfw/`（含 README 与复现命令），正文只摘关键段。

### 接口与配置校验

```go
type Decision struct {
	Allowed    bool
	Remaining  int
	RetryAfter time.Duration
}

type Limiter interface {
	Allow(ctx context.Context, key string) (Decision, error)
}

type Config struct {
	Rate  float64       // 每秒补充的令牌数
	Burst float64       // 桶容量，决定允许的瞬时突发
	TTL   time.Duration // key 空闲多久后被回收
	Now   func() time.Time
}

func (c Config) validate() error {
	switch {
	case c.Rate <= 0:
		return errors.New("limit: rate must be > 0")
	case c.Burst < 1:
		return errors.New("limit: burst must be >= 1")
	case c.TTL <= 0:
		return errors.New("limit: ttl must be > 0")
	}
	return nil
}
```

`Now` 放进配置是为了可测：测试注入假时钟，不用 `sleep` 等补充。配置错误在 `New` 时就返回，不允许「跑起来再说」。

### 令牌桶

```go
func (b *bucket) allow() Decision {
	b.mu.Lock()
	defer b.mu.Unlock()
	now := b.now()
	if el := now.Sub(b.last).Seconds(); el > 0 { // 时钟回拨时 el <= 0，不补也不欠
		b.tokens += el * b.rate
		if b.tokens > b.burst {
			b.tokens = b.burst
		}
		b.last = now
	}
	if b.tokens >= 1 {
		b.tokens--
		return Decision{Allowed: true, Remaining: int(b.tokens)}
	}
	need := (1 - b.tokens) / b.rate
	return Decision{Allowed: false, RetryAfter: time.Duration(need * float64(time.Second))}
}
```

三处细节：**回拨不补令牌**（`el > 0` 才补，回拨期间只是暂停补充）；**等待时间由缺多少令牌反算**，不是拍一个 1 秒；**`RetryAfter` 向上取整到秒**，否则客户端拿到 0 会立刻重试，把限流变成重试风暴。

### 按 key 隔离与回收

```go
func (k *Keyed) Allow(_ context.Context, key string) (Decision, error) {
	k.mu.Lock()
	e := k.items[key]
	if e == nil {
		e = &entry{b: newBucket(k.cfg.Rate, k.cfg.Burst, k.cfg.Now)}
		k.items[key] = e
	}
	e.seen = k.cfg.Now()
	k.mu.Unlock()
	return e.b.allow(), nil
}
```

全局 map 一把锁（上面的实测基线），同一 key 复用同一个桶；回收协程按 `TTL/2` 扫一遍，删掉闲置超过 `TTL` 的 key。分片版把这张 map 按哈希切成 8 份，另加 84 行净代码，语义不变。**没有回收，按 IP 限流就是内存泄漏**——扫描器每秒换一个 IP，一天能塞满几百万个 key。

### 接入 HTTP

```go
func Middleware(l Limiter, keyFn func(*http.Request) string, failOpen bool) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			d, err := l.Allow(r.Context(), keyFn(r))
			if err != nil {
				if failOpen {
					w.Header().Set("X-RateLimit-Degraded", "1")
					next.ServeHTTP(w, r)
					return
				}
				http.Error(w, "limiter unavailable", http.StatusServiceUnavailable)
				return
			}
			if !d.Allowed {
				w.Header().Set("Retry-After", RetryAfterSeconds(d.RetryAfter))
				w.Header().Set("X-RateLimit-Remaining", "0")
				http.Error(w, "rate limited", http.StatusTooManyRequests)
				return
			}
			next.ServeHTTP(w, r)
		})
	}
}
```

key 怎么取是业务决定：登录前只能 `r.RemoteAddr`，登录后换成租户 ID——**维度选错，限流器就成了误杀机器**（NAT 后面几千人共享一个出口 IP）。

### 验证：测试与实测

`go test -race ./...` 覆盖 8 个用例，全绿（go1.27.1 darwin/arm64，Apple M1）：

| 用例 | 断言 |
|---|---|
| `TestBurstThenDeny` | burst=3 放行 3 个，第 4 个拒绝且 `RetryAfter ∈ (0,100ms]`，前进 100ms 后恢复 |
| `TestKeyIsolation` | A 打满不影响 B，B 打满不影响 A |
| `TestConcurrentBurst` | 100 goroutine 抢 burst=10，恰好放行 10 个 |
| `TestTTLReclaimsIdleKeys` | 空闲超过 TTL 的 key 被回收，`Len()=0` |
| `TestConfigValidation` | rate/burst/TTL 非法时构造失败 |
| `TestMiddlewareDeny` | 第 2 个请求 429，`Retry-After: 1` |
| `TestMiddlewareFailOpen` | 故障时放行并带 `X-RateLimit-Degraded`；fail-closed 时 503 |
| `TestShardedMatchesKeyed` | 分片版与全局版对同一串请求的放行结果逐次一致 |

实测（`go test -run '^$' -bench . -benchmem -count=3`）：

| 场景 | ns/op（3 次） | B/op | allocs/op |
|---|---|---|---|
| 单协程、单 key | 114.1 / 116.3 / 116.3 | 0 | 0 |
| 8 核并行、1024 key、全局 map | 195.7 / 198.5 / 200.2 | 0 | 0 |
| 8 核并行、1024 key、8 分片 | 104.5 / 105.3 / 108.6 | 0 | 0 |
| 8 核并行、同一热点 key、全局 map | 203.2 / 204.2 / 208.2 | 0 | 0 |
| 8 核并行、同一热点 key、8 分片 | 202.6 / 202.6 / 207.4 | 0 | 0 |

按 15 万 QPS 折算：116 ns × 15 万 ≈ **17 ms CPU/秒**，占单核 1.7%；限流器本身不是瓶颈，**锁争用才是**，这也是分片值得做的唯一理由。

> ⚠️ 绝对值会随机器状态浮动：同一台 M1 在负载高时测到过 186 ns（单协程）与 495 ns（并行全局），空闲时是 116 ns 与 198 ns，接近 2 倍。**看比值，不看绝对值**；复现命令在 `tools/examples/84.11-limitfw/README.md`。

## 失败模式：这套组合最可能怎么坏

| 失败 | 触发 | 现象 | 防线 |
|---|---|---|---|
| key 爆炸 | 扫描器换 IP、租户 ID 带随机串 | map 内存涨、GC 变频繁 | TTL 回收 + key 数上限告警（超过阈值拒绝新建） |
| 热点 key 打满单分片 | 大促主 IP / 默认租户 | 其他 key 也变慢 | 拆 key（IP+UA 哈希）、热点单独配额 |
| 本地配额 × 40 | 扩缩容或流量不均 | 全局超发，下游被打穿 | 阈值按 N 算，扩缩容走发布流程；关键接口上第二轮全局配额 |
| 时钟回拨 | NTP 校时、虚拟机迁移 | 回拨期间令牌不补充（不超发） | 用单调时钟做补充间隔，墙钟只用于 TTL |
| 429 没带 Retry-After | 实现漏了 | 客户端立即重试，雪崩 | 中间件强制带上，最小 1 秒 |
| 误杀正常用户 | 维度选 IP（NAT 共享） | 投诉「偶尔打不开」 | 登录后切租户/用户维度；灰度观察拒绝率 |

## 演进：四波，不一次到位

| 波次 | 做什么 | 触发条件 |
|---|---|---|
| 1 | 单机令牌桶 + 按 key + 429 | 现在 |
| 2 | 8 分片、key 上限、指标钩子 | 并行压测出现锁争用（>400 ns/op） |
| 3 | 关键接口上 Redis 全局配额（本地预限流 + 秒级校准） | 出现超发事故或计费需求 |
| 4 | 自适应阈值（按延迟反馈），接进服务治理面 | 容量经常变、人工阈值维护不过来；治理面见 [30.4 服务治理 (注册、发现、熔断、限流)](../../L2-架构风格/30-微服务/30.4-服务治理.md) |

## 反模式

| 反模式 | 后果 |
|---|---|
| 在 handler 里 `NewLimiter()` | 每个请求新建桶，等于没限流，还多一次分配 |
| 用 QPS 限流保护连接池 | 突发时连接数照样打满，保护连接池要用并发限流 |
| 限流键用 `user_id`，但登录接口还没有用户 | 所有匿名请求共享一个 key，一限全站 |
| 拒绝返回 500 或空响应 | 客户端重试 + 监控误判为服务故障 |
| 阈值拍脑袋（「先设 1000 吧」） | 要么没保护，要么误杀；阈值应来自 [57.2 容量模型](../../L5-工程效能/57-容量与成本治理/57.2-容量模型.md) |
| 分布式限流每请求问 Redis | 多 0.3–1 ms，Redis 一抖全站 5xx，限流器成了单点 |

## 自检

**Q1** v1 为什么不做分布式限流？什么信号出现时才该做？

▸ 答案：本地限流保护的是「单机不被打穿」，分布式配额保护的是「全局不超发」，后者是计费/风控需求，不是可用性需求。该做的信号有两个：① 出现超发事故（下游被 N 倍流量打穿）；② 业务要按租户精确计费。两者都没有时，上 Redis 只是把限流器变成新的单点。

**Q2** 分片能解决热点 key 吗？为什么？

▸ 答案：不能。分片按 key 哈希，同一个 key 永远落在同一个分片，8 个分片里 7 个闲着，热点 key 仍然抢一把锁——实测同 key 并行，分片版 202.6–207.4 ns，全局版 203.2–208.2 ns——分片的 1.9 倍收益消失。热点 key 要靠拆 key（IP+UA、租户+接口）或单独配额，不是加锁。

**Q3** 限流器依赖的 Redis 挂了，登录接口该 fail-open 还是 fail-closed？

▸ 答案：登录 fail-closed（503）。理由是比较两种损失：fail-open 时攻击者可以无限撞库，损失是账号安全；fail-closed 时正常用户登不上，损失是可用性。登录接口的可用性可以用「稍后重试」兜底，账号被盗不可逆。反过来，商品详情应当 fail-open，因为限流器故障的概率远低于「详情页全站打不开」的损失。

**Q4** `Retry-After` 为什么最少给 1 秒，而不是按实际等待时间给 100 ms？

▸ 答案：HTTP 的 `Retry-After` 只支持秒级（或 HTTP-date），给 0 或小于 1 秒会被客户端当成「立刻重试」，形成重试风暴；令牌桶的补充时间通常在毫秒级，向上取整到 1 秒是**故意多等一点**，换客户端不抖动。要更细的控制得用响应体里的自定义字段，而不是 `Retry-After`。
