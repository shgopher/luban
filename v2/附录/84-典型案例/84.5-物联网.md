# 84.5 物联网：协议、连接与断网续传

## 一句话

> 物联网的取舍不是“选 MQTT 还是 CoAP”，而是**在连接成本、消息可靠性、端侧存储之间分配预算**——本例的答案是：**MQTT 长连接 + 持久会话只保留 24 小时/100 条指令 + 端侧 WAL 与独立水位**，代价是 80 万并发约 20 GB 连接内存、端侧 32 MB WAL 分区，以及约 0.3% 的重复上报。

**数字口径**：本节是**合成案例**（设备量、消息量、断网时长均为构造值），不是任何一家公司的真实数据。机制不在这里重讲：接入与协议见 [69.1 设备接入与协议](../../L4-组件与技术/69-物联网/69.1-设备接入与协议.md)，设备影子见 [69.2 设备影子与物模型](../../L4-组件与技术/69-物联网/69.2-设备影子与物模型.md)，海量连接见 [69.3 海量连接与消息](../../L4-组件与技术/69-物联网/69.3-海量连接与消息.md)，断网续传见 [69.4 边缘计算与断网续传](../../L4-组件与技术/69-物联网/69.4-边缘计算与断网续传.md)，OTA 见 [69.5 固件升级](../../L4-组件与技术/69-物联网/69.5-固件升级-OTA.md)。

## 规模前提卡

| 项 | 值 | 说明 |
|---|---|---|
| 设备总量 | 200 万台 | 电表/水表 70%、传感器 20%、摄像头 10% |
| 峰值在线 | 80 万台 | 40% 同时在线 |
| 日消息量 | 20 亿条 | 上报 16 亿、下发 4 亿 |
| 均值 / 峰值 | 2.3 万条/秒 / **10 万条/秒** | 峰值是均值的 4.3 倍 |
| 单设备上报 | 1000 条/日 | 平均 1 KB/条 |
| 网络 | 4G / NB-IoT | 每天断网约 3 次，平均 8 分钟 |
| 端侧 Flash | 512 MB | 可用 128 MB，WAL 分区 32 MB |
| 团队 | 30 人 | 接入、平台、端侧各一组 |
| 硬约束 | 数据不丢；断网 7 天可续传；重复率 <1%；峰值 10 万条/秒；在线设备指令 5 秒内可达 | 排序：不丢 > 可续传 > 低重复 |

## 三个关键取舍

### 取舍一：协议选 MQTT、CoAP 还是 HTTP

| 协议 | 传输 | 下行能力 | 功耗 | 连接开销 | 适用 |
|---|---|---|---|---|---|
| HTTP 轮询 | TCP | 无真正下行，靠轮询 | 高 | 每次请求建连/复用 | 低频、弱网、简单设备 |
| CoAP | UDP | Observe 可下行 | 低 | 无连接状态，但要走 NAT/DTLS | NB-IoT、电池设备 |
| **MQTT**（所选） | TCP | 原生 pub/sub | 中 | 长连接，单连接约 25 KB | 常在线设备、指令下发 |

算一笔连接账就知道为什么不能全用 HTTP：

- 200 万设备每 30 秒轮询一次 = **6.67 万 QPS**；每次 2 KB 响应 = **133 MB/s** 下行。服务端和电池都受不了。
- MQTT keepalive 300 秒 = **6667 个心跳/秒**，是轮询的 1/10；80 万并发 × 25 KB ≈ **20 GB** 连接内存，6 台 8 GB broker 的水位约 **42%**。

```go
// 长连接与轮询的连接账。
const (
	devices = 2_000_000
	online  = 800_000
	connKB  = 25
)
fmt.Printf("在线 %.0f 万 × %d KB=%.1f GB；HTTP 30 秒轮询=%.0f 次/秒\n",
	float64(online)/1e4, connKB, float64(online)*connKB/1e6, float64(devices)/30)
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
在线 80 万 × 25 KB=20.0 GB；HTTP 30 秒轮询=66667 次/秒
```

**代价**：

- MQTT 长连接要维护会话、心跳、重连和 ACL；25 KB/连接不是白来的，80 万并发就是 20 GB 内存，扩容按连接数而不是按消息量。
- CoAP 在 NB-IoT 上更省电，但 NAT 绑定、DTLS、Observe 续订都要自己做；团队 30 人，没有余力维护第二套接入语义，所以只给 5% 的电池设备留 CoAP 旁路。
- MQTT 5.0 的会话过期、原因码、共享订阅等特性要客户端支持；老设备只支持 3.1.1，协议版本碎片会长期存在，接入层必须同时兼容。协议与海量连接的机制见 [43.11 MQTT 与海量连接](../../L4-组件与技术/43-消息队列/43.11-MQTT与海量连接.md)。

### 取舍二：离线消息存 broker 还是存端侧

| 备选 | 离线 7 天存储 | 指令可达 | 端侧要求 | 结论 |
|---|---|---|---|---|
| broker 持久会话全量 | 200 万 × 1000 条/日 × 7 天 × 1 KB ≈ **14 TB**（3 副本约 43 TB） | 最好 | 无 | ❌ 存储先爆 |
| 端侧 WAL，broker 不排队 | 0 | 差（离线指令丢） | 32 MB WAL | 只适合纯上报设备 |
| **混合**（所选） | broker 只留 24 小时/100 条指令 ≈ **205 GB**（3 副本 614 GB） | 在线 5 秒内，离线指令过期 | 32 MB WAL 存 7 天遥测 | ✅ |

关键在于**谁产生消息**：

- 遥测是设备产生的，断网 7 天也必须补上；200 万设备 × 7.2 MB ≈ **14 TB** 端侧存储，分摊在设备上，平台不用为它付存储账单；放 broker 上就是灾难。
- 指令是服务端产生的，通常有时效性；离线 24 小时还没执行的开关指令，恢复后也不该盲目执行。broker 只保留 100 条/设备、24 小时，过期即丢，由设备重连后拉一次“影子状态”对齐。

端侧 WAL 的账：

| 项 | 计算 | 结果 |
|---|---|---|
| 7 天原始数据 | 1000 条/日 × 7 天 × 1 KB | **7.2 MB** |
| 4 倍余量（索引、对齐、坏块） | 7.2 MB × 4 | **29 MB** |
| 分区大小 | 向上取整 | **32 MB** |

**代价**：离线指令会过期，设备恢复后不能假设“把积压指令全执行一遍”；必须用设备影子/物模型做状态对齐，否则会出现“关机指令迟到 3 天，设备一上线就关机”的事故。设备影子见 [69.2 设备影子与物模型](../../L4-组件与技术/69-物联网/69.2-设备影子与物模型.md)。

### 取舍三：断网续传用全量重传、逐条 ACK 还是水位 + 分段重放

| 备选 | 重复量 | ACK 成本 | 端侧存储 | 结论 |
|---|---|---|---|---|
| 全量重传 7 天 | 7000 条/设备，200 万设备约 **14 TB** | 低 | 不需要 | ❌ 流量与时间都不可接受 |
| 逐条 ACK | 0 | 峰值 **10 万 ACK/秒** | 小 | ❌ ACK 放大 50 倍 |
| **水位 + 分段重放**（所选） | 最多 50 条/次重连 | 批量 ACK **2000 次/秒** | 32 MB WAL | ✅ 重复率约 0.3% |

协议只需要四个字段：

```text
hello { device_id, wal_start, acked_seq, last_seq }
resume { resume_seq }          // 服务端告诉设备从哪开始重放
data  { device_id, seq, payload }  // seq 单调递增
ack   { acked_seq }            // 每 50 条或每 5 秒批量确认
```

设备侧 WAL 追加写，`acked_seq` 单独存；重连时从 `max(acked_seq, resume_seq)` 开始重放。服务端用 `(device_id, seq)` 唯一键去重，重复上报最多是“最后一批未确认的 50 条”，按本案例的批量与故障设定估算约 **0.3%**。

**代价**：

- 多了一套 WAL 与水位，端侧代码复杂度上升；坏块、擦写寿命、断电丢最后一批都要处理。
- 批量 ACK 意味着崩溃时最多重放 50 条；去重键必须常驻，不能只靠内存。
- 重连本身是第二次故障：80 万设备断网恢复，70% 在 5 分钟内回来就是 **1867 次/秒**，已经接近 broker 2000 次/秒的握手上限；100% 在 5 分钟内回来就是 **2667 次/秒**，直接打穿。必须加 0–600 秒抖动，把 70% 场景压到 **933 次/秒**。

```go
// 重连风暴：70% 设备在 5 分钟内回来，对比 10 分钟抖动。
const (
	online   = 800_000
	window   = 300
	jitter   = 600
	brokerHS = 2000
)
fmt.Printf("5 分钟窗口：70%%=%.0f 次/秒，100%%=%.0f 次/秒，握手上限 %d/秒\n",
	online*0.7/window, float64(online)/window, brokerHS)
fmt.Printf("0–600 秒抖动：70%%=%.0f 次/秒，100%%=%.0f 次/秒\n",
	online*0.7/jitter, float64(online)/jitter)
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
5 分钟窗口：70%=1867 次/秒，100%=2667 次/秒，握手上限 2000/秒
0–600 秒抖动：70%=933 次/秒，100%=1333 次/秒
```

## 失败模式：这套组合最可能怎么坏

| 失败模式 | 触发条件 | 发现方式 | 退路 |
|---|---|---|---|
| **重连风暴** | 区域断网恢复、固件升级后集中上线 | broker 握手 QPS、TLS CPU | 指数退避 + 0–600 秒抖动 + 接入限流 |
| **离线队列溢出** | 设备 7 天未上线、指令堆积 | 队列深度、过期指令数 | 丢最旧指令，重连后拉影子状态 |
| **重复上报** | ACK 丢失、重放最后一批 | 唯一键冲突率 | `(device_id, seq)` 去重，保留 7 天 |
| **乱序覆盖** | 用设备时间戳排序、多链路并发 | 影子状态回退 | 用 `seq` 排序，服务端统一赋时间 |
| **WAL 写坏** | 断电、擦写寿命、坏块 | 设备自检、补传失败率 | 双分区 + 校验和，坏块隔离 |
| **OTA 中断变砖** | 升级中断电、包校验失败 | 升级成功率、回滚率 | A/B 分区 + 断点续传，见 [69.5 固件升级](../../L4-组件与技术/69-物联网/69.5-固件升级-OTA.md) |
| **协议版本碎片** | 老设备只支持 MQTT 3.1.1 | 接入失败率 | 接入层双协议兼容 + 能力协商 |

## 演进：三波，不一次到位

| 波 | 内容 | 退出标准 |
|---|---|---|
| W1（0–4 个月） | MQTT + clean session=true + 直写；只做在线设备 | 10 万设备；在线指令 <5 秒；断网数据可丢（明确接受） |
| W2（4–10 个月） | 持久会话 + 端侧 WAL + `acked_seq` 批量确认 | 100 万设备；断网 7 天可续传；重复率 <1% |
| W3（10–16 个月） | broker 只留指令 + 重连抖动 + OTA 灰度 + CoAP 旁路 | 200 万设备；峰值 10 万条/秒；重连不超 broker 上限 |

## 复盘：如果重来，改哪一处

> 最该改的是**先算“离线存哪里”，再选协议**。本例早期把 7 天离线队列全放 broker，200 万设备 × 1000 条/日 × 7 天 × 1 KB ≈ 14 TB，3 副本约 43 TB；broker 磁盘先爆，协议选型根本还没轮到。正确顺序是：先算端侧能存多少、断网多久、消息谁产生，再决定 broker 只保留指令、端侧保留遥测。

## 反模式

| 反模式 | 后果 |
|---|---|
| 所有设备 HTTP 轮询 | 6.67 万 QPS、133 MB/s，服务端与电池都扛不住 |
| `clean session=true` 却承诺离线消息 | 重连后消息全丢，业务以为“已送达” |
| broker 存 7 天全量遥测 | 14 TB × 3 副本，磁盘先于连接爆 |
| 逐条 ACK | 10 万 ACK/秒，ACK 放大 50 倍 |
| 重连不做抖动 | 断网恢复瞬间握手打满，二次雪崩 |
| 用设备时间戳排序 | 时钟漂移导致旧数据覆盖新状态 |
| 断网后全量重传 | 14 TB 流量，恢复时间以天计 |
| OTA 没有 A/B 分区 | 升级中断直接变砖，只能上门换机 |

## 自检

**Q1** 为什么 200 万台设备不能全用 HTTP 轮询？

▸ 答案：200 万台每 30 秒轮询一次就是 6.67 万 QPS、约 133 MB/s 下行，服务端连接与带宽成本高，设备电池也扛不住；MQTT 300 秒心跳只有 6667 次/秒，是轮询的 1/10，还能原生下行。

**Q2** 为什么 broker 只保留 24 小时/100 条指令，而不是 7 天全量？

▸ 答案：7 天全量遥测是 14 TB（3 副本约 43 TB），存储成本不可接受；遥测由设备产生，放端侧 WAL 只需 32 MB/设备。指令有时效性，离线 24 小时还没执行的指令恢复后也不该盲目执行，应该用影子状态对齐。

**Q3** 水位 + 分段重放为什么比逐条 ACK 好？

▸ 答案：逐条 ACK 在峰值 10 万条/秒时就是 10 万 ACK/秒，ACK 放大 50 倍；批量每 50 条 ACK 只需 2000 次/秒。代价是崩溃时最多重放 50 条，用 `(device_id, seq)` 唯一键去重，重复率约 0.3%，远低于 1% 的约束。

**Q4** 断网恢复时为什么要加 0–600 秒抖动？

▸ 答案：80 万设备断网恢复，70% 在 5 分钟内回来就是 1867 次/秒，已经接近 broker 2000 次/秒的握手上限；100% 回来是 2667 次/秒，直接打穿。抖动到 10 分钟把 70% 场景压到 933 次/秒，给 broker 留出余量。

**Q5** 这套方案最脆弱的环节是什么？

▸ 答案：**重连与 WAL 的配合**。设备本地 WAL 保证不丢，但重连瞬间的握手风暴、批量 ACK 的重复窗口、坏块导致的补传失败会同时出现；任何一处处理不好，都会表现为“数据没丢但传不上来”。所以重连限流、去重键、WAL 自检要一起设计。
