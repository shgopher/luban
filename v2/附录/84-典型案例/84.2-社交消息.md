# 84.2 社交消息：扩散模型与多端一致的取舍

## 一句话

> 社交消息的难点不是“把消息发出去”，而是**在写放大、同步成本、已读精度三者之间分配预算**——本例的答案是：**2000 人以下写扩散、以上读扩散 + 每会话 seq 与用户变更 seq 双游标 + 单聊水位/群聊人数聚合**，代价是两套游标、7 天变更日志，以及群已读永远查不到“具体是谁”。

**数字口径**：本节是**合成案例**（DAU、消息量、比例均为构造值，用来说明取舍关系），不是任何一家公司的真实数据。机制不在这里重讲：可靠投递见 [66.2 消息可靠投递与离线](../../L4-组件与技术/66-即时通信与音视频/66.2-消息可靠投递与离线.md)，多端同步见 [66.3 多端同步](../../L4-组件与技术/66-即时通信与音视频/66.3-多端同步.md)，群扩散见 [66.5 群聊与消息扩散](../../L4-组件与技术/66-即时通信与音视频/66.5-群聊与消息扩散.md)。

## 规模前提卡

| 项 | 值 | 说明 |
|---|---|---|
| DAU | 1200 万 | 社交消息的主用户盘 |
| 峰值长连接 | 350 万 | 约 29% 的 DAU 同时在线 |
| 日消息量 | 6 亿条 | 人均 50 条/日 |
| 峰值消息速率 | **2.4 万条/秒** | 均值约 6944 条/秒，峰值是均值的 3.5 倍 |
| 设备数 | 2.3 台/用户 | 手机 / 平板 / 桌面 |
| 单设备会话数 | 200 个 | 同步游标的规模前提 |
| 群数量 | 80 万个 | 其中 **2000 人以上 1200 个（0.15%）** |
| 大群消息占比 | **18%** | 0.15% 的群贡献了近 1/5 的群消息 |
| 团队 | 45 人 | 长连接、消息、同步、存储各一组 |
| 硬约束 | 不丢消息；多端最终一致；单聊已读准确；群已读人数误差 ≤1%；单聊 P99 < 200 ms、大群 P99 < 500 ms | 排序：不丢 > 可用 > 已读精度 |

## 三个关键取舍

### 取舍一：群消息扩散到哪一层

| 备选 | 每条消息写/投递次数 | 读放大 | 大群延迟 | 结论 |
|---|---|---|---|---|
| 全写扩散 | 1 + 在线成员 × 设备数 + 离线成员 | 1 次读自己的收件箱 | 低 | 只适合 ≤2000 人的群 |
| 全读扩散 | 1（群时间线） | 每次补齐 = 有未读的会话数 G | 中 | 超大群/频道；离线红点要额外水位 |
| **分级混合** | 小群写、大群只存时间线 | 小群 1 次、大群按群拉 | 大群补拉 P99 约 **1.2 s** | ✅ 本例 |

选择的不是“写扩散好还是读扩散好”，而是**一条按成员数切换的规则**：≤2000 人写扩散，>2000 人读扩散 + 只推“有新消息”，离线成员只记 `conv_seq` 水位，不物化收件箱。边界不是产品经理拍的，是容量算出来的：CPU 上界约 `0.4 / (10 条/秒 × 8.3 µs) ≈ 4800` 人；再叠加存储裁剪与产品语义，保守取 **2000**。

写放大的账可以逐项算：

```go
// 2000 人群，在线 50%，人均 2.3 台设备，群消息 10 条/秒。
const (
	members = 2000
	online  = 0.5
	devices = 2.3
	rate    = 10
	cmdUs   = 8.3 // 单条 Redis 写命令实测成本，来自 66.5
)
writes := 1 + members*online*devices + members*(1-online)
fmt.Printf("写放大=%.0f 次/条，%.0f 次/秒，占单节点 %.1f%%\n",
	writes, writes*rate, writes*rate/(1e6/cmdUs)*100)
```

真实输出（本机 `go1.27.1 darwin/arm64`，按 66.5 的 8.3 µs/命令折算）：

```text
写放大=3301 次/条，33010 次/秒，占单节点 27.4%
```

**代价**：

- 两条代码路径。小群写收件箱、大群写游标，发布时要同时回归；群成员跨过 2000 时还要做一次“收件箱 → 游标”的迁移。
- 1200 个大群只占群数的 0.15%，却贡献 18% 的群消息；峰值只要有 1% 的大群同时活跃（12 个群、每个 10 条/秒），就是 **39.6 万次写/秒，约 3.3 个节点**。大群不能按“少数群体”对待。
- 大群离线补拉不是免费：只推“有新消息”意味着用户点开时要现拉，补拉 P99 约 1.2 秒；这个延迟必须写进产品预期，而不是假装它不存在。

### 取舍二：多端同步用一条游标还是两条

| 备选 | 设备存什么 | 一次同步读什么 | 新设备/换机 | 代价 |
|---|---|---|---|---|
| 全局 `user_seq` 单游标 | 1 个 64 位游标 | 用户变更流水 | 从流水重放 | 单会话内难判空洞；全局计数器是写热点 |
| 每会话 `conv_seq` | 200 个会话游标 | 逐个会话查 | 200 次查询 | 不知道“哪些会话变了” |
| **双序列**（所选） | 每会话游标 + 1 个用户变更游标 | 先读变更流水，再按会话补洞 | 全量同步兜底 | 两套计数器、墓碑、7 天日志 |

双序列的分工只有一句话：**`user_change_seq` 回答“哪些会话变了”，`conv_seq` 回答“这个会话里缺哪几条”**。只有一条全局序列，设备能知道“有新东西”，但不知道新在哪个会话；只有每会话序列，设备得把 200 个会话全查一遍才知道哪里变了。

代价可以用数字说清：

| 项 | 计算 | 结果 |
|---|---|---|
| 设备游标存储 | 2760 万设备 × (200 × 8 B + 8 B) | **44.4 GB** |
| 变更日志 | 7 亿事件/日 × 96 B × 7 天 | **69.1 GB/日，7 天 483.8 GB** |
| 单设备全量同步 | 200 会话 × 50 条 × 1 KB | **9.8 MB，30 Mbps 约 2.6 秒** |
| 全量同步频率 | 游标超过 7 天未更新 | 约 1% 设备/周走全量 |

```go
// 游标与全量同步的账：设备数、单设备游标、全量同步体积。
devices := 12_000_000 * 2.3
cursor := 200*8 + 8
fullMB := float64(200*50*1) / 1024
fmt.Printf("设备=%.0f 万，游标=%.1f GB，全量同步=%.1f MB（30 Mbps 约 %.1f 秒）\n",
	devices/1e4, devices*float64(cursor)/1e9, fullMB, fullMB*8/30)
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
设备=2760 万，游标=44.4 GB，全量同步=9.8 MB（30 Mbps 约 2.6 秒）
```

**代价**：变更日志只保留 7 天。超过 7 天没上线的设备，登录时必须走全量同步；全量同步不是“异常路径”，而是产品必须接受的常规路径。若把日志保留拉到 30 天，存储从 484 GB 涨到 2.1 TB——这是“换机体验”和“存储成本”的直接对价。

### 取舍三：已读回执精确到人还是只给人数

| 备选 | 单聊 | 群聊 | 单条消息成本 | 结论 |
|---|---|---|---|---|
| 逐条 ACK + 逐人已读 | 精确 | 精确到人 | 2000 人群约 2000 条记录/消息 | ❌ 群聊写放大不可接受 |
| 会话级水位 | 精确 | 只能表示“读到哪” | 1 个整数/用户/会话 | 单聊够用，群聊不够 |
| **单聊水位 + 群已读 bitmap** | 精确 | 精确人数，不知道是谁 | **250 B/条**（2000 人） | ✅ 本例 |

单聊只有两个参与者，“已读到哪条”一个水位就够；群聊要回答“多少人读了”，但不能为此给 2000 人每人写一条已读记录。选择用 **bitmap** 记录每条消息的已读成员：2000 人 = 2000 bit = **250 B/条**，1000 条消息 = **244 KB/群**，1200 个活跃群约 **300 MB**。人数精确，但查不到“谁读了”——这就是代价。

```go
// 群已读 bitmap：2000 人一条消息 250 B，1000 条消息约 244 KB。
fmt.Printf("单条 bitmap=%d B，1000 条=%d KB\n", 2000/8, 2000/8*1000/1024)
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
单条 bitmap=250 B，1000 条=244 KB
```

**代价**：

- 群已读只对“人数”负责，不对“人名”负责；产品上的“谁已读”在群聊里做不了，只能做“已读人数”。
- bitmap 要按消息保留，不能只留最新一条；保留 30 天意味着 30 天内的群消息都要带 bitmap，存储按消息量线性增长。
- 重复已读、取消已读、多端已读要合并成同一个 bit；去重逻辑错了，人数会虚高。幂等与去重见 [25.4 幂等设计与去重](../../L1-分布式原理/25-并发、冲突与幂等/25.4-幂等设计与去重.md)。

## 失败模式：这套组合最可能怎么坏

| 失败模式 | 触发条件 | 发现方式 | 退路 |
|---|---|---|---|
| **大群扩散风暴** | 多个 2000+ 人群同时活跃，写扩散未切读 | Redis CPU、扇出 P99 突增 | 按群开关切读扩散，降级为“只推有新消息” |
| **游标回退/跳号** | 设备本地游标被清、版本回滚 | 重复消息、缺消息告警 | 服务端按 `conv_seq` 补洞，客户端幂等应用 |
| **变更日志过期** | 设备 7 天未上线 | 全量同步比例上升 | 走全量同步；不要尝试从过期日志“猜” |
| **已读人数虚高** | 重复上报、多端重复写 bit | 已读人数 > 群成员数 | 以成员列表做掩码，写入前校验 |
| **离线补拉过大** | 大群长期未打开、一次拉 1000+ 条 | 首屏 P99 上升、流量突增 | 分页 + 首屏只拉最近 50 条，其余按需 |
| **重连惊群** | 网络恢复、客户端集中重连 | 网关握手 QPS 打满 | 指数退避 + 抖动，见 [35.5 超时、重试与退避](../../L3-质量属性/35-可用性/35.5-超时重试与退避.md) |

## 演进：三波，不一次到位

| 波 | 内容 | 退出标准 |
|---|---|---|
| W1（0–4 个月） | 单聊 + 500 人群写扩散；单设备单游标 | 消息不丢；单聊 P99 < 200 ms |
| W2（4–10 个月） | 群上限提到 2000；双序列；多端同步 | 3 端游标一致；回退/跳号 0；全量同步 < 3 秒 |
| W3（10–16 个月） | >2000 人读扩散；群已读 bitmap；大群灰度 | 大群 P99 < 500 ms；群已读误差 < 1%；扩散风暴可一键切读 |

## 复盘：如果重来，改哪一处

> 最该改的不是扩散算法，是**先做游标、再做多端推送**。本例早期把“多端一致”实现成“每次登录全量拉”，350 万连接在早高峰集中重连时，登录接口和消息库一起被打满；后来补双序列，等于在高速公路上换轮胎。正确顺序是：先把 `conv_seq` / `user_change_seq` 和全量兜底做进协议，再谈实时推送。

## 反模式

| 反模式 | 后果 |
|---|---|
| 所有群一律写扩散 | 大群一条消息几千次写，峰值直接打穿单分片 |
| 只用一条全局序列 | 设备不知道哪个会话变了，只能全量扫 |
| 变更日志只留 1 天 | 换机/久未上线全部走全量，登录风暴 |
| 群已读逐人存 | 2000 人群每条消息 2000 条记录，写放大不可接受 |
| 已读 bitmap 不做成员掩码 | 退群/踢人后人数虚高，甚至超过群人数 |
| 大群离线也物化收件箱 | 写放大回到 N，读扩散白选 |
| 重连不做抖动 | 网络恢复瞬间握手打满，二次雪崩 |

## 自检

**Q1** 为什么群扩散边界是 2000 人，而不是 500 或 1 万？

▸ 答案：它是容量算出来的，不是产品拍的。按 66.5 的实测，单条写命令约 8.3 µs，10 条/秒的活跃群在 CPU 上的上界约 4800 人；再叠加存储裁剪（保留条数越多，单条成本从 17.4 B 涨到 78.8 B）和产品语义，保守取 2000。500 人偏保守、1 万人会先撞上扇出延迟。

**Q2** 双序列里的 `user_change_seq` 和 `conv_seq` 各解决什么问题？

▸ 答案：`user_change_seq` 解决“哪些会话变了”，让设备不用扫描全部会话；`conv_seq` 解决“这个会话里缺哪几条”，让补拉能定位空洞。只有前者不知道补哪里，只有后者不知道哪里变了。

**Q3** 群已读为什么不用逐人 ACK？

▸ 答案：2000 人群一条消息就是 2000 条已读记录，10 条/秒就是 2 万次写/秒/群，写放大和存储都不可接受。bitmap 用 250 B 换“人数精确”，代价是查不到“谁读了”；群聊产品要接受这个语义降级。

**Q4** 变更日志保留 7 天，超过 7 天没上线的设备怎么办？

▸ 答案：走全量同步，不能从过期日志里“猜”。全量同步约 9.8 MB、30 Mbps 下 2.6 秒，是产品必须接受的常规路径；把日志保留拉到 30 天，存储会从 484 GB 涨到约 2.1 TB，这是直接对价。

**Q5** 这套方案最脆弱的环节是什么？

▸ 答案：**大群扩散边界**。1200 个大群只占 0.15%，却贡献 18% 的消息；一旦多个大群同时活跃而切换开关没生效，写扩散会在几分钟内打满 Redis。所以边界必须有按群开关、监控和回切，而不是写死在代码里。
