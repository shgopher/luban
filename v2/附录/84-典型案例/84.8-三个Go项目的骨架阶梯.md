# 84.8 三个 Go 项目的骨架阶梯：fastgo → iam → onex

## 一句话

> 三个仓库共用**一套横向的 clean 分层**（handler/server → biz/service → store → model，接口在边界、依赖只朝内），差异全在**纵向**：fastgo 1 个进程、iam 4 个服务 + CLI、onex 16 个服务/CLI。"阶梯"量的是纵向拆分与服务化能力，不是横向整洁度——**单体不是 clean 架构的反面，只是纵向 = 1 的部署状态**：同一套分层既跑在一个单体里，也在每个微服务里各复制一份。跳过中间一级直接抄 onex，拿到的不是能力，是 112 个直接依赖、19 个 k8s.io 模块与 54.71% 的生成代码维护账单。

**来源**：三个仓库本地全量实测（2026-11-21，本机 macOS/arm64，命令见文末「怎么复核」）。三者出自同一作者（孔令飞）的连续三代项目：`github.com/shgopher/fastgo`、`github.com/shgopher/iam`、`github.com/shgopher/onex`，因此目录与包名同构——差异是设计选择，不是噪音。

## 先看三组数字

口径统一为「文件首行是 `// Code generated` 即生成物」——这比按文件名（`*.gen.go` 等）更严，能把 `pkg/generated/`、`*.pb.go`、`mock_*.go`、`wire_gen.go` 都算进去（两边口径的差值正好说明"生成物有多少藏在文件名之外"）。

| 指标 | fastgo（教学最小集） | iam（企业完整版） | onex（云原生平台） |
|---|---|---|---|
| Go 总行数（含测试/生成） | 3,086 | 30,882 | 120,577 |
| **手写行数**（排测试 + 生成） | **2,949** | **25,488** | **51,379** |
| 生成代码 文件 / 行数 | 2 / 56 | 4 / 1,170 | **167 / 65,972** |
| 生成代码占 Go 行数 | 1.81% | 3.79% | **54.71%** |
| 测试文件 / 行数 | 1 / 81 | 33 / 4,224 | 25 / 3,226 |
| Go 文件总数 | 49 | 339 | 883 |
| 非测试非生成包数 | 23 | 101 | 309 |
| `cmd/` 下一级目录 | 1（1 个二进制） | 10（5 服务/CLI + 5 生成工具） | 29（16 服务/CLI + 6 工具 + 7 占位） |
| `internal/` / `pkg/` 一级目录 | 2 / 5 | 6 / 8 | 16 / 21 |
| **直接依赖**（不含 indirect） | **15** | **65** | **112** |
| `k8s.io/*` 模块数 | 0 | 1（klog） | **19**（另有 replace 12 条） |
| `docs/` 下 Markdown | 1 | 89 | 76 |
| `configs/` 文件数 | 3 | 22 | 17 |
| `.golangci.yaml` 启用 linter | 无配置 | 70 条（69 唯一） | 67 条 |
| `Makefile` 目标数（去 `.PHONY`） | 无（`build.sh`） | 53 行 / 27 个 | 63 行 / 31 个 |
| CI workflow 文件 | 0 | 3 | 0 |
| `go.mod` 版本指令 | 1.24.0 | 1.21.4 | 1.22.0 |

三行最关键的数：**手写代码 2,949 → 25,488 → 51,379**、**直接依赖 15 → 65 → 112**、**生成代码占比 1.81% → 3.79% → 54.71%**。前两行说明工程面在扩大，第三行说明 onex 的复杂度有一半不写在 `.go` 里，而在生成器与依赖树里。

## 两条轴：横向分层不变，纵向拆分升级

先分清两条正交的轴，否则"阶梯"会被误读成"越往后越整洁"：

| 轴 | 三仓库的差异 | 不变的常量 | 判据 |
|---|---|---|---|
| **横向（层）** | 命名不同：fastgo `handler → biz → store → model`；iam `controller → service → store → model`；onex `server → service → biz → store → model` | **依赖只朝内、接口在边界、模型不跨界** | 业务核心能不能脱库 / 脱 HTTP 跑测试 |
| **纵向（服务）** | 1 → 4 服务 + CLI → 16 服务/CLI（另有 6 工具、7 占位） | 无——这一轴就是"拆几份" | 一次业务变更能不能只发一个进程 |

所以三个项目的真实关系是：

| 项目 | 横向（进程内） | 纵向（进程间） | clean 架构的状态 |
|---|---|---|---|
| fastgo | 一套四层，依赖朝内 | 1 个进程 | **单体** = 纵向为 1 的 clean 架构 |
| iam | 每个业务服务各一套（controller/service/store/model） | 4 服务 + 1 CLI，靠 HTTP / gRPC / Redis / Kafka 通信 | clean 架构 × 4 + 跨进程契约 |
| onex | usercenter / gateway / cacheserver 各一套；apiserver 用 K8s 的 registry/storage，controller 用声明式 | 16 服务/CLI，靠 K8s API / CRD 编排 | clean 架构 × N + 平台层 |

> 🔑 **顺序不能反**：横向分层让"拆"变便宜（store 接口换成 RPC 客户端即可，因为依赖倒置已经做完了）；纵向拆分不会自动让每个服务变整洁，拆得越快，越容易得到 N 个大泥球。机制与证据见 [26.3 整洁架构](../../L2-架构风格/26-分层与依赖/26.3-整洁架构.md) 的「横向与纵向」小节。

因此下文的"阶梯"只度量纵向与服务化能力（进程数、应用框架、生成器、K8s 生态），**不是整洁程度的阶梯**：fastgo 的横向并不比 onex 差，它只是纵向只有一份、没有多进程与平台化的负担。iam/onex 里也不是每个组件都套四层——pump 是管道、watcher 是监听器、controller-manager 是声明式控制器，它们守的是"接口在边界、依赖朝内"这条底线，而不是"每层必须叫 controller/service/store"。

## 阶梯的判据：每一级只多买一样东西

| 级别 | 新增的能力 | 多付的代价 | 什么时候值得升 |
|---|---|---|---|
| **fastgo** | 最小闭环：`cmd/options/app` 装配、四层分层（handler/biz/store/model）、三字段错误契约、slog、JWT、参数校验与 DTO 转换 | 几乎没有工程约束：1 个测试、无 lint、无 Makefile | 单人/小团队的第一个后台服务，先跑通闭环 |
| **iam** | 多组件工程化：`pkg/app` 应用框架、`pkg/shutdown` 退出管理、多实例日志、viper 多配置、错误码生成器、mock 生成、70 条 linter、89 篇文档、4,224 行测试 | 65 个直接依赖、2.5 万行手写、5 个二进制要一起部署运维 | 团队 ≥3 人、进程 ≥2 个、要对外承诺 API 与错误码 |
| **onex** | 声明式与生态：K8s 风格 apiserver/controller/informer、CRD 生命周期、i18n message ID、`gen-*` 生成器、29 个 cmd 目录 | 112 个直接依赖、19 个 k8s.io 模块、5.1 万行手写 + 6.6 万行生成（54.71%）、一整套 K8s 概念 | 要做平台（资源编排/控制器），且团队已有 K8s 经验 |

> 🔑 **判据不是"代码行数"，是"你要解决的失败模式"**：一个请求打不通 → fastgo 的闭环够；五个二进制退出顺序互相踩 → 需要 iam 的框架；资源要"声明期望状态、控制器收敛" → 才轮到 onex 的声明式。

## 每一级值得抄什么，不值得抄什么

| 级别 | 值得抄（精华） | 抄之前要改（坑） |
|---|---|---|
| **fastgo** | `cmd/fg-apiserver/app` 的三段式（options → config → server）；`internal/pkg/errorsx` 的 `ErrorX{Code,Reason,Message}` + `FromError`；`core.WriteResponse` 单一渲染点；middleware 链（recovery → cors → requestID → authn）；`contextx` 用空结构体做 key | 工程规范几乎为零（1 个测试、无 lint、无 CI）；`FromError` 把 `err.Error()` 塞进 `Message` 会泄露内部信息——换成固定文案（见 [40.7 错误码体系](../../L3-质量属性/40-可维护性/40.7-错误码体系.md)） |
| **iam** | `pkg/app` 七步模板 + `CliOptions` 三段式；`pkg/shutdown` 的 Manager/Callback 抽象；`internal/pkg/code` 的段位编号 + `codegen` 码表生成；`pkg/log` 多实例；`scripts/make-rules/` 把 Makefile 拆成 11 个文件；`tools/codegen` 的 AST 生成 | 回调式退出的三个坑（并行无序、无超时、`os.Exit` 跳过 defer，见 [55.8 应用框架与启动顺序](../../L5-工程效能/55-发布与回滚/55.8-应用框架与启动顺序.md)）；8 个中间件 + gRPC + Redis + Kafka 的运维面，业务后台不需要 |
| **onex** | `pkg/app` 的 `HealthCheckFunc` 与 `WithWatchConfig`；`pkg/i18n` 的 message ID + `locales`（en/zh 两份 yaml）；`internal/controller` 的声明式收敛结构；`cmd/gen-*` 与 29 处 `go:generate`；linter 逐条决策（67 开、40 注释） | 整套 K8s 依赖树（112 个直接依赖、19 个 k8s.io 模块、65,972 行生成代码）是"平台税"，业务服务抄了就是负债；`cmd/onex-allinone/main.go` 只有一句 `Not yet implemented`——**未完成的占位不要当范例**；大量 `pkg/apis` 生成物不可手改 |

## 升一级的触发条件（判断表）

| 你现在的症状 | 该不该升 | 升到 |
|---|---|---|
| 1 个二进制、1 个数据库、接口 < 30 个 | 不升 | fastgo 风格够用 |
| 进程变成 2–5 个（api/worker/console），启动脚本开始互相复制 | 升一级 | iam 风格：`pkg/app` + 显式退出注册 |
| 错误码开始被多端消费（App/小程序/开放平台） | 升一级 | 错误码段位 + 码表生成（iam 的 `codegen`） |
| 同一份规范要出现在 3 处以上（码表、配置示例、API 文档） | 升一级 | 生成器流水线（[52.6 代码生成](../../L5-工程效能/52-持续集成/52.6-代码生成.md)） |
| 需求是"给资源声明期望状态，系统自己收敛" | 升两级 | onex 风格：CRD + controller + informer |
| 只是"想用大厂同款架构" | 不升 | 先把 fastgo 的测试与退出补齐 |

## 怎么复核（可复现命令）

```bash
# 生成物：文件首行是 // Code generated（go generate 的通用约定）
grep -rl '^// Code generated' --include='*.go' <repo> | xargs wc -l | tail -1
# 总行数 / 测试行数
find <repo> -name '*.go' -print0 | xargs -0 wc -l | tail -1
find <repo> -name '*_test.go' -print0 | xargs -0 wc -l | tail -1
# 二进制/命令数；直接依赖数（不含 indirect）
ls -d <repo>/cmd/*/ | wc -l
grep -E '^\s+[a-zA-Z0-9./-]+ v' <repo>/go.mod | grep -v '// indirect' | wc -l
```

实测口径说明：三仓本地全量扫描、不联网、不 build；「手写行数 = 总行数 − 测试行数 − 生成物行数」。之所以用文件头而不是文件名：`pkg/generated/`、`*.pb.go`、`mock_*.go`、`wire_gen.go` 在 onex 合计 6 万行以上，只按 `*.gen.go` 之类的文件名会漏掉大半（口径 A 只能数出 36,799 行、30.52%）。

## 反模式

| 反模式 | 后果 |
|---|---|
| 把 onex 整仓当模板克隆到业务服务 | 112 个直接依赖、65,972 行生成代码（54.71%），构建从秒级变分钟级，没人能全读懂 |
| 为了"像大厂"一次上 70 个 linter | 历史代码全红，最后被迫 `nolint` 满仓，门禁形同虚设 |
| 抄目录结构但不抄测试与生成器 | 骨架有了，纪律没有：生成物手改、测试为零 |
| 抄生成物不抄生成命令 | 下次升级 K8s 库，36.8k 行代码无人能重生成 |
| 用 5 个二进制做一个小后台 | 部署、日志、配置、退出全要乘 5，收益为零 |
| 跳过 fastgo 直接读 onex | 看不到"最小闭环"的样子，误以为复杂度是必需品 |
| 按服务数量评价架构水平 | 16 个进程可能是 16 个泥球；横向分层不会因为拆服务自动获得 |
| 以为"整洁架构 = 单体专属"或"微服务 = 自动整洁" | 概念错位：clean 是横向代码结构，单体/微服务是纵向部署形态 |
| 先拆服务、再补分层 | 分布式单体：跨进程事务、联调、发布耦合一个不少 |

## 自检

Q1 为什么说三个仓库是"同一骨架的三个尺寸"，而不是三个独立项目？
▸ 答案：同一作者连续三代，`cmd/<binary>/app` + `internal/{handler,biz,store,model}` + `pkg/` 公共包的布局、`ErrorX`/错误码、cobra+viper 三段式都同构——这是**横向**的 clean 分层；差异集中在"多组件工程化"与"声明式生态"两件事上——这是**纵向**的拆分与服务化能力。横向三代未变，纵向从 1 涨到 16，所以可以按"同一骨架的不同尺寸"对照读。

Q2 依赖数 15 → 65 → 112、生成代码占比 54.71%，这两个数字说明什么？
▸ 答案：能力是借来的：每升一级，更多复杂度从"自己写"变成"依赖别人的约定"（框架、K8s 库、生成器）；onex 超过一半的代码不由人手写，因此抄 onex 必须同时抄它的生成命令与版本锁定，否则维护不了。

Q3 什么时候该从 fastgo 风格升到 iam 风格？给两个可观察的信号。
▸ 答案：① 进程数 ≥2 且启动/退出脚本开始复制粘贴；② 同一份规范要在多处手工同步（错误码表、配置样例、API 文档）。二者出现任一，升级的收益开始大于维护成本。

Q4 iam 的五个二进制里，为什么生成器（gendocs/genman/genyaml 等）也算 `cmd/` 下的命令？
▸ 答案：它们和业务二进制共享同一套构建、版本注入与 Makefile 目标，把"生成"当一等公民；这样生成器随主仓版本演进，避免"生成器漂移"。代价是 `cmd/` 计数要区分工具与业务。

Q5 为什么 onex 的 `onex-allinone`（单二进制跑全部组件）反而没实现？
▸ 答案：单二进制会把组件间的资源隔离、故障隔离、独立升级全部压回一个进程，只适合 demo；平台化的方向是"多二进制 + 声明式编排"，`allinone` 在 onex 里只剩占位，说明连作者也没把它当主线——这是"不要为了省部署而合并组件"的反证。

Q6 如果团队只有 3 人、已有 K8s 集群，该抄哪一级？为什么不是 onex？
▸ 答案：抄 iam 级别的工程化（应用框架、退出、错误码、生成器），业务上不需要 CRD/controller 时不要引入 onex；已有 K8s 只降低"部署"成本，不降低"声明式编程"的建模与调试成本，112 个依赖的账单照样要付。

Q7 有人说"三个项目都是 clean 架构"，对在哪、要限定在哪？
▸ 答案：对的部分：业务服务内部都守同一条依赖规则——接口在边界、依赖朝内、模型不跨界（fastgo `handler/biz/store/model`、iam `controller/service/store/model`、onex `server/service/biz/store/model`），而 fastgo 是这套横向分层只部署 1 份（单体），iam/onex 是它在 4 / 16 个进程里各一份（微服务形态）。要限定的部分：① pump/watcher/controller-manager/onex-apiserver 用管道/监听器/声明式/registry-storage 模式，不套四层，只守"依赖指向内层契约"；② "都是 clean 架构"是横向判断，不等于"都是微服务"，更不等于每个组件都整洁。
