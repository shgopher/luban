                          84.10 第二批零件：能力、引用与可验证的边界

                          一句话

                          84.9 拆的是“框架内部怎么组合”，这一节拆的是“平台边界怎么守住”：按 run 发一张能力票、把模型能自修的错误降级成 observation、大对象只传引用、一个资源只属于一侧存储、把性能陷阱编译成 vet 检查——五件事的共同点是“让错误在最早、最便宜的位置暴露”，而不是靠文档与 review 兜底。

                          为什么还有第二批

                          批次 关注点 典型问题 代表位置
                          84.9 第一批 框架内部：接口、缓存、契约、反馈、准入 换实现要改几处、故障时谁先崩 onexmesh、onexai 的 run 生命周期
                          84.10（本节） 平台边界：凭证、工具、数据、存储、静态检查 越权、泄露、双写、性能悬崖 onexai 的 capability/media/store、onexmesh 的 vet 工具

                          两节不重复：84.9 的零件 5 讲“怎么抢到执行权”，本节零件 5 讲“重跑与暂停怎么安全”；84.9 的零件 6 讲“CLI 怎么变成工具”，本节零件 2 讲“工具出错时模型怎么自修”。

                          零件 1：能力令牌——把长期密钥换成一次 run 的票

                          远端运行时（A2A、CLI 沙箱）要回连平台调用知识库、Skill、Memory。如果给它长期 AK/SK，等于把一个可能被 prompt injection 控制的进程，升级成整个租户的权限。onexai 的做法是一次 run 签一张短票：

                          // internal/agent/capability/token.go:35 —— 票里带身份、scope、收窄标记与委派链
type Claims struct {
	RunID      string   `json:"runId"`
	SessionKey string   `json:"sessionKey"`
	Agent      string   `json:"agent"`
	Subject    string   `json:"subject"`
	Scopes     []string `json:"scopes"`     // namespace 列表，"*" 通配
	ExpiresAt  int64    `json:"expiresAt"`

	SubjectKind string `json:"subjectKind,omitempty"` // 人 vs 服务账号，同名不同身份
	Narrowed    bool   `json:"narrowed,omitempty"`    // true 表示下面的列表是权威
	Skills          []string `json:"skills,omitempty"`
	KnowledgeBases  []string `json:"knowledgeBases,omitempty"`
	CustomCommands  []string `json:"customCommands,omitempty"`

	RootRunID   string `json:"rootRunId,omitempty"` // 委派链顶端
	ParentRunID string `json:"parentRunId,omitempty"`
	Depth       int    `json:"depth,omitempty"`     // 委派了几层
}

                          三个字段值得单独说：

                          字段 表达什么 抄错会怎样
                          Narrowed “收窄为空” vs “没有收窄” 只用空 slice 表达，会把“调试 run 不给任何 skill”误判成“给全部”
                          SubjectKind 同名的人与服务账号是两个主体 只存名字，授权时无法区分“张三”与“张三的机器人”
                          Depth / RootRunID 委派链可设上限、可追踪 不带上，A 调 B 调 C 的链无法限深，也无法归因

                          验签只回答“是不是我签的、过没过期”，故意不细分失败原因：

                          // token.go:24 —— 探针无法区分“伪造”与“过期”
var ErrInvalidToken = errors.New("capability: invalid runtime token")

                          真正有意思的是“票还有效，但 run 已经结束”怎么办：

                          // internal/agent/capability/provider.go:161
func (s *Service) checkActive(ctx context.Context, claims Claims) error {
	run, err := s.runs.GetRun(ctx, claims.RunID)
	if err != nil || run == nil {
		return nil // 查不到：放行（不能因存储丢一行就让所有工具调用失败）
	}
	switch run.State {
	case model.RunStateRunning, model.RunStateInterrupted:
		return nil
	default:
		return ErrRunNotActive // 查得到且已结束：拒绝（凭证活过了它的用途）
	}
}
                          校验 结果 理由
                          签名错 / 过期 401 票本身无效
                          run 不存在 放行 用一次窄窗口的“可能重放”，换“不因存储故障造成全量不可用”
                          run 存在且已结束 拒绝 这是凭证活过用途，必须挡
                          scope 不含工具 namespace 拒绝 票只允许它被签发的范围

                          代价与坑：

                          • HMAC 不是非对称签名：能验签的进程也能签发。多租户 SaaS 应换 Ed25519，把签发权收到一个服务。
                          • 令牌塞了 6 个列表字段，URL/header 会到 1KB 级；网关的 header 上限才是真实约束。
                          • checkActive 的“查不到就放行”是反直觉但正确的取舍，抄的时候最容易被改成“一律拒绝”，然后一次 DB 抖动让所有工具调用不可用。

                          🔑 能力令牌不是用户鉴权：它只回答“这个 run 能调哪些 namespace 的工具”，不回答“这个用户能不能用这个 agent”。两层要分开。

                          零件 2：工具面的三道闸——自愈、去重、搜索

                          模型调用工具时有三种错误，处理方式完全不同：

                          错误 例子 正确动作 错误动作的后果
                          模型能自修 编了一个不存在的工具名 返回可用工具列表，让它重选 整个 run 失败，用户重来
                          历史坏了 持久化的 tool_call 没有 tool_result 告诉模型“这次没执行”，让它重试 provider 直接 400，会话打不开
                          工具真的挂了 超时、连接失败 熔断 / 重试 / 降级 每轮都白等一个超时

                          onexai 把前两类降级成普通文本结果：

                          // internal/agent/pkg/agentbuilder/assemble.go:48 —— 未知工具不致命
func unknownToolResult(names []string) func(ctx context.Context, name, input string) (string, error) {
	return func(_ context.Context, toolName, _ string) (string, error) {
		return fmt.Sprintf("unknown tool %q: it does not exist in this run. "+
			"Available tools: %s. Do not call a tool outside this list; "+
			"answer directly if none applies.", toolName, list), nil
	}
}

                          第二类（悬挂调用）更隐蔽：进程崩在工具执行中，历史里留下 tool_call 却没有 tool_result，多数 provider 会直接拒绝整个请求。修法是补一条“这次没执行”的结果，而不是删记录。

                          工具多起来后，还有两道闸：

                          闸 做法 阈值 / 规则 代价
                          去重 同名工具 first-seen wins 无 后注册的同名工具被静默丢弃，需要日志
                          tool-search 把 MCP 工具折叠成一个检索入口 默认 ≥ 40 个才启用；只隐藏 MCP 工具，内置与“要问人”的工具始终可见 过滤工具列表会让 provider 的 prompt cache 失效

                          ⚠️ tool-search 不是“越早开越省”：它的收益是少传 schema，代价是打断 prompt cache。40 是魔法数，抄的时候应按 schema 字符数 估算，而不是工具个数。

                          零件 3：大对象只传引用

                          一张 3 MiB 的截图，如果以 base64 data URL 进入会话历史，会变成约 4 MiB 的字符串：每一轮对话都从 Redis 读出来、每一轮都发给模型、无法去重、无法鉴权、无法过期。onexai 的 pkg/media 把“图片”统一成一个引用：

                          // pkg/media/ref.go:81 —— 身份 + 元数据，永远不是字节
type Ref struct {
	AssetID   string `json:"asset_id,omitempty"`   // 鉴权与过期的锚点
	ObjectKey string `json:"object_key,omitempty"`
	URL       string `json:"url,omitempty"`
	MimeType  string `json:"mime_type,omitempty"`
	Size      int64  `json:"size,omitempty"`
	Width     int    `json:"width,omitempty"`
	Height    int    `json:"height,omitempty"`
	Name      string `json:"name,omitempty"`
	Source    string `json:"source,omitempty"`
}

                          为了让存量 wire 字段不用改，引用用字符串 scheme 承载：

                          // ref.go:57 —— 老字段是 repeated string，加一个前缀就能上车
const (
	AssetScheme  = "asset:" // 本服务签发的 asset id
	ObjectScheme = "media:" // 配置的 store 里的对象 key
)
                          维度 传字节（data URL） 传引用（Ref）
                          会话体积 3 MiB 图 → 约 4 MiB 字符串 几十字节
                          每轮成本 每轮重读、重发 每轮只在模型边界读一次
                          去重 / 鉴权 / 过期 没有身份，做不了 挂在 AssetID 上
                          兼容存量字段 要改消息结构 字符串前缀，不改 wire
                          失败路径 无 引用可能解析不到，每个消费点都要处理

                          🔑 引用化的代价是“字节不一定可达”：Ref 明确不是“字节可达”的承诺，所以每个消费点都必须有解析失败的分支。省下的带宽与内存，换来的是一条会传染到所有调用方的错误路径。

                          零件 4：双存储归属——一个资源只属于一侧

                          平台同时用 K8s 声明式控制面与 PostgreSQL 时，最危险的不是“用哪个”，而是“两边都写”。onexai 的纪律写在 store 层 README 里，而不是口头约定：

                          侧 资源 写入路径
                          声明式控制面（CRD） agent、agent template、binding、skill、custom command、MCP、knowledge base、prompt、model、webhook、runtime profile/hosting、sandbox template 只走 declclient
                          GORM / PostgreSQL secret、interaction、k8sgpt endpoint、retrieval audit、asset 只走 sqlstore
                          跨侧视图 namespace 只读映射，不建第二张表
                          // internal/agent/model/namespace.go:47 —— 视图不是表
// NamespaceM ... is a view, not a table. The corev1.Namespace object is the only
// source of truth ... There is deliberately no GORM registration or TableName:
// keeping a second row in PostgreSQL is what made the old implementation require
// a reverse syncer and left a write that could succeed in one place and fail in
// the other.

                          这套纪律的价值不在“选型”，在迁移完成后的动作：迁移完的资源删掉旧读路径，而不是“保留以防万一”。代价是：

                          • 跨侧事务不可能，只能接受“迁移中途不一致”的窗口；
                          • 归属会变（项目里同时存在 crd2pg 与 pg2crd 两个方向的迁移工具），所以纪律只能保证“任一时刻只有一个真源”；
                          • 文档会漂移：同一个 Namespaces() 在 README 里被描述成“视图”，在 StandardStore 里又出现“control plane 同步一份行存”的注释——归属规则需要有测试/告警，不能只靠注释。

                          🔑 双存储的判据不是“有没有同步器”，而是“任一资源，能不能指出唯一写入方”。指不出来，就一定会双写。

                          零件 5：可重跑与可暂停——长任务的两个边界

                          长任务有两个绕不开的问题：调度器会重跑（至少一次），人要中途审批（暂停）。两者的答案完全不同。

                          可重跑靠“确定性命名 + 已存在即成功”：

                          // internal/controller/job/cronjob/controller.go:367 —— 名字由计划分钟决定
func jobName(cronJob string, at time.Time) string {
	return fmt.Sprintf("%s-%d", cronJob, at.Unix()/60)
}

// :281 —— 重试到同一分钟，Create 会 AlreadyExists；把它当成功
if err := r.client.Create(ctx, job); err != nil {
	if client.IgnoreAlreadyExists(err) == nil {
		return nil
	}
	...
}

                          迁移/回填同理：用 migrated-from 注解标记“我创建的”，复用生产写路径的转换函数，并且所有工具都带 --dry-run。“重跑安全”不是一句口号，是三个具体动作：确定性 key、幂等错误码、可审阅的 dry-run。

                          可暂停有两种实现，边界完全不同：

                          场景 暂停方式 能否跨重启 代价
                          自己的引擎（eino） checkpoint 持久化 + Claim 原子认领 能，任意 Pod 续跑 需要存储、TTL、恢复时校验工具集
                          别人的 CLI（Claude Code 等） 利用 --permission-prompt-tool，在 CLI 的 tool loop 里阻塞等 HTTP 决议 不能，进程挂了审批就没了 简单，但只适合短时人工审批
                          // internal/agent/runtimecli/approval.go:47 —— 把“等人”伪装成一次阻塞的工具调用
// A CLI agent cannot pause itself: it either runs a tool or refuses it.
// Claude Code offers `--permission-prompt-tool`, an MCP tool it consults exactly
// when it would otherwise prompt; that tool's answer is the decision.
// ...
// The process stays alive for the duration of the decision, so a pause does not
// survive a restart ...

                          🔑 暂停机制要按“谁拥有引擎”选：自己的引擎用持久化断点，别人的引擎用阻塞调用。把后者宣传成“可恢复”，是把进程存活当成持久化。

                          零件 6：把性能陷阱编译成 vet 检查

                          ListOptions{ResourceVersion: "0"} 少了 "0"，List 就从“读 watch 缓存”变成“走 etcd 一致性读”，每次 reconcile 多一次 quorum 往返——代码看起来完全正常，测试也全绿。onexai 为这类“字符串字面量级性能悬崖”写了一个自定义 go vet 分析器：

                          // internal/lint/kubelistcheck/analyzer.go:15
// A List whose ListOptions carry no ResourceVersion is a consistent read:
// the apiserver must ask etcd ... ResourceVersion "0" asks for "any version
// you have" and is answered from the watch cache instead. The two differ only
// by a string literal, so a missing one costs a quorum read per reconcile and
// looks exactly like working code.

                          可迁移的“性能悬崖”清单：

                          必须带的字面量/参数 漏了会怎样
                          K8s List 的 ResourceVersion:"0" 每次 reconcile 一次 etcd quorum 读
                          http.Client 的 Timeout 默认无超时，连接永久挂起
                          DB 调用的 context 请求取消后查询继续跑
                          defer rows.Close() 连接池泄漏
                          gRPC 调用的 WaitForReady(false) 故障时无限排队

                          代价：分析器本身要维护（295 行，另有 94 行测试），误报一次就会被团队绕过；它只能识别 composite literal，rv := "0" 这种间接写法查不到。机制与完整写法见 52.2 静态检查。

                          抄之前要付的账

                          零件 引入成本 什么时候别抄
                          能力令牌 签发/验签、密钥分发、scope 设计 单进程、无不可信子进程
                          工具自愈 要配“未知工具命中率”指标 工具集固定、模型不会编名字
                          大对象引用 存储、解析器、全链路失败分支 对象很小（几 KB）、只读一次
                          双存储归属 一张归属表 + 迁移工具 + 测试 只有一个存储
                          可重跑 确定性 key + 幂等错误码 + dry-run 任务无副作用、可随意重跑
                          阻塞式 HITL 只适合外部 CLI 需要跨重启恢复
                          自定义 vet 分析器维护 + CI 集成 团队没有“性能悬崖”型 API

                          反模式

                          反模式 后果
                          给沙箱进程发长期 AK/SK 一次 prompt injection 拿到整个租户权限
                          用空 slice 表示“收窄为空” 被解释成“没有收窄”，调试 run 拿到全部能力
                          未知工具直接让 run 失败 模型一次口误毁掉整轮任务，且无法自修
                          把 40 个工具当定理、不量 schema tool-search 打断 prompt cache，成本反升
                          图片以 base64 进会话历史 每轮重读重发，无法去重/鉴权/过期
                          两个存储都写、靠同步器对齐 一边成功一边失败，产生无法对账的脏数据
                          迁移完还保留旧读路径 “以防万一”变成永久的双真源
                          把阻塞式 HITL 当可恢复 进程重启，审批与 run 一起消失
                          只靠 review 抓 ResourceVersion 漏一次就是每次 reconcile 一次 quorum 读

                          自检

                          Q1 能力令牌为什么要把“查不到 run”与“run 已结束”分开处理？

                          ▸ 答案：两者的风险不同。查不到 run 可能是存储丢了一行/查询失败，如果因此拒绝所有工具调用，一次存储故障会放大成“所有 run 都不可用”；而查得到且已结束，说明凭证活过了它的用途，是明确的重放风险，必须拒绝。这是“窄窗口重放”与“大面积不可用”之间的取舍。

                          Q2 Narrowed 为什么不能用“空 slice”代替？

                          ▸ 答案：空 slice 有两种含义：调试 run 明确不给任何 skill（收窄为空），以及没有收窄、按 agent 的完整能力走。两者授权结果相反。用 bool 显式区分“列表是否权威”，才能避免把“收窄为空”误判成“未收窄”。

                          Q3 模型调用了一个不存在的工具，为什么不应该让整个 run 失败？

                          ▸ 答案：这是模型自己能修的错误：它编了名字，把可用工具列表返回给它，它通常能改对。让 run 失败会把一次口误升级成任务失败，用户只能重来。代价是掩盖真实的注册缺失，所以要配“未知工具命中率”指标；同时“悬挂 tool_call”要补“未执行”的结果，否则 provider 会 400。

                          Q4 为什么大对象要传引用而不是 base64？

                          ▸ 答案：base64 没有身份，无法去重、鉴权、过期，而且会进入会话历史，每一轮都被重读、重发；3 MiB 的图会变成约 4 MiB 的字符串。引用只有几十字节，字节只在模型边界读一次，鉴权与过期挂在 AssetID 上。代价是每个消费点都要处理“解析不到”的失败。

                          Q5 双存储并存时，为什么“同步器”不是答案？

                          ▸ 答案：同步器只能缩小不一致窗口，不能消除双写：一边成功、一边失败时，仍然需要决定谁是真相。正确做法是划分所有权：每个资源只属于一侧，迁移完成的资源删掉旧读路径；跨侧字段做只读视图。代价是跨侧事务不可能，迁移期要接受不一致窗口。

                          Q6 为什么 jobName 用“计划分钟”而不是“创建时间”？

                          ▸ 答案：reconcile 是至少一次，重跑时创建时间会变，名字就变了，会创建出第二个 Job；用计划分钟做确定性 key，重跑落到同一个名字，Create 返回 AlreadyExists，把它当成功就实现了幂等。代价是同一分钟内两次手动触发会撞名，需要额外的触发 ID 区分。

                          Q7 为什么“阻塞式 HITL”不能宣传成“可恢复”？

                          ▸ 答案：它的暂停依赖 CLI 进程与 broker 进程都活着；进程重启、Pod 驱逐，审批状态就没了，run 也无法续跑。它只适合短时人工审批。真正可恢复的暂停要像 onexai 的 eino 路径那样，把断点持久化，用 Claim 原子认领，并在恢复前校验工具集仍存在。

                          Q8 为什么性能陷阱要用自定义 vet，而不是 code review？

                          ▸ 答案：这类陷阱只差一个字符串字面量（ResourceVersion:"0"、Timeout、context），代码看起来完全正常，测试也不会失败；review 会疲劳且不可重复。AST 分析器把规则变成每次 CI 都执行的检查，成本是一次性写 300 多行。它的边界是只认 composite literal，间接赋值仍会漏。
