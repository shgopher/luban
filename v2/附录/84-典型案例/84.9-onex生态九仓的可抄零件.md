# 84.9 onex 生态九仓：把框架设计拆成可抄的零件

## 一句话

> 84.8 量的是“纵向拆几个进程”，本节量的是“横向的零件做得怎么样”：`miniblog`、`cobrax`、`onexmesh`、`onexai`、`onexai-console`、`go-sample-queue`、`design-pattern` 七个新仓库分别把**注册表、缓存、双协议契约、反馈闭环、长任务恢复、工具面、界面收口**各做了一遍；`fastgo` 与 `onex` 已在 [84.8](84.8-三个Go项目的骨架阶梯.md) 按纵向阶梯解剖，本节末尾回到它们，补 84.8 没展开的**三处债与 i18n 设计**。七个零件值得单独拆走；零件 8 是“怎么读小仓库”的样本：一个 93 行原语可抄，一本 58 种模式的词典只抄目录。其余是平台税、生成器缺口与讲稿级代码，照抄会把别人的约束变成自己的负债。

## 读仓库的顺序：这次是怎么读的

这七个新仓库里，`onexai` 44.7 万行、`cobrax` 不到 1 万行，不能用同一种读法。这次统一按下面六步走，每一步都产出可引用的 `path:line`，读不动就先停在这一步：

| 步 | 看什么 | 回答什么问题 | 什么时候可以跳过 |
|---|---|---|---|
| 1 | README / CLAUDE.md | 作者**声称**它是什么（只当假设，不当证据） | 从不跳过，但要与代码对账 |
| 2 | `cmd/` + 依赖装配 | 有几个二进制、谁装配谁、哪些是工具 | 库项目（cobrax）直接跳到接口 |
| 3 | 接口定义 + 文件头注释 | 边界在哪、契约为什么这么定 | 注释缺失时改看调用点 |
| 4 | 测试 + fake | 作者认为**最难**的失败模式是什么 | 测试很少时，把这一步当风险信号 |
| 5 | `go.mod` + 生成物 | 能力是借来的还是自己写的、升级账单多大 | 无依赖的小仓库可跳过 |
| 6 | 失败路径（超时/取消/重复/崩溃） | 正常路径之外，它有没有兜底 | 从不跳过——这是“能抄”与“能上线”的分界 |

> 🔑 一条实用判据：**先读测试，再读实现**。测试告诉你作者怕什么；实现只告诉你他写了什么。`go-sample-queue` 的 328 行测试里全是“关闭输入 channel”“ctx 取消”“信号合并”这类时序用例，读完就大概知道这个队列的边界在哪。

## 零件 1：自描述后端——把 `switch` 换成注册表

注册中心、编解码器、负载均衡策略、MCP 工具，都会遇到同一个问题：**每加一个实现，就要改一次配置层的 `switch`**。onexmesh 的答案是让后端**自己描述自己**：

```go
// pkg/registry/backend.go:22 —— 一个后端要回答五个问题
type Backend interface {
	Name() string
	AddFlags(fs *pflag.FlagSet, prefix string)
	Decode(raw map[string]any) error
	NewRegistrar(host string, port int, protocol string) (Registrar, error)
	NewDiscovery() (Discovery, error)
}
```

```go
// pkg/options/registry_options.go:87 —— 配置层不再 import 任何具体后端
for _, name := range registry.BackendNames() {
	b, err := registry.NewBackend(name)
	if err != nil {
		continue
	}
	o.backends[name] = b
	b.AddFlags(fs, prefix+"."+name) // --registry.etcd.endpoints ...
}
```

| 写法 | 新增一个后端要改几处 | 编译期能发现漏改吗 | 典型故障 |
|---|---|---|---|
| 配置层 `switch type` + god struct | 3–6 处（struct、flags、decode、构造、校验、文档） | 能，但只覆盖已写到的字段 | 新字段忘了 decode，配置**静默失效** |
| 注册表 + 自描述后端 | 1 个新包 + 1 行空导入 | 不能（漏注册只在运行时报错） | 忘记 `RegisterBackend` → 启动报“未注册” |

这段代码里最值钱的不是接口，而是 `Decode` 方法上那段注释：它解释了一个**没有症状的失败**——YAML 里的 `dial-timeout` 与 Go 字段 `DialTimeout` 名字对不上时，解析不报错、服务照常启动，只是配置被忽略。所以 `DecodeOptions` 专门做了忽略大小写与连字符的匹配。**抄这个模式时，必须同时抄“名字归一化 + 未知后端报错”这两条，否则只是把 `switch` 换成了更难查的静默失败。**

onexai 的 MCP 工具注册表是同一形状的第二个样本：`namespace + name` 组成 wire 名，各工具包在 `init()` 里注册，`List` 缓存排序结果（注册后置空、下次重建），并且**重复注册直接 panic**（`internal/mcpserver/pkg/registry/registry.go:109`）。判据相同：**把“实现清单”从配置代码里移到实现自己身上，让新增变成追加，而不是修改。**

## 零件 2：缓存的是视图，不是答案

第二件零件在两层出现：onexmesh 缓存**实例列表**，onexai-console 缓存**HTTP 读响应**。两者都做了同一组事：合并并发、短 TTL、失败不污染、返回副本。

```go
// onexmesh/pkg/registry/cache/cache.go:99 —— 并发只查一次，且不继承第一个调用者的取消
v, err, _ := c.sg.Do(name, func() (any, error) {
	return c.fetch(context.WithoutCancel(ctx), name)
})
```

```ts
// onexai-console/src/lib/api-client/http-cache.ts —— 用 axios adapter 实现“在途合并 + 3s 缓存”
// 请求拦截器不能短路请求；能“不产生网络往返就交出响应”的只有 config.adapter。
// key 必须在 adapter 内部算：此时 url 已补上网关前缀，拦截器里算会算错。
```

| 决策 | onexmesh 发现缓存 | console HTTP 缓存 | 为什么必须这样 |
|---|---|---|---|
| 缓存对象 | 服务实例快照 | GET 响应 | 缓存“调用结果”会掩盖故障 |
| TTL | 服务 1 min / 节点 30 s | 3 s | 两层 TTL 让“单节点过期”不必整服务重查 |
| 并发 | singleflight | 同 key 复用 promise | 冷启动/首屏并发不放大 |
| 失败 | 有旧快照就返回旧的 | 失败删除表项 | 留 rejected promise 会让该 key 永远读不出来 |
| 写操作 | Watch 推送失效 | 任意写成功清空整表 | 猜“哪几个 key 受影响”一定会猜错 |
| 返回 | 深拷贝 | 新对象 | 防止调用方改坏缓存 |

> 🔑 共同判据：**缓存“视图”，不缓存“答案”**。视图过期最坏是晚几十秒知道变化；答案过期会把一次失败固化成一段时间的假成功。

代价也要抄进去：onexmesh 的 1 min/30 s 意味着扩容最晚 1 分钟才全量可见；console 的 3 s 意味着用户点“刷新”可能拿到 3 秒内的旧数据。两个数字都必须写进契约，而不是藏在实现里。**console 的这份 230 行缓存最终没有被安装（`installHttpCache` 无调用点），这是“设计对、接线没做”的反例——抄设计，不要抄死代码。**

## 零件 3：一份契约，多处适配

onexmesh 把业务处理器的签名定成与 `grpc.UnaryHandler` **完全一致**：

```go
// pkg/middleware/middleware.go:36
type Handler func(ctx context.Context, req interface{}) (interface{}, error)
type Middleware func(Handler) Handler
```

于是同一份 `Handler` 可以被四个桥接器接到不同入口：gRPC unary 服务端/客户端、gRPC stream 服务端、gin（`GinHandler` 与反向的 `FromGin`）。桥接器只做三件事：把协议元数据塞进 context、调用统一 Handler、把错误翻译回协议。

这段代码里有一个**极容易被忽略的状态 bug**，注释写得很清楚：

```go
// pkg/middleware/middleware.go:182
// 统一中间件链被注册成“每个中间件一个 GinHandler”，最直白的实现会为每个中间件
// 建一个 Transporter——于是每个中间件看到的是不同实例。构造时设置的字段看不出来，
// 结束时写入的状态是致命的：响应状态只由最内层写一次，tracing/metrics 在外层读，
// 各持一个 Transporter 时 tracing 读到的状态永远没人设置。
tr, ok := transport.FromServerContext(c.Request.Context())
if !ok {
	tr = newHTTPTransporter(c)
}
```

| 契约设计 | 好处 | 代价 |
|---|---|---|
| 选**最窄的公共签名**（ctx + req + error） | 适配器薄，业务只写一次 | 丢失协议特有信息，要靠 context/Transporter 补 |
| 状态对象**每请求一个** | tracing/metrics 能读到同一份状态 | 需要 context 传递与对象池，写错就出现“各看各的” |
| 中间件顺序**收敛到一个装配函数** | 顺序可评审、可测试 | 顺序错了不会编译报错，只能靠测试/评审 |

第三点 onexai 做到极致：`agentbuilder` 把 10+ 层中间件的顺序写成“反过来会怎样”的注释（图像提取最先、工具错误处理在外层、压缩在摘要前、AGENTS.md 在摘要后），调用方只声明“我是 tool 层还是 model 层”，不声明位置。**代价是这套顺序没有测试断言**——可抄，但必须补一条“顺序快照”测试。

`miniblog` 则给了“一份代码三种服务器”的最小样本：同一个 `Config.ServerMode` 在 `grpc`、`grpc-gateway`、`gin` 三种模式间切换，`wire` 负责把 store/biz/handler 装配起来。它不值得学规模（309 行测试），但值得学**装配点只有一个**：`InitializeWebServer(cfg)` 之外，业务代码不知道自己在哪种协议下运行。

miniblog 还有一个小设计：`store.TX` 把 `*gorm.DB` 放进 context，`DB(ctx)` 优先取事务实例，业务层不必层层传 `tx`。但要提醒：miniblog/fastgo 的 `biz/` 里**一次都没有调用 `TX`**——机制是零件，没有接线；真正的调用点看 onex 的 `usercenter.Create`。机制、嵌套事务与多 store 的坑见 [26.3 整洁架构](../../L2-架构风格/26-分层与依赖/26.3-整洁架构.md)。

## 零件 4：反馈闭环的四个补丁

第四件零件的目标是“让负载均衡与熔断看起来像控制论，而不是 if-else”。onexmesh 的实现里有四个补丁，缺一个就退化：

| 补丁 | 代码里的做法 | 缺了会怎样 |
|---|---|---|
| 反馈信号 | P2C 用 EWMA 延迟 + 成功率，负载 `sqrt(lag) × (inflight+1)` | 只看瞬时在途，慢节点判不出 |
| 时间衰减 | `w = exp(-Δt/10s)` | 一次抖动被永久记档 |
| 防饿死 | 1 s 未被选中强制选一次 | 新恢复节点永远排不上 |
| 状态回收 | Select 后 prune 不在候选集的地址 | 实例频繁发布，map 只增不减 |

熔断则提供了两套算法：三态机（Hystrix 风格）与概率丢弃（SRE 风格）。后者不设状态机，按窗口失败比例算 `dropRatio`，按概率拒；代价是“同一时刻不同请求结果不同”，且实现里的预热因子会让**均匀分布的 50% 失败也不丢**（公式推导见 [35.6 熔断与降级](../../L3-质量属性/35-可用性/35.6-熔断与降级.md)）。

自适降载再补一层：`maxFlight = maxPass × minRt × windowScale`（Little 定律），CPU 只作为“要不要开始丢”的闸门，最低保留 10% 放行。机制细节在 [35.7 限流](../../L3-质量属性/35-可用性/35.7-限流.md)。

真正值得抄的是**链的顺序与错误分类**，而不是某个算法：

```go
// pkg/client/resilience.go:40 —— deadline → bulkhead → breaker → retry，单一真相源
// gRPC 与 HTTP 两个适配器都消费这一个函数，只差“怎么包住最后一次调用”。
func buildResilienceChain(cfg resilienceConfig) []resilience.Middleware {
	// deadline 最外：整条重试序列共享一个预算
	// bulkhead 在 breaker 外：先限制并发，再判断要不要熔断
	// retry 最内：每次重试都算一次独立调用
}
```

顺序不是审美：deadline 放最内会让每次重试各自拿到完整超时，总耗时变成 `attempts × timeout`；retry 放最外会把熔断打开的快速失败也重试一遍。**错误分类同理**：`grpcAcceptable` 把 `InvalidArgument`/`NotFound` 排除在熔断失败之外，`grpcRetryable` 只重试瞬态错误——分类函数写错，熔断和重试会互相放大。

## 把零件 1/3/4 合起来：onexmesh 的“接口 + 组合”

零件 1、3、4 不是三件互不相干的事，它们是同一个设计动作的三次重复：**把变化点压到最小接口上，组合只发生在装配点**。把 onexmesh 的契约摊开看，方法数都不超过 5 个：

| 契约 | 形状 | 变化点 | 组合位置 |
|---|---|---|---|
| `registry.Backend` | 5 个方法 | 换注册中心 | `RegisterBackend` + `pkg/registry/all` 空导入 |
| `Registrar` / `Discovery` | 2 / 3 个方法 | 注册端 vs 发现端 | 接口隔离：客户端只依赖 `Discovery` |
| `middleware.Handler` | 1 个方法 | 换协议 | 4 个桥 + `Chain` |
| `Selector` | `Select` + `DoneFunc` | 换负载均衡策略 | `RegisterSelector` + `client.WithSelector` |
| `codec.Marshaler` | 3 个方法 | 换序列化 | `Register/Get` + HTTP 中间件 |

判据不是“接口多不多”，而是下面四个问题：

| 问题 | 差的设计 | onexmesh 的答案 |
|---|---|---|
| 新增一种实现改几处 | 配置层 `switch` 改 3–6 处 | 1 个新包 + 1 行空导入 |
| 业务包 import 具体实现吗 | 是，换后端要改业务 | 否，只 import 接口 |
| 删掉一种实现 | 全局搜引用 | 删包 + 删空导入 |
| 测试时怎么替换 | 起一个真后端 | fake/内存实现即可 |

组合也不是“上依赖注入框架”，而是在 `main`/装配点把接口拼起来：`pkg/registry/all` 用空导入把内置后端放进注册表，`server.NewMeshServer(opts, ...)` 是唯一装配点，`client.Dial` 用函数选项组合策略。业务代码不 import `etcd`/`polaris`，只 import `registry`。

> 🔑 “接口 + 组合”的判据只有一句：**换实现时，业务代码改 0 处，配置代码改 1 行。** 做不到，就说明接口切在了错误的位置——要么太细（把实现细节冻进契约，比如 `Backend.NewRegistrar(host, port, protocol)` 对 etcd 根本用不上却必须接收），要么太粗（一个 god interface 把注册、发现、健康检查全塞进去）。

## 零件 5：长任务——持久化准入 + 租约围栏

一次 Agent run 可能跑几分钟，中途要等人审批，人可能在另一台机器上一小时后才点“同意”。onexai 没有把 run 的准入交给消息队列，而是**用一张 PostgreSQL 表当队列**：

```go
// internal/agent/biz/v1/run/admit.go:111 —— 租约是三个数，不是布尔值
const (
	AdmissionLeaseTTL          = 90 * time.Second // 三次心跳，丢一次不误判
	AdmissionHeartbeatInterval = 30 * time.Second
	MaxAdmissionClaims         = int32(5)          // 毒丸上限
)
```

一次执行要过五道关：

| 关卡 | 做法 | 防的是什么 |
|---|---|---|
| 幂等 | `dedupKey` 唯一索引 | 同一请求重复提交 |
| 抢占 | `ClaimAdmission` 原子地把 owner 写进去 | 两个副本同时跑同一个任务 |
| 重读 | claim 之后再 `GetAdmission`，校验 `LeaseOwner == owner` | 取消恰好落在 UPDATE 与 SELECT 之间 |
| 续租 | 心跳失败/租约丢失 → `cancel()` 本地执行 | 失去领导权的副本继续写结果 |
| 围栏 | 终态写入 `WHERE lease_owner = ?` | 旧 owner 覆盖新 owner 的结果 |

围栏不是一句注释，是三条带条件的更新（GORM）：

```go
// runstore/store.go:505 —— 抢占：只有“待跑且到点”或“在跑但租约过期”的行能被抢（节选，省略 s.db.Model 前缀）
Where("id = ? AND claim_count < ?", id, maxClaims).
	Where("(state = ? AND scheduled_time <= ?) OR (state = ? AND lease_until <= ?)",
		model.RunStatePending, now, model.RunStateRunning, now).
	Updates(map[string]any{
		"state": model.RunStateRunning, "lease_owner": owner,
		"lease_until": until, "claim_count": gorm.Expr("claim_count + 1"),
	})

// :555 —— 续租：owner 与 state 必须同时匹配，否则返回 false，本地执行被取消
Where("id = ? AND lease_owner = ? AND state = ?", id, owner, model.RunStateRunning)

// :571 —— 终态：旧 owner 的写入影响 0 行，覆盖不了新 owner 的结果（节选）
db := db.Where("id = ? AND state NOT IN (?, ?, ?)", id, succeeded, failed, canceled)
if owner != "" {
	db = db.Where("lease_owner = ?", owner)
}
```

| 写操作 | 是否围栏 | 为什么 |
|---|---|---|
| `ClaimAdmission` | 条件 UPDATE（原子） | 抢占本身要原子，不能先查后写 |
| `RenewAdmission` | `WHERE id + lease_owner + state` | 丢了租约就不能再续 |
| `FinishAdmission` | `WHERE id + lease_owner` | 旧 owner 不能写终态 |
| `CancelAdmission` | **不围栏** | 取消是用户对 run 的动作，不是 owner 的执行结果；租约刚丢时它更必须成功 |
| `GetAdmission` 重读 | 读后校验 owner | 关闭“claim 成功”到“开始执行”之间的取消窗口 |

最后一条有测试守护：`runstore/store_test.go:154` 的 `TestFinishAdmissionIsFencedOnOwner` 明确构造了“旧 owner 写失败、新 owner 写成功”。**没有这条围栏，租约就只是“看起来在续”，旧副本仍能落库。**

恢复路径同样值得抄：调度器只做“扫 pending + 复用同一个 `Execute`”（30 s 一轮、每轮最多 100 条），所以“新提交”和“崩溃恢复”走同一条代码路径，不存在两套执行逻辑。人工审批的断点则用 `Claim(runID, requestID)` 的 `SETNX` 保证“只恢复一次”，并在恢复前校验“当初批准的工具有没有还在图里”（`checkPendingTools`）——否则工具被下线后，恢复会执行一个不存在的工具，而框架把未知工具降级成文本，run 会“报告成功但什么都没做”，这恰好是审批闸门要防的事。

| 代价 | 数字 | 什么时候别抄 |
|---|---|---|
| 每次执行 3 次 DB 往返（claim/get/校验） | 高 QPS 下是 3 倍压力 | 任务 < 1 min、重复执行无副作用 |
| 扫表与“提交即执行”争抢 | 30 s / 100 条 | 任务量大且没有分片扫描 |
| 无重试退避 | 5 次后进死信 | 需要自动重试的场景要自己补 |

## 零件 6：工具面——CLI→MCP 与最小权限

`cobrax` 解决的是“内部能力已经以 CLI 存在，怎么让 Agent 用上”。它给出两种执行模型，选择依据是**状态在哪**：

| 模型 | 状态来源 | 适合 | 代价 |
|---|---|---|---|
| 子进程 | 每次重跑二进制，只能从 flag/env 重建 | 无状态命令、危险操作隔离 | 启动开销；拿不到内存里的连接/缓存 |
| 进程内 | 直接调 `RunE`，闭包持有 client/db | 有连接、有缓存、低延迟 | 必须每次调用重建命令树，否则 flag 串写 |

```go
// cobrax/server.go:74 —— 进程内模型的全部秘密在这句注释里
// cmdFactory is called once per tool invocation to produce a fresh
// *cobra.Command tree. This eliminates all shared-state hazards...
```

工具面同时是权限边界：`AllowCmds`/`ExcludeCmds` 决定暴露哪些命令，`ExcludeFlags("token","secret")`/`NoFlags` 决定暴露哪些参数，隐藏/废弃/无 `Run` 的命令默认排除，`readOnlyHint`/`destructiveHint` 供审批层使用。**默认全暴露等于把 `delete`、`exec`、`--token` 一起交给模型。**

另一个容易被忽略的写操作：`cobrax` 改编辑器配置时先备份、再 `os.WriteFile(m.configPath, data, 0o644)`（`internal/cfgmgr/manager/manager.go:151`）。这不是原子写——进程在写一半时崩溃会留下半截 JSON；`0644` 还让同机其他用户可读（配置里可能有 PATH、环境变量甚至 token）。写用户配置的正确姿势是：同目录临时文件 + `fsync` + `rename`，权限 `0600` 或保留原文件 mode，备份按时间戳保留而不是每次覆盖同一份。

onexai 的 MCP 层补充了三个“接第三方 server 必踩”的细节：

| 坑 | 做法 | 代价 |
|---|---|---|
| 工具名不合模型 API 规范（`kubernetes_pod.logs`） | 消毒成 `^[a-zA-Z0-9_-]{1,64}$`，调用仍用原始 wire name | 消毒会丢信息，可能撞名（代码未查重） |
| 返回体多包一层 `{"content":[{"text":...}]}` | 扁平化后再给模型 | 丢失原始结构，排障时要看日志 |
| 一个挂死的 server 拖垮每个 run | 熔断只对“工具自己的超时”计数（4 次/1 min） | 进程内状态，多副本各自熔断 |

工具多到 40 个以上时，onexai 才启用 tool-search 把 MCP 工具折叠成一个检索入口；它明确写了**为什么不默认开**：过滤工具列表会让 provider 的 prompt cache 失效。抄这个阈值之前先量自己的 schema 字符数——40 是魔法数。

## 零件 7：界面——22 类资源、3 个页面、1 个状态机

`onexai-console` 是一个 6.3 万行的 React 控制台，真正撑住 22 类资源 CRUD 的只有三个通用页面：`ResourceList`（82 行）、`ResourceDetail`（363 行）、`ResourceForm`（994 行），加一个 1,339 行的列表组件。路由也是通配的 `:resourceKey/new`、`:resourceKey/:id/edit`，不逐资源注册。

| 收口 | 做法 | 可迁移性 |
|---|---|---|
| 三层描述符 | 线协议（`types.ts`）/ UI 字段（`ResourceSpec`）/ 表格（`ResourceDef`）各司其职 | 资源 < 10 类别做，否则描述符文件本身会变成 4,223 行的巨石 |
| 条件显示单一来源 | `when` 一份规则同时喂表单、详情、提交裁剪 | 高：避免“表单隐藏了但提交还带着” |
| 写后对账 | `reconcile` 1 s × 10 轮 + 代数防回退，应对 informer 缓存“写完读不到” | 高：声明式后端的通用问题 |
| 流式状态机 | `idle/streaming/suspended/done/stopped/error`，**没有 `final` 事件就判 error** | 极高：每个 LLM 前端都该抄 |
| 鉴权 | tokenStore 自广播（`useSyncExternalStore`）+ 路由外层单闸 | 高：避免“401 清了 token 但界面不知道” |

```ts

	setState(prev => prev.status === 'suspended' ? prev
```

`streamRequest` 也值得读：它明确用 `fetch` 而不是 `EventSource`（后者不能带 `Authorization`），手写 SSE 分帧（空行分隔、`\r\n` 与 `\n` 都认、多行 `data` 拼接），401 只重试一次，且把 429 的 `{code,message}` 翻译成和 axios 侧一致的文案。**流式端点的错误语义最容易两条路径各说各话。**

还有一个 TanStack Query 的经典死锁，值得抄进类型注释：同一个 queryKey 的 `queryFn` 里再调 `listAllRows`（内部 `queryClient.fetchQuery` 同键），内层会把**外层自己的 promise** 返回给外层，外层在等自己，页面永远 loading 且不发请求。正确做法是拆两个入口：观察用 `fetchAllRows`，命令式用 `listAllRows`，并把“不能互换”写在函数文档里。

不抄的部分同样清楚：`src` 里约 328 行 api-client 死代码（包括那份从未安装的 http-cache）、4 个整页死代码 1,133 行、i18n 只有约 15% 覆盖且用中文原文当 key、**0 个 ErrorBoundary**（一个页面抛错整树白屏）、测试 14 文件 92 用例（约 2%）。一个 6.3 万行的应用没有错误边界，是“能跑”与“能运维”的分界线。

## 零件 8：小仓库——一个 93 行的原语，一本 58 种的词典

`go-sample-queue` 用 93 行实现 + 328 行测试（**3.5 倍**）做了一件事：把 channel 的“会合”变成 list 的“缓冲”。实测生产者 200 ms/条、消费者 400 ms/条时，直接走无缓冲 channel 的最后一次发送在 **1608 ms**，换成队列后提前到 **804 ms**；但 100 万条不消费会让堆从 0.2 MB 涨到 **72.2 MB**（约 72 B/条）。它证明的是“队列能解耦速率”，也顺手证明了“无界队列会把积压从 broker 搬到堆内存”。机制与用法在 [43.5 积压与背压](../../L4-组件与技术/43-消息队列/43.5-积压与背压.md)。

`design-pattern` 是另一类样本：README 标称 58 种，表格实际勾了 **64 项**，分创建/行为/结构/同步/并发/消息/稳定七类；目录价值很高（尤其“并发/消息/稳定”这三类是 GoF 没有的），但实现大多是**讲稿级**：

| 模式 | 仓库里的实现 | 问题 |
|---|---|---|
| 断路器 | `stability/circuit/circuit.go` 42 行，`failCount >= 3` 就置 `breaker=true` | 没有窗口、没有半开、没有超时 |
| 隔离舱 | `stability/bulkhead/bulkhead.go` 27 行，起 3 个 goroutine 等 `WaitGroup` | 这不是隔离，只是并发 |
| 批处理 | `concurrency/batcher/batcher.go` 31 行，`go processBatch` + `Sleep` 等结果 | 没有背压、没有错误处理 |
| 信号量 | `synchronization/semaphore/semaphore.go` | 可用：带超时的 channel 信号量 |
| 截止期限 | `stability/deadline/deadline.go` | 可读，但有 goroutine 泄漏风险：超时后 `result` 无人接收，工作协程会阻塞在发送上 |

> 🔑 结论：**目录可以抄，实现不要抄。** 模式库回答“有哪些变化点”，生产实现回答“失败时怎么办”；这两件事在这套仓库里是分开的，混在一起读就会把 27 行的演示当成隔离舱。

## 补遗：回到 fastgo 与 onex

84.8 用“纵向阶梯”量过 fastgo → iam → onex：fastgo 3,086 行、15 个直接依赖、1 个测试；onex 120,577 行、112 个直接依赖、65,972 行生成物（54.71%）。这里不再重复阶梯，只补两处**只有读到调用点才看得见**的横向设计。

### fastgo：最小闭环的三处债

fastgo 的骨架是对的：`cmd/fg-apiserver/app/options` 把“命令行选项 → 应用配置 → 服务器对象”拆成三步，`Config.NewServer` 是唯一装配点，`core.WriteResponse` 是唯一响应出口。但“最小闭环”不等于“生产可用”，读调用点能找到三处债：

| 债 | 证据 | 后果 | 修法 |
|---|---|---|---|
| 认证失败返回 200 | `internal/pkg/middleware/authn.go:19` 调用 `core.WriteResponse(c, errorsx.ErrTokenInvalid, nil)` | `err` 为 nil，走成功分支，HTTP 状态是 200，只有响应体里有一个错误对象；客户端/网关会认为鉴权通过 | 改成 `WriteResponse(c, nil, errorsx.ErrTokenInvalid)`；并加一条“未带 token 必须 401”的集成测试 |
| 未知错误原文外泄 | `internal/pkg/errorsx/errorsx.go:54` 把 `err.Error()` 填进 `Message` | 数据库错误、文件路径、内部地址直接回给客户端 | 固定 `Message`（“Internal server error”），原始错误只进日志，用 RequestID/`Reason` 关联 |
| 默认 JWT 密钥 + `sync.Once` | `pkg/token/token.go:30` 硬编码默认密钥，`Init` 只生效一次 | 绕过 `ServerOptions.Validate` 的调用路径（测试、工具、其他二进制）会用公开默认密钥；测试里无法重置，第二个 server 实例的配置被忽略 | 删掉默认值，`Init` 改为显式依赖（或允许重复设置仅用于测试） |

```go
// internal/pkg/core/core.go:13 —— 统一响应出口只回 Reason/Message，不回 Code
type ErrorResponse struct {
	Reason  string `json:"reason,omitempty"`
	Message string `json:"message,omitempty"`
}
```

这个三字段契约真正缺的不是 `Code`（HTTP 状态已经承载它），而是**调用点的类型安全**：`WriteResponse(c, data any, err error)` 的 `data` 是 `any`，把 `ErrTokenInvalid` 放进 `data` 也能编译——上面那条 200 就是这么来的。把签名拆成“成功一个函数、失败一个函数”（或让 `data` 只接受成功 DTO），编译期就能挡住这类误用（错误码体系见 [40.7 错误码体系](../../L3-质量属性/40-可维护性/40.7-错误码体系.md)）。**单一渲染点是好事，但它必须配“调用点类型安全 + 一条 401 测试”，否则错误参数会在一个地方悄悄统一错。**

> 🔑 fastgo 的正确用法：把它当“最小闭环的样板”，不要当“工程规范的样板”。它的价值是让你看见装配顺序与错误契约的形状；它的债正好告诉你，形状之外还要有测试与安全默认值。

### onex：i18n 的 fallback 设计与声明式账单

onex 在 84.8 里是“平台税”的代表；它的 i18n 是少数可以单独拆走的零件。核心只有两条：

```go
// staging/.../pkg/i18n/i18n.go:81 —— 翻译失败时回退到 message ID，而不是空字符串
func (i I18n) LocalizeT(message *i18n.Message) (rp string) {
	rp, err = i.localizer.Localize(&i18n.LocalizeConfig{DefaultMessage: message})
	if err != nil {
		rp = message.ID
	}
	return
}
```

```go
// internal/pkg/middleware/i18n/i18n.go:21 —— 从 Accept-Language 选语言，放进 ctx，再回写响应头
func Translator(options ...func(*i18n.Options)) middleware.Middleware {
	i := i18n.New(options...)
	return func(handler middleware.Handler) middleware.Handler {
		return func(ctx context.Context, rq any) (rp any, err error) {
			var lang language.Tag
			header := make(metadata.MD)
			key := "Accept-Language"
			if tr, ok := transport.FromServerContext(ctx); ok {
				lang = language.Make(tr.RequestHeader().Get(key))
			}
			ii := i.Select(lang)
			header.Set(key, ii.Language().String())
			ctx = metadata.NewOutgoingContext(ctx, header)
			ctx = i18n.WithContext(ctx, ii)
			return handler(ctx, rq)
		}
	}
}
```

| 设计 | 好处 | 代价 |
|---|---|---|
| 错误文案 = message ID | 文案与翻译表同一份 key，调用点不散落硬编码文案 | message ID 不是错误码：客户端分支仍要看 Reason/HTTP code；改 ID 会破坏翻译 |
| 翻译失败回退 ID | 永不返回空错误；缺翻译时至少可定位 | 用户会看到 `record.not.found` 这种半成品 |
| `Accept-Language` 中间件 | 业务代码不传语言参数，横切面统一 | 多一层 context 依赖；异步任务/消息消费没有请求头时要显式带语言 |
| 语言回写响应头 | 客户端知道服务端实际用了哪种语言 | 缓存键要包含 `Vary: Accept-Language`，否则串语言 |

onex 的声明式部分则是另一面：`onex-controller-manager` 用 controller-runtime + k8s feature gates + leader election 搭起来，`internal/apiserver/registry` 按 K8s 的 registry/storage/strategy 分资源。这套东西解决的是“资源声明 + 控制器收敛”，不是“业务 CRUD 更快”。84.8 的数字已经说明账单：112 个直接依赖、65,972 行生成物（54.71%）、29 个 `cmd/` 目录。**如果需求里没有“声明期望状态、系统自动收敛”，这些代码一行都不该进业务服务。**

还有一条 84.8 没展开的：**同一仓库并存两套服务骨架**——业务服务（gateway/usercenter）用 Kratos（middleware/registry/i18n），平台组件（controller-manager/apiserver）用 controller-runtime + k8s 库，共享代码放在 `staging/`。这不是“不统一”，而是按“有没有资源声明”选骨架：有 CRD 与控制器，就用 controller-runtime；只有 CRUD，就用 Kratos。抄的时候别把 Kratos 硬塞进 controller，也别把 controller-runtime 塞进 CRUD 服务。

还有一个反例：`onex-pump` 不套四层，而是 source → filter → sink 的数据流（`source.Via(filter).To(sink)`）。组件形态由职责决定——管道就是管道，不要为了“统一”给它套 controller/service/store。

> 🔑 fastgo 与 onex 的关系，不是“简陋 vs 高级”，而是“闭环 vs 平台”：fastgo 用 3,000 行让你看清一次请求怎么走完；onex 用 12 万行让你看清资源怎么被声明与收敛。抄 fastgo 抄装配与错误契约（并补上它的三处债），抄 onex 只抄 i18n 与生成物边界，别抄它的依赖树。

| 发现缓存 | 实例变更最晚 1 min 可见 | 缩容必须立刻生效（叠 Watch 主动失效） |
| 统一 Handler + 桥 | 要改所有服务的处理器签名 | 只跑一种协议；适配层是纯成本 |
| 概率熔断 | 必须用混合成功/失败流量压测 | 低流量（<10 QPS）；要状态可告警 |
| 准入租约 | 一张表 + 3 次 DB 往返 + 死信处理 | 任务 <1 min；重复执行无副作用 |
| CLI→MCP | 工具面治理、PATH 注入、权限评审 | 没有破坏性命令；只是内部只读查询 |
| 通用资源页 | 描述符文件会长到数千行 | 资源 <10 类；页面差异大 |
| 内存队列 | 必须加上限与崩溃恢复 | ack 路径；不可重放的数据 |

## 自检

**Q1** 零件 1 的“自描述后端”把新增实现从“改 6 处”降为“加 1 个包”，它把什么风险换走了？怎么补？

▸ 答案：换走了**编译期可见性**。`switch` 写法漏改字段通常编译不过（或至少集中在一处 review），注册表写法漏 `RegisterBackend` 只会在运行时启动时报“未注册”，甚至被 `Validate` 挡住才暴露。补法有三条：① `Validate` 对“配置里出现但未注册的后端”明确报错；② 所有内置后端在 `pkg/registry/all` 空导入，保证默认可用；③ 加一条启动自检，列出已注册后端名。

**Q2** 为什么发现缓存与 console 的 HTTP 缓存都强调“失败要删表项”，而成功可以缓存？

▸ 答案：因为悬空的 rejected promise 会把这个 key 永久锁死：后续调用复用它，立即得到同一个错误，且错误看起来像业务错误；删掉表项，下一次调用至少还有机会成功。成功结果过期只是“旧”，失败结果滞留是“死”。这也是“缓存视图不缓存答案”的另一面：视图缓存失败可以降级返回旧快照，答案缓存失败只能返回错误。

**Q3** onexmesh 把 `deadline` 放在最外层、`retry` 放在最内层，如果反过来会怎样？用数字说明。

▸ 答案：反过来（retry 最外、deadline 最内）时，每次重试都会拿到一个新的完整超时，3 次尝试、每次 1 s，总耗时上限变成 3 s，且总预算不再受调用方控制；如果 deadline 在最外，1 s 预算内最多重试到预算耗尽，第 2 次之后就会被 ctx 取消。另一个方向：retry 最外还会把 breaker 打开的 `ErrCircuitOpen` 也重试 3 次，快速失败变成 3 次快速失败，放大无意义调用。

**Q4** onexai 的准入租约为什么要在 claim 之后“再读一次”并校验 owner？只 claim 一次不够吗？

▸ 答案：不够。claim 是原子的，但“claim 成功”与“开始执行”之间有一个窗口：用户可能在这个窗口里取消任务，或另一个副本因为租约过期接管。再读一次并校验 `state == running && lease_owner == owner`，才能确保“现在这个时刻，我仍是合法 owner”。这次读看似多余，实际是把“抢到”与“仍有资格”分开——只抢不验，取消会被忽略，旧 owner 会继续跑。

**Q5** 为什么 onexai 要在恢复前检查“当初批准的工具有没有还在图里”？不检查会“成功”还是“失败”？

▸ 答案：不检查会**假成功**。框架对未知工具的处理是返回一段可自愈的文本（避免模型幻觉导致整轮失败），所以恢复后调用一个已下线的工具，不会报错，模型会收到“工具不存在”的提示，然后可能直接回答“已完成”。run 最终标记 `Done`，但审批过的那件事根本没执行。检查 `Pending[].ToolName` 是否仍在工具集里，才能把“环境变了”变成显式失败。

**Q6** console 的 `streamRequest` 为什么不用 `EventSource`？它怎么处理 401 与 429？

▸ 答案：`EventSource` 不能自定义 `Authorization` 头，而平台的 SSE 端点要求 Bearer token；所以用 `fetch` + `ReadableStream` 手写分帧（空行分隔、兼容 `\r\n`、多行 `data` 拼接）。401 时刷新一次 token 并重发一次，仍 401 才清会话并回调 `onUnauthorized`；429/413 把 `{code,message}` 翻译成与 axios 侧一致的文案，避免“流式路径说 HTTP 429、普通路径说限流”的两套说法。

**Q7** 93 行的队列测试有 328 行，而 13,932 行的 miniblog 只有 309 行测试。这个反差说明“测试覆盖率”该怎么看？

▸ 答案：说明**测试密度应该跟失败模式走，不是跟代码量走**。队列的失败模式是并发、关闭、取消、信号合并，全部是“跑一万次可能挂一次”的时序问题，只能靠测试覆盖；miniblog 是教学项目，很多代码是装配与样板，测试少是取舍（但 2.2% 仍然偏低，发布前要补关键路径）。判断一个仓库能不能抄，先看它的测试是否覆盖**它最难的失败模式**，而不是看总行数比。

**Q8** 准入租约里，为什么 `FinishAdmission` 必须围栏在 `lease_owner` 上，而 `CancelAdmission` 反而不能围栏？

▸ 答案：因为两者保护的对象不同。终态写入是 **owner 对执行结果的声明**：租约过期后旧 owner 已经无权代表这个 run，它的结果必须被拒绝，否则会覆盖新 owner 的结果。取消是 **用户对 run 的动作**：用户点“取消”时，租约可能刚好过期、owner 可能已经失联，如果取消也要求 owner 匹配，就会在“最需要取消”的时刻失败。正确做法是取消不围栏、直接改状态，当前 owner 在下一次续租时发现租约丢失，自行停止。**围栏保护“谁能写结果”，不保护“用户能不能终止”。**
