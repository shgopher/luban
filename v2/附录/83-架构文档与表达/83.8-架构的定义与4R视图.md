# 83.8 架构的定义与 4R 视图

## 一句话

> 架构 ＝ 系统的**顶层结构**：先声明**层级**（Rank），再说清它由哪些**角色**（Role）组成、角色之间是什么**关系**（Relation）、按什么**规则**（Rule）协作；**一张图只回答一个问题**——静态图（Role + Relation）**1–2 张**，动态图（Rule，序列图）**多张**。

## 先分开三对常混的词

| 一对 | 区别 | 判据 | 常见误用 |
|---|---|---|---|
| **系统 / 子系统** | 不是两种东西，是**观察角度**：一个系统可以是更大系统的子系统 | 这次要交付的边界是哪一个 | 把系统架构与子系统架构混谈，层次错乱 |
| **模块 / 组件** | **模块按逻辑拆**（目的是职责分离）；**组件按物理拆**（目的是单元复用，独立且可替换） | 拆出来的单元能不能**单独替换 / 独立部署** | 「MySQL 模块」「安全加密组件」混着叫 |
| **框架 / 架构** | 框架关注**规范**（MVC、JPA 约束你写什么）；架构关注**结构**（有哪些角色、怎么连） | 它是「你必须遵守的规范」还是「你的系统长什么样」 | 「我们是 MVC 架构」「我们基于 SSH 架构开发」——说法不算错，但没交代分解角度 |

> 🔑 **同一个系统有多套正确架构**不是玄学：从业务逻辑看是三五个模块，从物理部署看是 Nginx + 应用 + MySQL，从开发规范看是 MVC——这些都是它的架构，只是**分解角度不同**。说「架构」时不带角度，讨论必然各说各话。

## 为什么用「顶层结构」而不是「基础结构」

维基百科的定义是「基础结构」，问题在于它没说清**是谁的**基础结构：微信有架构，微信的登录系统也有架构，两者用同一个词都成立，于是「系统架构」和「子系统架构」在文档里混成一锅。

改成**顶层结构**后有两件事被钉死：

1. **层级先行**：先声明这次谈的是哪一级，再谈内容（见下一节的 L0–L4）；
2. **两要素齐全**：既要说明「包含哪些个体」（子系统 / 模块 / 组件），也要说明「个体运作与协作的规则」——**只说组成不说规则，是清单，不是架构**。

## Rank：先定这次画哪一级

| 层级 | 回答什么 | 典型读者 | 元素数量经验 |
|---|---|---|---|
| **L0 产品级** | 整个产品由哪些系统组成、与哪些外部方交互 | 老板、业务方 | ≤ 15 |
| **L1 系统级** | 本系统由哪些子系统/服务组成 | 架构、开发、运维 | ≤ 20 |
| **L2 子系统级** | 子系统内部由哪些模块组成 | 该系统开发者 | ≤ 25 |
| **L3 应用级** | 有哪些可部署发布的程序 | 开发、测试、运维 | 按子域拆 |
| **L4 模块级** | 模块内部的类与接口 | 接手者 | 通常由工具生成 |

> 数字口径：元素数量经验来自 [83.1 C4 模型](83.1-C4模型.md) 的同一套判据（C1≤15、C2≤20、C3≤25）；**层级名称是 L0–L4，与 C4 的 C1–C4 是两套编号，别混用**。

## 4R：把定义变成四个动作

| 步骤 | 问什么 | 产出 | 判据（做不到就是没画完） |
|---|---|---|---|
| **Rank 层级** | 这次画哪一级？ | 一句话声明 + 边界 | 图里出现两个不同层级的角色（如「支付系统」与「风控的 Redis」并排）→ 层级没定 |
| **Role 角色** | 系统由哪些角色组成？ | 区块 / 图标 / 节点 | 每个角色能用**一句话**说清职责 |
| **Relation 关系** | 角色之间怎么连？ | 连接线（同步调用 / 异步消息 / 数据依赖） | 连线有**方向与类型**，不是一团网 |
| **Rule 规则** | 核心场景下它们怎么协作？ | 系统序列图 | 至少覆盖**一条主流程 + 一条异常流程** |

**静态 vs 动态**：

| 类型 | 画什么 | 数量经验 | 读者 | 什么时候画 |
|---|---|---|---|---|
| **静态架构图** | Role + Relation | **1–2 张**：简单系统 1 张；复杂系统拆 2 张（角色一张、关系一张） | 开发、运维、评审 | 方案评审、交接 |
| **动态架构图** | Rule（系统序列图） | **多张**：核心场景有几个就有几张 | 开发、测试、新人 | 关键链路设计、故障复盘 |

**为什么静态图只要 1–2 张**：静态结构对同一个系统是**唯一**的，角色与关系不随场景变化，多画只是换配色；而**核心场景有多个**（下单、退款、对账、补单…），每个场景的 Rule 都不同，所以动态图必须多张。

## 与 C4、4+1 怎么共存

| 体系 | 管什么 | 在本库的用法 |
|---|---|---|
| **C4**（[83.1](83.1-C4模型.md)） | 管**缩放级别**：同一个系统四个放大倍数 | 回答「画多细」 |
| **4+1 视图** | 管**视角**：逻辑 / 处理 / 开发 / 物理 / 场景 | 已被 C4 取代（取舍见 [83.1 C4 模型](83.1-C4模型.md)），只在需要与传统评审对齐时引用 |
| **4R**（本文） | 管**一张图回答一个问题**：先定层级，再分静态 / 动态 | 回答「这张图画什么、该有几张」 |

三层关系一句话：**C4 决定放大倍数，4R 决定这一张图答哪个问题，六类图（[83.9](83.9-六类架构图的分工与画法.md)）决定给谁看**。

## 一页检查清单

```text
画图前：
  [ ] Rank 写下来了（L0–L4 里的哪一级）
  [ ] 这张图只回答一个问题（Role/Relation 还是 Rule）
  [ ] 读者是谁（老板 / 运维 / 新人 / 评审）

画图后：
  [ ] 每个角色一句话能说清职责
  [ ] 每条连线有方向 + 类型（同步 / 异步 / 数据）
  [ ] 同一张图没有跨层级元素
  [ ] 复杂系统的静态图拆成了 2 张（角色、关系）
  [ ] 核心场景至少有一张序列图（含一条异常分支）
  [ ] 全图颜色 ≤ 3 种，且颜色有语义（不是装饰）
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 一张图里既有产品功能、又有部署机房、还有类图 | 谁都看不懂，评审变成猜图 |
| 只画静态框图，不画任何序列图 | 关系对了、规则错了；上线才发现调用是同步的 |
| 画 5 张静态图，每张都是同一层级的不同配色 | 信息量没增加，维护成本 ×5 |
| 用「模块 / 组件」两个词混指同一批东西 | 讨论粒度失控，拆分方案无法对齐 |
| 说「我们是 XX 架构」却不交代分解角度 | 各说各话，评审不收敛 |
| 把 Rank 当装饰，L0 级图上出现 Redis 实例 | 读者无法判断该看什么，也无法据此分工 |
| 动态图画成「一个大框套所有调用」 | 时序、失败分支全丢失，等于没画 |

## 自检

**Q1** 「我们的系统是 MVC 架构」这句话错在哪？
▸ 答案：没错，但缺了**分解角度**。MVC 是开发规范视角的架构；同一个系统从物理部署看是 Nginx + 应用 + MySQL，从业务逻辑看是登录 / 订单 / 支付模块。**不交代角度，架构讨论就没有共同坐标**。

**Q2** 模块和组件的划分目的分别是什么？
▸ 答案：模块按**逻辑**拆，目的是**职责分离**；组件按**物理**拆，目的是**单元复用**（可独立替换、独立部署）。同一套系统两种拆法同时成立。

**Q3** 为什么静态图最多 1–2 张，动态图却要多张？
▸ 答案：静态结构对同一个系统是**唯一**的，角色与关系不随场景变化，所以 1–2 张足够（复杂系统拆成「角色」「关系」两张）；而**核心场景有多个**，每个场景的 Rule 不同，动态图必须每个场景一张。

**Q4** 一张架构图里同时出现「支付系统」和「风控服务的 Redis」，问题在哪？
▸ 答案：**Rank 没定**。前者是 L1 系统级，后者是 L2/L4 组件级，混在一张图里读者无法判断粒度，也无法据此分工。

**Q5** 「顶层结构」比「基础结构」好在哪？
▸ 答案：它强迫你先声明**层级**，从而把「系统架构」和「子系统架构」分开；而「基础结构」对两者都成立，正是层次混乱的源头。

**Q6** 有了 C4，为什么还需要 4R？
▸ 答案：两者管的是不同维度。C4 管**放大倍数**（同一个系统画到多细），4R 管**这一张图回答哪个问题**（结构还是流程）。实践中常见「用 C2 的粒度画了一张既有容器又有调用时序的图」——C4 是对的，问题出在没做 4R 的第三、四步。
