# 83.9 六类架构图的分工与画法

## 一句话

> 架构图不该按「标准」画，该按**读者**画：业务方要看业务全景（业务架构图），运维要看到机房与硬件（部署架构图），开发要看到可部署的程序（应用架构图），新人要看到场景怎么跑通（系统序列图）——**给谁看，决定画哪一种**。

## 六类图：定义、读者、场景、技巧

| 图 | 定义 | 读者 | 使用场景 | 画图技巧 |
|---|---|---|---|---|
| **业务架构图** | 系统对用户提供了哪些**业务功能**（约等于 4+1 的场景视图） | 业务方、老板、新人 | 产品规划、给高管汇报、新人培训 | ① 颜色标识业务**状态**（发展好 / 问题多 / 稳定 / 竞争激烈）；② 业务分组用虚线框；③ 区块对齐求美观（长短不代表量级） |
| **客户端和前端架构图** | 客户端 / 前端的**领域逻辑**架构 | 客户端架构师、客户端开发 | 客户端整体设计、架构培训 | ① 颜色标识不同角色；② 多种关系用不同形状线条（直接调用 vs 事件通知）；③ 分层或分组 |
| **系统架构图** | 后端的**逻辑架构**（业务系统、中间件、OS、DB 都算） | 后端开发、架构 | 整体架构设计、架构培训 | 复杂系统拆 **2 张**：一张画角色与核心能力，一张画关系 |
| **应用架构图** | 系统由哪些**可部署发布的程序**组成 | 开发、测试、运维 | 项目开发测试、部署发布、子域设计 | 简单系统与应用架构等价；复杂系统**按子域**画（应用可能几百上千个，塞一张图必然看不清） |
| **部署架构图** | 机房 / 网络 / 硬件怎么部署 | 运维 | 总体架构设计、运维规划与优化 | **用图标代替区块**（服务器、交换机、机房图标） |
| **系统序列图** | 某业务场景下角色如何协作完成功能 | 开发、测试 | 配合系统 / 应用 / 部署图使用 | 用 UML 序列图；一条主流程 + 一条异常分支 |

## 按读者选图：一张决策表

| 你要回答谁的问题 | 画这张 | 不要用这张替代 |
|---|---|---|
| 老板问「我们业务覆盖到哪了、明年做什么」 | 业务架构图 | 系统架构图（他看不懂，且不关心） |
| 新人问「这个功能点一下，后端发生了什么」 | 系统架构图 + 系统序列图 | 部署架构图 |
| 运维问「这套东西要几台机器、在哪个机房」 | 部署架构图 + 应用架构图 | 业务架构图 |
| 测试问「我该给哪些服务造用例」 | 应用架构图 + 系统序列图 | 系统架构图（它不落到可部署单元） |
| 评审问「这个方案的结构合理吗」 | 系统架构图（1–2 张静态）+ 关键场景序列图 | 一张「全都有」的大图 |
| 客户端同学问「前端逻辑怎么分层」 | 客户端和前端架构图 | 系统架构图 |

## 通用制图规范（六类图都适用）

| 规则 | 具体做法 | 反例 |
|---|---|---|
| **颜色 ≤ 3 种** | 颜色必须有语义（状态 / 角色 / 分层），不是装饰 | 一张图 7 种颜色，读者要猜图例 |
| **一张图一个层级** | 先定 Rank（见 [83.8](83.8-架构的定义与4R视图.md)），同图不跨层 | L0 业务全景图里画 Redis 主从 |
| **连线要有类型** | 同步调用 / 异步消息 / 数据依赖用不同线型 | 全部实线箭头，看不出哪条会阻塞 |
| **区块对齐优先于漂亮** | 为对齐可以调整方块长短，但**长短不代表重要度**；重要度用颜色表达 | 靠区块大小暗示业务量级，读者误读 |
| **图标代替文字区块（部署图）** | 服务器、机柜、云用图标 | 部署图写满「8 核 32G」文本框 |

## 为什么不直接用 4+1、TOGAF 或 C4

| 体系 | 为什么不能直接用 | 本库取舍 |
|---|---|---|
| **4+1 视图** | ① 面向单体系统设计，微服务下 Development view 画不出来；② 绑定 UML，表达力弱、不美观；③ 逻辑视图 / 开发视图 / 处理视图三者容易混淆 | 只借用「多视角」思想，落到六类图 |
| **TOGAF**（业务 / 数据 / 应用 / 技术架构） | 企业级架构方法，基本到 CTO 层级才用；与单个系统的设计图不是一回事 | 不采用 |
| **C4** | 表达力够、工具友好，但只解决「放大倍数」，不解决「给谁看」 | [83.1](83.1-C4模型.md) 用 C4 管缩放，本文管读者 |

> 一句话：**C4 管画多细，六类图管给谁看，4R 管这张图答什么**。三者叠加才是完整的视图体系。

## 一页自检

```text
出图前：
  [ ] 这张图给谁看（业务方 / 运维 / 开发 / 测试 / 评审）
  [ ] 类型选对了吗（业务 / 客户端前端 / 系统 / 应用 / 部署 / 序列）
  [ ] 层级定死了吗（Rank 是哪一级）

出图后：
  [ ] 颜色 ≤ 3 种，且每种颜色有语义
  [ ] 连线有类型，不是一团实线
  [ ] 复杂系统按子域拆图，没有「几百个应用一张图」
  [ ] 至少一张序列图覆盖核心场景的异常分支
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 一张图既画业务功能又画机房部署 | 两类读者都看不懂，评审跑偏 |
| 给业务方看系统架构图 | 对方只关心业务覆盖，图越细越无效 |
| 应用架构图把几百个应用塞进一张图 | 图看不清，等于没画（应按子域拆） |
| 颜色超过 3 种且无语义 | 读者花时间猜图例，关键信息被淹没 |
| 部署图用文字框写配置 | 缺少机房 / 网络拓扑直觉，运维无法据此规划 |
| 只画静态图，没有一张序列图 | 协作规则缺失，联调阶段才发现接口对不上 |
| 拿 C4 的容器图当应用架构图 | 容器 ≠ 可部署程序，发布单元与设计单元对不上 |

## 自检

**Q1** 老板要看「我们业务明年怎么打」，你该给哪张图？
▸ 答案：**业务架构图**。它画的是业务功能全景与状态（哪些在发展、哪些竞争激烈），正是业务决策需要的粒度；系统架构图对他既太细又无关。

**Q2** 应用架构图与系统架构图的区别是什么？
▸ 答案：系统架构图讲**逻辑角色与关系**；应用架构图讲**可部署发布的程序**（一个应用就是一个能独立发布运行的程序）。简单系统两者等价，复杂系统必须分开——运维按应用发布，开发按系统分工。

**Q3** 为什么部署图要用图标而不是文字区块？
▸ 答案：部署图回答的是「在哪个机房、几台机器、怎么组网」，图标（服务器、交换机、机柜）能让运维一眼看出拓扑与冗余；文字框只传递配置，丢失拓扑直觉。

**Q4** 六类图与 C4 是替代关系吗？
▸ 答案：不是。C4 管**缩放级别**（同一张图放大到多细），六类图管**读者视角**（不同人关心不同的东西）。实践中先用 C4 定层级，再用六类图选类型，最后用 4R 确认这张图答哪个问题。

**Q5** 一张图里颜色最多用几种？为什么？
▸ 答案：**3 种以内**。颜色是稀缺的视觉资源，每多一种就多一层图例负担；超过 3 种通常说明这张图想同时回答多个问题（该拆图，而不是加颜色）。

**Q6** 复杂系统的应用有几百个，怎么画？
▸ 答案：**按子域拆图**。先在系统架构图里画出子域边界，再对每个子域单独出应用架构图；一张图画完所有应用，信息密度会超过可读阈值。
