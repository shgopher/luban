# 81.3 支付：渠道、对账与资损防线

## 一句话

> 支付系统的取舍只有一句话：**用多少资损风险，换多低的成本与多高的成功率**——本例的答案是：**智能路由 + 准实时对账 + 预扣兜底**，代价是 3 套渠道适配与每天约 300 笔差异要处理。

> ⚠️ **数字口径**：本节是**合成案例**（笔数、费率、比例均为构造值），不是真实公司数据。机制不重讲：幂等见 [67.2](../../L4-组件与技术/67-交易与账务/67.2-幂等与防重.md)、对账见 [67.3](../../L4-组件与技术/67-交易与账务/67.3-对账与差异处理.md)、账务见 [67.4](../../L4-组件与技术/67-交易与账务/67.4-复式记账与账务模型.md)、资金安全见 [67.5](../../L4-组件与技术/67-交易与账务/67.5-资金安全与风控联动.md)。

## 规模前提卡

| 项 | 值 | 说明 |
|---|---|---|
| 日支付笔数 | 150 万 | 峰值 5000 TPS |
| 客单价 | 200 元 | 日 GMV 约 **3 亿** |
| 渠道 | 3 个 | 微信 / 支付宝 / 银联 |
| 综合成功率 | 98.7% | 1.3% 失败里有渠道原因、用户取消、风控拦截 |
| 渠道费率 | 0.6% | 日手续费约 **180 万** |
| 资损容忍 | **0.01%** | 日资损 ≤ **3 万**（约 150 笔 × 200 元） |
| 团队 | 15 人 | 有 2 人专职对账/资金 |

## 三个关键取舍

### 取舍一：单渠道还是智能路由

| 备选 | 成功率 | 费率 | 对账复杂度 | 结论 |
|---|---|---|---|---|
| 单渠道（只接一家） | 97.5% | 0.6% | 1 套 | ❌ 成功率低、被单家绑架 |
| **智能路由**（费率 + 成功率 + 限额） | **98.7%** | 0.55–0.6% | **3 套** | ✅ |
| 全渠道并行（同时发） | 99.0% | 0.6%+重复扣款风险 | 3 套 | ❌ 重复支付代价太高 |

选择理由：路由的价值不在“便宜 0.05%”，而在**成功率**——支付失败一次，损失的是整笔订单（200 元）而不是 0.6% 的手续费。按日 150 万笔算，成功率每提升 0.1% 就是 1500 笔订单、30 万 GMV。

**代价**：3 套渠道适配（签名、回调格式、对账文件各不相同），对账复杂度 ×3；路由规则本身也要版本化与灰度。

### 取舍二：对账是 T+1 还是准实时

| 备选 | 差异发现时间 | 计算成本 | 适用 |
|---|---|---|---|
| T+1 全量 | 次日 | 低 | 小额、低频 |
| **准实时（支付后 1–5 分钟）+ T+1 全量** | 分钟级 | **+20%** | ✅ 本例 |
| 纯实时逐笔 | 秒级 | 高（每笔都查渠道） | 仅高价值交易 |

选择“混合”：对**高价值/异常**交易在支付后几分钟主动查一次渠道状态，日终再做全量逐笔比对（[67.3](../../L4-组件与技术/67-交易与账务/67.3-对账与差异处理.md)）。原因：回调丢失在分钟级发现，能把“用户重复支付”挡在当天；全量比对兜住所有遗漏。

### 取舍三：强一致扣款还是预扣 + 对账兜底

| 备选 | 一致性 | 可用性 | 代价 |
|---|---|---|---|
| 强一致（2PC/锁） | 强 | 低（渠道不可控） | 渠道超时即失败，成功率下降 |
| **预扣 + 对账兜底** | 最终一致 | 高 | 每天约 **300 笔差异**要处理 |
| 只记录、事后补 | 弱 | 最高 | 资损不可控 |

选择预扣 + 对账。代价可以用数字说清：

```go
// 支付资损账：日交易额、手续费收入、资损容忍线，以及差异挂账的成本。
fmt.Printf("资损容忍=%.0f 元/日（%.1f 万）\n", lossBudget, lossBudget/1e4)
fmt.Printf("单笔资损 200 元 → 容忍 %.0f 笔/日；差异率 0.02%% ≈ %.0f 笔\n",
	lossBudget/200, orders*0.0002)
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
日 GMV=300000000 元（3.00 亿）
渠道手续费=1800000 元/日（180.0 万）
资损容忍=30000 元/日（3.0 万）
单笔资损 200 元 → 容忍 150 笔/日；差异率 0.02% ≈ 300 笔
```

关键读数：**差异 ≠ 资损**。每天约 300 笔差异，但资损容忍只有 150 笔/日——只要对账能在 T+1 内把 150 笔以上差异“补回来/冲正掉”，就不会突破容忍线。所以这里的取舍不是“要不要差异”，而是“**差异的处理能力**”：处理不过来，差异才变成资损。

## 失败模式

| 失败模式 | 触发条件 | 发现 | 退路 |
|---|---|---|---|
| **回调丢失（长款）** | 渠道回调失败、网络断 | 准实时查询/对账 | 按渠道流水补单（[67.3](../../L4-组件与技术/67-交易与账务/67.3-对账与差异处理.md)） |
| **重复退款** | 退款幂等没做、回调重复 | 对账金额不一致 | 幂等键 + 状态机（[67.2](../../L4-组件与技术/67-交易与账务/67.2-幂等与防重.md)） |
| **路由切错** | 规则误配、渠道限额变更 | 成功率骤降 | 一键回切默认路由 |
| **对账漏单** | 对账文件缺、键不唯一 | 差异率突增 | 换渠道账单源 + 逐笔核对 |
| **大额误杀** | 风控阈值过严（[68.6](../../L4-组件与技术/68-风控/68.6-误杀与漏杀的权衡.md)） | 支付成功率下降 | 放宽阈值 + 白名单 |

## 演进：三波

| 波 | 内容 | 退出标准 |
|---|---|---|
| W1 | 单渠道 + T+1 对账 | 日 50 万笔，差异率 < 0.05% |
| W2 | 双渠道 + 路由（按成功率） | 成功率 ≥ 98.5%，对账双源可核 |
| W3 | 智能路由（费率 + 成功率 + 限额）+ 准实时对账 | 成功率 ≥ 98.7%，T+1 差异清零 |

## 复盘：如果重来，改哪一处

> 最该改的是**对账的“处理能力”**而不是“发现能力”：本例前期把精力放在“更快发现差异”，但真正卡住的是“发现了没人处理”——每天 300 笔差异只有 2 个人工，挂账池越滚越大。正确做法是先定“T+1 清零”的流程与人力，再优化发现速度。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只接一家渠道 | 成功率被单家绑架，费率没有议价空间 |
| 全渠道并行发 | 重复扣款与退款的代价远高于成功率收益 |
| 只做 T+1 对账 | 回调丢失要等一天，用户当天重复支付 |
| 对账只对总额 | 差异被抹平，资损漏掉 |
| 差异只记录不处理 | 挂账池越滚越大，最后没人看 |
| 强一致扣款硬扛渠道超时 | 成功率下降，订单流失 |
| 路由规则无灰度 | 一次误配全量切错渠道 |

## 自检

**Q1** 为什么“智能路由”的主要收益是成功率，而不是费率？

▸ 答案：因为一次支付失败的损失是整笔订单（200 元），而费率差 0.05% 只值 0.1 元。按日 150 万笔算，成功率提升 0.1% 就是 1500 笔订单、30 万 GMV，远大于费率优化。路由的第一目标是“让支付成功”，第二才是“便宜”。

**Q2** 为什么不做“全渠道并行发”来提高成功率？

▸ 答案：因为并行的代价是重复扣款：两个渠道都成功，用户被扣两次，退款与客诉成本远高于成功率收益。支付是“只能成功一次”的操作，宁可失败重试，也不能重复。

**Q3** 每天 300 笔差异，为什么没突破 3 万的资损容忍？

▸ 答案：因为差异不等于资损：只要对账能在 T+1 内把差异补回或冲正，它就不会变成真金白银的损失。容忍线是 150 笔/日，处理能力必须 ≥300 笔/日才能兜住；处理不过来，差异才转化为资损。

**Q4** 准实时对账为什么只对“高价值/异常”交易做？

▸ 答案：因为逐笔实时查渠道的成本高（每笔一次外部调用），且会拖慢主链路。高价值交易漏一笔就是大损失，值得实时核；小额交易靠日终全量就够了。这是“风险 × 成本”的分层，不是技术能力问题。

**Q5** 这套方案最脆弱的环节是什么？

▸ 答案：**对账的处理能力**。发现差异靠系统，处理差异靠人；本例只有 2 个人工对账，差异率一涨就会积压。脆弱点不在技术，在“发现之后有没有人/流程把它闭环”。
