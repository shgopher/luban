# 85.3 脑裂与数据不一致

## 一句话

> 脑裂的根因不是“选主失败”，而是**旧主还活着、还能写**；数据不一致只是后果。止血顺序是**先 fencing 旧主，再谈谁的数据对**；合并按数据类型分三档，金额与库存永远人工。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “网络恢复，数据就一致了” | 心跳恢复 ≠ 数据一致；分叉已经写入，恢复只让两边的写都留下来 |
| “有 quorum 就不会脑裂” | quorum 防“选主冲突”，防不住“假死旧主仍能访问共享存储” |
| “LWW 能自动合并” | LWW 只是**静默丢掉一边**，冲突不可见，丢的可能是后写 |
| “脑裂很少见” | 任何“异步复制 + 自动切换”的组合都具备条件，差别只在触发概率 |

> ⚠️ **数字口径**：本节案例为合成案例。脑裂的机理与三道防线在主场：[18.6 脑裂与防护](../../L1-分布式原理/18-数据复制/18.6-脑裂与防护.md)；故障检测与切换见 [18.5 故障检测与切换](../../L1-分布式原理/18-数据复制/18.5-故障检测与切换.md)；租约见 [21.11 领导者租约](../../L1-分布式原理/21-共识与选主/21.11-领导者租约.md)。

## 案例卡：VIP 漂移了，旧主没死

| 时间 | 发生了什么 |
|---|---|
| 02:11:03 | 机房 A 与 B 之间网络抖动，主库 A 的半同步确认超时，**降级为异步后继续可写** |
| 02:11:14 | HA 组件判定 A 不可达，VIP 漂移到 B，B 升主（切换耗时 11 秒） |
| 02:11:15 | 应用侧连接池自动重连，**部分实例仍连着 A 的 IP**（配置写死，没走 VIP） |
| 02:11:15–02:11:57 | A 的主库进程还在，接受 1,836 条订单状态写入 |
| 02:11:57 | 网络恢复；A 发现自己“不是主”，但 42 秒的写已经落盘 |
| 02:12–02:40 | 双向复制冲突；214 条已发货订单被 A 的旧快照覆盖成“待支付” |
| 03:05 | 人工停写、按订单号逐笔核对、重放正确状态 |
| 04:24 | 恢复写入，S1 关闭 |

影响：214 单状态错误，37 单重复发货，资损约 ¥8.6 万；S1 持续 2 小时 13 分。

根因不是“HA 组件误判”，而是三个条件同时成立：**旧主还能写（半同步超时降级为异步）、应用绕过 VIP、没有 fencing**。任何一个不成立，都只是短暂不可用，不会变成数据事故。

## 为什么“假死”最危险

假死节点的心跳不通，但进程活着、存储可达。它不知道自己是旧主，仍按“我是主”处理写入；新主也在写。两边都认为自己在维护唯一真相。

> 🔑 quorum 决定“谁有资格当主”，**fencing 决定“旧主还能不能写”**。前者防选主冲突，后者防旧主复活；只做前者，等于只锁了门没换锁芯。

## 不一致的四种形态

| 形态 | 机理 | 检测信号 | 合并难度 |
|---|---|---|---|
| **双写分叉** | 两边都接受同一 key 的写 | 双主告警、版本冲突 | 取决于是否有版本/操作日志 |
| **旧值覆盖新值** | 旧主快照/延迟 binlog 回放覆盖新数据 | 状态“倒退”、更新时间倒退 | 高；需按操作日志重放 |
| **切换丢事务** | 异步复制 lag 内的事务未到新主 | 对账少单、流水缺失 | 中；可从源库/渠道补 |
| **应用层脏读** | 本地缓存/连接池仍指向旧主 | 部分实例读旧值，随机不一致 | 低；清缓存/重连即可 |

## 数字：RPO 不是“大概丢一点”

异步复制下，潜在丢失量 ≈ **复制 lag × 写入 TPS**。lag 1 秒、写入 5,000 TPS，切换瞬间最多有 **5,000 条**事务不在新主上；lag 10 秒就是 5 万条。半同步把 RPO 压到 0，代价是写延迟取决于最慢副本的 P99——这个代价要在选型时付，不是在事故时付。

## 止血：先让旧主写不进去

| 顺序 | 动作 | 判据 | 常见错误 |
|---|---|---|---|
| 1 | **确认双主**：两边都报主 / 双写检测 | 两个节点同时接受写 | 只看 HA 组件状态 |
| 2 | **fencing**：撤销租约/token、切存储路径、STONITH、改 VIP/DNS | 旧主写入被拒绝 | 只改 DNS，TTL 没到，应用还在写 |
| 3 | **停写**：全局或按分片 | 不再产生新分叉 | 只停新主，旧主还在收 |
| 4 | **只读降级** | 查询可用，写入排队/拒绝 | 读也停，扩大影响 |
| 5 | **定界**：圈出分区时间窗 + 受影响 key | 差异可枚举 | 按“最近 5 分钟”猜 |
| 6 | **合并/补偿** | 每笔有依据 | 直接 LWW |
| 7 | **恢复写**：小流量、校验、再全量 | 校验一致 | 一把全开 |

> 🔑 网络恢复后的第一动作不是“合并数据”，是**确认旧主已经写不进去**。否则你合并的同时，它还在制造新的分叉。

> ⚠️ **不是所有分区都要停写**：只读副本落后、没有写入分叉时，等复制追平即可；停写的判据是“两个节点都接受过同一 key 的写”。过度停写会把可用性事故扩大成业务停摆。

## 合并三档：能自动的、必须人工的、救不回来的

| 档 | 判据 | 例子 | 做法 |
|---|---|---|---|
| **可自动** | 有单调版本、幂等键，或结构可交换 | 计数、集合、带版本的状态机 | 版本大者赢；CRDT 合并（见 [25.6 CRDT (计数 / 集合 / 寄存器)](../../L1-分布式原理/25-并发、冲突与幂等/25.6-CRDT.md)） |
| **必须人工** | 金额、库存、订单状态、权益 | 支付、退款、发货 | 逐笔核对操作日志 + 业务规则，人工裁决 |
| **救不回来** | 无版本、无日志、已被覆盖 | 旧快照覆盖且无 binlog | 按业务重放/赔付，并记录损失 |

本案例 1,836 条里：可自动 1,402 条（有版本号），必须人工 434 条（涉及金额/发货），救不回来 0 条。434 条 × 3 分钟/条 ≈ 21.7 小时；4 人并行约 5.4 小时——这就是“没有版本号”的代价，它把技术问题变成了人力问题。

## 可运行：LWW 的“自动合并”是假象

模拟双主：A 的本地时钟快 5 秒，A 写 key 0–899，B 写 key 100–999。两种合并策略对比。

```go
package main

import "fmt"

type write struct {
	key int
	seq int // 真实发生顺序
	val string
	ts  int // 节点本地时钟（毫秒）
}

func main() {
	const keys = 1000
	var a, b []write

	// A（旧主）本地时钟快 5 秒；B（新主）时钟正常。
	// 分区期间两边都接受写入：A 写 key 0-899，B 写 key 100-999。
	for i := 0; i < 900; i++ {
		a = append(a, write{i, i, "A", 1005 + i%7})
	}
	for i := 100; i < 1000; i++ {
		b = append(b, write{i, 10000 + i, "B", 1000 + i%5})
	}

	// 合并策略一：LWW（按本地时间戳，大者赢）
	lww := map[int]write{}
	for _, w := range append(append([]write{}, a...), b...) {
		if old, ok := lww[w.key]; !ok || w.ts > old.ts {
			lww[w.key] = w
		}
	}

	// 冲突键 = 两边都写过的 key
	conflict := 0
	for i := 100; i < 900; i++ {
		conflict++
	}
	awin := 0
	for i := 100; i < 900; i++ {
		if lww[i].val == "A" { // B 的 seq 更大（后写），却被覆盖
			awin++
		}
	}
	lostLater := awin

	fmt.Printf("双主写入：A=%d 条，B=%d 条，键空间=%d\n", len(a), len(b), keys)
	fmt.Printf("冲突键（两边都写）：%d 个，占键空间 %.0f%%\n", conflict, float64(conflict)/keys*100)
	fmt.Printf("LWW 合并：冲突键中 %d 个判 A 赢（A 的时钟快 5 秒）\n", awin)
	fmt.Printf("LWW 静默丢弃「后写」：%d 条（B 的 seq 更大）\n", lostLater)
	fmt.Printf("可自动判定、无需人工的键：%d 个\n", keys-conflict)
	fmt.Printf("需要人工裁决的键：%d 个（金额/库存类不可自动取一个）\n", conflict)

	fmt.Println("\n== 三种合并策略对比 ==")
	fmt.Printf("%-14s %-10s %-12s %-10s\n", "策略", "冲突可见", "自动合并", "数据丢失")
	fmt.Printf("%-14s %-10s %-12s %-10s\n", "LWW(时间戳)", "否", "是", fmt.Sprintf("%d 条", lostLater))
	fmt.Printf("%-14s %-10s %-12s %-10s\n", "版本向量", "是", "仅可交换结构", "0（转人工）")
	fmt.Printf("%-14s %-10s %-12s %-10s\n", "Quorum+fencing", "不发生", "—", "0")
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
双主写入：A=900 条，B=900 条，键空间=1000
冲突键（两边都写）：800 个，占键空间 80%
LWW 合并：冲突键中 800 个判 A 赢（A 的时钟快 5 秒）
LWW 静默丢弃「后写」：800 条（B 的 seq 更大）
可自动判定、无需人工的键：200 个
需要人工裁决的键：800 个（金额/库存类不可自动取一个）

== 三种合并策略对比 ==
策略             冲突可见       自动合并         数据丢失      
LWW(时间戳)       否          是            800 条     
版本向量           是          仅可交换结构       0（转人工）    
Quorum+fencing 不发生        —            0         
```

读法：LWW 输出了“合并完成”，但 800 个冲突键里，**后写的全部被丢**。它没有报错、没有告警，这就是“静默不一致”的可怕之处：监控上一切正常，账上少了数据。

## 防线

| 类型 | 动作 | 防住什么 |
|---|---|---|
| prevent | quorum：没有多数派不许写 | 分区时少数派接受写 |
| prevent | fencing token / 租约：存储侧只认最新 token | 假死旧主继续写 |
| prevent | 应用只连 VIP/DNS，不写死 IP | 切换后仍有实例连旧主 |
| prevent | 半同步复制（按业务选） | 切换丢事务 |
| detect | 双主检测（两边都报主即告警） | 分叉持续扩大 |
| detect | 关键字段校验（行数、金额汇总、版本单调） | 旧值覆盖新值 |
| mitigate | 全局停写开关 + 只读降级 | 止血期间继续分叉 |
| mitigate | 按版本合并 / 人工裁决队列 | 自动合并丢数据 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 只做 quorum，不做 fencing | 假死旧主复活后继续写，分叉 |
| 切换后只改 DNS，不等 TTL | 应用继续连旧主 |
| 用 LWW 合并金额/库存 | 静默丢后写，账实不符 |
| 心跳恢复就宣布“可以合并” | 旧主仍在写，边合边分 |
| 没有版本号/操作日志 | 只能人工逐笔，恢复时间以人日计 |
| 2 节点集群无仲裁 | 1:1 平票，切换卡住或双主 |
| 切换演练只演“新主可用” | 不验证“旧主写不进去” |

## 自检

**Q1** 有 quorum 就一定不会脑裂吗？为什么还需要 fencing？

▸ 答案：不一定。quorum 保证同一时刻只有一个多数派能选主，但假死旧主可能仍能访问共享存储、仍持有写权限；quorum 拦不住它写。fencing 在存储侧只认最新 token/租约，旧主的写会被拒绝，这才是根治。

**Q2** 网络恢复后，第一件事是合并数据吗？

▸ 答案：不是。第一件事是确认旧主已经写不进去（fencing 生效），否则合并过程中它还在产生新的分叉。顺序是：确认双主 → fencing → 停写 → 定界 → 合并 → 恢复。

**Q3** LWW 为什么在金额/库存场景不可接受？

▸ 答案：LWW 按时间戳挑一个，冲突不可见，且时钟偏移会让“后写”输给“先写”。金额与库存需要业务规则裁决（谁对、差多少、怎么补），不能用一个时间戳决定，否则就是静默丢账。

**Q4** 214 条已发货订单被回退成“待支付”，怎么才能更早发现？

▸ 答案：三个检测：状态机不允许“已发货 → 待支付”的逆向迁移（写入侧直接拒绝）；关键字段版本单调校验（更新时间/版本号倒退即告警）；分钟级抽样对账（已发货订单数与发货系统比对）。

**Q5** 半同步能消灭脑裂吗？

▸ 答案：不能。半同步降低 RPO（切换丢事务），但不阻止旧主在分区期间接受写。脑裂要靠 quorum + fencing + 应用侧不绕过 VIP 一起防；半同步只是减少“切换丢数据”这一种后果。
