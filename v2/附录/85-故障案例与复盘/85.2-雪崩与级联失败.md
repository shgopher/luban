# 85.2 雪崩与级联失败

## 一句话

> 级联失败不是“某个服务挂了”，而是**重试、超时、共享资源三者把局部故障放大成全局**；止血的关键是切断放大链，而不是加机器。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “雪崩是流量太大” | 多数雪崩的入口流量并没有涨，涨的是**被放大后的下游流量** |
| “加机器就好了” | 流量被放大 81 倍时，扩容追不上；瓶颈还常在连接池、线程池，不在 CPU |
| “超时设长一点更稳” | 超时叠加让上游先耗尽线程，下游还在做已经没人要的工作 |
| “重试提高成功率” | 下游故障时，重试是**自己发起的 DDoS**，把 5% 的失败放大成 100% 的不可用 |

> ⚠️ **数字口径**：本节案例为合成案例。重试、超时、熔断的机制在主场：见 [35.5 超时重试与退避](../../L3-质量属性/35-可用性/35.5-超时重试与退避.md)、[35.6 熔断与降级](../../L3-质量属性/35-可用性/35.6-熔断与降级.md)、[35.7 限流](../../L3-质量属性/35-可用性/35.7-限流.md)、[35.8 故障隔离](../../L3-质量属性/35-可用性/35.8-故障隔离.md)。

## 案例卡：库存服务慢了 2 秒，详情页全挂

| 时间 | 发生了什么 |
|---|---|
| 14:02 | 库存服务一次慢查询，P99 从 20ms 涨到 **2s**，错误率 5% |
| 14:03 | 详情页对库存的调用每层重试 **2 次**（共 3 次尝试），调用深度 4 层 |
| 14:04 | 入口 3,000 QPS × 81 ≈ **24.3 万 QPS** 打到库存服务；库存服务线程池打满 |
| 14:05 | 详情页线程池（200）被等待库存的请求占满，开始拒绝所有请求 |
| 14:07 | 购物车、订单详情也调详情页，级联到交易链路 |
| 14:12 | 关闭重试 + 详情页对库存降级（返回缓存价/库存），错误率回落 |
| 14:44 | 库存慢查询下线，全链路恢复 |

影响：详情页 42 分钟不可用，下单量下降 18%，S1。

关键点：库存服务只慢了 20 倍，入口流量没变，但**重试把 3,000 QPS 放大成 24.3 万 QPS**。这不是容量问题，是放大倍数问题。

## 放大公式：先算倍数，再谈扩容

每层重试 `r` 次（含首次共 `r+1` 次尝试），调用深度 `d` 层，入口放大倍数为：

```text
放大倍数 = (r + 1) ^ d
```

| 每层重试 | 深度 2 | 深度 4 | 深度 6 |
|---|---|---|---|
| 0 次 | 1× | 1× | 1× |
| 1 次 | 4× | 16× | 64× |
| 2 次 | 9× | **81×** | 729× |
| 3 次 | 16× | 256× | 4,096× |

深度 4、每层重试 2 次就是 81 倍。这个数字必须在设计时算出来，而不是在故障时从监控上“发现”。

## 四类放大器

| 放大器 | 机理 | 现场信号 |
|---|---|---|
| **重试风暴** | 失败 → 重试 → 更多失败 → 更多重试 | 入口 QPS 平稳，下游 QPS 暴涨 |
| **超时叠加** | 每层超时 1s，4 层最坏 4s，客户端 3s 已超时并重试 | 客户端超时率上升，下游仍在执行 |
| **共享池** | 一个下游慢，占满所有请求共用的线程池/连接池 | 自身 CPU 低，池等待队列高 |
| **缓存回源** | 一批 key 同时失效或缓存层故障，请求全打到 DB | 缓存命中率骤降，DB QPS 翻倍（见 [41.3 缓存穿透 / 击穿 / 雪崩](../../L4-组件与技术/41-缓存/41.3-缓存穿透-击穿-雪崩.md)） |

## 超时预算：每层超时必须小于上游剩余时间

| 深度 | 每层超时 | 最坏耗时 | 客户端 3s 的结局 |
|---|---|---|---|
| 2 | 1s | 2,000ms | 预算内 |
| 3 | 1s | 3,000ms | 刚好卡满 |
| 4 | 1s | 4,000ms | **客户端已超时，下游还在干活** |
| 6 | 1s | 6,000ms | 大量无效工作 + 重试 |

规则：`子调用超时 ≤ 上游剩余预算 ÷ (1 + 重试次数)`；工程上常用“每层取上游超时的 60%”，给序列化、排队、网络留余量。超时预算不是配置项，是**调用链契约**。

## 止血：先减少请求，再增加容量

| 顺序 | 动作 | 作用 | 注意 |
|---|---|---|---|
| 1 | **关重试 / 降重试预算** | 立刻削掉放大倍数 | 要能热更新，不能靠发版 |
| 2 | **降级非核心** | 详情页的推荐、评价、库存精确值可降 | 降级要返回“可用的旧值/默认值”，不是报错 |
| 3 | **入口限流** | 把总量压到下游接得住的量 | 按用户/租户分级，别一刀切 |
| 4 | **熔断下游** | 下游故障时快速失败，保护自身线程 | 半开探测要限流（见 [35.6 熔断与降级](../../L3-质量属性/35-可用性/35.6-熔断与降级.md)） |
| 5 | **隔离资源** | 给慢依赖独立线程池/连接池 | 隔离舱大小按“最坏情况”算 |
| 6 | **扩容** | 最后手段 | 放大 81 倍时，扩容只是给放大器加燃料 |

> 🔑 级联故障的第一动作永远是**减少请求**（关重试、降级、限流），不是加机器。加机器会让下游更快被打满，还会延长恢复时间。

> ⚠️ **不是所有调用都该重试**：只读、幂等、无副作用的查询可以重试；支付、扣库存这类写操作默认不重试，除非有幂等键与去重表。把“重试”当默认配置，是把放大器装进调用链。

## 可运行：重试放大与超时预算

```go
package main

import "fmt"

// 每层重试 r 次（含首次共 r+1 次尝试），调用深度 d 层
func amplification(r, d int) int {
	n := 1
	for i := 0; i < d; i++ {
		n *= r + 1
	}
	return n
}

func main() {
	fmt.Println("== 重试放大：入口 1000 QPS 时，最底层要承接多少 ==")
	fmt.Printf("%-8s %-6s %-10s %-12s\n", "重试次数", "深度", "放大倍数", "底层QPS")
	for _, r := range []int{0, 1, 2, 3} {
		for _, d := range []int{2, 4} {
			a := amplification(r, d)
			fmt.Printf("%-8d %-6d %-10d %-12d\n", r, d, a, 1000*a)
		}
	}

	fmt.Println("\n== 超时预算：客户端 3s，每层超时 1s ==")
	const client, perLayer = 3000, 1000
	for _, d := range []int{2, 3, 4, 6} {
		worst := d * perLayer
		verdict := "预算内"
		if worst > client {
			verdict = "客户端已超时，下游还在干活"
		}
		fmt.Printf("深度 %d：最坏耗时 %dms，%s\n", d, worst, verdict)
	}

	fmt.Println("\n== 相同的重试，加不加预算，底层压力差多少 ==")
	for _, r := range []int{2, 3} {
		raw := amplification(r, 4) * 1000
		budgeted := 1000 + 1000/10*1 // 只允许 10% 的请求重试一次
		fmt.Printf("重试 %d 次：无预算 %d QPS → 10%% 重试预算 %d QPS（%.0f 倍差）\n",
			r, raw, budgeted, float64(raw)/float64(budgeted))
	}
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text

0        2      1          1000        
0        4      1          1000        
1        2      4          4000        
1        4      16         16000       
2        2      9          9000        
2        4      81         81000       
3        2      16         16000       
3        4      256        256000      

== 超时预算：客户端 3s，每层超时 1s ==
深度 2：最坏耗时 2000ms，预算内
深度 3：最坏耗时 3000ms，预算内
深度 4：最坏耗时 4000ms，客户端已超时，下游还在干活

重试 2 次：无预算 81000 QPS → 10% 重试预算 1100 QPS（74 倍差）
重试 3 次：无预算 256000 QPS → 10% 重试预算 1100 QPS（233 倍差）
```

读法：同一套重试策略，**加不加“重试预算”差 74–233 倍**。重试预算的做法是给重试单独一个令牌桶，按请求量的 10% 放行；拿不到令牌就直接失败，让上游走降级，而不是继续排队。

## 诊断：是不是级联，看这四个信号

| 信号 | 指向 |
|---|---|
| 入口 QPS 平稳，下游 QPS 暴涨 | 重试放大 |
| 自身 CPU 低，线程池/连接池等待高 | 等待型级联，不是算力不足 |
| 只有某条调用链慢，其他链路正常 | 单依赖故障；看隔离是否生效 |
| 错误率随并发上升，重启后短暂恢复 | 池耗尽或队列积压；扩容可能加重 |

> ⚠️ 最后一行最容易误判：重启能恢复，说明“状态”在进程里（队列、连接、缓存），而不在容量里。此时扩容只是把同样的状态复制更多份。

## 防线：把放大倍数关进笼子

| 类型 | 动作 | 关键参数 |
|---|---|---|
| prevent | 重试预算（令牌桶） | 重试量 ≤ 请求量的 10% |
| prevent | 分层超时预算 | 子超时 ≤ 父剩余 × 0.6 |
| prevent | 退避 + 抖动 | 指数退避，抖动 0–50% |
| prevent | 隔离舱 | 每个依赖独立池；池满快速失败 |
| detect | 下游 QPS / 入口 QPS 比值 | 比值 > 3 持续 1 分钟即告警 |
| detect | 池等待队列、超时率 | 队列 > 0 持续上升 |
| mitigate | 熔断 + 降级 | 半开只放 1 个探测 |
| mitigate | 入口限流 / 负载丢弃 | 按优先级丢，保核心链路 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 所有 RPC 统一重试 3 次 | 深度 4 层时放大 256 倍 |
| 重试固定间隔、无抖动 | 重试请求同步到达，形成尖峰 |
| 超时从内到外一样大 | 上游先超时，下游做无用功 |
| 所有依赖共用一个线程池 | 一个慢依赖拖垮全部接口 |
| 熔断后立刻全量恢复 | 半开探测把刚恢复的下游再打挂 |
| 故障时先扩容 | 放大器被喂饱，恢复更慢 |
| 只压测单接口，不压测调用链 | 放大倍数与超时叠加测不出来 |

## 自检

**Q1** 入口 QPS 没涨，库存服务 QPS 涨了 20 倍，先查什么？

▸ 答案：先查重试次数与超时预算，而不是扩容。入口平稳、下游暴涨是重试放大的典型信号；先关重试或加重试预算，再定位下游为什么失败。

**Q2** 为什么“把超时调大”会让雪崩更糟？

▸ 答案：超时越大，上游线程被占用越久，队列更容易堆满；同时上游先到自己的超时后会重试，下游还在执行已经没人要的请求，形成“无效工作 + 重试”双重放大。

**Q3** 熔断和限流在级联里各管哪一段？

▸ 答案：限流管入口总量，防止超过系统承载；熔断管下游故障时的快速失败，保护自身线程与连接。缺一个都不行：只有限流，下游慢时仍会被拖死；只有熔断，入口洪峰仍会打满自身。

**Q4** 机器 CPU 只有 30%，但请求全部超时，可能是什么问题？

▸ 答案：等待型级联。线程池或连接池被慢下游占满，CPU 没有活干；要看池的等待队列、活跃连接数、下游 P99，而不是看 CPU。

**Q5** 重试预算 10% 具体怎么落地？

▸ 答案：给重试单独一个令牌桶，按正常请求量的 10% 发放令牌；重试前先取令牌，取不到就直接失败并走降级。配合指数退避 + 抖动，禁止固定间隔重试。
