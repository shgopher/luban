# 85.5 容量与成本事故

## 一句话

> 容量事故是**流量超过设计假设，且扩容追不上**；成本事故是**资源在没有产出的路径上持续燃烧**。两者同一个根：容量模型没有 owner，只有账单。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “容量事故 = 流量太大” | 多数是**瓶颈先于总量**到达：连接池、单分片、热点 key、锁 |
| “云上可以无限扩容” | 扩容有时间常数（镜像、预热、审批、配额），冷启动还会反噬 |
| “成本是财务的事” | 单位成本（元/万请求、元/订单）是架构指标，不是报销指标 |
| “降本 = 降配置” | 降错地方会把成本事故变成容量事故，付出的更多 |

> ⚠️ **数字口径**：本节案例与测算均为合成，单价、QPS、TB/天为构造值。容量模型、冗余系数、压测的机制在主场：[57.1 压测方法论](../../L5-工程效能/57-容量与成本治理/57.1-压测方法论.md)、[57.2 容量模型](../../L5-工程效能/57-容量与成本治理/57.2-容量模型.md)、[57.3 冗余系数](../../L5-工程效能/57-容量与成本治理/57.3-冗余系数.md)、[39.2 容量规划](../../L3-质量属性/39-成本/39.2-容量规划.md)。

## 案例 A：扩容把数据库打挂了

| 时间 | 发生了什么 |
|---|---|
| 19:58 | 运营活动开始，流量 10 分钟内爬到日常的 3 倍（8 万 → 24 万 QPS） |
| 20:00 | 应用 CPU 到 70%，值班按“CPU 高就扩容”，把 20 实例扩到 40 |
| 20:03 | 应用总连接数从 20×50=1,000 涨到 40×50=2,000；DB `max_connections=800` |
| 20:04 | 新实例连接被拒，启动探针失败，反复重启；旧实例也开始报“too many connections” |
| 20:06 | 错误率 50%，下单失败；活动页仍可浏览（缓存命中） |
| 20:14 | 定位到 DB 连接上限，回滚扩容、把连接池降到 20、开启入口限流 |
| 20:26 | 连接数回落，业务恢复 |

影响：28 分钟，50% 下单失败，S1。

关键点：**瓶颈是 DB 连接数，不是应用 CPU**。应用 CPU 70% 只是症状；扩容应用等于给 DB 连接上限加压。如果 20:00 先算一遍“20 实例 × 50 连接 = 1,000 > 800”，这起事故不会发生。

## 案例 B：一条 debug 日志，每月多花 1.4 万

| 时间 | 发生了什么 |
|---|---|
| M1 | 排障时给订单服务加了一条 `log.Debugf` 打印完整请求体，上线后忘了关 |
| M1–M3 | 日志量从 2 TB/天涨到 2.8 TB/天；保留 90 天，无人看账单 |
| M4 | 财务对账发现可观测性成本环比 +38%，追溯到日志量 |
| M4 | 改为 10% 采样 + 30 天热保留，日志成本从 ¥5.2 万/月降到 ¥1.2 万/月 |

按 ¥0.2/GB/月估算：2.8 TB/天 × 90 天 ≈ 252 TB → **¥5.16 万/月**；2 TB/天 × 90 天 = 180 TB → ¥3.69 万/月。每月多花约 **¥1.47 万**，三个月合计约 ¥4.4 万。

> 🔑 成本事故的共同特征：**没有单点故障，只有复利**。它不会告警，只会出现在账单上；等你发现时，已经付了几个月。

## 容量：三张表必须同时存在

| 表 | 内容 | 没有它会怎样 |
|---|---|---|
| **设计容量** | 各层 QPS、连接数、存储、单分片上限 | 不知道瓶颈在哪，扩容方向错 |
| **冗余系数** | 峰值 × (1 + 余量) | 要么天天打满，要么长期闲置 |
| **扩容速度** | 从决定到可承载的时间（镜像/预热/审批） | 以为能扩，实际来不及 |

事故判据只有一句：**打满时间 < 扩容时间 → 必出事故**。

## 冗余系数：不是越高越好，是“扩容时间 × 增长率”的函数

| 冗余 | 机器数 | 月成本（元） | 每万 QPS 成本 | 余量耗尽（月，20% 月增长） |
|---|---|---|---|---|
| 20% | 80 | 52,560 | 6,570 | 1.0 |
| 30% | 87 | 57,159 | 7,145 | 1.4 |
| 50% | 100 | 65,700 | 8,212 | 2.2 |
| 100% | 134 | 88,038 | 11,005 | 3.8 |

从 30% 提到 50%，月成本 +15%，余量寿命从 1.4 个月延到 2.2 个月。增长快的业务买的是“扩容来不及”的保险；稳定期业务应选低冗余 + 弹性伸缩，把余量交给云。

## 成本：四类泄漏，各有各的检测信号

| 类型 | 典型形态 | 检测信号 | 治理动作 |
|---|---|---|---|
| **闲置** | 僵尸实例、低利用率、忘删的测试环境 | CPU/内存 P95 < 10% 持续 7 天 | 关停/降规格；打标签追 owner |
| **数据膨胀** | 日志全量、副本过多、快照不删、索引冗余 | 存储月增 > 业务量增速 | 采样、TTL、分层、生命周期 |
| **流量** | 跨区调用、NAT 回程、CDN 回源 | 流量费占比异常 | 就近接入、连接复用、回源率治理 |
| **规格错配** | CPU 型跑内存型负载、大规格跑低负载 | 利用率与规格长期不匹配 | 换规格族；按 P95 选型 |

## 可运行：容量、冗余与日志成本

```go
package main

import (
	"fmt"
	"math"
)

func main() {
	const peak = 80000.0   // 峰值 QPS
	const perNode = 1200.0 // 单实例安全承载 QPS
	const nodeHour = 0.9   // 元/小时
	const grow = 0.20      // 月流量增长

	fmt.Println("== 冗余系数 → 机器数 / 月成本 / 余量耗尽时间 ==")
	fmt.Printf("%-8s %-10s %-12s %-12s %-10s\n", "冗余", "机器数", "月成本(元)", "每万QPS成本", "耗尽(月)")
	for _, h := range []float64{0.2, 0.3, 0.5, 1.0} {
		n := int(math.Ceil(peak * (1 + h) / perNode))
		cost := float64(n) * nodeHour * 730
		fmt.Printf("%-8s %-10d %-12.0f %-12.0f %-10.1f\n",
			fmt.Sprintf("%.0f%%", h*100), n, cost, cost/(peak/10000), math.Log(1+h)/math.Log(1+grow))
	}

	fmt.Println("\n== 扩容速度 vs 故障窗口 ==")
	const scaleOutMin = 4.0
	for _, surge := range []float64{1.5, 3.0} {
		// 冗余 30%：流量涨到 1.3 倍即打满；假设 10 分钟内线性爬升到 surge 倍
		headroom := 0.3
		timeToFull := headroom / (surge - 1) * 10
		verdict := "扩得动"
		if scaleOutMin > timeToFull {
			verdict = "扩不动"
		}
		fmt.Printf("流量跳到 %.1f 倍：%.1f 分钟打满，扩容需 %.0f 分钟 → %s\n",
			surge, timeToFull, scaleOutMin, verdict)
	}

	fmt.Println("\n== 日志成本：采样率 × 保留天数 ==")
	const tbPerDay = 2.0   // 全量日志每天 TB
	const pricePerGB = 0.2 // 元/GB/月
	for _, c := range []struct {
		name   string
		sample float64
		days   int
	}{
		{"全量 + 90 天", 1.0, 90},
		{"全量 + 30 天", 1.0, 30},
		{"10% 采样 + 30 天", 0.1, 30},
	} {
		tb := tbPerDay * c.sample * float64(c.days)
		fmt.Printf("%-18s %6.1f TB → ¥%.0f/月\n", c.name, tb, tb*1024*pricePerGB)
	}
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text

50%      100        65700        8212         2.2
```

读法：第一张表说明“冗余是花钱买时间”；第二张表说明“流量涨 3 倍时，1.5 分钟就打满，扩容要 4 分钟，扩不动”；第三张表说明“成本对采样率与保留天数都是线性的，两个乘起来就是 90% 的降幅空间”。**先算，再改。**

## 防线

| 类型 | 动作 | 关键参数 |
|---|---|---|
| prevent | 容量模型（每层瓶颈清单） | 季度更新，有 owner |
| prevent | 压测覆盖峰值 × 1.5 | 测全链路与瓶颈层，不只测单接口 |
| prevent | 连接池总量 ≤ DB 上限 × 0.8 | 应用实例数 × 单实例池 ≤ 上限 |
| prevent | 扩容预演 | 记录从决定到可承载的真实时间 |
| prevent | 预算与配额 | 按团队/服务设预算，超 80% 告警 |
| detect | 燃烧率告警 | 1 小时燃烧 > 月度预算的 5% |
| detect | 单位成本看板 | 元/万请求、元/订单，按周看趋势 |
| mitigate | 入口限流 / 降级非核心 | 保核心链路与付费用户 |
| mitigate | 存储分层 / TTL / 采样 | 日志、快照、冷数据 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 只看 CPU 扩容 | 瓶颈在连接池/DB 时，扩容加重故障 |
| 不建容量模型，只靠监控 | 到达瓶颈才知道，扩容来不及 |
| 压测只压单接口 | 全链路瓶颈（连接数、锁、下游）测不出 |
| 把冗余拉到 100% 求安心 | 长期成本翻倍，增长慢时全是浪费 |
| 降本一刀切降配置 | 把成本事故换成容量事故 |
| 日志全量 + 长保留，不设 TTL | 存储成本按月复利增长 |
| 成本只看总账单 | 看不到是哪个服务、哪类资源在涨 |
| 没有 owner 的容量假设 | 没人对“能扛多少”负责 |

## 自检

**Q1** 流量涨到 3 倍，扩容后反而更糟，为什么？

▸ 答案：瓶颈可能不在应用 CPU，而在 DB 连接数、单分片、热点 key 或锁。扩容应用会按“实例数 × 单实例连接池”放大对瓶颈层的压力，让故障更快到来。先定位瓶颈层，再决定扩哪一层。

**Q2** 冗余系数 30% 与 50%，怎么选？

▸ 答案：看“打满时间 vs 扩容时间”。若月增长 20%、扩容要 4 分钟、审批要 1 天，30% 只能撑 1.4 个月；增长快或扩容慢就选 50% 甚至更高。稳定期业务选低冗余 + 弹性，把余量交给云。

**Q3** 日志成本怎么降最有效？

▸ 答案：采样率与保留天数两个乘数一起降。全量 90 天 → 10% 采样 30 天，存储量降到 1/30（本例 180 TB → 6 TB，成本降 96.7%）；同时把冷日志转对象存储分层，热日志只留 7 天。

**Q4** 容量事故和成本事故为什么会互相转化？

▸ 答案：为了降本而降配置（连接池、副本、缓存、冗余）会削弱容量；为了扛峰值而长期保留高冗余会推高成本。两者要用同一套容量模型与单位成本指标决策，而不是两个团队各自优化。

**Q5** 怎么证明“扩容追不上”？

▸ 答案：记录两个数：当前余量能撑多少分钟（余量 ÷ 流量爬升速率），以及从决定扩容到新实例可承载的真实时间（含镜像、预热、审批）。前者小于后者，就是扩不动；这个结论要用演练验证，不是拍脑袋。
