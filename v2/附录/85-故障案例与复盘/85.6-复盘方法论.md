# 85.6 复盘方法论

## 一句话

> 复盘不是“写一份文档”，而是**把一次事故变成可验证的组织记忆**；方法的核心只有三件——证据链、贡献因素、能关闭的行动项。无指责的语言与行动项标准见 [56.6 无指责复盘](../../L5-工程效能/56-稳定性工程/56.6-无指责复盘.md)，本节补“何时复盘、谁组织、怎么跨团队、怎么聚类”。

## 何时必须复盘

| 触发条件 | 复盘类型 | 启动时限 | 产出深度 |
|---|---|---|---|
| S1 / S2 事故 | 单事故复盘 | ≤ 5 个工作日 | 完整报告 + 行动项 |
| S3，或同类问题 6 个月内复发 | 单事故 + 主题复盘 | ≤ 10 个工作日 | 完整报告 + 聚类 |
| 混沌实验/故障演练暴露缺陷 | 演练复盘 | ≤ 5 个工作日 | 场景、预期、实际、改进 |
| **Near miss（差一点出事）** | 轻量复盘 | ≤ 10 个工作日 | 1 页：条件、侥幸点、行动项 |
| 跨团队/跨供应商事故 | 联合复盘 | ≤ 5 个工作日 | 共享时间线 + 边界事实 |
| 变更被门禁拦下（本会出事） | 轻量复盘 | 随迭代 | 1 条：门禁是否可复用 |

> 🔑 **Near miss 是最便宜的复盘对象**：损失为零，信息完整。只复盘“已经出事”的组织，等于等别人替你付学费。

## 五种复盘，别用同一种模板

| 类型 | 输入 | 主持 | 产出 | 常见失败 |
|---|---|---|---|---|
| **单事故** | 时间线、变更、告警、日志 | facilitator（非当事团队） | 贡献因素 + 3–5 行动项 | 写成流水账 |
| **主题** | 多起事故的复盘报告 | 领域负责人 + facilitator | 共性因素、系统性修复 | 变成“再列一遍行动项” |
| **横向** | 同类系统/其他团队的事故 | 架构师/平台团队 | 检查清单、规范更新 | 只分享故事，不改自己系统 |
| **演练** | 演练方案、注入记录、观测数据 | 演练负责人 | 预案有效性、检测缺口 | 只评“演练成功/失败” |
| **供应商** | 供应商 RCA、合同 SLA | 采购 + 技术 | 责任边界、替代方案 | 接受“机房断电”式结论 |

## 谁组织：角色与禁区

| 角色 | 职责 | 禁区 |
|---|---|---|
| **facilitator** | 守流程、守无指责、逼出证据 | 不能是事故当事人；不能同时当 IC |
| **IC（事故指挥）** | 提供决策时间线与取舍 | 不主导归因（会为自己的决策辩护） |
| **Scribe** | 记录时间线、事实、未决问题 | 不参与辩论 |
| **SME** | 解释系统行为与数据 | 不替别的团队下结论 |
| **行动项 owner** | 现场认领、给期限与验证方式 | 不接受“相关同学” |
| **管理层** | 听结论、批资源、改制度 | 不主导归因、不追问“谁” |

跨团队复盘的三个硬要求：**统一时钟**（全部转 UTC+8 并标注来源）、**边界事实**（每个团队只陈述自己系统内发生了什么）、**接口契约**（跨边界的请求/响应/超时是谁配的）。禁止“我们这边没问题”——它不是事实，是立场。

## 证据链：事实、推断、未知分三栏

| 证据 | 能回答 | 不能回答 |
|---|---|---|
| 变更记录（代码/配置/DB/证书） | 什么被改了、何时、谁批的 | 为什么当时认为安全 |
| 告警与 on-call 记录 | 何时发现、谁认领、升级了几次 | 为什么没更早发现 |
| Trace / 日志 | 调用链在哪断、错误码分布 | 当事人看到了什么 |
| 监控指标 | 影响面、持续时间、基线偏移 | 业务为什么这样决策 |
| 人证（当事人/值班） | 当时的信息与判断依据 | 精确时间（记忆会漂移） |

时间线精确到分钟，并标注“事实 / 推断 / 未知”。未知不是耻辱，**把未知写成已知才是**。日志告诉你“发生了什么”，人证告诉你“为什么当时这么做”，两者缺一不可。

## 因果分析：五种方法，按场景选

| 方法 | 适合 | 不适合 | 产出 |
|---|---|---|---|
| **5 Whys** | 单链、快速定位 | 多因素、跨团队 | 一条因果链 |
| **鱼骨图** | 因素分类（人/机/料/法/环） | 需要排序时 | 因素清单 |
| **时间线 + 贡献因素** | 复杂系统（推荐） | 缺好 facilitator 时 | 触发 + 放大器 + 检测缺口 |
| **反事实分析** | 验证行动项是否真能阻止 | 单因素假设 | “如果当时有 X，是否不发生” |
| **FTA 故障树** | 有明确顶事件、可量化 | 时间紧、数据少 | 最小割集 |

> ⚠️ 5 Whys 的最大陷阱：问到“人没注意”就停。正确问法是继续往下——**什么让“没注意”成为可能**（告警太吵、界面默认值危险、检查单没有这一项）。停在“人”，行动项就只剩“加强意识”。5 Whys 的具体问法与四层追问（获知/处理/开发/团队）见 [56.6 无指责复盘](../../L5-工程效能/56-稳定性工程/56.6-无指责复盘.md)，本节只讲“什么时候该换一种方法”。

复杂系统很少有单一根因。Cook 在《How Complex Systems Fail》(1998) 里的判断是：安全来自多层防御，事故是**多层防御同时失效**。所以复盘的产出应是“哪些防御同时失效、各被什么条件击穿”，而不是一条根因。

## 从个案到组织学习：聚类，而不是堆报告

单起复盘的行动项，通常只修“这一次”。把多起事故放在一起按三类因素聚类，才能看到系统性缺口：

- **触发**：什么条件启动了故障（配置错误、依赖变更、流量突增）。
- **放大器**：什么让影响变大（重试、共享池、无隔离、缓存回源）。
- **检测缺口**：为什么发现晚（只看 CPU、告警路由错、对账 T+1）。

聚类之后做三件事：把共性因素写进 **runbook / 发布检查单 / 架构评审清单**；把可测的写成**回归用例或混沌实验**（见 [56.2 故障演练](../../L5-工程效能/56-稳定性工程/56.2-故障演练.md)、[53.10 回归测试与缺陷管理](../../L5-工程效能/53-测试与质量保障/53.10-回归测试与缺陷管理.md)）；把需要长期投入的并入技术债（见 [58.2 技术债管理](../../L5-工程效能/58-架构治理/58.2-技术债管理.md)）。

## 可运行：8 起事故的贡献因素聚类

```go
package main

import (
	"fmt"
	"sort"
)

type incident struct {
	id      string
	factors []string
}

func main() {
	// 8 起合成事故的贡献因素（不是根因，是可修复的条件）
	incs := []incident{
		{"INC-01", []string{"无幂等键", "重试放大", "对账T+1"}},
		{"INC-02", []string{"无幂等键", "回调乱序", "对账T+1"}},
		{"INC-03", []string{"重试放大", "线程池共享", "无熔断"}},
		{"INC-04", []string{"重试放大", "超时预算缺失", "无熔断"}},
		{"INC-05", []string{"配置无校验", "发布无灰度", "告警只看CPU"}},
		{"INC-06", []string{"配置无校验", "发布无灰度", "回滚未演练"}},
		{"INC-07", []string{"无幂等键", "缓存与DB双写", "对账T+1"}},
		{"INC-08", []string{"超时预算缺失", "线程池共享", "无熔断"}},
	}

	freq := map[string]int{}
	pair := map[string]int{}
	for _, in := range incs {
		for _, f := range in.factors {
			freq[f]++
		}
		for i := 0; i < len(in.factors); i++ {
			for j := i + 1; j < len(in.factors); j++ {
				a, b := in.factors[i], in.factors[j]
				if a > b {
					a, b = b, a
				}
				pair[a+" + "+b]++
			}
		}
	}

	rank := func(m map[string]int) []string {
		out := make([]string, 0, len(m))
		for k := range m {
			out = append(out, k)
		}
		sort.Slice(out, func(i, j int) bool {
			if m[out[i]] != m[out[j]] {
				return m[out[i]] > m[out[j]]
			}
			return out[i] < out[j]
		})
		return out
	}

	fmt.Printf("事故数：%d，去重后的贡献因素：%d 个\n\n", len(incs), len(freq))
	fmt.Println("== 因素排序（出现在几起事故里） ==")
	for _, f := range rank(freq) {
		fmt.Printf("%-14s %d/%d\n", f, freq[f], len(incs))
	}
	fmt.Println("\n== 共同出现的因素对（一起修才有效） ==")
	for _, p := range rank(pair) {
		if pair[p] >= 2 {
			fmt.Printf("%-32s %d 起\n", p, pair[p])
		}
	}

	fmt.Println("\n== 复发判断 ==")
	rec := 0
	for _, f := range freq {
		if f >= 2 {
			rec++
		}
	}
	fmt.Printf("出现 ≥2 次的贡献因素：%d 个；只修单起事故，这类因素会再发\n", rec)
	fmt.Printf("最大单因素覆盖率：%.0f%%（%d/%d）\n",
		float64(freq[rank(freq)[0]])/float64(len(incs))*100, freq[rank(freq)[0]], len(incs))
}
```

## 五条故障链放在一起看

把这五条合成案例并排看（样本是构造的，不构成统计结论）：

| 案例 | 触发 | 放大器 | 检测缺口 | 最贵的修复 |
|---|---|---|---|---|
| [85.1 超卖与资损](85.1-超卖与资损.md) | 释放任务不看订单状态 | 每 5 分钟重复释放 | 对账 T+1 | 状态机 + 幂等 |
| [85.2 雪崩与级联失败](85.2-雪崩与级联失败.md) | 库存慢查询 | 重试 81 倍 | 只看入口 QPS | 重试预算 + 熔断 |
| [85.3 脑裂与数据不一致](85.3-脑裂与数据不一致.md) | 网络分区 | 半同步降级 + 应用绕过 VIP | 无双主检测 | fencing + VIP 收敛 |
| [85.4 发布事故](85.4-发布事故.md) | 配置全量推送 | 全部实例同时生效 | 只看 HTTP 200 | 灰度 + 开关 |
| [85.5 容量与成本事故](85.5-容量与成本事故.md) | 活动 3 倍流量 | 扩容放大 DB 连接 | 无容量模型 | 瓶颈清单 + 限流 |

共同点比差异更有用：**5 起全都有检测缺口；3 起的放大器是“一次变更/一次重试在全局同时生效”（85.1、85.2、85.4）；只有 1 起由流量直接触发（85.5）**。所以“加监控、加机器”不是主线，**收敛爆炸半径**（灰度、开关、预算、隔离、限流）才是。

## 复盘的度量：组织层面看四个指标

行动项层面的完成率、逾期率、复验率属于“行动项追踪”，口径见 [56.6 无指责复盘](../../L5-工程效能/56-稳定性工程/56.6-无指责复盘.md)，这里不重复。组织层面只看四个：

| 指标 | 算法 | 经验目标 | 能否刷 |
|---|---|---|---|
| 复盘覆盖率 | 已复盘 S1/S2 / 应复盘 | 100% | 可以（把事故降级） |
| 复发率 | 6 个月内同类事故 | 0 | **很难刷** |
| 检测时间趋势 | MTTD 的 P50/P90 | 逐季下降 | 很难刷 |
| 同类变更拦截率 | 门禁/检查单拦下的同类变更 / 同类变更总数 | ≥ 80% | 可以（放宽定义） |

> ⚠️ 只看可刷的指标会掉进古德哈特定律（见 [59.3 度量的陷阱 (古德哈特定律)](../../L5-工程效能/59-研发效能度量/59.3-度量的陷阱.md)）：把覆盖率当目标，事故就会被降级；把拦截率当目标，定义就会被放宽。复发率与检测时间是“不会骗人”的那两个。

## 整改项取向：技术手段 vs 流程手段

> 一句话：整改项分两种——**用技术让错误不可能发生**，和**用流程让人更小心**；前者根治，后者只是把责任转移给下一班人。

先看原文点名的三种「复杂化整改」：

| 复杂化整改（反模式） | 为什么没用 |
|---|---|
| **双人操作**：一人操作、另一人检查操作过程 | 把一次判断变成两次判断，两个人可能在同一个错误假设上想错；处理路径更长，故障时更慢 |
| **加审批**：规定什么流程必须有审批环节 | 审批只增加等待，不增加正确性；紧急故障时最先被绕过的就是审批 |
| **加系统看住坏系统** | 原文点名：「不去把原有的系统改好，而是加入一个新的系统来看着原来的那个不好的系统」——坏系统还在，监控它的系统自己也会坏 |

再看同一类问题的技术解法：

| 技术手段（优先） | 把什么错误变得不可能 |
|---|---|
| **自动化校验**（配置 schema、发布前 diff、资源配额校验） | 手写错的配置进不了流水线 |
| **默认安全**（默认拒绝、默认只读、最小权限） | 忘记加限制时，默认值站在安全的那一侧 |
| **幂等 + 去重键** | 重试、重复点击不会产生第二笔 |
| **灰度发布** | 错误只影响一个比例而不是全量；原文认可的整改正是「通过灰度发布系统来减少故障面积」 |

> 🔑 判据：**新整改会让下一次故障的处理路径更长吗？会，就不是根治。** 技术手段把「人可能犯错」变成「错误根本进不来」；流程手段只是让人更小心，而人在压力与疲劳下一定会犯错。

原文的对比很直接：亚马逊的整改**更多通过技术手段解决问题，几乎没有增加更复杂的流程或把现有系统复杂化**；阿里则会出现复杂化问题的整改项。作者自认偏好技术手段——这也是把「双人操作 / 加审批 / 加系统看住坏系统」列为反模式、而不是「稳妥做法」的原因。

## 反模式

| 反模式 | 后果 |
|---|---|
| 复盘通胀：什么都复盘 | 报告没人看，重点被稀释 |
| 只写时间线，不写贡献因素 | 读完不知道改什么 |
| 把复盘当绩效依据 | 信息隐藏，下一次更晚暴露 |
| 行动项全是“加监控” | 只提高发现能力，不降低发生概率 |
| 跨团队复盘变成甩锅会 | 边界事实变成立场，联合改进流产 |
| 复盘结论不更新 runbook/检查单 | 知识留在文档里，人走了就没了 |
| 聚类只看标题不看因素 | 把不同原因的事故归成一类 |
| 行动项关闭即结案 | 不验证有效性，同类问题复发 |

## 自检

**Q1** Near miss 为什么要复盘？它又没造成损失。

▸ 答案：因为它的损失为零、信息完整，是最便宜的改进机会。等到真出事再复盘，学费已经由用户和资金付了；而且 near miss 往往暴露的是同一套防御的薄弱点。

**Q2** 5 Whys 什么时候不该用？

▸ 答案：多因素、跨团队、存在多个并行触发条件时。5 Whys 会强行收敛成一条链，通常停在“人没注意”。这类事故应用“时间线 + 贡献因素”，把触发、放大器、检测缺口分开写。

**Q3** facilitator 为什么不能是事故当事人？

▸ 答案：当事人有自己的决策需要辩护，容易把“我当时的信息”变成“客观事实”，也容易在追问中感到被审判。facilitator 的职责是守流程与证据，必须独立于当事团队；IC 可以参加，但不能主持归因。

**Q4** 复盘覆盖率 100%、行动项全部关闭，能说明复盘有效吗？

▸ 答案：不能。覆盖率可以通过把事故降级来刷，行动项可以通过只列容易的项来关闭。要看复发率（6 个月内同类事故是否为 0）、检测时间趋势与同类变更拦截率；这三个更难被操纵。

**Q5** 8 起事故、12 个因素、最大单因素覆盖 38%，说明什么？

▸ 答案：说明没有“银弹根因”。只修覆盖最高的那一个因素，最多解决不到四成；应按因素对（如“无熔断 + 重试放大 + 共享池”）做组合修复，并用聚类结果更新检查单与演练场景。

**Q6** 复盘会上有人提出整改项「以后这类操作必须双人复核、加一道审批」。请用本节的取向判断它是不是根治，并给出一个更好的替代。

▸ 答案：不是根治。双人复核与审批都属于**流程手段**：它们假设「多一双眼睛/多一道关卡就不会错」，但两个人可能共享同一个错误假设，审批在紧急时又最先被绕过；结果是处理路径更长、系统更复杂，错误仍然可能发生。更好的替代是**技术手段让错误不可能**：把危险操作做成幂等 + 二次确认令牌、在流水线里加自动化校验（配置 schema、变更 diff、配额检查）、默认只读、灰度发布缩小影响面。判据仍是那一句：**新整改会让下一次故障的处理路径更长吗？会，就不是根治。**
