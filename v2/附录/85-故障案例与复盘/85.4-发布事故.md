# 85.4 发布事故

## 一句话

> 发布事故的根因很少是“代码有 bug”，而是**变更与运行时状态不兼容**（新旧共存、数据不可逆、容量假设变化）；止血靠回滚或关开关，前提是发布前就把“可退”设计进去。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “只改配置不用走发布” | 配置就是变更；没有版本、评审、灰度的配置变更，是最高频的发布事故来源 |
| “回滚就是再发一次旧版本” | 数据库已写新格式、消息已发新 schema 时，代码回得去、数据回不去 |
| “灰度 5% 就安全” | 5% × 大流量 × 30 分钟，仍可能是几十万用户的暴露；灰度要配自动止损 |
| “发布事故 = 测试没覆盖” | 更多是环境差异、新旧共存窗口、依赖版本漂移，测试环境复制不出来 |

> ⚠️ **数字口径**：本节案例为合成案例。发布策略、回滚、数据库变更的机制在主场：[55.1 发布策略](../../L5-工程效能/55-发布与回滚/55.1-发布策略.md)、[55.3 回滚设计](../../L5-工程效能/55-发布与回滚/55.3-回滚设计.md)、[55.4 数据库变更管理 (Expand-Contract)](../../L5-工程效能/55-发布与回滚/55.4-数据库变更管理.md)。

## 案例卡：把连接池从 200 改成 20

| 时间 | 发生了什么 |
|---|---|
| 10:00 | 配置中心提交：`db.maxOpen: 200 → 20`，备注“降低 DB 压力”；未走发布流程，直接全量推送 |
| 10:02 | 全部实例热加载；连接池按 20 重建，排队开始 |
| 10:05 | 下单接口 P99 从 80ms 涨到 1.2s，错误率 3% |
| 10:10 | P99 到 3s，错误率 30%；线程池被等待连接的请求占满 |
| 10:12 | 值班判断“DB 慢”，开始扩容应用（错误方向） |
| 10:16 | 扩容的新实例同样连 20 个连接，DB 总连接反而更紧张 |
| 10:20 | 定位到配置变更，提交回滚 |
| 10:37 | 回滚完成（拉镜像 6 分钟 + 启动就绪 2 分钟 + 切流 1 分钟 + 验证 5 分钟） |
| 10:42 | 连接池恢复，错误率归零 |

影响：42 分钟，约 227 万次请求失败（3,000 QPS × 42 × 60 × 30%），S1。

## 发布事故的五类，回滚可行性完全不同

| 类型 | 例子 | 检测信号 | 能直接回滚吗 |
|---|---|---|---|
| **代码逻辑** | 空指针、死循环、并发 bug | 错误率、延迟、日志异常 | 能，回旧镜像即可 |
| **新旧不兼容** | 接口字段改名、序列化不兼容 | 部分请求随机失败（取决于落到哪个版本） | 能，但要**同时回滚调用方**（见 [55.5 向后兼容](../../L5-工程效能/55-发布与回滚/55.5-向后兼容.md)） |
| **数据库变更** | 加非空列、改字段类型、删列 | 写失败、慢查询、主从延迟 | **不一定**；必须 Expand-Contract（见 [55.4 数据库变更管理 (Expand-Contract)](../../L5-工程效能/55-发布与回滚/55.4-数据库变更管理.md)） |
| **配置/容量假设** | 连接池、超时、线程数、开关 | 延迟、池等待、错误率 | 能，改回配置；但连接/缓存已被污染，要重建 |
| **依赖/制品** | 基础镜像、库版本、证书 | 启动失败、内存上涨、TLS 失败 | 能，但拉取/启动耗时可能超过故障窗口 |

## 回滚时间花在哪

回滚不是一条 `rollout undo`。它由五段组成：

| 阶段 | 基线（分钟） | 预热/多版本常驻（分钟） |
|---|---|---|
| 决策/确认 | 3 | 3 |
| 拉镜像 | 6 | 0 |
| 启动 + 就绪 | 2 | 1 |
| 切流 | 1 | 1 |
| 验证 | 5 | 2 |
| **合计** | **17** | **7** |

两个结论：**拉镜像和验证占了一半以上**；把旧版本镜像预热到节点、把验证脚本化，能把回滚从 17 分钟压到 7 分钟。回滚演练要测的是这个总时长，不是“命令能执行”。

## 止血：本例为什么选回滚

回滚、前滚、关开关、停写的通用判据见 [55.3 回滚设计](../../L5-工程效能/55-发布与回滚/55.3-回滚设计.md)（含“检测/决策/执行/验证”的时间分解）。本例套一遍：

| 退路 | 本例可行性 | 预计耗时 |
|---|---|---|
| **关开关** | 连接池配置没有灰度能力，改了就全量 | — |
| **回滚** | DB 无变更，旧镜像可拉 | 17 分钟 |
| **前滚修复** | 改回配置要走发布流程 | 25–40 分钟 |
| **停写降级** | 下单不能停，只能入口限流 | 分钟级，但影响面大 |

结论：回滚最快且确定，选回滚。如果当初把连接池做成可灰度、可一键回滚的开关，这条退路的时间单位是**秒**，不是分钟。

> 🔑 能关开关就不要回滚，能回滚就不要前滚；这三条退路必须在发布前准备好，而不是事故时现找。

> ⚠️ **灰度不是万能**：证书轮换、一次性数据修复、不可并存的双版本变更无法灰度，只能靠预演、停写与回滚。把“所有变更都能灰度”当假设，会在最需要退路时发现没有退路。

## 可运行：灰度与回滚速度对暴露量的影响

```go
package main

import "fmt"

type phase struct {
	name string
	min  int
}

func total(ps []phase) int {
	t := 0
	for _, p := range ps {
		t += p.min
	}
	return t
}

func main() {
	// 回滚耗时分解：镜像已在本地 vs 需要现拉
	baseline := []phase{{"决策/确认", 3}, {"拉镜像", 6}, {"启动+就绪", 2}, {"切流", 1}, {"验证", 5}}
	optimized := []phase{{"决策/确认", 3}, {"拉镜像", 0}, {"启动+就绪", 1}, {"切流", 1}, {"验证", 2}}

	fmt.Println("== 回滚时间分解（分钟） ==")
	fmt.Printf("%-12s %-10s %-10s\n", "阶段", "基线", "预热后")
	for i := range baseline {
		fmt.Printf("%-12s %-10d %-10d\n", baseline[i].name, baseline[i].min, optimized[i].min)
	}
	fmt.Printf("%-12s %-10d %-10d\n", "合计", total(baseline), total(optimized))

	const users = 200000
	const errorRate = 0.30 // 故障版本对其余请求的失败率
	fmt.Println("\n== 故障暴露量（用户·分钟） ==")
	fmt.Printf("%-22s %-12s %-14s\n", "发布方式", "持续时长", "暴露量")
	full := int(float64(users) * errorRate * 40)
	canary := int(float64(users)*0.05*errorRate*30 + float64(users)*errorRate*10)
	canaryAbort := int(float64(users) * 0.05 * errorRate * 30)
	fmt.Printf("%-22s %-12s %-14d\n", "全量发布", "40 分钟", full)
	fmt.Printf("%-22s %-12s %-14d\n", "5% 灰度 30 分钟后全量", "40 分钟", canary)
	fmt.Printf("%-22s %-12s %-14d\n", "5% 灰度，30 分钟内止损", "30 分钟", canaryAbort)
	fmt.Printf("灰度+止损 相比 全量：暴露量降到 %.0f%%\n", float64(canaryAbort)/float64(full)*100)

	fmt.Println("\n== 不同回滚速度下的总故障时长 ==")
	for _, t := range []int{total(baseline), total(optimized), 5} {
		fmt.Printf("回滚 %2d 分钟 → 故障持续约 %2d 分钟（含发现 2 分钟）\n", t, t+2)
	}
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
== 回滚时间分解（分钟） ==
阶段           基线         预热后       
决策/确认        3          3         
拉镜像          6          0         
启动+就绪        2          1         
切流           1          1         
验证           5          2         
合计           17         7         

== 故障暴露量（用户·分钟） ==
发布方式                   持续时长         暴露量           
全量发布                   40 分钟        2400000       
5% 灰度 30 分钟后全量         40 分钟        690000        
5% 灰度，30 分钟内止损         30 分钟        90000         
灰度+止损 相比 全量：暴露量降到 4%

== 不同回滚速度下的总故障时长 ==
回滚 17 分钟 → 故障持续约 19 分钟（含发现 2 分钟）
回滚  7 分钟 → 故障持续约  9 分钟（含发现 2 分钟）
回滚  5 分钟 → 故障持续约  7 分钟（含发现 2 分钟）
```

读法：灰度本身不是护身符，**“灰度 + 及时止损”**才是。5% 灰度跑满 30 分钟再全量，暴露量只降到全量的 29%；在灰度阶段止损，才降到 4%。灰度必须配自动判据（错误率、延迟、业务指标）和明确的中止权限。

## 防线

| 类型 | 动作 | 关键参数 |
|---|---|---|
| prevent | 金丝雀 + 自动分析 | 5% 流量、5 分钟窗口、错误率 > 2×基线即中止 |
| prevent | [55.2 特性开关](../../L5-工程效能/55-发布与回滚/55.2-特性开关.md)，默认关 | 开关变更也走审批与审计 |
| prevent | N-1 兼容 | 新旧版本共存期间，接口/消息双向兼容 |
| prevent | Expand-Contract 变更 | 先加列/双写，再切读，最后删旧字段 |
| prevent | 配置也走发布 | 版本、评审、灰度、可回滚 |
| detect | 发布后对比看板（版本维度） | 错误率/延迟/业务指标按版本切分 |
| detect | 关键业务断言 | 下单成功率、支付成功率，不只看 HTTP 200 |
| mitigate | 回滚演练（季度） | 测总时长，不测“命令可用” |
| mitigate | 预热旧镜像 | 节点常驻 N-1 镜像，拉取时间为 0 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 配置变更不走发布流程 | 无评审、无灰度、无回滚版本 |
| 只按机器灰度，不按用户/租户 | 同一用户命中新旧两版，行为随机 |
| 数据库变更与代码同一批发布 | 回滚代码读不了新数据 |
| 回滚不演练 | 事故时发现镜像拉不到、脚本失效 |
| 发布后只看 HTTP 200 | 业务错误（下单失败）被掩盖 |
| 扩容代替回滚 | 新实例带着同样的坏配置，扩大故障 |
| 一次发布包含多个变更 | 无法定位是哪一个，也无法只回滚一个 |

## 自检

**Q1** 只改了一个配置项，为什么也要走发布流程？

▸ 答案：配置是运行时行为的一部分，且往往全量生效、无灰度、无版本。它需要和代码一样的评审、灰度、可回滚与审计；否则一个默认值写错就能让全部实例同时改变行为。

**Q2** 回滚 17 分钟，时间花在哪？怎么压到 7 分钟？

▸ 答案：拉镜像 6 分钟 + 验证 5 分钟占大头。把 N-1 镜像预热到节点（拉取 0）、把验证脚本化/自动化（5→2 分钟），并预热进程（2→1 分钟），可压到 7 分钟。

**Q3** 数据库已经写入新字段，能直接回滚代码吗？

▸ 答案：通常不能。旧代码可能不认识新字段/新格式，回滚后读写会失败或写坏数据。正确做法是 Expand-Contract：先兼容双写/双读，确认无旧版本后再删；紧急时停写 + 前滚修复。

**Q4** 5% 灰度为什么不能保证安全？

▸ 答案：5% 只是流量比例，不是风险上限。5% × 20 万用户 × 30 分钟仍是 30 万用户·分钟的暴露；如果没有自动止损与明确的中止判据，灰度只是把全量事故拆成“先小后大”。

**Q5** 发布后错误率只有 0.3%，要不要回滚？

▸ 答案：先看基线。如果基线是 0.01%，0.3% 是 30 倍，且持续，应回滚或关开关；如果基线是 0.5%，0.3% 反而更好，应继续观察。判据是“相对基线 + 是否持续 + 是否影响核心业务”，不是绝对值。
