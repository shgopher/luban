# 85.1 超卖与资损

## 一句话

> 超卖不是“库存算错了”，而是**判断与扣减之间出现了时间差**；资损不是“赔了钱”，而是**订单、资金、库存三本账对不上**。止血顺序固定：先停流入，再查差异，最后才补账。

## 先分清三件事

| 现象 | 定义 | 直接后果 | 第一动作 |
|---|---|---|---|
| **超卖** | 卖出的可售量 > 实际库存 | 发不出货、赔付、客诉 | 停售该 SKU |
| **少卖 / 死库存** | 可售被占用但未成交，库存回不去 | 有货卖不出，GMV 损失 | 核对预扣状态机 |
| **资损** | 订单账、资金账、库存账存在无法自动解释的差额 | 真金白银流出 | 冻结差异、停止自动补账 |

三者会互相伪装：负库存看起来是超卖，实际可能是“已支付未发货的预扣被释放”导致的虚增；账面对不上看起来是资损，可能只是一笔回调延迟。

> ⚠️ **数字口径**：本节案例是**合成案例**，规模、金额、比例为构造值，用来说明因果链，不是任何一家公司的真实数据。库存扣减、秒杀漏斗的机制不在这里重讲：见 [67.6 秒杀与抢购](../../L4-组件与技术/67-交易与账务/67.6-秒杀与抢购.md)，幂等见 [67.2 幂等与防重](../../L4-组件与技术/67-交易与账务/67.2-幂等与防重.md)，差异分类见 [67.3 对账与差异处理](../../L4-组件与技术/67-交易与账务/67.3-对账与差异处理.md)。

## 案例卡：预扣上线第三天，库存变成 -37

沿用 [84.1 电商交易](../84-典型案例/84.1-电商交易.md) 的规模前提：大促峰值 8 万 QPS，库存采用“预扣 + 分片 + 条件更新”，预扣 30 分钟未支付自动释放。

| 时间 | 发生了什么 |
|---|---|
| D0 10:00 | 发布 v2：释放任务改为“每 5 分钟扫一次过期预扣”，配置项 `release_paid=false`（默认值写错） |
| D0 20:00 | 某热点 SKU 库存显示 **-37**，运营手工补货 50 件，10 分钟后再次变负 |
| D0 20:04 | “库存负值”告警触达（阈值 `stock < 0`） |
| D0 20:06 | 停售该 SKU，冻结该 SKU 的自动补账 |
| D0 20:40 | 定位：释放任务把“已支付、未发货”的预扣当成过期预扣释放了 |
| D+1 09:00 | 对账：重复回调多扣 4 笔 ¥896，同单金额冲突 1 笔 ¥100 |
| D+3 | 37 单超卖补偿完成（3 倍赔付，合计 ¥2.2 万） |

影响：S1，38 分钟；超卖 37 件；直接资损约 **¥2.2 万**（含赔付），另有 4 笔重复扣款需退回。

## 超卖的六种成因，只有第一种是“并发”

| 成因 | 机理 | 现场信号 | 修法 |
|---|---|---|---|
| **先查后改**（check-then-act） | 两个请求都读到 1，都写 0 | 库存为负，且集中在热点 SKU | 条件更新 `WHERE stock >= n`、乐观锁版本号 |
| **回调重放** | 同一支付成功被处理多次，重复发货/重复入账 | 同一 `payID` 多条流水 | 幂等键 + 唯一索引（见 [25.4 幂等设计与去重](../../L1-分布式原理/25-并发、冲突与幂等/25.4-幂等设计与去重.md)） |
| **缓存与 DB 双写** | 缓存扣成功、DB 写失败（或反之） | 缓存有货、DB 无货 | 单一真相 + 对账；不要两边都当账本 |
| **分片汇总读错** | 展示层汇总漏片，运营按错的数补货 | 库存展示与实际差一个分片量级 | 汇总走同一函数、同一口径 |
| **释放条件不完整** | 只看“超时”，不看支付状态 | 负库存周期性出现，补货后又负 | 释放带状态机：未支付 + 已过期 + 无流水 |
| **补偿重复** | 退款重试把库存加两次 | 可售量虚高，随后超卖 | 退款单幂等，库存变动记流水 |

第一种最容易被当成“唯一原因”，于是加锁、降并发，结果后五种照旧发生。

## 为什么“支付成功才扣”必然超卖

支付回调有延迟、会丢失、会重复，把扣减放在回调里，等于把“不超卖”交给时序。这个取舍在 [84.1 电商交易](../84-典型案例/84.1-电商交易.md) 里已经用“预扣 + 超时释放”换掉了；本例的事故不是选型错，而是**释放任务没有尊重预扣的状态机**——选型对了，实现把不变量破坏了。

> 🔑 不变量只有一句：**库存的每一次变动，都必须能对应到一条订单状态迁移。** 释放、退款、补偿都不例外。

## 资损：三本账与五类差异

| 账本 | 记什么 | 典型差异 |
|---|---|---|
| 订单账 | 下单、支付、发货、退款状态 | 订单已支付，库存未扣 |
| 资金账 | 渠道流水、入账、出账、手续费 | 渠道成功、本地失败（或反之） |
| 库存账 | 可售、预扣、已售、在途 | 汇总与明细不等 |

差异的五类分法与挂账处理见 [67.3 对账与差异处理](../../L4-组件与技术/67-交易与账务/67.3-对账与差异处理.md)。故障现场只用记住一条：**先分清“能自动解释”和“不能自动解释”**。能解释的（回调延迟、批量入账时差）走自动重试；不能解释的（金额不一致、无流水入账）进人工裁决队列，不许“取一个”。

## 止血：顺序不能反

| 步 | 动作 | 判据 | 常见错误 |
|---|---|---|---|
| 0 | **停流入**：停售 SKU / 停新预扣 | 负库存不再扩大 | 先补库存，边补边卖 |
| 1 | **冻结**：关闭该 SKU 的自动补账、自动释放 | 差异不再变化 | 让定时任务继续跑 |
| 2 | **留证**：快照库存、订单、流水、任务日志 | 可复现时间线 | 重启/重跑覆盖现场 |
| 3 | **定界**：按时间窗 + SKU + 支付渠道圈范围 | 差异笔数可估算 | 只查“最近一小时” |
| 4 | **补账**：逐笔核对状态机后补偿 | 每笔有依据、可追溯 | 按总额一把补 |
| 5 | **恢复**：小流量放开、观察再全量 | 负库存归零且不再出现 | 直接全量恢复 |

> 🔑 资损事故里，“快”和“准”要分开：**止血要快**（分钟级），**补账要准**（逐笔）。用“快”去做补账，通常制造第二笔资损。

> ⚠️ **不是所有差异都要停售**：只影响展示、不影响可售量与资金的差异，走异步修正；停售的判据是“差异还在扩大，或已涉及资金”。一刀切停售会把资损事故变成 GMV 事故。

## 检测：三层防线的时间常数

| 层 | 手段 | 发现延迟 | 能拦住什么 |
|---|---|---|---|
| 单笔 | 幂等键、唯一索引、条件更新 | 毫秒 | 重复入账、并发覆盖 |
| 分钟级 | 库存负值、支付成功率、重复回调率 | 1–5 分钟 | 正在扩大的超卖 |
| 天级 | 对账（订单/资金/库存） | T+1 | 已发生但未暴露的差异 |

T+1 对账为什么不能当第一道防线：按峰值 5,000 QPS、异常率 0.01% 估算，24 小时窗口内可积累约 **43,200 笔**异常（5,000 × 86,400 × 0.01%），这些请求在无人看守的窗口里持续发生。对账是兜底，不是发现手段。

## 可运行：对账差异扫描器

输入是一段合成流水，做两件事：找同一 `payID` 的多次入账，找同一订单的金额冲突。两类检测必须都跑——只按 `payID` 去重会掩盖金额差异，只比金额会漏掉重复入账。

```go
package main

import (
	"fmt"
	"sort"
)

type call struct {
	payID   string
	orderID string
	amount  int // 分
}

func main() {
	// 合成流水：渠道回调重放 + 同单金额不一致
	calls := []call{
		{"P1001", "O1", 19900},
		{"P1001", "O1", 19900}, // 第二次回调
		{"P1002", "O2", 29900},
		{"P1003", "O3", 9900},
		{"P1003", "O3", 9900},
		{"P1003", "O3", 9900}, // 第三次
		{"P1004", "O4", 49900},
		{"P1004", "O4", 39900}, // 同单不同金额
		{"P1005", "O5", 12900},
	}

	byPay := map[string][]call{}
	byOrder := map[string]map[int]int{}
	for _, c := range calls {
		byPay[c.payID] = append(byPay[c.payID], c)
		if byOrder[c.orderID] == nil {
			byOrder[c.orderID] = map[int]int{}
		}
		byOrder[c.orderID][c.amount]++
	}

	fmt.Println("== 重复扣款（同一 payID 多次入账） ==")
	ids := make([]string, 0, len(byPay))
	for id := range byPay {
		ids = append(ids, id)
	}
	sort.Strings(ids)
	dupCount, dupLoss := 0, 0
	for _, id := range ids {
		cs := byPay[id]
		if len(cs) <= 1 {
			continue
		}
		extra := len(cs) - 1
		loss := cs[0].amount * extra
		dupCount += extra
		dupLoss += loss
		fmt.Printf("%s 回调 %d 次，多扣 %d 笔，损失 ¥%.2f\n", id, len(cs), extra, float64(loss)/100)
	}
	fmt.Printf("合计：多扣 %d 笔，资损 ¥%.2f\n\n", dupCount, float64(dupLoss)/100)

	fmt.Println("== 同单金额冲突（不能自动取一个） ==")
	oids := make([]string, 0, len(byOrder))
	for id := range byOrder {
		oids = append(oids, id)
	}
	sort.Strings(oids)
	for _, id := range oids {
		amts := byOrder[id]
		if len(amts) <= 1 {
			continue
		}
		vals := make([]int, 0, len(amts))
		for a := range amts {
			vals = append(vals, a)
		}
		sort.Ints(vals)
		fmt.Printf("%s 出现 %d 种金额：", id, len(vals))
		for i, a := range vals {
			if i > 0 {
				fmt.Print(" / ")
			}
			fmt.Printf("¥%.2f", float64(a)/100)
		}
		fmt.Printf("，差额 ¥%.2f，需人工裁决\n", float64(vals[len(vals)-1]-vals[0])/100)
	}

	gmv := 100000000 // 分，¥100 万
	fmt.Printf("\n资损率 = ¥%.2f / ¥%.2f = %.4f%%\n", float64(dupLoss)/100, float64(gmv)/100, float64(dupLoss)/float64(gmv)*100)
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
== 重复扣款（同一 payID 多次入账） ==
P1001 回调 2 次，多扣 1 笔，损失 ¥199.00
P1003 回调 3 次，多扣 2 笔，损失 ¥198.00
P1004 回调 2 次，多扣 1 笔，损失 ¥499.00
合计：多扣 4 笔，资损 ¥896.00

== 同单金额冲突（不能自动取一个） ==
O4 出现 2 种金额：¥399.00 / ¥499.00，差额 ¥100.00，需人工裁决

资损率 = ¥896.00 / ¥1000000.00 = 0.0896%
```

读法：`P1004` 同时命中两类检测——它既是“同号多次入账”，又有金额差异。只按 `payID` 去掉一条，会把 ¥100 的差异一起删掉；只按金额比，会漏掉多入账的一笔。**两类检测是并集，不是二选一。**

## 防线：prevent / detect / mitigate

| 类型 | 动作 | 拦住哪类成因 | 代价 |
|---|---|---|---|
| prevent | `UPDATE ... WHERE stock >= n` | 先查后改 | 需要数据库原子性；分片要路由正确 |
| prevent | 回调幂等键 + 唯一索引 | 回调重放 | 多一次索引写；键设计要覆盖渠道 |
| prevent | 释放任务带状态机 | 释放条件不完整 | 状态机要覆盖“已支付未发货” |
| prevent | 库存变动流水（append-only） | 补偿重复、汇总错 | 存储与写入放大 |
| detect | 库存负值、重复回调率、支付成功率 | 超卖扩大 | 告警阈值要按 SKU 分级 |
| detect | 分钟级对账（库存 vs 订单） | 差异积累 | 计算成本；需幂等 |
| mitigate | 单 SKU 限购、停售开关 | 已发生的超卖 | 少卖；需人工确认 |
| mitigate | 差异挂账 + 人工裁决队列 | 不能自动解释的资损 | 人力；要 SLA |

## 反模式

| 反模式 | 后果 |
|---|---|
| “查一下余额再扣” | 并发下必然超卖，压测也测不出来 |
| 把扣减放在支付回调里 | 回调延迟/丢失/重放都变成超卖 |
| 释放任务只看超时，不看支付状态 | 已支付订单的库存被释放，补货后又负 |
| 只按 `payID` 去重 | 掩盖金额差异与部分支付 |
| 超卖后先补库存再停售 | 边补边卖，负库存扩大 |
| 按总额补账 | 差异被抹平，无法逐笔追溯 |
| 把赔付全算进“资损”不分类 | 掩盖真正的资金漏洞 |

## 自检

**Q1** 库存显示 -37，为什么不能直接把 37 件加回去？

▸ 答案：负库存是结果，不是原因。直接加回会掩盖“释放任务错误释放已支付预扣”这条根因，而且可能把已支付未发货的预扣再加一次。正确顺序是停售、冻结、按订单状态机逐笔核对，再决定补货还是退款。

**Q2** 为什么 T+1 对账不能作为第一道防线？

▸ 答案：发现延迟最长 24 小时。按 5,000 QPS、0.01% 异常率，窗口内可积累约 4.3 万笔异常，且期间持续发生。对账是兜底；第一道防线必须是毫秒级的幂等键、唯一索引与条件更新。

**Q3** 同一 `payID` 回调两次、金额不同，按“重复”删一条为什么危险？

▸ 答案：金额不同说明不是单纯重放，可能是改价、部分支付或渠道错账。删一条会掩盖真实差异，导致账实不符。两笔都要保留，进人工裁决队列。

**Q4** 预扣释放任务为什么会造成超卖？修法是什么？

▸ 答案：它按“超时”释放，却不看订单是否已支付；已支付未发货的预扣被释放，可售量虚增，随后被卖超。修法是释放条件带状态机（未支付 + 已过期 + 无支付流水），并与订单状态变更放在同一事务或同一幂等流程里。

**Q5** 停售 38 分钟少卖，和继续卖 2 小时多赔，怎么选？

▸ 答案：比较边际损失。停售损失 ≈ 正常转化 × 时长 × 毛利；继续卖损失 ≈ 超卖率 × 时长 × 赔付倍数。资损类默认先停，因为赔付与信任损失不可逆；可用“部分 SKU 停 + 其余正常”缩小范围，而不是全站停。
