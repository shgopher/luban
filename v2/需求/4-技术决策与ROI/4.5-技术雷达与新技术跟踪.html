                      4.5 技术雷达与新技术跟踪

                      一句话

                      技术雷达不是 “新技术清单”，而是一张带证据等级和适用前提的判断表：每个条目回答 “我们在什么场景下用它、凭什么这么判断、什么条件下把它撤下来”；四环（Adopt / Trial / Assess / Hold）管的是 “现在能不能用”，不是 “它流不流行”。

                      四环的判据是证据，不是热度

                      环 允许做什么 证据门槛 退出条件
                      Adopt 新项目默认可以用，不必再评估 自家灰度跑满 4 周 + 至少 2 个生产案例 出现更优替代，或上游停更 → 降 Assess / Hold
                      Trial 只在指定低风险场景试点，禁止扩散 自家 POC 通过（2 周时间盒） 到期未达标 → 回 Assess；达标 → 升 Adopt
                      Assess 只做纸面评估与 POC，不进生产 官方文档 + 二手案例（L0） 连续 2 个季度无进展 → 移出雷达
                      Hold 新项目不得采用；存量给迁移窗口 有明确失败证据，或有更强替代 证据反转才解除

                      ⚠️ Hold ≠ 禁用。 Hold 约束的是 “新项目”；存量系统的正确写法是 “继续用 + 迁移窗口 + 接受理由”。写不出这三样，说明它不是技术判断，是没登记的技术债，见 58.2 技术债管理。

                      Thoughtworks 的公开实践把这套结构定为四环 × 四象限、每半年出一期，可以直接借用（环的名字与语义比自创的 “推荐/观察/谨慎” 更不容易吵）：

                      象限 里面放什么 谁负责 判断依据
                      技术 / 方法 架构模式、工程实践、协议 架构组 影响 “怎么写”，不影响 “买什么”
                      工具 构建、观测、CI、调试 平台 / 效能组 影响开发者的日常动作
                      平台 云、数据库、中间件、消息 基础设施组 影响运维与容量
                      语言 / 框架 语言版本、主流框架 各域 TL 影响招聘与人才池

                      一个象限只归一个 owner。四个人都想管 AI，结果就是四个方向各写一条，评审会上互相打架。

                      证据分级：把 “我觉得” 换成 L0–L3

                      等级 证据长什么样 能支撑的结论
                      L0 二手 官方文档、release notes、别人的基准测试、大会演讲 只能进 Assess
                      L1 自家 POC 2 周时间盒，跑通 “最贵的两个假设” 可以进 Trial
                      L2 灰度 一个真实场景、小流量 ≥ 4 周，含一次故障演练 可以进 Adopt
                      L3 全量 多团队、跨季度 只用于判断 “要不要降级”，不是升环的证据

                      “最贵的两个假设” 的选法与打分维度，和 4.3 技术选型的评估维度 里的 POC 原则一致：先验证 “换掉它要多久” 和 “它在你这个负载下的长尾”，不要先验证 demo 有多好看。

                      引入成本的估算不能只看 license：迁移人力、双跑期的资源、培训与文档，都算进 4.2 成本-收益分析 的 TCO 六层里；只算 license 的评估，结论一定是 “新技术更便宜”。

                      条目必须带三样东西：前提、证据、退出条件

                      # radar/2026-Q4/event-streaming.yaml —— 雷达条目，可直接抄
item: 事件流平台替换评估（Redpanda）
quadrant: platforms                 # 四象限之一
ring: assess                       # adopt / trial / assess / hold
since: 2026-Q4
claim: 单机吞吐高于 Kafka 约 3 倍，运维组件更少        # 一句话结论，不许写形容词
applies_when: 事件量 > 50 万条/秒 且 维护 Kafka 的人 < 3   # 适用前提：不写就是广告
evidence: L0（厂商基准 + 两篇第三方评测），暂无自家 POC   # 证据等级，决定它只能待在 assess
exit:
  condition: 2 个季度内未做 POC，或社区 issue 中位响应 > 7 天
  action: 移出雷达，并写进季度 Won't 清单
owner: 基础设施组
review_at: 2027-Q1

                      🔑 没有 “适用前提” 的雷达条目等于广告。 同一条结论在不同规模、不同团队下会反向成立：50 万条/秒 的团队该看 Redpanda，5 千条/秒 的团队换它只是多背一个运维组件。

                      跟踪的产能上限：把它当工作项，不当爱好

                      项 建议值 理由
                      每人每月投入 ≤ 4 小时（约 2 篇长文 + 1 次动手验证） 超过这个数，产出的是焦虑不是判断
                      每期评审时长 2 小时 / 季度 只处理有证据的条目，无证据的当场降级
                      雷达条目总数 20–40 条 超过 60 条，评审会就变成朗读会
                      每期淘汰率 ≥ 10% 只进不出的雷达三期后一定读不动
                      Trial 并行数 ≤ 3 个 再多就都停在 POC，团队产能被摊薄

                      三张决策表

                      你的情况 选择
                      有明确痛点 + 一个低风险场景 + 有人愿意为试点结果负责 + 有退出日期 Trial
                      只有 “看起来更好”，说不出具体场景 Assess，先做 L0 → L1
                      刚出过事故，团队在找 “银弹” Hold，先修流程——事故后的技术选型 90% 是情绪决策
                      已经在生产用，但没人能说清为什么用它 补一条 Hold / Adopt 记录 + 迁移窗口，不许留空
                      Trial 的门槛 不满足就别开
                      场景 一个具体的、失败不影响主营业务的流程
                      负责人 一个能签字 “试到什么程度就停” 的人
                      退出日期 写死的日期（建议 6–8 周），到期必须给结论
                      观测 至少一条能对比的指标（延迟 / 成本 / 故障率）

                      从 Assess 走到 Trial 的完整准入流程（谁提、谁批、几步、留什么证据），见 58.5 技术选型流程；本节的四环只回答 “在哪个环”，不替代那套流程。

                      新技术带来的风险（人才、锁定、维护）不是雷达能兜住的，那是 4.7 技术风险与止损 的活；雷达只负责 “判断它值不值得进你的技术栈”。

                      反模式

                      反模式 后果
                      简历 / 兴趣驱动（为了用它而用它） 上线即维护负担，作者一走就没人会改
                      会议或 Demo 驱动：看完演讲就立项 只验证了 demo，没验证运维与长尾
                      雷达只进不出 三期后 60+ 条，没人读，评审退化成走过场
                      条目没有适用前提 一年后没人能判断这条结论还成不成立
                      把 Hold 当禁用 存量系统偷偷用，风险从 “已知” 变 “不可见”
                      Trial 同时开 5 个 每个都停在 POC，团队产能被摊薄
                      用 “大厂都在用” 当证据 规模差 100 倍时结论不可迁移（判据见 4.3 技术选型的评估维度）
                      只有一条 “我们也上 AI” 的条目 没有场景与前提，无法评估也无法退出

                      三条铁律

                      🔑 雷达的判据是证据等级，不是热度；L0 证据只能待在 Assess。

                      🔑 每个条目必须写 适用前提 + 退出条件，否则半年后它就是噪音。

                      🔑 Hold 约束新项目，不约束存量；存量要写迁移窗口，写不出来就是技术债。

                      自检

                      Q1 团队把 “向量数据库” 放进 Adopt，理由是 “官方文档说有亿级 QPS”。这个环位对了吗？

                      ▸ 答案：不对，最多 Assess。官方文档属于 L0 二手证据，且 “亿级 QPS” 是特定硬件 + 特定查询下的数字。升到 Adopt 需要 L2：自家一个真实场景灰度跑满 4 周、含一次故障演练，并写出适用前提（数据量、召回率要求、运维人力）。否则这就是把别人的基准当自己的结论。

                      Q2 一篇雷达条目写着 “Kafka：Hold”。团队里的存量订单系统还在用它，这算违规吗？

                      ▸ 答案：不算，但必须补偿。Hold 只约束新项目；存量要么写清 “迁移窗口 + 目标时间”，要么写清 “继续用的理由 + 每年复核”。两者都不写，Hold 就变成一句没人执行的评语，而风险（版本停更、人才流失）也不会被登记——那正该进 58.2 技术债管理 的台账。

                      Q3 评审会上有人提议同时试点 5 个新技术，你怎么用数字说服他？

                      ▸ 答案：按产能算：每个 Trial 至少需要 1 个 owner 投入 30%–50% 的时间、6–8 周，加 1 个可对比的指标体系。5 个并行 = 2.5 个全职人力被占掉，而任何一个达标率都不会高。建议压到 ≤ 3 个，并给出排序依据（痛点强度 × 退出成本），其余留在 Assess。—— 这条建议本身就该记进 4.6 决策框架与决策记录 的台账。

                      Q4 为什么说 “雷达条目只进不出，三期后就失效”？

                      ▸ 答案：因为评审会的处理能力是常数（2 小时 / 20–40 条）。条目无限增长后，每条分到的时间趋近于零，评审只剩 “念标题”，而真正需要降级的条目（证据反转、上游停更）没人看。淘汰率 ≥ 10% 是强制把 “删除” 变成议程项，而不是靠自觉。

                      Q5 一条新技术 “看起来能省 40% 成本”，你会先要哪两样东西再决定进 Trial？

                      ▸ 答案：① 适用前提（在什么数据量、什么负载下省 40%？我们的规模落在里面吗）；② 退出成本（换回来要多久、数据能不能导出）。省 40% 是收益侧的单点数据，而 4.3 的判断标准是 “总代价最小且退出成本可控”——收益再大，若换不回来，也是一次单向押注。
