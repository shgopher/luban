# 1.6 AI 辅助需求流水线：Skill、文档与执行三件套

## 一句话

> AI 不是替你「写需求」，而是逼你把 **what（做什么）、why（为什么）、which（选哪条路）、how（怎么建）** 分层落到可留存的文档里；四个规划 Skill 解决「怎么问」，PRD / 设计文档 / SPEC 解决「写什么」，PLAN / Task List / Walkthrough / note-it 解决「执行时怎么留痕」。

三个词先给个最短解释，避免后面一路看一路猜：**PRD**（Product Requirements Document，产品需求文档）说做什么；**设计文档**（Design Doc，也叫技术方案 / RFC）说为什么选这条路；**SPEC**（Specification，规格说明书）说怎么建。它们是三个精度层，不是同一份文档的三个别名——逐项拆解在「三份文档：what / which / how」一节。

## 先破除五个误区

| 误区 | 现实 |
|---|---|
| 让 AI 直接写代码最快 | 跳过的每一步都会在返工里补回来；方向错了两千行代码就是两千行废料 |
| PRD、设计文档、SPEC 是一回事 | 一个说做什么，一个说为什么选这条路，一个说怎么建；混在一起，Agent 会替你做没审过的决策 |
| 文档越多越好 | 简单功能硬写十一节 SPEC 是仪式主义；三份文档是按需取用的工具 |
| 计划是形式 | PLAN 是「动手前唯一便宜的拦截点」；写两百行后再发现方向错，成本高一个量级 |
| Agent 说 done 就可信 | done 只代表它停了；改了什么、验没验、为什么这么改，都要另给证据 |

## 一张数字表：这条流水线有多少个「格子」

| 对象 | 数字 | 含义 |
|---|---|---|
| PRD 结构 | 9 段 | 概述、目标、用户故事、功能需求、非目标、设计考量、技术考量、成功指标、待解问题 |
| PRD 提问数 | 2–3 / 3–5 / 6–8 | 按简单 / 典型 / 跨系统复杂功能伸缩 |
| 设计文档骨架 | 6 段 | Abstract、Background、Design、Rationale、Compatibility、Implementation |
| SPEC 结构 | 11 节 | 摘要、架构、数据模型、API、业务逻辑、错误处理、安全、性能、测试、实施、风险 |
| 执行留痕 | 4 件 | PLAN、Task List、Walkthrough、note-it |

格子数不是硬性 KPI，是提醒：**每一格都对应一个后面会来追问的人**。少一格，就有人要靠猜。

## 规划先行：先关掉「直接开写」的冲动

好的 AI 规划 Skill 有一个共同点：**在需求/设计被批准前，禁止写代码**。

- brainstorming 有硬门（HARD-GATE）：设计没拿到批准，不许写代码、不许 scaffold、不许调用实现类 Skill；
- prd 明确只产出 PRD，不动手写代码；
- wayfinder 默认「只规划不执行」，一旦你想直接动手，往往说明已经走到地图边缘、该交接了。

这条约束不是形式主义。Agent 跑得快，能在你反应过来之前写完两百行、顺手定下五个你没审过的架构决定。规划把「想」和「做」分成两段，让你在**几段文字**的阶段拦下方向错误。

## 四个规划 Skill：先选入口，再谈模板

| Skill | 规模 | 产物 | 存储 | 适合 |
|---|---|---|---|---|
| **brainstorming**（superpowers） | 单功能/单项目 | 设计稿（Markdown spec） | 本地 `docs/` + git | 需求模糊、你全程在场，想通过连续对话磨清楚 |
| **grill-with-docs**（Matt Pocock） | 单份计划/设计 | ADR + 术语表 | 文档 | 已有草案，需要逐问拷问并沉淀决策 |
| **wayfinder**（Matt Pocock） | 超大、跨多会话 | issue tracker 上的决策地图 | 外部 tracker | 一摊活大到单份 spec 装不下，需要异步、多人接续 |
| **prd**（goal-workflow） | 单功能 | 九段式 PRD | 本地 `tasks/` | 需求已比较明确，要快速整理成可验收、可拆工单的文档 |

选择判据不是「哪个更强」，而是**不确定性落在哪一层**：

| 你的处境 | 先用什么 | 为什么 |
|---|---|---|
| 只有一句模糊需求（「把信送给加西亚」） | brainstorming 或 wayfinder | 先把问题问清楚；同步对话选 brainstorming，异步跨会话选 wayfinder |
| 已有代码原型/迁移目标，需求清楚 | prd | 把行为对齐成可验收条目，直接能拆 issue |
| 方案有争议，需要留决策记录 | grill-with-docs | 逐问拷问 + ADR + 术语表 |
| 跨多个团队/多个会话的大改造 | wayfinder | 地图、迷雾、前沿、每会话一个工单 |

grill-with-docs 是「怎么问」的原子能力，wayfinder 内部也复用它；brainstorming 和 prd 是同一层的两种风格：前者偏工程设计与方案探索，后者偏产品需求与验收。**别用一个 Skill 干所有层的事**。

## 三份文档：what / which / how

### 名词先说清：这三个词到底指什么

三者是同一件事的三个精度：都是「动手前写、写完别人能照着干活」的文档，区别只在**落到哪一层**。名字来自三套不同的行业传统，所以最容易被混着用。

| 词 | 全称 | 字面拆解 | 一句话定义 | 出自哪套传统 |
|---|---|---|---|---|
| **PRD** | Product Requirements Document | 产品 + 需求 + 文档 | 说清「做什么、给谁做、做到什么算完成」，刻意不写实现 | 产品管理（PM / PMF 那套流程） |
| **设计文档** | Design Doc（别名：技术方案 / RFC / design proposal） | 设计 + 文档 | 说清「为什么走这条技术路线而不是别的」，含备选、取舍、兼容性 | 工程设计（Google Design Doc、Go proposal、Rust RFC） |
| **SPEC** | Specification（规格说明书 / 技术规格） | 规格、明细 | 把方案压到施工精度：字段、API、状态机、错误码、测试用例 | 工程规格（IETF RFC 里的 specification、硬件规格书） |

拿盖楼打比方，三者的关系一眼就清楚：

- **PRD 是业主需求书**：要几间房、谁住、预算多少、什么算验收合格。业主会说「主卧朝南」，但不会指定钢筋型号。
- **设计文档是建筑方案**：为什么选钢结构而不是砖混，抗震、造价、工期怎么取舍，被否掉的方案为什么不选。
- **SPEC 是施工图加材料规格表**：梁的截面尺寸、钢筋等级、混凝土标号、每道工序的验收标准——工人拿着它就能开工，不用猜。

顺序也是这个顺序：PRD 定「要什么」，设计文档定「走哪条路」，SPEC 定「每一步怎么砌」。

现实里三个名字很乱：PRD 有的团队叫「需求文档」「需求说明」，设计文档叫「技术方案」「RFC」「Design Doc」，SPEC 叫「技术规格书」「详细设计」「接口文档」。**名字随便换，分层不能省**——一旦混在一起，就会出现「PRD 里写『用 Kafka』」这种把 what 和 how 焊死的写法——文章末尾的反模式表专门列了这一条。本书统一用 PRD / 设计文档 / SPEC 三个词。

| 维度 | PRD | 设计文档 | SPEC |
|---|---|---|---|
| 回答 | 做什么、为什么值得做 | 为什么选这条路，而不是别的 | 具体怎么建 |
| 视角 | 用户与产品 | 决策者与团队 | 实现者（工程师/Agent） |
| 主要读者 | 产品、设计、开发、测试 | 需要对齐方向的人 | 照着写代码的人或 Agent |
| 对实现的态度 | 刻意回避 | 论证选择，不落到字段 | 精确到可直接施工 |
| 灵魂章节 | 验收标准 | Rationale（被放弃的备选 + 原因） | 需求 → API / 业务规则 / 测试的逐条映射 |
| 什么时候可跳过 | 几乎总要写 | 有真实岔路、破坏性变更、难回退时才写 | 简单功能可跳过；多 Agent 并行时价值最高 |

### PRD：把「做什么」说到可验收

PRD 的两条硬约束值得抄：

1. **用户故事按 US-001 编号，每条带验收标准**；验收标准必须可观察、可测试、可验证三者之一，「运行正常」「体验良好」一律打回。
2. **功能需求按 FR-N 编号，每条只描述一个行为**；不许用「and」把多个行为塞进一条。

再加上固定的九段结构：概述、目标、用户故事、功能需求、非目标、设计考量、技术考量、成功指标、待解问题。**非目标**和**待解问题**最容易被省，但它们恰恰是防止范围蔓延的闸门。

### 设计文档：把「为什么不是别的」写下来

设计文档的灵魂是 **Rationale**：必须主动列出至少一个被放弃的备选方案，以及放弃它的原因——「我们没选 X，因为 Y」。

骨架可以借用 Go proposal / Rust RFC 的成熟结构：

```text
Abstract（摘要）
Background（背景与真实痛点）
Design（设计）
Rationale（理由、取舍、被放弃的备选）
Compatibility（兼容性与迁移）
Implementation（实现与验证）
```

三条纪律：

- Background 用**真实的痛点代码**讲「痛在哪」，不要堆「现状很糟」；
- 破坏性变更在 Compatibility 里开门见山承认，列代价和渐进迁移路径；
- Implementation 用实测数据和自动化工具支撑「可落地」，不空喊「风险可控」。

被否决的设计文档同样有价值：它记录「这条路为什么走不通」，Status 标 Rejected 就行。

### SPEC：把「怎么建」变成施工契约

SPEC 是写给实现者（人或 Agent）的契约，必须精确到能直接施工。参考十一节结构：摘要、架构、数据模型、API 设计、业务逻辑、错误处理、安全、性能、测试策略、实施计划、开放问题与风险。

三条质量红线：

1. **不许留 TBD / TODO**：要么现在解决，要么明确挪进「待解问题」；
2. **不复述 PRD**：SPEC 要加技术深度，把需求换个说法再抄一遍不算；
3. **逐条映射**：每条用户故事对应 SPEC 章节，每条功能需求落到 API/业务规则，每条验收标准至少对应一个测试用例。

> 🔑 一个人照模糊 PRD 还能凭常识补齐；多个 Agent 并行时不行——它们需要字段级的共享契约，否则会各自补出互相打架的实现。

## 一条从想法到代码的流水线

```text
/prd → /to-design → /prd-to-spec → /to-issues → /goal
   → PLAN → Task List → /review-it → /note-it → /ship-it
```

| 阶段 | 产物 | 回答 |
|---|---|---|
| `/prd` | PRD | 做什么、为什么 |
| `/to-design` | 设计文档 | 为什么选这条路 |
| `/prd-to-spec` | SPEC | 怎么建 |
| `/to-issues` | Issue 卡片 | 拆成能独立实现、带验收标准的小任务 |
| `/goal` | 代码 | 实现 |
| PLAN | 实施计划 | 打算怎么改 |
| Task List | 任务清单 | 走到哪了 |
| Walkthrough | 变更说明 | 改了什么、验没验 |
| `/note-it` | 决策实录 | 为什么这么改 |

三份文档管「进场之前」，执行三件套管「进场之后」，接缝就是动手写代码的那一下。

## 执行三件套：PLAN、Task List、Walkthrough

| 文档 | 时机 | 回答什么 | 存不存得下来 |
|---|---|---|---|
| **PLAN** | 动手前 | 打算怎么改，涉及哪些文件，验收标准是什么 | plan mode 多为会话级；Antigravity 的 Implementation Plan 是 artifact |
| **Task List** | 动手中 | 拆成几步、到哪了、还剩什么 | 内建 todo 多为会话级；`/to-issues` 落成 Issue 才能跨会话/跨人 |
| **Walkthrough** | 做完后 | 改了什么、怎么验的、截图/录屏 | artifact / 文档 |
| **`/note-it`** | 做完后 | 为什么这么改、哪里偏离 spec、放弃了什么、还有什么没底 | `docs/issue#XXXX.html` |

### PLAN：动手前先看一眼改法

PLAN 的价值是**便宜阶段拦截**：计划只是几段文字，改起来几乎零成本；等 Agent 写完两千行再发现方向错，代价完全不同。

适合先 PLAN 的情况：

- 要动公共 API；
- 跨多个文件/模块；
- 需求本身还含糊；
- 多 Agent 并行，需要先对齐边界。

单文件小修不必进 plan mode：探半天仓库、写一版计划、等人批，只为改三行，反而碍事。

### Task List：把黑箱开一道缝

内建 todo list 的作用是**让你不用盯每一次工具调用**，扫一眼就知道拆成了几步、走到哪、还剩什么。步骤拆得离谱，你当场能看出它理解偏了，赶在这份理解落进代码之前拦下来。

但它通常是会话级的：关掉窗口就没了，也带不到下一个会话。跨天、跨人的任务要用 `/to-issues` 落成 Issue 卡片，带验收标准、依赖关系、类型和优先级。

### Walkthrough：做完之后，把改动讲清楚

Agent 说 done，你信不信？Walkthrough 用一份带图、带录屏的总结回答「改了什么、怎么验的」：

- 起服务、点按钮、填数据，把关键路径跑一遍；
- 截图/录屏留在文档里，供你快速核对；
- 不要求你从 diff 一行行倒推它干了什么。

### `/note-it`：补上 diff 看不到的「为什么」

Walkthrough 和 diff 能告诉你改了哪些代码，但看不到：

- spec 没写清的地方，Agent 自己拿了什么主意；
- 哪里故意没照 spec 来，为什么；
- 考虑过哪些别的方案，为什么放弃；
- 哪条假设它自己也没底，需要你确认。

这些判断不写下来，就随着对话蒸发了。`/note-it` 在实现和 review 之后、交付之前，对着 spec 复盘，把四类判断记进 `docs/issue#XXXX.html`：设计决策、偏离、取舍、待确认。它和设计文档的 Rationale 是同一个路子，区别在时机——设计文档在动手前写（计划），note-it 在做完后写（实录）。

## 质量红线：AI 生成文档也要验收

| 文档 | 必须过 | 不过就重写 |
|---|---|---|
| PRD | 每条验收标准可观察/可测试/可验证；每条 FR 只含一个行为 | 「运行正常」「体验良好」「支持高并发」 |
| 设计文档 | 至少一个被放弃的备选 + 放弃原因；兼容性代价写清 | 只有单方面论证，没有取舍 |
| SPEC | 无 TBD/TODO；需求 → API/规则/测试逐条映射 | 复述 PRD、字段级细节缺失 |
| PLAN | 涉及文件、步骤、验收方式齐全 | 「先这样，再看」 |
| Walkthrough | 有真实运行证据，区分已实测/代码推断/未验证 | 只有一句「已完成」 |
| note-it | 四类判断有就写、没有写 None + 理由 | 空文件或复制 diff |

> 🔑 文档的验收标准不是「写得多」，是**下一个环节能不能直接拿它开工**。PRD 能拆 issue、设计能评审、SPEC 能照着写代码、PLAN 能照着改，才算过关。

## 反模式

| 反模式 | 后果 |
|---|---|
| 需求没批就开写 | 方向错，返工成本随代码量放大 |
| PRD 里写「用 Kafka」 | 把 what 和 how 混在一起，验收基准失效 |
| 设计文档只夸自己的方案 | 后来人不知道为什么不选别的，争论重来一遍 |
| SPEC 留 TBD 给实现者 | Agent 会替你补一个没审过的决策 |
| 简单功能硬写全套文档 | 文档成本超过实现成本，团队开始绕过流程 |
| 只有会话级 todo，没有 Issue | 跨天/换人就丢进度 |
| Walkthrough 只有一句 done | 无法核对，review 退化成信任 |
| 省掉 note-it | 三个月后没人记得为什么偏离 spec |

## 自检

**Q1** 为什么 AI 规划 Skill 普遍要求「设计批准前不许写代码」？

▸ 答案：Agent 跑得快，能在人反应过来之前写完大量代码并定下多个架构决定。规划把「想」和「做」分开，让人在几段文字的阶段拦下方向错误；等代码写完再改，成本高一个量级。HARD-GATE 就是把这条约束写死，防止 Agent 以「项目很简单」为由跳过。

**Q2** PRD、设计文档、SPEC 分别回答什么问题？混在一起会怎样？

▸ 答案：PRD 回答做什么/为什么，设计文档回答为什么选这条路（which/why），SPEC 回答怎么建（how）。混在一起时，Agent 会在你还没想清要什么的时候先替你把技术方案定了；或者照着一份只有需求、没有实现契约的文档，自行补出一堆没审过的架构决策。

**Q3** 设计文档的灵魂章节为什么是 Rationale？只写选中方案为什么不够？

▸ 答案：Rationale 要求列出至少一个被放弃的备选方案及放弃原因，让讨论建立在同一套事实和取舍上，后来人不必把同一场争论重吵一遍。只写选中方案是单方面论证，读者无法判断取舍是否成立；被否决的方案同样有价值，它记录了「这条路为什么走不通」。

**Q4** SPEC 的「逐条映射」具体指什么？为什么多 Agent 并行时更重要？

▸ 答案：每条用户故事对应 SPEC 章节，每条功能需求落到 API 端点或业务规则，每条验收标准至少对应一个测试用例。一个人照模糊 PRD 能凭常识补齐，多个 Agent 会各自补出互相打架的实现；字段级契约把大家拴在同一个方向上。

**Q5** PLAN、Task List、Walkthrough、note-it 各在什么时机用？分别解决什么？

▸ 答案：PLAN 在动手前，解决「打算怎么改、能不能先拦」；Task List 在动手中，解决「拆成几步、到哪了」；Walkthrough 在做完后，解决「改了什么、怎么验的」；note-it 在做完后，解决「为什么这么改、哪里偏离、放弃了什么」。前三个偏「做了什么」，note-it 补「为什么」。

**Q6** 三份文档是不是每次都要写全？

▸ 答案：不是。PRD 几乎总要写；设计文档只在有真实岔路、破坏性变更、难回退时写；SPEC 在简单功能可以跳过，但多 Agent 并行、接口/数据模型复杂时价值最高。判断标准是「这次改动的不确定性落在哪一层」，不是「模板有几节」。
