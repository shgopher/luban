# 2.4 从业务模型到系统边界

## 一句话

> 系统边界不是 “按组织切” 也不是 “按表切”，而是三条线的交集：**一致性边界**（哪些数据必须一起改）、**变更频率**（哪些总是一起改）、**团队边界**（谁能独立发布）；三条线对不上时，先看流程的跨边界比例。

## 三种切法

| 切法 | 依据 | 问题 |
|---|---|---|
| 按组织 | 部门归属 | 组织调整即失效；跨部门流程被切碎 |
| 按实体/表 | 数据库表 | 一个业务动作要改多张表 → 跨服务事务 |
| **按能力 + 一致性边界** | 业务能力 + “必须同事务的聚合” | 需要先做领域建模（成本前置） |

推荐组合：**能力定粗边界 → 聚合定细边界 → 团队边界做校验**（与 [29.3 聚合与事务边界](../../L2-架构风格/29-领域建模与边界/29.3-聚合与事务边界.md) 对齐）。

## 实测：跨边界比例判断 “切得对不对”

把 2.2 的流程活动映射到 2.1 的能力边界，再统计流程流转：

| 指标 | 结果 |
|---|---|
| 能力总数 / 已映射 | 9 / 7（2 个未映射） |
| 流程流转总数 | 5 |
| **跨边界流转** | **4（80%）** |
| 边界间调用对 | 订单→库存、库存→履约、风控→履约、履约→财务 |
| 最忙边界 | 履约中心（被 3 条流转碰到） |

判据：**跨边界 > 60% 说明边界的切法与流程不一致**——本例 80%，意味着 “几乎每一步都要跨系统”，延迟、事务、故障传播都会放大。整改方向不是 “加接口”，而是**按流程重组边界**（例如把 “锁库存 + 拣货” 合成履约域，或把 “审核信用” 前移到下单前）。

```python
cross = [(a,b) for a,b in flow if act2b[a] != act2b[b]]
ratio = len(cross)/len(flow)
print("跨边界比例:", f"{ratio:.0%}", "→", "需重组" if ratio > 0.6 else "可接受")
```

## 三条判定规则

| 规则 | 问法 | 结论 |
|---|---|---|
| 一致性 | 这两块数据必须同一事务改吗？ | 是 → 同一边界 |
| 变更频率 | 它们总是一起改吗？ | 是 → 同一边界 |
| 团队 | 能独立发布/回滚吗？ | 不能 → 边界太细或依赖未理清 |

## 边界判定的五个问题与一个反例

> 🔑 **边界是问出来的，不是画出来的**：五个问题里只要有一题答不上，就先别拆——拆错的代价不是多写几个接口，而是把一次本地事务变成跨团队对账。

### 五个问题：每道题都要判据

| 问题 | 答 “是” 的判据 | 答 “否” 的判据 | 误判后果 |
|---|---|---|---|
| 谁拥有这个词的最终解释权？ | 只有一个域能定义它：字段、口径、边界条件都由它说了算 | 两个域各解释一半（营销算 “应核销”、交易算 “已核销”） | 两套口径的报表，差异永远解释不清，对账靠人肉对齐 |
| 变更频率是否一致？ | 两边发布节奏同频，或一侧是几乎不改的字典 | 一侧日更、一侧周更 | 快的一侧被慢的一侧排队，活动上线等发版 |
| 事务边界在哪？ | 必须同事务成立的写入全在一侧 | 强一致写入对横跨两侧 | 强一致只能靠 2PC / Saga，失败率与延迟上一个台阶 |
| 数据一致性要求？ | 能接受最终一致，且有分钟级对账兜底 | 必须实时一致（超发、重复核销、重复支付） | 用最终一致冒充强一致：超发、重复核销，事后无法追溯 |
| 团队 / 发布是否独立？ | 各自能独立发布、独立回滚、独立 on-call | 一次改动要两个团队联调联发 | 康威定律反噬：边界随组织与排期漂移 |

判定规则：**五题全 “是” 才拆**；任何一题 “否”，先改模型或改边界，不要用 “加个接口” 盖过去。

五题不是并列的，权重分三档：**解释权与事务边界是硬约束**，答 “否” 就是不能拆；**变更频率与一致性是成本约束**，答 “否” 可以拆，但要用事件、异步与对账兜底；**团队独立是组织约束**，答 “否” 说明拆了也白拆——两个团队还是要一起发版。

### 反例：把 “优惠券” 从营销域切到交易域

看似顺理成章：券是在下单时被核销的，所以 “券属于交易”。把券整块从营销域搬到交易域，再用五题复核：

| 五问 | 切前（券在营销域） | 切后（券在交易域） | 判定 |
|---|---|---|---|
| 解释权 | 营销定义面额、门槛、叠加规则与活动预算 | 交易定义核销与归因字段，营销只能取数 | ❌ 营销丧失活动效果的自证能力 |
| 变更频率 | 活动规则 40 次/日，营销自主发布 | 规则调整要等交易域排期：10 次/周需求对 5 次/周发布窗口 | ❌ 缺口 5 次/周，活动上线被压 |
| 事务边界 | 发放 + 预算扣减同一事务（营销本地） | 发放 + 预算扣减变跨域，下单 + 核销变本地 | ⚠️ 转移而非消除：超发风险从下单挪到发券 |
| 一致性 | 下单 + 核销跨域强一致，12 万次/日 | 发券 + 预算跨域一致，3 万次/日但成批 | ⚠️ 频次降了，批量超发的破坏面更大 |
| 团队发布 | 营销、交易各自独立发布 | 券字段一改就要两团队联调 | ❌ 营销被交易域的节奏绑架 |

再算耦合（本机计算，环境 macOS 15.6 / Apple M1 / Python 3.14.8；原始输出见 `.cache/pilot-2.4/raw.txt`）：

```python
"""优惠券归属切换（营销域 → 交易域）前后的耦合量化。
频次为业务量估算假设，不是线上采集的数据；结论随假设变，脚本可改参数重算。
"""

# (事件, 每日次数, 单次事件跨域调用跳数, 其中 “必须跨域同事务” 的写对)
BEFORE = [
    ("下单用券", 120_000, 2, 1),   # 交易→营销：查券 1 跳 + 核销 1 跳
    ("发券", 30_000, 0, 0),        # 营销本地：发放 + 预算扣减同一事务
    ("活动规则变更", 40, 0, 0),     # 营销本地发布
    ("日终对账", 1, 2, 0),          # 财务分别取交易流水、营销核销明细
    ("活动 ROI 归因", 4, 0, 0),     # 营销本地算
]
AFTER = [
    ("下单用券", 120_000, 0, 0),   # 交易本地：下单 + 核销同一事务
    ("发券", 30_000, 1, 1),        # 营销→交易：建券/发券；预算扣减仍在营销
    ("活动规则变更", 40, 1, 0),     # 营销→交易：券字段/口径要交易域配合
    ("日终对账", 1, 1, 0),          # 财务→交易：流水与核销同源
    ("活动 ROI 归因", 4, 1, 0),     # 营销→交易：按活动维度取核销归因
]

# 依赖边：(上游, 下游, 用途)
EDGES_BEFORE = [("交易", "营销", "查券"), ("交易", "营销", "核销"),
                ("财务", "交易", "流水"), ("财务", "营销", "核销明细")]
EDGES_AFTER = [("营销", "交易", "建券/发券"), ("营销", "交易", "规则同步"),
               ("营销", "交易", "ROI 取数"), ("财务", "交易", "流水与核销")]

RULES_PER_DAY, CODE_RATIO, CAPACITY_PER_WEEK = 40, 0.05, 5


def total(events):
    calls = sum(n * hops for _, n, hops, _ in events)
    tx = sum(n * pairs for _, n, _, pairs in events)
    return calls, tx


def fan_in(edges):
    counter = {}
    for _, dst, _ in edges:
        counter[dst] = counter.get(dst, 0) + 1
    return counter


cb, tb = total(BEFORE)
ca, ta = total(AFTER)
print(f"每日跨域调用次数     切前 {cb:>7,}  切后 {ca:>6,}  变化 {(ca - cb) / cb:+.1%}")
print(f"每日跨域强一致写入对 切前 {tb:>7,}  切后 {ta:>6,}  变化 {(ta - tb) / tb:+.1%}")

print("\n边界被依赖数（fan-in）：")
fb, fa = fan_in(EDGES_BEFORE), fan_in(EDGES_AFTER)
for dom in ("营销", "交易", "财务"):
    print(f"  {dom}域  切前 {fb.get(dom, 0)}  切后 {fa.get(dom, 0)}")

need = RULES_PER_DAY * 5 * CODE_RATIO
print(f"\n需交易域发版的变更  切前 0 次/周  切后 {need:.0f} 次/周"
      f"（发布能力 {CAPACITY_PER_WEEK} 次/周，缺口 {need - CAPACITY_PER_WEEK:+.0f} 次/周）")

print("\n口径 owner（核销明细由谁定义与出数）：")
print("  切前：营销域（营销自证活动效果；交易域只管支付流水）")
print("  切后：交易域（营销的 ROI 报表要等交易域口径与排期）")
```

```text
每日跨域强一致写入对 切前 120,000  切后 30,000  变化 -75.0%

边界被依赖数（fan-in）：
  营销域  切前 3  切后 0
  交易域  切前 1  切后 4
  财务域  切前 0  切后 0

需交易域发版的变更  切前 0 次/周  切后 10 次/周（发布能力 5 次/周，缺口 +5 次/周）

口径 owner（核销明细由谁定义与出数）：
  切前：营销域（营销自证活动效果；交易域只管支付流水）
  切后：交易域（营销的 ROI 报表要等交易域口径与排期）
```

| 指标 | 切前 | 切后 | 说明 |
|---|---|---|---|
| 每日跨域调用次数 | 240,002 | 30,045 | −87.5%，**最会骗人的指标** |
| 每日跨域强一致写入对 | 120,000 | 30,000 | −75%，但风险从 “高频下单” 移到 “批量发券” |
| 营销域被依赖数（fan-in） | 3 | 0 | 营销不再被调用，也拿不到核销数据 |
| 交易域被依赖数（fan-in） | 1 | 4 | 交易成为新的耦合中心与故障中心 |
| 需交易域发版的变更 | 0 次/周 | 10 次/周 | 发布能力 5 次/周，缺口 5 次/周 |
| 核销明细口径 owner | 营销 | 交易 | 营销对账 / ROI 要等交易出数 |

结论：**跨域调用次数只统计 “调了几次”，不统计 “谁有解释权、谁被排期、谁承担对账”**。本例调用次数降 87.5% 看着漂亮，但交易域 fan-in 从 1 涨到 4、发布缺口从 0 变成 5 次/周、口径 owner 从营销换成交易——三个变化都不在调用计数里，却全是切边界的真实成本。

这也解释了一个常见现象：**“搬家” 在评审会上容易通过**，因为评审看的是调用关系图——切后图更干净、调用更少；而真正决定边界的是解释权、发布窗口与对账口径，这三样在图上都看不见。发布缺口 5 次/周尤其不是抽象数字：交易域每周 5 个工作日、每天 1 个发布窗口，营销 10 次/周的字段需求里至少有 5 次要排队到下一周。

正确切法不是 “整块搬家”，而是**沿事务边界纵向切**：营销域保留券模板、活动规则、发放、预算与口径解释权；交易域保留券实例状态、下单时校验与核销；两域用 “券核销事件” 同步，日终按 “发放数 − 核销数 − 过期数 = 存量” 对账。这样五道题才全部答 “是”：

| 对象 | 归属 | 为什么 |
|---|---|---|
| 券模板、活动规则、活动预算 | 营销 | 解释权 + 日更改动频率 + 发放与预算同一事务 |
| 券实例（谁领了哪张、当前状态） | 交易 | 下单与核销必须同一事务，状态随订单走 |
| 核销明细 | 交易出数、营销校验 | 数据在交易产生，口径由营销定义，双方各留一份可对 |

### 边界检查单：答不上就不拆

拆任何新服务之前，五个问题各要一个写下来的答案（进 ADR 或设计文档）：

1. **这个词的 owner 是谁？** 写下一个域的名字。答不上 → 不拆，先做上下文映射（见 [29.2 上下文映射](../../L2-架构风格/29-领域建模与边界/29.2-上下文映射.md)）。
2. **一次业务变更要改几个服务？** 目标 ≤ 2，并画出变更路径。答不上 → 不拆，先统计当前变更的跨服务次数。
3. **必须同事务的写入是否都在一侧？** 列出写对清单。答不上 → 不拆，先定聚合边界（见 [29.3 聚合与事务边界](../../L2-架构风格/29-领域建模与边界/29.3-聚合与事务边界.md)）。
4. **对账怎么做、谁出数、差异多久能查清？** 给出口径与兜底方案。答不上 → 不拆，先补对账。
5. **两个团队能否独立发布、独立回滚、独立 on-call？** 拿出最近三次发版记录。答不上 → 不拆，先理依赖。

> 🔑 检查单的作用不是 “证明能拆”，而是 **“拦住不能拆”**：五题全过才动手；一题不过，就把那题对应的建模或对账工作补完再回来。

## 反模式

| 反模式 | 后果 |
|---|---|
| 按部门切边界 | 跨部门流程变成跨系统调用，延迟与事务成本翻倍 |
| 按表切边界 | 一个业务动作改多张表 → 分布式事务 |
| 边界太细（每实体一服务） | 调用链长、故障点多 |
| 边界太粗（一个 “核心服务”） | 无法独立演进，团队互相阻塞 |
| 不做跨边界统计 | 不知道 “切得对不对”，只能凭感觉 |
| 边界与团队不一致 | 康威定律反噬：代码结构向组织漂移 |

## 三条铁律

> 🔑 **先定一致性边界，再谈服务拆分**；一致性边界错了，后面全错。

> 🔑 **跨边界比例 > 60% 就要重组**，不是加接口。

> 🔑 **边界必须能被团队独立发布**；不能独立发布说明粒度或依赖有问题。

## 自检

**Q1** 为什么 “按表切边界” 会导致分布式事务？

▸ 答案：因为一个业务动作通常要改多张表（下单要写订单、扣库存、记流水）。按表切意味着这些表分属不同服务，本地事务变成跨服务事务，只能靠 2PC/Saga 补偿。按 “一致性边界（聚合）” 切，则一个动作在一个服务内完成。

**Q2** 跨边界比例 80% 说明什么？该怎么改？

▸ 答案：说明**边界切法与业务流程不一致**：几乎每一步都要跨系统，延迟叠加、事务复杂、故障传播。改法不是 “加 RPC”，而是按流程重组：把高频连续流转的活动放进同一边界（如锁库存 + 拣货 → 履约），或把可前移的步骤（信用审核）提前到流程入口。

**Q3** “最忙边界” 为什么值得关注？

▸ 答案：因为它会成为**耦合中心与故障中心**：所有流转都经过它，它的可用性决定全链路；它的变更会牵动所有上游。本例 “履约中心” 被 3 条流转碰到，若继续加职责，就会退化成 “什么都做的核心服务”。

**Q4** 能力边界与限界上下文对不上时，信谁？

▸ 答案：以**限界上下文**为准来做代码边界，以**能力**为准来做组织与投资决策。两者对不上通常说明 “业务语言与模型语言不一致”——要么能力拆得太细（应合并），要么模型漏了某个上下文（应补）。这个差异本身就是重要信号。

**Q5** 边界确定后，第一件要落地的事是什么？

▸ 答案：**把边界写进构建**：模块/服务目录、依赖规则（见 [27.3 模块边界与依赖规则](../../L2-架构风格/27-单体与模块化/27.3-模块边界与依赖规则.md)）、数据 owner（每张表只有一个写方）。没有这三样，边界只存在于架构图里，三个月后就会被 “临时需求” 打穿。

**Q6** 什么时候应该 “合并边界” 而不是 “拆”？

▸ 答案：当两块数据**必须同一事务**、或**总是一起变更**、或**跨边界调用比例极高**时。拆分的收益（独立演进）小于成本（分布式事务、延迟、运维）时，就该合并。判据是 “拆开后，一次业务变更要改几个服务”。

**Q7** 怎么证明 “边界划分有效”？

▸ 答案：三个可测指标：**跨边界流转比例**（应下降）、**单次变更影响的边界数**（应为 1–2）、**独立发布成功率**（能只发一个边界且不回滚）。三者都改善，才说明边界真的立住了；只看 “服务数量变多” 是自欺。
