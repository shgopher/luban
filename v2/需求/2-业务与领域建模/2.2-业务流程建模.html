                  2.2 业务流程建模 (BPMN)

                  一句话

                  BPMN 的价值不是 “画得好看”，而是把流程变成可解析、可计算的结构：一旦有了节点与依赖，就能算出 “关键路径、卡在哪、要加几个人”——而不是靠开会吵 “到底哪个环节慢”。

                  核心元素（只用得起这五类）

                  元素 作用 建模时的坑
                  事件（Event） 开始/结束/中间（超时、消息） 忘建 “异常结束”，流程没有失败路径
                  任务（Task） 用户任务 / 服务任务 / 人工审批 把 “系统动作” 画成用户任务，责任不清
                  网关（Gateway） 排他（XOR）/ 并行（AND）/ 包容（OR） 并行分支忘了汇合（join），下游重复执行
                  泳道（Lane） 谁负责（部门/系统） 泳道按组织画，跨部门协作点看不清
                  消息流（Message Flow） 跨池通信 与顺序流混淆，画成 “跨部门直接连线”

                  实测 A：解析 BPMN，检查泳道与孤儿活动

                  本机解析一份 4 泳道、6 任务的采购流程 XML：

                  泳道 活动数 活动
                  客户 1 提交订单
                  销售 2 锁库存、审核信用
                  仓储 2 拣货、打包
                  财务 1 开票
                  孤儿活动（不在任何泳道） 0 —

                  “孤儿活动” 是最常见的建模缺陷：任务画了、却没人负责——上线后就会出现 “这一步到底谁做” 的扯皮。

                  实测 B：关键路径告诉你该优化哪

                  同一流程，各任务时长（分钟）+ 并行分支在 “拣货” 前汇合：

                  任务 时长 最早开始 结束
                  提交订单 3 0 3
                  锁库存 5 3 8
                  审核信用 20 3 23
                  拣货 10 23 33
                  打包 8 33 41
                  开票 5 41 46

                  关键路径 = 46 分钟，其中 “审核信用” 占 43%；把它压到 5 分钟，整条链路降到 31 分钟（−33%）。而 “锁库存 5 分钟” 压到 1 分钟，对总时长毫无影响——它不在关键路径上。

                  # 关键路径 = 依赖链上 “时长之和” 的最大值
def cp(n):
    return dur[n] + max([cp(d) for d in deps[n]], default=0)

                  这就是流程建模的实用价值：优化只对关键路径有效，其他优化是白花钱。

                  网关与泳道的建模检查：一个报销流程的走查

                  🔑 先建模，再走查：核心五元素只保证 “画得出”，走查要保证 “画得对”——每个网关有可判定条件、每条异常有去处、每个活动有责任泳道；再按概率加权算路径，才知道该压哪一步。

                  骨架：四段主线 + 两条异常支路

                  “提交 → 主管审批 → 财务复核 → 打款” 这条链，四个环节各自暴露一类建模问题：驳回要能回退、复核要能并行、大额要能加签、打款要等外部回执。

                  段落 活动（泳道） 网关 建模要点
                  ① 提交 发起报销 → 提交报销单（员工） — 事件与任务分开：发起可由系统定时触发
                  ② 主管审批 主管审批（主管） 排他：主管结论 通过 / 驳回二选一；驳回先 “退回修改” 再重提
                  ③ 财务复核 财务复核（财务）→ 发票查验 ∥ 预算校验 包容：是否加签；并行：校验开始 / 完成 金额 ≥ 1 万同时触发法务会签，与财务复核并行；两项校验都完成才可打款
                  ④ 打款 打款指令（财务）→ 银行转账（外部池） 事件：等回执或超时 银行回执是消息；超时 30 分钟转人工核对

                  消息流只跨池：主池的 “打款指令” 用消息流发给银行池的 “银行转账”，银行处理完再以消息流回主池的 “银行回执” 事件；同一池内部一律用顺序流。把跨组织协作画成同池顺序流，是走查最容易放过的一类错误——它让 “外部依赖不可控” 在图上消失。

                  网关选型：四种语义，四种典型误用

                  网关 语义 本流程用在哪 常见误用 后果
                  排他（XOR） 多条出边只走一条 主管审批：通过 / 驳回 出边条件不互斥，或没有默认边 两条都走 → 重复审批；都不走 → 流程停在网关
                  并行（AND） 所有出边同时激活，join 等全部入边 发票查验 ∥ 预算校验 有 split 无 join，或 join 入边数与 split 出边数不一致 下游执行两次；或永远等不齐，流程卡死
                  包容（OR） 条件成立的分支全部激活（0～n 条），join 只等已激活分支 加签：金额 ≥ 1 万触发法务会签，同时保留财务复核 用 OR 代替 XOR 做 “二选一” 两条都激活 → 重复审批、重复付款
                  事件（Event） 不判断条件，等 “先到的事件”（消息 / 定时 / 信号） 打款后等银行回执或 30 分钟超时 用 XOR 配 “消息已到达” 条件 条件恒真或恒假，超时支路永不触发

                  ⚠️ 两种网关的 “不等价” 是走查重点：排他网关必须条件互斥且全覆盖，缺默认边就会停在网关；包容网关的 join 只等被激活的分支，按 “全部到齐” 去实现，流程永远等不齐。

                  解析脚本按泳道的 flowNodeRef 反查 “谁没被认领”，并检查每条顺序流的两端是否存在：

                  import sys
import xml.etree.ElementTree as ET

# 读出文件里的 BPMN XML，解析主池的泳道、网关与孤儿节点
path = sys.argv[1] if len(sys.argv) > 1 else "reimburse.bpmn"
root = ET.parse(path).getroot()
NS = "{http://www.omg.org/spec/BPMN/20100524/MODEL}"
TASK_TAGS = {"userTask", "serviceTask", "manualTask", "scriptTask", "task",
             "receiveTask", "sendTask"}
GATEWAY_TAGS = {"exclusiveGateway", "parallelGateway", "inclusiveGateway",
                "eventBasedGateway", "complexGateway"}
EVENT_TAGS = {"startEvent", "endEvent", "intermediateCatchEvent",
              "intermediateThrowEvent", "boundaryEvent"}


def tag(el):
    return el.tag.split("}", 1)[1]


processes = root.findall(f"{NS}process")
main = next(p for p in processes if p.find(f"{NS}laneSet") is not None)

tasks = [el for el in main.iter() if tag(el) in TASK_TAGS]
gateways = [el for el in main.iter() if tag(el) in GATEWAY_TAGS]
events = [el for el in main.iter() if tag(el) in EVENT_TAGS]
nodes = {el.get("id"): el.get("name") for el in tasks + gateways + events}

lanes = {}
for lane in main.iter(f"{NS}lane"):
    refs = [r.text.strip() for r in lane.findall(f"{NS}flowNodeRef")
            if r.text and r.text.strip()]
    lanes[lane.get("name")] = refs

covered = {ref for refs in lanes.values() for ref in refs}
orphans = [nid for nid in nodes if nid not in covered]

dangling = []
for f in main.iter(f"{NS}sequenceFlow"):
    for attr in ("sourceRef", "targetRef"):
        if f.get(attr) not in nodes:
            dangling.append((f.get("id"), attr, f.get(attr)))

print(f"池 {len(processes)} 个（主池有泳道），消息流 {len(root.findall(f'{NS}messageFlow'))} 条")
print(f"主池节点 = {len(nodes)}，其中任务 {len(tasks)}、网关 {len(gateways)}、事件 {len(events)}")
print(f"网关 {len({tag(g) for g in gateways})} 类：")
for g in gateways:
    print(f"  {tag(g):<18} {g.get('name')}")
print(f"泳道 {len(lanes)} 条（被引用的节点 {len(covered)} 个）：")
for name, refs in lanes.items():
    n_task = sum(1 for r in refs if r in {t.get('id') for t in tasks})
    print(f"  {name:<3} 节点 {len(refs):>2} 个，其中任务 {n_task} 个")
if orphans:
    print("孤儿节点 " + "、".join(f"{i}（{nodes[i]}）" for i in orphans))
else:
    print("孤儿节点 0 个")
print(f"悬空连线引用 {len(dangling)} 个" + (f"：{dangling}" if dangling else ""))

                  本例是本机解析：主池 10 个任务、6 个网关、4 条泳道，孤儿 1 个——“催办提醒”（服务任务）画在流程里却不在任何泳道，上线后就是 “这一步谁做” 的扯皮点；悬空连线 0 个，说明 22 条顺序流两端都存在。单次检查成本是一条命令，收益是把评审从 “看图找茬” 变成 “看输出对账”。

                  网关密度也能算出来：本例 6 个网关 / 10 个任务 = 0.6。经验判据（本机算例的推论，不是行业统计）：网关:任务 超过 1:1，就先合并分支，再谈自动化和加人；本例 0.6，低于这条线——每多一条出边就多一条要测、要算时长的路径，图会先于系统变成没人改得动的资产。

                  路径时长：先看关键路径，再乘概率

                  三条路径按 “串行相加、并行取最大” 计算，概率按单据实际分布加权：

                  • T(正常) = 2 + 10 + 15 + max(8, 6) + 20 = 55 分钟
                  • T(驳回) = 2 + 10 + 30 + 2 + 10 + 15 + 8 + 20 = 97 分钟
                  • T(加签) = 2 + 10 + max(25, 15) + 8 + 20 = 65 分钟
                  • E[T] = Σ pᵢ·Tᵢ = 0.72×55 + 0.18×97 + 0.10×65 = 63.56 分钟
                  路径 构成（分钟） 概率 p 时长 T p·T
                  正常 提交 2 + 主管 10 + 财务复核 15 + max(发票 8, 预算 6) + 打款 20 0.72 55 39.60
                  驳回 提交 2 + 主管 10 + 退回修改 30 + 重提 2 + 主管 10 + 财务复核 15 + 校验 8 + 打款 20 0.18 97 17.46
                  加签 提交 2 + 主管 10 + max(法务会签 25, 财务复核 15) + 校验 8 + 打款 20 0.10 65 6.50
                  合计 E[T] = Σ pᵢ·Tᵢ 1.00 — 63.56

                  0.72 / 0.18 / 0.10 是本机算例的假设分布；换成自己系统按单据状态统计的比例即可，公式不变。

                  完整代码在仓库 tools/examples/2.2-bpmn-path/，python3 path_cost.py 可复现这张表；数值是本机计算，不是线上采集的数据。

                  为什么优化要先看关键路径

                  优化项 改后 E[T] 期望收益 期望降幅 卡在哪
                  打款 20 → 10 53.56 10.00 分 −15.7% 三条路径都必经；但耗时在外部银行，只能重设计接口
                  财务复核 15 → 5 54.56 9.00 分 −14.2% 三条路径都经过；加签路径与法务并行取大后仍是 25，该路径不变
                  退回修改 30 → 10 59.96 3.60 分 −5.7% 只在 18% 的驳回路径上，按概率打三折
                  发票查验 8 → 2 61.56 2.00 分 −3.1% 压到 6 分钟以下无收益：预算校验 6 分钟接管并行段关键位置
                  法务会签 25 → 5 62.56 1.00 分 −1.6% 局部看着最香：占加签路径 38%（25/65），但只覆盖 10% 单据，且压到 15 以下后关键位置让给财务复核

                  结论：按 “单条路径压缩比” 排序会先挑法务会签（38%），按期望收益排序应该先挑财务复核；两者差 9 倍（9.00 对 1.00 分钟）。顺序固定为：

                  1. 先算关键路径，把不在任何路径关键链上的节点排除——动它们总时长不变；
                  2. 再看节点被几条路径经过、各自概率多大，算 Σ pᵢ·ΔT；
                  3. 最后才谈单个节点能压多少分钟。

                  ⚠️ 并行段还有天花板：把发票查验压到 6 分钟以下，整段仍由预算校验的 6 分钟决定，多压的时间一分不省——优化并行分支要比的是 “次长分支”。

                  还有一个反直觉的数字：驳回路径只占 18%，却贡献了 E[T] 的 27%（17.46/63.56）。把驳回率从 18% 降到 8%（前置校验拦掉一半错误单据），E[T] 变成 0.82×55 + 0.08×97 + 0.10×65 = 59.36 分钟，省 4.20 分钟——比压缩“退回修改”（3.60 分钟）、法务会签（1.00 分钟）都大。流程改善的第一选择是减少回退，第二才是压缩回退的时长：回退是返工，一次做错、一次重做、审批还要再走一遍。

                  三条建模检查清单

                  1. 谁做：每个任务被且仅被一条泳道的 flowNodeRef 引用，服务任务落到具体系统；判据是解析后孤儿节点 = 0、悬空连线 = 0。跨泳道连线就是集成点，映射到系统边界见 2.4 从业务模型到系统边界。
                  2. 什么条件：每个排他 / 包容网关的每条出边都有可判定条件，排他网关另配一条默认边；判据是条件互斥、并集覆盖全部输入取值，否则流程停在网关。
                  3. 异常怎么办：驳回、超时、取消、打款失败四类异常各有终点或补偿路径，且不能静默落回正常路径的下一步；判据是每个网关至少一条 “非期望” 出边，并在图上标出等待时长。

                  自检

                  Q1 为什么 “优化锁库存” 对总时长没用？

                  ▸ 答案：因为它在非关键路径上：与 “审核信用” 并行，且只花 5 分钟，结束时间（8 分钟）远早于信用审核（23 分钟）。缩短它不会让下游提前开始，只有缩短关键路径上的任务（信用审核）才会改变总时长。

                  Q2 并行网关忘记 “汇合（join）” 会发生什么？

                  ▸ 答案：因为两条分支都会继续往下走，下游任务被执行两次：一次来自分支 A，一次来自分支 B。表现为 “重复下单/重复发货”。BPMN 里必须用并行网关的 join（等所有入边）来同步。

                  Q3 “孤儿活动” 为什么是建模缺陷？

                  ▸ 答案：因为泳道代表责任归属：活动不在任何泳道，意味着没人负责。上线后这一步要么被漏掉（流程卡住），要么被多个部门重复做（冲突）。检查方法就是 “所有任务/事件是否都被某个泳道的 flowNodeRef 引用”。

                  Q4 BPMN 与 “状态机” 该怎么选？

                  ▸ 答案：多角色、跨部门、有并行分支用 BPMN（它擅长表达 “谁在什么时候做什么”）；单实体生命周期（订单状态流转）用状态机更清晰。两者可以共存：BPMN 描述业务流程，状态机描述单个实体的状态约束。

                  Q5 关键路径和 “瓶颈” 是一回事吗？

                  ▸ 答案：不完全。关键路径是时长最长的那条依赖链，瓶颈通常指 “资源利用率最高/排队最长的环节”。关键路径上的任务一定是 “影响总时长” 的，但瓶颈可能在非关键路径上（如某个共享资源被多条分支争用）。分析时两者都要看。

                  Q6 流程建模要多细？

                  ▸ 答案：细到 “能算出关键路径并指认责任人” 即可：通常 5–15 个活动。细到 “每个按钮” 会失去可读性，粗到 “接单→发货” 又算不出瓶颈。粒度判据是 “这一步是否对应一个明确的角色 + 可估的时长”。

                  Q7 流程模型怎么和系统边界对上？

                  ▸ 答案：把 “服务任务” 映射到系统能力（见 2.1 业务能力地图），把 “用户任务” 映射到操作界面或人工工单。映射完检查：每个服务任务是否都有系统承接、每个跨泳道连线是否都是集成点——这些集成点就是系统边界。
