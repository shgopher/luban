# 第 66 章 即时通信与音视频 · 概论

## 一句话

> 这类系统的全部复杂度来自三个物理事实——**连接是有状态的、消息要穿过不可靠的网络、媒体必须实时**。六节就是在这三个约束下依次回答：连接放在哪（[66.1](66.1-长连接网关.md)）、消息怎么不丢（[66.2](66.2-消息可靠投递与离线.md)）、多端怎么一致（[66.3](66.3-多端同步.md)）、实时音视频怎么通（[66.4](66.4-音视频信令与媒体传输.md)）、一条消息怎么给 N 个人（[66.5](66.5-群聊与消息扩散.md)）、一万个人同时看直播怎么便宜（[66.6](66.6-流媒体处理.md)）。

## 5 分钟入门：先记住这 12 个词

| 词 | 一句话解释 | 生活类比 |
|---|---|---|
| **长连接网关** | 承接百万在线连接的接入层，只做连接、寻址、转发 | 小区传达室：记住每户人家住哪栋 |
| **连接路由表** | `userId → 网关节点 → 连接` 的映射，决定消息能不能找到人 | 电话总机的分机表 |
| **心跳** | 周期性探活，用来发现"看起来在线、其实已断"的半开连接 | 每隔几分钟敲一下门 |
| **会话内 seq** | 一个会话里单调递增的消息序号，排序、续传、去重全靠它 | 快递单号（会话内连号） |
| **客户端消息 ID** | 客户端生成、重发时复用的幂等键 | 转账时填的"用途备注" |
| **五段接力** | 上行 ACK → 持久化 → 下行投递 → 离线存储 → 推送通道 | 一封信要经过五个邮局 |
| **离线收件箱** | 用户离线期间消息的临时存放处，有保留期与条数上限 | 驿站代收 |
| **写扩散 / 读扩散** | 发消息时给每人各写一份 / 只写一份、读时各自来取 | 群发短信 vs 公告栏 |
| **游标（cursor）** | 每台设备"同步到哪了"的位置标记 | 书签 |
| **SFU** | 只转发不混流的媒体服务器，群视频的主流拓扑 | 会议室的转接台 |
| **GOP** | 两个关键帧之间的间隔；切片、ABR、秒开都挂在它上面 | 视频的"章节" |
| **码率阶梯** | 同一内容的多档清晰度/码率，供播放器按网络自动切换 | 同一部电影的高清/标清 |

> 记住三句话：**连接层管"找到人"，消息层管"不丢"，同步层管"一致"**；音视频另起一条"媒体面"；群聊和直播都是**同一条消息给 N 个人**的两种极端形态。

| 有负载均衡和 API 网关，为什么还要长连接网关？ | [66.1](66.1-长连接网关.md) | API 网关是无状态的请求入口；长连接网关要维护"谁连在哪台机器"这张有状态的路由表 |

| 消息存了就算"不丢"吗？ | [66.2](66.2-消息可靠投递与离线.md) | 不算；上行 ACK、持久化、下行投递、离线存储、推送五段，任一段失败都是丢 |
| 离线消息为什么不能按会话扫表？ | [66.2](66.2-消息可靠投递与离线.md) | 拉一次要扫该用户所有会话；按人存收件箱才能一次按 seq 游标分页拉取 |
| 多端在线，怎么保证三端顺序一致、不漏？ | [66.3](66.3-多端同步.md) | 会话内 seq 定序 + 每设备游标；推只叫醒、拉才补全，客户端按 seq 去重 |
| 断线 3 天，重连后拉什么？ | [66.3](66.3-多端同步.md) | 先算分界：全量 14.29 MiB、每条变更约 236 B，分界约 63,461 条（0.5 条/秒 ≈ 35.3 小时）；3 天 ≈ 12.96 万条已过界，**直接全量快照重建游标**；1 小时级短断线（实测 424,866 B ≈ 415 KiB）才走 `change_cursor` 增量；游标 7 天过期另论 |
| 信令和媒体能走同一条连接吗？ | [66.4](66.4-音视频信令与媒体传输.md) | 不能；信令要可靠有序可重放，媒体要低延迟可丢包，混在一起等于让 TCP 队头阻塞杀延迟 |
| 群视频为什么必须 SFU，P2P 上限几个人？ | [66.4](66.4-音视频信令与媒体传输.md) | P2P 上行 = N−1 路，4 人已到上限、5 人不可行；群视频用 SFU 每人只上行 1 路，代价是服务端出口 N×(N−1) |
| 10 万人大群发一条消息，写扩散几次？ | [66.5](66.5-群聊与消息扩散.md) | 10 万次（再乘设备数）；所以大群必须转读扩散，只推"有新消息" |
| 群已读为什么难做？ | [66.5](66.5-群聊与消息扩散.md) | 天然 O(N²)：每人要看所有人的已读；只能做聚合计数（已读 87/500），不做逐人同步 |
| 直播延迟为什么降不到 1 秒？ | [66.6](66.6-流媒体处理.md) | HLS 延迟下限 ≈ 3×切片时长；要 <1s 得换 WebRTC/低延迟协议，不是调参数 |
| 一路 1080p 转码成本多少？ | [66.6](66.6-流媒体处理.md) | 用本机实测的实时倍数算：软编单核转几路、GPU 省 CPU 但同码率画质更差，成本要一起算 |

## 3 个最常见误解

| 误区 | 现实 |
|---|---|
| "IM 就是 WebSocket + 一张消息表" | WebSocket 只解决"连接在"；消息会不会丢、多端会不会乱、群发会不会写爆，全靠后面的四层。真实系统里连接层代码只占一小部分（经验估计，无权威统计），大头是投递、同步、扩散与存储 |
| "消息可靠性靠 MQ 的重试就够了" | MQ 只能保证"进入队列的不丢"，而 IM 的丢点有五个：客户端发失败、服务端没落库、落库没投递、离线没存、推送没叫醒。**每一段的失败模式不同，兜底手段也不同**，靠单一机制兜不住 |
| "音视频难在编解码" | 编解码是标准库的事；线上问题的大头在**网络路径与拓扑**（经验判断，无权威统计）：NAT 打洞失败、TURN 没部署、群视频 P2P 上行爆炸、信令状态机并发缺陷。选型（P2P/SFU/MCU）比调编码参数影响大一个数量级 |

## 读完自检（入门级 3 题）

**Q1** 一个 IM 已经有 API 网关和消息队列，为什么还要单独一组"长连接网关"？

▸ 答案：API 网关是**无状态**的请求入口，处理的是"请求-响应"；长连接网关是**有状态**的连接路由层，处理的是"这条连接现在在哪"。消息要从业务服务到达某个用户的某条连接，必须知道 `userId → 网关 → connId` 的映射，这个映射只能由长连接网关在连接建立时注册、断开时注销。把长连接塞进 API 网关不是不行，而是会让无状态层变成有状态层，扩缩容、发布、故障隔离全部退化（[66.1](66.1-长连接网关.md) 与 [37.2 无状态化](../../L3-质量属性/37-扩展性/37.2-无状态化.md) 的张力）。

**Q2** 消息已经持久化到数据库了，为什么用户还可能"收不到"？

▸ 答案：持久化只覆盖了五段接力中的第二段。剩下四段各有丢法：上行时客户端以为失败其实服务端成功（重复而非丢）、下行投递时连接已断但服务端不知道（半开连接）、离线存储过期或被挤出（保留策略）、推送通道失败且用户没打开 App（叫醒失败）。所以"存了"只保证"数据在"，不保证"人看到"；证明没丢要靠**会话级 seq 连续性 + 端到端对账**（[66.2](66.2-消息可靠投递与离线.md)）。

**Q3** 10 万人大群，为什么不能像 500 人群一样"发一条给每人写一份"？

▸ 答案：写放大的公式是 `写次数 = 1（群时间线）+ 在线人数 × 设备数（投递）+ 离线人数 × 1（收件箱）`。本机实测：1000 人群单条写扩散 8.3ms（约 1002 次 Redis 写），10 万人群单条 507–574ms（约 10 万次 Redis 写），且这 10 万次写里大多数是给**离线成员**预付的、可能永远不被读。按这个成本反推，10 条/秒的活跃群单节点写到 2000 人左右就满了（[66.5](66.5-群聊与消息扩散.md)）。所以大群必须切成**读扩散**：消息只写一份到群时间线，成员按各自游标来拉；只对在线成员做推送（且在线的还要经 [66.1](66.1-长连接网关.md) 的网关）。阈值由"写扩散成本 vs 读扩散成本谁先撞上单节点容量"算出来。
