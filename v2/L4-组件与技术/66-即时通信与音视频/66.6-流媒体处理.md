# 66.6 流媒体处理 (转码 / 直播推拉流)

## 一句话

> 直播是一条**延迟预算 + 转码成本预算**的流水线：协议决定延迟下限，GOP 对齐决定切片质量，转码路数决定钱。

## 链路五段：每一段的延迟是谁给的

直播从摄像头到观众屏幕，固定五段。判断"延迟高"要落到段落上，否则只能盲调：

```text
采集/编码            推流              接入 + 转码              分发            播放
(camera→H.264/H.265) (RTMP/SRT/WHIP)  (ingest→转码→切片)       (CDN/边缘)      (HLS/FLV/RTC)
   ↑ 编码器预读         ↑ TCP 缓冲         ↑ 首片等待=切片时长       ↑ 回源/命中      ↑ 3 片回退+缓冲
```

| 段 | 干什么 | 延迟预算 | 依据 | 可优化项 |
|---|---|---|---|---|
| 采集+编码 | 采集帧 → H.264/H.265 | 0.1–1.6s | 本机实测：默认参数比 `-tune zerolatency` 首片多等 **0.89s** | `-tune zerolatency`、`-bf 0`、硬编 |
| 推流 | 编码流 → 接入点 | 0.1–0.5s | 实测 RTMP `-re -c copy` 推 602 帧/20.01s | SRT/QUIC、就近接入 |
| 接入 + 转码 | 收流、转多档、切片 | 0.1–0.5s（直通）/ 编码耗时的 1/N | 实测 720p 转码 2.14× 实时 | 一次解码多路输出、硬编 |
| 切片 + 分发 | 切片落 CDN、播放列表更新 | **≥ 1 个切片时长** | 实测首个切片 1.87–2.76s 可播 | 缩短切片、LL-HLS |
| 播放 | 下载、解码、缓冲 | **3 个切片回退 + 缓冲** | Apple HLS 规范建议从 live edge 往回 3 个切片起播 | 预加载、首片低码率、边缘命中（见 [9.1 边缘缓存原理](../../L0-运行时底座/9-CDN与边缘/9.1-边缘缓存原理.md)） |

> 🔑 **HLS 的端到端延迟下限 ≈ 3 × 切片时长 + 编码延迟**。2s 切片对应约 6–9s。想要 1s 以内，换协议（WebRTC/LL-HLS），不要指望调 `-hls_time`。

**媒体流不是事件流**：它不按时间窗口/水位线处理，按 GOP 与切片切分，状态是"当前 GOP、当前切片、关键帧位置"，不是"窗口内的聚合值"——流处理模型与时间语义的通用结论见 [62.1 流处理模型与时间语义](../62-实时计算与流处理/62.1-流处理模型与时间语义.md)，但窗口/水位线那套不能照搬。

先破掉五个流行误区，后面所有实测都是为它们服务的：

| 误区 | 现实 |
|---|---|
| 把 `-hls_time` 调到 1s 就能 1s 延迟 | 协议要求攒够 3 片才稳；实测 2s 切片首片 1.87s 只是"可播"，端到端还要加回退与缓冲 |
| 硬编一定比软编快很多 | 实测只快 **1.76×**；CPU 秒只差 **2.02×**，因为 1080p 软件解码两端都逃不掉 |
| 转码只是"把清晰度调低" | 转码产出是码率阶梯 + 合规审核 + 水印台标 + 录制格式统一 |
| GOP 设 1s 延迟就会更低 | 实测 2s 切片下 1s GOP 切片仍是 2.0s；1s GOP 的收益在超低延迟协议与 ABR 切换密度 |
| 切片时长随便填 | 切片只能落在关键帧上；GOP 与切片不整除时实测出现 1.5s/3.0s 混合切片 |

## 协议对比：延迟下限是协议给的

| 协议 | 传输层 | 典型延迟（量级） | 抗丢包 | CDN 支持 | 播放器兼容 | 典型场景 |
|---|---|---|---|---|---|---|
| RTMP | TCP | 1–3s | 弱（重传=队头阻塞） | 推流端全覆盖，分发弱 | 推流软件全覆盖 | **推流事实标准** |
| SRT | UDP + ARQ | 0.5–2s（公开量级） | 强（选择性重传） | 中等 | 需 SRT 网关/播放器 | 弱网、跨国上行回传 |
| WebRTC / WHIP | UDP / SRTP | **< 500ms** | 中（NACK/FEC） | 弱（需 RTC 分发） | 浏览器原生 | 连麦、互动直播（见 [66.4 音视频信令与媒体传输](66.4-音视频信令与媒体传输.md)） |
| HTTP-FLV | TCP | 1–3s | 弱 | 强（国内 CDN 普遍） | 需 flv.js 类播放器 | 国内低延迟直播 |
| HLS | HTTP / TCP | 3–30s（实测 2s 切片约 8–9s） | 依赖 TCP + CDN | 最强 | 原生（iOS/Android/浏览器） | 大并发观看、回看、时移 |
| LL-HLS | HTTP/2 + 部分切片 | 2–5s（公开量级） | 同上 | 部分 CDN | 新版播放器 | 低延迟 + 兼容性折中 |
| DASH + CMAF | HTTP / TCP | 同 HLS | 强 | 强 | MSE 播放器 | 非 Apple 生态、DRM |

> ⚠️ SRT 的延迟数字是公开量级：本机 ffmpeg 9.0.2 **没有编译 libsrt**（实测 `-protocols` 里无 srt），所以本节 SRT 只做选型对比，不做实测。

选型直接查表：

| 你的情况 | 选什么 |
|---|---|
| 主播推流（上行） | RTMP；弱网/跨国换 SRT |
| 观众能接受 5–10s 延迟 | HLS（TS 或 fMP4 均可） |
| 观众要 2–3s | HTTP-FLV（国内）/ LL-HLS（海外与 Apple） |
| 要 < 1s、还要连麦 | WebRTC，转推 HLS 做录制回看 |
| 需要 DRM、多终端自研播放器 | DASH + CMAF |

## 为什么必须转码，码率阶梯怎么定

转码不是为了"变小"，是为了把不可控的源变成**可预期的商品**：① 源编码/分辨率/码率不可控（手机、OBS、硬件编码器各不相同）；② ABR 需要多档适应网络；③ 合规审核/鉴黄/字幕需要统一解码；④ 水印台标；⑤ 录制与回看的格式统一。

反例也要写清楚：**源已是 H.264 720p、只服务单一终端**时，`-c copy` 直通（只换封装、不重编码）更省——实测 RTMP 链路里 copy 前后码率 8870.3 → 8906.7 kbps（差 0.4%，只是封装开销）。

码率阶梯（公开经验量级，GOP 统一 2s）：

| 档位 | 分辨率 | 帧率 | H.264 码率 | H.265 码率 | 场景 |
|---|---|---|---|---|---|
| 360p | 640×360 | 30 | 600–800k | 400–550k | 移动弱网/省流 |
| 540p | 960×540 | 30 | 1200–1500k | 800–1000k | 中端机 |
| 720p | 1280×720 | 30 | 2500–3000k | 1600–2000k | **主力档（本次实测 2500k）** |
| 1080p | 1920×1080 | 30 | 4500–6000k | 3000–4000k | 大屏/WiFi（本次实测 5000k） |

H.265 同画质省 30–50% 带宽（公开量级），代价是兼容性（老设备/浏览器）与专利池成本。码率和分辨率要匹配，用每像素比特 `bpp = 码率 / (宽 × 高 × 帧率)` 校验：1080p30@5000k ≈ 0.080 bpp、720p30@2500k ≈ 0.090 bpp；**低于 0.06 bpp 一定糊**（经验值），此时加分辨率不如加码率。

**编码参数不是"调清晰度"，是"决定钱花在哪"**。三种码率控制模式先选对：

| 模式 | 参数 | 行为 | 适合 | 坑 |
|---|---|---|---|---|
| CBR | `-b:v -maxrate -bufsize`（bufsize ≈ 2×maxrate） | 码率贴住目标、波动小 | 直播：带宽与 CDN 按峰值规划 | 简单画面也烧同样的钱；bufsize 太小画质会崩 |
| VBR | 只给 `-b:v`（或两遍编码） | 复杂场景多给码率、简单场景省 | 点播 / 录制 | 峰值不可控，直播按峰值买带宽会超 |
| CRF | `-crf 18–23` | 恒定质量，码率随内容浮动 | 点播源、归档母版 | 码率不可预期，不能用于直播计费 |

三个容易漏的参数：

- **profile/level 显式写**：`-profile:v high -level 4.1` 覆盖 1080p30，老设备与浏览器都认；升到 `-level 5.1` 省不了多少码率，但老 Android/iOS 可能直接不硬解。
- **`-force_key_frames` 的用途与坑**：`-force_key_frames "expr:gte(t,n_forced*2)"` 按时间强制插 IDR，用于"源关键帧不可控、输出必须对齐"的场合；本实验造抖动源就靠它（g4 的 44 个关键帧、间隔 0.033–2.0s，随机种子 20261121）。副作用是切点不再由 `-g` 控制，两个都设时要确认谁先命中，否则输出了 `-g` 也挡不住的不规则 GOP。
- **`-g 60` 只在 30fps 下是 2s**：25fps 要写 50、60fps 要写 120，`-keyint_min` 同步改；换帧率不改 `-g`，GOP 实际时长就变了（25fps 下 `-g 60` = 2.4s），切片时长随之整体偏移。

## 实测：一次解码、两档输出、HLS 打包

环境：macOS 15.6 / Apple Silicon arm64（8 核）/ ffmpeg 9.0.2（libx264、h264_videotoolbox、hls、flv）/ 2026-11-21。**所有耗时均为同机并行任务下测得**，功能类结论确定成立，速度类允许 ±20% 波动。正文引用的两个文件字节数——fMP4 拼接后的 708,397B、录制 flv 的 22,020,096B——都是实测文件大小，可在 `.cache/ch66/s666/out/` 下复核（`ls -l` 即可）。

源：60s 1080p30 合成源（`testsrc2` 运动纹理 + `sine`），固定 2s GOP：

```bash
# 生成实验源：60s、1080p30、2s 固定 GOP（-g 60 帧 = 2s）
ffmpeg -y -f lavfi -i "testsrc2=size=1920x1080:rate=30:duration=60" \
  -f lavfi -i "sine=frequency=440:sample_rate=48000:duration=60" \
  -c:v libx264 -preset veryfast -crf 18 -pix_fmt yuv420p \
  -g 60 -keyint_min 60 -sc_threshold 0 \
  -c:a aac -b:a 128k -ac 2 -movflags +faststart \
  .cache/ch66/s666/out/source_1080p30.mp4
```

真实读数：`bit_rate=8870321`、`size=66527414`、`nb_frames=1800`，关键帧时间戳 `0 2 4 6 … 58`（30 个，间隔恒为 2.0s）。

一条命令、一次解码、两档输出（同步产出 master playlist）：

```bash
# 一次解码两档编码：split 后 1080p 原分辨率 5000k + 720p 缩放 2500k
# 关键：-g 60 -keyint_min 60 -sc_threshold 0 保证两档关键帧严格对齐，切片才能对齐
ffmpeg -y -i .cache/ch66/s666/out/source_1080p30.mp4 \
  -filter_complex "[0:v]split=2[v1080][v720src];[v720src]scale=1280:720[v720]" \
  -map "[v1080]" -map 0:a:0 -map "[v720]" -map 0:a:0 \
  -c:v:0 libx264 -preset veryfast -b:v:0 5000k -maxrate:v:0 5000k -bufsize:v:0 10000k \
  -c:v:1 libx264 -preset veryfast -b:v:1 2500k -maxrate:v:1 2500k -bufsize:v:1 5000k \
  -g 60 -keyint_min 60 -sc_threshold 0 -c:a aac -b:a 128k \
  -f hls -hls_time 2 -hls_playlist_type vod -hls_segment_type mpegts \
  -hls_segment_filename ".cache/ch66/s666/out/hls_ts/%v/seg_%03d.ts" \
  -master_pl_name master.m3u8 \
  -var_stream_map "v:0,a:0,name:1080p v:1,a:1,name:720p" \
  .cache/ch66/s666/out/hls_ts/%v/index.m3u8
```

master playlist 实测（注意 `BANDWIDTH` 是播放器用来选档的上限，`AVERAGE-BANDWIDTH` 才是平均）：

```text
#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=6011488,AVERAGE-BANDWIDTH=5304457,RESOLUTION=1920x1080,CODECS="avc1.4d4028,mp4a.40.2"
1080p/index.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=3125312,AVERAGE-BANDWIDTH=2750414,RESOLUTION=1280x720,CODECS="avc1.4d401f,mp4a.40.2"
720p/index.m3u8
```

读数表（切片统计由 `#EXTINF` 逐片解析，见 `.cache/ch66/s666/code/parse_hls.py`）：

| 档位 | 名义码率 | 首片实测码率 | 相对名义 | 切片数 | EXTINF min/max | 目录体积 |
|---|---|---|---|---|---|---|
| 1080p | 5000k + 128k | 5,948,040 | +16% | 30 | 2.000s / 2.000s | 38MB |
| 720p | 2500k + 128k | 2,984,437 | +14% | 30 | 2.000s / 2.000s | 20MB |

两档 `#EXTINF` 全部是 `2.000000`、标准差 0.000、`#EXT-X-TARGETDURATION:2`——**不是因为 hls_time 写得好，而是因为 GOP 恰好 2s**（下一节反证）。首片码率超名义 +14% 的原因是首片包含 I 帧且带容器开销，后续切片会回落；`BANDWIDTH` 按峰值算就是这个道理。

这一次转码的 CPU 账：`bench: utime=141.903s stime=7.739s rtime=67.427s`（60s 内容、两路编码）。一次解码 N 次编码是省钱的根基——若分两条命令各解一次码，光解码就白干一遍。

## 实测：GOP 与切片对齐（核心反证）

环境同上：macOS 15.6 / Apple Silicon arm64（8 核）/ ffmpeg 9.0.2 / 2026-11-21，同机并行任务下测得。

机制只有一句话：**HLS 切片只能切在关键帧上，所以每片时长必然是 GOP 的整数倍**。`hls_time` 只是"目标"，不是"结果"。

四组对照，同一源、同一码率 2500k、同一目标 2s 切片：

| 组 | 编码参数 | 源关键帧情况 | 切片数 | EXTINF min | max | 均值 | 标准差 | TARGETDURATION |
|---|---|---|---|---|---|---|---|---|
| g1 | `-g 60`（2s GOP） | 恒定 2.0s | 30 | 2.000s | 2.000s | 2.000s | **0.000** | 2 |
| g2 | `-g 30`（1s GOP） | 恒定 1.0s | 30 | 2.000s | 2.000s | 2.000s | **0.000** | 2 |
| g3 | `-g 45`（1.5s GOP） | 恒定 1.5s | 30 | 1.500s | 3.000s | 2.000s | **0.707** | **3** |
| g4 | 源关键帧抖动 + `-c copy` 切片 | 44 个关键帧，间隔 0.033–2.0s，均值 1.352s | 30 | **0.167s** | **3.767s** | 2.000s | **1.001** | **4** |

g3 的真实时长序列（前 9 片）：`3 1.5 1.5 3 1.5 1.5 3 1.5 1.5`——每 3 片一个循环，永远凑不出 2.0s。
g4 的真实时长序列（前 9 片）：`2 2.2 3.76667 0.166667 2.93333 1.5 1.76667 3.46667 2`。

三条结论，全部能从数据里读出来：

1. **g2 说明"1s GOP 不降 HLS 延迟"**：1s 是 2s 的整数因子，切片照样 2.0s。1s GOP 的收益是 ABR 能更频繁切档、以及 LL-HLS/低延迟协议有更细的切点，不是 HLS 变快。
2. **g3 说明"非整数倍就抖动"**：1.5s 与 2s 不整除，切点只能在 1.5s 的整数倍里挑，于是 1.5/3.0 交替，`TARGETDURATION` 被迫从 2 抬到 3。播放器会按 3s 规划缓冲与重试，抖动片还会触发多余的起播判断——这是"看起来配置没错、线上就是卡"的典型来源。
3. **g4 说明"源不受控时更惨"**：真实源的关键帧间隔从来不等长（编码器在场景切换处额外插 I 帧）。直通 `-c copy` 时你完全没有切点控制权：30 片里出现 0.167s 的碎片片（5 帧一个文件，HTTP 请求数与建连开销按片计，翻倍都不止），`TARGETDURATION` 被抬到 4，是目标值的 2 倍。

GOP 与切片的取值判据：

| 目标 | GOP | 切片时长 | 说明 |
|---|---|---|---|
| 低延迟 HLS | 2s | 2s | HLS 主流下限；端到端约 6–9s |
| 平衡（默认推荐） | 2s | 4s | 切片少一半，抗抖动更好 |
| 兼容/回看 | 2s | 6s | 首片更慢，但 CDN 回源压力小 |
| 超低延迟 | 1s 或 0.5s | — | 换 LL-HLS/HTTP-FLV/WebRTC，别在 HLS 上做 |

## HLS 封装：m3u8 必读字段与 TS vs fMP4

| 字段 | 作用 | 实测值与坑 |
|---|---|---|
| `#EXTINF` | 本片时长（秒） | 实测 `2.000000`；统计切片质量就看它 |
| `#EXT-X-TARGETDURATION` | 所有片时长的天花板（向上取整） | 实测 2 / 3 / 4——随 GOP 错位膨胀，直接推高播放器缓冲 |
| `#EXT-X-MEDIA-SEQUENCE` | 直播窗口首片序号 | 时移/回看靠它定位；**不能按时间戳排序切片** |
| `#EXT-X-DISCONTINUITY` | 断点标记 | 断流重推会插入，播放器必须重初始化解码器 |
| `#EXT-X-MAP` | fMP4 的 init 段 | 实测 `URI="init.mp4"`，840 字节 |
| `#EXT-X-PART` / `PART-INF` | LL-HLS 部分切片 | 公开规范；本机 ffmpeg 9.0.2 的 hls muxer 不产出部分切片 |

TS 与 fMP4（CMAF）实测对比（同为 60s、720p、2s 切片）：

| 维度 | MPEG-TS | fMP4 / CMAF |
|---|---|---|
| 单片可独立解码 | 是（每片自带 PAT/PMT） | 否，必须先下 init 段 |
| 文件构成（实测） | 1 个 m3u8 + 30 个 ts | 1 个 m3u8 + 1 个 init.mp4 + 30 个 m4s |
| 目录体积（实测 720p） | 20MB | 18MB |
| 单片探测 | `ffprobe xxx.ts` 直接可用 | `ffprobe init.mp4` 报错：`no tfhd was found` |
| 拼接校验（实测） | — | `cat init.mp4 seg_000.m4s` 后可读：2.066667s / 708,397B |

`ffprobe init.mp4` 报错不是文件坏了，而是 init 段只有 moov 里的 track 描述、没有媒体数据（moof/mdat 在 m4s 里）。**校验 fMP4 要读 m3u8 或把 init 与分片拼起来**，这条几乎每次换 CMAF 都会踩。fMP4 的目录里还有一个实测细节：`#EXT-X-VERSION:7`（TS 是 3）。

端到端延迟估算公式（本地无网络损耗下）：

```text
HLS 延迟 ≈ 编码延迟 + 3 × 切片时长 + 播放器缓冲
         ≈ 0.1~1.6s + 3×2s + 1~2s ≈ 8~10s      （2s 切片，实测首片 1.87~2.76s）
LL-HLS  ≈ 编码延迟 + (1 个 part hold-back + 1 个 part) ≈ 1~2s   （公开规范量级，本机未产出 PART）
```

## 录制 / 时移 / 水印：同一条流分叉出三种产物

一句话原则：**所有产物都从"转码后的输出流"分叉，绝不为每种产物二次解码**。二次解码 = 多一份 CPU + 多一代画质损失。

| 产物 | 从哪分叉 | 机制与实测 | 成本口径 |
|---|---|---|---|
| 录制（MP4/FLV） | 转码输出 `-c copy` 落盘 | 实测 20s 1080p 流 copy 成 flv 得 22,020,096B，码率与源一致（8906.7 kbps） | 只有磁盘 IO，无编码 |
| 时移/回看 | 保留切片 + 播放列表回溯 | 实测 `-hls_list_size 0` 保留全部 30 片（60s）；直播窗口默认 5–6 片 | 存储 = 切片数 × 切片时长 × 码率 |
| 水印/台标 | 转码滤镜（`drawtext` / `overlay`） | 同一遍编码里叠加，不增加解码 | 编码开销约 +5%（公开量级）；二次编码=成本翻倍 |
| 截图/封面 | 关键帧直接解 | `-ss` 定位后只解 1 帧，不要解整段 | 毫秒级 |

两个实测坑：① 录制文件要**正常收尾**才有可信的时长/大小——本次实验里服务端被强杀，得到的 flv `duration=0.000000`（流参数可读、时长不可信），生产要用优雅停止或分片录制（每 5–10 分钟切一个文件，坏一个不牵连整场）；② 时移窗口是纯存储决策：2s 切片、5Mbps、保留 1 小时 ≈ `5Mbps × 3600s ÷ 8 ≈ 2.25GB/路`，要和"回看价值"一起算。水印则要固定在**转码这一遍**做完，任何"录完再加水印"的方案都是多一代重编码。

## 实测：编码成本（软编 vs 硬编）

环境同上：macOS 15.6 / Apple Silicon arm64（8 核）/ ffmpeg 9.0.2 / 2026-11-21，同机并行任务下测得。

同一任务：60s 1080p30 → 720p@2500k，CBR 味道参数（`-b:v 2500k -maxrate 2500k -bufsize 5000k`），各跑 3 次取中位（3 次取中位这种压测取值方法的通用做法见 [57.1 压测方法论](../../L5-工程效能/57-容量与成本治理/57.1-压测方法论.md)）：

| 编码器 | 3 次墙钟 | 中位 | 实时倍数 | 1 小时内容耗时 | 输出实际码率 |
|---|---|---|---|---|---|
| libx264 `-preset veryfast` | 24.30 / 29.05 / 28.07s | 28.07s | **2.14×** | 28.1min | 2,525,876 bps |
| h264_videotoolbox（硬编） | 21.07 / 15.97 / 15.54s | 15.97s | **3.76×** | 16.0min | 1,751,022 bps |

硬编/软编耗时比 **0.57×**（硬编快 1.76 倍）。但只看墙钟会高估硬编——CPU 账完全不同：

| 编码器 | utime | stime | rtime | 每 60s 内容 CPU 秒 | 折算每路实时核数 |
|---|---|---|---|---|---|
| libx264 | 64.041s | 3.023s | 28.098s | **67.1** | **1.12 核** |
| h264_videotoolbox | 31.282s | 1.898s | 24.271s | **33.2** | **0.55 核** |

> 🔑 硬编只省"编码"那段 CPU，**软件解码两端都要做**：实测 CPU 秒 67.1 → 33.2，只差 2.02 倍，不是宣传里的数量级。要再省一半，得把解码也搬上硬解（`-hwaccel videotoolbox` / NVDEC）。

同码率画质（10s 片段，对 720p 无损参考算 SSIM，各 3 次）：

| 编码器 | 名义码率 | 实际码率 | SSIM All（3 次） |
|---|---|---|---|
| libx264 veryfast | 2500k | 2,630,789 bps | 0.980330 / 0.980327 / 0.980335 |
| h264_videotoolbox | 2500k | 1,748,362 bps | 0.979042 / 0.979042 / 0.979042 |

注意第二个陷阱：**硬编根本没达到目标码率**（写 2500k 只出 1751k，约 70%）。所以"同码率对比"必须按实际码率对齐，否则结论会反。按每 bit 效率看硬编并不差，但它的码率控制精度对直播 CBR 是硬伤——码率不达标会表现为"码率忽高忽低、观众带宽规划失效"。

补码率实验（硬编加码，看能否追平软编的 SSIM）：

| 硬编名义码率 | 硬编实际码率 | SSIM All |
|---|---|---|
| 3000k | 2,098,854 | 0.979565 |
| 4000k | 2,796,191 | 0.980238 |
| 5000k | 3,501,514 | 0.980663 |
| 7000k | 4,655,687 | 0.981188 |

要超过软编@2500k 的 0.980330，硬编需要实际约 3.5Mbps（名义 5000k，是名义值的 2 倍）——按实际码率算**多 33%**。这就是"硬编省 CPU 但要拿带宽补"的量化口径。

画质对比的边界必须写：加噪变体（`noise=alls=15:allf=t+u`，模拟摄像头颗粒）反而硬编 SSIM 更高（x264 0.758798@2.53Mbps vs 硬编 0.764750@1.75Mbps）。原因是噪声不可压缩，**谁把它抹得更平谁 SSIM 更高**——所以含噪内容不能只用 SSIM 判画质，要看 VMAF 或人眼。低码率下差距仍一致：clean@1000k 软编 0.977465 vs 硬编 0.974475；clean@1500k 软编 0.978883 vs 硬编 0.977040。

8 核能转几路、每路每小时多少钱（全部由上面的实测 CPU 秒推出；口径是 **1080p 源 → 720p 输出**，输出 1080p 约需 ×1.5–2 的 CPU 秒，本机未单独测）：

```text
x264 720p 实时转码：67.1 CPU秒 / 60s 内容 = 1.12 核/路
8 核理论上限：8 / 1.12 ≈ 7 路；按 70% 规划余量 ≈ 5 路
硬编：33.2 / 60 = 0.55 核/路 → 8 核 ≈ 14 路（但媒体引擎路数与码率补偿另算）
```

按 8 vCPU 通用实例（CPU 转码）公开报价量级 ￥0.4–1.0/小时折算：每路 720p 转码约 **￥0.06–0.14/小时**（不含带宽）。GPU 实例（T4/A10 这类 NVENC，公开报价量级 ￥2–6/小时）单价高 3–6 倍，但每路只占 0.55 核、单机能跑的路数多，而且要按上面的结论多补约 33% 实际码率——**GPU 要用"更少机器 + 更高带宽"一起算，不能只比实例单价**。而带宽账是另一回事：720p@2.5Mbps 一个观众一小时约 `2.5Mbps × 3600s = 1.125GB`，按国内 CDN 公开量级 ￥0.2/GB 算约 **￥0.22/观众·小时**——**观众数上去以后，带宽比转码贵一个量级**。所以省钱顺序是：先直通、再砍档位、最后才谈硬编；加一档 360p 让移动端省 60% 流量，往往比换硬编更划算（成本模型见 [39.1 成本模型与单位经济](../../L3-质量属性/39-成本/39.1-成本模型与单位经济.md)，容量规划见 [34.2 性能建模 (利特尔法则、排队论)](../../L3-质量属性/34-性能/34.2-性能建模.md)）。

## 实测：延迟构成（编码器预读值 0.89s）

环境同上：macOS 15.6 / Apple Silicon arm64（8 核）/ ffmpeg 9.0.2 / 2026-11-21，同机并行任务下测得。

同一 `-re` 实时输入、同一 2s 切片，只差 `-tune zerolatency`：

| 参数组 | 起播 → 首片可播 | 后续切片出现间隔 | 切片时长统计 |
|---|---|---|---|
| 默认（x264 默认 rc-lookahead=40 帧） | **2.76s** | 2.01 / 2.00 / 1.99 / 1.20 | 5 × 2.000s，std 0.000 |
| `-tune zerolatency` | **1.87s** | 1.98 / 2.05 / 1.98 / 2.03 | 5 × 2.000s，std 0.000 |

| 项目 | 数值 |
|---|---|
| 差值 = 预读代价 | **0.89s** |
| 切片节奏 | 稳态约 2.0s 一片（±0.05s） |
| 结论 | 直播编码器必须开 `-tune zerolatency`，否则白送近 1s |

注意这是**同机并行任务下测得**的绝对值，机器有负载时每条链路都偏慢；差值的量级可靠（预读 40 帧 @30fps ≈ 1.3s 的理论上限，实测 0.89s 是被 -re 输入节奏重叠后的净值）。

首帧/秒开的六个动作，按收益排序：① 起播先用最低档，稳定后 1–2s 内切目标档（首片码率直接决定首片下载时间）；② 预取下一片与播放列表；③ 连接复用、HTTP/2 多路复用（见 [8.5 HTTP/1.1、HTTP/2、HTTP/3 (QUIC)](../../L0-运行时底座/8-网络/8.5-HTTP1.1-HTTP2-HTTP3.md)）；④ 边缘就近与缓存命中（见 [9.0 CDN 全景：它到底是什么](../../L0-运行时底座/9-CDN与边缘/9.0-CDN全景.md)）；⑤ 关键帧严格对齐，让每片都能独立起播（`independent_segments`）；⑥ 编码端 `-tune zerolatency`（实测省 0.89s）。①③④ 在客户端/CDN 侧，②⑤⑥ 在服务端/编码侧——定位首帧慢，先分清是哪一侧的问题。

## 实测：RTMP 推拉流链路

环境同上：macOS 15.6 / Apple Silicon arm64（8 核）/ ffmpeg 9.0.2 / 2026-11-21，同机并行任务下测得。

用 ffmpeg 的 `-listen 1` 当最小 RTMP 服务端（生产不用它，见落地四件套）。三个进程：服务端收流并切 2s HLS、推流端 `-re` 实时推 20s、轮询服务端播放列表：

```bash
# 终端 1：RTMP 服务端（-listen 1 在本机 19350 端口等一个推流连接），收到流后直接切 2s HLS
ffmpeg -y -listen 1 -i "rtmp://127.0.0.1:19350/live/test" \
  -c copy -f hls -hls_time 2 -hls_list_size 0 -hls_segment_type mpegts \
  -hls_segment_filename "/path/rtmp_hls/seg_%03d.ts" /path/rtmp_hls/index.m3u8

# 终端 2：推流端，-re 按实时节奏推（不 -re 会把整场瞬间推完），-c copy 不改编码
ffmpeg -y -re -t 20 -i /path/source_1080p30.mp4 -c copy -f flv \
  "rtmp://127.0.0.1:19350/live/test"
```

实测读数：

| 观测点 | 实测值 |
|---|---|
| 服务端收到的流 | `h264 (High) 1920x1080, 8733 kb/s, 30 fps` + `aac 48000 Hz stereo 128 kb/s`，`start 0.067` |
| 推流端 | `frame=602`、`time=20.01s`、`8906.7 kbits/s`（源 8870.3 kbps，copy 偏差 0.4%） |
| 推流起点 → 首片进播放列表 | **1.55s**（后续 3.53 / 5.57 / 7.58 / 9.59 / 11.54s，间隔约 2.0s） |
| 切片产出 | 11 片 = 10 × 2.000s + 1 × **0.066s 尾巴片**，`TARGETDURATION:2`，总 20.1s |
| 单片实测 | `duration=2.058833`、`size=2,286,832`、`bit_rate=8,885,934` |
| 拉流校验 | `ffprobe index.m3u8` 返回 1080p h264 + aac，可正常像播放器一样读取 |
| 第二个客户端 | 推流进行中再连 → `Connection refused`（`-listen 1` 只服务 1 个连接） |

那个 0.066s 的尾巴片值得单独说：服务端看到的流 `start 0.067`，`-c copy` 切片按累计时长判断，起点偏移让最后一片只剩 2 帧。**直通切片时时间戳起点、断流重推都会制造碎片片**，生产上要用 `-copyts` 或让接入服务端（SRS/MediaMTX）统一重置时间轴。

另一个必须写清的边界：`-listen 1` 在推流端 EOF 后，两端 RTMP close 握手会互等卡住（实测需 watchdog 强杀才收场），而且没有多路分发、鉴权、GOP 缓存、录制。**它只配做链路验证**。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名。** 转码/切片：**ffmpeg 9.0.2**（本机实测版本；服务端用 GStreamer 或云转码亦可）。接入分发：**SRS**（国产、RTMP/SRT/HTTP-FLV/HLS 全、社区活跃）或 **MediaMTX**（单二进制、配置极简）或**云直播**（阿里云视频直播/腾讯云直播，含转码与 CDN 一体）。替代：nginx-rtmp（维护停滞，不推荐新项目）、LiveKit（RTC 场景，见 [66.4 音视频信令与媒体传输](66.4-音视频信令与媒体传输.md)）。

**可抄（已在 ffmpeg 9.0.2 上跑通）。** 三件套：

```bash
# ① 推流端（采集侧必须自己定 GOP，这是切片整齐的前提）
ffmpeg -re -i camera_or_file -c:v libx264 -preset veryfast -tune zerolatency \
  -b:v 2500k -maxrate 2500k -bufsize 5000k \
  -g 60 -keyint_min 60 -sc_threshold 0 -pix_fmt yuv420p \
  -c:a aac -b:a 128k -ar 48000 -f flv "rtmp://ingest.example.com/live/streamkey"

# ② 服务端转码阶梯（一次解码两档，输出 2s HLS）
ffmpeg -i "rtmp://127.0.0.1:19350/live/test" \
  -filter_complex "[0:v]split=2[a][b];[b]scale=1280:720[b2]" \
  -map "[a]" -map 0:a -map "[b2]" -map 0:a \
  -c:v:0 libx264 -preset veryfast -b:v:0 5000k -maxrate:v:0 5000k -bufsize:v:0 10000k \
  -c:v:1 libx264 -preset veryfast -b:v:1 2500k -maxrate:v:1 2500k -bufsize:v:1 5000k \
  -g 60 -keyint_min 60 -sc_threshold 0 -c:a aac -b:a 128k \
  -f hls -hls_time 2 -hls_list_size 6 -hls_flags delete_segments+independent_segments \
  -hls_segment_filename "/data/hls/%v/seg_%05d.ts" -master_pl_name master.m3u8 \
  -var_stream_map "v:0,a:0,name:1080p v:1,a:1,name:720p" "/data/hls/%v/index.m3u8"

# ③ 校验：切片时长必须等于 GOP 整数倍，TARGETDURATION 不许超目标
ffprobe -v error -show_entries format=duration -show_entries stream=codec_name,width,height \
  -of default=noprint_wrappers=1 /data/hls/720p/index.m3u8
grep -E '^#EXTINF|^#EXT-X-TARGETDURATION' /data/hls/720p/index.m3u8 | sort | uniq -c
```

**可验（真实输出，成功/失败各一条）。** 成功：上面命令的 720p 播放列表里 `#EXTINF:2.000000` 出现 30 次、`#EXT-X-TARGETDURATION:2`；`ffprobe` 报 `width=1280 height=720`、`duration=60.000000`。失败（预期失败，用于识别 CMAP 误用）：`ffprobe init.mp4` 报 `no tfhd was found` —— 这是正常的，init 段本来就没有媒体数据，要读 `index.m3u8`。

**可退。** ① 关转码直通：输出侧改 `-c copy`（只换封装，实测码率基本不变：8870.3 → 8906.7 kbps），转码集群故障时 30s 内自动切直通保直播不断；② 降档降码率：砍掉 1080p 档、各档码率下调 30%（画质掉一档，带宽立省）；③ 换协议：HLS 卡顿时切 HTTP-FLV（国内）或退回大切片 HLS 保兼容；④ 关水印重编：水印在转码滤镜里做（别做二次编码），异常时直接去掉 filter 重跑；⑤ 灰度：按 stream_id 哈希切转码集群/新参数组。

**什么时候别用这套配置。** 单终端且源已合规 → `-c copy` 直通；要 < 1s → 别用 HLS，走 WebRTC/HTTP-FLV；纯点播 → 用 CRF 而非 CBR（CBR 是为直播稳带宽）；预算极紧的小直播 → 服务端直通 + 客户端自适应单档，不要上 ABR 阶梯。

## 反模式

| 反模式 | 后果 |
|---|---|
| GOP 与切片时长不整除（如 1.5s GOP 配 2s 切片） | 实测切片在 1.5/3.0s 交替、std 0.707，TARGETDURATION 从 2 抬到 3，播放器缓冲与重试全线变差 |
| 只设 `-g`，不设 `-keyint_min` / `-sc_threshold 0` | 场景切换处额外插 I 帧，切片时长抖动到 0.167–3.767s，TARGETDURATION 抬到 4 |
| 用 HLS 追 1s 以内延迟 | 协议下限 = 3 × 切片，调参无效；只能换 WebRTC/LL-HLS/HTTP-FLV |
| 所有源都转 4K | 按像素算一路 4K ≈ 4 路 1080p 的转码成本；ABR 档位不是越多越好，档位间要留 1.5–2 倍码率差 |
| CPU 软编硬扛 30 路 720p | 实测 1.12 核/路，30 路要 34 核，机器超卖后编码慢于实时，直播越推越卡 |
| 水印做成二次编码 | 多一次解码 + 编码，成本近翻倍、画质掉一代；水印应进转码滤镜 |
| 切片 10s 还要求秒开 | 首片等待 ≥ 切片时长，3 × 10s = 30s 起播；秒开与长切片不可兼得 |
| 不设码率阶梯只给单档 | 弱网用户只能卡或退出；CDN 带宽按最高档计，成本反而更高 |
| 按时间戳排序切片 | 时间戳可能重复/回退（断流重推、copy 起点偏移实测 0.067s），必须按 `#EXT-X-MEDIA-SEQUENCE` |
| 转码失败不回退直通 | 一场直播黑屏；必须有"转码异常 → 直通"的自动降级 |
| 硬编不补码率就上线 | 同 SSIM 需多约 33% 实际码率，观感"糊"且码率控制不准（写 2500k 只出 1751k） |

## 三条铁律

> 🔑 **协议决定延迟下限。** HLS 的延迟下限 ≈ 3 × 切片时长，2s 切片就是 6–9s；想 < 3s 必须换协议，调 `-hls_time` 只是自欺。

> 🔑 **GOP 先定，切片只能是 GOP 的整数倍。** 实测非整数倍 GOP 让切片标准差到 0.707、TARGETDURATION 从 2 涨到 3；源关键帧抖动（copy 直通）时标准差 1.001、TARGETDURATION 涨到 4。

> 🔑 **转码按 CPU 秒算成本，带宽按观众小时算成本。** 720p 转码约 1.12 核/路、￥0.06–0.14/路·小时；720p@2.5Mbps 约 ￥0.22/观众·小时——观众一多，省带宽（多一档低码率）比换硬编更值。

## 自检

**Q1** 一场 HLS 直播用 2s 切片，端到端延迟大概是多少？砍哪一段收益最大？想压到 2s 内该换什么？

▸ 答案：约 8–10s = 编码 0.1–1.6s + 3 × 2s 回退 + 播放缓冲 1–2s（实测首片 1.87–2.76s 可播，加 6s 回退）。收益最大的是 3 × 切片那一项——把切片砍到 1s 只能压到约 5–7s，且要 1s GOP；要 2s 内只能换协议：WebRTC（<500ms）或 LL-HLS（2–5s 量级），HLS 调参达不到。

**Q2** 源 GOP 恒定 2s，把 `-hls_time` 从 2 改成 3 会怎样？给出切片时长量级。

▸ 答案：3 不是 2 的整数倍，切点只能在关键帧上——每片会拉到 4s（等 2 片 GOP 才够 3s），即实测 g3 同型现象：时长变成 GOP 的整数倍×k，均值 4s，TARGETDURATION 变 4。想要 3s 切片得先改 GOP 到 1s 或 1.5s，且 1.5s 会再度抖动；正解是切片取 2/4/6s。

**Q3** 为什么写 `-b:v 2500k` 的硬编产物实际只有 1751kbps？直播里有什么风险？

▸ 答案：实测 h264_videotoolbox 的输出码率只有名义值的 70%，硬件编码器的码率控制不精确（受帧级 QP 步进与媒体引擎调度限制）。风险：① CDN 与观众带宽规划按 2.5M 算，实际出 1.75M，画质不达预期；② 码率忽高忽低导致 ABR 判定抖动；③ 与其它编码器混跑时档位不再可比。直播用硬编应实测实际码率，必要时把名义值上调（本机实测约需 2 倍名义值才能追平软编画质）。

**Q4** 8 核转码机，libx264 veryfast 转 720p 能跑几路实时？换硬编呢？为什么不是 10 倍？

▸ 答案：实测 60s 内容消耗 67.1 CPU 秒 → 1.12 核/路，8 核理论上限 7 路，按 70% 余量约 5 路。硬编 33.2 CPU 秒/60s → 0.55 核/路，约 14 路。不是 10 倍：硬编只省编码段的 CPU，1080p 软件解码两端都要做，实测 CPU 秒只差 2.02 倍；要接近数量级省 CPU 得连解码一起硬解。

**Q5** 用户反馈"首帧慢"，5 分钟内怎么按链路分段定位？给可执行的三条命令。

▸ 答案：分段量。① 服务端侧：`ffmpeg -i <ingest_url> -t 10 -f null -` 看 `speed=` 是否 ≥1，判断是不是转码慢于实时（<1 则整场堆积）；② 切片侧：`grep -E '^#EXTINF|TARGETDURATION' index.m3u8 | sort | uniq -c`，若出现非 GOP 整数倍时长或 TARGETDURATION 超目标，就是 GOP 对齐问题；③ 首片侧：`ffmpeg -re -t 10 -i src ... -tune zerolatency` 对比默认参数的首片时间（实测差 0.89s），再看播放列表第一个切片出现时刻（实测推流起点后 1.55s）。三段都对 → 去查 CDN 回源与播放器起播策略（见 [9.1 边缘缓存原理](../../L0-运行时底座/9-CDN与边缘/9.1-边缘缓存原理.md)）。

**Q6** 为什么 `ffprobe init.mp4` 会报错，而 `ffprobe index.m3u8` 正常？

▸ 答案：fMP4 把轨道描述放在 init 段（moov），媒体数据在 m4s（moof/mdat）。init.mp4 单独没有媒体数据，ffprobe 报 `no tfhd was found` / `error reading header` 是预期行为。校验要读 m3u8（会按 `#EXT-X-MAP` 去拼 init），或 `cat init.mp4 seg_000.m4s > t.mp4` 后探测（实测 2.066667s / 708,397B）。

**Q7** 硬编码省 CPU，为什么最终可能更贵？给算式。

▸ 答案：硬编省的是转码费、多花的是带宽费。实测同画质硬编需多约 33% 实际码率（追平软编 0.980330 需 3.5Mbps vs 2.63Mbps）：一个观众一小时多耗 `3.5-2.63=0.87Mbps × 3600s ≈ 0.39GB`，按 ￥0.2/GB 公开量级多约 ￥0.08/观众·小时；而转码成本本身约 ￥0.06–0.14/路·小时。观众数 ≥ 2 时带宽增量就超过省下的转码费，观众上千就是纯亏。结论：硬编适合"路数多、观众少"（如录制/审核/多档产出），软编或直通适合"观众多、路数少"。
