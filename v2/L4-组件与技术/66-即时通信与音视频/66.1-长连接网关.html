                                66.1 长连接网关

                                一句话

                                IM 接入层不是「一台上万连接的服务器」，而是有状态的连接路由层：网关只做连接 + 寻址 + 转发，容量瓶颈是内存与 fd，不是 CPU。

                                破除误区：四个把接入层想简单了的说法

                                误区 现实 依据
                                「长连接就是 WebSocket + 心跳，8.11 已经讲完了」 8.11 长连接与 WebSocket 讲的是一条连接怎么活着；这一节讲十万条连接怎么被组织、寻址、迁移、回收 连接协议 ≠ 连接集群
                                「长连接网关是 CPU 密集，扛不住就加机器」 实测 2000 条连接时服务端 CPU 几乎空转，每连接成本是 29KB 堆 + 2 个 goroutine + 1 个 fd；真正先撞的是 fd（本机进程实测上限 10236）和内存 本机实测（实验 A，raw/a-conncost-4KB.txt）
                                「有了 API 网关 / K8s Service 就不需要长连接网关」 47.2 API 网关 解决的是「请求怎么转给后端」，请求结束状态就没了；长连接网关解决的是「这个用户此刻连在哪台机器上」，这是有状态的路由问题 见下一节「连接路由表」
                                「网关顺手把 ACK、已读、群扩散做了，省一次 RPC」 ACK 的前提是消息状态机；网关重启时连接和内存状态一起没，做不了可信 ACK。网关做 ACK = 把最不可信的层当成消息真相 见 66.2 消息可靠投递与离线

                                🔑 一条判据：这段逻辑崩了之后，用户能不能从别的机器上恢复？ 能，放网关；不能，放逻辑层。

                                接入层演进三段：什么时候该独立出网关

                                阶段 拓扑 进入下一段的触发条件 这一段的撞墙表现
                                ① 业务直连 Web/App 直接连业务服务，每个服务自己维持 WebSocket 连接数接近单机内存/fd 上限；或需要多端（Web/iOS/Android/桌面）统一协议 业务进程被连接数拖 OOM；发版重启 = 全体掉线；每个服务重复实现心跳鉴权
                                ② 独立网关（网关与逻辑同机，连接表在本地内存，跨机靠广播） 网关进程只管连接，业务逻辑在同一进程或同机 网关超过 2 台后，下行消息找不到用户在哪个进程 本地广播 O(N²)，跨机丢消息；容量与业务互相打爆；发布互相牵连
                                ③ 网关与逻辑分离 + 中心路由表 网关只做连接/寻址/转发；逻辑层无状态（37.2 无状态化）；路由表在 Redis 或注册中心 —— 多一次网络跳，多一个 Redis 依赖（要靠降级兜底）

                                判据：连接数超过单机 5 万、或需要多端统一协议、或网关要独立于业务发布——三条中任一成立，就该走到第 ③ 段。没到之前不要提前拆：拆开的代价是路由表和跨节点投递，这两块在单机下本来不存在。

                                角色 只做什么 绝对不做 扩容单位
                                DNS + 四层 LB TCP 分发、健康检查、连接数均衡 解析业务、维持业务会话 加 LB 节点（受并发连接表限制，引 8.9 四层与七层负载均衡）
                                长连接网关 握手鉴权、心跳、连接注册、路由查询、消息转发、建连限速、指标 存消息、ACK、群扩散、已读聚合 加网关实例（每次扩容都要迁移存量连接）
                                路由表 uid -> gwId 的映射与 TTL 存业务数据、做强一致事务 加 Redis 分片（按 uid 哈希）
                                逻辑层 消息状态机、持久化、扩散、离线、推送 维持长连接 加无状态副本

                                上行与下行是两条完全不同的路径：上行（客户端发消息）走「网关 → RPC/队列 → 逻辑层」，网关只做协议转换和限速；下行（消息找用户）走「逻辑层 → 查路由表 → 向目标网关 PUBLISH → 网关写回连接」。很多 IM 事故出在只优化了上行、下行仍靠「每台网关广播」的老拓扑上。

                                连接路由表：三个方案与读放大

                                路由表回答唯一一个问题：uid 现在连在哪台网关。它有三个可选实现。

                                方案 命中率 失效窗口 每条下行消息的读放大 写放大 单点 扩容迁移代价
                                本地全量广播 / gossip 本机 100%，跨机靠广播 广播间隔（秒级） 0 O(N²)：N 台网关互相广播连接变更 无 新节点要全量同步连接表
                                中心存储（Redis） 100% 优雅下线 ms 级；进程崩溃 = TTL（本实验取 60s） 无缓存 1 次 GET；有缓存 ≈ 0 2 次（SET + 失效通知 PUBLISH） Redis 集群 低：加网关只影响自己那部分 key
                                uid 哈希分片 100% 分片表 TTL 0（可直接算出目标网关） 1 无（分片各自独立） 高：改分片数要迁移连接，靠一致性哈希/虚拟节点缓解

                                读放大公式（这一节最该记住的一条）：

                                路由表读 QPS = 下行消息 QPS × (1 − 网关本地缓存命中率)
无缓存时：Redis GET QPS = 下行消息 QPS

                                一个日活 1000 万的 IM（示例假设，非实测），峰值下行 5 万条/s（量级估算），若每条消息查一次 Redis，就是 5 万 QPS 全压在路由表上，而且热点 uid（明星、大群）会把单个分片打爆。必须本地缓存 + 失效通知，缓存命中率取决于用户切网关的频率（一天几次量级 → 命中率 99.9%+，经验估算）。

                                本地缓存的正确性靠两个失效源叠加：

                                • 主动失效：连接注册/注销时 PUBLISH im:route:inv "<uid> <gwId>"，所有网关清掉该 uid 的缓存项。
                                • 被动过期：缓存项 TTL 2s，兜住「失效通知丢包 / 网络分区」的最坏情况。
                                // 下行路由查询：本机连接 -> 本地缓存 -> Redis 三级（正文代码与仓库代码逐行一致）
func (g *Gateway) lookupRoute(uid string) (gwid, source string) {
	if g.cfg.RouteCache {
		g.mu.RLock()
		if c, ok := g.conns[uid]; ok && c != nil {
			g.mu.RUnlock() // 本机有连接：0 次路由查询，最热的一条路径
			g.routeCacheHit.Add(1)
			return g.cfg.ID, "local"
		}
		g.mu.RUnlock()
	}
	if gwid, ok := g.cacheGet(uid); ok {
		g.routeCacheHit.Add(1) // 本地缓存命中：0 次 Redis
		return gwid, "cache"
	}
	g.routeLookup.Add(1)
	c, err := g.pool.get()
	if err != nil {
		return "", "error"
	}
	v, err := c.Do("GET", "im:route:"+uid) // 只有未命中才查一次 Redis
	g.pool.put(c)
	if err != nil || v == nil {
		return "", "miss" // 用户不在线
	}
	gwid, _ = v.(string)
	g.cacheSet(uid, gwid) // TTL 2s，另有 im:route:inv 主动失效
	return gwid, "redis"
}

                                失效窗口分两种，必须分开算：

                                场景 路由什么时候失效 窗口 这期间的后果 兜底
                                优雅下线 网关主动删 key + 发失效通知 毫秒级 基本无感 客户端收到 redirect 重连
                                网关进程崩溃 / 机器失联 只能等 im:route:<uid> 的 TTL 过期 = RouteTTL（本实验 60s） 这 60s 内下行 PUBLISH 到已死的网关，receivers=0，消息静默丢失 靠 66.2 消息可靠投递与离线 的 server ACK + seq 对账补发
                                网关本地缓存 失效通知到达或 2s TTL 到期 ≤ 2s 消息被投到旧网关，旧网关查本地连接 miss 与上一条叠加，最终仍靠 ACK 兜底

                                🔑 路由表不是真相源，只是一个「大概率的提示」。所有依赖它的投递都必须当成 at-least-once + 可对账 来设计，投递语义见 43.2 投递语义 (at-most / at-least / exactly-once)。TTL 定 60s 不是拍脑袋：它 = 心跳续期周期（20s）× 3，宁可短一点多几次重连，也不要让「已死网关」在路由表里长时间存在。

                                连接生命周期：五个状态与三层心跳

                                状态 进入条件 超时值 超时/失败动作 客户端可见错误码 指标
                                CONNECTING TCP/TLS 握手 5s 断开 —— 建连失败率
                                AUTHING 带票/带 token 升级 1–3s 401 拒绝，不分配 WS 缓冲 401 im_gw_auth_fail_total
                                ACTIVE 鉴权通过，注册路由 心跳 20s，pong 窗口 60s 心跳超时踢掉 —— 在线连接数、心跳超时率
                                DRAINING 收到 redirect 或 LB 摘流量 排空 ≤ 10s redirect 到新网关 503 + Retry-After im_gw_draining
                                CLOSED EOF / 超时 / 顶号 / 强制断 —— 删路由、减在线数 4009（顶号）、4001（票据无效） 关闭原因分布

                                状态机里最容易做错的是 AUTHING 的位置：把鉴权放到 upgrade 之后（先升级成 WebSocket 再发第一帧 token），意味着每个攻击连接都能让网关先花掉 4KB 读缓冲 + 4KB 写缓冲 + 2 个 goroutine，最后才拒绝。正确顺序是先验票再升级——这也是建连风暴时唯一的自保手段（实验 C 的 429 就是在这个位置挡掉的）。

                                心跳要分三层看：

                                层 谁在发 默认值 能发现什么 成本 局限
                                TCP keepalive 内核 Linux 默认 7200s（要调 net.ipv4.tcp_keepalive_time）；macOS 默认 7200s 链路彻底断开 0（内核态） 不感知应用假死；NAT 映射早被回收；默认 2h 等于没有
                                协议层 Ping/Pong（WebSocket 控制帧） 网关 / 客户端 网关 20s 一次、60s 无 pong 判死 应用假死、NAT 保活 每连接每 20s 一个控制帧 需要客户端读循环真的在跑
                                应用层带 seq 心跳 客户端 30s 一次，带本地 seq/时间戳 消息序号断层、时钟漂移、弱网 RTT 一个 JSON/二进制小包 实现稍重，可做灰度指标

                                NAT 空闲超时是「假在线」的根因：家用 NAT 的 UDP/TCP 映射常见 60s–300s 就被回收（公开资料的量级；运营商级 NAT 更短），此后服务端里连接还在、fd 还在、路由表还说在线，但任何下行都到不了客户端。心跳间隔必须小于最小 NAT 超时，20s 是留了两三倍余量的常见取值。检测延迟的上限就是 pong 窗口：实验 F 把窗口调成 2s 实测 2.1s 检测到；生产取 60s，意味着用户最多假在线 60s——这 60s 的下行只能靠 66.2 消息可靠投递与离线 的 ACK + 重连补拉兜住。故障检测的通用模型（心跳/φ 值）见 35.4 故障检测 (心跳 / φ 值)。

                                协议选型：六种承载方式

                                协议 握手 RTT 弱网/切网恢复 NAT/代理兼容 服务端每连接成本 移动端功耗 生态与调试
                                WebSocket（RFC 6455） TLS + 1 RTT（HTTP Upgrade） 切网必重连 好（443/TCP，企业代理放行） 1 fd + 4KB 读 + 4KB 写（实测 29KB/连接） 中 最好：浏览器原生、抓包直接看帧
                                私有 TCP + 长度前缀 TLS + 1 RTT 切网必重连 差（非 443 常被拦） 最低：可自定义二进制头，无 HTTP 解析 中低 差：要自己写协议文档/抓包工具
                                HTTP/2 stream 复用 TLS + 1 RTT，之后多 stream 切网重连（连接级） 好（443） 低（一条连接多请求） 中 中：需要自定义帧语义
                                QUIC（HTTP/3） TLS 1.3 内建，0/1-RTT 最好：connection ID 支持连接迁移 差：UDP 在部分网络被限速/阻断 高：用户态协议栈 + 每包加解密 低（无队头阻塞） 中：需 8.5 HTTP/1.1、HTTP/2、HTTP/3 (QUIC) 的调试能力
                                SSE TLS + 1 RTT 切网必重连 最好（纯 HTTP 流） 低（但每消息有 HTTP 文本开销） 中 好；只能下行，二进制要 base64
                                MQTT TCP 1 RTT（TLS 另加） 重连 + QoS 重发 中（1883 常被拦，走 8883/WS） 低（broker 侧连接极轻） 最低（专为省电设计） 好（EMQX 等成熟）；协议语义主场在 43.11 MQTT 与海量连接

                                决策表：

                                你的情况 选什么 理由
                                Web 端为主，要兼容浏览器和 CDN WebSocket 浏览器原生，443 端口，Nginx/云 LB 都支持
                                App 深度定制、追求省电和包体 私有 TCP（或 MQTT） 自定义二进制头，省掉 HTTP 帧开销
                                用户经常在地铁/电梯/双卡切网 QUIC connection ID 迁移让连接不断，重连成本归零
                                只做「有新消息」通知、或长连接不可用时的降级 SSE / 长轮询 纯 HTTP，任何代理都通；代价是 QPS 高、延迟大
                                已有 EMQX/MQTT 资产、IoT 或大量低功耗设备 MQTT（43.11 MQTT 与海量连接） broker 替你管连接和 QoS，别自己重造
                                企业内网、代理只放 443 WebSocket over 443 私有 TCP 大概率被中间设备掐断

                                怎么选不影响网关架构：协议是连接层的实现，路由层、生命周期、限速、下线流程都一套。所以正确的做法是把网关的协议层做成可替换的 codec，而不是为每个协议写一套网关（反面案例：为 QUIC 重写一遍路由表和下线逻辑，两边行为不一致）。

                                容量公式：单机十万连接的账

                                单机连接数 = min(下面四条线算出来的值)，一条一条算：

                                线 公式 本机实测/取值 十万连接要多少
                                fd (nofile 上限 − 常驻 fd) / 每连接 fd 实测进程上限 10236（ulimit -n 显示 1048575 是假的，真顶是 kern.maxfilesperproc=10240）；网关 ulimit -n 2000 时只挂上 1983 条连接 10 万 fd：Linux 上调 fs.nr_open/systemd LimitNOFILE=1048576 后可，macOS 本机不可能
                                内存 内存预算 / 每连接内存 4KB 缓冲：29,405 B 堆 + 65,048 B Sys；64KB 缓冲：159,697 B 堆 + 191,000 B Sys 10 万 × 29KB ≈ 2.8 GiB 堆（4KB 缓冲）；64KB 缓冲要 15 GiB
                                端口/中间设备 LB 并发连接表、NAT 表项、网关→逻辑层连接数（网关作为客户端也要源端口） 本机压测时先在压测端撞 16384 个临时端口（实测报 can't assign requested address） 10 万并发要确认 LB/NAT 的并发连接表能放行
                                CPU 核数 / 单次建连 CPU 时间，只在建连峰值时是瓶颈；稳态心跳（20s 一次）可忽略 建连成本见实验 D：TLS RSA 2.36ms、ECDSA 0.93ms、WS 升级 0.19ms 稳态 CPU 很低，建连风暴时是主瓶颈

                                每连接成本不是一个数，至少四块（实测 4KB 缓冲组）：

                                Go 堆： 29,405 B   ← 读缓冲 4KB + 写缓冲 4KB + gorilla 帧构造缓冲 + 结构体
Go Sys：65,048 B   ← 含 2 个 goroutine 栈、堆管理元数据
内核 socket 缓冲：SO_RCVBUF 408,192 B / SO_SNDBUF 146,988 B（getsockopt 读数，macOS 会把请求值加倍）
路由表条目：~100 B/连接（Redis 里一条 key + 网关本地缓存）

                                ⚠️ 内核 socket 缓冲这一块最容易漏，它既不在 Go heap 也不在 Go Sys 里。不要把 getsockopt 的读数当成「每连接真实占用」直接乘——macOS 的自动调参会把上限放大，实际按流量动态分配；但它证明了「每连接 4KB」这种说法不成立，做容量规划时至少留 2–4 倍余量。

                                关键结论：缓冲大小是容量的隐形开关。4KB → 64KB，每连接堆从 29,405 B 涨到 159,697 B（+130,292 B；增量 4.4 倍，新值 5.4 倍），单机 10 万连接的堆内存从 2.8 GiB 变成 15 GiB。所以网关的读写缓冲要按业务消息大小定，默认 4KB 比 64KB 好；富媒体消息走对象存储链接，不要塞进长连接帧。

                                100 万连接怎么排（外推，非实测——本机 kern.maxfiles=30720 物理上开不到 1e6 连接）：

                                维度 按 4KB 缓冲线性外推 说明
                                Go 堆 27.4 GiB 29,405 B × 1e6
                                Go Sys 60.3 GiB 含栈和分配器元数据，外推偏保守（Sys 不随连接数线性涨）
                                fd 1,000,000 必须配 LimitNOFILE 和 fs.nr_open，且 LB 并发连接表要够
                                机器数 5 台 × 20 万连接（+2 台冗余） 20 万 × 29KB ≈ 5.5 GiB 堆/台，64GB 内存机器余量充足

                                🔑 100 万连接不是一个技术壮举，而是一道四则运算：fd 除以进程上限、内存除以每连接成本、端口数除以并发连接表。算完发现限制来自哪一条，就去补哪一条；补不了就分片。

                                实测：2000 条连接的单机成本 / 跨网关投递 / 重连风暴

                                环境（全部实验相同）：macOS 15.6 (24G84) / Apple silicon arm64 / 8 核 / 8 GiB / Go 1.27.1 / Redis 8.10.2 / gorilla/websocket v1.5.3 / 2026-11-21。网关与压测客户端、Redis 同机；各表标注当时 sysctl vm.loadavg，同机并行实验导致延迟类数字有 ±20% 抖动，内存/fd/功能类数字稳定可复现。代码在 tools/examples/66.1-gateway/code。 示例说明见 tools/examples/66.1-gateway/。

                                实验 A：单机连接成本（2000 条 WebSocket）

                                服务端与客户端是两个进程，客户端 256 并发 dial；服务端只改 websocket 读写缓冲，其余不变。规模取 2000 条而非预算的 4000 条：受本机 kern.maxfilesperproc=10240 与同机并行实验限制。

                                exp661 -mode=a -n 2000 -gw1 127.0.0.1:18081 -redis 127.0.0.1:16381
# 服务端用 -readbuf 4096 -writebuf 4096 与 -readbuf 65536 -writebuf 65536 各跑一次
                                配置 成功连接 建连速率 goroutine/连接 Go 堆/连接 Go Sys/连接
                                读写缓冲 4KB 2000/2000 8,364 conns/s 2.00 29,405 B 65,048 B
                                读写缓冲 64KB 2000/2000 5,947 conns/s 2.00 159,697 B 191,000 B
                                • 缓冲 4KB→64KB：每连接 +130,292 B（增量 4.4 倍、新值 5.4 倍），单机容量直接砍到原来的 1/5.4（约 −82%）。
                                • goroutine 数 / 连接 = 2.00：一条读循环 + 一条写循环，没有多余的每连接协程。
                                • fd 硬顶：ulimit -n 显示 1,048,575，进程实测只能开到 10,236（kern.maxfilesperproc=10240、kern.maxfiles=30720）。
                                • 把网关进程 ulimit -n 压到 2000 再接 3000 条：在线 1983（2000 减去监听/Redis/运行时占用的 17 个），网关日志出现 96 行：
                                http: Accept error: accept tcp 127.0.0.1:18081: accept: too many open files; retrying in 5ms
                                • 结论：连接上限第一条线是 fd，不是 CPU。进程 fd 打满后 accept 只能 5ms 重试，建连速率从 8,364/s 掉到 141/s——这是雪崩的开始。

                                实验 B：跨网关卡投递（1000 条下行 P50/P99）

                                两台网关共用一台 Redis（16381）：客户端连 gw1，业务侧把下行 push 打到 gw2（gw2 上没有这条连接），必须经路由表转发。端到端耗时 =「业务侧发 HTTP push」到「客户端收到 WS 帧」。

                                gw661 -id gw1 -addr 127.0.0.1:18081 -redis 127.0.0.1:16381
gw661 -id gw2 -addr 127.0.0.1:18082 -redis 127.0.0.1:16381   # 对照组追加 -route-cache=false
exp661 -mode=b -n 1000 -gw1 127.0.0.1:18081 -gw2 127.0.0.1:18082 -redis 127.0.0.1:16381
                                gw2 路由缓存 送达 端到端 P50 端到端 P99 Redis GET 次数（1000 条消息）
                                开（TTL 2s + 失效通知） 1000/1000 152µs 357µs 1
                                关（每条消息查一次） 1000/1000 249µs 471µs 1000
                                • 无缓存时 Redis GET QPS = 下行消息 QPS；开了本地缓存 + 失效通知后，1000 条消息只查 1 次 Redis。P50 差的 97µs ≈ 一次 loopback Redis 往返（与实验 D 的 GETDEL 32µs 同量级，差额来自 PUBLISH 路径）。
                                • 失败路径（真实响应）：
                                用户不在线     -> {"code":"offline","route":"miss"}
路由指向死网关 -> {"code":"stale","gw":"gw-dead","receivers":0,"route":"redis"}
不做路由层     -> 直接推 gw2 本机连接：{"code":"miss"}   // 100% 找不到
                                • receivers=0 是 Redis PUBLISH 的返回值：路由说在、但目标网关没有订阅者，这条消息就静默丢了，直到 RouteTTL 过期。这个返回值必须进指标（im_gw_route_stale_total），否则下游永远发现不了「消息发出去没人收」。

                                实验 C：重连风暴（1000 客户端同时断、同时重连）

                                1000 个客户端先连上网关，由服务端统一 kick-all 断开（等价网关重启/网络分区，且避免压测端 TIME_WAIT），然后同时重连。规模取 1000 个而非预算的 2000 个，原因同实验 A（fd 上限 + 同机并行实验限制）。

                                exp661 -mode=c -n 1000 -gw1 127.0.0.1:18081 -redis 127.0.0.1:16381 \
       -storm-mode fixed            # 第一组：固定 1s
exp661 -mode=c -n 1000 -gw1 127.0.0.1:18081 -redis 127.0.0.1:16381 \
       -storm-mode backoff          # 第二组：指数退避 + full jitter
exp661 -mode=c -n 1000 -gw1 127.0.0.1:18081 -redis 127.0.0.1:16381 \
       -storm-mode backoff -set-limit 500   # 第三组：断开后网关限速 500/s
                                重连策略 恢复 全部恢复耗时 峰值 accept/s 429 拒绝数
                                固定 1s（反模式） 1000/1000 1.3s 1000（全压在 1s 内） 0
                                指数退避 + full jitter 1000/1000 1.0s 526（摊到两秒：526 / 242） 0
                                退避 + 网关限速 500/s 1000/1000 2.6s 510（510 / 254 / 2） 3
                                • 同样 1000 个客户端，固定 1s 重连把 1000 个建连压进同一个 1s 桶（峰值 1000/s），退避 + 抖动把它摊到两个桶（峰值 526/s）。
                                • 服务端限速 500/s 后，风暴被明确削平：第一秒 510 个（含桶容量 500）、第二秒 254、第三秒 2，全程只拒绝 3 个（429 + Retry-After），2.6s 恢复完毕。限速的代价是恢复慢 1.6 倍，收益是网关不被打死。
                                • 结论：限速必须服务端和客户端配套。只有服务端限速没有客户端抖动，被拒的客户端会立刻重试，形成二次风暴；只有客户端抖动没有服务端限速，第一次冲击仍可能打满 fd。

                                建连成本拆解：风暴时的 CPU 花在哪

                                同一台机器上串行各跑 3 次，取多轮中噪声较小的一轮（vm.loadavg ≈ 9；TLS RSA 三次中位 2.384ms，与表内 2.356ms 差 1%；三次原始读数在 raw 目录）。

                                exp661 -mode=d -gw1 127.0.0.1:18081 -redis 127.0.0.1:16381
                                步骤 P50 P99 架构含义
                                Redis GETDEL（一次性票据核销） 32µs 86µs 把票据核销放网关 = 建连 QPS 直接变成 Redis QPS
                                JWT HS256 验签（512B） 0.79µs 1.33µs 无状态验签比一次 Redis 往返便宜 40 倍
                                TLS 1.3 握手（RSA-2048） 2.36ms 3.54ms 建连成本的大头，风暴时主要打的是 CPU
                                TLS 1.3 握手（ECDSA P-256） 0.93ms 1.20ms 换证书算法省 60%
                                WebSocket 升级（含票据核销 + 路由注册） 186µs 608µs TLS 之后的部分其实很便宜

                                由此推导单节点建连能力（推导，不是实测）：

                                TLS 在网关终止(RSA)   ：1s / 2.36ms ≈ 424 conn/s/核 → 8 核 ≈ 3,390/s
TLS 在网关终止(ECDSA) ：1s / 0.93ms ≈ 1,075 conn/s/核 → 8 核 ≈ 8,600/s
TLS 在 LB 终止(网关只做 WS)：1s / 0.186ms ≈ 5,376 conn/s/核 → 8 核 ≈ 43,000/s

                                限速阈值就从这个数取 50%：TLS 在网关终止的 8 核节点，阈值取 1,500–1,700/s；TLS 在边缘终止的节点可以放到万级。实验 C 用了保守的 500/s（机器同时跑着别的实验）。按 1,700/s 算，10 万客户端重连要 59s 才消化完——所以客户端抖动窗口必须大于 59s，否则退避几次之后又会在同一秒撞上来。

                                优雅下线：长连接没有「请求边界」

                                55.7 优雅停机：发布不丢请求的五个动作 的前提是 HTTP 有请求边界：停止接新请求 → 等在途请求完成 → 退出。长连接没有请求边界（一条连接活几小时），所以必须显式通知客户端换机器。顺序固定五步：

                                步 动作 做错的后果 命令/实现
                                ① 摘流量 从 LB 下线该节点（停止新建连接） 新连接继续进来，永远排不空 LB 侧下线，网关返回 503 + Retry-After
                                ② 删路由 删 im:route:<uid>（CAS：只删指向自己的）+ 发失效通知 不删：新消息继续路由过来，被投递到正在关闭的连接 Lua if GET==myself then DEL
                                ③ redirect 给每条连接发「去哪个网关」的指令 不通知：客户端只能等心跳超时（最长 60s）才发现，这段时间消息全丢 {"type":"redirect","peers":["127.0.0.1:18082"]}
                                ④ 排空 等在途写完成，最多 10s 直接关：写了一半的帧截断 排空窗口
                                ⑤ 强断 + 摘注册 超时强关剩余连接，从注册中心删除自己 不摘注册：其他网关 redirect 到一台已下线节点 HDEL im:gw:addr <id>

                                与 55.7 优雅停机：发布不丢请求的五个动作 的差异只有一句话：HTTP 等的是「请求」，长连接等的是「客户端收到 redirect 并主动断开」，所以要给客户端一个「新地址 + 新票据」的完整迁移包，而不是只发个 503。

                                实测（500 条在线连接，gw1 drain 到 gw2）：

                                DRAIN_RESP        map[drained:0 redirected:500]
DRAIN_DURATION    890ms
REDIRECT          sent=500 redirected=500 reconnected=500
AFTER             gw1_online=0 gw2_online=500 gw1_draining=1
LOSS              掉线未重连=0

                                单连接版本（curl -X POST .../admin/drain，客户端侧看到）：

                                FRAME {"peers":["127.0.0.1:18082"],"type":"redirect"}

                                边界：优雅下线能保证「用户无感」，但保证不了「消息不丢」——redirect 之前已经 PUBLISH 到旧网关、还没写进连接的消息，要靠 66.2 消息可靠投递与离线 的 ACK 与重连补拉。网关和消息可靠性是两件事。

                                多地域、多机房与安全边界

                                多机房：用户就近接入（DNS/GSLB/Anycast 就近），路由表按机房/单元分片，每个单元的路由表只记本单元的 uid → 网关。跨机房的下行由逻辑层转发到目标单元，不要跨城查路由表。切机房 = 主动踢连接：把整个机房的 im:route:* 删掉、给客户端发 redirect 到新机房，让用户在新机房重连，然后用 seq 把断线窗口补回来——比跨城维持连接可靠得多，代价是断线几秒（见 66.3 多端同步 的游标补拉）。单元化本身的做法见 36.5 单元化 / Set 化架构。

                                反模式 后果
                                网关里做消息存储、ACK、群扩散、已读聚合 网关重启即丢消息；把有状态逻辑放进最难扩容的一层；正确位置见 66.2 消息可靠投递与离线、66.5 群聊与消息扩散

                                每条下行消息查一次 Redis 路由 Redis QPS = 消息 QPS（实测 1000 条 = 1000 次 GET），热点 uid 打爆单个分片
                                优雅下线直接 kill 进程 路由表残留 RouteTTL（60s），这 60s 的下行全部 receivers=0 静默丢失；用户同一秒集体重连
                                鉴权放在业务层 / WS 升级之后 无效连接先吃掉 4KB+4KB 缓冲和 2 个 goroutine 才被拒，风暴时网关被垃圾连接打爆
                                客户端固定 1s 重连，无抖动 1000 客户端把建连全压进同一个 1s 桶（实测峰值 1000/s vs 抖动后 526/s）；10 万级会持续打满
                                用 HTTP 短连接轮询代替长连接 QPS = 在线数 / 轮询间隔；100 万在线、2s 轮询 = 50 万 QPS，成本高一个数量级且延迟更差
                                把在线状态当强一致数据（双写 + 强一致读） 路由表天然有 TTL 失效窗口，追求强一致会把可用性拖死；在线状态只能是「最佳努力」
                                网关与业务服务同机部署 内存/CPU 互相打爆，网关重启 = 业务重启，发布互相牵连
                                慢消费者不设上限（发送队列无限涨） 一个不读数据的客户端就能吃掉网关内存；必须有 slow_drop 计数并主动断开
                                redirect 里不带新网关地址和新票据 客户端重连到已摘流量的旧节点，100% 被 503 拒绝，形成无限重连循环

                                三条铁律

                                🔑 网关只做连接、寻址、转发。 凡是需要「消息状态」的判断——ACK、未读、群扩散、续传——都放逻辑层。网关崩了用户换个节点就能恢复，逻辑层崩了要靠消息状态机恢复。

                                🔑 连接是有状态资源，扩缩容不是加副本。 扩容网关必须走「摘流量 → 删路由 → redirect → 排空 → 强断」，少一步就是丢消息或丢用户。

                                🔑 容量按四条线分别算：fd、内存、端口/中间设备、CPU。 先撞哪条补哪条；CPU 通常不是第一条，而「每连接 4KB」这种口头估算至少会漏掉内核 socket 缓冲和 goroutine 栈。

                                自检

                                Q1 已经有 8.11 长连接与 WebSocket 和 47.2 API 网关，为什么 IM 还要一组长连接网关？三者的分工是什么？ ▸ 答案：8.11 讲单条连接的协议细节，47.2 讲「请求怎么转给后端」——请求结束状态就没了。IM 的难点是用户此刻连在哪台机器这个有状态事实：10 万连接在 N 台网关上，逻辑层要发消息时必须先查路由。所以长连接网关 = 连接管理（握手/鉴权/心跳/限速）+ 路由注册 + 转发，是「有状态的连接路由层」，既不是 API 网关也不是 WebSocket 协议本身。

                                Q2 100 万连接时，一条下行消息怎么找到用户当前连在哪台网关？路由表放哪、失效窗口多大？读放大怎么算？ ▸ 答案：逻辑层查 im:route:<uid>（Redis 或按 uid 哈希分片直接算）得到 gwId，再向 gw:<gwId> PUBLISH，目标网关查本地连接表写回。失效窗口分两种：优雅下线 ms 级（删 key + 失效通知），进程崩溃 = RouteTTL（60s），这期间 PUBLISH receivers=0 静默丢，只能靠 66.2 消息可靠投递与离线 的 ACK + seq 补。读放大 = 下行消息 QPS × (1 − 本地缓存命中率)：无缓存 1 次 GET/消息（实测 1000 条 = 1000 次），有缓存 + 失效通知 ≈ 0（实测 1 次）。

                                Q3 网关要重启发版，怎么让 10 万在线用户无感迁移？五步顺序是什么，哪一步反了会造成什么后果？ ▸ 答案：① LB 摘流量（拒绝新建）② 删路由（CAS 只删指向自己的）+ 失效通知 ③ 发 redirect 携带新网关地址与新票据 ④ 排空在途写（≤10s）⑤ 超时强断并摘除注册。反例：先删路由再摘流量 → 新连接继续进来永远排不空；直接 kill → 路由残留 60s、下行静默丢失 + 全员同一秒重连；redirect 不带地址/票据 → 客户端回到已下线节点，无限 503。实测 500 连接 890ms 完成迁移、0 丢失。

                                Q4 WebSocket、私有 TCP、QUIC、SSE 怎么选？各自的代价是什么？ ▸ 答案：看三件事——客户端形态、弱网程度、中间设备。Web 端/要兼容代理选 WebSocket；App 深度定制省包体选私有 TCP；切网频繁（地铁/电梯）选 QUIC（代价：UDP 可能被限速、每连接 CPU 高、LB 支持差）；只做通知或降级选 SSE/长轮询（代价：QPS 高、延迟大）。关键：协议只是连接层实现，路由表/生命周期/限速/下线流程必须一套，否则两套协议的行为会不一致。

                                Q5 单机 10 万连接的成本怎么算？会先撞哪个限制？ ▸ 答案：四条线取 min：fd（10 万 fd，Linux 要调 fs.nr_open/LimitNOFILE；本机 macOS 实测进程上限 10236，直接不可能）、内存（4KB 缓冲实测 29,405 B 堆 + 65,048 B Sys → 10 万约 2.8 GiB 堆；64KB 缓冲 160KB → 15 GiB）、端口/中间设备（LB 并发连接表、NAT 表项）、CPU（建连峰值时才是瓶颈）。本机实测先撞 fd：把 ulimit -n 压到 2000 时 3000 条只挂上 1983 条，日志全是 too many open files。

                                Q6 断网恢复的重连风暴怎么防？限速放哪一层？阈值定多少的依据是什么？ ▸ 答案：三层配合——客户端指数退避 + full jitter（delay ∈ [0, min(60s, 1s·2^(n−1))]）、网关令牌桶在建连最前面限速、LB 层粗粒度兜底。阈值从实测建连成本推：TLS 在网关终止（RSA 2.36ms）→ 8 核约 3390/s，取 50% ≈ 1500–1700/s；TLS 由 LB 终止时可达万级。实测 1000 客户端：固定 1s 峰值 1000/s，抖动后 526/s，限速 500/s 后 2.6s 平滑恢复。算一下就知道为什么必须抖动：10 万客户端按 1700/s 要 59s 才能消化完，抖动窗口必须大于这个数。

                                Q7 网关要不要做消息存储、ACK、群扩散、已读聚合？边界怎么划？ ▸ 答案：都不要。判据是「这段逻辑崩了之后用户能不能从别的机器恢复」：连接崩了换个网关重连即可恢复，所以放网关；消息状态崩了必须靠持久化的状态机恢复，所以放逻辑层。网关做 ACK 的问题是：ACK 需要「消息已持久化」这个事实，而网关不存消息，它生成的 ACK 只是「我把帧写进了 socket」，一旦进程崩了就是假 ACK。边界清单：网关负责连接/鉴权/心跳/路由/限速/转发/指标；逻辑层负责消息状态机、持久化、扩散、离线收件箱、已读。端到端案例见 84.2 社交消息：扩散模型与多端一致的取舍。
