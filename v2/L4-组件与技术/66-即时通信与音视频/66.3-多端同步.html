                                        66.3 多端同步

                                        一句话

                                        多端一致的正确抽象是每设备一个游标 + 服务端单调序列：推只负责叫醒、拉负责补全，正确性用五条不变量（不丢 / 不重 / 不乱序 / 已读单调 / 会话列表收敛）来判定。

                                        破除误区：多端同步不是"把每条消息推给每一端"

                                        误区 现实
                                        三端同时在线，每端推一份就一致 推送是 at-most-once 的唤醒通道：丢一条就永久丢，乱序到达要重排，断线期间的消息根本不在推送里
                                        同步就是消息同步 消息是 append-only 数据；会话列表、已读位置、设置/草稿都是可变状态，合并规则与消息完全不同
                                        用客户端时间戳排序就一致 多设备时钟差可达秒级到分钟级（经验值/量级），同一毫秒的消息无法定序；排序必须用服务端单调序列
                                        丢消息让客户端重试就行 重试只解决"没收到 ACK"，不解决"客户端游标没推进"和"增量从哪个序号续起"

                                        真正要回答的只有三个问题：每个设备知道自己的进度吗（游标）；服务端能给出比游标更新的有序增量吗（序列）；乱序 / 重复 / 断线之后，增量还能精确续上吗（幂等 + 分页 + 快照回退）。

                                        待同步的六类数据：合并策略完全不同

                                        数据 例子 一致性要求 合并策略 能接受近似吗
                                        消息 聊天记录 不丢、会话内有序 append-only + msg_id 去重 不丢，可重复投递
                                        会话列表 最后一条、置顶、草稿标记 最终收敛 按 change_seq 覆盖（LWW） 可短暂不一致
                                        已读位置 每会话 read_seq 单调不减 max 合并 可延迟，不可回退
                                        未读数 红点数字 最终一致 派生值 last_seq - read_seq 可近似，见 44.23 未读数系统
                                        设置 / 草稿 通知开关、输入框 最终一致 LWW + 服务端版本号 可丢中间态
                                        联系人 / 群成员 好友列表、群名 最终一致 快照 + 增量 + 版本号 可延迟

                                        只有消息是 append-only、天然无冲突；其余五类都要一个合并函数。把这六类都塞进同一条用户维度变更流水后，同步从"写六套协议"收敛成"一套游标 + 一组 reducer"。 群成员变化、群消息怎么扩散由 66.5 群聊与消息扩散 主讲，本节只关心它如何写进 change 流水。

                                        双序列：conv_seq 与 user_change_seq

                                        一个序列不够，最少要两个。

                                        序列 作用域 解决什么 谁生成 代价
                                        conv_seq 单会话内单调 消息排序、续传、已读定位 发号器 / 会话分片内的自增，见 44.24 发号器与全局 ID 每会话一个计数值，无热点
                                        user_change_seq 单用户维度单调 会话列表变化、已读变化、设置变化、新消息的"叫醒" 每用户一条变更流水 每用户流水存储 + TTL
                                        • 只用一个全局单序列：所有用户/会话都往一条序列上写，它变成写热点；而且客户端无法表达"我只想看 c1 的新消息"。
                                        • 只用 conv_seq：客户端不知道"哪几个会话有新东西"，只能对 N 个会话逐个拉一遍（N 次请求）；会话列表本身的变化（置顶、改名、最后一条消息）没有载体。
                                        • 只用 user_change_seq：消息正文不能塞进流水（流水会膨胀成消息库），而且同一会话的排序仍需要一个会话内的单调值。

                                        两条序列的分工是一句话：conv_seq 管"会话里第几条"，user_change_seq 管"我这个用户第几次变更"。 消息变更在流水里是瘦条目（只带 conv + seq + msg_id），正文由会话游标另拉。写路径上，业务事务提交后把变更追加到用户流水再唤醒在线设备；读路径上，拉流水和拉消息正文各自分页，客户端按 has_more 循环，直到两条游标都追上服务端。

                                        变更流水的存储成本（本机实测，见实验 C）：单条 change 瘦条目 JSON = 87 B。重度用户 0.5 条/秒 → 每天 43,200 条，7 天 TTL 约 302,400 条 ≈ 25.1 MiB/人；若 100 万日活按平均 200 条/天建模，7 天约 113.4 GiB。所以流水必须：按用户分片、按活跃度设 TTL、冷用户只留最近水位或落盘，过期就给客户端 reset_required 回退快照。

                                        同步协议：一次请求的 JSON 契约

                                        协议只有一条：客户端上报自己已经处理到哪，服务端返回比它更新的有序增量。本机真实跑通的请求与响应如下。

                                        # 请求：设备 t_phone 的 change_cursor=120，三个会话分别拉到 40 条
curl -s 'http://127.0.0.1:18103/sync?device_id=t_phone&change_cursor=120&conv_cursors=c1:40,c2:40,c3:40'

                                        {
  "change_cursor": 121,
  "changes": [{"change_seq": 121, "kind": "msg", "conv_id": "c1", "seq": 41, "msg_id": "m_c1_0041"}],
  "messages": {"c1": [{"msg_id": "m_c1_0041", "conv_id": "c1", "seq": 41, "sender": "u1002", "body": "hello-sync", "ts_ms": 1795242072798}]},
  "has_more": false,
  "snapshot_seq": 121
}

                                        语义五条，少一条就会在弱网下丢消息：

                                        1. 幂等可重放：同一个 change_cursor 重复请求，返回同一批增量；客户端应用两次结果不变（按 change_seq / msg_id 去重）。
                                        2. 分页 + has_more：单次响应有上限（本实现变更 10 条、每会话消息 2 条），客户端循环拉到 has_more=false，不能假设一轮拉完。
                                        3. 游标只进不退：客户端把 change_cursor 推进到已连续应用的最后一个 change_seq；只推进连续前缀，中间缺一个就停下等下次——跳过缺口等于永久丢消息。
                                        4. 首次登录是"快照 + 从 snapshot_seq 开始的增量"：先拿快照（会话列表 + 最近消息 + snapshot_seq），再从 snapshot_seq 拉增量。不能"先快照，再从 0 拉增量"——快照和增量之间会重复；也不能"只拿快照不记 seq"——会漏掉快照之后的写入。
                                        5. 游标过期必须显式告诉客户端：服务端 change 流水只保留 7 天，超出窗口返回 reset_required，客户端回退全量快照，而不是静默从窗口起点继续（那样会漏）。
                                        {"oldest_change_seq": 63, "reason": "change_cursor_expired", "reset_required": true, "snapshot_seq": 122}

                                        页大小按"一次失败重来的代价"定，不按"一次拉完"定：页越大，单次响应字节越多、弱网下超时重试浪费越大；页越小，请求数与 RTT 越多。工程上取 100–500 条/页（经验值/量级），并给单次响应设字节上限（1 MB 量级），按字节截断比按条数截断更稳。本实验为缩短用例把变更页压到 10 条、每会话消息压到 2 条，真实系统要调到百级——页大小是弱网收敛速度的旋钮，要和兜底轮询周期一起调。

                                        错误码也是协议的一部分：同步接口至少要区分四类——可重试（500/超时）、游标失效（reset_required）、设备被踢（401）、限流（429 + Retry-After）。客户端对每类的动作完全不同：重试、回退全量、重新登录、按 Retry-After 退避。四类混成一个"同步失败"，就是弱网下"越同步越慢"的常见根因。

                                        推 vs 拉：三种协议对比

                                        同一个负载（1 用户 3 设备、600 条消息、d_pad 在 120–150 s 断线 30 s）下本机实测，同一随机种子结果逐字节一致（实验 B）：

                                        协议 总流量 数据重复率 未送达 P50 延迟 P99 延迟 断线补齐（1Mbps 折算） 服务端成本
                                        只推（断线靠重连全量） 259,391 B 18.0% 146 条 15 ms 65,001 ms 341 ms / 38,881 B 连接常驻（内存/心跳/广播），断线后重连全量 = 广播放大
                                        只拉（1 s 轮询） 292,547 B 0% 0 条 500 ms 501 ms 93 ms / 7,939 B 无连接状态，成本 = 设备数 / 轮询间隔 的 QPS
                                        推叫醒 + 拉补全 340,544 B 0% 0 条 27 ms 539 ms 94 ms / 8,069 B 两者叠加：连接常驻 + 拉取 QPS

                                        读数：

                                        • 只推最省字节，但省出来的是错的：推送丢 10% 就永久丢 146/1800（8.1%），丢失的消息只能等下次重连用全量快照修补，于是 P99 被拉到 65 s；补齐一次花 38,881 B，是增量补齐（7,939 B）的 4.9 倍。断线越频繁，"只推"越贵。
                                        • 推叫醒 + 拉补全买的是延迟，不是流量：P50 从 500 ms 降到 27 ms，代价是推送本身的 19 B/条水位 + 更多次拉取请求（在持续有消息的压测负载下总流量反而最高）。空闲时段只拉仍要按周期空转轮询，那时推送才在流量上占优。
                                        • P99 由兜底轮询周期决定：推送丢包时，消息靠 3 s 兜底拉取补回，所以这套协议的 P99（539 ms）与只拉（501 ms）接近——推送不参与正确性，只影响 P50。
                                        • 只推的乱序到达 1,544 次（2,018 次投递里 76% 不是下一个连续序号）：不做排序的客户端会把消息显示成乱序。游标 + seq 排序是硬要求。
                                        你的情况 选什么
                                        客户端有长连接、消息量大、要低延迟 推叫醒 + 拉补全（默认选择）
                                        客户端只有短连接 / 受限网络（如部分 Web 端） 只拉 + 秒级轮询 + 退避，见 8.11 长连接与 WebSocket
                                        极端省电 / 推送通道不可用 只推 + 重连强制全量对账（只能用于可容忍丢消息的场景）
                                        多端 + 弱网 + 断线频繁 必须推叫醒 + 拉补全，且增量必须能续上

                                        为什么推送不携带消息正文：推送通道的语义是 at-most-once，且移动端对通知 payload 有大小限制、厂商通道还有去重与折叠；把正文放进推送，等于把"消息传输"押在一条不可靠通道上，丢了就得再补一套补偿逻辑。让推送只带一个单调水位，丢包的代价就只是"晚一拍被兜底轮询发现"，而不是"消息没了"——这是这套协议在弱网下仍然正确的原因。

                                        可变状态：已读、未读、会话列表、设置 / 草稿

                                        • 已读位置用 max 合并，天然幂等：每会话一个 read_seq，服务端 max(旧值, 上报值)，更旧的上报直接丢弃。乱序、重复、多端并发上报都不需要锁——这是一个单调偏序上的 join。实测（实验 A）3,929 次已读上报里有 1,067 次（27.2%）比当前值旧、被直接丢弃；所有设备的已读回退次数为 0。
                                        • 已读回执丢了不用补发：回执只是一次 read 变更，丢了就等本设备下一次增量拉取时取到服务端已合并的读位置；对发送端来说，已读展示天然是"最终正确"而不是"实时精确"。
                                        • 未读数是派生值：unread = last_seq - read_seq，随两个序列变化自动收敛，不需要单独同步计数器；精确算法与红点抖动见 44.23 未读数系统。
                                        • 会话列表靠 change_seq 收敛：最后一条消息、置顶、草稿标记都是 LWW，版本号用服务端 change_seq（不是客户端时间）；同一会话的多条元数据变更共享一个版本，客户端整条覆盖而不是逐字段合并，字段之间不会出现"最后一条是新的、置顶还是旧的"这种撕裂。客户端的会话列表最终与三端一致，但中间状态可以短暂不同——这正是"能接受近似"的边界。
                                        • 设置/草稿是 LWW：写请求带 base_version，服务端用服务端序号递增版本，旧版本写入丢弃。不用客户端时间做最后写入胜，因为设备时钟不可信；两者冲突时以服务端序号为准。真正的并发编辑（协同文档、共享草稿）才需要 25.6 CRDT (计数 / 集合 / 寄存器)，普通 IM 设置用不上 CRDT。
                                        • 消息为什么不需要冲突解决：每台设备写的是不同的消息（不同 msg_id），没有"同一位置被两个写入者覆盖"的并发；append-only 只需要去重。把消息当可变状态去合并，就会引入本不存在的冲突。

                                        五条不变量应该进 CI：用确定性随机模拟（固定 seed）注入断网、乱序、重复，跑固定步数后逐条断言；写扩散/读扩散这类策略切换时，同一 seed 的终态必须一致——这是回归测试能抓住"同步逻辑改坏"的唯一低成本手段。

                                        与会话保证的映射：四条保证在 IM 里怎么落

                                        一致性模型的定义在 16.6 会话保证 (读己之写、单调读、单调写)，本节只讲 IM 的落点：

                                        会话保证 IM 里的落点 实现手段
                                        读己之写 自己发的消息立刻出现在自己的会话里 本地 echo 先展示（带 client_msg_id），服务端 ACK 回来后用 conv_seq 校准位置，重复的按 msg_id 去重
                                        单调读 同一设备不会"看到新消息后又退回旧状态" 每设备游标只进不退 + 已读 read_seq 只增不减
                                        单调写 同一设备的连续操作不会互相覆盖回退 设置/草稿带 base_version，服务端按单调序号拒绝旧写
                                        写跟随读 发消息前先看到会话的最新状态 同步响应带 snapshot_seq，后续写入基于该水位

                                        代价是"多久能看见"从强一致的毫秒级变成最终一致的秒级：实测推叫醒 + 拉补全在持续有消息的负载下 P50 = 27 ms（实验 B）；到了设备离线 25% 时间的弱网压测（实验 A），P99 是 17.8 s。SLO 要按 P99 收敛时间定，而不是按"推送到达率"定——推送到达率再好，客户端不拉也看不见。

                                        已读的显示口径要提前定：自己发的消息显示"对方已读"，语义是"对方的用户维度已读位点越过了这条"，而不是"对方的每台设备都确认"；否则一台设备离线，"已读"就永远不亮。多端之间按用户维度 max 合并，设备维度只用于当前会话的展示，不参与幂等判定。

                                        客户端本地也要有"同步状态机"：idle → pulling → applying → converged；pulling 失败按错误码决定是否回退，applying 必须幂等（按 change_seq / msg_id 去重），否则重放会把本地状态改乱。服务端幂等 + 客户端幂等两边都要，只做一边，弱网重试下仍会出现重复或回退。

                                        四个同步指标：sync_cursor_lag（设备游标落后服务端的 change_seq 数）、sync_pull_bytes（每设备每次拉取字节）、sync_fail_ratio（按错误码分桶的失败率）、sync_converge_p99（从发消息到全部设备可见的 P99）。前两个看积压，后两个看体验；只盯推送成功率会得出错误的健康结论——推送成功但客户端不拉，一样不收敛。

                                        设备管理与踢下线

                                        • device_id 必须在安装时生成并持久化：每次登录生成新 ID，服务端就认为是一台新设备，旧游标作废、首登全量，代价是 14.29 MiB 起步（实验 C）。
                                        • "多端同时在线"与"同端互踢"是两条产品策略：默认多端在线、消息按设备游标各推各的；同类型设备（如第二台手机）上线时可以选择踢掉旧的，此时只失效被踢设备的令牌，其他端游标不受影响。策略写进协议里，而不是靠客户端自觉。
                                        • 服务端维护登录设备列表（型号、最后活跃、是否被踢）。踢下线是三个动作的组合：令牌失效（见 49.5 登录态与令牌生命周期）+ 断开网关连接（见 66.1 长连接网关）+ 保留该设备游标 7 天（用户换回设备时还能增量续上）。
                                        • 被踢设备的同步请求返回 401，客户端收到后走登录流程，不在本地反复重试。本机实测：
                                        $ curl -s -w ' [HTTP %{http_code}]' 'http://127.0.0.1:18103/sync?device_id=t_pad&amp;change_cursor=0'
{"device_id":"t_pad","error":"device_kicked","hint":"令牌已失效，需重新登录（服务端同时断开 66.1 的连接）"} [HTTP 401]

                                        全量还是增量：分界线

                                        实验 C 用 10 万条历史消息、20 个会话、48 字符正文真实测：

                                        • 全量快照（会话列表 + 10 万条消息）：14,979,131 B ≈ 14.29 MiB，JSON 编码中位 99.5 ms；gzip 后 5,331,325 B（压缩比 2.8×）；按 1 Mbps 弱网折算传输约 119.8 s。
                                        • 断线 1 小时增量（0.5 条/秒 → 1,800 条变更）：424,866 B ≈ 415 KiB，编码中位 3.1 ms，按 1 Mbps 折算约 3.4 s。
                                        • 全量/增量 = 35.3×；实测每条变更的增量成本 ≈ 236 B/条（change 瘦条目 + 消息正文 + JSON 开销）。

                                        分界公式：分界变更数 = 全量字节 / 每条增量字节 = 14,979,131 / 236 ≈ 63,461 条。按 0.5 条/秒就是 约 35.3 小时离线；gzip 后全量优势变小，分界点约 91,006 条。实测曲线：

                                        离线时长 变更数 增量字节 占全量比例
                                        0.5 h 900 212,466 1.42%
                                        8 h 14,400 3,417,266 22.81%
                                        24 h 43,200 10,271,666 68.57%
                                        72 h 129,600 30,904,066 206.31%

                                        结论：断线 3 天（129,600 条）时增量比全量还贵 2 倍，应直接快照重建游标；短断线走增量。两条边界要记住：别对短断线做全量（首登和频繁重连会把带宽与 CPU 放大 35 倍），也别对长断线做增量（游标早已过期，而且变更流水比快照还大）。游标 7 天 TTL 是另一条硬边界：过期后不管离线多久都只能全量。全量快照必须分页、限流、可断点续传，否则一次发版后所有设备重连就是自我 DDoS。

                                        协议要能版本演进：客户端版本分布不可控，同步响应要带 protocol_version，服务端按版本降级字段（老客户端不认新字段时忽略而不是报错）。加字段是兼容的，改语义不是——change_cursor 的口径一旦变了，必须靠版本号分流，不能悄悄改。

                                        同步不变量：五条可判定的断言

                                        实测 C：全量 vs 增量成本

                                        环境同实验 A。"全量还是增量"一节的数字来自本实验，这里补两个决策要点：

                                        • 编码耗时也是成本：全量 14.29 MiB 的 JSON 编码中位 99.5 ms，gzip 再花 466 ms；一次首登就要吃掉服务端约 0.6 秒 CPU。全量快照必须限流 + 分页 + 缓存，不能每次现算。
                                        • gzip 不是免费的：全量压缩比 2.8×、增量 4.0×，但 gzip 全量要 466 ms CPU；高并发首登时更常见的做法是快照分片 + 按会话拉取，而不是把 14 MB 压成一个包。

                                        全量快照也要有断点续传与一致性水位：快照按页发（每页带 snapshot_seq），客户端记下已收页；中途断线从"下一页游标"继续，而不是从头重发。快照期间服务端仍在写入——所以快照必须绑定一个水位（snapshot_seq），快照完成后从这个水位拉增量，两者之间有重叠、没有缺口（重叠靠 change_seq 去重）。这正是"快照 + 增量"比"只有快照"多一个水位参数的原因。

                                        三条铁律

                                        🔑 只有服务端单调序列能定序。 客户端时钟、消息自带时间戳只能做展示，不能进排序和合并逻辑。

                                        🔑 推送只负责叫醒，数据以拉为准。 正确性不依赖推送到达；推送全丢时，系统仍靠兜底轮询收敛。

                                        🔑 每设备一个游标，增量必须幂等。 游标只走连续前缀，缺口不许跳过；续不上就显式回退快照，不静默丢。

                                        灰度与回滚：同步协议的改动按客户端版本灰度（新端先 5%），服务端同时保留旧响应字段；回滚只需关掉新字段（或切回旧响应路径），不迁移数据——游标与 change 流水是同一套，不因协议版本变化而重建（旧端继续用旧字段，直到自然淘汰）。

                                        自检

                                        Q1 手机、平板、PC 同时在线，怎么保证三端看到的消息不漏、不乱序？ ▸ 答案：给每台设备独立游标（每会话 conv_cursor + 用户维度 change_cursor），服务端为每条消息分配会话内单调 conv_seq，并写入用户维度 change 流水；推送只带水位做叫醒，正文一律按游标拉，客户端按 msg_id 去重、按 conv_seq 排序，游标只推进连续前缀。正确性由 I1–I5 五条不变量验证，而不是由推送保证。

                                        Q2 为什么"把每条消息推给所有端"不够，还需要序列号和游标？ ▸ 答案：推送通道是 at-most-once 且无序的：丢一条就永久丢，乱序到达无法排序，断线期间的消息不在推送里。序列号解决"排序与去重"，游标解决"断线后从哪续"，两者缺一不可；实验 B 里只推方案丢 8.1% 消息、P99 被拉长到 65 s。

                                        Q3 断线 3 天后重连，怎么高效补齐？全量与增量的分界线在哪？ ▸ 答案：先算分界：全量快照 14.29 MiB，每条增量成本约 236 B，分界约 63,461 条变更（0.5 条/秒 ≈ 35.3 小时）。3 天 ≈ 129,600 条，增量要 29.5 MiB 且更慢，应直接全量快照并重置游标；短断线（1 小时 415 KiB）走增量。另外游标有 7 天 TTL，过期无论如何只能全量。

                                        Q4 已读位置为什么用 max 合并？它为什么天然幂等、不需要锁？ ▸ 答案：已读是"最多读到哪"的单调查询，多端上报是同一偏序上的 join；max 满足交换律、结合律、幂等律，所以乱序、重复、并发上报都收敛到同一个值。实测 3,929 次上报里 1,067 次（27.2%）更旧被丢弃，三端已读零回退。

                                        Q5 两台设备同时改同一份设置/草稿，冲突怎么解？为什么消息不需要冲突解决？ ▸ 答案：设置/草稿是可变状态，用 LWW + 服务端单调版本号（不用客户端时钟，因为设备时钟不可信），旧版本写入丢弃；真正并发编辑才用 CRDT，见 25.6 CRDT (计数 / 集合 / 寄存器)。消息是 append-only：两设备写的是不同 msg_id 的不同消息，没有同一位置被覆盖，只需去重，不存在冲突。

                                        Q6 怎么验证同步协议是对的？为什么不能只测正常路径？ ▸ 答案：用五条不变量（不丢/不重/不乱序/已读单调/会话列表收敛）做机器断言，用确定性随机模拟注入断网、乱序、重复、同步失败，最后断言收敛。正常路径测不出"游标跳过缺口""快照与增量之间重复""已读回退"这类只有在乱序/断连下才暴露的缺陷；而且功能类结论必须同 seed 可复现。

                                        Q7 推叫醒 + 拉补全的 P99 由什么决定？为什么它和只拉差不多？ ▸ 答案：由兜底轮询周期决定，而不是推送延迟。推送丢失时消息靠 3 s 兜底拉取补回，P99 落在兜底周期附近（实测 539 ms，只拉 501 ms）；推送只影响 P50（27 ms 对 500 ms）。要把 P99 压下去只能提高兜底频率或用推送重发，代价是流量与能耗。
