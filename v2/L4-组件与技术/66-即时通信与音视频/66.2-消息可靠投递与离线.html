                                    66.2 消息可靠投递与离线

                                    一句话

                                    IM 的"不丢"是五段接力：上行 ACK、服务端持久化、下行投递、离线存储、推送通道；任意一段没兜住就是丢，端到端只能做到 at-least-once + 幂等。

                                    先破三个误区

                                    误区 现实
                                    "网关把字节写进 socket 了，用户就收到了" 只走完第 3 段的一半：内核缓冲区会随进程崩溃/网关重启消失，且跨网关还要再转一跳
                                    "超时重发会重复入库、重复展示" 用 (sender_id, client_msg_id) 唯一键 + 会话 seq，重发命中返回同一条 msg_id
                                    "接上 APNs/FCM 就等于消息可靠了" push 只做"叫醒 + 摘要"，payload 有上限、可丢、用户可关通知；消息本体必须靠拉取

                                    五段接力：每一段都可能失败，各有各的兜底

                                    结论先行：可靠投递不是"一个 ACK"，而是五个独立故障域串联。任何一段只做"尽力而为"，端到端就退化成 at-most-once。

                                    段 动作 典型失败 兜底手段 责任方 可观测指标
                                    ① 上行 client→server 发送并等 ACK 请求丢、超时、服务端未收到 client_msg_id 复用 + 指数退避重试 客户端 SDK 上行成功率、重试率、上行 ACK P99
                                    ② 持久化 分配 conv_seq、写消息表、写收件箱 写失败、主从切换丢未同步数据 同步/半同步复制、失败回 NACK、客户端重发 服务端存储 落库失败率、复制延迟、丢数窗口
                                    ③ 下行 网关推送 + 收端送达 ACK 推送包丢、ACK 丢 服务端重传直到 ACK、客户端按 msg_id 去重 网关 + 客户端 下行重传率、重复投递率
                                    ④ 离线 断线期间写 per-user 收件箱 收件箱写失败、超期被清 冷热分层、保留策略、seq 游标补拉 服务端 离线积压条数、补拉延迟
                                    ⑤ 推送 APNs/FCM/厂商通道叫醒设备 通道丢、通知被关、厂商限频 push 只带摘要，App 起来必拉；push 失败不回滚消息 客户端 + 通道 push 到达率、push→拉取转化率

                                    两个反直觉点：

                                    1. 网关不能替服务端 ACK。网关 ACK 只证明"网关收到了"，不证明落库；网关重启，暂存内存的数据全丢。上行 ACK 必须由"已经持久化的那一层"发。
                                    2. 下行 ACK 丢了也照样可能送达。ACK 只是服务端停止重传的信号；收端可能已经展示。所以重复投递是常态，靠 msg_id 去重而不是靠"ACK 一定不丢"。

                                    上行要不要削峰？ 消息上行 QPS 通常远低于下行（一个人发、N 个人收），所以 IM 的上行瓶颈一般不在队列，而在落库与 seq 分配：同一会话的 seq 必须单写者，削峰只能缓冲、不能并行化。真正需要异步队列的是"扩散"与"推送"两段——把"必须同步完成的"（幂等 + 落库 + 分配 seq）和"可以异步重试的"（扩散、推送、已读聚合）切开，是 IM 写路径最重要的一次切分。切错了，表现就是"消息发出去了但对方迟迟不到"，而上行侧指标一切正常。

                                    两个视角的消息状态机

                                    状态机要分别定义，混在一起就说不清谁负责什么。迁移全部用幂等键 + CAS，不用"先查再改"。两张图对照着看：

                                    客户端（4 态）                          服务端（5 态）
SENDING                                 RECEIVED
  │ 上行 ACK（msg_id + conv_seq）        │ 幂等键 + seq 落库
  ▼                                      ▼
SERVER_ACKED                            STORED
  │ 渲染并上报送达                       │ 投递在线网关 / 写离线收件箱
  ▼                                      ▼
DELIVERED ──打开会话──► READ            PUSHED ──设备 ACK──► DELIVERED ──已读──► READ
                                    状态 视角 迁移条件 落地字段
                                    SENDING 客户端 用户点发送，本地落库后立刻入待确认表 本地库 local_status=0
                                    SERVER_ACKED 客户端 收到上行 ACK（含 msg_id + conv_seq） server_msg_id、conv_seq
                                    DELIVERED 客户端 消息渲染并上报送达 ACK delivered_at
                                    READ 客户端 用户打开会话，上报会话 read_seq read_seq（会话级）
                                    RECEIVED 服务端 请求到达、通过鉴权 无（内存）
                                    STORED 服务端 幂等键 + seq 落库成功 msg_id、conv_seq、status=0
                                    PUSHED 服务端 已投递到在线网关，或已写离线收件箱 pushed_at
                                    DELIVERED 服务端 收到设备级送达 ACK ack_seq（按设备）
                                    READ 服务端 收到用户级已读位点（客户端打开会话上报） read_seq（按用户/设备）

                                    服务端的 DELIVERED→READ 是位点合并，不是逐条状态：一条消息在 3 台设备上，只有 1 台上报已读也算不了整个用户已读。这是多端同步的活（见 66.3 多端同步）。

                                    ID 三件套：三个 ID 职责不能混

                                    ID 谁生成 唯一范围 用途 重试时
                                    msg_id 服务端（发号器，见 44.24 发号器与全局 ID） 全局 定位消息、回执引用、跨端去重 不变：重发命中返回旧值
                                    conv_id + seq 服务端按会话 INCR 会话内 排序、续传游标、连续性检测 不变：同一条消息同一个 seq
                                    client_msg_id 客户端（UUID） (sender_id, client_msg_id) 上行幂等键，唯一索引去重 必须复用，绝不能每次重试新生成

                                    用错 ID 的两种经典事故：拿 msg_id 做上行去重（重发时服务端还没分配 ID，第二次会生成新 msg_id，去重失效）；拿时间戳排序（客户端时钟差、服务端同一毫秒多条，顺序会错乱）。排序的唯一依据是 conv_id + seq。

                                    上行幂等：唯一索引才是裁决者

                                    先取证再判断：MySQL 26.7.0（REPEATABLE-READ）上，20 个并发客户端同时用同一个 (sender_id, client_msg_id) 插入：

                                    --- D4 20 个并发客户端抢插同一个 client_msg_id：唯一索引下只落 1 行
rows_for_cmid2
1
并发退出码统计（0=插入成功, 1=被挡住）:    1 0   19 1 
--- D5 反例：没有唯一索引、用「先查再插」，20 个并发客户端会插出多少行？

                                    D5 里 20 个客户端都先 SELECT 判断"不存在"（SLEEP 0.2 放大窗口），再插入 → 20 行重复。"先查再插"在并发下必出重复，唯一索引必须由数据库兜底；Redis 侧则用 Lua 脚本把"查去重键 + 分配 seq + 落库 + 写收件箱"做成一次原子执行：

                                    -- KEYS[1]=去重键 s662:if:{c66}:dedupe:<client_msg_id>
-- KEYS[2]=会话 seq 计数器  KEYS[3]=消息 hash  KEYS[4]=收件人离线收件箱
local cur = redis.call('GET', KEYS[1])
if cur then return cur end                    -- 重发：返回同一条 msg_id，不新建
local seq = redis.call('INCR', KEYS[2])       -- 只有首次落库才消耗 seq
local mid = 'm-' .. seq
redis.call('HSET', KEYS[3], seq, ARGV[1])
redis.call('ZADD', KEYS[4], seq, mid)
redis.call('SET', KEYS[1], mid, 'EX', 86400)  -- 去重键 TTL 覆盖用户重试窗口
return mid

                                    实测（redis-cli --eval，见 tools/examples/66.2-delivery/code/redis/verify.sh）：同一 client_msg_id 连发两次，两次都返回 m-1，hlen msgs = 1、zcard inbox = 1、seq 计数器 = 1、TTL 剩 86400 秒——重复发送不新增行、不消耗 seq。 示例说明见 tools/examples/66.2-delivery/。

                                    冷路径（MySQL）要求同样的语义。核心 DDL（完整版见 tools/examples/66.2-delivery/code/mysql/schema.sql）： 示例说明见 tools/examples/66.2-delivery/。

                                    CREATE TABLE message (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  conv_id       BIGINT UNSIGNED NOT NULL,
  conv_seq      BIGINT UNSIGNED NOT NULL,        -- 会话内单调，排序/续传/连续性检测
  msg_id        VARCHAR(40)     NOT NULL,
  sender_id     BIGINT UNSIGNED NOT NULL,
  client_msg_id VARCHAR(64)     NOT NULL,        -- 客户端生成，重试复用
  body          VARCHAR(2048)   NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_conv_seq    (conv_id, conv_seq),
  UNIQUE KEY uk_sender_cmid (sender_id, client_msg_id)  -- 上行幂等：重发不新建行
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

                                    重发时服务端必须"返回同一条"，而不是报错让客户端猜。两种写法都实测过：

                                    --- D2 同一 client_msg_id 重发：唯一索引报 1062
ERROR 1062 (23000) at line 1: Duplicate entry '66-1' for key 'message.uk_conv_seq'
--- D2b 服务端已分配新 seq 才发现是重复：uk_sender_cmid 单独报 1062
ERROR 1062 (23000) at line 1: Duplicate entry '1001-cmid-000001' for key 'message.uk_sender_cmid'
--- D3 ON DUPLICATE KEY UPDATE + LAST_INSERT_ID(id) 返回原来的 id
same_id = 1

                                    ⚠️ 唯一索引报 1062 只能证明"重复了"，不能告诉客户端"是哪条"。捕获 1062 后要按 (sender_id, client_msg_id) 再查一次拿回原 msg_id + conv_seq 返回，否则客户端会永远重试。

                                    下行 ACK：逐条、批量、窗口错配

                                    下行 ACK 是"收端已收到"的信号。逐条 ACK 的 QPS 等于消息 QPS 乘以设备数；批量/累计 ACK 能把它压 1–2 个数量级，代价是 ACK 延迟变大、重传窗口变紧。实测（10000 条、100 条/秒、RTO=1000ms、下行丢 2%、ACK 帧丢 5%）：

                                    策略 ACK 帧 重传消息数 重复投递率 平均 ACK 延迟 最终送达
                                    逐条 ACK 10521 521 5.21% 67ms 10000/10000
                                    批量累计 ACK（20 条 / 500ms） 562 1218 12.18% 626ms 10000/10000
                                    纯窗口 800ms 127 5161 51.61% 987ms 10000/10000
                                    窗口 1500ms > RTO 1000ms 69 8245 82.45% 1315ms 10000/10000

                                    读法：ACK 帧从 10521 降到 69（152x），重复投递率从 5.21% 涨到 82.45%。原因不是"批量不可靠"，而是两个机制的耦合：

                                    1. 批量 ACK 承载的是"连续已送达前缀"（累计语义）。中间一个包丢了，前缀卡住，后面已收到的消息都确认不了。
                                    2. 服务端为每条消息独立起 RTO。空洞没补上时，后面消息的 RTO 先到 → 触发一批"伪重传"。窗口越大，空洞期间积压的消息越多，伪重传越多。

                                    所以批量 ACK 有三条硬规则：批量窗口 < RTO（最好 < RTO/2）；必须有空洞快速上报（SACK/seq 区间上报），或把重传收敛为"只补最老未确认"；客户端必须按 msg_id 去重，重复投递是设计内行为。 另一种极端是窗口 > RTO：每条消息都等不到 ACK 就到点重传，ACK 帧省下的带宽全部变成重复下行流量。

                                    真实 Redis 的 ACK 状态写入成本也量了一遍（顺序单连接，3 轮中位数）：逐条 ACK 写 10000 次 HSET 耗 6.029s、key 内存 605592B；批量累计只写 500 次、耗 579ms、内存 49B——写入次数 20×、ACK 状态内存 12359×（耗时比随机器负载在 7–10× 间波动，写作时同机并发测得 10.4×，别把它当基准）。这是"批量 ACK 值得做"的真正理由：省的是服务端状态量和 QPS，不是省客户端几个字节。

                                    你的情况 选什么
                                    单聊为主、消息 QPS 低 逐条 ACK，最简单、重复率最低
                                    超大群/高 QPS、ACK 与消息同量级 批量累计 ACK（20–50 条 / 200–500ms），窗口 < RTO/2，配空洞上报
                                    移动端弱网、丢包 2% 以上 ACK 只能降低重传，兜底仍是 msg_id 去重；不要指望 ACK 必达
                                    直播弹幕/在线状态类 不需要逐条送达语义，走 seq 拉取 + 感知丢弃

                                    离线存储：按人存收件箱，拉完再删

                                    结论：离线消息不要"按会话扫表找"，要"按人写收件箱 + 按 seq 游标分页 + 拉完即删"。三段存储：

                                    层 介质 存什么 保留策略 典型延迟
                                    热 Redis ZSET（按用户） member=msg_id、score=用户维度 seq 时间 + 条数双上限（如 7 天 / 5000 条） 毫秒级
                                    冷 MySQL / HBase / RocksDB 消息本体、回执、会话元数据 长期（审计/多端补拉；分级模型见 39.3 存储分级） 十毫秒级
                                    归档 对象存储 + 索引 历史消息、导出 按合规/成本 秒级

                                    实测（20 个群 × 5000 条消息 = 100000 条，用户离线 7 天积压 5000 条，每页 200）：

                                    指标 按人收件箱 按会话扫表
                                    读取路径 ZRANGEBYSCORE 游标分页 25 页有效（多 1 次空页收尾） 20 个群全量 ZRANGE 再过滤
                                    扫描/读取条目 5000 100000（20x）
                                    总耗时 113.295ms（单页均值 4.357ms） 320ms（2.82x）
                                    取消息本体 pipeline HMGET 5000 条 无（本来就在扫）
                                    游标语义 seq 单调、天然稳定 每会话一个游标，跨会话合并排序困难

                                    注意一个反直觉读数：扫表的数据量是 20x，但本机耗时只慢 2.82x——因为收件箱路径有 26 次网络往返 + 取本体，扫表是 20 次大块读。收件箱的真正代价不在拉取侧，而在存储放大：收件箱 ZSET 实测 89 bytes/条；一个 500 人的群、全员离线时，每条消息要写 500 份引用 = 约 44500 bytes/条。这就是群聊必须另做取舍的原因。

                                    群聊离线的陷阱（结论指向 66.5 群聊与消息扩散，不在此展开）：按人写收件箱 = 写放大 × 群成员数；小群写扩散、大群读扩散、超大群只推"有新消息"。本节只给一句可执行判据：当"群成员数 × 离线天数 × 日消息量 × 89B"超过消息本体存储的 10 倍时，按人收件箱就不划算了。

                                    保留策略必须是"时间 + 条数"双上限，且裁剪要便宜：实测 ZREMRANGEBYRANK 按 rank 裁掉最老 1000 条耗时 1.326ms，ZREMRANGEBYSCORE 拉完即删清空 5000 条耗时 1.745ms。客户端 ack 到哪，服务端就删到哪；游标不推进就不删，保证"至少一次"。

                                    保留期是从"最坏补拉窗口"倒推出来的：太短，用户换机、长假离线后补不回来（表现为"消息凭空消失"）；太长，存储、审计与安全成本一起涨。做法是"时间 + 条数"双上限，并让"过期"成为可观测事件（客户端拿到 expired 标记而不是静默空列表）；合规要求的长保留（审计、取证）走归档层，不占热路径。

                                    推送通道：只做叫醒，不做消息通道

                                    通道 到达率 延迟量级 需用户授权 payload 上限（公开资料） 成本 可测性
                                    APNs 无 SLA；受通知开关/勿扰影响 秒级 是 4KB 免费 只能看发送成功，端到端要靠回执
                                    FCM 无 SLA；国内不可用 秒级 是 4KB 免费 同上，且无厂商级回执
                                    国内厂商通道（小米/华为/OPPO/vivo/荣耀） 各自无公开 SLA；受厂商限频、后台清理影响 秒级 是 约 1–4KB，各家不同 免费但需逐个接 SDK 各家后台统计口径不同
                                    自建长连接 在线/进程存活时接近 100%，被杀进程收不到 百毫秒级 否 无硬上限 服务器成本 最可控（自己打点）

                                    把上表读成一句话：push 的唯一职责是"把 App 叫起来"，消息本体永远走拉取。由此推出三条设计约束：

                                    1. push payload 只放"你有 N 条新消息 + 会话摘要"，不放消息正文；正文以服务端存储为准。
                                    2. push 失败不回滚消息——消息已在收件箱，只是用户晚点知道。实测 A 里 60 批 push 丢了 3 批（影响 152 条消息），这 152 条最终全部送达，只是首达延迟从毫秒级拉长到下一次拉取。
                                    3. 用户关通知 = push 通道彻底失效，但不影响不丢，只影响延迟；产品层的兜底是"下次打开 App 必拉全量增量"。

                                    推送还有个常被忽略的时序问题：叫醒和拉取是两次独立请求，必须能重入。设备可能收到 3 次叫醒才拉起 1 次拉取（合并窗口），也可能拉取在叫醒之前就完成（用户自己打开了 App）；所以叫醒只带"有新消息"的水位，拉取以服务端游标为准——两边都不做"事件绑定"，才能容忍重复与乱序；叫醒里带的水位只用来判断"要不要拉"，不用来判断"拉到哪"（拉到哪永远由客户端自己的游标决定）。

                                    回执体系：送达 ≠ 已读

                                    回执 语义 粒度 谁写 用途 存储
                                    送达 ACK 设备收到并可展示 设备 × 会话 客户端 服务端停止重传；对方"已送达" 可合并为每设备 ack_seq
                                    已读回执 用户看过 用户 × 会话 客户端 未读清零、对方"已读" read_seq（用户维度单调位点）
                                    群已读 群成员看过某条 成员 × 消息 客户端聚合 "已读 37 人"、已读列表 聚合计数 + 分页明细

                                    群已读天然是 O(N²)：N 个成员 × M 条消息。工程上不逐条存，而是按会话存每人 read_seq，需要展示时聚合（人数 = read_seq ≥ 消息 seq 的成员数）。未读数与 read_seq 的派生关系见 44.23 未读数系统；群已读的聚合解法见 66.5 群聊与消息扩散。

                                    业务通知：通道、模板、频控与降级

                                    上一节「推送通道」讲的是 IM 消息的叫醒：push 只负责把 App 拉起来，正文走拉取。业务通知（订单、支付、营销、系统公告）是另一类问题——它没有“会话收件箱”兜底，发不出去就是真的没触达，所以需要独立的通道、模板、频控与降级设计。两者共用 push 通道，但主场不同：

                                    维度 IM 消息推送（上一节） 业务通知（本小节）
                                    目的 叫醒用户去拉消息 把一条确定的信息触达用户
                                    正文 不在 push 里（走拉取） 在通知里（模板渲染后的短文本）
                                    失败兜底 收件箱还在，晚点拉 降级通道（短信/邮件/站内信）
                                    频控 基本不控（消息本身是用户预期） 必须控（营销打扰、系统噪音）
                                    合规 通知开关 退订、敏感词、号码脱敏、保留期

                                    三类通知，三种待遇

                                    类型 例子 时效 频控 免打扰 降级
                                    事务型 支付成功、验证码、订单发货 秒级 不控（用户预期） 放行 push 失败 → 短信
                                    系统型 安全提醒、账单、服务变更 分钟级 弱控 可静默到早晨 push → 站内信/邮件
                                    营销型 活动、优惠券、召回 小时级 强控（每日预算） 夜间延后 只走站内信/邮件，不降级短信

                                    🔑 判断一条通知该不该发，先问“它属于哪一类”，再问“用户有没有同意”。把营销当事务发（不控频、夜间照发）是投诉与退订的第一来源。

                                    通道选型：延迟、成本、到达率、可测性

                                    通道 延迟量级 成本量级 到达率口径 适合
                                    Push（APNs/FCM/厂商） 秒级 免费 发送成功 ≠ 送达（受开关/勿扰/清理影响） 事务/系统叫醒
                                    短信 秒级 约 0.03–0.06 元/条 运营商回执 事务兜底、验证码
                                    邮件 分钟级 约 0.001 元/封量级 送达/打开分开统计 账单、长文通知
                                    站内信 拉取时可见 存储成本 打开 App 才可见 营销、系统公告

                                    成本是公开量级，不是报价；到达率必须写清是“发送成功率”还是“端到端送达率”，否则运营看到的 99% 与用户感知的 90% 会对不上。

                                    模板与变量：渲染失败不能等于通知丢失

                                    模板 = 固定文案 + 变量（{name}、{order_id}、{amount}）。三条规则：

                                    1. 变量缺失渲染占位符（如 —），不要抛异常整条失败；缺变量率要成为指标（超过 5% 修模板/修上游）。
                                    2. 模板版本化：文案改动可回滚，不能直接改线上模板。
                                    3. 敏感字段不进模板：手机号、地址、金额在模板里只放脱敏/格式化后的值。

                                    频控与免打扰：打扰预算是产品参数，不是异常阈值

                                    • 营销：每用户每日 N 条（如 2 条）+ 每周 M 条；超预算的请求在入口就裁掉（人群圈选/分流），不要放到投递集群再丢。
                                    • 免打扰：23:00–07:00 营销延后、系统静默、事务放行；延后要记“延后时延”，否则会污染整体通知时延分位。
                                    • 幂等：同一条通知用业务键（order_id + template_id）去重，重试/重放不重复打扰。

                                    送达率口径：一张表把话说清

                                    指标 分子 分母 用途
                                    发送成功率 通道返回成功 请求发送 发现通道故障
                                    送达率 端到端回执/展示 发送成功 评估真实触达
                                    打开率 打开/点击 送达 评估内容与时机
                                    退订率 退订人数 触达人数 营销健康度（红线指标）

                                    失败重试与降级：给每个通道独立预算

                                    • 事务通知：push 失败/永久失效（如卸载、关闭通知）→ 短信兜底；短信也失败 → 站内信 + 人工工单。
                                    • 营销通知：只降级到站内信/邮件，不降级短信（成本与打扰都不允许）。
                                    • 重试窗口必须小于业务 SLO（验证码 60s 内到，重试窗口就不能按 30 分钟算）。
                                    • 每条通知记“最终通道 + 是否降级”，否则无法算降级率与成本。

                                    怎么证明"没丢"：序号连续性 + 对账 + SLO

                                    三件事各查一段，缺一段就只是"感觉没丢"：

                                    1. 会话 seq 连续性：按 (conv_id) 扫 seq 是否连续，缺口 = 丢或未同步。注意是会话级不是全局；全局 ID 不保证连续，也不能拿时间戳排序。
                                    2. 两端对账：发送端待确认表（SENDING/SERVER_ACKED 集合）与接收端已收集合按 msg_id 做差集，差出来的就是"以为发了但没收到的"；对账任务本身用延迟消息驱动（见 43.7 延迟消息与定时消息）。
                                    3. SLO：发送成功率、P99 端到端延迟、丢失率、重复率四个指标。丢失率的分母是"发送端认为成功的消息数"，重复率的分母是"接收端展示的消息数"，不要混。

                                    实测 A 的证明形态：seq 覆盖 1..10000、缺号 0；原始投递 10427 条、重复 427 条（下行重传 258 + 拉取重投 169），按 msg_id 去重后恰好 10000 条；发送端幂等命中 176 次、服务端只落库 10000 条。

                                    端到端语义：at-least-once + 幂等 ≈ 业务等价 exactly-once

                                    哪一段无法原子，推导很直接：

                                    • 客户端"落库后、发出上行 ACK 前"崩溃 → 重启重发 → 服务端收到两次；
                                    • 服务端"落库后、收到下行 ACK 前"崩溃/重传 → 客户端收到两次；
                                    • 两个跨进程边界都没有"分布式事务 + 幂等提交"的原子点。

                                    所以端到端 exactly-once 是伪命题，不可能三角是"不丢、不重、不阻塞"三选二：要不丢就会重（重传），要不重就会阻塞（等 ACK 等到超时），要低延迟就只能放宽一条。工程等价物 = at-least-once + 幂等键 + 会话 seq，业务层表现为"恰好一次"。MQ 位点语义与消费幂等的主场在 43.2 投递语义 (at-most / at-least / exactly-once) 与 43.6 可靠投递与幂等消费，本节只借用结论、不复述位点机制。幂等的一般方法（幂等表、唯一键、状态机）见 25.4 幂等设计与去重。

                                    读数 数值 架构含义
                                    单页拉取 4.357ms 均值 / 9.443ms 最慢 游标分页延迟与积压总量无关，只与页大小有关
                                    扫表放大 20x 条目 / 2.82x 耗时 数据量放大 20 倍但耗时只 2.82 倍：扫表不是慢在 IO，是慢在"没法分页+跨会话合并"

                                    裁剪/清理 1.326ms / 1.745ms 保留策略必须可在线执行，不能扫全表

                                    失败面也要能演：用没有唯一索引的表 + "先查再插"，20 个并发客户端会插出 20 行重复（raw/experiment-D-mysql.txt 的 D5）；反过来加了唯一索引，20 个并发只有 1 个成功、19 个收到 1062。

                                    可退（降级开关，按代价从低到高）：

                                    1. 去重键写入失败 → 降级为本地布隆过滤器 + 定时对账（短暂重复可接受，不能丢）；
                                    2. 离线收件箱超限 → 降级为"只拉最近 N 条 + 服务端标已过期"，客户端提示"消息已过期"；
                                    3. push 通道故障 → 关闭 push 只留拉取，产品上表现为"打开 App 才收到"；
                                    4. 大群收件箱写放大打满 → 自动切读扩散（见 66.5 群聊与消息扩散）；
                                    5. MySQL 主库故障 → 上行 ACK 暂停（宁可让客户端重试），不要在主从未同步时 ACK。

                                    什么时候别用这套：日活几十人的内部 IM 直接买云 IM 服务；不需要离线补拉的系统（纯在线弹幕）不需要收件箱和 seq 对账；追求"实时一致性"超过"可达性"的场景（如信令控制面）应换强一致 Raft 组，而不是加 ACK 重传。

                                    反模式

                                    反模式 后果
                                    只用 msg_id 去重，不用 client_msg_id 重发时服务端还没分配 msg_id，每次生成新 ID，去重失效 → 重复入库、重复展示
                                    "先查再插"判重 并发下 TOCTOU：实测 20 并发插出 20 行重复；必须靠唯一索引兜底
                                    ACK 在网关层发 网关重启丢暂存内存，服务端以为成功，消息永久丢失
                                    离线消息按会话全表扫 数据量随群规模爆炸；实测 100000 条扫表 vs 5000 条收件箱（20x），且跨会话无法分页合并
                                    把 push 当消息通道 push 有 payload 上限、可丢、用户可关通知；丢了消息就没兜底
                                    已读回执逐人逐条同步 O(N²) 写放大，群一大就打满带宽与存储；应聚合为 read_seq
                                    无 seq 只靠时间戳排序 客户端时钟漂移、同毫秒多条，顺序错乱且无法检测缺口
                                    保留期无限长 收件箱无限膨胀；实测 89B/条 × 离线设备数，500 人群写扩散就是 44.5KB/条
                                    ACK 延迟窗口大于重传超时 每条消息都在 ACK 到达前触发重传：实测窗口 1500ms > RTO 1000ms 时重复投递率 82.45%
                                    丢消息不报警、没有序号连续性检测 丢了没人知道；对账任务缺位，"没收到报错"被当成"没丢"

                                    三条铁律

                                    🔑 铁律一：ACK 必须由"能重传的那一层"发。 上行 ACK 由已持久化的服务端发，下行 ACK 由客户端发；网关只转发、不替服务端 ACK，因为网关内存里的数据重启即丢。

                                    🔑 铁律二：去重键由重试方生成并复用。 client_msg_id 客户端生成、重试不变、唯一索引兜底；msg_id 只做全局定位，绝不能拿来当上行去重键。

                                    🔑 铁律三：不丢的最终证明是"seq 连续 + 对账"，不是"没报错"。 没有序号连续性检测和两端对账，"没丢"只是没被发现。

                                    自检

                                    Q1 客户端点发送后超时，重试三次都超时，但服务端其实三次都落库成功。最终用户会看到几条消息？为什么？ ▸ 答案：一条。三次请求都携带同一个 client_msg_id，服务端第一次分配 msg_id + conv_seq 并写入去重键，后两次命中返回同一条 ID，不新建行。前提是客户端重试必须复用 client_msg_id；如果每次重试新生成，那就是三条消息。

                                    Q2 服务端已经 ACK 了，客户端却没收到 ACK，客户端重发；此时服务端怎么回答才能既不让客户端重试、也不产生重复？ ▸ 答案：用 (sender_id, client_msg_id) 查去重键/唯一索引，命中就返回第一次的 msg_id + conv_seq（MySQL 可用 ON DUPLICATE KEY UPDATE id=LAST_INSERT_ID(id) 拿回原 id）。不能返回 1062 让客户端自己猜；返回同一条 ID，客户端才会停止重试并复用本地那条消息。

                                    Q3 为什么下行的批量 ACK 窗口不能设成大于 RTO？上界怎么定？ ▸ 答案：窗口 > RTO 时，服务端在 ACK 到达前必然先到重传定时器，每条消息至少多投一次（实测窗口 1500ms > RTO 1000ms：重复投递率 82.45%，ACK 帧只剩 69 个）。上界取 RTO/2 左右，给网络抖动留余量；同时必须配空洞上报或"只补最老未确认"，否则累计前缀被一个丢包卡住，后面消息的 RTO 先到会触发一批伪重传（实测 800ms 窗口也有 51.61% 重复）。

                                    Q4 一个 500 人的群，10% 成员离线 3 天、每天 200 条消息。按人写收件箱的额外存储是多少？该怎么选？ ▸ 答案：离线 50 人 × 600 条/人 × 89B/条 ≈ 2.67MB，看起来不大。但看每条消息写几份：一条消息要写 50 份引用 = 4450B/条，而本体约 86B/条（实测单群 hash 431179B / 5000 条），放大 50 倍。日消息量一大就不划算，应切读扩散，见 66.5 群聊与消息扩散。

                                    Q5 数据里出现 seq 缺口，怎么判断是"丢了"还是"客户端没同步"？下一步查什么？ ▸ 答案：分两类查：服务端消息表里有该 seq → 存储没丢，是下行/拉取链路没送达；表里没有 → 真丢了，查上行 ACK 后的落库与复制链路。两类都要补一次两端对账，而不是盲目重发。

                                    Q6 有人主张"我们端到端做 exactly-once"，你怎么反驳？ ▸ 答案：指出两个无法原子的跨进程边界：客户端"落库后、发 ACK 前"崩溃会重发；服务端"落库后、收下行 ACK 前"崩溃/重传会重投。不存在能把这两个点与对端状态绑成一个事务的机制。可行承诺是 at-least-once + 幂等键 + 会话 seq，业务层用去重达到"恰好一次"的效果；不可能三角"不丢/不重/不阻塞"只能选二。

                                    Q7 push 到达率只有 60%，消息会丢吗？产品上怎么兜底？ ▸ 答案：不会丢。消息在服务端收件箱里，push 只负责叫醒；到达率低只拉长"用户看到"的延迟。兜底：payload 只带摘要（不带正文），App 启动/回前台/网络恢复时按 seq 游标增量拉取；push 失败不回滚消息，也不重发消息本体。实测 A 中 60 批 push 丢 3 批，影响的 152 条消息全部最终送达。
