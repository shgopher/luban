                            66.4 音视频信令与媒体传输

                            一句话

                            实时音视频的关键是把控制面（信令）与数据面（媒体）彻底分开：信令要可靠、有序、可重放，媒体要低延迟、可丢包；1v1 才 P2P，群聊必须 SFU——这不是偏好，是带宽公式算出来的。

                            先破除五个误区

                            误区 现实
                            用上 WebRTC 就通了 WebRTC 只包办"媒体怎么加密、怎么协商、怎么打洞"；信令、房间、多端、录制都要自己建，信令挂了媒体能力再强也发不出第一帧
                            P2P 省服务器，能用就用 P2P 客户端上行是 (N-1)×码率：4 人 1080p/3Mbps 每人要上行 9Mbps，很多家庭宽带与 4G 上行只有 5–10Mbps 量级
                            线上问题九成是编解码 编解码选型几天定死，故障却天天变；本机把 relay 建连从 2.0s 降到 4.6–14.0ms 靠的是一个 ICE 提名参数
                            TURN 是兜底，能省就省 对称 NAT 与严格企业网下，没有 relay 候选就是永久连不上；TURN 是可用性项，不是优化项
                            弱网就是"网络差"，加带宽就行 丢包、RTT、抖动、带宽是四个正交维度；加带宽不解决丢包，NACK 也不解决抖动

                            一、控制面与数据面：为什么必须彻底分开

                            核心结论：信令的失败模式是"呼叫没建立"，媒体的失败模式是"卡一下继续播"；两者要的传输保证相反，放进同一条通道就是把媒体的队头阻塞转嫁成信令超时。

                            维度 控制面（信令） 数据面（媒体）
                            载体 TLS / WebSocket / HTTP 长轮询，可复用长连接网关 UDP + SRTP（加密）/ RTCP（反馈）
                            可靠性 不能丢、要有序；重复接听、乱序挂断都是事故 允许丢，靠 NACK/FEC 补，补不上就跳过
                            延迟要求 百毫秒级可接受 P95 单向 <150ms 才谈得上"实时对话"
                            内容 call_id、状态迁移、SDP、ICE candidate、鉴权 token RTP 音视频帧、RTCP 统计与反馈（RR/NACK/PLI/REMB）
                            失败后果 呼叫建立失败或状态错乱，可重试、可提示 卡顿、花屏、音画不同步，用户直接流失
                            调试手段 调用链日志 + SDP 文本 + 状态机 抓包（SRTP 需密钥）/ 端点 getStats()
                            扩容单位 连接数、QPS、房间数 转发带宽（Mbps）、端口数、CPU（转码）

                            把两者塞进一条 TCP 会同时得到三个故障：视频大帧堵住信令 ACK，出现"接通了但对方还没收到挂断"；丢一个包触发 TCP 重传，整条通道上所有媒体一起等；重连风暴时媒体重传挤爆信令队列，越重连越连不上。WebRTC 的选择就是信令的可靠性用重传换，媒体的实时性用丢包换。

                            一次通话的建立顺序（可直接对照服务端日志排查）：

                            步 方向 消息/动作 关键点
                            1 主叫 → 服务端 invite{call_id, from, to, media} call_id 是幂等键；服务端校验 from，不信任客户端
                            2 服务端 → 被叫 ringing（同时下发推送叫醒离线端） 振铃超时 30–60s（推荐值），到点自动 cancel
                            3 被叫 → 服务端 answer{call_id} 服务端 CAS 抢占，只允许一个 answer 生效
                            4 双方 ↔ 服务端 sdp{offer/answer} 信令只搬运，不解析 SDP 字段
                            5 双方 ICE 收集 + 连通性检查 +（必要时）TURN allocation 10–15s 没有可用 pair 就判失败（推荐值）
                            6 双方 DTLS 握手 → 派生 SRTP 密钥 实测回环 2.2–2.5ms；弱网下被重传拖长
                            7 双方 ⇄ 双方/SFU RTP/RTCP 媒体流 数据面开始，信令只保留保活与 renegotiation

                            什么时候不需要两条独立通道：1v1 小产品、通话量很低时，信令完全可以复用现有的 WebSocket 通道，不必单独部署信令服务；但媒体仍然必须走 UDP，"省掉的是信令服务，不是数据面分离"。

                            信令通道可以复用长连接网关的 WebSocket，但不要重复造：网关的连接路由、心跳、重连抖动治理见 66.1 长连接网关，WebSocket 升级与心跳的基础机制见 8.11 长连接与 WebSocket。

                            二、信令状态机：每个状态都要有超时和幂等键

                            核心结论：信令服务本质是一台单通话串行状态机：用 call_id 做幂等键、seq 抗乱序、CAS 抢答；任何一项缺失，都会在重试或并发下变成重复呼叫、双端接通、僵尸通话。

                            状态 进入条件 允许事件 超时 超时动作
                            IDLE 无通话 invite — —
                            CALLING 主叫已发 invite，服务端已落库 ringing/reject/cancel/离线推送 振铃 30–60s 发 timeout，释放资源，写结束原因
                            RINGING 被叫在线且已下发 ringing answer/reject/busy/主叫 cancel 30–60s 自动 cancel，被叫停止振铃
                            CONNECTING 收到 answer，双方交换 SDP ICE 连通 / ice_failed / hangup 10–15s 降级（仅音频/切 SFU）或挂断
                            CONNECTED ICE+DTLS 就绪、首帧到达 media_update（renegotiation）/hangup 无媒体 5s 检测 标记异常、触发重连（ICE restart）
                            ENDED 任一方挂断、超时、失败 无（只允许查询） — 归档 CDR、释放 TURN 配额

                            异常分支要显式建模，不能 catch-all：

                            异常 触发方 服务端行为 主叫看到 被叫看到
                            拒接 被叫 reject → ENDED "对方已拒绝" 自己拒接
                            忙线 服务端（被叫有 CONNECTED 通话） 直接 busy，不进 RINGING "对方忙" 无打扰
                            取消 主叫 cancel → ENDED 挂断 振铃停止
                            对方离线 服务端（查在线表） 先推离线推送，超时未上线则 unreachable "对方暂时无法接听" 上线后收到未接来电
                            抢答冲突 两个设备同时 answer CAS 只放行第一个，第二个回 409 正常通话 后到设备转"通话中"

                            幂等落地很朴素：call_id 由发号器生成、全局唯一，服务端以它为键落库；重复 invite 只返回已有状态，不新建。抢答用一条带条件的更新，受影响行数 = 1 才算成功：

                            UPDATE call_session SET state='CONNECTING', answered_by=:device_id, answered_at=NOW()
WHERE call_id=:call_id AND state='RINGING';
-- affected rows = 1：接听成功；= 0：已被别人接听，回 409

                            抗乱序两条：每条信令带单调 seq，服务端按 call_id 串行化（单通话 actor / 分布式锁），客户端丢弃小于已处理值的消息（重试的退避与超时预算见 35.5 超时、重试与退避）。重放窗口不需要长——通话生命周期通常分钟级，关键是每通电话有独立边界，ENDED 即封口。最小消息 schema：

                            {"type":"invite","call_id":"c_01J8Z3K9Q2","seq":1,"from":"u_1001","to":"u_1002","media":["audio","video"],"sdp":null,"ts":1763700000000}

                            多端同账号提前定死规则：所有在线设备同时响铃（提升接听率），任一设备接听后向其余设备下发 cancel_ringing；CONNECTED 期间再收到 invite 按"忙线"还是"第二路通话"是产品决策，但必须在状态机里显式表达。防信令轰炸的限流见 35.7 限流 (漏桶 / 令牌桶 / 滑动窗口 / 自适应)。

                            信令服务自身也是有状态服务（房间/参与者状态与僵尸清理，以下为工程经验值，非本机实测）：

                            • 房间与参与者状态存哪：每房间一个内存 actor，join/invite/answer/hangup 事件串行处理，免锁且天然有序；同时把 room:{id} Hash（成员、发布/订阅关系）与 call:{id} 状态写 Redis 并带 TTL 兜底，进程崩溃后从 Redis 恢复，不靠重放信令日志。
                            • 信令心跳与僵尸清理：客户端信令心跳 15–30s，连续 2–3 次收不到判死；ENDED 后 Redis key 保留 60min（便于重连查状态、补收未接来电），到期自动过期；后台每分钟对账一次，扫「状态还是 CONNECTED、但两条腿心跳都停了超过 60s」的僵尸通话，标 timeout 归档并释放 TURN 配额——不清理的话 TURN 端口与计费记录会一直漏。
                            • 离线推送分两种通道：iOS 走 VoIP push（PushKit + CallKit，App 被杀也能弹系统来电界面，需单独申请 PushKit 授权、审核更严）；Android 走厂商普通 push 的高优先级通道 + 全屏 intent。推送只带 call_id 和 from，不靠 push 保时序——推送是 at-most-once，端到端状态一律以服务端状态机为准，客户端上线后按 call_id 查真实状态。

                            三、WebRTC 三件套：SDP 协商、ICE 连通、TURN 兜底

                            核心结论：SDP 回答"我们用什么编码怎么发"，ICE 回答"包走哪条路能到"，TURN 回答"没有路时从哪绕"；三者串行依赖，任何一环失败，媒体一帧都出不去。

                            组件 解决的问题 输入/输出 失败后果 失败为何难查
                            SDP 能力协商：编解码、方向、ICE 参数、DTLS 指纹 offer/answer 文本，交换后参数一致 无公共编解码 → 无媒体；方向错 → 静音 纯文本但字段极多，sendonly/recvonly 不匹配肉眼难看出
                            ICE 连通性：用候选地址做连通性检查，选出一条可用 pair 候选（host/srflx/prflx/relay）+ 提名结果 找不到 pair → CONNECTING 卡死超时 没有统一错误码，只能看候选收集与 pair 状态
                            TURN 中继：双方都在 NAT 后且打洞失败时，用服务器转发 allocation（中继地址+端口），需 refresh 续命 没有 relay 候选 → 该类网络永久连不上 用户只看到"转圈"，服务端只看到 allocation 数为 0

                            SDP 只需看懂关键行：

                            SDP 关键行 含义 配错时的典型现象
                            m=video 9 UDP/TLS/RTP/SAVPF 96 媒体行、端口、加密与 RTP 配置、payload type 端口 0 = 拒收该媒体；不是 SAVPF 就没有 SRTP
                            a=rtpmap:96 VP8/90000 payload type 映射到编码与时钟频率 双方无交集 → 协商失败或只有音频
                            a=rtcp-fb:96 nack 声明支持 NACK 反馈 不写就没有重传能力，丢包即花屏
                            a=ice-ufrag / a=ice-pwd ICE 凭证，成对出现 不匹配 → 连通性检查全部 401
                            a=fingerprint:sha-256 ... DTLS 证书指纹，防中间人 与真实证书不符 → DTLS 握手失败
                            a=setup:actpass/active/passive DTLS 角色协商 双方都是 active/passive → 握不上
                            a=sendrecv/sendonly/recvonly 媒体方向 双方都 sendonly → 谁也没收到

                            ICE 候选分四类，能力与代价完全不同：

                            候选类型 怎么来 何时胜出 代价
                            host 本机网卡地址 双方同局域网，最快 0，跨 NAT 不可用
                            srflx 经 STUN 拿到自己的公网映射地址 锥形 NAT 下打洞成功 一次 STUN 交互，可忽略
                            prflx 连通性检查时从对端包的反向地址发现 打洞过程中的意外收获 0，不可预期
                            relay TURN 分配的服务器中继地址 对称 NAT / 严格企业网下的唯一路径 带宽翻倍 + 多一跳 + 服务器端口

                            候选优先级是 host > prflx > srflx > relay（RFC 8445 推荐的类型优先级：host 126、prflx 110、srflx 100、relay 0）；实践中最常见的胜出顺序仍是 host → srflx → relay，所以有直连就绝不会用 relay；反过来当 host/srflx 全失败时 relay 是唯一让通话成立的路径——这就是"TURN 不可省"的全部理由。公网直连失败率随网络环境差异极大（公开资料量级在百分之十上下），但只要有 1% 的用户必失败，就是事故。

                            什么时候别强制 relay：生产默认用 all 策略（先直连、失败才中继），不要为了"链路质量可控"把所有人强制设成 relay-only——那会平白多两跳、把服务器带宽成本翻 4 倍（实测回环 relay 也多出 0.2–0.55ms，公网放大到几十毫秒量级）；只有排障、合规要求或对端不可控时才临时强制。

                            三个工程细节：trickle ICE 让候选边收边发，把建连从"等收集完"压到一个 RTT 量级（本机 gathering 3ms 内完成，公网 relay 收集通常几十到几百毫秒，量级估算）；renegotiation（屏幕共享/加轨）要重新 offer/answer，但通话状态机不能重置，失败只回滚媒体轨；TURN 凭证必须短时，标准做法是 TURN REST API 风格：username = 过期时间戳:用户id、password = base64(HMAC-SHA1(secret, username))，有效期与呼叫时长挂钩（如 1 小时），服务端只校验签名与过期时间。

                            加密不用额外设计：WebRTC 强制 DTLS-SRTP 与 DTLS，证书指纹走 SDP；传输层证书与 mTLS 见 8.6 TLS 握手、证书与 mTLS，密钥体系见 38.4 加密 (对称 / 非对称 / TLS / 密钥管理)，信令协议分层见 8.5 HTTP/1.1、HTTP/2、HTTP/3 (QUIC)。

                            四、拓扑选型：P2P / SFU / MCU

                            核心结论：拓扑不是偏好问题：P2P 客户端上行是 (N-1)r，SFU 服务器出口是 N(N-1)r，MCU 服务器出口是 Nr——三条公式代进去，人数上限和成本差一眼算完。

                            维度 P2P 全互联 SFU（选择性转发） MCU（服务端混流）
                            端到端延迟 最低（1 跳） 低（2 跳） 较高（解码+混合+编码，量级 +100ms 起）
                            服务端 CPU 0 低（只转发，不编解码） 高：解 N 路 + 编 N 路（或混 1 路）
                            服务端出口带宽 0 N(N-1)r Nr（混一路）
                            客户端上行 (N-1)r r（每人只发一路） r
                            人数上限 3–4 人（受上行限制） 数十人（受带宽/端口限制） 数十人（受 CPU 限制）
                            录制/转推 极难（要在客户端录） 容易（服务器旁路订阅） 最容易（已是混流）
                            成本结构 用户带宽 服务器出口带宽 服务器 CPU
                            典型场景 1v1 通话、客服、双人面试 群会议、互动直播、在线课堂 传统视频会议、需要统一画面的直播

                            9 人 1080p（单路 3Mbps，量级假设）的带宽账：

                            N 客户端上行/人 SFU 入口 SFU 出口 出口流量（GB/小时） P2P 每客户端上行
                            2 3 Mbps 6 Mbps 6 Mbps 2.7 3 Mbps
                            3 6 Mbps 9 Mbps 18 Mbps 8.1 6 Mbps
                            4 9 Mbps 12 Mbps 36 Mbps 16.2 9 Mbps
                            6 15 Mbps 18 Mbps 90 Mbps 40.5 15 Mbps
                            9 24 Mbps 27 Mbps 216 Mbps 97.2 24 Mbps
                            16 45 Mbps 48 Mbps 720 Mbps 324.0 45 Mbps

                            两条结论直接读表：第一，P2P 在 N=4 时每人要上行 9Mbps，已超过大量家庭宽带上行能力，所以 P2P 上限就是 3–4 人；第二，SFU 出口按 N² 增长，9 人 216Mbps 是 1v1 经 SFU（6Mbps）的 36 倍，服务器总流量是 1v1 的 20.2 倍——群视频成本大头不在 CPU 在出口带宽。若云厂商公网出流量按 0.7 元/GB 量级算，9 人 1080p 一小时出口流量成本约 68 元（公开报价量级，非实测）。再往上（16 人 720Mbps、50 人 7.35Gbps）必须级联/分区/SVC 选层，而不是加单机带宽。

                            你的情况 选什么 理由
                            1v1 通话/客服，双方网络可协商 P2P + TURN 兜底 省 2 跳与服务器出口带宽，延迟最低
                            3–4 人小会，要求简单 P2P 也能用，但建议直接 SFU 统一录制、降级、订阅控制，运维成本更低
                            ≥5 人，或需要录制/转推/服务端混流 SFU P2P 上行不可承受；录制与转推都需要服务端旁路
                            下行极弱、终端极老，只求看得见 MCU 每人只收 1 路，代价是服务端 CPU 与延迟
                            百人以上互动直播 SFU + simulcast + 只订阅少数 用分层编码控制下行，别让所有人收最高清

                            五、弱网策略：FEC、NACK、jitter buffer、ABR、simulcast

                            核心结论：弱网手段没有"最优"，只有"用什么换什么"：FEC 用带宽换丢包，NACK 用延迟换丢包，jitter buffer 用延迟换抖动，ABR 用清晰度换流畅，simulcast 用服务端复杂度换异构下行。

                            手段 修什么 适合区间（工程经验值） 代价 什么时候别用
                            NACK（重传） 随机丢包 丢包 5%–20% 延迟：至少 +1 RTT（实测 P99 单向 5.6ms → 269ms） 丢包 <1% 时白增延迟；RTT >300ms 时重传来不及
                            FEC（前向纠错） 随机丢包 音频、小比例丢包 1%–5% 带宽（冗余通常 10%–30%） 大丢包时冗余也丢，带宽反正更紧
                            jitter buffer 抖动、乱序 有缓冲的播放端 延迟（典型 50–200ms 量级，可自适应） 交互式场景别开太大
                            ABR / 码率自适应 带宽不足 带宽波动 清晰度 码率写死时降不下来，卡死是必然
                            simulcast / SVC 异构下行（有人 4G 有人 WiFi） 群聊、直播 服务端复杂度、上行多路编码 1v1 别做 simulcast：两端只有一路，白费上行

                            拥塞控制记一句话：发送端用 GCC/TWCC（延迟梯度 + 丢包 + 接收端反馈）估可用带宽并调码率；到 SFU 后，订阅侧按每个接收者的带宽选 simulcast 层。视频丢包下的降级顺序应是：先降码率（ABR）→ 再开 NACK/FEC → 再降分辨率/帧率 → 最后仅音频；反过来先砍分辨率最差——码率没降、丢包还在，画质先没了。

                            六、质量指标与降级阶梯

                            核心结论：通话质量要拆成 RTT、丢包、抖动、卡顿、首帧、端到端延迟六个可采集的数，每个数对应不同修法；把所有弱网问题都归因"网络差"，等于放弃定位。

                            指标 定义 目标（推荐） 采集方式
                            RTT 端到端往返时延 P50 <100ms，P99 <300ms ICE selected pair 心跳 / RTCP SR-RR
                            丢包率 收包缺口 / 发送数 <1% 无感，>5% 需干预 RTCP RR 的 fraction lost、接收端 seq 统计
                            抖动 到达间隔相对发送间隔的偏差 <30ms RTP 时间戳与到达时间差
                            卡顿率 卡顿次数/时长占通话时长 卡顿时长 <1% 应用层帧间隔（连续 >200ms 无新帧）
                            首帧时间 接听成功 → 首帧渲染 P50 <1s（量级目标） 客户端埋点
                            端到端延迟 采集→编码→网络→解码→渲染 见 G.114 分档 同源时钟或音画同步打点
                            MOS 综合主观分（1–5） ≥4 好，3.5–4 可接受 由上述指标映射，非直接测量

                            延迟分档用 ITU-T G.114 建议（公开标准）：单向 <150ms 自然；150–400ms 可接受但能感到回声与抢话；>400ms 无法正常对话。注意是单向延迟；工程上常用 RTT/2 近似，但编解码与 jitter buffer 还要加 30–100ms，所以 RTT 超过 200ms 就该检查链路，而不是只调参数。

                            指标采样与告警的做法不在本节展开：直方图与基数控制见 50.4 度量（四黄金指标 / 直方图 / 基数爆炸），SLO 与错误预算见 50.7 SLO 与错误预算，P99 口径见 34.1 性能指标 (延迟 / 吞吐 / P99)。这里强调一点：通话质量必须按通话维度聚合（每通电话一个结果），只按机器聚合会把"这一通全黑"稀释成"整体 0.01% 丢包"。

                            降级阶梯（触发条件是工程经验值，需按产品调）：

                            级别 触发条件 动作 用户提示 恢复条件
                            L0 正常 丢包 <5%，RTT <200ms 1080p/720p 原分辨率 无 —
                            L1 降清晰度 丢包 >10% 或带宽估计 <1.5Mbps，持续 5s 720p → 360p，降帧率 "网络不稳定，已降低画质" 指标恢复并稳定 10–15s
                            L2 降帧率 丢包 >20% 持续 5s，或 RTT >300ms 帧率降到 10–15fps，开更重的 FEC（更高冗余比例） "网络较差" 同上（迟滞）
                            L3 仅音频 带宽估计 <300kbps，或视频卡顿 >3s 关视频保留音频 "已切换为语音模式" 带宽恢复并稳定
                            L4 重连 5s 无媒体或 ICE 断开 ICE restart（同 call_id 重新协商） "正在重连…" 成功则回 L0；失败挂断

                            两个易错点：降级要有迟滞（升级条件比降级更严、观察窗口更长），否则网络在阈值附近抖动会让画质反复横跳；恢复要自动，但只能恢复到网络能承载的档位。

                            实测：本机回环建连、TURN 对比与弱网注入

                            核心结论：本机实测：host 直连建连 6–9ms、DataChannel RTT P50 0.18ms；强制 relay 后建连 7–23ms，但 Pion 默认的 relay 提名等待会把建连钉在 2.0s；NACK 把 5% 丢包救回 100% 到达，代价是 P99 单向时延从 5.6ms 抬到 269ms。

                            环境：macOS 15.6 (Apple M1, 8 核) / Go 1.27.1 / Pion webrtc v4.2.27 + turn v4.1.4 / 2026-11-21。同机并行跑着 5 个写作任务，延迟数字有 ±20% 以上抖动，下面取多轮噪声较小的几轮。

                            实验 A：两个 PeerConnection 回环建连（host 直连）

                            信令用进程内 channel + JSON 序列化模拟"过线"，trickle ICE（远端 SDP 未就绪时先缓存 candidate），A 建 DataChannel、B 原样回显。核心配置只有几行——回环测试必须打开 loopback 候选，否则建不起来：

                            se := webrtc.SettingEngine{}
_ = se.SetEphemeralUDPPortRange(13500, 13509)           // 固定端口段，便于隔离与抓包
se.SetICEMulticastDNSMode(ice.MulticastDNSModeDisabled) // 回环环境不需要 mDNS
se.SetIncludeLoopbackCandidate(true)                    // 关键：默认会过滤 127.0.0.1 候选
se.SetNetworkTypes([]webrtc.NetworkType{webrtc.NetworkTypeUDP4})
se.SetInterfaceFilter(func(name string) bool { return strings.HasPrefix(name, "lo") })

pcA, _ := webrtc.NewAPI(webrtc.WithSettingEngine(se)).NewPeerConnection(webrtc.Configuration{})
offer, _ := pcA.CreateOffer(nil)
_ = pcA.SetLocalDescription(offer)                      // 从这开始 trickle 出 candidate
// 对端：SetRemoteDescription(offer) → CreateAnswer → SetLocalDescription
// candidate 逐个走信令转发；双方都收到对端 candidate 后 ICE 进入 checking

                            relay 的 RTT 代价在回环上只有 +0.2–0.55ms（多两跳），但这是最理想情况，公网会大得多：真实 relay 比直连多出"客户端↔TURN"一整段 RTT，跨省通常几十毫秒量级（估算）；且 TURN 带宽双向计费，1v1 双方都中继时 TURN 总流量 = 4× 媒体码率。"relay 便宜、随便用"是错觉，正确姿势是能直连就直连，直连失败必须能切 relay。

                            非共识发现②：TURN over TCP 真的可用，且事件里的协议字段会骗人。 关掉服务端 UDP（-udp=false -tcp），客户端用 ?transport=tcp 依然建连成功（5.5–7.0ms）；allocation 事件里的 proto=UDP 指relay 转发协议，不是客户端到 TURN 的传输。反过来的失败更值得记住：UDP relay 客户端打 TCP-only TURN 时不报错，gathering 等到 7.8s 才 complete，然后 CONNECTING 卡到 20s 超时（raw/expA-fail-udp-vs-tcponly.txt）：

[+ 2.55ms] A ice-conn -> checking
[+ 7809.44ms] B ice-gathering -> complete
[+ 7810.18ms] A ICE gathering complete

                            这就是"配错 TURN"在生产上的表现：用户只看到一直转圈，服务端只看到 allocation 数为 0。 客户端必须自己给 ICE 失败兜底（超时降级/切 SFU），不能指望底层报错。

                            实验 C：网络层注入丢包与时延

                            用 SettingEngine.SetNet() 换掉网络实现：包装 transport.Net，让 ListenPacket/ListenUDP 返回的 conn 在 WriteTo 时按概率丢包（返回成功，模拟 UDP 链路丢包）、delay>0 时异步延迟发送，两个方向各注入一份：

                            func (n *lossyNet) write(b []byte, write func([]byte) (int, error),
	mu *sync.Mutex, rnd *rand.Rand) (int, error) {
	mu.Lock()
	r := rnd.Float64()
	mu.Unlock()
	if r < n.cfg.loss {                    // 丢包：对上层返回成功，等于链路层丢弃
		atomic.AddUint64(&n.dropped, 1)
		return len(b), nil
	}
	if n.cfg.delay > 0 {                   // 时延：异步发，别阻塞 ICE/DTLS 的写调用栈
		buf := append([]byte(nil), b...)
		go func() { time.Sleep(n.cfg.delay); _, _ = write(buf) }()
		return len(b), nil
	}
	return write(b)
}

                            媒体用 TrackLocalStaticRTP 直接写 RTP 包（VP8/PT 96、800B、20ms 一个），payload 前 4 字节放样本序号，接收端按同进程时钟算单向时延。两个坑：只包 ListenPacket 时注入完全不生效——设置端口段后 ICE 的 host 候选走 transport.Net.ListenUDP，必须同时包 UDPConn 的写路径；另外 Pion 默认不消费 sender 的 RTCP，不调 sender.Read() 的话 NACK 响应器收不到 NACK，重传永远不生效（这是"开了 NACK 却没重传"的一手根因，也是第三个反直觉点）。

                            配置 到达/400 丢失 乱序 单向时延 P50 / P99 DC RTT P50 / P99 建连
                            无丢包基线 400 0 0 0.24 / 5.59ms 0.15 / 1.04ms 6.1–10.0ms
                            5% + NACK 400 0 26 0.25 / 269.37ms 0.17 / 203.36ms 7.4ms
                            5% 无 NACK 380 20 0 0.25 / 7.20ms 0.20 / 202.76ms 7.3ms

                            读法：NACK 把 5% 丢包从 95% 到达救到 100%、20% 丢包救到 99.25%，代价是 P99 单向时延从 5–7ms 抬到 270–310ms（NACK 生成器默认 100ms 一轮 + 重传 RTT）；无 NACK 时到达率就是 (1-p) 的裸值。20% 双向丢包下 DTLS 握手被重传拖到 7.0s（另一次 1.2s），弱网下建连超时不能按理想值设，否则用户还没连上就被判失败。

                            反模式 后果
                            信令与媒体共用一条 TCP（甚至用 WebSocket 传媒体） 媒体大帧与重传堵住信令，通话卡顿时连"挂断"都发不出去

                            不部署 TURN，只配 STUN 碰运气 对称 NAT/企业网用户永久连不上，表现为"一直转圈"，客服无法自愈
                            用 TCP 传音视频 丢包触发重传放大延迟，越弱网越卡，形成正反馈
                            信令不做幂等（无 call_id 或重复 invite 就新建） 双击/重试产生两路通话，绑定计费时变成重复扣费事故
                            ICE 超时设 30s 甚至 60s 用户干等半分钟才看到失败，期间无法重试；应 10–15s 判失败并给兜底
                            把所有弱网问题归因"网络差" 丢包、RTT、抖动、带宽修法完全不同，改错参数让问题更糟
                            码率写死、不做 ABR 与降级阶梯 带宽一降就永久卡死；没有降级路径就没有恢复路径
                            群视频直接转发原始流、不做 simulcast/选层 下行差的人拖垮 SFU 出口，一人卡全群卡
                            僵尸通话不清理、TURN allocation 不释放 TURN 端口/配额被占满，新呼叫建不起来，通常高峰期爆
                            信令 from 字段信任客户端 可冒充任意用户发起呼叫与计费，属安全漏洞而非 bug
                            只按机器维度看质量指标 单通电话全黑被稀释成整体正常，用户投诉时日志早已滚掉

                            三条铁律

                            🔑 控制面与数据面分开：信令走可靠有序的 TCP/TLS 通道并要求幂等（call_id + seq + CAS），媒体走 UDP 且允许丢包；把媒体塞进信令通道，等于用队头阻塞换延迟。

                            🔑 拓扑由带宽账决定：客户端上行 (N-1)r、SFU 出口 N(N-1)r、MCU 出口 Nr，三条公式一算——1–4 人可 P2P，5 人以上必须 SFU，需要混流/极弱下行才上 MCU。

                            🔑 TURN 不是兜底而是必经之路：没有 relay 候选就有一批用户永远连不上；relay 的代价是带宽翻倍（双向计费）加多一跳，必须提前算进容量与成本，而不是等事故了再加。

                            自检

                            Q1 信令和媒体为什么不能共用一条 TCP 连接？说出两个具体的故障链。

                            ▸ 答案：TCP 有序可靠，代价是队头阻塞。故障链一：视频大帧占满发送缓冲，其后的 hangup 排队，对方迟迟收不到挂断，通话变僵尸。故障链二：媒体丢包触发 TCP 重传，整条连接所有流一起等；弱网下重传越积越多，媒体延迟爆炸，同时心跳与 ICE 消息被堵，连接最终被判失败。所以信令要可靠（重传换正确性），媒体要实时（丢包换延迟），必须在传输层分开。

                            Q2 4 人 1080p/3Mbps 的 P2P 通话，为什么说已经到上限？5 人呢？给出算式。

                            ▸ 答案：P2P 每人要发给其余 N-1 人，上行 (N-1)×3Mbps：4 人 = 9Mbps/人，5 人 = 12Mbps/人。家庭宽带上行 5–10Mbps 量级、4G 上行更低，9Mbps 已让一部分用户不可用，12Mbps 基本不可行。所以 P2P 实际上限 3–4 人，超过就该上 SFU，每人只发 1 路上行。

                            Q3 SDP、ICE、TURN 各解决什么问题？为什么 TURN 在"能直连"的公司内网也必须部署？

                            ▸ 答案：SDP 协商能力（编解码/方向/ICE 参数/DTLS 指纹），ICE 做候选发现与连通性检查选路径，TURN 在打洞失败时中继。TURN 不能省是因为公网用户、远程办公、对称 NAT、严格企业网会打洞失败——这些人不在你的内网里，只要有一个，没 relay 就是永久连不上。本机实测也验证：relay-only 策略下没有可用 TURN 时 gather 超时、20s 后连接失败且不报错。

                            Q4 5% 丢包下 NACK 能救回多少到达率？代价是什么？为什么 1v1 场景要慎开 FEC？

                            ▸ 答案：本机实测 400 样本、5% 丢包：无 NACK 到达 380/400（95%），开 NACK 后 400/400，但单向时延 P99 从 7.2ms 抬到 269ms（NACK 周期 100ms + 重传往返）。代价是延迟，所以 NACK 适合"丢得起一次 RTT、但不想丢帧"的场景。1v1 的丢包通常小且路径稳定，FEC 要付 10%–30% 冗余带宽、收益有限；应先确认是不是路径问题（relay/家用路由/WiFi），而不是盲目加冗余。

                            Q5 两端同时接听，服务端怎么保证只有一路生效？为什么还要 seq 和重放窗口？

                            ▸ 答案：用带条件的更新做 CAS：UPDATE ... WHERE call_id=? AND state='RINGING'，受影响行数为 1 的那次生效，另一次返回"已被接听"（409）。seq 解决消息乱序：重试与多路径会让 answer 早于 invite 到达，必须按 call_id 串行化并丢弃旧 seq。重放窗口防重复消息被当新事件（如重复 hangup 把刚建立的通话挂掉），而通话有天然边界（call_id 生命周期），封口后旧消息一律丢弃即可，窗口不需要无限长。

                            Q6 9 人 1080p/3Mbps 的 SFU 通话，服务器出口带宽是多少？和 1v1 经 SFU 差几倍？什么情况下要考虑级联/分区？

                            ▸ 答案：SFU 出口 = N(N-1)r = 9×8×3 = 216Mbps，入口 27Mbps，合计 243Mbps；1v1 经 SFU 出口 6Mbps、合计 12Mbps，所以出口差 36 倍、总流量差 20.2 倍。这个倍数按 N² 增长：16 人 720Mbps、25 人 1.8Gbps。单机出口到数 Gbps 且成本不可接受时，就要级联 SFU（跨区/跨运营商两跳）或按房间分区，并用 simulcast 让每个接收者只收自己承受得了的层。

                            Q7 线上收到"通话黑屏/一直转圈"，按什么顺序定位？给出三步，并说明每步看什么数。

                            ▸ 答案：第一步看信令状态机停在哪：CALLING/RINGING 停住是信令或推送问题（查在线表、推送结果、invite 日志）；CONNECTING 停住是 ICE 问题（查候选类型与 pair 状态，有没有 relay 候选、TURN allocation 是否成功）。第二步若已 CONNECTED 但黑屏，看媒体面 getStats()：inbound-rtp 收包数是否为 0、RTT/丢包/首帧时间；0 收包优先查 SDP 方向（sendonly/recvonly）与编解码协商，有收包但黑屏查解码与渲染。第三步看网络路径：选中 pair 是 host 还是 relay、丢包与 RTT 的 P99，relay 且 RTT 高就是 TURN 质量或跨区问题。三步都过不了再怀疑编解码——顺序反了会把大部分时间浪费在最后一层。
