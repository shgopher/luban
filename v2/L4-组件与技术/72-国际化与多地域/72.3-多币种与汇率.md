# 72.3 多币种与汇率

## 一句话

> 多币种的坑不在汇率公式，在四件事被谁负责：**金额用什么类型、舍入在哪一层、汇率带不带 as_of、分摊残差谁来平账**——本机实测 100 万笔 0.01 用 float64 累加漂 **1.72e-7 元**、同一笔 100 万 JPY 订单跨一个周末的 USD 收入差 **15.7161 美元（25.08 bps）**、ECB 与 er-api 同日 USD/JPY 差 **69.67 bps**。答案是内部标准表示（整数最小单位 + 币种 exponent）→ 边界转换（带 as_of 的快照）→ 版本化 → 可回退。

## 三个误区

| 误区 | 现实 |
|---|---|
| float64 误差小到可以忽略 | 误差小不是重点，重点是**答案取决于实现**：同一个 1.005，Go 用 float64 乘 100 再 half-up 得 **1.00**（实测 A），PostgreSQL 把 `1.005::float8` 转 numeric 再 `round` 得 **1.01**（实测 C2）。对账两边各算一遍就是终身 1 分差 |
| 金额一律保留 2 位小数 | SIX 官方 ISO 4217 表 178 个币种里 **17 个 0 位、7 个 3 位、2 个 4 位、13 个无辅币**（实测 D，Pblshd 2026-09-17）。JPY 存 2 位等于每笔多一个永恒的 `.00`；KWD 只存 2 位直接丢千分之一 |
| 有汇率表就能换算 | 同日两源 USD/JPY 差 **69.67 bps**（158.644222 vs 159.749510，实测 B2c）；ECB 周末不更新（90 天文件 65 个交易日、零个周六日；抓取日 11-21 周六，最新 as_of 仍是 11-20）。没有 `as_of` 与 `source` 的 rate 等于没有 rate |

## 金额表示：三种类型、三条判据

| 表示 | 精度 | 范围 | 误差 / 溢出 | 用在哪 | 致命点 |
|---|---|---|---|---|---|
| float64 | 二进制尾数 53 位 | 1.8e308 | 0.1+0.2≠0.3；100 万笔 19.99 漂 −0.0001 元（实测 A1） | 排序、图表、报表近似 | 舍入结果依赖实现，1.005 两种答案 |
| int64 最小单位 | 由币种 exponent 决定 | ±9.22e18（按分=9.2e16 元） | 无表示误差，只有溢出 | 交易、账务、分摊、对账 | 混合币种聚合要先换算；3/4 位小数币种要换单位 |
| numeric(19,4) / decimal 库 | 十进制精确，4 位小数 | 整数 15 位 + 4 位小数 | 超 1e15 溢出（实测 C4） | SQL 求和/窗口、财务报表 | 比 int64 慢；4 位对 CLF/UYW 刚好，对 1/5 非十进制不够 |

三条判据：① 参与金额运算（加减乘除、分摊、对账）就永远不用 float——不是误差大小问题，是同一笔数在两处得到不同结果；② 需要在 SQL 里求和使用 `numeric(19,4)`，别把最小单位塞进 `float8` 再求和（PostgreSQL 也没有 `round(double precision, int)`，见实测 C2）；③ 跨语言传输用字符串，形如 `{"amount":"19.99","currency":"CNY"}` 或最小单位字符串，别用 JSON number——int64 的 9007199254740993 编成数字后按 float64 解析会变 9007199254740992（实测 A4b）。

推荐组合（我的判断）：应用层 `int64` 最小单位 + `currency` 字段，PostgreSQL 落 `numeric(19,4)` 或 `BIGINT + exponent`，两层之间只经一个 `Amount` 值对象转换，禁止裸 int64 跨层传递。

```go
// 金额值对象：币种 + 最小单位 + exponent，三样缺一不可比较
type Amount struct {
	Minor    int64  // 最小单位：JPY=1 元、CNY=1 分、KWD=1 费尔
	Currency string // ISO 4217 字母码
	Exp      int8   // 由 ISO 表得来（实测 D：17 个币种 =0、7 个 =3），不写死 100
}

// Convert 只在边界调用：rate =「1 unit 换 rate 个 quote」；big.Rat 做十进制乘除，
// 避免 float 把实现相关的末位带进金额。
func (a Amount) Convert(rate float64, toExp int8) (int64, error) {
	if rate <= 0 {
		return 0, fmt.Errorf("invalid rate %v", rate)
	}
	scale := new(big.Int).Exp(big.NewInt(10), big.NewInt(int64(toExp-a.Exp)), nil)
	x := new(big.Rat).Mul(new(big.Rat).SetInt64(a.Minor), new(big.Rat).SetFloat64(rate))
	return roundHalfUpRat(x.Mul(x, new(big.Rat).SetInt(scale))), nil // half-up 整数版见实测 A
}
```

## exponent 不是常数：两套表会打架

ISO 4217 的 minor units 决定「1 个主币等于多少个最小单位」，按币种分档，不是全局常量：

| 档位 | 币种（SIX 官方表去重后全量） | 个数 |
|---|---|---|
| 0 位 | BIF CLP DJF GNF ISK JPY KMF KRW PYG RWF UGX UYI VND VUV XAF XOF XPF | 17 |
| 2 位 | 默认档（USD EUR CNY GBP…） | 多数 |
| 3 位 | BHD IQD JOD KWD LYD OMR TND | 7 |
| 4 位 | CLF UYW | 2 |
| 无辅币 N.A. | XAU XAG XPT XPD XDR XBA–XBD XSU XTS XUA XXX | 13 |

更麻烦的是**两套权威表对同一币种给出不同 exponent**（实测 D 交叉比对，15 项冲突，节选）：

| 币种 | ISO minor units | CLDR digits | CLDR cashRounding | 该信谁 |
|---|---|---|---|---|
| IQD | 3 | 0 | — | 存储/账务按 ISO=3；展示按 CLDR=0 |
| MGA | 2 | 0 | — | 同上；现实辅币是 1/5（文档值，见未验证） |
| HUF | 2 | 0 | 5 | 账务 2 位；现金价按 5 福林进位 |
| 另有 AFN ALL COP IDR IRR KPW LAK LBP MMK SOS SYP YER | 2 | 0 | — | 同上，合计 15 项 |

还有第三种口径：**现金进位**。CLDR 里 CHF `cashRounding=5`、DKK `cashRounding=50`、HUF `cashRounding=5`、MRU `cashRounding=20`——刷卡可以到分，付现金只能到 5 分/50 欧尔。账务小数位、展示小数位、现金进位是三个独立配置，混成一个 `scale=2` 常量就是事故。

> 🔑 **exponent 表要作为带版本号的配置资产**（币种、数字代码、minor units、展示位数、现金进位、生效日期）：账务用 ISO 口径、展示用 CLDR 口径，两张表都进代码评审。

## 舍入：只在「对外出具金额」处舍一次

| 模式 | `0.5` | `2.5` | `−0.5` | `0.125`（2 位） | 典型用途 / 坑 |
|---|---|---|---|---|---|
| half-up（远离零） | 1 | 3 | −1 | 0.13 | 零售价、发票、税；`floor(x+0.5)` 在负数上会偏 |
| half-even（银行家） | 0 | 2 | −0 | 0.12 | 利息、大批量对账；与用户手算不一致，客服要能解释 |
| toward-zero | 0 | 2 | −0 | 0.12 | 内部展示、临时估算；系统性少算，不能用于应收 |
| floor | 0 | 2 | −1 | 0.12 | 积分、平台让利、可用额度；对用户有利，成本要预算 |
| ceil | 1 | 3 | −0 | 0.13 | 税费、最低收费；对平台有利，用户侧投诉点 |

上表是本机实测 A2 的原样数字：`0.5` 在 half-up 与 half-even 差 1 个最小单位，`0.125` 差 1 分。再看实测 A3：每行 33.33 元、税率 9.50%，**逐行舍入再相加 = 634 分，合计后舍入 = 633 分，差 1 分/单**。

五条规则：① **先乘后舍**——金额 × 数量 × 税率一次算完，只在出具处舍入一次；② **合计优先**——行项目存精确值，合计处舍一次，不要「每行舍完再相加」；③ **差额只能由最大余数法分配**，不能随手补在最后一行（审计最爱抓这个）；④ **税与折扣的先后固定**（先折后税 = 先算净额再计税），顺序不同会产生分级差；⑤ **舍入模式与 exponent 一起落库**（`rounding_mode`），否则同一单据重算两次可能差 1 分。

## 分摊：最大余数法是唯一能平账的算法

每份独立四舍五入，加起来不等于总额（实测 A4：100.00 给 3 人，3333×3=9999 分，少 1 分；实测 A5：999 分给 7 人，独立舍入合计 1001 分，多 2 分）。最大余数法把余数显式分配，恒等式 `sum(份额) == total` 永远成立：

```go
// splitLargestRemainder 把 total（最小单位）按 weights 分摊：
// ① 向下取整得基础份额 ② 记余数 ③ 剩余单位按余数从大到小逐份 +1
func splitLargestRemainder(total int64, weights []int64) []int64 {
	var wsum int64
	for _, w := range weights {
		wsum += w
	}
	out := make([]int64, len(weights))
	rem := make([]int64, len(weights))
	var allocated int64
	for i, w := range weights {
		out[i] = total * w / wsum // 先乘后除，避免整数除法先丢精度
		rem[i] = total * w % wsum // 余数决定谁多拿 1 分
		allocated += out[i]
	}
	left := total - allocated // 0 <= left < len(weights)
	idx := make([]int, len(weights))
	for i := range idx {
		idx[i] = i
	}
	sort.SliceStable(idx, func(a, b int) bool { return rem[idx[a]] > rem[idx[b]] })
	for k := int64(0); k < left; k++ {
		out[idx[k]]++ // 余数相同按索引升序，保证可重放
	}
	return out
}
```

同一算法在 SQL 里用窗口函数实现（完整查询见 `code/c-postgres.sql` 的 C7，实测输出：10000 分给 3 人 → 3334/3333/3333，合计 10000）：`floor(total*weight/sum(weight))` 得基础份额与余数 `frac`，剩余单位按 `row_number() OVER (ORDER BY frac DESC, uid)` 逐份 +1。

单笔差 1 分看着无害：实测 A6 用最大余数法把 1 万笔 100.00 元分给三方，累计差额 0 分；换成独立舍入，1 万笔 × 1 分 = 100 元，100 万单就是 1 万元/年——这就是[67.3 对账与差异处理](../67-交易与账务/67.3-对账与差异处理.md)里那类「每天几百条 1 分差」的来源。

## 汇率：先问方向，再问时间

**方向**：`rate = 1 base 换多少 quote`。ECB 全部以 EUR 为 base（1 EUR 分别兑 1.0990 USD、7.3388 CNY、174.35 JPY），换 USD base 必须 `EUR/CNY ÷ EUR/USD`（实测 B1：USD/CNY=6.677707）。任一来源先确认 base、再确认 bid/ask、再确认 as_of，缺一样写出来的换算函数就是随机数。

**mid / bid / ask**：展示用 mid，成交用对应方向——`ask` 是买入 base 付出的 quote，`bid` 是卖出 base 得到的 quote；取倒数时 bid/ask 互换，写反等于天然亏一个点差（真实点差未验证，见实测 D 后的「未验证」）。

**三角交叉**：同源三角恒等——实测 B2a 用 ECB 数据 USD→CNY→JPY 与直接 USD/JPY 差 **0.0000 bps**，两者都从 EUR 推导，数学上无误差。误差全部来自跨源/跨时间：实测 B2b 用 er-api 的 USD/CNY × ECB 的 CNY/JPY 得 158.983310，对比 er-api 直接 159.749510，差 **−47.96 bps**；同日两源 USD/JPY 直接差 **69.67 bps**。**三角换算要留 buffer，不是公式不准，是两条腿的数据源与时间戳不同。**

**as_of 与有效期**：ECB 每日 16:00 CET 发布一次参考价，周末与 TARGET 假日不更新（实测 B0：90 天文件 65 个交易日、无周六日；抓取日 2026-11-21 是周六，最新 as_of 仍是 2026-11-20）。

| 用途 | 用哪个价 | 必须落什么 | 有效期 | 错了的后果 |
|---|---|---|---|---|
| 展示参考价 | mid | `as_of`、`source` | ≤1 个发布周期（如 1h 缓存） | 页面价与扣款价不一致，投诉 |
| 下单锁价 | mid ± spread | `quote_id`、`expires_at` | 10–15 分钟 | 支付时汇率动了，拒单或补差 |
| 结算入账 | 锁价快照 | `rate`、`as_of`、`source`、`version` | 永久 | 用今日汇率重算历史订单 = 白送/白亏 |
| 退款 | **原订单快照** | 原 `quote_id` | 永久 | 用今日汇率退款，损益记错 |

实测 B4 就是「用今日汇率重算」的代价：同一笔 1 000 000 JPY 订单，按 2026-11-13（周五）USD/JPY=159.998190 折 **6250.0707 USD**，按 2026-11-16（周一）159.596877 折 **6265.7868 USD**，一个周末差 **15.7161 USD（25.08 bps）**；用该汇率推算 1000 笔同额订单，收入差 **15 716.09 USD**（推算，非实测收入）。一周内 USD/JPY 极差 85.35 bps（实测 B6），这是定价护栏至少要覆盖的量级。

## 定价与结算：价格是配置，汇率只做边界

| 问题 | 做法 | 反例 |
|---|---|---|
| 区域定价 | 价格表按 `(sku, region, currency)` 存 `amount_minor` + `effective_from`；锚定币种只用于成本核算 | 用「基础价 × 今日汇率」实时算售价，用户刷新一次变一次 |
| 本地展示 | 锚定币种 + 本地价目表；汇率只用来校验本地价没偏离成本带 | 展示价用 mid 直接乘，越过支付通道点差 |
| 汇率护栏 | 本地价 ÷ 锚定价 偏离超过阈值（至少覆盖一周极差 85.35 bps + 通道点差）告警/改价 | 阈值取 5 bps，每天误报 |
| 退款 | 引用原 `quote_id`，按原 `rate` 退 | 按当前 mid 退，用户拿到不同金额 |
| 汇兑损益 | 只产出 `fx_gain_loss` 事件或分录请求（原币账户、本位币账户各一条） | 在订单表里改金额，账实不符 |

汇兑损益的**记账口径**（科目、方向、试算平衡）是[67.4 复式记账与账务模型](../67-交易与账务/67.4-复式记账与账务模型.md)的主场，这里只给接口边界：每笔跨币种业务输出 `{原币金额, 原币币种, 记账币金额, 使用汇率, quote_id}` 五元组，记账侧据此生成借贷分录，业务侧不写科目。套餐与配额的币种口径见[65.3 计费与配额](../65-多租户SaaS/65.3-计费与配额.md)。

## 数据模型：汇率表必须带三样东西

```sql
CREATE TABLE fx_rate (
  base char(3) NOT NULL, quote char(3) NOT NULL,      -- 报价方向：1 base = rate 个 quote
  rate numeric(24,12) NOT NULL,                       -- 12 位小数够 JPY/KWD，别用 float8
  as_of timestamptz NOT NULL,                         -- 数据源标注的报价时点，不是入库时间
  fetched_at timestamptz NOT NULL,                    -- 抓取时间，用于发现源停更
  source text NOT NULL, version int NOT NULL,         -- 来源；同一三元组的修订号（回滚用）
  PRIMARY KEY (base, quote, as_of, source, version)
);
CREATE TABLE quote_snapshot (                         -- 订单锁价快照，只追加不修改
  quote_id uuid PRIMARY KEY, order_id bigint NOT NULL,
  base char(3) NOT NULL, quote char(3) NOT NULL,
  rate numeric(24,12) NOT NULL, as_of timestamptz NOT NULL,
  source text NOT NULL, spread_bps int NOT NULL,      -- 展示 mid 与成交价的差，审计要看
  rounding_mode text NOT NULL, expires_at timestamptz NOT NULL
);
```

三条建模要点：① **`rate` 不用 float8**——`numeric(24,12)` 才能完整保留 158.644222 与 159.749510 的 69.67 bps 差；② **缓存 key 带 source 与 as_of**（`fx:{base}:{quote}:{source}:{as_of}`），不能只缓 `fx:USD:CNY`；③ **多币种账户/流水**——一个账户一个币种（见[67.4](../67-交易与账务/67.4-复式记账与账务模型.md) 的「一号一币种」），流水存 `原币金额 + 原币币种 + 记账币金额 + quote_id`，只存换算后金额会让历史订单无法复算；字段类型与范式取舍见[44.6 关系模型与范式](../44-数据库/44.6-关系模型与范式.md)。

回滚两个开关：汇率按 `(as_of, source, version)` 选版本，源出错整批回退；报价快照只追加不修改，回滚=重新引用旧 `quote_id`。金额序列化的跨语言细节（字符串 vs 数字、字段编号兼容）在[42.2 序列化与 IDL](../42-远程调用/42.2-序列化与IDL.md)已讲透，这里只留结论：**金额传字符串**。

## 实测 A：float64 vs int64、五种舍入、最大余数分摊

环境：macOS arm64 / Apple 芯片 / Go 1.27.1 / 2026-11-21。


| 读数 | 数字 | 架构含义 |
|---|---|---|
| 舍入的「同值不同命」 | 1.005 → 1.00（Go） | 不是快慢问题，是同一笔数两套实现两个答案；金额类型必须全链路统一，且绝不 float |
| 累加误差 | 100 万笔 0.01 漂 1.72e-7 元；19.99 漂 −0.0001 元 | 单笔可忽略，但账务是百万行级累加，且误差随路径变化，不能靠「最后四舍五入」修 |
| 舍入顺序 | 逐行 vs 合计差 1 分/单 | 100 万单/年 = 1 万元；口径必须写进单据（先算合计再舍） |
| 残差 | 3 人分 100 元少 1 分；999 分给 7 人多 2 分 | 唯一解是最大余数法，`sum==total` 要作为单测断言 |
| JSON | 2^53 后丢 1 个最小单位 | 跨语言传输用字符串；前端 JS 的 `Number` 只保证 2^53−1 |

## 实测 B：汇率方向、三角交叉、往返、as_of

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 float/double 存金额 | 100 万笔 19.99 累加漂 −0.0001 元；1.005 在 Go 与 PG 得到 1.00/1.01 两个答案，对账永久差 1 分 |
| 每行独立舍入后直接求和 | 100.00 分给 3 人少 1 分；999 分给 7 人多 2 分；100 万单 = 1 万元/年 |
| 用今日汇率重算历史订单 | 一个周末 25.08 bps；1000 笔 × 100 万 JPY 差 15 716 USD |
| 只存换算后金额，不存原币与 quote_id | 退款、对账、汇兑损益全部无法复算，只能拍脑袋调账 |
| 假设所有币种 2 位小数 | 178 个币种里 26 个有辅币的不是 2 位（另 13 个无辅币）；JPY 出现 0.5 元、KWD 丢千分之一 |
| 三角换算不留 buffer | 跨源三角 −47.96 bps、同日两源 69.67 bps，任一都大于多数业务毛利 |
| 汇率表没有 `as_of`/`source`/`version` | 无法判断停更、无法回滚、无法审计，出事只能全量重算 |

## 三条铁律

> 🔑 **金额是「整数最小单位 + 币种 exponent」的值对象，永远不用 float。** 同一笔数在 Go 与 PostgreSQL 里舍入结果可以不同（1.005 → 1.00 / 1.01），所以类型、exponent、舍入模式必须全链路一致且落库。

> 🔑 **汇率是「带 as_of 与 source 的快照」，不是一张当前值表。** 历史订单只能引用快照（`quote_id`），用今日汇率重算的代价是每个周末 25 bps 量级；快照只追加、按 version 回滚。

> 🔑 **舍入只发生在对外出具金额处，一次；差额只能由最大余数法分配。** `sum(份额) == total` 是硬断言，不是「对账时再看」；每行独立舍入再相加，误差随订单量线性累积。

## 自检

**Q1** 为什么说「float64 误差小」不是不用它的理由？给出两个本机实测证据。

▸ 答案：问题不是误差大小，而是**答案取决于实现**：同一个 1.005，Go 用 float64×100 再 half-up 得 1.00，PostgreSQL 把 `1.005::float8::numeric` 再 `round` 得 1.01（实测 A1/C2）；另外 100 万笔 19.99 累加漂 −0.0001 元、0.01 累加漂 +1.72e-7 元，误差随聚合路径变化，不能当确定值用。

**Q2** 一个系统只做 JPY 和 KWD 两个币种，金额类型怎么定？存 2 位小数会怎样？

▸ 答案：JPY exponent=0、KWD exponent=3（实测 D）。存 2 位：JPY 每笔多出永恒的 `.00`（对账口径错），KWD 丢掉第三位（1 费尔 = 千分之一第纳尔，百万第纳尔级流水就是 1000 第纳尔的系统误差）。正解：`int64` 最小单位 + 币种 exponent，或 `numeric(19,4)`；展示位按 CLDR（JPY=0、KWD=3）。

**Q3** 账单每行 33.33 元、税率 9.5%，逐行舍入与合计后舍入差多少？100 万单一年差多少？

▸ 答案：实测 A3 差 1 分/单（逐行 634 分 vs 合计 633 分）；100 万单 = 1 万元/年。规则是「合计优先」：行项目存精确值，合计处舍一次；残差分摊用最大余数法，`sum==total` 作为单测。

**Q4** 同源三角换算与跨源三角换算，误差差多少？为什么？

▸ 答案：同源 0.0000 bps（ECB 内部 USD→CNY→JPY 与直接 USD/JPY 完全相等，都从 EUR 推导）；跨源 −47.96 bps，同日两源直接对比 +69.67 bps（实测 B2）。三角公式本身不产生误差，误差来自两条腿的数据源与时间戳不同。

**Q5** 同一笔 100 万 JPY 订单，周五和周一结算，USD 收入差多少？该用哪天汇率？

▸ 答案：周五 USD/JPY=159.998190 → 6250.0707 USD；周一 159.596877 → 6265.7868 USD，差 15.7161 USD（25.08 bps，实测 B4）。用订单锁价时的 `quote_id` 快照，不是结算当天汇率，更不是「今天重算」；ECB 周末不更新，周五的 as_of 会一直挂到周一。
