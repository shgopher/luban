# 72.4 多地域部署与就近接入

## 一句话

> 就近接入是 **入口选路 × 部署单元 × 数据驻留** 三件事的乘积，不是"把服务部署到多个地域"；本机实测：同一域名同一时刻，7 个不同客户端子网被 ECS 调度到哈尔滨/上海/广州/济南/北京/新加坡 6 个城市的节点（2 个子网共享广州节点），本机不带 ECS 时落到同省郑州节点、建连 p50 **8.3 ms**，而经 1.1.1.1 解析落到西雅图节点、p50 **198.3 ms**（**23.9 倍**）——选路选错，后面所有加速都优化在了错误的目的地上。

## 三个误区

| 误区 | 现实 |
|---|---|
| 上了 CDN / Anycast 就自动"就近" | Anycast 按 **BGP 路径**选（RFC 4786），GeoDNS 按 **解析器位置**选，都不等于用户地理位置；实测同一台机器换解析器：本地 AliDNS 返回郑州节点（建连 p50 8.3 ms），1.1.1.1 返回西雅图节点（p50 198.3 ms），差 23.9 倍 |
| 多地域部署 = 多活 | 多地域只回答"副本放了几份"；多活要回答"本地能不能写、故障怎么切"，那是 [36.4 两地三中心与多活](../../L3-质量属性/36-灾备/36.4-两地三中心与多活.md) 与 [36.5 单元化 / Set 化架构](../../L3-质量属性/36-灾备/36.5-单元化-Set化架构.md) 的主场。本节只管**入口**与**部署单元**，写路径见 [72.5 跨地域读写与一致性](72.5-跨地域读写与一致性.md) |
| GeoDNS 切流是秒级操作 | 切流时间 = **DNS TTL + 递归/客户端缓存 + 连接 draining**；本机实测 A 记录剩余 TTL：淘宝 14 s、Apple 25 s、京东 32 s、B 站 68 s，最坏到分钟级；把"改一条 DNS"当成"已切完"是事故起点 |

## 先分清三个"地域"

"地域"在架构讨论里混着指三样东西，混着说就会把"部署"当成"接入"。

| 概念 | 回答什么 | 谁负责 | 典型错误 |
|---|---|---|---|
| **地理地域** | 用户/数据在法律与物理上属于哪里 | 业务 + 合规 | 用 IP 归属判断用户国籍 |
| **云 Region / AZ** | 资源放在哪个故障域、离用户多远 | 基础设施（[5.3 地域与可用区](../../L0-运行时底座/5-云计算基础/5.3-地域与可用区.md) 主场） | 把 Region 当"机房"，忽略 AZ 内共享依赖 |
| **部署单元（cell / unit）** | 一个能独立服务闭环的最小复制单位 | 架构 | 单元里留了跨区数据库，故障时一起挂 |

> 🔑 就近接入优化的是"用户 → 入口"这一段；部署单元决定"入口 → 数据"这一段。两段必须分别度量，否则会出现"入口 20 ms、进站后查库 150 ms"的假就近。

## 入口层：四种就近接入手段

| 手段 | 选路依据 | 粒度 | 生效时间 | 成本 | 主要坑 |
|---|---|---|---|---|---|
| **GeoDNS / GSLB** | 解析器 IP，或 ECS 携带的客户端子网 | 国家/省/运营商/自定义线路 | TTL 级别（实测 14–68 s） | 低（一个 DNS 产品） | 解析器位置偏差；本地 DNS 缓存；负缓存 |
| **Anycast** | BGP 路由度量（AS 路径、IGP 开销） | 路由可达的 POP | BGP 收敛（秒级） | 高（要自己的 AS + 多 POP） | 不保证地理最近；状态同步难；DDoS 会集中到一个 POP |
| **HTTP 302 / 应用层重定向** | 服务端实时判断（IP 库、用户归属） | 用户 | 立即 | 低 | 多 1 次 RTT + TLS 重建；跨区时 1 次 RTT 就是 84 ms（实测 72.5 的 84 ms 链路） |
| **客户端多端点竞速** | 客户端实测连接时延（Happy Eyeballs，RFC 8305） | 连接 | 立即 | 中（要发 SDK） | 首次启动慢；要处理"选到坏端点"的退避 |

### GeoDNS / GSLB：按"解析器位置"选，不是按"用户位置"选

DNS 服务器只看得见"谁在问"，也就是递归解析器的 IP；只有解析器支持 **EDNS Client Subnet（ECS）** 时，DNS 才能看到用户的真实子网。AWS Route 53 文档明确写了这条回退链：支持 ECS 时按客户端子网定位，**不支持时退回按解析器源 IP 粗估**（[Route 53 与 EDNS0](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-edns0.html)）。

实测 A（见本节「实测 A：同一域名、7 个客户端子网 → 6 个城市节点」）用 AliDNS 223.5.5.5 对同一域名带不同 ECS 子网查询，7 个子网落到 6 个城市的节点（113.108 与 218.30 两个子网共享广州节点）；同一台机器不用 ECS 查询时，返回的是本省（郑州）节点。**"就近"是按解析器/子网算出来的近似，不是精确地理。**

### Anycast：按路由选，近是结果不是目标

Anycast 把同一个 IP 宣告在多个 POP，BGP 把包送到"路由最优"的那个。RFC 4786 描述的就是这套运营方式：它带来两个真好处——**收敛快**（撤销一条路由，秒级把流量引走）与**抗 DDoS**（攻击被分散到多个 POP）；也有三个硬限制：

1. **不保证地理最近**：路由度量是 AS 路径与策略，不是公里数；跨国流量可能绕到邻国 POP。
2. **状态必须外部化**：一个 TCP 连接落到哪个 POP 不确定，会话状态不能只存在本地（引 [9.6 边缘计算模型](../../L0-运行时底座/9-CDN与边缘/9.6-边缘计算模型.md) 的"无状态"约束）。
3. **故障会"吸"流量**：一个 POP 挂掉，BGP 撤销后流量会集中到剩余 POP，容量必须按"少一个 POP"设计。

**未验证**：Anycast 的选路差异需要多个 AS 的观测点；本机只有一个出口（河南联通 AS4837），无法验证"不同运营商落到不同 POP"，只引用 RFC 4786 与产品文档的机制说明。

### 实测 A：同一域名、7 个客户端子网 → 6 个城市节点

环境：macOS arm64 / Apple 芯片 / 2026-11-21；本机位于河南洛阳（ipinfo：AS4837 中国联通）；查询对象 `www.taobao.com`，递归 `223.5.5.5`，带 `+subnet`；节点定位用 ipinfo 反查返回 IP。

```bash

curl -s https://ipinfo.io/<返回的IP>/json
```

### 实测 B：解析器位置偏差 → 建连差 23.9 倍

同一台机器、同一域名、1 分钟内：

| 解析方式 | 返回 IP | ipinfo 定位 | TCP 建连 p50（10 次） |
|---|---|---|---|
| 本地 ISP / AliDNS | 123.6.66.107 | 郑州 | **8.3 ms**（min 6.96 / max 11.27） |
| `@1.1.1.1` 解析 | 8.45.176.177 | **Seattle, US** | **198.3 ms**（min 171 / max 455） |

原始输出：`.cache/ch72/s7204/raw/c-rtt-probe.txt`。这是本节最贵的一条教训：**"用户用了哪个 DNS"直接决定他连到哪个大洲**；只看 CDN 覆盖率、不看解析器分布，就近接入就是抽奖。

### 实测 C：DNS TTL 决定切流下限

```bash
dig +time=3 +tries=1 @223.5.5.5 www.taobao.com A +noall +answer
```

原样输出（`.cache/ch72/s7204/raw/e-ttl-jitter.txt`，记录的是缓存**剩余** TTL，配置值只会更大）：

```text
www.taobao.com.         498  IN CNAME www.taobao.com.danuoyi.tbcache.com.
www.taobao.com.danuoyi.tbcache.com.  14 IN A 123.6.66.106
www.jd.com.s.galileo.jcloud-cdn.com. 32 IN A 123.6.77.65
a.w.bilicdn1.com.                    68 IN A 116.163.15.199
www.apple.com.w.cdngslb.com.         25 IN A 123.6.141.135
```

| 域名 | A 记录剩余 TTL | 切流最坏等待（按 TTL 计） |
|---|---|---|
| 淘宝 | 14 s | ≥14 s（还没算递归与客户端缓存） |
| Apple | 25 s | ≥25 s |
| 京东 | 32 s | ≥32 s |
| B 站 | 68 s | ≥68 s |

> 🔑 切流时间 = **TTL × 层数（CNAME 链）+ 递归/客户端缓存 + 连接 draining**。要 30 秒内切完，TTL 必须提前 5–10 分钟调小（让旧 TTL 先过期），否则"改了解析"只是"开始传播"。

## 部署单元：把"地域"做成可复制的最小单元

### 三种部署形态

| 形态 | 做法 | 写能力 | 故障域 | 成本 | 适用 |
|---|---|---|---|---|---|
| **全对称** | 每个 region 一套完整服务 + 完整数据副本 | 每区可写（需冲突方案） | 单区/单 AZ | 最高：N 倍容量 + 跨区流量 | 全球化 To C、写入按用户归属分区 |
| **全局控制面 + 区域数据面** | 配置/账号/计费在中心，业务与数据在区域 | 仅归属区可写 | 中心故障影响管理面 | 中 | SaaS、有明确归属的数据 |
| **中心 - 边缘** | 中心一套主库，边缘只放无状态与缓存 | 只能写中心 | 中心是单点 | 最低 | 读多写少、能接受回源延迟 |

### 一个 region 单元的必备件

| 组件 | 缺了会怎样 |
|---|---|
| 无状态服务副本 | 只能跨区调用，入口就近也白搭 |
| 区域缓存（本地/区域 Redis） | 缓存穿透到中心，跨区流量与延迟双涨 |
| 区域数据副本（或归属分区） | 每个请求都要跨区，RTT 直接进 P99 |
| 区域配置副本（[48 配置与协调](../48-配置与协调/0-概论.md) 主场） | 中心配置抖动 → 所有区一起抖动 |
| 区域观测（日志/指标/链路，[50 可观测性](../50-可观测性/0-概论.md) 主场） | 出故障时只能看到"别的区"的视角 |
| 区域限流/熔断 | 一个区被打爆，流量顺着共享依赖传染到全区 |

> 🔑 **共享依赖 = 故障传播路径**。单元里每留一个"大家都要用"的东西（中心数据库、全局锁、单点配置、同一个第三方支付），就多一条"拔网线测试"会失败的路径——判据仍是 [36.5 单元化 / Set 化架构](../../L3-质量属性/36-灾备/36.5-单元化-Set化架构.md) 的那条：**拔掉一个单元，其余单元不应有任何一条请求变慢**。

### 数据驻留：把法律约束变成路由约束

数据出境是合规问题（[3.3 数据出境与数据主权](../../需求/3-行业合规与外部约束/3.3-数据出境与数据主权.md) 主场），落到架构上就是一条**不可变归属**：`user → home_region` 由注册地/合同决定，不是由负载均衡决定。

| 流量类型 | 路由规则 | 失败时 |
|---|---|---|
| 本地用户访问本地数据 | 就近入口 → 归属 region | 归属区故障：按 RPO/RTO 切灾备区（[36.4](../../L3-质量属性/36-灾备/36.4-两地三中心与多活.md)、[36.6](../../L3-质量属性/36-灾备/36.6-切换时的数据一致性.md)） |
| 跨境用户访问归属地数据 | 入口就近，但**数据回归属区**（只读/代理） | 降级为"只读 + 提示"，不跨境写 |
| 内部服务跨区调用 | 只允许白名单接口 + 出站审计 | 熔断回本地缓存 |

**与 36.5 路由表的区别**：36.5 的 `uid → cell` 路由表解决负载、隔离、扩容，键是哈希/关系聚类；这里的 `user → home_region` 解决合规与入口，键是**注册地/合同**，变更要走数据迁移流程而不是 rehash。两者可以是同一套路由中间件，但**表与变更权限必须分开**。

## 如何度量"就近"是否真的生效

| 指标 | 口径 | 为什么必须看它 |
|---|---|---|
| 入口 RTT P95（分地域/运营商） | RUM 或合成拨测 | 平均值会把"20% 用户绕到海外"藏起来 |
| 跨区回源比例 | 跨区请求数 ÷ 总请求数 | 入口就近但数据跨区，等于没就近 |
| DNS 解析地理分布 | 按解析器 IP/ECS 子网统计 | 发现"一批用户用了不支持 ECS 的解析器" |
| 切流耗时 | 从下发到 P95 恢复 | 决定 RTO 的真实值 |
| 跨区流量（GB/天） | 云账单 + 链路监控 | 全对称部署的隐性成本主项 |

本机实测的公网建连梯度（每次 5 轮取 p50，详见 `.cache/ch72/s7204/raw/d-public-rtt.txt`）：

| 目标 | 解析 IP 归属 | 建连 p50 | 说明 |
|---|---|---|---|
| www.apple.com | 郑州 CDN | 11.6 ms | 同省边缘节点 |
| www.163.com | 郑州 | 15.7 ms | 同上 |
| www.qq.com | 郑州 | 24.4 ms | 同上 |
| www.baidu.com | 郑州 | 24.3 ms | 同上 |
| www.jd.com | 郑州 | 11.4 ms | 同上 |
| www.amazon.com | CloudFront | 80.5 ms | 海外/跨境 CDN |
| sgp1.digitaloceanspaces.com | 新加坡 | 387 ms | 公网跨境，路径绕行 |
| www.microsoft.com | Akamai | 422 ms | 跨境 CDN，落点远 |

ping 抖动对照：百度（国内）15 包 **21.7 ms ± 0.8 ms**，微软（海外 Akamai）15 包 **226.2 ms ± 0.6 ms**——**高延迟不等于高抖动**；抖动小但延迟高，说明路径稳定但绕得远，这类问题换协议、加连接复用都救不回来，只能换落点。

## 实测 D：入口层按地域路由（nginx geo + fail-open）

生产里"地域路由"通常由 GSLB 完成，但入口层（nginx/Envoy）也要能按地域做兜底与灰度。下面是本机真跑过的配置（alpine 3.20 / nginx 1.26.3）：

```nginx
worker_processes 1;
events { worker_connections 256; }
http {
  log_format main '$remote_addr geo=$geo_region up=$upstream_addr status=$status rt=$request_time';
  access_log /dev/stdout main;

  # 三个“区域入口”后端，用端口模拟；生产中是各地域 LB 的 VIP
  server { listen 18081; location / { return 200 "backend=cn-north\n"; } }
  server { listen 18082; location / { return 200 "backend=cn-east\n"; } }
  server { listen 18083; location / { return 200 "backend=global\n"; } }

  # 生产由四层 LB / CDN 注入 X-Forwarded-For；此处信任全部来源仅用于实验
  set_real_ip_from 0.0.0.0/0;
  real_ip_header X-Forwarded-For;

  # 生产用 GeoIP2 库或云厂商地域库；此处用固定网段模拟
  geo $geo_region {
    default   global;
    1.2.3.0/24 cn-north;
    5.6.7.0/24 cn-east;
  }
  # 关键：默认落到 global，任何未命中/库缺失的请求仍可服务（fail-open）
  map $geo_region $backend_port {
    default  18083;
    cn-north 18081;
    cn-east  18082;
  }

  server {
    listen 8080;
    location / {
      proxy_pass http://127.0.0.1:$backend_port;
      proxy_connect_timeout 50ms;
      proxy_next_upstream error timeout;
    }
  }
}
```

```bash
# 可抄：alpine 里装 nginx 再覆盖配置（先装再覆盖，避免 apk 与挂载文件冲突）
docker run -d --name nginx72 -p 18090:8080 alpine:3.20 sleep 3600
docker exec nginx72 sh -c 'apk add --no-cache nginx'
docker cp nginx.conf nginx72:/etc/nginx/nginx.conf
docker exec nginx72 nginx -t          # 先验证语法，再启动
docker exec nginx72 nginx
# 验证（XFF 模拟不同地域客户端）
for ip in 1.2.3.4 5.6.7.8 8.8.8.8 114.114.114.114; do
  printf "%-16s " $ip; curl -s -H "X-Forwarded-For: $ip" http://127.0.0.1:18090/; done
```

原样输出（`.cache/ch72/s7204/raw/f-nginx-geo.txt`）：

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
XFF=1.2.3.4          -> backend=cn-north
XFF=5.6.7.8          -> backend=cn-east
XFF=8.8.8.8          -> backend=global
XFF=114.114.114.114  -> backend=global
```

> 🔑 入口层地域路由必须**默认落到 global**：GeoIP 库过期、内网 IP、未知运营商都会 miss。把"命中不了就 502"当成严格是错的方向——入口层的第一职责是"还能服务"。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**

| 层 | 产品 | 关键能力 |
|---|---|---|
| DNS / GSLB | 阿里云云解析 DNS + 全局流量管理 GTM、AWS Route 53 | 线路/地域解析、健康检查、故障切换、权重；Route 53 支持 ECS（[edns0 说明](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-edns0.html)），GTM 支持"来源就近"策略与地址池健康检查（[GTM 产品简介](https://help.aliyun.com/zh/dns/gtm3-product-introduction)） |
| Anycast | Cloudflare / Akamai / 自建 BGP | 同一 IP 多 POP 宣告、DDoS 分散、BGP 秒级收敛（机制见 RFC 4786） |
| 入口层 | nginx / Envoy | 按地域/运营商做灰度、fail-open、连接 draining |

**可抄**：探测"就近是否生效"的两条命令（不需要改生产配置）：

```bash
# ① 用 ECS 模拟不同地域用户，看 GSLB 返回哪个节点（只有支持 ECS 的递归才有效）
dig +short @223.5.5.5 +subnet=116.228.0.0/16 www.example.com A

# ② 直接测到候选节点的 TCP 建连，比"ping 域名"更接近真实体验
curl -s -o /dev/null -w 'connect=%{time_connect} total=%{time_total}\n' https://www.example.com/
```

**可验**（本机真跑）：

| 检查项 | 期望值 | 原始输出 |
|---|---|---|
| 7 个 ECS 子网 → 不同节点 | 哈尔滨/上海/广州/济南/北京/新加坡 6 城（无 ECS 时本机为郑州） | `b-ecs-matrix.txt`、`g-ipgeo.txt` |
| 解析器位置偏差 | 本地节点 8.3 ms vs 海外节点 198.3 ms（23.9 倍） | `c-rtt-probe.txt` |
| TTL 实测 | 14/25/32/68 s | `e-ttl-jitter.txt` |
| nginx 地域路由 | 4 条 XFF 分别落到 cn-north / cn-east / global / global | `f-nginx-geo.txt` |

**可退**（每个开关都要能在线切）

| 退路 | 做法 | 代价 |
|---|---|---|
| 地域路由出错 | `map` 的 `default` 改回 global（一行配置） | 失去就近，但全量可服务 |
| GSLB 线路故障 | 地址池权重切 0 / 暂停地址池，走默认线路 | 部分用户延迟上升 |
| DNS 切流回滚 | 提前把 TTL 调到 30–60 s，回滚时同样等 2×TTL 再宣布完成 | 切流窗口变长 |
| 客户端竞速误选 | 下发配置固定 endpoint，关闭竞速 | 失去多径容错 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 只按"CDN 覆盖率"验收就近接入 | 实测同一用户换解析器，建连从 8.3 ms 变 198.3 ms（23.9 倍），覆盖率报表看不出来 |
| 把 TTL 设成 3600 s 还承诺"分钟级切流" | 切流下限被拉到 1 小时；实测常见 CDN 域名 TTL 就有 14–68 s |
| 入口层 geo 命中不了直接 502 | GeoIP 库过期/内网 IP 会打挂一批用户；必须 fail-open 到 global |
| 每个 region 都放完整主库且都接受写 | 冲突处理成本转移给业务（资金/库存不接受 LWW，[36.6](../../L3-质量属性/36-灾备/36.6-切换时的数据一致性.md) 已验证），跨区写延迟 84 ms 起 |
| 用 IP 归属判断用户国籍/数据归属 | 代理、企业出口、跨境漫游都会错；归属应由注册地/合同决定 |
| 全对称部署但容量按"总量 ÷ N"算 | 少一个 region 就过载；每区容量要按"峰值 × 冗余"独立算（[39.2 容量规划](../../L3-质量属性/39-成本/39.2-容量规划.md)） |
| 只做入口就近，数据仍在中心 | 用户到入口 15 ms，入口回源 84 ms，P99 反而更差 |

## 三条铁律

> 🔑 **就近接入先修"入口选路"，再谈"多地域部署"。** 入口选错，跨大洲 198 ms；入口选对，同省 8 ms——这 23.9 倍不是任何应用层优化能补回来的。

> 🔑 **切流时间由 TTL 决定，不由机房数量决定。** 实测 CDN TTL 14–68 s，加上递归与客户端缓存，分钟级是常态；RTO 承诺必须先把 TTL 调小，再谈切换演练。

> 🔑 **数据驻留把"用户归属 region"变成不可变属性。** 它让路由表成为合规单点：表错 = 数据出境；迁移要走数据搬迁流程，不能 rehash。

## 自检

**Q1** 用户反馈"海外访问慢"，但监控显示 CDN 命中率 95%、回源正常。你先查什么？

▸ 答案：先查**解析器位置**。命中率高只说明"缓存命中"，不说明"落点对"：实测同一用户经 1.1.1.1 解析落到西雅图节点，建连 198.3 ms；经本地 DNS 落到郑州节点，8.3 ms。查 RUM 的入口 RTT 按解析器/AS 维度拆分，再看 GSLB 是否对这批解析器返回了错误线路；不要先加带宽。

**Q2** 为什么 nginx 的 `geo` 路由默认一定要落到 global，而不是返回 404/502？

▸ 答案：`geo` 的输入是 IP 库与 XFF，内网 IP、未知 ASN、库过期都会 miss。入口层的第一职责是"服务不中断"，miss 时回 global 最多多花几十毫秒，返回 502 则是一批用户直接不可用。本机 4 条测试里 8.8.8.8 与 114.114.114.114 都按 default 落到 global，这就是 fail-open 的行为。

**Q3** 把 DNS 记录的 TTL 从 60 s 改成 5 s，为什么"切流变快"还要等一会儿才生效？

▸ 答案：TTL 是"缓存多久"的指令，不是"立刻刷新"。已经缓存了旧记录的递归/客户端会继续用到旧 TTL 到期；所以正确做法是**提前一个旧 TTL 周期**把 TTL 调小，等旧缓存自然过期，再切记录。否则切流时间 = 旧 TTL + 新记录传播时间。

**Q4** Anycast 已经"就近"了，为什么还要 GeoDNS？

▸ 答案：Anycast 的"近"是 BGP 路由度量意义下的近，按 AS 路径与策略选，可能绕到邻国；而且它无法表达"这个用户的数据必须在某个 region"这类合规约束。GeoDNS/GSLB 能按线路、地域、权重精确编排，也方便做灰度与回滚；两者通常叠加：Anycast 选入口 POP，GSLB/入口层再决定 region。

**Q5** 一个 region 的部署单元里，哪些组件"缺了就等于没做多地域"？

▸ 答案：缺**区域数据副本/归属分区**最致命——入口就近了，但每个请求都回中心查库，RTT 84 ms 直接进 P99；其次是区域配置与观测，缺了会在故障时"所有区一起抖"且看不到本地视角。判据用 36.5 的拔网线测试：拔掉一个单元，其余单元不能有任何一条请求变慢。
