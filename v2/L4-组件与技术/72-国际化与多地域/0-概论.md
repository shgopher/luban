# 第 72 章 国际化与多地域 · 概论

## 一句话

> 国际化与多地域不是「翻译 + 加机房」，而是把四条隐性假设——**语言、时区、币种、地域**——从代码的默认值里拽出来，变成「内部标准表示 + 边界转换 + 版本化 + 可回退」；五节各管一条边界，任何一条留在默认值里，都会以「差 8 小时 / 少 1 分钱 / 慢 190 ms / 读到旧值」的形式在线上潜伏很久。

## 5 分钟入门：先记住这 8 个词

| 词 | 一句话解释 | 生活类比 |
|---|---|---|
| **locale（BCP 47）** | `语言-文字-地区` 四段标识，如 `zh-Hans-CN`、`sr-Latn-RS` | 地址要写到「省-市-区」，只写国家会送错 |
| **CLDR 复数类** | 名词变格不是「加 s」，而是 zero/one/two/few/many/other 六类，按语言组合 | 不同语言数数的手势不一样，不能照搬 |
| **字素（grapheme）** | 用户眼里的一个「字」；一个 ZWJ 家庭 emoji 是 25 字节 / 7 rune / **1 字素** | 拼装家具按「件」算，不按螺丝数算 |
| **instant（时间点）** | 时间轴上唯一的一瞬，存 UTC，与时区无关 | 全球只有一条时间轴，钟面是投影 |
| **IANA zone id + DST** | `America/New_York` 这种带规则的时区名；夏令时会产生 23 h/25 h 的天 | 同一块表，夏天要手动拨快一小时 |
| **最小货币单位（exponent）** | 金额存整数：CNY 分（2 位）、JPY 元（0 位）、KWD 费尔（3 位） | 数钱按「分」数，不按「元的小数」数 |
| **as_of（汇率时点）** | 汇率不是数字，是「带时间戳与来源的价格」 | 昨天的菜价不能拿来结今天的账 |
| **home_region（数据归属）** | 用户/数据在法律上属于哪个地域，由注册地/合同决定，不可 rehash | 户口所在地，不是当前所在地 |

## 一张图：这章的骨架

```
用户（某地、某语言、某币种、受某地法律管辖）
   │  72.1：文案/格式/排序按 locale 渲染；长度按字素与显示格算
   │  72.2：时刻存 UTC；展示与日切按 IANA zone；DST 要显式处理
   ▼
请求入口 ──72.4：就近接入（ECS/GeoDNS/Anycast）+ 部署单元 + 数据驻留
   │
   ▼
业务与数据 ──72.3：金额 = 整数最小单位 + 币种 + 汇率 as_of
   │
   ▼
跨地域读写 ──72.5：写路径按冲突后果、读路径按允许多旧；RTT 是硬下界
```

- 竖看是**一条请求的生命周期**：语言在展示边界、时区在时间语义、币种在金额边界、地域在入口与数据归属。
- 横看是**一个统一纪律**：每条边界都要求「内部只有一种标准表示，转换只发生在边界一次，而且可版本化、可回退」。

## 本章要解决的 8 个真问题

| 问题 | 在哪一节 | 一句话答案 |
|---|---|---|
| 同一个页面，中文和阿拉伯语布局都崩 | [72.1](72.1-多语言与本地化.md) | 长度按字节/rune 算会切碎字素、低估 CJK 宽度；伪本地化实测字节膨胀 +48.39%、rune 只 +12.90% |
| 用户报「时间差 8 小时」，改前端还是后端 | [72.2](72.2-多时区处理.md) | 先查存的是 instant 还是墙钟字符串：同一条字面量在三个 session 时区插入 PG 得到 09:00Z/14:00Z/01:00Z 三个瞬时 |
| 按天统计的日报为什么少/多 1 小时 | [72.2](72.2-多时区处理.md) | 一天不总是 24 h：6 个时区 2026 年有 10 个非 24h 天（23/23.5/24.5/25h） |
| 同一个 1.005 元，两个服务算出两个结果 | [72.3](72.3-多币种与汇率.md) | 浮点 + 实现相关舍入；金额必须用整数最小单位或 decimal，舍入只在对外出具处做一次 |
| 多币种订单该用哪天的汇率 | [72.3](72.3-多币种与汇率.md) | 用下单时的 `as_of` 快照；同一笔 100 万 JPY 跨周末差 15.7161 USD（25.08 bps） |
| 海外访问慢，但 CDN 命中率 95% | [72.4](72.4-多地域部署与就近接入.md) | 命中率不说明落点对：换解析器后建连从 8.3 ms 变 198.3 ms（23.9 倍） |
| 「写完立刻读」为什么读到旧值 | [72.5](72.5-跨地域读写与一致性.md) | 异步复制有陈旧窗口：84 ms RTT 下窗口 p50 42.9 ms；监控的 `replay_lag` 86.55 ms 约为其 2 倍 |
| 多地域部署了，P99 还是 200 ms | [72.4](72.4-多地域部署与就近接入.md)、[72.5](72.5-跨地域读写与一致性.md) | 入口对了、数据还在中心：跨区点查 85.71–89.99 ms；入口与数据必须一起就近 |

## 3 个最常见误解

| 误区 | 现实 |
|---|---|
| 「国际化 = 翻译」 | 翻译只占四分之一：**语言（含格式/排序/长度）、时区、币种、地域**四条边界各有自己的正确性约束；翻译错的代价是体验，另外三条错的代价是资损、合规与数据错乱 |
| 「多地域部署 = 多活」 | 部署只回答「副本几份」，就近接入回答「用户连到哪」，多活回答「本地能不能写、故障怎么切」；后两者分别是 [72.4](72.4-多地域部署与就近接入.md) 与 [36.4](../../L3-质量属性/36-灾备/36.4-两地三中心与多活.md)、[36.5](../../L3-质量属性/36-灾备/36.5-单元化-Set化架构.md) 的主场 |
| 「内部统一用 UTC / 人民币 / 英文就没事」 | 统一表示是必要条件不是充分条件；还缺**边界转换（locale/zone/FX 快照）、版本化（tzdata/文案包/汇率）、可回退（灰度开关）**——本机实测 tzdata 三个版本在同一批瞬时上有 5/10/5 个时区名的偏移差异 |

## 读完自检（入门级 3 题）

**Q1** 一个系统同时有北京时间用户、纽约用户和东京用户，数据库里应该存什么？展示层怎么处理？

▸ 答案：所有"发生过的事件"存 **instant（UTC 或等价的时间戳）**，另存用户/业务的 **IANA zone id** 用于展示与业务日切；绝不存"本地时间字符串"。因为同一句话在三个时区差 13–14 小时，跨区对账与排序都会错（详见 [72.2 多时区处理](72.2-多时区处理.md)）。

**Q2** 上线一个支持 12 种语言的页面，最容易被低估的成本是什么？

▸ 答案：不是翻译费，是**布局与长度的返工**：伪本地化实测字节膨胀 +48.39%，一个 emoji 有 25 字节/7 rune/1 字素三种口径；如果 UI 与数据库列按字节或 rune 限长，德语/芬兰语会溢出、CJK 会低估宽度（详见 [72.1 多语言与本地化](72.1-多语言与本地化.md)）。

**Q3** 用户在日本、数据在新加坡、服务部署在东京，访问一次「我的订单」要跨几次区？延迟下限是多少？

▸ 答案：入口一次（用户→东京，约 10–30 ms），数据一次（东京→新加坡约 5 300 km，光纤 RTT 下限约 53 ms；实验用 84 ms 链路，实测点查 85.71–89.99 ms）；如果还要回源写，再加一次 RTT。要把"必须跨区"的请求数量压到最小，而不是指望中间件把它变快（详见 [72.4](72.4-多地域部署与就近接入.md) 与 [72.5](72.5-跨地域读写与一致性.md)）。
