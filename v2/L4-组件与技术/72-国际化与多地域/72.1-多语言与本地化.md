# 72.1 多语言与本地化

## 一句话

> 多语言不是「把文案翻一遍」，而是把语言假设显式化：locale 用 BCP 47 四段表示、句子整句交给 ICU MessageFormat、长度按字素与显示格管理——这 18 个真实 Accept-Language 头归一化后只落到 9 个内容 locale，伪本地化让字节膨胀 **+48.39%** 而 rune 只涨 **+12.90%**，一个 ZWJ 家庭 emoji 同时是 **25 字节 / 7 rune / 1 字素**。

## 三个误区

| 误区 | 现实 |
|---|---|
| locale 写成 `zh-CN` 就够，反正中文只有一种 | `zh` 缺 script 是内容分叉点：简繁不是地区是文字。实测 `zh-Hant-HK` 命中 `zh-Hant`、`sr-Cyrl-RS` 却落到 `sr-Latn`——只按语言匹配会把西里尔用户送进拉丁文案 |
| 复数就是「n > 1 加 s」 | CLDR 有 6 类（zero/one/two/few/many/other），阿拉伯语 6 类全用、俄语 4 类。实测 `0` 在英语是 `other`（`0 files` 不是 `0 file`），`21` 在俄语是 `one`、`11` 是 `many`，「大于 1」一条都判不对 |
| 字符串长度 = 字符数，按它限死数据库列和按钮宽度 | 长度有四种口径：一个 ZWJ 家庭 emoji 是 25 字节、7 rune、1 字素、2 显示格；中文 11 rune 占 22 格。按字节截断会切碎 emoji，按 rune 限制会低估中文宽度 |

## locale 标识：四段式，漏一段就多一个事故

BCP 47（RFC 5646）的 tag 是 `语言[-文字][-地区][-变体]`，文字段才是「简繁/拉丁 vs 西里尔」的真正开关。

| tag | 语言 | 文字 | 地区 | 为什么不能退化成两段 |
|---|---|---|---|---|
| `zh-Hans-CN` | zh | Hans | CN | 简体内容包；中国大陆用词 |
| `zh-Hant-HK` | zh | Hant | HK | 繁体内容包；香港用词（「軟件」vs 台湾「軟體」） |
| `sr-Latn-RS` | sr | Latn | RS | 塞尔维亚语拉丁字母；`sr-Cyrl-RS` 是另一套文字 |
| `es-419` | es | — | 419（UN M.49 拉美） | 一个地区码覆盖拉美多国，没有单一国家码可用 |

**内容包按「语言-文字」建，地区只影响格式与用词**。`zh-CN` 这种两段式在协商时能靠 likely subtags 补出 `Hans`，但它不是内容包的身份：把 `zh-CN` 当繁简判据，台湾用户会拿到简体；把 `zh-TW` 当唯一繁体键，香港用户就无包可用。协商链路固定五步：解析 `Accept-Language` → 按 q 排序 → 在服务端支持列表里匹配 → 得到内容包 → 逐级 fallback（`zh-Hant-CN → zh-Hant → zh → en`）。

```go
// 内容包 fallback：命名只允许「语言[-文字]」，地区不进包名；否则 9 个包炸成 12+ 个键。
func fallbackChain(t language.Tag) []string {
	base, _ := t.Base()
	script, sc := t.Script() // 只有显式文字段才算数
	out := []string{t.String()}
	if sc == language.Exact {
		out = append(out, base.String()+"-"+script.String())
	}
	return append(out, base.String(), "en") // 最后一定落到默认语言
}
```

实测 A 暴露四个协商细节，全部来自 `language.MatchStrings` 的真实行为：

| 输入头 | 行为 | 架构含义 |
|---|---|---|
| `en-US;q=0,fr;q=0.9` | `ParseAcceptLanguage` 直接把 `en-US` 剔除，匹配 `fr` | `q=0` 是「明确拒绝」，不是「权重最低」，别自己实现成排序 |
| `*` | 解析成 `mul`，匹配默认 `en` | 通配是兜底不是随机；默认语言必须显式配置 |
| `xx-YY` / `;;;` / `q=abc` | 解析失败，**静默**落到默认 `en` | 3/18 个非法头全部无声兜底，必须打日志与计数 |
| `sr-Cyrl-RS` | 匹配到 `sr-Latn`（因为只提供了拉丁包） | 语言对、文字错同样是事故；script 要显式检查 |

## 复数：六类，不是两类

CLDR 的基数词类别最多 6 个：`zero / one / two / few / many / other`。实测 B 的矩阵（Go `x/text/feature/plural` 与 Node `Intl.PluralRules` 逐格一致 90/90）：

| 语言 | zero | one | two | few | many | other |
|---|---|---|---|---|---|---|
| en | — | 1 | — | — | — | 0,2,3,5,11,21,100,1.5 |
| zh / ja | — | — | — | — | — | 全部数字（没有复数变化） |
| ru / uk | — | 1,21 | — | 2,3 | 0,5,11,100 | 1.5 |
| pl | — | 1 | — | 2,3 | 0,5,11,21,100 | 1.5 |
| ar | 0 | 1 | 2 | 3,5 | 11,21 | 100,1.5 |
| fr | — | 0,1,1.5 | — | — | — | 2,3,5,11,21,100 |
| cs | — | 1 | — | 2,3 | 1.5 | 0,5,11,21,100 |

「n > 1 加 s」在五处直接翻车：**英语 0 也是 other**（`0 files`）；**俄语 2 与 5 不同格**（`2 файла` vs `5 файлов`）；**阿拉伯语有双数**（`2` 是 two，`3..10` 是 few，`11..99` 是 many）；**小数不走整数规则**（法语 `1.5`=one、俄语 `1.5`=other、捷克语 `1.5`=many）；**中文没有复数但有量词与语序**（`删除 1 个文件`）。

CLDR 规则按 5 个操作数判定：`i`（整数位）、`v`（可见小数位）、`w`（去尾零小数位）、`f`/`t`（小数位值）。这解释了为什么「1」和「1.0」在部分语言里类别不同。**API 必须传操作数，不能只传 float。**

```go
// 整句翻译：句子是翻译单元，占位符只传值。反例："You have " + n + " files"。
form := plural.Cardinal.MatchPlural(language.MustParse("ru"), 5, 0, 0, 0, 0) // 5 файлов -> many
```

## 数字、日期、排序：都是展示边界的活

实测 C（同一数值、同一时刻，Node ICU 74.2 / CLDR 44.1）：

| locale | `1234567.891` | 日期（2026-11-21） | 备注 |
|---|---|---|---|
| en-US | `1,234,567.891` | `11/21/26` | 月/日/年 |
| de-DE | `1.234.567,891` | `21.11.26` | 分组与小数点互换 |
| fr-FR | `1 234 567,891` | `21/11/2026` | 分组符是 U+202F 窄不换行空格 |
| en-IN | `12,34,567.891` | `21/11/26` | 分组不是 3 位：2-2-3（lakh/crore） |
| ar-EG | `١٬٢٣٤٬٥٦٧٫٨٩١` | `٢١‏/١١‏/٢٠٢٦` | 阿拉伯-印度数字 + RTL 标记 |
| ja-JP | `1,234,567.891` | `2026/11/21` | 年/月/日 |

三个必须写进代码规范的点：**分组不是固定 3 位**（印度 `12,34,567`）；**分隔符是码位不是「空格」**（fr 用 U+202F，Go `x/text` 输出 U+00A0，跨栈逐字节比对必失败）；**数字系统可以完全不同**（ar-EG 默认阿拉伯-印度数字，Go `x/text` v0.31.0 默认拉丁数字，实测差异 5/18 格）。排序同理：实测 D 里 `sv` 把 `Åsa/Ärger/Ödla/Öl` 排在 `Zebra` 之后，而 `en/de` 把它们当变体排在前部；数据库默认 collation、应用层、前端三套不一致，分页会重复或漏项。

## 文本膨胀与排版：按字素和显示格算，不按字节

W3C《Text size in translation》引 IBM 规则：英语源文案 ≤10 字符平均膨胀到 200–300%，11–20 字符 180–200%，31–50 字符 140–160%，超过 70 字符约 130%（[W3C, Text size in translation](https://www.w3.org/International/articles/article-text-size.en)，2026-11-21 访问）。短文案膨胀最吓人，而按钮、标签恰恰都是短文案。

| 现象（实测 E） | 数字 | 架构含义 |
|---|---|---|
| 伪本地化（`[!! !!]` 包裹 + 重音替换） | rune +12.90%，**byte +48.39%** | 字节膨胀是 rune 膨胀的 3.75 倍；DB 列宽按字节设会误判 |
| 同一文案 en/zh/ja | en 28 格；zh/ja 均 11 rune = 22 格；德语 40 rune（+42.86%） | 中文 rune 少但每字 2 格；德语变长最狠，布局按最坏语言留位 |
| ZWJ 家庭 emoji | 25 字节 / 7 rune / 1 字素 / 2 格 | 截断按字节会切碎 emoji，按 rune 会切 ZWJ 序列，只能按字素 |

排版还有三类「不是字体问题」的问题：**CJK 宽度**（11 个中文字是 22 格，不能按 `len` 算）；**泰语无空格断行**（实测 29 rune / 23 字素，按空白切只有 1 段，ICU 词典分出 7 段；没有分词器就没有断行点。中文/日文分词主场见 [45.1 倒排索引与分词](../45-检索与搜索引擎/45.1-倒排索引与分词.md)）；**RTL 与 bidi**（数字与拉丁词是 LTR run，不能把整段字符串 reverse；括号镜像与阿拉伯文连写靠渲染器）。

## 多语言内容的数据模型与缓存

内容不进主表 JSON 大字段，用 i18n 副表：**locale 必须是唯一键的一部分**。

```sql
-- 一行 = 一个 key 在一个 locale 下的译文；唯一键含 locale，才能 per-locale 灰度与回滚
CREATE TABLE i18n_message (
  bundle CHAR(32) NOT NULL, locale VARCHAR(35) NOT NULL, msg_key VARCHAR(128) NOT NULL,
  value TEXT NOT NULL,                -- ICU MessageFormat 串
  source_version CHAR(16) NOT NULL,   -- 源文案版本 hash，用于回滚与失效
  updated_at TIMESTAMP NOT NULL,
  PRIMARY KEY (bundle, locale, msg_key)  -- 复合键，见 44.8
);
```

只按 key 唯一会把简繁、拉美/欧洲西语挤成一行 JSON，灰度、审计、回滚全部失效；复合键的索引原理见 [44.8 索引原理](../44-数据库/44.8-索引原理.md)。fallback 按「精确 → 语言 → 默认」取最具体：

```sql
SELECT value FROM i18n_message
WHERE bundle = :b AND msg_key = :k AND locale IN (:exact, :lang, 'en')
ORDER BY CASE locale WHEN :exact THEN 0 WHEN :lang THEN 1 ELSE 2 END LIMIT 1;
```

| 层 | key / 头 | 坑 |
|---|---|---|
| 应用缓存 | `i18n:{bundle}:{locale}:{source_version}` | 少了 `source_version`，灰度期新旧译文混读；通用原则见 [41.2 本地缓存与分布式缓存](../41-缓存/41.2-本地缓存与分布式缓存.md) |
| HTTP 响应 | `Content-Language: zh-Hant` + `Vary: Accept-Language` | `Vary` 按**原始头**分片：实测 18 个真实头对应 12 种 tag 字符串，而内容包只有 9 个；q 顺序、空格、大小写都产生新变体，缓存键无上限 |
| CDN | 网关归一化成 `X-Locale: zh-Hant`，CDN 按它缓存 | 别让 CDN 直接解析 Accept-Language；归一化后变体数从「头的写法数」收敛到「内容包数」 |

实测 A 的归一化数字就是这条设计的依据：**18 个真实请求头 → 12 种 `tag.String()`（带 `-u-rg-` 扩展）→ 9 个内容 locale**。缓存键、埋点、计费都取「支持列表索引 / 内容包 id」，不要取 matcher 返回的 tag 字符串。

## 翻译流水线：四个开关保证可回滚

| 环节 | 做法 | 不这么做的后果 |
|---|---|---|
| 文案 key | 语义 key（`checkout.submit_button`），不用英文原文 | 原文当 key，改一个词全语言失效 |
| 源文案版本 | 源文案变更写 `source_version`（内容 hash 前 16 位） | 无法定位「哪版翻译对应哪版代码」 |
| pseudo-localization | CI 用 `[!! !!]` + 重音替换跑布局与编码 | 漏掉硬编码、截断、不可见字符 |
| 硬编码文案卡口 | CI 扫代码里的 CJK 字符串字面量 | 文案散在代码里，翻译平台永远收不齐 |

回滚靠在线开关：`bundle_version`（整包版本进缓存键与 URL）、`locale.<tag>.enabled`（新语言灰度）、`pseudo=1`（内部预览）、`fallback=zh-Hans`（繁体包故障降级）。四个开关切换后缓存键必须跟着变，否则回滚读到旧缓存。

环境：macOS arm64 / Apple 芯片 / Go 1.27.1 / `golang.org/x/text` v0.31.0 / 2026-11-21，支持 13 个内容 locale。


原样输出（节选 2 条 + 归一化统计）：

```text
03	header="zh-Hant-HK"
    parsed=[zh-Hant-HK] q=[1]
    matched=zh-Hant-u-rg-hkzzzz idx=2 supported[idx]=zh-Hant
05	header="sr-Cyrl-RS"
    parsed=[sr-Cyrl-RS] q=[1]
    matched=sr-Latn-u-rg-rszzzz idx=3 supported[idx]=sr-Latn
```

## 实测 F：bidi 类别与 run 分析（未做真机渲染）

```bash

go run ./cmd/bidi          # raw/f-bidi.txt
```

原样输出（RTL 段落，节选）：

```text

paragraph_direction=1 runs=4
run 摆放顺序(屏幕左->右)=[3 2 1 0]
run[1] dir=0 pos=8..15 text="1,234.50"
run[3] dir=0 pos=17..19 text="USD"
```

| 读数 | 数字 | 架构含义 |
|---|---|---|
| 数字 run | `1,234.50` 是 LTR（dir=0），内部不反转 | 「阿拉伯语界面里数字颠倒」多数是布局/拼接造成，不是 bidi |
| 字体 shaping | **已观测**（Ubuntu 24.04 / HarfBuzz 8.3.0 / Noto Naskh Arabic） | 同一字母随位置换形：`بببب` → `uniFE90(init) uniFE92(medi) uniFE92(medi) uniFE91(fina)`；`بيت` → `uniFE96 uniFEF4 uniFE91`；独立形是 `uni0628`。希伯来 `מם` → `uni05DE`（普通）与 `uni05DD`（词尾） |
| 括号镜像 | **shaping 层就镜像**（前提：字体里有这些字形） | `hb-shape --direction=rtl DejaVuSans "(a)"` → 逻辑 `(`(cluster 0) 出 `parenright`、`)`(cluster 2) 出 `parenleft`；`[a]` → `bracketright/bracketleft`，`<a>` → `greater/less`；同样文本 `--direction=ltr` 不镜像。换 Noto Naskh Arabic 时是 `.notdef`——**阿拉伯语字体常常不含 ASCII 括号**，用错字体会把"没字形"误判成"没镜像" |
| 真机渲染 | 仍未验证 | 缺 iOS/Android/浏览器截图环境（本次是命令行 shaping，不是屏幕像素） |

| 边界 | 事实 | 怎么做 |

**验证状态**：

- ① **阿拉伯文 shaping 已实测**（HarfBuzz 8.3.0）：连写字母确实按词首/词中/词尾切换呈现形式（`uniFE90/FE92/FE91`），希伯来词尾字母也有独立字形（`uni05DD` vs `uni05DE`）——"字体能不能连写"这一层不再是猜测。**真机 RTL 截图像素仍未验证**。
- ①b **括号镜像在 shaping 层就会发生，但依赖"方向 + 字体"两个条件**：`hb-shape --direction=rtl` 会把括号族的字形换成镜像（`parenleft↔parenright`、`bracketleft↔bracketright`、`less↔greater`），`--direction=ltr` 则不换；`fribidi --rtl` 同样输出镜像后的字节（`"(A"` → `41 29`）。两个实测坑：① 字体里没有 ASCII 括号时得到 `.notdef`（Noto Naskh Arabic 就是这样），别误判；② GNU FriBidi 1.0.13 的 `--nomirror` 在 4 组对照里与默认**逐字节相同**，这个开关没生效。所以"要不要自己镜像括号"的答案是：给了正确 direction 就不用手动，但必须保证 bidi 方向传对了。
- ② TMS（Phrase/Lokalise/Crowdin）导出格式与回滚 API：**未验证**（未接账号）。
- ③ CDN `Vary`/自定义缓存键实际行为：**未验证**（未接 CDN 账号，结论来自归一化实测与缓存分片推算）。
- ④ MessageFormat 2.0 与 FormatJS 兼容细节：**未验证**（未实现，仅引用文档）。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 `len(s)` / JS `.length` 限字段与截断 | 家庭 emoji 按字节 25、按 rune 7、按字素 1；前两种都会切碎 |
| 代码里拼句子：`"You have " + n + " files"` | 语序、格、量词全丢；ru 的 `2 файла`/`5 файлов` 无法用拼接表达 |
| 用 `n != 1` 或 `n > 1` 判断复数 | 实测矩阵里 en/ru/ar/pl/cs/fr 至少 5 种语言的边界判错 |
| 用原始 Accept-Language 做缓存键 | 18 个头 → 12 种变体且无上限；CDN 命中率被 q 顺序和空格吃掉 |
| 用数据库默认 collation 排多语言用户列表 | sv 的 å/ä/ö 排到 z 前，用户看到「乱序」；分页重复/漏项 |
| 把日期格式化成字符串存库/进 API | 时区语义丢失；同一时刻换时区显示错日（[72.2 多时区处理](72.2-多时区处理.md)） |

## 三条铁律

> 🔑 **locale 是四段式（语言-文字-地区），内容包按「语言-文字」建，地区只影响格式与用词。** `zh-CN` 能协商出简体，但不能当内容包身份；缺 script 的判断在繁简、塞语两种字母上都会出事。

> 🔑 **句子只允许整句进翻译（ICU MessageFormat），禁止拼字符串；数字、日期、排序只在展示边界格式化，内部只存 UTC 时刻与整数最小单位。** CLDR 六类复数与 locale 分组规则都不是常量表能替代的。

> 🔑 **长度按字素与显示格算，缓存键按内容包与文案版本算；翻译流水线必须有 version + locale 开关，能一键回退。** 字节膨胀 48.39% 与 18→9 的归一化，是这条铁律的两个直接数字。

## 自检

**Q1** `zh-CN` 和 `zh-Hans-CN` 在协商上都能落到简体，为什么内容包名还要用 `zh-Hans` 而不是 `zh-CN`？

▸ 答案：协商可以靠 likely subtags 把 `zh-CN` 补成 `Hans`，但**内容包的身份**要按语言-文字建：繁简是文字分叉，不是地区分叉。用 `zh-CN` 当键，`zh-TW`/`zh-HK` 的繁体就无包可挂。实测 A 里 `sr-Cyrl-RS` 因只有拉丁包落到 `sr-Latn`——「按语言建包」不够，必须补文字维度。

**Q2** 为什么法语 `1.5`、俄语 `1.5`、捷克语 `1.5` 分别是 `one`/`other`/`many`？用「n 是否大于 1」能判断吗？

▸ 答案：CLDR 按操作数 `i`（整数位）、`v`（可见小数位）、`f/t`（小数位值）判定，不看浮点大小。法语规则是 `i = 0,1` 即 one（含小数）；俄语要求 `v = 0` 才进 one/few/many，否则 other；捷克语 `v != 0` 直接 many。实测 B 的 90 格矩阵里 cs `1.5`=many、ru `1.5`=other、fr `1.5`=one，`n > 1` 一格都判不对。

**Q3** 一段用户昵称要截断到 20 个「显示单位」，应该按什么截？为什么 `len` 和 rune 都不行、字素才安全？

▸ 答案：按**字素**截断、按**显示格**评估宽度（中文 2 格、拉丁 1 格）。按字节（`len`）会把 `👨‍👩‍👧‍👦`（25 字节）切成半个 ZWJ 序列；按 rune（7）会切在 ZWJ 连接符上；只有字素（1）边界是安全断点。宽度另算：11 个中文字是 11 rune 但 22 格，按 rune 留宽会溢出。

**Q4** 多语言页面接 CDN，为什么 `Vary: Accept-Language` 是坑？怎么改？

▸ 答案：`Vary` 按**原始请求头**分片，而 Accept-Language 写法近乎无限：q 顺序、空格、大小写、`-u-rg-` 扩展都产生新键。实测 18 个真实头已对应 12 种匹配 tag 字符串，内容包只有 9 个，多出来的都是无效分片，缓存命中率被吃掉且缓存键无上限。改法：网关先归一化成 `X-Locale: zh-Hant`（内容包 id），CDN 按 `X-Locale` 缓存。

**Q5** 线上某条德语文案翻译错了，怎么在 10 分钟内回滚且不污染缓存？

▸ 答案：四步：① 回滚 `bundle_version`（缓存键 `i18n:{bundle}:{locale}:{source_version}` 含版本，切版本即绕开旧缓存，见 [41.2 本地缓存与分布式缓存](../41-缓存/41.2-本地缓存与分布式缓存.md)）；② 若整语言有问题，置 `locale.de.enabled=false`，fallback 到 `en`；③ CDN 走版本路径 `/i18n/v/{version}/` 并 purge 该前缀；④ 用 `pseudo=1` 在预发复核布局。关键：**翻译包版本、缓存键、CDN 路径三者同源**。
