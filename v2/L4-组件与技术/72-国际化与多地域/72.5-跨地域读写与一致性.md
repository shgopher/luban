# 72.5 跨地域读写与一致性

## 一句话

> 跨地域读写只有三个变量：**光速给的下限、复制模式给的陈旧窗口、路由策略给的读放大**；本机 84 ms RTT 链路实测：异步提交 p50 **0.32 ms**、写后读副本的陈旧窗口 p50 **42.9 ms**，同步提交 p50 **84.93 ms**、`remote_apply` 后读己之写违例 **0**——"要更新鲜"的每一毫秒，都在按 RTT 付费。

## 三个误区

| 误区 | 现实 |
|---|---|
| 跨地域就是"把数据复制一份" | 复制模型只决定"副本几份、谁收写"（[18.1 复制模型](../../L1-分布式原理/18-数据复制/18.1-复制模型-单主-多主-无主.md) 主场）；**读到什么由路由决定**。实测同一份数据：本地副本点查 0.58–1.20 ms，跨区回源点查 82.71–89.99 ms（**69–155 倍**） |
| "复制延迟"就是监控面板上的那个数 | 实测空闲时 `pg_stat_replication.replay_lag` = **83.55 ms**，而副本上实际可见窗口 p50 = **42.9 ms**；前者是 RTT 口径，后者是单程口径。200k 行突发时追平要 **~1.04 s**。用错口径，SLO 会差一倍 |
| 多地域写 = 每个 region 都能写就更快 | 写多活的成本是冲突处理（[36.6 切换时的数据一致性](../../L3-质量属性/36-灾备/36.6-切换时的数据一致性.md) 已证明资金/库存不接受 LWW）；跨区同步提交 84.93 ms 是本地 0.32 ms 的 **265 倍**，单连接串行吞吐被 `1/RTT` 锁死在 **11.8 次/s** |

## 先算物理下限：光速不会为你的架构让路

光纤中的光速约 **2.0×10⁵ km/s**（真空 3.0×10⁵ 的 2/3），所以两点间 RTT 的物理下限是 `2d / 2.0×10⁵ km/s`，与中间件、协议、语言全无关。

| 城市对（本机位于洛阳） | 大圆距离 | RTT 理论下限 | 实测/参考 |
|---|---|---|---|
| 洛阳 → 北京 | 683 km | 6.8 ms | 百度 ping 21.7 ms（2.4–3.2 倍，含路由绕行） |
| 洛阳 → 上海 | 922 km | 9.2 ms | 同上量级 |
| 洛阳 → 广州 | 1 280 km | 12.8 ms | 广州 CDN 建连 24 ms 量级 |
| 洛阳 → 新加坡 | 3 806 km | 38.1 ms | DigitalOcean 新加坡 TCP 建连 387 ms（路径绕行 10 倍） |
| 洛阳 → 法兰克福 | 7 997 km | 80.0 ms | 未直连测量 |
| 洛阳 → 弗吉尼亚 | 11 771 km | 117.7 ms | 微软 Akamai ping 226 ms |
| 洛阳 → 圣保罗 | 17 646 km | 176.5 ms | 未直连测量 |

（距离用 haversine 计算；公网测量见 72.4 的 `.cache/ch72/s7204/raw/d-public-rtt.txt`。）

三个可以记一辈子的量级：**同城 0.1–1 ms、同国跨省 10–40 ms、跨洲 150–300 ms**。理论值的用途不是做预算，而是**否决方案**：任何"上海与纽约之间 5 ms 强同步提交"的设计，在物理上就不成立；预算要用实测 P95。

> 🔑 跨地域架构的第一性原理：**能本地完成的，不要跨区；必须跨区的，先问"能不能异步"；必须同步的，只为最小的数据子集付费。**

## 写路径：四种形态，按"冲突后果"选

| 写路径 | 写延迟（本机 84 ms 链路） | 可用性 | 冲突 | 适用 | 主场 |
|---|---|---|---|---|---|
| **单写区 + 回源写** | 同区 0.3–1.4 ms；跨区客户端 86.7–96.3 ms | 主区故障时需切换（RPO 由复制模式定） | 无 | 强一致、写量不大、可接受跨区写延迟 | [18.2 同步/半同步/异步](../../L1-分布式原理/18-数据复制/18.2-同步-半同步-异步.md)、[44.13 主从复制与读写分离](../44-数据库/44.13-主从复制与读写分离.md) |
| **归属分区写** | 本地 0.3 ms；跨归属区 = 回源 | 单分区故障隔离 | 无（按 key 收敛） | 用户/租户数据、订单、账户 | [19.1 分区键设计](../../L1-分布式原理/19-数据分区/19.1-分区键设计.md)、[36.5 单元化 / Set 化架构](../../L3-质量属性/36-灾备/36.5-单元化-Set化架构.md) |
| **多区写 + 冲突解决** | 本地 0.3 ms + 冲突处理 | 最高（每区可写） | 必须显式解决（LWW / CRDT / 业务合并） | 协作编辑、购物车、计数、社交 | [18.1](../../L1-分布式原理/18-数据复制/18.1-复制模型-单主-多主-无主.md)、[36.6](../../L3-质量属性/36-灾备/36.6-切换时的数据一致性.md) |
| **全局共识（跨区 quorum）** | ≥1 RTT（84 ms 起），3 地 5 副本更高 | 少数派可用 | 无（线性一致） | 元数据、配置、分布式锁、全局 ID | [21.2 Quorum](../../L1-分布式原理/21-共识与选主/21.2-Quorum与WR-N.md)、[44.19 分布式数据库](../44-数据库/44.19-分布式数据库.md) |

### 跨地域事务：能不能不跨就别跨

跨区 2PC 的延迟下界是 **2 个 RTT**（prepare 一轮 + commit 一轮），本机 84 ms 链路就是 **≥168 ms**，还没算锁持有、协调者故障恢复与参与者重试。更贵的是**锁的持有时间随 RTT 放大**：锁持有 168 ms，热点行每秒最多 6 次更新。

| 方案 | 跨区提交延迟 | 一致性 | 什么时候用 |
|---|---|---|---|
| 本地事务 + 消息/补偿 | 0（跨区只剩消息延迟） | 最终一致 | 绝大多数跨区业务（下单、扣减、通知），见 [24.6 本地消息表](../../L1-分布式原理/24-分布式事务/24.6-本地消息表.md)、[24.5 Saga](../../L1-分布式原理/24-分布式事务/24.5-Saga.md) |
| 2PC / XA | ≥2 RTT | 强一致 | 只在同一 region 内、或能接受 168 ms+ 的极少数场景 |
| 分布式事务（Percolator / Spanner 类） | 1–2 RTT + 提交等待（TrueTime 类要等不确定区间） | 强一致（外部一致性） | 跨区强一致的托管数据库，代价是延迟与成本（[23.2 NTP 与 TrueTime](../../L1-分布式原理/23-时间、顺序与因果/23.2-NTP与TrueTime.md)） |

> 🔑 **跨地域不要跨事务**。把"一次跨区写"拆成"本地事务 + 可重试的异步步骤"，延迟从 2 RTT 降到本地，代价是引入补偿与幂等——这笔交易在 99% 的业务里划算。

## 读路径：五种，按"允许多旧"选

| 读路径 | 延迟（本机实测） | 陈旧度 | 实现成本 | 适用 |
|---|---|---|---|---|
| 本地副本读 | 点查 0.58–1.20 ms；200k 行 count 6.9–24.3 ms（客户端总耗时） | 复制延迟窗口内可能旧（p50 42.9 ms） | 低 | 商品、Feed、报表 |
| 写后读主（时间窗） | 同区 0.7 ms；跨区 86 ms | 0（窗口内） | 低 | 用户刚改的资料、订单状态 |
| 版本/LSN 等待 | 0.7 ms + 等待（通常 0–45 ms） | 0 | 中（要版本号） | 资金流水、库存扣减后的回显 |
| 双读仲裁（本地 + 回源比版本） | 本地 + 异步回源 | 0 或一个 RTT | 高（两次读） | 极少数要求新鲜又要低延迟的详情页 |
| 回源读（读主区） | 点查 82.71–89.99 ms；count 98.4–114.9 ms（客户端总耗时） | 0 | 低（但贵） | 强一致读、对账、后台 |

（本机实测 与 `count-total.txt`；读己之写、单调读等会话保证的机制在 [16.6 会话保证](../../L1-分布式原理/16-一致性模型/16.6-会话保证.md) 与 [18.4 复制延迟与读一致性](../../L1-分布式原理/18-数据复制/18.4-复制延迟与读一致性.md) 已讲透，本节只算"跨地域的账"。）

### 实测：陈旧预算换算成"本地读覆盖率"

异步复制下，副本可见延迟的实测分布（200 次写后轮询，`.cache/ch72/s7205/raw/async-stale.txt`）：

| 允许陈旧 S | 命中本地副本的比例 | 结论 |
|---|---|---|
| 0 ms | 0% | 只有同步/remote_apply 或读主能保证 |
| 40 ms | 0% | 低于单向延迟，物理上不可能 |
| 45 ms | 95.5% | 覆盖大多数请求，但 P95 尾部仍会读旧 |
| 50 ms | 99.5% | 1 000 次里约 5 次读旧 |
| 60 ms | 100% | 本实验窗口内全命中（实测 max 57.1 ms） |

> 🔑 这张表才是"最终一致"的真实含义：**不是"最终会一致"，而是"X% 的请求能在此刻读到最新的概率"**。SLO 要写"允许陈旧 N ms、本地读覆盖率 ≥ P%"，而不是一句"异步复制、延迟很低"（分级方法见 [46.3 数据一致性分级](../46-数据架构/46.3-数据一致性分级.md)）。

### 两个反直觉的实测结论

**结论一：跨地域读优化的收益与查询计算量成反比。** 同一个跨区回源：点查从 0.58–1.20 ms 变成 82.71–89.99 ms（**69–155 倍**），而 200k 行 `count(*)` 从 6.9–24.3 ms 变成 98.4–114.9 ms（**约 5–15 倍**）。原因很简单：重查询的时间主要花在 CPU 与 IO 上，网络 RTT 只是叠加项，不是倍乘项——但注意，它仍是**加法项**，不是零。所以优化顺序是：**先把"高频小点查"从跨区路径上赶走，再谈聚合查询的缓存**；反过来做，收益极小。

**结论二：写响应的 RTT 会自己掩盖复制延迟。** 一个跨区客户端写主区，收到 ACK 时已经过了 86.7 ms，而复制延迟只有 ~43 ms——**它写完立刻读副本，通常读不到旧值**。真正会踩到陈旧的，是"写发生在 A 区、读发生在 B 区的两个不同请求"（例如用户在 A 区改资料、在 B 区刷新列表），以及"同区写、异地读"的自动化流程。**用"我写完立刻读是新的"来证明"没有陈旧窗口"，是错的。**

## 双写为什么几乎总是错

双写不是"两个主"，是**两个不知道对方存在的主**。它的问题不是延迟，是冲突。

**冲突率推导**：设单向延迟 `d`、同一 key 的平均写间隔 `T`，两次写的传播窗口为 `2d`，则落在同一窗口内的概率约为 `2d / T`。代入本机实测的 `d = 40 ms`：

| 同 key 写间隔 T | 冲突概率（2d/T） | 场景 |
|---|---|---|
| 1 s | 8% | 活跃用户的资料/购物车 |
| 10 s | 0.8% | 普通订单状态 |
| 60 s | 0.13% | 低频配置 |

看起来不高？但**资金、库存、优惠券的冲突后果不是"覆盖一下"，是资损**。所以：

| 数据 | 多区写 + LWW | 正确做法 |
|---|---|---|
| 余额 / 库存 / 券 | 禁止（后写覆盖先写，且无法检测） | 单写区，或条件更新 `UPDATE ... WHERE balance >= x`（[36.6](../../L3-质量属性/36-灾备/36.6-切换时的数据一致性.md)） |
| 用户资料 | 可接受 LWW，但要记录冲突 | 按归属区单写更省事 |
| 购物车 / 收藏 | 可用 CRDT（并集/计数器） | 多区写 + 合并 |
| 计数器 / 点赞 | 可用 CRDT 或按区累加后汇总 | 多区写 + 定期归并（[44.22 计数系统](../44-数据库/44.22-计数系统.md)） |

> 🔑 **能单写就不要双写；能按归属分区就不要全局一致。** 双写省下的那点写延迟，会在第一次数据对不上时连本带利还回来。

## 故障与降级：把"允许旧多久"变成开关

| 故障场景 | 读 | 写 | 开关 |
|---|---|---|---|
| 跨区链路抖动（RTT 84→300 ms） | 本地副本读，接受更旧 | 同步提交超时后降级为异步（RPO>0） | `synchronous_commit=off`；读路由本地优先 |
| 主区故障 | 只读（副本提升前） | 停写或切灾备区（fencing + 位点，[36.6](../../L3-质量属性/36-灾备/36.6-切换时的数据一致性.md) 主场） | 切流开关 + 只读开关 |
| 副本严重落后（lag > SLO） | 摘除该副本，回源读或降级 | 不受影响 | 按 `replay_lag` 自动摘除 |
| 跨区流量打满 | 限制回源比例，本地读覆盖率下降 | 排队/限流 | 回源熔断 + 优先级队列 |

**必须监控的四个指标**（口径见 [50.4 度量](../50-可观测性/50.4-度量.md)）：

| 指标 | 口径 | 本机参考值 |
|---|---|---|
| 跨区 RTT P95 | 按链路（A→B）分别统计 | 84 ms（netem 复现） |
| 复制延迟 P95 | `pg_stat_replication.replay_lag` 或 `now()-pg_last_xact_replay_timestamp()` | 空闲 83.55 ms；突发 ~1.04 s |
| 陈旧读比例 | 读到的版本 < 已知最新版本的请求占比 | 由 42.9 ms 窗口 × 读频率推算 |
| 跨区流量 | GB/天，按 region 对拆分 | 决定成本与容量（[39.2 容量规划](../../L3-质量属性/39-成本/39.2-容量规划.md)） |

## 实测 A：链路与复现环境

环境：macOS arm64 / Apple 芯片 / Docker Desktop 29.9.2（Linux VM）/ PostgreSQL 16.14（alpine 3.20）/ Go 1.27.1 / 2026-11-21。两台"region"容器在同一网桥，各自 eth0 egress 加 40 ms `netem`，模拟北京↔新加坡一类跨区链路（光纤下限 38.1 ms，见上表）。

```bash
# 复现脚本：.cache/ch72/s7205/setup.sh（幂等，重建两容器 + PG 流复制）
docker exec pgA tc qdisc add dev eth0 root netem delay 40ms
docker exec pgA ping -c 5 pgB
```

原样输出（`.cache/ch72/s7205/raw/netem-rtt.txt`）：

```text
5 packets transmitted, 5 packets received, 0% packet loss
round-trip min/avg/max = 81.783/86.410/91.593 ms
Time: 82.809 ms        # psql 从 A 连 B 的查询往返
```

> 🔑 实验里所有"跨区"延迟都以这条 84 ms 链路为基准；链路是模拟的，但 **RTT 量级与真实跨区一致**（洛阳→新加坡光纤下限 38.1 ms，真实公网 70–100 ms 常见）。

## 实测 B：异步 / 同步 / remote_apply 的提交延迟

同一张表、同一台主库，只改复制模式，各写 300 次（单行 INSERT，本地连接），原始数据 `.cache/ch72/s7205/raw/lat-{async,sync,remote-apply}.csv`：

```text
lat-async          p50=   0.32 p95=   1.02 p99=   3.97 max=  10.10
lat-sync           p50=  84.93 p95=  88.46 p99=  93.64 max= 100.54
lat-remote-apply   p50=  84.77 p95=  88.30 p99=  98.72 max= 104.99
```

| 模式 | p50 提交延迟 | 一次写要等什么 | 读己之写 |
|---|---|---|---|
| 异步（默认） | **0.32 ms** | 本地 WAL flush | 不保证（窗口 p50 42.9 ms） |
| `synchronous_commit=on` | **84.93 ms** | 备库收到并 flush（1 RTT） | 不保证（备库可能还没回放） |
| `synchronous_commit=remote_apply` | **84.77 ms** | 备库回放完成（1 RTT + 回放） | **保证**（实测立即读副本命中） |

> 🔑 `on` 与 `remote_apply` 在本实验里延迟几乎一样（84.93 vs 84.77 ms），因为**网络 RTT 占绝对主导**；但语义差一档：`on` 保证"收到了"，`remote_apply` 保证"能读到了"。要读己之写又不想读主，选后者。

## 实测 C：异步复制的陈旧窗口

写侧在 A 本地、读侧在 B 本地（各自 unix socket，无网络噪声），写 200 次、间隔 10 ms，读侧每 2 ms 轮询一次；时间戳都取数据库的 `clock_timestamp()`（同宿主时钟）。

```bash
# 二进制源码 .cache/ch72/s7205/code/main.go；跨编译后 docker cp 进两容器
docker exec -u postgres pgA /tmp/bench -mode writer -n 200 -gap 10ms
docker exec -u postgres pgB /tmp/bench -mode reader -n 200
```

原样输出（`.cache/ch72/s7205/raw/async-stale.txt`）：

```text
n=200  min=40.8 ms  p50=42.9 ms  p95=45.0 ms  max=57.1 ms
S=40ms 本地读覆盖率=0.0%
S=45ms 本地读覆盖率=95.5%
S=50ms 本地读覆盖率=99.5%
S=60ms 本地读覆盖率=100.0%
```

| 读数 | 数字 | 架构含义 |
|---|---|---|
| 窗口下界 | 40.8 ms | 与单向 netem 40 ms 吻合：**陈旧窗口 ≥ 单向延迟**，调优参数改变不了物理下界 |
| 窗口 p50 | 42.9 ms | 想在 42.9 ms 内读到最新，只能同步/读主 |
| 窗口尾部 | p95 45.0 / max 57.1 ms | 尾部由回放调度与 fsync 抖动贡献，SLO 要按 p95/p99 定 |
| 与监控口径 | `replay_lag` 83.55 ms | 监控（RTT 口径）≈ 实际窗口（单程）的 **1.95 倍** |

## 实测 D：突发写入下复制会"追不上"

一次事务插入 20 万行（`.cache/ch72/s7205/raw/burst-lag.txt`）：

```text
INSERT 0 200000
Time: 320.305 ms                      # 主库本地提交
replica caught up: n=200000 after 1037.8 ms   # 副本追平（含 docker exec 轮询开销 20–40 ms/次）
## 空闲时 pg_stat_replication
 state    | write_lag | flush_lag | replay_lag
 streaming| 00:00:00.08355 | 00:00:00.08355 | 00:00:00.083551
```

| 读数 | 数字 | 架构含义 |
|---|---|---|
| 稳态窗口 | 42.9 ms（p50） | 空闲时"延迟"看起来很小 |
| 突发追平 | 10 万行/秒量级的写入会把窗口拉到 **~1 s** | 报"复制延迟 50 ms"的监控，在批量任务时会失准 |
| 监控口径 | `replay_lag` 83.55 ms | 稳态是 RTT 口径；突发时它也会跟着涨，但**不要用单个瞬时值代表 SLO** |

> 🔑 复制延迟不是常数，是"带宽 × 回放能力 × 写入速率"的函数。容量规划要按"峰值写入 + 允许窗口"算回放能力，而不是按均值（[57.2 容量模型](../../L5-工程效能/57-容量与成本治理/57.2-容量模型.md)）。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**

| 需求 | 产品 | 关键配置 |
|---|---|---|
| 单写区 + 跨区只读副本 | PostgreSQL 16 流复制 / MySQL 8 半同步、组复制 | `synchronous_commit`、`synchronous_standby_names`（PG）；`rpl_semi_sync_*`、`group_replication_*`（MySQL，见 [44.13](../44-数据库/44.13-主从复制与读写分离.md)） |
| 跨区强一致数据库 | Spanner / CockroachDB / TiDB | 区域放置 + 共识副本；代价是写延迟 ≥ 1 RTT（[44.19](../44-数据库/44.19-分布式数据库.md)） |
| 元数据/配置/锁 | etcd（Raft） | 跨区 3 副本的写延迟 ≈ 1 RTT；跨洲部署要接受 100 ms+（[21.5 Raft 选主](../../L1-分布式原理/21-共识与选主/21.5-Raft选主.md)） |
| 跨区数据同步 | CDC（Debezium / Flink CDC） | 异步、可重放、不参与在线写（[46.4 CDC](../46-数据架构/46.4-CDC.md)） |

**可抄**：PostgreSQL 主库 / 备库两份最小配置（生产把 IP、SSL、认证换成你的）：

```ini
# 主库 postgresql.conf
wal_level = replica
max_wal_senders = 10
synchronous_standby_names = '*'      # 退化为异步时置空
synchronous_commit = remote_apply    # 要读己之写用这个；只保持久性用 on
```

```bash
# 备库：基于主库做一次 basebackup（-R 自动写 primary_conninfo 与 standby.signal）
pg_basebackup -h <primary> -U replicator -D /var/lib/postgresql/data -Fp -Xs -P -R

# 可验：主库上应看到 streaming，以及三种 lag
psql -c "SELECT state, write_lag, flush_lag, replay_lag FROM pg_stat_replication;"
# 备库上确认自己在回放
psql -c "SELECT pg_is_in_recovery(), pg_last_wal_replay_lsn();"
```

**会话级"读己之写"（不想全局开 remote_apply 时的折中）**：把写事务的 LSN 带回客户端，读副本前等到副本回放到该 LSN：

```go
// 写主库时顺手拿到 LSN
var lsn string
err := primary.QueryRow(`INSERT INTO t(v) VALUES($1) RETURNING pg_current_wal_lsn()::text`, v).Scan(&lsn)

// 读副本前：等到副本回放 >= lsn（最多等 100ms，超时降级读主）
deadline := time.Now().Add(100 * time.Millisecond)
for time.Now().Before(deadline) {
    var ok bool
    _ = replica.QueryRow(`SELECT pg_last_wal_replay_lsn() >= $1::pg_lsn`, lsn).Scan(&ok)
    if ok {
        break
    }
    time.Sleep(2 * time.Millisecond)
}
```

**可验**（本机真跑）：

| 检查项 | 期望值（本机实测） | 原始输出 |
|---|---|---|
| 跨区 RTT | 84–86 ms（netem 40 ms/侧） | `netem-rtt.txt` |
| 提交延迟 异步/同步/remote_apply | 0.32 / 84.93 / 84.77 ms | `lat-summary.txt` |
| 异步陈旧窗口 | p50 42.9 ms，p95 45.0 ms | `async-stale.txt` |
| 突发追平 | 20 万行 ~1.04 s | `burst-lag.txt` |
| 读路径 | 本地点查 0.58–1.20 ms vs 跨区 82.71–89.99 ms；count 本地 6.9–24.3 ms vs 跨区 98.4–114.9 ms | `read-write-latency.txt`、`count-total.txt` |

**可退**（每个开关都要能在线切，且写清代价）

| 退路 | 做法 | 代价 |
|---|---|---|
| 同步写太慢 | `synchronous_commit=off` / `synchronous_standby_names=''` | 提交从 84.9 ms 回到 0.32 ms；RPO>0，陈旧窗口 42.9 ms 起 |
| 跨区读太慢/故障 | 读路由切"本地优先"，限制回源比例 | 允许陈旧，按 SLO 摘副本 |
| 主区故障 | 停写 + 只读 + 副本提升（fencing + 位点） | RTO 分钟内；RPO 取决于复制模式 |
| 双写冲突 | 回退单写区，双向复制改单向 | 一边延迟上升，换回"无冲突" |

## 反模式

| 反模式 | 后果 |
|---|---|
| 跨区双写 + LWW 覆盖余额/库存 | 后写无条件覆盖先写，冲突率 2d/T：T=1 s 时约 8%，且无法检测，直接资损（[36.6](../../L3-质量属性/36-灾备/36.6-切换时的数据一致性.md)） |
| 用"复制延迟 50 ms"当 SLO，且只看瞬时值 | 突发写入实测追平 ~1.04 s；监控口径 83.55 ms 是实际窗口的 1.95 倍，SLO 会算错 |
| 所有读都回源"图省事" | 点查从 0.58–1.20 ms 变 82.71–89.99 ms（69–155 倍），跨区流量与成本一起涨 |
| 跨区 2PC 传账户余额 | 提交 ≥2 RTT（168 ms），锁持有时间 × RTT，热点行吞吐掉到个位数/秒 |
| 用"写完立刻读是新的"证明无陈旧窗口 | 跨区写 ACK 本身就花了 86.7 ms，> 43 ms 窗口；真正踩坑的是"同区写、异地读"的另一个请求 |
| 只加副本不加回放能力 | 副本越多写放大越大，回放跟不上，窗口从 43 ms 涨到秒级（[18.7 复制拓扑](../../L1-分布式原理/18-数据复制/18.7-复制拓扑.md)） |
| 强一致范围按"整个库"设计 | 只有少数数据集需要强一致；全库强一致 = 全站为最慢的那张表付 RTT（[46.3](../46-数据架构/46.3-数据一致性分级.md)） |

## 三条铁律

> 🔑 **先算 RTT，再谈一致性。** 同城 0.1–1 ms、同国 10–40 ms、跨洲 150–300 ms；任何"跨洲强同步"的方案先过物理这一关，过不了就改异步或改数据归属。

> 🔑 **写路径按"冲突后果"选，读路径按"允许多旧"选。** 资金/库存单写或条件更新；商品/Feed 本地读 + 陈旧预算；两件事不要混在一个方案里。

> 🔑 **监控的 `replay_lag`（RTT 口径）不等于用户看到的陈旧窗口（单程口径）。** 本机实测 83.55 ms vs 42.9 ms；SLO 必须用"可见窗口 + 本地读覆盖率"表达，并覆盖突发写入。

## 自检

**Q1** 一个跨区系统要求"用户写完立刻能看到自己的修改"，同时读要走本地副本。你至少有两种实现，怎么选？

▸ 答案：① 全局 `synchronous_commit=remote_apply`：写提交从 0.32 ms 变 84.77 ms，所有写都付 RTT；② 会话级 LSN 等待：写返回 LSN，读副本前等到回放 ≥ LSN（本机窗口 42.9 ms，通常等 0–45 ms），只让"写后读"这一小部分请求付钱。多数业务选 ②；只有资金类、写后必须强一致的场景才全量 ①。

**Q2** 监控显示复制延迟 50 ms，副本却偶发读到几分钟前的数据，为什么？

▸ 答案：`replay_lag` 是瞬时值且是 RTT 口径，突发/大事务/回放积压时窗口会跳到秒级（本机 20 万行突发追平 ~1.04 s）；另外瞬时值会被"刚好追平"的采样掩盖。要看 p95/p99 与"陈旧读比例"，并对"副本落后超过阈值"做自动摘除，而不是盯一个绿色数字。

**Q3** 为什么说"跨区双写 + LWW"在资金场景一定出事？用数字说。

▸ 答案：冲突概率约 2d/T，d=40 ms、T=1 s 时约 8%；LWW 的语义是"后写覆盖先写"，两笔并发扣款会被合成一笔，且事后无法从数据上判断哪笔丢了。资金/库存要用单写区、条件更新（`WHERE balance >= x`）或串行化，不能用时间戳裁决。

**Q4** 同一份数据，为什么点查跨区慢 69–155 倍，而 200k 行 count 只慢约 5–15 倍？

▸ 答案：跨区增加的是固定 RTT（本地回环 0.1–1 ms → 跨区 84 ms）；点查的本地耗时几乎为 0，RTT 就是全部，所以倍率极大。重查询的本地耗时 7–24 ms，RTT 84 ms 是叠加在后面的固定项，倍率小但绝对增量一样是 84 ms。由此得优化顺序：先把高频小点查赶出跨区路径，再考虑重查询的缓存/下推。

**Q5** 主区故障后，为什么"把副本提为主"之前一定要 fencing？

▸ 答案：不 fencing 会出现两个主同时接受写（脑裂），旧主恢复后带着新写入覆盖新主，丢的不只是切换窗口的数据而是两边的写。fencing 让存储层拒绝旧主（关网、撤权、改密码、租约），位点保证新主从旧主最后提交处接上；细节是 [36.6](../../L3-质量属性/36-灾备/36.6-切换时的数据一致性.md) 的主场。
