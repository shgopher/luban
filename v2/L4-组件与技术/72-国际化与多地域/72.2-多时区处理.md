# 72.2 多时区处理

## 一句话

> 时区不是"给时间加个后缀"，而是三种东西必须分开：**时间点存 UTC、墙上时间必须带 IANA zone id、偏移只配当渲染结果**；本机 6 个时区实测 2026 年有 **10 个不是 24 小时的天**（23h/25h，Lord Howe 还有 23.5h/24.5h），按 15 分钟粒度采样，纽约 03-08 只有 **92 条**、11-01 有 **100 条**（普通日与 UTC 都是 96 条），同一条 `2026-01-15 09:00` 字面量在三个 session 时区插进 PostgreSQL 得到 **09:00Z / 14:00Z / 01:00Z** 三个瞬时。

## 三个误区

| 误区 | 现实 |
|---|---|
| 存"本地时间字符串"就完事 | `2026-03-08 02:30` 在 America/New_York 不存在；Go 静默改成 **01:30 EST**（06:30Z），Node 改成 **03:30 EDT**（07:30Z），PostgreSQL 也改成 **03:30 EDT**——同一个字符串在三个运行时差 **1 小时**（实测 B） |
| 存了偏移就等于存了时区 | 偏移只描述一瞬间：`2026-07-15T09:00:00-04:00` 固定偏移加 6 个月仍是 `-04:00`，而纽约届时是 `EST`，差 **1 小时**（实测 G4） |
| 一天固定 24 小时，日报按 `ts/86400` 分桶 | 实测 A 的 6 个时区 2026 年共 **10 个非 24h 天**；纽约 11-01 是 **25h（90 000 s）**、03-08 是 **23h（82 800 s）**（实测 C/D） |

## 时间点 / 墙上时间 / 偏移：三种东西，三种存法

| 概念 | 定义 | 例子 | 存什么 | 用途 |
|---|---|---|---|---|
| **instant** | 时间轴上唯一瞬时，与时区无关 | 下单、支付回调、日志行、审计事件 | UTC 秒/微秒或 `timestamptz` | 排序、比较、对账、跨系统传递 |
| **local time**（墙上时间） | 日历上的钟面读数，会重复（overlap）也会缺失（gap） | "下周三 9 点开会"、营业时间 09:00–22:00 | 墙钟 + **IANA zone id** | 展示、调度、业务规则 |
| **offset**（偏移） | 某一瞬间 local−UTC 的差值 | `+08:00`、`-05:00` | 只在渲染/传输层出现 | 日志格式化、SQL 输出 |

| 场景 | 表示 | 为什么 |
|---|---|---|
| 订单时间、支付时间、日志时间、审计事件 | **instant（UTC）** | 只需回答"谁先谁后"，不需要也不应该关心用户在哪个时区；跨地域对账时把本地时间当排序键会错 |
| "下周三 9 点开会"、活动开始、营业时间 | **local time + IANA zone id** | 规则要跟着"那个地方"走：纽约 9 点开会，夏令时前后都是 9 点，换算成 UTC 分别是 14:00Z 和 13:00Z |
| 日报切日、配额重置、签到、连续打卡 | **业务时区配置 + 墙钟日期** | 业务定义的是"日历日"，不是"86400 秒"；口径必须先声明（三种口径见「业务日切」） |
| cron 表达式 / 时区缩写 | **表达式 + 时区**；缩写**不存** | 同一句 `0 9 * * *` 在不同时区落在不同 UTC 时刻；`CST` 对应 3 个时区 3 种偏移（+8/−6/−5），`IST` 是 +5.5/+1/+2（实测 F：`raw/f-abbr.txt`） |

**为什么"带 IANA zone id 而不是 offset"**：offset 只声明"这一瞬间"，不声明规则。RFC 9557 把这点写成定义：offset "makes no claims about the UTC offset of other related timestamps"，因此不能用来做"一天以后"这类本地时间运算；而 IANA zone 是一组会随政策更新的规则。存 `+08:00` 的会议约不到 2027 年的纽约客人，存 `America/New_York` 才能。

## 存储类型怎么选

**PostgreSQL：`timestamptz` 存 UTC，`timestamp` 存墙钟。** `timestamptz` 内部只存 UTC 微秒，`SET TIME ZONE` 只影响**显示与字面量解析**；`timestamp` 存的就是那串数字，永不转换。实测 D1：同一条字面量 `2026-01-15 09:00` 在三个 session 时区分别插入，`ts_tz` 变成三个不同瞬时，而 `ts_plain` 三行完全一样：

```text
 id |     note     |         ts_tz          |      ts_plain
----+--------------+------------------------+---------------------
  1 | UTC 会话插入 | 2026-01-15 09:00:00+00 | 2026-01-15 09:00:00
  2 | NY 会话插入  | 2026-01-15 14:00:00+00 | 2026-01-15 09:00:00
  3 | SH 会话插入  | 2026-01-15 01:00:00+00 | 2026-01-15 09:00:00
```

这解释了"为什么本地跑对、上线错"：应用没显式设 session 时区时，同一句 `INSERT ... TIMESTAMP '2026-01-15 09:00'` 的含义由数据库默认时区决定。**结论：instant 用 `timestamptz`，并且写入时永远带偏移或显式 `SET TIME ZONE`；业务日另存 `date` 列。**

```sql
-- 订单表：瞬时 + 业务日 + 业务时区，三个字段各司其职
CREATE TABLE orders (
  id            bigint PRIMARY KEY,
  created_at    timestamptz NOT NULL DEFAULT now(),   -- 订单时间：instant
  business_date date        NOT NULL,                 -- 业务日：应用按 business_tz 算好落库
  business_tz   text        NOT NULL DEFAULT 'Asia/Shanghai'
);
-- 按业务日聚合：显式时区，不依赖 session
SELECT date_trunc('day', created_at AT TIME ZONE 'Asia/Shanghai') AS d, count(*)
FROM orders
WHERE created_at >= '2026-11-01 00:00+08' AND created_at < '2026-11-02 00:00+08'
GROUP BY 1;
```

`AT TIME ZONE 'Asia/Shanghai'` 的返回类型是 `timestamp without time zone`（实测 D5 的 `pg_typeof`），即"本地墙钟"；拿它做 `date_trunc` 才是业务日，直接对 `timestamptz` 做 `date_trunc` 用的是 session 时区——实测 D4 同一批 6 笔订单在 UTC 会话是 `6`，在上海会话是 `5+1`，在纽约会话是 `1+5`。

**MySQL：`TIMESTAMP` 会转换且 2038 截止，`DATETIME` 不转换。**

| 类型 | 存什么 | 显示/写入受什么影响 | 范围 | 坑 |
|---|---|---|---|---|
| `TIMESTAMP` | UTC 秒值 | session `time_zone`：写入从当前时区转 UTC，读取转回来 | `1970-01-01 00:00:01`～`2038-01-19 03:14:07` UTC | 换 session 时区读同一行会变；2038 截止；命名时区要先灌 tz 表 |
| `DATETIME` | 字面墙钟，不转换 | 不受 session 时区影响 | `1000-01-01`～`9999-12-31` | 不带宽区语义：跨系统时必须外部约定"这列是 UTC 还是本地" |

以上范围与转换语义取自 MySQL 8.4 手册（[The DATE, DATETIME, and TIMESTAMP Types](https://docs.oracle.com/cd/E17952_01/mysql-8.4-en/datetime.html)，访问 2026-11-21）："MySQL converts TIMESTAMP values from the current time zone to UTC for storage, and back from UTC to the current time zone for retrieval. (This does not occur for other types such as DATETIME.)"。命名时区（如 `'Asia/Shanghai'`）**必须**先用 `mysql_tzinfo_to_sql` 灌 `mysql.time_zone*` 表，否则报 `ERROR 1298`；规则更新后还要重灌（[MySQL Server Time Zone Support](https://docs.oracle.com/cd/E17952_01/mysql-8.4-en/time-zone-support.html)）。

选型：instant 推荐 `TIMESTAMP(6)`（有内置 UTC 语义）但**必须**接受 2038 上限；要跨 2038 或不想依赖 tz 表，用 `DATETIME(6)` 存 UTC 并在应用层强约束，再单独存 `business_date`。两条路都不要"存本地墙钟再猜"。

**Go 与 JSON：`time.Time` 带 zone 记忆，RFC3339 不带。** `time.Time` 内部是 instant + 一个 `*Location`；序列化成 JSON 时只输出 RFC3339 的 offset，**zone id 丢了**。实测 G4：`json.Unmarshal` 回来 `America/New_York` 的 zone 名是空串（固定偏移），而 `+08:00` 在上海服务器上甚至会被认成机器本地时区 `CST`（这是 `time.Parse` 的文档行为：偏移匹配 Local 时用 Local）。

| 传输格式 | 带 zone id | 带 instant | 适用 |
|---|---|---|---|
| `int64` Unix 秒/毫秒 | 否 | 是 | 日志、事件、内部 API（最不易错） |
| RFC3339 `2026-03-08T00:30:00Z` | 否 | 是 | 通用 API 时间点 |
| RFC3339 + 裸 offset `...+08:00` | 否 | 是 | 同上，但别拿它做本地时间运算 |
| IXDTF/RFC 9557 `2026-03-08T00:30:00Z[America/New_York]` | 是 | 是 | 需要"墙钟语义 + 规则"的接口（会议、活动、日程） |
| `{"at":"...Z","tz":"America/New_York"}` | 是 | 是 | 老协议不想升 RFC 9557 时的最小侵入方案 |

同一句 `-04:00` 的字符串加 6 个月会差 1 小时（见误区表），根因就是 offset 不含规则；RFC 9557 明确警告不要用 offset 伪造时区（"MUST NOT copy the UTC offset from a timestamp into an offset time zone"）。

## DST 两类陷阱：gap 与 overlap

- **gap**：春季拨快，某段墙钟不存在。纽约 2026-03-08 本地 `02:00→03:00`，`02:30` 不存在。
- **overlap**：秋季拨慢，某段墙钟出现两次。纽约 2026-11-01 本地 `02:00→01:00`，`01:30` 出现两次，两个瞬时相差 3600 s；Lord Howe 是 30 分钟 DST，重复段两个瞬时相差 **1800 s**。

各运行时默认行为**不一致**，而且 Go 自己的方向也不固定（同一次实测）：

| 运行时 / 场景 | gap `2026-03-08 02:30` | overlap `2026-11-01 01:30` |
|---|---|---|
| Go `time.Date` (NY) | **01:30 EST**（06:30Z，往前挪 1h） | 第一次（05:30Z，EDT） |
| Go `time.Date` (Berlin) | **03:30 CEST**（01:30Z，往后挪 1h） | 第二次（01:30Z，CET） |
| Python `zoneinfo` fold=0 | 保持 `02:30-05:00`，UTC 07:30Z | 第一次（05:30Z） |
| Node（V8） | **03:30 EDT**（07:30Z） | 第一次（05:30Z） |
| PostgreSQL `timestamptz` | **03:30 EDT**（07:30Z） | 第二次（06:30Z，标准时） |

Go 文档对这类时间只承诺"correct in one of the two zones involved... does not guarantee which"（`go doc time.Date`）。所以**唯一安全的做法是把选择变成显式策略**：

```go
// candidates 返回该墙钟在 loc 中真实存在的所有瞬时：gap 时 0 个，overlap 时 2 个。
func candidates(loc *time.Location, y int, mo time.Month, d, hh, mm, ss int) []time.Time {
	want := time.Date(y, mo, d, hh, mm, ss, 0, time.UTC) // 仅作墙钟字段载体
	seen := map[int64]time.Time{}
	for k := -72; k <= 72; k++ { // 在 ±36h 里采样不同偏移，反推候选瞬时
		probe := want.Add(time.Duration(k) * 30 * time.Minute)
		_, off := probe.In(loc).Zone()
		cand := want.Add(-time.Duration(off) * time.Second)
		lt := cand.In(loc) // 只有回读后墙钟完全一致的才是真候选
		if lt.Year() == y && lt.Month() == mo && lt.Day() == d && lt.Hour() == hh && lt.Minute() == mm && lt.Second() == ss {
			seen[cand.Unix()] = cand
		}
	}
	var out []time.Time
	for _, t := range seen {
		out = append(out, t)
	}
	sort.Slice(out, func(i, j int) bool { return out[i].Before(out[j]) })
	return out
}
```

实测（`raw/b2-resolve.txt`）：NY `02:30` 候选 **0 个**、NY `01:30` 候选 **2 个**（05:30Z / 06:30Z）、Berlin `02:30` 候选 0 个、Lord Howe `01:30` 候选 2 个（14:30Z / 15:00Z）。拿到候选数后再按策略处理：

| 场景 | 策略 | 说明 |
|---|---|---|
| 用户填预约时间落在 gap | 拒绝并要求重选 / 顺延到 gap 结束 / 提前到 gap 开始 | 三选一，写进产品文案；不允许"静默规范化" |
| 用户填活动时间落在 overlap | 默认第一次出现；需要第二次时显式传 `fold=1` 或 UTC 瞬时 | 不声明就等于把选择交给运行时 |
| 日志/事件时间 | 永不存墙钟 | 只有 instant，不存在 gap/overlap |

## 业务日切：日报、配额、签到必须先声明"业务时区"

"今天"不是一个全局事实。实测 C3：`2026-11-01T17:00Z` 在上海是 **11-02 01:00**，UTC 还是 **11-01**，纽约是 **11-01 12:00**。三种口径必须显式选一个：

| 口径 | 定义 | 适合 | 风险 |
|---|---|---|---|
| **UTC 日** | 以 00:00Z 切 | 跨地域技术报表、日志归档 | 与用户直觉差 8–12 小时，日报"昨天的单"会漏 |
| **用户时区日** | 按用户各自 zone 切 | C 端"我的日报"、连续签到 | 同一业务日有 24 种边界，全局排行/风控口径会分裂 |
| **总部/业务时区日** | 全系统一个配置项（如 `Asia/Shanghai`） | 财务对账、配额、结算 | 海外用户觉得"重置时间很怪"，必须解释；换口径要迁移历史 |

实测 C4（每 20 分钟一笔、2026-10-31T16:00Z～11-02T16:00Z 共 144 笔）三种日切聚合结果完全不同：

```text
| 日切口径 | 2026-10-31 | 2026-11-01 | 2026-11-02 | 极差 |
| UTC | 24 | 72 | 48 | 48 |
| Asia/Shanghai | 0 | 72 | 72 | 72 |
| America/New_York | 36 | 75 | 33 | 42 |
```

**DST 日不是 24 小时**：实测 C2，按 15 分钟粒度采样，纽约 11-01 有 **100 条**（25h×4），普通日 96 条；实测 A 算出纽约 03-08=23h、11-01=25h，Lord Howe 是 23.5h/24.5h，Chile 的 America/Santiago 在本地 00:00 切换（00:00 当天不存在）。SQL 里可以直接验证：

```text
 spring_day |    fall_day
------------+----------------
 23:00:00   | 1 day 01:00:00
```

（`raw/d-postgres.txt` D6：两个 `date AT TIME ZONE zone` 相减。）所以"按天聚合"的判据是**本地日期**，不是秒数；"每日配额"必须写清是"每个本地日历日"还是"滚动 24 小时"——前者在 DST 日是 23/25 小时，按小时限速会突然多/少 1 小时额度（配额模型见 [65.3 计费与配额](../65-多租户SaaS/65.3-计费与配额.md)）。

## 定时任务：cron 在哪个时区解释

- **系统 cron 用守护进程的本地时区**（`/etc/localtime`）：容器把 `/etc/localtime` 设为 America/New_York 后，`* * * * *` 任务写出的日志是 `05:45:00 EST`（同时刻 UTC 10:45），证明"服务器时区 = 调度时区"（`raw/g-cron.txt`）。cronie 的 `CRON_TZ=Asia/Shanghai` 只改表达式解释，不改日志时区（[crontab(5)](https://man7.org/linux/man-pages/man5/crontab.5.html)，访问 2026-11-21）。
- Kubernetes CronJob 用 `.spec.timeZone`（v1.27 起 Stable）；不写则按 kube-controller-manager 本地时区；在 `schedule` 里写 `TZ=`/`CRON_TZ=` 会被拒绝（[CronJob](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/)，访问 2026-11-21）。
- **"每天 09:00 用户本地时间推送"** 不能写成一条全局 cron。做法：调度表存 `(user_id, zone, local_time, dst_policy)`，按 zone 分组批量算下一次触发，落库成 UTC；09:00 这类时刻不会落进 gap，但 `02:30` 会，`01:30` 会重复。

两种推进方式的差别是硬伤：从 2026-01-01 09:00 纽约开始，直接 `+24h` 推进，2026 年有 **238 天**钟面不是 09:00（7 月那次是 10:00 EDT），直到跨过秋季回拨才"碰巧"回到 09:00；按**本地墙钟每天重算**则 0 天偏差（实测 G1）。

| 调度目标 | 建议策略 | 一年触发次数（本机实测） |
|---|---|---|
| 每天 09:00 本地 | 墙钟重算 + zone，gap 不会命中 | 365 |
| 每天 02:30 本地 | 命中 gap：跳过=364 次；顺延到 03:30=365 次 | 364 / 365 |
| 每天 01:30 本地 | 命中 overlap：按日期各一次=365；按真实瞬时=366 | 365 / 366 |

## tzdata 是依赖不是常量

时区规则会因政治决定改变，历史数据也一样。实测 E（`raw/e-history-macos.txt`，macOS tzdata **2026f**）：

| 时区 | 变化 | UTC 切换时刻 |
|---|---|---|
| Europe/Istanbul | 2016-09 起永久 UTC+3（原 EET/EEST 双规则） | 2016-09-06T21:00Z |
| America/Mexico_City | 2022-10-30 之后不再有春季切换（取消 DST） | 2022-10-30T07:00Z |
| Asia/Almaty | 2024-03-01 起全国 UTC+5（原 +6） | 2024-02-29T18:00Z |
| Australia/Lord_Howe | DST 只拨 **30 分钟**（+10:30 ↔ +11） | 2026-04-04T15:00Z / 10-03T15:30Z |

同一台机器上就同时存在三份 tzdata：宿主 macOS **2026f**、Go 1.27.1 内嵌 **2026c**（`lib/time/update.bash` 的 `CODE/DATA=2026c`）、alpine 3.20 的 `tzdata-2026b-r0`。实测 E3 用同一批瞬时对比偏移：**2026f vs 2026c 有 5 个时区名不同、2026f vs 2026b 有 10 个、2026c vs 2026b 有 5 个**（差异集中在 2027 年以后的预测，如 Winnipeg 在 2027-01-15 是 −5 还是 −6、Casablanca 是 +1 还是 0）。这不是 bug，是"数据版本不同"。

工程含义只有一条：**tzdata 必须随发布走、版本必须可查、升级必须可回退**。Go 可以 `-tags timetzdata` 把 tzdata 编进二进制（实测二进制从 **2 381 774 字节**涨到 **2 778 974 字节**，+397 200 字节 ≈ +16.7%）；容器镜像里要显式 `apk add tzdata` 或固定基础镜像版本。裸 alpine 里普通 `go build` 的二进制 `LoadLocation` 全部失败：`unknown time zone America/New_York`，带 tag 的同一个程序三地全 OK（实测 E1）。

| Europe/Berlin | 2 | 1 | 0 | 0 | 1 | 2026-03-29=23.0h; 2026-10-25=25.0h |

| 读数 | 数字 | 架构含义 |
|---|---|---|
| 非 24h 天 | 6 个时区共 10 天（含 23.5/24.5） | 任何"天 = 86400 秒"的算术在切换日必错，误差 1800–3600 s |
| 切换时刻 | NY `07:00Z`、Berlin `01:00Z`、Chatham `14:00Z` | 切换点不在 UTC 整点/午夜，跨时区合并任务要按真实瞬时算 |
| 南半球与中国 | Santiago 在**本地 00:00** 切、Chatham 用 +12:45、上海 0 次切换 | 日界与切换点重合时 `time.Date(...,0,0,0)` 会退回前一天，日界必须二分找（代码 `boundary`）；"我们不用 DST"只对本地成立 |

  1 | gap 02:30     | 2026-03-08 07:30:00+00 | 2026-03-08 03:30:00
  3 | overlap 01:30 | 2026-11-01 06:30:00+00 | 2026-11-01 01:30:00
===== D4 session 时区分桶（同一批 6 笔订单）
 UTC: 11-01 -> 6；上海: 11-01 -> 5, 11-02 -> 1；纽约: 10-31 -> 1, 11-01 -> 5

| 读数 | 数字 | 架构含义 |

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：数据库用 **PostgreSQL 16** 的 `timestamptz`（替代：MySQL 8.4 `TIMESTAMP(6)`/`DATETIME(6)`，取舍见本节「存储类型怎么选」）；应用层 **Go 1.27** `time` + IANA zone（替代：Java `java.time.ZonedDateTime`、Python `zoneinfo`）；容器时区数据用发行版 **tzdata** 包或 Go `-tags timetzdata` 内嵌；定时任务用 **cronie `CRON_TZ`** 或 **Kubernetes CronJob `.spec.timeZone`**（v1.27 Stable）。

**可抄**（容器内 PostgreSQL 启停；本节实测用的就是这套）：

```bash
docker run -d --name pg72 --rm --sysctl net.ipv6.conf.all.disable_ipv6=1 alpine:3.20 sleep 3600
docker exec pg72 sh -c 'apk add --no-cache postgresql16 postgresql16-client tzdata'
docker exec pg72 sh -c 'mkdir -p /run/postgresql && chown postgres:postgres /run/postgresql'
docker exec -u postgres pg72 sh -c 'initdb -D /tmp/pgdata -E UTF8 --locale=C'
docker exec -u postgres pg72 sh -c 'pg_ctl -D /tmp/pgdata -l /tmp/pg.log \
  -o "-c listen_addresses=localhost -c unix_socket_directories=/run/postgresql" start'
docker exec -u postgres pg72 psql -X -q -c "SHOW TimeZone;"   # 预期：UTC
```

**可验**（本机真跑）：

| 检查项 | 期望值（本机实测） | 原始输出 |
|---|---|---|
| 6 时区 2026 非 24h 天数 | 10 天（23/23.5/24.5/25h） | `raw/a-zones.txt` |
| gap/overlap 候选数 | NY gap=0、NY overlap=2（差 3600s）、Lord Howe=2（差 1800s） | `raw/b2-resolve.txt` |
| 日切计数 | NY 11-01 = 100、UTC = 96 | `raw/c-daycut.txt` |
| PG 会话依赖 | 同字面量 → 09:00Z/14:00Z/01:00Z；`date_trunc` 分桶 6 vs 5+1 vs 1+5 | `raw/d-postgres.txt` |
| 裸容器 tzdata | 普通构建 3/3 失败，内嵌构建 3/3 成功 | `raw/e-tzdata.txt` |

**可退**（三个开关都要能在线切）：

| 退路 | 做法 | 代价 |
|---|---|---|
| tzdata 升级出问题 | 镜像固定 `tzdata=2026b-r0`；回滚只换基础镜像 tag | 丢失新政策，需补丁窗口内再升 |
| 口径或调度策略要改 | `business_tz` 放配置中心、`dst_policy=skip/shift/dup` 灰度；历史不重算、双口径落库比对 | 存储翻倍需对账；同一用户可能收到 0 或 2 次推送 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 日志/订单用本地时间字符串入库 | 同一字符串在 Go/PG/Node 得到两个瞬时（差 3600 s），跨系统排序错乱 |
| `TIMESTAMP` 列不设 session 时区就批量导入 | 导入机时区决定数据含义；实测 D1 差 5–13 小时 |
| 用 offset 或缩写代替 zone 存会议/活动 | 6 个月后差 1 小时（实测 G4）；`CST` 有 3 种偏移、PG 的 `pg_timezone_abbrevs` 里 CST 只有 −6（实测 F：`raw/f-abbr.txt`；D7） |
| 日报用 `date_trunc('day', ts)` 依赖 session | 同一批数据 UTC 6、上海 5+1、纽约 1+5（实测 D4） |
| 每天 09:00 用 `+24h` 推进 | 238 天钟面不是 09:00（实测 G1） |
| 定时任务落进 gap/overlap 不声明策略 | 一年少触发 1 次或多触发 1 次（364/365、365/366）；压缩镜像删掉 tzdata 则 `LoadLocation` 全失败（实测 E） |

## 三条铁律

> 🔑 **instant 一律存 UTC（数据库用 `timestamptz` 或 epoch），墙钟时间必须带 IANA zone id；offset 只是渲染结果，不能当存储语义。**

> 🔑 **"一天"由业务时区决定，不由 86400 秒决定；DST 日是 23/25 小时，所有日报、配额、签到、账期都要显式声明口径。**

> 🔑 **tzdata 是随发布走的依赖：锁版本、写进镜像、把 DST 日期写进回归用例；升级要能回退，审计要记版本。**

## 自检

**Q1** 用户在纽约预约"2026-03-08 02:30"，Go 后端收到这个墙钟后会发生什么？怎么处理才对？

▸ 答案：这个墙钟在 America/New_York 不存在；`time.Date` 会返回 **01:30 EST**（06:30Z），Node/PG 会返回 **03:30 EDT**（07:30Z）。正确做法：先用 `ZoneBounds` 采样算候选（返回 0 个候选），再按显式策略拒绝或顺延到 03:00，并把选择写进接口返回文案；不接受静默规范化。

**Q2** `timestamptz` 和 `timestamp` 都存 `2026-01-15 09:00`，为什么前者"更安全"？

▸ 答案：`timestamptz` 存的是 UTC 瞬时（09:00/14:00/01:00Z 由插入时会话决定，之后按 session 显示）；`timestamp` 永远存那串数字，语义完全靠外部约定。用 `timestamptz` 时"排序、比较、跨系统传输"不受显示时区影响；但字面量解析仍受 session 影响，所以写入必须带偏移或显式 `SET TIME ZONE`（实测 D1）。

**Q3** 老板说"日报统一按天"，为什么必须先问"哪天"？

▸ 答案：同一批 144 笔订单按 UTC/上海/纽约聚合是 24/72/48、0/72/72、36/75/33（实测 C4），极差 42–72 笔；而且 DST 日不是 24 小时（23/25h，实测 A/C/D），按秒数分桶会在切换日多算/少算 1 小时。先定口径（UTC 日 / 用户时区日 / 总部时区日）再写 SQL。

**Q4** 每天 09:00 给全球用户推送，能不能写一条 cron？

▸ 答案：不能。cron 用守护进程本地时区（实测容器里 `* * * * *` 写出 `05:45 EST`），Kubernetes CronJob 不写 `.spec.timeZone` 也按 controller-manager 本地时区。做法是调度表存 `(zone, local_time, dst_policy)`，按 zone 批量算下一次 UTC 触发；且不能用 `+24h` 推进——实测一年 238 天钟面偏 1 小时。

**Q5** 同一个服务在本地 macOS 上跑得好好的，一进裸 alpine 容器 `LoadLocation` 全部失败；换镜像后 2027 年的 DST 预测又悄悄变了。根因是什么、怎么防？

▸ 答案：因为 tzdata 是运行时依赖而不是常量：裸 alpine 没有 `/usr/share/zoneinfo`，代码再对也 `unknown time zone`（Go 静态编译不解决），可以 `-tags timetzdata` 内嵌（体积 +397 200 字节 ≈ +16.7%）或显式装包、固定基础镜像。不同版本 tzdata 对未来的预测不同，同一瞬时最多 10 个时区名偏移不一样，所以必须锁版本、写进镜像、把 DST 日期写进回归用例，升级要能回退、审计要记版本。
