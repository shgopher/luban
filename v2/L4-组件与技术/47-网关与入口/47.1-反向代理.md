# 47.1 反向代理

## 一句话

> 反向代理是“代表后端接收请求”的那一层：它终结 TLS、做路由与负载均衡、缓冲、限流、注入可观测信息；价值在于把横切关注点从业务里拿出来，风险在于**多了一跳，就多了一个超时、缓冲与连接池的失效点**。

## 它到底替后端做了什么

| 职责 | 具体动作 | 不做会怎样 |
|---|---|---|
| TLS 终结 | 证书管理、握手、HTTP/2 协商 | 每个服务都要管证书与握手 CPU |
| 路由 | 按 host/path/header 分发 | 后端要暴露多个端口，客户端感知拓扑 |
| 负载均衡 | 轮询/最少连接/一致性哈希 | 单实例打满，其它闲着 |
| 缓冲 | 收完请求再转发、收完响应再回传 | 慢客户端拖住后端连接 |
| 压缩 | gzip/br、按 `Accept-Encoding` 协商 | 带宽浪费、首屏变慢 |
| 限流/鉴权 | 入口统一拦截 | 每个服务重复实现 |
| 可观测 | access log、trace id、上游耗时 | 出问题只能猜 |

> 🔑 反向代理是**唯一能看到“完整请求生命周期”的地方**：客户端 IP、TLS 版本、上游耗时、响应大小都在这里。所以它是可观测性最好的埋点位置，也是最容易被塞进过多逻辑的地方（塞多了就变成 ESB 反模式）。

## 四层还是七层

| 维度 | 四层（L4） | 七层（L7） |
|---|---|---|
| 看得到 | IP/端口/TCP 标志 | HTTP 方法、路径、头、Cookie |
| 转发依据 | 五元组 | 路径/header/权重 |
| 性能 | 更高（不改写、不解析） | 低一些（解析 + 可能的缓冲） |
| 典型 | LVS、NLB、IPVS | Nginx、Envoy、HAProxy、网关 |
| 适合 | 数据库代理、大流量 TCP、需要保留客户端行为 | HTTP API、灰度、鉴权、限流 |

生产上常见“L4 在前 + L7 在后”：L4 扛连接数与 DDoS，L7 做业务路由。L4 看不到 HTTP，所以限流与灰度只能放在 L7。

## 数字一：轮询在“慢节点”面前会崩

4 台后端：3 台 300 QPS、1 台只有 150 QPS（慢节点）。负载 1000 QPS 持续 10 秒：

| 策略 | 最大等待 | 慢节点最终队列 | 超过 200ms 的请求 |
|---|---|---|---|
| 轮询 | **6664ms** | 1000 | 2425 / 10000 |
| 最少连接 | **1ms** | 0 | 0 |
| 两次随机取优（P2C） | 40ms | 2 | 0 |

轮询把 25% 的流量（250 QPS）固定压给只能处理 150 QPS 的节点，队列每秒涨 100 条，10 秒后积压 1000 条、等待 6.6 秒——**一台慢节点拖垮了整个入口的 P99**。

| 策略 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| 轮询 | 简单、均匀 | 无视负载，慢节点必崩 | 后端完全同质 |
| 最少连接 | 自动避开慢节点 | 需要维护计数；突增时抖动 | 请求耗时差异大 |
| P2C（两次随机取优） | 接近最少连接，无需全局状态 | 略差于最优 | 大规模、分布式决策 |
| 一致性哈希 | 缓存命中率高 | 节点变化导致倾斜 | 有状态/缓存场景 |
| 加权 | 按容量分配 | 权重需人工维护 | 异构机器 |

**最少连接的实现细节**：统计的是“在途请求数”而不是“连接数”。开了 keep-alive 或 HTTP/2 后，一条连接上可能同时有多个请求，只数连接会失真（HTTP/2 下连接数几乎恒定，最少连接退化成轮询）。

## 数字二：不复用连接，握手就吃掉并发

10 万 QPS、RTT 0.5ms：

```
不复用：每秒 10 万次 TCP 握手，≈ 50 个连接同时处于“握手中”
复用：每后端 200 条长连接 → 握手只发生 800 次；代理连接池上限 = 800 在途
```

TLS 还要再加 2 个 RTT（1.0 RTT 的 TLS 1.3 也至少 1 RTT），握手开销翻倍。所以代理到上游必须开 keep-alive，并且**连接池大小要 ≥ 并发 × 余量**：池子太小，请求在代理内部排队；池子太大，上游连接数暴涨。

> ⚠️ **代理的 idle timeout 必须大于上游的 keepalive timeout**。如果上游 60s 关连接、代理 75s 才回收，中间 15s 里的请求会拿到一个“已被对端关闭”的连接，表现为偶发 502——这类问题极难复现，因为只发生在时间窗口内。

## 缓冲：不是所有响应都能缓冲

| 类型 | 缓冲 | 原因 |
|---|---|---|
| 普通 JSON | 开 | 慢客户端不占后端连接 |
| 大文件下载 | 关（或限流） | 缓冲会把内存打满 |
| SSE / 长轮询 | **关** | 缓冲会让事件延迟到连接关闭才发出 |
| WebSocket | 不适用（升级后是隧道） | 需要 `Upgrade`/`Connection` 头透传 |
| 流式 gRPC | 关 | 同 SSE |

Nginx 的 `proxy_buffering off`、Envoy 的 `buffer` 配置都是这个开关。**缓冲的收益是“隔离慢客户端”，代价是“内存 + 首字节延迟”**，按响应类型分别配置，不要全局开或全局关。

## 头部：三个必须处理的点

| 头 | 正确做法 | 错误做法 |
|---|---|---|
| `X-Forwarded-For` | **追加**客户端 IP 到已有链 | 覆盖（丢失原始 IP） |
| `X-Forwarded-Proto` | 设为 `https`（TLS 在代理终结） | 不设，后端以为是 http，重定向成 http |
| `Forwarded`（标准） | 按 RFC 7239 格式 | 只支持 XFF，跨厂商不兼容 |
| hop-by-hop 头 | **删除** `Connection`、`Keep-Alive`、`Transfer-Encoding`、`Upgrade`（除升级场景） | 原样透传，导致上游解析错误 |
| `Host` | 按上游需要改写或保留 | 盲目透传，后端虚拟主机匹配失败 |

安全相关：**只信任来自已知代理的 XFF**。如果直接信任客户端传来的 `X-Forwarded-For`，攻击者可以伪造 IP 绕过限流与风控。

## 超时：三层，缺一不可

| 超时 | 含义 | 典型值 | 缺了会怎样 |
|---|---|---|---|
| connect | 与上游建连 | 1–3s | 后端宕机时请求挂住 |
| read/response | 等上游首字节/完整响应 | 按接口 P99 的 2–3 倍 | 慢接口占满代理 worker |
| idle | 长连接空闲 | 60–75s（> 上游 keepalive） | 半开连接、偶发 502 |

代理的超时要**小于上游调用方的超时**，否则调用方先放弃、代理还在等，白白占用连接（见 [35.5 超时、重试与退避](../../L3-质量属性/35-可用性/35.5-超时重试与退避.md)）。

## 重试：只在“连接没建起来”时安全

| 场景 | 能否重试 | 原因 |
|---|---|---|
| 连接被拒绝/建连超时 | 可以（幂等时） | 请求没发出去 |
| 上游返回 503 | 可以（有上限） | 通常表示过载，重试要配合预算 |
| 响应超时 | **谨慎** | 请求可能已执行 |
| POST 非幂等 | **不要** | 重复下单/扣款 |

代理层的重试会放大流量，必须配重试预算（见 [35.5 超时、重试与退避](../../L3-质量属性/35-可用性/35.5-超时重试与退避.md)）。很多线上事故的根因就是“代理默认重试 3 次 + 上游超时 5s”，故障时流量翻 3 倍。

## 可运行的负载均衡仿真

```go
package main

import (
	"fmt"
	"math/rand"
)

type backend struct {
	capPerMs float64 // 每毫秒能处理多少请求
	q        float64 // 当前排队
	maxQ     float64
}

func (b *backend) process() {
	b.q -= min(b.q, b.capPerMs)
}

func main() {
	// 4 台后端：3 台 300 QPS，1 台只有 150 QPS（慢节点）
	mk := func() []*backend {
		return []*backend{{300.0 / 1000, 0, 0}, {300.0 / 1000, 0, 0}, {300.0 / 1000, 0, 0}, {150.0 / 1000, 0, 0}}
	}
	const durationMs = 10_000 // 10 秒，每秒 1000 请求
	rnd := rand.New(rand.NewSource(7))

	type result struct {
		name    string
		maxWait float64 // ms
		slowQ   float64
		slowMax float64
		over200 int
	}
	var results []result

	policies := []string{"轮询", "最少连接", "两次随机取优"}
	for _, policy := range policies {
		bs := mk()
		rr, over200 := 0, 0
		var maxWait float64
		for ms := 0; ms < durationMs; ms++ {
			var idx int
			switch policy {
			case "轮询":
				idx = rr % len(bs)
				rr++
			case "最少连接":
				idx = 0
				for i := 1; i < len(bs); i++ {
					if bs[i].q < bs[idx].q {
						idx = i
					}
				}
			case "两次随机取优":
				a, b := rnd.Intn(len(bs)), rnd.Intn(len(bs))
				idx = a
				if bs[b].q < bs[a].q {
					idx = b
				}
			}
			b := bs[idx]
			wait := b.q / b.capPerMs // 预计排队等待时间
			if wait > maxWait {
				maxWait = wait
			}
			if wait > 200 {
				over200++
			}
			b.q++
			if b.q > b.maxQ {
				b.maxQ = b.q
			}
			for _, x := range bs {
				x.process()
			}
		}
		results = append(results, result{policy, maxWait, bs[3].q, bs[3].maxQ, over200})
	}

	fmt.Printf("%-14s %10s %10s %8s %12s\n", "策略", "最大等待", "慢节点队列", "队列峰值", ">200ms 请求")
	for _, r := range results {
		fmt.Printf("%-14s %8.0fms %9.0f %9.0f %10d/10000\n", r.name, r.maxWait, r.slowQ, r.slowMax, r.over200)
	}

	// 连接复用：10 万 QPS 时短连接与长连接的握手成本
	qps, rttMs := 100_000.0, 0.5
	fmt.Printf("\n上游连接：%.0f 万 QPS，每次新建连接要 1 个 RTT（%.1fms）做 TCP 握手，TLS 再加 2 RTT\n",
		qps/10000, rttMs)
	fmt.Printf("   不复用：每秒 %.0f 万次握手 ≈ %.0f 个连接同时处于握手中\n",
		qps/10000, qps*rttMs/1000)
	const perBackend, backs = 200, 4
	fmt.Printf("   复用（每后端 %d 条长连接）：握手只发生 %d 次；代理自身的连接池上限 = %d 在途\n",
		perBackend, perBackend*backs, perBackend*backs)
}
```

输出：

```
策略                   最大等待      慢节点队列     队列峰值    >200ms 请求
轮询                 6664ms      1000      1001       2425/10000
最少连接                  1ms         0         1          0/10000
两次随机取优               40ms         2         7          0/10000

上游连接：10 万 QPS，每次新建连接要 1 个 RTT（0.5ms）做 TCP 握手，TLS 再加 2 RTT
   不复用：每秒 10 万次握手 ≈ 50 个连接同时处于握手中
   复用（每后端 200 条长连接）：握手只发生 800 次；代理自身的连接池上限 = 800 在途
```

## 参数怎么给

| 你的场景 | 配置重点 |
|---|---|
| 常规 HTTP API | 七层代理 + 最少连接/P2C + keep-alive + 缓冲开 |
| 大文件下载/视频 | 缓冲关、限速、range 透传、超时放宽 |
| SSE/WebSocket | 升级头透传、缓冲关、idle 超时按心跳定 |
| 灰度发布 | 按 header/cookie/权重路由，保留回切开关 |
| 多租户入口 | 按 host 路由 + 每租户限流（[35.7 限流](../../L3-质量属性/35-可用性/35.7-限流.md)） |
| 内部服务互调 | L4 或 sidecar，避免多层代理叠加 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 轮询分发到异构/慢节点 | 慢节点积压，P99 被一台机器拖垮 |
| 只数连接不数在途请求 | HTTP/2 下最少连接退化成轮询 |
| 代理 idle 超时 < 上游 keepalive | 偶发 502，且只在时间窗口内复现 |
| 全局开响应缓冲 | 大文件打满内存，SSE 事件延迟 |
| 无条件透传客户端 XFF | 伪造 IP 绕过限流/风控 |
| 透传 hop-by-hop 头 | 上游解析错误、连接复用异常 |
| 代理层默认重试 3 次 | 故障时流量 ×3，雪崩加速 |
| 在代理里写业务逻辑 | 变成 ESB，改一次配置影响全站 |
| 上下游都设超时但没有预算关系 | 上游先放弃、下游还在跑，资源浪费 |
| 健康检查只探端口 | 进程活着但依赖全挂，流量照打 |

## 自检

**Q1** 4 台后端里 1 台只有一半性能，轮询策略下最大等待 6.6 秒、2425 个请求超过 200ms。为什么“平均分配”会造成这么严重的后果？

▸ 答案：轮询分配的是**请求数**，不是**处理能力**。慢节点每秒只能处理 150 个，却被分到 250 个，每秒净积压 100 个；队列在 10 秒内涨到 1000，等待时间 = 队列 / 处理速率 = 1000/0.15 ≈ 6.6 秒。而且积压是**单向恶化**的：等待越久，客户端越可能超时重试，流量进一步增加。最少连接/ P2C 通过“看过载信号”把流量移走，等待回到毫秒级。

**Q2** 最少连接在 HTTP/2 场景下为什么会退化成轮询？怎么修？

▸ 答案：最少连接统计的是“连接数”时，HTTP/2 的多路复用让每条连接长期存在、承载的流数量不同但连接数恒定，于是所有后端“连接数”都一样，选择退化成轮询。修法是统计**在途请求数（in-flight streams）**而不是连接数：Envoy 的 `least_request` 用 `active_requests`，Nginx 的 `least_conn` 在 HTTP/2 下需要注意版本行为。另一个办法是用 P2C + 在途数，天然适配多路复用。

**Q3** 上游 60 秒关空闲连接、代理 75 秒才回收，会出现什么问题？为什么难查？

▸ 答案：在 60–75 秒这个窗口里，代理池里保留着**已被上游关闭**的连接，新请求复用它会立刻收到 RST，表现为偶发 502/连接重置。难查的原因：① 只在“连接空闲超过 60 秒又被复用”时触发，与请求内容无关；② 频率取决于流量波动，压测时可能完全复现不了；③ 日志里只有一个 502，没有“连接年龄”信息。修法：代理 idle timeout 小于上游 keepalive timeout（如 55s vs 60s），并开启上游连接的健康检查。

**Q4** 为什么代理层的自动重试很危险？什么情况下可以重试？

▸ 答案：代理的重试发生在“它不知道请求是否已执行”的位置——响应超时可能代表后端已经扣款成功。盲目重试会重复下单、重复发券；同时故障时重试会放大流量（3 次重试 = 3 倍压力），加速雪崩。可以重试的情况：连接被拒绝/建连失败（请求肯定没发出去）、幂等请求（GET/PUT）、上游明确返回 503 且带重试预算。安全做法是把重试决策交给知道幂等语义的调用方，代理只做“连接级”重试。

**Q5** 反向代理和 API 网关的边界在哪？什么时候不该再加一层代理？

▸ 答案：反向代理解决“传输与分发”（TLS、路由、LB、缓冲、压缩），API 网关在此之上加“API 治理”（鉴权、配额、协议转换、版本、开发者门户）。每加一层代理就多一次网络跳转、一套超时/连接池/证书配置，以及一个故障点；如果只是为了“统一加个 header”，用 sidecar 或库更划算。判断标准：这一层是否承担了**独立于业务的横切职责**，且能被多个服务复用；如果只有一两个服务用，就不值得加。
