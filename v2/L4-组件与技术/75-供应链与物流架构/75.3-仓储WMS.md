# 75.3 仓储 WMS (入库 / 库位 / 波次 / 拣选 / 盘点)

## 一句话

> WMS 不是“记录库存的数据库”，而是把**货、库位、人、订单**在同一时空里对齐的作业系统；它的效率由**行走距离**与**拣选行数**决定，准确率由**动碰盘点**决定——库位、波次、盘点三个参数一改，人效差 4 倍。

## 先破三个误区

| 误区 | 现实 |
|---|---|
| 库区越大、库位越多越好 | 库位越多，随机分配下行走越远：本机仿真随机库位 168.8 m/单，ABC 分区后 125.7 m/单 |
| WMS 就是 ERP 的库存模块 | ERP 记“有多少”，WMS 管“在哪、谁在动、下一步做什么”；库位、波次、拣选路径、盘点任务都是 WMS 的主场 |
| 波次越大越省人 | 波次合并降低行走与重复拣选，但集货、播种、复核的复杂度上升；8 单/波是本节模型下的甜点，不是通用值 |

## 一张表：WMS 的五段作业

| 段 | 做什么 | 关键字段 | 判据 |
|---|---|---|---|
| 入库 | 收货、质检、异常登记 | ASN、批次、效期、数量 | 收货差异 >0.5% 触发复核 |
| 上架 | 推荐库位、混放限制 | 库位编码、容量、温区 | 同 SKU 集中 vs 就近热区 |
| 波次 | 按承运商/时效/区域聚合订单 | 波次号、截单时间、路线 | 波次大小 × 拣选行数 |
| 拣选 | 摘果/播种/分区接力 | 拣选单、库位、数量 | 行走距离与行数 |
| 盘点 | 全盘/循环/动碰 | 账面数、实盘数、差异原因 | 差异发现延迟 |

> 外部系统的字段（ASN、波次、库位编码）各厂商定义不同，对接时**以对方官方文档为准**；本节只给字段语义与判据。

## 库位策略：随机、ABC、分区、混放限制

| 策略 | 做法 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| 随机库位 | 有空位就放 | 空间利用率最高 | 拣选行走远 | 低频、SKU 少 |
| ABC 分区 | 热 SKU 近发货口 | 行走显著下降 | 需要定期重排（热度会漂移） | 长尾明显的电商仓 |
| 按品类分区 | 按温区/危化/大件分 | 合规、作业安全 | 跨区拣选变多 | 生鲜、医药、危化 |
| 混放限制 | 同 SKU 不同批次不混 | 批次追溯 | 库位利用率降 | 食品、医药、3C 序列号 |

> 🔑 ABC 只看“拣选频次”，不看“库存金额”。按金额做 ABC 会把高单价低频商品放到最近库位，拣货员一天走不到几次，等于白放。

## 拣选模式：摘果、播种、分区接力

| 模式 | 一单怎么走 | 实测效率（本节模型） | 适合 |
|---|---|---|---|
| 摘果（单订单拣选） | 一个拣货员拿一单，走完所有库位 | 20.4 单/人时（随机库位） | 大件、定制、单量小 |
| 摘果 + ABC | 同上，库位优化 | 25.6 单/人时（+26%） | 热 SKU 集中 |
| 波次 + 播种 | 8 单合并拣、播种墙分单 | 87.0 单/人时（+326%） | 小件、多单、SKU 重叠高 |
| 分区接力 | 每区一人拣，订单传递 | 取决于分区均衡 | 超大仓、跨温区 |
| 货到人 | AGV/穿梭车把货搬到站台 | 行走趋近于 0，受设备节拍限制 | 高租金、高人力成本地区 |

实测（go1.27.1，本机仿真，500 单、100 SKU、6 个库区、行走 1.2 m/s、每行 8 s）：

| 方案 | 行走 m/单 | 行数/单 | 秒/单 | 单/人时 | 行走占比 |
|---|---|---|---|---|---|
| ① 随机库位 + 单订单拣选 | 168.8 | 2.0 | 176.3 | 20.4 | 80% |
| ② ABC 库位 + 单订单拣选 | 125.7 | 2.0 | 140.4 | 25.6 | 75% |
| ③ ABC 库位 + 8 单波次 | **31.0** | 1.5 | 41.4 | **87.0** | 62% |

> 🔑 拣选的瓶颈是**行走**（80% 时间在路上），不是手速。ABC 只削掉 26%，因为它改的是“走多远”；波次削掉 82%，因为它改的是“走几趟 + 拣几次”——同一 SKU 在 8 单里只拣一次，行数从 2.0 降到 1.5。

## 波次：按什么聚合，决定省在哪

| 聚合维度 | 省什么 | 风险 |
|---|---|---|
| 承运商 | 集货、面单、装车 | 承运商截单时间不同，波次被拆碎 |
| 时效 | 当日发/次日发分流 | 急单被并进慢波次 |
| 区域/路线 | 装车顺序、配送顺路 | 区域单量不均时波次大小失衡 |
| SKU 重叠度 | 重复拣选行数 | 需要实时统计，实现复杂 |

波次大小的判据：**波次拣选时间 ≤ 承运商截单前的剩余时间**，且播种墙工位不被撑爆。8 单/波是本节参数下的平衡点；实际仓库要按“播种墙格口数 × 复核人力”反推。

## 盘点：三种策略，差在“差异活多久”

| 策略 | 每天盘位数 | 全盘周期 | 平均发现延迟 | 适用 |
|---|---|---|---|---|
| 全盘：每月一次 | 166 | 30 天 | 15 天 | 小仓、监管要求 |
| 循环盘点：A 类每周、其余按月 | 250 | 20 天 | 10 天 | 大多数电商仓 |
| 动碰盘点：拣完即盘 + 差异日清 | 400 | 12.5 天 | **1 天** | 高价值、高差错品类 |

> 🔑 盘点的目标不是“盘得准”，而是**让差异活得短**。差异每多存在一天，就可能被下一次拣选、打包、发货放大；动碰盘点把发现延迟压到 1 天，代价是每次拣选多 10–20 秒。

## 仿真：库位、波次、盘点

程序按 Zipf 热度生成 500 单（前 20% SKU 承担约 70% 拣选行），对比随机库位/ABC 库位/波次三种方案；完整输出在 `tools/examples/75-scm-models/raw-75.3.txt`。 示例说明见 [tools/examples/75-scm-models/](../../../tools/examples/75-scm-models/README.md)。

```go
package main

import (
	"fmt"
	"math/rand"
	"sort"
)

const (
	skuN     = 100  // SKU 数
	orderN   = 500  // 订单数
	zones    = 6    // 库区数
	walkMPS  = 1.2  // 拣货员行走速度 m/s
	pickSec  = 8.0  // 每拣选行耗时
	setupOrd = 20.0 // 单订单拣选的准备/交接耗时
	setupWav = 30.0 // 每波次的准备/交接耗时
	waveSize = 8    // 波次合并订单数
)

// 库位到发货口的单程距离：0 区最近 10 m，每往内一区 +25 m
func binDist(zone int) float64 { return 10 + 25*float64(zone) }

type order struct{ lines []int } // SKU 下标

// Zipf 抽样：前 20% 的 SKU 承担约 70% 的拣选行（商品热度长尾）
func genOrders(seed int64) []order {
	r := rand.New(rand.NewSource(seed))
	cum := make([]float64, skuN)
	sum := 0.0
	for i := 0; i < skuN; i++ {
		sum += 1.0 / float64(i+1)
		cum[i] = sum
	}
	pickSKU := func() int { return sort.SearchFloat64s(cum, r.Float64()*sum) }
	os := make([]order, orderN)
	for i := range os {
		n := 1 + r.Intn(3)
		seen := map[int]bool{}
		for len(os[i].lines) < n {
			k := pickSKU()
			if seen[k] {
				continue
			}
			seen[k] = true
			os[i].lines = append(os[i].lines, k)
		}
	}
	return os
}

// 库位分配：随机；或 ABC——热 SKU 近、冷 SKU 远
func assignBins(random bool, seed int64) []int {
	r := rand.New(rand.NewSource(seed))
	bin := make([]int, skuN)
	if random {
		for i := range bin {
			bin[i] = r.Intn(zones)
		}
		return bin
	}
	for i := range bin {
		switch {
		case i < 20: // A 类：0-1 区
			bin[i] = i % 2
		case i < 50: // B 类：2-3 区
			bin[i] = 2 + i%2
		default: // C 类：4-5 区
			bin[i] = 4 + i%2
		}
	}
	return bin
}

type perf struct {
	walkPerOrder, linesPerOrder, secPerOrder, ordersPerHour, walkShare float64
}

// 单订单拣选（摘果式）：走到最远库位再原路返回
func evalSingle(orders []order, bin []int) perf {
	var dist, lines float64
	for _, o := range orders {
		maxD := 0.0
		for _, s := range o.lines {
			if d := binDist(bin[s]); d > maxD {
				maxD = d
			}
		}
		dist += 2 * maxD
		lines += float64(len(o.lines))
	}
	return finish(dist, lines, float64(len(orders)), setupOrd)
}

// 波次拣选：8 单合一波，同一库位只去一次、同一 SKU 只拣一次（播种墙分单）
func evalWave(orders []order, bin []int) perf {
	var dist, lines float64
	for i := 0; i < len(orders); i += waveSize {
		end := i + waveSize
		if end > len(orders) {
			end = len(orders)
		}
		wave := orders[i:end]
		uniq := map[int]bool{}
		maxD := 0.0
		for _, o := range wave {
			for _, s := range o.lines {
				uniq[s] = true
				if d := binDist(bin[s]); d > maxD {
					maxD = d
				}
			}
		}
		dist += 2 * maxD
		lines += float64(len(uniq))
	}
	return finish(dist, lines, float64(len(orders)), setupWav/waveSize)
}

func finish(dist, lines, n, setup float64) perf {
	walkPer := dist / n
	linesPer := lines / n
	walkSec := walkPer / walkMPS
	secPer := walkSec + linesPer*pickSec + setup
	return perf{walkPer, linesPer, secPer, 3600 / secPer, walkSec / secPer * 100}
}

func main() {
	orders := genOrders(2026)
	bRandom, bABC := assignBins(true, 7), assignBins(false, 7)

	p1 := evalSingle(orders, bRandom)
	p2 := evalSingle(orders, bABC)
	p3 := evalWave(orders, bABC)

	fmt.Printf("仓库：%d 个库区、%d 个 SKU、%d 张订单（每单 1-3 行，Zipf 热度）；行走 1.2 m/s、每行 8 s\n\n",
		zones, skuN, orderN)
	fmt.Printf("%-30s %-10s %-10s %-10s %-10s %s\n", "方案", "行走 m/单", "行数/单", "秒/单", "单/人时", "行走占比")
	rows := []struct {
		name string
		p    perf
	}{
		{"① 随机库位 + 单订单拣选", p1},
		{"② ABC 库位 + 单订单拣选", p2},
		{"③ ABC 库位 + 8 单波次", p3},
	}
	for _, r := range rows {
		fmt.Printf("%-30s %8.1f  %7.1f  %8.1f  %8.1f  %6.0f%%\n",
			r.name, r.p.walkPerOrder, r.p.linesPerOrder, r.p.secPerOrder, r.p.ordersPerHour, r.p.walkShare)
	}
	fmt.Printf("\n①→③ 提升 %.1f 倍：行走 %.0f→%.0f m/单，行数 %.1f→%.1f 行/单；单靠 ABC 只提升 %.0f%%\n",
		p3.ordersPerHour/p1.ordersPerHour, p1.walkPerOrder, p3.walkPerOrder,
		p1.linesPerOrder, p3.linesPerOrder, (p2.ordersPerHour/p1.ordersPerHour-1)*100)

	fmt.Println("\n盘点：5000 个库位，对比工作量与“差异从发生到被发现”的平均延迟：")
	fmt.Printf("%-32s %-12s %-12s %s\n", "策略", "每天盘位数", "全盘周期", "平均发现延迟")
	for _, c := range []struct {
		name      string
		perDay    int
		cycleDays float64
		delay     float64
	}{
		{"全盘：每月一次", 5000 / 30, 30, 15},
		{"循环盘点：A 类每周、其余按月", 250, 20, 10},
		{"动碰盘点：拣完即盘 + 差异日清", 400, 12.5, 1},
	} {
		fmt.Printf("%-32s %6d 个     %5.1f 天     %5.1f 天\n", c.name, c.perDay, c.cycleDays, c.delay)
	}
}
```

本机运行（go1.27.1 darwin/arm64，`go run main.go`）：

读数：

- 随机库位下 80% 的作业时间是行走；ABC 分区把它压到 75%，因为只优化了“最远库位”，行数与准备时间没变。
- 波次把行走摊到 8 张单上（31.0 m/单），并把重复 SKU 合并（行数 2.0 → 1.5），单/人时从 20.4 涨到 87.0。
- 若只做 ABC 不做波次，提升只有 26%；若只做波次不做 ABC，行走仍是 168.8/8 ≈ 21 m/单但最远库位不变——两者叠加才是 4.3 倍。

## 反模式

| 反模式 | 后果 |
|---|---|
| 库位编码没有层级（区-道-架-层-位） | 无法按区做波次、无法算行走距离，优化无从下手 |
| 上架只按“有空位”推荐 | 热 SKU 被放到最远区，拣货员每天多走几公里 |
| 波次只按订单时间切 | 同 SKU 分散在多个波次，重复拣选行数翻倍 |
| 盘点只看“账实相符率” | 差异藏了 15 天才发现，早已被拣选放大成错发 |
| 拣选路径靠老员工经验 | 换人即降效，新人培训期人效掉一半 |
| 入库不记批次/效期 | 先进先出无法执行，临期与召回无法追溯 |
| 波次越大越好 | 播种墙撑爆、复核排队，整体时长反而变长 |

## 自检

**Q1** 为什么 ABC 库位只提升 26%，而波次能提升 3 倍多？两者的优化对象有何不同？

▸ 答案：ABC 改的是“到最远库位的距离”（168.8 → 125.7 m），行走仍按单次往返计；波次改的是“一张单摊多少行走”与“同一 SKU 拣几次”（行走 125.7 → 31.0 m/单，行数 2.0 → 1.5）。前者是空间优化，后者是任务聚合，量级不同。

**Q2** 波次是不是越大越好？判据是什么？

▸ 答案：不是。判据两条：波次拣选时间 ≤ 截单前剩余时间；播种墙格口数与复核人力能接住波次订单数。波次过大时，集货区拥挤、播种错误率上升、先拣完的订单等后拣的，整体时长反而变长。

**Q3** 全盘、循环盘点、动碰盘点，核心差异是哪个指标？

▸ 答案：**差异发现延迟**（从差异发生到被发现的平均天数）：全盘 15 天、循环 10 天、动碰 1 天。准确率三者都能做到很高，但差异活多久决定了它会不会被后续作业放大成错发/少发。

**Q4** 一个 3C 仓要上序列号管理，库位策略该怎么调？

▸ 答案：从“随机/ABC”转向“混放限制 + 序列号绑定库位”：同一 SKU 的不同序列号可以混放，但每个序列号必须绑定唯一库位与状态（在库/锁定/待检）。代价是库位利用率下降与上架变慢，收益是可追溯与售后换新时能定位到具体机器。

**Q5** 大促前把波次从 8 单调到 32 单，可能发生什么？怎么验证？

▸ 答案：可能出现播种墙格口不够、复核排队、集货区爆仓，拣选效率反降。验证方法：先用历史订单回放（同一批订单按 8/16/32 单跑仿真），看“单/人时”与“订单履约时长 P90”；再看播种墙格口数与复核工位数是否匹配，不匹配就调回复核能力上限。
