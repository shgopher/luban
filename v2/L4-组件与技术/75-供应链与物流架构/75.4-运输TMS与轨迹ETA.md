# 75.4 运输 TMS 与轨迹 ETA (承运商调度 / 轨迹 / 时效预测)

## 一句话

> TMS 不是“叫车软件”，而是把**承运商运力、轨迹事件、时效承诺**串成一张可调度、可预警、可结算的网；ETA 的价值不在“算得准”，而在**算得可解释、能随轨迹更新**——固定时效只能承诺 100.1 小时，轨迹更新后同样 95% 达成率只需 79.7 小时。

## 先破三个误区

| 误区 | 现实 |
|---|---|
| TMS = 物流下单系统 | 下单只占 10%；运力池、承运商比价、轨迹回传、时效预测、运费结算、异常理赔才是主体 |
| ETA 越准越好 | 精度只是手段；业务要的是“承诺时可兑现、运输中可预警、异常时可改约”，三者对应三个不同的数 |
| 轨迹 = GPS 打点 | 轨迹是**事件流**（揽收/发车/到分拨/派送/签收/异常），GPS 只是其中一种事件源；事件缺失比坐标漂移更致命 |

## 运输模式：先选模式，再谈调度

| 模式 | 时效 | 成本量级 | 追踪粒度 | 适用 |
|---|---|---|---|---|
| 快递 | 次日–3 天 | 首重 8–12 元 | 每节点扫描 | 小件、C 端 |
| 零担（快运） | 2–5 天 | 按重量/体积 | 分拨级 | 30 kg–3 t |
| 专线 | 3–7 天 | 最低 | 发车/到站 | 固定线路、大票 |
| 整车 | 按里程 | 整车计价 | GPS 全程 | 大批量、直送 |
| 同城即时配 | 1 小时–当日 | 按距离 | 骑手 GPS | 生鲜、O2O |

> 🔑 模式选择的判据是**单位重量成本 × 时效敏感度**：高价值小件选快递，低价值重货走专线，时效极敏感才用整车/即时配。模式选错，调度算法再优也救不回来。

## 计费：五种口径，结算时对不上就是资损

| 口径 | 算法 | 坑 |
|---|---|---|
| 首重 + 续重 | 首重价 + 续重价 × 向上取整重量 | 进位规则（0.5 kg 还是 1 kg）各家不同 |
| 体积重（抛重） | 长×宽×高 ÷ 6000（部分 5000） | 轻抛货按体积计，报价时容易漏算 |
| 分区计价 | 按目的地区间定价 | 同一城市不同区可能跨区 |
| 燃油/旺季附加 | 基础运费 × 附加率 | 附加率按月变，结算要按月取 |
| 最低一票 | max(计费重 × 单价, 最低收费) | 小件多发时最低收费吃掉利润 |

> 计费规则、重量进位、分区表各承运商不同，**以承运商官方计费文档为准**；系统要做的不是“算对一次”，而是把计费口径版本化，让对账能解释每一笔差异（见 [67.3 对账与差异处理](../67-交易与账务/67.3-对账与差异处理.md)）。

## 轨迹：状态机比坐标更重要

| 状态 | 触发事件 | 异常判据 |
|---|---|---|
| 已下单 | 面单生成 | 超 24h 未揽收 |
| 已揽收 | 揽收扫描 | 揽收后 48h 无干线路由 |
| 干线运输 | 发车/到站扫描 | 两节点间隔 > 历史 P95 |
| 派送中 | 到达派送点 | 派送超 24h 未签收 |
| 已签收 | 签收扫描 | 签收人与收件人不一致 |
| 异常 | 破损/丢件/拒收/地址异常 | 直接进工单与理赔流程 |

> 🔑 轨迹系统的核心指标不是“点密度”，而是**事件时效与缺失率**：一条 2 天没更新的轨迹，比 200 个漂移坐标更有信息量。车载终端的固件升级与断网续传见 [69.5 固件升级 (OTA)](../69-物联网/69.5-固件升级-OTA.md)、[69.4 边缘计算与断网续传](../69-物联网/69.4-边缘计算与断网续传.md)。

## ETA：三种算法，差在“用不用已发生的事实”

本机仿真 800 单、四段耗时（揽收/干线/分拨/末端），异常率设定 8%（实测 69/800 ≈ 8.6%）；历史校准集 2,000 单。

| 方法 | MAE | P90 误差 | 96h 承诺达成率 | 95% 达成所需承诺 | 超时预警召回 |
|---|---|---|---|---|---|
| M1 固定 4 日达（96h） | 30.8h | 45.0h | 94% | 100.1h | 0% |
| M2 下单时分段均值 | 10.9h | 21.1h | 94% | 100.1h | 0% |
| M3 分位初值 + 到分拨后更新 | **7.2h** | **13.1h** | 94% | **79.7h** | **50%** |

读数：

- M1 与 M2 的“95% 达成所需承诺”都是 100.1h：只要预测是**常量或近似常量**，95% 承诺就被实际值的尾部（异常延误）绑架，换成均值也没用。
- M3 在到达分拨中心后用“已发生的揽收 + 干线实际耗时 + 剩余段 P50”更新，MAE 降到 7.2h、P90 降到 13.1h，95% 承诺缩短 20.4 小时。
- 预警召回 50%：干线异常能提前识别，分拨之后的异常识别不了——**ETA 对可观测的延误有效，对不可观测的异常只能兜底**。

> 🔑 ETA 的工程重点不是模型，是**分段与更新点**：把运输拆成可独立观测的段，每到一个节点就用实际值替换预测值，剩余段用历史分位数而非均值。没有轨迹事件，再好的模型也只能输出一个常数。

## 仿真：固定时效、分段均值、轨迹更新

程序用固定种子生成 800 单并对齐校准集，训练/测试同一分布；完整输出在 `tools/examples/75-scm-models/raw-75.4.txt`。 示例说明见 [tools/examples/75-scm-models/](../../../tools/examples/75-scm-models/README.md)。

```go
package main

import (
	"fmt"
	"math"
	"math/rand"
	"sort"
)

// 一单的四段耗时（小时）：揽收 → 干线 → 分拨 → 末端
type segs struct{ pick, line, hub, last float64 }

func (s segs) total() float64 { return s.pick + s.line + s.hub + s.last }

// 8% 的包裹遇异常：6 成发生在干线、4 成发生在分拨，额外 24-72h
func sampleShipment(r *rand.Rand) (segs, bool) {
	s := segs{
		pick: 4 + r.Float64()*8,
		line: 24 * (0.6 + r.Float64()*0.8),
		hub:  6 + r.Float64()*12,
		last: 8 + r.Float64()*22,
	}
	if r.Float64() < 0.08 {
		if r.Float64() < 0.6 {
			s.line += 24 + r.Float64()*48
		} else {
			s.hub += 24 + r.Float64()*48
		}
		return s, true
	}
	return s, false
}

func mean(a []float64) float64 {
	s := 0.0
	for _, v := range a {
		s += v
	}
	return s / float64(len(a))
}

func percentile(a []float64, p float64) float64 {
	b := append([]float64(nil), a...)
	sort.Float64s(b)
	i := int(math.Ceil(p/100*float64(len(b)))) - 1
	if i < 0 {
		i = 0
	}
	if i >= len(b) {
		i = len(b) - 1
	}
	return b[i]
}

func main() {
	// 校准集：2000 单历史，取分段均值与分位数
	rc := rand.New(rand.NewSource(1))
	var cp, cl, ch, cls []float64
	for i := 0; i < 2000; i++ {
		s, _ := sampleShipment(rc)
		cp, cl, ch, cls = append(cp, s.pick), append(cl, s.line), append(ch, s.hub), append(cls, s.last)
	}
	meanPick, meanLine := mean(cp), mean(cl)
	medianHub, medianLast := percentile(ch, 50), percentile(cls, 50)

	// 测试集：800 单
	r := rand.New(rand.NewSource(2026))
	n := 800
	actual := make([]float64, n)
	p1, p2, p3 := make([]float64, n), make([]float64, n), make([]float64, n)
	anomaly := 0
	for i := 0; i < n; i++ {
		s, bad := sampleShipment(r)
		if bad {
			anomaly++
		}
		actual[i] = s.total()
		p1[i] = 96 // 对外固定 4 日达
		p2[i] = meanPick + meanLine + percentile(ch, 50) + percentile(cls, 50)
		// 到分拨中心：揽收 + 干线已发生（实际值），分拨 + 末端按中位数估
		p3[i] = s.pick + s.line + medianHub + medianLast
	}

	fmt.Printf("测试集 800 单：实际送达平均 %.1fh（P90 %.1fh），其中 %d 单（%.0f%%）遇异常延误\n",
		mean(actual), percentile(actual, 90), anomaly, 100*float64(anomaly)/float64(n))
	fmt.Printf("历史校准：揽收 %.1fh / 干线 %.1fh / 分拨中位 %.1fh / 末端中位 %.1fh\n\n",
		meanPick, meanLine, medianHub, medianLast)

	names := []string{"M1 固定 4 日达（96h）", "M2 下单时分段均值", "M3 分位初值 + 到分拨后更新"}
	preds := [][]float64{p1, p2, p3}
	fmt.Printf("%-28s %-8s %-9s %-13s %-14s %s\n",
		"方法", "MAE", "P90误差", "96h达成率", "95%达成的承诺", "超时预警召回")
	for i, p := range preds {
		var ae, overshoot []float64
		hit96, tp, fn := 0, 0, 0
		for k := 0; k < n; k++ {
			e := p[k] - actual[k]
			ae = append(ae, math.Abs(e))
			overshoot = append(overshoot, actual[k]-p[k]) // 实际比预测晚多少
			if actual[k] <= 96 {
				hit96++
			}
			if p[k] > 96 && actual[k] > 96 {
				tp++
			}
			if p[k] <= 96 && actual[k] > 96 {
				fn++
			}
		}
		// 要 95% 达成，承诺 = 平均预测 + 历史“实际-预测”的 P95 缓冲
		buffer := percentile(overshoot, 95)
		promise := mean(p) + buffer
		fmt.Printf("%-28s %5.1fh  %6.1fh    %3.0f%%          %6.1fh        %3.0f%%\n",
			names[i], mean(ae), percentile(ae, 90), 100*float64(hit96)/float64(n),
			promise, 100*float64(tp)/float64(tp+fn))
	}
}
```

## 承运商调度：选商不是选价格

| 维度 | 怎么量化 | 权重示例 |
|---|---|---|
| 价格 | 同口径（含抛重、附加）单均成本 | 30% |
| 时效 | P90 送达时长，不是均值 | 30% |
| 准点率 | 承诺达成率（近 30 天） | 20% |
| 覆盖 | 目的地区域/品类/特殊件 | 10% |
| 异常处理 | 理赔时效、丢件率 | 10% |

调度策略：**主承运商 + 备承运商**按比例分流（如 70/30），既保价格谈判力，又保大促时的运力弹性；切换用“熔断 + 灰度”，避免单一承运商爆仓拖垮全量订单。按线路维度维护“价格—时效”矩阵，比按承运商维度维护更贴近实际决策。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用固定时效对外承诺 | 异常单必然迟到，客诉与赔付同时上升（本节 M1 误差 P90 45h） |
| ETA 用均值不更新 | 车辆已晚点 2 天，系统还显示“明天到” |
| 计费口径不版本化 | 每月对账都对不上，财务手动调账，差异越积越多 |
| 只按价格选承运商 | 便宜但准点率低，赔付与客诉成本远超省下的运费 |
| 轨迹只存 GPS 坐标 | 事件缺失无法判断卡在哪，预警与理赔都没有依据 |
| 单一承运商承载全量 | 承运商爆仓/停运时无备选，全量订单停摆 |
| 异常单不回流 ETA 模型 | 同类异常反复发生，预测永远乐观 |

## 自检

**Q1** 为什么 M1（固定 96h）和 M2（分段均值）的“95% 达成承诺”完全相同？

▸ 答案：两者对每一单的预测都是常量（96h 或分段均值），“95% 达成承诺 = 预测值 + P95(实际−预测)”。当预测为常量 c 时，承诺 = c + P95(实际) − c = P95(实际)，与 c 无关。换言之，预测不随实际进展变化，承诺就只能由实际值的尾部决定。

**Q2** M3 的 MAE 只有 7.2h，为什么超时预警召回仍然只有 50%？

▸ 答案：M3 在“到达分拨中心”这个节点更新，能看到的只有揽收与干线。异常若发生在分拨之后（分拨滞留、末端延误），更新时还没发生，预测自然抓不到。要提升召回，必须增加更新点（分拨出库、派送扫描）并采集异常事件。

**Q3** 为什么“分段”比“整车一个总时长”更准？

▸ 答案：分段把误差来源拆开：揽收受仓库截单影响、干线受距离与路况影响、分拨受爆仓影响、末端受派送密度影响。每段独立用历史分位数估计，且已发生的段可以用实际值替换；总时长模型只能给一个混合了四种波动的数，无法利用“已经走了多远”这一事实。

**Q4** 承运商报价 A 比 B 便宜 15%，但 A 的 P90 时效慢 1 天，怎么决策？

▸ 答案：把时效差折算成钱：慢 1 天带来的承诺时长增加（转化率损失）+ 超时赔付 + 客诉成本，再与 15% 运价对比。若货值低、时效不敏感（如补货、备件），选 A；若时效敏感（如预售、礼盒），选 B 或主 B 备 A。决策单位是“每条线路的边际成本”，不是“整体报价”。

**Q5** 轨迹显示“已揽收”后 72 小时没有新事件，系统该做什么？

▸ 答案：先按异常判据标记（超过历史 P95 间隔），自动生成工单并向承运商查询；同时把该单 ETA 下调为“不可信/待确认”，并触发客户侧通知模板。不要等客户来问——轨迹缺失本身就是最可靠的异常信号。
