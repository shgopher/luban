# 67.4 复式记账与账务模型

## 一句话

> 账务系统的地基不是“订单表”，而是**复式记账**：每笔资金变动至少两条分录，**有借必有贷、借贷必相等**；交易记录“发生了什么”，账务记录“钱从哪来到哪去”——两者用凭证号关联，永不互相覆盖。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 订单表就是账 | 订单是**交易单据**，账务是**资金事实**；退款、手续费、分账、差错补记，订单表都表达不了 |
| 单边记账够用 | 单边只能回答“这个账户变了多少”，回答不了“钱从哪来”——对账时无法定位 |
| 余额可以只靠流水累加 | 可以算，但必须有**独立校验**（期初 + 发生 = 期末、日终试算平衡），否则错了发现不了 |

> 💡 复式记账是会计学常识（卢卡·帕乔利 1494 年《算术、几何、比与比例概论》系统化），不是互联网发明；本节讲的是**它落到系统里长什么样**。阈值与经验值是我的判断，已标注。

## 借贷规则：一句话记住方向

会计恒等式：**资产 = 负债 + 所有者权益**（扩展式再加收入、费用）。

| 科目类型 | 增加记 | 减少记 |
|---|---|---|
| 资产（银行存款、应收） | **借** | 贷 |
| 负债（商户待结算、应付） | 贷 | **借** |
| 收入（手续费收入） | 贷 | **借** |
| 费用（通道成本） | **借** | 贷 |

> 🔑 判据：**任何一笔业务，分录的借方合计必须等于贷方合计**。不等，就是记错了，没有例外。

## 四张表：账户、科目、凭证、分录

| 表 | 作用 | 关键字段 |
|---|---|---|
| **科目表** | 会计分类（资产/负债/收入/费用） | 科目号、名称、方向 |
| **账户表** | 每个主体（用户/商户/平台）在各科目下的账户 | 账户号、科目、币种、状态 |
| **凭证表** | 一次业务事件（不可修改，只能冲正） | 凭证号、业务单号、时间、摘要 |
| **分录表** | 凭证下的借贷明细 | 凭证号、账户、借/贷金额 |

**账户余额 = 期初余额 + 本期借方发生 − 本期贷方发生**（按科目方向调整符号）。

余额不能只靠实时累加：高并发下“读-改-写”会丢更新；常见做法是**分录为准、余额为派生**，余额异步汇总并定期与分录核对。

### 金额是值对象，账户是层级

两个建模细节，决定了账务系统好不好改：

| 概念 | 建模方式 | 为什么 |
|---|---|---|
| **金额** | **值对象**：币种 + 数额，不可变，比较按属性 | 改金额 = 替换一个新值对象，不是原地改；避免“同一笔金额被多方共享后被人改掉” |
| **账户** | **层级式**：平台 → 商户 → 子账户，一号一币种 | 资金池的余额只是“虚拟账号”，真钱在银行；层级决定谁能看谁的账 |

账户本身在原文的 DDD 两讲里没有展开建模（只提到“一号一币种”“资金池余额是虚拟账号”“需要层级式账户体系”），所以账户的聚合边界要按业务自己定：**一个账户一个聚合，余额变更走凭证**，不要把多个账户塞进一个聚合里。

## 试算平衡：日终必须跑

```go
// 复式记账：有借必有贷、借贷必相等；日终试算平衡。
for _, e := range entries {
	debit += e.debit
	credit += e.credit
}
fmt.Printf("借方合计=%d 贷方合计=%d 差额=%d\n", debit, credit, debit-credit)
```

真实输出（本机 `go1.27.1 darwin/arm64`，四笔分录：收款、待结算、手续费、手续费结转）：

```text
借方合计=1020 贷方合计=1020 差额=0
试算平衡：通过
```

日终还要做第二层校验：**每个账户的余额与“分录累加”一致**（余额表 vs 分录表），以及**总分核对**（明细账合计 = 总账）。

## 账本即事件流：事件溯源的一种用法

金融系统里还有一种更彻底的做法：把账本建模成**事件流**——凭证是事件，余额是状态，余额 = 重放事件的结果。这条思路与事件溯源（Event Sourcing）同构：

| 做法 | 好处 | 代价 |
|---|---|---|
| 分录表当事件流，余额表当投影 | 可重放、可审计、可做“时光机”（回到任意时点） | 查询要走投影（CQRS），事件不可改 |
| 快照 + 增量重放 | 不必从头重放，恢复快 | 快照要记“重放到哪个事件” |
| 日终重放校验 | 用重放结果核对余额，发现异常 | 计算量大，通常只对关键账户做 |

一个真实的差错案例能说明它的价值：某台机器的 CPU 浮点寄存器故障，算出了随机值，最后是靠**双时序 + 事件溯源**才定位到——如果只存“最终余额”，你根本不知道是哪一步算错的。

## 热点账户：账务系统最硬的性能问题

一个平台收款账户，可能每秒几千笔入账——所有分录都往一个账户上记，余额行会成为热点。

| 方案 | 做法 | 量级（经验值） | 代价 |
|---|---|---|---|
| **汇总记账** | 高频小额先记“汇总分录”，按分钟/笔数合并 | 合并粒度 1 分钟 / 500 笔 | 明细延迟，需可追溯到原始流水 |
| **缓冲账户** | 先进“过渡户”，再批量结转到主账户 | 结转批次 1–5 分钟 | 多一层账户与结转逻辑 |
| **分片账户** | 按用户/商户把余额拆成多行，读取时汇总 | 8–16 片起步 | 读放大，余额查询变复杂 |
| **异步余额** | 分录同步、余额异步更新 + 定期核对 | 延迟 1–5 秒 | 余额有秒级延迟 |

判据（我的判断）：**账户 TPS 超过单行更新能力（约数百到一两千 TPS，取决于库）时，就该上缓冲或分片**；不要等到热点锁把整个库拖慢。

## 交易与账务的分工

| | 交易系统 | 账务系统 |
|---|---|---|
| 记录 | 用户买了什么、付了多少 | 钱从哪个账户到哪个账户 |
| 状态 | 待支付/已支付/已退款 | 已记账/已冲正 |
| 可变性 | 状态可推进 | 凭证不可改，错用**冲正** |
| 校验 | 幂等、状态机 | 借贷平衡、试算平衡、总分核对 |
| 对账 | 提供业务单据 | 提供账务流水（对账的基准） |

> ⚠️ 最常见的坏设计：把退款、手续费、分账都塞进订单表的字段里。结果是“订单表越来越宽，账却永远对不平”——因为这些动作本质是**新的资金事件**，该各生成一张凭证。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用订单表代替账务 | 退款/手续费/分账无法表达，对账对不上 |
| 单边记账 | 无法回答“钱从哪来”，差错定位不了 |
| 凭证可修改/删除 | 审计链断裂，无法追责 |
| 余额只靠实时累加 | 并发丢更新，余额与流水不一致 |
| 不做日终试算平衡 | 错误累积到月底才发现，追溯成本极高 |
| 热点账户不分片 | 单行锁成为瓶颈，拖慢全站 |
| 没有币种/精度设计 | 用 float 记钱，四舍五入丢分 |

## 自检

**Q1** 为什么账务系统必须用复式记账，而不是“一个账户加加减减”？

▸ 答案：因为复式记账能同时回答两个问题：这个账户变了多少（余额），钱从哪来到哪去（对手方）。单边记账只回答第一个，出了差错无法定位——你不知道这笔钱是从哪个账户来的，也就无法核对。复式还自带校验：借贷必相等，错了立刻暴露。

**Q2** 余额能不能只靠流水累加算出来？为什么还要有余额表？

▸ 答案：能算，但每次查询都全量累加不现实，所以需要余额表做派生。关键是**余额是派生数据**：必须有独立校验（期初 + 发生 = 期末、与分录累加比对、日终试算平衡），否则余额错了没人发现。余额表的作用是性能，不是真相。

**Q3** 记错了账怎么办？为什么不能直接改？

▸ 答案：不能改，只能**冲正**：生成一张反向凭证把错误分录冲掉，再记正确的。直接改会破坏审计链——你无法证明“当时记的是什么”，也无法解释为什么余额变了。冲正留下两条记录，可追溯、可审计。

**Q4** 热点账户有哪几种解法？各自代价是什么？

▸ 答案：汇总记账（明细延迟）、缓冲账户（多一层结转）、分片账户（读放大）、异步余额（秒级延迟）。选择取决于“能不能接受延迟”与“查询模式”：对账要求可追溯，就不能只保留汇总；查询要求实时，就不能全靠异步。

**Q5** 为什么交易单据不能替代账务凭证？

▸ 答案：因为一笔交易可能对应多个资金事件：支付成功（收款）、手续费（费用）、分账（应付）、退款（冲减）。交易单据只有一条记录，账务要拆成多张凭证；而且交易状态会变，凭证不可变。两者用业务单号关联，但不能合并。
