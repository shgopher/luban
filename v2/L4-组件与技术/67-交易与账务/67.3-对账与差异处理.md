# 67.3 对账与差异处理

## 一句话

> 对账不是“比一下总额”，而是**拿两个独立的事实源逐笔比对**，把差异分成可解释的几类，并让每一笔差异都走到闭环（补单 / 冲正 / 挂账）；判据是——**差异能在 T+1 内清零，且每一笔都能说出原因**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 总额对平就没问题 | A 多记 100、B 少记 100，总额照样平；差异被抹平，问题被掩盖 |
| 对账是财务的事 | 对账是**技术系统的最后一道校验**，差异处理要靠交易与账务系统 |
| 差异可以攒着以后处理 | 差异会随时间扩散：越晚处理，越难还原现场，越容易变成资损 |

## 三个前提：先定清楚再比

| 前提 | 要定什么 | 定错的后果 |
|---|---|---|
| **时间口径** | 以哪边的时间为准？T+1 日终还是准实时？跨日交易算哪天？ | 大量“时间差”被误判成差异 |
| **数据源** | 平台账、渠道账单、银行流水，谁是基准？ | 两个都不准，对出来也不知道信谁 |
| **比对键** | 渠道流水号 / 订单号 / 退款单号 | 键不唯一，一笔对多笔，永远对不平 |

> 🔑 时间口径是最容易被忽略的一条：23:59 发起的支付，渠道记在 T 日、平台记在 T+1 日——不对齐口径，每天都会冒出几百笔“假差异”。

### 日切：每天一次的快照与校验

金融系统每晚固定时间做**日切**：清点当日业务、给数据打快照。日切与对账本质是**异步验证**——异步就必须配事后补偿，发现差异再补记或冲正。

两条硬要求：

| 校验 | 做法 | 为什么 |
|---|---|---|
| **余额与明细一一比对** | 另建一个系统，把变动明细求和，与日切余额比 | 余额是派生数据，必须能被明细复算 |
| **单条可验** | 事件与“变动前/变动后余额”合并存储 | 任取一条记录就能验，不必全量重算 |
| **顺链校验** | 相邻变动串成链，逐链核对 | 定位到具体哪一段断了，而不是只知道“总数不对” |

一个真实差错值得记住：某台机器的 CPU 某个核浮点寄存器故障，算出了随机值（怀疑是宇宙射线）——最后靠**双时序（发生时间 VT / 记录时间 TT）+ 事件溯源**才定位到。这解释了为什么金融系统要“记两套时间”：只记一个时间，你连“这条数据是什么时候被写进来的”都说不清。

## 五类差异，对应五种处理

| 差异类型 | 含义 | 常见原因 | 处理 |
|---|---|---|---|
| **长款** | 渠道有、平台无 | 回调丢失、平台漏记 | 补单（按渠道流水补记） |
| **短款** | 平台有、渠道无 | 渠道未受理、请求未到达 | 查渠道状态；确认失败则关单 |
| **金额不一致** | 两边都有，金额不同 | 手续费/汇率/优惠计算差异 | 核查计费规则；差异入损溢 |
| **状态不一致** | 金额同，状态不同 | 退款/撤销未同步 | 以渠道为准，补状态或冲正 |
| **时间差** | 一边已记、一边未记 | 跨日、渠道延迟 | 下一窗口自动核销，不算差异 |

```go
// 对账：以内部分账为基准，逐笔比对渠道账单，输出五类差异。
for id, i := range inner {
	c, ok := channel[id]
	if !ok { short++; continue }
	if i.amt != c.amt { amtDiff++ }
	if i.status != c.status { statusDiff++ }
}
for id := range channel {
	if _, ok := inner[id]; !ok { long++ }
}
```

真实输出（本机 `go1.27.1 darwin/arm64`，5 笔内部账 vs 4 笔渠道账）：

```text
金额不一致：T2 内部=2000 渠道=1800
短款（渠道无此笔）：T4
长款（内部无此笔）：T5
差异合计：长款=1 短款=1 金额=1 状态=0
```

这四行就是一张“差异工单”：长款补单、短款查渠道、金额差异核查计费、状态差异补状态。

## 差异处理：从挂账到闭环

| 步 | 动作 | 时限（经验值） |
|---|---|---|
| 1 | 差异入**挂账池**，带差异类型与原始流水 | T+1 当日 |
| 2 | 自动核查（查渠道单、查回调日志、查计费规则） | T+1 |
| 3 | 人工介入（自动核查不了的） | T+2 |
| 4 | 补单 / 冲正 / 确认无差异 | T+3 |
| 5 | 复盘：同类差异是否重复出现 | 周度 |

闭环的判据不是“处理完了”，而是**同类差异不再重复产生**——如果每周都在补同一类单，说明上游有系统性缺陷（回调不可靠、计费规则不一致）。

## 准实时对账：把差异挡在当天

日终对账是兜底，不能等一天。高价值交易可以在**支付成功后几分钟内**做一次“单笔核对”：

| 时机 | 做什么 | 好处 |
|---|---|---|
| 支付成功后 1–5 分钟 | 主动查一次渠道订单状态 | 回调丢失能在分钟级发现 |
| 日终 | 全量逐笔比对 | 兜住所有遗漏 |
| 每周 | 抽样核对历史订单 | 发现“对账规则本身错了” |

## 对账的四相符与异步三态

对账不是“比一次金额”，会计上要求**四相符**：

| 相符 | 比什么 | 系统里对应 |
|---|---|---|
| **账账相符** | 总账与明细账 | 总账余额 vs 分录汇总 |
| **账证相符** | 账簿与凭证 | 余额变动 vs 凭证记录 |
| **账表相符** | 账簿与报表 | 报表数字 vs 账务汇总 |
| **账实相符** | 账与真实资金 | 平台账 vs 渠道/银行流水 |

支付系统的异步调用还有**三态**：成功、失败、**不确定**。不确定时不能当失败——做法是**限时轮询 + 每晚对账补缺**：轮询有上限，超时后交给对账兜底。原文的说法很直接：需要把同步系统的一次调用拆成三步——**异步调用、轮询、对账**。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只对总额 | 差异被抹平，问题累积 |
| 时间口径不统一 | 每天大量假差异，团队麻木 |
| 对账键不唯一 | 一笔对多笔，永远对不平 |
| 差异只记录不闭环 | 挂账池越滚越大，最后没人看 |
| 以“平台账”为唯一基准 | 平台自己错了也发现不了 |
| 对账结果不驱动上游修复 | 同类差异每周重复 |
| 手工对账无留痕 | 谁改的、依据什么，全查不到 |

## 自检

**Q1** 为什么“总额对平”不能证明账没问题？

▸ 答案：因为总额是求和，求和会把方向相反的误差抵消：A 多记 100、B 少记 100，总额仍然相等。只有逐笔比对才能定位到具体哪一笔错、错在哪；总额只能做第一层粗筛。

**Q2** 对账前为什么必须先统一时间口径？

▸ 答案：因为跨日交易的时间归属不同，会产生大量“假差异”：23:59 的支付，渠道记 T 日、平台记 T+1 日。口径不统一，团队每天要处理几百笔本不存在的差异，真正的问题反而被淹没。

**Q3** 长款和短款分别怎么处理？为什么不能都“补一下”？

▸ 答案：长款是渠道有、平台无（回调丢失），要按渠道流水**补单**；短款是平台有、渠道无（请求未到达或渠道未受理），要先查渠道状态，确认失败再关单，不能盲目补记。方向不同，处理动作相反——都“补一下”会把短款补成真资损。

**Q4** 差异闭环的判据是什么？

▸ 答案：不是“处理完了”，而是**同类差异不再重复产生**。如果每周都在补同一类单，说明上游有系统性缺陷（回调不可靠、计费规则不一致、口径没统一），需要修根因，而不是继续补单。

**Q5** 已经有日终对账，为什么还要准实时核对？

▸ 答案：因为日终对账要等一天，期间用户可能重复支付、客诉已经产生。对高价值交易在支付成功后几分钟主动查一次渠道状态，能把“回调丢失”这类问题从“第二天发现”提前到“分钟级发现”，减少资损与客诉。
