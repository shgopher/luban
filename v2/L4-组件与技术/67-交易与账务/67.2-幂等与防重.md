# 67.2 幂等与防重

## 一句话

> 交易防重不是“加个去重表”，而是**三层各守一段**：入口用幂等键拒绝重复提交、状态机用条件更新拒绝非法重放、出口用唯一约束兜底；判据只有一条——**同一笔业务，无论重试多少次，资金只动一次**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 幂等 = 防重 | 防重是“同一请求不要执行两次”；幂等是“执行 N 次等价于 1 次”。前者靠键，后者靠状态与结果 |
| 加个 Redis 去重就完了 | Redis 会丢、会过期；最终裁判必须是**数据库唯一约束** |
| 重试是客户端的事 | 服务端必须假设“任何调用都可能被重试”，包括自己的上游、网关、消息队列 |

> ⚠️ 本节只讲**交易域**的防重（业务单号、渠道流水号、状态机重放）；通用幂等设计（幂等键、去重表、PENDING 悬挂）的主场在 [25.4 幂等设计与去重](../../L1-分布式原理/25-并发、冲突与幂等/25.4-幂等设计与去重.md)。

## 三层防线，各管一段

| 层 | 机制 | 拦住什么 | 失效时 |
|---|---|---|---|
| **入口** | 幂等键 + 去重表（唯一索引） | 用户连点、网关重发、上游重试 | 重复请求进入下一层 |
| **状态机** | 条件更新 `WHERE status = '待支付'` | 已支付订单被再次支付、已退款被再次退款 | 状态被非法推进 |
| **出口** | 渠道流水号 + 唯一约束 | 同一笔渠道回调被处理多次 | 资金重复变动 |

三层不是冗余，是**纵深**：入口的键可能因为客户端没传而缺失，状态机可能因为状态设计不全而漏，出口的唯一约束是最后一道。

## 幂等键：从哪来、怎么设计

| 场景 | 幂等键 | 说明 |
|---|---|---|
| 用户下单支付 | `用户ID + 订单号 + 操作类型` | 订单号是业务唯一标识 |
| 渠道回调 | **渠道流水号** | 渠道保证唯一，比订单号更可靠 |
| 退款 | `退款单号`（一单一次） | 同一订单可多次部分退款，用退款单号区分 |
| 内部重试 | 上游传入的 `request_id` | 没有就自己在入口生成并透传 |

三条设计规则：

1. **键要能覆盖“同一业务意图”**：同一个订单的两次支付请求，键必须相同；
2. **键要有唯一索引兜底**：`UNIQUE KEY (idem_key)`，插入冲突即“已处理”；
3. **键要有过期策略**：交易类至少保留到对账周期结束（T+1 之后），不能 5 分钟就过期。

## 三态：成功、失败、未知

超时是最容易出事的状态：**它既不是成功也不是失败**。

| 状态 | 处理 |
|---|---|
| 明确成功 | 落成功态，返回结果 |
| 明确失败 | 落失败态，允许用户重新发起（新幂等键） |
| **未知（超时/网络断）** | **不能当失败**：要么查询下游，要么等回调，要么进“处理中”并定时补偿 |

把超时当失败，是重复扣款最常见的来源：用户看到失败又点了一次，两笔都成功。

```go
// 幂等：同一幂等键的第二次请求必须返回第一次的结果，而不是再执行一次。
handle := func(key string) result {
	if r, ok := store[key]; ok {
		return result{true, "重复请求，返回首次结果: " + r.msg}
	}
	r := result{true, "扣款成功，流水号 T20261031001"}
	store[key] = r
	return r
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
第 1 次: 扣款成功，流水号 T20261031001
第 2 次: 重复请求，返回首次结果: 扣款成功，流水号 T20261031001
实际扣款次数=1
```

## 状态机幂等：用条件更新，而不是“先查再改”

```sql
-- 正确：把状态判断放进 WHERE，数据库保证原子性
UPDATE orders
SET status = 'PAID', paid_at = NOW()
WHERE order_id = ? AND status = 'PAYING';

-- affected rows = 0 说明：要么已支付，要么状态不对 —— 都不能再扣款
```

| 写法 | 并发下的结果 |
|---|---|
| `SELECT status` 再 `UPDATE` | 两个请求都读到 PAYING，都去扣款 |
| `UPDATE ... WHERE status='PAYING'` | 只有一个能成功，另一个 affected rows = 0 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 只靠 Redis 去重 | Redis 丢数据/过期后，重复请求直接穿透 |
| 幂等键用随机数 | 每次重试都是新键，等于没做幂等 |
| 超时当失败 | 用户重试，两笔都成功，重复扣款 |
| 先查再改 | 并发下两个请求都通过检查 |
| 去重表与业务表不同事务 | 标记写了、业务没做，或反之 |
| 渠道回调不校验签名与流水号 | 伪造回调或重复回调都能改状态 |
| 幂等键过期太早 | 对账期内重试直接穿透 |

## 自检

**Q1** 幂等和防重有什么区别？各自靠什么实现？

▸ 答案：防重是“同一请求不要执行两次”，靠**幂等键 + 唯一索引**在入口拦住；幂等是“执行 N 次等价于 1 次”，靠**状态机条件更新 + 结果持久化**保证。没有状态机，重复请求即使进来了也会被再次执行；没有幂等键，重复请求根本到不了状态机。

**Q2** 为什么“超时”不能当失败处理？

▸ 答案：因为超时只说明“没收到响应”，下游可能已经成功。当失败处理会让用户重试，而重试很可能再成功一次——两笔都扣款。正确做法是查询或等回调，落“处理中”并补偿。

**Q3** 幂等键怎么设计才算合格？

▸ 答案：三个条件：覆盖同一业务意图（同一订单的两次支付用同一个键）、有唯一索引兜底（插入冲突即已处理）、生命周期覆盖对账周期（至少 T+1，不能几分钟过期）。渠道回调要用渠道流水号，因为它比订单号更接近“渠道侧的唯一事实”。

**Q4** 为什么“先查再改”在并发下不可靠？

▸ 答案：因为查与改之间有时间窗，两个请求可能同时读到 `PAYING` 然后都去扣款。把状态判断放进 `UPDATE ... WHERE status='PAYING'`，由数据库保证原子性，只有一个能成功；另一个拿到 affected rows = 0，据此判定“已处理或状态不对”。

**Q5** 三层防线里，哪一层最不能省？

▸ 答案：出口的唯一约束。入口的键可能缺失（客户端没传）、状态机可能漏设计（新增状态没覆盖），只有数据库唯一约束是**物理兜底**——即使前两层都失效，重复插入也会失败。代价是要设计好唯一键，不能让它成为写入瓶颈。
