# 67.1 交易流程建模

## 一句话

> 交易建模的核心不是“建一张订单表”，而是**把一次交易拆成“单据 + 状态机 + 流水”三件套**：单据记录意图、状态机记录进度、流水记录事实；判据是——**任何一个时刻，系统都能回答“这笔钱现在在哪”**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 订单表就是交易模型 | 订单只是“意图”；支付单、退款单、渠道流水、账务凭证各有自己的生命周期 |
| 状态用字符串散落各处 | 状态散落 = 非法迁移遍地，最后没人说得清“已支付能不能再支付” |
| 只设计正向流程 | 逆向（退款、冲正、挂账）才是资损高发区；正向设计时就要设计反向 |

## 一笔支付要经过谁

| 环节 | 参与方 | 做什么 | 典型失败 |
|---|---|---|---|
| 下单 | 商户 → 交易系统 | 生成订单与支付单，锁定金额与商品 | 重复下单、金额被改 |
| 发起支付 | 交易 → 支付网关 | 组装渠道参数、签名、选路由 | 渠道超时、路由到不可用渠道 |
| 渠道处理 | 支付网关 → 渠道（微信/支付宝/银行） | 扣款/跳转/扫码 | 渠道成功但回调丢失 |
| 回调通知 | 渠道 → 交易系统 | 通知结果、验签、幂等处理 | 重复回调、伪造回调 |
| 清结算 | 交易 → 清算/账务 | 计算手续费、分账、入账 | 金额算错、分账遗漏 |
| 对账 | 账务 ↔ 渠道账单 | 逐笔比对、差异处理 | 长款/短款、状态不一致 |

> 🔑 关键认知：**支付网关收到“成功”不等于钱到账**。渠道侧成功、平台侧入账、银行侧清算，是三件事，各有各的时间差——这就是为什么必须有对账（[67.3](67.3-对账与差异处理.md)）。

## 本币代收的七步：一条真实链路

“支付成功”这四个字背后，真正发生的是七步（原文按第三方支付的本币代收拆解）：

| 步 | 谁做了什么 | 注意 |
|---|---|---|
| 1 | 第三方支付机构指令其开户行，从买家开户行把资金转来 | 此时只是**指令**，钱还没动 |
| 2 | 持用户 Token 发起代收 | Token 是鉴权结果，4 要素（姓名/身份证/卡号/银行预留手机号）换来的 |
| 3 | 交清算机构记录，并通知两家银行 | 清算机构负责“记白天的明细” |
| 4 | 买家开户行扣款，短信通知用户 | 用户看到“扣款成功”在这一步 |
| 5 | 第三方开户行给第三方支付公司打款 | **白天结束、尚未实质到账** |
| 6 | 夜间清算机构盘存，报央行 | 日终才做 |
| 7 | 央行调低买家开户行、调高第三方开户行准备金 | 真实资金转移只发生在央行账本上 |

这条链路解释了三件事：

- **信息流 ≠ 资金流**：信息流是“想象中钱的流转”，资金流是“钱的实际流转”；白天走的是信息流，晚上才轧差走资金流。
- **“日间记录、日终轧差”是标准做法**：白天只记录，日终算净额，经央行转一笔。轧差的本质是**实时消息的批量处理**，是一个延时更大的异步框架。
- **一笔购汇可能是两笔订单**：外汇零售里“一个账号一个币种”，人民币与美元各开账户，所以一笔购汇在系统里是两笔订单——这是“单据要按币种/账户拆”的典型原因。

## 三件套：单据、状态机、流水

| 件 | 记什么 | 例子 | 可变性 |
|---|---|---|---|
| **单据** | 业务意图与金额 | 订单、支付单、退款单 | 状态可推进，金额不可改 |
| **状态机** | 走到哪一步、允许去哪 | `INIT → PAYING → PAID → REFUNDING → REFUNDED` | 只能按白名单迁移 |
| **流水** | 实际发生了什么 | 渠道流水、账务分录、回调记录 | **只增不改** |

三件套的关系：**单据驱动状态机，状态机产生流水，流水反过来校验单据**。缺任何一件，都会出现“状态说成功了，但找不到钱”的情况。

## 状态机：把“能不能”写成白名单

```go
// 交易状态机校验：只允许白名单里的迁移，非法迁移必须被拦住。
var allowed = map[string][]string{
	"INIT":      {"PAYING", "CLOSED"},
	"PAYING":    {"PAID", "PAY_FAILED"},
	"PAID":      {"REFUNDING", "SETTLED"},
	"REFUNDING": {"REFUNDED", "REFUND_FAILED"},
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
✓ INIT -> PAYING
✓ PAYING -> PAID
✓ PAID -> REFUNDING
✗ 非法迁移 PAID -> PAYING
✗ 非法迁移 CLOSED -> PAID
✗ 非法迁移 REFUNDED -> PAID
```

这三条“非法迁移”就是资损的来源：已支付又被拉回支付中、已关闭又被支付、已退款又被支付。**状态机不是文档，是代码里的白名单**。

## 正向与逆向必须对称设计

| 正向动作 | 逆向动作 | 注意 |
|---|---|---|
| 下单 | 取消/关单 | 关单要释放预占库存 |
| 支付 | 退款 | 部分退款要按退款单管理 |
| 扣库存 | 回补库存 | 回补要幂等，避免超卖 |
| 入账 | 冲正 | 凭证不可改，只能冲正 |
| 分账 | 分账回退 | 已结算的分账回退要走审批 |

许式伟在讲补偿事务时说过一句话：**设计业务正向流程的时候，也需要设计业务的反向补偿流程**。交易系统里，逆向流程不是“异常分支”，是**与正向同等重要的一条主流程**。

## 建模自查：三个“点”有没有标出来

| 检查点 | 要回答 | 没标出来的后果 |
|---|---|---|
| **幂等点** | 哪些入口可能重复？键是什么？ | 重复支付/重复退款（[67.2](67.2-幂等与防重.md)） |
| **对账点** | 哪一步之后可以和渠道对？拿什么对？ | 差异永远发现不了（[67.3](67.3-对账与差异处理.md)） |
| **状态一致性** | 单据、渠道、账务三处状态谁为准？ | 三处各说各话，客诉无法定位 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 只有订单表，没有支付单/退款单 | 一个订单多次支付/部分退款无法表达 |
| 状态用字符串随意写 | 非法迁移遍地，资损无法拦截 |
| 逆向流程后补 | 退款、冲正没有幂等与审批，资损高发 |
| 不记录渠道流水 | 回调丢失后无法追溯，只能人工查 |
| 状态以“本地为准” | 渠道已成功、本地超时，用户被重复扣款 |
| 支付回调不验签 | 伪造回调可直接改单 |
| 没有“未知态” | 超时被当失败，用户重试导致重复支付 |

## 自检

**Q1** 为什么“订单表”不能等同于交易模型？

▸ 答案：因为一笔交易会产生多个单据：订单（买什么）、支付单（付多少、走哪个渠道）、退款单（退多少、退哪笔）、账务凭证（钱从哪到哪）。它们生命周期不同、状态机不同；只用一张订单表，多次支付、部分退款、分账都无法表达。

**Q2** 状态机为什么要写成代码里的白名单，而不是文档里的图？

▸ 答案：因为图拦不住非法迁移，代码可以。把“允许的迁移”写成 map/表，任何一次状态变更都过校验，非法迁移（已退款又支付、已关闭又支付）在入口就被拒绝；文档只能靠人记得。

**Q3** 支付渠道返回成功，为什么还不能算“钱到账”？

▸ 答案：因为渠道成功、平台入账、银行清算是三个环节，存在时间差；而且回调可能丢失、重复、甚至伪造。平台侧必须以“验签 + 幂等 + 对账”确认，不能把渠道的一次响应当最终事实。

**Q4** 为什么逆向流程要和正向流程一起设计？

▸ 答案：因为逆向流程才是资损高发区：退款要防重复、回补库存要防超卖、冲正要留审计链。正向设计时顺手设计逆向，成本最低；等出了问题再补，往往已经产生了脏数据，还要回头修历史。

**Q5** “幂等点、对账点、状态一致性”这三个检查点，分别在防什么？

▸ 答案：幂等点防重复执行（重复支付/退款）；对账点防“账实不符”（渠道与平台不一致却没人发现）；状态一致性防“三处各说各话”（本地、渠道、账务状态不一致导致客诉无法定位）。三者缺一，都会在资损或客诉时暴露。
