# 67.5 资金安全与风控联动

## 一句话

> 资金安全不是“防黑客”，而是把**“谁能动钱、能动多少、动完谁看得见”**制度化；风控是它的实时版——交易前拦、交易中查、交易后对，三处都必须具备“说不”的能力。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 资金安全 = 加密 + 防火墙 | 多数资损来自**内部流程与业务规则**，不是外部攻击 |
| 风控 = 一个模型 | 模型只是其中一层；规则、名单、限额、人工复核缺一不可 |
| 资损是小概率，不用专门设计 | 一次重复退款、一次汇率取错，就能吃掉几个月利润 |

## 三道防线：事前、事中、事后

| 阶段 | 手段 | 拦住什么 | 关键设计 |
|---|---|---|---|
| **事前** | 权限、限额、白名单、签约 | 越权操作、超额交易、未签约商户 | 最小权限 + 双人复核 |
| **事中** | 规则、名单、设备指纹、频次、人工复核 | 盗刷、刷单、异常大额、新设备 | 决策延迟预算 + 降级策略 |
| **事后** | 对账、巡检、告警、追损 | 差错、漏单、内部作弊 | 对账闭环（[67.3](67.3-对账与差异处理.md)） |

> 🔑 判据：**任何一笔资金变动，都要能回答三个问题**——谁发起的、依据是什么、谁复核的。答不全，就是流程漏洞。

## 权限：资金操作的四眼原则

| 规则 | 做法 | 反例 |
|---|---|---|
| **最小权限** | 按角色授权，资金操作单独授权 | 开发拥有生产库写权限 |
| **双人复核** | 大额/退款/调账至少两人确认 | 一个人能直接退款到任意账户 |
| **操作留痕** | 谁、何时、改了什么、依据哪张单 | 只记“已操作”，不记参数 |
| **限额** | 单人单笔/单日上限 + 超限走审批 | 无上限，靠“信任” |

## 风控联动：决策点与延迟预算

风控不是一个独立系统，而是嵌在交易链路里的**决策点**：

```go
// 交易风控：规则按顺序短路，命中即拒绝，记录命中规则。
switch {
case t.amount > 50000:
	verdict = "拒绝：超单笔限额"
case t.count5m > 5:
	verdict = "拒绝：5 分钟频次超限"
case t.newDevice && t.amount > 10000:
	verdict = "拒绝：新设备大额"
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
u1  金额=8000   → 通过
u2  金额=60000  → 拒绝：超单笔限额
u1  金额=12000  → 拒绝：5 分钟频次超限
u3  金额=300    → 通过
```

完整代码在仓库 [tools/examples/67.5-riskrule/](../../../tools/examples/67.5-riskrule/README.md)，`go run .` 可复现这四条判定。

| 设计项 | 经验值（我的判断） | 说明 |
|---|---|---|
| 风控决策延迟 | P99 ≤ **50–100ms** | 超过就会拖慢支付主链路 |
| 决策超时 | ≤ 200ms，超时按“降级策略”处理 | 不能无限等 |
| 降级策略 | 小额放行、大额拒绝或转人工 | 按金额分级，不能一刀切 |
| 规则数量 | 单次决策 ≤ 几十条 | 规则多了要分层（粗筛 → 精算） |

**风控挂了怎么办**是必须提前定的：全放行会资损，全拒绝会掉交易量。常见做法是按金额分级——小额放行并事后补查，大额转人工或拒绝。

## 资损从哪来：一张对照表

| 资损类型 | 典型原因 | 防线 |
|---|---|---|
| **重复退款** | 幂等没做、回调重复 | 幂等键 + 状态机（[67.2](67.2-幂等与防重.md)） |
| **超卖/超发** | 库存扣减非原子、并发 | 条件更新 + 唯一约束（[67.6](67.6-秒杀与抢购.md)） |
| **汇率/手续费算错** | 精度、口径、四舍五入 | 整数分存储 + 对账校验（[67.3](67.3-对账与差异处理.md)） |
| **内部作弊** | 权限过大、无复核 | 四眼原则 + 操作审计 |
| **对账漏单** | 只对金额不对状态 | 双边对账 + 差异闭环 |
| **配置错误** | 限额/费率改错 | 配置变更走审批 + 灰度 |

## 限额/拦截/复核的三级联动

把「拦不拦」压成一步判断，会同时制造两类错误：大客户提额前的正常交易被一刀拒掉，高风险的小额交易因为金额小被放行。三级联动把这件事拆成三个问题，每一级只回答一个问题，且只升档不降档：

| 层级 | 回答的问题 | 触发条件 | 动作 | 失败兜底 | 延迟预算 |
|---|---|---|---|---|---|
| **限额**（事前授权） | 这个人、这个渠道允许动多少钱 | 金额 > 用户等级限额 | 升一档：放行→二次验证、二次验证→人工复核 | 限额配置拉取失败 → 用本地缓存的上限；无缓存按最低档 | <1ms（内存比较） |
| **拦截**（事中决策） | 这笔像不像欺诈 | 名单、矩阵、规则、模型 | 放行 / 二次验证 / 人工复核 / 拦截 | 风控超时按金额分级（[68.1 风控系统架构](../68-风控/68.1-风控系统架构.md)） | 名单 + 规则 ≤10ms；含模型见 68.1 预算 |
| **复核**（事后处置） | 机器不敢定的，谁来签字 | 决策结果为人工复核 | 人工审核，SLA 15 分钟 | 超时：<1 万放行 + 事后补查；≥1 万拒绝 | 异步，不占主链路 |

拦截层的第一判断是一张二维矩阵，而不是一串阈值。金额分 4 档、风险分 4 档（风险分来自 68 章的模型与规则，按经验切成低 <0.3、中 0.3–0.6、高 0.6–0.85、极高 ≥0.85）：

| 金额区间 | 低风险 | 中风险 | 高风险 | 极高风险 |
|---|---|---|---|---|
| < 1,000 | 放行 | 放行 | 二次验证 | 拦截 |
| 1,000–9,999 | 放行 | 二次验证 | 人工复核 | 拦截 |
| 10,000–49,999 | 二次验证 | 人工复核 | 拦截 | 拦截 |
| ≥ 50,000 | 人工复核 | 拦截 | 拦截 | 拦截 |

为什么风险分只切 4 档、不直接用连续分？因为处置是离散动作（放行/验证/复核/拦截），4 档对应 4 个动作边界，业务能审计「0.62 落在高风险档」；而把连续分直接乘进金额再取阈值，客诉时解释不清，规则评审也过不了。分档阈值可调，但档位与动作的映射必须显式写在矩阵里。

矩阵给的是**初判**，限额层做的是**改档位**。关键设计是：超限额不等于拒绝。限额是授权档位，不是风险判断——超限只说明「这件事需要更强的确认」，所以把处置升一档就够：矩阵说放行、超限后变二次验证；矩阵说二次验证、超限后变人工复核。只有两种情况无条件拦截：**硬上限**（本实现取 20 万，绕过任何审批都必须拒）与**名单命中**（确定性事实）。

```go
// 金额 4 档 × 风险 4 档：放行 / 二次验证 / 人工复核 / 拦截
var grid = [4][4]Action{
	{Pass, Pass, Verify, Block},    // < 1,000
	{Pass, Verify, Review, Block},  // 1,000 – 9,999
	{Verify, Review, Block, Block}, // 10,000 – 49,999
	{Review, Block, Block, Block},  // ≥ 50,000
}

// 第一级：限额。超限不直接拒，只把处置升一档（复核已是人工档，不再升）。
func applyLimit(a Action, amount, limit int) (Action, bool) {
	if amount <= limit {
		return a, false
	}
	switch a {
	case Pass:
		return Verify, true
	case Verify:
		return Review, true
	default: // Review / Block 不动
		return a, true
	}
}

// 决策：名单 → 硬上限 → 矩阵 → 限额升档。返回动作与可解释原因。
func decide(amount int, risk Risk, limit int, blacklisted bool) (Action, string) {
	if blacklisted {
		return Block, "名单命中：确定性事实，直接拦截"
	}
	if amount > hardCeiling {
		return Block, fmt.Sprintf("金额 %d 超硬上限 %d，绕过限额审批也必须拒", amount, hardCeiling)
	}
	a := grid[amountBand(amount)][risk]
	reason := fmt.Sprintf("矩阵[金额档%d][风险%s]=%s", amountBand(amount), risk, a)
	if na, escalated := applyLimit(a, amount, limit); escalated {
		if na != a {
			reason += fmt.Sprintf("；超限额 %d → 升档为 %s", limit, na)
		} else {
			reason += fmt.Sprintf("；超限额 %d，但已在人工档，保持 %s", limit, na)
		}
		a = na
	}
	return a, reason
}
```

完整时序是先轻后重：交易请求进来，先在内存里比较限额（<1ms，无网络）；再调风控拿风险分（名单 + 规则优先，模型可降级，整体 P99 预算见 [68.1 风控系统架构](../68-风控/68.1-风控系统架构.md)）；拿到分数后查矩阵、做升档。风控超时或不可用时，不能把风险分当成 0：按金额分级兜底——小额放行并事后补查，大额拒绝或转人工，这条兜底正是 68.1「失败策略」在资金链路上的落点。

本机运行输出（`go1.27.1 / darwin/arm64 / Apple M1`）：

```text
用例   金额       风险   限额      名单     期望       实际       结果
T01  500      低    5000    false  放行       放行       true
T02  6000     低    5000    false  二次验证     二次验证     true
T03  6000     中    50000   false  二次验证     二次验证     true
T04  6000     高    50000   false  人工复核     人工复核     true
T05  20000    低    10000   false  人工复核     人工复核     true
T06  20000    高    50000   false  拦截       拦截       true
T07  80000    低    50000   false  人工复核     人工复核     true
T08  12000    极高   50000   false  拦截       拦截       true
T09  300000   低    500000  false  拦截       拦截       true
T10  100      低    50000   true   拦截       拦截       true

通过 10/10

复核超时兜底（SLA = 15 分钟）
  T04 6000 元 → 复核超时 → 放行（复核超时且金额 < 1 万：放行 + 事后补查（挂号））
  T05 20000 元 → 复核超时 → 拦截（复核超时且金额 ≥ 1 万：拒绝（fail-close））
  T07 80000 元 → 复核超时 → 拦截（复核超时且金额 ≥ 1 万：拒绝（fail-close））
```

10 组用例覆盖了全部 4 种处置，其中值得单独看的是三行：**T02** 矩阵初判放行、因 6000 > 5000 限额升为二次验证；**T05** 矩阵初判二次验证、因 20000 > 10000 限额升为人工复核——两次升档证明「限额」与「风险」是两条独立轴，不能被压成一个金额阈值。**T09** 金额 30 万没有因为限额配到 50 万就放行，被硬上限拦死，说明限额可以被审批调高，但硬上限是最后一道固定闸门。

复核层的 SLA 与兜底需要单独定，因为它是唯一「异步等待人」的一级：

| 处置 | 是否阻断交易 | 等待时限 | 超时兜底 |
|---|---|---|---|
| 二次验证（短信/人脸） | 同步等用户完成 | 60–90 秒 | 用户放弃 = 视为拒绝 |
| 人工复核 | 交易挂起，异步审 | 15 分钟 | <1 万放行 + 事后补查；≥1 万拒绝 |
| 拦截 | 立即返回拒绝 | 无 | 终态，不可降级 |

复核为什么必须异步、还要按金额分兜底？因为复核消耗的是人工工时：复核一条 5–15 元，而误放一笔大额可能是数百元级资损（单价量级见 [68.6 误杀与漏杀的权衡](../68-风控/68.6-误杀与漏杀的权衡.md)），成本比决定了不能全量转人工。异步又带来「交易挂多久」的问题：15 分钟是用户还能接受的挂起上限，超时必须自动决策；小额（<1 万）放行 + 事后补查，把误杀成本压到最低；大额（≥1 万）拒绝，宁可误杀也不给攻击者时间窗口。二次验证则按风险档位选强度：中风险发短信，高风险上人脸，验证方式本身也是一档处置。

三级联动要成立，还得守三条规则：

1. **只升档不降档**：任何一级只能把处置变严，不能把「拦截」改回「放行」；否则风险分再准也会被下游抹平。
2. **顺序固定、各自短路**：名单 → 硬上限 → 矩阵 → 限额升档 → 复核。名单先于一切（确定性事实，不需要算特征）；硬上限先于矩阵（不可协商）；矩阵先于升档（先有初判再改档位）。
3. **复核结果必须回流**：复核完成后把结论写回名单/规则/样本，下次同类交易自动命中；只审不回流，等于每天把同一类案件重新看一遍。

> 🔑 判断一笔资金操作要走几级，看的是**最坏后果**而不是金额大小：金额 300 元但收款方是新注册账户，同样值得一次二次验证；金额 8 万但收款方是白名单商户，可以只做验证。金额只决定档位，风险才决定是否放行。

> 🔑 67.5 与 68 章的分工是一句话：68 章回答「这笔像不像欺诈」，产出风险分与命中原因；67.5 回答「这笔钱让不让动、动多少、谁签字」，消费风险分决定处置。规则与模型只在 68 章维护一份，67.5 不重复实现。

几种常见错法，后果都很直接：

| 错法 | 后果 | 正确做法 |
|---|---|---|
| 超限额一律拒绝 | 大客户提额前的正常交易被误杀，提额流程变成投诉 | 超限升档到验证/复核，只为硬上限保留拒绝 |
| 复核队列没有 SLA、没有兜底 | 交易长时间挂起，用户重复提交，资损与客诉同时发生 | 15 分钟 SLA + 按金额分级兜底（小额放行补查、大额拒绝） |
| 只用金额一个维度 | 大额低风险被拦、小额高风险被放过 | 金额 × 风险二维矩阵，金额定档位、风险定放行 |
| 复核结论不回流 | 同类案件每天重复人工审核 | 回写名单/规则/样本，形成闭环 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 开发拥有生产资金操作权限 | 一次误操作就是资损 |
| 大额退款单人可完成 | 内部作弊与误操作都无法拦 |
| 风控同步调用无超时 | 风控一慢，支付全慢 |
| 风控挂了直接全放行 | 攻击窗口，资损集中爆发 |
| 只记“操作成功”不记参数 | 出事无法复盘 |
| 限额只在客户端校验 | 绕过客户端即可超额 |
| 对账只对总额不对明细 | 差额被抹平，问题被掩盖 |

## 自检

**Q1** 为什么说多数资损来自内部流程，而不是外部攻击？

▸ 答案：因为外部攻击有防火墙、WAF、风控多层拦；而内部流程漏洞（权限过大、无复核、限额只在客户端、配置可直改）不需要攻击技巧，一次误操作或一次监守自盗就能造成资损。所以资金安全的第一道防线是**权限与复核制度**，不是加密。

**Q2** “四眼原则”具体指什么？为什么大额操作必须双人？

▸ 答案：一笔资金操作至少经过两个人：发起人 + 复核人，且两人权限分离。原因是单人既能发起又能确认时，误操作与作弊都无法被拦住；双人复核把“一个人犯错”变成“两个人同时犯错”，概率大幅下降，且留下可追溯的记录。

**Q3** 风控决策的延迟预算怎么定？超时了怎么办？

▸ 答案：按支付主链路的延迟目标倒推，经验是 P99 ≤ 50–100ms、超时 ≤ 200ms。超时不能无限等，要按金额分级降级：小额放行并事后补查，大额拒绝或转人工。关键是**降级策略要提前写进代码**，不能等风控挂了再临时决定。

**Q4** 风控规则为什么不能无限加？

▸ 答案：因为规则越多，单次决策越慢、冲突越多、维护越难。做法是分层：先用少量粗规则挡掉大部分风险（限额、名单、频次），再对通过者做精细判断；规则数量控制在几十条内，新增规则要能说清“拦的是什么资损”。

**Q5** 对账为什么必须对明细，不能只对总额？

▸ 答案：因为总额相等不代表明细正确：A 多记 100、B 少记 100，总额仍然平。只对总额会把差异抹平，问题被掩盖到下一次；对明细才能定位到具体哪一笔，并驱动补单/冲正（[67.3](67.3-对账与差异处理.md)）。
