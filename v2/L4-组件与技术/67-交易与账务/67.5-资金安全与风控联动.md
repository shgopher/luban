# 67.5 资金安全与风控联动

## 一句话

> 资金安全不是“防黑客”，而是把**“谁能动钱、能动多少、动完谁看得见”**制度化；风控是它的实时版——交易前拦、交易中查、交易后对，三处都必须具备“说不”的能力。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 资金安全 = 加密 + 防火墙 | 多数资损来自**内部流程与业务规则**，不是外部攻击 |
| 风控 = 一个模型 | 模型只是其中一层；规则、名单、限额、人工复核缺一不可 |
| 资损是小概率，不用专门设计 | 一次重复退款、一次汇率取错，就能吃掉几个月利润 |

## 三道防线：事前、事中、事后

| 阶段 | 手段 | 拦住什么 | 关键设计 |
|---|---|---|---|
| **事前** | 权限、限额、白名单、签约 | 越权操作、超额交易、未签约商户 | 最小权限 + 双人复核 |
| **事中** | 规则、名单、设备指纹、频次、人工复核 | 盗刷、刷单、异常大额、新设备 | 决策延迟预算 + 降级策略 |
| **事后** | 对账、巡检、告警、追损 | 差错、漏单、内部作弊 | 对账闭环（[67.3](67.3-对账与差异处理.md)） |

> 🔑 判据：**任何一笔资金变动，都要能回答三个问题**——谁发起的、依据是什么、谁复核的。答不全，就是流程漏洞。

## 权限：资金操作的四眼原则

| 规则 | 做法 | 反例 |
|---|---|---|
| **最小权限** | 按角色授权，资金操作单独授权 | 开发拥有生产库写权限 |
| **双人复核** | 大额/退款/调账至少两人确认 | 一个人能直接退款到任意账户 |
| **操作留痕** | 谁、何时、改了什么、依据哪张单 | 只记“已操作”，不记参数 |
| **限额** | 单人单笔/单日上限 + 超限走审批 | 无上限，靠“信任” |

## 风控联动：决策点与延迟预算

风控不是一个独立系统，而是嵌在交易链路里的**决策点**：

```go
// 交易风控：规则按顺序短路，命中即拒绝，记录命中规则。
switch {
case t.amount > 50000:
	verdict = "拒绝：超单笔限额"
case t.count5m > 5:
	verdict = "拒绝：5 分钟频次超限"
case t.newDevice && t.amount > 10000:
	verdict = "拒绝：新设备大额"
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
u1  金额=8000   → 通过
u2  金额=60000  → 拒绝：超单笔限额
u1  金额=12000  → 拒绝：5 分钟频次超限
u3  金额=300    → 通过
```

| 设计项 | 经验值（我的判断） | 说明 |
|---|---|---|
| 风控决策延迟 | P99 ≤ **50–100ms** | 超过就会拖慢支付主链路 |
| 决策超时 | ≤ 200ms，超时按“降级策略”处理 | 不能无限等 |
| 降级策略 | 小额放行、大额拒绝或转人工 | 按金额分级，不能一刀切 |
| 规则数量 | 单次决策 ≤ 几十条 | 规则多了要分层（粗筛 → 精算） |

**风控挂了怎么办**是必须提前定的：全放行会资损，全拒绝会掉交易量。常见做法是按金额分级——小额放行并事后补查，大额转人工或拒绝。

## 资损从哪来：一张对照表

| 资损类型 | 典型原因 | 防线 |
|---|---|---|
| **重复退款** | 幂等没做、回调重复 | 幂等键 + 状态机（[67.2](67.2-幂等与防重.md)） |
| **超卖/超发** | 库存扣减非原子、并发 | 条件更新 + 唯一约束（[67.6](67.6-秒杀与抢购.md)） |
| **汇率/手续费算错** | 精度、口径、四舍五入 | 整数分存储 + 对账校验（[67.3](67.3-对账与差异处理.md)） |
| **内部作弊** | 权限过大、无复核 | 四眼原则 + 操作审计 |
| **对账漏单** | 只对金额不对状态 | 双边对账 + 差异闭环 |
| **配置错误** | 限额/费率改错 | 配置变更走审批 + 灰度 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 开发拥有生产资金操作权限 | 一次误操作就是资损 |
| 大额退款单人可完成 | 内部作弊与误操作都无法拦 |
| 风控同步调用无超时 | 风控一慢，支付全慢 |
| 风控挂了直接全放行 | 攻击窗口，资损集中爆发 |
| 只记“操作成功”不记参数 | 出事无法复盘 |
| 限额只在客户端校验 | 绕过客户端即可超额 |
| 对账只对总额不对明细 | 差额被抹平，问题被掩盖 |

## 自检

**Q1** 为什么说多数资损来自内部流程，而不是外部攻击？

▸ 答案：因为外部攻击有防火墙、WAF、风控多层拦；而内部流程漏洞（权限过大、无复核、限额只在客户端、配置可直改）不需要攻击技巧，一次误操作或一次监守自盗就能造成资损。所以资金安全的第一道防线是**权限与复核制度**，不是加密。

**Q2** “四眼原则”具体指什么？为什么大额操作必须双人？

▸ 答案：一笔资金操作至少经过两个人：发起人 + 复核人，且两人权限分离。原因是单人既能发起又能确认时，误操作与作弊都无法被拦住；双人复核把“一个人犯错”变成“两个人同时犯错”，概率大幅下降，且留下可追溯的记录。

**Q3** 风控决策的延迟预算怎么定？超时了怎么办？

▸ 答案：按支付主链路的延迟目标倒推，经验是 P99 ≤ 50–100ms、超时 ≤ 200ms。超时不能无限等，要按金额分级降级：小额放行并事后补查，大额拒绝或转人工。关键是**降级策略要提前写进代码**，不能等风控挂了再临时决定。

**Q4** 风控规则为什么不能无限加？

▸ 答案：因为规则越多，单次决策越慢、冲突越多、维护越难。做法是分层：先用少量粗规则挡掉大部分风险（限额、名单、频次），再对通过者做精细判断；规则数量控制在几十条内，新增规则要能说清“拦的是什么资损”。

**Q5** 对账为什么必须对明细，不能只对总额？

▸ 答案：因为总额相等不代表明细正确：A 多记 100、B 少记 100，总额仍然平。只对总额会把差异抹平，问题被掩盖到下一次；对明细才能定位到具体哪一笔，并驱动补单/冲正（[67.3](67.3-对账与差异处理.md)）。
