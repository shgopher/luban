                        61.5 Hive 与 SQL-on-Hadoop

                        一句话

                        Hive 的物理事实只有三样——MetaStore 里的一行元数据、对象存储上的一个目录、目录里的列存文件；同一条 SQL 快不快，取决于这三样里「能被跳过的部分」有多少，而不是 Hive 的版本号。

                        先把 Hive 拆成四个部件

                        Hive 经常被当成「数据库」，但它本身不存数据、不管事务引擎、也不执行计算——它是一个元数据服务 + 一个 SQL 翻译器 + 一个可插拔执行壳。

                        部件 干什么 坏了会怎样 能换吗
                        MetaStore 存库/表 schema、分区列表、列统计、权限；元数据落 MySQL/PostgreSQL，服务走 Thrift（默认 9083） 所有引擎「看不见表」：SHOW TABLES 报错，存量作业全挂 可换实现（AWS Glue、自建 HMS、Iceberg REST catalog），但要重新注册表
                        HQL 解析与优化 Parser → AST → 语义分析 → 逻辑计划 → CBO（Calcite）→ 物理计划（task DAG、算子选择） 执行计划差：多扫文件、join 顺序错、shuffle 爆炸 换执行引擎不改 SQL
                        执行引擎 按物理计划跑 task：MapReduce / Tez / Spark，由 hive.execution.engine 切换 慢、OOM、shuffle 多次落盘 可换；Hive 只是「翻译器 + 调度壳」
                        存储格式与文件系统 Text / ORC / Parquet / Avro + HDFS / S3 / OSS；表 = 目录，分区 = 子目录，文件 = 数据 小文件、格式不支持 ACID、对象存储 rename 语义缺失 可换（Iceberg / Delta / Hudi 表格式，见 60.3 数据湖与湖仓一体）

                        四句话把每个部件的定位钉住：

                        1. MetaStore 是事实标准 catalog：Spark、Trino、Presto、Flink 都能通过 HMS 或兼容实现读同一张表。所以「Hive 表」并不绑定 Hive 引擎——这也是 Hive 最难被替换的原因：表格式可以换，元数据注册中心换不动。
                        2. 解析层决定了「能不能少读」：分区裁剪、谓词下推、CBO 统计全在这一层发生。执行引擎再快，读到 30 倍数据也白搭。
                        3. 执行引擎可插拔，所以「Hive 慢」这句话不完整：必须问「Hive on 什么」。Hive on MR 与 Hive on Tez 跑同一个 SQL 的差距通常是 3–10 倍量级（工程经验值，受作业形状影响），Hive 后续版本已明显弱化 MR（Tez/Spark 为主），具体版本的引擎可用性以官方文档为准。
                        4. 存储格式决定物理上限：Text 表怎么调参都要全行读写；ORC/Parquet 才有「只读 2 列、只读 25 个块」的可能。

                        一次查询的路径可以写成三行：

                        SQL 文本
  → 逻辑计划：该读哪些分区、哪些文件、哪些列（裁剪在这一层决定）
  → 物理计划：切成多少 task、每个 task 读哪一段、要不要 shuffle
  → 执行：task 在 YARN/K8s 上跑，结果落盘

                        🔑 调优 Hive 的第一动作不是改参数，而是看逻辑计划跳掉了什么：分区跳了几个、文件跳了几个、列读了几列。跳不掉的部分，参数救不回来。

                        表、分区、文件、row group：四层物理映射

                        Hive 里没有「表」这个物理对象。建表 = 在 MetaStore 插一行 + 约定一个目录；INSERT = 往目录里写文件。所以「表」是四层映射的别名：

                        逻辑概念 物理形态 能被裁剪的粒度 谁负责
                        库 warehouse 下的目录 db.db/ — MetaStore
                        表 目录 + MetaStore 里一行记录 表级（分区表可整体跳过大半） MetaStore
                        分区 子目录 dt=2026-10-01/ 分区裁剪：整个目录跳过 查询层（分区列谓词）
                        文件 part-00000-xxx.orc 文件级 min/max 跳过 存储格式 footer
                        row group / stripe 文件内 64–128 MB 的块 块级 min/max、bloom filter ORC / Parquet 索引
                        行 块内一行 无索引则逐行过滤 执行引擎

                        这张表解释了三件常被搞混的事：

                        • 绕过 Hive 直接 hdfs dfs -put 往表目录塞文件：数据在、元数据不知道，查询看不到。必须 MSCK REPAIR TABLE 或 ALTER TABLE ADD PARTITION 补登记。
                        • DROP TABLE 的破坏力取决于表类型：managed 表连目录一起删，external 表只删元数据。线上事故里「删了元数据、数据还在」和「数据被一起删了」是两种完全不同的救援方案，建表时就要定。
                        • EXTERNAL 的判定标准是「数据归谁管」：多引擎共享（Spark 写、Hive 读、Trino 查）用 external，避免某个引擎的 DROP 把大家的数据带走；Hive 独占、需要能被 DDL 清理的中间表用 managed。

                        读一次表，元数据要付三次成本，顺序固定：

                        步骤 谁在付 成本量级（经验值） 3000 个分区时
                        ① 查分区与文件列表 MetaStore（Thrift RPC） 1–10 ms/次，响应体随分区数线性涨 一次 MB 级响应，10–100 ms
                        ② LIST 每个分区目录 文件系统 / 对象存储 本地 µs 级；对象存储 10 ms 量级 对象存储上约 30 s
                        ③ 读每个文件 footer 存储格式 每文件一次随机读（本机实测 22 µs） 与文件数成正比

                        这张表解释了两条工程纪律：分区数要控制（几千以内；上万就该考虑隐藏分区表格式），文件数要控制（第 ②③ 步都按分区/文件数计费）。也解释了一个常见现象——在小文件多、分区多的表上，「查询规划」比「执行」还慢，因为前两步还没碰到数据就已经花了十几秒。

                        分区与分桶：一个切目录，一个切文件

                        分区：按列值切目录

                        物理上，每个唯一值一个子目录，值编码在路径里（dt=2026-10-01/data.orc）。分区列不占文件空间——Hive 读文件时从路径解析出这一列的值再补回去。这条设计有两面：

                        • 好处：分区列天然被压缩成「目录名」，不重复存储，值再长也不占数据文件。
                        • 代价：分区列基数 = 目录数。按 user_id 分区会造出百万级小目录，LIST 与规划阶段就超时（见 60.3 数据湖与湖仓一体 里对象存储 LIST 的代价）。

                        分区裁剪要生效，下面三条必须同时成立：

                        1. 谓词直接作用在分区列上：dt >= '2026-10-01'、dt IN (...) 可以；substr(dt,1,7)='2026-10'、date_format(dt,'yyyyMM')='202610'、cast(...) 不行——列被函数包住后，优化器拿不到「分区列 = 常量」的直接比较。
                        2. 字面量的字符串形式与目录名完全一致：前导零（2026-10-1 vs 2026-10-01）、时区、大小写都要对齐。不一致时通常查不出数据或裁剪失效，而 EXPLAIN 是唯一能提前发现的地方。
                        3. 裁剪开关打开：hive.optimize.ppd 等默认开启，具体配置项与默认值以官方文档为准。

                        失效的后果是「全表扫」，而且不报错——这是最难发现的一类性能事故，表现是「昨天 3 分钟，今天 90 分钟」，SQL 一个字没改，只是有人把 dt='2026-10-01' 改成了 date_format 的写法。

                        按 1 TB 的表给一遍扫描量账（30 个日分区，每分区约 34 GB）：

                        查询条件 命中分区 本机实测读取 相对全表 1 TB 表等效扫描量
                        无分区条件 30/30 8.39 MB 1.0× 1000 GB
                        dt BETWEEN '2026-10-05' AND '2026-10-09' 5/30 1.40 MB 6.0× 167 GB
                        dt = '2026-10-07' 1/30 286.5 KB 30.0× 33 GB
                        substr(dt,1,7) = '2026-10' 30/30 8.39 MB（推导同①） 1.0× 1000 GB

                        数字来源：前三行「本机实测读取 / 相对全表」来自本节末尾脚本的真实输出；第 4 行按「分区列被函数包住 = 无法裁剪」推导，等同第 1 行；「1 TB 表等效扫描量」= 实测比例 × 1 TB 推导（1 TB ÷ 30 分区 ≈ 34 GB/分区）。表大小只影响绝对值，比例与分区占比强相关，可放心外推。

                        🔑 分区裁剪的收益 = 1 ÷ 命中分区占比，与引擎无关：Hive、Spark、Trino 都能做。差别只在「谁的优化器把谓词推到了 scan 层」，以及「谁的统计信息更准」。

                        动态分区裁剪：join 时才确定分区

                        静态裁剪要求分区值在编译期已知（字面量或参数）。但数仓里最常见的模式是「事实表按 dt 分区，用维表过滤」：

                        -- 事实表的 dt 条件由维表在运行时决定，静态裁剪无从下手
SELECT f.order_id, f.amount
FROM dwd.dwd_trade_order_di f
JOIN dim.dim_shop s ON f.shop_id = s.shop_id
WHERE s.city = 'Hangzhou';

                        这时引擎得先跑维表侧、拿到命中的 dt 集合、再把集合推给事实表扫描，即动态分区裁剪（Hive 2.3+ 由 hive.optimize.dynamic.partition.pruning 控制，Hive 3 默认开启；版本行为以官方文档为准）。它把「扫 30 天」变成「扫命中天」，代价是多一次子查询执行与一次等待。判据：EXPLAIN 里出现 DynamicPartitionPruning / SemiJoin 一类节点说明生效；没有，就退化成「全表扫 + join 过滤」，扫描量差一个分区数。

                        分桶：按哈希切文件

                        CLUSTERED BY (user_id) INTO 256 BUCKETS 的含义是：写入时对 user_id 取哈希、对 256 取模，同一个桶的行写进同一组文件。物理上，桶是文件，不是目录。

                        它换来三样东西：

                        • 桶内 join（SMB，sort-merge-bucket）：两表桶数相同、join key 相同、且都按该 key 排序时，桶 i 只需和桶 i join，整个 shuffle 被消掉。对于每天都要 join 的用户宽表，这是数量级的差。
                        • 采样：TABLESAMPLE(BUCKET 3 OUT OF 32) 直接读固定文件，不需要扫全表再随机取。
                        • 文件数受控：桶数由建表时定，写入端不可能「每个批次生成一批小文件」，天然压制小文件。

                        代价同样明确：

                        • 桶数写死在表定义里，改桶数 = 重写全表；
                        • 写入必须 hive.enforce.bucketing=true，否则文件数与桶数对不上，SMB join 会读到错的数据（不报错，结果错）；
                        • 桶列基数低会倾斜：按 channel（只有 3 个值）分 256 桶，等于把 3 种值摊到 256 个桶，桶大小不可控——倾斜治理见 61.4 数据倾斜与调优。
                        分区 分桶
                        切分依据 列值本身（日期/枚举/地区） hash(列) % N
                        物理形态 目录 文件
                        数量 值的个数，日增 1 个 建表时指定 N，之后固定
                        主要收益 分区裁剪：少读目录 SMB join、TABLESAMPLE、文件数受控
                        失效方式 分区列被函数包住 → 全表扫 桶数不一致 / 未按桶写 → 错读或全 shuffle
                        基数上限 几千到几万，再多就是小目录灾难 几百到几千，取决于并行度与单文件大小
                        改造成本 加分区便宜，回刷历史要重写 改桶数 = 重写全表

                        组合用法是常态：PARTITIONED BY (dt) CLUSTERED BY (user_id) INTO 256 BUCKETS——每天 256 个桶文件，一年约 9.3 万个文件（可接受），且与用户维度表 join 时不需要 shuffle。这也顺带说明了分桶的隐藏价值：它同时是「文件数规划」手段，不只是 join 优化。

                        ORC / Parquet：把「少读」落到字节上

                        ORC 的文件结构（Parquet 同构，只是名字不同）：

                        orders.orc
 ├─ stripe 0（默认 64 MB，对应 Parquet 的 row group）
 │   ├─ index data：每 10000 行一组 min/max/偏移（orc.row.index.stride）
 │   ├─ column 0 的数据（按列压缩：ZLIB / SNAPPY / ZSTD）
 │   ├─ ...
 │   └─ column 7 的数据
 ├─ stripe 1 ...
 └─ file footer：schema + 每个 stripe 每列的 min/max/null 数

                        footer 里那几行统计信息，是「少读」的全部依据：查询带 amount >= 100000 时，引擎先读 footer，跳过 max < 100000 的整个 stripe，再对存活 stripe 里的列块按行过滤。

                        裁剪有五个层级，成本从低到高：

                        层级 依据 跳过什么 谁实现
                        分区裁剪 目录名 整个分区目录（连文件列表都不取） 查询层，Hive/Spark/Trino 都能
                        文件 / 块统计 footer、row group 的 min/max、null 数 整个文件或一个 stripe 存储格式 + 引擎
                        页级索引 ORC row index、Parquet page index 块内一段行 引擎（更细，读取成本更高）
                        列裁剪 投影下推 未选列的字节 + 解码 CPU 引擎 + 列存格式
                        bloom filter 每列哈希表（orc.bloom.filter.columns） 明确「不存在」的块（等值查询最有效） ORC

                        前四层是乘性叠加的，这一点下一节的实测会给出直接证据。第五层是补充：min/max 对「等于某个值」只能排除区间外的块，bloom filter 能对区间内不存在的值也给出否定答案。

                        ORC 与 Parquet 怎么选，先把判据摆出来：

                        维度 ORC Parquet
                        设计来源 Hive 生态（stripe） Spark/Cloudera 生态（row group）
                        块大小默认 stripe 64 MB row group 128 MB
                        统计粒度 文件 + stripe + 每万行索引 文件 + row group + page index（Parquet 1.11 起，以官方文档为准）
                        复杂类型 struct/map/array 支持早 支持广，Spark 侧最成熟
                        Hive ACID 仅 ORC 支持事务表 不支持 Hive ACID
                        默认压缩（Hive 侧） ZLIB SNAPPY
                        多引擎读取 Hive / Spark / Trino / Presto 均可 Hive / Spark / Trino / Iceberg 均可，生态更广
                        选它的典型理由 要用 Hive ACID；只在 Hive 内跑 多引擎共享；湖仓表格式（Iceberg 默认 Parquet）
                        -- 建一张"裁剪友好"的 ORC 分区桶表（Hive 3 语法；默认值以官方文档为准）
CREATE TABLE dwd.dwd_trade_order_di (
  order_id STRING, shop_id BIGINT, user_id BIGINT,
  amount BIGINT, status STRING, ts STRING
)
PARTITIONED BY (dt STRING)
CLUSTERED BY (user_id) INTO 256 BUCKETS
STORED AS ORC
TBLPROPERTIES (
  'orc.compress' = 'ZSTD',                   -- 换 IO：压缩率与解压速度更均衡
  'orc.bloom.filter.columns' = 'order_id',   -- 换等值查询：整块否定"不存在"
  'orc.create.index' = 'true'                -- 换块内定位：默认开启
);

                        三个属性各买一项能力，别混着调：orc.compress 影响 IO 与 CPU 的平衡；bloom filter 只对 col = 常量 这类等值条件有效，且会增大文件、拖慢写入，只给真正被等值过滤的列开；行索引决定了块内定位的粒度。压缩算法从 ZLIB 换 ZSTD 通常能同时改善压缩率与解压速度，但老版本 Hive/Hadoop 可能不认，改之前先确认读取端都支持（以官方文档为准）。

                        压缩率的账必须用同一份数据算。本节脚本把 48 万行、8 列的数据分别以「行存 CSV」「行存 CSV + zlib」「列存 JSON」「列存 JSON + 每列 zlib」四种形态落盘，实测：

                        形态 字节 相对 CSV 未压缩
                        行存 CSV 未压缩 52.31 MB 1.00×
                        行存 CSV + zlib 10.26 MB 5.10×
                        列存 JSON 未压缩 57.81 MB 0.90×
                        列存 JSON + 每列 zlib 8.39 MB 6.23×

                        读数：列存 + zlib 比行存 + zlib 多出约 22%（6.23 ÷ 5.10）的压缩收益。原因不神秘：同一列的值类型相同、分布相近，字典编码与 RLE 才有效；行存把不同类型混在一起，压缩器只能做通用字符串压缩。但列存真正的大头不是这 22%，而是「只解压需要的列」——这一项在下面的实测里贡献了 4.5 倍。

                        💡 我的判断：在 Hive 里选格式，先看「要不要 ACID」（要 → ORC），再看「下游引擎是谁」（Spark/Trino/湖仓 → Parquet）。两者在文本源上常见 3–6 倍压缩（本节合成数据实测 6.23 倍，真实数据取决于重复度与列类型），不要为了零点几倍的压缩率差去重构 PB 级表——迁移期的双写与回滚成本远超这点收益。

                        谓词下推不是万能的，边界要背下来：

                        写法 能否裁剪 原因
                        WHERE dt = '2026-10-01' 能 直接作用在分区列，目录名可枚举
                        WHERE dt >= '2026-10-01' AND dt < '2026-11-01' 能 范围可枚举目录
                        WHERE substr(dt,1,7) = '2026-10' 不能 函数包住列，目录名里没有「月份」这个粒度
                        WHERE cast(ts AS date) = '2026-10-01' 部分 ts 的 min/max 是原始类型的，转换后区间对不上；若 ts 就是分区列则必失效
                        WHERE amount > 100000 能（靠 min/max） 前提是金额在文件内聚簇；随机分布时统计无区分度
                        WHERE payload LIKE '%refund%' 不能 前后模糊匹配用不了 min/max；这类全文检索要靠倒排索引，见 45.1 倒排索引与分词
                        WHERE lower(channel) = 'app' 部分 列被函数包住，统计层拿不到常量比较；有的引擎能重写成 channel IN ('app','APP')，取决于版本

                        本机实测：一条 SQL 从 8.39 MB 降到 39.7 KB

                        下面的程序不是 Hive 的替代品，它只保留四个决定扫描量的机制：分区即目录、row group 的 min/max 统计、列块单独压缩、footer 记录偏移。跑它就能把「分区裁剪 / 统计裁剪 / 列裁剪」各自的贡献拆开看。

                        #!/usr/bin/env python3
"""迷你列存表：实测「分区裁剪 / row group 统计裁剪 / 列裁剪 / 小文件」的扫描代价。

自造文件格式（模仿 ORC / Parquet 的 footer + 列块 + 统计信息）：
  MAGIC | 数据块(每个 row group 一列块，zlib 压缩) ... | footer(JSON) | footer_len(8B)
footer 记录每个 row group 的字节偏移、每列 [min, max, nulls]，
于是「只进需要的分区目录、跳掉不命中的 row group、只读需要的列」都能真实测出来。
"""
import json
import os
import shutil
import statistics
import struct
import tempfile
import time
import zlib
from pathlib import Path

MAGIC = b"MCOL\x01"
COLS = ["order_id", "user_id", "dt", "status", "channel", "amount", "ts", "payload"]


def write_file(path, rows, rg_rows):
    """写一个列存文件：按 row group 切块，每列单独压缩，footer 存偏移与统计。"""
    raw = comp = 0
    blocks = []
    with path.open("wb") as f:
        f.write(MAGIC)
        for i in range(0, len(rows), rg_rows):
            chunk = rows[i:i + rg_rows]
            blk = {"rows": len(chunk), "cols": {}, "stats": {}}
            for c in COLS:
                vals = [r[c] for r in chunk]
                buf = json.dumps(vals, separators=(",", ":")).encode()
                payload = zlib.compress(buf, 6)
                raw += len(buf)
                comp += len(payload)
                blk["cols"][c] = [f.tell(), len(payload)]
                f.write(payload)
                nn = [v for v in vals if v is not None]
                blk["stats"][c] = [min(nn), max(nn), len(vals) - len(nn)]
            blocks.append(blk)
        footer = json.dumps({"rows": len(rows), "rg_rows": rg_rows,
                             "cols": COLS, "blocks": blocks},
                            separators=(",", ":")).encode()
        f.write(footer)
        f.write(struct.pack("<Q", len(footer)))
    return raw, comp


def gen_rows(dt, n):
    """订单明细：amount 随 i 单调递增（金额与时间同向聚簇，统计裁剪才有用）。"""
    rows = []
    for i in range(n):
        sec = 12 * 3600 + i
        rows.append({
            "order_id": f"o{dt[5:7]}{dt[8:10]}{i:07d}",
            "user_id": 100000 + (i * 7919) % 500000,
            "dt": dt,
            "status": ["paid", "paid", "paid", "refunded", "created"][i % 5],
            "channel": ["app", "web", "mini"][i % 3],
            "amount": 100 + i * 7,
            "ts": f"{dt} {sec // 3600:02d}:{sec % 3600 // 60:02d}:{sec % 60:02d}",
            "payload": (f"sku={i % 977};camp={i % 31};device=ios-17;"
                        f"ip=10.{(i >> 8) % 255}.{i % 255}.{(i * 3) % 255};")[:72],
        })
    return rows


def build_table(root, days=30, rows_per_day=16000, files_per_part=4, rg_rows=400,
                shuffled=False):
    root = Path(root)
    root.mkdir(parents=True, exist_ok=True)
    all_rows = []
    for d in range(days):
        all_rows.extend(gen_rows(f"2026-10-{d + 1:02d}", rows_per_day))
    if shuffled:                       # 打乱 amount：拆掉「行号↔金额」的相关性，min/max 失效
        amounts = sorted(r["amount"] for r in all_rows)
        for k, r in enumerate(all_rows):
            r["amount"] = amounts[(k * 7919 + 13) % len(amounts)]
    raw = comp = files = rgs = 0
    csv = [",".join(str(r[c]) for c in COLS) + "\n" for r in all_rows]
    csv_raw = sum(len(x.encode()) for x in csv)
    csv_gz = len(zlib.compress("".join(csv).encode(), 6))
    for d in range(days):
        dt = f"2026-10-{d + 1:02d}"
        rows = [r for r in all_rows if r["dt"] == dt]
        part = root / f"dt={dt}"
        part.mkdir(exist_ok=True)
        step = (len(rows) + files_per_part - 1) // files_per_part
        for fi in range(files_per_part):
            sub = rows[fi * step:(fi + 1) * step]      # 连续切片：保持聚簇
            if not sub:
                continue
            r, c = write_file(part / f"part-{fi:03d}.mcol", sub, rg_rows)
            raw += r
            comp += c
            files += 1
            rgs += (len(sub) + rg_rows - 1) // rg_rows
    return {"files": files, "rgs": rgs, "raw": raw, "comp": comp,
            "csv_raw": csv_raw, "csv_gz": csv_gz,
            "rows": len(all_rows), "parts": days,
            "bytes": sum(p.stat().st_size for p in root.rglob("*.mcol"))}


def read_footer(f):
    f.seek(-8, os.SEEK_END)
    (n,) = struct.unpack("<Q", f.read(8))
    f.seek(-8 - n, os.SEEK_END)
    return json.loads(f.read(n)), 8 + n


def scan(root, days=None, where_days=None, amount_min=None, need=COLS, use_stats=True):
    """三级裁剪读表：① 分区目录 ② row group 统计 ③ 列块；返回真实读到的字节数。"""
    root = Path(root)
    st = {"files": 0, "rgs_total": 0, "rgs_scanned": 0, "bytes": 0,
          "rows_seen": 0, "rows_matched": 0}
    filt = set()
    if amount_min is not None:
        filt.add("amount")
    if where_days is not None:
        filt.add("dt")
    t0 = time.perf_counter()
    for d in sorted(os.listdir(root)):
        dt = d.split("=", 1)[1]
        if days is not None and dt not in days:     # ① 分区裁剪：目录都不进
            continue
        for name in sorted(os.listdir(root / d)):
            st["files"] += 1
            with (root / d / name).open("rb") as f:
                f.read(len(MAGIC))
                footer, fbytes = read_footer(f)
                for b in footer["blocks"]:
                    st["rgs_total"] += 1
                    if use_stats and amount_min is not None:
                        if b["stats"]["amount"][1] < amount_min:   # ② 整块跳过
                            continue
                    st["rgs_scanned"] += 1
                    chunks = {}
                    for c in need:                             # ③ 只读需要的列块
                        off, ln = b["cols"][c]
                        f.seek(off)
                        buf = f.read(ln)
                        st["bytes"] += ln
                        if c in filt:
                            chunks[c] = json.loads(zlib.decompress(buf))
                    if filt:
                        dv = chunks.get("dt")
                        av = chunks.get("amount")
                        for i in range(b["rows"]):
                            if where_days is not None and dv[i] not in where_days:
                                continue
                            if amount_min is not None and av[i] < amount_min:
                                continue
                            st["rows_matched"] += 1
                    else:
                        st["rows_seen"] += b["rows"]
    st["ms"] = (time.perf_counter() - t0) * 1000
    return st


def plan_only(root, days=None):
    """只做规划：逐个文件 open + 读 footer（生成 task 之前必须付的代价）。"""
    root = Path(root)
    t0 = time.perf_counter()
    files = fbytes = 0
    for d in sorted(os.listdir(root)):
        if days is not None and d.split("=", 1)[1] not in days:
            continue
        for name in sorted(os.listdir(root / d)):
            files += 1
            with (root / d / name).open("rb") as f:
                _, fb = read_footer(f)
                fbytes += fb
    return {"files": files, "bytes": fbytes,
            "ms": (time.perf_counter() - t0) * 1000}


def best(fn, rounds=5):
    res = [fn() for _ in range(rounds)]
    out = dict(res[0])
    out["ms"] = statistics.median(r["ms"] for r in res)
    return out


def fmt(n):
    return f"{n / 1024 / 1024:.2f} MB" if n >= 1 << 20 else f"{n / 1024:.1f} KB"


def pad(s, w):
    """按终端显示宽度左对齐（中文按 2 列算）。"""
    return s + " " * max(w - sum(2 if ord(c) > 0x2E80 else 1 for c in s), 0)


def rpad(s, w):
    return " " * max(w - len(s), 0) + s


def main():
    base = Path(tempfile.mkdtemp(prefix="minihive-"))
    try:
        t0 = time.perf_counter()
        A = build_table(base / "clustered")
        B = build_table(base / "shuffled", shuffled=True)
        C = build_table(base / "smallfiles", files_per_part=40, rg_rows=400)
        print(f"建表 {time.perf_counter() - t0:.1f}s：三张表同数据量（{A['rows']:,} 行 / 30 个分区）")
        for name, t, per in [("A 聚簇", A, 4), ("B 金额打乱", B, 4), ("C 小文件", C, 40)]:
            print(f"  表 {pad(name, 12)}：{t['parts']} 分区 × {per:>2} 文件 = "
                  f"{t['files']:>4} 文件 / {t['rgs']:>4} row group / "
                  f"单文件均 {t['rows'] // t['files']:>5} 行 / {fmt(t['bytes'])}")
        print("\n压缩阶梯（同一份 480,000 行数据，8 列）")
        ladder = [
            ("行存 CSV 未压缩", A["csv_raw"]),
            ("行存 CSV + zlib", A["csv_gz"]),
            ("列存 JSON 未压缩", A["raw"]),
            ("列存 JSON + 每列 zlib", A["comp"]),
        ]
        print(pad("形态", 26) + rpad("字节", 10) + rpad("相对 CSV", 11))
        for name, n in ladder:
            print(pad(name, 26) + rpad(fmt(n), 10) + rpad(f"{A['csv_raw'] / n:.2f}x", 11))

        dts5 = {f"2026-10-{d:02d}" for d in range(5, 10)}
        dts1 = {"2026-10-07"}
        print("\n查询：WHERE dt BETWEEN '2026-10-05' AND '2026-10-09' AND amount >= 100000")
        v1 = best(lambda: scan(base / "clustered"))
        v15 = best(lambda: scan(base / "clustered", days=dts5))
        v1d = best(lambda: scan(base / "clustered", days=dts1))
        v3 = best(lambda: scan(base / "clustered", days=dts5, amount_min=100000))
        v4 = best(lambda: scan(base / "clustered", days=dts5, amount_min=100000,
                               need=["order_id", "amount"]))
        rows = [("① 全表 + 全列", v1), ("② + 分区裁剪 5/30 天", v15),
                ("③ + row group 统计裁剪", v3), ("④ + 列裁剪 2/8 列", v4),
                ("②b 只查 1 天（分区裁剪 1/30）", v1d)]
        print(pad("方案", 30) + rpad("文件", 5) + rpad("扫描 row group", 15)
              + rpad("读取字节", 10) + rpad("耗时", 8) + rpad("相对①", 7))
        for name, r in rows:
            print(pad(name, 30) + rpad(str(r["files"]), 5)
                  + rpad(f"{r['rgs_scanned']}/{r['rgs_total']}", 15)
                  + rpad(fmt(r["bytes"]), 10) + rpad(f"{r['ms']:.1f}ms", 8)
                  + rpad(f"{v1['bytes'] / r['bytes']:.1f}x", 7))

        print("\n裁剪是否改变结果（同一查询，两种读法）：")
        full = scan(base / "clustered", where_days=dts5, amount_min=100000,
                    need=["dt", "amount"], use_stats=False)
        pruned = scan(base / "clustered", days=dts5, amount_min=100000,
                      need=["dt", "amount"])
        print(f"  全表逐块过滤 = {full['rows_matched']:,} 行；分区+统计裁剪 = "
              f"{pruned['rows_matched']:,} 行 -> "
              f"{'一致' if full['rows_matched'] == pruned['rows_matched'] else '不一致'}"
              f"（读字节 {fmt(full['bytes'])} vs {fmt(pruned['bytes'])}）")

        vB = best(lambda: scan(base / "shuffled", days=dts5, amount_min=100000))
        print("\n同一条 ③ 查询，换成金额随机打散的表 B（统计信息还在，只是区间不紧）：")
        print(f"  表 A 聚簇：扫 {v3['rgs_scanned']}/{v3['rgs_total']} 块，读 {fmt(v3['bytes'])}")
        print(f"  表 B 打乱：扫 {vB['rgs_scanned']}/{vB['rgs_total']} 块，读 {fmt(vB['bytes'])}"
              f" -> 是 A 的 {vB['bytes'] / v3['bytes']:.1f} 倍")

        pA = best(lambda: plan_only(base / "clustered", dts5))
        pC = best(lambda: plan_only(base / "smallfiles", dts5))
        sA = best(lambda: scan(base / "clustered", days=dts5, need=["amount"]))
        sC = best(lambda: scan(base / "smallfiles", days=dts5, need=["amount"]))
        print(f"\n小文件：同样 5 天数据（{A['rows'] // 6:,} 行、{sA['rgs_scanned']} / "
              f"{sC['rgs_scanned']} 个 row group）")
        print(f"  表 A：规划 {pA['files']:>4} 文件 {pA['ms']:>5.1f} ms（footer {fmt(pA['bytes'])}）"
              f"；扫描 {sA['ms']:>4.1f} ms / 读 {fmt(sA['bytes'])}")
        print(f"  表 C：规划 {pC['files']:>4} 文件 {pC['ms']:>5.1f} ms（footer {fmt(pC['bytes'])}）"
              f"；扫描 {sC['ms']:>4.1f} ms / 读 {fmt(sC['bytes'])}")
        per_us = (pC["ms"] - pA["ms"]) / (pC["files"] - pA["files"]) * 1000
        print(f"  每多一个文件的本地文件系统开销 ≈ {per_us:.0f} µs（open + 读 footer）")
        print(f"  本地扫描慢 {sC['ms'] / sA['ms']:.1f} 倍；换成对象存储 10 ms/GET："
              f"表 C 光取 {pC['files']} 个 footer 要 {pC['files'] * 10 / 1000:.1f} s，"
              f"表 A 只要 {pA['files'] * 10 / 1000:.1f} s")
    finally:
        shutil.rmtree(base)

                        三条洞察，比数字本身重要：

                        1. 三项裁剪是乘性的，不是加性的：6.0 × 7.8 × 4.5 ≈ 211，与实测 216.8× 的差异来自分项取整。因为它们省的是不同集合的字节——分区裁剪省「被打开的文件」，统计裁剪省「被读的块」，列裁剪省「每块里读的字节」。只做其中一项时，另外两项的收益不会自动出现，所以「我加了分区，怎么还是慢」通常是因为表里的数据没有聚簇，统计裁剪这一层拿不到收益。
                        2. 统计裁剪最不稳定：同样的表、同样的 SQL，只把 amount 在写入时打散，累计收益从 47.7× 掉到 5.7×（8.39 MB ÷ 1.48 MB）。min/max 只有在「同列相邻行的区间很窄」时才有区分度。要稳定拿到这块收益，必须在写入端排序/聚簇：DISTRIBUTE BY ... SORT BY、SORT BY amount，或表格式的 sort order（Iceberg 的 WRITE ORDERED BY）。
                        3. 本机耗时列不能当引擎基准：耗时由 Python 的 JSON 解码主导，只当「字节数不是幻觉」的旁证。真实引擎里 ①→④ 的时间差通常小于字节差（IO 省了，行过滤的 CPU 省不掉），所以优化顺序永远是「先省 IO，再省 CPU」。

                        ⚠️ 这份实测是自造列存格式的仿真，不是真实 Hive/ORC 集群的基准：stripe 大小、编码与压缩会改变绝对值，但三种裁剪的相对关系不变。统计裁剪只跳过 87.5% 的块是因为数据量小（每块 400 行，30 个分区）；生产表的单个 stripe 是 64 MB，跳过一个 stripe 的收益按 MB 计——amount >= 100000 这类谓词在聚簇表上跳过 90% 以上的块是常态，在随机分布的表上一块都跳不掉。

                        小文件：不是审美，是乘法

                        小文件的成本是三道固定开销同时乘文件数，哪一道都绕不开：

                        成本项 量级 影响
                        任务数 ≈ 文件数（未合并时） 每 task 启动 1–3 s（JVM/容器 + 调度，工程经验值） 1,200 个文件 ≈ 20–60 分钟纯启动开销
                        NameNode 内存 每文件/目录约 150 字节量级（见 61.1 Hadoop 生态） 1 亿文件 ≈ 15 GB 堆，只能扩到顶
                        对象存储 GET 每文件至少一次请求，10 ms RTT 量级 200 个文件光取 footer 就 2.0 s（本机外推实测）

                        本机实测能测准的只有第三行的本地版本：200 个文件规划 5.4 ms vs 20 个文件 1.5 ms，单文件约 22 µs —— 本地 SSD 上门都这么便宜，所以「本机跑得好好的」完全不能证明集群没问题。真正贵的是前两项：把 22 µs 换成 1–3 s 的 task 启动，1200 个文件就是半小时起步。

                        按「1,000 个分区 × 每分区 500 个文件」算一笔账：共 50 万个文件，NameNode 元数据约 75 MB（150 字节/文件）；把每分区文件数从 500 合并到 5 个，总文件数降到 5,000、元数据约 0.75 MB，单查询规划面对的文件数下降两个数量级。文件数到千万级才会顶到 NameNode（1,000 万文件约 1.5 GB 堆，1 亿文件约 15 GB）；但规划与任务开销在几十万文件时就已经很难受，所以治理指标要看文件数，而不是「平均文件大小」——平均 1 MB、总数 500 万的表，和平均 100 MB、总数 5 万的文件，查询体验不是一个量级。

                        Hive 侧有四类缓解手段，生效范围不同：

                        • CombineHiveInputFormat（Hive 常用输入格式，是否为默认值随版本而变，以官方文档为准）：把多个小文件合并进一个 map 的 split，只减少 task 数。它不减文件 open/规划成本、不减 NameNode 元数据、不减对象存储 GET。默认值与可合并的最大 split 由 mapreduce.input.fileinputformat.split.maxsize 等控制，以官方文档为准。
                        • 作业尾部合并：hive.merge.mapfiles=true（默认，map-only 作业结束时合并）、hive.merge.mapredfiles（默认 false）、hive.merge.size.per.task（默认 256 MB）、hive.merge.smallfiles.avgsize（默认 16 MB）——平均文件小于阈值时才触发合并。
                        • 写入端控制：写分区时用 DISTRIBUTE BY dt 把同一分区压到少数 reducer，按「每文件 128–256 MB」反推 reduce 数；动态分区写入时不要按「一批一个文件」。
                        • 定期重写/compaction：INSERT OVERWRITE 重写分区，或用表格式的 rewrite_data_files（见 60.3 数据湖与湖仓一体）。这一步同时修掉「历史小文件」，而不只是防止新小文件。

                        目标值按经验定，写进建表规范才有用：

                        参数 经验值 依据
                        单文件大小 128–256 MB（压缩后） 与 HDFS block 128 MB 对齐，减少 split 边界与跨块读取
                        每分区文件数 ≤ 几十个 超过 100 个就该排合并任务
                        每 task 处理量 128 MB–1 GB 低于 128 MB 时调度开销占比显著上升
                        合并频率 与写入批次同频（每日/每次写入后） 小文件是累积量，攒一周再合成本翻倍
                        规划阶段文件数上限 单查询 ≤ 1 万文件 超过后规划时间与 metastore 压力都会成为瓶颈（经验值）

                        🔑 小文件的成本 = 每文件固定成本 × 文件数，与数据总量无关。判断要不要治理，先算「文件数 × 1–3 s」和「文件数 × 10 ms」，再看合并任务的成本——通常差两个数量级。

                        Hive ACID：能更新，但有四条硬限制

                        Hive 从 0.14 起支持事务表（ACID），Hive 2.2 起支持 MERGE INTO（版本行为以官方文档为准）。它的物理机制是「base 文件 + delta 文件」，不是原地改：

                        • 建表三条件：ORC 格式 + 分桶（CLUSTERED BY ... INTO N BUCKETS）+ TBLPROPERTIES('transactional'='true')；
                        • 写入产生 base_0000001 与 delta_0000001_0000001/ 目录；UPDATE/DELETE/MERGE 只写新的 delta 文件；
                        • 读 = base + 所有 delta 合并，读到的版本由事务 ID 决定；
                        • compactor 负责合并：minor compaction 把多个 delta 合成一个，major compaction 把 base + delta 重写成新 base。需要 hive.compactor.initiator.on=true 与 hive.compactor.worker.threads>0（配置项以官方文档为准）。

                        四条限制决定了它只能做「低频、批量、单表」的更新：

                        1. 只支持 ORC + 分桶：Parquet/Text 表不能开事务；
                        2. 单语句原子：没有跨表、跨语句事务，没有唯一约束，也没有外键；
                        3. 读放大：delta 越多读越慢，读路径要合并 base + delta，还要按事务可见性过滤；
                        4. 写放大与小文件：每次更新产生新文件，高频小更新 = delta 堆积 + 小文件灾难，compaction 追不上写入速度。

                        所以 Hive ACID 的正确用法是「维表每天合并几万行」这类场景；拿它做每秒几笔的订单状态更新，延迟、文件数、读性能三条都会崩。真正的行级更新与 CDC 入湖，优先表格式的 MOR（见 60.3 数据湖与湖仓一体）。

                        更新需求 方案 代价
                        每天重算整分区 INSERT OVERWRITE ... PARTITION 重写整个分区，历史大表成本高
                        单表低频 UPDATE 几千到几万行 Hive ACID 事务表 只能 ORC + 分桶，必须部署 compactor
                        高频 upsert / CDC 入湖 Hudi MOR / Iceberg v2 运维复杂，读放大，需要 compaction
                        毫秒级点更新、多行事务、唯一约束 OLTP 数据库 不适合分析型扫描，容量受限

                        边界：Hive、Spark SQL、Trino 各站哪一段

                        三者的共同点比差异重要：都能读同一张 Hive 表（经 HMS 或兼容 catalog），都能做分区裁剪、列裁剪、谓词下推。差别在启动开销、内存模型、容错、写入能力这四项。

                        维度 Hive（Tez / MR） Spark SQL Trino / Presto
                        定位 长批 ETL、T+1 定式报表 通用批处理、迭代计算、特征工程 交互式查询、跨源联邦
                        启动开销 十秒到分钟（量级） 秒级；常驻 thrift server 可到亚秒 亚秒到秒
                        内存模型 落盘为主，抗 OOM 内存优先，可 spill，宽表 join 易 OOM 全内存流水线，join 超内存直接失败
                        容错 task 级重试，作业能连跑数小时 stage 重试 + 血统重算 失败即整条重跑（新版有 fault-tolerant execution，需显式开启）
                        写入能力 ORC ACID 事务表 只读 Hive 表；写湖仓表格式 基本只读（部分 connector 支持写入）
                        擅长规模 PB 级、长作业 PB 级、复杂 DAG GB–TB 级交互查询
                        不擅长 交互、高并发短查询 秒级高并发、纯 SQL 联邦 超大 shuffle、需要跑几小时的容错作业

                        表中「启动开销」是工程经验量级，受集群规模、队列与并发影响，不是基准测试结果；具体版本的默认值与行为以官方文档为准。要记住的是量级关系：Hive 的启动开销是秒到分钟，Trino 是亚秒到秒。举例（量级经验值，不是基准）：扫 50 GB 的过滤聚合，Hive 的时间大头是启动与调度，分钟级；Trino 通常十几秒到几十秒。而扫 5 TB 的 ETL，Trino 可能因内存/shuffle 直接失败，Hive 能靠落盘与 task 重试跑完。

                        你的情况 选 为什么

                        复杂 Python UDF / 迭代算法 / 机器学习 Spark 内存计算与生态

                        一条 SQL 跨 MySQL + Hive + Kafka Trino connector 联邦是它的主场
                        每天 2 万次看板查询 预聚合 + OLAP 引擎 高并发点查不是 Hive/Trino 的强项

                        什么场景 Hive 仍值得用

                        Hive 被「替代」的是交互式查询和复杂计算，不是全部。下面这些场景，换引擎的收益小于迁移成本：

                        场景 判断 理由
                        已有 PB 级 Hive 表 + 稳定调度 保留 迁移成本 > 收益；HMS 已被所有引擎共享，不必搬表
                        必须「跑几小时也一定出结果」 用 Hive on Tez task 级重试 + 落盘，抗内存不足；Spark/Trino 在这类作业上更脆
                        纯 SQL 分析师 + 大量 Hive UDF 用 Hive UDF 与 HQL 方言的迁移成本最高，重写等于重写全部报表
                        一次性大表重写 / 归档到冷存储 用 Hive（或 Spark） 顺序 IO、无内存压力、失败可重试
                        低频维表更新（几万行/天） 用 Hive ACID 不引入新组件，MERGE 够用
                        交互式探索、亚秒响应 别用 启动开销 >> 计算时间
                        高频 upsert、CDC 入湖 别用 ACID 只适合低频，读放大会累积
                        跨源联邦查询 别用 用 Trino
                        小团队、GB 级数据 别用 集群运维成本高于收益，托管数仓/OLAP 更便宜

                        一句话收口：Hive 的长期价值不在执行引擎，而在「HMS + HQL + ORC」这套表与元数据的契约。引擎可以换（Tez→Spark→Trino），契约换不掉；所以「学 Hive」真正要学的是分区/分桶/格式/裁剪这套物理设计，而不是某个参数。

                        引擎选型到此为止；再往上走一层是「批与流要不要用两套引擎、口径怎么对齐」，那是另一个判断，见 61.6 批流一体。

                        生产落地：指名 → 可抄 → 可验 → 可退

                        指名：Hive 3.1.x + Tez 0.10（或 Spark 3.5 作执行引擎）+ HDFS 3.x / 对象存储；元数据库用 PostgreSQL 或 MySQL 上的 HMS（不要用 Derby：单进程、不可共享、重启即丢元数据）；替代品是 Spark SQL、Trino、托管服务（EMR / Databricks / MaxCompute）。

                        自检

                        Q1 「分区裁剪」到底跳过了什么？为什么 substr(dt,1,7)='2026-10' 会让它失效？

                        ▸ 答案：跳过的是分区目录——规划阶段连该分区的文件列表都不取，所以省下的是「文件 open + footer 读取 + 块扫描」的全部。函数包住分区列后，优化器只看到「函数(dt) = 常量」，无法把它映射回「哪些目录名匹配」，只能退化成全表扫描并逐行过滤。判断方法：看 EXPLAIN 里 TableScan 是否还带 partition 谓词；带了却仍慢，就是值格式与目录不一致（例如少前导零）。

                        Q2 实测是「分区 6.0×、统计 7.8×、列裁剪 4.5×」，为什么总收益是 216× 而不是 18.3×？

                        ▸ 答案：三项省的是不同集合的字节，且作用在同一条读取路径上，所以乘性叠加：分区裁剪决定「打开哪些文件」，统计裁剪决定「每个文件里读哪些块」，列裁剪决定「每个块里读哪些列字节」。省掉的集合互不重叠，因此 6.0 × 7.8 × 4.5 ≈ 211（实测 216.8× 的差异来自分项取整）。反过来推论：只做分区裁剪时，统计与列裁剪的收益不会自动到账——这也是「加了分区还是慢」的根因。

                        Q3 同一张表、同一条 SQL，只把金额列在写入时打散，统计裁剪的收益从 47.7× 掉到哪里？为什么？

                        ▸ 答案：掉到 5.7×（8.39 MB ÷ 1.48 MB）。min/max 只在「同列相邻行的值区间很窄」时有区分度；打散后每个 row group 的 min/max 都接近全表范围，任何块都排除不掉，200 个块全扫。结论：统计裁剪的收益来自写入布局（排序/聚簇），不是格式自带的属性；要稳定拿到它，得在写入端 SORT BY 或用表格式的 sort order。

                        Q4 Hive ACID 既然支持 UPDATE，为什么不拿它当 OLTP 用？

                        ▸ 答案：四条限制同时作用：① 只能 ORC + 分桶，很多表开不了；② 单语句原子，没有跨表事务、唯一约束；③ 读路径要合并 base + delta 并按事务过滤，delta 越多读越慢；④ 每次更新产生新文件，高频更新造成 delta 与小文件堆积，compaction 追不上。它的合理场景是「维表每天合并几万行」这类低频批量更新；毫秒级点更新属于 OLTP。

                        Q5 什么情况下该选 Trino 而不是 Hive / Spark？

                        ▸ 答案：查询要秒级返回、并发多、扫描量在 GB–TB 级、且能接受「失败就整条重跑」时选 Trino：它没有作业启动开销，全内存流水线。反过来说，跑几小时的 PB 级 ETL、需要 task 级容错、join 会超内存的场景不要选 Trino——默认不落盘、失败即整条重跑（fault-tolerant execution 需显式开启且只覆盖部分查询形状），一条查询失败就前功尽弃。Hive/Spark 在这类场景胜在「慢但一定跑完」。

                        Q6 为什么「小文件」在 Hive 里比在本地磁盘上严重得多？

                        ▸ 答案：三笔固定成本同时乘文件数：① 任务数 ≈ 文件数，每个 task 启动 1–3 s（本机脚本只测到每文件 22 µs 的本地开销，所以本地测不出问题）；② NameNode 每文件约 150 字节内存，千万文件吃满堆；③ 对象存储每文件至少一次 GET（10 ms 量级，200 个文件光取 footer 就 2.0 s）。CombineHiveInputFormat 只减少 task 数，不减后两项。

                        Q7 Hive 表的分区列为什么不占文件空间？这带来哪三个副作用？

                        ▸ 答案：分区列的值编码在目录名（dt=2026-10-01）里，Hive 读取时从路径解析补回，所以数据文件里不再存这一列。副作用：① 分区列基数 = 目录数，高基数直接变成小目录灾难；② 目录名的字符串形式必须与查询字面量完全一致（前导零、时区、大小写），否则查不到或裁剪失效；③ 分区列改名/改类型不能只改元数据，必须重写目录与全部分区。
