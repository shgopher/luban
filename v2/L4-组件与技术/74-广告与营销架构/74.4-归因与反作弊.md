# 74.4 归因与反作弊

## 一句话

> 归因是**在多个触点之间分功劳**，反作弊是**先证明这个触点不是刷出来的**；判据是——同一批转化换个模型能复算，可疑点击能被扣回，且扣量有据可查。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| last-click 最公平 | 它把 100% 功劳给最后一次点击，系统性低估品牌曝光、信息流等上游触点，按它砍预算会越砍越没量 |
| 归因窗口越长越好 | 窗口越长归因率越高，但会把自然转化算成广告效果；窗口必须与计费口径、结算规则一致 |
| 反作弊是风控团队的事 | 广告反作弊直接决定计费与结算：不识别刷量，广告主预算被刷走，续费率先崩 |

## 归因窗口：定义「哪些转化算广告的」

| 渠道类型 | 点击窗口（量级） | 曝光窗口（量级） | 说明 |
|---|---|---|---|
| 搜索 / 信息流 | 7 天 | 1 天 | 决策周期长的品类可到 15–30 天 |
| 联盟 / 网盟 | 1–7 天 | 1 天 | 长窗口易被归因劫持 |
| 品牌曝光 | 不按点击归因 | 1 天 | 通常配合增量实验评估 |
| 应用激活 | 7 天 | 1 天 | 以官方文档为准 |

本机计算（`tools/examples/74-ad-models/raw-74.4.txt`）里同一批 6 次转化，窗口从 1 小时拉到 7 天： 示例说明见 [tools/examples/74-ad-models/](../../../tools/examples/74-ad-models/README.md)。

| 归因窗口 | 可归因转化 | 占 6 次比例 | 含义 |
|---|---|---|---|
| 1 小时 | 1 | 17% | 只认「临门一脚」 |
| 24 小时 | 5 | 83% | 覆盖当天决策 |
| 72 小时 | 6 | 100% | 覆盖短决策周期 |
| 168 小时（7 天） | 6 | 100% | 覆盖长决策周期 |
| 720 小时（30 天） | 6 | 100% | 本批样本已全命中 |

> 🔑 窗口是**计费合同的一部分**：平台按窗口内转化收钱，广告主按同一窗口核账；窗口不一致，账单必然对不上——改窗口要像改价格一样走评审。

## 五种归因模型

| 模型 | 分配规则 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **last-click** | 100% 给窗口内最后一次点击 | 简单、可解释、易结算 | 低估上游、易被劫持 | 效果类短链路 |
| **first-click** | 100% 给第一次触达 | 奖励拉新与品牌 | 忽略临门一脚 | 新品冷启动 |
| **linear** | 窗口内触点平均分 | 公平、不偏袒 | 不区分触点强弱 | 多触点复盘 |
| **time-decay** | 按距转化时间指数衰减（半衰期 48 小时） | 兼顾时效 | 半衰期要调参 | 决策周期中等 |
| **position-based** | 首末各 40%，中间平分 20%（U 形） | 兼顾拉新与收割 | 规则人为设定 | 品牌 + 效果混合 |

## 同一批转化，五个模型分钱

| 模型 | 信息流 | 搜索 | 联盟 | 私域 | 合计 |
|---|---|---|---|---|---|
| last-click | 200.0 | 0.0 | 400.0 | 600.0 | 1,200 |
| first-click | 600.0 | 200.0 | 200.0 | 200.0 | 1,200 |
| linear | 283.3 | 283.3 | 283.3 | 350.0 | 1,200 |
| time-decay | 236.6 | 213.6 | 341.2 | 408.6 | 1,200 |
| position-based | 340.0 | 200.0 | 280.0 | 380.0 | 1,200 |

再看各渠道的 ROAS（归因收入 ÷ 花费，花费：信息流 300、搜索 250、联盟 150、私域 120）：

| 模型 | 信息流 | 搜索 | 联盟 | 私域 |
|---|---|---|---|---|
| last-click | 0.67 | 0.00 | 2.67 | 5.00 |
| first-click | 2.00 | 0.80 | 1.33 | 1.67 |
| linear | 0.94 | 1.13 | 1.89 | 2.92 |
| time-decay | 0.79 | 0.85 | 2.27 | 3.41 |
| position-based | 1.13 | 0.80 | 1.87 | 3.17 |

> 🔑 同一个渠道，last-click 下搜索 ROAS 是 0.00、first-click 下 0.80、linear 下 1.13：**按 last-click 砍渠道会先砍掉搜索和信息流**，而它们是路径里的首次与中间触点；砍完路径变短、总转化下降，团队却以为「砍对了」。归因结果要做预算分配，至少两种模型交叉验证，再用增量实验定案（见 [63.5](../63-推荐系统/63.5-推荐效果评估与AB.md)）。

## 反作弊：点击欺诈的五个特征

| 特征 | 判据（量级） | 处置 |
|---|---|---|
| **CTIT 过短** | 点击到安装 < 3 秒（正常量级 30 秒–10 分钟） | 过滤、不计费 |
| **单设备高频** | 单设备单日点击 > 20 次 | 扣量、限频 |
| **IP / 设备聚集** | 同 IP 或同机型批量点击 | 拉黑 IP 段 |
| **转化率异常** | 点击量大但转化率 ≈ 0，或 100% 转化 | 人工复核、停投 |
| **归因劫持** | 最后 1 秒内插入点击（click injection） | 不计费、渠道处罚 |

> 🔑 反作弊的判据不是「看起来假」，而是**能用计费规则扣回**：过滤（不计费）→ 扣量 → 拉黑，三档处置对应三种证据强度；只标记不扣钱，等于没做。

## 隐私新常态：确定性归因在缩水

iOS ATT 之后，IDFA 匹配率从接近全覆盖掉到 10%–20%（以官方文档为准），行业转向 SKAdNetwork 这类聚合归因：只有 campaign 级汇总、延迟回传、无用户级触点链。归因从「确定性匹配」退化为「概率性估计」，iOS 侧只能靠聚合数据与增量建模补。

> 🔑 隐私收紧不会让归因消失，而是让**归因从「报表工具」变成「统计推断」**：窗口、模型、样本量都要写进方法说明，否则数字不可复现。

## 代码：归因模型对比 + 作弊识别

```go
package main

import (
	"fmt"
	"math"
)

func lcg(seed uint64) func() float64 {
	x := seed
	return func() float64 {
		x = x*6364136223846793005 + 1442695040888963407
		return float64(x>>11) / float64(1<<53)
	}
}

type touch struct {
	ch string
	t  float64 // 距首次触达的小时数
}

type user struct {
	id     string
	touch  []touch
	convAt float64 // 转化时间（小时）
}

var channels = []string{"信息流", "搜索", "联盟", "私域"}

// 按归因模型把一次转化拆给各渠道，返回渠道到归因份额的映射
func credit(u user, model string) map[string]float64 {
	c := map[string]float64{}
	var valid []touch
	for _, t := range u.touch {
		if u.convAt-t.t <= 168 { // 点击归因窗口 7 天
			valid = append(valid, t)
		}
	}
	if len(valid) == 0 {
		return c
	}
	switch model {
	case "last-click":
		c[valid[len(valid)-1].ch] = 1
	case "first-click":
		c[valid[0].ch] = 1
	case "linear":
		for _, t := range valid {
			c[t.ch] += 1 / float64(len(valid))
		}
	case "time-decay":
		sum := 0.0
		w := make([]float64, len(valid))
		for i, t := range valid {
			w[i] = math.Pow(0.5, (u.convAt-t.t)/48) // 半衰期 48 小时
			sum += w[i]
		}
		for i, t := range valid {
			c[t.ch] += w[i] / sum
		}
	case "position-based": // U 形：首末各 40%，中间平分 20%
		if len(valid) == 1 {
			c[valid[0].ch] = 1
		} else if len(valid) == 2 {
			c[valid[0].ch] += 0.5
			c[valid[1].ch] += 0.5
		} else {
			c[valid[0].ch] += 0.4
			c[valid[len(valid)-1].ch] += 0.4
			share := 0.2 / float64(len(valid)-2)
			for _, t := range valid[1 : len(valid)-1] {
				c[t.ch] += share
			}
		}
	}
	return c
}

func main() {
	users := []user{
		{"u1", []touch{{"信息流", 0}, {"搜索", 48}, {"联盟", 120}}, 144},
		{"u2", []touch{{"联盟", 24}, {"信息流", 96}}, 98},
		{"u3", []touch{{"搜索", 0}, {"搜索", 72}, {"私域", 144}}, 192},
		{"u4", []touch{{"信息流", 0}, {"联盟", 12}, {"搜索", 20}, {"私域", 30}}, 31},
		{"u5", []touch{{"私域", 0}}, 2},
		{"u6", []touch{{"信息流", 100}, {"搜索", 160}, {"联盟", 200}}, 220},
	}
	const value = 200.0
	spend := map[string]float64{"信息流": 300, "搜索": 250, "联盟": 150, "私域": 120}
	models := []string{"last-click", "first-click", "linear", "time-decay", "position-based"}

	fmt.Println("=== 74.4 六次转化、四个渠道：五种归因模型各分到多少钱（每次转化 200 元）===")
	fmt.Printf("%-14s", "模型")
	for _, ch := range channels {
		fmt.Printf("%10s", ch)
	}
	fmt.Println()
	rev := map[string]map[string]float64{}
	for _, m := range models {
		row := map[string]float64{}
		for _, u := range users {
			for ch, share := range credit(u, m) {
				row[ch] += share * value
			}
		}
		rev[m] = row
		fmt.Printf("%-14s", m)
		for _, ch := range channels {
			fmt.Printf("%10.1f", row[ch])
		}
		fmt.Println()
	}

	fmt.Println("\n=== 同一笔花费，不同模型下的 ROAS（归因收入 / 花费）===")
	fmt.Printf("%-14s", "模型")
	for _, ch := range channels {
		fmt.Printf("%10s", ch)
	}
	fmt.Println()
	for _, m := range models {
		fmt.Printf("%-14s", m)
		for _, ch := range channels {
			fmt.Printf("%10.2f", rev[m][ch]/spend[ch])
		}
		fmt.Println()
	}

	fmt.Println("\n=== 归因窗口：窗口越短，能归因的转化越少 ===")
	for _, win := range []float64{1, 24, 72, 168, 720} {
		cnt := 0
		for _, u := range users {
			hit := false
			for _, t := range u.touch {
				if u.convAt-t.t <= win {
					hit = true
				}
			}
			if hit {
				cnt++
			}
		}
		fmt.Printf("窗口 %4.0f 小时 → 可归因转化 %d / 6 次（%.0f%%）\n", win, cnt, float64(cnt)/6*100)
	}

	fmt.Println("\n=== 反作弊：异常点击识别与扣量（联盟 CPC 0.60 元/次）===")
	type click struct {
		dev     int
		ctitSec float64 // 点击到“安装”的间隔
		install bool
	}
	r := lcg(7404)
	var clicks []click
	for d := 0; d < 200; d++ {
		n := 1 + int(r()*2) // 正常设备 1~2 次点击
		for i := 0; i < n; i++ {
			install := r() < 0.10
			ctit := 60 + r()*3600
			if install {
				ctit = 3 + r()*600 // 正常安装：点击后 3~603 秒
			}
			clicks = append(clicks, click{d, ctit, install})
		}
	}
	for i := 0; i < 60; i++ { // 作弊设备：60 次点击、全部 1 秒内“安装”
		clicks = append(clicks, click{999, 0.5 + r()*0.4, true})
	}

	perDev := map[int][]click{}
	for _, c := range clicks {
		perDev[c.dev] = append(perDev[c.dev], c)
	}
	suspicious := 0
	deduct := 0.0
	fastInstalls := 0
	for dev, cs := range perDev {
		fast := 0
		for _, c := range cs {
			if c.install && c.ctitSec < 3 {
				fast++
			}
		}
		if len(cs) > 20 || (fast > 10 && fast*2 > len(cs)) {
			suspicious++
			deduct += float64(len(cs)) * 0.60
			if dev == 999 {
				fastInstalls = fast
			}
		}
	}
	fmt.Printf("总点击 %d 次，设备 %d 台；判定作弊设备 %d 台（含 999 号）\n", len(clicks), len(perDev), suspicious)
	fmt.Printf("999 号设备：点击 60 次，其中 %d 次点击后 3 秒内“安装”\n", fastInstalls)
	fmt.Printf("扣量点击 %d 次，扣回 %.0f 元\n", suspicious*60, deduct)
}
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 只看 last-click 做预算分配 | 上游渠道被砍，转化路径变短，总转化下降 |
| 归因窗口随活动随意调整 | 同一笔转化在周报与月报里金额不同，无法复盘 |
| 不做点击去重 | 同一用户多次点击重复计费，广告主投诉 |
| 作弊识别只看点击率 | 高点击、零转化的刷量被放过，扣量扣不到点 |
| 扣量不通知渠道、不给明细 | 结算争议，渠道停投，平台口碑受损 |
| 用归因结果代替增量实验 | 把自然转化当成广告效果，预算持续错配 |

## 自检

**Q1** 为什么 last-click 会系统性低估品牌广告？

▸ 答案：品牌广告多出现在决策早期（首次触达），last-click 却把 100% 功劳给最后一次点击。本机计算里信息流 last-click 只分 200 元、ROAS 0.67，first-click 分 600 元、ROAS 2.00——按 last-click 砍预算会先砍掉真正拉新的渠道。

**Q2** 归因窗口从 7 天缩到 1 小时，可归因转化从 6 次降到 1 次，说明什么？

▸ 答案：说明 5/6 的转化发生在点击后 1 小时之外。窗口决定「哪些转化算广告的」：越短归因率越低但越干净，越长归因率越高但越容易把自然转化算进来；窗口必须与计费合同一致并写进结算规则。

**Q3** 同一个渠道，last-click ROAS 2.67、linear ROAS 1.89，该信哪个？

▸ 答案：都不能单独信。归因是「分功劳」规则，不回答因果；两个数差异说明渠道在不同位置价值不同。要用两种以上模型交叉验证，再跑增量实验（holdout / geo）确认「多投是否真多转化」，预算按增量 ROI 分配。

**Q4** 点击后 0.5 秒就「安装」，为什么可疑？

▸ 答案：正常用户从点击到下载、安装、首次打开通常需要几十秒到几分钟（安装包下载 + 系统安装）。0.5 秒内完成安装，只能是点击注入/伪造回传——设备上根本没发生真实安装。这类点击既不产生真实用户，还会挤占归因、抬高 CPA。

**Q5** 归因和增量实验分别回答什么问题？

▸ 答案：归因回答「转化算谁的」（分配已发生转化）；增量实验回答「没有广告这些转化还会不会有」（因果）。归因是会计问题、增量是因果问题：预算用增量，结算用归因，不能互换。

**Q6** 隐私收紧后，归因为什么从「报表」变成「统计推断」？

▸ 答案：ATT 后 IDFA 匹配率只剩 10%–20%（以官方文档为准），聚合归因只给 campaign 级汇总、延迟回传，没有用户级触点链，无法确定性匹配，只能靠增量建模与营销组合模型估计；方法、窗口、样本量必须写清，否则数字不可复现。
