                            74.1 广告系统全景

                            一句话

                            广告系统是一条「投放 → 竞价 → 计费 → 归因」的四段闭环：投放决定「给谁看、出多少钱」，竞价决定「这次曝光归谁、按什么价成交」，计费决定「按什么事件收钱」，归因决定「效果算谁的」；四段任一段口径不一致，收入与效果就对不上。

                            先破除三个误区

                            误区 现实
                            广告系统 = 推荐系统加一个出价 推荐只解决「给谁看什么」；广告还多出定价（竞价）、收钱（计费）、分钱（归因）、对账（结算）四层，每层都有独立口径
                            广告收入 = 曝光数 ÷ 1000 × CPM 收入还受填充率、eCPM 分布、无效流量、账期与扣量影响；60% 填充率下，10 万请求只有 6 万次计费曝光
                            归因只是统计报表，改改不影响业务 归因直接决定渠道结算、预算分配与广告主续费；窗口从 7 天改成 1 天，一个渠道的收入可能腰斩

                            四段与数据流

                            广告主           平台                                    媒体/用户
预算+定向+出价 →  投放服务（计划/人群/出价）→ 广告请求 →  广告位
                  ↓
                 竞价服务（eCPM 排序/定价）→ 返回赢家素材 →  曝光
                  ↓                                        ↓
                 计费服务（曝光/点击/转化事件）← 点击/转化回传
                  ↓
                 归因服务（窗口/模型/去重）→ 渠道账单 → 结算与对账
                            段 输入 输出 核心指标 失败代价 延迟预算
                            投放 预算、定向、出价、素材 可参竞的广告候选 预算消耗率、定向覆盖、在投计划数 花不出（少赚）或超花（亏损） 离线 + 分钟级生效
                            竞价 一次请求 + 候选 + 预估 pCTR/pCVR 赢家、结算价、素材 填充率、eCPM、竞价胜率 流拍（收入 0）或低价成交（拉低市场价） P99 ≤ 50ms
                            计费 曝光、点击、转化事件 计费明细与账单 计费事件数、无效流量率、扣量率 多收（客诉、退款）或少收（资损） 准实时，账单 T+1
                            归因 触点序列 + 转化事件 渠道归因结果、回传 归因率、归因窗口、去重率 渠道分错钱、预算错配 小时级到 T+1

                            🔑 四段的数据方向不一样：投放与竞价是请求时同步（必须在 50–100ms 内出结果），计费与归因是事件后异步（可以重算、可以补）。把异步段塞进同步链路，是广告系统最典型的性能事故。

                            事件量级：10 万次请求的漏斗

                            本机计算（Go，tools/examples/74-ad-models/raw-74.1.txt）按填充率 60%、CTR 2%、点击后 CVR 5% 推演： 示例说明见 tools/examples/74-ad-models/。

                            事件 数量 相对曝光 计费口径 采集方
                            广告请求 100,000 1.67 不计费 媒体 SDK / 服务端
                            曝光 60,000（填充率 60%） 1 CPM 计费事件 媒体回传 / 监测像素
                            点击 1,200（CTR 2.0%） 0.020 CPC 计费事件 落地页跳转 / 点击上报
                            转化 60（点击后 CVR 5.0%） 0.0010 CPA / oCPX 计费事件 广告主回传 / SDK

                            🔑 事件量比是 1 : 0.02 : 0.001：曝光到点击差两个数量级，点击到转化再差一个数量级。这决定了采集架构——曝光用批量上报，点击用实时回传，转化用服务端 postback 并允许延迟补报。

                            同一批流量，三种计费口径的收入

                            计费方式 单价 计费事件数 收入 折合 eCPM 风险在谁
                            CPM 12 元/千次曝光 60,000 720 元 12.00 元 广告主（曝光没转化也要付）
                            CPC 0.60 元/次点击 1,200 720 元 12.00 元 媒体（点击少则收入少）
                            CPA 30 元/次转化 60 1,800 元 30.00 元 媒体（不转化就收不到钱）

                            读数：同一批流量，CPA 口径的名义收入是 CPM 的 2.5 倍——这不是「CPA 更赚钱」，而是媒体替广告主承担了转化风险。转化率从 5% 跌到 2.5%，CPA 收入立刻从 1,800 元掉到 900 元，CPM 收入一分不少。

                            🔑 计价方式的选择本质是风险分配：CPM 把风险给广告主，CPA 把风险给媒体，oCPX 把风险部分转移给平台并通过出价约束兜底。谁的预估更准，谁就该承担风险。

                            角色全景：谁向谁收钱

                            角色 是谁 核心诉求 怎么赚钱 关键接口
                            广告主 品牌、商家、App 用最少预算拿到最多有效转化 付钱 投放 API、转化回传
                            媒体 / 流量方 App、网站、内容平台 流量变现，同时不伤体验 广告分成 广告位 SDK、OpenRTB
                            广告平台 巨量、腾讯广告、Google 等（字段与计费口径以官方文档为准） 撮合供需、稳定收入 差价 / 服务费 投放平台 + 竞价 API
                            DSP 需求方平台 代广告主跨媒体采买 服务费 / 技术费 OpenRTB bid request / response
                            SSP 供给方平台 帮媒体卖库存、设底价 分成 OpenRTB、底价策略
                            广告网络 / 联盟 聚合中小媒体 把长尾流量打包卖 分成 联盟 API、点击回传
                            监测 / 归因方 第三方监测平台（以官方文档为准） 独立归因，防止平台自说自话 服务费 postback、监测像素
                            结算 / 财务 平台财务与广告主财务 账单准确、能对账 — 账单、发票、对账单

                            与 63 推荐、67 交易的分工

                            维度 63 推荐 74 广告 67 交易
                            目标 用户兴趣匹配、体验 平台收入与广告主 ROI 的平衡 资金正确、账能对平
                            输入 用户画像、行为、内容池 画像 + 出价 + 预算 + 频控 订单、支付、退款
                            输出 内容列表 排序后的广告 + 计费事件 账务凭证、对账结果
                            核心约束 多样性、冷启动、延迟 eCPM、预算、频控、合规、延迟 幂等、对账、资损
                            判据 CTR、时长、留存 eCPM、ROI、增量 账实相符

                            🔑 三者的接缝：推荐管「匹配」，广告管「定价与结算」，交易管「钱」。广告的转化事件（下单、付费）来自交易系统，交易的账单又要和广告的计费明细对账——所以广告系统必须复用交易的幂等键，否则同一笔转化会被重复计费。

                            投放流程：编排还是编制

                            一次广告请求要串起「召回候选 → 预估 pCTR/pCVR → 排序 → 定价 → 渲染」，这是典型的编排（中心协调者按顺序调用）；而曝光、点击、转化后的计费与归因，是各服务订阅事件自行处理，属于编制。两者的可观测性与补偿方式不同：

                            环节 形态 为什么 失败怎么补
                            请求 → 竞价 编排（同步） 必须在一个响应里给出结果 超时直接降级（不出广告）
                            计费 → 归因 → 结算 编制（异步） 事件可延迟、可重放、可重算 对账补记、冲正、扣量

                            编排与编制的取舍见 28.4 服务编排与编制；广告系统的判据是：同步链路只允许「可降级」的步骤，异步链路只允许「可重放」的步骤。

                            端到端延迟预算（P99 100ms）

                            阶段 预算 超时策略
                            候选 / 召回 20ms 返回兜底广告
                            粗排 10ms 跳过，直接进精排
                            精排（含 pCTR/pCVR） 35ms 用缓存分数
                            事件落库 / 埋点 2ms 先记账、异步补
                            网络与渲染 20ms 客户端兜底

                            合计 87ms、余量 13ms——计费与归因的重算在异步链路，不占同步预算（漏斗分段与预算法见 63.1 推荐系统架构）；余量留给跨机房网络与精排抖动。

                            代码：四段漏斗与收入构成

                            package main

import "fmt"

func main() {
	const req = 100000
	const fill, ctr, cvr = 0.60, 0.020, 0.050
	imp := int(float64(req) * fill)
	clk := int(float64(imp) * ctr)
	conv := int(float64(clk) * cvr)

	fmt.Println("=== 74.1 四段数据流：10 万次广告请求 ===")
	fmt.Printf("请求 %d → 曝光 %d（填充率 %.0f%%）→ 点击 %d（CTR %.1f%%）→ 转化 %d（CVR %.1f%%）\n",
		req, imp, fill*100, clk, ctr*100, conv, cvr*100)
	fmt.Printf("事件量比 曝光:点击:转化 = 1 : %.3f : %.4f\n",
		float64(clk)/float64(imp), float64(conv)/float64(imp))

	const cpm, cpc, cpa = 12.0, 0.60, 30.0
	revCPM := float64(imp) / 1000 * cpm
	revCPC := float64(clk) * cpc
	revCPA := float64(conv) * cpa
	fmt.Println("\n=== 同一批流量的收入（三种计费口径）===")
	fmt.Printf("CPM %5.2f 元/千次曝光 → 收入 %8.0f 元，折合 eCPM %6.2f 元\n", cpm, revCPM, revCPM/float64(imp)*1000)
	fmt.Printf("CPC %5.2f 元/次点击   → 收入 %8.0f 元，折合 eCPM %6.2f 元\n", cpc, revCPC, revCPC/float64(imp)*1000)
	fmt.Printf("CPA %5.2f 元/次转化   → 收入 %8.0f 元，折合 eCPM %6.2f 元\n", cpa, revCPA, revCPA/float64(imp)*1000)

	fmt.Println("\n=== 计费风险随口径后移而放大 ===")
	fmt.Printf("转化率从 %.1f%% 跌到 %.1f%%：CPM 收入不变，CPC 收入不变，CPA 收入 %.0f → %.0f 元\n",
		cvr*100, cvr*50, revCPA, revCPA*0.5)

	type stage struct {
		name string
		ms   float64
	}
	stages := []stage{{"候选/召回", 20}, {"粗排", 10}, {"精排", 35}, {"事件落库", 2}, {"网络与渲染", 20}}
	fmt.Println("\n=== 端到端延迟预算（P99 100ms）===")
	total := 0.0
	for _, s := range stages {
		total += s.ms
		fmt.Printf("%-12s %5.1f ms\n", s.name, s.ms)
	}
	fmt.Printf("合计 %.1f ms，余量 %.1f ms\n", total, 100-total)
}

                            反模式

                            反模式 后果
                            把推荐排序直接当广告排序 没有出价与计费，广告位变免费推荐位，收入为 0
                            曝光、点击、转化三套口径各自为政 账单、报表、归因三套数字，永远对不上
                            只优化 eCPM 不看预算节奏 上午把预算花光，下午高转化时段没量
                            同步链路里做归因重算 请求超时，填充率暴跌
                            点击不做无效流量过滤直接计费 刷量团队赚走预算，广告主 ROI 归零后停投
                            计费与结算混在一起实时扣款 扣量、退款、冲正无法回滚，只能人工改账
                            归因窗口随活动随意调整 同一批转化在月报和周报里金额不同，复盘无从谈起

                            自检

                            Q1 为什么 10 万次广告请求只产生 6 万次曝光？填充率低说明什么？

                            ▸ 答案：请求要经过竞价才可能填充，填充率 = 曝光 ÷ 请求；剩余 40% 是因为没有广告参竞、出价低于底价、定向不匹配或预算耗尽。填充率低通常说明「库存卖不出去」或「定向太窄」，前者要拓客，后者要放宽定向，二者解法相反。

                            Q2 同样一批流量，CPM 收入 720 元、CPA 收入 1,800 元，能说 CPA 更赚钱吗？

                            ▸ 答案：不能。CPA 的名义单价高是因为媒体承担了转化风险：转化率从 5% 掉到 2.5%，CPA 收入就掉到 900 元，而 CPM 收入不变。判断哪个更赚，要结合转化率稳定性、退款率和账期；平台通常用 oCPX 把风险再分配一部分。

                            Q3 推荐系统与广告系统最本质的差别是什么？

                            ▸ 答案：推荐只做「匹配」——给用户排内容；广告在匹配之外多了「定价」——把出价折算成 eCPM 排序、按一价/二价成交，再按曝光/点击/转化计费并归因分钱。所以广告系统的每一个技术决策都要能回答「这值多少钱、算谁的账」。

                            Q4 为什么计费与归因不能放在同步请求链路里？

                            ▸ 答案：一次广告请求的 P99 预算只有 50–100ms，计费与归因需要等曝光/点击/转化事件、要重算、要补报，本质是异步的。放进同步链路会挤占精排预算，导致超时和填充率下降；正确做法是先落事件、异步计费归因、用对账兜底。

                            Q5 为什么说「广告系统必须复用交易的幂等键」？

                            ▸ 答案：转化事件来自交易系统（下单、付费），如果广告侧用自己的 ID 重新生成事件，同一笔订单可能被回传两次、计费两次。复用交易的订单号/支付单号做去重键，才能保证「一次转化只计一次费」，也才能和交易账单对账。
