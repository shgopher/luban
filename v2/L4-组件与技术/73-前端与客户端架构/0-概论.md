# 第 73 章 前端与客户端架构 · 概论

## 一句话

> 服务端出问题可以回滚，客户端发出去就收不回来——本章把这条不可逆性拆成**五条边界**：渲染在哪一侧生成、设备上留什么状态、一套代码铺几个平台、两侧按什么契约通信、新旧版本怎么共存；每条边界都给出判据、代价与可退方案，而不是"选个框架"。

## 5 分钟入门：先记住这 8 个词

| 词 | 一句话解释 | 生活类比 |
|---|---|---|
| **TTFB** | 从请求发出到收到响应第一个字节；SSR 把它换成了"服务端渲染耗时" | 点餐后多久先上凉菜 |
| **首屏内容就绪（`content-ready`）** | 本章自定义标记：内容进入 DOM 的时刻；与浏览器指标 FCP/LCP 不是同一口径，不能混用 | 第一盘热菜上桌 |
| **水合（Hydration）** | 服务端给的是"死 HTML"，客户端要把同一份代码再跑一遍绑上事件 | 装修好的房子要通水电才算能住 |
| **TTI 与 INP** | 两个不同指标：TTI 是主线程可稳定响应的时间点，INP 是交互延迟的分位数；SSR 都不改善，改善它们的是少 JS、少水合 | 房子能住 ≠ 水压够洗澡 |
| **bundle 体积** | 首屏必须下载并解析执行的 JS 字节数；它是移动端最贵的一笔预算 | 搬家时每件家具都要搬上楼 |
| **版本割裂** | 用户设备上同时存在多个前端版本（多标签页、未升级的 App、缓存的 SW） | 一条街上新旧两版路牌并存 |
| **tolerant reader** | 客户端遇到未知字段/未知枚举值时忽略并降级，而不是崩溃 | 收到没见过的菜名，先按"今日特色"处理 |
| **原子切换** | 一次发布只改入口 `index.html` 指向，不逐个替换资源文件 | 换整张节目单，而不是边演边换演员 |

## 一张图：这章的骨架

```
用户设备（旧代码可能已存在三个月）
  │ 73.2 设备边界：分层 / 本地缓存 / 待发队列 / 按版本灰度
  │ 73.3 平台边界：一套代码铺 Web/iOS/Android/小程序，复用率与桥接成本
  ▼
渲染（73.1 渲染边界）
  │ 内容页：服务端/边缘生成 HTML → 客户端水合
  │ 交互页：客户端渲染 → 首屏内容晚到，但水合成本为零
  ▼
契约（73.4 契约边界）
  │ schema → 生成类型/客户端 → CI 门禁；字段语义、错误码、分页
  ▼
服务端（第 28～72 章的主场）
  ▲
  │ 73.5 版本边界：入口 HTML + 不可变资源 + 共存窗口，横切上面每一层
```

- 竖看是**一次首屏的生命周期**：设备 → 渲染 → 契约 → 服务端。
- 横看是**一条统一纪律**：凡是"发到用户手里"的东西，都必须**可识别版本、可共存、可回退**；凡是"能在服务端改"的东西，就别固化到客户端。

## 本章要解决的 8 个真问题

| 问题 | 在哪一节 | 一句话答案 |
|---|---|---|
| 首屏白屏 3 秒，上 SSR 能救吗 | [73.1 前端架构](73.1-前端架构.md) | 能救"内容早到"，救不了"交互可用"：4G 下内容就绪 1,291 → 250 ms（5.2 倍），可交互只从 1,294 → 1,199 ms（7%），水合要跑同一份 JS |
| 拆了微前端，首屏反而更慢 | [73.1 前端架构](73.1-前端架构.md) | 共享依赖不共享：两个子应用各打一份 154,974 B 的公共库，首屏 JS 49.8% 是重复字节，4G 下多等 715 ms；买的是组织解耦，不是性能 |
| App 发出去三个月，老版本还在跑 | [73.2 移动端架构](73.2-移动端架构.md) | 客户端不可强更：每 4 周发一版按 N-2 支持（约 8–12 周），接口要向后兼容、功能要能远端关闭、关键路径要有强制升级兜底 |
| 弱网下用户点了"提交"，订单丢了 | [73.2 移动端架构](73.2-移动端架构.md) | 本地先落待发队列（带幂等键），联网后重放；同页 6 个请求串行 1,215 ms、并发 438 ms（2.8 倍）——"提交成功"必须由服务端确认，不能由 UI 假装 |
| 一套代码跑多端，为什么 UI 还是各写一遍 | [73.3 跨端方案](73.3-跨端方案.md) | 复用率要分三层看：一份 59,685 B 的业务逻辑源码复用率 97.2%，但两个 App 的产物字节完全一致（共享不省安装包）；UI 层只能复用结构，不能复用像素 |
| 后端改一个字段，四端各炸一次 | [73.4 前后端契约与协作](73.4-前后端契约与协作.md) | 契约要能被 CI 校验：schema 生成类型 + 破坏性变更检测；`9007199254740993` 经 `JSON.parse` 静默变成 `...992`，且与常量比较仍为 `true` |
| 列表翻页出现重复卡片、漏卡片 | [73.4 前后端契约与协作](73.4-前后端契约与协作.md) | offset 分页在数据插入时会漂移：20 条、每页 5 条，翻到第 2 页前插入 3 条 → 重复 `[16 17 18]`；删除 3 条 → 漏 `[13 14 15]`，cursor 分页 0 重复 |
| 前端灰度后一批用户白屏 | [73.5 前端发布与灰度](73.5-前端发布与灰度.md) | 旧入口 HTML 指向了已删除的旧资源 → 404，实测 `bodyTextLen=0`、`window.__V=undefined`；发布必须"资源不可变 + 旧版本保留 K 个 + 入口可切" |

## 3 个最常见误解

| 误区 | 现实 |
|---|---|
| 「前端架构 = 选框架」 | 框架只是渲染边界的实现细节；真正决定成败的是**渲染放哪一侧、契约怎么校验、版本怎么共存**三件事——选错框架可以换，选错边界要重写 |
| 「跨端 = 一套代码跑多端」 | 一套代码能跑，不等于一套代码能维护：UI 层复用率通常远低于逻辑层，桥接成本与平台差异会以"每个端各一套特判"的形式回来（[73.3 跨端方案](73.3-跨端方案.md)） |
| 「灰度 = 按比例分流」 | 没有粘性的分流是"随机给用户换版本"；没有分版本指标的分流是"看不见的灰度"；没有保留旧资源的灰度是"回滚时才发现回不去"（[73.5 前端发布与灰度](73.5-前端发布与灰度.md)） |

## 读完自检（入门级 3 题）

**Q1** 上 SSR 后内容 0.8 s 就到了，但 TTFB 从 200 ms 涨到 600 ms，用户仍说"点了没反应"。这两个变化分别来自哪里？该拿哪个指标判断？

▸ 答案：TTFB 上涨来自服务端取数 + 渲染（SSR 把成本搬到了首字节之前）；"点了没反应"是水合没完成、主线程被 JS 占着，属 TTI/INP 的问题。判断体验不能看 TTFB，要看 `content-ready` 与 hydration 结束之间的窗口；优化方向是减 JS、选择性水合，而不是把 SSR 退回 CSR（[73.1 前端架构](73.1-前端架构.md)）。

**Q2** 服务端也有不可回滚的副作用（已扣款、已发消息、已改缓存）。"服务端能回滚"这句话要怎么修正？它把客户端的版本边界推到了哪？

▸ 答案：能回滚的只有代码与配置，副作用不会跟着退（[55.3 回滚设计](../../L5-工程效能/55-发布与回滚/55.3-回滚设计.md)）。所以"服务端可回滚"不能当作可以随便删字段的理由：旧客户端会长期存在，删字段必须等最后一个版本过了兼容窗口。客户端这边只能保证三件事——入口可切、旧资源可达、新前端兼容旧后端（[73.2 移动端架构](73.2-移动端架构.md)、[73.5 前端发布与灰度](73.5-前端发布与灰度.md)）。

**Q3** 后端给订单接口加了一个必填字段，前端没改就上线，最坏的结果是什么？

▸ 答案：不是"报错"，而是**静默错**：如果前端把缺失字段读成 `undefined`/`0`，可能把"未支付"当成"已支付"、把金额 0 当成免单。这类问题在契约层就要拦住——schema 变更要能被 CI 判定为破坏性，前端类型由 schema 生成，而不是手抄（[73.4 前后端契约与协作](73.4-前后端契约与协作.md)）。
