                  73.3 跨端方案

                  一句话

                  跨端方案只有四个比较维度——复用率、渲染一致性、桥接成本、组织成本；WebView 复用最高但交互与性能最差，Flutter 一致性最好但包体与原生能力桥接最贵，RN/KMP 在中间；选型不是选最强的框架，而是选「你们团队愿意长期维护哪种失配」。

                  先破除五个误区

                  误区 现实
                  跨端 = 写一次跑五端，复用率能到 80% 以上 复用率有三种口径，同一个仓库能同时报出 97.2%、0%、100% 三个数：本机实测一份 59,685 字节的业务逻辑，「一份共享 + 2 个薄壳」的源码复用率是 97.2%，但两个 App 的产物字节完全一致（各 10,913 字节 gzip），共享对安装包的增量是 0
                  桥慢是因为 JS 慢 本机实测同源 iframe 的 postMessage 往返 13.7 µs（1000 次均值中位数），MessageChannel 只要 3.8 µs——消息通道本身不慢；慢的是每次调用都重新序列化一份 payload：1.08 MiB 对象 JSON 编解码 6.75 ms，是空载荷往返的 493 倍
                  Flutter 渲染一致，所以没有平台差异 「一致」只覆盖自绘部分。输入法、状态栏、返回手势、权限弹窗、相机预览、通知仍是原生的，包体还多带一份引擎——一致性买到的是像素，不是平台行为
                  小程序包大小限制只影响首屏 主包/分包各 2 MB、总量 30 MB（微信官方文档，服务商代开发 20 MB）。它直接决定模块边界：一份 59,685 字节的共享逻辑已占主包 2.85%，加上框架 runtime 与首页，主包预算必须按三块切
                  共享得越多，包体越小 编译期的共享只在仓库里省字节；每个 App 仍然各打一份。共享省下的是「改一处要改几份」和维护漂移，不是安装包体积

                  五种形态：七个维度一张表

                  四维是骨架，落到形态要能对着格子填。七列如下；每格数字要么带来源，要么标量级或「我的判断」——没有来源的精确数字不许进表。WebView 行的渲染模式（CSR/SSR）归 73.1 前端架构 的主场。

                  形态 UI / 逻辑复用 渲染一致性 桥接 / 通道成本 包体增量 组织成本 典型失败模式
                  WebView / Hybrid UI 100%，逻辑 100%（同一份 H5） 低：各端内核版本不同，同一份 CSS 两端表现有差 JSBridge，每次调用 ≥1 次异步投递 + JSON 序列化 小：宿主自带内核，量级 <1 MB（我的判断） 最低：一套前端，不要双端原生 长列表与手势和原生混排割裂；首屏白屏
                  React Native UI 大部分复用（落到原生控件），逻辑 90%+ 中：控件是原生的，观感随平台走 老 bridge 异步 JSON，单次量级 0.3–2 ms（我的判断，待核实） + 数 MB：JS 引擎与框架（量级，待核实） 中：JS + 双端原生各需人手 桥调用风暴掉帧；原生模块版本错配
                  Flutter UI 95%+（自绘），逻辑 95%+ 高：自绘，除平台控件与输入法 Platform Channel，单次量级 0.1–1 ms（我的判断） + MB 级：引擎随包（待核实具体值） 中高：Dart + 双端打包 + 引擎升级排期 包体与冷启动；PlatformView 混排掉帧
                  KMP / 共享逻辑 UI 0（各端原生写），逻辑 60–90% 不适用：UI 各写各的，一致性由原生保证 0 运行时通道：编译进原生产物，不是消息桥 + 百 KB 量级（我的判断） 高：Kotlin + iOS 互操作 + 双端构建 iOS 互操作摩擦；协程与线程模型错配
                  小程序 DSL UI 高（一套 DSL 多端编译，我的判断 70–90%），逻辑高 中：各平台组件实现不同 setData 跨线程序列化，成本随 payload 线性涨 主包/分包各 2 MB 上限（官方） 低–中：一套代码，多平台审核 setData 过大掉帧；平台 API 差异分支

                  调试与发布单列一张小表——它决定「出问题多久能修」，比性能更早咬人。

                  形态 调试手段 发布与回退
                  WebView / Hybrid 浏览器 DevTools，与 Web 一致 改 HTML 即生效；回退 = 切入口（73.5 前端发布与灰度）
                  React Native Metro + 原生调试器，跨 JS 与原生两层 JS bundle 可动态下发，但受商店规则约束（合规边界见 73.2 移动端架构）
                  Flutter 热重载，改代码秒级看到 走商店审核；回退 = 重新发版，没有热更通道
                  小程序 DSL 各家开发者工具，真机预览 平台审核 + 分阶段发布；回退 = 回滚线上版本

                  🔑 这张表里没有「全赢」的一行：一致性好的把成本推给包体与引擎，复用高的把成本推给交互与桥，桥接便宜的（KMP）把成本推给组织与互操作。选型 = 选你愿意长期维护的那种失配。

                  桥接成本：把「一次调用」拆成四笔

                  本小节结论

                  桥接成本不是「过一次桥多少钱」，而是序列化 + 跨线程 + 异步往返 + 类型错位四笔账的和，前两笔能用毫秒量，后两笔只能用「改几处」量。

                  第一笔：序列化，按 KB 线性收费

                  同一台机器上，1.08 MiB 的业务对象（3,629 条记录，嵌套数组 + 字符串 + 数字），10 次取中位数、3 轮取中位：

                  运行环境 JSON.stringify JSON.parse 编解码往返（实测中位数） structuredClone
                  Node v26.10.0 6.69 ms 5.58 ms 12.12 ms 13.28 ms
                  Chrome 157 headless 3.70 ms 2.95 ms 6.75 ms 6.00 ms

                  「编解码往返」是同一轮里 stringify + parse 合跑的实测中位数，不等于左两列相加（相加会多算一次字符串驻留）。两件事直接推翻两个常见假设：

                  1. 换成二进制克隆不等于免费。structuredClone 6.00 ms，与 JSON 的 6.75 ms 同一量级（差 11%）。结构化克隆省掉的是「文本 ↔ 对象」的解析，省不掉「遍历 + 复制」。
                  2. 吞吐接近内存带宽：1.08 MiB ÷ 6.75 ms ≈ 160 MiB/s，即 0.0061 ms/KiB——后面所有算式的斜率。

                  第二笔：跨线程，一次投递微秒级

                  真浏览器里用同源 iframe 做 1,000 次严格串行 ping-pong（父 → 子 → 父，收到回执才发下一次），预热 50 次后计时。核心只有十几行：

                  // 一次往返只做「投递 → 回执」，不含任何业务，测的是通道本身
function onceIframe(seq) {
  return new Promise((res) => {
    const h = (ev) => {
      // 只认自己这一帧的回执：seq 对不上就不算，避免把上一轮的延迟算进来
      if (ev.source === f.contentWindow && ev.data && ev.data.ack === seq) {
        window.removeEventListener('message', h);
        res(performance.now());
      }
    };
    window.addEventListener('message', h);
    f.contentWindow.postMessage({ ping: 1, seq }, '*');
  });
}

                  本机实测（三轮，raw/a-bridge-1..3.txt）：

                  指标 iframe postMessage MessageChannel
                  均值/次（1000 次 ÷ 总时长） 13.7 µs（三轮 14.2 / 13.1 / 13.7） 3.8 µs
                  p50 0.0 ms 0.0 ms
                  p90 / p99 0.1 / 0.1 ms 0.0 / 0.1 ms
                  max 0.6–0.7 ms 0.1–0.2 ms
                  delta 恰好为 0 的样本 865–880 / 1000 963–965 / 1000

                  performance.now() 在无跨源隔离时被钳到 0.1 ms 量级，所以 86%–88% 的样本差值是 0，p50 必然是 0；只有「总时长 ÷ 次数」的均值可信。

                  💡 我的判断是：这 13.7 µs 不是「原生桥很快」的证据，而是同一类异步消息通道的下界。headless 里的同源 iframe 大概率同渲染进程、传的是已序列化的字符串，既没有跨语言编解码，也没有真正的线程切换。真实 JSBridge 还要在这之上加第一笔（序列化）和线程跳转，量级会大 1–2 个数量级；RN 老 bridge 的公开讨论里单次调用常在毫秒级（待核实）。

                  payload 变大时，通道本身几乎不变，成本几乎全在复制与序列化：

                  payload 200 次往返总时长 单次均值 相对空载荷
                  0 B 2.6 ms 0.013 ms 1×
                  4 KiB 3.9 ms 0.0195 ms 1.5×
                  64 KiB 12.2 ms 0.061 ms 4.7×
                  256 KiB 35.4 ms 0.177 ms 13.6×
                  1 MiB 87.2 ms 0.436 ms 33.5×

                  （三轮中位数；1 MiB 单次 0.436 ms 比 JSON 编解码 6.75 ms 低一个数量级——传的是已序列化的字符串，序列化发生在哪一侧决定这笔账记在谁头上。）

                  第三笔：异步往返，串行就按次数乘

                  每次调用至少 1 次消息投递 + 1 次回程，串行 N 次就是 N 个往返。把实测斜率代进去，每帧传 N 次、每次 KB 的 JSON 序列化成本近似：

                  T(帧) ≈ N × (0.0061 × KB + 0.014)   ms        # 0.0061 ms/KiB 来自实验 B，0.014 ms 来自实验 A 空载荷
掉帧条件：T(帧) > 16.7 − 渲染时间
                  每帧调用 每次 payload 估算成本 占 16.7 ms 预算
                  10 次 64 KiB 4.04 ms 24%
                  60 次 4 KiB 2.30 ms 14%
                  200 次 1 KiB 4.02 ms 24%
                  20 次 256 KiB 31.5 ms 189%，掉帧
                  5 次 512 KiB 15.7 ms 94%，只剩 1 ms 给渲染

                  反过来算「每帧最多几次」：N_max = 16.7 / L。L = 0.0137 ms（空载荷通道）→ 1,219 次；L = 0.436 ms（1 MiB 字符串往返）→ 38 次；L = 6.75 ms（1 MiB JSON 编解码）→ 2 次；L = 1 ms（原生桥，我的判断）→ 16 次；L = 3 ms → 5 次。

                  🔑 桥接优化的第一条不是「换桥」，而是把 N 降下来：批量（N 次 → 1 次带数组的调用）、合并（同帧多次 setState 合成一次）、下沉（把计算搬到原生侧或用共享逻辑编译进去）。换 JSI、换二进制编码只能改斜率，改不了 N。

                  第四笔：类型系统错位，只能用「改几处」量

                  动态（JS）↔ 静态（Kotlin/Swift/Dart/ArkTS）的失配不在毫秒里，在字段语义：null 还是缺字段、枚举新增值谁来兜、int64 过 JS number 会不会掉精度。跨端侧的可量代价只有一条：同一个字段要改几份声明（Kotlin、Swift、Dart、TS 各一份）。判据与修法——生成类型 + CI 校验——是 73.4 前后端契约与协作 的主场，这里只记一笔账：声明份数 × 端数 就是每次改字段的手工成本。

                  复用率：三层分开算，别把「看起来复用」当复用

                  本小节结论

                  复用率必须按层报、按口径报：UI 层复用的是设计 token 与组件 API，逻辑层复用的是一份源码，基础设施层复用的只有接口与协议——第三层最容易出现「接口同形、实现各写一遍」。

                  层 真正可复用的 看起来复用、实际各写一遍的 判据
                  UI 层 设计 token（颜色/间距/字号）、组件 API 与交互状态机 导航栈、状态栏、输入法避让、权限弹窗、原生控件观感 换端后要不要写平台适配文件
                  业务逻辑层 校验规则、格式化、状态机、金额与库存计算（本机实测一份 59,685 字节） 依赖平台能力的分支（相机、定位、支付回调） 能否在 Node 里跑单测
                  基础设施层 接口定义、重试与超时策略、错误码映射 HTTP 栈（URLSession / OkHttp / fetch）、存储（SQLite / Keychain / UserDefaults / 文件）、埋点 SDK、推送（APNs / FCM） 是否要为每端各接一次 SDK

                  推送与长连接不在跨端桥里，它是独立的连接层（66.1 长连接网关）；文本层复用的是规则不是渲染，各端排版仍有差异（72.1 多语言与本地化）。

                  「复用率幻觉」破除表

                  看起来复用 实际发生的事 证据
                  「我们共享了网络层」 共享的是接口签名与重试策略；每端仍各接一套 HTTP 栈与证书校验 四端要各写一次拦截器
                  「组件库两端共用」 RN 落到原生控件、Flutter 自绘，视觉靠 token 对齐，代码是两份 组件 API 同形，实现不同源
                  「复用率 80%」 80% 是按代码行算的；按产物字节算是 0，按维护落点算要除以端数 本机实测见下表
                  「跨端框架消灭了平台差异」 差异从业务代码转移到了插件/平台通道层 插件版本与引擎版本耦合
                  「小程序一套代码多端上架」 平台 API 差异要靠条件编译分支兜 分支占比是隐性维护成本（我的判断：5%–15%，未核实）

                  字节账：把「共享」算成三个不同的数

                  造一份真实可运行的领域逻辑（86 个字段校验器 + 12 个格式化函数 + 15 条状态流转，跑起来验过输出（raw/c-logic-runs.txt）），按两种组织各放一份：

                  组织 ①  一份共享 + 2 个薄壳        组织 ②  两端各复制一份
  logic.js        59,685 B           copied/ios/logic.js      59,685 B
  ios-shell.js       845 B           copied/ios/shell.js         845 B
  android-shell.js   844 B           copied/android/logic.js  59,685 B
                                     copied/android/shell.js     844 B
                  口径 组织 ① 共享 组织 ② 复制 差额
                  仓库源码字节 61,374 121,059 +59,685（58.3 KiB）
                  每文件独立 gzip 合计 11,443 22,014 +10,571
                  两个 App 的产物字节 21,826（10,913 × 2） 21,826（10,913 × 2） 0
                  改一条规则的落点文件数 1 2 +1
                  复用率（按代码字节） 97.2% 0% —

                  S = 59,685 B（逻辑）    T = 844.5 B（两壳均值）    P = 2（端数）

                  上表最后两行最重要：同一仓库按代码字节 97.2%、按同名函数 100%、按产物字节 0。汇报口径决定你会不会为一个不存在的收益买单。

                  漂移成本是模型，不是实测：设每季度改动 N 次、每次只落到一端（按端分工）的概率为 q，则另一端的不一致处数期望 ≈ N*q。N=40、q=0.9 时约 36 处/季度——这类不一致通常不会编译报错，只会在某一端表现为「这个校验没生效」。

                  🔑 共享逻辑要共享在编译期（一份源码编进各端产物），而不是共享在运行期（一个远程 bundle 让各端解释执行）。前者省维护，后者省发版——两者都要付运行时的桥接与启动成本，别混为一谈。

                  小程序：双线程与 2 MB 主包，决定了数据粒度

                  本小节结论

                  小程序的架构约束只有两条：逻辑层与渲染层分离，跨层只能 setData；主包与单个分包各 2 MB——前者决定「一次传多少」，后者决定「代码怎么切」。

                  • 双线程模型：逻辑层跑在没有 DOM 的 JS 引擎里，渲染层是 WebView；两层不共享内存，setData 是唯一的数据通道，每次调用都要序列化一次 payload、投递到渲染层、在渲染层做 diff 再更新。
                  • setData 的序列化代价：一次传 1 MiB，光 JSON 编解码就是 6.75 ms（本机实测，Chrome 157），再加投递与 diff，一帧 16.7 ms 里传两次就到顶。所以优化方向与桥接完全一致：减小 payload、按路径更新、分批、避免整对象替换。
                  • 包大小约束：微信官方文档写明「整个小程序所有分包大小不超过 30M（服务商代开发的小程序不超过 20M）；单个分包/主包大小不能超过 2M」（分包加载 (opens new window)，2026-11-21 抓取）。
                  • 对架构的影响：主包只放启动必需 + 共享逻辑；重功能进分包或独立分包；共享逻辑 59,685 字节占主包 2.85%，框架 runtime 再占一块（参考：Taro 4.3.3 CLI 包 unpacked 497,927 字节），主包预算按「框架 + 共享逻辑 + 首页」三块分。

                  ⚠️ 把 2 MB 当成「代码体积上限」是误解：它约束上传包；引一个大图表库就可能把主包顶爆，而这类问题只在打包时暴露。

                  什么时候不该跨端

                  你的情况 判断 理由
                  重动画、重相机、重传感器、强一致 UI 的品牌应用 不做跨端 UI，最多共享逻辑 桥接与合成层都在关键路径上，掉一帧就是品牌事故
                  团队没有专人维护跨端运行时 别上 RN/Flutter/小程序框架 引擎升级、插件适配、双端打包都要有人长期接（我的判断：至少 0.5–1 人年）
                  只需要 2 个端，且原生团队已存在 原生 + 共享逻辑（KMP 或代码生成） 复用率按代码字节已能到 90%+，产物增量为 0，组织成本最低
                  5 个端，以内容展示为主 WebView / 小程序 复用 100%，交互复杂度低，桥接调用少
                  5 个端，交互重且要求像素一致 Flutter 自绘换来一致性，代价是包体与引擎维护

                  「什么时候别用」还有一条常被忽略：产品还在找 PMF 的阶段别上重跨端。需求每两周推倒一次时，跨端的抽象层会先被推倒，剩下的只有两套半成品。

                  可退

                  退路 做法 代价
                  跨端页崩溃或白屏 同路由 H5 兜底，服务端开关切到 WebView 交互降级，桥接调用变多
                  某端动态化出问题 关闭该端动态下发，回内置包 回到发版节奏
                  小程序主包超限 功能移独立分包，启动页只留骨架 首次进入多一次分包下载
                  新框架试点失败 只在一个二级页面试点，原生实现保留 双实现并存期要人去重

                  WebView 兜底还有一条安全账：WebView 里的页面是 XSS 与恶意 URL 的高危面，降级方案必须同时收口（38.6 常见攻击）。

                  反模式

                  反模式 后果
                  用「代码行复用率」给老板汇报 本机实测：源码复用 97.2%，两个 App 产物字节差 0；承诺的包体收益不存在
                  共享逻辑放在主线程，逐条桥调用 N × L 直接进帧预算：20 次 × 256 KiB 就是 31.5 ms，一帧掉三次
                  小程序 setData 整对象替换 每次都要序列化全量 payload；1 MiB 光编解码 6.75 ms，一帧两次就到顶
                  用 WebView 承载重手势与长列表 滚动与手势和原生混排割裂，且 WebView 漏洞面必须额外收口
                  选 Flutter 却没人为引擎升级排期 插件与引擎版本锁死，某端系统升级后只能整体返工
                  只在 iOS 上验证跨端一致性 Android 内核与控件差异在发布后暴露，回滚成本高于验证成本
                  只有 2 个端、原生团队已在，硬上 RN 组织成本翻倍（JS + 双端原生三套人），产物字节收益为 0

                  自检

                  Q1 汇报里写「跨端复用率 85%」，老板问「那安装包小了多少」，你怎么答？

                  ▸ 答案：先问口径。代码行口径只说明仓库里少写了几份；安装包是按产物算的，每个 App 仍然各打一份共享代码，增量为 0——本机实测两个 App 各 10,913 字节 gzip，组织 ① 与 ② 完全一致。真正省下的是「改一条规则改 1 处还是 P 处」与漂移概率；要缩小安装包得靠裁剪依赖、分包、动态下发。

                  Q2 一帧内要发 60 次桥调用、每次 4 KiB JSON，会不会掉帧？把 60 换成原生桥（单次 1 ms）呢？

                  ▸ 答案：按本机实测斜率算 60 × (0.0061 × 4 + 0.014) = 2.30 ms，占 16.7 ms 的 14%，不会掉帧。换成单次 1 ms 的原生桥就是 60 ms，一帧掉三次多。关键变量是 N 与单次成本两项，payload 在 4 KiB 这个量级上只占小头（0.024 ms / 次），所以「优化 payload」在这种场景里几乎没有收益，该做的是把 60 次合成 1 次。

                  Q3 小程序首页一次 setData 传 2 MiB 的列表，按本节斜率算，它一帧能传几次？如果产品坚持不拆列表，你会先改什么？

                  ▸ 答案：2,048 KiB × 0.0061 ms/KiB ≈ 12.5 ms 只算序列化，16.7 ms 的帧预算只剩 4.2 ms 给渲染与逻辑——一帧最多 1 次，且必然掉帧。先改的不是框架，是数据粒度：按路径更新只传变化字段、列表分页 + 虚拟滚动、把大对象拆成"首屏必需 / 滚动补全"两批。setData 的成本随 payload 线性涨，这条斜率比"换哪个小程序框架"更能决定手感。

                  Q4 KMP 的桥接成本为什么可以当 0，代价跑到哪去了？

                  ▸ 答案：KMP 的逻辑是编译进原生产物的，不存在运行时消息通道，所以没有序列化、没有跨线程投递、没有异步往返。代价转移到三处：构建（双端各编一次共享模块）、互操作（Kotlin ↔ Swift 的类型与内存模型）、组织（团队要同时会 Kotlin 与两端原生）。判据是「这段逻辑崩了能不能只修一处」——能，就适合编译期共享；不能（要热修），就只能走运行时方案并接受桥接成本。

                  Q5 团队 2 人，要同时维护 iOS/Android，产品要求重相机与复杂动画，6 个月上线。RN、Flutter、原生三选一，你写进 ADR 的三条理由与一条退出条件是什么？

                  ▸ 答案：两条硬约束先卡死：重相机预览与复杂动画会同时踩到桥接（RN）与 PlatformView 混排（Flutter），而 2 人团队养不起双端原生。我的判断是：主力用 Flutter 做自绘页面，相机/相册等硬件页用原生页嵌入——理由是自绘覆盖动画、硬件页避开 PlatformView 掉帧、一套 UI 省下第二个人。ADR 里写三条理由（团队规模、硬件密集度、UI 一致性要求）和一条退出条件（例如 3 个月内硬件页掉帧超过验收线，或包体超预算，就把该页永久留在原生侧，不再尝试跨端）。

                  Q6 「Flutter 渲染一致」这个说法，边界在哪？

                  ▸ 答案：一致的是自绘的那部分像素与布局；输入法候选框、状态栏、返回手势、权限弹窗、相机预览、通知都由系统绘制，仍然各端不同。所以「一致」要靠验收清单落定：哪些页面必须像素一致（自绘），哪些必须用平台控件（PlatformView/原生页），混排处的掉帧与手势冲突才是真实工作量。包体上还要多带一份引擎，这条是选型时必须提前认的成本。
