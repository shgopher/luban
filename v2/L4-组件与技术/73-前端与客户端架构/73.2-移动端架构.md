# 73.2 移动端架构

## 一句话

> 移动端架构的第一约束是**客户端装出去就收不回来**：不能强更、网络不可靠、内存与电量有限；所以它必须同时做到三件事——分层（业务与 UI 解耦，才敢热修与灰度）、本地优先（缓存与待发队列，网络是概率事件）、可回退（按版本灰度、降级开关、强制升级兜底）。

## 先破除五个误区

| 误区 | 现实 |
|---|---|
| 「发出去有问题，下个版本修」 | iOS 上架版本不可替换，只能重新提审；Android 的 staged rollout 能**暂停**，但已装到设备的旧包不会回滚。线上长期同时存在 N / N-1 / N-2 三个版本 |
| 「网络失败是异常，重试就行」 | 弱网是常态。本机 4G + CPU 4 倍降速实测同页 6 个请求：串行 `await` **1215 ms**，`Promise.all` **438 ms**，差 **2.8 倍** |
| 「热修能改任何逻辑」 | 热修只覆盖方法体与部分资源，改不了 Manifest/Info.plist、签名、权限、新增组件；iOS 下发可执行代码受审核条款限制 |
| 「本地缓存 = 存个 JSON 文件」 | 重启后续传要有事务、索引、幂等键。本机 SQLite 写 10 000 条 **29.4 ms**，重启后仍读到 8 000 条 pending；放内存数组则重启即 `undefined` |
| 「包大小是发布同学的事」 | 首屏 JS 每多 1 MB，CPU 4 倍降速下多 **约 270 ms** 解析执行时间（本机实测）。这还只是 CPU，没算闪存读取与内存带宽 |

## 四条后果：把「收不回来」翻译成约束

| 约束 | 直接后果 | 必须付的架构账 |
|---|---|---|
| **无法强更** | 审核周期 + 用户不升级 → 旧版本活几个月 | 服务端向下兼容（[55.5 向后兼容](../../L5-工程效能/55-发布与回滚/55.5-向后兼容.md)）、能力协商、按版本灰度、强制升级兜底 |
| **网络是概率事件** | 每次请求都可能超时、半途中断、切网 | 本地优先 + 待发队列 + 幂等键；请求合并、并发上限、超时预算 |
| **内存 / 电量 / 存储有限** | 进程随时被系统杀（iOS jetsam、Android LMK），后台不能常驻 | 状态持久化、分代缓存、批量提交 |
| **多版本长期共存** | 不能假设"所有人都在最新版" | 版本窗口、远程开关、字段与错误码兼容（[73.4 前后端契约与协作](73.4-前后端契约与协作.md)） |

> 🔑 **服务端可以回滚，客户端只能等用户升级。** 移动端架构设计本质是在为"旧版本还会活很久"付利息；利息高低由版本窗口决定。

版本窗口按发布节奏算，不按自然时间算。我的判断：每 4 周发一版按 **N-2** 支持（约 8–12 周），每季度发一版按 **N-1**（约 6 个月）。窗口定下后，服务端就不能删字段、不能改语义——否则等于逼用户升级，而用户不会听。

## 分层：四层，依赖单向

分层的判据不是目录整齐，而是两个可验证的能力：**不碰 UI 就能换数据源**，**不发版就能关掉一个功能**。

```text
presentation ──依赖──▶ domain ◀──实现接口── data
     │                    ▲                  │
     └──────用 UI 工具─────┼──────使用────────┘
                          platform（网络/存储/日志/埋点/配置，无业务语义）
```

```text
shop/
├── presentation/  # 页面与组件：只依赖 state 与 domain 用例，不认识 DTO
├── domain/        # entity / usecase / state：纯逻辑，幂等键在这里生成
├── data/          # repository 实现 / remote / local / mapper：缓存、重试、队列在这里
└── platform/      # net / storage / telemetry / config：无业务语义，可整体替换
```

依赖规则用一行命令守住（本机真跑）：

```bash
grep -rnE '^import (androidx\.|android\.|okhttp3|retrofit2|com\.google\.gson)' app/src/main/kotlin/com/example/shop/domain/
```

```text
OK: domain clean (0 forbidden imports)
domain/place_order.kt:12:import okhttp3.OkHttpClient
FAIL: domain 依赖了上层/框架
```

判据只有两条：presentation 不许 import `data.*`，data 不许 import `presentation.*`；domain 连 HTTP 与数据库都不许 import，所以它的单测不需要 mock 网络。

### 为什么业务逻辑必须与 UI 解耦

因为**只有纯逻辑才具备"不发版就能改"的能力**：

- **热修**：能动态替换的只有方法体与资源。逻辑缠在 UI 里，要么改不动，要么整页替换——后者已越过合规边界。
- **灰度**：灰度单位是"能力"不是"页面"。决策点在 usecase 时开关就是一个参数；散落在 200 个页面里，一个开关改 200 处，灰度退化成发版。
- **多端复用与可测**：同一份逻辑给 iOS/Android/Web（[73.3 跨端方案](73.3-跨端方案.md)）；domain 单测毫秒级，UI 测试分钟级还要真机。

> 💡 **我的判断**：分层的收益不在代码好看，而在故障时能降级。事故里最值钱的动作往往是"远程关掉一个功能"或"让旧版本走兼容分支"——都要求决策点不在 UI 里。

**什么时候别用这套四层**：一次性活动页、纯展示 H5、生命周期两周的营销页。它们没有长尾版本，也没有离线写入，硬套架构只会多出编译期依赖与目录成本。

## 网络是概率事件：六个请求的两种写法

同一页面、同一份数据、同一个 4G 档位，只改请求组织方式。本机实测（4G：150 ms RTT / 1.6 Mbps；CPU 4 倍降速；5 次取中位数；原始输出 `c-result.json`）：

| 页面 | 请求数 | `ready`（ms） | 相对串行 | 说明 |
|---|---|---|---|---|
| `c_serial6` | 6 | **1215** | 1.00 | 每个约 200 ms，6 个累加 |
| `c_par6` | 6 | **438** | 0.36 | 一次并发，约 1 个 RTT + 服务端 120 ms |
| `c_serial12` / `c_par12` | 12 | 2172 / **621** | — | 并发只有串行的 0.29 倍，即 1.42 倍于 6 并发 |

`par6 → par12` 只涨 1.42 倍，是**同域连接数上限**在起作用：HTTP/1.1 下浏览器对同一 origin 一般开 6 条连接，12 个请求排两波。超过连接数的"并发"只是把排队从应用层挪到浏览器。

- **首屏只留 1 层串行依赖**：HTML → 关键数据（并发）→ 渲染；串行链每多一跳多付约 200 ms。
- **合并请求**：6 个接口合成 1 个 BFF 聚合接口，省 5 个 RTT（[33.6 BFF 与 API 组合](../../L2-架构风格/33-部署形态/33.6-BFF与API组合.md)）。
- **超时预算**：由首屏目标倒推，单请求超时 = min(剩余预算, 10 s)；服务端侧的闸门是 [35.7 限流](../../L3-质量属性/35-可用性/35.7-限流.md) 与 [35.8 故障隔离](../../L3-质量属性/35-可用性/35.8-故障隔离.md)。

> ⚠️ 并发优化的是 RTT 次数，不解决带宽与依赖顺序；HTTP/2 仍受 stream 并发与 TCP 丢包重传约束。

## 本地存储分层：五种介质，一张选型表

存储不是一个数据库，而是五层介质，按"容量 × 读写频率 × 是否加密"分工；选错的典型后果是队列放 UserDefaults，写 1 万条后每次启动全量反序列化，经验上是秒级卡顿（我的判断）。

| 介质 | 典型实现 | 容量量级 | 读写量级 | 加密 | 迁移与清理 |
|---|---|---|---|---|---|
| **内存缓存** | LruCache / NSCache | 受进程堆限制 | ns–µs | 否 | 内存警告、切后台、超阈值 LRU 淘汰 |
| **KV** | MMKV / SharedPreferences / UserDefaults | KB–几 MB | µs | 否（明文） | key 前缀带版本；只放偏好、游标、开关快照 |
| **文件** | Documents / Caches | GB 级 | 顺序读写，本机 NVMe 数百 MB/s | 需自行加密 | 目录名带版本 + 迁移；Caches 可被系统清，必须可重建 |
| **SQLite** | Room / SQLDelight / GRDB | GB 级 | 本机实测 10 000 行写 29.4 ms、8 000 行扫 6.4 ms | SQLCipher 可选，敏感列脱敏 | `PRAGMA user_version` + 迁移链；按 TTL + 容量双阈值删 |
| **安全存储** | Keychain / Keystore | KB 级 | 每次解密几十 µs 到 ms | 硬件支持（Secure Enclave / TEE） | 随登录态覆盖写；登出即删，换设备失效 |

- **iOS Keychain 数据默认在 App 卸载后仍保留**，重装能读到旧令牌；Android Keystore 密钥随卸载删除。同一份"记住登录"两端行为相反，必须显式处理（首启校验、登出 `deleteAll`）。
- **UserDefaults / SharedPreferences 是明文**，令牌不能放（[38.5 数据分级与脱敏](../../L3-质量属性/38-安全/38.5-数据分级与脱敏.md)、[49.5 登录态与令牌生命周期](../49-身份与访问管理/49.5-登录态与令牌生命周期.md)）；一个数据只留一个单一事实源（通常是 SQLite），内存与文件都是派生缓存。

> 🔑 判据：**杀进程后还能重建的才是缓存；不能重建的必须落 SQLite 或 Keychain。** 待发队列属于后者。

## 离线优先与待发队列

"本地优先"不是先读缓存再发请求，而是**写路径也以本地为准**：用户点"赞"，先落本地队列并立刻给 UI 反馈，再异步发。

```
用户操作 → ① 生成幂等键 → ② 一个事务写入 outbox(pending) → ③ UI 立即成功
                                                   ↓
        ⑥ 标记 sent / dead  ←  ⑤ 服务端 2xx / 4xx  ←  ④ 后台按 seq 批量发送
```

1. **幂等键**：`device_id + ULID`（时间有序）。重试必须复用同一个 key，换 key 等于告诉服务端"这是新请求"。去重语义以 [25.4 幂等设计与去重](../../L1-分布式原理/25-并发、冲突与幂等/25.4-幂等设计与去重.md) 为准。
2. **顺序**：只要**同一聚合内有序**（同一订单、同一会话）。全局单队列会被一个卡住的请求堵死；按 `aggregate_id` 分队列，队列之间并行。
3. **重放**：按 `status + seq` 扫描，批量 50 条，指数退避 + 抖动（1/2/4 s…封顶 5 min）；一条失败不阻塞整批，但同聚合保持 `seq` 顺序。
4. **冲突**：服务端权威。客户端带 `base_version`，409 时拉最新、合并、以**新幂等键**重放——旧 key 已被消费。

失败分级决定"重试还是丢弃"，写错就会无限重试：

| 失败类型 | 动作 | 重试上限 | UI |
|---|---|---|---|
| 无网络 / DNS 失败 | 挂起，等网络恢复事件 | 不消耗次数 | 静默 |
| 超时 / 连接重置 | 退避重试 | 6 次 / 24 h | 静默 |
| 401 | 刷新令牌后重试 1 次 | 1 | 失败才跳登录 |
| 400 / 422 | 不重试，标 dead | 0 | 提示或丢弃 |
| 409 冲突 | 拉最新、合并、换 key 重放 | 3 | 静默 |
| 5xx | 退避重试 | 6 次 | 静默 |

### 实测 B：本地队列的写入与重放成本

环境：macOS arm64 / Apple 芯片、Node **v26.10.0**、内置 `node:sqlite`（`DatabaseSync`）、`PRAGMA journal_mode=WAL` + `synchronous=NORMAL`；本机 NVMe。表结构只有三件事：`seq` 自增主键、`event_id` UNIQUE（幂等键）、`(status, seq)` 联合索引（重放扫描走它）。原始输出 `tools/examples/73-frontend/s732/raw/b-write.txt`、`b-restart.txt`（说明见 [示例 README](../../../tools/examples/73-frontend/README.md)）。

```text
"rows": 10000, "writeMs": 29.4, "writePerRowUs": 2.9     # 一个事务批量提交
"dupCheck1000Ms": 9.5, "dupRejected": 1000               # 幂等键被 UNIQUE 全部拒绝
"fullScanPendingMs": 6.4, "fullScanRows": 8000           # 重放一遍 8000 条待发
"getByEventIdMs": 0.054                                  # 按幂等键单条查询
```

重启进程再读（`b-restart.txt`）：

```text
"rowsAfterRestart": 10000, "byStatus": [{"status":"pending","c":8000},{"status":"sent","c":2000}]
"maxSeq": 10000, "firstPending": [{"seq":2001,"event_id":"evt-2000-1166b6d0","status":"pending"}]
mem array in fresh process = undefined
```

同一份数据换成"每条一次隐式事务"（移动端最常见的写法）：**28.7 µs/行**，比批量提交的 2.9 µs/行慢 **约 10 倍**（`b-single-commit.txt`）。所以队列要攒批：`BEGIN` → 50 条 → `COMMIT`。

> ⚠️ 这些是本机 NVMe 上的数字。手机闪存更慢，**我的判断是慢 3–10 倍**（量级判断，未在真机验证）；"每条一提交"叠加后台被挂起，就是"点赞半小时没发出去"。

队列容量写死：≤ 5 000 条或 ≤ 20 MB；同聚合可合并；超 7 天未成功进 dead-letter。

推送与跨端同步不归这条队列管：推只负责叫醒、拉负责补全（[66.3 多端同步](../66-即时通信与音视频/66.3-多端同步.md)），长连接断开后的重连与寻址见 [66.1 长连接网关](../66-即时通信与音视频/66.1-长连接网关.md)，断网续传的水位与重放协议见 [69.4 边缘计算与断网续传](../69-物联网/69.4-边缘计算与断网续传.md)。

## 启动三态：把"冷启动慢"拆成四段

| 阶段 | 冷启动 | 温启动 | 热启动 | 可观测口径 |
|---|---|---|---|---|
| 进程创建 | 有（fork/exec、动态库加载） | 无 | 无 | 进程 start uptime → 首个 App 代码执行 |
| 框架初始化 | 有（运行时、DI、SDK 初始化） | 无 | 无 | `didFinishLaunching` / `Application.onCreate` 耗时 |
| 首屏渲染 | 有 | 有（页面被回收后重建） | 无（只切前台） | TTID（首帧）/ TTFD（完全显示） |
| 首请求 | 有 | 有 | 可能有 | 进程启动 → 第一个请求发出 |

**冷启动** = 进程不存在；**温启动** = 进程在、页面被系统回收；**热启动** = 进程与页面都在后台。三态耗时差一个数量级，混在一起取平均没有意义。口径要分位分桶：P50/P90/P99 × 设备档位 × 冷温热（[34.1 性能指标](../../L3-质量属性/34-性能/34.1-性能指标.md)）。

Android 原始口径是 `am start -W` 的 `TotalTime` 与 `Displayed`/`reportFullyDrawn`；iOS 是 `os_signpost` 与 Organizer 的启动分布。**本机没有真机与 Android 构建链，这两条未跑**。

### 实测 A：首屏 JS 体积 → 解析执行耗时

三个页面首屏 JS 为 0.3 / 1 / 3 MB，内容是真实工作量（每约 152 字节一个块：300 次整数运算 + 插入 1 个 DOM 节点，共 2 020 / 6 897 / 20 694 块），结束处 `performance.mark('content-ready')`；bundle 开头埋 `js-start`，用 `ready − js 资源 responseEnd` 近似解析执行段。环境：Chrome 157 headless（`--no-sandbox`）、macOS arm64；4G = 150 ms RTT / 1.6 Mbps。原始输出 `a-result.json`。

| 首屏 JS | fast CPU 1× | fast CPU 4× | fast CPU 6× | 解析执行（4×） | 4G+CPU 4× | 其中传输段 |
|---|---|---|---|---|---|---|
| 0（基线） | 7 | 15 | 27 | 15 | 175 | 0 |
| 0.3 MB | 41 | 122 | 185 | 110 | 1 865 | 1 783 |
| 1 MB | 102 | 298 | 456 | 284 | 5 609 | 5 333 |
| 3 MB | 315 | 862 | 1 245 | 838 | 16 210 | 15 339 |

单位 ms；均为中位数（fast 3 次、4G 2 次，丢弃首次热身）。

从 1 MB 到 3 MB，解析执行从 284 ms 涨到 838 ms，斜率 = `(838−284) ÷ 2 MB ≈ **277 ms/MB**`；0.3→1 MB 段是 `(284−110) ÷ 0.7 ≈ 249 ms/MB`。取整：**每 MB 首屏 JS 在 CPU 4 倍降速下 ≈ 270 ms**。同一区段在 CPU 1 倍时 ≈ 97 ms/MB、6 倍时 ≈ 393 ms/MB，随降速倍数近似线性——说明这段开销主要是解析、执行与 2 万个 DOM 节点的布局，不是网络。

> ⚠️ CPU 降速只是**代理**，不是真机：它只放大 CPU 执行，没有放大内存带宽、闪存读取、GPU 合成与低端机的小缓存。真机的解析执行只会比这更长。

4G 下 3 MB 页面 `ready` 16 210 ms，传输段 15 339 ms（理论 `3 MB × 8 ÷ 1.6 Mbps ≈ 15.7 s`），解析 871 ms：**弱网首屏约 95% 时间在下载**；换到 WiFi 或缓存命中，解析才成为主项。

启动预算按四段分配。我的判断：进程创建 + 框架初始化 ≤ 400 ms，首帧 ≤ 800 ms，首请求放前台可见之后；首帧前不做网络、不做全量迁移、不初始化 SDK。

## 包大小与崩溃率：两条能自动拦发布的门禁

| 指标 | 建议阈值（**我的判断**） | 口径 | 不达标动作 |
|---|---|---|---|
| Android 首装下载（AAB 分渠道后） | ≤ 30 MB；30–60 MB 警告；> 60 MB 阻断 | Play Console 下载大小 | 阻断发布，出体积 diff |
| crash-free sessions | 全量 ≥ 99.5%，灰度批次 ≥ 99.7% | 崩溃 SDK 会话口径 | 自动暂停放量 |

算式可验：4G 实测 1.6 Mbps，30 MB ≈ `30×8÷1.6 = 150 s`，60 MB ≈ 300 s。装一个 App 等 2.5–5 分钟，安装转化会掉——这是 30 MB 的来源，不是行业惯例。

门禁要能**自动暂停**：Android 用 Play Developer API 暂停 staged rollout（通用策略见 [55.1 发布策略](../../L5-工程效能/55-发布与回滚/55.1-发布策略.md)）；iOS 在配置中心把 `rollout_percent` 降到 0，15 分钟内要有人响应。符号化文件（`mapping.txt` / dSYM）必须上传，否则崩溃栈不可读。

## 版本治理：按版本灰度、强制升级、热修的边界

客户端版本是最好的灰度键：天然批次，不会因用户换设备而漂移。服务端下发策略，客户端据此决策：

服务端返回的最小策略是四个字段：`min_supported` / `latest` / `force` / `store_url`，一条 JSON 小于 1 KB。

| 版本区间 | 服务端 | 客户端 | 备注 |
|---|---|---|---|
| `v >= latest` | 全功能 | 正常 | 基线 |
| `min_supported <= v < latest` | 全功能 + 兼容分支 | 非阻塞升级提示（可关 7 天） | 大多数用户在这里 |
| `v < min_supported` | 关键接口返回 426 + 最低版本 | 强制升级页，只留"去升级/退出" | 掉活跃，慎用 |

客户端更新要配合入口与资源切换（[73.5 前端发布与灰度](73.5-前端发布与灰度.md)）：商店放量按天，兼容分支按周，两者不能同时切。

强制升级是唯一能"收回"已发版本的合法手段，代价是掉活跃。我的判断：只在安全漏洞、资损风险、协议不兼容到无法降级时用，其余用"非阻塞提示 + 服务端降级"。iOS 无法静默更新，只能跳 App Store；Android 可用 Play In-App Updates 减少跳转损耗。

### 热修的合规边界

热修不是发版通道，是止血带。能不能用取决于"改的是什么"：

| 想改什么 | Android 热修（Tinker 类） | iOS | 合规替代 |
|---|---|---|---|
| 方法体里的逻辑 bug | 可以（dex 方法替换） | 不允许下发可执行代码 | 远程开关关掉该功能 |
| 资源 / 文案 | 部分可（资源补丁） | 不允许（需重新提审） | 服务端下发文案/图片（[72.1 多语言与本地化](../72-国际化与多地域/72.1-多语言与本地化.md)） |
| 新增页面/功能 | 不行（组件、权限、Manifest 改不了） | 不行 | H5/WebView 页面，且不得改变 App 主要功能 |
| 紧急关停 | 远程开关 | 远程开关 | 唯一无争议的"热修" |

- **iOS**：审核指南要求 App 自包含，禁止下载、安装、执行会引入或改变功能的代码；系统自带的解释器（WebView 走 WKWebView，RN 走 JavaScriptCore/Hermes）执行 JS 是允许的，但不得借此绕过审核改变主要功能——两条链路的审核判据要分别看。**具体条款号与措辞随版本调整，以官方原文为准**；2017 年苹果要求移除 JSPatch 类热修是公开事件，边界不是"任意代码"。
- **Android**：热修能替换方法体，改不了签名、权限、`AndroidManifest`、新增四大组件；Google Play 对"绕过商店更新自身"的政策同样适用，**以官方政策原文为准**。
- 结论：**能热修的是"逻辑开关"，不是"功能本身"**——要在架构阶段把可关的点设计出来（[55.2 特性开关](../../L5-工程效能/55-发布与回滚/55.2-特性开关.md)）。

## 生产落地：指名 → 可抄 → 可验 → 可退

| 能力 | 选一个 | 替代 | 关键约束 |
|---|---|---|---|
| 崩溃/ANR | Firebase Crashlytics | Sentry（自托管可控数据） | 必须上传符号表；采样率可远程调 |
| 本地 KV / 结构化存储 | MMKV + SQLite + Room（Android）/ GRDB（iOS） | SharedPreferences / SQLDelight | MMKV 明文不能放令牌；schema 迁移必须可测 |

**可抄**：一个能直接跑的最小 outbox（Node 26 内置 `node:sqlite`，零依赖），演示 schema、幂等键、WAL 与批量提交：

```bash
node -e 'const {DatabaseSync}=require("node:sqlite");const d=new DatabaseSync("/tmp/outbox.db");
d.exec("PRAGMA journal_mode=WAL;PRAGMA synchronous=NORMAL;CREATE TABLE IF NOT EXISTS outbox(seq INTEGER PRIMARY KEY,event_id TEXT UNIQUE,status TEXT);CREATE INDEX IF NOT EXISTS ix ON outbox(status,seq)");
const q=d.prepare("INSERT OR IGNORE INTO outbox VALUES(?,?,?)");d.exec("BEGIN");
for(let i=0;i<10000;i++)q.run(i,"evt-"+i,"pending");d.exec("COMMIT");
console.log(d.prepare("SELECT COUNT(*) c FROM outbox").get());'
```

```text
[Object: null prototype] { c: 10000 }     # 本机真跑；db 4,096 B + WAL 3,522,632 B（未 checkpoint）
```

**可验**（原始输出在 `tools/examples/73-frontend/s732/raw/`）：

| 检查项 | 期望 | 原始输出 |
|---|---|---|
| 写入 / 去重 | 单事务 29.4 ms；1000 个重复 key 全被拒 | `b-write.txt`：`writeMs: 29.4`、`dupRejected: 1000` |
| 重放 / 重启 | 8 000 条扫 6.4 ms；重启后仍在；违规 import 直接失败 | `fullScanPendingMs: 6.4`、`rowsAfterRestart: 10000`、`d-layering-gate.txt` |

**可退**：`outbox.enabled=false` 退回直连请求（弱网下操作会失败）、`rollout_percent=0` 停止放量（新功能不可用）、`min_supported` 回退一版（旧客户端继续可用）；三个开关都在配置中心在线改，默认值取安全侧。

## 反模式

| 反模式 | 后果 |
|---|---|
| UI 里直接 `fetch + setState`，没有 usecase 层 | 热修改不了、开关散落、两端各写一份，同一 bug 修三次 |
| 队列放 UserDefaults / SharedPreferences | 每次启动全量反序列化，冷启动多几百 ms；无事务，杀进程丢一半 |
| 重试时换新的幂等键 | 服务端无法去重，一次点赞变 5 条，只能人工对账 |
| 全局单队列、严格全局有序 | 一个卡住的请求堵死全部，弱网下队列雪崩 |
| 首屏串行 6 个接口、各超时 30 s | 实测串行 1215 ms vs 并发 438 ms；最坏等 180 s |
| 崩溃率只看版本、不接自动暂停 | 灰度批次崩了还在放量，1 小时后全量用户在崩 |

## 自检

**Q1** 一个功能上线后发现严重 bug，服务端能不能"回滚"？客户端能不能回滚？

▸ 答案：服务端能回滚代码与配置，但数据、消息、缓存的副作用可能不可逆（[55.3 回滚设计](../../L5-工程效能/55-发布与回滚/55.3-回滚设计.md)）。客户端**不能回滚**：iOS 上架版本不可替换，Android 只能暂停放量。替代只有三条：远程开关、服务端兼容、强制升级。

**Q2** 为什么待发队列的幂等键必须在"用户点下按钮"时生成，而不能在"真正发请求"时生成？

▸ 答案：幂等键标识**一次用户意图**，不是一次 HTTP 请求。发送时生成，重试与重启续传就会换新 key，服务端无法识别为同一件事，结果重复提交。key 要随事件落库、重放原样取出；只有"冲突合并后重新提交"才换。

**Q3** 首屏 12 个请求里 11 个各 200 ms、1 个慢接口 3 s，全部 `Promise.all`。首屏内容什么时候出来？你会怎么改？

▸ 答案：`Promise.all` 等最慢的那个，首屏约 3 s + 渲染（并发只省 RTT，省不掉木桶效应）。改三处：把慢接口移出首屏（骨架 + 懒加载）、给每个请求独立超时预算 `min(剩余预算, 10 s)`、用 `Promise.allSettled` 先渲染已就绪部分并把慢块标"加载中"。判据是"首屏可用的最小数据集"，不是"所有请求都完成"。

**Q4** 手机闪存按本机 5 倍慢算，后台每 30 s 只给一次执行窗口；10 万条待发事件"每条一提交"要多久？怎么改？

▸ 答案：`100 000 × 28.7 µs × 5 ≈ 14.4 s` 的 CPU 时间，但被切成 3,333 个 30 s 窗口，实际拖到十几分钟以上——这是"点赞半小时没发出去"的算术来源。改法：批量提交（2.9 µs/行，约 1.45 ms/条 → 10 万条约 145 ms 分散到窗口里）+ 同聚合合并 + 队列上限（5,000 条/20 MB）+ 超期进 dead-letter。提交粒度与批次上限，比换数据库更能决定体验。

**Q5** 首屏 JS 从 1 MB 涨到 3 MB，4G 下首屏慢了约 10 秒，其中多少是下载、多少是解析执行？怎么分别量？

▸ 答案：下载直接算 `2 MB × 8 ÷ 1.6 Mbps ≈ 10 s`；解析执行看 `ready − js 资源 responseEnd`，CPU 4 倍降速下约 **270 ms/MB**（实验 A）。下载靠拆包/压缩/预加载，解析靠减代码与延迟执行，只报 `ready` 无法区分。

**Q6** 团队想用热修直接改"支付按钮文案 + 新增一个活动页"，Android 与 iOS 各自可行吗？

▸ 答案：都不该走热修。文案属资源：Android 资源补丁只覆盖部分场景，iOS 必须重新提审；新增页面两端都要发版，热修改不了 Manifest/Info.plist、权限、签名与新增组件。替代方案是服务端下发文案（[72.1 多语言与本地化](../72-国际化与多地域/72.1-多语言与本地化.md)）、活动页走 H5/WebView 容器。
