                                73.4 前后端契约与协作

                                一句话

                                前后端契约不是接口文档，而是一份能被 CI 校验、能被编译器检查的兼容性承诺；前端侧真正会炸的是字段语义（null/缺失/精度/时间/枚举）与错误码分支——契约里没写清的，后端改一个字段，四端就各错一次。

                                先破除 5 个误区

                                误区 现实
                                “有 OpenAPI 文档就有契约” 文档不参与编译：amount 从 int64 改成 string 仍然合法；覆盖进仓库后 tsc 才报 TS2551
                                “契约是后端单方面定的” 精度损失只发生在前端。9007199254740993 经 JSON.parse 变成 9007199254740992，后端日志里永远是正确的那个值
                                “字段没给就是没有” null、缺失、""、0、[] 五种写法，Go 能区分 3 种状态，JS 只当“值”
                                “加字段一定安全” 加一个必填 idempotency_key，老客户端第一次提交就 400；加一个枚举值，前端穷举 switch 编译失败 TS2322
                                “前端按 message 提示就行” message 可改、可翻译、可拼接；稳定的是 code 与 HTTP 语义

                                契约的三层可校验性：schema → 生成物 → CI 门禁

                                契约只有在三个位置同时被机器读，才算成立。

                                层 产物 校验发生时机 谁执行 缺了这一层
                                ① 机器可读 schema openapi.json / .proto / schema.graphql PR 评审 + lint 接口 owner（后端） 语义只剩口头约定
                                ② 生成的类型与客户端 types.ts / client.go 编译期 前端 CI（tsc、go build） 类型与实现各写一份，编译器帮不上忙
                                ③ CI 门禁 重生成 diff + 破坏性变更报告 合并前 平台或前端 CI 破坏性变更直达主干

                                第二层不保证生成物与上一版兼容；把两者都做成 CI 失败条件，契约才从形容词变成动词。

                                谁声明、谁生成、谁入库、谁锁版本

                                技术栈 谁声明 谁生成 谁入库 谁锁版本
                                OpenAPI 后端接口 owner 前端 CI 跑 orval；Go 侧 oapi-codegen 前端入库 commit SHA + 生成器 lockfile
                                proto 服务 owner（字段号终身） buf generate 入库或发私有包 buf.lock + BSR 标签
                                GraphQL schema owner（通常是 BFF） graphql-codegen 前端入库 schema 版本 + 客户端版本头

                                按端裁剪是 33.6 BFF 与 API 组合 的职责；契约仍由服务层声明，BFF 只做投影。

                                🔑 生成物必须入库。 发包能锁版本，却看不见 diff：后端改字段会表现成“前端升级依赖后页面报错”。入库的 diff 就是契约变更记录。流水线见 52.6 代码生成。

                                字段语义矩阵：同一个 null，三种业务含义

                                真正会炸的是“这个字段没值”表示什么；三种业务含义必须在契约里各有确定的 wire 表示。

                                wire 形态 未设置 已清空 无权限
                                字段缺失 唯一可靠（PATCH） 不可区分 与“未设置”同形
                                null 需约定（PATCH=不修改） 推荐，标 nullable 不可用
                                "" 不用 仅 string 可用 不可用
                                0 不用 有歧义（0 值与清空同形） 不可用
                                [] 不用 仅列表可用 不可用

                                无权限只能用 HTTP 403 或 visible: false + 脱敏值表达，任何字段形态都不行。

                                实测其中四种 wire 形态的解码结果（matrix.go）：

                                | 字段缺失 | false | `` | true | &lt;nil> | 未设置（字段根本没出现） |
| 显式 null | true | `null` | true | &lt;nil> | 已清空（显式置空） |
| 空串 | true | `""` | false | "" | 已清空（空串，与 null 同义或不同义取决于约定） |
| 数字 0 | true | `0` | false | "" | 类型不合法（契约违约） ← 解码报错 |

                                🔑 “字段缺失”与 null 在 Go 里可区分（presence map + 指针），null 与 "" 也可区分；但“未设置”与“无权限”在报文里完全同形，只能靠 403 或 visible 这类额外信号。

                                [] 单独说：空数组是“确实没有订单”，与“无权限”必须分开——前者渲染空状态图，后者渲染“申请权限”，靠 visible 或 403 区分，别让前端猜 items.length === 0。

                                💡 我的判断是：null = 显式清空、缺失 = 不修改，只在 PATCH 下成立；PUT 全量时缺失必须视为违约直接 400，否则“漏传一个字段”会静默变成“清空一个字段”，这是最难查的数据丢失。

                                数字：int64 一过 2^53 就静默改值

                                JSON 数字没有精度声明，JS 的 number 是双精度，安全上限 2^53 - 1 = 9007199254740991；超过之后不报错、不警告，直接给邻近的可表示值（precision.mjs）：

                                Number.MAX_SAFE_INTEGER + 2           = 9007199254740992
9007199254740993 === 9007199254740992 ? true
JSON.parse('{"id":9007199254740993}')  = { id: 9007199254740992 }
雪花 ID 1234567890123456789  解析后     = 1234567890123456800
JSON.stringify({id: BigInt}) 抛出       = TypeError: Do not know how to serialize a BigInt

                                一个反直觉细节：parsed.id === 9007199254740993 竟然是 true——字面量在比较前已被解析成 ...992，两边都错所以相等，任何“前端与常量比一下”的测试都会假通过。另外 JSON.stringify 遇到 BigInt 直接抛错，回写必须转字符串。

                                Go 侧无损，两种形态互斥（semantics.go）：

                                解码后 ID=9007199254740993  IDStr=9007199254740993
string -> int64(无 ,string tag)                       => ERROR: json: cannot unmarshal string into Go struct field Payload.id of type int64
number -> int64(带 ,string tag)                       => ERROR: json: cannot unmarshal number into Go struct field Payload.id_str of type int64
                                值 Go int64 Go 标签 ,string JS JSON.parse JS BigInt
                                9007199254740993 精确 精确 变成 ...992 精确
                                1234567890123456789 精确 精确 变成 ...800 精确

                                🔑 契约里所有 int64 字段，wire 上写成 string（type: string, format: int64）。前端不做数值运算的 ID 一律用 string 接；要运算的（金额、计数）在展示层格式化，不 parseFloat。

                                我见过的多数生成器默认把 int64 映射成 number（经验判断，具体看生成器配置），schema 写成 integer，前端就永远拿不到精确值。

                                时间：三种形态，只有一种该进契约

                                time.Time 的挑剔程度超出前端预期（semantics.go）。

                                RFC3339 带偏移 +08:00       => 2026-11-21T19:00:00+08:00 (UnixMilli=1795258800000, Location=Local)
RFC3339 UTC 带 Z          => 2026-11-21T11:00:00Z (UnixMilli=1795258800000, Location=UTC)
毫秒时间戳(数字)                => ERROR: json: cannot unmarshal number into Go struct field WithTime.t of type time.Time

                                +08:00 与 Z 指向同一毫秒，两者等价；裸时间戳进不来。前端侧同样的坑（time.mjs）：

                                new Date("2026-11-21T19:00:00+08:00")          => 2026-11-21T11:00:00.000Z | ms = 1795258800000
new Date("2026-11-21T19:00:00Z")               => 2026-11-21T19:00:00.000Z | ms = 1795287600000
new Date(1795258800)                           => 1970-01-21T18:40:58.800Z | ms = 1795258800

                                同为“19:00:00”，带 +08:00 与带 Z 差 8 小时；不带偏移的 2026-11-21T19:00:00 按运行环境时区解析（本机 Asia/Shanghai 恰好等于 +08:00，换台机器结果就变）。1795258800 与 1795258800000 差 1000 倍且不报错。契约只有一条：wire 一律 RFC 3339 带偏移（推荐 Z），禁止裸时间戳、裸日期与无偏移的本地时间。时区归属与夏令时属于 72.2 的主场，见 72.2 多时区处理。

                                枚举、大小写与命名

                                把 refunded 塞进 status，后端只改一行，前端有四种反应：

                                读法 实测结果 结论
                                严格枚举（白名单） err=unknown enum value "refunded" 最安全，但必须能降级
                                宽容解析（按 string 读） err=<nil>，渲染“未知状态” 推荐：未知值降级，不阻断页面
                                穷举 switch 无 default 渲染 "" 像“数据丢失”，排查成本极高
                                生成类型 + never 穷举 TS2322: Type '"refunded"' is not assignable to type 'never' 编译期暴露，前提是生成物已更新

                                🔑 客户端默认宽容读取，但枚举必须写 default。 后端承诺“只增不删”，前端承诺“未知值有兜底”；缺一条，新增枚举值就是一次白屏。

                                命名混用不是“不好看”，而是同一字段在两端叫两个名字：前端写 order.userId、后端返回 user_id，TS 编译通过，运行时永远 undefined。

                                位置 常见写法 现实约束
                                JSON body user_id / userId / UserID 大小写敏感，取不到就是 undefined
                                Query / 路径 user_id=1、/users/{userId} 大小写敏感；与 body 风格不一致时生成两套命名
                                Header X-Request-Id 大小写不敏感

                                约定一条：在 schema 层统一命名策略，由生成器执行；手写类型把命名检查写进 lint。

                                错误码：按码分支，不按 message

                                message 给人看，code 给程序看：按 includes("超时") 分支的代码，后端一改文案就全部失效。码表设计是 40.7 的主场（40.7 错误码体系），这里只给客户端策略。

                                类别 怎么判定 客户端动作 重试 用户看到
                                网络错误 无响应、DNS/连接失败、CORS、超时 指数退避 + 上限；写操作进待发队列 仅幂等请求 “网络异常，稍后重试”
                                业务错误 4xx + 稳定 code 按 code 分支：改表单、跳详情 不重试 按 code 映射的文案
                                鉴权过期 401 + token_expired（与 403 分开） 刷新令牌后重放一次原请求 只重放一次 无感；失败才跳登录
                                限流 429 + Retry-After 按 header 延迟或排队 按 Retry-After “操作太频繁”

                                最容易做错的是 401 与 403 混用：401 是“不知道你是谁”，403 是“知道但不许”；混成一个“登录失效”分支，无权限用户会被反复踢去登录页，回来仍是 403。

                                一次 status + code 判定跑出来的分类（errors.mjs，节选）：

                                网络失败（fetch reject）       -> network   retryable=true
401 token 过期             -> reauth    retryable=true
429 限流                   -> throttled retryable=undefined retryAfter=2
418 契约里没写的码              -> business  retryable=false

                                兜底分支必须有：契约没写的 4xx 落到 business（不重试），非 4xx/5xx 落到 unknown——关键是每个分支都不崩、都不静默重试。

                                401 的两副面孔：会话失效 vs 表单错误

                                绝大多数拦截器把 401 一律当“会话失效”：刷新令牌、重放原请求、失败就登出。这条规则对业务请求基本正确，但对登录、改密码、验证码这几条端点是灾难——它们的 401 不是“你的会话没了”，而是“你这次填的凭据不对”。

                                401 的含义 典型业务码 正确动作 当成会话失效的后果
                                会话失效 Unauthenticated.TokenInvalid / 过期 刷新一次 → 重放 → 仍失败才登出 正确
                                凭据错误 Unauthenticated.InvalidCredentials 留在表单显示“当前密码不对”，不刷新、不登出 用户被自己的错别字踢下线
                                无权限（应是 403） PermissionDenied 显示无权限，不跳登录 来回跳登录页，回来仍是 403

                                一次“改密码时打错当前口令”的完整失败链：① 401；② 拦截器刷新令牌（这一步还会轮换 refresh token）；③ 重放原请求，口令仍是错的，再次 401（此时 _retry 已为 true）；④ 走登出。用户被自己的错别字踢下线，而真正的原因（当前密码不对）只留在两次被丢掉的响应体里。

                                // onexai-console/src/lib/api-client/form-error.ts —— 判断依据只能是业务码，不能是路径
export const FORM_ERROR_CODES: readonly string[] = ['Unauthenticated.InvalidCredentials'];

function isFormErrorBody(body: unknown): boolean {
	return FORM_ERROR_CODES.includes(codeIn(body));
}

                                这段代码有两个必须在契约层配合的前提：

                                1. 401 也要带 code：很多后端只给 401 + message，客户端只能猜；猜错就是误登出。
                                2. 码表是闭集，且两个方向不串：登录/改密码/验证码三处都回 InvalidCredentials，而鉴权中间件从不回它（令牌问题用 TokenInvalid）。这个“不串”的约定要写进错误码文档，否则前端维护的清单永远追不上后端新增。

                                🔑 判据：401 只回答“未认证”，不回答“为什么”；刷新、重放、登出这些动作必须由 code 决定，不能由状态码决定。

                                分页：offset 的重复与漏项是必然

                                “重复卡片/漏卡片”多数不是渲染问题，是 offset 分页在数据变动时的必然结果。20 条、每页 5 条、排序键 (created_at DESC, id DESC)，模拟翻到空页（paging.go，节选）：

                                A. offset 分页 + 第 1 页后插入 3 条(21,22,23)
   第 1 页 = [20 19 18 17 16]
   第 2 页 = [18 17 16 15 14]
   重复卡片 ID = [16 17 18]（3 条）
   原始 20 条里漏掉 = []（0 条）

B. offset 分页 + 第 1 页后删除 3 条(13,14,15)
   第 2 页 = [12 11 10 9 8]
   重复卡片 ID = []（0 条）
   原始 20 条里漏掉 = [13 14 15]（3 条）

C. cursor 分页 + 第 1 页后插入 3 条(21,22,23)
   重复卡片 ID = []（0 条）
   原始 20 条里漏掉 = []（0 条）

                                为什么恰好重复 3 条：插入 k 条让后续行后移 k 位，第 2 页窗口正好重取第 1 页最后 k 条（k 小于页大小时重复数 = k）；删除则窗口前移、跳过边界。

                                维度 offset / limit cursor（keyset）
                                能否跳页 能 不能，只能上一页/下一页
                                插入后 重复 k 条 0 条
                                删除后 漏 k 条 0 条误漏
                                深翻代价 OFFSET 100000 扫前 10 万行 走索引，近似常数
                                前端状态 页码（可放 URL） 不透明游标

                                🔑 前端把 items.length === 0 当“没有更多”是错的。 最后一页恰好装满时它是错判；契约里必须有显式 has_more。

                                写进契约的六条：游标不透明 · has_more 显式返回 · limit 有 maximum 且超限 400 · total 只用于“约 N 条” · 排序键唯一全序（同 created_at 必加 id）· 列表 key 用业务 ID 并先去重。

                                跨服务聚合的分页正确性属于 30.7（30.7 跨服务查询与数据聚合）。

                                契约先行：五个环节，谁负责，失败会怎样

                                环节 谁负责 产出 失败会怎样
                                schema 评审 后端 owner + 前端接口人 评审通过的 schema PR 联调才发现字段缺失
                                mock 前端（从 schema 生成） mock server / MSW 前端等后端，串行
                                契约测试 后端 CI（消费者提供期望） 通过的 provider 验证 上线前 N-1 才发现
                                联调 双方 真实环境冒烟 环境问题掩盖契约问题
                                上线 后端先上兼容版，前端后上 双版本共存窗口 前端先上直接打空

                                mock 的价值不在“假数据”，而在假数据是生成的：schema 改了 mock 自动跟着改；手写 mock 等于又维护一份契约。消费者驱动闭环、can-i-deploy 属于 53.5（53.5 契约测试）。

                                变更协作四条：谁提——任何一方都能提 PR，包括前端；谁评审——接口 owner + 至少一个消费者；兼容窗口——≥ 最长客户端版本寿命（移动端按强制升级覆盖率算）；何时删——deprecated → 双写/双读 → 观察 2 个发布周期 → 按版本头确认无调用 → 删。版本语义见 51.3 语义化版本与变更日志，破坏性变更分类见 28.3 服务契约设计，多版本共存见 30.6 服务版本与兼容，接口人机制见 78.4 跨团队协作与接口人。

                                客户端的宽容读取与版本协商

                                宽容读取是把“对未来版本的假设”收敛到三个固定位置：

                                位置 宽容做法 反例
                                未知字段 忽略，不报错 Go 的 DisallowUnknownFields
                                未知枚举值 落 default，展示“未知状态” 穷举 switch 无 default
                                未知响应码 兜底“未知错误”，不重试不白屏 只写 200/400 两个分支

                                反例实测（semantics.go）：

                                默认解码器（忽略未知字段）  => err=&lt;nil>, ID=1
DisallowUnknownFields      => err=json: unknown field "unknown_new_field"

                                ⚠️ DisallowUnknownFields 是“严格解码”，不是“契约严格”。 它让“后端新增字段”变成“老客户端解码失败”，兼容方向反了：该严格的是发出去的请求。

                                版本协商解决“少掉的能力”：

                                手段 做法 用在哪 注意

npx --yes orval --config orval.config.ts

go run detector.go v1.json v2-breaking.json

                                交叉验证：通用工具与自写检测器的覆盖面对不上。 同一组 fixture 喂给 oasdiff 1.39.0（go install github.com/oasdiff/oasdiff@latest，本机真跑）：

                                oasdiff breaking v1.json v2-breaking.json   # 6 changes: 6 error, 0 warning
                                变更 oasdiff 本节检测器 对前端意味着
                                参数可选变必填 ✅ 报 error ✅ 旧调用直接 400
                                字段类型 integer → string ✅ 报 3 处 ✅ 运算得 NaN
                                新增必填字段 ✅ 报 error ✅ 老客户端提交即失败
                                删除路径 ✅ 报 error ✅ 调用落 404
                                删除响应字段（remark） ❌ 未报 ✅ 读到 undefined，页面空白
                                枚举收窄（删 shipped） ❌ 未报 ✅ 旧值提交被拒
                                删除响应码（404） ❌ 未报 ✅ 分支逻辑落空

                                结论不是"自写比通用强"，而是两套覆盖面不同：工具按规则库报，规则库不覆盖的组合会静默通过；自写版按"谁依赖它"逐条判，能补上，但维护成本在自己身上。落地上两个都跑，合并结果（并集）才是门禁。

                                检查项 期望 实际输出
                                重生成 diff 门禁 非空即失败 门禁失败：重新生成 diff 非空
                                类型漂移 编译期报错 TS2551：toFixed 不存在于 string
                                枚举收窄 编译期报错 TS2678：shipped 不在联合类型里
                                枚举新增 穷举检查报错 TS2322：refunded 不能赋给 never

                                只加可选字段的 v2 不误报 0 条破坏级，1 条枚举新增警告

                                检测器输出（v2-breaking.json）：

                                | 破坏级 | 位置 | 变更 | 哪一端会炸 |
| 破坏级 | `GET /orders param:limit` | 参数从可选变必填 | 前端（调用方） |
| 破坏级 | `GET /orders -> 200.items[].remark（另 2 处同源）` | 删除字段 | 前端（读取方） |
| 破坏级 | `GET /orders -> 200.items[].amount（另 2 处同源）` | 字段类型变更 integer -> string | 前端（反序列化/取值） |
| 破坏级 | `GET /orders -> 200.items[].status.enum（另 2 处同源）` | 枚举收窄：删除 "shipped" | 前端（提交方向） |
| 破坏级 | `POST /orders body.idempotency_key` | 新增必填字段 | 前端（提交方） |

                                每条的前端爆炸时刻：参数/字段变必填 → 调用或提交即 400；字段删除 → 读到 undefined；类型变更 → 运算得 NaN；枚举收窄 → 旧值提交被拒；响应码或路径删除 → 落兜底页。

                                纯增量变体（加可选字段、路径、响应码、可选参数、枚举值）结果是 0 条破坏级、1 条枚举新增警告，另有 1 条 int32→int64 的兼容级提示：门禁不会因为正常演进变红，也不会把放宽类型的变更当成破坏。

                                可退

                                退路 做法 代价
                                门禁误报阻塞 --fail-on-breaking=false 破坏性变更靠评审
                                生成器升级 diff 爆炸 版本锁进 lockfile，单独 PR 人工确认 diff
                                schema 改坏 契约仓库回退 tag，重生成 前端跟退生成物
                                严格解码打挂线上 关闭 DisallowUnknownFields 拼写错误不再报错

                                什么时候别用这套：单人全栈、接口不到 10 个、没有 CI 的项目，三层门禁成本大于收益；一次性脚本、管理后台不需要契约测试；离线优先的移动端同步是另一套协议（本地库 + 变更流），不能直接套 offset 分页与宽容读取。

                                反模式

                                反模式 后果
                                int64 用 JSON number 传 9007199254740993 → ...992，前端展示错误订单号
                                用 0 / "" 表示“未设置” 与“清零”无法区分，用户清空余额后显示“未设置”
                                用字段缺失表示“无权限” 渲染成“未设置”，用户以为数据丢失，工单上涨
                                响应解码开 DisallowUnknownFields 后端加一个字段，所有老客户端解码失败
                                按 message 字符串分支 文案一改（甚至翻译）所有分支失效
                                把 offset 分页当稳定快照 插入 3 条重复 3 张卡片，删除 3 条漏 3 张卡片
                                所有 401 都刷新令牌并重放 改密码输错一次 → 刷新 + 重放 + 登出，用户被错别字踢下线
                                401 响应体不带业务码 客户端只能猜“会话失效”还是“表单错误”，猜错就误登出

                                自检

                                Q1 后端把 id 从 JSON number 改成 JSON string，前端为什么反而更安全？老前端会遇到什么？

                                ▸ 答案：JS number 超过 2^53-1 会静默改值（9007199254740993 读成 ...992），字符串无损。老前端若类型仍声明 number，就是“声明没变、运行时拿到 string”：tsc 不报错（生成物没更新），运算得到 NaN。改类型必须配生成物更新 + 兼容窗口。

                                Q2 移动端 PATCH 保存资料时省略了没改的 avatar 字段，后端却把它当 PUT 处理成 null，头像被清空。谁违约、契约怎么写、前端怎么防？

                                ▸ 答案：后端违约——PATCH 里「缺失」只能表示「不修改」，把它当「清空」是语义错误；PUT 全量才允许缺省即违约 400。契约必须把三条写死：PATCH 缺失=不改、null=清空、avatar 标 nullable。前端两道防线：只发送变更字段，并带 If-Match/version 做并发保护；契约测试必须有一条「只传 name 时 avatar 保持原值」的用例，否则这个错会在联调后每次保存都复现。

                                Q3 检测器把“新增枚举值”判为警告，可前端 tsc 却报错了，矛盾吗？

                                ▸ 答案：不矛盾，时刻不同。检测器判 wire 兼容性——新增值不会让老响应解析失败，所以不是破坏级；tsc 报错在生成物更新之后，union 变宽、never 穷举失败，属编译期提醒。真正的线上事故是“生成物没更新 + switch 无 default”。

                                Q4 实验 C 插入 3 条为什么恰好重复 3 条？插入 5 条（等于页大小）会怎样？

                                ▸ 答案：插入 k 条让第 1 页之后所有行后移 k 位，第 2 页取“新的第 6–10 名”，正好覆盖第 1 页最后 k 条，所以 k 小于页大小时重复数 = k。插入 5 条时第 2 页整页都是刚看过的 5 条，新数据完全不可见。

                                Q5 列表 5 万条，产品要“共 N 页”并能跳到第 100 页。你给什么方案，代价是什么？

                                ▸ 答案：先说结论：offset 能跳页但深翻 OFFSET 2000 要扫前 2,000 行且数据变动就漂移；cursor 稳定但不能跳。可用组合是「筛选/搜索缩小结果集 + 约 N 条 + has_more」，把“随便跳页”改成“按条件定位”；确实要任意跳，就得接受快照（导出快照 + 页码映射）或读模型预计算，成本在数据侧不在前端。判据是产品到底要「稳定快照 + 任意跳」还是「实时 + 连续翻」。

                                Q6 生成物入库和发私有包，各自失败模式是什么？小团队选哪个？

                                ▸ 答案：入库的失败模式是“多仓库各自重生成，容易漏”，好处是变更以 diff 可见；发包的失败模式是“版本锁住了但 diff 不可见，后端改字段表现成升级依赖后报错”。单前端仓库选入库 + diff 门禁；多仓库发包要配“重生成 diff 为空”的定时任务。

                                Q7 为什么“所有 401 都刷新令牌再重放”对“改密码时当前口令输错”是错的？正确策略是什么？

                                ▸ 答案：因为刷新令牌只解决“令牌过期/被撤销”，解决不了“凭据本身不对”。刷新会轮换 refresh token（可能让其他标签页的会话失效），重放仍是同一个错误口令，再得到 401，最后走登出——一次错别字触发两次失败请求 + 一次登出，且真正的原因被丢掉。正确策略：先按响应体的业务码判断，InvalidCredentials 直接作为表单错误返回，只有 TokenInvalid/过期才刷新与重放；刷新只重试一次，仍失败才登出。
