# 73.7 浏览器渲染流水线与性能预算

## 一句话

> 前端性能不是优化技巧的集合，而是两条预算：**关键渲染路径的阻塞链**，与**每一条资源的体积/请求预算**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 「性能优化 = 背一堆技巧」 | 技巧有前提。《高性能网站建设指南》的 14 条原则里，域名分片、文件合并、关 ETag 都是 HTTP/1.1 的产物；HTTP/2 在 2015 年获批（RFC 7540，头压缩 RFC 7541）后，多域名意味着多一轮 DNS 与 TLS 握手，合并带来的收益也被多路复用摊薄 |
| 「上了 SSR 性能就好了」 | SSR 只把**内容**推早，水合仍在主线程跑同一份 JS：73.1 实测内容 250 ms、可交互 1,199 ms，中间 949 ms 看得见点不动（[73.1 前端架构](73.1-前端架构.md)） |
| 「动画卡是 GPU 不行」 | 先看主线程。多数 Jank 来自每帧触发布局与重绘，GPU 只是在等主线程提交帧——用错属性时，换再好的显卡也救不回来 |

## 渲染流水线：六步，各有各的阻塞源

浏览器把字节变成一帧，要顺序走六步。**每一步的输入没齐，后面全部停住**；优化的本质是找出「当前这一帧卡在哪一步」，而不是把所有技巧都上一遍。

| 步 | 做什么 | 谁阻塞它 | 优化动作 |
|---|---|---|---|
| ① **DOM** | 解析 HTML 字节流，建节点树 | 同步 `<script>`：解析器停下，等下载并执行完才继续 | 关键 HTML 由服务端直出；脚本用 `defer`/`async`；不在解析期写 `document.write` |
| ② **CSSOM** | 解析 CSS，建样式规则树 | 外链 CSS 与 `@import`：CSSOM 不完整就不建渲染树 | 关键 CSS 内联进 `<head>`；非关键 CSS 异步加载；少用 `@import` 串行下载 |
| ③ **渲染树** | DOM 与 CSSOM 匹配，只保留可见节点 | DOM 或 CSSOM 任一未就绪 | 减少不可见节点与深层嵌套；别用大量空 `div` 撑布局 |
| ④ **布局** | 算每个节点的几何位置与尺寸 | 读写交错：刚改完样式又读 `offsetHeight`，触发强制同步布局 | 批量读 → 批量写；动画用 `transform`，不改 `top`/`left`/`width` |
| ⑤ **绘制** | 把节点填成像素 | 大面积重绘，阴影、模糊、圆角等昂贵效果 | 缩小重绘区域；图层提升（`will-change`）要克制，图层多了合成与显存都涨 |
| ⑥ **合成** | GPU 把各图层拼成一帧 | 主线程长任务推迟帧提交 | 把动画交给合成器（`transform`/`opacity`）；把长任务切片，别一帧干到底 |

六步不是每帧全跑：改一次 class 可能只走「布局 → 绘制 → 合成」，改 `transform` 通常只走「合成」。**能跳到第 ⑥ 步的动画，才可能不掉帧。**

## 关键渲染路径的三条阻塞规则

### ① CSS 阻塞渲染

浏览器必须等 CSSOM 建完，才肯构建渲染树。所以 `<head>` 里的外链 CSS 在关键路径上：**HTML 到了、CSS 没到，页面就是白屏**，不是「先显示无样式内容再美化」。

推论：CSS 要尽早、尽量小。把首屏用不到的样式拆出去异步加载，比把整站 CSS 塞进一个文件更快；但拆过头会变成多次往返，判据是「这段样式首屏用不用得上」。

### ② 同步 JS 阻塞解析

没有 `defer`/`async` 的 `<script>` 会打断 HTML 解析器：下载、执行，然后才继续解析。更隐蔽的是，**脚本执行前还要等它前面的 CSS 下载并解析完**——因为脚本可能读取样式。于是「一个外链 CSS + 一个同步脚本」能把首屏拖成两段串行等待。

### ③ `defer` 与 `async` 的分工

两者都**并行下载、不阻塞解析**，差别在执行时机与顺序：

| 写法 | 下载 | 执行时机 | 顺序保证 | 适用 |
|---|---|---|---|---|
| `<script>` | 阻塞解析 | 下载完立即执行 | 保证 | 极少数必须同步改 DOM 的内联初始化 |
| `<script async>` | 与解析并行 | 下载完立即执行，**仍会打断解析** | 不保证 | 独立第三方脚本：统计、广告、客服 |
| `<script defer>` | 与解析并行 | DOM 解析完、`DOMContentLoaded` 前执行 | 保证 | 依赖 DOM 的业务脚本、有依赖关系的模块 |
| `<script type="module">` | 与解析并行 | 默认等价于 `defer` | 保证 | 现代模块入口 |

> 🔑 判据只有两条：**脚本之间有没有依赖、要不要等 DOM。** 有依赖或要读 DOM → `defer`；完全独立 → `async`；两者都不满足才用同步脚本。注意 `defer` 只保证「不阻塞解析」，执行本身仍占主线程——一个巨大的 defer 脚本照样能把 TTI 推后。

## 把三条阻塞规则落到代码上

规则要变成可粘贴的代码才有用。最小的一套：

```html
<!-- 1) 关键 CSS 内联，避免 CSSOM 阻塞首屏渲染 -->
<style>/* 首屏所需的样式，控制在几 KB */</style>

<!-- 2) 非关键 CSS 异步加载，别让它进关键渲染路径 -->
<link rel="stylesheet" href="/app.css" media="print" onload="this.media='all'">

<!-- 3) 字体预连接 + 预加载，减少字体闪烁与二次布局 -->
<link rel="preconnect" href="https://fonts.example.com" crossorigin>
<link rel="preload" as="font" type="font/woff2" href="/font.woff2" crossorigin>

<!-- 4) 入口脚本用 defer：不阻塞解析，按顺序执行 -->
<script src="/app.js" defer></script>

<!-- 5) 首屏图片给尺寸，避免布局抖动（CLS 的主要来源） -->
<img src="/hero.avif" width="1200" height="630" alt="" fetchpriority="high">
```

验收命令（Lighthouse 与 WebPageTest 二选一，CI 里跑前者）：

```bash
npx lighthouse https://example.com --preset=desktop --only-categories=performance \
  --output=json --output-path=./lh.json
# 门槛示例：LCP <= 2.5s、CLS <= 0.1、TBT <= 200ms，任一超线即失败
```

## 性能检查单：八条，每条一个指标 + 一个反例

优化的第一步不是改代码，是**把预算写下来**。下面每一条都能在 DevTools 或真实用户监控里量到；量不到的项目，不该进优化排期。

| # | 检查项 | 指标（怎么量） | 反例 |
|---|---|---|---|
| 1 | **请求数** | Network 面板首屏请求总数与关键请求数（禁用缓存复测） | 首屏每个小图标各发一个请求；为了「模块化」把首屏拆成几十个碎文件 |
| 2 | **缓存头** | `Cache-Control` 的 `max-age`/`s-maxage`/`immutable`，以及 CDN 命中率与 `Age` | 带内容哈希的静态资源设成短缓存，每次访问都回源；或入口 HTML 设长缓存，发版后用户拿不到新版本（[73.5 前端发布与灰度](73.5-前端发布与灰度.md)、[9.1 边缘缓存原理](../../L0-运行时底座/9-CDN与边缘/9.1-边缘缓存原理.md)） |
| 3 | **压缩（gzip / br）** | 响应头 `Content-Encoding`，对比压缩前后字节 | 只给 HTML 开 gzip，JS/CSS 裸传；或服务端支持 br 却仍统一用 gzip |
| 4 | **域名收敛** | 首屏涉及的域名数、每个域名的连接数 | 照搬 HTTP/1.1 的域名分片：HTTP/2 下多一个域名就多一次 DNS + TLS；国内站还把公共库指向 Google 托管 |
| 5 | **图片与字体** | 图片实际渲染尺寸 vs 原始像素、字体文件字节与 `font-display` | 相机原图直接缩成缩略图展示；中文字体全量包只用了几个字；字体加载期文字不可见 |
| 6 | **JS 体积** | 首屏 bundle 的 raw/gzip 字节、主线程长任务数与总时长 | 全量引入组件库只为用一个按钮；两个子应用各打一份公共库（73.1 实测首屏 JS 49.8% 是重复字节） |
| 7 | **动画 Jank** | 帧间隔与掉帧数、每帧主线程任务时长 | 用 `top`/`left`/`width` 做动画，每帧触发布局与重绘；没有信息量的装饰动画一直跑 |
| 8 | **内存泄漏** | 堆快照对比、Detached DOM 数、常驻内存随交互次数是否单调上升 | 全局事件监听与定时器不解绑；闭包长期持有大对象；页面切走后仍留着整棵组件树 |

> ⚠️ 这八条不是并列的「都做一遍」：先量，再按「省下的时间 ÷ 改动成本」排序。请求数、压缩、图片字体、JS 体积属于**资源预算**（要下载多少字节、发几次请求）；缓存头决定这份预算**要重复付几次**；布局、绘制、动画与内存属于**关键路径预算**（每帧主线程要干多少活）。两类预算分开算，混在一起就只能比谁嗓门大。

## 与 73.1 的关系：SSR 只提前 FCP/LCP，不解决 TTI

把渲染流水线摊开看，SSR 的作用位置一目了然：

| 流水线阶段 | CSR | SSR |
|---|---|---|
| HTML → DOM | 先到空壳，内容要等 JS 执行后才有 | 内容已经在 HTML 里，DOM 一到就有 |
| CSSOM → 渲染树 → 布局 → 绘制 | 要等 JS 执行完才开始 | HTML 到达即开始，**FCP/LCP 提前** |
| JS 执行 + 水合 | 首次渲染即绑定事件 | 同一份代码再跑一遍，**949 ms 的窗口** |

所以 73.1 的两个数并不矛盾：SSR 内容就绪 250 ms，比 CSR 的 1,291 ms 快 5.2 倍；可交互 1,199 ms，只比 CSR 的 1,294 ms 领先 7%。**SSR 买的是「画出来」，不是「能操作」**——后者由主线程上的 JS 执行与水合决定，和 HTML 从哪来无关。

推论：首屏慢要先判断卡在「下载/解析」还是「主线程」。[34.1 性能指标](../../L3-质量属性/34-性能/34.1-性能指标.md) 的 FCP/LCP 看前者，TTI/INP 看后者；手段总表在 [34.4 优化手段](../../L3-质量属性/34-性能/34.4-优化手段.md)。如果 73.1 的账算下来大头是「等 JS 才能发数据请求」，先做数据内联 / 服务端预取，比换渲染框架便宜。

## 反模式

| 反模式 | 后果 |
|---|---|
| 把 YSlow 14 条当永久真理，HTTP/2 下继续域名分片、强行合并 | 多域名多握手，合并后的单文件缓存失效代价更大——优化变成负优化 |
| 只给 HTML 开压缩，JS/CSS 裸传 | 首屏最大的一块字节没有压缩，白付带宽与等待 |
| 给带哈希的静态资源设短缓存，给入口 HTML 设长缓存 | 前者每次回源，后者发版不生效——缓存头配反比不配更糟 |
| 用 `top`/`left`/`width` 做动画 | 每帧触发布局与重绘，主线程一忙就掉帧 |
| 加了 `defer` 就认为「不阻塞」 | 只不阻塞解析；执行仍占主线程，长脚本照样卡 TTI |
| 把 SSR 当性能银弹 | 内容早到、交互不变，还多付常驻 Node 的运维成本 |
| 只在实验室跑分，不看真实用户数据 | 实验室网络与设备不代表用户，优化了没人感知的部分 |
| 内存问题等 OOM 才查 | 泄漏早期只表现为「越用越卡」，堆快照对比才能定位 |

## 时效性

> 本文的框架/工具结论按 **2–3 年保鲜期**看待（Vue2→3、Redux→Zustand、YSlow 已停更）。渲染流水线六步与三条阻塞规则属于浏览器机制，保鲜期更长；「14 条优化原则」是 HTTP/1.1 时代的产物，域名分片、文件合并、关闭 ETag 这几条在 HTTP/2 下要重算。HTTP/2 于 2015 年获批（RFC 7540，头压缩 RFC 7541），今天的新建站应把 HTTP/3 纳入评估。

## 自检

**Q1** 页面 HTML 已经到了，但屏幕一直白着，直到样式表下载完才一次性出现内容。这是哪一步阻塞了哪一步？

▸ 答案：CSSOM 阻塞渲染树。浏览器要等 CSSOM 建完才能把 DOM 与样式匹配成渲染树，渲染树没建好就不会布局、绘制，所以 HTML 到了也白屏。修法是缩小关键 CSS、内联首屏样式，而不是先动 JS。

**Q2** 给脚本加了 `defer`，为什么页面交互仍然很慢？

▸ 答案：`defer` 只保证「下载不打断解析、DOM 解析完再按序执行」，不保证「执行不占主线程」。脚本本身很大或执行很久，仍然会推迟水合与后续交互。判据是看主线程长任务，而不是看脚本标签上有没有 `defer`。

**Q3** SSR 把内容就绪从 1,291 ms 降到 250 ms，为什么用户还是说「点了没反应」？

▸ 答案：因为 SSR 只优化了流水线前半段（DOM → 渲染树 → 布局 → 绘制），水合仍要在客户端把同一份 JS 跑一遍，实测到 1,199 ms 才可交互；对照 CSR 的 1,294 ms 只领先 7%。「看见」和「能操作」是两个指标，后者由主线程决定。

**Q4** 团队按 14 条原则把静态资源拆到多个域名，为什么在 HTTP/2 下反而更慢？

▸ 答案：HTTP/2 用一条连接多路复用多个请求，域名分片的好处（绕过 HTTP/1.1 的每域名连接数限制）消失了，代价却还在：每个新域名都要多做一次 DNS 解析与 TLS 握手。判据是「这条原则当年的瓶颈还在不在」，不在就该删。

**Q5** 同一个位移动画，用 `left` 会掉帧、用 `transform` 不会，流水线上差在哪？

▸ 答案：`left` 改的是几何属性，每帧触发「布局 → 绘制 → 合成」；`transform` 可以只在合成阶段改图层变换，跳过布局与绘制。差别不在 GPU 算力，而在每帧让主线程干了多少活。
