                            73.5 前端发布与灰度

                            一句话

                            前端发布的对象不是「一个版本」，而是入口 HTML + 带哈希的静态资源 + 已经跑到用户设备上的旧代码三样东西；因此前端灰度只有两条铁律：入口可切、资源不可变且旧版本不许 404；前端与后端必须能共存在一个兼容窗口里。

                            先破除四个误区

                            误区 现实
                            前端发版就是把 dist/ 覆盖上去 覆盖会改掉入口与资源的对应关系：实测换 v2 入口并删掉 v1 的 chunk 后，旧页面请求 app.86d39e86.js 得到 404，body.innerText 长度 0、window.__V=undefined——不是样式错位，是整页白屏
                            HTML 也能长缓存，回滚时刷 CDN 就行 实测 max-age=300：服务端把入口 BUILD 从 1 改到 2 之后，同一 URL 第二次导航 transferSize=0、deliveryType=cache、服务端回源 0 次，页面仍是 BUILD=1；回滚生效上限就是 300 s，再叠加 CDN 节点与递归缓存
                            灰度 = 按比例随机分流 同一个 uid 连打 20 次，随机模式相邻两次换版本 12/19 次；连打 1000 次换 512/999 次——一半请求落在另一个版本上
                            旧资源占空间，发布完就删 按 gzip 1.8 MB/版本算，留 5 个版本共 9 MB；一次全量发布（10 万 DAU × 1.8 MB = 180 GB）的 0.005%。删掉这 0.005%，换来的是一次白屏事故

                            发布对象是三样东西，不是"一个版本"

                            三种对象生命周期不同，缓存策略必须分开。

                            对象 发布时变不变 缓存在哪 正确策略 策略错的后果
                            入口 HTML 每次发布都变 浏览器、CDN、SW no-store；或 no-cache + ETag（每次验证，未变 304） 入口切了，用户还拿旧 HTML 请求旧资源
                            /assets/<name>.<hash>.* 内容变则文件名变；文件名不变则内容不变 浏览器、CDN、中间代理 public, max-age=31536000, immutable 同名文件被覆盖，缓存里一半新一半旧，无法原子切换
                            已下发到设备的旧代码 收不回来 用户设备上的标签页、SW、离线包 不设缓存头，只能检测 + 兜底 + 保留旧资源 旧标签页请求已删除的 chunk → 404 白屏

                            三者的差别不是大小，是能不能撤回：入口在服务端，改一次全量生效；哈希资源换内容就换 URL，所以敢永久缓存；设备上的旧代码，服务端权限为零。混成一句"发个版"，等于用管理服务端的办法管理用户设备。

                            🔑 前端发布的原子单位是入口 HTML，不是文件集合。入口指向哪一套资源，用户就跑哪一版；所以"切版本"永远只有一步：换入口。

                            内容哈希是不可变性的载体：app.86d39e86.js 与 app.e8767cf1.js 是两个 URL，前者永远不该变；"文件名不变、内容会变"的资源（app.js、config.js）不配拿 immutable。一般原则见 54.1 不可变制品。

                            原子切换：发布顺序错了，回滚就是假的

                            顺序只有一条解：任何时刻页面引用的资源必须存在。

                            1. 后端先上兼容版本：新后端能服务旧前端，旧后端能服务新前端，直到兼容窗口结束。
                            2. 上传新资源：文件名带内容哈希，都是新 URL，此刻没有任何入口引用它们，上传失败不影响线上。
                            3. 切入口：单文件 rename，POSIX 保证读者要么看到旧文件、要么看到新文件，不会读到半个。
                            4. 灰度放量：按入口切，一批一批换。
                            5. 全量。
                            6. 保留旧资源 K 个版本：K 由回滚窗口决定，不是"看磁盘剩多少"。
                            # 1) 资源只增不删：新文件名是新哈希，重复上传幂等
rsync -a dist/assets/ /srv/www/assets/

# 2) 入口最后切：同目录 rename 是原子操作，不会出现半个 index.html
cp dist/index.html /srv/www/.index.html.new
mv /srv/www/.index.html.new /srv/www/index.html

# 3) 回滚：把上一版入口放回去，旧资源仍在 /srv/www/assets/
cp /srv/www/releases/20261120/index.html /srv/www/.index.html.new
mv /srv/www/.index.html.new /srv/www/index.html

                            入口先切、资源后传，切完到传完之间的每次导航都可能 404；反过来资源先传，最坏多占几 MB，用户无感。发布顺序的目标不是快，是让每一步失败都可停。

                            缓存策略矩阵：三类对象，三套响应头

                            路径 响应头 行为 适用
                            /index.html Cache-Control: no-store 每次导航都回源 默认；要秒级回滚就选它
                            /index.html Cache-Control: no-cache + ETag 每次回源验证，未变 304 想省 HTML 字节、能接受 1 个 RTT
                            /assets/<hash>.* public, max-age=31536000, immutable 一年内不回源、不发条件请求 所有带内容哈希的 JS/CSS/字体
                            /sw.js no-cache 每次回源验证 SW 必须能更新，否则回滚失效
                            /api/* 按业务语义 见 41.1 缓存模式 登录态接口绝不设 public

                            环境：macOS arm64 / Node v26.10.0 / Chrome 157 headless / nginx 1.27.4。

                            实测：两种入口策略下"改完入口到用户看到新版"的差别（缓存开启，中间隔一次 about:blank）：

                            入口策略 第二次导航 transferSize deliveryType 服务端回源次数 页面读到的 BUILD
                            no-store 495 B 空（走网络） +1 2（新）
                            public, max-age=300 0 cache 0 1（旧）

                            max-age=300 那一行就是"回滚按钮按下去，用户还在旧版本"的证据：服务端内容已变，浏览器连问都没问。CDN 缓存机制在 9.1 边缘缓存原理，刷新与回源不展开。

                            可直接粘贴的 nginx 配置

                            这套配置在本机 nginx 1.27.4 上真跑过（实测时 root 指向 demo 目录、端口 18701），nginx -t 与 curl -I 输出如下。

                            worker_processes 1;
pid logs/nginx.pid;
events { worker_connections 64; }
http {
  include /etc/nginx/mime.types;   # 按你的安装路径改；本机实测用的是临时前缀
  default_type application/octet-stream;
  # 404 也有负缓存：缺失资源若带 immutable，CDN 会把 404 存一年
  map $status $assets_cc {
    200 "public, max-age=31536000, immutable";
    default "no-store";
  }
  server {
    listen 18701;
    root /srv/www;
    # 1) 入口：每次回源
    location = /index.html {
      add_header Cache-Control "no-store" always;
      try_files $uri =404;
    }
    # 2) 哈希资源：不可变长缓存；缺失必须 404，不能回落 index.html
    location /assets/ {
      add_header Cache-Control $assets_cc always;
      try_files $uri =404;
    }
    # 3) SW 脚本：可缓存但每次验证
    location = /sw.js {
      add_header Cache-Control "no-cache" always;
      try_files $uri =404;
    }
  }
}

                            打印版只把 include 与 root 换成了通用路径，其余与实测文件一致（tools/examples/73-frontend/s735/nginx/nginx-good.conf）；本机是源码编译的 nginx，装在临时前缀里，所以 include 指向 conf/ 下的 mime.types。

                            验证命令与真实输出（原始文件 tools/examples/73-frontend/s735/nginx/，说明见 示例 README）：

                            $ nginx -t -c /etc/nginx/nginx.conf          # 换成你的配置路径
nginx: configuration file ... test is successful

$ curl -sI http://127.0.0.1:18701/ | grep -i cache-control
Cache-Control: no-store

$ curl -sI http://127.0.0.1:18701/assets/app.e8767cf1.js | grep -i cache-control
Cache-Control: public, max-age=31536000, immutable

$ curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18701/assets/app.86d39e86.js
404

                            💡 非共识增量（实测发现）：第一版配置把 add_header ... immutable always 直接写在 /assets/ 里，缺失资源的 404 也带上了 immutable——CDN 会把一个 404 缓存一年，之后补回资源用户也拿不到。修法是 map $status：只有 200 才给 immutable。

                            另一个反例：location / { try_files $uri /index.html; }（SPA 全量兜底）。实测请求已删除的 chunk 返回 200 + text/html + 295 B 的 index.html；监控里 chunk 缺失率永远是 0，用户看到白页加一条 Failed to load module script。资源路径必须 404，页面路径才兜底。

                            前端版本 × 后端版本：共存窗口是一个矩阵

                            后端灰度切的是"请求"，前端灰度切的是"页面实例"。一个用户可能同时开着两个标签页：一个在灰度批次里拿到 v2、另一个还停在 v1；入口缓存与 SW 又让同一个 uid 在同一分钟里两个版本并存。所以兼容性不是一条线，是一个笛卡尔积：

                            前端 \ 后端 后端 N（旧） 后端 N+1（新）
                            前端 F（旧） 正常 必须支持：灰度期与回滚期都要能跑
                            前端 F+1（新） 必须支持：前端先回滚、后端还没退时 正常

                            两条约束：

                            • 后端新版本必须能服务旧前端：不删字段、不改字段语义、新增字段必须可选（契约层面的判据在 73.4 前后端契约，这里只管时间窗口）。
                            • 前端新版本必须能服务旧后端：读不到新字段要降级，不能 undefined.map。

                            窗口长度取三者最大值：

                            W ≥ max(2 × 前端发布间隔, 入口缓存 TTL + 最长会话时长, 客户端强制升级周期)

                            代入常见值：前端每周发 2 次 → 2 × 3.5 d = 7 d；入口 no-store → TTL 项可忽略；移动端强更 30 d → W = 30 d。后端删字段前，要保证最后一个可能调用它的前端版本已过强更窗口。窗口内后端 owner 保证旧前端可用，前端 owner 保证新前端兼容旧后端，发布负责人到期删兼容代码——三方签字，否则窗口无限延长。

                            💡 我的判断是：这个窗口应该写进发布 checklist，而不是靠"大家记得"。窗口到期的标志不是日期，是分版本指标里旧 build 的请求占比低于 0.1%；没有这个数，删字段就是赌博。

                            灰度键与批次：先定键，再定比例

                            键决定"同一用户是否稳定落在同一堆"，比例只决定"两堆多大"。粘性算法（哈希、分桶、漂移）的主场在 47.3 路由与灰度，前端侧只需记住：键必须是服务端可复现的稳定标识，不能是 Math.random()。

                            键 从哪来 稳定性 前端特有的坑
                            登录用户 ID 会话 最高 未登录时没有键，登录后可能跳一次
                            设备 ID 首次访问由服务端下发 cookie/localStorage 高（清缓存会变） 隐私模式每次新 ID，等于每次都是新用户
                            地域 CDN/边缘 IP 库 弱 出差、代理、VPN 都会跳
                            百分比 hash(uid) % 100 < N 高 换成随机数就退化成"每次给用户换版本"

                            实测三组（服务端按 sha256(uid) 分 100 桶，<50 走 v1）：

                            场景 v1 v2 相邻两次换版本
                            1000 个新用户（不带 cookie，各自新 uid） 470 530 —
                            同一 uid ×1000（cookie 哈希） 0 1000 0/999
                            同一 uid ×20（随机模式） 9 11 12/19
                            同一 uid ×20（cookie 哈希） 0 20 0/19
                            同一 uid ×1000（随机模式） 490 510 512/999

                            比例偏 6%（470/530）可以接受，粘性偏 0 次不能接受：同一用户 20 次访问换 12 次版本，前端状态、缓存、埋点全部对不上。批次比例是第二位的，键和粘性是第一位的。

                            前端特有分流手段，生效时间差一个数量级：

                            手段 生效时间 粒度 代价
                            配置中心下发版本号/开关 下次拉配置或下次启动 用户/设备 旧代码里必须有读取逻辑；已发出去的版本改不了
                            CDN 按路径/header 分流 下一次请求 请求 缓存键必须含分流 header，否则边缘缓存会串版本
                            客户端内置开关 立即（代码已下发） 功能 开关债与生命周期，见 55.2 特性开关

                            放量批次：1% → 5% → 25% → 100%；我的判断是每批至少观察 30 min，并覆盖一个业务高峰——批次之间等的是指标，不是时间。全链路染色的主场在 55.6 灰度与流量染色，前端只负责把 build_id 放进请求头，让后端日志能按前端版本切。

                            观测：没有分版本指标，就没有灰度

                            判断"这批能不能放量"时，每个指标都必须能按 build_id 切开。

                            指标 口径 放量门槛（我的判断）
                            版本覆盖率 带 build_id 的事件数 / 全部事件数 ≥99%，否则分版本指标不可信
                            分版本 JS 错误率 该 build 的错误数 / 该 build 的 PV 不超过基线 +0.1 pp
                            白屏率 加载后 3 s #app 无可见内容 / 该版本 PV 灰度期为 0，出现即停
                            chunk 404 率 /assets/* 的 404 数 / 资源请求数 0；大于 0 说明旧资源被删了
                            核心转化 下单/登录成功率，按 build 对比 不低于基线 -0.5 pp，且样本量够
                            // 所有上报共用同一个 build_id：错误、性能、埋点、API 请求头
const BUILD_ID = window.__BUILD_ID__; // 构建时注入
const report = (event, payload) => navigator.sendBeacon('/collect',
  JSON.stringify({ ...payload, app_version: BUILD_ID, ts: Date.now() }));
addEventListener('error', e => report('js_error', { msg: e.message, src: e.filename }));
// API 带上版本，后端日志才能按「前端版本 × 后端版本」切
fetch('/api/orders', { headers: { 'X-Client-Version': BUILD_ID } });

                            错误监控用 Sentry Release：build_id 当 release，source map 随构建上传，错误按 release 过滤。指标口径见 50.4 度量。

                            🔑 没有 app_version / build_id 的灰度，等于把用户当随机数种子：出问题时你只知道"线上有问题"，不知道"哪一版有问题、影响了多少人、该不该回滚"。

                            回滚：切入口 + 旧资源还在 + 让缓存失效

                            回滚三步，每步都有前提：

                            1. 切回上一版 index.html：前提是上一版入口文件还在（releases/ 目录按版本保留）。
                            2. 旧资源仍在线：前提是发布时"只增不删"，旧 chunk 没有被清掉。
                            3. 让缓存失效：no-store 下一次导航即可；max-age 要等 TTL，或用版本提示引导刷新；SW 缓存要 unregister 或等 SW 更新。

                            实测"改完入口到用户看到新版本"的时间下界：

                            动作 实测结果
                            no-store，切回旧入口 第二次导航 transferSize=495 B（回源），页面立即读到新 BUILD
                            max-age=300，切回旧入口 第二次导航 transferSize=0、deliveryType=cache、服务端 0 次回源、BUILD 仍是旧值
                            普通 F5（Page.reload） 回源 1 次，sleep 800 ms 后读到新 BUILD（非延迟上界）
                            硬刷新（ignoreCache:true） 回源 1 次，同样读到新 BUILD

                            所以时间下界可以写死：no-store ≈ 下一次导航；max-age=300 ≈ 最多 300 s，加上"用户不刷新"的长尾可以无限长。 这里的 300 s 还只是浏览器一侧，CDN 节点与递归缓存另算（9.1 边缘缓存原理）。

                            回滚要区分"代码回滚"与"数据回滚"：已写入的新格式、已发出的消息、已改过的缓存，退代码不会自动还原，设计见 55.3 回滚设计。前端只保证入口可切、旧资源可达，让退代码在一次导航内完成。

                            演练每月一次，记录"决定回滚到指标回落"的时长；目标 5 min（我的判断），超过 15 min 说明入口缓存或资源保留有问题。

                            版本割裂：多标签页、SW、离线包

                            前端版本不是全局状态，而是"每个标签页、每个 SW、每个离线包各有一份"。

                            旧标签页 + 已删除的 chunk。 实测：v2 发布、v1 资源删除后，旧页面请求 app.86d39e86.js 得到 404，真实 Chrome 里 bodyTextLen=0、window.__V=undefined。旧标签页不会自己恢复：里面没有代码知道"新版本存在"。

                            兜底一：chunk 加载失败自动刷新一次，带上限。

                            // 旧标签页加载不到 chunk：自动刷新一次，每会话上限 1 次，避免死循环
window.__reloads = Number(sessionStorage.getItem('t73_reloads') || 0);
addEventListener('error', e => {
  const t = e.target;
  if (!t || t.tagName !== 'SCRIPT') return;
  if (window.__reloads >= 1) return;
  sessionStorage.setItem('t73_reloads', String(window.__reloads + 1));
  location.replace('/?recovered=' + Date.now()); // 换 URL 同时绕开入口缓存
}, true);

                            实测效果：旧页面 → chunk 404 → 自动跳到 /?recovered=... → 新入口与新 chunk 均 200，页面渲染出 v2 rendered；同一会话第二次进旧页面时 reloads=1，不再刷新，停在空白页——上限生效，不会进刷新循环。?recovered= 不只是日志标记：它换了缓存键，能绕开 max-age 的旧入口。

                            兜底二：version.json 轮询。

                            const MINE = window.__BUILD_ID__;
async function checkVersion() {
  const { build_id } = await (await fetch('/version.json', { cache: 'no-store' })).json();
  if (build_id !== MINE) showUpdateBar(); // 或 location.reload()
}
setInterval(checkVersion, 60000);
document.addEventListener('visibilitychange', () => { if (!document.hidden) checkVersion(); });

                            服务端只需要一个 no-store 的小文件，实测返回 {"build_id":"20261121-1","entry":"/index.html"}。60 s 是及时性与请求量的折中：100 万在线 × 每分钟 1 次 = 1.67 万 QPS，必须放 CDN 且文件足够小。

                            SW 缓存旧入口。 SW 的 fetch 可返回缓存里的旧 index.html，服务端切回旧版后用户仍拿旧版——回滚"看起来生效了"，实际没有。三条约束：sw.js 用 no-cache；导航请求 network-first 或 network-only；更新用 skipWaiting() + clients.claim()。

                            离线包。 整份前端打进客户端，版本跟 App 走，切入口无效；只能靠强更、内置开关或下次启动拉新包，治理不在这一层。

                            生产落地：nginx + 三个替代品

                            指名：自建用 nginx（配置在 1.27.4 实测），托管用 Vercel，国内对象存储用阿里云 OSS + CDN，错误监控用 Sentry Release。

                            产品 入口怎么切 资源头怎么设 注意
                            nginx（实测） 覆盖 index.html（同目录 rename） 三个 location + map $status 404 不能带 immutable；资源路径不能兜底
                            Vercel 每次部署一个不可变 URL，别名指向新部署 vercel.json 的 headers 覆盖 /index.html 与 /assets/(.*) 平台默认给静态资源长缓存，入口头必须显式覆盖
                            阿里云 OSS + CDN 目录版本 + 覆盖入口对象 对象元数据 Cache-Control 缓存键别带无关 query；刷新是延迟生效
                            Sentry Release — — build_id 当 release，source map 上传后按版本看错误率

                            可退开关：保留 releases/<date>/index.html 与全部历史 assets/；回滚 = 一次 cp + mv（静态文件不需要 reload nginx）；用软链则 ln -sfn releases/20261120 current。开关粒度是"整个入口"，功能级回退见 55.2 特性开关。

                            什么时候别用：内部后台、单团队、日活几千、没有独立客户端——灰度基建（分流、分版本指标、兼容窗口）的固定成本大于收益。此时 no-store 入口 + 保留 1 个旧版本 + 5 分钟回滚就够。反过来，只要有独立客户端或入口缓存超过 1 min，这套一项都不能少。

                            反模式

                            反模式 后果
                            入口 HTML 设 max-age=3600 或更长，回滚靠刷 CDN 实测 300 s 就让回滚失效；1 h 意味着事故期一小时无法止损，CDN 刷新还有节点延迟
                            发布时清空 assets/ 只留当前版本 旧标签页、旧入口缓存、旧离线包请求已删除 chunk → 404 白屏（实测 bodyTextLen=0）
                            灰度用 Math.random() 按请求分流 同一用户 20 次访问换 12 次版本，状态与埋点全乱，灰度结论不可用
                            资源文件名不带内容哈希，或复用 app.js 无法原子切换；缓存里新旧混用，出问题无法判断用户跑的是哪份代码
                            /assets/ 的 404 也带 immutable CDN 把 404 缓存一年，补回资源用户也拿不到（实测踩到）
                            SPA 全量兜底 try_files $uri /index.html 覆盖资源路径 缺失 chunk 返回 200 + HTML，监控看不到 404，用户看到白屏
                            没有 app_version/build_id 就放量 出事只能全量回滚，无法回答"哪一版、多少人、要不要停"

                            自检

                            Q1 入口 HTML 用 no-cache + ETag 和用 no-store，回滚生效时间一样吗？代价差在哪？ ▸ 答案：都是"下一次导航"生效，no-cache 每次回源验证、ETag 只省响应体不省往返。no-cache 命中 304 时省 HTML 字节但仍有 1 个 RTT；入口在 10 KB 量级时，这个 RTT 换回滚确定性划算。

                            Q2 为什么前端灰度比后端多一个"版本维度"？举一个后端灰度不存在的场景。 ▸ 答案：后端灰度切请求，一个请求只属于一个版本；前端切页面实例，实例活在浏览器里。同一 uid 可同时开两个标签页，一个在灰度批次、一个在旧缓存，两个前端版本并发请求同一后端。后端不会"同一连接跑两个版本"，前端会，所以矩阵是笛卡尔积。

                            Q3 旧资源保留 K 个版本，K 怎么算？为什么不是"保留最近 3 个"？ ▸ 答案：K 要覆盖"最慢用户多久回到线上"，取 ceil(回滚窗口 / 发布间隔) + 1；窗口 = max(入口 TTL, SW 更新周期, 强更周期, 最长会话)。按天发版、30 d 强更算，K 至少 31 而不是 3。成本按 1.8 MB/版本是 56 MB，相对一次全量 180 GB 可忽略；成本在流程必须"只增不删"。

                            Q4 5% 灰度跑了两小时：JS 错误率持平，但 chunk 404 率 0.4%、白屏率 0.2%、build_id 覆盖率 62%。停还是放？下一步先做什么？ ▸ 答案：立刻停，不放量。chunk 404 > 0 说明旧资源被删或入口与资源不匹配，白屏 0.2% 已经触线；覆盖率 62% 说明 38% 的事件没带版本，所谓"错误率持平"本身不可信——先修上报再谈指标。下一步：查 404 的 chunk 名对应哪个旧入口、把旧资源补回并确认资源路径返回 404 而不是 200 + HTML，然后重新灰度。判据顺序是「资源完整 → 指标可信 → 再放量」。

                            Q5 用户反馈"还是旧页面"，你按什么顺序排查？ ▸ 答案：先看响应头：curl -I 入口是否 no-store、CDN 的 Age/X-Cache 是否命中；再看 SW 是否注册、缓存里是否有旧 HTML；再看标签页是否发布前就开着、version.json 的 build_id 是否一致；最后看灰度键：这个 uid 是否本来就不在批次里。顺序从"服务端说了什么"到"客户端存了什么"。

                            Q6 监控里 chunk 404 率为 0、JS 错误率为 0，但用户投诉白屏。最可能是哪条配置错了？给一条 5 分钟内能确认的命令。 ▸ 答案：最可能是 SPA 全量兜底 try_files $uri /index.html：缺失 chunk 返回 200 + text/html，于是 404 指标恒为 0，浏览器只报 MIME 错。确认：curl -sI https://host/assets/app.<hash>.js 看状态码与 Content-Type，若为 200 + text/html 即命中。修法：资源路径必须 try_files $uri =404，只有页面路径才兜底（实测同一缺失资源：正确配置 404，兜底 200 + HTML）。
