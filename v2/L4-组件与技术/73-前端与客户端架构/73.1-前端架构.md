# 73.1 前端架构 (SPA / SSR / 微前端)

## 一句话

> 前端架构的核心不是「选 SPA 还是 SSR」，而是**按页面决定渲染发生在哪一侧**：内容页把 HTML 生成推到服务端/边缘，交互页把渲染留在客户端；微前端解决的是「多个团队改同一个页面」的组织问题，代价是运行时隔离与共享依赖两笔账——渲染选错，首屏慢；拆分选错，团队互相拖慢。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| SSR 比 CSR 快，因为「服务端先算好了 HTML」 | SSR 只把**内容**提前，不把**交互**提前。同一份 100 条列表与 React 18.3.1 组件源码，4G+CPU 4 倍降速下：SSR 内容就绪 **250 ms**、水合完成 **1,199 ms**；纯 CSR 内容就绪 **1,291 ms**、可交互 **1,294 ms**——内容提前 5.2 倍，可交互只领先 95 ms（7%） |
| 静态化 = 内容冻结 | Next.js 14.2.3 里 `revalidate = 60` 的页面在 build 输出中仍是 ○（Static）符号；实测过期后第一次请求仍返回旧时间戳 `11:43:04`，之后才变成 `11:44:40`。静态化的是「HTML 形态」，不是「内容快照」 |
| 微前端能省重复代码 | 共享依赖不能共享时，两个子应用各打一份 **154,974 B** 的公共库：首屏 JS 共 **310,894 B**，其中 **49.8%** 是同一份库的第二份拷贝。4G 下首屏就绪 1,818 ms，共享版 1,103 ms，差 715 ms（1.65 倍） |
| 一个应用只能用一种渲染模式 | 同一个 Next.js 构建里四页四种模式：`/` 静态、`/isr` 60 秒重建、`/dynamic` 每请求渲染、`/client` 只发一个空壳（HTML 4,094 B，正文里 0 条数据） |

## 渲染模式：一张五维表 + 一张决策表

渲染模式的差别不在「谁生成 HTML」，而在**这笔账记在谁头上**：内容到得早不早、首字节等多久、水合花多久、缓存能不能吃、上线要养什么。

| 模式 | 首屏内容时间 | TTFB（谁在等） | 水合成本 | 缓存友好度 | 运维成本 |
|---|---|---|---|---|---|
| **CSR**（SPA） | 最晚：4G 实测 **1,291 ms**（等 JS → 发请求 → 渲染） | 最小：HTML 530 B，服务端不取数 | 0（渲染即交互） | 高，但**入口不能照搬**：SSG 页实测 `s-maxage=31536000, swr`；自建入口必须短缓存/不缓存（[73.5 前端发布与灰度](73.5-前端发布与灰度.md)） | 最低：纯静态托管 |
| **SSR**（逐请求） | 早：同内容实测 **250 ms**（实验 A 为构建期预渲染） | 最大：每次取数 + 渲染，实测 `/dynamic` 为 `no-store` | 高：同一棵列表树实测 **949 ms** | 最低：`private, no-cache, no-store` | 中高：常驻 Node、要压测限流 |
| **SSG**（构建期） | 最早：请求期不再渲染 | 最小：命中即返回 | 高（同 SSR 量级，取决于树大小） | 高：`s-maxage=31536000, swr`（实测 `/`） | 低：构建即发布，内容是「版本」不是「数据」 |
| **ISR**（增量重建） | 早：首发命中旧 HTML | 最小：命中缓存 | 高 | 高：`s-maxage=60, swr`（实测 `/isr`） | 中：要设计 revalidate 与失效 |
| **流式 SSR** | 分段最早：首字节出骨架 | 中：先发头，边取数边发 | 高且**分段** | 低：只能缓存片段 | 最高：要支持分块/流式输出的服务端与反代；HTTP/2 只减少队头阻塞，不是必需 |

> ⚠️ 数字来自同一份组件、同一份数据、同一台机器；流式 SSR 只写机制不写数字——**未验证**：需要支持分段传输的 Node 服务端，本节没做。

决策表按「你的情况」查，不用按「哪个技术新」查：

| 你的情况 | 选什么 | 理由（一句话） |
|---|---|---|
| 内容页（文章、商品、文档），SEO 与首屏权重高，内容按分钟级更新 | ISR 或 SSG + 按需重建 | 拿静态的 TTFB，不牺牲内容新鲜度 |
| 内容几乎不变（落地页、帮助中心） | SSG | 构建期算完，请求期零渲染成本 |
| 登录后的交互后台，SEO 无关，页面状态多 | CSR（SPA） | 首屏那点 HTML 省不下多少，交互复杂度才是主成本 |
| 首屏高度个性化（我的订单、我的看板）且不能缓存 | SSR + 关键数据内联 | 个性化内容没法整页缓存，只能把取数搬到服务端 |
| 页面很长、服务端取数有慢依赖 | 流式 SSR + Suspense 边界 | 先把头部与骨架发出去，慢的部分后到 |
| ≥3 个团队共改同一页面、各自要独立发布 | 微前端（qiankun / Module Federation） | 买的是组织解耦，不是性能 |
| 团队 <3 个、页面 <5 个、发布窗口能对齐 | 单仓单应用 + 路由级代码分割 | 微前端的运行时与依赖治理成本买不到组织收益 |

## 实测 A：同一份内容，CSR 与 SSR 差在哪

做法：`react@18.3.1` + `react-dom@18.3.1` 的 UMD（`react.production.min.js` 10,751 B、`react-dom.production.min.js` 131,835 B）；服务端在 Node `vm` 里 eval React，再 eval `react-dom-server-legacy.browser.production.min.js` 做 `renderToString`。组件源码是同一个字符串（服务端注入 `vm`，客户端拼进 `app.js`）。CSR 页是空 `#root` + 三个脚本，先 `fetch('/api/items')` 再 `createRoot().render()`；SSR 页把预渲染 HTML 与数据内联后 `hydrateRoot`，不发 API 请求。两页都在内容进 DOM 时打 `performance.mark('content-ready')`，SSR 页另在 `useEffect` 里打 `hydrated`。

```js
// 服务端同构内核（真跑过的版本，含两个必须踩的坑）
const ctx = vm.createContext({ console, TextEncoder, TextDecoder, setTimeout, clearTimeout });
vm.runInContext('var self = globalThis;', ctx);            // 坑①：UMD 头是 strict 模式，顶层 this 为 undefined，会去找 self
vm.runInContext(read('react.production.min.js'), ctx);
vm.runInContext(read('react-dom-server-legacy.browser.production.min.js'), ctx); // 坑②：browser(流式)构建没有 renderToString
vm.runInContext(COMPONENT, ctx);                            // 与客户端同一份组件源码
const html = vm.runInContext('ReactDOMServer.renderToString(React.createElement(App,{items}))', ctx);
```

三条报错都是本机原样打出来的，顺序就是我踩的顺序：

```text
ReferenceError: self is not defined
ReferenceError: TextEncoder is not defined
TypeError: ReactDOMServer.renderToString is not a function
```

环境：macOS arm64 / Chrome 157 / Node 26.10.0 / headless / 每组 5 次中位数（丢弃首次热身），原始输出在 `.cache/t73/s731/raw/`。

```bash
# 静态根目录里放 csr.html / ssr.html / 三个 js 与 api/items，然后：
node .cache/t73/bench/probe.js .cache/t73/s731/site /csr.html /ssr.html
# fast 与 4g+cpu4x（150 ms RTT / 1.6 Mbps / CPU 4 倍降速）两组
```

```text
/csr.html fast      ready=30    res=4  jsReq=3  wireBytes=164651
/csr.html 4g+cpu4x  ready=1291  res=4  jsReq=3  wireBytes=164651
/ssr.html 4g+cpu4x  ready=250   res=3  jsReq=3  wireBytes=182037
```

| 读数（4G+CPU4x，5 次中位数；内容就绪取 probe 组，可交互取同环境 hydration 标记组，两轮差 3 ms） | CSR | SSR | 差 |
|---|---|---|---|
| 内容就绪 `ready` | 1,291 ms | **250 ms** | 内容提前 **5.2 倍** |
| 可交互（CSR=`interactive`，SSR=`hydrated`） | 1,294 ms | **1,199 ms** | 只领先 **95 ms（7%）** |
| HTML 字节 | 530 B | 37,095 B | SSR 多 36,565 B（内联数据 + 预渲染列表） |
| 首屏 JS 字节 | 144,026 B | 143,742 B | 几乎相同（差 284 B） |
| 请求数 | 4 | 3 | SSR 少 1 次 API 往返 |
| `wireBytes` | 164,651 B | 182,037 B | SSR 反而**多 10.6%** |
| 4G 下 API 请求何时发出 | 导航后 **1,035 ms** | 不发 | HTML 154 ms 就到了，数据请求晚了 881 ms |

> 🔑 **SSR 的收益上限是 FCP/LCP，不是 TTI。** 内容 250 ms 到、水合 1,199 ms 完成，中间 949 ms 看得见却点不动；纯 CSR 的可交互是 1,294 ms——两页「能用」的时间几乎一样，差的是「看见」。

最容易被误读的是 `wireBytes`：SSR 总字节更多（多内联 18,595 B 数据），首屏内容却更早到达，原因是**关键路径形状**而非字节总量——CSR 要等 144 KB JS 下载执行完才发第一个数据请求（实测 881 ms 瀑布），SSR 把往返挪到了 HTML 到达之前。

> 💡 **我的判断是**：多数「SSR 项目」的真实收益来自**把数据请求搬到服务端**，不是 HTML 字符串本身。按本机数据估算，1,291 ms 里约 881 ms 是「等 JS 才能发请求」的瀑布，只有约 250 ms 是真正的 HTML 传输与渲染；所以先做「数据内联 / 服务端预取」，再考虑换渲染框架。手段总表见 [34.4 优化手段](../../L3-质量属性/34-性能/34.4-优化手段.md)，指标口径见 [34.1 性能指标](../../L3-质量属性/34-性能/34.1-性能指标.md)。

## 水合的本质：同一份代码在两侧各跑一遍

服务端只把组件树变成字符串；客户端拿到 HTML 后还要**把同一份代码再执行一遍**：重建组件树、绑事件、核对两侧首帧是否一致。三件事都在主线程，与「内容已可见」无关。React 18 的 `hydrateRoot` 在并发模式下是异步的，实测把 100 条列表的 `hydrated` 推到内容就绪之后 949 ms。

| 你以为的 SSR 时间线 | 实际时间线（4G，本机实测） |
|---|---|
| 请求 → 渲染 → HTML → 页面可用 | 0–250 ms 内容可见（能选中、能滚动）→ 250–1,028 ms 下载并执行 JS（点击无反应）→ 1,028–1,199 ms 水合 → 1,199 ms 后可交互 |

「SSR 让页面变快」要拆成两句：**内容更早可见**成立（5.2 倍），**更早可交互**基本不成立（7%）。水合长任务还会污染 INP：水合窗口里每次点击都排在它后面。

降成本三条路，按性价比排序：**缩小水合面**（Islands / 选择性水合，只水合要交互的组件，即 `client:visible` / `client:idle`）→ **服务端组件**（RSC 只传序列化结果、不参与水合，代价是第三方库逐个确认兼容）→ **分段水合**（Suspense 边界先到先水合，依赖流式传输）。

> 🔑 水合成本不会消失，只会转移：要么转移到「更少的组件」（缩小水合面），要么转移到「更晚的时间」（分段），要么转移到「构建期」（SSG 也逃不掉水合，它只是把渲染挪走了）。任何声称「SSR 免掉水合」的说法，都是在说另一件事——不水合，也就不交互。

## 同构代码的四类陷阱

同一份代码跑两侧，错误也在两侧各出一次。四类陷阱的判据都能本地复现。

| 陷阱 | 现象 | 判据 / 修法 |
|---|---|---|
| **浏览器 API 在服务端不存在** | 构建期或首个请求直接崩：`window is not defined`、`self is not defined`、`TextEncoder is not defined`（后两条本机原样报错） | 判据：模块顶层是否碰 `window`/`document`/`localStorage`。修法：挪进 `useEffect`、加 `typeof window` 守卫、或该组件 `dynamic(..., { ssr: false })` |
| **双端状态不一致** | `Date.now()`、`Math.random()`、时区/locale、随机 ID 让两侧首帧不同，React 报 mismatch 并丢掉服务端 HTML 重渲染 | 判据：服务端 HTML 与客户端首帧做字符串比对。修法：时间与随机数只放 `useEffect`，或服务端注入值后客户端原样用 |
| **内存 / 连接泄漏** | 模块级单例缓存、全局定时器、共享连接池把请求级数据带进下个请求——A 用户看到 B 的数据，RSS 随 QPS 线性涨 | 判据：压测看 RSS 是否随请求数单调上升；搜模块级 `let cache = []`。修法：每请求一个上下文，禁模块级可变状态 |
| **请求瀑布** | 服务端渲染里串行 `await` 三个接口；客户端先下 JS 再发请求（实测晚 881 ms） | 判据：TTFB ≈ 各接口 RTT 之和；首个 API 请求的开始时间晚于最后一个 JS 的结束时间。修法：服务端并行取数、客户端 `preload`/`preconnect` |

第三条最贵：不报错，只在并发上来后表现为「内存涨、串数据」。第四条最易忽略：一次串行取数就是一次额外 RTT，跨境链路一次 RTT 能到 80 ms 量级（[9.5 动态加速](../../L0-运行时底座/9-CDN与边缘/9.5-动态加速.md)），三次串行 240 ms 直接进 TTFB。

## 微前端：三种隔离，两笔账

微前端解决的是**组织问题**：多个团队改同一页面、各自要独立发布。它不解决性能——多一层运行时、多一份依赖治理。判断该不该上，先算三笔账。

### 第一笔账：共享依赖不复用

两个「子应用」各自依赖同一份 154,974 B 的公共库（模拟 lodash/组件库/i18n），分别按「各打一份」与「共享一份」构建，同一台机器、同一个探针量首屏。

| 配置 | 首屏 JS（raw） | gzip | 请求数 | 4G 首屏就绪 |
|---|---|---|---|---|
| 各打一份（每个子应用内联一份库） | **310,894 B** | 58,976 B | 2 | **1,818 ms** |
| 共享一份（库单独一个文件，子应用只带业务码 473 B） | **155,920 B** | 29,800 B | 3 | **1,103 ms** |
| 差 | 154,974 B（**49.8%**） | 29,176 B（49.5%） | +1 次请求 | -715 ms（1.65 倍） |

算式对得上：`154,974 B × 8 ÷ 1.6 Mbps ≈ 0.77 s`，实测差 715 ms。**重复的字节几乎原样变成了用户的等待**；重复的还有第二份代码的解析执行（已在 ready 里）。

> 🔑 「共享依赖」不是一句构建配置，而是一份**版本契约**：Module Federation 的 `shared` 只能保证「同一份运行时只加载一次」，保证不了「两个子应用要的 React 版本兼容」。同一个页面只能有一份 React 实例；17 与 18 的 concurrent 行为、StrictMode 双调用都不同，共享前必须锁版本并统一渲染入口。

### 第二笔账：样式不隔离

同一文档里，A 定义 `.btn{background:red}`、B 定义 `.btn{background:blue}`，先后挂载后读 A 的按钮计算色。

| 挂载方式 | A 按钮最终背景色 | B 按钮 | 结论 |
|---|---|---|---|
| 全局 class（各自注入 `<style>`） | **rgb(0, 0, 255)**（蓝） | rgb(0, 0, 255) | A 的 `.btn` 被 B 覆盖：后插入的样式赢，3 次测量一致 |
| 各自挂载 Shadow DOM | **rgb(255, 0, 0)**（红） | rgb(0, 0, 255) | 隔离生效，A 不受 B 影响 |

命名约定靠人守，隔离机制靠运行时保证。qiankun 的 `strictStyleIsolation` 走的就是 Shadow DOM 这条机制——本节验证的是机制，qiankun 的具体开关**未验证**（本机没装 qiankun）。

### 第三笔账：JS 运行时

| 隔离维度 | 常见手段 | 拦得住 | 拦不住 | 成本 |
|---|---|---|---|---|
| **JS 运行时** | Proxy 沙箱 / iframe / `with`+eval（qiankun 的 JS 沙箱） | 全局变量污染、`window` 覆盖、子应用之间的变量串台 | 内存泄漏、`setInterval`、事件监听、原型链篡改 | 中：每个子应用一套沙箱，断点调试变难 |
| **样式** | 前缀命名空间 / CSS Modules / Shadow DOM | class 覆盖（实测 A 被 B 改成蓝色） | `:root` 变量、全局字体、`z-index` 与 `position:fixed` 的层级竞争 | 低–中：Shadow DOM 会挡住全局主题注入 |
| **依赖** | Module Federation `shared` / externals / import map | 重复下载与重复执行（实测 49.8% 字节） | 版本冲突：同一个库只能有一份实例 | 高：要约定版本窗口、升级流程与回滚 |

### 组织前提与「什么时候别用」

前提是**团队边界已经存在**：≥3 个团队共改同一页面、发布节奏对不齐、各自独立值班与仓库。缺一条，微前端只是替一个团队给自己加一层运行时。判据在 [74.3 团队边界](../../组织/74-康威定律与团队拓扑/74.3-团队边界与架构边界的对齐.md)。

**什么时候别用微前端**（写进 ADR）：团队 < 3 个，没有多个发布主体；页面 < 5 个，路由级代码分割 + monorepo 就够；没有独立发布需求，发布窗口能对齐；只是想复用组件——那是组件库/设计系统的事。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：React 栈逐页选渲染模式用 **Next.js 14.2.3（App Router）**，Vue 栈对应 **Nuxt 3**；微前端用 **qiankun 2.x**（Shadow DOM 严格样式隔离）或 **webpack 5 / Rspack 的 Module Federation**。本节 Next.js 数字都来自本机真跑的 14.2.3 构建。

**可抄**：三种模式是**页面级导出**，不改构建配置：

```js
// app/isr/page.js —— ISR：60 秒后后台重建，先给旧 HTML
export const revalidate = 60;
// app/dynamic/page.js —— 退回逐请求 SSR
export const dynamic = 'force-dynamic';
// app/client/page.js —— 只把这个子树交给浏览器渲染
'use client';
```

```bash
# next.config.mjs 设 output:'standalone'，产物自带 server，部署不依赖 node_modules
npx next build && npx next start -p 3123
curl -sI http://127.0.0.1:3123/isr | grep -i 'x-nextjs-cache\|cache-control'
```

```text
# 节选（全量路由表含 /_not-found 与 /api/items，见 raw/c-next/build.txt）
Route (app)                              Size     First Load JS
┌ ○ /                                    146 B          87.1 kB
├ ○ /client                              383 B          87.3 kB
├ ƒ /dynamic                             146 B          87.1 kB
└ ○ /isr                                 147 B          87.1 kB
○  (Static)   prerendered as static content
ƒ  (Dynamic)  server-rendered on demand
```

**可验**：四种模式在同一次构建、同一端口上直接对比（原始输出在 `.cache/t73/s731/raw/c-next/`）：

| 路由 | 模式 | HTML 字节 | 正文里有数据吗 | 响应头 |
|---|---|---|---|---|
| `/` | SSG | 10,348 B | 有（100 条列表 ×2，含 RSC 载荷） | `s-maxage=31536000, swr` |
| `/client` | CSR 壳 | 4,094 B | 没有（只有 `loading…`） | `s-maxage=31536000, swr` |
| `/isr` | ISR（60 s） | 3,981 B | 有 | `s-maxage=60, swr` |
| `/dynamic` | SSR | 3,993 B | 有；HTML 里带服务端渲染时刻（实测样本 `2026-11-21T11:43:31.669Z`），且 `no-store`，每次请求重新渲染 | `private, no-cache, no-store` |

ISR 的「旧」可测：过期后第一次请求仍返回 `11:43:04`，随后才变 `11:44:40`——**先给旧内容，后台重建**。拿它承载库存、余额，用户看到的就是 60 秒前的数。

**可退**：每个路由一行开关就能降级，不用回滚构建：

| 退路 | 做法 | 代价 |
|---|---|---|
| ISR 数据过期出事故 | 该页改 `export const dynamic = 'force-dynamic'`（ISR → SSR），或把 `revalidate` 调到 0 | TTFB 变高，Node 压力上升 |
| SSR 服务扛不住 | 该页降为 SSG + 客户端补数据 | 内容变旧，个性化变弱 |
| 水合报错导致白屏 | 组件级 `dynamic(..., { ssr: false })`，或整页退回 CSR 壳 + 骨架 | 首屏内容时间退化 |
| 微前端样式/沙箱互踩 | 关 JS 沙箱，或子应用降级独立域名跳转 | 失去同页共存，但可服务 |

这些开关只救「渲染模式」这一类问题：发布顺序与旧资源共存窗口是 [73.5 前端发布与灰度](73.5-前端发布与灰度.md) 的主场，字段语义是 [73.4 前后端契约与协作](73.4-前后端契约与协作.md) 的主场；CDN 命中率由缓存键决定（[9.1 边缘缓存原理](../../L0-运行时底座/9-CDN与边缘/9.1-边缘缓存原理.md)），缓存头见 [41.1 缓存模式](../41-缓存/41.1-缓存模式.md)，灰度分流见 [47.3 路由与灰度](../47-网关与入口/47.3-路由与灰度.md)，BFF 聚合见 [33.6 BFF 与 API 组合](../../L2-架构风格/33-部署形态/33.6-BFF与API组合.md) 与 [47.2 API网关](../47-网关与入口/47.2-API网关.md)；把渲染推到 PoP 见 [9.6 边缘计算模型](../../L0-运行时底座/9-CDN与边缘/9.6-边缘计算模型.md)。

现实分布（2026-11-21 抓首页，原始数据在 `.cache/t73/s731/raw/c/`）：nextjs.org 首屏仍下 24 个 script、451,148 B；linear.app 只用 3 个 script，却把 HTML 撑到 1,265,756 B（压缩后 186,773 B）——**这两个首页都不是「零 JS 的 SSR」**。

## 反模式

| 反模式 | 后果 |
|---|---|
| 全站上 SSR，含登录后后台 | 多付常驻 Node 与压测成本，可交互几乎没变（1,199 vs 1,294 ms） |
| 服务端组件顶层读 `window`/`localStorage` | 构建期或首个请求崩：`self is not defined`、`TextEncoder is not defined` |
| 模块级可变状态装请求数据 | 请求间串数据，RSS 随 QPS 线性涨，压测才暴露 |
| 两个子应用各打一份 React/组件库还叫「微前端」 | 49.8% 首屏 JS 是重复字节，4G 多等 715 ms，解析执行再来一遍 |
| 用全局 class 做子应用样式，靠命名不冲突 | 实测 A 的按钮被 B 改成蓝色：命名约定不是隔离机制 |
| 用 ISR 承载库存/余额 | 过期后第一次请求仍返回旧 HTML（实测 `11:43:04`），直接超卖 |

## 三条铁律

> 🔑 **渲染模式按页面选，不按项目选。** 同一构建里可并存 SSG/ISR/SSR/CSR 四种；按项目一刀切，必然有一半页面在付另一半的账。

> 🔑 **SSR 优化 FCP/LCP，不优化 TTI。** 内容与可交互之间隔着水合：实测 949 ms。要么缩小水合面，要么接受「看得见、点不动」的窗口。

> 🔑 **微前端买组织解耦，付运行时隔离 + 依赖治理。** 没有 3 个团队与独立发布需求，这笔交易是负收益：重复字节（49.8%）与样式互踩立刻兑现，组织收益永远不出现。

## 自检

**Q1** 产品经理说「页面不是已经出来了吗，为什么点了没反应」，你拿哪两个数解释，分别代表什么？

▸ 答案：拿「内容就绪 250 ms」与「水合完成 1,199 ms」。前者是 HTML 到达、内容进 DOM（FCP/LCP）；后者是同一份代码在客户端跑完、事件绑上（TTI）。中间 949 ms 可见但不可交互；对照 CSR 的 1,294 ms，SSR 买的是「看见得早」。

**Q2** SSR 页的 `wireBytes` 比 CSR 页多 10.6%（182,037 vs 164,651），为什么内容反而早到 5.2 倍？

▸ 答案：关键路径形状不同，不是字节总量。CSR 是「HTML → 144 KB JS 下载执行 → 才发 API 请求」，实测晚到 1,035 ms；SSR 把数据内联进 HTML，多出来的字节是「提前传的数据」。

**Q3** 两个子应用各自打包了一份公共库，怎么用一条命令量出重复字节，而不是靠估算？

▸ 答案：构建两套产物（各打一份 / 共享一份），对每个 js 取 `stat -f%z` 与 `gzip -9` 双口径求和算差：310,894 − 155,920 = 154,974 B（49.8% raw，49.5% gzip）；再用 probe 比 `wireBytes` 与 `ready`（1,818 vs 1,103 ms）。

**Q4** 子应用样式互踩，除了 Shadow DOM 还有哪些手段？各自漏什么？

▸ 答案：前缀命名空间（漏：靠人守，`:root` 变量照样穿透）、CSS Modules（漏：只隔离自己写的）、iframe（漏：通信与路由成本、弹层被裁）。Shadow DOM 挡得住 class 覆盖（实测 A 保持红），挡不住全局字体与 `:root` 变量——主题要用 CSS 变量显式注入每个 shadow root。

**Q5** 商品详情页用 ISR 60 s，运营 10:00 改价，10:00:05 用户 A 看到旧价并下单成功，10:01 用户 B 用新价下单。A 的订单算 bug 吗？该改哪一层？

▸ 答案：算——价格与库存一样参与**不可撤销的决策**，60 s 的旧 HTML 会让一部分用户按旧价成交。改法不是把 `revalidate` 调到 0，而是把「价格/库存」从 ISR 页面里拆出去：页面壳用 ISR，价格走客户端/边缘实时接口，下单时服务端再校验一次并返回最新价。判据仍是「旧值能不能支撑不可撤销的决策」，不是「旧了几秒」。

**Q6** 团队 3 人、4 个页面、两个后端团队、发布窗口能对齐；领导要求"先上微前端，以后好扩展"。你拿哪三个数答复，替代方案是什么？

▸ 答案：拿三个数：① 共享依赖不共享时 **154,974 B / 49.8%** 的首屏 JS 是重复的；② 4G 下多等 **715 ms**；③ 上线条件是 ≥3 个**有独立发布权**的团队（发布窗口能对齐就不满足）。替代方案：monorepo + 路由级代码分割 + 包边界 lint，先在**不引入运行时**的前提下把模块边界立住。等出现"两个团队每周互相等对方发版"的实际记录，再评估微前端——那时买的是发布权，不是性能。
