# 76.4 风控与反欺诈

## 一句话

> 金融核心的风控不是「上一个模型」，而是**把便宜且硬的判据排在前面**：名单 → 限额 → 行为规则 → 模型评分 → 人工复核，逐级过滤、命中即止；判据是**每笔拒绝都能给出原因码与命中项，每笔复核都能在时限内闭环**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 风控就是上模型 | 名单与限额覆盖了绝大多数已知风险，模型只处理长尾；先上模型是拿最贵的手段解最简单的问题 |
| 限额是业务配置，跟架构无关 | 限额要在缓存里原子扣减并跨日聚合，架构错了必然超限 |
| 拦截率越高越安全 | 误杀一个正常客户 = 客诉 + 流失 + 口碑，代价可量化，且远高于单笔漏放 |
| 规则越多越安全 | 规则互相冲突、互相抑制；每次变更都是发版，规则库会变成没人敢动的黑箱 |
| 黑名单一查就够 | 黑名单只防已知坏人；团伙化、养号、快进快出要靠行为规则与模型 |

风控系统的流水线、决策点与整体时延预算在 [68.1 风控系统架构](../68-风控/68.1-风控系统架构.md) 讲透，本节聚焦金融核心交易侧：**限额体系怎么扣、名单怎么匹配、决策怎么串成一个可解释的级联**。

## 四类判据：先算成本，再谈准度

| 判据 | 数据来源 | 单次成本 | 覆盖风险 | 可解释性 | 误杀率 |
|---|---|---|---|---|---|
| 名单（黑/灰/白） | 内存表 / Redis | 微秒级 | 已知坏人与白名单客户 | 强（命中即是理由） | 低（白名单可纠偏） |
| 限额（单笔/日/月） | 缓存计数 | 微秒级 | 大额盗刷、异常集中 | 强（硬约束） | 极低 |
| 行为规则（时段/新对手方） | 特征直读 | 微秒级 | 盗刷、养号、快进快出 | 强（规则可复述） | 中 |
| 模型评分 | 特征计算 + 推理 | 数毫秒–数十毫秒 | 长尾、团伙 | 弱（需 SHAP 等归因） | 中 |
| 人工复核 | 工单系统 | 分钟–小时 | 极少数高价值可疑单 | 强（人给结论） | 最低（但成本最高） |

> 🔑 级联的原则：**越便宜、越硬、越可解释的判据越靠前**。黑名单命中直接拒绝，根本不该进模型——把已知坏人送进模型打分，只是浪费 30ms。

## 决策矩阵：四类判据怎么组合

| 名单 | 限额 | 行为特征 | 决策 | 说明 |
|---|---|---|---|---|
| 黑名单命中 | 任意 | 任意 | 拒绝 | 原因码 R01，不进模型、不进复核 |
| 白名单 | 超限 | 任意 | 拒绝 | 白名单只免「名单类」拦截，限额是硬约束 |
| 灰名单 | 未超限 | 大额 | 复核 | 灰名单不直接拒，转人工判断 |
| 正常 | 超限 | 任意 | 拒绝 | 限额类原因码 R02–R04，无解释空间 |
| 正常 | 未超限 | 深夜大额 / 新对手方 | 复核 | 行为规则只降级为复核，不直接拒绝 |
| 正常 | 未超限 | 无异常 | 通过 | 原因码 R99 |

白名单的边界最容易被误解：**白名单免的是「名单类拦截」，不免限额、不免行为规则**。把白名单当成「免死金牌」，等于给高价值客户开了盗刷通道。

## 限额体系：五个维度都要有

| 维度 | 本机仿真取值 | 实现要点 |
|---|---|---|
| 单笔限额 | 2 万 / 5 万 / 10 万（按客户等级） | 交易级硬校验，先于累计限额判断 |
| 日累计 | 5 万 / 20 万 / 50 万 | 当日计数缓存，日终与账务流水回填对账 |
| 月累计 | 20 万 / 100 万 / 500 万 | 跨日聚合，注意日切与自然月的边界 |
| 对手方限额 | 新对手方首笔限额 | 首次转账、新卡、新设备都要单独限额 |
| 渠道限额 | 手机银行 vs 柜面 vs 开放 API | 渠道风险不同，限额必须差异化 |

限额扣减的三个工程细节：

| 细节 | 正确做法 | 错的后果 |
|---|---|---|
| 原子性 | 缓存里 INCR + 校验，超限即回滚 | 并发下 10 笔同时通过，日累计爆表 |
| 只有「通过」才占用额度 | 复核单不占用，拒绝单释放 | 复核被拒的单永久吃掉额度 |
| 日切与幂等 | 日切按业务日期，重试不重复扣 | 跨日重试扣两次，客户额度凭空少一半 |

## 本机可运行：限额 + 名单 + 规则的决策级联

`go run main.go`（go1.27.1 darwin/arm64）。本机仿真 10 笔交易（含黑名单、灰名单、白名单、超限、深夜大额、新对手方），输出每笔决策、原因码与耗时。原始输出存 `.cache/domain-76/raw-76.4.txt`。

```go
package main

import (
	"fmt"
	"time"
)

type Limit struct{ Single, Day, Month int64 } // 元

type Txn struct {
	ID       string
	Cust     string
	Card     string
	Hour     int
	Amt      int64
	NewPayee bool
}

var limits = map[string]Limit{
	"C001": {Single: 50000, Day: 200000, Month: 1000000},
	"C002": {Single: 20000, Day: 50000, Month: 200000},
	"C003": {Single: 100000, Day: 500000, Month: 5000000},
}

var blackCards = map[string]bool{"6222****9999": true}
var grayCust = map[string]bool{"C002": true}
var whiteCust = map[string]bool{"C003": true}

// decide 返回决策与原因码；拒绝级原因优先于复核级原因。
func decide(t Txn, lim Limit, dayUsed, monthUsed int64) (string, []string) {
	var deny, review []string
	if blackCards[t.Card] {
		deny = append(deny, "R01 黑名单-卡号")
	}
	if t.Amt > lim.Single {
		deny = append(deny, "R02 超单笔限额")
	}
	if dayUsed+t.Amt > lim.Day {
		deny = append(deny, "R03 超日累计限额")
	}
	if monthUsed+t.Amt > lim.Month {
		deny = append(deny, "R04 超月累计限额")
	}
	// 白名单只免“名单类”拦截，限额与行为规则照常执行
	if !whiteCust[t.Cust] && grayCust[t.Cust] && t.Amt > 10000 {
		review = append(review, "R11 灰名单+大额")
	}
	if t.Hour < 6 && t.Amt > 10000 {
		review = append(review, "R12 深夜大额")
	}
	if t.NewPayee && t.Amt > 30000 {
		review = append(review, "R13 新对手方大额")
	}
	switch {
	case len(deny) > 0:
		return "拒绝", deny
	case len(review) > 0:
		return "复核", review
	}
	return "通过", []string{"R99 无命中"}
}

func main() {
	txns := []Txn{
		{"F01", "C001", "6222****0001", 14, 8000, false},
		{"F02", "C001", "6222****0001", 14, 60000, false}, // 超单笔
		{"F03", "C001", "6222****0001", 14, 45000, false}, // 当日累计 8000+45000=53000，未超 200000
		{"F04", "C001", "6222****0001", 14, 155000, true}, // 日累计 208000 > 200000
		{"F05", "C002", "6222****0002", 14, 18000, false}, // 灰名单 + 大额(>10000)，未超单笔
		{"F06", "C002", "6222****0002", 14, 9000, false},  // 灰名单但小额
		{"F07", "C003", "6222****0003", 2, 80000, true},   // 白名单，深夜大额 + 新对手方
		{"F08", "C003", "6222****0003", 2, 20000, false},  // 深夜大额（>10000）
		{"F09", "C001", "6222****9999", 14, 100, false},   // 黑名单卡号
		{"F10", "C001", "6222****0001", 14, 4000, true},   // 新对手方但小额
	}

	used := map[string]int64{} // 当日累计
	month := map[string]int64{"C001": 300000, "C002": 120000, "C003": 900000}
	var pass, review, deny int
	var totalNs int64
	fmt.Println("== 1. 逐笔实时决策（规则 + 名单 + 限额）==")
	fmt.Printf("%-4s %-5s %-7s %-4s %9s  %-4s %-22s %s\n", "单号", "客户", "时间", "金额", "日累计后", "决策", "原因码", "耗时")
	for _, t := range txns {
		lim := limits[t.Cust]
		start := time.Now()
		dec, reasons := decide(t, lim, used[t.Cust], month[t.Cust])
		cost := time.Since(start)
		totalNs += cost.Nanoseconds()
		after := used[t.Cust] + t.Amt
		switch dec {
		case "通过":
			pass++
			used[t.Cust] = after // 只有通过才占用额度
		case "复核":
			review++
		case "拒绝":
			deny++
		}
		fmt.Printf("%-4s %-5s %02d:00   %9d %9d  %-4s %-22s %v\n",
			t.ID, t.Cust, t.Hour, t.Amt, after, dec, joinReasons(reasons), cost)
	}
	fmt.Printf("决策分布：通过 %d、复核 %d、拒绝 %d（共 %d 笔）\n", pass, review, deny, len(txns))
	fmt.Printf("单笔决策平均耗时：%.2f µs（本机计算，仅含规则匹配，不含 IO/模型打分）\n\n",
		float64(totalNs)/float64(len(txns))/1000)

	fmt.Println("== 2. 各客户当日额度占用（只有“通过”才占用）==")
	for _, c := range []string{"C001", "C002", "C003"} {
		fmt.Printf("%s 日累计 %7d / 限额 %7d（%.1f%%）\n", c, used[c], limits[c].Day,
			float64(used[c])*100/float64(limits[c].Day))
	}

	fmt.Println("\n== 3. 决策级联判据（从便宜到昂贵，命中即止）==")
	for _, s := range []struct {
		layer, cost, hit string
	}{
		{"名单（卡号/证件/设备）", "微秒级，内存表", "R01 黑名单直接拒绝，不进模型"},
		{"限额（单笔/日/月）", "微秒级，缓存计数", "R02-R04 硬约束，无解释空间"},
		{"行为规则（时段/新对手方）", "微秒级，特征直读", "R11-R13 转复核，不直接拒绝"},
		{"模型评分", "数毫秒到数十毫秒", "只在前面全不命中时打分，分数进复核队列"},
		{"人工复核", "分钟到小时", "复核结论回写名单与阈值"},
	} {
		fmt.Printf("%-24s %-14s %s\n", s.layer, s.cost, s.hit)
	}
}

func joinReasons(rs []string) string {
	out := ""
	for i, r := range rs {
		if i > 0 {
			out += "+"
		}
		out += r
	}
	return out
}
```

## 误杀与漏放：两笔账都要算

| 决策 | 代价 | 量级（经验值） |
|---|---|---|
| 漏放（该拦没拦） | 单笔资损 + 追偿成本 + 监管事件 | 单笔可达数万元，团伙案可达百万元级 |
| 误杀（不该拦拦了） | 客诉 + 客户流失 + 口碑 | 单客年价值数百至数千元，且影响可扩散 |
| 复核（转人工） | 人力成本 + 时效损失 | 单笔人工 1–5 分钟，积压会拉长时效 |
| 拒绝正确 | 无 | — |

判据不是「拦截率」，而是**漏放损失 + 误杀损失 + 复核成本之和最小**（成本模型与阈值算法见 [68.6 误杀与漏杀的权衡](../68-风控/68.6-误杀与漏杀的权衡.md)）。这也是三档决策（通过/复核/拒绝）比两档更合理的原因：复核档把「不确定」这件事实体化了。

## 反模式

| 反模式 | 后果 |
|---|---|
| 所有交易都进模型打分 | 时延超标、成本暴涨，而黑名单明明可以直接拒 |
| 限额只在应用层校验，不进缓存原子扣减 | 并发超限，日累计形同虚设 |
| 复核单也占用额度 | 被拒的复核单永久吃掉客户额度，客诉不断 |
| 白名单当免死金牌 | 高价值客户被盗刷，损失最大 |
| 规则库只增不删、无冲突检测 | 规则互相抑制，没人敢动，最后整体失效 |
| 拒绝不给原因码或原因码含糊 | 客诉无法解释，也无法统计哪条规则在误杀 |
| 无异步补判机制 | 模型或名单服务抖动，整条交易链路超时 |

## 自检

**Q1** 为什么黑名单命中不该继续进模型打分？

▸ 答案：名单命中已经给出确定结论（拒绝），再进模型只会多花数毫秒到数十毫秒，且模型分数不可能推翻黑名单。级联设计的原则是「命中即止」：便宜、硬、可解释的判据在前，把昂贵资源留给真正不确定的长尾。

**Q2** 白名单客户是不是可以不受限额约束？

▸ 答案：不行。白名单只免「名单类」拦截（如灰名单、可疑标记），限额是硬约束、行为规则照常执行。把白名单当免死金牌，等于给被盗刷风险最高的客户群开了最大通道。

**Q3** 复核档（转人工）为什么必须存在？

▸ 答案：因为「不确定」是真实存在的状态，用通过或拒绝二选一必然产生误杀或漏放。复核档把不确定交给人工，同时保留时效要求（如 30 分钟内出结论）；它的成本（1–5 分钟人力）远低于误杀或漏放的代价。

**Q4** 限额扣减为什么必须在缓存里原子完成？

▸ 答案：日累计是「读-判-写」三步，若不加原子操作，并发下多笔同时读到「未超限」再各自写入，累计值会被覆盖，实际通过额度远超限额。正确做法是 INCR 后判断，超限回滚；重试要幂等，日切按业务日期而非自然时钟。

**Q5** 判断风控好坏该看拦截率还是看什么？

▸ 答案：看成本结构：漏放损失 + 误杀损失 + 复核成本之和是否最小。拦截率可以靠放宽规则刷高，但误杀成本会同步上升；单看拦截率会诱导团队做出「宁可错杀一千」的决策，最终伤害的是正常客户与业务规模。
