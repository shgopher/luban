# 76.5 合规审计与多活

## 一句话

> 合规审计与多活容灾是同一个问题的两面：**审计要证明「谁在什么时候改了什么、依据是什么」，多活要保证「机房挂了业务还能继续、数据不丢」**；两者都靠「留痕 + 可校验 + 可演练」成立，判据是**审计链验得过、切换后 RTO/RPO 达标、数据校验全过**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 审计 = 把操作日志存下来 | 日志能被改就不叫审计；要哈希链、WORM 存储、异地备份，且链尾摘要外送 |
| 多活 = 两个机房都部署 | 没有数据同步与流量切换方案，两个机房只是两套单点 |
| RTO 标 5 分钟就真能 5 分钟 | 不演练的 RTO 是愿望；真实 RTO 是「探测 + 决策 + 切换 + 预热 + 校验」各段之和 |
| RPO = 0 一定最好 | 强同步换来写延迟与可用性下降，必须按业务分级定 RPO |
| 灾备切换是运维的事 | 切换涉及账务一致性、幂等、对账，必须在架构层设计 |

## 审计留痕的四要素

| 要素 | 必须记录的字段 | 判据 | 留存 |
|---|---|---|---|
| 谁 | 操作人、系统身份、复核人 | 实名且不可冒用，代操作要留授权链 | 按监管要求（常见 ≥5 年，以官方文档为准） |
| 何时 | 发生时间 + 记录时间（双时间戳） | 两个时间都要，缺一无法还原时序 | 同上 |
| 做了什么 | 动作、对象、变更前值、变更后值 | 前后值都记，只记「已修改」等于没记 | 同上 |
| 依据 | 审批单号、原始流水号、工单号 | 必须可点开、可关联到原始凭证 | 同上 |

防篡改有四个层次，缺一层就有一个绕过口：

| 层次 | 手段 | 能防什么 |
|---|---|---|
| 单条完整性 | 每条记录哈希：`hash = H(prev_hash + 内容)` | 改单条内容 |
| 链式完整性 | 逐条串链，链尾摘要定期对外报送 / 上链 | 改历史并重算后续哈希 |
| 存储层 | WORM / 对象存储合规锁 / 一次写多次读 | 运维级删改 |
| 权限层 | 审计库只允许追加，DBA 无 DELETE 权限 | 内部人删记录 |

## 多活形态：先定 RTO/RPO，再选形态

RTO 与 RPO 的定义与分级在 [36.1 RTO / RPO](../../L3-质量属性/36-灾备/36.1-RTO-RPO.md)，冷/温/热备与多活形态的取舍见 [36.3](../../L3-质量属性/36-灾备/36.3-冷备-温备-热备.md) 与 [36.4](../../L3-质量属性/36-灾备/36.4-两地三中心与多活.md)，单元化路由在 [36.5 单元化 / Set 化架构](../../L3-质量属性/36-灾备/36.5-单元化-Set化架构.md)。金融核心要做的选择是：

| 形态 | 数据同步方式 | RTO（量级） | RPO（量级） | 成本 | 适合的业务 |
|---|---|---|---|---|---|
| 单机房主备 | 异步复制 | 30 分钟–小时级 | 分钟–小时级 | 1x | 内部管理类系统 |
| 同城双活 | 半同步复制 | 1–5 分钟（口径见 [36.4](../../L3-质量属性/36-灾备/36.4-两地三中心与多活.md)） | 秒级 | 2–3x | 核心交易与账务 |
| 两地三中心 | 同城半同步 + 异地异步 | 5–30 分钟 | 秒级–分钟级 | 4x | 有监管要求的核心系统 |
| 单元化多活 | 单元内闭环，跨单元异步 | 秒级–0 | 0–秒级 | 最高 | 超大流量核心 |

> 🔑 多活的判据不是「机房数」，而是**切换后账务是否还能平**。所以切换方案里必须带数据校验步骤，见 [36.6 切换时的数据一致性](../../L3-质量属性/36-灾备/36.6-切换时的数据一致性.md) 的三种数据状态与 fencing 机制。

## RTO 是加出来的，不是标出来的

| 阶段 | 本机仿真取值 | 压缩手段 |
|---|---|---|
| 故障探测（心跳 3 次 × 5s） | 15s | 缩短心跳间隔，但要防误判 |
| 切换决策（值班 + 双人复核） | 60s | 预授权剧本，减少人工确认层级 |
| 流量切换（DNS TTL 30s + 网关生效） | 30s | 客户端支持动态地址，不依赖 DNS |
| 备库提升为主（改拓扑 + fencing） | 20s | 自动化剧本，fencing 由存储层执行 |
| 应用预热（连接池/缓存/热点） | 90s | 常驻热备、缓存预热脚本 |
| 切换后 5 项数据校验 | 150s | 并行校验，关键项优先 |

## 切换后 30 分钟：先跑 36.6 的 5 项，再补 3 项账务校验

[36.6 切换时的数据一致性](../../L3-质量属性/36-灾备/36.6-切换时的数据一致性.md) 的 5 项（行数 / checksum / 位点 / 补放 / 抽样）是通用清单，本节不重复；金融核心在其后再加 3 项账务专项：

| 账务专项校验 | 通过判据 | 不过怎么办 |
|---|---|---|
| 账务借贷平衡 | 借余合计 = 贷余合计，差异 0 | 立即停止接单，回切 |
| 总分核对 | 总账 = 明细合计 + 挂账，差额 0 | 差额挂账并定位 |
| 幂等键连续性 | 无重复键、无缺口 | 缺口查明来源，重复键拦截 |

> 若涉及跨行/对外支付，再补「未决交易可追踪」「对外流水号连续」两项，不放进通用 5 项。

## 本机可运行：审计哈希链 + RTO/RPO 估算

`go run main.go`（go1.27.1 darwin/arm64）。本机仿真：5 条操作记录建哈希链并校验、篡改第 3 条后验证断链、RTO 逐段累加、RPO 按「复制延迟 × 写入速率」估算。原始输出存 `.cache/domain-76/raw-76.5.txt`。

```go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"fmt"
)

type Audit struct {
	Seq                   int
	Actor, Action, Detail string
	Prev, Hash            string
}

func digest(prev, actor, action, detail string) string {
	h := sha256.Sum256([]byte(prev + "|" + actor + "|" + action + "|" + detail))
	return hex.EncodeToString(h[:])[:16]
}

func build(ops []Audit) []Audit {
	prev := "0000000000000000"
	for i := range ops {
		ops[i].Prev = prev
		ops[i].Hash = digest(prev, ops[i].Actor, ops[i].Action, ops[i].Detail)
		prev = ops[i].Hash
	}
	return ops
}

// verify 逐条重算：前序哈希断链或本条哈希不匹配，都判校验失败。
func verify(ops []Audit) (bool, int) {
	prev := "0000000000000000"
	for i := range ops {
		if ops[i].Prev != prev {
			return false, ops[i].Seq
		}
		if ops[i].Hash != digest(ops[i].Prev, ops[i].Actor, ops[i].Action, ops[i].Detail) {
			return false, ops[i].Seq
		}
		prev = ops[i].Hash
	}
	return true, 0
}

func main() {
	fmt.Println("== 1. 审计留痕：操作日志哈希链 ==")
	ops := build([]Audit{
		{Seq: 1, Actor: "ops-li", Action: "开户", Detail: "客户 C9001 开立 I 类户，证件已核验"},
		{Seq: 2, Actor: "ops-li", Action: "限额变更", Detail: "C9001 单笔限额 50000→20000，附审批单 SP-771"},
		{Seq: 3, Actor: "ops-wang", Action: "手工调账", Detail: "内部户 2002 转入 1000 元，双人复核：ops-zhao"},
		{Seq: 4, Actor: "ops-zhao", Action: "复核", Detail: "同意调账凭证 CZ-012，核对原始流水 P03"},
		{Seq: 5, Actor: "ops-li", Action: "导出", Detail: "导出 T 日流水 1200 条，用途：监管报送"},
	})
	for _, o := range ops {
		fmt.Printf("seq=%d %-8s %-8s hash=%s\n", o.Seq, o.Actor, o.Action, o.Hash)
	}
	if ok, at := verify(ops); ok {
		fmt.Println("校验结果：整链有效，未发现篡改")
	} else {
		fmt.Printf("校验结果：断链于 seq=%d\n", at)
	}

	// 篡改第 3 条的金额：后续所有 Prev 都对不上，无法局部伪造
	ops[2].Detail = "内部户 2002 转入 10000 元，双人复核：ops-zhao"
	if ok, at := verify(ops); !ok {
		fmt.Printf("篡改 seq=3 后校验：失败于 seq=%d（该条哈希不匹配，且后续 Prev 断链）\n", at)
	}
	fmt.Println("结论：要改一条历史记录，必须重算该条之后全部哈希；链尾哈希已对外报送，改不动。\n")

	fmt.Println("== 2. RTO 逐段估算（本机计算，单位为秒）==")
	type Step struct {
		Name string
		Sec  int
	}
	steps := []Step{
		{"故障探测（心跳 3 次 × 5s）", 15},
		{"切换决策（值班 + 双人复核）", 60},
		{"流量切换（DNS TTL 30s + 网关生效）", 30},
		{"备库提升为主（改复制拓扑 + fencing）", 20},
		{"应用预热（连接池/缓存/热点数据）", 90},
		{"切换后 5 项数据校验", 150},
	}
	cum := 0
	for _, s := range steps {
		cum += s.Sec
		fmt.Printf("%-38s %4ds  累计 %3d 秒\n", s.Name, s.Sec, cum)
	}
	fmt.Printf("本机估算 RTO = %d 秒 ≈ %.1f 分钟\n\n", cum, float64(cum)/60)

	fmt.Println("== 3. RPO 估算：丢多少笔 = 复制延迟 × 写入速率 ==")
	lagSec := 2.0
	tps := 1200.0
	for _, l := range []float64{0.2, 2.0, 30.0} {
		fmt.Printf("复制延迟 %5.1fs × %4.0f TPS → 最多丢 %6.0f 笔\n", l, tps, l*tps)
	}
	fmt.Printf("本次取值：延迟 %.1fs、写入 %.0f TPS → RPO ≈ %.0f 笔 ≈ %.0f 秒的写入量\n\n",
		lagSec, tps, lagSec*tps, lagSec)

	fmt.Println("== 4. 四种形态的 RTO / RPO（经验量级，需按实际演练校准）==")
	for _, s := range []struct {
		form, rto, rpo, cost string
	}{
		{"冷备（备份介质）", "小时级（4–8h）", "小时级（丢最后一次备份后的全部写入）", "1x"},
		{"温备（备机常驻不接流）", "10–40min", "分钟级（异步复制延迟）", "1.5–2x"},
		{"热备（同城，可接流）", "1–5min", "秒级（同步/半同步复制）", "2–3x"},
		{"两地三中心 / 双活", "秒级–0", "0–秒级（按复制模式定）", "4x 以上"},
	} {
		fmt.Printf("%-24s RTO %-14s RPO %-36s 成本 %s\n", s.form, s.rto, s.rpo, s.cost)
	}

	fmt.Println("\n== 5. 回切（切回来）的代价 ==")
	for _, s := range []struct {
		item string
		sec  int
	}{
		{"确认原主库数据已补齐（追平新增写入）", 300},
		{"回切流量（灰度 1%→10%→100%）", 180},
		{"回切后双跑校验", 120},
	} {
		fmt.Printf("%-36s %4ds\n", s.item, s.sec)
	}
	fmt.Println("回切总耗时 ≥ 10 分钟：切换方案必须把回切成本一起写进预案。")
}
```

## 反模式

| 反模式 | 后果 |
|---|---|
| 审计日志与业务库同库同权限 | 内部人可删改，审计形同虚设 |
| 只记「已修改」不记前后值 | 无法证明改成了什么，也无法回放 |
| 单时间戳（只有记录时间） | 无法还原业务发生顺序，差错分析断链 |
| 多活没有流量切换与回切预案 | 切换时靠人现场指挥，RTO 不可控 |
| RPO 承诺 0 但用的是异步复制 | 切换必然丢数据，承诺无法兑现 |
| 切换后不做数据校验就放流量 | 丢单、重单、账不平在几小时后爆发 |
| 灾备环境长期不演练、不校验备份可恢复性 | 备份不可用，切换时才发现 |

## 自检

**Q1** 为什么审计日志要串成哈希链，而不是每条单独存哈希？

▸ 答案：单条哈希只能防「改这一条」，攻击者可以改内容并重算该条哈希。串链后每条都绑定前一条哈希，改任意一条都会让后续所有条目的 Prev 对不上；再加上链尾摘要定期外送或上链，就无法在不被发现的前提下重算整条链。

**Q2** RTO 6 分钟是怎么来的？为什么不能只看标称值？

▸ 答案：RTO 是各阶段耗时之和：探测 15s + 决策 60s + 流量切换 30s + 备库提升 20s + 预热 90s + 校验 150s = 365s。标称值通常只算「切换动作本身」，漏掉探测、决策与校验；不演练时这些段的真实耗时无人知道，所以承诺的 RTO 常常翻倍。

**Q3** RPO 为 0 的代价是什么？金融核心该怎么选？

▸ 答案：RPO = 0 要求同步复制，写请求必须等备库确认，代价是写延迟上升（跨机房多 1 个 RTT）与可用性下降（备库不可用时可能写不进去）。选择方式是按业务分级：账务与支付核心用同城半同步（RPO 秒级），内部管理类用异步（RPO 分钟级），不追求全系统 RPO=0。

**Q4** 切换后为什么必须校验「幂等键连续性」？

▸ 答案：切换瞬间可能有请求在旧主已提交、在新主未感知，也可能有请求重试。校验幂等键能同时发现两类问题：重复键（重单，会重复扣款）与缺口（丢单，会漏记）。这两类问题在账务上表现为长款/短款，几小时后才会在对账中暴露。

**Q5** 为什么说「不演练的灾备等于没有灾备」？

▸ 答案：灾备的所有指标（RTO、RPO、回切耗时、校验通过率）都依赖真实执行。演练能暴露三类问题：预案缺失步骤、依赖项没配（DNS、证书、白名单）、数据校验脚本本身有 bug。这些问题在真实故障时没有第二次机会验证。
