# 76.2 交易与清结算

## 一句话

> 交易是「双方达成合意」，清算是「算清谁欠谁多少」，结算是「真把钱挪过去」；三段失败处理完全不同——**交易可撤销、清算可重跑、结算不可逆**。把三段压成一个同步调用，是资金类系统最贵的架构错误。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 交易成功 = 钱到账 | 交易只表示受理；到账要等清算轧差加结算划拨，跨行通常 T+1 才最终确定 |
| 清算和结算是一回事 | 清算只算净额、不动钱，错了可以重算；结算动钱，错了只能冲正 |
| 净额结算更省事，所以一定更好 | 净额把信用风险集中到清算机构：一家违约，全体成员按规则分摊 |
| 全额实时结算最安全 | 安全但流动性成本最高：每笔都要备足头寸，大额支付系统靠排队与日间透支周转 |

## 三段拆开看：谁在做、失败怎么办

| 环节 | 谁在做 | 动作 | 时点 | 失败后果 | 可逆性 |
|---|---|---|---|---|---|
| 交易 | 渠道 + 交易系统 | 受理、落单、扣减可用额度 | 实时 | 用户可重试（须幂等） | 可撤销（未进清算前） |
| 清算 | 清算机构 / 平台清算系统 | 明细汇总、轧差、产出净额与清算文件 | T 日终 | 可重跑、可重算 | 可重算 |
| 结算 | 结算行 / 央行大额支付系统 | 资金划拨、回单落地 | T+1 窗口 | 排队、退回、需人工干预 | 不可逆，只能冲正 |
| 对账 | 账务 + 清算 | 明细比对、差异闭环 | T+1 | 差异挂账 | 靠补账/冲正解决 |

> 🔑 三段的**幂等键不同**：交易用订单号、清算用清算批次号、结算用支付指令号。用同一个键贯穿三段，会让「清算重跑」看起来像「重复结算」。

## 净额 vs 全额：省的是流动性，押的是信用

| 维度 | 逐笔全额 | 双边轧差 | 多边净额 |
|---|---|---|---|
| 资金划拨笔数 | N（= 交易笔数） | ≤ N（同一对机构合并） | ≤ 成员数 + 1 |
| 流动性占用 | 最高 | 中 | 最低 |
| 信用风险 | 分散在各对手方 | 分散在各对手方 | 集中到清算机构 |
| 实现复杂度 | 最低 | 中 | 最高（成员管理、保证金、违约处置） |
| 适用场景 | 大额实时支付 | 双边有来有往的同业业务 | 零售支付批量清算 |

净额结算不是「免费的午餐」，它有三个硬前提：

| 前提 | 作用 | 缺了会怎样 |
|---|---|---|
| 成员准入与授信 | 只让有资质的机构进净额圈 | 一家空壳机构违约，全体分摊损失 |
| 保证金 / 清算基金 | 违约时先垫付 | 违约直接击穿清算机构 |
| 违约瀑布规则 | 明确「先扣谁的保证金、再按什么比例分摊」 | 出事后靠临时谈判，结算窗口直接错过 |

## 手续费：必须在清算文件里带下来

计费规则（本机仿真取万六、四舍五入到分、付款方承担）一旦分散到「清算系统算一遍、账务系统再算一遍」，两边必然差一分钱，然后天天出差异。做法只有一条：**清算文件是手续费的唯一事实源**，账务按文件入账。

| 项 | 本机仿真取值 | 说明 |
|---|---|---|
| 费率 | 6 / 10000（万六） | 零售支付常见量级，实际以商务合同为准 |
| 取整 | 四舍五入到分 | 必须是确定性规则，不能浮点截断 |
| 承担方 | 付款方 | 决定净额方向：付款方付出本金 + 手续费 |
| 清算机构 | 单独一个净额成员 | 让 Σ 净额 = 0 可校验 |

## 本机可运行：多边净额与头寸检查

`go run main.go`（go1.27.1 darwin/arm64）。本机仿真 4 家机构、10 笔跨行交易，算双边轧差、多边净额、划拨笔数对比与结算前头寸检查。原始输出存 `.cache/domain-76/raw-76.2.txt`。

```go
package main

import (
	"fmt"
	"sort"
)

type Txn struct {
	ID           string
	Payer, Payee string
	Amt          int64 // 分
}

// fee 按万六计费、四舍五入到分，由付款方承担。
func fee(amt int64) int64 { return (amt*6 + 5000) / 10000 }

func yuan(v int64) string { return fmt.Sprintf("%.2f", float64(v)/100) }

func main() {
	txns := []Txn{
		{"T01", "A", "B", 12345},
		{"T02", "B", "C", 80000},
		{"T03", "C", "A", 250000},
		{"T04", "D", "A", 66666},
		{"T05", "A", "D", 999},
		{"T06", "B", "A", 1500000},
		{"T07", "C", "D", 43210},
		{"T08", "D", "B", 70000},
		{"T09", "A", "C", 550000},
		{"T10", "B", "D", 100},
	}

	fmt.Println("== 1. 交易明细（T 日受理，金额以元计）==")
	var totalAmt, totalFee int64
	for _, t := range txns {
		f := fee(t.Amt)
		totalAmt += t.Amt
		totalFee += f
		fmt.Printf("%s %s→%s 金额 %10s 手续费 %6s\n", t.ID, t.Payer, t.Payee, yuan(t.Amt), yuan(f))
	}
	fmt.Printf("合计：交易 %d 笔、金额 %s 元、手续费 %s 元\n\n", len(txns), yuan(totalAmt), yuan(totalFee))

	// 双边轧差：同一对机构之间方向相反的交易先对冲
	pair := map[string]int64{}
	for _, t := range txns {
		pair[t.Payer+">"+t.Payee] += t.Amt
	}
	keys := make([]string, 0, len(pair))
	for k := range pair {
		keys = append(keys, k)
	}
	sort.Strings(keys)
	fmt.Println("== 2. 双边轧差（同一对机构合并）==")
	seen := map[string]bool{}
	var bilateralAmt int64
	bilateralCnt := 0
	for _, k := range keys {
		var a, b string
		for i := 0; i < len(k); i++ {
			if k[i] == '>' {
				a, b = k[:i], k[i+1:]
			}
		}
		fwd, rev := a+">"+b, b+">"+a
		if seen[fwd] || seen[rev] {
			continue
		}
		seen[fwd], seen[rev] = true, true
		netv := pair[fwd] - pair[rev]
		if netv == 0 {
			fmt.Printf("%s↔%s 完全对冲，净额 0.00\n", a, b)
			continue
		}
		from, to := a, b
		if netv < 0 {
			netv, from, to = -netv, b, a
		}
		bilateralAmt += netv
		bilateralCnt++
		fmt.Printf("%s→%s 净额 %s\n", from, to, yuan(netv))
	}
	fmt.Printf("双边轧差：%d 笔划拨，合计 %s 元\n\n", bilateralCnt, yuan(bilateralAmt))

	// 多边轧差：每个成员对全体轧出一个净额，含手续费
	net := map[string]int64{}
	for _, t := range txns {
		f := fee(t.Amt)
		net[t.Payer] -= t.Amt + f // 付款方：付出本金 + 手续费
		net[t.Payee] += t.Amt     // 收款方：收到本金
		net["CC"] += f            // 清算机构：收手续费
	}
	members := []string{"A", "B", "C", "D", "CC"}
	fmt.Println("== 3. 多边净额（含手续费；正 = 应收，负 = 应付）==")
	var sum, multiAmt int64
	multiCnt := 0
	for _, m := range members {
		sum += net[m]
		if net[m] != 0 {
			multiCnt++
		}
		if net[m] < 0 {
			multiAmt -= net[m]
		}
		fmt.Printf("%-3s 净额 %12s 元\n", m, yuan(net[m]))
	}
	fmt.Printf("Σ净额 = %d（清算守恒，必须为 0）\n", sum)
	fmt.Printf("多边净额：%d 笔划拨，应付合计 %s 元\n\n", multiCnt, yuan(multiAmt))

	fmt.Println("== 4. 划拨笔数对比（净额结算的价值）==")
	fmt.Printf("逐笔全额  %2d 笔，资金流 %s 元\n", len(txns), yuan(totalAmt+totalFee))
	fmt.Printf("双边轧差  %2d 笔，资金流 %s 元\n", bilateralCnt, yuan(bilateralAmt))
	fmt.Printf("多边净额  %2d 笔，资金流 %s 元\n\n", multiCnt, yuan(multiAmt))

	// 头寸检查：净付方在结算窗口开盘前必须有足额头寸
	pos := map[string]int64{"A": 800000, "B": 300000, "C": 2000000, "D": 100000}
	fmt.Println("== 5. 结算前头寸检查（净付方）==")
	for _, m := range []string{"A", "B", "C", "D"} {
		if net[m] >= 0 {
			continue
		}
		need := -net[m]
		mark := "✓ 足额"
		if pos[m] < need {
			mark = "✗ 头寸不足，排队至下一窗口"
		}
		fmt.Printf("%s 需付 %12s 头寸 %12s %s\n", m, yuan(need), yuan(pos[m]), mark)
	}

	fmt.Println("\n== 6. 清算结算时间线 ==")
	type step struct{ at, what string }
	for _, s := range []step{
		{"T 日 20:00", "交易截单，渠道停止受理当日新单"},
		{"T 日 20:30", "生成清算文件，逐笔明细落库"},
		{"T 日 21:00", "多边轧差，产出各成员净额与净额确认书"},
		{"T 日 23:00", "净额确认书回执，成员确认应收应付"},
		{"T+1 09:00", "结算窗口开盘，头寸不足的成员排队"},
		{"T+1 09:30", "资金划拨指令发出（大额支付系统，报文以官方文档为准）"},
		{"T+1 10:00", "结算完成，回单落地；账务侧记账"},
		{"T+1 11:00", "总分核对 + 渠道对账"},
	} {
		fmt.Printf("%-10s %s\n", s.at, s.what)
	}
}
```

## 清算结算时序：T 日算账，T+1 动钱

| 时点 | 动作 | 判据 |
|---|---|---|
| T 日 20:00 | 交易截单 | 之后的交易落 T+1 |
| T 日 20:30 | 生成清算文件（逐笔明细） | 文件条数 = 当日受理笔数 |
| T 日 21:00 | 轧差产出净额与净额确认书 | Σ 净额 = 0 |
| T 日 23:00 | 成员回执确认 | 全部成员确认或有争议挂起 |
| T+1 09:00 | 结算窗口开盘，头寸检查 | 净付方头寸充足才能划拨 |
| T+1 09:30 | 资金划拨（大额支付系统报文，以官方文档为准） | 划拨指令号唯一且连续 |
| T+1 10:00 | 回单落地、账务记账 | 凭证与回单逐笔对应 |
| T+1 11:00 | 总分核对 + 渠道对账 | 差异进入差错处理 |

> ⚠️ 节假日日历是清结算最容易漏的配置：T+1 遇假日顺延，若系统按自然日推算，账期会整体错位一天，且错位会沿着「计息、报表、报送」一路传导。

## 反模式

| 反模式 | 后果 |
|---|---|
| 把清算与结算写成一次同步调用 | 结算失败无法回滚，清算文件与账务直接不一致 |
| 净额结算不做头寸检查 | 净付方无钱可付，结算窗口排队，连锁延误 |
| 手续费在清算与账务各算一遍 | 天天差一分钱，差异池被垃圾数据淹没 |
| 净额文件只放临时文件、不落库 | 无法重跑、无法举证、出事查不到原始明细 |
| 忽略节假日日历 | T+1 顺延错位，计息与报送全错 |
| 清算批次无幂等键 | 重跑重复划拨，直接资损 |
| 只记台账不核对清算文件 | 长款短款在月底集中爆发，处理成本翻十倍 |

## 自检

**Q1** 用户看到「交易成功」但钱没到账，问题最可能在哪一段？

▸ 答案：在清算或结算段。交易段只表示受理成功；若清算未截单（跨日）、轧差后净额未确认，或结算窗口头寸不足导致划拨排队，都会出现「状态成功、资金未到」。排查顺序是：交易流水 → 清算文件是否包含该笔 → 结算指令是否发出 → 回单是否落地。

**Q2** 净额结算省了什么？又把什么风险集中了？

▸ 答案：省的是流动性占用与资金划拨笔数（本机仿真：10 笔全额 25748.64 元压到 5 笔 15911.42 元）。集中起来的是信用风险：原本「各自对手方各自承担」，变成「清算机构先垫、全体成员按违约瀑布分摊」。所以净额必须配成员准入、保证金与违约处置规则。

**Q3** 为什么清算可以重跑，结算不可以？

▸ 答案：清算只是计算，产出净额文件，重跑的结果与上次一致（幂等），不改任何人的钱；结算已经真实划拨资金，重跑就是重复付款，只能靠幂等的支付指令号挡住、靠冲正纠正。这也解释了为什么结算指令必须带唯一号并落库。

**Q4** 手续费为什么必须由清算文件带下来？

▸ 答案：手续费参与净额计算，一旦清算与账务各自计算，取整规则或费率版本稍有差异就会产生分差，形成永久性小额差异。让清算文件成为唯一事实源，账务只做入账，才能保证「清算净额 = 账务余额变动」。

**Q5** 净付方头寸不足时，系统应该做什么？

▸ 答案：进入排队而不是直接失败：先尝试日间流动性工具（质押融资、日间透支，以官方文档为准），排队至下一结算窗口；同时告警并通知资金调度。若到日终仍不足，按违约处理流程走保证金垫付与损失分摊，绝不允许「先划了再说」。
