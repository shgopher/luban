                            41.10 Redis 可靠性与高可用：数据不丢的边界

                            一句话

                            Redis 的「不丢」不是某个开关，而是三道闸的乘积——fsync 时机 × 复制确认 × 故障判定；任何一道闸松了，前面配得再紧都白搭，而三道闸同时拧紧的代价是吞吐掉一个数量级。

                            一次写入要过几道闸

                            环节 默认行为 丢数据窗口 拧紧的代价
                            执行命令、写 AOF 缓冲 内存 进程崩溃即丢 无
                            fsync 到磁盘 appendfsync everysec ≤ 1 秒 always 让吞吐掉 34 倍
                            传到从库 异步复制 网络/从库慢的全部时间 同步等待 = 直接加延迟
                            从库确认（ack） 每秒一次 — —
                            故障判定与切换 哨兵 30 秒 判定期间的双写风险 判太快误切，判太慢停服

                            🔑 顺序搞反是最常见的错误：单机 fsync 再狠，机器没了照样丢；先有多副本与正确的故障判定，再谈 fsync。

                            RDB / AOF / 混合：三选一的真实代价

                            维度 RDB 快照 AOF 日志 混合（RDB + AOF）
                            记录的是 某一时刻的数据 每条写命令 快照打底 + 之后的命令
                            丢数据窗口 两次快照之间（按默认 save 最坏 1 小时） always≈0；everysec≤1s；no 由 OS 决定 接近 everysec
                            恢复方式 直接读文件进内存 逐条重放命令 先载 base 再回放增量
                            主线程影响 bgsave 不阻塞，但 fork 瞬间阻塞 刷盘在主线程；重写要 fork fork 频率大降
                            触发命令 BGSAVE BGREWRITEAOF aof-use-rdb-preamble yes（默认）

                            本机实测（Redis 8.10.2，63,251 个 key）：

                            项 RDB 纯命令 AOF 混合
                            文件体积 1,391,620 B 2,846,318 B（2.05×） 1.39 MB + 增量
                            启动加载 0.042 s 0.092 s（2.2×） ≈ RDB

                            读数是本节最反直觉的一点：AOF 体积约为 RDB 的 2 倍、加载慢约 2 倍。所以「AOF 更安全，就全上 AOF」要付双倍的恢复时间——大实例上这意味着几分钟的启动窗口。混合持久化的意义正在于此：用 RDB 的体积换恢复速度，用 AOF 补齐快照之后的秒级窗口。

                            AOF 三档：34 倍的差距

                            档位 丢数据窗口 本机 SET 吞吐 p50
                            always ≈ 0（每条命令等落盘） 2,507 rps 7.92 ms
                            everysec 上一秒内未落盘的命令 85,470 rps 0.175 ms
                            no 由操作系统决定，无上限 85,470 rps 0.175 ms
                            $ redis-benchmark -p 6402 -n 10000 -c 20 -t set -q   # appendfsync always
SET: 2507.52 requests per second, p50=7.919 msec

$ redis-benchmark -p 6403 -n 10000 -c 20 -t set -q   # appendfsync everysec
SET: 85470.09 requests per second, p50=0.175 msec

                            ⚠️ 这是 macOS/APFS 上的读数，单次 fsync 约 8ms；Linux 上通常 0.1–1ms，倍数会小一些，但「always 比 everysec 慢一个数量级」这个结论成立。everysec 与 no 的吞吐一样，是因为两者的命令路径完全相同，区别只在后台每秒 fsync 一次、还是完全交给 OS。

                            AOF 重写：主线程为什么不卡，7.0 又改了什么

                            重写的做法是读当前数据、按最新状态为每个键生成一条写命令，而不是回放历史命令（一个被 LPUSH 六次的 list 只需一条 LPUSH 三条元素）。整个过程不阻塞主线程，靠三件事：

                            1. fork 子进程做重写，子进程只读；
                            2. 双写：重写期间的新命令同时写「旧 AOF 缓冲」（保证宕机可恢复）和「重写缓冲」（保证新文件不丢最近写入）；
                            3. 写时复制（COW）：fork 拷贝的是页表而不是物理内存，主线程改哪页才复制哪页。
                            # 本机实测：触发重写并观察耗时与体积
redis-cli -p 6405 bgrewriteaof
redis-cli -p 6405 info persistence | grep -E "aof_rewrite_time|aof_base_size|aof_current_size"

                            7.0 起 AOF 从「单文件 + 重写替换」改成了多文件 + manifest：

                            appendonlydir/
├── appendonly.aof.1.base.rdb     # 基线：RDB 格式（aof-use-rdb-preamble yes）
├── appendonly.aof.1.incr.aof     # 增量：命令格式
└── appendonly.aof.manifest       # 清单：谁排第几、谁是 base、谁是 incr

                            file appendonly.aof.1.base.rdb seq 1 type b
file appendonly.aof.1.incr.aof seq 1 type i startoffset 0

                            推论：「AOF 就是一个大文件」这句老话已经不成立。备份脚本按 appendonly.aof 找文件会扑空；aof-use-rdb-preamble no 才能得到纯命令格式的 base（本机实测此时体积从 1.39MB 变成 2.85MB）。

                            主从复制：一次全量，之后靠环形缓冲

                            阶段 做什么 谁可能被拖住
                            ① 握手 从库 PSYNC ? -1，主库回 FULLRESYNC <runID> <offset> —
                            ② 传 RDB 主库 bgsave 生成快照发给从库（7.0 起默认 diskless 直传 socket） 主库 fork 瞬间
                            ③ 补增量 快照期间的新写从 replication buffer 补发，从库重放 从库加载期间不可读
                            断连重连 从 repl_backlog_buffer 增量续传，未读部分被覆盖则退回全量 主库 fork + 带宽

                            本机实测增量续传（从库重启后）：

                            # 主库日志
Partial resynchronization request from 127.0.0.1:6411 accepted.
Sending 0 bytes of backlog starting from offset 5400024.

# 从库日志
Successful partial resynchronization with master.

                            两个缓冲不能混：

                            缓冲 位置 作用 满了会怎样
                            replication buffer 主库，每个从库一份 全量传输期间新命令的待发队列 超 client-output-buffer-limit replica → 断开该从库
                            repl_backlog_buffer 主库，全局一份环形 断连期间的命令历史 覆盖未读部分 → 该从库只能全量重同步

                            repl-backlog-size 默认只有 1MB（本机实测 1048576），这是生产上最常见的「不明原因全量同步」来源。估算公式：(主库写入速率 − 网络传输速率) × 单条命令大小 × 2。例：写入 2000 ops/s、每条约 2KB，而主从网络只能传 1000 ops/s → 每秒净积压 2MB → repl-backlog-size 至少 4MB。

                            复制风暴与主从延迟

                            • 复制风暴：多个从库同时发起全量同步 → 主库反复 fork、带宽被 RDB 占满。解法是「主-从-从」级联：把约三分之一的从库挂到某个从库下，把一次全量变成多层。
                            • 延迟：复制是异步的，从库永远落后。本机实测：让从库 CLIENT PAUSE 3000 暂停，主库持续写入，主库视角的 offset 差涨到 1,350,000 字节（lag=1s），恢复后归零。
                            redis-cli -p 6410 info replication | grep slave0   # 看 offset 与 lag
                            • 从库的过期 key：从库不主动删过期键。3.2 之后从库遇到已过期 key 返回空值，但键仍占内存；3.2 之前会直接返回过期数据。更隐蔽的是 EXPIRE 的语义——它在从库重放时按「从库当前时间 + TTL」计算，若全量同步花了 2 分钟，EXPIRE testkey 60 在从库上的过期时刻就整体后移 2 分钟。

                            哨兵：判活、投票、选主

                            步骤 规则 失败模式
                            主观下线 单个哨兵 PING 超 down-after-milliseconds（默认 30s） 网络抖动即误判
                            客观下线 向其他哨兵拉票，达到 quorum（N/2+1） quorum 太大 → 永远切不了
                            选 Leader 多数票 且 ≥ quorum 5 个哨兵挂 3 个：判得出、切不了
                            选新主 在线 → replica-priority 最高 → offset 最接近旧主 → runID 最小 优先级压过复制进度 → 切过去丢数据
                            • 哨兵之间不需要互相配置：它们往主库的 __sentinel__:hello 频道发布自身地址、同时订阅该频道，先有主库后有「哨兵网」。
                            • 只要 2 个哨兵就等于没有高可用：挂掉一个就凑不齐 2 票，客观下线永远成立不了。起步 3 个，quorum 2。
                            • 哨兵只负责告知新主库地址，不代理请求；客户端必须自己订阅 switch-master 或走支持哨兵的客户端，否则会一直连旧主库。

                            脑裂：四步丢数据

                            ① 假故障：主库所在机器 CPU 被打满（同机采集程序），心跳超时
② 并行写：哨兵开始切换的同时，主库恢复响应，客户端仍在往「旧主库」写
③ 降级：新主选出，哨兵让旧主 REPLICAOF 新主
④ 抹掉：全量同步先清空旧主数据、再加载新主 RDB —— ② 期间写入的 key 永久消失

                            为什么监控看不出来：切换完成后，新旧主库的 master_repl_offset / slave_repl_offset 是一致的，差值监控显示「同步正常」。这也解释了为什么这类事故只能靠客户端操作日志和 CPU 监控反推。

                            防护是让「卡住的主库」自己拒绝写入：

                            # 本机实测：从库在线时能写，从库下线后主库立刻拒写
$ redis-cli -p 6406 config set min-replicas-to-write 1
$ redis-cli -p 6406 set probe 1
OK
$ redis-cli -p 6407 shutdown nosave       # 从库下线
$ redis-cli -p 6406 set probe 2
(error) NOREPLICAS Not enough good replicas to write.
                            参数 含义 本机默认 建议
                            min-replicas-to-write 至少 N 个从库在线才接受写 0（等于不设防） K 个从库 → K/2+1
                            min-replicas-max-lag 从库 ack 延迟上限（秒） 10 10–20
                            down-after-milliseconds 哨兵判活超时 30000 与上面配合：切主完成前旧主已禁写

                            落地：一套可抄的最小可靠配置

                            # 指名 + 可抄：单机「不丢到秒级 + 防脑裂」的最小配置
redis-server --port 6410 \
  --appendonly yes --appendfsync everysec \
  --aof-use-rdb-preamble yes \
  --repl-backlog-size 64mb \
  --min-replicas-to-write 1 --min-replicas-max-lag 10 \
  --save '3600 1' --dir /tmp/redis-lab --daemonize yes

                            可验（三条都要绿）：

                            redis-cli -p 6410 info persistence | grep -E "aof_enabled|aof_last_bgrewrite_status|aof_last_write_status"
redis-cli -p 6410 info replication | grep -E "role|connected_slaves|master_repl_offset"
redis-cli -p 6410 config get min-replicas-to-write
                            判据 成功输出 失败时看什么
                            AOF 生效 aof_enabled:1、aof_last_write_status:ok 磁盘满、appendonly 未开、appenddirname 权限
                            防脑裂生效 min-replicas-to-write 为 1（或 K/2+1） 设了但从库数不够 → 主库直接拒写，需要先补从库
                            积压够用 repl_backlog_histlen 远小于 repl_backlog_size 接近上限说明断连即全量，调大 repl-backlog-size

                            可退（不重启）：

                            redis-cli -p 6410 config set min-replicas-to-write 0   # 先解除写保护
redis-cli -p 6410 config set appendonly no            # 保留 AOF 文件，停止追加

                            反模式

                            反模式 后果
                            「开了 RDB 就算有持久化」 两次快照之间的写入全丢，最坏 1 小时
                            appendfsync always 上生产 吞吐从 8.5 万掉到 2,500 rps（本机 34 倍）
                            用 AOF 做全量同步 AOF 是操作流、体积约 RDB 的 2 倍，传输与重放都更慢
                            repl-backlog-size 保持默认 1MB 从库一断就退化成全量同步，主库被 fork 拖住
                            多从库同时全量重建 复制风暴：带宽与 fork 双重打满
                            只部署 2 个哨兵 挂一个就永远切不了，高可用形同虚设
                            min-replicas-to-write 留 0 脑裂时旧主库照收写入，切换后全部丢失
                            把从库当「实时一致」读 异步复制窗口内读到旧值，业务据此决策会错
                            单实例 25GB 还依赖 RDB fork 阻塞接近秒级，切换与快照都变成事故

                            自检

                            Q1 everysec 为什么最多只丢 1 秒，而 always 却要慢 34 倍？

                            ▸ 答案：everysec 把命令写进 AOF 缓冲就返回，由后台每秒 fsync 一次，所以丢的是「最近一秒未落盘」的命令；命令路径上不碰磁盘，吞吐与 no 相同（本机都是 85,470 rps）。always 每条写命令都等一次 fsync 落盘才算完成，单次 fsync 在本机 APFS 上约 8ms，于是 p50 从 0.175ms 涨到 7.92ms、吞吐掉到 2,507 rps。两者差的不是「写日志」而是「等落盘」。

                            Q2 AOF 比 RDB 大 2 倍、加载慢 2 倍，为什么还要开 AOF？

                            ▸ 答案：因为两者防的是不同的丢失窗口。RDB 只保证「快照时刻」之前的数据，两次快照之间（默认最坏 1 小时）的写入全丢；AOF 按命令追加，everysec 只丢 1 秒。所以正确组合是混合持久化：用 RDB 做 base 拿到恢复速度（本机 0.042s vs 0.092s），用 AOF 增量兜住秒级窗口。只上纯 AOF 会让大实例的启动时间翻倍。

                            Q3 fork 拷贝的是物理内存还是页表？这对容量规划意味着什么？

                            ▸ 答案：拷的是页表（虚拟地址映射），物理页靠写时复制才分离。所以「fork 需要 2 倍内存」是错的——但写多的实例会逼近 2 倍：主线程每改一页就复制一页，快照期间写入量越大，额外内存越多。容量规划要看「快照期间写入量」而不是「数据总量」，并观察 latest_fork_usec。

                            Q4 repl-backlog-size 太小会发生什么？怎么估？

                            ▸ 答案：从库断连期间，主库产生的命令写进这个环形缓冲；若从库回来时它的 offset 已被覆盖，就只能退回全量同步——主库 fork、带宽被 RDB 占满、从库长时间不可读。估算：(主库写入速率 − 网络传输速率) × 单条命令大小 × 2，再按断连时长留余量；默认 1MB 只够很轻的写入。

                            Q5 5 个哨兵挂了 3 个，主库真挂了会怎样？

                            ▸ 答案：大概率判得出、但切不了。5 个哨兵通常配 quorum=3：挂掉 3 个只剩 2 个，连客观下线所需的 3 票都凑不齐，会停在「主观下线」，什么都不发生。即使把 quorum 调到 2、侥幸判出客观下线，选 Leader 还需要「多数票（≥3）且 ≥ quorum」，2 个哨兵永远选不出 Leader，故障转移仍然不会执行。所以哨兵数量要按「能容忍挂几个」倒推：3 个容忍 1 个，5 个容忍 2 个。

                            Q6 脑裂丢了的数据，为什么 offset 监控查不出来？min-replicas-to-write 为什么能拦住？

                            ▸ 答案：因为丢的数据是在「旧主库已恢复、新主已选出、但旧主还没被降级」这段窗口写进旧主库的；切换完成后旧主被全量同步覆盖，两边 offset 已经一致，差值监控显示正常。min-replicas-to-write 从「从库确认」反向定义主库可用性：假故障期间旧主收不到从库 ack，达不到 N 或超过 lag，于是自己拒绝客户端写入——窗口被从源头关掉。

                            Q7 主从延迟 1 秒，业务读从库会出什么问题？工程上怎么兜底？

                            ▸ 答案：会读到 1 秒前的旧值（写后立即读从库读不到自己的写），典型症状是「下单成功但订单列表没有」。兜底三板斧：① 写后短窗口内强制读主库（会话粘滞/「读己之写」）；② 用 INFO replication 的 offset 差做监控，超过阈值就把该从库摘出读池，追上再放回（阈值要留足，否则可能把所有从库都摘掉）；③ 对一致性敏感的读直接走主库，把从库只用于可容忍陈旧的查询。
