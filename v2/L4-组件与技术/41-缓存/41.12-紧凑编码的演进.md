# 41.12 紧凑编码的演进：ziplist → quicklist → listpack

## 一句话

> 省内存的紧凑编码，代价一定从“可更新性”里扣：ziplist 把**前一项的长度**写进每个元素，插入一个大元素就可能触发**连锁更新**（逐项变长、逐项 realloc）。Redis 的两次修正给出一条通用判据——**元数据只能依赖自己，不能依赖邻居**；扛不住时先分段，再自描述。

**来源**：ziplist 的 prevlen 编码与连锁更新、quicklist 的分段设计、listpack 的“只记自身长度”来自蒋德钧《Redis 源码剖析与实战》第 6 讲；边界敏感性实验与通用判据为本节补充。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “紧凑编码只是省内存” | 它同时改变了更新复杂度。省下的字节，是从“可更新性”里借的 |
| “连锁更新是‘插入大元素’导致的” | 真正条件是**原有元素长度贴着编码边界**：元素 100 字节时连锁第一项就断；元素 250 字节时 1000 项全部受影响 |
| “quicklist 是更好的 ziplist” | 它是**链表 + 分段 ziplist**：把连锁关进一个节点，不是消灭它 |
| “listpack 只是换个名字” | 它把 prevlen 换成“自己的长度”，从根上断掉连锁；代价是编码更复杂、反向遍历要另设计 |

## 两种老路的代价

| 结构 | 内存 | 查找 | 插入 | 代表 |
|---|---|---|---|---|
| **连续紧凑**（数组式） | 省：无指针、缓存友好 | O(n) 顺序扫描 | O(n) memmove，可能整块 realloc | ziplist |
| **链表** | 贵：每节点两个指针（64 位下 16 字节） | O(n) | O(1) | 纯链表 |

列表类数据在 Redis 里量很大，所以先选了“省内存”的连续紧凑布局——代价随之而来：**没有指针，就只能靠“记录长度”来定位下一个元素**，而这个长度信息写在了“邻居”身上。

## 连锁更新：三步看清

1. 一个 ziplist entry = `prevlen`（前一项总长）+ `encoding` + `data`；`prevlen` 的编码：≤ 253 字节用 **1 字节**，否则用 **5 字节**。
2. 在表头插入一个 300 字节元素 → 第一个 entry 的 `prevlen` 从 1 字节变 5 字节 → 这个 entry 变长 4 字节。
3. 如果它因此越过 253 → 第二个 entry 的 `prevlen` 也从 1 变 5 → 再变长 4 字节 → 第三个……**最坏情况下 N 个 entry 逐个变长、逐个 realloc**。

这就是“连锁更新”：一次插入，引发一场全局重排。

## 可运行：边界到底在哪

```python
#!/usr/bin/env python3
"""compact.py —— 按编码规则模拟「紧凑列表」插入的代价：ziplist 的连锁更新 vs listpack 的自描述。

规则（Redis 的编码约束）：
  ziplist   每个 entry = prevlen（前一项总长 ≤253 用 1 字节，否则 5 字节）+ encoding + data
            在表头插入一个大元素，后继 entry 的 prevlen 可能从 1 字节变 5 字节，自身变长；
            变长后的 entry 又可能把「下一个 entry 的 prevlen」顶过 253 → 一路连锁
  listpack  每个 entry = encoding + data + 自身长度，不依赖邻居 → 插入只改自己
"""
N = 1000            # 原有元素个数
BIG = 300           # 插入元素的总长度（>253）

def prevlen_size(prev_total):
    return 1 if prev_total <= 253 else 5

def ziplist_chain(entry_size, n=N, big=BIG):
    """返回 (受影响 entry 数, 额外字节, realloc 次数)。"""
    affected = extra = 0
    prev = big                      # 新插入元素的长度，成为第一个 entry 的「前一项」
    for _ in range(n):
        delta = prevlen_size(prev) - prevlen_size(entry_size)   # 原来前一项都是 entry_size
        if delta > 0:
            affected += 1
            extra += delta
        prev = entry_size + max(delta, 0)
    return affected, extra, affected

print(f"在 {N} 个元素的最前面插入一个 {BIG} 字节元素：\n")
print(f"{'元素原长':>8}{'ziplist 受影响':>16}{'额外字节':>10}{'listpack 受影响':>18}")
for size in (100, 240, 250, 253):
    a, e, _ = ziplist_chain(size)
    print(f"{size:>8}{a:>16}{e:>10}{0:>18}")
```

**本机实测输出**（Python 3.14.8）：

```text
在 1000 个元素的最前面插入一个 300 字节元素：

    元素原长     ziplist 受影响      额外字节      listpack 受影响
     100               1         4                 0
     240               1         4                 0
     250            1000      4000                 0
     253            1000      4000                 0
```

三条读法：

1. **100 与 240 都只影响 1 个 entry**：变长后的元素是 104 / 244 字节，仍 ≤ 253，下一项不需要改编码，连锁当场断掉。
2. **250 与 253 全部 1000 项受影响**：+4 字节后是 254 / 257，越过 253，下一项的 `prevlen` 跟着变 5 字节——边界只差 4 个字节，代价差 1000 倍。
3. **listpack 恒为 0**：它不记录邻居，插入只改自己。这不是“优化了一点”，而是把一类问题从设计里删掉了。

> 🔑 记住这句：**灾难不来自“元素大”，来自“元素贴着编码边界”**。这类问题在任何变长编码里都存在，只是 ziplist 把它暴露得最清楚。

## 两次修正

| 结构 | 做法 | 解决了什么 | 遗留 |
|---|---|---|---|
| **quicklist** | 链表骨架 + 每个节点装一个 ziplist（限制节点内元素数量），节点还能整体压缩 | 连锁更新被关进**一个节点**；同时保留紧凑编码的内存优势 | 节点内仍可能连锁；跨节点遍历要跳指针 |
| **listpack** | entry = `encoding` + `data` + **自身长度**（放在元素里，不记 `prevlen`） | 插入/修改只涉及自己 → **彻底消除连锁更新**；反向遍历改为从元素尾部读长度 | 编码更复杂；老版本兼容要额外处理 |

演进顺序本身就是一条设计经验：**先加限制（分段），再改结构（自描述）**。前者是工程上的止血，后者才是问题的根除。

## 通用判据：把这条经验搬到别的系统

| 场景 | 反例（元数据依赖邻居） | 正解（自描述） |
|---|---|---|
| 变长记录格式 | 在上一块里写“下一块偏移/长度”，改一块会牵动全局 | 每块自带边界（TLV、长度前缀），块间只靠目录关联 |
| 日志 / WAL 分段 | 单个文件无限增长 + 全局索引，任何重写都要动全量 | 分段（段内自洽），段间用清单关联——就是 quicklist 的思路 |
| 列存 / 压缩块 | 压缩块之间共享字典与偏移 | 块内自洽，字典放段级，块可独立解压 |
| 序列化协议 | 字段长度写在别的字段里、跨字段引用 | 自定界编码，允许跳过未知字段 |

反过来也成立：**如果你为了省内存把元数据“塞进邻居”，就要预期到某一天会遇到连锁变更**；那时成本的量级不由你控制，由数据的长度分布决定。

## 反模式

| 反模式 | 后果 |
|---|---|
| 把紧凑编码用在“频繁增删”的列表上 | 每次插入都可能 memmove + realloc，P99 抖动 |
| 元素长度刚好卡在编码边界 | 一次插入引发全局重排，最坏 O(n) 次 realloc |
| 以为“大元素才危险” | 危险的是“贴着边界的元素”，小元素在长列表里一样能触发 |
| 用单个大 ziplist 存几十万元素 | 查找 O(n) + 更新 O(n)，两个维度一起退化 |
| 只做分段、不做自描述 | 连锁被关进节点，但节点内的问题没解决 |
| 引入 listpack 却不改反向遍历假设 | 代码按 prevlen 往前跳，直接读错数据 |
| 为了省几个字节，把偏移信息写进邻居 | 一个字段的变长引发全量重写，且量级不可控 |

## 自检

**Q1** ziplist 为什么“不适合存大量元素”？两个原因分别是什么？

▸ 答案：① 查找要顺序扫描，O(n)；② 插入/删除要 memmove，并可能触发连锁更新（最坏 O(n) 次 realloc）。内存省了，但两个操作维度都退化，所以它只适合“小数量、少改动”的场景。

**Q2** 为什么“插入一个大元素”不一定会触发连锁更新？真正条件是什么？

▸ 答案：连锁能否继续，取决于**变长后的元素是否越过 253 这个编码边界**。元素 100 字节时，+4 后仍 ≤253，下一项的 prevlen 不变，链立刻断；元素 250 字节时，+4 后 254，越过边界，于是下一项也变 5 字节——一路到底。所以条件是“元素长度贴着边界”，不是“元素大”。

**Q3** quicklist 解决了连锁更新吗？

▸ 答案：没有根除，只是**限定了影响范围**：每个节点是一个 ziplist，连锁最多在这个节点内发生；节点数量多、每个节点元素少，最坏代价从 O(总数) 降到 O(节点内元素数)。真正的根除要等 listpack。

**Q4** listpack 是怎么从根上消除连锁更新的？代价是什么？

▸ 答案：它不再记录 `prevlen`（前一项长度），改为记录**自己的长度**。插入或修改只影响自身，后继元素无需变化。代价是编码更复杂，并且“反向遍历”必须依赖元素尾部记录的长度信息，实现上比 prevlen 更绕。

**Q5** 这个演进故事能迁移到哪些系统设计上？

▸ 答案：任何“变长记录 + 元数据依赖邻居”的结构都适用——变长日志、WAL 分块、列存压缩块、自定义序列化协议。迁移后的两条动作固定：**先把全局不变量降级为段内不变量（分段），再让每段自描述（自定界）**。

**Q6** 一个团队为了省内存，把 10 万条记录塞进一个自定义紧凑结构。你会先问什么？

▸ 答案：先问“更新模式”——是只追加、还是随机插删？只追加且批量写，紧凑结构没问题；随机插删就要看元素长度分布是否贴着编码边界，以及是否有分段。只问内存、不问更新，是把账单留到线上。

**Q7** 为什么说“连锁更新”本质是一次写放大？

▸ 答案：一次逻辑插入，导致 N 个 entry 逐个重写、N 次 realloc——用户看到的是 1 次操作，存储层做了 N 次写。这和 LSM 的写放大、B+ 树的分裂是同一类现象（[44.5 读写放大与空间放大](../44-数据库/44.5-读写放大与空间放大.md)），区别只是触发条件更隐蔽。

**Q8** listpack 之后，ziplist 就可以完全不用了吗？

▸ 答案：新版本里 listpack 逐步替代 ziplist，但存量数据、老版本、以及一些未迁移的结构仍会碰到 ziplist 的语义。理解它的编码规则仍有价值：一是读老数据/老代码，二是它把“紧凑编码的代价”演示得最清楚——很多自研结构会重复同样的错。
