                              41.11 Redis 集群与变慢排查

                              一句话

                              集群只为解决「一台装不下」，代价是路由与迁移；而变慢要先分清是一条命令慢还是整个实例慢——前者看慢查询与 bigkey，后者看基线延迟、swap 与 fsync，用错方向会反复优化无效。

                              三种分片：路由放在谁手里

                              方案 路由表在哪 迁移粒度 客户端改造 代表与现状
                              客户端分片 客户端代码里 key 要改代码 ShardedJedis 一类，已少见
                              代理分片 代理进程 槽（1024） 不用改 Codis / Twemproxy；Codis 已停止维护
                              原生 Cluster 客户端缓存 + 重定向纠偏 槽（16384） 要换支持集群协议的客户端 官方方案

                              判据：存量客户端改不动、迁移频繁才考虑代理；新系统直接上 Cluster——代理少一层网络但没有官方维护，故障时要自己扛。

                              16384 个槽：一个 key 落在哪

                              key --CRC16--> 16 bit 值 --% 16384--> slot(0..16383) --> 实例

                              本机实测（3 主 3 槽区间：0–5460 / 5461–10922 / 10923–16383）：

                              $ redis-cli -p 7100 set foo bar
(error) MOVED 12182 127.0.0.1:7102

$ redis-cli -p 7100 cluster keyslot foo
12182

                              用 Python 独立复算 CRC16/XMODEM 再取模，结果一致：

                              crc16(b"foo") % 16384 = 12182

                              为什么用槽，而不是「key → 实例」的映射表：表的大小会随 key 数量无限膨胀，扩缩容时整张表都要改；槽把「映射」压缩成固定 16384 条，key 的位置用哈希现算，扩缩容只搬槽。

                              为什么要 Hash Tag：多 key 命令（MGET、事务、Lua）要求 key 同槽。用 {} 把参与哈希的部分圈出来：

                              $ redis-cli -p 7100 cluster keyslot '{tag}a'   # 8338
$ redis-cli -p 7100 cluster keyslot '{tag}b'   # 8338
$ redis-cli -p 7100 cluster keyslot 'a{tag}'   # 8338

                              ⚠️ Hash Tag 的代价是反倾斜：所有 {user:1}:* 都落在同一实例。用它换事务便利，就要接受这个实例成为热点。

                              MOVED 与 ASK：两种重定向，客户端动作不同

                              场景 服务端响应 客户端动作 是否更新本地槽缓存
                              槽已完全迁到别处 MOVED <slot> <ip:port> 把命令改发目标节点 是（后续都发新节点）
                              槽正在迁移、这个 key 已搬走 ASK <slot> <ip:port> 先发 ASKING，再发命令 否（只跳这一次）

                              只实现 MOVED 不实现 ASKING 的客户端，会在迁移期间「来回打转」：目标节点因为没收到 ASKING 又回 MOVED。

                              实测跨槽错误与属主查询：

                              $ redis-cli -p 7100 mget foo bar
(error) CROSSSLOT Keys in request don't hash to the same slot

$ redis-cli -p 7100 cluster countkeysinslot 12182   # 0：本节点不负责这个槽
$ redis-cli -p 7102 cluster countkeysinslot 12182   # 1：属主节点才数得到

                              CLUSTER COUNTKEYSINSLOT 是节点本地的，必须在属主节点上问——这是排查「迁移进度」时最常见的误判。

                              迁移一个槽的五步

                              # 目标节点：把这个槽标记为「正在导入」
redis-cli -p 7102 cluster setslot 300 importing <源节点ID>
# 源节点：标记为「正在迁出」
redis-cli -p 7101 cluster setslot 300 migrating <目标节点ID>
# 源节点：取一批 key（100 个）
redis-cli -p 7101 cluster getkeysinslot 300 100
# 源节点：搬过去（3.0.6 起支持一次传多个 key）
redis-cli -p 7101 migrate 127.0.0.1 7102 "" 0 5000 keys k1 k2 k3
# 重复「取 + 搬」直到空，最后把槽归属改掉
redis-cli -p 7102 cluster setslot 300 node <目标节点ID>

                              迁移期间：已搬走的 key 走 ASK，没搬的仍在源节点——所以 ASK 是「过渡态」的产物，不是异常。

                              ⚠️ bigkey 迁移是同步的：一个百万元素的 hash 迁移会让主线程卡住。迁移前先用 --bigkeys 找出大 key，必要时先拆。

                              gossip 与规模上限：为什么集群不能无限大

                              Cluster 没有中心元数据，每个实例都保存全量槽映射，靠 gossip 在 PING/PONG 里互相同步。开销是可算的：

                              项 数值
                              单条 gossip 状态 104 字节
                              每次 PING 携带的实例数 集群总数的 1/10
                              槽位图 16384 bit = 2KB
                              单条 PING（1000 实例时） ≈ 12KB（10KB 状态 + 2KB 槽位图）
                              PING + PONG ≈ 24KB
                              PING 发送量 1 + 10 × N（N = 超时未回 PONG 的实例数）
                              1000 实例、每 100ms 10 个超时 ≈ 1.2MB/s
                              建议规模 400–500 实例
                              # 验证心跳占用的方法：抓集群总线（端口 = 服务端口 + 10000）
tcpdump host 127.0.0.1 port 17100 -i lo0 -w /tmp/r1.cap

                              两个可调项只有 cluster-node-timeout（默认 15000ms，本机实测）与规模本身：

                              • 调小 → 故障发现快，但大规模下 PONG 频繁超时 → 每秒补发 1+10N 个 PING → 越拥塞越超时，正反馈；
                              • 调大 → 故障发现慢，切换窗口变长。

                              💡 关于「1000 是不是硬上限」：硬上限由 16384 个槽决定（主节点最多 16384 个），而官方 cluster 规范给的是建议规模——「1000 节点量级」；工程经验值更保守，400–500 更稳。别把 1000 当成分片数上限。

                              数据倾斜：两种倾斜，两套解法

                              类型 成因 解法
                              数据量倾斜 bigkey 落单实例；槽分配不均；Hash Tag 过度使用 拆 bigkey；按内存重新分槽；控制 Hash Tag 范围
                              访问倾斜 单个热 key（秒杀商品、明星微博） 本地缓存 → key 加随机前缀做只读副本 → 限流降级

                              热 key 多副本只适用于只读：多副本意味着多份写，一致性立刻出问题。有写有读的热点，正确方向是本地缓存 + 限流，而不是复制 key。

                              变慢排查：先分清「一条慢」还是「整体慢」

                              变慢
├── 单条命令慢（其余请求正常）
│   ├── SLOWLOG GET 看是哪条、耗时多少
│   ├── bigkey：HGETALL / SMEMBERS / DEL / 迁移
│   ├── O(N) 命令：KEYS、SORT、交并差
│   └── Lua 长脚本、FLUSHDB/FLUSHALL
└── 整体都慢（P99 普遍抬高）
    ├── 基线：--intrinsic-latency，运行时 ≥ 2× 基线 → 环境问题
    ├── swap：内存被换出，延迟数量级上升
    ├── AOF fsync 尖刺：always、everysec 遇到大写入
    ├── fork：latest_fork_usec 接近秒级
    ├── 碎片：mem_fragmentation_ratio
    └── 缓冲区：client list 的 qbuf / omem

                              单条慢的实测（10 万 field 的 hash，Redis 8.10.2）：

                              操作 耗时 说明
                              HGETALL 10 万 field 6,576 µs O(N)，一次返回全部
                              DEL 10 万 field 10,816 µs 同步释放内存，主线程卡住
                              UNLINK 10 万 field 7 µs 只摘链，内存交给后台线程

                              同一个删除操作，DEL 与 UNLINK 差 1,500 倍——这是「大 key 删除」最容易被低估的地方。

                              整体慢的第一件事是量基线，而不是猜：

                              redis-cli -p 6401 --intrinsic-latency 2
# 2542042 total runs (avg latency: 0.7868 microseconds / 786.77 nanoseconds per run).
# Worst run took 887x longer than the average latency.

                              --intrinsic-latency 测的是「这台机器上 Redis 线程能拿到 CPU 的最坏延迟」。先记下空闲时的基线，业务高峰再测一次：运行时延迟 ≥ 基线 2 倍，说明问题在环境（CPU 争用、虚拟化、绑核错误），不在 Redis 的命令。

                              内存碎片：ratio 会骗人

                              mem_fragmentation_ratio = used_memory_rss / used_memory。常规判读：1.0–1.5 正常，>1.5 说明碎片率超 50%，<1 说明部分内存被换到 swap。

                              但本机实测给了一个反例：

                              used_memory_human:1.23M
used_memory_rss_human:3.16M
mem_fragmentation_ratio:2.60
allocator_frag_ratio:1.00

                              ratio 2.60 看着「碎片严重」，但 allocator_frag_ratio 是 1.00——分配器内部没有碎片，差值是小实例的 RSS 粒度开销（1MB 数据也要占几 MB 的页）。所以：

                              • 判读要带数据量级：几 MB 的实例 ratio 天然偏高，别照着 1.5 的阈值去整理；
                              • 更可靠的是看趋势（同一实例 ratio 是否持续上升）与 allocator_frag_ratio；
                              • 真要整理用 activedefrag yes，四个参数（默认关闭）：active-defrag-ignore-bytes 100mb、active-defrag-threshold-lower 10、active-defrag-threshold-upper 25、active-defrag-cycle-min/max——代价是整理期间吃 CPU。

                              缓冲区：一个能打挂实例的地方

                              缓冲 默认限制 溢出后果
                              客户端输入缓冲 1GB，硬编码不可配 断开该连接
                              客户端输出——普通客户端 0 0 0（不限） 慢客户端堆积 → 内存上涨
                              客户端输出——pub/sub 32mb 8mb 60 断开订阅者
                              客户端输出——从库 256mb 64mb 60 断开从库 → 触发全量同步
                              AOF 缓冲 无独立上限 写失败、主线程阻塞
                              复制积压 repl-backlog 1MB 覆盖未读 → 全量重同步

                              最危险的是 pub/sub：输出缓冲不排队、不阻塞发送，慢消费者只能靠缓冲堆积顶着；把 client-output-buffer-limit pubsub 设成 0（不限），一个卡住的订阅者就能把实例内存吃到 OOM。普通客户端的 0 0 0 同理。

                              # 看谁在堆积
redis-cli -p 6401 client list | awk '{for(i=1;i<=NF;i++) if($i ~ /^(qbuf|omem|cmd)=/) printf "%s ", $i; print ""}'

                              落地：起一个 3 主集群并验证

                              # 指名 + 可抄：3 主 0 从（生产至少每分片 1 从）
for p in 7100 7101 7102; do
  redis-server --port $p --cluster-enabled yes --cluster-config-file nodes-$p.conf \
    --cluster-node-timeout 5000 --save '' --appendonly no \
    --dir /tmp/redis-lab/c2 --daemonize yes
done
redis-cli --cluster create 127.0.0.1:7100 127.0.0.1:7101 127.0.0.1:7102 \
  --cluster-replicas 0 --cluster-yes

# 可验
redis-cli -p 7100 cluster info | grep -E "cluster_state|slots_assigned|known_nodes"
redis-cli -p 7100 cluster shards | head -12        # 7.0+，比 CLUSTER SLOTS 信息全
redis-cli -p 7100 cluster keyslot foo
                              判据 成功输出 失败时看什么
                              集群可用 cluster_state:ok、cluster_slots_assigned:16384 槽没分完（必须 16384 个全覆盖）
                              路由正确 MOVED 12182 127.0.0.1:7102 节点互相看不见（cluster bus 端口 17100 被挡）
                              客户端可用 redis-cli -c 能自动跟随 客户端不支持 MOVED/ASK

                              可退：redis-cli --cluster reshard 把槽搬回、或直接按节点 shutdown 后重建——集群没有「降级成单机」的开关，这一点要在选型时就接受。

                              反模式

                              反模式 后果
                              槽没分完就上线 cluster_state:fail，整个集群不服务
                              客户端只处理 MOVED 不处理 ASK 迁移期间命令来回重定向，延迟抖动
                              在非属主节点数 COUNTKEYSINSLOT 永远返回 0，误判迁移已完成
                              用 Hash Tag 换便利却不控范围 大量 key 挤进同一实例，倾斜成新瓶颈
                              给有写有读的热点做多副本 多份写导致数据错乱；多副本只适用只读
                              扩到上千实例 gossip 心跳挤占带宽，越扩越慢（建议 400–500）
                              用 DEL 删 bigkey 本机实测 10 万 field 卡 10.8ms，百万级接近秒
                              看到 ratio>1.5 就判碎片 小实例天然偏高，看 allocator_frag_ratio 与趋势
                              pub/sub 输出缓冲设为 0 一个慢消费者把实例内存吃满

                              自检

                              Q1 为什么用 16384 个槽，而不是给每个 key 记一条「key → 实例」的映射？

                              ▸ 答案：映射表的大小要随 key 数量增长，且扩缩容时整表都要改，表本身还会变成单点与内存负担。槽把映射压缩成固定的 16384 条：key 用 CRC16 现算槽号，实例只存「槽 → 实例」这张小表；扩缩容只搬槽，key 的映射关系不变。本机用 Python 独立复算 crc16("foo") % 16384 = 12182，与 MOVED 12182 完全一致。

                              Q2 MOVED 与 ASK 的本质区别是什么？客户端少实现哪个会出问题？

                              ▸ 答案：MOVED 表示「这个槽已经不属于我了」，客户端要更新本地槽缓存并改发目标节点；ASK 表示「槽正在迁移，这个 key 恰好已经搬过去了」，客户端要先发 ASKING 再发命令，且不能更新缓存（因为槽还没迁完，其他 key 仍在源节点）。少实现 ASKING 的客户端会在迁移期间和目标节点来回打转。

                              Q3 为什么集群规模建议控制在 400–500 实例，而不是越多越好？

                              ▸ 答案：每个实例都要保存全量槽映射（2KB bitmap），并通过 gossip 互相交换自身与 1/10 其他实例的状态（1000 实例时单条 PING ≈12KB）。心跳数量是 1 + 10×N，一旦出现拥塞就 PONG 超时、再补发更多 PING，形成正反馈。公开测算的口径：1000 实例、每 100ms 有 10 个实例 PONG 超时时，心跳约 1.2MB/s；规模再大，带宽与 CPU 会被心跳吃掉，正常请求吞吐反而下降。

                              Q4 一个 hash 有 10 万个 field，HGETALL、DEL、UNLINK 各自的代价是什么？

                              ▸ 答案：HGETALL 是 O(N)，本机 6,576µs，且要把全部数据序列化回客户端（网络放大）；DEL 也是 O(N) 且同步释放内存（10,816µs），主线程全程阻塞；UNLINK 只把键从字典摘掉、把释放工作丢给后台线程，本机 7µs。所以「删大 key」要用 UNLINK，读大 key 要用 HSCAN 分批。

                              Q5 业务反馈「Redis 变慢了」，你先看什么？为什么先量基线？

                              ▸ 答案：先分类——是某几条命令慢（看 SLOWLOG GET、bigkey、O(N) 命令），还是所有请求的 P99 都抬高。后者要先跑 --intrinsic-latency 量「这台机器能给 Redis 的最坏延迟」：空闲基线 0.787µs、最坏 887 倍于均值，说明偶发调度抖动是正常的；若高峰期延迟达到基线的 2 倍以上，问题在 CPU 争用/虚拟化/绑核，不在 Redis 命令本身，改业务代码是白费。

                              Q6 mem_fragmentation_ratio 是 2.6，能说明碎片严重吗？

                              ▸ 答案：不能直接下结论。它是 rss / used_memory 的比值，小实例（本机 used 1.23MB、rss 3.16MB）天然偏高，因为 RSS 按页计、还有分配器预留；本机同实例 allocator_frag_ratio 是 1.00，说明分配器内部没有碎片。判读要结合数据量级、allocator_frag_ratio 与趋势：比例持续上升才是真碎片，才值得开 activedefrag。

                              Q7 为什么 pub/sub 的输出缓冲能把实例打挂，而普通请求不会？

                              ▸ 答案：普通请求是「一问一答」，响应发不出去只是这个连接慢；pub/sub 是服务端主动推送，发送不阻塞、消息不排队，慢消费者只能靠输出缓冲堆积。若把 client-output-buffer-limit pubsub 设为 0（不限），一个卡住的订阅者就能让缓冲无限增长直到 OOM；默认的 32mb 8mb 60 就是用来在 32MB 或 60 秒内累计 8MB 时把该订阅者踢掉。
