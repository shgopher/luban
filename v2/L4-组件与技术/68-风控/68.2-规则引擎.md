# 68.2 规则引擎

## 一句话

> 规则引擎的价值不是“能配规则”，而是**让业务在不发版的前提下改判据，且每次判定都能解释、能回放、能灰度**；判据是——**一条规则从提出到生效要多久，出错后多久能回滚**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 规则引擎 = 把 if-else 搬到配置里 | 只搬条件不搬**优先级、短路、版本、灰度**，等于换了个地方写死 |
| 规则越多越安全 | 规则之间会冲突、会重复、会互相掩盖；几十条以上就要分层 |
| 规则不需要测试 | 规则是最容易写错、又最直接影响收入的代码，必须有单测与回放 |

## 一条规则由什么组成

| 要素 | 说明 | 反例 |
|---|---|---|
| **条件** | 引用的特征与比较 | `amount > limit`，limit 要能按商户/用户配 |
| **动作** | 通过 / 拒绝 / 降额 / 转人工 | 只有“拒绝”，处置粒度太粗 |
| **优先级** | 数字越小越先 | 没有优先级，冲突时谁生效说不清 |
| **生效范围** | 全量 / 灰度 / 指定人群 | 规则一上线就全量，出事只能回滚 |
| **版本** | 可回溯、可回滚 | 改了直接覆盖，出问题找不到上一版 |

## 执行：优先级 + 短路

```go
// 规则引擎：按优先级短路，命中即返回，并记录命中原因（可解释）。
type rule struct {
	id       string
	priority int
	match    func(amount int, newDevice bool) bool
	action   string
}
```

真实输出（本机 `go1.27.1 darwin/arm64`，金额 6 万、新设备）：

```text
命中 R2 超限额（优先级 20）→ 拒绝
```

注意它**没有**继续匹配 R3（新设备大额，优先级 30）：高优先级规则先命中就短路。好处是决策快、结论唯一；代价是低优先级规则“被掩盖”了——所以规则设计要分层：

| 层 | 规则类型 | 优先级 |
|---|---|---|
| 第 1 层 | 名单（黑/白） | 最高，命中即终止 |
| 第 2 层 | 硬限额（单笔/单日） | 高 |
| 第 3 层 | 频次/设备/行为 | 中 |
| 第 4 层 | 模型打分 | 最低（兜底） |

## 表达力：决策表、DSL、脚本怎么选

| 形式 | 表达力 | 可审计性 | 适合 |
|---|---|---|---|
| **决策表**（条件 × 动作） | 低 | 高（业务能看懂） | 限额、名单、简单组合 |
| **DSL** | 中 | 中 | 大部分业务规则 |
| **脚本**（Groovy/Lua/表达式） | 高 | 低（可写任意逻辑） | 复杂计算、临时策略 |

判据（我的判断）：**能用决策表就不用 DSL，能用 DSL 就不用脚本**。表达力越强，越容易写出“没人看得懂、没人敢改”的规则。

## 测试、灰度、回滚

| 环节 | 做法 | 判据 |
|---|---|---|
| 单测 | 每条规则至少一个命中、一个不命中用例 | 改动后全绿 |
| 回放 | 拿历史请求跑新规则，对比决策差异 | 差异率在预期内 |
| 影子 | 新规则只记录不生效，观察一段时间 | 误杀率可接受 |
| 灰度 | 按用户/商户/比例放量 | 指标不劣化 |
| 回滚 | 版本化，一键切回上一版 | 分钟级 |

> 🔑 规则引擎最该被考核的指标是**变更时长**：从“业务提出”到“线上生效”要多久。如果还要排期发版，那它只是个配置表，不是引擎。

## 性能：规则数与延迟

| 规则数 | 匹配方式 | 延迟（经验值） |
|---|---|---|
| < 50 | 顺序匹配 + 短路 | 亚毫秒到几毫秒 |
| 50–500 | 按特征索引 + 分组 | 几毫秒 |
| > 500 | Rete/网路匹配，或拆成多级决策 | 需要专门优化 |

规则数量不是“越多越安全”，而是**越多越难维护、越容易冲突**。超过几百条，通常说明该按业务线拆成多个规则集。

## 反模式

| 反模式 | 后果 |
|---|---|
| 规则没有优先级 | 冲突时结果取决于加载顺序，不可复现 |
| 规则一上线就全量 | 出事只能回滚，影响已经产生 |
| 规则改了不版本化 | 无法回滚，也无法解释“为什么昨天放行今天拒绝” |
| 用脚本写所有规则 | 没人敢改，规则变成黑盒 |
| 规则不测试就上线 | 一条写错的条件可能误杀整个客群 |
| 规则数量无上限 | 冲突、重复、性能一起恶化 |
| 只记录结果不记录命中项 | 客诉无法解释 |

## 自检

**Q1** 规则引擎和“把 if-else 写成配置”差在哪？

▸ 答案：差在四个工程能力：**优先级与短路**（冲突时结论唯一）、**版本与回滚**（改错能退回）、**灰度与影子**（新规则先观察再放量）、**命中记录**（可解释可回放）。缺这四样，配置化只是把代码搬到了 YAML 里，改起来更危险。

**Q2** 为什么规则要有优先级，而且高优先级命中就短路？

▸ 答案：因为没有优先级，冲突结果取决于加载顺序，同一个请求可能得到不同结论，无法复现；短路则保证决策快、结论唯一。代价是低优先级规则可能被掩盖，所以要用“名单 → 硬限额 → 频次/设备 → 模型”的分层来安排优先级。

**Q3** 决策表、DSL、脚本该怎么选？

▸ 答案：按表达力与可审计性权衡：决策表最容易被业务看懂、最容易审计，适合限额与名单；DSL 适合大部分业务规则；脚本表达力最强但最难审计，只用于复杂计算或临时策略。原则是**能用弱的就不用强的**。

**Q4** 新规则上线前，为什么要做回放与影子？

▸ 答案：因为规则错误往往只在特定人群/金额/设备组合下暴露，单测覆盖不到。回放拿历史请求跑新规则，能提前看到“决策差异率”；影子只记录不生效，能看到真实流量下的误杀情况。两者都是为了把“上线后才发现”提前到“上线前”。

**Q5** 规则数量多到什么程度就该拆？

▸ 答案：经验上超过几百条就该按业务线/场景拆成多个规则集，因为冲突检测、评审、性能都会随数量恶化。更早的信号是“同一类规则重复出现”“规则之间互相覆盖”——这时候拆，比等到上千条再拆便宜得多。
