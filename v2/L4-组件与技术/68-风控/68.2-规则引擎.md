# 68.2 规则引擎

## 一句话

> 规则引擎的价值不是“能配规则”，而是**让业务在不发版的前提下改判据，且每次判定都能解释、能回放、能灰度**；判据是——**一条规则从提出到生效要多久，出错后多久能回滚**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 规则引擎 = 把 if-else 搬到配置里 | 只搬条件不搬**优先级、短路、版本、灰度**，等于换了个地方写死 |
| 规则越多越安全 | 规则之间会冲突、会重复、会互相掩盖；几十条以上就要分层 |
| 规则不需要测试 | 规则是最容易写错、又最直接影响收入的代码，必须有单测与回放 |

## 一条规则由什么组成

| 要素 | 说明 | 反例 |
|---|---|---|
| **条件** | 引用的特征与比较 | `amount > limit`，limit 要能按商户/用户配 |
| **动作** | 通过 / 拒绝 / 降额 / 转人工 | 只有“拒绝”，处置粒度太粗 |
| **优先级** | 数字越小越先 | 没有优先级，冲突时谁生效说不清 |
| **生效范围** | 全量 / 灰度 / 指定人群 | 规则一上线就全量，出事只能回滚 |
| **版本** | 可回溯、可回滚 | 改了直接覆盖，出问题找不到上一版 |

## 执行：优先级 + 短路

```go
// 规则引擎：按优先级短路，命中即返回，并记录命中原因（可解释）。
type rule struct {
	id       string
	priority int
	match    func(amount int, newDevice bool) bool
	action   string
}
```

真实输出（本机 `go1.27.1 darwin/arm64`，金额 6 万、新设备）：

```text
命中 R2 超限额（优先级 20）→ 拒绝
```

完整代码在仓库 [tools/examples/68.2-ruleengine/](../../../tools/examples/68.2-ruleengine/README.md)，`go run .` 可复现这段输出。

注意它**没有**继续匹配 R3（新设备大额，优先级 30）：高优先级规则先命中就短路。好处是决策快、结论唯一；代价是低优先级规则“被掩盖”了——所以规则设计要分层：

| 层 | 规则类型 | 优先级 |
|---|---|---|
| 第 1 层 | 名单（黑/白） | 最高，命中即终止 |
| 第 2 层 | 硬限额（单笔/单日） | 高 |
| 第 3 层 | 频次/设备/行为 | 中 |
| 第 4 层 | 模型打分 | 最低（兜底） |

## 表达力：决策表、DSL、脚本怎么选

| 形式 | 表达力 | 可审计性 | 适合 |
|---|---|---|---|
| **决策表**（条件 × 动作） | 低 | 高（业务能看懂） | 限额、名单、简单组合 |
| **DSL** | 中 | 中 | 大部分业务规则 |
| **脚本**（Groovy/Lua/表达式） | 高 | 低（可写任意逻辑） | 复杂计算、临时策略 |

判据（我的判断）：**能用决策表就不用 DSL，能用 DSL 就不用脚本**。表达力越强，越容易写出“没人看得懂、没人敢改”的规则。

## 测试、灰度、回滚

| 环节 | 做法 | 判据 |
|---|---|---|
| 单测 | 每条规则至少一个命中、一个不命中用例 | 改动后全绿 |
| 回放 | 拿历史请求跑新规则，对比决策差异 | 差异率在预期内 |
| 影子 | 新规则只记录不生效，观察一段时间 | 误杀率可接受 |
| 灰度 | 按用户/商户/比例放量 | 指标不劣化 |
| 回滚 | 版本化，一键切回上一版 | 分钟级 |

> 🔑 规则引擎最该被考核的指标是**变更时长**：从“业务提出”到“线上生效”要多久。如果还要排期发版，那它只是个配置表，不是引擎。

## 性能：规则数与延迟

| 规则数 | 匹配方式 | 延迟（经验值） |
|---|---|---|
| < 50 | 顺序匹配 + 短路 | 亚毫秒到几毫秒 |
| 50–500 | 按特征索引 + 分组 | 几毫秒 |
| > 500 | Rete/网路匹配，或拆成多级决策 | 需要专门优化 |

规则数量不是“越多越安全”，而是**越多越难维护、越容易冲突**。超过几百条，通常说明该按业务线拆成多个规则集。

## 规则引擎 vs 代码：决策表与一次基准

**结论先行**：规则引擎不是「更高级的 if-else」，它是用一笔**固定投入**（接入、管理台、审计、热更新、版本回滚）换**变更周期**。规则少、变得慢、没有业务方自己维护时，硬编码更便宜；延迟几乎从不是选它的理由——本机算下来 10 条规则只差约 0.56µs。

### 选型：五个维度一张决策表

| 规则数 | 月变更次数 | 谁维护 | 可解释性要求 | 延迟预算 | 选什么 |
|---|---|---|---|---|---|
| < 20 | < 1 | 研发 | 中 | 任意 | **硬编码 if/else**（另附一张决策表当文档） |
| 20–200 | 1–4 | 研发为主、业务提需求 | 高（客诉要能解释） | 毫秒级 | **配置化决策表 / DSL** |
| 200–1,000 | ≥ 4 | 业务 + 研发 | 高 | 毫秒级 | **规则引擎**（决策表为主 + 少量 DSL） |
| > 1,000 | ≥ 10 | 业务自助 | 极高（审计/合规） | 需专门优化 | 规则引擎 + 分层规则集 + 独立服务 |

三条读法：

- **规则数是分子，变更频率是分母**：20 条规则每月改 10 次，比 200 条规则一年不改更需要引擎。
- **谁维护决定形态**：业务要自己改，只能决策表（人看得懂）；研发自己改，DSL 就够。
- **延迟只影响实现，不影响选型**：嫌慢就去预编译规则、按特征建索引（「性能：规则数与延迟」那张表按规则数分了档），不是「所以不该用引擎」。

变更账可以算成一句公式：

```text
回本变更次数 = 引擎固定投入 ÷ (硬编码每次变更人力 − 引擎每次变更人力)
```

按引擎固定投入 10 人日（接入 + 管理台 + 审计 + 回滚演练）、硬编码每次变更 0.75 人日、引擎每次 0.15 人日算，回本点是 16.7 次变更：

| 月变更次数 | 年变更次数 | 回本（月） |
|---|---|---|
| 0.5 | 6 | 33.3 |
| 1 | 12 | 16.7 |
| 2 | 24 | 8.3 |
| 4 | 48 | 4.2 |
| 12 | 144 | 1.4 |

这张表比任何「规则多了就该上引擎」的经验都准：**每月改不到一次，引擎在两年内都是亏的**；反过来说，一个每周都在改判据的团队，硬编码的发版窗口就是它的主要瓶颈。

### 一次基准：10 条规则 × 100 万次

同一组 10 条规则（名单 → 限额 → 频次 → 设备/行为 → 模型分，按优先级短路），写成两份代码：一份规则是数据 + 通用解释器，一份是 10 个 if 硬编码。跑同一批合成请求、同一优先级顺序，比对耗时、结论一致性与代码行数。

```python
# 本机计算：10 条风控规则，决策表驱动 vs if/else 硬编码，各跑 100 万次
import random, statistics, time

# >>> RULES（决策表：规则是数据，顺序即优先级）
RULES = [
    ("R1  黑名单",     (("is_black", "==", True),),                         "reject"),
    ("R2  白名单",     (("is_white", "==", True),),                         "pass"),
    ("R3  单笔超限",   (("amount", ">", 50000),),                           "reject"),
    ("R4  新设备大额", (("new_device", "==", True), ("amount", ">", 10000)), "verify"),
    ("R5  频次超限",   (("cnt_1h", ">", 20),),                              "reject"),
    ("R6  小时累计",   (("amt_1h", ">", 100000),),                          "verify"),
    ("R7  境外 IP",    (("foreign_ip", "==", True),),                       "verify"),
    ("R8  夜间大额",   (("night", "==", True), ("amount", ">", 5000)),       "verify"),
    ("R9  新户大额",   (("age_days", "<", 1), ("amount", ">", 500)),         "verify"),
    ("R10 模型高分",   (("score", ">", 0.8),),                              "verify"),
]
# <<< RULES_END

# >>> TABLE_IMPL（解释器：一次写对，之后只改数据）
def decide_table(r):
    """通用解释器：顺序匹配 + 命中短路；规则不写死在代码里。"""
    for _id, conds, action in RULES:
        for f, op, v in conds:
            x = r[f]
            if not (x > v if op == ">" else x < v if op == "<" else x == v):
                break
        else:
            return action
    return "pass"
# <<< TABLE_IMPL_END

# >>> CODE_IMPL（硬编码：同样 10 条、同样优先级；改阈值 = 改函数体 + 发版）
def decide_code(r):
    if r["is_black"]:
        return "reject"
    if r["is_white"]:
        return "pass"
    if r["amount"] > 50000:
        return "reject"
    if r["new_device"] and r["amount"] > 10000:
        return "verify"
    if r["cnt_1h"] > 20:
        return "reject"
    if r["amt_1h"] > 100000:
        return "verify"
    if r["foreign_ip"]:
        return "verify"
    if r["night"] and r["amount"] > 5000:
        return "verify"
    if r["age_days"] < 1 and r["amount"] > 500:
        return "verify"
    if r["score"] > 0.8:
        return "verify"
    return "pass"
# <<< CODE_IMPL_END

POOL, ITER, ROUNDS, QPS = 1000, 1_000_000, 5, 20_000

def make_pool(n, seed=42):                      # 合成请求：让 10 条规则都有命中
    rnd, pool = random.Random(seed), []
    for _ in range(n):
        pool.append({"is_black": rnd.random() < 0.01, "is_white": rnd.random() < 0.02,
            "amount": rnd.choice([50, 300, 800, 3000, 9000, 30000, 80000]),
            "new_device": rnd.random() < 0.15, "cnt_1h": rnd.choice([0, 3, 8, 15, 25, 40]),
            "amt_1h": rnd.choice([0, 5000, 60000, 150000]), "foreign_ip": rnd.random() < 0.05,
            "night": rnd.random() < 0.30, "age_days": rnd.choice([0, 1, 30, 365]),
            "score": rnd.choice([0.1, 0.4, 0.7, 0.85, 0.95])})
    return pool

def bench(fn, pool):
    for i in range(20_000):
        fn(pool[i % POOL])                      # 预热，避免首轮解释器特化影响
    ts = []
    for _ in range(ROUNDS):
        t0 = time.perf_counter()
        for i in range(ITER):
            fn(pool[i % POOL])
        ts.append(time.perf_counter() - t0)
    return statistics.median(ts)

def loc(begin, end):                            # 数标记区间的有效行（非空非注释）
    inside, n = False, 0
    for ln in open(__file__, encoding="utf-8"):
        if begin in ln: inside = True; continue
        if end in ln: break
        s = ln.strip()
        if inside and s and not s.startswith("#"): n += 1
    return n

pool = make_pool(POOL)
t_code, t_table = bench(decide_code, pool), bench(decide_table, pool)
diff = sum(1 for r in pool if decide_code(r) != decide_table(r))
dist = {}
for r in pool:
    dist[decide_code(r)] = dist.get(decide_code(r), 0) + 1

us_code, us_table = t_code / ITER * 1e6, t_table / ITER * 1e6
extra = us_table - us_code
fixed_days, save_days = 10.0, 0.75 - 0.15

print(f"请求池 {POOL} 条 × {ITER:,} 次 × {ROUNDS} 轮取中位（本机计算，纯解释执行、无网络/DB）")
print(f"硬编码 {t_code:.3f}s  {us_code:.2f}µs/次")
print(f"决策表 {t_table:.3f}s  {us_table:.2f}µs/次  = {t_table/t_code:.2f}×（每次多 {extra:.2f}µs）")
print(f"决策一致性：{POOL-diff}/{POOL} 相同，差异 {diff} 条；分布 "
      + "，".join(f"{k}={v}" for k, v in sorted(dist.items())))
print(f"QPS={QPS:,} 时额外 CPU ≈ {extra*1e-6*QPS:.2f} 核")
n_rules = loc('>>> RULES', '<<< RULES_END')
n_eng = loc('>>> TABLE_IMPL', '<<< TABLE_IMPL_END')
n_code = loc('>>> CODE_IMPL', '<<< CODE_IMPL_END')
print(f"有效代码行：硬编码 {n_code} 行；决策表 = 规则数据 {n_rules} 行 + 解释器 {n_eng} 行 "
      f"= {n_rules + n_eng} 行（{((n_rules+n_eng)/n_code):.2f}×）")
print(f"回本变更次数 = 引擎固定 {fixed_days:.0f} 人日 ÷ 每次省 {save_days:.2f} 人日 "
      f"= {fixed_days/save_days:.1f} 次")
for pm in (0.5, 1, 2, 4, 12):
    print(f"  月变更 {pm:>4} 次 → 年 {pm*12:>3.0f} 次 → 回本 {fixed_days/save_days/pm:>5.1f} 个月")
```

本机计算（macOS 15.6 / Apple M1 / Python 3.14.8，真实计时，纯内存解释执行、无网络无 DB）：

决策表 0.766s  0.77µs/次  = 3.68×（每次多 0.56µs）
决策一致性：1000/1000 相同，差异 0 条；分布 pass=181，reject=421，verify=398

  月变更    2 次 → 年  24 次 → 回本   8.3 个月

完整代码在仓库 [tools/examples/68.2-rules-bench/](../../../tools/examples/68.2-rules-bench/README.md)，`python3 rules_bench.py` 可复现；计时随机器波动，绝对值 ±5%，比值（3.6–3.7×）稳定。

三个读法：

1. **延迟差约 3.6 倍（每次多约 0.56µs），换算成 CPU 只有 0.01 核**（按 QPS 2 万）。把规则引擎当「性能优化」是错位：它的开销在微秒级，风控决策预算是毫秒级（见 [68.1 风控系统架构](68.1-风控系统架构.md) 的时延预算），差两个数量级。
2. **代码行数打平（22 行 vs 22 行），但结构不同**：决策表的 22 行 = 12 行纯数据 + 10 行一次写对的解释器；硬编码的 22 行里每一行都既是数据又是逻辑。行数不是决策表的卖点，**改动半径**才是。
3. **一致性 1000/1000**：决策表不是「另一套判定」，它必须与硬编码逐条等价；不做回放比对就换决策表，等于把发版风险换成配置风险。

改动半径量化成下表（交付时长取研发经验值，可按自己团队的 CI 与灰度时长替换）：

| 动作 | 硬编码 | 决策表 | 差距来源 |
|---|---|---|---|
| 改 1 个阈值 | 改 1 行代码 + CI + 灰度 ≈ 45 分钟 | 改 1 行数据 + 热加载 ≈ 10 秒 | 发版流程 vs 数据替换 |
| 加 1 条规则 | 改 3 行 + 单测 + 发版 ≈ 0.75 人日 | 加 1 行数据 + 回放验证 ≈ 0.15 人日 | 代码评审 vs 数据评审 |
| 回滚上一条规则 | 回滚代码版本 ≈ 30 分钟 | 切回上一版规则集 ≈ 秒级 | 版本粒度：整包 vs 单规则集 |
| 向客诉解释一次拒绝 | 读代码找分支，容易找错 | 直接念命中的规则 id 与版本 | 结论与原因同源 |

> 🔑 10 条规则的规模上，决策表与硬编码代码量一样、慢约 3.6 倍、每次多约 0.56µs——这些都不构成选型理由；**唯一构成理由的是「谁来改、多久改一次、改完要不要发版」**。

### 隐藏成本：引擎不是免费的

| 隐藏成本 | 具体表现 | 量级（本机计算 / 工程估算） | 规避 |
|---|---|---|---|
| **表达式求值** | 每条规则要取字段、比较、判空 | 本机 10 条规则共约 0.56µs/次，单条约 0.1–0.5µs | 预编译 AST；按特征建索引，把「顺序扫 1,000 条」压到「只看命中的 10 条」 |
| **规则加载** | 启动时解析规则集、建索引 | 1,000 条约 50ms（一次性） | 启动预热 + 加载失败拒绝启动，不带着半套规则对外服务 |
| **热更新** | 新规则集替换旧规则集 | 双缓冲 + 原子切换，切换本身微秒级 | 新集合先校验（语法、引用字段存在、无环），失败保留旧版本 |
| **版本回滚** | 回到上一版规则集 | 秒级（前提：规则集有不可变快照） | 每次发布存版本号；决策日志必须写 `ruleset_version` |
| **审计与解释** | 每条决策记命中规则 id、版本、关键特征 | 1 亿条 × 200B ≈ 20GB | 命中项结构化落库，而不是只存「拒绝」 |
| **兜底策略** | 引擎故障/超时怎么办 | 按决策点定 fail-open / fail-close | 登录放行 + 告警，大额支付拒绝（见 [68.1 风控系统架构](68.1-风控系统架构.md)） |

其中**审计与版本**最容易被低估：没有 `ruleset_version`，「昨天放行、今天拒绝」永远解释不清；没有命中规则 id，客诉只能回一句「系统判定」。这两项不是上了引擎自动就有，而是要在接引擎之前就设计进决策日志。

### 什么时候别上规则引擎

满足任意两条，先用硬编码 + 决策表文档：

- **规则 < 20 条**，且互相独立、没有优先级冲突；
- **变更 < 1 次/月**，或变更都挤在版本发布窗口；
- **没有业务人员维护**——「研发改配置」也是改代码，只是换了文件格式；
- **强合规逻辑**（金额上限、监管红线）需要代码评审、单测、静态检查兜底，配置化反而绕过了这些门（见 [53.2 单元测试](../../L5-工程效能/53-测试与质量保障/53.2-单元测试.md)）；
- **单次决策预算 < 1ms 且 QPS 极高**：多出的约 0.56µs 会变成实打实的核数（0.56µs × 100 万 QPS ≈ 0.6 核，自己按真实 QPS 重算）。

> ⚠️ 最常见的错法：先上引擎、再补管理台、最后补审计——顺序反了。正确顺序是**先数据化（硬编码里把规则抽成表）→ 再外置配置 → 最后才引入引擎**；每一步都能独立回退，代价逐级上升。10 条规则时停在第一步就是最优解，这不可耻。

## 反模式

| 反模式 | 后果 |
|---|---|
| 规则没有优先级 | 冲突时结果取决于加载顺序，不可复现 |
| 规则一上线就全量 | 出事只能回滚，影响已经产生 |
| 规则改了不版本化 | 无法回滚，也无法解释“为什么昨天放行今天拒绝” |
| 用脚本写所有规则 | 没人敢改，规则变成黑盒 |
| 规则不测试就上线 | 一条写错的条件可能误杀整个客群 |
| 规则数量无上限 | 冲突、重复、性能一起恶化 |
| 只记录结果不记录命中项 | 客诉无法解释 |

## 自检

**Q1** 规则引擎和“把 if-else 写成配置”差在哪？

▸ 答案：差在四个工程能力：**优先级与短路**（冲突时结论唯一）、**版本与回滚**（改错能退回）、**灰度与影子**（新规则先观察再放量）、**命中记录**（可解释可回放）。缺这四样，配置化只是把代码搬到了 YAML 里，改起来更危险。

**Q2** 为什么规则要有优先级，而且高优先级命中就短路？

▸ 答案：因为没有优先级，冲突结果取决于加载顺序，同一个请求可能得到不同结论，无法复现；短路则保证决策快、结论唯一。代价是低优先级规则可能被掩盖，所以要用“名单 → 硬限额 → 频次/设备 → 模型”的分层来安排优先级。

**Q3** 决策表、DSL、脚本该怎么选？

▸ 答案：按表达力与可审计性权衡：决策表最容易被业务看懂、最容易审计，适合限额与名单；DSL 适合大部分业务规则；脚本表达力最强但最难审计，只用于复杂计算或临时策略。原则是**能用弱的就不用强的**。

**Q4** 新规则上线前，为什么要做回放与影子？

▸ 答案：因为规则错误往往只在特定人群/金额/设备组合下暴露，单测覆盖不到。回放拿历史请求跑新规则，能提前看到“决策差异率”；影子只记录不生效，能看到真实流量下的误杀情况。两者都是为了把“上线后才发现”提前到“上线前”。

**Q5** 规则数量多到什么程度就该拆？

▸ 答案：经验上超过几百条就该按业务线/场景拆成多个规则集，因为冲突检测、评审、性能都会随数量恶化。更早的信号是“同一类规则重复出现”“规则之间互相覆盖”——这时候拆，比等到上千条再拆便宜得多。
