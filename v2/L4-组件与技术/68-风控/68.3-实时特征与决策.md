# 68.3 实时特征与决策

## 一句话

> 实时特征的难点不是“算得快”，而是**训练与线上一致**：同一个特征在离线与在线必须是同一定义、同一时间口径、同一聚合窗口；否则离线 AUC 再高，上线也会崩。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 特征 = 日志里的字段 | 字段只是原料；特征是“按某个口径聚合出来的量”，口径不对就是错的特征 |
| 实时 = 越快越好 | 实时特征的价值是“及时反映行为”，不是“低延迟”；延迟与准确性要权衡 |
| 模型决定效果 | 特征决定上限，模型只是逼近上限；风控场景里，特征与名单往往比模型更有效 |

## 三类特征：离线、近线、实时

| 类型 | 计算方式 | 延迟 | 典型特征 |
|---|---|---|---|
| **离线** | 批处理（T+1） | 小时–天 | 用户历史逾期、商户月交易额 |
| **近线** | 流式聚合，落 KV | 秒–分钟 | 近 1 小时交易笔数、近 24 小时设备数 |
| **实时** | 请求内计算或读预聚合 | 毫秒 | 本次金额、设备指纹、当前 IP |

判据（我的判断）：**能在近线算的，不要放到请求里算**。请求内只做“读 + 简单比较”，窗口聚合一律前置。

## 时间口径：特征穿越的根源

| 概念 | 含义 | 坑 |
|---|---|---|
| **事件时间** | 业务真实发生的时间 | 与处理时间不一致时，窗口会错位 |
| **处理时间** | 系统收到/处理的时间 | 延迟到达的数据会被算进“未来”窗口 |
| **特征穿越** | 训练时用到了预测时点之后的数据 | 离线指标虚高，上线暴跌 |

> 🔑 防止穿越的唯一办法：**训练样本必须按“预测时点”截断特征**。同一笔交易，训练时只能用“这笔交易发生前”的特征，不能用它之后的任何数据。

## 滑动窗口：把“近 N 分钟”算对

```go
// 实时特征：滑动窗口（5 分钟）内的交易次数与金额，用于频次类规则。
now, window := 300, 300
for _, e := range events {
	if now-e.ts <= window {
		count++
		sum += e.amount
	}
}
```

真实输出（本机 `go1.27.1 darwin/arm64`，6 笔事件，时间 0–600 秒，当前 300 秒）：

```text
近 300 秒：笔数=6 金额=2400
判据：窗口内笔数 > 5 或金额 > 1000 → 触发频次规则
```

两个细节决定这个特征对不对：

- **边界**：`<=` 还是 `<`，决定同一笔在相邻窗口会不会被算两次；
- **口径**：用事件时间还是处理时间，决定延迟数据算进哪个窗口。

## 训练与线上一致：三条硬规则

| 规则 | 做法 | 不一致的后果 |
|---|---|---|
| **同一份定义** | 特征定义集中管理（[64.1 特征平台](../../L4-组件与技术/64-机器学习系统/64.1-特征平台.md)），离线/在线同源 | 两边各写一套，数值对不上 |
| **同一时间口径** | 统一事件时间，统一窗口边界 | 离线特征偏高/偏低 |
| **同一份样本** | 线上决策日志回流，作为训练样本 | 训练分布与线上分布漂移 |

## 决策：规则、模型、融合

| 方式 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **规则** | 可解释、可快速上线 | 覆盖有限、易被绕过 | 硬约束（限额、名单） |
| **模型** | 覆盖广、能发现组合特征 | 不可解释、需要样本、会漂移 | 软判断（欺诈概率） |
| **融合** | 规则兜底 + 模型排序 | 架构更复杂 | 大多数生产系统 |

时延预算见 [68.1 风控系统架构](68.1-风控系统架构.md)：模型打分是最重的一段，必须有降级路径（模型超时 → 规则兜底）。

## 反模式

| 反模式 | 后果 |
|---|---|
| 训练用了预测时点之后的数据 | 离线指标虚高，上线效果崩 |
| 离线/在线各写一套特征 | 数值对不上，模型行为不可预期 |
| 在请求里现算窗口聚合 | 延迟随流量放大，拖垮主链路 |
| 窗口边界不统一 | 同一笔被重复计入相邻窗口 |
| 只上模型、不留规则兜底 | 模型服务抖动 = 风控失效 |
| 特征不做监控 | 特征分布漂移无人发现，效果悄悄下降 |
| 用处理时间替代事件时间 | 延迟数据算错窗口，频次判断失真 |

## 自检

**Q1** 为什么“离线 AUC 很高”不能保证线上效果？

▸ 答案：因为离线评估可能犯了特征穿越（用了未来数据）或口径不一致（离线窗口与线上不同）。这类问题在离线看不出来，上线后特征值分布与训练分布不同，模型行为立刻偏离。所以上线前必须做“离线/在线特征一致性校验”。

**Q2** 实时特征为什么“能近线就不实时”？

▸ 答案：因为请求内计算会随流量放大，且窗口聚合需要状态，做在请求里既慢又难一致。近线流式聚合把计算前置，请求只做“读 + 比较”，既保证延迟，也保证离线/在线用同一份聚合结果。

**Q3** 滑动窗口的两个“边界”分别指什么？

▸ 答案：一是**时间边界**（`<=` 还是 `<`，避免同一笔被两个窗口重复计入）；二是**口径边界**（事件时间还是处理时间，决定延迟到达的数据算进哪个窗口）。两者不统一，频次类特征就会忽高忽低。

**Q4** 规则和模型在风控里怎么分工？

▸ 答案：规则管“硬约束”（黑名单、限额、频次），要求可解释、可快速上线；模型管“软判断”（欺诈概率、团伙相似度），覆盖规则想不到的组合。生产上通常融合：规则先短路，模型对剩余请求打分，模型超时则降级为规则兜底。

**Q5** 特征监控该看什么？

▸ 答案：看分布而不是看单值：均值/分位数漂移、缺失率、取值越界比例。特征分布漂移往往先于效果下降出现，是最早的预警信号；只监控“服务是否存活”发现不了效果衰减。
