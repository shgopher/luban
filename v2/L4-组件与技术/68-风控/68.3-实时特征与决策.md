# 68.3 实时特征与决策

## 一句话

> 实时特征的难点不是“算得快”，而是**训练与线上一致**：同一个特征在离线与在线必须是同一定义、同一时间口径、同一聚合窗口；否则离线 AUC 再高，上线也会崩。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 特征 = 日志里的字段 | 字段只是原料；特征是“按某个口径聚合出来的量”，口径不对就是错的特征 |
| 实时 = 越快越好 | 实时特征的价值是“及时反映行为”，不是“低延迟”；延迟与准确性要权衡 |
| 模型决定效果 | 特征决定上限，模型只是逼近上限；风控场景里，特征与名单往往比模型更有效 |

## 三类特征：离线、近线、实时

| 类型 | 计算方式 | 延迟 | 典型特征 |
|---|---|---|---|
| **离线** | 批处理（T+1） | 小时–天 | 用户历史逾期、商户月交易额 |
| **近线** | 流式聚合，落 KV | 秒–分钟 | 近 1 小时交易笔数、近 24 小时设备数 |
| **实时** | 请求内计算或读预聚合 | 毫秒 | 本次金额、设备指纹、当前 IP |

判据（我的判断）：**能在近线算的，不要放到请求里算**。请求内只做“读 + 简单比较”，窗口聚合一律前置。

## 时间口径：特征穿越的根源

| 概念 | 含义 | 坑 |
|---|---|---|
| **事件时间** | 业务真实发生的时间 | 与处理时间不一致时，窗口会错位 |
| **处理时间** | 系统收到/处理的时间 | 延迟到达的数据会被算进“未来”窗口 |
| **特征穿越** | 训练时用到了预测时点之后的数据 | 离线指标虚高，上线暴跌 |

> 🔑 防止穿越的唯一办法：**训练样本必须按“预测时点”截断特征**。同一笔交易，训练时只能用“这笔交易发生前”的特征，不能用它之后的任何数据。

## 滑动窗口：把“近 N 分钟”算对

```go
// 实时特征：滑动窗口（5 分钟）内的交易次数与金额，用于频次类规则。
now, window := 300, 300
for _, e := range events {
	if now-e.ts <= window {
		count++
		sum += e.amount
	}
}
```

真实输出（本机 `go1.27.1 darwin/arm64`，6 笔事件，时间 0–600 秒，当前 300 秒）：

```text
近 300 秒：笔数=6 金额=2400
判据：窗口内笔数 > 5 或金额 > 1000 → 触发频次规则
```

完整代码在仓库 [tools/examples/68.3-featurewin/](../../../tools/examples/68.3-featurewin/README.md)，`go run .` 可复现这个窗口。

两个细节决定这个特征对不对：

- **边界**：`<=` 还是 `<`，决定同一笔在相邻窗口会不会被算两次；
- **口径**：用事件时间还是处理时间，决定延迟数据算进哪个窗口。

## 训练与线上一致：三条硬规则

| 规则 | 做法 | 不一致的后果 |
|---|---|---|
| **同一份定义** | 特征定义集中管理（[64.1 特征平台](../../L4-组件与技术/64-机器学习系统/64.1-特征平台.md)），离线/在线同源 | 两边各写一套，数值对不上 |
| **同一时间口径** | 统一事件时间，统一窗口边界 | 离线特征偏高/偏低 |
| **同一份样本** | 线上决策日志回流，作为训练样本 | 训练分布与线上分布漂移 |

## 决策：规则、模型、融合

| 方式 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **规则** | 可解释、可快速上线 | 覆盖有限、易被绕过 | 硬约束（限额、名单） |
| **模型** | 覆盖广、能发现组合特征 | 不可解释、需要样本、会漂移 | 软判断（欺诈概率） |
| **融合** | 规则兜底 + 模型排序 | 架构更复杂 | 大多数生产系统 |

时延预算见 [68.1 风控系统架构](68.1-风控系统架构.md)：模型打分是最重的一段，必须有降级路径（模型超时 → 规则兜底）。

## 特征新鲜度 vs 决策质量

离线、近线、实时三档特征的分界线，不是「技术新旧」，而是**信息半衰期**：一条特征的价值衰减到一半所需的时间。半衰期短于一次决策的间隔，就必须放进请求里；半衰期以小时、天计，离线或准实时就够了。这句话要落地，得回答两个数：每档特征值多少 AUC 和拦截率，以及等它要花多少毫秒。用 10 万条样本做消融，再把「等待预算」扫成三组参数，两个数就摆在同一张表里了。

> 仿真设定：10 万条样本、欺诈率 2.02%；三档特征观测同一个潜在风险，各自带噪声并共享一部分「模型无法消除的个体差异」；实时特征 P99 约 5ms、准实时特征现算中位 12ms、P99 77ms。消融 = 每次去掉一档，看 AUC 与固定误杀率 1% 下的拦截率。本机仿真，固定随机种子 7。

| 特征档 | 数据新鲜度 | 单次决策成本（延迟占用） | AUC 增量（消融） | 拦截率增量（FPR=1%） | 典型特征 |
|---|---|---|---|---|---|
| 离线（T+1） | 1–24 小时 | <1ms | 基线 0.827 | 基线 11.0% | 历史逾期、用户等级、商户月交易额 |
| 实时（请求内/预聚合） | ≤5 毫秒 | 2–6ms | **+0.014**（0.827→0.841） | **+1.8pp**（11.0%→12.8%） | 本次金额、收款方、设备指纹、当前 IP |
| 准实时（流式） | 10–60 秒 | 现算 12–77ms；预计算后读 1–3ms | **+0.011**（0.841→0.852） | **+1.1pp**（12.8%→13.9%） | 近 1 小时笔数、近 24 小时设备数、团伙簇 |

这组消融数字来自 [tools/examples/68.3-feature-ablation/](../../../tools/examples/68.3-feature-ablation/README.md)，`go run .` 可复现。

边际价值一栏就是「这一档值不值得为它多花延迟」的答案：实时档用 2–6ms 换 +0.014 AUC 和 +1.8pp 拦截率；准实时档的 AUC 增量与实时档同一个量级（+0.011），但请求内现算要 12–77ms，差了一个数量级。**同样的价值、不同的成本，决定了它们该放在链路的哪一段。**

把准实时特征的等待预算 W 从 10ms 扫到 80ms，「决策覆盖率」就是准实时特征在 W 内就绪、决策能用上全量特征的请求占比，代价就更清楚了：

| 等待预算 W | 决策覆盖率（准实时就绪） | 有效 AUC | 拦截率@FPR1% | 端到端 P50 | 端到端 P99 | 读法 |
|---|---|---|---|---|---|---|
| 10ms | 41.0% | 0.847 | 12.9% | 17.0ms | 17.0ms | 基本只等到实时档 |
| 30ms | 87.3% | 0.851 | 13.5% | 19.0ms | 37.0ms | 覆盖 87%，仍有 13% 降级 |
| 80ms | 99.1% | 0.851 | 13.9% | 19.0ms | 84.4ms | 覆盖 99%，P99 吃掉 84% 预算 |
| 预计算（读 2ms） | 100% | 0.852 | 13.9% | 9.0ms | 12.0ms | 质量一样，P99 只有 1/7 |

```go
// 等待预算 W：准实时特征在 W 内就绪就用三档，否则只用离线 + 实时两档（降级决策）。
for _, w := range []float64{10, 30, 80} {
	scores := make([]float64, n)
	lats := make([]float64, n)
	ready := 0
	for i, s := range samples {
		hasNRT := s.nrtLat <= w // 准实时特征是否在预算内就绪
		if hasNRT {
			ready++
		}
		sum, k := s.off+s.rt, 2.0
		if hasNRT {
			sum += s.nrt
			k++
		}
		scores[i] = sum / k // 有效分数：只对已就绪的特征取平均
		wait := s.nrtLat
		if wait > w {
			wait = w // 没就绪就等到 W 为止，然后降级决策
		}
		lats[i] = wait + fixed
	}
	coverage := 100 * float64(ready) / float64(n)
	fmt.Printf("W=%-7.0f %8.1f%% %9.3f %13.1f%% %7.1f %8.1f\n",
		w, coverage, auc(scores, fraud), recallAtFPR(scores, fraud, 0.01), pct(lats, 50), pct(lats, 99))
}
```

本机仿真输出（`go1.27.1 / darwin/arm64 / Apple M1`）：

```text
=== 消融：三档特征对排序质量的影响（100000 条，欺诈率 2.02%；本机仿真） ===
特征集合                        AUC      拦截率@FPR1%
仅离线(off)                  0.827          11.0%
离线+实时(off+rt)             0.841          12.8%   (ΔAUC=+0.014, Δ拦截=+1.8pp)
全量(off+rt+nrt)            0.852          13.9%   (ΔAUC=+0.011, Δ拦截=+1.1pp)

=== 决策等待预算 W：覆盖率 / 有效 AUC / 拦截率 / 端到端延迟 ===
W               覆盖率     有效AUC      拦截率@FPR1%      P50      P99
W=10          41.0%     0.847          12.9%    17.0     17.0
W=30          87.3%     0.851          13.5%    19.0     37.0
W=80          99.1%     0.851          13.9%    19.0     84.4
预计算          100.0%     0.852          13.9%     9.0     12.0  ← 预计算：准实时特征按“读”处理
```

这三个读法决定了特征该怎么摆：

- **等待换覆盖率，边际收益极低**：W 从 10ms 到 80ms，覆盖率从 41.0% 涨到 99.1%（+58.1pp），有效 AUC 只从 0.847 涨到 0.851（+0.004），拦截率涨 1.0pp。为最后 1% 的覆盖多等 67ms，占掉 84% 的端到端预算，不值。
- **同一份质量，预计算把 P99 从 84.4ms 压到 12.0ms（7 倍）**：准实时特征不是没用，而是它的价值必须通过「离线/近线预计算成读」兑现，不能通过「请求里等它算完」兑现。这条是最该记住的工程结论。
- **折成每毫秒 AUC 增量**：实时档 0.014 AUC / 2–6ms ≈ 0.0023–0.007 每毫秒；准实时现算 0.011 / 12–77ms ≈ 0.00014–0.0009 每毫秒，差 3–50 倍。实时档放进请求，准实时档放到预计算，不是偏好，是算出来的。

延迟差还能换算成机器成本。按利特尔法则，在途请求数 = QPS × 延迟；假设决策 QPS 2 万，准实时特征现算 12ms 需要 20000 × 0.012 = 240 个并发请求同时挂着，预计算后读 2ms 只需 40 个，差 200 个并发的资源。实时档 2–6ms 对应 40–120 个并发，属于可以承受的量级。预计算当然不是免费的：要常驻流式作业、要存特征、要做离线/在线一致性校验（口径统一靠 [64.1 特征平台](../../L4-组件与技术/64-机器学习系统/64.1-特征平台.md)），成本从「延迟预算」转移到了「资源与工程复杂度」——但用 200 个并发换 67ms 的 P99，通常仍是划算的那一边。

**哪些特征必须实时**，三条判据按顺序卡：

1. **决策对象本身**：本次金额、收款方、渠道、设备指纹、当前 IP。请求里不取就没有，没有替代来源——必须实时。
2. **信息半衰期 ≤ 一次决策间隔**：近 5 分钟交易频次（半衰期 5 分钟）、本次设备是否首次出现。过期就失真，必须实时或秒级预聚合。
3. **每毫秒 AUC 增量 ≥ 0.002**：按上面的折算，只有「高信号 + 低成本」的特征能过线。过不了线的，即使信号强，也应该预计算成读，而不是现算。

| 特征 | 信息半衰期 | 计算/更新方式 | 该放哪一档 |
|---|---|---|---|
| 本次金额、收款方、渠道 | 0（只对本笔有效） | 请求内直接取 | 实时（不取就没有） |
| 设备指纹、当前 IP 风险 | 一次会话（分钟级） | 请求内 2–6ms | 实时（高信号、低成本） |
| 近 5 分钟交易频次 | 5 分钟 | 秒级预聚合，读 <1ms | 实时（半衰期 < 决策间隔） |
| 近 1 小时笔数/金额 | 1 小时 | 分钟级流式聚合，预计算 | 准实时：预计算成读，不能现算 |
| 近 24 小时设备数 | 1 天 | 小时级 | 准实时/离线 |
| 历史逾期、用户等级 | 月级 | T+1 批处理 | 离线（<1ms 读） |

怎么验证一档特征的新鲜度够不够？做一次「时间截断回放」：把该档特征的取值统一回退到决策前 N 分钟，再跑同一批历史样本，看拦截率掉多少。掉 1pp 以内，说明这档特征对新鲜度不敏感，可以降档；掉 5pp 以上，说明它的价值高度依赖时效，必须实时或缩短预计算链路。这个回放比上线后做 A/B 便宜得多，也是「该不该实时」最直接的证据。

半衰期怎么估？有数据时用「特征值随时间的相关性衰减」估：取同一用户相隔 Δt 的两个特征值，算相关系数，降到 0.5 所用的 Δt 就是半衰期。没有数据时按业务节律先估一个量级：分钟级（频次、当前设备）→ 实时；小时级（1 小时/24 小时窗口）→ 准实时预计算；天/月级（等级、历史逾期）→ 离线。估错的代价不对称：把短半衰期特征放到离线，效果直接崩；把长半衰期特征放到实时，只是白花几毫秒——所以宁可先按短的估，再逐档往下降。

一句话总结三档的定位：**实时档买的是「及时」，准实时档买的是「覆盖」，离线档买的是「稳定」**。及时的特征必须在请求内，覆盖的特征必须预计算，稳定的特征必须离线——三者的成本结构不同，不能用一个「实时化」的口号抹平。

> 🔑 判据：特征放哪一档，看**信息半衰期**与**每毫秒 AUC 增量**，不看「别人都上了实时」。半衰期短的必须实时；半衰期长的等一等不会变差；中间那档一律预计算成读。

> 🔑 不要用「多等一会儿」提高覆盖率：等来的是延迟预算的消耗，换来的 AUC 边际值（每毫秒 0.0001–0.0009）比重算/预计算低一个数量级。准实时特征的正确形态是「流式算好、请求里读」，不是「请求里算」。

## 反模式

| 反模式 | 后果 |
|---|---|
| 训练用了预测时点之后的数据 | 离线指标虚高，上线效果崩 |
| 离线/在线各写一套特征 | 数值对不上，模型行为不可预期 |
| 在请求里现算窗口聚合 | 延迟随流量放大，拖垮主链路 |
| 窗口边界不统一 | 同一笔被重复计入相邻窗口 |
| 只上模型、不留规则兜底 | 模型服务抖动 = 风控失效 |
| 特征不做监控 | 特征分布漂移无人发现，效果悄悄下降 |
| 用处理时间替代事件时间 | 延迟数据算错窗口，频次判断失真 |

## 自检

**Q1** 为什么“离线 AUC 很高”不能保证线上效果？

▸ 答案：因为离线评估可能犯了特征穿越（用了未来数据）或口径不一致（离线窗口与线上不同）。这类问题在离线看不出来，上线后特征值分布与训练分布不同，模型行为立刻偏离。所以上线前必须做“离线/在线特征一致性校验”。

**Q2** 实时特征为什么“能近线就不实时”？

▸ 答案：因为请求内计算会随流量放大，且窗口聚合需要状态，做在请求里既慢又难一致。近线流式聚合把计算前置，请求只做“读 + 比较”，既保证延迟，也保证离线/在线用同一份聚合结果。

**Q3** 滑动窗口的两个“边界”分别指什么？

▸ 答案：一是**时间边界**（`<=` 还是 `<`，避免同一笔被两个窗口重复计入）；二是**口径边界**（事件时间还是处理时间，决定延迟到达的数据算进哪个窗口）。两者不统一，频次类特征就会忽高忽低。

**Q4** 规则和模型在风控里怎么分工？

▸ 答案：规则管“硬约束”（黑名单、限额、频次），要求可解释、可快速上线；模型管“软判断”（欺诈概率、团伙相似度），覆盖规则想不到的组合。生产上通常融合：规则先短路，模型对剩余请求打分，模型超时则降级为规则兜底。

**Q5** 特征监控该看什么？

▸ 答案：看分布而不是看单值：均值/分位数漂移、缺失率、取值越界比例。特征分布漂移往往先于效果下降出现，是最早的预警信号；只监控“服务是否存活”发现不了效果衰减。
