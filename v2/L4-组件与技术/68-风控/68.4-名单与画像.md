# 68.4 名单与画像

## 一句话

> 名单是“已知坏人的黑名单”，画像是“未知人群的概率描述”；名单要求**快、准、可解释**，画像要求**覆盖、可圈选**——两者都不是“越多越好”，而是每一条都要有**来源、有效期、申诉通道**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 名单越多越安全 | 名单越大，误伤越多；没有证据与有效期的名单会迅速腐烂 |
| 画像 = 用户标签堆砌 | 标签没有口径、没有更新频率、没有来源，圈出来的人群就是错的 |
| 名单一旦加入就永久有效 | 攻击者会换号，正常用户会被误判；没有退出机制的名单就是永久误伤 |

## 名单：三种颜色，三种动作

| 名单 | 动作 | 加入依据 | 有效期 |
|---|---|---|---|
| **黑名单** | 直接拒绝/阻断 | 确认的攻击、作弊、违规 | 长（需申诉） |
| **白名单** | 跳过后续规则 | 可信商户、内部账号 | 定期复核 |
| **灰名单** | 降额、加验证、人工复核 | 疑似但未确认 | 短（7–30 天） |

```go
// 名单匹配：黑名单拒绝、白名单放行、灰名单降额/复核；优先级高于规则。
switch {
case black[req.user] || black[req.device]:
	fmt.Println("命中黑名单 → 直接拒绝")
case white[req.user]:
	fmt.Println("命中白名单 → 放行（跳过后续规则）")
case grey[req.ip]:
	fmt.Println("命中灰名单 → 降额或人工复核")
default:
	fmt.Println("未命中名单 → 进入规则引擎")
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
命中黑名单 → 直接拒绝
```

名单在规则引擎里优先级最高（[68.2 规则引擎](68.2-规则引擎.md)），因为它是**确定性事实**：命中就不需要再算特征、跑模型。

## 名单的存储：快，但别牺牲可管理

| 载体 | 查询延迟 | 适用 | 代价 |
|---|---|---|---|
| 进程内内存 | 纳秒–微秒 | 高频、小名单（万级） | 更新要广播 |
| Redis | 亚毫秒 | 中大名单（百万级） | 多一次网络往返 |
| **布隆过滤器** | 微秒 | 超大名单（亿级） | **有假阳性**，只能“疑似” |
| 数据库 | 毫秒–几十毫秒 | 后台管理、审计 | 不能放主链路 |

> ⚠️ 布隆过滤器说“不在”一定准，说“在”可能是误判（[41.8 布隆过滤器](../../L4-组件与技术/41-缓存/41.8-布隆过滤器.md)）。所以它只能用于**第一层粗筛**：命中后必须回源确认，不能直接拒绝。

## 名单治理：四条硬规则

| 规则 | 做法 | 不做的后果 |
|---|---|---|
| **有来源** | 每条记录带证据（订单号/设备/规则命中） | 无法申诉，也无法复盘 |
| **有有效期** | 黑名单 90 天复审，灰名单 7–30 天 | 名单腐烂，误伤累积 |
| **有申诉** | 用户可提交申诉，工单闭环 | 误伤无出口，客诉升级 |
| **有审计** | 谁加的、谁删的、依据什么 | 内部滥用无法追责 |

## 画像：标签体系而不是标签堆

| 维度 | 例子 | 更新频率 | 用途 |
|---|---|---|---|
| **用户** | 注册时长、历史逾期、消费能力 | 天 | 授信、限额 |
| **设备** | 机型、系统、是否模拟器 | 实时/天 | 设备风险 |
| **商户** | 行业、类目、退款率 | 天 | 商户风险 |
| **团伙** | 共用设备/IP/支付账号的簇 | 小时 | 团伙识别 |

画像的使用方式是**圈选**：按标签组合圈出一批人，再交给规则或模型。圈选的两个坑：

- **标签口径不一致**：同一个“高价值用户”在运营与风控里定义不同，圈出来的人群对不上；
- **标签过期**：用三个月前的标签做今天的决策，等于用旧地图找新路。

## 反模式

| 反模式 | 后果 |
|---|---|
| 名单没有有效期 | 误伤永久化，名单越滚越脏 |
| 布隆命中直接拒绝 | 假阳性直接变成误杀 |
| 名单查询走数据库 | 主链路延迟翻倍 |
| 标签没有口径文档 | 同一个标签两种含义，圈选结果不可信 |
| 画像只进不出 | 标签只增不删，人群越来越不准 |
| 名单加入无审计 | 内部人员可滥用名单 |
| 没有申诉通道 | 误伤用户无处申诉，客诉升级 |

## 自检

**Q1** 为什么布隆过滤器命中后还要回源确认？

▸ 答案：因为布隆过滤器有假阳性：它说“不在”一定准，说“在”可能是误判。名单是“直接拒绝”这种高代价动作，假阳性就是误杀，所以布隆只能做第一层粗筛，命中后回源（Redis/DB）确认。

**Q2** 黑名单和灰名单的差别只在“程度”吗？

▸ 答案：不只是程度，是**动作不同**：黑名单直接拒绝（确定性事实），灰名单降额/加验证/转人工（疑似）。动作不同，意味着误判代价不同：黑名单误判是“用户被拒”，灰名单误判只是“多一步验证”。所以灰名单的有效期更短、复审更频繁。

**Q3** 名单为什么必须有有效期与申诉？

▸ 答案：因为攻击者会换号、正常用户会被误判，名单不可能是“永久真相”。没有有效期，误伤会永久累积；没有申诉，误伤用户没有出口，客诉会升级。有效期 + 申诉 = 名单的自我纠错机制。

**Q4** 画像的“圈选”最容易出什么问题？

▸ 答案：两个：标签口径不一致（同一标签在运营与风控里定义不同）与标签过期（用旧标签做新决策）。解法是给每个标签写清口径、更新频率与来源，并给标签设“保质期”，过期标签降权或不用。

**Q5** 名单与画像在风控里怎么配合？

▸ 答案：名单管“已知的确定性事实”（命中即短路），画像管“未知的概率判断”（圈出高风险人群，交给规则/模型打分）。顺序上名单在前（快、便宜、确定），画像在后（贵、需要计算）。两者都只是输入，最终决策仍要经过规则与模型。
