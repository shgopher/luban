# 68.1 风控系统架构

## 一句话

> 风控系统不是一个“服务”，而是一条**决策流水线**：事件采集 → 名单/特征 → 规则/模型 → 决策 → 处置 → 反馈；它的核心指标不是“准确率”，而是**在时延预算内做出可解释的拒绝**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 风控 = 一个模型 | 模型只是流水线中的一段；名单、规则、特征、处置缺一不可 |
| 风控 = 拦截 | 拦截只是处置动作之一；放行、降额、二次验证、人工复核都是处置 |
| 风控可以离线跑 | 登录/交易必须实时决策，离线只能做“事后补查” |

## 决策点决定架构

| 决策点 | 时延预算 | 失败代价 | 失败策略 |
|---|---|---|---|
| **登录** | P99 ≤ 100ms | 用户登不进 | fail-open（放行 + 告警） |
| **交易支付** | P99 ≤ 50–100ms | 资损或掉单 | 按金额分级：小额放行、大额拒绝/转人工 |
| **营销领券** | ≤ 200ms | 被刷走预算 | fail-close（拒绝） |
| **内容发布** | 异步可接受 | 违规内容扩散 | 先审后发 / 先发后审 |

> 🔑 同一套风控组件，在不同决策点上的失败策略可能完全相反——**交易风控挂了大额要拒绝，登录风控挂了要放行**。这不是双标，是代价不同。

## 六段流水线

```mermaid
flowchart LR
    A[事件采集<br/>设备/行为/交易] --> B[名单<br/>黑/白/灰]
    B --> C[实时特征<br/>窗口/序列]
    C --> D[规则引擎<br/>优先级短路]
    D --> E[模型打分<br/>可选]
    E --> F[决策<br/>通过/拒绝/复核]
    F --> G[处置<br/>降额/验证/阻断]
    G --> H[反馈<br/>申诉/样本回流]
```

| 段 | 同步/异步 | 说明 |
|---|---|---|
| 事件采集 | 同步 | 只采必要字段，别在主链路做重活 |
| 名单 | 同步（内存/Redis） | 命中即短路，优先级最高 |
| 实时特征 | 同步（预计算 + 读） | 窗口类特征要么预计算，要么异步补 |
| 规则引擎 | 同步 | 几十条规则，毫秒级 |
| 模型打分 | 同步或异步 | 大模型打分通常几十毫秒，超预算就降级为“规则兜底” |
| 决策与落库 | 同步 | 落决策日志，供事后解释与回放 |

## 时延预算：先算，再设计

```go
// 风控决策时延预算：各阶段 P99 相加，超过预算就必须异步化。
stages := []struct{ name string; p99 float64 }{
	{"参数校验", 1}, {"名单查询", 2}, {"实时特征", 8},
	{"规则引擎", 5}, {"模型打分", 25}, {"决策与落库", 6},
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
参数校验           1 ms
名单查询           2 ms
实时特征           8 ms
规则引擎           5 ms
模型打分          25 ms
决策与落库          6 ms
合计 47 ms；预算 100 ms → 在预算内
```

完整代码在仓库 [tools/examples/68.1-riskbudget/](../../../tools/examples/68.1-riskbudget/README.md)，`go run .` 可复现这段输出。

读法：**模型打分占了 25ms，是最大的一段**。一旦它涨到 80ms，整条链路就超预算——所以模型必须能降级（规则兜底），不能成为单点。

## 可解释性：每条决策都要能复述

| 要记录 | 为什么 |
|---|---|
| 命中的规则/模型版本 | 客诉时说得出“为什么拒绝” |
| 关键特征值（窗口笔数、名单命中） | 复现与回放 |
| 决策结果与处置动作 | 区分“拒绝了”与“只降额” |
| 请求上下文（设备/IP/渠道） | 团伙分析 |

> ⚠️ 只记录“拒绝”不记录原因，等于把风控做成黑盒：客诉无法解释，规则调错也无法回溯。

## 一次决策的延迟预算

同页「时延预算：先算，再设计」给出的 47ms，是把各段 P99 直接相加得到的静态值：参数校验 1 + 名单 2 + 实时特征 8 + 规则 5 + 模型 25 + 落库 6。静态相加能用来看「数量级对不对」，但不能直接当预算用——真实决策是一条分布：每段都有长尾，长尾不一定同时出现，端到端 P99 既不等于各段 P99 相加，也不能靠「每段都不超」保证。把 4 个可观测段（设备指纹、名单、规则、模型）加固定开销 7ms（参数校验 1 + 决策落库 6）建成一条带 deadline 的流水线，跑 10,000 次决策，才能同时看到 P50/P99、分段超时率与端到端超时率。

> 仿真参数：设备指纹中位 2ms、名单 1.2ms、规则 3ms、模型中位 22ms（P99 43.7ms，比同页静态表的 25ms 保守，因为长尾才是预算要防的），每段用对数正态分布；固定随机种子 42，本机仿真。

| 段 | 基线 P50 | 基线 P99 | 分段预算 | P99/预算 | 超时降级动作 |
|---|---|---|---|---|---|
| 设备指纹 | 2.0ms | 6.4ms | 8ms | 80% | 用缓存指纹 + 标记 `feature_missing`，规则层补一条「缺指纹」判据 |
| 名单 | 1.2ms | 2.9ms | 5ms | 58% | 按未命中处理 + 告警；大额交易转人工复核兜底 |
| 规则 | 3.0ms | 9.6ms | 12ms | 80% | 跳过规则，模型分兜底 |
| 模型 | 22.0ms | 43.7ms | 60ms | 73% | 规则兜底，额外 +3ms |
| 固定开销（校验 1 + 落库 6） | 7.0ms | 7.0ms | — | — | 同步只写最小决策记录；全量日志与样本异步 |
| 各段 P99 之和 + 固定 | — | **69.6ms** | 85ms + 7ms = 92ms | — | 端到端实际 P99 58.3ms（长尾不同时发生） |

读表先建立一个反直觉事实：各段 P99 之和是 69.6ms，端到端实际 P99 只有 58.3ms，差了 11.3ms（16%）。因为四段的长尾不会同时踩满——某次请求模型慢，名单往往正常；下一次反过来。但这只是「平均而言不同时」，大促、机房抖动、GC 会让多段同时变慢，端到端 P99 就会向 69.6ms 靠拢，甚至更高。所以预算判据要留 20% 余量，而不是拿「P99 之和」直接卡 100ms。

分段 deadline 也不是免费的：它把「慢请求」变成「降级请求」。本仿真里每次降级都意味着少一段信息（模型超时用规则兜底、名单超时按未命中），所以 deadline 的代价是决策质量，不是零成本。定分段预算时，实际 P99 × 1.2–1.5 是比较稳的做法：模型段 P99 43.7ms，乘 1.37 得到 60ms 的分段预算，既容得下日常抖动，又不至于让降级变成常态。

这张表要过三道判据才算「算过预算」：

1. **分段预算之和 + 固定开销 ≤ 总预算**：92ms ≤ 100ms，留 8ms 给没被建模的抖动；
2. **各段仿真 P99 之和 + 固定开销 ≤ 总预算 × 0.8**：69.6ms ≤ 80ms。取 0.8 而不是 1.0，是因为单段 P99 独立统计、端到端 P99 有相关性叠加——大促时全链路一起抖，相加会逼近上界，必须留 20% 余量；
3. **单段 P99 不超过其分段预算的 85%**：本仿真最高 80%（设备指纹、规则），模型 73%。超过 85% 说明该段没有余量吸收抖动，下一次流量高峰就会成为整条链路的瓶颈。

```go
// run 对同一批原始延迟应用不同配置：deadline 是否生效、模型是否劣化。
func run(name string, raw [][4]float64, deadline bool) result {
	totals := make([]float64, 0, n)
	timeouts, degraded, modelTO := 0, 0, 0
	for _, r := range raw {
		total := fixedCost
		for i, v := range r {
			if deadline && v > segs[i].limit {
				degraded++              // 该段超预算：走降级，不阻塞主链路
				if i == 3 {
					modelTO++
					total += segs[i].limit + modelRetry // 模型超时 → 规则兜底 +3ms
				} else {
					total += segs[i].limit
				}
				continue
			}
			total += v
		}
		if total > budget {
			timeouts++
		}
		totals = append(totals, total)
	}
	return result{
		name: name, p50: pct(totals, 50), p99: pct(totals, 99),
		timeoutRt: 100 * float64(timeouts) / n,
		degradeRt: 100 * float64(degraded) / n,
		modelTO:   100 * float64(modelTO) / n,
	}
}
```

本机仿真输出（`go1.27.1 / darwin/arm64 / Apple M1`）：

```text
=== 端到端：P50 / P99 / >100ms 超时率 / 分段降级率 ===
场景                           P50     P99       超时率       分段降级率     其中模型超时
A 基线·无分段deadline           36.0    58.3     0.00%        0.0%       0.0%
B 基线·分段deadline            36.0    58.3     0.00%        0.6%       0.0%
C 模型×3·无分段deadline         80.1   145.6    18.97%        0.0%       0.0%
D 模型×3·分段deadline          75.3    83.2     0.00%       63.4%      62.8%
```

四个场景要放在一起读，才能看出 deadline 到底买到了什么：

- **A→B**：正常情况下分段 deadline 几乎不触发（降级率 0.6%，模型 0%），P50/P99 完全不变。降级是保险，不是常态——如果平时降级率就超过 1%，说明分段预算定得太紧，该扩容量而不是继续压预算。
- **C**：模型劣化 3 倍（中位 66ms、P99 131ms）且没有分段 deadline，18.97% 的请求端到端超过 100ms，P99 到 145.6ms。**一段慢，整条链路跟着慢**——这正是「模型打分必须有降级路径」的量化理由。
- **D**：开了分段 deadline 后超时率降到 0，P99 压回 83.2ms；代价是 63.4% 的请求至少一段降级、其中模型降级 62.8%。主链路活着，但大半决策已经不是全量信息。
- 所以 **超时率与降级率必须一起看**：超时率衡量「主链路会不会被拖垮」，降级率衡量「决策质量会不会被稀释」。超时率 0 而降级率 60% 不是成功，是「风控名义在线、实际靠规则兜底」，该做的是模型扩容或版本回滚。

还有一个常被放过的成本项：固定开销。本仿真里它是 7ms（参数校验 1 + 决策落库 6），占端到端 P50 的 19%。落到工程上，同步只写「谁、何时、结果、命中」这一条最小决策记录（约 1ms），把全量日志、特征快照、样本回流放到消息队列异步落库，整条延迟分布就左移约 5ms：P50 从 36.0ms 降到约 31ms，P99 从 58.3ms 降到约 53.3ms。5ms 在 100ms 预算里不算小，而且它买不到任何决策质量——这类「不影响决策、只影响事后」的开销，优先级应该排在降级与预计算之后，但一定要排进预算。

**哪段该异步**，不要凭感觉，按四条判据过：

| 判据 | 本仿真算例 | 处理 |
|---|---|---|
| 不返回就无法决策（决策关键路径） | 名单、规则、模型 | 必须同步，不能异步 |
| 段 P99 占端到端 P99 的比例 ≥ 30% | 模型 43.7 / 58.3 = 75% | 独立 deadline + 可降级 + 单独监控该段 P99 |
| 失败可无损降级 | 模型→规则兜底；设备指纹→缓存指纹 | 同步 + deadline；降级路径要定期演练，不能只写在文档里 |
| 失败不可降级 | 名单查询（不能当成「未命中」直接放行） | 只能同步 + 本地副本/多级缓存，用冗余换可用性，不能靠异步 |
| 只影响解释、审计、样本 | 全量决策日志、特征快照、样本回流、名单刷新、报表 | 异步：同步只落最小决策记录（谁、何时、结果、命中） |
| 可预计算 | 窗口特征、画像标签 | 移到近线，请求内只读（[68.3 实时特征与决策](68.3-实时特征与决策.md)） |

分预算的定法可以写成一条公式：**分段预算 = 该段线上 P99 × (1.2–1.5)**；总预算则从业务 SLA 倒推——支付确认 P99 ≤ 100ms，减去网络与业务处理余量后剩多少给风控，才是风控真正能用的数。先有线上 P99，再乘系数，最后校验「分预算之和 + 固定 ≤ 总预算」；反过来先拍一个 100ms 再往里塞段，必然有一段被挤到没有余量。

判断顺序也有讲究：预算超了，**先降级（不改决策语义）→ 再预计算（改实现）→ 最后才异步（改语义）**。顺序反了会出大问题：先把「名单查询」异步出去，名单没回来就决策，等于把名单层删掉；先把「模型」异步出去，实时打分就变成了事后补分。

> 🔑 延迟预算不是「各段 P99 之和小于 100ms」就算完：要同时满足「分预算和不超总预算」「P99 之和不超预算的 80%」，并为每段写出可执行、可演练的超时降级动作。没有降级动作的段，就是全链路单点。

> 🔑 模型段最该被异步吗？不是。模型在决策关键路径上，异步化等于放弃实时打分；正确做法是「独立 deadline + 规则兜底 + 特征预计算」，把等待压进预算，而不是把模型移出主链路。

## 反模式

| 反模式 | 后果 |
|---|---|
| 风控同步调用第三方情报 | 第三方抖动 = 你抖动，且挡不住换 IP 的攻击者 |
| 模型打分无法降级 | 模型一慢，主链路全慢 |
| 决策不记录命中原因 | 客诉无法解释，规则无法复盘 |
| 所有决策点共用一套失败策略 | 登录 fail-close 会把用户挡在门外 |
| 名单查询走数据库 | 主链路多一次 DB 往返，P99 直接翻倍 |
| 特征在请求里现算 | 窗口聚合拖慢决策，且随流量放大 |
| 风控与业务强耦合（业务代码里 if-else） | 规则一变就要发版 |

## 自检

**Q1** 为什么登录风控和交易风控的失败策略可以相反？

▸ 答案：因为失败代价不同。登录风控挂了如果 fail-close，等于把用户挡在门外，攻击者只要打满风控就能让全站登不进；交易风控挂了大额如果 fail-open，等于给攻击者开窗。所以登录 fail-open + 告警，交易按金额分级。

**Q2** 时延预算里，为什么模型打分最该被设计成“可降级”？

▸ 答案：因为它是链路上最重的一段（示例占 25ms，超过其他段总和的一半），且受特征、模型复杂度、流量影响大。不可降级就意味着“模型一慢，支付就慢”；可降级（规则兜底）能保证主链路始终在预算内。

**Q3** 风控为什么要记录“命中了什么”，而不只记录“拒绝了”？

▸ 答案：三个用途：客诉解释（为什么拒绝）、规则复盘（这条规则是不是误杀太多）、样本回流（哪些是真实攻击）。只记录结果，风控就是黑盒，既无法优化也无法自证。

**Q4** 名单查询为什么不能直接查数据库？

▸ 答案：因为它在主链路上，多一次 DB 往返就是几毫秒到几十毫秒，且流量一上来 DB 先成为瓶颈。名单应该放内存/Redis，命中即短路；数据库只作为名单的持久化与后台管理。

**Q5** 风控规则为什么不该写成业务代码里的 if-else？

▸ 答案：因为规则的变更频率远高于业务代码：今天加一条限额、明天改一个阈值。写死在业务里意味着每次调整都要发版、回归、上线；做成规则引擎 + 配置，才能做到“改规则不发版、可灰度、可回滚”。
