# 68.1 风控系统架构

## 一句话

> 风控系统不是一个“服务”，而是一条**决策流水线**：事件采集 → 名单/特征 → 规则/模型 → 决策 → 处置 → 反馈；它的核心指标不是“准确率”，而是**在时延预算内做出可解释的拒绝**。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 风控 = 一个模型 | 模型只是流水线中的一段；名单、规则、特征、处置缺一不可 |
| 风控 = 拦截 | 拦截只是处置动作之一；放行、降额、二次验证、人工复核都是处置 |
| 风控可以离线跑 | 登录/交易必须实时决策，离线只能做“事后补查” |

## 决策点决定架构

| 决策点 | 时延预算 | 失败代价 | 失败策略 |
|---|---|---|---|
| **登录** | P99 ≤ 100ms | 用户登不进 | fail-open（放行 + 告警） |
| **交易支付** | P99 ≤ 50–100ms | 资损或掉单 | 按金额分级：小额放行、大额拒绝/转人工 |
| **营销领券** | ≤ 200ms | 被刷走预算 | fail-close（拒绝） |
| **内容发布** | 异步可接受 | 违规内容扩散 | 先审后发 / 先发后审 |

> 🔑 同一套风控组件，在不同决策点上的失败策略可能完全相反——**交易风控挂了大额要拒绝，登录风控挂了要放行**。这不是双标，是代价不同。

## 六段流水线

```mermaid
flowchart LR
    A[事件采集<br/>设备/行为/交易] --> B[名单<br/>黑/白/灰]
    B --> C[实时特征<br/>窗口/序列]
    C --> D[规则引擎<br/>优先级短路]
    D --> E[模型打分<br/>可选]
    E --> F[决策<br/>通过/拒绝/复核]
    F --> G[处置<br/>降额/验证/阻断]
    G --> H[反馈<br/>申诉/样本回流]
```

| 段 | 同步/异步 | 说明 |
|---|---|---|
| 事件采集 | 同步 | 只采必要字段，别在主链路做重活 |
| 名单 | 同步（内存/Redis） | 命中即短路，优先级最高 |
| 实时特征 | 同步（预计算 + 读） | 窗口类特征要么预计算，要么异步补 |
| 规则引擎 | 同步 | 几十条规则，毫秒级 |
| 模型打分 | 同步或异步 | 大模型打分通常几十毫秒，超预算就降级为“规则兜底” |
| 决策与落库 | 同步 | 落决策日志，供事后解释与回放 |

## 时延预算：先算，再设计

```go
// 风控决策时延预算：各阶段 P99 相加，超过预算就必须异步化。
stages := []struct{ name string; p99 float64 }{
	{"参数校验", 1}, {"名单查询", 2}, {"实时特征", 8},
	{"规则引擎", 5}, {"模型打分", 25}, {"决策与落库", 6},
}
```

真实输出（本机 `go1.27.1 darwin/arm64`）：

```text
参数校验           1 ms
名单查询           2 ms
实时特征           8 ms
规则引擎           5 ms
模型打分          25 ms
决策与落库          6 ms
合计 47 ms；预算 100 ms → 在预算内
```

读法：**模型打分占了 25ms，是最大的一段**。一旦它涨到 80ms，整条链路就超预算——所以模型必须能降级（规则兜底），不能成为单点。

## 可解释性：每条决策都要能复述

| 要记录 | 为什么 |
|---|---|
| 命中的规则/模型版本 | 客诉时说得出“为什么拒绝” |
| 关键特征值（窗口笔数、名单命中） | 复现与回放 |
| 决策结果与处置动作 | 区分“拒绝了”与“只降额” |
| 请求上下文（设备/IP/渠道） | 团伙分析 |

> ⚠️ 只记录“拒绝”不记录原因，等于把风控做成黑盒：客诉无法解释，规则调错也无法回溯。

## 反模式

| 反模式 | 后果 |
|---|---|
| 风控同步调用第三方情报 | 第三方抖动 = 你抖动，且挡不住换 IP 的攻击者 |
| 模型打分无法降级 | 模型一慢，主链路全慢 |
| 决策不记录命中原因 | 客诉无法解释，规则无法复盘 |
| 所有决策点共用一套失败策略 | 登录 fail-close 会把用户挡在门外 |
| 名单查询走数据库 | 主链路多一次 DB 往返，P99 直接翻倍 |
| 特征在请求里现算 | 窗口聚合拖慢决策，且随流量放大 |
| 风控与业务强耦合（业务代码里 if-else） | 规则一变就要发版 |

## 自检

**Q1** 为什么登录风控和交易风控的失败策略可以相反？

▸ 答案：因为失败代价不同。登录风控挂了如果 fail-close，等于把用户挡在门外，攻击者只要打满风控就能让全站登不进；交易风控挂了大额如果 fail-open，等于给攻击者开窗。所以登录 fail-open + 告警，交易按金额分级。

**Q2** 时延预算里，为什么模型打分最该被设计成“可降级”？

▸ 答案：因为它是链路上最重的一段（示例占 25ms，超过其他段总和的一半），且受特征、模型复杂度、流量影响大。不可降级就意味着“模型一慢，支付就慢”；可降级（规则兜底）能保证主链路始终在预算内。

**Q3** 风控为什么要记录“命中了什么”，而不只记录“拒绝了”？

▸ 答案：三个用途：客诉解释（为什么拒绝）、规则复盘（这条规则是不是误杀太多）、样本回流（哪些是真实攻击）。只记录结果，风控就是黑盒，既无法优化也无法自证。

**Q4** 名单查询为什么不能直接查数据库？

▸ 答案：因为它在主链路上，多一次 DB 往返就是几毫秒到几十毫秒，且流量一上来 DB 先成为瓶颈。名单应该放内存/Redis，命中即短路；数据库只作为名单的持久化与后台管理。

**Q5** 风控规则为什么不该写成业务代码里的 if-else？

▸ 答案：因为规则的变更频率远高于业务代码：今天加一条限额、明天改一个阈值。写死在业务里意味着每次调整都要发版、回归、上线；做成规则引擎 + 配置，才能做到“改规则不发版、可灰度、可回滚”。
