                      68.4 名单与画像

                      一句话

                      名单是“已知坏人的黑名单”，画像是“未知人群的概率描述”；名单要求快、准、可解释，画像要求覆盖、可圈选——两者都不是“越多越好”，而是每一条都要有来源、有效期、申诉通道。

                      先破除三个误区

                      误区 现实
                      名单越多越安全 名单越大，误伤越多；没有证据与有效期的名单会迅速腐烂
                      画像 = 用户标签堆砌 标签没有口径、没有更新频率、没有来源，圈出来的人群就是错的
                      名单一旦加入就永久有效 攻击者会换号，正常用户会被误判；没有退出机制的名单就是永久误伤

                      名单：三种颜色，三种动作

                      名单 动作 加入依据 有效期
                      黑名单 直接拒绝/阻断 确认的攻击、作弊、违规 长（需申诉）
                      白名单 跳过后续规则 可信商户、内部账号 定期复核
                      灰名单 降额、加验证、人工复核 疑似但未确认 短（7–30 天）
                      // 名单匹配：黑名单拒绝、白名单放行、灰名单降额/复核；优先级高于规则。
switch {
case black[req.user] || black[req.device]:
	fmt.Println("命中黑名单 → 直接拒绝")
case white[req.user]:
	fmt.Println("命中白名单 → 放行（跳过后续规则）")
case grey[req.ip]:
	fmt.Println("命中灰名单 → 降额或人工复核")
default:
	fmt.Println("未命中名单 → 进入规则引擎")
}

                      完整代码在仓库 tools/examples/68.4-listmatch/，go run . 可复现优先级判定。

                      名单在规则引擎里优先级最高（68.2 规则引擎），因为它是确定性事实：命中就不需要再算特征、跑模型。

                      名单的存储：快，但别牺牲可管理

                      载体 查询延迟 适用 代价
                      进程内内存 纳秒–微秒 高频、小名单（万级） 更新要广播
                      Redis 亚毫秒 中大名单（百万级） 多一次网络往返
                      布隆过滤器 微秒 超大名单（亿级） 有假阳性，只能“疑似”
                      数据库 毫秒–几十毫秒 后台管理、审计 不能放主链路

                      ⚠️ 布隆过滤器说“不在”一定准，说“在”可能是误判（41.8 布隆过滤器）。所以它只能用于第一层粗筛：命中后必须回源确认，不能直接拒绝。

                      名单治理：四条硬规则

                      规则 做法 不做的后果
                      有来源 每条记录带证据（订单号/设备/规则命中） 无法申诉，也无法复盘
                      有有效期 黑名单 90 天复审，灰名单 7–30 天 名单腐烂，误伤累积
                      有申诉 用户可提交申诉，工单闭环 误伤无出口，客诉升级
                      有审计 谁加的、谁删的、依据什么 内部滥用无法追责

                      画像：标签体系而不是标签堆

                      维度 例子 更新频率 用途
                      用户 注册时长、历史逾期、消费能力 天 授信、限额
                      设备 机型、系统、是否模拟器 实时/天 设备风险
                      商户 行业、类目、退款率 天 商户风险
                      团伙 共用设备/IP/支付账号的簇 小时 团伙识别

                      画像的使用方式是圈选：按标签组合圈出一批人，再交给规则或模型。圈选的两个坑：

                      • 标签口径不一致：同一个“高价值用户”在运营与风控里定义不同，圈出来的人群对不上；
                      • 标签过期：用三个月前的标签做今天的决策，等于用旧地图找新路。

                      名单匹配的假阳性与容量账

                      名单选型最容易被两句话带偏：一句是“布隆省内存，所以更快”，另一句是“精确匹配最准，所以最慢”。把 10 万条名单、1 万条不在名单里的查询放进同一台机器量一遍，两句话都只对一半：

                      结构 假阳性（1 万查询） 内存（10 万条） 单次查询 每条约 换到什么
                      精确 map 0 4,979 KB 0.031 µs 51 B 判定精确、可删除、可直接拒绝
                      分片 map（16 片） 0 4,976 KB 0.037 µs 50 B 写锁粒度 1/16，热更新不阻塞整表
                      布隆 p=1% 89（0.89%） 117 KB 0.033 µs 1.2 B 内存省 42.6 倍，代价是回源与不可删

                      三个数字要一起读：

                      • 10 万级布隆不省时间：0.033 µs 与精确 map 的 0.031 µs 是同一量级，多出来的是 k=7 次位探测（m=958,506 bit、k=7）。布隆省的是内存，不是单次查询。
                      • 分片不省内存、也不更快：4,976 KB 与 4,979 KB 只差几十 KB；单线程反而慢一档（0.037 µs 对 0.031 µs），因为多算一次分片哈希。分片换的是热更新时的锁粒度——改一条名单只锁 1/16 的表。
                      • 假阳性必须换算成业务量：0.89% 落在 5,000 QPS 上是每秒 44.5 次回源；把“布隆说在”直接当拒绝，就是每天 384 万次误伤。假阳性本身不是错，把它当结论才是错（用法边界见 41.8 布隆过滤器）。

                      51 B 一条的钱花在哪。 这 51 B 是 Go 哈希表结构加上 key 字符串本身：key（user:12345，12 B）按分配器尺寸落在 16 B 内存类的区间，其余约 35 B 是哈希表的槽位、控制字与负载因子留白。所以名单从“10 万条短 ID”换成“10 万条 32 B 的订单号”，精确表会涨到 7 MB 量级；而布隆的 117 KB 只与条数有关、与 key 长度无关——长 key 场景布隆更划算，这一点第一张表里看不出来。完整程序在 tools/examples/68.4-bloom/。

                      构建耗时的账。 本机全量构建一次 10 万条：精确 map 16.9 ms，布隆 19.4 ms。这组数字决定名单热更新怎么做：

                      更新方式 代价 适用
                      全量重建 + 双 buffer 约 20 ms CPU + 双份内存 名单分钟级变一次
                      分片增量写 只锁 1/16 表，写入微秒级 名单秒级变（分片 map 的主场）
                      写后异步 Add 一个 Add 微秒级，但要可靠投递 布隆追加新名单

                      名单一天改几十条却每改一次全量重建，CPU 会周期性抖动，重建窗口里新数据还查不到；反过来，名单每秒都在变却建布隆，就要接受“增量 Add 失败会造成假阴性”（41.8 讲过的方向性错误）。载体选型必须连更新频率一起算，只算查询不算写入，上线后一定返工。

                      package main

// 68.4 名单匹配的假阳性与容量账：10 万名单 + 1 万条不在名单里的查询，
// 对比精确 map / 分片 map / 布隆过滤器的假阳性、常驻内存与单次查询延迟。
// 布隆参数公式与实现细节见 41.8。

import (
	"fmt"
	"hash/fnv"
	"math"
	"runtime"
	"time"
)

const (
	listN  = 100_000 // 名单条数
	queryN = 10_000  // 查询条数（全部不在名单里）
	shardN = 16      // 分片数
	bfP    = 0.01    // 布隆目标假阳性
	qps    = 5_000.0 // 峰值查询 QPS，用来把假阳性换算成回源/误伤
)

type bloom struct {
	bits []uint64
	m, k uint64
}

// newBloom 按 n、p 反推 m 与 k：m = -n·ln(p)/(ln2)²，k = (m/n)·ln2
func newBloom(n int, p float64) *bloom {
	m := uint64(math.Ceil(-float64(n) * math.Log(p) / (math.Ln2 * math.Ln2)))
	k := uint64(math.Round(float64(m) / float64(n) * math.Ln2))
	if k < 1 {
		k = 1
	}
	return &bloom{bits: make([]uint64, (m+63)/64), m: m, k: k}
}

// hash64 双哈希：h1 定起点、h2 定步长，一个字符串派生 k 个位置
func hash64(s string) (uint64, uint64) {
	h := fnv.New64a()
	h.Write([]byte(s))
	h1 := h.Sum64()
	h2 := (h1 >> 33) | (h1 << 31)
	h2 *= 0x9e3779b97f4a7c15
	h2 ^= h2 >> 29
	if h2 == 0 {
		h2 = 1
	}
	return h1, h2
}

func (b *bloom) add(s string) {
	h1, h2 := hash64(s)
	for i := uint64(0); i < b.k; i++ {
		pos := (h1 + i*h2) % b.m
		b.bits[pos/64] |= 1 << (pos % 64)
	}
}

func (b *bloom) has(s string) bool {
	h1, h2 := hash64(s)
	for i := uint64(0); i < b.k; i++ {
		pos := (h1 + i*h2) % b.m
		if b.bits[pos/64]&(1<<(pos%64)) == 0 {
			return false // 一位为 0：一定不在
		}
	}
	return true // 全为 1：可能在，需回源确认
}

type exact struct{ m map[string]struct{} }

func (x *exact) has(s string) bool { _, ok := x.m[s]; return ok }

type sharded struct{ sh [shardN]map[string]struct{} }

func shardOf(s string) int {
	h := fnv.New32a()
	h.Write([]byte(s))
	return int(h.Sum32() % shardN)
}

func (x *sharded) has(s string) bool {
	_, ok := x.sh[shardOf(s)][s]
	return ok
}

var keep any // 持有被测结构，避免被 GC 回收

// measure 先 GC 读基线，再建结构（连 key 字符串一起建），再 GC 读差值
func measure(build func() any) (int64, any) {
	runtime.GC()
	var before, after runtime.MemStats
	runtime.ReadMemStats(&before)
	v := build()
	keep = v
	runtime.GC()
	runtime.ReadMemStats(&after)
	return int64(after.HeapAlloc) - int64(before.HeapAlloc), v
}

func avgNS(has func(string) bool, keys []string) float64 {
	const rounds = 20
	for _, k := range keys { // 预热
		has(k)
	}
	start := time.Now()
	for r := 0; r < rounds; r++ {
		for _, k := range keys {
			has(k)
		}
	}
	return float64(time.Since(start).Nanoseconds()) / float64(rounds*len(keys))
}

func main() {
	queries := make([]string, queryN)
	for i := range queries {
		queries[i] = fmt.Sprintf("query:%d", i)
	}
	buildExact := func() any {
		x := &exact{m: make(map[string]struct{}, listN)}
		for i := 0; i < listN; i++ {
			x.m[fmt.Sprintf("user:%d", i)] = struct{}{}
		}
		return x
	}
	buildShard := func() any {
		x := &sharded{}
		for i := range x.sh {
			x.sh[i] = make(map[string]struct{}, listN/shardN)
		}
		for i := 0; i < listN; i++ {
			k := fmt.Sprintf("user:%d", i)
			x.sh[shardOf(k)][k] = struct{}{}
		}
		return x
	}
	buildBloom := func() any {
		b := newBloom(listN, bfP)
		for i := 0; i < listN; i++ {
			b.add(fmt.Sprintf("user:%d", i))
		}
		return b
	}

	// 布隆内存 = 位数组字节数，直接按 m 算，不受分配器取整影响；
	// 顺带量一次全量构建耗时：名单热更新要不要全量重建，看的就是这个数。
	t0 := time.Now()
	b := buildBloom().(*bloom)
	bloomBuild := time.Since(t0)
	t1 := time.Now()
	_ = buildExact()
	mapBuild := time.Since(t1)
	bloomBytes := int64(len(b.bits) * 8)
	memMap, v1 := measure(buildExact)
	memShard, v2 := measure(buildShard)
	ex := v1.(*exact)
	sh := v2.(*sharded)

	countFP := func(has func(string) bool) int {
		n := 0
		for _, k := range queries {
			if has(k) {
				n++
			}
		}
		return n
	}
	fpMap, fpShard, fpBloom := countFP(ex.has), countFP(sh.has), countFP(b.has)
	latMap := avgNS(ex.has, queries) / 1000
	latShard := avgNS(sh.has, queries) / 1000
	latBloom := avgNS(b.has, queries) / 1000

	fmt.Printf("名单=%d 条，查询=%d 条（全部不在名单中），分片数=%d，布隆目标 p=%.0f%%\n\n",
		listN, queryN, shardN, bfP*100)
	fmt.Printf("%-14s %-8s %-11s %-13s %s\n", "结构", "假阳性", "内存(KB)", "单次查询(µs)", "备注")
	fmt.Println("-------------------------------------------------------------------")
	fmt.Printf("%-14s %-8d %-11.1f %-13.3f %s\n", "精确 map", fpMap, float64(memMap)/1024, latMap, "零假阳性")
	fmt.Printf("%-14s %-8d %-11.1f %-13.3f %s\n", "分片 map(16)", fpShard, float64(memShard)/1024, latShard, "零假阳性")
	fmt.Printf("%-14s %-8d %-11.1f %-13.3f %s\n", "布隆 p=1%", fpBloom, float64(bloomBytes)/1024, latBloom, "需回源确认")
	fmt.Printf("\n布隆参数：m=%d bit（%.1f bit/key），k=%d，位数组 %.1f KB\n",
		b.m, float64(b.m)/float64(listN), b.k, float64(bloomBytes)/1024)

	perMap := float64(memMap) / listN
	perBloom := float64(bloomBytes) / listN
	fmt.Printf("\n每条约 %.0f B（map，含 key 字符串）/ %.2f B（布隆）\n", perMap, perBloom)
	fmt.Printf("外推：100 万条 → map %.0f MB、布隆 %.1f MB（同参数线性放大）\n",
		perMap*1e6/1024/1024, perBloom*1e6/1024/1024)
	fmt.Printf("全量构建耗时（10 万条，单线程）：map %.1f ms，布隆 %.1f ms\n",
		float64(mapBuild.Microseconds())/1000, float64(bloomBuild.Microseconds())/1000)

	fpRate := float64(fpBloom) / queryN
	fmt.Printf("\n假阳性率 %.2f%%：QPS=%.0f 时每秒回源 %.1f 次；\n", fpRate*100, qps, qps*fpRate)
	fmt.Printf("若把布隆命中直接当拒绝（错误用法），每天误伤 %.0f 人\n", qps*fpRate*86400)
}

                      容量账先乘实例数。 名单是每台机器都要查的，所以选型公式不是“名单多大”，而是：

                      内存 = 名单条数 × bit/key ÷ 8 × 实例数
回源 QPS = 查询 QPS × 假阳性率
                      规模 精确 map/实例 200 实例合计 布隆 1%/实例 200 实例合计 建议
                      10 万 4.9 MB 980 MB 117 KB 23 MB 实例 > 50 就上布隆
                      100 万 49 MB 9.8 GB 1.1 MB 220 MB 布隆 + 回源确认
                      1 亿 4.9 GB 不可行 110 MB 22 GB 服务端布隆单份（RedisBloom）或分片，本地只留热名单

                      10 万条、200 个实例这个规模，精确 map 要 980 MB——布隆登场的时机是“单实例内存 × 实例数”这一格，不是“名单有 10 万条”本身。反过来，名单只有 1 万条、实例 20 个时，精确 map 不到 100 MB，布隆只会给主链路加一层 0.9% 的回源和一套重建机制，不划算。

                      容量账的另一半是回源。布隆把 100% 的查询压到 0.89% 回源，5,000 QPS × 0.89% = 44.5 QPS，一层 Redis 足够；名单到亿级、假阳性 1% 时，同一个公式给出 50 QPS，能不能接住取决于回源层的容量与超时，而不是布隆本身。回源这一层还有两个隐藏成本：多一次网络往返（微秒变亚毫秒），以及回源超时时的降级动作——降级成“放行”是漏杀，降级成“拒绝”是误杀，这个选择必须在名单上线前定好，不能等超时那天临时决定。

                      命中率决定布隆划不划算。 布隆的收益是“把不在的查询挡掉”。名单命中率极低（风控黑名单通常 < 0.1%）时，99.9% 以上的查询走布隆的“不在”分支，收益最大；如果名单是内网 IP 白名单这种命中率 80% 的场景，布隆的“可能在”分支占大多数，回源量与不用布隆几乎一样，只剩内存收益——这时候该用精确表，而不是布隆。

                      什么规模用哪种：

                      你的情况 用什么 判据
                      名单 < 10 万、实例 < 50 进程内精确 map 250 MB 以内，零假阳性，可直接拒绝
                      名单 < 10 万、实例 > 50 布隆 + 回源 内存 980 MB → 23 MB，回源 44.5 QPS
                      名单 10 万–100 万 分片 map（改得勤）或布隆（读多写少） 看每天改多少条、能不能接受重建
                      名单 > 100 万 布隆 + 回源；亿级用 RedisBloom 单份 精确表单实例已过 GB，乘实例数不可接受
                      必须能删、假阳性必须为 0 精确表 / Cuckoo 标准布隆不能删（41.8）

                      名单的颜色不同，载体也不同。 黑名单量大、命中率低、必须精确拦截，适合“布隆粗筛 + 精确表/Redis 回源”；白名单量小、要求零误判、要能随时增删，适合精确表加审计；灰名单有效期短（7–30 天）、必须能删，标准布隆不能删，要么用带 TTL 的 Redis 集合，要么用 Cuckoo/计数布隆，并接受更高的内存。

                      名单 典型规模 假阳性容忍 推荐载体 删除要求
                      黑名单 10 万–亿级 只能当线索（必须回源） 布隆 + 精确回源 允许延迟删除
                      白名单 千–万级 零容忍 精确表 + 审计日志 必须实时删
                      灰名单 万–百万级 低（动作是降额/验证） 分片 map / Redis + TTL 到期自动删

                      🔑 选型的判据不是“名单有多大”，是两笔账的总和：单实例内存 × 实例数，回源 QPS × 回源单价。只算内存，可能忽略回源层接不住；只算 1% 这个比例，会忽略亿级名单上 1% 就是 100 万条候选误判——两个数字都算完，载体才定得下来。

                      反模式

                      反模式 后果
                      名单没有有效期 误伤永久化，名单越滚越脏
                      布隆命中直接拒绝 假阳性直接变成误杀
                      名单查询走数据库 主链路延迟翻倍
                      标签没有口径文档 同一个标签两种含义，圈选结果不可信
                      画像只进不出 标签只增不删，人群越来越不准
                      名单加入无审计 内部人员可滥用名单
                      没有申诉通道 误伤用户无处申诉，客诉升级

                      自检

                      Q1 为什么布隆过滤器命中后还要回源确认？

                      ▸ 答案：因为布隆过滤器有假阳性：它说“不在”一定准，说“在”可能是误判。名单是“直接拒绝”这种高代价动作，假阳性就是误杀，所以布隆只能做第一层粗筛，命中后回源（Redis/DB）确认。

                      Q2 黑名单和灰名单的差别只在“程度”吗？

                      ▸ 答案：不只是程度，是动作不同：黑名单直接拒绝（确定性事实），灰名单降额/加验证/转人工（疑似）。动作不同，意味着误判代价不同：黑名单误判是“用户被拒”，灰名单误判只是“多一步验证”。所以灰名单的有效期更短、复审更频繁。

                      Q3 名单为什么必须有有效期与申诉？

                      ▸ 答案：因为攻击者会换号、正常用户会被误判，名单不可能是“永久真相”。没有有效期，误伤会永久累积；没有申诉，误伤用户没有出口，客诉会升级。有效期 + 申诉 = 名单的自我纠错机制。

                      Q4 画像的“圈选”最容易出什么问题？

                      ▸ 答案：两个：标签口径不一致（同一标签在运营与风控里定义不同）与标签过期（用旧标签做新决策）。解法是给每个标签写清口径、更新频率与来源，并给标签设“保质期”，过期标签降权或不用。

                      Q5 名单与画像在风控里怎么配合？

                      ▸ 答案：名单管“已知的确定性事实”（命中即短路），画像管“未知的概率判断”（圈出高风险人群，交给规则/模型打分）。顺序上名单在前（快、便宜、确定），画像在后（贵、需要计算）。两者都只是输入，最终决策仍要经过规则与模型。
