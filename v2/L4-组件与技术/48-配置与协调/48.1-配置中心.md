# 48.1 配置中心

## 一句话

> 配置中心解决的不是“把配置存起来”，而是让变更**以可预期的延迟到达所有实例、以可控的爆炸半径生效、并且能一键回到上一个版本**；存储只是最不值钱的那部分。

## 四个能力，缺一不可

| 能力 | 没有会怎样 | 关键设计 |
|---|---|---|
| 存储 + 版本 | 改错了无法回滚，不知道谁改的 | 每次变更生成不可变版本号，保留历史 |
| 下发（推/拉） | 改完要重启，或等下一个发布周期 | watch/长轮询，秒级生效 |
| 灰度 | 一份坏配置 100% 生效 | 按实例/标签/百分比分批 |
| 回滚 + 审计 | 出事只能逐个实例改回去 | 一键切回上一版本，记录操作人/时间/差异 |

## 推还是拉：新鲜度与连接数

1000 台实例、每次变更要在多久内全量生效：

| 方式 | 平均陈旧 | 最坏陈旧 | 常态请求量 | 变更延迟 |
|---|---|---|---|---|
| 轮询 30s | **15s** | 30s | 33.3 QPS（288 万次/天） | 平均 15s |
| 长轮询 / watch | ~0.1s | ~0.1s | 1000 条长连接 | **0.1s** |
| 推（服务端主动） | ~0.1s | ~0.1s | 1000 条连接 + 心跳 | 0.1s |

- 轮询的实现最简单，但**变更生效慢半拍**：配错一个限流阈值，要等 15 秒才全量生效；紧急回滚时这 15 秒很难受。
- watch 的代价是**连接数与重连风暴**：配置中心重启时 1000 条连接同时重连，必须加随机抖动（0–30s），否则重启瞬间把配置中心再打挂一次。
- 折中：长轮询（客户端挂起 30s，无变更就返回 304）——兼顾实时性与兼容性，很多老客户端只支持 HTTP。

> 🔑 配置下发的关键指标不是 QPS，是**变更生效延迟的 P99** 和**配置中心故障时的可用性**。

## 数字一：坏配置的爆炸半径

一份配错的配置（比如把超时改成 0、把开关打开）在 1000 台实例上生效：

| 场景 | 暴露量 |
|---|---|
| 全量推送，5 分钟发现 | **5000 实例·分钟** |
| 1% 灰度（10 台），5 分钟发现 | **50 实例·分钟**（100 倍差距） |
| 问题只在规模上暴露（容量/热点） | 灰度救不了：1000 台 × 20 分钟回滚 = **20000 实例·分钟** |

两个结论：

1. **灰度只对“小规模就能复现”的问题有效**：拼错 key、类型错误、空指针，1% 流量就能暴露。
2. **容量/热点类问题灰度无效**：1% 流量下一切正常，全量才雪崩。这类问题要靠压测与容量模型（见 [34.5 性能测试与负载模型](../../L3-质量属性/34-性能/34.5-性能测试与负载模型.md)），而不是指望灰度。

## 数字二：回滚速度决定损失

| 回滚方式 | 耗时 | 说明 |
|---|---|---|
| 有版本号，一键回滚 + 推送 | **0.1s** | 版本切换 + watch 推送 |
| 人工找到原值、逐个改回 | 平均 **20 分钟** | 找值、确认、逐环境改 |

50 次变更/天、2% 需要回滚 = 每天 1 次：0.1 秒 vs 20 分钟。这就是“版本化”的全部意义——它不是为了好看，是为了**把一次事故从 20 分钟压到 0.1 秒**。

## 配置的边界：什么该进、什么不该进

| 该进配置中心 | 不该进 | 放在哪 |
|---|---|---|
| 功能开关、灰度比例 | 数据库密码、API Key | 密钥管理（KMS/Vault） |
| 超时、重试、限流阈值 | 大文件（证书、模型、词表） | 对象存储 + 引用 |
| 下游地址、路由规则 | 高频变更的业务数据 | 数据库/缓存 |
| 日志级别、采样率 | 需要事务一致性的数据 | 数据库 |
| 按环境的参数 | 代码逻辑分支 | 代码 + 开关 |

三条判据：

1. **敏感** → 密钥管理，配置中心只存引用（路径/版本）。
2. **大** → 对象存储，配置中心存 URL + 校验和。
3. **高频** → 数据库/缓存；配置中心的写入是“人工变更”，不是数据通道。

## 一致性与可用性：配置中心挂了怎么办

| 策略 | 行为 | 代价 |
|---|---|---|
| 本地缓存 + 兜底 | 启动读本地快照，连不上就用快照 | 可能用旧配置 |
| 启动强依赖 | 拿不到配置就拒绝启动 | 配置中心故障 = 无法扩容/重启 |
| 缓存 + 定期刷新 | 运行期用缓存，后台重试 | 变更延迟变大 |
| 多级：本地文件 → 配置中心 → 默认值 | 逐级降级 | 需要明确每一级的语义 |

**推荐**：启动时允许读本地快照（保证可启动），运行期 watch（保证新鲜），并明确“配置中心不可用时，最长容忍多久的旧配置”。此外，**配置必须有默认值**——没有默认值的配置项，等于给系统加了一个隐式强依赖。

## 版本、审计与灰度

| 机制 | 做法 | 作用 |
|---|---|---|
| 版本号 | 每次变更生成递增版本/内容哈希 | 回滚、比对、定位“哪次变更引入的问题” |
| 审计日志 | 谁、何时、改了什么、从什么改到什么 | 事故复盘、合规 |
| 灰度标签 | 按实例标签/机房/百分比分批 | 控制爆炸半径 |
| 变更审批 | 高危配置双人确认 | 防误操作 |
| 差异视图 | 提交前展示 diff | 防“改错一个字符” |

## 可运行的配置成本账本

```go
package main

import "fmt"

func main() {
	const (
		instances  = 1000.0
		changesDay = 50.0
	)

	// ① 轮询 vs 长轮询/推送：新鲜度与请求量
	pollSec := 30.0
	fmt.Println("① 配置下发方式对比（1000 台实例）")
	fmt.Printf("   轮询 %0.0fs：平均陈旧 %.0fs、最坏 %.0fs；请求量 %.1f QPS（%.0f 万次/天）\n",
		pollSec, pollSec/2, pollSec, instances/pollSec, instances/pollSec*86400/10000)
	fmt.Printf("   长轮询/watch：变更推送延迟约 100ms；%.0f 条长连接；配置中心重启时 %.0f 条连接同时重连\n",
		instances, instances)
	fmt.Printf("   每变更一次，轮询要等平均 %.0fs 才全量生效；推送只要 0.1s\n", pollSec/2)

	// ② 配置变更的爆炸半径：灰度能不能缩小损失，取决于“问题在灰度阶段可见吗”
	fmt.Println("\n② 一份坏配置的影响（每批观察 5 分钟）")
	fullExposure := instances * 5
	canaryExposure := instances * 0.01 * 5
	fmt.Printf("   小规模就能复现（如拼错 key）：全量推送暴露 %.0f 实例·分钟；1%% 灰度暴露 %.0f（%.0f 倍）\n",
		fullExposure, canaryExposure, fullExposure/canaryExposure)
	rollback := 20.0 // 人工回滚平均耗时（分钟）
	scaleOnly := instances * rollback
	fmt.Printf("   只在规模上暴露（容量/热点）：灰度救不了，最终仍是 %.0f 台 × %.0f 分钟回滚 = %.0f 实例·分钟\n",
		instances, rollback, scaleOnly)
	fmt.Println("   灰度只能缩短“发现问题”的时间；容量类问题要靠压测与容量模型")

	// ③ 版本化与回滚
	fmt.Printf("\n③ 回滚：有版本号/一键回滚 → 0.1s（推送）；没有版本化、靠人工改回 → 平均 20 分钟\n")
	fmt.Printf("   50 次变更/天，哪怕只有 2%% 需要回滚：1 次 × 20 分钟 vs 1 次 × 0.1 秒\n")

	// ④ 变更频率 × 实例数 = 配置中心的日常负载
	perDay := instances * changesDay * 2 // 每次变更：拉取 + 确认
	fmt.Printf("\n④ 日常负载：%.0f 台 × %.0f 次变更/天 × 2（拉取+确认）= %.0f 万次/天\n",
		instances, changesDay, perDay/10000)
}
```

## 参数怎么给

| 你的场景 | 方案 | 关键参数 |
|---|---|---|
| 几十台、变更不频繁 | 轮询 30–60s | 本地缓存 + 版本号，能回滚即可 |
| 上千台、要求秒级生效 | watch/长轮询 | 重连抖动、连接数上限、心跳 |
| 混合环境（云+IDC） | 每环境独立配置中心 + 同步 | 命名空间隔离，避免串环境 |
| 高危配置（限流/开关） | 灰度 + 审批 + 自动回滚 | 按 1%→10%→100%，观察指标 |
| 多租户 | 按租户命名空间 + 配额 | 防止单租户配置拖垮全局 |
| 密钥 | 只存引用 | 见 13.4 密钥与凭证管理（待补） |

## 反模式

| 反模式 | 后果 |
|---|---|
| 配置中心当数据库用 | 高频写入打爆存储，变更无审计 |
| 密文/密钥存配置中心且无加密 | 一次泄露全网失守 |
| 没有版本与回滚 | 改错只能逐个实例手工改回 |
| 全量推送无灰度 | 一份坏配置 100% 实例同时失效 |
| watch 重连无抖动 | 配置中心重启时被重连风暴二次打挂 |
| 应用启动强依赖配置中心 | 配置中心故障时无法扩容/重启，故障放大 |
| 配置项没有默认值 | 隐式强依赖，缺一项就启动失败 |
| 配置变更不通知、不审计 | 出问题找不到“哪次变更” |
| 环境共用一套配置中心且无隔离 | 测试环境误改生产配置 |
| 配置里写业务逻辑分支 | 逻辑散落在配置里，无法测试 |

## 自检

**Q1** 轮询 30 秒 vs watch，平均陈旧时间差 150 倍（15s vs 0.1s）。为什么很多系统仍然选轮询？

▸ 答案：因为轮询的**实现与运维成本最低**：无长连接、无心跳、无重连逻辑，客户端只要一个定时器和一次 HTTP GET，配置中心也不用维护百万连接。对于“变更一天几次、生效晚 15 秒无所谓”的系统（内部后台、批处理），15 秒完全可以接受。选 watch 的场景是“变更要秒级生效且变更频繁”（开关、限流阈值、灰度比例）。折中是长轮询：兼容 HTTP、实时性接近 watch、连接数可控。

**Q2** 1000 台实例、1% 灰度，为什么能把坏配置的暴露从 5000 实例·分钟降到 50？这个收益在什么情况下会消失？

▸ 答案：因为只有 10 台先吃到坏配置，观察 5 分钟发现问题就停止推送、回滚，暴露量 = 10 × 5 = 50；全量则是 1000 × 5 = 5000，正好 100 倍。收益消失的情况：问题**只在规模上出现**（容量不足、热点、长尾），1% 流量下指标完全正常，等到 100% 才雪崩——此时灰度只是把“一次性事故”变成“多批次事故”，暴露量反而是 1000 × 20 分钟回滚 = 20000。所以灰度必须配“能反映规模效应的指标”（容量、队列、P99），否则只是心理安慰。

**Q3** 配置中心挂了，应用应该“启动失败”还是“用本地快照启动”？怎么选？

▸ 答案：默认选**用本地快照启动 + 明确容忍窗口**。启动失败意味着配置中心成为硬依赖：一次故障会让所有扩容、重启、故障转移全部失败，把一个组件故障放大成整个系统不可恢复。本地快照的代价是“可能用旧配置”，所以要把快照做成不可变、带版本号，并明确“最多容忍多久的旧配置”（如 24 小时），超过就告警。例外：涉及安全策略（如鉴权开关）的配置，旧值可能不安全，这类要单独评估。

**Q4** 为什么密钥不应该放在配置中心？如果团队已经放了，怎么迁移？

▸ 答案：配置中心的定位是“可读、可审计、变更不频繁”，而密钥需要的是“最小权限、加密存储、轮换、不留痕迹的读取”。放在配置中心的风险：任何有读权限的服务/人都能拿到全量密钥；配置导出、备份、日志都可能带出明文；轮换要改配置并重启。迁移路径：① 配置中心只存“密钥引用”（路径 + 版本）；② 应用启动时从 KMS/Vault 拉取，内存中短期持有；③ 加审计与轮换机制；④ 逐步把历史明文密钥标记为“待轮换”。

**Q5** 配置变更的“爆炸半径”除了实例数，还和什么有关？

▸ 答案：还有三个维度：① **变更的影响面**——是改一个日志级别，还是改全局限流阈值（后者影响所有请求）；② **发现时间**——监控能否在 1 分钟内看到错误率/延迟变化；③ **回滚速度**——0.1 秒切回还是 20 分钟人工改。三者相乘才是真实损失。所以同样的“1000 台”，改日志级别可能无害，改限流阈值可能全站 5xx。控制爆炸半径的手段因此是组合：灰度（实例维度）+ 审批（变更维度）+ 自动回滚（时间维度）。
