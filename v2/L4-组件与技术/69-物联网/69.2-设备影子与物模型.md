# 69.2 设备影子与物模型

## 一句话

> 物模型解决「**设备能说什么**」，设备影子解决「**设备不在线时说的话还算不算**」；两者合起来是一份带版本号的期望值/上报值文档，delta 就是两者之差。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 「影子就是缓存设备最后一次上报」 | 只存上报值的是**状态缓存**；影子必须同时存 **desired**（期望）与 **reported**（实况），并能算出两者之差 |
| 「物模型是文档，写完就扔给前端」 | 物模型是**运行时校验器**：属性名、类型、读写权限、枚举范围都要在入口拦住，否则脏数据会写进影子与时序库 |
| 「影子能存所有数据」 | 影子只存**每个属性的最新值**；带时间戳的历史数据属于时序库（[44.17 时序数据库](../44-数据库/44.17-时序数据库.md)），塞进影子会让每次更新都变成大对象写 |

## 物模型：属性、事件、服务

| 元素 | 方向 | 例子 | 影子怎么处理 |
|---|---|---|---|
| **属性**（property） | 双向 | `power`、`target_temp`、`mode` | 进影子，参与 delta |
| **事件**（event） | 设备 → 云 | `fault`、`door_open`、`low_battery` | **不进影子**，走消息/规则链路（[69.3](69.3-海量连接与消息.md)） |
| **服务**（service） | 云 → 设备（带参数/返回） | `reboot`、`start_ota`、`calibrate` | 不进影子；要么走命令主题，要么用影子参数 + delta 触发 |

属性的最小定义（TSL 风格；字段名以你采用的物模型规范为准——阿里云 TSL 的数值类型是 `double`/`float`/`int32`，AWS/Azure 的影子则只存属性名与值，不单独声明类型）：

```json
{"identifier":"target_temp","name":"目标温度","dataType":{"type":"double","specs":{"unit":"℃","min":"16","max":"32"}},"access":"rw"}
```

> 🔑 物模型里两个字段最容易被忽略：`access`（只读属性不能被下行覆盖）和 `specs` 里的范围/枚举。这两条如果只在文档里、不在代码里，影子就会出现 80℃ 的目标温度——下面 `checkRange` 就是把 `min`/`max` 变成运行时拒绝的那几行。

## 设备影子：四个字段就够

| 字段 | 含义 | 谁写 | 写错的表现 |
|---|---|---|---|
| `desired` | 云端/App 期望设备达到的状态 | 云端 | 与 reported 混淆 → 设备一上报就把期望值冲掉 |
| `reported` | 设备最后一次确认的实际状态 | 设备 | 设备不上报 → delta 永远清不掉，重连就反复下发 |
| `delta` | `desired` 与 `reported` 的差，按属性展开 | 计算得出 | 用「全量下发」代替 delta → 弱网下每次重连都传全量 |
| `version` | 单调递增的文档版本号 | 云端 | 不做 CAS → 两个 App 同时改，后写的静默覆盖 |

一份具体的影子文档：

```json
{
  "version": 7,
  "desired":   {"power": true, "target_temp": 26.0},
  "reported":  {"power": true, "target_temp": 24.0, "current_temp": 23.5},
  "delta":     [{"path": "target_temp", "desired": 26.0}]
}
```

### 一次完整交互

```text
App/云端                         影子服务                        设备
   │  改 desired(target=26)          │                              │
   ├───────────────────────────────►│ version 6→7，算 delta         │
   │                                ├── 下发 delta（设备在线时）─────►│
   │                                │                              │ 调温
   │                                │◄── 上报 reported(target=26) ──┤
   │                                │ 合并 → delta 为空              │
   │                                │                              │
   │  （设备离线）改 desired(28)     │                              │
   ├───────────────────────────────►│ version 7→8，delta 保留        │
   │                                │◄── 设备重连，拉 delta ─────────┤
   │                                ├── 下发 delta(target=28) ──────►│
```

> 🔑 影子的价值全在「**设备离线的那段时间**」：desired 先落库，设备什么时候回来什么时候对齐。设备在线时它只是个转发器，别指望它提升性能。

## 和现成产品对照

| 方案 | 期望/上报 | 差量 | 版本控制 | 适用 |
|---|---|---|---|---|
| **AWS IoT Device Shadow** | `state.desired` / `state.reported` | 服务端生成 `delta` | 文档 `version` 号 | 用 AWS 生态、设备量大 |
| **Azure IoT Hub 设备孪生** | `properties.desired` / `properties.reported` | 服务端通知差异 | `ETag` | 用 Azure 生态、要跟 DPS 配合 |
| **阿里云/涂鸦等物模型平台** | TSL + 影子 | 平台计算 | 平台内部版本 | 国内量产设备、要现成 App SDK |
| **自研（本节实现）** | 自己定 | 自己算 | 自己定 | 有特殊设备协议、或不想绑定云厂商 |

选现成产品的真实理由通常是**设备管理配套**（批量任务、OTA、告警、App SDK），不是影子本身。我的判断是：影子的读改写逻辑本身不复杂，难的是「设备管理配套」与「和接入层/时序库的边界」，自研前先确认后者是否已有归属。

## 实现：先校验，再合并，最后算差量

核心实现（与下面两组输出同一套逻辑；`find`/`merge`、import 与 `main` 略）：

```go
type DataType struct {
	Type  string         `json:"type"` // bool / int32 / double / string / enum
	Specs map[string]any `json:"specs,omitempty"`
}
type Property struct {
	Identifier string   `json:"identifier"`
	DataType   DataType `json:"dataType"`
	Access     string   `json:"access"` // r / rw
}

// ValidatePatch：逐个属性校验；任一不合法就整包拒绝（不做部分写入）。
func (m *ThingModel) ValidatePatch(patch map[string]any) error {
	for id, v := range patch {
		p, ok := m.find(id)
		if !ok {
			return fmt.Errorf("物模型里没有这个属性: %s", id)
		}
		if p.Access == "r" {
			return fmt.Errorf("只读属性不接受下行: %s", id)
		}
		if err := checkType(p.DataType, v); err != nil {
			return fmt.Errorf("属性 %s: %w", id, err)
		}
	}
	return nil
}

func checkType(dt DataType, v any) error {
	switch dt.Type {
	case "bool":
		if _, ok := v.(bool); !ok {
			return fmt.Errorf("期望 bool，得到 %T", v)
		}
	case "int32":
		f, ok := v.(float64)
		if !ok || f != float64(int32(f)) {
			return fmt.Errorf("期望 int32 整数，得到 %v", v)
		}
		return checkRange(dt, f)
	case "double":
		f, ok := v.(float64)
		if !ok {
			return fmt.Errorf("期望数字，得到 %T", v)
		}
		return checkRange(dt, f)
	case "string":
		if _, ok := v.(string); !ok {
			return fmt.Errorf("期望 string，得到 %T", v)
		}
	case "enum":
		vals, _ := dt.Specs["values"].([]any)
		for _, x := range vals {
			if v == x {
				return nil
			}
		}
		return fmt.Errorf("不在枚举 %v 里：%v", vals, v)
	default:
		return fmt.Errorf("未知数据类型 %q", dt.Type)
	}
	return nil
}

// checkRange 读 specs 里的 min/max（TSL 常写成字符串），越界即拒绝。
func checkRange(dt DataType, f float64) error {
	for _, k := range []string{"min", "max"} {
		raw, ok := dt.Specs[k]
		if !ok {
			continue
		}
		var lim float64
		switch x := raw.(type) {
		case float64:
			lim = x
		case string:
			if _, err := fmt.Sscanf(x, "%g", &lim); err != nil {
				return fmt.Errorf("specs.%s 不是数字: %v", k, x)
			}
		default:
			return fmt.Errorf("specs.%s 类型不支持: %T", k, raw)
		}
		if k == "min" && f < lim {
			return fmt.Errorf("低于下限 %v: %v", lim, f)
		}
		if k == "max" && f > lim {
			return fmt.Errorf("高于上限 %v: %v", lim, f)
		}
	}
	return nil
}

type Delta struct {
	Path    string `json:"path"`
	Desired any    `json:"desired"`
}

type Shadow struct {
	mu       sync.Mutex // 同一设备的多请求会并发进来，读改写必须串行
	model    *ThingModel
	desired  map[string]any
	reported map[string]any
	version  int64
}

// ApplyDesired：版本 CAS（expectedVersion=0 表示不校验）→ 校验 → 合并 → 回差量。
func (s *Shadow) ApplyDesired(patch map[string]any, expectedVersion int64) (int64, []Delta, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if expectedVersion != 0 && expectedVersion != s.version {
		return s.version, nil, fmt.Errorf("版本冲突：期望 %d，实际 %d", expectedVersion, s.version)
	}
	if err := s.model.ValidatePatch(patch); err != nil {
		return s.version, nil, err
	}
	merge(s.desired, patch)
	s.version++
	return s.version, s.deltaLocked(), nil
}

func (s *Shadow) deltaLocked() []Delta {
	out := []Delta{}
	flatten("", s.desired, s.reported, &out)
	sort.Slice(out, func(i, j int) bool { return out[i].Path < out[j].Path })
	return out
}

// flatten 只遍历 desired：reported 多出来的属性不是「要下发的东西」。
func flatten(prefix string, desired, reported map[string]any, out *[]Delta) {
	for k, dv := range desired {
		path := k
		if prefix != "" {
			path = prefix + "/" + k
		}
		dm, dok := dv.(map[string]any)
		rv, present := reported[k]
		rm, rok := rv.(map[string]any)
		if dok && rok {
			flatten(path, dm, rm, out)
			continue
		}
		if !present || !reflect.DeepEqual(dv, rv) {
			*out = append(*out, Delta{Path: path, Desired: dv})
		}
	}
}
```

实测 1：场景复现（macOS 15.6 / Apple M1 / go1.27.1，单文件版 `go run main.go`）：

```text
① 下发期望后 version=1 delta=[{"path":"power","desired":true},{"path":"target_temp","desired":26}] err=<nil>
② 设备上报后 delta=[{"path":"target_temp","desired":26}]
③ 旧版本写入 err=版本冲突：期望 1，实际 2
④ 拒绝 map[current_temp:20] → 只读属性不接受下行: current_temp
④ 拒绝 map[no_such:1] → 物模型里没有这个属性: no_such
④ 拒绝 map[mode:dry] → 属性 mode: 不在枚举 [cool heat auto] 里：dry
④ 拒绝 map[power:true] → 属性 power: 期望 bool，得到 string
④ 拒绝 map[target_temp:80] → 属性 target_temp: 高于上限 32: 80
```

实测 2：`go test -race -v` 节选（同一实现）：

```text
--- PASS: TestDeltaThreeStates (0.00s)       delta=[{"path":"target_temp","desired":26}]
--- PASS: TestVersionConflict (0.00s)        同版本 CAS 成功、旧版本 CAS 报冲突
--- PASS: TestOfflineReplay (0.00s)          离线 desired 重连后只拿 delta，对齐后 delta 为空
--- PASS: TestThingModelValidation (0.00s)   未知/只读/类型/越界/枚举 五类全部拒绝
--- PASS: TestConcurrent (0.01s)             100 写者 + 100 上报，最终 version=200，无数据竞争
```

读法：① 两个属性都没对齐 → 两条 delta；② 设备执行了 power，delta 只剩 target_temp——**不是全量重发**；③ 版本 CAS 挡住并发覆盖；④ 五条物模型拦截，脏数据进不了影子；并发用例证明锁与版本号在 `-race` 下成立。

## 影子的存储与主题

| 选择 | 做法 | 判据 |
|---|---|---|
| **Redis 存整份文档** | key = `shadow:{product}:{device}`，value = 上述 JSON | 设备百万级、每次更新整份读写（几 KB），单机内存要算账：100 万设备 × 2KB ≈ 2GB |
| **DB 存行 + 缓存** | 一属性一行，Redis 缓存热点设备 | 属性多、要按属性查询/审计时用 |
| **只存 desired，reported 走时序库** | reported 最新值从时序库取 | 设备上报频率高、影子里 desired 很少变 |

影子文档可能长期不更新（设备离线），而设备重连后的对齐属于断网续传的一部分——本地缓存与补传机制见 [69.4 边缘计算与断网续传](69.4-边缘计算与断网续传.md)。

主题设计两种风格，二选一，不要混：

```text
# A. 一设备一主题（推荐，权限好做：设备只能读写自己的）
shadow/{productKey}/{deviceName}/desired     云端 → 设备（delta 也可合并到 update）
shadow/{productKey}/{deviceName}/reported    设备 → 云端
shadow/{productKey}/{deviceName}/update      设备拉取/上报

# B. 平台固定主题（跟随云厂商规范，如 AWS IoT：$aws/things/{thingName}/shadow/update）
```

> ⚠️ 自研主题别用 `$` 开头：`$` 是 broker 保留命名空间，`#`/`+` 通配不会匹配 `$` 开头的主题，监控、ACL 与规则引擎容易整片漏掉。主题还要与接入层的会话、ACL 一起设计，见 [69.1 设备接入与协议 (MQTT / CoAP)](69.1-设备接入与协议.md)。

## 时间与版本：影子里最容易出错的两处

| 问题 | 表现 | 解法 |
|---|---|---|
| **时钟** | 设备时间不准，reported 的时间戳比 desired 还早 | 以云端接收时间为准，设备时间只做参考；时钟问题见 [23.1 物理时钟与漂移](../../L1-分布式原理/23-时间、顺序与因果/23.1-物理时钟与漂移.md) |
| **乱序** | 旧上报后到，把新值覆盖成旧值 | reported 每条带「设备侧序号/采集时间」，影子只接受更新的那条（同 device 单调） |
| **重复** | 重连后设备重发同一条上报 | 上报带幂等键，影子服务去重（[25.4 幂等设计与去重](../../L1-分布式原理/25-并发、冲突与幂等/25.4-幂等设计与去重.md)） |
| **并发** | 两个 App 同时改同一属性 | version CAS，冲突方读最新再改（[25.1 乐观并发与悲观并发](../../L1-分布式原理/25-并发、冲突与幂等/25.1-乐观并发与悲观并发.md)） |

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：影子文档存 **Redis 7.2**（一台设备一份 JSON，key 带兜底 TTL）；替代方案是 MySQL JSON 列或云厂商托管 KV（设备量大、团队不想运维时）。Redis 只存「最新文档」，历史数据进时序库（[44.17 时序数据库](../44-数据库/44.17-时序数据库.md)）。

**可抄**（Alpine 容器内，Redis 7.2.9；`EX` 是影子文档的兜底过期，`desired` 的业务过期另做）：

```bash
apk add --no-cache redis             # 容器演示；生产要开 AOF/RDB，否则重启丢期望值
redis-server --daemonize yes --save "" --appendonly no
# ① 初始化影子文档：version=7，7 天过期
redis-cli SET "shadow:ac:gw-1001" '{"version":7,"desired":{"power":true},"reported":{"power":true}}' EX 604800
# ② 文档级 CAS：GET 文档 → 比 version → 写入新文档并保留 TTL
#    注意比较的是同一份影子文档（不是另开一个全局版本 key，那样多设备会互相干扰）
redis-cli EVAL 'local d=cjson.decode(redis.call("GET",KEYS[1])); if d.version==tonumber(ARGV[1]) then redis.call("SET",KEYS[1],ARGV[2],"KEEPTTL") return 1 else return 0 end' \
  1 shadow:ac:gw-1001 7 '{"version":8,"desired":{"power":true,"target_temp":26},"reported":{"power":true}}'
```

**可验**（本机容器实测输出；为省篇幅，JSON 与 Lua 用 `…` 省略，完整命令见上面的可抄）：

```text
$ redis-cli -v
redis-cli 7.2.9
$ redis-cli SET "shadow:ac:gw-1001" '{"version":7,...}' EX 604800
OK
$ redis-cli EVAL '<上面的 Lua>' 1 shadow:ac:gw-1001 7 '{"version":8,...}'
1
$ redis-cli GET shadow:ac:gw-1001
{"version":8,"desired":{"power":true,"target_temp":26},"reported":{"power":true}}
$ redis-cli TTL shadow:ac:gw-1001
604800
# 再用旧版本 7 试一次：应返回 0，文档不被覆盖
$ redis-cli EVAL '<上面的 Lua>' 1 shadow:ac:gw-1001 7 '{"version":9,...}'
0
$ redis-cli GET shadow:ac:gw-1001
{"version":8,"desired":{"power":true,"target_temp":26},"reported":{"power":true}}
```

读法：第一次 CAS 返回 **1**、文档 7→8 且 TTL 保持 604800；再用旧版本 7 返回 **0**、文档仍是 8——冲突被原子地挡住。把「比较 + 写」放进 Lua 是因为 Redis 单命令原子，而「读出来再写回去」在两条命令之间会插入别人的写。

**可退**：升级/回滚时 `redis-cli DEL shadow:ac:<device>`，影子会按设备下一次上报重建；也可以把读路径切回 DB（双写过渡期）；文档里保留 `version` 便于对账。注意 TTL 是整份文档的兜底，**不等于 desired 的业务过期**——desired 要单独设过期字段或清理任务。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只有 reported，没有 desired | 无法表达「设备该是什么样」，远程设置只能靠一次性命令，离线即丢 |
| 用全量影子代替 delta 下发 | 弱网下每次重连传整份文档，流量与电量翻倍 |
| 设备上报不校验物模型 | 未知属性/类型错误写进影子，下游时序库建表失败或字段污染 |
| 影子服务不做 version CAS | 两个 App 并发改，后写的静默覆盖，用户看到「设置没生效」 |
| 把高频遥测（每秒一条）写进影子 | 影子文档每秒重写，Redis 带宽与持久化压力暴涨 |
| 影子的 reported 直接取设备时间排序 | 设备时钟回拨导致新值被旧值覆盖 |
| 期望值没有过期/清理 | 设备永远不回来，desired 一直挂着，delta 每次重连都下发 |
| 把事件/告警塞进影子属性 | 影子变成事件表，delta 无意义且不断膨胀 |

## 自检

**Q1** 设备在线时，影子服务还要不要参与每次上报？

▸ 答案：要参与，但它的角色是「校验 + 合并 + 算差量」，不是转发。设备上报必须过物模型校验写入 reported，同时清掉对应 delta；如果绕过影子直写数据库，desired 与 reported 会失去唯一事实来源，远程设置与设备实况就无法对账。

**Q2** 为什么 delta 只遍历 desired，而不遍历 reported？

▸ 答案：delta 的语义是「设备还需要改什么」，只由期望值驱动。reported 里多出来的属性（设备自采的温度、自己发现的能力）不是需要下发的目标；如果遍历 reported，会把「设备有、云端没要求」的属性也当成差异，产生无意义下发甚至覆盖设备本地策略。

**Q3** 版本号 CAS 和「最后写入胜出」相比，多解决了什么问题？

▸ 答案：会静默丢更新。两种典型场景：① 两个 App 同时改**同一个属性**（都设 target_temp），后写的直接盖掉先写的，用户看到「我设的 22℃ 变成了 24℃」；② 客户端「读整份文档 → 本地改 → 整份写回」，即使改的是不同属性，写回时也会用本地旧值覆盖对方的新值。CAS 让后写者收到冲突、读最新值重算，两次修改都不丢；代价是多一次重试与一个错误分支。

**Q4** 影子里的 desired 需要过期时间吗？什么时候不需要？

▸ 答案：需要。设备可能永远不回来（退货、报废、断网数月），desired 一直挂着会让每次重连都下发一条早已无意义的命令，甚至重连风暴时放大流量。给 desired 设 TTL（比如 7 天）或按「设备最后在线时间」清理；如果业务语义要求「设置永久有效」（如门锁密码），则显式标注豁免。

**Q5** 物模型的 `access: "r"` 属性为什么不能允许下行？

▸ 答案：`r` 表示这个值只能由设备产生（如当前温度、电量）。允许下行会制造两个真相：云端写一个「当前温度」，设备上报另一个，影子无法判断哪个对，delta 会永远清不掉，还会误导用户。只读属性要从物模型入口就拒绝下行。

**Q6** 一个属性既想下发、又想区分「设备是否执行成功」，影子够用吗？

▸ 答案：影子只能表达「期望」和「最后一次上报」，不表达「执行中/失败原因」。要区分执行结果，得用服务调用（带 request id 与返回码）或事件（`set_result` 事件），把结果作为事件上报；影子只保留最终状态。把执行过程塞进影子会让 delta 语义混乱。

**Q7** 如果设备上报的属性比物模型多（新固件加了属性），云端应该怎么办？

▸ 答案：先物模型后固件是铁律：物模型里没有的属性，入口直接拒绝并记录（便于发现「悄悄上线的新固件」），而不是静默丢弃。若确实要支持新属性，先发布物模型（云端已认识），再灰度固件；删属性则相反——先让固件不再上报，等全量升级完再删物模型。
