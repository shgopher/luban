# 69.3 海量连接与消息

## 一句话

> 海量连接的解在接入层（收敛、分片、会话），海量**消息**的解在链路设计（分路、合并、限放大）；把两者混为一谈，就会出现「连接数达标了，后端被消息打穿」。

## 边界：连接机制不在这里重讲

[43.11 MQTT 与海量连接](../43-消息队列/43.11-MQTT与海量连接.md) 已经把「单连接 4–5KB、Proxy 收敛、Broker 分片、会话存哪、重连风暴」讲透了，本节只引用它的结论。本节回答的是连接建立**之后**的事：一条上报从设备到数据库要经过几段、哪一段会放大、放大多少倍、怎么在源头把量压下来。

## 先破除三个误区

| 误区 | 现实 |
|---|---|
| 「100 万连接 = 100 万条/秒」 | 连接数是**存量**，消息速率是**流量**。100 万设备每 30 秒上报一次只有 **3.3 万条/秒**；真正决定容量的是上报频率与每次的报文大小 |
| 「消息丢了无所谓，反正是传感器数据」 | 遥测丢几条确实无所谓；但**命令**和**事件**（告警、门锁开启）丢一条就是事故。三类消息要不同的通道（群控是命令的批量形态，还要单独限速），不是一个 QoS 走天下 |
| 「broker 能扛住就够了」 | broker 只负责转发；放大后的消息会打到规则引擎、时序库、应用。fan-out 1:100 时，broker 的 1 万条入站就是 100 万条出站 |

## 三类消息 + 群控：四条通道

| 类别 | 方向 | 频率 | 可靠性 | 通道 | 落库 | 丢一条的后果 |
|---|---|---|---|---|---|---|
| **遥测**（温度、电量、位置） | 上行 | 秒–分钟级 | QoS 0 可接受 | 设备 → 接入 → 消息队列 → 时序库 | 时序库（[44.17 时序数据库](../44-数据库/44.17-时序数据库.md)） | 曲线缺一个点，可插值 |
| **事件**（告警、故障、开门） | 上行 | 低频、突发 | at-least-once + 幂等 | 设备 → 接入 → 消息队列 → 规则/告警 | 事件表 + 消息队列 | 告警漏报，**必须补** |
| **命令**（开关、重启、OTA 触发） | 下行 | 低频 | at-least-once + 幂等 + 超时 | 应用 → 命令服务 → 设备主题 | 命令表（状态机） | 用户操作无响应，**必须可重试** |
| **群控/广播**（全屋关灯、批量参数） | 下行 | 极低频、**强放大** | 尽力 + 分批 | 应用 → 分组主题 → 共享订阅网关 | 任务表 + 进度 | 部分设备不生效，要可重放 |

> 🔑 分路的判据是「**这条消息丢了，谁赔**」：能插值的是遥测，能补发的是事件，能让用户再点一次的是命令。三类混在一个队列里，一定是可靠性向最松的那类看齐。

投递语义（at-most / at-least / exactly-once）的通用定义见 [43.2 投递语义 (at-most / at-least / exactly-once)](../43-消息队列/43.2-投递语义.md)，本节只讲 IoT 侧怎么按语义分通道。

## 先算容量：从设备数到每秒消息数

| 输入 | 公式 | 100 万设备时的值 |
|---|---|---|
| 遥测上报速率 | 设备数 ÷ 上报周期 | 30s 一次 → **33,333 条/秒**；5s 一次 → **200,000 条/秒** |
| 心跳 | 设备数 ÷ keepalive | 60s → **16,667 包/秒**（心跳也是流量） |
| 群控投递 | 设备数 × 命令条数 | 一次全量开关 → **1,000,000 条投递** |
| 时序落库 | 点数/秒 × 86400 | 30s 一次 → **28.8 亿点/天**；按 [44.17](../44-数据库/44.17-时序数据库.md) 的 2–5 B/点压缩 → **5.8–14.4 GB/天** |

容量规划见 [39.2 容量规划](../../L3-质量属性/39-成本/39.2-容量规划.md)：先按这张表算出「峰值条/秒」，再乘以单条成本，才知道要几台 broker、几个分区。**不先算这一步，后面所有架构讨论都是猜。**

## 实测：单 broker 到底能扛多少

环境：Alpine 3.20 容器，mosquitto 2.0.18 单进程（单线程），压测客户端为手写 MQTT 3.1.1 最小客户端（Go 1.27.1 静态编译），broker 与客户端同容器、回环网络、纯明文无 TLS。

| 指标 | 实测值 | 说明 |
|---|---|---|
| 单连接内存（broker） | **886–887 B/连接** | 5000 连接 +4,328 KB（886.4 B/条）、20000 连接 +17,324 KB（887.0 B/条） |
| 建连速率 | 10,381 条/秒（5000 连接）；3,388 条/秒（20000 连接） | 断线风暴时按这个数估恢复时间 |
| QoS 0 发布吞吐 | **684,652 条/秒**（100B 载荷；载荷 68.5 MB/s，含主题与协议头约 91 MB/s 线上） | 无订阅者，只有入站解析 |
| QoS 1 发布吞吐 | **20,369 条/秒** | 逐条等 PUBACK，受往返时延限制 |
| 单订阅者接收 | 233,008 条/秒（发布侧速率） | 5 万条全部收到，无丢失 |
| fan-out 50 | 246,675 条/秒投递 | 端到端 10 万条投递耗时 405ms |
| fan-out 500 | 161,082 条/秒投递 | 端到端 25 万条投递耗时 1.55s |

读数：

- **QoS 1 比 QoS 0 慢 34 倍**（2 万 vs 68 万）：不是 broker 慢，是「每条都等一次往返」的物理代价。遥测用 QoS 0 + 幂等/去重，是容量设计里最划算的一刀。
- **fan-out 会打满 CPU 而不是内存**：50 个订阅者时，2000 条入站变成 10 万条投递（**放大 50 倍**），端到端 405ms，投递吞吐 24.6 万条/秒——压力全在 broker 的编码与发送上。广播类操作必须限速分批。
- 886 B/连接是**裸连接**的成本；加上 TLS 会话、订阅树、未确认消息、会话存储，真实单连接成本通常是这个数的几倍到十几倍（[43.11](../43-消息队列/43.11-MQTT与海量连接.md) 有完整成本分层）。

## 消息放大：两次乘法决定了架构

```
一次群控 = 1 条入站 × N 台设备，投递量 = N
一次上行 = 1 条入站 × M 个消费方（规则/告警/时序/App），投递量 = M
```

| 操作 | 放大倍数 | 100 万设备时的投递量 | 允许的频次（按 20 万条/秒投递预算） |
|---|---|---|---|
| 单设备命令 | 1 | 1 条 | 不限 |
| 分组群控（1% 设备） | 10,000 | 1 万条 | 每秒 20 次 |
| 全量群控 | 1,000,000 | 100 万条 | **每分钟 12 次**（假设投递预算 20 万条/秒，按实测替换） |
| 上行规则多路消费 | 3–5 | 10 万条/秒 | 需要独立消费集群，不能和 broker 抢 CPU |

控制放大的三个手段：

| 手段 | 做法 | 代价 |
|---|---|---|
| **共享订阅** | 多个网关实例用同一 `$share/<group>/<topic>` 订阅，每条消息只投给组内一个实例 | 只解决「多个消费者」，不解决「每设备一条」 |
| **分批 + 限速** | 群控按 1%/分钟推进，令牌桶控制下发速率 | 生效变慢（100 万设备全量要 100 分钟） |
| **聚合/降采样** | 边缘侧先聚合（10 条变 1 条），云端只收聚合值 | 丢失单点细节，排障要能回溯原始数据 |

共享订阅是可用产品直接验证的：两个实例订阅同一共享组，8 条命令被 4/4 均分（实测）：

```text
$ mosquitto_sub -t '$share/gw/dev/+/cmd' -v &   # 实例 1
$ mosquitto_sub -t '$share/gw/dev/+/cmd' -v &   # 实例 2
$ for i in 1 2 3 4 5 6 7 8; do mosquitto_pub -t dev/1001/cmd -m "m$i"; done
实例 1 收到 m1 m3 m5 m7；实例 2 收到 m2 m4 m6 m8
```

## 上行合并：把 1000 条压成 1 条

同网关下 100 台设备、每台 10 条约 50B 的遥测（JSON 含设备名与时间戳），逐条发 vs 按 1s 窗口合并发（Go，本机实测）：

```go
type pack struct {
	BatchID string `json:"batch"`
	Data    map[string]struct {
		TS   []int64   `json:"t"`
		Temp []float64 `json:"v"`
	} `json:"data"`
}
// 逐条：每条都带主题 + 时间戳 + 设备名
// 合并：设备名只出现一次，时间戳用差分友好的数组
```

```text
逐条上报：1000 条，共 54000 字节
合并上报：1 条，共 18464 字节
合并后为原来的 34.2%，省 65.8% 字节
```

完整代码在仓库 [tools/examples/69.3-batch/](../../../tools/examples/69.3-batch/README.md)，`go run .` 可复现这组数字。

> 🔑 合并的收益来自「**去掉重复的元数据**」：设备名、主题、批次信息从 1000 份变成 1 份。但合并有代价：**延迟**（等窗口）与**失败重放粒度**（一批失败要整批重发）——遥测可以合，事件和命令不要合。合并最好在边缘做（先聚合、再上传），见 [69.4 边缘计算与断网续传](69.4-边缘计算与断网续传.md)。

## 下行通道：别用广播解决问题

| 方案 | 做法 | 适用 | 坑 |
|---|---|---|---|
| 每设备主题 | `dev/{id}/cmd`，设备订阅自己 | 单设备命令 | 群控要发 N 条 |
| 分组主题 | `group/{gid}/cmd`，组内设备订阅 | 群控 | 组变更要重订阅，组大小决定放大 |
| 共享订阅网关 | 网关用 `$share` 订阅，网关再推给设备 | 设备不能订阅（如 NB-IoT） | 网关要维护「设备在线表」 |
| 广播主题 | 一个主题全网订阅 | 极少用 | 一次误发 = 全网设备执行 |

人的长连接网关也做「连接路由 + 下行投递」，但面向的对象与消息模型不同，对照见 [66.1 长连接网关](../66-即时通信与音视频/66.1-长连接网关.md)。

命令通道必须有的四件东西：**命令 ID（幂等键）、超时时间、执行结果上报、状态机（待下发/已下发/成功/失败/超时）**。少了任何一件，「命令丢了」和「设备没执行」就分不清。

## 背压与丢弃：先定「丢谁」，再谈扩容

| 压力来源 | 策略 | 丢失的东西 | 什么时候用 |
|---|---|---|---|
| 上行超过写入能力 | 边缘聚合 / 降采样 | 单点细节 | 遥测，且历史可接受降采样 |
| 队列积压超过阈值 | 丢弃最旧（按设备公平丢弃） | 旧数据 | 只关心最新状态（状态类） |
| 命令通道过载 | 拒绝新命令（快速失败）+ 退避 | 新命令（用户可重试） | 命令类，不能静默丢 |
| 单设备刷屏 | 设备级限速（令牌桶） | 超出部分 | 任何类别，防止一台拖垮全站 |
| 全链路过载 | 分级降级：先关遥测，再关非关键事件，命令保底 | 按级别 | 容量事故（[35.6 熔断与降级](../../L3-质量属性/35-可用性/35.6-熔断与降级.md)） |

> ⚠️ 最常见的错误是「**所有消息一视同仁地丢**」：遥测和命令共用一个队列，过载时命令被遥测挤掉，用户看到「设备失控」。分队列、分优先级、分别限流，是容量设计的一部分。

## 落库：把「写多」变成「批量写」

时序数据的写入成本主要在**每次写的固定开销**（建连接、事务、索引、网络往返），不在数据本身。所以：

| 做法 | 效果 | 代价 |
|---|---|---|
| 单条 INSERT | 每次一个往返，10 万点/秒需要海量连接 | 不可行 |
| 批量写（500–5000 点/批） | 固定开销被摊薄，吞吐提升一个数量级 | 延迟增加（攒批时间） |
| 按设备/时间分区 | 删除变成整块丢弃（[44.17](../44-数据库/44.17-时序数据库.md)） | 跨分区查询变贵 |
| 冷热分层 | 90 天前降采样/归档（[39.3 存储分级](../../L3-质量属性/39-成本/39.3-存储分级.md)） | 查询路径变复杂 |

批量大小的判据：**批越大，吞吐越高、崩溃丢的越多**。遥测能接受丢几秒 → 批 1–5 秒；事件/命令不能 → 单独链路、单条确认。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：≤ 10 万设备用 **Mosquitto 2.0.18**（单机、单线程、运维最轻）；10 万–100 万沿用 [43.11](../43-消息队列/43.11-MQTT与海量连接.md) 的路线——**开源 broker + 前置 Proxy**，或云厂商 MQTT 服务（要原生集群、共享订阅、规则引擎、Prometheus 指标时可评估 **EMQX 5.x**）；>100 万见 43.11 的分界线。

**可抄**（在 69.1 起好的容器里执行，验证共享订阅与 broker 指标）：

```bash
# 1) 两个网关实例加入同一共享组
docker exec mqtt mosquitto_sub -h 127.0.0.1 -t '$share/gw/dev/+/cmd' -v &
docker exec mqtt mosquitto_sub -h 127.0.0.1 -t '$share/gw/dev/+/cmd' -v &
# 2) 发 8 条命令
for i in 1 2 3 4 5 6 7 8; do docker exec mqtt mosquitto_pub -h 127.0.0.1 -t dev/1001/cmd -m "m$i"; done
# 实测输出（两个订阅端各 4 条，无重复）：
#   实例 1                         实例 2
#   dev/1001/cmd m1                dev/1001/cmd m2
#   dev/1001/cmd m3                dev/1001/cmd m4
#   dev/1001/cmd m5                dev/1001/cmd m6
#   dev/1001/cmd m7                dev/1001/cmd m8

# 3) 看 broker 级指标（容量规划的输入）
docker exec mqtt mosquitto_sub -h 127.0.0.1 -t '$SYS/broker/messages/received' -C 1 -W 15
# 实测输出：255591          （broker 累计入站条数）
docker exec mqtt mosquitto_sub -h 127.0.0.1 -t '$SYS/broker/load/messages/received/1min' -C 1 -W 15
# 实测输出：6.32            （最近一分钟每秒平均入站条数）
# 注意 $SYS 默认按 sys_interval=10s 刷新，-W 要给够一个周期
```

| 检查点 | 通过判据 | 失败常见原因 |
|---|---|---|
| 共享订阅生效 | 每条命令只被一个实例收到 | broker 不支持 `$share`（老版本）或组名写错 |
| 指标可读 | `$SYS/broker/messages/received` 有数值 | 主题被禁用 `$SYS` / ACL 拦截 |
| 放大可控 | 群控时 `load/messages/sent` 不超过预算 | 没做分批，一次性全量下发 |

**可退**：群控任务用「任务表 + 进度」实现，发现异常时把任务状态置为暂停，已下发的不可撤回（设备侧命令要幂等，重放安全）；broker 侧回滚 = 切回上一个配置版本并重启（连接会断，选低峰）。

## 反模式

| 反模式 | 后果 |
|---|---|
| 遥测与命令共用一个队列/一个 QoS | 过载时命令被遥测挤掉，表现为设备失控 |
| 用 QoS 2 做「不重复」 | 吞吐减半、延迟翻倍，端到端仍不闭环；正解是 QoS 1 + 业务幂等（[43.6](../43-消息队列/43.6-可靠投递与幂等消费.md)） |
| 群控一次性全量下发 | 投递量瞬间 1:N 放大，broker CPU 打满，重连风暴叠加 |
| 每设备一个主题却不做主题规划 | 百万主题压 broker 元数据，见 [43.11](../43-消息队列/43.11-MQTT与海量连接.md) |
| 命令没有命令 ID 与结果上报 | 「发了没反应」无法定位是丢了还是设备没执行 |
| 只看连接数不看消息速率 | 连接数达标，但 1 万条/秒的上报把时序库打挂 |
| 批量写不设上限 | 一批攒 10 万点，崩溃丢 10 万点、内存峰值得按批大小预留 |
| 下行用广播主题图省事 | 一次误发让全网设备执行同一条命令 |

## 自检

**Q1** 100 万设备、每 30 秒上报一次，每秒多少条上行？为什么 QoS 0 的 68 万条/秒不能直接除出「能带多少设备」？

▸ 答案：33,333 条/秒。不能直接除，因为实测的 68 万条/秒是「无订阅者、纯入站、单条 100B、无 TLS」的理想值；真实系统要加 TLS、加规则引擎消费、每个订阅者一份投递、还要算心跳与重连峰值。正确做法是把 33,333 条/秒乘以放大倍数与单条成本，再留 2–3 倍余量。

**Q2** fan-out 50 时投递 24.6 万条/秒，入站只有 2000 条——瓶颈为什么在 CPU 而不在内存？

▸ 答案：每条消息要被复制并写到 50 条连接，CPU 花在协议编码、连接查找、内核发送上；内存只增加订阅关系与少量缓冲。所以扩容 fan-out 场景优先加实例/分片，而不是加内存；同时要在业务层限制广播频次与范围。

**Q3** 为什么「上行可以合并，命令不能合并」？

▸ 答案：上行合并只影响数据精度与延迟，失败重放的粒度变大但可接受（遥测丢了可插值）；命令合并会改变语义——两条命令（开灯、关灯）合并成一个批次，执行顺序与失败处理都变得不明确，且用户期望每条命令有独立结果。命令要单条确认、单条重试、单条回报。

**Q4** 共享订阅解决了什么问题，没解决什么问题？

▸ 答案：解决「多个消费者如何分摊同一主题的消息」，让网关/消费实例水平扩展时不会每条消息被所有实例处理（实测 8 条被 4/4 均分）。没解决「一条消息要投给 N 台设备」的放大问题，也没解决「消费实例挂了，分到的消息谁补」——后者要靠确认与重投策略。

**Q5** 队列积压时「丢最旧」和「丢弃新的」怎么选？

▸ 答案：看数据语义。状态类（最新温度、最新位置）丢旧留新，读到的旧值没有意义；事件类（告警、开门记录）必须保留，宁可拒绝新事件也不能丢已产生的；命令类不能静默丢任何一条，要快速失败并让调用方决定重试。三种语义对应三种队列策略，混在一起就必然出错。

**Q6** 「设备在线表」为什么是下行网关的关键，它和 broker 的会话状态是什么关系？

▸ 答案：broker 的会话状态只说明「这个 client id 有没有会话、有没有未确认消息」，不直接给出「设备此刻在哪条连接、由哪台网关服务」。网关做共享订阅时，要自己维护 device→gateway 的在线表才能把命令推到正确的连接；否则只能依赖共享订阅的随机分配，设备不在线时必须退回会话补发或影子（[69.2](69.2-设备影子与物模型.md)）。

**Q7** 每秒 33,333 条遥测、每条 100B，一年要存多少？这个数对架构意味着什么？

▸ 答案：33,333 × 100B × 86400 ≈ 288 GB/天的**原始**量（未压缩），压缩后按 2–5 B/点算约 6–14 GB/天，一年 2–5 TB。意味着：① 存储必须分层（热 7–30 天、冷归档）；② 采样/聚合要在边缘做，不能全量上云；③ 保留策略要写进架构，而不是等磁盘满了再删。
