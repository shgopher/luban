                    69.1 设备接入与协议 (MQTT / CoAP)

                    一句话

                    设备接入只回答三件事：这台设备凭什么被信任、连上之后消息怎么走、掉线之后算不算数；协议选型（MQTT / CoAP / HTTP）是这三条约束的结果，不是原因。

                    先破除三个误区

                    误区 现实
                    「设备接入 = 装个 MQTT broker」 broker 只解决「连上」；认证、会话、下行、限速、踢下线、影子初始化都是接入层的一部分
                    「CoAP 就是 UDP 版 HTTP，物联网都该用它」 CoAP 省的是握手和头部，代价是没有可靠会话、要自己处理重传与 NAT 超时；有稳定 TCP 的场景用 MQTT 更省事
                    「QoS 1 就是可靠投递」 QoS 1 只保证「到达 broker」，不保证「业务只执行一次」；端到端语义要业务幂等兜底（见 43.6 可靠投递与幂等消费）

                    接入层要做的六件事

                    # 动作 判据 做错的后果
                    1 设备身份（认证） 每台设备一个唯一凭据，能单独吊销 一台设备泄露 = 全网可伪造
                    2 注册与建档（物模型绑定） 设备属于哪个产品、有哪些属性 上报的属性云端不认识，数据进不了库
                    3 连接（协议/端口/保活） 心跳周期 < NAT 老化时间 半开连接堆积，fd 与内存被僵尸连接吃光
                    4 消息路由（上行/下行） 每设备一个专属主题或一个共享主题组 主题爆炸或串消息
                    5 会话（离线补发） 明确「掉线期间的消息要不要补」 该补的丢了、不该补的重复执行
                    6 接入治理（限速/踢下线/证书轮换） 单设备速率上限、连接数上限 一台设备刷爆集群，或旧固件永远不升级

                    设备接入与 IM 的长连接网关同属「有状态接入层」，但两者关心的东西不同：人的连接关心在线状态与多端同步，设备连接关心会话补发与省电，对照见 66.1 长连接网关。

                    🔑 六件事里只有第 3 件是协议自带的；其余五件是接入层的设计，换协议不会自动变好。

                    协议选型：先看物理约束，再看功能

                    协议 传输 头部开销 下行能力 适合 不适合
                    MQTT 3.1.1 / 5 TCP（或 TLS，或 WebSocket） 固定头最小 2 字节；QoS 1 一次 PUBACK broker → 设备推送（订阅） 需要双向、要补发、有稳定 TCP 的设备：家电、充电桩、车机 只能发 UDP、或极端省电的传感器
                    CoAP UDP（DTLS），另有 TCP/TLS 变体 固定头 4 字节 + token + option 服务端 Observe 通知（RFC 7641） 受限网络、NB-IoT、局域网设备发现与控制 需要长会话与大量下行广播
                    HTTP(S) TCP 请求头通常几百字节 只能轮询或长轮询 低频、设备资源充足、要复用现成运维体系 高频遥测、弱网、电池供电
                    LwM2M CoAP（可跑 TCP） 同 CoAP 注册/管理/固件升级一体化 运营商设备管理、需要标准设备管理模型 不想引入 OMA 规范的小团队
                    私有 TCP 协议 TCP 自定义，可以更小 自定义 有历史包袱或极端定制 新项目：协议要自己维护，生态与工具全无

                    💡 选择顺序：设备能不能连稳定 TCP → 能则 MQTT，不能则 CoAP；要不要标准设备管理 → 要则 LwM2M；上报频率低于分钟级且设备有电 → HTTP 也能用。

                    MQTT 与 CoAP 的机制对照（决定架构的差异）

                    维度 MQTT CoAP 架构含义
                    连接模型 长连接 + 会话（clean session / session expiry） 无连接，请求响应 + Observe MQTT 的「在线」是连接态；CoAP 的「在线」要自己维护
                    可靠性 QoS 0/1/2，broker 存储未确认消息 CON 消息带 ACK + 重传（默认 2s 起、指数退避），无跨请求会话 CoAP 的重传只管这一条消息，掉线期间的命令不会补
                    下行 broker 推送（订阅主题） Observe 通知，或设备轮询 Observe 依赖 NAT 绑定存活；超时后通知就断
                    报文开销 固定头最小 2 字节（规范值）；连接/会话流程见 43.11 MQTT 与海量连接 本机实测：CON GET /time 请求 17 字节，响应 24 字节 弱网/计量网络里，头部开销直接决定流量与电量
                    安全 TLS（1.2/1.3）、mTLS DTLS 1.2 / CoAP over TLS 两者都能做双向证书，但 DTLS 在 UDP 上的运维（NAT、重连）更麻烦
                    典型端口 1883（明文）/ 8883（TLS）/ 8083（WS） 5683（UDP）/ 5684（DTLS） 企业网络里先确认这些端口放不放行

                    CoAP 的实测（coap-client v4.3.4a，coap-server，本机回环）：

                    $ coap-client -m get -v 9 coap://127.0.0.1/time
v:1 t:CON c:GET i:20a7 {01} [ Uri-Path:time, Request-Tag:0x6b7ecc85 ]
netif: sent   17 bytes
v:1 t:ACK c:2.05 i:20a7 {01} [ Content-Format:text/plain, Max-Age:1 ] :: 'Nov 21 08:24:28'
netif: recv   24 bytes

                    读法：一条 GET 的协议开销只有 4 字节头 + 1 字节 token + 选项，所以 CoAP 才适合「一条消息只有几个字节」的计量场景。但注意响应里的 Max-Age:1——/time 是可观察资源，通知的可靠性靠 Observe 序号 + 客户端重注册，不是靠会话。

                    三个决定接入架构的细节

                    ① 会话：掉线补发是业务语义，不是协议细节

                    MQTT 用 clean session（3.1.1）或 session expiry interval（5.0）控制「掉线后会话留多久」。本机实测（mosquitto 2.0.18）：

                    # clean session=false：设备离线期间发布的 QoS1 消息，重连后补发
$ mosquitto_sub -c -i gw-1001 -q 1 -t dev/1001/cmd -v -W 2   # 首次订阅后超时退出
Timed out
$ mosquitto_pub -t dev/1001/cmd -m '{"op":"reboot"}' -q 1    # 设备离线期间发布
$ mosquitto_sub -c -i gw-1001 -q 1 -t dev/1001/cmd -v -W 2   # 同一 client id 重连
dev/1001/cmd {"op":"reboot"}

# clean session=true：同样的操作，重连后什么都收不到
$ mosquitto_sub -i gw-2002 -q 1 -t dev/2002/cmd -v -W 2
Timed out
$ mosquitto_pub -t dev/2002/cmd -m offline -q 1      # 设备离线期间发布
$ mosquitto_sub -i gw-2002 -q 1 -t dev/2002/cmd -v -W 2
Timed out                                            # 无输出：会话没保留，离线消息直接丢

                    再补一个容易踩的点：QoS 0 + 保留会话，默认补不回来。MQTT 3.1.1 只说 broker「可以」为离线客户端排队 QoS 0，mosquitto 默认 queue_qos0_messages=false；实测同样流程（离线期间发一条 QoS 0，重连）订阅端什么都收不到：

                    # QoS 0 + clean session=false：离线期间发布，重连收不到
$ mosquitto_sub -h 127.0.0.1 -c -i gw-q0 -q 0 -t dev/q0/cmd -v -W 2
Timed out
$ mosquitto_pub -h 127.0.0.1 -t dev/q0/cmd -m q0-offline -q 0
$ mosquitto_sub -h 127.0.0.1 -c -i gw-q0 -q 0 -t dev/q0/cmd -v -W 2
Timed out                              # 无输出

# 对照 QoS 1 + clean session=false：同一场景能收到
$ mosquitto_sub -h 127.0.0.1 -c -i gw-q1 -q 1 -t dev/q1/cmd -v -W 2
Timed out
$ mosquitto_pub -h 127.0.0.1 -t dev/q1/cmd -m q1-offline -q 1
$ mosquitto_sub -h 127.0.0.1 -c -i gw-q1 -q 1 -t dev/q1/cmd -v -W 2
dev/q1/cmd q1-offline
Timed out

                    🔑 三条判据：命令类（开关、重启）要补 → 会话保留 + QoS 1；状态类（温度）不要补 → 报最新值即可；会话保留时长决定设备最长能离线多久才丢命令；经验值是按「设备最坏断网时长 × 2」设（我的判断，按你的设备画像校准——保留越久，broker 侧要留的未确认消息越多）。

                    ② retain 不是设备影子

                    retain 让新订阅者立刻拿到某主题最后一条消息：

                    $ mosquitto_pub -t dev/3003/state -m '{"on":true}' -q 1 -r
$ mosquitto_sub -t dev/3003/state -C 1 -W 2 -v
dev/3003/state {"on":true}

                    它只有「最后一条」，没有期望值/上报值两份状态、版本号、差量计算——拿 retain 当影子，会出现「设备上报覆盖了云端期望值」的经典 bug。影子单独在 69.2 设备影子与物模型 讲。

                    ③ 接入鉴权：三种设备身份方案

                    方案 做法 优点 代价 适用
                    一机一密 每台设备独立密钥/证书，云端可单独吊销 泄露影响面 = 1 台 签发与轮换要 PKI/密钥服务 量产设备（推荐默认）
                    一型一密 同一型号共用密钥，靠设备 ID 区分 产线简单 一台泄露 = 全型号可伪造 内部/低价值设备
                    动态注册 设备用出厂凭据换临时证书（类似 bootstrap） 首装免烧录、可轮换 需要注册服务与风控 大型 fleet、代工厂生产

                    证书用 mTLS（8.6 TLS 握手、证书与 mTLS），密钥放安全存储（TPM/SE/Keychain），吊销走 CRL/OCSP 或短期证书 + 续签。设备身份一旦可伪造，后面所有数据都不可信（38.4 加密 (对称 / 非对称 / TLS / 密钥管理)）；命令重放、凭据窃取属于常见攻击面，见 38.6 常见攻击 (注入 / XSS / CSRF / SSRF / 越权 / 重放)。

                    生产落地：指名 → 可抄 → 可验 → 可退

                    指名：接入层用 Eclipse Mosquitto 2.0.18（单机、单线程、运维最轻）。规模分界线沿用 43.11 的工程经验值：≤10 万设备用开源 broker 单集群，10 万–100 万要加前置 Proxy 或上云服务；单机到底能带多少，要按你的 TLS 比例与消息速率实测——本章只验到 2 万连接。更大规模换 EMQX 5.x（原生集群、共享订阅、规则引擎）或云厂商 MQTT 服务。下面命令用容器跑，宿主机不需要装 broker。

                    可抄（Alpine 3.20 容器内，broker 监听 1883，允许匿名——仅用于验证，生产必须开认证）：

                    docker run -d --name mqtt -p 1883:1883 alpine:3.20 sh -c '
apk add --no-cache mosquitto mosquitto-clients >/dev/null 2>&1
cat > /tmp/m.conf <<EOF
listener 1883 0.0.0.0
allow_anonymous true
persistence true
persistence_location /tmp/
EOF
exec mosquitto -c /tmp/m.conf'

# 可验 1：订阅端（另开终端）
docker exec mqtt mosquitto_sub -h 127.0.0.1 -t 'dev/+/temp' -q 1 -v
# 可验 2：发布端，QoS 1
docker exec mqtt mosquitto_pub -h 127.0.0.1 -t 'dev/1001/temp' -m '{"t":23.5}' -q 1
# 实测输出（订阅端）：dev/1001/temp {"t":23.5}

# 可退：恢复上一版 mosquitto.conf 并重启（persistence 目录在，会话与 retained 消息不丢）；
#      设备侧把域名/端口切到备用 broker 即可整体回退。
# 验证完清理环境（数据随容器删除）：
docker rm -f mqtt
                    检查点 通过判据 失败常见原因
                    broker 起来 docker exec mqtt mosquitto -h 打印版本 端口被占 / 配置语法错，看 docker logs mqtt
                    收发 发布后订阅端立刻收到 通配符写错（+ 只匹配一层，# 才是多层）
                    会话 断开重连能收到离线 QoS1 clean session 为 true / 用了另一个 client id
                    权限 生产环境匿名连接被拒 没配 password_file / TLS，或 ACL 没开

                    ⚠️ 生产接入层必须补三样：TLS 8883 端口、per-device 凭据、ACL（设备只能读写自己的主题）。上面的 allow_anonymous true 只是验证用。

                    连接建好之后，设备域的消息怎么分三类通道、怎么控制 fan-out 放大，见 69.3 海量连接与消息。

                    反模式

                    反模式 后果
                    所有设备共用一个密钥 一台设备被逆向，全网可伪造上报与控制
                    用 retain 代替设备影子 设备上报覆盖云端期望值，远程设置静默失效
                    关闭会话（clean session=true）却承诺「命令必达」 设备离线期间命令全丢，用户侧表现为「点了没反应」
                    心跳设得比 NAT 老化还长（如 10 分钟） 半开连接堆积，broker 看似在线实则发不出去
                    把 MQTT 当 RPC 用（一问一答同步等） 弱网下超时重试放大，延迟不可控
                    上报报文塞大 JSON（几 KB） 流量与电量翻倍，弱网下频繁超时；按需压缩/裁剪字段
                    接入层不做限速 一台设备固件 bug 刷上报，打满 broker 与后端
                    CoAP 不加 DTLS 就上公网 命令可被伪造/窃听；UDP 放大反射也会被利用

                    自检

                    Q1 设备用 MQTT、clean session=true，为什么「远程重启」会时灵时不灵？

                    ▸ 答案：命令发布时设备若不在线，broker 不保留会话也就没有离线队列，命令直接丢弃。表现为「在线时灵、离线时丢」。修法是把命令类主题改成 clean session=false + QoS 1（或命令走影子期望值，见 69.2 设备影子与物模型）。

                    Q2 同样一条 20 字节的业务数据，为什么 CoAP 比 HTTP 省得多，而比 MQTT 省得有限？

                    ▸ 答案：CoAP 的协议头是 4 字节固定头 + token + 选项（本机实测一条 GET 请求 17 字节），HTTP 的请求头通常几百字节；MQTT 的固定头最小 2 字节，所以两者在「小报文」上是同一量级，CoAP 的优势在 UDP 无连接、省掉 TCP 握手与保活，而不是头部比 MQTT 小很多。

                    Q3 什么情况下 CoAP 的 Observe 会「悄悄失效」？

                    ▸ 答案：Observe 依赖客户端与服务器之间的 UDP 会话（NAT 绑定、DTLS 会话）。NAT 老化、设备换 IP、DTLS 重协商后，服务器继续往旧地址发通知，设备收不到；协议层没有 MQTT 那种「重连恢复订阅」的机制，必须由设备定时重新注册 Observe（或用 Max-Age 过期后主动重订阅）。

                    Q4 为什么接入层要先定「会话保留多久」，而不是先定 QoS？

                    ▸ 答案：QoS 只决定单条消息在传输链路上的确认次数；「设备离线 3 小时，这期间的控制命令要不要生效」是业务语义，由会话保留时长决定。两者组合才有意义：QoS 1 + 不保留会话 = 离线全丢；QoS 1 + 保留会话 = 能补（可能重复，要幂等）；QoS 0 + 保留会话 默认也补不回来——MQTT 3.1.1 只说 broker「可以」为离线客户端排队 QoS 0，mosquitto 默认 queue_qos0_messages=false（实测重连收不到）。先定语义，再选参数。

                    Q5 一机一密比一型一密贵在哪，值不值？

                    ▸ 答案：贵在 PKI：要签发、下发、轮换、吊销每台设备的证书/密钥，还要在产线安全烧录。值不值看泄露代价：能开锁、能控制车辆/充电桩的设备，一台泄露就是安全事故，必须一机一密；纯采集类、且数据可交叉校验的设备，可以一型一密降成本，但要接受「泄露即全型号」。

                    Q6 为什么接入层的「踢下线」能力是刚需？

                    ▸ 答案：三个场景：① 设备凭据泄露，要立刻断开并吊销；② 设备固件有 bug 疯狂重连，要限速隔离；③ 同一 client id 被两台设备冒用，后连的把先连的踢掉，否则消息会随机串。没有踢下线能力，接入层就无法止损。

                    Q7 只在局域网内、设备资源只有几十 KB RAM，你会选 MQTT 还是 CoAP？为什么？

                    ▸ 答案：CoAP 更合适。MQTT 客户端需要维护 TCP 连接、重连状态、会话（订阅与未确认消息），ROM/RAM 占用更高；CoAP 是无连接请求响应，实现可以做到几 KB。代价是要自己处理重传、Observe 刷新和局域网内的地址发现（mDNS/CoAP discovery）。

                    • 安全：38.4 加密 (对称 / 非对称 / TLS / 密钥管理)、38.6 常见攻击 (注入 / XSS / CSRF / SSRF / 越权 / 重放)
