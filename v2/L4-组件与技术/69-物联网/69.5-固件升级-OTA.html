                            69.5 固件升级 (OTA)

                            一句话

                            OTA 不是「把固件传到设备上」，而是一条带签名、能续传、可回滚、可熔断的发布流水线；它的核心指标是「变砖率」，不是「升级成功率」。

                            先破除三个误区

                            误区 现实
                            「OTA = 上传固件到 CDN，设备下载」 下载只占六步中的一步；签名、校验、刷写、试启动、回滚、批次熔断缺一步就会出事故
                            「校验放在刷写后，反正有问题能回滚」 校验必须在刷写前：把未验证的镜像写进分区，回滚依赖的 bootloader 本身也可能被破坏
                            「升级失败就重试」 重试只能解决网络问题；固件本身有 bug、设备硬件不兼容时，重试只会让更多设备变砖，必须按失败率熔断整个批次

                            OTA 六步，每一步都有失败模式

                            # 阶段 做什么 失败模式 兜底
                            1 构建与签名 出包、算 SHA256、对清单签名 私钥泄露、清单被改 离线签名机 + 公钥内置设备
                            2 发布 上传对象存储/CDN，按批次放量 CDN 缓存旧包、批次过大 SHA 校验兜底 + 1% 起灰度
                            3 下载 断点续传（HTTP Range） 断网、电量耗尽、server 不支持 Range .part 文件 + Range + 校验后续传
                            4 校验 验签 → 大小 → SHA256 篡改、下载不完整 任一失败删除 .part，不写分区
                            5 刷写与切换 写入备用分区，标记待启动 掉电写坏、校验和错 A/B 分区，bootloader 校验失败自动回退
                            6 试启动与提交 新固件启动、自检、上报 启动崩溃、驱动不兼容 试启动计数达阈值自动回滚旧分区

                            🔑 六步里只有第 3 步能靠「重试」修复；其余五步的失败都必须靠设计兜住。把 OTA 当下载问题做，就只能在事故里补回滚。

                            先算两个数：下载时长与批次大小

                            下载时长（决定「什么时候升级、要不要差分」）：

                            网络 持续吞吐（量级） 30MB 固件下载时长（推导） 结论
                            NB-IoT 10–100 kbps 40 分钟 – 6.7 小时 必须差分 + 充电/空闲窗口，且分块续传
                            2G（GPRS/EDGE） 100–500 kbps 8–40 分钟 需要断点续传，且升级任务要错峰
                            3G/4G 1–20 Mbps 12 秒 – 4 分钟 常规方案即可
                            Wi-Fi 10 Mbps+ 秒级 可全量

                            （吞吐是量级估算，用你自己的网络实测值替换；下载时长 = 固件大小 × 8 ÷ 吞吐。）

                            批次大小（决定「一次事故影响多少设备」）：

                            设备总量 首批比例 首批台数 观察窗口 熔断条件（示例）
                            1 万 1% 100 24h 失败率 > 5% 或变砖 > 0
                            100 万 0.1% 1,000 24h 失败率 > 2%；变砖 > 0（任一）
                            工业现场 1 台/现场 按现场 72h 任一现场回滚即暂停

                            ⚠️ 变砖的阈值是 0，不是「小于 0.1%」：能远程回滚的失败可容忍，回不来的设备一台就是线下成本。表里 0.1% 是「首批放量比例」，不是可接受的变砖率。

                            下载：断点续传的三条硬规则

                            规则 1：先写 &lt;fw>.part，校验通过再 rename —— 正式文件一旦存在就必须是完整且已验证的
规则 2：续传靠本地 .part 的大小做 Range 起点，不依赖服务端状态
规则 3：服务端返回 200（不支持 Range）时必须截断重下，不能追加 —— 否则文件拼坏

                            实测（本机 1MB 固件，Go 静态服务 + curl）：

                            === 断点：只取前 100KB ===
HTTP=206 size=102400
=== 续传：从 102400 开始 ===
HTTP=206 size=946176
=== 拼接后校验 ===
66c7761ea38091ed4581eba64bd8cf17555b35bd045079a62191155aa37fc268  /tmp/fw_full
66c7761ea38091ed4581eba64bd8cf17555b35bd045079a62191155aa37fc268  /tmp/fw_joined
=== 续传响应头 ===
HTTP/1.1 206 Partial Content
Accept-Ranges: bytes
Content-Length: 946176
Content-Range: bytes 102400-1048575/1048576
=== 越界请求（416） ===
HTTP/1.1 416 Requested Range Not Satisfiable
Content-Range: bytes */1048576

                            这套「本地记录已下字节 + 服务端 Range 续传」与 69.4 边缘计算与断网续传 的本地队列是同一个思路：都靠本地状态而非服务端状态恢复。

                            （固件内容每次生成都不同，哈希以实际为准；关键是「两段拼接后的 SHA256 = 全量文件的 SHA256」这一条。）

                            读数：206 + Content-Range 才是续传成功的证据；Accept-Ranges: bytes 说明服务端支持；416 说明请求越界（本地 .part 比服务端文件还大，通常是固件版本换了而 .part 没清）。

                            客户端侧的状态机（Go 实测：第一次读到 100KB 主动断开，第二次从 102400 续传）：

                            第一次：下载 102400 B 后中断（ResumedFrom=0），.part=102400 B
第二次：ResumedFrom=102400，本次拉取 159744 B / 总 262144 B
服务端：2 次请求，Range 头=["" "bytes=102400-"]

                            💡 CDN/对象存储（S3、OSS 等）普遍支持 Range，但缓存键里必须带版本号（如 /fw/2.3.0/fw.bin），否则 CDN 可能把旧包返回给新请求——最终 SHA256 会拦住，但用户侧表现为「反复下载失败」。

                            校验：签名锁清单，哈希锁固件

                            对象 保护什么 算法 校验时机
                            清单（Manifest） 版本号、大小、SHA256、URL 不被篡改 ed25519 签名（设备内置公钥） 下载前
                            固件本体 内容完整、未被替换 SHA256（或 SHA384） 下载完成后、刷写前
                            分区镜像 写入正确 bootloader 自带 CRC/签名 启动前
                            type Manifest struct {
	Product  string `json:"product"`
	HwRev    string `json:"hw_rev"`    // 硬件版本：A 型号固件不能推给 B 型号
	Version  string `json:"version"`
	Size     int64  `json:"size"`
	SHA256   string `json:"sha256"`
	URL      string `json:"url"`
	NotAfter int64  `json:"not_after"` // 清单过期时间，防多年后重放旧签名
	Rollback string `json:"rollback_to,omitempty"`
}

// 注意：Verify 只验证「签名有效」。设备侧还要自己比对 Product/HwRev 是否与本机一致、
// 拒绝低于当前版本的清单（防降级）、检查 NotAfter；这三步漏一步，签名机制就被绕开。

func Verify(pub ed25519.PublicKey, m Manifest, sigB64 string) error {
	sig, err := base64.StdEncoding.DecodeString(sigB64)
	if err != nil {
		return fmt.Errorf("签名不是合法 base64：%w", err)
	}
	if !ed25519.Verify(pub, mustJSON(m), sig) { // 规范序列化：字段顺序固定
		return errors.New("清单签名校验失败：拒绝升级")
	}
	return nil
}

                            实测（go test -race -v，篡改任一字段都必须失败）：

                            --- PASS: TestManifestSignature (0.01s)     # 改 version / 改 URL / 改 SHA / 换公钥 全部拒绝
--- PASS: TestTamperRejected (0.01s)        # 固件改 1 字节 → SHA256 不匹配
    拒绝原因：固件 SHA256 不匹配：期望 653f5cec…，实际 19bbf3a7…

                            完整代码在仓库 tools/examples/69.5-ota/，go test -race -v ./... 可复现这两条拒绝路径。

                            三条铁律：

                            1. 签名覆盖清单，不覆盖固件本体——不是签名慢（ed25519 签的是固定长度摘要，与文件大小无关），而是分工：清单一次签名就能同时钉住版本号、大小、URL、SHA256 这些会变的元数据；固件本体用 SHA256 钉住，哈希计算本来就是下载后必须做的一步，不额外增加成本。反过来「只签固件」，攻击者仍可改清单里的版本号/URL 做降级或换包。
                            2. 设备只存公钥，私钥在离线签名机/HSM，绝不进代码仓库；密钥轮换要留双公钥过渡期（38.4 加密 (对称 / 非对称 / TLS / 密钥管理)）。签名机、构建链、依赖包都算供应链，见 38.10 供应链安全。
                            3. 校验失败必须删除 .part 并上报：留着坏包会让设备每次重试都从坏数据续传，永远修不好。

                            🔑 三条容易漏掉、出事才想起来的校验：① 绑定产品与硬件版本——清单里必须有 Product 与硬件版本，设备验签后比对，否则 A 型号固件会被推给 B 型号（Verify 只验签名，不验「这包是不是给我的」，这步要在设备侧做）；② 防降级（anti-rollback）——设备记录当前版本，拒绝低于它的清单，否则攻击者拿一份旧的合法签名清单就能把设备刷回有漏洞的版本；③ 清单时效——给清单加 not_after，避免多年后旧签名被重放。

                            回滚：A/B 分区是变砖率最可靠的标准解

                            方案 做法 掉电/启动失败后果 存储成本
                            单分区覆盖 直接写唯一分区 写一半掉电 = 变砖，只能返厂 1×
                            单分区 + 备份 先备份再写 备份区也写坏时变砖；恢复慢 2×
                            A/B 双分区（推荐） 写非活动分区，bootloader 按标记启动 启动失败自动回退旧分区，不变砖 2×
                            A/B + 试启动计数 新分区启动失败 N 次自动回退 同上，且能区分「偶发失败」与「真不兼容」 2×

                            A/B 的决定性优势：旧固件从未被覆盖，回滚只是把启动指针改回去，不需要重新下载、不需要网络。应用侧的回滚设计（版本兼容、数据迁移）在 55.3 回滚设计，设备侧要额外解决「设备可能永远不回来」。

                            状态机（测试覆盖「连续两次启动失败 → 回滚」与「一次成功 → 提交」两条路径）：

                            active=A, version=2.2.9
  Stage(B, 2.3.0)      → pending=B, boot_attempts=0
  MarkBootFailed(2)    → boot_attempts=1
  MarkBootFailed(2)    → 回滚：pending="", version=2.2.9，active 仍是 A
  Stage(B, 2.3.0) + MarkBootOK() → active=B, version=2.3.0

                            试启动次数由 bootloader 计数（写在独立的小分区/寄存器），不是云端计数——设备连不上云时也要能自救。

                            灰度与熔断：把「一台的事故」限制在一批内

                            阶段 放量 进入下一阶段的判据 熔断动作
                            内测 1–10 台（自有设备） 全部启动成功、核心功能自检通过 停止发布，回滚样机
                            首批 0.1%–1% 24h 成功率 ≥ 99%、无变砖、无关键告警 暂停批次，已升级的回滚
                            扩大 5% → 20% → 50% 同上，且崩溃率/重启率不高于旧版 暂停 + 回滚批次
                            全量 100% —— 保留旧版本清单，支持按版本回滚

                            演练与熔断要一起设计：回滚只写在文档里等于没有，必须在内测批次上真的触发一次（36.7 演练与验证）。熔断的判据必须是设备侧上报的硬指标：启动成功/失败、看门狗复位次数、关键功能自检结果；不能只看「下载成功率」——下载成功但启动崩溃才是最危险的那类（55.1 发布策略 (滚动 / 蓝绿 / 金丝雀)、55.6 灰度与流量染色）。

                            差分升级：省流量，但增加一类失败

                            维度 全量升级 差分升级（如 bsdiff 生成的补丁）
                            下载量 固件大小（30MB 量级） 通常远小于全量，收益取决于两版本差异
                            服务端 存固件即可 要按「源版本 → 目标版本」生成并存储补丁组合（N² 增长）
                            设备端 直接刷 需要基线版本正确，打补丁过程耗 CPU 与内存
                            失败模式 下载不完整 补丁应用失败、基线不匹配、补丁被篡改

                            判据：设备网络差且固件大（NB-IoT/2G + 30MB）→ 差分值得做；Wi-Fi/4G 设备 → 全量更简单。差分补丁同样要签名，且必须校验「打完补丁后的整包 SHA256」，而不是只校验补丁本身。

                            生产落地：指名 → 可抄 → 可验 → 可退

                            指名：发布通道用对象存储 + CDN（S3 / OSS / OBS 均支持 Range 与版本化路径）；设备端 Linux 用 RAUC 或 SWUpdate（现成的 A/B 与签名框架），MCU 用 MCUboot（双 bank + 回滚）。自研只做「云端编排 + 设备代理」，不要自己实现 bootloader 的镜像校验。

                            可抄（验证你的 CDN/存储是否真的支持断点续传；把 URL 换成你的固件地址）：

                            # 1) 看服务端是否支持 Range
curl -s -D - -o /dev/null -r 102400- https://your-cdn.example.com/fw/2.3.0/fw.bin \
  | grep -iE 'HTTP/|content-range|accept-ranges'
# 2) 断点下载前 100KB，再续传剩余
curl -s -r 0-102399 -o fw.part -w 'first=%{http_code} bytes=%{size_download}\n' <URL>
curl -s -r 102400- -o fw.rest -w 'rest=%{http_code} bytes=%{size_download}\n' <URL>
cat fw.part fw.rest > fw.bin && sha256sum fw.bin

                            可验（本机 1MB 固件 + Go http.ServeContent 静态服务实测；你的 CDN/对象存储要按上面的命令再验一次，重点看是否返回 206）：

                            HTTP/1.1 206 Partial Content
Accept-Ranges: bytes
Content-Length: 946176
Content-Range: bytes 102400-1048575/1048576
first=206 bytes=102400
rest=206 bytes=946176
                            检查点 通过判据 失败常见原因
                            支持 Range 返回 206 且有 Content-Range CDN 关闭 Range、回源配置错、URL 走的是动态接口
                            续传正确 两段拼接后的 SHA256 = 清单里的值 版本路径没变、CDN 缓存了旧包
                            越界保护 请求超出文件返回 416 客户端没检查 .part 大小，拿旧包续传
                            签名可用 篡改清单后设备拒绝升级 设备端把验签做成「可选」或公钥可被替换

                            可退：云端把批次状态置为 paused 即可停止继续下发（已下载未刷写的设备下次检查时放弃）；设备侧回滚 = bootloader 切回旧分区（A/B）或重新下发旧版本清单；保留上一版本固件与清单至少一个完整灰度周期。

                            反模式

                            反模式 后果
                            固件不做签名，只做 SHA256 攻击者改固件后重算 SHA 即可通过，OTA 变成后门通道
                            先刷写再校验 坏镜像进了分区，bootloader 兜不住就变砖
                            单分区覆盖升级 写入过程掉电即变砖，只能返厂
                            只看下载成功率 下载都成功、启动全崩溃，事故规模最大
                            全量一次性推给所有设备 一次事故影响全部设备，且带宽/连接被打满
                            用 CDN 固定路径不加版本 缓存旧包，设备反复下载失败或刷回旧版本
                            差分补丁不校验最终整包 补丁应用错位后仍被刷入，问题极难定位
                            升级不检查电量 刷写中途断电，单分区直接变砖（A/B 也会浪费一次下载）

                            自检

                            Q1 为什么「签名覆盖清单」比「签名覆盖固件」更常用？

                            ▸ 答案：关键不是「签名快慢」（ed25519 签的是固定长度摘要，与文件大小无关），而是签名对象的选择：清单只有几百字节，却能把版本号、大小、URL、SHA256、硬件版本这些「会变的元数据」一次钉住；固件本体用 SHA256 钉住，而哈希计算本来就是下载后必须做的一步，不额外增加成本。反过来「只签固件」时，攻击者仍可改清单里的版本号/URL 做降级或换包，签名就白做了。

                            Q2 服务端返回 200 而不是 206 时，客户端为什么必须截断重下？

                            ▸ 答案：200 表示服务端返回的是完整文件，如果客户端此时把响应追加到已有 .part 后面，文件会变成「旧片段 + 完整文件」，SHA256 必错，而且每次重试都会继续拼坏。正确做法是识别 200 → 清空 .part → 从头写。

                            Q3 A/B 分区为什么能把变砖率降到接近 0，它的代价是什么？

                            ▸ 答案：旧固件始终在活动分区、从未被覆盖，新固件启动失败时 bootloader 只需改启动指针即可回退，不需要网络与重新下载。代价是存储翻倍（2× flash）、分区表与 bootloader 要支持双 bank，以及升级流程多一次切换与提交。

                            Q4 熔断阈值为什么不能只看「下载失败率」？

                            ▸ 答案：最危险的失败发生在下载成功之后——镜像刷进去但启动崩溃。只看下载成功率会把「全部设备下载成功、全部启动失败」判为正常。必须采集启动成功/失败、看门狗复位、关键自检结果这些设备侧硬指标，才能在下一次放量前熔断。

                            Q5 30MB 固件、NB-IoT 设备，为什么必须做差分或分块续传？

                            ▸ 答案：NB-IoT 持续吞吐量级只有几十 kbps，30MB 全量要数小时，期间断网、断电、移动都会中断下载。分块续传保证中断后从断点继续；差分把下载量压到远小于全量，缩短窗口。两者都做才现实，且升级要挑充电/空闲时段。

                            Q6 清单里的 RollbackTo 字段和 A/B 分区是什么关系？

                            ▸ 答案：RollbackTo 是业务层的回滚目标（例如「2.3.0 失败回 2.2.9」），用于云端编排与设备上报；A/B 分区是设备层的物理回滚能力（切回旧分区）。两者互补：设备侧保证不变砖，云端侧保证能解释「该回哪个版本、回滚后是否还要再试」。

                            Q7 升级过程中设备掉线了，恢复后应该怎么办？

                            ▸ 答案：分阶段处理：下载阶段 → 用 .part 续传；校验阶段 → 重新校验；刷写阶段 → 未提交的镜像标记为 pending，由 bootloader 的试启动计数决定回退；启动成功但未上报 → 设备侧先自检再上报 committed，云端按幂等键更新状态。关键是设备侧状态机要落盘，不能只存在内存里。
