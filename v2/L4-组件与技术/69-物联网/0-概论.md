# 第 69 章 物联网 · 概论

## 一句话

> 这一章回答：**当设备很便宜、网络很差、数量很大、离线是常态时，怎么让「数据上得来、命令下得去、状态对得上、版本升得动」**——四条链路，五节，每条都给可验证的实现。

## 5 分钟入门：先记住这 6 个词

| 词 | 一句话解释 | 生活类比 |
|---|---|---|
| **接入协议** | 设备用什么协议、怎么被认证后连上 | 不同门禁卡走不同读卡器 |
| **物模型** | 设备能上报/接受哪些属性、事件、服务 | 电器的说明书 + 遥控器按键表 |
| **设备影子** | 云端保存「期望值 + 实况值 + 差值」，设备离线也不丢 | 冰箱上的便利贴：要买牛奶（还没买） |
| **消息放大** | 一条命令 → N 台设备，投递量翻 N 倍 | 群里发一条通知，所有人都要送达 |
| **断网续传** | 断网期间本地攒着，恢复后按水位补齐 | 快递柜：人不在，包裹先存着 |
| **OTA** | 远程升级固件，且能失败回滚、不返厂 | 换电池要能换回来，不能装死 |

## 3 个最常见误解

| 误区 | 现实 |
|---|---|
| 「IoT 后端就是 MQTT broker 加数据库」 | broker 只解决连接；影子、命令状态机、断网续传、OTA 编排都是独立组件，且各有失效模式 |
| 「QoS 调高就可靠了」 | 协议只保证到 broker 的传输；业务语义（补发、幂等、顺序、离线决策）要自己设计 |
| 「设备端很笨，逻辑都放云端」 | 断网时云端连不上，边缘必须能自治；把决策全放云端等于假设网络永远在线 |

## 读完自检（入门级 3 题）

**Q1** 为什么「100 万连接」和「100 万条/秒消息」是两个完全不同的问题？

▸ 答案：连接数是**存量资源**（内存、fd、会话），100 万连接按实测约 886B/连接（裸连接）到几 KB/连接（含 TLS 与会话）；消息速率是**流量**，取决于上报频率与 fan-out 放大。100 万设备每 30 秒上报一次只有 3.3 万条/秒，但一次全量群控就是 100 万条投递。扩容前者加机器/加内存，扩容后者要分片、合并、限速。

**Q2** 设备影子里的 `desired` 和 `reported` 分别由谁写？为什么不能只留一个？

▸ 答案：`desired` 由云端/App 写（期望设备达到的状态），`reported` 由设备写（实际状态）。只留 `reported` 就无法表达「设备该是什么样」，远程设置只能靠一次性命令、离线即丢；只留 `desired` 就不知道设备是否执行成功，delta 永远清不掉。两者之差才是可下发的、最小的动作。

**Q3** 为什么 OTA 说「变砖率」而不是「升级成功率」？

▸ 答案：下载失败、校验失败都可以重试，设备还是好的；真正不可逆的是刷写后启动不了且回不去——也就是变砖，损失是线下返厂与用户信任。所以 OTA 的设计目标是「任何失败都能回到旧版本」（A/B + 试启动回滚），灰度与熔断的阈值也按变砖而非成功率来设。
