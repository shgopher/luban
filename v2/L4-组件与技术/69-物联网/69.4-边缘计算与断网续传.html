                              69.4 边缘计算与断网续传

                              一句话

                              断网续传不是「重连后重发一次」，而是一份本地持久化的待发队列 + 单调水位 + 幂等键；边缘计算则是在断网期间仍然能就地决策，并把决策结果按序补上。

                              边界：边缘模型不在这里重讲

                              边缘的部署位置与四条硬约束（无状态、时限、存储小、一致性弱），主场在 9.6 边缘计算模型；边缘与中心的分层取舍在 33.5 边缘计算。注意 9.6 说的「无状态」针对的是 CDN 边缘函数；设备/网关边缘恰恰是有状态的——它必须持久化待发队列与本地状态，否则断网就丢数据。本节只回答两个 IoT 特有问题：断网时还能不能决策、恢复后怎么把数据一条不丢、一条不重地补上去；上行消息怎么分路、合并、控制放大见 69.3 海量连接与消息，升级包的断点续传与回滚见 69.5 固件升级 (OTA)。

                              先破除三个误区

                              误区 现实
                              「MQTT 会话保留就能续传」 broker 的会话只在会话保留期内有效，且只补 QoS 1/2 的未确认消息；设备断电重启丢了内存状态、或断网超过会话时长，消息照样丢
                              「本地存了就不会丢」 存了不等于落盘：写进页缓存就断电，照样丢。要活过掉电，必须 fsync（代价见下面的实测）
                              「续传 = 从头重发」 从头重发在 10 万设备同时恢复时会形成重放风暴，把云端写入打满；正确做法是按水位续传 + 速率控制

                              续传的四个层次，各管一段

                              层次 机制 撑多久 不解决什么
                              连接层 TCP 重连、心跳探测 秒级断网 断网期间产生的数据
                              会话层 MQTT 会话（clean session=false / session expiry） 会话保留期内 设备重启、超期、QoS 0 消息
                              持久层 本地 WAL / SQLite outbox + 水位 存储容量内任意久 上游重复消费（需要幂等）
                              业务层 幂等键去重 + 顺序处理 永久 数据本身的正确性

                              🔑 四层是叠加关系，不是替代关系：会话层解决「短暂抖动不丢」，持久层解决「长时间断网/重启不丢」，业务层解决「补传时可能重复」。只做其中一层，都会有一类场景漏掉。

                              断网时边缘做什么：三种自治模式

                              模式 断网时行为 适用 风险
                              纯透传 数据存本地，等恢复后上传；本地不做决策 纯采集（水表、环境监测） 断网期间无法联动
                              本地自治 边缘跑规则引擎，断网照常决策（门禁开、温控调） 实时性要求高（安防、暖通） 边缘规则与云端规则可能不一致
                              混合（推荐） 关键决策本地做，非关键等云端；规则带版本号，云端可覆盖 大多数工业/楼宇场景 要实现规则同步与冲突处理

                              本地自治的前提是规则下发带版本号：边缘执行规则 v7，云端已升到 v8，恢复后要以云端为准并补记「用旧规则做过的决策」。否则事后无法解释设备为什么在某个时间点做了某个动作。

                              续传协议：四个字段就能说清

                              设备/边缘                                    云端
  seq=1001 ──── 上报（幂等键 = deviceID + seq）────►  写入成功
  seq=1002 ──── 上报（超时/断网）──────────────✗      未确认
  （本地 WAL 保留 1002，等重连）
  seq=1002 ──── 重传 ────────────────────────►  去重后写入，回 ack(1002)
  ack=1002 ◄──────────────────────────────────     云端水位推进
  （本地删除 ≤1002 的记录）
                              字段 作用 常见错误
                              seq 每设备（或每边缘节点）单调递增，去重与排序的依据 用全局自增 → 设备间互相阻塞；用时间戳 → 时钟回拨导致乱序
                              deviceID 与 seq 组成幂等键 用连接 ID → 重连后不幂等
                              ts（设备/边缘时间） 事件发生时间，用于迟到数据处理 只存云端接收时间 → 断网补传时时间全乱
                              ack 水位 云端已确认到哪，本地据此删记录 只 ack 单条 → 重连后要重放全部未确认

                              顺序与幂等的两个细节：

                              • 乱序：重传可能让 seq 1003 先于 1002 到达。云端要么按设备维护一个小重排窗口，要么接受乱序但保证每条只处理一次（很多时序场景乱序可接受，重复不可接受）。
                              • 时间：设备时钟不可信，云端要同时存「事件时间（设备 ts）」与「接收时间」，迟到数据按事件时间入库，监控按接收时间算延迟。时钟问题见 23.1 物理时钟与漂移，校时见 23.2 NTP 与 TrueTime。

                              实现：WAL + 独立水位 + 重放

                              核心不变量三条：① 只有 CRC 完整的帧才算一帧；② 水位只增不减、独立落盘；③ 重放从水位+1 开始，顺序不变。

                              // 帧格式：4B 长度 | 4B CRC32 | payload(JSON)
func (q *Queue) Append(ts int64, topic string, payload []byte) (uint64, error) {
	q.mu.Lock()
	defer q.mu.Unlock()
	q.lastSeq++
	rec := Record{Seq: q.lastSeq, TS: ts, Topic: topic, Payload: payload}
	body, _ := json.Marshal(rec)
	var hdr [8]byte
	binary.BigEndian.PutUint32(hdr[0:4], uint32(len(body)))
	binary.BigEndian.PutUint32(hdr[4:8], crc32.ChecksumIEEE(body))
	q.w.Write(hdr[:])       // 写 WAL
	q.w.Write(body)
	q.w.Flush()
	if q.fsync {
		q.f.Sync()          // 活过掉电的关键一步
	}
	return rec.Seq, nil
}

// Ack：原子 rename 落盘，只增不减；记录本身等压缩时再删（先 ack 后删，反了就会丢）
func (q *Queue) Ack(seq uint64) error {
	q.mu.Lock()
	defer q.mu.Unlock()
	if seq <= q.ack {
		return nil // 幂等：重复 ack 不倒退
	}
	if seq > q.lastSeq {
		return fmt.Errorf("ack %d 超过已写入的 %d", seq, q.lastSeq)
	}
	var b [8]byte
	binary.BigEndian.PutUint64(b[:], seq)
	// ① 写临时文件 + fsync（数据落盘）② rename（原子替换）③ fsync 目录（目录项落盘）
	f, err := os.OpenFile(q.ackPath+".tmp", os.O_CREATE|os.O_TRUNC|os.O_WRONLY, 0o644)
	if err != nil {
		return err
	}
	if _, err := f.Write(b[:]); err != nil {
		f.Close()
		return err
	}
	if err := f.Sync(); err != nil {
		f.Close()
		return err
	}
	f.Close()
	if err := os.Rename(q.ackPath+".tmp", q.ackPath); err != nil {
		return err
	}
	if dir, err := os.Open(filepath.Dir(q.ackPath)); err == nil {
		dir.Sync()
		dir.Close()
	}
	q.ack = seq
	return nil
}

                              💡 单次运行的数字：fsync 成本在本机稳定在 3.7–3.8 ms/条（APFS 写屏障 + SSD 刷盘），无 fsync 的 8.7 µs 受缓冲与调度影响会在 7–10 µs 波动，所以「429 倍」是这次运行的结果，量级上记为「两到三个数量级」更稳妥。

                              🔑 每条都 fsync 与不 fsync 差 429 倍。这个数字就是「断网续传要不要每条落盘」的全部答案：按消息类别分别对待，不是全局开或关。

                              fsync 策略：用「批量提交」换掉 429 倍差距

                              设单条 fsync 成本 3.74ms、单条写入成本 8.7µs，一批 N 条做一次 fsync：

                              每批条数 单批耗时（推导） 吞吐（推导） 掉电丢失窗口
                              1 3.74ms 267 条/秒 ≤ 1 条
                              100 3.74ms + 0.87ms ≈ 4.6ms ≈ 21,700 条/秒 ≤ 100 条
                              1000 3.74ms + 8.7ms ≈ 12.4ms ≈ 80,600 条/秒 ≤ 1000 条

                              推荐的分类策略：

                              消息类别 落盘方式 理由
                              命令/事件（开门、告警、计费） 每条 fsync（或 10ms 内组提交） 丢一条就是事故，267 条/秒对事件流足够
                              遥测 攒批（100–1000 条）或每 200ms fsync 可接受丢几秒，吞吐要求高
                              高价值但高频（电表计量） 组提交 + 本地冗余（双写/副本） 既要不丢又要吞吐

                              输入 取值 结果
                              边缘下挂设备 5,000 台 ——
                              上报频率 每 10 秒一条 500 条/秒
                              单条磁盘占用（实测 200B 载荷 → 319B/条） 319 B 约 160 KB/秒
                              断网缓冲目标 3 天 约 41 GB
                              若改用二进制编码（去掉 JSON 字段名与 base64） 约 1.3 倍压缩（判断值，需实测） 约 30 GB

                              ⚠️ 41GB 是「3 天全量」的账。真实部署要么降采样（3 天只保关键数据）、要么加大本地盘、要么缩短缓冲目标并接受少量丢弃。不先算这笔账，就会出现「断网第二天边缘磁盘满，进程崩溃」。

                              重连：别把恢复变成第二次故障

                              全城断网恢复时，几十万设备同时重连 + 补传，两个风暴叠加：

                              风险 后果 对策
                              重连风暴 接入层 CPU/握手打满 接入限速（令牌桶）+ 指数退避 + 随机抖动，见 35.5 超时、重试与退避
                              补传风暴 云端写入被打满，正常数据也被挤掉 补传限速 + 按设备公平调度 + 与实时数据分队列
                              重复消费 补传与实时重叠，同一条写两次 幂等键去重（25.4 幂等设计与去重）
                              雪崩 补传导致下游超时，边缘又重试 退避 + 熔断（35.6 熔断与降级）

                              退避参数要带抖动：固定 1s 重试会让 10 万设备在同一毫秒醒来；用 random(0.5, 1.5) × base 把重连摊开。

                              生产落地：指名 → 可抄 → 可验 → 可退

                              指名：边缘本地队列用 SQLite（WAL 模式） 做 outbox——单机、无服务、崩溃恢复成熟，适合大多数边缘盒子；资源极紧（MCU、几十 KB RAM）才用裸文件 WAL（上面那套）。本地消息表模式与 24.6 本地消息表 同源。

                              可抄（Alpine 3.20 容器内验证，sqlite3 3.45.3）：

                              apk add --no-cache sqlite
sqlite3 /tmp/edge.db <<'SQL'
PRAGMA journal_mode=WAL;
CREATE TABLE outbox(
  device_id TEXT NOT NULL,
  seq       INTEGER NOT NULL,
  topic     TEXT NOT NULL,
  payload   BLOB NOT NULL,
  ts        INTEGER NOT NULL,
  PRIMARY KEY (device_id, seq)          -- 幂等键：同设备同序号只能有一行
);
CREATE TABLE outbox_ack(               -- 独立水位：ack 只推进这张表，不删 outbox
  device_id TEXT PRIMARY KEY,
  seq       INTEGER NOT NULL
);
INSERT INTO outbox(device_id,seq,topic,payload,ts)
  VALUES ('gw-1001',1001,'dev/1/temp',x'7b2274223a32332e357d',1700000000000);
INSERT INTO outbox_ack(device_id,seq) VALUES ('gw-1001',1000);
SELECT device_id,seq,length(payload) FROM outbox;
SELECT device_id,seq FROM outbox_ack;
PRAGMA journal_mode;   -- 再确认一次：必须是 wal
SQL

                              可验（本机容器实测输出）：

                              wal
gw-1001|1001|10
gw-1001|1000
wal

                              读法：开头和结尾的 wal 是 journal_mode 的返回值——必须是 wal（delete 模式并发写会锁库，续传场景不可接受）；中间两行分别是「未确认的记录」与「已确认水位」——ack 推进 outbox_ack，记录删除走后台压缩，先删后确认会在崩溃窗口丢数据。

                              检查点 通过判据 失败常见原因
                              WAL 生效 PRAGMA journal_mode; 返回 wal 文件系统不支持（网络盘/NFS），或库被设为 delete 模式
                              写入成功 SELECT count(*) FROM outbox; 有值 表结构错、磁盘满（SQLITE_FULL）
                              崩溃恢复 kill 进程后重开，未 ack 记录仍在 PRAGMA synchronous=OFF 或 NORMAL：WAL 默认 FULL 才保证掉电不丢已提交事务，为性能调低就可能丢最近几条
                              清理正确 ack 后删除/归档，磁盘不涨 只 ack 不删，outbox 无限增长

                              可退：升级/回滚时 sqlite3 edge.db ".backup '/tmp/edge.db.bak'" 备份 outbox；恢复时停止上行泵，替换文件，按水位重放（幂等，重复补传安全）。

                              反模式

                              反模式 后果
                              只用 MQTT 会话做续传 断网超过会话保留期 / 设备重启，数据全丢
                              本地写内存队列就算「持久化」 断电/进程崩溃全丢，且用户以为已缓存
                              每条 fsync 用在遥测上 吞吐只有 267 条/秒，边缘 CPU 与磁盘被小写入拖死
                              不 fsync 却承诺不丢 掉电丢最后几秒到几十秒数据，事后无法对账
                              用时间戳当去重键 时钟回拨/同毫秒多事件 → 误去重或重复写入
                              ack 后立刻删、且未落盘 删除先于确认，崩溃后数据既没上报也没了
                              恢复后全量重发 重放风暴打满云端，正常数据也被挤掉
                              断网时边缘继续执行云端旧规则却不上报 事后无法解释设备行为，审计断链

                              自检

                              Q1 已经有 MQTT 会话保留，为什么还要本地 WAL？

                              ▸ 答案：MQTT 会话保留的是 broker 侧的订阅关系与未确认消息，且只在会话保留期内有效；设备自身断电重启后，如果本地没有持久队列，断网期间产生的数据从未发出过，broker 也没有。WAL 补的是「设备侧产生、尚未成功发出」这段，两者覆盖不同区间。

                              Q2 为什么 ack 水位要独立落盘，而不是直接删记录？

                              ▸ 答案：删除是不可逆的，一旦删除先于确认落盘，崩溃窗口里数据就既没上报也没了；独立水位 + 原子 rename 保证「要么旧水位要么新水位」，重启后最多重放已处理过的记录（由幂等键去重），不会丢。记录删除用批量压缩，降低删除频率。

                              Q3 3.74ms/条的 fsync 成本对设计意味着什么？

                              ▸ 答案：意味着「每条都 fsync」只适合低频高价值消息（命令、事件），不适合遥测。遥测要么攒批 fsync（牺牲几秒数据），要么降低持久化等级并接受丢失。设计的第一步是给消息分类，而不是给整个队列统一开 fsync。

                              Q4 断网恢复后，为什么补传速率要限？

                              ▸ 答案：补传与实时数据共享同一条链路和同一套下游；不限速时，补传会占满带宽与写入配额，把实时数据挤掉，形成「恢复了但新数据又丢」的二次故障。限速 + 按设备公平调度 + 补传与实时分队列，三者缺一不可。

                              Q5 seq 为什么按设备单调，而不是全局单调？

                              ▸ 答案：全局单调需要一个全局发号器，断网时边缘无法访问它，续传场景直接不可用；按设备单调只需本地计数，天然离线可用，且云端按 deviceID+seq 组成的幂等键去重即可。全局序只在跨设备因果分析时需要，用时间戳 + 逻辑时钟另做。

                              Q6 边缘本地自治时，云端规则更新了怎么办？

                              ▸ 答案：规则带版本号下发，边缘执行时记录「用的哪版规则」。云端更新后，边缘在下次连接时同步；如果断网期间用旧规则做了决策，恢复后要补报决策记录与规则版本，让云端可以解释与追溯。不能让边缘静默沿用旧规则——那等于埋了一个「设备行为与配置不一致」的隐患。

                              Q7 41GB 的本地缓冲算出来之后，第一件事应该做什么？

                              ▸ 答案：先做取舍，而不是买硬盘：① 遥测降采样（只保聚合值/关键点）；② 缩短缓冲目标（3 天 → 1 天）；③ 事件与遥测分表，事件保久、遥测可丢；④ 设置磁盘水位告警（80% 触发降采样）。存储容量见 39.3 存储分级，磁盘满了才处理已经是事故。

                              • 幂等与时钟：25.4 幂等设计与去重、23.1 物理时钟与漂移
