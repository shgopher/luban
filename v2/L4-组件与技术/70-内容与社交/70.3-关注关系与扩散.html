                        70.3 关注关系与扩散

                        一句话

                        关注关系是 Feed 的「边」，扩散是把边预计算成读路径：关系表的分片键决定你能查什么，扩散的批量与限速决定一次大 V 发布会压垮谁；阈值不是产品感觉，是扇出成本算出来的。

                        先破除三个误区

                        误区 现实
                        关注表一张就够，分片键随便选 主键只服务一个查询方向：按 follower_id 分片，关注列表命中单分片（0.240 ms/扫 203 行），粉丝列表打 8 分片（22.24 ms/扫 108,058 行），差 93 倍；按 followee_id 分片则反过来，关注 45.64 ms vs 粉丝 0.323 ms，差 141 倍
                        取关要回删收件箱 回删要遍历该用户全部历史帖；软删关系 + 出流读时过滤即可，实测 1000 个取关用户收件箱仍有行、靠读时过滤
                        粉丝列表可以全量扫 5 万粉 5 万行、1.2 亿粉 1.2 亿行，既占内存又占延迟；必须 keyset 分页，大 V 走离线导出、限流查询

                        三个误区同一个判据：关系表形状由查询方向决定，扩散节奏由扇出成本决定。

                        关系模型：边怎么存

                        三种关系，三种存法

                        单向关注是 Feed 主模型：一行 (follower_id, followee_id)，读查「我关注谁」、写按关系扩散。双向好友（IM）存两行或一行加状态位，请求要状态机。拉黑一行 state=2 或独立 block 表，出流/评论/搜索都要判，双向不可见、只存单向会漏一半。

                        一张关系表的 schema

                        -- 生产 DDL（MySQL 8）：按 follower_id 哈希分片，relation_0..relation_N 同构
CREATE TABLE relation_0 (
  follower_id BIGINT NOT NULL,
  followee_id BIGINT NOT NULL,
  state TINYINT NOT NULL DEFAULT 0,  -- 0 关注 1 取关软删 2 拉黑
  created_at BIGINT NOT NULL,         -- 关注时间（毫秒）
  seq BIGINT NOT NULL,                -- 全局单调创建序，做分页快照与游标
  PRIMARY KEY (follower_id, followee_id),      -- 关注列表单分片
  KEY idx_followee (followee_id, follower_id), -- 反向本地索引
  KEY idx_followee_seq (followee_id, seq)      -- 扩散按创建序翻粉丝页
) ENGINE=InnoDB;

                        主键兜幂等；state 软删与拉黑；created_at 决定关注列表时间倒序；seq 是全局创建序，同时做分页快照与游标——created_at 同毫秒会重复/漏行，一行序列号省掉双游标。

                        单表还是双表

                        方案 结构 关注列表 粉丝列表 写成本
                        单表 一行一条边，PK (follower, followee) 前缀扫，单分片 要反向索引，按分片散射 1 次写
                        双表 following/follower 各一份 查 following 查 follower 2 次写（事务或 Outbox）
                        单表 + 反向二级索引 PK + idx_followee 前缀扫 索引查，仍要按分片散射 1 次写 + 索引维护

                        双表让两个方向都变单分片前缀扫，代价是双倍存储、双倍写与两表不一致；单表 + 反向索引只多一份索引，但反向查询天然跨分片散射。判据：粉丝列表低频 → 单表 + 反向索引；高频前台 → 双表或独立粉丝存储。

                        分片键决定你能查什么

                        两种模型在同一份 20 万行数据上，两个查询方向的实测结果（细节见「实测」）：

                        模型 分片键 关注列表（我关注的人） 粉丝列表（关注我的人）
                        A follower_id 单分片，type=ref，扫 203 行，0.240 ms 散射 8 分片，扫 108,058 行，22.24 ms
                        B followee_id 散射 8 分片，扫 200,000 行，45.64 ms 单分片，type=ref，扫 203 行，0.323 ms
                        A + 反向索引 follower_id 单分片 散射 8 分片，扫 1,626 行，3.22 ms
                        B + 反向索引 followee_id 散射 8 分片，扫 1,003 行，2.12 ms 单分片

                        两个结论：

                        1. 分片键只能让一个方向免费：Feed 出流每次查「我关注了谁」，主表按 follower_id 分片；粉丝列表只在扩散/运营时查，可接受散射。
                        2. 反向索引不能把散射变回单分片：它把「扫 10.8 万行」压到 1,626 行（22.24 ms → 3.22 ms），但请求仍打到 8 个分片，延迟里始终有 8 次往返。真正的修法是双表或独立粉丝存储。

                        按 followee_id 分片还有第二重代价：大 V 的粉丝行全落在一个分片，该分片成为写热点，粉丝从 1 万涨到 100 万、热点分片写入量涨 100 倍，其它分片闲着（19.8 热点与数据倾斜）。按 follower_id 分片把写打散，代价是粉丝列表查询变贵。

                        大 V 粉丝列表：keyset 游标，不要 OFFSET

                        -- 第 1 页：单分片前缀扫
SELECT follower_id FROM follow_b_9 WHERE followee_id = 9999 AND state = 0
ORDER BY follower_id LIMIT 200;
-- 下一页：cursor = 上一页最后一行
SELECT ... WHERE followee_id = 9999 AND state = 0 AND follower_id > 1765432100
ORDER BY follower_id LIMIT 200;

                        OFFSET 100000 要做两件坏事：先扫过前 10 万行再丢弃，越翻越慢；扩散期间删行会让「第 10 万行」漂移，翻页重复或漏行。keyset 游标两件事都解决，代价是只能顺序翻——粉丝列表本来只有「下一页」。

                        读写路径：关注、取关、上限、计数

                        关注：唯一键幂等 + 计数 + 上限

                        -- 1) 幂等写入：重复关注不新增行、不改状态
INSERT INTO relation_0 (follower_id, followee_id, state, created_at, seq)
VALUES (?, ?, 0, ?, ?) ON DUPLICATE KEY UPDATE state = 0;
-- 2) 上限检查（2000 是容量规则）
SELECT COUNT(*) FROM relation_0 WHERE follower_id = ? AND state = 0;
-- 3) 计数异步更新：发 relation.changed 事件

                        顺序很重要：先写关系、再改计数。关系是真相，计数是派生；计数失败可重放事件重建，关系失败则用户真的没关注上。

                        ON DUPLICATE KEY UPDATE state=0 只复活关系，不更新 created_at/seq：重新关注会停在原列表位置。产品若要「重新关注置顶」，就同时更新两列，代价是历史位置在按 seq 分页的列表里丢失。

                        取关：软删，不回删收件箱

                        UPDATE relation_0 SET state = 1 ...。取关不改历史收件箱：出流时按关系状态过滤，旧行自然淘汰或被裁剪；删帖同理。读时一次判断，换写时零删除。

                        关注上限与计数都是容量/派生数据

                        关注上限 2000 不只是产品规则：44.23 未读数系统 已定性为容量规则——单请求成本随关注数线性上涨，没有上限，头部用户尾延迟无法收敛；上限一变，扩散与未读两条路径都要重算容量。

                        粉丝数/关注数是可重建的派生数据（44.22 计数系统）：全量扫关系表即可重算，不必与关系写同事务；Outbox 发事件、计数服务合并，比双写可靠。

                        扩散：把边预计算成读路径

                        推：一次发布四步

                        发布落库 + 写发件箱（同事务）
  → 投递扩散任务到队列（携带 feed_id 与作者）
  → worker 分页拉粉丝：按创建序 seq 做 keyset 游标，每页 1000，快照上界 = 开始时的 seq_snapshot
  → 批量写收件箱：pipeline ZADD inbox:&lt;follower_id> score=timestamp member=feed_id

                        每步都有失败策略：投递重试、分页重试整页、ZADD 重试整批（幂等）。最容易忽略的是分页快照上界：必须用创建序 seq 而非 follower_id——id 不是创建序，新粉丝 id 可能落在旧上界内被漏写，不设上界又会被写进历史帖。

                        大 V 转拉：阈值由扇出成本算出

                        扇出 1.2 亿行是什么量级，63.7 信息流（推 / 拉 / 推拉结合） 已算过 2.88 GB/条、写放大 1.2 亿倍；这里不重算，只给判据：阈值是「单条扇出成本上限 ÷ 每行成本」算出来的，超过就切拉——只写发件箱，粉丝读时补拉最近 N 条。

                        活跃粉丝 vs 非活跃

                        粉丝类型 策略 为什么
                        活跃粉丝（近 7 天刷过 Feed） 推，写进收件箱 读频繁，推省读成本
                        非活跃粉丝 不推，登录时补拉大 V 近文 不浪费写
                        全部粉丝（大 V） 拉，读时合并发件箱 1.2 亿次写不可接受

                        代价是多维护一份「活跃粉丝列表」，但比给 1.2 亿人各写一行便宜几个数量级。

                        取关、删帖、审核状态：读时过滤

                        三类变化都不回删收件箱，出流时统一过滤：关系是否有效（state=0）、帖子是否已删、审核状态是否可见。发布写成本因此是常数，代价是读路径多一次批量判定（pipeline 把 N 次读压成 1 次）。这些过滤在出流侧具体放在哪一段、怎么与游标和降级配合，见 70.2 Feed 流架构 (推 / 拉 / 推拉结合)；审核状态这一列从哪来，见 70.1 内容生产与审核。

                        群 vs 关注关系

                        群聊成本公式不同：66.5 群聊与消息扩散 明确「群是成员关系、Feed 是关注关系」——群成员有明确上限（按产品分级，500 到 20 万）、双向、按成员数扩散；Feed 单向关注、无粉丝上限（1.2 亿）、按粉丝数扩散。同一个「写扩散」，两套容量模型。

                        扩散 worker 的工程细节

                        分页稳定性：快照边界 + keyset

                        • 用创建序 seq 做快照：开始时取 seq_snapshot = max(seq)，分页 seq > cursor AND seq <= seq_snapshot ORDER BY seq。为什么不能用 max(follower_id)：follower_id 不是创建序——新粉丝是已有用户之后才关注作者，id 可能小于旧上界（id 游标越过就漏写），也可能更大（不设上界就会被写进历史帖）。实测反事实：500 条新关系里 190 条会被 id 游标漏写、310 条会被写进历史帖。
                        • 快照外的粉丝不补历史帖，下次刷新走拉路径补；期间取关的粉丝仍在快照里，照写、出流时过滤。
                        • 用 keyset（seq > cursor）而不是 OFFSET：增删时 OFFSET 会漂移，导致重复写或漏写。

                        重试与幂等：ZADD 天然幂等

                        ZADD 以 (key, member) 为唯一：同一粉丝重复收同一 feed_id 只更新 score、不新增行，实测重复写 3 次 ZCARD=1，所以整批重试安全——这是 worker 敢失败重试的前提。换成 LPUSH，重试就会造出重复 Feed。

                        限速：保护收件箱，也保护下游

                        不限速时实测峰值 392,000 行/秒（1 s 窗口），限速 5 万行/秒时 50,000 行/秒，差 7.8 倍。大 V 发布瞬间按峰值打，Redis、CPU 与下游缓存一起被打满，普通用户读请求跟着超时。限速是把写速率钉进容量预算。

                        积压与延迟监控

                        扩散延迟 = 积压行数 ÷ 写入速率。监控队列积压、单页 P99、重试率，指标口径见 50.4 度量（四黄金指标 / 直方图 / 基数爆炸）。告警线（起步阈值，按线上基线标定）：积压 > 5 分钟、重试率 > 1%、单页 P99 > 500 ms，任一触发就暂停大 V 扩散。

                        关注后立刻可见

                        关注是读己之写问题：刚关注 A，回 Feed 就该看到 A 的内容（16.6 会话保证 (读己之写、单调读、单调写)）。两条路径：① 出流时合并「关注列表最近发布的发件箱尾部」；② 关注后同步把 A 最近 N 条（N≤50）写进自己收件箱。①是拉路径本来就要做的，优先；②只作快路径。顺序不能反：先写关系再补收件箱，否则「收件箱有内容但关系没生效」。

                        实测：分片键选错的代价（MySQL，20 万行）

                        环境：macOS / Apple 芯片 / Go 1.27.1 / MySQL 26.7.0 / 2026-11-21；同机 4 个写作任务并行时测得，延迟允许 ±30% 波动。8 表模拟 8 分片（无跨机 RTT）。数据：20 万条边、92,560 粉丝、19,986 关注对象，含「关注 1000 人」与「被 5 万人关注」的长尾。

                        造数与建表（code/mysqlbench/main.go）：

                        CREATE TABLE follow_a_0 (   -- 模型 A：按 follower_id 分片
  follower_id BIGINT NOT NULL, followee_id BIGINT NOT NULL,
  state TINYINT NOT NULL DEFAULT 0, created_at BIGINT NOT NULL, seq BIGINT NOT NULL,
  PRIMARY KEY (follower_id, followee_id)) ENGINE=InnoDB;
CREATE TABLE follow_b_0 (   -- 模型 B：按 followee_id 分片；主键反过来
  followee_id BIGINT NOT NULL, follower_id BIGINT NOT NULL,
  state TINYINT NOT NULL DEFAULT 0, created_at BIGINT NOT NULL, seq BIGINT NOT NULL,

                        场景 EXPLAIN type / key / rows 真实扫描行数 中位耗时

                        读数：

                        1. EXPLAIN 的 rows=200 是骗人的：散射查询因 ORDER BY ... LIMIT 200 选 type=index、估 rows=200，实际 B 关注列表扫了 200,000 行（8 个分片各 25,000 行）。判分片键选错看 Handler_read_next。
                        2. 反向索引只把「扫全表」变成「扫 1,626 行」，8 次分片请求一次没少：3.22 ms 相对 0.240 ms 仍约 13 倍，真实集群还要叠 8 次跨机 RTT。

                        实测：pipeline 批量 ZADD 的吞吐（10 万行，批 100 vs 1000）

                        环境同上（Redis 8.10.2 / 127.0.0.1:16393）。场景等价于「10 万个粉丝各写一条收件箱」：10 万个不同 inbox:<id> key，每个 ZADD 一条。代码在 code/redisbench/main.go，核心循环：

                        for i := 0; i < rows; i += batch {
    pipe := rdb.Pipeline()
    for j := i; j < min(i+batch, rows); j++ {
        pipe.ZAdd(ctx, fmt.Sprintf("inbox:%d", j), redis.Z{Score: float64(1760000000000 + j), Member: "feed:000000009001"})
    }
    pipe.Exec(ctx)   // 一批命令一次往返
}

                        交替 5 轮、每轮独立 key 前缀（避免 FLUSHALL 异步释放内存污染下一轮），取中位数：

                        逐条 ZADD: 20000 行, 1.882s, 吞吐 10626 行/秒
MEDIAN batch=100  400742 行/秒（min=391620 max=411281）
MEDIAN batch=1000 502463 行/秒（min=412737 max=537524）
内存: 100000 keys 增量=11112224 bytes（111 B/行，单 key=70 B）
                        方式 吞吐 相对逐条 说明
                        逐条 ZADD（2 万行样本） 10,626 行/秒 1× 每行一次往返
                        pipeline 批 100 400,742 行/秒 38× 1000 次流水线
                        pipeline 批 1000 502,463 行/秒 47× 100 次流水线

                        读数：批大小 100→1000 提升约 25%（400,742 → 502,463），本机回环 RTT 只有几十微秒；真正带来 38–47 倍的是「逐条 → 批量流水线」；跨机房 RTT 500 µs 会放大批大小收益。

                        单连接: 120000000 / 502463 ≈ 238.8 秒 (4.0 分钟)
16 连接并行: 14.9 秒

64 连接并行: 3.7 秒
内存: 120000000 × 111 bytes ≈ 13.3 GB

                        两个结论：① 纯 ZADD 通道 32 连接也要 7.5 秒，端到端加限速、分页、持久化就是分钟到小时级；② 内存两种口径：10 万 key 折 111 B/行（key 前缀、member 补零、jemalloc 尺寸类取整与客户端缓冲），100 万 key 折 90.9 B/行，推算 13.3 GB / 10.9 GB，都 ≥ 63.7 裸行 2.88 GB 的 3 倍；取保守的 111 B。

                        实测：100 万粉丝的扩散 worker（分页 + 批量 + 限速）

                        环境同上。100 万粉丝按创建序 seq 建有序切片模拟分页源（每页加 300 µs 模拟索引查询）；中途追加 500 条新关系（seq 超快照，其中 400 条 follower_id 小于旧上界、100 条更大）；收件箱写真实 Redis。同进程 A/B：限速 5 万行/秒 vs 不限速。核心代码：

                        // 按创建序 keyset 分页：seq > cursor 且 seq <= snapshot，用 seq 而不是 follower_id
func fetchPage(rels []relation, cursorSeq, snapshotSeq int64) []relation {
    i := sort.Search(len(rels), func(k int) bool { return rels[k].seq > cursorSeq })
    out := make([]relation, 0, pageSize)
    for _, r := range rels[i:] {
        if r.seq > snapshotSeq || len(out) >= pageSize { break }
        out = append(out, r)
    }
    return out
}

// 令牌桶：桶容量=一页，补充速率=5 万行/秒
func (l *limiter) wait(n int) {
    for {
        l.tokens += time.Since(l.last).Seconds() * l.rate
        if l.tokens > l.cap { l.tokens = l.cap }
        l.last = time.Now()
        if l.tokens >= float64(n) { l.tokens -= float64(n); return }
        time.Sleep(time.Duration((float64(n) - l.tokens) / l.rate * float64(time.Second)))
    }
}

                        诚实口径：worker 粉丝源是内存有序切片；真实分片 MySQL 每页要打 8 个分片，各按 (followee_id, seq) 取 1000 行再归并，页面成本 ≈ 8 × 单索引 range（单片 0.2–0.5 ms 量级）≈ 1.6–4 ms/页（推算）；本程序用 300 µs/页模拟单分片，1000 页约多 1.6–4 s，主体仍由限速决定。

                        三条铁律

                        🔑 分片键跟着读路径走：Feed 出流每次都要查「我关注了谁」，主表就按 follower_id 分片；粉丝列表用双表、反向索引或离线管道，别指望一个分片键让两个方向都路由。

                        🔑 扩散以「页」为单位：seq 快照上界 + keyset 游标 + 批量 ZADD + 按页重试，缺一件就会在「新增粉丝」「取关」「重试」场景写出重复或漏行。

                        🔑 限速与阈值是容量参数：大 V 阈值、单 worker 5 万行/秒、收件箱 1000 条上限，每个数字都要能从扇出成本与 Redis 预算算出来。

                        自检

                        Q1 关系表按 follower_id 分片后，为什么「关注我的人」这个查询会变贵？贵多少？

                        ▸ 答案：关注列表落在同一分片，前缀扫 PRIMARY（203 行、0.240 ms）；「谁关注了 X」的边分散在 8 个分片，必须全部请求归并：无反向索引时共扫 108,058 行（22.24 ms），加 idx_followee 后 1,626 行（3.22 ms），但 8 次请求没少。

                        Q2 实测里 EXPLAIN 明明写 rows=200，为什么说它扫了 20 万行？该看什么指标？

                        ▸ 答案：ORDER BY ... LIMIT 200 下优化器选 type=index，rows 只是 LIMIT 期望值。B 关注列表每分片只有 125 行、凑不满 200，8 个分片各扫 25,000 行，Handler_read_next=200000。判分片键选错看它。

                        Q3 取关为什么不回删收件箱？实测数据怎么支撑这个结论？

                        ▸ 答案：回删要找出该用户所有历史帖的收件箱行，写成本可能和一次发布同量级，还会与进行中的扩散赛跑。实测 C 取关 1000 人、收件箱仍留 1000 行，出流按 state=0 过滤——读路径一次判断换零删除。

                        Q4 扩散过程中新增的粉丝为什么不补发历史帖？

                        ▸ 答案：用创建序做快照：seq_snapshot = max(seq)，分页 seq > cursor AND seq <= seq_snapshot。不能用 max(follower_id)——id 不是创建序，新粉丝是已有用户之后才关注作者，id 可能落在旧上界内被漏写。实测 500 条新关系全排除；反事实若用 id 上界，190 漏写、310 写进历史帖。

                        Q5 大 V 阈值到底怎么定？为什么不能拍一个「粉丝数 > 10 万」？

                        ▸ 答案：阈值来自扇出成本：单条要写 粉丝数 × 每行成本。63.7 信息流（推 / 拉 / 推拉结合） 已算 2.88 GB/条；实测 Redis 每行 90.9–111 B（保守 111 B），1.2 亿行约 13.3 GB（推算），32 连接纯 ZADD 7.5 秒（推算）。阈值 = 可接受上限 ÷ 每行成本。

                        Q6 为什么扩散 worker 敢「整批失败就整批重试」？

                        ▸ 答案：收件箱用 ZSET，member 是 feed_id，ZADD 对同一 (key, member) 只更新 score、不新增行，天然幂等。实测连写 3 次 ZCARD=1；注入 0.3%/批失败后总重试 1 次（按页上限 3 次）、100 万行一行不重。

                        Q7 限速把扩散从 2.55 s 拖到 20.428 s，为什么还要限速？

                        ▸ 答案：不限速峰值 392,000 行/秒（1 s 窗口），限速 5 万/秒时 50,000，差 7.8 倍。峰值一高，收件箱与下游缓存同时被打满，普通用户读 Feed 会超时。限速不减总量（40.9 分钟 vs 5.1 分钟，推算），只把峰值钉进预算。
