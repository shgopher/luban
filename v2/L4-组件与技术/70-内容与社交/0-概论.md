# 第 70 章 内容与社交 · 概论

## 一句话

> 内容社区的系统骨架只有一条链路：**发布 → 审核 → 可见性 → 扩散 → 召回 → 消费 → 互动 → 回流**；每一段都有各自的判据与代价，串起来才是一个 Feed——分开看，每一段都不难，连起来才会出事。

## 5 分钟入门：先记住这 8 个词

| 词 | 一句话解释 | 生活类比 |
|---|---|---|
| **内容状态机** | 一条内容从草稿到上线、下线、被申诉的合法状态与转移 | 快递的物流状态，不能从「待揽收」直接跳「已签收」 |
| **可见性** | 同一份内容对谁可见：仅自己 / 粉丝 / 公开 / 屏蔽 | 朋友圈分组可见 |
| **机审 / 人审** | 机器管覆盖率与召回，人管边界与误杀 | 安检机 + 人工开箱 |
| **扇出（推）** | 发布时就把内容写进每个粉丝的收件箱 | 群发短信，人越多越贵 |
| **收件箱 / 发件箱** | 每个用户一份「我该看到什么」的列表 | 自家信箱 vs 报刊架 |
| **多路召回** | 关注流、推荐流、热门、同城各出一批候选 | 几个采购员分头找货 |
| **游标分页** | 用「上一页最后一条的位置」继续翻，而不是数偏移 | 用书签接着读，而不是每次从第一页数 |
| **状态与计数分离** | 「谁赞过」是状态，「赞了多少」是计数，两份数据分开存 | 签到表与人数统计 |

```
发布 ──▶ 70.1 审核状态机 ──▶ 可见性（仅自己/粉丝/公开）
         机审 → 人审 → 申诉        │
                                    ▼
                        70.3 关系与扩散（推 / 拉 / 推拉结合）
                        关注表 → 扇出 worker → 收件箱
                                    │
                                    ▼
     70.2 Feed 读路径：多路召回 → 过滤 → 混排 → 游标 → 缓存
                                    │
                                    ▼
                    消费 ──▶ 70.4 互动（点赞 / 评论）──▶ 回流
                                                    重新影响召回与排序
```

- 竖看是**一条链路**：上一段的输出是下一段的输入；审核状态错了，Feed 会露出违规内容；游标错了，用户会看到重复内容。
- 横看是**一个回路**：互动数据回流影响排序（[63.6 偏差、反馈回路与多样性](../63-推荐系统/63.6-偏差与反馈回路.md)），越推越窄的锅不在模型，在回路。

## 3 个最常见误解

| 误区 | 现实 |
|---|---|
| 「内容系统就是 CRUD + 一个推荐模型」 | 审核状态决定「能不能被看见」，扩散决定「多久能看见」，分页决定「会不会看重复」——这三件都不是 CRUD |
| 「Feed 的难点是排序算法」 | 排序只决定顺序；出事故最多的是**分页一致性、审核状态兜底、扩散积压**这类「链路问题」 |
| 「点赞数不准是缓存问题」 | 根因通常是**状态没做幂等**：重复点赞把计数顶上去了，缓存只是把它显示出来 |

## 读完自检（入门级 3 题）

**Q1** 一条内容从发布到出现在陌生人的 Feed 里，最少要经过哪几个状态/环节？哪一步漏了会直接导致违规内容扩散？

▸ 答案：发布落库 → 审核（机审/人审）→ 可见性置为公开 → 扩散/索引 → 召回 → 出流。漏掉「可见性 = 公开」的前置条件（审核未通过就按公开处理），违规内容会立刻被扇出到粉丝收件箱并进入推荐召回，事后下线也删不干净。

**Q2** 同样是「发布一条内容」，为什么大 V 和普通用户可以用两套扩散策略？

▸ 答案：成本由扇出决定：`粉丝数 × 每行字节`。普通用户扇出有限、写完就完；大 V 一条内容要写上亿行，写放大不可接受，所以只写发件箱、由粉丝读时补拉（推拉结合的阈值推导在 [63.7 信息流（推 / 拉 / 推拉结合）](../63-推荐系统/63.7-信息流.md)）。

**Q3** 点赞接口返回成功，但用户刷新后赞数没变，最可能的原因是什么？

▸ 答案：状态写成功了、计数同步失败或还没合批落地。状态是真相、计数是派生数据，正确做法是「状态先落库（唯一键幂等）→ 计数异步合并 → 读侧容忍短暂不一致」，并保留从状态表重建计数的能力（计数存储见 [44.22 计数系统](../44-数据库/44.22-计数系统.md)）。
