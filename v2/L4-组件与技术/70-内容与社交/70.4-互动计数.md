# 70.4 互动计数 (点赞 / 评论)

## 一句话

> 点赞/评论的难点不在「计数」，在**状态与计数是两份数据**：状态要幂等、可批量判定、不能重复；计数可近似、可重算、要抗热 key——两者的更新路径必须分开设计。

## 三个误区：点赞不是「计数 +1」

| 误区 | 现实 |
|---|---|
| 点赞 = 计数 +1 | 连点两次就 `+2`，刷新后数字虚高；真正要落的是「谁赞了哪条」这条**状态**，计数只是聚合结果 |
| 取消赞 = 计数 -1 | 重复取消会多减，并发下 `-1` 可能落在别的 `+1` 之前，计数被打负；应先改状态再重算/条件扣减 |
| 状态和计数放一张表 | 一行既要唯一约束、又要高频 `UPDATE` 聚合值，互相拖累 |

根因同一个：**状态和计数不是一种数据**——一个是明细 + 唯一约束，一个是聚合 + 可近似。

## 点赞模型：状态是真相，计数是派生

```text
like_state:  id, user_id, object_id, object_type, action, state, created_at, updated_at
             UNIQUE (user_id, object_id, object_type, action)
             KEY (object_id, object_type, state)
like_counter: object_id, object_type, cnt, PRIMARY KEY (object_id, object_type)
```

| 维度 | `like_state`（状态） | `like_counter`（计数） |
|---|---|---|
| 回答的问题 | 我赞没赞这条？这条被谁赞过？ | 这条一共多少赞？ |
| 写频率 | 每次点赞/取消各一行 | 每个赞一次写，必须合批 |
| 读模式 | 按 `(user, object)` 点查、按内容取 ID 列表 | 按内容取一个数、批量取 N 个 |
| 一致性 | 强一致，写完立刻可查（读己之写） | 最终一致，可延迟 1 秒 |
| 丢了怎么办 | 没法从计数反推「谁赞了」，不可重建 | 从状态表 `COUNT(*)` 或 bitmap `BITCOUNT` 重算 |

**谁是真相**：状态是真相，计数是可重建的派生数据。结论在 [44.22 计数系统](../44-数据库/44.22-计数系统.md) 已讲透（布局、合批、冷热分层不重复），本节只用后半句——**既然计数可重建，就不要为「绝对准」牺牲状态写入的幂等性**。

**「谁赞了这条」的明细列表**：按 `idx_object_state (object_id, object_type, state)` 做 `id` 游标分页，`id` 单调递增，深翻页不重不漏：

查询是 `WHERE object_id=? AND object_type=? AND state=1 AND id < ? ORDER BY id DESC LIMIT 50`。

可见性在这里收口：开「隐藏我的赞」的用户不出现、双向拉黑出列表时过滤、隐藏赞仍计入计数但不进列表——**列表条数 ≤ `like_counter.cnt`**，对账以状态表 `COUNT(*)` 为准。

取消赞不删行，改状态：

```sql
UPDATE like_state SET state = 0
 WHERE user_id=? AND object_id=? AND object_type=? AND action=1 AND state=1;
```

保留 `state=0` 有三层收益：审计可查、重复取消幂等（`affected rows=0`）、重建时不会把「取消」误当「从未点过」；代价是表随历史增长，按 `created_at` 归档。

## 幂等：唯一键兜底，条件更新收口

| 场景 | 期望结果 | 靠什么保证 |
|---|---|---|
| 同一用户连点 5 次赞 | 状态 1 行、计数 1 | 唯一键 + `ON DUPLICATE KEY UPDATE`，affected rows 为 1/2 才动计数 |
| 同一用户连点 5 次取消 | 状态 1 行 `state=0`、计数 0 | 条件 `UPDATE ... WHERE state=1`，只有第一次 `affected rows=1` |
| 取消赞后再点赞 | 状态仍 1 行、计数回到 1 | upsert 命中唯一键、state 0→1，affected=2 才 +1；用 `INSERT IGNORE` 会 affected=0、点赞无效 |
| 并发同用户点赞 | 只有 1 次成功 | InnoDB 唯一索引行级互斥，后来的冲突被忽略 |
| 并发不同用户点赞 | 计数精确 +N | 计数侧原子 `UPDATE cnt=cnt+1` 或 `INCR` |

核心写入只有十几行，顺序不能反（低 QPS 把计数放同事务；热点改异步，见「计数展示」的判据）：

```go
tx, _ := db.BeginTx(ctx, nil)
res, _ := tx.ExecContext(ctx,
    `INSERT INTO like_state (user_id, object_id, object_type, action, state)
     VALUES (?, ?, 1, 1, 1)
     ON DUPLICATE KEY UPDATE
       updated_at = IF(state = 0, CURRENT_TIMESTAMP, updated_at),
       state = 1`, uid, oid)
// affected rows：1=新插入、2=从 state=0 重新激活、0=本来已赞
if n, _ := res.RowsAffected(); n == 1 || n == 2 {
    tx.ExecContext(ctx, `UPDATE like_counter SET cnt = cnt + 1
                          WHERE object_id = ? AND object_type = 1`, oid)
}
return tx.Commit()
```

取消赞是镜像：`UPDATE like_state SET state=0 WHERE ... AND state=1`，affected=1 才 `UPDATE like_counter SET cnt=cnt-1 ... AND cnt>0`。

**取消赞后再赞是最容易漏的坑**：保留 `state=0` 行后，重新点赞若还走 `INSERT IGNORE`，唯一键命中 → `affected rows=0`，state 停在 0、计数不加，用户看到「点了没反应」。`ON DUPLICATE KEY UPDATE` 的 affected rows 正好给出三态：1=新插入、2=0→1 重新激活、0=本来已赞；别把 `updated_at` 无条件写进 UPDATE，否则隔一秒的重复点赞也被算成 2、计数多加。

**非共识增量在这里**：大量示例写「先 `SELECT` 判断有没有点过，没有就 `INSERT`」。它不幂等，因为 check 和 act 不是原子操作：本机 100 并发同一用户 → **状态行 69/81/74（重复 68/80/73）、计数 100（真相 1）**；5000 并发 → **状态行 2540（去重用户 1000，重复 1540）、计数 5000**。唯一键不是优化，是正确性的下限（五种实现见 [25.4 幂等设计与去重](../../L1-分布式原理/25-并发、冲突与幂等/25.4-幂等设计与去重.md)）。

**缓存与 DB 的顺序**：先写 DB、再删缓存（Cache-Aside），见 [41.1 缓存模式 (旁路 / 读穿 / 写穿 / 写回)](../41-缓存/41.1-缓存模式.md)；反过来会在掉电/回滚后留下「缓存有赞、DB 没有」的脏状态。

**计数负数保护**：不做裸 `cnt = cnt - 1`，要么条件扣减 `WHERE cnt > 0`，要么等窗口按状态变化重算——计数是派生数据，**重算永远比减一安全**。

**未读数别在这里做**：@/评论/赞的未读是「每人一份、进页面置 0」的一对一数据，用通用计数即可，见 [44.23 未读数系统](../44-数据库/44.23-未读数系统.md)；互动计数只回答「一共多少」。

## 已赞状态批量判定：bitmap + pipeline

一屏 Feed 要回答 20 次「我赞过吗」，后台列表要回答 1000 次（出流侧怎么把这些判定并进 BFF 的批量回查，见 [70.2 Feed 流架构 (推 / 拉 / 推拉结合)](70.2-Feed流架构.md)）。逐个 `GETBIT` 是 1000 次 RTT，本机实测单次 RTT **86.7 µs**，1000 次 **86.7 ms**；一屏 20 条也要 1.7 ms 纯等待。批量判定是渲染路径的底线。

```text
key = like:bitmap:{object_type}:{object_id}
bit = 稠密用户编号（user_id 经映射/取模得到，见坑 1）
SETBIT like:bitmap:1:1001 42 1     -- 用户 42 赞了内容 1001
GETBIT like:bitmap:1:1001 42       -- 判定
BITCOUNT like:bitmap:1:1001        -- 重建这条内容的点赞数
```

两个坑必须先说：

1. **`user_id` 不能直接当 bit 偏移**：64 位雪花号会把单个 key 撑到 2^63 位。做法是取模到固定位宽（如 `user_id % 2^27`，16 MB），碰撞用状态表兜底；或用 Roaring Bitmap 分容器。
2. **bitmap 只给热内容建**：12.5 MB/条 × 10 万条日活 = 1.25 TB，放不下。按访问量取 top N（如 5 万条）或最近 7 天滚动，冷内容回落 `SELECT ... FROM like_state`，读不到按「未赞」处理。

**热 key 按用户分片**：把一条内容的 bitmap 拆成 16 个 key，第 i 片只存 `user_id % 16 == i` 的用户、片内位偏移 `user_id / 16`；判一个人只需读 1 片（1 个 `GETBIT`），写入与判定按 16 个 key 摊到 16 个 slot，爆款内容单 key 的 QPS 直接除 16。分片键设计见 [19.8 热点与数据倾斜](../../L1-分布式原理/19-数据分区/19.8-热点与数据倾斜.md)。同进程 A/B 实测：pipeline `GETBIT` 1000 对象 **1.125 ms** vs 逐个 **86.696 ms**（**77.0 倍**）；一次 `MGET` 1000 计数 **498 µs** vs 逐个 **85.358 ms**（**171.3 倍**）。

## 计数展示：可近似、可合批、可重建

合批的收益与窗口选择在 [44.22 计数系统](../44-数据库/44.22-计数系统.md) 已推导过（写次数 ÷25、最大延迟一个窗口），本节只补实测量级：100 万事件、20 个对象、窗口 500，逐条 **1,000,000 次写 / 84.38 s** vs 合批 **40,000 次写 / 261 ms**（25 倍 / 323.6 倍）。

**什么时候用哪种**：单对象、低 QPS（个人主页、小社区）把计数和状态放同一事务精确 `+1`，简单且强一致；热点对象、高 QPS 才拆——状态同步落库、计数异步合批，代价是一个窗口的延迟。两种都对，按 QPS 选一种，不要两个都上。

展示口径落在「近似」上：`1.2 万` / `3.5 亿` 缩写、四舍五入、负数兜底 0。前端点赞成功先本地 `+1`；计数读不到显示上一快照，再读不到隐藏；`BITCOUNT` / `COUNT(*)` 定期重建对账，错乱最多存活一个重建周期。

## 评论：树、游标、软删、审核态

点赞是「状态 + 计数」，评论是「**树 + 分页 + 审核状态**」叠在一起，任何一件照点赞做都翻车。

```sql
CREATE TABLE comment (
  id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  object_id   BIGINT UNSIGNED NOT NULL,
  root_id     BIGINT UNSIGNED NOT NULL DEFAULT 0,  -- 顶级=0；回复=所属顶级评论 id
  parent_id   BIGINT UNSIGNED NOT NULL DEFAULT 0,  -- 直接父评论 id
  user_id     BIGINT UNSIGNED NOT NULL,
  state       TINYINT NOT NULL DEFAULT 1,          -- 1待审 2通过 3拒绝 4软删
  content     VARCHAR(2000) NOT NULL,
  reply_count INT NOT NULL DEFAULT 0,
  created_at  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  seq         BIGINT UNSIGNED NOT NULL,            -- 单调递增，同毫秒 tiebreaker
  KEY idx_object_cursor (object_id, root_id, state, created_at, seq)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**只做两级树**：顶级评论 + 回复（楼中楼），`root_id` 指向顶级、`parent_id` 指向父级；更深层级用「展开更多回复」在同一 `root_id` 下翻页。无限树的深度优先分页无法用稳定游标表达，每加一层多一次递归查询。

**游标分页**。顶级评论按 `(created_at DESC, seq DESC)` 翻页，下一页带上上一页最后一条的 `(created_at, seq)`：

```sql
SELECT id, root_id, user_id, content, created_at, seq
  FROM comment
 WHERE object_id = ? AND root_id = 0 AND state = 2
   AND (created_at < ? OR (created_at = ? AND seq < ?))
 ORDER BY created_at DESC, seq DESC
 LIMIT 20;
```

本机 21500 行（object 5001 有 1000 顶级 + 500 回复，另 100 个对象各 200 条噪声）实测：深翻第 900 行时，`OFFSET 900` 的 `EXPLAIN ANALYZE` 扫描 **920 行**；改用 `(created_at, seq)` 游标只扫 **20 行**，两者都走 `idx_object_cursor`。`object_id` 放最左因为它选择度最高且是等值条件：先锁一条内容，再按 `root_id`、`state` 等值、`created_at`、`seq` 有序，索引直接给出翻页顺序。`seq` 是同毫秒 tiebreaker，否则两页会重复或漏条；热度排序用 `(heat_score, seq)` 双游标且只用于首屏。

**软删 + 计数**。`state=4` 表示已删除，列表显示占位或整条隐藏，**不物理删行**：物理删会把楼中楼回复变孤儿，`reply_count` 也永久偏移。实测把一条顶级评论置 4 后，可见顶级 1000 → **999**，其 **500 条回复仍在库里**。计数只统计 `state=2` 的 `root_id=0` 行，`reply_count` 按窗口异步重算，不在软删热路径上减一。

**审核态与 [70.1 内容生产与审核](70.1-内容生产与审核.md) 的流水线呼应，但模型不同**：70.1 把「审到哪一步」和「谁能看见」拆成 `status` + `visibility` 两列；评论只有 `state` 一列合并审核态与生命周期——1 待审仅作者可见、2 通过公开、3 拒绝仅作者可见、4 软删都不可见，只有 `state=2` 计入评论数。代价是每新增一种可见性就多一个分支。

「先审后发」时新评论对作者可见、对他人不可见，过滤条件永远 `state=2`；「先发后审」额外加「作者可见自己的待审评论」分支。列表缓存只缓存 `state=2` 首屏，状态一变就删对应 `object_id` 的版本号——评论写频远低于点赞，删缓存比合批简单。

## 防刷与限流

唯一键只保证「重复请求不重复写」，防不住「伪造 1000 个账号点赞」，入口必须限流：

- 单用户 5 次/秒、300 次/小时：超限 429 或排队（按接口选其一）。
- 单设备或单 IP 20 次/秒：超限进人机校验。
- 单内容 1 分钟点赞增速超基线 10 倍：计数进「可疑」态，展示值冻结。

漏桶/令牌桶/滑动窗口的实现与参数标定见 [35.7 限流 (漏桶 / 令牌桶 / 滑动窗口 / 自适应)](../../L3-质量属性/35-可用性/35.7-限流.md)。与风控联动只留一句判据：**计数异常突增先冻结展示、再异步回查状态表**，决策点编排见 [68.1 风控系统架构](../68-风控/68.1-风控系统架构.md)——数字可重建，可信感知不可重建。

## 实测：Redis bitmap vs SET（100 万用户 × 一条内容）

环境：macOS / Apple 芯片 / Go 1.27.1 / Redis 8.10.2（127.0.0.1:16394）/ 2026-11-21；同机 4 个写作任务并行，延迟允许 ±30%，内存与计数是确定性结果。

```go
for u := 0; u < 1_000_000; u++ {          // A/B 都按 batch=1000 pipeline 写入
    pipe.SetBit(ctx, "like:bitmap:obj:1", int64(u), 1) // A：bit 偏移 = 稠密编号
    // pipe.SAdd(ctx, "like:set:obj:1", u)             // B：member = 稠密编号
    if (u+1)%1000 == 0 { pipe.Exec(ctx); pipe = rdb.Pipeline() }
}
// 内存读 MEMORY USAGE / INFO memory（本机禁用 DEBUG OBJECT）
```

```text
== 方案 B: SET (SADD x1,000,000, member = dense uid 0..999999) ==
```

## 实测：批量已赞判定（1000 个对象，pipeline vs 逐个 RTT）

环境同上（Redis 8.10.2 / 127.0.0.1:16394）。1000 个内容 bitmap，同一用户对偶数对象已赞；A 逐个 `GETBIT`，B 一个 pipeline 里 1000 个 `GETBIT`，C1 逐个 `GET`、C2 一次 `MGET` 1000 个计数；跑 5 轮取平均/最小。

```go
for i := 0; i < 1000; i++ { rdb.GetBit(ctx, key(i), uid) } // A：1000 次 RTT
p := rdb.Pipeline()                                        // B：1 次 RTT
for i := 0; i < 1000; i++ { p.GetBit(ctx, key(i), uid) }
p.Exec(ctx); rdb.MGet(ctx, cntKeys...)                     // C2：一次取 1000 计数
```

```text
A 逐个 GETBIT (1000 RTT)  : avg 86.696ms     best 84.448ms
B pipeline GETBIT (1 RTT) : avg 1.125ms      best 870µs
A/B 加速倍数              : 77.0 x
单次 RTT 折算（A/1000）   : 86.7 µs

C1 逐个 GET (1000 RTT)    : avg 85.358ms     best 84.669ms
C2 MGET (1 RTT)           : avg 498µs        best 459µs
C1/C2 加速倍数            : 171.3 x
结果一致 (1000/1000)      : true
```

| 判定方式 | 1000 个对象耗时 | 架构含义 |
|---|---|---|
| pipeline `GETBIT` | 1.125 ms | 同样 1000 个 bit，批量摊掉 RTT 接近纯计算 |
| 一次 `MGET` 计数 | 498 µs | 计数快照批量取，与状态判定各走一条 pipeline |

## 实测：MySQL 1000 并发点赞幂等（含错误版对照）

环境：macOS / Apple 芯片 / Go 1.27.1 / MySQL 26.7.0（127.0.0.1:13390，db=`ch70_4`）/ 2026-11-21。应用连接池 64，1000 个 goroutine 同时起跑（请求并发 1000，DB 连接排队执行）。口径：`INSERT 行数` 是执行插入的次数，`COUNT(*)` 是表里实际行数，`去重用户对数` 是 `COUNT(DISTINCT user_id)`；错误版没有唯一键，每插入一次就多一行，所以前两项相等。

```go
// 正确版：aff1=新插入、aff2=取消赞后重新激活；错误版换成「SELECT 为 0 则 INSERT」且计数无条件 +1
res, _ := tx.ExecContext(ctx, `INSERT INTO like_state (user_id, object_id, object_type, action, state)
    VALUES (?,?,1,1,1) ON DUPLICATE KEY UPDATE state=1`, uid, oid)
if n, _ := res.RowsAffected(); n == 1 || n == 2 { // 只有真的变成「赞」才动计数（同事务）
    tx.ExecContext(ctx, `UPDATE like_counter SET cnt=cnt+1 WHERE object_id=? AND object_type=1`, oid)
}
```

```text
[1a] 同一用户(user=7) 重复点赞 100 次，object=1001
  INSERT 行数=1   COUNT(*) 行数=1   去重用户对数=1   like_counter.cnt=1

[1b] 1000 个不同用户各点赞 1 次，object=1002
  INSERT 行数=1000   COUNT(*) 行数=1000   去重用户对数=1000   like_counter.cnt=1000

[2a] 同一用户(user=7) 重复点赞 100 次，object=2001，跑 3 轮
  round1: requests=100 success=100 errors=0 elapsed=24ms INSERT行=69 COUNT(*)行=69 去重用户对=1 重复行=68 计数=100 (期望 1)
```

## 实测：100 万次点赞事件，合批 vs 逐条写

环境同上（Redis 8.10.2 / 127.0.0.1:16394）。20 个对象、窗口 500；A 每个事件同步 `INCR`，B 窗口内聚合后 pipeline `INCRBY`。只测写命令数与墙钟耗时。

```go
for i := 0; i < 1_000_000; i++ { rdb.Incr(ctx, key(i%20)) } // A：逐条
buf[k] += 1                                                  // B：窗口聚合
if inWindow == 500 { p := rdb.Pipeline(); for k, v := range buf { p.IncrBy(ctx, k, v) }; p.Exec(ctx) }
```

```text
A 逐条写: 写命令 1000000    耗时 1m24.381s    吞吐 11851 事件/s
B 合批写: 写命令 40000      耗时 261ms        吞吐 3834791 事件/s (pipeline 执行 2000 次)
写命令削减             : 25.0 x
耗时下降               : 323.6 x
结果一致 (总和 1000000 vs 1000000) : true
```

| 指标 | 逐条写 | 合批写 | 架构含义 |
|---|---|---|---|
| 写命令数 | 1,000,000 | 40,000 | 网络往返是主成本，25 倍来自「窗口 500 / 对象 20」 |
| 耗时 | 84.38 s | 261 ms | 同机同进程 A/B，差 323.6 倍 |

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：状态真相在 **MySQL 8.x**（`like_state` 唯一键 + `like_counter`）；**Redis 8.x** 只存「已赞状态查询缓存（bitmap + pipeline + 按用户分片）+ 计数」。

**可抄**（本机真跑，原始输出在 `.cache/ch70/s704/raw/exp5_落地命令.txt`）：

```bash
# 1) 已赞状态：写、判、重建计数
redis-cli -p 16394 SETBIT like:obj:1001 42 1     # 返回 0（该位原为 0）
redis-cli -p 16394 SETBIT like:obj:1001 43 1     # 返回 0
redis-cli -p 16394 GETBIT like:obj:1001 42       # 返回 1
redis-cli -p 16394 BITCOUNT like:obj:1001        # 返回 2
redis-cli -p 16394 MEMORY USAGE like:obj:1001    # 返回 40

# 2) 唯一键 DDL（真跑过，SHOW CREATE TABLE 与之一致）
mysql --protocol=tcp -h127.0.0.1 -P13390 -uroot ch70_4 -e "
CREATE TABLE IF NOT EXISTS like_state (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_id BIGINT UNSIGNED NOT NULL,
  object_id BIGINT UNSIGNED NOT NULL,
  object_type TINYINT NOT NULL DEFAULT 1,
  action TINYINT NOT NULL DEFAULT 1,
  state TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_object_action (user_id, object_id, object_type, action),
  KEY idx_object_state (object_id, object_type, state)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;"

# 3) 并发幂等测试（100 并发同用户 + 1000 用户并发 + 错误版 + 取消赞后再赞）
cd .cache/ch70/s704/code && go run ./cmd/e3_mysql
```

**可验**：三条命令判断「状态与计数是否已分家且可重建」：

```bash
redis-cli -p 16394 INFO memory | grep used_memory_human   # bitmap 常驻内存是否失控
redis-cli -p 16394 MEMORY USAGE like:obj:1001             # 单条内容的状态内存
mysql --protocol=tcp -h127.0.0.1 -P13390 -uroot ch70_4 -e \
  "SELECT object_id, COUNT(*) c FROM like_state WHERE state=1 GROUP BY object_id LIMIT 5;"
```

判据：同一内容 `like_counter.cnt` 与状态表 `COUNT(*)` 的差应 ≤ 一个合批窗口的事件数；持续更大说明在丢事件，先重建再查根因。

**可退**：互动计数天生可退，三条退路按代价从低到高：

| 退路 | 做法 | 用户感知 |
|---|---|---|
| 隐藏点赞数 | 只显示「已赞/未赞」 | 数字消失，状态仍在 |
| 计数回落 DB | 关 Redis 计数，读 `like_counter` 或实时 `COUNT(*)` | 变慢/偶发旧值 |
| 关闭点赞功能 | 特性开关摘掉整条链路，见 [55.2 特性开关](../../L5-工程效能/55-发布与回滚/55.2-特性开关.md) | 入口消失，数据保留 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 只 `UPDATE like_count=like_count+1` 不写状态行 | 无法判重、无法回答「我赞没赞」，取消赞也做不了 |
| 取消赞直接 `like_count-1` | 重复取消/并发交错把计数打负，且永远修不回真实值 |
| 取消赞保留 `state=0`、重新点赞仍用 `INSERT IGNORE` | 唯一键命中、affected=0：state 停在 0、计数不加，用户「点赞无效」 |
| 先 `SELECT` 再 `INSERT` 做幂等 | 100 并发同一用户实测出 69/81/74 条状态行、计数 100 |
| 状态和计数同一张表同一行 | 唯一约束与高频 `UPDATE` 抢同一行锁，写入并发被压死 |
| 用 SET 存一亿用户的点赞状态 | 32.28 B/用户 × 1 亿 = 3.23 GB（3.01 GiB）/条，内存先崩 |
| 评论用 `OFFSET` 深翻页 | 深翻 900 行实测扫 920 行；新评论插入还会造成重复/漏条 |

## 三条铁律

> 🔑 **状态是真相，计数是派生**：单对象低 QPS 可在同事务精确 `+1`；热点/高 QPS 才把计数异步合批。计数丢了从状态重算，状态写不进去宁可让点赞失败。

> 🔑 **幂等下沉到唯一键，不靠应用层判断**：`SELECT` 再 `INSERT` 并发下必错（100 并发留下 69/81/74 条状态行）；重新点赞必须用 upsert 的 affected rows 区分新插入/重新激活/本来已赞。

> 🔑 **热内容才建 bitmap，判定一律批量**：12.5 MB/亿用户的账先算清，只给 top 内容建；1000 个对象用 pipeline 差 77.0 倍，逐条 RTT 不可接受。

## 自检

**Q1** 为什么「点赞数 +1」不能作为点赞接口的全部逻辑？

▸ 答案：计数不是真相，状态才是。只加计数就没有「谁赞过」的明细，无法判重、无法回答「我赞没赞」、无法取消赞，错乱后也无法重建。先写 `like_state`（唯一键保幂等），只有真变成「赞」的那次才触发计数。

**Q2** 取消赞后再点赞，为什么用 `INSERT IGNORE` 会让用户「点了没反应」？正确写法是什么？

▸ 答案：取消赞保留 `state=0` 行，重新点赞唯一键命中，`INSERT IGNORE` 返回 affected=0，state 停在 0、计数不加。正确写法是 `ON DUPLICATE KEY UPDATE state=1`，按 affected rows：1=新插入、2=0→1 重新激活（要 +1）、0=本来已赞。实测 like→unlike→like 的 state/计数为 1/1 → 0/0 → 1/1。

**Q3** 1000 个不同用户点赞同一条内容，唯一键并不冲突，计数怎么保证不多不少？

▸ 答案：唯一键只负责「同一用户不重复写」，不同用户互不冲突；计数正确性靠「affected rows 为 1 或 2 才同事务 `UPDATE cnt=cnt+1`」。实测 1000 个不同用户 → 状态行 1000、计数 1000。

**Q4** 为什么说「先 `SELECT` 再 `INSERT`」不是幂等？

▸ 答案：check 和 act 不是原子操作，并发请求可以同时查到 0 再同时插入。本机 100 并发 3 轮留下 69/81/74 条状态行、计数 100（真相 1）；5000 并发留下 2540 条状态行（去重用户 1000）、计数 5000。错误依赖调度时机，线上是「偶尔多几条」，比确定性错误难查。

**Q5** 1 亿用户的点赞状态，为什么 bitmap 只需 12.5 MB 而 SET 要 3.23 GB？

▸ 答案：bitmap 是「1 用户 1 bit」，1 亿 bit = 12,500,000 B = 12.5 MB；SET 每成员实测 32.28 B，1 亿成员 = 3,227,758,700 B = 3.23 GB（3.01 GiB）。对含分配器开销 246 倍、对有效位 258 倍。

**Q6** 评论为什么只做两级树，而不是无限层级？

▸ 答案：无限树的深度优先分页无法用稳定游标表达，每加一层多一次递归查询，且「展开第 N 层」的游标语义会随父节点变化失效。两级树把楼中楼压平到同一 `root_id` 下按 `(created_at, seq)` 翻页，分页稳定、索引单一。

**Q7** 评论软删之后，子回复和 `reply_count` 怎么处理？

▸ 答案：只把该评论 `state` 置 4，不物理删行，子回复保留（实测软删一条顶级评论后 500 条回复仍在，可见顶级 1000 → 999）。列表按 `state=2` 过滤；`reply_count` 不在热路径 `-1`，按窗口从状态表重算。
