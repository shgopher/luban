# 71.4 轨迹存储与查询

## 一句话

> 轨迹是「按时间有序的点流」，难点是让「人 + 时间」与「空间 + 时间」两类查询同时成立：本机把 100 万点压到 **4.96 B/点**、回放 1 万点比每点一行快 **14.9×**，但段级空间预筛的候选放大率是 **112.8×**——解法是**点位压缩 + 分段存储 + 时间主索引 + 位点级空间派生索引**，并把压缩/抽稀误差写进契约。

## 三个误区

| 误区 | 现实 |
|---|---|
| 「每点一行最直观，加索引就行」 | 100 万点：每点一行 78.8 B/点（含索引），分段表 34.2 B/点；回放 1 万点 P50 5.07 vs 0.34 ms；1 亿点/天 90 天 ×3 副本 2.13 vs 0.92 TB |
| 「压缩比越高越好」 | CSV→delta 从 34.00 降到 4.38 B/点；量化从 1e-6 放到 1e-5 只省 31%，最大误差却从 0.14 m 涨到 1.40 m——1 Hz 静止轨迹上就是每步一次伪位移 |
| 「里程就是把相邻点距离加起来」 | 静止 1 小时、σ=5 m、1 Hz：相邻点累加得 31.282 km（真值 0）。精度闸只减 2.2%、速度闸只减 0.01%；只有停留聚合（R=50 m）能归零，R 小于 5σ 时闸门被打穿（σ=10、R=20 m 残余 63.349 km） |

## 数据模型：一条轨迹拆成「点流 + 段」

轨迹只有两种落库形态：**点表**（一行一个 fix，主键 `(uid, ts)`）与**段表**（一行一个 segment，几百点打包成 BLOB）。生产不是二选一，而是「段表做主存、点表做空间派生」或反过来，取决于哪类查询更多（见实测 C）。

坐标一律 **WGS84 + int32 定点 1e-7 度**，与 [71.1 地理编码与坐标系统](71.1-地理编码与坐标系统.md) 的存储结论一致（半量化步长 5.6 cm，远小于 GPS 的 3–10 m 噪声）：

| 表 | 字段 | 类型 | 选型理由 |
|---|---|---|---|
| track_point | uid / ts | BIGINT | 用户 ID + 时间；主键 `(uid, ts)`，顺序追加页分裂少 |
| track_point | lng / lat | INT | 定点 1e-7 度，4+4 字节、可索引、可范围比较；比 `DECIMAL(9,7)` 省 1–3 字节 |
| track_point | acc / speed / heading | SMALLINT | 精度（米）、×10 定点速度与航向；过闸与停留判定 |
| track_segment | uid / seg_id | INT | 段主键 `(uid, seg_id)` |
| track_segment | start_ts / end_ts | BIGINT | 段时间范围；`(uid, start_ts)` 二级索引供查询 1 |
| track_segment | point_count / distance_m | SMALLINT / INT | 500 点/段；段内里程，统计不重算 |
| track_segment | bbox 四列 / gh6 | INT / CHAR(6) | 段级空间预筛（1e-7 度）+ 起点格辅助 |
| track_segment | points_blob | BLOB | 编码点流；实测均值 2,479 B/段 = 4.96 B/点 |

类型判据：定长、可索引、可范围比较；JSON 每条至少 60 B 且不能整块扫，float64 是 24 B/点。

三条读数：

1. **生产选 ③，不是选最小**：4.38 B/点是二进制的 5.48×、CSV 的 7.76×；解码 10.37 ms/百万点意味回放 1 万点只花 0.1 ms 量级，而 MySQL 同一次查询要 5.07 ms（实测 C）——**解码不是瓶颈，磁盘和网络才是**。
2. **误差是显式参数，不是压缩的副作用**：0.14 m 来自截断量化——1e-6 纬度步长 0.111 m、40°N 经度步长 0.085 m，二维合成上界 √(0.111²+0.085²)=0.14 m；同样 1e-6 四舍五入后上界 0.07 m，与 [71.1 地理编码与坐标系统](71.1-地理编码与坐标系统.md) 实测的 0.065 m 对得上。**编码器必须 `round` 而不是 `trunc`，否则误差上限白翻一倍**。
3. **Polyline 的 2.77 B/点是假便宜**：只编码坐标，时间戳得另存（1.00 B/点），只能顺序解码、精度锁死 1e-5；生产库 int32 1e-7 的 blob 是 4.96 B/点（实测 C）——多 0.58 B/点，换 0.006 m 定点误差。

时序库的「差分 + XOR」把 16 字节/点压到 2–5 字节/点，那是一维时间序列算法；轨迹坐标是二维空间量，delta+zigzag varint 同一量级，不必再实现 XOR，见 [44.17 时序数据库](../44-数据库/44.17-时序数据库.md)。

## 实测 C：两类查询，真 MySQL

环境：macOS arm64 / Apple 芯片 / go1.27.1 / MySQL **26.7.0 @ `127.0.0.1:16306`**（buffer pool 128 MiB）/ 2026-11-21。数据：100 用户 × 10,000 点 = 1,000,000 点，采样 1–5 s，500 点/段 → **2,000 段**，geohash level 6，坐标量化 1e-7。

```sql
-- 方案 X：每点一行
CREATE TABLE track_x (
  uid INT NOT NULL, ts BIGINT NOT NULL,
  lng INT NOT NULL, lat INT NOT NULL, gh6 CHAR(6) NOT NULL,
  PRIMARY KEY (uid, ts)) ENGINE=InnoDB;
ALTER TABLE track_x ADD INDEX idx_gh_ts (gh6, ts);

-- 方案 Y：分段 BLOB + bbox 覆盖格倒排
CREATE TABLE track_seg (
  uid INT NOT NULL, seg_id INT NOT NULL,
  start_ts BIGINT NOT NULL, end_ts BIGINT NOT NULL,
  point_count SMALLINT NOT NULL,
  bbox_min_lng INT NOT NULL, bbox_max_lng INT NOT NULL,
  bbox_min_lat INT NOT NULL, bbox_max_lat INT NOT NULL,
  gh6 CHAR(6) NOT NULL, distance_m INT NOT NULL, points_blob BLOB NOT NULL,
  PRIMARY KEY (uid, seg_id), KEY idx_uid_start (uid, start_ts)) ENGINE=InnoDB;

CREATE TABLE seg_cells (
  gh6 CHAR(6) NOT NULL, uid INT NOT NULL, seg_id INT NOT NULL,
  start_ts BIGINT NOT NULL, end_ts BIGINT NOT NULL,
  KEY idx_gh (gh6, start_ts)) ENGINE=InnoDB;
```

复现：`cd tools/examples/71.4-trajectory/code && go run . exp_c`（重建库 `ch71_track`，约 50 s）。原样输出（`raw/c-mysql.txt`，节选，建表步骤略）： 示例说明见 [tools/examples/71.4-trajectory/](../../../tools/examples/71.4-trajectory/README.md)。

每类查询 100 轮、预热 10 次；同机 4 任务并行，P50 稳定、P99 有调度毛刺（`raw/c-mysql-run1.txt`）。

| 查询 | 方案 | 扫描/解码 | P50 | P99 | 返回 |
|---|---|---|---|---|---|
| 查询 1：某用户某 1 小时 | X 每点一行 | 扫 1,202 行 | 1.09 ms | 2.00 ms | 1,202 点 / 19,225 B |
| 查询 1：某用户某 1 小时 | Y 分段 | 3.4 段，解码 1,695 点 | 0.26 ms | 1.82 ms | 1,202 点 / 19,225 B |
| 查询 2：某格 + 某 1 小时 | X 位点索引 `(gh6, ts)` | 扫 288 索引项 | 0.55 ms | 2.06 ms | 288 点 |
| 查询 2：某格 + 某 1 小时 | Y 段 bbox 倒排 | 64.8 段，解码 32,425 点 | 3.80 ms | 8.23 ms | 288 点 |
| 查询 3：回放 1 万点 | X 每点一行 | 扫 10,000 行 | 5.07 ms | 7.48 ms | 10,000 点 / 160,000 B |
| 查询 3：回放 1 万点 | Y 分段 | 20 段 | 0.34 ms | 0.97 ms | 10,000 点 / 49,581 B |

四条读数：

1. **「人 + 时间」段表赢 4.2×（P50）**：查询 1 只碰 3.4 个段，X 扫 1,202 行；Y 解码 1,695 点才返回 1,202 点，**多解码 41%**，这是分段大小的第一个代价。
2. **「区域 + 时间」位点索引完胜**：X 的 `(gh6, ts)` 覆盖索引扫 288 项、P50 0.55 ms；Y 解码 32,425 点才筛出 288 点，**误命中 99.1%、放大率 112.8×**——段 bbox 是 500 点的外接矩形，横跨半个城区，与段内真实点几乎无关。
3. **段级空间索引不能只按起点格建**：只按段起点建 9 格索引的变体召回率仅 **23.0%**（6,622/28,755）——段移动 2–7 km，起点格和段内点格子不是一回事；必须维护「bbox→覆盖格」倒排（1M 点 252,404 行）。
4. **回放段表赢 14.9×**：取 1 万点，X 扫 10,000 行、返回 160 KB；Y 只读 20 个 BLOB、49,581 B（网络省 3.2×），回放天然适合整段顺序读。

结论不是「选 X 还是选 Y」，而是**两个索引分工**：主存按段（写放大低、回放快、体积小），「人+时间」走 `(uid, start_ts)`，「区域+时间」走位点级 `(gh6, ts)` 或「格内段数 ≈1」的段倒排。复合索引原理在 [44.8 索引原理 (B+ 树 / 哈希 / 覆盖索引 / 最左前缀)](../44-数据库/44.8-索引原理.md)，轨迹特有的两条是：**空间列必须在时间列左边**（先剪空间再剪时间）；**格前缀取 `r/c ≈ 1–3` 的层级**。段 bbox 的 112.8× 就是 [71.2 GeoHash 与空间索引](71.2-GeoHash与空间索引.md) 定义的候选放大率，超预算就换位点级索引。围栏判定同理走三级过滤（格+时间剪枝 → bbox 粗筛 → 逐点射线法）；停留点检测不要对全量轨迹跑 DBSCAN，用「速度阈值 + 时间窗 + 半径聚类」状态机，R 的取值就是实测 D 的停留半径。

## 实测 D：静止 1 小时的里程虚高

环境：macOS arm64 / Apple 芯片 / go1.27.1 / 2026-11-21；模拟「手机放桌上」1 小时，1 Hz 共 3,600 点，GPS 白噪声 σ=2/5/10 m。

```bash
cd tools/examples/71.4-trajectory/code && go run . exp_d 示例说明见 [tools/examples/71.4-trajectory/](../../../tools/examples/71.4-trajectory/README.md)。
```

原样输出（`raw/d-mileage.txt`）：

```text

sigma      每步均位移m       朴素km  闸1 acc>50    闸1+2 速度     闸3 R=20m     闸3 R=50m      R50/朴素%       步>5m占比
2            3.53     12.687     12.404     12.404        0.000        0.000         0.00         20.6%
5            8.69     31.282     30.592     30.592       21.369        0.000         0.00         77.5%
10           18.02     64.837     63.466     63.401       63.349        0.000         0.00         94.1%
```

| σ（米） | 朴素累加 | 折算「静止移动速度」 | 闸 1：acc>50 m | 闸 1+2：速度>200 km/h | 闸 3：停留聚合 R=20 m | 闸 3：停留聚合 R=50 m |
|---|---|---|---|---|---|---|
| 2 | 12.687 km | 12.7 km/h | 12.404 km（−2.2%） | 12.404 km（−2.2%） | 0.000 km | 0.000 km |
| 5 | 31.282 km | 31.3 km/h | 30.592 km（−2.2%） | 30.592 km（−2.2%） | 21.369 km（−31.7%） | 0.000 km |
| 10 | 64.837 km | 64.8 km/h | 63.466 km（−2.1%） | 63.401 km（−2.1%） | 63.349 km（−2.3%） | 0.000 km |

1. **虚增是量级错误**：真值 0，相邻点累加算出 12.687 / 31.282 / 64.837 km；每步均位移 3.53 / 8.69 / 18.02 m × 3,600 步。换算成速度，一部静止手机在「以 12.7–64.8 km/h 移动」——这就是「没出门被记 30 公里」的投诉来源。
2. **精度闸单独用没用**：`acc>50 m 丢弃`只减 2.2%——正常点 acc 都在 50 m 内，删点后相邻点被接线到更远、步长反而变大，过滤与重连必须一起做。
3. **速度闸在 1 Hz 下几乎不触发**：白噪声相邻步长最大约 4.5σ，σ=10 m 时 ≈45 m/s=162 km/h，仍在 200 km/h 之下，只减 0.01%。
4. **停留聚合才是对的闸，但 R 必须 ≥5σ**：R=50 m 三档全部归零（σ=10 恰好 5σ）；R=20 m（σ=10 的 2σ）时停留判定被噪声打穿，残余 63.349 km（只减 2.3%）。**R/σ≈5 是停留半径下限**，低于它闸门变成新的噪声放大器。顺序同样关键：**先判停留再算里程**，真实链路是「停留态里程冻结」的状态机。

## 写入链路：批量、幂等、乱序、分段

```text
设备：fix → WAL/SQLite（单调水位）→ 按水位补传 → 批量 ≤500 点/批
服务端：鉴权 → 幂等去重(uid,ts,seq) → 乱序窗口 5 min → 封段写 track_seg
  → 异步派生 seg_cells / 位点索引 → ack（已收水位）
```

| 环节 | 做法 | 数字依据 / 主场 |
|---|---|---|
| 设备缓冲 | WAL/SQLite outbox + 单调水位 | [69.4 边缘计算与断网续传](../69-物联网/69.4-边缘计算与断网续传.md) |
| 批量上报 | ≤500 点/批（与段大小同量级） | 实测 1M 行 10.2 s=98k 行/s；单点上报把 RTT 放大 500 倍 |
| 幂等 | 唯一键 `(uid, ts, seq)`，重复只覆盖 | [25.4 幂等设计与去重](../../L1-分布式原理/25-并发、冲突与幂等/25.4-幂等设计与去重.md) |
| 乱序窗口 | 5 min 内乱序可收，超窗进补录表 | [23.1 物理时钟与漂移](../../L1-分布式原理/23-时间、顺序与因果/23.1-物理时钟与漂移.md) |
| 分段触发 | 500 点 / 30 min / 4 KB / 静止 5 min 任一满足 | 实测 500 点=2,479 B；段越长 bbox 越大 |
| 派生索引 | 异步 worker 写 `seg_cells` | 实测 1M 点 252,404 行；同步写拉高 P99 |
| 分片 | 按 uid 哈希，单用户轨迹落同一分片 | 查询永远带 uid，[44.14 分库分表](../44-数据库/44.14-分库分表.md) |

阈值依据：**500 点**让 blob 稳定 2.4 KB、查询 1 只碰 3.4 段；**30 min** 是 bbox 精度上限；**4 KB** 是单次往返取一段的上限；**静止 5 min** 防停留段拉成长 bbox。

## 容量算术：1 亿点/天

| 方案 | B/点 | GB/天 | 90 天热存 | ×3 副本 | 1 年归档 |
|---|---|---|---|---|---|
| 每点一行 X（含 `(gh6,ts)` 索引） | 78.8 | 7.88 | 709 GB | **2.13 TB** | 2.88 TB |
| 分段 Y（含 bbox 格倒排） | 34.2 | 3.42 | 308 GB | **0.92 TB** | 1.25 TB |
| 分段 Y 仅段表（不做区域+时间） | 6.9 | 0.69 | 62 GB | 0.19 TB | 0.25 TB |

推导链：78.8 B/点 =(47.6+27.6) MiB×1,048,576÷1e6；34.2 同法；4.96 是 BLOB 实测。1 亿点/天 ×34.2 B =3.42 GB/天，×90 =308 GB，×3 =0.92 TB。

成本推算（**推算**，单价按 [39.3 存储分级](../../L3-质量属性/39-成本/39.3-存储分级.md) 的相对档位、热层示例 ¥0.60/GB·月）：90 天热存 ×3 副本，X ≈¥1,279/月、Y ≈¥552/月，差 **¥727/月**；年成本约 ¥16,200 vs ¥7,000。结论：**「每点一行」不是贵得离谱，而是 2.3 倍的钱换来更差的查询**——大头是热存 ×3 副本；空间倒排又把 Y 从 6.9 B/点抬到 34.2 B/点，不做「区域+时间」查询时 Y 只有 0.19 TB/90 天，那才是压缩红利。

## 冷热分层

| 层 | 放什么 | 组件 | 保留期 |
|---|---|---|---|
| 热 | 当前未封段 + 最近 24 h 封段 | Redis（TTL 24 h）/ MySQL 最近分区 | 1 天 |
| 温 | 90 天内封段 | MySQL 分段表 / 时序库 | 90 天 |
| 冷 | 90 天以上 | 对象存储 Parquet（uid 分桶 + 天分区） | 合规期（180 天/1 年） |

阈值是「访问频率 × 容忍延迟」的函数：90 天内要秒级，更早只进风控统计。分层收益来源（删数据 > 压缩 > 换层）见 [46.6 数据生命周期](../46-数据架构/46.6-数据生命周期.md) 与 [39.3 存储分级](../../L3-质量属性/39-成本/39.3-存储分级.md)，轨迹自己的数是：**热层 24 h 段只有 0.50 GB blob，放 Redis 放得下；90 天温层 308 GB 必须 `(uid, start_ts)` 加分区；冷层 181 GB/年约 ¥4/月（推算）**。时间分区让过期删除变成整块丢弃，见 [44.17 时序数据库](../44-数据库/44.17-时序数据库.md)。

## 生产落地：指名 → 可抄 → 可验 → 可退

**指名**：段主存 **MySQL 26.7.0**（本节实测库 `ch71_track` @ `127.0.0.1:16306`，`track_seg` + 派生 `seg_cells`）；热段 **Redis**（`track:seg:{uid}:{start_ts}` → BLOB，TTL 24 h）；温层 **TDengine / TimescaleDB / ClickHouse** 任一列存时序库；冷层 **Parquet + 对象存储**（uid 分桶 + 天分区）；编码用自研 delta+varint（实测 ③）或等价 ProtoBuf。位点级 `(gh6, ts)` 留在 MySQL 供「区域+时间」，段 bbox 只做粗筛。

**可抄**（前置 MySQL 26.7.0 @ `127.0.0.1:16306`，库 `ch71_track` 已按实测 C 建表）：

```bash
# ① 写一个段：BLOB 由 Go 编码器产出（500 点 ≈ 2,479 B），建表同实测 C
mysql -h127.0.0.1 -P16306 -uroot ch71_track -e "INSERT INTO track_seg VALUES
 (1001,0,1793510400,1793512500,500,1164810500,1164820000,399967940,399975000,'wx4g0b8',4200,0x0A8F01);"

# ② 查询 1：某用户某 1 小时（走 idx_uid_start）
mysql -h127.0.0.1 -P16306 -uroot ch71_track -e "SELECT start_ts,end_ts,point_count,points_blob FROM track_seg
 WHERE uid=1001 AND start_ts<1793514000 AND end_ts>1793510400 ORDER BY start_ts;"

# ③ 查询 2：某格 + 某 1 小时（走 seg_cells 倒排，段 bbox 粗筛）
mysql -h127.0.0.1 -P16306 -uroot ch71_track -e "SELECT s.points_blob FROM seg_cells c
 JOIN track_seg s ON s.uid=c.uid AND s.seg_id=c.seg_id
 WHERE c.gh6='wx4g0b' AND c.start_ts>=1793510400 AND c.end_ts<1793514000;"

# ④ 查询 3：回放 1 万点（20 段顺序读）
mysql -h127.0.0.1 -P16306 -uroot ch71_track -e "SELECT points_blob FROM track_seg WHERE uid=1001 ORDER BY start_ts;"
```

**可验**（本机真跑，所有数字可在 `raw/` 找到同源输出）：

| 检查项 | 期望值（本机实测） | 原始输出 |
|---|---|---|
| 压缩率与误差：③ / ④ | 4.38 B/点（0.14 m）/ 3.01 B/点（1.40 m） | `raw/a-compression.txt` |
| 抽稀：DP 10 m | 保留 10.31%，里程误差 2.485% | `raw/b-simplify.txt` |
| 查询 1 / 3：段表 vs 点表 P50 | 0.26 vs 1.09 ms（4.2×）/ 0.34 vs 5.07 ms（14.9×） | `raw/c-mysql.txt` |
| 查询 2：段 bbox 放大率 | 112.8×，误命中 99.1%，召回 100% | `raw/c-mysql.txt` |
| 静止里程：σ=5 m | 朴素 31.282 km，R=50 m 聚合后 0.000 km | `raw/d-mileage.txt` |

**可退**（四个开关，都要能在线切）：

| 退路 | 做法 | 代价 |
|---|---|---|
| 时序库挂 → MySQL 分段表 | 写入直接落 `track_seg`（本节 schema），查询走 `(uid, start_ts)`；时序库只当加速层 | 回放 P50 0.34 → 5.07 ms（14.9×）；区域+时间退回位点表 0.55 ms。实测 C 即此退路的完整形态 |
| 压缩编码故障 | 关掉 ③，落原始 float64（24 B/点） | 体积 ×5.48，解码更快（4.92 vs 10.37 ms/百万点） |
| 空间派生索引积压 | 只保「人+时间」，区域+时间退化为时间范围 + 逐点过滤 | 放大率从 112.8 变成全城/全表，必须限流 |
| Redis 热段不可用 | 直接读 MySQL 最近 24 h 段 | 查询 1 P50 0.26 → 1.09 ms，无丢失 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 每点一行当主存储 | 100 万点 78.8 B/点、回放 1 万点 5.07 ms；1 亿点/天 90 天 ×3 副本 2.13 TB（2.3 倍） |
| 抽稀阈值小于 GPS 噪声 | DP 2 m 在 σ=3 m 轨迹上只删 32%，存储没省、回放还变差 |
| 先算里程再过滤 | 精度闸只减 2.2%、速度闸 0.01%，静止 1 小时照样 31.282 km |
| 停留半径 R < 5σ | σ=10 m、R=20 m 时停留判定被噪声打穿，残余虚增 63.349 km（只减 2.3%） |
| 段级空间索引只按起点格建 | 召回率 23.0%，77% 的点永远查不到 |
| 用段 bbox 直接回答「区域+时间」 | 解码 32,425 点只返回 288 点（误命中 99.1%），放大率 112.8× |
| 压缩不存时间戳（Polyline 裸坐标） | 回放无法排序、去重没有时间键；2.77 B/点省下的是可用性 |

## 三条铁律

> 🔑 **压缩 = 体积 × 误差 × 解码成本三元组**：只报「4.38 B/点」不报「最大误差 0.14 m、解码 10.37 ms/百万点」等于没写；误差契约要能翻译成业务承诺（回放 ≤10 m、围栏漏判 ≤20 m）。

> 🔑 **里程只由「去过抖、去过重、按停留状态分段」的轨迹算**：原始点流直接相邻累加，静止 1 小时能算出 12.7–64.8 km；精度闸与速度闸治不了它，停留聚合（R ≥5σ）才是闸；顺序必须是先判停留再累加。

> 🔑 **两类查询分开建索引，放大率按实测记账**：人+时间走 `(uid, ts)`/段主键，区域+时间走位点级 `(gh6, ts)` 或「段 bbox→覆盖格」倒排；段 bbox 只能粗筛，本机放大率 112.8×、误命中 99.1%。

## 自检

**Q1** 1 亿点/天、4.96 B/点、90 天热存、3 副本，要多少存储？每点一行呢？

▸ 答案：只算 blob：1e8×4.96 B=0.50 GB/天→90 天 44.6 GB→×3=134 GB；完整口径 34.2 B/点→0.92 TB。每点一行 78.8 B/点→2.13 TB，按 ¥0.60/GB·月差 ¥727/月。推导链：B/点×1e8÷2^30=GB/天。

**Q2** 量化从 1e-6 放到 1e-5 省了 31% 体积，为什么可能让里程更不准？

▸ 答案：1e-6 最大误差 0.14 m、1e-5 是 1.40 m（实测 A）。静止 1 Hz 时量化抖动被当成位移：σ=2 m 每步均位移 3.53 m，再叠 1.4 m 伪位移，3,600 步可再虚增 5.04 km（推算：1.4×3600）。1e-5 只用于展示。

**Q3** DP 与在线距离阈值同为 10 m，保留率 10.31% vs 74.04%，差在哪？

▸ 答案：DP 判「子段内点到弦的垂直距离 ≤ε」，直路只留两端点；在线只判「离上一保留点 ≥ε」，低速、等灯、抖动很快凑够 10 m 而留点。实测在线体积是 DP 的 6.96×，里程误差更小（1.775% vs 2.485%）是抖动抵消切角所致。

**Q4** 「某区域+某 1 小时」用段 bbox 预筛，为什么放大 112.8 倍？怎么降到个位数？

▸ 答案：段=500 点≈25 分钟、移动 2–7 km，bbox 覆盖上百个 level-6 格；一个格+1 小时命中 64.8 个候选段，解码 32,425 点才筛出 288 点（误命中 99.1%）。降法：① 位点级 `(gh6, ts)` 索引（288 项、0.55 ms、放大率 1.0）；② 缩短段让 bbox 变小；③ 维护「bbox→覆盖格」倒排（起点格召回仅 23.0%）。

**Q5** 静止 1 小时、σ=5 m，朴素里程 31.282 km。三道闸各减掉多少？R 取多少？

▸ 答案：精度闸 12.404 km（−2.2%）；速度闸 30.592 km（−2.2%）；停留聚合 R=20 m 21.369 km（−31.7%）、R=50 m 归零。R 必须 ≥5σ：σ=10、R=20 m 残余 63.349 km（只减 2.3%）。

**Q6** 设备时钟慢 3 分钟，补传点 ts 全偏早，轨迹怎么乱？唯一键和窗口怎么定？

▸ 答案：偏早的 ts 落进已封段范围，会让段内时间非单调、排序错位，查询 1 的 `start_ts<hi AND end_ts>lo` 漏或重。做法：唯一键 `(uid, ts, seq)` 兜底（见 [25.4 幂等设计与去重](../../L1-分布式原理/25-并发、冲突与幂等/25.4-幂等设计与去重.md)）；按收到时间维护 5 min 乱序窗口，超窗进补录表按 ts 回填；封段用收到时间（漂移见 [23.1 物理时钟与漂移](../../L1-分布式原理/23-时间、顺序与因果/23.1-物理时钟与漂移.md)）。

**Q7** 回放 1 万点方案 Y 比 X 快 14.9 倍，为什么不能所有查询都只留 Y？

▸ 答案：Y 赢在「按 uid 顺序取整段」，输在「区域+时间」：段 bbox 放大 112.8×、误命中 99.1%，P50 3.80 ms 是 X 位点索引 0.55 ms 的 6.9 倍；还有 41% 的多余解码。生产是主存按段 + 位点级空间派生索引。
