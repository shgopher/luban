# 第 71 章 地理位置服务 · 概论

## 一句话

> 地理位置服务只有一个核心问题：**「谁、在什么时候、在哪里」这三个字段怎么存、怎么索引、怎么算、怎么藏**；四节分别回答坐标系、索引、读模型、历史轨迹，每一节的错误都会以「看起来对但差 500 米 / 偶尔漏一批人 / 里程多算一倍」的形式潜伏很久。

## 5 分钟入门：先记住这 8 个词

| 词 | 一句话解释 | 生活类比 |
|---|---|---|
| **坐标系（CRS）** | 同一个地点可以用 WGS84 / GCJ-02 / BD-09 三套坐标描述，彼此差几百米 | 三把刻度不同的尺子量同一个房间 |
| **fix（位置点）** | 一次定位的完整结果：坐标 + 时间 + 精度半径 + 来源 | 收据：金额、时间、商户缺一不可 |
| **地理编码 / 逆地理编码** | 地址 → 坐标 / 坐标 → 地址，两边都是「多解 + 分级精度」 | 查字典是正查，按页码反查词条是逆查 |
| **cell（格子）与层级** | 把地球切成一层套一层的方格，用格子编号代替坐标做索引 | 图书馆先分楼层，再分书架，再分格 |
| **候选放大率** | 索引给出的候选数 ÷ 真正命中的结果数，衡量「白算多少」 | 撒网捞鱼：网越大，捞上来的杂物越多 |
| **圈选半径 r** | 业务要的「附近」范围，必须和格子边长一起算 | 想找 1 公里内的店，得先决定走几个街区 |
| **在线位置槽** | 「谁现在在线、在哪」的实时表，靠心跳续命 | 网吧的座位牌，人走了牌子就失效 |
| **轨迹分段 + 抽稀压缩** | 把一串轨迹点打包成块存，并去掉不影响形状的点 | 把导航录像压成关键帧 |

- 竖看是**一条数据流**：71.1 定坐标系和精度，71.2 定索引，71.3 与 71.4 是同一份 fix 的两种用法（实时读 vs 历史查）。
- 横看是**一个取舍三角**：精度 ↔ 成本 ↔ 隐私。位置越精确，能做的业务越多，存储/查询/泄露风险同时变高，三节各自在一条边上做决定。

## 本章要解决的 8 个真问题

| 问题 | 在哪一节 | 一句话答案 |

## 3 个最常见误解

| 误区 | 现实 |
|---|---|
| 「地理位置服务 = 调地图厂商 API」 | API 只解决地址解析、瓦片、路线；**存储哪套坐标、怎么索引、怎么写放大、怎么脱敏、怎么算钱**全在自己这边，出事故的也全是这些 |
| 「坐标就是一个 `(lng, lat)`」 | 少了三样东西就没法用：**哪套坐标系、什么时间、精度多少米**。同一个坐标配错坐标系差 500 米，配错时间轨迹就乱序 |
| 「上了 Redis GEO 就有地理位置服务了」 | GEO 只解决「按半径查成员」这一件事；在线状态、分片、距离分档、翻页稳定性、轨迹压缩与补传，一件都没解决 |

## 读完自检（入门级 3 题）

**Q1** 一个新系统要同时做「附近的人」和「历史轨迹」，坐标系应该怎么定？

▸ 答案：服务端内部**只存一套**（通常 WGS84），在设备接入边界和展示边界各做一次转换；绝不允许同一张表里混存 GCJ-02 与 WGS84。因为国内展示要用 GCJ-02，而 GPS/北斗原始输出是 WGS84，混存会让 500 米级偏差随机出现，且无法用一条 SQL 修回来（详见 [71.1 地理编码与坐标系统](71.1-地理编码与坐标系统.md)）。

**Q2** 「附近的人」查询慢，加机器有用吗？

▸ 答案：先看慢在哪一段。若是候选放大率太高（格子选得不对，候选数是结果数的几百倍），加机器只是把浪费的算力加倍；正确顺序是**先调层级/圈数把放大率压到个位数，再谈扩容**（见 [71.2 GeoHash 与空间索引](71.2-GeoHash与空间索引.md)）。若慢在距离精算，则要减候选而不是加 CPU。

**Q3** 为什么轨迹「每点一行」在数据量上来后一定出问题？

▸ 答案：单点一行意味着每天 1 亿行，索引与扫描成本随行数线性涨；而轨迹查询几乎总是「按人 + 时间段取一串点」，本质是范围扫描。把它改成**按段打包**（一段几百点）后，扫描行数从百万级降到千级，压缩率也一起上来（见 [71.4 轨迹存储与查询](71.4-轨迹存储与查询.md)）。
