# 60.7 从 SQL 到分析：五种姿势与关联规则

## 一句话

> SQL 是分析的**取数入口**，不是算法本身：库内 ML 把模型塞进 SQL（耦合高、调参难），SQL + Python 把取数与建模分开（默认解）；而关联规则的核心不是 Apriori，是两个可解释指标——**支持度**（这个组合多常见）与**置信度**（买了 A 会不会买 B）。

## 五种姿势：越靠前耦合越高

| 姿势 | 代表 | 怎么做 | 代价 |
|---|---|---|---|
| **库内 BI/ML** | SQL Server Analysis Services | 内置聚类、决策树、朴素贝叶斯、回归 | 绑定单一 DBMS，调参空间小 |
| **库内算法库** | PostgreSQL + Madlib | SQL 调分类/聚类/回归/关联规则 | 要装扩展，算法版本受库限制 |
| **云数仓 ML** | BigQuery ML | `CREATE MODEL` / `ML.PREDICT` | 绑定云厂商，按扫描量计费 |
| **SQL 语法糖调 ML** | SQLFlow | `SELECT ... TRAIN` / `PREDICT` | 工具链重（Docker 镜像 >2G），生态不成熟 |
| **SQL + Python** | pandas + scikit-learn / efficient_apriori | SQL 取数，Python 清洗与建模 | 要多维护一条数据链路 |

> 🔑 默认选第五种：**SQL 负责“取对数据”，Python 负责“算对结果”**。前四种不是不能用，而是把“数据工程 + 算法工程”压进一个系统，换库/调参/排障都会被绑住。

## 关联规则：支持度与置信度

购物篮分析要找“经常一起买”的商品组合。两个指标都必须会算、会说方向：

| 指标 | 定义 | 公式 | 回答 |
|---|---|---|---|
| **支持度** | 组合出现的订单占比 | `包含 A∩B 的订单数 / 总订单数` | 这个组合有多常见 |
| **置信度** | 买了 A 的订单里，也买 B 的比例 | `包含 A∩B 的订单数 / 包含 A 的订单数` | 买了 A 会不会买 B |

5 笔订单的算例：牛奶出现 4 次、牛奶+面包出现 3 次、牛奶+啤酒出现 2 次、啤酒出现 3 次。

```
support(牛奶)        = 4/5 = 0.80
support(牛奶, 面包)  = 3/5 = 0.60
confidence(牛奶→啤酒) = 2/4 = 0.50
confidence(啤酒→牛奶) = 2/3 = 0.67
```

**置信度是有方向的**：`牛奶→啤酒` 与 `啤酒→牛奶` 不是同一个数，报告里必须写清前件/后件。支持度没有方向，`support(A,B)=support(B,A)`。

Apriori 的流程只有三步：

1. 定**最小支持度**与**最小置信度**；
2. 找出支持度 ≥ 阈值的**频繁项集**（先 1 项，再 2 项、3 项；低于阈值的超集直接剪掉）；
3. 在频繁项集上算置信度，留下 ≥ 阈值的**关联规则**。

阈值怎么定：`最小支持度 × 订单数 = 最小出现次数`。2 万笔订单、`min_support=0.02`，意味着组合至少出现 400 次才进入候选；阈值调高会丢长尾规则，调低会组合爆炸。

## 数据预处理：三个脏数据陷阱

课程的面包店数据集有 21,293 笔订单，字段 `Date/Time/Transaction/Item`，三类脏数据都会直接毁掉支持度：

| 脏数据 | 后果 | 处理 |
|---|---|---|
| **同一订单里商品重复** | 按行算支持度会被抬高 | 每笔订单转成 `set`，按**订单**而不是按行算 |
| **`Item = NONE`** | “无商品”变成一个高频商品 | 过滤掉 |
| **大小写不统一**（Coffee/coffee） | 同一商品被拆成两个 | 统一 `LOWER()` |
| **Transaction 缺号** | 不能用“最大 ID − 最小 ID”估订单数 | 用 `COUNT(DISTINCT Transaction)` |

SQL 侧先把“一行一商品”折成“一订单一集合”：

```sql
SELECT Transaction,
       GROUP_CONCAT(DISTINCT LOWER(Item) ORDER BY Item SEPARATOR ',') AS items
FROM bread_basket
WHERE Item IS NOT NULL AND LOWER(Item) <> 'none'
GROUP BY Transaction;
```

Python 侧用 `efficient_apriori`（课程示例，需 `pip install pandas sqlalchemy efficient_apriori`）：

```python
import pandas as pd
import sqlalchemy as sa
from efficient_apriori import apriori

engine = sa.create_engine('mysql+pymysql://root:pass@localhost/wucai')
df = pd.read_sql_query('SELECT Transaction, Item FROM bread_basket', engine)

df['Item'] = df['Item'].str.lower()
df = df[df['Item'] != 'none']

# 每笔订单一个 set；Apriori 按订单算支持度
transactions = list(df.groupby('Transaction')['Item'].agg(lambda x: set(x)))

itemsets, rules = apriori(transactions, min_support=0.02, min_confidence=0.5)
print(len(itemsets[1]), len(itemsets[2]), len(rules))   # 课程数据：19 / 14 / 8
```

> ⚠️ 输出里的 `19/14/8` 是“该数据集 + 该阈值”的结论，不是通用规律；换数据、换阈值都要重算。

## 零售分析还能问什么

关联规则只是零售分析的一类。同一份订单表还能回答：

| 问题 | 指标 | SQL 骨架 |
|---|---|---|
| 哪些客户最近没来？ | RFM 的 Recency | `DATEDIFF(MAX(order_date), CURDATE())` |
| 复购率多少？ | 重复购买客户/总客户 | `GROUP BY user_id HAVING COUNT(*) > 1` |
| 漏斗在哪一步掉？ | 曝光→点击→下单转化率 | 各事件 `COUNT(DISTINCT user_id)` 相除 |
| 哪些商品贡献大头？ | ABC 分类（累计销售额 80%） | 窗口函数 `SUM(amount) OVER (ORDER BY amount DESC)` |

这些指标的口径必须**只定义一次**（[60.2 数仓分层](60.2-数仓分层.md)），否则每个报表各算一遍，数字对不上时无法判断是数据错还是口径错。

## 反模式

| 反模式 | 后果 |
|---|---|
| 把“库内 ML”当默认方案 | 换库/调参/排障都被绑死，团队被工具绑架 |
| 按行算支持度 | 同一订单重复商品把组合频率抬高 |
| 置信度不写方向 | `A→B` 与 `B→A` 混用，结论反过来 |
| 不过滤 `NONE`/空值 | “无商品”成为高频项，规则全是噪声 |
| 最小支持度拍脑袋 | 太高没有规则，太低组合爆炸 |
| 用 SQL 硬写 Apriori | 递归/剪枝难维护，算法库更合适 |
| 报表层各写一套口径 | 同一指标多个版本，无法对账 |

## 自检

**Q1** 2 万笔订单，`support(A,B)=0.03`、`confidence(A→B)=0.6`，说明什么？

▸ 答案：`A` 与 `B` 一起出现约 600 笔（3%）；买 `A` 的订单里 60% 也买了 `B`。但不能反推 `B→A` 也是 0.6——置信度有方向。若 `support(B)` 很高，`B→A` 的置信度可能很低。

**Q2** 为什么同一订单里的重复商品必须先转成 `set`？

▸ 答案：Apriori 的支持度分母是“订单数”，不是“行数”。同一商品在同一订单出现 3 次，按行算会把该组合的出现次数抬高 3 倍，支持度虚高，规则失真。转 `set` 后一笔订单只算一次。

**Q3** 什么时候该用库内 ML，而不是 SQL + Python？

▸ 答案：数据不能出库、延迟要求极低、团队只维护一个 DBMS、模型很简单时，库内 ML 省一条链路；但调参、特征工程、模型版本管理会受库限制。多数分析场景默认 SQL 取数 + Python 建模，库内 ML 作为“不能出库”时的备选。

**Q4** 支持度很高、置信度却很低，说明什么？

▸ 答案：这个组合本身很常见，但“买了 A 再买 B”并不成立——B 可能本来就是高频商品。例如 A、B 各占 50%、组合占 45%，支持度 0.45 很高，但 `confidence(A→B)=0.9` 才叫强；若组合占 10%，`confidence` 只有 0.2。判断关联强度还要看提升度（lift），不能只看支持度。

**Q5** 为什么不直接用 SQL 实现 Apriori？

▸ 答案：Apriori 要逐层生成候选、剪枝、递归求频繁项集，组合数随商品数指数增长；SQL 的集合操作适合“算一次”，不适合“迭代剪枝 + 递归”。SQL 负责取数与预处理，算法交给 Python 库更稳。
