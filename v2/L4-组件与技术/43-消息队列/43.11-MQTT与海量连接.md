# 43.11 MQTT 与海量连接

## 一句话

> MQTT 的难点不在协议在规模：**百万连接靠前置 Proxy 把连接收敛成少量长连接，百万主题靠 Broker 分片**；协议本身只有 QoS 0/1/2、心跳与会话这几件事。

## IoT 的约束决定了协议长什么样

| 约束 | 具体表现 | 对协议的要求 |
|---|---|---|
| 设备极便宜 | 一个水杯几十块，智能模块成本十块封顶，内存按 KB 算，可能没有 CPU/OS | 报文头要短、功能要少、状态尽量放服务端 |
| 网络不稳定是常态 | 无线、移动、随时掉线 | 心跳探测 + 断线重连 + 会话恢复 |
| 在线规模极大 | 车辆、摄像头、家电、穿戴：百万到亿级 | 连接数与主题数必须能水平扩展 |

> 🔑 普通消息队列的客户端跑在服务器上（十万级连接已经很大），MQTT 的客户端跑在设备上（千万级连接起步）——**同一个“发布订阅”模型，规模差三个数量级，架构就完全不同。**

## 协议最小集：QoS、心跳、会话

MQTT 固定头最少 **2 字节**（报文类型 + 剩余长度），功能只有“订阅主题、收发消息”：

| QoS | 语义 | 握手 | 适合 |
|---|---|---|---|
| 0 | 至多一次（可能丢） | PUBLISH 发出即算完 | 高频遥测（温度、位置），丢几条无所谓 |
| 1 | 至少一次（可能重） | PUBLISH → PUBACK | 默认选择，配幂等处理 |
| 2 | 恰好一次 | PUBLISH → PUBREC → PUBREL → PUBCOMP | 极少用：两次往返换“不重”，吞吐与延迟都翻倍 |

两个保命机制：

- **心跳（keepalive）**：客户端周期发 `PINGREQ`，服务端回 `PINGRESP`；超过 1.5 倍 keepalive 没动静就判定掉线。没有心跳，半开连接会一直占着 fd 和内存。
- **会话**：MQTT 3.1.1 用 `clean session` 控制是否保留订阅与未确认消息；MQTT 5 用 `session expiry interval` 给会话设过期时间。**“掉线期间的 QoS1/2 消息要不要补发”完全取决于会话是否保留**——这是业务语义，不是实现细节。

## 与普通消息队列的三处不同

| 维度 | 普通 MQ（Kafka/RocketMQ） | MQTT |
|---|---|---|
| 主题数量 | 几十到几千，是“规划出来的” | 与客户端数量同量级（每设备一个专属主题） |
| 点对点 | 靠消费组 + 指定分区，本质仍是主题 | 协议不支持，用“以客户端 ID 命名的主题 + 订阅它”模拟 |
| 会话状态 | 位点在 broker，连接无状态 | 订阅关系与未确认消息绑在连接/会话上，**动了连接就动了状态** |
| 客户端 | 服务端程序，长连接数万 | 设备，长连接百万+，且随时掉线 |
| 消息堆积 | 主要矛盾（按天保留、可回放） | 次要矛盾（设备只关心最新状态，通常不留历史） |

> ⚠️ 最容易踩的坑：**把 Kafka 直接当 MQTT broker 接百万设备**。Kafka 的元数据（主题/分区/消费者组）在 controller 与 ZooKeeper/KRaft 里，撑不住百万主题；连接数也不是它的设计目标。需要的是“MQTT 接入层 + 后端普通 MQ”的两段式。

## 实测：一条长连接到底占多少

百万连接的说法很常见，先把单条连接的成本量出来。用 Go 起一个最小的 TCP 服务端 + 同进程 4000 条客户端长连接：

```go
package main

import (
	"fmt"
	"net"
	"runtime"
	"sync"
	"time"
)

// 量一量"海量连接"贵在哪：N 条长连接常驻，看 Go 堆/栈增量与建连速率。
// 注：macOS 单进程 fd 上限受 kern.maxfilesperproc 约束（本机 10240），
// 一条连接在建连进程里占 2 个 fd（客户端 + 服务端），所以 N 取 4000。
type mem struct{ heap, stack, sys uint64 }

func snapshot() mem {
	runtime.GC()
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return mem{m.HeapAlloc, m.StackInuse, m.Sys}
}

func main() {
	ln, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		panic(err)
	}
	defer ln.Close()

	var wg sync.WaitGroup
	go func() {
		for {
			c, err := ln.Accept()
			if err != nil {
				return
			}
			wg.Add(1)
			go func() { // 每条连接一个 goroutine + 一个读缓冲，模拟会话
				defer wg.Done()
				buf := make([]byte, 16)
				for {
					if _, err := c.Read(buf); err != nil {
						return
					}
				}
			}()
		}
	}()

	const n = 4000
	before := snapshot()
	start := time.Now()
	conns := make([]net.Conn, 0, n)
	for i := 0; i < n; i++ {
		c, err := net.Dial("tcp", ln.Addr().String())
		if err != nil {
			fmt.Printf("第 %d 条连接失败：%v\n", i, err)
			break
		}
		conns = append(conns, c)
	}
	established := time.Since(start)
	time.Sleep(200 * time.Millisecond) // 等 goroutine 稳定
	after := snapshot()

	k := float64(len(conns))
	fmt.Printf("建立 %d 条 TCP 长连接：耗时 %v，约 %.0f 条/秒\n", len(conns), established.Round(time.Millisecond), k/established.Seconds())
	fmt.Printf("堆：%.1f MB → %.1f MB（每条 %.1f KB）\n", float64(before.heap)/(1<<20), float64(after.heap)/(1<<20), float64(after.heap-before.heap)/1024/k)
	fmt.Printf("栈：%.1f MB → %.1f MB（每条 %.1f KB，一个 goroutine 站桩）\n", float64(before.stack)/(1<<20), float64(after.stack)/(1<<20), float64(after.stack-before.stack)/1024/k)
	fmt.Printf("进程总内存 Sys：%.1f MB → %.1f MB（每条 %.1f KB）\n", float64(before.sys)/(1<<20), float64(after.sys)/(1<<20), float64(after.sys-before.sys)/1024/k)
	fmt.Printf("推算：100 万条连接 ≈ %.1f GB 堆 + %.1f GB 栈\n", 1e6*float64(after.heap-before.heap)/1024/k/(1<<20), 1e6*float64(after.stack-before.stack)/1024/k/(1<<20))
	for _, c := range conns {
		c.Close()
	}
}
```

本机实测（macOS 15.6，Apple M1，Go 1.27.1，回环网络）：

```
建立 4000 条 TCP 长连接：耗时 256ms，约 15605 条/秒
堆：0.2 MB → 4.4 MB（每条 1.1 KB）
栈：0.5 MB → 8.4 MB（每条 2.0 KB，一个 goroutine 站桩）
进程总内存 Sys：12.1 MB → 29.2 MB（每条 4.4 KB）
推算：100 万条连接 ≈ 1.0 GB 堆 + 1.9 GB 栈
```

多次重复的波动：建连速率 1.2–1.6 万条/秒、每条连接 Sys 4.4–4.5 KB，**堆与栈的单连接成本稳定在 1.1 KB / 2.0 KB**（这两项由代码结构决定，不受负载影响）。

读数：

| 指标 | 单连接成本 | 100 万连接 | 含义 |
|---|---|---|---|
| Go 堆 | 1.1 KB | ≈ 1.0 GB | 应用层会话状态要省着花（一个 map 条目就上百字节） |
| Goroutine 栈 | 2.0 KB | ≈ 1.9 GB | “一连接一协程”在百万级就是 GB 级内存 |
| 进程 Total（含内核/GC 余量） | 4.4 KB | ≈ 4.5 GB | 选机器看这个数，不是看堆 |
| 建连速率 | 1.2–1.6 万条/秒 | 1–1.5 分钟建满 | 断线风暴（全城掉电重连）要限速，否则 CPU 先崩 |
| fd | 2/连接（同进程压测） | 200 万 fd | 单机 fd 上限是硬墙，必须靠多节点分摊 |

> 🔑 结论：百万连接的瓶颈**不在 CPU 而在内存与 fd**，每连接 4–5 KB 意味着 100 万连接就要 4–5 GB 常驻内存；再乘上会话状态（订阅树、未确认消息）只会更贵。这就是为什么要把连接“收敛”到 Proxy 层。

## 集群怎么撑住海量连接与海量主题

```
设备 ──► 域名/LB（四层） ──► Proxy 集群（连接 + 会话 + 转发） ──► Broker 小集群（按主题分片）
```

| 组件 | 解决什么 | 关键设计 |
|---|---|---|
| 负载均衡 | 把连接打散到多台 Proxy | 四层 TCP 即可；要 sticky session 时必须支持连接保持 |
| Proxy | 承接百万连接、维护会话、转发消息 | 每 Proxy 与每 Broker 只维持少量连接 → Broker 的连接数不再随设备数增长 |
| 会话存储 | 掉线重连后恢复订阅与未确认消息 | 本地（配 sticky）或外置（Redis/MySQL，Proxy 完全无状态） |
| Broker 分片 | 主题数 × 分区数带来的元数据压力 | 多组小集群，Proxy 按主题名做一致性哈希路由 |

两条会话路线的取舍：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 会话存 Proxy 本地 + sticky session | 延迟低、无外部依赖 | 扩缩容会踢掉一批会话；LB 必须支持会话保持 |
| 会话存外置存储（Redis 等） | Proxy 无状态，随便扩缩容 | 每次连接/重连都要读一次存储，要扛千万级 key |

> 💡 我的判断：**连接少于 50 万时优先“本地会话 + sticky”**（少一跳依赖，故障面小）；超过这个量级，“会话外置 + 无状态 Proxy”更好扩，但要先把 Redis 的容量与热 key 算清楚。

## 选型：十万是一条现实的分界线

| 规模 | 建议 | 理由 |
|---|---|---|
| ≤ 10 万设备 | 开源 broker 单集群（EMQX / Mosquitto / VerneMQ） | 协议实现完整、社区活跃，单集群能扛 |
| 10 万 – 100 万 | 开源 broker + 前置 Proxy 自建，或云厂商 MQTT 服务 | 连接数、主题数、会话存储都要自己设计 |
| > 100 万 | 云厂商 MQTT 服务，或自建多集群 + 单元化 | 运维复杂度超过自研收益 |

> ⚠️ 这条线是工程经验值，不是产品规格：真正的判据是“**单集群的主题数与连接数**是否还在 broker 元数据的舒适区”，以及你的运维能不能扛住“全城设备同时重连”。

## 落地：起一个 broker，跑通 QoS 1

> ⚠️ 本机未安装 Docker/EMQX/Mosquitto，以下命令**未在真实环境验证**；镜像 tag 与端口以官方文档为准。

```bash
# 指名 + 可抄：EMQX 5.x 单节点，1883 是 MQTT 端口，18083 是控制台
docker run -d --name emqx -p 1883:1883 -p 18083:18083 emqx/emqx:5.6

# 可验 1：broker 起来了
docker exec emqx emqx ctl status
# 预期：Node 'emqx@127.0.0.1' is started

# 可验 2：订阅端（另开一个终端）
mosquitto_sub -h localhost -p 1883 -t 'dev/+/temp' -q 1 -v

# 可验 3：发布端，QoS 1
mosquitto_pub -h localhost -p 1883 -t 'dev/1001/temp' -m '{"t":23.5}' -q 1
# 预期：订阅端打印 dev/1001/temp {"t":23.5}

# 可退：停掉并删除容器（数据卷一起删，别留脏状态）
docker rm -f emqx
```

| 检查点 | 通过判据 | 失败常见原因 |
|---|---|---|
| 端口 | `1883` 可连 | 端口被占 / 只映射了 8083(WS) |
| 订阅 | `mosquitto_sub` 无报错且保持连接 | 主题通配符写错（`+` 只能匹配一层） |
| 收发 | 发布后订阅端立刻收到 | QoS 与 retain 语义没对上 |
| 会话 | 断开重连后仍收到离线消息 | `clean session` 为 true，会话没保留 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 所有消息都用 QoS 2 | 四次握手，吞吐减半、延迟翻倍，收益几乎为零 |
| 不设 keepalive 省流量 | 半开连接堆积，fd 与内存被僵尸连接吃光 |
| 主题按“设备 ID + 时间戳”无限膨胀 | 元数据爆炸，订阅树遍历变慢 |
| 会话存本地却用轮询型 LB | 重连落到别的 Proxy，订阅与未确认消息全丢 |
| 把 MQTT 当 RPC（请求-响应）用 | 超时与重试语义混乱，延迟不可控 |
| 报文里塞大 JSON 明文 | 设备流量与电量都被吃掉，弱网下频繁超时 |
| 直接让 Kafka 承接百万设备连接 | 连接数与主题数双爆，集群不可用 |
| 断线重连不限速 | 区域断网恢复瞬间，重连风暴把 Proxy 打挂 |

## 自检

**Q1** 既然 QoS 2 能保证“恰好一次”，为什么生产上很少用？

▸ 答案：QoS 2 用两次往返（PUBREC/PUBREL）换“不重复”，代价是吞吐下降、延迟翻倍，而且端到端仍不闭环——客户端处理完业务后崩溃，重连仍可能重放。工程上更划算的是 **QoS 1 + 业务幂等**（和 [43.6 可靠投递与幂等消费](43.6-可靠投递与幂等消费.md) 同一个结论）：用去重键消灭重复，比让协议替你保证便宜得多。

**Q2** 为什么“主题数量”会成为 MQTT 集群的瓶颈，而普通 MQ 不会？

▸ 答案：普通 MQ 的主题是规划出来的（几十到几千），元数据放内存或 ZooKeeper 都够；MQTT 里“每个设备一个专属主题”是常规做法，主题数与设备数同量级，百万主题意味着订阅树、路由表、元数据都到百万级。所以架构上要做“多组 Broker 小集群 + 按主题哈希分片”，把单个 broker 的主题数压回可接受范围。

**Q3** 实测里 100 万连接约 4.5 GB 内存，这个数字对架构决策意味着什么？

▸ 答案：意味着**连接本身是“内存密集型”资源，不是 CPU 密集型**。所以扩容优先看内存与 fd，而不是核数；也意味着单机放不下百万连接时，正确做法是“多 Proxy 分摊连接 + Broker 只跟 Proxy 建连”，而不是给单机堆内存——后者会把故障域做得更大。

**Q4** 会话放 Proxy 本地还是放 Redis，怎么选？

▸ 答案：看两点：**扩缩容频率**和**重连率**。会话在本地时，Proxy 重启或缩容会踢掉会话，且必须配 sticky session；会话外置时 Proxy 无状态、随便扩，但每次重连都要读一次存储，千万级 key 对 Redis 的容量与热 key 是硬考验。连接数不大、变动少 → 本地 + sticky；规模大、弹性要求高 → 外置。

**Q5** 为什么要在 Broker 前加一层 Proxy，而不是让设备直连 Broker？

▸ 答案：三个原因：① **连接收敛**——百万设备连接变成“Proxy 数 × Broker 数”的少量连接，Broker 的连接数不再随设备数增长；② **会话与协议处理**可以独立扩缩容，不必动存储层；③ **主题分片**可以在 Proxy 层做一致性哈希，把主题数压力分散到多组 Broker。代价是多一跳转发与一层运维。

**Q6** 一个 20 万设备的项目，团队想直接用 Kafka 加个 MQTT 网关自己写，你会怎么劝？

▸ 答案：先算三笔账：**连接**（20 万 × 4.5 KB ≈ 900 MB 常驻，还要 fd）、**主题**（20 万主题对 Kafka 元数据是灾难）、**会话**（掉线补发要自己实现存储与重放）。这三点都不是 Kafka 的设计目标，自己写网关等于重写一个 MQTT broker 的会话层。合理路线是“成熟 MQTT broker 接入 + 后端 Kafka 做数据管道”。

**Q7** 全城断网恢复后，为什么“重连风暴”比“消息积压”更危险？

▸ 答案：积压是存储问题，可以慢慢消化；重连风暴是**瞬时资源问题**：几十万设备在几秒内同时 TCP 握手 + 认证 + 拉会话，CPU、TLS 握手、存储读会被瞬间打满，Proxy 直接不可用。对策是接入层限速（令牌桶）、连接排队、会话懒加载，并预留扩容余量——这也是 [35.7 限流 (漏桶 / 令牌桶 / 滑动窗口 / 自适应)](../../L3-质量属性/35-可用性/35.7-限流.md) 在接入层的直接应用。
