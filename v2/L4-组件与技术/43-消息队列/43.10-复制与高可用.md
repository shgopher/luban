# 43.10 复制与高可用

## 一句话

> 复制只有一个问题：**写几个副本才回 ack**——写 1 个快但可能丢，写多数派不丢且能自动切主，写全部则一挂就写不进；Kafka 的 ISR 与 RocketMQ 的 DLedger 都是这道题的不同答案。

## 先看清那个三角

复制要同时满足三件事，而它们天然打架：

| 目标 | 想达到的效果 | 代价 |
|---|---|---|
| 性能 | 写入尽快返回 | 少等副本 → 少写副本 |
| 可用性 | 挂任意节点还能写 | 少写副本 + 允许降级选主 |
| 一致性 | 不丢、不乱序 | 至少写多数派 + 只从同步副本选主 |

三条铁律，先记住再看实现：

> 🔑 ① **必须“主从”复制**：保证任一时刻至多一个主，才不会写冲突（这是有数学论证的结论，不是习惯）。② **写入副本数越少，可用性越好、越可能丢**。③ **“不丢”和“随便切”不能同时要**：异步复制的窗口里，主挂就是从数据的缺口。

## 副本数的算术：3 副本，写几个？

一主二从、共 3 副本时，三条路：

| 配置 | 客户端拿到 ack 的条件 | 能容忍几个节点挂 | 会不会丢 |
|---|---|---|---|
| 写 1 个（`acks=1`） | 主写本地即返回 | 2 个 | **会**：主挂时未复制的消息没了 |
| 写 2 个（`acks=all` + `min.insync.replicas=2`） | 主 + 至少 1 从确认 | 1 个 | 不会（已 ack 的一定在 2 个节点上） |
| 写 3 个（`acks=all` + `min.insync.replicas=3`） | 3 个全确认 | 0 个（挂 1 个就写不进） | 不会 |

> ⚠️ 注意第三行：**“写全部副本”没有换来额外的一致性，只换来更差的可用性**——因为 2 个副本已经能保证“多数派存活且数据完整”。所以生产配置几乎都是“3 副本 + `acks=all` + `min.insync.replicas=2`”。

## 实测：三种 ack 配置，主挂之后到底丢几条

把“3 副本、主在写满 500 条时宕机”这件事直接推演成表：`acks=k` 表示第 k 个副本确认才算写成功，切主只能从存活副本里选（同步窗口 10 条）：

```go
package main

import "fmt"

// 三副本集群（1 leader + 2 follower）的宕机推演：
// 把"acks 配成几"翻译成"主挂了之后丢几条 / 还能不能写"。
const (
	totalMsgs = 500 // 主节点写满 500 条后宕机
	isrWindow = 10  // follower 落后不超过 10 条时仍算同步副本（ISR），超出则被踢出
)

type cluster struct{ leader, f1, f2 int }

// isr 只返回存活的 follower：leader 已经宕机，不能参与选举
func (c cluster) isr() []int {
	var out []int
	for _, off := range []int{c.f1, c.f2} {
		if c.leader-off <= isrWindow {
			out = append(out, off)
		}
	}
	return out
}

// kthLargest：acks=k 意味着第 k 大的 offset 被确认后才算写成功
func kthLargest(offs []int, k int) int {
	s := append([]int(nil), offs...)
	for i := 1; i < len(s); i++ {
		for j := i; j > 0 && s[j] > s[j-1]; j-- {
			s[j], s[j-1] = s[j-1], s[j]
		}
	}
	return s[k-1]
}

func eval(acks, lag int, unclean bool) (acked, survive, lost int, writable string) {
	c := cluster{leader: totalMsgs, f1: totalMsgs - lag, f2: totalMsgs - lag}
	acked = kthLargest([]int{c.leader, c.f1, c.f2}, acks)

	newLeader := -1
	if isr := c.isr(); len(isr) > 0 { // 优先从 ISR 里选
		newLeader = isr[0]
		for _, off := range isr {
			if off > newLeader {
				newLeader = off
			}
		}
	} else if unclean { // ISR 为空：只有允许 unclean 才能选主（会丢数据）
		newLeader = c.f1
		if c.f2 > newLeader {
			newLeader = c.f2
		}
	}

	writable = "能"
	if acks > 2 { // 故障后只剩 2 个副本，acks=3 永远凑不齐
		writable = "不能（ISR 不足 3）"
	}
	if newLeader < 0 {
		return acked, 0, 0, "不能（分区离线）"
	}
	lost = acked - newLeader
	if lost < 0 {
		lost = 0
	}
	return acked, newLeader, lost, writable
}

func main() {
	for _, sc := range []struct {
		title string
		lag   int
	}{
		{"场景 A：follower 只落后 3 条，仍在 ISR 窗口内", 3},
		{"场景 B：follower 落后 50 条，已被踢出 ISR", 50},
	} {
		fmt.Printf("== %s ==\n", sc.title)
		fmt.Printf("%-26s %-7s %-10s %-10s %s\n", "配置", "已 ack", "切主后剩余", "ack 后丢失", "故障后能否写")
		for _, cfg := range []struct {
			name    string
			acks    int
			unclean bool
		}{
			{"acks=1（主确认即返回）", 1, true},
			{"acks=1（禁用 unclean 选举）", 1, false},
			{"acks=2（min.insync=2）", 2, true},
			{"acks=3（全副本）", 3, true},
		} {
			acked, survive, lost, writable := eval(cfg.acks, sc.lag, cfg.unclean)
			s := fmt.Sprint(survive)
			if survive == 0 {
				s = "—"
			}
			fmt.Printf("%-26s %-7d %-10s %-10d %s\n", cfg.name, acked, s, lost, writable)
		}
		fmt.Println()
	}
}
```

本机实测（macOS 15.6，Apple M1，Go 1.27.1，纯逻辑推演，无真实集群）：

```
== 场景 A：follower 只落后 3 条，仍在 ISR 窗口内 ==
配置                         已 ack   切主后剩余      ack 后丢失    故障后能否写
acks=1（主确认即返回）             500     497        3          能
acks=1（禁用 unclean 选举）      500     497        3          能
acks=2（min.insync=2）       497     497        0          能
acks=3（全副本）                497     497        0          不能（ISR 不足 3）

== 场景 B：follower 落后 50 条，已被踢出 ISR ==
配置                         已 ack   切主后剩余      ack 后丢失    故障后能否写
acks=1（主确认即返回）             500     450        50         能
acks=1（禁用 unclean 选举）      500     —          0          不能（分区离线）
acks=2（min.insync=2）       450     450        0          能
acks=3（全副本）                450     450        0          不能（ISR 不足 3）
```

读数，四条都是故障现场会吵起来的结论：

| 观察 | 数字 | 含义 |
|---|---|---|
| `acks=1` 丢的条数 = follower 落后条数 | 落后 3 条丢 3，落后 50 条丢 50 | **丢多少由网络抖动决定，不由你决定** |
| `acks=2` 两种场景都不丢 | 0 / 0 | 已 ack 的必在 2 个副本上，切主后仍在 |
| `acks=2` 的 ack 数更少 | 497 / 450 vs 500 | 最后几条还没复制就返给客户端“失败/重试”→ 重复而非丢失 |
| `acks=1` + 禁用 unclean，落后 50 条时 | 分区直接离线 | 用“不可用”换“不丢”，这是有意为之的取舍 |

> 🔑 一句话：**“不丢”不是靠“多写副本”，是靠“写够了才 ack + 只从写够的副本里选主”**。少一条都不成立。

## Kafka：ISR 是“写够”的判据

Kafka 把“哪些副本算写够”具象成一个集合：

| 概念 | 含义 | 配错的后果 |
|---|---|---|
| `replication.factor` | 每个分区几副本（通常 3） | =1 时无冗余，节点挂即丢 |
| ISR | 与 leader 保持同步的副本集合，**包含 leader 自己** | ISR 被踢空的瞬间，写入直接报 `NOT_ENOUGH_REPLICAS` |
| `min.insync.replicas` | 写成功至少要几个 ISR（含 leader） | 设 1 等于 `acks=1` 的保护，白配 |
| `acks` | 生产者等几个副本确认 | `all` 与 `min.insync` 必须成对出现才有意义 |
| `unclean.leader.election.enable` | 是否允许非同步副本当主 | 开 true = 用“可能丢数据”换“不停服” |

关键机制：

- **只有 ISR 里的副本能当新 leader**，因为只有它们的 offset 足够新；默认 ISR 全挂则分区不可写（宁可停，不丢）。
- **follower 落后超过 `replica.lag.time.max.ms` 就被踢出 ISR**，之后即使它活着也不能当选。
- 选举由 controller（KRaft 或 ZooKeeper 时代的老路径）执行，切换通常在秒级——**但 leader 挂掉到新 leader 选出的窗口里，该分区不可写**。

## RocketMQ：固定主从与 DLedger 两条路

| 方式 | 写成功条件 | 主挂了怎样 | 适合 |
|---|---|---|---|
| 异步复制 | 主写本地即返回 | 生产者不可写，消费者可切到从节点继续读；**不丢**（数据还在主节点磁盘，恢复后继续同步） | 绝大多数业务 |
| 同步双写 | 主 + 从都写成功 | 同上 | 金融级、不能容忍“恢复前不可写” |
| DLedger（Raft） | 多数派（3 节点写 2） | 自动选举新主，**可继续写**，且只从数据最新的节点选 → 不丢不乱序 | 要求自动切主 + 严格顺序 |

两个必须知道的代价：

1. **传统主从下“严格顺序”和“高可用”只能选一个**：某个队列固定落在一对主从节点上，主挂了其他主节点替代不了它——替代就破坏了“同一队列只被一个节点服务”的顺序前提。
2. **DLedger 3 节点只能挂 1 台**：多数派要 2 票，挂 2 台就凑不齐多数派，剩 1 台活着也不能服务（这是 Raft 的代价，不是实现缺陷）；且选举期间不可写，写延迟也比异步复制高。

> 🔑 所以 RocketMQ 的生产姿势是“多对主从铺开”：一个主题的队列分散到多组主从，单组主挂只影响部分队列——用**水平铺开**换整体可用性，而不是让单组具备自动切主能力。

## 怎么选：一张决策表

| 你的情况 | 配置 | 预期结果 |
|---|---|---|
| 交易/订单，丢一条要赔付 | 3 副本 + `acks=all` + `min.insync=2` + 禁 unclean | 挂 1 台不停写、不丢 |
| 日志/埋点，丢几条可接受 | `acks=1`（或 `acks=0`） | 延迟最低，主挂丢最后一批 |
| 缓存刷新/通知，宁可停不可错 | 3 副本 + 禁 unclean | ISR 不足就停写，等恢复 |
| 必须自动切主且消息有序 | RocketMQ DLedger（3 节点起） | 自动选举，只容忍 1 台故障 |
| 跨机房容灾 | 副本跨机架/可用区打散 | 防的是“整机架掉电”，见 [36.4 两地三中心与多活](../../L3-质量属性/36-灾备/36.4-两地三中心与多活.md) |

## 落地：Kafka 的一致性与一条验证

> ⚠️ 本机未安装 Kafka，以下命令**未在真实集群验证**；参数以对应版本文档为准。

```bash
# 指名 + 可抄：三副本、写全部 ISR、最少 2 个 ISR、禁止非同步副本当选
docker run -d --name kafka -p 9092:9092 \
  -e KAFKA_NODE_ID=1 -e KAFKA_PROCESS_ROLES=broker,controller \
  -e KAFKA_CONTROLLER_QUORUM_VOTERS=1@localhost:9093 \
  -e KAFKA_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093 \
  -e KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092 \
  -e KAFKA_CONTROLLER_LISTENER_NAMES=CONTROLLER \
  -e KAFKA_UNCLEAN_LEADER_ELECTION_ENABLE=false \
  apache/kafka:3.7.0

# 可验：建 3 副本 topic，describe 里每个分区的 Isr 应为 3 个 broker
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3 --replication-factor 3 \
  --config min.insync.replicas=2
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic orders
# 预期输出每行含：Leader: 1  Replicas: 1,2,3  Isr: 1,2,3

# 可验（负向）：在 3 节点集群里停掉 2 个 broker，写入应失败而不是静默丢
# （上面只起了 1 个容器，验证这一步需按同样方式起 3 个 broker，端口 9092/9093/9094）
docker stop kafka-2 kafka-3 2>/dev/null || true
echo "x" | docker exec -i kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic orders --producer-property acks=all
# 预期：NotEnoughReplicasException / NOT_ENOUGH_REPLICAS（ISR 只剩 1 < min.insync=2）

# 可退：把保护降回单副本（仅测试环境），或直接重建集群
docker exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --alter --entity-type topics --entity-name orders --add-config min.insync.replicas=1
```

| 检查点 | 通过判据 | 失败常见原因 |
|---|---|---|
| 副本数 | `Replicas` 长度 = 3 且分布在 3 个 broker | 集群只有 1–2 个 broker |
| ISR 健康 | `Isr` 长度 = 3 且稳定 | follower 追不上（磁盘/网络瓶颈） |
| 保护生效 | 停 2 台后写入报 `NOT_ENOUGH_REPLICAS` | `acks` 没设 `all`，或 `min.insync.replicas=1` |
| 回退 | 改回 1 后写入恢复 | 忘记同步回退 `acks` |

## 反模式

| 反模式 | 后果 |
|---|---|
| `acks=all` 配 `min.insync.replicas=1` | 保护形同虚设，ISR 只剩 leader 也照样 ack |
| 3 副本塞在同一台物理机/同一机架 | 故障域重叠，一次掉电“三副本齐挂” |
| 为“高可用”打开 `unclean.leader.election` | 静默丢数据，且丢了没人报警 |
| 交易消息用 `replication.factor=1` | 节点挂 = 消息永久消失 |
| 以为“主从切换成功”就等于“零丢失” | 异步复制窗口里的消息已经丢了 |
| DLedger 只部署 2 节点图省钱 | 无多数派，选举永远选不出来 |
| 副本数随手设 5 追求“更稳” | 写延迟与存储成本翻倍，可用性没提升（多数派 3 就够） |

## 自检

**Q1** 为什么复制必须“主从”，不能多主同时写同一分区？

▸ 答案：多主写同一分区意味着两个节点各自接受写入并各自生成 offset，冲突时没有仲裁依据，顺序与位点都会分叉。主从把“谁定序”收敛到唯一一个 leader，副本只做跟随，才能既保证顺序又有唯一事实来源。切换时用选举保证“任一时刻至多一个主”，这条件一破，一致性就没法用简单规则维护。

**Q2** `acks=all` 却把 `min.insync.replicas` 设成 1，会发生什么？

▸ 答案：`acks=all` 的含义是“等所有 ISR 确认”，而 ISR 的大小由 `min.insync.replicas` 兜底。设成 1 时，两个 follower 被踢出 ISR 后 ISR 只剩 leader，`acks=all` 就退化成 `acks=1`——主挂即丢，而配置看上去却是“最安全的”。两者必须成对设置才有意义。

**Q3** 实测里 `acks=2` 的 ack 数比 `acks=1` 少，这算丢消息吗？

▸ 答案：不算丢，算“没承诺”。客户端没收到 ack 的那几条会重试，重试成功后仍然入库；如果重试时 broker 已经落盘（只是 ack 丢了），就会产生重复——这正是 at-least-once 的来源（[43.2 投递语义 (at-most / at-least / exactly-once)](43.2-投递语义.md)）。用 ack 换一致性，就必须用幂等消化重复。

**Q4** Kafka 的 ISR 为什么会把 leader 自己算进去？

▸ 答案：因为 `min.insync.replicas` 的语义是“写入成功至少需要几个副本持有这条消息”，而 leader 本身就是持有者之一。3 副本 + `min.insync=2` 意味着“leader + 至少 1 个 follower”，这是能容忍 1 台故障的最小配置；把 leader 排除在外会让算术整体错位。

**Q5** RocketMQ 传统主从“主挂了不丢消息”，为什么还说它牺牲了可用性？

▸ 答案：不丢是因为数据还在主节点磁盘上，等它恢复后继续复制；牺牲的是**写可用性**——主挂期间生产者写不进去（从节点不能自动升主），而且这个队列固定在这组主从，其他主节点替代它会破坏顺序。它用“短暂不可写”换“不丢 + 不乱序”，DLedger 则是用“选举停顿 + 更高写延迟”换“自动切主”。

**Q6** 为什么 3 节点的 DLedger 只能容忍 1 台故障，而不是 2 台？

▸ 答案：Raft 要求多数派（quorum = ⌊n/2⌋+1 = 2）确认才能提交。挂 2 台只剩 1 台，凑不出 2 票，既不能选主也不能提交新日志，服务只能停。要容忍 2 台故障必须 5 节点（quorum=3），代价是写要等 3 个节点确认、存储 5 份。

**Q7** 老板要求“消息一条都不能丢，而且任何一台机器挂了都不能停服”，你怎么回答？

▸ 答案：可以做到，但要付代价并划清边界：3 副本 + `acks=all` + `min.insync=2` + 禁止 unclean 选主，能保证“挂 1 台不丢不停”；挂 2 台会停写（而不是丢数据）。如果要求“挂 2 台也不停”，就得上 5 副本（quorum 3）或跨机房多活，成本与写延迟都会上升。**“不丢”和“随便停”可以同时要，“不丢”和“永远不停”不行**。
