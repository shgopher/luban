# 43.9 存储与索引

## 一句话

> 消息队列的存储只有一条主线：**只追加的日志 + 一层索引**；Kafka 用稀疏索引换空间、RocketMQ 用 20 字节定长稠密索引换寻址速度、Pulsar 把日志搬进 BookKeeper 换无状态 Broker——三者是同一道题的三种取舍。

## 一条主线：只追加

消息队列的每个分区就是一个 **WAL（Write Ahead Log）**：只能尾部追加，不能改、不能随机写。这个约束不是偷懒，是拿性能换来的：

| 访问方式 | 相对成本 | 原因 |
|---|---|---|
| 顺序写 | 基准 | 寻址一次，之后连续写，几乎全是带宽 |
| 随机写 | SSD 慢几倍，机械盘慢几十倍 | 每次都要重新寻址（机械盘还要移磁头） |
| 内存随机读写 | 比磁盘快约 10 万倍量级 | 不用等设备，差在纳秒 vs 微秒/毫秒 |

> 🔑 “只追加”一次性买到三样东西：**写入只碰盘尾**（顺序 IO）、**读取可以按位置批量顺序读**（预读有效）、**天然是 WAL**（崩了按位点重放即可恢复）。

代价也很明确：**不能原地删除单条消息**。所以“消费完删掉”的产品（RabbitMQ）只能靠删除整个队列段来回收空间；而“按时间/大小保留”的产品（Kafka、RocketMQ、Pulsar）才能做到回放历史——保留策略与回放能力是同一件事的两面（[43.8 产品 (Kafka / RocketMQ / RabbitMQ / NATS)](43.8-产品对比.md)）。

## 三种产品，三种形状

| 维度 | Kafka | RocketMQ | Pulsar |
|---|---|---|---|
| 写入单位 | 分区（Partition） | Broker（整个 Broker 一套日志） | Ledger（BookKeeper 的写段） |
| 日志文件 | 每分区多个 segment，写满滚动 | 一个 Broker 一组 CommitLog，**所有主题混写**，单文件固定 1 GiB | Ledger 一次性写入，写满换新 Ledger |
| 索引 | 每 segment 一个 `.index`，**稀疏** | 每队列一个 ConsumeQueue，**定长稠密**，每项 20 B | 元数据在 ZooKeeper，数据在 BookKeeper |
| 寻址 | 二分索引 → 定位 → 顺序扫 | 两次绝对定位（ConsumeQueue → CommitLog） | Broker 向 BookKeeper 读 |
| 天然优势 | 分区级迁移/扩容灵活 | 大量主题时写入批量大、顺序性好 | Broker 无状态，故障转移快 |

> 🔑 一句话记住差别：**Kafka 按分区切段、RocketMQ 全校混写再加一份“目录”、Pulsar 把日志外包**。

## Kafka：按分区切段 + 稀疏索引

每个 partition 目录里是一组大小相同、命名连续的文件对：

```
orders-0/
  00000000000000000000.log     # 消息本体，追加写
  00000000000000000000.index   # 稀疏索引：每 4 KiB 日志一条
  00000000000000000000.timeindex
  00000000000036841728.log     # 文件名 = 这个 segment 的第一条消息 offset
  00000000000036841728.index
```

- 文件名就是 **baseOffset**：要查 offset=40000000 的消息，先按文件名找到它落在哪个 segment。
- `.index` 每项 8 字节（4 字节相对 offset + 4 字节物理位置），默认 `log.index.interval.bytes=4096`，即**每 4 KiB 日志才记一条索引**——这就是“稀疏”。
- 查找 = 索引文件二分 → 拿到不大于目标的最近一条索引 → 从那个物理位置**顺序往后扫**，直到命中。

## RocketMQ：一个 CommitLog + 稠密 ConsumeQueue

RocketMQ 把“写”和“读”拆成两套文件：

```
store/
  commitlog/00000000000000000000   # 所有主题、所有队列混在一起顺序追加，单文件 1 GiB
  consumequeue/orders/3/00000000000000000000  # 每队列一份，定长 20 B/条
```

ConsumeQueue 每项 20 字节 = 8 字节 commitlog 物理偏移 + 4 字节消息长度 + 8 字节 tag hash。因为定长，**队列内第 N 条消息的索引位置直接算得出来**：`N × 20`。于是寻址变成两次绝对定位：

1. 按 `N × 20` 读出索引项（得到 commitlog offset）；
2. 按那个 offset 直接读出消息本体。

| 取舍点 | Kafka 稀疏 | RocketMQ 稠密 |
|---|---|---|
| 索引体积 | 日志的约 1/500（4 KiB 一条 8 B） | 日志的约 1/10（200 B 消息对应 20 B 索引） |
| 单次查找 | 多一次“扫最多一个索引间隔” | 两次定位，无扫描 |
| 大量主题（上千 topic） | 每分区都要独立顺序写，写放大明显 | 全校混写，一次刷盘带多个主题，写性能更好 |
| 大量小消息（几十字节） | 索引占比低，省空间 | 20 B 索引相对小消息占比高，浪费更多盘 |

> ⚠️ 这两条不是“谁更好”，而是“你的负载长什么样”：**主题多、消息大 → RocketMQ 的混写更划算；分区少、消息小、要回放 → Kafka 的稀疏索引更省。**

## 实测：稀疏 vs 稠密，省下的空间与多付的查找

把两种索引都放进内存跑同一批随机查找（1000 万条、200 B/条、200 万次查找），只比索引本身：

```go
package main

import (
	"encoding/binary"
	"fmt"
	"math/rand"
	"sort"
	"time"
)

const (
	nMsgs    = 10_000_000          // 1000 万条消息
	msgSize  = 200                 // 每条 200 字节 → 日志 1.9 GB
	interval = 4096                // Kafka index.interval.bytes
	perEntry = interval / msgSize  // 一条索引覆盖 20 条消息
	lookups  = 2_000_000
)

func main() {
	// 稠密索引：每条消息一项，每项 20 B（RocketMQ ConsumeQueue 的定长项）
	dense := make([]byte, nMsgs*20)
	for i := 0; i < nMsgs; i++ {
		binary.BigEndian.PutUint64(dense[i*20:], uint64(i))
	}
	// 稀疏索引：每 20 条一项，每项 8 B（Kafka index 的相对 offset + position）
	nSparse := nMsgs / perEntry
	sparse := make([]uint64, nSparse)
	for i := range sparse {
		sparse[i] = uint64(i * perEntry)
	}

	r := rand.New(rand.NewSource(42))
	targets := make([]int, lookups)
	for i := range targets {
		targets[i] = r.Intn(nMsgs)
	}

	// 稀疏：二分找到最近索引项，再顺序扫最多 perEntry 条
	start := time.Now()
	scanned := 0
	for _, t := range targets {
		i := sort.Search(nSparse, func(k int) bool { return int(sparse[k]) > t }) - 1
		if i < 0 {
			i = 0
		}
		scanned += t - int(sparse[i]) + 1 // 从索引项扫到目标
	}
	sparseDur := time.Since(start)

	// 稠密：下标直接算，一次定位
	start = time.Now()
	hits := 0
	for _, t := range targets {
		if int(binary.BigEndian.Uint64(dense[t*20:])) == t {
			hits++
		}
	}
	denseDur := time.Since(start)

	fmt.Printf("消息 %d 条 × %d B = 日志 %.1f GB\n", nMsgs, msgSize, float64(nMsgs)*msgSize/(1<<30))
	fmt.Printf("稀疏索引 %d 项 × 8 B = %.1f MB（每 %d 条一个索引项）\n", nSparse, float64(nSparse*8)/(1<<20), perEntry)
	fmt.Printf("稠密索引 %d 项 × 20 B = %.1f MB\n", nMsgs, float64(nMsgs*20)/(1<<20))
	fmt.Printf("\n%d 次随机查找：\n", lookups)
	fmt.Printf("  稀疏 + 顺序扫   %8.1f ns/次   平均扫 %.1f 条消息\n", float64(sparseDur.Nanoseconds())/float64(lookups), float64(scanned)/float64(lookups))
	fmt.Printf("  稠密直接定位   %8.1f ns/次   命中 %d\n", float64(denseDur.Nanoseconds())/float64(lookups), hits)
	fmt.Printf("  索引存储比     %8.1fx\n", float64(nMsgs*20)/float64(nSparse*8))
}
```

本机实测（macOS 15.6，Apple M1，Go 1.27.1，索引全在内存）：

```
消息 10000000 条 × 200 B = 日志 1.9 GB
稀疏索引 500000 项 × 8 B = 3.8 MB（每 20 条一个索引项）
稠密索引 10000000 项 × 20 B = 190.7 MB

2000000 次随机查找：
  稀疏 + 顺序扫      103.6 ns/次   平均扫 10.5 条消息
  稠密直接定位       23.4 ns/次   命中 2000000
  索引存储比         50.0x
```

同一台机器连跑 3 次（隔开后台负载）后取中位数：稀疏 **103.6 ns**、稠密 **12.2 ns**——单次会在 12–23 ns 间波动（差额来自缓存未命中的运气），但“稠密约快 8 倍、稀疏省 50 倍空间”这两个结论稳定。

读数：

| 指标 | 稀疏 | 稠密 | 结论 |
|---|---|---|---|
| 索引体积 | 3.8 MB | 190.7 MB | 稀疏省 **50 倍**空间 |
| 单次查找 | 103.6 ns | 23.4 ns（中位 12.2） | 稠密快 **4–8 倍**（内存态） |
| 额外动作 | 平均多扫 10.5 条 | 无 | 稀疏把成本转给“扫一段日志” |

> ⚠️ 这是**内存态**数字，不等于磁盘延迟。真实场景里两者都要额外 1 次 `pread`：稀疏多付的是“把扫到的那 4 KiB 日志读进页缓存”，命中页缓存时只有几十微秒；**但如果被淘汰，就是一次随机读**。所以“索引省空间”在**小消息 + 海量分区**下最值钱，“索引快”在**大消息 + 高 QPS 点查**下最值钱。

## 消费为什么快：PageCache + 零拷贝

写进磁盘的消息马上就会被消费，[43.1](43.1-消息模型.md) 里“生产与消费都走分区日志”之所以能跑满网卡，靠的是操作系统的两层免费加速：

| 层 | 做什么 | 省掉什么 |
|---|---|---|
| PageCache | 写入先进内核页缓存，攒批刷盘；读取先查页缓存 | 刚写入的消息大概率命中，省一次磁盘读 |
| 零拷贝（`sendfile`） | 数据从页缓存直接进 socket 缓冲区 | 省掉“内核 → 用户态 → 内核”的一次复制与 CPU 参与 |

普通读+发是 3 次复制（磁盘→页缓存→用户缓冲→socket），零拷贝后是 2 次，且后一次由 DMA 完成。**这条优化只在“数据不需要在用户态被加工”时成立**，所以压缩/加密一旦落到 broker 上，零拷贝就废了——这也是为什么 Kafka 坚持“按批压缩、broker 不解压”（见「压缩：按批压、broker 不解压」）。零拷贝本身的主场在 [11.5 零拷贝](../../L0-运行时底座/11-操作系统与内核基础/11.5-零拷贝.md)，这里只记结论：**broker 越少碰消息内容，越能跑满盘和网卡。**

## 压缩：按批压、broker 不解压（实测）

压缩的本质是**用 CPU 换带宽和磁盘**，划不划算只看瓶颈在哪：

`压缩后总时间 = 压缩耗时 + 传输耗时 + 解压耗时`，如果瓶颈是 CPU，压缩只会让系统更慢。

Kafka 的做法是把“一批消息”当成一个压缩单元：Producer 攒批压缩，broker **原样存储、原样发出**，Consumer 解压。好处是 broker 的 CPU 完全不被压缩占用，而带宽和磁盘占用按压缩比下降。

课程里给过一组压测数据（1 KiB 种子消息、客户端多并发异步批量发送）：单节点不压缩接近 **100 万 TPS**（已打满万兆网卡），开启压缩后 **2000 万 TPS**，而实际网络流量只有约 **7 Gb/s**——2000 万 × 1 KiB ≈ 160 Gb/s 的“逻辑带宽”，能塞进 10 Gb/s 的网卡，靠的就是压缩比。

真实业务数据压缩率当然没这么夸张，本机用 10 万条订单 JSON 实测：

```go
package main

import (
	"bytes"
	"compress/flate"
	"compress/gzip"
	"fmt"
	"io"
	"time"
)

// 10 万条订单 JSON（一条约 124 B），模拟真实的“批消息”
func makeBatch(n int) []byte {
	var b bytes.Buffer
	for i := 0; i < n; i++ {
		fmt.Fprintf(&b, `{"orderId":"ORD%08d","userId":"U%06d","sku":"SKU-%04d","qty":%d,"amount":%d.%02d,"ts":1698888888,"region":"cn-hangzhou"}`, i, i%5000, i%200, i%3+1, i%1000, i%100)
		b.WriteByte('\n')
	}
	return b.Bytes()
}

func measure(level int, raw []byte) (size int, enc, dec time.Duration) {
	var buf bytes.Buffer
	start := time.Now()
	w, _ := gzip.NewWriterLevel(&buf, level)
	w.Write(raw)
	w.Close()
	enc = time.Since(start)

	start = time.Now()
	r, _ := gzip.NewReader(bytes.NewReader(buf.Bytes()))
	out, _ := io.ReadAll(r)
	dec = time.Since(start)
	if !bytes.Equal(out, raw) { // 无损：往返必须字节相同
		panic("round-trip mismatch")
	}
	return buf.Len(), enc, dec
}

func main() {
	raw := makeBatch(100_000)
	mb := float64(len(raw)) / (1 << 20)
	fmt.Printf("原始数据 %.1f MB（10 万条订单 JSON，平均 %d B/条）\n\n", mb, len(raw)/100_000)
	fmt.Printf("%-22s %-10s %-12s %-12s %s\n", "模式", "压缩后", "压缩率", "压缩吞吐", "解压吞吐")
	for _, c := range []struct {
		name  string
		level int
	}{
		{"gzip BestSpeed", flate.BestSpeed},
		{"gzip Default", flate.DefaultCompression},
		{"gzip BestCompression", flate.BestCompression},
	} {
		size, enc, dec := measure(c.level, raw)
		fmt.Printf("%-22s %-10s %-12.1f %-12s %s\n", c.name,
			fmt.Sprintf("%.1f MB", float64(size)/(1<<20)),
			float64(len(raw))/float64(size),
			fmt.Sprintf("%.0f MB/s", mb/enc.Seconds()),
			fmt.Sprintf("%.0f MB/s", mb/dec.Seconds()))
	}
}
```

本机实测（同上环境，纯内存压缩，不含网络与磁盘）：

```
原始数据 11.9 MB（10 万条订单 JSON，平均 124 B/条）

模式                     压缩后        压缩率          压缩吞吐         解压吞吐
gzip BestSpeed         1.3 MB     9.3          512 MB/s     493 MB/s
gzip Default           1.0 MB     12.5         360 MB/s     763 MB/s
gzip BestCompression   1.0 MB     12.4         56 MB/s      847 MB/s
```

三次重复的波动范围：BestSpeed 压缩吞吐 512–623 MB/s、Default 360–364 MB/s、BestCompression 56 MB/s（±2%）；**压缩率三次完全一致（9.3 / 12.5 / 12.4）**——说明吞吐受机器负载影响，压缩比只由数据决定。

读数，三条都能直接拿去做决策：

| 现象 | 数字 | 怎么用 |
|---|---|---|
| 业务 JSON 压缩比约 **9–12 倍** | 11.9 MB → 1.0 MB | 带宽/磁盘按 10 倍估算，别按课程那 20 倍 |
| 最慢挡位几乎不提压缩率 | 12.4 vs 12.5，耗时 **6.4 倍**（56 vs 360 MB/s） | 短消息批上“调最高级别”纯亏，选快的不选狠的 |
| 解压比压缩快 | 492–710 MB/s | 消费者多解压一次通常不是瓶颈，瓶颈在业务处理 |

> 🔑 结论：**按批压缩 + 只在客户端压/解**。选择顺序是“先看瓶颈是不是 CPU/网卡”，再选 LZ4/Snappy 一类快算法；算法细节与编码原理见 [44.4 压缩与编码](../44-数据库/44.4-压缩与编码.md)，不在这里展开。

## 落地：两个参数与一条验证命令

> ⚠️ 本机未安装 Kafka/RocketMQ，下面的命令**未在真实集群验证**；参数含义以对应版本文档为准。

```bash
# 指名：Kafka（单节点 KRaft，3.7+ 不需要 ZooKeeper），存储相关参数写在 server.properties
# 可抄：段大小 1 GiB、每 4 KiB 记一条索引（默认值，明确写出来便于评审）
cat >> /opt/kafka/config/kraft/server.properties <<'EOF'
log.segment.bytes=1073741824
log.index.interval.bytes=4096
log.retention.hours=168
EOF

# 可验：建 topic 写 3 条，再看 segment 与索引是否成对出现
/opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic seg-demo --partitions 1 --replication-factor 1
seq 1 3 | /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic seg-demo
ls -l /var/lib/kafka/data/seg-demo-0/
# 预期：00000000000000000000.log 与 00000000000000000000.index 成对出现，index 远小于 log

# 可验（索引自检）：直接读索引文件，检查 offset 单调、位置在文件范围内
/opt/kafka/bin/kafka-dump-log.sh --files /var/lib/kafka/data/seg-demo-0/00000000000000000000.log \
  --index-sanity-check --print-data-log | head

# 可退：段大小/索引间隔改动后回滚到默认，重启该 broker 生效
sed -i.bak '/^log\.segment\.bytes=/d;/^log\.index\.interval\.bytes=/d' \
  /opt/kafka/config/kraft/server.properties
```

| 参数 | 调大 | 调小 | 判断依据 |
|---|---|---|---|
| `log.segment.bytes` | 段少、打开文件少，但删旧数据粒度粗 | 段多、按时间清理更精确，但文件句柄多 | 保留策略是“按时间删”就该小一些 |
| `log.index.interval.bytes` | 索引更小、写更快 | 查找少扫几条 | 点查多（按 offset 精确取）就调小 |

RocketMQ 这一侧没有对应开关：CommitLog 固定 1 GiB、ConsumeQueue 每项固定 20 B，**想改存储形状只能换产品**——这就是“参数可调”与“结构固定”的区别。

## 反模式

| 反模式 | 后果 |
|---|---|
| 把 MQ 当数据库，按 key 频繁查历史消息 | 每次都是随机读 + 扫段，比查库慢一个量级 |
| 用很小的 `log.segment.bytes`（如 64 MiB）跑高吞吐 | 段数暴涨，文件句柄与清理开销吃掉性能 |
| 把 `log.index.interval.bytes` 调到几十 KB 图省空间 | 每次查找多扫几十条，点查延迟明显上升 |
| 在 broker 侧做业务加工（解密/转码/过滤后再存） | 破坏零拷贝与“原样存储”，CPU 与延迟双升 |
| 开启压缩但消费者是 CPU 瓶颈 | 解压把仅剩的 CPU 吃光，端到端反而变慢 |
| 压缩级别一律拉满 | 压缩率几乎不变（12.4 vs 12.5），压缩耗时涨 6 倍（本机实测） |
| 用“消息文件大小”估算磁盘占用 | 忘了多副本 × N 与索引（约 1/10–1/500） |

## 自检

**Q1** 既然顺序写比随机写快几倍到几十倍，为什么消息队列不干脆全放内存？

▸ 答案：内存贵且不持久。1 TiB 内存的成本远高于 1 TiB SSD，而消息队列要按天/周保留海量数据；掉电即丢也违背“持久化”的初衷。正确做法是**顺序写盘 + PageCache 兜住热数据 + 多副本兜住可靠性**：热数据命中页缓存（内存级速度），冷数据落盘（便宜），可靠性交给副本而不是单机内存。

**Q2** Kafka 每 4 KiB 才记一条索引，查找时怎么保证还能找到目标消息？

▸ 答案：三段式：① 按文件名（baseOffset）定位到 segment；② 在 `.index` 里二分找到**不大于目标 offset 的最近索引项**，得到物理位置；③ 从该位置**顺序往后扫**（最多一个索引间隔的数据量）直到命中。所以索引只负责“缩小到一段”，精确命中靠顺序扫——这就是“稀疏”的含义。

**Q3** RocketMQ 的 ConsumeQueue 只有 20 字节，为什么不做成 Kafka 那样的稀疏索引省空间？

▸ 答案：因为 RocketMQ 的 CommitLog 是**所有主题混写**的：同一条队列的消息在 CommitLog 里是分散的，无法靠“从索引位置往后顺序扫”找到下一条。它必须为每条消息记录精确的 commitlog 偏移，才能“跳”过去。代价是索引占日志约 1/10（本机实测 20 B 索引对 200 B 消息），换来的是写入侧大 batch 顺序写和两次绝对定位。

**Q4** 为什么 Kafka 强调“broker 不解压”？

▸ 答案：一旦 broker 解压，就要把数据从页缓存复制到用户态、解压、再写回发送路径，零拷贝失效，CPU 也被压缩算法占走。按批压缩后 broker 只搬字节，压缩/解压成本落在生产者和消费者（可以水平扩展的客户端），broker 保持“哑存储”，这是它能跑满网卡的前提。

**Q5** 本机实测里“最慢挡位压缩率反而更低”，这说明什么？

▸ 答案：说明压缩率不是算法级别的单调函数，而是**由数据本身的重码结构决定**的。这批 JSON 字段高度重复，BestSpeed 已经吃到了主要收益；再往上找更优编码的搜索空间收益极小，却要多花 7.7 倍时间。工程结论：**用真实样本测，不要凭“级别越高越好”直觉配置**。

**Q6** 团队要把 300 个主题塞进一个 3 节点 Kafka 集群，你会提醒什么？

▸ 答案：分区数会随主题数线性膨胀（300 主题 × 12 分区 = 3600 个分区副本），每个分区都要独立顺序写与独立段文件，写入放大和文件句柄都会成为瓶颈。同等负载下 RocketMQ 的“全校混写”更省；若必须用 Kafka，就要控制分区数、合并主题、或按业务拆集群。

**Q7** RocketMQ 的 ConsumeQueue 被误删了，消息还能救回来吗？反过来呢？

▸ 答案：**ConsumeQueue 删了能重建，CommitLog 删了救不回来**。ConsumeQueue 只是“派生索引”，每项记录的是消息在 CommitLog 里的物理偏移与长度，理论上可以把 CommitLog 顺序扫一遍、按主题队列重新生成索引；而 CommitLog 是唯一的事实来源，它一丢，索引里那些偏移就指向空气。这条“日志是源、索引是派生”的关系，和数据库里“WAL 是源、B+ 树是派生”（[44.2 存储引擎：WAL 与崩溃恢复](../44-数据库/44.2-WAL与崩溃恢复.md)）是同一个道理——**备份要备源，不要备派生**。
