# 44.29 临时表、内部临时表与 Memory 引擎

## 一句话

> 临时表拼的是**归属**（`table_def_key` 里带 `server_id + thread_id`，所以能重名、能自动消失），内部临时表拼的是**形态**（`UNION` 去重、`GROUP BY` 累加计数都需要一张二维表），而 Memory 引擎拼的是**存储**——它只该出现在"用户临时表"这一个位置上，普通表用它等于把表锁和重启丢数据一起请进生产。

**来源**：临时表特性与主备复制、内部临时表与 `GROUP BY` 三种算法、Memory 引擎的数据组织与主备案例，来自丁奇《MySQL 实战 45 讲》（极客时间，2019）第 36、37、38 讲；`distinct` 与 `group by` 的等价性来自第 44 讲答疑。本节 SQL 与实测为 MySQL 8.0.46（linux/arm64 的 Docker，RR 隔离，`innodb_page_size=16384`，buffer pool 128M）本机重跑，凡与 5.7 行为不同处均已标注。

## 先把三张"表"分开

三个词天天混着用，但它们描述的是三件不同的事：

| 名字 | 建法 | 数据放哪 | 谁能看见 | 什么时候消失 |
|---|---|---|---|---|
| 普通表 | `create table ...` | InnoDB 落盘 / Memory 在内存 | 所有 session | `drop table` |
| 用户临时表 | `create temporary table ...` | 取决于引擎：InnoDB/MyISAM 落盘，Memory 在内存 | 只有建它的 session | 会话结束（服务端执行 `DROP TEMPORARY TABLE`） |
| 内部临时表 | 优化器自己建，SQL 里看不到 | 先内存，放不下转磁盘 | 只有执行该语句的线程 | 语句结束 |
| 内存表 | `create table ... engine=Memory` | 全在内存 | 所有 session | 数据在重启时清空，**表结构还在** |

> 🔑 临时表说的是"这张表归哪个会话"，内存表说的是"数据放在哪一级存储"。临时表可以用 InnoDB、MyISAM、Memory 任意引擎；反过来，一张 Memory 表是**普通表**，所有人都能看见，也会跟着实例重启丢掉数据——这三件事互相正交，混起来就会得出"临时表就是内存表"这种错结论。

内存表的数据只在内存里，重启清空数据、保留结构；临时表则连"存在"都只属于一个会话。原文第 36 讲把这条边界讲得很干脆：**临时表可以使用各种引擎类型，用 InnoDB 或 MyISAM 时写数据照样落盘**；内存表则是"除了重启清空、结构保留这两个奇怪特性外，就是一张正常的表"。

## 用户临时表：只属于一个 session

`create temporary table` 建出来的表，行为可以压缩成五条：

| # | 特性 | 具体表现 | 本机实测（8.0.46） |
|---|---|---|---|
| 1 | 语法 | `create temporary table ...`，其余 DDL 与普通表一致 | 建表成功，无需先删同名普通表 |
| 2 | 可见性 | 只对创建它的 session 可见，其他线程完全看不到 | 会话 B `show create table t1` 看到普通表，会话 A 看到临时表 |
| 3 | 可重名 | 同一库下可与普通表同名；不同 session 的临时表也可同名 | A 建 `t1` 与普通表 `t1` 并存，B 的 `select count(*)` 仍是 1000 |
| 4 | 遮蔽顺序 | 本会话内有同名临时表和普通表时，`show create` 与增删改查都打到临时表 | A 的 `select * from t1` 返回 1 行 `temp-shadow` |
| 5 | 不显示 | `show tables` 不列出临时表 | A、B 的 `show tables` 都只有 `t1`、`t_big` |

会话 A（`connection_id()=11`）：

```sql
USE d;
CREATE TEMPORARY TABLE t_tmp(id int primary key, note varchar(20)) ENGINE=InnoDB;
CREATE TEMPORARY TABLE t1(id int primary key, a int, b int, note varchar(20)) ENGINE=InnoDB;
INSERT INTO t1(id,a,b,note) VALUES (100,100,100,'temp-shadow');
SHOW CREATE TABLE t1;          -- 带 TEMPORARY 关键字
SELECT * FROM t1;              -- 只有 1 行
SHOW TABLES;                   -- 只有普通表 t1
SELECT table_id, name FROM information_schema.innodb_temp_table_info;
```

"不显示"这件事比想象中更彻底：临时表**连 `information_schema.TABLES` 里都查不到**（本机实测 `visible_in_tables=0`），只有 `information_schema.innodb_temp_table_info` 能看到它（`in_temp_info=1`）。所以任何靠"扫 `information_schema` 盘点表"的工具，都看不见会话里的临时表——包括那些"一键对比主备表结构"的脚本。

### 为什么临时表可以重名

原因不在表名，在**标识**。MySQL 在内存里给每张表维护一个 `table_def_key`：

| 表的类型 | `table_def_key` 的组成 | 结果 |
|---|---|---|
| 普通表 | `库名 + 表名` | 同库建第二个同名表，很快发现 key 已存在，报错 |
| 用户临时表 | `库名 + 表名 + server_id + thread_id` | 不同线程的 key 不同，可以并存 |
| 备库上重放的主库临时表 | `库名 + 表名 + 主库 server_id + 主库 thread_id` | 同一个备库应用线程先后建两个 `t1` 也不冲突 |

磁盘上还有第二重保险。5.6 及更早，临时表的 `.frm` 与 `.ibd` 都放在 `tmpdir`（`select @@tmpdir` 可查）下，文件名前缀是 `#sql{进程 id}_{线程 id}_序列号`；5.7 起引入**临时文件表空间**，临时表的数据不再单独建 `.ibd`。所以同一个 `t1` 在普通表里是 `d/t1.ibd`，在临时表里是另一个物理存在，两者从不互相覆盖。

本机实测到的是下一代的形态：8.0 数据字典化后 `tmpdir`（`/tmp`）下**一个 `#sql*` 文件都没有**，名字规则只保留在服务端的内部表名里，也就是上面那行 `#sql1_b_0`——`1` 是 `server_id`，`b` 是线程 id 的十六进制（本会话 `connection_id()=11`，`0xb=11`），最后一位是同一线程内的序号。这行输出正好把原文那条"文件名前缀含线程 id"的规则，在 8.0 上换了个载体演示出来。

"每个线程维护自己的临时表链表"是可见性规则的实现：会话内操作一张表时，**先遍历链表找同名临时表，找到就优先用它，找不到才落到普通表**；会话结束时，对链表里每张表执行 `DROP TEMPORARY TABLE`。这就是特性 2、3、4 共用一套机制的原因，也是"临时表能自动回收、不需要业务清理"的底气。

### 临时表为什么要写 binlog

一个只在会话内可见的表，为什么它的 `create` 和 `drop` 还要进 binlog？因为这跟 `binlog_format` 有关，而格式决定了备库能不能重放：

| binlog_format | 临时表相关语句 | 备库要做什么 | 结论 |
|---|---|---|---|
| `row` | 不记录 | 不需要临时表，`insert ... select` 记的是每行数据（write_row event） | 最省事 |
| `statement` / `mixed` | 记录 | 必须重放 `create temporary table`，否则后续 `insert into t_normal select * from temp_t` 报"表不存在" | 主库退出时要补一条 `DROP TEMPORARY TABLE` |

`statement` 格式下还有两个细节，都是"为了让备库能执行"：

- 主库线程退出时会自动删临时表，但**备库的同步线程是长期运行的**，不会"退出"。所以主库必须额外把 `DROP TEMPORARY TABLE` 写进 binlog 传给备库，否则备库上的临时表会一直留着。
- `drop table t_normal` 记录 binlog 时会被改写成 `DROP TABLE \`t_normal\` /* generated by server */`。原因是 `drop table` 可以一次删多张表，比如 `drop table t_normal, temp_t`——备库上根本没有 `temp_t`，原样传过去同步线程就停了。`/* generated by server */` 就是"这条命令被服务端改写过了"的标记。
- 主库上两个 session 建了同名临时表 `t1`，两条 `create temporary table t1` 都会传到备库，而备库应用线程可能只有一个（即使开多线程复制，也可能落到同一个 worker）。之所以不冲突，还是靠 `table_def_key`：binlog 里记了主库执行该语句的线程 id，备库据此拼出"库名 + t1 + 主库 server_id + 主库 thread_id"，两个 `t1` 于是成了两张不同的表。

> 💡 选 `binlog_format` 时可以把这条算进去：`row` 下临时表操作根本不进 binlog，`statement` 下则要额外处理 `DROP TEMPORARY TABLE` 和 `drop table` 的改写。副本格式的取舍见 [44.13 主从复制与读写分离](44.13-主从复制与读写分离.md)。

本机把两种格式都跑了一遍。`binlog_format=ROW`（8.0 默认）时，`create temporary table` / `insert` / `drop temporary table` 三条执行完后，binlog 里**一个事件都没多**（`SHOW BINLOG EVENTS` 只有 `Format_desc` 与 `Previous_gtids` 两行）。切到 `STATEMENT` 后重做同一套动作，事件立刻出现：

```text
| binlog.000003 |  448 | Query | 1 |  567 | use `d`; CREATE TEMPORARY TABLE temp_t LIKE t_normal_binlog |
| binlog.000003 |  722 | Query | 1 |  824 | use `d`; INSERT INTO temp_t VALUES (1,1)                       |
| binlog.000003 | 1056 | Query | 1 | 1175 | use `d`; INSERT INTO t_normal_binlog SELECT * FROM temp_t     |
| binlog.000003 | 1283 | Query | 1 | 1409 | use `d`; DROP TEMPORARY TABLE `temp_t` /* generated by server */ |
| binlog.000003 | 1486 | Query | 1 | 1620 | use `d`; DROP TABLE `t_normal_binlog` /* generated by server */ /* xid=3081 */ |
```

五条语句里有三条值得记住：`CREATE TEMPORARY TABLE` 必须传给备库（否则后面的 `INSERT ... SELECT` 找不到表）；`DROP TEMPORARY TABLE` 带 `/* generated by server */`（主库线程退出时补写的，备库没有"退出"这个动作）；`DROP TABLE` 也被改写成带注释的形态（`drop table` 可能一次删多张表，其中包括备库没有的临时表）。

### 改名：`alter table` 行，`rename table` 不行

原文留过一个思考题：为什么临时表能用 `alter table ... rename` 改名，却不能用 `rename table`？答案是**两者找文件的方式不同**：`rename table` 按"库名/表名.frm"的规则去磁盘上找文件，而临时表的 `.frm` 放在 `tmpdir` 下、名字是 `#sql{进程 id}_{线程 id}_序列号.frm`，按普通表的路径去找必然报"找不到文件名"。`alter table` 走的是另一条路径，不受这条规则约束。

本节实测（`code/02a-temp-table-session-a.sql`）里 `ALTER TABLE t_tmp RENAME TO t_tmp2` 执行成功，`SHOW TABLES` 依旧只列出普通表——改名既没影响普通表，也没让临时表"露出来"。

### 临时表的 DDL 边界

临时表不是"另一张普通表"，它有几条硬边界，写代码时容易撞上：

| 写法 | 结果 | 说明 |
|---|---|---|
| `create temporary table t like normal_t` | 成功，只复制结构不复制数据 | 本节 `02c` 实测，这也是原文 join 优化里 `create temporary table temp_t like t1` 的写法 |
| `create temporary table t as select ...` | 成功，建表并写入查询结果 | 一步完成"建结构 + 灌数"，但会锁源表（见下） |
| `create temporary table t (..., foreign key (pid) references p(id))` | `ERROR 1215 (HY000): Cannot add foreign key constraint` | 临时表不支持外键，跨表约束得自己在应用层保证 |
| `rename table t to t2` | 报"找不到文件名" | 见上一条，`rename` 按普通表的路径找文件 |
| `drop table t`（会话内只有临时表 `t`） | 删掉临时表，不影响同名普通表 | 但语义上应该写 `drop temporary table t`，避免歧义 |

### 用它做什么：复杂查询的中间结果

临时表最典型的用法是**分库分表的跨库查询**：一张逻辑大表 `ht` 按字段 `f` 拆成 1024 个分表、分布在 32 个实例上。带分区键的 `select v from ht where f=N` 能路由到单个分表；不带分区键、还要 `order by ... limit 100` 的语句，就必须到所有分片取数再汇总。两条路：

| 思路 | 做法 | 优点 | 代价 |
|---|---|---|---|
| proxy 内存排序 | 各分片返回结果，在中间层进程里归并排序 | 快，数据不出内存 | 开发量大（`group by`、`join` 都要在中间层重写）；proxy 内存与 CPU 容易成瓶颈 |
| 汇总库临时表 | 建 `temp_ht`，各分片 `select ... limit 100` 插进来，再在汇总实例上排序 | 复用 MySQL 的排序与聚合能力，中间层只搬运数据 | 多一跳网络与一次落表；汇总实例要有余量 |

第二种做法在实践中常常直接把临时表建在 32 个分库中的某一个上——分片计算量本来就不饱和，没必要为一次汇总再养一个实例。具体流程（原文的 `select v from ht where k >= M order by t_modified desc limit 100`）：

1. 在汇总实例上建临时表 `temp_ht`，包含 `v`、`k`、`t_modified` 三个字段；
2. 到每个分库上执行 `select v,k,t_modified from ht_x where k >= M order by t_modified desc limit 100`；
3. 把各分库的结果插入 `temp_ht`；
4. 在汇总实例上执行 `select v from temp_ht order by t_modified desc limit 100`，得到结果。

注意第 2 步的 `limit 100`：每个分片只取自己局部的 top 100，汇总后再取全局 top 100——这个"局部 limit 上推"是跨库查询能跑得动的关键，否则每个分片都要吐全量。分片键选择与跨库查询的完整取舍见 [44.14 分库分表](44.14-分库分表.md)。

临时表适合这个场景，原因就两条，都来自"归属单个会话"：**不同 session 的临时表可以重名**，多个会话同时跑同一套汇总逻辑不必担心建表冲突；**数据不用业务自己清理**，客户端异常断开、数据库异常重启都不会留下中间表。反过来，如果中间结果要跨请求复用、或者要给别人看，临时表就不合适了——它随会话消失，这是特性不是缺陷。

原文给 join 优化的那三行，是临时表最经典的用法：

```sql
create temporary table temp_t like t1;                              -- 只复制结构
alter table temp_t add index(b);                                    -- 给关联列补索引
insert into temp_t select * from t2 where b>=1 and b<=2000;         -- 把"小结果"搬进来
select * from t1 join temp_t on (t1.b=temp_t.b);                    -- 再做有索引的 join
```

把这段搬到第 38 讲，还能再加一层优化：`temp_t` 用 Memory 引擎、`b` 上建 hash 索引。原文的结论是导入数据与执行 join 两步都是内存临时表占优，但没给数字。本机用 5 万行补上（同一台实例、同样结构、同样 `index(b)`）：

| 临时表引擎 | 插入 5 万行耗时（两次运行） | 说明 |
|---|---|---|
| `engine=innodb` | 1.073s / 2.009s | 写会话临时表空间 `temp_N.ibt`，索引是 B+ 树 |
| `engine=memory` | 0.309s / 1.124s | 纯内存，索引是 hash |

快了 2–3.5 倍，具体倍数随机器负载漂，但方向稳定。2000 行的规模下差距不会这么明显，但方向一致：**临时表是自己建的、数据量可控，用 Memory 引擎是它唯一没有争议的合法场景**（并发、持久化两个缺陷都被"只属于本会话"抵消了）。

> ⚠️ 用户临时表还有一条容易撞上的限制：**同一张临时表不能在一条语句里被打开两次**。本机实测 `select ... from tt_mem a join tt_mem b on a.b=b.b` 直接报 `ERROR 1137 (HY000): Can't reopen table: 'a'`。需要自连接时只能建两张临时表，或者先把结果落到普通表。

> ⚠️ `insert ... select`（以及 `create temporary table ... as select`）对**源表**是要加锁的：没有索引时锁全表，跑得越久锁得越久。原文第 36 讲的回复里给的建议是"如果不是业务急需，从源表导出来再写到目标表也是好的"——放到本节语境里就是：灌临时表这一步尽量选源表上有索引的读法，或者分批灌，别用一条大 `insert ... select` 去锁住线上表。

> ⚠️ 连接池会把这个特性变成坑：连接不释放（长连接）时，临时表**不会**因为"一次请求结束"而消失。A 客户端建了临时表、用完把连接放回池子，B 客户端复用这条连接就可能看到 A 留下的表，甚至往里面写数据。所以"临时表会自动回收"只保证异常场景不收尾，正常路径上还是应该用完就 `drop temporary table`。

> ⚠️ 还有一个只在运维时才会咬人的副作用：临时表存在期间，**在这个会话里 `show create table t1` 看到的是临时表的结构**，不是线上普通表。有人连上实例核对表结构、发现"字段怎么少了/多了"，八成是上一个用这条连接的人留下了临时表——先 `select count(*) from information_schema.innodb_temp_table_info` 看一眼再下结论。

> 🔑 用户临时表的三条铁律：只在当前会话可见；重名靠 `table_def_key` 里的 `server_id + thread_id`（不是靠改表名）；生命周期绑定会话而非事务——`commit` 不会删它，断开连接才会。

## 内部临时表：`Using temporary` 的真身

用户临时表得自己建；内部临时表是**优化器在语句执行过程中自己建的**，你在 SQL 里看不到它，只能从 `EXPLAIN` 的 `Extra` 里看到 `Using temporary`。

### 什么时候需要一张二维表

原文给的判据不是"语句里有没有 `group by`"，而是**执行过程中需不需要一张能按行查找、能带唯一约束的临时二维表**：

| 语句形态 | 为什么要临时表 | 典型 `Extra` |
|---|---|---|
| `UNION` | 要去重，需要一个带主键/唯一键的地方暂存并判重 | `Using temporary`（在 `UNION RESULT` 行上） |
| `UNION ALL` | 不去重，两个子查询结果直接拼起来发客户端 | 没有 |
| `GROUP BY`，分组字段无有序索引 | 要记"每个分组当前的累计值"，二维表天然能存"分组键 + 计数" | `Using temporary`（可能带 `Using filesort`） |
| `DISTINCT`，去重字段无索引 | 同 `UNION` 的去重语义 | `Using temporary` |
| 派生表 / `IN` 子查询 | 子查询结果要先物化成表才能被外层引用 | `Using temporary` 或物化标记 |
| `ORDER BY` 与 `GROUP BY` 字段不一致 | 分组用一张表，排序再排一次 | `Using temporary; Using filesort` |
| `INSERT ... SELECT` | 读和写是同一张表时要先暂存结果，否则会读到自己刚写的行 | `Using temporary` |

原文把这件事归纳成三句：**能边读边出结果的语句不需要额外内存；`join_buffer` 是无序数组、`sort_buffer` 是有序数组、临时表是二维表结构；一旦执行逻辑需要二维表特性（唯一索引约束、额外字段存累计值），就优先用临时表。**

这三种中间结构的分工值得单列一张表，因为"该调哪个参数"完全取决于语句用的是哪一种：

| 结构 | 形态 | 有序性 | 典型用途 | 调大哪个参数 |
|---|---|---|---|---|
| `join_buffer` | 无序数组 | 无序 | 被驱动表没索引时的 BNL join | `join_buffer_size` |
| `sort_buffer` | 有序数组 | 排完序才有 | `ORDER BY`、`SQL_BIG_RESULT` 的排序 | `sort_buffer_size` |
| 内部临时表 | 二维表 | 看引擎（hash / B+ 树） | `UNION` 去重、`GROUP BY` 分组计数、`DISTINCT` | `tmp_table_size` / `temptable_max_ram` |

`INSERT ... SELECT` 属于"看情况"的一类，本机把两种情况都跑了：

| 写法 | `Extra` | `Created_tmp_tables` | 原因 |
|---|---|---|---|
| `insert into t_ins select ... from t1`（不同表） | 无 | 0 | 可以边读边写，流式插入 |
| `insert into t_ins select ... from t_ins`（同一张表） | `Using temporary` | 1 | 读和写是同一张表，必须先物化结果，否则会读到自己刚写入的行 |

> ⚠️ `UNION ALL` 本身不建临时表，但**外层只要带 `ORDER BY`，`UNION RESULT` 行照样会出现**，`Extra` 变成 `Using temporary; Using filesort`——两条分支的结果要先拼在一起才能整体排序。所以"我用了 `UNION ALL`，所以没有临时表"只在没有外层排序/去重时成立（本机两种写法都验证过，`UNION ALL` 单跑 0 个临时表，加 `ORDER BY` 后 `UNION RESULT` 行出现）。

### `UNION`：临时表就是去重器

原文用的是 1000 行的 `t1`，语句是 `(select 1000 as f) union (select id from t1 order by id desc limit 2)`。执行流程五步：

1. 建一个内存临时表，只有一个整型字段 `f`，且 `f` 是**主键**；
2. 执行第一个子查询，得到 `1000`，插入临时表；
3. 执行第二个子查询，取到第一行 `id=1000`，试图插入——违反主键唯一性，插入失败，跳过；
4. 继续取到 `id=999`，插入成功；
5. 从临时表按行取出数据返回（两行：1000、999），然后删掉临时表。

第 3 步就是"去重"的全部秘密：**`UNION` 的语义靠临时表的主键/唯一键约束实现**，不是靠事后再比较。本机 8.0.46 的 `EXPLAIN` 把这件事写得很直白：

```text
| id | select_type  | table      | type  | key     | rows | Extra                            |
|  1 | PRIMARY      | NULL       | NULL  | NULL    | NULL | No tables used                   |
|  2 | UNION        | t1         | index | PRIMARY |    2 | Backward index scan; Using index |
|  3 | UNION RESULT | <union1,2> | ALL   | NULL    | NULL | Using temporary                  |
```

换成 `UNION ALL`，第三行 `UNION RESULT` **整行消失**，`Extra` 里也没有 `Using temporary`——因为没有去重语义，两个子查询的结果依次发给客户端就够了：

```text
|  1 | PRIMARY | NULL | NULL | NULL | NULL | No tables used                   |
|  2 | UNION   | t1   | index | PRIMARY | 2 | Backward index scan; Using index |
```

计数也能对上（同一会话内 `FLUSH STATUS` 后各跑一次）：

| 语句 | `Created_tmp_tables` | `Created_tmp_disk_tables` | 结论 |
|---|---|---|---|
| `UNION` | 1 | 0 | 建了 1 个内部临时表 |
| `UNION ALL` | 0 | 0 | 一个都没建 |

> 💡 `UNION RESULT` 那一行的 `type=ALL`、`table=<union1,2>` 不是真表，是"临时表扫描"的占位。看到这一行就说明去重发生了；`UNION ALL` 没有这一行，是判断"有没有白建临时表"最快的一眼。

选 `UNION` 还是 `UNION ALL`，看三条：

| 判据 | 选 `UNION` | 选 `UNION ALL` |
|---|---|---|
| 两个分支的结果可能重复 | 必须（去重是语义的一部分） | 不适用 |
| 两个分支条件互斥（如 `status=1` 与 `status=2`） | 浪费一次判重 | 应选 |
| 外层还要 `ORDER BY` / `LIMIT` | 两者都会多一次临时表 + 排序，去重不额外加价 | 仍有排序的代价 |
| 结果集很大（几十万行以上） | 临时表大概率落盘，要评估磁盘 | 优先；若必须去重，考虑在应用层或分片上去 |

### `GROUP BY`：排序后分组，还是顺着索引分组

原文的 `select id%10 as m, count(*) as c from t1 group by m` 在 5.7 上的 `Extra` 有三个标记：`Using index`（覆盖索引，选了索引 `a`，不用回表）、`Using temporary`（用了临时表）、`Using filesort`（要排序）。执行流程：

1. 建内存临时表，两个字段 `m`、`c`，主键是 `m`；
2. 扫索引 `a`，取出每个 `id`，算 `id%10` 记为 `x`；
3. 临时表里没有主键为 `x` 的行，就插 `(x,1)`；有就把该行 `c` 加 1；
4. 遍历完成后按 `m` 排序，把结果返回。

第 4 步能省掉：语句末尾加 `order by null`，就跳过最后排序、直接从临时表取数据返回。这也是原文的第一条使用建议——**对 `GROUP BY` 结果没有排序要求，就加 `order by null`**。

> ⚠️ 8.0 的行为与 5.7 不同，别照抄 5.7 的 `Extra` 去核对：本机 8.0.46 上同一条语句的 `Extra` 只有 `Using index; Using temporary`，**没有 `Using filesort`**；`EXPLAIN FORMAT=TREE` 显示 `Aggregate using temporary table`，说明分组走的是哈希聚合、不再必然排序。根因是 8.0 移除了 `GROUP BY` 的隐式排序（5.7 起就在弃用清单上），所以那次 filesort 本来就不该再有——本机加不加 `order by null`，`Extra` 完全一样，正好印证这一点。加上 `order by null` 之后返回顺序也不保证：实测 `id%10` 那次是 `1..9, 0`（0 在最后），`id%100` 那次是 `0,1,2,...`（0 在第一）。**所以"不加 `order by` 就别依赖返回顺序"在 8.0 上比 5.7 更成立。**

分组键上有索引时，连临时表都不需要（本机 `a` 列有索引）：

```text
EXPLAIN SELECT a, count(*) AS c FROM t1 GROUP BY a;
| type  | key | rows | Extra       |
| index | a   | 1000 | Using index |
```

这里一行 `Using index` 就够了：输入按 `a` 有序，分组退化成顺序累加。

反过来，只要"分组之后还要按聚合结果排序"，临时表和排序会一起出现：

```text
EXPLAIN SELECT b, count(*) AS c FROM t1 GROUP BY b ORDER BY c DESC;
| type | key  | rows | Extra                           |
| ALL  | NULL | 1000 | Using temporary; Using filesort |
```

`b` 无索引 → 建临时表分组；`ORDER BY c` 的 `c` 是聚合结果、临时表里才有的列 → 分组完还得对临时表再排一次。这就是"`ORDER BY` 与 `GROUP BY` 字段不一致"的代价：**不是多扫一遍表，是多排一遍中间结果**。

`GROUP BY` 一共五条实现路径，代价从低到高差一个数量级：

| 实现 | `Extra` 长什么样 | 前提 | 代价 |
|---|---|---|---|
| 顺着索引顺序分组（最优） | 只有 `Using index` | `GROUP BY` 的列上有（或能拼出）有序索引 | 一次顺序扫描，无临时表、无排序 |
| 生成列 + 索引 | 只有 `Using index` | 5.7 起支持 generated column，可给表达式建索引 | 多一列存储 + 索引维护成本 |
| 内存临时表 + 排序 | `Using temporary`（5.7 还带 `Using filesort`） | 分组结果放得进内存临时表 | 建表 + 插入 + 排序 |
| 磁盘临时表 + 排序 | 同上，但落盘 | 分组结果超过内存上限 | 以上全部 + 磁盘 I/O |
| `SQL_BIG_RESULT` 直接排序 | `Using filesort`，**没有** `Using temporary` | 数据量很大、优化器接受 hint | 只用一个 `sort_buffer`（不够则用磁盘临时文件） |

"顺着索引分组"的写法，原文给的是生成列：

```sql
ALTER TABLE t1 ADD COLUMN z int GENERATED ALWAYS AS (id % 100), ADD INDEX(z);
SELECT z, count(*) AS c FROM t1 GROUP BY z;   -- Extra: Using index
```

原理是第 2 步里那句话的反面：**如果扫描过程中数据本身就是有序的，`GROUP BY` 就只需要从左到右顺序累加**——碰到第一个 1 时已经知道累计了 X 个 0，结果集第一行就是 `(0,X)`；碰到第一个 2 时第二行就是 `(1,Y)`，既不需要临时表，也不需要额外排序。索引天然提供这个有序输入。本机实测 `Extra` 只剩 `Using index`，与原文一致。

"直接排序"走的是 `SQL_BIG_RESULT`。原文的动机很实在：明明知道分组数据量特别大，却还要"先放内存临时表、放不下再转磁盘临时表"，绕一圈很傻。加了 hint 之后，优化器认为"磁盘临时表是 B+ 树存储、存储效率不如数组"，干脆用数组：

1. 初始化 `sort_buffer`，放入一个整型字段 `m`；
2. 扫索引 `a`，把 `id%100` 的值依次存入 `sort_buffer`；
3. 扫完后对 `m` 排序（`sort_buffer` 不够就用磁盘临时文件辅助）；
4. 得到一个有序数组，再从中数出不同值及其出现次数。

本机 8.0.46 实测 `Extra` 是 `Using index; Using filesort`，`Using temporary` 确实消失了，与原文结论一致。判断"排序有没有落盘"，5.7 时代读 `optimizer_trace` 的 `filesort_summary.number_of_tmp_files` 即可；本机 8.0.46 实测该字段已不在（`filesort_summary` 里只剩 `memory_available`、`key_size`、`row_size`、`num_rows_found` 等），所以下面改用 `Created_tmp%` 三个计数做判据。

### `distinct` 与 `group by` 什么时候等价

原文第 44 讲的答疑给了一个能直接用的结论：**只需要去重、不需要聚合函数时，`distinct` 和 `group by` 的语义与执行流程相同，性能也相同**。两条语句在字段 `a` 上没有索引时，都是"建一个带唯一索引的临时表 → 遍历表插入（冲突就跳过）→ 把临时表作为结果集返回"。

本机实测（`b` 列无索引）：

```text
EXPLAIN SELECT DISTINCT b FROM t1;              -- Extra: Using temporary
EXPLAIN SELECT b FROM t1 GROUP BY b ORDER BY null;  -- Extra: Using temporary
```

两条 `Extra` 完全一样。差异只在带 `LIMIT` 时出现：`distinct` 可以在凑够行数后提前停，`group by` 则倾向于把分组做完，所以**有 `limit` 时 `distinct` 能提前收工**（原文评论区结论）。

> 🔑 内部临时表不是"写法难看"，而是"执行计划需要一个二维表"。优化的方向只有两个：**让它不需要**（加索引/生成列，让输入有序）、**让它更小**（`order by null`、只取需要的列、`SQL_BIG_RESULT` 换排序算法）。加内存（调 `tmp_table_size`）只是把落盘推迟，不是消除代价。

## 内部临时表什么时候落盘

同一个 `GROUP BY`，可能全程在内存里跑完，也可能落成磁盘临时表、把磁盘写满。判断规则随版本变过两次，这是本节最容易踩错的地方。

原文（5.7 口径）的规则：内存临时表的大小由 `tmp_table_size` 控制，默认 16M；执行过程中发现到达上限，就把内存临时表转成磁盘临时表，**磁盘临时表默认用 InnoDB**（更早的 5.6 默认是 MyISAM）。原话是"如果表的数据量很大，这个查询需要的磁盘临时表就可能占用大量磁盘空间"。

三个版本的规则并列：

| 版本 | 内存临时表用什么引擎 | 内存上限由谁决定 | 磁盘临时表用什么引擎 |
|---|---|---|---|
| 5.6 及更早 | MEMORY（堆表） | `tmp_table_size` 与 `max_heap_table_size` 取较小者 | MyISAM（默认） |
| 5.7 | MEMORY（堆表） | 同上 | InnoDB（`internal_tmp_disk_storage_engine` 控制，默认 `INNODB`） |
| 8.0（本机 8.0.46） | **TempTable**（`internal_tmp_mem_storage_engine` 默认值） | `temptable_max_ram`，默认 1GB；**`tmp_table_size` 不生效** | InnoDB 临时表空间（`ibtmp1`） |

8.0 上这三个旋钮的实测（同一张 10 万行表、5 万个分组，同一个会话内逐组做 `FLUSH STATUS`）：

| 场景 | `internal_tmp_mem_storage_engine` | `tmp_table_size` / `max_heap_table_size` | `Created_tmp_tables` | `Created_tmp_disk_tables` |
|---|---|---|---|---|
| 默认配置 | `TempTable` | 16M / 16M | 1 | **0** |
| 只调小 `tmp_table_size` | `TempTable` | 1024 / 1024 | 1 | **0**（参数根本没被读） |
| 切回 MEMORY 引擎 | `MEMORY` | 1024 / 1024 | 1 | **1**（落盘） |
| MEMORY，给足内存 | `MEMORY` | 32M / 32M | 1 | **0** |

> ⚠️ 在 8.0 上照抄"把 `tmp_table_size` 调到 1M 就能复现落盘"的教程，会得到一个 `Created_tmp_disk_tables=0` 的困惑结果——默认内部临时表是 TempTable，`tmp_table_size` 对它无效。要复现必须先把 `internal_tmp_mem_storage_engine` 切成 `MEMORY`，或者去动 `temptable_max_ram`。

`temptable_max_ram` 这条路也验证过：把它全局调到最小值（2MB，参数本身有下限，写 1MB 会被抬到 2MB）再跑同一条 `GROUP BY`，`Created_tmp_disk_tables` 仍是 0，但 `Created_tmp_files` 从 0 涨到 3。这说明 **TempTable 的"溢出"不是"转成磁盘临时表"，而是内存块溢出到临时文件**；两个计数器口径不同，别拿 `Created_tmp_disk_tables=0` 就当没落盘。另外 `SELECT @@internal_tmp_disk_storage_engine` 在 8.0.46 直接报 `ERROR 1193 (HY000): Unknown system variable`——5.7 的这个开关在 8.0 已被移除。

### 落到哪里去：`tmpdir` 与 `ibtmp1`

"磁盘临时表"落在两个不同的地方，磁盘告警时要分开找：

| 落点 | 由谁决定 | 本机实测 | 内容 |
|---|---|---|---|
| `tmpdir` | `select @@tmpdir` | `/tmp` | 8.0 下不再放临时表的 `.frm`；排序溢出、部分临时文件会落这里 |
| `ibtmp1` | `select @@innodb_temp_data_file_path` | `ibtmp1:12M:autoextend`，文件 12M | InnoDB 磁盘临时表与临时表数据；自动扩展，重启回收 |
| 会话临时表空间 | 每个会话一份 `temp_N.ibt` | `/var/lib/mysql/#innodb_temp/` 下 10 个文件 | 用户临时表（InnoDB 引擎）的数据 |

`ibtmp1` 的 `:12M:autoextend` 是排查磁盘写满时最该先看的一行：一个失控的 `GROUP BY` 或 `ALTER TABLE` 能把它撑到几十 GB，而它**重启后会被回收**——所以"磁盘满了、重启就恢复"的现象，八成是它。临时表撑爆磁盘的处置顺序：

1. `select @@innodb_temp_data_file_path;` 确认是不是 `ibtmp1:autoextend`；
2. 查 `performance_schema.events_statements_summary_by_digest` 里 `SUM_CREATED_TMP_DISK_TABLES` 最高的几条 SQL；
3. 用 `information_schema.processlist` 找到正在跑的那条长查询，评估后 `kill`；
4. 磁盘仍不降：确认无长事务后重启实例，`ibtmp1` 会重建回 12MB；
5. 根治：按上面那张"五条实现路径"给语句加索引或改写，而不是把 `tmp_table_size` 调大。

第 4 步只在紧急时做，第 5 步才是"不再复发"的动作。完整故障处置见 [44.25 MySQL 运维与故障处置](44.25-MySQL运维与故障处置.md)。

另外，"行宽"是内部临时表落盘的最隐蔽推手：`SELECT *` 把宽列（`varchar(200)`、`text`）一起带进临时表，每行可能从 100 字节涨到 800 字节以上（第 5 节 `t_mem20` 与 `t_mem200` 的 102.2 / 823.4 就是同一现象），同样的分组行数会让临时表体积放大约 8 倍、提前跨过内存上限。**只取需要的列，比调大 `tmp_table_size` 更有效**。

### 两个内存参数各管一段

`tmp_table_size` 与 `max_heap_table_size` 名字很像，管的东西不同，混用会得出错误结论：

| 参数 | 管什么 | 本机证据 |
|---|---|---|
| `tmp_table_size` | **内部临时表**的内存上限（且只在 `internal_tmp_mem_storage_engine=MEMORY` 时生效） | 8.0 默认 TempTable 下设成 1024，`Created_tmp_disk_tables` 仍为 0 |
| `max_heap_table_size` | **用户建的 Memory 表**的单表上限；同时与 `tmp_table_size` 一起决定 MEMORY 引擎内部临时表的上限 | 把它设成 1M 后写 1260 行 × 800 字节，报 `The table 't_mem_full' is full` |
| 两者取较小者 | 只发生在"内部临时表且引擎是 MEMORY"这一种组合 | 04.4 那组：1024 / 1024 → 落盘；32M / 32M → 不落盘 |

反向验证也做了：`tmp_table_size` 设成 1024、`max_heap_table_size` 保持默认 16M，往自建的 Memory 表里插 1000 行 × 约 800 字节（`data_length=899,792`，约 880KB），**写入全部成功**。也就是说"把 `tmp_table_size` 调小会导致 Memory 表写不进去"是错觉——它管不到用户表。

三个计数器的分工，是排查"临时表问题"的唯一入口：

| 计数器 | 含义 | 什么时候该警觉 |
|---|---|---|
| `Created_tmp_tables` | 建过多少个内部临时表（内存 + 磁盘） | 单条 SQL 就 +1 以上，说明语句需要二维表 |
| `Created_tmp_disk_tables` | 其中有多少个是**磁盘临时表** | 占比高（比如 > 20%）说明内存不够或行太宽 |
| `Created_tmp_files` | 建过多少个临时文件（含排序溢出、TempTable 溢出） | 涨得比 `disk_tables` 快，说明是溢出而不是磁盘临时表 |

业务侧可直接查的两条：

```sql
SHOW GLOBAL STATUS LIKE 'Created_tmp%';
SHOW SESSION STATUS LIKE 'Created_tmp%';   -- 排查单条语句时用会话级，先 FLUSH STATUS
```

怎么读这三个数：

- **看比值，不看绝对值**：`Created_tmp_disk_tables / Created_tmp_tables` 是落盘比例。这个比值在同一个实例上有稳定基线（本机空跑时是 0，压测分组查询时会跳上去），**突然翻倍**比"数值很大"更值得报警。
- **`Created_tmp_files` 与 `Created_tmp_disk_tables` 的差值**指向两类不同的落盘：差值为正，说明有排序溢出或 TempTable 溢出（不进磁盘临时表计数）；两者同步上涨，才是真的"磁盘临时表"变多。
- **两个计数器都是累计值**：排查单条语句必须先 `FLUSH STATUS`，否则看到的是上次重启以来的总和，永远"很大"。

### 定位到具体 SQL：`performance_schema` 的 digest 表

`SHOW GLOBAL STATUS` 只告诉你"这个实例建了多少临时表"，不告诉你是哪条 SQL。`performance_schema` 按 SQL 指纹聚合，正好补这一刀：

```sql
SELECT DIGEST_TEXT, COUNT_STAR AS exec_count,
       SUM_CREATED_TMP_TABLES AS tmp_tables,
       SUM_CREATED_TMP_DISK_TABLES AS disk_tables,
       SUM_SELECT_SCAN AS full_scans
FROM performance_schema.events_statements_summary_by_digest
WHERE SUM_CREATED_TMP_TABLES > 0 AND SCHEMA_NAME = 'd'
ORDER BY SUM_CREATED_TMP_DISK_TABLES DESC, COUNT_STAR DESC
LIMIT 5;
```

本机输出（跑过几轮 `GROUP BY` 之后）：

```text
| DIGEST_TEXT                                                       | exec_count | tmp_tables | disk_tables | full_scans |
| SELECT `b` , COUNT ( * ) AS `c` FROM `t_big` GROUP BY `b` ...     |          3 |          3 |           1 |          3 |
| SHOW SESSION STATUS LIKE ?                                        |          5 |          5 |           0 |         10 |
| ( SELECT ? AS `f` ) UNION ( SELECT `id` FROM `t1` ... )           |          2 |          2 |           0 |          4 |
```

第一行就是那个"落过盘"的 `GROUP BY`：执行 3 次、建 3 个临时表、其中 1 个是磁盘临时表。把 `SUM_CREATED_TMP_DISK_TABLES > 0` 当过滤条件、按 `SUM_CREATED_TMP_DISK_TABLES` 排序，就是一张"临时表落盘排行榜"。注意 `SHOW SESSION STATUS` 自己也会被统计进去（它内部开了临时表），抓大放小时按 `COUNT_STAR` 与 `disk_tables` 排序即可。

### 落地：四件套

| 项 | 内容 |
|---|---|
| 指名 | MySQL 8.0（本机 8.0.46）；同类参数在 MariaDB / 阿里云 RDS 上名称一致，但 `temptable_max_ram` 需 8.0.2 以上 |
| 可抄 | 见下面两条 SQL：会话级定位、全局级兜底 |
| 可验 | `Created_tmp%` 计数 + `EXPLAIN` 的 `Extra`，两条都要看 |
| 可退 | 会话级设置断开即失效；全局参数用 `SET GLOBAL ... = DEFAULT` 回退，无需重启 |

```sql
-- ① 定位：会话级复现"落盘"，只影响当前连接
SET SESSION internal_tmp_mem_storage_engine = MEMORY;  -- 8.0 默认 TempTable，切回旧行为
SET SESSION tmp_table_size = 1024;                     -- MEMORY 引擎下才生效
SET SESSION max_heap_table_size = 1024;                -- 与上者取较小值
FLUSH STATUS;
SELECT b, count(*) FROM t_big GROUP BY b ORDER BY null;  -- 10 万行 / 5 万分组
SHOW SESSION STATUS LIKE 'Created_tmp%';               -- Created_tmp_disk_tables 应变 1

-- ② 兜底：全局放大内存上限（8.0 默认 TempTable 时改这个才有效）
SET GLOBAL temptable_max_ram = 268435456;              -- 256MB，默认 1GB，按实例内存定
-- 回滚
SET GLOBAL temptable_max_ram = DEFAULT;
```

本机跑出来的验证输出：

```text
-- ① 之后（MEMORY + 1024）
| Created_tmp_disk_tables | 1     |
| Created_tmp_tables      | 1     |

-- 04.5 给足内存后（MEMORY + 32M）
| Created_tmp_disk_tables | 0     |
| Created_tmp_tables      | 1     |
```

> 🔑 排查顺序固定为：先看 `Extra` 有没有 `Using temporary`（有没有二维表）→ 再看 `Created_tmp_disk_tables`（落没落盘）→ 最后才决定调参数还是改 SQL。反过来先调参数，等于给一条本该加索引的语句加内存，问题只是被推迟到数据量更大的那天。

### 版本差异一张表

这几条差异是最容易把老文章照抄错的地方，集中列一遍：

| 项目 | 5.6 | 5.7 | 8.0（本机 8.0.46 实测） |
|---|---|---|---|
| 内部临时表的内存引擎 | MEMORY | MEMORY | TempTable（`internal_tmp_mem_storage_engine`） |
| `tmp_table_size` 对内部临时表 | 生效 | 生效 | 默认**不生效**（TempTable 由 `temptable_max_ram` 管） |
| `GROUP BY` 隐式排序 | 有 | 有（已标记弃用） | 已移除（`Extra` 里不再有那次 `Using filesort`） |
| 磁盘临时表引擎 | 默认 MyISAM | InnoDB（`internal_tmp_disk_storage_engine`） | InnoDB 临时表空间；该变量已移除（查询报 1193） |
| 临时表的磁盘形态 | `.frm` + `.ibd` | `.frm` + 临时表空间 | 数据字典，`tmpdir` 下无 `.frm` |
| 重启后清空内存表写进 binlog 的语句 | `DELETE FROM t` | `DELETE FROM t` | `TRUNCATE TABLE t /* implicitly emptying in-memory table */` |

> 💡 8.0 上 `order by null` 已经不影响计划（因为隐式排序没了），写它只是为了兼容 5.7 或表达意图。**"加 `order by null` 能省一次排序"这句在 8.0 上不成立**，别再把它当性能优化写进新代码。

## 案例：把一条 10 万行的 `GROUP BY` 从临时表改回索引

`t_big` 有 10 万行、`b` 列 5 万个不同值，`select b, count(*) from t_big group by b order by null` 就是最典型的"分组结果装不进小内存临时表"的形态。用 `EXPLAIN ANALYZE`（8.0.18 起可看实际耗时）对比三种计划：

| 计划 | `Extra` | `EXPLAIN ANALYZE` 实际耗时（两次运行） | 临时表 |
|---|---|---|---|
| `b` 无索引 | 无（`Table scan on <temporary>`） | 410ms / 750ms（大头是建表 + 插入） | 1 个内存临时表 |
| 加 `index(b)` | `Using index` | 75ms / 187ms（`Covering index scan`） | 0 |
| 加索引后 `SQL_BIG_RESULT` | `Using index; Using filesort` | 215ms / 228ms（`Sort: t_big.b`） | 0（用 `sort_buffer`） |

改造前：

```text
-> Table scan on <temporary>  (actual time=398..410 rows=50000 loops=1)
    -> Aggregate using temporary table  (actual time=398..398 rows=50000 loops=1)
        -> Table scan on t_big  (cost=10085 rows=100129) (actual time=2.15..94.7 rows=100000 loops=1)
```

一条 `ALTER TABLE t_big ADD INDEX idx_b(b)` 之后：

```text
-> Group aggregate: count(0)  (cost=20098 rows=50220) (actual time=0.336..74.7 rows=50000 loops=1)
    -> Covering index scan on t_big using idx_b  (cost=10085 rows=100129) (actual time=0.312..43.1 rows=100000 loops=1)
```

同一个查询从 410–750ms 降到 75–187ms，**临时表整个消失**。原因就是前面那条原理：`idx_b` 让输入按 `b` 有序，分组退化成"从左到右累加"，既不用建表也不用排序；而且它还是覆盖索引，不用回表。

同样加了索引，硬加 `SQL_BIG_RESULT` 反而慢一点（两次都是 215ms / 228ms，慢于加索引后的 75–187ms）：因为这时排序已经不是瓶颈，多一次 `Sort` 只是白花时间。**hint 是"分组数据量很大且没索引可用"时的兜底，不是通用加速器。**

`SQL_BIG_RESULT` 还有一条边界：它让优化器"先整体排序、再分组"，所以**带 `LIMIT` 的分组查询不该加它**——本来取前 10 组就够了，加了之后要先把几十万行排完。原文的建议顺序也是"数据量实在太大才用这个提示"。

> 🔑 临时表问题的处置顺序，用这个案例可以背下来：先看 `Extra` 有没有 `Using temporary` → 有就找"能不能让输入有序"（加索引 / 生成列索引 / 改写 `group by` 的列顺序）→ 加不了才考虑 `order by null` 与 `SQL_BIG_RESULT` → 最后才是调 `tmp_table_size` / `temptable_max_ram`。前三步改的是"要不要建表"，最后一步只改"表建在哪"。

## Memory 引擎：数据与索引分开放的堆组织表

把同样 10 行数据分别塞进 Memory 表和 InnoDB 表，`select *` 出来的顺序不一样，这件事本身就是理解 Memory 引擎的入口：

```text
+----+------+          +----+------+
| id | c    |          | id | c    |
+----+------+          +----+------+
|  1 |    1 |          |  0 |    0 |
|  2 |    2 |          |  1 |    1 |
| ...       |          | ...       |
|  9 |    9 |          |  9 |    9 |
|  0 |    0 |          +----+------+
+----+------+
   Memory                  InnoDB
```

InnoDB 是**索引组织表**（Index Organized Table）：数据就放在主键 B+ 树上，`select *` 按叶子节点从左到右扫，`0` 自然排在第一行。Memory 是**堆组织表**（Heap Organized Table）：数据部分按数组单独存放，主键索引（hash）里存的是"数据在数组里的位置"，`select *` 走全表扫描 = 顺序扫这个数组，所以最后插入的 `0` 最后被读到。

原文第 37 讲留过一个思考题：两条都带 `order by null` 的 `group by`，为什么用**内存临时表**时结果里 `0` 在最后一行、用**磁盘临时表**时 `0` 在第一行？答案就是上面这两张表的区别——内存临时表是堆组织表，数据按写入顺序放，`0` 是最后插入的；磁盘临时表（5.7 默认 InnoDB）是索引组织表，按主键有序存，`0` 排在最前。这个问题在 5.7 上能稳定复现；8.0 因为内部临时表默认换成 TempTable、且 `group by` 不再隐式排序，**返回顺序本身不再有保证**（本机两次 `order by null` 分别给出 `0` 在最后和 `0` 在第一），所以 8.0 上正确的结论不是"记住 0 在哪"，而是"不加 `order by` 就别依赖顺序"。

两种组织方式带来五条可以拿来判断行为的差异：

| 维度 | InnoDB（索引组织表） | Memory（堆组织表） |
|---|---|---|
| 数据存放 | 数据在聚簇索引叶子上，按主键有序 | 数据在数组里，按写入顺序；索引只存位置 |
| 有空洞时插入 | 为保证有序，只能插到固定位置 | 找到空位就插，位置可复用 |
| 数据位置变化 | 只改主键索引 | 要改**所有**索引里存的位置 |
| 查询开销 | 主键查一次，普通索引查两次（回表） | 所有索引地位相同，都是一次 |
| 行长度 | 支持变长，不同记录长度可不同 | 不支持 `BLOB`/`TEXT`；`varchar(N)` 当 `char(N)` 存，**每行定长** |

"位置可复用"这一条实测得很清楚——删掉 `id=5` 再插 `id=10`，`10` 出现在 `id=4` 后面，正好是 `5` 空出来的位置：

```text
+----+------+
| id | c    |
+----+------+
|  1 |    1 |
|  2 |    2 |
|  3 |    3 |
|  4 |    4 |
| 10 |   10 |   <- 占了 5 的位置
|  6 |    6 |
|  7 |    7 |
|  8 |    8 |
|  9 |    9 |
|  0 |    0 |
+----+------+
```

### 索引：默认 hash，范围查询会退化成全扫

Memory 表的主键是 hash 索引，等值查询 O(1)，范围查询用不上。原文的例子是 `select * from t1 where id<5`：优化器直接给全表扫描。本机实测：

```text
-- 只有 hash 主键
| type | possible_keys | key  | rows | Extra       |
| ALL  | PRIMARY       | NULL |   10 | Using where |

-- 加一个 B-Tree 索引之后
| type  | possible_keys         | key           | rows | Extra       |
| range | PRIMARY,a_btree_index | a_btree_index |    6 | Using where |
```

加上 B-Tree 索引后，`select * from t1 where id<5` 返回 `0,1,2,3,4`（有序）；而 `force index(primary)` 强行走 hash 索引时，返回的是 `1,2,3,4,0`——因为 hash 索引只负责定位，顺序由数组决定。建 B-Tree 索引的写法：

```sql
ALTER TABLE t_mem ADD INDEX a_btree_index USING BTREE (id);
```

> 💡 一条经验：Memory 表上"等值查得多、范围查得少"才配 hash 索引；一旦有范围条件，`using btree` 的索引必须显式建，否则优化器只能全表扫——而全表扫的是内存里的数组，快是快，但 O(n) 的复杂度不会因为你数据在内存里就变成 O(1)。

### 定长存储：`varchar` 当 `char` 用，空间按最坏情况付

`create table ... (s varchar(20)) engine=Memory` 里存 `'ab'`，占的不是 2 字节，而是 `char(20)` 的定长空间。用两张只差列宽的表来量化（各 5000 行，存的都是 `'ab'`）：

| 表 | 列定义 | `TABLE_ROWS` | `DATA_LENGTH` | 每行字节 |
|---|---|---|---|---|
| `t_mem20` | `s varchar(20)` | 5000 | 511,008 | 102.2 |
| `t_mem200` | `s varchar(200)` | 5000 | 4,116,992 | 823.4 |

同样的数据、同样的行数，列宽放大 10 倍，占用放大 8 倍（`823.4 / 102.2 = 8.06`；差额来自行头与对齐）。`utf8mb4` 下 `varchar(20)` 按 80 字节算，加行头约 102 字节，与实测吻合。这两张表同时也说明 Memory 的 `DATA_LENGTH` 与 `INDEX_LENGTH` 是分开统计的（`t_mem20` 是 511,008 / 126,984），与"数据与索引分离"的组织方式一致。

另外三条边界同样是实测出来的：

| 行为 | 实测结果 | 影响 |
|---|---|---|
| `BLOB`/`TEXT` 列 | `ERROR 1163 (42000): The used table type doesn't support BLOB/TEXT columns` | 大字段放不进 Memory 表 |
| 表容量 | `max_heap_table_size=1M` 时写满报 `ERROR 1114 (HY000): The table 't_mem_full' is full`（写入 1260 行 × 800 字节 ≈ 1.0MB 后触发） | 单表上限由参数决定，不是"内存有多大就能存多少" |
| 自增主键 | 删掉 `id=2` 再插一行，拿到 `id=4`，`AUTO_INCREMENT=5` 不回退 | 与 InnoDB 一致；但数据重启即清空，自增值也就失去"连续发号"的意义 |

> 🔑 Memory 表省的不是"读磁盘"，省的是"页管理"：没有 16KB 页、没有 buffer pool、没有 B+ 树，只有数组 + hash。代价是定长行、无事务、表锁、范围查询全扫——这四条里任何一条命中你的业务，Memory 就不是 InnoDB 的替代品。

## Memory 表的两个生产级缺陷

原文的结论是"不建议在生产环境上使用普通内存表"，理由只有两条：**锁粒度**和**数据持久化**。这两条都不是理论风险，都能用一个表、两条 SQL 复现。

### 缺陷一：表锁，一行更新堵住全表

Memory 表不支持行锁，只支持表锁：**一张表只要有更新，就会堵住其他所有在这张表上的读写**。这个表锁跟 MDL 锁不是一回事（MDL 是元数据锁，这里是数据读写锁），但都是表级的。

本机实测的办法：让 A 的 `update` 语句本身跑 5 秒（在 `where` 里塞 `sleep(5)=0`），B 同时更新**另一行**，量 B 等了多久：

```sql
-- A（后台）
UPDATE t_mem SET c=c+1 WHERE id=1 AND sleep(5)=0;   -- 持有表写锁约 5 秒
-- B（同一时刻）
SET @t0 = NOW(6);
UPDATE t_mem SET c=c+1 WHERE id=2;                  -- 不同行，照样要等
SELECT TIMESTAMPDIFF(MICROSECOND, @t0, NOW(6))/1000000 AS memory_wait_seconds;

-- 同样的构造换成 InnoDB 表
UPDATE t_inn SET c=c+1 WHERE id=1 AND sleep(5)=0;
UPDATE t_inn SET c=c+1 WHERE id=2;                  -- 不同行，立即执行
```

真实输出：

```text
+---------------------+
| memory_wait_seconds |
+---------------------+
|              4.0221 |
+---------------------+
+---------------------+
| innodb_wait_seconds |
+---------------------+
|              0.0238 |
+---------------------+
```

另一次运行的同样对照是 `4.7317` 与 `0.0510`。

差了近 170 倍。这不是"Memory 慢"，是**锁粒度决定了并发度**：`id=1` 的更新把 `id=2` 的更新一起挡住了。

> ⚠️ 这里有个容易踩空的细节：Memory 是**非事务引擎**，你不能用"`begin; update; sleep(6); commit`"来制造 6 秒的持锁窗口——语句一结束锁就释放了，B 根本不会等（本节实测：这种写法下 B 的耗时是 0.08 秒）。要复现表锁，必须让 **`update` 语句本身**变慢。

### 缺陷二：重启丢数据，还会把主库的数据一起清掉

数据在内存里，重启就清空——这本身还能接受，毕竟高可用架构下重启是运维动作。真正致命的是它对**复制**的影响。原文给的主备（M-S）序列：

1. 业务正常访问主库；
2. 备库硬件升级，**备库重启**，内存表 `t1` 的内容被清空；
3. 备库重启后，客户端发来一条 `update`，备库应用线程要改 `t1` 的数据行——**报"找不到要更新的行"**，主备同步就此停止。

用 proxy 的架构里，主备切换由系统自己做，客户端的感受就是"网络断开、重连之后内存表的数据没了"。更"诡异"的是双 M 结构：MySQL 知道重启会丢内存表数据，为避免主库重启后主备不一致，**重启后会往 binlog 里写一条清空内存表的语句**；在双 M 结构下，备库 binlog 里这条语句会传到主库，把主库的内存表内容也删掉——现象就是"主库的内存表数据突然被清空"。

这条"重启写 binlog"的行为，本机 8.0.46 直接抓到了（重启容器后看 binlog）：

```text
| binlog.000003 | 234 | Query | 1 | 390 | use `d`; TRUNCATE TABLE `d`.`t_mem` /* generated by server, implicitly emptying in-memory table */ |
```

> ⚠️ 原文（5.7）写的是"往 binlog 里写入一行 `DELETE FROM t1`"，8.0.46 实测已经变成 `TRUNCATE TABLE ... /* generated by server, implicitly emptying in-memory table */`。**语句形态变了，"重启清空内存表并复制出去"这个语义没变**——双 M 下清空主库的风险依旧，5.7 时代的规避方案（备库重启前把表改成 InnoDB、或临时跳过该表的复制）也依旧适用。

同一次重启的对照组很干净：

```text
| mem_rows_before | inn_rows_before |      | mem_rows_after |      | inn_rows_after |
|              11 |              10 |      |              0 |      |             10 |
```

Memory 表 11 行清零、`SHOW CREATE TABLE` 仍是 `ENGINE=MEMORY`（结构在、数据没了）；同库的 InnoDB 表一行不少。

> 🔑 内存表重启丢数据不是"丢缓存"，而是**丢了一份别人也依赖的数据**：备库上丢会让同步线程停摆，双 M 下丢会通过 binlog 反向清空主库。这就是为什么原文把它称为"简直可以当做 bug 来看待"。

已经有一张 Memory 表在线上、又暂时不允许改引擎时，四条规避手段的对比：

| 手段 | 做法 | 代价 | 是否根治 |
|---|---|---|---|
| 重启前改成 InnoDB | `alter table t engine=innodb;` 重启后再改回 `engine=memory` | 表小则秒级；重启窗口内不能有写入 | 一次重启管一次 |
| 跳过该表的复制 | 启动参数加 `skip-slave-errors`，或按 GTID 跳过这条事件 | 会连其它引擎表的不一致一起放过 | 否 |
| 定时持久化 | 定时任务把内存表内容写到同结构 InnoDB 表，启动后回灌 | 有窗口期丢数据；要处理并发覆盖 | 缓解，不根治 |
| 换成 InnoDB | 一次性 `alter table t engine=innodb;` | 读性能靠 buffer pool 兜（小表本来就命中） | 是 |

如果是 DBA，标准的重启前检查只要一条 SQL 就能捞出所有内存表：

```sql
SELECT table_schema, table_name, table_rows, data_length
FROM information_schema.tables
WHERE engine = 'MEMORY' AND table_schema NOT IN ('mysql','sys','performance_schema');
```

> 💡 原文评论区还提到一种"反向持久化"：定时检测内存表，数据非空就写进 InnoDB 镜像表、为空就从镜像表回灌，且这些动作可以不写 binlog。思路可用，但**重启时服务端已经先写了一条清空语句**，回灌动作必须在那之后执行，否则会被自己覆盖——顺序错了比不做更糟。

### Memory 与 InnoDB 怎么选

| 维度 | Memory | InnoDB |
|---|---|---|
| 数据位置 | 全部在内存 | 内存（buffer pool）+ 磁盘 |
| 读写延迟 | 低（无页管理、hash 等值 O(1)） | 命中 buffer pool 时同样低；未命中要读盘 |
| 写并发 | 表锁，写会阻塞全表读写 | 行锁 + MVCC，并发度高 |
| 事务 | 不支持 | 支持 ACID |
| 崩溃/重启 | 数据全丢，结构保留 | 崩溃恢复（redo/undo）后数据在 |
| 范围查询 | hash 索引不支持，需另建 B-Tree | B+ 树天然支持 |
| 大字段 | 不支持 `BLOB`/`TEXT` | 支持 |
| 复制 | 重启清空会打断/污染复制 | 正常复制 |
| 容量上限 | `max_heap_table_size`（默认 16M/表） | 磁盘容量 |

所以"读性能"这条理由站不住：**能放进内存表的数据量都不大，而数据量不大的表，InnoDB 的数据本来就会全部缓存在 buffer pool 里**。读 QPS 高、数据量小的表用 InnoDB，读性能不会差；反过来写多的表，InnoDB 的行锁并发度比 Memory 的表锁好。buffer pool 的命中率与容量规划见 [44.3 缓冲池与页面管理](44.3-缓冲池与页面管理.md)。

这个判断有实测支撑。两张表都只有 10 行（都能完整放进任何缓存），各做 2 万次主键等值查询：

| 引擎 | 2 万次等值查询（两次运行） | 单次平均 | 备注 |
|---|---|---|---|
| Memory | 0.353s / 1.921s | 18–96µs | hash 索引，O(1) |
| InnoDB | 1.278s / 3.416s | 64–171µs | B+ 树，数据在 buffer pool |

Memory 确实占优，但只快 **1.8–3.6 倍**——因为单条查询的时间大头是 SQL 层解析与执行，不是"从内存还是从磁盘取一行"。而一旦并发上来，Memory 的表锁会把这点优势吃回去（上面 4 秒 vs 0.02–0.05 秒的对比就是并发下的真实差距）。**"内存表的读优势"只在单线程微基准里成立，在生产并发下不成立。**

### 什么时候用哪个：决策表

| 你的情况 | 选什么 | 理由 |
|---|---|---|
| 会话内暂存中间结果、用完即弃 | `create temporary table`，引擎按数据量在 InnoDB / Memory 之间选 | 自动回收、可重名，不怕并发冲突 |
| 中间结果在 2000 行以内、且会被反复等值查找 | 用户临时表 + `engine=memory` + hash 索引 | 本节实测插入快 2–3.5 倍，且无并发冲突 |
| 复杂查询的聚合中间结果 | 先想办法加索引（生成列 / 联合索引），让 `GROUP BY` 顺着索引走 | 案例实测 410–750ms → 75–187ms |
| 只读、极小、可重建的维表（如配置映射） | Memory 表可以作为例外，但要接受重启清空 | 数据量小，InnoDB 的 buffer pool 命中率也接近 100% |
| 表要参与事务、要被多会话并写、要能恢复 | InnoDB，不要考虑 Memory | 表锁 + 无事务 + 重启丢数据，三条都致命 |
| 备库上已经有 Memory 表 | 制定重启前检查清单，或直接改引擎 | 重启会让复制线程停摆，双 M 下还会清空主库 |

原文留了一个例外：**用户临时表**可以放心用 Memory 引擎。数据量可控、不会占太多内存时，内存临时表恰好无视了内存表的两个缺陷：

1. 临时表不会被其他线程访问，没有并发问题；
2. 临时表重启后本来就要删除，清空数据不算问题；
3. 备库的临时表也不影响主库的用户线程。

原文在 join 优化里把这个例外量化过：把 InnoDB 临时表换成 Memory 临时表并在 `b` 上建 hash 索引，导入 2000 行数据和后续 join 都比 InnoDB 临时表省时——不写磁盘、hash 查找比 B+ 树省，而 2000 行占用的内存有限。

我的判断（非原文）：Memory 表只在这三种情况下值得保留——**① 会话内的中间结果**（用户临时表，用完即弃）；**② 只读的小维表**（几百到几万行，实例启动时灌入、不接受写入，挂了能从上游重建）；**③ 压测/演示环境的对照组**。除此之外，用 InnoDB 加足够大的 buffer pool，收益更稳、风险更低。

> 🔑 一条可以直接写进建表规范的判据：**`ENGINE=MEMORY` 出现在业务表 DDL 里就驳回**，除非它同时满足"非持久（可重建）+ 只读或单写 + 数据量 < 100MB + 无范围查询"。临时表例外，因为它的生命周期本来就不跨会话。

把本节三块串起来：**临时表解决"归属"**（`table_def_key` 带会话标识，所以能重名、能自动消失）、**内部临时表解决"形态"**（`UNION` 去重与 `GROUP BY` 计数需要二维表）、**Memory 引擎解决"存储"**（数据与索引分离、定长行、表锁）。三者可以任意组合，组合出来的结论只有三条值得记：用户临时表 + Memory 引擎 = 唯一被推荐的 Memory 用法；内部临时表 + TempTable = 8.0 默认，`tmp_table_size` 管不到；普通表 + Memory 引擎 = 本节最不推荐的组合。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用普通 Memory 表存业务数据 | 重启数据清零；备库重启后同步线程报"找不到要更新的行"，主备同步停止 |
| 双 M 架构里保留 Memory 表 | 备库重启时 binlog 里的清空语句传到主库，**主库的数据也被清空**（8.0 记的是 `TRUNCATE ... implicitly emptying in-memory table`） |
| 连接池里建临时表、用完不删 | 连接归还后临时表还在，下一个客户端复用连接就会看到/写进上一个人的表 |
| 用 `begin; update ...; sleep; commit` 去构造 Memory 表锁实验 | 非事务引擎语句结束即释放锁，根本复现不出阻塞，得出的"表锁不生效"结论是错的 |
| 看到 `Using temporary` 就调大 `tmp_table_size` | 8.0 默认内部临时表是 TempTable，这个参数不生效；且加内存只是推迟落盘，代价还在 |
| 在 8.0 上照抄 5.7 的 `Extra` 判断 | 8.0 的 `GROUP BY` 少了 `Using filesort`，按"有没有 filesort"判断优化是否生效会误判 |
| 不加 `order by` 却依赖 `GROUP BY` 的返回顺序 | 8.0 上是哈希聚合，顺序不保证；同一张表换个分组列，`0` 就可能从最后跑到最前 |
| 用 `rename table` 改临时表名 | 报"找不到文件名"——`rename` 按 `库名/表名.frm` 找文件，临时表的 `frm` 在 `tmpdir` 下、名字是 `#sql...` |
| Memory 表上做范围查询却不建 B-Tree 索引 | hash 索引对范围条件无效，优化器退化为全表扫描（`type=ALL`） |
| 给 Memory 表存 `TEXT`、或指望它装下整库 | 直接报 `ERROR 1163`；容量受 `max_heap_table_size` 限制，写满报 `ERROR 1114` |
| 用 `UNION` 代替 `UNION ALL` 而结果本就不重复 | 白建一个带唯一索引的临时表，多一次判重与写表，大结果集上直接多出一次落盘风险 |
| 把 `tmp_table_size` 当成 Memory 表的容量上限 | 用户建的 Memory 表只受 `max_heap_table_size` 限制，调错参数等于白调 |
| 用 `select *` 灌临时表 | 宽列让每行放大数倍，同样的分组行数更早跨过内存上限、提前落盘 |
| 在 8.0 上给 `GROUP BY` 加 `order by null` 期待"省一次排序" | 隐式排序已被移除，`Extra` 与执行计划都不变，只是让读者误以为做了优化 |

## 自检

**Q1** 三个 `t1` 同时存在：会话 A 的临时表 `t1`、会话 B 的临时表 `t1`、普通表 `t1`。它们的 `table_def_key` 分别由什么组成？备库上重放 A、B 两条 `create temporary table t1` 时，为什么不会互相覆盖？

▸ 答案：普通表是`库名 + 表名`；A 的临时表是`库名 + t1 + 本机 server_id + A 的 thread_id`；B 的同理换成 B 的 thread_id。三者在内存里是三个不同的 key，所以能并存——重名不是靠改表名实现的。备库上，binlog 里带着主库执行该语句的线程 id，备库应用线程拼出的是`库名 + t1 + 主库 server_id + 主库 thread_id`；A、B 的 thread_id 不同，两个 key 依然不同。即使多线程复制把两条语句分到同一个 worker，也不会冲突。

**Q2** 同一条 `GROUP BY`，5.7 的 `Extra` 是 `Using index; Using temporary; Using filesort`，8.0.46 只有 `Using index; Using temporary`。是不是 8.0 变快了？怎么验证？

▸ 答案：不一定"变快"，但确实**少了一步排序**：8.0 的分组可以走哈希聚合（`EXPLAIN FORMAT=TREE` 显示 `Aggregate using temporary table`），不再必然对临时表做 filesort，所以 `Using filesort` 消失。验证三步：① 看 `Created_tmp_tables` 有没有增加（临时表还在）；② 看 `EXPLAIN FORMAT=TREE` 是 `Aggregate using temporary table` 还是带排序；③ 比较同一语句在 5.7 与 8.0 上的 `Handler_read_*` 与响应时间。要提醒的是：少了 filesort 不等于没有临时表，`Using temporary` 才是"要不要建表"的判据。

**Q3** 备库重启后，主备同步停在"找不到要更新的行"，业务侧只看到"内存表数据没了"。为什么同步会停？为什么双 M 结构下主库的数据也会消失？

▸ 答案：备库重启清空了 Memory 表的数据（结构和 binlog 位点都还在），应用线程收到一条 `update` 时找不到对应行，复制报错停止。双 M 之所以连主库一起丢，是因为服务端在重启后**主动往 binlog 写一条清空内存表的语句**（8.0.46 实测为 `TRUNCATE TABLE ... /* generated by server, implicitly emptying in-memory table */`）；备库的这条 binlog 会传到主库执行，于是主库的内存表也被清空。规避方式：重启前把表改成 InnoDB、或临时跳过该表的复制（但会放过其他不一致）；根治是把业务表换成 InnoDB。

**Q4** "Memory 表的数据都在内存里，所以读一定比 InnoDB 快"——这句话在什么条件下不成立？给出两个可验证的判据。

▸ 答案：不成立的条件有两个。① **数据量小**：能放进 Memory 表的数据量都不大，而小表的 InnoDB 数据本来就在 buffer pool 里，读路径同样是内存，Memory 没有优势；判据是查 `Innodb_buffer_pool_read_requests` 与 `Innodb_buffer_pool_reads` 的比值，命中率接近 100% 就说明 InnoDB 也在内存里读。② **有范围查询或写并发**：Memory 的 hash 主键不支持范围（`type=ALL`），且写是表锁（本节实测另一行更新等了约 4 秒，InnoDB 0.02–0.05 秒），并发一上来反而更慢。判据是 `EXPLAIN` 的 `type` 与 `performance_schema` 里的锁等待时间。
