                      44.10 事务与隔离级别的实现 (锁 / MVCC)

                      一句话

                      隔离级别的实现只由两件事决定：快照从哪一刻取（事务级还是语句级）与冲突什么时候检测（写时还是提交时）——RC 用语句级快照，RR/SI 用事务级快照，串行化额外检测“读-写”冲突。

                      来源：隔离级别、长事务与回滚段来自丁奇《MySQL 实战 45 讲》（极客时间，2019）第 03 讲；一致性视图、当前读与幻读的推演来自第 08 讲；本节 SQL 与实测为本机 MySQL 8.0.46 补充。

                      ACID 与事务控制：先把边界说清

                      事务是“一次处理的基本单元”：要么全做，要么全不做。ACID 四条不是并列的口号，各自管一段：

                      字母 含义 靠什么实现 一句话定位
                      A 原子性 事务内的操作不可分割 undo log / 回滚 基础
                      C 一致性 事务前后都满足业务约束 约束 + 应用逻辑 约束条件
                      I 隔离性 并发事务互不干扰 锁 + MVCC 手段
                      D 持久性 提交后崩溃不丢 redo log + fsync 目的

                      隔离性是最难的一条：原子性和持久性靠日志就能保证，单机、确定；隔离性要在多个事务同时跑时定义什么叫“正确”，而对账要“停在某一刻”、库存扣减要“看到最新”，两个业务要的正确答案正好相反。数据库给不出统一答案，只能提供级别和两种读，让应用自己选。

                      🔑 原子性是基础，隔离性是手段，一致性是约束条件，持久性是目的。 一致性不是数据库单独保证的：唯一约束、外键、CHECK 能挡一部分，跨表的业务规则仍要靠应用或事务边界。

                      六条控制语句

                      语句 作用 注意
                      START TRANSACTION / BEGIN 显式开启事务 连续 BEGIN 会隐式提交前一个事务（MySQL）
                      COMMIT 提交，修改永久化 提交后不能再回滚
                      ROLLBACK 回滚所有未提交修改 只作用于当前事务
                      SAVEPOINT s1 在事务内打保存点 一个事务可有多个
                      ROLLBACK TO SAVEPOINT s1 回滚到保存点，之前的修改保留 保存点之后的修改撤销
                      RELEASE SAVEPOINT s1 删除保存点 不提交也不回滚

                      autocommit 与 completion_type 决定“事务边界到底在哪”：

                      开关 取值 行为
                      autocommit 1（MySQL 默认） 每条 SQL 自动提交；显式 BEGIN 后仍要 COMMIT/ROLLBACK
                      autocommit 0 必须显式 COMMIT 才生效；Oracle 默认行为
                      completion_type 0（默认） COMMIT 后需重新 BEGIN
                      completion_type 1 COMMIT AND CHAIN：提交后自动开一个同隔离级别的新事务
                      completion_type 2 COMMIT AND RELEASE：提交后断开连接

                      三个本机实测（MySQL 8.0.46）

                      -- ① 连续 BEGIN：第一个事务被隐式提交，ROLLBACK 只回滚第二个
CREATE TABLE tx_test(name VARCHAR(20) PRIMARY KEY) ENGINE=InnoDB;
BEGIN; INSERT INTO tx_test VALUES ('关羽');
BEGIN; INSERT INTO tx_test VALUES ('张飞');
INSERT INTO tx_test VALUES ('张飞');   -- 1062 主键冲突
ROLLBACK;
SELECT * FROM tx_test;                 -- 只剩 关羽

                      -- ② 遇错不自动回滚：第一条张飞仍在事务里，COMMIT 后落库
CREATE TABLE tx_test2(name VARCHAR(20) PRIMARY KEY) ENGINE=InnoDB;
BEGIN; INSERT INTO tx_test2 VALUES ('张飞');
INSERT INTO tx_test2 VALUES ('张飞');   -- 1062，语句失败，事务未回滚
COMMIT;
SELECT * FROM tx_test2;                 -- 张飞

                      -- ③ SAVEPOINT：只撤销保存点之后的修改
CREATE TABLE tx_sp(name VARCHAR(20) PRIMARY KEY) ENGINE=InnoDB;
BEGIN;
INSERT INTO tx_sp VALUES ('a');
SAVEPOINT s1;
INSERT INTO tx_sp VALUES ('b');
ROLLBACK TO SAVEPOINT s1;
INSERT INTO tx_sp VALUES ('c');
COMMIT;
SELECT * FROM tx_sp ORDER BY name;      -- a, c

                      ⚠️ 三条反直觉结论：连续 BEGIN 不是嵌套事务，而是隐式提交前一个；语句报错不等于事务回滚，要不要回滚由你的错误处理决定；BEGIN...END 是存储过程的语句块，不是事务。另外，MySQL 的 DDL 会隐式提交当前事务；MyISAM 不支持事务，ROLLBACK 对它静默无效。

                      完整脚本与真实输出见 tools/examples/44.10-mvcc-lab，bash code/run.sh 会先跑这三条事务控制实验，再跑隔离级别实验。

                      三类异常与四级隔离：两个客户端的最小复现

                      SQL-92 用“能消除哪些异常”定义隔离级别。三类异常的区别不在名字，在变了什么：

                      异常 现象 关键动作 例子
                      脏读 读到别人未提交的数据 对方可能回滚 小张插入“吕布”未提交，小李已查到
                      不可重复读 同一行两次读到的值不同 别人 UPDATE/DELETE 了同一行 张飞被改成张翼德
                      幻读 同一范围两次读到的行数不同 别人 INSERT/DELETE 了范围内的行 3 个英雄变 4 个

                      判别口诀：改同一行 → 不可重复读；范围内多/少行 → 幻读。SELECT 发现记录不存在、INSERT 时却主键冲突，也属于幻读的一种形态（插入时隐式读到了新行）。

                      原文的 A/B 时间线

                      三类异常的定义容易背，难的是在同一条时间线上对上号。表 T(c int) 只有一行 c=1，两个事务按时刻执行：

                      时刻 事务 A 事务 B
                      1 begin
                      2 begin
                      3 update T set c=2（未提交）
                      4 select c → V1
                      5 commit
                      6 select c → V2
                      7 commit
                      8 select c → V3（A 的新事务）

                      同一段操作，四个级别的答案与剩下的异常：

                      隔离级别 V1 V2 V3 三类异常里还剩哪些
                      读未提交 2 2 2 脏读、不可重复读、幻读
                      读已提交 1 2 2 不可重复读、幻读（默认：Oracle、SQL Server）
                      可重复读 1 1 2 标准说幻读；InnoDB 当前读用 next-key 防住（默认：MySQL）
                      串行化 1 1 2 无，吞吐最低

                      ⚠️ 有的版本把 V3 也画在事务 A 内。若 V3 确实在事务内，RR 下它仍然是 1；「V3=2」只能发生在 A 提交之后。判断可重复读有没有生效，看的是同一事务内的 V1 与 V2，不是提交后的那次读。

                      🔑 级别越高，消除的是「看见」而不是「并发」：RC 让每条语句看见最新的已提交世界，RR 让整个事务停在启动那一刻，串行化让冲突的事务排队。三个答案的差别，本质是视图的生命周期。

                      MySQL 把 RR 设为默认是历史选择：binlog_format=STATEMENT 年代，RC 下同一事务的多次读在主库与从库可能落在不同的提交边界上，主从数据会分叉；RR 的事务级视图把这个差异抹平。8.0 默认 ROW 格式后这层约束已弱化，大量互联网业务改成 RC。反方向同样要核对：Oracle 默认 RC，迁到 MySQL 若级别不一致，同一段代码的可见性会变。

                      两个客户端的最小复现

                      -- 两个会话都执行
SHOW VARIABLES LIKE 'transaction_isolation';   -- 8.0；5.6 及更早是 tx_isolation
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SET autocommit = 0;

-- 会话 2：不提交，会话 1 就能读到 → 脏读
BEGIN; INSERT INTO heros_temp VALUES (4, '吕布');

-- 会话 2：改同一行并提交，会话 1 再读不同 → 不可重复读
BEGIN; UPDATE heros_temp SET name='张翼德' WHERE id=1; COMMIT;

-- 会话 2：插入范围内新行，会话 1 再数变多 → 幻读
BEGIN; INSERT INTO heros_temp VALUES (5, '貂蝉'); COMMIT;

                      ⚠️ 这套演示把会话 1 压到 READ UNCOMMITTED，所以会话 2 不提交也能被看见；照抄脚本但不改隔离级别，就复现不出来。MySQL 默认 RR 下，快照读看不到会话 2 的未提交修改。

                      “MySQL RR 能防幻读”要分读法：快照读靠 Read View 看不见新行；当前读（FOR UPDATE、LOCK IN SHARE MODE、DML）靠 next-key 锁挡住插入。标准语义与 InnoDB 实现不是一回事，跨库迁移时按实现核对，不要只看级别名（44.11 锁）。

                      MVCC 的三件套

                      组件 作用 没有它会怎样
                      版本链 每行保留多个版本（commit_ts + 值） 读写互斥，只能靠锁
                      快照 / Read View 读的时候“看见到哪个时刻为止的提交” 读到未提交或读到未来
                      冲突检测 / 回滚 提交时发现“我写的东西被别人改过” 丢失更新、写偏斜

                      行上真实存在三个隐藏列，理解版本链必须知道它们：

                      隐藏列 作用
                      DB_ROW_ID 建表没指定主键时，InnoDB 用它生成默认聚簇索引
                      DB_TRX_ID 最后一个插入/更新该行的事务 ID
                      DB_ROLL_PTR 回滚指针，指向 undo log 里的旧版本；版本链就是沿它走

                      💡 不同 MySQL 版本的文档对隐藏列的命名略有差异，但职责固定：行 ID、最后修改事务、undo 指针。Read View 不是“把数据复制一份”，而是“拿行上的 DB_TRX_ID 和一组事务 ID 比较，决定这个版本可不可见”。

                      package main

import (
	"fmt"
	"sort"
	"sync"
)

type ver struct {
	commitTS int64
	val      string
}

type store struct {
	mu   sync.Mutex
	data map[string][]ver
	ts   int64
}

func newStore() *store { return &store{data: map[string][]ver{}} }

// 在 ts 时刻提交一个版本
func (s *store) commitAt(writes map[string]string) int64 {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.ts++
	for k, v := range writes {
		s.data[k] = append(s.data[k], ver{s.ts, v})
	}
	return s.ts
}

// 快照读：只看 commitTS <= snapshot 的最新版本
func (s *store) readAt(k string, snapshot int64) (string, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	vs := s.data[k]
	for i := len(vs) - 1; i >= 0; i-- {
		if vs[i].commitTS <= snapshot {
			return vs[i].val, true
		}
	}
	return "", false
}

// 快照隔离下的提交：写-写冲突检测（first-committer-wins）
func (s *store) commitSI(snapshot int64, writes map[string]string) (int64, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	for k := range writes {
		for _, v := range s.data[k] {
			if v.commitTS > snapshot {
				return 0, false // 我快照之后有人改过这个 key
			}
		}
	}
	s.ts++
	for k, v := range writes {
		s.data[k] = append(s.data[k], ver{s.ts, v})
	}
	return s.ts, true
}

func main() {
	// ---------- ① 不可重复读：RR 用事务快照，RC 用语句快照 ----------
	s := newStore()
	s.commitAt(map[string]string{"x": "v1"})
	rrSnapshot := s.ts // T1 开始（RR：整个事务用这个快照）
	s.commitAt(map[string]string{"x": "v2"}) // T2 改了并提交
	rr, _ := s.readAt("x", rrSnapshot)
	rc, _ := s.readAt("x", s.ts) // RC：每条语句取“当前已提交”
	fmt.Printf("① 不可重复读   RR 读到 %s，RC 读到 %s（数据库实际是 v2）\n", rr, rc)

	// ---------- ② 幻读：快照读看不到新插入的行 ----------
	s2 := newStore()
	s2.commitAt(map[string]string{"user:1": "a"})
	snap := s2.ts
	s2.commitAt(map[string]string{"user:2": "b"}) // 别的事务插入
	var oldKeys, newKeys []string
	for k := range s2.data {
		if v, ok := s2.readAt(k, snap); ok && v != "" {
			oldKeys = append(oldKeys, k)
		}
		if _, ok := s2.readAt(k, s2.ts); ok {
			newKeys = append(newKeys, k)
		}
	}
	sort.Strings(oldKeys)
	sort.Strings(newKeys)
	fmt.Printf("② 幻读（快照隔离）旧快照看到 %v，当前能看到 %v\n", oldKeys, newKeys)

	// ---------- ③ 写偏斜：两个事务各读各写，SI 不检测 ----------
	s3 := newStore()
	s3.commitAt(map[string]string{"x": "1", "y": "1"})
	snap3 := s3.ts
	// T1：读 y=1，写 x=0
	y1, _ := s3.readAt("y", snap3)
	_, ok1 := s3.commitSI(snap3, map[string]string{"x": "0"})
	// T2：读 x=1（旧快照），写 y=0
	x1, _ := s3.readAt("x", snap3)
	_, ok2 := s3.commitSI(snap3, map[string]string{"y": "0"})
	fx, _ := s3.readAt("x", s3.ts)
	fy, _ := s3.readAt("y", s3.ts)
	fmt.Printf("③ 写偏斜：T1 读到 y=%s 写 x=0（提交=%v），T2 读到 x=%s 写 y=0（提交=%v）\n", y1, ok1, x1, ok2)
	fmt.Printf("   最终 x=%s y=%s —— 两个事务写的是不同的行，SI 的写-写检测抓不到\n", fx, fy)

	// ---------- ④ 丢失更新：两个事务写同一行，第二个被拒 ----------
	s4 := newStore()
	s4.commitAt(map[string]string{"balance": "100"})
	snap4 := s4.ts
	_, okA := s4.commitSI(snap4, map[string]string{"balance": "80"})
	_, okB := s4.commitSI(snap4, map[string]string{"balance": "60"})
	fmt.Printf("④ 丢失更新：先提交者=%v，后提交者=%v（第二个被写-写冲突拒绝）\n", okA, okB)
}

                      本机实测（macOS，Apple M1，Go 1.27）：

                      ① 不可重复读   RR 读到 v1，RC 读到 v2（数据库实际是 v2）
② 幻读（快照隔离）旧快照看到 [user:1]，当前能看到 [user:1 user:2]
③ 写偏斜：T1 读到 y=1 写 x=0（提交=true），T2 读到 x=1 写 y=0（提交=true）
   最终 x=0 y=0 —— 两个事务写的是不同的行，SI 的写-写检测抓不到
④ 丢失更新：先提交者=true，后提交者=false（第二个被写-写冲突拒绝）

                      读数：

                      场景 结果 说明
                      不可重复读 RR 读到 v1、RC 读到 v2 差别只在“快照是事务级还是语句级”
                      幻读 旧快照只有 user:1，当前有 user:1,user:2 快照隔离下“读不到新行”= 用 MVCC 消除了幻读，但代价是可能读到旧世界
                      写偏斜 两个事务都提交，最终 x=0 y=0 SI 只检测“写同一行”，不检测“读写交叉”
                      丢失更新 后提交者被拒 写-写冲突检测生效（first-committer-wins）

                      🔑 快照隔离（SI）防住了丢失更新与脏读，但防不住写偏斜——写偏斜需要串行化快照隔离（SSI，检测“读写依赖环”）或显式加锁。这就是“RR 够用”这句话的危险之处：它在多数业务里够用，在“约束跨两行”的场景（余额、库存、名额）里不够。

                      InnoDB 怎么把「100G 的快照」做成几个整数

                      RR 的快照不拷贝任何数据。每个行版本带一个 row trx_id，事务启动时只记一个「活跃事务 ID 数组 + 高水位」，读的时候拿版本的 trx_id 和这个视图比大小——所以「拍快照」是常数开销。

                      部件 存在哪 内容
                      行版本 + undo 行上只有最新版本，旧版本按 undo 反算出来 每个版本带 row trx_id
                      一致性视图 read view 事务（RR）或语句（RC）的内存结构 m_ids 活跃事务数组、min_trx_id 低水位、max_trx_id 高水位、creator_trx_id
                      事务 ID 全局递增，事务启动时申请 决定版本的先后

                      回退次数 = 从最新版本到你的视图之间，这一行被改过几次。同一行被改 100 次，老视图就要顺着 undo 链回退 100 次，每次都访问 undo 页——这是长事务下查询变慢的直接原因。视图本身的大小只与活跃事务数有关：每个事务 id 8 字节，几千个并发也不过几十 KB，与库是 1GB 还是 100GB 无关。

                      💡 V1 / V2 / V3 这些历史版本不是物理存在的：从最新版本出发，按 undo 一条条回退算出来。所以一个事务持有越老的视图，能回退的链就越长——这是长事务伤全库的机制。

                      可见性判定：四个分支

                      设事务 A 的视图为「数组 [99,100]、低水位 99、高水位 101」，行版本依次是 90 → 102 → 101：

                      版本的 row trx_id 落在哪 可见性 本例取值
                      = creator_trx_id（自己改的） 自己 可见 100（A 自己写的版本）
                      < min_trx_id（视图创建前已提交） 绿色 可见 90 → k=1
                      ≥ max_trx_id（视图创建后才启动） 红色 不可见 101（B）、102（C）
                      在 m_ids 里（视图创建时活跃、未提交） 黄色 不可见 99

                      事务 A 读一行时：当前版本是 101（B 生成，晚于 A 的视图 → 不可见）→ 按 undo 回退到 102（C 生成，同样不可见）→ 再回退到 90（可见）→ 返回 k=1。「可重复读」的实现是「不认新版本」，不是「锁住行」。

                      B 的 3 和 A 的 1：三个事务的账怎么算

                      08 讲的场景：表 t(id,k) 两行 (1,1)、(2,2)。

                      事务 做了什么 事务 id
                      C 不显式 begin，update t set k=2 where id=1 自动提交 102
                      B begin；update t set k=k+1 where id=1；select k 101
                      A start transaction with consistent snapshot；select k 100

                      前提：A 之前系统里有一个活跃事务 99，行 (1,1) 的 row trx_id=90。于是 A 的视图是 m_ids=[99,100]、低水位 99、高水位 101、creator_trx_id=100。

                      A 读到 1 的推演，前面的四分支表已经给出；容易漏掉的是 B 的 3 从哪来。B 的 update 不是快照读：写之前必须读当前值，这个读是当前读，拿到 C 已提交的 (1,2)，加 1 得到 3，新版本 row trx_id=101。B 随后的 select 看到版本 101 等于自己的 creator_trx_id，直接可见，返回 3。如果 B 先做一次普通 select，会读到 1；但 update 仍然从 2 算起——同一事务里两种读并存，这是最容易把人绕晕的地方。

                      B 之前的动作 B 的 update 基于 B 的 select A 的 select
                      C 已提交 2 → 写 3 3 1
                      C' 未提交 等 C' 提交后基于 2 → 写 3 3 1
                      C 已提交、A 处于 RC 2 → 写 3 3 2

                      C' 是原文的变体：C 改完不提交，B 的 update 就会卡住。原因是当前读要读最新版本并加锁，而 (1,2) 上的写锁还在 C' 手里；两阶段锁协议要求锁到事务提交才释放，B 只能等。

                      RC 下 A 读到 2：A 的视图在 select 语句执行时重建，此时 B 的 101 未提交（在 m_ids 里，不可见），C 的 102 已提交且不在 m_ids 里（可见）。

                      黄色区间为什么还要分两种

                      视图数组存的是“活跃”事务，不是“已提交”事务。所以 min_trx_id 与 max_trx_id 之间（黄色）既有未提交的，也有已提交的：m_ids=[99,100,102]，而 101 已提交，则 row trx_id=101 的版本可见。只存一个“已提交的最大事务 id”不够，因为比它小的事务（比如 98）可能在视图创建之后才提交；反过来只有 m_ids 也不够，因为低水位以下的一定已提交，不必逐个查。两个边界加一个数组，才把“可见/不可见”划干净。

                      视图数组和高水位是在事务系统的锁保护下一起取的，可以当成一个原子操作：取数组与取高水位之间不会插进来一个新事务。否则就会出现“数组里没有它、高水位也没盖住它”的版本，可见性判定直接失效。

                      🔑 row trx_id 的大小不代表版本新旧：B 的 101 比 C 的 102 小，但 B 写得更晚。版本链的顺序由 undo 指针决定，比较时只拿 row trx_id 和视图比，不能拿两个版本的事务 id 互相比。

                      两种读：同一事务里可以并存

                      语句 读什么 加锁 看到的数据
                      SELECT ... 快照读（一致性读） 不加锁 视图时刻已提交的版本
                      SELECT ... LOCK IN SHARE MODE / FOR UPDATE 当前读 S / X 锁 最新已提交版本
                      UPDATE / DELETE 当前读（先读后写） X 锁，持有到事务结束 最新已提交版本

                      UPDATE 必须当前读：如果按快照读的旧值算 k=k+1，别人已提交的修改就被覆盖了（丢失更新）。所以「先 SELECT 判断、再 UPDATE」在任何隔离级别下都不是原子的——要么用条件更新（UPDATE ... SET n=n-1 WHERE n>0），要么用当前读加锁。

                      -- 会话 A（MySQL 8.0，本机无实例，未执行）
SET SESSION transaction_isolation = 'REPEATABLE-READ';
BEGIN;
SELECT k FROM t WHERE id=1;              -- 1（视图建立）
-- 会话 B 执行：UPDATE t SET k=k+1 WHERE id=1; COMMIT;
SELECT k FROM t WHERE id=1;              -- 仍是 1：快照读
SELECT k FROM t WHERE id=1 FOR UPDATE;   -- 3：当前读，读最新并加锁

                      RC 与 RR 只差一行代码：视图什么时候建

                      级别 视图创建时机 同一事务两次快照读
                      RC 每条语句执行前重建 可能不同
                      RR 事务第一条快照读时（或 START TRANSACTION WITH CONSISTENT SNAPSHOT） 一定相同

                      START TRANSACTION WITH CONSISTENT SNAPSHOT 在 RC 下没有额外含义，等效普通 START TRANSACTION——它不改变「每条语句重建视图」这件事。

                      表结构不支持可重复读：DDL 没有 row_trx_id，只能走当前读。这也是「加字段」在 RR 下仍会被别人的 DDL 顺序影响的原因。

                      表结构也没有对应的行数据可以挂版本链：MySQL 8.0 把表结构放进了 InnoDB 数据字典，但这个限制来自“没有版本链”，不是来自存储位置。

                      🔑 两种读可以混用，所以「RR 下我读到了新值」不是 bug：同一个事务里先 SELECT（旧值）再 SELECT ... FOR UPDATE（新值）是合法且常见的，很多人用「RR 保证了隔离」去解释业务逻辑，忽略了语句级差异。

                      四种隔离级别的实现差异

                      级别 快照粒度 写冲突检测 读是否加锁 仍可能出现
                      读未提交 无（读最新） 无 无 脏读
                      读已提交 RC 每条语句 写时（行锁） 无 不可重复读、幻读
                      可重复读 RR 每个事务 写时（行锁 + 间隙锁） 无（快照读） 写偏斜（InnoDB 的一致性非锁定读同样可能；需 Serializable/加锁读才能防）
                      串行化 事务 读写都检测（SSI/2PL） 可能 只有串行化冲突时回滚

                      ⚠️ 同样是“RR”，MySQL InnoDB 用“快照读 + 间隙锁”，PostgreSQL 的 RR 实际是 SI（不阻止写偏斜）；Oracle 的“可串行化”是 SI + SSI。名字一样，语义不一样——跨库迁移时必须看文档，而不是看级别名。

                      当前读：四种语句，共同点是“读最新 + 加锁”

                      语句 读什么 加锁 说明
                      SELECT ... 视图里的版本 无 快照读
                      SELECT ... LOCK IN SHARE MODE 最新已提交 S 当前读，别人能读不能改
                      SELECT ... FOR UPDATE 最新已提交 X 当前读，锁到提交
                      UPDATE / DELETE 先当前读再写 X 锁持有到事务结束
                      INSERT 不读旧值，查唯一键 插入意向 + 唯一键检查 冲突时等待或报 1062

                      update / delete 算当前读，是因为“先读后写”的读必须最新，否则覆盖别人已提交的修改；insert 没有旧版本可读，但唯一键冲突时要对冲突行加锁。当前读的收益是判断不基于旧世界，代价是可能被别人的锁挡住。

                      🔑 快照读和当前读不是两个隔离级别，而是同一个事务里的两种语句。RR 只保证快照读可重复，不保证当前读。

                      SELECT ... FOR UPDATE 在 RR 下锁的不是“这一行”，而是 next-key lock（记录 + 前面的间隙），范围取决于扫描到的索引；展开在 44.11 锁。

                      一个把两种读用错的例子

                      08 讲的思考题：RR 下执行 update t set c=0 where c=id，想把 c 与 id 相等的行清零，执行完却发现一行都没改。原因是另一个事务在它之前执行了 update t set c=id+1 并提交：update 的 where 走当前读，看到的是 c=id+1，谓词不命中；而同一事务里的普通 select 走快照读，看到的还是 c=id。于是“查出来该改，改的时候说没有”——谓词里的读与更新时的读不是同一个世界。

                      begin 不是起点：视图在第一条语句才建

                      写法 视图建立时刻 说明
                      begin / start transaction 之后第一条访问 InnoDB 的语句 命令本身不建视图
                      start transaction with consistent snapshot 语句执行时 要“立刻定格”用这个
                      autocommit=0 连接上第一条语句，直到 commit / rollback / 断开 没有 begin 也在事务里
                      autocommit=1 + begin 显式 begin 生产推荐

                      autocommit=0 是长事务的头号来源：连接池初始化执行一次，之后这条连接上的每条 select 都开事务，直到提交或断开。频繁开事务又想省一次交互，用 commit work and chain。RC 下 start transaction with consistent snapshot 没有额外含义，等效普通 start transaction。

                      ⚠️ RR 下 begin 后先查 MyISAM 表或调一次 RPC，视图还没建；这期间别人提交的修改会被算进你的“快照”。要严格从某一刻开始，用 start transaction with consistent snapshot。

                      本机实测（MySQL 8.0.46，端口 33107）：A 执行 START TRANSACTION WITH CONSISTENT SNAPSHOT 后读到 k=3，B 把 k 改成 4 并提交，A 再读仍是 3。

                      幻读：快照读看不见，当前读挡不住

                      时刻 T1（RR） T2
                      1 begin
                      2 select count(*) where id>=1 → 3
                      3 insert id=4；commit
                      4 select count(*) where id>=1 → 3
                      5 select count(*) where id>=1 for update → 4
                      6 commit

                      快照读返回 3，因为视图里没有 id=4；当前读返回 4，因为它必须读最新版本并加锁。快照读的“不幻读”是看不见，不是阻止插入；让当前读也看不到新行的，是 next-key lock（44.11 锁）。

                      💡 标准只说串行化消除幻读；InnoDB 在 RR 用 next-key lock 补住了当前读，快照读仍可能读到旧的行集合。两者别混。

                      长事务：代价不是“慢”，是“全库都不能清理”

                      代价 机制 观测点
                      undo 不能清理 老视图要求保留它可能读到的所有旧版本 History list length
                      回滚段膨胀 5.5 以前 undo 在 ibdata，清理也不缩文件；原文见 20GB 数据、200GB 回滚段 磁盘占用
                      锁不释放 行锁、MDL 持有到提交 锁等待、DDL 被堵
                      主从延迟 大事务一次写 binlog Seconds_Behind_Master
                      连接与内存 长连接 + 老视图 连接数、内存

                      purge 从 history list 的老端开始清理，碰到“比最老视图还新”的 undo 就停下等；所以一个长事务不是拖慢自己，是让整条清理流水线停在它那一刻。

                      定位：

                      SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS seconds,
       trx_isolation_level, trx_rows_modified, trx_mysql_thread_id
FROM information_schema.innodb_trx
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60
ORDER BY trx_started;

                      trx_mysql_thread_id 就是 SHOW PROCESSLIST 的 Id。确认语句后再 KILL；杀之前先看 trx_rows_modified，回滚一个改了几百万行的事务，可能比让它跑完更久。

                      SHOW ENGINE INNODB STATUS 的 History list length（HLL）：本机 8.0.46 上，让一个 RR 事务先建视图，再用 200 个独立事务更新 200 行，HLL 从 17 涨到 204，A 提交 2 秒后仍是 204；同一镜像上没有长视图时，同样 200 个事务后 HLL 只有 4。原文的数字更极端：数据 20GB、回滚段 200GB，最后只能重建库。

                      只读事务用 START TRANSACTION READ ONLY，不申请事务 ID，适合对账、报表；但它仍然持有一致性视图，跑十分钟一样挡住 purge。只读不等于无代价。

                      业务侧四条：

                      • 事务里不放 RPC、MQ 发送、循环查库、等用户输入；
                      • 批量删除分批：DELETE ... LIMIT 500，每批单独提交；
                      • autocommit=1，显式 begin / commit，不用 autocommit=0 省交互；
                      • 监控 innodb_trx 里超过 60 秒的事务，按 trx_started 报警。

                      原文的对账场景要的是“校对期间不受新交易影响”，用 RR 的短事务或固定快照即可，不是把整个校对塞进一个长事务。慢 SQL 与锁等待的排查步骤见 44.28 MySQL 慢 SQL 案例集。

                      本机实测：RR 的 1、RC 的 3 与 HLL 的 204

                      环境：MySQL 8.0.46（Docker，innodb_buffer_pool_size=128M、innodb_page_size=16384，默认 RR），端口 33107。会话 A 固定，B 在中间提交：

                      场景 A 第一次读 B 的动作 A 第二次读 结论
                      RR 快照读 1 update k=k+1 提交 1 视图没变
                      RR 当前读 1 同上 for update → 2 当前读读最新
                      RC 2 update 提交 3 每条语句重建视图
                      一致性快照 3 update 提交 3 视图在 start 时建
                      幻读 count=3 insert id=4 提交 count=3；for update 得 4 快照读 vs 当前读
                      长事务 HLL 17 200 个独立事务更新 200 行 HLL 204 老视图挡住 purge

                      完整脚本在仓库 tools/examples/44.10-mvcc-lab/，bash code/run.sh 可复现（端口 33199）。

                      复现这类场景，两个会话必须各自持有一条长连接：用 mysql -e 每次执行都是一条新连接，事务在命令结束时就没了，看到的永远是单语句结果。

                      回滚/降级：实验只改会话级 transaction_isolation，COMMIT 即恢复；生产改全局级别用 SET GLOBAL TRANSACTION ISOLATION LEVEL ...，只影响新连接。

                      反模式

                      反模式 后果
                      以为 RR 就不会有并发问题 写偏斜照样发生（本节③）
                      RC 下先查后改，不做条件更新 检查与更新之间有窗口，超卖
                      长事务持有快照 undo 无法回收，版本链膨胀，查询越来越慢
                      用 SELECT ... FOR UPDATE 代替一切 锁竞争、死锁率上升（44.11）
                      把“读已提交”当“没有脏读就够了” 业务逻辑可能在两条语句之间看到不同世界
                      跨库迁移不看隔离级别实现 从 MySQL 迁到 PG 前，要按隔离实现（InnoDB 快照读 + 间隙锁 vs PG SI）核对写偏斜风险，而不是只看级别名
                      用普通 SELECT 做“读-判断-写” 快照读看不到别人已提交的修改，判断基于旧世界，UPDATE 覆盖别人的写
                      同一事务里混用快照读与当前读 前后两次读到的值不同，业务把它当“隔离失效”去查，方向跑偏
                      事务开分钟级 老视图让 undo 无法 purge，版本链拉长，全库查询一起变慢
                      以为 START TRANSACTION WITH CONSISTENT SNAPSHOT 在 RC 下更强 它等效普通 START TRANSACTION，一行保证都没多
                      用连续 BEGIN 做嵌套事务 MySQL 隐式提交前一个事务，ROLLBACK 只回滚最后一个
                      语句报错就以为事务已回滚 默认不会自动回滚；错误处理里必须显式 ROLLBACK
                      事务里混入 DDL MySQL 的 DDL 隐式提交，事务边界被切断
                      对 MyISAM 表做 ROLLBACK 引擎不支持事务，静默无效
                      长期 autocommit=0 不提交 连接一直持锁、undo 不回收，影响全库
                      把 begin 当快照起点 视图建在第一条语句，begin 与第一条语句之间的提交会被算进来
                      只读事务开很久不提交 START TRANSACTION READ ONLY 一样持有视图，undo 无法清理
                      只看 History list length 判断长事务 它只说明 undo 在堆积，定位要查 innodb_trx.trx_started 与 trx_rows_modified

                      自检

                      Q1 为什么“可重复读”能消除不可重复读，却不能消除写偏斜？

                      ▸ 答案：可重复读保证“同一个事务里读到的快照不变”，所以两次读同一行结果一致。但写偏斜的问题是“两个事务读的是不同行、写的是不同行”：T1 读 y 写 x，T2 读 x 写 y，两个事务没有写同一行，写-写冲突检测（which 只看被写的行）永远抓不到。要防它，必须在“读”上也建立依赖检测（SSI）或对读到的行加锁（SELECT ... FOR UPDATE）。

                      Q2 RC 与 RR 在高并发下怎么选？

                      ▸ 答案：RC 的锁持有时间短、undo 回收快、并发度高，但同一事务内可能读到不同版本，业务要能容忍“不可重复读”。RR 提供事务级一致性视图，适合“一个事务内多次读同一批数据要给出一致结论”的场景（报表、对账），但长事务会拖住 undo 回收。多数互联网业务默认 RC，把“需要一致性”的部分用单条 SQL（带条件更新）或显式锁解决。

                      Q3 写偏斜的经典例子是“两个医生同时值班，各自请假”，为什么加一个 SELECT ... FOR UPDATE 就能解决？

                      ▸ 答案：因为写偏斜的根源是“读的时候没锁”。两个事务各自读到“还有 2 人在岗”，然后各自把自己设为离岗。如果 SELECT count(*) ... FOR UPDATE 对“在岗记录”加锁，第二个事务会等第一个提交，重新读到“只剩 1 人”，从而拒绝请假。代价是串行化：所有修改值班状态的事务排队。另一种解法是把约束物化（比如“值班人数”单独一行，用条件更新 SET n=n-1 WHERE n>1），把跨行约束变成单行原子操作。

                      Q4 用 RC（读已提交）+ 行锁，为什么仍然可能死锁？

                      ▸ 答案：因为死锁来自 “加锁顺序不一致”，与隔离级别无关：两个事务分别先锁 A 再锁 B、先锁 B 再锁 A，就会互相等待。RC 只是减少间隙锁、降低概率，不消除环路。解法是统一加锁顺序、缩短事务、并接受 “死锁检测 + 重试”。

                      Q5 隔离级别与 “重试 + 幂等” 怎么配合？

                      ▸ 答案：高隔离级别（RR/Serializable）会把冲突变成失败（死锁、序列化失败），应用必须能重试；重试要求操作幂等（否则重复扣款）。所以 “提高隔离级别” 的前提是 “业务可重试 + 幂等键”，否则只是把并发问题变成用户可见的错误。

                      Q6 一个 100GB 的库，开启 RR 事务时“拍快照”为什么不慢？快照里到底存了什么？

                      ▸ 答案：没有拷贝数据。事务启动只申请一个事务 ID，并记录「当前活跃事务 ID 数组 + 低水位 + 高水位」，这三个数是常数大小。数据侧的代价早就付过了：每行更新时保留 row_trx_id 并把旧值写进 undo。所以快照是“声明”，不是“副本”；读的时候用视图去筛选版本，筛不到就按 undo 往前回退。

                      Q7 事务 A 在 RR 下先 SELECT 得到 k=1，随后 SELECT ... FOR UPDATE 得到 k=3，隔离级别是不是失效了？

                      ▸ 答案：没有。第一条是快照读，只看视图时刻已提交的版本；第二条是当前读，读最新已提交版本并加 X 锁。RR 只保证快照读的可重复性，不约束当前读。这也是「先查后改」错在哪里：查是旧值、改是新值，中间别人可能已经改过。要一致，要么把判断写进 UPDATE ... WHERE 的谓词里，要么一开始就用当前读加锁。

                      Q8 连续执行两个 BEGIN，第一个事务里已插入的行会怎样？

                      ▸ 答案：MySQL 会隐式提交第一个事务，再开启第二个；所以后面的 ROLLBACK 只回滚第二个事务，第一段插入已落库。这不是嵌套事务。Oracle 没有这个行为，跨库脚本不能照搬。

                      Q9 同一事务里两次 select count(*) 都是 3，加上 for update 却数出 4，隔离级别失效了吗？

                      ▸ 答案：没有。前两条是快照读，视图停在事务启动时；for update 是当前读，读最新已提交版本并加锁，所以看见了别的事务插入的行。RR 的可重复只约束快照读。要让当前读也看不到新行，靠的是 next-key lock 对区间加锁（44.11 锁），而不是快照。

                      Q10 一个只读报表事务跑十分钟，为什么会让写入变慢？

                      ▸ 答案：它持有老的一致性视图，purge 不能删除比它更早的 undo，版本链越拉越长、回滚段膨胀，写入要维护更多版本，purge 也一直落后。START TRANSACTION READ ONLY 只是不申请事务 ID、不写 undo，不等于不持有视图。对策是把报表拆小批、限制单事务时长，或放到从库上跑。
