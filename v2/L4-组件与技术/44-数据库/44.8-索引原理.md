# 44.8 索引原理 (B+ 树 / 哈希 / 覆盖索引 / 最左前缀)

## 一句话

> 索引是**用写放大和空间换更少的页读取**：B+ 树赢了范围查询，哈希赢了等值点查，覆盖索引赢在“不回表”——选型不是比谁先进，而是算清“这类查询要读几页”。

## 四种结构，四种胜负

| 结构 | 等值 | 范围 | 排序 | 写放大 | 典型场景 |
|---|---|---|---|---|---|
| **B+ 树** | O(log n) | ✅ 叶子有序、区间扫描 | ✅ 天然有序 | 页分裂 | 绝大多数 OLTP 索引 |
| 哈希 | O(1) | ❌ 完全无序 | ❌ | 低 | 内存表、等值查找 |
| 倒排（全文） | 按词 | ❌ | ❌ | 高 | 搜索（[45.1 倒排索引与分词](../45-检索与搜索引擎/45.1-倒排索引与分词.md)） |
| 位图 | 按集合 | ⚠️ 低基数 | ❌ | 中 | 数仓低基数维度 |

> 🔑 B+ 树的本质是**“让叶子节点按 key 有序，并且用兄弟指针串起来”**：所以 `BETWEEN`、`ORDER BY`、`LIMIT` 都能在索引上顺序扫，不用回表排序。哈希把 key 打散，天然丢失顺序，所以只能等值。

## 聚簇索引与二级索引：回表的代价

| 索引类型 | 叶子存什么 | 查一行要几次 I/O |
|---|---|---|
| 聚簇索引（主键） | 整行数据 | 树高次（3–4 页），拿到就是整行 |
| 二级索引 | 索引列 + 主键值 | 树高次 + **回表**（按主键再查一次聚簇索引） |
| 覆盖索引 | 查询需要的全部列 | 树高次，**不回表** |

```go
package main

import "fmt"

const (
	rows         = 1_000_000 // 表行数
	rowsPerPage  = 100       // 每页 100 行
	treeHeight   = 3         // 扇出约 500 时，1M 行约 3 层
	randReadMs   = 0.10      // 随机读一页
	seqReadMs    = 0.01      // 顺序读一页
)

func pages(n int) int {
	p := n / rowsPerPage
	if n%rowsPerPage != 0 {
		p++
	}
	return p
}

func main() {
	tablePages := pages(rows) // 全表扫描要读的页数

	type result struct {
		name  string
		desc  string
		pages int
		rand  int // 其中随机读的页数
	}
	cases := []result{
		{"主键点查", "B+ 树 3 层", treeHeight, treeHeight},
		{"二级索引查 1,000 行（非覆盖）", "3 页索引 + 1,000 次回表", treeHeight + 10 + 1000, treeHeight + 1000},
		{"二级索引查 1,000 行（覆盖索引）", "3 页索引 + 10 页叶子", treeHeight + 10, treeHeight + 10},
		{"索引下推（索引层过滤）", "扫 1,000 条，仅 120 条回表", treeHeight + 10 + 120, treeHeight + 120},
		{"哈希等值点查", "1 页定位", 1, 1},
		{"哈希做范围查询", "不支持，退化为全表扫描", tablePages, 0},
		{"B+ 树范围查 1,000 行", "3 页索引 + 10 页顺序叶子", treeHeight + 10, treeHeight},
	}

	fmt.Printf("表 %d 行、每页 %d 行、全表 %d 页；随机读 %.2fms、顺序读 %.2fms\n\n",
		rows, rowsPerPage, tablePages, randReadMs, seqReadMs)
	fmt.Printf("%-32s %-28s %-8s %-10s %s\n", "场景", "做什么", "页数", "估算耗时", "备注")

	for _, c := range cases {
		seq := c.pages - c.rand
		ms := float64(c.rand)*randReadMs + float64(seq)*seqReadMs
		note := ""
		if c.name == "二级索引查 1,000 行（非覆盖）" {
			note = "回表是主要成本"
		}
		if c.name == "二级索引查 1,000 行（覆盖索引）" {
			note = "省掉 1,000 次随机读"
		}
		if c.name == "索引下推（索引层过滤）" {
			note = "回表从 1,000 降到 120"
		}
		fmt.Printf("%-32s %-28s %-8d %-10s %s\n", c.name, c.desc, c.pages,
			fmt.Sprintf("%.1fms", ms), note)
	}
}
```

本机实测（macOS，Apple M1，Go 1.27）：

```
表 1000000 行、每页 100 行、全表 10000 页；随机读 0.10ms、顺序读 0.01ms

场景                               做什么                          页数       估算耗时       备注
主键点查                             B+ 树 3 层                     3        0.3ms      
二级索引查 1,000 行（非覆盖）               3 页索引 + 1,000 次回表            1013     100.4ms    回表是主要成本
二级索引查 1,000 行（覆盖索引）              3 页索引 + 10 页叶子               13       1.3ms      省掉 1,000 次随机读
索引下推（索引层过滤）                      扫 1,000 条，仅 120 条回表          133      12.4ms     回表从 1,000 降到 120
哈希等值点查                           1 页定位                        1        0.1ms      
哈希做范围查询                          不支持，退化为全表扫描                  10000    100.0ms    
B+ 树范围查 1,000 行                  3 页索引 + 10 页顺序叶子             13       0.4ms      
```

读数：

| 对比 | 差距 | 结论 |
|---|---|---|
| 非覆盖 vs 覆盖索引 | 1,013 页 vs 13 页（**78 倍**） | 查的列都在索引里，就不要回表 |
| 索引下推前后 | 回表 1,000 → 120（**8 倍**） | 把过滤条件下推到索引层，能少 88% 的回表 |
| 哈希等值 vs B+ 树等值 | 1 页 vs 3 页 | 哈希点查只读 1 页，但代价是丢掉范围与排序 |
| 哈希做范围查询 | 10,000 页（全表） | 不支持就是全表，索引等于没用 |

> 🔑 所以“加索引”之前先问：**这条查询的列，能不能被一个索引完全覆盖？** 能 → 覆盖索引（最优）；不能 → 至少把过滤条件下推到索引（联合索引把过滤列放在前面）；范围查询与排序 → 只能 B+ 树。

## 普通索引还是唯一索引：差在写路径，不在读路径

同一个字段（例如身份证号），业务代码已经保证不会重复，建**普通索引**还是**唯一索引**？读的差别可以忽略，写的差别能大到「整库堵住」。

| 路径 | 唯一索引 | 普通索引 | 差在哪 |
|---|---|---|---|
| 等值查询命中 | 找到第一条即停 | 找到第一条后还要看下一条是否同值 | 一次指针移动，**页已在内存，可忽略** |
| 更新，目标页在内存 | 判断冲突 → 改内存 | 直接改内存 | 一次比较，可忽略 |
| 更新，目标页**不在**内存 | 必须把页读进来才能判断是否重复 → **一次随机读** | 变更记进 change buffer，事务即可结束 | 随机读 vs 一次顺序写日志 |

> 🔑 **唯一索引用不上 change buffer**：唯一性判断必须先把数据页读进内存，页都读进来了，直接改内存本来就快，缓存变更没有意义。所以「唯一」买到的是约束，付出的是写路径上每页一次随机读。

### change buffer 在做什么

更新一个不在内存的页时，InnoDB 不急着读盘：把「哪个页要插哪一行」记进 change buffer（内存里有拷贝，也会落到系统表空间 `ibdata1`），下次查询真正要访问这个页时，再把页读进来、把积压的变更应用上去，这个过程叫 **merge**。后台线程会定期 merge，正常 shutdown 也会 merge。

| 机制 | 省掉的是什么 | 位置 |
|---|---|---|
| **redo log** | 随机**写**盘 → 顺序写 | `ib_logfile*` |
| **change buffer** | 随机**读**盘 | buffer pool 内存 + `ibdata1` |

两条容易混：redo log 保证「崩溃不丢」，change buffer 保证「更新不必先读页」。掉电重启后，change buffer 里已持久化的部分由 redo 重放恢复，未持久化但已提交的部分同样在 redo 里——**change buffer 不是内存里的临时变量**。

```ini
[mysqld]
innodb_change_buffer_max_size = 50   # 占 buffer pool 的上限（%），默认 25、最大 50
```

`50` 的语义是「change buffer 最多占 buffer pool 的一半」，不是「写缓存占磁盘 50%」。写多读少的归档库、账单库开到最大；写入后立刻要读的库反而该关小——马上 merge 等于白记一遍，只多付维护成本。change buffer 挤占的是缓冲池的内存，命中率的账要一起算（[44.3 缓冲池与页面管理](44.3-缓冲池与页面管理.md)）。

```sql
-- 验证：看 change buffer 的合并次数与占用（MySQL 8.0，本机无实例，未执行）
SELECT NAME, COUNT FROM information_schema.INNODB_METRICS WHERE NAME LIKE 'ibuf%';
```

### 一个真实量级的后果

某业务把一条普通索引改成唯一索引，**buffer pool 命中率从 99% 掉到 75%，更新语句全部堵住**。原因就是原来写密集的插入全走 change buffer，改完每一行都要把目标页读进内存——随机读把缓冲池冲干净了，命中率再往下掉，恶性循环。排查这类「没改 SQL、没涨流量，写入突然变慢」时，先看最近有没有人动过索引的**唯一性**。

| 你的情况 | 选什么 |
|---|---|
| 业务代码能保证不重复（且不打算靠 DB 兜底） | **普通索引**，写路径吃 change buffer |
| 业务不能保证，或要求数据库做约束 | **唯一索引**，没得选；性能问题另找出口（拆批、归档） |
| 写多读少：账单、日志、归档库 | 普通索引 + `innodb_change_buffer_max_size` 开大，机械盘收益尤其明显 |
| 写完立刻读（如先插后查的幂等表） | 普通索引但把 change buffer 关小，避免「记完马上 merge」 |

## 字符串字段：全字段、前缀、倒序、哈希列

长字符串（邮箱、身份证号、URL）直接建全字段索引的问题是**索引太宽**：页里放的键少了，树变高，写放大也大。四种做法的差别不在「省不省空间」，而在**扫描行数、能否覆盖、能否范围查**。

| 方案 | 空间 | 扫描行数 | 覆盖索引 | 范围查询 | 额外 CPU |
|---|---|---|---|---|---|
| 全字段索引 `(email)` | 最宽 | 1 行 | ✅ | ✅ | 无 |
| 前缀索引 `(email(6))` | 最省 | **可能多行**（本例 4 行） | ❌ **永远回表** | ✅ | 无 |
| 倒序存储 + 前缀索引 | 省 | 可能多行 | ❌ | ❌ | `reverse()` |
| 哈希列 `crc32()` + 索引 | 4 字节 | 接近 1 行 | ❌ | ❌ | `crc32()` |

前缀索引的第一个代价是**回表次数**：`email(6)` 只索引 `zhangs`，同一前缀下的行全要回表比对，例子里扫了 4 行才命中；把长度改成 `email(7)`（前缀 `zhangss` 已唯一）就只扫 1 行。

第二个代价更隐蔽：**前缀索引永远用不上覆盖索引**。哪怕 `email(18)` 已经把整个字段装下，InnoDB 仍然要回主键再确认一次——它无法证明前缀没有截断完整值。`SELECT id, email` 这种本来能覆盖的查询，在前缀索引上仍然回表。

长度靠**区分度**定，不靠猜：

```sql
-- 1) 基线：全列有多少个不同的值
SELECT COUNT(DISTINCT email) AS L FROM SUser;

-- 2) 各前缀长度的不同值个数，取「不低于 L 的 95%」的最短长度
SELECT COUNT(DISTINCT LEFT(email,4)) AS L4,
       COUNT(DISTINCT LEFT(email,5)) AS L5,
       COUNT(DISTINCT LEFT(email,6)) AS L6,
       COUNT(DISTINCT LEFT(email,7)) AS L7
FROM SUser;

-- 3) 建索引（8.0，Online DDL，不锁表；本机无实例，未执行）
ALTER TABLE SUser ADD INDEX idx_email6 (email(6)), ALGORITHM=INPLACE, LOCK=NONE;
```

5% 是**可接受的区分度损失**，可以按业务调；关键是先量再建，不要凭「取前 6 位」的直觉。

前缀区分度天然不够时（身份证号前 6 位是地址码，同县的人全一样），换第 3、4 种做法：

```sql
-- 倒序存：写时 reverse，读时也 reverse，索引按倒序字符串排序
UPDATE t SET id_card = REVERSE(id_card);
SELECT * FROM t WHERE id_card = REVERSE(?);

-- 哈希列：4 字节索引，冲突概率极低，但必须回表比对原值
ALTER TABLE t ADD COLUMN id_card_crc INT UNSIGNED, ADD INDEX idx_crc (id_card_crc);
SELECT * FROM t WHERE id_card_crc = CRC32(?) AND id_card = ?;
```

两种都不支持范围查询：倒序索引按「倒着的字符串」有序，哈希列干脆无序。需要 `BETWEEN`、前缀匹配、排序的字段，只能回到全字段索引。

> 🔑 字符串索引的判据是**「这条查询要不要范围 / 要不要覆盖」**：只要等值、又要省空间 → 前缀、倒序、哈希三选一；要范围或要覆盖 → 只能全字段，代价是接受索引宽度。

## 最左前缀：不是规则，是物理事实

联合索引 `(a, b, c)` 在 B+ 树里是按 `(a, b, c)` 的**字典序**排列的：

```
(a=1,b=1,c=1) → (1,1,2) → (1,1,3) → (1,2,1) → (1,2,2) → (2,1,1) → ...
```

所以：

| 查询条件 | 能否用索引 | 为什么 |
|---|---|---|
| `a=1` | ✅ | 按 a 有序 |
| `a=1 AND b=2` | ✅ | 前缀连续 |
| `a=1 AND b=2 AND c=3` | ✅ | 完整前缀 |
| `b=2` | ❌ | b 在 a 相同的前提下才有序，跨 a 无序 |
| `a=1 AND c=3` | ⚠️ 只用 a，c 靠回表过滤 | c 跳过了 b |
| `a>1 AND b=2` | ⚠️ 只用 a 的范围 | 范围之后 b 不再有序 |

> ⚠️ 最常见的误解：“把选择性最高的列放最左”。真正的最左规则是**“等值条件放前面、范围条件放最后”**——因为范围一旦出现，它右边的列在索引里就不再有序，无法继续用于定位。

## 反模式

| 反模式 | 后果 |
|---|---|
| 给每个列都建单列索引 | 写放大、优化器选择困难，回表依旧 |
| 联合索引顺序按“选择性”而不是“查询形态”排 | 范围列放前面，后面的列全废 |
| 用 `SELECT *` 导致覆盖索引失效 | 每次查询都回表 |
| 在索引列上做函数/隐式转换（`WHERE DATE(ts)=...`） | 索引失效，全表扫描 |
| 用哈希索引做范围/排序 | 退化为全表 |
| 索引列太多（超宽联合索引） | 索引本身比数据大，写放大严重 |
| 业务能保证唯一，仍建唯一索引 | 写路径失去 change buffer，写密集时命中率与吞吐一起掉 |
| 用前缀索引还想让查询覆盖 | InnoDB 无法证明前缀没截断，永远回表，覆盖收益归零 |
| 对身份证号直接建 `(id_card(6))` | 前 6 位地址码区分度极低，回表放大几十倍 |
| 给倒序列或哈希列写范围查询 | 两种方案只支持等值，范围条件直接退化成全表扫 |

## 自检

**Q1** 为什么“二级索引查 1000 行”比“覆盖索引查 1000 行”慢几十倍，而“点查一行”两者差不多？

▸ 答案：因为回表是**按行数线性增长**的：每回表一次就是一次随机 I/O（查聚簇索引的另一棵 B+ 树）。点查时回表只有 1 次，占比小；1000 行时回表 1000 次，直接主导成本。覆盖索引把查询需要的列都放在二级索引叶子里，回表次数为 0，所以行数越多差距越大。

**Q2** `WHERE b=2` 用不上 `(a,b,c)` 联合索引，加一个 `(b)` 单列索引就好了吗？

▸ 答案：取决于查询形态。如果这条查询很频繁且只需要 b，加 `(b)` 或 `(b, 查询需要的列)` 覆盖索引是合理的；但如果它只是偶尔出现，多一个索引会带来写放大与空间成本（每个索引都要维护 B+ 树）。更常见的做法是调整查询或联合索引顺序，让高频查询走同一个索引。**索引是写路径的成本，不是免费的读优化**。

**Q3** 索引下推（ICP）到底省了什么？为什么它不能省掉“回表”本身？

▸ 答案：ICP 把“能在索引列上判断的条件”下推到存储引擎层，在回表**之前**先过滤掉不满足的行，从而减少回表次数（本节 1000 → 120）。但它仍然要回表取“索引里没有的列”，所以只能减少、不能消除回表。要消除回表，只能让索引覆盖查询需要的全部列。

**Q4** 为什么在索引列上做函数运算（如 `WHERE date(created_at)='2026-01-01'`）会让索引用不上？

▸ 答案：因为 B+ 树索引存的是**列的原值**，不是 “函数结果”。对列做函数后，优化器无法用原值的有序性定位，只能逐行计算再比较（全表扫描）。解法是 “改写成范围查询”（`created_at >= '2026-01-01' AND < '2026-01-02'`）或建 “函数索引/生成列索引”。

**Q5** 一张表建了 10 个索引，写入会付出什么代价？怎么判断 “索引太多”？

▸ 答案：每个索引都是一棵 B+ 树：**每次写入要更新所有索引**，写放大与锁开销随索引数线性增长，还会占缓冲池。判据是 “索引的使用次数”——把长期零命中（或只被低效查询用到）的索引删掉；通常单表 5–6 个索引以上就要逐个 review。

**Q6** 同样是 `WHERE id_card = ?` 的查询，唯一索引和普通索引的读性能差多少？写性能又差多少？为什么差在写上？

▸ 答案：读几乎不差——唯一索引命中第一条就停，普通索引要多看一条是否同值，而那一页已经在内存里，只多一次指针移动。写差在**目标页不在内存**时：唯一索引必须先读页才能判断是否重复，也就是每行多一次随机读；普通索引把变更记进 change buffer 就返回，随机读被推迟到 merge。所以「唯一」是用写路径的随机读换一个数据库级约束。

**Q7** 为什么 `email(18)` 已经把整个 email 装进索引了，`SELECT id, email` 还是要回表？

▸ 答案：因为 InnoDB 无法证明「18 字节的前缀」等于「完整值」：`email` 是 `varchar`，索引里存的只是前 18 个字节，系统不确定有没有第 19 个字节。所以前缀索引一律按「不覆盖」处理。要覆盖只能建全字段索引 `(email)`。

**Q8** 身份证号要按等值查，前缀区分度太低，用倒序还是加 crc32 哈希列？

▸ 答案：看**要不要范围查询**与**要性能稳定还是要省空间**。两种都只支持等值：倒序省一个字段但仍是前缀索引、平均扫描行数大于 1、每次读多一次 `reverse()`；哈希列固定 4 字节、扫描行数接近 1、性能稳定，代价是多一个字段和一次 `crc32()`，并且必须回表用原值确认（哈希会冲突）。有范围需求时两者都不能用，只能全字段索引或改用别的检索结构。
