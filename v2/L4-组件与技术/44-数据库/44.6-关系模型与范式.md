# 44.6 关系模型与范式

## 一句话

> 范式解决的是 “**同一事实只存一处**”：1NF 去重复组、2NF 去部分依赖、3NF 去传递依赖、BCNF 去 “非候选键决定”；但范式不是目标，**读写模式才是**——分析型负载常常故意反范式，用冗余换掉 JOIN。

## 键的谱系：六个词，一张表

范式讨论的“依赖”，依赖的是**候选键**，不是“主键”这个默认选择。六个词先用一张球员表分清：

设 `player(球员编号, 姓名, 身份证号, 年龄, 球队编号)`。

| 概念 | 定义 | 在这张表里 |
|---|---|---|
| **超键** | 能唯一标识一行的属性集 | `(球员编号)`、`(球员编号, 姓名)`、`(身份证号, 年龄)` |
| **候选键** | 不含多余属性的超键（最小的超键） | `(球员编号)`、`(身份证号)` |
| **主键** | 从候选键里选定一个 | `(球员编号)` |
| **外键** | 本表某属性集不是本表主键，而是另一张表的主键 | `球队编号 → team.team_id` |
| **主属性** | 包含在**任一**候选键中的属性 | `球员编号`、`身份证号` |
| **非主属性** | 不在任何候选键中的属性 | `姓名`、`年龄`、`球队编号` |

> 🔑 “主键”只是候选键里被选中的那一个；范式约束的是**所有候选键**。只盯主键，就会漏掉 BCNF 那类“另一个候选键被部分依赖”的问题。

## 函数依赖：部分依赖与传递依赖

记 `X → Y` 为“X 确定，Y 就唯一确定”。2NF 与 3NF 的差别，就是依赖路径走了一步还是两步：

| 范式 | 消除的依赖 | 判据 |
|---|---|---|
| **2NF** | **部分依赖**：非主属性只依赖联合候选键的一部分 | `(球员编号, 比赛编号) → 姓名`，而 `球员编号 → 姓名` |
| **3NF** | **传递依赖**：非主属性依赖另一个非主属性，再由它依赖候选键 | `球员编号 → 球队名称 → 球队主教练` |

2NF 的经典反例 `player_game(球员编号, 姓名, 年龄, 比赛编号, 比赛时间, 比赛场地, 得分)`，候选键是 `(球员编号, 比赛编号)`，但 `姓名/年龄` 只依赖球员、`比赛时间/场地` 只依赖比赛。它同时带来四类异常：

| 异常 | 具体后果 |
|---|---|
| **数据冗余** | 球员参加 m 场，姓名年龄重复 m−1 次；比赛有 n 人，时间场地重复 n−1 次 |
| **插入异常** | 新比赛还没定参赛球员，主键缺一半，插不进去 |
| **删除异常** | 删掉最后一个参赛球员，比赛信息跟着消失 |
| **更新异常** | 改一场比赛时间，要改该比赛的所有行，漏一行就出现两个时间 |

拆法是把“一个表只表达一个意思”落实：`player(球员编号, 姓名, 年龄)`、`game(比赛编号, 比赛时间, 比赛场地)`、`player_game(球员编号, 比赛编号, 得分)`。

## 范式谱系（工程常用到 BCNF）

范式从低到高是 1NF、2NF、3NF、BCNF、4NF、5NF：**高阶一定满足低阶**，但表也越拆越多。工程上通常做到 3NF，遇到“多个候选键交叉决定”时补到 BCNF；4NF/5NF 处理多值依赖与连接依赖，业务建模很少直接用到。

| 范式 | 消除什么 | 反例 |
|---|---|---|
| **1NF** | 字段里存 “多值/重复组” | `tags = "a,b,c"` 存在一个字段 |
| **2NF** | 非主属性依赖 “联合主键的一部分” | `(order_id, sku_id) → sku_name`（只依赖 sku_id） |
| **3NF** | 非主属性依赖 “另一个非主属性” | `order → user_id → user_city`（city 传递依赖） |
| **BCNF** | 任何决定因素不是候选键 | 一个表里有多个 “候选键交叉决定” |

## BCNF：3NF 管不到主属性

3NF 只约束“**非主属性**不传递依赖候选键”。如果两个**主属性**互相决定，3NF 检查不出来。

`warehouse_keeper(仓库名, 管理员, 物品名, 数量)`，业务约束是“一个仓库只有一个管理员，一个管理员也只管一个仓库”：

- 候选键有两个：`(仓库名, 物品名)` 与 `(管理员, 物品名)`；主键取前者。
- 主属性：`仓库名`、`管理员`、`物品名`；非主属性：`数量`。
- 1NF、2NF、3NF 全部满足：`数量` 与两个候选键都完全依赖，也不传递依赖。

但它仍有异常：

| 异常 | 后果 |
|---|---|
| **插入异常** | 新仓库还没放物品，主键含 `物品名` 不能为空，插不进去 |
| **更新异常** | 换管理员要改该仓库的所有行 |
| **删除异常** | 物品卖空、删掉最后一行，仓库与管理员信息一起丢失 |

根因是主属性 `仓库名` 对候选键 `(管理员, 物品名)` 是**部分依赖**。BCNF 的定义因此更狠：**每一个决定因素都必须是候选键**。`仓库名 → 管理员` 成立，但 `仓库名` 单独不是候选键，所以违反 BCNF。

拆成 `warehouse(仓库名, 管理员)` 与 `stock(仓库名, 物品名, 数量)` 后，两个决定因素 `仓库名`、`(仓库名, 物品名)` 都是所在表的候选键。

> 🔑 3NF 问“非主属性有没有绕路”，BCNF 问“**所有**决定因素是不是候选键”。后者才是“一张表只表达一个意思”的严格版本。

## 一次拆表：从 “一张大表” 到 3NF

```sql
-- 反例：所有信息塞一张表，插入/更新/删除都有异常
CREATE TABLE orders_bad (
  order_id INT, user_id INT, user_name TEXT, user_city TEXT,
  sku_id INT, sku_name TEXT, qty INT, price DECIMAL
);
-- 问题：user_city 随 user 重复；改名要改多行；删掉最后一个订单会丢掉用户信息

-- 3NF 拆分：每个事实一处
CREATE TABLE users   (user_id PK, name, city);
CREATE TABLE orders  (order_id PK, user_id FK, created_at);
CREATE TABLE items   (order_id FK, sku_id FK, qty, price, PRIMARY KEY(order_id, sku_id));
CREATE TABLE skus    (sku_id PK, name);
```

代价是查询要 JOIN：查 “订单 + 用户名 + 商品名” 从 1 次变 3 次表访问。**范式用 JOIN 换一致性**。

## 反范式：什么时候故意冗余

| 场景 | 做法 | 代价 |
|---|---|---|
| 读多写少、报表/列表页 | 宽表/物化视图，冗余用户名 | 更新要同步冗余 |
| 高频 JOIN 的详情页 | 订单表冗余 `buyer_name` | 改名要异步刷新 |
| 数仓/OLAP | 星型/雪花模型，维度冗余 | 存储变大 |
| 跨库查询 | 冗余快照字段（见 [32.6 共享数据库反模式](../../L2-架构风格/32-数据模式/32.6-共享数据库反模式.md)） | 一致性靠事件/对账 |

判据：**“这个冗余字段的更新频率 × 一致性要求” 是否可接受**。可接受就冗余，不可接受就走 JOIN/API。

## 反范式的量化收益：一次原文实验

课程在 MySQL 5.7 上造了 100 万用户、100 万条评论（评论只属于 `product_id=10001`），比较两种取“某商品最新 1000 条评论 + 用户昵称”的写法：

| 写法 | SQL 形态 | 原文耗时 |
|---|---|---|
| 3NF | `product_comment LEFT JOIN user ON user_id`，取 1000 行 | **0.395 s** |
| 反范式 | `product_comment2` 里冗余 `user_name`，单表取 1000 行 | **0.039 s** |

差 **10 倍**（数字来自课程原文实验：MySQL 5.7、100 万行，2019；本节未重跑这批数据，复现时看量级而非绝对值）。原因不是“JOIN 一定慢”，而是执行路径不同：3NF 版要在评论表与用户表上各走一次聚集索引再嵌套循环；反范式版只扫一次评论表。**这笔账只在结果集大、JOIN 频繁时成立**——数据量小时冗余只会让设计更复杂。

代价同样具体：用户改昵称，要同步改评论表里的冗余 `user_name`；改得越频繁，同步成本越高，漏同步就是永久不一致。所以判据不是“能不能冗余”，而是：

```
收益 = 每次查询省下的 JOIN 成本 × 查询频率
成本 = 冗余字段的写放大 × 更新频率 + 不一致的对账成本
```

> 🔑 反范式有两类正当理由，不要混为一谈：**性能**（少一次 JOIN）与**正确性**（历史快照必须冻结）。订单的收货人姓名、电话、地址属于后者——用户后来改了地址，不能改写已发生订单的收货信息。这类冗余即使查询不变快也必须保留。

## 反模式

| 反模式 | 后果 |
|---|---|
| 字段里存逗号分隔的多值 | 无法索引、无法约束、查询要 `LIKE` |
| 为了 “少 JOIN” 把所有表合成一张 | 更新异常、冗余失控 |
| 只到 1NF 就上线 | 部分依赖导致 “改一处漏一处” |
| 无脑 3NF 到极致 | 查询要 6 表 JOIN，性能崩 |
| 反范式但不做同步 | 冗余字段永久不一致 |
| 用 “范式” 当教条拒绝冗余 | 报表查询拖垮主库 |

## 三条铁律

> 🔑 **范式保证 “一处存一份”，反范式换取 “一次查一条”**。

> 🔑 **反范式必须配同步机制**（事件/CDC），否则就是脏数据。

> 🔑 **OLTP 偏范式，OLAP 偏反范式**；不要用一套标准套所有场景。

## 自检

**Q1** 1NF 为什么要求 “字段不可再分”？

▸ 答案：因为关系模型的操作（选择、投影、连接）都以 “**列是原子值**” 为前提：`tags="a,b,c"` 无法建索引、无法用 `WHERE tag='a'` 精确匹配、无法做外键约束。要么拆成关联表，要么用数组类型 + 专门的索引（如 GIN），但后者已不是 “纯关系” 用法。

**Q2** 2NF 与 3NF 的区别用一个例子说明？

▸ 答案：`(order_id, sku_id) → qty, sku_name`：`sku_name` 只依赖 `sku_id`（联合主键的一部分）→ 违反 **2NF**；`order_id → user_id → user_city`：`user_city` 依赖非主属性 `user_id`（传递依赖）→ 违反 **3NF**。前者拆出 sku 表，后者拆出 user 表。

**Q3** 为什么 3NF 的表 “更新更安全”？

▸ 答案：因为每个事实只有一处：改用户城市只改 `users` 一行，不会出现 “订单表里改了、用户表里没改” 的不一致。范式消除的是**更新异常/插入异常/删除异常**，不是 “为了好看”。

**Q4** 反范式一定会导致不一致吗？

▸ 答案：不一定，但要付代价：要么**同事务双写**（写放大、跨表事务），要么**异步同步 + 对账**（短暂不一致）。没有同步机制的反范式才是 “必然不一致”。

**Q5** 星型模型为什么在数仓里流行？

▸ 答案：因为它把 “分析查询常用的维度” 冗余到维表，事实表只存 “外键 + 度量”：JOIN 次数少、列少、适合列存与聚合。它本质是 **“为读路径反范式”**，代价是维度更新要同步到维表。

**Q6** 什么时候应该从 3NF 走向反范式？

▸ 答案：当出现 “**高频查询需要多表 JOIN、且写频率低**” 时：报表、列表页、详情页。判断依据是 “JOIN 的成本 × 频率” 是否超过 “冗余的存储 + 同步成本”，而不是 “范式好不好”。

**Q7** 分库分表后，范式还重要吗？

▸ 答案：更重要，但形式变了：跨库 JOIN 不可用，所以要么 “按查询边界冗余”，要么 “读侧宽表”（见 [32.1 CQRS](../../L2-架构风格/32-数据模式/32.1-CQRS.md)）。此时 “每个库内部仍要范式”，跨库用冗余/读模型替代 JOIN。

**Q8** `warehouse_keeper(仓库名, 管理员, 物品名, 数量)` 已经满足 3NF，为什么还要拆？

▸ 答案：因为 `仓库名 ↔ 管理员` 是两个**主属性**互相决定，且 `仓库名` 对候选键 `(管理员, 物品名)` 是部分依赖。3NF 只检查非主属性，查不出这个洞。BCNF 要求“每个决定因素都是候选键”，`仓库名` 单独不是候选键，所以拆成 `warehouse(仓库名, 管理员)` 与 `stock(仓库名, 物品名, 数量)`。
