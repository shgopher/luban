          44.26 MySQL 一条 SQL 的一生：Server 层与 InnoDB 日志系统

          一句话

          一条 SQL 的一生有两段：Server 层把一串字符变成“对某个引擎的第 N 次接口调用”，引擎层把这次调用变成“内存页改了 + 一条 redo 记下来”；真正保证提交不丢的不是数据页，而是 redo（prepare 且已 fsync）与 binlog（完整）这两条日志的先后顺序——两阶段提交把它们钉成同一个状态，组提交把一组事务的两次 fsync 压成一次。

          来源：一条查询与一条更新的执行链路、两阶段提交与崩溃恢复判据、组提交与刷脏页策略、不丢数据的参数边界，来自丁奇《MySQL 实战 45 讲》（极客时间，2019）第 01、02、12、15、23 讲与特别放送《我的 MySQL 心路历程》；本节 SQL、参数默认值与全部实测输出为本机 linux/arm64 容器内的 MySQL 8.0.46 补充。

          分层：Server 层决定“做什么”，引擎层决定“数据在哪”

          本节要点

          MySQL 只有两层：Server 层管语义（认证、解析、选计划、调接口），引擎层管存取（页、索引、日志、锁）；所有跨引擎的功能都在 Server 层，插件式引擎共用同一套 Server 层。

          层 组件 职责 出错时的典型现象
          Server 连接器 TCP 握手、认证、读权限、维持连接 Access denied for user；空闲超时后 Lost connection to MySQL server during query
          Server 查询缓存 key = SQL 文本，value = 结果集 表上任何一次更新，整表缓存全部清空；8.0 已整体删除
          Server 分析器 词法 → 语法 → 语义（表、列是否存在） You have an error in your SQL syntax；Unknown column 'k' in 'where clause'
          Server 优化器 选索引、定 join 顺序、产出执行计划 选错索引 → 扫几百万行（44.9 执行计划与慢查询 的主场）
          Server 执行器 校验表权限、逐行调引擎接口、累加 rows_examined SELECT command denied to user；慢日志里 rows_examined 暴涨
          引擎 InnoDB / MyISAM / Memory 数据页、索引、redo、undo、锁、MVCC 崩溃恢复、刷脏页、锁等待、页分裂（44.1 存储引擎B+树与LSM）

          InnoDB 从 5.5.5 起成为默认引擎：create table 不写 engine= 就是 InnoDB；要换引擎得显式写 engine=memory。插件式架构的含义是“引擎可换，Server 层不换”，所以同一份连接器、分析器、优化器代码服务于所有引擎——这也解释了为什么 binlog 属于 Server 层而 redo 属于 InnoDB：前者所有引擎都能用，后者只有 InnoDB 有。

          Server 层还兜着两类东西，判断“一个能力属于哪层”时很好用：

          类别 例子 为什么在 Server 层
          所有内置函数 日期、时间、数学、加解密 与存储格式无关，换引擎结果不变
          所有跨引擎功能 存储过程、触发器、视图 可能要跨多个引擎的表，只能由上层协调

          💡 一条推论：同一个 SQL 换成不同引擎，语义层的结果不变，持久化与并发行为会变。MyISAM 没有事务和 crash-safe、Memory 引擎数据只在内存——这也是为什么“表用哪个引擎”是个必须显式决定的运维项，而不是默认值随便。

          连接器：认证一次，权限快照管一生

          连库的第一步永远是连接器：TCP 握手 → 用你输入的用户名密码认证 → 去权限表查出你拥有的权限。认证失败就是 Access denied for user，客户端直接结束。

          mysql -h$ip -P$port -u$user -p     # 密码不要直接跟在 -p 后面，会留在 shell 历史与进程列表里

          ⚠️ 认证通过的一瞬间，权限就被“拍成快照”带在这条连接上。之后即使管理员改了你的权限，已存在的连接仍按旧权限判定，只有新建连接才用新权限。授完权发现“怎么还是没权限”，先确认是不是连接没重连。

          连接建好后没事干就是空闲状态，show processlist 里 Command 列为 Sleep 的那一行就是它。客户端太久没动静，连接器会主动断开，时限由 wait_timeout 控制，默认 28800 秒，即 8 小时（本机实测 28800）。断开后客户端再发请求，收到的是 Lost connection to MySQL server during query，要继续就得重连再发一次。

          长连接 vs 短连接：长连接指连接成功后客户端持续有请求就一直复用同一条；短连接指执行完很少几次查询就断开、下次重连。建连过程本身要走 TCP 握手 + 认证 + 读权限，成本不低，所以生产上默认用长连接——连接池的存在就是为了这个（44.12 连接池）。

          代价是内存。MySQL 执行过程中临时用的内存挂在连接对象上，只有连接断开才释放。全用长连接时，内存会随连接累积而涨，涨到被系统 OOM 杀掉，现象就是“MySQL 异常重启了”。两种解法：

          方案 做法 代价
          定期断开 用一段时间、或跑完一个大查询后主动断开，下次查询再重连 重连要重新认证，冷启动几毫秒到几十毫秒
          mysql_reset_connection MySQL 5.7+ 每次大操作后调用，把连接恢复到刚创建完的状态 不重连、不重新认证，但会话状态（临时表、变量）被清

          ⚠️ 连接池的“最大存活时间”必须小于 wait_timeout。池子以为连接还活着、服务端早已按 8 小时把它断开，取出来的连接第一次使用就会报 Lost connection to MySQL server during query，表现为“每天固定时间偶发几个请求失败”。要么把池的 maxLifetime 设成几分钟，要么调大 wait_timeout，二选一（44.12 连接池）。而连接上累积的内存，大头往往是会话里的临时表与排序缓冲（44.29 临时表、内部临时表与 Memory 引擎）。

          查询缓存：一个被 8.0 删掉的功能

          拿到查询后，MySQL 会先查查询缓存：之前执行过的语句和结果按 key-value 存在内存里，key 是语句文本，value 是结果集，命中就直接返回，后面的分析器、优化器、执行器全省了。

          听起来很美，实际是负收益：只要一个表有更新，这个表上所有查询缓存立刻清空。辛苦存下的结果可能还没被读一次就被一个 update 全废掉；更新压力大的库命中率极低。只有“很久才更新一次”的静态表（比如系统配置表）才配得上它。5.7 给了按需使用的开关：

          SET query_cache_type = DEMAND;              -- 默认语句不用缓存
SELECT SQL_CACHE * FROM T WHERE ID = 10;    -- 这一条显式要求缓存

          MySQL 8.0 把查询缓存整块删掉了，query_cache_type 这个参数不复存在。所以“缓存热点查询”这件事在 MySQL 内部已经没有位置，要挪到 Redis 之类的旁路缓存，而旁路缓存就要处理一致性（41.4 缓存一致性策略）。

          分析器：错误发生在第一现场

          没命中缓存就真开始执行了，第一站是分析器。它做两件事：

          1. 词法分析：把一串字符和空格切开，认出 select 是查询关键字，T 是表名，ID 是列名。
          2. 语法分析：按语法规则判断这句话是否合法。不合法就报 You have an error in your SQL syntax，提示里 use near 后面跟的才是第一个出错位置——看报错要看这一段，不是看后面一大串。

          少打字母的例子：

          mysql> elect * from t where ID=1;
ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that
corresponds to your MySQL server version for the right syntax to use near 'elect * from t where ID=1' at line 1

          语义检查（表在不在、列在不在）也在分析器这一层。select * from T where k=1 而 T 没有 k 列，报的是 Unknown column 'k' in 'where clause'——这个错在分析器就出了，走不到优化器，更走不到执行器。一个佐证：给没权限的用户执行同样的语句，收到的是 SELECT command denied，因为没权限的人连“这个列存不存在”都不该被告知。

          三类错误的发生位置，记这张表比记报错文案有用：

          错误类型 例子 报在哪 特征
          词法/语法错 elect * from t 分析器 ERROR 1064，提示 near '...' 是第一个出错位置
          语义错（对象不存在） 表/列名拼错、别名有歧义 分析器 Unknown column / Table doesn't exist
          权限错 无 SELECT 权限 执行器（或缓存返回时） ERROR 1142，且不会泄露“列是否存在”

          💡 只有更新语句才产生 redo 与 binlog，纯查询一个字节日志都不写。所以“双 1 拖慢性能”只对写密集库成立；读多写少的库把双 1 关掉，省下的 fsync 有限，风险却照旧——这类库的性能瓶颈通常在缓冲池命中率与执行计划上。

          优化器：只选路线，不改结果

          分析器之后 MySQL 知道“要做什么”，但还不知道“怎么做”。优化器决定两件事：

          • 表上有多个索引时用哪个；
          • 多表 join 时先查哪张、后查哪张。
          select * from t1 join t2 using(ID) where t1.c=10 and t2.d=20;

          既可以先从 t1 取 c=10 的记录拿 ID 去 t2 找，也可以先从 t2 取 d=20 的记录拿 ID 去 t1 找。两条路的结果集完全一样，耗时差几个数量级。优化器一旦选错，就是“SQL 写得对、跑得慢”的根因，所以索引与执行计划各自有主场：44.8 索引原理、44.7 SQL与查询优化。

          执行器：逐行调引擎，把次数记在 rows_examined 上

          执行器开工前先校验一次权限（对表 T 有没有查询权限），没权限就报 ERROR 1142 (42000): SELECT command denied to user 'b'@'localhost' for table 'T'；然后按表的引擎定义打开表，调引擎提供的接口。

          以 select * from T where ID=10、ID 无索引为例：

          1. 调 InnoDB 接口取第一行，判断 ID 是不是 10，不是就跳过，是就放进结果集；
          2. 调“下一行”接口，重复同样的判断，直到取完；
          3. 把结果集返回客户端。

          有索引的表逻辑一样，只是第一次调“取满足条件的第一行”，之后循环调“取满足条件的下一行”。这些接口是引擎定义好的，执行器只是循环调用者——所以“SQL 慢”至少有一半责任在引擎侧扫了多少行。

          💡 表结构在 Server 层和 InnoDB 层各存了一份，所以“执行器打开表”和“引擎打开表”在实现上是同一个动作的两面；有些资料把它拆成两步讲，看到时不必当成两个阶段。

          慢日志里的 rows_examined 就是执行器每次调引擎取数据行时累加出来的。本机实测：big 表 2 万行、c 列无索引，SELECT COUNT(*) FROM big WHERE c > 0 在慢日志里 rows_examined=20000、rows_sent=1、query_time=0.0089s。

          💡 rows_examined 不等于引擎内部扫描行数。执行器调一次，引擎内部可能扫多行（回表、索引下推、范围扫描都是这样），所以两个数会不一致，排查时两个都要看。

          🔑 权限校验不放在优化器之前，是因为 SQL 要碰的表不一定都在字面量里：带触发器时，要执行到那一行才知道动的是哪张表，优化器阶段无从判断。所以除了优化器前的 precheck，执行器阶段还要再校验一次；命中查询缓存时，权限校验发生在缓存返回结果那一刻。

          一条查询走完的五步

          步骤 谁在做 输入 输出 失败表现
          1 连接 连接器 用户、密码、库名 一条带权限快照的会话 Access denied for user
          2 查缓存 查询缓存（≤5.7） SQL 文本 结果集，命中即返回 无（8.0 无此步）
          3 解析 分析器 SQL 文本 语法树 + 表/列校验结果 ERROR 1064、Unknown column
          4 选计划 优化器 语法树 + 统计信息 执行计划 无报错，只有选错
          5 执行 执行器 执行计划 结果集 + rows_examined ERROR 1142

          一条 update 的一生：粉板、账本和一次两阶段提交

          本节要点

          update 和 select 走的是同一条 Server 层链路，差别全在引擎侧和后半段：先改内存页并把“改了什么”写进 redo（prepare），再把整条逻辑写进 binlog，最后把 redo 标成 commit——这三步的顺序就是“不丢数据”的全部秘密。

          前半段一样，只是缓存要失效

          update T set c=c+1 where ID=2 进来，照样先连接、照样让表 T 上的查询缓存全部失效（这正是不建议用查询缓存的原因），分析器认出这是更新语句，优化器决定走 ID 主键索引，执行器负责找到那一行并更新。查询那一套流程，更新一样走一遍，多出来的是两个日志模块。更新为什么不加锁就没法正确并发、隔离级别怎么和这些日志配合，是 44.10 事务与隔离级别 的主场，这里只用到它的结论：一个事务的修改，提交前对其他事务不可见。

          redo log：孔乙己的粉板

          《孔乙己》里咸亨酒店的掌柜有块粉板记赊账，还有一本账本记总账。有人赊账时他有两种做法：直接翻账本找到那个人、算出新数额、写回去；或者先在粉板上记一笔，打烊后再汇总进账本。生意忙的时候掌柜一定选后者——翻几十页账本找名字太慢。

          MySQL 面对的是同一个问题：每次更新都去磁盘找到对应记录再改，IO 成本和查找成本都高。于是有了同一套思路：先写日志（粉板），再择机写磁盘（账本），这就是 WAL（Write-Ahead Logging，通用原理在 44.2 WAL与崩溃恢复）。具体到 InnoDB：更新时先把记录写进 redo log 并改内存，更新就算完成；磁盘上的数据页在系统空闲时再刷。

          粉板会写满，所以 redo log 是固定大小、循环写的：可以配成一组 4 个文件、每个 1GB，这块“粉板”总共记 4GB。

          指针 含义 移动方式
          write pos 当前记录写到哪 一边写一边后移，写到 3 号文件末尾就回到 0 号文件开头
          checkpoint 当前要擦除到哪 往后推，擦之前必须把这段日志对应的脏页刷到数据文件

          write pos 到 checkpoint 之间是还能写的空位（注意是环形的：从 write pos 到末尾，加上开头到 checkpoint）。一旦 write pos 追上 checkpoint，粉板满了，不能再执行新的更新，必须先停下来推进 checkpoint 腾地方。

          checkpoint 不是随便往后挪一个位置就行：把 checkpoint 从 CP 推到 CP'，必须先把这两点之间所有日志对应的脏页都刷到磁盘，之后这段 redo 空间才能复用。所以“推进 checkpoint”从来不是免费的，它等价于“一次批量刷脏”。

          按水位把 redo 分三档，运维上很好用：

          水位（LSN − Last checkpoint） 状态 该做什么
          < 容量 50% 安全 什么都不用做
          50%~75% 偏紧，说明刷脏跟不上写入 检查 innodb_io_capacity 是否偏小、脏页比例是否偏高
          > 75% 或贴满 随时进入“更新全堵” 立刻降写入或扩容 redo 容量，别等它满

          有了 redo，InnoDB 就能保证异常重启后已提交的记录不丢，这个能力叫 crash-safe。类比一下：只要赊账记在了粉板或账本上，掌柜就算突然停业几天，回来照样能把账目对上。

          💡 8.0.30 起不再用 innodb_log_file_size 拼文件数，改成一个总容量参数 innodb_redo_log_capacity。本机 8.0.46 默认 104857600，即 100MB——比原文举例的 4GB 小两个数量级，这也是容器/小实例上“抖”的常见原因。

          binlog：掌柜的账本

          redo 是 InnoDB 特有的，Server 层还有自己的日志：binlog（归档日志）。它是逻辑日志，记的是“给 ID=2 这一行的 c 字段加 1”这种原始逻辑，采用追加写——文件写到一定大小就切下一个，从不覆盖以前的日志。

          为什么会有两份日志？历史原因是 MySQL 自带的 MyISAM 没有 crash-safe 能力，binlog 只能用于归档；InnoDB 是另一家公司以插件形式引入的，它自带 redo 来实现 crash-safe，于是两套日志并存至今。

          一个事务的 binlog 不能被拆开，所以每个线程有自己的 binlog_cache（本机默认 binlog_cache_size=32768，即 32KB，超了暂存磁盘），事务提交时才把整块写进 binlog 文件并清空。redo 没有这个约束，用的是全局共享的 redo log buffer，还能“搭便车”——别的线程提交时顺手把它一起刷下去。

          维度 redo log binlog
          归属 InnoDB 引擎特有 Server 层实现，所有引擎可用
          内容 物理日志：在某个数据页上做了什么修改 逻辑日志：语句的原始逻辑；ROW 格式记前镜像 + 后镜像两行
          写入方式 循环写，空间固定会用完 追加写，切文件不覆盖
          用途 crash-safe（崩溃恢复数据页） 归档、主从复制、异构下游（46.4 CDC）
          对应关系 事务 ID（XID） 同一 XID

          🔑 redo 记的是“这个页做了什么改动”，不是“页更新之后的状态”。binlog 的 ROW 格式记的是行的前后镜像（本机实测 update 一条记录，binlog 里是 @2=0 改 @2=1 两行）。两者都不能当数据页快照用。

          五步链路：谁在第几步落盘

          步 执行者 动作 落盘点
          1 执行器 找引擎取 ID=2 这行；页在内存就直接给，不在就先从磁盘读进来 可能一次随机读
          2 执行器 把 c 加 1，调引擎接口写回新行 只改内存页（变脏页）
          3 InnoDB 更新内存页，同时把这次修改记进 redo，状态置 prepare，告诉执行器“可以提交了” redo buffer
          4 执行器 生成这条操作的 binlog 并写入磁盘 binlog cache → binlog 文件
          5 执行器 调引擎提交接口，redo 从 prepare 改成 commit redo 文件

          后三步看着“绕”，因为它把 redo 的写入拆成了 prepare 和 commit 两次——这就是两阶段提交。

          按写盘次数算，一次更新实际是 3 次写：redo 在 prepare 阶段一次、commit 阶段再一次，binlog 一次。并发更新时这 3 次会被合并——多个事务的 redo 合成一次 fsync、多个 binlog 合成一次 fsync，这就是后面组提交要讲的事。

          这里有两个“commit”，混淆了就理解不了整条链路：

          说法 指什么 例子
          commit 语句 MySQL 语法里的提交命令，和 begin/start transaction 配对 begin; update ...; commit; 里的最后一句
          commit 步骤 事务提交过程中的最后一个小步骤，执行完事务才算提交完成 五步链路里的第 5 步

          单条 update T set c=c+1 where ID=2 没有显式 begin，它自己就是一个事务，语句执行完就走到“commit 步骤”；而“commit 语句”在执行时，内部包含“commit 步骤”。问“update 的流程图里怎么会有 commit”是把这两个概念看成了一个。

          两阶段提交：让两份日志说同一句话

          先说它要解决的问题：DBA 说“能恢复到半个月内任意一秒”，靠的是“定期全量备份 + 从备份时刻起重放 binlog”。扩容加备库也是同一套路：全量备份 + 应用 binlog。所以 binlog 必须和主库的真实状态逐事务对得上，否则恢复出来的库、新拉的备库都会和原库不一致。

          “恢复到任意一秒”的具体操作只有三步，binlog 的作用在这里最直观：

          ① 用最近一次全量备份恢复到临时库（比如昨天 23:00 的备份）
② 从备份时间点开始，把 binlog 依次重放到“误删之前”那一刻
③ 把临时库里需要的表数据取出，按需写回线上库

          第 ② 步按时间窗口截取，靠的就是 binlog 文件的时间戳或事件时间：

          mysqlbinlog --start-datetime='2026-11-27 23:00:00' \
            --stop-datetime='2026-11-28 11:59:59' \
            binlog.000007 binlog.000008 > replay.sql

          前提是备份系统保留着这段时间的全部 binlog，且定期做了全量备份。

          备份周期取“一天一备”还是“一周一备”，影响的是恢复时长：备得越勤，要重放的 binlog 越少，恢复越快；能“后悔”的时间窗口反而越短（只能回到最近一次全量的时点之后）。这两个指标方向相反，靠业务重要性定。

          用反证法看：假设不用两阶段提交，只有两种顺序，且都在“第一个日志写完、第二个没写完”时崩溃。设 ID=2 这行原来是 c=0。

          顺序 崩溃点 主库崩溃恢复后 c 用 binlog 恢复出的库 c 后果
          先 redo 后 binlog redo 写完、binlog 未写完 1（redo 保证恢复） 0（binlog 里没这条语句） 恢复库比原库少一次更新
          先 binlog 后 redo binlog 写完、redo 未写 0（事务无效） 1（binlog 里多一个事务） 恢复库比原库多一次更新

          两种顺序都会让“库的真实状态”和“日志重放出的状态”分叉。redo 和 binlog 都能表示一个事务是否提交，两阶段提交就是让这两个“提交状态”在逻辑上始终一致。

          🔑 两阶段提交不是 MySQL 独有的技巧，它是跨系统保持逻辑一致的通用方案：所有参与者都说“我准备好了”，再统一提交。日常写业务代码也会用到同一模式（44.20 分布式事务的实现）。

          崩溃恢复的三条判据

          两阶段提交把事务切成三个瞬间：prepare 之后还没写 binlog（时刻 A）、binlog 写完但 redo 还没 commit（时刻 B）、commit 完成。重启时 InnoDB 按顺序扫 redo，规则只有三条：

          redo 里的事务状态 binlog 情况 恢复动作 时刻
          有完整 prepare + 有 commit 标识 不必再看 直接提交 已提交
          只有完整 prepare binlog 存在且完整 提交（2PC 的核心判据） B
          只有完整 prepare binlog 不存在或不完整 回滚 A

          时刻 A 崩溃很好理解：binlog 没写、redo 也没提交，事务回滚，binlog 里没这条，也不会传给备库，主备一致。

          时刻 B 才是容易想歪的地方：binlog 已经写完整了，它之后一定会被从库或恢复库拿去重放。所以主库必须提交这个事务，否则备库有、主库没有。“prepare 的 redo + 完整的 binlog = 提交”这条规则，本质是让主库跟着 binlog 走。

          两个配套问题：

          • binlog 完整怎么判？ 一个事务的 binlog 格式是自洽的：statement 格式最后有 COMMIT，row 格式最后有一个 Xid event。5.6.2 之后还引入 binlog_checksum（本机默认 CRC32），能发现日志中段因磁盘问题写坏的情况——本机实测每个事件都带 CRC32 0x... 校验值。
          • 两份日志怎么对上？ 靠共同字段 XID。恢复时按顺序扫 redo：既有 prepare 又有 commit 的直接提交；只有 prepare 的，拿它的 XID 去 binlog 找对应事务，找到且完整就提交，找不到就回滚。

          七个追问一次说清

          第 15 讲答疑里把这块问透了，答案可以压成一张表：

          追问 结论
          为什么 prepare + 完整 binlog 就能恢复，非要这么设计？ 因为 binlog 已经会被备库/恢复库使用，主库必须跟着提交，两边才一致
          既然崩溃时要求两份都完整，为什么不干脆先写完 redo 再写 binlog、恢复时要求都完整？ 不行。redo 一旦提交就不能回滚（回滚会覆盖别的事务的更新），此时 binlog 写失败就再也补不齐；2PC 是给双方一个“都 ok 再一起提交”的机会
          只留 binlog，用它做崩溃恢复行不行？ 不行。binlog 没有能力恢复数据页：它不记录页级修改细节。事务 1 已被认为提交完成、不会再重放，此时崩溃，事务 1 的修改是数据页级丢失，binlog 补不回来。要让 binlog 记页改动，那等于再造一个 redo
          那反过来只留 redo 呢？ 从崩溃恢复看可以（关掉 binlog 依然 crash-safe），但生产库不能关：redo 是循环写、不归档；MySQL 高可用依赖 binlog 复制；异构下游靠消费 binlog 更新
          redo 该设多大？ 太小会很快写满、被迫强刷，WAL 的优势发挥不出来。TB 级磁盘的常规配置是 4 个文件、每个 1GB
          正常运行时的数据最终落盘，是从 redo 更新过去的吗？ 不是。redo 不记录数据页的完整内容，没能力自己改磁盘页。正常路径是“内存脏页写盘”，与 redo 无关；只有崩溃恢复时，才把可疑页读进内存、用 redo 改内存内容，之后又回到“脏页写盘”
          redo log buffer 是什么？先改内存还是先写日志文件？ 是一块内存，先存 redo。事务执行中改内存的同时写 buffer；真正写进 redo 文件（ib_logfile*）是在 commit 时。执行中间也可能被动写盘：buffer 用量接近 innodb_log_buffer_size 一半时后台只 write 不 fsync；别的并发事务提交时会把你的日志一起 fsync

          💡 顺带破一个常见误读：update t set a=2 where id=1 而 a 本来就是 2，返回“匹配 1 行、修改 0 行”，并不等于“MySQL 提前发现没变化就不干活”。实际是 InnoDB 认真执行了这次修改（该加锁加锁、该写 redo 写 redo），只是行格式没变。所以**“值没变”不代表没有日志和锁的开销**，这是执行器“总是调引擎接口”的直接后果。

          一个事务会写很多次 redo，这就是 redo log buffer 存在的理由：

          begin;
insert into t1 ...;   -- 内存页改了，redo 写进 buffer；事务没提交，不能直接写 redo 文件
insert into t2 ...;   -- 再来一条，继续追加到 buffer
commit;               -- 这时才 write 到 redo 文件，并按参数决定是否 fsync

          事务执行期间不主动刷盘是为了省 IO，但会有两种“被动写盘”：buffer 用量接近 innodb_log_buffer_size 一半时后台只 write；别的并发事务提交时，把这批日志一起 fsync 下去。所以没提交的事务，它的 redo 也可能已经在磁盘上了——这不影响正确性，恢复时找不到 commit、binlog 里也没有，照样回滚。

          💡 第 15 讲里另一半关于索引的讨论（互相关注为什么用唯一索引 + 行锁而不是先查再插、普通索引与唯一索引怎么选）属于 44.8 索引原理 与 44.11 锁 的主场，这里只记一句结论：“先查再插”在并发下不安全，因为没有记录时行锁无法生效，要用唯一索引 + insert ... on duplicate key update 先把锁占住。

          还有一个“为什么不能只靠 binlog”的硬理由：binlog 是能关的。有权限的会话执行 SET sql_log_bin=0，本线程后续的修改就不会进 binlog，只进 redo。所以拿 binlog 当唯一的恢复依据并不可靠——它是归档与复制的依据，不是崩溃恢复的依据。

          redo 为什么不能省：直接改数据页的代价

          如果去掉 redo、每次更新直接改磁盘上的数据页，代价是三项叠加：

          做法 写放大 崩溃后果 事务吞吐
          只改数据页 一次更新要定位页 → 改页 → 刷整页（16KB），随机写 页写一半断电 → 页内结构损坏，无法判断改到哪一步 受随机 IOPS 限制，机械盘只有几百
          改内存页 + 写 redo 顺序追加几十到几百字节 重放 redo 即可补齐，页损坏由 doublewrite 兜底 受顺序写 + 组提交限制，可到数万 TPS

          🔑 redo 的价值不在“少写一次磁盘”，而在把随机写换成顺序写，并且让“提交”只依赖一次顺序追加 + fsync，而不依赖“把 16KB 的页原地改对”。数据页的刷写因此可以推迟、可以合并、可以乱序——崩溃恢复会用 redo 补上。

          redo 与 binlog 各自不可替代，一句话对照：redo 管“页怎么改回来”（物理、循环、引擎私有），binlog 管“逻辑上发生过什么”（逻辑、追加、全引擎共享、可归档可复制）。

          不丢数据：两个 fsync 开关与一次组提交

          本节要点

          “不丢”不是某个开关给的，而是两个 fsync 的时序给的：提交前 redo 必须 fsync 过一次（prepare 阶段），binlog 也必须 fsync 过一次；而 write 只是写进 page cache，进程崩了还在、主机掉电就没了。

          redo 的三种状态：先分清“写到哪了”

          状态 物理位置 进程 crash（mysqld 被杀） 主机掉电 / OS crash
          在 redo log buffer mysqld 进程内存 丢 丢
          已 write，未 fsync 文件系统 page cache 还在（OS 接管） 丢
          已 fsync 磁盘 在 在

          日志写进 buffer 很快，write 到 page cache 也差不多快，只有 fsync 慢——所以“一般情况下我们认为 fsync 才真正占磁盘 IOPS”。

          innodb_flush_log_at_trx_commit：提交时 redo 走到哪一步

          取值 每次提交做的事 mysqld 异常重启丢什么 主机掉电丢什么
          1（本机默认） 直接 fsync 到磁盘 不丢 不丢
          2 只 write 到 page cache 不丢（OS 还在） 丢最近约 1 秒内提交的事务
          0 只留在 redo log buffer 丢最近约 1 秒内提交的事务 丢最近约 1 秒内提交的事务

          后台线程每秒做一轮：把 buffer 里的日志 write 到 page cache，再 fsync 到磁盘。所以 0 和 2 的丢数据窗口都以“约 1 秒”为界。原文的建议很直接：不要设 0。0 连 mysqld 自己重启都会丢；2 的性能和 0 差不多（write 到 page cache 也很快），但至少扛得住进程崩溃。生产用 1。

          sync_binlog：binlog 的 write 与 fsync 分开控

          取值 每次提交做的事 崩溃/掉电代价
          0 只 write，从不主动 fsync，靠 OS 刷 掉电丢 page cache 里的 binlog，量不可控
          1（本机默认） 每次提交都 fsync 不丢
          N（N>1） 每次提交 write，累积 N 个事务才 fsync 主机异常重启丢最近 N 个事务的 binlog

          实务里 sync_binlog 常见设成 100~1000，不建议设 0——设 0 时丢多少完全由 OS 决定，无法估算容量。设 N 至少能算出“最多丢 N 个事务”。

          双 1：一次提交，两次刷盘

          sync_binlog=1 且 innodb_flush_log_at_trx_commit=1 就是常说的**“双 1”**：一个事务完整提交前要等两次刷盘，一次是 prepare 阶段的 redo，一次是 binlog。

          这里有个容易漏的细节：redo 在 prepare 阶段就已经 fsync 过一次（崩溃恢复要靠“prepare 的 redo + 完整 binlog”，所以 prepare 必须落盘）。既然每秒还有后台轮询、prepare 又已经落盘，InnoDB 认为 commit 阶段不需要再 fsync，只 write 到 page cache 就够。所以“双 1 两次刷盘”指的是 prepare 的 redo 和 binlog，不是 redo 的 prepare 与 commit 各一次。

          组提交：把 N 次 fsync 压成一次

          双 1 下每秒 2 万 TPS 意味着每秒 4 万次刷盘，而磁盘能力只有 2 万——账面对不上，靠的是组提交。先定义 LSN：单调递增，每次写入长度为 length 的 redo，LSN 就加 length；LSN 也会写进数据页，用来保证一个页不会重复应用同一段 redo。

          三个并发事务在 prepare 阶段都写完 redo buffer，LSN 分别是 50、120、160：

          事务 LSN 角色 结果
          trx1 50 leader（第一个到达） 等它真要写盘时，组里已有 3 个事务，LSN 已是 160；它带 LSN=160 去 fsync
          trx2 120 组员 trx1 返回时，所有 LSN ≤ 160 的 redo 都已落盘，直接返回
          trx3 160 组员 同上

          一次组提交里组员越多，省下的 IOPS 越多；单线程压测时组里永远只有自己，组提交完全无效。

          binlog 侧同样分三段，这就是 binlog group commit：

          阶段 做什么 谁参与
          flush 把 binlog 从 cache 写进文件（write） 组内所有事务按序写
          sync 对 binlog 文件 fsync 组内第一个（leader）替全组刷
          commit 引擎层提交（redo 置 commit），按顺序放行 组内按序

          MySQL 为了让 binlog 也能攒组，还做了一件“拖时间”的事：5.7 起把 redo 的 fsync 从 commit 之前拖到 binlog write 之后，于是“写 binlog 文件”和“fsync binlog”之间有了空隙，别的事务的 binlog 就能挤进同一组。binlog_order_commits=ON（本机默认 ON）保证进入 commit 阶段的事务按 binlog 顺序提交。通常 binlog 组提交效果不如 redo，因为 write 到 fsync 的间隔很短、能凑到一组的事务少。

          两个专门用来“攒组”的参数：

          参数 含义 注意
          binlog_group_commit_sync_delay 延迟多少微秒再 fsync 设 0 时下面那个参数也失效
          binlog_group_commit_sync_no_delay_count 攒到多少个事务就 fsync 与 delay 是或关系，谁先满足谁触发

          代价是故意多等：语句响应时间变长，但不丢数据（写已经 write 进 page cache，只是晚点 fsync）。这正是“提升 IO 瓶颈性能但不牺牲可靠性”的那一档手段。

          两个参数与 sync_binlog 的执行顺序也要说清：先达到 sync_binlog 的次数要求，再进入“delay 与 no_delay_count 取或”的等待逻辑。所以 sync_binlog=N 与 sync_no_delay_count=M 同时设置时，真实节奏由两者先到的那个决定；而 sync_binlog=0 时也会进入这段等待逻辑，等完之后不调 fsync——配了 delay 也换不来持久化。

          IO 瓶颈时能动的三档手段

          原文把这条路按风险分了三级，从上到下风险递增：

          档 手段 收益 风险
          一 调 binlog_group_commit_sync_delay / sync_no_delay_count，减少 binlog 刷盘次数 省 fsync，可靠性不变 语句响应时间变长（故意等）
          二 sync_binlog 设成 N（常见 100~1000） 大幅省 binlog fsync 主机掉电丢最近 N 个事务的 binlog
          三 innodb_flush_log_at_trx_commit=2 省 redo fsync 主机掉电丢最近约 1 秒的事务

          innodb_flush_log_at_trx_commit=0 不在这个列表里：它连 mysqld 自身异常重启都会丢，而设成 2 的性能与它接近、却扛得住进程崩溃，没有理由选 0。

          🔑 WAL 之所以能一边“多写两份日志”一边还提升性能，只靠两点：redo 与 binlog 都是顺序写（顺序写远快于随机写），以及组提交把一组事务的 fsync 合并成一次。缺任何一条，WAL 都会变成“多写还不快”。

          参数组合与丢数据边界

          redo 策略 binlog 策略 mysqld crash 主机掉电 适用
          1 1 不丢 不丢 交易、账务、任何不能丢的库
          1 N(100~1000) 不丢 丢 ≤N 个事务的 binlog 可容忍重放缺失的日志型库
          2 1 不丢 丢 ≤1 秒事务 高写入、能接受秒级损失的场景
          2 N 不丢 丢 ≤1 秒事务 + ≤N 个事务 binlog 大促非核心库、从库追主库
          0 任意 丢 ≤1 秒事务 丢 ≤1 秒事务 不建议

          💡 从库要不要双 1？原文评论区里有团队反馈：内网从库坚持双 1 会追不上主库，于是把从库设成非双 1。这个做法成立的前提是从库的数据可以从 relay log 重放回来（掉电后位点回退、重新回放，不产生主从分叉），代价是切主瞬间可能丢掉从库上尚未持久化的那部分回放。核心库的从库是否照做，要按“切主时能不能接受这段损失”来定，不能照抄。

          写 binlog 成功、redo 却没 fsync 会怎样

          这个组合是两阶段提交真正要兜的底，逐个场景看：

          场景 崩溃后 redo 状态 binlog 状态 恢复动作 数据
          redo prepare 已 fsync，binlog 写到一半 prepare 不完整 回滚 无这次更新，binlog 里也没有
          redo prepare 已 fsync，binlog 完整，commit 还没 fsync prepare 完整 提交 有这次更新
          redo prepare 的 fsync 就失败了 无有效记录 未写 事务报错返回 无，客户端收到失败
          binlog fsync 失败、redo 仍 prepare prepare 不完整 回滚 无，客户端收到失败

          🔑 记住那条“唯一判据”：redo 有 commit → 提交；只有 prepare → 看 binlog，完整就提交、不完整就回滚。除此之外的崩溃点，都不会产生“主库有、binlog 没有”或反过来。

          掉电的最后一公里

          💡 fsync 只保证数据交到了存储设备的持久介质。如果磁盘/阵列自带易失写缓存且没开回写保护，fsync 返回成功、掉电仍可能丢——这类问题在 MySQL 层看不出来，只能靠关掉设备写缓存或带电池保护（BBU）的阵列。另外 fsync 卡住（IO hang）时提交会一直等，表现为 TPS 掉零但 CPU 不高，这属于运维处置的范畴（44.25 MySQL运维与故障处置）。

          最后把“crash-safe 到底承诺了什么”钉死，客户端只会收到三种结果：

          1. 收到成功：事务一定已持久化；
          2. 收到失败（主键冲突、回滚等）：事务一定失败；
          3. 收到执行异常（连接断开、超时）：数据库只保证内部一致（数据与日志、主库与备库），应用要重连后查状态再决定继续。

          所以“binlog 写完盘、还没答复客户端就崩了，重连发现事务已提交”不是 bug；“整个事务都提交成功、备库也执行了，只是回包时网络断了”，客户端看到的也是异常，同样不算 bug。

          还有一个容易被误判的场景：事务执行到一半、还没提交时崩溃。这时 redo 可能已有一部分落盘（搭便车被刷下去的），但 binlog 还在 binlog_cache 里、根本没发给备库。崩溃后 redo 里没有 commit、binlog 也没有这个事务，主库回滚，从业务角度看这个事务从未提交——主备一致，不需要额外处理。

          “抖”一下：刷脏页的四种触发与控制

          本节要点

          平时快是因为只写内存和日志；偶尔“抖”是因为某个瞬间要去刷脏页——四种触发里，“redo 写满”最致命（更新全堵），其余三种靠“脏页比例 + redo 增速”两个旋钮调速率。

          脏页、干净页与四种触发

          内存页和磁盘页内容不一致，这个内存页就叫脏页；内存写到磁盘后两边一致，叫干净页。两者都在内存里。把内存中的数据写盘的动作就是 flush——flush 之前，账本（数据文件）和记忆（内存）是对不上的。

          掌柜什么时候会把粉板上的账誊到账本？对应到 InnoDB 就是四种 flush 触发：

          # 触发条件 对应机制 对性能的影响
          1 粉板记不下了 redo log 写满，推进 checkpoint 腾空间 最坏：系统停止所有更新，更新数跌为 0
          2 事情太多记不住了 内存不足，淘汰数据页时要先把脏页刷盘 常态；一次要淘汰的脏页太多时，单条查询响应明显变长
          3 生意不忙时 MySQL 认为系统空闲 无感，正是设计意图
          4 年底关门结账 正常关闭，把脏页全部刷盘 无感；下次启动直接读磁盘即可，省掉一遍恢复

          内存不足时为什么不干脆把脏页丢掉、下次要用时再从磁盘读入并应用 redo？因为那是拿性能换正确性：刷脏页写盘保证了每个页只有两种状态——在内存里，内存里就是正确结果，直接返回；不在内存里，磁盘上就是正确结果，读进来就能用。这样任何一次读的路径都最短（缓冲池的淘汰与预读细节在 44.3 缓冲池与页面管理）。

          缓冲池里的页因此分三种：还没用过的、用过且干净的、用过且脏的。InnoDB 的策略是尽量用满内存，所以长时间运行的库几乎见不到“未使用”的页；要读的页不在内存，就得淘汰最久不用的页——淘汰干净页直接复用，淘汰脏页必须先把脏页刷盘。

          刷脏页的速度：两个因子取最大

          刷太慢会有两个后果：脏页越积越多、redo 越写越满。所以 InnoDB 只看两个因素，各算一个 0~100 的数，取较大者作为“全力刷盘能力”的使用百分比：

          F1(M):  M = 当前脏页比例
        if M >= innodb_max_dirty_pages_pct: return 100
        else:                                return 100 * M / innodb_max_dirty_pages_pct

F2(N):  N = 当前写入 LSN 与 checkpoint 对应 LSN 的差值（还有多少 redo 没落页）
        N 越大，返回值越大（算法复杂，只需记住单调性）

R = max(F1(M), F2(N))
实际刷盘速度 = innodb_io_capacity * R%
          因子 输入 上限参数 本机 8.0.46 默认
          F1 脏页比例 Innodb_buffer_pool_pages_dirty / Innodb_buffer_pool_pages_total innodb_max_dirty_pages_pct 90（原文写作 75，那是 5.7 的默认值）
          F2 redo 增速 当前 LSN − checkpoint LSN 由 innodb_io_capacity / _max 间接约束 见下两行
          全力刷能力 磁盘 IOPS 的估计值 innodb_io_capacity 200
          上限 突发时可飙到的值 innodb_io_capacity_max 2000

          8.0 还多一个 innodb_max_dirty_pages_pct_lwm（本机默认 10）：脏页比例超过这个低水位就开始按比例提前刷，而不是等到逼近上限才动手。

          ⚠️ innodb_io_capacity 设小了比设大了更糟。原文有个真实案例：主机是 SSD，这个参数却设成 300，InnoDB 以为磁盘就这么点能力，刷脏页比脏页产生的速度还慢，脏页持续累积，写入变慢、TPS 很低，但主机 IO 压力并不大——看起来“磁盘闲着却写不动”，根因就在这个参数。设值方法是照着磁盘的 IOPS 设，用 fio 测：

          fio -filename=/data/fio_test -direct=1 -iodepth 1 -thread -rw=randrw \
    -ioengine=psync -bs=16k -size=1G -numjobs=1 -runtime=60 -group_reporting -name=rw

          -filename 一定要指向一个具体文件，指到块设备分区（如 /dev/sdb1）会直接往分区首扇区写随机数据，那是破坏性的。

          连坐：一个脏页带走一串邻居

          准备刷一个脏页时，如果它旁边的页也是脏页，InnoDB 会把这个“邻居”一起刷；邻居的邻居也照此办理，一路蔓延。开关是 innodb_flush_neighbors：1 打开连坐，0 只刷自己。

          磁盘 建议值 理由
          机械盘（随机 IOPS 只有几百） 1 相邻页一起刷能把随机 IO 合并成顺序 IO，收益大
          SSD（IOPS 高、不是瓶颈） 0 只刷这次真正要用的页，刷脏动作结束得早，单条语句的响应时间随之变短

          MySQL 8.0 的默认值已经是 0（本机实测 0）。

          💡 同一个坑不止 InnoDB 有。《我的 MySQL 心路历程》里还有个二手案例：2012 年双十一把 SSD 当二级缓存（Flashcache），性能反而不如纯机械盘。看源码才发现，Flashcache 也有一条"脏页比例到 80% 就强制刷盘"的规则，只不过它是按桶算的——一个桶 20MB，顺序写会飞快地把某一个桶写到 80%，于是频繁触发强制刷盘，把 SSD 的随机写优势全吃掉。处置办法是按访问形态分盘：日志这类顺序写回机械盘，随机写留在 Flashcache。判据：任何"脏页阈值 + 刷盘"的缓存层，都要先问阈值是按整块算还是按桶算，再看你的写是不是顺序的。

          为什么 redo 写满会“抖”，以及 redo 太小为什么长期抖

          redo 写满时，checkpoint 必须往前推，而推进前要把这段日志覆盖的所有脏页刷完——这期间整个系统不能接受更新，所有更新都堵住。从监控上看就是更新数瞬间跌为 0，业务侧表现为请求堆积、超时。这是 InnoDB 要尽量避免的状态，也是 innodb_io_capacity 与脏页比例控制要解决的问题。

          反过来，redo 设得太小会长期抖。原文的思考题：128GB 内存、innodb_io_capacity=20000 的实例，正常该配 4 个 1GB 的 redo，如果不小心配成 1 个 100MB，会发生什么？

          环节 后果
          100MB 很快被写满 F2(N) 迅速变大，checkpoint 被迫频繁推进
          每次推进都要刷大量脏页 刷脏 IO 与业务 IO 抢磁盘，语句响应抖动
          buffer pool 有 128GB、脏页随便就攒起来 内存优势完全用不上，WAL 退化成“近似直接写磁盘”
          极端时更新被堵 表现为周期性卡顿，压力测试里“先快后慢、延迟很大”

          同一个推理也解释了为什么单线程压测测不出组提交的收益、为什么大内存实例配小 redo 是典型的自废武功。

          💡 一个页到底是不是脏页，不用额外标记位：每个数据页头部有 8 字节的 LSN，每次修改都会变大，拿它跟 checkpoint 的 LSN 比就行——比 checkpoint 小的一定是干净页。redo 重放时也一样：碰到已经刷过盘的页，LSN 已经不小于要重放的位点，直接跳过，不会重复应用。

          两个来自作者经历的现场

          原文作者在《我的 MySQL 心路历程》（特别放送）里讲过两个案例，正好各对应本节一条判据：

          ① 崩溃恢复后的“空闲刷脏”，把首次全表扫描从 2 分钟拖到 30 分钟。 某系统启动时要把权限表全量读进内存，正常重启 2 分钟跑完，MySQL 崩溃重启后却要 30 分钟。原因是崩溃恢复结束时 Buffer Pool 里堆着大量脏页，而此刻 Server 层还没开始服务、实例里只有那一个全表扫描请求——MySQL 判定自己“很闲”，于是按空闲策略拼命刷脏页，磁盘带宽被刷脏吃掉，全表扫描跟着变慢。处置办法不是调 SQL，而是每 0.5 秒发一条极简查询，让实例“觉得忙”，刷脏速率随之降下来。这印证了刷脏速率由 innodb_io_capacity 与脏页比例共同决定，与你的 SQL 无关；反过来说，压测刚结束、实例刚恢复的那一刻，看到的慢查询不能直接归因于 SQL。

          ② “每天早上必须重启一次应用”，根因是一个默认值。 系统每晚六点后无人访问，次日九点上班报“连接数据库失败”。数据库默认 wait_timeout=28800 秒（8 小时），夜里连接早被服务端断开，而应用没有重连、继续用旧句柄；重启应用等于重建连接，于是“重启就好了”。判据：报错是 Lost connection 类而不是权限或语法错误时，先量“空闲时长 vs wait_timeout”，再去改应用的重连与连接池保活。

          🔑 这两个案例的共同点：参数语义懂了，定位就只剩一条命令。第一个要看的不是慢日志，是脏页与刷脏；第二个要看的不是 SQL，是连接空闲时长。

          验证二：四个 LSN 说明 redo 压了多少

          SHOW ENGINE INNODB STATUS 的 LOG 段有四个数，8.0.46 在 2 万行更新之后（双 1）：

          字段 含义 实测值
          Log sequence number 已经生成的最新 LSN（写到 redo buffer 的末尾） 36947884
          Log flushed up to 已经 fsync 到磁盘的 LSN 36947758
          Pages flushed up to 数据页已经刷到哪个 LSN 29547154
          Last checkpoint at checkpoint 位置（比它更早的 redo 空间可复用） 29547154

          它们必须满足 LSN ≥ Log flushed ≥ Pages flushed ≥ Last checkpoint。这组数读出来是：redo 里已记录 7,400,730 字节（36947884−29547154，约 7.1MiB）的修改还没落到数据页，checkpoint 停在 29547154——这些 redo 空间不能复用。容量是 104,857,600 字节（100MiB），所以离“写满”还剩 97,456,870 字节（约 92.9MiB）。

          把 innodb_flush_log_at_trx_commit 临时改成 0 再跑同样 2 万行更新，四个数立刻分层：

          Log sequence number          38644482
Log flushed up to            38125773      -- 比上面小 518,709 字节：这段 redo 还在 buffer 里
Pages flushed up to          29547154
Last checkpoint at           29547154

          Log flushed 落后 LSN 的那 518,709 字节（约 506KiB），就是“提交已返回客户端、但进程一崩就没了”的部分——这正是 =0 的代价，也是为什么它在生产上是禁选项。（掉电本身在本机无法验证：需要真实断电或拔盘，容器里测不了，只能按上表的语义推。）

          验证三：数据页没落盘也能读到

          SHOW ENGINE INNODB STATUS 里 Modified db pages 在双 1 那次是 437 —— 437 个页是脏的、磁盘上是旧值，但查询走内存页，读到的永远是最新值。这就是“WAL 之后读路径不受影响”的直接证据，也是 hexdump 看 ibd 文件看不到 update 结果的原因。

          降级与回滚

          目标 动作 代价 回滚
          写入 IO 顶不住，先保吞吐 SET GLOBAL innodb_flush_log_at_trx_commit=2 主机掉电丢 ≤1 秒事务；mysqld 崩溃不丢 SET GLOBAL ...=1，立即生效
          binlog fsync 成瓶颈 SET GLOBAL sync_binlog=1000 掉电丢 ≤1000 个事务的 binlog 改回 1
          两者都要临时放开 双非 1（2 + 1000） 上述风险叠加，只用于非核心库/大促窗口 大促结束立刻改回双 1

          ⚠️ 降级是“临时保命”，现场还有 kill 不掉、内存打爆、饮鸩止渴式的开关连招，那些属于 44.30 MySQL 应急手册 的处置流程；这里的边界只有一条——动了就写清丢数据范围，并且一定改回来。

          ⚠️ 降级只解决“本机掉电丢最近若干事务”。如果要求 RPO=0（主库提交成功就不能丢），本机双 1 不够——异步复制下主库 commit 成功、备库还没收到就切主，这段数据就没了；只有半同步（semi-sync）把“备库确认收到 binlog”纳入提交路径，才能把 RPO 压到 0，代价是每次提交多一个网络往返（44.13 主从复制与读写分离、18.2 同步/半同步/异步复制）。

          反模式

          反模式 后果
          为了压测好看把 innodb_flush_log_at_trx_commit 设成 0 并留在生产 mysqld 自己重启就丢最近约 1 秒的提交；更糟的是 sync_binlog=1 时 binlog 已落盘、redo 没落，重启后主库回滚而备库照常应用——主备数据分叉，且 binlog 也补不回来
          大内存实例配 100MB 的 innodb_redo_log_capacity redo 反复写满，checkpoint 被迫高频推进，刷脏 IO 与业务 IO 抢盘，周期性“抖”，压力测试表现为先快后慢、延迟骤增
          SSD 上留着出厂值 innodb_io_capacity=200 引擎以为自己很慢，刷脏页比脏页产生还慢；症状是磁盘不忙但写入很慢，TPS 上不去
          sync_binlog=0 换取吞吐 丢多少 binlog 由 OS 刷盘时机决定，无法估算容量；一掉电可能出现“数据在、日志没”或“日志在、数据没”
          用 hexdump 看 ibd 文件“没变化”就判断 update 没生效 WAL 下正常现象：数据只在内存页与 redo 里；据此重复提交会造成重复扣款类事故
          认为 update 的值没变就“不会加锁、不会写日志” InnoDB 会照常加锁、照常写 redo；Changed: 0 只表示行格式没变，不表示没有锁与日志开销
          只保留 binlog、关掉 redo 来做崩溃恢复 binlog 不记录页级修改，数据页级丢失补不回来；要让 binlog 记页改动等于重造 redo
          以为“双 1”就是主库提交后一定不丢 双 1 只保证单机持久化；异步复制下切主仍可能丢已提交事务，RPO=0 需要 semi-sync

          自检

          Q1 16 并发压测，双 1 下 TPS 跑到 8000，iostat 里这块盘每秒只有约 500 次 fsync，两次刷盘怎么算都不该够——哪里想错了？

          ▸ 答案：漏了组提交。双 1 的两次刷盘是“每次提交各自等”，但组提交让一组事务共用一次 fsync：leader 带全组最大的 LSN 去刷，组员的返回等 leader 返回即可，所以 fsync 次数 ≈ 组数而不是事务数。反面推论同样成立：单线程压测时组里只有自己，组提交收益为 0，用单线程测出来的 TPS 不能代表并发能力。

          Q2 实例配的是 innodb_flush_log_at_trx_commit=2、sync_binlog=1。分别发生（a）kill -9 mysqld、（b）主机掉电，各丢什么？

          ▸ 答案：（a）不丢。=2 的 redo 已经 write 进文件系统 page cache，进程死了 page cache 还在，OS 会把它刷下去；binlog 也 fsync 过。（b）丢最近约 1 秒内提交的事务：page cache 随掉电消失，这段 redo 没了。注意（b）里 binlog 是完整的（sync_binlog=1），所以重启后主库回滚、备库却已应用——这正是“两个开关不匹配”的隐蔽风险，也是降级必须成对评估的原因。

          Q3 一条 update 返回 Query OK, 1 row affected，立刻 hexdump 数据文件看不到任何改动。怎么用一条命令证明它真的写了日志？

          ▸ 答案：看 LSN。SHOW ENGINE INNODB STATUS 的 Log sequence number 在这次 update 前后会增长（本机实测一次 2 万行更新后 LSN − Last checkpoint 是 7,400,730 字节，约 7.1MiB 的 redo 尚未落页），而 Pages flushed up to / Last checkpoint at 不动或远远落后。数据只改了内存页 + 追加了 redo，磁盘上的页还是旧值——WAL 的正常状态，不是没生效。

          Q4 在“binlog 已完整写入、redo 只有 prepare”的瞬间断电，重启后这条事务提交还是回滚？客户端当时收到的是什么？

          ▸ 答案：提交。按恢复判据，redo 只有 prepare 时拿 XID 去 binlog 找，找到且完整就提交——因为这份 binlog 之后一定会被从库/恢复库重放，主库必须跟着它走。客户端在断电前大概率收到的是“执行异常”（连接断开），而不是成功；它必须重连后查状态再决定，这正是 crash-safe 三条承诺里第三条的含义。

          Q5 为什么"先写 redo、再写 binlog、最后 redo commit"这个顺序不能调换？崩溃恢复时靠什么判断这条事务该提交还是回滚？

          ▸ 答案：不能调换，因为 binlog 是主从与备份的权威依据，redo 是本机的崩溃恢复依据，两者必须能对齐。顺序保证了两点：① redo 处于 prepare 时事务还没"对外生效"，此时崩溃一定回滚；② binlog 写完（且完整，带 XID/commit 标记）之后崩溃，恢复时拿 binlog 里的 XID 去比对 redo，一致就补 commit、不一致就回滚。判断口径：崩溃点之前 binlog 是否完整落盘，完整则提交，不完整则回滚——这也是"半同步复制至少一个从库收到 binlog 才返回"能提升一致性的原因。
