# 44.7 SQL 与查询优化

## 一句话

> SQL 优化不是“加索引”，而是让优化器用**更少的页读**拿到同样的结果：选择性决定走索引还是全表扫，覆盖索引消除回表，连接条件漏写直接变笛卡尔积（10⁶ × 10⁵ = 10¹¹ 行），关联子查询把成本从 O(n) 推到 O(n × m)，深分页则必须换写法。

## 一条 SQL 的执行路径

```
SQL → 解析（语法/语义）→ 重写（视图展开、子查询展开）→ 优化器（选索引、选连接顺序与算法）
    → 执行器（按计划取行）→ 存储引擎（页读、缓冲池）
```

**你能影响的是“优化器有没有正确的信息”和“SQL 有没有给优化器留出选择”**：统计信息是否新鲜、索引是否存在、谓词是否可下推、有没有隐式类型转换让索引失效。

## 数字一：索引的高度决定点查成本

设定：1000 万行、每页放 100 行、B+ 树扇出 500。

| 操作 | 页读次数 |
|---|---|
| B+ 树点查 | **3 次**（根 + 内部 + 叶子） |
| 全表扫描 | **10 万页** |

高度的算法：`log₅₀₀(10,000,000) ≈ 2.6 → 向上取整 3 层`。这就是“索引让点查从 O(N) 变 O(log N)”的具体数字：**3 次页读 vs 10 万次**。

> 🔑 索引的收益来自“少读页”，不是“少读行”。一个回表查询读了 10 万行，但每行都触发一次随机页读，成本可能比顺序扫全表还高。

## 数字二：1.1% 的选择率，索引反而更慢

订单表 1000 万行、3 年数据，查“最近 30 天 + status='paid'（占 40%）”：

```
时间选择率 = 30 / (3×365) = 2.74%
命中行数   = 10,000,000 × 2.74% × 40% ≈ 109,589 行（1.1%）
```

按“顺序读 0.04ms/页、随机读 0.10ms/页”估算：

| 执行路径 | 页读构成 | 估算成本 |
|---|---|---|
| 全表扫描 | 10 万页顺序读 | **4000ms** |
| 单列索引 `(created_at)` 回表 | 索引页 + 10.9 万次随机回表 | 11233ms |
| 联合索引 `(status, created_at)` 回表 | 索引页 + 10.9 万次随机回表 | 11068ms |
| **覆盖索引**（索引里含所有列） | 只读索引页，**不回表** | **44ms** |

同一份数据，最慢和最快的写法差 **250 倍**。而且“加索引”在这里会让查询变慢 2.8 倍——因为 10.9 万次随机页读比 10 万页顺序读更贵。

交叉点可以算出来：

```
全表扫描成本 / 单次随机读成本 = 100,000 × 0.04 / 0.10 = 40,000 行 = 0.40%
```

**命中行数超过 0.40% 时，全表扫描通常更快**。本例 1.1% 已超过，所以优化器大概率选全表扫描——除非有覆盖索引，或者能通过更好的谓词把选择率压下去。

| 选择率 | 优化器倾向 | 你该做什么 |
|---|---|---|
| < 0.1% | 索引 | 确保谓词可索引、无隐式转换 |
| 0.1%–1% | 看成本，可能走索引 | 用覆盖索引消除回表 |
| 1%–10% | 常走全表扫 | 减少返回列、加 LIMIT、分区 |
| > 10% | 全表扫/分区裁剪 | 别指望索引，改查询或改模型 |

## 数字三：连接算法差 6 个数量级

1000 万订单 × 100 万用户，`orders.user_id = users.id`：

| 算法 | 操作量 | 适用 |
|---|---|---|
| 嵌套循环（无索引） | 10⁷ × 10⁶ = **10¹³** 次比较 | 只适合小表 |
| 哈希连接 | 10⁷ + 10⁶ = **1.1×10⁷** | 大表等值连接，内存放得下 build 侧 |
| 索引嵌套循环（INLJ） | 10⁷ × 3 层 = **3×10⁷ 次页读** | 驱动表小、被驱动表有索引 |

10¹³ 次比较在 10⁹ 次/秒的机器上也要 2.8 小时——所以“两张大表没索引做连接”不是慢，是跑不完。哈希连接把复杂度降到线性，代价是内存；INLJ 把“比较”换成“页读”，适合驱动表很小、每次都命中索引的查询。

## 连接：五种形态，两个致命坑

连接的语义只有三类：**内连接**（只留匹配）、**外连接**（主表全保留）、**交叉连接**（全组合）。SQL92 与 SQL99 的差别只在**写法**，不在语义——同一句内连接有两种写法，选错写法才会引入坑。

| 形态 | SQL92（`FROM` 多表 + `WHERE`） | SQL99（`JOIN` + `ON`） | 结果 |
|---|---|---|---|
| 交叉连接 | `FROM player, team` | `CROSS JOIN` | **m × n 行**：37 个球员 × 3 支球队 = **111 行** |
| 等值连接 | `... WHERE p.team_id = t.team_id` | `JOIN team t ON p.team_id = t.team_id` | 只留匹配行（37 条） |
| 非等值连接 | `WHERE p.height BETWEEN h.lo AND h.hi` | `ON p.height BETWEEN h.lo AND h.hi` | 条件用比较符，不是等号 |
| 自连接 | `FROM player a, player b WHERE a.height > b.height` | `JOIN player b ON a.height > b.height` | 同一张表两次：比格里芬高的有 **6 人** |
| 左/右外连接 | `WHERE p.team_id = t.team_id(+)` | `LEFT / RIGHT JOIN ... ON` | 主表全保留，从表补 NULL |
| 全外连接 | **没有** | `FULL JOIN` | 两边都保留；**MySQL 不支持** |

SQL92 用 `(+)` 标记「从表」，是 Oracle 系写法，MySQL 不认。日常写法建议统一 SQL99：`JOIN` 一次连一张表，连接条件紧贴 `ON`，比把 5 张表堆在 `FROM` 后面再靠 `WHERE` 过滤容易读，也更容易看出「哪张表没写连接条件」。

### 坑一：漏写连接条件，得到笛卡尔积

37 × 3 = 111 行还能看；换两张真实表，`10⁶` 订单 × `10⁵` 用户 = **10¹¹ 行**，还没等过滤，临时目录先写满。SQL92 写法最容易犯：表加进 `FROM` 却忘了在 `WHERE` 里写条件。发现手段是 `EXPLAIN` 的 `rows`：**几张表的 `rows` 相乘**，基本就是你在算笛卡尔积。

### 坑二：外连接的条件写进 `WHERE`，外连接退化成内连接

外连接的定义是「主表保留全部行，从表没匹配就补 NULL」。一旦在 `WHERE` 里对**从表**的列加条件，NULL 行必然不满足，主表那部分行就被滤掉了——语义变回内连接：

```sql
-- ① 全部 37 名球员；没有球队的球员，team_name 为 NULL
SELECT p.player_name, t.team_name
FROM player p LEFT JOIN team t ON p.team_id = t.team_id;

-- ② 只剩「湖人」的球员：对从表列加了 WHERE，NULL 行被滤掉 → 等价于内连接
SELECT p.player_name, t.team_name
FROM player p LEFT JOIN team t ON p.team_id = t.team_id
WHERE t.team_name = '湖人';

-- ③ 仍保留全部 37 人，只把「湖人」的队名填上，其余为 NULL
SELECT p.player_name, t.team_name
FROM player p LEFT JOIN team t
  ON p.team_id = t.team_id AND t.team_name = '湖人';
```

判据只有一条：**这个条件是用来「筛主表」还是「限制匹配」**。筛主表 → `WHERE`；限制匹配、主表要全留 → `ON`。

> 🔑 外连接的 `ON` 决定「能不能配上」，`WHERE` 决定「配完之后留不留」。把「限制匹配」的条件错写进 `WHERE`，SQL 不报错、结果少一批行——这类 bug 只有对数时才看得见。

## join 怎么执行：NLJ、BNL 与 BKA

决定 join 快慢的不是 SQL 怎么写，而是**被驱动表的连接列有没有索引**：有索引走 NLJ（可优化成 BKA），没索引就掉进 BNL——每多一段 `join_buffer`，被驱动表就多扫一遍。

| 算法 | 触发条件 | 扫描量 | 内存判断 | 判断 |
|---|---|---|---|---|
| Simple NLJ（理论模型） | 无索引且不用 buffer | `N + N×M` | 0 | MySQL **不用**它 |
| **NLJ**（索引嵌套循环） | 被驱动表连接列**有索引** | `N + N×2log₂M` | 0 | 首选 |
| **BNL**（块嵌套循环） | 被驱动表连接列**无索引** | `N + K×M`（K=分段数） | `N×M` | 尽量别用 |
| **BKA**（批量取键） | NLJ + MRR 开启 | 同 NLJ，但按主键**顺序**回表 | 0 | BNL 的替代方案 |

课程用两张表算过账：`t1` 100 行、`t2` 1000 行，`a` 列有索引。

| 语句 | 算法 | 总扫描行数 | 内存判断次数 |
|---|---|---|---|
| `t1 straight_join t2 on t1.a=t2.a` | NLJ | **200**（100 + 100） | — |
| `t1 straight_join t2 on t1.a=t2.b`（`b` 无索引） | BNL | **1100**（100 + 1000），`join_buffer` 不够时 `t2` 还要再扫 | **10 万次**（100 × 1000） |
| 同上，`join_buffer_size=1200` 只放得下 88 行 | BNL 分两段 | `t2` 被扫 **2 次** | 仍 10 万次（判断次数与分段无关） |

判断有没有掉进 BNL，看 `EXPLAIN` 的 `Extra`：出现 `Using join buffer (Block Nested Loop)` 就是 BNL；8.0 无索引等值连接可能显示 `hash join`。

### 驱动表：永远让「小表」驱动

| 算法 | 谁做驱动表 | 为什么 |
|---|---|---|
| NLJ | **小表** | 成本 `N + N×2log₂M`，N 翻 1000 倍扫描翻 1000 倍，M 翻 1000 倍只涨不到 10 倍 |
| BNL（buffer 够） | 都一样 | 扫描 `M+N`、判断 `M×N`，交换 M/N 无差别 |
| BNL（buffer 不够，**更常见**） | **小表** | 扫描 `N + λNM`，N 越小分段越少，被驱动表扫的次数越少 |

「小表」不是「行数少的表」，而是**按各自条件过滤后、参与 join 的字段总数据量小的那个**。课程的例子：两张表都只有 100 行参与 join，但一张只需带 `b` 一列、另一张要带全部字段——带一列的那张才是「小表」，应该做驱动表。

### 掉进 BNL 之后的三条补救

| 做法 | 怎么做 | 代价 |
|---|---|---|
| 加索引（首选） | 给被驱动表的连接列建索引，BNL 直接转 BKA | 写放大；只被低频 SQL 用到就不划算 |
| 临时表 | 先把过滤后的小结果集灌进带索引的临时表，再 join | 多一次全表扫 + 建表开销 |
| 应用层哈希 | 把驱动表结果建成 map，再逐行探测被驱动表 | 数据量必须能装进应用内存 |

课程实测的对比（1000 行 × 100 万行、过滤后只剩 2000 行、低频 SQL）：直接 BNL 要判 **10 亿次**、跑 **1 分 11 秒**；换成「临时表 + 索引再 join」总耗时**不到 1 秒**。

```sql
-- 临时表方案：先过滤、加索引、再 join（MySQL 8.0，本机无实例，未执行）
CREATE TEMPORARY TABLE temp_t (id INT PRIMARY KEY, a INT, b INT, INDEX(b)) ENGINE=InnoDB;
INSERT INTO temp_t SELECT * FROM t2 WHERE b BETWEEN 1 AND 2000;
SELECT * FROM t1 JOIN temp_t ON t1.b = temp_t.b;

-- 打开 BKA（依赖 MRR，两个 mrr 参数缺一不可）
SET optimizer_switch = 'mrr=on,mrr_cost_based=off,batched_key_access=on';
```

```ini
[mysqld]
join_buffer_size = 256K   # 默认；BNL 分段数由它决定，调大能减少被驱动表的扫描次数
```

> ⚠️ 课程写作时（2019）MySQL 还没有 hash join，原文结论是「只能自己用 map 模拟」。**8.0.18 起官方支持 hash join**，无索引的等值连接会自动改走哈希（`EXPLAIN` 里的 `hash join`），BNL 的场景因此少了很多——判断仍然以 `EXPLAIN` 的实际计划为准。

### BNL 真正贵的地方：不只是慢

| 副作用 | 机制 | 后果 |
|---|---|---|
| 磁盘 IO | 被驱动表被扫 K 次 | 大冷表 join 直接把 IO 打满 |
| CPU | `M×N` 次等值判断（10 亿次量级） | 单条 SQL 吃满一个核 |
| **buffer pool 被污染** | 冷表页反复进 LRU，占满 old 区；热数据页等不到「1 秒后再被访问」的晋升条件 | 命中率下降，且**语句结束后不会自愈**，要靠后续请求慢慢暖回来 |

第三条最容易被忽略：慢 SQL 结束就以为没事了，实际上缓冲池的账要还很久（[44.3 缓冲池与页面管理](44.3-缓冲池与页面管理.md)）。

> 🔑 要不要用 join，判据只有一条：**被驱动表的连接列有没有索引**。有 → 用 join（比应用层拆成 101 条 SQL、自己拼结果更省交互）；没有 → 别用，先建索引或先用临时表把数据缩小。

## 子查询：先问「它执行几次」

子查询按**执行次数**分两类，性能差异全部来自这里：非关联子查询只算一次，关联子查询外层每行算一次。

| 类型 | 执行次数 | 典型写法 | 规模风险 |
|---|---|---|---|
| **非关联** | 1 次，结果当外层条件 | `WHERE cc IN (SELECT cc FROM B)` | 子查询结果集大小决定内存 |
| **关联** | 外层行数（37 行 → 37 次） | `EXISTS (SELECT 1 FROM B WHERE B.cc = A.cc)` | 子查询没走索引 → `O(n × m)` |

`EXISTS` 天然是关联子查询（它要拿外层的值去判断「存在与否」），所以 `IN` 与 `EXISTS` 的选择本质是「让哪张表当驱动表」。课程给的判据是：

| 场景（`cc` 列有索引） | 选谁 | 为什么 |
|---|---|---|
| 外层表 A **大**，子查询表 B 小 | `IN` | 一次算出 B 的集合，再用它过滤 A |
| 外层表 A **小**，子查询表 B 大 | `EXISTS` | 外层每行去 B 上按索引探一次，不用把 B 全取回来 |

课件的实测（37 名球员的表）：`EXISTS` 查出 **19** 条出场球员，`NOT EXISTS` 查出 **18** 条未出场——两者互补，加起来正好 37；集合比较里 `ANY` 查出 **35** 条，`ALL` 只查出 **1** 条（只有最高的那位）。

> ⚠️ 上表是「有索引」前提下的经验判据。现代优化器会把 `IN` 改写成半连接（semi-join），改写成功时两者计划可能一样——**以 `EXPLAIN` 的实际计划为准，别背口诀**。

### 一个必须知道的 NULL 陷阱

`NOT IN (子查询)` 只要子查询结果里有一个 NULL，整个条件就恒为 `UNKNOWN`，返回**空集**；`NOT EXISTS` 不受影响。可复现：

```sql
-- B 里有一行 cc 为 NULL 时，下面两句结果不同（MySQL 8.0，本机无实例，未执行）
SELECT * FROM A WHERE cc NOT IN (SELECT cc FROM B);          -- 0 行
SELECT * FROM A WHERE NOT EXISTS (SELECT 1 FROM B WHERE B.cc = A.cc);  -- 正常返回
```

所以「排除一批 id」优先写 `NOT EXISTS` 或 `LEFT JOIN ... WHERE B.cc IS NULL`，别用 `NOT IN`。

## 最左前缀：联合索引 (a, b, c)

| 条件 | 能用到索引的列 | 说明 |
|---|---|---|
| `a = ?` | a | 最左列可用 |
| `a = ? AND b = ?` | a, b | 前缀连续 |
| `a = ? AND b = ? AND c = ?` | a, b, c | 全用上 |
| `a = ? AND c = ?` | 只用 a | c 只能在回表后过滤 |
| `b = ?` | **用不了** | 跳过最左列，索引树按 a 有序，无法定位 |
| `c = ?` | **用不了** | 同上 |

范围条件会截断后续列：`a = ? AND b > ? AND c = ?` 只能用到 `a, b`（b 是范围，c 无法再用于定位）。这是“最左前缀”最容易被忽略的细节——很多慢查询是列顺序排错了，而不是索引没建。

## 深分页：从 100 万行到 20 行

```sql
-- 慢：要先读出前 1,000,020 行再丢掉
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;

-- 快：从上一页最后一条的 id 继续（keyset / seek 分页）
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 20;
```

| 写法 | 读取行数 | 相对成本 |
|---|---|---|
| `OFFSET 1000000 LIMIT 20` | 1,000,020 | 50001× |
| keyset（`id > ?`） | 20 | 1× |

深分页慢的根因是**偏移量必须被“走过”**：数据库不知道第 100 万行在哪，只能顺序数过去。keyset 分页把“位置”变成“条件”，直接定位。代价是不能跳页（只能上一页/下一页），适合信息流、导出、遍历。

> ⚠️ `SELECT *` 不只是“多传几个字段”：它会让覆盖索引失效（必须回表）、增加网络传输、破坏“索引即数据”的可能。在宽表（200 字节/行 vs 40 字节/行）上，IO 差 5 倍。

## 可运行的成本模型

```go
package main

import (
	"fmt"
	"math"
)

const (
	rows         = 10_000_000.0 // orders 表行数
	rowsPerPage  = 100.0        // 每页放 100 行
	seqPageMs    = 0.04         // 顺序读一页 0.04ms（约 200MB/s）
	randomPageMs = 0.10         // 随机读一页 0.10ms
	fanout       = 500.0        // B+ 树每个内部节点的分叉数
)

func pages(rs float64) float64 { return rs / rowsPerPage }

func main() {
	// ① B+ 树高度：点查要读几页
	height := math.Ceil(math.Log(rows) / math.Log(fanout))
	fmt.Printf("① %.0f 万行、扇出 %.0f → B+ 树高 %.0f 层；点查约 %.0f 次页读；全表 %.0f 万页\n",
		rows/10000, fanout, height, height, pages(rows)/10000)

	// ② 选择性：3 年数据，查最近 30 天 + status='paid'（占 40%）
	dateSel := 30.0 / (3 * 365)
	statusSel := 0.40
	matched := rows * dateSel * statusSel
	fmt.Printf("② 时间选择率 %.2f%%，status 选择率 %.0f%% → 命中 %.0f 行（%.1f%%）\n",
		dateSel*100, statusSel*100, matched, matched/rows*100)

	// ③ 三种执行路径的 IO 成本
	fullScan := pages(rows) * seqPageMs
	idxDate := pages(rows*dateSel)*randomPageMs + matched*randomPageMs
	idxBoth := pages(matched)*randomPageMs + matched*randomPageMs
	covering := pages(matched) * seqPageMs
	fmt.Printf("③ 执行成本（ms）：全表扫描 %.0f；单列索引(created_at)回表 %.0f；联合索引(status,created_at)回表 %.0f；覆盖索引 %.0f\n",
		fullScan, idxDate, idxBoth, covering)

	// ④ 索引回表 vs 全表扫描的交叉点
	crossover := math.Floor(pages(rows) * seqPageMs / randomPageMs)
	fmt.Printf("④ 回表行数超过 %.0f 行（%.2f%% 的选择率）时，全表扫描反而更快\n",
		crossover, crossover/rows*100)
	fmt.Printf("   本例命中 %.0f 行 > %.0f → 优化器大概率选全表扫描，除非用覆盖索引\n", matched, crossover)

	// ⑤ 连接：10M 订单 × 1M 用户
	orderRows, userRows := rows, 1_000_000.0
	fmt.Printf("⑤ 连接 1000 万订单与 100 万用户：嵌套循环无索引 %.0e 次比较；哈希连接 %.1e 次；索引嵌套循环 %.0e 次页读\n",
		orderRows*userRows, orderRows+userRows, orderRows*3)

	// ⑥ 深分页：LIMIT 1000000, 20
	offset := 1_000_000.0
	fmt.Printf("⑥ OFFSET %.0f LIMIT 20：要读 %.0f 行；keyset（WHERE id > ?）只读 20 行，差 %.0f 倍\n",
		offset, offset+20, (offset+20)/20)

	// ⑦ 最左前缀：联合索引 (a,b,c)
	fmt.Println("⑦ 联合索引 (a,b,c) 能用到哪几列：")
	for _, q := range []struct{ cond, use string }{
		{"a = ?", "a"},
		{"a = ? AND b = ?", "a,b"},
		{"a = ? AND b = ? AND c = ?", "a,b,c"},
		{"a = ? AND c = ?", "只用 a（c 回表过滤）"},
		{"b = ?", "用不了（跳过最左列）"},
		{"c = ?", "用不了（跳过最左列）"},
	} {
		fmt.Printf("   %-32s → %s\n", q.cond, q.use)
	}
}
```

输出：

```

② 时间选择率 2.74%，status 选择率 40% → 命中 109589 行（1.1%）
③ 执行成本（ms）：全表扫描 4000；单列索引(created_at)回表 11233；联合索引(status,created_at)回表 11068；覆盖索引 44

   a = ?                            → a
   a = ? AND b = ?                  → a,b
   a = ? AND b = ? AND c = ?        → a,b,c
   a = ? AND c = ?                  → 只用 a（c 回表过滤）
   b = ?                            → 用不了（跳过最左列）
   c = ?                            → 用不了（跳过最左列）
```

## EXPLAIN 该看什么

| 列 | 关注点 |
|---|---|
| `type` | `ALL`（全表）、`index`（全索引扫）、`range`、`ref`、`eq_ref`、`const`：越靠右越好 |
| `key` / `key_len` | 实际用了哪个索引、用了联合索引的几列（`key_len` 能看出最左前缀用了几列） |
| `rows` | 优化器估算的扫描行数；和实际差很多说明统计信息过期 |
| `filtered` | 扫描后剩余比例，低说明索引选择性差 |
| `Extra` | `Using index`（覆盖索引，好）、`Using filesort`（排序无索引）、`Using temporary`（临时表） |

三个常见误判：① 看到 `type=ALL` 就以为必须加索引——1.1% 选择率下全表扫是对的；② 看到 `Using index` 就以为最优——它可能是全索引扫描（`type=index`），扫了整棵索引树；③ 只看单条 SQL 不看执行频率——一天跑一次的慢查询不如一秒跑一万次的“稍慢查询”值得优化。

## 慢日志 → EXPLAIN ANALYZE → 回归：一条闭环

先让慢查询自己冒出来（`my.cnf` 片段，`mysqld --validate-config` 校验过）：

```ini
[mysqld]
slow_query_log = ON
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 0.2                # 按接口 P99 目标定，别用默认 10s
min_examined_row_limit = 1000        # 扫描不足 1000 行不记，滤掉噪声
log_queries_not_using_indexes = OFF  # 开了会写爆日志，只可短时打开
innodb_buffer_pool_size = 40G          # 机器内存的 60%–70%（64G 机器给 40G）
```

再按“总耗时”而不是“单次最慢”排序：

```sql
SELECT DIGEST_TEXT, COUNT_STAR,
       ROUND(SUM_TIMER_WAIT/1e9, 1) AS total_ms,
       ROUND(AVG_TIMER_WAIT/1e6, 2) AS avg_ms,
       SUM_ROWS_EXAMINED
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;
```

一条 5ms 但每秒 1 万次的查询（总耗时 50 秒/秒），比一条 2s 每分钟一次的查询（0.03 秒/秒）更值得修——**优化对象是总耗时，不是单条最慢**。

`EXPLAIN ANALYZE` 看“实际扫描行数”（20 万行测试表实测）：

| 写法 | 执行计划 | 实际扫描 | 耗时 |
|---|---|---|---|
| `WHERE DATE(created_at) = CURDATE()` | Table scan | 200000 行，命中 547 | 34.5ms |
| `WHERE created_at >= ? AND created_at < ?` | Index range scan（`idx_created`） | 547 行 | 0.8ms |
| `WHERE user_id = ? ORDER BY created_at DESC LIMIT 20` | Index lookup（`idx_user_created`，reverse） | 20 行 | 0.04ms |
| `ORDER BY id LIMIT 100000, 20` | Index scan | 100020 行 | — |
| `WHERE id > ? ORDER BY id LIMIT 20` | Index range scan（PRIMARY） | 20 行 | 0.57ms |

修复后的回归看三条，缺一条都可能是“把成本挪走了”：

1. `EXPLAIN ANALYZE` 的 `rows` 从 20 万降到几百；
2. 该 digest 的 `SUM_ROWS_EXAMINED` 下降一个量级；
3. 接口 P99 与 DB CPU 同步下降（只改计划不看 P99，可能只是把成本挪到了排序/回表）。

回滚也要提前写：

```sql
-- 加错索引：Online DDL 回滚，先确认磁盘余量与复制延迟
ALTER TABLE orders DROP INDEX idx_created, ALGORITHM=INPLACE, LOCK=NONE;
```

SQL 改写靠代码版本回退；**别只把 SQL 改回去、忘了把新加的索引删掉**——写放大和优化器误判会留下来。

## 参数怎么给

| 症状 | 先查 | 改法 |
|---|---|---|
| 点查慢 | 是否命中索引、有无隐式转换 | 修正类型/加索引 |
| 范围查慢 | 选择率、`EXPLAIN rows` | 覆盖索引、减少返回列 |
| 排序慢 | `Using filesort` | 索引顺序与 `ORDER BY` 对齐 |
| 连接慢 | 驱动表大小、被驱动表有无索引 | 小表驱动 + 被驱动表索引，或哈希连接 |
| 深分页慢 | `OFFSET` 大小 | keyset 分页 |
| 偶发慢 | 统计信息、锁等待、缓冲池命中 | 更新统计、看 `innodb_buffer_pool` |
| 写慢 | 索引数量、唯一约束、二级索引维护 | 精简索引（每个索引都是写放大） |

## 反模式

| 反模式 | 后果 |
|---|---|
| 见慢查询就加索引 | 写放大、优化器选择变差、1.1% 选择率下反而更慢 |
| `SELECT *` | 覆盖索引失效、回表、网络放大 |
| 在索引列上做函数/运算（`WHERE DATE(created_at)=?`） | 索引失效，全表扫 |
| 隐式类型转换（字符串列传数字） | 索引失效 |
| 联合索引列顺序随意 | 最左前缀用不上 |
| `OFFSET` 翻到几十万页 | 线性变慢，拖垮 DB |
| 用 `LIKE '%x%'` 做搜索 | 索引失效，走全表 |
| 大表 `JOIN` 无索引 | 10¹³ 次比较，跑不完 |
| 不更新统计信息 | 优化器选错计划，且难以复现 |
| 只优化 SQL 不看表结构 | 宽表、无分区，单条再快也扛不住量 |
| SQL92 写法漏写连接条件 | 笛卡尔积，`10⁶ × 10⁵ = 10¹¹` 行，临时空间先爆 |
| 外连接把从表条件写进 `WHERE` | 退化成内连接，主表行静默丢失 |
| `NOT IN` 遇到子查询里的 NULL | 条件恒为 UNKNOWN，返回空集 |
| 关联子查询无索引 | 外层 37 行 × 内层全表扫 = `O(n × m)` |
| 混用 SQL92 / SQL99 连接写法 | 连接条件散落 `WHERE` 与 `ON`，漏写一处就出笛卡尔积 |
| join 的连接列没索引 | 掉进 BNL，`M×N` 次判断 + 被驱动表被扫 K 次 |
| 让大表做驱动表 | NLJ 下扫描量随驱动表行数线性膨胀 |
| 大冷表 join 跑完就完事 | buffer pool 的 old 区被占满，命中率下降且要很久才恢复 |

## 自检

**Q1** 命中 10.9 万行（1.1%）时，走索引回表要 11233ms，全表扫描只要 4000ms。为什么“用了索引”反而更慢？

▸ 答案：因为成本由**页读方式**决定，不是“有没有用索引”。全表扫描是 10 万页**顺序读**（0.04ms/页）；索引回表是 10.9 万次**随机读**（0.10ms/次），每次只取一行所在页，页里的其余 99 行浪费了。总成本 10.9 万 × 0.1ms ≈ 11s，是顺序扫的两倍多。所以优化器的选择是对的：低选择率（本例 1.1%）下全表扫更便宜。要让它变快，得减少回表——覆盖索引把 11233ms 降到 44ms。

**Q2** 覆盖索引为什么能把 11233ms 降到 44ms？它成立的条件是什么？

▸ 答案：覆盖索引把查询需要的所有列都放进索引，**不需要回表**：只读 109,589 行 / 100 行每页 ≈ 1096 个索引页，顺序读约 44ms。条件有三：① `SELECT` 的列全部在索引里（不能 `SELECT *`）；② 过滤条件能用到索引（最左前缀 + 范围）；③ 索引本身不太宽（宽索引的页数会变多，收益下降）。代价是索引更大、写放大更高，所以覆盖索引要针对**高频查询**设计，不是给每张表都加。

**Q3** 联合索引 `(a,b,c)`，为什么 `WHERE b = ?` 用不了索引，而 `WHERE a = ? AND c = ?` 至少能用 a？

▸ 答案：B+ 树按“a 然后 b 然后 c”排序，只有 a 确定时，b 才在索引里局部有序；跳过 a 直接查 b，b 在整个索引里无序，无法二分定位，只能全索引扫。`a = ? AND c = ?` 里 a 能定位到一段连续区间，c 在这段区间内无序，所以只能回表后过滤——索引仍然缩小了扫描范围。**列顺序要按“等值在前、范围在后、高频组合优先”排**。

**Q4** `LIMIT 1000000, 20` 为什么要读 100 万行？换成 keyset 分页后为什么只读 20 行？代价是什么？

▸ 答案：`OFFSET` 的语义是“跳过前 N 行”，数据库必须真的数过这 N 行（即使不返回），所以读了 1,000,020 行。keyset 用 `WHERE id > 上一页最后一个 id` 把“位置”变成“索引上的起点”，B+ 树直接定位，只读 20 行。代价：① 不能随机跳页（只能上一页/下一页）；② 需要单调且唯一的排序键（id/时间戳 + 去重）；③ 排序键变了分页就失效。

**Q5** 哈希连接和索引嵌套循环，什么时候选哪个？

▸ 答案：**哈希连接**适合两张大表做等值连接、内存能放下 build 侧（小表）：一次建表 + 一次探测，复杂度线性，但只支持等值、内存不够会落盘。**索引嵌套循环**适合驱动表很小（几十~几千行）、被驱动表连接列有索引：每行一次 3 层索引查找，成本 = 驱动行数 × 3 页读，不需要大内存。优化器会根据统计信息选；如果你发现它选错了（比如统计过期），可以用 hint 或改写查询，但先确认统计信息是否新鲜。

**Q6** 一条 SQL 在测试环境 37 行、上线后跑了几分钟还没出结果，`EXPLAIN` 里两张表的 `rows` 分别是 1,000,000 和 100,000。最可能的原因？

▸ 答案：连接条件漏了（或写在了不生效的位置），得到的是笛卡尔积：`10⁶ × 10⁵ = 10¹¹` 行。判据是 `EXPLAIN` 里**各表 `rows` 相乘**≈结果行数量级，且 `Extra` 里没有可用的连接索引。SQL92 写法最常犯：表加进 `FROM` 就忘了 `WHERE` 里的条件。

**Q7** `LEFT JOIN` 之后想「只看湖人的球员」，为什么把 `t.team_name='湖人'` 写进 `WHERE` 就错了？该写在哪？

▸ 答案：写进 `WHERE` 会先补 NULL、再统一过滤——没有球队的球员 `team_name` 是 NULL，必然被滤掉，主表那部分行就消失了，外连接退化成内连接。想「只保留湖人的球员」本来就该用内连接；想「保留全部球员、只把湖人的队名填上」，条件要写在 `ON` 里。判据：**筛选主表 → `WHERE`；限制匹配、主表全留 → `ON`**。

**Q8** 「找出没有下过单的用户」，`NOT IN (SELECT user_id FROM orders)` 与 `NOT EXISTS (...)` 有什么区别？什么情况下前者会返回空集？

▸ 答案：`NOT IN` 要求子查询结果里**没有 NULL**：只要 `orders.user_id` 有一行为 NULL，`user_id NOT IN (..., NULL)` 就恒为 UNKNOWN，整条查询返回空集。`NOT EXISTS` 是逐行判断「存不存在」，不受 NULL 影响。所以排除类查询优先 `NOT EXISTS`，或 `LEFT JOIN ... WHERE orders.user_id IS NULL`。另外注意 `orders.user_id` 上的索引：`EXISTS` 靠它把「外层每行探一次」变成索引查找，否则就是 37 行 × 全表扫。

**Q9** `join_buffer_size` 从 256K 改小到放不下驱动表时，等值判断次数会变吗？什么会变？

▸ 答案：**判断次数不变**，仍是 `M×N`；变的是**扫描行数**。驱动表被切成 K 段，每段都要把被驱动表完整扫一遍，扫描量变成 `N + K×M`。课程例子里 100 行驱动表被切成 88 + 12 两段，`t2`（1000 行）就被扫 2 次，总扫描 1100 → 2100，而 10 万次内存判断一次不少。所以调大 `join_buffer_size` 减少的是**被驱动表的重复扫描**，不是 CPU 的等值比较。

**Q10** 一条大冷表 join 跑了 3 分钟，结束后业务查询还是慢，命中率一直上不去。为什么？

▸ 答案：BNL 反复扫冷表，把冷数据页推进 buffer pool 的 **old 区**；而 InnoDB 的 LRU 要求数据页「1 秒后再次被访问」才能晋升到 young 区，冷表扫描循环太快，热数据页要么被挤掉、要么来不及晋升。结果是 `young` 区该淘汰的没淘汰、热页进不来。**语句结束不等于影响结束**——IO 和 CPU 会立刻恢复，缓冲池要等后续请求慢慢暖回来（[44.3 缓冲池与页面管理](44.3-缓冲池与页面管理.md)）。
