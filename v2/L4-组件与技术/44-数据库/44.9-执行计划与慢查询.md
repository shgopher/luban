# 44.9 执行计划与慢查询

## 一句话

> 执行计划是**优化器用“统计信息 + 代价模型”猜出来的**：猜错行数，就会选错算子（索引 vs 全表、嵌套循环 vs 哈希连接），而慢查询治理的第一步不是加索引，是**把慢日志按“指纹”聚合，找出代价最大的那一类**。

## 优化器只做一件事：比代价

| 计划 | 代价模型 | 什么时候赢 |
|---|---|---|
| 全表扫描 | 页数 × 顺序读代价 | 匹配行占比高（> 百分之几） |
| 索引扫描 + 回表 | 树高 + 匹配行数 × 随机读代价 | 匹配行很少（< 千分之几） |
| 覆盖索引扫描 | 树高 + 索引页数 | 列都被索引覆盖 |
| 嵌套循环连接 | 外表行数 × 内表一次查找 | 外表很小、内表有索引 |
| 哈希连接 | 两表各扫一遍 + 建哈希表 | 大表连大表、无索引 |
| 排序合并连接 | 两边排序 + 归并 | 两边都已有序 |

> 🔑 优化器的输入是**统计信息**（行数、NDV、直方图），输出是**计划**。统计信息陈旧（大批量导入/删除后没 analyze），代价估算就会偏几个数量级，计划随之翻转。

## 代码：代价翻转点与“统计信息错误”的代价

```go
package main

import (
	"fmt"
	"sort"
)

const (
	tableRows  = 1_000_000
	tablePages = 10_000
	treeHeight = 3
	randCost   = 4.0 // 随机读一页相当于 4 次顺序读
)

// 全表扫描代价：顺序读所有页
func scanCost() float64 { return float64(tablePages) }

// 索引扫描代价：树高 + 回表（每行一次随机读）
func indexCost(matched float64) float64 { return treeHeight + matched*randCost }

func main() {
	fmt.Println("=== 计划翻转：匹配行数与两种计划的代价 ===")
	fmt.Printf("%-12s %-12s %-14s %-14s %s\n", "选择率", "匹配行数", "全表扫描", "索引+回表", "优化器选谁")
	for _, sel := range []float64{0.0001, 0.001, 0.002, 0.0025, 0.005, 0.01, 0.05, 0.2} {
		m := sel * tableRows
		s, i := scanCost(), indexCost(m)
		chosen := "索引"
		if s < i {
			chosen = "全表"
		}
		fmt.Printf("%-12s %-12.0f %-14.0f %-14.0f %s\n",
			fmt.Sprintf("%.2f%%", sel*100), m, s, i, chosen)
	}

	fmt.Println("\n=== 统计信息错误：优化器以为 50 行，实际 50,000 行 ===")
	est := 50.0
	actual := 50_000.0
	chosenByEst := indexCost(est) // 估算：50*4+3 = 203 < 10000 → 选索引
	realCost := indexCost(actual) // 实际：50000*4+3 = 200003
	fmt.Printf("按估算：索引代价 %.0f vs 全表 %.0f → 选索引\n", chosenByEst, scanCost())
	fmt.Printf("按实际：索引代价 %.0f vs 全表 %.0f → 慢了 %.0f 倍\n",
		realCost, scanCost(), realCost/scanCost())
	fmt.Println("这就是“加了索引反而更慢”的典型成因：不是索引坏，是优化器估错了行数")

	fmt.Println("\n=== 慢日志按指纹聚合（按总耗时排序）===")
	type entry struct {
		fp   string
		ms   float64
		rows int
	}
	logs := []entry{
		{"SELECT * FROM orders WHERE user_id = ?", 120, 1},
		{"SELECT * FROM orders WHERE user_id = ?", 95, 1},
		{"SELECT * FROM orders WHERE user_id = ?", 210, 1},
		{"SELECT * FROM items WHERE category = ? ORDER BY created_at", 80, 5000},
		{"SELECT * FROM items WHERE category = ? ORDER BY created_at", 60, 5000},
		{"UPDATE stock SET n = n - 1 WHERE sku = ?", 400, 1},
		{"SELECT count(*) FROM logs WHERE ts > ?", 3000, 1},
		{"SELECT count(*) FROM logs WHERE ts > ?", 2800, 1},
	}
	type agg struct {
		fp      string
		count   int
		total   float64
		max     float64
		avgRows float64
	}
	m := map[string]*agg{}
	for _, l := range logs {
		a, ok := m[l.fp]
		if !ok {
			a = &agg{fp: l.fp}
			m[l.fp] = a
		}
		a.count++
		a.total += l.ms
		if l.ms > a.max {
			a.max = l.ms
		}
		a.avgRows += float64(l.rows)
	}
	var list []*agg
	for _, a := range m {
		a.avgRows /= float64(a.count)
		list = append(list, a)
	}
	sort.Slice(list, func(i, j int) bool { return list[i].total > list[j].total })
	fmt.Printf("%-52s %-6s %-10s %-8s %s\n", "SQL 指纹", "次数", "总耗时ms", "最大ms", "平均扫描行")
	for _, a := range list {
		fmt.Printf("%-52s %-6d %-10.0f %-8.0f %.0f\n", a.fp, a.count, a.total, a.max, a.avgRows)
	}
}
```

读数：

| 现象 | 含义 | 动作 |
|---|---|---|
| 选择率 0.25% 附近翻转 | 低于它索引赢，高于它全表赢 | 别对“查 10% 行”的查询建索引，优化器不会用 |
| 估算 50 行、实际 50,000 行 | 索引代价从 203 变 200,003，比全表慢 **20 倍** | 大批量变更后 `ANALYZE`；用 `EXPLAIN ANALYZE` 看真实行数 |
| 慢日志聚合后，`count(*)` 一条占 5,800ms | 单条最慢的 `UPDATE` 只有 400ms，但总耗时被高频查询主导 | 按“总耗时”排序，而不是按“单次最慢” |

> 🔑 慢查询治理的顺序：**按指纹聚合并按总耗时排序 → 看 `rows_examined/rows_sent` 比值 → `EXPLAIN ANALYZE` 看估算行数与实际行数 → 再决定加索引/改 SQL/改统计信息**。跳过第一步，就会去优化那条“偶尔 3 秒”的查询，而放过每天跑 10 万次的 50ms 查询。

## 优化器为什么会选错索引：三个输入，三种失真

选错索引不是优化器乱选，是三个输入之一失真：**基数不准、回表代价算轻、排序被当成免费**。先对号入座，再谈对策——顺序反了就会先上 `FORCE INDEX`，把一次救火变成永久固化。

### 基数是采样外推出来的，不是数出来的

`SHOW INDEX` 的 `Cardinality` 是「索引上有多少个不同的值」，即区分度。InnoDB 不逐行数：取 N 个数据页 → 算这些页上的平均不同值 → 乘以索引页数，外推成整棵索引的基数；再定一个阈值，变更行数超过 `1/M` 时自动重算。

| `innodb_stats_persistent` | 统计放在哪 | 采样页数 | 重算阈值 | 重启后 |
|---|---|---|---|---|
| `on`（5.6.6 起默认） | 持久化 | 20 | 变更行数 > 1/10 | 保留 |
| `off` | 只在内存 | 8 | 变更行数 > 1/16 | 丢失，重新采样 |

两档都是**采样**，所以都可能不准：页内的值分布和全表不一致时，20 页的外推照样偏。这解释了「明明有索引却走全表」的第一类原因——优化器以为这个索引的选择性很差。

```sql
-- MySQL 5.7 / 8.0，本机无实例，未执行
SHOW INDEX FROM t;      -- Cardinality 是采样值，不是 count(distinct)
ANALYZE TABLE t;        -- 重算统计，治「估算 rows 与实际差几个数量级」
```

### 案例一：扫 10 万行的那条赢了扫 1 万行的

表 `t` 上 `a`、`b` 各一个索引，10 万行。原句本来走 `a`（估 `rows=10001`），后来优化器改成全表扫：

| 写法 | 走哪个索引 | 估算 rows | 实际扫描 | 课程材料耗时 |
|---|---|---|---|---|
| 原句 | 全表（主键） | 104,620 | 100,000 | 40ms |
| 原句 + `FORCE INDEX(a)` | `a` | 37,116 | 10,001 | 21ms |

两处失真叠在一起：**估算本身离谱**（强制走 `a` 时估 37,116，实际 10,001），而且**回表被乘了权**——走 `a` 每行都要回主键取整行，全表扫没有这笔账。于是「扫 3.7 万行 + 回表」输给了「扫 10 万行」。

> 🔑 `rows` 小不等于被选中。优化器比的是总代价：回表乘权、排序计价。只盯 `rows`，会把「统计估错」和「代价权重偏」混成同一个问题。

### 案例二：能免排序的索引，扫 5 万行也赢

```sql
SELECT * FROM t
WHERE (a BETWEEN 1 AND 1000) AND (b BETWEEN 50000 AND 100000)
ORDER BY b LIMIT 1;
```

结果集为空。走 `a` 只需扫约 1,000 行再回表过滤 `b`；走 `b` 要扫约 50,001 行。`EXPLAIN` 选的是 `b`，`rows=50198`——因为 `b` 有序，走它免掉了排序，而排序在代价模型里是要计价的。课程材料给的对比：原句 2.23 秒，`FORCE INDEX(a)` 后 0.05 秒。

### 四条对策，按改动半径排

| 对策 | 命令 | 改的是 | 什么时候用 | 代价 |
|---|---|---|---|---|
| 更新统计 | `ANALYZE TABLE t;` | 库内数据，不动 SQL | `rows` 与实际差几个数量级 | 重算占 I/O；治不了代价模型的偏差 |
| 改写引导 | `ORDER BY b, a LIMIT 1`；子查询套 `LIMIT 100` | 代码，要发版 | 语义等价改写成立 | 只对这一条语句有效 |
| 强制索引 | `SELECT ... FORCE INDEX(a)` | 代码，要发版 | 线上已错、要立刻矫正 | 索引改名/换库都要跟着改，且没人回来删 |
| 增删索引 | `ALTER TABLE t DROP INDEX b;` | 表结构 | 被误用的索引本就不该存在 | DDL 锁与复制延迟，删错要重建 |

`FORCE INDEX` 的语义要记准：优化器列出候选索引后，指定的索引若在候选里就**直接选它，不再比较其他索引的代价**——它绕过的是「比代价」这一步，统计信息一个字没改。

`ORDER BY b` 改成 `ORDER BY b, a` 为什么有效：两个索引都得排序了，扫描行数重新成为唯一变量，优化器于是选只扫 1,000 行的那条。**这个改写只在带 `LIMIT 1` 且语义等价时成立**，不是通用技巧。

## 执行计划里最该看的三列

| 列 | 看什么 | 异常信号 |
|---|---|---|
| `type` / 访问方式 | `ALL`（全表）、`index`（全索引扫描）、`range`、`ref`、`eq_ref` | `ALL` 且行数大 |
| `rows` / `actual rows` | 估算行数 vs 实际行数 | 差 10 倍以上 = 统计信息问题 |
| `Extra` | `Using filesort`、`Using temporary`、`Using index`、`Using where` | `filesort` + 大结果集 = 排序溢出到磁盘 |

> ⚠️ `Using index` 是好事（覆盖索引），`Using index condition` 是索引下推，`Using temporary` 才是要命的——它意味着中间结果落到了临时表（可能写磁盘）。

## 慢日志之外：聚合与逐段耗时

慢日志告诉你「哪条 SQL 超了阈值」，不告诉你「这一类 SQL 一共烧了多少」和「一条语句的时间花在算还是等」。补两个工具就够。

| 工具 | 回答什么 | 命令 | 边界 |
|---|---|---|---|
| `mysqldumpslow` | 同类 SQL 聚合后按维度排序 | `mysqldumpslow -s t -t 10 slow.log` | Perl 脚本；只能聚合，没有执行计划 |
| `SHOW PROFILE` | 语句切成 STATE 后各花多久，CPU 与块 I/O 各占多少 | `SHOW PROFILE CPU, BLOCK IO FOR QUERY 2;` | 会话级；5.7 可用，8.0 起标记弃用 |

```bash
# 前置：装了 perl；日志路径按实际改。本机无 MySQL，未执行。
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log
# -s 排序维度：c 次数 / t 总时间 / at 平均 / l 锁时间 / r 返回行数
# -t 取前 N；-g 'orders' 按正则过滤
```

```sql
-- 会话级，5.7 可用；8.0 起弃用，改用 performance_schema。未执行
SET profiling = ON;
SHOW PROFILES;                           -- 本会话每条语句的 Query_ID 与 Duration
SHOW PROFILE CPU, BLOCK IO FOR QUERY 2;  -- 按 STATE 拆开
```

`SHOW PROFILE` 的用法是一条判据：**某段 STATE 占大头但 `CPU_USER` 很小 → 时间不在计算**。这时查三处：回表随机读（`rows_examined` 大）、缓冲池命中率（[44.3 缓冲池与页面管理](44.3-缓冲池与页面管理.md)）、锁等待（[44.11 锁](44.11-锁.md)）。这三类问题加索引一律无效。

> 🔑 三个工具各管一段：慢日志回答「谁慢」，`mysqldumpslow` 回答「哪一类最贵」，`SHOW PROFILE` 回答「时间花在算还是等」，`EXPLAIN` 回答「为什么选这个计划」。拿一个去证另一个，方向必错。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只看“单次最慢”的 SQL | 优化了长尾，放过了总耗时最大的高频查询 |
| 不看估算行数，只凭 `type` 判断 | `ref` 也可能因为估算错误扫了几十万行 |
| 大批量导入/删除后不 `ANALYZE` | 计划劣化，加索引也没用 |
| 用 `SELECT *` 导致覆盖索引失效、临时表 | 回表 + filesort，慢一个数量级 |
| 对低选择率列建索引 | 优化器不用，白付写放大 |
| 慢日志不按指纹聚合 | 同一类 SQL 的 100 条记录被当成 100 个问题 |
| 把 `Cardinality` 当精确去重数 | 它是采样外推值，页内分布与全表不一致时偏得离谱 |
| `SET GLOBAL long_query_time` 后不重连就以为当前会话生效 | 旧会话仍按老阈值记，改完看不到变化 |
| `FORCE INDEX` 生效后就留在代码里 | 索引改名、换库、分布变化后，救火变成拖累 |
| 把 `SHOW PROFILE` 的 STATE 耗时当成 SQL 的真实成本 | 它含等待，与 `EXPLAIN` 的估算不是一个量纲 |

## 自检

**Q1** 为什么“匹配 10% 行”的查询，加索引反而更慢？

▸ 答案：因为索引扫描的代价是“树高 + 匹配行数 × 随机读”，10 万行回表就是 10 万次随机 I/O（本节模型 `100000 × 4 = 400,000`，远超全表顺序扫的 10,000）；而全表扫描是顺序读，页数固定。优化器会算出这一点并选全表，于是索引不但没用，还多了维护成本。经验阈值：匹配行超过表的 1%–5%，全表往往更划算（取决于行宽与聚簇程度）。

**Q2** `EXPLAIN` 显示 `rows=50`，但 `EXPLAIN ANALYZE` 显示实际扫了 50,000 行，问题出在哪？

▸ 答案：统计信息与实际数据分布不符。常见原因：① 大批量导入/删除后没有重新收集统计信息；② 数据倾斜严重，直方图没覆盖；③ 用了函数或隐式转换，优化器无法用索引统计；④ 参数化查询的“参数敏感”问题（同一 SQL 不同参数，选择率差几个数量级）。修法是先 `ANALYZE`，再看是否需要直方图/索引调整；必要时用 hint 或改写 SQL 强制计划。

**Q3** 慢日志里有一类 SQL 每次只跑 50ms，但每天 10 万次；另一类每天 3 次、每次 3 秒。先优化哪个？

▸ 答案：先算总耗时：前者 `50ms × 100000 = 5,000 秒/天`，后者 `3s × 3 = 9 秒/天`——前者是后者的 500 倍。而且高频 SQL 往往影响更多用户、占用更多连接。正确顺序是按“总耗时（次数 × 平均耗时）”排序，再结合“是否在关键路径”决定。单次最慢的查询适合做容量与超时保护，不一定是第一优先优化对象。

**Q4** 为什么会出现 “昨天还快、今天突然变慢”，而且 SQL 一个字没改？

▸ 答案：因为**统计信息变了**：数据量增长、数据分布变化（如某城市订单暴涨）会让优化器低估/高估行数，从而选错连接顺序或索引。`EXPLAIN` 里 `rows` 估计与实际差几个数量级，基本就是统计信息问题；更新统计信息或改写查询可解。

**Q5** 为什么 “加 hint 强制走某个索引” 只能当最后手段？

▸ 答案：因为 hint 把 “当时的执行计划” **固化**了：数据分布变化后，它可能从 “救火” 变成 “拖累”，而且没人会记得回来删。正确顺序是：修统计信息 → 改查询/加合适索引 → 调优化器参数 → 最后才 hint，并给 hint 加注释与到期 review。

**Q6** `EXPLAIN` 里走索引的 `rows` 只有 37,116，走全表的 `rows` 有 104,620，为什么优化器还是选了全表？

▸ 答案：`rows` 不是判据，**总代价**才是。走索引的每一行都要回主键取整行，代价模型给它乘了一个远大于 1 的权（本节模型里随机读 ≈ 4 次顺序读）；全表扫没有这笔账。37,116 × 回表权 可能已经超过 104,620 次顺序页读。所以「rows 小的计划输给 rows 大的计划」是正常的，**只有当你算出它估错了基数时，才是统计信息的问题**。

**Q7** `FORCE INDEX(a)` 到底跳过了优化器的哪一步？为什么它不算「修好了」？

▸ 答案：它跳过的是「比较各候选索引的代价」这一步：优化器列出候选索引后，只要指定的索引在候选列表里就直接选它。统计信息、代价模型一个字没改，所以数据分布再变一次，它可能从救火变成拖累，而没人会记得回来删。修好的判据是 `ANALYZE` / 改写后 `EXPLAIN` 能自己选对，`FORCE INDEX` 只算「止血」。

**Q8** 一条语句 `SHOW PROFILE` 显示时间几乎都花在 `Sending data` 上，`CPU_USER` 却很小，下一步查什么？

▸ 答案：`Sending data` 大、`CPU_USER` 小说明时间不在计算，在 IO 或等待。按顺序查三处：① `rows_examined` 是否远大于 `rows_sent`（回表/无效扫描）；② 缓冲池命中率是否掉了（[44.3 缓冲池与页面管理](44.3-缓冲池与页面管理.md)）；③ 是否有锁等待（[44.11 锁](44.11-锁.md)）。这三类加索引都可能无效——加索引只治「扫得太多」，治不了「页不在内存」和「行被锁住」。
