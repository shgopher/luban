                    44.8 索引原理 (B+ 树 / 哈希 / 覆盖索引 / 最左前缀)

                    一句话

                    索引是用写放大和空间换更少的页读取：B+ 树赢了范围查询，哈希赢了等值点查，覆盖索引赢在“不回表”——选型不是比谁先进，而是算清“这类查询要读几页”。

                    来源：索引模型与索引维护、覆盖索引与索引下推、普通索引与唯一索引的取舍，来自丁奇《MySQL 实战 45 讲》（极客时间，2019）第 04/05/09 讲；本节 SQL 与实测为本机 MySQL 8.0.46 补充。

                    四种结构，四种胜负

                    结构 等值 范围 排序 写放大 典型场景
                    B+ 树 O(log n) ✅ 叶子有序、区间扫描 ✅ 天然有序 页分裂 绝大多数 OLTP 索引
                    哈希 O(1) ❌ 完全无序 ❌ 低 内存表、等值查找
                    倒排（全文） 按词 ❌ ❌ 高 搜索（45.1 倒排索引与分词）
                    位图 按集合 ⚠️ 低基数 ❌ 中 数仓低基数维度

                    🔑 B+ 树的本质是**“让叶子节点按 key 有序，并且用兄弟指针串起来”**：所以 BETWEEN、ORDER BY、LIMIT 都能在索引上顺序扫，不用回表排序。哈希把 key 打散，天然丢失顺序，所以只能等值。

                    三种模型与一棵“把数据装在自己身上”的树

                    哈希、有序数组、搜索树是三种最朴素的可选模型，它们的差别不在实现难易，而在有序性值多少钱。

                    模型 等值 范围 更新 有序性 典型引擎
                    哈希表 O(1)，数组下标直接定位 ❌ 全扫 只追加，快 主动丢掉 Memcached、部分 NoSQL
                    有序数组 O(log N) 二分 ✅ O(log N) O(N)，要挪动后面全部记录 完整保留 静态数据、内存分析
                    二叉搜索树 O(log N) ✅ O(log N)，但要维持平衡 完整保留 内存结构，不是磁盘索引
                    N 叉树（B+ 树） O(log N)，层数极少 ✅ 叶子有序 O(log N) + 页分裂 完整保留 InnoDB
                    LSM 树 O(log N)，多层查找 ✅ 每层有序 只追加 + 后台 compaction 按层保留 RocksDB、HBase

                    哈希表是“数组 + 哈希函数 + 冲突链”。身份证号 ID_card_n2 算出的槽位是 N，而 User2 和 User4 算出来都是 N，就在这个槽位后面拉一条链表，顺序遍历到 User2。它的好处是插入只往后追加，坏处是四个 ID_card_n 之间没有顺序：要查 [ID_card_X, ID_card_Y] 区间，只能把整个哈希表扫一遍。所以哈希只适用于等值查询。

                    InnoDB 里还有一个容易与哈希索引混淆的东西：自适应哈希索引（AHI）。它不是用户能 CREATE INDEX 的索引，而是引擎在内存里给“被反复访问的 B+ 树页”建的一层哈希，用来少走几层树。它的收益不限于等值—— AHI 只是加速“找到叶子页”这一步，找到之后区间扫描照旧，所以范围查询也能受益。开关是 innodb_adaptive_hash_index。

                    有序数组把有序性用到极致：等值、范围都是 O(log N)，查区间时先二分找到 ID_card_X（不存在就找第一个大于它的），再向右遍历到第一个大于 ID_card_Y 的记录。代价全在写：往中间插一条，后面所有记录都要挪位。所以它只适合静态存储引擎——比如“2017 年某城市的所有人口信息”这种不再改的数据。

                    二叉搜索树在内存里是优等生，落到磁盘上就不及格。100 万节点的平衡二叉树树高 20，一次查询要访问 20 个数据块；机械盘随机读一个块约 10ms，于是单行查询 200ms。真正的问题不是 O(log N) 不够快，而是“每一次树高都要一次随机 I/O”。

                    N 叉树把树高压下来：N 取决于数据块大小。InnoDB 一个整数字段索引的 N 约 1200，树高 4 时能存 1200³ ≈ 17 亿 个值。根页几乎总在内存里，所以 10 亿行的表上查一个整数，最多读 3 次磁盘；第二层也大概率在内存，平均更少。5.6 之后还可以用 innodb_page_size 间接调 N（页越大，一页装的键越多）。

                    结构 100 万行时的树高 点查访问数据块 机械盘估算（10ms/次）
                    平衡二叉树（N=2） 20 20 200ms
                    B+ 树，页 16KB、整数键（N≈1200） 3 3（根常驻则 2） 20–30ms
                    哈希表 1 1 10ms，但只支持等值

                    🔑 磁盘索引的第一性原理不是“查找复杂度”，而是树高 = 随机 I/O 次数。所以每页装尽量多的键（宽键、长主键都会减少每页键数），比优化比较次数重要得多。

                    索引组织表：主键就是数据

                    InnoDB 的表按主键顺序以索引形式存放，这种组织方式叫索引组织表（index organized table）。它有两个直接推论：

                    1. 每个索引在 InnoDB 里都是一棵独立的 B+ 树，一张表 = 一棵聚簇索引 + N 棵二级索引；
                    2. 主键索引的叶子节点存整行数据，所以“按主键查”和“按二级索引查”不是同一件事：后者拿到主键值后还要再搜一次聚簇索引，这就是回表。

                    “主键即数据”还有两个容易被忽略的后果。其一，换主键等于重排整张表——主键不是一列属性，是物理顺序。其二，没有显式主键时 InnoDB 会造一个 6 字节的隐式 rowid 当主键，二级索引里存的就是这个 rowid，所以“没主键也能回表”，但你失去了对物理顺序的控制。

                    想确认一棵索引树到底有多少页、多高，不用猜，直接读统计表：

                    -- MySQL 8.0；需要先 ANALYZE TABLE 让统计信息刷新（本机已执行）
SELECT table_name, stat_name, stat_value
FROM mysql.innodb_index_stats
WHERE database_name = 'idxlab' AND table_name = 'seq_t'
  AND index_name = 'PRIMARY' AND stat_name IN ('n_leaf_pages','size');

                    +------------+--------------+------------+
| table_name | stat_name    | stat_value |
+------------+--------------+------------+
| seq_t      | n_leaf_pages |        747 |
| seq_t      | size         |        801 |
+------------+--------------+------------+

                    n_leaf_pages 是叶子页数，size 是索引总页数（含非叶子页）。这两个数都是采样估算，与实际 ±10% 以内，够用来估树高：5 万行 × 约 208B/行 ÷ 16KB ≈ 660 个叶子页，实测 747 页，一个根页就能指向全部叶子（扇出约 1200），所以树高是 2，与“行宽决定扇出”的算法一致。

                    聚簇索引与二级索引：回表的代价

                    索引类型 叶子存什么 查一行要几次 I/O
                    聚簇索引（主键） 整行数据 树高次（3–4 页），拿到就是整行
                    二级索引 索引列 + 主键值 树高次 + 回表（按主键再查一次聚簇索引）
                    覆盖索引 查询需要的全部列 树高次，不回表
                    package main

import "fmt"

const (
	rows         = 1_000_000 // 表行数
	rowsPerPage  = 100       // 每页 100 行
	treeHeight   = 3         // 扇出约 500 时，1M 行约 3 层
	randReadMs   = 0.10      // 随机读一页
	seqReadMs    = 0.01      // 顺序读一页
)

func pages(n int) int {
	p := n / rowsPerPage
	if n%rowsPerPage != 0 {
		p++
	}
	return p
}

func main() {
	tablePages := pages(rows) // 全表扫描要读的页数

	type result struct {
		name  string
		desc  string
		pages int
		rand  int // 其中随机读的页数
	}
	cases := []result{
		{"主键点查", "B+ 树 3 层", treeHeight, treeHeight},
		{"二级索引查 1,000 行（非覆盖）", "3 页索引 + 1,000 次回表", treeHeight + 10 + 1000, treeHeight + 1000},
		{"二级索引查 1,000 行（覆盖索引）", "3 页索引 + 10 页叶子", treeHeight + 10, treeHeight + 10},
		{"索引下推（索引层过滤）", "扫 1,000 条，仅 120 条回表", treeHeight + 10 + 120, treeHeight + 120},
		{"哈希等值点查", "1 页定位", 1, 1},
		{"哈希做范围查询", "不支持，退化为全表扫描", tablePages, 0},
		{"B+ 树范围查 1,000 行", "3 页索引 + 10 页顺序叶子", treeHeight + 10, treeHeight},
	}

	fmt.Printf("表 %d 行、每页 %d 行、全表 %d 页；随机读 %.2fms、顺序读 %.2fms\n\n",
		rows, rowsPerPage, tablePages, randReadMs, seqReadMs)
	fmt.Printf("%-32s %-28s %-8s %-10s %s\n", "场景", "做什么", "页数", "估算耗时", "备注")

	for _, c := range cases {
		seq := c.pages - c.rand
		ms := float64(c.rand)*randReadMs + float64(seq)*seqReadMs
		note := ""
		if c.name == "二级索引查 1,000 行（非覆盖）" {
			note = "回表是主要成本"
		}
		if c.name == "二级索引查 1,000 行（覆盖索引）" {
			note = "省掉 1,000 次随机读"
		}
		if c.name == "索引下推（索引层过滤）" {
			note = "回表从 1,000 降到 120"
		}
		fmt.Printf("%-32s %-28s %-8d %-10s %s\n", c.name, c.desc, c.pages,
			fmt.Sprintf("%.1fms", ms), note)
	}
}

                    读数：

                    对比 差距 结论
                    非覆盖 vs 覆盖索引 1,013 页 vs 13 页（78 倍） 查的列都在索引里，就不要回表
                    索引下推前后 回表 1,000 → 120（8 倍） 把过滤条件下推到索引层，能少 88% 的回表
                    哈希等值 vs B+ 树等值 1 页 vs 3 页 哈希点查只读 1 页，但代价是丢掉范围与排序
                    哈希做范围查询 10,000 页（全表） 不支持就是全表，索引等于没用

                    🔑 所以“加索引”之前先问：这条查询的列，能不能被一个索引完全覆盖？ 能 → 覆盖索引（最优）；不能 → 至少把过滤条件下推到索引（联合索引把过滤列放在前面）；范围查询与排序 → 只能 B+ 树。

                    覆盖索引与索引下推：消除回表，还是少回表

                    05 讲把回表拆成了一步一步的账。表 T(ID 主键, k, s)、k 上有索引，查 select * from T where k between 3 and 5：

                    1. 在 k 索引上找到 k=3，取到 ID=300；
                    2. 回表查 ID=300 的 R3；
                    3. 在 k 索引上取下一个 k=5，取到 ID=500；
                    4. 回表查 ID=500 的 R4；
                    5. 再取下一条 k=6，不满足，结束。

                    读 k 索引 3 条记录（3、5、6），回表 2 次。 把语句换成 select ID from T where k between 3 and 5，ID 已经在 k 索引的叶子里，第 2、4 步消失——这就是覆盖索引。有个细节值得记住：引擎内部仍然读了 3 条索引记录（k=3、k=5、k=6），但 Server 层只收到 2 行，所以 rows_examined 记的是 2。引擎的扫描行数与 Server 层的扫描行数不是同一个数，排查时两个都要看。

                    市民表那个例子把“该不该多加一个索引”讲清楚了：tuser 上已有 id_card 和 name_age(name, age)，若存在高频请求“按身份证号查姓名”，再加一个 (id_card, name) 联合索引就能覆盖这条查询；如果没有这个高频请求，(id_card, name) 只是多一棵要维护的 B+ 树。索引字段的维护永远有代价，用冗余索引换覆盖，是权衡不是定式。

                    Extra 里看到 含义 还要回表吗
                    Using index 查询列全在索引里，覆盖索引 不回表
                    Using index condition 索引列上的条件被下推到引擎（ICP） 看 select 列表：要索引外的列仍回表
                    Using where 条件留给 Server 层过滤 通常已回表
                    Using index; Using filesort 列覆盖了，但排序没走索引 不回表，但要额外排序

                    EXPLAIN 各列怎么读见 44.9 执行计划与慢查询；这里的判据只有一条——先看 Extra 有没有 Using index，再看有没有回表。

                    本机 10 万行的对照（tuser，KEY idx_name_age(name, age)，姓名首字为「张」的 1 万行）：

                    -- 谓词完全相同，只差选择列表（MySQL 8.0.46，本机已执行）
EXPLAIN SELECT id FROM tuser WHERE name LIKE '张%' AND age = 10;
EXPLAIN SELECT *  FROM tuser WHERE name LIKE '张%' AND age = 10;

                    | id | table | type  | key          | key_len | rows  | filtered | Extra                    |
|  1 | tuser | range | idx_name_age |     136 | 19272 |    10.00 | Using where; Using index |
|  1 | tuser | range | idx_name_age |     136 | 19272 |    10.00 | Using index condition    |

                    EXPLAIN ANALYZE 把“实际做了多少事”也打了出来：覆盖那条是 Covering index range scan，扫 1 万条索引记录、过滤出 2000 行，索引层耗时 8.13ms；回表那条是 Index range scan ... with index condition，回表 2000 次，11.8ms。差距看着不大，是因为这 2000 次回表全部命中缓冲池——行数越多、缓冲池越冷，覆盖索引的收益越接近“每行一次随机读”。

                    索引下推：把索引列上的判断提前

                    同一张市民表，需求是“名字第一个字是张、年龄 10 岁、男孩”：

                    SELECT * FROM tuser WHERE name LIKE '张%' AND age = 10 AND ismale = 1;

                    (name, age) 索引只能按 name LIKE '张%' 定位到第一条满足的记录。5.6 之前，引擎从这里开始一条条回表，把整行取出来再比对 age；原文的例子里回表 4 次。5.6 引入索引下推（index condition pushdown，ICP）后，引擎在遍历索引时就判断 age=10，不相等的直接跳过，于是只对 2 条记录回表（原文图中的 ID4、ID5）——回表从 4 次降到 2 次。变化不在 B+ 树结构，而在存储引擎接口多了一个“把条件下推”的能力。

                    本机把开关拨到关，同一语句的差别是量级上的：

                    -- 会话级开关，8.0 默认 on（本机已执行）
EXPLAIN ANALYZE SELECT * FROM tuser WHERE name LIKE '张%' AND age = 10 AND ismale = 1;
SET optimizer_switch = 'index_condition_pushdown=off';
EXPLAIN ANALYZE SELECT * FROM tuser WHERE name LIKE '张%' AND age = 10 AND ismale = 1;
SET optimizer_switch = 'index_condition_pushdown=on';
                    开关 Extra 索引层实际读 索引层耗时 外层过滤
                    on Using index condition; Using where 2000 行 5.16ms 5.31ms
                    off Using where 10000 行 44.9ms 45.8ms

                    （单次执行、数据全在缓冲池，耗时只作量级参考；行数是稳定的。）

                    🔑 ICP 与覆盖索引解决的不是同一件事：覆盖索引把回表次数变成 0，ICP 只是把回表次数从“满足最左前缀的行数”压到“满足全部索引列条件的行数”。ismale 不在索引里，所以它一定要回表后再过滤；想让 ismale 也被下推，只能把它加进索引。

                    ⚠️ ICP 只对索引里存在的列生效。把过滤列放在范围条件之后（(a, b) 上 a > ? AND b = ?），b 既不能定位也不能下推——索引列顺序错了，ICP 也救不回来。

                    行宽决定扇出：一次可复现的层数实验

                    上面的模型用“每页 100 行”是为了好算；真实 InnoDB 页是 16KB，每页能放几行由行宽决定，而每页行数直接决定 3 层能装多少行。

                    书里（p134–140）用 MySQL 8.0.28 + char(255)×4 造出 1024B 定长行，实测：

                    行数 结果 说明
                    1 1 层 index_tree.ibd 112KB
                    15 首次分裂成 2 层 页 5 存 7 行、页 6 存 8 行，页可用 14–15KB
                    16500 仍 2 层 根页有 1180 个指针
                    17000 转 3 层 只改 3 个页：旧根复制、新兄弟页、重初始化根
                    21,427,000 转 4 层 24GB，仍然只改 3 个页

                    由 (14×1024/12)×14 = 16725 与实测吻合，可反推页指针 12B（int 主键）或 16B（bigint），页号 8B。

                    换成生产行宽就能复算：

                    #!/usr/bin/env python3
"""3 层 B+ 树的容量上限：行宽 → 每页行数 → 扇出 → 行数。"""

PAGE = 14 * 1024          # 16KB 页扣掉头部/槽位，可用约 14KB
PTR = 12                  # int 主键：4B id + 8B 页号
PTRS_PER_PAGE = PAGE // PTR

for row_bytes in (900, 1024, 5120):
    rows_per_page = PAGE // row_bytes
    limit3 = PTRS_PER_PAGE ** 2 * rows_per_page
    print(f"行宽 {row_bytes:>4}B：每页 {rows_per_page:>2} 行，3 层上限 {limit3:,} 行")

# 行宽  900B：每页 15 行，3 层上限 21,384,540 行
# 行宽 1024B：每页 14 行，3 层上限 19,958,904 行
# 行宽 5120B：每页  2 行，3 层上限  2,851,272 行

                    读数：

                    行宽 每页行数 3 层上限 结论
                    0.9KB（订单商品表实测） 15 ≈2138 万 “2000 万”这个经验值大致成立
                    1KB 14 ≈1996 万 书里实测 2142.7 万转 4 层，数量级一致
                    5KB 2 ≈285 万 行太宽，先垂直分表，不是先水平分片

                    所以“2000 万行必须分表”是层数边界，不是性能悬崖：3 层转 4 层只多一次页读（有 Buffer Pool 时上层页几乎常驻）。真正该分表的情况是：单行太宽、varchar 导致页内行数不均、频繁删改产生碎片、单文件过大。判据与顺序见 44.14 分库分表。

                    ⚠️ 别把“层数边界”当成“性能拐点”，也别反过来说“永远不用分表”：本书另一处（p209）用“B+ 树复杂度超线性”论证“单机也要分 256 张表”，那句话是错的——B+ 查找是 O(log n)，不是超线性；分表的理由是写吞吐/DDL 窗口/单文件，不是查询复杂度。

                    主键怎么选：自增、业务字段与页分裂

                    B+ 树为了维持键有序，插入时要维护位置。04 讲的例子：ID 依次是 100、200、300、500、600，插入 700 只在最后一个记录后面追加；插入 400 就要逻辑上挪动后面的记录腾位置。更糟的是目标页已经满了——此时要申请一个新页、把一部分记录挪过去，这个动作叫页分裂。

                    页分裂有两个后果：一是当次插入变慢（要搬数据、改兄弟指针）；二是空间利用率下降，原本一页的数据分到两页，填充率大约掉一半。删除方向有反向动作页合并：相邻两页利用率都很低时合并成一页，另一页被释放。5.7 之后这个“很低”有了名字和默认值：MERGE_THRESHOLD，默认 50%，可以按索引单独设：

                    -- 页内填充率低于 40% 时更积极地与相邻页合并（MySQL 5.7+，本机 8.0.46 已执行）
ALTER TABLE orders DROP INDEX idx_k, ADD INDEX idx_k (k) COMMENT 'MERGE_THRESHOLD=40';

                    50 的含义是“页内数据占比低于 50% 就考虑合并”，调大更省空间但更容易在后续插入时再次分裂，调小则相反。它只影响页的合并时机，不改变唯一性与可见性。

                    于是主键选择就变成一道成本题：

                    主键 插入形态 页分裂 二级索引叶子里的主键 适用
                    AUTO_INCREMENT 整型 追加到最右 基本不发生 4 字节（bigint 8 字节） 绝大多数 OLTP 表
                    业务字段（身份证 20 字节） 无序，随机落页 频繁 每个二级索引都多 20 字节 只有一个索引且必须唯一（KV）
                    雪花 / 号段（趋势递增，8 字节） 近似追加 很少 8 字节 分库分表后的替代方案
                    UUID() / CHAR(36) 完全随机 最频繁 36 字节起 只适合当业务 ID，不适合当主键

                    存储空间的账要算两遍。第一遍在聚簇索引：随机主键让页填充率变低，同样的行数占更多页。第二遍在每个二级索引：二级索引的叶子存的是主键值，主键越长，每棵二级索引都跟着变胖。原文的数字：身份证号做二级索引键约 20 字节，整型主键 4 字节，bigint 8 字节——一张有 5 个二级索引的表，主键从 4 字节换成 20 字节，等于凭空多出 5 份 16 字节/行。

                    本机把这件事压成了两个可比的数字：同样是 5 万行、CHAR(200) 的行，一份按 id 递增插入，一份按 ORDER BY RAND(42) 随机顺序插入：

                    表 插入顺序 叶子页 size（总页） data_length 每行摊到的页字节
                    seq_t 递增 747 801 12.5MB 245B
                    rand_t 随机 1062 1249 19.5MB 348B

                    行数完全一样，随机插入多用了 42% 的叶子页、56% 的磁盘。这不是“随机插入慢一点”，而是同样的数据永久多占一半空间，还会让后续每次范围扫描多读页、缓冲池能装下的行数变少。

                    🔑 自增主键的收益有两层：写路径上“只追加、不分裂”，空间上“主键最短、所有二级索引最小”。所以“建表必须有自增主键”这条规范在大多数场景成立——例外是 KV 表：只有一个索引，且该索引必须是唯一索引。这时把业务字段直接做主键，可以避免“先查二级索引再回表”走两棵树，主键长度也只影响这一棵树。

                    innodb_page_size 与重建索引

                    innodb_page_size 决定一页装多少键，也就决定了 N 叉树的 N。可选 4KB / 8KB / 16KB（默认）/ 32KB / 64KB，只能在初始化实例时设定，之后不能在线改（改它等于重建整个实例）。页越大扇出越大、树越矮，但单次读的 I/O 更大、页分裂时要搬的字节更多；页越小适合小行宽与写密集的 SSD 场景，代价是树更高。5.6 之后调页大小是“间接调 N”的官方手段。

                    顺带把 05 讲那道重建索引的思考题收掉。重建二级索引 k：

                    ALTER TABLE T DROP INDEX k;
ALTER TABLE T ADD INDEX k;

                    这两句是合理的：新索引按顺序插入构建，页利用率最高，能消掉删除与页分裂留下的空洞。但重建主键：

                    ALTER TABLE T DROP PRIMARY KEY;
ALTER TABLE T ADD PRIMARY KEY(id);

                    不合理。删主键和加主键都会重建整张表，第一句的成果被第二句推翻，等于把表重建了两次。要重建就用一条：

                    ALTER TABLE T ENGINE=InnoDB;   -- 8.0 为原地重建，仍需额外磁盘空间与 DDL 窗口

                    空洞怎么产生、重建怎么选在线 DDL 算法，见 44.27 InnoDB 表空间与在线 DDL；这里只记结论：索引的“紧”是靠顺序构建换来的，跑久了的表一定会松。

                    普通索引还是唯一索引：差在写路径，不在读路径

                    同一个字段（例如身份证号），业务代码已经保证不会重复，建普通索引还是唯一索引？读的差别可以忽略，写的差别能大到「整库堵住」。

                    路径 唯一索引 普通索引 差在哪
                    等值查询命中 找到第一条即停 找到第一条后还要看下一条是否同值 一次指针移动，页已在内存，可忽略
                    更新，目标页在内存 判断冲突 → 改内存 直接改内存 一次比较，可忽略
                    更新，目标页不在内存 必须把页读进来才能判断是否重复 → 一次随机读 变更记进 change buffer，事务即可结束 随机读 vs 一次顺序写日志

                    🔑 唯一索引用不上 change buffer：唯一性判断必须先把数据页读进内存，页都读进来了，直接改内存本来就快，缓存变更没有意义。所以「唯一」买到的是约束，付出的是写路径上每页一次随机读。

                    change buffer 在做什么

                    更新一个不在内存的页时，InnoDB 不急着读盘：把「哪个页要插哪一行」记进 change buffer（内存里有拷贝，也会落到系统表空间 ibdata1），下次查询真正要访问这个页时，再把页读进来、把积压的变更应用上去，这个过程叫 merge。后台线程会定期 merge，正常 shutdown 也会 merge。

                    机制 省掉的是什么 位置
                    redo log 随机写盘 → 顺序写 ib_logfile*
                    change buffer 随机读盘 buffer pool 内存 + ibdata1

                    两条容易混：redo log 保证「崩溃不丢」，change buffer 保证「更新不必先读页」。掉电重启后，change buffer 里已持久化的部分由 redo 重放恢复，未持久化但已提交的部分同样在 redo 里——change buffer 不是内存里的临时变量。

                    [mysqld]
innodb_change_buffer_max_size = 50   # 占 buffer pool 的上限（%），默认 25、最大 50

                    50 的语义是「change buffer 最多占 buffer pool 的一半」，不是「写缓存占磁盘 50%」。写多读少的归档库、账单库开到最大；写入后立刻要读的库反而该关小——马上 merge 等于白记一遍，只多付维护成本。change buffer 挤占的是缓冲池的内存，命中率的账要一起算（44.3 缓冲池与页面管理）。

                    -- 验证：看 change buffer 的合并次数与占用（MySQL 8.0，本机无实例，未执行）
SELECT NAME, COUNT FROM information_schema.INNODB_METRICS WHERE NAME LIKE 'ibuf%';

                    change buffer 的 merge 时机与真实收益

                    merge 有三个触发点，顺序就是收益消失的顺序：

                    触发点 谁触发 对写入延迟的影响
                    后续查询要读这个页 前台线程，读页时顺带 merge 写入时省下的随机读，在读到的时候还回来
                    后台线程定期 merge ibuf_merge 类后台线程 不在用户路径上，但占 I/O
                    实例正常 shutdown 关闭流程 启动后不用再重放，重启更干净

                    所以判断“这个库该不该依赖 change buffer”，只看一件事：一个页在 merge 之前能攒下多少次变更。攒得越多，一次随机读摊掉的写越多，收益越大；写完立刻就读，页马上被读进内存并 merge，等于白记一遍，还多付了维护成本——这正是原文说的“写多读少（账单、日志）收益最好，写完马上查反而起副作用”。

                    原文对小节的收尾是两句判断，都没有给 tps 数字，不要替它编：机械盘上 change buffer 的收效非常显著，历史数据库如果出于成本跑在机械盘上，应尽量用普通索引并把 change buffer 开大；SSD 上收益变小但仍存在，因为省掉的是随机读的次数，SSD 只是把每次随机读变便宜了，次数没变。

                    change buffer 与 redo log 的分工，原文用一条插入语句把四个部件串了起来：insert into t(id,k) values(id1,k1),(id2,k2)，k1 所在页在内存、k2 所在页不在内存。

                    步骤 动作 落点
                    1 Page 1 在内存，直接改内存 buffer pool
                    2 Page 2 不在内存，记“要往 Page 2 插一行” change buffer（内存 + ibdata1）
                    3 上面两个动作都记进 redo log ib_logfile*，顺序写

                    事务到这里就结束了：两次内存写 + 一次顺序磁盘写。之后读 Page 1 直接从内存返回（磁盘上还是旧值也正确）；读 Page 2 才把页读进来、应用 change buffer 里的操作再返回。所以两者的账要分开记：redo log 省的是随机写，change buffer 省的是随机读。

                    原文也解释了“为什么唯一索引用不上”：插入 (4,400) 前必须先确认 k=4 不存在，这个判断要求把数据页读进内存；页都进来了，直接改内存更快，再记一遍 change buffer 没有意义。

                    本机把“收益从哪来”量了出来。判据不是“有没有普通索引”，而是二级索引的工作集有没有超过缓冲池：

                    -- 关键条件：容器固定 innodb_buffer_pool_size=128M（本机 8.0.46，一次真实运行）
-- 表：600000 行，主键自增（顺序），二级索引键是 192 字符的随机串
SELECT ROUND(data_length/1024/1024,1) AS data_mb,
       ROUND(index_length/1024/1024,1) AS index_mb
FROM information_schema.tables
WHERE table_schema = 'idxlab' AND table_name = 'cb_wide';
-- data_mb 134.6 / index_mb 202.0 → 数据 + 索引 336MB，是缓冲池的 2.6 倍

                    -- SHOW ENGINE INNODB STATUS 的 change buffer 段（同一时刻）
INSERT BUFFER AND ADAPTIVE HASH INDEX
-------------------------------------
Ibuf: size 305, free list len 236, seg size 542, 5329 merges
merged operations:
 insert 35192, delete mark 0, delete 0

                    size 305 是 change buffer 里积压的页数，5329 merges 是累计合并次数，insert 35192 是被合并进去的插入操作数。对照实验是同样形状的小表（插入 2 万行后约 12 万行，数据 25.5MB + 索引 39MB，合计 65MB，缓冲池装得下）：批量插 2 万行后 Ibuf 仍是 size 1, 0 merges，物理读只增加 57 页；把同一批数据插进唯一索引版本，物理读增加 67 页、Ibuf 同样不动。

                    场景 工作集 vs 缓冲池 Ibuf 计数 结论
                    12 万行小表 + 唯一索引 装得下 0 merges，物理读 +67 页常驻，唯一索引的“判重读页”不产生额外 I/O
                    12 万行小表 + 普通索引 装得下 0 merges，物理读 +57 页常驻，change buffer 也无事可做
                    60 万行宽二级索引 + 普通索引 2.6 倍 5329 merges / 305 页积压 页被挤出缓冲池，随机插入才真正走 change buffer

                    🔑 唯一索引与普通索引的写路径差距，只在目标页不在缓冲池时才出现：页在内存，两者都只改内存（本机 +67 与 +57 个物理读，差异在噪声内）；页不在内存，普通索引记 change buffer 就返回，唯一索引必须先把页读进来。所以“小表上测不出差别”不是结论错了，是没测到条件。

                    💡 线上临时降级：SET GLOBAL innodb_change_buffering = 'none' 可整体关掉（默认 all，可选 inserts/deletes/changes），用完记得改回；innodb_change_buffer_max_size 只调上限（默认 25，最大 50），不改变“能不能用”。两者都不影响正确性，只影响随机读的量。

                    一个真实量级的后果

                    某业务把一条普通索引改成唯一索引，buffer pool 命中率从 99% 掉到 75%，更新语句全部堵住。原因就是原来写密集的插入全走 change buffer，改完每一行都要把目标页读进内存——随机读把缓冲池冲干净了，命中率再往下掉，恶性循环。排查这类「没改 SQL、没涨流量，写入突然变慢」时，先看最近有没有人动过索引的唯一性。

                    你的情况 选什么
                    业务代码能保证不重复（且不打算靠 DB 兜底） 普通索引，写路径吃 change buffer
                    业务不能保证，或要求数据库做约束 唯一索引，没得选；性能问题另找出口（拆批、归档）
                    写多读少：账单、日志、归档库 普通索引 + innodb_change_buffer_max_size 开大，机械盘收益尤其明显
                    写完立刻读（如先插后查的幂等表） 普通索引但把 change buffer 关小，避免「记完马上 merge」

                    字符串字段：全字段、前缀、倒序、哈希列

                    长字符串（邮箱、身份证号、URL）直接建全字段索引的问题是索引太宽：页里放的键少了，树变高，写放大也大。四种做法的差别不在「省不省空间」，而在扫描行数、能否覆盖、能否范围查。

                    方案 空间 扫描行数 覆盖索引 范围查询 额外 CPU
                    全字段索引 (email) 最宽 1 行 ✅ ✅ 无
                    前缀索引 (email(6)) 最省 可能多行（本例 4 行） ❌ 永远回表 ✅ 无
                    倒序存储 + 前缀索引 省 可能多行 ❌ ❌ reverse()
                    哈希列 crc32() + 索引 4 字节 接近 1 行 ❌ ❌ crc32()

                    前缀索引的第一个代价是回表次数：email(6) 只索引 zhangs，同一前缀下的行全要回表比对，例子里扫了 4 行才命中；把长度改成 email(7)（前缀 zhangss 已唯一）就只扫 1 行。

                    第二个代价更隐蔽：前缀索引永远用不上覆盖索引。哪怕 email(18) 已经把整个字段装下，InnoDB 仍然要回主键再确认一次——它无法证明前缀没有截断完整值。SELECT id, email 这种本来能覆盖的查询，在前缀索引上仍然回表。

                    长度靠区分度定，不靠猜：

                    -- 1) 基线：全列有多少个不同的值
SELECT COUNT(DISTINCT email) AS L FROM SUser;

-- 2) 各前缀长度的不同值个数，取「不低于 L 的 95%」的最短长度
SELECT COUNT(DISTINCT LEFT(email,4)) AS L4,
       COUNT(DISTINCT LEFT(email,5)) AS L5,
       COUNT(DISTINCT LEFT(email,6)) AS L6,
       COUNT(DISTINCT LEFT(email,7)) AS L7
FROM SUser;

-- 3) 建索引（8.0，Online DDL，不锁表；本机无实例，未执行）
ALTER TABLE SUser ADD INDEX idx_email6 (email(6)), ALGORITHM=INPLACE, LOCK=NONE;

                    5% 是可接受的区分度损失，可以按业务调；关键是先量再建，不要凭「取前 6 位」的直觉。

                    前缀区分度天然不够时（身份证号前 6 位是地址码，同县的人全一样），换第 3、4 种做法：

                    -- 倒序存：写时 reverse，读时也 reverse，索引按倒序字符串排序
UPDATE t SET id_card = REVERSE(id_card);
SELECT * FROM t WHERE id_card = REVERSE(?);

-- 哈希列：4 字节索引，冲突概率极低，但必须回表比对原值
ALTER TABLE t ADD COLUMN id_card_crc INT UNSIGNED, ADD INDEX idx_crc (id_card_crc);
SELECT * FROM t WHERE id_card_crc = CRC32(?) AND id_card = ?;

                    两种都不支持范围查询：倒序索引按「倒着的字符串」有序，哈希列干脆无序。需要 BETWEEN、前缀匹配、排序的字段，只能回到全字段索引。

                    🔑 字符串索引的判据是**「这条查询要不要范围 / 要不要覆盖」**：只要等值、又要省空间 → 前缀、倒序、哈希三选一；要范围或要覆盖 → 只能全字段，代价是接受索引宽度。

                    最左前缀：不是规则，是物理事实

                    联合索引 (a, b, c) 在 B+ 树里是按 (a, b, c) 的字典序排列的：

                    (a=1,b=1,c=1) → (1,1,2) → (1,1,3) → (1,2,1) → (1,2,2) → (2,1,1) → ...

                    所以：

                    查询条件 能否用索引 为什么
                    a=1 ✅ 按 a 有序
                    a=1 AND b=2 ✅ 前缀连续
                    a=1 AND b=2 AND c=3 ✅ 完整前缀
                    b=2 ❌ b 在 a 相同的前提下才有序，跨 a 无序
                    a=1 AND c=3 ⚠️ 只用 a，c 靠回表过滤 c 跳过了 b
                    a>1 AND b=2 ⚠️ 只用 a 的范围 范围之后 b 不再有序

                    ⚠️ 最常见的误解：“把选择性最高的列放最左”。真正的最左规则是**“等值条件放前面、范围条件放最后”**——因为范围一旦出现，它右边的列在索引里就不再有序，无法继续用于定位。

                    索引复用与 ORDER BY：一个索引能服务几种查询

                    最左前缀的直接用途不是“记规则”，而是少建索引。已经有 (a, b) 时：

                    查询形态 能用 (a, b) 吗 说明
                    a = ? ✅ 用 a 定位，b 不参与
                    a = ? AND b = ? ✅ 完整前缀
                    b = ? ❌ b 只在 a 相同的前提下有序，跨 a 无序
                    a = ? ORDER BY b ✅ a 是常量，剩下的 b 天然有序
                    a > ? ORDER BY b ❌ 排序 a 是范围，b 在范围内不再有序

                    所以有 (a, b) 就不必再单独建 (a)——这正是原文说的第一原则：如果调整顺序能少维护一个索引，这个顺序就优先。反过来的情形（查询条件里只有 b）只能再建一个 (b)；这时要考虑的是空间，而不是顺序。原文的市民表就是例子：name 字段比 age 大，所以建 (name, age) + (age)，比建 (age, name) + (name) 更省。

                    同一原则还有一个用法：高频请求“按身份证号查姓名”，建 (id_card, name) 既覆盖了它，又能用最左前缀服务“按身份证号查地址”（地址回表）。一个联合索引服务两条查询，靠的是最左前缀 + 覆盖。

                    ORDER BY 走索引的三个条件

                    排序能不能免掉，Extra 里有没有 Using filesort 是唯一判据。本机 5000 行、KEY idx_ab(a, b) 的四种写法：

                    -- MySQL 8.0.46，本机已执行；table 名 t_order
EXPLAIN SELECT a, b FROM t_order ORDER BY a, b LIMIT 10;
EXPLAIN SELECT a, b FROM t_order WHERE a = 3 ORDER BY b LIMIT 10;
EXPLAIN SELECT a, b FROM t_order ORDER BY b LIMIT 10;
EXPLAIN SELECT a, b FROM t_order WHERE a > 3 ORDER BY b LIMIT 10;
                    SQL 形态 type rows Extra 为什么
                    ORDER BY a, b LIMIT 10 index 10 Using index 顺着索引叶子读，读到 10 行就停
                    WHERE a=3 ORDER BY b LIMIT 10 ref 50 Using index a 是常量，剩下的 b 有序
                    ORDER BY b LIMIT 10 index 5000 Using index; Using filesort b 跨 a 无序，只能整棵索引读出来再排
                    WHERE a>3 ORDER BY b LIMIT 10 range 4800 Using where; Using index; Using filesort 范围之后 b 不再有序

                    三个条件可以合成一句话：排序键必须是“等值前缀 + 排序列”这个连续前缀。a=3 是等值前缀，所以 ORDER BY b 能免排序；a>3 是范围，b 的有序性在范围里就断了。

                    ⚠️ ORDER BY b LIMIT 10 的 rows=5000 不是“只扫 5000 行”，而是全索引扫描：type=index 表示要读完整个索引，filesort 之后 LIMIT 才生效。能提前终止的只有第一行那种“索引顺序与排序顺序一致”的计划，读到 10 行就收工。

                    💡 8.0 支持降序索引（KEY idx (a, b DESC)），混合方向排序（ORDER BY a ASC, b DESC）才可能免掉 filesort；5.7 之前声明 DESC 会被忽略。这条与“最左前缀”无关，是索引列自身的排序方向。

                    💡 本节的四组「本机实测」全部可复现：插入顺序与叶子页、覆盖索引与 ICP、ORDER BY 三种结局、change buffer 的 ibuf 计数。完整脚本在仓库 tools/examples/44.8-index-lab/，bash code/run.sh 一条命令起容器、灌数、跑完并清理（change buffer 那组约 2 分钟，SKIP_CB=1 可跳过）。

                    反模式

                    反模式 后果
                    给每个列都建单列索引 写放大、优化器选择困难，回表依旧
                    按「2000 万」一刀切分表 行宽 5KB 时 285 万就该处理，行宽 0.9KB 时 2000 万仍可承受
                    联合索引顺序按“选择性”而不是“查询形态”排 范围列放前面，后面的列全废
                    用 SELECT * 导致覆盖索引失效 每次查询都回表
                    在索引列上做函数/隐式转换（WHERE DATE(ts)=...） 索引失效，全表扫描
                    用哈希索引做范围/排序 退化为全表
                    索引列太多（超宽联合索引） 索引本身比数据大，写放大严重
                    业务能保证唯一，仍建唯一索引 写路径失去 change buffer，写密集时命中率与吞吐一起掉
                    用前缀索引还想让查询覆盖 InnoDB 无法证明前缀没截断，永远回表，覆盖收益归零
                    对身份证号直接建 (id_card(6)) 前 6 位地址码区分度极低，回表放大几十倍
                    给倒序列或哈希列写范围查询 两种方案只支持等值，范围条件直接退化成全表扫
                    给重复度 >10% 的列建单列索引（经验阈值） 优化器多半不用，白付写放大；真判据是选择率 × 回表成本
                    索引越多越好 每个索引都要维护；索引过多还会增加优化器“筛可用索引”的时间
                    用身份证、手机号等业务字段做主键（非 KV 表） 随机插入触发页分裂、页利用率降到约一半；主键被每个二级索引复制一份，索引集体变胖
                    把 DROP PRIMARY KEY + ADD PRIMARY KEY 当“重建主键” 两条语句各自重建整表，第一句的成果被第二句推翻；用 ALTER TABLE ... ENGINE=InnoDB
                    用 count(*) 相同判断两张表一样紧 行数相同，随机插入的叶子页可以多 42%、磁盘多 56%
                    在小表上没测出差别就否定 change buffer 页常驻缓冲池时机制本就不介入；工作集超池才会出现 merges
                    在 (a, b) 上写 WHERE b = ? 还指望走索引 最左前缀不成立，退化为全表扫描或全索引扫描
                    用 (a, b) 索引配 ORDER BY b 还指望免排序 b 跨 a 无序，只能 filesort，LIMIT 也挡不住全索引扫描
                    指望 ICP 救“范围列之后的过滤列” 范围之后列既不参与定位也不参与下推，回表放大到全部前缀行

                    自检

                    Q1 为什么“二级索引查 1000 行”比“覆盖索引查 1000 行”慢几十倍，而“点查一行”两者差不多？

                    ▸ 答案：因为回表是按行数线性增长的：每回表一次就是一次随机 I/O（查聚簇索引的另一棵 B+ 树）。点查时回表只有 1 次，占比小；1000 行时回表 1000 次，直接主导成本。覆盖索引把查询需要的列都放在二级索引叶子里，回表次数为 0，所以行数越多差距越大。

                    Q2 WHERE b=2 用不上 (a,b,c) 联合索引，加一个 (b) 单列索引就好了吗？

                    ▸ 答案：取决于查询形态。如果这条查询很频繁且只需要 b，加 (b) 或 (b, 查询需要的列) 覆盖索引是合理的；但如果它只是偶尔出现，多一个索引会带来写放大与空间成本（每个索引都要维护 B+ 树）。更常见的做法是调整查询或联合索引顺序，让高频查询走同一个索引。索引是写路径的成本，不是免费的读优化。

                    Q3 索引下推（ICP）到底省了什么？为什么它不能省掉“回表”本身？

                    ▸ 答案：ICP 把“能在索引列上判断的条件”下推到存储引擎层，在回表之前先过滤掉不满足的行，从而减少回表次数（本节 1000 → 120）。但它仍然要回表取“索引里没有的列”，所以只能减少、不能消除回表。要消除回表，只能让索引覆盖查询需要的全部列。

                    Q4 为什么在索引列上做函数运算（如 WHERE date(created_at)='2026-01-01'）会让索引用不上？

                    ▸ 答案：因为 B+ 树索引存的是列的原值，不是 “函数结果”。对列做函数后，优化器无法用原值的有序性定位，只能逐行计算再比较（全表扫描）。解法是 “改写成范围查询”（created_at >= '2026-01-01' AND < '2026-01-02'）或建 “函数索引/生成列索引”。

                    Q5 一张表建了 10 个索引，写入会付出什么代价？怎么判断 “索引太多”？

                    ▸ 答案：每个索引都是一棵 B+ 树：每次写入要更新所有索引，写放大与锁开销随索引数线性增长，还会占缓冲池。判据是 “索引的使用次数”——把长期零命中（或只被低效查询用到）的索引删掉；通常单表 5–6 个索引以上就要逐个 review。

                    Q6 同样是 WHERE id_card = ? 的查询，唯一索引和普通索引的读性能差多少？写性能又差多少？为什么差在写上？

                    ▸ 答案：读几乎不差——唯一索引命中第一条就停，普通索引要多看一条是否同值，而那一页已经在内存里，只多一次指针移动。写差在目标页不在内存时：唯一索引必须先读页才能判断是否重复，也就是每行多一次随机读；普通索引把变更记进 change buffer 就返回，随机读被推迟到 merge。所以「唯一」是用写路径的随机读换一个数据库级约束。

                    Q7 为什么 email(18) 已经把整个 email 装进索引了，SELECT id, email 还是要回表？

                    ▸ 答案：因为 InnoDB 无法证明「18 字节的前缀」等于「完整值」：email 是 varchar，索引里存的只是前 18 个字节，系统不确定有没有第 19 个字节。所以前缀索引一律按「不覆盖」处理。要覆盖只能建全字段索引 (email)。

                    Q8 身份证号要按等值查，前缀区分度太低，用倒序还是加 crc32 哈希列？

                    ▸ 答案：看要不要范围查询与要性能稳定还是要省空间。两种都只支持等值：倒序省一个字段但仍是前缀索引、平均扫描行数大于 1、每次读多一次 reverse()；哈希列固定 4 字节、扫描行数接近 1、性能稳定，代价是多一个字段和一次 crc32()，并且必须回表用原值确认（哈希会冲突）。有范围需求时两者都不能用，只能全字段索引或改用别的检索结构。

                    Q9 同样是 2000 万行，为什么有的表“什么事都没有”，有的表查询已经明显变慢？

                    ▸ 答案：因为 2000 万只是“3 层转 4 层”的行数边界，不是性能拐点。变慢通常来自四件事：① 行太宽，每页只放几行，3 层容量掉到几百万；② varchar 变长导致页内行数不均、树不平衡；③ 频繁删改产生碎片，页填充率低；④ 单文件过大，文件系统/IOPS 变差。先算“行宽→每页行数→3 层上限”，再看 Buffer Pool 是否装得下热数据，最后才决定垂直分表还是水平分片（44.14）。

                    Q10 两张表行数完全相同，count(*) 都是 5 万，但 information_schema.TABLES 里一张 12.5MB、另一张 19.5MB。数据一模一样，多出来的 7MB 是什么？

                    ▸ 答案：是页分裂留下的空位。两张表的数据相同，但插入顺序不同：递增插入只在最右页追加，页填充率接近满；随机顺序插入会让目标页反复分裂，每分裂一次就有一半空间长期空着。本机 5 万行实测叶子页 747 vs 1062。所以 data_length 的大小不只看行数，还要看行的“写入历史”；要回收只能重建（ALTER TABLE ... ENGINE=InnoDB），删数据不会把空位还给操作系统。

                    Q11 在 128MB 缓冲池的实例上，反复查 SHOW ENGINE INNODB STATUS 都看到 Ibuf: size 1 ... 0 merges，能不能据此判断“change buffer 没生效、普通索引白建了”？

                    ▸ 答案：不能。change buffer 只在目标页不在缓冲池时介入；表小、索引页全部常驻时，普通索引和唯一索引都直接改内存，Ibuf 自然一直是 1（空）。本机对照：12 万行小表批量插入 2 万行，Ibuf 不动、物理读只多 57–67 页；把规模放大到 60 万行、二级索引 202MB（数据+索引 336MB，是缓冲池的 2.6 倍），才出现 size 305 / 5329 merges / insert 35192。判断依据是“工作集 / 缓冲池”的比值，不是开关有没有打开。
