# 44.25 MySQL 运维与故障处置

## 一句话

> 值班时真正要答的只有五个问题：**删错了怎么恢复、kill 不掉怎么办、自增 ID 用完了怎么办、分区表什么时候用、权限改了为什么不生效**——每个都有确定的判据和命令，靠现场翻文档来不及。

## 误删数据：四种删法，四条恢复路径

恢复能力由「删的时候 binlog 里留下了什么」决定，不由「删了多少」决定。

| 删法 | binlog 里记的是什么 | 能否闪回 | 恢复路径 |
|---|---|---|---|
| `DELETE FROM t WHERE ...` | ROW 格式下的 `Delete_rows` 事件（**有完整行镜像**） | ✅ | Flashback / binlog2sql：把 `Delete_rows` 反写成 `Write_rows` 重放 |
| `TRUNCATE TABLE` / `DROP TABLE` | **statement**：只有一句 truncate/drop | ❌ | 全量备份 + binlog 重放到误操作前 |
| `DROP DATABASE` | statement | ❌ | 同上，整库恢复 |
| `rm` 掉 `.ibd` 文件 | 什么都没有 | ❌ | 备库 / 延迟从库，或全量备份 |

闪回的前提是两个参数，缺一不可：`binlog_format=ROW` 且 `binlog_row_image=FULL`。只配了 ROW 而 image 是 `MINIMAL` 时，binlog 里只有被改的列，反写出来的行不是原来那一行。

```sql
-- 检查闪回前提（MySQL 8.0，本机无实例，未执行）
SHOW VARIABLES LIKE 'binlog_format';        -- 必须是 ROW
SHOW VARIABLES LIKE 'binlog_row_image';     -- 必须是 FULL
```

恢复的三条事件反写规则：`insert` ↔ `delete` 互换，`update` 对调前后镜像。**必须在临时实例上重放**（最近的全量备份，或一个从库）——直接在主库重放，会把别人这段时间的正常修改一起覆盖掉。

`truncate` / `drop` 只能走「全量 + 增量」：

| 步 | 动作 | 关键参数 |
|---|---|---|
| ① | 取最近一次全量备份（假设每天 0 点） | — |
| ② | 用备份恢复出一个临时实例 | — |
| ③ | 从 binlog 备份取 0 点之后的日志 | `mysqlbinlog --database=db1` 限定库 |
| ④ | 重放到**误操作之前**那一刻 | 无 GTID：`--stop-position`；有 GTID：`SET gtid_next='误操作的 gtid'; BEGIN; COMMIT;` 造一个空事务把它跳过 |
| ⑤ | 校验后回灌主库 | 先比对数，再按主键回写 |

> ⚠️ 这条链路慢在两处：`mysqlbinlog` 不能只解析一张表，且应用日志是**单线程**——44.13 讲的并行复制在这里用不上。所以临时实例恢复完，可以把它挂成线上备库的从库，快速追平。

事前预防比事后恢复便宜：

| 措施 | 作用 |
|---|---|
| `SET GLOBAL sql_safe_updates = ON;` | `UPDATE`/`DELETE` 不带 `WHERE` 或 `WHERE` 不走索引时直接报错 |
| SQL 审计（上线前） | 拦住 `DROP`/无条件 `DELETE` |
| 权限分离（业务账号无 `DROP`/`TRUNCATE`） | 从权限上断掉「一条命令删库」 |
| **延迟复制备库** | 误删后能在延迟窗口内从备库取回 |

延迟从库是最直接的兜底：`CHANGE MASTER TO MASTER_DELAY = 3600`（8.0.23+ 改名 `CHANGE REPLICATION SOURCE TO SOURCE_DELAY = 3600`），备库落后主库 1 小时执行——误删发生在 10 分钟前，备库上那份数据还在。

## kill 不掉：两类原因，两种处置

`kill query <id>` 只是把线程状态标成 `KILL_QUERY` 并发个信号，**线程自己跑到「埋点」才会停**。所以杀不掉只有两类原因：

| 现象 | 原因 | 处置 |
|---|---|---|
| `kill query` 后语句继续跑 | 线程**没走到埋点**：等 InnoDB 并发槽位（`innodb_thread_concurrency` 满）、IO 卡住不返回 | `kill connection`；但服务端仍会把这条语句跑完，`SHOW PROCESSLIST` 里 `Command=Killed` |
| `kill connection` 后 `Command` 还是 `Killed` | **终止逻辑耗时长**：大事务回滚要逐版本回收、大查询要删临时文件、DDL 到收尾阶段要清中间文件 | 先算回滚成本再决定杀不杀；已经杀了就等它自己结束 |

课程的例子：`SET GLOBAL innodb_thread_concurrency = 2;` 之后第三个会话进不了 InnoDB，线程每 10ms 判断一次「能不能进」然后 `nanosleep`，这个循环里**不检查 kill 状态**——`kill query` 无效，`kill connection` 也只是断开网络，语句照跑。

客户端按 Ctrl+C 不等于直达服务端：MySQL 是停等协议，同一条连接上一条语句没返回就发不了新命令；Ctrl+C 实际是客户端**另开一个连接**去发 `kill query`。

```sql
-- 找「谁在等、等了多久」（MySQL 8.0，未执行）
SELECT id, user, command, time, state, LEFT(info, 80) AS sql_head
FROM information_schema.processlist
WHERE command <> 'Sleep' ORDER BY time DESC;

-- 找长事务：决定 kill 之前先看它已经写了多少（回滚要多久）
SELECT trx_id, trx_started, trx_rows_modified, trx_mysql_thread_id
FROM information_schema.innodb_trx ORDER BY trx_started;
```

> 🔑 `kill` 不是「立即停止」，是「通知 + 等它自己停」。判断标准看 `innodb_trx.trx_rows_modified`：改过几十万行的事务，kill 之后回滚可能比它继续跑还久。

## 自增 ID 耗尽：`int unsigned` 的 4294967295

`int unsigned` 是 4 字节，上限 `2³²−1 = 4294967295`。达到上限后，InnoDB 申请下一个 id 时**得到的值保持不变**，于是第二条插入直接撞主键：

```sql
-- MySQL 8.0，未执行
CREATE TABLE t (id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY) AUTO_INCREMENT = 4294967295;
INSERT INTO t VALUES ();   -- id = 4294967295，成功
INSERT INTO t VALUES ();   -- ERROR 1062: Duplicate entry '4294967295' for key 'PRIMARY'
```

| 处置 | 做法 | 代价 |
|---|---|---|
| 建表就给足位宽（首选） | 直接 `BIGINT UNSIGNED`，上限 `1.8×10¹⁹` | 主键多 4 字节，所有二级索引叶子跟着变宽 |
| 已经写满 | 新建同结构表（`BIGINT` 主键）+ 双写迁移 + 回填 | 一次数据搬迁 + 迁移期双写校验 |
| 换发号器 | 改用号段/Snowflake 这类外部 ID（[44.24 发号器与全局 ID](44.24-发号器与全局ID.md)） | 引入外部依赖，主键不再「趋势递增」 |

另外别忘了「自增不连续」是正常现象：唯一键冲突、事务回滚、批量申请都会留下空洞。**空洞不影响正确性，不要为了消空洞去改自增策略**——那是在改一张能用的表。

## 分区表：能用，但别拿它替代索引

分区表的价值只有一个：**把「删除历史数据」从 `DELETE` 变成 `DROP PARTITION`**。删一个分区文件是秒级操作，`DELETE 1000 万行` 要写 undo、redo、binlog，还要担心长事务。

| 适用 | 不适用 |
|---|---|
| 按时间归档：`ALTER TABLE t DROP PARTITION p202501` | 想靠分区提升点查性能——**分区不替代索引** |
| 单表很大，查询几乎总带分区键 | 查询不带分区键：要扫全部分区，比不分区更慢 |
| 冷热分层：老分区放低速盘 | 分区键与主键冲突的模型（见下） |

四条硬限制，选型前先对上：

1. **主键 / 唯一键必须包含分区列**——`PRIMARY KEY (id, created_at)` 才能按 `created_at` 分区；
2. 第一次访问分区表要**打开所有分区**，分区太多会撞文件句柄与内存（5.7.9 之后由 InnoDB 管理打开行为，但首次仍会全开）；
3. 分区数有上限（8.0 为 8192，课程未涉及，以官方文档为准）；
4. 每个分区是独立的 B+ 树，**没有跨分区的全局索引**——唯一约束必须带分区列才成立。

> ⚠️ 分区表最常见的误用：表已经有一个 `id` 主键，又想按 `created_at` 分区，于是被迫把主键改成 `(id, created_at)`——所有二级索引都变宽，写入成本上升。收益只有「删历史变快」这一条，值不值要算清楚。

## 权限：`grant` 立即生效，`flush privileges` 是给脏数据用的

权限在**两处**存在，`grant` 同时写两处：

| 层级 | 磁盘 | 内存 | 什么时候读进连接 |
|---|---|---|---|
| 全局 | `mysql.user` | `acl_users` 数组 | 连接建立时**拷进线程对象** |
| 库 | `mysql.db` | `acl_dbs` 数组 | 执行 `USE db` 时判断 |
| 表 / 列 | `mysql.tables_priv` / `columns_priv` | `column_priv_hash` | 每次访问时判断 |

由此推出三个常被问到的现象：

- **`grant` 之后不需要 `flush privileges`**：语句本身已经同步修改磁盘和内存。`flush privileges` 是「用磁盘数据重建内存数组」，只在两者不一致时才需要。
- **什么时候才会不一致**：直接用 DML 改 `mysql.user` 等权限表（`DELETE FROM mysql.user WHERE ...`）。这时内存里还有这个用户，`grant` 给它会失败、重建它也会失败。
- **已存在的连接不受 `grant` 影响**：全局权限在连接建立时就拷进了线程对象，改权限只对**新连接**生效。要立刻生效只能让连接重连（这也是连接池下「改权限不生效」的原因，见 [44.12 连接池](44.12-连接池.md)）。

```sql
-- 标准写法：建用户与授权分开（MySQL 8.0，未执行）
CREATE USER 'app'@'%' IDENTIFIED BY '***';
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'app'@'%';
-- 不要再写 GRANT ... IDENTIFIED BY ...：5.7 起不推荐，8.0 已移除该写法
```

> 🔑 权限变更只对**新连接**生效。线上「授权了但还是 403」时，先让连接池滚动重启，别去 `flush privileges`——那治不了「老连接的权限缓存」。

## 反模式

| 反模式 | 后果 |
|---|---|
| 靠 `redo` 恢复误删的数据 | redo 只保证崩溃不丢已提交数据，**不记录「删之前是什么」**，救不了逻辑误删 |
| 只在主库上重放闪回日志 | 把误删之后别人的正常修改一起覆盖，账更难对 |
| 生产库长期 `binlog_row_image=MINIMAL` | 闪回出来只有被改的列，不是完整行 |
| 没有全量备份，只留 binlog | `DROP TABLE` 的 binlog 是 statement，无数据可恢 |
| 长事务被 kill 后立刻重连重试 | 回滚还没走完，新事务继续抢锁，雪上加霜 |
| 建表用 `int unsigned` 自增 | 高频表几年后撞 4294967295，插入报 1062 |
| 用分区替代索引 | 查询不带分区键时扫全部分区，比不分区更慢 |
| `grant` 之后习惯性 `flush privileges` | 无害但掩盖问题：真正的不一致来自直接改权限表 |
| 用 `GRANT ... IDENTIFIED BY` 顺带建用户 | 老写法会**顺手改掉已有用户的密码**（8.0 已移除该语法） |

## 自检

**Q1** 同样是「删了一张表的数据」，为什么 `DELETE FROM t` 能闪回，`TRUNCATE TABLE t` 不能？

▸ 答案：因为 binlog 里记的东西不同。`DELETE` 在 `binlog_format=ROW` 下记的是 `Delete_rows` 事件，带**被删行的完整镜像**，把它反写成 `Write_rows` 重放就恢复了。`TRUNCATE` / `DROP` 即使开了 ROW 格式，binlog 里也只有一句 statement，没有任何行数据——没有原料，闪回无从谈起，只能靠「全量备份 + 增量 binlog 重放到误操作前」。

**Q2** 闪回日志为什么必须在临时实例上重放，不能直接打回主库？

▸ 答案：因为闪回只回滚「那几行」，而主库在误删之后可能已经有新的正常写入。直接重放会把误删时间点之后的合法修改一并覆盖（尤其是同一行的后续更新），制造二次故障。正确做法是在备份/从库拉起的临时实例上重放、比对数、确认无误后按主键回写。

**Q3** `kill query` 发出去了，语句还在跑，`SHOW PROCESSLIST` 里 `Command` 已经是 `Killed`，这条语句到底停了没有？

▸ 答案：不一定。`Command=Killed` 只说明线程状态被标成了 `KILL_CONNECTION`（客户端已断开），服务端语句可能仍在执行——要么没走到检查状态的「埋点」（比如等 InnoDB 并发槽位、IO 不返回），要么正在做终止逻辑（大事务回滚、删临时文件）。真正结束的标志是线程从 `PROCESSLIST` 消失。

**Q4** 一个已经改了 50 万行的事务被 kill，为什么可能比不 kill 更糟？

▸ 答案：因为 kill 触发的是**回滚**，而回滚要把这 50 万行生成的每个版本逐个回收：读 undo、写 redo、写 binlog，代价与「再跑一遍」同级甚至更高，期间还继续持锁。判断依据是 `information_schema.innodb_trx.trx_rows_modified`：数值大就要先评估回滚时长，再决定是杀还是等它跑完。

**Q5** 表的主键是 `int unsigned` 自增，现在插入报 `Duplicate entry '4294967295' for key 'PRIMARY'`，发生了什么？

▸ 答案：自增值已经用满 `2³²−1`。InnoDB 在达到上限后申请下一个 id 时**返回值不再增长**，仍给出 4294967295，于是第二次插入撞主键（错误码 1062）。处置：新建 `BIGINT UNSIGNED` 主键的表做双写迁移，或用外部发号器；不要在这个表上继续插。

**Q6** 有一张 20 亿行的日志表，只想「按天快速删历史」，该用分区还是索引？

▸ 答案：用分区，且分区键是时间列。收益来自 `ALTER TABLE ... DROP PARTITION` 直接删文件（秒级），而 `DELETE` 20 亿行要写 undo/redo/binlog、还会形成长事务。代价是主键/唯一键必须包含分区列（通常变成 `(id, created_at)`），二级索引变宽。**分区不提升点查性能**——点查仍然靠索引。

**Q7** 用 `GRANT SELECT ON shop.* TO 'app'@'%';` 授权后，应用还是报没权限，为什么？

▸ 答案：大概率是老连接。全局权限在**连接建立时**就拷进了线程对象，`grant` 只写磁盘和内存数组，不影响已存在的连接；库级权限在执行 `USE db` 时才读，所以同一连接在切换库之前也保留旧判断。让连接池滚动重启、建立新连接即可生效。`flush privileges` 对此无效——它只重建内存，不刷新已有连接里的那份拷贝。

**Q8** 什么情况下 `flush privileges` 是必须的？怎么避免走到那一步？

▸ 答案：只在「直接对 `mysql.user` / `mysql.db` 等权限表做 DML」造成内存与磁盘不一致时才是必须的——比如 `DELETE FROM mysql.user WHERE user='ua'` 之后，内存 `acl_users` 里还有 `ua`，会出现「能登录但授权失败、重建用户也失败」的怪象，此时才需要 `flush privileges` 重建内存。避免方式是把权限操作全部收敛到 `CREATE USER` / `GRANT` / `REVOKE`，禁止直接改权限表。
