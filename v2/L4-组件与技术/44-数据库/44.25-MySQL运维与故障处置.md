# 44.25 MySQL 运维与故障处置

## 一句话

> 值班时真正要答的是五个问题：**删错了怎么恢复、自增主键为什么有空洞、自增 ID 用完了会怎样、权限改了为什么不生效、故障现场先看哪张表**——每个都有确定的判据和命令，靠现场翻文档来不及；kill 不掉、内存打爆、分区表、DDL 各有主场，这里只留入口。

**来源**：MySQL 运维、参数与故障案例来自丁奇《MySQL 实战 45 讲》（极客时间，2019）第 31、39、42、45 讲；本节 SQL 与实测为本机 MySQL 8.0.46 补充。

## 误删数据：四种删法，四条恢复路径

恢复能力由「删的时候 binlog 里留下了什么」决定，不由「删了多少」决定。

| 删法 | binlog 里记的是什么 | 能否闪回 | 恢复路径 |
|---|---|---|---|
| `DELETE FROM t WHERE ...` | ROW 格式下的 `Delete_rows` 事件（**有完整行镜像**） | ✅ | Flashback / binlog2sql：把 `Delete_rows` 反写成 `Write_rows` 重放 |
| `TRUNCATE TABLE` / `DROP TABLE` | **statement**：只有一句 truncate/drop | ❌ | 全量备份 + binlog 重放到误操作前 |
| `DROP DATABASE` | statement | ❌ | 同上，整库恢复 |
| `rm` 掉 `.ibd` 文件 | 什么都没有 | ❌ | 备库 / 延迟从库，或全量备份 |

闪回的前提是两个参数，缺一不可：`binlog_format=ROW` 且 `binlog_row_image=FULL`。只配了 ROW 而 image 是 `MINIMAL` 时，binlog 里只有被改的列，反写出来的行不是原来那一行。

```sql
-- 检查闪回前提（MySQL 8.0，实测见本节示例区）
SHOW VARIABLES LIKE 'binlog_format';        -- 必须是 ROW
SHOW VARIABLES LIKE 'binlog_row_image';     -- 必须是 FULL
```

恢复的三条事件反写规则：`insert` ↔ `delete` 互换，`update` 对调前后镜像。**必须在临时实例上重放**（最近的全量备份，或一个从库）——直接在主库重放，会把别人这段时间的正常修改一起覆盖掉。

`truncate` / `drop` 只能走「全量 + 增量」：

| 步 | 动作 | 关键参数 |
|---|---|---|
| ① | 取最近一次全量备份（假设每天 0 点） | — |
| ② | 用备份恢复出一个临时实例 | — |
| ③ | 从 binlog 备份取 0 点之后的日志 | `mysqlbinlog --database=db1` 限定库 |
| ④ | 重放到**误操作之前**那一刻 | 无 GTID：`--stop-position`；有 GTID：`SET gtid_next='误操作的 gtid'; BEGIN; COMMIT;` 造一个空事务把它跳过 |
| ⑤ | 校验后回灌主库 | 先比对数，再按主键回写 |

> ⚠️ 这条链路慢在两处：`mysqlbinlog` 不能只解析一张表，且应用日志是**单线程**——44.13 讲的并行复制在这里用不上。所以临时实例恢复完，可以把它挂成线上备库的从库，快速追平。

事前预防比事后恢复便宜：

| 措施 | 作用 |
|---|---|
| `SET GLOBAL sql_safe_updates = ON;` | `UPDATE`/`DELETE` 不带 `WHERE` 或 `WHERE` 不走索引时直接报错 |
| SQL 审计（上线前） | 拦住 `DROP`/无条件 `DELETE` |
| 权限分离（业务账号无 `DROP`/`TRUNCATE`） | 从权限上断掉「一条命令删库」 |
| **延迟复制备库** | 误删后能在延迟窗口内从备库取回 |

延迟从库是最直接的兜底：`CHANGE MASTER TO MASTER_DELAY = 3600`（8.0.23+ 改名 `CHANGE REPLICATION SOURCE TO SOURCE_DELAY = 3600`），备库落后主库 1 小时执行——误删发生在 10 分钟前，备库上那份数据还在。

### 误删之后的前 30 分钟：先冻结，再定位，最后才恢复

误删现场最常见的二次伤害是「一边查一边继续写」；顺序错了，恢复点就被推后。

1. **冻结**：应用切只读，停定时任务与 DDL；临时库可 `SET GLOBAL super_read_only=ON`。继续写会把 binlog 位置推过误删点。
2. **定性留证**：对照四种删法判断行/表/库/文件级，用 `SHOW MASTER STATUS`、`SHOW BINARY LOGS` 记下时间与位点。
3. **选点隔离**：最近全量备份 + 该点后的 binlog，在临时实例重放到误删前，比对 `CHECKSUM TABLE` 后按主键回灌。

恢复窗口取三者最小：**min(延迟从库的延迟秒数, binlog 保留天数, 全量备份可追溯天数)**。承诺「恢复到半个月内任意时间点」，三件事就都要覆盖半个月。

### `rm` 文件、坏道、`drop` 后 `.ibd` 被删

这三种都不是 SQL 层误删，恢复路径也不同：

| 现场 | 本质 | 首选路径 |
|---|---|---|
| `rm` 掉单个节点的 `.ibd` | 文件缺失 | HA 摘除该节点，用备份重建后接入；整集群被删只能靠异地备份 |
| 磁盘坏道 / 文件系统损坏 | 物理损坏 | 从库提升 + 备份重建，坏盘不原地修；binlog 重放补不了坏页 |
| `DROP TABLE` 后 `.ibd` 被清理 | 元数据与文件都没了 | 从备份取 `.ibd`，`DISCARD` 后 `IMPORT TABLESPACE`；版本、页大小、加密须一致 |

## kill 不掉：先分清「没到埋点」还是「停不下来」

`kill query <id>` 只是给线程置 `KILL_QUERY` 并唤醒它，**线程走到埋点才会退**。杀不掉只有两类：① 线程卡在不可中断处（等 InnoDB 并发槽位、IO 不返回），`kill query` 无效，只能 `kill connection`；② 已经进入终止逻辑（大事务回滚、删临时文件、DDL 收尾），`Command` 会长时间停在 `Killed`，这时**回滚成本可能高于让它跑完**——先看 `innodb_trx.trx_rows_modified` 再决定。

完整判据、`innodb_thread_concurrency` 的假活现场、`Sending to client` 与内存打爆、短连接风暴与 QPS 突增的处置，见 [44.30 MySQL 应急手册](44.30-MySQL应急手册.md)。

## 自增主键为什么不是连续的

**自增只保证递增，不保证连续**。把它当流水号（订单号、凭证号）用，是在依赖数据库从未承诺的属性。

实测环境：MySQL 8.0.46，buffer pool 128M，RR 隔离，`binlog_format=ROW`，`innodb_autoinc_lock_mode` 默认 2；模式 1 用启动参数验证。

### 自增值存在哪儿

`SHOW CREATE TABLE` 里的 `AUTO_INCREMENT=2` 不是存在表结构里：

| 引擎 / 版本 | 保存在 | 重启后 |
|---|---|---|
| MyISAM | 数据文件 | 不变 |
| InnoDB ≤ 5.7 | 只在内存 | 取 `max(id)+1`，**可能变小** |
| InnoDB 8.0 | 变更写 redo log，数据字典在 `mysql.ibd` | 恢复重启前的值 |

5.7 的表最大 id=10、计数器 11，删掉 id=10 后计数器仍是 11，重启后却取 `max(id)+1=10`，**计数器回退**；8.0 靠 redo 恢复，不回退。`information_schema.tables.AUTO_INCREMENT` 是「下一个待分配值」，和 `max(id)` 的差就是空洞数。

### 修改机制：自动值与指定值

id 写 `0`、`NULL` 或不写 → 用当前自增值；写 X → 用 X，但可能抬高计数器。设当前值为 Y：X<Y 不动；X≥Y 时从 `auto_increment_offset` 起按 `auto_increment_increment` 累加，取**第一个大于 X** 的值；两参数默认 1。

### 修改时机：先领号，再插入

空洞的根源：**自增值在真正插入之前就领走了**。

```sql
INSERT INTO t VALUES (NULL, 1, 1);
-- ① 取当前自增值 2，把行改成 (2,1,1)，计数器改成 3
-- ② 写入时 c=1 撞唯一键
-- ERROR 1062 (23000): Duplicate entry '1' for key 't.c'
```

失败后计数器不回退，下一次拿到 3，id=2 永远空着（实测冲突前 `AUTO_INCREMENT=2`，冲突后 3，再插得到 id=3）。`INSERT IGNORE` 和 `ON DUPLICATE KEY UPDATE` 同样先领号，所以「忽略」「更新」都不还号：id=3 插入后计数器为 4，再连撞两次同一个唯一键，计数器跳到 5、再跳到 6。

### 三类空洞

| 原因 | 机制 | 现象 | 能否避免 |
|---|---|---|---|
| 唯一键冲突 | 领号早于唯一键检查，失败不退 | `INSERT`、`INSERT IGNORE` 都消耗 id | 不能 |
| 事务回滚 | 自增值不是事务资源 | 回滚后下一行 id 跳过 | 不能 |
| 批量预分配 | 一次申请 2 的幂个，用不完作废 | `INSERT ... SELECT` 插 4 行消耗 7 个 | 能缩小，不能消除 |

### 为什么不能回退

A 领到 2、B 领到 3，B 提交、A 冲突。若允许 A 改回 2，下一事务会再领 2、3，而 id=3 已存在，直接主键冲突。避免它只能「领号前查主键」或「锁扩到提交」，都拿性能换连续性，InnoDB 选择不回退。

> 🔑 「不连续」不是 bug，是「用少量空洞换无锁领号」的设计代价。依赖自增 id 连续的业务逻辑，会在第一次唯一键冲突时出错。

### 自增锁：三档

`innodb_autoinc_lock_mode` 控制领号锁的范围。5.1.22 引入，5.7 默认 1；8.0.3 起默认 2（原文按 1 讲，8.0.46 实测为 2，且**只读**，不能 `SET GLOBAL`）。

| 取值 | 锁释放 | 批量插入 | statement binlog 安全吗 |
|---|---|---|---|
| 0 传统 | 语句结束 | 锁到语句结束 | 安全，并发最差 |
| 1 连续（5.7 默认） | 普通 insert 领完即放；批量锁到语句结束 | 一次预分配，id 连续 | 安全 |
| 2 交错（8.0 默认） | 领完即放 | 并发语句的 id 可能交错 | 只有 ROW 格式安全 |

「批量」指 `INSERT ... SELECT`、`REPLACE ... SELECT`、`LOAD DATA`，执行前不知道行数；`INSERT ... VALUES (...),(...)` 能精确算出个数，任何档位都一次领够、立刻放锁。不知道行数时按**翻倍预分配**：1、2、4……实测 `INSERT ... SELECT` 插 4 行领 1+2+4=7 个，`AUTO_INCREMENT` 到 8，下一行拿 8，5、6、7 作废；模式 1 和 2 下都复现。

> 🔑 生产用 `innodb_autoinc_lock_mode=2` + `binlog_format=ROW`：前者放开并发，后者让从库按行镜像重放、不依赖主键生成顺序。statement 格式下用 2，主从可能生成不同 id。

### 回退与复用

| 操作 | 结果（8.0.46 实测） | 能否复用已删 id |
|---|---|---|
| `DELETE` 最大行后重启 | 不回退 | 不能 |
| `TRUNCATE TABLE` | 重置为 **1**，建表时的 `AUTO_INCREMENT=100` 也不保留 | 能，但从 1 开始，有撞历史数据风险 |
| `ALTER ... AUTO_INCREMENT=1` | 空表可降到 1；非空表最多降到 `max(id)+1` | 不能 |
| 5.7 重启 | 回退到 `max(id)+1` | 可能 |

> ⚠️ 非空表上 `ALTER ... AUTO_INCREMENT=1` 补不回删掉的号，只会抬到 `max(id)+1`。

需要连续编号时另建发号表，或用 [44.24 发号器与全局 ID](44.24-发号器与全局ID.md)，别修自增；发号串行化是必然代价。

完整脚本在仓库 [tools/examples/44.25-mysql-ops-lab/](../../../tools/examples/44.25-mysql-ops-lab/README.md)，`bash code/run.sh` 可复现。

## 自增 ID 用完了会怎样：五种 ID，五种下场

MySQL 里不止表自增一个 id，都有上限，**到顶后行为完全不同**：有的报错，有的归零，有的覆盖数据。

### 整数列的上限

| 类型 | 字节 | signed 上限 | unsigned 上限 |
|---|---|---|---|
| `TINYINT` | 1 | 127 | 255 |
| `SMALLINT` | 2 | 32767 | 65535 |
| `MEDIUMINT` | 3 | 8388607 | 16777215 |
| `INT` | 4 | 2147483647 | 4294967295 |
| `BIGINT` | 8 | 9223372036854775807 | 18446744073709551615 |

```sql
-- MySQL 8.0，未执行
CREATE TABLE t (id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY) AUTO_INCREMENT = 4294967295;
INSERT INTO t VALUES ();   -- id = 4294967295，成功
INSERT INTO t VALUES ();   -- ERROR 1062: Duplicate entry '4294967295' for key 'PRIMARY'
```

| 处置 | 做法 | 代价 |
|---|---|---|
| 建表就给足位宽（首选） | 直接 `BIGINT UNSIGNED`，上限 `1.8×10¹⁹` | 主键多 4 字节，所有二级索引叶子跟着变宽 |
| 已经写满 | 新建同结构表（`BIGINT` 主键）+ 双写迁移 + 回填 | 一次数据搬迁 + 迁移期双写校验 |
| 换发号器 | 改用号段/Snowflake 这类外部 ID（[44.24 发号器与全局 ID](44.24-发号器与全局ID.md)） | 引入外部依赖，主键不再「趋势递增」 |

表自增 id 只是这些 id 里最温和的一个，下面看另外几种。

### 五种 ID 对照

| ID | 谁维护 | 宽度 / 上限 | 到顶后 | 后果 |
|---|---|---|---|---|
| 表自增 id | 用户表定义 | 取决于列类型 | 值不再增长 | 报 1062，**可用性**受损 |
| `row_id` | InnoDB | 6 字节 / 2⁴⁸−1 | 归零 | 覆盖旧行，**静默丢数据** |
| `Xid` | server 层 | 8 字节 / 2⁶⁴−1 | 归零 | 同 binlog 理论重复，可忽略 |
| `max_trx_id` | InnoDB | 48 位 / 2⁴⁸−1 | 归零 | 新 id 小于低水位，**持续脏读** |
| `thread_id` | server 层 | 4 字节 / 2³²−1 | 归零 | 唯一数组去重，无影响 |

### `row_id`：不报错，直接覆盖

InnoDB 表没有显式主键时，用 6 字节 `row_id` 做隐式聚簇索引键。全局 `dict_sys.row_id` 每行加 1；代码里 8 字节，写进页只留低 6 字节，取值 0 ~ 2⁴⁸−1，到顶归零。申请到 N 后直接写，若表里已有 `row_id=N` 的行，**新行覆盖旧行，不报错**。

原文用 gdb 把 `dict_sys.row_id` 改成 2⁴⁸，复现了「新行顶掉旧行」。单表每秒 1 万行要跑约 892 年，但它是**实例级全局**，所有无主键表共享，实例够久就不是理论问题。

> 🔑 表自增 id 到顶是插入失败，影响可用性；`row_id` 到顶是覆盖数据，影响可靠性。**可靠性优先于可用性**，InnoDB 表应主动建主键。

### `Xid` 与 `trx_id`：名字像，后果差一个数量级

`Xid` 是 server 层 `global_query_id`，每执行一条语句加 1，事务第一条语句把它记成 Xid，用于关联 redo 和 binlog。纯内存，重启清零；但重启会开新 binlog，所以**同一 binlog 文件内 Xid 唯一**，上限 2⁶⁴−1。

`trx_id` 是 InnoDB 的 `max_trx_id`，只读事务**不分配**，普通 `select` 不消耗；`update`/`delete` 因 purge 至少 +2。`max_trx_id` **持久化**，重启不清零；跑到 2⁴⁸−1 归零后，新 id 从 0 开始而低水位仍是巨大旧值，新版本全被判可见，**持续脏读**，重启也修不好（原文按 TPS 50 万估算约 17.8 年触顶）。

> ⚠️ 不要用「定期重启」解决 id 上限：`thread_id`、`Xid` 会清零，`max_trx_id` 和 8.0 的表自增值不会。

### `thread_id`：处理得最好的一个

`thread_id_counter` 是 4 字节，到 2³²−1 归零；分配时「取号 → 查唯一数组 → 冲突再取」，所以 `SHOW PROCESSLIST` 永远不会有两个相同 `thread_id`。

## 分区表：只用它换「删历史」，别指望它提速

分区表只买一件事：`ALTER TABLE ... DROP PARTITION` 秒级删掉一批历史数据，省掉 `DELETE` 的 undo/redo/binlog 与长事务。**它不替代索引**，查询不带分区键反而更慢；主键/唯一键必须包含分区列，所以「`id` 主键 + 按时间分区」会逼你把主键改成 `(id, created_at)`，所有二级索引跟着变宽。

Server 层如何把 N 个分区当一张表、分区裁剪与 MDL、分区键的取舍、`rows` 估算与文件句柄限制，见 [44.27 InnoDB 表空间、空间回收与在线 DDL](44.27-InnoDB表空间与在线DDL.md)。

## 权限：`grant` 立即生效，`flush privileges` 是给脏数据用的

权限在**两处**存在，`grant` 同时写两处：

| 层级 | 磁盘 | 内存 | 什么时候读进连接 |
|---|---|---|---|
| 全局 | `mysql.user` | `acl_users` 数组 | 连接建立时**拷进线程对象** |
| 库 | `mysql.db` | `acl_dbs` 数组 | 执行 `USE db` 时判断 |
| 表 / 列 | `mysql.tables_priv` / `columns_priv` | `column_priv_hash` | 每次访问时判断 |

由此推出三个常被问到的现象：

- **`grant` 之后不需要 `flush privileges`**：语句本身已经同步修改磁盘和内存。`flush privileges` 是「用磁盘数据重建内存数组」，只在两者不一致时才需要。
- **什么时候才会不一致**：直接用 DML 改 `mysql.user` 等权限表（`DELETE FROM mysql.user WHERE ...`）。这时内存里还有这个用户，`grant` 给它会失败、重建它也会失败。
- **已存在的连接不受 `grant` 影响**：全局权限在连接建立时就拷进了线程对象，改权限只对**新连接**生效。要立刻生效只能让连接重连（这也是连接池下「改权限不生效」的原因，见 [44.12 连接池](44.12-连接池.md)）。

```sql
-- 标准写法：建用户与授权分开（MySQL 8.0，未执行）
CREATE USER 'app'@'%' IDENTIFIED BY '***';
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'app'@'%';
-- 不要再写 GRANT ... IDENTIFIED BY ...：5.7 起不推荐，8.0 已移除该写法
```

> 🔑 权限变更只对**新连接**生效。线上「授权了但还是 403」时，先让连接池滚动重启，别去 `flush privileges`——那治不了「老连接的权限缓存」。

### 三个层级的权限，对已存在连接的影响不一样

| 层级 | 内存结构 | 已存在连接 |
|---|---|---|
| 全局 | `acl_users` | 连接建立时拷进线程对象，**不生效** |
| 库 | `acl_dbs` | 每次查全局数组，**生效**；当前库权限缓存在会话变量 |
| 表 / 列 | `column_priv_hash` | 每次查 hash，**生效** |

实测（8.0.46）：会话 A `USE lab4425` 后，另一会话 `REVOKE SELECT ON lab4425.*`，A 在同一个库继续查**仍然成功**；切走再回来才 `ERROR 1044 Access denied`。全局更彻底：建连后再 `GRANT SELECT ON *.*`，老连接查 `mysql.user` 仍报 `ERROR 1142`，新连接才成功。

`FLUSH PRIVILEGES` 清空 `acl_users` 等数组并从权限表重载，但**不改**已存在的线程对象；只在直接 DML 权限表时需要：`DELETE FROM mysql.user WHERE user='ub'` 后，老连接仍能登录；`GRANT` 报 `ERROR 1410`；`CREATE USER` 报 `ERROR 1396`；`FLUSH PRIVILEGES` 后 ub 登录报 `ERROR 1045`，内存与磁盘才一致。

> 🔑 `FLUSH PRIVILEGES` 不是「让权限生效」的开关，是「磁盘和内存打架」时的急救；规范路径只有 `CREATE USER` / `GRANT` / `REVOKE` / `DROP USER`。`GRANT ALL ON *.* ... WITH GRANT OPTION` 配 `'%'`，等于交出「删库 + 转授权 + 任意 IP 可登」。

> ⚠️ 连接器建连时拿到的权限快照见 [44.26 一条 SQL 的一生](44.26-MySQL一条SQL的一生.md)；应用账号只给单库 DML，DDL 走审批。

## 反模式

| 反模式 | 后果 |
|---|---|
| 靠 `redo` 恢复误删的数据 | redo 只保证崩溃不丢已提交数据，**不记录「删之前是什么」**，救不了逻辑误删 |
| 只在主库上重放闪回日志 | 把误删之后别人的正常修改一起覆盖，账更难对 |
| 生产库长期 `binlog_row_image=MINIMAL` | 闪回出来只有被改的列，不是完整行 |
| 没有全量备份，只留 binlog | `DROP TABLE` 的 binlog 是 statement，无数据可恢 |
| 长事务被 kill 后立刻重连重试 | 回滚还没走完，新事务继续抢锁，雪上加霜 |
| 建表用 `int unsigned` 自增 | 高频表几年后撞 4294967295，插入报 1062 |
| 用分区替代索引 | 查询不带分区键时扫全部分区，比不分区更慢 |
| `grant` 之后习惯性 `flush privileges` | 无害但掩盖问题：真正的不一致来自直接改权限表 |
| 用 `GRANT ... IDENTIFIED BY` 顺带建用户 | 老写法会**顺手改掉已有用户的密码**（8.0 已移除该语法） |
| 把自增主键当连续流水号 | 唯一键冲突、回滚、批量插入都会断号，对账与补偿逻辑从第一天就错 |
| 无主键表依赖 InnoDB 的 `row_id` | 2⁴⁸ 用完后新行覆盖旧行，不报错，静默丢数据 |
| 认为 `FLUSH PRIVILEGES` 能让老连接拿到新权限 | 全局权限在连接建立时已拷贝，flush 只重建内存，不刷新线程对象 |

## 自检

**Q1** 同样是「删了一张表的数据」，为什么 `DELETE FROM t` 能闪回，`TRUNCATE TABLE t` 不能？

▸ 答案：因为 binlog 里记的东西不同。`DELETE` 在 `binlog_format=ROW` 下记的是 `Delete_rows` 事件，带**被删行的完整镜像**，把它反写成 `Write_rows` 重放就恢复了。`TRUNCATE` / `DROP` 即使开了 ROW 格式，binlog 里也只有一句 statement，没有任何行数据——没有原料，闪回无从谈起，只能靠「全量备份 + 增量 binlog 重放到误操作前」。

**Q2** 闪回日志为什么必须在临时实例上重放，不能直接打回主库？

▸ 答案：因为闪回只回滚「那几行」，而主库在误删之后可能已经有新的正常写入。直接重放会把误删时间点之后的合法修改一并覆盖（尤其是同一行的后续更新），制造二次故障。正确做法是在备份/从库拉起的临时实例上重放、比对数、确认无误后按主键回写。

**Q3** `kill query` 发出去了，语句还在跑，`SHOW PROCESSLIST` 里 `Command` 已经是 `Killed`，这条语句到底停了没有？

▸ 答案：不一定。`Command=Killed` 只说明线程状态被标成了 `KILL_CONNECTION`（客户端已断开），服务端语句可能仍在执行——要么没走到检查状态的「埋点」（比如等 InnoDB 并发槽位、IO 不返回），要么正在做终止逻辑（大事务回滚、删临时文件）。真正结束的标志是线程从 `PROCESSLIST` 消失。

**Q4** 一个已经改了 50 万行的事务被 kill，为什么可能比不 kill 更糟？

▸ 答案：因为 kill 触发的是**回滚**，而回滚要把这 50 万行生成的每个版本逐个回收：读 undo、写 redo、写 binlog，代价与「再跑一遍」同级甚至更高，期间还继续持锁。判断依据是 `information_schema.innodb_trx.trx_rows_modified`：数值大就要先评估回滚时长，再决定是杀还是等它跑完。

**Q5** 表的主键是 `int unsigned` 自增，现在插入报 `Duplicate entry '4294967295' for key 'PRIMARY'`，发生了什么？

▸ 答案：自增值已经用满 `2³²−1`。InnoDB 在达到上限后申请下一个 id 时**返回值不再增长**，仍给出 4294967295，于是第二次插入撞主键（错误码 1062）。处置：新建 `BIGINT UNSIGNED` 主键的表做双写迁移，或用外部发号器；不要在这个表上继续插。

**Q6** 有一张 20 亿行的日志表，只想「按天快速删历史」，该用分区还是索引？

▸ 答案：用分区，且分区键是时间列。收益来自 `ALTER TABLE ... DROP PARTITION` 直接删文件（秒级），而 `DELETE` 20 亿行要写 undo/redo/binlog、还会形成长事务。代价是主键/唯一键必须包含分区列（通常变成 `(id, created_at)`），二级索引变宽。**分区不提升点查性能**——点查仍然靠索引。

**Q7** 用 `GRANT SELECT ON shop.* TO 'app'@'%';` 授权后，应用还是报没权限，为什么？

▸ 答案：大概率是老连接。全局权限在**连接建立时**就拷进了线程对象，`grant` 只写磁盘和内存数组，不影响已存在的连接；库级权限在执行 `USE db` 时才读，所以同一连接在切换库之前也保留旧判断。让连接池滚动重启、建立新连接即可生效。`flush privileges` 对此无效——它只重建内存，不刷新已有连接里的那份拷贝。

**Q8** 什么情况下 `flush privileges` 是必须的？怎么避免走到那一步？

▸ 答案：只在「直接对 `mysql.user` / `mysql.db` 等权限表做 DML」造成内存与磁盘不一致时才是必须的——比如 `DELETE FROM mysql.user WHERE user='ua'` 之后，内存 `acl_users` 里还有 `ua`，会出现「能登录但授权失败、重建用户也失败」的怪象，此时才需要 `flush privileges` 重建内存。避免方式是把权限操作全部收敛到 `CREATE USER` / `GRANT` / `REVOKE`，禁止直接改权限表。

**Q9** 表 `t` 里只有 id=1 和 id=3 两行，`AUTO_INCREMENT=5`。中间没有 2 和 4，是删过吗？

▸ 答案：不是删过，是「领了号但没插成」。id=2 来自唯一键冲突：InnoDB 写入前领走 2、计数器改 3，随后撞键失败，号不退。id=4 来自 `INSERT IGNORE`，同样先领号再吞掉错误。`rollback` 也退不了——自增值不是事务资源，否则并发事务会把已提交的 id 重新发出去。有空洞不等于删过行，不能靠 `max(id)` 推断删除量。

**Q10** A 表 `INT UNSIGNED` 自增主键插入报 1062；B 表没有显式主键但插入一直成功。哪张更危险？

▸ 答案：B 更危险。A 的 1062 是计数器到顶不再增长，插入失败但**旧数据完好**，损失可用性；B 靠 6 字节 `row_id`，2⁴⁸ 用完后归零，遇到相同 `row_id` **直接覆盖旧行且不报错**，损失可靠性。`SHOW CREATE TABLE` 看不到 `PRIMARY KEY` 就是 B 类表，立刻补 `BIGINT UNSIGNED` 主键。
