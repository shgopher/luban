                                        44.13 主从复制与读写分离

                                        一句话

                                        主从复制解决「数据有几份」，读写分离解决「读走哪份」；读的承诺由路由策略决定，写的承诺由复制模式决定——异步复制可能丢最近几毫秒到几秒的提交，半同步把 RPO 压到 0 却仍给不了「读到最新」——读写分离只能在读侧做文章，补不了写的持久性。

                                        来源：主备切换流程、seconds_behind_master 与双 M 循环复制来自丁奇《MySQL 实战 45 讲》（极客时间，2019）第 24、25 讲；备库延迟的四个来源与并行复制的三代方案来自第 26 讲；一主多从的位点切换与 GTID 来自第 27 讲；过期读的六种解法来自第 28 讲；判活与 performance_schema 内部统计来自第 29 讲；本节 SQL、参数默认值与全部实测输出为本机 MySQL 8.0.46 补充（端口 33109，脚本见 tools/examples/44.13-repl-lab）。

                                        复制链路：三个线程、两段延迟

                                        主库                                    从库
────                                    ────
用户 COMMIT
  │ 写 binlog（sync_binlog 决定何时落盘）
  ▼
binlog ──dump thread──发送──▶ IO thread ──写 relay log──▶ SQL thread ──回放──▶ 对读可见
        └──── 传输延迟 ────┘                └──────── 回放延迟 ────────┘
                                        环节 谁在做 典型耗时 什么时候成为瓶颈
                                        主库写 binlog 提交线程 0.1–1ms（sync_binlog=1 时含 fsync） 高并发小事务
                                        传输 dump thread → IO thread 同机房 <1ms，跨城 30ms 跨地域、大事务
                                        写 relay log IO thread <1ms 从库磁盘慢
                                        回放 SQL thread / worker 单线程 2–5k 事务/s 大事务、并行度不足
                                        从库可见延迟 ≈ 传输延迟 + relay log 积压量 / 回放速率

                                        🔑 绝大多数「延迟几分钟」都不是网络问题，而是回放跟不上：积压量涨、回放速率不变，延迟就线性增长。加带宽没用，得加回放并行度或拆大事务。

                                        binlog 三种格式：选错就是数据不一致

                                        格式 记录什么 日志量 确定性 适用
                                        STATEMENT 原始 SQL 最小（约为 ROW 的 1/10） ❌ NOW()、UUID()、RAND()、无 ORDER BY 的 LIMIT 在从库可能算出不同结果 基本淘汰
                                        ROW 每行的 before / after image 最大 ✅ 回放是「按行赋值」，结果确定 默认，绝大多数场景
                                        MIXED 默认 STATEMENT，非确定语句自动切 ROW 中 ⚠️ 取决于判定是否覆盖全 历史系统

                                        量级算一遍：一张 1KB 宽的表更新 100 万行——

                                        • binlog_row_image=FULL：before + after ≈ 2GB binlog；
                                        • binlog_row_image=MINIMAL（只记主键与变更列）：约 1GB；
                                        • 传输 2GB（100MB/s 链路）≈ 20 秒，但单线程回放 100 万行按 2000 行/秒算要 500 秒。

                                        这就是「大事务」为什么是复制延迟的头号杀手：传输可以并行、可以加带宽，回放一个事务只能串行。

                                        复制日志的三种形态（语句 / 行 / 逻辑）在数据库无关层面的对比，见 18.3 复制日志。

                                        💡 ROW 也不是「绝对一致」的护身符：从库 read_only 没开、有人手工写了数据，或者用 sql_slave_skip_counter 跳过事务，都会让从库和主库分叉。格式解决的是「回放确定性」，不解决「人为破坏」。

                                        自增主键在 statement binlog 里怎么对齐

                                        STATEMENT 格式还有一个隐蔽的不一致源：自增 id 的生成顺序和 binlog 的写入顺序不是同一个顺序。主库上两条 insert 并发执行，谁先拿到自增值由存储引擎决定；binlog 却必须按事务提交顺序追加。于是备库如果重新申请自增值，就可能把同一行写成另一个 id——主备数据「看起来都在，但对不上」。

                                        MySQL 的解法是把自动值写进 binlog：记录这条 insert 之前，先写一句 SET INSERT_ID=<n>，备库回放时不再重新分配，直接用这个值：

                                        # 主库 binlog（statement 格式，mysqlbinlog -vv 解出）
SET INSERT_ID=2/*!*/;
INSERT INTO t VALUES (NULL, 'b');
SET INSERT_ID=1/*!*/;
INSERT INTO t VALUES (NULL, 'a');

                                        上例中主库先插入 'b'（拿到 2）、后插入 'a'（拿到 1），binlog 按提交顺序记成「先 2 后 1」；备库照 SET INSERT_ID 回放，两行 id 与主库一致。ROW 格式没有这个问题——Write_rows 事件里直接写了每一列的值，自增列也在内。

                                        🔑 判据：用 statement 格式就必须接受「自增值由 binlog 指定」这套机制，它的一致性依赖 innodb_autoinc_lock_mode 的取值（0/1 保证连续分配，2 交错分配在并发下会与语句顺序脱钩，见 44.25 MySQL运维与故障处置）；row 格式下这三档只影响并发插入性能，不影响主备一致。

                                        自增值本身的空洞从哪来（唯一键冲突、回滚、批量预分配），见 44.25 MySQL运维与故障处置。

                                        半同步：RPO=0 的三个前提

                                        模式 提交顺序 客户端看到提交时 主库崩溃后
                                        异步 写 binlog → 返回客户端 → 后台发送 从库可能还没收到 丢最近未发送的事务
                                        半同步 AFTER_COMMIT 写 binlog → 提交（对客户端可见）→ 等 ACK 从库可能还没收到 仍可能丢
                                        半同步 AFTER_SYNC（5.7+） 写 binlog → 等 ACK → 提交 至少一个从库已收到 不丢（有前提）

                                        ⚠️ 很多人以为「开了半同步就是强一致」，其实 AFTER_COMMIT 版本和异步的丢失窗口一样，只是多了一次等待。必须确认是 AFTER_SYNC。

                                        即使是 AFTER_SYNC，RPO=0 也有三个前提：

                                        前提 不满足会怎样
                                        ACK 的那个从库不一起挂 主从同机架 / 同可用区，一起断电就丢
                                        relay log 真正落盘 sync_relay_log 很大时 ACK 只代表「在页缓存里」，OS 崩溃仍丢
                                        没有超时退化 rpl_semi_sync_master_timeout（默认 10s）触发后自动退化为异步，此时 RPO>0 且没人告警

                                        同步、半同步、异步的一般性权衡（延迟、可用性、持久性三者的取舍）见 18.2 同步、半同步、异步。

                                        代价是写延迟：同城 RTT 0.5–2ms → 每条提交多一次往返，P99 上升 0.5–2ms；跨城 30ms → 写吞吐直接掉一个数量级（组提交可以摊薄，但摊不掉单次 RTT）。

                                        🔑 半同步只保证「至少一个副本收到」，不保证「已回放」。所以它保护的是持久性，不是读一致性——从库照样可能读到旧值。

                                        GTID：切换时不再算 binlog 位点

                                        GTID = server_uuid:transaction_id      例：3E11FA47-...:1-1000
                                        能力 没有 GTID 有 GTID
                                        从库定位 记 MASTER_LOG_FILE + POS，人工算 SOURCE_AUTO_POSITION=1 自动找
                                        主库切换 每个从库手算新位点，易错 全部 CHANGE REPLICATION SOURCE TO 指向新主即可
                                        一致性校验 只能比对行数 WAIT_FOR_EXECUTED_GTID_SET / 比较 gtid_executed
                                        故障恢复 旧主恢复后要人工对位点 看 GTID 集合差，能精确知道缺哪些事务

                                        代价：gtid_purged 之后，落后太多的从库无法增量追，只能重做；enforce_gtid_consistency=ON 会禁用 CREATE TABLE ... SELECT 这类语句。

                                        故障切换：选谁、丢多少、多久能写

                                        自动切换的完整流程（故障检测 → 选主 → 提升 → 流量重定向）见 18.5 故障检测与切换。

                                        选主顺序（唯一正确顺序）：

                                        1. 按 GTID 选最全的从库（received 最大），不是按负载最低、延迟最小、机器最新；
                                        2. 先把它自己的 relay log 回放完（received − applied 的缺口），再开放写；
                                        3. fencing 旧主：super_read_only=ON、摘 VIP、必要时 STONITH——旧主只要还能写，就会脑裂（防护手段见 18.6 脑裂与防护；判定「真死」的误判代价见 35.4 故障检测）；
                                        4. 其他从库改指向新主（SOURCE_AUTO_POSITION=1），客户端 / 代理切换入口。

                                        丢多少：

                                        异步复制   丢失 ≤ committed − max(received)   ← 通常是最近 1ms–数秒的提交
半同步     丢失 = 0（三个前提都满足时）

                                        可运行：异步 vs 半同步，切换时到底丢几条

                                        主库 200ms 内提交 400 条（2000 事务/s），三个从库：A 回放 3 条/ms、B 2 条/ms、C 1 条/ms（C 的回放能力只有写入速度的一半，越落越远）。

                                        package main

import "fmt"

// 一个 tick = 1ms；主库每个 tick 提交 2 条事务，共 200 个 tick = 400 条。
const (
	ticks     = 200
	perTick   = 2
	committed = ticks * perTick // 400
)

type replica struct {
	name     string
	lagTx    int // 网络延迟，折算成「落后多少条事务」
	rate     int // 每个 tick 能回放多少条事务
	received int // 已写入 relay log
	applied  int // 已回放（对读可见）
}

func newReplicas() []*replica {
	return []*replica{
		{name: "A", lagTx: 4, rate: 3},
		{name: "B", lagTx: 10, rate: 2},
		{name: "C", lagTx: 2, rate: 1}, // 回放能力只有写入速度的一半，越落越远
	}
}

// step 推进一个 tick：先投递（受网络延迟限制），再回放（受回放速率限制）。
// semi=true 时，主库等到「最先 ACK 的那个从库」才返回，所以只有它保证收到了全部事务，
// 其他从库该滞后还是滞后——这正是「有副本收到 ≠ 每个副本都追平」。
func step(reps []*replica, now int, semi bool) {
	sent := (now + 1) * perTick
	fastest := reps[0]
	for _, r := range reps[1:] {
		if r.lagTx < fastest.lagTx {
			fastest = r
		}
	}
	for _, r := range reps {
		if semi && r == fastest {
			r.received = sent // ACK 语义：这个从库已把 relay log 落盘
			continue
		}
		if v := sent - r.lagTx; v > r.received {
			r.received = v
		}
	}
	for _, r := range reps {
		if r.received-r.applied > r.rate {
			r.applied += r.rate
		} else {
			r.applied = r.received
		}
	}
}

// failover 选「GTID 最全」的从库：先比 received，再比 applied。
func failover(reps []*replica) *replica {
	best := reps[0]
	for _, r := range reps[1:] {
		if r.received > best.received || (r.received == best.received && r.applied > best.applied) {
			best = r
		}
	}
	return best
}

func run(semi bool) {
	reps := newReplicas()
	for now := 0; now < ticks; now++ {
		step(reps, now, semi)
	}
	fmt.Println("--------------------------------------------------")
	if semi {
		fmt.Println("半同步复制：主库等 1 个从库 ACK 才返回（每条 +1 次 RTT）")
	} else {
		fmt.Println("异步复制：主库提交即返回，不等从库")
	}
	for _, r := range reps {
		fmt.Printf("  从库%s：received=%-3d applied=%-3d（回放速率 %d 条/tick）\n",
			r.name, r.received, r.applied, r.rate)
	}
	newPrimary := failover(reps)
	loss := committed - newPrimary.received
	backlog := newPrimary.received - newPrimary.applied
	fmt.Printf("  选 GTID 最全的从库%s 提升为新主：丢失 %d 条，切换后需先回放 %d 条才能对外服务\n",
		newPrimary.name, loss, backlog)
	fmt.Printf("  其他从库改指向新主后，还需回放各自缺口：")
	for _, r := range reps {
		if r != newPrimary {
			fmt.Printf(" %s=%d 条", r.name, newPrimary.received-r.applied)
		}
	}
	fmt.Println()
}

func main() {
	run(false)
	run(true)
	fmt.Println("--------------------------------------------------")
	fmt.Println("异步：RPO = 丢失 2 条（约 1ms 的写入）；半同步：RPO = 0，代价是每条提交多一次 RTT。")
	fmt.Println("注意半同步只保证「有副本收到」，不保证「已回放」——切换时仍要先追 relay log。")
}

                                        三个结论：

                                        • 异步丢 2 条（GTID 398 vs 提交 400）。这 2 条是「客户端已经收到成功、但还没到任何从库」的事务——用户看到下单成功，切换后订单不存在。
                                        • 半同步丢 0 条，代价是每条提交多一次 ACK 往返；它把「丢 2 条」换成「写 P99 高 1 个 RTT」。注意：ACK 只来自最快的那个从库（C），它收到了全部 400 条，但回放仍落后 200 条——RPO=0 不代表切换后立刻能写。
                                        • GTID 最全 ≠ 立即可用：C 数据最全，但回放落后 199 条，切换后要先把 relay log 追完才能写；若改选「已回放最多」的 A，只丢 4 条但秒级可写。这是 RPO 与 RTO 的交换，必须由业务拍板，不能由运维按经验选。

                                        延迟怎么调：四个旋钮

                                        旋钮 做法 效果
                                        并行回放 LOGICAL_CLOCK（按组提交并行）/ WRITESET（按行冲突检测），replica_parallel_workers=8 从 2–5k tx/s 提到约 2 万 tx/s
                                        拆大事务 100 万行的 UPDATE 拆成 1000 行 × 1000 批 延迟从「尖峰 500s」变成「每批 0.5s」，可观测、可限流
                                        减小 binlog binlog_row_image=MINIMAL 日志量减半，传输与回放都受益
                                        从库硬件 回放是写密集；从库 IOPS 不低于主库 避免回放线程等 fsync

                                        ⚠️ replica_parallel_workers（旧名 slave_parallel_workers）不是越大越好：并行度受「主库组提交并发度」限制，设成 64 但主库每批只有 2 个事务，多出来的线程只增加调度开销。先看主库的组提交大小，再定并行度。

                                        参数 值 依据 配错的后果
                                        sync_binlog + innodb_flush_log_at_trx_commit 双 1 每次提交都落盘，主库本地才可能不丢 掉电丢已 ACK 事务，半同步也救不了

                                        读写分离：复制模式给它划了三条边界

                                        读写分离的路由方式、读一致性四档策略（全读从库 / 写后读主 / 位点等待 / 强制读主）、Seconds_Behind_Source（旧名 Seconds_Behind_Master）为什么不可信，都在 37.4 读写分离——那是它的主场。本节只补复制机制给它划的边界：

                                        复制模式 RPO（能丢多少） 读一致性 写延迟 适用
                                        异步 最近 1ms–数秒的提交 可能读到旧值 最低 大多数业务
                                        半同步 ≈0（三个前提） 仍可能读到旧值 +0.5–2ms（同城） 订单、支付
                                        组复制 (MGR) 0（多数派认证） 仍可能旧（除非读主） 最慢多数派的 RTT 金融核心

                                        🔑 三条边界：① 读可能旧（由路由策略兜，见 37.4）；② 写后立刻读可能读不到（由写后读主 / GTID 位点等待兜）；③ 主库故障可能丢最近 N 条写（由复制模式兜，且只有半同步 / 组复制能兜住）。前两条是「读的问题」，第三条是「写的问题」——读写分离只能放大读能力，永远补不了写的持久性。

                                        写能力本身不够时（单主写满），下一步不是加从库，而是分库分表（见 44.14 分库分表）或换分布式数据库。

                                        「几个副本、放哪个可用区、切换由谁执行」这类拓扑级选型不在本节：见 46.7 数据库的架构定位与部署拓扑选型。

                                        CQRS 的语义边界：读写分离只是它的物理投影

                                        常有人把「主从 + 读写分离」直接叫 CQRS，这是把部署形态当成了模型划分。

                                        CQRS（Command and Query Responsibility Segregation）切的是语义：

                                        概念 能做什么 不能做什么
                                        Command 改变状态，返回执行状态（成功 / 失败 / 任务号） 不返回查询结果——要读，再发一次 Query
                                        Query 返回结果数据 没有副作用——查一次不能顺手改一次计数或写一次表

                                        这两条就是 CQRS 的全部硬约束：

                                        • Command 不返回查询结果，所以「提交订单并返回订单详情」本质是一个 Command + 一个 Query 拼在一次 RPC 里，不是 CQRS 的 Command。
                                        • Query 无副作用，所以「查列表时顺手把过期数据标记为已读」是违规写法：它让读产生了写放大，重试一次就多改一次。

                                        两者的关系一句话说清：读写分离是 CQRS 的一种物理投影——把 Query 路由到从库、Command 打在主库，是这套语义分离在部署上的一种落地。但反过来不成立：路由到了从库，模型层可能还是一个 CRUD 实体，Command 照样返回详情、Query 照样写脏数据。

                                        🔑 判据：看接口契约，不看库的拓扑。一个「读写分离 + CRUD」的系统不是 CQRS；一个单库系统只要命令与查询的语义守住了，它就是 CQRS。

                                        模型划分本身的做法见 32.1 CQRS，另一条落地路径见 32.3 读写模型分离。

                                        复制与 WAL 的关系

                                        binlog 是逻辑/行级的「做了什么」，InnoDB redo log 是物理的「页怎么改」。崩溃恢复靠 redo（见 44.2 WAL 与崩溃恢复），主从复制靠 binlog；两阶段提交（redo prepare → binlog → redo commit）保证「binlog 里有的，主库自身也一定能恢复出来」——这是复制不丢数据的前提。

                                        主备切换：可靠性优先与可用性优先，只能保一个

                                        一主一备的双 M 结构里，切换就是把「客户端连谁」从 A 挪到 B，同时把两边的 read_only 反过来：状态 1 是 A 读写、B 只读；状态 2 是 B 读写、A 只读。备库平时就该设成 read_only=ON，理由有三条，都不是洁癖：① 常有运营查询被临时丢到备库，只读能挡住误写；② 切换逻辑有 bug 时，只读是最后一道防双写的闸；③ 只读状态本身可以当作「这是备库」的角色标记。

                                        read_only 对拥有 SUPER 权限的账号无效，而备库上执行 relay log 的复制线程正是用 SUPER 权限写数据——所以备库「只读」与「能同步」并不冲突。这一条在 8.0 上可以当场验证：普通账号写入报 ERROR 1290 (HY000): The MySQL server is running with the --read-only option，root 写入照样成功。

                                        延迟的口径要先对齐，否则后面全是鸡同鸭讲：

                                        时刻 事件 说明
                                        T1 主库执行完事务、写入 binlog 客户端拿到提交确认的起点
                                        T2 备库收完这个 binlog（进 relay log） 网络正常时 T2−T1 约等于 0
                                        T3 备库执行完这个事务（对读可见） 主备延迟 = T3 − T1

                                        seconds_behind_master（8.0.26+ 显示为 Seconds_Behind_Source）算的就是 T3−T1：取备库「当前正在执行的事务」在 binlog 里的时间戳，减去当前系统时间。精度是秒。主备机器时钟不一致不会让它算错——备库建连时会执行 SELECT UNIX_TIMESTAMP() 取主库时间并扣掉差值；但取时间只在建立连接时做一次，之后再改主库系统时间，这个值就不准了。

                                        ⚠️ 网络正常时 T2−T1 很小，所以延迟的主体是「收完了但没回放完」。反过来说，Seconds_Behind_Source=0 只代表「收到的都回放完了」，不代表「主库提交的都已送达」——这个漏洞是所有过期读方案的起点，见「过期读：六种解法，六种代价」。

                                        可靠性优先：五步，代价是一段不可写窗口。

                                        步骤 动作 判据 卡住的后果
                                        1 读备库 B 的 seconds_behind_master 小于阈值（原文举例 5 秒）才继续，否则重试 延迟 30 分钟时直接切，不可用就是 30 分钟
                                        2 主库 A SET GLOBAL read_only=ON 新写入被拒 双写风险归零，业务开始报错
                                        3 等 B 的 seconds_behind_master 变成 0 relay log 追平 最耗时的一步，几秒到几十分钟
                                        4 备库 B read_only=OFF 可写 此时 A、B 都可能被写，靠步骤 2 的只读挡着
                                        5 把业务请求切到 B 连接指向改变 完成

                                        不可用窗口 = 步骤 2 到步骤 5 之间：A 已只读、B 还没放开，系统整体不可写。窗口长度≈步骤 3 的等待时间，这也是为什么步骤 1 必须先做一次判断。

                                        可用性优先：把步骤 4、5 提到最前面，几乎零不可用，代价是不一致。 原文的例子值得完整保留：表 t(id int unsigned auto_increment primary key, c int unsigned)，主备各有 3 行；业务依次执行 insert into t(c) values(4) 和 insert into t(c) values(5)；主库上其他表的大量更新已把延迟推到 5 秒；c=4 插入完成后立刻发起切换。

                                        时刻 主库 A（binlog_format=mixed） 备库 B（binlog_format=mixed）
                                        切换前 执行 insert c=4，写入 (4,4) 还在回放别的表，尚未收到这条
                                        切换中 被设成只读 直接开放读写，收到 insert c=5，写入 (4,5) 并把 binlog 回传 A
                                        追平 收到 B 的 (4,5) 回放 A 的 insert c=4，写入 (5,4)
                                        终态 有 (5,5)（来自 B 的 c=5）和 (4,5) 有 (5,4)（来自 A 的 c=4）和 (4,5)

                                        两行数据在主备上不一致：同一张表、同一个自增主键 5，一边是 c=5、一边是 c=4。换成 binlog_format=row，结果只剩一行不一致，而且两边的应用线程会直接报 duplicate key error 并停下——不一致变成了可见的故障，而不是悄悄错下去。

                                        维度 可靠性优先 可用性优先
                                        不可用窗口 秒级到「延迟长度」 ≈ 0
                                        切换后数据 一致 可能 1~2 行不一致（row 会报错停下，mixed/statement 静默）
                                        适用 常规切换、能接受秒级停写 该库不可写会卡死业务（如操作日志表），且不一致能靠 binlog 补
                                        事后成本 无 对账、补数，严重时要重建从库

                                        异常切换没有「等」的选项，这才是高可用的真问题。 假设主备延迟已有 30 分钟，主库 A 突然掉电——主动切换可以先等延迟小于 5 秒再动手，被动切换没有这个机会。可靠性优先下必须等 B 追到 seconds_behind_master=0 才能切，而这段时间 A 已死、连接还没指到 B，系统处于完全不可用。有人会想「先切到 B 但保持 B 只读」：也不行，relay log 没回放完，客户端查不到已经提交成功的事务，业务会判定为「数据丢了」——对某些业务来说，读到「暂时缺数据」和真丢数据一样不可接受。

                                        🔑 在保证数据可靠的前提下，MySQL 高可用的可用性上限由主备延迟决定：延迟越小，故障切换的 RTO 越短。把延迟从 30 分钟压到 1 秒，等于把最坏情况下的恢复时间从 30 分钟压到 1 秒——这比任何切换脚本都值钱。

                                        半同步在这里的位置容易被误解：AFTER_SYNC 让客户端收到「成功」时至少一个备库已有 binlog，把 RPO 压到 0；但备库回放到哪儿它不管，切换前照样要等 seconds_behind_master=0。半同步解决丢不丢，不解决等多久。

                                        切换期间业务看到的是连续的写失败：ERROR 1290 (HY000) ... --read-only（步骤 2 之后的主库）和连接重置（连到已死的主库）。这两类错误都不是「重试一次就好」的语义——重试可能落在尚未提升的从库上。所以客户端要么在切换窗口内做带退避的重试并把错误码 1290 当作「可重试」，要么把重试交给代理层排队；把 1290 当致命错误直接抛给用户的实现，切换一次就掉一批订单。

                                        能不能自动切换：四条判据

                                        故障检测与切换的一般流程（心跳、租约、仲裁）见 18.5 故障检测与切换，这里只给「够不够格做自动切换」的判据：

                                        判据 不成立时的后果
                                        主备延迟可控（切换窗口 ≤ 业务可接受的停写时长） RTO 没有上限，自动切换等于自动制造长故障
                                        探活能识别「假活」（见「判活」一节） 该切的时候不切，HA 一直报绿
                                        fencing 能真正执行（旧主写不进去） 脑裂双写，两份数据都「合法」
                                        有第三方仲裁（从库多数派或独立仲裁者） 两台都认为自己该当主，或该切的没人拍板

                                        四条缺任何一条，自动切换都只是「把人工决策提前到了脚本里」，误判的代价还更高。

                                        延迟的四个来源与一条 45° 直线

                                        来源 现象 判据 处置
                                        备库机器比主库差、多实例混部 回放线程等 IO 备库 IOPS 低于主库；一台机器上挤了多个实例 主备同规格、对称部署；别把 20 个主库塞 4 台机器
                                        备库承担读查询/备份 回放被查询抢 CPU 备库 QPS 高、CPU 打满，主库反而闲 一主多从分流；统计类查询走 binlog 同步到外部系统（canal、Hadoop）
                                        大事务（批量 delete、大表 DDL） 延迟直线上升，回放卡在同一个事务 relay log 积压、sql_thread 停在同一个事务上 拆批提交；DDL 用 gh-ost 一类工具（见 44.27 InnoDB 表空间与在线 DDL）
                                        并行度不足 延迟缓慢爬升、长期追不上 主库组提交并发远大于 replica_parallel_workers 换 LOGICAL_CLOCK/WRITESET，按组提交大小定 worker 数

                                        原文把「备库机器差」和「备库压力大」分成两类，处置方向相反：前者要对称部署（因为备库随时可能变成主库），后者要减少备库上的读。两者都排除后还剩大事务与并行度——这就到了并行复制的地盘。

                                        监控图上的一条 45° 直线（延迟匀速上涨、斜率不变）几乎只有两种成因：一是大事务（含大表 DDL），二是一个隐蔽的长事务——备库上有 begin; select * from t limit 1; 开着不提交，主库对表 t 做加字段，哪怕表很小，这个 DDL 在备库也会被 MDL 锁堵住，回放全线停摆。注意区分：并行度不足是「斜着爬」但会有起伏，不是标准 45°。

                                        大事务的量级可以直接量。同一张 50,000 行、行长约 68 字节的表，执行同一条「更新 5 万行」的语句，三种写法在 binlog 里的体积差三个数量级：

                                        写法 50,000 行 UPDATE 的 binlog 增长 占 FULL 的比例 回放预估（单线程 2,000 行/秒）
                                        STATEMENT 347 字节（一条 SQL 原文） 0.03% 无法按行估算，语句要在备库重跑 5 万行
                                        ROW + binlog_row_image=MINIMAL 502,493 字节 45% 约 25 秒
                                        ROW + binlog_row_image=FULL 1,105,121 字节 100% 约 25 秒

                                        口径：本机 MySQL 8.0.46、RR 隔离、innodb_page_size=16384、buffer pool 128M，表 50,000 行、行长约 68 字节（id INT + c INT + pad CHAR(60)）；三种写法的语句本身在主库都是亚秒级（0.33~0.45 秒，含客户端建连）。数据与脚本见 tools/examples/44.13-repl-lab。

                                        这张表说明两件事。其一，STATEMENT 的体积优势接近 3000 倍，这正是 mixed 格式存在的理由——但体积小不代表安全：这条 UPDATE ... ORDER BY id LIMIT 50000 在 STATEMENT 下被 MySQL 判为 unsafe，SHOW WARNINGS 给出 Note 1592 ... The statement is unsafe because it uses a LIMIT clause。原文的 delete from t where a>=4 and t_modified<='2018-11-10' limit 1 是同一个坑：表 t 上 a 和 t_modified 都有索引，走 a 索引删掉的是 a=4 那行，走 t_modified 索引删掉的是 a=5 那行——主库和备库只要选的索引不同（统计信息不同、优化器版本不同），删的就不是同一行。ROW 格式记的是主键 id=4，无论谁回放都删同一行。

                                        其二，回放时间与写入时间不成比例。 主库 0.3~0.5 秒写完的事务，备库按单线程 2,000 行/秒要回放约 25 秒——一个大事务就能把延迟顶到几十秒，而它占用的主库时间还不到半秒。批量删历史数据、批量改状态、大表 DDL 都属于这一类，处置只有一条：拆。

                                        并行复制三代：按库、按组提交、按行

                                        先把模型钉住：sql_thread 演化成 coordinator + N 个 worker（N = replica_parallel_workers，旧名 slave_parallel_workers）。coordinator 只读 relay log、分发事务，worker 真正改数据。分发必须守两条铁律，所有版本都绕不开：

                                        1. 更新同一行的两个事务必须进同一个 worker——否则两个 worker 独立执行，CPU 调度可能让后提交的事务先落地，同一行在备库上的更新顺序与主库相反。
                                        2. 一个事务不能被拆给多个 worker——事务更新 t1、t2 各一行，拆开后 t1 提交、t2 未提交的瞬间，备库上的查询会看到「半个事务」，隔离性被破坏。

                                        也不能简单轮询分发：事务 1 给 worker_1、事务 2 给 worker_2，两者改同一行时先后顺序就不受控了。

                                        代 版本/来源 分发键 并行度上限 什么时候失效
                                        按表 5.5 自研 库名.表名 表的数量 热点表：所有事务都改同一张表，退化为单线程
                                        按行 5.5 自研 库名+表名+唯一键值 无冲突行数 大事务耗内存/CPU（100 万行要 100 万个 hash 项），超阈值退化为单线程
                                        按库 5.6 官方 数据库名 库的数量 单库业务、或各库热度不均（一个业务库 + 一个配置库）
                                        组提交 MariaDB commit_id（同组相同，下一组 +1） 同组事务数 组内有大事务时，其余 worker 空转；下一组要等上一组全部完成
                                        LOGICAL_CLOCK 5.7 官方 同时处于 prepare/commit 同时 prepare 的事务数 主库组提交并发低（每批只有 2 个事务）时并行度只有 2
                                        WRITESET 5.7.22 / 8.0 每行的 hash 集合 无交集事务数 表无主键、有外键约束时退化为单线程

                                        MariaDB 的思路是「模拟主库的提交组」，5.7 把它改进一步：不等 commit，到 redo prepare 就算通过了锁冲突检验，所以「同时处于 prepare 的事务可以并行」「prepare 与 commit 之间也可以并行」。这也解释了 5.7 里 binlog_group_commit_sync_delay、binlog_group_commit_sync_no_delay_count 的另一个用途：故意拉长 binlog 从 write 到 fsync 的窗口，制造更多同时 prepare 的事务——主库提交慢一点，备库回放快一点，追延迟时可以用。

                                        WRITESET 的工程优势值得单独记：hash 在主库算好直接写进 binlog，备库分发时不用解析行数据；不用扫完整个事务的 binlog 才决定分给谁，省内存；甚至 binlog_format=statement 也能用。

                                        按库并行是三者里最省事的一代：hash 只算库名，不需要 row 格式，DB 个数有限也不会出现「百万项 hash 表」；代价是并行度上限被库的个数封死——单库业务一路单线程，两个库热度不同（业务库 + 配置库）也拿不到并行。理论上可以把热度均匀拆到多个库强行并行，但要搬数据，原文的判断是「用得并不多」。这也解释了为什么 5.6 之后还要继续做按组提交和按行：并行度不能取决于「你有几个库」这种偶然的部署细节。

                                        按行（含 WRITESET）的有效性依赖三条使用规范：binlog 必须是 row、表必须有主键、不能有外键（级联更新的行不记在 binlog 里，冲突检测就不准）。这三条本来就是线上建表规范，所以实践里很少踩到；真正会踩的是大事务——100 万行的操作要构造 100 万个 hash 项，内存和 CPU 都吃不消，实现上会给一个行数阈值（原文举的是 10 万行），超了就暂时退化为单线程：hold 住该事务、等所有 worker 空队列、coordinator 自己执行，再恢复并行。

                                        binlog_transaction_dependency_tracking 依据 适合的主库
                                        COMMIT_ORDER（默认） 同时 prepare/commit 并发写入、组提交大的主库
                                        WRITESET 行 hash 无交集即可并行 主库单线程/低并发写入、要最大并行度
                                        WRITESET_SESSION WRITESET + 同线程事务保序 需要保持同一会话内顺序

                                        原文的思考题正好考这个：5.7.22 主库单线程插入了 3 小时数据，再搭同版本备库，选哪个？答案是 WRITESET——单线程写入时每个事务的 commit_id 都不同，COMMIT_ORDER 会退化成单线程；WRITESET_SESSION 又要求同线程顺序，同样退化为单线程；只有 WRITESET 能按行冲突并行。

                                        本机默认值可以当基线（8.0.46 单实例实测）：

                                        SHOW VARIABLES LIKE 'replica_parallel%';
-- replica_parallel_type    LOGICAL_CLOCK
-- replica_parallel_workers 4
SHOW VARIABLES LIKE 'binlog_transaction_dependency_tracking';
-- COMMIT_ORDER

                                        32 核物理机建议 replica_parallel_workers 取 8~16（原文经验值），因为备库还要对外提供读，不能把 CPU 吃光。replica_preserve_commit_order=ON 与并行并不矛盾：并行的是执行，保序的是提交可见顺序，从库上看到的事务先后仍与主库一致。

                                        ⚠️ 5.7 的并行策略改了 binlog 的内容，binlog 协议不向上兼容。主备版本不一致、或升级后再降级，可能直接起不来——版本变更时把复制链路的兼容性一起纳入方案，而不是只测单机。

                                        一主多从：位点法为什么必然出错，GTID 补了什么

                                        一主多从是读写分离的物理形态：A 与 A' 互为主备，B、C、D 都指向 A。A 故障后 A' 提升为新主，B、C、D 还要重新指向 A'——切换的复杂度全在这个「重新指向」上。

                                        基于位点的切换，核心是给每个从库找一个「新主上的同步位点」，而这个位点取不准：

                                        步骤 命令 输出与坑
                                        1 等 A' 把 relay log 全部回放完 没追平就不能当基准
                                        2 SHOW MASTER STATUS（A' 上） 得到最新 File 与 Position
                                        3 取原主 A 的故障时刻 T 只能取个大概
                                        4 mysqlbinlog File --stop-datetime=T --start-datetime=T 找到 T 时刻的 end_log_pos（原文例子里是 123）
                                        5 B 上 CHANGE MASTER TO MASTER_LOG_FILE=..., MASTER_LOG_POS=... 从位点往后拉；8.0.26+ 写作 CHANGE REPLICATION SOURCE TO SOURCE_LOG_FILE=..., SOURCE_LOG_POS=...

                                        位点不精确的典型后果：T 时刻 A 已插入行 R、binlog 也发给了 A' 和 B，然后掉电。此时 B 上已有 R，按 123 位点再拉一遍，就会重复执行插入 R 的 binlog，从库报 Duplicate entry ... for key 'PRIMARY'（1062）并停住。反方向是 1032（删除时找不到行）。跳过手段有两种：

                                        -- 逐个事务跳：跳过一个 event 后会跳到事务末尾，所以等于跳过整个事务
SET GLOBAL sql_slave_skip_counter = 1;
START SLAVE;

                                        # 批量跳过指定错误码：只在 my.cnf 里配，不能运行时 SET
[mysqld]
slave_skip_errors = 1032,1062

                                        两种手段的适用面不一样。sql_slave_skip_counter 是运行时变量，但只能一个事务一个事务地跳，切换过程中要盯着错误反复执行，跳完还要确认没有新错误；slave_skip_errors 是启动参数——本机 8.0.46 上执行 SET GLOBAL slave_skip_errors='1032,1062' 会直接报 ERROR 1238 (HY000): Variable 'slave_skip_errors' is a read only variable，只能改 my.cnf 重启。它的风险也更大：切换窗口内跳 1032/1062 是无损的（这两类错误只可能来自位点不精确），但同步稳定后必须清空并重启，否则之后真的主从不一致也会被它吞掉。

                                        GTID 把这个过程变成「集合运算」。GTID = server_uuid:gno，server_uuid 是实例首次启动生成的全局唯一值，gno 在提交时分配（回滚不占号，所以看起来连续）。两种生成方式取决于 gtid_next：automatic 时由系统分配 server_uuid:gno 并加进本实例的 GTID 集合；指定具体 GTID 时，若该 GTID 已在集合里则事务被忽略，不在则直接用它、gno 不加 1。

                                        切换只用一条：CHANGE MASTER TO ..., SOURCE_AUTO_POSITION=1（旧语法 MASTER_AUTO_POSITION=1）。从库 B 把自己的 GTID 集合 set_b 发给新主 A'，A' 算 set_a − set_b，只发差集里的事务；如果差集需要的事务已经被 purge 掉，A' 直接报错拒绝。这与位点协议的设计哲学不同：位点协议由备库说了算、主库不检查日志完整性；GTID 协议认为「建立主备关系就必须保证日志完整」，所以缺日志时宁可拒绝，也不给一个看起来能跑、实际有洞的复制链。

                                        动作 位点法 GTID 法
                                        找基准 解析 binlog 找 T 时刻位点 不需要，主库自己算
                                        从库指令 FILE + POS AUTO_POSITION=1
                                        重复事务 报 1062/1032，手工 skip 集合去重，自动跳过
                                        主库缺日志 不检查，可能重放错位 直接报错
                                        后遗症 slave_skip_errors 忘清空 → 真不一致也被吞 无

                                        补 GTID 的标准动作是「空事务」——把某个 GTID 塞进本实例的集合，让后续同名事务被忽略：

                                        SET GTID_NEXT = 'aaaaaaaa-cccc-dddd-eeee-ffffffffffff:10';
BEGIN;
COMMIT;
SET GTID_NEXT = automatic;
START SLAVE;

                                        这套动作还是 GTID 下做在线 DDL 的正解。双 M 结构里在备库加索引，若用 SET sql_log_bin=OFF 关掉 binlog，主库上就永远没有这条 DDL——schema 分叉。替代做法是：主库 STOP SLAVE → 备库执行 DDL（不关 binlog，生成 GTID server_uuid_of_Y:gno）→ 主库用上面的空事务序列把这个 GTID 标记为「已执行」→ START SLAVE。效果是 DDL 有 binlog、有 GTID，但主库不会真的再执行一遍。

                                        旧主恢复后回来的流程：先 SET GLOBAL super_read_only=ON 挡住写入，再按 GTID 把它接成新主的从库（SOURCE_AUTO_POSITION=1），确认 Executed_Gtid_Set 追平后再决定是否切回。别在主库上执行 RESET MASTER：它会清空 GTID 集合，从库随后会静默跳过 gno 小于当前值的事务——复制看起来没报错，数据却不再同步。

                                        拓扑上一主多从还会演化成级联复制（A → A' → B），好处是主库只服务一个下游、避免网卡与 dump 线程被从库数量拖垮。代价是延迟读数被放大：Seconds_Behind_Source 比的是「当前时间」与「这个事务在 A 上写下 binlog 的时间」，A 上一条耗时 1 分钟的 DDL，在级联第二跳的 B 上最长延迟约 2 分钟——多一跳就多一分钟，并不代表 B 落后了两倍的数据量。级联越深，越不能只看单个延迟数字。

                                        过期读：六种解法，六种代价

                                        「刚写完，读不到」在读写分离里是常态而非故障。它有两个层次：一是「已提交但备库还没回放」，二是「备库连日志都还没收到」。前者靠等，后者靠半同步。

                                        方案 做法 能保证什么 代价
                                        强制走主库 请求分两类：必须最新的走主库，能忍旧的走从库 一定读到最新 主库读压力上升；全走主库等于放弃扩展性
                                        sleep N 秒 写完先等，或前端先用本地数据渲染再刷新 概率正确 不精确：0.5 秒能拿到的也要等满；延迟超过 N 秒照样过期读
                                        等 SBM=0 查询前等 seconds_behind_master=0 备库「收到的」都回放完 已提交未送达的事务仍读不到；秒级精度
                                        等比位点 Master_Log_File+Read_Master_Log_Pos 与 Relay_Master_Log_File+Exec_Master_Log_Pos 两组全等 同上、更精确 高峰期位点一直在更新，查询可能一直等不到
                                        等主库位点 SELECT master_pos_wait(file, pos, 1) 该位点之前的事务已回放 每次写后多一次 SHOW MASTER STATUS；超时要退化到主库
                                        半同步 + 位点判断 semi-sync 保证「已确认 = 已送达」，再加位点等 一主一备下可避免过期读 一主多从只有回 ACK 的那个从库是新的
                                        等 GTID SELECT wait_for_executed_gtid_set(gtid1, 1) 精确到「这个事务」 需 session_track_gtids=OWN_GTID 并解析返回包

                                        两条等待语句的返回值必须背下来，返回值决定「查从库还是回主库」：

                                        语句 返回 含义 动作
                                        master_pos_wait(file, pos, timeout) ≥0 整数 等待期间又执行了 M 个事务，该位点已应用 在从库查
                                        0 调用时就已经执行过该位点 在从库查
                                        -1 超时 退化到主库
                                        NULL 复制线程异常 退化到主库并告警
                                        wait_for_executed_gtid_set(gtid_set, timeout) 0 传入的 GTID 集合已全部执行 在从库查
                                        1 超时 退化到主库

                                        两个函数都有前置条件，写错就是运行时报错而不是「慢一点」：wait_for_executed_gtid_set 要求 gtid_mode=ON，本机 8.0.46 在 gtid_mode=OFF 下直接返回 ERROR 3062 (HY000): Cannot use WAIT_FOR_EXECUTED_GTID_SET when GTID_MODE = OFF；master_pos_wait 在没有复制关系（或复制线程异常）的实例上返回 NULL——本机单实例上实测就是 NULL，所以调用方必须能区分「等到了」和「问不到」。

                                        -- 事务提交后直接从返回包拿本次事务的 GTID（需客户端调用 mysql_session_track_get_first 解析）
SET SESSION session_track_gtids = OWN_GTID;

-- 在选定的从库上等这个 GTID 落地：0 = 已执行，1 = 超时
SELECT wait_for_executed_gtid_set('3E11FA47-71CA-11E1-9E33-C80AA9429562:101', 1);

-- 没有 GTID 时用位点等：>=0 已到该位点，-1 超时，NULL 复制线程异常
SELECT master_pos_wait('binlog.000007', 12345, 1);

                                        半同步 + 位点判断有两个漏洞，原文说得很清楚：① 一主多从时主库只等一个从库的 ACK，查询落到没回 ACK 的从库照样过期读；② 位点判断要求「完全无延迟」，而业务其实只需要「我这个事务已回放」。原文的 bad case 是主备持续相差一个事务——从状态 1 到状态 4 一直差一条，按「必须无延迟」的逻辑，这条 select 从头等到尾都执行不了，实际上在状态 3 查就已经能拿到预期结果了。

                                        🔑 过期读不可能被「消除」，只能被定价：要么多等（延迟换一致），要么回主库（主库容量换一致），要么业务容忍旧值（一致性换吞吐）。选择依据是「这个查询读错的业务代价」，不是「哪种方案更先进」。

                                        全部从库都延迟时，等不到就会把流量打回主库——这本身可能把主库打挂，所以限流和降级必须与等待方案同时上线：降级开关有两个，把等待超时调到 0（等价于强制走主库）和按比例把读切回主库，两者都要能在线改，不能写死在业务代码里。原文的延伸问题同样现实：对大表做 10 分钟的 DDL，这 10 分钟内所有「等 GTID」的查询都会超时并转到主库，预期内的 DDL 应该放在低峰、先把读切到主库、等从库追上再切回来。

                                        判活：select 1 通过，不代表这个库能干活

                                        select 1 能证明的只有三件事：进程在、端口通、能返回一行常量。它不进 InnoDB，不碰缓冲池、不碰锁、不碰磁盘。

                                        被它漏掉的第一类问题是 InnoDB 并发线程打满。innodb_thread_concurrency 控制进入 InnoDB 的并发线程上限（默认 0 = 不限；建议 64~128），达到上限后新请求排队。这里要区分两个概念：SHOW PROCESSLIST 里几千行是并发连接（只占内存），真正吃 CPU 的是并发查询（正在执行的语句）。还有一个设计细节：进入行锁/间隙锁等待的线程，并发计数会减一——否则 128 个等锁线程就能把引擎堵死，而它们其实不吃 CPU。

                                        探测方法 能发现 发现不了 代价与坑
                                        SELECT 1 进程死、端口不通、连接被打满 InnoDB 线程打满、锁等待、磁盘满、误设只读 零成本；MHA 默认就是它
                                        查 mysql.health_check 一行 InnoDB 并发线程打满 binlog 盘满（此时读仍正常） 要在系统库建表、授权
                                        UPDATE mysql.health_check SET t_modified=now() 上述两者（提交要写 binlog） IO 100% 但探针仍能在超时前挤进去 双 M 下必须用 server_id 做主键，否则互相回传 insert 触发 1062 停同步
                                        performance_schema 的 MAX_TIMER_WAIT 单次 IO 超过阈值（如 200ms） 需要打开 instrument（全开约 10% 性能损耗） 是「一段时间内的统计」，不是某一刻的快照

                                        健康检查表的设计有个必须避开的坑：双 M 结构里主备都用同一条 insert ... on duplicate key update 检测，如果表里只有一行（id=1），空表时两边都会写出一条 insert 的 binlog，回传到对方就撞主键，同步直接停。正确做法是用 @@server_id 做主键、每个实例一行：

                                        CREATE TABLE mysql.health_check (
  id         INT NOT NULL,
  t_modified TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id)
) ENGINE=InnoDB;

INSERT INTO mysql.health_check(id, t_modified)
VALUES (@@server_id, NOW())
ON DUPLICATE KEY UPDATE t_modified = NOW();

                                        「判定慢」是外部检测的固有缺陷：日志盘 IO 利用率 100% 时，业务 SQL 已经慢到不可用，但检测用的 update 只需要很少的 IO，仍可能在超时阈值内返回，HA 系统于是认为「主库健康」。根因是外部检测靠定时轮询，天然有随机性：故障可能发生在两次轮询之间，第一次探测还未必撞上。

                                        内部统计能补这一块。performance_schema.file_summary_by_event_name 按事件类型统计 IO 耗时（单位皮秒），wait/io/file/innodb/innodb_log_file 是 redo log、wait/io/file/sql/binlog 是 binlog，MAX_TIMER_WAIT 就是单次最坏耗时：

                                        -- 只开需要的 instrument，全开有性能损耗
UPDATE setup_instruments SET ENABLED='YES', TIMED='YES'
WHERE NAME LIKE 'wait/io/file/%';

-- 单次 IO 超过 200ms 视为异常
SELECT EVENT_NAME, COUNT_STAR, ROUND(MAX_TIMER_WAIT/1000000000, 3) AS max_ms
FROM performance_schema.file_summary_by_event_name
WHERE EVENT_NAME IN ('wait/io/file/innodb/innodb_log_file', 'wait/io/file/sql/binlog')
  AND MAX_TIMER_WAIT > 200 * 1000000000;

-- 取走异常信息后清空累计值，下一轮才能看出新增异常
TRUNCATE TABLE performance_schema.file_summary_by_event_name;

                                        探针本身的代价也可以量化。同一实例、同一个 performance_schema.events_statements_history 口径下：

                                        探针 冷缓存首读 预热后 是否访问 InnoDB
                                        SELECT 1 1.907ms 0.122ms 否
                                        SELECT COUNT(*) FROM big（50,000 行） 366.461ms 3.738ms 是，全表扫

                                        口径：MySQL 8.0.46、单实例、两个探针在同一 mysql 会话中先后执行，取 performance_schema.events_statements_history 的 TIMER_WAIT；冷缓存指重启后第一次访问该表，预热指同一实例上再次全表扫。SELECT 1 的耗时与表大小、缓存状态无关，因为它根本没进存储引擎——引擎层出问题时它照样秒回。真正的判活至少要有一条「读真实表」或「写系统表」的探针。

                                        只读状态也可以拿来做检测，代价是一条 SQL：

                                        SET GLOBAL read_only = ON;        -- 普通账号写入：ERROR 1290 (--read-only)
SET GLOBAL super_read_only = ON;  -- 连 SUPER 一起挡：ERROR 1290 (--super-read-only)

                                        💡 把 innodb_thread_concurrency 设小来「保护 CPU」，代价是正常查询在引擎门口排队，那套排队行为与实测数字见 44.30 MySQL 应急手册。本节只需要记住一句：select 1 根本不进 InnoDB，门口排多长的队它都测不出来。

                                        判活的结论不是「换更贵的探针」，而是三层叠加：select 1（进程/网络）、读写真实表（InnoDB 与 binlog）、performance_schema（单次 IO 的最坏值）。每加一层都多一分开销与误报，按业务的 RTO 要求选层数。原文的倾向也是这个顺序：先 update 系统表，再补 performance_schema 的内部统计。

                                        从库 read_only 没开 人为写入导致分叉
                                        100 万行的大事务一次性提交 从库回放 500 秒，期间所有读都是旧数据

                                        业务高峰对大表做 DDL，指望「等 GTID」的读请求自己撑过去 等待集中超时，读流量瞬间全打回主库，主库被打挂

                                        slave_skip_errors 切换完没清空 之后真的 1032/1062 也被吞掉，数据悄悄分叉

                                        自检

                                        Q1 同事说「我们开了半同步，所以主库挂了也不会丢数据」。要让他补充哪三个前提？

                                        ▸ 答案：① 必须是 AFTER_SYNC——AFTER_COMMIT 是「先提交再等 ACK」，客户端看到提交后主库崩溃仍会丢；② ACK 的那个从库不能和主库一起挂——同机架、同可用区、同电源的从库不算数，RPO=0 要求故障域独立；③ relay log 必须真正落盘（sync_relay_log=1 级别），否则 ACK 只代表「进了页缓存」，OS 崩溃照样丢。外加一条运维前提：超时退化要告警，rpl_semi_sync_master_timeout 触发后系统已悄悄退化为异步。

                                        Q2 主库宕机。C 从库 GTID 最全（收到 398 条，主库已提交 400 条），但回放落后 199 条；A 从库回放最新（396 条），比 C 少 2 条事务。你选谁？

                                        ▸ 答案：选 C。已经提交给客户端的数据要尽量少丢：选 C 丢 2 条，选 A 丢 4 条——A 少的那 2 条也是客户端收到过「成功」的事务。代价是 C 要先把 relay log 回放完（199 条、按 1 条/ms 约 200ms）才能开放写，RTO 增加 200ms。只有业务明确接受「多丢 2 条换 200ms」时才选 A，且必须留下数据差异清单人工补偿。判据是 RPO 要求，不是谁恢复得快。

                                        Q3 复制延迟 30 分钟，但从库 CPU 只有 10%、主库 CPU 70%。问题最可能在哪？

                                        ▸ 答案：不在算力，在串行。CPU 低说明回放线程大部分时间在等：等一个大事务回放完（单事务无法并行）、等锁、等磁盘 fsync，或者并行 worker 数远小于主库的组提交并发度。排查顺序：① 看 relay log 积压量与 Slave_SQL_Running_State 卡在哪个事务；② 找 binlog 里最大的事务（行数 × 行长）；③ 看主库组提交大小与 replica_parallel_workers 是否匹配。加 CPU、加带宽都无效——回放的瓶颈是「一个事务只能由一个线程回放」。

                                        Q4 binlog 保留期应该设多长？和备份策略是什么关系？

                                        ▸ 答案：binlog 保留期 ≥ 全备周期 + 最长恢复演练时间。恢复链路是「最近一次全备 + 从该全备位点重放 binlog 到目标时刻」，若全备 7 天一次，binlog 至少要留 8 天，否则最坏情况下只能恢复到 7 天前的全备点，RPO 从「秒级」变成「天级」。同时要校验：gtid_purged 不能超过全备的起点，否则从库无法增量追。云数据库的「自动备份 + binlog 备份」要一起看，别只看备份保留天数。

                                        Q5 为什么说「读写分离解决不了写瓶颈」？什么情况下才轮到分库分表？

                                        ▸ 答案：读写分离只是把读分散到多个从库，写仍然打在唯一主库上：主库写 TPS 的上限（单机 5k–2 万 TPS 量级，取决于行大小与索引数）不变。判据：主库写 CPU 持续 >70%、单表 > 数千万行且 DDL 窗口不可接受、单库磁盘 >2TB、备份恢复超过 RTO——满足其中两条，才考虑分库分表（见 44.14 分库分表）。先确认瓶颈是「读多」还是「写多」：读多→读写分离 + 缓存；写多→分片。

                                        Q6 主库 sync_binlog=1、innodb_flush_log_at_trx_commit=1、半同步也开了，能保证 RPO=0 吗？

                                        ▸ 答案：只能保证“主库本地不丢 + 至少 1 个从库确认收到”。还差四个缺口：① 半同步是 AFTER_SYNC 还是 AFTER_COMMIT（后者会丢已确认事务）；② 超时退化为异步后没有告警；③ 从库侧落盘与回放进度（sync_binlog、sync_relay_log、Executed_Gtid_Set）；④ 切换时选了没追平的从库。RPO=0 是“参数 + 告警 + 切换流程”一起给的。

                                        Q7 一个系统「主库写、三个从库读」，团队说「我们做了 CQRS」。这个说法对吗？CQRS 的两条硬约束是什么？

                                        ▸ 答案：不对，他们做的是读写分离。CQRS 是语义上的模型划分，两条硬约束是：① Command 只改状态、返回执行状态，不返回查询结果；② Query 无副作用。只把读路由到从库，模型层还是 CRUD 实体，Command 照样返回详情、Query 照样顺手写表，那只是 CQRS 的一种物理投影，投影不等于实现。判据是看接口契约，不看库的拓扑：单库系统只要命令与查询的语义守住了，它就是 CQRS；主从再多的系统字面上也可能完全不是。

                                        Q8 主备延迟 30 分钟时主库突然掉电，业务要求「已确认的订单一条都不能丢」。你按什么顺序切？如果业务只给 1 分钟 RTO，问题该在哪里解决？

                                        ▸ 答案：只能走可靠性优先：先确认新主候选，把它自己的 relay log 回放完，等 seconds_behind_master 追到 0，再开放写——代价是最坏 30 分钟不可写。不能为了快就「先切过去但保持只读」，那会让客户端读到「已提交却查不到」的状态，业务会判定为丢数据；也不能改成可用性优先，那等于主动丢 30 分钟订单。若 RTO 只有 1 分钟，答案不在切换脚本里，而在故障之前：把延迟压到秒级（拆大事务、并行回放）、用半同步把 RPO 压到 0、用同城多副本把「等回放」的时间缩到亚秒——RTO 的上限在延迟，延迟的上限在日常运维。

                                        Q9 监控显示备库 Seconds_Behind_Source=0，客户端刚提交的一笔订单却读不到。这算不算矛盾？给出两种能兜住的做法，并说明各自的代价。

                                        ▸ 答案：不矛盾。Seconds_Behind_Source 算的是「已收到的 relay log 是否回放完」，而订单的 binlog 可能还没送到备库（客户端已收到提交确认）——这是「已确认未送达」，属于等不出来的过期读。兜法一：半同步 AFTER_SYNC，保证「已确认 = 至少一个从库已收到」，再配合只把读路由到那个回了 ACK 的从库（一主多从下别的从库仍可能旧）；代价是每条提交多一次 RTT。兜法二：等 GTID，提交后拿到 gtid1，在从库执行 SELECT wait_for_executed_gtid_set(gtid1, 1)，返回 0 才查从库、返回 1 退化到主库；代价是每次多一次等待，全部从库都超时时流量会压回主库，必须配合限流。
