          44.27 InnoDB 表空间、空间回收与在线 DDL

          一句话

          表文件删完数据不缩，不是删得不够狠，而是 DELETE 只把页内名额标成可复用、从不把字节还给操作系统；要缩只有重建表一条路，而重建在 8.0 里分三档——INSTANT 只改元数据、INPLACE 边拷边收日志、COPY 建临时表逐行拷，选错档位的代价是分钟级锁表。

          来源：InnoDB 表空间与空洞机制、重建表的 Online DDL 流程、分区表的两层视角、复制表的四条路线来自丁奇《MySQL 实战 45 讲》（极客时间，2019）第 13、41、43、44 讲；本节 SQL 与实测为本机 linux/arm64 容器内的 MySQL 8.0.46 补充。

          环境：MySQL 8.0.46 容器，innodb_page_size=16384，innodb_buffer_pool_size=128M，默认 REPEATABLE-READ，单机无主从。

          表空间的账本有四层：表空间 → 段 → 区 → 页

          本节要点

          页是 IO 单位（16KB），区是分配单位（1MB = 64 页），段是"一个索引的页集合"，表空间是"文件"——回收空间卡在区与文件之间，因为文件只增不缩。

          层级 单位 大小 归谁管 判据
          表空间 tablespace 一个 .ibd 文件（独立）或 ibdata1（共享） 无上限，按区扩展 InnoDB 能否 DROP 掉整个文件
          段 segment 一个索引的页集合 按需增长 InnoDB InnoDB 里每个索引有两个段：叶子段 + 非叶子段（回滚段另算）
          区 extent 连续 64 个页 1MB（innodb_page_size=16384 时） InnoDB 空间分配的最小单位，空洞以"区是否整块空闲"体现
          页 page B+ 树节点 16KB InnoDB 记录存这里，删除留下的洞也在这里

          页大小由 innodb_page_size 在建库时决定，建库后不可改；区的大小随页大小联动（16KB 页 → 1MB 区；32KB 页 → 2MB 区），所以"1MB = 64 页"只在默认页大小下成立。本机实测 @@innodb_page_size = 16384。

          独立表空间与共享表空间：一个能还，一个只借不还

          innodb_file_per_table 决定表数据放哪：

          维度 ON（独立表空间） OFF（共享表空间）
          数据位置 每表一个 库名/表名.ibd 全部挤进 ibdata1，与数据字典同住
          DROP TABLE 直接删文件，空间立刻还给 OS 页只标可复用，ibdata1 不变
          单表搬迁 cp 一个文件即可（可传输表空间） 无法单独搬
          单表大小 受文件系统限制 全库共享，互相挤占
          本机实测 sp/t.ibd 独立存在，字节数可 ls 灌 10 万行后 ibdata1 12MB → 76MB，DROP TABLE 后仍 76MB

          🔑 独立表空间是"空间能回收"的前提：DROP 删的是一个文件，重建换的也是一个文件。共享表空间里删表只是把页标记成可复用，ibdata1 只增不减——这是"删了表磁盘还是满的"最常见的一种解释。

          innodb_file_per_table 从 MySQL 5.6.6 起默认 ON。这里有个口径差：5.6.6 的 changelog 记录了默认值从 0 改 1，而官方 glossary 写的是 5.6.7，两处不一致，不影响结论——5.6.6 及以后默认开。8.0 之前表结构存在 .frm 文件里，8.0 起表结构进系统数据字典，*.frm 消失，但数据部分的空间账本没变。

          💡 缓冲池与页的关系在 44.3 缓冲池与页面管理 里是主场；这里的页只关心"磁盘上占多少字节"。

          删除为什么"文件不变"：空洞的三种来源

          本节要点

          DELETE 做的是"标记 + 加入复用链表"：记录位置可复用、整页可复用、相邻页可合并，但磁盘文件从不因此缩短一个字节，腾出来的空间在文件内部形成"空洞"。

          删除分三个粒度，复用规则完全不同：

          粒度 InnoDB 的动作 谁能复用 文件变化
          删一条记录 标记删除（等 purge 线程真正清理） 只有符合范围条件的插入能复用这个位置 不变
          删光一页 整页从 B+ 树摘下，标记可复用 任意位置的新插入 不变
          相邻两页利用率都低 把两页数据合并到一页，另一页标记可复用 任意位置 不变

          原文的例子很直白：删掉 R4（ID=300 与 600 之间）后插入 ID=400 可以复用这个位置，插入 ID=800 就不能——记录的复用是范围受限的，页的复用才是自由的。

          空洞不止来自删除：

          来源 机制 后果
          DELETE 记录标记删除，页内留空隙 页利用率下降
          随机插入 页满触发页分裂，原页末尾留空 索引变"松"，页数变多
          UPDATE 改索引列 本质是"删旧值 + 插新值" 同删除 + 随机插入

          页分裂的代价可以量化。同样 5 万行、同样 217 字节的行宽，只差插入顺序：

          插入顺序 file_size 页数 DATA_LENGTH
          主键递增（INSERT ... SELECT 顺序） 20971520 1280 12.52 MB
          随机（ORDER BY RAND() 打乱后插入） 28311552 1728 19.52 MB

          同样是 5 万行，随机插入多占 35% 的页、多花 7MB 文件。 这不是"数据变多了"，纯粹是页分裂留下的半空页。它同时也解释了为什么"重建表能缩"——重建时数据是按主键顺序读出来再顺序写进去的，页分裂不会发生。

          复现：bash code/run.sh 的第 3 段（code/05-fragment.sql），完整输出见 tools/examples/44.27-mysql-space/。

          所以大量增删改过的表都带空洞；把空洞去掉，就是重建表要干的事。反过来，按主键递增顺序插入的表索引是紧凑的，空洞最少。

          实测：删掉一半，.ibd 一个字节没少

          10,000 行、CHAR(200) 撑大每行、主键递增插入，然后删一半（file_size 取自 information_schema.INNODB_TABLESPACES，其余取自 information_schema.TABLES）：

          阶段 file_size（字节） 页数 DATA_LENGTH DATA_FREE
          初始 10000 行 10485760 640 2.52 MB 4.00 MB
          DELETE 一半（剩 5000 行） 10485760 640 2.52 MB 4.00 MB
          OPTIMIZE TABLE 之后 7340032 448 2.52 MB 4.00 MB

          删一半之后字节数和页数一个没变；重建之后少了 30%，而 DATA_LENGTH / DATA_FREE 三行完全一样——这两个指标根本不反映页内空洞。

          OPTIMIZE TABLE sp.t 的返回也说明它是重建而不是"原地整理"：

          +-------+----------+----------+-------------------------------------------------------------------+
| Table | Op       | Msg_type | Msg_text                                                          |
+-------+----------+----------+-------------------------------------------------------------------+
| sp.t  | optimize | note     | Table does not support optimize, doing recreate + analyze instead |
| sp.t  | optimize | status   | OK                                                                |
+-------+----------+----------+-------------------------------------------------------------------+

          ⚠️ 别把 information_schema.TABLES.DATA_FREE 当碎片率：它是"整块空闲的区"，页内空洞不计入。上表里删一半前后都是 4.00MB，DATA_LENGTH 也一动不动，唯一变化的是 OPTIMIZE 之后文件字节数。要看真实字节数，用 information_schema.INNODB_TABLESPACES.FILE_SIZE（本机 10485760 → 7340032）或直接 ls -l 那个 .ibd。

          TRUNCATE / DROP / DELETE 的差别

          操作 实际动作 空间回收 可回滚 binlog
          DELETE FROM t 逐行标记删除，写 undo/redo/binlog 不回收，只留可复用空洞 可以（事务内） row 格式记每行删除
          DELETE FROM t（全表） 同上，所有页标可复用 文件不变 可以 同上，量大到能打爆磁盘
          TRUNCATE TABLE t 等价的 DROP + CREATE，换一个新表空间 整文件回收：实测 7340032 → 131072 字节 不可以 记 DDL，不记行
          DROP TABLE t 删表空间文件 + 数据字典登记 整文件回收（独立表空间时） 不可以 记 DDL
          DROP TABLE t（file_per_table=OFF） 页还回共享表空间复用链 不回收：实测 ibdata1 79691776 字节不变 不可以 记 DDL

          🔑 DELETE 还的是页内名额，TRUNCATE / DROP 还的是整个文件。前者能回滚、能进 binlog 做闪回；后者不可回滚，TRUNCATE 之后想找回数据只能靠备份或 binlog 里那条 DDL 之前的位置。

          TRUNCATE 在实测里 1.06s 完成（含客户端连接开销），对象是一张 5 万行、17MB 的表（17.00MB → 0.13MB）：这点时间里几乎全是元数据操作，它不逐行删数据。

          重建表：唯一能把空洞还给 OS 的动作

          本节要点

          重建表 = 按主键顺序把数据读出来、写进一个新文件、再换名：新文件里没有空洞，页利用率拉满，代价是一份额外空间 + 全表扫描的 IO + 重建期间的写日志。

          重建不是"压缩"，是"重排"。原文的流程拆开是四步：

          1. 新建一个与 A 结构相同的表 B；
          2. 按主键 ID 递增顺序，把 A 的数据一行行读出来插进 B（顺序插入不会产生页分裂，B 的主键索引紧凑）；
          3. 数据导完后，用 B 替换 A（MySQL 5.5 之前就是这套，临时表建在 server 层，DDL 全程表 A 不能有更新）；
          4. 5.6 引入 Online DDL 后，第 2 步变成"InnoDB 内部建临时文件 + 把期间对 A 的增删改记进 row log"，最后把 row log 应用到临时文件再换文件。
          阶段 5.5 及之前（COPY） 5.6+ Online DDL（INPLACE）
          临时文件位置 server 层临时表 InnoDB 内部 tmp_file
          重建期间能否 DML 不能，全程锁写 能，增量写进 row log
          增量日志 无 row log，上限 innodb_online_alter_log_max_size
          结束时动作 导完 → 换名 → 删旧表 应用 row log → 换文件
          失败恢复 旧表还在，丢弃临时表 旧表还在，丢弃临时文件

          Online DDL 之所以"在线"，靠的是 row log 兜住重建期间的写；一旦这段时间的写入量超过 innodb_online_alter_log_max_size（本机实测 134217728，即 128MB），DDL 会失败回滚——大表在写入高峰做重建，最可能的失败原因就是它。这个参数的语义是"online log 的上限，超了 DDL 报错"，本机只验证了取值 128MB，没有压到超限。

          三个容易答错的细节

          ① inplace 也要占额外空间。 原文的经典问答：1TB 的表、磁盘剩 1.2TB，能不能做 inplace 重建？不能。inplace 的"原地"只是相对 server 层而言（没有 server 层临时表），InnoDB 内部的 tmp_file 一样要占接近一张表的空间。再造一份 1TB 需要 2TB 空间，1.2TB 不够。

          ② inplace 不等于 online。 关系是单向的：

          🔑 Online 的 DDL 一定是 inplace 的；inplace 的 DDL 不一定 online。 全文索引、空间索引就是反例——ALGORITHM=INPLACE 能过，LOCK=NONE 过不了。

          ③ OPTIMIZE / ALTER / ANALYZE 不是一回事。

          命令 本质 改数据文件 锁
          ALTER TABLE t ENGINE=InnoDB recreate（重建表） 是 5.6+ 走 Online DDL
          ALTER TABLE t FORCE 强制 recreate，语义同上 是 同上
          OPTIMIZE TABLE t recreate + analyze 是 同 recreate，另加统计信息刷新
          ANALYZE TABLE t 只重算索引统计信息 否 MDL 读锁

          ANALYZE 不缩空间——它连数据页都不碰；OPTIMIZE 的价值在"重建 + 顺便刷新统计信息"，原文作者的偏好是直接用 ALTER TABLE t ENGINE=InnoDB（少一次 analyze）。

          为什么重建之后可能更大

          原文留过一道题：1TB 的表做完 ALTER TABLE t ENGINE=InnoDB，空间不但没小，还变成了 1.01TB。原因在填充因子：重建时页不是塞到 100%，而是按约 90% 的利用率重新组织，留 10% 给后续 UPDATE。如果重建前页利用率已经高于 90%（比如表只有插入、没有删除，页本来就紧），重建后反而会多出几个百分点的空间。

          本机复现了一个温和版本：一张 5 万行、按主键递增插入、从未删除的表，ALTER TABLE src ENGINE=InnoDB, ALGORITHM=INPLACE, LOCK=NONE 之后 17MB → 16MB（-5.9%，耗时 6.08s）。它确实缩了一点，但缩的比例远小于"删除比例"——这就是"重建治碎片、不治数据量"的意思。

          ⚠️ 重建前先算两笔账：空间账（要能放下接近一张表大小的 tmp_file）和时间账（全表读 + 全表写 + 应用 row log，实测 5 万行/17MB 用了 6.08s，按行数线性外推 1 亿行就是小时级）。

          在线 DDL 的三档算法：INSTANT / INPLACE / COPY

          本节要点

          8.0 把 DDL 分成三档：能只改元数据的走 INSTANT（毫秒级、不碰数据页）、能边拷边收日志的走 INPLACE（秒到分钟、不锁 DML）、剩下的一律 COPY（建临时表逐行拷、锁写）——能不能选到前两档，取决于"改的东西能不能用元数据表达"。

          维度 ALGORITHM=INSTANT ALGORITHM=INPLACE ALGORITHM=COPY
          做什么 只改数据字典；新列默认值按需展开 重建/就地改索引，期间 DML 记 row log 建临时表，逐行拷数据
          是否拷数据页 否 是（或改索引结构） 是
          是否允许 DML 允许（不需要也不接受 LOCK 子句） LOCK=NONE 时允许 不允许，锁写
          额外磁盘 几乎为 0 接近一张表 接近一张表
          8.0 典型操作 ADD COLUMN（8.0.12+，8.0.29+ 支持任意位置）、DROP COLUMN、改列默认值、改列名 ADD INDEX、DROP INDEX、重建表、改索引类型 改列类型/字符集、加全文索引（LOCK=SHARED）
          本机实测 ADD COLUMN ... ALGORITHM=INSTANT 立即返回，file_size 不变 ADD INDEX ... LOCK=NONE 成功 改字符集必须走它

          实测：三次成功、四次报错

          -- 成功：INSTANT 加列（含 AFTER，8.0.29+ 支持任意位置）
ALTER TABLE ddl_t ADD COLUMN c1 INT, ALGORITHM = INSTANT;
ALTER TABLE ddl_t ADD COLUMN c3 INT AFTER a, ALGORITHM = INSTANT;

-- 失败：INSTANT 加索引 → 只能 INPLACE
ALTER TABLE ddl_t ADD INDEX idx_c1 (c1), ALGORITHM = INSTANT;
ERROR 1845 (0A000): ALGORITHM=INSTANT is not supported for this operation. Try ALGORITHM=COPY/INPLACE.

-- 失败：INSTANT 不接受 LOCK 子句
ALTER TABLE ddl_t ADD COLUMN c4 INT, ALGORITHM = INSTANT, LOCK = NONE;
ERROR 1221 (HY000): Incorrect usage of ALGORITHM=INSTANT and LOCK=NONE/SHARED/EXCLUSIVE

-- 成功：INPLACE + LOCK=NONE 加索引，不锁 DML
ALTER TABLE ddl_t ADD INDEX idx_a (a), ALGORITHM = INPLACE, LOCK = NONE;

-- 失败：改字符集只能 COPY
ALTER TABLE ddl_t MODIFY pad VARCHAR(200) CHARACTER SET gbk, ALGORITHM = INPLACE;
ERROR 1846 (0A000): ALGORITHM=INPLACE is not supported. Reason: Cannot change column type INPLACE. Try ALGORITHM=COPY.

-- 失败：全文索引是 inplace 但非 online
ALTER TABLE ddl_t ADD FULLTEXT KEY ft_pad (pad), ALGORITHM = INPLACE, LOCK = NONE;
ERROR 1846 (0A000): LOCK=NONE is not supported. Reason: Fulltext index creation requires a lock. Try LOCK=SHARED.

          🔑 INSTANT 只覆盖"元数据能表达"的变更：加列、删列、改默认值、改列名。加索引永远没有 INSTANT——索引必须真的写进每一个数据页，只能 INPLACE。

          ⚠️ 一个连带现象（8.0.46 实测）：表上已有 FULLTEXT 索引之后，再做 ALTER TABLE ... ENGINE=InnoDB, ALGORITHM=INPLACE 会被拒，报 Reason: InnoDB presently supports one FULLTEXT index creation at a time. Try ALGORITHM=COPY.——想重建这张表，要么先删全文索引，要么接受 COPY 的锁写。

          选算法的判定顺序

          你的操作 能选到的算法 该带什么子句
          加/删列、改默认值、改列名 INSTANT 只写 ALGORITHM=INSTANT，不要带 LOCK
          加/删二级索引、（多数）重建表 INPLACE ALGORITHM=INPLACE, LOCK=NONE
          改列类型/字符集、加全文/空间索引 COPY（全文索引可 LOCK=SHARED） 显式写 ALGORITHM=COPY，在低峰做
          不确定 先 ALGORITHM=INPLACE, LOCK=NONE 试，报 1846 就知道要降级 —

          让 MySQL 自己降级很危险：不写 ALGORITHM 时，它会在 INSTANT → INPLACE → COPY 之间自动选，你以为只是改个字符集，它可能已经在拷贝整张表并锁写。把算法和锁级别写死，是让 DDL 可预期的最低成本。

          DDL 与 MDL 排队的关系（一条 DDL 等写锁、把后面所有读写拖下水）在 44.11 锁 里是主场，这里只留一句：ALGORITHM=INPLACE 治的是"拷表"，治不了"MDL 排队"。

          生产落地：删历史数据/瘦表的安全姿势

          完整脚本在 tools/examples/44.27-mysql-space/，bash code/run.sh 可复现下面每条输出。

          第一步：量体。 先判断"该不该重建"，别凭感觉：

          -- 表空间真实字节数与区数（8.0）
SELECT name, file_size, ROUND(file_size/16384) AS pages
FROM information_schema.innodb_tablespaces
WHERE name = 'sp/t';

-- 逻辑大小与整块空闲区（注意：data_free 不含页内空洞）
SELECT table_rows,
       ROUND(data_length/1024/1024, 2)  AS data_mb,
       ROUND(index_length/1024/1024, 2) AS idx_mb,
       ROUND(data_free/1024/1024, 2)    AS free_mb
FROM information_schema.tables
WHERE table_schema = 'sp' AND table_name = 't';

          第二步：选再造方式。 原生 DDL 只有一种"半在线"能力（INPLACE 仍要拷表、占双份空间），大表在业务时段做重建要换工具：

          方式 原理 适用 代价
          原生 ALTER ... ALGORITHM=INPLACE, LOCK=NONE 重建 + row log 小表、低峰、能接受双份空间 占接近一张表空间，结束瞬间切换
          gh-ost 读 binlog 追增量，无触发器 大表在线改结构 需要额外主机/空间，切换需切换动作
          pt-online-schema-change 触发器同步增量 大表在线改结构 触发器带来额外写放大
          备库先做再切换 在只读备库执行，切换后补做旧主 有主从、能接受切换 需要一次主从切换

          第三步：验证与回滚。 重建的验证点是"文件变小 + 行数一致 + 统计信息刷新"：

          mysql> SELECT name, file_size, ROUND(file_size/16384) AS pages
    -> FROM information_schema.innodb_tablespaces WHERE name='sp/t';
+------+-----------+-------+
| name | file_size | pages |
+------+-----------+-------+
| sp/t |   7340032 |   448 |     ← 重建前 10485760 / 640 页
+------+-----------+-------+

          ⚠️ 重建不可回滚。DROP COLUMN 之后数据就没了（INSTANT 删列的文件空间不立即归还），ENGINE=InnoDB 重建之后旧文件被删除。可退的做法只有三条：先在备库做、先做全量备份、用 gh-ost/pt-osc 的重命名切换留退路。

          分区表：Server 层一张表，引擎层 N 张表

          本节要点

          分区表的价值只有一个：把"删历史数据"从 DELETE 换成 DROP PARTITION（删文件）；它不提升点查性能、不解决单机容量，还带来"首次访问打开所有分区"和"全表共用一个 MDL 锁"两个绕不开的代价。

          按 RANGE(YEAR(ftime)) 建一张四分区表，磁盘上就是四个独立表空间文件：

          -rw-r----- 1 mysql mysql 131072 pt#p#p2023.ibd
-rw-r----- 1 mysql mysql 131072 pt#p#p2024.ibd
-rw-r----- 1 mysql mysql 131072 pt#p#p2025.ibd
-rw-r----- 1 mysql mysql 131072 pt#p#pmax.ibd

          每个分区是一个独立的 .ibd，也就是一张独立的"引擎表"。这句话的两层含义决定了一切：

          视角 看到什么 后果
          Server 层 1 张表 pt 1 个 MDL 锁：任何分区的 DDL 都堵住整表
          引擎层 4 张表 p2023/p2024/p2025/pmax 分区裁剪、分区级表锁/间隙锁、可单独 DROP 文件

          原文用间隙锁和 MyISAM 表锁两个实验证明"引擎层是 N 张表"：在 p2018 上加的间隙锁管不到 p2019 的插入（因为 2017-4-1 的下一个记录是该分区的 supremum，不是 2018-4-1），MyISAM 的表锁也只锁住落在那个分区的语句。反过来说，server 层的 MDL 是整表一份——ALTER 一个分区，整张表的所有查询都排队，这是 DBA 常说"分区表做 DDL 影响更大"的根因。

          分区键的硬约束与取舍

          主键、唯一键必须包含分区字段，否则建表就报错。这就引出原文那道题：一张按 YEAR(ftime) 分区、又想要自增 id 的表，主键只有两种写法：

          主键写法 二级索引 评价
          PRIMARY KEY (ftime, id) + KEY id (id) 1 个 推荐：查询几乎都带 ftime，可复用前缀，少一个索引
          PRIMARY KEY (id, ftime) + KEY id (ftime) 1 个 也能用，但 ftime 前缀用不上，索引更宽

          本机实测第一种：

          CREATE TABLE pt2 (
  id    INT NOT NULL AUTO_INCREMENT,
  ftime DATETIME NOT NULL,
  c     INT,
  PRIMARY KEY (ftime, id),
  KEY id (id)
) ENGINE=InnoDB
PARTITION BY RANGE (YEAR(ftime)) (...);

          注意 InnoDB 要求"至少有一个索引以自增字段打头"，所以 (ftime, id) 之外还得补一个 KEY id (id)——这个额外索引就是分区键约束的隐性成本。

          分区类型与裁剪：条件必须直接落在分区列上

          分区类型 表达式示例 适用 注意
          RANGE RANGE (YEAR(ftime)) 时间归档、冷热分离 需要 MAXVALUE 兜底分区
          RANGE COLUMNS RANGE COLUMNS(ftime) 直接按列范围，不走函数 支持多列、字符串/日期
          LIST LIST (store_id) 枚举值（地区、租户组） 值不在列表里就插不进去
          HASH / KEY HASH (id) / KEY (id) 打散写热点 无法按范围裁剪、无法 DROP 单分区归档

          裁剪能力实测（EXPLAIN 的 partitions 列）：

          查询条件 partitions 列 说明
          ftime = '2024-04-01' p2024 等值 → 裁到 1 个
          ftime BETWEEN '2024-01-01' AND '2024-12-31' p2024 范围 → 1 个
          ftime >= '2024-04-01' p2024,p2025,pmax 开区间 → 3 个
          ftime IN ('2023-06-01','2025-06-01') p2023,p2025 离散值 → 2 个
          c = 5（不带分区键） p2023,p2024,p2025,pmax 全扫，比不分区更慢
          YEAR(ftime) = 2024 p2023,p2024,p2025,pmax 列上包了函数，实测不裁剪

          🔑 裁剪的前提是 WHERE 条件直接作用在分区列上。分区表达式是 YEAR(ftime)，但写成 WHERE YEAR(ftime)=2024 反而拿不到裁剪（8.0.46 实测走全部分区）——想裁剪就写成对列的范围比较：ftime >= '2024-01-01' AND ftime < '2025-01-01'。

          💡 EXPLAIN PARTITIONS 语法在 8.0 已废弃，直接用 EXPLAIN 看 partitions 列即可。执行计划各字段的含义在 44.9 执行计划与慢查询。

          分区表的两个固有代价

          代价 机制 触发条件
          首次访问打开所有分区 分区表第一次被访问要把所有分区文件打开 分区数多 + open_files_limit 小
          全表共用一个 MDL 锁 server 层认为是一张表 任何分区上的 DDL

          原文的报错场景是 MyISAM 分区表：分区数超过 1000、open_files_limit 用默认 1024，一条只需要访问一个分区的 INSERT 直接报"打开文件过多"。原因是 MyISAM 用的是通用分区策略（generic partitioning，每次访问由 server 层控制，文件管理很粗糙）；InnoDB 从 5.7.9 起用本地分区策略（native partitioning，由 InnoDB 自己管理分区打开行为），打开文件数超过 innodb_open_files 时会淘汰旧句柄，所以不会撞 open_files_limit——但首次访问仍然要打开所有分区。

          版本线：5.7.17 起 MyISAM 分区表被标记为弃用（deprecated）；8.0 起不允许创建 MyISAM 分区表，只允许已经实现本地分区策略的引擎（InnoDB、NDB）。8.0 的分区数上限是 8192（官方文档，原文未涉及）。

          ⚠️ 分区不是越细越好，也不要提前预留太多。见过按天分区、预先建 10 年（3650 个分区）的表，首次访问要打开 3650 个文件，性能自然差。正确做法：按月/按年分区，用到之前再建（每年年底建下一年 12 个），没有数据的历史分区及时 DROP。另外，单表或单分区一千万行、没有特别大的索引，对现在的硬件就是小表，不需要为了"行数多"分区。

          什么时候用、什么时候不用

          场景 选择 理由
          日志/流水表，按时间删历史 ✅ 分区 + DROP PARTITION 删文件（实测 0.265s 删掉 365 行分区并回收文件），不写 undo/redo 行
          冷热分离，老数据放低速盘 ✅ 分区（可单独指定表空间） 分区是独立 .ibd，可搬到不同磁盘
          单表太大想"提性能" ❌ 先看索引 分区不替代索引，查询不带分区键要扫全部分区
          需要跨分区 join / 聚合 ❌ 慎用 跨分区查询要打开多个分区取数据
          想靠分区解决单机容量 ❌ 这要分库分表 分区还是单机；见 44.14 分库分表
          表要做频繁 DDL ❌ 慎用 所有分区共用一个 MDL 锁，DDL 影响整表

          实测 DROP PARTITION 的效果：

          -- 删之前 1095 行，四个分区文件各 131072 字节
ALTER TABLE pt DROP PARTITION p2023;
-- 0.265s 返回
+------------+     +----------------+------------+
| rows_after |     | PARTITION_NAME | TABLE_ROWS |
+------------+     +----------------+------------+
|        730 |     | p2024          |        366 |
+------------+     | p2025          |        364 |
                   | pmax           |          0 |
                   +----------------+------------+

          p2023 对应的 pt#p#p2023.ibd 文件直接消失，行数从 1095 掉到 730，没有逐行删除、没有 undo 膨胀、没有长事务。这就是分区表唯一无可替代的收益。

          🔑 分区表只买"删历史"这一件事：单机容量、跨分区查询、DDL 成本它都不解决。如果团队已经有成熟的分库分表中间件、业务分表对开发没有额外复杂度，用业务分表更直观——那是 44.14 分库分表 的主场。

          复制一张表：四条路，先看约束再看速度

          本节要点

          复制表有四条路：CREATE TABLE LIKE + INSERT ... SELECT（同实例最快）、mysqldump（逻辑、可跨版本、可过滤）、SELECT ... INTO OUTFILE + LOAD DATA（最快逻辑导出、只能导数据）、可传输表空间（物理拷贝、最快、但要求同版本同页大小同字符集）——选型先看约束，速度是最后一位。

          路线 层次 5 万行实测（两轮） 带表结构 跨实例/跨版本 硬约束
          CREATE TABLE LIKE + INSERT ... SELECT 逻辑，SQL 内 1.7s / 2.7s 需另建表 同实例；跨实例要 FEDERATED/中间件 大表 INSERT SELECT 要控制扫描与锁范围
          SELECT ... INTO OUTFILE + LOAD DATA 逻辑，文件 导出 0.6–0.9s + 导入 2.6–4.8s 不带，要单独导结构 可跨版本 服务端路径、secure_file_priv、只能整表导数据
          mysqldump \| mysql 逻辑，SQL 文本 3.1s / 8.2s 带（去掉 --no-create-info） 可跨版本 文本体积大，导入逐条执行
          可传输表空间 物理，文件 1.7s / 2.8s 带（CREATE TABLE LIKE） 必须同版本、同页大小、同字符集 只对独立表空间、必须全表、要登录主机

          🔑 5 万行（表空间 17MB）量级上四条路都在 2–8 秒，差异主要是常数开销；真正拉开差距的是数据量——物理拷贝省掉"读出来解析再写回去"的全过程，大表时差距按数量级放大（原文结论，本节未复现 TB 级）。所以选型顺序是：约束（跨版本？要部分数据？能登主机？）→ 再比速度。

          mysqldump：参数决定它锁不锁表

          mysqldump -h127.0.0.1 -P33102 -uroot --protocol=TCP \
  --single-transaction --no-create-info --skip-disable-keys \
  --add-locks=0 --set-gtid-purged=off sp src \
  | sed 's/INSERT INTO `src`/INSERT INTO `dst`/' | mysql -h127.0.0.1 -P33102 -uroot sp
          参数 作用 不加会怎样
          --single-transaction 用 START TRANSACTION WITH CONSISTENT SNAPSHOT 拿一致性快照，不锁表 导出期间锁表或数据不一致
          --add-locks=0 输出里不加 LOCK TABLES t WRITE 导入时反复锁表
          --no-create-info 只导数据，不导建表语句 目标表已存在时建表语句报错
          --set-gtid-purged=off 不输出 GTID 信息 导入时报 GTID 相关错误
          --skip-disable-keys 不输出 ALTER TABLE ... DISABLE KEYS 往同一实例回灌时会自锁（见下）

          两个真跑出来的坑：

          ⚠️ 坑一：mysqldump 默认输出的 ALTER TABLE ... DISABLE KEYS 会和自己的快照互锁。 导出连接持有 src 的 MDL 读锁（一致性快照），同一个 dump 文件里的 ALTER TABLE src DISABLE KEYS 要 MDL 写锁，于是自己等自己。实测卡了 6 分钟以上，SHOW PROCESSLIST 里状态是 Waiting for table metadata lock。加 --skip-disable-keys 解决。

          ⚠️ 坑二：--no-create-info 导出的语句是 INSERT INTO `src`，不带库名。 直接灌进目标库，插的还是 src，报 Duplicate entry '1' for key 'src.PRIMARY'。要么用 sed 把表名换掉，要么导到另一个库再 RENAME TABLE。

          OUTFILE / LOAD DATA：最快的逻辑导出，代价是一堆限制

          -- 文件生成在**服务端**，不是客户端
SELECT * FROM sp.src INTO OUTFILE '/var/lib/mysql-files/src.csv';
LOAD DATA INFILE '/var/lib/mysql-files/src.csv' INTO TABLE sp.dst_csv;

          原文点到的四条注意，条条会踩：

          限制 具体表现
          文件在服务端 客户端与服务器不同机时，客户端目录下不会有文件
          secure_file_priv 限制目录 本机实测 = /var/lib/mysql-files/，只能写这个目录或子目录
          不能覆盖同名文件 文件已存在直接报错，先删
          字段里的换行/制表符 输出时加 \ 转义，所以"一行数据"不一定对应"文本一行"

          secure_file_priv 三态：empty = 不限制（不安全）、指定路径 = 只能放该目录及子目录、NULL = 禁止在本实例执行 SELECT ... INTO OUTFILE。

          LOAD DATA 在 binlog_format=statement 下有个绕不开的问题：文件只在主库主机上，把语句原文写进 binlog，备库执行时找不到文件，主备同步就断了。所以完整流程是——主库把 csv 内容直接写进 binlog，再写一条带 local 的 load data local infile '/tmp/SQL_LOAD_MB-1-0'；备库 apply 时先把 binlog 里的文件内容还原到本地临时文件，再执行。加 local 的含义是"读客户端本地文件"，这样不受备库 secure_file_priv 的影响。

          💡 SELECT ... INTO OUTFILE 不生成表结构，要单独导；mysqldump --tab=<dir> 可以同时产出建表语句（t.sql）和 CSV 数据（t.txt）。

          可传输表空间：物理拷贝，六步

          直接 cp t.ibd 是不行的——InnoDB 表除了 .ibd，还要在数据字典里登记。5.6 引入的可传输表空间（transportable tablespace）才是合法的物理拷贝：

          -- 1. 建一张同结构的空表
CREATE TABLE r LIKE t;
-- 2. 丢掉它自己的表空间（r.ibd 被删除）
ALTER TABLE r DISCARD TABLESPACE;
-- 3. 让源表进入只读导出态，库目录下生成 t.cfg
FLUSH TABLE t FOR EXPORT;
-- 4. 在库目录里拷文件（注意属主，MySQL 进程要能读写）
--    cp t.cfg r.cfg; cp t.ibd r.ibd; chown mysql:mysql r.cfg r.ibd
UNLOCK TABLES;                                  -- 5. 解锁，t.cfg 被删除
ALTER TABLE r IMPORT TABLESPACE;                -- 6. 把 r.ibd 认成 r 的表空间

          本机实测（5 万行 / 17MB）：六步 1.7–2.8s 跑完，dst_ts.ibd 与 src.ibd 字节数完全相同（17,825,792）。四个必须知道的点：

          注意点 说明
          导出期间源表只读 FLUSH TABLE ... FOR EXPORT 之后到 UNLOCK TABLES 之前，t 整表只读
          IMPORT 要改表空间 ID 每个数据页里都存着表空间 ID，大文件要逐页改，TB 级也要跑一段时间（但比逻辑导入短得多）
          .cfg 不会自动删 实测 import 之后 dst_ts.cfg（843 字节）仍留在库目录
          四条硬限制 必须同版本、同 innodb_page_size、同字符集；只对独立表空间（file_per_table=ON）有效；必须整表，不能只拷部分数据；要能登录数据库主机

          🔑 误删表恢复最快的路就是物理拷贝：从备份恢复出误删前的临时库，再用可传输表空间把那张表搬回生产库——省掉"全库逻辑导入"的解析开销。前提是版本、页大小、字符集一致，且表是独立表空间。

          反模式

          反模式 后果
          用 DELETE 删历史数据"省空间" 空间一个字节不还，空洞越攒越多，ibdata1 或 .ibd 只涨不缩；还要写 undo/redo/binlog
          把 DATA_FREE 当碎片率 它只统计整块空闲的区，页内空洞完全不计入；实测删一半前后都是 4.00MB，看不出任何变化
          在业务高峰做 ALTER TABLE ... ENGINE=InnoDB 且不写算法 优化器自行降级到 COPY，整表锁写；还要额外一份接近表大小的 tmp_file 空间
          1TB 表、磁盘只剩 1.2TB，做 inplace 重建 tmp_file 也要空间，重建到一半磁盘满，DDL 失败回滚
          给 ALGORITHM=INSTANT 加 LOCK=NONE 直接报 ERROR 1221，DDL 不执行；INSTANT 根本不需要锁子句
          预先按天分区建十年（3650 个分区） 首次访问要打开全部分区，性能与文件句柄都吃紧；分区不是越细越好
          WHERE YEAR(ftime)=2024 指望分区裁剪 列上包函数，实测走全部分区，比不分区更慢
          用分区表替代索引 / 替代分库分表 查询不带分区键就扫全部分区；单机容量与跨分区查询都不解决
          直接 cp 表 .ibd 到另一个库 数据字典里没有登记，系统不识别；必须走 DISCARD / IMPORT TABLESPACE
          mysqldump 回灌同实例不加 --skip-disable-keys 导出快照的 MDL 读锁与自己的 DISABLE KEYS 互锁，实测卡死 6 分钟以上

          自检

          Q1 一张 2000 万行的表删掉 90% 的行，information_schema.TABLES 里 DATA_LENGTH 和 DATA_FREE 都几乎没变，.ibd 也没缩。是统计信息没刷新，还是别的？

          ▸ 答案：都不是统计信息的问题。DELETE 只把记录和页标成"可复用"，页仍然分配在文件里，所以 DATA_LENGTH（已分配页的字节数）不变；DATA_FREE 只统计整块空闲的区，页内空洞不进这个数，所以也不变。ANALYZE TABLE 只会重算行数估算，不动文件。要缩必须重建表（ALTER TABLE ... ENGINE=InnoDB 或 OPTIMIZE TABLE），重建后实测 10485760 → 7340032 字节。判据看 information_schema.INNODB_TABLESPACES.FILE_SIZE 或 ls -l 那个 .ibd，不看 DATA_*。

          Q2 同一张表，ALTER TABLE t ADD COLUMN c INT 用时 0.01s，ALTER TABLE t ADD INDEX(c) 用时 40s。都加了 ALGORITHM=INPLACE 的话，为什么差这么多？

          ▸ 答案：因为加列根本没走 INPLACE。8.0.12 起 ADD COLUMN 支持 ALGORITHM=INSTANT，只改数据字典、不碰数据页，所以是毫秒级；ADD INDEX 没有 INSTANT——索引必须写进每一个数据页，只能 INPLACE（重建索引 + row log）。实测 ADD INDEX ... ALGORITHM=INSTANT 直接报 ERROR 1845: ALGORITHM=INSTANT is not supported for this operation。所以"加字段很快"不能推广成"加索引也很快"，后者与表大小成正比。

          Q3 一张按 RANGE(YEAR(ftime)) 分区的表，WHERE ftime='2024-04-01' 只扫 p2024，改成 WHERE YEAR(ftime)=2024 却扫了全部分区。分区表达式明明就是 YEAR(ftime)，为什么反而不裁剪？

          ▸ 答案：裁剪是"用 WHERE 条件去推分区范围"，要求条件直接作用在分区列上、能映射成列上的区间。ftime='2024-04-01'、ftime BETWEEN ...、ftime IN (...) 都能映射；YEAR(ftime)=2024 是把列包进函数后再比较，优化器不做反向求解，只能全分区扫描（8.0.46 实测 partitions 列为全部四个分区）。写法上等价不代表执行上等价——改成 ftime >= '2024-01-01' AND ftime < '2025-01-01' 就能裁到一个分区。

          Q4 一张表的 .ibd 是 17MB，information_schema.TABLES 里 data_length + index_length 只有 9MB，差了 8MB。是统计不准吗？这 8MB 能不能要回来？

          ▸ 答案：不是统计不准，是口径不同。data_length + index_length 算的是"正在存数据的页"，FILE_SIZE 是"文件实际占的字节"，差额主要就是空闲的区与页（data_free）。这 8MB 可以通过重建表要回来一部分：实测把一张 5 万行、按主键顺序插入、从未删除的表重建，17MB → 16MB（-5.9%），因为重建会把页按约 90% 的利用率重排——如果表本来就很紧，重建只能拿回很少一点，甚至因为留 10% 给 UPDATE 而略微变大（原文的 1TB → 1.01TB 就是这个原因）。

          Q5 在线 DDL 为什么普遍走"建临时表 → 增量同步 → rename 切换"，而不是直接改原表结构？判断一次 DDL 会不会锁表，看哪两个观测点？

          ▸ 答案：因为 rename 是原子的元数据操作，切换瞬间对业务是"要么全旧、要么全新"，失败还能回滚（临时表还在）。直接改原表结构需要就地重写页面，中途失败会留下半新半旧的结构，无法回滚。两个观测点：① performance_schema.metadata_locks 里有没有长时间的 EXCLUSIVE MDL（有就是被长事务挡住，会连带阻塞后续查询）；② SHOW PROCESSLIST 的 State 是否长期停在 altering table / copy to tmp table（处于 copy 算法就是全表重写，不是 in-place）。
