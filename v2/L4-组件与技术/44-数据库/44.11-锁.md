# 44.11 锁 (行锁 / 间隙锁 / 意向锁 / 死锁)

## 一句话

> 三种锁各管一件事：**行锁防丢失更新、间隙锁防幻读、意向锁让表级操作不必逐行检查**；而死锁不是 bug，是“多个事务以不同顺序加锁”的必然结果——只能靠等待图检测并回滚一个事务来打断。

**来源**：行锁/间隙锁、死锁与 DDL 案例来自丁奇《MySQL 实战 45 讲》（极客时间，2019）；两阶段锁与热点行来自第 07 讲，全局锁与 MDL 来自第 06 讲，幻读与间隙锁来自第 20 讲，加锁规则逐例推演来自第 21 讲，动态加锁与死锁日志判读来自第 30 讲，insert 的锁来自第 40 讲；本节代码、实测与推演为本机 MySQL 8.0.46 补充（端口 33108 / 33199）。

## 锁粒度：行锁、页锁、表锁与锁升级

“悲观锁/乐观锁”是两种**并发控制思想**，行/页/表锁是**粒度**，两者正交，不能混着背。

| 粒度 | 并发度 | 开销 | 死锁风险 | 典型引擎 |
|---|---|---|---|---|
| **行锁** | 高 | 大（每行锁对象） | 高 | InnoDB、Oracle |
| **页锁** | 中 | 中 | 中 | BDB |
| **表锁** | 低 | 小 | 低（MyISAM 一次拿全） | MyISAM |

InnoDB/Oracle 支持行锁 + 表锁；MyISAM **只支持表锁**；SQL Server 三种都支持。每个层级的锁数量有上限（锁占内存），超过阈值时数据库会把多个细粒度锁**升级**成一个大粒度锁——用并发度换锁空间。行锁升表锁后，其他事务基本只能排队。

| 写法 | 语义 | 代价 |
|---|---|---|
| `LOCK TABLE t READ` | 表级 S 锁：整表只读 | 任何 `UPDATE` 报 **ERROR 1099**，直到 `UNLOCK TABLES` |
| `LOCK TABLE t WRITE` | 表级 X 锁：别人读写都等 | 并发骤降，只适合批量维护 |
| `SELECT ... LOCK IN SHARE MODE`（8.0 推荐 `FOR SHARE`） | 行级 S 锁 | 两个事务各持同一行 S 锁、再都想升级 X，会互相等待 |
| `SELECT ... FOR UPDATE` | 行级 X 锁 | 锁竞争、死锁率上升；要固定加锁顺序 |
| `UPDATE ... SET version=version+1 WHERE id=? AND version=?` | 乐观锁：提交时 CAS | 影响行数为 0 要重读重试；防不了程序外的直接写 |

> 🔑 悲观锁把排它性交给数据库，适合写多、冲突重；乐观锁把冲突检测推迟到提交，适合读多写少。**乐观锁不是“没有锁”**：它把锁换成了版本号 + 影响行数检查，检查漏了就是静默丢失更新（[25.1 乐观并发与悲观并发](../../L1-分布式原理/25-并发、冲突与幂等/25.1-乐观并发与悲观并发.md)）。

## 六种锁，一张兼容表

| 锁 | 加在什么上 | 解决什么 | 与谁冲突 |
|---|---|---|---|
| 共享锁 S | 行 | 读时阻止别人改 | X |
| 排他锁 X | 行 | 写时阻止别人读/写 | S、X |
| 意向共享 IS | 表 | 声明“我要在某行加 S” | IX |
| 意向排他 IX | 表 | 声明“我要在某行加 X” | S、X、IS |
| **间隙锁 GAP** | 索引区间 | 阻止区间内插入（防幻读） | 插入意向锁 |
| **Next-Key** | 记录 + 前面的间隙 | 行锁 + 间隙锁的组合 | 同上 |

|  | S | X | IS | IX |
|---|---|---|---|---|
| **S** | ✅ | ❌ | ✅ | ❌ |
| **X** | ❌ | ❌ | ❌ | ❌ |
| **IS** | ✅ | ❌ | ✅ | ✅ |
| **IX** | ❌ | ❌ | ✅ | ✅ |

> 🔑 意向锁的意义：如果没有它，一个事务要加**表锁**，必须扫描全表每一行看有没有行锁；有了 IS/IX，只需看表上有没有冲突的意向锁——**用一次表级检查替代 O(n) 行扫描**。

## 加锁规则：两个原则、两个优化、一个 bug

「改一行却锁了这么多」不是玄学：InnoDB 的加锁范围可以从五条规则推出来。前提是 RR 隔离级别。

> ⚠️ 规则边界：这套总结来自《MySQL 实战 45 讲》作者对源码的归纳，适用范围是 5.x ≤ 5.7.24、8.0 ≤ 8.0.13。更新的小版本可能改策略——判断前先用 `performance_schema.data_locks` 实测，别背规则下结论。

| 编号 | 规则 | 含义 |
|---|---|---|
| 原则 1 | 加锁的基本单位是 **next-key lock** | 前开后闭区间 `(a, b]`，即「行锁 + 前面的间隙锁」 |
| 原则 2 | **访问到的对象才加锁** | 没被扫描到的索引行不加锁，所以「走不走索引」决定锁范围 |
| 优化 1 | 唯一索引上的**等值**查询 | next-key lock 退化成**行锁** |
| 优化 2 | 等值查询向右遍历，最后一个值不满足条件 | next-key lock 退化成**间隙锁**（不锁那一行） |
| 一个 bug | 唯一索引上的**范围**查询 | 会一直扫到第一个不满足条件的行，多锁一段 |

用表 `t`（`id` 主键，`c` 有普通索引，值均为 `0,5,10,15,20,25`）走一遍：

| 语句 | 实际加锁 | 用到哪条规则 |
|---|---|---|
| `where id=7 for update`（7 不存在） | 间隙锁 `(5,10)` | 原则 1 圈出 `(5,10]`，优化 2 去掉 `id=10` 那行 |
| `where c=5 lock in share mode` | 索引 `c` 上 `(0,5]` 与 `(5,10)`；**主键无锁** | 非唯一索引要向右扫到 `c=10` 才停；覆盖索引不回表，所以主键不加锁 |
| `where id>=10 and id<11 for update` | 行锁 `id=10` + `(10,15]` | 首次等值定位走优化 1，向右按范围加锁 |
| `where c=10`（非唯一索引） | `(5,10]` + `(10,15]` | 非唯一索引**没有**优化 1，不会退化成行锁 |
| `where id>=10 and id<=15 for update` | 行锁 `id=10` + `(10,15]` + **`(15,20]`** | bug：扫到 `id=20` 才确认结束 |
| `delete from t where c=10 limit 2` | 到 `(c=10,id=30)` 为止 | `limit` 让遍历提前结束，锁范围随之缩小 |

两个能立刻用上的推论：

- **`limit` 能缩锁**：删除/更新时带 `limit`，既控条数也控锁范围。大批量操作要分批，不是「一条 SQL 更省事」。
- **`lock in share mode` + 覆盖索引锁不住主键**：上表第二行里，另一个会话 `update t set d=d+1 where c=5` 照样能执行——它要改的 `d` 不在索引 `c` 里，而主键上根本没锁。想用读锁阻止更新，查询列表里要带上索引外的字段（如 `select d from t where c=5 lock in share mode`），或者直接用 `for update`。

RC 下的两条差异值得记住：**没有间隙锁**（外键场景除外），并且语句执行完就释放「不满足条件」的行锁，不等事务提交。所以 RC 的锁范围更小、持锁更短——这是大量业务默认 RC 的真实原因，不只是「RC 性能好」。

### next-key lock 是两段加的，所以会死锁

案例八：会话 A `select * from t where c=5 lock in share mode`（持 `(5,10]` 与 `(10,15)`），会话 B `update t set d=d+1 where c=10` 进入等待，会话 A 再 `insert into t values(8,8,8)`——被 B 挡住，死锁，B 回滚。

原因：B 的 `next-key lock(5,10]` 分两步执行，**先加间隙锁 `(5,10)`（成功），再加 `c=10` 的行锁（被 A 挡住）**。于是 B 手里已握着 A 需要的间隙锁，A 又在等 B 需要的资源。

> 🔑 判断锁范围只看一件事：**这条语句扫到了哪些索引记录**。不是「改了几行」，也不是「有没有 `FOR UPDATE`」。没有索引 → 扫全表 → 锁全表，这条因果链没有例外。

## 代码：等待图 + 死锁检测 + 间隙锁

```go
package main

import (
	"fmt"
	"sort"
)

type lockMgr struct {
	holder  map[string]string   // resource -> txn（简化为单持有者）
	waitFor map[string]string   // txn -> 它等待的 txn
	held    map[string][]string // txn -> 持有的资源
}

func newLockMgr() *lockMgr {
	return &lockMgr{holder: map[string]string{}, waitFor: map[string]string{}, held: map[string][]string{}}
}

// acquire 返回 "ok" / "wait" / "deadlock"
func (m *lockMgr) acquire(txn, res string) string {
	if h, ok := m.holder[res]; ok {
		if h == txn {
			return "ok(重入)"
		}
		m.waitFor[txn] = h
		if m.detectCycle(txn) {
			delete(m.waitFor, txn)
			return "deadlock"
		}
		return fmt.Sprintf("wait(%s)", h)
	}
	m.holder[res] = txn
	m.held[txn] = append(m.held[txn], res)
	return "ok"
}

// 从 txn 出发沿 waitFor 走，看能否回到自己
func (m *lockMgr) detectCycle(start string) bool {
	seen := map[string]bool{}
	cur := start
	for {
		next, ok := m.waitFor[cur]
		if !ok {
			return false
		}
		if next == start {
			return true
		}
		if seen[next] {
			return false
		}
		seen[next] = true
		cur = next
	}
}

func (m *lockMgr) release(txn string) {
	for _, r := range m.held[txn] {
		if m.holder[r] == txn {
			delete(m.holder, r)
		}
	}
	delete(m.held, txn)
	// 清理那些“在等这个事务”的等待关系
	for waiter, holder := range m.waitFor {
		if holder == txn {
			delete(m.waitFor, waiter)
		}
	}
}

func main() {
	m := newLockMgr()
	fmt.Println("=== 加锁序列（两个事务以相反顺序加锁）===")
	steps := []struct{ txn, res string }{
		{"T1", "row:1"}, {"T2", "row:2"},
		{"T1", "row:2"}, {"T2", "row:1"},
	}
	for _, s := range steps {
		r := m.acquire(s.txn, s.res)
		fmt.Printf("%s 请求 X(%s) -> %s\n", s.txn, s.res, r)
		if r == "deadlock" {
			fmt.Println("  检测到环：T1 -> T2 -> T1，选择回滚 T2（新加入等待环的事务）")
			m.release("T2")
			fmt.Printf("  T2 回滚后，T1 重试 X(row:2) -> %s\n", m.acquire("T1", "row:2"))
		}
	}

	fmt.Println("\n=== 间隙锁：阻止区间内插入 ===")
	// 索引上有 10、20、30；事务对 (10,30) 加间隙锁
	gaps := []struct {
		lo, hi int
		holder string
	}{{10, 30, "T3"}}
	tryInsert := func(v int) {
		for _, g := range gaps {
			if v > g.lo && v < g.hi {
				fmt.Printf("插入 %d -> 阻塞（落在 T3 的间隙锁 (%d,%d) 内）\n", v, g.lo, g.hi)
				return
			}
		}
		fmt.Printf("插入 %d -> 成功（不在任何间隙锁内）\n", v)
	}
	tryInsert(18)
	tryInsert(35)

	// 统计每个事务持有的锁（按资源名排序，输出稳定）
	fmt.Println("\n=== 当前锁持有情况 ===")
	for txn, rs := range m.held {
		sort.Strings(rs)
		fmt.Printf("%s: %v\n", txn, rs)
	}
}
```

本机实测（macOS，Apple M1，Go 1.27）：

```
=== 加锁序列（两个事务以相反顺序加锁）===
T1 请求 X(row:1) -> ok
T2 请求 X(row:2) -> ok
T1 请求 X(row:2) -> wait(T2)
T2 请求 X(row:1) -> deadlock
  检测到环：T1 -> T2 -> T1，选择回滚 T2（新加入等待环的事务）
  T2 回滚后，T1 重试 X(row:2) -> ok

=== 间隙锁：阻止区间内插入 ===
插入 18 -> 阻塞（落在 T3 的间隙锁 (10,30) 内）
插入 35 -> 成功（不在任何间隙锁内）

=== 当前锁持有情况 ===
T1: [row:1 row:2]
```

读数：

| 现象 | 含义 |
|---|---|
| T1 与 T2 各持一把锁、再互相请求 | 等待图出现环 `T1 → T2 → T1`，这就是死锁 |
| 检测到环后回滚 T2 | 数据库不会“等一等就好”，必须选一个牺牲者 |
| 插入 18 被阻塞 | 间隙锁锁的是“区间”，不是“已存在的行”——这正是防幻读的机制 |
| 插入 35 成功 | 落在间隙之外，不受影响 |

> ⚠️ 间隙锁的代价：它锁住的是**区间**，会阻塞所有落在区间内的插入（哪怕这些行与查询条件无关）。所以高并发写入的表要谨慎使用 `SELECT ... FOR UPDATE` + 范围条件，否则容易“锁住一大片”。

## 死锁的四个条件与三种解法

| 条件 | 含义 | 解法 |
|---|---|---|
| 互斥 | 资源不能共享 | 无法消除（写操作天然互斥） |
| 持有并等待 | 拿着 A 等 B | 一次性申请所有锁（或按固定顺序） |
| 不可抢占 | 不能强行拿走 | 超时回滚（`innodb_lock_wait_timeout`） |
| 循环等待 | 形成环 | **按固定顺序加锁**（最有效）、检测到环后回滚 |

> 🔑 工程上最有效的一条是“**固定加锁顺序**”：所有事务都按 `min(id), max(id)` 的顺序锁行，环就不可能形成。其次是“小事务”（锁持有时间短，碰撞概率低）与“走索引”（避免锁范围扩大到全表）。

## 全局锁与元数据锁：加个字段为什么能挂掉整库

不是所有锁都在行上。备份要「一致性视图」，DDL 要「表结构不被并发改」，这两件事用的是整库锁与表级锁——而**真正天天咬人的是 MDL**：它由系统自动加，事务不提交就不释放。

| 手段 | 锁住什么 | 阻塞谁 | 什么时候该用 |
|---|---|---|---|
| `FLUSH TABLES WITH READ LOCK`（FTWRL） | 全库只读 | 所有 DML、DDL、更新类事务的提交 | 只有**非事务引擎**（MyISAM）做逻辑备份时才不得不用 |
| `SET GLOBAL readonly=on` | 全库只读 | 写 | 不推荐：可能被业务用来判主备；客户端异常断开后不自动恢复 |
| `LOCK TABLES ... READ/WRITE` | 指定表 | 别的线程读写**且本线程只能操作列出的表** | 只在引擎没有行锁时才有意义 |
| MDL 读锁 / 写锁 | 表结构 | 读锁之间不互斥；读-写、写-写互斥 | 自动加，关不掉 |

### 备份：`--single-transaction` 与 FTWRL 二选一

不加锁直接备份，拿到的是「余额表已备份、课程表未备份」的中间态——逻辑上不一致。`mysqldump --single-transaction` 在导出前开一个 RR 事务拿一致性视图，靠 MVCC 让备份期间的写入照常进行。**它的前提是所有表都是事务引擎**：有 MyISAM 表就只能 FTWRL，整库只读。这也是 DBA 要求把 MyISAM 换成 InnoDB 的理由之一。

### MDL 事故：一条 DDL 把表变成不可读写

1. 会话 A `BEGIN; SELECT * FROM t;` → 持有 MDL 读锁；
2. 会话 B `SELECT * FROM t;` → 同为读锁，正常；
3. 会话 C `ALTER TABLE t ADD COLUMN c INT;` → 要 MDL **写锁**，被 A 挡住，进入等待；
4. 此后所有新查询都要申请 MDL 读锁，全部排在 C 后面 → 表彻底不可读写，客户端重试把线程数打满。

根因只有一句：**MDL 在语句开始时申请，语句结束不释放，等整个事务提交才释放**。所以一个「已经跑完 SELECT 但没提交」的长事务，就足以让 DDL 排队、让全表停摆。

### 安全加字段的四步

| 步骤 | 命令 | 作用 |
|---|---|---|
| ① 先查长事务 | `SELECT trx_id, trx_started, trx_mysql_thread_id FROM information_schema.innodb_trx ORDER BY trx_started;` | 有长事务先 kill 或等它结束 |
| ② DDL 带算法与锁级别 | `ALTER TABLE t ADD COLUMN c INT, ALGORITHM=INPLACE, LOCK=NONE;` | 避免拷贝表与锁表；**它治不了 MDL 排队** |
| ③ 拿不到锁就放弃 | `ALTER TABLE t NOWAIT ADD COLUMN c INT;`（MariaDB / AliSQL 分支支持 `WAIT n`） | 不让一条 DDL 卡住后续所有请求 |
| ④ 大表走影子表 | 在影子表上改结构、追平增量，最后 `RENAME` 切换 | 《MySQL 实战 45 讲》未覆盖，属于 DBA 侧做法（我的判断：超过千万行的表不要在主表上直接 DDL） |

> 🔑 `ALGORITHM=INPLACE` 不等于「不影响线上」。它解决的是**拷贝表**，不解决 **MDL 排队**：一条 DDL 在等写锁时，后面所有读请求都会跟着排队。

## 两阶段锁：行锁不是用完就还

一条 `update` 执行完，它加的行锁并不会立刻归还。InnoDB 的规则是：**行锁在需要的时候才加，但并不是不需要了就立刻释放，而要等到事务结束时才释放**——这就是两阶段锁协议。它把「加锁」和「放锁」分成两个阶段，中间整段时间都持有。

代价可以直接量化。本机 MySQL 8.0.46，两个会话对同一行 `update`：

| 事务 A 的语句顺序 | 事务 B（`update t set d=d+1 where id=5`）从发出到返回 |
|---|---|
| `update id=5` → `sleep(2)` → `update id=10` → `commit` | **2.37s**：A 一上来就锁住 id=5，B 排队到 A 提交 |
| `update id=10` → `sleep(2)` → `update id=5` → `commit` | **0.28s**：B 在 A 还没碰 id=5 时先拿到锁，A 反过来等 B |

同一组 SQL，只换了顺序，别人的等待时间差 8 倍。数字随机器负载漂（另一次运行是 1.84s / 0.07s），看比值不看绝对值；命令与原始输出见 [tools/examples/44.11-lock-lab](../../../tools/examples/44.11-lock-lab/README.md) 场景 7。

### 电影票：把最容易冲突的语句放最后

顾客 A 在影院 B 买票，一个事务三件事：① 扣 A 的余额；② 给影院 B 的余额加钱；③ 记一条交易日志。同时顾客 C 也在影院 B 买票——两个事务必然在语句 ② 上撞车，因为改的是同一个影院账户。

按两阶段锁，三条语句的锁都要到 `commit` 才放，所以顺序不改变「总持锁时长」，只改变**每一行各自被持有多久**。把 ② 放到最后（顺序 3、1、2：先写日志、再扣买家、最后加影院），影院余额这行的锁就只在整个事务的尾巴上待一小段，冲突窗口最小。

> 🔑 事务里的语句顺序是一个性能参数：**把最可能冲突、最影响并发的锁尽量往后放**，和「加索引」一样属于设计决定，不是代码风格。

### 热点行：影院预售把 CPU 打到 100%

影院做「低价预售一年电影票、只做一天」的活动，活动一开始数据库就挂了：CPU 接近 100%，每秒却执行不到 100 个事务。原因不是锁等待本身，而是**死锁检测**：每来一个被堵住的线程，都要判断「我的加入有没有形成环」，这是 O(n) 的活。1000 个并发线程同时更新同一行，检测量就是 100 万这个量级，检测结果还是「没有死锁」——CPU 全烧在证明「没死锁」上。

两个参数决定死锁的处置方式：`innodb_lock_wait_timeout` 默认 **50s**（等到超时），`innodb_deadlock_detect` 默认 **on**（主动检测并回滚一个）。超时不能调得太小，否则普通锁等待会被误杀；所以正常路径是主动检测，而主动检测在热点行上会反噬。

| 解法 | 做法 | 代价 / 边界 |
|---|---|---|
| 拆行 | 影院账户拆成 10 行，总额等于 10 行之和，每次随机挑一行加钱 | 冲突概率降到 1/10；余额可能减少（退票）时，要处理「部分行减到 0」 |
| 服务端排队 | 相同行的更新在进入引擎前排队（中间件或改 MySQL 源码） | 客户端做并发控制不可行：600 个客户端 × 5 并发 = 峰值 3000 |
| 合并请求 | 把短时间内的多次「加 N 元」在应用层合并成一次更新 | 只适用于可合并的累加语义；扣减、有先后依赖的写不能合并 |
| 关死锁检测 | 确认业务不会死锁时临时设 `innodb_deadlock_detect=off` | 业务有损：真出现死锁时只能等 50s 超时 |
| 原子更新代替「先查后改」 | 用 `update ... set n=n-1 where n>0`，不用 `select ... for update` 再算 | 只适合能用一条 SQL 表达约束的场景 |

前两条与最后一条的取舍：原文给的是「关检测 / 控并发 / 拆行」，后两条是工程上常用的补充。原子更新的价值在于把「读-判断-写」三步压成一条语句，锁窗口从「两次网络往返」缩到「一条语句」，同时天然不会丢更新。

> ⚠️ 拆分与合并都不是无损重构：拆分要处理余额减少与汇总查询，合并要保证语义可加。上线前先确认「这个热点行的写，是不是真的可拆、可并」。

## 幻读：锁声明被破坏，而不是读错了值

幻读的定义只有一句：**一个事务在前后两次查询同一个范围的时候，后一次查询看到了前一次查询没有看到的行**。注意两个限定：RR 下普通查询是快照读，看不到别的事务插入的行，所以幻读**只在当前读下出现**；而别人把某一行的值改成满足条件，导致第二次多查出一行，那叫不可重复读，**幻读专指新插入的行**。

| 现象 | 两次读的差异 | 谁造成的 | RR 快照读 | RR 当前读 |
|---|---|---|---|---|
| 脏读 | 读到未提交的值 | 别的事务未提交的写 | 不会 | 不会 |
| 不可重复读 | 同一行的值变了 | 别的事务 `update` 同一行并提交 | 不会 | 会（读最新值） |
| 幻读 | 同一个范围的行**数量**变了 | 别的事务 `insert` 并提交 | 不会 | **会** |

快照读为什么看不到新行，属于 MVCC 的可见性判定（[44.10 事务与隔离级别的实现](44.10-事务与隔离级别.md)）；这里只关心锁这一半：**当前读会看到新行，而锁没盖住新行**。

### 危害一：加锁语义被破坏

表 `t(id PK, c, d)`，会话 A 在 T1 执行 `begin; select * from t where d=5 for update;`，意图很明确：把「所有 d=5 的行」锁住。`d` 上没索引，只能全表扫，扫到的 6 行里只有 id=5 满足。原文用一个假设暴露问题：**假设 InnoDB 只给命中的 id=5 加行锁，其他被扫到的行不加锁**，会发生什么。

- T2：会话 B 执行 `update t set d=5 where id=0;`——id=0 原来 `d=0`，改完变成 `d=5`。这行没被 A 锁住（A 只锁了 id=5），B 成功。
- T3：A 再查一次，多出 id=0。
- T4：会话 C `insert into t values(1,1,5);` 又插进一行 `d=5`。
- T5：A 第三次查，三行：id=0、id=1、id=5。

A 声明「锁住所有 d=5 的行」，在这个假设下 B 和 C 却各塞了一行进来。这就是幻读的第一层危害：**锁的声明与实际效果不一致**，而应用层是按声明写逻辑的。

### 危害二：主库与 binlog 重放的结果不一样

在 T1 里再加一条 `update t set d=100 where d=5;`——A 认为自己锁住了所有 `d=5` 的行，所以放心地把它们改成 100。执行完，主库里的三行是：

| 行 | 主库最终值 | 原因 |
|---|---|---|
| id=0 | `(0,5,5)` | B 的 `update set c=5` 在 T2 提交，之后 A 的 `update set d=100 where d=5` 没锁到它 |
| id=1 | `(1,5,5)` | C 插入时 A 的锁已经加完，新行不在锁里 |
| id=5 | `(5,5,100)` | A 唯一真正锁住并改掉的行 |

而 binlog 里记录的语句序列是 B 的两条、C 的两条、A 的一条，按顺序重放（备库或克隆库）得到的是 `(0,5,100)`、`(1,5,100)`、`(5,5,100)`——三行全变 100。**主库与备库的数据不一致**，这是幻读的第二层危害，也是必须解决的真正原因。

### 为什么「把所有已存在的行都锁上」还不够

把扫描到的行全部加写锁，B 的 `update` 就会被挡住，id=0 的问题解决了。但 id=1 依然无解：T3 加锁的时候 id=1 还不存在，**不存在的记录加不上行锁**。行锁能锁住「行」，锁不住「行与行之间的空隙」，而插入恰恰发生在空隙里。这就是幻读被单独拿出来处理的原因。

解法是引入**间隙锁（Gap Lock）**：锁住两个索引值之间的空隙。6 行记录把主键索引切成 7 个间隙，执行 `select * from t for update` 会形成 7 个 next-key lock：`(-∞,0]`、`(0,5]`、`(5,10]`、`(10,15]`、`(15,20]`、`(20,25]`、`(25,+supremum]`。`supremum` 是 InnoDB 给每个索引加的一个不存在的最大值，因为 `+∞` 是开区间，得有个「右端点」才能让最后一个 next-key lock 也满足「前开后闭」。

间隙锁与行锁的冲突关系完全不同：**行锁跟行锁冲突，间隙锁只跟「往这个间隙里插入」冲突，间隙锁之间互不冲突**。两个事务可以对同一个间隙各加一把间隙锁（它们目标一致：保护这个间隙不许插入），然后都去插入——两个都在等对方，死锁。

```
session A: begin; select * from t where id=9 for update;  -- id=9 不存在 -> 间隙锁 (5,10)
session B: begin; select * from t where id=9 for update;  -- 同为间隙锁 (5,10)，不冲突，成功
session B: insert into t values(9,9,9);                   -- 等 A 的间隙锁
session A: insert into t values(9,9,9);                   -- 等 B 的间隙锁 -> 死锁
```

这个「先 `select ... for update` 判不存在、再 `insert`」的写法看起来很严格，实际是生产上间隙锁死锁的常见来源。要彻底绕开它，可以换 `insert ... on duplicate key update`（语义不同，见下节），或者把隔离级别降到 RC 并用 `binlog_format=row` 保证日志一致——RC 下没有间隙锁，代价是失去 RR 的范围可重复读保证。

> 🔑 幻读的锁解法是间隙锁，不是行锁：**行锁防「改」，间隙锁防「插」**。RC + `binlog_format=row` 是另一条路：没有间隙锁、并发更高，但同一事务的范围查询不再可重复。

## 加锁规则逐例推演：谁会被堵，只看一张表

规则本身只有五条，难的是把它套到具体 SQL 上。下面七例全部基于表 `t(id PK, c KEY, d)` 的 6 行数据 `(0,0,0)`…`(25,25,25)`，RR 隔离级别。看表的方法：「会被堵」的语句，其要加的锁与 A 已持有的锁冲突；「不会被堵」的语句，其要加的锁落在 A 的锁范围之外或落在间隙的开区间里。

| 案例 | 会话 A 的语句 | A 实际加的锁 | 会被堵 | 不会被堵 | 依据 |
|---|---|---|---|---|---|
| 1 | `where id=7 for update` | 主键间隙 `(5,10)` | `insert (8,8,8)` | `update ... where id=10` | 优化 2：`id=10` 不满足等值，退化为间隙 |
| 2 | `select id from t where c=5 lock in share mode` | 索引 `c` 上 `(0,5]` + 间隙 `(5,10)`；**主键无锁** | `insert (8,8,8)` | `update t set d=d+1 where c=5` | 覆盖索引不回表，原则 2 |
| 3 | `where id>=10 and id<11 for update` | 行锁 `id=10` + next-key `(10,15]` | `update ... where id=15`、`insert (12,12,12)` | `insert (8,8,8)` | 首次定位是等值 → 优化 1；之后是范围扫描 |
| 4 | `where c=10 for update` | 索引 `c` 上 `(5,10]` + `(10,15]` | `insert (8,8,8)`、`insert (12,12,12)` | `insert (4,4,4)` | 非唯一索引没有优化 1 |
| 5 | `where id>=10 and id<=15 for update` | 行锁 `id=10` + `(10,15]` + **`(15,20]`** | `update ... where id=20`、`insert (16,16,16)` | `insert (8,8,8)` | bug（≤5.7.24 / ≤8.0.13）：范围查询扫到第一个不满足的值才停 |
| 6 | `delete from t where c=10`（表里 `c=10` 有 id=10、id=30 两行） | 索引 `c` 上从 `(c=5,id=5)` 到 `(c=10,id=30)` 的区间，再带一段到 `(c=15,id=15)` 的间隙 | `insert (12,12,12)`、`delete ... where id=10` | `insert (4,4,4)` | 优化 2 收在 `(c=15,id=15)` |
| 7 | `delete from t where c=10 limit 2` | 到 `(c=10,id=30)` 为止，不含其后的间隙 | — | `insert (12,12,12)` | `limit 2` 让遍历提前结束 |

第 6、7 例的差别是本机实测过的：同样删 `c=10` 的两行，不带 `limit` 时 `data_locks` 有 **5** 条记录锁（多一条落在 `(c=10,id=30)` 之后、`(c=15,id=15)` 之前的间隙），带 `limit 2` 只有 **4** 条，插入 `c=12` 从被堵变成通过。

> ⚠️ 第 5 例的 bug 有版本边界：8.0.46 实测 `where id>=10 and id<=15 for update` 只加 `REC_NOT_GAP` 的 id=10 与 next-key `(10,15]`，**不再**多锁 `(15,20]`。规则来自 5.x ≤ 5.7.24 / 8.0 ≤ 8.0.13 的源码归纳，新版本可能已修；判据永远是 `data_locks` 的实测输出，不是背规则。

推演一条语句的锁，按三步走：

1. **看执行路径**：`EXPLAIN` 确认走哪个索引、扫到哪一行停。锁加在「扫描访问到的索引记录」上，走错索引就是另一套锁。
2. **圈范围再退化**：按原则 1 圈出 next-key lock，再按优化 1（唯一索引等值命中 → 行锁）或优化 2（等值向右最后一个不满足 → 间隙锁）收窄。
3. **对照冲突语句**：把「谁会被堵」翻译成「它要加的锁是否与已有锁冲突」，而不是「它改了几行」。

## 加锁是动态的：间隙由右边界定义

加锁不是对 SQL 文本做静态翻译，它发生在**语句执行过程中**，跟着索引树的搜索路径走。所以同一条 SQL，`order by` 的方向不同、`in` 列表的顺序不同、表里的行被删过，锁范围都会变。

### 不等号里的「等值查询」

```
begin;
select * from t where id>9 and id<12 order by id desc for update;
```

`where` 里全是大于小于，但过程里有等值查询：为了满足 `order by id desc`，优化器要先找到「第一个 `id<12` 的值」，这一步用树搜索定位 `id=12`——没找到，落进间隙 `(10,15)`。定位用的是等值方法，于是走优化 2，next-key 退化成间隙 `(10,15)`。然后向左遍历：扫到 `id=10` 加 `(5,10]`，扫到 `id=5` 加 `(0,5]`。

最终锁范围是 `(0,5]`、`(5,10]`、`(10,15)`——**`id=15` 这一行没有被加行锁**，只有它前面的间隙。本机 8.0.46 实测输出正是三行：`X 5`、`X 10`、`X,GAP 15`。

### `in` 列表按索引顺序逐个加，反过来就死锁

`select id from t where c in(5,20,10) lock in share mode` 会在索引 `c` 上依次锁 `c=5`、`c=10`、`c=20` 三处，每处都带右向间隙。加锁顺序是**按索引值从小到大**，不是按 `in` 里的书写顺序。

如果另一条语句写成 `select id from t where c in(5,20,10) order by c desc for update`，加锁顺序变成 `c=20` → `c=10` → `c=5`。两条语句锁同一组资源、顺序相反，并发执行就是死锁。原文的死锁现场显示：`lock in share mode` 持有 `c=5` 的记录锁、在等 `c=10`；`for update` 持有 `c=20`、`c=10`、在等 `c=5`。**InnoDB 回滚了持有资源更少、回滚成本更小的 `lock in share mode`**。

> 🔑 死锁的规避不是「别用 `for update`」，而是**对同一组资源保持相同的访问顺序**；`order by desc` 会把顺序整个倒过来。

### 锁日志怎么读

`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段只保留最后一次死锁现场，字段要按这张表翻译：

| 日志片段 | 含义 |
|---|---|
| `lock_mode X waiting` | 在等一把 next-key lock（间隙 + 行锁） |
| `lock_mode X locks rec but not gap` | 只持有行锁，没有间隙 |
| `lock_mode X locks gap before rec` | 只有间隙锁 |
| `lock_mode X locks gap before rec insert intention waiting` | 插入意向锁被间隙锁挡住，即 `insert` 在排队 |
| `n_fields 2` / `hex 0000000a` | 记录有 2 列，第一列是 `c`，值 0x0a = 10 |
| `WE ROLL BACK TRANSACTION (1)` | 被选为牺牲者的是第一个事务 |

### 行被删了，间隙会变大

「间隙」不是一个坐标，而是**由这个间隙右边的那个记录定义的**。`id=10` 存在时，间隙是 `(5,10)` 和 `(10,15)`；把 `id=10` 删掉，两个间隙合并成 `(5,15)`。原文的案例里，这个删除由**另一个事务**执行，而 A 只是执行过一条 `select`——它持有的锁范围却「变大」了，因为它锁的是「记录 15 前面的间隙」，边界随记录移动而移动。

同理，`update` 修改带索引的列，等价于「插入一条新记录 + 删除一条旧记录」：`update t set c=5 where c=1` 需要先在 `(1,·)` 附近插入 `(c=5, id=5)`，如果这个位置落在别人的间隙锁里，就会被堵住。

空表也有间隙：没有记录时，间隙由 `supremum` 这个伪记录定义，所以空表上的范围加锁照样能挡住插入。

### 「锁加在索引上」的两个推论

- **没索引 → 全表逐行加锁**。`update t set d=d+1 where d=5`（`d` 无索引）本机实测在 `PRIMARY` 上加 **7** 条记录锁：6 行各一条 next-key，外加 `supremum`。这就是「改一行锁全表」的机制，不是优化器偷懒。
- **改哪一行由索引决定，不是由 `where` 的文字决定**。同一行数据，走主键改和走二级索引改，锁加在不同的索引上，冲突关系也不同。

## insert 的锁：唯一键冲突是一把读锁

普通 `insert` 是很轻的操作：MySQL 对自增主键的锁做过优化，申请到自增 id 后就把自增锁释放掉（自增耗尽与空洞见 [44.25 MySQL 运维与故障处置](44.25-MySQL运维与故障处置.md)）。但有几类 `insert` 会额外加锁，且加锁量常常出人意料。

| 语句 | 额外加什么锁 | 加在谁身上 | 典型后果 |
|---|---|---|---|
| `insert ... values(...)` | 不加显式行锁（新行由隐式锁保护） | 目标表 | 轻量；自增锁申请到 id 即释放 |
| `insert ... select ... from 源表` | 源表扫描到的记录与间隙加 **S next-key lock** | 源表 | 源表在语句执行期间不能插入 |
| `insert` 撞唯一键（报 1062） | 冲突的唯一值上加 **S next-key lock** | 冲突索引 | 冲突不提交，锁一直挂着 |
| `insert ... on duplicate key update` | 冲突值上加 **X next-key lock** | 冲突索引 | 阻塞其他插入/更新 |
| `insert ... select` 且源表 = 目标表 | 临时表 + 全表扫描 + 源表全部间隙共享锁 | 同一张表 | 语句期间整表不能插入 |
| `replace into` | 冲突时先删后插（两套锁） | 冲突索引 + 主键 | 锁范围与自增值消耗都更大 |

### insert ... select 为什么要锁源表

RR 下执行 `insert into t2(c,d) select c,d from t`，会给源表 `t` 上扫描到的记录和间隙加**共享** next-key lock。原文用 `binlog_format=statement` 解释必要性：若不加锁，会话 B 可能先插入 `id=-1` 并先写入 binlog，而 A 的 `insert ... select` 后写；备库按 binlog 顺序重放就会多出一行 `id=-1`，主备不一致。

本机 8.0.46、`binlog_format=ROW`、RR 的实测结果是：**照锁**。源表 `t` 的 6 行各一把 `S` 锁，`supremum` 另有一把，共 7 把；期间另一个会话往源表插 `(9,9,9)` 被挡住，A 提交后才通过。

| 组合 | 源表是否被加 S next-key lock | 说明 |
|---|---|---|
| RR + `statement` | 是 | 原文的推理场景 |
| RR + `row`（本机实测） | **是** | 不要以为换成 ROW 就免锁 |
| RC + `row` | 否 | 代价是同一事务的范围读不再可重复 |

### 同表循环写入要临时表

需求：把表 `t` 里 `c` 的最大值加 1 后插回 `t`。

```sql
-- 慢查询日志 Rows_examined=5：表 t 全表扫 4 行 + 临时表 1 行
insert into t(c,d) (select c+1, d from t force index(c) order by c desc limit 1);
-- EXPLAIN 的 Extra 出现 Using temporary
```

`limit 1` 只限制了「从临时表取几行」，没有限制「往临时表灌几行」：执行流程是建临时表 → 按索引 `c` 倒序把 4 行全读出来写进临时表（`Innodb_rows_read` 增加 4）→ 只取临时表第一行插入 `t`（再 +1），合计 5。原因是一边遍历一边写回原表，可能读到刚插入的记录。优化写法是先落到内存临时表再插：

```sql
create temporary table temp_t(c int, d int) engine=memory;
insert into temp_t (select c+1, d from t force index(c) order by c desc limit 1);
insert into t select * from temp_t;
drop table temp_t;
```

这时的代价是：语句期间 `t` 的索引 `c` 上所有间隙都带共享 next-key lock，别的会话不能往这张表插数据。

### 唯一键冲突：报错也要留一把锁

```
-- 表 tu(id auto_increment PK, c UNIQUE, d)，已有 c=1..4
session A: begin; insert into tu(c,d) values(5,5);   -- 成功，持 c=5 的 X 记录锁
session B: begin; insert into tu(c,d) values(5,5);   -- 1062 冲突，改为申请 c=5 的 S next-key lock，等 A
session C: begin; insert into tu(c,d) values(5,5);   -- 同上，也在等 A
session A: rollback;                                  -- B、C 同时拿到 S 锁，再各自申请插入需要的 X 锁 -> 互等
```

本机复现的输出：A 持 `c` 索引 `X,REC_NOT_GAP`（`LOCK_DATA=5, 9`），B、C 各一条 `S` + `WAITING`；A 回滚后其中一个会话返回 `ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction`。

四个结论：

- 唯一键冲突不是「报错就结束」，**冲突值上会留一把共享 next-key lock**。作者也没找到官方解释，只推测「避免这一行被别的事务删掉」。
- 官方文档说「主键冲突加记录锁、唯一索引冲突加 next-key lock」，原文实测两类索引冲突加的都是 next-key lock——文档这一句是错的。
- 冲突报错后要**尽快提交或回滚**，否则这把 S 锁一直挂着，别人插同一个值全排队。
- `insert ... on duplicate key update` 在发现冲突时**直接加 X next-key lock**，不是「先加 S 再升级」。有多个唯一键同时冲突时，按索引顺序改第一个冲突的行（主键 `id` 先判断）；`affected rows` 返回 2 是假象——`insert` 与 `update` 各记了一次成功，真正只更新了一行。

`replace into` 的语义是「删掉冲突行再插入」，因此一次语句里既有删除的锁也有插入的锁，还会消耗自增值。我的判断：**upsert 优先用 `on duplicate key update`**，`replace into` 只在「整行覆盖、且不在乎自增空洞」时用。

## 真机实测：`data_locks` 里的四个现场

环境：MySQL **8.0.46**，默认 RR，`binlog_format=ROW`，`innodb_buffer_pool_size=128M`，`innodb_page_size=16384`，表 `t` 6 行（表结构与第 20/21 讲一致；现场四临时加一行变 7 行）。会话用两个 `mysql` 客户端 + FIFO 喂语句，锁信息从 `performance_schema.data_locks` / `data_lock_waits` 读，MySQL 8.0 起替代了 5.7 的 `information_schema.innodb_locks`。

```sql
-- 判读现场的三条查询（MySQL 8.0，需 performance_schema=on，默认开）
SELECT ENGINE_TRANSACTION_ID trx, INDEX_NAME idx, LOCK_MODE, LOCK_STATUS, LOCK_DATA
FROM performance_schema.data_locks
WHERE OBJECT_NAME='t' AND LOCK_TYPE='RECORD' ORDER BY INDEX_NAME, LOCK_DATA;
-- 谁在等谁
SELECT r.ENGINE_TRANSACTION_ID req, r.LOCK_MODE req_mode,
       b.ENGINE_TRANSACTION_ID blk, b.LOCK_MODE blk_mode, b.LOCK_DATA blk_data
FROM performance_schema.data_lock_waits w
JOIN performance_schema.data_locks r ON w.REQUESTING_ENGINE_LOCK_ID=r.ENGINE_LOCK_ID
JOIN performance_schema.data_locks b ON w.BLOCKING_ENGINE_LOCK_ID=b.ENGINE_LOCK_ID;
```

**现场一：`select ... for update` 走非唯一索引。** A 执行 `select * from t where c=5 for update`：

```text
trx     idx       LOCK_MODE        LOCK_STATUS  LOCK_DATA
1854    c         X,GAP            GRANTED      10, 10
1854    c         X                GRANTED      5, 5
1854    PRIMARY   X,REC_NOT_GAP    GRANTED      5
```

`INDEX_NAME=c` 上两条：`X`（不带 `REC_NOT_GAP` 就是 next-key `(0,5]`）与 `X,GAP`（`(5,10)`）；`PRIMARY` 上一条 `X,REC_NOT_GAP`——`for update` 会顺带给主键上加行锁，这正是它和 `lock in share mode` 的区别。此时 B 插入 `(8,8,8)` 被堵，等待关系是 `c X,GAP,INSERT_INTENTION` 等 `c X,GAP`。

**现场二：唯一索引 `update`，存在与不存在。** `update t set d=d+1 where id=10` 只有一条 `PRIMARY X,REC_NOT_GAP LOCK_DATA=10`；`where id=7` 变成 `PRIMARY X,GAP LOCK_DATA=10`（间隙 `(5,10)`，`LOCK_DATA` 指向右边界记录 10）。

**现场三：唯一键冲突死锁。** 见上节，`ERROR 1213`。

**现场四：`limit` 缩锁。** `delete from t where c=10`（表里 `c=10` 两行）5 条记录锁；`delete from t where c=10 limit 2` 4 条，少了 `c X,GAP LOCK_DATA=15, 15` 这条。

| `LOCK_MODE` 取值 | 含义 |
|---|---|
| `X,REC_NOT_GAP` | 只有行锁，没有间隙（唯一索引等值命中） |
| `X`（无后缀） | next-key lock：行锁 + 前面的间隙 |
| `X,GAP` | 只有间隙锁，不锁右边界那一行 |
| `X,GAP,INSERT_INTENTION` | 插入意向锁在排队，`insert` 被间隙锁挡住 |
| `S` / `S,GAP` | 共享 next-key / 共享间隙（唯一键冲突、`lock in share mode`） |
| `LOCK_DATA=supremum pseudo-record` | 索引末尾的伪记录，挡住最大记录之后的插入 |

回滚与降级：实验全部跑在 `docker run --rm` 的临时容器里，脚本 `trap` 在退出时 `docker rm -f`，不在宿主机留实例与数据；线上定位锁只需 `SELECT`，不改任何数据。若为降并发而把隔离级别降到 RC，务必同步确认 `binlog_format=row`，这是行为变更（范围读不再可重复），不能当性能开关随手拨。

完整脚本在仓库 [tools/examples/44.11-lock-lab](../../../tools/examples/44.11-lock-lab/README.md)，`bash code/run.sh` 可复现这七个现场（含本节的四个输出）。

## 表锁补遗：`lock tables` 的三条限制

`lock tables t1 read, t2 write` 除了限制别的线程，也限制本线程——这一点最容易被忽略：

| 对象 | 别的线程 | 本线程（直到 `unlock tables`） |
|---|---|---|
| `t1` | 写被阻塞，读正常 | 只能读，**不能写** |
| `t2` | 读写都被阻塞 | 可读可写 |
| 其他表 | 不受影响 | **完全不能访问** |

锁在 `unlock tables` 或客户端断开时释放。InnoDB 支持行锁，一般不用 `lock tables`；如果代码里出现它，通常两种原因：还在用 MyISAM 这类不支持事务的引擎，或者引擎升级了、代码没升级——把 `lock tables`/`unlock tables` 换成 `begin`/`commit` 往往就解决了。

MDL 与表锁是两个不同的结构，会同时存在：在 MyISAM 表上更新一行，会加一把 MDL 读锁和一把表写锁；另一个线程更新同一张表的另一行，MDL 读锁能加上（读锁不互斥），但会被表写锁堵住。同理，`online DDL` 的过程是「拿 MDL 写锁 → 降级成 MDL 读锁 → 真正做 DDL → 升级成 MDL 写锁 → 释放」，第 3 步占绝大部分时间、期间表可正常读写，所以叫 online；**第一、四步的写锁要等长事务放掉 MDL 读锁**，这就是加字段被卡住的机制。

FTWRL 与它们的等待关系是单向的：`FLUSH TABLES WITH READ LOCK` 要等当前所有读写执行完（并刷脏页）才能拿到，拿到之后阻塞所有 DML、DDL 和更新类事务的提交。影子表类工具（gh-ost、pt-online-schema-change）用「影子表改结构 + 追增量 + `RENAME` 切换」绕开长 DDL，但 `RENAME` 那一刻仍要拿 MDL 写锁——**它们减少的是持锁时长，不是消灭锁**。

## 反模式

| 反模式 | 后果 |
|---|---|
| 两个事务以不同顺序更新同一批行 | 死锁，靠数据库回滚一个 |
| 长事务持锁等外部 IO（RPC、用户输入） | 锁持有时间从毫秒变秒级，连锁阻塞 |
| 范围 `FOR UPDATE` 不带索引 | 间隙锁/表锁范围扩大，写入大面积阻塞 |
| 用 `SELECT ... FOR UPDATE` 做“读” | 读也排队，吞吐骤降 |
| 死锁后无限重试不加重试次数上限 | 两个事务反复互相回滚，CPU 打满 |
| 忽略 `innodb_lock_wait_timeout` 默认值 | 等待时间过长，连接池被占满（[44.12](44.12-连接池.md)） |
| 用覆盖索引 + `lock in share mode` 当读锁 | 主键没锁，别人的 UPDATE 照样改成功 |
| 大批量 `DELETE` 不带 `limit` | 一次锁住的区间覆盖全范围，期间插入全堵 |
| 长事务期间做 DDL | MDL 排队，后续所有读写跟着排队，整表不可用 |
| 用 `SET GLOBAL readonly` 代替 FTWRL | 客户端异常断开后库一直只读，比全局锁更危险 |
| 以为 `ALGORITHM=INPLACE` 就万事大吉 | 只免了拷贝表，MDL 等待与复制延迟照旧 |
| 事务里把最容易冲突的语句放最前 | 该行锁被持有到 `commit`，别人的等待时间被放大数倍（实测 2.37s vs 0.28s） |
| 先 `select ... for update` 判「不存在」再 `insert` 做 upsert | 两个并发事务各持同一间隙的间隙锁，再互相等对方的插入 → 死锁 |
| 唯一键冲突报错后不提交、不回滚 | 冲突值上留着 S next-key lock，其他会话插同一个值全部排队 |
| 以为 `binlog_format=row` 能让 `insert ... select` 不锁源表 | RR 下照样加 S next-key lock（含 `supremum`），源表插入全堵 |
| 只背「两个原则、两个优化、一个 bug」不看版本 | 8.0.46 上唯一索引范围查询的 bug 已不复现，按旧规则推理会误判锁范围 |
| `update` 的 `where` 条件没有索引 | 主键上逐行加锁 + `supremum`（实测 7 条记录锁），等价于锁全表 |
| 用 `replace into` 做 upsert | 删 + 插两套锁、自增空洞，冲突多时锁竞争比 `on duplicate key update` 更大 |

## 自检

**Q1** 为什么“间隙锁”能防幻读，而“行锁”不能？

▸ 答案：幻读是“同一个事务两次范围查询，第二次多出了别的事务插入的行”。行锁只能锁住**已经存在的行**，对新插入的行无能为力；间隙锁锁的是**索引区间**（如 `(10,30)`），任何试图插入该区间的操作都会被阻塞，于是第二次范围查询不会多出新行。代价是并发插入能力下降，且间隙锁只在 RR 及以上、且走索引时生效。

**Q2** 意向锁（IS/IX）到底解决了什么问题？

▸ 答案：解决了“表级锁如何快速判断行级锁冲突”的问题。没有意向锁时，事务要给表加 S/X 锁，必须逐行检查是否有行锁（O(n)）；有了 IS/IX，行级加锁前先在表上登记“我要在某行加 S/X”，表级操作只需检查表上的意向锁就能判断冲突（O(1)）。它不改变行级并发的语义，只是把“检查成本”从行数降到了常数。

**Q3** 两个事务按 `id` 升序更新同一批行，为什么不会死锁？还有什么情况会死锁？

▸ 答案：固定顺序消除了“循环等待”：所有事务都先锁小 id 再锁大 id，等待关系只能单向（小 id 持有者 → 大 id 持有者），不可能形成环。仍可能死锁的情况：① 其中一个事务用了不同的访问路径（例如一个走二级索引、一个走主键，加锁顺序不同）；② 间隙锁与插入意向锁交叉（插入不同行但落在同一间隙）；③ 涉及多张表时，表之间的加锁顺序不一致。所以“固定顺序”要覆盖**所有**资源（行、表、间隙）。

**Q4** 为什么 “没有索引的 UPDATE” 会锁住大量行甚至全表？

▸ 答案：因为 InnoDB 的锁加在**索引记录**上：没有可用索引时，只能全表扫描并给扫到的每一行加锁（RC 下还会释放不匹配的，RR 下范围更大）。表现是 “更新一行却锁住整表”，并发立刻崩。解法是给 WHERE 条件建索引。

**Q5** 定位死锁时，`SHOW ENGINE INNODB STATUS` 里最该看什么？

▸ 答案：看 `LATEST DETECTED DEADLOCK` 段：**两个事务各自的 SQL、持有的锁、等待的锁**。重点判断 “加锁顺序是否相反” 与 “是否用了二级索引导致锁范围过大”。修复通常不是调参数，而是改 SQL/加索引/统一顺序。

**Q6** `where id=7 for update`（`id=7` 不存在）为什么锁的是间隙 `(5,10)` 而不是 `(5,10]`？

▸ 答案：两步。原则 1 先把加锁单位圈成 next-key lock `(5,10]`（前开后闭，包含 `id=10` 这一行）；但这是等值查询，向右扫描到 `id=10` 时发现它不满足 `id=7`，属于「最后一个值不满足等值条件」，于是优化 2 把 next-key lock 退化成间隙锁 `(5,10)`——`id=10` 这一行不加行锁。效果：插 `id=8` 被堵，`update id=10` 不被堵。

**Q7** 用 `select c from t where c=5 lock in share mode` 给行加读锁，为什么另一个会话还能 `update t set d=d+1 where c=5`？

▸ 答案：因为这条查询是**覆盖索引**：`c` 在索引里，不需要回表，所以只有索引 `c` 上加了锁，**主键索引上一把锁都没有**。而 `update` 要改的 `d` 不在索引 `c` 里，它按主键找到行、加行锁，与索引 `c` 上的锁不冲突。要真正锁住这行，查询列表里必须带上索引外的字段（绕开覆盖索引），或者用 `for update`——后者会顺带给主键上满足条件的行加锁。

**Q8** 一条 `ALTER TABLE ... ADD COLUMN` 为什么能让一张只有几千行的表彻底不可读写？

▸ 答案：MDL 排队。DDL 需要 MDL 写锁，而表上一个「做完了 SELECT、还没提交」的长事务持着 MDL 读锁，两者互斥，DDL 只能等；更关键的是**后续所有查询申请 MDL 读锁时，也要排在等写锁的 DDL 后面**（写锁优先，防止饿死）。于是表上所有读写一起排队，客户端超时重试又把线程打满。解法是先查 `information_schema.innodb_trx` 清掉长事务，DDL 用 `NOWAIT`/`WAIT n` 避免无限等待。

**Q9** 同一组 SQL，只把 `update` 的位置从事务第一句挪到最后一句，别人的等待从 2.37s 降到 0.28s。总持锁时长明明没变（都要到 `commit` 才释放），为什么等待少了？

▸ 答案：两阶段锁改变不了「总持锁时长」，改变的是**每一行各自被持有的窗口**。冲突行如果在第一句被锁住，它的锁要跨越后面所有语句（本机是 `sleep(2)`）+ 提交，别人在这整段时间里排队；放到最后一句，冲突行的锁只在事务尾部待一小段。所以优化点是「把最可能冲突的行锁推迟到最后申请」，不是「少加锁」，也不是「提前提交」。如果答成「锁变少了」或「事务变短了」，就是没分清「锁的总量」与「单行的持锁窗口」。

**Q10** 用 `insert into t2(c,d) select c,d from t` 拷数据，另一个会话往源表 `t` 插入被堵；把 `binlog_format` 从 statement 改成 row 后**还是被堵**。为什么？怎么才能真正不锁源表？

▸ 答案：RR 下这条语句按「加锁读」执行：对源表扫描到的记录和间隙加 S next-key lock，保证语句执行期间读到的源数据不被改动。加锁由**隔离级别**决定，不由 binlog 格式决定——换成 row 只消除了「备库重放语句序列不一致」这个隐患，锁还在（本机 8.0.46 + ROW 实测仍是 7 把 S 锁含 `supremum`）。要真正不锁源表，得同时满足 RC + `binlog_format=row`，代价是同一事务的范围读不再可重复；或者改成「导出文件 / 分批小事务」把一条大语句拆成多条短语句。答题时若把「row 格式」当成免锁开关，就是背了结论没背条件。
