# 44.11 锁 (行锁 / 间隙锁 / 意向锁 / 死锁)

## 一句话

> 三种锁各管一件事：**行锁防丢失更新、间隙锁防幻读、意向锁让表级操作不必逐行检查**；而死锁不是 bug，是“多个事务以不同顺序加锁”的必然结果——只能靠等待图检测并回滚一个事务来打断。

## 六种锁，一张兼容表

| 锁 | 加在什么上 | 解决什么 | 与谁冲突 |
|---|---|---|---|
| 共享锁 S | 行 | 读时阻止别人改 | X |
| 排他锁 X | 行 | 写时阻止别人读/写 | S、X |
| 意向共享 IS | 表 | 声明“我要在某行加 S” | IX |
| 意向排他 IX | 表 | 声明“我要在某行加 X” | S、X、IS |
| **间隙锁 GAP** | 索引区间 | 阻止区间内插入（防幻读） | 插入意向锁 |
| **Next-Key** | 记录 + 前面的间隙 | 行锁 + 间隙锁的组合 | 同上 |

|  | S | X | IS | IX |
|---|---|---|---|---|
| **S** | ✅ | ❌ | ✅ | ❌ |
| **X** | ❌ | ❌ | ❌ | ❌ |
| **IS** | ✅ | ❌ | ✅ | ✅ |
| **IX** | ❌ | ❌ | ✅ | ✅ |

> 🔑 意向锁的意义：如果没有它，一个事务要加**表锁**，必须扫描全表每一行看有没有行锁；有了 IS/IX，只需看表上有没有冲突的意向锁——**用一次表级检查替代 O(n) 行扫描**。

## 加锁规则：两个原则、两个优化、一个 bug

「改一行却锁了这么多」不是玄学：InnoDB 的加锁范围可以从五条规则推出来。前提是 RR 隔离级别。

> ⚠️ 规则边界：这套总结来自《MySQL 实战 45 讲》作者对源码的归纳，适用范围是 5.x ≤ 5.7.24、8.0 ≤ 8.0.13。更新的小版本可能改策略——判断前先用 `performance_schema.data_locks` 实测，别背规则下结论。

| 编号 | 规则 | 含义 |
|---|---|---|
| 原则 1 | 加锁的基本单位是 **next-key lock** | 前开后闭区间 `(a, b]`，即「行锁 + 前面的间隙锁」 |
| 原则 2 | **访问到的对象才加锁** | 没被扫描到的索引行不加锁，所以「走不走索引」决定锁范围 |
| 优化 1 | 唯一索引上的**等值**查询 | next-key lock 退化成**行锁** |
| 优化 2 | 等值查询向右遍历，最后一个值不满足条件 | next-key lock 退化成**间隙锁**（不锁那一行） |
| 一个 bug | 唯一索引上的**范围**查询 | 会一直扫到第一个不满足条件的行，多锁一段 |

用表 `t`（`id` 主键，`c` 有普通索引，值均为 `0,5,10,15,20,25`）走一遍：

| 语句 | 实际加锁 | 用到哪条规则 |
|---|---|---|
| `where id=7 for update`（7 不存在） | 间隙锁 `(5,10)` | 原则 1 圈出 `(5,10]`，优化 2 去掉 `id=10` 那行 |
| `where c=5 lock in share mode` | 索引 `c` 上 `(0,5]` 与 `(5,10)`；**主键无锁** | 非唯一索引要向右扫到 `c=10` 才停；覆盖索引不回表，所以主键不加锁 |
| `where id>=10 and id<11 for update` | 行锁 `id=10` + `(10,15]` | 首次等值定位走优化 1，向右按范围加锁 |
| `where c=10`（非唯一索引） | `(5,10]` + `(10,15]` | 非唯一索引**没有**优化 1，不会退化成行锁 |
| `where id>=10 and id<=15 for update` | 行锁 `id=10` + `(10,15]` + **`(15,20]`** | bug：扫到 `id=20` 才确认结束 |
| `delete from t where c=10 limit 2` | 到 `(c=10,id=30)` 为止 | `limit` 让遍历提前结束，锁范围随之缩小 |

两个能立刻用上的推论：

- **`limit` 能缩锁**：删除/更新时带 `limit`，既控条数也控锁范围。大批量操作要分批，不是「一条 SQL 更省事」。
- **`lock in share mode` + 覆盖索引锁不住主键**：上表第二行里，另一个会话 `update t set d=d+1 where c=5` 照样能执行——它要改的 `d` 不在索引 `c` 里，而主键上根本没锁。想用读锁阻止更新，查询列表里要带上索引外的字段（如 `select d from t where c=5 lock in share mode`），或者直接用 `for update`。

RC 下的两条差异值得记住：**没有间隙锁**（外键场景除外），并且语句执行完就释放「不满足条件」的行锁，不等事务提交。所以 RC 的锁范围更小、持锁更短——这是大量业务默认 RC 的真实原因，不只是「RC 性能好」。

### next-key lock 是两段加的，所以会死锁

案例八：会话 A `select * from t where c=5 lock in share mode`（持 `(5,10]` 与 `(10,15)`），会话 B `update t set d=d+1 where c=10` 进入等待，会话 A 再 `insert into t values(8,8,8)`——被 B 挡住，死锁，B 回滚。

原因：B 的 `next-key lock(5,10]` 分两步执行，**先加间隙锁 `(5,10)`（成功），再加 `c=10` 的行锁（被 A 挡住）**。于是 B 手里已握着 A 需要的间隙锁，A 又在等 B 需要的资源。

> 🔑 判断锁范围只看一件事：**这条语句扫到了哪些索引记录**。不是「改了几行」，也不是「有没有 `FOR UPDATE`」。没有索引 → 扫全表 → 锁全表，这条因果链没有例外。

## 代码：等待图 + 死锁检测 + 间隙锁

```go
package main

import (
	"fmt"
	"sort"
)

type lockMgr struct {
	holder  map[string]string   // resource -> txn（简化为单持有者）
	waitFor map[string]string   // txn -> 它等待的 txn
	held    map[string][]string // txn -> 持有的资源
}

func newLockMgr() *lockMgr {
	return &lockMgr{holder: map[string]string{}, waitFor: map[string]string{}, held: map[string][]string{}}
}

// acquire 返回 "ok" / "wait" / "deadlock"
func (m *lockMgr) acquire(txn, res string) string {
	if h, ok := m.holder[res]; ok {
		if h == txn {
			return "ok(重入)"
		}
		m.waitFor[txn] = h
		if m.detectCycle(txn) {
			delete(m.waitFor, txn)
			return "deadlock"
		}
		return fmt.Sprintf("wait(%s)", h)
	}
	m.holder[res] = txn
	m.held[txn] = append(m.held[txn], res)
	return "ok"
}

// 从 txn 出发沿 waitFor 走，看能否回到自己
func (m *lockMgr) detectCycle(start string) bool {
	seen := map[string]bool{}
	cur := start
	for {
		next, ok := m.waitFor[cur]
		if !ok {
			return false
		}
		if next == start {
			return true
		}
		if seen[next] {
			return false
		}
		seen[next] = true
		cur = next
	}
}

func (m *lockMgr) release(txn string) {
	for _, r := range m.held[txn] {
		if m.holder[r] == txn {
			delete(m.holder, r)
		}
	}
	delete(m.held, txn)
	// 清理那些“在等这个事务”的等待关系
	for waiter, holder := range m.waitFor {
		if holder == txn {
			delete(m.waitFor, waiter)
		}
	}
}

func main() {
	m := newLockMgr()
	fmt.Println("=== 加锁序列（两个事务以相反顺序加锁）===")
	steps := []struct{ txn, res string }{
		{"T1", "row:1"}, {"T2", "row:2"},
		{"T1", "row:2"}, {"T2", "row:1"},
	}
	for _, s := range steps {
		r := m.acquire(s.txn, s.res)
		fmt.Printf("%s 请求 X(%s) -> %s\n", s.txn, s.res, r)
		if r == "deadlock" {
			fmt.Println("  检测到环：T1 -> T2 -> T1，选择回滚 T2（新加入等待环的事务）")
			m.release("T2")
			fmt.Printf("  T2 回滚后，T1 重试 X(row:2) -> %s\n", m.acquire("T1", "row:2"))
		}
	}

	fmt.Println("\n=== 间隙锁：阻止区间内插入 ===")
	// 索引上有 10、20、30；事务对 (10,30) 加间隙锁
	gaps := []struct {
		lo, hi int
		holder string
	}{{10, 30, "T3"}}
	tryInsert := func(v int) {
		for _, g := range gaps {
			if v > g.lo && v < g.hi {
				fmt.Printf("插入 %d -> 阻塞（落在 T3 的间隙锁 (%d,%d) 内）\n", v, g.lo, g.hi)
				return
			}
		}
		fmt.Printf("插入 %d -> 成功（不在任何间隙锁内）\n", v)
	}
	tryInsert(18)
	tryInsert(35)

	// 统计每个事务持有的锁（按资源名排序，输出稳定）
	fmt.Println("\n=== 当前锁持有情况 ===")
	for txn, rs := range m.held {
		sort.Strings(rs)
		fmt.Printf("%s: %v\n", txn, rs)
	}
}
```

本机实测（macOS，Apple M1，Go 1.27）：

```
=== 加锁序列（两个事务以相反顺序加锁）===
T1 请求 X(row:1) -> ok
T2 请求 X(row:2) -> ok
T1 请求 X(row:2) -> wait(T2)
T2 请求 X(row:1) -> deadlock
  检测到环：T1 -> T2 -> T1，选择回滚 T2（新加入等待环的事务）
  T2 回滚后，T1 重试 X(row:2) -> ok

=== 间隙锁：阻止区间内插入 ===
插入 18 -> 阻塞（落在 T3 的间隙锁 (10,30) 内）
插入 35 -> 成功（不在任何间隙锁内）

=== 当前锁持有情况 ===
T1: [row:1 row:2]
```

读数：

| 现象 | 含义 |
|---|---|
| T1 与 T2 各持一把锁、再互相请求 | 等待图出现环 `T1 → T2 → T1`，这就是死锁 |
| 检测到环后回滚 T2 | 数据库不会“等一等就好”，必须选一个牺牲者 |
| 插入 18 被阻塞 | 间隙锁锁的是“区间”，不是“已存在的行”——这正是防幻读的机制 |
| 插入 35 成功 | 落在间隙之外，不受影响 |

> ⚠️ 间隙锁的代价：它锁住的是**区间**，会阻塞所有落在区间内的插入（哪怕这些行与查询条件无关）。所以高并发写入的表要谨慎使用 `SELECT ... FOR UPDATE` + 范围条件，否则容易“锁住一大片”。

## 死锁的四个条件与三种解法

| 条件 | 含义 | 解法 |
|---|---|---|
| 互斥 | 资源不能共享 | 无法消除（写操作天然互斥） |
| 持有并等待 | 拿着 A 等 B | 一次性申请所有锁（或按固定顺序） |
| 不可抢占 | 不能强行拿走 | 超时回滚（`innodb_lock_wait_timeout`） |
| 循环等待 | 形成环 | **按固定顺序加锁**（最有效）、检测到环后回滚 |

> 🔑 工程上最有效的一条是“**固定加锁顺序**”：所有事务都按 `min(id), max(id)` 的顺序锁行，环就不可能形成。其次是“小事务”（锁持有时间短，碰撞概率低）与“走索引”（避免锁范围扩大到全表）。

## 全局锁与元数据锁：加个字段为什么能挂掉整库

不是所有锁都在行上。备份要「一致性视图」，DDL 要「表结构不被并发改」，这两件事用的是整库锁与表级锁——而**真正天天咬人的是 MDL**：它由系统自动加，事务不提交就不释放。

| 手段 | 锁住什么 | 阻塞谁 | 什么时候该用 |
|---|---|---|---|
| `FLUSH TABLES WITH READ LOCK`（FTWRL） | 全库只读 | 所有 DML、DDL、更新类事务的提交 | 只有**非事务引擎**（MyISAM）做逻辑备份时才不得不用 |
| `SET GLOBAL readonly=on` | 全库只读 | 写 | 不推荐：可能被业务用来判主备；客户端异常断开后不自动恢复 |
| `LOCK TABLES ... READ/WRITE` | 指定表 | 别的线程读写**且本线程只能操作列出的表** | 只在引擎没有行锁时才有意义 |
| MDL 读锁 / 写锁 | 表结构 | 读锁之间不互斥；读-写、写-写互斥 | 自动加，关不掉 |

### 备份：`--single-transaction` 与 FTWRL 二选一

不加锁直接备份，拿到的是「余额表已备份、课程表未备份」的中间态——逻辑上不一致。`mysqldump --single-transaction` 在导出前开一个 RR 事务拿一致性视图，靠 MVCC 让备份期间的写入照常进行。**它的前提是所有表都是事务引擎**：有 MyISAM 表就只能 FTWRL，整库只读。这也是 DBA 要求把 MyISAM 换成 InnoDB 的理由之一。

### MDL 事故：一条 DDL 把表变成不可读写

1. 会话 A `BEGIN; SELECT * FROM t;` → 持有 MDL 读锁；
2. 会话 B `SELECT * FROM t;` → 同为读锁，正常；
3. 会话 C `ALTER TABLE t ADD COLUMN c INT;` → 要 MDL **写锁**，被 A 挡住，进入等待；
4. 此后所有新查询都要申请 MDL 读锁，全部排在 C 后面 → 表彻底不可读写，客户端重试把线程数打满。

根因只有一句：**MDL 在语句开始时申请，语句结束不释放，等整个事务提交才释放**。所以一个「已经跑完 SELECT 但没提交」的长事务，就足以让 DDL 排队、让全表停摆。

### 安全加字段的四步

| 步骤 | 命令 | 作用 |
|---|---|---|
| ① 先查长事务 | `SELECT trx_id, trx_started, trx_mysql_thread_id FROM information_schema.innodb_trx ORDER BY trx_started;` | 有长事务先 kill 或等它结束 |
| ② DDL 带算法与锁级别 | `ALTER TABLE t ADD COLUMN c INT, ALGORITHM=INPLACE, LOCK=NONE;` | 避免拷贝表与锁表；**它治不了 MDL 排队** |
| ③ 拿不到锁就放弃 | `ALTER TABLE t NOWAIT ADD COLUMN c INT;`（MariaDB / AliSQL 分支支持 `WAIT n`） | 不让一条 DDL 卡住后续所有请求 |
| ④ 大表走影子表 | 在影子表上改结构、追平增量，最后 `RENAME` 切换 | 课程未覆盖，属于 DBA 侧做法（我的判断：超过千万行的表不要在主表上直接 DDL） |

> 🔑 `ALGORITHM=INPLACE` 不等于「不影响线上」。它解决的是**拷贝表**，不解决 **MDL 排队**：一条 DDL 在等写锁时，后面所有读请求都会跟着排队。

## 反模式

| 反模式 | 后果 |
|---|---|
| 两个事务以不同顺序更新同一批行 | 死锁，靠数据库回滚一个 |
| 长事务持锁等外部 IO（RPC、用户输入） | 锁持有时间从毫秒变秒级，连锁阻塞 |
| 范围 `FOR UPDATE` 不带索引 | 间隙锁/表锁范围扩大，写入大面积阻塞 |
| 用 `SELECT ... FOR UPDATE` 做“读” | 读也排队，吞吐骤降 |
| 死锁后无限重试不加重试次数上限 | 两个事务反复互相回滚，CPU 打满 |
| 忽略 `innodb_lock_wait_timeout` 默认值 | 等待时间过长，连接池被占满（[44.12](44.12-连接池.md)） |
| 用覆盖索引 + `lock in share mode` 当读锁 | 主键没锁，别人的 UPDATE 照样改成功 |
| 大批量 `DELETE` 不带 `limit` | 一次锁住的区间覆盖全范围，期间插入全堵 |
| 长事务期间做 DDL | MDL 排队，后续所有读写跟着排队，整表不可用 |
| 用 `SET GLOBAL readonly` 代替 FTWRL | 客户端异常断开后库一直只读，比全局锁更危险 |
| 以为 `ALGORITHM=INPLACE` 就万事大吉 | 只免了拷贝表，MDL 等待与复制延迟照旧 |

## 自检

**Q1** 为什么“间隙锁”能防幻读，而“行锁”不能？

▸ 答案：幻读是“同一个事务两次范围查询，第二次多出了别的事务插入的行”。行锁只能锁住**已经存在的行**，对新插入的行无能为力；间隙锁锁的是**索引区间**（如 `(10,30)`），任何试图插入该区间的操作都会被阻塞，于是第二次范围查询不会多出新行。代价是并发插入能力下降，且间隙锁只在 RR 及以上、且走索引时生效。

**Q2** 意向锁（IS/IX）到底解决了什么问题？

▸ 答案：解决了“表级锁如何快速判断行级锁冲突”的问题。没有意向锁时，事务要给表加 S/X 锁，必须逐行检查是否有行锁（O(n)）；有了 IS/IX，行级加锁前先在表上登记“我要在某行加 S/X”，表级操作只需检查表上的意向锁就能判断冲突（O(1)）。它不改变行级并发的语义，只是把“检查成本”从行数降到了常数。

**Q3** 两个事务按 `id` 升序更新同一批行，为什么不会死锁？还有什么情况会死锁？

▸ 答案：固定顺序消除了“循环等待”：所有事务都先锁小 id 再锁大 id，等待关系只能单向（小 id 持有者 → 大 id 持有者），不可能形成环。仍可能死锁的情况：① 其中一个事务用了不同的访问路径（例如一个走二级索引、一个走主键，加锁顺序不同）；② 间隙锁与插入意向锁交叉（插入不同行但落在同一间隙）；③ 涉及多张表时，表之间的加锁顺序不一致。所以“固定顺序”要覆盖**所有**资源（行、表、间隙）。

**Q4** 为什么 “没有索引的 UPDATE” 会锁住大量行甚至全表？

▸ 答案：因为 InnoDB 的锁加在**索引记录**上：没有可用索引时，只能全表扫描并给扫到的每一行加锁（RC 下还会释放不匹配的，RR 下范围更大）。表现是 “更新一行却锁住整表”，并发立刻崩。解法是给 WHERE 条件建索引。

**Q5** 定位死锁时，`SHOW ENGINE INNODB STATUS` 里最该看什么？

▸ 答案：看 `LATEST DETECTED DEADLOCK` 段：**两个事务各自的 SQL、持有的锁、等待的锁**。重点判断 “加锁顺序是否相反” 与 “是否用了二级索引导致锁范围过大”。修复通常不是调参数，而是改 SQL/加索引/统一顺序。

**Q6** `where id=7 for update`（`id=7` 不存在）为什么锁的是间隙 `(5,10)` 而不是 `(5,10]`？

▸ 答案：两步。原则 1 先把加锁单位圈成 next-key lock `(5,10]`（前开后闭，包含 `id=10` 这一行）；但这是等值查询，向右扫描到 `id=10` 时发现它不满足 `id=7`，属于「最后一个值不满足等值条件」，于是优化 2 把 next-key lock 退化成间隙锁 `(5,10)`——`id=10` 这一行不加行锁。效果：插 `id=8` 被堵，`update id=10` 不被堵。

**Q7** 用 `select c from t where c=5 lock in share mode` 给行加读锁，为什么另一个会话还能 `update t set d=d+1 where c=5`？

▸ 答案：因为这条查询是**覆盖索引**：`c` 在索引里，不需要回表，所以只有索引 `c` 上加了锁，**主键索引上一把锁都没有**。而 `update` 要改的 `d` 不在索引 `c` 里，它按主键找到行、加行锁，与索引 `c` 上的锁不冲突。要真正锁住这行，查询列表里必须带上索引外的字段（绕开覆盖索引），或者用 `for update`——后者会顺带给主键上满足条件的行加锁。

**Q8** 一条 `ALTER TABLE ... ADD COLUMN` 为什么能让一张只有几千行的表彻底不可读写？

▸ 答案：MDL 排队。DDL 需要 MDL 写锁，而表上一个「做完了 SELECT、还没提交」的长事务持着 MDL 读锁，两者互斥，DDL 只能等；更关键的是**后续所有查询申请 MDL 读锁时，也要排在等写锁的 DDL 后面**（写锁优先，防止饿死）。于是表上所有读写一起排队，客户端超时重试又把线程打满。解法是先查 `information_schema.innodb_trx` 清掉长事务，DDL 用 `NOWAIT`/`WAIT n` 避免无限等待。
