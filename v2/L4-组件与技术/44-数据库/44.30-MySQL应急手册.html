              44.30 MySQL 应急手册：饮鸩止渴、kill 不掉与内存打爆

              一句话

              应急只有两条边界：能立刻做的是「减少进入系统的请求」，不是「让数据库更猛」；kill 只是给线程置一个状态位，不是断电，真正结束的标志是线程从 PROCESSLIST 里消失。

              来源：短连接、慢查询、QPS 突增、kill 语义、结果集发送与内存来自丁奇《MySQL 实战 45 讲》（极客时间，2019）第 22、32、33 讲，并发槽位与临时表加速分别来自第 29、35 讲；本节 SQL 与实测为本机 linux/arm64 容器内的 MySQL 8.0.46 补充。

              环境：MySQL 8.0.46 容器，innodb_buffer_pool_size=128M、max_connections=200、innodb_page_size=16384、RR 隔离。文中的 id、耗时、RSS 会随机器与负载漂移，结论看比值与量级。

              应急决策表：先看证据，再动手

              值班时最贵的不是命令，是判断顺序。同一句「数据库卡了」，六种现象的第一动作完全不同：

              现象 第一眼看什么 能立刻做（有损） 不要做
              连接数打满、报 Too many connections Threads_connected / max_connections；PROCESSLIST 里 Sleep 占比 先 kill 事务外空闲连接，再考虑事务内空闲 直接调大 max_connections；--skip-grant-tables
              新出现慢查询 慢日志里同一指纹的 Rows_examined、EXPLAIN 备库加索引后切换；query_rewrite 改写；force index 在主库高峰期直接跑 DDL
              QPS 突增 Questions / Com_* 的每秒增量、Threads_running 业务侧限流降级；摘白名单、删独立账号 先调 innodb_thread_concurrency 挡请求
              长事务、锁等待堆积 innodb_trx.trx_rows_modified、data_locks.LOCK_STATUS 评估回滚成本后再决定是否 kill 不看行数就 kill 一个改了几十万行的事务
              kill 后线程还在 Command 是否 Killed、State 是什么 调大 innodb_thread_concurrency、降低 IO 压力让它走完 反复 kill、直接重启 mysqld
              内存持续上涨 Sending to client 线程数、每连接 buffer 配置 让客户端恢复读取；加大 net_buffer_length 止血 认定「大查询会把内存打爆」而去扩内存

              🔑 应急的顺序永远是「降进入量 → 降单语句代价 → 加资源」。反过来做——先扩内存、先加连接数、先放开并发——就是把压力灌进一个已经满的管道。

              短连接风暴：max_connections 数的是「连着」，不是「干着」

              短连接的模式是：连上、执行很少几条 SQL、断开，下次用时再连。数据库压力小时，建连成本不明显；一旦数据库处理变慢，每个连接被持有的时间变长，新建连接还在源源不断进来，就会撞上 max_connections。

              建连成本有三块，都在数据库侧：

              1. 网络三次握手；
              2. 登录权限判断；
              3. 取得这个连接的数据读写权限。

              超过 max_connections 后，新连接被拒绝并报 Too many connections。从业务角度看，这就是数据库不可用——即使已经在执行的查询全都正常。

              max_connections 的计数口径是关键：只要连着就占一个位置，不看它是否在 running。所以一个 Sleep 的连接和一个正在扫 200 万行的连接，在计数上完全等价。

              为什么「调大连接数」是饮鸩止渴

              设计 max_connections 的目的是保护 MySQL。改大之后，更多连接可以进来，系统负载进一步升高，大量资源花在权限验证这类建连逻辑上；结果是已经连上的线程拿不到 CPU 去执行 SQL。现象是连接数很漂亮，吞吐反而更低。

              手段 立刻效果 代价 适用边界
              kill connection <id> 踢掉 Sleep 连接 立刻腾出计数位置 事务内连接被踢 = 回滚；客户端要到下一次请求才知道 连接数打满、且能分辨事务内外
              调小 wait_timeout 空闲连接自动回收 同上，且是「无差别误伤」：分不清谁在事务里 连接泄漏长期存在，非瞬时故障
              调大 max_connections 报错消失 建连成本挤占 CPU，已在跑的语句更慢 仅当确认瓶颈不是 CPU/内存
              --skip-grant-tables 启动 跳过全部权限验证 任何能连上的人都是超级权限；8.0 会默认打开 --skip-networking 基本不该用，尤其库对外可访问时

              ⚠️ --skip-grant-tables 是这份清单里风险最高的一条：它不是「少一次校验」，是「整个实例没有权限系统」。MySQL 8.0 在这个参数下默认把 --skip-networking 一起打开，只能本地连接——官方对它的态度已经写在默认值里。

              踢连接之前，先分清事务内还是事务外

              SHOW PROCESSLIST 里两个都是 Sleep 的连接，代价可能差一个数量级：

              • 踢 事务外空闲（Sleep，且不在任何事务里）：连接断开就结束了，接近无感；
              • 踢 事务内空闲（BEGIN 之后没有提交，客户端在 Sleep）：MySQL 只能按回滚事务处理，改过的行越多，回滚越久。

              判断依据不是 Sleep 这个字样，而是 information_schema.innodb_trx：

              -- 谁还处在事务里：trx_mysql_thread_id 就是 PROCESSLIST 的 Id（MySQL 8.0，本机实测）
SELECT trx_mysql_thread_id, trx_started, trx_rows_modified, trx_state
FROM information_schema.innodb_trx;

              先踢「不在 innodb_trx 结果里」的 Sleep 连接，还不够再踢事务内的。这个顺序能把「为了腾位置反而制造一批回滚」的概率降到最低。

              从服务端断开一个 Sleep 连接，客户端不会马上知道：它要等到下一次在这条连接上发请求，才收到 ERROR 2013 (HY000): Lost connection to MySQL server during query。本机用 FIFO 保持一条空闲连接，服务端 KILL CONNECTION 后再发一条 SELECT 1，客户端拿到的正是这个错误：

              ERROR 2013 (HY000) at line 1: Lost connection to MySQL server during query

              真正的坑在应用侧：有的代码收到 2013 后不重建连接，而是拿这个已经废掉的句柄继续重试。从监控上看就是「MySQL 一直没恢复」，其实数据库早就好了。原文作者说这类事他碰到过不下 10 次。所以哪怕只是断开连接，也要提前通知业务开发：连接异常断开是常态，客户端必须有重建连接 + 重试的机制。

              连接池视角：mysql_reset_connection 省掉的是握手与鉴权

              如果压力确实来自「短时间大量建连」，比放开权限更安全的做法是让应用复用连接、只重置会话。MySQL 提供 mysql_reset_connection()（C API，5.7.3 起）：不重新做 TCP 握手和登录鉴权，只把会话状态清回初始（回滚未提交事务、释放表锁与临时表、重置会话变量）。代价是它需要驱动/连接池支持，不是所有池都暴露这个能力。连接池的容量与探活配置见 44.12 连接池。

              做法 省掉什么 风险
              关闭短连接、改连接池 握手 + 鉴权的绝大部分 需要改业务代码
              mysql_reset_connection() 握手 + 鉴权，保留 TCP 连接 清会话状态，依赖驱动支持；事务会被回滚
              调小 wait_timeout 空闲连接占位 误伤事务内空闲连接，触发回滚
              调大 max_connections 报错 建连成本上升，吞吐可能下降

              🔑 短连接风暴的根因是「连接建立成本 × 建连频率」，不是「上限太小」。治本是连接池 + 重试，治标是踢事务外空闲连接；调大上限只是把队列挪到数据库内部。

              慢查询性能问题：三类来源，三种止血，一条根治流程

              线上突然变慢的查询，来源只有三类：索引没设计好、语句没写好、MySQL 选错了索引。三类里前两类完全可以在上线前消灭，第三类才是真正的「优化器猜错」。

              来源 典型判据 应急止血 根治
              索引没设计好 EXPLAIN 的 key=NULL、Rows_examined 接近表行数 备库 Online DDL 加索引 → 主备切换 → 回切补另一侧 上线前按访问模式设计索引；变更走 gh-ost
              语句没写好 条件列上带函数/隐式转换，索引失效 query_rewrite 把语句改写成能走索引的形式 改代码 + SQL 审计
              MySQL 选错索引 同一语句换 force index 后 Rows_examined 骤降 force index，或用 query_rewrite 自动加 hint ANALYZE TABLE 更新统计；必要时调整索引顺序

              索引没设计好：先在备库加，再切换

              MySQL 5.6 起创建索引支持 Online DDL，高峰期数据库已经被这条语句打挂时，最高效的动作就是直接 ALTER TABLE 加索引。更稳的顺序是在备库先做，一主一备的流程：

              1. 备库 B 上执行 SET sql_log_bin=OFF;（不写 binlog），再 ALTER TABLE 加索引；
              2. 主备切换，B 成为主库；
              3. 原主库 A 变成备库，在 A 上同样 SET sql_log_bin=OFF; 后加索引。

              这是原文说的「古老」DDL 方案：平时变更应该用 gh-ost 这类工具，但在需要紧急止血时，它的效率最高。原因是它把「给大表加索引」的耗时从主库的可用性里摘了出去。

              ⚠️ 在备库上 SET sql_log_bin=OFF 再 DDL，意味着这段变更不会同步给另一侧。所以第 3 步不能省，否则切换回来时新主库缺索引。这个方案只适合「确定要马上切换」的场景。

              语句没写好：用 query_rewrite 在服务端改写

              MySQL 5.7 起提供 query_rewrite 插件，把一种语句模式改写成另一种。典型例子是条件列上做运算导致索引失效：SELECT * FROM t WHERE id + 1 = 10000。改写规则如下（MySQL 8.0）：

              -- 前置：插件未安装时先装（8.0 需要显式安装）
INSTALL PLUGIN query_rewrite SONAME 'query_rewrite.so';

INSERT INTO query_rewrite.rewrite_rules (pattern, replacement, pattern_database)
VALUES ('select * from t where id + 1 = ?',
        'select * from t where id = ? - 1',
        'luban');

-- 让新规则生效
CALL query_rewrite.flush_rewrite_rules();

-- 核对规则是否命中
SELECT rule_id, pattern, replacement, pattern_database, hits
FROM query_rewrite.rewrite_rules;

              hits 是规则命中次数，它比「我记得配了」可靠。改写发生在服务端，业务代码不用发版——这是它适合止血的原因，也是它的风险：改错了会影响所有走这个模板的语句。

              选错索引：force index 是止痛针，不是治疗方案

              第三种来源是优化器选错索引。应急就是给语句加 force index，同样可以用 query_rewrite 批量加，避免改代码。

              force index 的后患必须写清楚：

              后患 触发条件 后果
              索引被改名/删除 后续 DDL 调整索引 语句直接报错，从「慢」变成「不可用」
              数据分布变了 该索引选择性下降、或范围扩大 hint 把计划锁死在错误的索引上，比不加强
              优化器本可以选对 统计信息更新后 人为放弃优化器的自适应能力
              被复制到新代码 复制粘贴 技术债扩散，没人知道为什么加

              🔑 判断标准只有一条：加 force index 之后，必须同时留下「为什么加、什么条件下删」的记录和跟踪项。只加不删的 hint，半年后就是一次新的故障。

              根治流程：把慢查询挡在上线前

              原文给的流程只有三步，成本极低：

              1. 上线前在测试环境打开慢查询日志，把 long_query_time 设成 0，确保每条语句都记录；
              2. 在测试表里灌入接近线上的数据量，做一遍回归测试；
              3. 逐条看慢日志里的 Rows_examined，确认它与预期一致——这一列比执行时间更稳定，不受测试机负载影响。

              新增语句不多时手跑即可；新项目或改了表结构，就要全量回归，用 pt-query-digest 按指纹聚合所有 SQL 的返回结果与扫描行数。

              检查项 阈值/判据 不通过的处置
              Rows_examined / 返回行数 接近 1:1；出现数量级倍数就是缺索引或选错索引 加索引或改写
              EXPLAIN 的 type 不应出现 ALL（小表除外） 补索引
              慢日志条数 long_query_time=0 下逐条过 逐条评审
              新索引 必须能对应到具体语句 删掉「预防性」索引

              💡 慢查询的「慢」有两层：语句本身扫描多（Rows_examined 大），和语句在等（锁、IO、并发槽位）。前者看执行计划，后者看 State 与 data_locks——见 44.9 执行计划与慢查询 与 44.11 锁。

              QPS 突增：先证明它真的突增了

              「QPS 涨了」经常是监控口径造成的错觉。三个计数器的关系先分清：

              计数器 统计什么 判读要点
              Questions 客户端发来的语句数 不含存储程序内部执行的语句；要取每秒增量，不是累计值
              Queries 服务端执行的语句数 含存储程序内部的语句，因此 ≥ Questions
              Com_select / Com_insert / … 按命令类型分开计数 定位「是哪类语句在涨」
              Com_kill 执行过多少次 KILL 每次 kill 加 1，用来确认「我们到底杀了多少」
              Threads_running 当前正在执行的线程数 不含 Sleep；这是判断「忙」还是「堵」的核心指标

              ⚠️ 统计会被监控自己污染。本机开着 general_log 抓了一次 mysql 客户端连接，每个连接都会先发 select @@version_comment limit 1——它计入 Com_select。所以「三个 SELECT 让 Com_select 涨了 12」是正常现象：其余是监控连接和取线程 id 的查询。判读时先扣掉监控自身，或者只看同一口径的差值。

              Threads_running 与 TPS 的四象限

              TPS 用 Com_commit + Com_rollback 的每秒增量近似（两者都是累计值，先取差值）。它和 Threads_running 一起看，才能分清「忙」和「堵」：

              Threads_running TPS 含义 第一动作
              高 高 真忙：请求多、执行快 业务侧限流；评估扩容
              高 低 在排队：锁等待、IO 卡住、并发槽位满 看 data_locks、State、SHOW ENGINE INNODB STATUS
              低 高 单语句很快，吞吐健康 不用动
              低 低 请求根本没进来（连接/网络/上游） 查上游与连接数

              本机在一次锁等待里读到 Threads_running=4，其中包含两个空闲/等待会话；杀掉持锁的空闲会话后回落到 2。它数的是「正在执行」的线程，不是连接数——这一点和 max_connections 正好相反。

              业务侧先降级，数据库侧只做最后一刀

              QPS 突增如果是新功能 bug 引起的，最理想的是业务把这个功能下掉，服务自然恢复。从数据库端处理，按侵入性从低到高：

              方案 前提 做法 副作用
              ① 摘白名单 白名单是一个个加的，运维规范 从数据库侧去掉该业务的来源白名单 该业务全部连接失败
              ② 删独立账号 + 断连接 新功能用单独数据库用户 DROP USER 后断开现有连接 该用户所有功能不可用
              ③ query_rewrite 成 select 1 新功能与主体混部，只能按语句拦 把压力最大的 SQL 模板直接改写 同模板的其他功能被误伤；后续业务逻辑因拿不到数据一起失败

              方案 ③ 的风险有两层：误伤（别的功能也用这个模板）和连锁失败（业务不是靠一条语句完成的，返回 select 1 会让后面的逻辑全错）。所以它是止血手段里优先级最低的一个，只在没有别的选择时用。

              🔑 方案 ① 和 ② 都依赖平时攒下的运维体系：虚拟化、白名单、业务账号分离。应急时的选项数量，是平时规范程度的函数。

              innodb_thread_concurrency：一道会把正常查询挡在门外的闸门

              这个参数控制同时进入 InnoDB 引擎执行的线程数上限，不是连接数上限：

              • 默认值 0，表示不限制；
              • 不限制并不好：CPU 核数有限，线程全冲进来，上下文切换成本会吃掉吞吐；
              • 通常建议设成 64~128；
              • 「几千个连接」和「几千个并发查询」是两件事：几千个连接只是多占内存，并发查询才是 CPU 杀手。

              它有两个反直觉的设计，必须一起理解：

              设计 行为 为什么
              等锁的线程不计数 进入行锁/间隙锁等待时，并发计数减一 等锁不吃 CPU；若计数不减，128 个等锁线程会把槽位占满，持锁线程反而进不来，系统死锁
              SLEEP() 之类的执行仍计数 语句真在执行就占槽位 它确实在消耗执行资源
              请求被挡在门外时 select 1 仍成功 select 1 不进 InnoDB 用 select 1 做健康检查会得到假阳性

              原文的死锁推演：线程 1 BEGIN; UPDATE ... WHERE id=1 后空闲（不计数）；线程 2~129 都更新同一行，进入锁等待（若计数，则占满 128 个槽位）；此时线程 1 想提交却进不了引擎——所有人都活着，系统却死了。所以「等锁减一」不是优化，是正确性要求。

              ⚠️ 把 innodb_thread_concurrency 设小，等于让正常查询在门口排队。本机实测：两条同样的 10 表自连接并行执行，innodb_thread_concurrency=0 时合计 2.583s，设成 1 后变成 3.816s（+48%）——两条语句只能串行。它适合「压住 CPU 不让雪崩」的极端场景，不适合当日常限流阀；设完必须尽快调回 0。

              大事务：kill 之前先算回滚账

              大事务的伤害不在「执行慢」，在它把资源占住的时间长：

              1. 锁：改过的每一行都持行锁到提交，别人改同一批行只能等；
              2. undo：每个旧版本都要保留给 MVCC，undo 表空间持续膨胀，回滚段越来越长（MVCC 与版本链见 44.10 事务与隔离级别）；
              3. 回滚：一旦失败或被 kill，要把这些版本逐个回收，成本与被改行数成正比。

              判断一个事务有多大，只看 information_schema.innodb_trx 的四个字段：

              字段 含义 怎么用
              trx_started 事务开始时间 找「活得太久」的事务，按它排序
              trx_rows_modified 已修改行数 回滚成本的直接估计；几十万就要先算账
              trx_mysql_thread_id 执行该事务的线程 id 与 PROCESSLIST.Id / performance_schema.threads 对齐，才能 kill 对人
              trx_state RUNNING / ROLLING BACK / PREPARED 判断「在执行」还是「已经在回滚」
              trx_is_read_only 是否只读事务 只读事务也会出现在这张表里，别误判

              两个容易误判的现象：

              • 只读事务也在表里：START TRANSACTION READ ONLY 之后做一次查询，innodb_trx 里就有一行，trx_state=RUNNING、trx_rows_modified=0、trx_is_read_only=1。它不是大事务，但会占着快照、阻止 purge 推进。
              • 事务在、连接不在：XA PREPARE 之后，事务行还在，trx_mysql_thread_id=0，PROCESSLIST 里找不到对应查询。gh-ost / pt-osc 这类工具用内部线程应用 binlog 时也会出现「innodb_trx 有 RUNNING，PROCESSLIST 里对不上号」——这时不要按客户端连接去 kill，先按 trx_mysql_thread_id 能不能对上人来判断。

              实测：200,000 行的事务被 kill 之后

              本机造一个不提交的长事务：

              -- session A（MySQL 8.0.46，本机实测）
BEGIN;
UPDATE luban.t SET c = c + 1 WHERE id <= 200000;   -- 不提交
SELECT SLEEP(300);                                  -- 让事务停在打开状态

              另一个 session 里看到：

              trx_id  trx_state  trx_started          trx_rows_modified  trx_mysql_thread_id
1821    RUNNING    2026-11-28 05:32:51  200000             17

              data_locks 里对应的锁记录有 200,377 行（1 行表级 IX + 20 万行 X 记录锁 + 间隙锁与 supremum 锁）。此时执行 KILL CONNECTION 17，trx_state 立刻变成 ROLLING BACK，trx_rows_modified 每 0.5 秒采样一次：

              2026-11-28 05:33:02.011  ROLLING BACK  176963  rollback
2026-11-28 05:33:02.631  ROLLING BACK   69686  rollback
2026-11-28 05:33:03.284  ROLLING BACK   13205  rollback
（下一次采样：事务已消失）

              20 万行的回滚用了约 2 秒，比更新本身还久。行数再上一个数量级，就是分钟级——这期间锁还在，别人还在等。

              🔑 kill 大事务不是「取消」，是「换一种方式把同样的工作量做完」：更新时要写 undo/redo，回滚时要把它们再读一遍、写一遍。行数越大，kill 越像自伤。

              已经杀了，就别再重启

              如果事务已经进入 ROLLING BACK：

              • 对已经在 ROLLING BACK 的事务再发 KILL 没有额外效果，连接已经断了，能做的只有等；
              • 强行重启 mysqld 不会让它更快——崩溃恢复仍然要把未提交事务回滚完；
              • 从恢复速度看，让它自己走完更快；
              • 如果它占着锁或 IO 已经影响别的语句，正确动作是先做主备切换，把流量切到新主库，旧实例上的回滚让它自己跑完。切换后别的线程断开，压力自然下降，回滚也会更快。

              真正该做的是事前消除大事务：批量更新拆批、DELETE 分批、避免一次改几十万行。

              临时表加速：用一次物化换掉 N 次重复计算

              有一类慢查询，加索引不合适（大表上低频字段）、改语句也救不了（连接算法本身差）。这时的应急手段是在 DB 内把中间结果落成一张带索引的临时表，让后续查询走索引而不是反复做条件判断。

              原文的实测场景：t1 1,000 行，t2 100 万行，t1.b = t2.b 且 t2.b 在 [1,2000] 之间。不做处理时走 BNL，等值条件要判断 1000 × 100 万 = 10 亿次，执行 1 分 11 秒。改成三步：

              -- MySQL 8.0，本机未跑这套数据（原文数据：t1 1000 行 / t2 100 万行）
CREATE TEMPORARY TABLE temp_t (
  id INT PRIMARY KEY, a INT, b INT, INDEX(b)
) ENGINE=InnoDB;

INSERT INTO temp_t
SELECT * FROM t2 WHERE b >= 1 AND b <= 2000;   -- 只物化 2000 行

SELECT * FROM t1 JOIN temp_t ON t1.b = temp_t.b;

              三步总耗时不到 1 秒。代价被拆得清清楚楚：INSERT 对 t2 做一次全表扫描（100 万行），join 扫描 t1 1,000 行 + 1,000 次带索引的查找。10 亿次判断变成 1,000 次索引查找——这是「临时表 + 索引」触发 BKA 的全部意义。

              维度 直接 join 临时表 + 索引
              条件判断次数 10 亿 1,000 次索引查找
              对大表的 schema 变更 无 无（不用加索引）
              额外写放大 0 物化 2,000 行
              额外空间 0 临时表（内存或 tmpdir）
              可复用性 — 仅当前会话，断开即消失

              适用与不适用要分清：

              适用 不适用
              中间结果能提前过滤到很小（几千行量级） 中间结果本身很大（物化成本 > 省下的判断）
              大表上不该为低频查询加永久索引 需要跨会话复用（临时表会话级，别人看不见）
              一次性分析/报表/应急查询 高频在线事务（每次物化都是额外 IO）

              🔑 临时表加速的本质是「用一次物化，换掉 N 次重复计算」。判断能不能用，只看一条：过滤后的中间结果，是否小到值得单独建索引。

              kill 不掉：置位、埋点、终止逻辑

              MySQL 有两个 kill：

              命令 语义 事务会回滚吗 客户端连接
              KILL QUERY <id> 终止该线程正在执行的语句 不会，事务还在 保留
              KILL CONNECTION <id> 断开连接；若有语句在执行，先停语句 会（连接断开时未提交事务回滚） 断开

              connection 可以省略，KILL <id> 等价于 KILL CONNECTION <id>。

              它不是「停止」，是「通知 + 等它自己停」

              执行 KILL QUERY 时，处理 kill 的线程只做两件事：

              1. 把目标线程的状态改成 THD::KILL_QUERY（把 killed 变量赋值）；
              2. 给目标线程发一个信号。

              发信号是因为目标线程可能正在等锁——只改状态它看不见，信号把它从等待里叫醒去检查状态。这里隐含三层意思：

              1. 语句执行过程中有多个「埋点」，只有走到埋点才会检查 THD::KILL_QUERY 并进入终止逻辑；
              2. 如果处于等待，这个等待必须是可被唤醒的，否则根本走不到埋点；
              3. 从进入终止逻辑到终止完成，本身要花时间。

              所以 KILL 之后 PROCESSLIST 里看到 Command=Killed，意思是**「状态已置位」**，不是「已经停了」。

              两类「kill 不掉」，机制不同

              类型 卡在哪 典型场景 表现
              ① 走不到埋点 等待不可唤醒，或循环里不检查 killed 等 InnoDB 并发槽位（每 10ms 判断一次能否进入，然后 nanosleep）；IO 卡住，读写函数不返回；网络写阻塞在等客户端收 KILL QUERY 无效；KILL CONNECTION 只断开网络，服务端语句照跑
              ② 终止逻辑耗时长 进入终止逻辑了，但收尾很慢 超大事务回滚、大查询删临时文件、DDL 到最后阶段清中间文件 Command=Killed 长时间不变

              原文的例子属于 ①：SET GLOBAL innodb_thread_concurrency=2; 之后第三个会话进不了 InnoDB，等待循环每 10 毫秒判断一次能否进入、不行就 nanosleep，这个循环不检查线程状态，所以 KILL QUERY 不生效；KILL CONNECTION 关掉网络后，Command 显示 Killed，但服务端仍在等槽位。只有当它真正进入 InnoDB、继续执行并走到埋点，才可能退出。

              💡 show processlist 里 Command 显示 Killed 有一条特殊逻辑：线程状态是 KILL_CONNECTION 就把 Command 列显示成 Killed。所以这一列反映的是「状态位」，不是「执行进度」。

              实测一：Sending to client 时 KILL QUERY 真的杀不掉

              本机造一个 60.5 MB 的结果集（20 万行 × 300 字节），用 mysql --quick 流式读取，但让下游管道不读：

              # 客户端读一行写一行，写不出去就停住，于是不再读 socket
mysql -h127.0.0.1 -P33199 -uroot -N --quick \
  -e "SELECT * FROM luban.big" | (sleep 40; wc -c)

              服务端 PROCESSLIST 显示（id、time 每次不同，下同）：

              id  command  time  state              info
65  Query      4   Sending to client  SELECT * FROM luban.big

              此时 KILL QUERY 65，等 2 秒再看：

              id  command  time  state              info
65  Query     10   Sending to client  SELECT * FROM luban.big

              线程还在，状态没变。因为服务端正阻塞在网络写（等客户端把 socket 收走），写调用返回之前走不到检查 killed 的埋点。接着 KILL CONNECTION 65：

              still_there
0

              连接断开让写操作失败返回，线程才退出。这就是「KILL QUERY 无效、KILL CONNECTION 才有效」的可复现版本。

              实测二：并发槽位等待在 8.0.46 已能被打断

              按原文的 5.7 场景复现：innodb_thread_concurrency=1，第一条长查询占住槽位，第二条在门口等。本机在它等槽位时发 KILL QUERY，返回的是中断错误，而不是等槽位释放后才退出：

              ERROR 1317 (70100) at line 1: Query execution was interrupted

              也就是说，原文「并发槽位等待循环不检查 kill 状态」的问题，在 8.0.46 上未复现：等待已经可以被 kill 打断。结论要按版本写：

              版本 并发槽位等待中的 KILL QUERY 依据
              5.7（原文场景） 无效，Command=Killed 长期挂着 原文第 32 讲
              8.0.46（本机） 有效，返回 1317 本机实测
              网络写阻塞（各版本） 无效，必须 KILL CONNECTION 本机实测（见上）

              所以「kill 不掉」不能一概而论，要落到它卡在哪个等待点。

              State 怎么读：Sending data 是历史包袱

              原文反复强调的一个误读：Sending data 不等于「正在发送数据」。查询进入执行阶段后状态先被设成 Sending data，然后发送列信息（meta data）、继续执行、完成后置空。所以执行器过程中的任意阶段都可能是 Sending data，等锁时也是。真正表示「等服务端网络栈可写」的是 Sending to client。

              在 8.0.46 上，状态名已经细化，实测对不上原文的名字：

              场景 5.7（原文） 8.0.46（本机实测）
              客户端不收结果、服务端写阻塞 Sending to client Sending to client
              执行中的普通查询 Sending data executing
              等行锁的 SELECT ... FOR UPDATE Sending data statistics
              会话空闲 Sleep Sleep
              已置位 kill、还没退出 Killed Killed（Command 列）

              ⚠️ 别用 State 文本判断「是不是在等锁」。本机等锁的 SELECT ... FOR UPDATE 显示 statistics，看字面会以为是优化器在统计。可靠判据是 performance_schema.data_locks 里有没有 LOCK_STATUS='WAITING'，以及 innodb_trx 的 trx_state。

              处置顺序：先改环境，再等它自己结束

              一个线程处于 Killed 之后，你能做的其实只有「改善它等待的条件」：

              1. 若是并发槽位问题：临时调大 innodb_thread_concurrency，或停掉别的线程腾位置；
              2. 若是 IO 受限导致回滚/删临时文件慢：降低系统压力，让它拿到 IO；
              3. 若它占着锁影响别人：先做主备切换，把流量切走，再让旧实例慢慢回滚；
              4. 做完这些，只能等。反复 kill 不会加速，重启也不会让回滚消失。

              🔑 能被 kill 掉的语句，是「走得到埋点 + 终止逻辑跑得完」的语句。判断 kill 是否生效，不要看 Command，要看线程是否从 PROCESSLIST 消失、innodb_trx 里那行是否消失。

              内存打爆：server 层边算边发，InnoDB 有 LRU 隔离

              先回答那个经典问题：主机内存 100G，对一个 200G 的表做全表扫描，会不会把数据库内存用光？

              不会。逻辑备份就是整库扫描，如果扫一遍就 OOM，备份早就跑不起来了。原因是 MySQL 发结果的方式是「边读边发」。

              结果集不落在服务端：net_buffer 的四个步骤

              1. 取一行，写到 net_buffer；这块内存大小由 net_buffer_length 决定，默认 16KB；
              2. 重复取行，直到 net_buffer 写满，调用网络接口发出去；
              3. 发送成功就清空 net_buffer，继续取下一行；
              4. 如果发送函数返回 EAGAIN 或 WSAEWOULDBLOCK，说明本地网络栈（socket send buffer）写满了，进入等待，直到网络栈重新可写。

              由此得到两个上限：

              • 一个查询在发送过程中，占用的 MySQL 内部内存最大就是 net_buffer_length 这么大，不会到 200G；
              • socket send buffer 也不可能到 200G（默认由 /proc/sys/net/core/wmem_default 决定，量级是几 MB）；写满就暂停读数据。

              🔑 「边读边发」是这套内存结论的全部基础。它同时意味着：客户端收得慢，会拖长服务端这条语句的执行时间——内存没炸，但语句一直不结束。

              实测：60.5MB 结果集，RSS 只涨了 648KB

              本机 20 万行 × 300 字节，SUM(LENGTH(pad)+行开销) 合计 60.5MB。用不读下游的客户端拉这条查询，服务端停在 Sending to client。前后测 mysqld 的内存：

              指标 之前 发送阻塞时 差值
              mysqld 进程 VmRSS 529,212 KB 529,860 KB +648 KB
              容器 cgroup memory.current 740,827,136 B 750,477,312 B +9.2 MiB（主要是页缓存）

              60MB 的结果集经过服务端，常驻内存只多了不到 1MB——正好是「net_buffer 一批 + 网络栈缓冲」的量级。大结果集不会打爆服务端内存，它打爆的是客户端的接收侧（如果客户端用 mysql_store_result 把 60MB 全存本地）。

              Sending to client 与 net_buffer_length 的取舍

              看到大量线程处于 Sending to client，说明服务端网络栈写满、在等客户端收。可选动作：

              • 让业务优化查询、减少返回行数/列数（根治）；
              • 评估这么多返回结果是否合理；
              • 临时调大 net_buffer_length 止血。

              调大它的效果是：没发完的数据先缓存在 net_buffer 里，对执行器来说「已经写出去了」，语句可以结束、不再占着 MDL 读锁；网络栈仍在慢慢发。代价是每条连接多占内存，且这只掩盖了「客户端读得慢」的事实。

              参数 默认值 上限 说明
              net_buffer_length 16,384（16KB） 1GB 每连接一份；调大能减少 Sending to client 卡语句
              socket send buffer 几 MB（wmem_default） 内核参数决定 写满即暂停读数据

              原文答疑里的量级例子：业务平均查询结果是 10MB，把 net_buffer_length 改成 10MB，执行器就不会卡在「发不出去」上；但状态仍可能显示 Sending to client，只是语句已经执行完了。

              客户端侧：store_result 与 use_result 的选择

              接口 行为 适合 风险
              mysql_store_result（默认） 结果全部读进本地内存 结果集不大 结果大时客户端内存暴涨（原文有近 20GB 的案例）
              mysql_use_result（--quick） 读一行处理一行 结果集很大、可流式处理 客户端处理慢会阻塞服务端发送

              --quick 这个参数名容易被误解成「让服务端更快」，实际是让客户端更快，代价可能是服务端变慢。它有三个效果：

              1. 跳过表名自动补全（连接大库时更快，等价于 -A）；
              2. 不用本地内存缓存结果，避免客户端内存被大结果集吃掉；
              3. 不把执行命令记进本地命令历史文件。

              反过来，连接一个有几万张表的库时觉得「连接很慢」，通常不是服务端慢：客户端连上后会执行 SHOW DATABASES、SHOW TABLES，在本地建哈希表做补全。加 -A 或 --quick 就能跳过。

              每连接 buffer：真正会被「连接数」放大的内存

              net_buffer 只是每连接内存的一小项。下面这些参数都是每连接分配，乘以几千个连接就是另一个量级：

              参数 本机默认值 何时分配 放大方式
              net_buffer_length 16KB 每个连接 × 连接数
              sort_buffer_size 256KB 需要排序时 × 同时排序的线程数
              join_buffer_size 256KB 无索引 join 时 × 同时 join 的线程数
              read_buffer_size 128KB 顺序扫描/临时表 × 扫描线程数
              tmp_table_size 16MB 内存临时表 超出后落盘到 tmpdir

              所以「内存被打爆」的真实路径通常是：

              1. 连接数暴涨 × 每连接 buffer → 服务端 RSS 上升；
              2. 大排序/大 join 的临时表超过 tmp_table_size → 落到磁盘，打爆的是磁盘不是内存；
              3. innodb_buffer_pool_size 配得过大（超过物理内存的 80%）→ 挤占 OS 页缓存，触发系统 OOM；
              4. 客户端把结果全读进内存 → 客户端 OOM，服务端安然无恙。

              Buffer Pool：全表扫描为什么不会冲垮命中率

              innodb_buffer_pool_size 一般建议设为可用物理内存的 60%~80%。线上稳定服务要保证响应时间，Buffer Pool 命中率通常要在 99% 以上，可在 SHOW ENGINE INNODB STATUS 的 Buffer pool hit rate 看到。

              如果直接用朴素 LRU，扫一张 200G 的冷历史表会把 Buffer Pool 里的业务数据全部淘汰，命中率骤降。InnoDB 的改进是把 LRU 链表按 5:3 分成 young 和 old 两区（靠近头部 5/8 是 young，尾部 3/8 是 old），新读入的页先放 LRU_old：

              • old 区的页被访问时，若在链表中存在时间超过 1 秒（innodb_old_blocks_time=1000，单位毫秒），才移到链表头部；
              • 顺序扫描时，同一数据页的第一次和最后一次访问间隔不超过 1 秒，所以一直留在 old 区，很快被淘汰。

              结果：全表扫描用到了 Buffer Pool，但对 young 区几乎没有影响，业务查询命中率保住了。注意这是「单次扫描」的结论：连续两次全表扫描、间隔超过 1 秒，仍会覆盖 young 区。

              用 performance_schema 找内存去了哪

              memory_summary_by_thread_by_event_name 按线程 + 内存事件统计当前占用，适合抓「哪个连接在漏内存」：

              -- 按线程汇总当前占用（MySQL 8.0，本机实测）
SELECT THREAD_ID, SUM(CURRENT_NUMBER_OF_BYTES_USED) AS bytes_used
FROM performance_schema.memory_summary_by_thread_by_event_name
GROUP BY THREAD_ID
ORDER BY bytes_used DESC
LIMIT 6;

              本机在 60MB 结果集发送阻塞时的结果：占用最高的是线程 1（约 1.8MB），整个实例按线程统计加起来只有几 MB，而 RSS 是 529MB。原因有两条，读这张表时必须知道：

              • Buffer Pool 不按线程记账，它不在这个视图里；
              • 小额的 net_buffer 分配可能记在别的线程/事件下，甚至未 instrument，别指望在这里看到 16KB 的 buffer。

              所以它的正确用法是：查每连接 buffer 的异常放大（排序、join、临时表），不是查 Buffer Pool。看 Buffer Pool 用 SHOW ENGINE INNODB STATUS 和 information_schema.INNODB_BUFFER_POOL_STATS。

              💡 一台机器上 mysqld 往往是唯一的内存大户（原文评论区有一个 132.1g VIRT / 111.8g RES / 88.9% MEM 的实例）。看到 RSS 高，先分清是「预算内」的 Buffer Pool，还是「预算外」的每连接 buffer / 临时表——两者的处置完全相反：前者是配置，后者是连接数与 SQL 形态。

              一条命令看全：值班巡检 SQL

              上面所有判断，可以合成一条查询，10 秒内给出「连接、执行、阻塞、事务」四个维度。前置条件：MySQL 8.0（用到 performance_schema.data_locks，5.7 叫 information_schema.innodb_locks）。

              -- MySQL 8.0，只读查询，不改变实例状态
SELECT
  (SELECT COUNT(*) FROM information_schema.processlist)                               AS threads_connected,
  (SELECT @@max_connections)                                                          AS max_connections,
  (SELECT COUNT(*) FROM information_schema.processlist WHERE command = 'Query')        AS threads_running,
  (SELECT COUNT(*) FROM information_schema.processlist WHERE state = 'Sending to client') AS sending_to_client,
  (SELECT COUNT(*) FROM information_schema.innodb_trx)                                 AS open_trx,
  (SELECT COUNT(*) FROM information_schema.innodb_trx WHERE trx_rows_modified > 10000) AS big_trx,
  (SELECT COUNT(*) FROM performance_schema.data_locks WHERE lock_status = 'WAITING')   AS lock_waiters;

              本机在「一个 5 万行未提交事务 + 一个 60MB 结果集发送阻塞」的负载下，真实输出：

              +-------------------+-----------------+-----------------+-------------------+----------+---------+--------------+
| threads_connected | max_connections | threads_running | sending_to_client | open_trx | big_trx | lock_waiters |
+-------------------+-----------------+-----------------+-------------------+----------+---------+--------------+
|                 4 |             200 |               3 |                 1 |        2 |       1 |            0 |
+-------------------+-----------------+-----------------+-------------------+----------+---------+--------------+

              怎么读这一行：

              指标 这一行的值 判读
              threads_connected / max_connections 4 / 200 连接数不紧张，问题不在短连接
              threads_running 3 有 3 条语句真在执行，不是排队
              sending_to_client 1 有一条在等客户端收结果，客户端是瓶颈
              open_trx 2 注意：那个大查询的一致性读也算一个事务
              big_trx 1 5 万行未提交，kill 前先算回滚成本
              lock_waiters 0 此刻没有锁等待

              每个应急开关的回退命令

              有损操作必须成对出现，否则「临时」会变成永久：

              操作 回退命令 生效范围
              调小 wait_timeout SET GLOBAL wait_timeout = 28800; 新连接
              调大 max_connections SET GLOBAL max_connections = 200; 新连接
              设小 innodb_thread_concurrency SET GLOBAL innodb_thread_concurrency = 0; 立即
              调大 net_buffer_length SET GLOBAL net_buffer_length = 16384; 新连接
              加 force index / 改写规则 DELETE FROM query_rewrite.rewrite_rules WHERE rule_id = ?; 后 CALL query_rewrite.flush_rewrite_rules(); 立即

              完整脚本在仓库 tools/examples/44.30-mysql-emergency/，bash code/run.sh 可复现本节的巡检、长事务回滚、Sending to client 与状态计数器四组输出。

              ⚠️ 应急操作要留痕：谁、几点、改了哪个参数、回退条件是什么。没有回退时间的开关，本质上是在给下一次故障埋引信。

              边界说明：误删恢复、自增 ID 耗尽、分区表、grant 与权限的处置在 44.25 MySQL 运维与故障处置；复制与高可用故障（主库切走、延迟）在 44.13 主从复制与读写分离。本节只讲「高峰期把系统从雪崩边缘拉回来」的判据与手段。

              反模式

              反模式 后果
              连接数打满就调大 max_connections 建连鉴权挤占 CPU，已连接线程更拿不到 CPU，吞吐反而下降
              用 SELECT 1 做健康检查 并发槽位被占满时它照样成功，探活全绿而业务全超时
              不看 trx_rows_modified 就 KILL 几十万行的回滚可能比原更新更久，锁还继续占着
              kill 之后立刻让业务重试 回滚没走完，新事务排队等同一批行锁，故障时间翻倍
              高峰在主库直接 ALTER TABLE 加索引 DDL 与业务抢 IO/CPU；正确姿势是备库加完再切
              force index 只加不删 索引改名/删除后语句直接报错，从「慢」升级成「不可用」
              把 query_rewrite 成 select 1 当常规手段 同模板语句被误伤，后续业务逻辑拿不到数据一起失败
              把 innodb_thread_concurrency 当日常限流阀 正常查询在引擎门口排队（实测 +48% 耗时），且健康检查看不出来
              大结果集用 store_result 全量读进客户端 服务端没事，客户端内存被打爆（原文有近 20GB 的案例）
              看到 Sending data 就认定「在发数据」 它可能只是在执行或等锁；8.0.46 里等锁甚至显示 statistics
              innodb_buffer_pool_size 配到物理内存 90% 以上 挤占 OS 页缓存，触发系统级 OOM，MySQL 被内核杀
              用 --skip-grant-tables 救连接风暴 整个实例失去权限系统；8.0 默认只能本地连

              自检

              Q1 一条 SELECT 已经 KILL QUERY，Command 显示 Killed，两秒后线程还在，State=Sending to client。它为什么没停？下一步做什么？如果换成一条在等行锁的 UPDATE，结论一样吗？

              ▸ 答案：不一样。Sending to client 表示服务端阻塞在网络写（客户端不收结果），写调用返回之前走不到检查 killed 的埋点，所以 KILL QUERY 只是置了位。下一步是 KILL CONNECTION：断开连接让写失败返回，线程才退出（本机实测：KILL QUERY 后 2 秒仍在，KILL CONNECTION 后立刻消失）。等行锁的 UPDATE 不同：行锁等待用的是可被唤醒的等待（pthread_cond_timedwait），信号能把它叫醒去检查状态，所以 KILL QUERY 通常有效。

              Q2 两个连接在 SHOW PROCESSLIST 里都是 Sleep，只能踢一个，踢哪个？你怎么在 3 秒内判断？

              ▸ 答案：踢不在事务里的那个。Sleep 只说明当前没执行语句，不区分「事务外空闲」和「BEGIN 之后没提交」。查 information_schema.innodb_trx：trx_mysql_thread_id 出现在里面的，就是事务内空闲，踢它等于触发回滚，改过的行越多回滚越久；不在里面的，踢掉几乎无感。所以先踢「不在 innodb_trx 结果里」的，还不够再动事务内的。

              Q3 一个事务 trx_rows_modified=300000，业务催「快杀掉，库卡死了」。你杀不杀？给出判据和动作顺序。

              ▸ 答案：先不杀，先算账。30 万行的回滚成本与被改行数成正比，本机 20 万行回滚用了约 2 秒且期间持续持锁；30 万行只会更久，而它现在至少还在向前推进。动作顺序：① 看它是否真的阻塞了别的语句（data_locks 里 WAITING 的会话数）；② 若阻塞面小，让它跑完或让它提交；③ 若阻塞面大，先做主备切换把流量切走，再决定是否 kill，杀完也只能等回滚结束；④ 重启不解决问题，崩溃恢复仍要回滚。

              Q4 有人把 innodb_thread_concurrency 设成 16「保护 CPU」，随后业务所有查询超时，但监控探活 SELECT 1 全部成功。怎么解释？

              ▸ 答案：SELECT 1 不进入 InnoDB，所以并发槽位满时它照样成功——探活是假阳性。16 个槽位被慢语句（或执行中的 SLEEP() 类语句）占满后，正常查询全部在引擎门口排队；等锁的线程虽然会减计数，但「真在执行」的不会。判据是 Threads_running 高、TPS 低、State 多为 executing，而不是连接数或 SELECT 1。处置：把 innodb_thread_concurrency 调回 0（或临时调大）让排队释放，同时找出占槽的语句；它不是限流阀，是防雪崩的最后一道闸。

              Q5 "饮鸩止渴"的三条边界是什么？哪些应急手段必须等根因确认后才能用？

              ▸ 答案：三条边界：① 先确认不是"锁等待/复制延迟"这类可自愈的问题——对可自愈的故障动手，等于把短痛变长痛；② 只在业务可承受窗口内执行（先算清影响面：杀掉一个大事务会回滚多久、期间该表是否全表不可写）；③ 必须留下可回退的动作与时间点（kill 的会话 ID、改过的参数原值、切换前的位点）。必须等根因确认才能用的：kill 长事务、调低 innodb_thread_concurrency、主从切换、大量加从库——它们都会改变系统状态，掩盖现场，让事后复盘失去证据。
