                                        44.7 SQL 与查询优化

                                        一句话

                                        SQL 的语言层先保证语义对（执行顺序、NULL、分组、连接），优化层再让优化器少读页（选择性、覆盖索引、连接算法、子查询次数、深分页写法）——语义错了，再快的计划也是错的。

                                        来源：执行路径、连接算法（NLJ/BNL/BKA、MRR）、索引与子查询判据来自丁奇《MySQL 实战 45 讲》（极客时间，2019）第 34、35、44 讲；SQL 语言层（执行顺序、DDL、过滤、函数、聚集）来自陈旸《SQL 必知必会》（极客时间，2019）并做了 MySQL 8.0 复核；本节代码与推演为本机补充。

                                        调优的六个维度与一条硬约束：先选型，再改写，最后外援

                                        调优不是“先把索引加一遍”。先排除硬约束，再按改动半径从小到大排，顺序本身就是优先级：

                                        顺序 维度 主要动作 落点
                                        0 硬约束 CPU/内存/磁盘 IOPS、网络、预算 先排除“机器不够”
                                        1 选 DBMS 事务型/分析型/文档/时序；单机还是分布式 44.21 数据库选型方法
                                        2 表设计 3NF 为主、读多写少处反范式；字段类型能用数值不用字符，定长 CHAR、变长 VARCHAR 44.6 关系模型与范式
                                        3 逻辑查询优化 等价改写：子查询改连接、函数挪到常量侧、EXISTS/IN 按小表驱动、去掉多余 DISTINCT/ORDER BY 本节“SQL 语言层”
                                        4 物理查询优化 索引、联合索引顺序、覆盖索引、连接顺序与算法、统计信息 44.8、44.9
                                        5 缓存 旁路缓存、多级缓存；Redis 有持久化与丰富结构，Memcached 只有 KV 41.1 缓存模式
                                        6 库级 连接池、读写分离、分区、垂直/水平拆分 44.12、44.13、44.14

                                        🔑 “选择比努力更重要”：库选错、表设计错，后面加多少索引都是补丁；相反，改写 SQL 与加对索引通常不改架构，收益却最大。

                                        先看什么：除了慢日志，优先看**活动会话（Active Session）**与锁等待——活动会话持续很高说明并发打满或 SQL 堆积，锁等待高说明事务持锁太久；这两类问题加索引通常无效。监控四项：CPU、内存、I/O、活动会话，再对照历史基线判断是“真的忙”还是“被一条 SQL 拖住”。

                                        这一节不展开硬件/OS 参数（innodb_buffer_pool_size、IO 调度、NUMA 等）：它们属于“硬约束”层，先按 44.3 缓冲池 与 44.25 MySQL 运维 排查，再回到 SQL 层。

                                        一条 SQL 的执行路径

                                        SQL → 解析（语法/语义）→ 重写（视图展开、子查询展开）→ 优化器（选索引、选连接顺序与算法）
    → 执行器（按计划取行）→ 存储引擎（页读、缓冲池）

                                        你能影响的是“优化器有没有正确的信息”和“SQL 有没有给优化器留出选择”：统计信息是否新鲜、索引是否存在、谓词是否可下推、有没有隐式类型转换让索引失效。

                                        Oracle 把“解析”拆得更细：SQL 先做 Hash，在共享池的库缓存里找执行计划——命中叫软解析，直接执行；未命中才建解析树、生成计划，叫硬解析。所以高频常量 SQL（WHERE id=10001、id=10002…）会反复硬解析，把优化器打爆；改写成绑定变量 WHERE id=:id 能复用计划。代价是绑定变量可能让优化器忽略直方图，数据分布倾斜时计划反而变差——是否绑定要看分布是否均匀。MySQL 8.0 则直接删掉了查询缓存：表一更新缓存全清，写多的表上缓存只会增加失效开销。

                                        SQL 语言层：一条查询的八个阶段

                                        优化器再聪明，也只能在你写出的语义里选计划。先把语言层补齐：一条 SQL 的逻辑执行顺序、DDL 的约束、过滤与聚合的 NULL 语义。

                                        两个顺序，一张流水线

                                        书写顺序不能颠倒：

                                        SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT ...

                                        执行顺序却是另一条线（MySQL 与 Oracle 基本一致）：

                                        FROM/JOIN → WHERE → GROUP BY → 聚集函数 → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
                                        阶段 做什么 产出（虚拟表）
                                        1. FROM / JOIN 笛卡尔积 → ON 过滤 → 补外部行 vt1：原始行集
                                        2. WHERE 过滤行 vt2
                                        3. GROUP BY 分组，NULL 自成一组 vt3
                                        4. 聚集函数 COUNT/SUM/AVG/MIN/MAX 在每组内算完 组内聚合值
                                        5. HAVING 过滤组 vt4
                                        6. SELECT 取列、算表达式、起别名 vt5
                                        7. DISTINCT 对 SELECT 的整行组合去重 vt6
                                        8. ORDER BY / LIMIT 排序、截断 vt7

                                        这张流水线解释了三件常被背错的事：

                                        • SELECT 的别名在 WHERE 里不可见，在 HAVING/ORDER BY 里可见。因为 WHERE 在第 2 步，别名到第 6 步才产生；而聚集函数在第 4 步已经算完，所以 HAVING num > 1 能引用 COUNT(*) AS num。MySQL 允许 HAVING 引用别名，标准 SQL 不保证，跨库写法是把聚合表达式再写一遍。
                                        • DISTINCT 去重的是整行，不是“最后一个列”。SELECT DISTINCT attack_range, name 里 name 各不相同，结果仍是一行一个英雄；只选 attack_range 才是 2 行。
                                        • LIMIT 最后执行，但能提前停：结果只需 1 条且没有排序/聚合时，执行器找到一条就返回，不必扫完。

                                        DDL：结构即约束

                                        CREATE DATABASE nba;
CREATE TABLE player (
  player_id   INT UNSIGNED NOT NULL AUTO_INCREMENT,
  player_name VARCHAR(64)  NOT NULL,
  height      DECIMAL(3,2) DEFAULT 0.00,
  team_id     INT,
  PRIMARY KEY (player_id),
  UNIQUE KEY uk_player_name (player_name),
  CONSTRAINT fk_team FOREIGN KEY (team_id) REFERENCES team(team_id),
  CONSTRAINT ck_height CHECK (height >= 0 AND height < 3)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
                                        约束 语义 易错点
                                        主键 唯一 + 非空；一张表只能一个，可复合 不是“必须自增”；自增主键有耗尽风险
                                        外键 引用另一张表的主键，保证引用完整性 分库分表后数据库层做不到；高并发写要额外检查
                                        唯一 字段值唯一，可多个 唯一约束 = 约束 + 索引，不是“普通索引加个开关”
                                        NOT NULL 必须有值 与 DEFAULT 是两件事：有默认值仍可显式插 NULL（除非 NOT NULL）
                                        DEFAULT 未赋值时填默认 默认值不参与“是否为空”的判断
                                        CHECK 值必须满足表达式 MySQL 8.0.16 起才真正执行；之前只解析不生效

                                        四个版本/方言坑：

                                        • INT(11) 的 11 是显示宽度，不是精度；8.0.19 起标记弃用，别再拿它当“能存 11 位”。
                                        • MySQL 的 utf8 是 utf8mb3（最多 3 字节），emoji 要用 utf8mb4；utf8_general_ci 大小写不敏感，utf8_bin 敏感。
                                        • 改列名：MySQL 8.0 支持 ALTER TABLE t RENAME COLUMN old TO new；5.7 要用 CHANGE old new type。改类型用 MODIFY，改表名用 RENAME TO。
                                        • 外键不是“越多越好”：单机低并发、正确性优先时用它；分库分表、高并发写入、频繁级联更新时，按 2/8 原则把最耗资源的那部分外键拆到业务层。阿里《Java 开发手册》直接禁止外键与级联，理由是级联更新是强阻塞，可能引发更新风暴。

                                        SELECT 的四个易错点

                                        写法 结果 说明
                                        SELECT * 返回全部列 探索期方便；生产会破坏覆盖索引、增加网络传输
                                        SELECT name, DISTINCT range 语法错误 DISTINCT 必须紧跟在 SELECT 后
                                        SELECT 'WZRY' AS platform, name 常数列 字符串/字母必须加引号；数字可不加
                                        ORDER BY mp_max, hp_max DESC 先按 mp_max 升序，再按 hp_max 降序 ASC/DESC 只作用于紧挨着的那一列

                                        分页方言是跨库第一道坎：

                                        DBMS 写法 注意
                                        MySQL / PostgreSQL / SQLite LIMIT 5 / LIMIT 10,5 放语句最后
                                        SQL Server / Access SELECT TOP 5 ... 与 ORDER BY 配合
                                        DB2 FETCH FIRST 5 ROWS ONLY 标准写法
                                        Oracle WHERE ROWNUM <= 5 先取行再排序；要“最高的 5 个”必须套子查询先排序

                                        WHERE：三种武器与 NULL

                                        比较运算符（= <> != > < >= <= BETWEEN IS NULL IN LIKE）、逻辑运算符（AND OR NOT）、通配符（% _）。三条硬规则：

                                        1. AND 优先级高于 OR。a OR b AND c 是 a OR (b AND c)，不报错但结果少一批；跨条件一律加括号。
                                        2. NULL 参与的比较结果是 UNKNOWN，不是 TRUE/FALSE。NULL = NULL、NULL <> 1 都不成立；判空只能用 IS NULL/IS NOT NULL。NOT IN 的子查询里只要有一个 NULL，整个条件恒为 UNKNOWN、返回空集（见「子查询：先问它执行几次」的 NULL 陷阱）。
                                        3. LIKE 的 % 匹配 0 个或任意多个字符，_ 匹配恰好一个字符。LIKE '%太%' 与 LIKE '_%太%' 只差一个下划线，结果可能差一行。
                                        -- MySQL 8.0.46 实测
SELECT 'abc' LIKE '%', '' LIKE '%', NULL LIKE '%', 'a' LIKE '_';
-- 1 | 1 | NULL | 1

                                        LIKE '%' 看起来“匹配所有”，但 NULL 不匹配——WHERE col LIKE '%' 会漏掉 col IS NULL 的行。

                                        索引与 LIKE 的判据只有一条：模式是不是常量前缀。LIKE '太%' 可以按前缀定位区间；LIKE '%太%'、LIKE '%太' 的前缀是通配符，B+ 树无法定位，只能全表扫。

                                        函数：四类与可移植性

                                        类别 必记函数 语义/坑
                                        算术 ABS、MOD、ROUND(x,d) ROUND(37.25,1)=37.3
                                        字符串 CONCAT、LENGTH、CHAR_LENGTH、LOWER/UPPER、REPLACE、SUBSTRING LENGTH 是字节数，CHAR_LENGTH 是字符数：utf8mb4 下 LENGTH('你好')=6、CHAR_LENGTH('你好')=2
                                        日期 CURRENT_DATE/TIME/TIMESTAMP、EXTRACT、DATE DATE('2019-04-01 12:00:05')='2019-04-01'；格式必须是 yyyy-mm-dd
                                        转换 CAST、COALESCE COALESCE 返回第一个非 NULL；CAST 的目标类型各库不同

                                        两个必须按 MySQL 8.0 纠正的细节：

                                        • CAST(x AS INT) 在 MySQL 是语法错误，因为 CAST 允许的目标类型里没有 INT；要整数用 CAST(x AS SIGNED)，要保留小数用 DECIMAL(8,2)。
                                        • CAST(123.9 AS SIGNED) 的结果是 124（四舍五入），不是截断；金额不要用浮点/整数强转，直接用 DECIMAL。

                                        函数真正的风险不是“写错”，是可移植性和索引失效：

                                        • MySQL 用 CONCAT 拼串，Oracle 的 CONCAT 只接受两个参数（多个要用 ||），SQLite 用 ||；只有很少的函数被所有 DBMS 同时支持。
                                        • 在列上套函数（WHERE DATE(created_at)=...、WHERE SUBSTRING(name,1,3)=...）会让该列索引失效；正确做法是把函数挪到常量侧，或改写成 created_at >= '...' AND created_at < '...'、name LIKE 'abc%'。后者的实测差异见「函数改写：一个可复现的对照」与 44.9 执行计划。

                                        聚集函数：NULL、分组与 HAVING

                                        五个聚集函数：COUNT、SUM、AVG、MAX、MIN。输入多行，输出一个值。

                                        规则 结果
                                        COUNT(*) 统计行数，不管列是否为 NULL
                                        COUNT(col) 只统计 col IS NOT NULL 的行
                                        SUM/AVG/MAX/MIN 自动忽略 NULL 行；全是 NULL 时 SUM 返回 NULL、COUNT 返回 0
                                        GROUP BY col NULL 自成一组，不是被丢掉
                                        HAVING 过滤组；WHERE 过滤行，不能互换

                                        MySQL 8.0.46 实测（6 行，v 有 2 个 NULL）：

                                        SELECT COUNT(*) AS c_star, COUNT(v) AS c_v, AVG(v) AS avg_v FROM t;
-- 6 | 4 | 20.0000
SELECT grp, COUNT(*) FROM t GROUP BY grp;
-- NULL 2 / a 2 / b 2

                                        HAVING 引用 SELECT 别名在 MySQL 可行，因为聚集函数在 HAVING 之前算完；但把只涉及原始列的条件下推到 WHERE 更早减少行数：

                                        SELECT grp, COUNT(*) AS num
FROM t
WHERE v IS NOT NULL      -- 先筛行
GROUP BY grp
HAVING num > 1;          -- 再筛组

                                        ⚠️ MAX/MIN 也能用于字符串，但结果取决于排序规则（collation）。课程用 CONVERT(name USING gbk) 近似按拼音比较，这不是跨库通用做法；跨库要显式指定 collation 或把排序键单独存一列。

                                        COUNT 的三种写法

                                        COUNT(*)、COUNT(1)、COUNT(col) 常被排成“效率从高到低”，这是错的：

                                        • COUNT(*) 与 COUNT(1) 在 InnoDB 里本质相同：都要扫满足条件的行，复杂度 O(N)。
                                        • MyISAM 能 O(1)，因为表级锁保证 row_count 元数据一致；InnoDB 有 MVCC，不能只维护一个全局行数。
                                        • COUNT(col) 语义不同（只数非空），不能拿不同结果比效率。

                                        能优化的是走哪个索引：COUNT(*) 不需要取行，优化器会选占用空间更小的二级索引；有多个二级索引时选 key_len 小的，没有二级索引才扫聚簇索引。

                                        -- MySQL 8.0.46；big 表 3000 行，二级索引 idx_k
EXPLAIN SELECT COUNT(*) FROM big;
-- type=index, key=idx_k, key_len=5, Extra=Using index

                                        完整脚本与真实输出见 tools/examples/44.7-sql-semantics/count.sql。

                                        🔑 COUNT(*) 想快，不是改写成 COUNT(1)，而是让表上有一个窄的二级索引。这能把“扫整行”降成“扫索引页”。

                                        上面的 NULL/分组/长度结果可用一次性 MySQL 容器复现：完整脚本与真实输出在 tools/examples/44.7-sql-semantics，mysql < verify.sql 一条命令跑完。

                                        函数改写：一个可复现的对照

                                        -- 慢：列上套函数，索引失效
SELECT comment_id, comment_text, comment_time
FROM product_comment
WHERE SUBSTRING(comment_text, 1, 3) = 'abc';

-- 快：改成常量前缀，可用索引
SELECT comment_id, comment_text, comment_time
FROM product_comment
WHERE comment_text LIKE 'abc%';

                                        课程原文实测第二条耗时约为第一条的 1/10；44.9 里 DATE(created_at)=CURDATE() 与本机范围查的对比是 34.5ms vs 0.8ms，同一类问题的两个量级样本。判据不是“函数能不能用”，而是“函数有没有落在索引列上”。

                                        视图、存储过程与游标：逻辑放在哪一层

                                        SQL 是声明式语言，但业务里总有人想把“过程”塞进数据库。四种对象的边界先分清：

                                        对象 存什么 生命周期 主要价值 主要代价
                                        视图 一条 SELECT 的定义 持久，随库 封装查询、限制列、统一口径 不存数据，不加速；更新受限
                                        临时表 真实数据 连接/会话 存中间结果、拆复杂查询 占空间；连接池复用时要清理
                                        存储过程 SQL + 流控语句 持久，随库 少网络往返、一次编译、权限封装 不可移植、难调试、难版本管理
                                        游标 结果集上的指针 存储过程内 逐行处理、行间规则不同 逐行取数 + 加锁 + 内存，慢

                                        视图：存下来的是 SELECT，不是数据

                                        CREATE VIEW player_above_avg_height AS
SELECT player_id, player_name, height
FROM player
WHERE height > (SELECT AVG(height) FROM player);

ALTER VIEW player_above_avg_height AS
SELECT player_id, player_name, height, team_id
FROM player
WHERE height > (SELECT AVG(height) FROM player);

DROP VIEW player_above_avg_height;

                                        四个正当用途：只暴露部分列（薪酬字段不对所有人开放）、固定复杂连接、统一格式化（CONCAT(name,'(',team,')')）、把计算字段命名后复用。视图可以嵌套，但每嵌套一层就多一次展开。

                                        三条边界：

                                        • 视图不存数据，所以不提升查询速度。它省的是“写 SQL 的力气”，不是“算的力气”；要省算力用物化视图（32.2 物化视图）。
                                        • 不是所有视图都能改。单表、不含聚合/DISTINCT/GROUP BY/UNION/计算列的视图通常可更新；含聚合的视图执行 UPDATE 会报 ERROR 1288: The target table ... is not updatable（MySQL 8.0.46 实测）。生产上更常见的做法是“视图只读，写走原表”。
                                        • SQLite 只支持只读视图，改定义要先 DROP 再 CREATE。

                                        游标：逐行处理的最后手段

                                        游标五步，顺序不能乱：

                                        DELIMITER //
CREATE PROCEDURE calc_hp_sum()
BEGIN
  DECLARE hp INT;
  DECLARE hp_sum INT DEFAULT 0;
  DECLARE done INT DEFAULT FALSE;
  DECLARE cur CURSOR FOR SELECT hp_max FROM heros;
  DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = TRUE;

  OPEN cur;
  read_loop: LOOP
    FETCH cur INTO hp;
    IF done THEN LEAVE read_loop; END IF;
    SET hp_sum = hp_sum + hp;
  END LOOP;
  CLOSE cur;
  SELECT hp_sum;
END //
DELIMITER ;
                                        步骤 做什么 坑
                                        DECLARE 声明游标与 SELECT 只能在存储过程/函数/触发器内，不能裸执行
                                        OPEN 执行 SELECT，结果进游标工作区 这时才开始占内存
                                        FETCH 取当前行，指针下移 取到末尾之后继续取会报 1329，必须用 HANDLER FOR NOT FOUND
                                        CLOSE 关闭，释放结果集 关闭后不能再 FETCH
                                        DEALLOCATE 释放游标 不是 DEALLOCATE PREPARE；后者是预处理语句用的，游标用了会报 1243

                                        三条判据：

                                        1. 能一条集合 SQL 写出来的，不用游标。上面的累加就是反例：SELECT SUM(hp_max) FROM heros 一行就够。
                                        2. 能写成 CASE WHEN 的，不用游标。按行分档更新通常可以写成一条 UPDATE ... SET x = CASE WHEN ... END。
                                        3. 只有“每行规则不同且无法用 CASE 表达”或“多表嵌套查找、JOIN 计划确实更差”时才用；用的时候限制结果集、先备份、别在长事务里跑——游标会加锁、占内存，逐行 FETCH 还是逐次往返。

                                        数字一：索引的高度决定点查成本

                                        设定：1000 万行、每页放 100 行、B+ 树扇出 500。

                                        操作 页读次数
                                        B+ 树点查 3 次（根 + 内部 + 叶子）
                                        全表扫描 10 万页

                                        高度的算法：log₅₀₀(10,000,000) ≈ 2.6 → 向上取整 3 层。这就是“索引让点查从 O(N) 变 O(log N)”的具体数字：3 次页读 vs 10 万次。

                                        🔑 索引的收益来自“少读页”，不是“少读行”。一个回表查询读了 10 万行，但每行都触发一次随机页读，成本可能比顺序扫全表还高。

命中行数   = 10,000,000 × 2.74% × 40% ≈ 109,589 行（1.1%）

                                        执行路径 页读构成 估算成本
                                        全表扫描 10 万页顺序读 4000ms
                                        单列索引 (created_at) 回表 索引页 + 10.9 万次随机回表 11233ms
                                        联合索引 (status, created_at) 回表 索引页 + 10.9 万次随机回表 11068ms

                                        交叉点可以算出来：

                                        全表扫描成本 / 单次随机读成本 = 100,000 × 0.04 / 0.10 = 40,000 行 = 0.40%

                                        命中行数超过 0.40% 时，全表扫描通常更快。本例 1.1% 已超过，所以优化器大概率选全表扫描——除非有覆盖索引，或者能通过更好的谓词把选择率压下去。

                                        选择率 优化器倾向 你该做什么
                                        < 0.1% 索引 确保谓词可索引、无隐式转换
                                        0.1%–1% 看成本，可能走索引 用覆盖索引消除回表
                                        1%–10% 常走全表扫 减少返回列、加 LIMIT、分区
                                        > 10% 全表扫/分区裁剪 别指望索引，改查询或改模型

                                        数字三：连接算法差 6 个数量级

                                        1000 万订单 × 100 万用户，orders.user_id = users.id：

                                        算法 操作量 适用
                                        嵌套循环（无索引） 10⁷ × 10⁶ = 10¹³ 次比较 只适合小表
                                        哈希连接 10⁷ + 10⁶ = 1.1×10⁷ 大表等值连接，内存放得下 build 侧
                                        索引嵌套循环（INLJ） 10⁷ × 3 层 = 3×10⁷ 次页读 驱动表小、被驱动表有索引

                                        10¹³ 次比较在 10⁹ 次/秒的机器上也要 2.8 小时——所以“两张大表没索引做连接”不是慢，是跑不完。哈希连接把复杂度降到线性，代价是内存；INLJ 把“比较”换成“页读”，适合驱动表很小、每次都命中索引的查询。

                                        连接：五种形态，两个致命坑

                                        连接的语义只有三类：内连接（只留匹配）、外连接（主表全保留）、交叉连接（全组合）。SQL92 与 SQL99 的差别只在写法，不在语义——同一句内连接有两种写法，选错写法才会引入坑。

                                        形态 SQL92（FROM 多表 + WHERE） SQL99（JOIN + ON） 结果
                                        交叉连接 FROM player, team CROSS JOIN m × n 行：37 个球员 × 3 支球队 = 111 行
                                        等值连接 ... WHERE p.team_id = t.team_id JOIN team t ON p.team_id = t.team_id 只留匹配行（37 条）
                                        非等值连接 WHERE p.height BETWEEN h.lo AND h.hi ON p.height BETWEEN h.lo AND h.hi 条件用比较符，不是等号
                                        自连接 FROM player a, player b WHERE a.height > b.height JOIN player b ON a.height > b.height 同一张表两次：比格里芬高的有 6 人
                                        左/右外连接 WHERE p.team_id = t.team_id(+) LEFT / RIGHT JOIN ... ON 主表全保留，从表补 NULL
                                        全外连接 没有 FULL JOIN 两边都保留；MySQL 不支持

                                        SQL92 用 (+) 标记「从表」，是 Oracle 系写法，MySQL 不认。日常写法建议统一 SQL99：JOIN 一次连一张表，连接条件紧贴 ON，比把 5 张表堆在 FROM 后面再靠 WHERE 过滤容易读，也更容易看出「哪张表没写连接条件」。

                                        坑一：漏写连接条件，得到笛卡尔积

                                        37 × 3 = 111 行还能看；换两张真实表，10⁶ 订单 × 10⁵ 用户 = 10¹¹ 行，还没等过滤，临时目录先写满。SQL92 写法最容易犯：表加进 FROM 却忘了在 WHERE 里写条件。发现手段是 EXPLAIN 的 rows：几张表的 rows 相乘，基本就是你在算笛卡尔积。

                                        坑二：外连接的条件写进 WHERE，外连接退化成内连接

                                        外连接的定义是「主表保留全部行，从表没匹配就补 NULL」。一旦在 WHERE 里对从表的列加条件，NULL 行必然不满足，主表那部分行就被滤掉了——语义变回内连接：

                                        -- ① 全部 37 名球员；没有球队的球员，team_name 为 NULL
SELECT p.player_name, t.team_name
FROM player p LEFT JOIN team t ON p.team_id = t.team_id;

-- ② 只剩「湖人」的球员：对从表列加了 WHERE，NULL 行被滤掉 → 等价于内连接
SELECT p.player_name, t.team_name
FROM player p LEFT JOIN team t ON p.team_id = t.team_id
WHERE t.team_name = '湖人';

-- ③ 仍保留全部 37 人，只把「湖人」的队名填上，其余为 NULL
SELECT p.player_name, t.team_name
FROM player p LEFT JOIN team t
  ON p.team_id = t.team_id AND t.team_name = '湖人';

                                        判据只有一条：这个条件是用来「筛主表」还是「限制匹配」。筛主表 → WHERE；限制匹配、主表要全留 → ON。

                                        🔑 外连接的 ON 决定「能不能配上」，WHERE 决定「配完之后留不留」。把「限制匹配」的条件错写进 WHERE，SQL 不报错、结果少一批行——这类 bug 只有对数时才看得见。

                                        join 怎么执行：NLJ、BNL 与 BKA

                                        决定 join 快慢的不是 SQL 怎么写，而是被驱动表的连接列有没有索引：有索引走 NLJ（可优化成 BKA），没索引就掉进 BNL——每多一段 join_buffer，被驱动表就多扫一遍。

                                        算法 触发条件 扫描量 内存判断 判断
                                        Simple NLJ（理论模型） 无索引且不用 buffer N + N×M 0 MySQL 不用它
                                        NLJ（索引嵌套循环） 被驱动表连接列有索引 N + N×2log₂M 0 首选
                                        BNL（块嵌套循环） 被驱动表连接列无索引 N + K×M（K=分段数） N×M 尽量别用
                                        BKA（批量取键） NLJ + MRR 开启 同 NLJ，但按主键顺序回表 0 BNL 的替代方案

                                        《MySQL 实战 45 讲》用两张表算过账：t1 100 行、t2 1000 行，a 列有索引。

                                        语句 算法 总扫描行数 内存判断次数
                                        t1 straight_join t2 on t1.a=t2.a NLJ 200（100 + 100） —
                                        t1 straight_join t2 on t1.a=t2.b（b 无索引） BNL 1100（100 + 1000），join_buffer 不够时 t2 还要再扫 10 万次（100 × 1000）
                                        同上，join_buffer_size=1200 只放得下 88 行 BNL 分两段 t2 被扫 2 次 仍 10 万次（判断次数与分段无关）

                                        判断有没有掉进 BNL，看 EXPLAIN 的 Extra：出现 Using join buffer (Block Nested Loop) 就是 BNL；8.0 无索引等值连接可能显示 hash join。

                                        驱动表：永远让「小表」驱动

                                        算法 谁做驱动表 为什么
                                        NLJ 小表 成本 N + N×2log₂M，N 翻 1000 倍扫描翻 1000 倍，M 翻 1000 倍只涨不到 10 倍
                                        BNL（buffer 够） 都一样 扫描 M+N、判断 M×N，交换 M/N 无差别
                                        BNL（buffer 不够，更常见） 小表 扫描 N + λNM，N 越小分段越少，被驱动表扫的次数越少

                                        「小表」不是「行数少的表」，而是按各自条件过滤后、参与 join 的字段总数据量小的那个。《MySQL 实战 45 讲》的例子：两张表都只有 100 行参与 join，但一张只需带 b 一列、另一张要带全部字段——带一列的那张才是「小表」，应该做驱动表。

                                        掉进 BNL 之后的三条补救

                                        做法 怎么做 代价
                                        加索引（首选） 给被驱动表的连接列建索引，BNL 直接转 BKA 写放大；只被低频 SQL 用到就不划算
                                        临时表 先把过滤后的小结果集灌进带索引的临时表，再 join 多一次全表扫 + 建表开销
                                        应用层哈希 把驱动表结果建成 map，再逐行探测被驱动表 数据量必须能装进应用内存

                                        《MySQL 实战 45 讲》实测的对比（1000 行 × 100 万行、过滤后只剩 2000 行、低频 SQL）：直接 BNL 要判 10 亿次、跑 1 分 11 秒；换成「临时表 + 索引再 join」总耗时不到 1 秒。

                                        BNL 真正贵的地方：不只是慢

                                        副作用 机制 后果

                                        跨库、分库分表 单机 join 的判据不适用 见 44.14 分库分表

                                        straight_join 是这条判据的验证工具：

                                        -- 强制 t1 驱动 t2；只固定顺序，不固定算法
SELECT count(*) FROM t1 STRAIGHT_JOIN t2 ON t1.a = t2.a;

-- 对调：强制 t2 驱动 t1
SELECT count(*) FROM t2 STRAIGHT_JOIN t1 ON t1.a = t2.a;

                                        它的语义是「按书写顺序从左到右连接」，ON 条件照常生效。风险也在这里：顺序被写死，数据量、索引、统计信息一变，原来最优的顺序可能变最差；而且 SQL 里看不出这个顺序是「测过的」还是「抄来的」。只在两种场合用：排查阶段做 A/B，或已经用真实数据验证、并在代码里注明原因。它不改变算法——被驱动表没索引，straight_join 也救不了。

                                        🔑 join 不是原罪。三类真问题：被驱动表没索引、驱动表选错、外连接语义被 WHERE 改写。用 EXPLAIN 逐条排除，而不是一刀切禁用。

                                        本机实测（10,000 行 t1 × 100,000 行 t2，t2.a 有索引）：t1 驱动 t2 耗时 15.2–26.9ms，t2 驱动 t1 耗时 196–303ms，差约 10 倍；EXPLAIN 第一行的 rows 分别约 1 万和 10 万。

                                        join 的账单：N、M、K 与 join_buffer_size

                                        先把 EXPLAIN 的 rows 代进式子。N 是驱动表过滤后的行数，M 是被驱动表过滤后的行数，K 是 join_buffer 放不下时驱动表被切成的段数。

                                        算法 扫描行数 内存匹配次数 8.0.46 的 Extra
                                        Simple NLJ N×M（驱动表每行全扫一次被驱动表） 0（比较发生在页上） 无 join buffer
                                        NLJ N + N×2log₂M 0 无 join buffer，被驱动表 type=ref
                                        BNL（buffer 够） N + M M×N Using join buffer (Block Nested Loop)（5.7；8.0.18 前）
                                        BNL（分 K 段） N + K×M M×N 同上，K 由 buffer 决定
                                        hash join N + M（build + probe） 约 max(N,M) 次哈希查找 Using join buffer (hash join)（8.0.18+）

                                        2log₂M 的来历：每次到被驱动表匹配一行，先走二级索引 a 的 B+ 树，再走主键索引的 B+ 树回表，两棵树各约 log₂M 层（44.8 索引原理）。

                                        N 与 M 对成本的影响不对称：N 翻 1000 倍，扫描行数基本翻 1000 倍；M 翻 1000 倍，树只多约 10 层（log₂1000≈10），扫描行数涨不到 10 倍。这就是「小表驱动」的数学依据，不是经验口诀。

                                        语句 算法 扫描行数 匹配次数

                                        t1 straight_join t2 on t1.a=t2.b（b 无索引） Simple NLJ 理论值 100,000（100 × 1000） 100,000
                                        同上，实际 BNL BNL 1,100（100 + 1000） 100,000

                                        两个 10 万行的表、连接列无索引，Simple NLJ 要扫 10⁵ × 10⁵ = 10¹⁰ 行（100 亿）；BNL 把扫描降到 10⁵ + 10⁵，但内存判断仍是 100 亿次——BNL 省的是 IO 和页访问，不是 CPU 的比较次数。这也是为什么只调大 join_buffer_size 治不好大表 join。

                                        这三个式子的用途不是精确预测毫秒，而是排除「量级上不可能」的方案：算出 10¹⁰ 次比较，先别上线试，先加索引或改结构；算出 200 行的方案，才值得比较 NLJ 与 hash join 的常数项。

                                        K 不是常数：K = λN，λ∈(0,1)。扫描量是 N + λNM，λ 越小被驱动表被扫的次数越少；join_buffer_size 越大、每行参与 join 的列越少，λ 越小。判断次数的 M×N 与这两者都无关。

                                        join_buffer_size 默认 256K（本机 show variables 实测 262144 字节）。它是每个连接、每个 join 各分一块，不是全局共享；把它调到 4M，100 个并发 join 就可能多占 400M。所以调参前先确认两件事：EXPLAIN 确实有 Using join buffer，且慢在扫描/溢写而不是 M×N 比较。

                                        块大小按字节算，不按行数算：join_buffer_size=1200 放得下 88 行，意味着每行约 13.6 字节；select * 每行 3 个 int 就比只 select b 大 2–3 倍，K 也按比例涨。

                                        只 SELECT 参与 join 的列 变小 不变
                                        先过滤驱动表（WHERE） 变小 变小

                                        Simple NLJ 与 BNL 的判断次数相同，性能却差几个数量级，原因不在算法复杂度，在数据怎么被访问：

                                        维度 Simple NLJ BNL
                                        被驱动表访问次数 驱动表每行都全扫一次，N 次 每个 block 扫一次，K 次
                                        每次访问的数据 走 B+ 树/页，可能反复读磁盘 驱动表一次进 join_buffer，被驱动表顺序扫
                                        内存里的结构 页内记录，找下一条像指针跳转 无序数组，连续遍历，CPU 缓存友好
                                        buffer pool 反复读冷页，冷页反复进 LRU，挤掉热页 每个 block 只顺序读一遍

                                        课程答疑里的原话是：即使被驱动表的数据都在内存里，Simple NLJ 每次找「下一条记录」也是类似指针的操作；join_buffer 是数组，遍历成本更低。再叠加多次全表扫描把冷页推进 buffer pool 的 old/young 区，热数据被淘汰，命中率掉下来（44.3 缓冲池与页面管理）。

                                        join 优化四板斧：索引、小表、BKA/MRR、临时表

                                        板斧 动作 生效标志 代价与边界
                                        ① 给被驱动表加索引 在连接列建索引 被驱动表 type=ref；Extra 无 join buffer 或出现 BKA 写放大；低频 SQL 不值得
                                        ② 小表驱动 按过滤后参与 join 的列数据量选驱动表 EXPLAIN 第一行是过滤后更小的表 统计信息过期会选错
                                        ③ BNL→BKA/MRR 开 batched_key_access，必要时 mrr_cost_based=off Using join buffer (Batched Key Access)、Using MRR BKA 依赖 MRR，只在 NLJ 上有效
                                        ④ 临时表 先过滤出小结果集、建索引、再 join 临时表 type=ref 多一次全表扫 + 建表；高频不划算
                                        ⑤ hash join 8.0.18+ 自动 Using join buffer (hash join) 版本差异；内存不够会溢写/分批

                                        MRR：把回表变成按主键顺序读

                                        MRR 不是 join 算法，是回表优化。走二级索引拿到一批主键后，如果按索引顺序逐个回表，主键是乱的，就是随机读；MRR 先把主键放进 read_rnd_buffer，按主键递增排序，再批量回表，把随机读尽量变成顺序读。

                                        成立条件有四个：① 二级索引上是范围/多值查询，能拿到一批主键，单行点查没有排序收益；② 需要回表，覆盖索引不需要；③ mrr=on；④ 想稳定触发要 mrr_cost_based=off，因为优化器算成本时常常觉得 MRR 不划算，默认会放弃。read_rnd_buffer_size 控制这一批的大小。

                                        SET optimizer_switch='mrr=on,mrr_cost_based=on';   -- Extra: Using index condition
SET optimizer_switch='mrr=on,mrr_cost_based=off';  -- Extra: Using index condition; Using MRR

                                        本机 8.0.46 对 t3（10,000 行，a 列逆序、有索引，范围 1,000 行）实测，Extra 从 Using index condition 变成 Using index condition; Using MRR。代价是排序和一块 read_rnd_buffer 内存；范围很小、主键本来就有序时，MRR 是白忙。范围查出来的主键很稀疏时也一样：排序后相邻 id 仍隔很远，顺序读的收益被抵消。mrr_cost_based=on 时优化器会算这笔账，强制 off 前先用 EXPLAIN ANALYZE 对比。

                                        BKA：把 NLJ 的「一次一个值」变成「一批值」

                                        NLJ 每次只把驱动表一行的连接键传给被驱动表，MRR 的批量优势用不上。BKA 把驱动表的一批行先放进 join_buffer，批量取键，再让被驱动表按 MRR 的方式回表。它复用了 BNL 的 join_buffer，所以名字叫 Batched Key Access。

                                        SET optimizer_switch='mrr=on,mrr_cost_based=off,batched_key_access=on';

                                        三个参数缺一不可：mrr=on 打开 MRR，mrr_cost_based=off 强制用它，batched_key_access=on 才允许 BKA。本机实测同一句 join：

                                        开关 EXPLAIN 的 Extra
                                        BKA 关 NULL（普通 NLJ）
                                        BKA 开，select t2.b Using join buffer (Batched Key Access)
                                        BKA 开，select count(*) Using index（覆盖索引，不回表，BKA 不触发）

                                        最后一行是判断 BKA 有没有生效的关键：BKA 的收益来自回表。count(*) 只读索引就能完成，没有回表，优化器不会为它开 BKA。另一个边界是：BKA 只能优化 NLJ；被驱动表没索引、走 BNL/hash join 时，先加索引，BKA 本身不解决无索引问题。三表 join 时每多一个 join 就多一个 join_buffer，内存账要按 join 个数乘，不是按语句数乘。

                                        临时表：低频 SQL 的「一次性索引」

                                        课程的例子是 1,000 行 t1 join 100 万行 t2，过滤后 t2 只有 2,000 行参与，且这条 SQL 是低频的。直接 BNL 要做 10 亿次判断，原文实测 1 分 11 秒；改成「先把 2,000 行灌进带索引的临时表，再 join」，三条语句总耗时不到 1 秒（原文数据，5.7 时代，本机 8.0.46 已是 hash join，未复现这组数字）。

                                        CREATE TEMPORARY TABLE tmp_t (id INT PRIMARY KEY, a INT, b INT, INDEX(b)) ENGINE=InnoDB;
INSERT INTO tmp_t SELECT * FROM t2 WHERE b BETWEEN 1 AND 2000;
SELECT * FROM t1 JOIN tmp_t ON t1.b = tmp_t.b;
                                        方案 额外扫描 额外写入 适合
                                        直接给 t2.b 加索引 0 永久索引的写放大 高频、连接列稳定
                                        临时表 1 次 t2 全表扫（100 万行） 2,000 行 + 临时索引 低频、过滤后结果小
                                        应用层哈希 0（两条单表查询） 0 结果能装进应用内存

                                        临时表的账要算全：INSERT ... SELECT 扫了 100 万行，建临时表和索引有开销，join 只扫 1,000 行 + 1,000 次索引查找。它省的是永久索引的写放大，不是白拿的——高频 SQL 用临时表，每次都要重建，反而更贵。临时表还会占磁盘/内存，连接池复用时要清理（44.29 临时表与 Memory 引擎）。

                                        三表 join：顺序按「过滤后行数」排

                                        三表 join 不是「前两张先 join 成结果集，再和第三张 join」。优化器按执行计划决定顺序；走 BKA 时是「1 关联 2 找到一行，马上去关联 3」，每层各有一个 join_buffer。课程留的练习题是：

                                        SELECT * FROM t1 JOIN t2 ON (t1.a=t2.a)
               JOIN t3 ON (t2.b=t3.b)
WHERE t1.c>=X AND t2.c>=Y;

                                        索引至少覆盖「连接列 + 过滤列」：t1 要 c，t2 要 a、b、c，t3 要 b、c。组合索引的列顺序由「谁驱动谁」决定：t2 由 t1.a 驱动时索引要以 a 开头，由 t3.b 驱动时要以 b 开头；课程留言里的 t1(c)、t2(b,c)、t3(b,c) 对应的是 t2 由 b 侧驱动的顺序，不是唯一答案。驱动顺序按三张表各自过滤后的行数从小到大排，让最少的行数先驱动；用 straight_join 固定顺序时，也是这个顺序。三张表各自的过滤条件越强，这个顺序越重要——行数估错一次，后面每一层都要乘上这个误差。

                                        hash join 与半连接：两条改写边界

                                        35 讲写作时（2019，5.7）MySQL 还没有 hash join，原文只能建议在应用层用 map 模拟。8.0.18 起官方支持 hash join；本机 8.0.46 上，无索引等值/非等值 join 都显示 Using join buffer (hash join)，hash_join=off 实测没有改回 BNL。版本不同，优化手段就不同：5.7 上要躲 BNL，8.0 上要判断 hash join 的建表成本与内存。

                                        IN/EXISTS 子查询在 5.6+ 可能被优化器改写成半连接（semi-join），可选策略包括 FirstMatch、LooseScan、Materialize、DuplicateWeedout；改写成功时，子查询可能从 EXPLAIN 里消失，变成一张临时表或一次 join。边界有两条：NOT IN 的子查询结果含 NULL 时不能按 anti-join 等价改写（三值逻辑，见「子查询：先问它执行几次」）；相关子查询含非等值条件或 OR 时，也可能退化成逐行执行。判断方式不是背口诀，是看 EXPLAIN 和 SHOW WARNINGS 的实际改写结果。

                                        left join：ON/WHERE 与驱动表顺序

                                        LEFT JOIN 的左边不一定是驱动表。把从表条件写进 WHERE，优化器可能直接把 LEFT JOIN 改写成 INNER JOIN，顺带把驱动表换掉。课程的两个表：a、b 各 6 行，a.f1 有索引、b.f1 无索引，两表 f1/f2 都有 4 行相同。

                                        -- Q1：两个条件都在 ON，返回 6 行
SELECT * FROM a LEFT JOIN b ON (a.f1=b.f1) AND (a.f2=b.f2);

-- Q2：一个条件在 WHERE，返回 4 行
SELECT * FROM a LEFT JOIN b ON (a.f1=b.f1) WHERE (a.f2=b.f2);
                                        语句 条件位置 返回行数 驱动表 算法
                                        Q1 都在 ON 6 a（左表） hash join（b 无索引）
                                        Q2 一个在 WHERE 4 b（右表） NLJ（a.f1 有索引）

                                        Q2 的 EXPLAIN 第一行是 b（type=ALL），第二行才是 a（type=ref，key=f1）；Q1 反之。SHOW WARNINGS 直接给出改写后的语句：

                                        /* select#1 */ select ... from `a` join `b`
where ((`a`.`f1`=`b`.`f1`) and (`a`.`f2`=`b`.`f2`))

                                        内连接里两种写法通常等价：a JOIN b ON a.f1=b.f1 WHERE a.f2=b.f2 会被改写成 a JOIN b WHERE (a.f1=b.f1) AND (a.f2=b.f2)，执行计划一样；有区别的是外连接，所以「条件写 ON 还是 WHERE」只在 LEFT/RIGHT JOIN 里成为问题。

                                        LEFT JOIN 不见了，where 里的条件也被合并进去。原因是三值逻辑：WHERE a.f2=b.f2 里只要 b.f2 是 NULL，比较结果就是 NULL，不满足 WHERE；而 LEFT JOIN 补 NULL 的那两行（a 的 1、2）恰好 b.f2 IS NULL，必然被滤掉。既然主表不匹配的行最终都要丢，外连接就退化成了内连接，优化器才敢改写并换驱动表。

                                        两种写法都不要背成口诀，看条件作用在谁身上：

                                        WHERE 条件 是否消掉外连接语义 结果
                                        从表列等值/不等值比较（b.f2=?、a.f2=b.f2） 是，补 NULL 行必不满足 可改写为 inner join，驱动表可能换
                                        主表列过滤（a.f2=2） 否，只是过滤主表 仍是 LEFT JOIN，保留主表其余行
                                        从表列 IS NULL（找未匹配） 否，这是反连接 保留主表未匹配行

                                        所以「要 LEFT JOIN 的语义，就把从表条件全写在 ON 里」；如果本来就只想留匹配行，直接写 JOIN，别用 LEFT JOIN 再靠 WHERE 补救。

                                        反过来，「找 a 里没有匹配 b 的行」也有固定写法：LEFT JOIN ... ON ... WHERE b.f1 IS NULL，或 NOT EXISTS。WHERE b.f1 IS NULL 作用在从表列上，看起来像「会被改写成 inner join」，但 IS NULL 正是用来筛补 NULL 的行，优化器会按反连接（anti-join）处理，不会把主表行滤光。

                                        🔑 驱动表看 EXPLAIN 第一行和 rows，不看 SQL 里谁写在左边；LEFT JOIN 只保证结果保留左表全部行，不保证执行顺序。

                                        本机实测的 Q1/Q2 行数就是 6 和 4；把 WHERE 里的 a.f2=b.f2 换成 a.f2=2，结果只剩 a.f2=2 的 1 行，但仍是 LEFT JOIN（a 继续做驱动表），不会被改写成 inner join——条件落在主表还是从表，决定改写是否发生。

                                        join 改动的验证与回退

                                        改动 验证 看什么 回退
                                        给被驱动表加索引 EXPLAIN + EXPLAIN ANALYZE 被驱动表 type=ref、rows 下降、接口 P99 ALTER TABLE ... DROP INDEX ...，先看磁盘余量与复制延迟
                                        开 BKA/MRR SET optimizer_switch=... 后 EXPLAIN Extra 出现 Using MRR 或 Batched Key Access SET optimizer_switch 改回默认，会话级立即生效
                                        调 join_buffer_size 同一条 SQL 跑 3 次取中位数 扫描次数/溢写，不看单次 SET GLOBAL 改回 256K；只影响新连接
                                        用 straight_join 对调驱动表做 A/B 两次耗时与 rows 删掉 straight_join，交回优化器

                                        子查询：先问「它执行几次」

                                        子查询按返回形态分四类，决定它能放在哪：

                                        形态 返回 典型位置
                                        标量子查询 1 行 1 列 SELECT (SELECT MAX(x) FROM b) AS m、WHERE x = (SELECT ...)
                                        列子查询 1 列多行 WHERE x IN (SELECT ...)
                                        行子查询 1 行多列 WHERE (a,b) = (SELECT ...)
                                        表子查询 多行多列 FROM (SELECT ...) AS t、EXISTS (SELECT ...)

                                        按执行次数又分两类，性能差异全部来自这里：非关联子查询只算一次，关联子查询外层每行算一次。

                                        类型 执行次数 典型写法 规模风险
                                        非关联 1 次，结果当外层条件 WHERE cc IN (SELECT cc FROM B) 子查询结果集大小决定内存
                                        关联 外层行数（37 行 → 37 次） EXISTS (SELECT 1 FROM B WHERE B.cc = A.cc) 子查询没走索引 → O(n × m)

                                        EXISTS 天然是关联子查询（它要拿外层的值去判断「存在与否」），所以 IN 与 EXISTS 的选择本质是「让哪张表当驱动表」。《MySQL 实战 45 讲》给的判据是：

                                        场景（cc 列有索引） 选谁 为什么
                                        外层表 A 大，子查询表 B 小 IN 一次算出 B 的集合，再用它过滤 A
                                        外层表 A 小，子查询表 B 大 EXISTS 外层每行去 B 上按索引探一次，不用把 B 全取回来

                                        课件的实测（37 名球员的表）：EXISTS 查出 19 条出场球员，NOT EXISTS 查出 18 条未出场——两者互补，加起来正好 37；集合比较里 ANY 查出 35 条，ALL 只查出 1 条（只有最高的那位）。

                                        ⚠️ 上表是「有索引」前提下的经验判据。现代优化器会把 IN 改写成半连接（semi-join），改写成功时两者计划可能一样——以 EXPLAIN 的实际计划为准，别背口诀。

                                        一个必须知道的 NULL 陷阱

                                        NOT IN (子查询) 只要子查询结果里有一个 NULL，整个条件就恒为 UNKNOWN，返回空集；NOT EXISTS 不受影响。可复现：

                                        -- B 里有一行 cc 为 NULL 时，下面两句结果不同（MySQL 8.0，本机无实例，未执行）
SELECT * FROM A WHERE cc NOT IN (SELECT cc FROM B);          -- 0 行
SELECT * FROM A WHERE NOT EXISTS (SELECT 1 FROM B WHERE B.cc = A.cc);  -- 正常返回

                                        所以「排除一批 id」优先写 NOT EXISTS 或 LEFT JOIN ... WHERE B.cc IS NULL，别用 NOT IN。

                                        最左前缀：联合索引 (a, b, c)

                                        条件 能用到索引的列 说明
                                        a = ? a 最左列可用
                                        a = ? AND b = ? a, b 前缀连续
                                        a = ? AND b = ? AND c = ? a, b, c 全用上
                                        a = ? AND c = ? 只用 a c 只能在回表后过滤
                                        b = ? 用不了 跳过最左列，索引树按 a 有序，无法定位
                                        c = ? 用不了 同上

                                        范围条件会截断后续列：a = ? AND b > ? AND c = ? 只能用到 a, b（b 是范围，c 无法再用于定位）。这是“最左前缀”最容易被忽略的细节——很多慢查询是列顺序排错了，而不是索引没建。

                                        深分页：从 100 万行到 20 行

                                        -- 慢：要先读出前 1,000,020 行再丢掉
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;

-- 快：从上一页最后一条的 id 继续（keyset / seek 分页）
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 20;
                                        写法 读取行数 相对成本
                                        OFFSET 1000000 LIMIT 20 1,000,020 50001×
                                        keyset（id > ?） 20 1×

                                        深分页慢的根因是偏移量必须被“走过”：数据库不知道第 100 万行在哪，只能顺序数过去。keyset 分页把“位置”变成“条件”，直接定位。代价是不能跳页（只能上一页/下一页），适合信息流、导出、遍历。

                                        ⚠️ SELECT * 不只是“多传几个字段”：它会让覆盖索引失效（必须回表）、增加网络传输、破坏“索引即数据”的可能。在宽表（200 字节/行 vs 40 字节/行）上，IO 差 5 倍。

                                        可运行的成本模型

                                        package main

import (
	"fmt"
	"math"
)

const (
	rows         = 10_000_000.0 // orders 表行数
	rowsPerPage  = 100.0        // 每页放 100 行
	seqPageMs    = 0.04         // 顺序读一页 0.04ms（约 200MB/s）
	randomPageMs = 0.10         // 随机读一页 0.10ms
	fanout       = 500.0        // B+ 树每个内部节点的分叉数
)

func pages(rs float64) float64 { return rs / rowsPerPage }

func main() {
	// ① B+ 树高度：点查要读几页
	height := math.Ceil(math.Log(rows) / math.Log(fanout))
	fmt.Printf("① %.0f 万行、扇出 %.0f → B+ 树高 %.0f 层；点查约 %.0f 次页读；全表 %.0f 万页\n",
		rows/10000, fanout, height, height, pages(rows)/10000)

	// ② 选择性：3 年数据，查最近 30 天 + status='paid'（占 40%）
	dateSel := 30.0 / (3 * 365)
	statusSel := 0.40
	matched := rows * dateSel * statusSel
	fmt.Printf("② 时间选择率 %.2f%%，status 选择率 %.0f%% → 命中 %.0f 行（%.1f%%）\n",
		dateSel*100, statusSel*100, matched, matched/rows*100)

	// ③ 三种执行路径的 IO 成本
	fullScan := pages(rows) * seqPageMs
	idxDate := pages(rows*dateSel)*randomPageMs + matched*randomPageMs
	idxBoth := pages(matched)*randomPageMs + matched*randomPageMs
	covering := pages(matched) * seqPageMs
	fmt.Printf("③ 执行成本（ms）：全表扫描 %.0f；单列索引(created_at)回表 %.0f；联合索引(status,created_at)回表 %.0f；覆盖索引 %.0f\n",
		fullScan, idxDate, idxBoth, covering)

	// ④ 索引回表 vs 全表扫描的交叉点
	crossover := math.Floor(pages(rows) * seqPageMs / randomPageMs)
	fmt.Printf("④ 回表行数超过 %.0f 行（%.2f%% 的选择率）时，全表扫描反而更快\n",
		crossover, crossover/rows*100)
	fmt.Printf("   本例命中 %.0f 行 > %.0f → 优化器大概率选全表扫描，除非用覆盖索引\n", matched, crossover)

	// ⑤ 连接：10M 订单 × 1M 用户
	orderRows, userRows := rows, 1_000_000.0
	fmt.Printf("⑤ 连接 1000 万订单与 100 万用户：嵌套循环无索引 %.0e 次比较；哈希连接 %.1e 次；索引嵌套循环 %.0e 次页读\n",
		orderRows*userRows, orderRows+userRows, orderRows*3)

	// ⑥ 深分页：LIMIT 1000000, 20
	offset := 1_000_000.0
	fmt.Printf("⑥ OFFSET %.0f LIMIT 20：要读 %.0f 行；keyset（WHERE id > ?）只读 20 行，差 %.0f 倍\n",
		offset, offset+20, (offset+20)/20)

	// ⑦ 最左前缀：联合索引 (a,b,c)
	fmt.Println("⑦ 联合索引 (a,b,c) 能用到哪几列：")
	for _, q := range []struct{ cond, use string }{
		{"a = ?", "a"},
		{"a = ? AND b = ?", "a,b"},
		{"a = ? AND b = ? AND c = ?", "a,b,c"},
		{"a = ? AND c = ?", "只用 a（c 回表过滤）"},
		{"b = ?", "用不了（跳过最左列）"},
		{"c = ?", "用不了（跳过最左列）"},
	} {
		fmt.Printf("   %-32s → %s\n", q.cond, q.use)
	}
}

                                        自检

                                        Q1 命中 10.9 万行（1.1%）时，走索引回表要 11233ms，全表扫描只要 4000ms。为什么“用了索引”反而更慢？

                                        ▸ 答案：因为成本由页读方式决定，不是“有没有用索引”。全表扫描是 10 万页顺序读（0.04ms/页）；索引回表是 10.9 万次随机读（0.10ms/次），每次只取一行所在页，页里的其余 99 行浪费了。总成本 10.9 万 × 0.1ms ≈ 11s，是顺序扫的两倍多。所以优化器的选择是对的：低选择率（本例 1.1%）下全表扫更便宜。要让它变快，得减少回表——覆盖索引把 11233ms 降到 44ms。

                                        Q2 覆盖索引为什么能把 11233ms 降到 44ms？它成立的条件是什么？

                                        ▸ 答案：覆盖索引把查询需要的所有列都放进索引，不需要回表：只读 109,589 行 / 100 行每页 ≈ 1096 个索引页，顺序读约 44ms。条件有三：① SELECT 的列全部在索引里（不能 SELECT *）；② 过滤条件能用到索引（最左前缀 + 范围）；③ 索引本身不太宽（宽索引的页数会变多，收益下降）。代价是索引更大、写放大更高，所以覆盖索引要针对高频查询设计，不是给每张表都加。

                                        Q3 联合索引 (a,b,c)，为什么 WHERE b = ? 用不了索引，而 WHERE a = ? AND c = ? 至少能用 a？

                                        ▸ 答案：B+ 树按“a 然后 b 然后 c”排序，只有 a 确定时，b 才在索引里局部有序；跳过 a 直接查 b，b 在整个索引里无序，无法二分定位，只能全索引扫。a = ? AND c = ? 里 a 能定位到一段连续区间，c 在这段区间内无序，所以只能回表后过滤——索引仍然缩小了扫描范围。列顺序要按“等值在前、范围在后、高频组合优先”排。

                                        Q4 LIMIT 1000000, 20 为什么要读 100 万行？换成 keyset 分页后为什么只读 20 行？代价是什么？

                                        ▸ 答案：OFFSET 的语义是“跳过前 N 行”，数据库必须真的数过这 N 行（即使不返回），所以读了 1,000,020 行。keyset 用 WHERE id > 上一页最后一个 id 把“位置”变成“索引上的起点”，B+ 树直接定位，只读 20 行。代价：① 不能随机跳页（只能上一页/下一页）；② 需要单调且唯一的排序键（id/时间戳 + 去重）；③ 排序键变了分页就失效。

                                        Q5 哈希连接和索引嵌套循环，什么时候选哪个？

                                        ▸ 答案：哈希连接适合两张大表做等值连接、内存能放下 build 侧（小表）：一次建表 + 一次探测，复杂度线性，但只支持等值、内存不够会落盘。索引嵌套循环适合驱动表很小（几十~几千行）、被驱动表连接列有索引：每行一次 3 层索引查找，成本 = 驱动行数 × 3 页读，不需要大内存。优化器会根据统计信息选；如果你发现它选错了（比如统计过期），可以用 hint 或改写查询，但先确认统计信息是否新鲜。

                                        Q6 一条 SQL 在测试环境 37 行、上线后跑了几分钟还没出结果，EXPLAIN 里两张表的 rows 分别是 1,000,000 和 100,000。最可能的原因？

                                        ▸ 答案：连接条件漏了（或写在了不生效的位置），得到的是笛卡尔积：10⁶ × 10⁵ = 10¹¹ 行。判据是 EXPLAIN 里各表 rows 相乘≈结果行数量级，且 Extra 里没有可用的连接索引。SQL92 写法最常犯：表加进 FROM 就忘了 WHERE 里的条件。

                                        Q7 LEFT JOIN 之后想「只看湖人的球员」，为什么把 t.team_name='湖人' 写进 WHERE 就错了？该写在哪？

                                        ▸ 答案：写进 WHERE 会先补 NULL、再统一过滤——没有球队的球员 team_name 是 NULL，必然被滤掉，主表那部分行就消失了，外连接退化成内连接。想「只保留湖人的球员」本来就该用内连接；想「保留全部球员、只把湖人的队名填上」，条件要写在 ON 里。判据：筛选主表 → WHERE；限制匹配、主表全留 → ON。

                                        Q8 「找出没有下过单的用户」，NOT IN (SELECT user_id FROM orders) 与 NOT EXISTS (...) 有什么区别？什么情况下前者会返回空集？

                                        ▸ 答案：NOT IN 要求子查询结果里没有 NULL：只要 orders.user_id 有一行为 NULL，user_id NOT IN (..., NULL) 就恒为 UNKNOWN，整条查询返回空集。NOT EXISTS 是逐行判断「存不存在」，不受 NULL 影响。所以排除类查询优先 NOT EXISTS，或 LEFT JOIN ... WHERE orders.user_id IS NULL。另外注意 orders.user_id 上的索引：EXISTS 靠它把「外层每行探一次」变成索引查找，否则就是 37 行 × 全表扫。

                                        Q9 join_buffer_size 从 256K 改小到放不下驱动表时，等值判断次数会变吗？什么会变？

                                        ▸ 答案：判断次数不变，仍是 M×N；变的是扫描行数。驱动表被切成 K 段，每段都要把被驱动表完整扫一遍，扫描量变成 N + K×M。《MySQL 实战 45 讲》例子里 100 行驱动表被切成 88 + 12 两段，t2（1000 行）就被扫 2 次，总扫描 1100 → 2100，而 10 万次内存判断一次不少。所以调大 join_buffer_size 减少的是被驱动表的重复扫描，不是 CPU 的等值比较。

                                        Q10 一条大冷表 join 跑了 3 分钟，结束后业务查询还是慢，命中率一直上不去。为什么？

                                        ▸ 答案：BNL 反复扫冷表，把冷数据页推进 buffer pool 的 old 区；而 InnoDB 的 LRU 要求数据页「1 秒后再次被访问」才能晋升到 young 区，冷表扫描循环太快，热数据页要么被挤掉、要么来不及晋升。结果是 young 区该淘汰的没淘汰、热页进不来。语句结束不等于影响结束——IO 和 CPU 会立刻恢复，缓冲池要等后续请求慢慢暖回来（44.3 缓冲池与页面管理）。

                                        Q11 为什么 SELECT 里定义的别名，WHERE 用不了，HAVING 却能用？

                                        ▸ 答案：逻辑执行顺序是 FROM → WHERE → GROUP BY → 聚集 → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT。别名在第 6 步 SELECT 才产生，WHERE 在第 2 步，所以看不到；聚集函数在第 4 步已算完，HAVING 在第 5 步，所以 HAVING num > 1 能引用 COUNT(*) AS num。MySQL 允许这种写法，标准 SQL 不保证；跨库时把聚合表达式再写一遍最稳。

                                        Q12 把复杂 JOIN 封装成视图后，查询会变快吗？为什么？

                                        ▸ 答案：不会。视图存的是 SELECT 定义，不是数据；每次查询都会展开成原查询再优化，执行计划和直接写 JOIN 基本一样。它省的是开发与权限管理的力气。要省算力得用物化视图，把结果落下来并承担刷新/陈旧窗口的代价（32.2 物化视图）。

                                        Q13 一个“按行分档更新 10 万行”的需求，为什么优先写 UPDATE ... CASE WHEN，而不是游标？

                                        ▸ 答案：游标是逐行 FETCH + 逐行 UPDATE，每行一次往返、持锁时间长、内存占用高；CASE WHEN 是一条集合 UPDATE，优化器可以走索引、批量改页。只有“每行规则无法用 CASE 表达”或“多表嵌套查找 JOIN 计划确实更差”时才用游标，且要限制结果集、先备份、别放长事务。游标取到末尾不写 HANDLER FOR NOT FOUND 会报 1329；释放游标用 DEALLOCATE，不是 DEALLOCATE PREPARE（1243）。

                                        Q14 两条 SQL 都返回 4 行：a LEFT JOIN b ON a.f1=b.f1 WHERE a.f2=b.f2 与 a JOIN b ON a.f1=b.f1 AND a.f2=b.f2，EXPLAIN 也一模一样。为什么？如果业务其实要保留 a 的 6 行，应该怎么改？

                                        ▸ 答案：WHERE 里的 a.f2=b.f2 对补 NULL 的从表行结果是 NULL，主表未匹配行必然被滤掉，LEFT JOIN 的语义已经等价于 INNER JOIN；优化器在 SHOW WARNINGS 里直接把它改写成 join。要保留 6 行，把 a.f2=b.f2 放回 ON，让不匹配的 a 行补 NULL 保留；如果本来就要内连接语义，直接写 JOIN，别用 LEFT JOIN 再靠 WHERE 补救。

                                        Q15 t1 10,000 行、t2 100,000 行，t1.a=t2.b、t2.b 无索引。8.0.46 的 EXPLAIN 显示 Using join buffer (hash join)，把 join_buffer_size 从 128K 调到 4M 后变快。它省掉的是哪部分？如果换到 5.7，同一句会看到什么？

                                        ▸ 答案：省的是 hash join 哈希表放不下时的分批/溢写成本，不是 M×N 次匹配；匹配次数由行数决定，调 buffer 不变。5.7 没有 hash join，同一句会走 BNL，Extra 显示 Using join buffer (Block Nested Loop)，join_buffer_size 影响的是驱动表被切成几段（K），被驱动表被全表扫 K 次；M×N 次内存判断仍不变。
