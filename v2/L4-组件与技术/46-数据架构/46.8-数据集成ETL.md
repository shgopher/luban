# 46.8 数据集成：ETL / ELT 的三段职责

## 一句话

> 数据集成不是“把表拷过去”，而是把**不同库、不同规范、不同质量**的数据变成**一个可分析的数据源**：抽取要选全量还是增量，转换要把口径统一，加载要保证可重跑——三段里最贵的永远是抽取与口径，不是工具。

## 先分清四个问题

| 问题 | 表现 | 处理 |
|---|---|---|
| **异构** | MySQL、Oracle、PostgreSQL、MongoDB 各一套 | 统一类型/字符集/时区，落到目标库的公共模型 |
| **重复** | 同一条记录在多个源都有 | 定业务主键，去重/合并，保留来源标记 |
| **标识不统一** | 用户 ID、商品编码各系统不同 | 建映射表/主数据，禁止“猜” |
| **格式不一致** | 日期、金额单位、枚举值不同 | 转换层统一，口径写进数据契约 |

这四件事与 [46.1 数据建模](46.1-数据建模.md) 的“事实/维度”是两层：建模决定“长什么样”，集成决定“怎么把源数据搬成那个样子”。

## ETL 三段：每段各管什么

| 阶段 | 职责 | 主要风险 | 判据 |
|---|---|---|---|
| **Extract 抽取** | 盘点源库类型、结构化程度；选全量/增量 | 漏采、重复采、源库压力 | 有没有可靠的变化标识（时间戳/自增 ID/日志） |
| **Transform 转换** | 字段映射、清洗、校验、过滤、派生 | 口径不一致、类型截断、时区错位 | 同一指标是否只有一处定义 |
| **Load 加载** | 写入目标库/文件/湖 | 重复写入、部分成功、schema 漂移 | 能不能幂等重跑 |

### 抽取：全量 vs 增量

| 方式 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **全量** | 每次搬全表 | 小表、无变化标识、对账 | 源库压力大、窗口长 |
| **增量** | 只取上次之后的变化 | 大表、有 `updated_at`/自增 ID | 依赖标识可靠；删除/更新要额外处理 |
| **CDC** | 订阅 binlog/WAL | 低延迟、不能改源表 | 运维复杂，见 [46.4 CDC](46.4-CDC.md) |

增量抽取的三个坑：**软删除**（`is_deleted=1` 也要抽）、**迟到数据**（业务时间晚于抽取时间）、**更新不改时间戳**（`updated_at` 没维护）。没有可靠标识时，不要硬做增量，先补标识或走 CDC。

### 转换：四类组件

| 组件 | 做什么 | 例子 |
|---|---|---|
| **映射** | 源字段 → 目标字段 | `sex` 的 `M/F` → `1/0` |
| **清洗** | 缺失、重复、异常、格式 | 去空格、统一大小写、补默认值（[60.5 数据质量](../60-数据平台与数仓/60.5-数据质量.md)） |
| **校验** | 类型、范围、枚举、唯一 | 金额 ≥ 0、状态在枚举内 |
| **过滤** | 只保留需要的行/列 | 只同步近 3 年、剔除测试账号 |

转换逻辑要**可版本化、可测试**：一段 SQL/一个脚本就是一段代码，不能只存在工具的画布里。否则口径变更时，没人知道线上跑的是哪一版。

### 加载：SQL 还是批量

- 小批量：`INSERT` / `UPSERT`（`INSERT ... ON DUPLICATE KEY UPDATE`）即可。
- 大批量：`LOAD DATA`、批量文件、warehouse 的 `COPY`；比逐条 INSERT 快一个数量级以上。
- **幂等**：同一批数据重跑两次，结果必须一样。做法是“按分区覆盖”或“按业务主键 upsert”，不要裸 `INSERT` 追加。

## ETL 还是 ELT

| 模式 | 顺序 | 适用 | 代价 |
|---|---|---|---|
| **ETL** | 先转换，再加载 | 目标库算力弱、数据不能原样落地、合规要求先脱敏 | 转换层成为瓶颈，原始数据没保留 |
| **ELT** | 先原样加载，再用目标库算力转换 | 云数仓/湖仓、算力弹性、要保留原始层 | 存储成本高，转换逻辑要治理 |

云数仓时代更常见 ELT：先把 ODS 原样落地（可重算），再在数仓内做 DWD/DWS（[60.2 数仓分层](../60-数据平台与数仓/60.2-数仓分层.md)）。但“数据不能出域”“按扫描量计费”“源库不允许长连接”这些约束会把方案推回 ETL——选型看约束，不看流行。

## 工具：只留判据，不背产品手册

课程以 Kettle 为例：Spoon 是图形界面，Pan 跑 Transformation（`.ktr`），Kitchen 跑 Job（`.kjb`）；Job 管流程与调度，Transformation 管数据流，**Job > Transformation**。它最值得抄的不是按钮，而是一句翻译：

> **Kettle 的“数据库查询”组件 ≡ SQL 里的 `LEFT JOIN`。**

例如交易表要补收款/付款账户类型，图形化是“表输入 → 数据库查询 → 过滤 → 输出”，SQL 就是：

```sql
SELECT t.*, a1.customer_type AS payer_type, a2.customer_type AS payee_type
FROM trade t
LEFT JOIN account a1 ON t.account_id1 = a1.account_id
LEFT JOIN account a2 ON t.account_id2 = a2.account_id;
```

理解这个等价，才能在工具坏了/换工具时把流程还原成 SQL。现代栈通常用 Airbyte/Fivetran 做抽取、dbt 做转换、Airflow/Dagster 做调度；产品会换，三段职责不变。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用跨库 `JOIN` 直接抽数 | 权限、网络、字符集、性能四重坑；源库被拖垮 |
| 增量只按 `updated_at`，不管删除 | 目标库永远多出已删数据 |
| 转换逻辑只存在工具画布 | 无法 code review、无法回滚、口径漂移 |
| 裸 `INSERT` 追加 | 重跑一次翻倍，对账永远不平 |
| 全量与增量混用不标来源 | 同一行两份，主键冲突或重复计数 |
| 把清洗放在 BI 报表层 | 每个报表各洗一遍，口径必然分叉 |
| 源库 schema 变更不设门禁 | 上游删列，下游凌晨全空（[60.5](../60-数据平台与数仓/60.5-数据质量.md) 的数据契约） |

## 自检

**Q1** 一张 2 亿行的订单表要同步到数仓，源表有 `updated_at` 但历史数据里 30% 是 NULL，能做增量吗？

▸ 答案：不能直接做。`updated_at IS NULL` 的行永远不会被增量捕获，会漏采。先补历史时间戳（用 `created_at` 兜底或一次性回填），或改走 CDC；同时处理软删除。增量的前提是“变化标识对每一行都可靠”，不是“表里有这个字段”。

**Q2** 为什么“Kettle 的数据库查询组件等于 LEFT JOIN”这句话有价值？

▸ 答案：它把图形化流程还原成可审查的 SQL，让口径、去重、空值行为都能被验证；工具迁移时也能照着 SQL 重搭。反过来，如果只会拖控件、说不出等价的 SQL，就无法判断“查不到”是数据问题还是 JOIN 条件写错。

**Q3** ETL 与 ELT 怎么选？

▸ 答案：看约束。目标侧算力弹性、要保留原始层、团队能治理转换逻辑 → ELT；数据不能原样落地、要先脱敏、目标库算力弱 → ETL。不要把“云上流行 ELT”当默认答案。

**Q4** 增量抽取只按 `updated_at` 拉数，为什么目标库会多出已删除的数据？

▸ 答案：物理删除不会留下 `updated_at` 变更，增量链路看不到。要么源表改软删除并同步 `is_deleted`，要么走 CDC 捕获 delete 事件，要么定期做全量对账/分区重建。三者至少选一个，否则删除永远不同步。

**Q5** 为什么加载层必须幂等？不幂等会怎样？

▸ 答案：抽取/转换失败后要重跑，重跑可能重复写。不幂等就会一行变两行、金额翻倍，对账永远不平。做法是按业务主键 upsert，或按分区覆盖；裸 `INSERT` 追加最危险。
