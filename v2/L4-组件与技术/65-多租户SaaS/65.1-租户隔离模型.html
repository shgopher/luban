                        65.1 租户隔离模型 (独立库 / 共享库 / 混合)

                        一句话

                        隔离模型没有"最优解"，只有按租户分层的组合——小客户进共享池压成本、大客户单开一套买隔离、合规客户独立地域；判据是每租户的爆炸半径 × 合规等级 × 单位成本，代价是路由层与迁移路径这两笔一次性投入。

                        先破除五个误区

                        误区 现实
                        隔离 = 安全 隔离只决定"漏了以后炸多大"，不决定"会不会漏"。同一套代码在独立库里照样能被 BOLA 打穿，权限判定归 49.4 多租户权限模型
                        一租户一库最安全，能上就上 隔离度是买来的：租户数 × 每租户一套实例 = 实例数、备份任务、DDL 发布、账单一起线性涨；50 家客户时它性价比最差
                        共享表 + tenant_id 最省钱 便宜的是存储，贵的是路由层与"哪个计数器先归零"。加一列是一行代码，连接数、索引基数、备份粒度、单租户恢复这四件事都得单独设计
                        schema 隔离是"折中最优解" 它是第三种形态，有自己的天花板：catalog 规模。实测 3000 个租户 schema、9000 张空表后，库从 7.4 MB 涨到 205 MB，information_schema.tables 全量扫描从 0.45 ms 涨到 12.9 ms
                        混合形态 = 维护两套代码 代码只有一套（数据源抽象 + 路由），真正新增的是路由层与迁移路径两笔一次性投入；不做这两笔，混合形态一定退化成两套部署

                        四种隔离形态：先看爆炸半径，再看成本

                        形态 隔离强度 真实爆炸半径 单位租户成本 可承载租户量级 迁移代价
                        一租户一库 最强（进程级） bug 只炸一库；故障只炸一实例；无邻居性能干扰 最高：每租户 1 主 1 备，实例数 = 2 × 租户数 数十到数百 高：迁数据 + 切路由 + 停写窗口
                        一租户一 schema 中（同实例内） bug 与故障都炸全实例；性能互相干扰 中：0 实例增量，只增 catalog 数百到数千 中：移表 + 切 search_path
                        共享表 + tenant_id 弱（行级） bug 炸全库；故障炸全部；性能靠索引 最低：增量接近 0 数千到数十万 低：加列 + 回填，回滚难
                        混合（池化 + 大客户独立） 分层 小客户共享爆炸半径，大客户独立 分层摊薄 上千 两套路径 + 迁移通道
                        同形态内再加资源级隔离 局部加强 独立实例/可用区/物理机只挡"故障"一类，挡不住 bug 与性能 按需叠加 任意 各自形态的代价

                        "资源级隔离"最容易被误读：独立可用区挡的是机器与机房故障，挡不住写进同一套代码的 bug，也挡不住抢同一实例 CPU 的慢查询。隔离维度要对准要挡的风险，故障域设计见 35.8 故障隔离。

                        爆炸半径拆成四类，四形态对照：

                        形态 bug 泄漏（少写租户条件） 故障（实例宕机） 性能（邻居慢查询 / 大租户） 合规举证
                        一租户一库 1 个租户 1 个租户 无 最强：物理可指认"数据只在这台机器"
                        一租户一 schema 全实例租户 全实例租户 强干扰 中：逻辑可指认，物理不可
                        共享表 全库租户 全库租户 强干扰 + 数据倾斜 弱：只能证明"代码里带了 tenant_id"
                        混合 按层 按层 大客户已隔离 按租户给证据

                        量化瓶颈：先算清哪个计数器先归零

                        隔离形态之争换成计数器之争就能算。三种形态各自先撞的墙不一样：

                        形态 先撞的计数器 算式（本机实测值代入）
                        共享表 + 每租户一个连接池 数据库 max_connections 3000 租户 × 10 条 = 30000 连接；单库默认 100，超级用户保留 3 → 应用只能用 97 → 97 ÷ 10 = 9.7 个租户就把一个库占满
                        一租户一库 实例数与备份任务数 3000 × 2（主 + 备）= 6000 个实例；每晚 3000 个备份任务；每次发版 3000 次 DDL
                        一租户一 schema catalog 规模与元数据查询 3000 schema × 3 表 = 9000 张表 → pg_class 3 万行、库 205 MB、元数据查询慢 4.8–28 倍（实测见下）
                        共享表（单池） 索引基数与大租户倾斜 200 万行里头部租户占 50% → 主键索引 73 MB；大租户聚合 226 ms vs 小租户 1.6 ms（实测见下）

                        计数器一：连接数，3000 租户 × 10 条 = 3 万

                        "每租户一个小连接池"在共享库形态下是最常见的错误设计，算式一步撞墙：3000 租户 × 10 条常驻连接 = 30000 条，而 PostgreSQL 默认 max_connections = 100。

                        本机实测（PostgreSQL 16.14，max_connections=100、superuser_reserved_connections=3）：先开 90 条普通角色连接，再申请 130 条。

                        基线：postgres 进程总 RSS=69236 KB，当前连接数=6，max_connections=100
打开 90 条应用连接后：VmRSS 合计=1381892 KB（含共享内存重复计入），RssAnon 合计=238652 KB，RssShmem 合计=461384 KB，app 连接数=90
单连接私有内存 ≈ 2504 KB（RssAnon 增量 / 90）
再申请 130 条连接：成功 7 条，失败 123 条
失败报错原文：psql: error: connection to server at "127.0.0.1", port 5432 failed: FATAL:  remaining connection slots are reserved for roles with the SUPERUSER attribute
此刻连接数：6

                        90 + 7 = 97 = 100 − 3，正好等于非超级用户可用槽位；每连接服务端私有内存约 2.5 MB。代入 3000 租户：30000 条 × 2.5 MB ≈ 75 GB 私有内存，还没算客户端侧。

                        客户端侧同样有硬墙。纯标准库 Go 程序向本机监听端口连到 30000 条空闲连接（模拟 3000 租户 × 10 条），实测：

                        目标连接数 30000，实际建立 5118 条，用时 380ms
第 5119 条失败：dial tcp 127.0.0.1:57518: socket: too many open files
进程 RSS：4064 KB -> 17328 KB，增量 13264 KB，平均每条连接 2.6 KB
RLIMIT_NOFILE 软限制=10240（每条连接在本进程内占 2 个 fd：客户端 + 服务端）

                        5118 条 × 2 个 fd ≈ 10236，正好顶到 10240 的上限。一个进程连 3 万条连接在 fd 这一层就做不到，与数据库还有多少槽位无关。服务端 2.5 MB/条是客户端 2.6 KB/条的 1000 倍，成本在数据库那侧。

                        🔑 "每租户一个连接池"只适用于租户数几十以内的独立库形态。共享库/schema 形态下必须去掉"每租户池"，改用全租户共享池 + 连接级租户上下文（SET LOCAL 机制见 49.4 多租户权限模型），或用事务模式连接池把 3 万客户端连接压成几十条后端连接。

                        计数器二：实例数与备份任务数

                        一租户一库的真实成本是运维乘法：3000 租户 → 6000 个实例（主 + 备）、3000 个备份任务、3000 条迁移脚本、3000 个监控对象。逐租户备份即使每库 1 秒，串行也要 50 分钟。独立库形态的正确备份方式是存储层快照（一次快照覆盖整实例），不是逐库 pg_dump（见 10.4 快照与备份）。这笔成本最后要进报价，单位经济模型见 39.6 成本驱动的架构决策。

                        计数器三：schema 的数量会推高 catalog 成本

                        在同一台 PostgreSQL 16.14 上做两组对照：库 A 只有 1 个租户 schema（3 张表），库 B 有 3000 个租户 schema（9000 张空表）。同一批查询用 EXPLAIN (ANALYZE) 取 Execution Time：

                        指标 1 个租户 schema 3000 个租户 schema 倍数
                        pg_class 行数 413 30413 73.6×
                        information_schema.tables 行数 212 9209 43.4×
                        库大小 7.4 MB 205 MB 27.7×
                        information_schema.tables 全量扫描 0.451 ms 12.864 ms 28.5×
                        同上，精确到单个 schema 0.316 ms 1.518 ms 4.8×
                        pg_class 按 schema 点查 0.095 ms 0.775 ms 8.2×
                        单租户业务查询（空表 count(*)） 0.011 ms 0.020 ms 1.8×

                        结论：业务查询基本不受影响，元数据查询被拖慢一个量级。information_schema 是视图、过滤器推不下去，先按全库 catalog 展开再筛，所以"只看一个租户的表"也要付 3000 个 schema 的扫描成本。9000 张空表占 205 MB，每张空表约 23 KB catalog 开销。

                        换成无授权的普通应用角色更糟：同一句查询在 3000 schema 库上 281.9 ms（超级用户 12.9 ms），因为它要对 9209 行逐行做权限检查，最后只返回 189 行——这决定"运维后台租户列表页"能不能扛住。

                        schema 形态有两个实测坑：

                        • 批量建 schema 会撞锁表。3000 个 schema 放进一个事务，跑到第 1168 个失败：ERROR: out of shared memory / HINT: You might need to increase max_locks_per_transaction。默认 max_locks_per_transaction = 64 × max_connections = 100 ≈ 6400 个锁槽，1168 个 schema × 5 个对象 ≈ 5840 正好吃满。正确做法是分批提交：实测每批 100 个 schema（400 条 DDL）0.48–0.88 s，3000 个约 20 s，即每租户 schema 约 6.5 ms 开通成本。
                        • 单租户导出/恢复不是"只读一个 schema"。实测 pg_dump --schema-only -n 一个租户 要 0.240 s，而全库 3000 个 schema 的 schema-only dump 只要 1.330 s（输出文本 3.7 MB）。因为每次导出都要先读整份 catalog 再过滤。3000 个租户逐个导出 = 0.24 × 3000 ≈ 12 分钟，全库一次只要 1.3 秒。按租户导出/恢复的需求落到 schema 形态上，成本模型完全不同（操作设计见 65.2 数据隔离与合规）。

                        计数器四：共享表的索引基数与大租户倾斜

                        共享表的业务查询很稳：200 万行、头部租户占 50% 的表上按主键点查，大租户 0.049 ms、小租户 0.027 ms——邻居的数据量不影响点查。被影响的是聚合与全量操作：

                        操作 大租户（100.1 万行） 小租户（1001 行） 倍数
                        按 (tenant_id, id) 点查 0.049 ms 0.027 ms 1.8×
                        按 tenant_id 全量 count(*) 225.951 ms 1.615 ms 140×
                        主键索引体积 73 MB（占表总量 187 MB 的 39%） — —

                        表本身的存储效率没问题（200 万行 5.94 s 导入，187 MB），问题是倾斜：tenant_id 的统计信息只有一个平均基数，规划器对大租户估 9338 行、实际 1001001 行，差 107 倍。点查不受影响，因为等值条件走索引精确路径；受影响的是"按租户统计/导出/重建索引/迁移"这类要扫 tenant_id 的作业，以及基于行数估值的复杂查询计划。要不要按 tenant_id 分区、分区后跨分区查询的代价，主场在 19.1 分区键设计。

                        租户路由层：整套架构里唯一必须新增的组件

                        选了独立库或混合形态，就必须有一个"租户 → 数据源/库/schema"的解析层。它的最小元数据表长这样：

                        CREATE TABLE tenant_route (
  tenant_id   TEXT PRIMARY KEY,
  ds_key      TEXT NOT NULL,          -- 数据源 key：pool-a / dedicated-9
  state       TEXT NOT NULL,          -- active / migrating / disabled
  route_ver   BIGINT NOT NULL,        -- 每次变更 +1，用于缓存失效
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

                        三条硬要求，缺一条就会在生产上出跨租户事故：

                        1. fail-closed：查不到映射、状态不是 active、解析出错，一律拒绝请求，绝不落到"默认库"。
                        2. 本地缓存：热路径不许每次都查元数据表；未命中才回源。
                        3. 变更通知：映射改了要立刻失效缓存，不能等 TTL 自然过期（迁移窗口里等 30 秒就是 30 秒的串写）。

                        下面是 resolve 函数的原文，逐字复制自程序（完整可运行程序与原始输出在 tools/examples/65.1-router/router/main.go，go version go1.27.1 darwin/arm64，纯标准库 go run 直跑）： 示例说明见 tools/examples/65.1-router/。

                        // 以下是 tools/examples/65.1-router/router/main.go 里 resolve 函数的原文（entry / router / route / 示例说明见 [tools/examples/65.1-router/](../../../tools/examples/65.1-router/README.md)。
// metaStore 类型与 main 都在同一文件，此处只省略类型声明与 import）
func (r *router) resolve(tenant string) (string, error) {
	r.mu.RLock()
	e, ok := r.cache[tenant]
	ver := r.routeVer
	r.mu.RUnlock()
	if ok && e.version == ver && time.Now().Before(e.expire) {
		r.mu.Lock()
		r.hits++
		r.mu.Unlock()
		return e.dsn, nil
	}

	row, found := r.meta.get(tenant) // 缓存未命中：允许这一次远程点查
	r.mu.Lock()
	r.misses++
	r.mu.Unlock()
	if !found {
		// 关键：查不到就报错。这里如果 return "db-default", nil，就等于把所有
		// 新租户 / 被删租户的数据写进同一个库。
		return "", fmt.Errorf("%w: %s", ErrNoRoute, tenant)
	}
	if row.State != "active" {
		return "", fmt.Errorf("%w: %s state=%s", ErrNoRoute, tenant, row.State)
	}
	r.mu.Lock()
	r.cache[tenant] = entry{dsn: row.DSN, version: r.routeVer, expire: time.Now().Add(r.ttl)}
	r.mu.Unlock()
	return row.DSN, nil
}

                        真实输出（完整程序在 tools/examples/65.1-router/router/main.go）： 示例说明见 tools/examples/65.1-router/。

                        | 请求租户 | 解析出的数据源 | 结果 |
|---|---|---|
| t-001 | pool-a | ✅ 路由 |
| t-002 | pool-a | ✅ 路由 |
| t-003 | dedicated-9 | ✅ 路由 |
| t-004 | （无） | ⛔ no route for tenant: fail closed: t-004 state=migrating |
| t-005 | （无） | ⛔ no route for tenant: fail closed: t-005 |

收到变更通知后 t-003 -> pool-b（不依赖 TTL 过期）
缓存命中 200000 次共耗时 23.2ms，单次 116ns
缓存未命中（回源 2ms 模拟）单次 2.269037ms，是命中的 19561 倍
命中率 0.9990（199999 命中 / 207 回源）

                        t-004 是迁移中的租户（state=migrating），t-005 是元数据里根本不存在的租户。两者在请求层看起来一样（都拿不到路由），处理方式也一样：拒绝。这是路由层最重要的一条设计：把"未知"和"删除"都当异常，而不是当"默认值"。

                        缓存与回源差 19561 倍，换算成容量：5000 QPS 的服务若每请求都回源，光路由就要 5000 × 2.27 ms = 11.35 核秒/秒，至少 12 个核专职等元数据查询；缓存命中只占 116 ns 的 CPU。所以路由层不是"多一次网络查询"，而是必须有本地缓存、且缓存必须能被变更通知主动失效。

                        💡 我的判断是：路由层不要读主库，读"本地快照 + 变更订阅"。 元数据表的主库是路由层的单点；正确形态是每个实例启动时拉一份全量路由快照（几千行），之后只订阅 route_ver 变更，本地增量更新。热路径永远只读本地内存，元数据表不可用时已有请求继续按旧快照工作，新租户开通降级为"延迟生效"。这比"高可用元数据库"便宜一个数量级。风险要说清：快照模式下，删除租户/迁移租户必须能阻断流量，所以 state 字段要参与路由判定，不能只靠删行。

                        路由表高可用只需两件事：快照可重建（实例启动先读对象存储快照再追变更，避免雪崩回源）；变更广播可兜底（订阅断了按 TTL 全量刷新，失效延迟退到分钟级）。负缓存只能缓存"查无此租户"，不能缓存成可用数据源。

                        混合形态怎么落地：一份代码，两条路径

                        混合形态是同一条代码路径支持两种"数据源形状"：

                        关注点 池化池（小客户） 独立池（大客户）
                        连接管理 全租户共享连接池，连接数 = 副本数 × 池大小 每租户一套连接池，连接数 = 租户数 × 池大小
                        租户上下文 请求级设置（SET LOCAL 或 RLS 变量） 数据源本身即隔离，SQL 不必带租户条件
                        数据源抽象 DataSourceFor(tenant) → pool DataSourceFor(tenant) → dedicated
                        schema 变更 一次 DDL 覆盖全部租户（用 Expand-Contract，见 55.4 数据库变更管理） 每租户单独执行，按批次灰度
                        单租户恢复 从备份/快照恢复到临时库，再按租户导回 恢复到新实例，切路由

                        代码上的关键抽象只有一个接口：DataSourceFor(tenant) (*sql.DB, error)。池化与独立的差别全部沉在实现里，业务代码只拿 *sql.DB（或事务对象），不感知形态——迁移一个租户 = 改一行路由数据，不发版。租户之间的差异（配置项、扩展点）不在这条路径上表达，见 65.4 定制化与版本管理。

                        什么信号触发迁出：

                        信号 经验阈值 触发后的动作
                        合规/合同要求 合同写明"物理隔离"或"独立地域" 无阈值可谈，直接独立部署（驻留与删除见 65.2 数据隔离与合规）
                        单租户 QPS 占比 持续 > 20% 全局 QPS 迁独立实例，避免打满共享池
                        单租户数据量占比 > 单库容量 20%，或单表 > 2000 万行 迁独立库，顺带解决大表 DDL 窗口
                        单租户故障/工单占比 该租户慢查询/超时占全局 > 30% 先限流（见 35.7 限流），再评估迁出
                        备份/恢复 SLA 合同 RTO 短于共享库恢复时间 迁独立库，走快照恢复

                        💡 我的判断是：第一批迁出去的应该是"合规客户"，不是"最大客户"。 最大的客户通常还能靠限流、只读副本、索引优化撑住，迁出去只是把它的性能问题搬了个家；而合规客户一旦在合同里写了物理隔离，晚迁就是违约。爆炸半径的收益只有对"共享池里其它租户"才成立——把一个大客户迁走，小租户感受到的改善远小于把"最常出故障的那个租户"迁走。

                        迁移路径：三个方向，各自的停写窗口与回滚点

                        方向 数据一致性手段 停写窗口 回滚点
                        池化 → 独立（升隔离） 快照 + 增量（CDC 追平） 分钟级：追平后切写 切换前保留双向写入开关；切写后旧库只读但不删
                        独立 → 池化（降成本） 双写 + 校验（逐行比对） 两次：切读、切写 每次切换后保留旧库 7 天；校验不一致即回切
                        同形态内水平扩容 一致性哈希/目录迁移（按租户搬） 通常无（按租户分批搬） 单租户粒度回滚：路由回旧位置

                        共同点：一致性靠"快照 + 增量追平"或"双写 + 校验"，不靠停写；停写窗口只在"追平之后、切写之前"那一下。双写五步法（含每步回滚点与校验）的主场在 44.14 分库分表，这里只承接它对租户维度的三个额外要求：

                        1. 迁移单位是租户，不是行：判定、切换、回滚都以 tenant_id 为粒度，否则一个租户会在两个库里各有一半数据。
                        2. 迁移中必须有 state=migrating 中间态，由路由层 fail-closed 挡住旧路由的写入（核心逻辑见上面的路由代码）。
                        3. 回滚点要能表达"回到旧位置"：旧库至少保留一个计费周期，删旧库是不可逆动作，单独审批。

                        迁移与切流的批次顺序、租户内不可分流这些发布侧约束，见 65.5 租户级灰度发布。

                        🔑 迁移的验收标准不是"数据搬完了"，而是"切换后 24 小时内该租户的延迟、错误率、数据校验三项回到迁移前基线"。 搬完就删旧库，是混合形态最常见的事故来源。

                        选型决策表

                        你的情况 选什么 关键理由
                        客户 < 50 家，单租户数据量 < 100 GB 池化：共享表 + tenant_id，或共享库 + 每租户 schema 独立库的实例/备份/迁移成本会吃掉隔离收益
                        客户 50–500 家，有少量大客户 混合：默认池化 + 大客户独立库 用 10% 的运维成本买 90% 的爆炸半径
                        客户 > 1000 家，SMB 为主 共享表 + tenant_id（或 schema 按需） 租户数决定必须摊薄；主要工作量在连接池与索引
                        合同要求数据物理隔离 / 独立地域 一租户一库（或独立实例/可用区） 合规无谈判空间；成本进报价
                        单租户写入 > 5000 TPS 或单表 > 2000 万行 该租户独立库，其余池化 先解决资源冲突，再谈架构纯度
                        团队 < 5 人，没有专职 DBA 池化，且只做一种形态 两套形态的运维复杂度会直接压垮小团队

                        什么时候别用独立库

                        场景 别用独立库 用什么
                        客户 < 50 家，单租户数据量小 每租户一套实例的固定成本远超数据库本身，运维模板还没写完客户先流失 共享表 + tenant_id，路由层预留扩展点
                        团队 < 5 人、无专职 DBA 备份、升级、监控、排障都是人力乘法，排查面从 1 个变 3000 个 共享库 + 独立 schema，DDL 批量管理
                        租户间数据量差异 < 2 倍、无合规要求 买不到爆炸半径收益，只买到运维成本 池化，预算花在限流与隔离舱上
                        还没做路由层就想上独立库 只能靠"每租户一个部署"，等于把 SaaS 做成 N 个私有化项目 先建路由层与元数据表

                        反模式

                        反模式 后果
                        拿不到租户映射就落到 default 库 新租户、已删租户、迁移中租户写进同一个库，串号且无法按租户回滚
                        每租户一个连接池，用在共享库形态 3000 × 10 = 3 万连接，97 个槽位只够 9.7 个租户
                        用行数/租户数当唯一选型依据 忽略爆炸半径与合规等级：小客户被大租户拖死，或合规客户被池化拖到违约
                        路由缓存只设 TTL、没有变更通知 迁/删租户后最长一个 TTL 内继续写旧库，数据分叉
                        一个事务里批量建几千个租户 schema 撞 max_locks_per_transaction，实测第 1168 个报 out of shared memory
                        独立库逐库 pg_dump 备份 备份任务数 = 租户数，串行时长线性涨；应走快照
                        迁移成功就删旧库 数据校验问题 24 小时后才暴露，失去回滚能力
                        混合形态写成两套部署 版本、配置、迁移脚本双份，成本随租户数而非版本数增长

                        自检

                        Q1 客户只有 30 家，但其中一家要求"数据物理隔离"。你只给它做独立库，其余 29 家留在共享表，需要改代码吗？

                        ▸ 答案：不需要改业务代码，但需要路由层与数据源抽象：业务只依赖"按租户拿数据源"的接口，差别沉在实现里。要新增的是元数据表里一行（ds_key=dedicated-x）、迁移与切流、这条独立路径的备份/监控/DDL 脚本。要为它 fork 一份代码，说明抽象做错了。

                        Q2 为什么"每租户 10 条连接 × 3000 租户"在共享库里必死，而在独立库里却不死？

                        ▸ 答案：因为连接上限是每个数据库实例的属性。共享库里 3 万条连接抢同一个实例的 97 个槽位，第 10 个租户就排不上；独立库里每个租户一个实例，各用各的槽位，代价转移到实例数与备份任务数。连接数问题没被解决，只是换成了运维问题。

                        Q3 3000 个租户 schema 后，哪些查询变慢、哪些不变？为什么？

                        ▸ 答案：变慢的是元数据查询——information_schema.tables 全量扫描实测 0.45 ms → 12.86 ms（28.5×），因为它要展开全库 catalog 再筛；普通业务查询几乎不变（0.011 ms → 0.020 ms），因为它走 schema 内索引、根节点常驻 Buffer Pool，与实例里有多少别的 schema 无关。所以 schema 形态的天花板是"运维后台、迁移工具、备份工具"，不是"用户请求"。

                        Q4 路由层为什么必须 fail-closed？"查不到就用默认库"在什么场景下是致命的？

                        ▸ 答案：查不到映射只有三种可能——新租户未开通、租户已删除、租户迁移中。把请求导向默认库，等于把 A 租户的写落到 B 租户的数据源上；迁移中的租户还会同时写新旧两库，形成无法用单租户回滚修复的分叉。默认库兜底只在小规模、单形态、且"先建库再上线"的流程里勉强可用。

                        Q5 共享表形态下，一个租户的慢查询会怎么影响别人？点查为什么没受影响？

                        ▸ 答案：影响的是实例级共享资源——CPU、Buffer Pool、连接数、WAL 带宽：一个租户的全表聚合（实测大租户 count(*) 226 ms vs 小租户 1.6 ms）会抢走它们。点查不受影响，因为等值条件走主键精确路径，只读少量页。共享表的隔离重点是"限流 + 大租户识别 + 慢查询熔断"。

                        Q6 迁移一个租户从共享池到独立库，哪一步最容易被跳过、后果最大？

                        ▸ 答案：切写之后、删旧库之前的"双跑期"。容易跳过的是逐行校验（只对行数不对内容）与旧库保留期（迁移成功就删）。一条增量漏掉或某条路径仍写旧库，都要等对账才暴露，那时旧库已删、回滚点已失。切写后至少保留一个计费周期并定时校验，零差异再删。
