# 65.5 租户级灰度发布

## 一句话

> 租户级灰度的最小单元是**租户**而不是用户，因为同一租户内的数据模型与配置必须一致；这带来三条硬约束——租户内不能分流、共享表下不能按租户改 schema、回滚粒度只能是整租户，所以灰度顺序要按"**爆炸半径 × 可承受损失**"排。

## 先破除五个误区

| 误区 | 现实 |
|---|---|
| 把切分键从 `uid` 换成 `tenant_id` 就完事 | 切分键好换，一致性约束换不掉。用户级切错只影响体验；租户级切错会分裂数据格式、缓存与账单口径 |
| 租户级灰度就是"慢一点的金丝雀" | 它多出一类金丝雀不处理的问题：灰度窗口内共享状态要双版本兼容，窗口比放量节奏长得多 |
| 共享表也能"只给灰度租户加列" | 表结构是全局的，加列那一秒所有租户的应用都在同一张表上写入 |
| 出问题把路由切回去就恢复了 | 路由能回，已按新格式写入的数据回不去，只能兼容读或回填 |
| 大盘错误率没动，说明灰度没问题 | 一个占 0.1% 流量的租户全挂，全局错误率只涨 0.1 个百分点，被稀释到看不见 |

## 为什么最小灰度单元是租户

灰度切的是**体验单元**：同一个体验单元不能一半新一半旧。B2C 的体验单元是用户会话，按 `uid` 哈希切就够了。SaaS 多了一层——**一个租户的全部用户共享同一套数据、配置、缓存、权限和账单**，这层是"数据世界"，边界比会话大得多；租户级灰度切的是数据世界。

### 三种切法对比

| 切分粒度 | 切分精度 | 一致性风险 | 可观测性 | 客户可感知度 | 典型适用场景 |
|---|---|---|---|---|---|
| 按请求 | 流量比例准 | 最高：同一会话里新旧混用 | 只能看全局 | 强：刷新一次换一个版本 | 无状态读接口、压测、镜像 |
| 按用户 | 用户比例准，流量近似 | 中：用户内一致，租户内分裂（数据、缓存、账单） | 归因到用户，归因不到客户 | 中：同一家客户的人看到不同界面 | 有登录态的 B2C、只改读路径 |
| 按租户 | 租户比例准，流量比例可能严重偏离 | 低：租户内完全一致 | 归因到客户与合同 | 强：整个客户一起升级或一起不动 | SaaS 写路径、schema 与计费变更 |

切分键怎么选、粘性怎么保证，见 [47.3 路由与灰度](../47-网关与入口/47.3-路由与灰度.md)：它解决"同一个键不来回跳"，不解决"租户内共享状态被切成两半"。

### 一半用户 v1 一半 v2：在 B2C 是体验问题，在 SaaS 是数据事故

同一个租户内按用户分流，破的是租户级共享状态，不是用户级体验：

| 共享状态 | 用户级分流后发生什么 |
|---|---|
| 数据模型 | 同一个租户的订单、发票、项目记录被写进两种格式；导出、报表、对账、下游 ETL 同时读到两种 |
| 配置 | 租户配置版本是**租户粒度**的（见 [65.4 定制化与版本管理](65.4-定制化与版本管理.md)），一份配置被两个版本解释，两个用户读到不同行为 |
| 权限 | 权限按租户组织，v2 改了继承规则，一半人权限变大、一半人变小 |
| 缓存 | 缓存键带 `tenant_id` 不带 `user_id`，两个版本抢写同一个键 |
| 计费 | 用量事件的去重键、计量单位、聚合粒度按租户收敛，两个口径叠加出不可解释的账单 |

用一个独立程序（同样 200 租户 × 40 用户、同样 FNV-1a 桶函数）跑两组：整租户切取桶号前 10% 的租户，用户切让每个用户按 `FNV(user:租户:用户)` 独立抽 10% 的签。本机实测输出（`go version go1.27.1 darwin/arm64`，两组实验各跑一遍）：

```text
user  ：v2 用户占比 9.9%（790/8000），租户内格式分裂 198/200
tenant：v2 用户占比 10.0%（800/8000），租户内格式分裂 0/200
```

两行只差一个切分键：**流量占比 9.9% 对 10.0%，效果是 198 个租户格式分裂对 0 个**。按用户切的那一半，198 个租户里每个都同时有新老两版用户，它们的写路径、缓存键、账单解析器在同一个租户内并行——而工程侧的错误率指标全程正常，因为没有任何请求失败，只是数据在慢慢分成两套。用户级灰度在 B2C 是"更细"；在 SaaS 是"把一个客户劈成两个数据世界"。

> 💡 我的判断是：SaaS 的灰度单元不该由"流量比例要多准"决定，而该由"共享状态的最小闭包"决定。租户是数据、缓存、配置、账单这四样共享状态的最小闭包，所以它是灰度单元的下限，不是粒度选项之一。按用户切比按租户切"更细"只是错觉——细的是切分比例，裂的是数据。

## 租户分桶与批次顺序

### 分桶键：把租户映射到固定的批次

四种常用键：**`tenant_id` 哈希**（FNV/xxhash + 固定盐，稳定均匀，按比例放量，坑是改盐等于重新洗牌）；**合同分层 `tier`**（商务侧可解释，大客户单独一批，坑是合同变更会让租户换桶）；**地域/合规域**（与故障域一致，小地域租户太少，一批可能不到 3 个）；**白名单**（内部租户与友好客户，人工指定，坑是被当成"测试账号"走特殊路径）。

同一个租户的桶号必须**固定**：批次只是"桶区间"，B1 是 0–10% 的桶，B2 是 10%–100% 的桶，扩批是把区间拉宽，不是重新抽签。

### 批次顺序的判据：爆炸半径 × 可承受损失

批次顺序不是按流量比例排，而是按 **爆炸半径 × 可承受损失** 从小到大排。三个输入：

- **爆炸半径**：这批租户坏掉，波及多少客户、多少用户。单位是**客户数**，不是请求数——客户投诉不以 QPS 计。
- **可承受损失**：营收在险（该批租户全挂一天的营收损失）+ 声誉在险（内部租户是 0，旗舰客户的一次公开故障可能进新闻）。
- **可观测性**：这批租户有没有人在盯、数据量够不够下结论。内部租户和友好客户有对讲机，旗舰客户有专属群。

```go
// go run plan.go：1000 个租户按 tier 分层、按桶号排批次，算每批的影响面。
package main

import (
	"fmt"
	"sort"
)

type T struct {
	id, users int
	tier      string
	qps, acct float64 // qps：平均请求/秒；acct：全挂时每天损失的营收（USD）
}

func h(s string) float64 { // 桶号 = FNV-1a(tenant_id) % 10000；桶号固定，批次只是桶区间
	x := uint32(2166136261)
	for i := 0; i < len(s); i++ {
		x = (x ^ uint32(s[i])) * 16777619
	}
	return float64(x%10000) / 10000
}

func main() {
	tiers := []struct {
		name      string
		n, lo, hi int
		per, acct float64
	}{
		{"internal", 6, 40, 40, .015, 0},
		{"friendly", 6, 180, 260, .016, 120},
		{"small", 640, 3, 30, .010, 60},
		{"mid", 288, 60, 300, .015, 400},
		{"large", 46, 500, 2000, .020, 2500},
		{"flagship", 14, 3000, 9000, .030, 12000},
	}
	var ts []T
	by := map[string][]T{}
	for _, tr := range tiers {
		for i := 0; i < tr.n; i++ {
			u := tr.lo + int(h(fmt.Sprintf("%s-%d", tr.name, i))*float64(tr.hi-tr.lo+1))
			t := T{len(ts), u, tr.name, float64(u) * tr.per, tr.acct}
			ts = append(ts, t)
			by[tr.name] = append(by[tr.name], t)
		}
	}
	for k := range by {
		sort.Slice(by[k], func(a, b int) bool {
			return h(fmt.Sprint(k, by[k][a].id)) < h(fmt.Sprint(k, by[k][b].id))
		})
	}
	pick := func(tier string, lo, hi float64) (ids []int) {
		l := by[tier]
		for i := int(lo * float64(len(l))); i < int(hi*float64(len(l))); i++ {
			ids = append(ids, l[i].id)
		}
		return
	}
	type B struct {
		name, rule string
		ids        []int
	}
	bs := []B{
		{"B0", "内部租户 dogfood", pick("internal", 0, 1)},
		{"B1", "白名单友好客户 + 小客户前 10%", append(pick("friendly", 0, 1), pick("small", 0, .10)...)},
		{"B2", "小客户剩余 90%", pick("small", .10, 1)},
		{"B3", "中型客户前 15%", pick("mid", 0, .15)},
		{"B4", "中型客户剩余 85%", pick("mid", .15, 1)},
		{"B5", "大型客户 100%", pick("large", 0, 1)},
		{"B6", "旗舰客户 100%", pick("flagship", 0, 1)},
	}
	idx := map[int]T{}
	var totalQPS, totalUsers float64
	for _, t := range ts {
		idx[t.id], totalQPS, totalUsers = t, totalQPS+t.qps, totalUsers+float64(t.users)
	}
	qps, risk := map[string]float64{}, map[string]float64{}
	fmt.Println("| 批次 | 放量内容 | 租户数 | 租户占比 | 流量占比 | 影响用户数 | 用户占比 | 预期工单数* | 单日营收在险(USD) |")
	fmt.Println("|---|---|---|---|---|---|---|---|---|")
	for _, b := range bs {
		var q, u, m float64
		for _, id := range b.ids {
			q, u, m = q+idx[id].qps, u+float64(idx[id].users), m+idx[id].acct
		}
		qps[b.name], risk[b.name] = q, m
		fmt.Printf("| %s | %s | %d | %.1f%% | %.1f%% | %.0f | %.1f%% | %.0f | %.0f |\n",
			b.name, b.rule, len(b.ids), float64(len(b.ids))/10, q/totalQPS*100, u, u/totalUsers*100, float64(len(b.ids))*.6, m)
	}
	byQPS := append([]B(nil), bs...)
	sort.Slice(byQPS, func(a, b int) bool { return qps[byQPS[a].name] > qps[byQPS[b].name] })
	fmt.Printf("\n按流量降序（错）：第一批 = %s，%d 租户、%.1f%% 流量、单日营收在险 %.0f USD\n",
		byQPS[0].name, len(byQPS[0].ids), qps[byQPS[0].name]/totalQPS*100, risk[byQPS[0].name])
	fmt.Printf("按爆炸半径 × 可承受损失（对）：第一批 = B0，%d 租户、%.2f%% 流量、营收在险 0 USD\n",
		len(bs[0].ids), qps["B0"]/totalQPS*100)
}
```

完整代码在仓库 [tools/examples/65.5-plan/](../../../tools/examples/65.5-plan/README.md)，`go run ./plan` 可复现这批分层与影响面。

本机实测输出（`go version go1.27.1 darwin/arm64`，`go run plan.go`；* 工单数假设受影响租户中 60% 会提 1 张工单，作为"客户可感知"的代理指标）：

```text
| 批次 | 放量内容 | 租户数 | 租户占比 | 流量占比 | 影响用户数 | 用户占比 | 预期工单数* | 单日营收在险(USD) |
|---|---|---|---|---|---|---|---|---|
| B0 | 内部租户 dogfood | 6 | 0.6% | 0.1% | 240 | 0.1% | 4 | 0 |
| B1 | 白名单友好客户 + 小客户前 10% | 70 | 7.0% | 0.7% | 2362 | 1.2% | 42 | 4560 |
| B2 | 小客户剩余 90% | 576 | 57.6% | 2.1% | 9551 | 4.7% | 346 | 34560 |
| B3 | 中型客户前 15% | 43 | 4.3% | 2.7% | 8137 | 4.0% | 26 | 17200 |
| B4 | 中型客户剩余 85% | 245 | 24.5% | 14.7% | 44133 | 21.7% | 147 | 98000 |
| B5 | 大型客户 100% | 46 | 4.6% | 25.5% | 57542 | 28.3% | 28 | 115000 |
| B6 | 旗舰客户 100% | 14 | 1.4% | 54.2% | 81403 | 40.0% | 8 | 168000 |

按流量降序（错）：第一批 = B6，14 租户、54.2% 流量、单日营收在险 168000 USD
按爆炸半径 × 可承受损失（对）：第一批 = B0，6 租户、0.08% 流量、营收在险 0 USD
```

这张表有两个反直觉之处。

**流量占比不等于影响占比。** 旗舰客户 14 个（1.4% 租户）占 54.2% 流量；小客户 576 个（57.6% 租户）只占 2.1% 流量。把影响换成客户可感知的工单，比例倒过来：B2 是 346 张，B6 是 8 张。**按流量排批次，第一批就是旗舰客户——一次押上 54.2% 流量和 16.8 万美元/日的营收在险；按客户可感知的影响排，最吵的 B2 排在客户有耐心的位置，旗舰客户放最后。** 爆炸半径的盒子大小见 [35.8 故障隔离](../../L3-质量属性/35-可用性/35.8-故障隔离.md)。

**白名单租户不是"测试账号"。** 内部租户和友好客户必须在**生产**链路上跑，走和其他租户完全相同的版本路径与数据库。给白名单开特例（读副本、跳过限流、单独配置），它验证的就是生产上不存在的路径，第一批结论作废。批次顺序的判据可写成一条不等式：**先让"损失 × 概率"最小的那批上**。内部租户损失为 0；小客户数量多、单户损失小，是"看统计显著性"的最佳批次；大客户与旗舰损失大、数量少，只能放最后并提前通知。

> 🔑 铁律：**批次顺序按"这一批坏了谁受损、损失多大"排，不按流量占比排。** 流量是容量指标，不是风险指标；不占流量的批可能最吵（小客户 576 个），占一半流量的批可能只有 8 张工单（旗舰 14 个），但它是唯一可能上新闻的批。

## 租户内不可分流的三条硬约束

三条约束的共同点：破了以后事故不是"体验不一致"，而是"数据不一致"。

| 约束 | 为什么不能分流 | 违反后的事故 | 防线 |
|---|---|---|---|
| ① 数据格式：写路径必须统一版本 | 记录格式由代码版本决定；租户内任意一次导出、报表、对账都会同时读到两种格式 | 导出文件里一半金额是分、一半是元；ETL 把 v2 字段当 null。按 1/10 写量走 v2 算：70 条 v2 记录被 v1 解析器读成 0，账单少算 70/400 = 17.5% | 写路径分流只允许"整租户"粒度；v2 写的字段旧版本必须能读，否则影子表或独立库 |
| ② 缓存与派生数据：同一租户的缓存键不能一半新一半旧 | 缓存键是 `tenant_id + 业务键`，不含版本；物化视图、搜索索引、聚合表按租户增量更新 | v2 写的结构被 v1 读，反序列化失败或字段丢失；搜索索引里同租户一半文档有字段一半没有，排序错乱 | 窗口内缓存键加版本号，或 v2 只用专属键；派生数据按租户整体切换并重建 |
| ③ 计费与配额：同一用量事件的口径必须一致 | 用量事件是计费原料，两版本的单位、去重键、聚合粒度必须一致；配额预扣是账期累计 | v1 按"次"计、v2 按"GB"计，同一账期两种口径叠加，账单无法解释到事件级；预扣一半在 v1 计数器一半在 v2 计数器，超卖 | 口径变更走版本化的事件 schema（见 [65.3 计费与配额](65.3-计费与配额.md)），灰度期由一套计量服务收口；配额只有一个写者 |

公共根因只有一条：**读路径可以兼容多版本，写路径不可以**。实践里唯一安全的"租户内分流"形态是写接口全租户统一版本、只灰度读接口；前提是 v2 的读能读 v1 写的全部历史数据（向后兼容的判据见 [55.5 向后兼容](../../L5-工程效能/55-发布与回滚/55.5-向后兼容.md)），不是只读新数据。

> ⚠️ 常见错误：灰度"只改前端/只改展示"就以为没有一致性约束。缓存的 value 结构、导出文件的列格式、搜索索引的 mapping 都算"写"，都是租户级共享状态。

## 数据库变更：共享表下不能按租户改 schema

这是三条硬约束里最容易被忽略的一条：**共享表下不存在"给灰度租户加一列"这个动作。** 表结构是全局的，加列、改类型、加约束、改默认值，对所有租户瞬间生效。

| 隔离形态 | schema 边界 | 能按租户灰度 DB 变更吗 | 代码与 DB 的发布顺序 | 代价 |
|---|---|---|---|---|
| 共享表 + `tenant_id` | 一套全局 schema | **不能** | DB 全局先行（Expand-Contract），旧代码要能在新 schema 上跑 | 兼容期长，双写与回填 |
| 独立 schema（同库、每租户一个） | 每租户独立 | **能**，但要写"两种 schema 都能跑"的代码 | 先改灰度租户的 schema，再灰度代码 | DDL 跑 N 次，schema 漂移要 CI 校验 |
| 独立库 | 每租户独立 | **能**，真正可按租户灰度 | 同上，连接、迁移、备份按租户走 | 成本最高 |

反直觉的例子：给共享表加一个 `NOT NULL` 且无默认值的列，DDL 先上而代码没跟上，**所有租户**的写入立刻失败，不只是灰度租户。索引同理：单独给某个租户加的索引拖慢所有租户的写入，还占全局 DDL 窗口。

所以共享表下"租户级灰度"管不到 DB 变更，只有全局先行一条路；三阶段步骤与发布顺序见 [55.4 数据库变更管理 (Expand-Contract)](../../L5-工程效能/55-发布与回滚/55.4-数据库变更管理.md)。独立 schema/独立库（形态怎么选见 [65.1 租户隔离模型](65.1-租户隔离模型.md)）才有"先改这批租户的 schema"的奢侈，代价是迁移跑 N 次、schema 漂移要靠 `schema_version` 表加校验任务盯住。

> 🔑 铁律：**能按租户灰度的只有"每租户独立的资源"**——独立 schema、独立库、缓存实例、配置。共享资源（表结构、全局索引、消息 topic）的变更只能全局先行、全局回滚，它不在租户灰度的可控范围内。

## 多版本共存窗口

从第一批租户切到 v2，到最后一批切完并决定不回滚，这段窗口里 v1 和 v2 同时在线，**所有共享状态必须双向兼容**（同一条请求怎么整链走同一版本，见 [55.6 灰度与流量染色](../../L5-工程效能/55-发布与回滚/55.6-灰度与流量染色.md)）。

| 共享状态 | 窗口内的要求 | 破了的症状 |
|---|---|---|
| 数据库表 | v2 写的行 v1 能读：新增字段可空、旧代码忽略未知列、不产生新约束 | 旧版本读到 null 崩溃；v1 的回写覆盖掉 v2 的新字段 |
| 缓存 | 两版本对同一键的 value 结构一致，或各用各的键 | 反序列化失败；读到"版本不对"的数据 |
| 消息 / 事件 | 事件 schema 向后兼容，消费者按版本路由或双版本都能消费 | 旧消费者丢弃新事件或解析失败，消息积压 |
| 第三方接口 | v2 新增的调用与字段不能让 v1 租户的回调失配 | 回调无法处理，人工补偿 |

窗口长度 = 批次数 × 每批观察时长 + 回滚缓冲。算例：7 批 × 24h + 48h = 216h = **9 天**；7 批 × 12h + 24h = 108h = **4.5 天**；若合同要求提前 7 天通知，分别是 16 天与 11.5 天。窗口越长成本越高：双版本资源、兼容代码、两套回归矩阵、on-call 记两个版本的行为。

## 按租户归因的指标与放量门槛

全局指标会**稀释**小租户的灾难、**放大**单一大客户的抖动：全局 5xx 错误率 = Σ 租户错误数 / Σ 租户请求数。占 0.1% 流量的租户 100% 失败，全局只从 0.05% 到 0.15%（+0.1 个百分点），告警不响；占 40% 流量的旗舰 5% 失败，全局 +2 个百分点，看着像全局事故，其实只砸一个客户。所以放量决策必须看**每租户**：请求错误率、P99（和它自己的基线比，不和全局比）、关键业务动作成功率（下单/支付/导出/同步）、数据一致性指标（格式分裂条数、回填差异、账单重算偏差）、客服工单。SLO 口径与错误预算见 [50.7 SLO 与错误预算](../50-可观测性/50.7-SLO与错误预算.md)。

放量门槛（**示例口径，阈值按业务定**）：

| 门槛指标 | 计算口径 | 示例阈值 | 不达标动作 |
|---|---|---|---|
| 错误率 | 本批 v2 请求 5xx / 总量 | 比基线高 0.5 个百分点，或 > 1% | 停止放量，回滚本批 |
| 关键动作成功率 | 本批下单/支付成功率 | 比基线低 1 个百分点 | 停止放量，查数据一致性 |
| P99 延迟 | 每租户 P99 的 95 分位 | 超过该租户基线 1.5 倍 | 暂停 1 小时再评估 |
| 数据一致性 | 格式分裂 + 回填差异条数 | > 0 条 | 立即回滚，不谈判 |
| 客户声量 | 本批 P1 工单数 | ≥ 1 | 回滚并主动通知 |

小样本绕不开：每租户请求量 < 100 次/小时时，1 个错误就是 1%。做法两层：批级合并看趋势，单租户异常检测看突变（如某租户错误率从 0 跳到 10%）。

## 回滚粒度：只能整租户

回滚的最小单位是"一批租户"或"一个租户"，不存在"把这个租户里 30% 的用户切回去"——那等于承认租户内可以分流。

三个对象可回性不同：**路由**能回，改桶到上游版本的映射，秒到分钟，机制见 [47.3 路由与灰度](../47-网关与入口/47.3-路由与灰度.md)；**代码**能回，回滚部署，分钟级，但 v2 写的数据仍在；**数据格式**不能"反向执行"，只能靠兼容读、双写或回填，小时到天级。

已写的新格式数据只有三条路：**兼容读**（旧版本能读新格式，字段缺省——首选）、**双写**（窗口内两版都写旧+新格式，回滚后旧版本可读，代价是写放大）、**回填**（按租户重算/重写，代价最大）。这就是"回滚即数据回不去"的边界：回滚设计要区分"能撤销的操作"和"已发生的事实"，见 [55.3 回滚设计](../../L5-工程效能/55-发布与回滚/55.3-回滚设计.md)。模型版本是另一种粒度——原子别名切换，不涉及数据格式，见 [64.4 模型版本与回滚](../64-机器学习系统/64.4-模型版本与回滚.md)。

开灰度前必须准备好三样，缺一样就别开：**每条写路径都有"旧版本可读"的兜底**；**按租户的数据标识**（`tenant_id` 必须在所有派生数据里可查，否则回填与清理找不到边界）；**回滚演练**（至少在一批内部租户上真的切回去一次，验证兼容读有效）。

> 🔑 铁律：**能回滚的开关只有路由，数据没有回滚按钮。** 灰度前先做出"新格式数据旧代码能读"，再谈放量；做不到，就说明这次变更根本不该在共享表上灰度。

## 什么时候别用租户级灰度

| 你的情况 | 别做租户级灰度，改用 |
|---|---|
| 租户数 < 20 | 蓝绿 + 特性开关：每批 2–3 个客户，出问题分不清是版本还是这个客户特殊 |
| 只改展示/文案，无写路径与 schema 变更 | 特性开关按租户开（见 [55.2 特性开关](../../L5-工程效能/55-发布与回滚/55.2-特性开关.md)），不需要两套服务版本 |
| 能秒级回滚且无数据格式变化 | 蓝绿（见 [55.1 发布策略](../../L5-工程效能/55-发布与回滚/55.1-发布策略.md)）：一次切 100% 再回滚，比排 7 批快得多 |
| 客户合同要求变更前书面通知 | 先谈通知期再谈批次，灰度不是绕过合同的工具 |
| 租户多但流量高度集中（少数大客户占 90%） | 有效样本只有 3–5 个客户，按客户逐个谈，别假装是统计灰度 |

租户数 20–100、变更涉及写路径时 3 批就够：内部 → 一半小客户 → 全量。

## 反模式

| 反模式 | 后果 |
|---|---|
| 把 `uid` 哈希换成 `tenant_id` 哈希就开灰度 | 租户内数据格式、缓存、账单被切两半，回滚后数据仍是坏的 |
| 共享表上"只给灰度租户加列" | schema 全局生效，所有租户的写入与查询立刻受影响 |
| 灰度期同时上 DB 变更和代码变更 | 分不清是 schema 还是代码，回滚顺序错一步就丢数据 |
| 按流量占比排批次 | 第一批就是旗舰客户，一次押上 54% 流量与最高营收在险 |
| 只看全局大盘指标 | 小租户 100% 故障被稀释成 0.1 个百分点，发现时已烧一个业务日 |
| 回滚只切路由、不做兼容读 | 旧版本读 v2 数据失败，回滚变成二次事故 |
| 白名单租户走特殊路径 | 验证的是不存在的路径，第一批结论作废 |

## 自检

**Q1** 为什么 SaaS 的灰度单元不能是用户？说出至少两条会被打破的租户级共享状态。

▸ 答案：用户级分流把同一租户的数据世界切成两半。数据格式：同租户的记录被写进两种格式，导出/报表/对账同时读到两种；缓存：键是 `tenant_id + 业务键`，两版本抢写同一个键；计费：用量事件的单位与去重键按租户收敛，两种口径叠加出不可解释的账单；配置与权限也是租户粒度。变更触及这四样中任意一样，用户级分流就不是"更细"，而是 split brain。

**Q2** 1000 个租户里 14 个旗舰客户占 54% 流量，为什么第一批不能是它们？应该看什么指标排批次？

▸ 答案：排序要按"爆炸半径 × 可承受损失"，不是按流量。旗舰客户少但单户损失最大（营收 + 声誉），一批全挂可能上新闻；576 个小客户只占 2% 流量，却会产生 346 张工单——最吵的批流量最小。排批次看：受影响客户数、每客户日营收损失、可观测性，最后才看流量占比。

**Q3** 共享表 + `tenant_id` 的隔离下，能不能"只给灰度租户加一列"？为什么？独立库下呢？

▸ 答案：共享表下不能：schema 属于所有租户，DDL 一瞬间生效；加一个无默认值的 `NOT NULL` 列，老代码 `INSERT` 不带它，所有租户的写入一起失败。共享表下 DB 变更必须全局先行（Expand-Contract），旧代码要能在新 schema 上跑。独立库下可以：先改灰度租户的库，再灰度代码，代价是迁移跑 N 次、schema 漂移要校验。

**Q4** 灰度窗口长度由什么决定？7 批 × 24h 观察 + 48h 缓冲是多长？为什么必须留缓冲？

▸ 答案：窗口 = 批次数 × 观察时长 + 回滚缓冲，7×24+48 = 216h = 9 天。缓冲是给"决定回滚但新格式数据已写入"留的处理时间——回填、兼容读、通知客户都要时间；没有缓冲，回滚只能做成"切路由就算完"，数据回不去。合同要求提前 7 天通知就再加 7 天。

**Q5** 全局错误率 0.15% 看着正常，为什么仍然要按租户看指标？举一个被稀释的例子。

▸ 答案：全局指标按请求数加权，小租户的灾难被稀释、大客户的抖动被放大。占 0.1% 流量的租户 100% 失败，全局错误率只从 0.05% 升到 0.15%，告警不响，但那个客户业务全停。占 40% 流量的客户 5% 请求失败会让全局涨 2 个百分点，看着像全局事故。所以要看每租户错误率、P99、关键动作成功率。

**Q6** 灰度出问题回滚路由后，数据就恢复了吗？说出三种处理已写新格式数据的办法和各自代价。

▸ 答案：没有恢复。路由回滚只让流量回旧版本，新格式数据仍在库里。三种办法：兼容读（旧版本能读新格式，字段缺省，代价最低，首选）、双写（两版都写旧+新格式，回滚后可读，代价是写放大）、回填（按租户重算或重写，代价最大且可能不可逆）。灰度前先做出兼容读，否则不许开写灰度。
