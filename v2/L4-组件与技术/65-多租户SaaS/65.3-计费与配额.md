# 65.3 计费与配额

## 一句话

> 计费 = **计量 → 计价 → 出账 → 收款** 四段流水线，配额 = **账期累计的用量上限**（不是瞬时速率）；两者分开设计，用幂等的用量事件 + 可重算的账单 + 预扣式配额，才做得到"不超卖、不多收、可解释"。

## 先破除五个误区

| 误区 | 现实 |
|---|---|
| 计量就是打日志，月底跑个脚本出账 | 日志是排查用的、会丢会轮转、没有幂等键；计量是**账务前置流水线**，事件不可重写、可重放 |
| 配额 = 限流，超了返回 429 就完事 | 配额管账期累计（月度 100 万次），限流管瞬时速率（每秒 100 次）；配额超限是超额计费/降级/停服，不是每秒一次的 429 |
| 账单要"实时准确" | 账单是派生数据，允许 T+1~T+3 才稳定；真正的要求是**可重算、可追溯**，不是秒级刷新 |
| 先查配额再扣减，逻辑上没问题 | 查与扣之间有并发窗口：1000 个并发抢 100 个配额，实测能超卖 23~900 个 |
| 接上支付渠道，计费系统就算做完 | 收款只是一段；对账、差异处理、发票、催收各是一套机制，混在一段里必然对不平 |

## 四段流水线：每段的失败代价不同

计费不是一个服务，是四段职责清晰的流水线。**上一段的输出是下一段的唯一输入**，越往后改错的代价越大。

| 段 | 输入 | 输出 | 失败后果 | 重跑代价 |
|---|---|---|---|---|
| ① 采集（metering） | 网关日志、业务请求、离线 SDK 上报、消息 | 只追加的幂等用量事件 | 漏记=少收（资损）；重复=多收+退款+客诉 | **低**：按 `(tenant, event_id)` 幂等重放，只补不重 |
| ② 计价（rating） | 用量事件 + 价目表版本 + 合同（承诺/折扣） | 计价明细（每行：聚合区间 + 单价 + 金额） | 算错=账单一致地错，错得很稳定 | **中**：可全量重放，前提是能定位当时的价目版本 |
| ③ 出账（invoicing） | 计价明细 + 账期状态 + 税/币种 | 不可变账单快照 + 调整单 | 晚=收入确认推迟；错=只能红冲 | **高**：账单一旦发出，改数就是改合同凭证 |
| ④ 收款（collection） | 账单 + 支付渠道/银行 | 回款记录、应收账龄、催收状态 | 收不回=坏账 | 见 [67.3 对账与差异处理](../67-交易与账务/67.3-对账与差异处理.md) |

> 🔑 **账单是派生数据，事件才是事实。** 账单可以随时用事件日志重建；事件一旦被"修正"，历史账单就再也无法证明自己。所以计量层只做两件事：**接收、判重**；发现错了就补一条冲正事件，绝不改原事件。

### 重算还是调整：两条路的分界线

封账前用**全量重算（replay）**，封账后用**增量调整（红冲/补记）**。两者不是二选一的技术方案，是账期状态决定的。

| 维度 | 全量重算 replay | 增量调整 红冲/补记 |
|---|---|---|
| 适用时机 | 封账前；价目规则修 bug；对客户无感的重出 | 封账后；单笔争议；迟到事件 |
| 依据 | 事件日志 + 价目版本 | 已发账单 + 调整单 |
| 客户是否可见 | 不可见（重建后重新出账） | **可见**，调整单必须给客户看 |
| 成本量级 | 按月 1 亿事件、单核 5 万事件/秒估：1 亿 ÷ 5 万 = 2000 秒 ≈ 33 分钟 | 与调整笔数成正比，通常秒级 |
| 风险 | 重算结果与已发账单不一致时必须能解释差异 | 调整单堆积，账单越来越难解释 |

> 🔑 每个账期封账时冻结一份**重算指纹**：事件条数 + 最大 `received_at` + 价目表版本号。没有这份指纹，事后说"重算结果和原来一样"无法自证。

## 计量事件：字段决定能不能重算

计量事件是整条流水线的原子事实，字段设计错一个，其余三段全要返工。对外开放 API 的计量口径必须唯一：同一调用在网关与业务侧各记一次，账单就对不平（[47.7 开放平台与API生态](../47-网关与入口/47.7-开放平台与API生态.md)）。

| 字段 | 作用 | 约束 / 出错后果 |
|---|---|---|
| `event_id` | 幂等键，由产生方生成 | 用 ULID 或 UUIDv7（有序，利于索引）；不能用自增 ID，多来源会撞 |
| `tenant_id` | 账务主体 | 必须是唯一键的第一列，否则跨租户会互相去重（实测少收 58.8%） |
| `dimension` | 计量维度 | `api_calls` / `storage_gb_month` / `seats` / `tokens`；维度一旦发布就不能改名，否则历史账单无法归并 |
| `quantity` | 数量 | 用整数最小单位（次 / 字节 / 秒），**禁止浮点**：0.1 的浮点累加误差会变成账单尾差 |
| `occurred_at` | 业务时间 | 决定归哪个账期；客户端时间可错，网关时间更可信 |
| `received_at` | 到达时间 | 只用于两件事：封账判定、审计追溯。**不能拿它归账期** |
| `source` | 来源系统 | 网关 / 业务服务 / 开放平台；对账时要能按来源分口径 |

### 幂等靠唯一约束，不靠"消费端不重复"

上游默认 at-least-once（重试、网关重发、消息重复投递，见 [25.4 幂等设计与去重](../../L1-分布式原理/25-并发、冲突与幂等/25.4-幂等设计与去重.md)），所以重复事件是**正常流量**，不是异常。唯一正确的做法是一条数据库约束：

```sql
-- 幂等键必须带租户：不同租户的事件 ID 空间彼此独立
ALTER TABLE usage_event ADD CONSTRAINT uk_usage_event UNIQUE (tenant_id, event_id);
```

写入时 `INSERT ... ON CONFLICT DO NOTHING` 或捕获唯一键冲突：**插入成功=新事件，冲突=重复事件**。这与交易域"出口唯一约束"是同一条判据（[67.2 幂等与防重](../67-交易与账务/67.2-幂等与防重.md)）。重复要计数但不报警——报警该盯的是**迟到率**和**来源中断**，不是重复。

### 迟到事件：两个时间戳各管一件事

| 事件情况 | 判据 | 处理 |
|---|---|---|
| 正常 | `occurred_at` 在当期，`received_at` ≤ 封账时间 | 计入当期 |
| 迟到未封账 | `occurred_at` 在当期，`received_at` 落在 grace 内 | 计入当期；封账必须等 grace 结束 |
| **迟到已封账** | `received_at` ≥ 封账时间 | 出调整单补记，同时计入迟到率指标 |
| 重复 | `(tenant_id, event_id)` 已存在 | 幂等丢弃 + 计数，不算迟到 |
| 乱序 | `received_at` 的先后 ≠ `occurred_at` 的先后 | 无需特殊处理：归期只看 `occurred_at` |

账期封账时间 = 账期结束 + grace。以 T+3 为例：10 月账期在 11-04 00:00 封账（含 11-03 全天），任何 11-04 及以后到达的 10 月事件都只能走补记。**别把两个时间合成一个**：合成 `occurred_at` 就丢掉"什么时候真的收到"，迟到无法发现；合成 `received_at` 就会把跨月迟到全挤进下月，账期数字与业务对不上。

本机真实跑过的聚合器核心（完整程序与输出在 `tools/examples/65.3-meter/`）： 示例说明见 [tools/examples/65.3-meter/](../../../tools/examples/65.3-meter/README.md)。

```go
// 幂等键：租户 + 事件 ID；重复事件不进任何账期
func (a *Agg) Add(e Event) string {
	k := a.dedupe(e)
	if a.seen[k] {
		a.dups++
		return "重复→丢弃"
	}
	a.seen[k] = true
	p := periodOf(e)                       // 归期只看业务时间
	if isClosed(p, e.Received) {           // 账期已封：只能补记
		a.adjust[key{e.TenantID, p}] += e.Qty
		a.late++
		return "迟到→补记(调整单)"
	}
	a.usage[key{e.TenantID, p}] += e.Qty
	return "计入账期 " + p
}
```

实测输出（`go1.27.1 darwin/arm64`，9 条事件含 2 条重复、1 条迟到、乱序）：

```text
== 按业务时间归期（2026-10 账期已于 2026-11-04 00:00 封账）==
t-001  2026-10  api_calls = 300
t-001  2026-11  api_calls = 420
t-002  2026-10  api_calls = 170
迟到补记（不改已发账单）： t-001 2026-10 = 50
统计：输入 9 条；重复丢弃 2 条；迟到 1 条；乱序到达 3 次；计入账期 6 条

== 账单重算（全量重放事件日志，按业务时间排序喂入）==
重放：t-001 2026-10 = 300，t-001 2026-11 = 420，t-002 2026-10 = 170，2026-10 补记 = 50
与增量聚合一致 = true

== 反例：幂等键只用 event_id（漏 tenant_id）==
正确 key (tenant|event_id)：t-002 2026-10 = 170
错误 key (event_id)       ：t-002 2026-10 = 70  ← 少收 100 次（占 t-002 十月用量的 58.8%）

== 封账后直接改数 vs 出调整单 ==
已发账单 t-001 2026-10 = 300；把迟到 50 直接并进 10 月 = 350，差额 16.7%
```

三个结论都能从输出里直接读出：**重放与增量结果一致**（可重算）；**幂等键漏租户会少收**（58.8% 不是小数）；**迟到事件直接并进已封账账期，会让已发账单变动 16.7%**——所以它只能进调整单。

## 配额 ≠ 限流：一对最容易混的东西

配额和限流经常被做成同一个中间件，结果是两边都不对。它们回答两个不同的问题。

| 维度 | 配额（quota） | 限流（rate limit） |
|---|---|---|
| 语义 | **账期累计**用量上限 | **瞬时速率**上限 |
| 例子 | 月度 API 调用 100 万次 | 每秒 100 次 |
| 时间尺度 | 月 / 季 / 年 | 秒 / 分钟 |
| 判定位置 | 业务/计量层（要记账、要能对账） | 网关/入口层（保护系统） |
| 存储 | 按账期分键的持久计数，不能靠 TTL 过期来"重置" | 短生命周期计数，窗口一过自动失效 |
| 超限行为 | 超额计费 / 降级 / 停服 / 提示续购 | 429 + `Retry-After` |
| 超限后怎么恢复 | 续购、下账期重置、买加油包；不能"等一秒" | 窗口一过自动恢复 |
| 失败后果 | 少收钱或多收钱 | 系统被打穿 |
| 实现主场 | 这里 | [35.7 限流](../../L3-质量属性/35-可用性/35.7-限流.md) |

一个场景把区别说死：月度配额 100 万次、入口限流 100 次/秒。某租户 2 秒内打了 150 次——限流层在第 1 秒内第 101 次就开始 429（**150 次里只有约 100 次通过**），配额层看到的是"本月已用 100 次"，远没到上限，不会有任何提示。反过来，配额用满 100 万次的瞬间，限流层毫无反应（它只看每秒速率）。

> 🔑 正确的串联顺序是**先限流、后扣配额**：限流在入口保系统不死，配额在业务层决定收多少钱。把两者合成一个计数器，就会出现"因为本月额度用完，所以每秒限流也变了"这种根本讲不通的行为。

租户维度独立计数是前提：配额键、限流键都必须带 `tenant`，否则一个租户打满，全体租户一起 429（见 [49.4 多租户权限模型](../49-身份与访问管理/49.4-多租户权限模型.md)）。

### 配额必须预扣：先查再写一定会超卖

"先查用量，没超就扣减"是计费系统最常见的一行代码，也是超卖的唯一来源：

```go
// 错误：查与扣之间是并发窗口，窗口内所有请求都读到同一个旧值
seen := atomic.LoadInt64(&used)   // ① 查
if seen < limit {                 // ③ 用旧值判定
	atomic.AddInt64(&used, 1)     // ④ 扣
}

// 正确：CAS 预扣，判定与扣减是同一个原子操作
for {
	cur := atomic.LoadInt64(&used)
	if cur >= limit {
		return // 配额已满，拒绝
	}
	if atomic.CompareAndSwapInt64(&used, cur, cur+1) {
		return // 预扣成功
	}
}
```

本机实测：配额 100，1000 并发同时抢（`go1.27.1 darwin/arm64`，GOMAXPROCS=8）：

```text
== 错误实现：先查再改（读有 1ms 存储往返）==
放行 1000 个，超卖 900 个（放行量是配额的 1000%）

== 错误实现：先查再改（无模拟延迟，仅在读写之间让出一次调度）==
不让出调度 5 次放行：[100 100 100 100 100]（超卖 0）
让出一次调度 5 次放行：[387 135 1000 603 1000]（超卖 287–900）

== 正确实现：CAS 原子预扣 ==
放行 100 个，拒绝 900 个，超卖 0 个

== 预扣 + 补偿（100 个预扣成功的请求里 20% 下游失败）==
忘了退配额：预扣 100，成功 80，最终用量 100 → 按 100 计费，多收 20 次（占成功量的 25%）
失败退配额：预扣 100，成功 80，释放 20，最终用量 80 → 按 80 计费，多收 0%
```

超卖量怎么估：**超卖上界 ≈ 检查窗口内并发进入的请求数 ≈ QPS × (查看到写入的延迟)**。检查有 1ms 往返、峰值 1000 QPS，窗口里就有约 1 个请求；赶上突发拥塞，窗口内可能是几十上百个。「不让出调度时 5 次都正好 100」是最危险的实测结果——**本地小流量测不出窗口，不代表窗口不存在**，一旦 GC 或线程切换把它撑开，就直接超卖到 10 倍。

### 落到真实存储：Redis 上的三行代码差别

同样的逻辑到 Redis，差别在命令顺序。本机用本地 `redis:7.2.9`（容器 `alpine:3.20`，端口 16382）实测 1000 并发：

```text
== 错误：GET 判定后再 INCR ==
放行 123 个，超卖 23 个，Redis 最终计数 123（配额的 123%）

== 正确：INCR 先扣，超限 DECR 回退 ==
放行 100 个，拒绝 900 个，超卖 0 个，Redis 最终计数 100（客户端多花 900 次 DECR）

== 正确且单次往返：Lua 里「扣 + 判 + 回退」==
放行 100 个，拒绝 900 个，超卖 0 个，Redis 最终计数 100（客户端只 1 次往返）
```

注意 Redis 这组只超卖 23 个（本机回环 RTT 极小，窗口窄），Go 那组模拟 1ms 往返就超卖 900 个——**超卖量跟窗口宽度成正比**，不是 Redis 比内存安全。配额计数是高频写入的计数系统，存储布局与合批不归计费层（见 [44.22 计数系统](../44-数据库/44.22-计数系统.md)）。

| 预扣实现 | 原子性 | 代价与坑 |
|---|---|---|
| SQL：`UPDATE ... SET used=used+1 WHERE used < limit`，看 affected rows | 原子 | 单行热点，写入 QPS 被单行锁卡死 |
| Redis：`INCR` 后判超限再 `DECR` | 原子 | 被拒请求多一次回退往返（实测 900 次 DECR） |
| Redis Lua：扣 + 判 + 回退写在脚本里 | 原子 | 单次往返，推荐；脚本要短，避免长事务阻塞 |
| 本地原子变量 / CAS | 单机原子 | 多实例各算各的，全局照样超卖 |
| `GET` 判 + `INCR`/`SET` | 非原子 | 必超卖（实测 23~900 个） |

### 补偿：预扣最大的坑不是超卖，是忘了退

预扣是"先占坑再办事"，办事失败必须把坑退回去，否则客户为失败的请求付钱。

| 预扣时机 | 失败类型 | 补偿动作 | 幂等要求 |
|---|---|---|---|
| 请求入口 | 参数校验失败、鉴权失败 | 立即释放 | 用同一个 `request_id` 做释放事件，重复释放也只减一次 |
| 同步调用下游 | 超时/未知状态 | 不能立刻释放：先查询结果，确认失败再释放 | 未知状态不能当失败（同 [67.2 幂等与防重](../67-交易与账务/67.2-幂等与防重.md) 的三态） |
| 异步任务 | 重试中 | 保留占用直到终态，重试不再扣 | 以任务终态为释放依据 |
| 进程崩溃 | 无终态 | 定时对账扫描：占用超过 N 分钟且无终态 → 释放 | 扫描补偿本身也要幂等 |

> 💡 我的判断是：**预扣最贵的不是实现，是补偿的完整度。** 实测里"忘了退"直接让成功量多收 25%——这比超卖更难发现，因为超卖会表现为"用量突然暴涨"被监控抓到，而漏退表现为"用量长期偏高几个点"，客户不逐笔查就发现不了，等发现时已经收错几个账期。

> ⚠️ 什么时候别用预扣：如果计费是**后付费的软配额**（超额就多收钱、不拦截），预扣就是给自己找麻烦——直接异步计量、账单期算超额即可。但入口仍要有粗粒度限流兜底，别让一个租户把系统打穿。

## 计费模型怎么选

模型决定收入曲线、客诉结构和工程复杂度，不是"定价部门的事"。

| 模型 | 收入可预测性 | 主要客诉点 | 实现复杂度 | 与配额的耦合 |
|---|---|---|---|---|
| 按席位 | 高（可预测） | 离职员工算到月底、按天折算扯皮 | 低（用户数变更事件） | 弱（席位本身是计费对象） |
| 按用量 | 低（波动大） | 账单震惊、无法做预算 | 高（计量+计价+超额+明细） | 强（配额就是用量上限） |
| 按功能包 | 中 | 买了没用、用了没买 | 中（计费与权限联动） | 弱 |
| 混合：底价 + 超量 | 中高 | 底价觉得贵、超量单价觉得坑 | 最高（两套计价叠加） | 强 |

### 阶梯定价与承诺消费怎么落到 rating

阶梯有两种，算法完全不同，报价单上必须写清是哪一种（单价为示例值，非任何厂商报价）：0–100 万次 0.010 元/次，100–1000 万次 0.008 元/次，>1000 万次 0.006 元/次。

- **累进（graduated）**：800 万次 = 100 万×0.010 + 700 万×0.008 = 1 万 + 5.6 万 = **6.6 万元**
- **整档（volume）**：800 万次 = 800 万×0.008 = **6.4 万元**

同一份"阶梯价目表"两种算法差 2000 元。`rating` 模块必须把 `tier_mode` 作为价目表字段持久化，不能靠代码里写死。

**承诺消费（commit）**是"预付费 + 折扣"，落成三条规则：① 合同签 1200 万次/年，每月释放 100 万次额度（1200 ÷ 12）；② 实际用量先抵扣当月释放额度；③ 超出部分按合同折扣价计费。未用完的额度按合同决定结转还是作废——**这条必须写进合同**，否则月底会有"我买了为什么不能用"的争议。账务上它是"预收 → 按月释放确认"，不是"用了才收"。

### 价格变更：版本化价目表，生效时间按 `occurred_at`

| 规则 | 做法 | 不做会怎样 |
|---|---|---|
| 不原地改价 | 每次调价新增一个价目版本，`price_version_id` 写进每条计价明细 | 改价后重算历史账单，金额全变，审计对不上 |
| 生效区间 | 版本带 `effective_from` / `effective_to`，按事件 `occurred_at` 匹配 | 按出账时间匹配，跨月事件被套上新价格 |
| 合同锁价 | 签约时把 `price_list_id + version` 写进合同 | 客户签的是旧价，账单按新价收 |
| 跨变更账期 | 按 `occurred_at` 把账单行拆成两段（旧价段 + 新价段） | 整月按一个价算，必然多收或少收 |
| 红冲 | 冲正使用**原版本**单价 | 红冲金额与原账单不等，对不平 |

## 账期封账与可解释性

封账要做三件事，缺一件都会在半年后爆炸：① **冻结输入**：记录账期事件条数、最大 `received_at`、所用价目版本，形成重算指纹；② **生成不可变账单快照**（含计价明细与事件区间引用）；③ **关闭该账期的写入口**：此后只允许调整单，不允许任何"修正"。

为什么封账后不能改数：账单是**合同凭证**——客户手里拿着一份、财务已确认收入、可能已开票、审计要留痕。改数意味着系统版本与客户版本不一致，任何一方都拿不出可信证据。正确做法只有调整单，三要素缺一不可：

| 调整单要素 | 作用 |
|---|---|
| 引用原账单行 | 客户能对上"改的是哪一行" |
| 原因码 | 迟到补记 / 计费 bug / 合同变更 / 争议让步，可统计分类 |
| 审批人与时间 | 审计追责，也防止"随手改一下" |

### 可解释性：客户问"这 1 万次是哪来的"，要能三步下钻

| 客户问题 | 需要的数据 | 存在哪 |
|---|---|---|
| 这 1 万次是哪来的 | 计价明细行 → 聚合区间 → 事件 ID 列表 | `usage_event` 明细（按租户+账期分区） |
| 为什么单价变了 | 账单行上的 `price_version_id` | 价目表版本库 |
| 为什么有这笔调整 | 调整单的 `cause_code` + 原账单行 | 调整单表 |

`usage_event` 明细保存期要覆盖**计费争议期**：经验上 12–24 个月（最终由合同与税务口径定），按 `(tenant, 账期)` 分区，到期归档冷存而不是直接删（保留期与冷热分层见 [46.6 数据生命周期](../46-数据架构/46.6-数据生命周期.md)）。明细只存聚合数不存事件 ID，第一笔争议就答不上来。

收款段与对账的衔接只有一句：**账单是应收，渠道流水是实收，两者逐笔比对并让差异闭环**，机制见 [67.3 对账与差异处理](../67-交易与账务/67.3-对账与差异处理.md)。

## 内部成本 ≠ 对外客户账单

FinOps 的成本账单和客户账单长得像，口径完全不同，**不能互相替代**。

| 维度 | 内部成本账单（FinOps） | 对外客户账单 |
|---|---|---|
| 口径 | 分摊与估算，含共享成本（网络、监控、控制面） | 合同约定的计量口径，逐笔可举证 |
| 可变性 | 分摊规则可调（尽量季度稳定） | 变更要公告/改合同，**不能追溯** |
| 精度 | 近似即可，±5% 通常可接受 | 精确到计价单位，尾差要能解释 |
| 争议处理 | 内部裁决 | 客户可拒付、可要求审计、可诉讼 |
| 目的 | 降本问责 | 收钱 + 合规 |

把内部成本账单直接发给客户，等于把"估算 + 可变口径"卖出去：分摊规则一改，客户账单就波动，而客户没有任何合同依据接受这个波动。成本归因、分摊口径与 chargeback 的完整机制见 [39.5 FinOps与账单治理](../../L3-质量属性/39-成本/39.5-FinOps与账单治理.md)。

## 什么时候别自研

自研计费 = 计量 + 计价 + 出账 + 对账 + 发票 + 催收六个模块，还要跟着税率、发票规则、支付渠道变。判据如下：

| 你的情况 | 建议 |
|---|---|
| 客户 < 50、只有一种订阅套餐、不按量计费 | 用托管计费（Stripe Billing / Chargebee / 云市场计费），自研是负资产 |
| 按量计费但只有 1–2 个维度、合同简单 | 自建计量，计价与出账托管 |
| 多维度用量 + 承诺消费 + 信用额度 + 发票税务深度集成 | 自研（托管很难贴合合同条款） |
| 客户数千以上、毛利对抽成费率敏感 | 自研，抽成会吃掉毛利 |

量级对比的算法（人月成本按 3 万估，非报价）：自研 2–3 人 × 3–6 个月 = 6–18 人月 → 18–54 万元，加 0.5 人维护 ≈ 18 万元/年，首年合计 36–72 万元；托管按流水抽成，费率多为 0.5%–1%（以厂商报价为准），月流水 100 万 → 6–12 万元/年。**月流水低于 100 万、租户少于 50 时，自研首年成本通常是托管的 3–12 倍**，且要自己承担合规与对账责任。月流水上千万时抽成就是真金白银，自研才划算。

## 反模式

| 反模式 | 后果 |
|---|---|
| 账单直接按网关日志 `COUNT(*)` 出 | 重试/网关重发导致多收；日志轮转后被清理，账单无法重算也无法举证 |
| 计量事件没有幂等键，或幂等键只用 `event_id` | 重复投递多收；跨租户 ID 撞号少收（实测少收 58.8%） |
| 用 `received_at` 归账期 | 跨月迟到事件全挤进下月，账期数字与业务对不上，且迟到永远发现不了 |
| 封账后直接 `UPDATE` 账单金额 | 与客户持有的账单不一致，已确认收入与已开票对不上，审计无法解释 |
| 配额"先查再扣" | 并发超卖（实测 23~900 个），超卖部分要么收不到钱要么得罪客户 |
| 预扣后业务失败不退配额 | 客户为失败请求付费，用量虚高且不报警，实测多收 25% |
| 价目表原地改价 | 历史账单被追溯改价，已签合同客户金额变化，法律风险 |
| 把配额和限流做成同一个计数器 | 配额靠 TTL 过期重置会丢已用量；限流被持久化拖慢，两边都不准 |
| 内部成本账单直接给客户 | 客户看到的是分摊估算，争议时无合同依据可举证 |

## 自检

**Q1** 为什么账单可以全量重算，而"已发出的账单"又不能改数？

▸ 答案：两者操作的对象不同。重算重建的是**派生数据**（用事件日志重新算出金额），不碰已发账单；已发账单是合同凭证，客户手里、财务账上、发票上都有一份，改数等于制造多个互相矛盾的版本。所以封账前的错误用重算修，封账后的错误只能出调整单，靠"引用原行 + 原因码 + 审批人"把变更变成可审计的增量。

**Q2** 一个事件 `occurred_at = 10-31 23:58`、`received_at = 11-05`，而 10 月账期在 11-04 封账。这笔记到哪？两个时间能不能合成一个？

▸ 答案：不能进 10 月账单，只能出调整单补记（或按合同记到 11 月）。两个时间各管一件事：`occurred_at` 决定"属于哪个账期"，`received_at` 决定"账期是否已封"。只留 `occurred_at` 就发现不了迟到、迟到率无从监控；只留 `received_at` 就会把跨月迟到全挤进下月，账期与业务错位。这条 50 次的迟到事件相当于 t-001 十月用量的 16.7%。

**Q3** 月度配额 100 万次、入口限流 100 次/秒。某租户 2 秒内打了 150 次，配额层和限流层分别会发生什么？

▸ 答案：限流层在第 1 秒第 101 次之后开始 429，两秒里只有约 100 次通过；配额层只看到"本月已用约 100 次"，远低于 100 万，不会有任何提示。这说明两者语义不同：限流管瞬时速率、超了立即拒绝且秒级恢复；配额管账期累计、超了要续购或等账期重置。把两者做成同一个计数器，必然出现"因为本月额度用了多少，所以每秒限流变了"这种不合理行为。

**Q4** "先查配额再扣"在 1000 并发下会超卖多少？加一把互斥锁为什么不是最优解？

▸ 答案：超卖量取决于检查窗口宽度：本机模拟 1ms 往返时 1000 个请求全部放行（超卖 900），真实 Redis 回环 RTT 下超卖 23 个。互斥锁能防超卖，但热点 key 上的 QPS 被单锁串行化；数据库单行 `UPDATE ... WHERE used < limit` 同样是单行热点。更合适的是 Redis `INCR` 先扣后判（超限 `DECR` 回退）或 Lua 单次往返；大配额再按实例/分片预取，精度与负载的取舍见 [35.7 限流](../../L3-质量属性/35-可用性/35.7-限流.md)。

**Q5** 承诺消费（commit）在 `rating` 里怎么落？为什么不能简单"用满了就给最低价"？

▸ 答案：承诺消费是预付费合同，要拆成三条规则：每月按承诺总额 1/12 释放额度、实际用量优先抵扣释放额度、超出部分按合同折扣价计费；未用额度按合同结转或作废。简单"用满给最低价"会把预付费错记成后付费：收入确认时点错了、未用额度没有负债科目、客户中途解约时已付费用与已用量对不上。它同时要求价目表带合同绑定（`price_list_id + version`），否则调价会追溯改到已签合同。

**Q6** 客户问"这 1 万次是哪来的"，你需要哪些数据才能答？这些数据要留多久？

▸ 答案：要能三步下钻：账单行 → 计价明细行（含单价与 `price_version_id`）→ 用量事件（含事件 ID、时间区间、来源）。所以要存事件级明细，不能只存聚合数，也不能只存日志（日志会轮转、无幂等键、无法重算）。留存期要覆盖计费争议期，经验上 12–24 个月，最终由合同与税务口径定；按租户+账期分区，到期归档冷存。少了任一环，客户一追问就只能"人工查日志猜"。
