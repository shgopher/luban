# 65.4 定制化与版本管理

## 一句话

> 定制化只能往**配置与扩展点**里沉，绝不能往代码分支里沉；版本管理真正要管的是三样东西的乘积——**平台版本 × 租户配置版本 × 数据模型版本**，组合数决定升级成本，所以**支持窗口必须写进合同**。

## 先破除四个误区

| 误区 | 现实 |
|---|---|
| “大客户要定制，就给他拉个分支” | 分支不是一次交付，是**第二条产品线**：每个补丁、每个线上修复都要 backport，每份合同都要单独回归；分支数翻倍，长期人力接近翻倍 |
| “配置越多越灵活” | 每个配置项都是一份**长期兼容契约**：有默认值、校验、审计、回滚路径。只加不删，三年后没人说得清哪项为什么是这个值 |
| “版本管理就是写 CHANGELOG” | CHANGELOG 是产物，不是管理。管理的是**线上同时存在几个版本、每个支持到什么时候、谁为组合付费** |
| “所有客户都用最新版最省事” | 客户有发布窗口、审计冻结期、内部对接系统；强制升级在合同里往往就是违约——省下测试费，付出续费率 |

四句话指向同一件事：**定制化与版本管理，都是把“差异”变成可计量、可定价、可退出的对象**。差异不可怕，可怕的是它长成“代码”——代码没有版本边界，只有越来越多的人不敢动它。

## 定制化只有三种形态，而且是一条有方向的台阶

差异的载体只有三个：**值、行为、代码**：

| 形态 | 交付周期 | 可维护成本 | 升级成本 | 故障归属 | 能回滚 | 适用条件 |
|---|---|---|---|---|---|---|
| **配置**（参数 / 套餐 / 模板） | 小时级～1 天 | 低：一项一套校验 | ≈0：随平台发布升级 | 平台（校验不严就是平台的错） | 秒级：改回上一 revision | 差异只是“取值不同” |
| **扩展点**（插件 / webhook / 脚本 / 自定义字段） | 1～6 周（经验上） | 中：一份契约 + 每个插件联调 | 中：契约版本兼容，插件跟一版 | 契约双方（契约不清算平台的） | 停用插件即可 | 差异是“行为不同但语义可复用” |
| **代码分支**（fork / 专有版本） | 1～6 个月（经验上） | 高：一条产品线的全部开销 | 高：每个补丁都要 backport | 分支维护者（事实上无人能甩锅） | 整份回滚到另一个专用版本 | 合同买断 + 隔离部署 + 代码面差异 ≥30% |

三行是一条台阶，方向是**代码重复度**：配置 0 份代码、扩展点 1 份内核 + N 份小插件、分支 N 份完整代码。每下一级，修复的批量性掉一级——配置 bug 修一次全租户受益，插件 bug 修一个插件版本，分支 bug 只修一家。

> 🔑 铁律：**能用配置解决的绝不动扩展点，能用扩展点解决的绝不拉分支。**

这条判据不是“便宜优先”，是**责任边界优先**：配置错误有兜底，服务端校验不通过就拒绝写入，一处修好全部租户受益；分支错误没有兜底，没人能同时看懂 N 条分支，每条分支都靠“当初做它的那个人”维护，而人会离职、会转岗。

### 什么时候必须拉分支：极少数例外

| 例外条件 | 为什么只能拉分支 | 前提 |
|---|---|---|
| 私有化部署 + 客户机房 + 版本冻结 | 升级由客户自己排期，你无法替他决定运行版本 | 合同写明升级责任与冻结期限 |
| 强监管测评后冻结版本 | 等保/行业测评后 12–24 个月内代码不能动 | 客户书面确认冻结范围 |
| 客户按年付费买专属版本 | 客户买的是“不被别人的需求影响”，不是功能 | 合同期 ≥24 个月且差异面 ≥30% 代码 |

拉分支的代价可以直接算：上游每季度 12 个要移植的补丁，1/3/5 条分支每季度就是 12/36/60 次 backport，按每次 0.5 人日（经验上）折合 6/18/30 人日，回归矩阵按分支数翻倍。这还没算“合并回主干”：分支存活 6 个月后，合并成本通常超过重写这一段（经验上），于是分支只能一直活下去，直到客户不续费。**分支一旦拉到第二条，就回不到一条产品线**——扩展点可以下线，分支只能等客户走。

> 💡 我的判断是：分支不是“定制手段”，而是“退出策略”——拉分支等于宣布这个客户从产品里摘出去、按项目养。没准备好养一条产品线（专属测试、值班、发布、安全响应），就不要拉。真要做，先留一份 [58.1 ADR 实践](../../L5-工程效能/58-架构治理/58.1-ADR实践.md)，写清退出条件。

## 配置也要被治理，否则它只是把分支换了个地方

把定制从分支挪进配置，不是把“代码复制”变成“零成本”，而是变成“**数据复制**”：配置本身就是一份有 schema、有版本、有审计、有回滚路径的契约，没人治理就会把分支债换一种形态还回来。

### 先分级，再谈“灵活”

| 层 | 典型项 | 谁能改 | 变更频率 | 审计要求 |
|---|---|---|---|---|
| 平台默认 | 超时、重试、数据保留期 | 研发 | 随发布 | 代码评审 |
| 套餐 | 配额、功能开关、SLA 档位 | 产品运营 | 月度 | 审批 + 变更单 |
| 租户 | 地域、SSO、品牌、通知模板 | 客户管理员 | 周 | 高风险项双人复核 |
| 用户 | 时区、语言、通知偏好 | 终端用户 | 随时 | 操作日志 |

“谁能改”本质是权限问题（见 [49.4 多租户权限模型](../49-身份与访问管理/49.4-多租户权限模型.md)），这张表只回答“这一项落在哪一层”。层级判断错了，后面的校验、审计、回滚全白做：把“数据保留期”放在用户层，等于让终端用户决定公司的合规边界。

平台级配置项要有**预算**：经验上 80 项是还能靠人维护的量级，过百就要评审；每项必须回答默认值、谁能改、怎么回滚，答不出来就不许加。配置项数量付的是“逐项排除税”——排查“这个租户为什么不一样”最坏要逐项排除 n 项，每项 2 分钟，80 项约 2.7 小时、200 项约 6.7 小时。

组合数上界不在这里算——开关组合爆炸的主场是 [55.2 特性开关](../../L5-工程效能/55-发布与回滚/55.2-特性开关.md)，这里只留一个结论：**配置项数量本身就是支持成本，和代码行数一样要设预算**。

### schema 与校验：失败必须拒绝，不能回落默认

服务端 schema 至少五类校验：类型、枚举、范围、跨字段依赖、引用资源存在性。比“校验什么”更关键的是**失败之后怎么办**：

> ⚠️ 校验失败必须**拒绝写入**（fail-closed），绝不能回落默认值。

回落默认会把错误藏起来：地域写成 `eu-west`，系统静默回落成 `cn`，数据进了错误地域，三个月后做数据驻留审计才发现；SSO 配置写错，系统忽略这一项继续跑，安全策略静默降级，没人报警。前端校验不算数——直连 API 能绕过，规则还会写三遍。

### 四级继承：平台默认 → 套餐 → 租户 → 用户

| 配置项 | 生效值 | 来源层 |
|---|---|---|
| region | eu | 租户（T1042） |
| timeout_s | 120 | 用户（u7） |
| sso | true | 套餐（pro） |
| sso_meta | https://idp.example.com | 套餐（pro） |
| retention_days | 90 | 平台默认 |

实现只有两个要点。第一，**“未设置”和“设为空”必须能区分**（未设置 / 显式空 / 有值三态，Go 里用指针或 `optional`），否则套餐层想显式清空平台默认值时做不到。第二，**必须能追踪来源层**——客服排查“这个客户的超时为什么是 120 秒”，要一眼看到是用户 u7 覆盖的。四层 `map` 逐层覆盖并记下来源层，再对生效值跑五类校验（类型、枚举、范围、跨字段、资源存在性），失败即拒绝落库。完整程序在 `.cache/t65/65.4/config/main.go`，`go run` 实测（`go1.27.1 darwin/arm64`，原始输出在 `.cache/t65/65.4/config-output.txt`）：

```text
② 校验（fail-closed：失败就拒绝落库，不回落平台默认）
   拒绝: region="eu-west" 不在枚举 {cn,eu,us}
   拒绝: timeout_s=600 越界 [1,300]
   拒绝: sso=true 但缺 sso_meta（跨字段依赖）
```

### 变更审计、回滚与生效延迟

配置写库只追加、不删除：每次写入生成一个 revision，存 **diff + 操作者 + 原因 + 审批单号**；回滚不是删历史，而是用旧 revision 的值生成新 revision。审计要能回答：谁、何时、对哪个租户、把哪项从什么改成什么、为什么（五要素见 [3.5 审计与取证](../../需求/3-行业合规与外部约束/3.5-审计与取证.md)）。配置的特殊性在于**爆炸半径按租户算**：同一变更对 A 是修 bug，对 B 可能是事故，所以回滚分三档——单租户、一批租户（套餐或灰度分组）、单个配置项（紧急 kill-switch）。

配置从“写入”到“所有实例生效”是分钟级，不是瞬时（推还是拉、缓存 TTL 怎么设，见 [48.1 配置中心](../48-配置与协调/48.1-配置中心.md)）。所以要有**生效状态**（`pending → applied`，变更后 N 分钟未全量生效就告警并阻断后续变更），还要有**漂移检测**：定时把“期望配置快照”与实例实际生效值比对。经验上配置事故里相当一部分不是“改错了”，而是“改对了没生效”——实例没收到推送、缓存过期策略不一致、老实例漏在灰度池外。

## 版本矩阵：三个轴，一个乘积

### 三个轴各是什么

| 轴 | 是什么 | 变化节奏 | 作用域 | 谁负责 |
|---|---|---|---|---|
| **P 平台版本** | 应用代码/镜像的发布版本 | 季度 minor | 每个环境一套 | 平台团队 |
| **C 租户配置版本** | 租户配置文档的 schema 版本（`config_version`） | 季度 | 每租户一个 | 平台团队 |
| **D 数据模型版本** | 库 schema 版本（表/列/索引的状态） | 随发布 | 共享库全环境 1–2 个并存；独立库租户可各自滞后 | DBA + 平台 |

平台版本号怎么排、CHANGELOG 怎么写，见 [51.3 语义化版本与变更日志](../../L5-工程效能/51-版本与协作/51.3-语义化版本与变更日志.md)，这里不重复 semver 规则。要强调的是：**三个轴是三份不同的兼容承诺**——平台版本回答“代码什么样”，配置版本回答“这家租户的数据结构什么样”，数据模型版本回答“库里的列和索引什么样”。同一个平台版本上可以跑 30 种配置形态，这正是“平台版本号相同却行为不同”的来源。

### 组合数是上界，不是待验证集合

名义乘积是 `|P| × |C| × |D|`，但它不是要验证的集合，因为**不是所有组合都可达**：旧平台的代码读不了新配置（新版配置项随新平台发布，每个平台版本有一个 **C 上限**），平台也只认识其绑定范围内的数据模型（Expand-Contract 期间只并存相邻两版，每个平台版本有一个 **D 区间**）。真正要验证的是可达组合 `Σ over 支持窗口内的每个平台版本 ( C上限(P) × D区间宽度(P) )`。程序骨架如下（纯标准库，完整版在 `.cache/t65/65.4/matrix/main.go`）：

```go
type platform struct {
	cfgCap, dmFloor, dmCeil int // C 上限、D 区间下界、D 区间上界
}

func reachable(ps []platform) int {
	n := 0
	for _, p := range ps {
		n += p.cfgCap * (p.dmCeil - p.dmFloor + 1)
	}
	return n
}

// P0 最新 / P1 上一版 / P2 上上版 / P3 窗口外：新平台认识全部历史配置版本
full := []platform{
	{30, 5, 6}, {12, 4, 5}, {4, 3, 4}, {2, 2, 3},
}
// 窗口长度 N 从 1 扫到 4：打印名义组合、可达组合、全测工时
```

本机实测（`go1.27.1 darwin/arm64`，原始输出在 `.cache/t65/65.4/matrix-output.txt`）：

```text
输入：平台一年 4 个 minor（季度发布），支持窗口 N=3，配置版本 |C|=30，数据模型版本 |D|=6，单组合验证 25 分钟

① 支持窗口长度 → 组合数（名义乘积 vs 可达组合）
N   在线P   名义 |P|×|C|×|D|   可达组合   占比      全测工时
1   1         180                60     33.3%     25.0h
2   2         360                84     23.3%     35.0h
3   3         540                92     17.0%     38.3h
4   4         720                96     13.3%     40.0h

② 治理前：|P|×|C|×|D| 与可达组合
   名义乘积 = 3 × 30 × 6 = 540
   平台版本      C 上限   D 范围     该版本组合数
   P0 最新           30    v5..v6       60
   P1 上一版          12    v4..v5       24
   P2 上上版           4    v3..v4        8
   可达组合 = 92（名义乘积的 17.0%），全测工时 = 38.3h ≈ 4.8 人日

③ 配置版本 30 → 8 之后
   可达组合 92 → 40，少 52 个组合
   全测工时 38.3h → 16.7h，省 21.7h ≈ 2.7 人日
```

三个读数值得停下来看。**其一，83% 的组合根本不可达**：540 / 92 ≈ 5.9，按名义乘积报预算会为不存在的组合多付近 5 倍成本。**其二，配置版本的长尾成本压在新平台上**：最新平台要认识全部 30 个版本（它还服务着没迁移完的租户），上一版只认识 12 个、上上版 4 个——**每发一个新平台版本，它就要多背一批历史配置的兼容代码**，拖得越久越贵；治理的收益也集中在新平台：30→8 让组合 92→40，省 21.7 小时 ≈ 2.7 人日/次发布。**配置治理不是清理垃圾，是给下一个平台版本减负。** **其三，窗口从 3 加到 4，组合只从 92 涨到 96**：组合数成本是**饱和**的；但老版本继续跑还要兼容代码不删、补丁 backport、排障分版本，这些随窗口**线性**增长——窗口要算两笔账，组合（饱和）+ 老版本存活（线性），后者是大头。

### 支持窗口：窗口长度、EOL、强制升级

窗口长度直接决定客户能滞后多久：N=1 只容一个发布周期（60 个可达组合），N=2 约 6 个月（84 个），N=3 约 9 个月（92 个），N=4 约 12 个月（96 个，适合大客户/合规客户）。N=3 是经验上的平衡点（我的判断）：覆盖客户季度变更窗口与一次审计周期，又不让兼容代码无限堆积。窗口再宽，多出来的不是客户满意度，是你替客户保管旧版本的义务。

> 🔑 铁律：**支持窗口是合同条款，不是测试排期表。** 测试计划里写“支持 N-1”、合同里什么都没写，等于给了一个无限期的口头承诺——客户滞后三年时，你既没有拒付依据，也没有加价理由。

四个条款必须写进合同：

| 条款 | 建议写法 | 不写会怎样 |
|---|---|---|
| 支持窗口 | 最近 3 个 minor（约 9 个月）内提供修复与兼容 | 客户滞后 3 年仍被要求支持，成本无法收回 |
| EOL 公告 | 版本退出前至少 90 天书面通知 | 客户说“没收到通知”，升级变成违约 |
| 强制升级 | 窗口关闭前 30 天平台可安排升级，客户配合提供变更窗口 | 客户无限期拖延，老版本永远在线 |
| 超窗/冻结版本 | 超窗支持按人日计费；冻结版本单独立项报价，不并入标准产品线 | 一个客户冻结，整个发布火车被拖慢 |

### 版本组合 → 测试策略

可达组合也不是全测。按**爆炸半径**分层：

| 组合类型 | 例子 | 策略 | 频率 |
|---|---|---|---|
| 契约跨越组合（平台 × 数据模型边界） | 最新平台 × 最新/上一版 D | 全测 | 每次发布 |
| 高爆炸半径租户所在组合 | 合规客户、最大客户在用的 P/C/D | 全测 | 每次发布 |
| 中间平台版本 × 高频配置版本 | P1 × C 的前 3 个版本 | 抽样 1/3 | 每次发布 |
| 最老支持版本 | P2 | 核心路径冒烟（登录/计费/关键写路径） | 每次发布 |
| 窗口外组合 | P3 及更老 | 不测，合同不承诺 | — |

代入算例：全测 6 个组合（3 个平台版本 × 2 个数据模型边界）= 2.5 小时，其余 86 个抽样 1/3 ≈ 28 个 ≈ 11.7 小时，每次发布回归 ≈ 14.2 小时——比可达组合全测的 38.3 小时压掉 63%，比名义乘积的 225 小时（540 × 25 分钟）压掉 94%。**策略的价值不在测得少，而在把预算花在真正会炸的组合上。**

> 💡 我的判断是：版本矩阵的正确用法不是“测遍所有组合”，而是**把组合数当成本，反推窗口宽度与价格**。每季度生成一次“在线版本清单”（各 P/C/D 版本 × 租户数 × EOL 日期），每行都要有 owner 和清零计划。这张清单也是谈判底牌：客户问“能不能再支持半年”，你能当场报价。组合与窗口定下来之后，按租户分批放量的做法见 [65.5 租户级灰度发布](65.5-租户级灰度发布.md)。

## 租户滞后升级：允许，但要定价

### 为什么必须允许滞后

- 客户的变更管理有排期：季度变更窗口、CAB 审批，不是你说升就升；
- 合规冻结：测评/审计期间系统不能动；
- 上游依赖：客户的 ERP 脚本、自建报表按旧 API 字段写死了；
- 采购与预算周期：升级要客户内部立项。

一刀切强制升级，省下的是测试费，付出的是合同违约、大客户流失、客服工单暴涨。滞后不是客户不配合，是**客户的变更节奏天生比你慢**。

### 滞后的代价

后端要同时兼容旧前端与旧 API 契约（判据见 [55.5 向后兼容](../../L5-工程效能/55-发布与回滚/55.5-向后兼容.md)）；兼容代码不能删，新平台越背越重；监控排障按版本打标，一个问题先问“哪个平台版本 + 哪个配置版本 + 哪个数据模型版本”；测试矩阵不为 1。这些代价必须被定价，否则就是全体客户在补贴滞后客户。

### 用契约版本判兼容，不用平台版本号

平台版本号是**发布单元**，不是兼容单位。兼容性由每个契约面独立决定：

| 契约面 | 版本载体 | 兼容判据 | 谁承诺 |
|---|---|---|---|
| API | 路径版本（`/v1`）或请求头版本 | 已发布契约只增不改；字段弃用走两段式 | 平台 |
| 事件 | 消息体里的 `schema_version` | 消费方 tolerant reader：能读新旧两版 | 平台 + 消费方 |
| 数据库列 | migration 版本号 | Expand-Contract 期间不删列、不收紧约束 | 平台 + DBA |
| 租户配置 | `config_version` | 旧平台拒绝读新配置（fail-closed），迁移链只前进 | 平台 |
| 前端静态资源 | 资源 hash / index 版本 | 旧前端能调通新 API | 平台 |

事件 schema 的演进规则在 [31.4 事件 Schema 演进](../../L2-架构风格/31-事件驱动/31.4-事件Schema演进.md)，服务多版本共存的兼容判据在 [30.6 服务版本与兼容](../../L2-架构风格/30-微服务/30.6-服务版本与兼容.md)。结论一条：**用平台版本号判兼容会出两种错**——平台升了但契约没变，误判成破坏性变更；契约变了但平台号没变（配置 schema 先行发布），漏判成兼容，上线才发现老代码读不了新配置。

### 弃用流程：给时间表，不给突然死亡

弃用按时间表走：D-90 发公告，用日志标出旧调用量、找出还在调的租户；D-30 一对一通知、给出豁免名单；D-0 关闭旧契约并返回明确的升级错误（410 + 提示），不是 404/500；D+ 复盘剩余调用，把豁免名单写进合同的“冻结版本”附件。判据：**旧调用量不归零就不许关**。

## 配置 schema 的版本化与迁移

租户配置是库里的数据，不是重新部署就能换结构。平台必须能同时读多版本配置，否则一次配置结构变更 = 全租户停机迁移。

机制是 **`config_version` + 单向迁移链**：

1. 每个租户的配置文档带 `config_version`，迁移链 v1→v2→v3 每一步只做一件事；
2. **幂等可重入**：“检查再改”（字段不存在才补），重跑结果一致；
3. **失败停链**：任何一步无法自动迁移，原配置不动、进人工队列，绝不写半成品；
4. **先 dry-run 再落库**：迁移结果先过目标版本 schema 校验，通过才写；
5. **留迁移记录**：租户 ID、from/to、触发者（发布/人工/后台任务）、结果、耗时。

```go
// 迁移链：每一步返回新配置 + 本步说明；返回 nil 表示停链
var chain = []migrator{
	{1, 2, func(c kv) (kv, string) {
		n := clone(c)
		rename := map[string]string{"cn-north": "cn", "eu-west": "eu"}
		if r, ok := rename[c["region"].(string)]; ok {
			n["region"] = r
		}
		if s, ok := c["timeout_s"].(string); ok { // v1 里是字符串
			var f float64
			fmt.Sscanf(s, "%f", &f)
			n["timeout_s"] = f
		}
		return n, "region 重命名 + timeout_s 转数字"
	}},
	{2, 3, func(c kv) (kv, string) {
		n := clone(c)
		if _, ok := n["retention_days"]; !ok {
			n["retention_days"] = 90.0 // 只补默认值，不覆盖已有值
		}
		return n, "新增 retention_days=90"
	}},
}
```

本机实测（`go1.27.1 darwin/arm64`，原始输出在 `.cache/t65/65.4/config-output.txt`）：

```text
③ config_version 迁移链（v1 → v3）
   T1042 原始 v1: region=cn-north timeout_s=45(string)
   v1→v2: region 重命名映射 + timeout_s 字符串转数字 + 补 sso=false
   v2→v3: 新增 retention_days=90（默认值，不覆盖已有值）
   迁移结果 v3: region=cn timeout_s=45(float64) sso=false retention_days=90
   校验: 通过

   T2211 迁移停链: v1→v2 无法自动迁移：region="xx" 没有映射规则，停链
   已执行步骤数: 0 → 原配置不动，进人工迁移队列

④ 旧平台遇到新配置：拒绝加载，不猜默认值（fail-closed）
   平台认识 config_version ≤ 2，租户是 v3 → 返回错误、租户留在旧平台
```

第 ④ 条是整节收口：**旧平台遇到新 `config_version` 必须拒绝加载**，不能“尽力解析”、不能回落默认——尽力解析的后果是 `sso=true` 被忽略（安全降级）、计费单位回默认（少收钱），还没有任何报警。这也解释了每个平台版本为什么都有 C 上限：那是代码的认知边界，不是人为设的。

### 租户自定义字段的 schema 演进

自定义字段是最容易失控的扩展点：它改的是**数据模型**，不是行为。

| 变更 | 风险 | 做法 |
|---|---|---|
| 加可选字段 | 低 | 给默认值；老租户懒迁移（首次写回时升版本） |
| 加必填字段 | 中 | 不能直接加；先可选 + 回填 + 收紧校验（两次发布） |
| 改类型 | 高 | 双写影子字段、读时兼容、回填后切读、旧字段弃用（Expand-Contract 思路，见 [55.4 数据库变更管理](../../L5-工程效能/55-发布与回滚/55.4-数据库变更管理.md)） |
| 删字段 | 中 | 先停止写入（弃用）→ 观察一个发布周期 → 再删存储 |
| 枚举加值 | 低但危险 | 消费方遇到未知值必须降级而不是崩溃（见 [31.4 事件 Schema 演进](../../L2-架构风格/31-事件驱动/31.4-事件Schema演进.md)） |

迁移链会随每次平台发布越接越长。链到十几节时，“每次读配置都跑一遍迁移函数”变成性能问题；这时改成“存储层已迁移 + 运行时只兼容最近 2 版”，迁移链只用于离线迁移与审计回溯。

## 什么时候别做扩展点

扩展点不是免费的抽象。年化成本 = 契约设计与维护 + 每个插件联调回归 + 契约版本协调 + 故障排查（SPI 怎么设计，见 [37.8 微内核与插件化](../../L3-质量属性/37-扩展性/37.8-微内核与插件化.md)）；收益 = 被复用的定制次数 × 单次定制成本。**客户数 < 20 且需求差异 < 20% 代码面时，抽象成本大于它省下的定制成本**，先用“人工配置 + 排期”顶住。

| 客户数 | 需求差异 | 建议 |
|---|---|---|
| < 20 | < 20% 代码面 | 不做扩展点；人工配置 + 排期，把需求写进路线图 |
| < 20 | 同一类差异出现 ≥3 次 | 先做最小 SPI（只抽这一处，不设计通用框架） |
| 20–100 | 有 2 类以上重复需求 | 做扩展点：一个明确 SPI + 契约版本号 |
| > 100 | 需求持续发散 | 扩展点 + 开放平台/插件市场（见 [47.7 开放平台与API生态](../47-网关与入口/47.7-开放平台与API生态.md)） |

经验上，一个 SPI 要经历 3 个真实插件才算稳定；两个样本就抽象，第 3 个插件大概率推翻契约，返工比不抽象更贵。该问的不是“将来会不会有更多插件”，而是“**现在是否已经有 3 个真实需求在等同一个契约**”——够不上这个门槛，就先别用扩展点。

## 反模式

| 反模式 | 后果 |
|---|---|
| 给大客户拉长期分支 | 补丁 backport 拖欠，分支变成第二产品，合并成本随存活时间上升 |
| 配置项只加不删、无 owner | 配置面膨胀，无人说得清某项为什么是这个值；事故只能逐项排除 |
| 校验失败回落默认值 | 错误被藏起来：地域写错回落 cn、SSO 配置失效被静默忽略 |
| 用平台版本号判兼容 | 平台升了契约没变时误判破坏性；契约变了平台号没变时漏判 |
| 支持窗口只写进测试计划 | 客户滞后三年仍被要求支持，成本无法收回，合同里没有拒付依据 |
| 按名义乘积做测试预算 | 为永远不可达的组合设计兼容分支，预算虚高数倍，真正的可达组合反而没测 |

## 自检

**Q1** 三种定制形态的判据是什么？“配置优先”到底在省什么钱？

▸ 答案：判据不是价格，是**责任边界**。值不同→配置（平台校验兜底）；行为不同但语义可复用→扩展点（平台保契约，插件自己演进）；语义都不同且合同买断，才考虑分支。配置优先省的不是开发工时，是**修复的批量性**：配置 bug 一次修所有租户，分支 bug 只能修一家。把“配置优先”当教条的人会硬塞行为差异，最后配置里长出 if-else。

**Q2** `|P|×|C|×|D|` 为什么不能直接当测试矩阵？可达组合怎么算？

▸ 答案：乘积是上界。可达组合要按兼容规则过滤：每个平台版本能读的配置 schema 有上限（旧代码读不了新配置），能读的数据模型有区间（Expand-Contract 只并存相邻两版）。算例里名义 `3×30×6=540`，可达只有 92（17%）。按 540 排预算会多付近 5 倍成本，还漏掉真正在线的组合。算法是**从平台版本往下过滤**，不是从乘积往下抽样。

**Q3** 支持窗口写进合同要写哪几项？

▸ 答案：四件事：窗口长度（如最近 3 个 minor ≈ 9 个月）、EOL 公告期（90 天书面通知）、强制升级条款（窗口关闭前 30 天可安排升级）、超窗与冻结版本的报价。少写一项，窗口就只是工程侧的自我约束，客户侧没有义务。

**Q4** 滞后升级时为什么不能用平台版本号判兼容？

▸ 答案：平台版本号是发布单元，兼容性由每个契约面独立决定：API 路径版本、事件 `schema_version`、DB migration 版本、`config_version`。平台升了但契约没变，会误判成破坏性变更、白留兼容分支；契约变了但平台号没变（配置 schema 先行发布），会漏判成兼容，上线才发现老代码读不了新配置。

**Q5** 配置迁移链为什么必须可重入、失败要停链？

▸ 答案：迁移会在发布、人工修数、后台任务里被重复触发；不可重入的脚本重复加字段、重复转类型，第二次跑就破坏数据。停链是因为半新半旧的配置**没有任何一版代码能正确读**——宁可让租户留在旧版本并进人工队列，也不写半成品。标准：同一份输入连跑两遍，输出与校验结果一致。

**Q6** 什么数字条件下不该做扩展点？

▸ 答案：客户数 <20 且需求差异 <20% 代码面时，抽象成本高于定制成本，先用人工配置 + 排期。同一类差异出现 ≥3 次才做最小 SPI；经验上一个 SPI 要 3 个真实插件才稳定。客户数会涨、判据要重估，但用两个样本设计通用契约，几乎一定被第三个推倒。
