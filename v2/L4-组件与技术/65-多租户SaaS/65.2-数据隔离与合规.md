# 65.2 数据隔离与合规

## 一句话

> 合规在 SaaS 里不是"写一堆制度"，而是**把合同里的承诺做成可执行的租户级操作**——能按租户导出、能按租户删除（含备份与派生数据）、能按租户恢复、能证明谁动过；四件事做不到，合规条款就是空话。

## 先破除五个误区

| 误区 | 现实 |
|---|---|
| 合规 = 加密 + 一份隐私政策 | 加密只覆盖"存储被拖库"；客户验收看的是**导出、删除、恢复、审计**能否按租户执行并留证 |
| 删了主库的行就算删除 | 备份、CDC 下游、缓存、搜索索引、对象存储、数仓、训练集都还有副本，主库 `DELETE` 只处理一层 |
| 共享表带 `tenant_id` 就隔离了 | `tenant_id` 防的是读写串号（见 [49.4 多租户权限模型](../49-身份与访问管理/49.4-多租户权限模型.md)），管不了删除与恢复的租户粒度 |
| 备份必须留着，所以删除权做不到 | 两条正路：等备份过期并把保留期写进删除证明；或每租户一把密钥，销毁密钥让历史密文永久不可解 |
| 数据存在境内就不算出境 | 判定看"谁、从哪里、能读到什么"：境外客服**读一次**就是跨境访问 |

## 四个动词：把合同条款翻译成系统能力

合同与法规里的话是法律语言，落到系统只有四个动词：**导出、删除、恢复、审计**。再加一条贯穿全部动作的约束：**数据驻留**。

| 合同/法规里的说法 | 系统里必须存在的能力 | 可验收的完成判据 |
|---|---|---|
| 访问权 / 数据可携带 | 按租户全量导出，结构化且机器可读 | 导出任务 ID + 清单 + 校验和；重跑结果逐字节一致 |
| 被遗忘权 / 删除权 | 按租户级联删除，覆盖主库、派生、下游、备份 | 删除任务 ID + 各存储删除回执 + 备份保留期说明 |
| 服务连续性 / 误删恢复 | 按租户时间点恢复 | 演练记录：单租户 RTO、临时资源、对生产影响 |
| 全程可追溯 / 审计权 | 带 `tenant_id` 的审计 + 平台跨租户操作留痕 | 审计能按租户过滤；平台操作 100% 有记录、有工单号 |
| 数据驻留 | 租户 → region 映射与 fail-closed 路由 | 能证明该租户数据未被所选 region 之外的主体读取 |

> ⚠️ 四个动词的主语都是**租户**，不是库、不是表。共享表的物理边界比租户粗，每个动词都要回答"怎么把范围缩小到一个租户"。

> 🔑 合规能力的最小可交付不是文档，而是**三条能按租户重放的作业流水线**（导出、删除、恢复）加一份按租户可查的审计；没有任务 ID 和回执的"已完成"等于没做。

## 先有数据地图，再谈导出与删除

导出和删除都要回答同一个问题：**这个租户的数据分布在几个存储里？** 答案必须是一张登记表，不能是某个人的记忆。

```sql
-- 可抄：数据资产登记表（放配置库，CI 里校验"新存储必须登记"）
CREATE TABLE data_asset (
  asset_id       TEXT PRIMARY KEY,   -- users.email / s3-avatars / es-users
  name           TEXT NOT NULL,      -- 人可读名
  store          TEXT NOT NULL,      -- mysql-orders / s3-avatars / es-users / kafka-cdc / warehouse
  tenant_key     TEXT NOT NULL,      -- 按什么分租户：tenant_id / 桶前缀 / 索引字段
  contains_pii   BOOLEAN NOT NULL,
  encrypted      BOOLEAN NOT NULL,   -- 是否在 crypto-shredding 覆盖范围内
  retention_days INT,
  export_rule    TEXT NOT NULL,      -- include / mask / exclude
  delete_rule    TEXT NOT NULL,      -- hard / crypto_shred / anonymize / retain
  owner          TEXT NOT NULL
);
```

三条使用规则：

1. **新存储不登记就不许上线**：把"`data_asset` 有对应行"做成接入检查项。
2. `contains_pii` 沿用[38.5 数据分级与脱敏](../../L3-质量属性/38-安全/38.5-数据分级与脱敏.md)的四级分级；`export_rule=mask` 用它给的六种脱敏手段；`delete_rule` 只有四个合法值：硬删、销毁密钥、匿名化、依法保留。

> 💡 我的判断是：数据地图不要一上来就做自动血缘平台。先用一张手工维护的表，每接入一种存储加一行，成本约半天；自动血缘是二期，一期靠代码评审和上线检查卡住——它在跨云、自建、SaaS 混用时准确率远低于宣传。

## 按租户导出：边界、格式与断点续传

导出最容易被低估的是**边界**：客户说"导出我的全部数据"，法务理解的是"个人信息"，工程交付的却常只是主库几张表。

| 数据类别 | 例子 | 是否导出 | 怎么导 |
|---|---|---|---|
| 主库业务行 | 订单、客户、配置 | 是 | 按 `tenant_id` 游标分页 |
| 文件对象 | 头像、合同 PDF | 是 | 对象存储按 `/{tenant}/` 前缀打包 + 清单 |
| 派生数据 | 搜索索引、推荐特征 | 不导原件 | 导"可由主数据重建"的说明与脚本 |
| 日志与审计 | 访问日志、审计事件 | 按合同 | 按 `tenant_id` + 时间窗查询 |
| 加密字段 | 手机号、证件号 | 是，默认脱敏 | 明文导出需二次授权与审计 |
| 密钥材料 | DEK / KEK | 否 | 拒绝并记录 |

格式上只有两种选择，适用面不同：

| 维度 | 一次性打包（ZIP/Parquet + manifest） | 分页 API（游标） |
|---|---|---|
| 适用数据量 | 数十 GB 以内 | 任意，客户端按游标拉 |
| 交付方式 | 预签名 URL，24–72 小时过期 | OAuth2 + 游标 |
| 幂等键 | `(tenant_id, export_id)` 唯一 | `(tenant_id, cursor)` 无状态 |
| 断点续传 | 按 part 续，manifest 记录已完成 part | 天然按游标续 |
| 举证能力 | 清单 + 校验和，适合给客户 | 需额外审计证明"导了哪些" |

建议：**大客户用一次性打包，集成方用分页 API**，共用同一个分页内核。

分页内核必须是 keyset（`WHERE tenant_id=? AND id > ? ORDER BY id LIMIT ?`），不是 offset，并且开口就固定快照上限 `MAX(id)`：

```sql
-- 每页一条，last_id 来自上一页最后一行；snapshot_max 是开始导出时取的 MAX(id)
SELECT id, body FROM t WHERE tenant_id = ? AND id > ? AND id <= ? ORDER BY id LIMIT 5000;
```

下面这组真实输出验证了断点续传、重投幂等与 offset 漂移（本机 `go1.27.1 darwin/arm64`，纯标准库；程序与原始输出在 `.cache/t65/65.2/export/`）：

```text
环境：纯标准库；租户 t-001 共 12347 行，每页 5000 行，快照上限 maxID=12347
全量 part1 rows=5000  sha256[:8]=d579a9e6e9c76953 lastID=5000
全量 part2 rows=5000  sha256[:8]=0ac9165f28ca5074 lastID=10000
全量 part3 rows=2347  sha256[:8]=28da184021032be9 lastID=12347

中断于 part2 后，从 lastID=10000 续传：rows=2347 sha256[:8]=28da184021032be9 与全量 part3 一致=true
同一分页请求重投两次 sha256[:8]=28da184021032be9 / 28da184021032be9 一致=true（接收端按 (export_id,part) 覆盖写，不会翻倍）

导出期间回填 3 行（12347 → 12350 行）
offset 分页重取 part3：重复行=3、漏行=0（回填行把游标往后挤）

```

中断续传靠 manifest 里的 `last_id`（每页记 `(part_no, rows, sha256, last_id)`）；重投靠 `(export_id, part_no)` 覆盖写实现幂等；offset 在有回填时实测重复 3 行，keyset 重复与漏行都是 0。

## 按租户删除：五层清单与删除证明

`DELETE FROM users WHERE tenant_id='t-002'` 只是删掉了五层里的第一层。用 SQLite 跑一遍就能看到"备份里还有"：

```bash
sqlite3 :memory: "CREATE TABLE u(tenant TEXT,uid TEXT); INSERT INTO u VALUES('t-001','u1'),('t-002','u2'),('t-002','u3'); CREATE TABLE bak AS SELECT * FROM u; DELETE FROM u WHERE tenant='t-002'; SELECT '主库='||count(*) FROM u WHERE tenant='t-002'; SELECT '备份副本='||count(*) FROM bak WHERE tenant='t-002';"
```

```text
主库=0
备份副本=2
```

级联删除必须按五层清：

| 层 | 存什么 | 删除动作 | 可验收的确认 |
|---|---|---|---|
| L1 主库 | 业务行、关联表 | 按 `tenant_id` 事务删，关联表按依赖顺序，软删最终硬删 | 行数为 0 + 删除任务 ID |
| L2 派生存储 | 缓存、搜索索引、对象存储、MQ 积压 | 按租户键/前缀删；MQ 按租户分区、消费端跳过 | 各存储返回"已删/不存在" |
| L3 下游副本 | CDC 目标、数仓、报表、特征库、训练集 | 下游按 `tenant_id` 删；数仓按租户分区重建 | 下游回执（表/分区/行数） |
| L4 备份与快照 | 全量备份、PITR 归档、冷归档 | 到期自然过期并记录保留期；或在加密字段上销毁密钥 | 保留期说明 +（可选）密钥销毁记录 |
| L5 日志 | 应用日志、访问日志、审计日志 | PII 字段脱敏/轮转；审计按法规保留（留存与到期删除见[46.6 数据生命周期](../../L4-组件与技术/46-数据架构/46.6-数据生命周期.md)） | 留存策略 + 抽样验证 |

删除证明不是一句"已删除"，而是一份能同时交给客户和监管的作业记录：

```json
{
  "delete_task_id": "del-20261120-t002", "tenant_id": "t-002",
  "stores": [
    {"asset": "users", "action": "hard_delete", "rows": 1284, "evidence": "binlog mysql-bin.0007:88123"},
    {"asset": "s3-avatars", "action": "prefix_delete", "objects": 93},
    {"asset": "es-users", "action": "delete_by_query", "docs": 1284},
    {"asset": "warehouse.dim_user", "action": "partition_rebuild", "partitions": 3}
  ],
  "backup": {"policy": "保留 35 天", "mode": "crypto_shred", "dek_destroyed_at": "2026-11-20T03:02:11Z"},
  "status": "verified", "verified_by": ["ops-a", "compliance-b"]
}
```

> ⚠️ 最容易漏的是 **L3 下游**：数仓里一张宽表、特征库里一份训练样本，往往是"删除任务显示成功"之后客户还能查到的数据。下游算不算"处理者"、能不能要求它删，口径见[3.2 个人信息保护与 GDPR](../../需求/3-行业合规与外部约束/3.2-个人信息保护与GDPR.md)；工程上先做到"能通知、能收确认"。

## crypto-shredding：删密钥，而不是删字节

备份里的数据删不掉，除非它从一开始就是密文，而密钥可以单独销毁。这就是 envelope encryption 在合规上的真正用途：**KEK（KMS/HSM，平台级，不导出）包裹每租户的 DEK（32 字节），DEK 加密该租户的敏感字段**；删除租户 = 删掉 DEK 的包裹记录（并在 KMS 销毁），历史密文（含备份）随之永久不可解。

Go 标准库就能实现核心：`crypto/aes` + `cipher.NewGCM`（32 字节密钥 = AES-256，12 字节 nonce，16 字节 tag），`crypto/rand` 取随机 nonce。以下是真实运行的程序节选（完整文件在 `.cache/t65/65.2/shred/main.go`）：

```go
// 每租户一把 DEK；KEK 只负责包裹 DEK，不直接加密业务数据
func mustGCM(key []byte) cipher.AEAD {
	block, _ := aes.NewCipher(key)
	g, _ := cipher.NewGCM(block)
	return g
}

// seal: nonce(12B) || ciphertext || tag(16B)；nonce 每次新取，绝不复用
func seal(g cipher.AEAD, plain, aad []byte) []byte {
	nonce := make([]byte, g.NonceSize())
	rand.Read(nonce)
	return g.Seal(nonce, nonce, plain, aad)
}

// 解密与之对称：g.Open(nil, blob[:12], blob[12:], aad)；tag 校验失败即返回错误
```

删租户只有两步：清零内存里的 DEK、删除被 KEK 包裹的记录（`victim.wrapped = nil`）——密文留在原地，从此不可解。

真实输出（本机 `go1.27.1 darwin/arm64`，AES-256-GCM）：

```text
租户     DEK 指纹(sha256前8)   包裹后长度        状态
t-001  90c6ba96957995c9   60           active
t-002  96df10d50e6ca390   60           active
t-003  595b396a4ad3e367   60           active

-- 对 t-002 执行 crypto-shredding：DEK 清零 + 删除包裹记录 --
读 t-002 加密列      → 失败：cipher: message authentication failed
读 t-002 未加密金额  → 成功：300（加密边界之外的数据没被删）
解密破坏前的备份密文 → 失败：cipher: message authentication failed（备份里的密文一起失效）
读 t-001 加密列      → 成功：alice@a.example（密钥隔离 = 爆炸半径单租户）
t-001 密文配错 AAD   → 失败：cipher: message authentication failed
```

这段输出证明三件事：**备份里的密文随密钥一起失效**（销毁后同样解不开，备份保留期不再是删除承诺的障碍）；**爆炸半径是单租户**（t-001 照常解密）；**AAD 绑定租户**（附加认证数据是 `tenant_id | 字段路径`，配错租户也解不开）。未加密的金额列仍可读——加密边界就是删除边界。

nonce 管理只有一条铁律：**同一 DEK 下 nonce 绝不复用**。GCM 对 nonce 复用不会报错，但密钥流重复会让两段密文的异或直接等于两段明文的异或，实测：

```text
-- nonce 复用实验（同一 key、同一 12B nonce）--
C1 xor C2 = 00000000000000080909
P1 xor P2 = 00000000000000080909
两者相等 = true（密钥流重复，攻击者由 C1 xor C2 直接得到 P1 xor P2，GCM 不报警）
```

用随机 12 字节 nonce 时，10 亿条记录的单密钥碰撞概率约 `n² / 2^97 = (10^9)² / (2 × 2^96) ≈ 6.3 × 10^-12`（生日界，算式可自己验），工程上可接受；但**绝不能把 nonce 写死或按计数器手工分配**，计数器在多实例并发下必然重复。KEK 的轮换、托管与吊销见[13.4 密钥与凭证管理](../../L0-运行时底座/13-基础设施安全/13.4-密钥与凭证管理.md)。

适用边界必须写进设计文档，缺一条都会在审计时被问住：

| 限制 | 事实 | 应对 |
|---|---|---|
| 只覆盖加密字段 | 未加密列、索引键、搜索倒排、排序结果仍是明文 | 敏感字段全走加密列；索引只放不可逆摘要或分桶值（口径见 [38.5 数据分级与脱敏](../../L3-质量属性/38-安全/38.5-数据分级与脱敏.md)） |
| 密钥销毁不可逆 | 删错租户就是永久丢失，备份也救不回 | 双人复核 + 冷静期（KMS 延迟删除窗口，例如 7 天）+ 操作审计 |
| 密钥服务是单点 | KMS 不可用时该租户加密字段全读不出 | KMS 可用性目标高于业务库；降级方案单独设计 |
| 物理删除口径 | 部分监管/客户要求"数据被物理擦除" | 合同写清"通过销毁密钥实现不可恢复"；拿不准时按[3.3 数据出境与数据主权](../../需求/3-行业合规与外部约束/3.3-数据出境与数据主权.md)同级的保守口径书面确认 |

与逐存储物理删除比：删 2.3 TB 按 200 MB/s 算约 3.35 小时（算式 `2.3 × 1024 × 1024 MB ÷ 200 MB/s ≈ 12 060 秒`），还要协调下游；crypto-shredding 只删一条密钥记录，毫秒级，写路径多一次加解密，代价是**不可逆**。

> 💡 我的判断是：crypto-shredding 的价值不在"删得快"，而在**把备份里的数据从"删不掉"变成"可承诺删除"**。共享表 + 备份保留 35 天 + 客户要求 30 天彻底删除，这三者不加 crypto-shredding 是数学上矛盾的；加了之后，删除承诺收敛成"销毁一把密钥"这一件可验证、可审计、毫秒级完成的事。

## 按租户恢复：PITR 的单租户粒度

PITR（时间点恢复）在共享表架构里是**整实例**动作：把全量备份恢复到某个时刻，再重放 WAL/binlog 到目标时间点；它没有"只回放 t-002"的开关，因为所有租户的日志混在一条流里。

| 路径 | 做法 | 恢复 1 个租户的 RTO（约） | 需要的存储 | 对生产影响 | 前提 |
|---|---|---|---|---|---|
| 临时实例 + 按租户抽取 | 整库恢复到临时实例，按 `tenant_id` 抽出导回生产 | 1 TiB 库：87.4 分钟恢复 + 30–60 分钟抽取校验，约 2 小时 | 1 套临时实例 + 1 倍库大小的副本 | 无（读备份） | 有 PITR 归档，能起临时实例 |
| 逻辑导出 + 回放 | 按 `tenant_id` 过滤 binlog/CDC 重放 | 分钟到小时，取决于事件量 | 目标库 + 归档日志 | 写回生产有冲突风险 | 事件带 `tenant_id`、可重放 |
| 事件溯源重建 | 从事件流重建该租户状态 | 分钟级 | 事件存储 | 只适合事实源是事件的系统 | 事件是唯一事实源 |
| 独立库整库恢复 | 恢复到新实例、改路由（见 [65.1 租户隔离模型](65.1-租户隔离模型.md)） | 分钟级 | 1 个实例 | 路由切换，无数据合并 | 已按租户独立部署 |

两个细节：

- **恢复点之后的新数据会丢**：恢复到"错误发生前 1 秒"，该租户在这之后产生的合法数据也不在恢复点里，要么停写，要么把这 1 秒到现在的增量按租户重放补回。
- **恢复演练要按租户做**：整库演练只证明"备份能用"，证明不了"单个租户 2 小时内能回来"；按[10.4 快照与备份](../../L0-运行时底座/10-存储基础设施/10.4-快照与备份.md)的 RTO 公式逐段计时。

共享库独立 schema 形态介于中间：抽取边界是 schema，成本量级见[65.1 租户隔离模型](65.1-租户隔离模型.md)。

> 🔑 这正是**独立库在合规场景真正值钱的地方**：共享表下恢复一个租户要搬整个库，独立库下恢复一个租户就是"恢复到新实例、切路由"。隔离形态选型（见[65.1 租户隔离模型](65.1-租户隔离模型.md)）平时看不出差别，在"单租户恢复到某一刻"上差一个数量级。

## 按租户审计：让"谁动过我的数据"可查

审计五要素（谁、何时、对什么、做了什么、结果如何）的主场在[3.5 审计与取证](../../需求/3-行业合规与外部约束/3.5-审计与取证.md)，这里只补三件多租户特有的事：

1. **每条审计事件必须带 `tenant_id`**，服务端从上下文取、不接受客户端传入（与[49.4 多租户权限模型](../49-身份与访问管理/49.4-多租户权限模型.md)的"租户只从令牌来"同一原则）。
2. **平台侧跨租户操作必须 100% 留痕**：客服查数据、运维导出、跑批修数据，都要记操作人、目标租户、动作、工单号；没有工单号的跨租户操作直接拒绝。
3. **租户可见性**：客户控制台要能查"本租户最近谁访问/导出/删除了数据"。审计库按 `(tenant_id, ts)` 建索引，对外只返回本租户记录，过滤逻辑复用 49.4 的租户一致性校验。

可证明隔离的**证据链**是两层拼起来的：审计事件回答"谁、何时、动了哪个租户的什么"，操作回执回答"动了多少、结果如何"（任务 ID、校验和、下游确认）。只有审计没有回执，说明不了数据真删了；只有回执没有审计，说明不了谁授权的。

审计日志本身也是数据：PII 字段按[38.5 数据分级与脱敏](../../L3-质量属性/38-安全/38.5-数据分级与脱敏.md)脱敏入库；留存期常见要求不少于 6 个月（口径以[3.5 审计与取证](../../需求/3-行业合规与外部约束/3.5-审计与取证.md)为准），到期删除同样走五层清单。

## 数据驻留：租户级的地域选择

同一个 SaaS 里，A 客户要求数据留在境内、B 客户要求留在欧盟，方案不是"部署两套系统"，而是**一张租户到 region 的映射表加一层路由**。它与隔离形态相关：共享池租户只能按 region 分池，只有独立库/独立部署才做得到"一租户一 region"。

| 方案 | 数据位置 | 跨境风险 | 成本 | 适用 |
|---|---|---|---|---|
| 单 region 服务全部租户 | 一处 | 高：驻留合同直接违约 | 最低 | 客户全在同地 |
| region 分池（共享池按 region） | 每 region 一组共享池 | 中：租户不能跨池 | 约按 region 数线性增加 | 区域型 SaaS |
| 租户独立 region | 一租户一 region | 低 | 最高 | 大客户、强驻留行业 |

落地要点：

- **`tenant_region(tenant_id, region, residency_class)` 是路由的唯一依据**：连接池、对象存储桶、备份目标、分析任务都按它选；找不到映射时 fail closed，**不默认落主 region**。
- **"读到"就构成访问**：境外客服打开含手机号的工单、海外 BI 跑一次报表，都是跨境访问。判定口径与三条路径见[3.3 数据出境与数据主权](../../需求/3-行业合规与外部约束/3.3-数据出境与数据主权.md)；工程上要么给境外坐席脱敏视图，要么把分析任务放到 region 内。
- **迁 region 是一次新的出境**：从 A region 迁到 B region 等于重走一遍出境判定，不能"点一下迁移"就算完。
- **备份与分析必须在 region 内闭环**：备份跨 region 复制、数仓集中到总部，都会让"数据只留在境内"失效。

## 什么时候别做

客户少于 10 家、全部境内小微、没有敏感个人信息时，crypto-shredding（KMS + 每租户 DEK + 双人复核 + 冷静期）与单租户恢复（临时实例 + 演练）的工程量远超收益。过渡方案是把承诺降级并写进合同：

| 你的情况 | 建议的合规动作 |
|---|---|
| 少于 10 租户、境内、无敏感个人信息 | 先做导出与审计；删除用"删除任务 + 人工核验"，合同写清删除 SLA（如主库 24h、备份随保留期过期） |
| 有敏感个人信息或跨境合同 | 敏感字段上 envelope + crypto-shredding；恢复演练做到单租户 |
| 金融 / 医疗 / 等保三级 | 独立库或独立 region + crypto-shredding + 双人复核 + 完整删除证明 |
| 超过 1000 租户的共享池 | 导出、删除、恢复必须自动化流水线，人工核验不可扩展 |

> ⚠️ 过渡不等于不承诺：只删主库、备份里继续留着，却在合同里写"彻底删除"，是本节后果最重的一条。写不出删除 SLA 时，宁可写"备份保留 35 天，到期后不可恢复"，也不要写"立即彻底删除"。

## 反模式

| 反模式 | 后果 |
|---|---|
| 用 `DELETE ... WHERE tenant_id=?` 当删除完成 | 备份、CDC、缓存、数仓仍有副本，客户复核时直接失信 |
| 导出用 offset 分页 | 导出期间有写入就重复或漏行，交付数据对不上账 |
| 认为"数据存境内 = 没有出境" | 境外客服或分析读一次就构成跨境访问，合同违约 |
| 恢复演练只做整库 | 真出事时不知道单租户要多久，RTO 承诺无法兑现 |
| 所有租户共用一把密钥 | crypto-shredding 退化成全量重加密，删一个租户要重写全部数据 |
| 密钥与备份放同一个账号或同一个 KMS | 拿到备份即拿到密钥，加密与不加密没区别 |

## 自检

**Q1** 客户合同写"30 天内彻底删除全部数据"，而共享表架构的备份保留 35 天。你怎么做到？

▸ 答案：拆两条：① 主库、派生、下游 30 天内逐层删并留回执；② 敏感字段从写入起就是密文、密钥存 KMS，销毁 DEK 后历史备份的密文永久不可解，备份文件等 35 天过期。删除证明写"各存储回执 + 密钥销毁时间 + 备份保留期"。只做①做不到。

**Q2** crypto-shredding 能删干净吗？哪些东西它删不掉，为什么？

▸ 答案：只删"加密字段 + 密钥"这条链。删不掉：未加密列与索引键、对象元数据、日志里已落盘的明文、第三方下游留存的副本。它必须与逐存储删除配合；边界就看数据地图的 `encrypted` 列，false 的资产它无效。

**Q3** 为什么导出要用 keyset 而不是 offset？`snapshotMax` 又解决什么？

▸ 答案：offset 的游标是"数过的行数"，导出期间有回填或插入，后面的页就整体错位——实测回填 3 行造成 3 行重复。keyset 按"上一页最后一个 id"定位不受影响；但它会带进导出开始后新写入的 id，所以要记 `MAX(id)` 并加 `id <= snapshotMax`。

**Q4** 共享表下"把 t-002 恢复到昨天 14:00"为什么难？三条路各自代价是什么？

▸ 答案：PITR 是整实例回放，所有租户日志混在一条流里，没有单租户开关。① 整库恢复到临时实例再按 `tenant_id` 抽出，RTO 小时级、要 1 倍库大小临时存储，对生产无影响；② 过滤 binlog/CDC 重放，分钟到小时，需事件带租户且写回有冲突；③ 事件溯源重建，分钟级，需事件是唯一事实源。独立库直接切路由。

**Q5** 数据存在境内，境外客服查一次工单，算不算数据出境？

▸ 答案：算跨境访问。判定看"谁、从哪里、能读到什么"，不看存储位置。工程上要么给境外坐席脱敏视图，要么把功能放到 region 内；合规路径按[3.3 数据出境与数据主权](../../需求/3-行业合规与外部约束/3.3-数据出境与数据主权.md)判定，不能因为"只是读一下"就跳过。

**Q6** 什么情况下不该上 crypto-shredding 与单租户恢复？

▸ 答案：租户少于 10 家、全境内、无敏感个人信息时，KMS + 每租户 DEK + 双人复核 + 冷静期 + 临时实例演练的工程量远超收益。先用"删除任务 + 人工核验 + 备份到期过期"，合同写清删除 SLA；出现敏感信息、跨境合同或强监管行业时再补。
