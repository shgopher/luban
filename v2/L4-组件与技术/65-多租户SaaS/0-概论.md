# 第 65 章 多租户 SaaS · 概论

## 一句话

> 多租户 SaaS 的全部难度来自同一个约束——**一套系统同时服务互不信任的多家客户**。五节就是在这个约束下依次回答五个问题：数据放哪（[65.1](65.1-租户隔离模型.md)）、合规怎么证明（[65.2](65.2-数据隔离与合规.md)）、钱怎么收（[65.3](65.3-计费与配额.md)）、差异怎么沉（[65.4](65.4-定制化与版本管理.md)）、变更怎么放（[65.5](65.5-租户级灰度发布.md)）。前三节是**底线**，做错会泄漏、过不了审计、收错钱；后两节是**寿命**，做错会让系统随客户数线性变慢、随版本数指数变贵。

## 5 分钟入门：先记住这 10 个词

| 词 | 一句话解释 | 生活类比 |
|---|---|---|
| **租户 (tenant)** | 逻辑上独立的一个客户组织，是计费、隔离、审计的共同单位 | 写字楼里的一家公司 |
| **池化 (pooled)** | 多个租户共用同一套库表，靠 `tenant_id` 区分 | 合租房，共用厨房但要分清谁的锅 |
| **单开 (silo)** | 一个租户独占一套库/实例 | 独栋别墅，贵但不吵 |
| **爆炸半径** | 一处 bug、一次故障、一条错误 SQL 能波及多少租户 | 燃气总阀装在几层 |
| **租户路由** | 请求进来先确定"这个请求去哪个库/schema" | 前台查你在几楼 |
| **数据驻留** | 某租户的数据必须存在哪个国家/地域 | 房产证上的地址 |
| **crypto-shredding** | 销毁该租户的密钥，等于让它的密文永久不可解——删除的一种实现 | 把保险箱的钥匙熔了 |
| **计量 (metering)** | 记录"用了多少"，只增不改 | 水电表 |
| **配额 (quota)** | 一个账期内累计用量的上限 | 手机套餐的流量包 |
| **版本矩阵** | 平台版本 × 租户配置版本 × 数据模型版本的乘积 | 同时卖几个年款的车 |

> 记住：**租户是单位、路由是入口、密钥是底盘**。隔离、合规、计费三件事都挂在这三个词上。

        ▼

        ▼

        │             （版本矩阵的组合数决定升级成本）

        │             （租户内不分流、schema 不能按租户改）

## 本章要解决的 12 个真问题

| 问题 | 在哪一节 | 一句话答案 |
|---|---|---|
| 独立库最安全，是不是就该选它？ | [65.1](65.1-租户隔离模型.md) | 不是；隔离度是买来的，先算爆炸半径与单位成本 |
| 共享表加个 `tenant_id` 就够了吗？ | [65.1](65.1-租户隔离模型.md) | 不够；路由层、连接池、备份粒度会更早撑不住 |
| 什么时候该把一个客户"迁出去"单开？ | [65.1](65.1-租户隔离模型.md) | 合规要求、单租户流量/故障占比、数据量，任一越线 |
| 客户要求"删除我的数据"，删完就完了吗？ | [65.2](65.2-数据隔离与合规.md) | 没完；备份、索引、缓存、日志、数仓里都还有 |
| 备份能不能只恢复一个租户？ | [65.2](65.2-数据隔离与合规.md) | 共享表下几乎不能；这正是独立库真正值钱的地方 |
| 每租户一把密钥，除了加密还有别的用？ | [65.2](65.2-数据隔离与合规.md) | 有；销毁密钥即删除，备份里的密文一起作废 |
| 用量记录重复、迟到、乱序怎么办？ | [65.3](65.3-计费与配额.md) | 幂等键 + 两个时间戳 + 封账期 + 补账 |
| 配额和限流是不是一回事？ | [65.3](65.3-计费与配额.md) | 不是；账期累计 vs 瞬时速率，判定位置与超限行为都不同 |
| 为什么"先查配额再扣"一定超卖？ | [65.3](65.3-计费与配额.md) | 查与扣之间有并发窗口，必须原子预扣 + 失败补偿 |
| 大客户要定制，能不能给他拉个分支？ | [65.4](65.4-定制化与版本管理.md) | 能配置别开扩展点，能开扩展点别拉分支；分支成本是永久的双份 |
| 为什么版本一多，升级就突然变难？ | [65.4](65.4-定制化与版本管理.md) | 要验证的是版本**组合数**，不是版本**个数** |
| 能不能只让一部分用户先看到新版本？ | [65.5](65.5-租户级灰度发布.md) | 多租户下不行；同一个租户的数据必须同一版本 |

## 3 个最常见误解

| 误区 | 现实 |
|---|---|
| "多租户就是每张表加个 `tenant_id`" | 加列是 [65.1](65.1-租户隔离模型.md) 里最便宜的一行代码；真正的工作在路由、缓存、消息、备份、计费五处都要带租户，漏一处就是事故 |
| "隔离做得越重越安全" | 隔离成本随租户数**线性**上涨（实例数、连接数、备份任务数），过度隔离会吃掉全部毛利，还换不来合规认可——合规要的是**可证明**的操作，不是"看起来分开了" |
| "SaaS 的难点在功能要做得比别人多" | 功能多是需求问题；多租户的难点是"同一份代码同时服务 N 个客户"这个**约束**——它让每个决定都要乘上客户数 |

## 读完自检（入门级 3 题）

**Q1** 一个 SaaS 只有一个客户，还需要做多租户设计吗？

▸ 答案：看**未来 12 个月的客户数预期**，而不是看当下。只有一个客户时，池化（共享表 + `tenant_id`）的额外成本几乎为零，而且它把"以后加客户"变成加一行数据；反过来，如果现在就按单租户写死（一个客户一套部署），以后每加一个客户就要多一次部署与备份任务。真正不能提前做的是"独立库/独立实例"这类重隔离——它要等有客户愿意付费买隔离时再做。

**Q2** 为什么说"数据放哪"（[65.1](65.1-租户隔离模型.md)）比"权限怎么判"（[49.4](../49-身份与访问管理/49.4-多租户权限模型.md)）更早要定？

▸ 答案：因为隔离形态是**结构决定**，权限是**逐次判定**。隔离形态一旦定了，路由层、备份策略、恢复粒度、密钥体系都跟着定，改一次要大动；权限可以随接口逐步加严，代价小得多。而且两者是互补而不是替代：隔离只决定"漏了会炸多大"，不决定"会不会漏"——共享表下把权限做对也能活，独立库下权限做错照样越权。

**Q3** 为什么"隔离可证明"这件事不能靠架构图来证明？

▸ 答案：架构图证明的是"设计上分开了"，合规和客户要的是"**操作上分开了**"：给定一个租户 ID，能导出它的全部数据、能删除它（含备份与派生数据）、能只恢复它、能列出谁动过它。这四件事都是可执行、可留痕、可复现的操作。没有这四件事，架构图画得再干净，合规审计一问"你怎么证明 A 客户的数据不在 B 客户的备份里"就答不上来。
