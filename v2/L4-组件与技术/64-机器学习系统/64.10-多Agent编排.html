                      64.10 多 Agent 编排：subagent、agent teams 与终端编排

                      一句话

                      单个上下文窗口装不下的任务才需要拆：拆的目的只有两个——把中间产物关在子窗口里、让互不依赖的工作并行；而并行一旦发生，真正的底座不是更强的模型，是「共享任务记录 + 每个 agent 一个 git worktree」。

                      来源：《AI 时代的软件工程》第 33 章（原文 (opens new window)）。文中 star 数、工具数等为原文快照，未独立复现。

                      单个 agent 内部也有编排：计划、任务列表、走查文档。这里往外走一层：一个上下文窗口装不下的任务，怎么让多个 agent 分头做。

                      先破除误区：按「岗位」拆 agent 为什么成批失败

                      「多 agent」最流行的讲法是照搬公司组织：一个产品经理 agent、一个架构师 agent、一个测试 agent，互传文档。这条路在实践里成批失败。

                      误区 现实
                      给 agent 分配人类岗位，就获得了专业分工 角色是人类的分工方式；LLM 没有职业壁垒，同一个模型既能写 PRD 又能写代码
                      上游把结论交给下游，链路就成立 传的是结论，丢的是推理过程；下游只能信，不能验
                      每个 agent 各自正确，整体就正确 错误出在接缝：局部正确的结论拼起来会漂移
                      用共享文档同步状态 单向交接没有「谁做过什么」的历史，接手者只能重做

                      🔑 活下来的分工不靠头衔，靠共享任务记录：谁做了什么随时追加，接手的 agent 读完整历史，再接下一段。头衔不承载状态，记录才承载。

                      两个动机，一个约束

                      动机 解决什么 代价
                      上下文隔离 让子 agent 去读 3000 行代码、跑测试、翻文档，海量中间产物留在它自己的窗口，主会话只收结论 要设计任务边界、结果格式、失败回传
                      并行 互不依赖的工作单元同时开工，例如同时审查五个模块 多个 agent 同时改一个工作区会互相踩

                      🔑 行业对「互相踩」的答案已经统一：git worktree。每个 agent 一份独立工作目录、一个独立分支，在文件系统层面先隔离开。这一条后来成了整个行业的标准配置。

                      OpenAI 在 Harness Engineering 实践里反复强调第一条：主会话的上下文窗口是稀缺资源，不要拿它装搜索结果和测试日志。

                      三层编排：Claude Code 的演进

                      Claude Code 把编排拆成三层，一层比一层重。

                      层 怎么定义 上下文与回传 协调方式 适用
                      Subagent 项目 .claude/agents/ 下一个 markdown：职责、思维规则、输出格式 独立窗口；干完只把结果带回主线程 主 agent 集中派发 单一、独立的子任务
                      Agent Teams 一个会话当 lead；若干 teammate 是独立 Claude Code 实例 各自独立，不汇总 共享任务列表，成员可直连 多层面、需要讨论
                      Dynamic Workflows 整个编排写成一段 JavaScript，交给独立运行时 结果收在脚本变量里，主上下文只留最终答案 代码里的循环、分支、收集 几十上百并行、流程可固化

                      Subagent：能力即文件

                      • 定义就是一个 markdown 文件，可进 git、可团队共享，和 skill 是同一思路：能力即文件（1.6 AI 辅助需求流水线 里的 Skill 就是这套做法）。
                      • 社区最流行的例子之一，是七个 subagent 文件配研究员、编辑、项目经理这类角色；注意角色只是提示词包装，真正起作用的是边界、输出格式和共享记录。
                      • 子 agent 只向主 agent 报告，不与其他 agent 通信。

                      Agent Teams：共享任务列表 + 成员直连

                      • 2026 年年中上线，早期要开实验开关。
                      • lead 负责拆任务、分配、收尾；teammate 是独立实例，各有各的上下文窗口。
                      • 所有成员共享一个任务列表：谁领了什么、做到哪一步，一目了然。
                      • 成员之间可以直接通信，不必事事经过 lead。
                      • 观察方式：tmux 或 iTerm2 分屏，一个队友的终端摊开一格。
                      • 两个控制开关：delegate mode 把主 agent 限制成只协调、不写代码；plan approval 让 lead 在队友动手前先审计划。

                      Dynamic Workflows：编排者从模型换成代码

                      • 2026 年 5 月底随 Opus 4.8 发布的研究预览。
                      • 针对前两层的共同瓶颈：编排者始终是 Claude 本身，每个子 agent 的结果都要回到它的上下文窗口，协调几十上百个并行任务时装不下。
                      • 解法：Claude 把整个编排过程写成 JavaScript，循环、分支、中间结果收集都固化在代码里，交给独立运行时执行。

                      “工作流把计划搬进代码。用 subagent 和 skill 时，编排者是 Claude 自己；工作流脚本自己握住循环、分支和中间结果，Claude 的上下文里只留最终答案。” —— Anthropic，《Orchestrate subagents at scale with dynamic workflows》

                      标志性案例：Bun 作者 Jarred Sumner 用它 11 天把 Bun 运行时从 Zig 迁到 Rust，75 万行代码，99.8% 的原有测试通过。

                      🔑 三层的本质差别是编排者站在哪：subagent 由主 agent 派活，teams 由共享任务列表调度，workflow 由代码调度。编排逻辑从提示词搬进定义文件，再搬进可执行代码。

                      Codex：subagent + worktree + 无头

                      OpenAI 记录过一次实验：3 个工程师、5 个月、零行手写代码，做出约 100 万行的生产产品，合并约 1500 个 PR；人只描述任务、审 PR、给反馈，单人吞吐 3.5 PR/天，单次任务经常无人值守跑 6 小时以上。

                      支撑它的是三个能力：

                      能力 作用 缺了会怎样
                      Subagents 为并行子任务派生 child agent，每个有隔离的上下文 主上下文被中间产物淹没
                      Worktrees 每个任务一个独立 git worktree、独立分支 并行 agent 互相覆盖，冲突排查吃掉收益
                      无头模式 codex exec 在 CI/CD 里跑，不进交互界面 无法无人值守，无法接流水线

                      ⚠️ worktree 只隔离文件系统冲突，不隔离语义冲突：两个 agent 改同一个接口的两侧，合并时照样炸。worktree 让并行成为可能，不保证并行结果正确。

                      OpenCode：agent 写进配置文件

                      OpenCode 最透明：agent 是配置。定义写在 opencode.json 或 markdown 文件里，mode 三选一。

                      mode 含义
                      primary 主会话可用
                      subagent 只能被 Task 工具调用
                      all 两者都行

                      内置三个 subagent：

                      内置 定位 权限
                      general 通用代理，可并行多个实例干多步任务 完整工具
                      Explore 只读探索：找文件、搜关键字、答代码库问题 不能改文件
                      Scout 只读研究外部文档与依赖，例如把依赖仓库克隆到托管缓存里对照源码 不能改文件

                      两个值得抄的细节：

                      • 每个 agent 单独指定 model：主 agent 挂强模型，子 agent 挂便宜快速的模型，成本立刻分化。
                      • hidden: true：把 subagent 从 @ 自动补全里藏起来，用户在界面上点不到，只允许其他 agent 通过 Task 工具程序化调用。权限也按 agent 单独配。

                      🔑 子 agent 的模型选择按任务定，不按层级定：机械的搜索/摘要用便宜模型，需要判断的探索用强模型。用错模型是编排里最贵的浪费。

                      终端编排：从底座到地图

                      CLI 内置的编排覆盖不到一种场景：你想同时跑三五个、十几个 agent，各领各的任务。这时要终端编排工具。

                      工具 定位 关键能力 边界
                      tmux 底座（2007 年） 一个 server 托所有会话；断线 detach，回来 reattach；窗口随便分屏 认识 pane，不认识 agent：哪个 pane 在等人，它没有任何表示
                      herdr 会看 agent 的运行时（Rust，40.8k star） 后台 server 拥有终端；关客户端、断 SSH 照跑；重启恢复布局；pane 标 working/blocked/idle 不包装也不替换 Claude Code、Codex、Cursor、OpenCode，只当终端房东
                      luvus 任务控制台（Rust，2026 年 6 月） pane 管理之上加 token/成本/上下文占用、Git/GitHub 面板、worktree、依赖任务、任务队列、路径租约、质量门、合并 新工具，生态与稳定性待时间验证
                      awesome-agent-orchestrators 地图（2k star） 7 大类 + Resting（停止维护）：终端并行 agent、桌面与 Web、Multi-Agent Swarms、自主循环 Runner、自主任务 Runner、基础设施原语、个人助理；网站版收录 221 个工具 清单不是选型结论，月月新增

                      tmux 的局限，正是 herdr 的入口

                      • tmux 的模型：一个 server 托着所有会话，断线随时 detach，回来一条命令 reattach，现场原样；窗口里随便分屏。
                      • 这一领域的工具几乎都长在它上面：claude-squad 的每个实例是一个 tmux 会话，orchestrators 清单里一串工具的名字里都带 mux。
                      • tmux 唯一的问题：它认识 pane，不认识 agent。哪个 pane 里的 agent 停下来等人，它不会告诉你。

                      herdr：agent-native 的运行时

                      • 自我定位一句话：the runtime your coding agents live on。
                      • 后台 server 拥有 agent 的终端：关掉客户端、断掉 SSH，里面的终端照跑；机器重启后恢复布局，受支持的 agent 会话还能接回去。
                      • ctrl+b q 离开，敲一下 herdr 回来。
                      • 每个 pane 标着 working、blocked、idle：agent 停下来要答案，herdr 直接告诉你，不用挨个 pane 找。
                      • 真正的差异在 agent-native：agent 自己通过 CLI 和 socket API 驱动 herdr，自己开 pane、互相发 prompt，等另一个 agent 真的 blocked 才继续。
                      • 生态：手机端 collie、macOS 控制台 herdrm、审查侧栏 herdr-reviewr。

                      luvus：把任务队列和质量门管起来

                      • 除终端 pane 管理和 agent 状态感知（连 token、成本、上下文占用都显示）外，还有 Git、GitHub 面板。
                      • 编排要用的东西也装了进来：建 worktree、管依赖任务、任务队列和路径租约按项目隔离、给 agent 派活、跑质量门、合并成品。
                      • Commander 从底部输入框向指定的几个 agent pane 群发 prompt。
                      • Claude、Codex、Grok 的会话可以带着完整上下文 fork 出一份。
                      • 接口层是 UHP（Universal Harness Protocol）：方法注册表带版本号，别人可以在上面造自己的编排器。

                      选型：先问「谁需要知道谁卡住了」

                      你的情况 选什么 理由
                      一个独立子任务，只嫌主上下文脏 subagent 拆完就回收，不需要额外基础设施
                      多层面任务，成员要互相讨论 agent teams 共享任务列表 + 直连，避免 lead 成瓶颈
                      几十上百个并行单元，流程能写死 dynamic workflow 编排进代码，主上下文只留结果
                      同时盯 3–15 个会话，要知道谁 blocked herdr / luvus pane 级状态与任务队列
                      只需要并行开发，不要统一 UI git worktree + 自己的 CI 最便宜的隔离，不引入新工具
                      团队要选型，不知道有什么 awesome-agent-orchestrators 先看地图再试，别从零造

                      ⚠️ 一个 agent 能干完的活不要拆。拆分要维护任务边界、结果格式、失败回传和合并评审，这些开销超过并行收益时，多 agent 是负优化。

                      落地：worktree + tmux 的最小起手式

                      实测环境：Alpine 3.20 / tmux 3.4 / git 2.45.4（arm64 容器）。下面命令假设当前目录是一个已有提交的 git 仓库。

                      # 每个 agent 一个目录 + 一个分支；同一起点，互不影响
for a in a b c; do
  git worktree add "../wt-$a" -b "agent/$a"

  # 每个 agent 一个会话，工作目录就是它的 worktree；-d 不占当前终端
  tmux new-session -d -s "agent-$a" -c "$PWD/../wt-$a"
done

# 看谁在哪、在哪个分支、在哪个会话
git worktree list
tmux list-sessions -F '#{session_name} (#{session_windows} window)'

                      实测输出（节选）：

                      agent-a (1 window)
agent-b (1 window)
agent-c (1 window)
/tmp/agent-orchestration/repo  c15ebdb [main]
/tmp/agent-orchestration/wt-a  c15ebdb [agent/a]

                      tmux 只能告诉你 pane 里跑的是什么进程，不能告诉你 agent 在干什么：

                      agent-a | /tmp/agent-orchestration/wt-a | sleep
agent-b | /tmp/agent-orchestration/wt-b | sleep
agent-c | /tmp/agent-orchestration/wt-c | bash

                      完整代码在仓库 tools/examples/64.10-agent-orchestration/，docker build + docker run --rm 两条命令可复现以上输出。

                      • working 与 blocked 的 pane 命令都是 sleep：一个在跑长任务、一个在等审批，从 pane 分不出来。状态得由 agent 自己上报，或在 tmux 之上加一层（herdr 那类）。
                      • 会话由 server 托管：创建脚本退出后再查，0 个客户端，3 个会话仍在；关掉客户端不等于杀掉终端。
                      • git worktree remove 只删工作目录，分支保留；要一并删，再 git branch -D agent/a。
                      • 超过 10 个 worktree 时给它们单独放一个父目录，并按任务编号命名，否则很快认不出谁是谁。

                      术语澄清：三种「编排」不是一回事

                      说法 编排对象 在哪 关键区别
                      服务编排（28.4） 服务调用顺序 运行时 谁调谁、超时、补偿
                      事件编排 vs 协同（31.3） 事件消费者之间的控制流 架构 中心指挥，还是各自响应
                      agent 编排（本节） 多个 LLM 会话 开发时 上下文、任务记录、worktree

                      反模式

                      反模式 后果
                      用岗位头衔当分工 传结论丢推理，局部正确整体漂移
                      多个 agent 共用一个工作区 互相覆盖，冲突排查成本高于并行收益
                      子 agent 结果只回主上下文，不写共享记录 主会话一压缩，历史就没了，接手的 agent 重做
                      没有步数与预算上限就并行 token 账单和失败重试一起放大
                      把 pane 数量当吞吐 12 个 pane 里 9 个在等审批，等于没并行
                      编排逻辑停留在提示词里 循环和分支每次靠模型即兴，不可复现
                      为并行而并行 拆分与合并的开销超过任务本身

                      自检

                      Q1 照搬公司岗位拆 agent，最先坏在哪一环？

                      ▸ 答案：坏在交接：岗位分工本身不是问题，问题是单向交接只传结论、丢推理，下游无法验证，错误在接缝处累积。改用共享任务记录，让接手者读完整历史，才修掉这个接缝。

                      Q2 subagent 与 agent teams 的本质差别是「结果是否汇总」还是「成员能否直连」？

                      ▸ 答案：两者都是表象，本质是协调结构。subagent 是主 agent 的私有子程序：主 agent 派活、收结果，子 agent 彼此不可见。agent teams 是共享任务列表上的多个平等 worker：成员可直连，lead 只做协调。前者适合一个独立子任务，后者适合需要讨论的多层面任务。

                      Q3 dynamic workflows 到底解决了 subagent 的什么瓶颈？

                      ▸ 答案：解决编排者自身的上下文瓶颈。subagent 和 teams 里，所有子结果最终都要回到编排者的窗口，几十上百个并行就装不下。workflow 把循环、分支、中间结果搬进脚本，主上下文只留最终答案，于是并行规模不再受编排者窗口限制。

                      Q4 两个 agent 并行改代码，worktree 能避免什么、不能避免什么？

                      ▸ 答案：能避免工作区与分支冲突：各自目录、各自分支，互不覆盖。不能避免语义冲突：两边改同一个接口、同一份契约，合并时仍会冲突。所以 worktree 之后仍要代码评审、测试和合并门禁。

                      Q5 为什么子 agent 更适合挂便宜模型，而主 agent 适合挂强模型？

                      ▸ 答案：因为两者做的事不同。主 agent 负责拆任务、判断、整合结果，判断错会放大到全部子任务；子 agent 通常执行边界明确、可验证的活（搜索、摘要、按格式实现），便宜模型够用。但这条不是铁律：需要探索和取舍的子任务（如 Explore / Scout）仍应挂强模型。

                      Q6 tmux 和 herdr 的差别，用一句话说清是什么？

                      ▸ 答案：tmux 认识 pane，herdr 认识 agent。tmux 能保住会话和分屏，但不知道某个 pane 里的 agent 是在干活还是在等你回答；herdr 的 pane 带 working/blocked/idle 状态，且终端由后台 server 持有，断 SSH、重启都能恢复。

                      Q7 什么情况下不该拆多 agent？

                      ▸ 答案：任务小、边界不清、共享状态多、合并成本高于并行收益时都不该拆。典型信号是：拆完还要花大量时间对齐结果格式、处理重复劳动、反复合并冲突。先用单 agent 加任务列表跑通，再按瓶颈拆。
